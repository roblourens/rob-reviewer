# Performance review: agentHost: offer skills of runtime plugins waiting for session start

[PR #349326](https://github.com/microsoft/vscode/pull/349326) at `087f93a7c4d286be85c765295f2c9dad96679d83`

## Findings (1)

### 1. [medium] Reuse the database across pending-plugin completion requests

**Finding ID:** `PERF-58347A4FA797`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSkillCompletionProvider.ts:103</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** SQLite connections, filesystem mkdir/statfs or realpath calls, journal/schema setup queries, metadata reads, and full-cache JSON parsing  
**Scaling:** One cache read per completion request, shared across all eligible servers—not one per server. Sequential requests after the previous reference is released reopen the database when no runtime or other consumer holds it; overlapping requests share connection initialization but still issue separate metadata reads and parse the entire cache. Parsing scales with all cached skill entries, including unrelated servers.  
**Outcome:** Repeated filesystem/database initialization delays slash suggestions and all other completion-provider results, with additional I/O and parsing work while typing.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** For the same session with no other eligible undiscovered MCP servers, the published-disabled pending plugins were excluded and no MCP-cache database read/open occurred. Existing top-level or settled-plugin fallback reads are not the regression being reported.  
**Changed behavior:** Slash completion requests in an unstarted session with only pending-plugin MCP declarations now read the session database on every request, even when the cache is absent or the typed slash matches only a local skill.  
**Confidence:** 0.94 — The changed enablement gate, parsed pending MCP declarations, one-read-per-request grouping, immediate reference disposal, repeated connection setup without a resident runtime, and completion critical path are traced in code. Exact storage latency and how many installations declare MCP servers are unmeasured; other eligible undiscovered servers or an independently held DB reference can reduce the incremental cost.

**Causal diff evidence:** The replaced gate at line 103 now calls isSkillContainerEnabled, which returns the intended enablement for Loading runtime plugins without effectiveEnabled. Previously their published enablement was false, so their MCP children could not make undiscoveredServers nonempty. With an enabled pending plugin containing an undiscovered MCP server, the changed gate now reaches the awaited readMcpSkillCache at line 111.

In a new or restored session whose runtime has not started, an installed enabled plugin declaring an MCP server with children undefined now causes every slash-prefix update to await database access. With no resident session holding the database warm, even an empty cache repeatedly incurs connection and filesystem setup; slow or network-backed profile storage makes suggestions noticeably slower.

**Evidence:** CopilotAgent.\_readRuntimePlugins (12863–12881) publishes parsed MCP declarations under Loading plugins with effectiveEnabled absent and enabled:false. makeMcpServerCustomization (pluginParsers.ts:451–459) leaves children undefined, and resolveCustomizationEnablement resolves child enablement independently of the pending parent. \_getCandidates gathers all such servers then awaits one readMcpSkillCache before returning even the already-built local candidates. readMcpSkillCache (shared/mcpSkillCache.ts:58–69) acquires and immediately disposes a DB reference on every call, with no positive, negative, or in-flight read cache. SessionDataService destroys the database at the last release (41–54); SessionDatabase.\_ensureDb (686–715) performs mkdir, SQLite open, journal configuration and migration checks, and getMetadata (1399–1402) then queries SQLite. CopilotAgentSession normally keeps a reference warm (2714–2715), but that owner is absent before runtime creation. AgentHostInputCompletionsBase returns incomplete:true (109), causing subsequent prefix updates to request completions again; cancellation is not forwarded across IPC (agentHostSessionHandler.ts:1769–1772). AgentHostCompletions awaits all providers (143–145), so this new await delays the combined response. This is static call-path evidence, not a measured benchmark.

**Suggested direction:** Keep a bounded session-keyed database lease across an active completion sequence, releasing it on idle/session teardown/provider disposal, rather than reopening it for each pending-plugin request. Preserve the existing latest-cache semantics and coalesce simultaneous reads for the same storage resource.
