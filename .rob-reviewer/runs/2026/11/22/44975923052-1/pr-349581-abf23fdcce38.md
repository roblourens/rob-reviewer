### Scenario 3: Remove an extension-contributed plugin from Agents, accepting or cancelling the owning-extension prompt

- Critical path: The existing plugin remove callback first awaits confirmation. Cancel returns without executing the command. Confirmation executes the now-registered uninstall command and awaits inventory selection and owning-extension removal before returning success.
- Scaling input: One explicitly selected extension-contributed plugin maps to one owning extension. Installed-extension inventory and any owning extension pack control service cost, not the total number of plugin cards or bundled features.
- Effective concurrency: Confirmation gates issuance. Once accepted, configured-server scans and normal service tasks follow the existing concurrent/grouped implementation; per-profile file writes remain serialized. No automatic fan-out from startup, rendering, or discovery is added.
- Cache behavior: Same existing shared service, scan coalescing, per-profile inventory cache, workspace initialization, and task deduplication as Editor. No new retained plugin metadata, polling, failure retry loop, or per-plugin cache is introduced.
- Mechanism confidence: High: the sole production call site supplies one extensionId after confirmed dialogue, the source remove closure is per selected plugin, and the moved handler has unchanged service calls.
- Magnitude uncertainty: Agents inventory size and uninstall durations are unmeasured. Enabling the intended operation has inherent cost, but there is no evidenced gratuitous amplification.
- Expensive boundaries:

### Scenario 4: Uninstall with remote servers, language-pack replicas, application-scoped extensions, or packed extensions

- Critical path: Initial server inventories finish before target selection. Remote dependent checks and language-pack replica lookup occur before grouped uninstall requests. Application-scope profile discovery and pack/dependent validation precede parallel task execution and queued profile updates.
- Scaling input: Number of configured servers, configured profiles for application-scoped extensions, installed inventory per profile, and deduplicated owner/pack tasks. These differ from the number of visible plugin features.
- Effective concurrency: Initial server scans run concurrently; language-pack replica reads and cross-profile discovery are awaited while collecting tasks. Grouped server uninstalls and distinct tasks run concurrently; same-profile file accesses serialize, and opposite install tasks are awaited. No global scan limiter is added or removed.
- Cache behavior: Within-invocation installedExtensionsMap groups reads by profile, native scan promises coalesce overlapping same-profile/language scans, and uninstallingExtensions joins existing same-key tasks and removes entries in finally. No cache key, invalidation, negative-cache policy, or lifetime is changed.
- Mechanism confidence: High: inspected server grouping, remote-check loop, profile inventory map, task-key deduplication, parallel execution, and profile queue directly establish effective cardinality and concurrency.
- Magnitude uncertainty: Prevalence of large packs, many profiles, and remote sessions is unknown; all scaling mechanisms examined here are unchanged rather than introduced by this PR.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/extensionManagement/common/extensionManagementService.ts:getInstalled, uninstallExtensions, uninstallInServer</code>: Read inventories from configured servers, check remote dependents, locate language-pack copies, and submit grouped server uninstalls.; cardinality: Initial inventory: one request per server.     - Introduced by diff: false; previous behavior: Identical for Editor command invocations.   - filesystem at <code>src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts:uninstallExtensions; src/vs/platform/extensionManagement/common/extensionsProfileScannerService.ts:withProfileExtensions</code>: Scan applicable profiles, identify packed extensions, and rewrite profile membership for each distinct task.; cardinality: Profile inventory is cached per distinct profile within each server invocation, not fetched for every pack member.
