## Findings (2)

### 1. [low] Prefer the compact output artifact for owner assignment

**Finding ID:** `PERF-63A2525B7CBC`  
**Location:** <code>.github/workflows/issue-triage.lock.yml:1331</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** The full agent diagnostic archive, including agent/session logs, MCP/proxy/firewall logs and prompt files.  
**Scaling:** One full diagnostic archive download per qualifying assignment job, in addition to the compact output archive. Excess bytes scale with that run's accumulated diagnostic data, and total traffic scales with assigned issue runs; no cross-job artifact cache or deduplication is configured.  
**Outcome:** Excess artifact-network traffic and filesystem extraction increase owner-assignment latency and runner I/O.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The base revision did not have this assignment job or its diagnostic download. The newly introduced deterministic consumer only needs the compact JSON, but the new selector eagerly adds the entire diagnostic bundle to its critical path.  
**Changed behavior:** Every qualifying owner-assignment job downloads and extracts the full diagnostic artifact as well as the compact output artifact before invoking the deterministic assignment action.  
**Confidence:** 0.98 — The artifact selector explicitly matches both archives, their contents are listed in the diff, and the complete assignment call path reads only agent\_output.json. Diagnostic archive size and transfer duration are unmeasured, so severity is low.

**Causal diff evidence:** Added line 1331 selects both agent and agent-output-fallback for the new assign\_owner job. Added lines 1283–1312 package all agent, MCP, proxy and firewall diagnostics into agent, while lines 1266–1281 already publish agent\_output.json in the compact fallback artifact.

On successful triage runs that propose owners, assignment and label cleanup wait for an unnecessary diagnostic archive transfer and extraction. Longer agent conversations and related-issue/tool activity increase the downloaded logs without increasing the assignment input.

**Evidence:** issue-triage.lock.yml:1331 downloads both archives onto a fresh assignment runner before the action at 1344. issueTriage.ts:299–306 reads only the proposed owners from agent\_output.json; assignOwner then performs issue/permission/assignment API calls without reading any diagnostics. The required JSON is already included in agent-output-fallback at lockfile line 1273.

**Suggested direction:** Download agent-output-fallback first for assignment; fetch the larger agent artifact only if the compact artifact or required JSON is unavailable. This preserves the existing fallback behavior without transferring diagnostics on normal runs.

### 2. [medium] Gate detector runtime downloads before the no-output branch

**Finding ID:** `PERF-2D6E51C4E930`  
**Location:** <code>.github/workflows/issue-triage.lock.yml:1694</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Three detector container images plus AWF/Copilot runtime installation and their downloaded/extracted bytes.  
**Scaling:** One three-image preparation and runtime setup per non-skipped agent run with no outputs; total work scales with affected issue runs. Warm local image/tool caches can reduce downloads, but the detection job uses a separate hosted runner from the agent.  
**Outcome:** Unnecessary network and extraction work increases failed-run completion latency and consumes runner capacity.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The base revision had no Issue Triage detection job, so failed issue processing did not start this detector bootstrap. This PR introduces the bootstrap on a branch where its own guard proves the runtime will not be used.  
**Changed behavior:** A failed agent run with no output now starts a separate detection runner and prepares the detector runtime even though run\_detection becomes false and detector execution is skipped.  
**Confidence:** 0.95 — The job condition, step order, false branch, unguarded runtime setup and conclusion dependencies are explicit in the generated workflow. Exact image sizes, installer cache hits and failure frequency are unmeasured; they affect magnitude rather than reachability.

**Causal diff evidence:** The entirely new detection job runs for failed as well as successful non-skipped agent jobs (line 1624). Added line 1694 downloads three detector images before detection\_guard examines output\_types/has\_patch at lines 1695–1708; added lines 1740–1752 also install the runtime without consulting that guard.

When agent startup, authentication or execution fails before producing outputs or a patch, the workflow still waits for detector image/runtime preparation before reporting its final conclusion. Cold hosted runners incur unnecessary registry/release downloads and filesystem extraction, repeated for each affected issue run.

**Evidence:** issue-triage.lock.yml:1624 permits detection after agent failure. Lines 1694–1708 place image preparation before the no-output guard. AWF and Copilot installation at 1740–1752 remain unconditional, while actual execution at 1761 is guarded. The detector uses those images via awf --skip-pull, and conclusion needs detection at 1389, so this preparation delays final reporting despite no analysis being performed.

**Suggested direction:** Compute detection\_guard before image/runtime preparation and guard detector-only image, AWF and CLI setup with run\_detection. Keep conclusion and usage handling available on the no-output branch, and ensure the generated workflow preserves those conditions.
