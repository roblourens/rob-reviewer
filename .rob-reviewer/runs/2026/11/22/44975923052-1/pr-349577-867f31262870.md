## Findings (1)

### 1. [low] Keep full configuration inspection off the non-Snap resize path

**Finding ID:** `PERF-6702422D4D3E`  
**Location:** <code>src/vs/platform/window/common/window.ts:447</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Synchronous renderer CPU for nested configuration-override scans and deep-cloned override contents, plus temporary objects generating GC pressure.  
**Scaling:** For B effective consolidated override groups and I identifier occurrences, each inspection performs O(B\*I) group checks plus cloning/merging matching contents; typical single-language groups give O(B^2). This repeats once per titlebar layout with changed dimensions, even with warm configuration caches.  
**Outcome:** Increased synchronous CPU and allocation before resize frames can complete, degrading resize responsiveness in configurations with many or large language overrides.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** getWindowControlsStyle read controlsStyle from the cached consolidated window configuration using getValue('window'); it did not enumerate or clone language overrides.  
**Changed behavior:** Every call now constructs a configuration inspection and enumerates every consolidated language-override identifier, even when window.controlsStyle cannot have language overrides and the process is not a Snap.  
**Confidence:** 0.97 — The resize listener, grid's dimension-change guard, native titlebar layout, and configuration inspection implementation establish the complete synchronous path. Built-in language extensions provide dozens of override groups; exact frame-time impact is unmeasured.

**Causal diff evidence:** The deleted cached getValue('window') lookup is replaced by unconditional inspect('window.controlsStyle') at line 447, before the Linux-Snap/Wayland condition. This adds override enumeration to existing layout calls on non-Snap Windows/Linux as well as Snap.

Resizing an ordinary non-Snap Windows/Linux window with a custom titlebar now pays collection-wide override scans and cloning on each width-changing layout. Built-in language defaults already supply dozens of groups, and additional language extensions/user overrides increase the cost despite having no relationship to the Snap-specific default.

**Evidence:** src/vs/workbench/electron-browser/window.ts:154 directly handles resize with layoutService.layout(); workbench/browser/layout.ts:1894 lays out the grid, whose gridview.ts:935-944 skips only unchanged dimensions. NativeTitlebarPart.layout at workbench/electron-browser/parts/titlebar/titlebarPart.ts:273-276 calls useWindowControlsOverlay, which calls getWindowControlsStyle at window.ts:479. Configuration.inspect in configurationModels.ts:837-848 loops all override identifiers and invokes getOverrideValue for each; getOverrideValue at 122-126 calls getContentsForOverrideIdentifer, which at 247-272 rescans all groups and deep-clones/merges the matching contents before discovering this setting is absent. This enumeration is not cached. Language defaults such as extensions/prompt-basics/package.json:108-170 and extensions/json-language-features/package.json:152-170 populate those groups.

**Suggested direction:** Retain the getValue-based fast path outside Linux-Snap Wayland, and perform the explicit-configuration inspection only when needed for the Snap fallback. If the Snap decision is cached, invalidate it on relevant configuration changes rather than recomputing it during layout.
