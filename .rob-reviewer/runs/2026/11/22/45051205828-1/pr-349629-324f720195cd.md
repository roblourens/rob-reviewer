### Scenario 2: Resume a cold chat or fork a conversation; reuse an already live chat.

Fork first resolves the source and history boundary, forks the SDK session and attempts a database copy, then resumes the child. Already live sessions are reused instead of re-entering the launcher.
- Scaling input: Distinct cold/resumed/forked SDK sessions, not messages within a conversation. Fork database-copy work scales with source history size, unchanged by the diff.
- Effective concurrency: Duplicate resumes for a chat join; chat work is serialized per key. Different chat keys may resume concurrently. Existing fallback attempts for one launch are sequential, not a new concurrency burst.
- Cache behavior: CopilotSessionLifetime joins default resumes with one promise and peer resumes per chat key, removing promises after settlement. Live-session maps avoid reopening already live chats. Managed-settings joining remains per runtime/token/directory. Runtime assignment cache behavior is inaccessible; no host cache is added or removed.
- Mechanism confidence: High confidence in per-chat resume joining and unchanged fork boundaries. No high-confidence uncached assignment fan-out or added history-proportional work demonstrated.
