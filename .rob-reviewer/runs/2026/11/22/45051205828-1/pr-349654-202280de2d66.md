## Findings (1)

### 1. [medium] Skip first-turn MCP warm-up when discovering draft canvases

**Finding ID:** `PERF-6B2A197DBAA6`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3730</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** SDK-owned MCP server subprocesses/connections and first-turn tool-catalog/memory preparation.  
**Scaling:** One rpc.mcp.list and, if not cancelled or claimed first, one tools.initializeAndValidate per newly launched draft. Each MCP list starts the enabled SDK-owned servers after same-name overrides and disablement; for K picker invocations and M such servers, startup work scales with K times M. Forwarded workbench servers may share underlying resources and are not counted as M new subprocesses. Shared CLI-client startup does not coalesce these per-session RPCs. Warm-up is off the awaited discovery path and runs independently across drafts.  
**Outcome:** Unnecessary server startup and tool-catalog CPU/I/O work, with transient process and memory pressure during canvas selection; repeated picker invocations restart that work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Provisional draft canvas listing was rejected, and supported listing on an existing chat called liveSession.listCanvases without \_warmChat or first-turn warmUp. MCP/tool prewarming belonged to composing a chat intended for a send, not canvas inventory discovery.  
**Changed behavior:** Listing an unstarted workspace-less draft now performs first-turn MCP and tool preparation as well as the runtime launch needed for canvas discovery. NewCanvasSessionAction creates a fresh draft on each invocation, so this preparation also happens when the picker is cancelled or used only to discover extensions.  
**Confidence:** 0.95 — The new discovery-to-\_warmChat call, unconditional warmUp on a new launch, and exact MCP/tool RPCs are traced in code; both existing warm-up tests and the new draft-listing test corroborate issuance. Runtime comments establish lazy MCP startup, and launcher configuration retains enabled root/plugin servers for these non-ephemeral drafts. Actual server startup duration and users' server counts are unmeasured.

**Causal diff evidence:** The added call at copilotAgent.ts:3730 sends draft canvas discovery through \_warmChat. \_warmChat:8389-8403 invokes launch.session.warmUp for every new early launch. warmUp at copilotAgentSession.ts:1788-1799 issues rpc.mcp.list and then rpc.tools.initializeAndValidate; the documented invariant immediately above it states that mcp.list starts otherwise-lazy servers. The added listing test at copilotAgent.test.ts:23996 explicitly expects one mcpLists call before materialization.

With the experimental Canvases section enabled and SDK-owned MCP servers configured, merely opening New Canvas starts unrelated server processes/connections and prepares chat tools before any canvas is chosen. Browsing or repeatedly opening and cancelling the picker causes avoidable startup CPU/I/O and transient process/memory pressure, even when the canvas requires no chat tools.

**Evidence:** NewCanvasSessionAction.run creates the draft before showing the picker (newCanvasSessionAction.ts:88-99), regardless of the persisted catalog. BaseAgentHostSessionsProvider.createCanvasDraft immediately requests listSessionCanvases (baseAgentHostSessionsProvider.ts:8193). The new \_listDraftCanvases invokes \_warmChat, which starts warmUp outside the chat queue. CopilotAgentSession.warmUp calls rpc.mcp.list, bringing lazy servers up, then initializes the entire tool catalog including memory preparation. toSessionConfigMcpServers includes root and enabled explicitly projected plugin servers for non-ephemeral sessions (copilotSessionLauncher.ts:136-144); draft sessions are not ephemeral. Cancelling discards the runtime through \_discardEarlyLaunch, so the next picker cannot reuse its MCP/tool preparation.

**Suggested direction:** Separate early runtime launch from first-turn warmUp, allowing canvas-only discovery to reuse/claim an early launch without issuing mcp.list or tools.initializeAndValidate. Keep first-turn preparation on the existing composer/send path; canvas listing can still activate its extensions through the existing canvas RPC.
