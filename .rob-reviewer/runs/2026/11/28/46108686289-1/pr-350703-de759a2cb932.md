## Findings (1)

### 1. [medium] Skip filesystem scans when no saved allow can approve

**Finding ID:** `PERF-930065D273E6`  
**Location:** <code>src/vs/platform/agentHost/node/agentSideEffects.ts:1748</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Filesystem realpath and lstat operations for the write target and configured sensitive-edit locations.  
**Scaling:** For an ordinary write outside protected locations, each evaluation adds one target resolution plus K sensitive-location resolutions for the current single workspace root. Missing suffixes add ancestor realpath/lstat probes. A completed reevaluation of P such pending writes performs P\*(1+K) resolutions serially across writes; subsequent triggers repeat them without application caching.  
**Outcome:** Additional filesystem latency on prompt/rejection delivery and head-of-line blocking of pending-approval reevaluation.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After permission denials were checked, requiresUserConfirmation returned an empty decision without getAutoApproval. With an empty deny list, unattended rejection and pending reevaluation performed no path I/O. Interactive path-grant construction already resolved the target and sensitive locations; this PR adds a separate scan before that existing work.  
**Changed behavior:** Reviewer-required writes now enter getAutoApproval before publishing a prompt or returning the unattended rejection. With no saved allows, it still resolves the target and scans sensitive-edit locations before returning undefined; those checks cannot produce an approval in explicit-only mode.  
**Confidence:** 0.96 — The early-return removal, awaited initial evaluation, unconditional write resolution, sequential sensitive-location loop, and serial pending-confirmation reevaluation are directly visible in the code. No saved allow means the eventual result is necessarily undefined. Filesystem latency and configuration size are unmeasured; the extra operations and critical-path placement are established statically.

**Causal diff evidence:** agentSideEffects.ts replaces the \`e.managedApprovalRequired \|\| e.requiresUserConfirmation\` early return with a managed-only return and invokes getAutoApproval(..., { explicitRulesOnly: true }) at added line 1748. That newly reaches unconditional write-path resolution and protected-write checks even when the filtered saved allow list is empty.

An Assisted Autopilot write with no saved allow rules now waits for filesystem checks before reporting that approval is unavailable. On a network-mounted workspace, configured agent/hook locations add serial filesystem latency. Interactive prompts also gain an extra scan, and pending writes repeat it during reevaluation, delaying later eligible approvals.

**Evidence:** SessionPermissionManager.getAutoApproval resolves writeResources before checking whether any allow exists, then calls \_requiresEditConfirmation when matchingAllowRules is empty. \_matchesSensitiveEditLocations awaits \_resolveResourcesForApproval for each configured location sequentially; \_resolveResourcesForApproval uses realpath, with realpath/lstat ancestor walking for missing paths. AgentSideEffects.\_handleToolReady awaits this evaluation before its unattended branch and prompt construction. \_reevaluatePendingConfirmations also awaits it sequentially for pending calls on every new prompt/configuration change.

**Suggested direction:** In explicitRulesOnly mode, return undefined immediately after collecting saved permissions when allow is empty, before canonicalization or protected-write checks. For non-shell requests, also avoid protected-write scans once canonical matching establishes that no allow can approve. Keep the caller's deny check and all checks for potentially approving grants unchanged.
