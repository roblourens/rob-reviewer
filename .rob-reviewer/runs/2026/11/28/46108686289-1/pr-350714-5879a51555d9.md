## Performance regression fixes detected (2)

### 1. eager-work

**Fix location:** `src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts:92` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts:87`  
**Introducing path:** `src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts`  
**Introducing commit:** `e380facb66e760f7702e995d8efd65a2ea09e07a`  
**Mechanism family:** `eager-work`  
**Performance category:** `ipc`  
**Confidence:** 0.97

**Mechanism:** Eagerly serialize and transfer every running command's output to every extension host even when that host has no execution reader and immediately drops the data. Cost scales with total output bytes multiplied by uninterested extension hosts.

**Symptom:** Unnecessary renderer JSON encoding, IPC/remote-network traffic, and extension-host decoding for high-output shell-integrated commands with no readers.

**Fixed behavior:** After the existing start RPC reports no reader, unsubscribe from output and discard the pending batch. Forwarding can resume once for a late reader with a matching command ID. Filtering is per terminal and extension host, not per extension; hosts with no readers no longer serialize or transmit ongoing command output.

**Evidence:** The deleted base lines 86-87 install Event.accumulate on each command's terminal.onData and unconditionally join/send its output via $shellExecutionData. TerminalInstance.\_writeProcessData fires onData after xterm parsing; RPCProtocol.\_remoteCall synchronously JSON-serializes these strings and sends them across the extension-host transport. InternalTerminalShellExecution.emitData only delivers to an existing \_dataStream, so output is discarded if read() was never called. Added main-thread lines 88-94 pause the forwarder on a false start result, and pause() removes the listener and clears unsent data. The new no-reader test asserts no data messages and no remaining onData listener. Blame of the original join/send line returns e380facb66e760f7702e995d8efd65a2ea09e07a.

### 2. unbounded-retention

**Fix location:** `src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts:208` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts:87`  
**Introducing path:** `src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts`  
**Introducing commit:** `e380facb66e760f7702e995d8efd65a2ea09e07a`  
**Mechanism family:** `unbounded-retention`  
**Performance category:** `memory`  
**Confidence:** 0.95

**Mechanism:** A sliding debounce retains all parsed output chunks throughout uninterrupted command output, then allocates and serializes one joined string covering the entire interval.

**Symptom:** Renderer output-buffer growth proportional to the uninterrupted output duration, large eventual serialization bursts, and delayed extension stream delivery until output pauses. These consequences are established statically by the timer reset and accumulation call path, not measured in this review.

**Fixed behavior:** Flush after 50 ms from the first chunk without resetting the deadline, or immediately when accumulated character count reaches 1 Mi. Release each batch before sending, and flush on command replacement/end/disposal. A single source chunk can exceed the threshold; the bound does not imply a hard IPC-byte cap or transport backpressure.

**Evidence:** Deleted base lines 86-87 accumulate terminal.onData with a 50 ms debounce then join the entire accumulated array for $shellExecutionData. Event.accumulate delegates to Event.debounce, which pushes every chunk and clears/restarts its timeout on every event (event.ts:279-303,347-354). Parsed terminal output can arrive continuously or every 20 ms, so no flush occurs until a pause or disposal; retained data and the eventual string/serialization scale with the complete uninterrupted output interval. Added forwarder lines 205-209 flush at 1 Mi characters or schedule only when no timer is already scheduled, and lines 223-227 clear the batch before sending. The new periodic-output test covers ten chunks 20 ms apart and an immediate size-triggered send. Blame on the original full-accumulation join/send line returns e380facb66e760f7702e995d8efd65a2ea09e07a.

### Scenario 4: Finish or replace a command, close a terminal, or dispose the shell-integration customer while an execution is active.

- Critical path: The main thread disposes the current forwarder, flushes its remaining batch, and then sends end/close or the next start. Extension-host end processing opens the stream barrier and asynchronously flushes iterables before publishing its end event. Terminal close releases stream-created callbacks.
- Scaling input: Active terminals times instantiated extension hosts, remaining batch lengths, pending execution count on close, and iterables created per execution.
- Effective concurrency: Cleanup executes per event; final output encoding is synchronous, while iterable flush uses the existing Promise.all across readers. No additional cleanup IPC per reader or new teardown subprocess is introduced.
- Cache behavior: DisposableMap entries are removed on replacement, finish and close, and all entries are disposed with the customer. Listener and timer disposal prevent future scheduled sends. Execution callbacks are cleared after first read, at end, and for current/pending executions when the integration closes.
- Mechanism confidence: High: lifecycle call sites, DisposableMap ownership, pause/resume guards and execution release code are explicit; tests cover finish, replacement, terminal/customer disposal, and retained-execution callback release.
- Magnitude uncertainty: Close cost grows with pending executions and reader count; those collections pre-exist. Added callback clearing is constant work per execution and prevents retention rather than introducing expensive cleanup.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadTerminalShellIntegration.ts:83,98-111 and ShellExecutionDataForwarder.dispose</code>: Flush a remaining data batch before the existing execution-end, next-start, or terminal-close message.; cardinality: At most one remaining-batch data request per disposed active forwarder, followed by existing lifecycle messages. Empty/paused forwarders emit no data.
    - Introduced by diff: false; previous behavior: The accumulator also flushed on listener removal at finish/close/disposal; replacement flushed after sending the new start. The prior pending batch could cover an arbitrarily long uninterrupted interval.; critical-path effect: Final renderer encoding occurs before the lifecycle message; extension-host flushing remains asynchronous. Replacement now sends old data before the new start.
- Verdict: No new leak or cleanup amplification found. The callback is new but its last handles are explicitly cleared; prior full-output disposal bursts become bounded batches.
