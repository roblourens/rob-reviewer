### Scenario 3: Accept a suggested scoped approval rule and persist it for later terminal commands.

- Critical path: Workbench session grants update in-memory rules; workspace/user grants await one grouped configuration update before completing confirmation. Agent-host session grants dispatch a grouped configuration change; host grants update state immediately and enqueue persistence without awaiting disk completion on the confirmation handler.
- Scaling input: K distinct selected prefix keys are merged with R existing rules. A scope action contains all K keys, not K separate persistence requests. Scoped keys can increase the number of intentionally selected rules relative to a broad pnpm/bun grant, but growth requires explicit user grants and remains bounded by selected command prefixes.
- Effective concurrency: Workbench workspace/user writes are awaited once per nonempty scope group. Agent-host root writes are chained on \_rootConfigWrite, giving one-at-a-time filesystem persistence rather than a per-rule burst. Session updates are synchronous state dispatches.
- Cache behavior: Workbench settings/session rule stores merge by key. Agent-host session and host permission lists deduplicate using Set and skip updates when no new rules are added. Existing configurations are reused; no new cache or retained history is introduced.
- Mechanism confidence: High confidence from the workbench scope grouping, agent-host grant deduplication, session dispatch, and serialized root persistence implementation.
- Magnitude uncertainty: The number of user-selected scoped grants and existing configuration size are unknown. The changed prefix specificity does not by itself prove unacceptable rule-store growth or costly persistence.
