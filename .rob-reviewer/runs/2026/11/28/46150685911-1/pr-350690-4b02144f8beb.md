# Performance review: automations: fix: show feedback while dragging an automation file to import

[PR #350690](https://github.com/microsoft/vscode/pull/350690) at `4b02144f8beb36e1a8b09bd4171d49a5a2ae2d34`

## Findings (1)

### 1. [low] Avoid retaining the drop target in the notification action

**Finding ID:** `PERF-5284A58E638F`  
**Location:** <code>src/vs/sessions/contrib/automations/browser/automationImportDropTarget.ts:254</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Disposed AutomationImportDropTarget instances and their detached root DOM subtrees, including remaining controls and automation detail text.  
**Scaling:** One retained root per disposed widget generation that still has at least one distinct outstanding invalid-drop notification, not one root per drop within the same widget. Identical messages deduplicate; distinct filenames do not. Memory scales with those retained generations and their remaining DOM/text size.  
**Outcome:** Unnecessary retained memory accumulates across disposed widget generations and cannot be reclaimed while their notifications remain open.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The page displayed an error dialog using message/detail strings without registering a callback that retained its owner after dismissal. The modal had no import-drop notifications.  
**Changed behavior:** Invalid drops now create sticky error notifications whose Import action strongly references the AutomationImportDropTarget instance, allowing the notification lifetime to outlast the owning widget and retain its root DOM.  
**Confidence:** 0.96 — NotificationService.prompt wraps the choice in ChoiceAction, which retains and invokes choice.run; NotificationsModel retains the action until notification closure. Error notifications with actions are sticky. AutomationsEditor clears/disposes its widget on hide or clearInput, but drop-target disposal does not clear its readonly root reference. Notification equality compares messages, so distinct rejected filenames avoid deduplication. This is a static retention-chain finding; retained byte size is not measured.

**Causal diff evidence:** The added callback at automationImportDropTarget.ts:254 captures \`this\` in a notification action. The previous page rejection path called dialogService.error with strings and installed no persistent callback referring to the drop target; the modal previously had no drop handler.

Drop a wrongly named file, then close or switch away from the Automations modal without dismissing the notification. The disposed drop target and detached modal DOM remain in memory. Repeating this across widget recreations with different rejected filenames retains additional roots until the notifications are dismissed.

**Evidence:** notificationService.ts:258-323 stores choices in actions and disposes them only on handle.onDidClose; notifications.ts:226-239 retains notifications in the model, :636-645 makes errors with actions sticky, and :815-820 retains choice.run. The new drop target stores root at :155 and only removes the overlay/class at :174-177. automationsEditor.ts:89-103 clears the modal widget on hide/clearInput, while automationsModalWidget.ts:114 removes its DOM root without clearing its contents. Raw detail text, including automation prompts (:493-503), therefore remains reachable through the disposed root.

**Suggested direction:** Capture the command service in a local variable and have the notification action use that variable, rather than capturing the drop-target instance. This preserves the action after widget disposal without retaining the DOM owner.
