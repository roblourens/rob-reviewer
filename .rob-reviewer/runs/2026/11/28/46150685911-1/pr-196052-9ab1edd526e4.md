# Performance review: Add TF-IDF as a backup option for settings search

[PR #196052](https://github.com/microsoft/vscode/pull/196052) at `9ab1edd526e42365e84b839c8bc6eacb8e8105c7`

## Findings (1)

### 1. [medium] Reuse the TF-IDF index across settings searches

**Finding ID:** `PERF-E50388DEE31C`  
**Location:** <code>src/vs/workbench/contrib/preferences/browser/preferencesSearch.ts:478</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Whole-corpus Unicode tokenization, camel-case splitting, per-document term-frequency Maps, and global occurrence-map allocations.  
**Scaling:** For Q executed debounced non-exact queries and T total text/token-processing work across the cached non-common settings corpus, index construction costs approximately 2 × Q × O(T). MostCommonlyUsed is excluded; document-key deduplication during scoring does not eliminate updateDocuments processing of the input corpus. Both builds run serially on the renderer thread.  
**Outcome:** Avoidable synchronous renderer CPU work delays fallback results and can interrupt input/rendering, with repeated temporary allocations adding GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The base RemoteSearchProvider.searchModel returned null immediately when IAiRelatedInformationService.isEnabled() was false. The same two caller invocations therefore performed zero TF-IDF indexing or corpus-tokenization work in this scenario.  
**Changed behavior:** Without an AI provider, each debounced non-exact settings query now rebuilds the entire TF-IDF term-frequency index twice, including warm searches against the same cached document corpus.  
**Confidence:** 0.99 — The caller explicitly invokes both Remote and NewExtensions searches with the same cached provider and model; the added code creates and populates a fresh calculator for each call. updateDocuments visibly tokenizes every document and allocates term maps synchronously. Exact timings and extension-corpus sizes are unmeasured, but reachability and two rebuilds per executed query are established.

**Causal diff evidence:** Added lines 477–478 create a new TfIdfCalculator and call updateDocuments(this.\_documents) on every getTfIdfItems invocation, outside the model-change/document-refresh branch at lines 449–469. Added lines 514 and 536 make this work reachable when the AI service is disabled, where the base provider returned null before doing any corpus work.

With natural-language search enabled (the default) and no registered AI provider, repeatedly editing a non-exact Settings search reparses all built-in and contributed setting descriptions twice per settled query. Large extension-contributed corpora therefore add avoidable renderer-thread stalls, reduced input responsiveness, and allocation/GC pressure even after the first search.

**Evidence:** settingsEditor2.ts:1657–1673 schedules remote work after a non-exact local result; :1684–1690 requests the same service provider twice and invokes searchModel for both result slots. preferencesSearch.ts:449–469 caches only document strings by model identity, while :477–478 rebuilds the calculator on every invocation. tfIdf.ts:117–142 processes every text chunk, runs termFrequencies/splitTerms (Unicode word matching and camel-case splitting), creates per-document Maps, and rebuilds occurrence counts. These calls execute before the first await yields, so Promise.all does not parallelize the two index builds.

**Suggested direction:** Retain a TfIdfCalculator alongside the cached corpus and populate it only when that corpus is refreshed or invalidated. Warm searches should calculate and rank scores without calling updateDocuments again.

- Expensive boundaries: none found
- Verdict: Same reported root cause, not a separate finding: warm searches fail to reuse the index and repeatedly allocate term maps.

### Scenario 5: Exact-key searches, tag-only/empty queries, natural-language search disabled, and replacement of the settings model.

- Critical path: Exact local matches skip remote scheduling; empty/tag-only queries cancel remote scheduling; disabling natural-language search returns no remote provider. - Cache behavior: The fallback replaces its document array and settings record on model-identity changes. The singleton retains one latest model/corpus per concrete provider, rather than an unbounded map. The AI and TF-IDF providers can both remain cached after availability changes, but retention is bounded. In-place schema updates already mutate the model; index reuse should follow corpus invalidation rather than query frequency.
- Mechanism confidence: High: local exactMatch handling, triggerSearch cancellation, remoteSearchAllowed, corpus replacement, and Settings2EditorModel/DefaultSettings registry access were inspected.
- Magnitude uncertainty: The bounded retained corpus depends on extension contributions. No independent unbounded-retention or cleanup regression is established.
- Expensive boundaries: none found
- Verdict: No separate performance finding. Replacement-model indexing is expected cold work; repeated indexing for the same corpus remains the single reported issue.
