## Findings (2)

### 1. [medium] Coalesce the target change and mode refresh into one rebuild

**Finding ID:** `PERF-1A8F4B5D31ED`  
**Location:** <code>src/vs/workbench/contrib/preferences/browser/settingsEditor2.ts:970</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Settings model objects, layout-resolution CPU, forced tree renders, and grouped installed-extension requests  
**Scaling:** Two full O(S) model reconstructions per affected mode entry, where S includes core and extension-contributed settings; two list requests per enabled extension-management server, not per installed extension. Backend scanner coalescing can share the scan but does not merge the renderer rebuilds.  
**Outcome:** Duplicate UI refresh work, CPU/GC pressure and jank during mode entry  
**PR causality:** <code>introduced</code>  
**Previous behavior:** An ordinary target-change notification caused one full rebuild through onDidSettingsTargetChange. There was no mode listener issuing another unconditional rebuild after that same target-change notification.  
**Changed behavior:** The added mode handler invokes a target-normalizing setter that can already trigger a full rebuild, then unconditionally invokes a second full rebuild.  
**Confidence:** 0.97 — The folder-target normalization and synchronous event chain directly establish two uncoalesced calls with the same final view state; the complete model recreation is traced. Additional configuration events can cause more work, but are not needed for this finding. Duration depends on catalog size.

**Causal diff evidence:** Added settingsEditor2.ts:968-970 sets the mode, calls setAgentsMode, then calls onConfigUpdate unconditionally; added preferencesWidgets.ts:356-357 routes the existing folder target through updateTarget, whose existing event fires the first rebuild.

Entering Agents mode while the Settings editor is on a folder target in a multi-root window performs two complete Settings model rebuilds and renders for the same final state. Large extension-contributed Settings catalogs incur duplicate renderer CPU/allocation and visible refresh jank. When extension recommendations are enabled, both invocations also request the installed-extension list.

**Evidence:** onDidChangeAgentsMode sets viewState.isAgentsMode, then calls settingsTargetsWidget.setAgentsMode. For a selected folder target, setAgentsMode -&gt; updateTarget -&gt; \_onDidTargetChange.fire synchronously invokes onDidSettingsTargetChange, which already calls onConfigUpdate(undefined, true) at line 960. The added line 970 immediately starts another identical refresh. onConfigUpdate has no in-flight joining: each invocation resolves the full layout, awaits extension data, refreshes models and forces rendering. SettingsTreeModel.update (settingsTreeModels.ts:638-651, 697-753) recreates all group/setting elements and disposes the previous children.

**Suggested direction:** Update the mode and normalized target atomically and request one refresh, or coalesce these same-turn full refresh requests. Keep an explicit mode refresh when normalization does not emit a target change.

### 2. [medium] Limit switch comparisons to changed layers and folder overrides

**Finding ID:** `PERF-CC6484C8E1AA`  
**Location:** <code>src/vs/workbench/services/configuration/browser/agents/agentsModeWorkspaceService.ts:273</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Renderer-thread configuration lookups/deep comparisons and complete merged configuration-tree allocations  
**Scaling:** For S mostly unchanged registered keys and F distinct folders, up to 2\*S\*(F+1) getValue calls plus one full merged-tree clone per folder on each folder-bearing side, with additional per-language comparisons. Cache reuse bounds clones within one switch, but fresh parsed snapshots repeat them on the next switch.  
**Outcome:** Longer synchronous mode switches and restored-window startup, with transient allocation and GC pressure proportional to folder count times configuration-tree size  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The base desktop window used WorkspaceService directly and had no mode-switch snapshot comparison. Its consolidated folder models were lazy and reused for actual resource consumers; it did not create fresh copies of every folder's merged configuration for this operation.  
**Changed behavior:** The new mode-switch path reconstructs snapshot caches and eagerly queries the full registered-setting union at every folder before announcing configuration changes.  
**Confidence:** 0.93 — The added loop, startup await, fresh configuration caches, and full-tree cloning implementation are directly traced. Unchanged defaults exhaust the folder loop even for empty folder configurations. Exact pause duration and the prevalence of very large multi-root windows are unmeasured.

**Causal diff evidence:** Added lines 269-277 create fresh BaseConfiguration snapshots, union their allKeys(), expand overrides to all folders, and invoke getValue on both configurations inside the key-by-folder loop; switchDelegates calls this synchronously, and desktop.main.ts:340-341 awaits restoration.

Entering or leaving Agents mode in a multi-root window with tens or hundreds of folders synchronously evaluates thousands of registered settings across those folders and eagerly clones complete configuration trees for folders without open editors. This increases mode-switch latency and renderer CPU/GC pressure; restored mode also awaits this work before workspace-trust initialization.

**Evidence:** fireConfigurationSwitch parses both snapshots into fresh BaseConfiguration instances, takes allKeys(), and checks each unchanged key against every folder. BaseConfiguration.getFolderConsolidatedConfiguration (configurationModels.ts:1126-1138) caches one workspaceConfiguration.merge(folderConfiguration) per folder; ConfigurationModel.merge (same file:157-159) deep-clones the complete contents and overrides, even when the folder configuration is empty. Those caches are new for every switch, so existing delegate caches cannot serve the comparisons.

**Suggested direction:** Derive candidates from differences in the configuration layers and configured folder/ language-override keys, and restrict folder-specific comparisons to affected keys/folders instead of evaluating every default against every folder. Preserve the resource- and language-aware ConfigurationChangeEvent semantics.
