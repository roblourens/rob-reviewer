## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/preferences/browser/preferencesSearch.ts:507` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/preferences/browser/preferencesSearch.ts:518`  
**Introducing path:** `src/vs/workbench/contrib/preferences/browser/preferencesSearch.ts`  
**Introducing commit:** `8e11b537e3b091a8b52c7179fb623ecdeecaf4ea`  
**Mechanism family:** `repeated-work`  
**Performance category:** `latency`  
**Confidence:** 0.99

**Mechanism:** Every debounced nonexact Settings search rebuilt the complete TF-IDF corpus synchronously on the renderer thread, despite cached documents and an unchanged settings model. With Q searches and T total setting text/terms, this repeated O(Q\*T) corpus tokenization and term-frequency/occurrence-map allocation before calculating rankings.

**Symptom:** Repeated related-settings searches incurred renderer-thread blocking and allocation proportional to the entire settings corpus before final search results could be rendered. This consequence is statically established by the synchronous updateDocuments implementation and awaited editor call path; timings from PR metadata were not independently verified.

**Fixed behavior:** Build and retain a single TF-IDF index on the first nonempty related-settings search for the current settings-model identity; reuse it for subsequent queries and replace it when the model changes. Corpus-wide tokenization and term-map allocation no longer repeat for warm searches.

**Evidence:** The deleted base line 518 called updateDocuments(this.\_documents) unconditionally inside getTfIdfItems for every nonempty TF-IDF search. settingsEditor2.ts triggerFilterPreferences awaits doRemoteSearch after local matching unless there is an exact match; doRemoteSearch -&gt; searchWithProvider -&gt; RemoteSearchProvider.searchModel -&gt; TfIdfSearchProvider.searchModel -&gt; getTfIdfItems. TfIdfCalculator.updateDocuments (tfIdf.ts:118-149) synchronously tokenizes every document chunk, builds per-document term-frequency maps, and updates corpus occurrence maps. The new line 507 builds the calculator only under the existing model-identity check, while the added calculateScores line reuses it. The added test explicitly expects two builds for three searches across two models. Blame of base line 518 attributes the unconditional build to the returned introducing commit.

### Scenario 2: Closing and reopening Settings, or searching a replacement settings model

- Critical path: SettingsEditor2Input creates a new Settings2EditorModel; the first eligible related search on that identity replaces the cached index synchronously before scoring. Merely creating/opening the model does not build the index. Input disposal disposes the model; the service already retained its last searched model and settings record before this PR.
- Scaling input: The current model's D document entries and T text/terms, plus the prior model's index during replacement. Retention is bounded by the last indexed model, not the number of searches or editor openings.
- Effective concurrency: Replacement is one synchronous build for the newly encountered identity. The old index remains referenced while the replacement is constructed, producing bounded old-plus-new peak retention rather than accumulation across openings.
- Cache behavior: A different model identity replaces the calculator rather than updating or appending to its existing document map. The old index becomes unreachable after assignment. One index remains retained in the delayed PreferencesSearchService singleton alongside the already-retained model/settings record; original document wrapper arrays are no longer persistently retained. Same-object schema changes do not invalidate the index, matching the pre-existing document-cache policy; no performance issue was established from that policy.
- Mechanism confidence: High: model construction/disposal, registry-backed DefaultSettings initialization, service singleton ownership, calculator document storage, and replacement assignment were inspected. The reached model and index construction use in-memory registry data, not filesystem, database, network, IPC, or subprocess operations.
- Magnitude uncertainty: Additional steady-state term-map memory and replacement peak memory were not measured. They scale with the corpus, but the cache is intentionally bounded to one model and trades retention for eliminating repeated allocation.
- Expensive boundaries: none found
- Verdict: No actionable lifecycle regression. The index retains additional bounded corpus state, but there is no new accumulation, lost live external resource, eager corpus build on opening, or introduced expensive external boundary.
