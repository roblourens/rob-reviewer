### Scenario 1: Markdown extension activation on desktop and web

- Critical path: Activation constructs the client, starts one desktop language-server worker process over IPC or one browser Web Worker, and awaits client.start before registering shared features. Removing the middleware does not add work to this critical path and slightly reduces client option construction.
- Scaling input: Extension activations, normally one per extension-host lifetime.
- Effective concurrency: Exactly one language-server instance is created; the diff neither adds parallel startup nor changes sequencing.
- Cache behavior: No startup cache key, coalescing, or negative-cache behavior changes; the document workspace cache is created exactly as before.
- Mechanism confidence: High: both desktop and browser activation call the changed startClient, and surrounding code proves worker/watcher cardinality is unchanged.
- Magnitude uncertainty: Actual worker startup duration varies by platform, but this diff removes only a middleware object and does not increase startup work.
- Expensive boundaries:
  - subprocess at <code>extensions/markdown-language-features/src/extension.ts:startServer</code>: Start the Markdown language-server worker with IPC transport.; cardinality: One worker per extension activation.
    - Introduced by diff: false; previous behavior: The same worker was started and awaited before this diff.; critical-path effect: Server startup must complete before activation registers shared Markdown features.
  - IPC at <code>extensions/markdown-language-features/src/extension.browser.ts:startServer</code>: Start and initialize one browser Web Worker language server.; cardinality: One worker and one localization postMessage per extension activation.
    - Introduced by diff: false; previous behavior: The same worker and initialization message existed before this diff.; critical-path effect: The worker backs the language client whose start is awaited during activation.
  - filesystem at <code>extensions/markdown-language-features/src/client/client.ts:startClient and client/workspace.ts:VsCodeMdWorkspace</code>: Create workspace file-system watchers for Markdown resources.; cardinality: Two watcher registrations per client/workspace lifetime, independent of document count.
    - Introduced by diff: false; previous behavior: The same watchers were created before the diff.; critical-path effect: Watcher registration occurs during activation but no filesystem scan or extra watcher is added by the diff.
- Verdict: No regression. The diff removes middleware allocation and introduces no startup boundary or fan-out.

### Scenario 2: Open, edit, and request links for Markdown-variant documents such as chatagent, prompt, instructions, or skill files

- Critical path: Opening a selector-matched document produces one didOpen notification to the existing language server; edits produce the existing didChange notifications, and a link request crosses the same client/server connection. The diff changes only the languageId value passed through didOpen and removes an Object.create/Object.defineProperty wrapper.
- Scaling input: Number of opened variant documents, edit events, and explicit language-feature requests; no selector broadening occurs.
- Effective concurrency: Notifications and requests share the existing single language-client connection and server instance; the diff adds no Promise fan-out, limiter bypass, or parallel worker.
- Cache behavior: The synchronized server document retains the same URI and one-entry-per-document cardinality. The local workspace cache remains keyed by URI and is invalidated on file/open/close events. With the intended server behavior, preserving languageId changes filtering semantics but not cache multiplicity; current 0.5.0 compatibility is a correctness concern, not an independently proven performance regression.
- Mechanism confidence: High: documentSelector already included all five IDs, middleware ran after selection, and the deleted code performed only one prototype wrapper plus property definition before the same next call.
- Magnitude uncertainty: Server implementation details for language-specific processing are outside the repository, but changed code proves equal document and IPC cardinality and removes rather than adds per-open allocation.
- Expensive boundaries:
  - IPC at <code>extensions/markdown-language-features/src/client/client.ts:clientOptions.documentSelector</code>: Synchronize didOpen/didChange for selector-matched text documents to the Markdown language server.; cardinality: One didOpen per opened document and existing change notifications per edit; effective document cardinality remains the same five selected language IDs.
    - Introduced by diff: false; previous behavior: Before the diff, the same selected documents sent one didOpen over IPC after a synthetic prototype wrapper changed only languageId to markdown.; critical-path effect: Server synchronization is required before language features use current unsaved content, but notification count and payload text size are unchanged.
  - IPC at <code>extensions/markdown-language-features/src/test/documentLink.test.ts:getLinksForFile (product path through the registered language client)</code>: Request document links from the language server after open or edit.; cardinality: One request per executeLinkProvider invocation, independent of the removed middleware.
    - Introduced by diff: false; previous behavior: The same request was issued before the diff.; critical-path effect: The request is on the link-navigation critical path, but the diff does not add requests or serialization volume.
  - filesystem at <code>extensions/markdown-language-features/src/client/workspace.ts:getOrLoadMarkdownDocument</code>: Read a Markdown resource when a server parse request cannot use an open document or cached document.; cardinality: At most one read per uncached resource until watcher/open/close invalidation; open variant documents are found in memory.
    - Introduced by diff: false; previous behavior: The same cache, open-document lookup, and cold filesystem fallback existed before the diff.; critical-path effect: A cold read can block a server parse response, but preserving didOpen languageId does not add client parse requests or filesystem misses.
- Verdict: No reportable performance regression. Per-open IPC, text serialization, cache keys, and request concurrency are unchanged; one small per-open wrapper allocation is removed.

### Scenario 3: Synchronize Markdown notebook cells

- Critical path: Client startup registers notebook synchronization filtered to markdown cells, then notebook cell changes use the existing server connection. This registration and filter are unchanged.
- Scaling input: Number of opened notebooks and Markdown cells.
- Effective concurrency: One language server and existing protocol connection handle notebook events; no new parallelism or burst is introduced.
- Cache behavior: No notebook cache or cache invalidation code changes; client-side cell filtering remains markdown-only.
- Mechanism confidence: High: the explicit notebook registration is adjacent to and independent of the deleted text-document didOpen middleware.
- Magnitude uncertainty: Exact notebook protocol batching is implemented by the language client, but registration options and selected cell cardinality are unchanged in the diff.
- Expensive boundaries:
  - IPC at <code>extensions/markdown-language-features/src/client/client.ts:notebookFeature.register</code>: Synchronize selected notebook documents and Markdown cells with the language server.; cardinality: One registration at startup and synchronization proportional to Markdown cells in opened notebooks.
    - Introduced by diff: false; previous behavior: Notebook synchronization already filtered cells to language markdown and used the same server connection.; critical-path effect: Cell synchronization precedes server-backed language features, but the diff does not broaden the cell filter or add messages.
- Verdict: No regression. Notebook boundary cardinality, filtering, and concurrency are unchanged.
