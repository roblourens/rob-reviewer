### Scenario 1: Copilot-routed session title, pull-request text, commit-message, and branch-name generation

- Critical path: The existing Copilot account/model resolution and chat-completions request must finish before the generated value is usable. The new Microsoft telemetry logging and GitHub telemetry POST occur synchronously only for small event construction/serialization; the GitHub fetch is fire-and-forget and its response is off the product critical path.
- Scaling input: Number of actual utility-model invocations: generally one for the first/fork title, one per explicit PR-text or commit-message generation, and one per generated branch. Diff and conversation content affect the pre-existing model request, not telemetry size or telemetry call count.
- Effective concurrency: Each feature starts one utility completion. Same-token account discovery is promise-coalesced; model IDs are cached per token. Title generation cancels/replaces prior title work, worktree branch generation is sequenced per repository, and PR/commit operations await their single call. GitHub telemetry POSTs have no explicit limiter, but effective cardinality is one per completed model call rather than per token, message, file, or response chunk.
- Cache behavior: Copilot account discovery is coalesced per token and reused until its 30-minute TTL reaches the 5-minute refresh window; utility model IDs are cached in the same entry. Success and concurrent cold calls share the cache promise; failed discovery follows existing invalidation/stale-entry behavior.
- Mechanism confidence: High: changed lines, call sites, cache implementation, and telemetry sender were traced directly.
- Magnitude uncertainty: Exact user frequency and telemetry endpoint latency vary, but the new network request is off the critical path and bounded one-to-one with already expensive model calls.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/shared/copilotApiService.ts:CopilotApiService.utilityChatCompletion</code>: Resolve \`/copilot\_internal/user\` and \`/models\` as needed, then POST one non-streaming chat completion.; cardinality: Cold credential: one coalesced account-discovery GET, one model-list GET, and one completion POST; warm credential/model cache: one completion POST. Calls are per title, PR text, commit message, or generated branch name, not per prompt message or changed file.
    - Introduced by diff: false; previous behavior: The same account/model resolution and one completion POST were already required.; critical-path effect: All pre-completion discovery and model calls are on the existing generation critical path.

### Scenario 2: BYOK-routed session title and pull-request text generation

- Critical path: One existing BYOK bridge chat call must finish. The new Copilot-account attribution lookup starts in parallel and is not awaited by the model result; telemetry waits on that lookup separately after the BYOK outcome, so account discovery and telemetry delivery are off the generated-value critical path.
- Scaling input: Number of BYOK utility invocations and distinct Copilot credentials. Same-token concurrent calls share discovery; report payload size is constant and does not scale with prompt or output.
- Effective concurrency: The BYOK bridge receives one request per utility call. Copilot account discovery is shared per token through the existing promise cache. The telemetry report attaches one continuation per call, but each continuation retains only bounded metadata and converges on the same discovery promise for concurrent calls.
- Cache behavior: Warm account lookup is an immediate cached resolution; cold and refresh lookups are coalesced. Failed lookups produce Microsoft-only reporting and use existing cache invalidation/stale-cache rules; there is no new negative-cache retry loop inside a single call.
- Mechanism confidence: High: the fire-and-forget promise chain and \`\_getEntryForToken\` coalescing/TTL were inspected directly.
- Magnitude uncertainty: A cold account lookup can consume network resources, but it is shared, off-path, and commonly overlaps existing Copilot account setup; endpoint duration does not delay the BYOK result.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/agentHostUtilityModelService.ts:AgentHostUtilityModelService.\_byokChatCompletion</code>: Send the utility prompt to the renderer-hosted BYOK model bridge.; cardinality: One bridge call per BYOK utility invocation.
    - Introduced by diff: false; previous behavior: The same single BYOK bridge call was awaited.; critical-path effect: The bridge result remains the sole expensive boundary required before the generated value returns.
  - network at <code>src/vs/platform/agentHost/node/agentHostUtilityModelService.ts:\_resolveByokGitHubTelemetry</code>: Resolve the session Copilot account via cached \`/copilot\_internal/user\` discovery for GitHub telemetry attribution.; cardinality: At most one coalesced cold/refresh GET per credential cache window; warm calls use the cached entry.     - Introduced by diff: true; previous behavior: The BYOK utility path did not itself request account attribution, though the same shared account cache is also populated by Copilot agent telemetry/account setup.; critical-path effect: Started alongside the bridge call and never awaited by \`\_byokChatCompletion\`; only telemetry reporting waits for it.
  - network at <code>src/vs/platform/agentHost/node/shared/utilityModelCallTelemetry.ts:reportUtilityModelCall</code>: POST one GitHub standard-stream event after the BYOK result and account attribution resolve.; cardinality: One fire-and-forget POST per completed BYOK utility call with a Copilot account; Microsoft-only logging when no account resolves.
    - Introduced by diff: true; previous behavior: No utility-call event was sent.; critical-path effect: Off the generated-value critical path.
- Verdict: No reportable regression. New attribution/network work is bounded and off-path, with effective discovery cardinality reduced by the existing cache and coalescing.
