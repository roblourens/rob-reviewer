# Performance review: dictation: play a sound when cloud dictation disconnects

## Findings

No high-confidence performance findings.

<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** eager-work, repeated-work, cache-lifecycle, concurrency-burst

### Scenario 1: Workbench startup and accessibility configuration registration

- Critical path: Module evaluation registers one additional AccessibilitySignal and one configuration schema entry; no audio is loaded or played during startup.
- Scaling input: Constant one signal/schema entry; the existing signal migration and quick-pick enumerations grow by one bounded element.
- Effective concurrency: Synchronous module/configuration registration only; no queued or parallel boundary work.
- Cache behavior: No media cache is touched. Signal enablement observables remain lazily created by playSignal/getEnabledState.
- Mechanism confidence: High: static registration and lazy signal-service code were inspected directly.
- Magnitude uncertainty: Exact schema-registration cost is unmeasured, but the added constant-size object and one-element enumeration increase are negligible.
- Expensive boundaries: none found
- Verdict: No regression: the diff adds only bounded metadata at startup and does not eagerly load the sound resource.

### Scenario 2: Active cloud dictation receives a terminal WebSocket error or close event

- Critical path: The existing error/close event tears down capture and the cloud session, sets Idle, then invokes playSignal without awaiting it before showing the notification. Audio completion is therefore off the failure-handling critical path.
- Scaling input: One terminal failure per active cloud dictation session, independent of transcript length and audio chunk count.
- Effective concurrency: Failure handling transitions synchronously to Idle and clears listeners; playSound also rejects overlapping playback of the same Sound.error unless explicitly allowed, which this call does not do.
- Cache behavior: Cold playback creates and loads one HTMLAudioElement for error.mp3; successful playback is cached by URL and warm playback resets/reuses that element. Disabled sound avoids media work entirely.
- Mechanism confidence: High: event guards, teardown, non-awaited call, playingSounds deduplication, and URL-based sound cache were inspected.
- Magnitude uncertainty: Browser-specific media load/decode latency is unmeasured, but it is off the critical path and bounded to one shared resource.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/speechToText/chatSpeechToTextService.ts:\_startMaiSession/\_cancelBackend</code>: Existing cloud transcription WebSocket emits terminal error/close and is disconnected during teardown.; cardinality: One active WebSocket per cloud dictation session; duplicate close/error callbacks are suppressed after teardown clears the turn and sets Idle.
    - Introduced by diff: false; previous behavior: The same WebSocket error/close path tore down the session and showed an error notification without playing audio.; critical-path effect: The disconnect event triggers failure handling; disconnect itself was already on this path and signal playback does not wait on it.
  - other expensive boundary at <code>src/vs/platform/accessibilitySignal/browser/accessibilitySignalService.ts:playSignal/playSound</code>: Load/decode/play packaged error.mp3 through an HTMLAudioElement on the first enabled occurrence.; cardinality: At most one playback for the terminal failure; concurrent uses of the same Sound.error are coalesced by playingSounds.
    - Introduced by diff: true; previous behavior: No disconnect sound was requested on this failure path.; critical-path effect: Introduced but fire-and-forget; notification and failure teardown do not await media loading or playback.
- Verdict: No reportable regression: one intentional, bounded, cached audio playback is added only on terminal cloud disconnect and does not block teardown or notification.

### Scenario 3: Cloud audio-chunk send observes an already closed socket before the close event

- Critical path: The synchronous send failure checks isConnected, starts the disconnect sound, then runs existing generic failure teardown. playSignal is not awaited, so media playback does not delay session shutdown.
- Scaling input: Although PCM chunks arrive repeatedly, effective failure cardinality is one per failed session because \_failSession synchronously sets Idle and stops capture.
- Effective concurrency: Synchronous WebSocket send and single-shot failure handling; no burst of audio loads because of state gating plus shared-sound in-flight suppression.
- Cache behavior: Same cold/warm error.mp3 behavior as the close-event scenario; the cache is shared across all signals using Sound.error.
- Mechanism confidence: High: \_pushAudio, \_onAudioPushError, \_failSession, teardown, and sound deduplication were traced.
- Magnitude uncertainty: A close/send race can vary by browser, but neither branch causes playback to scale with chunk frequency.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/speechToText/chatSpeechToTextService.ts:\_pushAudio</code>: Existing WebSocket audio chunk send throws after the connection is no longer open.; cardinality: Audio chunks are frequent while recording, but the first failure synchronously transitions state away from Recording; later chunk errors return before work.
    - Introduced by diff: false; previous behavior: The same failed send invoked generic session failure without a sound.; critical-path effect: The send was already on the recording path; its failure triggers teardown.
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/speechToText/chatSpeechToTextService.ts:\_onAudioPushError</code>: Load/decode/play packaged error.mp3 through the accessibility signal service.; cardinality: One request for the first closed-connection send failure; subsequent errors are gated by Recording state and overlapping Sound.error playback is deduplicated.
    - Introduced by diff: true; previous behavior: No audio resource was requested for this error.; critical-path effect: Fire-and-forget and therefore off the teardown critical path.
- Verdict: No reportable regression: the new playback remains bounded to one asynchronous signal per failed session, rather than one per audio chunk.

### Scenario 4: Normal cloud or on-device dictation without disconnect

- Critical path: No new playSignal call is reached during normal recording, transcription, or successful stop; only static metadata exists.
- Scaling input: Recording duration and audio chunk count; the diff adds no per-chunk work while connections remain healthy and no work to on-device sessions.
- Effective concurrency: Existing backend behavior is unchanged; no new task, queue, or playback is scheduled on successful chunks.
- Cache behavior: The new signal's enabled-state and media caches are untouched unless a covered disconnect failure occurs.
- Mechanism confidence: High: both added runtime calls are restricted to terminal MAI failure branches.
- Magnitude uncertainty: None material for diff causality.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/speechToText/chatSpeechToTextService.ts:\_startMaiSession/\_pushAudio</code>: Existing cloud transcription WebSocket carries audio and transcript messages.; cardinality: One connection per cloud session and existing per-chunk sends.
    - Introduced by diff: false; previous behavior: Identical network operation and cardinality.; critical-path effect: Unchanged by the diff during successful operation.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/speechToText/chatSpeechToTextService.ts:\_pushAudio</code>: Existing on-device pushAudio calls enter the local transcription service.; cardinality: Existing per-chunk calls for on-device sessions.
    - Introduced by diff: false; previous behavior: Identical IPC operation and cardinality.; critical-path effect: Unchanged; the added disconnected signal condition excludes the on-device backend.
- Verdict: No regression on the normal dictation hot path.

**Summary:** Reviewed all four changed files and traced startup/configuration registration, cloud WebSocket disconnect handling, audio-send failure races, normal cloud recording, and on-device recording. The only new expensive work is one intentional error-sound media load/play per covered terminal cloud failure; it is asynchronous, URL-cached, shared with existing error signals, deduplicated while in flight, and guarded by synchronous teardown/state transitions. No high-confidence actionable performance issue was introduced.
