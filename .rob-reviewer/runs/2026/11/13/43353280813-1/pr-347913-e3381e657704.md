# Performance review: Chat input pills: only rescan the row when its state changes

[PR #347913](https://github.com/microsoft/vscode/pull/347913) at `e3381e6577040d115965ec5e440c7f03512cb2fb`

## Findings

No high-confidence performance findings.

## Performance regression fixes detected (1)

### 1. synchronous-ui-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/chatInputPills.ts:527` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/chatInputPills.ts:534`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/chatInputPills.ts`  
**Introducing commit:** `1e1ee361e263c95c283dddceae3a7bd3373590ee`  
**Mechanism family:** `synchronous-ui-work`  
**Performance category:** `layout`  
**Confidence:** 0.98

**Mechanism:** Every live pill-source update invoked synchronous scrollbar geometry reads even when row visibility/emptiness was unchanged, multiplying layout work by streaming update count.

**Symptom:** Streaming an agent response caused hundreds of unnecessary row rescans and dozens of forced layouts, adding measurable main-thread layout time.

**Fixed behavior:** The added autorun reads a separately derived scalar rowState. Derived uses strict equality and only notifies the autorun when that state changes, so source updates that merely alter pill data no longer execute DOM class updates or scanDomNode. Actual pill size changes remain covered by ChatPillsRow's ResizeObserver, while visibility-state transitions still scan once.

**Evidence:** Base line 534 called ChatPillsRow.scanDomNode from a derived(...).recomputeInitiallyAndOnChange callback. Observable KeepAliveObserver invokes that callback at the end of every dependency update, regardless of whether the derived 'visible'/'empty'/'hidden' value changed. AgentHostSessionInputPills feeds ChatInputPills from live session/chat subscriptions and derived artifact/reference/change sources, so streaming state updates repeatedly reached this callback. ChatPillsRow.scanDomNode delegates to DomScrollableElement.scanDomNode, which synchronously reads clientWidth, scrollWidth, clientHeight, and scrollHeight. The PR's layout probe reports 320 rescans, 43 forced layouts, and 52 ms over one streamed response, matching the traced mechanism.

### Scenario 2: Pills appear, disappear, or all become filtered/hidden, changing the row between visible, empty, and hidden

- Critical path: The pill/visibility observable changes rowState; the autorun immediately updates classes, focusability, persistent-row visibility, and performs one scan before the UI state transition completes. This preserves the pre-diff critical-path work only for actual row-state transitions.
- Scaling input: Work scales with the number of row-state transitions, not the number of source or entry updates. The scalar state has only three values and no collection-size-dependent boundary calls are introduced.
- Effective concurrency: Single synchronous autorun on the UI thread per committed state transition; observable transactions coalesce dependency propagation and there is no concurrent fan-out.
- Cache behavior: rowState's cached strict-equality value suppresses duplicate state notifications. There are no positive/negative data caches or external cache misses on this path.
- Mechanism confidence: High: the changed autorun directly reads only rowState, and the unchanged scan remains inside that transition handler.
- Magnitude uncertainty: The frequency of user-driven hide/filter transitions varies, but each transition intentionally retains one geometry scan and constant DOM state updates.
- Expensive boundaries: none found
- Verdict: No regression: required synchronous work remains bounded to actual state changes.

### Scenario 3: Visible pill labels, entries, or dimensions change without changing row visibility

- Critical path: ChatPillsWidget updates rendered pill DOM; ChatPillsRow's existing ResizeObserver observes the pills element/content and runs layout/scan when dimensions actually change. The new rowState autorun is skipped, so redundant synchronous scanning is removed from the source-update stack and dimension handling remains observer-driven.
- Scaling input: Widget rendering can scale with pill count as before. Row scans now scale with actual resize deliveries rather than every data update; no new per-pill IPC, filesystem, network, or subprocess work is present.
- Effective concurrency: DOM rendering and observer callbacks are serialized by the browser/UI thread. Resize notifications can batch multiple DOM changes; there is no added timer, queue, or unbounded concurrency.
- Cache behavior: No external cache participates. Automatic-compaction measurements are invalidated only by existing resize/mutation handling; the diff does not alter that lifecycle.
- Mechanism confidence: High: ChatInputPills calls ChatPillsRow.observe on the pills element, and ChatPillsRow's ResizeObserver invalidates measurements and calls layout, which scans the DOM.
- Magnitude uncertainty: Browser ResizeObserver batching and exact layout cost vary, but source inspection establishes that the observed pills element is already registered and its callback calls layout/scan.
- Expensive boundaries: none found
- Verdict: No regression: the existing resize path covers dimension changes while the diff removes duplicate eager scans.
