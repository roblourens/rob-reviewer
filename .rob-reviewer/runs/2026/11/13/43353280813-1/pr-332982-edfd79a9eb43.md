## Findings (2)

### 1. [medium] Reuse the intrinsic-width cache while the row is expanded

**Finding ID:** `PERF-3C3FC23875AC`  
**Location:** <code>src/vs/workbench/browser/chatPills.ts:202</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous DOM geometry/style resolution for the pill toolbar subtree  
**Scaling:** Cost repeats for each ResizeObserver delivery during a panel/editor drag and grows with the rendered pill toolbar subtree.  
**Outcome:** Repeated forced layout on the resize critical path can increase resize latency and drop frames.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous session toolbar resize observer only rescanned the scrollable node, and editor/panel chat had no responsive pill row; it did not remove compact styling and remeasure intrinsic pill width on every expanded-state resize.  
**Changed behavior:** Auto-compact rows now call layout for each observed resize, and the added \`\|\| \!...compact\` condition recomputes expanded width even when \`\_expandedContentWidth\` is already cached and only available width changed.  
**Confidence:** 0.95 — The added auto-compact resize callback and geometry reads are directly traced: ResizeObserver calls layout on container changes, and line 202 unconditionally re-enters the measurement block whenever the row is expanded. Mutations and observed child resizes already invalidate the cache, so the repeated measurement during a pure width drag is not needed; exact frame cost varies with DOM/theme complexity.

**Causal diff evidence:** Added RIGHT line 202 explicitly bypasses the new \`\_expandedContentWidth\` cache whenever the row is expanded, placing intrinsic subtree measurement on every resize callback.

Dragging the chat panel boundary or resizing a chat editor while pills fit keeps the row expanded, so every resize delivery reads \`getBoundingClientRect\`, removes compact styling, and reads offsets/widths before paint, causing avoidable resize jank.

**Evidence:** \`ChatPillsRow\` observes \`content\` and its pill element and calls \`layout()\` from the ResizeObserver. In \`layout\`, line 201 reads the viewport width; line 202 enters the intrinsic-width block whenever the row is not compact, and lines 205-206 read \`offsetLeft\`/\`offsetWidth\`. \`\_expandedContentWidth\` is already invalidated by MutationObserver and non-content ResizeObserver entries, proving pure container-width changes can reuse it.

**Suggested direction:** Measure intrinsic width only when \`\_expandedContentWidth\` is undefined; keep the existing mutation and child-resize invalidation paths for real sizing changes.

### 2. [medium] Defer materializing every changeset diff until activation

**Finding ID:** `PERF-41A829CB45FB`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionInputPills.ts:294</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Parsed/wrapped URI objects and per-file diff objects, plus repeated collection scans  
**Scaling:** CPU and allocation grow linearly with the number of files in the session-wide changeset and recur on each authoritative changeset update for each open Agent Host chat surface.  
**Outcome:** Large changesets add synchronous CPU and GC pressure to session-state delivery and pill rendering, increasing chat UI latency.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Editor and panel chat did not create this session-wide Changes pill or materialize changeset files. The Agents Window summary path aggregated counts directly from session changes/summary without creating editor diff resources for every file.  
**Changed behavior:** The new Agent Host input adapter maps every changeset file through \`agentHostChangesetFileToEntryDiff\` before computing three scalar pill counts, even when the Changes pill is never activated.  
**Confidence:** 0.93 — The observable call path is explicit: the Changes source's \`hasData\` reads \`changeStats\`, which reads \`changes\`, so the mapping runs as part of normal pill presentation rather than only when the user opens Changes. Each helper call parses and canonicalizes before/after/content URIs and wraps resources. The exact largest changeset size is uncertain, affecting severity but not the mechanism.

**Causal diff evidence:** Added RIGHT line 294 eagerly invokes the URI-heavy diff conversion for every file in the newly subscribed session changeset on the pill's observed rendering path.

Opening or updating an Agent Host session with hundreds or thousands of changed files synchronously parses up to four URIs per file, creates wrapped Agent Host URIs and diff objects, then scans the result again for additions/deletions; this can visibly delay pill/chat updates and create GC churn.

**Evidence:** Line 294 maps the full \`ChangesetState.files\` array. \`agentHostChangesetFileToEntryDiff\` calls \`normalizeFileEdit\`, which parses before/after and content URIs and canonicalizes them, then creates wrapped original/modified/snapshot URIs and a diff object. \`changeStats\` immediately consumes that allocated array only to read length and reduce additions/deletions twice; the array is otherwise needed only by the Changes click handler.

**Suggested direction:** Derive files/additions/deletions directly from the raw changeset entries for presentation, retain the raw files, and convert them to \`IEditSessionEntryDiff\` only inside the Changes activation path (or memoize that conversion on first activation).
