# Performance review: Avoid quadratic work when many text models are disposed at once

[PR #347898](https://github.com/microsoft/vscode/pull/347898) at `1316880de856fc0b92798d21b655b77c9dd1a8c0`

## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/editor/browser/services/editorWorkerService.ts:370` (`RIGHT`)  
**Blamed base line:** `src/vs/editor/browser/services/editorWorkerService.ts:367`  
**Introducing path:** `src/vs/editor/common/services/editorWorkerServiceImpl.ts`  
**Introducing commit:** `18101697a800782d6e5738c3264dd433e5ccb415`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.99

**Mechanism:** Every model-removal event synchronously rebuilt/scanned the complete remaining model array merely to determine whether the editor worker could stop, making bulk disposal quadratic.

**Symptom:** Closing a large multi-diff or changes session can block the renderer for seconds while thousands of text models are disposed.

**Fixed behavior:** The changed listener uses a zero-delay RunOnceScheduler and schedules only when a worker exists and no check is pending, so a synchronous removal burst performs one emptiness scan after the burst rather than one scan per removed model.

**Evidence:** In the base revision, WorkerManager's onModelRemoved listener synchronously invoked \_checkStopEmptyWorker for every removal. That method calls ModelService.getModels(), which materializes/scans the remaining model collection. A multi-diff teardown can synchronously remove thousands of original/modified models, so the listener performs a decreasing full scan after every removal (quadratic aggregate CPU/allocation) on the renderer teardown path. The PR metadata's profile identifies this call chain during a tens-of-seconds renderer freeze, and the changed listener directly removes the repeated scans.

### Scenario 1: Closing a large multi-diff/Changes editor that disposes thousands of original and modified text models in one renderer turn

- Critical path: ModelService removes each model and synchronously fires onModelRemoved. The changed document-state handler now deletes that model from its tracked Set and emits the same one-document delta; the worker emptiness check is deferred until the next timer turn and is therefore off the synchronous disposal critical path.
- Scaling input: N disposed synchronized text models (realistically two per file in a large multi-diff); live code-editor snapshots E are typically limited to instantiated/visible editors. Document-state work changes from repeated collection-wide O(N) recomputation to O(E) membership checking per synchronized removal, while worker scans change from N decreasing full scans to one scan.
- Effective concurrency: Disposals and listeners run serially on the renderer event loop. The RunOnceScheduler provides one shared pending check for the burst; it does not create parallel worker operations.
- Cache behavior: No cache miss path is added. The current synchronized-document Set is updated in place; models excluded from synchronization are rejected by membership without recomputation. Worker scheduling is coalesced only while a check is pending.
- Mechanism confidence: High: changed handlers, model-removal event order, full-state computation, IPC emission, and scheduler implementation were traced directly.
- Magnitude uncertainty: Exact remaining latency depends on the number of synchronized models and extension-host IPC overhead, but the removed quadratic scans and unchanged linear delta fan-out are explicit.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts:\_onDelta</code>: Send $acceptDocumentsAndEditorsDelta with the removed model URI to the extension host.; cardinality: One small delta per synchronized removed model; for N synchronized models, N IPC messages. Unsynchronized large/simple-widget models emit none.
    - Introduced by diff: false; previous behavior: The previous full recomputation also detected the single removal for each onModelRemoved event and sent one delta per synchronized model.; critical-path effect: The proxy call is issued synchronously during each removal, but this cardinality is unchanged by the PR and remains linear.
  - IPC at <code>src/vs/editor/browser/services/editorWorkerService.ts:WorkerManager.\_checkStopEmptyWorker</code>: Dispose the single editor web-worker client once no text models remain.; cardinality: At most one worker disposal after the coalesced burst, and none when no worker exists or models remain.

- Verdict: No regression. The diff removes the dominant repeated scans; the remaining per-model IPC existed before and the new O(E) scan replaces a larger scan.

### Scenario 2: Removing a single model during ordinary editor use, including a model still shown by a code editor

- Critical path: For an unshown synchronized model, the state Set is updated and its removal delta is sent immediately. If a tracked editor snapshot still references the model, the handler falls back to the same full state recomputation used before so editor and active-editor state are reconciled. The worker emptiness check runs on the next timer turn.
- Scaling input: One removed model and the number of live editor snapshots E; the common unshown case scans only E snapshots, while the shown case retains the prior full recomputation.
- Effective concurrency: Single-threaded event delivery; one zero-delay scheduled worker check. New worker use before the callback is observed by the callback's current model count.
- Cache behavior: The authoritative current-state Set acts as a membership index. Unsynchronized models are negative membership hits and do no further work. No cold/warm cache difference or retry behavior is introduced.
- Mechanism confidence: High: both branches and event ordering are explicit in the changed code and model service.
- Magnitude uncertainty: E varies by UI composition, but it is the instantiated editor count and the fallback preserves the previous path when needed.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts:\_onDelta</code>: Send the document/editor removal delta to the extension host.; cardinality: One message for the single removal; an editor-associated removal combines the document/editor state in the computed delta.
    - Introduced by diff: false; previous behavior: One full recomputation followed by one extension-host delta.; critical-path effect: Remains on the synchronous removal path exactly as before.
  - IPC at <code>src/vs/editor/browser/services/editorWorkerService.ts:WorkerManager</code>: Potentially dispose the editor web worker when this was the last model.; cardinality: Zero or one scheduled check and zero or one worker disposal.
    - Introduced by diff: false; previous behavior: The same check and possible disposal ran synchronously inside onModelRemoved.; critical-path effect: Delayed by one timer turn, moving rather than adding the worker check and teardown off the immediate model-disposal path.
- Verdict: No reportable regression. Single-removal work is reduced or deferred, with no added boundary call or retained resource.

### Scenario 3: Editor model changes and normal state lifetime after storing the model directly in TextEditorSnapshot

- Critical path: Code-editor model-change events trigger a full state rebuild, replacing snapshots; editor removal disposes its listeners and rebuilds state. The added model field is then used only for identity checks on model removal.
- Scaling input: Number of live code-editor snapshots and frequency of editor model changes.
- Effective concurrency: Synchronous renderer event handling with no parallelism.
- Cache behavior: Snapshots are replaced on model-change/full-state updates; there is no growing key history or cache.
- Mechanism confidence: High: snapshot ownership and the editor model-change/removal listeners were traced directly.
- Magnitude uncertainty: None material; the snapshot already strongly retained the editor, which itself owns the same current model.
- Expensive boundaries: none found
- Verdict: No retention regression. The explicit model reference has the same snapshot lifetime as the already-retained editor and is released when state is rebuilt or disposed.
