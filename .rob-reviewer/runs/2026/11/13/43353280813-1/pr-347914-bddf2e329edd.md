# Performance review: Add editor part \`supportsSplitting\` capability and hide "Open to the Side" where it is unsupported

[PR #347914](https://github.com/microsoft/vscode/pull/347914) at `bddf2e329edd3b871b51e73994ef9b1218210cfe`

## Findings (1)

### 1. [medium] Snapshot splitting support before converting workspace symbols

**Finding ID:** `PERF-54BF03C1A20B`  
**Location:** <code>src/vs/workbench/contrib/search/browser/symbolsQuickAccess.ts:207</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work, document.hasFocus calls, editor-part scans, and temporary document arrays  
**Scaling:** O(S \* (W + P)) per query for S deduplicated symbols surviving filtering, W registered windows, and P editor parts; previously this added cost was absent.  
**Outcome:** Increased picker-update latency and CPU/GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The symbol loop created the side button unconditionally and did not perform an editor-part or active-window lookup per result.  
**Changed behavior:** Every retained workspace-symbol result now evaluates editorGroupService.supportsSplitting while its pick is constructed.  
**Confidence:** 0.97 — The added line is directly inside the result loop, and the getter chain proves the repeated allocations, focus queries, and part scan. Provider result count varies, affecting severity but not the mechanism.

**Causal diff evidence:** RIGHT line 207 adds \`this.editorGroupService.supportsSplitting\` to each pick created by the workspace-symbol loop.

With an auxiliary editor window open, workspace-symbol searches repeat focus detection and allocation for every result on each query, adding synchronous CPU and GC work to picker updates and degrading typing responsiveness in symbol-heavy workspaces.

**Evidence:** The condition is inside the loop over the deduplicated output of getWorkspaceSymbols. EditorParts.supportsSplitting delegates through activePart; MultiWindowParts.activePart calls getActiveDocument and getPartByDocument. With multiple registered windows, getActiveDocument allocates document arrays and calls document.hasFocus, after which getPartByDocument scans registered parts. The whole lookup therefore repeats before the picker receives each result batch.

**Suggested direction:** Read supportsSplitting once after the awaited symbol query and before the loop, then reuse that snapshot for the whole result batch.
