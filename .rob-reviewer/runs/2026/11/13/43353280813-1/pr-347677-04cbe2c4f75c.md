# Performance review: Agents window: add the Agents Launcher to start sessions from anywhere

[PR #347677](https://github.com/microsoft/vscode/pull/347677) at `04cbe2c4f75cd4bee9d0e73944ed45efcd38b29f`

## Findings (2)

### 1. [medium] Avoid materializing focused-window arrays in the hot active-window lookup

**Finding ID:** `PERF-ABC34CB8C6A0`  
**Location:** <code>src/vs/base/browser/dom.ts:1090</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** temporary JavaScript arrays plus repeated Document.hasFocus() calls  
**Scaling:** With W registered windows, every getActiveWindow() call now scans all W windows and allocates both the Array.from result and the filtered result; callers such as viewLinesGpu invoke getActiveWindow() inside per-character loops, so a C-character range performs O(C\*W) focus checks and O(C) extra allocations.  
**Outcome:** Higher CPU and GC pressure on rendering, selection, and hit-testing paths, causing avoidable frame or input latency in multi-window sessions.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous implementation allocated one documents array and used find(), which stopped checking focus at the first focused document. Single-window sessions still took the existing fast path.  
**Changed behavior:** The changed line maps every registered window and then filters the entire collection before another find, forcing a second array allocation and preventing focus checks from short-circuiting.  
**Confidence:** 0.97 — The allocation count, loss of short-circuiting, per-character caller, and launcher-created multi-window trigger are all directly traced in code. Exact frame-time impact depends on GPU rendering use, line content, and auxiliary-window count, so severity is medium rather than high.

**Causal diff evidence:** RIGHT line 1090 replaces the prior one-array/short-circuit lookup with Array.from(...).filter(...), adding a filtered array and full-window scan to each multi-window call.

Once any auxiliary window is registered—including the launcher window that remains registered while hidden—GPU range calculations over long non-ASCII lines can allocate thousands of short-lived arrays and query every window's focus state once per character, increasing selection/render latency and GC churn.

**Evidence:** getActiveWindow() delegates to getActiveDocument(). The changed line uses Array.from(...).filter(...), whereas the deleted code used one Array.from(...).map(...) followed by a short-circuiting find(). In src/vs/editor/browser/viewParts/viewLinesGpu/viewLinesGpu.ts, \_visibleRangesForLineRange calls getActiveWindow().devicePixelRatio inside both character loops (lines 683 and 701), establishing a real per-character hot path. The new launcher keeps an auxiliary window registered after hide, so its normal warm state bypasses getActiveDocument's single-window fast path.

**Suggested direction:** Check the last-focused registered window directly first, then use a single iterator pass for the fallback; avoid constructing either a windows list or a filtered list while preserving the last-focused semantics.

### 2. [low] Evict the hidden launcher window after an idle period

**Finding ID:** `PERF-8AC0087EA5C3`  
**Location:** <code>src/vs/sessions/contrib/agentsLauncher/electron-browser/agentsLauncher.contribution.ts:264</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** one native auxiliary window plus the complete NewChatView/ChatWidget DOM, input editor, scoped services, resize observer, and event subscriptions  
**Scaling:** The retained set is bounded to one launcher per Agents window, but its cost persists for the entire remaining Agents-window lifetime after a single use, even if the launcher is never shown again.  
**Outcome:** Persistently elevated renderer/native-window memory and background subscription overhead after dismissal.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no launcher auxiliary window or launcher chat widget retained after use.  
**Changed behavior:** hide() only hides the native window; the auxiliary window, full composer view, observer, and window-scoped disposables remain owned until Chat is disabled, AI is hidden, the user closes the auxiliary window, or the Agents window is disposed.  
**Confidence:** 0.93 — Ownership and disposal paths directly prove lifetime retention after first use. The exact retained byte count is not measured and the cache is intentionally bounded to one window, so the finding is low severity.

**Causal diff evidence:** RIGHT line 264 makes dismissal use presenter.hide(), which preserves the added auxiliary window and its complete rendered composer rather than disposing the window-owned resources.

A user who summons the launcher once and dismisses it keeps a full hidden chat UI and native auxiliary window alive for a potentially days-long Agents-window session, so process memory does not return to its prior baseline.

**Evidence:** \_renderComposer creates a SessionHost, child instantiation service, and complete createNewChatView result and installs layout, keyboard, unload, and ResizeObserver listeners (lines 347-399). The presentation hide callback only calls native hide and view.setVisible(false) (lines 123-132), and this hide method returns that path without clearing \_auxiliaryWindow or \_windowDisposables. \_destroyWindow, which actually disposes these resources, is only reached for disablement or service disposal (lines 510-526). The separate ChatWindowComposerModel owns the draft, so preserving the draft does not require retaining the rendered window indefinitely.

**Suggested direction:** Keep the composer model/draft, but dispose the auxiliary window and its window-scoped view after a bounded idle timeout; cancel that eviction on a quick re-show so warm-toggle latency remains fast.

- Cache behavior: Cold miss creates the Agents window if absent and one auxiliary launcher window. A warm invocation reuses both; failed/disabled preparation is not negatively cached.
- Mechanism confidence: High: all boundaries and coalescing behavior are explicit in the changed call path.

- Mechanism confidence: High: the hide and destroy ownership paths prove the complete window/view survives indefinitely after first use.

### Scenario 4: Agents-window editor rendering after an auxiliary window is registered, including while the launcher is hidden

- Effective concurrency: Synchronous on the UI/rendering thread; no limiter or deferral is possible once invoked.
- Cache behavior: No result is cached. The launcher remaining registered while hidden keeps this path warm but permanently outside the single-window fast path.
- Mechanism confidence: High: the changed allocation pattern and per-character caller are directly present in repository code.
- Magnitude uncertainty: Prevalence depends on GPU rendering, non-ASCII line length, and number of auxiliary windows; the added allocation and scan multiplicity are certain.
- Expensive boundaries: none found
- Verdict: Reported the allocation/full-scan regression because it adds CPU and GC work to a proven per-character rendering path.

- Mechanism confidence: High for one-request cardinality and launcher IPC; provider implementation details vary but are unchanged by this PR.
