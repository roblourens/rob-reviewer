# Performance review: sessions: hold the custom agents spotlight until 3 Agents window requests

[PR #348151](https://github.com/microsoft/vscode/pull/348151) at `cc259eb6051b82be5d0e40fedabddb10b6f14cfc`

## Findings (1)

### 1. [medium] Cache the selected agent’s provenance instead of re-enumerating providers on every send

**Finding ID:** `PERF-9B2C9ED59F85`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/customAgentUsage.contribution.ts:33</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** extension-host IPC calls, extension provider discovery work, and readonly-file update work  
**Scaling:** For Agent Host sessions, cost grows as accepted custom-agent requests × registered custom-agent providers; queued requests launch independent, overlapping enumerations because the listener discards the promise and has no cache or coalescing.  
**Outcome:** excessive IPC and extension-host/filesystem work, reducing extension-host throughput and responsiveness during repeated or queued Agent Host requests  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this contribution, accepting an Agent Host request did not resolve the complete custom-agent inventory. Agent metadata was enumerated only for consumers such as the picker/customization UI; request acceptance itself performed no provider-listing IPC for usage accounting.  
**Changed behavior:** Each accepted non-builtin request with a mode URI now calls ICustomizationHarnessService.getCustomAgents. For Agent Host harnesses this invokes AgentCustomizationItemProvider.provideCustomAgents, whose getAgentSources calls listPromptFilesForStorage(extension) on every invocation.  
**Confidence:** 0.97 — The changed event path, uncached Agent Host provider path, explicit extension-host proxy call, and per-request/queued multiplicity are all directly traced in repository code. Exact provider cost and number of affected users vary, so severity is medium rather than high; the repeated IPC mechanism itself is not speculative.

**Causal diff evidence:** RIGHT line 33 newly invokes customizationHarnessService.getCustomAgents for every accepted non-builtin request with a URI; no request-acceptance listener performed this inventory/provider enumeration before the PR.

Using a custom agent in an Agent Host session now causes a full extension-agent source resolution after every send. With one or more ChatCustomAgentProviders, each send activates the provider event and invokes every provider across the extension-host boundary; several queued sends can multiply that work concurrently even though only the selected agent’s built-in/custom classification is needed.

**Evidence:** The added call at line 33 reaches CustomizationHarnessServiceBase.getCustomAgents -&gt; AgentCustomizationItemProvider.provideCustomAgents -&gt; getAgentSources -&gt; PromptsService.listPromptFilesForStorage(PromptsStorage.extension). ExtensionPromptFileService.getExtensionPromptFiles has no cache and \_listFromProviders calls each provider's providePromptFiles sequentially; MainThreadChatAgents2 implements that call with this.\_proxy.$providePromptFiles, an extension-host IPC. The onDidAcceptRequest listener starts recordRequest without awaiting or coalescing it, so queued accepted requests can run separate passes concurrently. The normal local prompts-service path has CachedPromise, but the Agent Host item-provider path does not.

**Suggested direction:** Record or retain the selected mode’s provenance when modes are produced and pass that classification with modeInfo, or cache classification by session/type and mode URI with invalidation from onDidChangeCustomAgents. At minimum, coalesce in-flight inventory resolution so queued sends share one provider enumeration.
