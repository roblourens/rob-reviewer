### Scenario 2: Open or switch a title-bar or compact menubar menu

- Critical path: showCustomMenu constructs and lays out the menu, then the new alignment helper walks the short ancestor chain for CSS zoom, reads the holder rect, and writes adjusted inline insets before focus/open completion.
- Scaling input: The helper's own style traversal scales with fixed DOM ancestor depth and runs once per opened menu. Browser rect resolution can depend on the constructed menu subtree, but the constructor has already synchronously scanned that same subtree and there is no loop over actions introduced by the diff.
- Effective concurrency: One active custom menu at a time; opening or switching menus executes synchronously and sequentially with no queued or parallel reads.
- Cache behavior: No cache is used or needed. Each newly created holder is measured once; repeat calls across separate opens act on new menu DOM.
- Mechanism confidence: High that the new synchronous read exists; high that cardinality is one per menu open/switch and does not fan out. Confidence is low that it causes a material regression because surrounding construction already forces menu measurements.
- Magnitude uncertainty: The exact cost of the final rect read depends on browser dirty-layout state and menu size. Code evidence shows bounded once-per-open cardinality and an existing constructor layout scan, so there is no concrete evidence of user-visible latency or a meaningful scaling amplification.
- Expensive boundaries:
  - other at <code>src/vs/base/browser/ui/menu/menubar.ts:MenuBar.showCustomMenu and src/vs/base/browser/dom.ts:alignToDevicePixels</code>: Computed-style traversal and getBoundingClientRect for the newly constructed menu holder; cardinality: Once for each opened or keyboard-switched menu; only one menu is active and calls are serialized
    - Introduced by diff: true; previous behavior: After constructing the Menu, the code immediately registered handlers and focused it; it did not perform the final zoom/rect read or device-pixel inset adjustment.; critical-path effect: The read is synchronous on menu-open critical path. Menu construction already calls getDomNodeZoomLevel, measures the holder, appends all rows, and scanDomNode reads client/scroll dimensions; the diff adds one final bounded alignment read and inset write rather than per-row or per-frame work.
- Verdict: No reportable regression. The added read is bounded and serialized, with no realistic multiplicity or demonstrated material critical-path cost that meets the performance finding threshold.
