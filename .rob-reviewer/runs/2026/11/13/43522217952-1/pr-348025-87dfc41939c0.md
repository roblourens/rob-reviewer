**Relevant issue families:** repeated-work, boundary-fanout, synchronous-ui-work

### Scenario 1: User moves one or more chats, and any companion editors, from a chat window into the main Agents window.

- Critical path: The command closes the source window, resolves moved chats, opens the first chat and remaining chat groups/sessions, restores companion editors, optionally reselects the first chat, then awaits main-window focus before focusing the active session. All newly added work is on this interaction's critical path; the host focus must complete before DOM focus is assigned.
- Scaling input: The number of chats and companion editors in the one window being moved. Existing chat placement/editor restoration scales with those collections; the diff adds only one extra chat reselection for N&gt;1 and one host-focus call.
- Effective concurrency: The move path is serialized with await. Same-session side chats are already opened sequentially; distinct sessions are grouped before placement. The diff adds no parallel burst or unbounded queue.
- Cache behavior: Chats and sessions are normally warm because they were visible in the source window. Session-resource providers use already surfaced/session-cache state on this path; the second open does not reload an already displayed transcript, and there is no new cache or retained key. Cold legacy migration can cross an agent-host boundary, but a chat already hosted in the window has normally completed that resolution, so the added call uses surfaced state.
- Mechanism confidence: High confidence in the exact constant call counts and sequential critical path from the changed method and service implementations.
- Magnitude uncertainty: Native focus latency varies by platform and provider-resolution cost varies by provider, but both added operations have fixed cardinality per explicit move and no realistic scaling or burst mechanism.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/chatWindow/browser/sessionsChatWindowProvider.ts:823</code>: Focus the native main window through IHostService/nativeHostService.focusWindow; browser builds call Window.focus directly.; cardinality: Exactly one call per successful user-initiated move, independent of the number of chats.
    - Introduced by diff: true; previous behavior: No host-focus boundary was invoked by SessionsChatWindowProvider after moving chats.; critical-path effect: Newly awaited immediately before focusing the active session, so its single round trip contributes to move completion latency but is required to raise the destination window.
  - other expensive boundary at <code>src/vs/sessions/contrib/chatWindow/browser/sessionsChatWindowProvider.ts:821 via SessionsService.openChat</code>: Resolve the first session through registered providers and re-open/reselect its first chat.; cardinality: One additional provider-resolution chain only when at least two chats move; it does not grow with chat count. The normal moved-chat scenario is warm because the session was already displayed in the source chat window, and transcript reopening is a no-op unless an existing load failure has an explicit retry action.
    - Introduced by diff: true; previous behavior: openMovedChats performed the first resolution/open once; there was no final reselection call.; critical-path effect: Sequentially awaited before host focus. Existing openMovedChats already resolves and opens the first chat; the added call repeats selection so the original first chat is active after opening the rest.
  - filesystem at <code>src/vs/sessions/contrib/chatWindow/browser/sessionsChatWindowProvider.ts:828-841</code>: Open serialized companion editor inputs in the main editor group, which can load their backing resources.; cardinality: One batched openEditors request containing the editors captured from the moved window.
    - Introduced by diff: false; previous behavior: The same editors were opened after moved chats with the same restore-state wait and batched openEditors call.; critical-path effect: Awaited before destination-window focus. The diff extracts the unchanged editor restoration into a helper and preserves its prior placement after openMovedChats.
- Verdict: No reportable regression. The added constant work is necessary to raise and focus the destination and preserve the intended active-chat order; it does not fan out with moved-chat cardinality or cause repeated transcript loading.

### Scenario 2: A visible chat group changes presentation kind, such as a new-session composer becoming a chat after a request starts.

- Critical path: The group's reactive autorun computes the desired kind, creates and installs the replacement view, lays it out, binds the chat, and now restores focus only if the detached old view contained focus and that document still owns window focus.
- Scaling input: One affected ChatGroupView per presentation-kind transition. The added ancestry check walks only the focused element's DOM ancestors within that group, and focus is invoked once per actual replacement rather than on every autorun update.
- Effective concurrency: Synchronous UI work in the autorun; no async fan-out, queue, IPC, filesystem, database, subprocess, or network boundary is reached by the added focus predicate/action.
- Cache behavior: No cache is read or introduced. Existing view construction and transcript binding behavior is unchanged; the added state is a transient boolean.
- Mechanism confidence: High confidence from the replacingView guard, DOM ancestry/window-focus predicates, and direct ChatView/NewChatView focus implementations.
- Magnitude uncertainty: Browser focus can trigger style/focus-event work dependent on listeners, but this occurs once at a user-visible view replacement and only when focus was already inside the replaced subtree.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added synchronous DOM work is bounded to actual view replacement and restores focus rather than adding per-render, per-frame, or collection-scaling work.

### Scenario 3: Updated browser tests capture retained pane DOM elements and exercise focus restoration/provider focus ordering.

- Magnitude uncertainty: None relevant to shipped performance because these files execute only in tests.
