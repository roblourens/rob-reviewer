### Scenario 2: Docker capability discovery and Dev Container choices for SSH/Tunnel hosts using Use Remote VS Code

- Critical path: A newly advertised capability permits asynchronous Docker discovery after host initialization. Create Dev Container visibility waits for the discovery result. Workspace-specific availability first checks the two supported configuration paths and then Docker availability; ordinary host connection and picker rendering do not await these checks.
- Scaling input: H distinct configured connected hosts for environment discovery and W distinct provider/workspace keys for workspace availability. Docker RPCs for workspace checks occur only for workspaces with configuration.
- Effective concurrency: Picker availability uses a shared Limiter(4); each job issues two configuration checks in parallel. Distinct host discovery RPCs can overlap, but repeated checks for the same connection are coalesced and all Docker lookups within a service share one promise.
- Cache behavior: Host discovery caches pending/success/false/error-as-unavailable by connection identity and removes unconfigured hosts. Docker executable resolution caches the promise including undefined. Picker availability caches promises, booleans, and errors by provider plus normalized workspace URI, with existing invalidation and explicit error retry.
- Mechanism confidence: High: capability gates, client RPC adapter, service lookup cache, file-provider boundary, and picker limiter/cache were inspected.
- Magnitude uncertainty: Host/workspace counts, network RTT, and slow PATH filesystem prevalence are not measured.
- Expensive boundaries:

### Scenario 3: First prompt in a remote workspace container, explicit Create Dev Container, and reconnecting stored remote environments

- Critical path: Workspace launches request trust before invoking the launcher. Container preparation, CLI setup, endpoint selection, and relay establishment must finish before container sessions can proceed. New environments are explicitly created; stored remote environments follow source-host connection changes through existing reconciliation. Unrelated source-host session listing does not await these launches.
- Scaling input: One launch per requested workspace or environment, or E stored environments belonging to a reconnected host. Repeated attempts for one environment share state.pending; operations for the same source key are serialized.
- Effective concurrency: DevContainerAgentHostService uses SequencerByKey for each workspace/environment source, not a global limiter. Distinct stored environments can reconnect concurrently; state.pending coalesces duplicate environment connects and each environment has its own operations sequencer. This scheduling architecture is unchanged.
- Cache behavior: Executable and shell-environment resolution are shared. Native certificates are loaded once and client certificates once per provider connection. Certificate files are content-addressed. Environment volumes, Docker images, shared CLI/server caches, matching CLI executables, and live Agent Host endpoints are reused. Existing failure/cancellation cleanup remains in place.
- Mechanism confidence: High: launch ownership, environment reconciliation, sequencers, subprocess creation, cold/warm installer behavior, and cancellation cleanup were traced.

### Scenario 4: Container protocol traffic, disconnect/cancellation, and explicit stop/removal

- Critical path: Container messages traverse the existing source connection and the devcontainer-exec relay. Disconnect cancels active work and disposes the relay; explicit stop/removal awaits source-key-serialized Docker lifecycle operations. These operations are not part of editor startup or workspace picker rendering.
- Scaling input: M messages/bytes for active container connections; C active relays on disconnect; lifecycle work for the selected workspace/environment and its matching containers/volumes.
- Effective concurrency: Same-source lifecycle actions share the launcher's SequencerByKey. Disconnecting several active relays may overlap but does not start replacement relays. Message forwarding filters by ownership; no new broadcast fan-out is introduced.
- Cache behavior: Connection maps are removed on disconnect, failure, or close. Protocol adapters are owned by transport initializationDisposables; closing the transport disposes subscriptions and disconnects started launches. Launcher disposable maps release relay processes and stores. Lifecycle operations reuse recorded container IDs and group matching resources.
- Mechanism confidence: High: transport-close disposal, protocol ownership maps, service cleanup, relay disposal, and grouped lifecycle operations were inspected.
- Magnitude uncertainty: Traffic volume, container process counts in the existing session scan, and Docker shutdown duration are unmeasured.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/agentHost/common/devContainerAgentHostProtocolClient.ts:relaySend; src/vs/platform/agentHost/node/devContainerAgentHostProtocol.ts:\_forward; src/vs/platform/agentHost/node/devContainerAgentHostService.ts:\_createRelay/relaySend</code>: Wrap container messages in source-host RPCs/notifications and forward them to or from the relay WebSocket.; cardinality: One wrapper per actual container message; notifications are forwarded only to the adapter owning the connection ID, not to every client.
    - Introduced by diff: true; previous behavior: Container relaying was unavailable on the editor endpoint; the same framing/forwarding implementation already served other supported hosts.; critical-path effect: Affects active container message delivery only.
  - subprocess at <code>src/vs/platform/agentHost/node/devContainerAgentHostService.ts:\_disconnect; DevContainerRelay.dispose; \_changeContainerState/\_removeEnvironment</code>: Kill disposed relay subprocesses; inspect active container sessions and stop/remove requested containers or environment volumes.; cardinality: One relay disposal per active connection. Workspace lifecycle typically performs a session-check Docker exec and one stop/rm command; environment removal uses scoped lookup commands and grouped rm calls for matching IDs/volumes.
    - Introduced by diff: true; previous behavior: Unavailable through this endpoint; underlying disposal, lifecycle grouping, and per-source ordering are unchanged.; critical-path effect: Disconnect releases resources immediately; explicit lifecycle actions wait for their Docker commands.
  - filesystem at <code>src/vs/platform/agentHost/node/devContainerEnvironments.ts:removeDevContainerEnvironment</code>: Remove an explicitly deleted environment's cached configuration directory.; cardinality: One recursive removal for the selected environment.
    - Introduced by diff: true; previous behavior: Same existing cleanup became accessible through the newly enabled endpoint.; critical-path effect: Part of explicit environment deletion only.
- Verdict: No reportable retention, cleanup, serialization, or boundary-fan-out regression. Existing behavior is exposed on another endpoint without increasing per-message copies or losing resource ownership.
