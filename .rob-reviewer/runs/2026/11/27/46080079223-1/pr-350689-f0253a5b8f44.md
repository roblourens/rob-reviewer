# Performance review: agent host: fix: refresh local plugin copies on nested file changes

[PR #350689](https://github.com/microsoft/vscode/pull/350689) at `f0253a5b8f4443980a2e533e5919c57101d840b1`

## Findings (1)

### 1. [medium] Cache and coalesce unchanged plugin fingerprints

**Finding ID:** `PERF-00AA97E9B444`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLocalCustomizations.ts:338</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Filesystem metadata/readdir operations and their main-process or remote IPC calls.  
**Scaling:** For a non-symlink tree with F files and D non-root directories below the 2,000-entry limit, each scan performs F+D+1 provider stat calls and D+1 readdir calls. Work multiplies by the number of distinct live harness/root scopes and issued refreshes, not by sessions sharing a scope. The 16-entry limit is per scan, not global; simultaneous scopes and overlapping updates run independent batches. Warm host-copy caches do not avoid this work, and oversized-tree fallback tokens are consulted only after another scan reaches overflow.  
**Outcome:** Increased filesystem/IPC traffic and customization-resolution latency, with initial active-client claiming blocked on redundant scans.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The same scope initialization or refresh obtained one root mtime stat per forwarded plugin. Identical scopes were already shared and refreshes already debounced, but an unchanged plugin did not incur a full-tree metadata traversal on each resolution.  
**Changed behavior:** Every scope initialization and debounced customization refresh now walks every forwarded plugin tree, including unchanged plugins, before it can publish refs. Identical plugin instances are scanned separately across working-directory/harness scopes and across overlapping refreshes.  
**Confidence:** 0.98 — The scope map is keyed by session type and normalized roots, not plugin URI; every scope subscribes to the same customization-change event. The traversal has no nonce-result or in-flight cache, and FileService forwards stat/readdir to the filesystem provider. Desktop provider calls cross main-process IPC; remote providers use the remote channel. Exact latency and typical plugin sizes are unmeasured.

**Causal diff evidence:** agentHostLocalCustomizations.ts:338 replaces the single root fileService.stat(plugin.uri) with computePluginNonce on every toPluginRef call. The added traversal at lines 256-288 resolves every directory and stats every file, without memoizing or joining scans. resolveCustomizationRefs still maps all forwarded plugins for each scope resolution.

With a sizeable local plugin installed, starting a chat in a new working-directory scope re-scans the plugin even if an ambient scope already resolved it. Editing an unrelated prompt, changing MCP definitions, or toggling sync enablement also re-scans all unchanged plugins in every live scope. This adds potentially thousands of filesystem/IPC operations and delays initial active-client readiness; slower or remote filesystems amplify the delay and overlapping refreshes waste further I/O.

**Evidence:** AgentCustomizationScope.updateCustomizations (agentHostActiveClientService.ts:148-180) awaits resolveCustomizationRefs before completing initial resolution; each scope subscribes to global source changes at 189-190. acquireScope (287-309) shares only identical session-type/root scopes, while agentHostChatContribution.ts:412 creates an additional ambient scope for each harness. FileService.doResolveFile/toFileStat (fileService.ts:209-277) performs a provider stat plus readdir per directory; FileService.stat (315-320) performs another provider stat per file. diskFileSystemProviderClient.ts:81-90 forwards each operation through channel.call. ActiveClientEntry.claim (agentHostSessionHandler.ts:1304) waits for scope.whenResolved. The 50 ms Delayer only coalesces work before execution; async.ts:450-455 clears its pending promise before running the task, so a later refresh can start another scan while the earlier scan is still running.

**Suggested direction:** Memoize and coalesce the computed nonce for watched plugins using the plugin instance and contentVersion already introduced by this PR. Invalidate on a version change or plugin replacement, avoid caching a scan against a version that changed while it ran, and retain a fresh-scan fallback for plugins without a reliable contentVersion.

### Scenario 3: Oversized plugin trees exceeding the 2,000-entry fingerprint budget, including restart and unchanged refreshes

- Critical path: computePluginNonce starts resolving/listing the tree and only switches to getOverflowPluginNonce after enqueueChildren detects overflow. A defined fallback nonce then permits normal ref publication and downstream copy caching.
- Scaling input: The scanned prefix up to overflow, width of each resolved directory, distinct plugin instances/contentVersion values, and S distinct scopes. A root with more than 2,000 children exits before child stats but still performs a root resolve/listing and sorts that listing.
- Effective concurrency: The same 16-entry batches and independent per-scope scans apply until overflow. Queue and hashed parts are entry-budgeted, but a directory listing and its child sorting happen before detecting that directory's overflow. Watcher revisions are computed synchronously after the scan returns undefined.
- Cache behavior: WeakMap tokens are stable for an unchanged plugin instance/version, advance on watched edits, and rotate on replacement/restart. They do not cache the fact of overflow or prevent subsequent prefix scans. Host revision copies can be reused for stable fallback tokens; restart rotation intentionally makes them miss.
- Mechanism confidence: High for repeating the overflow prefix scan despite warm fallback tokens. No independent high-confidence catastrophic memory issue was established.
- Magnitude uncertainty: Tree shapes determine how much of the budget is read before overflow. Wide-list allocation/sorting costs and full-copy sizes were not measured.
- Expensive boundaries:
