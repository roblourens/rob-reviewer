## Findings (3)

### 1. [medium] Keep passive repository reads off changeset-operation completion

**Finding ID:** `PERF-506D7CEDC09D`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostGitStateService.ts:700</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Git subprocesses, especially repository-wide git status and associated filesystem traversal  
**Scaling:** Each selected distinct checkout starts three initial Git commands plus optional base/upstream probes. Up to 16 discovered checkouts are awaited for a one-folder session; with gitCoalesceReads enabled commands share the global eight-read limiter, while the default false setting launches them without that limiter. Completion depends on the slowest read or on multiple limiter waves.  
**Outcome:** Increased changeset-operation response latency and prolonged Running status because unrelated large or slow checkouts block completion  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After a changesGitState operation, the refresh read the source checkout (and the session checkout when applicable); unrelated nested checkouts were not read before completing the operation.  
**Changed behavior:** Once discovery is cached, completing the same operation also waits for passive state reads of up to min(unique discovered roots, max(0,16-(session folders-1))) unrelated checkouts. Unlike cold discovery, these warm reads are not background work.  
**Confidence:** 0.98 — The added await reaches \_applyDiscoveredRepositories on every warm-cache refresh, which awaits all selected Git reads. The unchanged operation service explicitly awaits this refresh before publishing Idle and returning the operation result. The delay magnitude depends on checkout and disk size, not on an uncertain call path.

**Causal diff evidence:** The added await at line 700 invokes \_refreshSessionRepositories before the refresh event and refresh completion. Its new warm-cache branch at line 888 returns \_applyDiscoveredRepositories, whose line 959 awaits Promise.all of discovered-root Git-state reads. No such discovered-repository work existed in the base refresh.

Discarding a file or another Git-changing operation in the primary checkout can remain Running until an unrelated discovered checkout finishes git status. Each Git command has a 30-second default timeout. This affects warm-cache sessions even though discovery itself is backgrounded.

**Evidence:** AgentHostChangesetOperationService.\_executeChangesetOperation lines 489-506 awaits \_refreshGitState before publishing Idle and returning. \_refreshGitState lines 80-87 awaits the source/session refresh. AgentHostDiscardChangesOperationHandler line 109 sets changesGitState=true. The new \_refreshSessionRepositories line 888 awaits \_applyDiscoveredRepositories; lines 958-959 select and await discovered-root reads. AgentHostGitService.\_computeSessionGitState lines 1888-1906 resolves each root and runs status -b --porcelain=v2, remote -v, and symbolic-ref. \_spawnGit uses the 30-second default timeout.

**Suggested direction:** Publish and complete the authoritative source/session-checkout refresh without waiting for passive additional/discovered-checkout reads; run those reads in a coalesced background lane with the existing generation guards and announce their results separately.

### 2. [medium] Share additional-folder Git reads by checkout root

**Finding ID:** `PERF-8D5DA18F1F86`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostGitStateService.ts:759</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Duplicate git status traversals, Git subprocesses, filesystem reads, and status-output parsing  
**Scaling:** For F additional eligible folder URIs under one checkout, F&lt;=16, the default configuration starts F identical status commands plus F remote and F symbolic-ref commands before optional probes, even though the effective checkout/default-base group count is one. Command coalescing, when explicitly enabled, reduces overlapping identical probes but does not provide grouping in the default configuration.  
**Outcome:** Redundant CPU/filesystem work and subprocess contention on every refresh, increasing latency and reducing host throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A session containing several subfolders of one monorepo read its primary checkout once during a session refresh; it did not automatically reread that checkout for each additional session folder.  
**Changed behavior:** The session now computes the same root-wide default-base Git state once per additional folder URI, although all those calls resolve to the same checkout and return equivalent data.  
**Confidence:** 0.98 — The PR explicitly supports different folder paths within the same checkout, including a new test. \_readGitState keys in-flight reads by the original folder URI, but \_computeSessionGitState executes all probes at the resolved checkout root. The production schema defaults command coalescing to false, establishing duplicate processes rather than merely duplicate helper calls.

**Causal diff evidence:** The new folders.map loop at lines 752-759 calls \_readGitState separately for every additional workingDirectory. Its unchanged in-flight key includes workingDirectory.toString(), so distinct subfolders of the same root are not grouped. The base session refresh did not enumerate and read these additional folders.

A multi-root workspace that opens several packages of the same large monorepo repeatedly runs repository-wide git status for each package after file changes or explicit refreshes. Sixteen additional folders can issue 48 initial commands for a single checkout, in addition to the primary refresh.

**Evidence:** The new test at agentHostGitStateService.test.ts around lines 3357-3385 uses file:///repo/sub and file:///repo/other and confirms both resolve to file:///repo. The added loop calls \_readGitState at line 759 for each URI. \_readGitState lines 1161 onward keys by original URI and baseBranchRef. AgentHostGitService.getSessionGitState lines 1553-1554 always computes state, and \_computeSessionGitState lines 1888-1906 runs all probes at repositoryRoot. agentHostSchema.ts lines 1178-1182 defaults gitCoalesceReads to false.

**Suggested direction:** Resolve each additional folder's cached checkout root and group its Git-state read by normalized root and base-branch input, then apply the shared result to each folder scope. Keep primary reads with a different configured base separate and preserve per-folder non-repository classification.

### 3. [medium] Bound directory entries before allocating and sorting them

**Finding ID:** `PERF-E8E12504609A`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostGitService.ts:503</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Dirent objects and strings for the whole directory, sort temporary storage, and synchronous localeCompare comparisons on the agent-host event loop  
**Scaling:** A scanned directory containing N entries allocates O(N) objects and performs O(N log N) comparisons. The 10,000-probe and five-second start-deadline budgets do not bound N; one readdir consumes only one probe. The work repeats on rediscovery after 60 seconds, or eligible forced refreshes after 30 seconds.  
**Outcome:** Agent-host event-loop stalls and memory/GC spikes despite repository discovery being scheduled in the background  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Session Git-state refreshes did not enumerate and sort scanned subdirectories for repository discovery.  
**Changed behavior:** Each scanned directory is fully materialized and sorted, including every ordinary file, even when no repository can be found there or the discovery deadline expired during readdir.  
**Confidence:** 0.97 — The new code materializes the entire directory and synchronously sorts it before the first loop-body budget check or file/directory filter. The budget charges one readdir operation, not entries or comparisons. The exact pause depends on directory size, but the unbounded allocation and synchronous O(N log N) work are directly established.

**Causal diff evidence:** Added lines 502-503 read all Dirents using readdir and immediately sort them with localeCompare. Added lines 504-509 check done() and reject ordinary files only after sorting. Repository discovery and this work did not exist in the base revision.

Scanning a large generated-output, dataset, or cache directory containing tens or hundreds of thousands of files blocks other agent-host requests while sorting entries that are then all discarded as non-directories. A deep or unlimited-depth detection setting can reach such folders.

**Evidence:** findRepositories lines 399-400 defines done() and charges each boundary call once. Lines 502-509 materialize and sort entries before checking done() or entry.isDirectory(). The discovery caller supplies a shared 10,000-probe/five-second budget and revisits the scan via \_refreshSessionRepositories. Existing worktreeDiskUsage.ts lines 183-194 demonstrates fs.opendir-based incremental directory iteration in this subsystem.

**Suggested direction:** Use bounded directory iteration, charge/check the entry budget while consuming results, and sort only a bounded set of eligible directory candidates. Stop before allocating or sorting the rest of a huge directory when the deadline or entry cap is reached.
