## Findings (2)

### 1. [medium] Bound DOM wrapping for large floating replies

**Finding ID:** `PERF-124360E0C6E2`  
**Location:** <code>src/vs/workbench/contrib/comments/browser/commentReply.ts:107</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Temporary DOM nodes, HTML and per-character arrays, browser text layout, and Range.getClientRects queries for the entire reply draft.  
**Scaling:** For one reply editor, whole-draft allocation/layout scales with total draft characters and lines, multiplied by distinct wrapping-column changes during resizing. Identical widths/columns are deduplicated; ordinary edits need not rewrap the entire draft.  
**Outcome:** Increased paste/restore latency and renderer-main-thread blocking during interactive horizontal resizing, with additional allocation and GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Outside accessibility mode, SimpleCommentEditor used the default simple strategy with the configured editor font. Whole-model wrapping on initialization or width changes used MonospaceLineBreaksComputerFactory rather than live browser DOM measurement.  
**Changed behavior:** All floating replies now use browser-based wrapping regardless of draft size. Full-model initialization and each distinct wrapping-column change allocate and measure a temporary DOM representation of the complete draft.  
**Confidence:** 0.96 — The override selects the DOM factory directly. The traced resize path synchronously rebuilds projections for all draft lines when the wrapping column changes, and the factory constructs live DOM and reads character ranges without reusing previous break data. Duration depends on draft size; no timings were measured.

**Causal diff evidence:** Added wrappingStrategy: 'advanced' at commentReply.ts:107 replaces the normal default 'simple' strategy for every floating reply, including large pasted or restored drafts.

Pasting/restoring a lengthy review draft containing logs or code, then dragging the card's horizontal resize handle, now performs whole-draft DOM construction and synchronous layout repeatedly on the renderer input path, causing stalls and dropped resize frames.

**Evidence:** ReviewFloatingWidget.\_onResize calls \_setWidth, which calls CommentThreadWidget.layout and CommentReply.layout. ViewModelLines.setWrappingSettings calls \_constructLines for changed wrapping columns; \_constructLines requests every model line. DOMLineBreaksComputerFactory ignores previousLineBreakData, builds HTML and per-character arrays for all requests, attaches the container to document.body, and discovers breaks through Range.getClientRects (domLineBreaksComputer.ts:29-36, 83-175, 409-472). The reply's capped height does not limit these requests.

**Suggested direction:** Keep proportional/advanced wrapping for ordinary replies but add a large-draft fallback that switches font and wrapping strategy together to the existing monospace/simple path, or defer expensive large-draft width reflows until the resize settles.

### 2. [medium] Suspend live card blur during movement

**Finding ID:** `PERF-DC65B0F06CF4`  
**Location:** <code>src/vs/workbench/contrib/modernUI/browser/media/frostedGlass.css:147</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** GPU backdrop sampling, blur passes, and intermediate compositor surfaces for each affected visible card.  
**Scaling:** Scales with the sum of affected visible cards' physical pixel areas and invalidated frames. Detached cards do not contribute; GPU eligibility does not bound area or card count.  
**Outcome:** Increased frame-production cost and dropped drag, resize, or scrolling frames.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Floating cards painted an opaque peekViewResult background and existing shadow, without a card-sized backdrop blur during dragging, resizing, or scrolling.  
**Changed behavior:** Each eligible visible card now has a live, full-area blur layer that stays enabled during movement and backdrop changes.  
**Confidence:** 0.90 — The new selector reaches the full-size pseudo-element's blur(12px). Existing drag, resize, and horizontal-scroll paths change its size or sampled backdrop continuously without disabling the filter. Added compositor work is statically established; duration depends on GPU, pixel density, and visible card area.

**Causal diff evidence:** The added floating-widget selector at frostedGlass.css:147 applies the existing full-size backdrop-filter pseudo-element to previously solid comment cards.

With floating comments and Modern UI glass enabled, dragging/resizing a large card over code or horizontally scrolling code behind cards adds repeated full-area filtering, degrading smoothness on high-DPI or lower-powered accelerated GPUs.

**Evidence:** frostedGlass.css:155-173 creates a width:100%, height:100% ::before with backdrop-filter:blur(12px), without a motion exclusion. ReviewFloatingWidget's header-drag callback and \_onResize call \_render; \_attach subscribes to both vertical and horizontal scrolling. \_render updates overlay placement, while horizontal scrolling changes code underneath cards. Independently expanded widgets have independent materials, without shared filtering or motion suppression.

**Suggested direction:** Use the solid theme background during dragging/resizing or backdrop scrolling, and restore glass after a coalesced settled notification, preserving existing capability and transparency gates.

- Mechanism confidence: High: direct option-to-factory selection and the complete resize-to-projection-to-browser-measurement path were traced.

### Scenario 3: Drag or resize visible cards, or horizontally scroll code behind them with glass enabled

- Critical path: Drag callbacks, resize callbacks, and scroll listeners update card geometry; the compositor must then produce the frame. The newly applied full-size material filters the changing sampled backdrop before that frame can be presented.
- Scaling input: Affected visible card count, physical pixel area of each card, and invalidated frames. Hidden/collapsed cards are detached. Cards can overlap code after user placement; horizontal code scrolling changes the backdrop even when their horizontal placement stays fixed.
- Effective concurrency: Each attached widget has its own direct scroll listener. Dragging targets one card; several cards may have changing backdrops simultaneously. Model/content/view-zone notifications are animation-frame coalesced, but scroll/drag updates and compositor filtering have no new global limiter.
- Cache behavior: Code-line extents have existing invalidation and caching. Header midpoint is cached until reattachment. Connector outline strings are deduplicated as before; the added connector path and min/max scans are bounded by visible range rectangles. No application snapshot or settled-state cache bounds the new live material.
- Mechanism confidence: High confidence in newly enabled full-area filtering and direct interactive reachability. The cached geometry additions do not independently establish a significant regression.
- Magnitude uncertainty: GPU speed, device pixel ratio, surface size, overlap, and number of visible cards determine the frame-time impact; no compositor trace was collected.
- Expensive boundaries:
