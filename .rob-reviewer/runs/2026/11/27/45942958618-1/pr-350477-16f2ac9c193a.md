### Scenario 1: Desktop and mobile entry startup, including restoring an open Automations page

- Critical path: Entry modules and BlockRestore registrations must load before restoration. View construction occurs only when the custom view is mounted; a restored page renders cached/provider state without awaiting its background refresh.
- Scaling input: Entry dependency graph and number of connected provider stores; no new per-schedule startup instantiation.
- Effective concurrency: BlockRestore contribution registration is synchronous; asynchronous provider loading retains its existing scheduling. No new startup fan-out was identified.
- Cache behavior: Existing module cache and provider-owned observable catalogue state are reused. Presentation services remain delayed; custom view ownership releases mounted views when replaced.
- Mechanism confidence: High confidence from entry import diffs, delayed singleton registration, CustomViewService registration, and CustomViewNode ownership.
- Magnitude uncertainty: Bundle byte sizes and actual cold-start duration were not measured; historical provenance does not establish a specific shipped regression fix.
- Expensive boundaries:
  - network at <code>src/vs/sessions/sessions.common.main.ts and src/vs/sessions/agents.web.mobile.main.ts contribution imports</code>: Load Automations presentation modules and CSS with the selected entry.; cardinality: One entry-selected presentation dependency graph; desktop retains its existing cards, catalogue editor, and dialog dependencies, while mobile no longer imports those desktop presentations.

  - IPC at <code>src/vs/workbench/contrib/sessions/providers/agentHost/browser/agentHostAutomationStore.ts constructor</code>: Acquire an authoritative AutomationCatalog subscription for an agent host.; cardinality: One subscription per connected provider store, not per rendered automation or history row.
    - Introduced by diff: false; previous behavior: The same provider-owned subscriptions supplied the desktop presentation mounted on mobile.; critical-path effect: Provider state arrives asynchronously; the page can show loading/cached state.
- Verdict: No reportable regression. Mobile dependency isolation removes desktop presentation work; desktop registrations are relocated rather than duplicated.

### Scenario 2: Open Automations, refresh the catalogue, retry failures, and observe recent-run updates

- Critical path: Synchronous view rendering shows available state immediately. Automatic refresh is off the navigation critical path; explicit Retry awaits the existing provider refresh to publish updated schedules and history.
- Scaling input: Visible schedules N, retained runs R, catalogued sessions S, and distinct cloud repositories G. Session resolution builds maps in O(S+R); history initially displays 10 runs plus active/focused exceptions and grows by pages of 20.
- Effective concurrency: Provider refresh uses Promise.all across stores. Each cloud store serializes catalogue/history/mutations through its existing Sequencer; repository catalogue requests are sequential, and history uses a four-worker limiter. The scheduler is cancelled while refreshing and disposed with the view; active-cloud history polling remains the existing 15-second cadence.
- Cache behavior: Provider catalogue/history snapshots survive failures. Definition refreshes join refreshPromise; history refreshes join historyRefresh. Background refresh preserves target-eligibility caches; foreground Retry clears existing eligibility/failure caches. Cached rendering does not eliminate the intentional refresh requests.
- Mechanism confidence: High confidence from the extracted scheduler's exact before/after match and traced cloud provider/store implementations.
- Magnitude uncertainty: Real catalogue sizes, number of active tasks, and request durations are unknown. No runtime profiling was performed.
- Expensive boundaries:

    - Introduced by diff: false; previous behavior: AutomationsCardsWidget used the identical immediate refresh and 60-second scheduler and the same provider implementation.; critical-path effect: Background on page entry and the 60-second cadence; completion is necessary to replace cached catalogue data.

### Scenario 3: Create or edit an automation, choose a template/workspace, save, and dismiss with Cancel or browser Back

- Critical path: The requested form constructs its prompt editor and controls synchronously. Saving waits for draft synchronization, customization choices, configuration capture, and then the selected provider's authoritative persistence. Browser Back is held only during commit.
- Scaling input: Repository search results, selected-target customizations, template count, prompt size, and actual target changes. Three schedule selects are constructed, irrespective of total saved schedule count.
- Effective concurrency: Save is guarded by saveInProgress. Draft synchronization runs one loop and coalesces pending target changes. Cloud operations retain their per-store Sequencer; target checks retain their five-slot limiter. Navigation registration uses MutableDisposable and replaces rather than accumulates history handles.
- Cache behavior: Templates read existing plugin blueprint observables only when requested on mobile; they do not add file reads. Customization loads deduplicate an unchanged serialized target key. Shared draft synchronization preserves per-target configuration. Existing provider eligibility and catalog caches are retained.
- Mechanism confidence: High confidence from unchanged shared form/capture paths and new surface/button implementations. Gesture.ignoreTarget returns a removable registration owned by each SelectBoxNative.
- Magnitude uncertainty: Provider resolution durations and prompt/customization sizes were not measured; upstream implementation costs remain pre-existing.
- Expensive boundaries:

- Effective concurrency: Cloud requests are serialized through the existing store Sequencer. Host actions retain existing request/state waits. The new scheduled-chat confirmation adds no background or repeated operation.
- Cache behavior: Active cloud runs are checked before dispatch. Provider-owned state supplies enablement and management choices. Mutation-uncertain state prevents repeated blind submissions until refresh, unchanged by this PR.
- Mechanism confidence: High confidence from MobileAutomationsView.manage routing to AutomationCommands and traced unchanged provider mutation methods.
- Magnitude uncertainty: Deletion-history sizes and host/network latency are unknown; no new multiplicity was found.
- Expensive boundaries:

### Scenario 5: Open a recent automation run's conversation and return to Automations

- Critical path: The shared history handler resolves an uncatalogued resource if necessary, then opens one session. SessionsService mounts the conversation before provider preparation/loading completes.
- Scaling input: Run/session catalogue size controls in-memory resolution maps; expensive open operations are selected-run scoped. Rendering initially pages history at 10 runs with active/focused exceptions.
- Effective concurrency: SessionsService cancels superseded opens through its existing navigation token. Reopening and provider preparation are awaited together after mounting; no new multi-run concurrency was introduced.
- Cache behavior: Shared SessionsManagementService catalogue avoids uncatalogued-task resolution for warm resources. History session projections are reused and removed when runs/sessions disappear. Replacing the custom view disposes its history groups and refresh scheduler.
- Mechanism confidence: High confidence from reuse of AutomationHistorySection without an overriding openSession hook and traced SessionsService/provider branches.
- Magnitude uncertainty: Provider-specific chat fetch/reconnect durations were not measured; these downstream operations are unchanged.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/automations/browser/automationRunHistory.ts openRunSession; src/vs/workbench/contrib/sessions/providers/copilotChatSessions/browser/copilotChatSessionsProvider.ts resolveSessionResource</code>: Resolve an uncatalogued cloud task conversation through the existing task resolver/provider activation and session model resolution.; cardinality: Only the clicked run is resolved. Already catalogued tasks bypass the cloud task-resolution branch; the subsequent SessionsService resolution also uses that existing cached state.
    - Introduced by diff: false; previous behavior: The desktop history component on mobile used exactly the same openRunSession handler and session resolver.; critical-path effect: Resource resolution precedes opening the conversation.
  - other expensive boundary at <code>src/vs/workbench/contrib/sessions/browser/sessionsService.ts \_openSession and sessionOpen.ts prepareSessionForOpen</code>: Provider-specific preparation/reconnection and chat loading for the selected session.; cardinality: One selected session's existing preparation/load work, not all recent runs; an already visible chat can be revealed through its existing opener.
    - Introduced by diff: false; previous behavior: Same shared session-open, provider preparation, and readiness path.; critical-path effect: Conversation UI mounts before preparation finishes, but full session readiness waits for provider loading.
- Verdict: No reportable regression. Recent-run navigation preserves the existing expensive call path and caching behavior.

### Scenario 6: Read Automations with Accessible View and interact with phone notifications/native pickers

- Critical path: Accessible content is synchronously assembled on request from in-memory schedules, runs, sessions, and chat models. Notification layout updates when phone-layout mode changes. Native select activation is handled by the browser.
- Scaling input: Accessible text scales with visible schedules and retained runs; existing run/session matching and chat-progress formatting remain shared. Notification row height changes from 44 to 56 pixels without changing notification count or update frequency. Native schedule controls remain three fixed select widgets.
- Effective concurrency: Requested accessibility assembly and notification sizing are synchronous UI work. Notification sizing uses the same layout-policy autorun and reset-on-dispose. No added event-frequency multiplier or forced-layout loop was established.
- Cache behavior: Accessible views read provider snapshots and storage settings without new network/filesystem calls. Shared accessibility helper extraction preserves previous matching/formatting. Native gesture registrations and listeners are disposed with their controls.
- Mechanism confidence: High confidence from the accessibility before/after extraction, notification sizing's unchanged caller, CSS diffs, and Gesture.ignoreTarget disposal implementation.
- Magnitude uncertainty: Accessible-output lengths and device rendering time were not measured. A small extra empty-history helper allocation is insufficient to establish a meaningful regression.
- Expensive boundaries: none found
- Verdict: No reportable regression. The changes are presentation sizing/activation and shared formatting, without a concrete new expensive boundary or retained-resource lifecycle problem.
