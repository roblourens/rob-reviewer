# Performance review: Browser tools: dialog flake in the click and typing tools test (\#350285)

[PR #350592](https://github.com/microsoft/vscode/pull/350592) at `104c4c7933614d886957097a562d62d822b7845e`

## Findings (1)

### 1. [medium] Make the 40-round browser stress run opt-in

**Finding ID:** `PERF-720D5F752F78`  
**Location:** <code>extensions/vscode-api-tests/src/singlefolder-tests/browser.tools.test.ts:23</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Sequential browser-view creation/navigation, extension-host and shared-process IPC calls, Playwright/CDP actions, and configuration-file edits.  
**Scaling:** Test-case and hook execution counts grow exactly 40-fold for matching desktop cases (12 to 480 locally; 10 to 400 remotely). Browser work remains serial across rounds; cached Playwright session initialization is not multiplied by 40, but forceNew page creation and individual actions are.  
**Outcome:** Longer integration-test feedback and CI critical-path latency, with increased risk of exhausting the existing step timeout.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The suite was registered once: 12 local desktop cases or 10 remote desktop cases, with one setup/teardown and one sequence of tool/browser operations per case.  
**Changed behavior:** Every ordinary desktop single-folder integration run now executes all browser-tool cases and their setup/teardown 40 times sequentially: 480 cases locally, or 400 with a remote extension host, instead of 12 or 10.  
**Confidence:** 0.99 — The complete test file establishes the case counts, and testrunner.js loads all test files into a non-parallel Mocha runner. The awaited tool calls cross extension-host RPC, browser creation/navigation, and shared-process Playwright IPC. Session caching reduces initialization, not repeated test execution. Actual elapsed time and timeout incidence are unmeasured.

**Causal diff evidence:** Added line 23 wraps the entire existing suite in \`for (let round = 0; round &lt; 40; round++)\`, replacing the single suite registration with 40 distinct registrations. The loop is unconditional for desktop runs; it is not gated on CI or a diagnostic environment variable.

Running the normal desktop API integration suite, or reproducing one test with --grep, now includes 39 extra executions of each matching browser test. This adds sequential browser navigation, dialog automation, RPC, and settings-edit latency to developer feedback and CI completion, increasing pressure on the existing 15-minute CI budget.

**Evidence:** test/integration/electron/testrunner.js:26-46 applies only an optional MOCHA\_GREP and otherwise runs every loaded test serially. scripts/test-integration.sh:286-287 includes this file through the singlefolder-tests directory; .github/workflows/pr-linux-test.yml:539-548 runs it under a 15-minute extension-host step. Each case performs awaited configuration updates and editor cleanup (changed file:28-58). Tool invocations use extHostLanguageModelTools.ts:124 RPC; OpenBrowserTool.\_openNewPage creates a browser view and awaits navigation/readiness, while Playwright calls use the shared-process proxy. Multiple cases explicitly set forceNew, so warm session/page caches cannot remove the repeated browser work.

**Suggested direction:** Make the 40-round stress reproduction explicitly opt-in, with one round by default, or remove the temporary repetition before merging. Keep diagnostics independent of the repetition gate.
