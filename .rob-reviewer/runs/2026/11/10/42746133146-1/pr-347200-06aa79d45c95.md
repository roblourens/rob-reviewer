# Performance review: Engineering - install every pnpm root with the isolated linker

[PR #347200](https://github.com/microsoft/vscode/pull/347200) at `06aa79d45c95e01b59d438bbcf0500a350ad5010`

## Findings (1)

### 1. [medium] Limit staging to files that can enter the VSIX

**Finding ID:** `PERF-DF2D04C73B01`  
**Location:** <code>extensions/copilot/script/build/packageVsix.ts:30</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** filesystem operations and bytes for a full temporary project plus hoisted production dependency tree  
**Scaling:** Each packaging invocation copies work proportional to the entire extensions/copilot source tree and all transitive production dependencies, then recursively deletes that staging tree; the final VSIX remains constrained by .vscodeignore to a small allowlist.  
**Outcome:** increased Copilot VSIX packaging latency and temporary disk usage on local and product-build critical paths  
**PR causality:** <code>introduced</code>  
**Previous behavior:** \`vsce package\` ran directly in extensions/copilot and traversed the installed dependency graph without first creating and deleting another complete deployment.  
**Changed behavior:** The added synchronous \`pnpm deploy --prod\` creates a hoisted portable copy of the project and every production dependency before \`vsce\` packages it, after which the entire staging directory is synchronously removed.  
**Confidence:** 0.97 — The before/after subprocess sequence, manifest dependency closure, lack of a \`files\` bound, ignore-file allowlist, and synchronous cleanup are all directly visible. Exact elapsed time depends on filesystem/link behavior and cache warmth, which affects severity but not the I/O amplification mechanism.

**Causal diff evidence:** RIGHT line 30 adds the full \`pnpm deploy --prod --config.node-linker=hoisted\` subprocess before the existing packager; this deployment and its later recursive deletion did not exist in the previous direct \`vsce package\` path.

Every \`pnpm run package\`, including the Product Copilot pipeline, now waits for an additional full-tree deployment and cleanup. This scales with the large Copilot source tree and its 40+ direct production dependencies even though \`.vscodeignore\` starts with \`\*\*\` and admits only the built artifacts and selected dependency files.

**Evidence:** Added line 30 invokes \`pnpm deploy --prod\` into a fresh temp directory; lines 44-45 then run the pre-existing \`vsce package\`, and line 42 recursively removes the deployment. \`extensions/copilot/package.json\` has no \`files\` allowlist and declares 40+ production dependencies, while \`.vscodeignore\` excludes everything by default and selectively includes only build outputs, the server plugin, and selected \`&#64;github/copilot\` files. The changed product pipeline calls this script on its packaging critical path.

**Suggested direction:** Keep the flat dependency layout needed by \`vsce\`, but construct the staging deployment from a package/files allowlist matching the VSIX inputs (or otherwise stage only the built artifacts and explicitly included dependency/plugin files) so source, tests, and excluded production packages are never copied and deleted.
