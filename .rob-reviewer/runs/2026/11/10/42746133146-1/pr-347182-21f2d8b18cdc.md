# Performance review: sessions: wait for startup providers before resolving a handed-off folder

[PR #347182](https://github.com/microsoft/vscode/pull/347182) at `21f2d8b18cdcca4bfb2f3a7efc4c1058b60c81a1`

## Findings (1)

### 1. [medium] Wait only for startup session providers

**Finding ID:** `PERF-AB67A64AE0D7`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/agentsWindowWorkspaceHandoff.ts:197</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** main-thread idle scheduling and synchronous construction of all AfterRestored workbench contributions  
**Scaling:** The cold-open delay grows with the number and constructor cost of every AfterRestored contribution; when an idle slice is exhausted, the registry schedules another slice with a 500 ms forced timeout before the global promise can settle.  
**Outcome:** increased cold Agents-window folder-handoff latency before the composer can apply the requested workspace  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After setup/view restoration, a folder handoff immediately queried the providers currently registered and applied the workspace; unrelated AfterRestored contributions were not on this critical path.  
**Changed behavior:** Every cold-start handoff with a folder now awaits the global workbench \`whenRestored\` promise before resolving the workspace.  
**Confidence:** 0.97 — The changed critical-path await, the exact global-promise completion condition, idle batching, 500 ms timeout, and cold-start call path are all explicit in repository code. Exact device-specific delay is uncertain, which is reflected in medium severity rather than mechanism confidence.

**Causal diff evidence:** The added \`await raceCancellationError(this.whenStartupProvidersRegistered...)\` at line 197 is passed \`IWorkbenchContributionsRegistry.whenRestored\`, changing the folder path from immediate provider resolution to a global restored-contribution barrier.

Opening a cold Agents window from a local-folder editor, including draft handoffs, can leave the new-session composer waiting for all unrelated restored contributions even after the required provider has registered. The PR description already observes about 130 ms on this path, and busy startup or additional contributions can push it toward one or more idle timeouts.

**Evidence:** \`IWorkbenchContributionsRegistry.whenRestored\` is documented as completing only after all contributions through Restored are instantiated. Its implementation constructs the full Restored list via \`runWhenGlobalIdle\`; each exhausted slice is rescheduled and Restored uses a 500 ms forced timeout. The list includes unrelated work such as terminal setup and GitHub PR polling, while the actual default and local session providers are only two AfterRestored contributions. \`SelectAgentsFolderContribution\` is a BlockStartup contribution, so an initial folder IPC can reach this await before those idle batches complete.

**Suggested direction:** Use a dedicated startup-session-provider registration barrier (completed once the relevant provider contributions have synchronously registered), or another provider-scoped readiness signal, and await that instead of global \`whenRestored\`; preserve the existing cancellation behavior.
