Network polling is upstream of the snapshot and unchanged by the diff.
- Scaling input: Reported checks C, expected suites S, required names R, and missing required names M. The new helper invokes existing classification, which can scan checks by required name, then allocates M small placeholder objects; it is snapshot-driven and does not multiply network calls.
- Effective concurrency: One shared PullRequestResource subscription coalesces interests for the pull request. Snapshot-derived presentation runs synchronously once per observable update; pending checks poll at roughly 15 seconds while visible or 60 seconds in the background, not per row or per frame.
- Cache behavior: The resource snapshot is shared; required contexts have a five-minute positive cache and workflow definitions have a bounded 50-entry cache. The diff adds no cache keys or miss behavior and consumes the already-materialized snapshot.
- Mechanism confidence: High confidence that the diff adds local collection work and no boundary operations; call sites, polling policy, and query implementation were traced directly.
- Magnitude uncertainty: Repositories can have unusually large matrix check sets, but required-name and missing-name counts are ordinarily small. No evidence shows the additional local classification materially affecting snapshot rendering latency.

### Scenario 2: Open and paginate the Checks details view

- Critical path: Acquiring details raises the existing subscription priority; once snapshot data is available, the view locally builds the check list, appends missing placeholders, sorts it, and slices pages of 200.
- Scaling input: All reported checks plus M missing required checks are sorted once per details derivation; displayed rows are sliced to 200. loadMore recomputes list length locally but introduces no remote request.
- Effective concurrency: A details lease updates the same coalesced pull-request subscription rather than starting an independent fetch. Local list derivation is serialized by the observable update.
- Cache behavior: The details view reads the shared snapshot. Loading another local page does not fetch another GitHub page because all check contexts were already materialized; required-context and workflow caches behave unchanged.
- Mechanism confidence: High confidence from the acquireDetails, derived details, and loadMore call paths.
- Magnitude uncertainty: Very large check rollups increase existing sort and list costs, while the diff adds only missing placeholders and one classification call. There is no evidence of dropped frames or material interaction delay.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/artifactIntegrations/githubPullRequestArtifactIntegration.ts:GitHubPullRequestArtifactResource.acquireDetails</code>: Raises priority on the existing pull-request subscription, whose query service refreshes checks; cardinality: No separate request is directly issued by the changed code; refresh cardinality remains determined by the shared subscription and paginated check count
    - Introduced by diff: false; previous behavior: Opening details already acquired a lease and raised the same subscription priority.; critical-path effect: Fresh remote data may be awaited by the existing resource, while local pagination itself uses the current snapshot
- Verdict: No reportable regression. The diff does not create per-row or per-page I/O, and the added local work is small relative to the existing full-list sort and mapping.

### Scenario 3: Show the disabled Merge action reason when GitHub reports the pull request blocked

- Critical path: The action presentation reads the current core and checks snapshot, classifies missing required names locally, joins only those names, and localizes the message. Existing checks and mergeability snapshots must already be available for the artifact view.
- Scaling input: Classification scales with required names and reported checks; message joining scales only with missing required names. It runs once for the visible disabled merge action per snapshot-derived update.
- Effective concurrency: Synchronous local computation during one derived-view update; no task, queue, subprocess, or new request is started.
- Cache behavior: Uses the current shared snapshot and the same required-context/workflow caches. No negative cache, cache invalidation, or lifetime changes are introduced.
- Mechanism confidence: High confidence that the new branch performs no I/O and is not on a per-frame, scroll, or input loop.
- Magnitude uncertainty: The exact number of required checks varies, but there is no realistic evidence that this snapshot-driven local scan creates noticeable latency.
- Expensive boundaries:
  - network at <code>src/vs/platform/github/common/pullRequestQueryService.ts:\_fetchChecks and mergeability query</code>: Existing GitHub queries populate check and mergeability fragments; cardinality: Existing polling performs one logical fragment refresh, with check pagination based on reported context count; the disabled-reason helper adds zero calls
    - Introduced by diff: false; previous behavior: The disabled Merge action already depended on the same core, checks, and mergeability resource state; it previously returned a generic local message.; critical-path effect: Remote state gates whether the view can present an authoritative reason, but the changed message computation itself is local
- Verdict: No reportable regression. The richer disabled reason adds bounded local CPU/allocation only and does not alter fetch frequency, concurrency, or cache lifetime.
