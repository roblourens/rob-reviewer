- Critical path: The provider must create the side chat, openChat must resolve the session and open the new chat beside the reference in the existing chat window, and the provider send must complete. All remain awaited before the command resolves.
- Scaling input: One explicit side-chat action. Opener discovery scales with the number of open chat-window contents/chats/editor groups; there is one registered production opener and no collection-wide boundary fan-out.
- Effective concurrency: One create, one open, and one send are serialized for each user action. The background send changes follow/navigation semantics but still awaits the same single provider send; no burst or new parallelism is introduced.
- Cache behavior: No new cache is introduced or bypassed. Session/provider state and opener contents are live in-memory lookups; cold and warm behavior have the same boundary cardinality.
- Mechanism confidence: High: the changed call path and all awaited operations are directly visible in the orchestration, SessionsService, opener service, and chat-window opener implementation.
- Magnitude uncertainty: Provider and editor-open latency depends on backend and window state, but their call counts are fixed at one and the diff replaces grid routing rather than stacking work.

### Scenario 2: Create and send a side chat from the main sessions grid

- Critical path: Create the chat, resolve/open it in the grid, split it to the side, and send through the provider.
- Scaling input: One user action; the added reference lookup scans the in-memory opener collection and chat-window contents once after the target lookup. It does not scale with session history or cause boundary calls.
- Effective concurrency: The operations remain serialized and user-triggered, with one provider send. No new concurrent work is scheduled.
- Cache behavior: No changed cache behavior. If no chat window owns the grid reference, the lookup misses in memory and proceeds through the prior grid path.
- Mechanism confidence: High: the sourceInGrid branch preserves split and foreground-send behavior, and the opener implementation establishes the lookup cardinality.
- Magnitude uncertainty: A user can open multiple chat-window chats/groups, increasing the in-memory showsChat scan, but this occurs once per explicit action and has no realistic high-frequency trigger.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/sessions/browser/sessionsManagementService.ts:createSideChatInSession</code>: Create one side chat through the sessions provider.; cardinality: One call per action.
    - Introduced by diff: false; previous behavior: Identical provider create call.; critical-path effect: Awaited before opening.
  - IPC at <code>src/vs/workbench/contrib/sessions/browser/sessionsManagementService.ts:resolveSessionResource</code>: Resolve the session through providers supporting resolution.; cardinality: One sequential pass for the single open.
    - Introduced by diff: false; previous behavior: Identical resolution pass.; critical-path effect: Awaited before grid activation.
  - network at <code>src/vs/workbench/contrib/sessions/browser/sessionsManagementService.ts:sendRequest</code>: Submit one request to the provider/backend.; cardinality: One call per side chat.
    - Introduced by diff: false; previous behavior: Identical foreground send.; critical-path effect: Awaited before the action completes.
- Verdict: No reportable regression. The only added work is one bounded in-memory ownership lookup on a human-triggered path.

### Scenario 3: Fork a chat within a multi-chat session from the grid or a chat window, including open-to-side

- Critical path: The provider fork must finish, then SessionsService resolves the resource and opens the fork either in the grid or beside the source in its chat window.
- Scaling input: One explicit fork command. History is scanned once locally to locate the source turn, as before; routing adds at most one in-memory reference-owner lookup.
- Effective concurrency: One fork and one open are serialized per command. No Promise.all, queue expansion, or per-history-item fan-out is added.
- Cache behavior: No new cache or retention. Opener ownership is queried live so closed windows naturally miss and fall back to the existing grid route.
- Mechanism confidence: High: fork provider invocation, routing branches, opener lookup, and tests all establish one-for-one replacement behavior.
- Magnitude uncertainty: Backend fork duration is provider-dependent, but unchanged. Editor-open costs differ between grid and chat window, with no evidence that the substituted existing-window route is more expensive.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/sessions/browser/sessionsManagementService.ts:forkChatInSession</code>: Fork one chat through the selected agent-host sessions provider/backend.; cardinality: Exactly one fork call per command, independent of request-history size after the local turn lookup.

  - IPC at <code>src/vs/workbench/contrib/sessions/browser/sessionsManagementService.ts:resolveSessionResource</code>: Resolve the fork's session resource through applicable providers.; cardinality: One sequential resolution pass for one fork open.
    - Introduced by diff: false; previous behavior: Both openChat and openChatToSide already resolved the resource.; critical-path effect: Awaited before display routing.
  - other at <code>src/vs/sessions/contrib/chatWindow/browser/sessionsChatWindowProvider.ts:IChatHostOpener.openBeside</code>: Open the fork beside its source when the source is hosted by a chat window.; cardinality: One editor open per fork.

- Verdict: No reportable regression. Boundary cardinality is unchanged, and the new reference routing replaces rather than adds UI opening work.
