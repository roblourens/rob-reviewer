## Findings (1)

### 1. [medium] Bound automatic paging through hidden footer runs

**Finding ID:** `PERF-1F9FAA178F03`  
**Location:** <code>src/vs/workbench/contrib/sessions/browser/chat/artifactActivitiesModel.ts:140</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Artifact-history IPC calls, serialized run pages, and repeated history scans  
**Scaling:** For H consecutive user footer runs, opening details performs ceil(H/50) serial getRuns calls; reopening repeats the scan. Composite models also rescan source-history prefixes for successive cursors.  
**Outcome:** Excessive IPC and CPU work with increased activity-card resolution latency  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Footer runs were visible, so a collapsed open made no history request when one was in the snapshot; an expanded view stopped after its first fetched page.  
**Changed behavior:** User footer-action runs now count as hidden, so loadPage serially fetches 50-run pages until another activity is found or history ends.  
**Confidence:** 0.97 — The constructor path, 50-run page size, awaited loop, and history protocol boundary are explicit. Only the prevalence of histories exceeding 50 footer clicks is uncertain.

**Causal diff evidence:** RIGHT line 140 now applies the snapshot-aware predicate; RIGHT lines 263-264 newly reject user general-action runs, so pages that previously ended the loop now trigger another getRuns call.

Opening an artifact with a long history of repeated general-action clicks can issue a serial cascade of history RPCs even while Activities is collapsed, increasing IPC/CPU work and delaying resolution of the card.

**Evidence:** Snapshots retain the latest 50 runs (artifactIntegrationService.ts:338). Opening details creates this model, and its autorun invokes loadPage when all snapshot runs are hidden (lines 84-89). The loop at lines 140-146 awaits getRuns(..., 50) for every all-hidden page. getRuns uses the ArtifactIntegrationProtocol history request, while CompositeArtifactModel.getRuns fans out to backing models and restarts from their newest pages on each outer request.

**Suggested direction:** Bound automatic discovery and defer deeper scanning to explicit demand, or expose one filtered/seek history operation so finding the first displayable run does not require one client RPC per 50 hidden records.
