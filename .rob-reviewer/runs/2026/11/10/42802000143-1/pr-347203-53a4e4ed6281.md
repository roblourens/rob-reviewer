### Scenario 1: Product-affecting PR runs Linux Electron smoke tests on the normal warm workspace-image/cache path

- Critical path: Detect Changes enables electron\_smoke\_affected; the reusable Linux workflow starts all smoke jobs, each completes shared setup and its assigned smoke suites, the linux-tests caller waits for every job, and PR Gate waits for linux-tests. The slowest of the four shards is therefore on the required-check critical path. The PR reports this falls from 5.53 minutes with three shards to 4.63 minutes with four.
- Scaling input: Fixed Linux shard count (3 to 4), 33 registered top-level suites with 27 runnable in the measured PR environment, and one shared setup sequence per shard. Suite execution cardinality remains one assignment per suite.
- Effective concurrency: Four independent 8-core jobs now run concurrently instead of three. Within each job, the shard selector assigns a disjoint subset of the 33 registered suites; Mocha runs that subset without diff-introduced intra-job parallelism. There is no shared limiter across jobs, but runner selection is explicitly justified as plentiful and the burst is bounded at four.
- Cache behavior: Workspace images, pnpm store, apt packages, built-in extensions, and Electron are reused when warm; each of four jobs performs its own restore/lookups. A cache miss falls back to downloads/installations independently in each job. There is no cross-job request coalescing, but the increase is a fixed one-job increment rather than input-scaled fan-out.
- Mechanism confidence: High confidence that shared setup boundaries increase from three to four and that suite execution remains deduplicated; low confidence that the bounded aggregate-resource increase causes any adverse performance symptom.
- Magnitude uncertainty: The fourth job increases aggregate CPU, filesystem, cache, artifact, and network load by one setup copy. There is no repository evidence that four jobs exhaust runner capacity or contend enough to increase user-visible latency; measured PR runs instead show a 54-second reduction in the slowest smoke job.

Aggregate resource cost alone, without evidenced contention or throughput degradation, is not a reportable performance regression.

### Scenario 2: Product-affecting PR runs Linux Electron smoke tests when workspace images or dependency caches are cold/unavailable

- Critical path: All four jobs independently take fallback checkout/install/download paths before running their shard; PR Gate waits for the slowest fallback job. These operations remain parallel rather than serial.
- Scaling input: A fixed fourth shard combined with cache/image misses or transient download failures; cost does not scale with the number of suites because setup is once per job.
- Effective concurrency: Up to four concurrent workspace restores/checkouts/package installs/Electron preparations and repository clones, versus three before. Retries are bounded per operation but are not globally limited or coalesced.
- Cache behavior: Cold misses amplify the extra job's network and installation work; successful future jobs can use repository-managed caches/images, but running shard jobs do not coalesce an in-flight miss. Failure retries are bounded.
- Mechanism confidence: High for the increase from three to four concurrent cold setup paths; insufficient evidence for a concrete adverse performance outcome.
- Magnitude uncertainty: Cold-path durations and service capacity are not measured in the diff. The mechanism of one additional concurrent miss path is certain, but whether it causes throttling, queueing, or a slower gate is unsupported.
- Expensive boundaries:
  - network at <code>.github/workflows/pr-linux-test.yml shared &steps and .github/actions/install-linux-packages/action.yml</code>: On misses, restore/download package caches or run apt update/install and pnpm installs.; cardinality: Four independent miss paths versus three. Each job can retry bounded installs; no per-suite multiplication occurs.
    - Introduced by diff: false; previous behavior: The same cold path existed in three shard jobs; the diff adds one concurrent copy.; critical-path effect: Cold installation is on every shard's critical path; the gate waits for the slowest one.
  - network at <code>.github/actions/setup-electron/action.yml</code>: Restore Electron archives or download and prepare Electron on cache miss.; cardinality: Four preparations/restores versus three, with up to three download attempts per failing job.
    - Introduced by diff: false; previous behavior: Three shard jobs independently performed the same operation.; critical-path effect: Must complete before each Electron smoke runner starts.
  - network at <code>test/smoke/src/main.ts setupRepository, lines 278-305</code>: Clone the smoke-test fixture repository with bounded retries.; cardinality: Four clones, or up to twenty attempts only if all four independently fail repeatedly, versus three clones/up to fifteen attempts before.
    - Introduced by diff: false; previous behavior: Three jobs cloned independently.; critical-path effect: Root setup blocks each shard's suites.
- Verdict: No finding. The concurrency burst is bounded and intentional, and there is no evidence that the extra cold-path request crosses a service or runner limit or outweighs the reduced suite duration.

### Scenario 4: Linux sharded smoke execution computes suite placement using the new platform-specific duration table

- Critical path: At smoke-runner startup all suites are registered, selectShardSuites estimates their durations in memory, sorts 33 indexes, and filters the selected subset before Mocha executes the root before hook and suites. The balancing computation is negligible and does not add an external boundary.
- Scaling input: Number of registered top-level suites (about 33) and fixed shard total (four in Linux PR CI).
- Effective concurrency: Assignment is recomputed once in each of four jobs with identical inputs; suite execution is disjoint by shard index. No new asynchronous concurrency is introduced by the table.
- Cache behavior: The duration map has no external cache. The smoke fixture is job-local and absent on fresh runners; stable-build download is not reached in the changed PR workflow invocation.
- Mechanism confidence: High that the new table changes only assignment and that each suite remains selected once.
- Magnitude uncertainty: Measured suite durations vary by run and first-launch placement, so exact balance can drift, but stale estimates affect only bounded shard balance and not total suite cardinality.
- Expensive boundaries:
  - other at <code>test/smoke/src/shard.ts selectShardSuites, lines 91-104</code>: In-memory traversal of Mocha suites, map lookups, sorting, and assignment.; cardinality: Once per shard over about 33 suites: four O(n log n) computations versus three. This is tiny compared with smoke setup and execution.
    - Introduced by diff: false; previous behavior: The same algorithm ran once in each of three jobs with a shared duration table and a 20-second default.; critical-path effect: Runs synchronously before tests but has negligible fixed cost at this collection size.
  - network at <code>test/smoke/src/main.ts setup/ensureStableCode, lines 308-408</code>: Optional stable-release metadata fetch/download and smoke fixture repository clone after selection.; cardinality: In PR CI the runner has no --build, so stable-code download is skipped; each shard clones one fixture repository. In other Linux --build invocations stable setup remains once per shard exactly as before.
    - Introduced by diff: false; previous behavior: Identical setup boundaries existed; only estimated weights and Linux's default estimate changed.; critical-path effect: The duration table only changes suite placement; it does not add or move these setup boundaries. Root setup still runs before the selected suites.
- Verdict: No finding. The changed metadata improves expected balance without introducing expensive work, retention, or boundary fan-out.

**Summary:** Reviewed all four changed files and the complete diff inventory under the performance focus. Traced the Linux PR gate, shared workflow setup, cache miss paths, Electron/smoke subprocesses, fixture clone, artifact uploads, and in-memory sharding. The only material cost increase is one bounded parallel copy of per-job setup; the suite set remains deduplicated and measured critical-path latency improves, so no actionable performance regression was found.
