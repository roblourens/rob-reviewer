# Performance review: Allow comment width to always be resized

[PR #347304](https://github.com/microsoft/vscode/pull/347304) at `8f43f912f9dd7e622b98bca9675e8d6df3841458`

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work

### Scenario 1: Opening, restoring, or resetting a floating comment thread widget

- Critical path: The widget measures editor/content widths, computes the default or restored width, applies width/height, and renders before placement is visible. The diff adds a cached local for the already-required width measurement plus constant-time range/default-width calculations; it does not add another DOM measurement or asynchronous dependency.
- Scaling input: One sizing pass per shown/reset widget; occupied-rectangle placement still scales with the number of other visible floating comment widgets, but that unchanged host scan is not increased by this diff.
- Effective concurrency: Synchronous UI work on the renderer event path, one widget sizing operation at a time; no new queue, burst, or parallel work is introduced.
- Cache behavior: Stored layouts remain in the existing bounded 500-entry LRU cache. Cold widgets compute a default layout; warm widgets restore a layout and apply the same single width measurement as before. The diff does not change keys, misses, invalidation, or coalescing.
- Mechanism confidence: High confidence from tracing \_computeDefaultLayout, \_applySize, \_measureContentWidths, and the host layout cache. The only new work is pure arithmetic, including a duplicate pure getWidthRange calculation inside getDefaultWidth.
- Magnitude uncertainty: Actual DOM layout cost varies with thread complexity, but the changed code does not increase measurement cardinality: content widths are measured once in the default-layout path before and after the PR.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. Initial width behavior changes, but synchronous DOM reads, writes, comment layout calls, and render count are not materially increased.

### Scenario 2: Dragging a floating comment widget resize sash horizontally or from a corner

- Critical path: ResizableHTMLElement emits one resize event per sash movement; \_onResize clamps width, lays out the comment thread when width changes, measures heights, and renders. The PR broadens the permitted maximum width from natural content width to editor width but does not add events, measurements per event, or a boundary call.
- Scaling input: Cost scales with pointer-move events during an intentional resize and with rendered comment-thread complexity. The user can now continue changing width over a larger range, so more moves may perform actual layout instead of clamping, but that work is the direct requested interaction and remains bounded by editor width and event count.
- Effective concurrency: Synchronous, serial pointer-event handling with one active resize session; no parallelism, background work, limiter, IPC, or concurrency burst.
- Cache behavior: The width range is captured once at resize start. No cache or coalescing behavior changes; content-layout calls remain skipped when computed content width is unchanged.
- Mechanism confidence: High confidence from tracing ResizableHTMLElement.onDidChange through \_onWillResize, \_onResize, \_setWidth, \_measureContentHeights, and \_render.
- Magnitude uncertainty: Browser layout cost depends on comment DOM size and pointer frequency. The wider interactive range can cause additional expected relayout while actively dragging, but there is no realistic evidence of a material regression beyond the feature's required resize updates.
- Expensive boundaries: none found
- Verdict: No actionable performance finding. The broader resize range is intentional, editor-bounded, user-driven, and does not change per-event work or event fan-out enough to establish a concrete regression.

### Scenario 3: Comment content changes while a floating widget is already wider than its natural content

- Critical path: A content-size event synchronously calls \_applySize and \_render. The new width range preserves a user-selected width up to editor width rather than clamping it to natural content; the same width/height measurements and render operations occur as before.
- Scaling input: One apply/render pass per existing content-size event; cost scales with comment DOM complexity, not with the newly allowed width itself.
- Effective concurrency: Serial renderer event handling; no new scheduling, batching, or concurrency behavior.
- Cache behavior: The in-memory chosen layout and existing \_contentLayoutWidth guard are unchanged. Warm updates avoid CommentThreadWidget.layout when the applied content width is unchanged.
- Mechanism confidence: High confidence from tracing onDidChangeContentSize to \_onContentSizeChanged and \_applySize.
- Magnitude uncertainty: DOM geometry cost varies by thread, but the diff changes the allowed value rather than the number of content-size events or geometry reads.
- Expensive boundaries: none found
- Verdict: No reportable performance regression; preserving the wider chosen size does not introduce repeated work, unbounded retention, or an expensive boundary.

**Summary:** Completed the performance pass over all three changed files and traced initial sizing, restored sizing, content updates, and interactive resize handling. No changed subprocess, IPC, filesystem, database, network, or serialization boundaries are reachable. The PR changes width policy while preserving DOM measurement and event cardinality, so no high-confidence actionable performance issue was found.
