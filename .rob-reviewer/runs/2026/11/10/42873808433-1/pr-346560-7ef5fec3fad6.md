### 1. [medium] Avoid cloning the whole thread on edit-height changes

**Finding ID:** `PERF-7402E6A117AB`  
**Location:** <code>src/vs/workbench/contrib/comments/browser/commentThreadBody.ts:53</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** cloned DOM nodes and synchronous browser style/layout work  
**Scaling:** O(thread DOM size) allocation and layout for every comment-element resize at unchanged width, including each edit that changes the embedded editor's line-count height  
**Outcome:** blocked input latency and CPU/GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Inline comment widgets did not need natural-width floating-window sizing, so comment editor growth did not clone the full comments subtree or force a max-content offsetWidth measurement.  
**Changed behavior:** Floating threads now derive their natural width by cloning the complete comments subtree and synchronously laying out that hidden clone after comment-size changes. Height-only growth while editing invalidates the width cache even though FloatingWidgetSizeModel ignores the natural maximum while isEditing is true.  
**Confidence:** 0.97 — The call path is explicit: CommentThreadBody's new ResizeObserver clears \_naturalWidth and fires onDidChangeCommentsSize; CommentThreadWidget forwards onDidChangeContentSize; ReviewFloatingWidget.\_onContentSizeChanged calls \_applySize; \_measureContentWidths calls measureNaturalWidth. CommentNode recalculates and lays out its editor when line count changes, providing a concrete typing trigger. The exact duration depends on thread DOM size, but the forced layout and full-subtree allocation are certain.

**Causal diff evidence:** Added lines 53-62 introduce cloneNode(true), temporary DOM insertion, and an offsetWidth read in measureNaturalWidth(); the new floating-widget resize path invalidates this cache whenever the comments element changes size at the same width and immediately re-enters width measurement.

In a floating thread with a long discussion, adding or removing lines while editing an existing comment can synchronously clone and lay out the entire thread on the input path. Cost grows with all rendered comments and repeats for each height-changing edit, causing typing latency plus DOM allocation and GC pressure.

**Evidence:** CommentThreadBody.measureNaturalWidth clones every comment node, appends the clone with width=max-content, and reads offsetWidth. The new ResizeObserver at lines 212-228 clears \_naturalWidth whenever the comments element resizes without changing width. ReviewFloatingWidget.\_onContentSizeChanged synchronously calls \_applySize, whose \_measureContentWidths path invokes this method before getWidthRange; getWidthRange does not use content.natural when the thread is being edited. CommentNode.calculateEditorHeight/layout changes the comments element height as edited line count changes.

**Suggested direction:** Separate width invalidation from height-only resize notifications and skip natural-width measurement while isEditing, since getWidthRange ignores it on that path. Recompute the cached natural width only for content changes that can affect width or when leaving edit mode.

### 2. [medium] Coalesce floating-widget renders during scrolling

**Finding ID:** `PERF-C9A6505EA681`  
**Location:** <code>src/vs/workbench/contrib/comments/browser/commentThreadFloatingWidget.ts:430</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** CPU geometry work plus overlay layout and SVG/DOM writes  
**Scaling:** O(expanded floating widgets × scroll notifications), with additional visible-range line work for commented ranges intersecting the viewport; repeated notifications within one frame repeat the entire render  
**Outcome:** increased main-thread scroll latency and dropped frames  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Inline zone widgets relied on the editor's view-zone rendering and did not add a per-thread scroll listener that recomputed code geometry and rewrote an overlay connector.  
**Changed behavior:** Every expanded floating thread now performs its own synchronous geometry and overlay/SVG render on each editor scroll event. Multiple scroll updates before a frame are not coalesced, and Expand All installs this listener for every thread.  
**Confidence:** 0.95 — The listener lifetime and multiplicity are explicit: \_attach adds it per expanded ReviewFloatingWidget and \_detach removes it. \_render traces directly through code-range geometry, layoutOverlayWidget, SVG path generation, and DOM attribute/style writes. The repository exposes Expand All over every comment widget, making many listeners realistic. Exact frame loss varies with thread count and range size, but the repeated work mechanism is certain.

**Causal diff evidence:** Added lines 428-432 register one editor scroll listener per attached floating widget and call \_render() directly for every horizontal or vertical scroll notification rather than using the class's existing frame scheduler.

With floating style enabled and many threads expanded (including via Expand All), touchpad or smooth scrolling runs one full overlay/connector render per widget per scroll notification. Work scales with expanded thread count and scroll-event frequency, producing main-thread scroll jank and dropped frames.

**Evidence:** ReviewFloatingWidget.\_attach subscribes each expanded widget to editor.onDidScrollChange and invokes \_render synchronously. \_render calls CommentedCodeGeometry.getLineRects, which scans intersecting visible lines and checks injected text, then calls editor.layoutOverlayWidget and CommentThreadConnector.render; the connector builds an outline path and updates SVG/DOM. The same class already has \_scheduleRender, used for model/content changes, but scroll bypasses it.

**Suggested direction:** Route scroll changes through \_scheduleRender so each widget renders at most once per animation frame; preferably share one host-level frame callback across floating widgets and avoid connector geometry work for widgets and ranges wholly outside the viewport.
