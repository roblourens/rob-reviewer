**Relevant issue families:** synchronous-ui-work, repeated-work, serialization-allocation

### Scenario 1: Pinning or unpinning the session currently open in the main window from the row action or context menu

- Critical path: The action calls SessionsList.pinSession/unpinSession; the model persists the pin set and synchronously fires onDidChange, which performs the existing full list update. The new revealOpenChatRow then resolves the rebuilt row, reveals it only as needed, accounts for the sticky footer, and updates focus/selection before the action returns.
- Scaling input: The existing list rebuild scales with all loaded sessions and chats. The new reveal lookup scans the session array once and a selected session's child rows; only the one session matching the main-window session proceeds to geometry/reveal work.
- Effective concurrency: Fully serialized on the UI thread: storage mutation, synchronous event-driven list rebuild, then reveal/focus/selection. No subprocess, IPC, database, or network work is reached.
- Cache behavior: Pin state is held in an in-memory Set and persisted; section collapse state is read from profile storage and immediately persisted when changed. No cold/warm network cache participates.
- Mechanism confidence: High confidence in the synchronous ordering and bounded cardinality from the model event handler, action loop, reveal helper, and collapse-state listener.
- Magnitude uncertainty: Profile-storage backend latency and the maximum real session/chat count are not measured, but the new boundary cardinality is bounded to one user-triggered collapse-state write and the geometry work is bounded to one active row.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/sessions/browser/sessionsListModelService.ts:310-325</code>: Persist the pinned-session ID set through profile storage; cardinality: One profile-storage write per effective single-session pin or unpin; unchanged for this scenario
    - Introduced by diff: false; previous behavior: Pin and unpin already persisted exactly once before firing the synchronous list update; critical-path effect: Runs synchronously before the list-model change event and therefore before the row reveal
  - filesystem at <code>src/vs/workbench/contrib/sessions/browser/views/sessionsList.ts:5572-5596 and 9376-9383</code>: Persist expanded section collapse state when revealing an active row expands a user-collapsed ancestor; cardinality: At most one write for the collapsed destination section in the tested pin/unpin move; only when an ancestor must expand
    - Introduced by diff: true; previous behavior: The row was not revealed after pin/unpin, so this automatic expansion and its corresponding collapse-state write did not occur; critical-path effect: Occurs during the synchronous reveal/ancestor expansion path
- Verdict: No reportable regression. The added UI-thread work is user-triggered and bounded to one active row; the only new storage write occurs when intentionally persisting a newly expanded collapsed section.

### Scenario 2: Pinning or unpinning one or more sessions that are not open in the main window

- Critical path: Each action target still mutates the model and synchronously rebuilds the visible list as before. The new revealOpenChatRow exits immediately after checking the current shown session ID, so it performs no tree traversal, geometry work, scrolling, or extra persistence for non-active targets.
- Scaling input: Selected action target count controls the pre-existing number of model writes and list rebuilds. The new helper adds only constant-time shown-session checks for non-active targets.
- Effective concurrency: Serial per target on the UI thread; there is no burst of parallel subprocess, IPC, filesystem, database, or network calls introduced by the diff.
- Cache behavior: In-memory pin membership avoids work for no-op mutations; no negative cache or request coalescing is involved.
- Mechanism confidence: High confidence because the guard precedes all new session-array and tree work.
- Magnitude uncertainty: Large multi-selection prevalence is unknown, but the diff does not increase expensive boundary cardinality or rebuild count for these targets.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/sessions/browser/sessionsListModelService.ts:310-336</code>: Persist the pinned-session ID set through profile storage; cardinality: One write and one synchronous list update per effective target in the existing action loop; batch drag/drop uses the existing unpinSessions path
    - Introduced by diff: false; previous behavior: The same per-target action loop and model persistence/event behavior existed before the diff; critical-path effect: Remains on the action critical path
- Verdict: No reportable regression; the changed path exits before expensive reveal work and does not amplify existing per-target storage or update behavior.

### Scenario 3: Routine sessions-list updates while an active or onboarding session must remain visible past section and folder caps

- Critical path: A visible-list update derives up to two reveal IDs, performs normal filtering/grouping, checks capped folder sections for either ID, and for each capped section filters only the tail beyond the five-item default cap before rebuilding the virtual trees. Active-chat changes schedule this update at the next animation frame; model/filter changes may update synchronously under existing behavior.
- Scaling input: The added folder checks and capped-tail filters sum to O(number of sessions in relevant sections), using at most two reveal IDs after deduplication by Set membership. At most the active and onboarding sessions are appended beyond caps, so rendered-row growth is bounded to two sessions plus their existing chat children.
- Effective concurrency: Single UI-thread update, with active-session updates coalesced to the next animation frame and other scheduled session/chat updates also coalesced by pendingListUpdate. No subprocess, IPC, filesystem, database, or network boundary is introduced on this update path; the experiment treatment is fetched separately and retained in an observable.
- Cache behavior: The session-group limit is cached in sessionGroupLimit after the asynchronous treatment fetch. Reveal IDs are recomputed from in-memory observables each update; there is no miss retry or retained unbounded cache.
- Mechanism confidence: High confidence in the O(N) scan/allocation mechanism and its execution on list updates; low evidence that its bounded incremental cost creates user-visible latency over the pre-existing full rebuild.
- Magnitude uncertainty: Real maximum session counts and update rates are unknown, but the surrounding update already performs multiple full-session filters, grouping, sorting, and tree reconstruction, and the added pass is linear with constant-size membership state.
- Expensive boundaries: none found
- Verdict: No finding. The diff adds linear scans and short-lived arrays/Sets, but not a higher asymptotic cost than the existing update, unbounded retention, extra boundary fan-out, or enough concrete hot-path impact to establish a performance regression.

### Scenario 4: Changing the chat shown in the main window while the sessions list is visible

- Critical path: The existing autorun schedules one animation-frame list update and selection synchronization. The changed cap logic can keep that active session's row in a capped section or folder during the rebuild, after which existing syncActiveChatSelection selects/reveals it.
- Scaling input: The update scales with loaded sessions as above; only one main-window active session is retained beyond caps.
- Effective concurrency: One coalesced animation-frame task replaces any pending active-session task; all tree work is synchronous within that frame. No external boundaries are reached.
- Cache behavior: The shown chat is an in-memory observable, and session/chat models are reused; no cold/warm external cache behavior changes.
- Mechanism confidence: High confidence from the MutableDisposable animation-frame scheduling and single active-session model.
- Magnitude uncertainty: The number of active-chat switches and list sizes varies, but task replacement prevents an accumulating queue.
- Expensive boundaries: none found
- Verdict: No reportable regression. The new cap inclusion participates in an already coalesced rebuild and cannot accumulate concurrent work or retained entries.
