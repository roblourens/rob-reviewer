### Scenario 2: Developer selects, switches, or stops a simulated Copilot plan

- Critical path: The picker waits for one profile-storage store/remove and one local entitlement recomputation before announcing completion. The recomputation consumes the current default account and synthesized quota objects; it does not refresh the account or issue an entitlement request.
- Scaling input: Nine fixed picker options; one selected value. Cross-window fanout scales with the small number of concurrently open windows, not repository or user data size.
- Effective concurrency: Each window handles the storage event independently. Within a window, resolve cancels its predecessor; picker invocation awaits the latest stored-change resolve.
- Cache behavior: Actual account data is reused from DefaultAccountService; no cold network fetch is requested. Duplicate local and storage events are coalesced by comparing the stored value with \_simulatedEntitlement.
- Mechanism confidence: High confidence that persistence and fanout are real and that account/network refresh is absent from getDefaultAccount on this path.
- Magnitude uncertainty: Cross-window count varies by user, but this is an explicitly invoked developer command with bounded local work per window.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/services/chat/common/chatEntitlementService.ts:1227 ChatEntitlementRequests.setSimulatedEntitlement</code>: Persist or remove the profile-scoped simulated entitlement.; cardinality: One keyed write per accepted picker change, fanned out once to each open window sharing the profile.

  - network at <code>src/vs/workbench/services/chat/common/chatEntitlementService.ts:1259 ChatEntitlementRequests.resolve</code>: Read the current default account before locally mapping simulated entitlement data.; cardinality: One getDefaultAccount call per effective simulation change per open window; this waits for existing initialization and performs no refresh itself.

- Verdict: No finding: the new work is bounded, user-triggered, coalesced for duplicate notifications, and does not fan out across data items or remote calls.

### Scenario 3: Quota snapshots arrive while a plan is simulated

- Critical path: acceptQuotas checks the already-instantiated request controller and returns before quota merging, context-key updates, storage writes, event fanout, and telemetry. Simulated quotas are applied only by the local resolve through doAcceptQuotas.
- Scaling input: Cost scales with quota snapshot frequency, but the added check is constant time and prevents larger work while active.
- Effective concurrency: Incoming snapshots are synchronously rejected while simulation is active; no queued or burst remote work is created.
- Cache behavior: No new cache. Actual and simulated quota snapshots are deliberately not merged; clearing and one local replacement occur on each effective simulation change.
- Mechanism confidence: High confidence from the early return and direct doAcceptQuotas path.
- Magnitude uncertainty: Snapshot frequency is environment-dependent, but the direction of performance change is neutral to beneficial.
