### Scenario 2: Non-fast-forward merge with git.enableCommitSigning enabled

- Critical path: The local configuration lookup selects \`-S\`; the existing Git merge subprocess then creates and cryptographically signs one merge commit before the existing model refresh runs. Signing is required behavior for this opt-in setting.
- Scaling input: One signature for the single merge commit produced by one explicit merge invocation; it does not scale with files, commits being merged, refs, or repositories beyond separate user-issued merges.
- Effective concurrency: The merge and its Git-managed signing helper are serial on the command critical path. No Promise.all or per-item loop creates concurrent signing; repository-lock retries remain sequential.
- Cache behavior: The setting is resolved per repository at invocation time. Signing-agent/key caching is owned by the configured Git signing backend and unchanged by this code; no application cache is introduced or defeated.
- Mechanism confidence: High: the changed argument directly requests one Git signature only when the resource-scoped setting is true, and merge operations are not collection-driven or concurrent.
- Magnitude uncertainty: Signing latency depends on backend, agent state, hardware token, and prompts, but cardinality is strictly one and the work is the explicit semantics of the enabled setting.
- Expensive boundaries:
  - subprocess at <code>extensions/git/src/git.ts:2283 Repository.merge</code>: Run the existing \`git merge\` process with the added \`-S\` argument.; cardinality: One Git process per explicit merge invocation, as before.
    - Introduced by diff: false; previous behavior: One \`git merge &lt;ref&gt;\` process ran, but it did not honor the enabled VS Code signing setting.; critical-path effect: The process is awaited before refresh and command completion.
  - subprocess at <code>extensions/git/src/git.ts:2286 conditional \`args.push('-S')\`</code>: Git invokes the configured GPG, X.509, or SSH signing backend to sign the newly created merge commit.; cardinality: At most one signing operation for the one merge commit; no signing occurs when the merge creates no commit.

    - Introduced by diff: false; previous behavior: The same refresh already occurred after an unsigned merge.; critical-path effect: Awaited after signing/merge completes.
- Verdict: No reportable performance regression: the single additional signing boundary is intentional, opt-in, bounded, and inseparable from the requested signed-merge behavior.

### Scenario 3: Fast-forward or conflicting merge with git.enableCommitSigning enabled

- Critical path: The existing \`git merge -S &lt;ref&gt;\` process runs. Fast-forward merges create no commit and therefore do not invoke signing; conflicting merges stop before commit creation and are later concluded through the existing commit flow. The existing model refresh remains awaited.
- Scaling input: One selected ref per explicit operation; conflict count and repository size affect pre-existing Git/status work, but the diff adds no per-conflict or per-file work.
- Effective concurrency: One merge subprocess, followed by the existing bounded refresh. Any later conflict-resolution commit is a separate serialized user action using the pre-existing commit path.
- Cache behavior: No new cache is involved. The resource-scoped configuration lookup is local and signing-agent caches are not touched when no merge commit is created.
- Mechanism confidence: High: \`-S\` requests signing of a commit only if Git creates one, while the diff contains no loops, retained state, or scheduling changes.
- Magnitude uncertainty: Git's merge and refresh durations depend on repository size and conflict volume, but no new signing operation occurs in these no-commit cases.
- Expensive boundaries:
  - subprocess at <code>extensions/git/src/git.ts:2283 Repository.merge</code>: Run \`git merge -S &lt;ref&gt;\` without creating a merge commit on fast-forward or conflict.; cardinality: One per explicit merge invocation.

- Verdict: No reportable regression: subprocess count and expensive work remain effectively unchanged for merge attempts that create no merge commit.
