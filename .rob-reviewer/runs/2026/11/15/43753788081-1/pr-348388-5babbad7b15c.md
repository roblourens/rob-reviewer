# Performance review: SCM Graph - use the active editor's repository when it opens after the editor

[PR #348388](https://github.com/microsoft/vscode/pull/348388) at `5babbad7b15c970a6771202c654db549cc0d444a`

## Findings (1)

### 1. [medium] Reject unrelated repositories before rescanning them all

**Finding ID:** `PERF-1FA488E16D4A`  
**Location:** <code>src/vs/workbench/contrib/scm/browser/scmViewService.ts:280</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Main-thread CPU spent normalizing and comparing repository URIs  
**Scaling:** For N repositories registered during restoration, getRepository scans 1, 2, ... N registered providers, yielding Θ(N²) relativePath computations even when only one repository can contain the unchanged active editor.  
**Outcome:** Increased SCM restoration latency and main-thread CPU/UI stalls in large multi-repository workspaces  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, repository registration updated the SCM view but did not re-run the active editor's full repository lookup for every provider; that lookup ran when the active editor observable was read or changed.  
**Changed behavior:** Every onDidAddRepository event now synchronously invokes getRepository(activeResource), which walks all currently registered repositories; only after completing that walk does the filter suppress unrelated additions.  
**Confidence:** 0.98 — The changed callback, synchronous registration call path, and linear getRepository implementation directly prove quadratic main-thread work with repository count. Only the exact user-visible duration varies with repository count and URI implementation cost; that uncertainty is reflected in medium severity.

**Causal diff evidence:** The added return expression at line 280 places the collection-wide getRepository(activeResource) scan inside the per-repository onDidAddRepository filter; this event was not part of \_activeEditorObs before the PR.

On reload with a restored editor and many discovered Git/SCM repositories, provider registrations are handled sequentially on the main thread, so the newly added 1+…+N URI scans delay Source Control readiness and can make the window briefly unresponsive. The cost is paid even when almost every added repository is unrelated to the active file.

**Evidence:** SCMService.registerSCMProvider inserts each provider and synchronously fires onDidAddRepository. The added predicate calls SCMService.getRepository for every such event; getRepository iterates this.repositories and calls uriIdentityService.extUri.relativePath for each visible provider. MainThreadSCM.$registerSourceControl reaches registerSCMProvider from the extension-host registration RPC, so this work runs synchronously in each registration handler. Git repository discovery allows arbitrary workspace-folder counts and repositoryScanMaxDepth=-1, making large N realistic.

**Suggested direction:** First test whether the newly added repository's root can contain the active resource using URI-identity-aware containment, immediately reject unrelated roots, and only perform the authoritative getRepository lookup for a containing candidate (preserving nested-repository precedence).

### Scenario 2: SCM Graph is visible in Auto mode while the repository containing the restored editor is added

- Critical path: A containing repository passes the changed filter, updates activeRepository, and the visible graph's repository autorun refreshes its tree. Fetching the corrected repository's history is on the graph-content critical path; if the Graph is hidden, visibility-scoped subscriptions are absent and this history work is off the path.
- Scaling input: Normally one authoritative containing repository after unrelated additions are filtered; nested parent/child repositories can produce a small number of updates as a more specific root becomes authoritative. Graph page size is clamped to 1..1000 history items.
- Effective concurrency: Graph refresh uses a throttler plus an update-children throttler and tree-operation sequencer, so refreshes are coalesced/serialized rather than launched as an unbounded burst.
- Cache behavior: The graph retains per-repository view-model state, but a repository-triggered refresh clears state before fetching; a newly selected repository is cold. Hidden views perform no graph fetch. The SCM active-resource predicate itself has no cache.
- Mechanism confidence: High for the event-to-refresh-to-IPC/subprocess call path when the graph is visible; low uncertainty only around timing and visibility.
- Magnitude uncertainty: The exact Git-log duration and whether the graph is visible during discovery vary. The work is typically a single bounded refresh and is necessary to render the corrected repository.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadSCM.ts:MainThreadSCMHistoryProvider.provideHistoryItems</code>: Request history items from the extension-host SCM history provider for the corrected graph repository.; cardinality: At most one effective request per coalesced visible graph refresh; usually one for the newly authoritative repository.
    - Introduced by diff: true; previous behavior: The repository-add event did not revise the active editor repository, so the graph did not fetch the restored editor's repository and remained on the previously selected/first repository.; critical-path effect: Blocks rendering the corrected graph page while history is fetched.
  - subprocess at <code>extensions/git/src/historyProvider.ts:GitHistoryProvider.provideHistoryItems</code>: Run repository.log (Git log) to populate the requested graph page; optional history detail providers may also enrich returned items.; cardinality: One Git log for a cold, coalesced graph history request in the ordinary case.
    - Introduced by diff: true; previous behavior: No Git log for the restored editor's repository was triggered by its later registration; only the old/wrong graph repository could have been loaded.; critical-path effect: Blocks the corrected graph's content, but is not on window progress when the graph is hidden.
- Verdict: No additional finding: the new bounded/coalesced fetch is the required work for the PR's corrected graph and does not create fan-out beyond containing repository changes.

### Scenario 3: User switches the active editor after repositories are already open

- Critical path: The existing editor-change event still reevaluates the active editor and performs one repository lookup before active-repository observers and any visible graph refresh can proceed.
- Scaling input: One lookup across N open repositories per active-editor change, unchanged from the base behavior.
- Effective concurrency: Editor changes are processed synchronously on the main thread; visible graph refreshes remain throttled and sequenced.
- Cache behavior: The lookup is uncached both before and after the diff. The newly added repository event source does not fire in this scenario, so warm/cold behavior is unchanged.
- Mechanism confidence: High: Event.any forwards the pre-existing editor event once, and the added filter subscribes only to repository-add events.
- Magnitude uncertainty: None material for PR causality; editor-change frequency and repository count vary but the diff does not increase this scenario's lookup or boundary cardinality.
- Expensive boundaries: none found
- Verdict: No regression introduced for normal active-editor switching.
