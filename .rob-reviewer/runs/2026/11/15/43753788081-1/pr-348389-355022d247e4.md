# Performance review: Git - keep tag conflict dialog short and chunk forced tag fetch

[PR #348389](https://github.com/microsoft/vscode/pull/348389) at `355022d247e4efc82d009831f53c6140d8d873d9`

## Findings (1)

### 1. [medium] Keep forced tag replacement in one fetch

**Finding ID:** `PERF-320E61EC1C56`  
**Location:** <code>extensions/git/src/git.ts:2527</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Git subprocesses and serialized remote fetch round trips  
**Scaling:** Once the generated refspec text exceeds 30 KB, cost grows as ceil(total refspec characters / 30,000); every chunk starts and awaits another remote \`git fetch\`. For the documented 7,500-tag shape this is roughly 40 serial fetches.  
**Outcome:** Conflict resolution blocks the pull on repeated process startup and remote discovery/connection latency, producing substantially higher end-to-end pull latency on platforms whose native argument limit would have allowed fewer or one fetch.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, tag replacement issued one \`git fetch\` containing all conflicting-tag refspecs. That failed when the host command-line limit was exceeded, but on Linux and on macOS for inputs between 30 KB and the native limit it completed with one subprocess and one remote fetch.  
**Changed behavior:** The change applies the conservative 30 KB threshold on every OS and serially executes one remote fetch per chunk, including on hosts where the original command still fits under the actual process argument limit.  
**Confidence:** 0.98 — The changed loop, fixed threshold, synchronous call path, and one remote fetch per chunk are explicit in code. Exact latency depends on transport and tag-name lengths, but the boundary multiplication and critical-path placement are certain; platform argument limits only affect which input sizes regress versus previously fail.

**Causal diff evidence:** The added loop at line 2527 invokes and awaits \`this.exec(\[...args, ...chunk\], spawnOptions)\` once for every fixed-size chunk; the deleted code invoked \`this.exec(args, spawnOptions)\` exactly once after appending all refspecs.

Repositories with hundreds or thousands of conflicting tags can wait through many serialized remote fetches before the original pull is retried. The regression is especially visible on Linux, where a refspec list far larger than 30 KB can still fit in one process invocation.

**Evidence:** \`fetchTags\` is reached synchronously while handling a pull/sync tag conflict, and \`\_pullAndHandleTagConflict\` cannot retry the pull until it returns. \`splitInChunks\` groups solely by cumulative string length at 30,000 characters; the loop awaits each \`exec\`, so there is no coalescing and effective concurrency is one. Each command is \`git fetch \[--force\] &lt;remote&gt; &lt;chunk&gt;\`, crossing both subprocess and remote-network boundaries. The repository already supports supplying stdin through \`SpawnOptions.input\`, so the argument-size limit does not require repeated remote commands.

**Suggested direction:** Pass the newline-separated refspecs through a single \`git fetch --stdin\` invocation using \`spawnOptions.input\` (while preserving \`--force\` and the remote), rather than splitting them into multiple remote fetches. This removes command-line-size pressure without multiplying subprocess and network boundaries.
