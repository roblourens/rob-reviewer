# Performance review: agentHost: don't show a turn twice after the host replaces a chat's turns

[PR #348368](https://github.com/microsoft/vscode/pull/348368) at `7d5e168548758dfef567ce9a8dcbd8f54526f110`

## Findings (1)

### 1. [medium] Batch replacement cleanup instead of removing requests one by one

**Finding ID:** `PERF-669F7673A242`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:3218</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** main-thread array scans/splices, view-model reconciliation, response disposal, and model change notifications  
**Scaling:** For k missing requests in a transcript with n request/response rows, this performs k individual removals; each removal linearly searches and splices ChatModel, linearly searches/splices ChatViewModel rows, and causes PersistentBackgroundActivityTracker to rescan all responses, yielding O(k\*n) synchronous work (O(n^2) when IDs for many locally sent turns are replaced).  
**Outcome:** A host history replacement can block the renderer/main thread and make a long chat visibly hang while its transcript is reconciled.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, a ChatTruncated/ChatTurnsLoaded replacement refreshed host history but did not synchronously remove each unmatched ChatModel request, so it did not trigger a full chain of per-request model/view listeners on this action path.  
**Changed behavior:** The new replacement handler builds the missing set and invokes ChatService.removeRequest once per missing completed request. Although wrapped in Promise.all, ChatService.removeRequest contains no await and calls ChatModel.removeRequest synchronously, so all removals and their listeners run back-to-back in the action callback.  
**Confidence:** 0.94 — The synchronous call path and linear per-removal listeners are explicit, and the replacement scenario is directly documented and exercised by the added test. Exact latency depends on transcript length and how many locally sent IDs are replaced, so severity is medium rather than high.

**Causal diff evidence:** Added line 3218 maps every element of \`missing\` to a separate \`\_chatService.removeRequest(...)\`; this is the line that introduces the repeated synchronous model/view update chain on host history replacement.

When an externally restored or taken-over long session gives new stored IDs to many turns sent from this window, applying ChatTurnsLoaded repeatedly scans and mutates the remaining transcript for every missing turn, causing UI jank proportional to the product of missing and total turns.

**Evidence:** ChatService.removeRequest synchronously calls model.removeRequest (chatServiceImpl.ts:2639-2653). ChatModel.removeRequest uses findIndex/splice and fires one removeRequest event (chatModel.ts:3792-3803). ChatViewModel handles every event with up to two additional findIndex/splice passes (chatViewModel.ts:417-443), while PersistentBackgroundActivityTracker directly handles every model removal by rebuilding a Set from all response items and reconciling it (chatListRenderer.ts:858-902). The host's refreshChatHistory emits the truncate/load pair with an unbounded turns array (agentHostStateManager.ts:792-800), including reload and provider-history refresh paths.

**Suggested direction:** Add/use a bulk removal operation that identifies all missing IDs once, removes/disposes them in one pass, resets billing once, and emits one batched/initialize-style model change so view-model and renderer reconciliation run once; then restore host usage once after the batch.

### Scenario 1: Reloading or taking over an already-open agent chat replaces the host transcript after stored turn IDs differ from requests sent by this window.

- Critical path: Provider/session history reads and hydration finish first; the host then emits ChatTruncated followed by ChatTurnsLoaded. On the ChatTurnsLoaded action-processing/UI path, the added handler computes missing requests and synchronously executes every ChatService/ChatModel removal and model/view listener before its first await settles, so this cleanup blocks action progress and rendering.
- Scaling input: n loaded ChatModel requests/response rows and k completed local requests absent from the replacement. Effective cardinality is k removals after Set-based ID deduplication; cost is O(k\*n), reaching O(n^2) when many locally sent turn IDs are replaced.
- Effective concurrency: Host refreshes are serialized per chat by \`\_chatHistoryRefreshes\`. The added Promise.all does not provide useful concurrency because \`ChatService.removeRequest\` has no await and synchronously mutates the model; all k removals execute back-to-back on the main thread. Separate chats may receive independent action streams, with no shared limiter for their UI reconciliation.
- Cache behavior: The host and ChatModel states are already in memory. There is no cleanup cache or coalescing; every authoritative replacement recomputes IDs and repeats listener reconciliation. Cold versus warm state does not change the new O(k\*n) path, though the pre-existing provider/storage work may vary.
- Mechanism confidence: High: the added line invokes one synchronous removal per missing request, and each traced model/view/renderer listener contains full-array scans or splices.
- Magnitude uncertainty: The exact number of turns sent in one window and per-listener duration varies; short chats will not show visible delay. Long-running agent sessions can realistically accumulate enough replaced local turns for the quadratic main-thread work to become noticeable, so severity is medium.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/agentService.ts \`\_getChatMessages\` (around 10808)</code>: Read the provider's complete chat messages via \`provider.chats.getMessages\`.; cardinality: One provider read for a reload replacement, returning n turns; host per-chat sequencing prevents duplicate concurrent reads for the same queued refresh.
    - Introduced by diff: false; previous behavior: The same provider read and hydration occurred before this diff; the workbench then refreshed history without deleting each unmatched ChatModel request.; critical-path effect: Must complete before the replacement actions can be emitted; it precedes the newly added UI cleanup.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts \`\_loadWorkspaceTransitions\` (around 10863)</code>: Open/read session storage for workspace-transition hydration.; cardinality: One storage lookup per host history refresh, independent of k missing workbench requests.
    - Introduced by diff: false; previous behavior: Identical storage hydration existed before the diff.; critical-path effect: Completes before hydrated turns and replacement actions are available; it is not part of the added removal loop.
  - IPC at <code>src/vs/platform/agentHost/node/agentHostStateManager.ts \`refreshChatHistory\` (792-800); src/vs/platform/agentHost/common/state/agentSubscription.ts \`receiveEnvelope\` (219-243)</code>: Deliver the server-originated ChatTruncated and ChatTurnsLoaded action envelopes from the agent host to the workbench subscription.; cardinality: Two protocol actions per changed authoritative history, regardless of n or k.

- Verdict: Reportable medium performance regression. Batch model mutation and one reconciliation event can preserve replacement semantics while avoiding O(k\*n) UI work.

### Scenario 2: Paging older host turns into an open transcript via ChatTurnsLoaded without a preceding server-originated clear.

- Critical path: A pre-existing fetchTurns protocol roundtrip loads a page, then ChatTurnsLoaded prepends it and refreshHistory updates the visible transcript. The added \`replaced\` guard remains false, so \`\_removeRequestsMissingFromHost\` is not called.
- Scaling input: One fetched page plus the already loaded turn window; the new code performs only constant flag/action checks.
- Effective concurrency: Protocol action application is ordered. Paging does not launch the Promise.all removal path, and no new concurrency or fan-out is introduced.
- Cache behavior: Already loaded turn IDs are deduplicated by the existing reducer; repeated pages do not activate cleanup. Cold first-page and warm subsequent-page behavior are unchanged by the diff.
- Mechanism confidence: High: the handler records \`replaced\` only from the immediately preceding server-originated full ChatTruncated action.
- Magnitude uncertainty: Provider-specific page sizes are not established here, but they do not affect the new guarded cleanup because no server clear precedes paging.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/common/state/protocol/channels-session/commands.ts \`FetchTurnsParams\`; src/vs/platform/agentHost/node/protocolServerHandler.ts \`fetchTurns\` (2625-2640)</code>: Send fetchTurns and receive ChatTurnsLoaded over the existing agent-host protocol.; cardinality: One command/response-action sequence per requested page.
    - Introduced by diff: false; previous behavior: Paging used the same roundtrip and history refresh before the diff.; critical-path effect: The roundtrip must finish before older rows appear; the diff adds no boundary and no removal work on this path.
- Verdict: No reportable regression; the added checks are constant-time and the test explicitly covers this no-removal path.

### Scenario 3: Normal live turns and client-originated truncation/undo actions update an open chat.

- Critical path: Existing host protocol actions reduce state and update history/progress. Client-originated ChatTruncated envelopes fail the \`\!envelope.origin\` condition, and ordinary turn actions do not match either new action branch.
- Scaling input: Action frequency follows live response/progress events, but the changed code performs only a few comparisons per relevant truncate/load action, not per streamed token or response part.
- Effective concurrency: Existing ordered action processing is unchanged; no removal tasks are started for client-originated truncation or normal turn actions.
- Cache behavior: The new host-usage accessor reads the current in-memory session subscription and performs the same \`readChatUsage\` work previously done by \`updateSessionCost\`; no cache behavior changes.
- Mechanism confidence: High: action-type and origin guards exclude these actions from the cleanup helper.
- Magnitude uncertainty: Live action rates vary, but the changed comparisons are trivial and do not invoke collection work on this scenario.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/common/state/agentSubscription.ts \`receiveEnvelope\` (219-243)</code>: Exchange existing live chat action envelopes with the agent host.; cardinality: Existing per-action delivery; no additional messages are emitted by the diff.
    - Introduced by diff: false; previous behavior: The same actions crossed the boundary and drove the same normal history/progress handling.; critical-path effect: Only constant-time branch/state updates are added unless the specific authoritative replacement pair occurs.
- Verdict: No reportable performance regression.

**Summary:** Reviewed both changed files and traced host history replacement through provider refresh, protocol actions, ChatService/ChatModel removal, ChatViewModel, and renderer listeners. Reported one medium-confidence scaling regression: per-request removal creates quadratic synchronous transcript reconciliation. Paging and ordinary action handling do not activate the new cleanup and add no performance regression. The PR fixes duplicate-turn correctness, but available evidence does not establish a shipped performance symptom suitable for regression-fix learning.
