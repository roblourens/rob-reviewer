### Scenario 1: Create or resume a Copilot Agent Host session with SDK sandboxing enabled, then apply later sandbox configuration changes.

- Critical path: Session configuration is built before the SDK create/resume RPC; the sandbox configuration is included in that existing RPC and is applied again through the existing options.update RPC during finalization. Later relevant config changes pass through the existing sequencer and await options.update only when serialized configuration differs.
- Scaling input: One added application-root string per sandbox configuration, independent of application file count, attachment count, plugin count, history size, or workspace size.
- Effective concurrency: Launch operations follow the existing session launch sequence. Runtime configuration mutations are serialized by \_configSequencer; the diff introduces no parallel RPCs or burst.
- Cache behavior: appBundleRoot is memoized on first access. \_appliedConfig stores the serialized effective configuration and suppresses unchanged options.update calls; managed readonly policy can omit all host-generated extra roots. No new cache key or negative-cache state is introduced.
- Mechanism confidence: High confidence from tracing getLaunchConfig/\_computeConfig through launch and \_updateConfig: the changed behavior alters only the existing configuration payload and no boundary cardinality.
- Magnitude uncertainty: Exact SDK serialization and runtime policy-compilation duration is not measured, but the increment is one path string and cannot scale with installation contents because no traversal is performed here.

### Scenario 2: Wrap or preflight a command through the Agent Host custom terminal sandbox.

- Critical path: On first use or policy/command invalidation, wrapCommand awaits sandbox JSON regeneration before returning a wrapped command. checkFileAccess independently resolves effective filesystem paths before returning its preflight decision.
- Scaling input: One additional host read root per generated/access-check policy. Cost scales with sandbox regenerations or access checks, not with the number of files beneath the application root.
- Effective concurrency: All effective paths in one policy are canonicalized with Promise.all, so the new realpath joins the existing batch. The engine caches the generated config path between unchanged commands; the diff adds no scheduler, queue, or new command-level parallelism.
- Cache behavior: The environment getter is memoized. TerminalSandboxEngine reuses \_sandboxConfigPath until force refresh or root/settings/command inputs require regeneration; canonicalized roots themselves are not cached, so the new root adds one realpath per regeneration or access check.
- Mechanism confidence: High confidence that one filesystem operation is added on regeneration/access checks; high confidence that it remains constant-cardinality and joins an existing parallel resolution batch.
- Magnitude uncertainty: Filesystem latency varies, but the added operation is one local realpath against the installed application directory and no evidence shows traversal, fan-out, or a remote/network path in this scenario.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/sandbox/common/terminalSandboxEngine.ts:904</code>: Canonicalize the application root with fileService.realpath while resolving allow-read paths.; cardinality: One additional realpath per sandbox JSON regeneration and per checkFileAccess policy resolution; it is batched with existing root resolutions and does not recurse into the directory.
    - Introduced by diff: true; previous behavior: Existing session, runtime, workspace, configured, and command roots were canonicalized; the application installation root was not.; critical-path effect: Awaited by policy generation/access preflight, but adds only one local metadata lookup at constant cardinality.
  - filesystem at <code>src/vs/platform/sandbox/common/terminalSandboxEngine.ts:675</code>: Overwrite the terminal sandbox JSON policy file.; cardinality: One existing write per first use or invalidating refresh; unchanged commands reuse the cached path.
    - Introduced by diff: false; previous behavior: The same file was already serialized and written with all other effective roots.; critical-path effect: Awaited before command wrapping; payload grows by one path (or original plus canonical path for a symlink).
- Verdict: No reportable regression. The single bounded metadata lookup is a micro-cost, while config caching prevents unconditional per-command repetition and no directory contents are scanned.

### Scenario 3: Resolve the native application bundle root for sandbox policy composition.

- Critical path: The first sandbox policy computation reads appBundleRoot and performs synchronous path parsing; subsequent reads return the memoized value. This work occurs before the existing sandbox RPC or terminal-policy generation.
- Scaling input: Fixed number of dirname/basename/parse operations over one short installation path.
- Effective concurrency: Synchronous one-time getter evaluation per environment-service instance; no spawned work or fan-out.
- Cache behavior: &#64;memoize retains the computed string for the environment-service lifetime. Source/non-built layouts return the already memoized appRoot.
- Mechanism confidence: High confidence from the getter and getAppBundleRoot implementation.
- Magnitude uncertainty: None material: the helper performs no filesystem, IPC, network, subprocess, or database operation.
- Expensive boundaries: none found
- Verdict: No reportable regression. This is bounded one-time CPU work with no expensive boundary.
