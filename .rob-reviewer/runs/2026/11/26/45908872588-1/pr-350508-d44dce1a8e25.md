### Scenario 1: Reply to the current turn's exact sender using send\_remote\_message, including nested and same-host senders; preserve explicit-target and origin sends.

- Critical path: Tool preparation resolves the source session, reads the current chat only for the new sender alias, and resolves the target before approval. Invocation repeats resolution, then waits for target state, workspace trust, background client-tool preparation, dispatch, and acknowledgement. Explicit targets and origin bypass the added source-chat read.
- Scaling input: One source chat and one destination per distinct tool request, including each hop in a delegation chain. Cold snapshot bytes depend on that chat's history; this is not a read per historical turn or per connected session.
- Effective concurrency: Sender resolution precedes the existing per-target SequencerByKey and send limiter. Concurrent acquisitions for one source share its subscription; different resources remain independent. Destination delivery is serialized per target chat, not globally. This diff adds no loop over destinations or sessions.
- Cache behavior: AgentSubscriptionManager shares both hydrated and in-flight subscriptions by resource. Current-turn client tools run through AgentHostSessionHandler, which holds default or additional chat subscriptions; background remote chats also retain models during active work. Thus the normal sender lookup reuses state without a wire read. An unheld or errored source subscription can require one snapshot per resolution, potentially two across preparation and invocation when no other owner retains it. The new reference, timer, and cancellation source are disposed in finally. send() shares in-flight and settled results for the same source/request ID within its existing retry window.
- Mechanism confidence: High confidence from the routing branches, subscription manager's refcount/in-flight behavior, client-tool invocation path, and finally cleanup. The only added boundary is conditional source-chat subscription acquisition.
- Magnitude uncertainty: Cold source-state lookup duration and snapshot sizes were not measured. Ordinary current-turn tool execution has held chat state; no evidence establishes repeated cold transcript transfers on that normal path.

### Scenario 2: Read get\_session\_context to find sender addresses for recent or earlier agent-authored turns.

- Effective concurrency: Existing listing legacy fallback is limited to four concurrent sessions, with provider prewarming grouped by provider. Session and chat restores coalesce per resource. Added window serialization is synchronous and bounded, with no asynchronous fan-out.

### Scenario 3: Reply to a same-host sender's exact chat through send\_message, including a recorded default chat absent from a stale listing.

- Scaling input: One linked target per send. Existing session/chat lookup can scan known metadata, but the added recorded-default lookup is an in-memory lookup; no new loop or destination fan-out.
- Effective concurrency: Existing SequencerByKey serializes queued sends by exact destination chat; different chats remain independent. The changed argument resolver performs no concurrent work.

- Mechanism confidence: High: traced getDefaultChat through agentHostChatOwnershipService to agentHostStateManager's in-memory entries; the added branch does not load or enumerate storage.
