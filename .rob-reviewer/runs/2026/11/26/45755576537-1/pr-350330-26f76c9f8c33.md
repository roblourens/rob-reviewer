# Performance review: chat: show model provider logos on subagents and routing rows

## Findings (1)

### 1. [medium] Avoid rescanning Fusion routing on every streamed update

**Finding ID:** `PERF-F85E8477B002`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:4559</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Response-part traversal and newly allocated system-notification metadata/row objects on the workbench thread.  
**Scaling:** For D relevant state/stream updates, adds O(sum(P\_current)) active-part visits plus O(D \* P\_previous) predecessor-part visits, even when there are zero new Fusion model changes. Metadata allocations scale with the notifications revisited; effective emitted rows remain bounded by actual model changes.  
**Outcome:** Increased synchronous workbench CPU and short-lived allocation during streaming, reducing responsiveness and delaying response updates as turns grow.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The existing reducer and keyed progress adapter handled streamed updates, but there was no Fusion-routing scan of the active transcript or repeated parsing of the completed predecessor transcript for each update.  
**Changed behavior:** Every streamed markdown/reasoning or tool update now rescans the active turn's responseParts for Fusion metadata, and every merged-state update rescans the completed predecessor's responseParts. Deduplicating the resulting rows does not deduplicate these computations, and disabled logos or non-Fusion turns still pay the scans once the explainability treatment is known.  
**Confidence:** 0.96 — Traced ChatDelta through updateResponsePart's new responseParts array, ChatStateSubscription's synchronous onDidChange, observableFromSubscription, and the new derived/autorun. DerivedImpl computes the value before applying equalsFn. fusionPassModels explicitly visits every part and allocates metadata objects for system notifications. Exact CPU time and frequency of very long turns are not measured.

**Causal diff evidence:** Added agentHostSessionHandler.ts:4559 derives fusionPassModels from the entire responseParts$ on every invalidation; added :4386 derives previousFusionPassModel directly from mergedState$. The new autorun reads this derived before the ModelLogos setting is checked, which only happens in toFusionPassResolution at :8212. Previously neither Fusion-specific scan existed.

Long, tool-heavy agent-host tasks followed by another streamed response repeatedly traverse hundreds of already-processed parts and reparse their notifications on the workbench thread, adding CPU/GC pressure and delaying progress rendering and input responsiveness. This also affects ordinary non-Fusion chats and Stable with model logos disabled.

**Evidence:** protocol/channels-chat/reducer.ts:371-376 and :294-325 replace the responseParts array for each ChatDelta; tool updates do likewise at :267-285. agentSubscription.ts:624-640 fires onDidChange per envelope, and :1514-1519 adapts it without debounce. The new derived at agentHostSessionHandler.ts:4559 invokes stateToProgressAdapter.ts:1067-1089's full loop; :1093-1097 repeats that loop for the previous completed turn on merged-state changes. readAgentSystemNotificationMeta constructs an object for every notification visited. observableInternal/observables/derivedImpl.ts:201-217 applies equality only after computing the value.

**Suggested direction:** Consume Fusion model changes incrementally through the existing keyed notification handling, seed once when joining, and rebuild for snapshot replacement/truncation. Derive/cache the predecessor result from its responseParts identity rather than the whole merged state, and avoid activating this work when the feature is disabled.
