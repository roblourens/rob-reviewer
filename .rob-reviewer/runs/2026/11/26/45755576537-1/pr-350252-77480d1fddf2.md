## Findings (1)

### 1. [low] Prune action IDs for worktrees that leave the filter

**Finding ID:** `PERF-F7EB86DAE4ED`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentSessionsFilter.ts:372</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Strongly retained worktree/repository URI comparison-key strings and Map entries containing numeric action IDs.  
**Scaling:** O(W\_history + R\_history) retained entries over the filter lifetime, after deduplication by worktree/repository URI, even if W\_current remains bounded. Repeated sessions in an existing worktree do not add entries.  
**Outcome:** Persistent heap growth proportional to historical distinct worktrees rather than currently offered worktrees; old key strings cannot be reclaimed while the view remains alive.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The filter held only current worktreeOptions and disposable action registrations. Rebuilding disposed departed worktree commands; no additional map retained their URI keys indefinitely.  
**Changed behavior:** Worktree command IDs now require a persistent URI-key-to-number mapping. Entries survive after their worktrees disappear from the current filter options, accumulating for the lifetime of the Chat view.  
**Confidence:** 0.97 — The insertion and absence of any eviction are directly traced; ChatViewPane owns this filter for its view lifetime. getWorktreeFilterOptions deduplicates by folder URI, and the session-change listener replaces the current options when sessions leave. The retained objects are only URI strings and numeric map entries, so the magnitude is modest and workload-dependent, not a retained session/DOM graph.

**Causal diff evidence:** The added RIGHT line 372 inserts every offered option.key into the newly added worktreeActionIds Map (line 106) via getOrSet. Before the diff, the command ID was derived directly from encodeURIComponent(option.key), with no historical ID map. updateFilterActions() clears actionDisposables, but neither it nor the session-change listener removes departed keys from the new map.

In a long-running Chat view that repeatedly creates and archives or deletes sessions in new worktrees, memory for every previously offered folder key remains retained even when only a small set of worktrees is still active.

**Evidence:** AgentSessionsFilter.registerListeners (lines 137–151) replaces worktreeOptions and rebuilds actions when the session set changes; getWorktreeOptions (line 163) excludes archived sessions. getWorktreeFilterOptions in chat/common/sessionWorktreeFolders.ts emits one option per distinct worktree URI plus its repository, not one per session. updateFilterActions (lines 234–248) disposes old commands; registerAction2 and CommandsRegistry remove registrations on disposal. The new worktreeActionIds map is only read/inserted at line 372 and has no deletion. ChatViewPane creates the filter with this.\_register at line 968, so closing the menu does not release it.

**Suggested direction:** Keep IDs stable for options that remain present, but prune mappings for departed options when rebuilding. Allocate IDs with a separate monotonically increasing counter rather than Map.size so removed IDs are never reassigned to another folder while an old menu may still reference them.
