### Scenario 1: Construct, resize, and dispose Remote Environments; open the header More Actions menu or accessibility help.

- Critical path: Widget construction adds one ActionBar and dropdown control. Menu contents are requested only when the context menu opens; getAddActions reads two observable values and creates at most three actions plus a separator. Accessibility help remains generated on demand. No new discovery or connection work must finish before the menu opens.
- Scaling input: One header control per widget, independent of environment count; at most three menu actions per opening. Existing table rendering and help generation retain their previous multiplicity.
- Effective concurrency: Synchronous bounded menu construction. ActionBar owns and disposes its view items; DropdownMenuActionViewItem registers its dropdown and hover resources. Both the added Action and ActionBar are registered with the widget.
- Cache behavior: Menu availability reads already-maintained observable state, not fresh Docker or authentication queries. Docker availability is cached per connector or remote connection, including negative results, in DevContainerEnvironments.\_updateEnvironmentHosts. Opening the menu does not invalidate or rerun those checks.
- Mechanism confidence: High: the lazy action-provider callback, constant-sized getAddActions implementation, unchanged render subscriptions, and disposal ownership were traced.
- Magnitude uncertainty: No profiling of the extra header control or changed flex layout; their cost is bounded and no changed repeated layout or collection-wide work was found.
- Expensive boundaries: none found
- Verdict: No reportable regression: a bounded header control and on-demand menu are added without eager boundary calls, collection-scaling work, or lost cleanup.

- Effective concurrency: One awaited action flow; independent addresses may connect concurrently as before. Same-address requests join existing work.
- Cache behavior: Connected addresses are reused. Renderer and node services join in-flight requests by connection key and remove pending entries after settlement. Cancellation during prompts issues no connection; failure cleanup and progress-listener disposal remain unchanged.
- Mechanism confidence: High: the new action calls the unchanged credential/connection helper, with connected-address reuse and both renderer/node pending maps traced.
- Magnitude uncertainty: Cold SSH setup duration depends on authentication, network, and remote installation. No measurements were taken; no increased work per equivalent connection was found.
- Expensive boundaries:

### Scenario 4: Create a Dev Container from the header when this computer or a connected host supports Docker.

- Effective concurrency: Per-environment operation sequencing and pending-connect joining; independent environments can run concurrently. Neither the header route nor its availability evaluation introduces an automatic burst.
- Cache behavior: Host/Docker availability comes from existing positive/negative connection-scoped checks. The node service caches Docker executable resolution. Cold images may need Docker downloads; warm image/container state reuses existing Docker behavior. New environments intentionally have distinct IDs.
- Mechanism confidence: High: the header callback, host selection, environment creation, per-state queue, connector dispatch, and node source-key queue were traced.

- Scaling input: Distinct SSH aliases A, configured additional tunnel names N, and returned inventory sizes. Discovery launches four method tasks, SSH resolves at most eight aliases concurrently, WSL uses two probes total, and tunnel additional-name lookups are sequential.
- Effective concurrency: Four method tasks in Promise.all, with SSH's eight-wide limiter, two parallel WSL probes, and sequential additional-tunnel-name requests. Sign-in remains guarded until its follow-up refresh settles. Existing refresh cancellation/version handling is preserved.
- Cache behavior: The menu uses the recorded authentication-required state. Sign-in is coalesced by a widget-wide guard. Refresh uses cached authentication silently, preserves previous inventory on failed methods, deduplicates SSH aliases, and forces existing GitHub inventory refresh. Cancellation/version checks and refresh-button disabling are unchanged.
