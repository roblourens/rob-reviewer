# Performance review: agentHost: report Dev Container connect failure stages and up error causes

## Findings (1)

### 1. [medium] Classify failed CLI output without rebuilding the entire log

**Finding ID:** `PERF-93BE142E5DC8`  
**Location:** <code>src/vs/platform/agentHost/node/devContainerState.ts:737</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Whole-log derived strings, multiple arrays of log lines, and one RegExp object per retained line, in addition to the already captured stderr.  
**Scaling:** For each non-lifecycle/non-config failed stage, extra allocation grows with total stderr bytes B and retained line count L: O(B+L) auxiliary memory and O(L) temporary RegExp objects. Same-source attempts are serialized, but independent sources share the host event loop; no cache or grouping reduces this per-failure log processing.  
**Outcome:** Increased transient heap usage and GC pressure, with synchronous failure-path latency and host event-loop blocking.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With persistUserState=false, \_runDevContainerStage parsed the existing stdout result and returned without any failure-telemetry normalization of stderr. With persistence enabled, getDevContainerCliErrorMessage scanned stderr for a daemon line but, when the CLI supplied its normal error result, sanitized only description/message and that selected daemon line rather than rebuilding all stderr.  
**Changed behavior:** An unsuccessful up now synchronously normalizes the complete captured debug stderr into a second log-sized string, with several line arrays and a RegExp object per retained line, merely to select one of five fixed categories. This runs even when state persistence is disabled.  
**Confidence:** 0.92 — The caller passes the uncapped stderr accumulated by \_runDevContainer, and the new helper explicitly materializes the whole log before classification. The disabled-setting before/after difference is visible in the diff. This is static evidence; how large typical failing build logs are and the resulting pause duration are not measured. Lifecycle/config descriptions return early and are excluded from this trigger.

**Causal diff evidence:** The added devContainerState.ts:737-740 concatenates description/message with all output, strips ANSI, splits, filters, maps, and rejoins it. The changed \_runDevContainerStage at devContainerAgentHostService.ts:908 newly invokes this with result.stderr on every unsuccessful stage, including persistUserState=false; previously the report flag excluded all failure-telemetry processing in that arm.

A workspace Dev Container whose verbose image build fails after producing a large debug log incurs an additional heap/GC spike and delayed failure reporting in the shared process or standalone remote host. Other work on that host's event loop is also delayed. This occurs once per failed stage, not once per container, volume, or output chunk.

**Evidence:** \_connect runs up with DEV\_CONTAINER\_LOG\_ARGS=\['--log-level','debug'\] (service.ts:63,378-387). \_runDevContainer accumulates every stderr chunk without a size limit (1221-1266). On failure, \_runDevContainerStage calls getDevContainerUpErrorCause(parseDevContainerErrorResult(result.stdout), result.stderr) before returning (908). Unless a lifecycle/config description matches, the added helper creates a concatenated/normalized whole-log string, split/filter/map arrays, per-line RegExp objects, and a joined whole-log string (state.ts:737-740), then scans that string with the category patterns. The connection cannot reject or release its per-source sequencer until this synchronous work finishes.

**Suggested direction:** Classify the existing output incrementally, processing one line or bounded chunk at a time and retaining only the highest-priority matching category. Reuse the failed-command RegExp instead of constructing it per line; preserve lifecycle/config precedence and command-log exclusion without split/filter/map/join materialization of the complete log.
