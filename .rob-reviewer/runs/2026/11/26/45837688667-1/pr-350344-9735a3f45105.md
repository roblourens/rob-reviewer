SDK positive cache is version/target keyed with a completion sentinel, in-flight downloads are shared, and recent non-cancellation failures are negatively cached. ### Scenario 3: Send successive messages while workspace folders are replaced, reduced, removed or become virtual-only.

- Critical path: Send filters the snapshot, adopts a different local cwd only through existing prewarm rules, refreshes MCP discovery, reconciles customization signatures, and awaits one turn/start acknowledgement. Already materialized threads retain their process cwd.
- Scaling input: Current URI snapshot N, retained distinct roots K, messages M, and customization files in retained roots. An empty local snapshot falls back to the one existing cwd rather than accumulating historical roots.
- Effective concurrency: Send preparation is sequential along its awaits; MCP root scans are shared/serialized per root and concurrent across roots. Materialization and resume use per-session promises. Linux start/resume/fork locking is per intersecting root set; turn/start is one request containing the entire root array.
- Cache behavior: MCP roots are signature-keyed, shared and initialized even for empty results. Root-set changes dispose prior entries. Materialized customization/MCP signatures avoid reload when stable; customization filesystem scanning itself remains uncached. Undefined legacy snapshots preserve restored roots, while explicit empty snapshots replace them.
- Mechanism confidence: High: changed empty-snapshot assignment, customization fallback, cached MCP implementation, prewarm adoption and reload signature checks were traced; added tests corroborate one existing-thread turn request and cwd-only roots after removal.
- Magnitude uncertainty: File counts under the retained cwd and cost of a one-time signature transition are unmeasured. No evidence shows new collection fan-out, repeated reloads or unbounded retained roots.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts: \_refreshSessionMcpDiscovery / \_buildCustomizationLaunch</code>: Refresh cached MCP snapshots and discover customization files for the current effective roots.; cardinality: MCP disk reads are cold per shared root or watcher-forced; root-set replacement disposes prior discovery references. Existing customization scans run during send preparation. After an explicit empty snapshot, discovery can use the single existing cwd instead of zero customization roots.
    - Introduced by diff: true; previous behavior: MCP discovery already fell back to session.workingDirectory when the snapshot was empty. Workspace customization discovery previously saw an explicit empty array; the new undefined fallback intentionally gives it the existing cwd, matching ordinary single-root behavior.; critical-path effect: Discovery needed for launch signatures is awaited before turn submission.
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts: \_adoptWorkingDirectoryBeforeSend / \_resumeSession / \_sendMessage</code>: Unsubscribe/recreate stale prewarm when adopting a genuinely different local cwd, resume when launch signatures change, and submit turn/start with replacement runtime roots.; cardinality: One turn/start per ordinary message, not per root. - Verdict: No high-confidence actionable performance bug: the changed fallback intentionally retains the thread's cwd, with bounded single-root discovery and existing signature-based reload behavior. Additional transient filtering is not a demonstrated material regression.

### Scenario 5: Fork an existing Codex chat, including one created with only virtual workspace folders.

- Critical path: Fork creation resolves the source binding, resumes the source if required, reads authoritative source turns, resolves the requested fork boundary, optionally prepares/copies managed scratch, and awaits thread/fork. The fork's first send later resumes its backing.
- Scaling input: Source history H and page count P, inherited distinct local roots K, and managed scratch file count/bytes B when the source owns scratch. Root filtering does not increase H or P.
- Effective concurrency: Source reads/history pages complete in order. Fork creation is sequenced per chat, and Linux thread/fork shares the sorted intersecting-root sequencer. Recursive scratch copy is one awaited operation per managed fork; the diff adds no copy loop or concurrency burst.
- Cache behavior: Live source bindings and working directories are reused. The existing read and history handling is unchanged. Managed scratch is an owned per-backing resource, not an accumulating cache; source and fork each retain their own explicit path.
- Mechanism confidence: High for call-path and ownership: source resolution, history paging, inherited root filtering, managed scratch copy and error cleanup were inspected.
- Magnitude uncertainty: Actual scratch size and fork history length are unmeasured. Large managed scratch can make the existing copy expensive, but no new multiplicity or avoidable copying was established.
- Expensive boundaries:

- Verdict: No reportable regression: filtering narrows inherited roots and preserves the existing semantics required for independent forks of workspaceless sources.
