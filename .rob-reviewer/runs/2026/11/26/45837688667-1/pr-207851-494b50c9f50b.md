### 1. [high] Dispose active gutter views before removing their DOM

**Finding ID:** `PERF-EB0DDE410644`  
**Location:** <code>src/vs/editor/browser/widget/diffEditor/utils/editorGutter.ts:60</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Detached toolbar DOM trees, menu and configuration listeners, gutter/item state and editor references retained through action-runner closures.  
**Scaling:** Each destroyed gutter leaks its last V visible views; repeated gutter/widget lifecycles retain the sum of those V values. Views previously scrolled offscreen are disposed and do not contribute.  
**Outcome:** Session-long retained-memory growth and increasing work on global menu/configuration events.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** RevertButtonsFeature registered every RevertButton in its autorunWithStore and removed glyph widgets on teardown; disposing the feature disposed its buttons and listeners.  
**Changed behavior:** Disabling the gutter or disposing a diff widget detaches its DOM while leaving the currently visible DiffToolBar instances, their menus, hover delegates, observable reactions and action-context closures alive.  
**Confidence:** 0.99 — Item views are stored only in views, not registered with EditorGutter's disposable store. DiffToolBar owns menu/hover subscriptions; MenuImpl registers with the global MenuRegistry and persisted hidden-state emitter. Those roots survive editor disposal. Offscreen removal correctly disposes views, but gutter disposal does not.

**Causal diff evidence:** The new dispose() calls super.dispose() and reset(this.\_domNode) without disposing any views. Added lines 107-112 create and retain DiffToolBar instances, while line 136 shows the explicit disposal required when a view leaves the viewport.

When a multi-diff widget is destroyed or renderGutterMenu is disabled with hunks visible, its active toolbars remain reachable from global event sources. Repeating these lifecycles accumulates detached UI and listeners instead of releasing them.

**Evidence:** EditorGutter.dispose (57-61) never walks views. DiffToolBar creates WorkbenchHoverDelegate (gutterFeature.ts:180-185) and MenuWorkbenchToolBar inside its own registered autorunWithStore (200-233). MenuWorkbenchToolBar registers its MenuImpl and menu-change listener (toolbar.ts:317-335); MenuImpl subscribes to MenuRegistry.onDidChangeMenu and hiddenStates.onDidChange (menuService.ts:351,392). The menu's toolbar listener and action runner retain the detached toolbar and gutter. WorkbenchHoverDelegate additionally subscribes to configuration changes (hover.ts:262).

**Suggested direction:** Before resetting the DOM, dispose every view.gutterItemView and clear views, using the same ownership cleanup as the offscreen-removal path.

### 2. [medium] Keep gutter action context range-based

**Finding ID:** `PERF-FE026225C5A1`  
**Location:** <code>src/vs/editor/browser/widget/diffEditor/features/gutterFeature.ts:222</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Whole-file strings, JSON serialization/UTF-8 request buffers and extension-host RPC bytes; synchronous renderer text extraction.  
**Scaling:** For a file of B bytes, each click adds O(B) renderer reconstruction and, for Git actions, O(B) RPC encoding/transfer/decoding regardless of the selected hunk size. Repeated clicks repeat this work even with warm document caches; there is one command request per click, not per inner change.  
**Outcome:** Main-thread stalls and GC pressure on large-file actions, plus increased staging latency from file-sized RPC payloads.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** RevertButton directly reverted the affected range(s), reading only the original changed text. Git stageChange/stageSelectedChanges passed URI/line-change metadata and \_stageChanges built the full result in the extension host from TextDocuments; ensureDocumentData reuses already-open documents and coalesces cold loads.  
**Changed behavior:** Every action now reconstructs the whole original-with-edits string synchronously in the renderer, even Revert, which ignores it. Git staging additionally sends that full result through the command RPC on every invocation.  
**Confidence:** 0.99 — The action runner unconditionally invokes computeStagedValue before action.run. TextEdit.apply reads unchanged prefix/suffix through the end of the original model. Git's command registration forwards this string through JSON RPC; the prior warm staging path reconstructed the file in the extension host. Revert consumes only mappings. Exact duration is unmeasured, but file-size scaling and main-thread reachability are explicit.

**Causal diff evidence:** Added line 222 materializes originalWithModifiedChanges for every gutter action. Added computeStagedValue at lines 96-100 constructs the entire staged file, and the new Git handler at commands.ts:1534 consumes the transmitted string instead of the previous extension-host reconstruction.

Staging or reverting a small hunk in a multi-megabyte file now processes the entire file before the command can run. Revert pays this cost without using the result; warm Git staging newly serializes and transfers the entire staged file for each click.

**Evidence:** ActionRunnerWithContext.runAction evaluates \_getContext synchronously before super.runAction (multiDiffEditor/utils.ts:13-15). computeStagedValue calls TextEdit.apply(TextModelText), whose apply implementation reads unchanged text through text.endPositionExclusive (textEdit.ts:95-116). RevertHunkOrSelection uses only arg.mapping.innerChanges (diffEditor/commands.ts:183). MainThreadCommands.$registerCommand forwards args to $executeContributedCommand (mainThreadCommands.ts:57-64); RPCProtocol serializes arguments to JSON, UTF-8 buffers and JSON.parse (rpcProtocol.ts:731-791). The old \_stageChanges reconstructs in the extension host (extensions/git/src/commands.ts:1686-1699); ExtHostDocuments.ensureDocumentData returns cached documents or joins a per-URI load (extHostDocuments.ts:78-101).

**Suggested direction:** Forward only the mapping and changed replacement text needed for staging, and reconstruct the staged file inside the Git command using the existing original/modified TextDocument APIs. Revert should receive mappings without constructing staged text. Preserve character-range staging semantics.

### 3. [medium] Batch toolbar measurements instead of flushing layout per new hunk

**Finding ID:** `PERF-EC5AF6BC23ED`  
**Location:** <code>src/vs/editor/browser/widget/diffEditor/features/gutterFeature.ts:245</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Browser synchronous style/layout resolution for toolbar DOM geometry.  
**Scaling:** An initial viewport or scroll step exposing V new hunk views can require a separate layout flush for each of those V views, rather than one batched measurement. Cached existing views avoid creation; geometry/toolbar changes can reintroduce invalidation.  
**Outcome:** Extra synchronous layout on the renderer's initial-render and scroll critical paths, causing slower diff opening and scroll jank.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The revert arrows were glyph-margin widgets. GlyphMarginWidgets.render positioned them using viewport offsets and configured lineHeight, applying cached FastDomNode writes without measuring each arrow's DOM height.  
**Changed behavior:** Rendering newly visible hunks appends a toolbar, writes item geometry, measures its height synchronously, writes more geometry, then repeats that sequence for the next hunk.  
**Confidence:** 0.96 — EditorGutter creates and appends each new visible toolbar inside a loop and immediately invokes layout, which reads clientHeight before the next toolbar is created. New DOM and toolbar contents require layout for that geometry read. The old glyph renderer uses known lineHeight and model coordinates without per-button DOM measurement. Steady-state scrolling can reuse views, so the claim is limited to newly entering views and changed geometry.

**Causal diff evidence:** Added line 245 synchronously reads buttons.clientHeight. Added editorGutter.ts:103-128 interleaves toolbar DOM creation and parent geometry writes with this layout call for every intersecting item.

Opening a diff with many visible hunks, or scrolling a group of new hunks into view, repeatedly forces browser layout while building the gutter. The new default-enabled toolbar path replaces arrows that did not need these per-widget geometry reads.

**Evidence:** EditorGutter.render appends viewDomNode and creates DiffToolBar at editorGutter.ts:103-112, then writes top/height and calls gutterItemView.layout at 125-128 inside the per-item loop. DiffToolBar's constructor inserts toolbar/action-bar DOM (gutterFeature.ts:200-227; toolbar.ts:317-337). layout reads clientHeight twice at gutterFeature.ts:245,248, with a potentially toolbar-rebuilding \_isSmall update between them. Previous GlyphMarginWidgets.render (glyphMargin.ts:399-413) computes dimensions from lineHeight and viewportData and only writes styles.

**Suggested direction:** Create/update all visible toolbars before measuring them, batch geometry reads ahead of writes, and cache intrinsic toolbar height with invalidation on menu/overflow-size changes (or observe height changes). Avoid measuring each newly inserted toolbar inside the item-construction loop.

### 1. eager-work

**Fix location:** `src/vs/editor/browser/widget/diffEditor/utils/editorGutter.ts:97` (`RIGHT`)  
**Blamed base line:** `src/vs/editor/browser/widget/diffEditor/features/revertButtonsFeature.ts:62`  
**Introducing path:** `src/vs/editor/browser/widget/diffEditor/features/revertButtonsFeature.ts`  
**Introducing commit:** `4ab700330c138d400bb21d3670c7f66f745fe33a`  
**Mechanism family:** `eager-work`  
**Performance category:** `rendering`  
**Confidence:** 0.94

**Mechanism:** The original revert feature synchronously constructed and attached one RevertButton DOM widget for every nonempty hunk with inner changes, including all offscreen hunks, during initial diff publication.

**Symptom:** Large diffs with H eligible hunks incurred O(H) hidden button DOM creation and listener allocation on the renderer before initialization completed; the glyph-margin addWidget path attached all widgets with display:none even though only a viewport subset could be shown.

**Fixed behavior:** The default gutter creates live toolbar DOM only for viewport-intersecting items, reuses views by ID, and disposes offscreen views. Live initialization DOM scales with visible V rather than all H eligible hunks.

**Evidence:** Base revertButtonsFeature.ts:59-69 loops through all diff.mappings, creates each RevertButton at blamed line 62, registers it and adds it to the modified editor. RevertButton constructs DOM and mouse listeners; GlyphMarginWidgets.addWidget (glyphMargin.ts:207-222) immediately attaches every widget. The PR suppresses this old feature when renderGutterMenu is enabled (diffEditorOptions.ts:39), now the default. New EditorGutter.render rejects nonintersecting items at line 97 before createView at 107 and disposes views leaving the viewport at 134-139. This specifically removes hidden DOM construction, although the new provider still allocates metadata for all mappings and has separately reported teardown/layout issues.
