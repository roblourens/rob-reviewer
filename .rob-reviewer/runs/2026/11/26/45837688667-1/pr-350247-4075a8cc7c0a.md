## Findings (1)

### 1. [medium] Avoid rescanning the tree for each hidden drop anchor

**Finding ID:** `PERF-9D2392970D4E`  
**Location:** <code>src/vs/workbench/contrib/sessions/browser/views/sessionsList.ts:8761</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Main-thread root-node scans, sibling-array indexOf comparisons, and temporary tree-location arrays  
**Scaling:** With H unpinned root headers hidden by search, the loop performs O(H^2) root visits per drag-over. Each accumulated getListRenderCount resolves the root's location using parent.children.indexOf, producing O(H^3) sibling comparisons in this worst case. Search bypasses workspace/worktree section capping, so H includes all distinct unpinned sections after grouping, plus custom groups; repeated drag events repeat the work.  
**Outcome:** Increased main-thread CPU and allocation pressure delays insertion feedback and makes dragging janky in large filtered session lists.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Header-edge drops used the hovered target's supplied index and, for an after-drop, one render-count lookup. The unchanged placement validation could traverse group state, but it did not scan all root nodes separately for every hidden candidate.  
**Changed behavior:** The new belowPinned feedback path iterates candidate header IDs and calls getTopLevelHeaderIndex for each one. That helper restarts at the root's first child, including search-hidden nodes, and computes preceding render counts on every restart.  
**Confidence:** 0.98 — The added search-and-drag test at sessionsList.test.ts:9058 demonstrates this reachable state: only Pinned has rows, while other headers retain their nodes. The drag-over call chain and nested scans are explicit; render-count lookups also resolve locations through a sibling indexOf. Magnitude is inferred statically, not measured.

**Causal diff evidence:** Added line 8761 invokes getTopLevelHeaderIndex inside the added \_topLevelOrder loop at 8760. Added lines 8783-8789 restart the root traversal and call getListRenderCount for preceding children. Added line 4309 invokes this path from resolveHeaderDrop, which onDragOver calls on every event.

When a user searches a large worktree/group list so only a pinned subtree matches, then drags a nested header to the top edge of a pinned group to extract it, every drag-over repeats these scans across the hidden headers. Accumulated distinct worktrees can make this expensive even though only a few rows are visible.

**Evidence:** SessionsListDragAndDrop.onDragOver calls resolveDrop and resolveHeaderDrop; the new belowPinned branch at 4309 calls getBelowPinnedDropFeedback. With no visible unpinned anchor, 8760-8765 exhaust every candidate and 8783-8789 repeatedly traverse increasingly long root prefixes. objectTreeModel.ts:235-237 and 305-316 resolve each render-count location through indexTreeModel.ts:747-756, whose parent.children.indexOf is linear. listView.ts:1428 calls the delegate before its unchanged-feedback shortcut at 1457, so that shortcut does not coalesce this computation. sessionsList.ts:6427 disables section partitioning during search; groupByWorktree groups by distinct working-directory keys rather than bounding their number.

**Suggested direction:** Build the current visible-header/index lookup once per feedback calculation, or find the first eligible visible anchor with one tree traversal, instead of restarting the root scan for every candidate. Reuse cumulative row counts within that traversal and preserve the hidden-anchor and leading-section fallback semantics.
