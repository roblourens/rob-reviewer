### Scenario 1: An extension registers hosts during activation in an editor or Agents window.

- Critical path: Validation and one extension-host RPC precede synchronous registry publication. Editor windows do not register the extension connection factory, so registration there does not wait for or initiate remote connections.
- Scaling input: R live registration handles, deduplicated to H normalized addresses; the latest registration supplies each address.
- Effective concurrency: One IPC message per registration or disposal; registry mutations are synchronous. Address deduplication happens before connection scheduling.
- Cache behavior: Registrations are in-memory and not persisted. Derived hosts and connectable entries reuse observable values until registrations or disconnect preferences change. Disconnect preferences are loaded once from application storage and updated on storage events.
- Mechanism confidence: High: traced the API, DTO, main-thread disposable map, observable registry, and Agents-only factory registration.
- Magnitude uncertainty: The number of hosts an adopting extension will publish is unspecified. No additional boundary fan-out beyond the registration lifecycle was established.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/common/extHostRemoteAgentHosts.ts:registerRemoteAgentHost</code>: Send a small host descriptor to MainThreadRemoteAgentHosts, and send its handle when disposed.; cardinality: One registration RPC and at most one unregister RPC per API disposable, not per session or rendered row.
    - Introduced by diff: true; previous behavior: No extension remote-host registration API or corresponding RPC existed.; critical-path effect: Required to publish a registration in the window; remote readiness is not awaited by the API.
- Verdict: No reportable regression: lightweight registration is separated from remote readiness, and editor registrations do not eagerly dial hosts.

### Scenario 2: The Agents window connects registered hosts and displays their sessions, including reconnect after transport failure.

- Critical path: For each connectable address, socket establishment, protocol initialization, and required authentication precede connected status; session listing follows connection wiring. Different hosts do not block one another or overall workbench restoration.
- Scaling input: H distinct connectable addresses; A distinct required authentication-resource descriptions per host after deduplication; S returned session summaries per host.
- Effective concurrency: At most one pending dial per address, with no global cross-address limiter. Required authentication resources are resolved sequentially within a host. Listing is serialized/coalesced per connection. Existing default outer reconnect policy has ten attempts and exponential backoff.
- Cache behavior: Pending dials coalesce by normalized address. Repeated reconciliation with the same connection/default directory exits setConnection before listing again. Persisted session summaries are loaded through the existing provider cache, capped at 100 saved entries per host; a live connection still refreshes the authoritative list. Empty successful listings initialize the cache, failures use existing backoff, and concurrent refresh requests share one active plus at most one trailing listing.
- Mechanism confidence: High: traced factory creation through pending-dial ownership, native socket creation, protocol handshake, provider connection identity guard, and coalesced session refresh.
- Magnitude uncertainty: Host count, network latency, credential-provider behavior, and session-history sizes vary. No duplicated per-session network work or new retry bypass was found.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/browser/webSocketConnectionFactory.ts:createConnection; src/vs/platform/agentHost/browser/webSocketClientTransport.ts:connect</code>: Open a native WebSocket and exchange protocol initialization/authentication messages.; cardinality: One initial socket per distinct connectable address; transport recovery follows existing retry logic. Duplicate registrations do not add sockets for the same address.
    - Introduced by diff: true; previous behavior: Extension registrations did not exist. Settings-defined WebSocket hosts used the same transport and handshake implementation; that implementation was extracted without changing their call count.; critical-path effect: Blocks readiness of that host, not other hosts.
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostAuthenticationResolver.ts:\_resolve</code>: Resolve credentials through existing authentication providers for required advertised resources.; cardinality: One resolution per distinct resource/scopes/authorization-server description per authentication pass, not per advertised agent when descriptions match.
    - Introduced by diff: true; previous behavior: The same authentication resolver was already used for settings-defined WebSocket hosts. The diff makes it reachable for the new extension-host kind without changing its grouping.; critical-path effect: Required authentication is on the affected host's handshake path.
  - network/serialization at <code>src/vs/workbench/contrib/sessions/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_listSessions; src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:listSessions</code>: Request the host-wide session listing and deserialize returned summaries.; cardinality: One host-wide listSessions request per effective refresh, with processing proportional to returned summaries; not one request per session.

- Verdict: No reportable regression: the added remote work implements the requested connections, retains address-level coalescing, and reuses established cache/retry behavior.

### Scenario 3: A user disconnects or reconnects an extension host, or its registration/extension host is disposed.

- Critical path: Disconnect first excludes the address from connectable entries, then removes connection state. Reconnect restores eligibility and joins or starts the address's dial. Disposal invalidates registrations and existing reconciliation releases providers/connections.
- Scaling input: D explicitly disconnected addresses retained as user preferences; live registrations and active connections for affected addresses.
- Effective concurrency: Preference updates and registry removal are synchronous; pending connections are tracked by identity. Extension-host manager disposal disposes the main-thread customer, whose disposable map releases its registrations.
- Cache behavior: Disconnect preferences persist across restart and are keyed by normalized address. Identical preference updates are suppressed. Registration disposal removes its exact registration and can reveal an older same-address registration. Obsolete pending connection results are disposed rather than installed.
- Mechanism confidence: High: traced disconnect ordering, disposable ownership through ExtensionHostManager, timer cancellation, and disposal of late connection results.
- Magnitude uncertainty: Preference-set size and registration churn are unspecified; retained preferences are intentional user choices rather than leaked registration objects.
- Expensive boundaries:
  - serialization/storage at <code>src/vs/platform/agentHost/common/extensionRemoteAgentHosts.ts:setDisconnected</code>: Serialize the sorted disconnected-address set into existing application storage, or remove the key when empty.; cardinality: One store/remove operation per actual user preference change, serializing D address strings; registration itself does not write this list.
    - Introduced by diff: true; previous behavior: No extension-host disconnect preference existed; other host-management persistence already used application storage.; critical-path effect: Preference publication prevents automatic redial before connection removal; persistence uses the existing storage service.
  - network at <code>src/vs/platform/agentHost/browser/remoteAgentHostServiceImpl.ts:\_removeConnection; src/vs/platform/agentHost/browser/webSocketClientTransport.ts:dispose</code>: Dispose the protocol client/transport and close its WebSocket; cancel pending reconnect timers.; cardinality: Affected address only; stale asynchronously created clients are also disposed through existing attempt-identity checks.
    - Introduced by diff: true; previous behavior: Identical cleanup machinery handled removed settings hosts; this PR connects extension-registration removal to that lifecycle.; critical-path effect: Releases remote resources during removal rather than retaining them after the registration ends.
- Verdict: No reportable regression: ownership and cleanup are explicit, preference writes are change-sensitive, and removed addresses do not keep retrying.

### Scenario 4: An extension temporarily registers the address of an already configured WebSocket host.

- Critical path: Address upsert chooses one authoritative entry. A change of entry kind replaces the provider to update management options, while the existing address-level connection remains reusable.
- Scaling input: One effective connection/provider per shared address, regardless of competing registration handles; provider reconstruction occurs on kind transitions, not every connection-status event.
- Effective concurrency: Provider replacement is synchronous and owned by the single WebSocket contribution. Address-keyed pending dials and connections avoid parallel duplicate sockets.
- Cache behavior: The replacement provider uses the same address-derived cache key, reloads saved summaries, then refreshes its live listing. Repeated events with unchanged kind/name reuse the provider.
- Mechanism confidence: High: traced configured-entry upsert, provider-kind tracking, provider disposal, and the connection-address reuse checks.
- Magnitude uncertainty: Frequency of overlapping extension/settings registrations is unknown. The reconstruction has an explicit lifecycle/management purpose and is not triggered by unchanged metadata.
- Expensive boundaries:
  - storage/network at <code>src/vs/workbench/contrib/sessions/providers/remoteAgentHost/browser/entryDrivenProviderContribution.ts:\_reconcileProviders; src/vs/workbench/contrib/sessions/providers/remoteAgentHost/browser/remoteAgentHostSessionsProvider.ts:setConnection</code>: Read the existing session cache and issue the replacement provider's live session refresh.; cardinality: One cache load and effective listing per actual provider kind transition; no per-session remote requests.
    - Introduced by diff: true; previous behavior: Only the settings kind could supply this address, so extension/settings ownership transitions did not exist.; critical-path effect: Refreshes the replacement provider's session view; does not require redialing the already connected host.
- Verdict: No reportable regression: the new kind-transition work is bounded and duplicate-address connections remain consolidated.

- Effective concurrency: UI updates are synchronous. Explicit refresh runs SSH, WSL, tunnel, and environment discovery concurrently; WSL uses two parallel probes, while additional tunnel-name lookups are sequential in the existing node implementation.
- Cache behavior: Initial rows use cached SSH/storage, WSL, tunnel, environment, and extension state. Hover attribution only reads existing configured entries. Extension rows do not invalidate or bypass remote-discovery caches.
- Mechanism confidence: High: inspected changed model/widget/picker paths and existing discovery implementations; added attribution does not alter remote operation counts.
- Magnitude uncertainty: Existing discovery latency and visible collection size depend on user configuration. Added strings and rows do not independently establish a harmful rendering or boundary mechanism.
- Expensive boundaries:
