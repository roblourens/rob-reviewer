**Relevant issue families:** serialization-allocation, repeated-work, boundary-fanout

### Scenario 1: Windows CI browser integration suites running Firefox against the packaged web server

- Critical path: Each of the seven sequential suite invocations spawns one server, waits for the Web UI readiness line, launches one Firefox process, navigates to localhost, and loads test assets. The changed DNS preference is applied before Firefox launch and therefore affects the critical-path navigation and later fresh localhost connections.
- Scaling input: Seven sequential suite invocations; within each suite, the number of fresh localhost connections after browser connection reuse. The new stdout buffer scales with bytes emitted before the single readiness line, not with test count after startup.
- Effective concurrency: The Windows test script runs suite invocations sequentially. Within an invocation there is one server and one browser; Playwright/Firefox may issue asset requests concurrently, but the diff adds no concurrency or fan-out.
- Cache behavior: Every suite launches a fresh Firefox process and temporary server data directory, so DNS/profile and HTTP cache state do not carry across suites. The parsed family is per-launch and has no persistent cache or negative-cache lifecycle.
- Mechanism confidence: High: the code parses the server's actual IPv4/IPv6 listener family before launch and passes the matching Firefox preference; authoritative server code emits that family before the readiness URL.
- Magnitude uncertainty: Exact connection reuse and OS refusal latency vary by Firefox and Windows version, but the changed routing mechanism is clear. Startup stdout volume varies in source runs; repository paths show packaged CI startup is small, and there is no evidence that temporary buffering is materially costly.
- Expensive boundaries:

- Verdict: No reportable regression. The change removes wrong-family connection attempts on the affected Firefox path and adds only bounded, startup-only parsing work.

### Scenario 2: Chromium/WebKit runs and Firefox runs where the server binds IPv4, including local source-server execution

- Critical path: The runner starts the server, collects output through the readiness URL, launches the selected browser, and navigates to localhost. For non-Firefox browsers the new preference is undefined; for IPv4 Firefox it is false, matching the normal IPv4-first behavior.
- Scaling input: Bytes emitted by prelaunch/server startup before the readiness line, and seven independent suite launches in a full run. The retained buffer resets for every suite and is discarded at readiness.
- Effective concurrency: Suite processes are sequential in the provided scripts; browser resource requests may be concurrent but the diff neither increases their count nor removes backpressure.
- Cache behavior: Prelaunch checks use existing node\_modules/out/Electron artifacts as warm-state gates; missing artifacts can trigger cold installs/downloads/compile, but those are pre-existing operations. Browser/server state is fresh per suite.
- Mechanism confidence: High for the temporary allocation mechanism and unchanged browser paths; low for any meaningful adverse magnitude, so no issue is reported.
- Magnitude uncertainty: A pathological cold source setup could emit more stdout and make concatenation cost grow, but the data remains startup-scoped and repository evidence does not establish a realistic material regression; this is insufficient for a finding.
- Expensive boundaries:
  - subprocess at <code>test/integration/browser/src/index.ts:224 and scripts/code-server.sh:14 / scripts/code-server.bat:15</code>: Run scripts/code-server and, in source mode, its prelaunch checks before starting the Node server; cardinality: One server process per suite invocation; source mode may invoke prelaunch checks once per invocation, while packaged CI bypasses this script via VSCODE\_REMOTE\_SERVER\_PATH.
    - Introduced by diff: false; previous behavior: Identical source-server and prelaunch subprocess behavior; stdout was scanned one chunk at a time.; critical-path effect: All source prelaunch output and server initialization precede readiness. The diff observes this existing stdout but does not add subprocesses or filesystem/network work.
  - network at <code>test/integration/browser/src/index.ts:152</code>: Load the localhost workbench and integration-test resources; cardinality: One page navigation and its resource graph per suite, with browser-managed request concurrency and caching within that browser process.
    - Introduced by diff: false; previous behavior: The same browser requests and retry policy occurred.; critical-path effect: Required resources block test progress. The diff leaves address-family behavior unchanged for Chromium/WebKit and effectively unchanged for IPv4-bound Firefox.
  - serialization at <code>test/integration/browser/src/index.ts:282-293</code>: Accumulate stdout across chunks until readiness so both server-address and URL lines can be parsed; cardinality: One buffer per launch, released before tests begin; source prelaunch output can make it larger than packaged-server output.
    - Introduced by diff: true; previous behavior: No cross-chunk accumulation; only the current chunk was converted and searched.; critical-path effect: Adds allocation and repeated string concatenation during startup, but normal scripts only run prelaunch checks/downloads when dependencies or build outputs are missing, and no concrete material startup or memory regression is established.
- Verdict: No reportable regression. Non-Firefox behavior is unchanged, IPv4 Firefox retains its default preference, and temporary stdout retention is not evidenced as materially harmful.
