# Performance review: Monaco: bundle the &#64;vscode/diff TypeScript backend in the editor worker

[PR #348527](https://github.com/microsoft/vscode/pull/348527) at `079cb17653376b876323e3b10d0779463c1e5b68`

## Findings (1)

### 1. [medium] Defer the bundled diff backend until an external algorithm is selected

**Finding ID:** `PERF-C4BFD4CC6C14`  
**Location:** <code>src/vs/editor/standalone/common/bundledDiffComputer.ts:6</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** JavaScript bytes for the \`&#64;vscode/diff/core\` import graph plus browser parse/evaluation CPU and the eagerly created diff-computer object  
**Scaling:** The cost is paid once per Monaco editor-worker creation rather than once per external-diff use; cold loads additionally transfer the package bytes, and workers recreated after the five-minute idle shutdown repeat parse/evaluation regardless of whether any external diff is ever requested.  
**Outcome:** blocked worker startup and increased first-interaction latency, with repeated parse/evaluation CPU after idle worker recreation  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, the Monaco worker entries loaded only the built-in editor worker. \`&#64;vscode/diff\` was requested lazily by \`getExternalLinesDiffComputer()\` only when \`advanced-external\` or \`advanced-wasm\` was selected, so routine worker features and the default \`advanced\` algorithm did not carry this package on their startup path.  
**Changed behavior:** Every Monaco editor worker now includes, loads, parses, evaluates, and instantiates the \`&#64;vscode/diff\` TypeScript backend at worker startup, before any external diff algorithm is requested.  
**Confidence:** 0.97 — The static import and top-level constructor call are direct changed-code evidence. The worker entries import this module unconditionally, while \`editorWorkerService.ts\` shows the same worker is created for ordinary links, Unicode highlighting, colors, word ranges, and default word completions. \`diffEditorDefaultOptions\` remains \`advanced\`, and \`linesDiffComputers.ts\` reaches this package only for the opt-in \`advanced-external\`/\`advanced-wasm\` algorithms. Exact added byte and millisecond cost depends on each consumer's bundler and browser, which affects severity but not the mechanism.

**Causal diff evidence:** The added static import \`import { createTsDiffComputer } from '&#64;vscode/diff/core';\` at line 6 is reached unconditionally because both Monaco worker entry points newly import \`bundledDiffComputer.ts\`; line 11 also constructs and registers the backend during module evaluation.

A standalone editor's first worker-backed interaction—commonly word completion, link computation, highlighting, or a default \`advanced\` diff—must wait for additional JavaScript download on a cold cache and additional parse/evaluation/initialization on every worker creation, increasing interaction latency even for applications that never opt into the package algorithms.

**Evidence:** \`editor.worker.start.ts:7\` and \`standaloneEditorWebWorkerMain.ts:7\` unconditionally import this module. \`EditorWorkerService.workerDescriptor\` selects the new standalone entry for bundlers, and \`WorkerManager.withWorker()\` creates that worker on first use. Ordinary hot interactions such as \`WordBasedCompletionItemProvider.provideCompletionItems()\` call \`withWorker()\`, so the optional backend is on their startup critical path. The worker is also disposed after five idle minutes, making parse/evaluation recur on later worker recreation even when browser caching avoids another transfer. The package was previously loaded only from \`getExternalLinesDiffComputer()\` after an external algorithm was selected; ordinary worker startup did not import it.

**Suggested direction:** Register a lazy bundled provider from the worker entry and dynamically import \`&#64;vscode/diff/core\` inside it on the first \`advanced-external\`/\`advanced-wasm\` request, caching that promise/computer. This lets bundlers emit the backend as an on-demand worker chunk while preserving one-time initialization and fallback semantics.
