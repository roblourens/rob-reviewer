# Performance review: \[Perf\] arrays: adjust duplicate tracking (reviewer test)

## Findings (1)

### 1. [medium] Restore Set-based membership checks in distinct

**Finding ID:** `PERF-16ADB1E81A57`  
**Location:** <code>src/vs/base/common/arrays.ts:406</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work scanning and comparing previously seen keys.  
**Scaling:** For n inputs and u unique keys, membership costs O(n\*u); all-unique inputs require n\*(n-1)/2 comparisons instead of expected O(n) total membership work. Settings filters run this over the full settings collection before filtering, not merely the visible matches.  
**Outcome:** Increased synchronous CPU time blocks the renderer event loop and delays settings/keybinding results.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** distinct retained keys in a local Set, using seen.has and seen.add for expected O(n) duplicate tracking with O(u) transient storage.  
**Changed behavior:** distinct now linearly scans accumulated unique keys for every input element, turning expected O(n) duplicate tracking into O(n\*u), quadratic when most keys are unique.  
**Confidence:** 0.99 — The changed membership operation and growing collection directly establish the complexity change. Traced production callers process complete settings and command collections synchronously before rendering; actual collection sizes and elapsed time are not measured.

**Causal diff evidence:** At arrays.ts:406 the diff replaces seen.has(key) with seen.includes(key), while lines 402 and 409 replace the Set with a growing array and push. Consequently each new unique key scans every previously accepted key rather than performing a hash lookup.

Filtering Settings with &#64;modified or a broad search, and opening/rebuilding Keyboard Shortcuts, now perform quadratic duplicate checks on potentially thousands of mostly unique setting or command keys on the renderer thread, delaying results and blocking UI responsiveness even when the visible filtered result is small.

**Evidence:** SettingsEditor2.createFilterModel (settingsEditor2.ts:1979-2005) collects every default/extension setting for filter-only queries such as &#64;modified. setResult -&gt; updateChildren -&gt; getUniqueSearchResults -&gt; sortResults reaches arrays.distinct at settingsTreeModels.ts:1113 before the tag/scope filters at 1196-1202 reduce the displayed set. The result cache is cleared by each setResult. KeybindingsEditorModel.resolve likewise deduplicates all bound and unbound commands at keybindingsEditorModel.ts:211-226, and keybindingsEditor.ts:565-566 awaits it before rendering. For n distinct keys the new implementation examines n\*(n-1)/2 prior entries; the removed Set implementation did expected constant-time membership per key.

**Suggested direction:** Keep Set-based membership tracking (a Set&lt;unknown&gt; preserves the intended typing); retain the existing filter order and keyFn invocation semantics.

### Scenario 3: Refresh extension-contributed tree views after a batch of change events.

- Critical path: The 200ms event debounce combines elements, then synchronously invokes distinct before enqueuing \_refresh. \_refresh checks root invalidation or suppresses descendants, refreshes surviving nodes, and submits a grouped refresh to the main thread.
- Scaling input: m element references accumulated in a debounced batch and u unique references govern the new O(m\*u) scan. Subsequent ancestor/root suppression may reduce downstream work to h handles or a single root refresh, but occurs after distinct.
- Effective concurrency: Refresh work is chained per tree through \_refreshQueue. Within a batch, \_refreshHandles uses Promise.all for h provider getTreeItem callbacks, followed by one grouped IPC. The newly slower synchronous distinct runs before that queue step.
- Cache behavior: Every distinct call has a fresh local seen collection. Existing tree-node caches map references to handles; refresh clears affected child caches. Neither the debounce nor node caching avoids scanning unique references in a new batch.
- Mechanism confidence: High: constructor debounce and distinct at 409-437, queue chaining, and \_refresh/\_refreshHandles at 801-860 establish ordering and effective grouping.
- Magnitude uncertainty: Extensions determine batch sizes and provider callback work; those callbacks may do their own I/O, but no particular external I/O implementation is assumed. The PR adds CPU work, not additional refresh IPCs or callbacks.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/common/extHostTreeViews.ts:\_refresh and \_refreshHandles, lines 801-860</code>: Send a root invalidation or grouped changed tree-item payload to the main thread.; cardinality: At most one $refresh IPC for a batch: one for a root refresh, or one containing refreshed items when the surviving handle refreshes produce items; none if no handles/items remain.
    - Introduced by diff: false; previous behavior: The same debounce, ancestor grouping, Promise.all callbacks, payload cardinality, and single grouped IPC followed expected-linear Set-based element deduplication.; critical-path effect: Tree-view UI refresh cannot be sent until synchronous deduplication and any required node-refresh callbacks finish.
- Verdict: Additional exposure of the same shared-helper CPU regression, not boundary fan-out or a new concurrency burst. No separate finding.

- Mechanism confidence: High: wordHighlighter.ts:46-88 directly ties Promise.all results to distinct, and 675-795 connects requests to rendering and documents the existing cache/early-return behavior.

### Scenario 5: Resolve language-specific configuration values from already loaded configuration models.

- Critical path: Configuration.getValue consolidates workspace/folder models, then override(identifier) may create an override model. Creation deduplicates base and override top-level keys; configuration merges may also deduplicate language-specific key lists before returning the requested value.

- Cache behavior: Workspace consolidation is cached, folder consolidation is cached by folder URI, and override configurations are cached per identifier on each ConfigurationModel. Warm reads generally avoid rebuilding the affected collections; new models or new identifiers incur cold work.

- Expensive boundaries: none found
- Verdict: The same membership complexity worsens cold model creation, but warm caches limit repeated work. No independent finding or claim that all configuration reads now scan every setting.
