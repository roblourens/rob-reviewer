### Scenario 1: Open, restore, or switch an integrated-browser editor, with empty or populated recent history.

- Critical path: setInput resolves the browser model, initializes navigation state, refreshes the recent list synchronously, lays out the editor, and awaits browser visibility. The new list work precedes completion of setInput; periodic screenshots remain off that initialization path.
- Scaling input: History written by this implementation contains at most 10 distinct URLs. Each input initially displays at most 3 rows. One BrowserEditor pane is reused for different tabs within an editor group; inactive tabs are not independent recent-list renderers.
- Effective concurrency: The additional history read, list construction, and row updates are synchronous renderer work. Existing asynchronous model initialization and visibility operations retain their previous scheduling; the diff adds no collection-wide IPC fan-out.
- Cache behavior: History reads use the existing initialized workspace-storage memory map, including a cheap missing-key result; JSON is reparsed on refresh. BrowserEditorInput caches its model and in-flight resolution, and the workbench/main-process services reuse models/views by ID. Recent lists are recreated on input replacement, with old input resources cleared.
- Mechanism confidence: High confidence in the traced initialization path, memory-backed storage reads, 10-entry write cap, 3-row initial display, and unchanged native-browser boundaries.
- Magnitude uncertainty: No timings are supplied for constructing the bounded list; URL lengths and number of simultaneously instantiated editor groups vary.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/browserView/common/browserView.ts: BrowserViewModel.initialize, layout, setVisible</code>: Resolve or create the native browser view, position it, and update visibility through IBrowserViewService.; cardinality: Existing model/view initialization per uncached browser ID; layout and visibility calls per editor initialization or visibility change, not per recent URL.

  - IPC at <code>src/vs/workbench/contrib/browserView/electron-browser/browserEditor.ts: capturePlaceholderSnapshot</code>: Capture the native browser screenshot and encode the returned buffer for the placeholder.; cardinality: Existing one-second interval per pane with a resolved input, subject to the existing model/overlay checks.
    - Introduced by diff: false; previous behavior: The screenshot interval, capture operation, and base64 conversion are unchanged.; critical-path effect: Runs periodically after input setup, not as part of the added history refresh.
- Verdict: No actionable regression established. The added UI construction is bounded and does not add native-view or storage-read boundary calls per history entry.

### Scenario 2: Navigate from the address bar or a recent URL, including redirects and modifier-click background opening.

- Critical path: Normal navigation issues one browser loadURL request. Its navigation event now updates recent history and synchronously refreshes subscribed pane lists. Saving history does not await persistence. Modifier-click opens one browser editor through the existing resolver, which starts resolving its model in the background.
- Scaling input: At most 10 stored entries; one history addition per pending user navigation, plus a removal if a different original URL actually exists in history. Refresh fan-out is to subscribed BrowserEditor panes/editor groups, not all browser tabs or all URLs.
- Effective concurrency: History mutations and event delivery are synchronous. Each mutation refreshes subscribed panes serially. Storage uses a 100 ms ThrottledDelayer and pending-key maps; remove/add within one redirect handler normally coalesce into one persistence batch. The diff adds no concurrent load for each history item.
- Cache behavior: Successful history additions deduplicate by exact URL before truncating to 10. Redirect removal misses do not write or emit. Workspace storage serves reads from memory, deduplicates unchanged values, and coalesces pending writes by key. Empty history requires no disk lookup on refresh.
- Mechanism confidence: High confidence in call counts, event fan-out granularity, capped history size, and deferred/coalesced storage persistence.
- Magnitude uncertainty: Exact URL byte lengths, navigation frequency, and number of subscribed editor-group panes vary; no measurements establish problematic cost at the bounded entry count.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/browserView/common/browserView.ts: BrowserViewModel.loadURL; src/vs/platform/browserView/electron-main/browserView.ts: loadURL</code>: Forward the selected URL to Electron webContents.loadURL.; cardinality: One loadURL operation per explicit navigation or newly opened recent-URL editor, not one per stored entry.

    - Introduced by diff: false; previous behavior: Navigating to the same URL through the address bar or existing editor-opening path performed the same network work.; critical-path effect: Document navigation and page loading determine navigation completion.

One save for addition and, only on a successful redirect removal, one preceding save; each subscribed pane reparses on its refresh.
    - Introduced by diff: true; previous behavior: There was no recent-URL serialization or history-driven list refresh.; critical-path effect: Small synchronous renderer work in navigation-event handling; it does not wait for disk.

### Scenario 3: Expand/collapse recent URLs, remove entries, clear workspace history, and replace or close the browser input.

- Critical path: Expand/collapse refreshes the local list and restores focus. Removal/clear mutates memory-backed storage and synchronously refreshes subscribed panes; persistence is deferred. Input replacement/clear disposes input-owned widgets and subscriptions.
- Scaling input: Collapsed view contains at most 3 entries; expanded history contains at most 10, with a 300 px virtual-list viewport. Each explicit remove or clear emits at most one history-change event. Repeated clear/repopulate cycles are confined to the current input's ownership lifetime.
- Effective concurrency: List updates and disposal run synchronously, with no background operation per row. Storage updates use the same throttled, key-coalesced persistence path as navigation.
- Cache behavior: Remove misses cause no save/event. Clear removes the existing workspace key. List templates are reused during splice operations; empty history disposes the active list, and input replacement clears its owning DisposableStore. Toggle Link instances are reused while the input remains attached.
- Mechanism confidence: High confidence in row caps, synchronous refresh, deferred persistence, and input-level cleanup; insufficient evidence of a concrete user-visible performance problem from the disposed-shell edge case.
- Magnitude uncertainty: Repeated clear/repopulate cycles can retain disposed widget shells in the input's DisposableStore until input replacement, but no material high-frequency or substantial-growth scenario was established. Normal row counts and active listeners remain small.
- Expensive boundaries:
  - IPC/database at <code>src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts: removeRecentUrl/clearRecentUrls; src/vs/base/parts/storage/common/storage.ts: Storage.delete/flushPending</code>: Persist the final history value or key deletion through existing batched workspace storage.; cardinality: At most one recent-history key mutation per successful remove/clear; target-marker changes share the storage flush. Expansion/collapse performs zero persistence calls.
    - Introduced by diff: true; previous behavior: These recent-history interactions and their storage mutations did not exist.; critical-path effect: No persistence await blocks list interaction; only the capped synchronous refresh is on the interaction path.
- Verdict: No actionable performance finding. Normal interaction work is bounded and virtualized; the inspected cleanup paths do not establish significant long-lived resource growth in the realistic workflows.

### Scenario 4: Open Recent URLs Settings from the new overflow menu.

- Critical path: The action calls preferencesService.openSettings with an exact setting-ID query, which selects the existing Settings UI path and opens its editor.
- Scaling input: One explicit menu invocation and one setting-ID query, independent of recent-history length.
- Effective concurrency: One awaited preferences-editor open per action; no new loop, queue, or parallel request burst.
- Cache behavior: PreferencesService.openSettings2 reuses its cached settings-editor input. The history array is not read, serialized, or traversed by this action.
- Mechanism confidence: High confidence from tracing the action through openSettings/open/openSettings2 to cached input and group.openEditor; no direct subprocess, IPC, filesystem, database, or network operation is added by the menu/query plumbing.
- Magnitude uncertainty: Cold Settings UI initialization cost is subsystem-dependent, but the diff introduces only an explicit user-requested entry point with no added multiplicity.
- Expensive boundaries: none found
- Verdict: No performance regression established. This is a demand-driven invocation of the existing settings editor, not eager initialization or repeated work.
