### Scenario 1: First TypeScript 7 feature use and initial context-provider registration

- Critical path: Registration awaits extension activation and isActivated(), which awaits the shared API connection. Connection establishment awaits subscription, SDK pipe initialization, and API.fromLSPConnection. Construction alone does not connect.
- Scaling input: Up to three fixed extension IDs, stopping at the first event-providing extension; all four native-API consumer types share one connection rather than connecting per document or consumer.
- Effective concurrency: Extension activation is sequential within discovery; one connection-creation promise is shared globally. At most three sequential connection attempts handle generation changes, preserving the existing attempt bound.
- Cache behavior: Concurrent getApi calls share apiPromise; successful connections are cached. Subscription is cached independently. A subscribed server with an absent or unsupported SDK returns undefined without pipe initialization. If no extension exposes an API, later calls rescan the bounded extension list; retrying discovery after an unsuccessful attempt also existed before.
- Mechanism confidence: High: connection sharing, promise coalescing, fixed extension inventory, version gating, and retry bounds are explicit in the implementation and covered by the added connection tests.
- Magnitude uncertainty: External extension activation and pipe setup durations are not available in the repository. No input-dependent increase beyond the intentional fixed fallback is established.
- Expensive boundaries:
  - other at <code>extensions/copilot/src/extension/typescriptContext/vscode-node/ts7/ts7Api.ts: subscribe</code>: Activate candidate TypeScript extensions through the extension API.; cardinality: At most three activation calls during a discovery pass, stopping at the first usable extension API; no repeated activation after subscription succeeds.

- Verdict: No actionable performance regression: lazy shared connection creation and bounded sequential discovery remain intact.

### Scenario 2: Late language-server initialization, server restart, and provider re-registration

- Critical path: Initialization updates the SDK, resets the connection, clears context state, and queues checkRegistration. Registration waits for a shared replacement connection before replacing registrations. This runs on server initialization, not on each edit or context item.
- Scaling input: One event subscription per shared connection and one activation-forwarding chain for the context service; work scales with actual server initialization events, not open files or symbols.
- Effective concurrency: The registration Queue has parallelism one. Connection creation is separately coalesced through apiPromise. Old provider registrations are disposed before replacements, and service event listeners are cleared on service replacement.
- Cache behavior: Each server initialization invalidates the API and runnable cache intentionally. An SDK replay during initial subscription does not emit a reconnect notification. Existing pending connection work remains coalesced.
- Mechanism confidence: High: the event path, queue implementation, registry cleanup, and extension-host registration IPC were traced directly.
- Magnitude uncertainty: Restart frequency and external activation durations are unknown. There is no evidence of an event feedback loop, per-file fan-out, or accumulating registrations.
- Expensive boundaries:

### Scenario 3: Typing, cursor selection, cache population, and inline completion context resolution

- Critical path: Existing selection/completion triggers populate context asynchronously. Population obtains the shared API, creates a snapshot, reads the project/source, computes context, and disposes the snapshot. Completion resolution primarily yields cached results and can race in-flight population for at most 20 ms.
- Scaling input: Active-document selection/completion events and requested context size; not all workspace documents. One in-flight population request plus the latest pending request is retained.
- Effective concurrency: Existing throttled selection handling and in-flight population suppression remain. All feature callers coalesce connection creation; completed-context reads do not create independent connections.
- Cache behavior: Warm API calls do not reconnect. Runnable-result cache use is unchanged. With a subscribed unsupported or not-yet-initialized SDK, getApi does no pipe work. Failed connection attempts can be retried on later calls, as before.
- Mechanism confidence: High: population triggers, cancellation, pending-request handling, and cached completion consumption are explicit in the surrounding code.
- Magnitude uncertainty: Actual native-query duration depends on project size, but this diff does not increase steady-state query cardinality or change budgets.
- Expensive boundaries:
  - IPC at <code>extensions/copilot/src/extension/typescriptContext/vscode-node/ts7/tsContextService.ts: computeContext</code>: Create a native snapshot, obtain the default project and source file, perform native context queries, and dispose the snapshot.; cardinality: One snapshot lifecycle per actual population request, with query count controlled by existing context computation and budgets. - Verdict: No steady-state hot-path regression: changed connection handling preserves caching and request coalescing.

### Scenario 5: Switching TypeScript versions or disabling support, then disposing services

- Critical path: Configuration changes dispose the previous language-context service and rebind listeners. Disposing the last native-API handle closes the shared connection; closing is asynchronous.
- Scaling input: Configuration transitions and a fixed set of service handles, rather than document history or workspace size.
- Effective concurrency: Existing ref counting owns connection lifetime. New event emitters and subscriptions are owned by DisposableStores; no additional background task or unbounded retained collection is added.
- Cache behavior: The shared connection persists only while reference-counted handles remain. Subscription disposal removes the server listener; serviceListeners.clear removes forwarded listeners before replacement.
- Mechanism confidence: High: ownership of each added emitter and listener is explicit and replacement clears the old forwarding store.
- Magnitude uncertainty: No measured retained sizes are available, but no lost disposal owner or growing collection is present in the changed code.
- Expensive boundaries:
  - IPC at <code>extensions/copilot/src/extension/typescriptContext/vscode-node/ts7/ts7Api.ts: TypeScript7Api.dispose and TypeScript7Connection.dispose</code>: Close the shared native API connection when its final handle is disposed.; cardinality: One close for the cached connection when the last handle is removed; no close per document or per remaining handle.
    - Introduced by diff: false; previous behavior: The same reference-counted disposal and asynchronous close mechanism existed before this PR.; critical-path effect: Cleanup is initiated without awaiting API.close.
- Verdict: No cleanup or retention regression found.
