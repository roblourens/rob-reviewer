## Findings (1)

### 1. [low] Remove disposed recent-URL lists from their owning store

**Finding ID:** `PERF-0EA8F6ED6AEA`  
**Location:** <code>src/vs/workbench/contrib/browserView/electron-browser/browserEditor.ts:836</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Disposed List/ListView objects and their detached DOM subtrees retained by \_inputDisposables.  
**Scaling:** One additional retained widget per empty-to-nonempty history cycle per subscribed browser pane that keeps the same input; the ten-URL cap does not bound the number of retained widgets.  
**Outcome:** Renderer memory grows across history-reset cycles until the affected pane switches or clears its input.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR browser panes had no recent-URL List widgets or history-change subscriptions, so history resets could not accumulate these objects.  
**Changed behavior:** Recent-history empty/nonempty transitions now dispose and recreate List widgets while keeping every disposed widget registered in the input-lifetime DisposableStore.  
**Confidence:** 0.99 — DisposableStore.add retains objects in \_toDispose until clear/delete (lifecycle.ts:420, 453-462, 471-488). List.dispose delegates to ListView.dispose, which removes domNode but leaves its reference on the retained view (listWidget.ts:2013-2017; listView.ts:1679-1698). The recreation and ownership paths are explicit; only the frequency of repeated history resets is uncertain.

**Causal diff evidence:** The added empty-history branch at browserEditor.ts:836 disposes the List and :837 drops \_recentUrls.list, but added :859 registers every replacement List in \_inputDisposables. Nothing removes the old List from that store before registering its replacement.

Repeatedly clearing/removing the last recent URL and recording another URL while a browser pane keeps the same input—for example, clearing history from a welcome page in another editor group—accumulates detached list widgets and increases renderer memory usage despite the ten-entry history limit.

**Evidence:** refreshRecentUrlsList disposes and forgets the current list when history becomes empty (:834-838), then creates a replacement via \_inputDisposables.add(new List(...)) on the next history addition (:851-873). The service broadcasts both clear/remove and add events to all bound browser panes (:474-476; browserViewWorkbenchService.ts:99-100, 128-139), including panes whose welcome screen is hidden. The input store still strongly retains the disposed List, its view, and its detached DOM subtree until setInput/clearInput clears the store.

**Suggested direction:** Use a replaceable owner for the current list and its selection subscription, releasing the previous owner when history becomes empty, or keep and reuse one hidden list until input cleanup.

### Scenario 3: Expand/collapse history, remove entries, clear history, and repopulate it while another browser pane keeps the same input.

- Critical path: Expansion synchronously splices/layouts the bounded list. Remove/clear updates cached workspace storage and synchronously broadcasts refreshes. An empty history disposes the current list; a subsequent recorded URL creates a replacement. Switching/clearing input eventually releases the input-lifetime store.
- Scaling input: At most ten current history entries, three collapsed rows, and a 300px expanded viewport. Retained widgets instead scale with the number C of empty/nonempty cycles times the number P of subscribed panes that keep the same input.
- Effective concurrency: Each history mutation synchronously refreshes all subscribed panes, including hidden welcome screens. No parallel subprocess or network burst is created. Multiple groups make it possible to clear history in a welcome pane while loaded browser panes remain bound.
- Cache behavior: Empty history is a cheap cached missing-key result. Nonempty history is reparsed from cached storage. The current list reference is cleared on empty history, but the owning DisposableStore still retains the disposed List; there is no replacement eviction until input cleanup.
- Mechanism confidence: Very high: new lists are registered in \_inputDisposables; empty history calls dispose without deleting that registration; ListView.dispose detaches but retains its domNode reference. The next addition registers a distinct replacement.
- Magnitude uncertainty: Repeated clears/removal of the final item is less frequent than ordinary navigation, and exact retained bytes per widget are unmeasured. This limits severity, not confidence in retention.
- Expensive boundaries:
  - database at <code>src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts:removeRecentUrl, clearRecentUrls; src/vs/base/parts/storage/common/storage.ts:delete, doFlush</code>: Persist recent-history removal through the existing deferred storage IPC/database pipeline.; cardinality: At most one changed history key plus its target marker per clear/remove, coalesced with subsequent changes; no persistence operation for expansion/collapse.
    - Introduced by diff: true; previous behavior: There was no recent-history removal or persistence path.; critical-path effect: Storage deletion/update is scheduled asynchronously; list disposal and rendering are synchronous.
- Verdict: Reported one low-severity cleanup-lifecycle memory regression: each reset/repopulate cycle retains another disposed list and detached subtree until input cleanup. Normal row count and persistence remain bounded.
