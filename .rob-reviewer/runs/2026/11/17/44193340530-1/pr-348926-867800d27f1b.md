# Performance review: \[Perf\] collections: simplify group accumulation (reviewer test)

[PR #348926](https://github.com/microsoft/vscode/pull/348926) at `867800d27f1b734c551ab5e88a4e622d23ed5692`

## Findings (1)

### 1. [medium] Restore in-place bucket accumulation to keep grouping linear

**Finding ID:** `PERF-A3D06A78144C`  
**Location:** <code>src/vs/base/common/collections.ts:26</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Copied array references and short-lived bucket arrays.  
**Scaling:** For a bucket of k distinct input items, k insertions now copy k(k-1)/2 prior references instead of k amortized-constant-time appends. Across groups the cost is proportional to sum(k\_g^2), not the number of groups or subprocesses. In changed-file search the effective k is the unique changed-file include count within each workspace root.  
**Outcome:** Increased search startup latency and CPU/GC pressure; renderer callers can also block UI rendering for large buckets.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A result bucket was created only for a new key and then mutated with push, yielding amortized linear grouping work and one growing bucket array per key.  
**Changed behavior:** Each insertion allocates a replacement bucket and copies every previously grouped value, changing total grouping work from amortized O(N) to O(N + sum(k\_g^2)) for bucket sizes k\_g.  
**Confidence:** 1.00 — The quadratic prefix copying follows directly from the changed loop. A concrete scaling caller is traced from SearchView's changed-file URI list through QueryBuilder.commonQueryFromFileList and TextSearchManager.getSearchOptionsForFolder to ripgrep argument construction. These deduplicate paths but retain one include per distinct changed file; ordinary relative paths all enter the same bucket. Duration is not measured.

**Causal diff evidence:** The deleted code allocated a bucket once and used target.push(element). Added collections.ts:26 instead spreads the entire existing result\[key\] into a fresh array on every element, introducing repeated prefix copies.

Searching only changed files in a large change set now performs quadratic CPU work and generates transient arrays before ripgrep starts, delaying the first search result and increasing GC pressure. Warm model/module caches do not avoid this grouping.

**Evidence:** SearchView (searchView.ts:1654-1675) supplies SCM changed-file URIs. QueryBuilder.commonQueryFromFileList (queryBuilder.ts:280-304) produces one unique include pattern per file within a workspace root. TextSearchManager (textSearchManager.ts:205-226) passes those patterns to the provider. pushIncludeAndExcludeGlobs (ripgrepTextSearchEngine.ts:612-615) groups them into just two categories before getRgArgs returns and cp.spawn runs (:122-135). Thousands of distinct relative file paths therefore produce a thousands-element otherIncludes bucket and quadratic synchronous copying before the existing one-process-per-folder search can start. The same helper also runs synchronously in SCM badge rendering (scmHistoryViewPane.ts:532,545).

**Suggested direction:** Restore one-time bucket initialization followed by in-place push, preserving both group membership and order without repeatedly cloning prefixes.
