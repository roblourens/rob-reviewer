### Scenario 1: Successful Windows Chromium web smoke suite, including workbench restoration and normal teardown

- Critical path: Application.start awaits server startup, browser launch, navigation, workbench DOM readiness, and the existing restoration RPC. Network logging runs during the browser lifetime. On stop, driver.close closes the browser, deletes the raw log, and tears down the server; Code.exit polls for server termination rather than directly awaiting driver.close.
- Scaling input: One browser and raw log per suite/application launch, not one per module request. Event production scales with network activity; the launch requests a 200 MB log limit. The source comment estimates about 80 MB per workbench load, but this was not independently measured.
- Effective concurrency: The inspected suite hooks await application startup and shutdown. Logging is browser-owned; normal teardown does not start compression. No new per-request subprocess or Playwright RPC fan-out is introduced.
- Cache behavior: Every browser launch has a PID/counter-specific log path and a fresh restoration boolean. Logging is not skipped for warm network caches, although reduced network activity can reduce events. Successful restoration causes deletion without reading or gzipping the log.
- Mechanism confidence: High confidence in the platform gate, one-log-per-browser ownership, unchanged RPC/request multiplicity, success-path deletion, and configured size limit, directly from the changed code and callers.
- Magnitude uncertainty: Actual NetLog generation rate, Chromium limit implementation, disk throughput, and startup overhead are not measured by the supplied repository evidence.
- Expensive boundaries:

### Scenario 2: Navigation succeeds but the workbench never restores; suite teardown preserves diagnostics

- Critical path: Application.checkWindowReady fails before successful restoration. The registered Code instance is stopped by the suite after hook. Driver.close performs existing client-log extraction and browser close, then awaits NetLog compression/removal before terminating the server. Code.exit retains its existing server polling and force-kill fallback.
- Scaling input: One retained log per failed browser startup, not per refused request or readiness polling attempt. Compression work scales with the closed browser's raw log size, configured to at most 200 MB.
- Effective concurrency: One backpressured read-to-gzip-to-write pipeline per failed browser. The pipeline is awaited within driver.close; there is no Promise.all over network events or log chunks. Existing Code.exit can force server termination after roughly ten seconds independently of completion of close.
- Cache behavior: No shared cache or retained map is introduced. A false restoration boolean selects preservation; normal helper completion or stream failure runs raw-file removal in finally. Repeated launches receive different raw paths.
- Mechanism confidence: High confidence that preservation is once per failed browser and compression is streamed, failure-only, and ordered after browser close. Its placement before server teardown is explicit.
- Magnitude uncertainty: Failure frequency, compression duration, compressed size, and interaction with unusually slow storage are unmeasured.
- Expensive boundaries:
  - IPC at <code>test/automation/src/playwrightDriver.ts:close</code>: Extract existing web client logs and close Chromium before consuming its network log.; cardinality: Same existing teardown calls once per driver close.
    - Introduced by diff: false; previous behavior: The same calls were followed directly by server teardown.; critical-path effect: They precede the newly added compression step.
  - filesystem/serialization at <code>test/automation/src/playwrightDriver.ts:1104-1116 saveOrDeleteNetLog</code>: Create the suite log directory, stream the raw NetLog through gzip to chromium-netlog.json.gz, and delete the raw file.; cardinality: One directory creation, streaming input/output pair, and removal per failed browser; O(raw log bytes) compression with stream backpressure rather than whole-file buffering.
    - Introduced by diff: true; previous behavior: No network-log read, gzip work, artifact write, or deletion occurred.; critical-path effect: Runs after Chromium closes and before the normal server teardown; it does not block a successful workbench becoming usable.
  - subprocess at <code>test/automation/src/playwrightDriver.ts:close; test/automation/src/code.ts:exit; test/automation/src/processes.ts:teardown</code>: Terminate the server with existing tree-kill logic and existing forced-exit fallback.; cardinality: Normal teardown plus the pre-existing fallback if shutdown exceeds its threshold; no new subprocess loop is added.
    - Introduced by diff: false; previous behavior: Normal server termination followed browser close without NetLog processing; the same timeout fallback existed.; critical-path effect: Normal termination now follows diagnostic compression; existing Code.exit can terminate the server independently.
- Verdict: No reportable regression beyond the intended failure-diagnostic cost. There is no evidence of unbounded in-memory buffering, per-event compression, uncontrolled concurrency, or newly introduced persistent resource loss. This PR adds diagnostics rather than fixing the underlying connection failure.

### Scenario 3: Windows Chromium page.goto rejects before a PlaywrightDriver is returned

- Critical path: The launchBrowser catch now awaits browser.close and preservation/removal of the NetLog, then rethrows the navigation error. No driver is constructed for this branch.
- Scaling input: One browser close and one preservation pipeline per rejected navigation. Cost scales with the events captured before failure, subject to the configured browser log limit.
- Effective concurrency: Browser closure and the single streaming gzip pipeline run sequentially. There is no retry or per-module fan-out in the added catch.
- Cache behavior: The unique raw path is consumed once and removed in the helper's finally block. This path always preserves diagnostics regardless of cache warmth.
- Mechanism confidence: High confidence in branch reachability, sequential scheduling, and bounded streaming allocation from the catch and shared helper.
- Magnitude uncertainty: The number of events preceding navigation rejection and resulting compression delay are not measured.
- Expensive boundaries:
  - IPC/subprocess at <code>test/automation/src/playwrightBrowser.ts:205-218</code>: Close the already-launched Chromium browser when navigation rejects.; cardinality: One close attempt per rejected Windows Chromium navigation.
    - Introduced by diff: true; previous behavior: The rejected navigation propagated without this local browser-close attempt.; critical-path effect: New cleanup is awaited before the original error is rethrown.
  - filesystem/serialization at <code>test/automation/src/playwrightBrowser.ts:215; test/automation/src/playwrightDriver.ts:saveOrDeleteNetLog</code>: Stream the closed browser's raw NetLog into a gzip artifact and remove the raw file.; cardinality: One pipeline and deletion per failed launch, not per failed network request.
    - Introduced by diff: true; previous behavior: There was no NetLog preservation or removal before propagating the navigation failure.; critical-path effect: Adds diagnostic time to the already-failing launch path, not the successful startup path.
- Verdict: No actionable performance finding. Added work is explicit failure cleanup and diagnostic preservation. The pre-existing server-registration gap on launch failure is not caused by this diff and is not reported.
