### Scenario 1: Agent discovers comparison-capable harnesses and models from a running or nested chat

- Critical path: The tool must acquire the exact caller configuration, resolve creation configuration for every eligible session type, then serialize the local model snapshots before returning. All of this is on the discovery call's critical path.
- Scaling input: Eligible session types and fixed models registered for the caller's Agent Host. Typical harness counts are small; calls are grouped once per session type rather than per model.
- Effective concurrency: Configuration resolution is parallel across session types; subscription acquisition is sequential over the normally short caller config chain. There is no global limiter, but fan-out is bounded by advertised session types.
- Cache behavior: Model snapshots are local registry reads. Agent subscriptions are connection-ref-counted and warm subscriptions are shared; explicit leases release immediately and hidden chat subscriptions then follow the existing 30-second idle policy. Creation-config resolution is not cached or coalesced.
- Mechanism confidence: High confidence in the IPC count and critical path from the changed code; low confidence that normal cardinality creates material latency.
- Magnitude uncertainty: Provider-specific resolve latency and unusually large harness/model registries are not measured, but expected cardinality is small and the operation is explicitly requested.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:acquireSessionConfig</code>: Acquire/ref-count the Agent Host session state and applicable chat-state configuration subscriptions.; cardinality: One session subscription plus one chat subscription for each resource in the caller's config chain; concurrent callers share connection-level subscriptions.
    - Introduced by diff: true; previous behavior: The evaluator discovery tool did not exist; visible chats could already hold these subscriptions through the provider's existing pinning path.; critical-path effect: Discovery waits until the exact caller config is available.
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:resolveSessionConfigForCreation</code>: Resolve new-session configuration for a workspace and harness.; cardinality: One call per eligible session type, issued concurrently with Promise.all; effective cardinality is the provider's filtered session-type count.
    - Introduced by diff: true; previous behavior: Manual draft creation resolved configuration through the existing provider flow; there was no agent-driven discovery call.; critical-path effect: All resolutions must finish before discovery returns because worktree support is derived from each resolved schema.
  - serialization at <code>src/vs/sessions/contrib/sessionComparison/browser/modelEvaluationTools.ts:getComparisonModels</code>: JSON-serialize fixed model IDs, labels, and configuration schemas.; cardinality: One bounded response over locally registered fixed models for each eligible harness.
    - Introduced by diff: true; previous behavior: The model picker consumed these local snapshots in-process rather than returning them as a tool result.; critical-path effect: Serialization completes before the tool result is delivered.
- Verdict: No finding: discovery introduces bounded, required capability checks and local serialization, without realistic evidence of harmful fan-out at expected harness cardinality.

### Scenario 2: Agent prepares, approves, and launches a model comparison

- Critical path: Preparation acquires caller config and resolves each distinct selected harness before showing confirmation. Invocation redoes those checks after approval, then waits for the existing comparison service to create and send all attempts.
- Scaling input: Two to ten attempts, deduplicated selected session types, plus at most one Judge and one Synthesizer configuration.
- Effective concurrency: Capability checks run concurrently per distinct type. Attempt creation runs concurrently across all requested attempts with no separate limiter, matching the existing manual comparison behavior and the explicit comparison contract.
- Cache behavior: Caller subscriptions are shared/ref-counted and disposed after each prepare/invoke phase. Capability results are intentionally re-read after approval; there is no stale result cache. Failed launch survivors are returned without creating a retry loop.
- Mechanism confidence: High confidence in the duplicate pre/post-approval capability checks and bounded parallel launch; high confidence that post-approval revalidation is intentional and that launch fan-out is pre-existing service behavior.
- Magnitude uncertainty: Worktree and provider launch duration varies by host and repository, but cardinality is explicitly user-approved and capped at ten.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/sessionComparison/browser/modelEvaluationTools.ts:creationContext</code>: Resolve creation configuration for selected harnesses during preparation and post-approval revalidation.; cardinality: One call per distinct selected session type during preparation and again during invocation; at most the distinct types represented by ten attempts plus Judge and Synthesizer.
    - Introduced by diff: true; previous behavior: The agent-driven launch did not exist. Manual comparison setup used already-resolved draft configuration; it did not cross this new tool-approval boundary.; critical-path effect: The first round precedes approval UI; the second round intentionally blocks launch to reject stale configuration.
  - filesystem at <code>src/vs/sessions/services/sessions/browser/sessionComparisonService.ts:startComparison</code>: Create isolated participant worktrees through createAndSendNewChatRequest.; cardinality: One worktree/session creation per attempt, from two through ten, launched concurrently.
    - Introduced by diff: false; previous behavior: The existing manual comparison path already used the same startComparison implementation and the same per-attempt worktree cardinality.; critical-path effect: The tool result waits for all attempt launches, but not for model completion.
  - IPC at <code>src/vs/sessions/services/sessions/browser/sessionComparisonService.ts:\_createAndSendRequest</code>: Create provider sessions and send the scenario prompt.; cardinality: One provider launch/send operation per attempt, two through ten, concurrent via Promise.all.
    - Introduced by diff: false; previous behavior: Existing manual comparisons already performed this bounded parallel launch.; critical-path effect: All launch outcomes are collected before the creation tool returns.
  - network at <code>src/vs/sessions/services/sessions/browser/sessionComparisonService.ts:startComparison</code>: Each launched provider/model processes the scenario independently after send.; cardinality: Two through ten requested attempts; optional Judge starts later only after terminal attempt states.
    - Introduced by diff: false; previous behavior: The comparison service already owned this model fan-out for manual comparisons.; critical-path effect: Attempt inference is off the creation tool's return critical path after successful send, while later comparison completion depends on it.
- Verdict: No finding: remote launch fan-out is bounded, visible in approval, and inherited from the existing comparison service; repeated capability resolution preserves required post-approval freshness.

### Scenario 3: Agent lists and reads persisted model comparisons

- Critical path: Listing filters and sorts the in-memory comparison collection, maps at most 25 summaries, and serializes them. Reading finds one comparison, builds bounded attempt/change/verdict manifests, resolves local transcript references, and serializes the result.
- Scaling input: Persisted comparison history for list calls; one comparison's participant and changed-file counts for read calls.
- Effective concurrency: Both tools execute synchronously in-process with no subprocess, filesystem, database, network, or IPC calls. Pagination is caller-serialized through nextCursor.
- Cache behavior: Comparisons are already loaded in memory by the existing service. No new cache is introduced; list pages recompute filtering/sorting, and reads use current in-memory session/chat state.
- Mechanism confidence: High confidence in local O(N log N) list work and bounded read serialization; low confidence that realistic histories make either a material regression.
- Magnitude uncertainty: Comparison history is not explicitly capped, so very large long-lived profiles would increase repeated page-sort cost, but realistic prevalence and enough magnitude for user-visible latency are not established.
- Expensive boundaries:
  - serialization at <code>src/vs/sessions/contrib/sessionComparison/browser/modelEvaluationTools.ts:list</code>: Serialize one comparison list page.; cardinality: At most 25 returned comparisons per call; filtering and sorting inspect the retained collection once per requested page.
    - Introduced by diff: true; previous behavior: No agent-facing persisted comparison listing existed.; critical-path effect: Local CPU and allocation are on the tool-call critical path.
  - serialization at <code>src/vs/sessions/contrib/sessionComparison/browser/modelEvaluationTools.ts:readModelComparison</code>: Build and serialize comparison evidence, changed-file summaries, completion metrics, and bounded verdict text.; cardinality: One comparison; normally at most ten attempts, up to 200 changed files per attempt, verdict lists capped to 32 entries, and text capped to 1000 characters in the manifest.
    - Introduced by diff: true; previous behavior: Judge sessions already built substantially the same bounded manifest; the diff exposes evaluator mode to eligible ordinary agents.; critical-path effect: Local serialization must finish before the read tool returns.
- Verdict: No finding: outputs are explicitly paged/bounded and no expensive external boundary is introduced; the uncapped retained-history sort lacks evidence of realistic material impact.

### Scenario 4: Agent Host caller configuration leases are acquired and released across hidden chats, cancellation, disconnect, and provider disposal

- Critical path: Tools requiring authoritative permissions wait for session/chat state. Cancellation, errors, or connection replacement dispose pending leases; successful callers dispose the returned lease after the operation.
- Scaling input: Concurrent config-dependent tool calls and config-chain depth for one caller chat.
- Effective concurrency: CounterSet tracks independent leases per backend chat; one caller's chain is awaited sequentially. There is no unbounded task creation.
- Cache behavior: Pinned or referenced chat subscriptions stay warm. After the last reference is removed they return to the existing 30-second idle timer; session and lease disposables are released immediately. Connection replacement clears all leases.
- Mechanism confidence: High confidence that disposal owns every added subscription on success, failure, cancellation, disconnect, and provider shutdown.
- Magnitude uncertainty: Config-chain depth and simultaneous evaluator calls vary, but normal chains and tool concurrency are small.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:acquireSessionConfig</code>: Subscribe to Agent Host session and chat state while exact caller configuration is needed.; cardinality: One retained session reference and one subscription per config-chain chat per concurrent logical lease, with underlying connection subscriptions ref-counted.
    - Introduced by diff: true; previous behavior: Hidden chats could lose idle subscriptions and consumers had no explicit exact-chat lease.; critical-path effect: Cold state blocks config-dependent tools; warm state resolves from existing subscription values.
- Verdict: No finding: the diff adds explicit cleanup ownership and reference counting rather than unbounded retention.

### Scenario 5: Comparison status notifications and isolated Judge layout react to session/chat changes

- Critical path: Observable reactions walk active comparisons and participant sessions, maintain one status listener per chat in a tracked session, and perform local pane visibility decisions when active chat state changes.
- Scaling input: Active non-archived comparisons, their participant sessions, and chats contained in shared parent sessions.
- Effective concurrency: Synchronous observable reactions are serialized on the UI thread; notification delays remain scheduled through existing timers. Session deduplication prevents rebuilding listener sets once per participant sharing the same session.
- Cache behavior: Nested DisposableMaps retain listeners only while their session remains tracked and dispose removed chats/sessions. The Judge controller retains only one pane/chat identity.
- Mechanism confidence: High confidence from the before/after loops and disposal paths that no additional external work or unbounded listener growth is introduced.
- Magnitude uncertainty: Large shared sessions can have more chats, but the prior implementation already iterated every chat for every comparison participant; the new session-level deduplication does not increase effective cardinality.
- Expensive boundaries: none found
- Verdict: No finding: changed UI work is local and either unchanged in cardinality or reduced through per-session deduplication.
