### Scenario 1: Submit a user chat request with an explicitly selected language model

- Critical path: ChatWidget.sendRequest awaits ChatService.sendRequest, which dispatches one agent invocation and returns response promises. The diff removes the recent-model storage update immediately before the submit event/return, so no new work is placed on the request critical path.
- Scaling input: Number of qualifying user submissions and concurrently active chat sessions; the removed preference work previously scaled once per qualifying request, not per history item or attachment.
- Effective concurrency: Requests in one session use the existing pending-request sequencing; separate sessions can invoke agents concurrently. The removed storage update had no shared limiter but was one bounded update per qualifying request.
- Cache behavior: The selected-model option is read from current widget state. The deleted recent list was an in-memory bounded array backed by profile/application storage; positive, negative, and failure cache behavior for agent/model execution is unchanged.
- Mechanism confidence: High: the changed hunk directly deletes the only recent-list write from the request path, and the traced request still performs exactly one agent invocation.
- Magnitude uncertainty: Agent transport and provider latency vary by implementation, but those boundaries are unchanged. The removed storage update is bounded and small, so this is a modest improvement rather than evidence of a shipped regression fix.
- Expensive boundaries:
  - IPC/network at <code>src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:2225 ChatService.sendRequestInternal -&gt; ChatAgentService.invokeAgent</code>: Invoke the selected chat agent, which may cross the extension-host/remote provider boundary and perform a model request.; cardinality: One agent invocation per dispatched request; queued requests remain sequenced per session while independent sessions may proceed concurrently.
    - Introduced by diff: false; previous behavior: The same single agent invocation occurred per dispatched request.; critical-path effect: Authoritative request execution remains on the response critical path and is unchanged by this diff.
  - database at <code>src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:2339 deleted addToRecentlyUsedList call; src/vs/platform/storage/common/storage.ts:490 AbstractStorageService.store</code>: Update and persist the bounded recent-model preference list.; cardinality: Previously one storage update for each non-system request carrying userSelectedModelId, with at most 20 identifiers; now zero.
    - Introduced by diff: false; previous behavior: Each qualifying request reordered the list, serialized it through storage, emitted storage change handling, and scheduled persistence.; critical-path effect: The synchronous in-memory update/serialization was before request submission returned, while physical storage flush is deferred; the diff removes rather than adds this work.
- Verdict: No reportable regression: request-path CPU, serialization, event fanout, and eventual storage I/O decrease.

### Scenario 2: Open or refresh the tabbed language-model picker, including an entitlement change that invalidates the selection

- Critical path: ModelPickerWidget synchronously builds the picker context and TabbedModelPicker builds destinations/sections. On entitlement changes, fallback selection scans pinned identifiers against available models, then scans models once; all work is in-memory on the UI path.
- Scaling input: Available model count M and pinned identifier count P. Fallback remains O(P\*M + M); removing up to four recent identifiers lowers the prior candidate scan and removes one filtered recent-list read during picker creation.
- Effective concurrency: Single synchronous UI-thread refresh; no worker, queue, IPC, filesystem, database, or network operation is introduced by the changed context construction or fallback loop.
- Cache behavior: Derived auto-model data is memoized per context in a WeakMap. Pinned identifiers come from the service's in-memory preference state. Removing recent identifiers neither creates a cache miss path nor changes model/provider discovery.
- Mechanism confidence: High: changed lines remove a service read/filter, a context field, and recent candidates from the fallback loop without adding replacement work.
- Magnitude uncertainty: Exact model and pin counts vary, but both the operation count and retained context size can only decrease in the changed path.
- Expensive boundaries: none found
- Verdict: No reportable regression: synchronous UI work and allocation are reduced; fallback behavior changes functionally but does not add a performance mechanism.

### Scenario 3: Initialize LanguageModelsService and synchronize model preferences across normal and Agents windows

- Critical path: The service constructor synchronously selects the preference scope, optionally performs the one-time Agents-window merge, reads pinned/hidden state, and installs cross-window listeners before initialization continues. The diff removes recent-list initialization, one listener, and the recent-list migration category.
- Scaling input: Number of windows and stored preference identifiers. Recent IDs were capped at 20; pinned/hidden cardinalities and existing listener lifetimes are unchanged.
- Effective concurrency: Each window owns one service and listener set. Cross-window storage notifications may arrive independently, but the diff removes one listener and does not add concurrency or fanout.
- Cache behavior: Pinned and hidden preferences remain cached in memory and invalidated by key-specific storage events. The recent-list cache, listener, and migration are removed. A legacy storage value may remain, but it is bounded to the prior 20-entry cap and is no longer read or expanded by this code.
- Mechanism confidence: High: constructor, listener registration, and migration hunks all delete recent-preference work with no replacement boundary.
- Magnitude uncertainty: Storage implementation and profile population affect absolute startup cost, but changed operation counts are strictly lower; the retained legacy key is tiny and pre-existing.
- Expensive boundaries:
  - database at <code>src/vs/workbench/contrib/chat/common/languageModels.ts:1297 LanguageModelsService constructor and :2627 \_mergeAgentsWindowModelPreferences</code>: Read model preferences from storage and, for an unmigrated Agents profile, merge nonempty preference categories into application storage.; cardinality: Ordinary initialization now omits one recent-list read and one listener. First Agents-profile migration now processes two preference categories instead of three; each category has at most two reads and one conditional write, followed by the unchanged migration-marker write.
    - Introduced by diff: false; previous behavior: Initialization read the recent list and subscribed to cross-window changes; one-time Agents migration also read and conditionally wrote that category.; critical-path effect: These synchronous storage/cache operations occur during service construction, but the diff removes a category and therefore shortens rather than lengthens the path; eventual persistence remains managed by the storage service.
- Verdict: No reportable regression: startup work, event-listener retention, cross-window event handling, and migration storage operations decrease.

### Scenario 4: Register and invoke chat developer commands

- Critical path: Chat developer actions are registered during contribution setup. The diff removes one action registration; the removed clear command previously performed one bounded storage write only when explicitly invoked.
- Scaling input: Number of workbench windows for registration and explicit developer-command invocations; no collection-scaled work is added.
- Effective concurrency: Synchronous registration and a single explicit command callback; no queue or burst behavior.
- Cache behavior: The removed command mutated the same bounded in-memory/storage-backed recent list. No replacement cache is introduced.
- Mechanism confidence: High: the registration and complete action implementation are deleted.
- Magnitude uncertainty: Command usage is uncommon, but prevalence does not affect the conclusion because the changed path only removes work.
- Expensive boundaries:
  - database at <code>src/vs/workbench/contrib/chat/browser/actions/chatDeveloperActions.ts:51 and deleted ClearRecentlyUsedLanguageModelsAction.run</code>: Clear and persist the bounded recent-model preference list when the developer command is invoked.; cardinality: Previously zero during registration and one storage update per explicit command invocation; now no such command or storage update exists.
    - Introduced by diff: false; previous behavior: Action registration retained one additional command descriptor, and explicit invocation wrote an empty list to storage.; critical-path effect: The command was off normal product critical paths and user-triggered; its removal cannot add latency.
- Verdict: No reportable regression: startup registration and optional storage work decrease.

**Summary:** Reviewed all 13 changed files and traced chat submission, picker UI refresh/fallback, language-model service initialization/cross-window storage, and developer command registration. The PR consistently removes bounded recent-model state, synchronous scans, listeners, serialization, and storage writes; it introduces no actionable performance regression and provides insufficient evidence of a user-visible shipped regression to record as a regression fix.
