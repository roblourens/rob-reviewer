**Relevant issue families:** eager-work, repeated-work, synchronous-ui-work, serialization-allocation

### Scenario 1: Workbench startup loads chat contributions and registers the Open Agent Picker action.

- Critical path: Workbench module evaluation and synchronous action/keybinding registration must complete during startup. The added controller imports do not add a new module-evaluation boundary because workbench.common.main imports editor.all before chat.shared.contribution, and editor.all already imports both paste/drop contributions and their controller modules.
- Scaling input: One workbench renderer startup and one OpenModePickerAction registration; cost is constant and does not scale with editors, chats, messages, or providers.
- Effective concurrency: Single-threaded, serialized ES module evaluation followed by synchronous registry mutation; no queue, limiter, or asynchronous fan-out is involved.
- Cache behavior: Each ES module is evaluated once per renderer/module graph. Cold startup already evaluates both controller modules through editor.all; subsequent chat registration reuses the evaluated module bindings. There is no positive, negative, or miss cache introduced by the diff.
- Mechanism confidence: High: the entrypoint import order and editor.all contribution imports directly establish prior loading, while the changed action constructor only builds two additional context expressions.
- Magnitude uncertainty: Exact module-loader timings vary by build, but the dependency graph proves the changed imports do not add first-time evaluation of these modules on the normal workbench startup path.
- Expensive boundaries: none found
- Verdict: No reportable regression. The suspected eager-loading mechanism is absent on the product startup path, and the added registration work is two constant-size context-key expressions.

### Scenario 2: A user presses Ctrl/Cmd+Period in a normal chat input or while a paste/drop selector is visible.

- Critical path: Synchronous keybinding resolution must inspect the action's when-clause before dispatch. The diff adds two boolean context-key predicates; ContextKeyAndExpr evaluates these as short-circuiting local context lookups. Paste/drop selector handling remains in the existing editor commands and controllers.
- Scaling input: One specific Ctrl/Cmd+Period event; added work remains two lookups regardless of document size, attachment count, provider count, or chat history.
- Effective concurrency: One synchronous resolver invocation per key event; there is no asynchronous work, concurrency burst, queue, or backpressure change.
- Cache behavior: Cold and warm behavior are equivalent for the changed predicates: they read already-maintained context-key values. The diff adds no cache, cache key, invalidation path, negative lookup, or coalescing behavior.
- Mechanism confidence: High: the changed when-clause and ContextKeyAndExpr.evaluate implementation establish exactly two extra short-circuitable in-memory evaluations, with no controller invocation or boundary call added by resolution.
- Magnitude uncertainty: Hardware-dependent nanosecond-level lookup cost is not measured, but cardinality and code path are certain and bounded to two extra predicates on the relevant key event.
- Expensive boundaries: none found
- Verdict: No reportable regression. The input-path work is constant, local, allocation-free during evaluation, and does not scale with user data or invoke an expensive boundary.

### Scenario 3: A user opens accessibility help on a supported workbench chat surface.

- Critical path: The help provider synchronously assembles localized strings and joins them before showing the accessible view. The diff adds one constant localized sentence and one array push only on non-inline, non-sessions-window surfaces.
- Scaling input: One help invocation; added CPU and allocation are O(1) and independent of chats, messages, attachments, editors, and workspace resources.
- Effective concurrency: Single synchronous help-text construction per invocation; no parallelism, serialization queue, or background task is involved.
- Cache behavior: Help text is generated per provider opening both before and after the diff. The new string has no cache lifecycle or invalidation behavior; localization data is local and no network or filesystem lookup occurs on this path.
- Mechanism confidence: High: the complete changed branch and provider call path show one bounded string addition, with no transitive subprocess, IPC, filesystem, database, or network operation.
- Magnitude uncertainty: The exact added bytes depend on localization, but the addition is one bounded sentence and cannot grow with chat history or workspace size.
- Expensive boundaries: none found
- Verdict: No reportable regression. The bounded string allocation is negligible relative to the existing one-shot help construction and introduces no scaling or retention mechanism.
