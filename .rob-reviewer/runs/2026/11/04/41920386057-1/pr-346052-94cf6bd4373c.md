**Relevant issue families:** repeated-work, serialization-allocation, boundary-fanout, missing-coalescing, synchronous-ui-work, cache-lifecycle

### Scenario 1: Open the chat model picker or cycle to the next pinned model

- Critical path: After model discovery, getPinnedModelIds synchronously walks the in-memory model cache, groups identifiers by pin identity, and returns matching available copies before the picker can render or the cycle command can choose a model. Model discovery itself is unchanged and is not initiated by the new identity helper.
- Scaling input: Total resolved models M, stored pin identities P, and the number of available vendor/harness copies per identity C. The pass is O(M + P\*C); although the implementation copies each per-identity array while grouping, effective C is bounded by the small set of extension/CLI/Codex/Claude copies rather than M, so realistic cost remains near-linear.
- Effective concurrency: Entire pin-query computation is synchronous with no queue or parallel work. Existing vendor model resolution is independently sequenced/coalesced per vendor and is not changed by this diff.
- Cache behavior: The model cache is the authoritative warm cache. On a cold/unresolved cache, no available copies are returned, as before unavailable stored pins were filtered out; subsequent model resolution populates the cache. The diff adds no retained identity cache, miss retry, or negative-cache state.
- Mechanism confidence: High confidence that the diff adds an in-memory model-cache scan and small allocations on each query; callers and cache ownership are directly traced. It does not add an external boundary or hot per-frame invocation.
- Magnitude uncertainty: Installations can have varying numbers of extension/BYOK models, but picker opening and pinned cycling are user-triggered, and duplicate copies per identity remain small. No evidence supports user-visible latency at realistic cardinality.
- Expensive boundaries: none found
- Verdict: No reportable regression. The query is more expensive than the prior O(P) filter, but remains bounded, user-triggered, in-memory work at realistic model counts and copy multiplicity.

### Scenario 2: Render or interact with rows in the Manage Language Models table

- Critical path: Visible model rows synchronously call isModelPinned while rendering pin actions; context-menu creation may call it for each selected row. The new implementation resolves the candidate identity and scans stored pins, all in memory, before actions are shown.
- Scaling input: Visible/selected model rows R and stored pins P. Both before and after the diff the membership check scales O(R\*P); the diff adds cache lookups and provider-ID decoding for built-in entries but does not increase asymptotic cardinality. Table virtualization bounds normal row rendering.
- Effective concurrency: Synchronous UI work only; no async fan-out is started by isModelPinned.
- Cache behavior: Metadata is read from the existing model cache. Unknown/stale stored identifiers fall back to their literal identifier without creating or retaining cache entries.
- Mechanism confidence: High confidence from the row renderer and context-menu call sites that checks occur per rendered/selected row and remain in-memory.
- Magnitude uncertainty: P is user-controlled and not explicitly capped, but it was already scanned by Array.includes for each row and ordinarily tracks a small curated list. The added constant-factor identity work is insufficient for a concrete regression finding.
- Expensive boundaries: none found
- Verdict: No reportable regression. There is no new scaling class, boundary, retained state, or realistic dropped-frame mechanism.

### Scenario 3: Pin or unpin a model, including cross-window copies and multi-selection in Manage Models

- Critical path: A pin checks identity membership, stores one normalized identity, writes preferences, logs telemetry, and emits the existing change event. Unpin filters equivalent stored identities, then performs the same existing write/log/event sequence. In the Manage Models view, that event still invokes the pre-existing refresh path that resolves vendors before rebuilding rows.
- Scaling input: Stored pins P per action; multi-selection count S. Identity matching adds O(P) in-memory work per action. Equivalent copies are now coalesced, so later pin/unpin calls for the same identity can return without duplicate writes, telemetry, events, or refreshes.
- Effective concurrency: Pin identity work is synchronous. Existing model refresh uses per-vendor SequencerByKey queues and joins queued resolutions; the diff does not alter this scheduling. Multi-selection still invokes actions serially in its loop, as before.
- Cache behavior: Pin identity is derived from the current authoritative model cache; stored identities persist through the existing storage service. No new cache or retained map survives a call. Cross-window storage listeners reload the same bounded persisted array.
- Mechanism confidence: High confidence in the storage, telemetry, event, and provider-refresh call flow and in the diff's unchanged or reduced boundary cardinality.
- Magnitude uncertainty: Provider resolution duration varies by installed provider, but the diff neither introduces that boundary nor increases successful mutation events for a given action sequence.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/common/languageModels.ts:\_savePinnedModels</code>: Persist the pinned-model identifier array through IStorageService.store; cardinality: One write per successful pin or unpin action; equivalent-copy operations can now be coalesced into no-ops.
    - Introduced by diff: false; previous behavior: Successful pin/unpin already performed one storage write; the diff changes stored identifiers but does not add writes and can reduce them for duplicate copies.; critical-path effect: The existing storage call occurs before the action emits its change event and completes.
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/common/languageModels.ts:\_logPinChange</code>: Emit chat.modelPinChange telemetry; cardinality: One telemetry event per successful pin/unpin, unchanged; equivalent-copy no-ops can reduce events.
    - Introduced by diff: false; previous behavior: The same telemetry call occurred once after every successful mutation.; critical-path effect: Telemetry API invocation remains on the action path, while transport batching/network behavior is owned downstream and unchanged.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/chatManagement/chatModelsViewModel.ts:refresh and src/vs/workbench/contrib/chat/common/languageModels.ts:selectLanguageModels</code>: Resolve language-model information from registered providers via provideLanguageModelChatInfo during the Manage Models refresh triggered by the existing pin-change listener; cardinality: At most one joined/queued resolution per vendor per refresh request under the existing per-vendor sequencer; successful mutations emit the same event as before, while equivalent duplicates can emit fewer.
    - Introduced by diff: false; previous behavior: Every successful pin/unpin already fired onDidChangePinnedModels, whose listener called the same refresh and provider-resolution path.; critical-path effect: Manage Models waits for provider resolution before rebuilding all vendor rows; this pre-existing refresh is not added or moved by the diff.
- Verdict: No regression. Added O(P) identity work is small relative to existing explicit-action boundaries, and coalescing equivalent copies can reduce duplicate boundary work.

- Effective concurrency: Parsing is synchronous and constant per identifier. Existing model-refresh sequencing, Claude subprocess lifecycle, and request concurrency are unchanged.
- Cache behavior: No cache is involved or added; encoding/decoding remains stateless. Warm and cold behavior are identical.
- Mechanism confidence: High confidence because the deleted and added parser bodies are mechanically equivalent and all call sites continue through the wrapper functions.
- Magnitude uncertainty: Downstream subprocess and network latencies vary, but their occurrence, scheduling, and cardinality are unchanged.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/claude/claudeAgentSession.ts:setModel</code>: Use the parsed Claude provider/model to select or rebuild the existing Claude subprocess transport on a later send; cardinality: At most the same transport decision/rebuild per actual cross-transport model switch as before.

  - network at <code>src/vs/platform/agentHost/common/codexModelSelection.ts:parseCodexModelSelection and src/vs/platform/agentHost/node/claude/claudeModelSelection.ts:parseClaudeModelSelection transitive dispatch paths</code>: Dispatch an existing Codex or Claude model request through the selected provider/transport; cardinality: One existing request per user send; parser extraction does not alter request count or fan-out.
    - Introduced by diff: false; previous behavior: Equivalent module-local encode/decode logic selected the provider before the same request dispatch.; critical-path effect: Provider parsing precedes dispatch but adds no extra network operation and preserves the same decoding algorithm.
- Verdict: No reportable performance change; this is a shared-helper refactor with unchanged per-identifier CPU and unchanged external boundaries.
