# Performance review: chat: use Agent Host defaults across chat entry points

[PR #346083](https://github.com/microsoft/vscode/pull/346083) at `39a916f95b001dc9287443b3d5984c84df1635fa`

## Findings (1)

### 1. [medium] Evict abandoned Agent Host drafts from the session cache

**Finding ID:** `PERF-BC4B7FA9D664`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widgetHosts/chatQuick.ts:444</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** UUID-keyed \`ContributedChatSessionData\`, synthetic \`IChatSession\`, URI, option-map, and listener objects retained in \`ChatSessionsService.\_sessions\`  
**Scaling:** One unreachable cache entry is retained per Quick Chat clear/new-draft operation; cost grows linearly with abandoned drafts for the lifetime of the provider/workbench.  
**Outcome:** unbounded retained memory and increasing GC/cleanup cost over the workbench lifetime  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Quick Chat always called \`startNewLocalSession\`; disposing the model reference released an empty local session, as opposed to inserting a synthetic contributed session into \`ChatSessionsService.\_sessions\`.  
**Changed behavior:** Clearing Quick Chat now acquires a uniquely addressed contributed Agent Host draft. Disposing the prior \`modelRef\` removes the chat model, but the contributed-session cache entry created during acquisition is not removed.  
**Confidence:** 0.97 — The changed branch, unique-resource generation, clear/reinitialize call path, and cache ownership are directly traced. \`ChatSessionsService\` caches every synthetic untitled session in \`\_sessions\`; that synthetic object has \`onWillDispose: Event.None\`, and model-reference teardown has no call to \`\_disposeSession\`. The only uncertainty is typical user reset count, which affects magnitude rather than the mechanism.

**Causal diff evidence:** The added non-local branch at \`chatQuick.ts:444\` replaces the previous \`startNewLocalSession(...)\`-only initialization with \`acquireOrLoadSession(getNewChatSessionResource(...))\`; \`getNewChatSessionResource\` generates a fresh UUID for every Agent Host draft, including every \`clear()\` replacement.

In a long-running window, repeatedly using Clear/New Chat in Quick Chat (and the same new default path used by voice drafts) grows the contributed-session cache linearly. The retained URIs, session wrappers, option maps, and listeners increase memory/GC pressure and make cache-wide provider cleanup progressively more expensive.

**Evidence:** \`QuickChat.clear()\` disposes \`modelRef\`, clears \`modelPromise\`, and immediately calls \`initializeModel\`; the added line then acquires a fresh Agent Host URI. \`ChatSessionsService.\_getOrCreateChatSession\` synthesizes untitled Agent Host sessions and stores each in \`\_sessions\` as \`ContributedChatSessionData\`. Its removal callback only listens to \`session.onWillDispose\`, but synthetic sessions use \`Event.None\`; searches show \`\_disposeSession\` is only reached from provider-item removal/deletion, not chat-model disposal. Therefore the UUID-keyed cache entry survives after Quick Chat releases the model.

**Suggested direction:** Tie synthetic untitled contributed-session cache ownership to the corresponding chat-model lifetime (or add an explicit release API and invoke it when an untitled draft is abandoned), while preserving entries that are still referenced or have materialized aliases.

### Scenario 1: Open, submit, clear, and reopen Quick Chat under the new Copilot Agent Host default.

- Critical path: The Quick Chat UI appears before initialization completes, but programmatic submission and normal submit handling await policy settlement, Agent Host draft acquisition, and host Ask-mode resolution. First send then materializes the draft before dispatch.
- Scaling input: Number of Quick Chat clear/new-draft operations over the lifetime of a workbench window.
- Effective concurrency: Initialization is one promise per Quick Chat instance; overlapping query opens share it and only the latest query submits. Clearing starts one replacement acquisition. Distinct UUID drafts do not coalesce.
- Cache behavior: Each Agent Host draft uses a fresh UUID, so acquisition is cold per new/cleared conversation. Repeated \`whenReady\` calls for the same Quick Chat are coalesced by \`modelPromise\`, and overlapping identical remote loads are coalesced by \`ChatService.\_remoteSessionLoads\`. Synthetic untitled sessions are cached in \`ChatSessionsService.\_sessions\` but are not evicted when the final chat-model reference is disposed, which is the reported regression.
- Mechanism confidence: High: unique URI generation, cache insertion, absent disposal event, and model-reference teardown were all traced directly.
- Magnitude uncertainty: The retained object set per abandoned draft is small, and typical clear counts are unknown; retention is nevertheless unbounded over a long workbench lifetime.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/widgetHosts/chatQuick.ts:424-468 and src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:\_materializeUntitledSession</code>: Resolve an Agent Host draft and, on first send, create/materialize the host session.; cardinality: One contributed-session acquisition per initial Quick Chat model and per clear; one Agent Host session-creation/dispatch sequence on the first send. Repeated \`whenReady\` calls do not multiply acquisition.
    - Introduced by diff: true; previous behavior: Quick Chat synchronously created an in-memory local session and did not enter the contributed-session cache or Agent Host materialization path.; critical-path effect: Draft acquisition and mode readiness gate submission; backend materialization gates first-send dispatch. The visible input itself is available while acquisition runs.
- Verdict: Reportable cache-lifecycle regression: every abandoned unique Agent Host draft remains in the contributed-session cache after its model is released.

### Scenario 2: Continue an inline chat request in the panel.

- Scaling input: One operation per user-initiated inline-to-panel handoff, independent of workspace file count.

- Cache behavior: A handoff creates one fresh destination draft. \`acquireOrLoadSession\` coalesces only matching resources; cancellation releases a late model reference. No repeated negative-cache retry is introduced within one handoff.
- Mechanism confidence: High for the changed critical path and cancellation behavior; no scaling multiplicity was found.
- Magnitude uncertainty: Cold Agent Host and policy-settlement latency varies by environment, but operation count is fixed at one and required by the routing change.
- Expensive boundaries:

    - Introduced by diff: true; previous behavior: The handoff synchronously created a local chat model, opened it, and submitted without Agent Host draft/materialization work.; critical-path effect: All are awaited before handoff completes and the inline session is disposed.
- Verdict: No separate performance finding: the new boundary is intentional one-per-handoff work, is awaited for required routing, and is cancellation-safe.

### Scenario 3: Create a voice target and send a first utterance, including floating-window operation.

- Critical path: Creating a target waits for policy and draft acquisition, then awaits switching a host if present. First voice send waits through queued materialization so it can adopt the real session before completing.
- Scaling input: Number of voice New Session clicks and first utterances; no collection-sized multiplicity.
- Effective concurrency: Per-send queue results are awaited serially. Distinct New Session clicks are not UI-disabled or coalesced, though generation checks reject stale completions and dispose their model references.
- Cache behavior: Voice session creation uses a fresh untitled resource. Chat-service loads coalesce only identical resources; distinct rapid New Session clicks can overlap, but obsolete references are released. The shared synthetic-session cache retention is covered by the reported Quick Chat cache-lifecycle finding.
- Mechanism confidence: High for operation placement, generation handling, and lack of UI coalescing; no independent expensive fan-out beyond user click cardinality was established.
- Magnitude uncertainty: Rapid-click prevalence and cold host duration are unknown; stale model references are released, limiting transient model retention.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/voiceClient/voiceToolDispatchService.ts:createChatSession/\_sendChatRequest and voiceSessionController.ts:\_sendVoiceRequest</code>: Resolve the default harness, materialize the untitled Agent Host session, send the utterance, and switch/adopt the returned resource.; cardinality: One draft acquisition per New Session click; one Agent Host materialization/send per first utterance; at most one materialized-session load when the target is owned but not displayed.
    - Introduced by diff: true; previous behavior: Voice New Session synchronously created a local model; direct fallback sends used that local resource and did not materialize an Agent Host session.; critical-path effect: Creation and first-send materialization are on the voice action's critical path so the target can be switched and adopted consistently.
- Verdict: No additional finding beyond the shared cache leak: required IPC is one per conversation, stale model references are cleaned up, and no high-confidence throughput regression was proven.

### Scenario 6: Create a standard editor or view chat under the changed default preference.

- Critical path: New editor/view chat resolution waits for policy and default-harness acquisition; first send materializes the draft. Existing chat editor/view code already implemented this path, while this PR changes its default reachability.
- Scaling input: Number of new conversations, not messages or workspace items.
- Effective concurrency: One acquisition per new conversation. ChatService coalesces duplicate loads by resource and cancels abandoned loads when consumer count reaches zero.
- Cache behavior: The setting default now selects Copilot Agent Host for ordinary new chats unless policy, availability, explicit choice, or remembered opt-out overrides it. Each fresh non-local draft is uniquely keyed; identical-resource loads coalesce.
- Mechanism confidence: High for routing and boundary placement; no multiplicative fan-out was found.

- Expensive boundaries:

    - Introduced by diff: true; previous behavior: The editor-specific Copilot harness preference defaulted off, preserving local creation in scenarios where that preference controlled routing.; critical-path effect: Acquisition gates model readiness; first-send materialization gates dispatch.
- Verdict: No separate finding for intended one-per-conversation Agent Host work; caching/coalescing is present. The abandoned-draft cache lifecycle is reported on the newly changed Quick Chat path where repeated resets expose unbounded growth.
