# Performance review: Chat windows follow-ups: proportional resize, keyboard shortcuts, and drag-out/close fixes

[PR #346039](https://github.com/microsoft/vscode/pull/346039) at `30938a49f3b553582b5795ffd59238433bf90b7f`

## Findings (2)

### 1. [medium] Capture state only when the chat actually leaves

**Finding ID:** `PERF-45ADE538CB36`  
**Location:** <code>src/vs/workbench/contrib/chatWindow/browser/chatWindowService.ts:262</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Editor serializer CPU, serialized editor-state strings, and the retained chat-part snapshot  
**Scaling:** A move of any tab out of the chat's group serializes every serializable editor in every chat-part group; cost and allocated bytes grow with total open tabs and their serialized state, and repeat for separate tab moves because the microtask guard only coalesces one synchronous batch.  
**Outcome:** Higher drag/drop latency, allocation/GC pressure, and a duplicate serialized snapshot retained for the window lifetime  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Ordinary editor moves from the chat group did not capture or serialize the complete chat-part state.  
**Changed behavior:** The new onWillMoveEditor listener ignores the event's editor and target; while the chat remains in the source group it always calls \_captureChatPartAsChatLeaves, which stores captureChatPart's full state snapshot.  
**Confidence:** 0.97 — The event payload includes the moved editor, the new callback discards it, and the complete synchronous serialization chain is directly visible. The exact serialized byte size depends on editor types, but the per-editor work and unnecessary trigger are certain.

**Causal diff evidence:** The added \`\_captureChatPartAsChatLeaves(group)\` call is registered for every \`group.onWillMoveEditor\` event, not only for an event whose editor is the chat or whose operation moves the containing group.

Moving a normal tab out of a chat group that also contains the chat synchronously serializes all tabs before the move can complete, even though no restoration snapshot is needed. With many or heavyweight serializable editors this blocks the drop and retains the copied strings until another capture or window disposal.

**Evidence:** The added listener checks only \`group.contains(content.input)\`. Its call reaches captureChatPart -&gt; chatPart.createState -&gt; Grid.serialize -&gt; EditorGroupView.toJSON -&gt; EditorGroupModel.serialize, whose loop calls each editor serializer's canSerialize/serialize. The snapshot is assigned to \`\_chatPartAsChatLeft\`; the queueMicrotask flag merely suppresses repeated captures within the same synchronous group merge.

**Suggested direction:** Use the move event/editor and a group-leaving signal to capture only when the chat or its group is actually leaving the window; retain the once-per-operation handling for multi-editor merges, and clear/avoid the snapshot when an ordinary sibling tab moves.

### 2. [medium] Batch kept-size corrections into one layout

**Finding ID:** `PERF-E3FBAE6D4015`  
**Location:** <code>src/vs/workbench/browser/parts/partGrid/partGrid.ts:1559</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous SplitView relayouts and editor-part/DOM layout callbacks  
**Scaling:** Each native window resize performs one corrective resize for every flexible sibling before the final kept-size resize; with k siblings this adds O(k) whole-line relayouts per resize event, and each relayout walks and lays out affected editor parts.  
**Outcome:** Increased synchronous resize cost and dropped frames while dragging or maximizing a populated chat window  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After the grid layout, ChatWindowGrid restored the terminal with one resizeCell call; in the common stacked topology this produced one post-layout height correction.  
**Changed behavior:** PartGrid now restores the proportional shares by calling resizeNode separately for each sibling target and then for the kept terminal, and every resizeNode immediately calls GridView.resizeView.  
**Confidence:** 0.95 — The native resize call path and synchronous relayout behavior are explicit in repository code, and the added tests establish the default stacked line has main, chat, and terminal siblings. Exact frame time varies by active editors and number of dropped parts, which affects severity but not the mechanism.

**Causal diff evidence:** The added call \`grid.resizeNode(\[...current.location, index\], line.orientation, value)\` is reached once for every function in the newly added \`steps\` loop; before this diff ChatWindowGrid performed a single terminal resize after the main grid layout.

Dragging or maximizing a stacked chat window with terminals visible now performs multiple editor-part layouts for every uncoalesced native resize event. The default main/chat/terminal line already needs two post-layout corrections instead of one, and parts created by edge drops add another correction each, making visible resize increasingly prone to jank.

**Evidence:** AuxiliaryWindow registers the native RESIZE event directly to layout(), ChatWindowGrid forwards every event to PartGrid.layout(), and this loop invokes grid.resizeNode once per step. GridView.resizeView calls BranchNode.resizeChild, SplitView.resizeView calls relayout, and relayout/layoutViews synchronously invokes each affected PartGridCell.layout; part cells then call IContentPart.layout and editor layout code.

**Suggested direction:** Compute the final sibling and terminal sizes together and commit them through one grid/SplitView layout transaction (or encode the fixed terminal plus sibling proportions in the primary layout), preserving the current rounding and constraint behavior without invoking resizeView per sibling.

### Scenario 2: Move a normal tab, the chat editor, or an entire chat group out of the chat's group/window

- Critical path: Before an editor move completes, group.onWillMoveEditor now calls \_captureChatPartAsChatLeaves whenever the source group still contains the chat. captureChatPart synchronously creates editor-part state and serializes every serializable editor before the target opens.
- Scaling input: Total groups and editors in the chat part and the size/cost of each editor serializer; separate user moves repeat the full work because only callbacks within one microtask are coalesced.
- Effective concurrency: Synchronous serialization blocks the move. The boolean guard coalesces a same-turn multi-editor merge, but provides no cross-event coalescing or cancellation.
- Cache behavior: There is no serialization cache. The latest snapshot replaces the previous one, but remains retained even when only a non-chat sibling tab moved and the chat never left.
- Mechanism confidence: High: the new listener discards the moved-editor payload, and the full synchronous serialization chain is explicit.
- Magnitude uncertainty: Editor serializer payloads vary substantially; a small tab set is cheap, while many or heavyweight editors amplify the cost.
- Expensive boundaries:
  - serialization at <code>src/vs/workbench/contrib/chatWindow/browser/chatWindowService.ts:262 via captureChatPart, EditorPart.createState, and EditorGroupModel.serialize</code>: Serialize the full editor-part grid and every serializable editor input; cardinality: One full pass over all chat-part groups/editors for every separate editor move from a group containing the chat; serializer output bytes scale with editor state.
    - Introduced by diff: true; previous behavior: No chat-part snapshot was created for ordinary per-editor moves.; critical-path effect: Runs before the editor move/drop completes, adding latency and allocation/GC pressure.
- Verdict: Reportable serialization/allocation regression for ordinary sibling-tab moves; filed as a medium-severity finding. Actual chat/group departure still legitimately needs a once-per-operation capture.

### Scenario 3: Close a chat window or reopen it after moving the chat between windows

- Effective concurrency: Checks and serialization are synchronous and sequential; the subsequent reopen is awaited once. No per-editor subprocess, IPC, filesystem, database, or network fan-out was introduced.
- Cache behavior: Captured chat-part state is reused after the chat leaves; serialized editor lists are temporary. No new cache miss/retry loop exists.
- Mechanism confidence: High for the call path and cardinality; no external I/O boundary is evidenced in the changed filtering logic.
- Magnitude uncertainty: Large tab sets increase explicit reopen cost, but this operation is infrequent and the diff does not increase effective serialization cardinality on the normal reopen path.
- Expensive boundaries:
  - serialization at <code>src/vs/workbench/contrib/chatWindow/browser/chatWindowEditors.ts:83 reopenChatWindow</code>: Serialize restorable editor inputs for explicit close/reopen; cardinality: At most one pass over each relevant group/editor per explicit reopen, with dirty/confirmation editors filtered out.

- Verdict: No additional performance finding beyond the over-broad per-tab capture listener.
