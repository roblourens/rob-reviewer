# Performance review: build: remove the install-state fast path and \`install-fast\`

[PR #346049](https://github.com/microsoft/vscode/pull/346049) at `3ac7bacfc40fe82f775701782e27b8d2e3d59eb5`

## Findings (1)

### 1. [medium] Skip unchanged install roots before spawning pnpm

**Finding ID:** `PERF-35F850D968CB`  
**Location:** <code>build/npm/postinstall.ts:210</code> (<code>LEFT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Four to seven pnpm subprocesses plus their lockfile and node\_modules filesystem work.  
**Scaling:** Cost grows linearly with the number of separate/distro install roots and repeats on every warm root install: four child calls in a normal checkout and seven with distro roots; three or four of them execute serially.  
**Outcome:** Increased warm-install latency from extra subprocess startup and per-root dependency-state scans on the command's critical path.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** When the complete saved state matched, postinstall performed the already-required Electron typings check and git configuration, then returned without spawning any child pnpm installs.  
**Changed behavior:** An unchanged root install now launches one child pnpm install for every separate install root instead of returning before those calls. The default checkout launches four child installs; a distro checkout launches seven.  
**Confidence:** 0.99 — The removed return and the unchanged loop/call path directly establish the frequency change. \`dirs.ts\` fixes the effective cardinality at four normal roots plus three optional distro roots, and \`postinstall.ts\` shows that build, remote, Copilot, and distro remote installs are serialized before the remaining roots run with bounded concurrency. The exact duration varies by platform and pnpm cache state, but the PR's own alternating warm-run timing corroborates a median increase from 1.75 s to 2.46 s.

**Causal diff evidence:** Deleting the \`if (\!process.env\['VSCODE\_FORCE\_INSTALL'\] && isUpToDate())\` return at base line 210 makes every invocation fall through to the loop over \`separateRoots\`/\`distroRoots\` and call \`pnpmInstallAsync\` even when the saved install state previously matched.

Every no-op \`pnpm install\` now blocks on at least four extra pnpm subprocesses and their filesystem scans, increasing repeat-install latency in the common developer workflow; platform process-launch overhead amplifies the delay on Windows.

**Evidence:** \`pnpm-workspace.yaml\` disables optimistic repeat install for the repository root, so this postinstall runs on every root \`pnpm install\`. Before the diff, a matching state returned at line 210; after its deletion, lines 220-254 enqueue \`pnpm install\` subprocesses for \`build\`, \`remote\`, \`remote/web\`, and \`extensions/copilot\` (plus three distro roots when present). Three default tasks are awaited serially, and the remaining task still requires a separate process and lock/module-state scan. Pnpm reporting "Already up to date" only avoids relinking inside each child; it does not avoid process startup and per-root checks.

**Suggested direction:** Keep required relink fix-ups unconditional, but restore a correctness-complete pre-spawn freshness check per install root (for example, compare that root's lock/install state and all script/native inputs) so only stale roots launch pnpm; alternatively coalesce the checks without starting one process per unchanged root.

### Scenario 1: Developer runs a no-op \`pnpm install\`, including from a workspace member.

- Critical path: The root install cannot complete until preinstall runs the gyp pnpm install and up to two sequential node-gyp header checks, then postinstall completes the child-root installs, git configuration, and links. None of the newly unconditional child processes is off the critical path.
- Scaling input: Number of repeat install invocations and effective install-root cardinality: four roots normally, seven with distro roots.
- Effective concurrency: The preinstall boundaries are sequential. In postinstall, build, remote, and extensions/copilot execute serially; remote/web is then the only default parallel task. With distro roots, four native tasks are serial and three JS-only roots run with a limiter of at most 8.
- Cache behavior: Previously a matching \`.postinstall-state\` skipped preinstall and the child-root portion of postinstall. The diff removes that warm fast path. Child pnpm invocations retain their own warm checks, and node-gyp \`--ensure\` avoids downloading cached header versions, but those checks happen only after the subprocesses start.
- Mechanism confidence: High: the deleted returns, fixed root lists, subprocess implementations, and scheduler directly prove the warm-path fan-out.
- Magnitude uncertainty: The exact delay varies by OS and pnpm/filesystem cache warmth. The fixed subprocess cardinality and serialization are certain; the PR's reported warm benchmark indicates about 0.7 seconds median on macOS, while Windows magnitude is not independently measured.
- Expensive boundaries:
  - subprocess at <code>build/npm/preinstall.ts:114</code>: Run \`pnpm install --frozen-lockfile\` in build/npm/gyp.; cardinality: One child pnpm process per warm root install.
    - Introduced by diff: true; previous behavior: A matching saved state returned before this subprocess.; critical-path effect: Blocks preinstall before the root dependency operation proceeds.
  - subprocess at <code>build/npm/preinstall.ts:127-133 via build/npm/nodeGypHeaders.ts:59</code>: Run node-gyp header installation/checks.; cardinality: Up to two sequential processes per warm install, one each for the root and remote native targets.

  - subprocess at <code>build/npm/postinstall.ts:220-254</code>: Run pnpm in every separate and distro install root.; cardinality: Four child pnpm processes normally and seven when distro roots exist.

### Scenario 2: Cold checkout or dependency/native-target change requires a real install.

- Critical path: Header preparation, root dependency installation, all separate-root installs, and any required downloads/rebuilds are on the install critical path.
- Scaling input: Number of missing packages, native targets, and separate/distro roots.

The new node-gyp \`--ensure\` uses cached headers when available; missing target versions still download. Pnpm stores and root-level install state may be cold.
- Mechanism confidence: High: a cold/stale old state necessarily bypassed the deleted guards and reached the same work.
- Magnitude uncertainty: Native rebuild and download duration depends on store/header cache misses, but this uncertainty does not create a diff-caused regression on the cold path.
- Expensive boundaries:
  - subprocess at <code>build/npm/preinstall.ts:114-133</code>: Install node-gyp and prepare runtime headers.; cardinality: One gyp pnpm process and up to two node-gyp processes.
    - Introduced by diff: false; previous behavior: The same processes ran when the saved state was absent/stale; node-gyp lacked \`--ensure\`.; critical-path effect: Required before dependency scripts can compile native modules.
  - network at <code>build/npm/nodeGypHeaders.ts:59</code>: Fetch Electron/Node headers.; cardinality: Zero to two downloads, depending on whether each target version exists in node-gyp's shared cache.

  - subprocess at <code>build/npm/postinstall.ts:220-254</code>: Install all separate and distro roots.; cardinality: Four to seven child pnpm installs.

- Verdict: No regression on this scenario; \`--ensure\` improves header-cache behavior, while removed state writes are minor savings.

### Scenario 3: Cloud Sandbox startup prepares prerequisites and then runs pnpm install.

- Critical path: On a setup-fingerprint miss, sandbox preparation and one explicit preinstall must finish before the user install starts; that install then performs its own preinstall. On a fingerprint hit only the user install's preinstall remains.
- Scaling input: Number of sandbox setup fingerprint changes and install invocations.
- Effective concurrency: A cross-checkout lock serializes setup; header/gyp operations are sequential. There is no coalescing between setup's explicit preinstall and the install lifecycle.
- Cache behavior: Cloud setup is guarded by \`.build/cloud-sandbox-setup\`, a fingerprint covering Node/pnpm versions, preinstall, gyp inputs, native targets, and custom headers. A warm matching fingerprint skips setup preinstall, but the subsequent root install now always performs its own preinstall because the install-state gate is gone.
- Mechanism confidence: High for the call path and lack of coalescing; moderate for prevalence of a fingerprint miss combined with a formerly matching install state.
- Magnitude uncertainty: How often sandbox setup fingerprints miss while the old install-state still matched is uncertain, and warm header checks are bounded, so this does not justify a separate finding beyond the general warm-install regression.
- Expensive boundaries:
  - subprocess at <code>build/npm/cloudSandboxSetup.ts:111-115</code>: Execute build/npm/preinstall.ts with the sandbox Node.; cardinality: One explicit preinstall process per setup-fingerprint miss.
    - Introduced by diff: false; previous behavior: The setup already forced this preinstall on a fingerprint miss.; critical-path effect: Blocks sandbox readiness before pnpm can run.
  - subprocess at <code>build/npm/preinstall.ts:49</code>: Run header preparation without the former saved-state early exit.; cardinality: One additional lifecycle preinstall for the following root install; its internal cardinality is one gyp pnpm plus up to two node-gyp checks.
    - Introduced by diff: true; previous behavior: A matching install-state file could skip this second preparation; a truly cold checkout without state already ran it.; critical-path effect: Blocks the install after setup; warm header caches reduce it to process/cache checks.
- Verdict: The same removed fast path can duplicate bounded warm checks, but this is covered by the reported repeated-install fan-out rather than a separate issue.

### Scenario 4: Alpine/distro product build installs remote dependencies inside a container.

- Critical path: The root install, remote-container Docker work, tool installation, remote pnpm install, and ownership restoration are all critical-path steps.
- Scaling input: CI retries/cache state, architecture, and package/store misses.
- Effective concurrency: The remote container branch is one of the serial native tasks. Other native roots remain serial and JS roots are bounded by the existing pool.
- Cache behavior: CI node\_modules jobs generally run on clean checkout/cache-miss paths, so the former repository state file did not provide a warm shortcut. Pnpm/store and node-gyp caches may still be warm. Alpine remote installation uses its mounted pnpm store.
- Mechanism confidence: High for boundary behavior; low prevalence confidence for a matching-state warm Alpine run.
- Magnitude uncertainty: A hypothetical cached CI checkout retaining a matching old state would expose the warm regression and make this branch expensive, but repository pipeline evidence shows these jobs as install/cache-build paths rather than established no-op repeats.
- Expensive boundaries:
  - subprocess at <code>build/npm/postinstall.ts:83-99</code>: Start the build container, globally install node-gyp-build/pnpm, install remote dependencies, and restore ownership.; cardinality: For an Alpine build, one Docker run for \`remote\`; arm64 may add one QEMU Docker run, followed by up to two ownership commands.
    - Introduced by diff: false; previous behavior: Cold/cache-miss CI installs already missed the old state check and executed this branch.; critical-path effect: Blocks the serial remote-root install.
  - network at <code>build/npm/postinstall.ts:94</code>: Fetch global tooling or missing remote packages inside the container.; cardinality: Network access as needed by global npm installation and pnpm store misses.
    - Introduced by diff: false; previous behavior: The same network-capable command ran on the old CI cold path.; critical-path effect: Downloads block the container command.
- Verdict: No separate finding: the expensive boundary is real but pre-existing on the demonstrated cold CI path; only a warm matching-state invocation would be newly exposed.
