# Performance review: Webview: check resolved paths against local resource roots

## Findings (1)

### 1. [high] Avoid statting every ancestor on every resource request

**Finding ID:** `PERF-8506052C7654`  
**Location:** <code>src/vs/workbench/contrib/webview/browser/resourceLoading.ts:194</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Filesystem metadata operations and IPC/remote-channel calls: one realpath plus one stat per path component below the closest root for each requested asset.  
**Scaling:** For N requested assets at average depth D below their effective closest root, authorization grows from no boundary calls to N realpath calls plus N\*D stat calls. Requests execute independently, with up to 32 host resource requests admitted concurrently on Electron, so the metadata operations can also arrive as a burst.  
**Outcome:** Blocked resource-load critical path, increased IPC/filesystem throughput demand, and higher remote webview load latency.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The same webview resource request performed an in-memory lexical containment check and proceeded directly to readFileStream; it did not issue realpath or per-component stat calls.  
**Changed behavior:** After resolving an allowed resource, the common case where realpath equals the requested path now builds every path component below the closest localResourceRoot and issues provider.stat for all of them before the file read can start.  
**Confidence:** 0.99 — The common non-link branch, per-component call count, desktop/remote IPC implementations, per-resource caller, cache revalidation behavior, and before/after placement are all directly traced in repository code. Exact milliseconds and typical asset counts vary, but the introduced boundary fan-out and critical-path delay do not.

**Causal diff evidence:** The added line \`const stats = await Promise.all(candidates.map(candidate =&gt; provider.stat(candidate)));\` directly introduces the per-component provider calls; the newly added await at line 78 places them before every allowed resource read.

Opening or refreshing a webview such as Markdown preview now delays each local asset by a realpath boundary round followed by a stat boundary round before reading. A page with many images, scripts, or styles can generate a burst of filesystem IPC (or remote-channel calls), increasing preview load latency and filesystem/IPC load; remote workspaces additionally pay network round trips.

**Evidence:** loadLocalResource now awaits isResolvedResourceInAnyRoot before readFileStream (resourceLoading.ts:78). For an ordinary non-link resource, resolveRealpath returns the same URI, which enters hasLinkBelowRoot (lines 183-184); line 194 invokes provider.stat once for the file and once for every ancestor below the closest root. The desktop file provider delegates both realpath and stat through DiskFileSystemProviderClient.channel.call, and RemoteFileSystemProviderClient uses the remote filesystem channel. webviewElement starts loadResource independently for every service-worker load-resource message, while the service worker revalidates cached responses through the host with an ETag, so this work also occurs on warm-cache requests.

**Suggested direction:** Keep strict link authorization without walking every component on the normal path: have the disk/remote realpath operation expose whether it used the unresolved fallback (or add a strict variant), and perform the component checks only for that rare fallback. Coalesce any unavoidable checks per request/root and preserve provider-change invalidation rather than issuing D metadata calls per asset.
