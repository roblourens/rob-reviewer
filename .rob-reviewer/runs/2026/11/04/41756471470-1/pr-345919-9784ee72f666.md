### Scenario 1: Open or restore the Inbox with an empty Ready for you tab and no configured welcome name

- Critical path: The view constructor/render synchronously reads and advances the message index and renders an unnamed empty message. Default-account resolution, authentication-session lookup, and the GitHub /user request run asynchronously and are not awaited by canvas opening or rendering; only the later personalized text update depends on them.
- Scaling input: One profile operation per distinct provider/session cache key, independent of Inbox row count; the empty-state render performs one additional short-circuit scan over all session rows to detect a Working row.
- Effective concurrency: The global Map stores the in-flight Promise, so concurrent WelcomeName instances for the same provider/session produce one authentication lookup/request. Distinct account keys are not limited, but account switching is user-paced.
- Cache behavior: Configured names and hidden surfaces bypass lookup. The first cold account key performs one lookup/request; the Promise, including undefined/failure results, is retained and reused across Inbox and new-chat instances. Account changes use a distinct provider/session key.
- Mechanism confidence: High: constructor visibility, autorun, promise insertion before await, and the non-awaited refresh call establish the scheduling and coalescing behavior directly.
- Magnitude uncertainty: Actual network latency and Inbox row counts vary, but neither delays first render. The retained cache grows only with distinct signed-in session IDs, which is realistically small.
- Expensive boundaries:
  - database at <code>src/vs/sessions/contrib/inboxOne/browser/inboxNotificationsView.ts:492 and InboxNotificationsView.advanceEmptyMessage</code>: Read the profile-scoped rotation index from storage and enqueue the incremented value for delayed storage flush.; cardinality: One read and one coalescible write when the view presentation is first constructed; storage flush is delayed and grouped by the storage service.

  - IPC at <code>src/vs/sessions/contrib/chat/browser/welcomeName.ts:109</code>: Resolve the selected authentication session with authenticationService.getSessions.; cardinality: At most one lookup for a cold provider/session key; concurrent Inbox and new-chat consumers coalesce through the module-level promise cache. - Verdict: No reportable regression. The diff adds a single cold, off-critical-path profile request to support personalization, coalesces it with the pre-existing new-chat lookup, and adds only one O(rows) short-circuit scan when the Ready tab is empty.

### Scenario 2: Hide and revisit an existing Inbox canvas

- Critical path: setVisible(true) synchronously reloads the rotation index, enqueues the next value, then marks the retained canvas visible and reruns the list autorun. No profile boundary is repeated for an unchanged warm account key.
- Scaling input: Cost scales with user-paced Inbox visits, not notifications or frames. Rendering still scales linearly with the rows already processed by the existing list autorun.
- Effective concurrency: Visibility transitions are serialized on the UI thread; storage writes to the same key collapse in the storage pending-insert map before flush.
- Cache behavior: The welcome-name promise remains warm across retained visits; no repeated authentication or network request occurs for the same account key.
- Mechanism confidence: High: the changed setVisible branch and storage implementation directly establish frequency and deferred persistence.
- Magnitude uncertainty: Visit frequency varies, but operations are one key read/write per visit and backing persistence is coalesced.
- Expensive boundaries:
  - database at <code>src/vs/sessions/contrib/inboxOne/browser/inboxNotificationsView.ts:575 and InboxNotificationsView.advanceEmptyMessage</code>: Read and advance the profile-scoped empty-message rotation index.; cardinality: One read and one delayed/coalescible write per hidden-to-visible visit, regardless of tab contents.
    - Introduced by diff: true; previous behavior: Revisiting Inbox did not access a rotation key.; critical-path effect: Only bounded in-memory storage operations occur before visibility changes; persistent database work is deferred by the storage flush delayer.
- Verdict: No reportable regression. The new work is bounded, user-paced, and coalesced rather than frame- or row-scaled.

### Scenario 3: Display a populated Inbox while the asynchronously fetched welcome name resolves or the configured name changes

- Critical path: The WelcomeName observable is now a dependency of the visible list autorun, so a name change performs one additional full row filter and renderList pass even though populated or non-Ready tabs do not consume the name. There are no subprocess, IPC, filesystem, database, or network calls inside that rerender.
- Scaling input: One extra O(number of session rows) list pass per profile resolution or relevant configuration change; profile resolution occurs once per cold account key and configuration changes are user-paced. Existing rendering already scales over the same row collection.
- Effective concurrency: Observable reactions execute synchronously and serially; no concurrent render burst is introduced.
- Cache behavior: The profile cache bounds automatic name resolution to once per provider/session key. Warm keys can resolve immediately during construction, avoiding a later response-driven rerender.
- Mechanism confidence: High for the extra rerender path; lower for material user-visible cost because it occurs once and existing card rendering reuses cached card renderings.
- Magnitude uncertainty: Inbox populations can vary, but the added pass is a single low-frequency event rather than repeated per row update, input event, or frame.
- Expensive boundaries: none found
- Verdict: No finding. Although the dependency is broader than the empty Ready state, its effective multiplicity is one bounded pass per cold profile result and does not establish a realistic latency or throughput regression.

### Scenario 4: Render the new-session welcome surface after extracting profile-name resolution into WelcomeName

- Critical path: Rendering creates WelcomeName and starts the same conditional asynchronous profile resolution used before the PR. Welcome phrase rendering does not await account, authentication, or network completion.
- Scaling input: One lookup per distinct signed-in provider/session key, independent of widget content or session count.
- Effective concurrency: In-flight requests for the same key are coalesced globally; separate keys can overlap only after account changes.
- Cache behavior: The cache semantics are preserved and broadened across both surfaces; configured names and disabled welcome phrases bypass the request.
- Mechanism confidence: High from the deleted implementation and equivalent added WelcomeName implementation.
- Magnitude uncertainty: None material for causality; the call path and count are equivalent or improved through cross-surface reuse.
- Expensive boundaries:

  - network at <code>src/vs/sessions/contrib/chat/browser/welcomeName.ts:114</code>: Fetch GitHub /user profile metadata.; cardinality: One per cold provider/session key; shared cache can reduce total calls when Inbox already fetched it.
    - Introduced by diff: false; previous behavior: newChatWidget performed the same request with the same provider/session-keyed promise cache.; critical-path effect: Off the initial widget render critical path; only personalization waits.
- Verdict: No regression and no qualifying regression-fix record. This is a behavior-preserving extraction for new chat with potentially better cross-surface coalescing.

### Scenario 5: Open Accessible View for Inbox content

- Critical path: Accessible View first reads the already-rendered empty-state text. When absent, it follows the existing row mapping and preview lookup path; no new external boundary is introduced.
- Scaling input: Empty content is O(1); populated fallback remains O(number of session rows), as before.
- Effective concurrency: Synchronous content generation with no queue or parallel work.
- Cache behavior: Uses already-rendered DOM text and existing preview map; no profile fetch is initiated by Accessible View itself.
- Mechanism confidence: High from the nullish short-circuit in the changed provider callback.
- Magnitude uncertainty: None material.
- Expensive boundaries: none found
- Verdict: No regression. The empty-state branch avoids rather than adds collection mapping, while the populated path is unchanged.
