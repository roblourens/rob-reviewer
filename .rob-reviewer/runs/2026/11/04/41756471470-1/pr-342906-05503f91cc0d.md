# Performance review: editTelemetry: preserve precise edit survival attribution

[PR #342906](https://github.com/microsoft/vscode/pull/342906) at `05503f91cc0d2cddeea474f727170540bc5e57a5`

## Findings (1)

### 1. [medium] Isolate reload attribution diffs from the shared editor worker

**Finding ID:** `PERF-6540B9B96A6F`  
**Location:** <code>src/vs/workbench/contrib/editTelemetry/browser/helpers/documentWithAnnotatedEdits.ts:281</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Full before/after document strings sent over worker IPC plus whole-document line/character diff CPU on the singleton editor worker  
**Scaling:** Cost grows with the number of externally reloaded, previously visible open models and with each model's byte/line count; every reload is deliberately kept separate and can consume up to 500 ms, while all documents converge on the same editor worker event loop.  
**Outcome:** Queued reload-attribution jobs can delay interactive editor-worker operations such as word-based completions, diff computation, link detection, and edit minimization; in the synchronous fallback they can block the renderer directly.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** External reload events used the StringEdit already supplied by the text-model change and published it without invoking the editor worker; only streamed chat edits used DiffService.  
**Changed behavior:** The added external-edit branch now awaits DiffService.computeDiff for every reload. DiffService forwards both complete snapshots to IEditorWorkerService with a 500 ms budget, and WorkerManager serves this and all core editor-worker features through one EditorWorkerClient.  
**Confidence:** 0.96 — The added boundary call, one-call-per-reload cardinality, full-snapshot payloads, 500 ms budget, and singleton shared worker are all directly traced in repository code. Exact delay depends on file sizes and how many open files an external operation changes, which affects severity rather than the mechanism.

**Causal diff evidence:** RIGHT line 281 is inside the newly added all-external branch and adds \`await this.\_diffService.computeDiff(peeked.prevValue.value, peeked.value.value)\` where the pre-diff code directly published the composed external edit.

A source-control checkout, external formatter, or generator that updates several open files now fans out into one full-document worker diff per reload. Those CPU-bound calls share and serialize on the editor worker, so background telemetry attribution can noticeably postpone completion lists or diff/formatting results after the reload burst.

**Evidence:** VSCodeWorkspace tracks every syncable model and snapshots textModel.getValue() on content changes; TextFileEditorModel marks disk updates as reloadFromDisk; this changed branch passes each reload's full prevValue/value to DiffService. DiffService calls computeStringEditFromDiffWithMetadata(..., maxComputationTimeMs: 500), while EditorWorkerService's WorkerManager owns a single EditorWorkerClient also used by computeDiff, textualSuggest, computeLinks, and computeMoreMinimalEdits. WebWorkerServer executes the CPU-bound DefaultLinesDiffComputer on that single worker event loop.

**Suggested direction:** Keep the per-reload attribution boundaries, but run these background telemetry diffs in a telemetry-owned worker or another low-priority/preemptible execution path rather than the singleton editor worker; also apply a global queue/budget so a multi-file reload burst cannot monopolize worker CPU.
