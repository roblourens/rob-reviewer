## Performance regression fixes detected (1)

### 1. unbounded-retention

**Fix location:** `src/vs/workbench/contrib/editTelemetry/browser/helpers/utils.ts:37` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/editTelemetry/browser/helpers/utils.ts:33`  
**Introducing path:** `src/vs/workbench/contrib/editTelemetry/browser/helpers/utils.ts`  
**Introducing commit:** `22440e0276be6fa9554868660a41dff33785d5e6`  
**Mechanism family:** `unbounded-retention`  
**Performance category:** `memory`  
**Confidence:** 0.99

**Mechanism:** A replaying AsyncIterableSource retained every emitted change object, including both full StringText document snapshots, after the sole consumer had processed it; retained memory therefore grew with edit history for as long as document telemetry tracking remained active.

**Symptom:** Repeated edits, especially in large long-lived documents, caused monotonically growing retained heap and corresponding GC pressure.

**Fixed behavior:** The changed helper now returns a single-consumer AsyncIterableProducer. Its ProducerConsumer removes each consumed value from \_unconsumedValues, while the startup buffer is explicitly cleared after transfer, so only pending changes remain retained and consumed full-document snapshots can be collected.

**Evidence:** Base line 33 constructed AsyncIterableSource for iterateObservableChanges; AsyncIterableSource delegates to AsyncIterableObject, whose \_results array appends every emitted change and whose iterator advances only a private index, so consumed entries remain referenced for the stream lifetime. CombineStreamedChanges creates this stream per tracked document and each change includes value/prevValue StringText snapshots. The added GC regression test drives 80 edits while the pipeline remains active and requires all 40 sampled consumed snapshots to be collectible.

### Scenario 1: Ordinary typing and inline edits in a tracked open document

- Critical path: The observable change callback synchronously enqueues a value/prevValue snapshot, then returns; the single async consumer publishes non-chat, non-external edits without awaiting an expensive boundary, so telemetry processing is off the editor input critical path after enqueue.
- Scaling input: Edit frequency and the number/size of pending document snapshots for one tracked document; effective retained cardinality is queue backlog rather than total edit history.
- Effective concurrency: One AsyncIterableProducer consumer and one serialized \_run loop per document; edits arriving while the consumer is busy remain ordered in the producer queue. Different documents are independent.
- Cache behavior: There is no cache or cache key. Before the producer microtask starts, synchronous changes use a short startup buffer that is transferred and cleared; afterward changes go directly to the producer. Consumed entries are removed rather than replay-cached.
- Mechanism confidence: High: the changed helper is directly invoked by CombineStreamedChanges, and AsyncIterableProducer removes consumed queue entries while preserving only pending edits.
- Magnitude uncertainty: The exact memory benefit depends on document size, edit frequency, and document lifetime; the changed mechanism itself is clear and does not add work proportional to consumed history.
- Expensive boundaries: none found
- Verdict: No regression. The diff removes history-sized retention; ordinary edits add only bounded enqueue/dequeue work and no new boundary call.

### Scenario 2: Streamed chat edits and disk-reload edits that require diff computation

- Critical path: Changes are enqueued, then CombineStreamedChanges serially groups chat changes or handles each external reload and awaits editor-worker diff computation before publishing. The worker call was already on this path; the diff only replaces the in-process stream queue.
- Scaling input: Effective cardinality is chat groups plus individual reloads, with pending edit count during an active worker diff controlling temporary memory.
- Effective concurrency: Per document, \_run awaits one diff at a time. Chat edits are coalesced over the existing one-second window; external reloads remain one diff per observable reload change. Backlog accumulates only while the current serialized operation is pending.
- Cache behavior: No diff-result cache is present. Chat edits use existing temporal coalescing; reloads intentionally remain separate. The new producer retains pending snapshots during a slow worker call but releases them after consumption.
- Mechanism confidence: High for unchanged worker-boundary behavior and reduced consumed-snapshot retention; medium for maximum real-world backlog magnitude.
- Magnitude uncertainty: Backlog size depends on edit bursts and worker latency, but the diff neither increases worker-call cardinality nor concurrency. AsyncIterableProducer uses array shifts for backlog draining, yet realistic backlog is bounded by the serialized diff window and does not establish a high-confidence regression.
- Expensive boundaries:

- Verdict: No introduced performance issue. Existing worker IPC remains serialized and unchanged, while consumed full-document snapshots are now released.

### Scenario 3: Document shutdown and waitForQueue drain/restart boundaries

- Critical path: waitForQueue clears the old run store, completes its stream after already queued edits, waits for the existing serialized run to drain, runs the boundary callback, and starts the next stream. Disposal may wait for an already-started worker diff but adds no new boundary.
- Scaling input: Number of edits already queued at the boundary; retained state falls as the single consumer drains it.
- Effective concurrency: \_runQueue serializes the previous consumer, the drain callback, and the replacement consumer. Store disposal synchronously unsubscribes and resolves the producer; no parallel drain burst is introduced.
- Cache behavior: No cache. Queued pre-disposal changes are drained in order; post-boundary changes enter the newly created producer. Startup buffers are cleared after transfer and completion wakes a pending reader.
- Mechanism confidence: High: lifecycle ordering is explicit in \_restart, DeferredPromise completion, and the added queue/disposal tests.
- Magnitude uncertainty: Drain duration depends on pre-existing queued edits or an in-flight worker diff, but the changed completion mechanism does not add a new wait or repeated operation.
- Expensive boundaries: none found
- Verdict: No regression. The new lifecycle releases consumed values and preserves serialized draining without new I/O, IPC, or concurrency.
