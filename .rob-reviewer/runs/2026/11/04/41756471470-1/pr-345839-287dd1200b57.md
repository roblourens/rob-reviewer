### Scenario 1: Root dependency install and native-module configuration

- Critical path: On a warm unchanged tree, install-state hashing completes and preinstall exits before header setup. On a cold or invalidated install, the preinstall's gyp install and two runtime-header installs must finish before dependency installation can proceed; later separate native roots are installed sequentially as before.
- Scaling input: Number of install roots is fixed and small; dependency count does not multiply manifest parsing or header downloads.
- Effective concurrency: The Electron and server Node.js header subprocesses remain sequential. Postinstall native roots remain sequential to avoid node-gyp conflicts, while JS-only roots retain the existing CPU-count limiter capped at 8. The pnpm updateConfig hook reads one manifest once per install-root pnpm process, not once per dependency script.
- Cache behavior: The warm install-state fast path remains before header setup. Adding nativeBuild to the normalized install-state input intentionally invalidates after runtime configuration changes; unrelated package.json fields remain excluded. Header caches continue to key internally by target.
- Mechanism confidence: High: call sites, ordering, hook lifetime, and unchanged two-target header boundary are explicit in the code.
- Magnitude uncertainty: Exact JSON parse cost varies with manifest size, but call count is fixed and the work replaces configuration parsing on an already expensive cold path.
- Expensive boundaries:
  - filesystem at <code>build/npm/pnpm/nativeBuildEnv.ts:readNativeBuildConfig; build/npm/preinstall.ts:getHeaderInfo</code>: Read and JSON-parse package.json/remote/package.json for nativeBuild settings instead of reading and regex-parsing .npmrc files.; cardinality: Two manifest reads in cold preinstall plus one read per pnpm install-root hook process; independent of dependency count because updateConfig computes extraEnv once.
    - Introduced by diff: false; previous behavior: The same paths synchronously read small .npmrc files; the diff changes the source and parsing format, not boundary cardinality.; critical-path effect: Synchronous reads are on cold-install setup, but replace equivalent synchronous configuration-file reads and are negligible beside package installation and native compilation.
  - subprocess at <code>build/npm/preinstall.ts:installHeaders; build/npm/nodeGypHeaders.ts:installNodeGypHeaders</code>: Install the pinned node-gyp package, then run node-gyp to install Electron and server Node.js headers.; cardinality: One pnpm subprocess and two sequential node-gyp subprocesses on a cold/invalidated install; cached headers may avoid network transfer inside node-gyp.
    - Introduced by diff: false; previous behavior: Identical subprocess count and ordering; only dist URL and target lookup moved from .npmrc to package.json.; critical-path effect: These operations block cold install before dependency installation.
  - network at <code>build/npm/nodeGypHeaders.ts:installNodeGypHeaders</code>: Download Electron and Node.js headers through node-gyp on cache misses.; cardinality: At most two logical header installs per cold preinstall, each with the existing retry policy; effective target count remains two.
    - Introduced by diff: false; previous behavior: The same two targets and URLs were read from .npmrc and downloaded on the same path.; critical-path effect: Cold cache misses block install; warm node-gyp caches avoid the downloads.
- Verdict: No reportable regression: expensive subprocess/network work and concurrency are unchanged, while added manifest parsing is bounded and one-time per root.

### Scenario 2: CI node\_modules and Electron cache-key computation/restoration

- Critical path: Local synchronous file hashing must finish before cache restore keys are available; subsequent cache restore/download behavior depends on the resulting keys.
- Scaling input: Fixed repository package count for filesystem hashing and one cache operation per job; no per-dependency network fan-out.
- Effective concurrency: Cache-key file reads and hashing are sequential in one Node.js process. Cache actions remain one logical restore per cache; no loop adds parallel network requests.
- Cache behavior: Electron cache remains keyed by OS, architecture, and Electron checksum inventory, so target changes still miss and ordinary manifest changes no longer cause false misses. node\_modules keys now include nativeBuild, preventing reuse of binaries built for a different runtime. No negative cache is introduced.
- Mechanism confidence: High for key composition and file-read cardinality; high that the base helper has no non-test caller in this revision.
- Magnitude uncertainty: Future use of the base-key helper could add roughly one manifest read per listed directory, but current production reachability is absent and the bounded local work is small compared with cache restore/install.
- Expensive boundaries:
  - filesystem at <code>build/azure-pipelines/common/cacheKeys.ts:computeNodeModulesCacheKey/computeNodeModulesBaseCacheKey</code>: Read package manifests and native-build hook files to compute node\_modules keys.; cardinality: The main key already reads each of roughly 60 workspace/install-root package.json files once. The base-key helper now reads the same fixed directory list to extract nativeBuild, but repository search finds no production caller in this revision beyond tests.
    - Introduced by diff: true; previous behavior: The main key read the same manifests but omitted nativeBuild from the selected object. The base helper read three .npmrc files rather than the fixed manifest list.; critical-path effect: Main key hashing is required before restore; base-key work is not currently on a production workflow path in this revision.
  - network at <code>.github/actions/setup-electron/action.yml</code>: Restore an Electron download cache and download Electron archives on a cold cache miss.; cardinality: One cache restore and one logical Electron download setup per job, unchanged; the key now hashes one checksum file instead of the checksum plus .npmrc.
    - Introduced by diff: false; previous behavior: The same cache action and download ran; .npmrc contributed to the key. The checksum file changes with every Electron target bump, preserving target invalidation.; critical-path effect: Cache misses can block setup, while warm hits avoid archive downloads.
- Verdict: No reportable regression: cache invalidation becomes more precise, network cardinality is unchanged, and the only added filesystem scan is bounded and not currently on a production path.

### Scenario 3: Build, package, sign, and test launch runtime-version resolution

- Critical path: Runtime version lookup occurs once during each affected script's startup before signing, packaging, downloading runtimes, or launching tests can proceed.
- Scaling input: Number of script invocations and build platform/architecture tasks; version parsing is constant per invocation and does not scale with source-tree size.
- Effective concurrency: Each script resolves versions synchronously once. Alpine commands run one node process instead of a grep/cut pipeline; Unix and Windows test launchers run one node process where they previously invoked sed or findstr. useRunnerNodeForServer removes a nested Node subprocess and performs direct reads.
- Cache behavior: Runtime artifact cache targets remain the same. Generated desktop/server manifests explicitly omit nativeBuild, avoiding shipped metadata growth. Warm installed-Electron checks still compare the same target value.
- Mechanism confidence: High: all command substitutions and direct-helper call paths are visible in changed lines.
- Magnitude uncertainty: Node startup is heavier than sed/findstr on test launch, but it occurs once before a full suite and is partly offset in Alpine and CI helper paths; no realistic user-visible regression is evidenced.
- Expensive boundaries:
  - subprocess at <code>scripts/test.sh; scripts/test.bat; build/azure-pipelines/alpine/product-build-alpine\*.yml</code>: Resolve Electron or server Node.js version from package.json in shell/CI scripts.; cardinality: One version-resolution command per script invocation. Alpine reduces two pipeline processes to one Node process; test launch remains one external command.
    - Introduced by diff: true; previous behavior: Unix tests used one sed command, Windows used findstr, and Alpine used grep piped to cut. The diff substitutes a single Node process.; critical-path effect: The command is on script startup, but fixed-cardinality and followed by much larger test/build work.
  - subprocess at <code>build/azure-pipelines/common/useRunnerNodeForServer.ts:main</code>: Locate the server Node.js binary for CI reuse.; cardinality: Zero nested subprocesses after the diff; direct helper calls replace one execFileSync Node process.
    - Introduced by diff: false; previous behavior: Spawned one Node subprocess to execute build/lib/node.ts, then separately read remote/.npmrc.; critical-path effect: Removes process startup from the CI setup critical path.
  - network at <code>build/lib/electron.ts; build/gulpfile.reh.ts</code>: Fetch Electron/server Node.js archives during build tasks when absent.; cardinality: One runtime artifact per requested platform/architecture task, unchanged by the version reader refactor.
    - Introduced by diff: false; previous behavior: The same target and internal build IDs selected the same artifact fetches; only their checked-in source moved.; critical-path effect: Cold artifact fetches block their build tasks; existing caches serve warm runs.
  - filesystem at <code>build/lib/electronVersion.ts; build/lib/node.ts; build/gulpfile.vscode.ts; build/gulpfile.reh.ts</code>: Read package.json to obtain nativeBuild and remove nativeBuild while generating shipped manifests.; cardinality: One or a few fixed reads/JSON edits per build-script invocation or packaged product, not per source file.
    - Introduced by diff: true; previous behavior: Version readers synchronously read tiny .npmrc files, and package editors did not need to remove nativeBuild because the field did not exist.; critical-path effect: Bounded setup work before substantially heavier packaging/signing operations.
- Verdict: No reportable regression: all added work is constant startup overhead on heavyweight build/test workflows, while one existing subprocess is removed and artifact boundary cardinality is unchanged.
