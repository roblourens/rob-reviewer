# Performance review: chat windows: chat windows of the Agents window on parts

[PR #345683](https://github.com/microsoft/vscode/pull/345683) at `eb200c4e8c48b27217231ca4f5d8828554528d34`

## Findings (2)

### 1. [medium] Avoid the unconditional second grid layout on resize

**Finding ID:** `PERF-57209283B71E`  
**Location:** <code>src/vs/workbench/contrib/chatWindow/browser/chatWindowGrid.ts:342</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** full part-grid, editor-pane, and xterm layout CPU work  
**Scaling:** The duplicate work runs for every auxiliary-window resize event while terminals are visible, and scales with the number and complexity of cells/editor panes in that chat window.  
**Outcome:** increased main-thread resize latency and dropped frames, with redundant terminal dimension evaluation and possible coalesced PTY resize work  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Without the new chat-window grid path, resizing did not perform this extra post-layout \`resizeCell\` pass to preserve a chat-window terminal height.  
**Changed behavior:** After \`grid.layout(width, height)\` has already laid out every visible cell, the added branch always calls \`\_resizeTerminals\`, even when the terminal height is unchanged (for example during width-only resizing). \`resizeCell\` unconditionally enters \`Grid.resizeView\`/\`SplitView.resizeView\`, whose relayout lays out the grid and active terminal editor again.  
**Confidence:** 0.98 — The synchronous double-layout call chain is explicit in the grid and terminal implementations, and width-only window resizing guarantees cases where the corrective resize is redundant. Exact frame cost varies with pane content and hardware.

**Causal diff evidence:** Added line 342 performs \`\_resizeTerminals(grid, terminalsHeight)\` after every noninitial layout whenever the terminal cell is visible, without checking whether \`grid.layout\` changed its height.

Dragging the edge of a chat window with terminals open performs two full layout passes per resize event; TerminalEditor then invokes TerminalInstance.layout again, making interactive resizing visibly more prone to jank.

**Evidence:** Lines 337-342 capture the terminal height, call \`grid.layout\`, then unconditionally call \`\_resizeTerminals\`; that helper reads the current width and calls \`PartGrid.resizeCell\`. \`PartGrid.resizeCell\` delegates to \`Grid.resizeView\`, and \`SplitView.resizeView\` always calls \`relayout\`. TerminalEditor.layout calls \`instance.layout\`, which reevaluates rows/columns and schedules process dimensions. The same file's \`\_update\` path already demonstrates the bounded guard by comparing the post-layout height before resizing at lines 391-392.

**Suggested direction:** At minimum, mirror the existing \`\_update\` guard and call \`\_resizeTerminals\` only when the post-layout terminal height differs; ideally feed the preserved terminal height into a single grid layout transaction so height-changing resizes also avoid laying out terminal/editor content twice.

### 2. [medium] Coalesce terminal show operations per chat window

**Finding ID:** `PERF-DEA01BAF42C7`  
**Location:** <code>src/vs/sessions/contrib/terminal/browser/chatWindowTerminals.ts:144</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** terminal subprocesses and their renderer/process objects  
**Scaling:** The cost grows with the number of overlapping show/toggle requests issued before the first terminal lookup or launch resolves; each request can independently launch another terminal.  
**Outcome:** duplicate subprocess launches, extra retained terminal/rendering resources, and higher latency/CPU during slow local or remote terminal startup  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this chat-window terminal path, there was no per-window show operation that could independently launch a terminal for the same window. A single user request launched at most the requested terminal.  
**Changed behavior:** Every call to show() observes the shared terminal set before awaiting getChatWindowTerminal(), but no pending promise is recorded. Concurrent calls therefore all see an empty set and independently cross the terminal-creation boundary.  
**Confidence:** 0.97 — The call path from repeated toggle/show calls to asynchronous terminal creation is explicit, and terminal visibility cannot flip until after the awaited launch and editor move. The only uncertainty is how often users overlap requests; slow remote terminal startup makes the trigger realistic.

**Causal diff evidence:** Added line 144 invokes \`getChatWindowTerminal\` independently from each \`show()\` after an empty-set check, with no per-window pending operation recorded around the await.

Rapidly clicking the terminal toggle, or clicking it while restoration is still populating the window, can start two or more terminals for one chat window—especially when remote/profile initialization makes the first launch slow—wasting subprocess, CPU, and memory resources.

**Evidence:** show() checks \`\!terminals.size\` and then awaits \`\_source.getChatWindowTerminal(...)\` at the changed line without an in-flight guard. \`toggle()\` calls show while \`terminalsVisible\` remains false until an editor arrives. The source reaches \`SessionsTerminalContribution.\_ensureTerminal\`, whose empty result path calls \`\_createTerminalForSession\`/\`ITerminalService.createTerminal\`; parallel callers can all pass the empty checks before any created terminal is tracked. Existing generation checks only cancel hide/close races and do not coalesce shows.

**Suggested direction:** Keep one in-flight show promise per window and have subsequent show/toggle requests join it; preserve the existing generation cancellation so a hide or close during the shared launch still releases the resulting terminal exactly once.

### Scenario 1: Open or reveal a chat in its own window

- Critical path: The command awaits content resolution, auxiliary-window creation, scoped services/parts, chat/editor restoration, and the first layout before returning. Chat-model holding avoids reloading an already loaded transcript while the view moves.
- Scaling input: Number of distinct chats opened concurrently and number of editors/created parts restored into each window.
- Effective concurrency: Requests for the same chat are coalesced by \`InFlightOperations\`; an already open resolved chat is revealed. Different chats can open concurrently and have no global limiter.
- Cache behavior: Open windows act as a positive cache and same-chat pending opens are coalesced. Failed/unknown content is not negatively cached, which is appropriate for explicit user retries.
- Mechanism confidence: High: the complete open path and same-key in-flight map are directly visible.
- Magnitude uncertainty: Auxiliary-window creation duration and typical editor counts vary, but the cardinality and coalescing behavior are explicit.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chatWindow/browser/chatWindowService.ts \`\_openWindow\`</code>: Create/focus an auxiliary workbench window; cardinality: One creation per distinct newly opened chat; zero for an already open chat, with same-chat pending opens coalesced.
    - Introduced by diff: true; previous behavior: The base revision had no generic part-based chat-window service on this path.; critical-path effect: Window creation must complete before parts and editors can be attached, so it is on the open command's critical path.
- Verdict: No additional reportable regression: expensive creation is one per requested distinct window and duplicate same-chat opens are coalesced.

### Scenario 2: Restore chat windows after workbench startup

- Critical path: Restoration runs asynchronously after the provider and restore setting become ready, so it does not block the main workbench restore, but each restored chat window waits for \`canRestore\` and auxiliary-window opening before the next stored entry. Terminal population is scheduled separately after each window appears.
- Scaling input: Number of persisted chat windows, serialized editors/created parts per window, and the subset with terminals shown.
- Effective concurrency: Chat-window validation/opening is serialized by the restore loop. Restored terminal shows are independently scheduled and can overlap across windows; no shared terminal-launch limiter was found.
- Cache behavior: Stored state is retained while restore is disabled/pending and removed after restoration; \`canRestore\` relies on loaded session state. Existing/pending chat opens are deduplicated by chat key. Terminal shows lack per-window in-flight coalescing.
- Mechanism confidence: High for sequencing and boundary cardinality; moderate for aggregate startup contention because user window counts vary.
- Magnitude uncertainty: Typical persisted-window counts are unknown and the feature is disabled by default; session loading can wait up to the provider's 30-second timeout.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chatWindow/browser/chatWindowsRestoration.ts \`\_read\`/\`\_write\`</code>: Read/write serialized restoration state through the workspace storage service; cardinality: One read when restoration starts plus save/remove events; payload grows with restored windows, groups, and serializable editors.

  - IPC at <code>src/vs/workbench/contrib/chatWindow/browser/chatWindowsRestoration.ts \`\_restore\` -&gt; ChatWindowService.open</code>: Create one auxiliary window for each restorable stored chat; cardinality: One per effective stored chat that \`canRestore\` accepts; the loop serializes these calls.

  - subprocess at <code>src/vs/sessions/contrib/terminal/browser/chatWindowTerminals.ts \`\_trackWindow\`/\`show\`</code>: Create or acquire a session terminal for every restored window whose terminal part was stored as shown; cardinality: Up to one initial terminal operation per restored terminal-visible window; operations can overlap across windows.
    - Introduced by diff: true; previous behavior: The base path did not repopulate terminals in part-based chat windows.; critical-path effect: Off the main startup critical path, but concurrent launches contend with post-startup rendering and make restored windows fully usable later.
- Verdict: The broad restoration fan-out is bounded by stored windows and opening is serialized. The independently scheduled terminal launch path contributes to the separately reported missing-coalescing risk when another show overlaps.

### Scenario 3: Toggle or restore terminals in a chat window

- Critical path: Showing terminals awaits session cwd/profile resolution, terminal acquisition or creation, moving the terminal editor into the window part, and optional focus. Hiding moves running terminals back to the panel without killing them.
- Scaling input: Number of overlapping clicks/restoration-triggered shows before the first terminal launch resolves; remote/profile startup increases the overlap window.
- Effective concurrency: There is no per-window pending-show promise. Multiple \`show\`/\`toggle\` calls can execute concurrently while visibility remains false, and each can independently reach terminal creation. Different windows are also unrestricted.
- Cache behavior: Running terminals are retained per window and reused after hide/show, with disposed entries removed. There is no cache/coalescing state for a pending first terminal.
- Mechanism confidence: Very high: all callers inspect an empty shared set before an unguarded await and the source creates when no tracked terminal exists.
- Magnitude uncertainty: Overlap frequency depends on user interaction and terminal launch latency, but slow remote starts make duplicate requests realistic.
- Expensive boundaries:
  - filesystem at <code>src/vs/sessions/contrib/terminal/browser/sessionsTerminalContribution.ts \`getChatWindowTerminal\`</code>: Resolve the user home directory when the session has no known cwd; cardinality: Once per show attempt that lacks session cwd, including overlapping attempts; normal sessions with cwd avoid it.
    - Introduced by diff: true; previous behavior: This fallback was not invoked by a chat-window terminal show path.; critical-path effect: Awaited before terminal lookup/creation, so it delays showing terminals.
  - subprocess at <code>src/vs/sessions/contrib/terminal/browser/sessionsTerminalContribution.ts \`\_createTerminalForSession\`</code>: Create a local or agent-host terminal process and renderer; cardinality: Intended as one initial terminal per window, but overlapping shows can each launch one before either is tracked.
    - Introduced by diff: true; previous behavior: No chat-window show operation could race terminal creation for the same window.; critical-path effect: Launch is awaited by each show and dominates slow local/remote startup.
- Verdict: Reportable missing-coalescing regression: overlapping requests can create duplicate subprocesses for one window.

### Scenario 4: Resize a chat window with terminals visible

- Critical path: Every native window layout synchronously lays out the part grid and active editor panes. With terminals visible, the changed code captures terminal height, performs the full grid layout, then performs an unconditional \`resizeCell\` relayout to restore height.
- Scaling input: Window resize event frequency and number/complexity of visible part cells and active editor panes.
- Effective concurrency: Synchronous on the renderer event path; resize events are sequential but can arrive at frame rate. Terminal PTY dimension updates use their existing debouncer, while grid/editor/xterm layout CPU still runs synchronously.
- Cache behavior: No layout-result cache is used. The existing \`\_update\` path compares heights before corrective resizing, but the resize path does not.
- Mechanism confidence: Very high: \`grid.layout\` is immediately followed by \`resizeCell\`, and SplitView.resizeView unconditionally relayouts.
- Magnitude uncertainty: Exact frame loss varies by hardware and pane contents; the duplicate synchronous relayout is guaranteed for width-only resizes with a visible terminal.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminal/browser/terminalInstance.ts \`\_updatePtyDimensions\`</code>: Propagate changed terminal rows/columns/pixel dimensions to the terminal process manager; cardinality: At most the terminal resize debouncer's effective rate; duplicate layouts reevaluate dimensions twice and may collapse to one final process update.
    - Introduced by diff: false; previous behavior: Terminal dimension propagation already existed, but the diff's chat-window grid invokes terminal/editor layout an extra time per resize.; critical-path effect: The synchronous grid/xterm evaluation is on the resize critical path; eventual process resize work follows.
- Verdict: Reportable synchronous UI regression: the added unconditional corrective resize doubles layout work in cases where terminal height did not change.

### Scenario 5: Drag editors or cards to create, move, or merge part-grid cells

- Critical path: Drag start captures cell/card rectangles and overlay state. Retargeting performs an in-memory serialized-grid dry run only when the drop zone changes, then updates transform/clip-based reflow visuals; drop commits once.
- Scaling input: Number of visible grid cells, registered native overlays, and distinct drop-zone transitions during one drag.
- Effective concurrency: Single renderer interaction; hysteresis and candidate-key checks suppress repeated previews while remaining in the same zone.
- Cache behavior: The reflow object caches shown rectangles for the drag lifetime and is disposed/reset after settle or cancellation. Overlay registrations are disposed with their hosts.
- Mechanism confidence: High for synchronous geometry/grid-copy work and suppression behavior.
- Magnitude uncertainty: Large custom part counts could make geometry scans noticeable, but realistic chat-window grids are small and previews are not run on every pointer event.
- Expensive boundaries: none found
- Verdict: No reportable regression: changed-zone gating, transform-based motion, cleanup, and small effective grid cardinality bound the interaction work.

### Scenario 6: Close a chat window or move its chat back to the main window

- Critical path: Closing first releases terminal ownership, closes parts, disposes per-window services/listeners/maps, and closes the auxiliary window. Moving back serializes main-part editor identities, closes the window, waits for the main session/editor restore, then reopens those editors.
- Scaling input: Number of editor groups/editors and terminals owned by the closing window.
- Effective concurrency: One close per window is guarded by closed/closing state. Same-chat reopen is coalesced by the chat-window open service.
- Cache behavior: Window, grid, host, overlay, terminal, and session maps all have explicit removal/disposal paths; terminal instances are intentionally retained by their session after hiding/closing.
- Mechanism confidence: High for cleanup ownership and batching.
- Magnitude uncertainty: Editor close confirmation and restore duration depend on editor types, but no unbounded retained collection was found.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chatWindow/browser/chatWindowService.ts \`ChatWindow.close\`/\`moveToMainWindow\`</code>: Close/focus the auxiliary window and return editor state to the main window; cardinality: One auxiliary-window close per chat window; editor reopening is batched through \`openEditors\`.
    - Introduced by diff: true; previous behavior: The generic part-based chat-window lifecycle did not exist.; critical-path effect: On the explicit move-to-main command's critical path; ordinary unload cleanup is shutdown work.
- Verdict: No additional performance finding: lifecycle cleanup is explicit and editor reopening is grouped rather than per-editor IPC.
