## Findings (1)

### 1. [medium] Skip global scenario registration once the spotlight is shown

**Finding ID:** `PERF-7606F0439786`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/compareAgentsSpotlight.ts:66</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Synchronous CPU work, configuration-schema/default rebuilding, observable trigger subscriptions, and global registry events  
**Scaling:** Each eligible model-picker open performs one global scenario registration and popup disposal performs one deregistration; every mutation rescans all registered onboarding scenarios/descriptors and rebuilds their trigger/configuration state, so cost grows with picker-open frequency and global onboarding scenario count.  
**Outcome:** Increased model-picker open/close latency and avoidable main-thread CPU work  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Opening or closing the model picker did not mutate the global onboarding registry or configuration registry.  
**Changed behavior:** Rendering the Compare Models toggle registers a short-lived global onboarding scenario; closing or rerendering the popup disposes it. This still happens after the one-time scenario has been shown because the constructor only checks the feature setting and current registry membership, while the separate discovered flag is written only when comparison setup starts.  
**Confidence:** 0.97 — The register/dispose event fan-out and synchronous picker call path are directly traced in repository code. The only magnitude uncertainty is the current number of scenarios/listeners and whether Settings UI is open; repetition after dismissal is deterministic because shown state and comparison-discovered state are separate.

**Causal diff evidence:** Added line 66 registers the scenario into the global registry for the rendered button lifetime; the same new object's disposal unregisters it. No equivalent registry mutation existed on picker rendering before this diff.

With the setting enabled, a user who dismisses the introduction with Understood/Escape but does not open comparison setup pays two global registry updates on every later model-picker open. Each update synchronously rebuilds onboarding trigger listeners/evaluation and the developer-mode configuration node, which emits configuration/schema updates on the picker UI path.

**Evidence:** \`onboardingScenarioRegistry.register\` fires \`onDidChange\` synchronously, and its returned disposable fires it again. The onboarding service listener calls \`\_registerTriggerListeners\`, \`\_resolveExperiments\`, and \`\_evaluate\`; the onboarding contribution rebuilds/sorts all scenario descriptors and calls \`configurationRegistry.updateConfigurations\`, which emits schema/default configuration updates; the tryout service also clears and reconstructs its contribution listeners. \`shouldShowNudge\` later suppresses presentation but is only checked after this registration fan-out, and \`SessionComparisonModelSelection.start()\` is the only path that sets the separate discovered storage key.

**Suggested direction:** Before registering, short-circuit on \`onboardingService.hasBeenShown(COMPARE\_AGENTS\_SPOTLIGHT\_ID)\` (while preserving developer-mode semantics if needed), or keep one stable scenario registration and vary only the per-button target. This retains retries before the spotlight is actually shown without rebuilding global onboarding/configuration state on every later picker open.
