# Performance review: tasks: resolve process variables before Windows executable lookup

[PR #345960](https://github.com/microsoft/vscode/pull/345960) at `4c1905effa7dd8e9ea22ef79ea9e80900c0ae4a7`

## Findings (1)

### 1. [medium] Keep unresolved commands out of the first PATH scan

**Finding ID:** `PERF-71E8DA33EE6F`  
**Location:** <code>src/vs/workbench/api/node/extHostTask.ts:185</code> (<code>LEFT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem existence/stat operations across PATH and PATHEXT candidates  
**Scaling:** Per affected launch, the wasted work grows with PATH-entry count times PATHEXT count (plus bare-path checks); it repeats for every variable-driven task and can overlap across parallel dependency tasks.  
**Outcome:** increased task-launch latency and excessive filesystem I/O  
**PR causality:** <code>introduced</code>  
**Previous behavior:** When the extension-host resolver could not expand a process command, the deleted guard returned the placeholder without probing the filesystem; only the later task-system stage needed to look up the acquired command value.  
**Changed behavior:** Windows task variable resolution now performs an extension-host executable search before command/input variables have been acquired, then the changed TerminalTaskSystem path performs the authoritative executable search again after substituting those values.  
**Confidence:** 0.99 — The call path is explicit: TerminalTaskSystem supplies \`resolveSet.process\`, MainThreadTask forwards it to \`$resolveVariables\`, and this changed code awaits \`findExecutable\` on the unresolved text. \`findExecutable\` checks each PATH entry and Windows PATHEXT candidate through filesystem \`exists\`/\`stat\`; the new task-system code and its tests establish a second lookup after variables are resolved. Only exact prevalence and filesystem latency vary.

**Causal diff evidence:** The deleted \`if (/\\$\\{.+?\\}/.test(processName))\` branch at LEFT line 185 was the only guard preventing unresolved \`${command:...}\`/\`${input:...}\` text from reaching \`findExecutable\`; the replacement now calls \`findExecutable(processName, cwd, paths)\` unconditionally.

Launching a variable-driven Windows process task incurs a guaranteed useless PATH scan before the real lookup, increasing launch latency and filesystem I/O; parallel task dependencies can multiply the probes, and remote or slow filesystems make the delay more visible.

**Evidence:** For a Windows process task whose command is \`${input:tool}\` or \`${command:tool}\`, the extension-host resolver leaves that token unresolved. With the guard removed, \`src/vs/base/node/processes.ts:86-133\` walks PATH and checks each PATHEXT candidate for that literal, even though no such executable can be selected. After interaction, \`\_resolveAndFindExecutable\` at \`terminalTaskSystem.ts:694-707\` calls \`taskSystemInfo.findExecutable\` again with the real value. Both awaits are on the task-launch critical path.

**Suggested direction:** Restore the unresolved-placeholder guard in \`$resolveVariables\` (or otherwise skip this first executable lookup when variables remain) and leave executable discovery to the post-acquisition \`\_resolveAndFindExecutable\` call.
