# Performance review: chat: add accessible previews for inline GitHub references

[PR #345729](https://github.com/microsoft/vscode/pull/345729) at `e6418479b151298b0c46f1e226b54526af1d6c84`

## Findings (1)

### 1. [medium] Defer GitHub resolution until the delayed preview is shown

**Finding ID:** `PERF-79108B586711`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInlineAttachments.ts:1333</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** GitHub client acquisitions and issue/PR refresh network requests (including PR checks)  
**Scaling:** On a cold cache, each distinct reference crossed by the pointer or arrow keys starts one interactive resolution; rapidly traversing N references can therefore start N independent requests, and interactive resolutions bypass the resolver's three-request prefetch limiter.  
**Outcome:** Excess network traffic and request bursts, with avoidable authentication/client work and GitHub API pressure for previews that never become visible.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Inline GitHub pills had no detail-preview resolution path, so merely moving the pointer or cursor across them did not acquire a GitHub client or refresh issue/PR data.  
**Changed behavior:** \_showPillPreview calls getHoverContent synchronously before passing the resulting element to showDelayedHover. The content factory immediately renders CachedChatPillHover, whose cold render invokes resolver.resolveIssue/resolvePullRequest, while HoverService only waits for workbench.hover.delay after the hover widget has already been created.  
**Confidence:** 0.98 — The call chain from the changed synchronous getHoverContent call through CachedChatPillHover.\_render to concrete GitHub subscription.refresh operations is direct. The only magnitude uncertainty is how many cold references users traverse before the delay, not whether those requests start early.

**Causal diff evidence:** The added call at RIGHT line 1333 constructs/resolves preview content synchronously on pointer/keyboard activation, before the added showDelayedHover call later in the same method can enforce the configured delay.

With the default 500–1500 ms delay, a user can leave a cold reference before any card is shown yet still trigger its GitHub request. Arrowing or sweeping across several references can launch a burst of interactive API work even though all pending previews are cancelled visually.

**Evidence:** At the changed line, pill.getHoverContent() runs before showDelayedHover. DefaultChatAttachmentWidget.getPreviewHoverContent calls content(), and CachedChatPillHover.\_render starts provider.resolve whenever the cache is cold. That reaches GitHubResourceDetailsResolver.\_resolveIssue/\_resolvePullRequest, which acquires the default account client and calls subscription.refresh; pull requests may also refresh checks. HoverService applies the configured delay only after \_createHover returns, and clearing the hover does not abort these requests because retain() keeps every reference target cached.

**Suggested direction:** Keep cold content creation side-effect free until onDidShow (or add a delayed-hover content factory that is evaluated only after the timer). Start/promote resolution only when the preview actually becomes visible, while preserving the existing resolver coalescing and bounded prefetch behavior.
