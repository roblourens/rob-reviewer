**Relevant issue families:** boundary-fanout, concurrency-burst, repeated-work, serialization-allocation, missing-coalescing

### Scenario 1: Launch a local Copilot Agent Host client with a configured policy helper

- Critical path: Renderer configuration is mirrored to the local Agent Host, then client acquisition snapshots the normalized helper, serializes it into the subprocess environment, loads certificates/runtime paths, and starts the Copilot runtime before chat work can proceed.
- Scaling input: Normally one helper registration with a short path and argument list; subprocess cardinality follows existing shared/scoped client ownership, not the argument count.
- Effective concurrency: Shared client startup is coalesced by \_clientStarting/\_ensureClientHealing. Scoped clients remain isolated per credential-bearing chat and can start independently, as before.
- Cache behavior: Startup configuration is snapshotted per client; equivalent normalized registrations compare equal and reuse the running client. Runtime paths/certificates follow existing startup caches and reads.
- Mechanism confidence: High confidence in the IPC and runtime startup call path; insufficient evidence that the small added serialization/environment work causes measurable degradation.
- Magnitude uncertainty: The runtime's helper invocation cost and frequency are unavailable in this repository, so no regression can be inferred from enabling the explicitly requested integration.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:\_forwardClientConfig</code>: Dispatch the full mirrored root-configuration patch to the Agent Host on connect or reconnect.; cardinality: One root-config action per client connect/reconnect; the policy-helper value is one field in the existing grouped patch.
    - Introduced by diff: true; previous behavior: The grouped configuration IPC already occurred, but it did not include a policy-helper field.; critical-path effect: On initial connection it supplies startup state before the runtime is acquired; reconnect dispatch is asynchronous protocol work.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_ensureClientOnce</code>: Start the Copilot runtime with COPILOT\_CLI\_POLICY\_HELPER and the POLICY\_HELPER feature flag.; cardinality: One runtime start for the shared client; scoped credential clients each retain their existing one-client-per-chat ownership.
    - Introduced by diff: false; previous behavior: The same runtime subprocess was started; this diff only adds one environment value and feature flag when explicitly configured.; critical-path effect: Runtime startup is on first chat/client acquisition's critical path; the added environment manipulation is constant-size for normal helper arguments.
  - subprocess at <code>Copilot runtime policy-helper integration configured by src/vs/platform/agentHost/node/copilot/copilotAgent.ts:4341</code>: The external policy helper may be executed by the runtime when policy is resolved.; cardinality: Runtime-defined and not established by repository code; enabled only when the user/extension explicitly configures a helper.
    - Introduced by diff: true; previous behavior: VS Code did not opt the runtime into the configured external policy helper.; critical-path effect: Potentially part of runtime policy resolution, but invocation frequency and scheduling are outside the reviewed diff.
- Verdict: No reportable regression. The expensive runtime boundary already exists on client acquisition, and execution of the configured helper is opt-in required behavior whose frequency is not proven here.

### Scenario 2: Add, change, or remove the policy-helper registration while shared chats are active or idle

- Critical path: A configuration change crosses one IPC root-config action, startup snapshots are compared, and an effective change requests one shared-client restart. Busy turns, subagents, and credential updates finish first; the next client use pays runtime startup.
- Scaling input: Cost is constant per batch of effective helper changes before the idle boundary, independent of chat count for the shared client.
- Effective concurrency: Pending shared restart reasons are stored in a Set and drained once. Active turns/subagents and credential updates gate teardown, preventing overlapping shared restarts.
- Cache behavior: The normalized path/args are serialized deterministically; omitted args become \[\], so semantically equivalent objects hit the equality check. Removal normalizes to undefined after transport.
- Mechanism confidence: High confidence that an effective change causes one deferred shared-runtime restart and equivalent writes do not.
- Magnitude uncertainty: Runtime startup duration varies by certificates, runtime path resolution, and environment, but the restart is required to change startup-only environment and is bounded/coalesced.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:onDidChangeConfiguration</code>: Send the transformed helper registration or empty-path removal object to the local Agent Host.; cardinality: One action per effective application-setting change; unrelated configuration events are filtered by affectsConfiguration.
    - Introduced by diff: true; previous behavior: Policy-helper setting changes had no mirrored action.; critical-path effect: Triggers host-side comparison; it does not block an already active turn.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_applyPendingClientRestart</code>: Stop the shared Copilot client and start a replacement lazily after configuration changes.; cardinality: At most one shared restart for coalesced pending reasons once all live work is idle; repeated equivalent normalized values cause zero restarts.
    - Introduced by diff: true; previous behavior: Policy-helper changes did not restart the runtime; other startup-baked settings already used this restart flow.; critical-path effect: Deferred off active turns, but the next operation requiring the client pays replacement startup latency.
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_applyPendingClientRestart</code>: Schedule model-catalog refresh after stopping the old runtime.; cardinality: One scheduled refresh per applied shared-client restart, using the existing refresh coalescing path.
    - Introduced by diff: true; previous behavior: No restart/model refresh occurred for policy-helper setting changes.; critical-path effect: Off the stop path via a fire-and-forget schedule; last-known models remain published while it runs.
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_ensureClientOnce</code>: Reload certificates, resolve runtime paths, and potentially write the user-data certificate file during replacement startup.; cardinality: Once per replacement client startup under the existing startup logic.
    - Introduced by diff: false; previous behavior: These operations already accompanied every runtime restart; the diff adds policy-helper changes as a deliberate restart trigger.; critical-path effect: Part of replacement startup paid on next client acquisition.
- Verdict: No reportable regression. The expensive work is bounded, coalesced, deferred away from active work, and necessary to apply a startup-only value.

### Scenario 3: Use credential-scoped chats after a policy-helper change

- Critical path: Each scoped chat checks its client's captured startup snapshot at its next idle credential boundary. A stale scoped client/session is stopped and replaced before that chat sends through the updated runtime.
- Scaling input: Number of distinct credential-scoped chats used after the effective setting change, not total stored chats or messages.
- Effective concurrency: Each chat owns a scoped client; replacements are serialized by that chat's boundary but independent chats can replace concurrently. No new global limiter is added, though the setting is expected to change rarely and inactive chats do no work.
- Cache behavior: Each scoped client stores its startup snapshot; once replaced it is warm for subsequent sends until another effective startup configuration change. Equivalent helper values do not mark it stale.
- Mechanism confidence: High confidence in lazy per-scoped-client replacement; low confidence that realistic usage produces a harmful burst rather than a small, required set of replacements.
- Magnitude uncertainty: The repository does not establish a realistically large number of concurrently active credential-scoped chats or frequent helper changes; the observed mechanism is bounded to used chats.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_applyChatCredentialBoundary</code>: Stop and replace a stale credential-scoped Copilot runtime, then resume/recreate the chat session.; cardinality: At most one replacement for each scoped chat actually used after the change; effective cardinality is the number of distinct credential-scoped chats subsequently activated.
    - Introduced by diff: true; previous behavior: A helper change did not stale scoped snapshots; existing startup-config changes already used the same lazy replacement mechanism.; critical-path effect: Replacement is on that chat's next-send critical path, but never interrupts an active turn or subagent.
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_ensureClientOnce</code>: Perform existing certificate and runtime-path startup work for each replacement scoped client.; cardinality: Once per activated stale scoped client.
    - Introduced by diff: false; previous behavior: The work already occurred whenever a scoped client was created or replaced.; critical-path effect: Blocks each affected chat's replacement startup.
- Verdict: No reportable regression. Multiplicity follows existing security isolation, inactive clients are not eagerly restarted, and evidence does not establish a realistic harmful concurrency burst.

**Summary:** Reviewed all eight changed files and traced configuration mirroring, normalization/serialization, shared restart coalescing, scoped-client refresh, runtime startup, filesystem/certificate work, model-refresh networking, and the opt-in helper subprocess boundary. No high-confidence actionable performance regression was introduced.
