## Findings (1)

### 1. [medium] Batch fallback agent-file reads during discovery

**Finding ID:** `PERF-AB3D6B7A4A25`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:610</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem reads and frontmatter parsing CPU  
**Scaling:** For N non-builtin agents whose discovery response omits reasoningEffort, discovery now performs N file reads serially because each await is inside the loop; plugin agents may also be read again by parsePlugin/readAgentComponents later in the same discovery.  
**Outcome:** Increased customization/session initialization latency and slower refreshes, especially with many agents or slow/network-mounted filesystems.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** discoverAgents awaited the single agents.discover RPC and projected its result without reading each agent file; plugin parsing remained the only file-parse path for plugin agents.  
**Changed behavior:** Each non-builtin agent missing reasoningEffort now blocks the loop on parseAgentFile, which calls IFileService.readFile and parses the full frontmatter before the next agent is processed.  
**Confidence:** 0.99 — The new read, its placement inside the loop, and the awaited session-publication call path are explicit. Runtime omission is both the stated compatibility case and covered by the added test. Exact delay varies with agent count and filesystem latency, which affects severity rather than mechanism confidence.

**Causal diff evidence:** The added expression \`agent.reasoningEffort ?? (await parseAgentFile(uri, this.\_fileService)).reasoningEffort\` at line 610 introduces the per-agent read and serial await; the deleted implementation had no filesystem operation in this loop.

Creating a session for a new anchor waits through getCustomizationsSettled -&gt; SessionDiscoveredEntry.whenSettled -&gt; discover, so an older runtime that omits this field adds one serialized filesystem round trip per discovered agent before customizations can be published. Watched customization changes repeat the same fan-out after the 100 ms debounce.

**Evidence:** SessionCustomizationDiscovery.discover awaits discoverAgents in its discovery Promise.all. discoverAgents loops the runtime result and the changed line awaits parseAgentFile for every missing value. parseAgentFile immediately awaits fileService.readFile. SessionDiscoveredEntry.\_refresh awaits discover, while SessionPluginController.getCustomizationsSettled/getAppliedCustomizations await the entry's whenSettled before session publication/application. toPluginCustomizations subsequently calls parsePlugin, whose readAgentComponents reads plugin agent files again.

**Suggested direction:** Collect agents first and resolve all missing-effort fallbacks concurrently with a bounded/shared parse pass (for example, Promise.all over missing entries, reusing plugin parse results where applicable), then preserve result order when projecting them. Cache by URI/etag across refreshes if reads cannot be shared.
