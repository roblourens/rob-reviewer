**Relevant issue families:** serialization-allocation, repeated-work, eager-work, synchronous-ui-work

### Scenario 1: Agent Host executes the forwarded client semantic tool search and publishes its completed title/details

- Critical path: A model tool-search call must cross the existing Agent Host-to-workbench client-tool path, invoke the existing embedding search, and return before the agent can use matched tools. The diff adds only bounded title formatting and attaches disclosure metadata after the result is available; neither adds a new blocking boundary.
- Scaling input: Number of model-issued searches and deferred candidate tools. Display metadata scales with the raw query plus the matched-name result, normally bounded to five names by DEFAULT\_SEARCH\_LIMIT; candidates are not copied into rawInput/toolSpecificData.
- Effective concurrency: Each invocation awaits its own existing toolsService/embedding call. The diff adds no fan-out, limiter change, or new concurrent work.
- Cache behavior: Existing embedding profiles and tool embeddings retain their prior initialization/cache behavior. New title/detail formatting is uncached local work and does not alter positive, negative, or coalescing behavior.
- Mechanism confidence: High: the execution path, default result bound, and completion metadata assignment are directly visible in the changed and transitive code.
- Magnitude uncertainty: A model could issue several searches in a long turn, but each added formatting/detail operation remains per search and small relative to the existing embedding operation.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:\_setupClientToolCall</code>: Dispatch tool-ready/completion actions between Agent Host and the workbench/client-tool owner; cardinality: One ready/invocation/completion sequence per model-issued tool-search call; the candidate corpus is grouped into that single call.
    - Introduced by diff: false; previous behavior: The same client-tool actions crossed the boundary, but completion did not additionally expose the raw query and matched-name output as simple invocation details.; critical-path effect: Existing critical-path transport for executing the client tool; the added metadata is attached to the existing completion.
  - other expensive boundary at <code>extensions/copilot/src/extension/tools/node/toolSearchTool.ts:ToolSearchTool.invoke</code>: Compute one query embedding and rank the complete deferred-tool corpus; cardinality: One embedding search per tool-search invocation, over the grouped candidate corpus; normal output defaults to at most five matched names.
    - Introduced by diff: false; previous behavior: The identical embedding search and grouped candidate processing already occurred; the diff only adds prepared/completed messages.; critical-path effect: Must complete before matched tools are returned to the agent.
- Verdict: No reportable regression. The diff does not add or amplify the expensive embedding/IPC boundary, and the added retained/serialized data excludes the potentially large candidate corpus.

### Scenario 2: Native/runtime tool-search completion is formatted for live sessions and restored session history

- Critical path: On completion or replay, Agent Host extracts the already-available result text, parses a JSON string once to count names, and builds the title before publishing the tool-call state. No subprocess, filesystem, database, network, or new IPC call is introduced by this formatting.
- Scaling input: Tool-search result text length and number of completed/replayed searches. Parsing is linear in one result per completion; result cardinality is the matched tool list rather than the full candidate corpus.
- Effective concurrency: Formatting is synchronous within each completion/replay mapping; there is no changed parallelism or burst scheduling.
- Cache behavior: No cache is involved or defeated. Live and replay paths independently format their one completion as required.
- Mechanism confidence: High for one-time parsing placement and lack of boundaries; moderate for the maximum provider-native result size.
- Magnitude uncertainty: Provider-native output size is not explicitly capped in the inspected code, but tool-search outputs are tool-name lists and parsing occurs once rather than on render frames or repeated events.
- Expensive boundaries: none found
- Verdict: No reportable regression. The new JSON parse is one-time, local, and tied to a realistically bounded tool-name result rather than a hot UI loop.

### Scenario 3: Chat renders, persists, restores, and optionally expands completed tool-search disclosure details

- Critical path: Collapsed chat rendering creates only the title/disclosure shell. Input/output code models, editors, resize observation, and geometry reads are initialized lazily only when the user expands the disclosure, so they are off the default render/scroll critical path.
- Scaling input: Number of retained tool-search calls in chat history. Added data scales with each raw query and matched-name output; normal client-search output defaults to five names and does not retain candidate descriptions.
- Effective concurrency: Rendering follows the existing virtualized chat renderer. Disclosure content is created only on user expansion; no new parallel rendering or editor creation burst occurs for collapsed history.
- Cache behavior: Expanded state is remembered per invocation in the existing WeakMap. Restored records carry the new details, while editor/model allocation remains lazy and is disposed with the content part.
- Mechanism confidence: High: serialization includes toolSpecificData, while ChatCollapsibleInputOutputContentPart explicitly gates createMessageContents on first expansion.
- Magnitude uncertainty: Very long histories can contain many searches, but added bytes per normal client search are small and editor allocation is user-triggered rather than eager.
- Expensive boundaries:
  - database at <code>src/vs/workbench/contrib/chat/common/model/chatProgressTypes/chatToolInvocation.ts:ChatToolInvocation.toJSON</code>: Persist and restore serialized chat/tool invocation state through the existing chat history storage path; cardinality: One serialized invocation per completed search; the diff adds one query string and one matched-name JSON string to the existing record without adding a storage operation.
    - Introduced by diff: false; previous behavior: The invocation was already serialized and restored, but without simpleToolInvocation input/output fields for this client tool search.; critical-path effect: Existing persistence/restore work; the added bounded fields slightly increase payload bytes but do not add a new call or fan-out.
- Verdict: No reportable regression. Retention and serialized payload growth are bounded per search, and the potentially heavier UI/editor work stays lazy.

### Scenario 4: Chat tool rows resolve the tool-search icon during live rendering and history scrolling

- Critical path: The existing icon helper lowercases the tool ID and now performs a constant-size set of string comparisons before returning Codicon.tools. There are no transitive subprocess, IPC, filesystem, database, or network calls.
- Scaling input: Number of visible/rendered tool rows; added work is constant per icon lookup and independent of tool corpus or result size.
- Effective concurrency: Synchronous rendering on the UI thread, unchanged from prior icon resolution; no scheduling or concurrency changes.
- Cache behavior: No cache is involved. The returned codicon is a shared static value.
- Mechanism confidence: High: the changed helper is directly local and returns before all later icon inference branches for recognized tool-search IDs.
- Magnitude uncertainty: Chat histories may have many rows, but virtualization limits visible rendering and the added constant comparisons are negligible.
- Expensive boundaries: none found
- Verdict: No reportable regression. The change reduces downstream icon inference for matching IDs and adds only constant-time comparisons.
