# Performance review: Fix backslash escaping in MarkdownString.appendLink

[PR #345591](https://github.com/microsoft/vscode/pull/345591) at `d97bee44f78bcba0db76a6b4c4c7d44a87290baa`

## Findings (1)

### 1. [high] Avoid quadratic backtracking in link escaping

**Finding ID:** `PERF-2B5147E366B2`  
**Location:** <code>src/vs/base/common/htmlContent.ts:109</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** regular-expression matching and backtracking CPU work on the renderer/UI thread  
**Scaling:** For maximum consecutive backslash-run length k not immediately followed by the escaped delimiter, matching grows as O(k^2); total refresh cost sums this work across all detected links.  
**Outcome:** quadratic CPU growth and blocked UI-thread latency during link-decoration refresh  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous \`new RegExp(delimiter, 'g')\` scanned each target linearly and invoked the replacement only for actual delimiters, so non-delimiter backslash runs did not trigger repeated suffix scans.  
**Changed behavior:** Escaping now searches for every possible start of a backslash run and greedily consumes the remaining run before testing for a delimiter or end-of-string.  
**Confidence:** 0.98 — The regex backtracking behavior and synchronous call path are explicit. The built-in link computer accepts backslashes in detected URLs, decoration creation eagerly calls appendLink for every returned link, and models up to 50 MB are eligible. Only the prevalence and exact stall duration of very long runs are uncertain.

**Causal diff evidence:** RIGHT line 109 replaces the prior delimiter-only global regex with \`(\\\\\*)(delimiter\|$)\`, introducing a greedy backslash quantifier before an alternative that commonly fails.

Opening or editing a generated or crafted document containing an auto-detected URL with a long backslash run can block the editor UI while link decorations are installed; a single sufficiently long run can cause seconds of CPU work rather than scaling with document length.

**Evidence:** For a URL segment containing k consecutive backslashes followed by an ordinary character, \`\\\\\*\` first consumes all k characters, \`(delimiter\|$)\` fails, and the engine backtracks across the run. The unanchored global search then retries at the next backslash, doing k+(k-1)+... work. \`LinkDetector.updateDecorations\` synchronously calls \`LinkOccurrence.decoration\` -&gt; \`getHoverMessage\` -&gt; \`MarkdownString.appendLink\` for every detected link after providers return; the default link computer treats backslash as a valid in-link character.

**Suggested direction:** Implement the parity handling as a single forward scan, or match non-overlapping backslash runs and delimiters without retrying every suffix, preserving odd/even and trailing-run semantics in O(value.length).
