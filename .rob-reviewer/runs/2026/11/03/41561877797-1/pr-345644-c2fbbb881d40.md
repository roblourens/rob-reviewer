### Scenario 2: Opening and closing an auxiliary editor/chat window in the Agents workbench

- Critical path: The pre-existing auxiliary-window service creates and registers the window, then synchronously fires onDidOpenAuxiliaryWindow before open() returns. The diff adds an onDidAddContainer notification on that path; current consumers perform a fixed number of class/attribute updates and register per-window DOM listeners. Closing the window disposes the parent event store, nested container store, timeout, and listeners.
- Scaling input: One notification per auxiliary window open; retained listeners and one idle timer scale linearly with concurrently open windows, the intended ownership model. Current event fan-out is a small fixed set of consumers, not per editor or per DOM row.
- Effective concurrency: Window opens are not burst-scheduled by this change. Each synchronous event completes during its own open path; each open window owns at most one sash idle timeout.
- Cache behavior: No cache is involved. Existing windows are discovered through layoutService.containers by late-created contributions, while future windows are delivered once by the event, avoiding duplicate registration.
- Mechanism confidence: High: event firing order, all repository onDidAddContainer consumers, and disposal ownership were inspected.
- Magnitude uncertainty: The exact cost of fixed consumer DOM updates depends on enabled contributions, but cardinality is one per opened window and no collection-wide relayout or external call is reached by the event handlers.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/workbench/services/auxiliaryWindow/browser/auxiliaryWindowService.ts BrowserAuxiliaryWindowService.open/openWindow</code>: Create/open an auxiliary browser or native window; cardinality: One pre-existing window-open operation per user-requested auxiliary window; the changed event does not add or repeat it.
    - Introduced by diff: false; previous behavior: The Agents workbench used the same auxiliary-window creation path but did not notify ILayoutService consumers about the new container.; critical-path effect: Window creation remains the dominant pre-existing boundary before the open promise resolves; the changed fixed DOM/listener setup runs after creation and before return.
- Verdict: No reportable regression: fixed per-window bookkeeping is required for correct tracking, is cleaned up on close, and does not amplify the existing window-open boundary.

### Scenario 3: Mouse activity and two-second idle transitions independently hide sash grippers in each main or auxiliary window

- Critical path: A distinct mouse position clears/replaces one timeout and removes one container attribute; idle expiry sets the attribute. CSS invalidation is scoped to .monaco-sash descendants in that window. Repeated identical webview coordinates are deduplicated. No external boundary lies on the input or timer path.
- Scaling input: JavaScript work is O(1) per distinct mouse event per window; selector matching/style updates scale with the sashes in only that container. At most one timeout is live per tracked window.
- Effective concurrency: Independent windows can each have one pending timer; events are serialized on their window event loops and no unbounded tasks are queued.
- Cache behavior: No cache is involved. lastMousePosition serves as per-window event deduplication and remains unchanged.
- Mechanism confidence: High: mouse listener, timeout replacement, attribute mutation, CSS selector scope, and class-only auxiliary mirroring were directly traced.
- Magnitude uncertainty: Browser style invalidation cost varies with sash count, but the selector scope and mutation frequency are equivalent to the prior class-based rule and avoid mirroring the main window's idle mutation into auxiliary containers.
- Expensive boundaries: none found
- Verdict: No regression: class-to-attribute replacement preserves local style work and can reduce cross-window invalidation by preventing idle state mirroring.
