# Performance review: TypeScript: resolve Node from PATH when detecting the TS Server Node

[PR #345587](https://github.com/microsoft/vscode/pull/345587) at `2989b1caa2b28107e44b8e6325a2f93d88ba515e`

## Findings (1)

### 1. [medium] Cache the synchronous PATH resolution across configuration loads

**Finding ID:** `PERF-4B73ECD98E39`  
**Location:** <code>extensions/typescript-language-features/src/utils/findExecutable.electron.ts:39</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** synchronous filesystem metadata/access calls for every eligible PATH candidate  
**Scaling:** Each service-configuration load performs up to two synchronous probes per absolute Windows PATH entry before the first match (and one stat plus one access check per viable POSIX entry); the full scan repeats on initial JS/TS client creation and on every workspace configuration event, and can run twice when both workspace and global Node settings are \`node\`.  
**Outcome:** blocked extension-host critical path and increased IntelliSense/configuration-change latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** For a \`node\` setting, configuration loading directly called the existing \`execFileSync('node', ...)\`; it did not first issue a JavaScript-level synchronous filesystem probe for every PATH candidate.  
**Changed behavior:** The new loop invokes \`isExecutableFile\` for every \`.com\`/\`.exe\` candidate until a match, and the default implementation uses synchronous \`statSync\`/\`accessSync\`. \`loadFromWorkspace\` reaches this on first supported-document activation and its unfiltered \`onDidChangeConfiguration\` listener reaches it again for every configuration change.  
**Confidence:** 0.94 — The added synchronous I/O, loop cardinality, and activation/reconfiguration call paths are explicit in the code. Exact duration depends on PATH ordering and filesystem/network responsiveness, which affects severity rather than the mechanism.

**Causal diff evidence:** Added line 39 places \`isExecutableFile(candidate)\` inside nested PATH-entry/extension loops; this entire filesystem search is new and executes before the pre-existing \`execFileSync\` Node detection.

Users who configure the TS server Node as \`node\` now block the extension host while PATH is scanned before TS Server setup. Long PATHs amplify the added I/O, and an absolute UNC/network entry before Node can make each synchronous probe slow, delaying initial IntelliSense and unrelated settings changes.

**Evidence:** \`findExecutableOnPath\` loops over every absolute PATH entry and calls \`isExecutableFile(candidate)\` here; the default at lines 60-64 performs synchronous filesystem calls. \`ElectronServiceConfigurationProvider.findNodePath\` calls this helper synchronously, \`BaseServiceConfigurationProvider.loadFromWorkspace\` reads both local/global Node paths, and \`TypeScriptServiceClient\` calls that loader in its constructor (line 186) and its broad configuration-change callback (lines 212-214). There is no result cache or coalescing.

**Suggested direction:** Cache positive and negative resolutions keyed by the effective PATH value, platform, and executable name (or cache them in the provider while that key is unchanged), so configuration reloads and local/global reads reuse one scan while still rerunning the existing workspace-sensitive Node process check.
