# Performance review: chat: open Copilot CLI sessions from product protocol links

## Findings (2)

### 1. [medium] Keep ordinary session imports lazy

**Finding ID:** `PERF-521D67E8409E`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:2432</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Copilot runtime initialization, SDK subprocess/RPC work, filesystem metadata reads, plugin/customization snapshots, shell/session objects, and retained live runtime memory  
**Scaling:** The existing Sessions view accepts multi-selection and imports sessions sequentially; this new hook starts one runtime per selected Copilot session, so command latency and initialization work grow linearly with the number imported, while up to the 10-session residency limit can remain live.  
**Outcome:** The Import command is blocked on heavyweight runtime starts and incurs unnecessary CPU/I/O and retained memory for sessions the user may never open or message.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, importSession restored host/catalog state and adopted the external session only. CopilotAgent.materializeChat explicitly records the backing so it "can be resumed lazily on its first send," avoiding a live runtime during a list-only import.  
**Changed behavior:** Importing an external Copilot session now resumes and initializes its runtime immediately to read modes/model/agent, even for the pre-existing Sessions-view Import action.  
**Confidence:** 0.99 — The shared call path, the existing multi-select sequential caller, the explicit lazy-resume comment, and the runtime initialization implementation are all directly traced. Exact startup duration varies by plugins/workspace, which affects magnitude rather than mechanism.

**Causal diff evidence:** The added call at agentService.ts:2432 invokes provider.importChat for every import. CopilotAgent.importChat then calls \_ensureResolvedChatSession, which reaches \_resumeSession/\_resumeSessionOnce and initializes/registers a live CopilotAgentSession before importSession returns.

Selecting one or several external Copilot sessions and choosing Import now makes the UI command wait for one full runtime resume per session and can leave several heavyweight runtimes resident, even though Import only changes list ownership and does not open a chat.

**Evidence:** SessionsView Import accepts ISession\[\] and loops over each selected session, awaiting SessionsManagementService.importSession and BaseAgentHostSessionsProvider.importSession. The changed AgentService path invokes CopilotAgent.importChat; its \_ensureResolvedChatSession resumes the SDK session, and \_resumeSessionOnce performs client acquisition, metadata/filesystem reads, customization/plugin snapshot creation, ShellManager creation, and \_initializeAndRegisterSession. AgentSessionResidency retains up to 10 resident sessions, so this is not just transient metadata work.

**Suggested direction:** Keep the generic Sessions-view import metadata-only. Gate provider.importChat/runtime-state adoption behind an explicit option used by the CLI deeplink, or defer runtime mode/selection adoption until the chat is actually opened/first used so bulk imports remain lazy.

### 2. [medium] Look up the named CLI session without listing the full catalog

**Finding ID:** `PERF-2A01A9B283DA`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5171</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** SDK subprocess IPC response bytes, serialized/deserialized session metadata objects, and catalog filtering/allocation  
**Scaling:** Each explicit import of an unregistered session transfers and filters O(N) metadata for every saved SDK session to locate one ID; repository tests explicitly exercise catalogs of 5,000 sessions, while the effective requested cardinality is one.  
**Outcome:** Opening a Copilot CLI deeplink can suffer avoidable latency and CPU/GC pressure proportional to total session history, and on cold start this full listing can overlap the normal startup discovery listing.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Existing imports operate on sessions already present in the registry/list and did not add this catalog scan. The provider already uses client.getSessionMetadata(sessionId) elsewhere for exact per-session reads, including getChatMetadata and resume.  
**Changed behavior:** An import that names one unseen CLI session now performs a full SDK catalog RPC and materializes all session metadata before selecting the requested session.  
**Confidence:** 0.98 — The one-ID input, full-list boundary, post-RPC filter, exact alternative API, critical-path caller, and large catalog cardinality are directly visible. Actual milliseconds depend on SDK storage and machine speed.

**Causal diff evidence:** The new discoverChat path sets a one-element sessionIds set but calls \_discoverCopilotChats, whose added explicit-import branch still executes client.rpc.sessions.list({ source: 'local' }) at copilotAgent.ts:5171 and only filters the returned catalog afterward.

Users with long Copilot histories pay a full-catalog IPC/serialization cost on the critical path from a \`/code\` link to the Chat view, even though the link already supplies the exact session ID.

**Evidence:** \_registerSessionForImport invokes discoverChat only on a registry miss. discoverChat passes exactly one session ID, but \_discoverCopilotChats lists the complete local catalog and applies catalog.filter afterward. Tests in this file model 5,000 saved sessions, establishing realistic large-history scaling. The same implementation already uses client.getSessionMetadata(sessionId), proving a bounded SDK API exists.

**Suggested direction:** Implement explicit discovery with client.getSessionMetadata(sessionId) and classify that single result, or coalesce with an already-running startup discovery scan; preserve the same eligibility checks without transferring the full catalog.

### Scenario 4: Import while the Copilot CLI still holds the session

- Critical path: After restore, import checks lock state immediately and every 250 ms for up to five seconds. If still held it returns Conflict; the renderer prompts, and confirmed takeover retries import with one lock check before runtime resume/open.
- Scaling input: One held session, fixed maximum 21 serial checks on first attempt and one on takeover retry.
- Effective concurrency: Deliberately serial polling with no burst; takeover retry repeats restore/import entry but warm state makes restore mostly a no-op.
- Cache behavior: No lock-result cache, appropriately, because lock state must become current. Session registration/restore are warm on retry.
- Mechanism confidence: High.
- Magnitude uncertainty: How often CLI teardown takes long enough to poll is unknown; maximum delay and call count are fixed and tested.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5024</code>: Repeated SDK \`sessions.checkInUse\` calls.; cardinality: Up to 21 over five seconds, plus one if takeover is confirmed.
    - Introduced by diff: true; previous behavior: No lock safety check or wait existed.; critical-path effect: Adds a bounded intentional handoff wait before prompting/opening.
- Verdict: No separate finding: the bounded delay is an explicit one-writer correctness tradeoff and avoids immediately prompting during normal CLI exit.
