<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** serialization-allocation, boundary-fanout

### Scenario 1: Restricted engine snapshot telemetry (\`engine.messages\` and \`engine.messages.length\`) emitted during a Copilot model call

- Critical path: The SDK telemetry callback launches \`\_routeGitHubTelemetry\`; for a restricted target it resolves the account context, constructs properties, awaits \`multiplexProperties\`, then schedules the enabled telemetry sink(s). Context resolution and gzip, when needed, must finish before routing reaches the send call; the sender's network delivery is fire-and-forget and therefore off the callback's completion critical path. The changed \`isEngineSnapshot\` check is constant-time and removes only the fallback \`modelCallId\` property when the native pairing ID is absent.
- Scaling input: Work scales with the number of SDK engine snapshot notifications and the byte length of their telemetry properties. Effective sink cardinality remains one enhanced event per admitted snapshot, plus one internal event only for \`engine.messages.length\` when internal. The new comparison remains O(1) per event and does not scale with message contents.
- Effective concurrency: SDK notifications can invoke independent async routes concurrently. Same-token cold account discovery is coalesced by the per-token client promise; warm calls reuse it. Large-property gzip jobs and fire-and-forget telemetry POSTs may overlap across events, as before. There is one enhanced-GH send for an admitted \`engine.messages\` event and, for an internal opted-in user, one enhanced-GH plus one internal appender send for \`engine.messages.length\`; the diff does not alter this cardinality or concurrency.
- Cache behavior: Restricted telemetry context uses a per-token cached/coalesced entry: the first event can wait for discovery, concurrent cold requests share it, and warm events avoid discovery. The changed engine-name classification has no cache and does not change cache keys, misses, invalidation, or negative behavior.
- Mechanism confidence: High: the complete changed production hunk and its transitive router, compressor, account cache, enhanced sender, and internal sender paths show unchanged expensive work and boundary cardinality.
- Magnitude uncertainty: Actual engine snapshot frequency and payload sizes vary by model call, but the diff neither increases event count nor payload processing; it omits one short property in the missing-pairing-ID case.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_routeGitHubTelemetry and src/vs/platform/agentHost/node/shared/copilotApiService.ts:resolveRestrictedTelemetryContext</code>: Resolve \`/copilot\_internal/user\` account and telemetry policy on a cold token; cardinality: At most one coalesced discovery for concurrent calls sharing a token; subsequent events use the cached per-token entry until invalidation.
    - Introduced by diff: false; previous behavior: The same context resolution occurred before this PR for every restricted target route, backed by the same coalesced cache.; critical-path effect: Cold discovery blocks routing of the event; warm lookup does not perform network I/O.
  - serialization at <code>src/vs/platform/agentHost/node/agentHostGitHubTelemetryRouter.ts:route and src/vs/platform/agentHost/node/agentHostRestrictedTelemetry.ts:multiplexProperties/\_post</code>: Copy properties, gzip always-compressed or oversized string values, chunk them, and JSON-serialize the envelope; cardinality: Once per source event before sinks; the multiplexed object is shared by both sinks. Cost scales with telemetry property bytes, especially \`messagesJson\`.
    - Introduced by diff: false; previous behavior: The same full property multiplexing and envelope serialization occurred; pre-diff engine snapshots missing a pairing ID additionally carried the short SDK fallback ID.; critical-path effect: Property multiplexing is awaited before sink dispatch; envelope serialization is synchronous in the send call. Removing one short fallback ID for engine snapshots slightly reduces, rather than increases, bytes and allocation.
  - network at <code>src/vs/platform/agentHost/node/agentHostRestrictedTelemetry.ts:AgentHostRestrictedTelemetrySender.\_post</code>: POST one Application Insights envelope to the enhanced GitHub telemetry endpoint; cardinality: One POST per admitted enhanced-GH event; no retry. \`engine.messages.length\` may additionally use the separate internal sink.
    - Introduced by diff: false; previous behavior: Exactly the same POST count and scheduling occurred before the diff.; critical-path effect: The fetch is started after serialization but is fire-and-forget, so response latency does not block routing completion.
  - network at <code>src/vs/platform/agentHost/node/agentHostMicrosoftTelemetry.ts:AgentHostInternalTelemetrySender.sendForContext</code>: Queue an internal telemetry event through the OneDataSystem appender for internal users; cardinality: One internal appender log for each admitted \`engine.messages.length\` event for an internal user; none for \`engine.messages\`.
    - Introduced by diff: false; previous behavior: The same internal event cardinality and appender path existed before the diff.; critical-path effect: The appender call is synchronous enqueueing; transport/flush is managed by the existing appender and unchanged by the diff.
- Verdict: No reportable performance regression. The PR adds two string comparisons per target event and suppresses one short property for two event kinds; it does not add serialization, compression, network calls, retention, or concurrency.

### Scenario 2: Other allowlisted telemetry such as \`conversation.repetition.detected\` retaining the SDK model-call fallback

- Critical path: The same SDK callback and cached context resolution lead to property construction, multiplexing, and the pre-existing sink. The new \`isEngineSnapshot\` comparison evaluates false, after which the existing \`model\_call\_id\` fallback and all downstream behavior remain unchanged.
- Scaling input: The only added cost is O(1) string comparison per allowlisted event, independent of payload size and collection cardinality.
- Effective concurrency: Independent notifications can route concurrently; same-token cold discovery is coalesced, and each admitted event retains its existing single-sink cardinality. The diff adds no queue, limiter, fan-out, or serialization point.
- Cache behavior: Same per-token coalesced account-context cache as before; no cache behavior is changed by the event classification.
- Mechanism confidence: High: the false branch preserves the prior property spread and all downstream calls.
- Magnitude uncertainty: Notification frequency varies, but two primitive equality checks are not a realistic user-visible regression and do not amplify expensive downstream work.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_routeGitHubTelemetry and src/vs/platform/agentHost/node/agentHostRestrictedTelemetry.ts:\_post</code>: Resolve cold account context and POST the admitted enhanced telemetry envelope; cardinality: One coalesced discovery per cold token and one POST per admitted event.
    - Introduced by diff: false; previous behavior: Both boundary calls and their cardinality are unchanged; these non-engine events still receive the same fallback property.; critical-path effect: Cold discovery and property multiplexing precede dispatch; POST completion is off the critical path.
  - serialization at <code>src/vs/platform/agentHost/node/agentHostGitHubTelemetryRouter.ts:route and src/vs/platform/agentHost/node/agentHostRestrictedTelemetry.ts:multiplexProperties/\_post</code>: Multiplex telemetry properties and serialize one envelope; cardinality: Once per admitted source event; cost scales with property bytes.
    - Introduced by diff: false; previous behavior: No change beyond the constant-time engine-kind classification.; critical-path effect: Multiplexing is awaited and JSON serialization occurs before fetch, exactly as before.
- Verdict: No reportable performance regression; existing boundary and serialization costs are neither introduced nor amplified.

**Summary:** Completed the performance pass over the full two-file diff and traced both engine and non-engine telemetry routes through account discovery, compression/chunking, serialization, enhanced telemetry POST, and internal appender dispatch. No diff-caused performance issue was found, and the PR is not evidenced as a performance-regression fix requiring blame attribution.
