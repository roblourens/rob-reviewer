## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/editor/common/diff/externalLinesDiffComputer.ts:58` (`RIGHT`)  
**Blamed base line:** `src/vs/editor/common/diff/externalLinesDiffComputer.ts:59`  
**Introducing path:** `src/vs/editor/common/diff/externalLinesDiffComputer.ts`  
**Introducing commit:** `cf676eb9119f308cb6337e778689af22a38152a2`  
**Mechanism family:** `eager-work`  
**Performance category:** `latency`  
**Confidence:** 0.97

**Mechanism:** The external diff adapters ignored the caller's time budget and synchronously computed the full diff in the shared editor worker, allowing CPU work and awaited diff-render latency to grow without the configured 5-second bound.

**Symptom:** Opening or updating a large/pathological diff with advanced-external or advanced-wasm could keep the editor worker occupied and delay diff rendering past diffEditor.maxComputationTime instead of quitting early.

**Fixed behavior:** The bridge now passes options.maxComputationTimeMs into &#64;vscode/diff, so external JavaScript and WASM computations can terminate at the same configured budget as the built-in advanced algorithm and return a coarse timed-out result rather than running to completion.

**Evidence:** The base bridge explicitly omitted maxComputationTimeMs on the synchronous &#64;vscode/diff computeDiff call (base line 59), while DiffEditorViewModel awaits WorkerBasedDocumentDiffProvider.computeDiff before committing/rendering the result, and the worker invokes diffAlgorithm.computeDiff synchronously. The UI option defaults to 5000 ms and is documented as cancelling computation after that budget, but advanced-external/advanced-wasm discarded it; large or pathological diffs could therefore keep the editor worker busy and leave the diff editor awaiting a result beyond the configured bound. Blame identifies cf676eb9119f308cb6337e778689af22a38152a2 as introducing the omitted-forwarding line.

- Mechanism confidence: High that one lookup is introduced and that heavyweight diff initialization remains lazy; low evidence of any measurable startup degradation.

- Mechanism confidence: High from the deleted helper and added metadata predicate.
- Magnitude uncertainty: The number and size of replacements vary by diff, but the changed operation strictly removes text scanning/allocation from this loop.
- Expensive boundaries: none found
- Verdict: No regression. This is a per-replacement CPU/allocation reduction.
