# Performance review: editor: fix &#64;vscode/diff bridge, report diff validity in telemetry

[PR #344144](https://github.com/microsoft/vscode/pull/344144) at `23300dafcfb0c909e3baaadb29ad886e228cd853`

## Findings (2)

### 1. [medium] \[medium\] Bound sampled verification by character count

**Finding ID:** `PERF-EC879739F300`  
**Location:** <code>src/vs/editor/browser/widget/diffEditor/diffProviderFactoryService.ts:184</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU work and document-sized strings/arrays allocated while reconstructing and comparing the texts  
**Scaling:** Once sampled, cost grows with total character count, not line count; a one-line or otherwise low-line-count generated file can be tens of megabytes and still pass both 50,000-line checks.  
**Outcome:** Sampled large diffs remain on the diff editor critical path longer and create substantial transient memory/GC pressure before the result can render.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, a cache-miss diff returned after the configured diff algorithm completed; it did not reconstruct and compare the entire output text for telemetry.  
**Changed behavior:** For every sampled cache miss under 50,000 lines, the worker now calls \`verifyLinesDiff\` before returning. That function materializes an applied result, joins the entire modified document (or splits and trims the applied result), so low-line-count large files receive additional full-document work.  
**Confidence:** 0.99 — The added critical-path call, full-text allocations, force-large-model synchronization, and ineffective line-only bound are directly traced. Exact latency varies by file size and sampling rate, but the mechanism and realistic long-line trigger are deterministic.

**Causal diff evidence:** The added \`\_shouldVerify\` guard at lines 184-185 enables verification based only on each model's line count, while the same diff adds the worker-side call to \`verifyLinesDiff\`; no character-count bound is applied.

With the experiment enabled, opening or editing a diff of a large minified bundle, generated JSON, or another file with very long lines can add large full-text copies and linear scans after diff computation. The caller awaits this same worker request before rendering, and diff model synchronization explicitly forces large models, so the line limit does not protect this scenario.

**Evidence:** \`computeDiff\` calls \`\_shouldVerify\` on each cache miss and awaits the worker. The new guard checks only \`getLineCount()\`. In \`EditorWorker.computeDiff\`, a true flag synchronously calls \`verifyLinesDiff\`; \`verifyLinesDiff\` calls \`edit.normalize().apply(...)\` and then either \`modifiedLines.join('\\n')\` or \`actual.split('\\n')\` plus per-line trim. \`EditorWorkerService.computeDiff\` uses \`\_workerWithResources(..., true)\`, bypassing the model's 50 MB synchronization limit, and the view model awaits this result on its render/update path.

**Suggested direction:** Add a total-character/byte bound using the models' value lengths (in addition to the line bound) before sampling, sized to the telemetry budget; skip verification when either model or their combined size exceeds it.

### 2. [medium] \[medium\] Avoid rescanning an entire long line for every whitespace edit

**Finding ID:** `PERF-752857181405`  
**Location:** <code>src/vs/editor/common/diff/externalLinesDiffComputer.ts:109</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU string searches and substring/regular-expression work in the editor worker  
**Scaling:** For k whitespace-only replacements on a line of length L, each call performs \`lastIndexOf\` and \`indexOf\` searches to the line boundaries, making the new filtering stage O(k×L) on a long single line rather than proportional to the document plus edit ranges.  
**Outcome:** External/wasm diff results can be delayed by repeated multi-megabyte scans, reducing worker throughput and making the diff editor wait before rendering.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Previously the adapter passed \`ignoreTrimWhitespace: true\` into \`&#64;vscode/diff\` and only converted the replacements returned by the package; it did not rescan the containing source and target lines for each replacement.  
**Changed behavior:** The PR always asks the package to diff whitespace, then classifies each whitespace-only replacement in the adapter. Classification repeatedly searches from the edit to both ends of its containing line in both original and modified text.  
**Confidence:** 0.95 — The repeated boundary scans and awaited call path are explicit. The exact replacement count depends on \`&#64;vscode/diff\`, but the tests establish separate intra-line mappings and isolated whitespace edits are a realistic high-cardinality input.

**Causal diff evidence:** The added \`isInTrimWhitespace\` implementation computes both line boundaries with \`lastIndexOf\`/\`indexOf\` for every candidate replacement at lines 109-111, and the added loop call at line 74 invokes it while filtering edits.

With \`ignoreTrimWhitespace\` enabled, a realistic minified bundle or generated single-line JSON file containing many isolated whitespace edits causes the post-diff adapter to scan the same very long line once per edit. This runs inside the awaited worker request after the external diff has already completed and can add seconds of CPU for sufficiently large lines/edit counts.

**Evidence:** The loop processes every external replacement. \`isInTrimWhitespace\` first confirms a whitespace-only range, then unconditionally calls \`text.lastIndexOf('\\n', range.start - 1)\` and \`text.indexOf('\\n', range.endExclusive)\` before testing the prefix/suffix. The added fixture demonstrates that isolated intra-line whitespace differences remain separate replacement mappings, so replacement cardinality can grow independently within one line. The diff view awaits this worker call; cache hits avoid it, but every changed model version is a cache miss.

**Suggested direction:** Classify trim whitespace with bounded scans outward from the range that stop at the first non-whitespace character or newline (or precompute line boundaries once and reuse them), so total filtering work is proportional to text/edit size rather than rescanning the containing line per replacement.

- Critical path: On a diff-cache miss, the view awaits worker resolution of the external computer, external diff computation, the changed per-replacement trim-whitespace filter, line mapping conversion, and the IPC response. The filter is therefore on the visible diff critical path.

- Magnitude uncertainty: Exact edit coalescing by the external package and machine-specific string-search throughput determine duration. The added per-edit scans and long-single-line trigger are deterministic.
- Expensive boundaries:

- Verdict: Reportable repeated-work regression: adapter-side trim filtering can repeatedly scan the same very long line once per isolated whitespace edit.
