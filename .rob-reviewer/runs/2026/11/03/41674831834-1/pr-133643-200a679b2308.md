# Performance review: debug: read/write memory support

## Findings (1)

### 1. [medium] Dispose each per-row variables menu

**Finding ID:** `PERF-0438C2621B81`  
**Location:** <code>src/vs/workbench/contrib/debug/browser/variablesView.ts:433</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Menu instances, their MenuRegistry event subscriptions, overlay context maps, and rebuild schedulers  
**Scaling:** Retention grows by one menu for every rendered variable-row lifecycle; repeated debugger stops, variable refreshes, and scrolling continuously add menus even though the tree virtualizes rows.  
**Outcome:** steadily increasing retained heap and GC pressure during long debugging sessions, plus fan-out rebuilding every leaked menu when the variables menu registry changes  
**PR causality:** <code>introduced</code>  
**Previous behavior:** VariablesView created one DebugVariablesContext menu in its constructor and registered that single menu with the view lifecycle for disposal.  
**Changed behavior:** Every VariablesRenderer.renderActionBar call now creates a new menu for that row, but elementDisposable receives only the actions returned by createAndFillInContextMenuActions; the menu itself is never disposed when disposeElement recycles the row.  
**Confidence:** 0.99 — The changed render path, row disposal ownership, and Menu's global registry subscription are all explicit in repository code. Virtualization bounds simultaneous rows but not leaked menus across render lifecycles; only the exact growth rate depends on user stepping and scrolling frequency.

**Causal diff evidence:** The added \`const menu = this.menuService.createMenu(...)\` at line 433 moves menu creation from one view-owned instance to each row render, while the following added push stores only \`createAndFillInContextMenuActions(...)\` in \`data.elementDisposable\`.

A long stepping session or browsing a large variable tree leaks a menu on each visible-row render, causing memory growth and making later menu-registry updates increasingly expensive.

**Evidence:** MenuService.createMenu returns a Menu that immediately subscribes to the global MenuRegistry.onDidChangeMenu and owns a RunOnceScheduler until Menu.dispose() is called. createAndFillInContextMenuActions disposes only the generated actions. AbstractExpressionsRenderer.disposeElement disposes only data.elementDisposable, where this code adds the actions but not menu. Thus the global registry retains every menu and its overlay after the row is recycled.

**Suggested direction:** Add the created menu (and its per-row context service for lifecycle symmetry) to data.elementDisposable/one row DisposableStore before adding the generated actions, so disposeElement releases the registry subscription whenever the row is rerendered or recycled.
