# Performance review: perf: reduce renderer memory usage when reading large agentHost plugin files

[PR #345802](https://github.com/microsoft/vscode/pull/345802) at `9f44db2139acd78d779d0c4c9625227f9722abdc`

## Findings (1)

### 1. [medium] Scope the read limiter to avoid cross-host head-of-line blocking

**Finding ID:** `PERF-9F0ECEF43C04`  
**Location:** <code>src/vs/platform/agentHost/common/agentHostFileSystemProvider.ts:497</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** queued \`resourceRead\` IPC calls and limiter slots  
**Scaling:** Waiting time for an unrelated authority grows with the number of earlier queued reads and their RPC duration; ten slow or hung active reads consume all execution slots.  
**Outcome:** Interactive file-read latency and blocked critical-path progress across otherwise independent agent-host connections.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each \`readFile\` immediately called \`\_readFromConnection\` for its own authority, so traffic on one connection did not queue an unrelated authority before its IPC began.  
**Changed behavior:** Every \`readFile\` now enters a single provider-wide FIFO limiter before authority selection and the \`resourceRead\` IPC.  
**Confidence:** 0.96 — The singleton ownership, multi-authority registrations, global limiter field, and FIFO implementation are directly traced. The exact delay depends on bulk-sync size and remote read duration, but the cross-authority critical-path blocking mechanism is deterministic once more than 10 reads overlap.

**Causal diff evidence:** Added line 497 wraps the entire authority-specific read operation in \`this.\_readLimiter.queue(...)\`; the limiter is a single instance field shared by all registered authorities.

When one agent-host authority starts a bulk plugin/directory read, its first 10 RPCs run and all later reads queue in this FIFO. A user-visible file, log, or attachment read from a different local/remote authority is appended behind that backlog, so its latency grows with the number and duration of unrelated reads and can stall indefinitely behind hung RPCs.

**Evidence:** \`AgentHostFileSystemService\` owns one singleton \`AgentHostFileSystemProvider\`, while local and each remote connection register distinct authorities on that same provider. This added wrapper sends every authority through one \`Limiter(10)\`, and \`Limiter.consume()\` drains its single \`outstandingPromises\` array FIFO. Therefore 10 active plus N queued reads for host A prevent a later host B \`resourceRead\` IPC from even starting until earlier entries complete.

**Suggested direction:** Keep the aggregate memory cap but schedule by authority (for example, per-authority queues feeding a fair/round-robin global limiter, or reserved capacity for unrelated authorities) so one host's backlog cannot monopolize all slots.


## Performance regression fixes detected (1)

### 1. serialization-allocation

**Fix location:** `src/vs/base/common/buffer.ts:502` (`RIGHT`)  
**Blamed base line:** `src/vs/base/common/buffer.ts:439`  
**Introducing path:** `src/vs/base/common/buffer.ts`  
**Introducing commit:** `29bde3176c7451e966797931aa8a1f7c3fce2983`  
**Mechanism family:** `serialization-allocation`  
**Performance category:** `memory`  
**Confidence:** 0.97

**Mechanism:** The fallback base64 encoder appends four one-character strings for every three input bytes, creating O(n) concatenation operations and substantial transient string/rope allocation for large binary resource payloads.

**Symptom:** Large agent-host `resourceRead` responses encoded tens-of-megabyte files through this loop, producing severe transient memory growth and CPU time proportional to millions of JavaScript concatenations.

**Fixed behavior:** The added `Uint8Array.prototype.toBase64` fast path performs the encoding natively and bypasses the per-character JavaScript concatenation loop when the runtime supports it.

**Evidence:** Agent-host filesystem resource providers call `encodeBase64(content.value)` for Base64 reads, and the old loop performs four `output +=` operations per three bytes. Added line 502 returns the native typed-array encoding before that loop. The PR's supplied 45 MiB profile reports the corresponding allocation and CPU spike collapsing after this path is used.
