# Performance review: search\_code\_subagent encouragement in first 2 turns

## Findings (1)

### 1. [medium] Coalesce tool-metadata RPCs before handling grep calls

**Finding ID:** `PERF-88590232FF76`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotGrepSearchNudge.ts:104</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SDK RPC calls plus serialization/allocation of the complete current tool metadata list and schemas  
**Scaling:** Cost grows linearly with the number N of eligible grep/rg tool calls during the first two user messages; parallel calls produce an N-wide RPC burst, and each nudged exact retry adds another RPC.  
**Outcome:** increased pre-tool latency and excessive IPC/serialization work  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, grep/rg pre-tool handling did not call \`rpc.tools.getCurrentMetadata\`; it proceeded directly through existing hooks and permissions. The new experiment path adds one full metadata RPC per eligible attempt.  
**Changed behavior:** With the experiment enabled during either of the first two user messages, every primary grep/rg pre-tool hook now fetches and serializes the session's complete current tool metadata before it can deny or allow the call. Parallel grep calls issue independent RPCs, and an identical retry after a nudge performs the same RPC again before discovering the pending retry.  
**Confidence:** 0.96 — The changed hook is directly awaited by \`\_handlePreToolUse\`, the SDK call is explicit, history alone is memoized, and retry detection is visibly ordered after the metadata call. Tests establish realistic parallel grep calls and a subsequent identical retry. Actual RPC duration and tool-list size vary, which affects severity but not the mechanism.

**Causal diff evidence:** Added line 104 unconditionally awaits \`session.rpc.tools.getCurrentMetadata()\` for every eligible grep/rg evaluation; the added retry lookup (\`\_pendingRetries.get(key)\`) does not occur until lines 139-145, so even a retry already authorized to continue pays another metadata RPC. The added parallel-call test invokes three eligible calls together, while only history initialization is memoized.

A model response containing several grep searches bursts one full tool-metadata IPC per call, and each call remains blocked on that RPC for up to 500 ms before tool execution or the nudge can proceed. The required exact retry is also unnecessarily delayed, increasing interactive agent latency and IPC/serialization load when the experiment is enabled.

**Evidence:** \`CopilotAgentSession.\_handlePreToolUse\` awaits \`CopilotGrepSearchNudge.evaluate\` before normal tool checks. In \`evaluate\`, line 104 calls the full \`session.rpc.tools.getCurrentMetadata()\` on every eligible invocation. \`\_historyInitialization\` coalesces only event-log reads; there is no corresponding metadata promise/cache. \`\_pendingRetries\` is consulted only after this RPC. Therefore N grep/rg calls from one model response create N full-metadata RPCs, and the next model response's exact retry creates one more. The 500 ms shared-per-call deadline bounds individual delay but not aggregate concurrent RPC count.

**Suggested direction:** Coalesce/cache one metadata snapshot per model response (invalidating when the response or tool set changes), and compute/check the pending-retry key before fetching metadata so an exact retry can continue immediately. This preserves current-availability checks for new calls while reducing same-response calls to one RPC and retries to zero.
