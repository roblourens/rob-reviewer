# Performance review: sessions: keep layout state per chat by default

[PR #346836](https://github.com/microsoft/vscode/pull/346836) at `856458acf08c3a70cac43d49c4bc51817ac26415`

## Findings (1)

### 1. [medium] Avoid rebuilding and serializing every editor working set on ordinary chat switches

**Finding ID:** `PERF-7E6FCF47D8FA`  
**Location:** <code>src/vs/sessions/contrib/layout/browser/sessions.layout.contribution.ts:58</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU work and allocations from serializing all saved editor working sets twice, plus editor-group/DOM reconstruction for the incoming working set  
**Scaling:** Each switch among chats in one session costs O(total serialized state across visited chats) for delete/save persistence and O(open editor groups and tabs) for apply; the persisted collection grows with chats that have had editors open until those chats are deleted.  
**Outcome:** Increased chat-switch latency and UI/GC churn, especially in long-lived sessions with many chats or editor tabs.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** With the previous \`session-shared\` default, changing chats inside the same session retained the session owner key, so it did not save or apply an editor working set and did not rebuild the editor grid. Per-chat behavior ran only for users explicitly opting in.  
**Changed behavior:** Making \`chat\` the registered default gives each chat a different owner key. On every same-session chat change, \`ChatLayoutContext\` invokes \`\_saveOutgoingWorkingSet\`, and the target change invokes \`\_applyWorkingSet\` for the incoming chat.  
**Confidence:** 0.97 — The default-to-enabled call path, same-session owner-key change, two whole-collection JSON serializations, and full editor-grid apply are directly established by the configuration, controller, and EditorParts implementations. Exact milliseconds vary with tab count and editor types, so severity is medium rather than high.

**Causal diff evidence:** The added \`default: 'chat'\` at line 58 activates the per-chat owner/save/apply path for every desktop Agents window with no explicit setting; the deleted default limited that path to opt-in users.

For users without an explicit setting or experiment override, switching chats now synchronously snapshots the editor grid and rewrites the complete \`editor.workingSets\` payload twice (delete then add), then asynchronously disposes/recreates editor groups and restores the active editor. A session with many visited chats or tabs can therefore pause and churn the visible editor area on every chat switch.

**Evidence:** \`BaseLayoutController\`'s per-chat owner-change callback calls \`\_saveOutgoingWorkingSet\`; \`\_saveWorkingSet\` first calls \`\_deleteWorkingSet\` and then \`saveWorkingSet\`. \`EditorParts.deleteWorkingSet\` and \`saveWorkingSet\` each call \`saveWorkingSets()\`, which JSON-stringifies the entire accumulated working-set array. The incoming path calls \`EditorParts.applyWorkingSet\`, whose \`EditorPart.doApplyState\` disposes all groups, deserializes the grid, and restores editors. The same-session switch does none of this when chat layout is disabled because its owner key remains the session resource.

**Suggested direction:** Before changing the default, make working-set replacement atomic so delete+add produces one bounded persistence update, and add a same-state transition path that updates ownership without disposing/recreating the editor grid when the incoming chat's saved editor state matches the live state. Otherwise retain \`session-shared\` as the default.
