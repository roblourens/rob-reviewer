# Performance review: Minimap: keep the slider from jumping back while view zones scroll by

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work

### Scenario 1: Scrolling or otherwise rendering an editor with the minimap enabled, including tall view zones, editor padding, and custom-height lines

- Critical path: Each editor render synchronously builds the minimap rendering context, queries the first visible line's vertical offset and now its height, then computes and applies the minimap slider layout. The added height query is on the render critical path.
- Scaling input: One added lookup per editor/minimap render. The lookup binary-searches the number of custom-height line entries, so its cost is O(log H), where H is the effective number of custom-height entries; it does not iterate document lines or view zones.
- Effective concurrency: Single synchronous UI-thread render; no queue, parallelism, or burst behavior is introduced.
- Cache behavior: No new cache is added or bypassed. The immediately preceding vertical-offset query commits any pending line-height changes, so the added height lookup normally performs only a binary search over already-current line-height data.
- Mechanism confidence: High: the changed call path and LineHeightsManager implementation directly establish one extra synchronous binary search per render, while also showing that the preceding offset query already performs pending-change commitment.
- Magnitude uncertainty: Exact nanosecond-level cost depends on the number of custom-height decorations and render frequency, but the mechanism is bounded to one allocation-free logarithmic in-memory lookup per render and is dominated by existing minimap rendering work.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff adds bounded CPU work but no collection-wide repetition, DOM/layout read, retained memory, or expensive boundary, and the lookup is required to correctly clamp progress for the actual first-line height.

### Scenario 2: Rendering an editor when minimap output is disabled

- Critical path: The outer Minimap view part constructs IMinimapRenderingContext before InnerMinimap.render checks RenderMinimap.None, so the new line-height lookup can execute on an editor render even though minimap drawing exits early.
- Scaling input: At most one O(log H) in-memory lookup per outer minimap view-part render, with H custom-height entries; no per-line or per-zone loop is added.
- Effective concurrency: Single synchronous UI-thread call with no asynchronous work or concurrency.
- Cache behavior: No cache behavior changes. As in the enabled case, the existing preceding vertical-offset query has already committed pending line-height changes.
- Mechanism confidence: High for the code path and bounded lookup cost; lower prevalence does not affect the conclusion because the per-call mechanism is minimal.
- Magnitude uncertainty: Whether the minimap view part is scheduled for every disabled-minimap render depends on existing view invalidation, but even when reached the added work is one bounded binary search.
- Expensive boundaries: none found
- Verdict: No finding. Although the query precedes the inner disabled-minimap guard, its bounded allocation-free cost is too small to establish a concrete user-visible performance regression.

**Summary:** Reviewed the complete two-file diff and traced the added first-visible-line-height query through editor rendering and LineHeightsManager. Considered synchronous UI work and repeated work, including enabled and disabled minimap paths. No subprocess, IPC, filesystem, database, network, serialization, cache-lifecycle, allocation, or retention mechanism was introduced, and no valid performance finding or regression-fix learning signal was established.
