# Performance review: Model router skill: learn the user's work from their recent chats

[PR #346816](https://github.com/microsoft/vscode/pull/346816) at `6c5b7701323919d13091c4e684e6ffdc83e7d04e`

## Findings (1)

### 1. [medium] Bound and stream the recent-chat history scan

**Finding ID:** `PERF-E17CCFD015CA`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotBuiltinSkills.ts:322</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem reads, JSON parsing, and user-message bytes emitted into the agent context  
**Scaling:** The work grows with every matching session and with the full byte size of each events.jsonl file; the glob provides no cap on session count, aggregate bytes, or extracted messages, and repeated router runs rescan the same history.  
**Outcome:** increased router-creation latency, excessive disk I/O, and potentially large context/token processing  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Creating or editing a model router did not inspect session logs, so this workflow incurred no history-wide filesystem scan before writing the router.  
**Changed behavior:** After the user agrees, the new mandatory workflow tells the agent to read user.message content across all session event logs from the last few weeks before it writes the router.  
**Confidence:** 0.97 — The new critical-path scan and unbounded glob are explicit in the changed line, and the same source file directly establishes realistic per-file sizes. The exact delay depends on consent and the user's recent-session volume, which affects severity rather than the mechanism.

**Causal diff evidence:** Added line 322 is the first code that directs model-router creation to read every recent session log; before this line the workflow went directly from checking available models to writing the router.

A user with many recent chats can make a one-time router setup scan many large files on its critical path; even one event log is documented in this same skill as potentially hundreds of MB, and the added instruction neither requires streaming nor caps extracted content, so setup can stall on disk/JSON work and flood the model context.

**Evidence:** The added workflow targets \`session-state/\*/events.jsonl\` and requires aggregating message kinds and frequencies across them. The repository's adjacent Tooling Strategy at lines 207-210 explicitly warns that an individual \`events.jsonl\` can be hundreds of MB and must never be loaded whole, requiring a constant-memory streaming pass. That safety rule belongs only to the troubleshoot skill and is absent from the newly added model-router workflow. No cache, grouping, aggregate-byte limit, message limit, or concurrency limiter is introduced.

**Suggested direction:** Change the skill to enumerate recent files first, impose explicit session/aggregate-byte/message limits, and use one streaming type-and-timestamp-filtered pass that emits only a bounded sample or incremental aggregate rather than loading or printing all message content.
