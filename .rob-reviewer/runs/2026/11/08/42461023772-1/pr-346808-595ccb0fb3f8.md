# Performance review: Model router: judge a follow-up's effort by the work it hands over

[PR #346808](https://github.com/microsoft/vscode/pull/346808) at `595ccb0fb3f88f5dfc131bc3ff58b9fa31aec8d2`

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** serialization-allocation, repeated-work

### Scenario 1: An eligible non-continuation follow-up in a multi-route chat configured with \`switching: auto\`, where effort is \`auto\` and at least one route has no fixed effort

- Critical path: \`agentSideEffects\` awaits \`resolveTurnModel\`; that awaits catalog/model availability, \`CopilotModelRouter.\_routeFollowUp\`, request construction, and the Decisions API result before the agent turn can proceed. The new note is serialized into the existing effort question on this blocking path.
- Scaling input: One decision request per eligible follow-up. Context is bounded to four recent turns, 8 KiB per turn, a 32 KiB latest prompt, and a 200 KiB whole request. The diff adds one fixed roughly 350-byte instruction, independent of chat length, route count, or recent-turn size.
- Effective concurrency: Each turn awaits its one decision request. \`DecisionsGate\` neither coalesces nor serializes successful calls; the runtime is documented as bounding aggregate concurrency. The diff does not change call count, scheduling, or concurrency.
- Cache behavior: Decision answers are never cached. A per-client/per-token gate retains only failure cooldown state; warm calls still invoke the service once, while active failure cooldowns reject without a boundary call. Client, router catalog, and credential-scoped model catalogs can be reused, all unchanged by the diff.
- Mechanism confidence: High confidence in the path and one-call cardinality from \`\_routeFollowUp\` through \`DecisionsModelRouterPicker.pick\`, \`askDecisions\`, and \`DecisionsGate\`.
- Magnitude uncertainty: Exact tokenization and service-side latency for the added fixed text are not measured, but payload growth is constant and small relative to bounded context; no multiplicative or unbounded mechanism exists.
- Expensive boundaries:
  - filesystem/network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:resolveTurnModel</code>: Settle the model-router catalog and obtain available models for the chat credential before routing; cardinality: At most one catalog settlement and one model-list lookup per turn; warm catalog/model state is reused by existing caches.
    - Introduced by diff: false; previous behavior: The same catalog settlement and model lookup occurred for the same follow-up.; critical-path effect: These operations precede the decision request and may block model resolution when cold, but the changed instruction does not alter them.
  - IPC/network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:askDecisions</code>: Invoke the Copilot SDK \`decisions.ask\` RPC, which sends the bounded request to the decision model; cardinality: One call for each eligible follow-up when the failure gate is open; zero when the follow-up is skipped or a cooldown gate is active.
    - Introduced by diff: false; previous behavior: The same scenario made one blocking \`decisions.ask\` call with the same context and questions except for the fixed follow-up-effort note.; critical-path effect: The result is awaited before the turn model and effort are selected. The diff increases only this existing request by a fixed instruction; it adds no round trip.
- Verdict: No reportable regression. The change intentionally adds a small constant amount of serialization and model input to an already-required call, without increasing boundary count, frequency, concurrency, or retained state.

### Scenario 2: A first turn, a follow-up with fixed/off effort, or a follow-up skipped as a simple continuation

- Critical path: First turns can still await one Decisions API call; fixed/off-effort requests omit the effort question, and continuation follow-ups return before constructing a decision request. The new conditional note is absent on all these paths.
- Scaling input: First-turn prompt remains capped at 32 KiB. Skipped follow-ups make zero decision calls. Fixed/off-effort follow-ups preserve their prior bounded request shape.
- Effective concurrency: Unchanged: at most the pre-existing single awaited call for a routed turn, with no call on continuation shortcuts.
- Cache behavior: Unchanged client/catalog reuse and failure cooldown behavior; successful decisions remain uncached.
- Mechanism confidence: High confidence from the \`followUp\` and \`askEffort\` guards and the continuation early return.
- Magnitude uncertainty: None material for diff causality because the new conditional evaluates false.
- Expensive boundaries:
  - IPC/network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:askDecisions</code>: Invoke \`decisions.ask\` only on paths that already required routing; cardinality: One for an eligible first turn or fixed/off-effort auto-switch follow-up; zero for continuation follow-ups.
    - Introduced by diff: false; previous behavior: Identical call count, request content, and critical-path placement.; critical-path effect: Existing awaited routing boundary; the diff does not alter its payload on these paths.
- Verdict: No performance change on these scenarios.

### Scenario 3: A follow-up request whose serialized size is within the fixed note's size of the 200 KiB cap

- Critical path: Request construction repeatedly measures serialized size before making the same Decisions API call. The added text can make a previously just-under-cap request enter the existing trimming loop once, dropping an oldest recent turn and rebuilding.
- Scaling input: Bounded by a 200 KiB request and at most four recent turns. The narrow trigger is a payload within roughly the note's fixed byte size of the cap; trimming reduces subsequent request size.
- Effective concurrency: Synchronous request construction for one turn; no parallel work or burst is introduced.
- Cache behavior: No cache participates in serialization. Existing bounded recent-turn and prompt truncation remains unchanged.
- Mechanism confidence: High confidence that the existing cap loop can gain an iteration at the threshold; high confidence that it cannot scale beyond existing bounded context and does not add a boundary call.
- Magnitude uncertainty: The prevalence of payloads in this few-hundred-byte threshold is unknown, but the work is tightly bounded and offset by a smaller outbound payload.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/agentHost/node/copilot/copilotModelRouterPicker.ts:buildModelRouterDecisionsRequest</code>: JSON stringify the built Decisions request to enforce the whole-request byte cap; cardinality: Normally unchanged; at this narrow cap boundary the note can cause one additional bounded rebuild/size check before the outbound call.
    - Introduced by diff: true; previous behavior: A request just below the cap skipped the trim-loop rebuild.; critical-path effect: Adds at most bounded synchronous serialization/allocation for an approximately 200 KiB object, then generally sends a smaller payload after removing a recent turn.
  - IPC/network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:askDecisions</code>: Send the final bounded request through \`decisions.ask\`; cardinality: Still exactly one call.
    - Introduced by diff: false; previous behavior: One call with the just-under-cap payload.; critical-path effect: No extra round trip; after trimming, transferred bytes can be lower than before.
- Verdict: Not reportable: the edge-case extra serialization is bounded, narrowly triggered, and does not establish meaningful user-visible latency or throughput degradation.

**Summary:** Completed the performance pass over both changed files and all diff pages. Traced follow-up routing from turn submission through request construction, cache/gate behavior, and the SDK Decisions boundary. The PR adds only constant-size prompt text to an existing bounded call; no actionable performance regression or qualifying regression fix was found.
