# Performance review: Show the minimap slider while scrolling when showSlider is mouseover

[PR #346862](https://github.com/microsoft/vscode/pull/346862) at `ac7019492e13aa06aa6ceda0f972f0e487b0a364`

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work, eager-work, cleanup-lifecycle

### Scenario 1: Continuously scroll an editor with the default enabled minimap and \`showSlider: "mouseover"\`

- Critical path: Each changed scroll position synchronously reaches \`Minimap.onScrollChanged\`, ensures the \`slider-scrolling\` class is present, and resets a 500 ms timer before the already-existing minimap render is requested. No external operation must complete; browser style/compositor processing is the only added UI work.
- Scaling input: Added work scales with scroll-event frequency, not document line count or decoration count: one class-list operation and one timer reset per event. The slider is already layer-hinted and strictly contained.
- Effective concurrency: One \`RunOnceScheduler\` exists per editor. Every scroll event cancels the previous timeout before creating the replacement, so at most one hide callback remains pending per editor and no callback burst accumulates.
- Cache behavior: No cache or remote lookup is involved. Repeated class application is idempotent, while the single pending timer coalesces all events into one removal after scrolling stops.
- Mechanism confidence: High confidence in the event path and per-event timer reset from the changed handler and \`RunOnceScheduler.schedule\`; high confidence that only one timeout remains pending and opacity targets an already composited, contained slider.
- Magnitude uncertainty: Actual wheel/trackpad event rates and browser timer costs vary, but the operation is constant-size and mirrors the existing scrollbar reveal debounce; there is no evidence of enough main-thread work to cause dropped frames.
- Expensive boundaries: none found
- Verdict: No reportable regression. The intended visibility update adds bounded O(1) UI work without layout reads, collection-wide work, unbounded retention, or concurrent timer buildup.

### Scenario 2: Stop scrolling and allow the minimap slider to fade

- Critical path: After 500 ms without another scroll event, the sole pending timeout removes \`slider-scrolling\`; CSS then performs the existing 100 ms opacity transition. This runs after scrolling and is off the active scroll critical path.
- Scaling input: Cost is constant per scrolling burst: one class removal and one opacity transition, independent of file size or number of scroll events in the burst.
- Effective concurrency: Exactly one timeout callback can fire per quiescent scrolling sequence for each editor because each new event replaces the prior timeout.
- Cache behavior: The scheduled state itself provides coalescing; warm/repeated events replace the deadline rather than queueing callbacks. No cache keys or negative-cache states exist.
- Mechanism confidence: High confidence from the scheduler implementation, CSS selector, and slider construction.
- Magnitude uncertainty: Browser compositing details vary, but the slider already has \`translate3d\` layer hinting and \`contain: strict\`, making a material layout or paint fan-out unlikely.
- Expensive boundaries: none found
- Verdict: No reportable regression. Deferred cleanup is bounded and occurs once after a burst.

### Scenario 3: Create, reconfigure, and dispose editor instances

- Critical path: Construction now allocates one scheduler and closure per editor; changing minimap options rebuilds the minimap class name, and disposal synchronously cancels any pending scheduler timeout through the registered disposable.
- Scaling input: Memory grows by one small scheduler/closure per live editor and is released with the editor. It does not grow with scroll history or document size.
- Effective concurrency: One scheduler per live editor; no background worker, IPC, filesystem, network, or subprocess concurrency is introduced.
- Cache behavior: No cache is involved. Option changes reset the class state, and lifecycle registration owns timer cancellation.
- Mechanism confidence: High confidence from constructor registration and \`RunOnceScheduler.dispose\` cancellation behavior.
- Magnitude uncertainty: Exact object size is runtime-dependent, but the fixed per-editor allocation is too small to establish meaningful startup or memory degradation.
- Expensive boundaries: none found
- Verdict: No reportable regression. The eager allocation is constant and correctly lifecycle-bound, with no leak or retained history.

**Summary:** Reviewed the complete two-file diff and traced scroll dispatch, DOM mutation/compositor behavior, timer scheduling/coalescing, option changes, and disposal. No high-confidence actionable performance regression was introduced, and the PR does not itself fix a separately evidenced shipped performance regression.
