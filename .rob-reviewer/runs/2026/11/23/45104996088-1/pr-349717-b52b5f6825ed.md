## Performance regression fixes detected (1)

### 1. boundary-fanout

**Fix location:** `src/vs/workbench/api/common/extHostFileSystemConsumer.ts:163` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/api/common/extHostFileSystemConsumer.ts:46`  
**Introducing path:** `src/vs/workbench/api/common/extHostFileSystemConsumer.ts`  
**Introducing commit:** `e2834de739e7505aa8e72f314f11187652d8bbb3`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `ipc`  
**Confidence:** 0.97

**Mechanism:** For N workspace.fs shortcut operations on a registered local scheme, the base performed N separately serialized activation requests and awaited N renderer replies before the otherwise-local provider calls, despite cached extension activation. This adds IPC processing and critical-path latency proportional to operation count, including watcher-event fan-out and repeated metadata reads.

**Symptom:** Statically established redundant renderer round trips delay local filesystem API completion and consume extension-host/renderer serialization and dispatch work. No measured duration is asserted.

**Fixed behavior:** One successful activation IPC round trip per local provider registration, shared by concurrent first calls and reused by subsequent stat/read/list/mutation operations; rejected activations are cleared for retry and re-registration gets a new cache object.

**Evidence:** The deleted stat line 46 awaited \_proxy.$ensureActivation(uri.scheme) on every call; five other shortcut operations did the same. workspace.fs exposes this consumer directly (extHost.api.impl.ts:1408-1409), and the Node host installs a local file provider (extHostExtensionService.ts:168; extHostDiskFileSystemProvider.ts:24,36-37). A parent-directory creation invokes stat for each interested TypeScript watcher (extensions/typescript-language-features/src/tsServer/fileWatchingManager.ts:81-84), providing a concrete repeated-call path. RPCProtocol.\_remoteCall serializes and sends every invocation and allocates a pending reply (rpcProtocol.ts:476-495); MainThreadFileSystem.$ensureActivation calls FileService.activateProvider, which fires an activation event even for an already-present provider (fileService.ts:95-108). Existing per-event extension-host activation caching does not eliminate these consumer-to-renderer requests. Added lines 162-169 cache one activation promise on the registration; the new tests demonstrate joining concurrent calls, reuse across operations, retry after rejection, and fresh activation after re-registration. Blame resolves the old stat await to the supplied introducing commit.

- Effective concurrency: One in-flight activation per registration; separate schemes can activate concurrently. Concurrent failures share one rejection rather than multiplying IPC attempts. Pending callers can retain their registration until settlement, as they already did before this PR.
- Cache behavior: Failure is not permanently cached: catch resets activation to undefined. Registration disposal deletes the map entry; replacement creates a new object. A successful void-valued promise is retained only with its owning registration. Tests cover concurrent reuse, rejection retry, and re-registration. Successful activation does not require a renderer provider to exist, matching FileService.activateProvider's existing semantics; no retry loop or per-resource negative cache is added.
- Mechanism confidence: High for bounded ownership and coalescing: registration object construction/removal, rejection handling, tests, RPC pending-reply cleanup, and LazyPromise were inspected.
- Magnitude uncertainty: Activation failures and remote-web deployment prevalence are unknown. Actual third-party extension startup durations are not measured.
