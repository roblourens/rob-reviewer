## Findings (1)

### 1. [medium] Include queue wait in the Git-read timeout budget

**Finding ID:** `PERF-579CAA7B3AA5`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostGitService.ts:1622</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Git-read queue slots held by slow status/diff/ls-files subprocesses; pending foreground read promises  
**Scaling:** Queue delay grows with distinct slow reads ahead of the request after directory/command coalescing: eight slow worktree probes can delay an unrelated read for one timeout interval, and additional distinct worktrees add further waves. Identical callers in one worktree may share, but different worktree directories do not.  
**Outcome:** Foreground turn-start tools and commit/merge operations can be blocked for multiple command-timeout intervals by unrelated background repository work, even when their own Git commands are fast.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each \_runGit call spawned immediately and began its timeout immediately; a fast read in another repository did not have to wait for previously requested status/diff commands to finish.  
**Changed behavior:** With coalescing enabled, all shareable foreground and background reads enter the same eight-slot FIFO queue, with no enqueue deadline or cancellation. Only execution after dequeue is timed.  
**Confidence:** 0.96 — The diff inserts a host-wide FIFO Limiter before \_spawnGit, while the timeout is created only inside \_spawnGit. Turn-end captures and foreground turn-start captures both reach it, and Copilot's pre-tool hook awaits the latter. Existing directory grouping cannot combine reads from distinct worktrees. Exact delay depends on repository/I/O speed; the unbudgeted wait is statically established.

**Causal diff evidence:** Added line 1622 queues every shareable read through \_gitReadLimiter, and line 1627 calls \_spawnGit only when that queue grants a slot. \_spawnGit still starts its 30-second default timer at line 1740, so none of the new queue wait consumes the command's timeout budget.

When multiple large or slow worktrees refresh together, starting a turn or invoking commit/merge in a healthy repository waits behind their probes. The normal 30-second Git timeout no longer bounds even a single read's request-to-result latency; several queued batches can turn this into a multi-minute stall.

**Evidence:** CheckpointAndChangesetContribution.onTurnEnd starts captures without awaiting them; AgentHostCheckpointService captures independently per session and calls captureWorkingTreeAsTree (line 415). That method issues status, HEAD-tree and cold index-path reads in parallel (1235–1239). The same method is awaited by \_captureTurnStartCheckpoint (262), and CopilotAgentSession.\_handlePreToolUse awaits \_turnStartCheckpoint (11209). CommitOperationHandler awaits hasUncommittedChanges (93), which also enters this queue. Limiter.consume uses FIFO outstandingPromises.shift and keeps a slot until its factory promise settles (async.ts 833–858). The timeout and cooldown apply only after spawn; neither bounds time spent waiting.

**Suggested direction:** Keep the concurrency cap, but assign queued reads an end-to-end deadline and expire/remove queued work before spawning when that budget is exhausted; pass only the remaining budget to \_spawnGit and preserve existing throwOnError versus undefined timeout semantics. Alternatively reserve/prioritize capacity for foreground reads while still bounding their queue wait.


## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/platform/agentHost/node/agentHostGitService.ts:1700` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentHostGitService.ts:1597`  
**Introducing path:** `src/vs/platform/agentHost/node/agentHostGitService.ts`  
**Introducing commit:** `d9eb8ee3a902bdf8f3735fd74e7e4c2eb827e2d9`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.97

**Mechanism:** The manually created Git timeout was cleared only by the child's exit event. A failed spawn, such as ENOENT for a deleted worktree cwd, invokes the execFile error callback without an exit event, leaving a referenced timer and its child/service closure alive until the timeout.

**Symptom:** Repeated direct status probes of deleted worktrees retained one timer/closure per failed spawn for the default 30 seconds, with unnecessary timer wakeups and an event-loop liveness tail despite requests already having finished.

**Fixed behavior:** The execFile callback now clears the timer before either success or error handling, releasing the timeout resource promptly even when no child exit event occurs.

**Evidence:** The diff adds clearTimeout(timer) at RIGHT line 1700 in \_spawnGit's execFile callback; the base timer creation at 1597 and exit-only clearing at 1605 both blame to d9eb8ee3a902bdf8f3735fd74e7e4c2eb827e2d9. Public hasUncommittedChanges calls \_runGitStatus directly without the getRepositoryRoot missing-directory guard, making failed cwd spawns reachable during worktree lifecycle races. Previously the callback settled the request but did not clear the timer; Node failed-spawn error/close delivery does not emit exit. The added failed-directory test corroborates reachability, although its counter assertions alone do not measure timer retention.
