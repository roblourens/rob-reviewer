## Findings (1)

### 1. [medium] Keep the fast rejection for missing contiguous substrings

**Finding ID:** `PERF-20254BB56528`  
**Location:** <code>src/vs/base/common/fuzzyScorer.ts:44</code> (<code>LEFT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Q\*T CPU matrix-cell calculations and two temporary Q\*T numeric arrays per target.  
**Scaling:** O(U\*Q\*T) matrix work for U distinct uncached substring misses. U is at most 200 for history and can be thousands of fuzzy-filtered workspace paths; identical cached queries do not repeat scoring.  
**Outcome:** UI-thread input latency and GC pressure in quick access, plus slower workspace search-result delivery.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Non-fuzzy substring misses returned NO\_SCORE before constructing scoring matrices.  
**Changed behavior:** Every eligible substring miss now builds both full scoring matrices, despite returning zero.  
**Confidence:** 0.99 — Static callers, exhaustive loops, cache behavior, history cap and full-candidate top selection prove the mechanism; duration and large-workspace prevalence are unmeasured.

**Causal diff evidence:** The deleted includes guard removes the early return before doScoreFuzzy; the replacement startsWith check is inside the exhaustive matrix loops.

Typing a nonmatching history filter now builds unnecessary matrices on the UI thread. A quoted query that matches thousands of workspace paths only non-contiguously causes the same work across all those candidates before results return.

**Evidence:** doScoreFuzzy loops over all Q\*T cells and writes two arrays even with zero scores. anythingQuickAccess.ts:456 uses false synchronously for history, capped at 200. Quoted queries also select false at fuzzyScorer.ts:465,507. Workspace filtering uses fuzzyContains (search.ts:557), allowing subsequence-only paths into rawSearchService.ts:256 scoring. topAsync examines all candidates, not just the 512 returned results. Cache hits avoid repeat comparator scoring, but each new item/query key incurs the work.

**Suggested direction:** Restore the upfront includes rejection when non-contiguous matching is disabled, while retaining the new startsWith scoring gate for contiguous highlights.
