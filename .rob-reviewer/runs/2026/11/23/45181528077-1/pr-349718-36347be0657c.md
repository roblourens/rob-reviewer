## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/base/common/fuzzyScorer.ts:672` (`RIGHT`)  
**Blamed base line:** `src/vs/base/common/fuzzyScorer.ts:649`  
**Introducing path:** `src/vs/base/common/fuzzyScorer.ts`  
**Introducing commit:** `c574731ae915d9f24184baf887399ac4c1360528`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.94

**Mechanism:** Repeated content-based scorer-cache lookups inside the ranking comparator reread and hash label/description/query text for both operands even when fuzzy scores are already cached. In top selection with N matches and K retained results, an incumbent can be rehashed for many of the N comparisons, with additional comparisons on insertion; full history sorting performs O(H log H) such comparisons. This adds CPU/string processing on the path to displaying Go to File results.

**Symptom:** Strongly evidenced redundant character-scanning hash and accessor work delays ranking and consumes extension-host/UI-thread CPU during Go to File queries over large matching file sets; warm scorer-cache hits still incurred this work before the change. No timing measurements were independently executed.

**Fixed behavior:** The three ranking sites create a fresh comparator for each sort. For nonempty queries its identity Map reuses IItemScore references and bypasses accessor/cache-hash computation on subsequent comparisons of the same item, including cached no-match scores; the original comparison and tie-breaking rules remain in compareItemScores. Hash/scoring lookup multiplicity falls from two per comparison to at most one per distinct compared item. The additional Map is confined to the synchronous sort or active topAsync invocation.

**Evidence:** The base comparator calls scoreItemFuzzy for both operands on every comparison at fuzzyScorer.ts:649-650. scoreItemFuzzy reads the accessor label/description and computes getCacheHash before checking the existing cache (head lines 423-446, unchanged). getCacheHash hashes label, description and query text through doHash/stringHash; hash.ts:52-57 scans every string character. rawSearchService.sortResults previously invoked this comparator from topAsync; arrays.ts:325-350 repeatedly compares the same retained top candidates while scanning all matching files, and the two browser ranking paths also repeatedly compare picks. This diff adds a per-sort identity Map at fuzzyScorer.ts:666-678 and replaces the raw and browser comparators, reducing these cache-key computations to once per distinct compared item. The added test repeats comparisons in both directions and asserts zero subsequent accessor reads. Blame resolves the old score call to c574731ae915d9f24184baf887399ac4c1360528 in src/vs/base/common/fuzzyScorer.ts. Static call-flow evidence establishes the removed CPU work independently of PR-described benchmark timings.
