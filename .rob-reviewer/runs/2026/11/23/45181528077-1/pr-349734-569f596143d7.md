# Performance review: Model router: add a command to open the routers folder

[PR #349734](https://github.com/microsoft/vscode/pull/349734) at `569f596143d7d6b0610088645d13622f313b2000`

## Findings (1)

### 1. [low] Avoid metadata-resolving creation for an existing routers folder

**Finding ID:** `PERF-BA421E77D688`  
**Location:** <code>src/vs/workbench/contrib/chat/electron-browser/actions/openModelRoutersFolderAction.ts:46</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** N child-stat IPC requests and filesystem metadata operations, plus an extra directory listing and discarded file-stat objects.  
**Scaling:** N is all immediate directory entries, not just valid or deduplicated routers. For an existing folder, each invocation makes N child-stat requests plus three folder-stat requests and two readdir requests; child stats run concurrently but the action awaits the entire batch. No application cache removes this work.  
**Outcome:** Avoidable folder-reveal latency and filesystem/IPC traffic on every invocation, including warm invocations.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The base had no model-router folder command and therefore no creation/metadata pass on this reveal path. Its existing folder-reveal pattern, such as OpenExtensionsFolderAction, used one non-metadata resolve followed by showItemInFolder. The newly required missing-folder creation does not require a metadata pass over an already existing folder.  
**Changed behavior:** Opening an existing routers folder now performs a metadata-resolving creation pass, followed by a second directory listing, before revealing one child. For N immediate entries this adds N independent child-stat IPC/filesystem requests that the action does not consume.  
**Confidence:** 0.97 — The awaited action, unconditional metadata resolution in FileService.createFolder, per-child stat branch in toFileStat, and desktop provider's channel.call('stat') are all traced. These requests are concurrent, not N serialized round trips. Directory sizes and actual filesystem latency are unmeasured.

**Causal diff evidence:** The added unconditional await fileService.createFolder(folder) at line 46 invokes FileService.createFolder's resolve(resource, { resolveMetadata: true }) even when mkdirp finds the directory already exists. FileService.toFileStat then calls provider.stat for every immediate child. The added line 47 separately resolves the same folder without metadata.

Users opening an existing folder containing saved router variants or renamed/backup files wait for metadata retrieval for every immediate entry before the file manager appears. This produces avoidable filesystem/IPC traffic and increasing reveal latency as the folder grows, especially with a slow home-directory filesystem.

**Evidence:** FileService.createFolder (src/vs/platform/files/common/fileService.ts:1007-1015) always resolves with resolveMetadata:true after mkdirp. toFileStat (:271-277) lists the folder and maps every entry to provider.stat(childResource), awaiting all results. The desktop DiskFileSystemProvider delegates to DiskFileSystemProviderClient, whose stat (:81-82) issues one main-process IPC call per entry. The action discards this result and performs another resolve at line 47; showItemInFolder at line 49 cannot start until both passes finish.

**Suggested direction:** Resolve the folder without metadata first. Only call createFolder when that resolve fails with FILE\_NOT\_FOUND, and use its returned children on that cold path. This preserves first-use creation and file selection while avoiding the per-entry metadata pass and second listing for existing folders.
