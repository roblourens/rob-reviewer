## Findings (1)

### 1. [medium] Avoid flattening every prefix when reassembling large snapshots

**Finding ID:** `PERF-D61AD9E68F3C`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostConnectionChannels.ts:57</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Renderer string-prefix copying, transient UTF-16 buffers, and garbage collection  
**Scaling:** For a snapshot of S UTF-16-accounted bytes fragmented into F frames, prefix flattening copies O(S\*F) bytes, approximately O(S^2/B) for effective payload size B at most 256 KiB. For example, 25 MiB of accounted snapshot text requires at least 100 fragments before escaping overhead and repeatedly copies roughly a gigabyte of prefixes. Concurrent restored channels add their individual costs.  
**Outcome:** Superlinear renderer CPU/allocation cost, GC pressure, and increased chat-open/reconnect latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** State subscribe returned the snapshot in one JSON-RPC response, serialized and parsed as a whole with linear string processing. The prefix-flattening reassembler was only reached by the existing bounded TCP delivery path.  
**Changed behavior:** Every accepted non-root state subscription now sends its full snapshot through the channel reassembler, with frames capped at 256 KiB and no client snapshot-size bound, newly applying repeated prefix flattening to large conversation histories.  
**Confidence:** 0.95 — The added state snapshot call, default 256 KiB effective fragment cap, repeated prefix character access after concatenation, and client await path are all traced. V8's flattening of non-flat cons strings establishes the copying mechanism; exact snapshot prevalence and wall-clock cost are unmeasured.

**Causal diff evidence:** The added sendSnapshot(snapshot) at agentHostConnectionChannels.ts:57 routes state snapshots through fragmented AgentHostChannelDelivery for the first time. protocolServerHandler.ts:2235 now returns only flowControl instead of the ordinary snapshot response, and agentHostProtocolClient.ts:2114 waits for the separately reassembled snapshot. Previously only bounded TCP messages used this reassembler; state snapshot delivery did not perform repeated prefix character accesses.

Opening or reconnecting a chat with multi-megabyte conversation/tool-output history now repeatedly copies its accumulated snapshot on the renderer, causing CPU/GC pressure and delaying snapshot readiness; larger histories produce increasingly long main-thread work.

**Evidence:** StateChannel.start now calls AgentHostChannelSubscription.sendSnapshot, whose delivery sendFrame fragments at at most 256 KiB (agentHostChannelDelivery.ts:349,409-435), despite the 16 MiB negotiated maximum. On the renderer, accept appends each fragment to \_fragments (line 510), then the next fragment reads \_fragments.charCodeAt(\_fragments.length - 1) (line 505). In V8, reading a non-flat concatenated string here flattens the accumulated prefix; this repeats for every fragment. The state policy permits arbitrarily large received snapshots. \_requestSnapshot waits for reassembly before exposing the state, and reconnect also waits for these snapshots.

**Suggested direction:** Accumulate fragments in an array, retain the previous fragment's final code unit separately for surrogate validation, and join once for the final JSON.parse. Preserve byte accounting and credit behavior.
