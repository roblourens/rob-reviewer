### Scenario 2: Slow upstream build stages or slow ESRP provisioning exceed 180 minutes

- Critical path: Publish waits for enabled stages and gating jobs, prepares available artifacts as they arrive, then joins outstanding release workers. The new deadline permits this existing work to finish until 300 minutes instead of canceling at 180. It does not impose a 300-minute wait on completion.
- Scaling input: S enabled stages and A distinct artifacts, plus time spent waiting for upstream stages and remote releases. At most 120 additional minutes of agent occupancy per long-running PublishBuild job; independent builds may each occupy an agent.
- Effective concurrency: Same two parallel inventory requests per cycle, serial download preparation, overlapping workers, and per-file leases. Timeout extension introduces no new fan-out loop or worker-concurrency setting.
- Cache behavior: Completed and in-progress artifact names remain excluded from rescheduling. Additional inventory polling does not redownload already processed artifacts. CDN hits still skip ESRP provisioning; remote status is deliberately polled rather than negatively cached.
- Mechanism confidence: High for the intentional maximum occupancy/polling-lifetime increase and unchanged processing cardinality. No evidence establishes problematic pool saturation or new wasted-work rescheduling.
- Magnitude uncertainty: Actual long-build frequency, Windows pool capacity/utilization, remote service duration and resulting queue contention are not established. PR narrative is contextual evidence, not independent measurements.
- Expensive boundaries:
  - other expensive boundary at <code>build/azure-pipelines/product-publish.yml:18 PublishBuild.timeoutInMinutes</code>: Retain the allocated Windows pipeline agent while existing work is pending; cardinality: One agent per PublishBuild job, with the maximum occupancy increased by 120 minutes only for jobs reaching the old deadline.
    - Introduced by diff: true; previous behavior: Job cancellation at 180 minutes released the agent but prevented pending publication from completing.; critical-path effect: Allows publishing to progress instead of being canceled; possible contention with other jobs depends on pool capacity and build arrival rates.
  - network at <code>build/azure-pipelines/common/publish.ts:958-1050 main polling loop</code>: Continue timeline/artifact inventory polling while stages or eligible artifact discovery remain pending; cardinality: Two requests per round; at the unchanged 10-second sleep, up to approximately 720 extra rounds/1,440 primary requests over the additional two hours when requests are fast and there are no downloads.     - Introduced by diff: false; previous behavior: Same polling boundary and cadence, truncated by job cancellation at 180 minutes; the diff extends its permitted lifetime.; critical-path effect: Continued requests allow discovery of late artifacts and stage completion; the loop exits once stages complete and all artifacts are accounted for.
  - network at <code>build/azure-pipelines/common/publish.ts: processArtifact, ESRPReleaseService.createRelease, withLease</code>: Finish late artifact uploads, ESRP provisioning/status polling and blob lease renewal/cleanup; cardinality: Same work per distinct remaining artifact and existing 720-status/360-lease-acquisition iteration bounds; no added release submission for an already scheduled artifact. - Verdict: No actionable high-confidence performance bug: the additional bounded agent occupancy and polling are the explicit availability tradeoff. Unchanged early completion and per-operation limits reject speculative claims of increased normal latency or an unbounded concurrency regression.

### Scenario 3: Publish retry or stage rerun with previously processed artifacts

- Critical path: Download prior completion manifests, restore State, skip completed artifacts, wait for remaining stages/gates, prepare remaining eligible artifacts and join workers. CDN checks protect already provisioned but not yet recorded artifacts. Retry setup remains on the critical path.
- Scaling input: A distinct artifact names, D persisted successful names, and R remaining eligible names. Archive downloads and workers scale with R, not all A on every poll or rerun.
- Effective concurrency: Setup is sequential; inventory requests are paired; remaining downloads/extraction are serial; remaining workers overlap with per-friendlyFileName blob leases. No concurrency increase per attempt from the timeout setting.
- Cache behavior: Latest available artifacts\_processed attempt populates done; current processing names coalesce work within an attempt. Provisioned CDN resources skip new ESRP release submission even when completion state is absent. Existing transient-retry and optional-failure behavior is unchanged.
- Mechanism confidence: High: State and main filtering explicitly exclude previously completed/in-flight artifacts, and processArtifact checks CDN availability before ESRP creation.
- Magnitude uncertainty: Retry prevalence and partially completed artifact counts are unknown. Avoided reruns and release-delay improvements are not quantified or established as a specific historical performance regression by code alone.
- Expensive boundaries:
  - subprocess at <code>build/azure-pipelines/product-publish.yml: Download all artifacts\_processed/Create build/Process artifacts steps</code>: Restore completion manifests and rerun existing publishing commands; cardinality: One manifest-download step per job attempt; build creation is skipped when a completion manifest exists. Existing task retry count remains three.
    - Introduced by diff: false; previous behavior: Same resume/setup logic; the lower cap could require a new attempt but the diff does not change retry policy.; critical-path effect: Manifest restoration/setup precede retry processing.
  - filesystem at <code>build/azure-pipelines/common/publish.ts: State constructor/add, main preparation</code>: Read/write completion manifest and prepare only remaining artifacts; cardinality: Read the latest available manifest once; archive work for R remaining artifacts and append for each newly successful artifact.

  - network at <code>build/azure-pipelines/common/publish.ts: main/processArtifact/ESRPReleaseService</code>: Inventory polling, remaining downloads, lease/CDN checks and provisioning only on CDN misses; cardinality: Two inventory requests per round, normally R downloads/workers; CDN hits avoid staging upload/submission/status calls, while misses retain existing bounded polling.   - database at <code>build/azure-pipelines/common/publish.ts: processArtifact createAsset</code>: Register remaining assets using existing stored-procedure semantics; cardinality: One primary createAsset execution per successful remaining worker, with existing transient retries.
    - Introduced by diff: false; previous behavior: Identical asset-registration behavior, including already-exists responses.; critical-path effect: Must complete before each worker is recorded done.
- Verdict: No regression: the diff preserves resumability, deduplication and warm provisioning behavior. It is not classified as an internal learned regression fix without independently proven historical introducing-change causality.
