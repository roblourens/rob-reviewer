### Scenario 1: First message in a persistent folder-mode session or a new folder changeset scope

- Critical path: AgentSideEffects.\_sendTurnMessage awaits \_resolveWorkingDirectoryBeforeSend before provider preparation and dispatch. The new branch-base lookup is awaited before existing default-branch lookup and immediate base persistence. Checkpoint capture starts through onResolved before these reads and can overlap them.
- Scaling input: One primary working directory and one previously uninitialized folder scope, not every configured root or changed file. Successful base persistence suppresses resolution on subsequent messages.
- Effective concurrency: The new lookup executes its Git commands sequentially. Existing getDefaultBranch2 overlaps origin/HEAD and remote enumeration. The path has no global Git limiter, but introduces no collection fan-out. Session metadata writes serialize per session.
- Cache behavior: Repository roots use a 100-entry positive/negative LRU and in-flight coalescing. Loaded session state supplies the persisted base without database reads. getBranch coalesces only concurrent identical directory/ref requests and removes pending entries on settlement; there is no completed branch-base cache. If no base can be persisted, a later send can retry, as it could before.
- Mechanism confidence: High confidence in the bounded additional subprocess sequence and first-send critical-path reachability, supported by implementations and the two-send persistence test.
- Magnitude uncertainty: No runtime timings; local process startup and ref access depend on OS and disk cache. This does not establish a substantial scaling regression.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/agentHostGitService.ts:getBranchBase, getHEAD, \_readBranch, \_runGit</code>: Read HEAD with symbolic-ref, inspect the local branch with a ref-filtered for-each-ref, and resolve an upstream remote ref plus its remote name when present.; cardinality: Normally four newly added Git processes with an existing upstream; two with no upstream or detached HEAD; three with an upstream whose ref is missing. Concurrent identical getBranch calls can share the ref reads, but symbolic-ref is not coalesced.
    - Introduced by diff: true; previous behavior: This send path did not perform branch-base probes. It ran getDefaultBranch2 and, if configuration did not supply a branch, getCurrentBranch. Those existing fallback reads remain.; critical-path effect: Adds a bounded local Git read sequence before provider dispatch; no fetch or remote network access is performed.
  - database at <code>src/vs/platform/agentHost/node/agentHostSessionStateStore.ts:readBaseBranchWithoutImport, writeMetadata</code>: Read the stored scope base and write central state plus the immediate legacy metadata mirror.; cardinality: Loaded base read is in memory; an unloaded read can access central state/catalog or the legacy database. One logical base write per newly initialized scope, with the same central/mirror persistence structure as before.
    - Introduced by diff: false; previous behavior: The same scope read, immediate base write and mirror flush occurred, using the default/configured branch instead.; critical-path effect: Immediate persistence is awaited before dispatch, unchanged by the PR.
- Verdict: No reportable high-confidence regression. The added local reads implement the requested base selection, are first-use scoped when persistence succeeds, and do not introduce per-file work, network access, unbounded retention or a new fan-out.

### Scenario 2: Restore or adopt a session whose working directory is an existing linked worktree

- Critical path: AgentService.\_restoreSessionState awaits probe-based worktree adoption or external project discovery before completing catalog hydration. Adoption with authoritative predecessor worktree metadata bypasses the changed probe path.
- Scaling input: One primary checkout per restored session needing discovery. Sessions with an existing project or authoritative adoption metadata bypass this work. Repository discovery groups linked checkouts, but branch bases remain checkout-specific.
- Effective concurrency: Primary-root discovery misses serialize per Git service, including a cache recheck. After root resolution, branch-base queries are sequential within each invocation and can overlap across sessions. There is no new loop or bulk scheduling operation.
- Cache behavior: Repository roots are bounded and coalesced. PrimaryWorktreeRootResolver serializes cache misses and stores every root from one repository listing in a 100-entry cache; successful warm lookups avoid the listing. Branch ref lookups only share concurrent identical keys and clear on completion. The PR adds no retained cache.
- Mechanism confidence: High confidence in the call path, primary-root grouping/cache behavior, early return for primary checkouts and two-to-four-command branch lookup.
- Magnitude uncertainty: Concurrent adoption prevalence and process latency are unknown. Additional work is bounded per discovery and uses small local ref queries.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostGitService.ts:\_readRepositoryRoot</code>: Check whether an uncached directory exists before resolving its repository root.; cardinality: One directory check per uncached repository-root request; zero for a cached root.
    - Introduced by diff: false; previous behavior: The same root-existence check preceded linked-worktree discovery.; critical-path effect: Part of awaited discovery, unchanged.
  - subprocess at <code>src/vs/platform/agentHost/common/agentHostGitService.ts:PrimaryWorktreeRootResolver.resolve; src/vs/platform/agentHost/node/shared/worktreeIsolation.ts:\_resolveLinkedWorktree</code>: Resolve repository roots, list worktrees on a primary-root cache miss, and select the checked-out branch base.; cardinality: Uncached root discovery uses one rev-parse; a cold primary mapping uses one worktree listing serving all reported linked checkouts. For a linked worktree, the PR adds two to four branch-base commands. A usable differently named upstream replaces the default lookup; otherwise the old default lookup follows. A normal default lookup used two commands.
    - Introduced by diff: true; previous behavior: Identical root discovery and grouped worktree listing, followed directly by getDefaultBranch(primaryRoot). With a usable default ref this was two base-selection subprocesses rather than four for a usable upstream, or the new probes plus fallback.; critical-path effect: Discovery is awaited during restore/adoption. Primary checkouts return before the new branch-base lookup.
  - database at <code>src/vs/platform/agentHost/node/shared/worktreeIsolation.ts:adoptExistingWorktreeMetadata, recordExternalWorktreeProject</code>: Persist discovered repository/worktree identity and the selected base.; cardinality: One logical metadata write per discovery/adoption, with unchanged metadata persistence ownership.
    - Introduced by diff: false; previous behavior: The same metadata was persisted with the default branch as base.; critical-path effect: Awaited during restore, unchanged.
- Verdict: No high-confidence actionable performance bug. The PR changes base selection with bounded extra work; it neither defeats the existing grouped root discovery nor introduces a catalog-wide loop or persistent allocation.

### Scenario 3: Convert a session or chat workspace to an existing linked worktree

- Critical path: When shown, the workspace transition is created before conversion and uses resolveExternalWorktreeProject to classify the folder. Conversion resolves the external project again before committing workspace metadata and continuing the turn. Thus transition classification can reach the changed branch lookup even though it needs only worktree identity.
- Scaling input: A single selected target folder. The ordinary shown-transition folder conversion performs up to two sequential external-worktree resolutions, not one per sibling chat or changed file.
- Effective concurrency: Transition classification precedes conversion, so these discovery calls are sequential. Conversion is guarded by its pending phase; the session-replacement chat path can also run under the existing chat catalog lock. No new concurrency burst is introduced.
- Cache behavior: The second discovery reuses repository-root and primary-root caches. Branch-base reads are not completed-result cached, and sequential invocations do not share the pending ref cache. This is also true of the prior default-branch reads.
- Mechanism confidence: High confidence in the sequential two-call path and cache reuse; the duplicated discovery structure predates the diff.
- Magnitude uncertainty: No timing data for Git process startup or conversion duration. This is a bounded explicit workspace change, not a per-keystroke or collection-sized operation.
- Expensive boundaries:

  - database at <code>src/vs/platform/agentHost/node/chatContributions/sessionWorkspaceConversion/sessionWorkspaceConversionService.ts:\_convert, \_convertChat</code>: Commit workspace/configuration metadata and working-directory changes.; cardinality: One logical conversion commit, with existing per-chat working-directory updates where applicable.
    - Introduced by diff: false; previous behavior: The same conversion persistence ran with default-branch external-worktree metadata.; critical-path effect: Must finish before continuing the turn, unchanged.
- Verdict: No high-confidence reportable regression. Extra ref discovery is real, but repeated project resolution is pre-existing, the effective cardinality is at most two on this ordinary path, and no evidence establishes a substantial performance defect rather than bounded behavior-supporting work.

### Scenario 4: Display and refresh Branch Changes using the newly persisted base

- Critical path: Changeset computation resolves the persisted folder base, computes a fingerprint, and performs the existing Git diff on a cache miss before publishing changes. These computations are not awaited by the new first-send base-selection statement itself.
- Scaling input: One canonical folder changeset owner; for multi-folder changes, deduplicated repository roots rather than every supplied folder or file. Git diff/output work depends on repository state and changed paths relative to the selected base.
- Effective concurrency: Static recomputations serialize/coalesce by changeset key and mid-turn work is debounced. Multi-repository diff computations use Limiter(5); fingerprint probes use Promise.all across deduplicated repositories, and each fingerprint uses a 16-wide stat limiter. These existing limits are unchanged.
- Cache behavior: The fingerprint includes the base branch, directories, merge-base/HEAD/status and up to 2,000 changed-path stats. Equal ready fingerprints can skip recomputation; multi-repository results also reuse unchanged per-repository fingerprints. Changed bases correctly cause new results. All of this behavior predates the PR.
- Mechanism confidence: High confidence that downstream expensive operations, grouping, fingerprints and scheduling are unchanged; the diff passes a different base into existing consumers.
- Magnitude uncertainty: The selected baseline can change result size in either direction depending on branch history. No evidence proves added scaling work, and a smaller correct diff is not sufficient to identify a historical performance regression fix.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/agentHostGitService.ts:getBranchDiffFingerprint, computeSessionFileDiffs, \_resolveBranchMergeBaseCommit</code>: Resolve the baseline, inspect HEAD/status and compute raw/numstat diffs; use a temporary index when untracked files are present.; cardinality: One existing fingerprint sequence per effective repository per recompute; one existing diff sequence per repository cache miss.     - Introduced by diff: false; previous behavior: Identical fingerprint/diff algorithms and cache behavior, using the persisted default-branch base.; critical-path effect: Required before a refreshed changeset can publish; unchanged.
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostGitService.ts:getBranchDiffFingerprint, \_runWithTempIndex</code>: Stat changed paths for fingerprints; create and remove a temporary index directory for untracked-file diffs.; cardinality: Up to 2,000 stats per repository fingerprint, concurrency 16; one temporary directory lifecycle per untracked-file diff. Both are existing behaviors.
    - Introduced by diff: false; previous behavior: The same path stats and temporary index lifecycle occurred.; critical-path effect: Fingerprint and untracked-file diff preparation are awaited; unchanged.
  - database at <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:\_resolveBranchBaseBranch</code>: Load the session-state snapshot and select the persisted folder base before the Git-state fallback.; cardinality: One logical state load per resolution, served by existing loaded-state caching when warm.
    - Introduced by diff: false; previous behavior: The same loaded snapshot supplied the old persisted base.; critical-path effect: Precedes fingerprint/diff computation, unchanged.
- Verdict: No reportable regression and no qualifying regression-fix provenance signal. Different metadata alone does not establish increased subprocess frequency, serialization, allocation or retained lifetime.
