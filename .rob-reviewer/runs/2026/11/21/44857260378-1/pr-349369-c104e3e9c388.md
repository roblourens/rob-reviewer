### Scenario 1: GitHub or signed-out window startup and refresh, with the Microsoft setting disabled or enabled without a remembered account

- Critical path: DefaultAccountService.getDefaultAccount waits for provider initialization. Initialization waits for authentication-provider availability, managed-settings initialization, GitHub session discovery, and any required entitlement/policy requests. Classic web without remote skips provider initialization as before.
- Scaling input: One default-account provider per window; authentication sessions for the configured GitHub provider; refreshes from focus, the hourly poll, configuration, and followed authentication events.
- Effective concurrency: Existing 100 ms ThrottledDelayer debounces updates and its Throttler permits one active reconciliation with one coalesced pending task per window. GitHub discovery is sequential; token and managed-settings requests can run concurrently after entitlements.
- Cache behavior: The Microsoft preference is read from existing in-memory workspace/application storage only when enabled. No preference means no Microsoft sessions are read. GitHub policy/entitlement data keeps its account/server scoping and one-hour freshness; successful managed-settings initialization is reused.
- Mechanism confidence: High: traced the added gates, initialization barrier, discovery helper, RPC bridge, throttler, and cache checks; added tests also count absence of Microsoft lookups and unrelated-event updates.
- Magnitude uncertainty: Actual startup and request durations are not measured. Session counts, policy-file sizes, and authentication failures vary by installation.

### Scenario 2: Restore or refresh a remembered Microsoft default account, including stale preferences and failed lookups

- Critical path: After the unchanged managed-settings initialization, fetchDefaultAccount awaits one Microsoft session-list read. A matching account finishes without GitHub discovery or entitlement requests. An empty successful lookup falls through to GitHub; a failed lookup keeps the current account.
- Scaling input: Cached public-client applications and their account entries, deduplicated by homeAccountId into one returned session per Microsoft account; one remembered label per window; focus/hourly/explicit reconciliations.
- Effective concurrency: One throttled reconciliation per window; authentication extension operations serialize per provider through SequencerByKey. Cold PCA initialization uses Promise.allSettled across cached clients, while the warm enumeration itself is synchronous in the extension host.
- Cache behavior: Microsoft account enumeration uses the provider's existing in-memory account cache and does not mint tokens. The preference is retained on empty results or errors so later session/provider events can reconcile it. Existing successful source-initialization caches remain effective. A stable account is deep-equality suppressed before notifications.
- Mechanism confidence: High: inspected actual Microsoft undefined-scopes branch, cached account getter, homeAccountId deduplication, RPC serialization, activation path, and feature/preference guards. Repository search found no production consumer that remembers an account beyond the service wrappers themselves.
- Magnitude uncertainty: Microsoft selection currently requires externally populated preference state; product prevalence and cold authentication-cache duration are unknown. Legacy migration prevalence is also unknown.
- Expensive boundaries:

### Scenario 3: Remember, forget, or sign out a Microsoft account; react to Microsoft session/provider/preference changes

- Critical path: Remember/forget promises wait for the window's throttled account reconciliation. Removal of the current Microsoft session first reads remaining sessions; if the account has disappeared, it clears the preference and reconciles the fallback.
- Scaling input: One remembered preference; actual account-list change events from the Microsoft provider. Events are account changes, not every token refresh. Bulk changes are buffered/deduplicated by the provider.
- Effective concurrency: Reconciliation remains debounced and serialized per window. Removal checks occur outside that throttler, but extension-host Microsoft operations serialize per provider. Provider account events are already buffered and deduplicated; no per-token-refresh feedback loop was found.
- Cache behavior: Preference reads are local; remember's synchronous preference event and explicit update normally coalesce through the existing delayer. No growing map or session history is added. Microsoft sessions remain backed by cached account metadata; equal resolved accounts suppress account notifications.
- Mechanism confidence: High: traced real preference-event emission, absence of removal-event emission, direct and throttled lookups, provider account-change semantics, and disposal ownership.
- Magnitude uncertainty: Frequency of genuine account changes and bursts from multiple clients is unmeasured; expected returned data is a user's account list, not session/token history.
- Expensive boundaries:
  - database at <code>src/vs/workbench/services/authentication/browser/authenticationExtensionsService.ts: updateAccountPreference/removeAccountPreference; src/vs/platform/storage/common/storage.ts: store/remove</code>: Update or remove the remembered account label in existing workspace and application storage.; cardinality: Two storage mutations per remember or forget, using one fixed preference key per scope; persistence uses the existing storage lifecycle rather than an awaited per-account transaction.
    - Introduced by diff: true; previous behavior: No Microsoft-default-account preference was written or removed by this service.; critical-path effect: Local mutation precedes reconciliation; the returned promise waits for reconciliation, not a new explicit disk flush.
  - IPC at <code>src/vs/workbench/services/accounts/browser/defaultAccount.ts: onDidChangeMicrosoftSessions/getMicrosoftDefaultAccount</code>: Read remaining Microsoft accounts after removal of the selected session, then reconcile the default account.; cardinality: Ordinary followed changes cause one Microsoft list RPC per coalesced reconciliation. Selected-session removal adds one direct list RPC; if the account remains, reconciliation adds one more. If absent, forgetting avoids a second Microsoft RPC and may perform existing GitHub fallback discovery.
    - Introduced by diff: true; previous behavior: Microsoft session changes were ignored by the default-account provider.; critical-path effect: The remaining-account read precedes forgetting/reconciliation; unrelated Microsoft events without remembered/current state return without discovery.
- Verdict: No high-confidence performance bug: the extra removal lookup is bounded verification of account disappearance, normal events coalesce, unrelated events are gated, and no new unbounded retention or heavyweight recreation is established.

Microsoft-to-Microsoft changes do not create GitHub stores. The marketplace's Microsoft session events no longer clear browse caches through the GitHub-session filter. ### Scenario 6: Chat entitlement resolution and Copilot Free signup with a Microsoft default account

- Critical path: Entitlement resolution waits for initialized account state and returns Unresolved from missing entitlement data without a network request. signUpFree awaits getSessions, receives an empty list for Microsoft, and returns before signup.
- Scaling input: One signup action and the configured GitHub session list; eligible session count matters only for unchanged GitHub/no-account signup paths.
- Effective concurrency: No new parallel requests. Existing signup session attempts are sequential; Microsoft executes none.
- Cache behavior: getDefaultAccount reads initialized state, not a fresh account discovery for each caller. Entitlement resolution consumes account metadata and does not retry missing Microsoft entitlement data over the network. Existing cancellation replaces pending entitlement resolutions.
- Mechanism confidence: High: traced getSessions caller, explicit early return, signup guard, and metadata-only entitlement resolution.
- Magnitude uncertainty: Signup frequency and failed eligible-session counts are unmeasured. Microsoft reachability is currently gated by remembered state.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/chat/common/chatEntitlementService.ts: getSessions</code>: Read configured GitHub authentication sessions for eligible signup paths.; cardinality: Zero session-list RPCs for a Microsoft default account. GitHub selected-session lookup uses one RPC, with a second fallback lookup only if the selected session is absent; no-account uses one RPC.
    - Introduced by diff: false; previous behavior: The helper fell back to configured GitHub sessions after an accessor miss; the new explicit non-GitHub-account branch suppresses that fallback.; critical-path effect: Signup waits for these existing authentication reads, but the Microsoft branch now terminates immediately after account initialization.
  - network at <code>src/vs/workbench/services/chat/common/chatEntitlementService.ts: signUpFree/doSignUpFree/request</code>: POST Copilot Free signup using eligible GitHub sessions.; cardinality: Zero requests for Microsoft accounts.     - Introduced by diff: false; previous behavior: The existing fallback could supply configured GitHub sessions; the PR prevents that for a non-GitHub default account rather than adding requests.; critical-path effect: A signup POST is awaited only when eligible sessions exist.
- Verdict: No reportable regression and no confirmed historical performance-regression fix: the changed branch suppresses GitHub work for newly supported Microsoft state that the pre-diff production provider could not create.
