## Findings (3)

### 1. [medium] Reuse scanned counts when a search page ends within a turn

**Finding ID:** `PERF-CDA0EFC2C2A9`  
**Location:** <code>src/vs/platform/agentHost/node/chatHistoryQueries.ts:185</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Worker subprocesses, serialized child-process IPC text, Markdown tokenization, and regex match-counting CPU.  
**Scaling:** For M matches in one turn and batch size B, the UI performs ceil(min(M, 9999)/100) serial worker launches and approximately that many B-sized scans/transfers. At least 10,000 hits produce 100 launches for essentially the same batch. The global four-worker limit bounds simultaneous workers, not this repetition.  
**Outcome:** Sustained host CPU/allocation pressure and cumulative process-startup overhead delay completion of Find and contend with other chats.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Find searched the loaded transcript locally; there was no host search continuation, worker fork, or transcript transfer over child-process IPC.  
**Changed behavior:** A continuation within one matching turn launches another worker, transfers that turn and neighboring batch text again, and repeats Markdown parsing and all match counting just to return the next 100 locators.  
**Confidence:** 0.99 — The cursor stores the same turn index plus a skip count, but every continuation rebuilds its batch and calls countMatches before using skip. The widget traverses pages serially up to 9,999 results. Exact process-startup duration is unmeasured.

**Causal diff evidence:** The new search calls countMatches(params, batch) on every page (line 185), while its limit branch returns a cursor for the current turn (line 196). Resumed skip is used only after the whole batch has been scanned again.

Searching a common word or character in a large retained reply repeatedly forks and rescans the same text, even with warm host state. Initial local hits can appear promptly, but whole-chat traversal remains unnecessarily expensive.

**Evidence:** chatHistoryQueries.ts:170–185 rebuilds the batch from cursor.index without accounting for skip; line 190 applies skip only when emitting results. countMatches forks at line 74, sends full batch text at line 87, and kills the worker at line 94. chatHistorySearchWorker.ts counts all request/Markdown matches. ChatFindWidget.\_readHistoryMatches traverses sequential 100-hit pages until its 9,999-hit cap; no scanned-count cache exists.

**Suggested direction:** Carry or retain bounded counts for an unfinished scanned batch, scoped to query, flags, and history revision, invalidating on revision or subscription changes. Serve within-batch continuations without launching another scanner.

### 2. [high] Keep uncapped history text processing off the UI thread

**Finding ID:** `PERF-B746F4D9DE03`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatFind/chatFindContent.ts:105</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Renderer-thread Markdown tokens, regex execution, match objects, and history-location allocations.  
**Scaling:** Each recompute processes all B characters and M matches of a reached history reply rather than the previously capped prefix. Multi-megabyte replies are allowed by the paging budget; query changes and continued streaming repeat this work, with content updates debounced at 200 ms.  
**Outcome:** Long main-thread tasks and GC pressure block input, painting, and scrolling while Find is open.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Response plaintext extraction truncated Markdown to 100,000 characters before parsing; segment matching also stopped after 100,000 occurrences.  
**Changed behavior:** Agent Host replies receive historyPartId, so local Find lexes their entire Markdown and enumerates every matching occurrence synchronously, despite retaining only 9,999 results.  
**Confidence:** 0.98 — The old plaintext helper explicitly truncates input at 100,000 characters. The new helper calls marked.lexer on the entire string, and history-identified segments bypass MAX\_SEGMENT\_SCAN. The widget invokes recompute synchronously on query changes and its 200-ms content debounce; exact stall duration is unmeasured.

**Causal diff evidence:** The added historyPartId branch replaces renderAsPlaintext(part.content, FIND\_PLAINTEXT\_OPTIONS) with markdownToPlainText(part.content.value), whose new implementation has no input cap. chatFindModel.ts:141 also makes the former 100,000-match limit conditional on the absence of a history identity.

Opening Find or changing its query in an Agent Host chat containing a multi-megabyte Markdown reply can freeze the workbench. A byte-bounded page still permits a large individual reply, so transcript virtualization does not bound this local scan.

**Evidence:** markdownRenderer.ts:861–865 bounds renderAsPlaintext input at 100,000 characters. New base/common/markdown.ts:90–91 lexes the entire Markdown string. stateToProgressAdapter.ts supplies historyPartId for retained and active replies. chatFindModel.ts:123–143 performs uncapped matching for those segments, including match/location allocations; ChatFindWidget.ts:336–338 recomputes on the renderer thread after the 200-ms content debounce.

**Suggested direction:** Preserve full-history occurrence semantics by moving plaintext extraction and match enumeration to cancellable background work, or cooperatively slicing them with a bounded UI-thread budget. Do not bypass the existing parsing and scan safeguards in synchronous recompute.

### 3. [high] Avoid draining the source transcript for a pinned chat attachment

**Finding ID:** `PERF-D8C1D0D7A40C`  
**Location:** <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:4789</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** History JSON serialization, relay chunk/base64 frames, queued outbound bytes, and client history models.  
**Scaling:** For an already-subscribed source with H hidden turns between its tail and the pin, enough byte/count-bounded pages are emitted to cover all H turns. Repeated references share the expanded source window, but the first old pin can enqueue tens of megabytes in one event-loop turn. ACKs cannot drain the queue during that loop.  
**Outcome:** Bulk serialization and transfer delay prompt submission; sufficiently large suffixes overflow the aggregate relay publish queue and disconnect the client.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Sending a pinned chat attachment issued no history-page notifications. The source transcript was resolved on the host by AgentSideEffects; client openings had already received the full snapshot.  
**Changed behavior:** With the short source subscription, an older pinned attachment synchronously downloads the entire intervening source suffix into the client before the prompt is dispatched, although no source-chat reducer operation needs those turns.  
**Confidence:** 0.97 — The attachment hook reaches a synchronous loop that fetches all intervening subscription pages before prompt dispatch. Relay publication eagerly serializes/enqueues pages, has a 64-MiB aggregate limit, and disposes the lane on send failure. Attachment resolution uses authoritative host turns, not the client window.

**Causal diff evidence:** The new \_loadChatAttachmentTurns invokes \_loadReferencedTurn for attachment.endTurn. Added dispatch handling calls it before \_agentService.dispatchAction. \_loadReferencedTurn loops at lines 4806–4812, sending pages until the old pin lies in the subscribed suffix.

Reuse a pinned reference to an early turn after its source chat has accumulated a long transcript and is open at latest. Sending the prompt triggers an unsolicited download of later source replies, potentially exhausting the 64-MiB relay queue even though every page meets the message-size budget.

**Evidence:** ProtocolServerHandler.ts:3217–3218 invokes attachment hydration before dispatchAction; lines 4786–4812 synchronously generate and send every preceding page to the pin. Paged subscriptions disable channel flow control at line 2460, so AgentHostConnectionChannels.send forwards directly to transport. MissionControlLane.send and \_publish eagerly serialize pages; \_enqueue rejects aggregate queued/in-flight bytes above 64 MiB, and send disposes the lane on failure. AgentSideEffects.ts:2554–2563 already resolves pinned attachment text from authoritative source turns independently of client views.

**Suggested direction:** Do not expand a source subscription merely to resolve a chat attachment; use the existing authoritative attachment-resolution path. Keep genuinely required reducer hydration separate and paced with relay backpressure, rather than synchronously draining all pages.

### 1. serialization-allocation

**Fix location:** `src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:2261` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:2158`  
**Introducing path:** `src/vs/platform/agentHost/browser/agentHostProtocolClient.ts`  
**Introducing commit:** `2b6ab699bce9a529341f64ac9ebed66353198521`  
**Mechanism family:** `serialization-allocation`  
**Performance category:** `network`  
**Confidence:** 0.93

**Mechanism:** Relay chat subscriptions requested an unbounded completed-turn snapshot. The host sent the full retained transcript through relay JSON/chunk encoding, whose 32-MiB reassembly ceiling rejects sufficiently long chats after allocating/serializing the payload.

**Fixed behavior:** The client now requests a ten-turn relay view. ChatHistoryView constructs a normally 4-MiB tail with a hard transport ceiling before the final response is serialized; older turns are transferred only through explicit reads/pages.

**Evidence:** The deleted base request option at agentHostProtocolClient.ts:2158 supplied only bypassReconnectGate, with no history view. Blame identifies the commit carrying that request. Added line 2261 supplies view.turns=10 for WebPubSub chat subscriptions. ProtocolServerHandler.\_pagedChatBaseline replaces completed turns with the bounded ChatHistoryView.baseline result; chunking.ts:113–117 proves the existing 32-MiB rejection. Existing provider restoration remains unchanged.
