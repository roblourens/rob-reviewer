## Findings (1)

### 1. [low] Coalesce the three inventory reads triggered by one marketplace refresh

**Finding ID:** `PERF-D7D96843FBD9`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/pluginMarketplacesWidget.ts:253</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Agent Host inventory IPC calls, Copilot SDK marketplace-list RPC calls, and mapped inventory objects.  
**Scaling:** For K completed marketplace refresh actions, the widget performs 3K inventory reads instead of K, each returning and mapping M marketplaces. The pending set limits mutations per marketplace ID, not inventory reads shared across IDs. Existing workbench-service inventory reads are additional but unchanged and are not attributed to this finding.  
**Outcome:** Excess IPC/RPC traffic and full-inventory allocation, with redundant work on the post-action refresh path.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The quick-pick management loop awaited provider.refresh and then listed the inventory once on the next loop iteration. Existing workbench marketplace-service event subscriptions could also list, but those subscriptions remain unchanged.  
**Changed behavior:** A single provider marketplace refresh now starts three inventory reads in the widget instead of one: two from the provider's paired change events and one from runEntry's finally block. Incrementing generation suppresses older results but does not coalesce or cancel their IPC/RPC work.  
**Confidence:** 0.98 — AgentHostCustomizationMarketplaceInstallProvider.refresh explicitly calls fireMarketplacesChanged(), which synchronously fires both subscribed events. All three widget refresh paths reach listPluginMarketplaces and the SDK RPC without a shared pending request. Call count is statically established; inventory size and RPC duration are not measured.

**Causal diff evidence:** The added provider.onDidChange and provider.onDidChangeMarketplaces subscriptions at pluginMarketplacesWidget.ts:253-254 both immediately invoke refresh(), which calls provider.list at line 318. The added runEntry finally block at line 467 invokes it a third time. Previously the deleted manageProviderMarketplaces loop issued one provider.list when returning from Refresh Marketplace.

Using Refresh Marketplace in the visible Copilot marketplace page performs two avoidable inventory IPC/RPC round trips and full-inventory transformations per action. Repeated refreshes or refreshing several different marketplaces increase backend traffic and allocation pressure; the page's final refresh completion awaits the third read rather than using the already-started authoritative read.

**Evidence:** AgentHostCustomizationMarketplaceInstallProvider.ts:107-110 fires both events; its refresh method at 224-230 calls that helper after the mutation. Its list method at 149-153 forwards to agentHostService.listPluginMarketplaces. LocalAgentHostService.ts:675-676 and AgentHostManagementService.ts:237-241 forward each call independently, and CopilotAgent.ts:3800-3804 / CopilotAgentSession.ts:1351-1352 issue plugins.marketplaces.list RPCs. PluginMarketplacesWidget.refresh has no in-flight guard and only discards stale results after listing and mapping the entire inventory (318-342).

**Suggested direction:** Coalesce the paired provider events and the post-action refresh into one session/provider-scoped scheduled or in-flight inventory read. Let runEntry await that shared post-mutation refresh; retain generation checks and ensure a later mutation marks the inventory dirty for a subsequent read.
