## Findings (2)

### 1. [medium] Filter unrelated root changes before refreshing profile controls

**Finding ID:** `PERF-ADBF90EFD61F`  
**Location:** <code>src/vs/platform/agentHost/common/sandboxProfiles.ts:60</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CodeEditorWidget instances, JSON text models, settings controls, profile validation allocations, and select option DOM nodes  
**Scaling:** One full editor reconstruction per root event while the modal is open; a session transitioning idle→active→idle produces two such events, not one event per token or per chat in an already-active session. Each rendered remote-host row also rebuilds its host's P+1 options per event.  
**Outcome:** Avoidable synchronous UI work and allocation/GC pressure during background agent activity, causing editing or table interaction to stutter.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Session activity and terminal-list changes did not perform any sandbox-profile UI reconstruction; neither this watcher nor the profile controls existed.  
**Changed behavior:** An unrelated root/activeSessionsChanged, root/terminalsChanged, or root configuration update now invokes the profile callbacks even when profiles and the active selection are unchanged.  
**Confidence:** 0.98 — The root subscription emits for every root action, active-turn tracking emits when a session becomes active or idle, and both new consumers synchronously refresh without checking profile changes. The editor explicitly disposes and recreates its CodeEditorWidget and model on each notification. Duration is not measured.

**Causal diff evidence:** The added rootState.onDidChange(() =&gt; onChange()) at line 60 connects all root actions, rather than changes to the profile keys, to the newly added refresh paths.

Leaving Manage Sandbox Profiles open while another client runs turns on the same host causes repeated heavyweight editor reconstruction despite no profile changes. The Remote Environments table likewise repeatedly rebuilds the affected host's dropdown.

**Evidence:** RootStateSubscription.\_isRelevantEnvelope accepts every root/\* action (agentSubscription.ts:303-304), and BaseAgentSubscription.\_reconcile fires onDidChange (287). AgentHostStateManager.\_addChatActiveTurn/\_removeChatActiveTurn dispatch active-count updates on session activity transitions (3271, 3284). SandboxProfilesInput.\_onDidChangeHost fires onDidSelect even for an unchanged saved profile or an edit in progress (170-182). SandboxProfilesEditor.setInput wires that event to \_render (250); \_render clears all controls and DOM (354-359), then \_jsonRow recreates CodeEditorWidget, schema registration, and model (477-502). RemotesTableRenderer.refresh also creates fresh option objects (543), defeating SelectBoxList.setOptions' reference-based array comparison (selectBoxCustom.ts:304-312).

**Suggested direction:** Track host availability/capability, the profiles value, and active selection and notify only when these actually change, resetting the comparison on reconnect. Keep ordinary activity/terminal/root-config updates out of these refresh paths.

### 2. [low] Avoid revalidating all saved profiles on every sandbox read

**Finding ID:** `PERF-409320AAB3AA`  
**Location:** <code>src/vs/platform/agentHost/node/sessionSandbox.ts:22</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Recursive schema-validation CPU work and temporary property-path strings/arrays for the entire profiles bag  
**Scaling:** Adds O(P×F+L) validation per root sandbox read, with P saved profiles, fixed F sandbox fields, and L total domain/path/credential entries across all profiles. This repeats across turns and shell checks, even with a warm unchanged configuration or no active profile; some SDK config computations perform two root reads.  
**Outcome:** Increased agent-host CPU and allocation/GC work on the critical path before starting turns or approving shell tools.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each sandbox resolution validated only the host's sandbox values and session overrides; the cost was independent of saved inactive profiles.  
**Changed behavior:** Every sandbox resolution now recursively validates every saved profile, including every configured domain/path array, before using at most one profile or none.  
**Confidence:** 0.97 — getRootValue has no validation cache and invokes the recursive schema assertion for every read. The new call always reads the entire profiles bag before checking the active ID, and traced callers run before turns and shell permission decisions. Exact list sizes and elapsed time are unmeasured.

**Causal diff evidence:** The added getRootValue(sandboxConfigSchema, SandboxProfiles) at line 22 is evaluated unconditionally by getRootSandboxConfig, including when ActiveSandboxProfile is unset, and replaces the old single Sandbox property read in getSessionSandboxConfig.

Hosts keeping several sandbox variants with substantial domain or path lists pay to validate all inactive variants for every turn and shell-policy check; selecting Default does not remove this overhead.

**Evidence:** AgentConfigurationService.getRootValue (1288-1305) calls schema.assertValid on every invocation without caching. agentHostSchema.buildAssert (207-253) walks object additionalProperties, nested sandbox properties, and every array element. getRootSandboxConfig now reads SandboxProfiles unconditionally; resolveRootSandboxConfig only subsequently selects the active entry. CopilotAgentSession.\_prepareSdkTurn awaits sandbox.applyConfig (7755), which computes the config before serialized-config deduplication (copilotSessionSandbox.ts:550, 568-572). Shell permissions call isShellSandboxedByDefault (copilotAgentSession.ts:9286), whose SDK path computes the config (copilotSessionSandbox.ts:377); the custom engine also resolves it for each getSandboxSetting (agentHostSandboxEngine.ts:132).

**Suggested direction:** Read the active ID first and skip profiles entirely for Default. For active profiles, reuse validated values until the raw profiles value changes, with invalidation on profile replacement and proper handling of invalid/missing values, rather than rescanning the bag for every setting read.
