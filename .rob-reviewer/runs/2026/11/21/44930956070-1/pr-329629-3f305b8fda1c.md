## Findings (1)

### 1. [medium] Cancel the parent-directory scan with the onboarding lookup

**Finding ID:** `PERF-A5FCED47B69D`  
**Location:** <code>src/vs/sessions/contrib/onboardingTours/browser/gitHubRepositoryResolver.ts:54</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Remote resourceResolve requests and filesystem stat/read operations  
**Scaling:** For a selected folder without a nearby .git entry, work is one serial stat per visited parent, bounded by the directory depth and 50 iterations. All remaining iterations can still execute after cancellation; there is no positive/negative cache or coalescing in this resolver.  
**Outcome:** Unnecessary remote and filesystem I/O continues after dismissal or fallback, consuming the connection and remote host resources needed by ongoing work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The V3 tour inserted its static prompt without traversing parent directories or issuing repository-discovery filesystem requests.  
**Changed behavior:** GitHub prompt discovery now traverses parent directories even after its owning tour has been cancelled or its total lookup timeout has selected the fallback prompt.  
**Confidence:** 0.96 — The new resolver accepts no cancellation token and awaits each parent stat without checking cancellation. The caller explicitly cancels on its six-second deadline, and the run-step presentation also cancels on dismissal. Remote Agent Host stat maps directly to an uncached resourceResolve request, establishing the continued I/O independently of its measured duration.

**Causal diff evidence:** The added loop at lines 54–56 schedules sequential statIfExists calls for up to 50 parents. The added caller at newSessionViewV3Prompt.ts:427 does not pass its token; cancellation at :181 therefore cannot stop subsequent iterations.

Dismiss the tour while it is discovering a nested remote workspace, or let discovery exceed the six-second timeout on a slow connection. The prompt flow has already stopped or fallen back, but the scan continues sending requests through the remaining ancestors.

**Evidence:** newSessionViewV3Prompt.ts:170–185 races discovery against a timeout and cancels operationCts; :395 checks cancellation only before entering repository resolution, then :427 awaits the tokenless resolver. gitHubRepositoryResolver.ts:52–76 checks only iteration count and filesystem root. FileService.stat delegates to provider.stat (fileService.ts:313–318); AHPFileSystemProvider.stat calls \_resolve (agentHostFileSystemProvider.ts:387–404), which sends connection.resourceResolve (:615–616), and RemoteAgentHostProtocolClient.resourceResolve sends a protocol request (:1161–1162). RunOnboardingStepPresentation.runStep races the callback against cancellation, so dismissal does not wait for this scan.

**Suggested direction:** Thread the lookup token through git-config discovery, check it before each stat/read and after awaited operations, and recheck it before entering the Git-extension fallback. Individual stats need not gain a cancellation API; stop scheduling additional operations once the current one settles.

### Scenario 5: Dismissal, timeout, or workspace replacement during personalized lookup

- Critical path: Run-step dismissal races cancellation so the UI can proceed immediately. The total GitHub timeout selects the default prompt at six seconds. Repository-context changes cause a bounded retry after the current awaited lookup and cancel that attempt's outstanding GitHub work.
- Scaling input: Remaining directory depth when cancellation occurs, multiplied by remote round-trip latency. A typical nested remote workspace is sufficient; reaching the maximum cap is not required.
- Effective concurrency: The offending directory requests remain serial but continue being newly scheduled after cancellation. GitHub requests are independently bounded and cancelled on timeout/attempt completion; workspace retries are sequential and share the total time budget.
- Cache behavior: Tokenless directory discovery has no cached positive or negative results. In contrast, HTTP requests receive cancellation tokens and the browser implementation checks already-cancelled tokens and aborts active fetches.
- Mechanism confidence: High: the caller cancels explicitly, the presentation stops waiting, and the new resolver accepts no token or cancellation checks while the provider sends uncached requests.
- Magnitude uncertainty: How often users dismiss during discovery or use slow deep remote paths is unknown; the number of remaining requests and their duration are not measured.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/onboardingTours/browser/gitHubRepositoryResolver.ts:54–76; src/vs/platform/agentHost/common/agentHostFileSystemProvider.ts:stat/\_resolve</code>: Continue remote ancestor metadata requests after the owning lookup has been cancelled.; cardinality: One request for each remaining parent after the in-flight stat settles, up to the remaining D within the 50-iteration cap; reads can also continue if a .git entry is found. No caching or coalescing eliminates them.
    - Introduced by diff: true; previous behavior: Cancellation stopped the existing prompt animation; no directory-discovery request chain existed.; critical-path effect: After dismissal/fallback this is off the original critical path, but continues consuming remote connection and filesystem resources. A slow lookup can outlive the foreground deadline.
- Verdict: Reported one medium-severity introduced cleanup-lifecycle I/O regression with a bounded fix: stop issuing additional stats/reads when cancellation is observed.
