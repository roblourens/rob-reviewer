### Scenario 1: Discover and open repositories at extension startup or when an editor exposes a new repository

- Critical path: Repository-root and git-directory discovery, realpath resolution, trust request, Source Control creation, and watcher setup precede publishing the opened repository. Initial status is queued without awaiting it, so Git metadata/status does not block repository publication.
- Scaling input: Distinct repository roots after existing-repository checks; child discovery remains capped by configured submodule/worktree detection limits.
- Effective concurrency: Model.openRepository is sequentialized on the Model instance. Initial status has a shared limiter of five repositories; each status itself performs parallel metadata reads.
- Cache behavior: Already-open exact repositories return early. Detached reuse requires matching root, git directories, bare status, and realpath, but still performs discovery/trust checks. No production caller currently populates the detached cache. Resource-state publication tracks array identity; count/template setters also suppress unchanged IPC.
- Mechanism confidence: High: complete opening diff, sequentialize decorator, initial-status limiter, watcher implementations, and SCM batching were inspected.
- Magnitude uncertainty: Repository counts and filesystem/process latency vary; no durations were measured.
- Expensive boundaries:
  - subprocess at <code>extensions/git/src/model.ts:openRepository -&gt; extensions/git/src/git.ts:getRepositoryRoot/getRepositoryDotGit</code>: Run rev-parse for root discovery and git-directory discovery, with additional root normalization calls only for applicable path cases.; cardinality: Normally two Git subprocesses per newly opened distinct root, not per changed file; existing exact repositories skip discovery.

  - filesystem at <code>extensions/git/src/git.ts:getRepositoryDotGit; extensions/git/src/model.ts:getRepositoryRootRealPath; extensions/git/src/repository.ts:watchRepository/DotGitWatcher</code>: Read git config and resolve realpath; establish a recursive working-tree watcher, two git-directory/worktrees watchers, and an upstream watcher when applicable.; cardinality: One config read and one realpath resolution per new opening; three baseline watchers per attached repository, plus a conditional upstream watcher.

  - IPC at <code>extensions/git/src/model.ts:openRepository; extensions/git/src/sourceControl.ts:GitSourceControl.constructor; src/vs/workbench/api/common/extHostSCM.ts:addResourceGroups</code>: Request resource trust and register/configure Source Control and its four resource groups.; cardinality: One trust request and one Source Control per distinct attached root; four resource groups are registered together by the existing 100ms debounce.

- Verdict: No reportable regression. Extraction retains discovery call counts, watcher cardinality, initial-status concurrency, and the non-awaited status scheduling.

### Scenario 2: Refresh status after file changes, staging, committing, or relevant configuration changes

- Critical path: Write operations await the same model refresh: parallel metadata/template reads finish before parallel status and refs reads, then resource groups and status notifications are published. Filesystem-triggered refresh is deferred until idle/focused.
- Scaling input: Changed resources up to the configured status limit (default 10000), refs, attached repository count, and registered worktrees; worktree enumeration performs two reads per linked worktree.
- Effective concurrency: Metadata requests use Promise.all, followed by status/refs Promise.all. Initial statuses are globally limited to five. Runtime status is throttled per Repository with at most one current and one pending call; file events additionally use a 1000ms debounce and 5000ms post-refresh wait. Direct configuration refresh scheduling is unchanged.
- Cache behavior: Virtual-filesystem configuration is initialized once per Repository, including a cached false result. Commit-template absence remains uncached and is queried during refresh as before. Repository-owned arrays remove defensive-copy getter costs; GitSourceControl copies only groups with new array identities. SCM count/template setters deduplicate equal values.
- Mechanism confidence: High for scheduling, boundaries, and deduplication: refresh callers, status parser limit, SCM setters, and snapshot batching were traced.
- Magnitude uncertainty: Large working trees and refs can make existing refresh work expensive. The new pre-status update can recompute the tracked-count filter, but it does not add group serialization and replaces several prior getter copies; no high-confidence net degradation was established.
- Expensive boundaries:
  - subprocess at <code>extensions/git/src/repository.ts:\_updateModelState/getInputTemplate/getStatus/getRefs; extensions/git/src/git.ts:getHEADRef/getCommitTemplate/getStatus/getRefs</code>: Resolve branch/upstream, obtain commit template, run git status and for-each-ref, with conditional rebase-commit and cold virtual-filesystem config queries.; cardinality: One status and one refs subprocess per completed refresh, plus a template query when merge/squash messages are absent and branch/upstream-dependent queries; no new per-resource subprocesses.
    - Introduced by diff: false; previous behavior: Same two-phase refresh and conditional subprocess calls were present.; critical-path effect: Awaited by status/write-operation completion; status/refs begin after metadata completes.
  - filesystem at <code>extensions/git/src/repository.ts:getRebaseCommit/isMergeInProgress/isCherryPickInProgress/getInputTemplate; extensions/git/src/git.ts:getHEADFS/getRemotesFS/getSubmodules/getWorktreesFS</code>: Read HEAD, config, .gitmodules, merge/squash/rebase state, optional template contents, and worktree metadata.; cardinality: A fixed set of reads/probes per refresh plus main HEAD/readdir and two sequential reads per linked worktree; unchanged fallback Git reads apply on existing failure paths.
    - Introduced by diff: false; previous behavior: Identical metadata reads and worktree enumeration were already required.; critical-path effect: Metadata reads are on the refresh critical path; worktree reads remain sequential within their metadata task.
  - serialization at <code>extensions/git/src/sourceControl.ts:update/updateCount; src/vs/workbench/api/common/extHostSCM.ts:\_takeResourceStateSnapshot/updateResourceStates</code>: Copy changed resource arrays into SCM, sort/diff snapshots, serialize resource splices, and update count/template/context information.; cardinality: At most four changed groups per model publication. - Verdict: No high-confidence performance regression. No boundary fan-out was introduced, and unchanged resource groups are not republished by the extra update call.

### Scenario 3: Periodic automatic fetch and SCM operation progress

- Critical path: Automatic fetch waits for an idle/focused repository and runs in the background. Progress/input enablement responds to existing operation events rather than introducing a new awaited operation.
- Scaling input: Attached repositories with autofetch enabled and configured fetch period; remote count when fetch-all is selected.
- Effective concurrency: One fetch loop per enabled repository with per-method throttling; no new cross-repository limiter or burst is introduced. The idle wait yields before the attachment is assigned, preventing synchronous startup fetch execution during constructor setup.
- Cache behavior: Enablement/configuration is maintained per AutoFetcher. Detach disposes the fetcher; normal attachment still creates one fetcher per repository. Authentication-failure disabling and periodic wake-up behavior are unchanged.
- Mechanism confidence: High: AutoFetcher construction, idle wait, loop, throttle, and extracted ProgressManager were inspected.
- Magnitude uncertainty: Network latency and enabled-repository counts are workload-dependent; no measurement was made.
- Expensive boundaries:
  - network at <code>extensions/git/src/autofetch.ts:run -&gt; extensions/git/src/repository.ts:\_fetch -&gt; underlying Git fetch</code>: Fetch default or all remotes through Git.; cardinality: One fetch operation per enabled repository per loop period, with Git remote fan-out for fetch-all unchanged.
    - Introduced by diff: false; previous behavior: Repository construction created the same AutoFetcher, loop, fetch options, and throttling.; critical-path effect: Off the repository-opening critical path; awaited within each background loop.
  - IPC at <code>extensions/git/src/sourceControl.ts:ProgressManager</code>: Update commit input enablement and invoke SCM progress for operation lifecycle events.; cardinality: Existing operation-event-driven updates; progress end remains debounced by 300ms.
    - Introduced by diff: false; previous behavior: Same ProgressManager implementation lived in repository.ts.; critical-path effect: Progress observation does not add awaited Git work.
- Verdict: No regression. Expensive fetch scheduling is preserved, and attachment disposal owns the existing background fetcher.

### Scenario 6: Detach/reopen a repository, or close a parent repository while extensions retain API objects

- Critical path: Detach recursively removes children, publishes close events, and disposes SCM/watchers/fetchers. Reopen reruns discovery and attaches a new SCM before publication. Normal close still permits held API objects to perform operations.
- Scaling input: Attached parent/child repository tree and, if detach becomes reachable, distinct detached roots retained for the Model lifetime. Current detachRepository callers are smoke tests only.
- Effective concurrency: Detach/close cleanup is synchronous; reopening is Model-sequentialized and first status uses the shared five-repository limiter. In-flight model updates are canceled/dropped when their attachment changes.
- Cache behavior: Detached repositories are reused only for matching locations, disposed on location mismatch or Model disposal, and removed from the detached list when reopened. Reattachment clears model state and resets first-status. Normal close retains its disposed SCM as before.
- Mechanism confidence: High for ownership, cancellation, reuse checks, and the absence of production detach callers: repository-wide caller search and smoke-test additions were inspected.
- Magnitude uncertainty: Detached-cache growth and repeated detach/attach overhead have no current production trigger. A future caller would need a separate lifecycle/cardinality review.
- Expensive boundaries:
  - IPC at <code>extensions/git/src/model.ts:openRepository.detach/dispose; extensions/git/src/repository.ts:detachSourceControl/dispose; src/vs/workbench/api/common/extHostSCM.ts:dispose</code>: Dispose/unregister SCM groups/providers and release watcher registrations; reattach recreates SCM/watcher registrations.; cardinality: One attachment cleanup per repository in the affected child tree; closed guard prevents duplicate close cleanup/events. Reopen recreates the same attachment resources as a fresh open.
    - Introduced by diff: true; previous behavior: Normal close performed equivalent cleanup while discarding Repository. Detach/reuse did not exist; normal parent close could reenter a child's close path.; critical-path effect: Cleanup occurs during detach/close; creation precedes reopened-repository publication.
  - subprocess at <code>extensions/git/src/model.ts:openRepository; extensions/git/src/api/api1.ts:ApiRepository operations -&gt; extensions/git/src/repository.ts:run/getCommit</code>: Reopening performs existing discovery and queued status. Held normally closed API objects can still run requested Git operations; detached objects reject before spawning.; cardinality: Existing discovery/status calls per reopen and requested Git operations per retained API invocation; detach itself adds no Git process.
    - Introduced by diff: false; previous behavior: Reopening a closed root created a fresh Repository with the same discovery/status boundaries. Held closed API objects already could perform operations.; critical-path effect: Reopen discovery is awaited; initial status is not. Requested held-object operations retain their existing awaited behavior.
- Verdict: No currently reachable retention/concurrency regression. Normal cleanup preserves its prior expensive boundaries, and duplicate close handling is bounded.
