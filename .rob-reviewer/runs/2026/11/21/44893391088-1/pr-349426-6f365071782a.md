## Findings (1)

### 1. [medium] Resolve explicit fork targets without listing the whole catalog

**Finding ID:** `PERF-3A1E1D6211DF`  
**Location:** <code>src/vs/platform/agentHost/node/shared/sessionServerTools.ts:1721</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Session-catalog database batch reads, decoded metadata objects for unrelated sessions, and provider/session-storage reads for ineligible rows.  
**Scaling:** For N visible registered sessions, each non-overlapping explicit fork requests ceil(N/400) catalog batches and reconstructs O(N) metadata; F ineligible rows add F fallback resolutions limited to four concurrently. Concurrent calls in the same catalog mode coalesce, but successive forks recompute the catalog.  
**Outcome:** Increased fork and parent-agent continuation latency, unnecessary database/provider I/O, and catalog-sized allocation work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The existing UI fork used the known source chat and invoked createChat without enumerating unrelated sessions. No fork\_session handler existed. The new tool's omitted-session branch also resolves ownership directly without a listing.  
**Changed behavior:** The new agent-triggered fork path performs a complete session-catalog computation before every non-overlapping invocation with an explicit session link, even when that source is already loaded. Only concurrent listings share a computation; a warm source does not avoid the global read.  
**Confidence:** 0.94 — The new explicit-session branch unconditionally awaits listSessions before reading the selected chat. Its accessor resolves to AgentService.listSessions, whose settled computations are discarded; the catalog reader batches 400 sessions with concurrency four. The existing getSession accessor supplies one session's recorded chats, and live targets can use its summary fast path. Exact elapsed time depends on catalog size and fallback eligibility.

**Causal diff evidence:** Added line 1721 awaits listSessions whenever session is supplied, including a link to the already-running calling session. Lines 1722 and 1727 then consume only the selected session and its chats. The pre-existing UI fork path in baseAgentHostSessionsProvider.forkChat calls connection.createChat directly without a whole-catalog listing.

Forking a linked chat in a host with a large saved-session catalog delays the tool result and the calling agent's continuation on unrelated catalog I/O and metadata reconstruction, even if the source chat is warm. Ineligible catalog rows can also cause unrelated provider and session-database reads.

**Evidence:** AgentService's sessionServerToolAccessor.listSessions calls this.listSessions (agentService.ts:2357). listSessions and \_startSessionListComputation (5527-5570, 5648-5674) share in-flight work but clear settled entries. \_computeSessions reads all visible registered sessions and calls \_catalogListReader.readMany (5706-5733); agentHostCatalogListReader.ts:94-103 issues ceil(N/400) readSessionListCatalogs batches with Limiter(4), then decodes metadata for all N sessions. Ineligible rows additionally use provider/session-storage fallbacks under Limiter(4) (agentService.ts:5779-5835). In contrast, accessor.getSession resolves to \_getSessionMetadata (3541-3561), which looks up one registry entry and, for a live source, returns its summary including recorded chats (3592-3611). resolveLinkedChat and resolveDefaultChat accept that single metadata entry.

**Suggested direction:** Parse the explicit link with the existing parser and resolve its session through the existing getSession accessor, retaining equivalent known/visible-session validation and resolving the chat against that session's recorded chats. At minimum, fast-path explicit links to the already-known calling session so they do not enumerate unrelated sessions.
