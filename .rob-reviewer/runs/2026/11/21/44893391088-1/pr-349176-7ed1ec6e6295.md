### Scenario 3: Send a peer reply to an idle or busy chat, then replace or cancel a queued version.

- Critical path: Source lookup and the existing listSessions request precede target validation. Normal sends enter the per-target sequencer, restore a cold destination if necessary, then queue or admit one Message. Replacement/cancellation updates existing pending state without starting additional provider work.
- Scaling input: K message operations, T live tool calls, C distinct target chats and F catalog fallback sessions. New attribution stores one small source/version record per exact live Message. Ordinary sends retain the existing 100-per-source-session/hour limit; replacement/cancellation do not obtain a new global limit.
- Effective concurrency: Normal sends are serialized per target chat by SequencerByKey; different targets can proceed concurrently. Catalog work occurs before that sequencer and retains existing coalescing/fallback limiting. Replacement/cancellation remains synchronous after catalog resolution.
- Cache behavior: listSessions coalesces concurrent mode/epoch computations, but settled results are removed rather than permanently cached. Cold target restoration is shared per session and hydration per chat; warm target state bypasses restore. Failed restores clear in-flight state for retry. WeakMap attribution neither retains dead message versions nor reconstructs restored evidence.
- Mechanism confidence: High: per-target serialization, cold/warm guards, restore coalescing and replacement ownership were inspected. No new database, provider or transcript read was added for attribution.
- Magnitude uncertainty: Catalog size, reply rates and restore duration vary and were not measured. They affect unchanged costs, not diff-introduced boundary fan-out.

### Scenario 4: Track provider-promoted steering successors and background workers after the parent turn finishes.

- Critical path: Provider progress already arrives before host tracking. The diff finds the pending steering message using the same collection search as the former some(), and obtains worker roots from a direct live spawning-call lookup. Every tool start on a steering successor may read the provider's interaction snapshot synchronously; completion performs the already-existing interaction read.
- Scaling input: Tool starts in steering successor turns, pending steering-message count, and live/historical root timing entries. Copilot's interaction snapshots copy at most 64 IDs from an LRU with 1000 turns, not full transcript/model history.
- Effective concurrency: Synchronous host progress processing remains unchanged. Attribution introduces no asynchronous task, fan-out, ancestor traversal or new worker spawn; independent workers retain their existing provider concurrency.
- Cache behavior: Non-steering trigger access is a direct map lookup. Copilot getTurnInteraction uses live chat maps plus the bounded interaction LRU. Roots are shared small ID objects; tool timings clear on completion/turn teardown, root timings on existing truncation/session disposal. Reused workers without fresh evidence perform no external recovery lookup.
- Mechanism confidence: High: the only implemented getTurnInteraction resolves bounded in-memory snapshots, and its interaction array cap was verified. Spawn lookup is direct and lifecycle cleanup is preserved.
- Magnitude uncertainty: Steering/tool-start frequency is not profiled. The extra snapshot allocation is bounded to 64 references and does not establish substantial CPU/GC pressure on realistic usage.

### Scenario 5: Execute a Codex delegation callback after delayed approval while a successor turn changes the item map.

- Critical path: The existing app-server callback resolves its pending item, possibly awaits approval, executes the same host tool once and returns its result. The diff captures the delegation call ID before approval instead of rereading it afterward.
- Scaling input: One pending callback per dynamic tool invocation, regardless of approval duration or number of later turns. Captured state is an ID/reference, not an approval-time transcript snapshot.
- Effective concurrency: Pending approvals await their own decisions; other turns may progress meanwhile as before. Host delegation tools retain the creation/send concurrency and per-target ordering described above.
- Cache behavior: Uses existing thread/session and item-to-tool maps. Capturing the call ID does not introduce caches, retry loops, successor-turn scans or restored attribution recovery.
- Mechanism confidence: High: changed code only pins and selects the call ID; approval and executeTool await structure is unchanged.

- Verdict: No performance regression or concrete performance-regression fix: this is attribution/correlation behavior, with unchanged expensive execution and IPC cardinality.
