**Relevant issue families:** repeated-work, cleanup-lifecycle, concurrency-burst, boundary-fanout, eager-work

### Scenario 1: A chat tab leaves a chat window while one or more of that chat's canvas editors are open

- Critical path: The chat-window chats observable invalidates the new canvas autorun; it synchronously checks tracked canvas inputs and starts closeInput for disallowed groups. Editor closing and browser-view destruction are not awaited by the chat-removal operation, so cleanup is off that interaction's critical path.
- Scaling input: Number C of currently tracked/open canvas inputs, across visible and retained working sets; invalid cleanup cardinality is the subset belonging to chats that left the window.
- Effective concurrency: The autorun checks inputs serially. Invalid inputs start independent async closeInput operations without a shared limiter; model disposal synchronously initiates one fire-and-forget destroy request per resolved canvas model.
- Cache behavior: No cache is involved. Inputs without a resolved browser model avoid browser-view destruction; each invalid input is synchronously removed from the maps before asynchronous editor closure, preventing repeat cleanup of the same input.
- Mechanism confidence: High: the observable dependency, per-input iteration, close path, and BrowserView destruction call are directly traced.
- Magnitude uncertainty: The live canvas collection is provider-supplied and has no explicit cap, but repository scenarios and tests establish only small numbers of simultaneously open canvases. No evidence shows a realistic count large enough for the required off-path cleanup burst to regress responsiveness.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/canvases/electron-browser/canvasService.ts:closeInput/deletePresentation/disposePresentationModel; src/vs/workbench/contrib/browserView/common/browserView.ts:BrowserViewModel.dispose</code>: Destroy the external BrowserView backing a canvas model via BrowserViewModel.dispose -&gt; destroyBrowserView.; cardinality: At most one destroy request for each invalid open canvas that has a resolved model; C requests when all C such canvases leave.
    - Introduced by diff: true; previous behavior: The canvas editor and its model remained open after the chat left, so this cleanup boundary was not reached on this event.; critical-path effect: Fire-and-forget cleanup; it does not block the chat tab leaving, though many models can create a cleanup burst.
- Verdict: No finding. The added work releases heavyweight browser resources that previously remained live, is proportional to resources that must be cleaned up, and runs off the chat-removal critical path.

### Scenario 2: A canvas editor opens or is moved between main-window and chat-window editor groups

- Critical path: An EDITOR\_OPEN event and presentation-state signals run the new synchronous validation before subsequent UI work; actual BrowserView creation and URL loading remain on the existing canvas-resolution path and were not moved by the diff.
- Scaling input: C tracked canvas inputs, G editor groups, and E open editors. Each validation pass calls findEditors for each non-opening input; lookup uses a resource counter fast check and then scans groups containing matching resources.
- Effective concurrency: Validation is synchronous and serial. Existing canvas opens and BrowserView creation can already proceed concurrently; the diff does not add concurrency to those boundaries.
- Cache behavior: EditorService uses EditorsObserver.hasEditors as a resource-presence fast path. No new cache is introduced; validation reacts only to canvas opens, presentation lifecycle signals, and relevant chat-window observables rather than render, scroll, or input frames.
- Mechanism confidence: High for the synchronous scan and its scaling; low for any user-visible degradation at realistic cardinality.
- Magnitude uncertainty: The new scan is multiplicative in open canvases and editors, but it runs on lifecycle events rather than a hot frame/input path, and no realistic high-cardinality restore/open case is established by the repository.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/canvases/electron-browser/canvasService.ts:resolveCanvasModel</code>: Create an external BrowserView for a canvas and load its URL.; cardinality: One creation/load per canvas model cache miss; reused presentations avoid creation.
    - Introduced by diff: false; previous behavior: The same create/load occurred when a canvas model first resolved.; critical-path effect: Required for first canvas rendering and unchanged by this PR; the new group validation itself performs no IPC/network operation.
- Verdict: No finding. The scan is newly added repeated CPU work, but available evidence does not establish a concrete, realistic latency regression rather than a bounded lifecycle check.

### Scenario 3: The Changes entry is invoked in a chat window with or without an exact chat-scoped Changes tab

- Critical path: If the exact resource is already open, the command only scans the group's editor list and activates it. Otherwise it opens a chat-scoped SessionChangesEditorInput; resolving that active editor builds the multi-diff resource list and resolves text models before the view is ready.
- Scaling input: E editors in the target group for exact-resource matching; on a miss, F changed files in the selected chat, with up to two text-model references per file.
- Effective concurrency: The editor match is serial. MultiDiff model resolution uses paired Promise.allSettled calls per file and the existing multi-diff machinery; the diff adds no limiter or scheduling change inside that machinery.
- Cache behavior: An already-open exact chat resource is reused. MultiDiff inputs lazily create their inner input, and when a Changes editor stops being shown its view model is cleared unless another group shows the same input. Different chat resources intentionally do not share models because their change sets differ.
- Mechanism confidence: High for the miss path and per-file model resolution; high that the changed matching can cause a new open where a non-exact session tab exists.
- Magnitude uncertainty: File count and model cache warmth vary. The newly reached work is tied to the intentional requirement for a distinct authoritative chat change set, and inactive replaced Changes inputs release their view models, so no unbounded retained-model growth is established.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:\_createModel</code>: Resolve original and modified text models for each changed file through ITextModelService while opening a new chat-scoped multi-diff editor.; cardinality: Up to 2F model-reference resolutions for F changed files, with model-service reuse where available.
    - Introduced by diff: true; previous behavior: Any Changes tab resolving to the same session could be activated, avoiding a new resolve but potentially showing another chat's changes; when no session tab existed, the same open/resolve path already ran.; critical-path effect: On the critical path to rendering a newly opened Changes editor. For a window that only has a session-level or another chat's tab, the stricter match can newly take this path instead of activating the wrong tab.
- Verdict: No finding. The additional resolve is necessary to avoid presenting a different chat's data, exact resources are reused thereafter, and repository cleanup releases inactive view models; there is no bounded alternative proven that preserves the required semantics while eliminating the work.

### Scenario 4: A chat-scoped Changes tab is created, displayed, or updated after a chat rename/session change

- Critical path: Construction parses the resource twice, subscribes one derived title observer, and computes the matching chat title. A rename/session event recomputes the session lookup and scans that session's chats before firing a label update; no external operation blocks tab display.
- Scaling input: T open chat-scoped Changes inputs and H chats in each associated session; a global session-change event can cause O(T\*H) in-memory URI comparisons.
- Effective concurrency: All observer recomputation is synchronous and serial on the event dispatch. There is no queue, subprocess, IPC, filesystem, database, or network work.
- Cache behavior: The derived observable caches/comparatively propagates its string value, and each listener is disposed with its editor input. Session-level Changes inputs use a constant observable and do not subscribe.
- Mechanism confidence: High for listener lifetime and O(T\*H) recomputation; low for material performance impact.
- Magnitude uncertainty: Many simultaneous chat-scoped Changes tabs are possible, but normal editor cardinality is small and session-change events are lifecycle/provider updates rather than per-frame events. No evidence establishes enough T or H to cause visible label-update latency.
- Expensive boundaries: none found
- Verdict: No finding. The work is bounded to live editor inputs, disposed correctly, and no realistic hot-path or boundary amplification is demonstrated.

**Summary:** Completed the performance pass over all 12 changed files and relevant canvas, editor, BrowserView, session-management, and multi-diff call paths. The diff adds lifecycle-time canvas validation and required cleanup, plus exact chat Changes matching and reactive labels. No actionable, high-confidence performance regression was established.
