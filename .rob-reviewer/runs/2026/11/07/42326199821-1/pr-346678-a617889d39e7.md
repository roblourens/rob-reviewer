# Performance review: Agents window: start a new session in a chat window

## Findings (2)

### 1. [medium] Coalesce full draft snapshots off the typing path

**Finding ID:** `PERF-D8AB1F24CC0C`  
**Location:** <code>src/vs/workbench/contrib/sessions/browser/chat/sharedChatInputComposer.ts:750</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Full prompt strings plus cloned attachment/reference arrays and projection objects  
**Scaling:** Each edit performs work proportional to the current prompt length plus attachment/reference count; typing a prompt from length 0 to N makes the new snapshot work grow quadratically in N, with additional duplicate events possible from inline-reference updates.  
**Outcome:** Synchronous typing latency and CPU/GC pressure for long or attachment-rich prompts  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Without a host input snapshot, SharedChatInputComposer persisted its full draft only from \`saveState\`; ordinary model-content changes did not rebuild a complete draft snapshot. Chat-window composers did not previously exist.  
**Changed behavior:** The new model-content listener synchronously calls \`\_writeInputSnapshot\` for every edit. That method calls \`getInputValue\`, clones all attachments, and projects/clones draft references before replacing the snapshot.  
**Confidence:** 0.98 — The synchronous event path and whole-model/projection calls are explicit. The exact visible delay depends on prompt and reference size, so the magnitude is medium, but the repeated allocation mechanism and scaling are certain.

**Causal diff evidence:** RIGHT line 750 newly attaches full snapshot reconstruction to every editor model-content event for hosted composers; previously the full draft was written only by \`saveState\`.

Editing or pasting a long prompt in a chat-window composer repeatedly reconstructs the entire prompt state on the UI input event, which can make continued typing lag and generate avoidable garbage.

**Evidence:** RIGHT line 750 registers \`write\` directly on every \`onDidChangeModelContent\`. \`\_writeInputSnapshot\` at line 781 reads the complete prompt and clones attachments/references. \`ChatWidget.getInput()\` delegates to \`ChatInputPart.getPromptText()\`, whose inline-attachment path projects \`model.getValue()\` across pills/references; \`\_getDraftReferences\` invokes projection again, so a text edit can traverse/materialize the full model twice before returning.

**Suggested direction:** Keep edits cheap by marking the snapshot dirty and coalescing reconstruction, then synchronously flush the latest editor state on host save, view handoff/disposal, and send boundaries so reload and failure-recovery semantics remain exact.

### 2. [medium] Defer the hidden chat group for composer-only tabs

**Finding ID:** `PERF-B1427871FB17`  
**Location:** <code>src/vs/sessions/contrib/chatEditor/browser/chatEditorContent.ts:142</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** DOM nodes, context keys, service/listener objects, and UI component instances  
**Scaling:** The retained cost grows once per unsent composer tab; inactive view-editor tabs remain alive until their input closes or moves.  
**Outcome:** Higher composer-open latency and retained UI memory  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Before this change, ChatEditorContent represented an actual chat, so its eagerly constructed ChatGroupView was the visible/required content. There was no composer-only path that constructed a second view while leaving the group unused.  
**Changed behavior:** The added composer branch runs after the constructor has already created ChatGroupView, then creates a separate NewChatView and replaces the group's DOM element. The hidden group remains owned by ChatEditorContent.  
**Confidence:** 0.95 — The constructor order, separate composer view, and inactive-view retention are directly established in the code. Exact bytes and milliseconds depend on component implementations and how many drafts users keep open, so severity is medium rather than high.

**Causal diff evidence:** RIGHT line 142 adds a composer-only display state to ChatEditorContent even though the same instance has already eagerly constructed its ChatGroupView; this newly puts that full tree on every unsent-composer path.

Opening an unsent composer synchronously constructs both the full chat-group shell and the composer view. Each additional unsent tab retains the unused group while hidden, increasing open latency and memory in chat windows with several drafts.

**Evidence:** ChatEditorContent eagerly creates ChatGroupView at line 134 before the added \`showsComposer\` branch at line 142; \`\_showComposer\` then creates a separate view at line 168 and replaces the container child. ChatGroupView's constructor creates a scoped instantiation service/context keys, SessionRemoteConnection, header, composite bar, banner, activity bar, and their DOM/listeners. ViewEditorPane explicitly retains inactive view-editor views in \`hiddenViews\`, so switching tabs does not release this unused tree.

**Suggested direction:** Create the ChatGroupView lazily when chat content first becomes available (or dispose/recreate it across the composer-to-chat handoff), so a composer-only tab owns only its NewChatView while preserving the existing focus/model handoff.
