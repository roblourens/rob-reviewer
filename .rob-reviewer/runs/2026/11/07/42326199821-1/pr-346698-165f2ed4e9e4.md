- Critical path: For each colored header template that enters the rendered viewport, renderSessionHeaderIcon synchronously constructs SessionHeaderLabelColor; its constructor resolves three theme colors, computes normal and hover contrast, and writes one class plus two CSS custom properties before the row paint can complete.
- Scaling input: Work scales with the effective number of simultaneously rendered colored headers, including a possible sticky-header copy, rather than all stored groups; WorkbenchObjectTree virtualizes off-screen rows.
- Effective concurrency: All contrast calculations and DOM writes run serially on the UI thread during row rendering; there is no queue, parallelism, or asynchronous boundary.

- Mechanism confidence: High: the constructor call, synchronous updateStyles call, virtualized renderer lifecycle, and disposal through elementDisposables are directly traced.
- Magnitude uncertainty: Exact viewport/header counts and rerender frequency vary, but each unit performs only bounded color arithmetic and three style/class mutations; realistic visible cardinality is bounded by the viewport.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff adds bounded synchronous work per visible colored header, but does not force layout, scan an unbounded collection, retain off-screen listeners, or cross an expensive boundary.

### Scenario 2: Switch the active color theme while colored Sessions headers are visible

- Critical path: The existing theme service synchronously notifies one newly added Themable listener per rendered colored header; each listener recomputes two contrast colors and updates that header's class and CSS properties before the theme update settles.
- Scaling input: Fan-out scales with currently rendered colored header templates, including sticky copies, not the total session/group history.
- Effective concurrency: Theme listeners execute serially on the UI thread; no subprocess, IPC, filesystem, database, or network work is reached.
- Cache behavior: Each header recomputes on a theme change because the background, hover background, and selected custom color can all change. Disposing or recycling a row unregisters its listener, so there is no stale-listener accumulation across scrolling.
- Mechanism confidence: High: Themable registers onDidColorThemeChange, and both section/group renderers clear elementDisposables on rerender and disposal.
- Magnitude uncertainty: Theme changes are user-driven and infrequent; the precise number of visible customized headers varies, but virtualization bounds it.
- Expensive boundaries: none found
- Verdict: No reportable regression. The new fan-out is bounded to live rendered headers and performs small in-memory arithmetic plus DOM writes without layout reads or retained-growth behavior.
