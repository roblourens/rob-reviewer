# Performance review: Create isolated side chat for terminal command explanations

[PR #346633](https://github.com/microsoft/vscode/pull/346633) at `4e4d7702f585bd73bccbe755551d295724e55c10`

## Findings (1)

### 1. [medium] Keep the context flag off the first-send disk path

**Finding ID:** `PERF-1C36664DF5D3`  
**Location:** <code>src/vs/platform/agentHost/node/chatContributions/sideChat/sideChatContribution.ts:53</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** filesystem stat operations, SQLite database opens/queries, and the paired immediate metadata write  
**Scaling:** One immediate metadata write plus one stat/query is added per created side chat; the read repeats for each unsuccessful first-turn attempt until a turn completes. The cost is independent of history coalescing and applies to both contextual and isolated side chats.  
**Outcome:** blocked first-request critical path and increased side-chat latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** onOutgoingTurn was synchronous and built/injected the source context entirely from live state; it performed no filesystem or database operation before provider dispatch, and side-chat creation did not persist this extra metadata key.  
**Changed behavior:** The first outgoing turn of every side chat now waits for persisted metadata lookup, after creation has already waited for a new immediate metadata write. The contribution remains unseeded until a successful turn ends, so failed/retried first turns perform the lookup again.  
**Confidence:** 0.98 — The changed call path is direct and fully traced: SideChatContribution.onOutgoingTurn is awaited serially by AgentHostChatContributions.outgoingTurn, AgentSideEffects awaits that before agent.chats.sendMessage, tryOpenDatabase always performs a filesystem stat, and getMetadata issues a SQLite SELECT. The exact disk duration varies by machine, but the added critical-path boundaries and one-per-side-chat cardinality are certain.

**Causal diff evidence:** The added await at sideChatContribution.ts:53 calls readSideChatSourceContext for every unseeded side chat. That helper unconditionally awaits tryOpenDatabase, whose implementation performs fileService.stat, and then awaits SessionDatabase.getMetadata, which executes a SQLite SELECT. The same diff also adds AgentService.ts:7824, which awaits persistSideChatSourceContext during creation; this unknown metadata key goes through writeMetadata with Immediate flush before the chat is published.

Opening an Explain or /btw side chat incurs avoidable local-disk/SQLite latency before the first prompt can reach the model; on slow, busy, remote, or cold storage this directly increases time to first response, and retries after a failed first turn pay it again.

**Evidence:** AgentHostChatContributions awaits contributions sequentially, and AgentSideEffects awaits outgoingTurn before marking the provider stage and calling sendMessage. readSideChatSourceContext awaits SessionDataService.tryOpenDatabase; tryOpenDatabase increments the storage stat count and awaits IFileService.stat even when a database can be acquired from the collection, then getMetadata awaits \`SELECT value FROM session\_metadata WHERE key = ?\`. onTurnEnd only sets sideChatSeededMemento after success, so no successful first turn means no suppression.

**Suggested direction:** Keep the context-inheritance choice in live chat state/memento when creating the chat and hydrate it once during restore, using the persisted value only on that restore path. Then onOutgoingTurn can branch on the in-memory value without stat/open/query; fold persistence into the existing chat upsert/normalized metadata write rather than adding a separate immediate legacy write.
