# Performance review: Show Copilot Fusion reasoning in the agent host chat

[PR #346434](https://github.com/microsoft/vscode/pull/346434) at `39ea613d494df1d2852f1e32fa7001960ba6276b`

## Findings (1)

### 1. [low] Avoid serializing full reasoning text for deduplication

**Finding ID:** `PERF-F1E9E41DCAEA`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:10072</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** full-length serialized reasoning strings and retained heap bytes  
**Scaling:** O(total reasoning characters across provisional and committed Fusion messages); unique reasoning keys retain approximately another encoded copy of each reasoning text until turn completion, while committed replays add another O(text length) temporary allocation.  
**Outcome:** increased synchronous publication latency plus CPU/GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, live Fusion assistant messages did not construct or retain any deduplication key from \`reasoningText\`, so this full-payload serialization and turn-long duplicate storage did not occur.  
**Changed behavior:** Each provisional Fusion reasoning message and its committed replay now synchronously JSON-serializes the complete reasoning text to perform deduplication, and each unique serialized copy is retained until the turn is cleared.  
**Confidence:** 0.97 — The changed helper, provisional/committed call paths, and turn cleanup are explicit: both live and committed Fusion messages call the helper, the key includes the complete text, and the Set is cleared only with provisional turn state. Exact model output lengths vary, which affects severity but not the mechanism.

**Causal diff evidence:** Added RIGHT line 10072 constructs \`JSON.stringify(\[e.data.messageId, reasoning\])\` for every Fusion assistant message before the duplicate check; RIGHT line 10076 stores that serialized key in the turn-scoped Set.

On Fusion turns with long chain-of-thought output across several phase model calls, completion of each message performs an extra full-string allocation on the synchronous publication path, delaying reasoning display and adding retained heap/GC pressure for the lifetime of the turn; committed replays repeat the CPU/allocation even when no UI action is emitted.

**Evidence:** \`renderFusionReasoning\` builds the key from the full \`reasoningText\` before \`\_emitAction\`; provisional inline messages call it at 10889 and committed messages reach it through \`renderMessage\`. Tests at 23651-23656 show the same message/reasoning is replayed at commit, so even suppressed copies pay the full serialization cost. The serialized unique keys remain in \`\_shownFusionReasoning\` until \`\_clearProvisionalFusionState\` at 12730.

**Suggested direction:** Deduplicate without encoding the payload, for example use a map keyed by \`messageId\` whose value is the original reasoning string (or a small per-message identity/version if SDK IDs are sufficient), and test emptiness before creating any key. This preserves provisional/commit suppression while avoiding a copied JSON string.
