### 1. cleanup-lifecycle

**Fix location:** `src/vs/workbench/browser/parts/editor/editorActions.ts:2706` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/browser/parts/editor/editorActions.ts:2694`  
**Introducing path:** `src/vs/workbench/browser/parts/editor/editorActions.ts`  
**Introducing commit:** `2e5e0760311327e38b81c66862a19edf54abb450`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.97

**Mechanism:** Each retry of a vetoed detach command created and retained another empty auxiliary window, including its DOM, editor part, title/status bars, scoped services, and listeners, because creation preceded the only canMove check and rejection did not close the window.

**Symptom:** Repeated attempts to detach an editor or group that cannot move accumulate empty auxiliary windows and their renderer resources, increasing retained memory and window-management/rendering overhead.

**Fixed behavior:** Move/Copy Editor and Move/Copy Editor Group now reject known vetoes before opening an auxiliary window, and close a just-created empty window when the authoritative target-group recheck vetoes, bounding auxiliary windows to successful transfers or windows concurrently populated by other work.

**Evidence:** In the base command path, editorActions.ts:2694 awaited createAuxiliaryEditorPart before mergeGroup attempted per-editor canMove checks; a veto therefore left the newly created empty auxiliary editor part alive. The same ordering existed for selected-editor commands. The changed commands now route through transferToNewWindow, whose added preflight calls getVeto(NEW\_WINDOW\_TARGET) before createPart and whose post-creation recheck closes the part while all groups are still empty if the editor changed meanwhile.
