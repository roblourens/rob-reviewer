- Scaling input: Number of configured variable names and injectHosts strings; normal configurations are expected to contain a small credential map.
- Effective concurrency: Single settings UI/configuration validation path; no parallel boundary work.
- Cache behavior: The registered schema and display metadata are static. There is no new runtime cache or negative-cache state.
- Mechanism confidence: High confidence that the schema performs local collection-proportional validation and introduces no expensive boundary.
- Magnitude uncertainty: Very large hand-authored maps would increase schema-validation CPU linearly, but the diff adds only the validation required for the new structured setting and provides no evidence of realistically large cardinality or user-visible latency.
- Expensive boundaries: none found
- Verdict: No reportable regression: local validation and completion metadata are required by the setting and bounded by a realistically small user-authored map.

Host-side handling persists root configuration and notifies configuration consumers; session-specific SDK updates occur only for eligible active sessions.
- Scaling input: Connected Agent Hosts, active Copilot sessions on each host, and credential-map size. The effective host cardinality is one grouped dispatch per connection, not one dispatch per environment variable.
- Effective concurrency: Connection dispatches are iterated synchronously. Eligible sessions react independently, while each session's SDK updates are serialized by \_configSequencer; aggregate concurrency can reach the number of active sessions, as it already does for sandbox changes.
- Cache behavior: The workbench caches the desired sandbox object in \_desired across connections and invalidates it only on relevant setting changes. Each session compares JSON against \_appliedConfig and skips an unchanged SDK update; inactive sessions apply current configuration when activated/resumed.
- Mechanism confidence: High confidence in the grouped per-connection dispatch, queued filesystem persistence, active-session filter, and per-session serialization based on the traced callers.
- Magnitude uncertainty: Users may have multiple remote connections or active sessions, but typical credential maps and simultaneously active sessions are small; no evidence indicates a new large fan-out or high-frequency trigger.

### Scenario 3: Live-edit or reset chat.agent.sandbox.credentials.envVars while Agent Hosts and sessions are running

- Critical path: A configuration event invalidates the cached desired object, computes it once, and pushes changed sandbox state to each connected host. Each receiving host persists root state and active sessions serialize and apply a changed SDK sandbox configuration. Intermediate edits are not explicitly coalesced at the workbench, but configuration events occur on accepted setting updates and per-session work is sequenced.
- Scaling input: Accepted edits times connected hosts and eligible active sessions, with serialization bytes proportional to the complete credential map. Effective cardinality is per host/session, not per variable or host pattern.
- Effective concurrency: Per-host dispatches are immediate; active sessions can update concurrently in aggregate, while each individual session queues updates on its sequencer. Filesystem writes are serialized by \_rootConfigWrite.
- Cache behavior: The desired workbench object is recomputed once per accepted relevant setting event and reused across connections. Deep equality avoids dispatch when host state already matches. Session-level serialized-config comparison suppresses redundant SDK calls; there is no explicit cross-event latest-value coalescing.
- Mechanism confidence: High confidence in the changed event reachability, boundary counts, and sequencing; lower confidence that realistic editing frequency or cardinality would produce measurable degradation.
- Magnitude uncertainty: Rapid auto-saved JSON edits could create multiple accepted updates, but this is an infrequent user configuration workflow, maps are expected to be small, writes are serialized, and no evidence establishes a harmful burst at realistic session counts.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/agentHostSandboxForwarder.ts::\_pushToAllConnections</code>: Send one grouped RootConfigChanged action with the updated environment-variable map; cardinality: One dispatch per connected host whose current sandbox value differs, regardless of the number of map entries.
    - Introduced by diff: true; previous behavior: Changes to this newly exposed setting did not previously trigger forwarding; other sandbox settings already followed this exact grouped path.; critical-path effect: Required for live policy propagation; calls are issued immediately after the accepted configuration update.
  - filesystem at <code>src/vs/platform/agentHost/node/agentConfigurationService.ts::persistRootConfig</code>: Persist the resulting root configuration via temporary-file write and rename; cardinality: One queued atomic persistence operation per accepted host update; repeated accepted edits queue in order.
    - Introduced by diff: false; previous behavior: The persistence boundary existed for every RootConfigChanged action; the new setting can now trigger it when the user changes that setting.; critical-path effect: Not awaited by the workbench dispatch, but consumes host filesystem I/O in the background.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionSandbox.ts::\_updateConfig</code>: Call the Copilot SDK to apply the updated effective sandbox config; cardinality: One call per eligible active session when credentials alter the serialized effective config; no call for inactive sessions or unchanged serialized configs.
    - Introduced by diff: true; previous behavior: This credential setting could not previously alter running sessions, while other sandbox settings already triggered the same update mechanism.; critical-path effect: Required for each running session to begin enforcing the new credential policy; per-session calls are sequenced.
- Verdict: No reportable regression: live propagation is the feature's required behavior, each map is grouped rather than fanned out per entry, unchanged/inactive work is filtered, and realistic update frequency does not establish excessive IPC or I/O.

### Scenario 4: Run the next terminal-sandboxed command after changing the credential setting

- Critical path: Because the credential key was added to the shared sandbox-setting list, TerminalSandboxEngine marks its generated config stale even though that engine does not read credentials.envVars. The next wrapped command regenerates the sandbox JSON config before command execution.
- Scaling input: Credential-setting changes between terminal commands; repeated changes before a command collapse to one rewrite and do not scale with credential-map entries in the terminal engine.
- Effective concurrency: Single engine invalidation and one awaited config regeneration on the next wrapping operation; no per-entry or per-session fan-out.
- Cache behavior: The engine's \_needsForceUpdateConfigFile boolean coalesces all invalidations until the next generated config, then resets.
- Mechanism confidence: High confidence that the unrelated key causes one deferred rewrite; high confidence that repeated edits coalesce to one rewrite before command use.
- Magnitude uncertainty: The exact config-file write duration varies by filesystem, but this is one small deferred local write after an infrequent settings change and is commonly subsumed by command-specific config refreshes.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/sandbox/common/terminalSandboxEngine.ts::wrapCommand/getSandboxConfigPath</code>: Regenerate and write the terminal sandbox configuration file; cardinality: At most one deferred rewrite after one or many credential-setting changes before the next command; the boolean invalidation coalesces repeated changes.
    - Introduced by diff: true; previous behavior: Changing this credential setting did not previously invalidate the terminal sandbox config because the key was absent from SANDBOX\_SETTING\_KEYS.; critical-path effect: The single rewrite is on the next sandboxed command's wrapping critical path.
- Verdict: No finding: although the invalidation is broader than necessary, it creates only one coalesced small local rewrite after an infrequent configuration edit, insufficient for a concrete user-visible performance regression.
