## Findings (1)

### 1. [medium] Release card-backed preparations when configuration is canceled

**Finding ID:** `PERF-351A60544830`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/customizations/copilotCustomizationInstallations.ts:1043</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** parsed MCP package/remote objects and generated command/environment strings retained by pending preparations  
**Scaling:** Retained memory grows with the size of each accepted card-derived choice (the fetch accepts responses up to 5 MiB) multiplied by every preparation abandoned before its runtime-supplied expiry; the preparations map has no count or byte bound.  
**Outcome:** retained memory and subsequent GC pressure in the long-lived Agent Host process  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Pending configured remote preparations retained only the runtime plan's choice/configuration data. Local packages and direct-card remotes needing values were rejected before fetching and retaining card-derived transport objects, so canceling those flows could not accumulate this additional payload.  
**Changed behavior:** The added map entry stores serverPackage/serverRemote plus the separately generated preview, then the whole choices map is placed in this.preparations. The workbench cancellation path throws without applying or notifying the host, so only the externally supplied plan expiry removes it.  
**Confidence:** 0.93 — The retention path, 5 MiB fetch bound, uncapped preparation map, timer-only cleanup, and cancellation path were all traced directly. Actual card sizes and how often users retry before expiry are uncertain, which limits severity rather than mechanism confidence.

**Causal diff evidence:** The added line 1043 changes each retained choice from the previous { choice, configuration } payload to { choice, configuration, serverPackage, serverRemote, preview }, adding card-sized objects/strings to the pending preparation lifecycle.

Opening configuration for a large package/remote card and dismissing the Quick Input leaves its card-derived objects resident; repeated install/cancel attempts can accumulate tens or hundreds of MiB until the plan timers expire, increasing Agent Host memory and GC pauses.

**Evidence:** fetchMcpCardServer accepts and parses up to 5 MiB; requestMcpConfiguration stores the matched card subtree and describeMcpPackage preview at this line, then PendingCustomizationPreparation is inserted into an uncapped DisposableMap. collectConfiguration cancellation exits via CancellationError, and there is no cancellation/release API for the host preparation. Thus each canceled request remains live until planHandleExpiresAt.

**Suggested direction:** Add an explicit release/cancel operation that the workbench invokes whenever prompting or confirmation is dismissed, and enforce a host-side count/byte bound for pending card-backed preparations. If release cannot be wired immediately, retain only a bounded normalized choice payload and cap its expiry independently of the runtime plan.
