**Relevant issue families:** eager-work, repeated-work, synchronous-ui-work, serialization-allocation, boundary-fanout

### Scenario 1: Open an existing multi-chat session with no explicit sessions.showChatTabs setting

- Critical path: Configuration resolution selects Single, then ChatGroupsView restores/creates the grid and ChatGroupView creates one active ChatView. The active transcript load remains on the existing session-opening critical path; the diff adds no awaited work.
- Scaling input: Number of visible chats and persisted split groups. In the common unsplit case, Single assigns only the active chat to the sole group and suppresses tab DOM, while Multiple assigned all visible chats to the tab bar.
- Effective concurrency: Grid/group construction is synchronous and sequential; transcript loading behavior is unchanged and remains owned by the active ChatView.
- Cache behavior: Loaded session/chat models and transcript state are reused as before. Persisted layout lookup has identical cold/warm behavior; changing the default neither adds a cache key nor defeats coalescing.
- Mechanism confidence: High: the constant reaches ChatGroupsView directly, and both branches were traced through group creation, reconciliation, and ChatView creation.
- Magnitude uncertainty: Transcript size and provider latency vary, but the changed literal does not increase view count, transcript loads, or storage calls.
- Expensive boundaries:
  - filesystem at <code>src/vs/sessions/browser/parts/chatGroupsView.ts:\_loadStored/\_readStoredLayouts</code>: Read and JSON-parse the workspace-stored per-session chat-group layouts.; cardinality: One storage read per session view setup; serialized content scales with previously persisted split groups, not with the new default.
    - Introduced by diff: false; previous behavior: Multiple mode used the same storage read and restore path with the same call count.; critical-path effect: Synchronous setup work before the grid can be restored.
  - other expensive boundary at <code>src/vs/sessions/browser/parts/chatGroupView.ts:ChatGroupView.setContext</code>: Create the active chat view and load/render its transcript through the existing ChatView.; cardinality: One active ChatView for the normal single-group session in both modes; additional views only correspond to explicitly restored split groups.
    - Introduced by diff: false; previous behavior: Multiple mode also created one ChatGroupView and one active ChatView; it additionally rendered the tab strip and assigned all visible chats to it.; critical-path effect: The active view must exist before the session transcript is rendered.
- Verdict: No regression. The default Single path creates the same one expensive active chat view and less tab DOM/work for an unsplit session.

### Scenario 2: Switch from one chat to another in the same session under the new Single default

- Critical path: The explicit navigation resolves the session/chat, waits for any existing provider-backed session load, updates the active chat, then reuses the current ChatView via setChat and reloads the selected transcript. This is the same openChat path used before when selecting a tab.
- Scaling input: User chat-navigation frequency and selected transcript size; the total number of hidden chats does not cause transcript loads in Single mode.
- Effective concurrency: Navigation uses existing cancellation so superseded opens do not produce an unbounded concurrent burst; rendering remains one active chat per group.
- Cache behavior: The same chat model/view-state and transcript reuse paths apply in both modes; the default does not change positive, negative, or in-flight cache behavior.
- Mechanism confidence: High: the mode-specific reconciliation changes only group assignment/presentation; navigation and transcript-loading implementations are shared.
- Magnitude uncertainty: Provider and transcript latency vary, but call cardinality and cancellation are unchanged.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/services/sessions/browser/sessionsService.ts:\_openChatSession/\_openChat</code>: Resolve provider-backed session/chat state and wait for the session to load; provider implementations may cross the extension-host or remote boundary.; cardinality: At most one resolution/load sequence per explicit chat navigation, cancellation-coalesced by the existing navigation token.
    - Introduced by diff: false; previous behavior: Selecting a chat tab in Multiple mode invoked the same SessionsService.openChat path.; critical-path effect: The requested chat cannot display until provider-backed state is available.
  - other expensive boundary at <code>src/vs/sessions/contrib/chat/browser/chatView.ts:ChatView.setChat</code>: Clear the previous transcript state and load/render the newly selected chat in the retained widget.; cardinality: One transcript switch per explicit chat navigation; no per-visible-chat fan-out.
    - Introduced by diff: false; previous behavior: Multiple mode reused the same active ChatView and called setChat when switching tabs.; critical-path effect: Required to render the selected chat.
- Verdict: No regression. Switching presentation does not add provider calls or recreate the ChatView.

### Scenario 3: Restore or explicitly open side-by-side chat groups

- Critical path: Persisted groups are deserialized and one ChatGroupView/ChatView is created per restored pane, or a new group is created on an explicit open-to-side action; grid layout then runs for those groups.
- Scaling input: Number of explicitly created or restored split groups, not total chats. Each group owns one expensive chat widget in both modes.
- Effective concurrency: Group creation and grid layout are synchronous/sequential; explicit chat opens use the existing single navigation flow.
- Cache behavior: Persisted layouts are keyed by session ID and reused identically in both modes. The default does not create additional persisted groups automatically.
- Mechanism confidence: High: reconciliation replaces an unpinned peer in place under Single mode; new groups require pinning, restoration, drag/drop, or explicit open-to-side actions.
- Magnitude uncertainty: Users can create varying numbers of panes, but Single mode does not automatically fan chats out into groups.
- Expensive boundaries:
  - filesystem at <code>src/vs/sessions/browser/parts/chatGroupsView.ts:\_persistLayout/\_saveStored</code>: Serialize all split groups and store the workspace layout after topology or active-group changes.; cardinality: One full layout write per existing persistence trigger; payload scales with explicit split-group count.
    - Introduced by diff: false; previous behavior: The same split layout serialization and storage triggers applied under Multiple mode.; critical-path effect: Synchronous persistence occurs after reconciliation/layout actions, as before.
- Verdict: No regression caused by the default change. Any multi-widget cost is tied to explicit/restored split panes and existed before.

### Scenario 4: Open Sessions accessibility help

- Critical path: Accessibility help performs one configuration lookup and appends the mode-specific localized strings; no asynchronous or external work is added.
- Scaling input: Constant work independent of session/chat count.
- Effective concurrency: Synchronous single invocation.
- Cache behavior: Configuration lookup behavior is unchanged; only the fallback enum value differs.
- Mechanism confidence: High: the only runtime consumer in this path branches between predeclared localized text.
- Magnitude uncertainty: None material.
- Expensive boundaries: none found
- Verdict: No performance regression; tests only update the expected fallback wording.

**Summary:** Reviewed all three changed files and traced the changed default through configuration registration, ChatGroupsView reconciliation, ChatGroupView/ChatView lifecycle, session navigation, layout persistence, and accessibility help. The new Single default does not add boundary calls, eager views, repeated transcript work, or concurrency; for the common unsplit case it suppresses tab rendering and assigns only the active chat.
