## Findings

No high-confidence performance findings.

<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** eager-work, boundary-fanout, repeated-work

### Scenario 1: Normal Windows product-test job finalization with no process holding a log file

- Critical path: After tests and result publication, the existing broad process cleanup runs, then the new script synchronously compiles its Restart Manager interop helper, recursively enumerates \`.build/logs\`, and—when files exist—completes one Restart Manager session before the always-on pipeline artifact upload can begin. All added work is on job-finalization's critical path.
- Scaling input: The number F of files recursively present under \`.build/logs\`; the helper materializes F full paths and registers all F in one bulk Restart Manager call. Effective holder cardinality is zero in this scenario.
- Effective concurrency: Fully serialized in one PowerShell task. File enumeration is sequential from the caller's perspective, and all F paths are grouped into one Restart Manager registration rather than F calls. No limiter is needed because there is one session and no per-file concurrency.
- Cache behavior: There is no cross-job cache: this task starts a fresh Windows PowerShell process, so \`Add-Type\` runs once per job. File paths and the negative no-holder result are not cached, but in the no-holder branch they are computed only once. The existing artifact publisher later traverses the directory independently.
- Mechanism confidence: High: the changed YAML unconditionally invokes the script under \`condition: always()\`, and the script's compile, recursive enumeration, and bulk native call are explicit. There is no per-file boundary fan-out.
- Magnitude uncertainty: Repository evidence does not establish typical F or measured \`Add-Type\`/Restart Manager duration. The work runs once at job teardown, is bulked, and does not execute in an interactive or repeated test path.
- Expensive boundaries:
  - other expensive boundary at <code>build/azure-pipelines/win32/stop-log-file-holders.ps1:18</code>: Dynamically compile and load the C\# Restart Manager interop type with \`Add-Type\`.; cardinality: Once per Windows product-test job because the script runs in its own PowerShell task.
    - Introduced by diff: true; previous behavior: The previous cleanup was inline PowerShell and performed no dynamic compilation.; critical-path effect: Must complete before holder detection and therefore before job-finalization artifact publication.
  - filesystem at <code>build/azure-pipelines/win32/stop-log-file-holders.ps1:91</code>: Recursively enumerate every file under \`.build/logs\` and materialize each full path.; cardinality: One directory traversal and F path objects when no holder is found.
    - Introduced by diff: true; previous behavior: The previous cleanup did not traverse the log tree; the later artifact publisher still performed its own unchanged traversal/upload.; critical-path effect: Synchronous prerequisite to the Restart Manager query and subsequent artifact publication.
  - IPC at <code>build/azure-pipelines/win32/stop-log-file-holders.ps1:57-85</code>: Start a Restart Manager session, bulk-register F files, query affected processes, and end the session.; cardinality: One session with one bulk registration and one \`RmGetList\` probe in the no-holder case, independent of F call count.
    - Introduced by diff: true; previous behavior: No Restart Manager boundary existed; cleanup only queried the process list and killed executables rooted under the test directory.; critical-path effect: The native OS query completes synchronously before publication can proceed.
  - network at <code>build/azure-pipelines/win32/product-build-win32-test.yml:47-50</code>: Publish \`.build/logs\` as the pipeline log artifact.; cardinality: One artifact publication per job, with uploaded bytes/files determined by the existing log tree.
    - Introduced by diff: false; previous behavior: The same artifact was always published immediately after the prior cleanup and remaining job steps.; critical-path effect: This unchanged post-job output now starts after the new cleanup script; the diff does not increase upload cardinality or bytes.
- Verdict: No reportable regression. The diff adds bounded, synchronous teardown overhead, but groups all files into one Restart Manager registration and performs only one scan/query on the dominant no-holder path; there is no high-confidence hot-path, fan-out, or unbounded mechanism.

### Scenario 2: Windows product-test job finalization when one or more out-of-tree processes hold log files

- Critical path: The same compile, recursive scan, and Restart Manager query run first. For each of H unique holders, the task synchronously queries WMI metadata/ownership, may force-stop the process, waits up to 10 seconds for that process, then performs one second full log-tree scan and Restart Manager session. Artifact publication waits for all of this.
- Scaling input: F log files and H unique holder PIDs returned after \`Sort-Object -Unique\`; WMI and stop/wait work scales with H, while filesystem/native registration work is exactly two bulk passes when any holder is detected.
- Effective concurrency: Holder processing is deliberately serial. There is no concurrent process-stop burst; each eligible holder is stopped and awaited before the next. Restart Manager still receives files in one bulk call per pass.
- Cache behavior: No positive or negative holder cache is retained. The second enumeration/query intentionally refreshes state after stopping processes. PID deduplication prevents repeated per-holder WMI/stop work when one process holds multiple files.
- Mechanism confidence: High: F- and H-scaling, PID deduplication, serial waits, and the second verification pass are explicit in changed code. The task is directly before post-job artifact publication.
- Magnitude uncertainty: The repository and PR metadata establish rare observed holder incidents and examples with a small number of processes, but do not establish large H, large F, or force-killed processes routinely consuming the full wait timeout. Thus the theoretical O(F + H) teardown delay lacks a realistic high-impact trigger.
- Expensive boundaries:
  - filesystem at <code>build/azure-pipelines/win32/stop-log-file-holders.ps1:91,129</code>: Recursively enumerate all log files before and after holder cleanup.; cardinality: Two traversals, materializing F paths each time, regardless of how many files each holder has open.
    - Introduced by diff: true; previous behavior: The prior cleanup did not inspect log files or re-scan them after process termination.; critical-path effect: Both synchronous traversals precede artifact publication; the second verifies cleanup.
  - IPC at <code>build/azure-pipelines/win32/stop-log-file-holders.ps1:57-85</code>: Run two bulk Restart Manager sessions to discover holders before cleanup and verify remaining holders afterward.; cardinality: Two sessions, each with one bulk F-file registration; holder results are deduplicated before per-process handling.
    - Introduced by diff: true; previous behavior: No file-holder query existed, so out-of-tree holders survived and could cause the later publication to fail.; critical-path effect: Both OS queries block cleanup completion and artifact publication.
  - IPC at <code>build/azure-pipelines/win32/stop-log-file-holders.ps1:108-112</code>: Query \`Win32\_Process\` and invoke \`GetOwner\` for each unique holder through CIM/WMI.; cardinality: Up to two serialized WMI operations per unique holder PID H.
    - Introduced by diff: true; previous behavior: The existing cleanup made one broad \`Win32\_Process\` query and filtered by executable path; it did not perform per-holder lookup/owner calls for out-of-tree processes.; critical-path effect: Ownership and agent-process checks must finish before each stop decision.
  - subprocess at <code>build/azure-pipelines/win32/stop-log-file-holders.ps1:120-121</code>: Force-stop each eligible holder and wait up to 10 seconds for termination.; cardinality: At most one stop and one serialized wait per eligible unique holder; ineligible/current/agent holders are skipped.
    - Introduced by diff: true; previous behavior: Only processes whose executable path was under the test root were stopped, without an explicit wait; out-of-tree holders such as inherited \`git.exe\` processes were not touched.; critical-path effect: Termination and any wait directly delay the artifact upload, but remove the file lock that previously caused publication failure.
  - network at <code>build/azure-pipelines/win32/product-build-win32-test.yml:47-50</code>: Publish \`.build/logs\` as a pipeline artifact after cleanup.; cardinality: One unchanged artifact upload per job.
    - Introduced by diff: false; previous behavior: Publication could begin sooner but fail when an out-of-tree process retained a log handle.; critical-path effect: The upload is delayed by holder cleanup but is expected to succeed after locks are released instead of failing on locked files.
- Verdict: No reportable regression. The extra work is intentional, holder-triggered teardown on the publication critical path; file operations are bulked, holder PIDs are deduplicated, and process handling is serialized. There is insufficient evidence of realistically large H/F or repeated 10-second waits to establish an actionable performance bug.

**Summary:** Reviewed the complete two-file diff and traced normal and holder-present Windows CI teardown paths through dynamic compilation, filesystem traversal, Restart Manager, WMI, process termination, and artifact publication. The PR adds bounded one-time cleanup latency but avoids per-file boundary fan-out and concurrency bursts; no high-confidence performance regression or qualifying regression fix was found.
