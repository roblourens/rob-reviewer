# Performance review: mediaPreview: warn when a media file's audio codec can't be played

[PR #346571](https://github.com/microsoft/vscode/pull/346571) at `02e96e83955d4fbeb18b21d8b3200522b4ccab06`

## Findings (1)

### 1. [medium] Avoid whole-file codec reads on non-range providers

**Finding ID:** `PERF-8DA2571405B0`  
**Location:** <code>src/vs/workbench/contrib/mediaPreview/common/mediaCodecs.ts:100</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** whole-media-file bytes transferred over provider RPC/IPC plus the corresponding in-memory buffers  
**Scaling:** The added cost is O(file size) per render for files up to 64 MiB, and up to 200 MiB on the WebM fallback; repeated file-change renders repeat that transfer because each readMediaInfo call creates a new reader.  
**Outcome:** large duplicate IPC/network transfers, playback startup delay on the WebM fallback, and transient memory/GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Media previews did not read the file through IFileService to discover codecs. In particular, the WebM fallback fetched the media once in the webview and derived its codec type from those same bytes before appending them to MediaSource.  
**Changed behavior:** When a provider lacks FileReadStream/FileOpenReadWriteClose, createReader now calls readFile and buffers the entire media file merely to parse metadata. The normal render allows 64 MiB, while \_postWebmType retries with a 200 MiB allowance and only then lets the webview fetch the same file for MediaSource playback.  
**Confidence:** 0.99 — The capability branch, full-buffer implementation, 64/200 MiB bounds, and sequential WebM call flow are all explicit in repository code. Only prevalence of large media on non-range providers is uncertain, which is reflected in medium severity rather than mechanism confidence.

**Causal diff evidence:** The added line \`content ??= fileService.readFile(resource).then(file =&gt; file.value);\` introduces a whole-file provider read in the codec parser; the same diff wires that parser into every render and into the WebM fallback before the existing webview fetch.

Opening media from providers such as the Agent Host filesystem (which exposes only FileReadWrite and base64-decodes a whole resourceRead result) or ordinary extension filesystems without the proposed chunk API transfers and buffers the entire file. For a 100–200 MiB WebM on a build that needs the existing MSE fallback, this new full-file RPC is sequentially on the playback critical path and is followed by a second full fetch, roughly doubling bytes and delaying playback; even an MP3 under 64 MiB is fully read although this parser cannot identify MP3 files.

**Evidence:** createReader selects this branch specifically when range/stream capabilities are absent, and line 100 invokes fileService.readFile, whose service/provider path materializes the full Uint8Array. AHPFileSystemProvider advertises FileReadWrite but neither range capability and implements readFile by resourceRead(...Base64) followed by decodeBase64. The changed \_postWebmType awaits readMediaInfo(..., 200 MiB) before replying, while the changed webview waits for that reply before readMedia fetches the complete media. The deleted fallback instead called readWebm once and computed getWebmType(bytes) from that same buffer.

**Suggested direction:** Do not use readFile for codec discovery on providers without range support. For the MSE fallback, parse the codecs from the same bytes the webview already fetches (or otherwise share that single read); for normal warnings, skip/strictly cap unsupported whole-file providers and short-circuit formats such as MP3 that the parser cannot inspect.

### Scenario 2: Open media from an Agent Host or extension filesystem without range/stream capabilities

- Critical path: The new parser starts during render in parallel with direct playback, but consumes the same provider/connection resources. Codec warning delivery waits for the full read; provider contention can also delay the media fetch.
- Scaling input: Media file byte size up to the 64 MiB normal-render threshold; unsupported MP3 files are included even though the parser returns no media info.
- Effective concurrency: One whole-file parser read per editor/render runs concurrently with the webview media fetch. Agent Host limits readFile operations globally to 10, so multiple previews or updates queue and contend for that limiter.
- Cache behavior: The entire-file promise is cached only within one ChunkedReader invocation. \_mediaInfo coalesces requests for one render, but there is no cross-render cache or negative cache.
- Mechanism confidence: Very high: capability checks force this branch, readFile materializes the complete file, and Agent Host advertises no range capability.
- Magnitude uncertainty: The prevalence and bandwidth of large files on these providers varies, but the byte count and duplicate boundary are deterministic.
- Expensive boundaries:

- Verdict: Reportable: the diff adds an O(file-size) whole-file transfer/allocation for metadata, including formats it cannot parse.

### Scenario 4: Keep a changing/generated media file open in the preview

- Critical path: File events schedule render after 100 ms. Each render reloads the webview and starts a new codec parse; parsing is not awaited by \_render and older parses are only ignored after completion, not cancelled.
- Scaling input: Number of update windows while the file remains open, multiplied by file size for whole-file providers or by up to 32 chunks for range providers.
- Effective concurrency: Events within a 100 ms window coalesce, but a later window can start another parse while a slow prior parse is still running. There is no shared parse limiter; Agent Host's provider-level limiter bounds only whole-file read execution to 10.
- Cache behavior: Each render replaces \_mediaInfo and creates a fresh ChunkedReader/cache. Identity checks suppress stale posts but do not cancel or share reads.
- Mechanism confidence: High: RunOnceScheduler does not await its runner, \_render does not await readMediaInfo, and no cancellation token is passed.
- Magnitude uncertainty: Update frequency and provider latency depend on the producer; continuously generated media is less common than a single open.
- Expensive boundaries:

    - Introduced by diff: true; previous behavior: Renders already reloaded the media webview, but did not also launch codec parsing.; critical-path effect: Usually background work, but overlaps later renders and can contend with the current media load.
  - filesystem at <code>src/vs/workbench/contrib/mediaPreview/browser/mediaPlayerEditorInput.ts:\_render/\_getHtml</code>: Reload the media resource after each render; cardinality: One existing media reload per scheduled render

- Verdict: This amplifies the submitted whole-file finding through repeated/overlapping reads; it does not require a separate duplicate comment.
