# Performance review: agentHost: reload a loaded session on import when another client ran it

[PR #346076](https://github.com/microsoft/vscode/pull/346076) at `04127e3425af668b8f8fc2657e5c78d92f48e865`

## Findings (1)

### 1. [low] Check session metadata before refreshing detached-shell tasks

**Finding ID:** `PERF-C56C0EEF255C`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5252</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Two SDK task-control IPC calls (\`tasks.refresh\` and \`tasks.list\`) per loaded-chat import  
**Scaling:** The two sequential calls repeat on every re-import of an idle loaded session, including the common no-reload case where VS Code was the last client.  
**Outcome:** Increased latency on the session-link opening critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Importing an already loaded chat did not inspect detached shell tasks, so opening the link did not pay these two task RPC round trips.  
**Changed behavior:** Before reading \`lastClientName\`, the new stale-reload check always awaits \`target.hasRunningDetachedShells()\` for an idle target; that method synchronously performs \`rpc.tasks.refresh()\` followed by \`rpc.tasks.list()\`. Even when metadata then proves \`lastClientName === vscode-agent-host\` and no reload is possible, both calls have already completed.  
**Confidence:** 0.97 — The changed critical path and the two sequential IPC operations are directly traced in repository code, and the PR test establishes the realistic no-reload case. Only the exact duration of the local SDK RPCs is uncertain, which is reflected in low severity.

**Causal diff evidence:** The added condition at line 5252 introduces \`await target.hasRunningDetachedShells()\` into every idle loaded-session import before the newly added metadata guard; no detached-task query existed on the import path before this diff.

Reopening a loaded Copilot CLI session link while VS Code was the last client now waits for two unnecessary sequential SDK IPC operations before the chat can open. The cost recurs for each explicit re-import and is visible under the window-level “Opening Copilot CLI session” progress UI.

**Evidence:** \`importSession\` marks every already-loaded session with \`reloadIfStale\`; \`importChat\` awaits \`\_releaseChatRunElsewhere\` on its critical path. At the changed line, the helper calls \`hasRunningDetachedShells()\` before \`client.getSessionMetadata()\`. \`CopilotAgentSession.hasRunningDetachedShells\` performs \`session.rpc.tasks.refresh()\` and then \`session.rpc.tasks.list()\`, while line 5266 returns without reloading when metadata says the agent host ran the session last. The added test includes exactly this \`lastClientName: 'vscode-agent-host'\` no-reload scenario.

**Suggested direction:** Keep the in-memory active-turn/subagent checks first, then read \`lastClientName\` and return immediately when it is the agent host; query detached-shell state only when metadata indicates the session would otherwise be reloaded.

### Scenario 3: Import while a turn, subagent, or detached shell is running, including a turn starting during history replacement

- Critical path: An already active turn or subagent suppresses reload immediately. Detached-shell detection awaits task refresh/list. If a turn races with replacement after the provider reload, replacement is deferred until the turn ends, then the provider history is read again and applied.
- Scaling input: One pending entry per affected imported chat; post-turn scanning scales with the number of pending reloaded chats, while the eventual read scales with that chat's full event history.
- Effective concurrency: The provider import is serialized per chat. \`\_pendingChatReloads\` keeps one latest provider per chat, and \`\_chatHistoryRefreshes\` coalesces same-chat queued work; different chats remain independent.
- Cache behavior: When active/background work is detected before release, the warm live copy remains and no history cache is invalidated. In the race case, the provider has already reloaded, so the eventual replacement reads from the fresh session's memoized event reconstruction; session removal clears pending reload entries.
- Mechanism confidence: High for ordering, map ownership, and coalescing; lower prevalence does not alter the mechanism.
- Magnitude uncertainty: Races between import and turn start should be uncommon; histories and concurrent pending chats vary. Coalescing and cleanup bound normal behavior.
