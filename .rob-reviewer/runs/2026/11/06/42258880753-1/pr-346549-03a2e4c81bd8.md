## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:739` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:749`  
**Introducing path:** `src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts`  
**Introducing commit:** `e790751bf2feb3d854ff7b7a4ca6cc8b7755f8f1`  
**Mechanism family:** `repeated-work`  
**Performance category:** `io`  
**Confidence:** 0.93

**Mechanism:** Each customization discovery refresh repeated filesystem manifest probes for every native plugin contribution and then rescanned all five component classes for each deduplicated plugin root, even though the SDK had already enumerated the effective contributions.

**Symptom:** Customization publication and refresh latency, plus filesystem I/O, scaled with both the number/depth of plugin contribution paths and the number and size of installed plugin trees.

**Fixed behavior:** The changed toPluginCustomizations implementation resolves roots from one SDK plugin inventory and projects only SDK-enumerated children, eliminating per-contribution ancestor manifest searches and per-plugin full directory parsing from each discovery refresh.

**Evidence:** In the base revision, every settled SessionCustomizationDiscovery refresh collected each SDK-reported plugin contribution in pluginFiles, then line 749 called findPluginRoot for every distinct contribution URI. findPluginRoot walked parent directories and hasPluginManifest probed up to five manifest locations at each level. After roots were deduplicated, the same refresh called parsePlugin for every root; parsePlugin reads the manifest and scans hooks, MCP, skills, agents, and instructions. SessionDiscoveredEntry runs this discovery on the session-creation getCustomizationsSettled critical path and on debounced watcher/plugin refreshes. The changed implementation instead gathers opaque plugin IDs, makes one conditional SDK plugins.list inventory request, and joins the already-discovered children in memory without ancestor probes or component-directory rescans.

### Scenario 2: Customization refresh after watched file changes or plugin install/enable/disable/uninstall

- Scaling input: Active client count, distinct active anchor sets, watched change frequency after debouncing, installed plugin count, and discovered contribution count.

- Mechanism confidence: High for refresh coalescing, fan-out, and boundary counts based on SessionDiscoveredEntry and PluginController call flow.
