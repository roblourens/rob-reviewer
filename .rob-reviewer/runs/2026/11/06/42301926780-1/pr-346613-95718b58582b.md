# Performance review: chore: use Node.js 24 in Copilot and sanity CI pipelines

[PR #346613](https://github.com/microsoft/vscode/pull/346613) at `95718b58582b40cca8a25134ee2b31aca46fe97d`

## Findings (1)

### 1. [medium] Resolve the Node release once per sanity pipeline

**Finding ID:** `PERF-4D2413BB8044`  
**Location:** <code>build/azure-pipelines/common/sanity-tests.yml:182</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** HTTPS requests to nodejs.org and blocked CI agents  
**Scaling:** The unconditional lookup runs once for every sanity job; the standalone and release sanity stages expand the template to as many as 28 parallel OS/architecture jobs, so one pipeline produces up to 28 concurrent version-resolution requests even with fully warm Node and node\_modules caches.  
**Outcome:** Increased sanity-pipeline latency and an avoidable burst of outbound network I/O; any slow lookup blocks that job before cache restoration and can delay stage completion by the configured request timeout.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** SANITY\_NODE\_VERSION was pinned to 22.22.0, so a warm job proceeded directly to the Azure pipeline caches and install-node exited from the restored Node cache without contacting nodejs.org.  
**Changed behavior:** Each non-Windows job now unconditionally downloads latest-v24.x/SHASUMS256.txt before restoring either cache; the analogous added PowerShell branch does the same for Windows. This happens independently in every expanded job.  
**Confidence:** 0.99 — The added boundary call, its placement before cache restoration, and the 28-job template fan-out are explicit in repository YAML. Exact nodejs.org latency and stall prevalence are uncertain, which limits severity, but the mechanism and critical-path regression are direct.

**Causal diff evidence:** Added RIGHT line 182 executes curl against nodejs.org unconditionally in the per-job sanity template, before the Node cache at line 192; the diff replaced the prior fixed SANITY\_NODE\_VERSION with a version spec that requires this lookup.

Every sanity run adds up to 28 concurrent nodejs.org calls. Under the already-documented endpoint stalls, an otherwise warm job can spend up to the bounded lookup time doing no useful work, and the slowest affected job extends the sanity stage.

**Evidence:** product-sanity-tests.yml instantiates this template 28 times in one stage, and product-build-template.yml instantiates the same platform matrix for published builds. The lookup is on each job's critical path before Cache&#64;2. The existing comment immediately below notes that nodejs.org sometimes stalls from the shared agent pools, while this request permits up to 60 seconds and retries. Cache hits cannot eliminate the new request.

**Suggested direction:** Resolve the exact 24.x version once in a small preparation job and pass it as an output to all sanity jobs, or pin the exact version centrally and update it deliberately; retain the resolved version in both cache keys so new releases still receive fresh caches.

- Effective concurrency: The jobs are independent members of one stage and may execute concurrently subject to agent-pool capacity. Consequently the changed lookup can burst to 28 concurrent nodejs.org requests; there is no shared limiter or preparation job.
- Cache behavior: Warm Node and node\_modules caches avoid archive download and pnpm install, but cannot avoid the newly unconditional release lookup because it precedes Cache&#64;2. On a new Node patch, the versioned Node and node\_modules keys intentionally make all platform caches cold; failed release lookups are not negatively cached or coalesced.

- Magnitude uncertainty: Normal response time for the small checksum file and frequency of endpoint stalls are not measured.
