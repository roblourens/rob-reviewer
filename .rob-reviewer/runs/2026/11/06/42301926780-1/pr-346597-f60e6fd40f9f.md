## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:223` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:218`  
**Introducing path:** `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts`  
**Introducing commit:** `70f5e0883a3e5d445006faba45115b9c70bd8753`  
**Mechanism family:** `eager-work`  
**Performance category:** `latency`  
**Confidence:** 0.99

**Mechanism:** Opening a multi-diff with N files eagerly acquired up to 2N text-model references and started N diff computations before the model could be published, placing filesystem/content-provider/Git reads and diff CPU for the entire change set on the editor-open critical path.

**Symptom:** Large SCM/history change sets could leave the multi-diff editor loading while all file contents were resolved and all diffs were started; the cost and external reads scaled linearly with total files rather than the visible initial batch.

**Fixed behavior:** The editor now publishes all lightweight file entries immediately, resolves text models only through each entry's on-demand resolve callback, and starts only the first five diffs initially; visible/navigation-targeted items reuse a per-item ObservableLazyPromise, so each requested file resolves once.

**Evidence:** In the base revision, line 218 constructs an async mapped entry for every resource; that mapper calls createModelReference for both sides, and \_createModel awaits Promise.all of the entire mapped collection before publishing documents. MultiDiffEditorViewModel then creates a DiffEditorViewModel and waits for each item's initial diff. The changed code instead publishes URI-only entries whose added resolve callback is invoked lazily, while MultiDiffEditorViewModel limits startup loading to items.slice(0, 5). The added 1,000-entry test asserts exactly 10 model-reference requests and 5 diff computations at initial open, directly establishing the reduced cardinality.

### Scenario 2: Scroll through, expand, reveal, restore, focus, or navigate to an initially unloaded file

- Critical path: A rendered expanded item or explicit navigation calls the item's coalesced load, resolves its text models, starts one diff, and navigation waits for that diff before positioning/focusing. Unrelated offscreen or collapsed items remain off the critical path.
- Scaling input: Unique files actually visited or expanded V, after virtualization and per-item coalescing; cost grows with V rather than total files N. Slowly traversing every file makes V=N.
- Effective concurrency: Visibility-triggered work is bounded by the simultaneously rendered expanded viewport items, plus any explicit navigation target and the initial five. Each item's two sides are parallel; there is no shared global limiter, but this is materially smaller than the prior N-file startup burst.
- Cache behavior: Cold first access performs resolution and diffing. Warm repeat access uses the cached ObservableLazyPromise result. Failures are cached as loadError and are not retried per render. Loaded models intentionally remain until editor disposal; removed/in-flight items release resolved references after completion.
- Mechanism confidence: High: template binding loads only uncollapsed rendered items, navigation calls the same lazy promise, and tests cover duplicate calls, collapsed files, slow targets, and superseded navigation.
- Magnitude uncertainty: Viewport size, file-provider latency, and how quickly users traverse the list vary. The load cardinality and coalescing are explicit.

- Mechanism confidence: High: the added test confirms a dirty unloaded resource is saved without additional model-reference requests, while loaded modified resources preserve prior behavior.

### Scenario 4: Live change-set updates, item removal during loading, and editor disposal

- Critical path: Resource metadata updates rebuild/reorder lightweight entries and may load newly visible or newly entering initial-five items. Removal/disposal does not wait for outstanding resolution, but completed references are released before they can create a diff model.
