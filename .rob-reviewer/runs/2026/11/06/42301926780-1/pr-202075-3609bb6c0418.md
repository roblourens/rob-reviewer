### Scenario 1: Open a multi-diff editor backed by an explicit static resource list

- Critical path: Editor resolution constructs the input, getViewModel creates the model, and model creation waits for all text-model references before constructing per-document DiffEditorViewModels. waitForDiffs is then on the open path but bounded by the existing one-second race timeout.
- Scaling input: N resource pairs; up to 2N model-reference requests, reduced for created/deleted files that use an in-memory empty model.
- Effective concurrency: The outer mapping starts one async mapper per resource, so up to N original references are in flight; each modified reference starts after its corresponding original resolves. There is no shared limiter, matching the prior static-list implementation.
- Cache behavior: The new local array map keys entries by the original/modified URI pair and retains successful or failed promises while the entry remains. For a static list it computes once. The underlying text-model service may reuse warm models. Failed entries are negatively cached until removal.
- Mechanism confidence: High: the complete before/after model-creation code shows equivalent model-reference fan-out, and the added observable mapping only wraps the same static work.
- Magnitude uncertainty: Exact file-provider latency and text-model cache hit rate vary, but the diff does not increase boundary cardinality or concurrency for this existing scenario.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:164-169</code>: Resolve original and modified URIs into text models through ITextModelService.createModelReference.; cardinality: Up to 2N calls for N resource pairs. Different items start concurrently; within each pair, the original await precedes starting the modified reference. Existing text-model-service reuse may make warm references cheaper.
    - Introduced by diff: false; previous behavior: The previous implementation also eagerly issued up to 2N createModelReference calls through Promise.all, with the same per-pair sequential awaits and collection-wide wait.; critical-path effect: All references must resolve before \_createModel returns and the editor view model can be created.
- Verdict: No reportable regression. Initial opening retains the prior eager 2N boundary pattern; added URI-key caching and view-model caching do not add repeated model loads for the static case.

### Scenario 2: Open and refresh a multi-diff editor backed by a dynamic multiDiffSource

- Critical path: Opening first awaits one resolver service call, then follows the same text-model-reference and diff-model path. A source onDidChange event synchronously recomputes the keyed promise list; newly added entries begin model resolution, and publication waits for all promises in that generation.
- Scaling input: N current resource pairs, K URI pairs newly added since the previous event, and U source events that overlap before model resolution finishes. Key caching reduces model-reference creation to up to 2K per update rather than 2N.
- Effective concurrency: All newly added resource mappers can run concurrently, with original then modified serialized inside each pair. Async autorun generations are not coalesced, so overlapping source events can all complete and publish; however, no IMultiDiffSourceResolver is registered anywhere in the current repository, so this path is not presently product-reachable.
- Cache behavior: The map cache uses serialized original/modified URIs, reuses unchanged entries, retains failed promises as negative results, disposes removed entry stores after a published generation, and is torn down with its final observer. One reset path omits the key selector, but both current call sites remain observed until terminal disposal, so it does not cause repeated work in a reachable lifecycle.
- Mechanism confidence: High for the traced caching, concurrency, and uncoalesced-generation behavior; high that repository-wide search finds no resolver registration, so a present user-visible regression cannot be established.
- Magnitude uncertainty: A future resolver's event frequency, resource cardinality, and boundary choice are unknown. The uncoalesced async publication could be costly under rapid events, but no current resolver provides a realistic trigger in this PR.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:133-137 and src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffSourceResolverService.ts:68-71</code>: Resolve the multiDiffSource through the first registered source resolver.; cardinality: One resolver call per input initialization; the resolver implementation could internally use filesystem, IPC, or network, but no resolver registration or implementation exists in the repository diff/tree.
    - Introduced by diff: true; previous behavior: Source-backed inputs did not exist; explicit lists proceeded directly to model-reference creation.; critical-path effect: The call blocks model creation and editor opening for source-backed inputs.
  - filesystem at <code>src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:164-169</code>: Resolve text models for resource pairs newly introduced by a source event.; cardinality: Up to 2K calls per refresh after URI-pair deduplication by the local cache; unchanged URI pairs reuse their existing promise and references.
    - Introduced by diff: true; previous behavior: The old static model had no refresh path; its initial open still made the equivalent up-to-2N calls.; critical-path effect: Each refresh publication waits for all current promises; editor opening waits for the initial publication.
- Verdict: No finding. The diff introduces a potentially overlapping refresh design, but without any registered resolver it is latent rather than a concrete current regression; reporting it would require speculating about a future consumer.

### Scenario 3: Render, scroll, collapse, expand, and dispose a populated multi-diff editor

- Critical path: Per-document diff view models are created when the document list is published. Scrolling uses virtualized templates and DOM/style updates on the UI path; collapse/expand synchronously iterates N items. Disposal clears any live template before releasing the view item.
- Scaling input: N documents overall and V currently materialized virtualized templates; collapse/expand scale with N, while scroll rendering scales primarily with visible/near-visible items.
- Effective concurrency: Rendering and collapse state changes are synchronous on the UI thread. Diff computations are owned by each DiffEditorViewModel; unchanged document promises now retain their existing view models across list updates rather than recreating them.
- Cache behavior: mapObservableArrayCached preserves DocumentDiffItemViewModel instances by promise identity while observed. The widget's object pool continues to reuse templates, and the changed disposal path clears a template directly rather than relying on a hidden-state autorun.
- Mechanism confidence: High: widget observers, virtualized item lifecycle, and DiffEditorViewModel construction were traced directly.
- Magnitude uncertainty: Actual diff CPU depends on file size and algorithms, but the changed caching reduces reconstruction for unchanged entries and no new per-scroll boundary or layout read/write loop was added.
- Expensive boundaries: none found
- Verdict: No reportable regression. Action bodies are moved unchanged, view-model caching avoids repeated diff-model construction on list updates, and direct template clearing improves cleanup behavior.

### Scenario 4: Serialize and restore multi-diff editor inputs

- Critical path: Serialization maps an explicit initial list to URI strings and JSON-encodes it. Restoration parses that JSON, rebuilds URI objects, and later follows either static model creation or one dynamic resolver call when the serialized input has no explicit list.
- Scaling input: N explicit resource pairs for static inputs; source-backed inputs serialize only the source URI and label.
- Effective concurrency: Serialization and parsing are synchronous; subsequent restoration uses the same model-loading concurrency described in the open scenarios.
- Cache behavior: No serialization cache is added. Explicit resources remain retained by the input as before; source-backed inputs avoid embedding a dynamically derived resource list.
- Mechanism confidence: High from direct comparison of the old and new serializer hunks.
- Magnitude uncertainty: Workspace/editor persistence frequency and list sizes vary, but the payload growth remains linear and is not increased versus the prior explicit-list format.
- Expensive boundaries:
  - serialization at <code>src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:108-117 and 306-317</code>: Map URI pairs to strings and JSON serialize/parse the editor input.; cardinality: One linear pass over N explicit resource pairs during serialization and deserialization; constant-size payload for source-backed inputs.
    - Introduced by diff: false; previous behavior: The prior serializer also JSON-serialized the full explicit resources array and parsed it on restore; the new source-backed representation can be smaller.; critical-path effect: Runs on editor persistence/restore paths before the restored input can be reconstructed.
- Verdict: No reportable regression. Static serialization remains O(N), while dynamic-source serialization reduces retained/encoded list data.
