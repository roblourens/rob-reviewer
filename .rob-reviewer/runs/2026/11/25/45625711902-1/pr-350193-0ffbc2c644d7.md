## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `.vscode/settings.json:18` (`LEFT`)  
**Blamed base line:** `.vscode/settings.json:18`  
**Introducing path:** `.vscode/settings.json`  
**Introducing commit:** `ee88620afc77cd8f92a98a95574a88cd74b4b9c7`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.97

**Mechanism:** The workspace enabled debug verification for ordinary contributor editing. Every attached, eligible TextMate model was background-tokenized both by the shared worker and by a legacy tokenizer in main-thread idle slices, with separate debug token/state stores and per-line equality checks. CPU work scales with file contents and subsequent invalidation, even after grammars and the worker are warm.

**Symptom:** Strong static evidence of avoidable main-thread regex tokenization and duplicate token/state retention when opening large repository files or editing text that invalidates many following lines, competing with UI responsiveness. No independent timing measurements were performed.

**Fixed behavior:** Remove the repository's verification=true override, allowing the default false (unless explicitly enabled in user settings). With async tokenization still enabled, worker-capable attached models use the existing shared worker as their background tokenizer rather than performing an additional full-file legacy background pass on the UI thread and retaining verification stores.

**Evidence:** The deleted workspace setting forces verification true; editorConfigurationSchema.ts:111-115 defaults it to false. TextMateTokenizationFeature.\_createTokenizationSupport (textMateTokenizationFeatureImpl.ts:312-317) supplies that configuration through TextMateTokenizationSupport.backgroundTokenizerShouldOnlyVerifyTokens. TokenizerSyntaxTokenBackend.todo\_resetTokenization:148-176 then skips the authoritative worker path, starts DefaultBackgroundTokenizer, and separately starts the worker for verification. DefaultBackgroundTokenizer (textModelTokens.ts:463-552) repeatedly tokenizes invalid lines on the window thread until all states are valid; content changes restart this work. Disabling verification instead uses the existing worker as the authoritative tokenizer and does not instantiate the default background tokenizer when worker tokenization is supported. getLineTokens:286-296 also stops maintaining/comparing the duplicate verification token store. Blame identifies the introducing commit for the removed base line.

### Scenario 2: Scroll, type, or make edits that invalidate many following lines in an already attached repository file.

- Critical path: Input and visible-range tokenization remain synchronous on the window thread. Content changes are sent to the existing worker without awaiting completion; worker updates eventually replace background tokens. Edits formerly also restarted the legacy idle tokenizer, and token reads compared authoritative and debug stores. Those duplicate activities disappear by default.
- Scaling input: Content-change event count, payload bytes, invalidated lines until tokenizer state converges, visible ranges and outstanding edits. A small edit need not retokenize the whole file; state-changing edits can invalidate a long suffix.
- Effective concurrency: One worker executes model jobs; tokenization yields after approximately 20 ms and sends bounded line chunks. Model change notifications remain asynchronous. The removed main-thread idle loop was separate duplicate execution, not a concurrency limit on the worker.
- Cache behavior: The shared worker, language grammar and valid line states remain warm. Incremental state invalidation is preserved. The worker's per-model RunOnceScheduler coalesces tokenization after changes with a 10 ms delay; content-change messages themselves remain uncoalesced as before. No new cache or key retention is introduced.
- Mechanism confidence: High: content listeners, idle-tokenizer restart, visible-range tokenization, debouncer, result batching and verification comparisons were inspected.
- Magnitude uncertainty: Actual savings and any cold/lagging-worker visible-token fallback cost depend on grammar, edit locality and scrolling rate; source establishes removed duplicate work without asserting measured latency gains.

- Effective concurrency: Fallback uses coalesced main-thread idle callbacks; explicit verification runs that idle tokenizer alongside the same shared worker. These are unchanged configurations after resolving settings.
- Cache behavior: Existing grammar/module caches are unchanged. Explicit user opt-in preserves duplicate verification stores; unsupported worker models retain existing fallback behavior. Detachment still disposes controllers and removes worker models.
