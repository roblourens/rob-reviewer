- Effective concurrency: The service pump is serial, duplicate scenario IDs join the existing run, and the shared presentation queue serializes per window. Modal waiting is observable/event driven, not polling.
- Cache behavior: Modal event observables cache booleans while observed and detach/reset when unobserved. Quick Input controller initialization is cached for service lifetime. Eligibility/seen-state deduplication remains unchanged.
- Mechanism confidence: High: traced contribution construction, eligibility evaluation, queue acquisition, waitForState disposal, and the lazy Quick Input implementation.
- Magnitude uncertainty: No timings were measured; first-use service initialization depends on whether other workbench features already used Quick Input.

### Scenario 2: Starting or advancing spotlight tours and sequence steps while dialogs or Quick Input are open

- Critical path: A visual step waits for modal closure, then a 200 ms settle interval if it actually waited, before preparation, target resolution, and rendering. With no modal UI it proceeds without the timer. Existing target-resolution polling and finite-animation settling remain bounded.
- Scaling input: Sequential visual steps, modal handovers, and the target's ancestor chain; no work per session/history row is added.
- Effective concurrency: Steps execute sequentially within the per-window presentation slot. A suspended flag permits one restoration task per live shown step; waits are cancellation-aware and do not spin.
- Cache behavior: Modal boolean observations are shared within the presentation and equality-filter unchanged values. Target resolution intentionally revalidates visibility rather than retaining stale geometry.
- Mechanism confidence: High: traced runStep, \_runPayload, \_showStep, the modal helper, target lookup, and animation waits.
- Magnitude uncertainty: The settle delay is explicit; actual modal handover and target animation duration vary. No timing measurements were made.
- Expensive boundaries:
  - other at <code>src/vs/workbench/contrib/onboarding/browser/spotlight/spotlightPresentation.ts: \_resolveTarget/\_waitForTargetReady; browser/spotlight/onboardingTarget.ts: isVisibleOnboardingTarget</code>: Query the target DOM, inspect computed style/geometry and ancestor animations, and wait for an animation frame.; cardinality: Existing target resolution per step; restoration adds one readiness/visibility pass after the relevant modal interaction settles. - Verdict: No reportable regression. The added delay is the deliberate modal-handover behavior; there is no evidence of an unintended scaling critical path.

### Scenario 3: Suspending and restoring a visible spotlight, including workspace-picker and model-picker steps

- Critical path: Suspension removes frame/layout/key listeners immediately. Restoration awaits modal closure and any pending selection, checks current context/target visibility, then reconstructs the callout and optionally reopens its target. Accepted selections advance instead. Non-modal spotlights do not reopen the target when focus is elsewhere.
- Scaling input: User-driven completed modal interactions during one active step; workspace validation scales with the recent-workspace catalog after existing URI deduplication, and model rendering scales with available models.
- Effective concurrency: One restore task per suspended step; ordinary presentations serialize per window. Workspace stats share a four-slot limiter across reopens. Host discovery is grouped and skipped while already discovering; handler concurrency is not multiplied by workspace count.
- Cache behavior: Overlay DOM shell and model-picker instance are reused; content resources are cleared on reconstruction. Workspace existence checks intentionally remain uncached as on ordinary opens. Remote results/credentials retain existing policies; cloud automatic discovery uses its stale-refresh policy.
- Mechanism confidence: High for restored rendering and transitive boundary counts: traced target.open to workspace/model implementations, filesystem provider.stat, native-host IPC, and grouped discovery handlers.
- Magnitude uncertainty: Catalog size, remote-host enablement, configured tunnel names, modal frequency, and filesystem/network duration are unknown. All identified extra catalog/discovery work is off the restoration critical path.

### Scenario 4: Ending, cancelling, or replacing a step while modal UI or a target selection is pending

- Critical path: Step completion disposes its observable reaction and listeners, cancels modal waits/action tokens, and resolves the presentation. Overlay teardown removes DOM and clears pending activation/layout handles. A pending selection may resolve later, but ended guards prevent rendering.
- Scaling input: One live step and at most one queued target activation/restoration task; repeated modal transitions do not accumulate active step subscriptions.
- Effective concurrency: MutableDisposable bounds queued target activation to one timer. DisposableStore owns each step's reactions/listeners, and waitForState removes its subscriptions on resolution or cancellation.
- Cache behavior: FromEventObservable drops cached state and subscriptions after its last observer. Description rendering disposables are cleared on reuse and disposed with the overlay; target registrations use existing WeakMap/provider ownership.
- Mechanism confidence: High: traced done(), cancellation ownership, waitForState cleanup, suspend/hide, activation disposal, and overlay disposal.
- Magnitude uncertainty: Unresolved owner selection promises can outlive a step, but the prior selection callback already awaited those promises; no independently unbounded retention introduced by the diff was established.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/onboarding/browser/spotlight/spotlightPresentation.ts: \_createOverlay cleanup</code>: Clear native window dimming on overlay disposal.; cardinality: One cleanup request per created backdrop overlay.
    - Introduced by diff: false; previous behavior: The same cleanup request was registered for backdrop overlays.; critical-path effect: Fire-and-forget during teardown, as before.
- Verdict: No reportable cleanup or retention regression. The new persistent activation handle is bounded and owned; suspension also stops the existing per-frame target tracking while modal UI is open.
