**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.98

**Mechanism:** Disposing N distinct universal watch requests called arrays.remove N times over a shrinking array. indexOf and splice perform collection-sized search and/or shifts even though refresh work is coalesced, yielding O(N^2) synchronous CPU during large project watcher churn.

**Symptom:** Strong static evidence of synchronous quadratic CPU work on desktop window watcher disposal for large TypeScript projects; it competes with the window event loop. No benchmark was independently executed.

**Fixed behavior:** Identity-based Set.add/delete makes collection maintenance expected constant time per request, avoiding quadratic synchronous disposal work. Array.from is performed only at the existing debounced/throttled refresh, whose 0/500 ms delays and one-active-plus-coalesced-pending execution remain unchanged.

**Evidence:** The deleted base line 88 used insert(this.universalWatchRequests, request); its returned remover was called synchronously on disposal at base line 97. arrays.ts:488-505 implements this as push followed by indexOf and splice. typescriptServiceClient.ts:1057-1089 creates/closes watchers from TypeScript server events; mainThreadFileSystemEventService.ts:258-268 forwards watch/unwatch to FileService. FileService.doWatch:1295-1325 reference-counts identical URI/options but retains distinct requests, so thousands of distinct files can still reach this collection. The desktop provider forces all requests through the universal collection (electron-browser/diskFileSystemProvider.ts:43). Each removal scans and/or shifts the remaining collection, producing quadratic aggregate CPU for disposing a large batch. The changed RIGHT line 96 uses Set.delete instead. blame\_base\_line(88) identifies commit 7dd4d72fcb35508f9ec1b8575c240513856bb972.

- Effective concurrency: Error restart replay exists outside the provider delayer both before and after the change. - Magnitude uncertainty: Unexpected process failures overlapping request churn are uncommon and their exact frequency is unknown.
