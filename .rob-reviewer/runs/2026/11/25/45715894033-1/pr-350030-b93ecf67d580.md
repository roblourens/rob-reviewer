### Scenario 1: Minimal GitHub account authorizes Agent Host access from local/remote chat, the additional-permissions notification, or a protected pull-request artifact.

- Critical path: After the user chooses a provider, ChatSetupRunner -&gt; ChatSetupController -&gt; ChatEntitlementRequests -&gt; DefaultAccountProvider.signIn now awaits scope discovery, then the existing session creation and default-account update. Interactive chat then resolves and forwards the credential before proceeding. Notification construction itself only creates options and starts no authentication work.
- Scaling input: One selected provider and one sign-in per setup run; usually a small number of account sessions and three configured accepted scope sets. resolveAuthenticationInteractively returns after handling the first protected resource, rather than prompting once for every resource or scope.
- Effective concurrency: ChatSetupRunner.pendingRun joins overlapping setup requests. Extension-host authentication operations are sequenced by provider. The new getAccounts and getSessions calls are sequential. Account updates retain their existing throttler; token-entitlement and managed-settings requests may run in parallel after entitlement resolution.
- Cache behavior: The added lookup has no separate result cache. Provider sessions are held in persisted-session promises and transient-session maps; ordinary warm OAuth reads do not perform network validation. Microsoft-backed restore attempts are negatively cached by account/scopes and coalesced in flight; renewals are coalesced by session. Existing Agent Host token/rejection caches still govern forwarding. Resource resolution normally reads existing sessions before prompting, warming this state.
- Mechanism confidence: High confidence in the bounded two-read addition, option propagation, provider sequencing, existing cache behavior and unchanged downstream work, based on the implementations and callers. No independent high-confidence harmful scaling mechanism was established.
- Magnitude uncertainty: Live provider/network durations and the frequency of cold Microsoft-backed or multi-enterprise-host accounts are unknown; this was a static review.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/accounts/browser/defaultAccount.ts:getMinimalSignInScopes -&gt; findMatchingProviderSession -&gt; getSessions; src/vs/workbench/services/authentication/browser/authenticationService.ts:getAccounts</code>: Read all provider sessions to enumerate accounts, then read sessions for the preferred account.; cardinality: Normally two additional extension-host getSessions round trips per qualifying sign-in, not per resource, account, or scope. The helper retries at most three attempts on exceptions with two 500 ms waits; each attempt reaches one or two reads.

### Scenario 2: Agent Host sign-in while signed out, renewing a full-scope account after a challenge, or switching to an enterprise provider without an existing session.

- Critical path: The same shared setup run performs the new conditional lookup when additionalScopes is nonempty, then falls back to the original default-scope union and existing session creation/update. Empty additionalScopes skips the lookup entirely.
- Scaling input: One selected provider per coalesced setup run, its existing sessions, and any configured enterprise hosts; not workspace files or chat history.
- Effective concurrency: One joined setup run, sequential provider reads and per-provider extension-host queueing. Enterprise host enumeration can use the existing Promise.all across configured hosts; no new provider-wide concurrency loop is added.
- Cache behavior: No matching session and lookup exceptions fall back without adding cached state. Provider registration/activation, persisted sessions, Microsoft restoration negative caches, and post-sign-in account metadata caches are unchanged. The existing session helper allows three exception attempts rather than an unbounded retry.
- Mechanism confidence: High confidence that the additional discovery is bounded and downstream scheduling is preserved. No evidence that this diff creates a realistic unbounded burst or repeated automatic sign-in loop.
- Magnitude uncertainty: Provider activation, exceptional lookup retries and enterprise-host prevalence are unmeasured.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/accounts/browser/defaultAccount.ts:signIn, getMinimalSignInScopes, getSessions</code>: Discover whether the selected provider already has an accepted session without default scopes.; cardinality: Normally two additional session reads, including empty successful reads; at most three helper attempts on exceptions. Not one call per configured accepted scope set.
    - Introduced by diff: true; previous behavior: No pre-createSession discovery inside signIn; default scopes were chosen directly.; critical-path effect: New pre-sign-in prerequisite even when discovery ultimately preserves default scopes.
  - network at <code>extensions/github-authentication/src/githubEnterprise.ts:getSessions; extensions/github-authentication/src/github.ts:getSessions, createSession</code>: Read host session engines and conditionally restore/renew credentials, then perform the existing selected-provider login.; cardinality: Warm empty or persisted-session reads cause no token exchange. Cold missing Microsoft links and stale transient tokens use the existing account/session-keyed restore/renew mechanisms. One interactive createSession remains, with enterprise host choice occurring inside that existing operation.
    - Introduced by diff: true; previous behavior: The login and provider maintenance mechanisms existed, but signIn did not add its own preliminary discovery invocation.; critical-path effect: Potential maintenance latency precedes interactive login; successful reads are normally warmed by startup or prior authentication resolution.
  - IPC/filesystem/network at <code>src/vs/workbench/services/accounts/browser/defaultAccount.ts:signIn, updateDefaultAccount; extensions/github-authentication/src/github.ts:storeSessions</code>: Create/persist the session and refresh account metadata after authorization.; cardinality: Same one session creation and account-update path as before. Warm account-specific caches suppress metadata requests; a new account uses the existing cold refresh path.
    - Introduced by diff: false; previous behavior: Identical default-scope request, persistence, refresh scheduling and cache behavior in these fallback cases.; critical-path effect: Existing awaited successful sign-in work.
- Verdict: No high-confidence actionable performance regression; an intentional authoritative scope check adds bounded work to an already interactive operation.
