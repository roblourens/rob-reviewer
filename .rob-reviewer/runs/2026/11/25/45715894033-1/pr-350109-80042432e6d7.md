Reporting runs after resolving/rejecting connection waiters; telemetry transport completion is not awaited.
- Scaling input: Distinct SSH addresses, concurrent logical clients, distinct remote endpoint PIDs, configured trust files, and cold installation/agent-start state.
- Effective concurrency: One renderer dial per address; shared physical-session bootstrap is coalesced by key. Independent hosts may proceed concurrently, and endpoint liveness probes run concurrently per distinct PID. Per-session bootstrap stages and registry polling remain ordered. No new concurrency is introduced.
- Cache behavior: Renderer pending maps join same-address callers. Shared-process \_pendingSessions joins bootstrap by connection key and \_connections reuses successful sessions. Installed commit-keyed CLIs are reused; misses install/download using the existing helper. A renderer with an already usable connection returns its handle without a new factory dial. Failure-code wrappers do not change positive or negative cache behavior.
- Mechanism confidence: High: traced both renderer coalescing and shared-process session/relay ownership, plus the remote command, subprocess, filesystem, and telemetry enqueue implementations.

### Scenario 2: Startup autoconnection to saved SSH hosts and automatic retries of unavailable hosts

- Critical path: Each configured host independently waits for its existing connect pipeline. A failed attempt schedules the next existing backoff before reporting its outcome; telemetry delivery does not gate the next retry.
- Scaling input: Number of distinct saved hosts and actual failed dials within the unchanged retry cycle; separate windows may each own a logical dial but physical-session bootstrap is shared by connection key.
- Effective concurrency: Independent addresses may dial concurrently as before, with no global limiter introduced or removed. Each address retains one in-flight dial and one reconnect timer. Reporting does not issue another dial or await network telemetry.
- Cache behavior: In-flight attempts are joined per address and per physical connection key; successful sessions are reused. Failed attempts retain the existing retry policy rather than adding a negative cache. Telemetry's pre-experiment buffer is bounded by the existing MAX\_BUFFER\_SIZE.
- Mechanism confidence: High: compared the old and new short-circuit retry expressions, the separate counter maps, and telemetry's gating/buffering/IPC implementation.
- Magnitude uncertainty: Unknown typical saved-host count and telemetry enqueue duration; no evidence of a high-frequency unbounded telemetry loop added by this change.
- Expensive boundaries:

### Scenario 3: Recovery of an established SSH connection, including relay-only recovery and protocol-handshake failure

- Critical path: The existing protocol client first attempts self-recovery. Fatal outer recovery rebuilds through the factory; protocol incompatibility and terminal authentication failures stop retries. New telemetry describes these decisions without waiting for delivery.
- Scaling input: Actual transport drops, outer retry cycles, logical relay clients, and independent connection IDs; not session-history length or message traffic.
- Effective concurrency: The existing inner recovery client retains ownership until terminal failure; the outer service does not rebuild during self-healing reconnect. Pending outer dials join per address; pending relay replacements join per expected connection ID.
- Cache behavior: Existing SSH sessions and pending relay replacements are reused. Successful recovery resets both the old retry-budget map and new dial-number map. Inner reconnects do not generate additional factory-operation map entries.
- Mechanism confidence: High: traced self-healing versus fatal recovery branches, shared-process lease acquisition, unchanged boundary calls, and all report-hook call sites.
- Magnitude uncertainty: Drop frequency and transport-recovery duration are environment-dependent; no measurements were available.

### Scenario 4: Connection removal, disposal, and generic non-SSH connection bookkeeping

- Critical path: Existing removal/disposal paths cancel reconnect timers and dispose clients/transports. Generic non-SSH dials execute their existing factories and handshake; only SSH implements the new optional production reporting hook.
- Scaling input: Active or failed addresses, removed connections, and actual dial count. New maps hold address keys and scalar operation/count values, not SSH clients, errors, payloads, or connection histories.
- Effective concurrency: No changes to disposal ordering, pending-dial identity guards, or factory invocation concurrency. Repository search confirms no other production factory implements reportConnectionAttempt.
- Cache behavior: Dial counters are reset on successful/incompatible connections, explicit fresh reconnect, removal, disablement, and service disposal. Normal SSH outcome reporting deletes the per-dial operation entry. No new heavyweight cache or eager factory construction is introduced.
- Mechanism confidence: High for unchanged resource ownership and optional-hook reachability; no substantial diff-introduced retention mechanism established.
- Magnitude uncertainty: Rare discarded attempts can leave small scalar factory bookkeeping until replacement/factory lifetime ends; inspected paths do not establish significant retained-resource growth under a realistic high-volume workflow.
- Expensive boundaries:
  - other at <code>src/vs/platform/agentHost/browser/remoteAgentHostServiceImpl.ts:\_reconcileConnections, \_removeConnection, \_resetReconnectAttempts, dispose</code>: Run existing transport/client disposal while clearing per-address retry bookkeeping.; cardinality: Existing disposal work remains once per removed connection/transport generation.     - Introduced by diff: false; previous behavior: The same clients, transports, and timers were removed; only the new dial-number map needs additional bookkeeping.; critical-path effect: Same synchronous teardown placement as before.
- Verdict: No actionable performance finding. Generic connection paths gain constant-size bookkeeping without new subprocess, network, filesystem, or database calls.
