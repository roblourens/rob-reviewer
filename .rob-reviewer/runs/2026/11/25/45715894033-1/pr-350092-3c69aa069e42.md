## Findings (1)

### 1. [medium] Validate the selected ref without relisting every branch

**Finding ID:** `PERF-E4BAF474A4E1`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostBaseBranchOperationProvider.ts:91</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** One additional Git subprocess enumerating and sorting all branch refs, reading their tip commits, and buffering/parsing all resulting branch records.  
**Scaling:** One redundant full-list subprocess per applied selection, not one process per branch. Its work scales with the total number B of local and remote branches: all B refs and tip commits are visited and the records are sorted, even though only one ref is being validated. Same-operation in-flight joining does not help because the picker listing has already completed.  
**Outcome:** Additional input-size-dependent latency before the selected base is persisted and the comparison refresh can begin.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The base revision had no base-selection operation and did not add this second scan on a picker selection. In the new workflow, the full branch listing is already paid once when opening the picker; repeating that display-oriented query is newly introduced validation work.  
**Changed behavior:** Applying one selected ref now waits for another complete, commit-date-sorted branch listing before writing the base metadata and initiating the diff refresh.  
**Confidence:** 0.97 — The picker-to-set call path and awaited full query are explicit. getRefs constructs --sort -committerdate, and the Git service documents that this reads every ref's tip commit. Completed reads are not cached. Actual delay depends on branch count and filesystem cache warmth; no timing was measured.

**Causal diff evidence:** The new \_setBaseBranch implementation awaits getBranches(repositoryRoot, branchQuery) at line 91; branchQuery at line 24 selects every local and remote ref and sorts by committerdate. This adds a second full enumeration after \_listBaseBranches has already completed the same query to populate the picker.

In repositories with thousands of local/remote branches, choosing a base repeats the repository-wide tip-commit reads, sorting, output buffering and parsing, delaying the label and comparison update after the picker closes. Warm filesystem caches reduce I/O latency but do not eliminate the second full scan and sort.

**Evidence:** showBaseBranchPicker first awaits getCandidates, then invokes setBaseBranch for a selected row. \_listBaseBranches performs getBranches with branchQuery. \_setBaseBranch repeats that query solely for branches.some(ref equality). AgentHostGitService.getRefs (lines 183-202) runs git for-each-ref with the query's sort and patterns, and parses the full output. Its in-flight read cache is cleared on completion, so it cannot reuse the listing that produced the selected row. The existing getBranch(repositoryRoot, ref) API (lines 210-230) accepts full refs, performs an unsorted ref-scoped lookup, and selects the exact match.

**Suggested direction:** Validate the selected full ref with the existing getBranch(repositoryRoot, ref) API and reject an absent or nonmatching result, rather than rerunning the sorted all-branches query. Keep the full sorted query only for populating the picker.
