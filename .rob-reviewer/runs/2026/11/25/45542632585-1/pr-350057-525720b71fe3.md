### Scenario 1: Agents window startup and picker registration; editor-window registration remains unchanged

- Critical path: The new contribution registers one picker at AfterRestored. Its constructor only retains injected services; session enumeration and eligibility checks wait until the user chooses Sessions. SessionsManagementService was already registered eagerly before this PR.
- Scaling input: Constant registration work; existing service initialization depends on registered providers and configured hosts, not the number of picker openings.
- Effective concurrency: One contribution and one picker registration per window, with the old picker explicitly excluded in the Agents window. No new task fan-out or recurring listeners.
- Cache behavior: The contribution creates no cache. Existing session catalogs and remote connection services retain their existing initialization, caching, and retry behavior.
- Mechanism confidence: High: inspected contribution registration, both picker constructors, eager SessionsManagementService registration, and service initialization.
- Magnitude uncertainty: No startup timing measurements; module-load and small registration costs are not quantified.
- Expensive boundaries: none found
- Verdict: No actionable startup regression: the added registration does not enumerate sessions or issue new picker-specific boundary operations.

### Scenario 2: Open, search, reopen, and close the local Sessions attachment picker

- Critical path: asPicker synchronously reads the catalog, filters, sorts eligible sessions, and constructs pick descriptions before the quick pick is shown. Construction occurs once per opening, not on every search keystroke. Normal populated catalogs require no awaited boundary operation.
- Scaling input: N sessions across registered providers, deduplicated by SessionsManagementService; K eligible same-host sessions excluding the current session. Filtering is collection-wide and sorting is O(K log K), with K descriptions and closures.
- Effective concurrency: Synchronous catalog processing on the UI thread; no per-session asynchronous operations. Any cold provider refresh is background work, coalesced per provider/connection with existing retry backoff.
- Cache behavior: Catalog reads use provider caches seeded by the existing management-service subscription. Agent-host providers treat successful empty listings as initialized, join in-flight refreshes, and honor scheduled retry backoff. Reopening rebuilds picks but does not refresh initialized agent-host catalogs.
- Mechanism confidence: High: traced asPicker through management/provider reads and the quick-pick caller; the promise-backed picks are not recomputed on query changes.
- Magnitude uncertainty: Production catalog sizes and formatting durations are not measured. Large catalogs incur synchronous work, but the prior picker and existing session completions already use collection sorting and per-result date formatting; no independently established actionable regression.
- Expensive boundaries:
  - IPC/network at <code>src/vs/workbench/contrib/sessions/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_ensureSessionCache, \_startSessionRefresh, \_listSessions</code>: A genuinely uninitialized connected provider may issue connection.listSessions().; cardinality: At most one newly started listing per uninitialized provider/connection without an existing refresh or retry; zero on initialized reads. Never one listing per session.
    - Introduced by diff: true; previous behavior: The Agents picker used getChatSessionItems instead of this catalog path, but SessionsManagementService already called provider.getSessions during provider subscription, initiating the same cold listing independently of the picker.; critical-path effect: Refresh is started without awaiting it; the picker uses the currently available catalog. Existing startup subscriptions normally already initiated cache population.
- Verdict: No high-confidence performance regression. The change performs demand-driven catalog processing without per-session I/O or repeated query-triggered enumeration.

### Scenario 3: Open the Sessions picker for a remote session, including disconnected or missing-home hosts

- Critical path: The picker filters sessions to the current host and resolves event-log paths using in-memory connection metadata. buildHostLocalEventsPath and resolveEventsUri only construct and convert URIs; they do not stat or read event logs or establish connections.
- Scaling input: N deduplicated catalog entries, K readable same-host sessions, and H configured connection entries. Remote eligibility checks involve O(KH) connection-snapshot/search work, not K remote requests; only K picks are sorted and displayed.
- Effective concurrency: Synchronous processing. For each eligible remote candidate, the connections getter constructs a snapshot and find searches it. Existing provider cache refreshes remain coalesced per connection, not per session; independent cold providers can refresh concurrently as before.
- Cache behavior: No new remote cache. Connection status and home-directory metadata come from existing services; disconnected or unavailable paths are rejected without retries from the eligibility resolver. Provider cold/warm behavior is the same as the local catalog scenario.
- Mechanism confidence: High: inspected remote connections getter, host filtering, URI resolver, and provider refresh guards.
- Magnitude uncertainty: Host and catalog counts are unmeasured. The connection-snapshot pattern also exists in the prior picker helper; there is no evidence of a realistic new resource burst or user-visible bottleneck from this change.
- Expensive boundaries:
  - IPC/network at <code>src/vs/workbench/contrib/sessions/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_listSessions</code>: Existing cold catalog refresh calls connection.listSessions for a remote provider.; cardinality: Zero additional calls for initialized catalogs or providers with a current refresh/backoff; otherwise at most one start per cold provider/connection, not per matching session or remote path resolution.
    - Introduced by diff: true; previous behavior: The old Agents picker did not consult this catalog, while the existing eagerly initialized management service and sidebar already populated these provider caches through the same operation.; critical-path effect: Not awaited by asPicker; no remote round trip is required to format an already cached candidate.
- Verdict: No reportable boundary fan-out or cache regression. Remote eligibility is pure metadata work, with any actual listing grouped by provider/connection and off the picker critical path.

### Scenario 4: Accept a session attachment and dispose the picker

- Critical path: Accepting a result synchronously creates one sessionReference entry and passes it to the existing attachment model. The entry contains the selected resource, title, and icon, not the session transcript. Closing disposes quick-pick subscriptions through the unchanged caller.
- Scaling input: K short-lived pick objects during an opening and A explicitly selected attachment resources afterward; no catalog-wide attachment serialization or transcript loading.
- Effective concurrency: One entry per accepted selection; background acceptance reuses the same pick list. Attachment IDs are deduplicated by the existing model. No new asynchronous producer or listener is owned by individual pick entries.
- Cache behavior: Picker arrays are scoped to the existing quick-pick lifecycle, with no global accumulation. The attachment model retains only selected entries and uses its existing removal/clear lifecycle.
- Mechanism confidence: High: traced asAttachment, the quick-pick acceptance/disposal path, ChatAttachmentModel, and the unchanged agent-host session-reference conversion.
- Magnitude uncertainty: No heap profiling was performed. Downstream agent request processing remains the existing session-reference path, which already constructs a small text attachment and a trajectory resource reference.
- Expensive boundaries: none found
- Verdict: No diff-introduced retention or serialization regression. The new picker feeds the existing attachment representation without eagerly reading or copying event logs.
