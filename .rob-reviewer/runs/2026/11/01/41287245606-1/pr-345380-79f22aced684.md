# Performance review: Drop pending system notifications when the user stops a chat request

[PR #345380](https://github.com/microsoft/vscode/pull/345380) at `79f22aced684da82591cd318045526659bff6e35`

## Findings (1)

### 1. [medium] Batch queued notification removals before refreshing the chat list

**Finding ID:** `PERF-2AC1F51B581D`  
**Location:** <code>src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:2682</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** main-thread queue scans, ChatRequestViewModel allocations, and chat list refreshes  
**Scaling:** For K queued system notifications, each call scans/splices the remaining N-item queue and synchronously fires onDidChangePendingRequests; the visible widget then recomputes its transcript-wide T-item view and refreshes the list, making the stop path O(K\*(N+T)) rather than one O(N+T) batch update.  
**Outcome:** Repeated synchronous list reconstruction and refresh can make the Stop action visibly stall or jank when several parallel background terminal completions have queued notifications in a long chat.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Canceling an active request did not mutate the pending queue, so it did not synchronously emit one pending-queue event and list refresh per queued system notification.  
**Changed behavior:** The added cancellation loop removes each matching notification through removePendingRequest separately, and each removal synchronously emits a pending-queue change before the next item is removed.  
**Confidence:** 0.96 — The changed loop, synchronous event chain, repeated full transcript/queue recomputation, and uncapped parallel notification source are all directly traced in repository code. Exact notification counts and device-specific frame impact vary, which limits severity rather than confidence in the mechanism.

**Causal diff evidence:** Added lines 2682-2683 iterate every queued system notification and invoke removePendingRequest once per item; before this diff cancellation performed no queue removals or pending-queue UI notifications.

When an agent has launched several background terminals in parallel and their completion notifications accumulate while a long chat request is active, pressing Stop now performs and renders every intermediate queue state before returning to the user.

**Evidence:** runInTerminalTool.ts documents that background mode always creates a new terminal to allow parallel execution and maintains uncapped active-execution/background-notification maps. Each completion sends an isSystemInitiated steering request. ChatModel.removePendingRequest uses findIndex/splice and immediately fires onDidChangePendingRequests; ChatViewModel handles that event by invalidating its cache, ChatWidget calls onDidChangeItems, computeItems scans the full transcript and pending queue and creates pending ChatRequestViewModels, and onDidChangeItems refreshes the list. removePendingRequest also rescans the remaining queue for steering requests on every iteration.

**Suggested direction:** Add a batched removal path that filters/replaces the pending queue once, emits one pending-queue change, completes each removed deferred, and resets yield state once; use it here so observers see only the final queue while preserving rejection semantics.
