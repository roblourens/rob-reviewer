<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work, serialization-allocation

### Scenario 1: Show or relayout a context view, including menus, hovers, and action widgets near the title bar

- Critical path: ContextView.show/layout synchronously measures the anchor and view, computes layout2d, then the changed code reads visible WCO geometry and adjusts the position before writing CSS coordinates. All of this completes before the context view is positioned and usable.
- Scaling input: One lookup and constant-size adjustment per visible ContextView layout. Most relayouts occur once on show or on container/hover content changes; an existing action-widget animation can invoke layout once per animation frame, but there is still only one active service context view and no multiplication by menu items or document size.
- Effective concurrency: Synchronous on the UI thread; calls are serialized by the event loop. Existing layout events and animation frames are not given new parallelism or queues by the diff.
- Cache behavior: The code intentionally does not cache WCO geometry, so both cold and warm layouts perform one lookup when the overlay is visible. Unsupported or invisible overlays return before allocating the helper's validation and strip arrays. There is no positive/negative cache or coalescing behavior changed by the PR.
- Mechanism confidence: High confidence in the changed call path, synchronous placement, and fixed cardinality; low evidence that the browser getter or constant-size allocations are expensive enough to cause user-visible latency or frame loss.
- Magnitude uncertainty: The implementation cost of Chromium's WCO geometry getter is not established in repository evidence, but the changed cardinality is strictly one per layout and the helper processes only two strips. This is insufficient to establish a meaningful regression even on the existing short per-frame animation path.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/base/browser/ui/contextview/contextview.ts:621 via src/vs/base/browser/browser.ts:158-162</code>: Synchronous browser Window Controls Overlay geometry lookup via navigator.windowControlsOverlay.getTitlebarAreaRect(); cardinality: At most once per ContextView layout; one active shared context view for the service path, or once per independently visible hover layout. Existing per-frame action-widget animation yields one lookup per frame, not per action/item.
    - Introduced by diff: true; previous behavior: The same scenario already synchronously wrote temporary position styles and measured page position and total view size, but did not query WCO geometry or run the fixed-size overlap adjustment.; critical-path effect: The lookup is on the positioning critical path, after existing DOM measurement and before style writes. Repository usage treats the same API as a direct geometry getter; there is no evidence it performs IPC, forces an additional DOM layout, or has input-dependent cost.
- Verdict: No reportable performance regression. The added work is bounded and small relative to the pre-existing forced DOM measurements in the same layout pass, with no collection scaling, fan-out, concurrency burst, or retained lifecycle.

### Scenario 2: Open a first-level or nested submenu

- Critical path: Submenu creation constructs and measures the menu, computes its viewport placement, then the changed code reads WCO geometry and adjusts the result before setting left/top. The submenu cannot be displayed at its final position until this synchronous work completes.
- Scaling input: Exactly one WCO lookup and one constant-size overlap calculation for each submenu level when that level is opened. Cost scales with user-opened nesting depth, not with the number of submenu actions; menu construction and DOM measurement already scale with action count before this change.
- Effective concurrency: Submenus open serially in response to keyboard/pointer interaction. No Promise fan-out, background task, limiter, or burst is introduced.
- Cache behavior: No cache is used. Unsupported or invisible overlays take an immediate return; visible overlays are read once for each newly opened submenu so current geometry is used. Re-focusing an already-created submenu does not rerun \_layoutSubmenu in the shown path.
- Mechanism confidence: High confidence that the new work occurs once per opened level and is synchronous; no evidence supports a material latency, CPU, GC, rendering, or IPC regression.
- Magnitude uncertainty: Native getter latency is not measured, but realistic depth is small and the changed work does not scale with the 200-item tall-menu case beyond the existing menu construction/measurement.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/base/browser/ui/menu/menu.ts:1019 via src/vs/base/browser/browser.ts:158-162</code>: Synchronous browser Window Controls Overlay geometry lookup; cardinality: One call per newly opened submenu level, independent of submenu child count.
    - Introduced by diff: true; previous behavior: Opening each submenu already performed synchronous style and DOM geometry reads and menu construction; it did not read WCO geometry or apply the fixed-size two-strip adjustment.; critical-path effect: Runs on the submenu-open critical path after pre-existing getComputedStyle and two getBoundingClientRect measurements. No evidence shows a new layout flush or cross-process operation.
- Verdict: No reportable performance regression. The change adds constant bounded work to an already geometry-heavy, user-triggered open path and does not add per-item work.

### Scenario 3: Compute title-bar geometry for existing titlebar layout callers

- Critical path: Existing titlebar minimum-height getters continue using getWCOTitlebarAreaRect directly. The new exported helper is not invoked by those callers, so their startup/layout critical path is unchanged.
- Scaling input: No changed multiplicity for titlebar parts; the helper addition itself performs no eager work at module load.
- Effective concurrency: Unchanged synchronous getter execution in existing titlebar layout.
- Cache behavior: Existing titlebar callers remain uncached and unchanged. The new helper has no module-level state and cannot retain geometry or objects.
- Mechanism confidence: High confidence based on complete symbol search and the pure new module.
- Magnitude uncertainty: None material: repository call-site search confirms only the two new UI placement call sites use getVisibleWCOTitlebarAreaRect.
- Expensive boundaries: none found
- Verdict: No performance change on existing titlebar layout or startup paths; importing the helper module adds only declarations with no eager runtime initialization.

**Summary:** Reviewed all 7 changed files and traced context-view show/relayout, per-frame action-widget relayout, hover resize, submenu opening, and existing titlebar geometry use. The PR adds one synchronous WCO getter plus fixed two-strip arithmetic per affected layout/open. It introduces no scaling boundary calls, cache growth, retained resources, unbounded concurrency, or additional DOM layout flush proven by the code, so no performance finding was submitted.
