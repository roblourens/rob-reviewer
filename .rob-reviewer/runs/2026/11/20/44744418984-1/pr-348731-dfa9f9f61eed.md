### Scenario 1: Merge queue runs selected browser unit tests in the new Linux WebKit job, including full-suite fallback.

- Critical path: Detect Changes must finish before the reusable Linux workflow starts. The new job performs setup, installs WebKit, and runs tests sequentially within its runner. PR Gate waits for linux-tests as well as sibling workflows; this is an additional parallel gate dependency, not an unconditional serial stage before all other tests. The whole WebKit job has a 12-minute timeout.
- Scaling input: One additional runner per eligible merge-group run. N is the unique selected compiled browser test files after runList Set filtering and exclusion of Node/Electron-only folders; without a usable plan, N is all browser test files. Each of W workers imports all N files, but filesystem-backed claims distribute test-file execution rather than executing the whole suite W times.
- Effective concurrency: A separate 8-core merge-queue runner executes the new job independently of Chromium and other jobs. W is capped at 4, available CPUs, and one worker per 2 GiB of total memory. With a run list, W is additionally min(fileCount, max(2, floor(fileCount/75))), with a minimum of 1. Image restoration uses at most 32 connections and a bounded 64-chunk decompression window. No new per-test browser launch or unbounded worker fan-out.
- Cache behavior: Workspace images of main retain dependencies and the pnpm store; image restore failure falls back to cached-store/cold installation. Linux system packages have an image/version/list-keyed deb cache. Built-in extensions have a content-keyed cache and version checks. The Linux workspace image installs only Chromium, and this new job does not restore a WebKit browser cache, so successful fresh jobs download WebKit even when the workspace image is warm. Within an installation retry, completed files can be reused. Test selection remains artifact-driven and fails open to the whole suite.
- Mechanism confidence: High confidence in the new gate dependency, uncached WebKit installation, cache-aware shared setup, bounded worker count, all-files-per-worker imports, and distributed test execution, established directly from workflow and runner code.
- Magnitude uncertainty: No measured runner durations, cache-hit rates, queue contention, or selected-file distributions were independently available. The additional uncached installation and test run can increase gate latency when this job becomes the slowest sibling; the repository's timing comments are not treated as proof that it never does.
