# Performance review: sessions: show the editor of a session inside the Agents window

[PR #349243](https://github.com/microsoft/vscode/pull/349243) at `6e2edb74a349b5c426abae1f27b668c60c99cf4a`

## Findings (3)

### 1. [high] Reuse multi-folder editors before creating an untitled workspace

**Finding ID:** `PERF-2CFCF45F0726`  
**Location:** <code>src/vs/platform/windows/electron-main/windowsMainService.ts:338</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** Untitled workspace files, full workbench renderers, workspace initialization, extension-host processes and file-watcher workers  
**Scaling:** For R returns to the same remembered multi-folder session, there are R new workspace creations and R editor startups despite an unchanged folder set; local path validation is F stats per return for F folders. Workers are keyed by window ID, so duplicate editors do not share the per-window worker cache.  
**Outcome:** Repeated cold editor initialization delays session switching and accumulates duplicate renderer/process memory and workspace I/O.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Selecting another session and returning did not reopen an editor or create another workspace. Untitled workspace creation on the old explicit Open in Editor action existed, but was not performed on session-list navigation.  
**Changed behavior:** For a session with multiple folders not matching a workspace from the previous application run, each return creates a new workspace config path. The existing embedded editor consequently misses the identity lookup and another complete editor is started instead of reusing it.  
**Confidence:** 0.99 — The last-session lookup reads startup-restored window state, createUntitledWorkspace generates a new config path, and windowsFinder matches multi-folder windows only by that path. The new session-selection autorun reaches this code on every return to a remembered session. This is static evidence; startup duration depends on workspace and extensions.

**Causal diff evidence:** Added line 338 creates a new untitled workspace before added line 349 searches embeddedWindows by workspaceUri. Added embeddedEditor.ts:255-258 invokes doShow again when a remembered session is selected, introducing this repeated creation into ordinary navigation.

Open the embedded editor for a new two-folder session, switch to another session, then return repeatedly. Each return starts another editor and writes another untitled workspace rather than displaying the already-loaded editor, making navigation expensive even with a nominally warm cache.

**Evidence:** windowsMainService.ts:1259-1279 searches only doGetPathsFromLastSession(); :1186-1236 sources that list from windowsStateHandler.state. workspacesManagementMainService.ts:171-199 generates a new random config folder and performs mkdir/writeFile. windowsFinder.ts:42-58 matches workspace.configPath, not folder membership. windowsMainService.ts:349-357 therefore creates another CodeWindow; :1807 retains it. Each workbench loads normally (:1936), with window-keyed watcher workers (utilityProcessWorkerMainService.ts:80-84).

**Suggested direction:** Match the current embedded editors by normalized folder set and remote authority before creating an untitled workspace, reusing their existing workspace identifier. Retain that identity for the embedded editor's lifetime and remove it on close; resolveLocalWorkspace already exposes workspace folders for comparison.

### 2. [medium] Bound retention of hidden embedded workbenches

**Finding ID:** `PERF-F934DB0CC595`  
**Location:** <code>src/vs/platform/windows/electron-main/windowsMainService.ts:403</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Hidden workbench renderer heaps and native views, local extension hosts, and per-window file-watcher workers  
**Scaling:** Retention grows with the number of distinct workspace identities whose editors have been opened during one Agents-window lifetime, not with session count when folders are shared. Successful single-folder cache hits reuse one editor, but there is no cap or eviction across distinct folders/worktrees.  
**Outcome:** Growing resident memory and background process/watch activity persist after leaving editors, increasing memory pressure and reducing responsiveness during long-lived Agents sessions.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The editor was a separate, user-visible window with its ordinary close lifecycle. Closing it when returning to Agents released its workbench and window-bound processes; selecting sessions did not maintain an invisible editor cache owned by the Agents window.  
**Changed behavior:** Back to Agents and switching sessions leave every previously opened distinct workspace's complete editor resident, even when the session preference is forgotten. Only the visible-window map entry is removed; all hidden CodeWindows remain in the global windows map and attached to the parent.  
**Confidence:** 0.98 — The changed hide path only hides the native view; the windows map and child view retain the full CodeWindow until an explicit editor close or parent close. Transitive worker ownership is per window and ends on close/reload, not hiding. The number of distinct workspaces visited and their memory footprints are unmeasured.

**Causal diff evidence:** Added line 403 replaces the previous embedded editor with layoutEmbedded(undefined), whose added windowImpl.ts:1015-1024 only calls setVisible(false). No close or eviction occurs when Back to Agents forgets the session or when another workspace is opened.

A user opens editors for successive session folders/worktrees and presses Back to Agents after each. All those hidden workbenches and their window-owned resources remain loaded for the entire Agents-window lifetime, even though none is visible or remembered for automatic restoration.

**Evidence:** windowsMainService.ts:349-357 creates an editor for each missing workspace; :1807 stores it in windows. :399-403 deletes only visibleEmbeddedWindows and hides the previous view. windowImpl.ts:909-922 attaches its WebContentsView and closes it only during disposal; :1015-1024 does not dispose. EmbeddedEditorSessionMemory.willHide (:133-136) forgets the preference without releasing the editor. WorkspaceWatcher initializes recursive watches; UniversalWatcherClient creates a worker whose lifetime is close/reload, and utilityProcessWorkerMainService.ts:80-84 keys workers by windowId. Parent-close cleanup appears only at windowsMainService.ts:419-424.

**Suggested direction:** Keep instant toggling for a bounded set of recently used embedded editors, but evict inactive clean editors through their normal close lifecycle and release editors for removed sessions. Preserve dirty-file vetoes/pinned editors rather than destroying them, and clear cache ownership on close.

### 3. [medium] Reuse the snapshot while the editor is already occluded

**Finding ID:** `PERF-78AB4CAA8EE5`  
**Location:** <code>src/vs/sessions/electron-browser/embeddedEditor.ts:351</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Full-view compositor readbacks, synchronous main-process JPEG encoding, image-byte IPC transfers and renderer Blob/image allocations  
**Scaling:** One full-view capture and JPEG encode per picker onShow, including each provider change during a single continuously visible quick-input interval. Cost grows with provider replacements and captured pixel area; no snapshot reuse or in-flight coalescing exists, and native encoding runs on the single main-process thread.  
**Outcome:** Redundant main-thread CPU and image transfer/allocation work causes input latency and IPC contention, especially with a large or high-DPI editor view.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Quick-access provider replacement used the same quick-input surface without any native screenshot, JPEG encoding or image IPC transfer.  
**Changed behavior:** Every quick-input controller replacement captures the embedded editor again, although the editor is already hidden behind the existing snapshot. Rapid replacements also launch independent captures and discard superseded results only after the expensive work.  
**Confidence:** 0.96 — QuickAccess recreates its picker on provider changes; QuickInputController emits onShow for replacement without emitting its global onHide. The added handler unconditionally captures and the native service synchronously JPEG-encodes the full view before returning. Pixel size and measured encode latency are unknown, but redundant boundary calls and main-thread work are directly traced.

**Causal diff evidence:** Added line 351 invokes getScreenshot for every onShow, even when picture already holds a snapshot or a previous request is in flight. The generation check at line 352 happens only after capture and encoding have completed.

With an embedded editor open, switch quick-access providers by changing the prefix, or replace an open picker with another picker. Each replacement repeats a full editor capture and JPEG(95) encode while the editor is already occluded; quick changes can produce captures whose results are immediately discarded.

**Evidence:** sessions.common.main.ts:38,265 enables the shared quick-access actions/providers. quickAccess.ts:213-224 recreates the picker when the provider changes and :166 calls show(). quickInputController.ts:742-757 replaces the old controller via didHide(), then :819 fires onShow; the service-level onHide fires only in hide() at :918. EmbeddedEditorService.occludeWhile (:348-352) has no picture/in-flight guard. nativeHostMainService.ts:1179-1184 calls capturePage(rect) with no rect here and synchronously toJPEG(95); embeddedEditor.ts:358-360 then copies the returned bytes into a Blob.

**Suggested direction:** Capture once per actual occlusion interval and reuse its picture across picker replacements. Coalesce an in-flight capture rather than launching another; invalidate on embedded-window/bounds changes, and release the snapshot on the actual onHide or service-store disposal.
