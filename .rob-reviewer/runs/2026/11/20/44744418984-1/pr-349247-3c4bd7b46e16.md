### Scenario 1: Run Chat: Plugins or /plugins in the editor window with a local chat session, including first open and repeated invocation.

- Critical path: ManagePluginsAction awaits one OpenEditor command, which awaits editorService.openEditor before selecting Plugins. Editor construction/layout is synchronous; provider item loading, plugin filtering, and migration discovery are launched asynchronously and are not awaited by the action. Installed rows await provider data where applicable.
- Scaling input: Five fixed customization section types, configured customization folders/files, installed plugin count, deduplicated marketplace repository references, and migration recovery directories. User command frequency is explicit invocation, not input/scroll/render frequency.
- Effective concurrency: One nested command per invocation. Five local section queries share one provider promise. Initialization migration requests coalesce through a zero-delay Delayer. Marketplace references use Promise.all, while clone-backed operations are serialized per repository key, not globally.
- Cache behavior: Management input is singleton-style and selected-section dispatch returns early when already selected. Item sources cache an in-flight/resolved provider promise across section consumers and invalidate on provider changes. Plugin snapshots distinguish uninitialized/loading/loaded/failed, so empty or failed results are not retried on every render. GitHub success cache and repository refresh TTL are unchanged.
- Mechanism confidence: High confidence in command routing, asynchronous loading, shared provider caching, snapshot lifecycle and repository-level grouping from implementation reads.
- Magnitude uncertainty: No timings or profiling are available. File counts, recovery history and marketplace configuration vary. Existing editor construction does additional work compared with displaying the former intermediary, but no pathological new multiplicity or blocking boundary was established.

### Scenario 2: Run Chat: Plugins or /plugins in the editor window while an agent-host-backed customization harness is active.

- Critical path: The command resolves the active harness/session, opens the same singleton management editor and then selects Plugins. Plugin rows asynchronously await shared provider customizations; migration information is independently deferred.
- Scaling input: Distinct runtime providers, plugin directory contents, active-harness customization files, fixed migration categories and recovery history. Effective inventory cardinality is provider count, not installed plugin count.
- Effective concurrency: Inventories run concurrently across distinct providers, directory expansions across uncached plugins; all section reads coalesce into one provider call. Migration initialization is delayed/coalesced and uses cancellation/sequence checks. No new concurrency policy is introduced.
- Cache behavior: PureItemProviderItemSource caches the in-flight/resolved provider promise, invalidates on provider changes, and resets rejected promises. Directory expansions reuse nonce/label-validated entries. Repeated invocation reuses the singleton input; section selection has an unchanged early return.
- Mechanism confidence: High confidence in grouped inventory requests, provider-promise coalescing, expansion caching and the separation of async data population from command completion.
- Magnitude uncertainty: Host latency, plugin file counts and migration candidate counts are not measured. Broader initialization is the existing management UI's behavior, not evidence by itself of a newly pathological mechanism.
- Expensive boundaries:
