# Performance review: Chat: search agent requests across connected hosts (proposed by opus 5.5)

[PR #349136](https://github.com/microsoft/vscode/pull/349136) at `4bbbe8453d946f62e8be4f49234fc830b562d424`

## Findings (1)

### 1. [medium] Coalesce superseded searches before dispatching another host RPC

**Finding ID:** `PERF-0E47CBAD0FE6`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/requestSearch/agentRequestSearchService.ts:161</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Host search RPCs, serial request-index queue entries, substring database scans, and optional per-hit session-database I/O.  
**Scaling:** For Q input revisions that each survive the 250 ms debounce and H eligible connected hosts, up to Q×H searches are dispatched. Each host executes its Q searches serially; if searches take longer than the input pauses, the latest query waits for the accumulated obsolete work. The index retains roughly 20,000 requests; hydration is bounded to the requested 20 default/50 maximum visible hits, with suppression checks grouped per session within each search.  
**Outcome:** Increasing latency and avoidable timeouts for the latest search, with wasted host CPU and filesystem/database I/O from superseded queries.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The base supplied the host search endpoint but had no production quick-pick caller repeatedly issuing it as input changed, so typing and abandoning queries could not build this client-generated queue of obsolete host searches.  
**Changed behavior:** Each debounce-fired query now dispatches another search to every eligible connected host, even when a superseded search on that connection has not finished. Cancellation and the 10-second timeout release the caller without cancelling or coalescing the actual host work.  
**Confidence:** 0.98 — Static tracing establishes that Delayer does not throttle running tasks, neither race helper cancels its input promise, searchRequests accepts no cancellation token, and AgentHostRequestIndex.search serializes complete searches on one Sequencer. The amount of accumulated latency depends on host storage speed and history size, not on an uncertain call path.

**Causal diff evidence:** New line 161 starts connection.searchRequests(query, limit) and wraps only its returned promise in raceCancellation/raceTimeout. The new quick-pick driver (searchAgentRequestsAction.ts:57-69) cancels the previous token on every edit but uses a plain 250 ms Delayer, which permits another dispatch while the previous underlying RPC remains active. Before this PR there was no production search-as-you-type caller of this host endpoint.

When refining a query against a large request history or a slow host, obsolete searches continue consuming database/filesystem work and occupy the host's serial search queue. The final query waits behind requests whose results will never be displayed and can exhaust its 10-second timeout before it gets serviced; closing the picker also leaves dispatched work running.

**Evidence:** searchAgentRequestsAction.ts:57-69 starts a new debounced search after cancelling the old token. agentHostProtocolClient.ts:2461-2466 sends an ordinary extension RPC with no cancellation; \_sendExtensionRequest at 3854-3855 supplies no protocol deadline. AgentHostRequestIndex.search (agentHostRequestIndex.ts:157-205) queues each entire search on \_sequencer, runs substring SQL over indexed requests, and awaits hit hydration sequentially. For unloaded hits, \_eventId additionally stats/opens session databases via SessionDataService.tryOpenDatabase. Neither the host sequencer nor these operations observes the cancelled UI token.

**Suggested direction:** Keep at most one underlying search RPC in flight per connection and replace pending superseded queries with the latest query. Hold that slot until the actual RPC settles, not merely until its cancellation/timeout wrapper resolves, and recheck cancellation before dispatching queued work.

### Scenario 3: Typing refinements, clearing input, closing the picker, or timing out while earlier host searches remain active

- Critical path: A new query's result must wait for its own host search, which can sit behind previously dispatched obsolete searches in the host's Sequencer. Cancelling the UI token promptly releases the waiting client operation but does not remove backend work. Closing the picker disposes UI/listeners and cancels the waiter, not the search RPC.
- Scaling input: Number of debounce-fired revisions multiplied by eligible hosts, with per-search cost controlled by history size, matching sessions, and cold/unloaded hit hydration. Backlog grows when search service time exceeds input pauses.
- Effective concurrency: Plain Delayer coalesces only edits before its timer fires; it does not throttle a running task. Q debounce-fired revisions can create Q overlapping RPCs on each of H hosts, while the actual request-index work is serial per host. There is no shared per-connection active-RPC slot or latest-query queue.
- Cache behavior: No query cache, negative cache, or in-flight coalescing avoids superseded work. Warm request-index connections do not skip scans, and per-search suppression caches are rebuilt. The outer timeout does not remove pending protocol requests or cancel queued host searches.
- Mechanism confidence: Very high: race helpers do not cancel their input promise, the protocol method accepts no token, Delayer allows overlapping running tasks, and the host explicitly uses one Sequencer.
- Magnitude uncertainty: The exact backlog and delay depend on typing pauses and host performance. No timings are invented; cold archived-history hydration and large substring searches provide realistic slower-than-debounce triggers.
- Expensive boundaries:
  - IPC/network/database/filesystem at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/requestSearch/searchAgentRequestsAction.ts:57-69; src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/requestSearch/agentRequestSearchService.ts:161</code>: Redispatch a full host search while superseded underlying RPCs continue performing the boundary operations described in the single-query scenario; cardinality: Up to Q×H RPCs for Q revisions surviving the debounce. Each host serially processes Q searches even if only the final query can be displayed. Retention lasts until real response or transport cleanup, not merely the caller's timeout.
    - Introduced by diff: true; previous behavior: The base had the endpoint but no production search-as-you-type driver, so editing or abandoning this picker could not enqueue obsolete host searches.; critical-path effect: Obsolete work directly delays the latest search and can consume its 10-second waiting budget before execution completes.
- Verdict: Reported one medium-severity missing-coalescing regression, anchored at the new host RPC dispatch. Bounded correction is one real in-flight RPC per connection plus latest-pending-query replacement.
