### 1. [medium] Back off failed connector-inventory loads before retrying on input

**Finding ID:** `PERF-7E0B666623AF`  
**Location:** <code>src/vs/workbench/contrib/sessions/browser/chat/newChatConnectorRecommendations.ts:180</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** Authentication-provider IPC calls and connector-catalog HTTP GET requests, plus associated request/logging work.  
**Scaling:** For one composer, at most one load is in flight, but the total grows with input/update events after completed failures rather than with account changes or an explicit retry. One matching connector URL suffices; this is not per connector. Multiple composers have independent guards.  
**Outcome:** Excessive background IPC and network traffic while composing a prompt, consuming request-queue capacity and account/server quota.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Typing after a matching connector URL performed local URL matching and tip construction; the recommendation provider made no authentication or catalog requests.  
**Changed behavior:** After an unsuccessful initial catalog load, each subsequent input/layout/inventory event arriving after the prior attempt finishes can initiate another load, with no cooldown or remembered unavailable result.  
**Confidence:** 0.99 — The input listener calls update directly; unknown inventory calls ensureConnectorInventory, whose finally clears its only guard. The service caches only successful refreshes, and the connector request provider explicitly disables transport coalescing and retries. Failure frequency and response duration are unmeasured, but the repeated-call mechanism is explicit.

**Causal diff evidence:** The new update branch at lines 159-161 calls ensureConnectorInventory whenever a URL matches and connectionStateKnown is false; new lines 180-181 call getConnectors and reset \_connectorInventoryLoading after every attempt. Previously recommendation updates never requested connector inventory.

With recommendations enabled, paste a matching URL and continue typing while the initial catalog is unavailable, for example a non-rate-limit HTTP 403 rollout refusal or repeated network failure. The composer repeatedly probes the same unavailable inventory instead of backing off; signed-out inventory also repeats authentication-session IPC.

**Evidence:** newChatConnectorRecommendations.ts:89 subscribes directly to input, :159-161 requests unknown inventory, and :175-185 only guards an active attempt. CopilotConnectorsService.getConnectors (:382-386) uses \_lastRefreshTime, which refresh only sets after a successful document (:407-432); unavailable documents retain connectionStateKnown=false. getAuthentication (:827-855) calls authenticationService.getSessions, forwarded to extension-host $getSessions by mainThreadAuthentication.ts:85-87. LocalConnectorsRequestProvider.execute (:66-80) issues GET /plugins through transport with coalesce:false and retry:false; githubTransport.ts:852-856 throws HTTP failures before caching successful representations. Server quota cooldowns still apply, but do not prevent repeated ordinary 403/network-failure probes.

**Suggested direction:** Remember failed/unavailable inventory attempts and impose a retry cooldown or explicit retry, resetting that state on account/authentication changes. Preserve the existing in-flight guard and successful inventory reuse.

### 2. [medium] Avoid rebuilding marketplace inventory on each input change

**Finding ID:** `PERF-E82530FCD19C`  
**Location:** <code>src/vs/workbench/contrib/sessions/browser/chat/newChatConnectorRecommendations.ts:220</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** UI-thread installation/resource normalization, resource-key serialization, and temporary arrays/objects across all marketplace installations and remembered catalog resources.  
**Scaling:** When no other consumer observes installations, there is one complete snapshot callback per matching nondismissed recommendation per input event. For P provider installations and K remembered catalog resources, its provider normalization can scan P×K pairs, with further installation lookups on matches; knownResources retains up to 1,000 catalog entries. One URL and tens of installed customizations after browsing hundreds of catalog entries are sufficient.  
**Outcome:** Additional synchronous CPU/allocation on the typing path, causing input latency and GC pressure as marketplace inventory grows.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Recommendation input updates matched URLs, selected an ID and constructed a tip without reading or normalizing marketplace installation inventory.  
**Changed behavior:** Every matching, nondismissed recommendation reads the complete installation snapshot during synchronous input processing, even when both inventory and selected recommendation are unchanged.  
**Confidence:** 0.96 — The new synchronous call is reached directly on input events. FromEventObservable.get explicitly bypasses caching without observable subscribers, and getInstallationSnapshot performs both mapping passes before its cached-return expression. Nested provider/catalog scans are visible in findKnownResource. Exact latency depends on inventory/catalog sizes and whether another view retains an observable subscription.

**Causal diff evidence:** New lines 193-194 add isConnectorInstalled to recommendation filtering, and new line 220 reads installations.get() synchronously. Before this PR the input-driven recommendation update did not enumerate marketplace installations; the previously occasional snapshot-building work is now on every input event with a matching URL.

After browsing marketplace entries, close the customization UI and type a prompt containing a recommended URL with no other installations-observable consumer active, such as with Chat Pet disabled. The warm catalog does not avoid the inventory-normalization work on each edit, so unrelated installed skills/plugins can slow connector recommendations.

**Evidence:** newChatConnectorRecommendations.ts:89 invokes update directly on input; :190-195 filters matching recommendations with isConnectorInstalled; :220 calls installations.get(). CustomizationMarketplaceInstallService constructs installations with observableFromEvent at :103. FromEventObservable.get (observableInternal/observables/observableFromEvent.ts:138-149) calls \_getValue on every unobserved get. getInstallationSnapshot (:129-140) maps all records and provider installations before \`return this.installationSnapshot ??= ...\`, so the internal snapshot cache does not skip those passes. Each provider item calls findKnownResource (:220-232), which scans knownResources and performs resource-key/identity comparisons and potentially findProviderInstallation (:277-281). rememberResource bounds knownResources at 1,000 (:203-205), not at the matching connector count.

**Suggested direction:** Observe installations once and update a connector-identity projection only when that snapshot changes, then use that stable projection during input updates. Alternatively, ensure the snapshot callback returns its cached snapshot before performing normalization; do not rebuild unrelated installation metadata per keystroke.

- Effective concurrency: Reconciliation is serial after that operation's failure. Same-key installs share one promise; there is no new catalog-wide/per-source fanout or unbounded retry in this branch.
- Cache behavior: refresh deliberately bypasses the service's 60-second freshness shortcut to obtain authoritative post-authentication state; transport ETags remain usable. Account and authorization conditions are checked before and after the read. The existing per-connector pending map coalesces duplicate install callers.
- Mechanism confidence: High: the new catch branch performs exactly one conditional refresh and preserves its original error when reconciliation cannot establish success.
