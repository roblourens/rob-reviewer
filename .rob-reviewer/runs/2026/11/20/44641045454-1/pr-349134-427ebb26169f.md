# Performance review: Agent host: index sent requests and answer request searches (proposed by opus 5.5)

[PR #349134](https://github.com/microsoft/vscode/pull/349134) at `427ebb26169fc1e7b21e985cd3320f984c05921e`

## Findings (2)

### 1. [medium] Use cursor pagination when skipping suppressed requests

**Finding ID:** `PERF-9E42329E3BE6`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostRequestIndex.ts:179</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Repeated SQLite row visits, substring predicate evaluation and database-page reads.  
**Scaling:** With M matching rows skipped because their sessions are suppressed and page size P = limit + 1, SQL examines prefixes of P, 2P, 3P, etc., producing approximately O(M²/P) qualifying-row visits rather than O(M). Thousands of retained requests from a deleted default chat suffice; the index permits roughly 20,000 retained rows. Suppression checks remain once per distinct session, not once per row.  
**Outcome:** Superlinear CPU and database-read work increases search latency and holds the shared index Sequencer, delaying subsequent searches and queued indexing work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** There was no request-index pagination or repeated substring-query work before this PR. The new search introduces repeated prefix scans, beyond the single bounded table traversal needed for its chosen substring-search semantics.  
**Changed behavior:** The new search pages matching requests with an increasing OFFSET, then filters suppressed sessions outside SQLite. Each additional page reevaluates the substring predicates over the already-skipped prefix.  
**Confidence:** 0.99 — The OFFSET loop, post-query suppression, retained deleted-session rows and index definitions directly establish repeated prefix evaluation. The number of suppressed matching requests and actual duration are workload-dependent, not uncertainties in the mechanism.

**Causal diff evidence:** The added loop at lines 177-180 reruns WHERE instr(folded, ...) ORDER BY started\_at DESC, seq DESC LIMIT ? OFFSET ? with offset incremented by each page's length. Lines 184-190 skip suppressed sessions without advancing a SQL key cursor or removing their rows.

A common-term search after deleting or hiding a long chat can execute hundreds of increasingly expensive page queries even when it ultimately returns no hits. Warm caches do not remove the repeated substring evaluation.

**Evidence:** The only relevant SQL indexes are requests\_by\_time and requests\_by\_chat; neither indexes instr predicates. OFFSET must find and skip preceding qualifying rows again on every statement. Suppression is cached once per distinct session, but this does not cache the SQL prefix scan. Deleted sessions can leave large matching prefixes: RequestIndexContribution removes rows for SessionChatRemoved only, whereas AgentHostStateManager.deleteSession calls removeSession and emits root/sessionRemoved/onDidDeleteSession, not per-chat removal actions (node/agentHostStateManager.ts:2399-2488). The new test also explicitly retains indexed requests while suppressing their session.

**Suggested direction:** Page by the last visited (started\_at, seq) tuple instead of OFFSET, retaining the existing ordering and suppression filtering so each candidate row is visited only once per search.

### 2. [medium] Reuse database references across turn-ID lookups

**Finding ID:** `PERF-D3BFBAA23E13`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostRequestIndex.ts:247</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Filesystem existence probes, SQLite connection opens/closes, journal-configuration statements and schema-version checks.  
**Scaling:** For H cold hits across G storage resources, the implementation performs H stats and, when no other owner holds the databases, H connection initializations rather than G. H defaults to 20 and can reach 50, including 20 or 50 hits from one chat. Truncation can invoke the same helper for hundreds of candidate turns. Operations are awaited serially inside the index-wide Sequencer.  
**Outcome:** Additional serial filesystem/database I/O delays search results and subsequent searches and index operations queued behind them.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, the host had no request-search path performing these storage probes and database opens. The new implementation adds repeated initialization even when multiple hits share one storage resource.  
**Changed behavior:** The new search resolves each nonresident hit's turn ID by separately acquiring and immediately disposing its session-database reference. Truncation uses the same helper for each candidate turn.  
**Confidence:** 0.99 — The serial per-row call chain, unconditional stat, immediate last-reference eviction and connection initialization are directly established by the implementation. The trigger explicitly uses cold, otherwise-unheld databases; only the storage-dependent duration is unmeasured.

**Causal diff evidence:** The added \_eventId calls tryOpenDatabase at line 247 and disposes its reference at line 254. search awaits \_toHit per returned row, which reaches \_exposedTurnId/\_eventId for cold chats; truncateChat also awaits \_eventId inside its row loop.

After restarting the host, searching for a term occurring repeatedly in one historical chat can reopen the same session.db 20 times for the default result limit, or 50 times at the maximum. Repeating the search repeats the opens despite warm OS caches; slow or redirected user-data storage magnifies the latency.

**Evidence:** SessionDataService.tryOpenDatabase (node/sessionDataService.ts:132-146) performs a filesystem stat on every call. Its ReferenceCollection destroys the object as soon as the last reference is disposed (base/common/lifecycle.ts:704-708), and SessionDatabaseCollection destroys it by calling dispose. Thus, for an unheld cold database, successive hits each create a fresh SessionDatabase. SessionDatabase.\_ensureDb (node/sessionDatabase.ts:684-703) repeats mkdir, SQLite open, journal configuration and migration-version checks before getTurnEventId. There is no operation-scoped reference reuse in this index.

**Suggested direction:** Keep an operation-scoped map of storage resources to database references (including missing-database results), reuse each reference for all mappings in that search or truncation, and dispose the references in a finally block after the operation.

### Scenario 4: Search after deleting or hiding chats' owning sessions

- Critical path: The search must page through suppressed matching requests before it can return enough visible hits or determine there are none. Each page finishes before the next page starts.
- Scaling input: Thousands of matching retained requests in deleted or hidden sessions, potentially most of the roughly 20,000-row index. Permanent session deletion does not dispatch the per-chat removal action handled by the contribution.
- Effective concurrency: The query-page loop, suppression lookups and all other index operations are globally serialized. No per-row subprocesses or external network requests occur.
- Cache behavior: The connection and OS pages can be warm, and the per-search suppression map prevents duplicate host-database checks. Neither caches the instr predicate evaluation or OFFSET prefix traversal.
- Mechanism confidence: Very high: OFFSET progression, post-query suppression, indexes and session-deletion notification behavior establish the quadratic-prefix mechanism.
- Magnitude uncertainty: The number of retained suppressed matches and average request text size are unknown; both control magnitude rather than mechanism validity.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostRequestIndex.ts:search lines 177-190; node/agentHostDatabase.ts:isSessionSuppressed</code>: Rerun the substring query with increasing OFFSET and check owning-session suppression.; cardinality: For M suppressed matching rows and P = limit + 1, approximately M/P result-page statements repeatedly scan qualifying prefixes, giving O(M²/P) qualifying-row visits. Suppression SELECTs are correctly cached once per distinct session, and suppressed rows never reach session-database ID mapping.
    - Introduced by diff: true; previous behavior: No request-search pagination or repeated prefix evaluation existed.; critical-path effect: Repeated scans block this search and occupy the shared index Sequencer until enough visible hits are found or matches end.
- Verdict: Reported OFFSET-driven repeated work. Keyset pagination using the existing time/sequence ordering preserves behavior while avoiding prefix rescans.

### Scenario 5: Client truncation, chat removal/move and renaming

- Critical path: Contribution hooks enqueue index maintenance without awaiting it, so index maintenance does not directly block the provider operation. Searches and other index work arriving afterward wait for the maintenance to finish.
- Scaling input: K retained turns in the affected chat and distance from the newest indexed turn to the kept turn; the retained request-table cap bounds K.
- Effective concurrency: All maintenance runs through the same global Sequencer. Per-candidate ID mapping is awaited serially; moves/removals do not spawn concurrent boundary fan-out.
- Cache behavior: No operation-scoped mapping-reference or negative-result reuse. Existing turn/session databases are reused only while another owner holds them. Server-origin truncations are correctly excluded from index truncation.
- Mechanism confidence: High: action-origin gating, SQL operations and per-row helper calls are explicit.
- Magnitude uncertainty: Typical truncation depth and concurrent database ownership are unknown.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostRequestIndex.ts:truncateChat, removeChat, moveChat, setTitle</code>: Read candidate turn positions, delete truncated/removed request rows, update ownership or upsert a title.; cardinality: Clear-all truncation is one DELETE. Point truncation reads K indexed turns for that chat and examines candidates newest-first. Removal is two DELETEs; move and title change are one UPDATE/upsert each.
    - Introduced by diff: true; previous behavior: These lifecycle actions did not maintain a request index.; critical-path effect: Off the initiating action's synchronous critical path, but occupies the index queue before following searches.
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostRequestIndex.ts:truncateChat, \_eventId; node/sessionDataService.ts:tryOpenDatabase</code>: Probe and acquire the chat's session database while comparing restored event IDs.; cardinality: One \_eventId call per examined candidate whose original ID does not equal the kept ID, potentially hundreds of candidates from the same chat.     - Introduced by diff: true; previous behavior: Truncation had no additional request-index mapping loop or its storage probes.; critical-path effect: Serially awaited within truncation's index task and delays subsequent searches; not awaited by the contribution caller.
- Verdict: The per-candidate database-lifecycle cost is included in the shared reference-reuse finding, not duplicated. No separate performance regression found in moves, normal removals or renaming.

### Scenario 6: Disable request search and dispose the host index

- Critical path: The configuration hook queues close/delete after earlier index operations; callers do not synchronously await it. Disabled searches return an empty disabled result without opening the database. Disposal queues close and prevents subsequent opens.
- Scaling input: Configuration-change frequency and the lifetime of the index; deletion cardinality is constant per notification.
- Effective concurrency: Queue ordering serializes close/delete with index tasks; only the four sidecar-removal calls use Promise.all.
- Cache behavior: Close clears the cached database promise. Re-enabling creates a fresh index lazily. Disabled writes are rejected before opening or queueing database work.
- Mechanism confidence: High: configuration listener, disabled guards and serialized cleanup are explicit.
- Magnitude uncertainty: Configuration changes are low-frequency; cleanup duration depends on prior queued work and storage.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostRequestIndex.ts:\_deleteIndex, \_close, dispose</code>: Close the existing request-index connection after queued work.; cardinality: One close for an existing connection; subsequent queued closes encounter no connection.
    - Introduced by diff: true; previous behavior: No request-index connection needed closing.; critical-path effect: Runs after the index queue drains and outside turn dispatch; earlier long searches can delay cleanup.
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostRequestIndex.ts:\_deleteIndex</code>: Remove the database and WAL/SHM/rollback-journal sidecars.; cardinality: Four concurrent force-removal calls per queued deletion for a file-backed index; none for an in-memory index. While disabled, further root-config change notifications can queue another deletion.
    - Introduced by diff: true; previous behavior: No request-index files or associated removal operations existed.; critical-path effect: Asynchronous configuration cleanup, not blocking chat progress. Subsequent enabled index work is ordered behind it.
- Verdict: No separate high-confidence performance regression: cleanup ownership is explicit and boundary cardinality is constant. Earlier reported search costs can delay cleanup but are not duplicated as lifecycle findings.
