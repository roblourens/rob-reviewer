### Scenario 1: Open a session link in the Agents main window, including side-by-side chats.

- Critical path: Session lookup, optional default-chat resolution, and the existing openChat/openChatToSide/openSessionToSide operation complete before reveal starts. A ready request is focused and revealed synchronously once; otherwise the reveal runs without awaiting its polling promise.
- Scaling input: One linked chat per activation; session lookup scales with known sessions, and reveal lookup scales with visible transcript items H. Unsuccessful reveal checks run every 100 ms for at most 15 seconds.
- Effective concurrency: One pending reveal per in-window opener, replaced on subsequent opens; generation checks suppress older completed opens. Existing session/model resolution remains coalesced by resource. Poll callbacks are synchronous and do not spawn concurrent boundary operations.
- Cache behavior: getWidgetBySessionResource scans registered widgets in memory. ChatViewModel.getItems caches its computed visible array until a model change; polling does not restore history, list sessions, or copy that array on each tick. Links without a turn allocate no reveal timer.
- Mechanism confidence: High: traced routing, default-chat fallback, model-load coalescing, visible-item caching, and list focus/reveal implementations.
- Magnitude uncertainty: Transcript lengths and restoration durations are unmeasured; the repeated work is a bounded in-memory search rather than boundary fan-out.
- Expensive boundaries:
  - IPC/network at <code>src/vs/platform/agentHost/common/agentHostConnectionsService.ts:isDefaultChatLinkId</code>: Read the cached session subscription, falling back to connection.listSessions to identify the default chat.; cardinality: Zero listing calls with a session subscription or without an explicit chat ID; otherwise one listing call per resolution.
    - Introduced by diff: false; previous behavior: The same resolveLinkedChat call and cache/listing fallback already ran before this PR.; critical-path effect: Awaited before opening the chat.
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:provideChatSessionContent</code>: Restore an uncached chat using hydrated session/chat subscriptions and history conversion.; cardinality: One provider content resolution per uncached chat, coalesced by resource in ChatService and ChatSessionsService; cached models avoid resolution. Existing history enrichment remains unchanged.
    - Introduced by diff: false; previous behavior: Opening the same chat already restored its model and history through these services.; critical-path effect: Existing restoration must make the transcript available before a request can be revealed.
  - other at <code>src/vs/workbench/contrib/chat/browser/widget/chatRequestReveal.ts:tryReveal</code>: Focus the matched transcript item and reveal it through the virtualized list.; cardinality: One successful focus/reveal per link with a rendered matching request; failed hasElement checks do not focus or reveal.
    - Introduced by diff: true; previous behavior: Links opened the chat without request-specific focus or scroll.; critical-path effect: The immediate attempt runs synchronously after opening; later attempts run on interval callbacks.
- Verdict: No reportable regression. Added request navigation is demand-driven and bounded, with no increase in existing restore or listing call cardinality.

### Scenario 2: Activate a session link from an auxiliary chat window.

- Critical path: Existing chat-window resolution and open/reveal complete first. The new helper then finds the widget and reveals its request; asynchronous waiting is not awaited by the opener.
- Scaling input: One destination chat per activation, registered widget count W, and destination transcript item count H.
- Effective concurrency: Existing chat-window single-flight and per-chat queue remain intact. Reveal is limited to one pending operation for this opener and stops on success, replacement, cancellation, another focused widget, or timeout.
- Cache behavior: The window service reuses chats by URI; SessionsChatWindowContent also reuses resolved chat entries. The new widget and transcript searches are in-memory and use the view-model visible-items cache.
- Mechanism confidence: High: inspected window-service grouping, provider chat reuse, model coalescing, and the reveal helper.

### Scenario 3: Open an agent-session turn link in the editor window's Chat view or chat editor.

- Critical path: Existing client identity resolution, default-chat normalization, provider activation, and openSession complete before reveal. A ready transcript is revealed once; polling does not extend the awaited open operation by the timeout duration.
- Scaling input: One session/chat per link; a cold identity refresh handles the selected authority's session listing, while request lookup scans H visible transcript items.
- Effective concurrency: One pending reveal for this contribution; a generation counter prevents an older open from installing a reveal after a newer open. Model and content resolutions remain shared by resource; distinct existing opens are not newly globally serialized or fanned out.
- Cache behavior: Identity cache and per-authority refresh sharing are unchanged. Existing widget/model/content caches remain effective. getItems returns its cached visible array between changes.
- Mechanism confidence: High: both pre/post branches perform the same single openSession and unchanged identity/default-chat resolution.
- Magnitude uncertainty: No timings were measured. The immediate new work is an in-memory lookup and one requested focus/scroll, not another host listing or content request.

  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/openSessionLinkOpener.contribution.ts:\_withoutDefaultChatFragment</code>: Use the subscription cache or listSessions fallback to normalize an explicit default-chat ID.; cardinality: Zero listing calls with a hydrated session or no fragment; otherwise one fallback call. ### Scenario 4: Follow a turn link delivered by the OS to the Agents window, including cold startup and a disconnected provider.

- Critical path: Existing LifecyclePhase.Restored readiness, session availability, optional provider connection, default-chat resolution, and chat opening must complete. Reveal is installed afterward without awaiting its promise.
- Scaling input: One linked session and chat per handoff. Existing session availability checks react to provider/resolution events; new reveal checks only the destination widget/transcript.
- Effective concurrency: The handoff's cancellation token rejects superseded completions; its MutableDisposable retains one reveal. In-app and OS routing have separate owners, so the Agents window can have one reveal from each, not unbounded reveals per link. Both are time-bounded.
- Cache behavior: Known sessions and connected providers bypass their existing waits/connect step. Default-chat subscription and chat-model caches retain their behavior. The new reveal never forces a reconnect or history reload on a missing request.
- Mechanism confidence: High: inspected the IPC handler, cancellation ownership, session-availability wait, connection branch, and new reveal placement.
- Magnitude uncertainty: Cold provider connection/history duration is environment-dependent but unchanged; the diff introduces no new startup-wide fan-out.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/chat/electron-browser/chat.contribution.ts:handleSelectAgentsFolder</code>: Receive the vscode:selectAgentsFolder handoff.; cardinality: One IPC event per external open intent.
    - Introduced by diff: false; previous behavior: The same handler received and processed the external session link.; critical-path effect: Starts the workflow; no new IPC is issued by reveal polling.
  - IPC/network at <code>src/vs/sessions/contrib/chat/electron-browser/chat.contribution.ts:resolveAndOpenSessionLink</code>: Optionally connect the session's provider, resolve its default chat, and restore/open the destination through the existing services.; cardinality: At most one explicit provider.connect invocation when disconnected, one default-chat listing fallback when required, and the existing resource-coalesced content load for the target chat.
    - Introduced by diff: false; previous behavior: Connection, resolution, and opening occurred in the same order before the PR.; critical-path effect: These existing operations precede reveal and can dominate cold startup latency.
- Verdict: No high-confidence performance regression. The extra 15-second deadline is not an awaited startup delay.

### Scenario 5: A linked request is missing, history renders late, or a later open/focus change supersedes the reveal.

- Critical path: There is no awaited 15-second delay in the callers. Interval callbacks perform in-memory searches until success, cancellation, another focused chat, or timeout.
- Scaling input: Approximately 150 retry opportunities at most per pending reveal, each scanning up to W widgets and H visible transcript items. A present item not yet in the list receives only a guarded hasElement check; a successful focus/reveal terminates retries.
- Effective concurrency: One timer and deadline per pending reveal owner. DisposableStore disposes the interval, timeout, cancellation subscription, and focus subscription on finish. Replacement/disposal cancels the previous owner; generation checks prevent accumulating stale reveals.
- Cache behavior: Visible-item computation is cached until a model change; unsuccessful polling does not invalidate it or allocate a new history/model. There is no negative-result cache, but retries have a fixed deadline and do not cross host boundaries.
- Mechanism confidence: High for bounded retry count, cache behavior, and cleanup: inspected ChatViewModel.getItems, ChatWidget.focus, ChatListWidget.focusItem, IntervalTimer disposal, and cancellation-token ownership.
- Magnitude uncertainty: Very large transcripts increase total scan work, but static evidence does not establish a meaningful degradation from this bounded, cached-array search. No unbounded retained collection or expensive per-poll operation was found.
- Expensive boundaries:
  - other at <code>src/vs/sessions/contrib/chat/browser/chatLinkRouting.ts:revealLinkedTurn; src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/openSessionLinkOpener.contribution.ts:\_open</code>: Emit a trace diagnostic after an uncancelled unsuccessful reveal.; cardinality: At most one diagnostic per timed-out reveal, conditional on the logging sink's trace handling; not one per poll or transcript item.
    - Introduced by diff: true; previous behavior: No request-specific timeout diagnostic existed.; critical-path effect: Runs after the asynchronous wait settles, not as a prerequisite to opening the chat.
- Verdict: No actionable high-confidence performance regression. Missing-turn handling adds bounded local work, not repeated restore/I/O or lifetime-growing retention.
