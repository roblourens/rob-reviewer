# Performance review: Engineering - cache the Chromium build scripts so the Linux jobs don't depend on GitHub's rate limits

[PR #348980](https://github.com/microsoft/vscode/pull/348980) at `373429aee97b99d6c4a1180e25d183c6f4b747cb`

## Findings (1)

### 1. [medium] Skip blocking cache warm-up in jobs that consume neither script

**Finding ID:** `PERF-7031E5D0CAA7`  
**Location:** <code>build/azure-pipelines/linux/steps/product-build-linux-setup.yml:154</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Synchronous curl subprocesses and HTTP requests for two unused scripts.  
**Scaling:** Per cache-missing non-consumer job: two requests if first sources succeed; four sequential requests if the first script exhausts its sources, then prefetch aborts. Each request allows 120 seconds. Jobs do not coalesce this work.  
**Outcome:** Unnecessary network waits block compilation and delay dependent jobs, potentially by minutes with stalled sources.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** ARM64 Compile made zero Chromium-script requests: update.py was x64-only, and VSCODE\_BUILD\_ONLY:true excluded Debian preparation and its dpkg-shlibdeps.pl download.  
**Changed behavior:** Common Linux setup now warms both Chromium scripts synchronously on cache misses, including jobs that use neither script.  
**Confidence:** 0.97 — ARM64 setup excludes the x64-only script download; Compile sets VSCODE\_BUILD\_ONLY:true and excludes Debian packaging. The new unconditional template and synchronous prefetch/curl implementation prove the added critical-path work. Response times are unmeasured.

**Causal diff evidence:** The new inclusion at product-build-linux-setup.yml:154 reaches restore-chromium-build-files.yml:14 on every cache-missing ARM64 Compile job, adding synchronous downloads where that job previously made none.

Cold-cache ARM64 compilation and dependent signing/test jobs now wait on potentially slow Chromium sources despite needing neither downloaded script.

**Evidence:** product-build-linux.yml:60-66 sets VSCODE\_BUILD\_ONLY:true; product-build-linux-compile.yml excludes package preparation in this mode. setup-env.sh:40-45 downloads update.py only for x64. The newly included template runs prefetchChromiumBuildFiles, whose loop synchronously fetches both scripts (chromiumSource.ts:139-141). With GITHUB\_TOKEN there are four sequential sources, using spawnSync curl with --max-time 120. A failing first script can consume eight minutes of configured request time before this otherwise independent compile proceeds. continueOnError does not avoid waiting.

**Suggested direction:** Skip this restore/prefetch template for jobs consuming neither script, such as ARM64 Compile; warm the complete cache from consumer/producer jobs instead.

### Scenario 5: Non-pipeline download and invalid or unreadable cache fallback

- Critical path: A caller synchronously obtains a demanded script before executing it or generating dependencies.
- Scaling input: Only the demanded file per invocation; Debian still memoizes one acquisition per process. Cache contents are two fixed scripts per prefetched version, and CI jobs use separate workspaces.
- Effective concurrency: All operations are synchronous per caller; no new background workers, retained listeners, growing in-memory cache, or cross-call queue.
- Cache behavior: Ordinary downloads never populate the cache. Missing, unreadable, invalid, wrong-version, or hash-mismatched entries fall back to the original network retry behavior. A hit reads content/hash and validates SHA-256. Prefetch catches failures and writes only after all fetches succeed; write failure attempts cache cleanup.
- Mechanism confidence: High for bounded cache reads, unchanged miss retries, no ordinary-download cache writes, and buffer lifetime.
- Magnitude uncertainty: Local prefetch usage and file sizes were not profiled; no evidence of a hot unbounded local workload.
