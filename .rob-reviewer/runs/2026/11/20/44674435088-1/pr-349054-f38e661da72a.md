## Performance regression fixes detected (1)

### 1. synchronous-ui-work

**Fix location:** `src/vs/editor/contrib/hover/browser/markdownHoverParticipant.ts:363` (`LEFT`)  
**Blamed base line:** `src/vs/editor/contrib/hover/browser/markdownHoverParticipant.ts:363`  
**Introducing path:** `src/vs/editor/contrib/hover/browser/markdownHoverParticipant.ts`  
**Introducing commit:** `8961ff9f680d04110cc19e62384ba1f72554bc41`  
**Mechanism family:** `synchronous-ui-work`  
**Performance category:** `layout`  
**Confidence:** 0.95

**Mechanism:** Uncoalesced synchronous hover scroll handling performs O(P) part traversal and 2V layout-dependent reads plus V positional style writes per update, where V is the number of rendered provider rows offering verbosity controls and P is the number of markdown parts. Writes for one row precede geometry reads for the next, introducing forced style/layout synchronization on the UI thread.

**Symptom:** Statically evidenced extra main-thread layout synchronization and JavaScript work while wheel/keyboard scrolling overflowing hovers, with potential scroll jank that grows with event frequency and verbosity-enabled provider rows. No measured timing or user-reported performance symptom is asserted.

**Fixed behavior:** CSS flex-end and position: sticky; bottom: 0 replace the JavaScript scroll callback, eliminating the per-scroll full-part traversal, two synchronous geometry reads per verbosity-enabled row, and corresponding style.top writes without adding provider calls or rebuilding DOM.

**Evidence:** The deleted MarkdownRenderedHoverParts.handleScroll iterated all rendered markdown parts on every hover scrollbar event. For each part with verbosity actions it read hoverElement.offsetTop and clientHeight (base lines 362–363), then wrote actionsContainerInner.style.top (base line 372). The base diff also shows the synchronous forwarding chain DomScrollableElement.onScroll -&gt; ContentHoverWidget.\_onDidScroll -&gt; ContentHoverWidgetWrapper -&gt; MarkdownHoverParticipant.handleScroll. DomScrollableElement sets native scrollTop before later subscribers run (scrollableElement.ts:739–745), and does not smooth/coalesce mouse-wheel updates (727–732). Thus an overflowing TypeScript hover with verbosity controls ran geometry reads and positional writes on every scroll update; multiple eligible provider rows interleaved reads and writes. This PR deletes that callback chain and uses CSS sticky positioning instead (hover.css:96–97). Blame resolves the removed clientHeight read to commit 8961ff9f680d04110cc19e62384ba1f72554bc41.
