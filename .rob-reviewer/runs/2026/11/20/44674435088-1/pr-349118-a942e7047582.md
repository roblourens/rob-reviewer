### Scenario 1: Connect/reconnect to a remote agent host and mirror Computer Use settings, including opt-in/opt-out changes.

- Critical path: Existing initialization sends the root-configuration patch without awaiting persistence. A setting change can request a runtime restart, but active turns and subagents finish first. Host-side configuration processing remains synchronous; disk persistence is queued off the immediate path.
- Scaling input: Number of connected protocol clients/hosts and actual global-setting changes. Connect patches contain one additional boolean, not one operation per chat or setting. Existing root-config observers inspect registered sessions/chats.
- Effective concurrency: One combined configuration dispatch per client on connect; one patch for affected settings per change. Filesystem writes use the existing per-service promise chain. There is no new per-item dispatch loop.
- Cache behavior: Configuration values come from the existing configuration model. Repeated equal values do not restart the runtime because CopilotAgentStartupConfig.equals rejects unchanged configurations. Workspace/folder/memory-only changes are not mirrored.
- Mechanism confidence: High: traced registration scope through sync target filtering, protocol patch batching, host persistence, startup-config equality, and deferred restart ownership.
- Magnitude uncertainty: Host/session counts and storage latency are not measured. The added connect payload is constant-sized; additional standalone actions require actual global-setting changes.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:\_forwardClientConfig, configuration-change listener, \_dispatchRootConfig</code>: Send RootConfigChanged over the existing agent-host protocol transport.; cardinality: Connect/reconnect uses the same single combined patch as before, with one extra boolean for remote targets. A Computer Use setting change now contributes one patch per connected remote protocol client.
    - Introduced by diff: true; previous behavior: Remote connect patches omitted Computer Use; changes to that setting did not themselves produce a remote patch. Local mirroring was already present.; critical-path effect: Dispatch is not awaited by \_forwardClientConfig. Host processing can request a deferred restart only when the effective startup configuration changes.
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts:14132; src/vs/platform/agentHost/node/agentConfigurationService.ts:persistRootConfig</code>: Serialize existing root configuration and queue mkdir, temporary-file write, and atomic rename.; cardinality: Same write sequence per existing connect patch; one new sequence per forwarded remote Computer Use setting-change patch.     - Introduced by diff: true; previous behavior: Connect patches already persisted root configuration. A remote Computer Use setting change was not forwarded and therefore did not independently schedule this persistence.; critical-path effect: JSON serialization happens while scheduling persistence, but asynchronous filesystem operations are queued and not awaited by action dispatch.
- Verdict: No reportable regression. Remote mirroring adds bounded work required by the feature, preserves batching, and does not turn connection synchronization into collection-sized boundary fan-out.

### Scenario 2: Start ordinary remote Copilot chats or list migratable chats with Computer Use enabled, on cold and warm plugin caches.

- Critical path: Shared runtime startup awaits one supported-platform sentinel probe alongside other startup assets. A missing plugin downloads in the background, so slow or failed downloads do not gate ordinary chats. Installation causes one shared-runtime restart at an idle point; if installation lands during startup, the start can repeat once before returning the client.
- Scaling input: Distinct enabled agent-host processes and the pinned platform/version archive, not the number of historical or active chats. Archive byte size and entry count control one installation's work.
- Effective concurrency: \_clientStarting coalesces shared-runtime starts. \_computerUseDownload permits one in-flight installation per CopilotAgent; different hosts operate independently. Startup assets use Promise.all. ZIP extraction uses lazy entries and a throttler, not an unzip subprocess. Disable/disposal cancels the pending download.
- Cache behavior: Persistent cache key is userDataPath/agent-host/computer-use-plugin/release.version/platform-arch with a .complete sentinel. Warm starts probe it and do not download or extract. Unsupported platforms return before filesystem/download work. Failed installs leave no complete sentinel; a later runtime start can retry, but every ordinary chat does not trigger a fresh start.
- Mechanism confidence: High: production code and neighboring tests establish persistent cache reuse, one download per agent, background resolution, one-time startup retry, and restart deferral/cancellation.
- Magnitude uncertainty: Pinned release sizes, download bandwidth, and restart duration were not measured. SDK-internal plugin loading is external to the inspected repository. Independent host count determines aggregate background downloads.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_resolveComputerUsePlugin; src/vs/platform/agentHost/node/copilot/copilotComputerUsePlugin.ts:getInstalledPath</code>: Probe the pinned plugin directory's .complete sentinel.; cardinality: One probe per supported enabled shared-runtime start; cold download resolution performs another probe. Calls are shared across chats through the shared client lifecycle.
    - Introduced by diff: true; previous behavior: Remote shared-runtime startup skipped Computer Use resolution entirely; local enabled startup already used this exact path.; critical-path effect: The initial asynchronous probe is on startup's Promise.all path; archive download is not.
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotComputerUsePlugin.ts:resolve</code>: GET the pinned GitHub release ZIP and buffer/verify its SHA-256.; cardinality: One download per cold enabled supported host installation, coalesced per agent. Zero on warm caches; failed attempts retry only when plugin resolution runs on a later runtime start.
    - Introduced by diff: true; previous behavior: Remote hosts did not offer or download the plugin. Local enabled hosts already downloaded it in the background.; critical-path effect: Runs in the background. Does not block ordinary chat startup on network completion.
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotComputerUsePlugin.ts:installComputerUsePluginArchive; src/vs/base/node/zip.ts:extract</code>: Stage the ZIP, extract its platform subtree, write the sentinel, atomically publish the directory, and remove staging files.; cardinality: Once per successful cold installation, with file operations proportional to entries in the pinned archive. No extraction on warm starts and no external extraction process.
    - Introduced by diff: true; previous behavior: This installation path existed for local enabled hosts but was unreachable from remote Computer Use registration.; critical-path effect: Background installation precedes plugin availability but not ordinary chats. The ZIP buffer and checksum work temporarily consume host memory/CPU.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_ensureClient, \_downloadComputerUsePlugin, \_requestClientRestart, \_stopClient</code>: Start the existing Copilot runtime and optionally stop/start it once to register a newly installed plugin.; cardinality: One shared runtime per ordinary host; a cold install can cause one extra start, not a restart per chat. A real setting transition can also request a restart, with reasons coalesced.
    - Introduced by diff: true; previous behavior: Remote hosts started the same runtime without the plugin and without an installation-triggered restart. The same bounded restart logic already served local enabled hosts.; critical-path effect: Normal startup is already required. An installation completed during startup can add one bounded restart to that startup; otherwise restart waits for all in-flight work to become idle.
- Verdict: No high-confidence regression. The remote feature deliberately enables one cached installation per host, preserves nonblocking downloads and coalescing, and introduces no per-chat installation or unbounded restart loop.

### Scenario 3: Launch a remote chat, show Computer Use activation consent, and enable the plugin after approval.

- Critical path: Non-ephemeral, non-scoped chat launch awaits the existing Computer Use tool-state check concurrently with other session preparations. Activation checks plugin state, waits for the user's answer, enables it, and confirms state before returning tools to the agent.
- Scaling input: Actual non-ephemeral chat launches and activation attempts; plugin-list payload scales with the runtime's installed plugin catalog. Historical chat restoration text processing does not itself invoke activation RPCs.
- Effective concurrency: Launch preparations use Promise.all. Activation has ordered precheck, user decision, enable, and postcheck; overlapping activation calls in the same chat share one promise and card. Distinct chats are independent and use the shared runtime.
- Cache behavior: Plugin state is read from the authoritative runtime, not a new shadow cache. \_asking coalesces concurrent activation attempts within one chat. Decline is retained for that chat; subsequent calls may still check plugin state. No additional cache or retained catalog is introduced by the diff.
- Mechanism confidence: High confidence in call counts, gating, launch reachability, and per-chat activation coalescing. Insufficient evidence of a new pathological SDK-internal cost.
- Magnitude uncertainty: Runtime plugin-list implementation and latency are external; this repository establishes bounded RPC counts but does not establish an independently costly repeated catalog rebuild or remote client-host roundtrip per plugin.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:11198; src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:2567; src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:1607</code>: client.rpc.plugins.list to obtain runtime plugin state for activation-tool creation.; cardinality: One list RPC per eligible chat launch while the setting is true; ephemeral and scoped-credential chats skip it. No per-plugin RPC fan-out.
    - Introduced by diff: true; previous behavior: Normally remote hosts never received the mirrored opt-in, so the existing setting check skipped this RPC. If a remote root config already explicitly enabled Computer Use, this unchanged RPC path could already run despite the previous registration gate.; critical-path effect: Included in concurrent session-preparation work before launch can proceed.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotComputerUseActivationTool.ts:\_ask; src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:2568</code>: List plugins before activation, enable the single computer-use plugin after consent, and list again to confirm.; cardinality: Accepted activation uses two list RPCs plus one enable RPC. Concurrent attempts within one chat share the same sequence; declines do not invoke enable/postcheck.
    - Introduced by diff: true; previous behavior: Remote hosts did not register the built-in plugin, so successful activation was unavailable. The same bounded sequence already existed for local activation.; critical-path effect: Activation completion awaits these ordered operations; waiting for explicit consent is intentional.
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotComputerUseActivationTool.ts:createActivationRequest; src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_computerUseActivation</code>: Send the existing chat-input request and receive the consent response through the agent-host protocol.; cardinality: One card per coalesced activation attempt. Changed descriptions add only a fixed-length explanatory suffix.
    - Introduced by diff: true; previous behavior: The same card transport and response mechanism existed locally; remote sessions could not activate an unregistered built-in. The text change does not add a new rendering or serialization loop.; critical-path effect: User approval gates enabling the plugin, not unrelated chat initialization.
- Verdict: No reportable regression. The added remote workflow reuses bounded state/activation RPCs required for consent, and the explanatory text does not independently increase expensive work or retention.

### Scenario 4: Keep native macOS permission setup local while remote Computer Use uses the plugin's ordinary prompts.

- Critical path: The changed guard prevents remote hosts from constructing CopilotComputerUsePermissionSetup. Local setup continues to be created only for enabled local macOS hosts; helper icon reading and setup dialogs remain in their existing setup lifecycle.
- Scaling input: At most one permission-setup owner per local enabled macOS agent, shared across chats. Remote hosts create zero such owners regardless of chat count.
- Effective concurrency: Singleton ownership per local agent. Remote hosts skip construction entirely; local setup behavior and cleanup are unchanged.
- Cache behavior: MutableDisposable retains the single local setup instance while enabled and clears it when disabled. No new remote icon/status cache or remote polling state is allocated.
- Mechanism confidence: High: traced explicit host/platform guard, singleton disposal ownership, setup callback, and client service's local-platform/status gating.
- Magnitude uncertainty: External plugin-native permission prompts were not inspected end to end. No repository evidence shows new client-side desktop probing, layout work, or retained setup resources.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_updateComputerUsePermissionSetup; src/vs/platform/agentHost/node/copilot/copilotComputerUsePlugin.ts:readMacAppIcon</code>: Read the local macOS helper Info.plist and icon when the local permission setup requests them.; cardinality: Existing local setup reads only; zero such reads from remote setup after the diff.
    - Introduced by diff: false; previous behavior: The previous local-only registration gate also prevented remote setup creation. The new explicit local guard preserves that exclusion while enabling remote plugin registration.; critical-path effect: Only the local permission-setup workflow owns these reads, not remote ordinary-chat startup.
- Verdict: No regression and no concrete old regression fix to record: the added guard preserves the prior local-only setup lifecycle rather than removing previously reachable expensive work.
