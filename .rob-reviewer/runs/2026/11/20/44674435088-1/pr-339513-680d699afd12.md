## Findings (2)

### 1. [high] Allow bounded pipelining instead of globally awaiting each publish ack

**Finding ID:** `PERF-314A8DE7263A`  
**Location:** <code>src/vs/platform/agentHost/node/missionControl/missionControlProtocolServer.ts:290</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Web PubSub publication slots and sequential network acknowledgement waits shared by all lanes and mirror namespaces.  
**Scaling:** For Q frames ahead of a response and acknowledgement interval R, send latency grows approximately Q×R rather than allowing a bounded batch in flight. Q is the admitted FIFO backlog, not the entire retained history; mirror admission caps it at 128 frames before byte limits, and chunking increases frame count for larger payloads.  
**Outcome:** Head-of-line blocking of interactive remote responses and reduced aggregate relay throughput during streaming or replay.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Native sessions delivered through the existing local IPC/WebSocket handlers without this service-acknowledgement gate or shared mirror backlog. The existing Web PubSub client transport also writes all message fragments in order while tracking acknowledgements independently.  
**Changed behavior:** The new native Mission Control publisher shares one outbound FIFO across interactive lane messages and historical/live mirror events, and allows only one publication awaiting a Web PubSub acknowledgement.  
**Confidence:** 0.99 — The pending-set gate, shared FIFO, acknowledgement-driven drain, per-action mirror admission, and explicit serialization/backlog tests establish the mechanism and realistic trigger. Actual service RTT and workload prevalence are not measured; the latency relationship follows statically from the code.

**Causal diff evidence:** The added condition \`while (this.\_pending.size === 0 && this.\_outbound.length &gt; 0)\` at line 290 stops after \`\_pending.add(next.ackId)\` and resumes only when acknowledgement handling deletes that ID. Added \`\_publish()\` and \`publishMirrorEvent()\` both append to this same \`\_outbound\` queue.

After reconnect/backfill, or while native sessions stream actions, an initialize/file/dispatch response behind Q already-admitted frames cannot even be sent until those Q acknowledgements arrive. With 128 queued small mirror frames this creates roughly 128 sequential service-acknowledgement waits; additional client lanes share the same bottleneck. This delays remote attachment and interaction and limits aggregate streaming throughput to one frame per acknowledgement interval.

**Evidence:** MissionControlHost.\_createMirror forwards each authoritative action to mirror.enqueue, including individual SDK ChatDelta emissions (copilotAgentSession.ts:2574–2604). MissionControlProtocolServer.\_enqueue uses a single FIFO; \_drain adds the acknowledgement before socket.send; \_receive at lines 339–364 removes it and drains again. Mirror admission permits 128 queued frames/16 MiB, and the whole FIFO permits 512 frames/64 MiB. The new tests explicitly expect only one of two responses before an acknowledgement, and exercise 600-frame historical backlogs with an initialize reply queued during the backlog. In contrast, webPubSubRelayTransport.ts:473–482 sends every fragment without awaiting prior acknowledgements.

**Suggested direction:** Keep bounded backpressure and required per-lane ordering, but permit a bounded in-flight publication window with acknowledgement tracking rather than global stop-and-wait; ensure bulk mirror/replay traffic cannot monopolize interactive response delivery.

### 2. [medium] Perform relay path canonicalization off the host event loop

**Finding ID:** `PERF-27590B222ED3`  
**Location:** <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:2295</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous filesystem realpath, lstat, and stat operations on the shared Agent Host event loop.  
**Scaling:** For F file requests, an existing target costs F target canonicalizations plus the sum of roots visited before each match; absent targets add ancestor checks. Cold and warm requests both repeat these calls. Root cardinality is explicit grants plus loaded/resident workspace/content entries, with early exit and the normal 10-session residency target accounted for.  
**Outcome:** Event-loop stalls and serialized metadata I/O causing slower file browsing and interference with local and remote agent activity on slow filesystems.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The existing native resource handlers used asynchronous file-service operations; there was no relay-specific synchronous realpath/stat authorization loop running ahead of dispatch in the shared Agent Host process.  
**Changed behavior:** Relay resource requests now synchronously canonicalize the requested file or its existing ancestors, then synchronously canonicalize each grant visited before a match, before dispatching the existing asynchronous operation.  
**Confidence:** 0.96 — The synchronous pre-dispatch guard, filesystem calls, non-deduplicated root construction, asynchronous underlying read, and shared-process ownership are directly traced. Exact mount latency and frequency of later-root matches are uncertain, so severity is medium; no benchmark duration is assumed.

**Causal diff evidence:** The added \`relative(realpathSync(root), canonical)\` at line 2295 is inside a per-request roots.some loop. The diff also adds target realpathSync/lstatSync/statSync and calls \`\_requireRelayResourceAccess()\` synchronously from \_handleRequest before invoking asynchronous handlers.

Browsing a mounted workspace or opening several changed files adds blocking filesystem calls to every relay read/list/resolve. Even a first-root match repeats target and root canonicalization; a later worktree/content-root match additionally visits preceding roots, including duplicate resident-session workspaces. Slow mount metadata operations stall the shared host event loop, delaying local session progress and other remote lanes as well as the file request.

**Evidence:** ProtocolServerHandler.\_handleRequest:2011–2012 invokes the guard synchronously. \_isGrantedRelayResource:2265–2305 resolves the target/ancestors synchronously and then realpaths grants until the first match. MissionControlHost.\_resourceRoots:106–112 rebuilds \`\[...grantedRoots, ...residentSessionWorkspaces, ...sessionContentRoots\]\` without deduplicating workspaces. The handler uses the same AgentService/state manager and utility-process event loop as local IPC. AgentService.resourceRead:9613 awaits fileService.readFile. Residency normally targets 10 sessions but exempts subscribed/active/held sessions; this is not a loop over all persisted history.

**Suggested direction:** Preserve symlink/grant enforcement but perform canonicalization/stat checks asynchronously before dispatch, maintaining required action ordering. Deduplicate roots within a check; do not cache canonical paths across filesystem/grant changes without appropriate invalidation.
