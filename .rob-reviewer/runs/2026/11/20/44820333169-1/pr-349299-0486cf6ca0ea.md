### Scenario 2: Request a next edit with embedder-supplied language context enabled, including repeated requests and cancellation.

Prompt construction follows, then the remaining debounce and the streaming completion request. DelaySession subtracts elapsed collection time, so context collection does not add a second full debounce. With context disabled, collection is skipped unless recording explicitly requests it; recording-only collection is not awaited for prompting.
- Scaling input: D open text documents for the active-document lookup, C yielded context items and their URI lists, and the configured snippet token budget. One async context-collection invocation per fresh prompt attempt, not one network request per snippet or provider.
- Effective concurrency: A context stream is consumed sequentially, with URI checks grouped within each snippet and resolved by the no-op ignore service. Existing request reuse and cancellation remain unchanged. Internal provider parallelism and cancellation cooperation belong to the supplied implementation; the diff adds no fan-out scheduler.
- Cache behavior: NextEditProvider checks the edit cache before fetching and joins compatible pending regular or speculative requests, avoiding duplicate context collection on those paths. No new library-level context-result cache is added; external provider caching is unspecified. NullIgnoreService remains installed, so snippet ignore checks do not perform filesystem or network I/O.
- Mechanism confidence: High for the traced gate, remaining-debounce timeout, request reuse, token budgeting, and unchanged completion count. No concrete external-provider IPC or network implementation is available.
- Magnitude uncertainty: Host provider latency, snippet volume, cache behavior, and cancellation responsiveness cannot be measured or inferred from the new API or fixed-size test.

### Scenario 3: Resolve a cross-file cursor prediction into an edit using the supplied workspace service.

- Critical path: After an initial completion yields no usable edits, an enabled predictor may make a prediction request. For a different-file OnlyWithEdit prediction, the existing handler awaits opening the target document, checks cancellation and intervening typing, creates its snapshot, and makes a follow-up edit attempt. The RetryState guard prevents recursive cursor-jump prediction.
- Scaling input: At most one predicted target and one target-document open per cursor-jump chain, rather than one open per workspace file. Snapshot work scales with target file size.
- Effective concurrency: Initial completion, optional prediction, target opening, and target follow-up are sequential for one chain. Existing compatible-request joining is preserved. No new per-file parallelism or concurrency burst is introduced.
- Cache behavior: The workspace service owns document-open caching. Existing edit-cache hits can avoid the prediction/open/follow-up chain when the target is open and matches its cached snapshot; invalid targets fall back to a fresh request. The PR does not change those checks or keys.
- Mechanism confidence: High: target opening, snapshot creation, follow-up, and the retry guard were read directly, along with cache validation and pending-request reuse.
- Magnitude uncertainty: Cold target-open latency and file sizes depend on the embedding workspace. No concrete implementation or timings accompany the hook.
- Expensive boundaries:
  - network at <code>extensions/copilot/src/extension/xtab/node/xtabNextCursorPredictor.ts: predictNextCursorPosition</code>: Request the next cursor position through endpoint.makeChatRequest2.; cardinality: At most one cursor-prediction request in this chain because retrying edit attempts skip further cursor prediction.
    - Introduced by diff: false; previous behavior: The same optional prediction request could already run with null workspace services.; critical-path effect: Completes after the first no-edit response and before the target can be resolved.
  - filesystem at <code>extensions/copilot/src/extension/xtab/node/xtabProvider.ts: handleCrossFilePrediction, openTextDocument(targetUri)</code>: Ask the workspace service to open one predicted target document; an embedder may satisfy this from memory or perform filesystem/IPC access.; cardinality: One openTextDocument call per eligible cross-file prediction. There is no workspace-wide file enumeration.
    - Introduced by diff: true; previous behavior: The call site already existed, but NullWorkspaceService had no documents and rejected immediately. Injection permits a real host-backed open to succeed.; critical-path effect: Awaited before reading the target snapshot and requesting the follow-up edit.
  - network at <code>extensions/copilot/src/extension/xtab/node/xtabProvider.ts: handleCrossFilePrediction -&gt; doGetNextEditWithSelection -&gt; \_performFetch</code>: Request an edit for the successfully resolved target document.; cardinality: One follow-up edit attempt per cursor-jump chain, apart from the existing guarded model-not-found fallback; not a request per file in the workspace.
    - Introduced by diff: true; previous behavior: The handler and follow-up implementation existed, but the library's empty workspace service prevented successful target resolution and this follow-up.; critical-path effect: Needed to obtain the cross-file edit; it is serialized after target opening.
- Verdict: No reportable regression: these bounded operations are necessary to deliver the newly supported cross-file result, and no redundant opens, unbounded retries, or multiplied boundary calls are introduced.
