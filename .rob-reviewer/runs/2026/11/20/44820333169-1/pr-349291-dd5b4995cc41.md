### 1. cleanup-lifecycle

**Fix location:** `src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts:440` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts:432`  
**Introducing path:** `src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts`  
**Introducing commit:** `5d6f7a65d38bd14a2c80094cc0531fec07f15d9e`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `io`  
**Confidence:** 0.94

**Mechanism:** A cancellation token supplied for a multi-item Explorer copy was ignored inside the sequential working-copy copy loop and not forwarded to the underlying transfer. Remaining files in the same homogeneous group continued consuming disk I/O, IPC/network bandwidth, and per-target queue time after cancellation; cost scaled with the remaining file count and bytes.

**Symptom:** Cancelling a large multi-item copy could leave the full remaining homogeneous group transferring and its operation promise pending. Static call-path evidence establishes the wasted work; no timing measurements are claimed.

**Fixed behavior:** Cancellation now terminates the sequential operation loop before starting another copy and reaches the file-service transfer loop for an active cross-provider copy. Already-open handles close and the partial target is deleted before the target queue is released. Provider-native copies remain non-interruptible while active but no longer force later items to run.

**Evidence:** Before the diff, ExplorerService.applyBulkEdit already exposed cancellation for edit.length &gt; 1 and passed its token into bulkEditService.apply. BulkFileEdits.apply groups consecutive copies into one CopyOperation and checks cancellation only between groups; CopyOperation passes the token into WorkingCopyFileService.copy. The base doMoveOrCopy loop nevertheless invoked fileService.copy(source, target, overwrite) for every operation without checking that token. Thus cancelling an in-progress homogeneous copy group still copied all remaining files. The added check at workingCopyFileService.ts:440-441 stops subsequent operations, and token forwarding at :457 plus fileService.ts:1499 stops buffered cross-provider copies between chunks. DiskFileSystemProviderClient.read/write cross channel.call boundaries, so this removes actual unnecessary filesystem/IPC/network work rather than merely changing progress presentation. Blame of the old unconditional copy at base line 432 identifies commit 5d6f7a65d38bd14a2c80094cc0531fec07f15d9e.
