# Performance review: terminal: make type-ahead local echo agree with shell output

[PR #346179](https://github.com/microsoft/vscode/pull/346179) at `0dcb66e6f3885b5fe16dcb414e95ff04bf50d5fe`

## Findings (2)

### 1. [high] Bound buffering of fragmented control strings

**Finding ID:** `PERF-98DF7DA600ED`  
**Location:** <code>src/vs/workbench/contrib/terminalContrib/typeAhead/browser/terminalTypeAheadAddon.ts:1170</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** All incoming string chunks and the joined duplicate of a fragmented OSC/DCS/control-string payload  
**Scaling:** Retained memory grows linearly with every server-output chunk until a terminator arrives; completion joins the entire retained payload into another large string. Continuous chunks also reset the prediction timeout, so neither size nor lifetime is bounded.  
**Outcome:** Unbounded renderer memory growth followed by a large allocation/parse stall, with terminal output withheld throughout the transfer.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A control-string chunk that did not match the pending prediction caused prediction reconciliation to fail and the chunk was forwarded; later chunks were then streamed with no pending prediction state, so the addon did not retain the full payload.  
**Changed behavior:** When the scanner remains incomplete at offset zero, each new chunk is pushed into \_incompleteEscapeChunks and an empty string is returned. \_onBeforeProcessData then calls \_deferClearingPredictions for every chunk, repeatedly postponing the only timeout that could release the buffer.  
**Confidence:** 0.98 — The retention, suppression, timeout reset, and full join are directly traced in changed code. Large chunked terminal control payloads are realistic, though their prevalence varies, so the mechanism is certain while frequency is not.

**Causal diff evidence:** RIGHT line 1170 newly appends every continuation chunk to \`\_incompleteEscapeChunks\`; this array and scanner-based withholding did not exist before the PR, whose mismatch path rolled back and forwarded output.

If a prediction is pending when a large chunked OSC/DCS payload begins (for example a clipboard or image transfer), all payload bytes are duplicated and held until termination; a long or unterminated transfer can keep growing memory and then stall the UI when join/reconciliation runs.

**Evidence:** Lines 1168-1172 append and suppress every continuation while predictions remain. \`\_onBeforeProcessData\` invokes \`\_deferClearingPredictions\` after each server event, and that method disposes/restarts a &gt;=500 ms timeout. The completion path at line 1174 uses \`\_incompleteEscapeChunks.join('') + complete\`, allocating the whole retained payload again. Tests cover only short fragmented strings and do not impose a byte/chunk limit.

**Suggested direction:** Do not retain arbitrary control-string payloads. Once an incomplete non-CSI control string is detected, roll back/disable pending predictions and immediately forward the buffered/current chunks while keeping only scanner state; alternatively enforce a small byte cap that flushes and exits reconciliation before appending more.

### 2. [medium] Avoid copying all predicted cells on every cursor clone

**Finding ID:** `PERF-7865DDF21AF9`  
**Location:** <code>src/vs/workbench/contrib/terminalContrib/typeAhead/browser/terminalTypeAheadAddon.ts:157</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Map entries and short-lived Map allocations on the synchronous terminal input/output path  
**Scaling:** For a command with N distinct predicted cells, each character adds a cell and both tentative-cursor creation and character confirmation clone the current N-entry map, producing O(N²) entry copies and allocations over the command.  
**Outcome:** Increasing input latency and CPU/GC pressure, potentially freezing local echo for long commands or unbracketed paste bursts on a high-latency terminal.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Cursor.clone copied only cursor coordinates via moveTo, so cloning was O(1) regardless of how many predictions had already been made.  
**Changed behavior:** Cursor.clone now calls adopt, and adopt constructs new Map(cursor.\_cells); the map retains prior predicted cells until prediction state is cleared, while ordinary character handling repeatedly requests tentativeCursor and CharacterPrediction.rollForwards also clones the cursor.  
**Confidence:** 0.97 — The changed O(N) copy, retained per-command cell map, and per-character clone call sites are all explicit in the implementation. Exact milliseconds depend on command length and type-ahead activation, so severity is medium rather than high.

**Causal diff evidence:** RIGHT line 157 changes adoption from coordinate-only state to \`this.\_cells = new Map(cursor.\_cells)\`, turning every newly added clone/adopt call into a full copy of all accumulated predicted cells; before the diff clone used only \`moveTo(this)\`.

With type-ahead active, a long shell command or plain paste causes progressively larger synchronous copies per key/echo; 1,000 predicted cells entail on the order of a million copied map entries instead of linear work, delaying typing and terminal rendering.

**Evidence:** The added cell overlay is populated by CharacterPrediction.apply/setCell. addPrediction invalidates \_tenativeCursor after every character, and the ordinary-character path immediately calls tentativeCursor again, whose clone reaches this line. CharacterPrediction.rollForwards also calls cursor.clone for each confirmed character. Confirmed predictions are shifted from \_expected but their cells are not removed from Cursor.\_cells, so the copied map grows across the command until \_clearPredictionState clears the cursor.

**Suggested direction:** Keep cursor cloning O(1), for example with an immutable/shared cell snapshot plus small copy-on-write overlays, or separate coordinate-only clones from the rare operation that truly needs an independent cell map; also discard confirmed cells that can no longer be revisited.

### Scenario 2: Receiving a large or unterminated fragmented OSC/DCS/control string while a prediction remains pending

- Critical path: Each PTY chunk enters beforeServerInput synchronously. The changed scanner marks the sequence incomplete, appends the chunk, and returns an empty string, so xterm parsing/rendering cannot progress until termination, timeout, cancellation, or disposal.
- Scaling input: Total payload bytes B and chunk count C after the first incomplete sequence. Retention is O(B), the chunks array is O(C), and completion joins/copies O(B); there is no byte or chunk cap.
- Effective concurrency: PTY callbacks are serialized. Every callback restarts the single prediction-clear timeout, so a continuous transfer prevents cleanup rather than allowing timeout and output processing to overlap.
- Cache behavior: \_incompleteEscapeChunks is an unbounded transient buffer, not a cache: there is no deduplication, size cap, spill, or incremental consumption. Completion clears it only after allocating a joined string; cancellation/disposal flushes it.
- Mechanism confidence: High: append-and-suppress, full join, and per-event timeout restart are explicit and reachable whenever a prediction precedes a fragmented control string.
- Magnitude uncertainty: Frequency and payload size vary by terminal workload, but OSC clipboard/image transfers can be large and an unterminated stream establishes no finite upper bound.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminalContrib/typeAhead/browser/terminalTypeAheadAddon.ts:1971 \_onBeforeProcessData</code>: Receive chunked terminal output from the shell/process host; cardinality: One event per upstream output chunk; large clipboard/image/control payloads can produce many chunks. The diff does not add IPC calls but changes every continuation from streamed to retained.
    - Introduced by diff: false; previous behavior: Incoming PTY events already existed, but a prediction mismatch rolled back and forwarded the first control chunk, after which later chunks streamed normally.; critical-path effect: The changed return value suppresses every chunk from xterm, blocking parser/render progress until the whole control string is released.
  - serialization at <code>src/vs/workbench/contrib/terminalContrib/typeAhead/browser/terminalTypeAheadAddon.ts:1174 beforeServerInput</code>: Join all retained control-string chunks into one string and concatenate the completion; cardinality: One whole-payload allocation when the sequence terminates, after retaining C original chunk strings.
    - Introduced by diff: true; previous behavior: No whole-control-string chunk array or final join existed.; critical-path effect: The full join and subsequent reconciliation occur synchronously before completed output can reach xterm.
  - other expensive boundary at <code>src/vs/workbench/contrib/terminalContrib/typeAhead/browser/terminalTypeAheadAddon.ts:1978 \_onBeforeProcessData caller path</code>: Submit released control output to xterm parsing/rendering; cardinality: Changed from incremental writes per process chunk to no writes during buffering followed by one potentially very large write.
    - Introduced by diff: true; previous behavior: Control output was forwarded incrementally after prediction failure.; critical-path effect: Parser/render work is delayed and burst at completion.
- Verdict: Reportable high unbounded-retention regression: the addon can duplicate and indefinitely retain an arbitrary process-output payload while blocking terminal progress.

### Scenario 3: Fish and PSReadLine repaint reconciliation after each edit

- Critical path: Each incoming repaint is scanned, parsed into row cells, compared against pending predictions, and pending edits are reapplied before the rewritten output reaches xterm.
- Scaling input: At most the current terminal row width W cells and P pending predictions. Erase-to-end and reapply paths can approach O(W\*P), but normal per-key shell replies keep P small and W is bounded by terminal columns.
- Effective concurrency: Serialized per PTY output event on the renderer event loop; there is no parallel work or external limiter.
- Cache behavior: Cell snapshots are temporary per repaint and discarded after the callback. Cursor overlays persist for prediction reconciliation; no cold/warm external cache is involved.
- Mechanism confidence: High for the synchronous O(W\*P) code shape; lower for harmful magnitude under realistic effective P.
- Magnitude uncertainty: Very wide terminals and unusual bursts increase W and P, but repository tests and shell behavior show ordinary repaint confirmations quickly reduce P; no independent high-confidence user-visible regression beyond the reported cursor-copy mechanism was established.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminalContrib/typeAhead/browser/terminalTypeAheadAddon.ts:1971</code>: Receive shell repaint output; cardinality: Typically one or several chunks per keypress, controlled by shell and transport fragmentation; unchanged by the diff.
    - Introduced by diff: false; previous behavior: The same PTY output arrived, but unsupported repaint patterns caused prediction rollback rather than detailed row reconciliation.; critical-path effect: Reconciliation is synchronous before forwarding to xterm, but it avoids extra subprocess/network calls.

    - Introduced by diff: false; previous behavior: Output was also passed to xterm after simpler matching/rollback.; critical-path effect: Visible repaint waits for synchronous row parsing and prediction reapplication.
- Verdict: No additional finding: added repaint support performs bounded row-local work, and realistic effective cardinality did not prove a separate actionable regression.

- Verdict: No regression: repeated reevaluation remains coalesced and scheduled work is lifecycle-owned.
