**Relevant issue families:** boundary-fanout, repeated-work, cache-lifecycle

### Scenario 1: Starting a retained or one-off Codex app-server connection after explicit Codex use

- Critical path: SDK root resolution (including a cold download when necessary) completes first; the new binary resolver then performs filesystem realpath lookups, followed by executable access, proxy startup, temporary-directory creation, process spawn, and the app-server initialization handshake. The added realpath work is on the startup critical path.
- Scaling input: Cost scales with actual Codex process starts (initial explicit activation, process-loss restart, or serialized one-off actions), not with messages or concurrent callers. The diff adds a constant two to three filesystem metadata calls per start.
- Effective concurrency: Concurrent retained-connection callers share \`\_ensureConnection\`'s single starting promise and then reuse the ready process. One-off actions are serialized by \`\_onDemandConnectionSequencer\`. Cold SDK downloads are coalesced by cache-directory key, so the changed lookup is executed once per actual connection start, not once per concurrent caller or chat message.
- Cache behavior: The SDK downloader uses a persistent sentinel cache, coalesces cold downloads, and negatively caches failures. The binary path itself is not memoized, but a retained ready connection avoids subsequent resolution; only a genuine restart or serialized one-off connection repeats it. Flat, isolated, and missing layouts are resolved independently on each actual start.
- Mechanism confidence: High: changed lines directly add the awaited realpath calls, and connection lifecycle code proves coalescing and reuse.
- Magnitude uncertainty: Exact realpath latency depends on the local filesystem and development layout, but the added count is fixed and is adjacent to an existing SDK check, process spawn, and IPC handshake.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/agentSdkDownloader.ts:\_download</code>: Fetch a configured Codex SDK tarball on a cold SDK-cache miss.; cardinality: At most one coalesced download per package/version/target and downloader process; zero with a warm cache or development override.
    - Introduced by diff: false; previous behavior: The same cold SDK resolution/download occurred before direct binary-path construction.; critical-path effect: Blocks a cold connection start, but is unchanged by this diff.
  - filesystem at <code>src/vs/platform/agentHost/node/codex/codexSdk.ts:resolveCodexBinaryPath</code>: Resolve the real directory of \`&#64;openai/codex\` and the real native-binary path.; cardinality: Two successful/attempted realpath calls in a flat or missing layout, and three in the isolated pnpm fallback layout where the first binary candidate misses.
    - Introduced by diff: true; previous behavior: The caller constructed the flat binary path without these realpath operations.; critical-path effect: Adds two to three local metadata operations before executable validation and process spawn.
  - filesystem at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_startRawConnection</code>: Validate executable access, create a sandbox temporary directory, and on Linux resolve the launch path.; cardinality: One access and one temporary-directory creation per actual connection start; Linux also performs one realpath. These operations pre-existed.
    - Introduced by diff: false; previous behavior: The same access, temporary-directory creation, and Linux realpath occurred against the directly constructed path.; critical-path effect: Blocks process launch but is unchanged except that the supplied path is now already canonical.
  - subprocess at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_startRawConnection</code>: Spawn the Codex app-server.; cardinality: One process per actual retained or transient connection start.
    - Introduced by diff: false; previous behavior: The same binary was spawned when present at the flat path.; critical-path effect: Process startup is required before Codex actions can proceed and dominates the bounded metadata lookup added here.
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_startRawConnection</code>: Initialize the spawned app-server over its child-process transport.; cardinality: One initialization handshake per spawned connection, followed by operation-specific requests.
    - Introduced by diff: false; previous behavior: The same initialization handshake followed process spawn.; critical-path effect: The handshake remains on the connection-start critical path.
- Verdict: No reportable regression. The diff adds bounded metadata work to startup, but it does not fan out with messages or callers and is minor relative to the unchanged subprocess startup; canonicalization is required for the supported isolated layout.

### Scenario 2: Opening or validating a saved Codex chat from native history

- Critical path: Saved-chat metadata/database resolution precedes the provider reader. The reader resolves the installed SDK root, executes the new binary-path realpath lookups, snapshots native history into scratch storage, spawns a one-shot Codex process, reads the thread over IPC, optionally reads rollout metadata, and replays turns. The new realpath calls are on this read critical path.
- Scaling input: Overall work scales with requested saved chats and transcript turn count. The diff's incremental work is fixed at two to three metadata calls per chat; IPC pagination remains approximately one request per 100 turns and is unchanged.
- Effective concurrency: \`CodexSavedChatReader.\_reads\` is a single Sequencer, so heavy native reads—including the changed lookup—run one at a time even when callers request multiple chats concurrently. Each completed saved-chat read starts one one-shot process; there is no parallel process burst.
- Cache behavior: Installed SDK discovery checks the persistent cache sentinel; this path does not trigger a network download. The binary path has no explicit memoization, so each requested chat repeats the fixed lookup, while the sequencer prevents overlap. The native history itself is snapshotted per read rather than cached, as before.
- Mechanism confidence: High: the changed awaited helper is directly reached once per sequenced provider read, and the reader and tests establish serialization.
- Magnitude uncertainty: A bulk continuation/archive workflow can request several chats, but the reads are serialized and each already performs a filesystem snapshot plus process startup. Exact filesystem latency is environment-dependent.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/codex/codexSavedChatReader.ts:read</code>: Read saved-session metadata and resolve the native thread identifier.; cardinality: One metadata read per requested saved chat, plus host-level saved-chat resolution around the provider read.
    - Introduced by diff: false; previous behavior: The same metadata reads selected the native thread before binary-path construction.; critical-path effect: Must complete before native history decoding and is unchanged.
  - filesystem at <code>src/vs/platform/agentHost/node/codex/codexSdk.ts:resolveCodexBinaryPath</code>: Resolve the real \`&#64;openai/codex\` scope and native executable path.; cardinality: Two realpath attempts in flat/missing layouts or three in isolated pnpm layout per sequenced saved-chat read.
    - Introduced by diff: true; previous behavior: The saved-chat reader directly constructed the flat executable path with no realpath lookup.; critical-path effect: Adds a constant local metadata delay before the one-shot native reader starts.
  - filesystem at <code>src/vs/platform/agentHost/node/codex/codexSavedThreadReader.ts:readCodexSavedThreadFromDisk</code>: Validate the executable, discover and snapshot native history, create/remove scratch storage, validate history, and canonicalize the returned transcript path.; cardinality: One snapshot lifecycle per saved-chat read; copied history volume depends on the native history store.
    - Introduced by diff: false; previous behavior: The same access, snapshot, validation, and cleanup ran using the directly constructed binary path.; critical-path effect: This existing snapshot work must complete around the one-shot decode and is substantially broader than the added fixed metadata lookups.
  - subprocess at <code>src/vs/platform/agentHost/node/codex/codexSavedThreadReader.ts:readCodexSavedThreadFromDisk</code>: Spawn a sandboxed one-shot Codex app-server to decode native history.; cardinality: One process per saved-chat read, globally serialized by the reader.
    - Introduced by diff: false; previous behavior: The same one-shot process was spawned when the flat executable path existed.; critical-path effect: Required for the read and unchanged by the diff.
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexSavedThreadReader.ts:readCodexSavedThread</code>: Initialize the child, read thread metadata, and fetch full turn pages.; cardinality: One initialize and one initial thread read, then either one legacy full read or approximately one page request per 100 turns.
    - Introduced by diff: false; previous behavior: The same child-process requests and pagination were performed.; critical-path effect: Controls native decoding latency and remains unchanged.
- Verdict: No reportable regression. Repeated reads do repeat the new lookup, but only at constant cardinality per already-heavy, serialized process-based read; the diff does not introduce meaningful fan-out, concurrency, or retained state.

**Summary:** Reviewed all four changed files and traced both production call paths. The only new performance cost is two to three awaited filesystem realpath operations per actual Codex process start or sequenced saved-chat read. Existing connection coalescing, SDK caching/download deduplication, and saved-reader sequencing keep the work bounded; no actionable performance regression was found.
