## Performance regression fixes detected (3)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/workbench/contrib/comments/browser/commentReply.ts:101` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/comments/browser/commentReply.ts:102`  
**Introducing path:** `src/vs/workbench/contrib/comments/browser/commentReply.ts`  
**Introducing commit:** `7d735425b6156dc7d8ac45755e9c443838565890`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.99

**Mechanism:** CommentReply could be disposed while createModelReference was pending; when the promise resolved, the old code registered the reference with an already-disposed DisposableStore. DisposableStore.add explicitly does not retain or dispose such an item, so the model reference and underlying text model were leaked.

**Symptom:** Rapidly closing a comment thread while its reply model resolves could retain one model reference and text model per race, producing disposal-leak failures and cumulative workbench memory growth.

**Fixed behavior:** After model creation resolves, the new disposed-state check immediately disposes the model reference and returns instead of registering it into a dead owner.

**Evidence:** The changed branch at RIGHT line 101 calls model.dispose() when this.\_store.isDisposed. The prior continuation reached base line 102, this.\_register(model), after the await; lifecycle.ts documents and implements that add on a disposed store leaks the added object. createModelReference is reference-counted by TextModelResolverService, so failing to dispose the returned reference retains the model. Blame identifies the commit that introduced that registration.
