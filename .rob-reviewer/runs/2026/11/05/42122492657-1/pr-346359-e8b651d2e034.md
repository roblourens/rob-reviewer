### Scenario 1: First opening the Inbox new-session composer, followed by subsequent warm opens

- Critical path: On the cold path, ensureNewSessionComposer coalesces callers through composerInitialization, creates one scoped context and child instantiation service, then synchronously creates and attaches one chat view. Warm calls stop at the existing newSessionView check and only update composer mode. The diff only changes which already-owned disposable store receives the two scope objects; it does not add chat-view construction or move it onto a hotter path.
- Scaling input: One composer and one service scope per InboxNotificationsView lifetime, independent of notification count and repeated openNewSession calls.
- Effective concurrency: Cold initialization is coalesced by the shared composerInitialization promise; the synchronous newSessionView guard prevents duplicate construction. Warm opens reuse the singleton view.
- Cache behavior: newSessionView is the positive singleton state. Cold creation occurs once; warm accesses reuse it. Failures clear composerInitialization for an explicit retry, unchanged by the diff.
- Mechanism confidence: High: changed lines only redirect two add calls to a second store registered immediately after the composer store, and all usages show no path that clears or recreates the composer during the view lifetime.
- Magnitude uncertainty: The chat view may be heavyweight, but its construction frequency and timing are unchanged; the only additional steady allocation is one DisposableStore per Inbox view.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added store is constant-size lifecycle bookkeeping and neither repeats expensive work nor retains the scope beyond the owning view.

### Scenario 2: Creating and opening a window canvas presentation

- Critical path: getPresentation synchronously creates the DOM element, scope, child instantiation service, canvas content, and renders it only when entry.presentation is absent. The diff splits content and scoped services into adjacent stores solely to control later disposal order; all pre-existing UI construction remains on the same cold path.
- Scaling input: One presentation and one pair of stores per opened canvas entry, rather than work scaling with rows, messages, or frames.
- Effective concurrency: Presentation construction is synchronous and guarded by entry.presentation; each canvas entry receives at most one successful presentation. Failed construction synchronously deletes and disposes both new stores before rethrowing.
- Cache behavior: entry.presentation is the positive singleton cache. Warm getPresentation calls return it directly. Failed construction leaves no presentation and disposes both temporary stores, allowing a later explicit retry without retained scope state.
- Mechanism confidence: High: the guard, synchronous construction, and catch cleanup are visible in the changed method, and the entry store owns both stores until closure.
- Magnitude uncertainty: Canvas constructors can vary in cost, but the diff neither invokes them more often nor changes their render inputs.
- Expensive boundaries: none found
- Verdict: No reportable regression. One extra constant-sized DisposableStore does not establish meaningful startup, CPU, or memory degradation.

### Scenario 3: Closing an Inbox-backed window canvas with a live new-session composer

- Critical path: Canvas forget removes the element and synchronously disposes entry.store. In insertion order this now disposes canvas content first; Inbox disposal hides the view and disposes its composer before the composer's scoped services, then the canvas-level scoped services dispose. Only after teardown does forget persist the open-canvas set. The reordered service cleanup remains within the same synchronous close operation and is not deferred or leaked.
- Scaling input: Teardown work remains proportional to the pre-existing disposables owned by one composer/canvas. The diff adds two constant-size nested stores and does not multiply work by notification count, repeated closes, or session history.
- Effective concurrency: Disposal is synchronous and serial in DisposableStore insertion order. Closing one canvas does not launch concurrent service cleanup, subprocesses, IPC bursts, or network work.
- Cache behavior: No cache lookup occurs during teardown. The composer and canvas presentation singletons are released once with their owning view/entry; no negative-cache or retry behavior changes.
- Mechanism confidence: High: DisposableStore uses insertion-ordered Set disposal; both new scope stores are registered immediately after their content stores, catch paths dispose both, and owner teardown disposes the parent store once.
- Magnitude uncertainty: Individual chat-view disposables may have varying cost, but they were already disposed on this path. The changed order adds no duplicate disposal and scoped services remain retained only until the immediately following store entry.
- Expensive boundaries:
  - serialization at <code>src/vs/sessions/contrib/inboxOne/browser/inboxNotificationsView.ts:655 logViewState</code>: Emit the existing agents/inboxViewState close telemetry event with fixed-size scalar fields while InboxNotificationsView.setVisible(false) runs.; cardinality: One close event per visible Inbox close, plus an existing blur event only when focus timing requires it; independent of notification collection size.
    - Introduced by diff: false; previous behavior: The same close/blur telemetry was emitted before the disposal-store reordering.; critical-path effect: Called synchronously before super.dispose, but the diff does not add, duplicate, or move this telemetry call.
  - filesystem at <code>src/vs/sessions/services/canvas/browser/windowCanvasService.ts:433 saveOpenCanvases</code>: Persist the remaining restored canvas ID array through IStorageService.store.; cardinality: One storage call per forgotten canvas, serializing the current set of restored canvas IDs.
    - Introduced by diff: false; previous behavior: The same storage write occurred once after every canvas forget before this PR.; critical-path effect: Runs synchronously after entry.store disposal on the close path; its placement and cardinality are unchanged.
- Verdict: No reportable performance regression. The PR fixes cleanup ordering without increasing lifecycle cardinality, crossing a new expensive boundary, or extending resource lifetime beyond the same synchronous close.

**Summary:** Reviewed all four changed files and both lifecycle-order changes. The diff adds constant-size disposable-store separation so content tears down before its scoped services. Cold/warm creation guards, failure cleanup, boundary cardinality, and synchronous close behavior remain unchanged; no actionable diff-introduced performance issue or qualifying performance-regression fix was found.
