## Findings (1)

### 1. [medium] Scope allowlist cleanups to the affected files

**Finding ID:** `PERF-32D721D62B1B`  
**Location:** <code>build/lib/changedFiles.ts:37</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem reads/content hashing and, on cold cache entries, parsing plus AST analysis for every JavaScript/TypeScript file in the repository  
**Scaling:** Each edit to the 211-line migration allowlist expands from the one fixed source file to every path matched by eslintFilter; cost grows with total repository JS/TS files rather than the number of files removed from the allowlist.  
**Outcome:** Incremental cleanup PRs incur full-repository ESLint I/O and CPU, increasing the Hygiene & ESLint job latency from the intended changed-file check to a repository-wide check.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this entry, fixing one source file used getEslintScope's changed-files branch and linted that file only; this allowlist did not force a full lint.  
**Changed behavior:** The added path matches eslintFullCheckPaths, so getEslintScope returns kind 'full' whenever any entry is removed from .eslint-allowed-register-after-await-files, and build/eslint.ts expands that to the complete eslintFilter.  
**Confidence:** 0.97 — The scope transition and CI call path are explicit, as is the planned repeated trigger for baseline removals. Exact elapsed time depends on cache warmth and repository size, but the repository-wide file discovery/hash cardinality versus one changed source file is deterministic.

**Causal diff evidence:** The added RIGHT-side entry \`'.eslint-allowed-register-after-await-files',\` at build/lib/changedFiles.ts:37 makes matchesAny classify every modification of the new migration baseline as a full ESLint check.

The README explicitly requires removing a file from this 211-line baseline when it is fixed. Every such follow-up now sends all repository JS/TS files through lintFiles instead of the affected source file; warm cache still requires repository-wide discovery/content-cache validation, while cold or invalidated entries also parse and run the new rule.

**Evidence:** build/lib/changedFiles.ts:161-165 returns full scope for any matchesAny hit, and build/eslint.ts:57-63 maps full scope to getEslintFilePatterns(\[\]), whose build/filters.ts:262-270 globs all JS/TS. The PR workflow invokes eslint --changed-since for every PR (.github/workflows/pr.yml:301-306), while the new README at line 172 directs each cleanup to edit this allowlist.

**Suggested direction:** Special-case this migration baseline so a cleanup lints the changed source files plus any paths removed from the allowlist (derive removed entries from the diff), rather than treating every baseline edit as globally affecting all lint targets.
