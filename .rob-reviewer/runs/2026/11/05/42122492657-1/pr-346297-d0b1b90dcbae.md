## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts:1197` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts:1175`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts`  
**Introducing commit:** `15dba1928a0799a0f465415b344931e98550d0eb`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.97

**Mechanism:** Disposing a chat editing session while asynchronous text/notebook entry creation was in flight lost the only cleanup owner for the completed entry, retaining model references, models, listeners/watchers, autoruns, and notebook snapshot resources beyond the session lifetime.

**Symptom:** Repeatedly closing or replacing editing sessions while file/notebook model resolution is in flight can accumulate orphaned editing entries and their heavyweight model/listener graphs, increasing retained memory and background listener work.

**Fixed behavior:** After asynchronous entry creation returns, the added disposed-store guard immediately disposes the newly created entry and throws cancellation. The changed streaming/external queue handlers complete their deferred start/acquisition promises in finally blocks, so this cleanup cancellation also cannot strand per-resource sequencers or baseline locks.

**Evidence:** In the base revision, \_getOrCreateModifiedFileEntry awaited \_createModifiedFileEntry at line 1175 and then unconditionally adopted the returned entry. ChatEditingSession.dispose() only disposes entries already present in \_entriesObs before disposing its store. If disposal occurs during that await, the newly returned entry was never seen by dispose(). Text entries own a text-model reference, an original model, a file watcher, global file-change listener, autoruns, and diff services; notebook entries own two resolved notebook-model references and registered snapshot resources. The changed post-await guard detects that ownership has already ended and disposes the orphan before it can escape.

### Scenario 3: A chat editing session is disposed while asynchronous text or notebook entry creation is unresolved.

- Critical path: Session disposal synchronously disposes entries already published in \_entriesObs and its DisposableStore. In-flight creation still finishes its existing model-resolution/serialization work; the new post-await guard then disposes that orphan and throws cancellation. Queue handlers swallow only this disposal cancellation and release their deferred gates. Cleanup is on the shutdown path, not a normal edit-start critical path.
- Scaling input: Potential work and retained state scale with the number of distinct entry creations simultaneously in flight when the session is disposed. Each completed orphan is now disposed exactly once.
- Effective concurrency: Different resource keys can have creations in flight concurrently. Added checks do not launch more work; each continuation independently observes the disposed store and tears down its own entry.
- Cache behavior: Published entries are disposed by the normal \_entriesObs ownership path. In-flight entries have not reached that cache, so the new guard supplies the missing ownership handoff. No new cache or retained key is introduced.
- Mechanism confidence: Very high: disposal order, await boundary, disposed-store guard, explicit entry disposal, and owned resource graphs are directly traced. Base blame identified the introducing commit for the old mechanism.
- Magnitude uncertainty: Race frequency and retained model size vary; repeated session replacement during slow model resolution is the realistic worst case.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts:\_getOrCreateModifiedFileEntry</code>: Complete the already-started text/notebook model resolution after session disposal.; cardinality: One completion per resource whose entry creation was already in flight at disposal.

- Verdict: This is a concrete cleanup-lifecycle regression fix, recorded through report\_regression\_fix. It reduces retained memory/background listener work and removes cancellation-induced queue hangs; it introduces no actionable performance regression.
