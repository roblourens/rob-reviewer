# Performance review: Fix nb stickyscroll not having outline if outline pane is closed

[PR #239859](https://github.com/microsoft/vscode/pull/239859) at `054be4ab311b8e70af7e408b2f4c3c4111d37e82`

## Findings (1)

### 1. [medium] Avoid resolving every code cell before initializing sticky scroll

**Finding ID:** `PERF-6C5C438320D1`  
**Location:** <code>src/vs/workbench/contrib/notebook/browser/viewParts/notebookEditorStickyScroll.ts:228</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Up to 50 text-model references and concurrent document-symbol provider calls, including one extension-host IPC request per cell/provider on a cold outline-model cache  
**Scaling:** Each notebook attachment launches min(code-cell count, 50) cacheSymbols operations concurrently; provider work further multiplies by the number of registered document-symbol providers, and Promise.allSettled delays sticky content until the slowest request finishes  
**Outcome:** A burst of extension-host/CPU work immediately after notebook attachment and delayed sticky-header initialization, causing post-open contention and latency on code-heavy notebooks  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Sticky-scroll initialization only synchronously consumed the shared outline data source. Code-symbol resolution was initiated by the Outline pane only when code-cell symbols were enabled, so opening a notebook with sticky scroll enabled and the Outline pane closed did not fan out document-symbol requests.  
**Changed behavior:** The new attachment handler awaits computeFullSymbols with CancellationToken.None before updating sticky content, and init does the same when sticky scroll is enabled. computeFullSymbols starts cacheSymbols for the first 50 code cells in parallel.  
**Confidence:** 0.99 — The changed call path, 50-cell cap, all-at-once scheduling, provider IPC boundary, and sticky renderer's rejection of level-7+ entries are all explicit in repository code. Exact provider latency and the fraction of users enabling the default-off feature are uncertain, which limits severity rather than mechanism confidence.

**Causal diff evidence:** Added RIGHT line 228 now calls \`await notebookCellOutline.computeFullSymbols(CancellationToken.None)\` on every view-model attachment; added line 212 also puts the same fan-out on sticky-scroll enablement/initialization.

With sticky scroll enabled, opening or reusing an editor for a notebook containing dozens of code cells now starts up to 50 concurrent symbol-provider requests even when the Outline pane is closed. Sticky content waits for all requests, while the extension-host/CPU burst competes with the just-opened editor; disabling or switching notebooks cannot cancel it because CancellationToken.None is used.

**Evidence:** computeFullSymbols slices the code-cell collection to 50 and immediately pushes every cacheSymbols promise before Promise.allSettled. cacheSymbols creates a text-model reference and calls OutlineModelService.getOrCreate; on a cold/version-changed model, OutlineModel.create invokes every document-symbol provider, and extension providers cross mainThreadLanguageFeatures.ts to $provideDocumentSymbols. Notebook sticky rendering treats level 7+ entries as non-headers and skips them, while cached code symbols are created at level 8+, so this boundary work is not needed to render sticky markdown headers.

**Suggested direction:** For sticky scroll, call \`recomputeState()\` on attachment so the synchronous markdown-header entries are rebuilt, and leave \`computeFullSymbols\` gated to the Outline-pane code-symbol feature. If code symbols become required later, resolve only relevant visible cells through a cancellable bounded limiter and do not await the full batch before the initial sticky update.
