**Relevant issue families:** repeated-work, serialization-allocation, cache-lifecycle, boundary-fanout, concurrency-burst

### Scenario 1: Open or recompute a diff using the default built-in \`advanced\` algorithm

- Critical path: The diff view debounce completes, model synchronization and one \`$computeDiff\` IPC complete, the worker copies both models to line arrays and computes one built-in diff, then the reply is converted and rendered. Optional sampled verification was already on this path. The added fallback metadata and telemetry field do not add another computation or boundary call.
- Scaling input: One uncached computation per original/modified model version and options tuple; CPU and allocations scale with both documents. Exact repeated inputs are served by \`WorkerBasedDocumentDiffProvider.diffCache\`.
- Effective concurrency: A shared editor worker receives requests; each diff computation is synchronous once dispatch reaches it, so CPU-heavy computations serialize on the worker thread. The diff view debounces edits, but cancellation is checked only after the worker result, as before this change.
- Cache behavior: The provider's bounded result cache handles exact warm requests. Built-in backend resolution is synchronous and stateless; no package-module cache is involved. Cold and warm behavior are materially unchanged.
- Mechanism confidence: High: the algorithm guard in \`resolveLinesDiffComputerWithFallback\` prevents fallback for built-in algorithms, and the worker call path was traced end to end.
- Magnitude uncertainty: The exact document sizes and worker contention vary, but the diff introduces no additional document-sized work on this default path.
- Expensive boundaries:
  - IPC at <code>src/vs/editor/browser/services/editorWorkerService.ts:110</code>: Synchronize the two text models and invoke \`$computeDiff\`, then return compact line-change tuples.; cardinality: One request/reply per provider cache miss; model synchronization is handled by the existing model sync manager.

  - serialization at <code>src/vs/editor/browser/widget/diffEditor/diffProviderFactoryService.ts:126</code>: Log \`diffEditor.computeDiff\` telemetry with one additional small \`fallback\` enum field.; cardinality: One existing telemetry event per completed uncached computation; no additional event is emitted.

- Verdict: No reportable regression: this remains one computation and at most one pre-existing sampled verification per uncached request.

### Scenario 2: Compute a package-backed (\`advanced-external\` or \`advanced-wasm\`) diff successfully

- Critical path: On a cold worker, one dynamic module load and backend initialization must finish before model lines are read; then one external diff runs, optionally followed by the existing sampled verification, and the IPC reply completes. On a warm worker, the cached backend promise resolves without another module load. The new wrapper does not invoke the built-in algorithm when the package result is successful and valid or unverified.
- Scaling input: One external computation per effective provider cache miss. Computation and optional verification scale with document bytes/lines; verification is sampled, defaults to zero, and is restricted to models of at most 50,000 lines each.
- Effective concurrency: Concurrent cold calls share \`externalModulePromise\` and the per-WASM-mode \`externalComputers\` promise. After loading, synchronous computations execute on the single worker event loop rather than creating a CPU burst.
- Cache behavior: The provider result cache serves exact warm diff inputs. Package loading and backend construction are positively coalesced per worker and per \`useWasm\` mode; a worker restart creates a new cold load.
- Mechanism confidence: High: the external module and computer promises are explicitly cached, and the fallback branch is unreachable without a load/compute failure or sampled invalid result.
- Magnitude uncertainty: Backend load and diff duration depend on host and document shape, but their frequency and cardinality are unchanged on successful results.
- Expensive boundaries:

    - Introduced by diff: false; previous behavior: Identical worker IPC cardinality.; critical-path effect: Required before rendering the computed diff.
  - other at <code>src/vs/editor/common/diff/externalLinesDiffComputer.ts:16</code>: Dynamically import \`&#64;vscode/diff\` and initialize the JS or WASM backend.; cardinality: At most one module import per worker lifetime and one coalesced computer initialization per backend mode, regardless of concurrent callers.
    - Introduced by diff: false; previous behavior: The same cached dynamic import and initialization were awaited before computing.; critical-path effect: Cold package-backed diffs wait for loading; warm diffs reuse the promise.

- Verdict: No reportable regression: cold/warm boundary behavior and successful-path document-sized work are unchanged apart from negligible wrapper and metadata allocation.

### Scenario 3: A package backend fails to load or throws while computing

- Critical path: The failing package resolution or computation is observed and reported, then the built-in algorithm computes one replacement diff before the worker replies. This newly adds a built-in computation only on the failure path; with the default editor option it has its own 5-second computation bound, and exact repeated model versions can then be served from the provider result cache.
- Scaling input: One built-in fallback per uncached failed package diff. Cost scales with the two documents; there is no per-change or per-line boundary fan-out.
- Effective concurrency: A single worker runs fallback computation synchronously. Concurrent cold callers share the same package load promise; if that promise rejects, each distinct uncached request computes the fallback it needs, serialized on the worker.
- Cache behavior: The package's rejected load promise remains negatively cached, preventing repeated dynamic imports. A successfully returned fallback result is stored in the bounded provider diff cache for the same model versions/options.
- Mechanism confidence: High: the changed branches add exactly one fallback computation and no new boundary fan-out; cache and timeout behavior are explicit in the traced implementations.
- Magnitude uncertainty: The package failure rate and whether a computation throws early or near its timeout are unknown. A late throw can lengthen this degraded path, but no evidence establishes such failures as a realistic hot-path mechanism rather than the explicit recovery case.
- Expensive boundaries:
  - IPC at <code>src/vs/editor/browser/services/editorWorkerService.ts:110</code>: Invoke package-backed diff computation and return the built-in fallback result.; cardinality: One request/reply per provider cache miss, unchanged from before the diff.
    - Introduced by diff: false; previous behavior: The same RPC rejected when package loading or computation failed.; critical-path effect: Unlike the previous rejection, the RPC now waits for one built-in replacement computation so the diff editor receives a usable result.
  - other at <code>src/vs/editor/common/diff/externalLinesDiffComputer.ts:16</code>: Dynamically load and initialize the package backend.; cardinality: One coalesced attempt per worker lifetime; rejection is cached rather than retried per diff.
    - Introduced by diff: false; previous behavior: The same cached load was attempted, but its failure propagated instead of triggering built-in computation.; critical-path effect: The first failing request waits for the failed load; subsequent requests observe the cached rejection before fallback.
- Verdict: No reportable performance bug: the added work is the bounded, intentional recovery needed to replace a previously failed result, occurs only on package failure, and does not create unbounded retention, boundary fan-out, or concurrency amplification.

### Scenario 4: A sampled package diff is verified as invalid

- Critical path: One external diff and linear verification run first; only when verification returns \`invalid\` does the worker compute one built-in diff and verify that replacement before replying. This is the sole successful-computation path with repeated document-scale work, and it is gated by experimental sampling plus an invalid package result.
- Scaling input: At most one external diff, two verifications, and one built-in fallback for an uncached sampled-invalid request. Sampling defaults to zero and both models must have at most 50,000 lines; exact repeats are cached afterward.
- Effective concurrency: All CPU and allocation work is synchronous in the shared worker and therefore serialized. There is no Promise-all burst or per-change IPC.
- Cache behavior: Warm exact requests return the cached fallback result. Backend initialization remains coalesced. Unsampled requests neither verify nor fallback for invalidity.
- Mechanism confidence: High that the repeated CPU/allocation mechanism exists; lower confidence that it produces a meaningful regression because its trigger is narrow, bounded to one fallback, and is the feature's required replacement behavior.
- Magnitude uncertainty: Invalid-result prevalence and concrete document byte sizes are not established. The line cap does not strictly cap bytes, but the path additionally requires experiment sampling and an invalid backend output.
- Expensive boundaries:
  - IPC at <code>src/vs/editor/browser/services/editorWorkerService.ts:110</code>: Send one diff request and return one fallback result.; cardinality: One request/reply per provider cache miss, regardless of fallback.
    - Introduced by diff: false; previous behavior: The same sampled request performed the external diff and one verification, then returned the invalid result.; critical-path effect: The reply waits for external computation, both verifications, and built-in computation on sampled-invalid results.
  - serialization at <code>src/vs/editor/browser/widget/diffEditor/diffProviderFactoryService.ts:126</code>: Emit the existing telemetry event marking fallback=\`invalid\` and the replacement validity.; cardinality: One event per uncached computation, not one per algorithm attempt.
    - Introduced by diff: false; previous behavior: The same event reported the external result's validity without fallback metadata.; critical-path effect: Constant-size metadata only; no document content is serialized into telemetry.
- Verdict: No finding: although this intentionally repeats document-scale computation on sampled-invalid results, it is bounded to one replacement, sampled off by default, cached for exact repeats, and no evidence shows realistic latency or memory impact severe enough to make the required fallback mechanism independently defective.

No high-confidence actionable performance regression was found.
