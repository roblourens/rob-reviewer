### Scenario 2: Render an AI customization management editor screenshot fixture

- Critical path: Each render now defines one fixture-local DI instance containing constObservable(options.extensionsSectionBadge). For ordinary fixtures, Extensions is absent from managementSections, so badge resolution never touches this service. In the two Extensions fixtures, editor creation performs one DI lookup and reads the constant observable while building sidebar badge state.
- Scaling input: One small service object and constant observable per fixture render; badge work scales with configured management sections, whose fixture lists are fixed at about 8-9 entries, and only one Extensions entry can use the new service.
- Effective concurrency: Each fixture owns an isolated instantiation service. Badge evaluation is synchronous and once per active harness derivation; there is no Promise fan-out, queue, limiter, or cross-fixture shared mutable badge state.
- Cache behavior: The derived badge list resolves observables once per active harness and subsequent reads use the same constant observable. No external cache or repeated miss path is introduced.
- Mechanism confidence: High: the transitive call path is defineInstance -&gt; registry getBadge -&gt; accessor.get -&gt; const observable read, all in memory; the contribution is not initializeOnEditorOpen and its widget creation is a no-op.
- Magnitude uncertainty: Exact number of fixture/theme renders depends on the fixture runner selection, but cost remains constant per render and does not reach an expensive boundary.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added per-render object allocation and DI lookup are bounded test-fixture overhead, while default fixtures do not include the contributed section.
