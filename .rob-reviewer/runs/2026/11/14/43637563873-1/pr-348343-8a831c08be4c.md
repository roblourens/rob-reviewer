### Scenario 1: Selecting a persisted pinned canvas whose chat no longer publishes that canvas after restart

- Critical path: The pin first observes cached/live chat membership. If membership is authoritative and missing, the selection waits for renderer-to-provider openCanvas dispatch, Agent Host chat restoration if cold, optional runtime refresh, and the SDK canvas.open/provider activation before membership can publish and the page can bind. The 10-second publication timer is only a post-open bound and does not add work to the success critical path.
- Scaling input: One request per selected missing pin, coalesced by the pin's \_reopen state; persisted pins are capped at five. Explicitly selecting again after failure retries, and rapid selection of different pins can leave up to five independent requests in flight.
- Effective concurrency: Each pin coalesces its own reopen while in flight or awaiting publication. Agent runtime resolution/restart is serialized by the per-chat queue; the subsequent canvas RPC is not globally limited, but product cardinality is capped at five and ordinary interaction selects pins serially.
- Cache behavior: Warm membership containing the instance binds without an open. Authoritative missing membership triggers one open; successful publication binds and ends observation. Failure/timeout is negatively held as Unavailable until another explicit show. After process restart live canvas membership is intentionally not persisted, so this is a cold path.
- Mechanism confidence: High: the added reopenCanvas call reaches renderer/Agent Host IPC and SDK canvas.open; guards, cap, and retry lifecycle are explicit in code and tests.
- Magnitude uncertainty: Provider startup duration varies by extension and remote host. The request is user-initiated, capped, coalesced per pin, and replaces a previously nonfunctional path, so the added cost is bounded and required rather than a reportable regression.
- Expensive boundaries:

### Scenario 2: Sending the next turn, or opening a canvas while idle, after chat canvas enablement changes

- Critical path: On every existing turn-refresh path the new in-memory canvas-enable mismatch check can select a restart reason. A mismatch destroys and resumes the SDK session before the turn proceeds. An idle open performs the same refresh before canvas.open; listing canvases explicitly does not refresh. If no mismatch exists, the added check is an in-memory boolean/config lookup after pre-existing refresh work.
- Scaling input: One restart per live chat whose launch-time canvas mode differs from current configuration, paid on that chat's next turn or idle canvas open. Once relaunched, the stored wrapper flag matches and later operations do not restart for this reason.
- Effective concurrency: Refresh and replacement are serialized by each chat's queue. A setting change does not eagerly fan out across sessions; separate chats restart only as users next operate them.
- Cache behavior: The launch-time mode is retained on CopilotSessionWrapper and compared to current root configuration. Matching warm sessions take no restart. Cold sessions launch directly with current configuration. The state transition acts as a one-shot invalidation until replacement.
- Mechanism confidence: High: the new reason is directly in the refresh decision and replacement path, with per-chat queueing and wrapper state proving one-shot behavior.
- Magnitude uncertainty: Runtime resume latency and the number of simultaneously warm chats vary, but no bulk restart is scheduled and ordinary no-change turns add only a constant in-memory comparison.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:8652</code>: Read stored working-directory/session refresh state as part of the pre-existing refresh check; cardinality: Once per turn refresh, unchanged by this diff.
    - Introduced by diff: false; previous behavior: The same stored-directory read and snapshot work already ran for refresh checks.; critical-path effect: Already on the turn preparation path before the new mismatch reason is evaluated.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:8779</code>: Destroy and resume/relaunch the Copilot SDK runtime when canvas enablement mismatches; cardinality: Once per affected live chat per actual configuration transition, deferred until next use.
    - Introduced by diff: true; previous behavior: Canvas setting changes did not trigger runtime replacement, so turns continued on the stale launch mode.; critical-path effect: Blocks that first turn or idle open so it uses a correctly configured runtime; subsequent operations reuse the replacement.
- Verdict: No finding. The restart is a bounded, deferred configuration transition required for correct runtime capabilities; it is not repeated after replacement and does not eagerly fan out.

### Scenario 3: Retrying a pinned-canvas reopen after extension consent was declined

- Critical path: The notification action sends one retryDeniedConsent open and then shows/reconnects the pin. If membership has not propagated when show runs, the reconnect path can issue another stable-instance open; publication may otherwise bind immediately.
- Scaling input: Consent retry is per explicitly clicked notification action for one pin. The normal reopen remains coalesced; the edge can produce at most two sequential stable-instance opens for that action, with total pins capped at five.
- Effective concurrency: The retry open is awaited before show. A possible follow-up is sequential for that pin, not a burst; different user actions/pins can overlap but require separate interaction.
- Cache behavior: If the first retry publishes membership before resolving, show binds from warm membership and sends no follow-up. If response precedes publication, stable instance identity lets the runtime focus/reuse the same canvas on a follow-up. Declined state is not automatically retried.
- Mechanism confidence: Medium-high for the possible second call, lower for concrete performance impact because runtime deduplication cost is not evidenced.
- Magnitude uncertainty: The repository explicitly supports response-before-publication, but the cost of a second stable-instance open after the first succeeds is not established; it may be an inexpensive idempotent focus. The trigger also requires a prior denial plus an explicit retry.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/canvases/browser/pinnedCanvasService.ts:672</code>: Retry renderer-to-Agent Host openSessionCanvas with extension-consent retry; cardinality: One explicit retry IPC; potentially one additional stable-instance IPC if publication lags behind the response.
    - Introduced by diff: true; previous behavior: Pinned canvases had no consent-aware reopen or retry path.; critical-path effect: The first retry is required to relaunch/authorize the extension; a possible follow-up occurs while waiting for membership.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:5372</code>: SDK rpc.canvas.open for the retried stable instance; cardinality: Normally one; at most two sequential calls in the response-before-publication edge.
    - Introduced by diff: true; previous behavior: No pinned-canvas retry invoked the SDK open boundary.; critical-path effect: Provider authorization/activation and opening must complete before the pin can become live.
- Verdict: No finding. Although a narrow sequential duplicate call is possible when publication lags, the trigger is rare, bounded, user-driven, and the diff does not establish a concrete user-visible performance degradation from the idempotent second open.
