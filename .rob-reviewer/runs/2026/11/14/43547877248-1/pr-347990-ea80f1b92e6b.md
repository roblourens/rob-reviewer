# Performance review: sessions: add Close Others to the chat tab context menu

[PR #347990](https://github.com/microsoft/vscode/pull/347990) at `ea80f1b92e6bb095be0b2a946cf7dd832a29c752`

## Findings (1)

### 1. [medium] Publish the batch close only once

**Finding ID:** `PERF-FC23DC12CECC`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/sessionsActions.ts:1247</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** DOM nodes, tab actions/listeners/observables, reconciliation CPU, temporary arrays/sets/JSON, and workspace storage operations  
**Scaling:** Closing T chats triggers T reconciliations and rebuilds T-1 through zero remaining tabs, producing O(T^2) widget construction; a split layout can also be serialized and stored T times.  
**Outcome:** Synchronous UI latency, CPU and GC pressure, and repeated storage I/O  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Close Others did not exist, so no single context-menu action synchronously published all other tab closures one at a time. Close All already used an equivalent loop, and this refactor preserves that pre-existing cost while newly applying it to Close Others.  
**Changed behavior:** The added shared helper loops over every target chat and awaits an individual close or delete, publishing a distinct visibility update for each committed chat.  
**Confidence:** 0.97 — The individual publication, reconciliation autorun, full tab rebuild, and per-reconcile persistence paths are directly traced. Only the exact latency depends on realistic tab and group counts.

**Causal diff evidence:** The added \`for (const chat of chats)\` at line 1247 makes both batch gestures execute as a sequence of individual state changes; the new Close Others action calls this helper with all other strip chats.

Closing the other tabs in a large strip can block the UI while the remaining tab strip and group layout are reconstructed repeatedly instead of once.

**Evidence:** Every committed iteration reaches SessionsService.closeChat and SessionSlotState.closeChat, which clones and publishes \`\_closedChatUris\` in its own transaction. That publication reruns ChatGroupsView reconciliation and, for the affected group, ChatCompositeBar \`\_rebuildTabs\`, which clears and recreates every remaining tab widget and listener. Split layouts also call \`\_persistLayout\`, parsing, serializing, and storing layout state after each publication.

**Suggested direction:** Provide a batch visibility-close operation that computes and publishes the final closed/shown sets and persisted state once in one transaction, causing one reconciliation and tab rebuild; keep required ordering for draft deletion and external-host closure.

- Verdict: No separate finding. The fan-out is real but distinct resources require deletion, no bulk provider API was found, and realistic draft cardinality is not established; batching the local visibility updates remains the actionable regression.
