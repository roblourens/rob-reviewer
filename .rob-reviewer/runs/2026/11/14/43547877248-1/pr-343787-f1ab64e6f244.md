## Findings (1)

### 1. [medium] Defer opener probing to the active chat

**Finding ID:** `PERF-450EE6D78FAB`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionChatInputToolbar.ts:617</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Extension activation work and extension-host \`$canOpenUri\` IPC calls  
**Scaling:** For each loaded chat group, the toolbar probes every deduplicated pull-request URI concurrently; after HTTPS activation is coalesced once, warm checks still issue one \`canOpen\` RPC per URI per registered opener, with no cache shared across chat groups.  
**Outcome:** Background extension activation and IPC/CPU bursts during session restoration or chat switching, increasing contention and latency as split chats and referenced pull requests grow.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The removed \`sessions.sessionActivityBar.showGitHubActions\` gate defaulted to false, so ordinary session views did not evaluate \`activityBarOpeners\` and performed no opener activation or support IPC until users explicitly opted in.  
**Changed behavior:** The new condition evaluates opener support whenever pills are visible. Every enabled \`SessionActivityBar\` observes each group's \`activityBarActions\` even when that bar is marked inactive, so loading a chat with PR references now starts these checks automatically.  
**Confidence:** 0.97 — The changed default gate, lazy-observable subscription, extension activation, and per-opener RPC call path are all explicit in repository code. The exact wall-time varies with installed opener extensions and session size, so severity is medium rather than high.

**Causal diff evidence:** RIGHT line 617 removes the former \`\!gitHubActionsEnabled.read(reader)\` short-circuit. Since the removed setting defaulted to false, this line newly allows the existing per-reference \`getOpener\` loop to execute automatically for normal chats.

Opening or restoring an Agents window with PR-bearing split chats can activate HTTPS opener extensions (including the built-in Simple Browser) and fan out extension-host support checks for hidden/inactive activity bars. Rendering is not awaited, but this newly eager work competes with restoration and retains the activated extension for the window lifetime.

**Evidence:** \`activityBarActions\` reads \`activityBarOpeners\`, which maps each ref through \`externalUriOpenerService.getOpener\`. That service calls each provider's \`getOpeners\`; \`MainThreadUriOpeners.getOpeners\` awaits \`activateByEvent('onOpenExternalUri:https')\`, and validation invokes \`proxy.$canOpenUri\` for every registered opener. \`ChatGroupView\` installs the observable on each group's \`SessionActivityBar\`, whose autorun reads it whenever the activity-bar setting is enabled; \`setActive\` only changes CSS and does not stop observation. \`getSessionGitHubReferences\` deduplicates within one chat, but there is no cross-group result cache.

**Suggested direction:** Keep automatic visibility, but start support probing only for the currently active, enabled activity bar and coalesce/cache checks by URI across chat toolbars; invalidate the shared results on extension or external-opener configuration changes.
