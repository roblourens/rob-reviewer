<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, cleanup-lifecycle, eager-work

### Scenario 1: Workbench startup with \`window.menuBarVisibility: compact\` and the Activity Bar location set to \`hidden\`

- Critical path: Initial layout evaluates title-bar visibility and menu ownership, then synchronously creates one \`CustomMenubarControl\` in the title bar. This work must complete before the compact menu is usable, but it is bounded to one control and one title-bar layout.
- Scaling input: One main window and one compact menu; cost does not scale with files, editors, menu items at this ownership layer, or auxiliary-window count.
- Effective concurrency: Single-threaded UI initialization; no queue, parallel fan-out, or concurrency burst is introduced.
- Cache behavior: No cache or miss path is involved. Configuration reads are direct service lookups; cold and warm behavior have the same bounded cardinality.
- Mechanism confidence: High: the changed predicate directly transfers ownership from the hidden Activity Bar to the title bar, and the title-bar visibility branch is directly reached during initial layout.
- Magnitude uncertainty: Exact DOM/layout duration varies by platform, but the diff relocates one existing menu control and makes one existing title-bar part visible rather than adding collection-scaled work.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added synchronous UI work is constant and required to expose the menu; before the diff the existing control was owned by the hidden Activity Bar, while after it is owned by the title bar. No subprocess, IPC, filesystem, database, network, or new serialization boundary is reached.

### Scenario 2: Runtime changes among default, top, bottom, and hidden Activity Bar locations or custom-title-bar visibility modes

- Critical path: A configuration event synchronously updates Activity Bar and title-bar menu ownership, disposes the prior menu control when ownership changes, creates the replacement, and performs a bounded relayout before the setting change is visually settled.
- Scaling input: Number of relevant configuration transitions, with constant work per transition; no per-editor, per-file, or per-menu-entry boundary fan-out is added.
- Effective concurrency: Configuration listeners execute on the UI thread; installation is guarded against duplicates and ownership remains one control at a time. There is no aggregate parallel work.
- Cache behavior: No cache is used. Each actual relevant configuration event performs one ownership check; repeated identical installation is suppressed by existing \`menubar\` guards.
- Mechanism confidence: High: changed ownership for \`hidden\` reaches the existing install/uninstall paths in both parts, whose disposal and duplicate guards were inspected.
- Magnitude uncertainty: Menu creation and relayout cost are platform-dependent, but the trigger is an infrequent explicit setting change and cardinality is one menu per main window.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff adds a bounded ownership transfer when entering or leaving \`hidden\`, analogous to the existing top/bottom transfer, with explicit cleanup and no retained duplicate control or external expensive boundary.

### Scenario 3: Entering or leaving fullscreen with a hidden Activity Bar and compact menu

- Critical path: The fullscreen event updates layout state and synchronously calls \`shouldShowCustomTitleBar\`; the changed emptiness rule keeps the main-window title bar visible and the grid lays it out. The menu remains available on the same UI critical path.
- Scaling input: One title-bar subtree per main window and one visibility evaluation per fullscreen transition; auxiliary windows are explicitly excluded.
- Effective concurrency: One fullscreen event is processed synchronously for the main window. Activity Bar ownership checks and grid visibility updates are serialized on the UI thread.
- Cache behavior: No cache or coalescing layer is involved. The visibility calculation is constant-time configuration and window-state lookup for every fullscreen transition.
- Mechanism confidence: High: the added \`isTitleBarEmpty\` branch directly changes the fullscreen grid visibility decision for exactly the main-window compact/hidden configuration.
- Magnitude uncertainty: Keeping the title bar visible has a small persistent rendering/layout footprint whose exact cost is not measured, but it is one existing DOM subtree and does not grow with workspace size or event frequency beyond fullscreen transitions.
- Expensive boundaries: none found
- Verdict: No reportable regression. The constant rendering footprint is the intended host for the compact menu, and the diff introduces no repeated geometry read/write loop, frame-frequency work, external boundary, or unbounded allocation.

### Scenario 4: Opening the compact menu by mouse or Alt mnemonic while the Activity Bar is hidden

- Critical path: Input reaches the existing \`CustomMenubarControl\` now hosted in the title bar; popup direction is selected synchronously and the existing menu rendering path runs. No new prerequisite boundary is added by the diff.
- Scaling input: One popup per user input; menu item count is unchanged from the pre-diff \`CustomMenubarControl\`.
- Effective concurrency: One input event and one popup; existing menu interaction is serialized on the UI thread.
- Cache behavior: Ownership and popup-direction checks read current configuration directly. The diff does not alter menu-model caching, invalidation, or item enumeration.
- Mechanism confidence: High: the only changed production behavior on this path is the ownership predicate, while the popup implementation remains unchanged.
- Magnitude uncertainty: Actual menu size varies, but the diff does not change item cardinality or rendering behavior; it only changes which existing container owns the control.
- Expensive boundaries: none found
- Verdict: No reportable regression. Richer reachability of the existing menu does not increase its per-open work, boundary count, concurrency, or retained state.

**Summary:** Completed the performance pass over all five changed files and traced startup, configuration handoff, fullscreen layout, and menu-input scenarios. The production change adds \`hidden\` to an existing constant-time ownership predicate and keeps one existing title-bar subtree visible when needed. Install/uninstall lifecycle remains bounded and guarded, and no subprocess, IPC, filesystem, database, network, collection fan-out, unbounded retention, or hot-loop mechanism was introduced. No performance finding or regression-fix record is warranted.
