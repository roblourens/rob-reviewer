### Scenario 1: Cold-opening an existing Copilot CLI chat through /code and restoring its draft model configuration

- Critical path: The existing session and chat subscriptions must hydrate, history must be restored, and the remote chat model must publish before the chat is usable. The diff only reads the already-hydrated draft model config and carries the same small object into intended-model state; it adds no await or boundary to this path.
- Scaling input: History size controls pre-existing replay/conversion work, while the added selectedModelConfiguration has only the model's bounded picker keys and is retained once per open session.
- Effective concurrency: Session and chat hydration are awaited sequentially as before. ChatService coalesces concurrent loads per session resource in \_remoteSessionLoads, and warm opens reuse the existing model.
- Cache behavior: A warm open acquires the existing ChatModel. Cold concurrent opens are coalesced by session resource; canceled loads are sequenced before retry. The added configuration has no cache or negative-cache behavior.
- Mechanism confidence: High: the changed lines perform direct property reads and retain/pass one bounded configuration object after existing hydration.
- Magnitude uncertainty: Exact subscription latency and history size vary, but the diff does not add calls, waits, history scans, or copies proportional to history.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:provideChatSessionContent</code>: Hydrate the existing backend session and chat subscriptions.; cardinality: At most one session-channel and one chat-channel hydration for a cold open; existing subscriptions can be reused.
    - Introduced by diff: false; previous behavior: The same session and chat subscriptions were hydrated and awaited; the draft's model configuration was simply not retained in transferredState.; critical-path effect: Both hydrations are already on the cold-open critical path before draft and history conversion.
  - IPC at <code>src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:loadRemoteSession</code>: Resolve the chat-session provider content via getOrCreateChatSession.; cardinality: One provider load per session resource after coalescing concurrent consumers; zero on a warm cached-model hit.

- Verdict: No reportable regression. The critical-path boundaries and their cardinality are unchanged, and the added local work is constant and small.

### Scenario 2: Importing/resuming a Copilot CLI session and deriving the picker selection from the runtime model tier

- Critical path: The existing in-use check, optional bounded release polling, session resume, mode adoption, and runtime-selection read must complete before import returns. The diff adds a model-catalog lookup and filtering only when the runtime context tier is unset.
- Scaling input: The newly reached local work scans the loaded model catalog once and filters one model's small context-size enum; it does not scale with history, turns, or sessions beyond one execution per import.
- Effective concurrency: Import work is serialized by the existing per-chat queue/sequencer. Release polling is sequential and capped by IMPORT\_SESSION\_RELEASE\_POLLS.
- Cache behavior: The existing Copilot client and resolved chat session are reused when available. If model metadata is not loaded, the helper returns undefined without retries or new boundary work.
- Mechanism confidence: High: \_contextSizeForTier now reaches \_contextSizeWindows for an unset tier, which performs one Array.find and one small enum filter with no I/O.
- Magnitude uncertainty: Catalog size can vary, but it is a bounded UI model catalog and this work occurs once per explicit import, not per token, turn item, or frame.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:importChat</code>: Check whether the SDK session is in use, potentially poll, resume the session, adopt modes, and read runtime selection.; cardinality: One initial checkInUse call, a bounded number of retry checks only while another client still holds the session, and one runtime selection read for a successful import.
    - Introduced by diff: false; previous behavior: The same calls and sequencing occurred; an unset context tier skipped only the subsequent local context-window derivation.; critical-path effect: These existing RPCs are on the import critical path.
- Verdict: No reportable regression. The added O(model-catalog-size) local lookup is low-frequency and bounded, while all RPC cardinality remains unchanged.

### Scenario 3: Refreshing and displaying a running session's managed model configuration

- Critical path: A refresh resolves managed settings, lists runtime models, reads the current model, builds a report, publishes changed session configuration, and reactively updates the chat input picker. The diff changes provider-id matching, default-tier projection, and key precedence but does not schedule another refresh.
- Scaling input: Report construction remains O(number of catalog models times the three supported option keys). UI application remains O(reported model IDs times schema/default keys). The changed current config adds only bounded primitive fields.
- Effective concurrency: Refreshes are serialized through \_modelConfigurationRefresh; a generation check drops stale results. Publishing is deep-equality guarded, and ChatModelConfigurationStore also ignores equal reports.
- Cache behavior: Equal reports are suppressed both before session-config publication and in the UI store. Warm unchanged reports therefore do not retrigger reconciliation; failures publish undefined as before.
- Mechanism confidence: High: callers, sequencer, generation guard, equality checks, and reactive consumer were traced directly.
- Magnitude uncertainty: Model catalog size varies, but effective option cardinality is fixed at three and no changed line increases refresh frequency or boundary fan-out.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_refreshManagedModelConfiguration</code>: Resolve managed settings and invoke session.model.list plus session.model.getCurrent.; cardinality: One settings resolution, one model-list RPC, and one current-model RPC per pre-existing refresh trigger; queued refreshes execute serially and stale generations do not publish.
    - Introduced by diff: false; previous behavior: The same refresh triggers and RPC sequence existed; the report could fail to match a Copilot-provider current model and omitted contextSize for an unset tier.; critical-path effect: These operations gate configuration-report publication but are not newly placed on chat rendering or message-send paths by this diff.
  - serialization at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_publishModelConfiguration</code>: Compare and publish the per-chat model configuration through session config state.; cardinality: At most one publication per materially changed report; equal reports are suppressed.
    - Introduced by diff: false; previous behavior: The same report object was compared and published; the changed report contains at most a few additional primitive config fields.; critical-path effect: Publication drives a reactive picker update after the RPC refresh completes.
- Verdict: No reportable regression. Existing boundary work remains serialized and deduplicated; additional report data and local reconciliation are bounded.

### Scenario 4: Applying a runtime configuration report to a started chat whose inherited preferences were never explicitly selected

- Critical path: A reactive session-report change synchronously reconciles model configurations and fires one batched change event before the picker rerenders.
- Scaling input: Existing reconciliation scales with the union of override and reported model IDs and each model's schema keys. The diff adds one \_ownKeys lookup and, only when absent, an empty Set allocation for the current model's runtime application.
- Effective concurrency: The UI update runs synchronously on one report notification, but equal reports return early and all affected model IDs are notified in one event.
- Cache behavior: Deep equality suppresses unchanged snapshots. The configuration store keeps per-model overrides and own-key sets for the editor lifetime; the new fallback Set is temporary and not retained.
- Mechanism confidence: High: the changed branch and all call sites were inspected; there is no new boundary, listener, per-frame path, or unbounded retention.
- Magnitude uncertainty: Report frequency depends on runtime configuration changes, but unchanged reports are suppressed upstream and locally.
- Expensive boundaries: none found
- Verdict: No reportable regression. The extra synchronous work is constant per affected current model and remains behind existing report deduplication.
