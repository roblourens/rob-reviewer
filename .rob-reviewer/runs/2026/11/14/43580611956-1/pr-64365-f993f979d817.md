## Findings (1)

### 1. [medium] Avoid rebuilding the menubar on every resize layout

**Finding ID:** `PERF-9221A56EAC92`  
**Location:** <code>src/vs/workbench/browser/parts/titlebar/menubarControl.ts:605</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** DOM reconstruction, synchronous style/layout calculation, and transient SubmenuAction objects  
**Scaling:** Cost grows with the number of raw resize events and top-level menus; overflow additionally allocates actions for each hidden top-level menu on every event.  
**Outcome:** Higher synchronous resize latency, CPU/GC pressure, and dropped resize frames  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, MenubarControl.layout only set the container height and adjusted visibility; it did not rebuild labels or scan menu widths on each workbench layout.  
**Changed behavior:** Every titlebar layout now calls MenuBar.update, which rewrites every top-level label and synchronously recalculates overflow.  
**Confidence:** 0.97 — The resize-to-layout call chain and the synchronous DOM reads/writes are explicit in repository code. The exact millisecond cost varies by platform and extension-contributed menu state, but execution on every resize event is certain.

**Causal diff evidence:** The added call at MenubarControl.layout line 605 places MenuBar.update on every titlebar layout; the deleted implementation at the same method only updated height and visibility.

Dragging the window edge can spend each raw resize event rebuilding menu DOM, forcing layout, and allocating overflow actions, increasing resize latency and causing visible frame drops.

**Evidence:** Electron's window resize listener calls shell.layout synchronously; WorkbenchLayout then calls titlebar.layout, which reaches this added line. MenuBar.update assigns innerHTML for every cached menu and calls updateOverflowAction; that method reads container/menu offsetWidth values while changing visibility and moving the overflow node, so style/layout work is forced on the resize critical path. When overflow is active it also recreates one SubmenuAction per hidden top-level menu.

**Suggested direction:** Keep resize handling to an overflow-only layout method, cache the last available width, and skip work when it is unchanged. Update labels only when mnemonic/options change, and batch width reads before visibility/node writes (or coalesce the relayout to one animation frame).
