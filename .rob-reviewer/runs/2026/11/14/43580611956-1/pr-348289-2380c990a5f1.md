## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/base/browser/ui/menu/menubar.ts:448` (`RIGHT`)  
**Blamed base line:** `src/vs/base/browser/ui/menu/menubar.ts:442`  
**Introducing path:** `src/vs/base/browser/ui/menu/menubar.ts`  
**Introducing commit:** `95b5f886572fbf5b23572840d88c16cc3634389b`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.95

**Mechanism:** Disposing a MenuBar with an open, focused menu could synchronously emit focus loss before host listeners were disposed; CustomMenubarControl could re-enter setupCustomMenubar and allocate/register a replacement during the enclosing DisposableStore.clear(), losing normal lifecycle ownership and retaining the replacement DOM/listeners.

**Symptom:** Repeated menubar replacement while a menu is open could leak reconstructed MenuBar instances, DOM nodes, event listeners, and action/menu state, causing retained-memory growth across reinstallation cycles.

**Fixed behavior:** The new isOpen branch invokes cleanupCustomMenu() before super.dispose(). cleanupCustomMenu first moves focus back to the menu button inside the same container, removes the holder/widget, and clears menu disposables without transitioning focusState, so host focus listeners cannot reconstruct the menubar during disposal. super.dispose() then tears down the remaining listeners and emitters once, bounding the lifecycle to the single instance being disposed.

**Evidence:** Before this PR, MenuBar.dispose() entered super.dispose() while an open menu still owned the focused holder/widget. menuDisposables is the first registered disposable (line 91), so super disposal tears down that focused menu before the container FOCUS\_OUT listener and \_onFocusStateChange emitter are disposed. The focus-out path calls setUnfocusedState(), which fires onFocusStateChange(false); CustomMenubarControl's listener at menubarControl.ts:527 responds by calling setupCustomMenubar(true) when pendingFirstTimeUpdate is set, re-entering reinstallDisposables.clear() and constructing another MenuBar during disposal. The added test exercises open-menu disposal and verifies that no focus/visibility host events escape. This is a concrete re-entrant allocation/listener retention path, not merely an optimization label.

### Scenario 3: Dispose or reinstall a MenuBar while a menu is open

- Critical path: MenuBar.dispose now synchronously calls cleanupCustomMenu before super.dispose, moving focus within the container, removing the current holder/widget, and clearing menu disposables. This cleanup is part of disposal and prevents host focus listeners from reconstructing a menubar during the enclosing DisposableStore.clear.
- Scaling input: Number of open-menu reinstall/disposal cycles. Before the fix, retained MenuBar DOM/listener/action state could grow with repeated cycles; after the diff, disposal remains bounded to the current menu and instance.
- Effective concurrency: Synchronous, single-threaded disposal. Before the fix, focus loss could re-enter CustomMenubarControl.setupCustomMenubar during store clearing; the changed ordering eliminates that nested reconstruction rather than adding concurrency.
- Cache behavior: No cache applies. The open menu's DOM/widget is cleaned exactly once; a closed menu skips the new branch. No negative-cache or coalescing behavior exists on this path.
- Mechanism confidence: High: menuDisposables is registered before emitters/listeners, focus-out fires focusState notifications, the host listener can call setupCustomMenubar(true), and the new pre-super cleanup avoids that state transition. The regression fix was recorded against introducing commit 95b5f886572fbf5b23572840d88c16cc3634389b.
- Magnitude uncertainty: How often users trigger menubar reinstallation while a menu is open is uncertain, but the lifecycle mechanism and retained-resource risk of the old re-entrant path are directly evidenced. This PR reduces rather than increases that cost.
- Expensive boundaries: none found
- Verdict: Performance improvement, not a finding against the PR. The change closes a cleanup-lifecycle leak/re-entrant allocation path while adding only the necessary one-time cleanup when disposal occurs with an open menu.
