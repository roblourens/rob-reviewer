### Scenario 4: Move keyboard focus through the customization rows while a More/Less menu update replaces the focused item

- Critical path: Each focus-in scans the current toolbar rows to remember the focused index; a replacement checks connectivity and, only if browser focus is otherwise lost, focuses the corresponding new row before the existing DOM scan/layout notification.
- Scaling input: The scan is bounded by the static toolbar size (at most roughly 11 rows including Overview and More/Less), once per focus-in; replacement work is once per menu update.
- Effective concurrency: A single microtask handles ambiguous focus-out; menu updates and focus restoration remain serialized on the UI thread with no queued accumulation.
- Cache behavior: Only one focused HTMLElement/index pair is retained and cleared when focus leaves or after restoration; no collection or lifetime growth exists.
- Mechanism confidence: High: event listeners, toolbar cardinality, microtask, and restoration conditions are directly visible.
- Magnitude uncertainty: Exact browser focus-event ordering differs by window state, but the bounded loop and single-element retention are explicit.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added synchronous DOM work is tiny, fixed-cardinality, and limited to keyboard focus/menu replacement events.
