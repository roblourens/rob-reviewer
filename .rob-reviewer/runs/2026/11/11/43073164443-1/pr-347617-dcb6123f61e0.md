### Scenario 1: Open or reload a chat window and restore a user-arranged grid

- Critical path: The service synchronously reads the existing size record and the new arrangement record before constructing ChatWindowGrid; arrangement validation and the first grid restore/layout must finish before the auxiliary window is laid out.
- Scaling input: Each arrangement lookup scans at most 200 stored chats, and each accepted arrangement contains only the chat, main part, and optional two chrome cells; restored grid work scales with the current small cell tree.
- Effective concurrency: One synchronous construction path per opened auxiliary chat window; separate window opens are serialized per chat by the existing keyed sequencer, with no new aggregate remote-operation burst.
- Cache behavior: PerChatMemory reparses the in-memory storage string on each get and has no parsed-object cache, but records are capped at 200 and invalid/cold entries fall back once to the default arrangement. There is no network/filesystem cache miss on this path because storage get reads the initialized storage cache.
- Mechanism confidence: High: the constructor call path, 200-entry cap, validation, and synchronous grid restoration are explicit in the changed code.
- Magnitude uncertainty: Exact stored JSON size and number of concurrently opened chat windows vary, but accepted arrangement trees are structurally restricted to the window cells.
- Expensive boundaries: none found
- Verdict: No reportable regression: the added startup work is bounded to one small cached-storage scan and one small grid restore per opened chat window, without expensive boundary fan-out.

### Scenario 2: Hide/show chat or editor parts, change split layout, and let terminals join, move, empty, or refill

- Critical path: Observable updates synchronously serialize and compare the small grid, toggle visibility, and sometimes resize or rebuild grid rows before the layout-mode or terminal-state transition completes.
- Scaling input: Work scales with the number of grid cells and created editor parts. Normal grids have chat, main, terminal, and up to two chrome cells; serialization is triggered by user/state transitions rather than every frame of sash movement.
- Effective concurrency: Updates run synchronously through one autorun and PartGrid event chain per window; no promises, queues, subprocesses, IPC, filesystem, database, or network calls are reached.
- Cache behavior: The pre-hide and pre-first-terminal serialized snapshots are retained in memory and replaced on relevant arrangement changes, then cleared when both parts show, split layout changes, reset occurs, or terminals first show.
- Mechanism confidence: High: event sources and snapshot lifecycle are directly traceable through the changed methods and PartGrid's arrangement event.
- Magnitude uncertainty: Users can create extra editor parts, but realistic cell counts are low; the retained created-ID set could grow only through repeated create-resize-close cycles while a part remains hidden and is released on ordinary mode/layout transitions or disposal.
- Expensive boundaries: none found
- Verdict: No reportable regression: synchronous tree work is bounded and gesture/state-driven, and retained snapshots have clear lifecycle exits under realistic use.

### Scenario 3: Periodic storage flush, focus loss, shutdown, reset, or auxiliary-window unload persists sizes and arrangements

- Critical path: Each open chat window's synchronous onWillSaveState/onBeforeUnload handler exports the grid, parses the capped per-chat arrangement list, and stringifies/stores it when custom; this completes before the storage flush or unload proceeds. The backend database flush occurs afterward and is off the synchronous export/serialization portion.
- Scaling input: CPU/allocation scales with open chat-window count times at most 200 small stored arrangements; persisted history is capped and each exported arrangement strips terminals and dynamically created parts.
- Effective concurrency: Storage listeners run synchronously and sequentially on the main thread; open windows do not issue concurrent arrangement writes, and the final backend flush handles queued storage updates.
- Cache behavior: PerChatMemory has no parsed cache, but storage itself is initialized/cached; set rewrites the capped list, while delete now negative-checks and skips unchanged absent records.
- Mechanism confidence: High for the synchronous per-window serialization and introduced storage operation; medium for physical database-write cardinality because the storage backend buffers same-key updates.
- Magnitude uncertainty: The maximum practical count of simultaneously open chat windows is not explicit, but the per-record tree and retained history are tightly bounded; exact backend write coalescing is implementation-dependent.
- Expensive boundaries:

- Verdict: No finding: this adds bounded periodic serialization and one buffered workspace-storage key, but evidence does not establish user-visible latency or excessive I/O under realistic open-window counts.

### Scenario 4: Add an initially invisible part-grid cell, including empty terminal/editor parts

- Critical path: PartGrid computes the reference/edge extent and inserts the cell with Sizing.Invisible or a serialized visible:false node during the explicit add operation, then performs the existing visibility/look update.
- Scaling input: Cost scales with explicit cell additions and, for edge rebuild cases, the current grid tree size; it is not on scroll, typing, frame, or resize loops.
- Effective concurrency: Single synchronous grid mutation per added cell; no asynchronous or external boundary work.
- Cache behavior: No cache is involved; visibility is derived from the current cell state and immediately committed to the grid.
- Mechanism confidence: High: the changed addCell/addAtEdge branches and PartGrid arrangement event are explicit.
- Magnitude uncertainty: Other PartGrid consumers may have different small cell shapes, but changed behavior applies only to cells already determined not to show.
- Expensive boundaries: none found
- Verdict: No reportable regression: the extra model reads and visibility flagging are constant/small-tree work on a cold structural mutation and avoid the prior visible-then-hidden relayout.
