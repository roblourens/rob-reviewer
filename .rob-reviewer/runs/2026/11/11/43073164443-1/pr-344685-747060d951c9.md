## Performance regression fixes detected (1)

### 1. boundary-fanout

**Fix location:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostResponseFileChanges.ts:424` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostResponseFileChanges.ts:417`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostResponseFileChanges.ts`  
**Introducing commit:** `a8c1541df5a2123e56282a0f286861c872b569c8`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `ipc`  
**Confidence:** 0.99

**Mechanism:** An observed response-file-changes value with an initially unresolved backend chat created and retained one Agent Host subscription for every chat in the session catalog, including archived chats, instead of subscribing only the response's chat.

**Symptom:** Opening or reconnecting a session with many catalog chats caused subscription IPC, host-side subscription state, and chat snapshot work to scale with the full catalog for one response.

**Fixed behavior:** When a response's backend chat is not resolved at request time, the provider now waits for the session snapshot, resolves that exact chat, and maps only a singleton URI rather than every catalog chat.

**Evidence:** The deleted base line built a mapped source for every URI in source.chatUris, and each mapping calls \_getChatSource(chatUri), which acquires a chat subscription. The added resolver instead derives a singleton URI from the session state. The new test constructs six peer chats plus the default chat and proves the unresolved-after-reconnect path now subscribes only the default chat while preserving the file diff result.

- Effective concurrency: Peer metadata hydrations run concurrently as before. Foreign-agent config resolutions are coalesced by provider plus primary working directory within each restore, while the metadata range scan is globally promise-coalesced and cached.
- Cache behavior: Cold startup performs one metadata scan; all later callers reuse the mutable cached map. Foreign-agent config caching is scoped to a single session restore because working-directory context can differ. Failures clear the metadata promise so later restores can retry rather than pinning a negative result.

### Scenario 2: Create a peer chat on another harness, switch its harness in the composer, and send immediately

- Critical path: Creating the selected draft must complete before it appears. A send during a harness switch explicitly waits for that single switch, then workspace resolution and the normal send path proceed against the replacement chat.
- Scaling input: User harness-picker actions; effective work is constant per action and does not scale with the session's chat count or history.
- Effective concurrency: Harness switches are explicitly serialized to one in flight. Folder refreshes cancel/supersede prior resolutions. The create and subsequent delete are sequential, not burst-concurrent.
- Cache behavior: An existing untitled chat with the requested harness is reused. Provider/session capability and model snapshots are in-memory; no negative cache is added. Folder refresh state is replaced and cancellation-aware.
- Mechanism confidence: High: the create/delete ordering, one-operation guard, reuse condition, and send await are explicit.
- Magnitude uncertainty: Remote Agent Host latency and provider config latency vary, so an individual switch may be perceptible, but multiplicity is bounded by direct user actions.
- Expensive boundaries:

- Critical path: Loading the selected chat waits for its model reference and required Agent Host subscriptions. Respondent/model presentation and accessibility labels use in-memory observables. Response-file changes subscribe to the exact chat after session state resolves.
- Scaling input: Chats in the active session, visible tab/list rows, and response updates. The fixed subscription cardinality is one exact chat rather than all catalog chats; UI scans are linear over each session's own small chat list and perform no boundary calls.
- Effective concurrency: Observable recomputation is synchronous and in-memory. Chat subscriptions remain refcounted/coalesced by resource. Provider model/session-type events share one weakly keyed signal per provider, and only the bound chat's respondent autorun is retained.
- Cache behavior: Per-request observables are cached by session/chat/request key; provider-change signals are shared in a WeakMap; model snapshots and harness presentations are in-memory. Subscription errors can retry without permanently poisoning the resource.
- Mechanism confidence: High: the changed resolver, subscription helper, and regression test establish exact pre/post cardinality.
- Magnitude uncertainty: Sessions can contain many archived chats, making the removed fan-out large; normal UI list sizes and model counts are comparatively small.

### Scenario 4: Enable multiple chat providers at runtime and reconnect an already-running host

- Critical path: If the host gate is on but the previous handshake did not advertise the capability, the client deliberately closes the transport, performs one fresh initialize, then restores held subscriptions before the connection is usable again.
- Scaling input: Number of currently held subscriptions at the moment the user turns the feature on; inactive catalog sessions are not subscribed solely for this transition.
- Effective concurrency: The reinitialize is guarded by \_reinitializedForChatProviders and the connection state. Active subscriptions replay through existing subscription management; in-flight subscribe requests retry after reconnection and released resources are unsubscribed again.
- Cache behavior: The guard resets only when the setting or host gate turns off. The initialize result is observable and reused after connection. Local host startup seeds the setting before the first handshake, avoiding a cold double handshake.
- Mechanism confidence: High: the one-shot guard, transport close, initialize branch, and active-subscription restoration are explicit.
- Magnitude uncertainty: Reconnect duration depends on transport and host location; active subscription count varies with visible/open sessions.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:\_maybeReinitializeForChatProviders/\_reconnectOrInitialize</code>: Fresh initialize and replay of active subscriptions; cardinality: At most one reinitialize per gate-on period per connection; replay cardinality equals currently held, refcounted subscriptions, not all known sessions/chats.
    - Introduced by diff: true; previous behavior: There was no multiple-provider capability negotiation or setting-triggered reinitialize.; critical-path effect: The opt-in runtime setting transition briefly moves the connection through reconnecting; local hosts launched with the setting already on avoid this reinitialize via the environment seed.
- Verdict: No reportable regression: the one-time opt-in reconnect is bounded, necessary for protocol negotiation, and avoided on the common local cold-start path.

### Scenario 5: Move a chat across agents or archive/unarchive a mixed-agent session

- Critical path: Cross-agent moves run through the existing global move sequencer and await catalog/database/config preparation before commit. Archive/unarchive updates session state immediately; worktree cleanup and provider notifications are launched asynchronously.
- Scaling input: Moved chat chain/source-destination catalog size, or distinct agents represented in one session after deduplication.
- Effective concurrency: Moves use the pre-existing global sequencer. Archive notifications may run concurrently, but aggregate concurrency is bounded by distinct registered agents rather than chat count.
- Cache behavior: The global chat-agent map is updated after durable writes and reused. Move config resolution groups applicable chats; no unbounded per-chat provider cache is introduced.
- Mechanism confidence: High: serialization and Set-based deduplication are explicit, as are the durable move boundaries.
- Magnitude uncertainty: Provider archive RPC duration varies, especially for Codex, but it is off the user-visible state-update critical path and distinct-agent count is low.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:cross-agent move paths</code>: Read/write chat catalog, storage identity, chat-agent metadata, and moved-chat records during a move; cardinality: Bounded to the moved chat chain and source/destination sessions; chat-agent deletion/upsert is batched, and moves are globally serialized.
    - Introduced by diff: true; previous behavior: Moves were limited to sessions of the same agent and did not update per-chat agent/config records.; critical-path effect: Move completion waits for durable metadata/catalog ordering so restart cannot route the chat to the wrong agent.
  - subprocess at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:SessionIsArchivedChanged</code>: Notify each distinct agent represented in the session of archive/unarchive; cardinality: One call per distinct agent after Set deduplication, not one per chat; registered agent cardinality is small.
    - Introduced by diff: true; previous behavior: Only the session agent received the provider-specific archive notification.; critical-path effect: Calls are fire-and-forget relative to the state action. Existing worktree cleanup/recreation is also off the immediate action path.
- Verdict: No reportable regression: newly required cross-agent lifecycle work is grouped, serialized where consistency requires it, and archive fan-out is deduplicated and asynchronous.
