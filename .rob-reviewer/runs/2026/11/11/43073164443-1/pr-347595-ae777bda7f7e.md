### Scenario 1: Windows CI test jobs with a current or compatible workspace image

- Critical path: Each of the six opted-in Windows test jobs must restore the pipeline-cache entry, recreate and mount the VHDX, update the checkout, run the incremental dependency install, replace affected pnpm links, compile, and test. The separate image-producer job is not a dependency and is off each test job's critical path.
- Scaling input: Six opted-in Windows jobs per CI run; one image restore and mount per job. Image recreation scales with packed-image bytes/raw VHDX bytes, while junction discovery scales with the installed pnpm package/link layout across about 60 declared install/workspace directories. The PR reports roughly 500 replaced links, and the code visits each relevant node\_modules/.pnpm entry once.
- Effective concurrency: The six jobs run in parallel on separate Windows agents. Within each restore, unpack uses os.availableParallelism workers with a 64-chunk readiness window and one ordered writer; PowerShell VHD attachment starts concurrently with unpack but waits for the ready marker. Dependency install and junction replacement are sequential afterward. CI runs use trigger batch:true, limiting normal main-branch producer overlap.
- Cache behavior: Cache&#64;2 first requests the exact daily image key and, for use-mode jobs, falls back to the newest image with matching native-build inputs. Exact and inexact hits mount the image; misses install from the pre-existing pnpm-store path. Inexact hits rewrite key files to discarded before job completion so test jobs do not publish an image. There is no negative-cache state beyond the pipeline cache miss, but each job performs only one lookup.
- Mechanism confidence: High: cache, unpack, subprocess, local checkout, install, and junction ordering are explicit in the templates and implementation; cardinality is explicit in product-build.yml.
- Magnitude uncertainty: Exact image sizes, cache-service throughput, and agent memory pressure are not present in repository evidence. The supplied run context reports 0.2-0.3 minute mounts and materially shorter installs, so there is no evidence that the new bounded restore and junction work outweighs the removed install work.
- Expensive boundaries:
  - network at <code>build/azure-pipelines/common/workspace-image.yml Cache&#64;2</code>: Restore the packed workspace image from Azure Pipeline Cache; cardinality: One cache restore per opted-in job, six concurrent restores on a warm CI run; exact/inexact grouping is per platform/architecture key, not shared between agents.
    - Introduced by diff: true; previous behavior: Each Windows job restored its pnpm store cache and then performed a roughly four-minute dependency install; it did not download a workspace image.; critical-path effect: On the critical path before install in each job; a hit replaces the prior pnpm-store restore plus most clean-install work.
  - filesystem at <code>.github/workflows/workspace\_image/image.ts mountWindowsImage/unpack</code>: Decompress and write the full raw VHDX into a temporary file; cardinality: Once per warm opted-in job; bytes scale with the packed image and raw VHDX, with a bounded 64-chunk window.
    - Introduced by diff: true; previous behavior: No VHDX recreation occurred in Azure Windows CI jobs.; critical-path effect: Required before VHD attachment completes; the temporary-file hint allows Windows file cache to absorb writes and the restore timeout bounds this path.
  - subprocess at <code>build/azure-pipelines/common/workspaceImage.ts mountImage and .github/workflows/workspace\_image/win32/vhd.ps1</code>: Attach the VHDX with PowerShell and mountvol, then run local git fetch/checkout from the moved checkout; cardinality: One PowerShell attach and one local git update per warm opted-in job.
    - Introduced by diff: true; previous behavior: The checked-out working tree was used directly, with no VHD attach or local fetch.; critical-path effect: PowerShell startup overlaps unpack; attachment and local checkout must finish before dependency install.
  - filesystem at <code>build/azure-pipelines/common/workspaceImage.ts findLinksToRoot/junctions</code>: Scan pnpm node\_modules/virtual stores and replace root-reaching relative links with junctions; cardinality: One scan per warm opted-in job; each relevant directory/package entry is read once and each matching link is replaced once.
    - Introduced by diff: true; previous behavior: No junction scan or replacement was needed because dependencies lived on the ordinary checkout volume.; critical-path effect: Runs after install and before compile; measured PR context says under one second for about 500 links, and traversal is bounded by the installed dependency graph.
  - network at <code>build/azure-pipelines/win32/steps/product-build-win32-setup.yml Install dependencies</code>: Run pnpm install for dependency deltas and private distro roots; cardinality: Once per job as before; image hits reuse node\_modules and the image-local pnpm store, so network work is limited to changes and private roots.

- Verdict: No reportable regression. The diff adds bounded image I/O and link scanning but replaces larger repeated dependency-install work on the same critical paths, and its per-job concurrency is bounded.

### Scenario 2: First Windows CI run of a day or after dependency/native-input changes

- Critical path: Test jobs do not wait for the image producer. They either use the newest compatible fallback image or, if none exists, follow the prior full-install path. The new producer independently creates an NTFS VHDX, installs dependencies, packs it, and publishes it for later runs.
- Scaling input: One Windows x64 producer job per CI run; a new image is built only when the exact daily/lockfile/native-input key misses. Work scales with checkout size, dependency graph, VHDX allocated bytes, and packed output bytes.
- Effective concurrency: The producer runs concurrently with the seven Windows test jobs and has no dependency edge to them. Normal CI is batch:true, so producer bursts across overlapping main-branch CI runs are coalesced by pipeline triggering; manual CI overlap remains possible but is not evidenced as a prevalent path. Packing uses os.availableParallelism compression workers and retains compressed frames until output, bounded by image size and job timeout rather than an explicit byte cap.
- Cache behavior: The image key includes native inputs, lockfiles/pnpm-store key, and pipeline-start day. An exact cache miss creates one image; exact hits skip creation/install/pack. Cache save occurs only after successful producer completion. Test jobs use compatible older images or fall back cleanly and never wait for the producer.
- Mechanism confidence: High for the producer work and its off-critical-path placement; medium for cross-run concurrency because normal CI is explicitly batch:true and only manual runs could overlap.
- Magnitude uncertainty: The compressed Windows image size and Windows pool capacity are not available. Whole-image packing retains compressed frames, but this implementation is shared with existing platforms and the supplied run context records a successful Windows pack; there is no concrete symptom or evidence of memory exhaustion.
- Expensive boundaries:
  - network at <code>build/azure-pipelines/common/workspace-image.yml Cache&#64;2</code>: Look up/restore the exact producer cache entry and publish a newly packed image on a miss; cardinality: One producer cache operation per CI run; one upload only on an exact-key miss and successful build.
    - Introduced by diff: true; previous behavior: There was no Windows workspace-image producer, lookup, or image upload.; critical-path effect: Off test-job critical paths, though the job consumes a Windows agent and the stage cannot finish before all jobs complete. Tests are expected to dominate a warm producer lookup.
  - subprocess at <code>build/azure-pipelines/common/workspaceImage.ts create/packWindowsVolume and .github/workflows/workspace\_image/win32/vhd.ps1</code>: Create, format, mount, flush, detach, and clean an NTFS VHDX; cardinality: One create/detach lifecycle per exact-key miss; system-folder cleanup runs after creation and before packing.
    - Introduced by diff: true; previous behavior: No Windows CI producer volume lifecycle existed.; critical-path effect: Only on the producer path and not required for current test jobs to proceed.
  - network at <code>build/azure-pipelines/win32/steps/product-build-win32-setup.yml Install dependencies in build mode</code>: Perform a clean pnpm dependency install without the pnpm-store cache; cardinality: Once per exact-key miss; CI trigger batching normally prevents simultaneous main-branch runs from duplicating the daily build.
    - Introduced by diff: true; previous behavior: Each test job installed independently, but there was no additional producer install.; critical-path effect: Off current test-job critical paths; creates the reusable image for later runs.
  - serialization at <code>.github/workflows/workspace\_image/image.ts pack via build/azure-pipelines/common/workspaceImage.ts packWindowsVolume</code>: Read, zero-page filter, zstd-compress, and write the VHDX image; cardinality: One whole-image pack per producer miss; CPU, retained compressed buffers, and I/O scale with VHDX allocated/nonzero content.
    - Introduced by diff: true; previous behavior: No Windows VHDX was packed in Azure CI.; critical-path effect: Producer-only and bounded by a 15-minute pack step plus job timeout; not on test-job progress.
- Verdict: No reportable regression. The producer adds intentional off-path work to amortize repeated installs, cache misses are daily/input-bound, and normal CI batching rejects the realistic unbounded duplicate-producer candidate.

### Scenario 3: Windows CI cache miss, restore failure, or timeout; Smoke job

- Critical path: On a cache miss the opted-in jobs continue with the existing pnpm-store restore and full dependency install. On mount failure or the 240-second restore timeout, cleanup unmounts/detaches the VHDX, restores the moved checkout, and then follows the same fallback. The Windows Smoke job is not opted in and retains its previous path.
- Scaling input: At most one failed restore attempt per opted-in job, with a 240-second internal abort and 10-minute step timeout. Cleanup operates on one VHDX and one moved checkout per job.
- Effective concurrency: Failures can occur independently in six jobs, each on its own agent. Cleanup subprocesses are sequential per job; no retry loop remounts the image. Smoke remains one ordinary job with no image work.
- Cache behavior: A missing image sets WORKSPACE\_IMAGE\_USED=false; failed restores empty the restored cache folder and fall back. The pnpm store cache is restored only when no workspace image was successfully mounted. Smoke always uses the existing pnpm-store behavior.
- Mechanism confidence: High: fallback conditions, timeout, cleanup ownership, and Smoke exclusion are explicit in code and templates.
- Magnitude uncertainty: Cache task service-side duration is not explicitly bounded in the repository, and failure prevalence is unknown. The mount path itself is bounded and does not retry, so there is no evidenced repeated-I/O amplification.
- Expensive boundaries:
  - filesystem at <code>build/azure-pipelines/common/workspaceImage.ts keepCheckout/moveCheckoutBack/restore</code>: Move checkout entries aside and back, delete temporary image/cache files, and restore the original checkout on failure; cardinality: One move-out and one rollback per failed mount; entries are same-volume renames, with at most ten 500ms retries per locked entry.
    - Introduced by diff: true; previous behavior: No checkout relocation or VHD cleanup was needed.; critical-path effect: Adds bounded fallback latency before the prior install path; prevents retaining a mounted image or duplicating a checkout after failure.
  - subprocess at <code>.github/workflows/workspace\_image/image.ts mountWindowsImage release</code>: Unmount via mountvol and detach via PowerShell after failed mount; cardinality: At most one release sequence per failed restore attempt.
    - Introduced by diff: true; previous behavior: No VHD process cleanup existed.; critical-path effect: On the failure fallback path only; detachment has a 30-second timeout.
  - network at <code>build/azure-pipelines/win32/steps/product-build-win32-setup.yml</code>: Restore pnpm store and perform the full dependency install after no image is used; cardinality: Once per fallback job, same effective install cardinality as before the diff.
    - Introduced by diff: false; previous behavior: This was the normal path for every Windows test job.; critical-path effect: Returns to the prior critical path after the bounded image attempt.
- Verdict: No reportable regression. Failure adds one bounded attempt and then preserves the prior install behavior; cleanup retains the handles needed to unmount/detach and restore the checkout, while Smoke is unchanged.
