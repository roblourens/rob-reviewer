**Relevant issue families:** cache-lifecycle, boundary-fanout, missing-coalescing, eager-work, cleanup-lifecycle

### Scenario 1: Agent host startup with the Microsoft credential bridge enabled

- Critical path: CopilotAgent eagerly creates a lightweight in-memory bridge and passes a synchronous tokenProvider into SDK client creation. Runtime startup does not wait for credential acquisition: a cache miss returns unavailable immediately and publishes a requirement asynchronously.
- Scaling input: Number of agents, distinct protected resources, authorization servers, and signed-in sessions. Microsoft additions are statically bounded to one discovery resource plus two known audience resources, and duplicate requirement states are coalesced.
- Effective concurrency: Protected resources and authorization servers are processed serially in the workbench resolver; identical authenticate RPCs share a pending promise per key. No new concurrency burst is introduced.
- Cache behavior: Host credentials are keyed by resource/scopes and expiry; workbench forwarding deduplicates completed and pending credentials. Missing Microsoft credentials are represented by a deduplicated observable requirement rather than a negative token cache; repeat identical SDK requests do not republish state.
- Mechanism confidence: High: constructor, token callback, observable publication, resolver, and authenticate RPC paths were traced directly.
- Magnitude uncertainty: Authentication provider implementations may perform keychain or refresh work internally, but cardinality is bounded and the new query is conditional on account-only enumeration.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:\_publishAgentInfos and src/vs/platform/agentHost/node/copilot/copilotEntraAuthentication.ts:requireCredential</code>: Publish changed protected-resource metadata/auth-required state from agent host to workbench and later deliver authenticate back to the host; cardinality: At most one publication per distinct resource/reason/scope state because requireCredential deduplicates identical requirements; Microsoft has one discovery resource and two mapped token resources.
    - Introduced by diff: true; previous behavior: No Microsoft requirement or credential IPC existed; GitHub authentication already used the host/workbench authentication channel.; critical-path effect: The SDK callback returns unavailable synchronously, so publication and credential delivery are off the immediate callback critical path; a later authenticated operation may retry after delivery.
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts:resolveAuthenticationSessionForResource</code>: Activate an authentication provider and enumerate existing sessions, optionally acquire scopes for the selected account; cardinality: Serial per advertised resource and authorization server; for account-placeholder providers, one account enumeration plus one scoped query for the preferred account. The bridge advertises only the currently required Microsoft resource.
    - Introduced by diff: true; previous behavior: Existing resources performed provider activation/session enumeration; the diff adds one scoped account query only when account enumeration does not itself contain a usable scoped credential.; critical-path effect: Required before the workbench can deliver a credential, but not before the host token callback returns unavailable. Remote initial handshake skips required:false resources.
- Verdict: No reportable regression. The eager object is lightweight, misses do not block the SDK callback, and expensive provider work is bounded and deduplicated.

### Scenario 2: Runtime requests a Microsoft audience token during login or an M365-backed operation

- Critical path: The synchronous SDK tokenProvider checks the in-memory credential store. A hit returns immediately; a miss invalidates an expired/rejected entry when necessary, publishes one requirement, and returns unavailable. Workbench session resolution and authenticate IPC happen before a later retry can succeed, not within the callback.
- Scaling input: Distinct Microsoft audiences/scopes requested by the packaged runtime. Audience validation restricts requests to two static mappings, and one requirement replaces the prior requirement for the same resource.
- Effective concurrency: SDK callback work is synchronous. Workbench lookup is serial per resolver invocation; recovery coalesces concurrent challenges by protected-resource key.
- Cache behavior: Warm valid credentials are returned from AgentHostAuthenticationService. Expired or skip-cache requests invalidate that resource and remember only the most recently rejected host token; workbench forwarding coalesces pending requests and caches the last credential key.
- Mechanism confidence: High: request validation, cache reads, challenge state, requirement deduplication, and workbench pending-recovery maps were inspected.
- Magnitude uncertainty: Actual provider token refresh latency is implementation-dependent, but no collection-driven or unbounded fan-out was introduced.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts:forwardAuthenticationToken</code>: Authenticate request carrying the selected scoped session token and account metadata; cardinality: One RPC per changed resource/scope/token key; concurrent identical forwarding shares one pending promise and completed values suppress repeats.
    - Introduced by diff: true; previous behavior: There was no Microsoft token delivery; existing GitHub resources used the same deduplicated authentication RPC cache.; critical-path effect: Required for a later successful token retry, but a missing token request itself finishes immediately as unavailable.
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts:resolveAuthenticationSessionForResource</code>: Authentication-service session enumeration/scoped token acquisition; cardinality: One provider lookup and normally one session query for a required resource; account-placeholder enumeration can add one scoped query. Multiple authorization servers are tried serially.
    - Introduced by diff: true; previous behavior: The resolver previously selected already-enumerated sessions; the conditional account-scoped query is new and necessary to turn an account placeholder into the advertised scoped credential.; critical-path effect: On the asynchronous credential-supply path; it can delay a successful retry but does not block the initial token callback.
- Verdict: No reportable regression. Boundary work is one-per-changed credential, coalesced, and bounded to known audiences.

### Scenario 3: Microsoft sign-out or rejected/expired credential recovery

- Critical path: Sign-out clears authority and the bounded mapped resources, publishes a single discovery requirement, then schedules a runtime restart after active shared-runtime turns finish. Expired/rejected token requests synchronously invalidate only the affected resource before returning unavailable.
- Scaling input: Stored credential keys for three statically known resources and number of active turns. Repeated revocations without authority are no-ops.
- Effective concurrency: Resource invalidation is synchronous and serial over small maps. Runtime restart requests use the existing restart coordination and wait for active turns rather than spawning concurrent runtimes.
- Cache behavior: Revocation clears authority, challenges, requirements, and all stored tokens for the static resources. Replacement requirements are deduplicated. The workbench rejection cache is connection-scoped and cleared on session removal or connection reset.
- Mechanism confidence: High: revocation, invalidation loops, observable update, and restart callback were traced.
- Magnitude uncertainty: Cold runtime restart duration varies, but it is tied to explicit sign-out and not repeated by duplicate empty revocations.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotEntraAuthentication.ts:clearAuthority/revoke</code>: Publish token removals and the replacement authentication requirement; receive replacement authenticate; cardinality: A sign-out scans the authentication store once for each of three static resources and emits per matching stored credential; replacement delivery is deduplicated per resource/scope/token.
    - Introduced by diff: true; previous behavior: Microsoft state and restart behavior did not exist; analogous GitHub credential clearing already restarted runtime state.; critical-path effect: Runtime restart is intentionally deferred until running turns finish; credential replacement is required for future Microsoft-backed operations.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:onDidRevoke callback to \_requestClientRestart</code>: Stop and later recreate the shared Copilot runtime after authority revocation; cardinality: One requested restart per effective revocation while authority exists; repeated empty-token revocations return early once authority is cleared.
    - Introduced by diff: true; previous behavior: Microsoft revocation could not trigger a restart because no bridge existed.; critical-path effect: Off the active-turn critical path because restart waits for running shared-runtime turns to finish; later sessions may pay cold restart cost.
- Verdict: No reportable regression. Cleanup and restart have bounded cardinality and preserve active-turn scheduling.

### Scenario 4: Authentication-session changes and remote connection bootstrap

- Critical path: Session changes reconcile removed credentials, then re-run protected-resource authentication. Remote bootstrap resolves only resources marked required; with the bridge enabled, GitHub and Microsoft alternatives are optional, so they are excluded from the initial remote handshake.
- Scaling input: Connected remote hosts, agents, resources, and removed sessions. Reconciliation remains serial per connection; resources are deduplicated during removal handling and token RPCs are cached per connection.
- Effective concurrency: Connections may authenticate independently, while resources within a connection are serial. Existing per-key pending promises prevent duplicate sends within a connection.
- Cache behavior: Each connection owns a cache dropped on connection disposal. Completed and pending tokens coalesce repeats; generation invalidation cancels stale forwards. Remote initial resolver ignores required:false resources.
- Mechanism confidence: High: local and remote event handlers, remote initial resolver, and per-connection cache ownership were inspected.
- Magnitude uncertainty: A provider may internally perform slower keychain or refresh operations, but the diff neither increases unbounded concurrency nor makes optional Microsoft work part of remote bootstrap.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts:authenticateProtectedResources and revokeAuthenticationForRemovedSessions</code>: Resolve provider IDs and enumerate sessions for each applicable protected resource; cardinality: Serial per agent/resource, with duplicate token sends suppressed by AgentHostAuthTokenCache. Removed-session reconciliation deduplicates resources with a local set.
    - Introduced by diff: false; previous behavior: Full protected-resource reconciliation on root/session changes already existed; the diff changes account selection and adds conditional scoped acquisition.; critical-path effect: Runs before authentication-pending clears for local/remote contributions; remote bootstrap does not query optional Microsoft resources.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts:\_authenticateWithConnection</code>: Remote connection authenticate RPC for a changed selected session; cardinality: At most one changed-token RPC per resource/scope key; warm identical credentials are suppressed.
    - Introduced by diff: false; previous behavior: Remote connections already forwarded required protected-resource credentials over IPC.; critical-path effect: Part of connection authentication settling only for required advertised resources; optional alternatives are skipped by the initial resolver.
- Verdict: No reportable regression. New optional credentials do not expand remote bootstrap boundaries, and changed-token forwarding remains coalesced.
