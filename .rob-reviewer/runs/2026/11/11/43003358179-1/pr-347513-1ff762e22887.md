[PR #347513](https://github.com/microsoft/vscode/pull/347513) at `1ff762e22887a9370a9ae5e2c2f351ec5e7d7bf3`

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** cleanup-lifecycle, cache-lifecycle

### Scenario 1: A subagent requests shell permission before its tool.execution\_start event has been bridged to the host.

- Critical path: The SDK permission callback performs its existing policy/sandbox checks, emits pending\_confirmation, and waits for the user's decision. The added agent-ID association and parent lookup are synchronous Map operations and add no await or boundary to this critical path.
- Scaling input: The map scales with concurrently unresolved subagent permission requests, not session history or event volume; one entry is removed when each handler settles and all remaining entries are cleared on abort/disposal.
- Effective concurrency: Permission callbacks may overlap across distinct toolCallIds; each adds one independently keyed entry. There is no new fan-out or burst, and lookup/removal remain O(1) per request.
- Cache behavior: The existing subagent agentId-to-toolCallId map supplies the parent association after subagent.started. The new request map is a transient correlation table rather than a reusable cache, with explicit per-request and bulk invalidation.
- Mechanism confidence: High: the changed set/get/delete/clear sites and the handler/event ordering are explicit, and the parent lookup is backed by Map.get.
- Magnitude uncertainty: The maximum number of simultaneous permission prompts varies by workload, but this affects only a pair of short strings per unresolved request and does not change the bounded lifecycle.
- Expensive boundaries: none found
- Verdict: No reportable regression. The change adds bounded O(1) correlation work and no expensive boundary, scheduling delay, or retained session-history growth.

### Scenario 2: A subagent write request builds a file-edit preview before displaying its permission confirmation.

- Critical path: The pre-existing handler checks file existence and writes the proposed content to the pending-edit-content provider before emitting the confirmation. The changed routing lookup runs only after those operations and does not duplicate or move them.
- Scaling input: Cost remains linear in the number of actual concurrent write permission requests, with one pre-existing preview per request; the diff contributes only constant-time map operations.
- Effective concurrency: Each qualifying write permission owns one pending preview and one routing-map entry keyed by toolCallId. The diff neither increases permission concurrency nor adds boundary calls.
- Cache behavior: No cache behavior changes. Pending preview content and the new agent association are both removed on request completion and bulk-cleared during cancellation.
- Mechanism confidence: High: the handler call flow places the unchanged preview operations before the added lookup, and no changed line invokes them more often.
- Magnitude uncertainty: File-provider latency depends on the target/provider, but its call count and critical-path placement are unchanged by this PR.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_buildEditsForPermission</code>: Check whether the target file exists for the preview.; cardinality: One exists call per qualifying write permission request.
    - Introduced by diff: false; previous behavior: The same existence check was already performed once per qualifying write permission.; critical-path effect: Must complete before the preview-backed confirmation is emitted.
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_buildEditsForPermission/\_deletePendingEditContent</code>: Write proposed contents to the pending-edit-content file provider and delete them after resolution/abort.; cardinality: One write and at most one cleanup delete per qualifying write permission request.
    - Introduced by diff: false; previous behavior: The same preview write and cleanup lifecycle existed before the diff.; critical-path effect: The write is on the confirmation critical path; cleanup is off the user-decision critical path.
- Verdict: No reportable regression. The existing filesystem work is neither introduced nor amplified, and the new correlation state is bounded to pending requests.

### Scenario 3: The user aborts or disposes a session while subagent permission requests are pending.

- Critical path: Abort synchronously denies pending interactions; the new map is cleared in the same cleanup sweep. Disposal invokes the abort sweep before base disposal, so no new asynchronous cleanup blocks shutdown.
- Scaling input: Clear cost is O(P) for P concurrently pending permissions, matching the number of retained entries and bounded by active unresolved requests.
- Effective concurrency: A single synchronous clear handles all outstanding associations; it does not perform per-entry I/O or schedule concurrent cleanup.
- Cache behavior: Both normal completion (delete by toolCallId) and abnormal termination (clear all) are covered; no negative entries or completed-request records remain cached.
- Mechanism confidence: High: the cleanup call path from \_beginAbort to \_cancelAllPendingInteractions to \_denyPendingPermissions is explicit, and the changed clear is synchronous.
- Magnitude uncertainty: P can vary with agent parallelism, but clearing an in-memory Map is small compared with the already-existing pending-permission denial sweep.
- Expensive boundaries: none found
- Verdict: No cleanup-lifecycle or retained-memory regression; cancellation and disposal bound the new state.

**Summary:** Reviewed all three changed files and the complete diff. The production change adds a transient toolCallId-to-agentId correlation for early subagent permissions, performs only O(1) map operations on the permission path, and cleans entries on normal completion plus abort/disposal. Existing filesystem preview work is unchanged in count and placement. No actionable performance regression or qualifying regression fix was found.
