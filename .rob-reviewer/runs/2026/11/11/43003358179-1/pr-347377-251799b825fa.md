# Performance review: agentHost: Move Chats and multi-harness settings are experiment-controlled

[PR #347377](https://github.com/microsoft/vscode/pull/347377) at `251799b825fa29f9888d3149ab94be1455113128`

## Findings (1)

### 1. [medium] Resolve the rollout before prewarming Agent Host

**Finding ID:** `PERF-20F108B93D90`  
**Location:** <code>src/vs/platform/agentHost/common/agentHostStarter.config.contribution.ts:232</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Agent Host transport connections, initialize IPC/RPC calls, and serialized subscription snapshots  
**Scaling:** The diff causes one extra transport teardown and fresh initialize per already-connected Agent Host client on each startup assigned \`true\`; the initialize payload and snapshot reconstruction grow with the client's active session/chat subscriptions, and omitted snapshots fan out into concurrent per-subscription snapshot requests.  
**Outcome:** Increased Agent Host startup/session-readiness latency and avoidable IPC/network plus host serialization work  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The setting had a synchronous fixed default of \`false\`. Users who explicitly enabled it had that value available before the host starter and first handshake, so the host was seeded enabled and the protocol test asserts only one transport/initialize was needed.  
**Changed behavior:** Adding startup experiment metadata makes a \`true\` default arrive asynchronously from \`ConfigurationDefaultOverridesContribution\` after TAS treatment resolution. \`AgentHostPrewarmContribution\` independently starts the host in \`BlockRestore\`, so the first handshake can occur with the old false default; the later default-change is mirrored to the host and deliberately forces a fresh protocol initialization.  
**Confidence:** 0.97 — The asynchronous treatment path, same-phase ungated prewarm, forced fresh-initialize code, subscription scaling, and one-versus-two-transport behavior are all directly established by repository code and tests. Exact latency varies by transport and subscription count, but the repeated boundary work is deterministic whenever the true assignment lands after connection.

**Causal diff evidence:** The added \`experiment: { mode: 'startup' }\` at line 232 is the only change that allows this setting's default to transition asynchronously from false to an assigned true during startup, moving the existing forced-reinitialize path onto every assigned user's cold-start flow.

For users assigned \`config.chat.agentHost.multipleChatProviders.enabled=true\`, an enabled Agent Host can connect during restore and then immediately disconnect/reconnect when the assignment lands. This repeats authentication/config forwarding and restores every active session/chat subscription, delaying restored Agent Host sessions and doing work proportional to open subscriptions.

**Evidence:** \`ConfigurationDefaultOverridesContribution\` queues async \`updateDefaults()\` in its constructor and awaits \`getTreatmentWithAssignment\` for each experimental setting, while \`AgentHostPrewarmContribution\` is also registered at \`WorkbenchPhase.BlockRestore\` and calls \`startAgentHost()\` without waiting for those defaults. On the late configuration change, \`AgentHostProtocolClient\` mirrors the flag and \`\_maybeReinitializeForChatProviders()\` clears the transport and requests a fresh initialize. That initialize sends all current subscription URIs; the server loops over them to build snapshots, and missing snapshots are restored per subscription. The existing protocol test \`re-initializes once when the host enables chats with their own agents after the handshake\` proves the late false-to-true path creates two transports, while \`does not re-initialize when the first handshake already advertises...\` proves the pre-resolved path uses one.

**Suggested direction:** Ensure this startup treatment is resolved before Agent Host prewarm/connection captures the setting and performs its first handshake (or otherwise seed the starter/initial handshake from the resolved treatment). Do not apply the rollout as a post-connect default change that requires reinitializing the transport.
