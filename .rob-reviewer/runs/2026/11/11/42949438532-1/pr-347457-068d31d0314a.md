### Scenario 1: Workbench startup and live configuration forwarding for the two experiment-capable settings

- Critical path: The contribution computes four scalar root values and dispatches changed values asynchronously; it does not await host persistence, customization refresh, or automation refresh before the workbench can continue. A session launched before forwarding completes may observe prior configuration, but that is correctness/config timing rather than a performance block.
- Scaling input: Constant four new keys, with secondary in-memory/mostly cached work scaling with registered sessions. Effective filesystem scan cardinality is one per distinct cold workspace root because RootMcpDiscovery is shared and initialized after its first scan.
- Effective concurrency: The four workbench pushes may start concurrently; host config writes are serialized by \_rootConfigWrite, customization publications are serialized per session, and root MCP discovery is serialized/shared per root.
- Cache behavior: Missing persisted keys cause cold dispatch and writes. Persisted equal values suppress all four actions on warm startup. Customization and MCP discovery retain settled/shared state; only the first cold root discovery scans .mcp.json.
- Mechanism confidence: High confidence in the four-action/four-write cold mechanism and its suppression on warm starts, based on the forwarder equality guard and serialized persistence implementation.
- Magnitude uncertainty: The number of restored sessions varies, but expensive filesystem persistence is fixed at four cold transactions and is off the critical path. No evidence shows user-visible startup latency.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostRootConfigForwarder.ts:\_push</code>: Dispatch RootConfigChanged from the workbench to the local agent host; cardinality: Cold upgrade or changed experiment assignment: four actions for the two value/default-control pairs; a direct change to one setting can produce two actions. Warm startup: zero actions because structural equality suppresses unchanged values.
    - Introduced by diff: true; previous behavior: These four keys did not exist, so they generated no root-config IPC actions.; critical-path effect: Asynchronous and not awaited by contribution startup; it does not block workbench progress.
  - filesystem at <code>src/vs/platform/agentHost/node/agentConfigurationService.ts:persistRootConfig</code>: Serialize the full persisted root config, mkdir the parent, write a temporary file, and rename it; cardinality: One serialized write transaction per accepted RootConfigChanged action: at most four for initial hydration of these keys, then zero on warm starts unless a value changes.
    - Introduced by diff: true; previous behavior: No persistence transactions existed for these absent keys; other forwarded settings already use the same per-key persistence path.; critical-path effect: Queued on \_rootConfigWrite and not awaited by the originating workbench dispatch, so it is off the interactive critical path.
  - other at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:RootConfigChanged</code>: Recompute agent descriptors and queue customization publication for registered sessions; cardinality: Triggered once per accepted action, so four cold-start passes; per-session Copilot customization reads share settled discovery, and RootMcpDiscovery performs its filesystem scan only on the first cold refresh.
    - Introduced by diff: true; previous behavior: These keys caused no passes, though every existing root-config update already used this broad invalidation path.; critical-path effect: Queued/asynchronous and guarded by equality/cached discovery; no changed request waits for all session refreshes.
- Verdict: Not reportable: the added boundary work is finite, asynchronous, warm-cache suppressed, and follows the existing forwarding architecture; no concrete user-visible regression is established.

- Effective concurrency: Unchanged from the launcher: independent setup work is already combined with Promise.all, and the feature-flag reads add no concurrency.
- Cache behavior: Flags are off by default. When experiment-enabled, sent-history adoption is intended to extend the prior cached prompt and tool estimation is intended to avoid unnecessary compaction; no repository evidence establishes cache invalidation or retention growth.
- Mechanism confidence: High confidence that this diff changes only constant-size configuration and not launch/model boundary cardinality; low confidence about undocumented SDK internals, so no adverse behavior is inferred.
- Magnitude uncertainty: The downstream SDK implementation is outside the supplied repository, so exact token/cache savings are unknown; importantly, there is also no code evidence of a regression mechanism.
- Expensive boundaries:

### Scenario 3: Process a routed Fusion turn and attribute the two setting experiments

- Critical path: On session.fusion\_resolved, the host synchronously checks default-control/assignment state and calls the existing telemetry helper. Telemetry submission is not awaited before Fusion progress processing continues.
- Scaling input: Fusion resolutions can occur once per routed turn, but external telemetry cardinality is capped at two per process; subsequent turns perform two constant-time map/set checks.
- Effective concurrency: Fusion events are handled in the existing session event stream. No Promise fan-out or concurrent network burst is introduced.
- Cache behavior: The first eligible route populates the telemetry deduplication Set. All warm routes are negative lookups followed by early return; pending treatment names are bounded to the two settings while assignment context is absent.
- Mechanism confidence: High confidence from the helper's explicit per-telemetry-service deduplication and the bounded pending Set.
- Magnitude uncertainty: Telemetry implementation buffering details are not shown, but the strict two-event cap and non-awaited call remove realistic scaling risk.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_acceptFusionEvent</code>: Queue experimentTrigger telemetry through logSettingExperimentTrigger/publicLog2; cardinality: At most two events per telemetry service/process across all Fusion turns because experimentTrigger.ts deduplicates treatment names in a WeakMap-backed Set.
    - Introduced by diff: true; previous behavior: These two setting treatments emitted no trigger events.; critical-path effect: The helper runs in event handling but does not await network I/O; after the first routed turn, calls reduce to Set lookups.
- Verdict: Not reportable: bounded telemetry and constant-time warm-route checks do not create a concrete throughput or latency regression.
