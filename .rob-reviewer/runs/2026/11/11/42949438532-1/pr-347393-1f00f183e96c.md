# Performance review: agentHost: use harness-owned plugin enablement in customizations

[PR #347393](https://github.com/microsoft/vscode/pull/347393) at `1f00f183e96c9303b59ca8e915d8453cbb0638c0`

## Findings (3)

### 1. [medium] Coalesce queued runtime inventory refreshes

**Finding ID:** `PERF-1435DC1EDEB7`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:12046</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Copilot SDK plugins.list RPC calls  
**Scaling:** Every caller enqueues a distinct refresh; each executes one global SDK RPC and optionally a second live-session RPC, so work grows with snapshot, publication, and file-change frequency across active sessions.  
**Outcome:** blocked create/resume paths and queued IPC latency during bursts  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, session customization snapshots did not refresh the runtime plugin inventory and therefore did not queue these SDK RPCs.  
**Changed behavior:** The new refresh method uses Sequencer.queue for every request. Settled and applied customization snapshots now call it unconditionally, while the queued operation reaches listPluginInstallations(session), which performs global plugins.list and then live-session plugins.list when available.  
**Confidence:** 0.98 — The queue semantics, callers, and downstream RPCs are explicit; only the runtime-specific RPC duration varies.

**Causal diff evidence:** RIGHT line 12046 introduces per-request sequencing for runtime inventory refreshes; unlike coalescing, Sequencer executes every queued task.

Concurrent session startup, customization publication, or watcher notifications serialize repeated inventory round trips even when all callers need the same unchanged result.

**Evidence:** The added line 12046 queues \_readRuntimePlugins without retaining or reusing an in-flight/current promise. Added calls from getCustomizationsSettled and getAppliedCustomizations put it on create/resume and publication critical paths. The installedPlugins callback is wired to listPluginInstallations(session), whose implementation performs the SDK RPCs serially.

**Suggested direction:** Keep one current/in-flight inventory promise per session and have concurrent readers share it. Invalidate and start a new refresh only after plugin mutations, runtime plugin-change events, or explicit discovery invalidation.

### 2. [medium] Share runtime plugin parsing across sessions

**Finding ID:** `PERF-4B0C4C33D788`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:11886</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** filesystem reads plus recursive watcher and file-change listener objects  
**Scaling:** With S active Copilot configuration scopes and P installed plugins, cold parsing and retained watch/listener state grow as S×P; changing one plugin also wakes each session-local listener and causes each session to reparse and republish independently.  
**Outcome:** duplicated filesystem I/O and CPU during session creation/resume, increased retained watcher/listener memory, and update-time I/O bursts  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, SessionPluginController did not discover, parse, cache, or recursively watch every runtime-owned installed plugin; those per-session S×P resources and reads were absent from this path.  
**Changed behavior:** Each SessionPluginController now owns its own ResourceMap of parsed plugin promises and DisposableResourceMap of watchers. Its first runtime inventory refresh maps every installation through \_readRuntimePluginContents, which creates a recursive watch/listener and invokes parsePlugin for that session.  
**Confidence:** 0.97 — The ownership, first-use call path, parser filesystem operations, and session lifetime are explicit in code. The exact OS watcher deduplication is implementation-dependent, but duplicate parse work, cache objects, file-change listeners, and per-session publications remain certain.

**Causal diff evidence:** RIGHT line 11886 adds the parsed-content cache directly to each newly created SessionPluginController (with the watcher map on the next added line), making cache and watch ownership per session rather than shared by installed plugin resource.

Users with several installed plugins and multiple live Copilot sessions repeatedly pay the same manifest/component directory reads when sessions start or resume, retain duplicate listeners for the lifetime of those sessions, and fan a plugin update out across every session.

**Evidence:** The added session-local fields at lines 11886-11887 are consumed by \_readRuntimePlugins, which Promise.all-parses every installed resource. \_readRuntimePluginContents registers fileService.watch(resource, { recursive: true }) and a global onDidFilesChange listener, then calls PluginController.tryParsePlugin. parsePlugin detects format, reads the manifest, resolves component directories, and reads agent/skill/instruction files. Active clients are keyed per configuration scope and these resources live until \_finalizeConfigurationScope disposes that session.

**Suggested direction:** Move parsed runtime plugin content and its recursive invalidation watcher to PluginController (or another provider-wide, ref-counted cache) keyed by resource/version. Let sessions share the parsed promise and subscribe to one invalidation signal while keeping only chat-specific activation in SessionPluginController.

### 3. [low] Avoid blocking customization enumeration on fresh inventory RPCs

**Finding ID:** `PERF-6387B6B25F8B`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentCustomizationItemProvider.ts:363</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** agent-host IPC/network calls and downstream Copilot SDK plugins.list RPCs  
**Scaling:** Each uncached item-provider fetch issues one inventory call per distinct runtime provider (providers run in parallel); for Copilot each call expands to one global SDK RPC and optionally one session RPC. The work repeats whenever the item source is recreated or invalidated, independent of plugin count.  
**Outcome:** longer time to render the customization management list, especially for remote agent hosts  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The provider previously projected the already-published customization snapshot immediately and began plugin expansion without any management-service or runtime SDK inventory round trip.  
**Changed behavior:** The provider now awaits resolveRuntimePluginEnablement before iterating any customizations. That resolver has no cache and calls target.listPluginInstallations for every represented provider; the Copilot implementation performs global and optional session plugins.list RPCs serially.  
**Confidence:** 0.95 — The blocking await and complete IPC/RPC path are explicit. Actual latency varies between local and remote hosts, so severity is low despite high mechanism confidence.

**Causal diff evidence:** RIGHT line 363 moves runtime inventory resolution onto provideChatSessionCustomizations' blocking path; before the hunk the method used getCustomizations(sessionResource) directly.

Opening or refreshing Chat Customizations cannot show any host items until the remote/runtime inventory completes, adding visible panel latency even though most item metadata is already in the session snapshot.

**Evidence:** RIGHT line 363 awaits resolution before the item-building loop. AbstractAgentHostCustomizationService.resolveRuntimePluginEnablement calls listPluginInstallations once per provider, and the connection bridge can cross a remote host. CopilotAgent.listPluginInstallations always invokes global plugins.list and then invokes the live session's plugins.list when available. ItemProviderItemSource caches only the whole provider promise until onDidChange, so a new source or each invalidation repeats the boundary.

**Suggested direction:** Cache/coalesce inventory by provider, backend session, and exact chat, invalidating after runtime mutations or host activation-change events. Preserve the advertised default-chat value when authoritative, and avoid withholding the entire item list while an exact-chat refresh is in flight.
