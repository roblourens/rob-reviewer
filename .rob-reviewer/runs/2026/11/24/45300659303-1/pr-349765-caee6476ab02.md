- Scaling input: One desktop workbench startup per window. Deleted session-list, transcript-history, auxiliary-window, and polling work has zero effective runtime cardinality on the supported pre-diff paths.
- Effective concurrency: Startup loses a module import and command registrations; no new parallel creation, polling, IPC, or cleanup is scheduled.
- Cache behavior: Removal does not add cache lookups or invalidations. The deleted service only cleared its obsolete persisted window-open flag; the remaining voice storage and transcript index are unchanged.
- Mechanism confidence: High: complete changed-file inventory and diff pages inspected, including all deleted implementations and the desktop import removal.
- Magnitude uncertainty: Any reduction in module-loading cost is unmeasured; unreachable deleted work is not counted as a demonstrated runtime performance improvement.
- Expensive boundaries: none found
- Verdict: No regression. Entire implementations and their callers are removed together; searches found no remaining references to the deleted window/widget/native-command/event-stream implementations. There is also insufficient evidence of an existing reachable performance regression being fixed to justify a regression-fix provenance report.

- Mechanism confidence: High: both changed render branches and the lookup implementation/shared resolver cache were inspected.

- Expensive boundaries: none found
- Verdict: No regression. The diff changes the displayed shortcut source without adding work, listeners, render passes, or expensive boundaries.

The removed cancellation-suppression map could only be populated by markUserCancelled, whose production callers were exclusively in the deleted window service. Live workflows therefore do not newly cross the previously guarded paths. Disconnect still stops capture/playback, disconnects the client, clears timers/maps, and disposes response watchers/model references.
- Scaling input: Distinct tracked nonarchived agent-session resources plus resident non-agent chat models with requests, deduplicated by resource; settled transitions rather than every intermediate state drive persisted autorun events.
- Effective concurrency: Local state scanning is synchronous. Autorun transitions coalesce per session using one settle timer; standard network context shares one debounce. Eager model work is coalesced per resource, not globally serialized. Transcript writes use one store-wide Sequencer. None of these concurrency controls changes.

### Scenario 4: Submitting voice transcription to a nonvisible target chat session

- Critical path: The controller checks the current target, awaits acquisition/loading if needed, and submits one chat request. The only removed operation on this path is the unawaited \_agentsVoice.openWindow command after an accepted request. Response watching and reference ownership remain as before.
- Scaling input: One explicit or pinned target per submitted utterance; history length affects only the existing cold restoration. No new per-history-item or per-session boundary fan-out.
- Effective concurrency: Acquisition precedes request dispatch within a submission; concurrent acquisitions of the same remote resource join. Existing per-session steering/queue behavior is unchanged. The removed fire-and-forget command does not add a wait or parallel burst.
- Cache behavior: Existing model references bypass cold loads. ChatService and ChatSessionsService join in-flight remote resolution by resource. Response references are still released on response stop, failure, stale generation, or disconnect. Existing response preview watchers still dispose on completion/cancellation or timeout.
- Mechanism confidence: High: changed command removal, target routing, acquisition implementation, request submission, response watcher, and disconnect disposal were inspected.
- Magnitude uncertainty: Actual cold history sizes and remote provider latency are unknown, but both costs and their critical-path placement are unchanged by this PR.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:acquireOrRestoreLocalSession</code>: Read a cold local target session from the existing chat-session store.; cardinality: One acquisition attempt for the selected target per submission; a resident model returns an existing reference without a store read. No iteration over all sessions is added.
    - Introduced by diff: false; previous behavior: The same acquisition and cold-store read occurred before submitting the same voice request.; critical-path effect: A cold local target must be restored before submitting the request.
  - ipc at <code>src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:acquireOrLoadSession, loadRemoteSession; src/vs/workbench/api/browser/mainThreadChatSessions.ts:ObservableChatSession.\_doInitializeContent</code>: For extension-backed remote targets, request session content across the extension-host boundary; existing request dispatch also reaches the selected chat provider.; cardinality: One selected target, with same-resource cold loads coalesced and resident content reused.     - Introduced by diff: false; previous behavior: Identical loading, in-flight joining, request dispatch, and request queue semantics. The additional legacy window command was invoked afterward and did not own the model reference.; critical-path effect: Cold provider content must load before direct submission; the provider request starts the response. - Verdict: No regression. The change removes an obsolete command invocation without changing expensive request/load scheduling or cleanup. Remaining response-preview work is pre-existing, not a diff-introduced performance issue.
