# Performance review: sessions: open existing cloud automation runs without the extension provider

[PR #349488](https://github.com/microsoft/vscode/pull/349488) at `6f47d2326b77bf5500d1a047aa43ec8189d0b809`

## Findings (1)

### 1. [medium] Avoid rereading the entire transcript on every poll

**Finding ID:** `PERF-466180C7D2DA`  
**Location:** <code>src/vs/workbench/contrib/sessions/providers/copilotChatSessions/browser/cloudAutomationTaskConversations.ts:197</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Sequential GitHub task/event HTTP requests, desktop IPC response bodies, and repeated JSON parsing and event allocations  
**Scaling:** For N events, each read performs one task GET plus P event-page GETs, normally P = ceil(N/100), capped at 100 pages. Both polling loops repeat this traversal after a five-second delay; ID deduplication happens only after fetching. Different task IDs do not coalesce.  
**Outcome:** Excessive recurring network/IPC traffic and transcript-size-dependent latency before newly generated output can be observed  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Without the extension provider, core did not load or poll task transcripts. Existing automation-history refreshes read run summaries and active task details, not every event page. The extension-owned route is unchanged.  
**Changed behavior:** The new read() always starts event pagination at page 1. Both the active-history scheduler and followReply() invoke it repeatedly, even when only a new tail event—or no event at all—has appeared.  
**Confidence:** 0.96 — The two callers, five-second rescheduling, serial pagination, page size, transport revalidation, and desktop IPC path are directly traced. This is static evidence; typical transcript size, server latency, and ETag availability determine magnitude.

**Causal diff evidence:** Added lines 195–197 create a fresh Map and restart the full page traversal for every read(); added line 239 calls read() from the rescheduled history observer, and line 294 calls it inside the reply-following loop.

Opening a long-running automation with hundreds or thousands of tool/session events, or replying to an older run, repeatedly revisits all historical pages. This consumes GitHub request capacity and delays showing fresh output behind the old-page round trips, even when most events are not rendered by this text-only adapter.

**Evidence:** read() awaits each getEvents() sequentially until the complete event total is collected. The observer reschedules five seconds after completion while the task is active and has a history listener; RemoteChatSessionRestorer subscribes to that event. followReply() likewise scans the complete history before sleeping five seconds. TasksClient.getEvents() requests one page when maxPages is omitted. Transport ETags can reduce transferred HTTP bytes but still revalidate each page, return the cached body across desktop IPC, and parse it again; in-flight sharing does not eliminate successive polls. Thus a 1,000-event run requires 11 sequential HTTP operations per iteration, not one incremental check. The downstream restorer can suppress unchanged model mutations, but not these requests or allocations.

**Suggested direction:** Separate initial full loading from ongoing observation. Use the existing page API and retained snapshot for a page-aware refresh that reconciles mutable pending events and falls back to full reconciliation on discontinuities, rather than replaying every historical page on each poll.
