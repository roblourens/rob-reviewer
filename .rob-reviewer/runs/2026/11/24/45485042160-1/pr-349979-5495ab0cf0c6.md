# Performance review: sessions: inspect a session's customizations on phones

[PR #349979](https://github.com/microsoft/vscode/pull/349979) at `5495ab0cf0c671fdafe15705c3cdb6c4f68222dd`

## Findings (1)

### 1. [medium] Avoid restoring the entire chat for cold customization inspection

**Finding ID:** `PERF-28D24476DACF`  
**Location:** <code>src/vs/workbench/contrib/sessions/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:7877</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Default-chat transcript reads and hydrated turn objects; provider runtime initialization when required by the restore.  
**Scaling:** One coalesced restore per selected cold session, with transcript work growing with that chat's history, not with the number of customization rows. Warm existing subscriptions are shared and avoid this restore.  
**Outcome:** The customization list remains loading behind unrelated chat restoration, with additional host I/O and turn-object allocation for large histories.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Catalog/drawer inspection did not restore a selected inactive chat for customization details, and getCustomizations only returned already-known \_lastSessionStates data. Full restoration was associated with paths that needed the chat rather than this new inventory-only reader.  
**Changed behavior:** Opening the read-only inspector for a listed but host-unrestored session now issues a restoring session subscription and waits for full default-chat hydration before receiving its inventory.  
**Confidence:** 0.96 — Traced the new inspector through observeSessionCustomizations and the subscription manager to AgentService.subscribe's missing-snapshot branch, then through the explicit full restore and awaited provider history read. Listed sessions need not be restored: \_announceSurfacedSession publishes summaries separately. Existing subscriptions are refcounted, so this finding specifically concerns cold sessions, not every opening or every customization.

**Causal diff evidence:** The new acquireSessionCustomizationState method calls connection.getSubscription(StateComponents.Session, cached.backendUri, 'SessionCustomizations') at line 7877 for any eligible catalog-cached session. Previously getCustomizations immediately above only read \_lastSessionStates; opening the drawer did not acquire a session subscription for inspection.

After reconnecting to a host or selecting an inactive session whose state has been evicted, opening Customizations can wait for SDK initialization and the selected chat's entire transcript to be read and hydrated. Long-running chats therefore incur history-sized I/O, allocation, and latency merely to display the inventory.

**Evidence:** MobileCustomizationsInspector.open calls observeSessionCustomizations at mobileCustomizationsInspector.ts:177; that method acquires this reference and waits for sub.verifiedValue. AgentSubscriptionManager.getSubscription (agentSubscription.ts:1130-1183) sends subscribe on a cache miss. AgentService.subscribe (agentService.ts:12072-12090) restores a missing session snapshot; \_doRestoreSession invokes \_restoreSessionState with { kind: 'full' } at 14705. That path awaits agent.materializeChat at 14980 and \_getChatMessages at 15190, which awaits provider.chats.getMessages and hydrateTurns at 10861-10870. Copilot's \_getChatMessages (copilotAgent.ts:9694-9744) can resolve/resume the runtime; its persisted-history path also reads the journal in pages (9778 onward). None of this chat history is consumed by the inspector.

**Suggested direction:** Reuse an already-held session snapshot for inspection and show unavailable for cold sessions until a passive inventory capability is available, rather than creating a normal restoring subscription from this read-only path.
