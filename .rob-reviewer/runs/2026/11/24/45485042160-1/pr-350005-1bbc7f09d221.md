### Scenario 3: Start a due or manual automation using a signed-out BYOK model that has a configuration schema

- Critical path: Once readiness succeeds, \_startRun follows the existing allocateSession, durable running-state mutation, createSession, link-session mutation, and startSession sequence. These are execution prerequisites, not work performed for each model candidate.
- Scaling input: R eligible pending runs. Allocation and session creation occur once per run that needs a new session, not once per catalog model. Existing previous-session targets can reuse sessions.
- Effective concurrency: \_startingRuns prevents duplicate starts per run; durable mutations are serialized through \_mutationTail. Different runs may start concurrently, while previous-session starts are sequenced per automation. None of these concurrency rules changes.
- Cache behavior: Readiness uses cached catalogs. Existing SDK-client acquisition reuses \_client and coalesces in-flight startup through \_ensureClientHealing/\_clientStarting; the PR does not change those caches or startup scheduling.
- Mechanism confidence: High for the changed readiness gate and traced scheduler/allocation/storage sequence; downstream execution machinery is unchanged.
- Magnitude uncertainty: Pending-run counts and execution durations are unmeasured. Expected work from newly functioning automations does not independently establish a regression.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts: \_mintSessionUri</code>: Check candidate session data-directory existence while selecting a new session URI.; cardinality: Normally one existence check per newly allocated session; additional checks only for candidate collisions. No model-count multiplier.
    - Introduced by diff: true; previous behavior: Unchanged allocation path was already reachable for authenticated automations and signed-out BYOK models without copied schemas. Copied-schema BYOK models were incorrectly blocked before allocation; this PR intentionally enables their requested execution.; critical-path effect: Completes before a new automation session is allocated.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts: \_createProviderSession</code>: Prepare session storage and record default-chat storage identity before provider chat creation.; cardinality: One existing storage-preparation sequence per newly created session; not per readiness check or model.
    - Introduced by diff: true; previous behavior: Same session-creation implementation and storage work; newly reachable only because valid schema-bearing signed-out selections now pass readiness.; critical-path effect: Existing prerequisite to creating a runnable session.
- Verdict: Enabling the requested automation execution is not an actionable performance regression. No redundant starts, per-model boundary calls, defeated coalescing, or changed concurrency policy is introduced.
