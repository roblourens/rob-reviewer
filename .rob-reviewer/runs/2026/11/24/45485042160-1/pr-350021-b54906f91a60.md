## Findings (2)

### 1. [medium] Release text models resolved only to snapshot a selection

**Finding ID:** `PERF-EFD3351CEC1D`  
**Location:** <code>src/vs/workbench/contrib/chat/common/attachments/chatFileAttachmentSnapshots.ts:60</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Full text-file models, text buffers, and model listeners retained in the long-lived TextFileEditorModelManager.  
**Scaling:** One retained model per distinct previously unloaded selected file, potentially across many messages. Retention scales with whole source-file sizes, not selection sizes or the 16 MiB message limit; already loaded models are reused.  
**Outcome:** Accumulating renderer memory and associated GC/model-service overhead throughout the window lifetime.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The submission path passed selection locations through as URI/range attachments; it did not create an unowned client text-file model during snapshot preparation.  
**Changed behavior:** Preparing a selected file whose editor model is not loaded now directly resolves a full TextFileEditorModel and retains no disposable reference or cleanup handle.  
**Confidence:** 0.99 — The unloaded-selection trigger, strong manager retention, absent success-path disposal, and existing reference-counted cleanup mechanism are explicit in the traced code. Only the number and size of files users attach are uncertain.

**Causal diff evidence:** The newly added fallback at line 60 calls this.textFileService.files.resolve(uri), extracts textEditorModel, and never releases the resolved model after textSnapshot or on failure.

Sending selections from closed files keeps the full source buffers and associated editor models alive after submission or chat closure. Repeating this with distinct files accumulates renderer memory even when only a few selected lines were sent.

**Evidence:** Selections can be attached without opening their files through chatContextActions.ts:349-360, or their editor can be closed before submission; ChatAttachmentModel.asFileVariableEntry retains only uri/range (chatAttachmentModel.ts:189-196). TextFileEditorModelManager.doResolve creates/registers a model and stores it in mapResourceToModel; successful resolution leaves it there (textFileEditorModelManager.ts:429-448,458-488,537-550). Its automatic disposal only handles failed resolution, not successful snapshot extraction. ResourceModelCollection provides the existing lifecycle-safe alternative: createModelReference resolves the shared file model and destroyReferencedObject waits for canDispose before disposing it (services/textmodelResolver/common/textModelResolverService.ts:76-80,132-167). No cleanup in prepare releases the directly resolved model, including when a later attachment fails.

**Suggested direction:** Acquire a scoped ITextModelService.createModelReference when resolution is needed and dispose that reference in finally after capturing the selection, preserving ownership of models already held by editors.

### 2. [medium] Bound the filesystem read before allocating oversized attachments

**Finding ID:** `PERF-93E931B16D6F`  
**Location:** <code>src/vs/workbench/contrib/chat/common/attachments/chatFileAttachmentSnapshots.ts:68</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Bytes read from disk and the full-file native buffer allocated by the local filesystem process.  
**Scaling:** One unbuffered read for each newly captured clean file, processed serially until the first failure; the offending read scales with the entire file size, not the remaining per-message budget. Existing snapshots skip the content read.  
**Outcome:** Large transient memory pressure and excessive disk I/O, potentially exhausting filesystem-process memory on very large attachments.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Cloud submissions did not perform this local snapshot read; files were represented by URI references, and the cloud file picker was restricted to images.  
**Changed behavior:** Submitting a clean device-file attachment now calls IFileService.readFile before request acceptance, relying on limits.size to prevent oversized reads.  
**Confidence:** 0.98 — The newly awaited call, unrestricted file-picker route, unbuffered preference, parallel validation, and uncancellable regular-file native read are all traced in repository code. Exact memory duration and frequency of oversized attachments are unmeasured.

**Causal diff evidence:** The new prepare() implementation adds fileService.readFile(uri, { limits: { size: remaining } }, token) at line 68, and chatServiceImpl.ts:1674 awaits prepare() for cloud submissions. Cloud registrations also newly enable unrestricted file attachments.

Attaching an oversized dataset, archive, or binary can consume hundreds of MiB or GiB of filesystem-process memory and disk I/O merely to reject the message, despite the advertised 16 MiB budget.

**Evidence:** FileService.doReadFile sets preferUnbuffered: true (src/vs/platform/files/common/fileService.ts:558-573). doReadFileStream starts the content read alongside validateReadFile rather than awaiting its size check, and readFileUnbuffered passes no size limit to provider.readFile (:604-641, :701-728). For local files, DiskFileSystemProviderClient.readFile sends a readFile IPC; DiskFileSystemProvider.readFile uses Promises.readFile(fd) for regular files and does not consult the cancellation token (src/vs/platform/files/node/diskFileSystemProvider.ts:223-243). Thus even when the parallel stat rejects the attachment, an already-issued native read still reads and allocates the entire file. The existing readFileStream path instead checks limits incrementally through files/common/io.ts:91-95,122-125.

**Suggested direction:** Use the existing bounded readFileStream path and buffer only its size-limited output; optionally reject from a preliminary stat as well. Do not rely on readFile's parallel metadata validation to bound allocation.
