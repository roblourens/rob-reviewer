## Findings (1)

### 1. [medium] Time-slice the encoding-loss check before saving large files

**Finding ID:** `PERF-60E9925002D9`  
**Location:** <code>src/vs/workbench/services/textfile/common/encoding.ts:289</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Workbench main-thread snapshot traversal, codec CPU, temporary encoded buffers and decoded strings, and full-text comparisons.  
**Scaling:** One uninterrupted O(N) encode/decode/compare pass per actual dirty non-UTF document save, with early exit only on a mismatch. Same-version saves are coalesced and saves serialize per model, but Save All starts distinct documents concurrently and their synchronous scans execute on the same thread.  
**Outcome:** Dropped frames and blocked editor input during validation, plus additional save latency before any file write starts.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The model immediately handed one snapshot to textFileService.write. On the normal desktop/remote buffered path, encoding was pull-driven and separated by awaited chunk writes; there was no full-file validation task before writing.  
**Changed behavior:** Every non-bypassed save in a non-UTF encoding now performs a complete synchronous encode/decode/compare pass in the workbench before issuing the existing file write.  
**Confidence:** 0.98 — The production save path directly awaits this function, and there is no await or scheduling boundary inside its snapshot loop. Desktop and remote buffered writes previously awaited provider IPC between encoded chunks. The UI-thread blocking mechanism and linear scaling are statically established; the exact pause depends on document size and codec.

**Causal diff evidence:** The added loop at encoding.ts:289-298 synchronously calls encoder.write, decoder.write, startsWith, and substring until the snapshot ends. The added await at textFileEditorModel.ts:1043 requires that entire loop to finish before textFileService.write at line 1053 can start.

Saving or auto-saving a multi-megabyte Windows-1252/Shift-JIS document containing entirely representable text blocks typing and rendering for the full validation pass, then encodes the file again for writing. Save All can run these scans back-to-back for distinct dirty files. UTF encodings and Save Anyway bypass the scan.

**Evidence:** TextFileEditorModel.doSaveSequential calls isLossyEncoding before write (textFileEditorModel.ts:1041-1053). After the module-load await, isLossyEncoding consumes the entire readable synchronously (encoding.ts:276-303). Previously toEncodeReadable encoded lazily in read() (encoding.ts:217-263), and FileService.doWriteReadableBufferedQueued awaited doWriteBuffer per chunk (fileService.ts:1425-1446); the desktop provider forwards writes over IPC. The new validation adds a full-file uninterrupted renderer task even on that buffered path.

**Suggested direction:** Keep validation before writing, but perform it in a worker or in bounded character/time slices with actual event-loop yields, preserving the captured snapshot and encoding. Do not rely solely on snapshot chunk boundaries, since a returned piece can itself be large.
