### Scenario 1: Delete a resource's last descendant while retaining an ancestor with its own element; also delete ordinary leaves, missing paths, or whole subtrees.

- Critical path: ResourceTree.delete synchronously computes a relative path, traverses path segments, removes the target, and unwinds ancestor pruning. The added element check is a plain field read on that existing unwind path.
- Scaling input: Path length/depth controls deletion work. Retained nodes correspond to explicitly added, still-live elements and their ancestor paths, not deletion history.
- Effective concurrency: One synchronous traversal per call; no tasks, promises, subprocesses, or concurrent work introduced.
- Cache behavior: No external cache or negative-cache state. Map lookups and size checks remain in-memory; absent paths terminate early. Explicit deletion and clear still remove retained elements.
- Mechanism confidence: High: the complete ResourceTree implementation, PathIterator, URI-relative-path implementation, and changed test establish the mechanism directly.
- Magnitude uncertainty: No timings measured; additional field checks are bounded by the existing traversal depth.
- Expensive boundaries: none found
- Verdict: No regression. Previously pruning could discard a still-live ancestor element; now that element and required ancestors remain until explicitly removed. This is required ownership, not unbounded retention, and does not change traversal complexity.

### Scenario 2: Update Source Control resource groups after files are removed or changed.

- Critical path: Existing extension-host batching delivers resource splices; the main thread applies them and invalidates each affected group's tree. A later resourceTree getter synchronously rebuilds the group using add before rendering.
- Scaling input: One batched update can contain several groups and slices. Rebuilding scales with the resources and path depths in an accessed group, not with one IPC per resource.
- Effective concurrency: Extension-host updates are debounced and grouped. Main-thread splice application and each lazy rebuild are synchronous; the existing repository barrier can delay update application.
- Cache behavior: Group tree is lazy and reused on warm reads; splice invalidates it. The next read builds a fresh tree. Neither invalidation nor cache lifetime changes.
- Mechanism confidence: High: inspected extension-host batching, main-thread splice entry point and application, and resourceTree getter/invalidation.
- Magnitude uncertainty: Group sizes and provider timings vary, but none of those costs are increased by this diff.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/common/extHostSCM.ts:eventuallyUpdateResourceStates; src/vs/workbench/api/browser/mainThreadSCM.ts:$spliceResourceStates</code>: Send grouped SCMRawResourceSplices from extension host to main thread.; cardinality: One call for all nonempty updated-group snapshots collected by the existing 100 ms debounce, per source-control instance.

- Verdict: No regression: this production workflow never reaches the changed deletion condition. Existing IPC, allocations, and rebuilding are unchanged.
