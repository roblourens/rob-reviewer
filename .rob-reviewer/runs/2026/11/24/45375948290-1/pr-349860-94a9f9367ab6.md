- Critical path: Load the runner and dependencies, discover selected test files, create the HTTP server, launch a browser/context/page, discover and compress CSS paths, load renderer.html and test modules, run tests, and close the browser. Selfhost additionally starts one runner subprocess and consumes its stdout.
- Scaling input: N selected browser-compatible test files and their shared dependency graph, C CSS files, T test/hook events, and filesystem requests explicitly made by tests. --runList entries are normalized and deduplicated in a Set before file filtering.
- Effective concurrency: Without workers, requested browsers run concurrently unless --sequential is set; module imports within each page are sequential. Individual test filesystem requests follow test scheduling. The diff preserves these policies and the default browser list.
- Cache behavior: Node dependencies remain cached per runner process; browser modules are cached per page. Fresh browser contexts do not share an application module cache across attempts. OS/package caches can reduce cold filesystem and installation costs. No cache invalidation, negative caching, or request coalescing changes were found.
- Mechanism confidence: High confidence from complete runner diff and traced selfhost, renderer, and cleanup paths that expensive operation counts and scheduling are preserved.
- Magnitude uncertainty: Native TypeScript/ESM startup overhead was not measured. No changed scaling mechanism establishes an actionable regression.
- Expensive boundaries:

### Scenario 2: Run selected browser tests in parallel workers and rerun failures

- Critical path: Discover modules, calculate the capped worker count, spawn workers, load modules in every worker page, claim and execute files, collect worker reports, then optionally rerun unresolved failures in fresh single browsers.
- Scaling input: N selected files, W capped workers, B requested browsers, and R configured retries. W is limited by requested count, CPUs, and one worker per 2 GB; with --runList it is additionally limited by file count and the existing 75-files-per-worker policy.
- Effective concurrency: At most W worker processes for one browser at a time; browsers serialize when workers apply. Only the first attempt uses workers. Reruns run sequentially in one browser per browser type. CI requests four workers, subject to existing caps.
- Cache behavior: Each worker has its own Node/page module caches and loads all N selected files. File claims cache successful ownership, claimAll caches its boolean result, and recorded-file Sets suppress duplicate log entries. Failed ownership claims are not negatively cached, unchanged. HTTP claim requests retry at most three times on failure.
- Mechanism confidence: High confidence: worker policy, shared helper implementation, page RPCs, and rerun call paths were inspected and compared with the diff.
- Magnitude uncertainty: The existing W\*N module loading and claim overhead can be substantial, but this PR does not introduce or amplify it.
- Expensive boundaries:
  - subprocess at <code>test/unit/browser/index.ts:runFirstAttemptInWorkers and test/unit/parallel.ts:runInWorkers</code>: Spawn runner workers, each of which launches a browser.; cardinality: W runner children and W browser launches per browser's first attempt, plus at most R single-browser rerun launches; no worker fan-out on reruns.
    - Introduced by diff: false; previous behavior: Identical worker caps, arguments, spawning, and rerun placement; \_\_filename becomes import.meta.filename.; critical-path effect: First-attempt completion waits for all workers; retries follow report aggregation.
  - network at <code>test/unit/browser/renderer.html:createTestFileClaims and loadModules</code>: Load test modules and issue synchronous localhost file-claim RPCs.; cardinality: All N files load in each worker page. Up to approximately W\*N normal claim attempts, plus per-worker start and successful-file recordRun calls; failure retries are capped at three per RPC. Claims operate per file, not per test.
    - Introduced by diff: false; previous behavior: The same renderer helper, import loop, claim scheduling, and retries were used.; critical-path effect: Imports precede execution; synchronous claim calls gate selection of subsequent suites.
  - filesystem at <code>test/unit/parallel.ts:createTestFileClaims, writeWorkerReport, and runInWorkers</code>: Atomically create claim directories, record run order and worker reports, read aggregated reports, and remove temporary worker storage.; cardinality: Claim filesystem attempts follow RPC cardinality after ownership caching; reports occur once per worker; cleanup once per worker group.
    - Introduced by diff: false; previous behavior: parallel.ts is unchanged, including caches, filesystem operations, and cleanup.; critical-path effect: Claims gate work allocation; report reads and cleanup precede aggregate completion.
- Verdict: No reportable regression: the migration preserves effective concurrency, file-level ownership, and single-browser retries.

### Scenario 3: Stream test results to selfhost consumers or produce console/JUnit reports in browser and Electron runners

- Critical path: Load reporter modules, construct reporters for each runner attempt, serialize relevant test events, and write output. Electron waits for reporter drain before treating its renderer as done.
- Scaling input: T test events, F failures with their existing diagnostic payloads, optional coverage events, and one reporter set per attempt/worker.
- Effective concurrency: Event callbacks perform synchronous JSON construction/stringification and issue stdout writes; there is no newly introduced batching, queue, or parallel reporter creation. JUnit and console reporters are paired in the existing --tfs path.
- Cache behavior: Reporter modules are loaded once per process through normal module caching. Built-in and custom reporter resolution still use createRequire with CommonJS resolution. No per-event imports or new retained history are introduced.
- Mechanism confidence: High confidence from both reporter diffs, browser reporter construction, Electron drain handling, and selfhost launch arguments.
- Magnitude uncertainty: No throughput measurement was performed; the added failure-only object spread and callback wrapper do not establish a meaningful performance degradation.
- Expensive boundaries:
  - serialization at <code>test/unit/fullJsonStreamReporter.mts:writeEvent and failure callback</code>: JSON.stringify each emitted JSON-stream event, including failure and coverage payloads.; cardinality: One serialization per emitted event; failure construction adds one small intermediate clean(test) object but does not copy the potentially large actual/expected payloads.
    - Introduced by diff: false; previous behavior: The reporter serialized the same event families and failure payloads. currentRetry is now omitted; failure fields are assembled using object spread rather than assignment.; critical-path effect: Synchronous work occurs during reporting, as before.
  - IPC at <code>test/unit/fullJsonStreamReporter.mts:writeEvent and .vscode/extensions/vscode-selfhost-test-provider/src/vscodeTestRunner.ts:run</code>: Write JSON lines to stdout for the selfhost output scanner.; cardinality: One stdout write per emitted event, unchanged; the write callback now resolves through a wrapper.
    - Introduced by diff: false; previous behavior: The same stream writes and lastEvent-based drain existed.; critical-path effect: Electron explicitly awaits drain on completion; live selfhost results arrive through the pipe.
  - filesystem at <code>test/unit/reporter.mts:importMochaReporter/applyReporter and test/unit/browser/index.ts:withReporter</code>: Resolve/load reporter modules and write optional JUnit output via mocha-junit-reporter.; cardinality: Reporter module loads are cached per process; JUnit files remain separated per browser, worker, and attempt.
    - Introduced by diff: false; previous behavior: The same reporters were eagerly loaded, resolved, and constructed. Electron now requires reporter.mts instead of reporter.js.; critical-path effect: Reporter setup precedes events; report output is part of completing the test attempt.
- Verdict: No reportable regression: event cardinality, large-payload handling, stream lifetime, and reporter resolution are preserved.

### Scenario 4: Collect diagnostics after a browser test run stalls

- Critical path: Only after the existing inactivity watchdog fires: probe page responsiveness with a ten-second timeout, enumerate processes, optionally sample browser processes on macOS, then exit with failure.
- Scaling input: P matching browser processes and total system process count for the ps snapshot; this is a failure-only path, not normal test startup or execution.
- Effective concurrency: One diagnostic run per fired watchdog. macOS samples matching P processes concurrently with Promise.all, each with a 180-second subprocess timeout; unchanged scheduling.
- Cache behavior: No diagnostic cache; each stall takes one fresh process snapshot. The watchdog interval is cleared before diagnostics and disposed after normal execution.
- Mechanism confidence: High confidence in diagnostic-only reachability, one-shot watchdog behavior, and preserved process-count scaling.
- Magnitude uncertainty: Successful sampling may take longer than previously invalid arguments; duration and matching process count are not measured.
- Expensive boundaries:
  - IPC at <code>test/unit/browser/index.ts:reportStallAndExit</code>: Probe document.readyState using page.evaluate.; cardinality: One probe per watchdog-triggered diagnostic run.
    - Introduced by diff: false; previous behavior: The same timed probe preceded process collection.; critical-path effect: Failure exit waits for the response or the existing ten-second timeout.
  - subprocess at <code>test/unit/browser/index.ts:dumpBrowserProcesses</code>: Run ps on non-Windows platforms and sample each matching browser process on macOS.; cardinality: One ps process; on macOS, P concurrent sample processes.
    - Introduced by diff: false; previous behavior: The same execFile calls, Promise.all placement, and timeouts existed. Converting pid to String makes the existing sample command arguments valid and can enable intended diagnostic work that previously failed.; critical-path effect: Diagnostics finish before failure exit, off the successful test path.
  - filesystem at <code>test/unit/browser/index.ts:dumpBrowserProcesses</code>: Create the diagnostic output directory and write native samples through the sample subprocess.; cardinality: One recursive mkdir and up to P sample files per macOS diagnostic run.
    - Introduced by diff: false; previous behavior: The same output directory, filenames, and intended sampling operations existed.; critical-path effect: Only delays an already-stalled run's diagnostic failure exit.
- Verdict: No reportable regression: the only substantive change repairs intended, bounded failure diagnostics rather than adding work to an important successful path.

- Critical path: The existing typecheck-test-unit command now checks browser and reporter sources as well as node runner sources. Ripple reads the runner patterns and dependency references before selecting test jobs.
- Scaling input: The newly included browser runner and two reporter modules, their bounded directly followed JavaScript dependency surface with maxNodeModuleJsDepth=1, and repository graph size for the existing planner.
- Effective concurrency: No new subprocess loop, worker count, or CI job fan-out is introduced by the changed configuration. Type checking remains one tsc invocation; planning remains the existing planner invocation.
- Cache behavior: The unit tsconfig has noEmit and skipLibCheck and introduces no custom cache. Ripple's existing cached binary and test-selection behavior are unchanged; renamed .mts reporters are now covered by the runner patterns.
- Mechanism confidence: High confidence that compiler inclusion expands intentionally and runner-pattern coverage preserves the renamed files' dependency role.
- Magnitude uncertainty: Additional typecheck time is unmeasured; no unbounded traversal, repeated compiler invocation, or unintended test-selection expansion was established.
- Expensive boundaries:

- Verdict: No reportable regression: the added bounded checking is the migration's intended behavior and the planner update preserves existing coverage.
