# Performance review: Artifact integrations: keep references in the References pill and present item actions on their item

[PR #347045](https://github.com/microsoft/vscode/pull/347045) at `eac3850a2d325dd543bb8cc3665944651c25e746`

## Findings (1)

### 1. [medium] Reuse or evict cached detail snapshots after model disposal

**Finding ID:** `PERF-4284F50F8ADF`  
**Location:** <code>src/vs/workbench/api/browser/mainThreadChatArtifactIntegrations.ts:338</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** Retained ArtifactDetails object graphs, including item arrays and their strings/resources  
**Scaling:** Retained memory grows with the total size of every details section acquired across all live artifact resources; partial/load-more lists increase each retained graph, and changing presentation details IDs can grow the map because removed IDs are never evicted.  
**Outcome:** Increased retained heap and subsequent GC pressure while browsing artifact details in a long-lived session  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The bridge retained the resource's original initialDetails snapshot, but a later details snapshot was owned by the active ExtensionArtifactDetails model and became collectible when that model was disposed.  
**Changed behavior:** Every result or update received by a details model is now stored in latestDetails, while initialDetails remains retained too; disposing the model does not remove either cache entry, and acceptState does not prune IDs that are no longer exposed.  
**Confidence:** 0.95 — The retention path and absence of eviction are explicit in the changed code, and model/resource ownership confirms that UI model disposal no longer releases the latest graph. Exact heap impact depends on extension list sizes and how many artifact details users browse, which affects severity rather than the mechanism.

**Causal diff evidence:** The added callback at line 338 stores each full details snapshot in latestDetails; the same diff adds latestDetails as a resource-lifetime Map and leaves the existing initialDetails record intact.

After a user opens or pages details for many artifacts, those full snapshots remain reachable even after each details view closes; long-lived sessions therefore accumulate duplicate list data and consume more memory until the artifact resource is released.

**Evidence:** ExtensionArtifactDetails.accept invokes the new received callback for both the acquire result and every extension update. ExtensionArtifactResource owns latestDetails for its whole lifetime and has no delete/clear path. The existing initialDetails record still holds the original full snapshot. The proposed API supports partial details with loadMore, so these snapshots can contain large item arrays. SessionArtifacts keeps an artifact integration reference for each record in the focused chat, so closing the details UI disposes the model but not the resource or this cache.

**Suggested direction:** Use a single per-ID snapshot cache seeded from initialDetails and replace its entry on updates (keeping canLoadMore separately), prune IDs when acceptState removes them, and avoid retaining a second full snapshot after the last details model closes unless it is required for a pending item-action presentation.

### Scenario 2: Open, update, page, and close artifact detail lists across a focused session

- Critical path: Opening details awaits the artifact model's details acquisition and extension-host result. Later updates/loadMore cross the extension-host boundary before rendering. Closing the details UI disposes the model, but the newly added latestDetails cache remains reachable from the live artifact resource.
- Scaling input: Total detail snapshot size across every details ID acquired for every live artifact record; item arrays can be partial/paged, and state revisions may expose different IDs.
- Effective concurrency: ArtifactBinding coalesces simultaneous consumers of the same details ID behind one provider model. Different artifacts and IDs remain independent. The regression is retained state after consumers reach zero, not concurrency.
- Cache behavior: Cold creation retains initialDetails for every exposed section. The diff adds a second resource-lifetime latestDetails cache populated by acquire results and updates. Entries are neither removed when the last model closes nor pruned when state stops exposing an ID.
- Mechanism confidence: High: received snapshots are stored in a Map owned by ExtensionArtifactResource, initialDetails is still retained, and there is no eviction path before resource disposal.
- Magnitude uncertainty: Actual heap growth depends on extension snapshot sizes, paging representation, records in the focused chat, and browsing behavior; these affect severity but not the retention mechanism.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadChatArtifactIntegrations.ts ExtensionArtifactDetails constructor</code>: Acquire details and serialize the complete ArtifactDetails snapshot from the extension host; cardinality: One acquisition per active details model, coalesced by the platform binding for same-artifact/same-ID consumers
    - Introduced by diff: false; previous behavior: The same acquire and serialization occurred, but returned/updated snapshots became collectible after the details model was disposed.; critical-path effect: The initial acquire is awaited by the details view; subsequent change notifications update rendering
  - IPC at <code>src/vs/workbench/api/browser/mainThreadChatArtifactIntegrations.ts ExtensionArtifactDetails.loadMore</code>: Load another details page through the extension host; cardinality: One IPC per user load-more request

- Verdict: Reportable cache-lifecycle regression: full updated snapshots survive details-model disposal and duplicate the retained initial snapshot, increasing heap and GC pressure over a long-lived browsing session.
