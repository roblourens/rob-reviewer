# Performance review: chat: log a Welcome graphic trigger with multiple editor windows open

[PR #347047](https://github.com/microsoft/vscode/pull/347047) at `dc1fc222aa2c765201b5adad8e9c789748c8b295`

## Findings (1)

### 1. [low] Defer telemetry-only window enumeration until banner exposure

**Finding ID:** `PERF-F0857139B2DD`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentsWindowGraphic.ts:86</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** renderer-to-main-process IPC calls plus allocation and serialization of metadata for every open editor window  
**Scaling:** One new IPC occurs per \`AgentsWindowGraphic\` construction and per graphic-setting change in each non-auto arm; each response does O(open editor windows) mapping/serialization, and page rebuilds or multiple editor windows create additional calls, with in-flight calls not cancelled on disposal.  
**Outcome:** excessive IPC and avoidable main-process/renderer work  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Only the \`Auto\` variant enumerated windows because its rendered design depended on the count; fixed variants and \`None\` rendered without any \`getWindows\` boundary call.  
**Changed behavior:** Constructing \`AgentsWindowGraphic\` and every graphic-setting change now starts editor-window enumeration for every variant instead of only when \`Auto\` needs the result.  
**Confidence:** 0.98 — The changed guard, constructor call from \`buildCategoriesSlide\`, banner visibility gate, and Electron \`ProxyChannel\` implementation were traced directly. The exact IPC duration varies by platform and window count, but its new reachability and eager placement are explicit and tests assert the increased request counts.

**Causal diff evidence:** At RIGHT line 86 the previous \`Auto\` guard is replaced by an unconditional \`variant.read(reader)\`, so the unchanged async \`countEditorWindows(...)\` call below is now reached for \`None\`, \`WindowComparison\`, and \`ManyWindowsToOne\` as well as \`Auto\`.

Opening or rebuilding the Welcome page now performs unnecessary renderer/main-process IPC and main-process window-list serialization in all non-auto experiment arms, including when AI/agent mode hides the banner and no trigger can be logged. This adds avoidable work to a common startup surface and multiplies across Welcome-page instances or rebuilds.

**Evidence:** \`GettingStartedPage.buildCategoriesSlide\` always constructs \`AgentsWindowGraphic\` before \`createAgentsBanner\` determines whether the banner is visible. The autorun now calls \`countEditorWindows\`, whose \`hostService.getWindows({ includeAuxiliaryWindows: false })\` delegates through \`NativeHostService\`'s \`ProxyChannel\` to the Electron main process; the main-process handler maps every open main window and returns all metadata. The updated test demonstrates one request even for \`None\` and a new request on every variant change.

**Suggested direction:** Keep the existing eager count only for \`Auto\`; for fixed/none variants, start and coalesce the count when \`visible && isExposed\` first becomes true (or otherwise activate it lazily from the banner), so hidden/unavailable banners and category rebuilds do not issue telemetry-only IPC.
