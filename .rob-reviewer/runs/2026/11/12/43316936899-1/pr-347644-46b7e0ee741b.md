# Performance review: issueReporter: simple and detailed layouts, and fewer steps to report

## Findings (2)

### 1. [medium] Do not block Preview on title generation

**Finding ID:** `PERF-156A6396262F`  
**Location:** <code>src/vs/workbench/contrib/issue/browser/issueReporterOverlay.ts:1804</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** One foreground language-model request, including extension registration/model selection and remote model response streaming  
**Scaling:** Each simple-layout report previewed with a blank title adds one uncached foreground model request; latency scales with cold extension/model activation and network/model response time, with the new timeout allowing 10 seconds before fallback.  
**Outcome:** Blocked Preview critical path and multi-second interaction latency before attachment upload/GitHub preview can begin.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Preview validation previously required a title and then synchronously built and submitted the draft; language-model title generation ran only when the user explicitly clicked the Generate button, so Preview itself did not initiate or await this remote work.  
**Changed behavior:** The added await automatically invokes title generation when a simple report has no title. The listener waits for installed extensions, selects a Copilot model, and calls ChatUtilityModelService.sendRequest as a foreground request; generateTitleForPreview blocks submission until it resolves or the new 10-second timeout falls back.  
**Confidence:** 0.99 — The changed await, 10-second bound, foreground model call chain, expected blank-title trigger, and before/after Preview behavior are all explicit in code and tests. Only the typical model duration and experiment prevalence are uncertain.

**Causal diff evidence:** The added line 1804 moves the pre-existing optional AI-title operation onto the mandatory Preview path for blank titles; the deleted submit implementation never requested or awaited title generation.

The simple layout explicitly makes the title optional, so leaving it blank is the expected path. For users with a Copilot model, clicking Preview can now sit at “Generating title...” for network/model latency—up to 10 seconds—before the report can progress, even though a local first-line fallback is already available.

**Evidence:** issueReporterOverlay.ts:1804 awaits generateTitleForPreview before model update, body construction, and onDidSubmit. That method races requestGeneratedTitle against TITLE\_GENERATION\_TIMEOUT=10\_000. issueReporterController routes the request through extensionService.whenInstalledExtensionsRegistered, selectLanguageModels, and chatUtilityModelService.sendRequest; ChatUtilityModelService marks this request non-background and calls languageModelsService.sendChatRequest. The added test explicitly advances 10,000 ms before observing submission.

**Suggested direction:** Keep Preview non-blocking: start/debounce title generation while the user edits or leaves the description, consume it only if already ready, and otherwise immediately submit with getFallbackIssueTitle. Leave the existing Generate button for users who choose to wait explicitly.

### 2. [medium] Open the reporter before doing the automatic capture

**Finding ID:** `PERF-CFD7DFF4D932`  
**Location:** <code>src/vs/workbench/contrib/issue/electron-browser/nativeIssueFormService.ts:210</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** A fixed 100 ms timer followed by one native IPC capturePage, full-window JPEG encoding/base64 conversion, and browser image decode  
**Scaling:** Every new simple-layout report pays at least the fixed 100 ms delay; the capture, encoding, transferred bytes, base64 allocation, and decode grow with the source window's pixel count (notably on high-DPI/4K displays).  
**Outcome:** Increased time before the issue reporter editor or auxiliary window becomes visible, plus avoidable CPU and allocation pressure on that interaction.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, the wizard created its input and opened the editor/auxiliary window directly; opening a report did not first wait for a screenshot or repaint timer.  
**Changed behavior:** For every simple-layout report, openNewReporter now awaits captureWindow before it creates the input or starts opening either host. captureWindow({ afterRepaint: true }) waits 100 ms, crosses to Electron capturePage, JPEG-encodes the full window, converts it to a base64 data URL, and decodes that image before resolving.  
**Confidence:** 0.98 — The fixed delay, IPC/capture/encode/decode call chain, placement before all visible opening work, one-per-simple-report cardinality, and pre-diff absence are explicit in changed code. Exact capture duration varies by hardware and pixel count, affecting severity but not the mechanism.

**Causal diff evidence:** The added line 210 introduces \`await this.screenshotToolService.captureWindow(sourceWindow, { afterRepaint: true })\` ahead of all reporter construction/opening; no equivalent capture existed on this path before the PR.

With the experimental simple layout selected, Help: Report Issue has a guaranteed extra 100 ms pause and then waits for a full-window native capture before showing any reporter UI. The delay and allocation cost are larger on high-resolution displays.

**Evidence:** nativeIssueFormService.ts:210 is before both createInstance and auxiliaryWindowService.open/editorService.openEditor. screenshotToolService.captureWindowArea first awaits REPAINT\_DELAY=100, then awaits hostService.getScreenshot; NativeHostService forwards that across the native boundary to webContents.capturePage and toJPEG(95), after which the renderer base64-encodes and decode()s the full image. openingReporter also serializes concurrent opens, so none of this is off the user-visible critical path.

**Suggested direction:** Keep the automatic attachment, but remove it from the reporter's visible-open critical path: wait only for an actual next-paint/compositor signal instead of a fixed 100 ms and begin showing/constructing the reporter shell while capture processing completes, attaching the result asynchronously without allowing the reporter window into the source capture.
