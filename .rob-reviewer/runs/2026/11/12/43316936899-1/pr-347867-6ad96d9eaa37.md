### Scenario 1: An opted-in scheduled or manual automation continues the latest run's chat when that session is currently unloaded

- Critical path: Run dispatch scans retained run metadata to select the latest session, validates it through the host database, restores the session and its default chat/history, persists the running/link lifecycle, then starts the provider turn. The database, restore, chat-history load, storage writes, and provider send are on the run's critical path.
- Scaling input: One candidate session per run after selecting the latest prior run; selection scales with retained automation-run history, while restored chat data scales with the shared conversation's turn history. The effective run history is retained beyond the 50-item presentation window, but existing persistence and run-window construction already process that history.
- Effective concurrency: Run-state mutations remain globally sequenced by the existing mutation queue. Continued starts are serialized per session with ThrottlerByKey; different sessions can proceed independently. A schedule coalesces additional due occurrences while one continued run has not started.
- Cache behavior: A resident session makes the second restore and chat resolution fast-path state checks; an evicted session performs a cold provider/storage restore and loads chat history. There is no negative cache for a missing/archived candidate, but the failed candidate causes a new session whose run becomes the next candidate rather than repeated retries against the old session.
- Mechanism confidence: High confidence in the exact database, restore, persistence, and provider call path; uncertain provider-specific cost does not change the traced cardinality.
- Magnitude uncertainty: Provider restore and shared-history costs vary by provider, eviction, and conversation length. The feature is opt-in and these costs are intrinsic to preserving chat context; the diff also avoids fresh session allocation/creation, so no independent actionable regression is established.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts: canContinueSession</code>: Read the candidate session registration and list provisional-session markers.; cardinality: One targeted registration query plus one provisional-list query for the single latest candidate per opted-in run.
    - Introduced by diff: true; previous behavior: Every run skipped these validation reads and proceeded to allocate/create a new session.; critical-path effect: Both queries must complete before deciding whether to reuse or create a session.
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts: canContinueSession, \_continueAutomationSession; src/vs/platform/agentHost/node/agentHostStateManager.ts: resolveChatState</code>: Restore an evicted session and resolve its default chat history from provider/session storage.; cardinality: At most one cold session restore and one cold chat-history resolution for the selected session; repeated restore calls join or take the resident fast path.
    - Introduced by diff: true; previous behavior: A fresh empty session was created, so no previous chat history was restored; session creation had its own provider and storage cost.; critical-path effect: Cold restore/history resolution blocks starting the continued turn.
  - serialization at <code>src/vs/platform/agentHost/node/agentHostAutomationService.ts: \_markRunRunning, \_linkRunSession, \_persist</code>: Persist automation run lifecycle/link state including retained run state.; cardinality: Two existing-style durable state writes per started run; the continued path does not add a third write.
    - Introduced by diff: false; previous behavior: Fresh-session runs also persisted running and linked states in two writes.; critical-path effect: Both durable mutations precede provider turn start.
  - network at <code>src/vs/platform/agentHost/node/agentService.ts: \_startSessionMessage</code>: Send the automation prompt as a provider turn in the restored chat.; cardinality: One provider turn per non-coalesced run.
    - Introduced by diff: false; previous behavior: One provider turn was sent in a newly created chat instead of the prior chat.; critical-path effect: This is the principal run execution boundary after admission.
- Verdict: No finding. The new boundaries occur only for the opted-in reuse behavior and replace fresh-session allocation/creation; calls are one-candidate, serialized, and cold work is cached by resident session/chat state.

### Scenario 2: A continued automation becomes due while its shared chat is running a user turn or an earlier automation turn

- Critical path: The run validates and links the shared session, makes one start attempt, then waits event-driven. A terminal chat action schedules the next per-session attempt, which restores/resolves through warm state and starts the turn. No timer polling or repeated boundary loop blocks the existing user turn.
- Scaling input: Waiting work scales with the number of distinct shared sessions, not elapsed wait time. Additional due occurrences for the same automation are skipped while a run is creating or waiting, and only the earliest waiting run for a session is selected.
- Effective concurrency: ThrottlerByKey permits one active start attempt per session and coalesces requests arriving during it. Existing mutation serialization orders durable links/cancellation; separate sessions remain independent.
- Cache behavior: The initial validation usually makes the session resident. Retries after turn completion use warm session and chat state unless residency evicted the session during a long wait; per-session throttling prevents duplicate concurrent restores.
- Mechanism confidence: High confidence from the per-session throttler, continued-run map, turn terminal event path, and schedule coalescing condition.
- Magnitude uncertainty: Very long user turns and provider-specific eviction can make the eventual warm/cold distinction vary, but attempt count remains bounded and event-driven.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts: \_continueAutomationSession</code>: Restore/resolve the shared session and chat before checking admission.; cardinality: One attempt when linked and one event-triggered attempt when the blocking turn ends; no polling with wait duration.
    - Introduced by diff: true; previous behavior: Runs created independent sessions and did not wait on another turn in a shared chat.; critical-path effect: The first attempt establishes that the run must wait; the later attempt is on the continued run's start path, not the blocking user's turn path.
  - serialization at <code>src/vs/platform/agentHost/node/agentHostAutomationService.ts</code>: Persist link, cancellation, and terminal lifecycle transitions.; cardinality: One write per state transition; cancellation holds the waiter so persistence cannot race an additional start.
    - Introduced by diff: false; previous behavior: Equivalent run lifecycle transitions were already durably persisted, though there was no shared-session waiter.; critical-path effect: Link persistence precedes start; cancellation persistence prevents the waiting run from starting.
- Verdict: No finding. The diff explicitly coalesces due occurrences and serializes starts per session, avoiding polling, duplicate turns, and a concurrency burst.

### Scenario 3: Automation scheduling with multiple definitions and retained run history

- Critical path: At each earliest schedule wake, the scheduler walks available definitions. For definitions using Same Chat it scans retained runs to detect an already waiting/unlinked run, then advances cursors and performs the existing durable catalog/run write when state changes.
- Scaling input: The new waiting-run check is O(total retained runs) per Same Chat definition examined at a schedule wake; retained runs are unbounded by the 50-item presentation window. However existing claimed-run summary construction sorts retained runs and existing persistence serializes all retained runs on each claimed occurrence, which already dominates long-history schedules.
- Effective concurrency: Schedule claiming is globally sequenced through the mutation queue and creates at most one run per automation per tick; subsequent starts may run independently by session after the claim.
- Cache behavior: Run state is in-memory; there is no separate active-run index. Durable storage is rewritten through the existing storage service after changed schedule state.
- Mechanism confidence: High confidence in the O(definitions × retained runs) check and existing larger costs; low evidence that the increment creates a user-visible regression.
- Magnitude uncertainty: The number of long-lived high-frequency automations is unknown, but the added in-memory scan is not independently material relative to unchanged full-history summary sorting and durable serialization on the same due-run path.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/agentHost/node/agentHostAutomationService.ts: \_claimDueRuns, \_persist</code>: Serialize and flush the automation catalog and all retained runs after schedule cursor/run changes.; cardinality: One flush for a schedule-claim batch, as before; no per-definition flush.
    - Introduced by diff: false; previous behavior: The same full retained-run state was flushed for schedule claims.; critical-path effect: The batch flush completes before claimed state is published and runs start.
- Verdict: No finding. Although the diff adds a history scan for Same Chat definitions, it prevents duplicate waiting runs and is not shown to materially amplify the already history-scaling claim/persistence path.

### Scenario 4: Open/edit an automation dialog or configure it through the automation tool

- Critical path: The UI reads provider capability from in-memory provider/store state, renders one additional switch, and includes one metadata boolean in the existing create/update operation. Tool validation similarly performs an in-memory capability check before the existing operation.
- Scaling input: Constant work per dialog render/change and per configure invocation; customization collections and provider count are unchanged.
- Effective concurrency: No new parallel work, queue, subprocess, or fan-out. The save/configure operation retains the provider store's existing sequencing.
- Cache behavior: Capability state comes from the current connected store/initialize result; no new cache or repeated remote lookup is introduced.
- Mechanism confidence: High confidence from the dialog, tool, provider service, and store call paths.
- Magnitude uncertainty: None material; DOM and metadata additions are constant-sized.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/sessions/providers/agentHost/browser/agentHostAutomationStore.ts</code>: Send the existing automation create/update request with the continue-session metadata flag.; cardinality: One existing request per user save or accepted tool operation; payload grows by one boolean metadata property.
    - Introduced by diff: false; previous behavior: The same create/update request was sent without this metadata property.; critical-path effect: The existing request remains on save/configure's critical path.
- Verdict: No finding. The UI and tool changes add constant in-memory/DOM work and no additional boundary call.

### Scenario 5: Render automation run history when several runs share one session

- Critical path: Each history render filters the already supplied run array using a Set of session object identities, then performs the existing grouping/list rendering. Focus restoration may scan the current focus-target collection only when focus was owned by history.
- Scaling input: Linear in loaded run rows and focus targets. Effective cardinality is the currently loaded/paged history, and duplicate shared sessions reduce downstream rows and DOM work.
- Effective concurrency: Synchronous UI rendering on the existing render call; no async fan-out or boundary concurrency.
- Cache behavior: No cache is introduced; a short-lived Set is allocated per render and released. Session data is supplied by existing observable/service caches.
- Mechanism confidence: High confidence from the changed render method and history paging model.
- Magnitude uncertainty: Loaded history can be paged beyond 50, but the new linear filter replaces rendering duplicate rows, so net DOM/layout work decreases for shared sessions.
- Expensive boundaries: none found
- Verdict: No finding. The added linear filter is bounded by loaded history and avoids more expensive duplicate session-row rendering.
