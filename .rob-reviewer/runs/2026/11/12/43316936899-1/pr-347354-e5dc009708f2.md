# Performance review: Chat resources: let the agent choose how the chat shows what it records

[PR #347354](https://github.com/microsoft/vscode/pull/347354) at `e5dc009708f2c08af9baf75254536d5a6326e888`

## Findings (2)

### 1. [medium] Prune applied requests with their session lifecycle

**Finding ID:** `PERF-DE000206BE0B`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatResources/chatResourcesControl.ts:290</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** Persisted JSON bytes and reconstructed JavaScript objects for historical session/resource request entries  
**Scaling:** The stored object grows with every session that ever receives a request and every requested resource in that session (S × R), independent of how many sessions or artifacts still exist. Every control request pass parses and reconstructs the complete history, and each new request serializes it again.  
**Outcome:** Long-lived workspaces retain increasing storage and incur rising renderer CPU/GC and chat-opening latency as obsolete request history accumulates.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no applied-request history. Rendering a chat therefore did not parse or retain a workspace-wide map of historical agent mode requests.  
**Changed behavior:** The PR stores all applied request tokens under one workspace key and \`\_readAppliedRequests\` rebuilds every session's nested object, but no removal path exists when an artifact or session is removed.  
**Confidence:** 0.97 — Repository-wide search proves the new key has only read/store sites and no cleanup, and the control call path proves full-history parsing. The time needed to become noticeable varies with session/resource churn.

**Causal diff evidence:** Added line 290 serializes \`{ ...all, \[chat\]: applied }\`, retaining every prior chat/session entry. The adjacent newly added reader enumerates all stored chats, while the diff adds no lifecycle cleanup.

Users who create/delete many agent sessions or rotate recorded status files accumulate entries forever; opening or updating any later chat synchronously processes all obsolete entries.

**Evidence:** The only references to \`chat.resources.appliedRequests\` are the new store at line 290 and full parser \`\_readAppliedRequests\`; there is no delete/prune call. \`\_applyRequests\` starts by reading the whole map on its renderer autorun, and its store spreads all historical sessions back into JSON. Artifact and agent-session removal paths exist elsewhere but do not touch this key.

**Suggested direction:** Tie applied tokens to artifact/session removal and delete empty nested maps, or store them in lifecycle-owned session metadata with bounded retention; also avoid materializing unrelated sessions when applying requests for the current session.

### 2. [medium] Batch requested pins before persisting UI state

**Finding ID:** `PERF-C5C64B601875`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatResources/chatResourcesControl.ts:279</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Synchronous JSON parsing/serialization and workspace/profile storage operations on the renderer thread  
**Scaling:** For R unique existing recorded resources carrying a new request, the loop invokes one pin persistence and one opens-in-chat persistence per resource. Each pin call reparses the entire profile pin map twice and rewrites it, while each opens-in-chat call reparses and rewrites its workspace map, so a batch performs O(R) storage mutations and O(R²) aggregate copying as the maps grow.  
**Outcome:** Large artifact batches can block the renderer while the chat input updates, causing delayed pill rendering and dropped frames.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, publishing a batch of artifacts did not automatically pin resources or persist per-resource chat display choices; those writes occurred only one at a time in response to explicit user actions.  
**Changed behavior:** The new autorun sends all requested resources through \_applyRequests, whose loop calls \_pin(resource) and then \_setOpensInChat(...) separately for every unapplied request.  
**Confidence:** 0.95 — The changed renderer call path, unbounded batch input, and per-item full-map persistence are directly visible. Exact user batch sizes and milliseconds vary, which affects severity but not the mechanism.

**Causal diff evidence:** Added line 279 places \`\_pin(resource)\` in the per-resource loop; added line 283 then calls \`\_setOpensInChat\` for the same item. This automatic batch path did not exist before the diff.

When an agent records a realistic batch of many files with mode set, the state publication synchronously triggers multiple whole-map reads, JSON transformations, writes, and storage events before the UI settles.

**Evidence:** \_applyRequests iterates every effective resource request. \_pin delegates to StandardChatInputPillSources.pin -&gt; ChatInputPillPins.setPinned, which reads/parses the full pinned map twice and stores a full JSON replacement. \_setOpensInChat similarly reads/parses and rewrites the complete workspace map. The artifact tool's items schema has no maximum, so one tool result can publish many unique file requests together; these operations are serial and synchronous in the renderer autorun.

**Suggested direction:** Collect all newly applicable requests first, update pin and opens-in-chat maps in memory, and persist each backing storage key once per autorun/batch (with one notification/event), while marking requests applied only after the batched pin operation succeeds.
