# Performance review: agentHost: fix Keep and Undo getting stuck after forking a chat

[PR #347817](https://github.com/microsoft/vscode/pull/347817) at `a738644b3b69c80e5a6d37af6aeee18778b1562a`

## Findings (2)

### 1. [medium] Decode each Working Set snapshot only once

**Finding ID:** `PERF-5D755926044F`  
**Location:** <code>src/vs/platform/agentHost/node/workingSetSources.ts:68</code> (<code>RIGHT</code>)  
**Performance category:** <code>gc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU and transient UTF-16 strings allocated by TextDecoder for full-file baseline/current snapshots  
**Scaling:** The added changed predicate decodes both full snapshots once in \`sources.filter(changed)\` and again in the second \`sources.filter(source =&gt; \!changed(source))\`; a pending file's selected baseline/current are then decoded a third time in computeWorkingSetFiles. Cost scales with total snapshot bytes across every file/source and repeats on each Working Set refresh.  
**Outcome:** Increased CPU time and short-lived string allocation/GC delay Working Set updates, especially for multi-megabyte edited files or changesets containing many files.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The removed computeSingleSourceWorkingSetDiff path decoded baseline and current once, compared those strings, and reused them for computeDiffCounts; the fallback similarly decoded only its final endpoints once.  
**Changed behavior:** The new source classifier converts every source baseline/current to text each time \`changed\` is invoked, invokes it in both result filters, and does not retain those strings for the final diff call.  
**Confidence:** 0.99 — The exact number of TextDecoder calls follows directly from the added predicate and its two call sites; the old diff shows one decode pair reused. Only magnitude varies with edited-file size and refresh frequency.

**Causal diff evidence:** Added line 68 introduces uncached full-content decoding used by two separate filters; this replaces deleted code that held \`beforeText\`/\`afterText\` and reused them for equality and diff computation.

Even the common single-chat Working Set now performs three pairs of full-file UTF-8 decodes instead of one whenever a file has pending changes. Because observed Working Sets recompute after each tool edit, large files generate repeated large string allocations and slower UI refreshes.

**Evidence:** Line 68 defines \`changed\` via two \`toText\` calls; lines 70-71 call that predicate independently for pending and unchanged partitioning, and sessionDiffAggregator.ts:440 decodes the chosen baseline/current again before posting them to the diff worker. AgentHostChangesetService refreshes this path after every applied tool edit while subscribed.

**Suggested direction:** Partition sources in one pass and cache decoded baseline/current text (or use a behavior-equivalent byte comparison for classification), then reuse cached endpoint text for computeDiffCounts so each snapshot is decoded at most once.

### 2. [medium] Reuse snapshots instead of rereading every cross-chat edit

**Finding ID:** `PERF-270C041C0B45`  
**Location:** <code>src/vs/platform/agentHost/node/workingSetSources.ts:97</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SQLite BLOB reads and the full-file byte arrays allocated for each before/after snapshot  
**Scaling:** For a file with E unaccepted records spread across multiple non-held chat databases, computeContents first reads all E snapshots and this line reads all E snapshots again; each snapshot contains whole-file before/after content, so bytes and queries scale as O(E \* file size) per pass. Reads for one file/database are serialized by SessionDatabase's per-file sequencer.  
**Outcome:** Working Set publication incurs excessive database I/O and latency after each tool edit, with additional allocation/GC pressure from loading the same full-file blobs twice.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous Working Set aggregator read each row once when one database held the complete sequence; when no database held all cross-chat rows, it loaded only the first and last snapshots. It did not perform two full row sweeps.  
**Changed behavior:** computeWorkingSetSources now calls computeContents, which loads every candidate row through computeWorkingSetFileContents, and findWorkingSetEnds then maps every row through readStep again whenever there are multiple pending sources or a pending plus unchanged source.  
**Confidence:** 0.98 — The duplicate call path and SQLite query are explicit, and the multi-source trigger is covered by the PR's new cross-chat tests. Exact wall-clock duration depends on file size and edit count, but the doubled query/blob cardinality is deterministic.

**Causal diff evidence:** Added line 97 introduces \`source.rows.map(... await readStep(...))\` after the newly added computeWorkingSetSources pass has already loaded those rows' contents.

With the Working Set visible, every applied tool edit queues a full recomputation. If two chats have independently edited the same large file over several tool calls, publishing the refreshed pending-changes UI rereads both full snapshots for every historical row and can visibly lag as history grows.

**Evidence:** AgentHostChangesetService.onToolCallEditsApplied refreshes the subscribed Working Set, computeWorkingSetFiles calls computeWorkingSetSources and then findWorkingSetEnds, and SessionDatabase.readFileEditContent executes a SQLite SELECT returning both content BLOBs. computeContents already traverses and reads each source row; added line 97 performs another readStep for every one of those rows on the same critical path.

**Suggested direction:** Load each record's start/end once and carry a per-source step array or shared \`(sourceIdx, record key)\` cache from computeContents into findWorkingSetEnds; preserve the current ordering logic while eliminating the second database sweep.

### Scenario 2: Keep all or selected Working Set changes after chats fork

- Critical path: The operation reads source histories and content, computes pending sources, writes accept records, and only then returns success; range Keep additionally waits for a hunk diff.
- Scaling input: Tracked chat/source count, unaccepted records for the target file, full-file snapshot size, and number of databases requiring accept rows.
- Effective concurrency: Source metadata reads and accept transactions are serial loops. Content computation across surviving candidates uses Promise.all, but same-file reads in a database serialize. Subsequent Working Set refresh requests are coalesced per owner when queued.
- Cache behavior: No warm cache is used; rows and content are reread for every operation. Already accepted/copied rows reduce effective candidates, and an empty pending set avoids writes.
- Mechanism confidence: High for boundary counts and serialization; lower concern for impact because each database requires an authoritative accept record.
- Magnitude uncertainty: Sessions normally have few forks, so serial transaction latency is uncertain and lower-severity than the reported repeated snapshot work.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostAcceptChangesOperationHandler.ts:invoke</code>: Read all edit metadata and candidate content from each tracked source; cardinality: One metadata query per tracked source, plus one content query per effective candidate row used by computeWorkingSetSources.

  - database at <code>src/vs/platform/agentHost/node/agentHostAcceptChangesOperationHandler.ts:invoke / fileEditAccept.ts:storeFileEditAcceptRecord</code>: Store an accept row transaction and validate the previous row in each pending/unchanged source; cardinality: One serial transaction per effective source whose records are accepted; each transaction scans metadata and reads the previous content.

  - ipc at <code>src/vs/platform/agentHost/node/workingSetFileContents.ts:computeWorkingSetRangeChanges</code>: Compute range hunks in the diff worker; cardinality: Zero for whole-file Keep; one call for a range when exactly one pending source exists.
