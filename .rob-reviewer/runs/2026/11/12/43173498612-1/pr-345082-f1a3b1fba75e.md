**Relevant issue families:** boundary-fanout, eager-work, serialization-allocation, concurrency-burst

### Scenario 1: Successful Windows compile, CI, flaky-build, and product-test jobs

- Critical path: Azure evaluates the added template step's \`failed()\` condition, but the collector subprocess and compile diagnostic artifact output do not run; successful job completion has no new diagnostic work on its critical path.
- Scaling input: One condition evaluation per Windows job; the number of product-test jobs can be several, but each successful job skips the body independently.
- Effective concurrency: No collector process is launched. Existing Windows jobs retain their prior cross-job parallelism.
- Cache behavior: No cache is consulted or populated by the added diagnostics; cold and warm dependency-cache behavior is unchanged.
- Mechanism confidence: High: the added step and compile artifact both have explicit failure conditions, and tests assert failure-only placement.
- Magnitude uncertainty: Only negligible pipeline-template/condition evaluation remains; no changed expensive boundary is reachable.
- Expensive boundaries: none found
- Verdict: No reportable regression: successful build and test critical paths do not execute the new subprocess, probes, event queries, serialization, or artifact upload.

### Scenario 2: Failed Windows compile, combined CI, or flaky-build job

- Critical path: After all prior user steps fail, one diagnostic step runs before Network Isolation teardown and delays failed-job completion until it finishes or the 45-second process-tree deadline expires. Any configured failure artifact publication follows it.
- Scaling input: Exactly one collector invocation per failed job attempt. Each invocation caps section records at 64, output files at 64 KiB, and total runtime at 45 seconds; aggregate work scales with the number of concurrently failed jobs, which run on separate agents.
- Effective concurrency: The PowerShell collector performs its sections sequentially. There is one collector per job; parallel CI/flaky jobs can each run one on their own agents, with no within-agent burst.
- Cache behavior: There is no cache. Every failed attempt captures a fresh snapshot and first overwrites sections with \`notCollected\`; no cold/warm distinction or retry amplification occurs inside one attempt.
- Mechanism confidence: High: template reachability, sequential call flow, source-side event caps, output caps, and timeout semantics were traced directly.
- Magnitude uncertainty: Exact Windows cmdlet and event-log latency varies by hosted image state, but the one-per-failed-attempt cardinality and 45-second hard deadline are explicit.
- Expensive boundaries:
  - subprocess at <code>build/azure-pipelines/win32/steps/product-build-win32-network-diagnostics.yml:4</code>: Node launches one PowerShell collector under the existing process-tree timeout helper.; cardinality: One Node-to-PowerShell launch per failed job attempt.
    - Introduced by diff: true; previous behavior: Failed jobs proceeded directly to existing output publication and Network Isolation teardown without this collector.; critical-path effect: Runs on the failed-job completion path and is bounded to 45 seconds, with a two-minute task backstop.

  - other expensive boundary at <code>build/azure-pipelines/win32/collect-network-diagnostics.ps1:156-286</code>: PowerShell queries process, DNS server, UDP endpoint, TCP connection, and Windows event-log state.; cardinality: Two process enumerations, one DNS-server query, one UDP-endpoint query, one TCP-connection query, and up to four log metadata plus four bounded event queries per failed job; event results stop at 65 and the hosted disabled DNS Operational channel skips its event query.

- Verdict: No reportable regression: the added latency and bounded I/O are intentional diagnostic work restricted to already-failed jobs, with one invocation per attempt, no fan-out by event/item, and hard runtime/output bounds.

### Scenario 3: Failed standalone Windows product-test job

- Critical path: The final failure-only diagnostic step runs after setup/download/test steps and before teardown; its completion is required before the job's existing always-published logs artifact can finish.
- Scaling input: One invocation per failed product-test job attempt. A product build may have several test jobs, but each invocation is independently bounded and concurrent jobs execute on separate agents.
- Effective concurrency: Sections are sequential within a job. Multiple failed product-test jobs may collect concurrently only through the pipeline's existing job-level parallelism.
- Cache behavior: No cache or coalescing exists or is needed across isolated job agents; each failed attempt records current state.
- Mechanism confidence: High: the template is the last job step and the existing logs output condition and path were inspected.
- Magnitude uncertainty: The exact number of simultaneously failing test jobs varies by build configuration, but per-job work and output are hard-bounded.
- Expensive boundaries:
  - subprocess at <code>build/azure-pipelines/win32/product-build-win32-test.yml:76</code>: Runs the same bounded Node/PowerShell collector as the final product-test step.; cardinality: One launch for each failed standalone product-test attempt.
    - Introduced by diff: true; previous behavior: The test job moved directly from its test steps to existing outputs/teardown.; critical-path effect: Adds up to 45 seconds after failure before existing log artifact publication and teardown.
  - network at <code>build/azure-pipelines/win32/product-build-win32-test.yml:42-47</code>: Existing \`.build/logs\` pipeline artifact upload now includes the bounded network diagnostic files.; cardinality: Upload call count remains one per job; payload increases by no more than roughly 704 KiB from eleven 64 KiB files.
    - Introduced by diff: false; previous behavior: The same logs artifact was uploaded without the new network snapshot.; critical-path effect: Only bounded additional upload bytes; artifact publication already occurred unconditionally.
- Verdict: No reportable regression: deliberate post-failure diagnostics add bounded per-job latency and bytes without changing successful test execution or introducing per-test-case fan-out.

### Scenario 4: Focused Windows network-diagnostics test execution

- Critical path: The added Node test file runs isolated PowerShell collector fixtures synchronously; the interruption fixture invokes the timeout helper and intentionally waits for its deadline before assertions continue.
- Scaling input: Twelve collector fixtures are run serially on Windows, including one five-second timeout case; the suite is skipped on non-Windows platforms.
- Effective concurrency: \`spawnSync\` serializes all fixture processes. The local loopback server tests do not create an unbounded concurrent workload.
- Cache behavior: Each fixture uses a fresh temporary directory and process, so there is no warm cache; this isolation is deliberate test behavior.
- Mechanism confidence: High: synchronous spawn calls and the explicit five-second deadline are direct in the added test.
- Magnitude uncertainty: PowerShell startup time varies by Windows runner; the timeout fixture contributes a known five-second floor.
- Expensive boundaries:
  - subprocess at <code>build/lib/test/windowsNetworkDiagnostics.test.ts:117-128</code>: Spawns isolated PowerShell collectors, with one case nesting the Node timeout helper.; cardinality: One synchronous child per test fixture, twelve in the current suite; one timeout fixture is deliberately held for five seconds.
    - Introduced by diff: true; previous behavior: The test file and its child-process work did not exist.; critical-path effect: Adds seconds to the focused Windows-only test command, but does not execute in product jobs or non-Windows test runs.
  - filesystem at <code>build/lib/test/windowsNetworkDiagnostics.test.ts:106-132</code>: Creates fixture trees/files, reads bounded JSON outputs, and removes each temporary tree.; cardinality: One small isolated tree per fixture, plus 70 files in the explicit limit fixture.
    - Introduced by diff: true; previous behavior: No diagnostic fixtures were created.; critical-path effect: Bounded local test-only I/O serialized with each fixture.
- Verdict: No finding: the cost is confined to the new focused Windows-only validation, is fixed and bounded, and the longer deadline supports reliable observation of partially written interruption state rather than affecting product or general successful pipeline execution.

**Summary:** Completed the performance pass over all seven changed files and transitive pipeline/timeout paths. The change adds bounded, sequential diagnostics only after Windows job failures; successful paths skip them. OS queries, one proxy probe, JSON/file work, and artifact bytes were counted and compared with prior behavior. No high-confidence actionable performance regression was found, and the PR does not fix a prior shipped performance regression.
