# Performance review: Resize anchored quick input when its anchor resizes

[PR #347680](https://github.com/microsoft/vscode/pull/347680) at `759206165f628fadcae4641f732d0592c853bbcd`

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work, cleanup-lifecycle

### Scenario 1: Integrated browser URL quick pick remains open while the editor group or panel is resized

- Critical path: The browser delivers a ResizeObserver notification for the URL-bar anchor, then the callback synchronously clears the overlay correction and runs updateLayout before the resized picker can paint. updateLayout performs DOM geometry reads/writes and list/tree layout on the UI thread.
- Scaling input: Cost scales with browser-delivered anchor resize notifications during a drag; ResizeObserver coalesces size mutations into delivery cycles, so effective cardinality is at most one callback per observer delivery rather than per suggestion or DOM mutation.
- Effective concurrency: A single observer is installed for the one visible quick input. Browser delivery and updateLayout are serialized on the UI thread; there is no task burst or parallel boundary work.
- Cache behavior: overlayLayoutCorrection is reused between ordinary layouts but intentionally invalidated on a real anchor resize. There is no remote or persistent cache; warm/cold behavior is otherwise unchanged.
- Mechanism confidence: High: the added observer directly reaches updateLayout, whose geometry reads, style writes, and list/tree layouts are visible in the traced code.
- Magnitude uncertainty: Exact layout duration depends on visible quick-input content and resize frame rate, but the callback cardinality and UI-thread work are bounded and directly tied to the requested live alignment.
- Expensive boundaries: none found
- Verdict: No reportable regression. Before the diff, editor-group resizing could leave this overlay stale because no layout ran; after the diff, one coalesced UI layout runs per delivered anchor resize. This is the necessary bounded work for live alignment, with no evidence of an avoidable fan-out or frame-amplifying loop.

### Scenario 2: Opening, replacing, and hiding generic element-anchored quick inputs

- Critical path: Showing an element-anchored input installs one ResizeObserver after the existing initial updateLayout; native observation may cause an initial asynchronous delivery and subsequent deliveries only when the anchor size changes. Hiding clears the observer before teardown, and showing another input clears the prior observer first.
- Scaling input: One observer and at most one active observed HTMLElement per QuickInputController; work scales with anchor resize delivery count while that input is visible, not with item count or application lifetime.
- Effective concurrency: Observer callbacks are serialized on the browser UI thread. MutableDisposable and DisposableStore ensure only one live observer for the controller.
- Cache behavior: No cache lookup or miss path is introduced. The only retained state is one observer/store for the visible input, released on hide, replacement, or controller disposal.
- Mechanism confidence: High for lifecycle and callback reachability; low uncertainty only in the negligible magnitude of the initial notification.
- Magnitude uncertainty: An initial observer delivery can add one extra layout after show, but it is a bounded single delivery and the inspected layout methods do not establish a meaningful user-visible regression on their own.
- Expensive boundaries: none found
- Verdict: No reportable regression. The observer lifecycle is bounded and explicitly cleaned up, and resize-driven work does not continue while hidden or accumulate across picker replacements.

**Summary:** Reviewed the complete two-file diff and traced the added ResizeObserver through quick-input layout, browser URL-bar usage, generic anchored picker consumers, observer semantics, and cleanup. The change adds bounded, browser-coalesced synchronous layout needed for live anchor alignment; no high-confidence actionable performance regression or qualifying regression fix was found.
