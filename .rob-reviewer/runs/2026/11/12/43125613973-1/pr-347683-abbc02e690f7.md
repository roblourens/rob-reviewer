### Scenario 1: Open an artifact pill and render the artifact-details panel, including a recorded pull request with main/checks/comments details.

- Critical path: The context view synchronously creates the details model and panel and can render loading state immediately. Each unique details lease then completes before that section has authoritative content; those asynchronous acquisitions are not newly placed on initial panel construction by this diff.
- Scaling input: Number of unique details IDs across contributions after Map deduplication, typically 1-3 for the PR integration; item count affects existing list rendering but not the moved header actions.
- Effective concurrency: ArtifactDetailsModel starts one asynchronous acquire per deduplicated integration/details key without a shared limiter. ArtifactBinding coalesces concurrent references to the same detailsId and reference-counts disposal. This behavior and concurrency are unchanged by the header move.
- Cache behavior: ArtifactBinding caches a provider details model by detailsId while references exist and coalesces concurrent same-key leases; the final release removes and disposes it. Provider snapshots can supply warm state, while a cold/opened subscription may refresh remotely. The diff changes neither keys, positive/negative states, coalescing, nor release lifecycle.
- Mechanism confidence: High: constructor, lease deduplication, protocol path, provider subscription, and reference-counted cache were traced directly.
- Magnitude uncertainty: Provider implementations vary in remote refresh cost, but the diff does not add, duplicate, or move these calls onto a new critical path.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/sessions/browser/chat/artifactDetailsModel.ts:ArtifactDetailsLease.acquire; src/vs/platform/artifactIntegrations/common/artifactIntegrationProtocol.ts:acquireDetails</code>: Acquire and subscribe to provider details; remote extension/agent-host implementations cross their protocol boundary and may trigger provider network refreshes.; cardinality: One acquisition per effective unique (integrationId, detailsId), deduplicated by the wanted Map. The concrete pull-request view exposes up to main, checks, and comments, so a typical fully populated PR is three acquisitions rather than one per section/item.
    - Introduced by diff: false; previous behavior: Opening the same panel created the same leases and made the same protocol/provider calls; only the already-produced general-action buttons were rendered in a footer.; critical-path effect: The panel opens with loading state, but each section's useful details depend on its acquisition response.
  - network at <code>src/vs/platform/agentHost/node/artifactIntegrations/githubPullRequestArtifactIntegration.ts:acquireDetails / PullRequestArtifactResource.acquireDetails</code>: Maintain or raise the artifact provider's interactive details subscription, which can refresh GitHub pull-request core, checks, and review-thread data.; cardinality: The three PR details models share the underlying resource; each lease updates the same subscription interests rather than issuing a new request per displayed row.
    - Introduced by diff: false; previous behavior: Identical details leases and subscription priority changes occurred before the diff.; critical-path effect: Fresh remote data is needed for authoritative details, while cached snapshot state can render first.
- Verdict: No reportable regression. The expensive acquisition path and its cardinality are unchanged; the diff only relocates a small keyed action set.

### Scenario 2: Live artifact updates and user invocation of a general action such as Open Pull Request Changes, Copy Link, Remove Artifact, Sign In, or provider Refresh.

- Critical path: A snapshot/details observable update synchronously projects view data and updates the existing keyed button widgets, then requests layout. A user action performs exactly one existing action callback; completion depends on that action's existing IPC/network/editor boundary.
- Scaling input: Number of general actions, ordinarily a few; each live update performs O(actions) keyed updates as before, with one additional constant close-button update.
- Effective concurrency: Button updates are synchronous and keyed by action id. Layout is coalesced to at most one scheduled animation-frame request. User clicks are not newly parallelized or fanned out by this diff.
- Cache behavior: ArtifactButtons retains and reuses widgets by stable action id, disposing only removed ids. The moved actions use this same cache/lifecycle pattern as the former footer. No result cache or negative-cache behavior changes.
- Mechanism confidence: High: the before/after renderer path, keyed DisposableMap behavior, and click callbacks were inspected directly.
- Magnitude uncertainty: Update frequency depends on provider polling/activity, but action cardinality is bounded in realistic integrations and the only added work is one constant keyed close-button reset.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/sessions/browser/chat/artifactIntegrationPresentation.ts:invoke / authenticationButton</code>: Invoke a provider action or request authentication when the selected general action is provider-owned.; cardinality: One invocation per user click, independent of the number of header buttons.
    - Introduced by diff: false; previous behavior: The same footer button called the same callback once per click.; critical-path effect: The selected action waits for its existing provider/authentication operation; merely rendering it in the header performs no invocation.
  - other at <code>src/vs/workbench/contrib/sessions/browser/chat/artifactDetailsModel.ts:generalActions shell action mapping; src/vs/workbench/contrib/sessions/browser/chat/sessionArtifacts.ts recorded artifact toolbar actions</code>: Open pull-request changes/editor content, copy a link, remove the recorded artifact, or open a resource through the existing shell toolbar action callback.; cardinality: One shell callback per click; realistic header cardinality is a small set (for a recorded PR, open changes/copy/remove plus any provider action).
    - Introduced by diff: false; previous behavior: The footer exposed and ran the identical action object; the diff changes icon/placement only.; critical-path effect: Action-specific work is on the clicked command's critical path, not panel refresh or hover.
- Verdict: No reportable regression. General actions already underwent O(actions) DOM updates; combining Close adds only constant work and introduces no boundary fan-out or retention.

### Scenario 3: Resize or narrow the Agents/chat pane while artifact details are open, causing the title and header actions to share one row or wrap to two rows.

- Critical path: CSS flex layout wraps the whole action group below the title when necessary. ResizeObserver schedules the existing panel layout at the next animation frame; panel.layout performs existing geometry reads and scrollbar scans.
- Scaling input: Pane resize frequency and a small number of header actions; flex layout grows with header children, not artifact list-item count.
- Effective concurrency: Resize-driven layout requests are coalesced by pendingLayout to one animation-frame callback. Browser style/layout work is synchronous in that callback, with no worker, subprocess, or queue fan-out.
- Cache behavior: No data cache is involved. The pending-layout disposable is the coalescing state and is cleared on hide/disposal; this lifecycle is unchanged.
- Mechanism confidence: High: the CSS, ResizeObserver sources, animation-frame guard, and synchronous layout reads were traced.
- Magnitude uncertainty: Exact browser layout cost varies by platform and width, but the changed flex rules affect only one small header and do not establish frame-scale repeated work.
- Expensive boundaries: none found
- Verdict: No reportable regression. Wrapping can add one header line, but resize work remains frame-coalesced and bounded to a small toolbar.
