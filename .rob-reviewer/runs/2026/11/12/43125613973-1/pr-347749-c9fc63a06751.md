<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work, eager-work, serialization-allocation, cache-lifecycle

### Scenario 1: Desktop chat model picker cold startup with no live catalog or a restored legacy Auto snapshot

- Critical path: Chat input construction renders ModelPickerWidget.\_renderLabel synchronously before the picker label is usable. The diff adds only isPendingLegacyAutoModel: constant metadata checks plus getVendors/find and getLanguageModelIds/includes; no asynchronous or external operation blocks startup.
- Scaling input: The added work is O(V + M) in registered vendors and cached model IDs and allocates two short arrays through existing service accessors, once per label render while the selected model is legacy Auto. Realistic catalogs are small, and non-Auto/Fusion/user-provided selections short-circuit before the ID scan.
- Effective concurrency: Single synchronous UI render; no queue, limiter, IPC, subprocess, filesystem, database, or network concurrency is introduced.
- Cache behavior: With a cold empty language-model cache, getLanguageModelIds returns an empty array and the restored Auto is treated as pending. With a warm/live cache, membership is found in the current in-memory Map keys. No new positive/negative cache or retry behavior is introduced.
- Mechanism confidence: High: the full helper, service implementations, widget listeners, and render call sites were traced. The only new cost is bounded in-memory array creation and linear membership checks.
- Magnitude uncertainty: Exact catalog sizes and label rerender counts vary by extensions and UI state, but no high-frequency event or expensive boundary reaches this helper; the surrounding render already performs DOM replacement and geometry measurement.
- Expensive boundaries: none found
- Verdict: No finding. The diff changes startup presentation without adding an actionable latency, CPU, GC, or boundary regression.

### Scenario 2: Phone chat input startup and reactive mode/model label updates

- Critical path: MobileChatInputCombinedPickerActionItem.\_updateTrigger synchronously clears and rebuilds the compact trigger. The helper is evaluated before text is appended; it performs only in-memory service reads. ILanguageModelsService was already instantiated by ChatInputPart, so the new constructor injection does not activate a new service on this path.
- Scaling input: For pending legacy Auto only, cost grows linearly with vendor/model catalog size. Autorun frequency is bounded by mode/model changes rather than frames, keystrokes, or scrolling.
- Effective concurrency: One synchronous autorun per active phone chip; updates serialize on observable mode/model changes and do not spawn concurrent work.
- Cache behavior: The check reads the shared language-model service's existing vendor/model maps. Cold catalog state yields pending Fusion presentation; publication warms the existing model cache and the next model observable update reads it. There is no polling, retry, or retained per-render cache.
- Mechanism confidence: High: constructor ownership, ChatInputPart dependencies, autorun triggers, and service registration were inspected.
- Magnitude uncertainty: Multiple chat inputs could each own a chip, but only rendered active surfaces react, and the added arrays remain catalog-sized and short-lived.
- Expensive boundaries: none found
- Verdict: No finding. The added dependency and scans do not create eager heavyweight initialization or realistic UI jank.

### Scenario 3: Live model discovery switches restored Auto metadata to Copilot Fusion on desktop and phone

- Critical path: Provider publication updates the existing in-memory model cache and emits onDidChangeLanguageModels. Desktop synchronously rerenders its label; phone updates when the selected-model observable changes. The diff adds catalog-membership checks on those renders but no provider resolution or external request.
- Scaling input: One added O(V + M) check per affected picker render after a publication/selection update, with effective cardinality equal to rendered picker instances, not model rows.
- Effective concurrency: Existing service publication fans out synchronously to listeners; the diff neither increases publication cardinality nor creates parallel boundary work.
- Cache behavior: Cold restored metadata is distinguished from the warm authoritative model cache. Once the identifier is present, the helper's membership result changes immediately; no stale negative cache or repeated miss-triggered discovery is added.
- Mechanism confidence: High: the language-model event listener, phone observable path, helper, and service cache access were traced end to end.
- Magnitude uncertainty: The number of simultaneous rendered chat inputs is product-state dependent, but the diff performs no per-row model resolution and no remote work for each listener.
- Expensive boundaries: none found
- Verdict: No finding. Existing event fan-out remains unchanged and the added local work is too small and infrequent to establish a concrete regression.

**Summary:** Reviewed all five changed files and all diff pages. Traced desktop and phone startup/render paths, service lifecycle, catalog accessors, publication listeners, cache state, and external-boundary reachability. No reportable performance issue or regression-fix learning signal was found.
