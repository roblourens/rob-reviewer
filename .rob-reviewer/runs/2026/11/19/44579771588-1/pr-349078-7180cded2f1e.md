### Scenario 2: Split, open a document beside a chat/editor, toggle compact mode, resize, and remove groups in an opt-in compact auxiliary window.

- Critical path: Group selection/addition synchronously resolves getAddGroupLocation and creates one group in the selected grid. The requested editor is then opened through the existing editor pane. Resize uses the existing auxiliary onWillLayout handler. Explicit compact-mode transitions update existing options and chrome.
- Scaling input: User-requested split/group operations and live groups in the destination window. This is not a loop creating a group for every editor or history entry.
- Effective concurrency: Group routing and grid mutation remain synchronous, with the same one-group creation path. Existing editor opens are asynchronous. Skipping updateCompact(false) for opt-in splits avoids the automatic chrome/options transition rather than adding nested relayout work.
- Cache behavior: Text-model sharing, per-resource pending resolution, and asynchronous warm reload remain unchanged. optionsDisposable retains at most one enforced-options registration per compact part; repeated compact option updates do not accumulate registrations.
- Mechanism confidence: High: inspected getAddGroupLocation, resolveAddGroupLocation, EditorPart.addGroup, option enforcement, compact event handlers, and ownership/disposal. The changed conditional only retains the existing compact policy and chooses the local grid.
- Magnitude uncertainty: Layout cost depends on live groups and editor contents; no timings were measured. Keeping compact chrome while splitting is intentional functionality, not independently demonstrated extra work.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/browser/parts/editor/editorPart.ts: addGroup -&gt; src/vs/workbench/browser/parts/editor/editorGroupView.ts: doShowEditor -&gt; src/vs/workbench/contrib/files/browser/editors/fileEditorInput.ts: doResolveAsText</code>: Open the requested editor and resolve its content through the existing editor-pane/model services.; cardinality: One added group per add/split request and the corresponding requested editor open; existing SIDE\_GROUP neighbor reuse is unchanged. - Verdict: No reportable regression. No new boundary fan-out, repeated model loading, or unbounded retained collection is introduced. Existing per-group listeners and window-level cleanup were already used by split auxiliary windows; the diff does not remove disposal ownership.
