## Findings (2)

### 1. [medium] Avoid rebuilding subpixel-strip borders on every changed frame

**Finding ID:** `PERF-14E9E7F4B17C`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatPetJumpGameLiteShapes.ts:142</code> (<code>RIGHT</code>)  
**Performance category:** <code>gc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Short-lived sprite objects/arrays, border tessellation CPU work, and instance-buffer upload bytes  
**Scaling:** A six-pixel-high platform emits 48 strips per half-cap plus two straight edges: 98 border instances, before its fill. Ten visible platforms therefore add about 980 border instances and about 3,920 object/array allocations per changed frame. Each instance occupies 52 uploaded bytes. Calls remain batched into one instance upload and one draw, not one GPU call per strip; unchanged-hash frames skip this work.  
**Outcome:** Substantially increased short-lived allocation, CPU reconstruction, and GPU-upload volume during high-contrast gameplay, producing avoidable GC/frame-time pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each visible platform or wall was a reused DOM element with a CSS border. Animation updated its position; JavaScript did not retessellate the rounded border or allocate per-strip sprite data.  
**Changed behavior:** When contrastBorder is defined, every changed frame reconstructs the rounded perimeters in JavaScript and copies all resulting strip instances into the GPU upload.  
**Confidence:** 0.96 — The default high-contrast color definitions enable this branch, and the strip count and per-sprite allocations follow directly from the code. The new perimeter test also confirms 356 border sprites for just one platform and one 16-pixel-wide wall. Runtime duration and GC frequency have not been measured.

**Causal diff evidence:** The new 0.125-pixel strip loop at lines 141-154 expands each rounded border into many sprites. The new renderer clears and reconstructs the whole layer at lines 157-168 and allocates an object plus position, size, and color arrays for each emitted sprite.

With either built-in high-contrast theme, jumping or animating a visible moving platform causes this work at frame rate even for a normal handful of visible platforms. Hundreds to roughly a thousand border instances replace a handful of CSS-bordered elements.

**Evidence:** contrastBorder has non-null hcDark/hcLight defaults in platform/theme/common/colors/baseColors.ts:41-43 and is passed into renderer colors by ChatPetJumpGame.updateRenderer. renderChatPetJumpGameLiteShapes invokes addCapsuleBorder for every visible platform and wall. A platform's fixed height is six pixels, so each cap's loop executes 6/0.125=48 times. The callback in chatPetJumpGameWebGpuRenderer.ts:159-165 constructs four objects/arrays per instance. lite-webgpu.js creates 13-float instances and uploadSpriteInstances writes the entire rebuilt dirty range. The added high-contrast perimeter test explicitly expects 356 border sprites for its two objects.

**Suggested direction:** Render rounded border caps with a constant-size atlas representation prepared outside the frame loop, or retain the DOM renderer for border themes until a bounded-cost GPU border representation is available.

### 2. [medium] Keep the drawing-buffer size stable while platforms move

**Finding ID:** `PERF-37D0D45C10A6`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatPetJumpGameWebGpuRenderer.ts:155</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** WebGPU presentation textures/drawing buffers and compositor surface updates  
**Scaling:** One backing-buffer resize per changed frame whose rounded visible width changes, potentially at animation-frame frequency while an outermost moving platform travels. The affected buffer covers the cropped width times the full playfield height, scaled by devicePixelRatio squared; this is not a per-platform GPU call.  
**Outcome:** Repeated presentation-buffer invalidation/reallocation and surface-size churn during normal animation, adding GPU/compositor work and frame-time pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The DOM renderer reused visible platform elements and updated their positions. Moving a platform did not resize or replace a WebGPU drawing buffer.  
**Changed behavior:** Horizontal platform motion now changes the cropped canvas dimensions whenever a moving extreme crosses an integer pixel, even though the playfield itself has not resized.  
**Confidence:** 0.95 — The frame loop, moving-platform updates, visible-extents calculation, and backing-canvas width/height assignments are all traced. Reallocation frequency depends on whether a moving platform defines an unclipped horizontal extremum; exact GPU cost is not measured.

**Causal diff evidence:** New line 155 derives the canvas width from the current visible platform/wall extrema on each changed frame. updateCanvasBounds then invokes setEngineSize at line 188; the newly vendored setSurfaceSize writes canvas.width and canvas.height whenever that width changes.

During ordinary play, a visible moving platform can define the leftmost or rightmost extent. Its motion then repeatedly reallocates the full-height drawing buffer rather than merely updating sprite positions; high-DPI and tall playfields amplify the cost.

**Evidence:** ChatPetJumpGame.scheduleFrame renders on each animation frame. ChatPetJumpGameModel.step updates moving platform.left sinusoidally. getChatPetJumpGameLiteRenderInfo computes left/right directly from those positions (chatPetJumpGameLiteShapes.ts:111-112). render uses floor/ceil of those extents at lines 154-155. updateCanvasBounds calls setEngineSize, whose setSurfaceSize implementation (lite-webgpu.js:151-160) assigns both canvas.width and canvas.height on any size difference. The following renderFrame obtains the presentation texture at the new size. No size buckets or hysteresis bound these changes.

**Suggested direction:** Keep a stable playfield-sized backing buffer and update sprite positions only, or use a padded/bucketed crop whose allocation does not track each pixel of platform movement.

### Scenario 5: Resize the chat host, change themes, or pause through accessibility help

- Critical path: Host layout invokes game layout synchronously. Theme changes synchronously recolor and rerender the last state. Pausing cancels the game animation callback and renders once; resuming schedules it again.
- Scaling input: One layout/render per host notification or theme event; visible geometry count and canvas pixel area control the rendering cost. Paused gameplay does not continue its frame loop.
- Effective concurrency: Synchronous UI event handling; no additional timer/render loop is created by the Babylon engine because the integration invokes renderFrame manually.
- Cache behavior: Layout and theme changes invalidate the render hash. Layout first expands the canvas to the full playfield and the following render can shrink it to the crop even when the previous crop would fit. Theme colors are refreshed only on theme changes.
- Mechanism confidence: High: host callers, pause/resume ownership, hash invalidation, and manual frame submission are traced.
- Magnitude uncertainty: Host notification rates and the duration of synchronous graphics calls are unmeasured.
- Expensive boundaries:

### Scenario 6: Exit, fall, retry, dispose during initialization, or fall back after GPU failure

- Critical path: Exit cancels game scheduling and either removes effects immediately or transfers renderer ownership to a bounded 160 ms fade. Failure installs the DOM renderer and disposes the active GPU renderer. A factory resolving after game disposal is disposed instead of installed.
- Scaling input: One renderer/device per active game, plus a bounded fading renderer. Retry retains the existing game model as before. Pending initializations can finish after exit but do not remain installed.
- Effective concurrency: Fade disposal is event-driven and also owned by the widget disposable. Initialization is asynchronous and checked for staleness after resolution; the code does not globally limit initialization across separate game instances, but no realistic unbounded burst was established.
- Cache behavior: Successful module imports survive repeated starts; GPU resources, theme listeners, and device callbacks are disposed per renderer. There is no automatic same-game retry loop after failure.
- Mechanism confidence: High for established normal, stale-resolution, fade, and fallback ownership. No additional high-confidence persistent resource leak was established.
- Magnitude uncertainty: Driver disposal cost and prevalence of overlapping pending starts are unknown; neither establishes another actionable regression here.
