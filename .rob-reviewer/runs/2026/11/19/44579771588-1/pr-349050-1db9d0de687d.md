### 1. [medium] Keep unchanged turns on the no-I/O guidance path

**Finding ID:** `PERF-A819B6358DA9`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:9539</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Stdio runtime RPC round trips, agent-file reads and buffers, and YAML parsing work.  
**Scaling:** One additional agent.getCurrent RPC per synchronization for a resumed wrapper until an explicit selection establishes \_lastAppliedAgent; one file read/parse per synchronization when its selected agent resolves to a file. Synchronization occurs at initialization, each turn, agent changes, and root-config changes; root-config work scales with live sessions, not all discovered agents.  
**Outcome:** Additional serial latency before model requests and repeated filesystem/CPU work, including on warm turns with unchanged or absent guidance.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With unchanged user instructions, synchronization compared the configured string to \_appliedAssistedApprovalInstructions and returned without agent-discovery RPCs or agent-file reads.  
**Changed behavior:** Every synchronization now discovers agent guidance before checking whether the applied instructions changed. Resumed sessions repeatedly query the current agent, and sessions with a resolvable custom-agent file repeatedly read and parse it.  
**Confidence:** 0.98 — The send and /fleet paths await \_prepareSdkTurn, which always awaits this synchronization. The new discovery call precedes the existing equality check. Resume initializes \_lastAppliedAgent to undefined, and the helper never stores its getCurrent result. These are direct static call-path facts; actual RPC and file-read durations are unmeasured.

**Causal diff evidence:** Added line 9539 awaits \_readAgentAssistedApprovalInstructions before the unchanged-value return. Added lines 9568-9573 query agent.getCurrent when \_lastAppliedAgent is undefined and call parseAgentFile without retaining either discovery result.

Continuing a resumed conversation now waits for an extra runtime round trip before every request, even with the default agent. Custom-agent conversations additionally reload their agent file on each turn, delaying dispatch unnecessarily; unrelated root-config updates repeat discovery across live sessions.

**Evidence:** \_prepareSdkTurn at 7627-7635 runs this synchronization for normal session.send (7389-7403) and /fleet (7665). \_initializeSdkWrapper sets \_lastAppliedAgent to undefined for resumes at 5168. The new helper leaves that field unchanged, so successful getCurrent calls repeat even when no custom agent exists. parseAgentFile at pluginParsers.ts:1294-1296 reads the entire file and parses YAML on every invocation. CopilotAgent constructs the runtime connection with RuntimeConnection.forStdio at copilotAgent.ts:5273. Root-config changes also invoke synchronization for every subscribed live session at 9414-9416.

**Suggested direction:** Resolve and retain the restored selection, including no selection, per SDK wrapper. Cache selected-agent guidance including absence, invalidate it on agent/file/customization changes, and reset wrapper-specific state on relaunch so unchanged turns retain the existing no-I/O fast path.

### 2. [medium] Skip greeting reads and rendering for populated chats

**Finding ID:** `PERF-52DEAF82C93B`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatAgentStartExperience.ts:92</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Unnecessary agent-file reads and remote filesystem calls, markdown parsing/sanitization, code-block tokenization, and allocated greeting DOM/listeners.  
**Scaling:** One fresh file read per custom-agent widget update when its file has no open text model, plus one full greeting render when the header defines a message. Work scales with restored widgets and conversation/mode switches, and rendering with greeting size; there is no per-URI coalescing across widgets.  
**Outcome:** Avoidable remote/local I/O and renderer CPU/allocation during existing-conversation restoration and switching, with hidden greeting resources retained per widget.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Opening or switching an existing conversation performed no agent-file reads or rendering for this empty-chat greeting.  
**Changed behavior:** The new contribution reads every selected custom agent's file on each update and constructs its greeting whenever present, even when the widget already contains a transcript and cannot display it.  
**Confidence:** 0.97 — Widget attachment, mode changes, and view-model changes invoke \_update without checking transcript contents or visibility. The consumer explicitly mounts the result only when there are zero items. File reads and markdown/code-tokenization work are established by their implementations; greeting sizes and observed UI delays are unmeasured.

**Causal diff evidence:** Added lines 82-85 invoke \_update on mode/view-model changes and attachment. Added line 92 unconditionally reads a non-builtin mode's URI, and added line 101 renders its message without an empty-transcript check.

Restoring or switching among existing custom-agent conversations performs greeting work that can never be visible. Remote agent files add stat/read traffic even when they have no greeting, while greetings with formatted examples additionally trigger markdown rendering and syntax tokenization on the UI thread.

**Evidence:** \_read uses IPromptsService.parseNew at line 108. promptsServiceImpl.ts:839-849 reuses an open text model, but otherwise calls fileService.readFile and parses afresh; it has no closed-file cache. \_render at 125-126 invokes the markdown renderer, which synchronously parses/sanitizes markdown (base/browser/markdownRenderer.ts:224-262) and invokes the default code-block renderer. EditorMarkdownCodeBlockRenderer.renderCodeBlock tokenizes fenced examples at line 50. Meanwhile chatWidget.ts:1739-1746 mounts this content only when numItems is zero. For vscode-remote agent files, RemoteFileSystemProviderClient uses DiskFileSystemProviderClient, whose stat/readFile methods cross the remote channel.

**Suggested direction:** Check that the transcript is empty before loading the greeting and again after the asynchronous read before rendering it. Refresh when the widget becomes empty, and release the greeting when leaving that state; defer hidden-widget rendering until it can be shown.
