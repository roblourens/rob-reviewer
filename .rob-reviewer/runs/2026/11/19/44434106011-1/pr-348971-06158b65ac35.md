## Findings (1)

### 1. [medium] Share legacy normalization with plaintext extraction

**Finding ID:** `PERF-6F5B40A6BA0A`  
**Location:** <code>src/vs/workbench/contrib/chat/common/model/chatModel.ts:3988</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU spent rebuilding normalization text, lexing Markdown, and scanning source/removal spans, plus temporary strings, arrays, and lexer tokens.  
**Scaling:** One additional normalization per qualifying response per completed query/content debounce, across the entire transcript. Work scales with each response's full Markdown and source-span/removal collections; cold and warm rebuilds both repeat it. It is not a separate operation per file reference.  
**Outcome:** Increased synchronous Find-rebuild latency and allocation/GC pressure on large restored transcripts.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Find performed one legacy-normalization pass per response for annotation/source mapping, then extracted plaintext directly from the raw parts. Accessible View likewise performed its existing annotation pass for joined code-block descriptions without independently rerunning legacy normalization during its parts loop.  
**Changed behavior:** Plaintext extraction independently repeats legacy normalization after its caller has already performed it for rendered-part mapping. The Accessible View provider also already normalizes through describeJoinedCodeBlocks before entering this new generator.  
**Confidence:** 0.97 — Both synchronous call paths and the lack of memoization are explicit in the code. getLegacySubagentMarkdown's guard limits substantial work to responses containing a non-standalone subagent codeblockUri; for those responses it constructs and lexes the full Markdown. The uncertain factors are the size and prevalence of these restored histories, not the additional pass.

**Causal diff evidence:** Added chatModel.ts:3988 invokes getLegacySubagentMarkdown from getResponsePartsForPlaintext. The changed chatFindContent.ts:100 now uses this generator, whereas the old loop visited response parts directly. chatFindModel.ts:74 already invokes annotateSpecialMarkdownContentWithSource, whose annotations.ts:23 calls the same normalization helper. Thus each Find rebuild now normalizes every qualifying response twice instead of once.

Searching a large restored agent transcript with legacy subagent file references performs an extra full-response Markdown lexing/allocation pass for every qualifying response on each debounced rebuild, increasing main-thread pauses and GC pressure. This also applies when those responses contain no empty thinking markers.

**Evidence:** chatFindModel.ts:74 computes annotations before calling getChatFindTextParts at line 84. annotations.ts:23 normalizes through getLegacySubagentMarkdown. The new generator repeats that call at chatModel.ts:3988. For qualifying responses, chatModel.ts:4035-4114 builds concatenated text and span arrays, invokes marked.lexer for each segment, and computes removals. None of these results are cached. ChatFindModel.recompute builds segments for the entire transcript synchronously; chatFindWidget.ts:258,311-320 coalesces content changes with a 200 ms Delayer but does not reuse normalization between the two calls within one rebuild. Accessible View similarly calls describeJoinedCodeBlocks, which annotates, before iterating the generator.

**Suggested direction:** Compute legacy normalization once per response extraction/rebuild and pass the result to both annotation and plaintext coalescing. Keep the existing distinct plaintext/source-mapping semantics; a persistent cache is not necessary to eliminate this duplicate pass.


## Performance regression fixes detected (1)

### 1. serialization-allocation

**Fix location:** `src/vs/workbench/contrib/chat/common/widget/annotations.ts:89` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/common/widget/annotations.ts:94`  
**Introducing path:** `src/vs/workbench/contrib/chat/common/widget/annotations.ts`  
**Introducing commit:** `f5929d2a1e34b2dc062e80f9b14958d915928a44`  
**Mechanism family:** `serialization-allocation`  
**Performance category:** `gc`  
**Confidence:** 0.97

**Mechanism:** Copying the accumulated sourceIndexes array for each merged fragment caused quadratic index copying and temporary allocations.

**Symptom:** Avoidable synchronous CPU and GC pressure on fragmented restored responses and inline-reference runs; established statically, without measured timings.

**Fixed behavior:** Push source indices into function-local arrays, eliminating repeated growing-array copies while preserving source mappings.

**Evidence:** Base annotations.ts:94 spread the entire growing sourceIndexes array for every compatible Markdown merge. A run of n compatible restored fragments therefore copied n(n-1)/2 indices. The annotation function is synchronously called by chatListRenderer.ts:getNextProgressiveRenderContent and chatFindModel.ts:buildSegments. Added annotations.ts:89 uses push on the locally owned entry instead, and analogous merge branches are updated. blame\_base\_line resolved the old allocation to f5929d2a1e34b2dc062e80f9b14958d915928a44 at the same origin path.
