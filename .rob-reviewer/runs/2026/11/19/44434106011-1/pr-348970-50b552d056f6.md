### Scenario 1: Create an automation with client-served customizations on a local or remote Agent Host

- Critical path: The store resolves its customization scope, dispatches the create action, and waits for authoritative catalog state. The added URI iteration registers grants synchronously but does not await realpath before dispatch. Host capture, persistence, and response remain on the save critical path; subsequent permission checks can await grant realpath promises.
- Scaling input: N selected/enabled customization references; U distinct URI keys not already granted on this connection, U &lt;= N. Actual capture traffic depends on uncached bundle files/directories and their total bytes, not on all installed customizations or automation catalog entries.
- Effective concurrency: The new grant loop starts up to U asynchronous realpath operations without awaiting them or adding a limiter. Host catalog mutations are globally serialized by \_mutationTail and capture iterates customization references sequentially. The client-filesystem provider limits content reads to 10; metadata/list operations are separate. No per-file concurrency increase is introduced by this diff.
- Cache behavior: The existing connection-wide ResourceSet deduplicates grants across automation actions, session actions, and session creation. Each new URI retains one grant and one realpath promise, including fallback to the lexical URI on failure. Host capture reuses a nonce-derived destination when present; references without a nonce receive a fresh destination. Providers without realpath capability perform no underlying realpath operation.
- Mechanism confidence: High: traced store dispatch, synchronous grant registration, production grant service, provider realpath, host capture cache, mutation sequencer, and content-read limiter.
- Magnitude uncertainty: No runtime timings or installed-plugin distribution are available. Cold grants can fan out by selected distinct customization roots, but the inspected path provides no evidence of a pathological count or unnecessary repeated boundary work.

### Scenario 2: Update an automation, including repeated saves, customization replacement, and updates without a session customization change

- Critical path: The store dispatches an update and waits for matching authoritative catalog state. The added branch runs only when changes.session.customizations is present. Existing host capture runs for session changes and precedes persistence.
- Scaling input: N submitted customization references; U previously unseen URI keys on the connection; K changed references requiring capture after comparing previous id/URI/nonce. Repeated edits to title, triggers, or other fields may resend a session template but do not imply U = N or K = N.
- Effective concurrency: Grant realpaths for U new URIs launch asynchronously. Existing updates are globally serialized on the host; capture processes references sequentially, with the shared provider's 10-content-read limiter for any copied bundles.
- Cache behavior: Repeated saves of identical URIs only parse/check N references and add no grants or grant realpath calls. Previously captured references with matching id, URI, and nonce are reused without contacting their client. Different nonce at the same URI does not create an additional client grant. Missing session/customizations adds no work.
- Mechanism confidence: High: verified both changed branches, ResourceSet deduplication, store session-template reuse, and host previous-reference comparisons.

### Scenario 3: Reconnect with pending automation actions and close/dispose the connection

- Critical path: Reconnect drains pending actions before queued outgoing messages. It deduplicates pending actions against queued clientSeq values, then re-runs the existing outgoing-grant hook for replayed actions. Terminal close clears URI keys and disposes grants.
- Scaling input: Pending replayed actions and their customization references; grant allocation and realpath work depend on the union of previously ungranted URI keys, not the sum of references across every replay. Retention depends on unique granted URIs during the connection lifetime.
- Effective concurrency: Reconnect constructs and sends replays in existing order, skipping sequences already queued. Any cold grant realpaths are asynchronous and can overlap; warm replays add none. No new replay notifications or reconnect loops are introduced.
- Cache behavior: Ordinary soft reconnect retains the dedup set, so replayed same-URI grants are warm. Connection-setup restart explicitly clears grants; subsequent applicable grant registration is cold. Terminal close clears both the dedup set and grant store, and the resource service removes identity-owned grants. The grant store is also registered for disposal.
- Mechanism confidence: High: verified reconnect hook placement, queued-sequence deduplication, grant reset points, terminal-close cleanup, and registered disposal ownership.
- Magnitude uncertainty: Pending-action count and distinct URI turnover are not measured. No additional unbounded replay queue, resource watcher, or persistent grant lifecycle was introduced.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:\_drainAfterReconnect, \_beginReconnectFromConnecting, \_handleClose; src/vs/workbench/services/agentHost/common/agentHostResourceService.ts:grantImplicitRead</code>: Potential canonical-path resolution for replayed automation grants that are not already registered.; cardinality: Zero additional grant realpaths for warm URIs; at most one per distinct cold URI. Grant cleanup itself deletes in-memory entries rather than performing filesystem operations.
    - Introduced by diff: true; previous behavior: The outgoing-action hook was already called during replay but did not handle automation create/update actions.; critical-path effect: No newly awaited filesystem operation in reconnect draining; later access checks can await grant promises.
  - network at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:\_drainAfterReconnect</code>: Replay unacknowledged action notifications and flush the queued outbox.; cardinality: Existing replay/outbox cardinality, with clientSeq deduplication; the diff adds no wire messages for permission grants.
    - Introduced by diff: false; previous behavior: Identical replay notifications and outbox ordering, without automation-specific grant registration.; critical-path effect: The existing replay ordering is preserved.
- Verdict: No reportable replay fan-out or retention regression. Grants reuse existing connection ownership and cleanup, and repeated references are deduplicated.
