# Performance review: Keep the new tab button next to the last tab when tabs wrap

[PR #349041](https://github.com/microsoft/vscode/pull/349041) at `87b8fea51942cbc9463760a07314cdc88618a3c6`

## Findings (1)

### 1. [low] Preserve the follow layout on geometry-neutral updates

**Finding ID:** `PERF-843F272FFC76`  
**Location:** <code>src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:2139</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Main-thread browser style/flex layout work over the tab strip and an additional array/geometry pass over its tabs.  
**Scaling:** One undo-and-reapply cycle per affected visible tab control per scheduled animation frame, with layout and row-marker work scaling with that control's tab count; requests in the same frame are already coalesced.  
**Outcome:** Additional synchronous renderer CPU/layout time on the next-paint critical path, including warm updates with unchanged geometry.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The existing wrapping layout measured and updated row markers without temporarily changing the last tab's margins to move it between rows and then restoring that arrangement.  
**Changed behavior:** Every queued tab layout now removes the follow class before measuring wrapping, then reapplies it and measures again when the button would otherwise be orphaned, including when tab and group geometry have not changed.  
**Confidence:** 0.93 — The changed margin rules, both write/read flush points, callers, and per-control animation-frame coalescing are directly traceable. This is static evidence of extra work, not a measured frame-time result; its bounded and configuration-dependent magnitude warrants low severity.

**Causal diff evidence:** The added unconditional classList.remove at line 2139 changes the margins defined by the new add-tab-follows-last-tab CSS rules. doLayoutTabsWrapping immediately reads addTabContainer.offsetWidth at line 2249; the new helper reapplies the class at line 2419 and immediately reads offsetTop at line 2420.

For groups containing many wrapped tabs, repeated tab activation or resizing spends additional renderer time laying out an intermediate arrangement that is never displayed, reducing frame headroom and input responsiveness.

**Evidence:** With wrapTabs enabled and the follow class already active, removing it moves the last tab back to the previous row. The subsequent geometry read flushes that intermediate flex layout, and layoutAddTabWithLastTab then changes the margins again and synchronously flushes the corrected layout. The helper also repeats the collection-wide row-marker measurement. This repeats for unchanged-size calls from handleOpenedEditors (including reopening the active editor), selection/dirty invalidation in Connected tabs, and group layout. layout() coalesces requests within one animation frame, but does not suppress these cycles across frames.

**Suggested direction:** Keep the existing follow/wrapping decision for geometry-neutral updates rather than always removing the class. Invalidate that decision when available/container dimensions, tab geometry or membership, toolbar width, or add-button visibility/width changes; retain the unadjusted measurement when such an invalidation actually requires it.
