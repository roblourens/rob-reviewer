### 1. [medium] Index sessions once before projecting run history

**Finding ID:** `PERF-5293886CBDB9`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/automationsLayoutWidget.ts:568</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Repeated allocation of complete provider/session arrays and linear URI/previous-identity comparisons.  
**Scaling:** For H linked visible history runs and S known sessions, the runs projection makes about 2H full-collection lookups: O(H\*S) work and array-element allocation per recomputation. Marking U distinct sessions read can cause U recomputations because those observable writes are not batched together. Warm session caches do not eliminate array reconstruction.  
**Outcome:** Increased opening/update latency and renderer CPU/GC pressure; bulk read-state changes multiply the synchronous work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The existing cards/history surface took one getSessions snapshot, indexed it by URI comparison key, and associated history through map lookups, O(S+H) for this association. Its history rendering is also suspended while Mark all as read is running; ordinary already-presented runs do not require the cards' fallback session lookups.  
**Changed behavior:** Opening either experimental layout now resolves every linked historical run through a collection-wide session lookup, and repeats these lookups whenever the runs projection is invalidated, including individual read-state changes.  
**Confidence:** 0.99 — Traced the unconditional runs.map, both getSession calls, and SessionsManagementService.getSession through \_getAllSessions and provider.getAllSessions. The latter rebuilds session arrays even with warm provider caches. The existing view's single snapshot/map provides a direct before/after comparison. Duration depends on history and session counts, not on an uncertain call path.

**Causal diff evidence:** The new history projection calls getSession for every run at automationsLayoutWidget.ts:568, after withLocalProgress already calls it at :546. The existing AutomationsCardsWidget instead builds sessionsByResource once at automationsView.ts:336-348 and passes that map into history rendering.

With hundreds of retained runs and a large session history, opening Automations or processing live session updates performs repeated full-session scans on the renderer thread. Mark all as read is particularly costly: individual isRead changes rerun the whole projection despite the provider's event batching, potentially freezing the surface and generating substantial garbage.

**Evidence:** AutomationsLayoutModel.runs maps the entire visible history at lines 564-598; each linked run invokes getSession through withLocalProgress and again at line 568. SessionsManagementService.getSession (sessionsManagementService.ts:435-445) calls \_getAllSessions(), which enumerates every provider's sessions, then performs a linear find. BaseAgentHostSessionsProvider.getAllSessions (:5608-5641) constructs a fresh array on every call. The widget unconditionally observes model.runs at :1032, even outside Runs/details. The projection also observes each finished session's isRead at :590; setSessionsReadState (:8397-8406) pauses provider events but does not transactionally batch those observable changes.

**Suggested direction:** Resolve sessions from one URI-identity-aware snapshot/index per model update instead of calling getSession inside the run loop and its progress helper. Preserve hidden-session and previous-identity resolution semantics, and coalesce the projection during bulk read updates.

### 2. [medium] Preserve table rows across live run updates

**Finding ID:** `PERF-BAC365698E9D`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/automationsLayoutWidget.ts:1540</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** DOM nodes, Button/Switch instances, hover registrations, event listeners, and browser layout work.  
**Scaling:** Each observed run/session update recreates O(N) expanded, filtered automation rows and, when details are open, O(Ha) run-detail rows for that automation. Cost grows with update frequency times N+Ha; there is no scheduling/coalescing before these synchronous renders. Collapsed sections reduce N but do not prevent rebuilding the remaining table.  
**Outcome:** Repeated renderer CPU work, DOM/control allocation and garbage collection, increasing the risk of dropped frames during live updates.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The baseline page retained keyed automation cards and persistent history groups/session lists. Live session presentation could update its own observable consumers without disposing and reconstructing the complete automation catalogue; unchanged session-list membership short-circuited updates.  
**Changed behavior:** An individual run's activity, title, artifacts, or read-state update now tears down and recreates the entire displayed automation table, plus the selected automation's entire run-details body when open.  
**Confidence:** 0.98 — The observable subscriptions and unconditional destructive render calls are explicit. Agent-host activity updates reach session.description and session-change notifications, and the model subscribes to both. The old view's persistentCards and identity-checked history blocks establish that full reconstruction is new. No timing measurements are assumed.

**Causal diff evidence:** The new widget autorun at :1027-1051 reads the complete model.runs and always calls renderPane. Added lines :1536-1540 clear all row disposables, switches, and DOM before rebuilding every displayed row. The open-details autorun similarly rebuilds its complete body at :2196-2217.

While an automation is running, activity updates repeatedly reconstruct even unrelated rows. With a substantial automation list or long history in the open details panel, this causes avoidable main-thread allocation/layout work and visible interaction or scrolling jank. Updating another automation's run also rebuilds the selected details.

**Evidence:** The widget subscribes to model.runs regardless of selected navigation (:1032). That model reads live session outcomes, artifacts, changes, and read state (:582-590), so changes unrelated to a table row's displayed fields still invalidate the table. renderPane disposes all controls and clears this.content (:1536-1540), then renderAutomationSections/renderAutomationRow recreate all shown rows, Buttons, Switches, hovers, and listeners. Details also subscribe to the global runs collection (:2085-2088), clear their body (:2196-2198), and map every own run into new DOM (:2306). In contrast, AutomationCardsSection keeps persistentCards (:642-651), and AutomationHistorySection.updateGroupSessions (:2338-2344) returns when session identities are unchanged.

**Suggested direction:** Keep keyed row/control instances and update only changed presentation fields. Separate navigation counts and live run-detail dependencies from the catalogue renderer, and scope details updates to the selected automation rather than the global runs collection.
