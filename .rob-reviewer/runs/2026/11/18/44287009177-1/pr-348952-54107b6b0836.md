### Scenario 1: Load Agent Host installation inventory and resolve friendly names, including reloads and registry replacement

- Critical path: Plugin inventory and SDK installation inventory must finish before the installation snapshot is available. The added registry lookup is explicitly fire-and-forget; inventory does not await registry responses. A successful batch subsequently requests one inventory refresh.
- Scaling input: Distinct registry-shaped configured names lacking catalogue metadata, deduplicated across a batch and cached across sessions owned by the provider; typically a user's configured MCP-server collection rather than registry search results.
- Effective concurrency: Inventory plugin and installation reads are sequential at provider level; three SDK inventory reads run in parallel. Registry resolution uses Promise.all across distinct missing names, sequential endpoint fallbacks per name, and no application-level global limiter; actual HTTP transport scheduling is browser-controlled.
- Cache behavior: Found and definitive NotFound results are remembered for the registry lifetime. Pending requests and transient failures receive a five-minute retry timestamp, suppressing immediate duplicate reads. Retries require another inventory read, not a periodic timer. Registry replacement swaps the map and stale responses cannot publish a refresh. Policy-session creation is separately coalesced and its live session is reused.
- Mechanism confidence: High: traced the changed invocation through gallery endpoint resolution and native fetch, plus the inventory refresh consumer and cache states.
- Magnitude uncertainty: Configured-name counts, response sizes, registry latency and browser connection scheduling are not measured.

- Critical path: Form construction creates choice sections synchronously. Input validation, multiline measurement and scrollbar scanning run on the renderer; cancellation removes the page and resolves collection without applying.

- Effective concurrency: Renderer work is synchronous; ResizeObserver triggers layout. No network, filesystem, SDK calls or subprocess launches are made by editing or transport switching.
- Cache behavior: Each choice keeps its controls and entered values for the form lifetime. Multiline inputs are measured on layout. The page, observer, controls, event subscriptions and cancellation listener are disposed together on close, replacement, hidden editor or navigation.
- Mechanism confidence: High: reviewed all form code, InputBox layout, scrollbar scanning and editor-owned DisposableStore/MutableDisposable cleanup.
- Magnitude uncertainty: DOM/layout timings were not profiled; no evidence established a self-sustaining resize loop or realistically excessive field count.
- Expensive boundaries: none found
- Verdict: All-choice construction and geometry measurements are bounded by the current form, with explicit teardown. No high-confidence eager-work, layout-thrashing or retention regression found.
