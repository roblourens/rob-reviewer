## Performance regression fixes detected (1)

### 1. unbounded-retention

**Fix location:** `src/vs/workbench/contrib/sessions/browser/agentsView/agentsChatPart.ts:875` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/sessions/browser/agentsView/agentsChatPart.ts:856`  
**Introducing path:** `src/vs/workbench/contrib/sessions/browser/agentsView/agentsChatPart.ts`  
**Introducing commit:** `3b381b139291d9bbdd5a5a1ae60d41dad26d137d`  
**Mechanism family:** `unbounded-retention`  
**Performance category:** `memory`  
**Confidence:** 0.95

**Mechanism:** In Single mode, moving a nonempty unsent composer between chat-part groups fired the ordinary close handlers, which captured its draft and appended it to \_kept although the same composer stayed open in the target. Repeated moves accumulated duplicate entries without consuming them. \_save/\_writeStored exported attachments and serialized every entry, so m moves of a draft of serialized size d added O(m\*d) serialization and stored bytes; editing between moves could also retain distinct historical snapshots.

**Symptom:** Statically established accumulation of duplicate kept drafts across moves, with increasing save-time allocation/serialization and persisted state; reloading also materializes the duplicate drafts. No measured timings are claimed.

**Fixed behavior:** The added MOVE guards skip both draft capture and the kept-draft append for a transfer, preserving the live composer and retaining its draft only when it actually closes.

**Evidence:** EditorGroupView.doMoveOrCopyEditorAcrossGroups opens the same input in the target before closing it in the source with EditorCloseContext.MOVE (editorGroupView.ts:1603-1607); handleOnDidCloseEditor still fires close events but does not dispose an input open elsewhere (lines 719-746). The deleted base line 856 appended the captured draft unconditionally, and no move path pops \_kept. The new guards at agentsChatPart.ts:862 and :875 bypass this. \_captureClosingComposerInput/\_sendableComposerInput (909-931) show that nonempty unsent drafts qualify; \_writeStored (986-994) maps every kept entry through toStoredChatDraft and stringify, and newChatDraftState.ts:39-44 exports all attachments. The added movedD case at agentsChatPart.test.ts:1302-1311 corroborates retaining the moved draft only once. Blame identifies the introducing commit for the old append.

- Mechanism confidence: High: lifecycle cleanup, move restrictions, and event ordering were inspected. No subprocess, network, filesystem, or database operation is added to the changed callbacks; persistence occurs on the separate save path.
- Magnitude uncertainty: No timings or large-tab-count profiles were available. The added linear array bookkeeping is evident but does not establish a meaningful regression for realistic interactive tab counts.
- Expensive boundaries: none found
- Verdict: No qualifying introduced regression. The MOVE guards also fix duplicate draft retention, recorded separately through report\_regression\_fix with blame provenance.
