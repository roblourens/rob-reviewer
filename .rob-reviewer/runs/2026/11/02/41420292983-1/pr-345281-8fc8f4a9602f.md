# Performance review: agentHost: manage sandbox CA trust on remote agent hosts

[PR #345281](https://github.com/microsoft/vscode/pull/345281) at `8fc8f4a9602f5926d6e576333852d8d8b3497251`

## Findings (1)

### 1. [medium] Keep unrelated session checks off the Refresh critical path

**Finding ID:** `PERF-99FEAB716381`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:4820</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SDK IPC calls to Copilot runtimes (\`checkRelevance\`, \`checkInstallationSupport\`, and \`getStatus\`).  
**Scaling:** After cache invalidation, work grows with the number of distinct live \`(CopilotClient RPC, credential configuration)\` groups: identical groups coalesce, but each scoped runtime incurs its own check sequence and all groups are launched concurrently.  
**Outcome:** The interactive Refresh critical path is extended by the slowest unrelated live-session status check and can generate excessive concurrent IPC.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The PR base had certificate mutation paths but no read-only Refresh method or UI action, so a status refresh request did not fan out across and await every live session.  
**Changed behavior:** A Refresh click now refreshes the selected session, globally invalidates shared certificate observations, and then synchronously refreshes certificate diagnostics for every live session before replying to the client.  
**Confidence:** 0.97 — The call path is explicit from the added protocol method to \`\_withSandboxCertificateRefresh\`, and the repository tests prove that refresh invalidates every client/configuration. Distinct scoped chats use distinct \`CopilotClient\` runtimes, while each uncached status check performs bounded SDK RPCs. The only magnitude uncertainty is how many scoped live chats a typical host retains.

**Causal diff evidence:** The added \`refreshSandboxCertificate\` implementation at RIGHT line 4820 routes the new Refresh request through \`\_withSandboxCertificateRefresh\`; that helper does not return until \`Promise.all(this.\_allLiveSessions().map(...))\` completes. Before this PR there was no refresh request/action, so an interactive read-only refresh could not trigger this all-session wait.

On a remote host with several live or credential-scoped chats, clicking Refresh keeps the notice spinner and the AHP request open until unrelated sessions finish their SDK status checks. One slow unrelated runtime can add up to roughly 15 seconds of tail latency, while many scoped runtimes also create a concurrent IPC burst.

**Evidence:** \`CopilotSandboxCertificate.refresh\` replaces the entire \`\_runtimes\` WeakMap, so observations for all clients/configurations are cold. \`\_withSandboxCertificateRefresh\` then awaits \`Promise.all\` over \`\_allLiveSessions()\`. Each cold \`CopilotSandboxCertificateDiagnostics.update\` reaches \`\_check\`, which calls \`checkRelevance\`, one coalesced \`checkInstallationSupport\` per runtime, and \`getStatus\`; each \`\_query\` can wait 5 seconds. \`CopilotAgent.\_ensureClientForChat\` creates a separate scoped \`CopilotClient\` per credential-scoped chat, so those calls are not all collapsed by the per-RPC cache. \`copilotSandboxCertificate.test.ts\` explicitly verifies that refresh invalidates and rechecks multiple clients and configurations.

**Suggested direction:** Await and return the selected session's fresh status, then publish diagnostics for other affected live sessions off the request critical path using bounded, per-RPC/config coalesced work. Preserve eventual all-session updates without making the clicked chat wait for unrelated runtimes.
