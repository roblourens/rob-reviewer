# Performance review: Update bundled DOMPurify to 3.4.17

[PR #345505](https://github.com/microsoft/vscode/pull/345505) at `f4c8396ec7f35243dcf864130e01a447d692cba1`

## Findings (1)

### 1. [low] Coalesce the new whole-tree IN\_PLACE bookkeeping

**Finding ID:** `PERF-EC7CA6BF96BA`  
**Location:** <code>src/vs/base/browser/dompurify/dompurify.js:2440</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** DOM traversal CPU plus arrays and Sets retaining references to O(N) DOM nodes  
**Scaling:** The added work and retained references grow linearly with every node in the input tree; in the no-mutation common case all three extra O(N) walks still execute, with no cache, coalescing, or early gate.  
**Outcome:** increased synchronous sanitization latency and transient GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, \`IN\_PLACE\` did not snapshot every input node, maintain a visited Set, rescan for unvisited originals, or build a final reachable Set; after the existing patch-linkage and shadow-root scans it sanitized the tree and only neutralized subtrees recorded as removed.  
**Changed behavior:** Every successful \`IN\_PLACE\` call now performs three additional whole-tree walks and allocates an N-node snapshot, an N-entry visited Set, two temporary N-node arrays, and a reachable-element Set, even when no hook or custom element moves a node.  
**Confidence:** 0.96 — The public declaration explicitly supports \`IN\_PLACE\` as the faster node-sanitization mode, and the changed synchronous call path and unconditional helper calls establish the added O(N) work directly. Exact wall-clock cost varies by DOM size and browser, which is reflected in low severity; VS Code's in-repository markdown callers use strings, but the vendored Monaco API exposes this path to downstream consumers.

**Causal diff evidence:** RIGHT line 2440 newly snapshots the entire live tree with \`\_collectLiveNodes(dirty)\` immediately after the pre-existing \`\_neutralizePatchLinkage(dirty)\` full-tree sweep. The same diff then adds another \`\_collectLiveNodes(root)\` in \`\_sanitizeUnvisitedNodes\` (reached unconditionally at RIGHT line 2463) and another in \`\_neutralizeEscapedElements\` (reached unconditionally through RIGHT line 2475).

A Monaco consumer sanitizing a large existing DOM with \`{ IN\_PLACE: true }\` now blocks the calling/UI thread for roughly twice as many whole-tree traversals and creates several node-sized collections, increasing latency and GC pressure on the exact large-tree use case for which \`IN\_PLACE\` is documented as faster.

**Evidence:** For an unchanged N-node tree, the old path already swept \`\_neutralizePatchLinkage\`, scanned for attached shadow roots, and ran the sanitizer iterator. The new path additionally collects all live nodes at entry, marks every sanitized node in a Set, collects the tree again solely to discover whether anything was unvisited, and finally collects it a third time to construct a reachable Set before returning. None of these three added traversals is conditional on actual tree mutation.

**Suggested direction:** Preserve the mutation hardening but coalesce bookkeeping with existing walks: collect the initial snapshot during the patch-linkage/shadow discovery pass, and have the unvisited/reachability walkers update their boolean/Set directly instead of first materializing full \`live\` arrays. This removes duplicate traversal/allocation without dropping the final mutation checks.

### Scenario 1: VS Code markdown, notebook, and release-note string sanitization before rendering

- Critical path: DOMPurify sanitizes synchronously before markdown, notebook output, or release-note HTML can be assigned to the DOM, so sanitizer CPU is on the rendering critical path.

- Effective concurrency: Calls are synchronous and serialized on the renderer/UI thread; there is no worker, limiter, queue, or coalescing layer.
- Cache behavior: No sanitizer result cache is used; each rendered HTML string is parsed and sanitized independently, for both cold and repeated renders.
- Mechanism confidence: High: call sites, configuration construction, and the \`typeof dirty \!== "string"\` IN\_PLACE gate were traced directly.
- Magnitude uncertainty: Markdown size and render frequency vary, but repository callers pass strings and therefore do not enter the new IN\_PLACE snapshot/visited/reachability path.
- Expensive boundaries: none found
- Verdict: No reportable regression on this path. The changed sanitizer remains a synchronous O(N) parse/walk; the substantial new repeated-tree bookkeeping is gated off for string inputs, and the remaining per-node changes do not establish a concrete user-visible regression.

### Scenario 2: Monaco/DOMPurify consumers sanitizing an existing DOM node with IN\_PLACE enabled

- Critical path: The public sanitize call completes all tree scans and collection construction synchronously before returning the sanitized node, so every added pass blocks consumer progress.
- Scaling input: Total light-DOM and open-shadow-root nodes N, after no deduplication is possible because each node identity is retained; element count controls the final reachable Set.
- Effective concurrency: Single-threaded synchronous DOM work; concurrent callers on the same renderer serialize naturally on the event loop, with no batching or backpressure.
- Cache behavior: There is no cache across calls and no reuse of the new node snapshots or Sets; cold and warm calls perform the same bookkeeping.
- Mechanism confidence: Very high: the diff unconditionally adds the entry snapshot, visited Set, unvisited rescan, and final reachability rescan for every successful node input with IN\_PLACE enabled.
- Magnitude uncertainty: The repository contains no direct IN\_PLACE caller, so downstream Monaco usage and typical DOM sizes are uncertain; the API declaration explicitly exposes and describes this mode, lowering severity rather than confidence in the mechanism.
- Expensive boundaries: none found
- Verdict: Reportable low-severity repeated-work regression: the no-mutation common case still adds three O(N) tree walks and multiple O(N) collections on the synchronous call path.

### Scenario 3: First sanitizer-module load in VS Code or Monaco

- Critical path: Static sanitizer initialization may occur on first import, but it performs only local constructor/getter setup and is not connected to filesystem, network, IPC, or subprocess work.
- Scaling input: Fixed-size tables and prototype accessor lookups, independent of document size.
- Effective concurrency: One module evaluation per realm, serialized by the module loader.
- Cache behavior: Module initialization has no cache-miss cycle beyond JavaScript module singleton evaluation; subsequent imports reuse the evaluated module.
- Mechanism confidence: High: top-level additions and removals are directly visible in the diff.
- Magnitude uncertainty: First-import placement varies by bundle and product surface, but the changed fixed-size initialization work is small and does not scale with user content.
- Expensive boundaries: none found
- Verdict: No reportable startup regression; the fixed Set/prototype helper setup is bounded, while removal of the per-tag literal-close regex table offsets initialization work.
