<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work

### Scenario 1: Render or refresh a completed chat reasoning-duration label, including grouped reasoning rows.

- Critical path: On initial rendering of completed reasoning, or after a changed reasoningDurationMs value is matched, the UI synchronously computes the label before setting title/text content. The diff adds Math.ceil, Math.max, division, and multiplication before the existing localization and elapsed-time formatting; no asynchronous work gates progress.
- Scaling input: One computation per completed single-run title and per displayed unique reasoning source when timing changes. History/group size affects a pre-existing render loop, while the diff adds only O(1) work to each existing formatter invocation.
- Effective concurrency: Runs synchronously on the UI thread. Timing refreshes are coalesced by reasoningDurationSnapshots for unchanged values; grouped row formatting remains a serial loop over already-rendered parts, with no new task scheduling or parallel fan-out.
- Cache behavior: No cache behavior changes. Existing duration snapshots suppress unchanged timing updates, and the change neither introduces cache keys nor changes cold/warm behavior.
- Mechanism confidence: High: both call sites, the timing-update deduplication, the grouped-label loop, and the formatter implementation were inspected; the diff only changes constant-time arithmetic passed to the existing formatter.
- Magnitude uncertainty: No benchmark was inspected, but the added work is a fixed number of primitive arithmetic operations per formatted label, so realistic duration values and chat history size do not create a new scaling mechanism.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. The changed label rounding adds negligible constant-time CPU work without new DOM geometry reads, retained state, allocation proportional to duration, or subprocess/IPC/filesystem/database/network boundaries.

**Summary:** Reviewed all four changed files and traced the runtime formatter through construction, finalization, grouped-label refresh, and timing-update deduplication. Documentation and tests have no product runtime impact; the production change adds only bounded arithmetic to existing label formatting, so no performance finding was submitted.
