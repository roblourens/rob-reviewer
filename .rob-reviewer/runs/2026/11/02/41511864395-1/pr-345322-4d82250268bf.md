## Findings

No high-confidence performance findings.

**Relevant issue families:** boundary-fanout, concurrency-burst, cleanup-lifecycle, eager-work

### Scenario 1: Startup with one or more file/workspace protocol URLs from CLI or queued macOS open-url events

- Critical path: Each parsed openable is processed by resolveInitialProtocolUrls in a sequential await loop; when confirmation is enabled, the native message box must complete before that URL can be admitted and startup URL resolution can progress. Parenting remains on this already-existing critical path and adds only synchronous window lookup.
- Scaling input: Number of initial protocol URLs. Confirmations remain one per eligible URL, processed serially; parent resolution checks at most three candidates, with last-active fallback scanning the currently open main windows.
- Effective concurrency: One confirmation at a time because the existing startup loop awaits each URL. The selected parent changes DialogMainService from its global no-window queue to that window's queue, but does not increase startup concurrency.
- Cache behavior: The confirmation setting is read from the existing configuration service for each URL as before. No new cache, cache key, miss behavior, negative cache, or coalescing behavior is introduced.
- Mechanism confidence: High: the call path, await loop, DialogMainService queue selection, and before/after native-dialog count are directly visible in the changed and surrounding code.
- Magnitude uncertainty: The number of URLs supplied in one startup invocation and number of open windows vary, but native-dialog cardinality and serial ordering are unchanged; the added lookup is bounded by realistic window count.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/code/electron-main/protocolDialogs.ts:55 confirmProtocolOpenable</code>: Electron native showMessageBox confirmation; cardinality: One native dialog per eligible initial protocol URL when confirmation is enabled, serially awaited.
    - Introduced by diff: false; previous behavior: The same showMessageBox operation ran once per eligible URL without a parent through the global no-window queue.; critical-path effect: Blocks admission of each URL exactly as before until the user responds; the diff passes an existing BrowserWindow parent but does not add another dialog.
  - IPC at <code>src/vs/code/electron-main/protocolDialogs.ts:76-77 confirmProtocolOpenable</code>: Notify the focused and next opening renderer to disable future protocol prompts when the checkbox is accepted; cardinality: Two sends only for an accepted dialog with the checkbox checked, unchanged from the previous inline implementation.
    - Introduced by diff: false; previous behavior: The inline app.ts implementation issued the same sendToFocused and sendToOpeningWindow calls.; critical-path effect: Synchronous message scheduling occurs after the user response and before the helper returns, as before.
- Verdict: No reportable regression. The change adds small parent selection work but neither adds an expensive boundary nor amplifies its cardinality, concurrency, or retained lifetime.

### Scenario 2: Runtime OS protocol link while a main or auxiliary window is focused, including bursts of links

- Critical path: Electron open-url dispatch reaches URLService and handleProtocolUrl; for file/remote openables the confirmation must settle before the unchanged window-open/link-routing path proceeds. Parent selection precedes the same native dialog and is therefore on the critical path, while subsequent opening work is unchanged.
- Scaling input: Number of runtime open-url events and number of application windows. Each event can request one confirmation; fallback last-active lookup is linear in main-window count only when neither auxiliary nor main focus yields a usable window.
- Effective concurrency: Runtime URL events may overlap. Previously all unparented confirmations shared one global queue; now they queue once per resolved parent. Ordinary bursts with stable focus still serialize on one parent. If focus changes across events, confirmations may run on distinct windows concurrently, bounded by the number of involved windows; this is the intentional modal-parenting behavior and no realistic harmful burst is established.
- Cache behavior: No new cache. The existing configuration value gates every event, and checking the prompt-suppression setting remains unchanged. Dialog queues are existing transient queues deleted on drain.
- Mechanism confidence: High for the queue change and event call path; low evidence of harmful magnitude, because stable-focus bursts remain serialized and the native-dialog count is unchanged.
- Magnitude uncertainty: Pathological event streams with focus alternating among many windows could use more than one existing dialog queue, but realistic protocol-link traffic is low-cardinality and the concurrency remains bounded per window. There is no evidence of CPU, memory, I/O, rendering, or latency degradation sufficient for a finding.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/code/electron-main/protocolDialogs.ts:55 confirmProtocolOpenable</code>: Electron native showMessageBox, now invoked with the focused auxiliary/main or last-active main BrowserWindow; cardinality: One dialog per eligible event, unchanged; events resolving to the same parent are coalesced by the existing per-window DialogMainService queue.
    - Introduced by diff: false; previous behavior: The same confirmation was invoked unparented and used DialogMainService's global no-window queue.; critical-path effect: The user response continues to gate file/workspace opening. Passing the parent changes modality and queue identity but does not add a boundary call.
  - IPC at <code>src/vs/code/electron-main/protocolDialogs.ts:76-77 confirmProtocolOpenable</code>: Optional prompt-disable notifications to focused and opening windows; cardinality: Two sends per accepted checked confirmation, unchanged and independent of link collection size.
    - Introduced by diff: false; previous behavior: Identical sends occurred inline in shouldBlockOpenable.; critical-path effect: Scheduled after confirmation; no new serialization or round trip is added.
  - other expensive boundary at <code>src/vs/code/electron-main/app.ts:1138 handleProtocolUrl</code>: Existing windowsMainService.open and downstream file/remote window handling after confirmation; cardinality: At most one open operation per admitted openable, unchanged by this diff.
    - Introduced by diff: false; previous behavior: The same admitted URL followed the same open path.; critical-path effect: Runs only after confirmation and is not moved, duplicated, or modified by the parent-selection change.
- Verdict: No reportable performance regression. Per-window queueing is a direct consequence of required native modality, remains bounded, and does not increase calls per link.

### Scenario 3: Protocol confirmation with no usable window, or with a parent destroyed while the prompt is pending

- Critical path: Parent resolution checks focused auxiliary, focused main, and last-active main windows. With no live parent it calls the same unparented native dialog as before; with a selected parent, destruction causes the helper to block after the dialog settles or rejects.
- Scaling input: One pending confirmation and at most the current main-window collection for fallback selection; repeated requests without a window continue sharing the existing global no-window queue.
- Effective concurrency: No-parent requests serialize on DialogMainService's unchanged global queue. Parent-bound requests serialize per selected window. Destruction handling does not schedule retries or replacement dialogs.
- Cache behavior: No cache is consulted beyond existing configuration gating. Existing DialogMainService queue entries are removed when drained, including rejection paths through Queue settlement.
- Mechanism confidence: High: explicit single-call try/catch and post-await checks establish bounded work, and DialogMainService owns queue cleanup.
- Magnitude uncertainty: Electron rejection timing after parent destruction is platform-dependent, but the diff adds no loop, retry, retained handle, or additional boundary call.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/code/electron-main/protocolDialogs.ts:55 confirmProtocolOpenable</code>: Electron native showMessageBox with undefined or selected parent; cardinality: Exactly one call per confirmation attempt; no retry on destruction.
    - Introduced by diff: false; previous behavior: One unparented native dialog was shown and awaited.; critical-path effect: Remains the sole blocking prompt boundary. Destruction checks are synchronous and do not add boundary work.
- Verdict: No reportable performance issue. The new destruction checks are constant-time and do not leak, retry, or amplify native work.

**Summary:** Reviewed all three changed files and traced startup and runtime protocol-link flows through native dialog queueing, window lookup, optional IPC notification, and downstream opening. The PR preserves expensive-boundary cardinality and adds only bounded parent resolution; no actionable performance regression was found.
