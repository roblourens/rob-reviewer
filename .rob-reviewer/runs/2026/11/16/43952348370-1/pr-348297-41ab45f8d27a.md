- Critical path: Module evaluation registers service descriptors; both services remain delayed, so neither NullChatWindowService nor SessionAttentionService construction is added to startup's critical path.
- Scaling input: One registration per window/module load; no collection-sized work was added.
- Effective concurrency: No asynchronous work or queue is started by the changed registration/import lines.
- Cache behavior: No cache is read. Delayed singleton instantiation remains demand-driven before and after the change.
- Mechanism confidence: High; the changed singleton declarations use InstantiationType.Delayed, and the same sessions contribution that previously registered the attention service now imports its self-registering module.
- Magnitude uncertainty: None material: the changed work is descriptor registration and import relocation only.
- Expensive boundaries: none found
- Verdict: No regression. Registration ownership moved without eager construction, I/O, IPC, or repeated startup work.

- Verdict: No regression. Existing background network/IPC behavior is neither introduced nor amplified.

### Scenario 3: Reopening the most recently closed session or chat in a scoped editor window

- Critical path: The command synchronously resolves the recorded resource through getSession, then an existing chat reopen may await provider resource resolution and session/chat loading. The changed lookup itself is an in-memory traversal and is not awaited on a remote listing.
- Scaling input: Number of registered providers and total cached sessions; history cardinality is fixed at one.
- Effective concurrency: Resource resolution is serialized across providers; agent-host catalog refreshes are coalesced per provider; only one closed history item is retained and reopened.
- Cache behavior: Warm lookups enumerate cached arrays. On a cold agent-host cache, refresh is shared and not awaited; there is no new retry or negative-cache behavior.
- Mechanism confidence: High; getSession traverses all provider caches and the downstream open path is unchanged.
- Magnitude uncertainty: Total session history can vary, but the new all-session traversal is linear, synchronous, and only occurs on the explicit reopen command.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/sessions/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_ensureSessionCache/\_listSessions</code>: Cold agent-host session catalog refresh via connection.listSessions().; cardinality: At most one current refresh per agent-host provider, with calls coalesced and one optional trailing refresh; provider subscription already requests the unscoped catalog.

- Verdict: No reportable regression. The broader lookup enables hidden sessions, adds no uncoalesced boundary call, and runs once per explicit reopen.

### Scenario 4: Opening, editing, and cleaning up an agent-session settings document for a session outside listing scope

- Critical path: A synthetic filesystem read serializes current config and performs an in-memory all-session lookup before registering a JSON schema. Saving parses the document and uses the existing replaceSessionConfig operation. Provider removal performs synchronous schema cleanup.
- Scaling input: All cached sessions known by the selected provider rather than only the scoped listed subset. Config-change lookup and provider-removal cleanup are O(total cached sessions).
- Effective concurrency: Reads and schema updates are synchronous per event; catalog refresh is coalesced per provider; saves issue one awaited replacement.
- Cache behavior: Session data is cache-backed; schema registration is lazy on first read and skips refresh when schema identity is unchanged. Provider cleanup disposes only registered schema map entries even though it enumerates all known sessions.
- Mechanism confidence: High for the broader linear traversal and high that no new awaited boundary is added.
- Magnitude uncertainty: A provider may retain more hidden sessions than the scoped list, but the added cost is an array construction/search on explicit read or config-change events and a one-time provider-removal traversal; no evidence establishes a realistic user-visible delay.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/sessions/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_ensureSessionCache/\_listSessions</code>: Cold agent-host session catalog refresh via connection.listSessions().; cardinality: At most one coalesced refresh per provider; normal provider registration has already requested this catalog before the AfterRestored settings contribution is used.
    - Introduced by diff: false; previous behavior: The same provider catalog was already initialized through management-service provider subscription and through unscoped getSessions.; critical-path effect: The synchronous getAllSessions call can schedule but does not await refresh; readFile uses the currently cached config/session state.
  - IPC at <code>src/vs/workbench/contrib/sessions/providers/agentHost/browser/agentSessionSettingsFileSystemProvider.ts:\_replaceConfig</code>: Replace one session's configuration on save.; cardinality: One replace operation per explicit file save.
    - Introduced by diff: false; previous behavior: The write path and replace call are unchanged.; critical-path effect: Awaited by writeFile and therefore on the save critical path.
- Verdict: No finding. The diff broadens local cleanup/lookup cardinality to preserve hidden-session schemas, but does not add per-session I/O, IPC, eager schema registration, or an unbounded retained collection.
