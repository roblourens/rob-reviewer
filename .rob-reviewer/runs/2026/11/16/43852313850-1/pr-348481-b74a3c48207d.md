# Performance review: agentHost: harden canvas icon reads against races and oversized images

## Findings (1)

### 1. [medium] Flatten icon-update ancestry instead of retaining every prior icon

**Finding ID:** `PERF-F2379DC13423`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:6141</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Historical canvas projection objects and icon data-URI strings retained in memory  
**Scaling:** Retention grows linearly with the number of successful changed-icon refreshes for each open canvas (up to eight projected canvases), rather than remaining bounded to the current projection.  
**Outcome:** Unbounded retained memory and increasing GC pressure over the session lifetime  
**PR causality:** <code>introduced</code>  
**Previous behavior:** An icon refresh replaced the projection in \`\_canvasByInstanceId\`; once in-flight users released the old projection, prior canvas states and their icon data URIs were collectible.  
**Changed behavior:** Each successful icon change now stores \`shown -&gt; current\` in a WeakMap before \`shown\` becomes the strongly held current projection. On the next change, the new current points to the previous current, creating a backward chain.  
**Confidence:** 0.96 — The registry-change call path, 350,000-character icon bound, strong current-map root, WeakMap value semantics, and explicit ancestry traversal are all directly visible. The exact number of repeated icon changes varies by workflow, but the retention mechanism and linear scaling are deterministic.

**Causal diff evidence:** The added \`\_canvasIconUpdateBases.set(shown, current)\` at line 6141 links every replacement to its predecessor, and line 6142 makes \`shown\` strongly reachable from \`\_canvasByInstanceId\`; repeated changed icons therefore retain all predecessors through WeakMap values.

A long-lived session whose canvas extension is repeatedly reloaded with changing icon contents retains every historical icon, causing steadily growing agent-host memory and GC pressure; extension development/hot reload can accumulate roughly one up-to-350k-character data URI per refresh per open canvas.

**Evidence:** \`\_revalidateCanvasIcons\` invokes \`\_showCanvasIcon\` for every open canvas on each registry-change event. A changed icon reaches this line and each projection contains its canvas metadata, including a data URI allowed up to \`MAX\_CANVAS\_ICON\_DATA\_URI\_LENGTH\` (350,000 characters). WeakMap keys are weak, but their values are strongly retained while the key is live: the current projection is live in \`\_canvasByInstanceId\`, its value retains the previous projection, that previous projection is itself a key whose value retains the next predecessor, and so on. \`\_isCurrentCanvasProjection\` confirms the code intentionally walks this full chain. There is no per-canvas chain bound until the projection is replaced for another reason, closed, or the session is cleared.

**Suggested direction:** Keep ancestry bounded: map each icon-only replacement directly to the canonical/root projection needed by restoration (or use a stable projection/version token), rather than to the immediately previous projection, so intermediate states and old icon strings become collectible.
