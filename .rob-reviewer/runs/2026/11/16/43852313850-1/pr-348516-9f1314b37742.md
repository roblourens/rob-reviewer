# Performance review: Chat resources: show recorded resources of any provided scheme

[PR #348516](https://github.com/microsoft/vscode/pull/348516) at `9f1314b37742b71a31058b0ed92c0fe860f9c28f`

## Findings (1)

### 1. [low] Coalesce extension-status refreshes by scheme

**Finding ID:** `PERF-4BD85D08C0CE`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatResources/chatResourceExistence.ts:66</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** global event-listener callbacks, async refresh promises, and filesystem-provider activation dispatch CPU work  
**Scaling:** For W live chat widgets, R non-filesystem resources, and S extension-status events, this adds O(W×R×S) refreshes even when those resources share one scheme; text-content resources continue refreshing after their provider has already been found because they never acquire a file-system provider.  
**Outcome:** increased CPU/GC pressure and UI-thread latency while extensions activate or repeatedly report runtime errors  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Observed resources listened for file changes and provider registrations only. Contributed resources did not react to extension-status changes, and recorded non-file resources were filtered out before existence observers were created.  
**Changed behavior:** Each observed resource now installs its own global onDidChangeExtensionsStatus listener. Every status event for any extension calls refresh for every resource without a file-system provider; refresh allocates an async continuation and calls fileService.activateProvider, which synchronously dispatches onWillActivateFileSystemProvider into the extension activation service before provider-kind detection.  
**Confidence:** 0.96 — The listener ownership, event frequency sources, synchronous refresh prefix, and per-resource cardinality are directly traced in repository code. Exact milliseconds depend on active widgets and resource counts, so severity is low, but the repeated-work mechanism and before/after increase are certain.

**Causal diff evidence:** RIGHT line 66 adds the per-resource subscription to the global extension-status event; RIGHT lines 67-68 route every unrelated status change for non-filesystem resources into refresh. The same PR also begins feeding recorded resources of arbitrary schemes into these observers, increasing the affected cardinality beyond contributed/file resources.

With chat resources enabled, a long agent chat containing many recorded links/custom resources (and especially multiple open chat editors) multiplies every unrelated extension activation or runtime-error status event into one refresh per resource. This can add bursts of UI-thread CPU and promise garbage during extension activation, even after a text-content scheme is already known to be supported.

**Evidence:** The added listener at line 66 is created by observeChatResourceExists once per distinct resource through mapObservableArrayCached in both ChatResourcesControl and ChatResourceContributionEntries. Its guard is only \!fileService.hasProvider(resource), so text-content resources always pass it. refresh calls fileService.activateProvider before getChatResourceProviderKind; FileService.activateProvider synchronously fires onWillActivateFileSystemProvider, and AbstractExtensionService handles that by calling activateByEvent(onFileSystem:&lt;scheme&gt;). onDidChangeExtensionsStatus fires after every extension activation and runtime error, not only when a relevant text provider registers.

**Suggested direction:** Observe extension-status changes once per control/provider set and coalesce refreshes by unresolved URI scheme. Cache the scheme-level provider kind so one activation probe serves all resources of that scheme, while retaining per-resource file existence/watch logic only after the scheme resolves to a file-system provider.

### Scenario 2: An extension activates, fails, or reports a runtime error while chat resource observers are alive

- Critical path: onDidChangeExtensionsStatus synchronously visits every registered resource listener. Each qualifying listener enters refresh and synchronously dispatches filesystem-provider activation before its first await; the resulting existence update is asynchronous and off the extension's own completion critical path after listener dispatch.
- Scaling input: Live chat widgets × resources without a filesystem provider × extension-status events. Text-content resources remain in this set after successful discovery because the guard checks only fileService.hasProvider.
- Effective concurrency: Every listener starts a separate refresh with no batching or limiter. The extension-host manager caches activation per scheme, so repeated warm events mostly duplicate listener, promise, registry, and dispatch CPU rather than repeated extension-host activation.
- Cache behavior: There is no shared provider-kind cache or negative cache by scheme. Warm text-content hits and unsupported schemes are retried on every unrelated status event; map caches only observer identity/lifetime.
- Mechanism confidence: Very high: the added per-resource global listener, event sources, unconditional text-resource retry, and refresh call path are directly traced.
- Magnitude uncertainty: Exact UI delay depends on resource count, live widget count, and extension event rate; a noisy extension or long session makes the burst larger.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/chatResources/chatResourceExistence.ts:66-69 -&gt; IFileService.activateProvider</code>: Potential first activation of an extension that declares onFileSystem:&lt;scheme&gt;; cardinality: At most one effective extension-host activation per unique scheme because ExtensionHostManager caches the event, but O(resources) activation dispatches and promises are created per status event.
    - Introduced by diff: true; previous behavior: No extension-status listener existed, so unrelated activations/errors caused zero resource refreshes.; critical-path effect: The synchronous dispatch prefix runs during global status-event delivery; any first matching activation is awaited only by each background refresh.
- Verdict: Reportable low-severity repeated-work regression; one finding was submitted recommending scheme-level coalescing/caching.
