# Performance review: mcp: make assisted setup destination-aware

[PR #337845](https://github.com/microsoft/vscode/pull/337845) at `ce12e24461128fb897e19481035b27bc3e8c62f4`

## Findings (1)

### 1. [medium] Do not block the destination picker on Copilot-home discovery

**Finding ID:** `PERF-1FC347102031`  
**Location:** <code>src/vs/workbench/contrib/mcp/browser/mcpCommandsAddConfiguration.ts:371</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** A main-process or remote-agent IPC call that resolves the shell environment and Copilot home directory  
**Scaling:** The uncached lookup runs once, serially, on every package-assisted setup that selects the Global scope, including setups that subsequently choose the VS Code user configuration; each invocation can wait for the full five-second timeout.  
**Outcome:** The add-server workflow is blocked before the global destination picker appears, adding avoidable latency of up to five seconds.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Package-assisted NPM, Pip, NuGet, and Docker additions generated the configuration first and then selected the install target; the old Copilot-global resource lookup was guarded to manual stdio/HTTP server types, so a package addition targeting VS Code user configuration made no discovery IPC call.  
**Changed behavior:** Package-assisted additions now call getSetupDestination before asking for package details, and selecting Global immediately awaits getConfigurationResource before presenting the Copilot Global versus VS Code picker.  
**Confidence:** 0.99 — The changed call order, prior package guard, IPC implementation, lack of caching, and five-second bound are all explicit in code and tests. Exact typical IPC duration is environment-dependent, which affects severity but not the mechanism or critical-path reachability.

**Causal diff evidence:** Added line 371 awaits \`\_copilotGlobalConfigurationService.getConfigurationResource()\` in the new pre-generation destination path. The added package branch at lines 556-568 calls that path before \`getAssistedConfig\`; the service performs \`ProxyChannel...load()\` against the main process or remote agent and wraps it in a 5000 ms timeout.

With Agent Host enabled, choosing Global for any package-assisted MCP install can leave the UI waiting before the next picker is shown; slow remote IPC or shell-environment startup can impose the entire five-second timeout even when the user only wants the VS Code user configuration.

**Evidence:** \`McpCopilotGlobalConfigurationService.getConfigurationResource\` awaits \`loadDiscoveryData\`; desktop and remote implementations cross IPC, and \`NativeMcpDiscoveryHelperService.load\` may await shell-environment resolution. Its test explicitly establishes a five-second timeout. The new entry-point test for choosing \`User Configuration (deprecated)\` changes the expected discovery lookups from 0 to 1, directly confirming that the diff adds this boundary even when Copilot Global is not selected.

**Suggested direction:** Present the global destination choices without awaiting discovery and resolve the Copilot resource only if Copilot Global is selected, or consume a cached/coalesced discovery result already populated by native MCP discovery. Preserve the current destination-first ordering for generation.
