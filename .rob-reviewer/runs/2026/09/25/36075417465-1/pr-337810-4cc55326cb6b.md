- Critical path: The welcome page reads Marketplace/source configuration, chooses the original Overview, and never constructs the Discover page. The lazy marketplace query service/provider is not dereferenced, so catalog work is off the critical path and absent.
- Scaling input: Configuration filtering is O(S) in registered marketplace sources; production currently registers one source.
- Effective concurrency: No catalog request, IPC call, provider initialization, or network operation runs. Configuration checks are synchronous and serial.
- Cache behavior: Neither the renderer browse cache nor service continuation cache is populated. There is no cold request, and warm behavior is unchanged because Discover was never entered.
- Mechanism confidence: High: the welcome page uses getVisibleCustomizationMarketplaceSources, the public source requires visibility, and both desktop IPC and web services call the same gate before dereferencing lazy services.
- Magnitude uncertainty: Future source count is unknown, but the current production cardinality is one and no expensive work is reached.
- Expensive boundaries: none found
- Verdict: No regression. The changed default does not introduce startup/open-page network, IPC, or eager provider work while Marketplace is hidden.

### Scenario 2: Enable Marketplace and browse or search Discover, including pagination and multi-source priority merging

The boundary is required before available catalog results appear.

- Effective concurrency: CustomizationMarketplaceService uses Promise.all across active sources, so effective concurrency is S source requests per refill; production S=1. Pagination is sequential and no new limiter or burst behavior is introduced.
- Cache behavior: Queryless results use the existing renderer cache keyed by selected source. Combined continuations retain at most 32 entries for 30 minutes, with at most one bounded native page buffered per source; priority adds only an optional number to already-retained entries. Configuration changes clear renderer caches and invalidate in-flight work.
- Mechanism confidence: High: the full renderer-to-IPC/direct-service-to-REST call path, page caps, Promise.all concurrency, and continuation bounds are explicit.
- Magnitude uncertainty: Additional future sources and adapters may increase S, but the diff neither increases requests per source nor changes aggregate concurrency from the pre-diff merge.
- Expensive boundaries:

### Scenario 3: Render install state for catalog rows and react to Marketplace/source configuration changes

- Critical path: Each visible/result catalog item synchronously asks the install service for local state. A configuration toggle synchronously disposes/recreates the home surface only when visibility changes, clears disabled-source state, and notifies renderers.
- Scaling input: A normal page has 24 catalog items. The new visibility/source helper scans S sources per state check, currently S=1; existing plugin/MCP installation scans dominate and are unchanged.
- Effective concurrency: State checks are synchronous. Rendering handles the current bounded catalog collection; configuration toggles are serialized user actions.
- Cache behavior: Installed-skill/manual-setup maps are pruned when their source becomes unavailable; enabled listeners are disposed when Marketplace becomes hidden. No new retained cache or listener lifecycle is introduced.
- Mechanism confidence: High: getInstallState performs configuration/array/map checks only and reaches no IPC, filesystem, or network boundary.
- Magnitude uncertainty: Future source counts could increase the small local scan, but realistic current cardinality and the 24-item page bound make user-visible impact unsupported.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added local gate is bounded and configuration-triggered reconstruction is intentional, low-frequency, and cancels rather than adds expensive work.

### Scenario 4: Disable Marketplace or a source while a catalog request or explicit skill/plugin/MCP installation is in flight

- Critical path: The configuration event cancels the current catalog token and pending source-specific install token. Any already-started provider/import operation must observe cancellation before completing; no new operation is started by the toggle.
- Scaling input: Cleanup scales with currently pending catalog requests and explicit installations, not catalog size or history. Typical trigger cardinality is one request/install at the moment of a user setting toggle.
- Effective concurrency: Requests from active sources run concurrently as before. Install calls for the same resource are coalesced in pending maps; independent explicit installs can overlap as before. The new switch only cancels existing work.
- Cache behavior: Catalog requests are cancelled and renderer browse state is cleared. Installed-skill and manual-setup cache entries for unavailable sources are removed, while other legacy sources remain available when allowed; no stale resource is retained by the new gate.
- Mechanism confidence: High: configuration listeners dispose cancellation tokens and existing cleanup paths own temporary filesystem state.
- Magnitude uncertainty: Underlying cancellation latency depends on remote and filesystem services, but the diff reduces obsolete lifetime rather than increasing work.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentFinder/common/agentFinderRestProvider.ts:query and src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceInstallService.ts:installSkill</code>: Cancel an in-flight GitHub Feed REST request or repository acquisition for an explicit installation; cardinality: At most the already-running catalog request per active source and one coalesced operation per resource key; only explicit user installations reach repository acquisition.
    - Introduced by diff: false; previous behavior: Source disablement already cancelled these operations; the diff extends the same cleanup to the new Marketplace visibility switch.; critical-path effect: Cancellation shortens obsolete work and rejects the pending user operation; it does not add blocking work.
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceInstallService.ts:installSkill</code>: Validate/copy/move a selected skill package, with cleanup if cancellation occurs; cardinality: One file-tree copy/move sequence per explicit skill install, scaling with the selected package's files; pending operations are coalesced by resource key.
    - Introduced by diff: false; previous behavior: The same filesystem install and cancellation cleanup existed for source disablement; Marketplace visibility now invokes that existing lifecycle.; critical-path effect: This is on the explicit install critical path, not browse/startup. Hiding Marketplace requests cancellation and may trigger bounded cleanup of the same staging/target paths.
- Verdict: No regression. The change extends cleanup/cancellation ownership to the new gate without adding I/O, fan-out, or retained state.
