# Performance review: agentHost: Detect Codex writer locks before sending

[PR #337659](https://github.com/microsoft/vscode/pull/337659) at `33c779aae3f495fa584a6a8a3f43243bae56dbb7`

## Findings (1)

### 1. [medium] Hydrate the chat before awaiting native thread resume

**Finding ID:** `PERF-3A94DBA6DCBF`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:6105</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Codex child-process \`thread/resume\` IPC plus workspace filesystem/configuration work  
**Scaling:** One resume is added for each restored chat whose runtime has \`needsResume\`; fresh restore can initiate this for every active chat subscription, while repeated subscriptions after a successful resume take the warm fast path.  
**Outcome:** increased latency and a blocked chat-open/reconnect critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A chat subscription could return its existing snapshot/history without acquiring the Codex writer lock; restored threads were resumed by \`\_sendMessage\` when the user actually sent the next turn.  
**Changed behavior:** Opening or restoring an existing interactive Codex chat now waits for native writer-lock acquisition and full thread resume before the subscription snapshot is returned.  
**Confidence:** 0.97 — The awaited call path is explicit: \`AgentHostSessionHandler.provideChatSessionContent\` waits for the chat subscription to hydrate, the server waits for \`AgentService.subscribe\`, and the new line waits for provider preparation. Codex restored entries set \`needsResume: true\`; preparation reaches \`\_resumeSession\`, which performs filesystem/config discovery and \`thread/resume\`. Exact duration varies with app-server, workspace, and MCP configuration, so severity is medium rather than high.

**Causal diff evidence:** The added \`await this.\_chatInputService.prepareChat(resource)\` at RIGHT line 6105 inserts provider preparation before \`AgentService.subscribe\` can return the chat snapshot. \`prepareChat\` marks the chat checking and awaits Codex \`\_prepareChat\`, which calls \`\_ensureThreadConnection\`; restored Codex entries are created with \`needsResume: true\`, so this runs \`\_resumeSession\` and its \`thread/resume\` IPC before subscription hydration completes.

Opening a previously saved Codex conversation can leave the transcript/composer load blocked on child-process IPC and workspace/configuration work, even when the user only wants to read history. On fresh restore, several active chats can amplify reconnect latency and app-server load.

**Evidence:** \`AgentHostSessionHandler.provideChatSessionContent\` blocks at \`\_whenSubscriptionHydrated(chatSub)\`. The new subscribe await reaches \`CodexAgent.\_prepareChat\` -&gt; \`\_ensureThreadConnection\`. For restored sessions, \`\_createResumedSessionEntry\` sets \`needsResume: true\`; \`\_resumeSession\` refreshes session MCP discovery (reading each workspace \`.mcp.json\`), resolves launch/model/hook state, and sends \`thread/resume\` to the Codex child process. The prior send path already performed this resume in \`\_sendMessage\`, so this diff moves that work from first send onto chat-open hydration. Fresh reconnect/host restore processes active chat subscriptions in \`Promise.all\`, so the same boundary cost can occur once per restored chat, with only per-chat sequencing rather than a global resume limiter.

**Suggested direction:** Return/activate the chat subscription after publishing the synchronous \`checking\` input-block state, then run provider preparation off the transcript-hydration critical path while buffering or snapshotting its completion so sends remain blocked and no update is lost.
