### Scenario 1: First or visible-widget handoff from Agents/Open in Editor or a session protocol URL into an editor window

- Critical path: The main process routes/focuses the target window, sends vscode:openChatSession, and the renderer awaits openSession to reveal the Chat view and load the session before the requested UI is ready. The new controller adds one ResourceMap lookup and one linear scan over currently open chat widgets before the unchanged open path.
- Scaling input: One handoff event and one session URI per explicit user action; the added scan scales with live chat widgets/editor tabs, not session history. Session-history size affects the pre-existing load/parse path.
- Effective concurrency: Same-session handoffs are now coalesced by pendingOpens. Different-session handoffs can proceed concurrently, as they could before; the Chat view's loadSession cancellation token applies last-call-wins behavior.
- Cache behavior: openedSessions is cold on the first handoff. The chat model/session services may reuse a warm in-memory model/session; a cold local session reads persisted data and a cold remote session resolves provider content. Failed opens are deliberately not added to openedSessions and therefore retry.
- Mechanism confidence: High: the renderer call path, widget scan, per-key coalescing, local filesystem read, and remote provider resolution are directly visible in the implementation.
- Magnitude uncertainty: The number of open chat widgets and session-history size vary, but the added scan is over live widgets and does not multiply any expensive boundary.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/native/electron-main/nativeHostMainService.ts:306 and src/vs/code/electron-main/app.ts:1130</code>: Send vscode:openChatSession from the main process to the selected renderer window.; cardinality: One IPC message per explicit handoff/protocol invocation.
    - Introduced by diff: false; previous behavior: The same IPC message was sent before this PR.; critical-path effect: The renderer cannot begin revealing/loading the requested session until this message arrives.

### Scenario 2: Repeated handoff of a successfully opened session whose Chat view is currently hidden

- Critical path: After the existing main-to-renderer IPC, the controller scans live widgets and returns immediately when the same handed-off session is found in a hidden Chat view. Session reveal, model acquisition, rendering, filesystem reads, and provider resolution are kept off this path.
- Scaling input: One lookup per repeated explicit handoff; scan cost scales with live widgets. openedSessions membership scales with distinct successful handoffs during the editor-window lifetime.
- Effective concurrency: If no open is pending, the hidden repeat returns immediately. If an earlier open for the same URI is pending, repeated callers share that promise rather than starting another load.
- Cache behavior: openedSessions is a positive window-lifetime marker populated only after a successful open. There is no negative caching: missing/failed opens retry. The set has no per-entry eviction, but each entry is only a URI/string key from an explicit successful handoff, so the evidenced cardinality and retained resource are too small to establish a meaningful performance regression.
- Mechanism confidence: High: the suppression guard and window-lifetime ResourceSet are explicit in ChatSessionHandoffController.
- Magnitude uncertainty: A very long-lived window can accumulate stale URI markers, but growth requires distinct successful explicit handoffs and retains only URI metadata; no realistic high-cardinality or material memory impact is established.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/native/electron-main/nativeHostMainService.ts:306</code>: Deliver the repeated handoff to the renderer.; cardinality: One IPC per user invocation; unchanged by this PR.
    - Introduced by diff: false; previous behavior: The same IPC was sent and then always triggered openSession.; critical-path effect: The IPC occurs before suppression, but the renderer then completes without loading or revealing Chat.
- Verdict: No reportable regression. This scenario removes pre-existing UI/model work and expensive cold-load boundaries rather than adding them.

### Scenario 3: Concurrent handoffs for the same session

- Critical path: The first renderer event starts the normal openSession path; later same-key events await the promise stored in pendingOpens, so completion still depends on the single underlying session load.
- Scaling input: Cost is one underlying open per distinct session URI in the concurrent burst, rather than one per event. Aggregate work can still scale with distinct session keys, matching pre-diff event cardinality.
- Effective concurrency: Per-session concurrency is coalesced. pendingOpens entries are removed in finally on success or failure; distinct keys are not globally limited.
- Cache behavior: The pending map is an in-flight cache only and is cleared in finally. A successful open populates openedSessions; failures remain retryable. Lower session services also coalesce/cache same-resource provider resolution.
- Mechanism confidence: High: the pending map is keyed by ResourceMap URI identity and deletion is guaranteed by finally; the focused test confirms one attempt for concurrent same-session calls.
- Magnitude uncertainty: The frequency of duplicate user handoffs is unknown, but uncertainty only affects the size of the improvement, not regression risk.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/common/model/chatSessionStore.ts:635-674</code>: Potential cold local-session read for the one underlying same-session open.; cardinality: At most one controller-initiated load for concurrent events sharing the same URI; lower layers may also reuse an existing model.
    - Introduced by diff: false; previous behavior: Each concurrent IPC handler could call openSession independently; the PR reduces this cardinality.; critical-path effect: All coalesced callers await the same cold read when needed.
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/chatSessions/chatSessions.contribution.ts:1289-1328 and 1339-1386</code>: Potential provider-backed remote-session resolution, already coalesced at the session service and now also coalesced before view-opening work.; cardinality: One provider resolution per remote session key after service caching/coalescing; the new controller also prevents duplicate view open/load calls for that key.
    - Introduced by diff: false; previous behavior: Provider resolution already coalesced below, but duplicate renderer open/view work could still be initiated; this PR reduces that repeated work.; critical-path effect: The first cold resolution remains on the UI-open critical path; duplicate callers share it.
- Verdict: No reportable regression. Same-key concurrency and duplicate UI work are reduced; distinct-key concurrency is not increased relative to the prior handler.

**Summary:** Reviewed all three changed files and traced the handoff through Electron IPC, widget lookup/reveal, local persisted-session reads, and remote provider resolution. The PR adds only small per-event map/scan bookkeeping, suppresses repeated hidden-session loads, and coalesces concurrent same-session opens. No high-confidence diff-introduced performance regression was found.
