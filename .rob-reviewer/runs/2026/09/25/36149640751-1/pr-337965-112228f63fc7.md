## Findings (1)

### 1. [medium] Cache negative worktree-ownership lookups

**Finding ID:** `PERF-EEBF110D2F20`  
**Location:** <code>src/vs/platform/agentHost/node/chatContributions/worktreeAnnouncement/worktreeAnnouncementContribution.ts:59</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** filesystem stat calls, SQLite metadata reads, JSON parsing/validation, and array scans  
**Scaling:** For each non-owner peer chat, cost grows with every outgoing turn and every hydration/history-refresh event; each event performs one stat and one SQL query, while CPU/allocation also grows with the number of additional-worktree records in the session.  
**Outcome:** Repeated critical-path I/O increases prompt-dispatch latency and background history-refresh I/O.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Peer-chat outgoing turns did not execute this contribution or access additional-worktree metadata; peer-chat hydration also returned without storage I/O.  
**Changed behavior:** Every non-default outgoing turn first checks an in-memory positive-only memento, then performs a durable ownership lookup when it is false; misses do not change the memento and are retried indefinitely.  
**Confidence:** 0.99 — The added call is reached for every non-default outgoing turn until an announcement is emitted, and \`\_findOwnedWorktree\` is directly shown to call \`tryOpenDatabase\` plus \`getMetadata\`; the contribution dispatcher awaits it serially before \`agent.chats.sendMessage\`. For the common peer chat that does not own a newly-created additional worktree, the miss is never memoized, so this repeats deterministically. Exact disk latency varies by filesystem and SQLite contention, which affects severity but not the mechanism.

**Causal diff evidence:** Before the diff, non-default chats returned immediately from \`onHydrateTurns\` and this contribution had no \`onOutgoingTurn\`, so ordinary peer-chat sends performed no additional-worktree storage lookup. The added RIGHT line 59 now places that lookup on every non-default outgoing-turn path unless the positive announcement state was reached.

Sending messages in any ordinary peer chat now waits for a filesystem stat and SQLite metadata query before the prompt can reach the provider. Subscribed provider-history refreshes also repeat the lookup. On slower or contended storage this adds recurring send latency and unnecessary disk/SQLite activity even though ownership cannot appear after the chat has been created through this flow.

**Evidence:** \`onOutgoingTurn\` awaits \`\_findOwnedWorktree\` at the added line. That helper calls \`readSessionAdditionalWorktrees\`, which invokes \`ISessionDataService.tryOpenDatabase\` (an awaited filesystem \`stat\` even when the DB is already warm), executes \`SELECT value FROM session\_metadata WHERE key = ?\`, parses and validates the complete JSON array, then scans it. \`AgentHostChatContributions.outgoingTurn\` awaits contributions sequentially, and \`AgentSideEffects\` awaits that result immediately before provider dispatch. The same uncached helper is also reached from peer-chat hydration/history refresh. Only successful ownership plus metadata sets \`announcementEmittedKey\`; a non-owner leaves it false forever.

**Suggested direction:** Memoize the ownership resolution, including \`undefined\`, per chat (or load a session-level chat-to-worktree map once) and clear it with the existing chat/session contribution lifecycle. Association is persisted before chat creation in this PR, so a chat created through this path can safely retain the negative result; preserve an explicit invalidation path if any other flow can associate an already-live chat.
