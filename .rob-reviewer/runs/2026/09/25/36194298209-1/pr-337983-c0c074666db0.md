## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/platform/actionWidget/browser/actionList.ts:1641` (`LEFT`)  
**Blamed base line:** `src/vs/platform/actionWidget/browser/actionList.ts:1641`  
**Introducing path:** `src/vs/platform/actionWidget/browser/actionList.ts`  
**Introducing commit:** `4d3755c056420033d92f58157e53e1e5ef3115a7`  
**Mechanism family:** `eager-work`  
**Performance category:** `latency`  
**Confidence:** 0.98

**Mechanism:** Opening a collection eagerly constructed the first tab-through preview; for image entries this also initiated a file read of up to 20 MiB, and for GitHub entries it allocated/rendered the full rich-card DOM before the user requested details.

**Symptom:** Collection opening incurred unnecessary filesystem I/O, allocation, and layout work for the initially highlighted item, increasing open latency and resource use even when the user never viewed the preview.

**Fixed behavior:** Opening an ActionList now only focuses/highlights the initial row. Rich hover construction and any image file read are deferred until pointer intent or explicit keyboard navigation requests the details.

**Evidence:** In the base revision, ActionListWidget.focus() called \_showTabThroughPanelForFocusedItem() after focusing the first row. That helper immediately called \_showSubmenuForElement for a first item with tabThroughPanel, which invokes element.hover.content(). Chat dropdown image entries implement content() with createChatPillImagePreview, and that function immediately starts fileService.readFile with a 20 MiB limit; GitHub PR/issue content also builds a multi-element rich preview. The changed deletion at base line 1641 removes this work from popup opening, while the changed keyboard/pointer paths still reveal the panel on deliberate interaction.
