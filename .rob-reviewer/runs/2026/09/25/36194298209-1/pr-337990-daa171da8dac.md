## Performance regression fixes detected (3)

### 1. repeated-work

**Fix location:** `src/vs/editor/browser/services/editorWorkerService.ts:365` (`RIGHT`)  
**Blamed base line:** `src/vs/editor/browser/services/editorWorkerService.ts:361`  
**Introducing path:** `src/vs/editor/common/services/editorWorkerServiceImpl.ts`  
**Introducing commit:** `18101697a800782d6e5738c3264dd433e5ccb415`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.99

**Mechanism:** Each model-removal event synchronously rescanned the complete remaining model collection to decide whether an existing editor worker should stop.

**Symptom:** Closing a bulk-model surface can block the renderer event loop with quadratic model enumeration before disposal completes.

**Fixed behavior:** The changed listener debounces removals to one microtask callback and snapshots \_workerUseCount, reducing each synchronous removal burst to one getModels() scan while avoiding disposal when the worker was requested after the removal.

**Evidence:** In the base revision, every synchronous IModelService.onModelRemoved event invoked \_checkStopEmptyWorker(), whose first live-worker path calls \_modelService.getModels(). Bulk disposal emits once per model, so disposing N models while an editor worker exists performed N shrinking full-model scans (quadratic total model visits). The added regression test exercises 200 removals and establishes that the changed listener performs one scan for the nonempty burst and one when the final model is removed.

### 2. repeated-work

**Fix location:** `src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts:129` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts:129`  
**Introducing path:** `src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts`  
**Introducing commit:** `2cd36100c46f25aea9e41581fa975b7b3350dad7`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.97

**Mechanism:** Every unattached model removal rebuilt document/editor state by scanning the complete remaining model and editor collections, yielding quadratic aggregate work during bulk disposal.

**Symptom:** Closing views that release thousands of models can synchronously block the UI while document/editor state is repeatedly reconstructed.

**Fixed behavior:** The new removal fast path deletes an unattached model directly from the maintained document set and emits its delta without rebuilding model/editor state; attached models retain the full recomputation path.

**Evidence:** The base onModelRemoved handler called \_updateState for every removed model. \_updateState enumerates all remaining models, all code editors, computes set/map diffs, and resolves active-editor state before emitting the same per-document removal delta. Since IModelService fires synchronously for every disposal, removing N unattached synchronized models caused N shrinking full-state rebuilds. The changed test establishes zero getModels scans while retaining one immediate removal delta per model.

### 3. repeated-work

**Fix location:** `src/vs/workbench/contrib/editTelemetry/browser/helpers/vscodeObservableWorkspace.ts:32` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/editTelemetry/browser/helpers/vscodeObservableWorkspace.ts:29`  
**Introducing path:** `src/vs/workbench/contrib/editTelemetry/browser/vscodeObservableWorkspace.ts`  
**Introducing commit:** `c6f916e443c79259a99c040d8021e7ea470abe42`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.99

**Mechanism:** Every model-removal event synchronously triggered a full model-service scan and cached observable-array reconciliation, producing quadratic aggregate CPU and allocation churn during bulk disposal.

**Symptom:** Closing a multi-diff or other bulk-model view can stall the renderer and create avoidable allocation/GC pressure while edit-telemetry document state is repeatedly rebuilt.

**Fixed behavior:** The removal signal is now sourced from an Event.debounce with MicrotaskDelay, so all removals in one checkpoint invalidate and reconcile the observable model array once; the debounce emitter is tied to the workspace store for cleanup.

**Evidence:** In the base revision, observableSignalFromEvent invalidated the models derived value on every synchronous model-removal event. The eagerly subscribed recomputeInitiallyAndOnChange chain then called IModelService.getModels and reconciled mapObservableArrayCached for every removal. A burst removing N models therefore caused N shrinking collection scans/reconciliations. The added test disposes 200 models in one checkpoint and establishes one scan and one downstream document refresh after the change.

### Scenario 1: Closing a multi-diff or another surface that synchronously disposes hundreds to thousands of unattached text models

- Critical path: ModelService fires onModelRemoved synchronously for each disposal. The main-thread document state fast path and extension notification remain immediate; editor-worker emptiness checking and edit-telemetry workspace reconciliation are deferred to one microtask and therefore no longer repeat collection-wide work on the synchronous disposal path.
- Scaling input: The number N of models released in one JavaScript microtask checkpoint. Before the change, three consumers could repeatedly traverse shrinking model collections, giving quadratic aggregate model visits; after the change the main-thread fast path is O(1) per unattached model and the worker/edit-telemetry consumers scan once per burst.
- Effective concurrency: Disposals and main-thread deltas are serialized synchronously. The two changed Event.debounce listeners independently coalesce all removals in the current checkpoint into one callback each; no parallel work or unbounded queue is introduced.
- Cache behavior: No persistent cache is added. Main-thread state is incrementally updated from its authoritative Set; edit-telemetry's existing mapObservableArrayCached is reconciled once after the burst; worker state is guarded by a monotonic use generation. Cold and warm behavior differ only in whether an editor worker exists.
- Mechanism confidence: High: synchronous model-removal emission, the old full-collection call paths, the changed fast path/coalescers, and targeted scan-count tests directly establish cardinality.
- Magnitude uncertainty: Actual model counts vary by view and workload, but the tests establish burst sizes of 200 and the call graph establishes the former quadratic scaling independently of timing measurements.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts:\_onDelta</code>: Send IDocumentsAndEditorsDelta to the extension host for each removed synchronized document.; cardinality: One IPC message per removed synchronized model, so N messages for N models; no grouping is added, but this is the same effective cardinality as before because the old full-state recomputation emitted each removal delta synchronously.
    - Introduced by diff: false; previous behavior: The old onModelRemoved path recomputed all state and then emitted one removal delta for each model, producing the same IPC count plus N full model/editor scans.; critical-path effect: Each notification is initiated during the synchronous removal call; extension-host handling is across the RPC boundary, while the renderer-side call only enqueues/sends the delta.
  - IPC at <code>src/vs/editor/browser/services/editorWorkerService.ts:WorkerManager.\_checkStopEmptyWorker</code>: Dispose the editor web worker when the coalesced emptiness check finds no remaining models.; cardinality: At most one worker disposal for a burst, and zero when no worker exists or a post-removal worker request invalidates the check.
    - Introduced by diff: false; previous behavior: Every removal checked the full model collection; the first event observing an empty collection disposed the worker, while subsequent events became no-ops after the worker reference was cleared.; critical-path effect: Moved from every synchronous removal callback to one microtask after the burst; it is not added to an earlier critical path.
- Verdict: No regression. The diff removes repeated collection-wide work while preserving the pre-existing per-document extension-host notification count.

### Scenario 2: Removing the last model and immediately requesting a model-independent editor-worker operation in the same checkpoint

- Critical path: The worker request increments \_workerUseCount before the deferred removal callback runs. The callback observes that newer use and skips empty-workspace disposal, allowing the request to reuse the live worker instead of tearing it down and launching another.
- Scaling input: Frequency of remove-last-model/request-worker sequences; each sequence now avoids one teardown/recreation pair.
- Effective concurrency: Single-threaded event ordering: synchronous removal and request, followed by one queued microtask. Worker RPC remains asynchronous and is not burst-concurrent because of this change.
- Cache behavior: The live EditorWorkerClient is effectively reused as a warm resource. If no newer request occurs, the microtask emptiness check still disposes it; the existing idle timer remains a fallback.
- Mechanism confidence: High: the generation is captured by the debounce reducer, incremented synchronously in withWorker, and compared before cleanup; the regression test verifies same-client reuse.
- Magnitude uncertainty: Worker startup duration depends on platform and worker implementation, but the direction and boundary elimination are explicit.
- Expensive boundaries:
  - IPC at <code>src/vs/editor/browser/services/editorWorkerService.ts:WorkerManager.withWorker</code>: Invoke editor-worker computation through the existing worker client.; cardinality: One worker request per caller invocation; unchanged by the diff.
    - Introduced by diff: false; previous behavior: The synchronous empty-model check disposed the live worker before the immediate request, forcing withWorker to construct a replacement client.; critical-path effect: The computation remains on the request critical path, but the change can remove a worker restart from that path.
  - other expensive boundary at <code>src/vs/editor/browser/services/editorWorkerService.ts:WorkerManager</code>: Create or terminate the editor web worker.; cardinality: After the change, zero restart operations for the remove-then-request sequence; before the change there was one termination followed by one creation.
    - Introduced by diff: false; previous behavior: The last-model removal synchronously terminated the worker, so the following request recreated it.; critical-path effect: The changed generation guard avoids placing worker startup on the immediate computation path.
- Verdict: No regression. The delayed cleanup is generation-guarded and reduces worker lifecycle churn without extending retention beyond cases where the worker was just requested.

### Scenario 3: Removing a model still attached to a code editor, including active-editor teardown

- Critical path: The new removal handler deliberately falls back to \_updateState, which rescans models and editors so editor removal and active-editor transitions are computed before notifying the extension host.
- Scaling input: Number of attached code editors inspected by \_updateState; this path is unchanged and is not used for the realistic large burst of unattached models targeted by the PR.
- Effective concurrency: One synchronous full-state recomputation per attached-model removal, as before. Typical cardinality is bounded by visible/instantiated editors rather than all bulk-disposed unattached models.
- Cache behavior: The maintained current state is replaced by a freshly computed authoritative state on this fallback. No new cache, miss behavior, or invalidation policy is introduced.
- Mechanism confidence: High: the explicit isAttachedToEditor branch and existing \_updateState/\_onDelta flow establish unchanged behavior.
- Magnitude uncertainty: Editor counts and extension-host transport cost vary, but neither mechanism nor cardinality is increased by the change.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadDocumentsAndEditors.ts:\_onDelta</code>: Send a combined removed-document, removed-editor, and active-editor delta to the extension host.; cardinality: One message for the attached model removal; unchanged from the pre-diff recomputation path.
    - Introduced by diff: false; previous behavior: The same full-state recomputation generated and sent the combined delta.; critical-path effect: Initiated synchronously after state recomputation to preserve document/editor ordering.
- Verdict: No reportable performance regression; the expensive fallback is intentionally retained only where editor state also needs reconciliation.

The PR removes three independently verified repeated-scan regressions during bulk model disposal, preserves immediate extension-host notification cardinality, coalesces only collection reconciliation, and introduces no actionable performance regression.
