## Findings (2)

### 1. [medium] Keep draft CI polling off the global session path

**Finding ID:** `PERF-895FCC43F402`  
**Location:** <code>src/vs/sessions/contrib/github/browser/github.contribution.ts:278</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub HTTP check-runs requests and their response parsing/model updates  
**Scaling:** Cost is one immediate request plus one request per minute for every unique open draft PR head across all unarchived tracked sessions; different drafts start independently with no aggregate limiter.  
**Outcome:** excessive network I/O and background CPU, with startup request bursts and reduced GitHub API quota  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous guard returned for open drafts before acquiring or refreshing a CI model, so inactive draft sessions generated no check-runs traffic from this contribution.  
**Changed behavior:** The status autorun no longer rejects draft pull requests, so every open draft tracked by the global contribution now creates a CI model, refreshes it immediately, and starts its 60-second poll loop.  
**Confidence:** 0.99 — The changed guard, all-session ownership, exact REST endpoint, shared-key coalescing, and 60-second cadence are directly traced. Only the number of users with multiple unarchived draft PRs is uncertain, which limits severity rather than mechanism confidence.

**Causal diff evidence:** RIGHT line 278 removes \`prDetails.isDraft\` from the early-return condition, making draft PRs flow into the existing refresh/startPolling calls that were previously unreachable for them.

Opening VS Code with accumulated agent sessions containing draft PRs creates an immediate burst of GitHub requests and then continuous background traffic even if the user never opens a reference hover, increasing network/battery use and consuming API quota.

**Evidence:** GitHubPullRequestPollingContribution tracks every added unarchived session, including non-active sessions, and invokes this autorun for each referenced PR. The now-reachable lines 287-289 call refresh() and startPolling(); GitHubPullRequestCIModel.refresh issues GET /repos/{owner}/{repo}/commits/{sha}/check-runs, and its default polling interval is 60,000 ms. Models are shared by owner/repo/PR/head SHA, so duplicate session references coalesce, but each unique draft head retains its own poller.

**Suggested direction:** Do not keep draft CI warm for every tracked session. Preserve draft hover status by refreshing lazily when its pill/dropdown is actually shown, or restrict recurring draft polling to the active/visible session and dispose it when that visibility ends.

### 2. [medium] Bound Markdown work before building the 200-character preview

**Finding ID:** `PERF-4632AA3315AF`  
**Location:** <code>src/vs/sessions/contrib/github/browser/githubHover.ts:16</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** main-thread Markdown parsing/sanitization CPU plus transient token, HTML, normalized-string, and Unicode-array allocations  
**Scaling:** Work grows with the full body length and the number of focus/hover transitions, while useful output remains capped at 200 code points; repeated visits parse the same body again.  
**Outcome:** increased interaction latency, CPU/GC pressure, and possible dropped frames during list navigation  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Collection rows had no rich detail construction on focus, and standalone hovers inserted the body as text without invoking the Markdown parser/sanitizer. The PR therefore adds full Markdown parsing to this interaction path.  
**Changed behavior:** Rich issue/PR hovers now run renderAsPlaintext, whitespace normalization, and Unicode-array truncation over the complete body each time hover content is constructed, even though only 200 code points are displayed.  
**Confidence:** 0.95 — The synchronous focus call path and parser/sanitizer implementation are directly traced, and the absence of caching is explicit. Exact milliseconds vary with body shape and hardware, so severity is medium.

**Causal diff evidence:** RIGHT line 16 introduces full-body \`renderAsPlaintext(...)\` before line 17 applies the 200-code-point limit; the new dropdown hover factories make this helper run synchronously on focused-row changes.

Keyboarding or hovering through a collection containing long issue templates, logs, or PR descriptions can block the UI thread on each row transition, causing delayed focus updates and dropped frames; revisiting rows repeats the same parse and allocations.

**Evidence:** renderAsPlaintext calls marked.parse and sanitizeRenderedMarkdown over up to 100,000 input characters before returning. ActionList.onFocus synchronously calls \_showHoverForElement, whose \_showSubmenuForElement invokes the entry's hover.content factory; buildSessionIssueSections/buildSessionPullRequestSections create a fresh hover each time, and revisiting a row repeats the work with no memoization.

**Suggested direction:** Produce the preview with a bounded-input/streaming plain-text extraction that stops after enough visible text, or memoize a bounded normalized preview per immutable body and compute it outside the focus handler, so row navigation only builds the small DOM card.
