<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, serialization-allocation

### Scenario 1: Create or resume a Copilot agent session and apply its effective sandbox policy

- Critical path: Session creation/resume completes first, then script-safety and sandbox-policy RPC updates must complete before the session wrapper is returned. The diff adds synchronous normalization of the selected OS filesystem arrays before the existing sandbox update RPC.
- Scaling input: Total strings and characters in the four filesystem policy arrays for the executing OS, once per launched session; no cross-platform arrays are traversed.
- Effective concurrency: One finalization sequence per launched session; separate sessions can launch concurrently as before. The diff adds no limiter, queue, or additional asynchronous operation.
- Cache behavior: Root/session configuration is read from the in-memory configuration service. There is no normalized-policy cache, so each launch maps the configured path arrays once; cold and warm launch behavior differ only in surrounding pre-existing runtime/session state.
- Mechanism confidence: High: the added map/replace work and unchanged single RPC are directly visible in the changed helper and launcher call path.
- Magnitude uncertainty: Filesystem policy lists may vary, but realistic configuration cardinality is bounded and the added linear string mapping is small relative to the existing critical-path runtime RPC.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:592 applySandboxConfig</code>: session.rpc.options.update forwards the computed sandboxConfig to the Copilot runtime; cardinality: One sandbox-config update per successful create/resume finalization; fallback resume attempts still finalize only the successful session
    - Introduced by diff: false; previous behavior: The same one options.update call was made from \_finalizeSession using a policy built directly from root settings plus session overrides; critical-path effect: The RPC is on the launch critical path, but its count and payload fields are unchanged; local normalization runs immediately before it
- Verdict: No finding. The diff adds bounded local O(P) normalization but no new expensive boundary or changed boundary cardinality.

### Scenario 2: Start an SDK-backed agent turn or react to a sandbox/permission configuration change

- Critical path: \_prepareSdkTurn waits for the sandbox options update before starting the agent loop. Configuration-change updates and per-turn updates are serialized by \_sandboxConfigSequencer. The changed helper normalizes paths before the existing SDK policy construction and RPC.
- Scaling input: Filesystem rule count P per policy update and active-session count for configuration broadcasts; effective work is O(P) per already-existing update, not per individual tool or path access.
- Effective concurrency: Per session, sandbox updates are serialized by \_sandboxConfigSequencer; different sessions remain independent. The diff does not increase concurrency or remove coalescing.
- Cache behavior: Configuration reads are warm in-memory reads. Sandbox policy updates themselves are not value-deduplicated in this code before or after the diff; normalization is likewise recomputed per update. Shell-init script payload/path caching remains unchanged.
- Mechanism confidence: High for the call path and O(P) allocation; low magnitude risk because there is no boundary amplification and updates are serialized.
- Magnitude uncertainty: Large centrally managed path lists could add allocation, but no evidence establishes policy sizes high enough for this single pass to create user-visible latency.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:4725 \_updateEffectiveSandboxConfig -&gt; applySandboxConfig</code>: Update the runtime's sandboxConfig through session.rpc.options.update; cardinality: One update per turn preparation and one per relevant configuration synchronization, with an occasional additional existing update when registering a new shell-init-script path
    - Introduced by diff: false; previous behavior: The same updates and sequencing existed; policy construction merged root settings and session overrides without separator normalization; critical-path effect: Per-turn update blocks turn start; configuration updates run through the same sequencer. The diff only adds one local normalization pass before each existing RPC.
- Verdict: No finding. Added normalization is bounded and does not materially amplify the existing per-turn IPC or its concurrency.

### Scenario 3: Run a command through the Agent Host custom terminal sandbox

- Critical path: The shell tool checks sandbox settings, wraps the command, may regenerate and write the sandbox settings file, then executes the wrapped command in the terminal/subprocess. getSandboxSetting now resolves and normalizes the selected filesystem arrays each time it is queried.
- Scaling input: Number P and character length of configured filesystem paths, multiplied by the constant number of sandbox-setting queries in enablement, wrapping, and policy generation; command count determines repetition over time.
- Effective concurrency: A tool invocation awaits wrapCommand and then terminal execution. Per-shell behavior and command concurrency are unchanged; no new concurrent subprocess or file operation is added.
- Cache behavior: TerminalSandboxEngine caches the generated config path and invalidates it on root/session setting or root changes; Windows command-line changes already force refresh. The new accessor does not cache normalized arrays and can map them for multiple setting reads during one command, while the underlying root/session values remain warm. Effective repetition is a small constant number of O(P) passes.
- Mechanism confidence: High that repeated mapping occurs; low confidence that its bounded cost is material enough to qualify as a performance bug.
- Magnitude uncertainty: Very large filesystem policies would increase CPU/allocation, especially on Windows, but typical user/managed lists are modest and existing path resolution, file generation, MXC work, and command execution dominate. No realistic threshold or evidence supports user-visible regression.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/sandbox/common/terminalSandboxEngine.ts:398 getSandboxConfigPath / \_createSandboxConfig</code>: Create or overwrite the generated sandbox-settings JSON when the cached configuration requires refresh; cardinality: At most one settings-file write for a wrap refresh; Windows refreshes for changed command lines and other platforms refresh on the existing command/config/root conditions
    - Introduced by diff: false; previous behavior: The engine generated the same policy file under the same refresh rules, reading unnormalized Agent Host settings; critical-path effect: Existing file generation is on command wrapping's critical path; separator normalization occurs before the existing generation but does not add writes
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotShellTools.ts:488 handler -&gt; executeCommandInShell</code>: Execute the wrapped user command through the existing terminal/sandbox runtime path; cardinality: One command execution per shell-tool invocation, with an optional second wrap only for the existing unsandboxed-confirmation retry path
    - Introduced by diff: false; previous behavior: The same wrapped command was executed with the same invocation cardinality; critical-path effect: Command execution dominates the workflow and is unchanged by the diff
  - IPC at <code>src/vs/platform/agentHost/node/copilot/agentHostSandboxEngine.ts:111-117 Windows MXC helper methods</code>: Obtain/build Windows MXC filesystem/environment/payload data through the existing sandbox helper service; cardinality: Existing per-config-generation helper calls; the diff changes only the configuration value accessor feeding the engine
    - Introduced by diff: false; previous behavior: Windows policy generation called the same helper methods; critical-path effect: These existing helper calls participate in Windows policy generation; normalization neither adds nor multiplies them
- Verdict: No finding. Although the shared accessor repeats path-array mapping across setting reads, it adds no boundary calls and the bounded local work is not sufficiently material for an actionable regression.

**Summary:** Reviewed all 11 changed files and complete diff pages. Traced session launch/resume, per-turn/config policy updates, and custom terminal command execution through IPC, filesystem, MXC helper, and subprocess boundaries. The change adds linear in-memory path normalization, sometimes repeated by the terminal setting accessor, but does not change expensive-boundary cardinality, critical-path concurrency, cache invalidation, or retained lifetime enough to establish a reportable performance regression.
