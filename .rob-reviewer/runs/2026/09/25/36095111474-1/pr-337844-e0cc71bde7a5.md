## Findings (1)

### 1. [medium] Cache user MCP membership instead of refetching it every turn

**Finding ID:** `PERF-4BEA72608931`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:6826</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Copilot CLI subprocess IPC requests and response serialization  
**Scaling:** One extra config-list round trip per affected session seed, per later-turn loaded event, and again for lifecycle-race retries; aggregate work scales with active sessions and turns even though the underlying user configuration is process-global.  
**Outcome:** Excessive IPC, increased MCP inventory publication latency, and reduced CLI subprocess throughput under multiple active sessions or long conversations  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each seed or session.mcp\_servers\_loaded invalidation performed one session-scoped rpc.mcp.list call and then applied the result; it did not make the additional client-level config RPC.  
**Changed behavior:** After each session-scoped rpc.mcp.list response containing any server without a source, the refresh now awaits a separate client-level rpc.mcp.config.list call before publishing inventory.  
**Confidence:** 0.97 — The changed await, its production callback, the per-turn trigger, and the stdio subprocess boundary are all directly traced in repository code. Exact RPC duration and number of concurrent active sessions are uncertain, which limits severity rather than mechanism confidence.

**Causal diff evidence:** Added lines 6825-6827 conditionally await \_getUserMcpServerNames for every source-less inventory response, and added lines 5650-5653 wire that callback to a fresh client.rpc.mcp.config.list call.

With SDK versions that omit source metadata, every session initialization and every later turn that re-emits session.mcp\_servers\_loaded incurs another subprocess round trip, delaying MCP inventory/tab refresh and adding contention on the Copilot CLI stdio channel used by other session operations.

**Evidence:** \_refreshMcpServersFromRpc is called once when a session subscribes and on every session.mcp\_servers\_loaded event; the adjacent comment explicitly says that event is re-emitted on later turns. Production wires getUserMcpServerNames to client.rpc.mcp.config.list, and CopilotClient is connected through RuntimeConnection.forStdio. The list is client-level configuration, but there is no cache or in-flight coalescing; concurrent refreshes are only made stale after both RPCs complete.

**Suggested direction:** Keep a client-generation-scoped, coalesced cache of user MCP server names shared by sessions, and invalidate it only when MCP configuration actually changes or the Copilot client restarts; inventory refreshes should reuse the cached/in-flight result rather than issuing a per-turn RPC.
