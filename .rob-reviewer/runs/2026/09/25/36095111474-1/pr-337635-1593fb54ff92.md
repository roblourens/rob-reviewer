### Scenario 1: Live HydraFusion phase messages and tool lifecycle events appear in the phase child chat while a phase runs

- Critical path: Each provisional SDK event is synchronously classified by CopilotSessionWrapper, routed by CopilotAgentSession, reduced into child-chat state, and published to subscribed AHP clients before event handling returns. There is no awaited subprocess, filesystem, database, or remote call on this path; transport publication is the only changed expensive boundary.
- Scaling input: Cost scales linearly with provisional assistant-message chunks plus tool start/complete events across the bounded set of Fusion phases, multiplied by the number of connected clients subscribed to the affected chat. There is no collection-wide work nested inside each event.
- Effective concurrency: SDK events and synchronous emitters are processed serially on the Node event loop. Each envelope is synchronously offered once to each relevant connected client; the diff adds no Promise.all fan-out or concurrent remote work.
- Cache behavior: No cache lookup is involved. Message-id deduplication is turn-local; committed chunks for one model call are coalesced until the last chunk, then provisional copies are skipped. State and deduplication sets are cleared at turn reset/completion.
- Mechanism confidence: High: the event-to-state-to-transport call path and one-action-per-event cardinality are explicit in the changed handler and state publication code.
- Magnitude uncertainty: The exact number and size of runtime chunks and connected clients varies, but Fusion phases are bounded and the changed work is the product behavior itself rather than accidental per-item duplication.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:5502 renderMessage, transitively protocolServerHandler.ts:\_broadcastAction</code>: Publish one chat action envelope to each connected client subscribed to the phase chat; cardinality: One markdown action per non-empty provisional assistant-message chunk and the existing start/ready/complete actions per surfaced tool, per relevant connected client
    - Introduced by diff: true; previous behavior: Provisional assistant messages were dropped and provisional tool starts were generally held until approval/client handling or committed replay, so losing-phase conversation produced no corresponding live client envelopes.; critical-path effect: Synchronous state reduction and transport send invocation happen before the SDK event callback returns, but no response is awaited.
- Verdict: No reportable regression. The added linear publication and retained child-chat content are necessary to show live phase work, are bounded by turn/phase output, and duplicate committed phase work is suppressed.

### Scenario 2: Winning Fusion phase committed replay and answer routing

- Critical path: Committed assistant-message chunks enter the existing SDK event path. Chunks are retained only until the model-call boundary; phase-work chunks already shown provisionally perform in-memory accounting/deduplication, while the no-tool final call emits the root answer as before.
- Scaling input: Temporary work is linear in chunks in the current model call. The shown-message-id set scales with provisional messages in the current turn and is cleared when the turn resets or ends.
- Effective concurrency: Model calls within a phase are assumed sequential and events are handled serially. There is no new concurrent boundary fan-out.
- Cache behavior: The turn-local shown-message-id set acts as a positive deduplication cache. It has explicit reset/completion invalidation; incomplete chunk groups are also cleared on those lifecycle boundaries. No negative cache or cross-turn state is retained.
- Mechanism confidence: High: buffering, deduplication, and lifecycle clears are explicit in CopilotFusionMessageChunks and \_clearProvisionalFusionState.
- Magnitude uncertainty: Malformed or abandoned chunk streams could retain several event objects until turn cleanup, but the lifetime is bounded to the active turn and realistic cardinality is the number of incomplete model calls.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:5530 renderCommittedFusionMessage</code>: Publish the winning final answer to the root chat and any committed phase content not already shown; cardinality: One envelope per final-answer chunk; committed phase-work chunks emit no duplicate envelope when their message ids were shown provisionally
    - Introduced by diff: false; previous behavior: The committed final answer was already rendered to the root response; this diff changes classification/coalescing and suppresses duplicates for newly shown provisional phase work.; critical-path effect: State reduction and transport send invocation are synchronous but do not await a remote response.
- Verdict: No reportable regression. Buffering is bounded to a model call/turn, committed duplicate rendering is avoided, and no new expensive boundary is added to replayed phase work.

### Scenario 3: Restoring persisted chats containing chunked Fusion phase work

- Critical path: Session restore first pages the SDK event log, then mapSessionEvents scans the already materialized event array to classify complete Fusion model calls before constructing root and phase turns. Existing edit/shell restoration follows afterward.
- Scaling input: CPU and temporary references scale linearly with total persisted events; the new chunk map and phase-work set scale only with committed Fusion assistant messages in the loaded history. Effective cardinality is message chunks after provisional events are excluded.
- Effective concurrency: Event-log pages are fetched sequentially and mapping is synchronous. Existing stored shell-output restoration is sequential by chat/turn; the diff does not change its concurrency.
- Cache behavior: No persistent cache is added. The chunk classifier is function-local and discarded after one restore; pending groups are cleared at top-level user-message boundaries to prevent cross-turn correlation.
- Mechanism confidence: High: mapSessionEvents already had the relevant passes; the diff adds constant-time classification inside an existing pass and no new I/O call.
- Magnitude uncertainty: Persisted histories can be large, but the added scan work is constant per event and temporary memory contains references rather than copies of message content.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_computeMappedEvents</code>: Read persisted SDK event-log pages of up to 1000 events; cardinality: One pre-existing RPC per history page, independent of the new Fusion classification
    - Introduced by diff: false; previous behavior: The same complete event log was paged before the diff.; critical-path effect: History reconstruction waits for all pages before mapping.
  - database at <code>src/vs/platform/agentHost/node/copilot/mapSessionEvents.ts and copilotAgentSession.ts:\_restoreStoredShellOutputs</code>: Load stored edit data during mapSessionEvents and stored shell output after mapping; cardinality: Existing grouped/edit-tool and completed-shell cardinality; unchanged by the added Fusion message classification
    - Introduced by diff: false; previous behavior: The same edit and shell restoration ran before the diff.; critical-path effect: These existing reads remain on chat restoration's critical path.
  - IPC at <code>src/vs/platform/agentHost/node/agentHostStateManager.ts history loading path</code>: Publish reconstructed turns/chat state to clients after restore; cardinality: Existing bulk history actions; routing more Fusion chunks into phase turns changes payload placement/content but does not add per-event publication during mapping
    - Introduced by diff: false; previous behavior: Restored turns were already published; some earlier chunks were classified into the root rather than their phase chat.; critical-path effect: Occurs after reconstruction and is required to display restored history.
- Verdict: No reportable regression. Restore remains O(number of events), adds no I/O or concurrency burst, and the temporary maps/sets are released after mapping.
