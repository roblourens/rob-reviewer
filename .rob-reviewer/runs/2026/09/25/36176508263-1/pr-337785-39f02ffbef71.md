# Performance review: chat: Add continuous customization discovery paging

[PR #337785](https://github.com/microsoft/vscode/pull/337785) at `39f02ffbef71ff3d8d9fc7caa315c572240788ee`

## Findings (1)

### 1. [medium] Bound automatic continuation across the whole search

**Finding ID:** `PERF-68C5FCCE62DD`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationDiscoveryPage.ts:1095</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** sequential marketplace IPC calls, HTTPS requests, response bytes, and accumulated catalog objects  
**Scaling:** Cost grows with the number of remote catalog pages before enough locally matching rows fill the viewport, or with the entire result depth when no matching type exists; each scheduled invocation permits another batch of up to 8 pages, with no search-wide cap.  
**Outcome:** excessive network I/O and prolonged search loading  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The same filtered search stopped automatically after at most 8 pages and rendered a \`Load More\` button, so further network requests required explicit user action. The PR removes that fallback and automatically requests page 9 and subsequent batches.  
**Changed behavior:** Underfilled or near-bottom search results now automatically schedule another continuation batch after each render; because the eight-page counter is local to each \`loadCatalog\` call, automatic scheduling repeatedly resets the counter and keeps fetching until a matching list fills the viewport or the catalog is exhausted.  
**Confidence:** 0.98 — The added scheduler call, \`layout()\` call after every request completion, local eight-page loop, test expecting an automatic ninth request, and marketplace implementation's IPC/HTTPS query path establish the mechanism directly. Exact catalog depth and network latency vary, which affects severity rather than causality.

**Causal diff evidence:** The added \`this.continuationScheduler.schedule()\` at \`aiCustomizationDiscoveryPage.ts:1095\` runs from \`layout()\` after every completed render while the list is underfilled. Each scheduled \`loadCatalog(true)\` resets the local \`pageCount\` loop and can issue another \`maxFilteredCatalogPagesPerLoad\` (8) marketplace queries. The updated test explicitly proves the behavior crosses the former bound by expecting request 9 without a click.

A search such as \`&#64;type:plugin mail\` with sparse plugin matches can silently walk the entire remote result set, keeping Discover busy and generating many sequential IPC/HTTPS requests even though the user did not request more pages. On a large or slow catalog this causes prolonged background loading, excess bandwidth/server traffic, and increasing CPU/allocation as all pages are accumulated and re-filtered.

**Evidence:** \`loadCatalog\` invokes \`marketplaceService.query\` sequentially up to 8 times for filtered plugin searches where no single server media type exists. Each marketplace query crosses shared-process IPC on desktop and \`AgentFinderRestProvider.query\` performs a cancellable HTTPS request (potentially more while skipping unsupported pages). \`render()\` calls \`layout()\`, which reaches the added scheduler line and launches another 8-query batch when filtered rows still do not fill the viewport. \`catalogPage.items\` also accumulates every fetched page, so network, allocation, copying, and filtering all grow with remote result depth.

**Suggested direction:** Keep a continuation budget across scheduler invocations for the current query/source (rather than resetting it per \`loadCatalog\` call), and require explicit user action or another bounded trigger after that budget is exhausted. Reset the budget only when the query/source changes; preserve cancellation and cursor ordering.
