**Relevant issue families:** boundary-fanout, cleanup-lifecycle, concurrency-burst, serialization-allocation

### Scenario 1: User connects from the Agents UI to a configured direct SSH host without ProxyJump.

- Critical path: The renderer resolves the alias, stages the configuration, and waits for the main-process connection. Existing \`ssh -G\` resolution, ssh2 network handshake, remote platform probes, CLI installation check, endpoint discovery, and relay setup remain on the critical path; the new proxy transport returns immediately without spawning anything.
- Scaling input: One logical host connection. Repeated clicks/retry requests for the same normalized address are coalesced by \`RemoteAgentHostService.\_pendingConnects\`; active connections are keyed and reused.
- Effective concurrency: At most one in-flight dial per normalized address through the browser service. Different hosts can connect independently, as before.
- Cache behavior: Resolved SSH config is not cached and \`ssh -G\` runs for each fresh connect/reconnect, unchanged by the diff. The active main-process \`\_connections\` map reuses an established SSH client; relay-only reconnects reuse that client.
- Mechanism confidence: High: the new guard requires both \`sshConfigHost\` and \`proxyJump\`, so direct configurations do not call \`cp.spawn\`.
- Magnitude uncertainty: Remote bootstrap duration varies by target and whether the CLI is already installed, but the diff adds no work on this path.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostActions.ts:connectToConfiguredSSHHost</code>: Renderer-to-main calls to resolve SSH configuration and establish the connection.; cardinality: One resolve request and one staged connection request per coalesced user connect.
    - Introduced by diff: false; previous behavior: The same IPC sequence existed before the diff.; critical-path effect: Both must complete before the UI receives a usable connection.
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:resolveSSHConfig</code>: Run \`ssh -G &lt;alias&gt;\` to resolve effective OpenSSH configuration.; cardinality: One process per fresh configured-host resolution; no cache, unchanged.
    - Introduced by diff: false; previous behavior: The same one-per-resolution subprocess ran before the diff.; critical-path effect: Configuration resolution blocks dialing.
  - network at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:connect/\_connectSSH</code>: ssh2 connects directly to the target and performs existing remote exec/relay setup.; cardinality: One SSH transport per fresh logical host connection, followed by a bounded sequence of existing remote commands on that transport.
    - Introduced by diff: false; previous behavior: Direct hosts used the same ssh2 transport and bootstrap sequence.; critical-path effect: Handshake and bootstrap must complete before the host is usable.
- Verdict: No performance regression: direct-host execution and boundary cardinality are unchanged apart from carrying one optional string.

### Scenario 2: User establishes a fresh Agent Host connection to a target whose resolved SSH config contains one ProxyJump.

- Critical path: After the existing \`ssh -G\` resolution and auth-attempt preparation, the main process starts one native OpenSSH \`ssh -W\` helper. Its spawn and jump-host/target forwarding are on the handshake critical path, and the existing ssh2 handshake plus remote bootstrap run over the helper's stdio.
- Scaling input: One helper and one forwarded transport per fresh, effectively deduplicated host connection, not per authentication attempt, endpoint, message, or remote command.
- Effective concurrency: Same-address connect requests are coalesced before reaching the factory. Connections to distinct configured hosts can each own one helper concurrently, matching independent user sessions.
- Cache behavior: There is no transport cache across fully closed SSH sessions. While connected, the main \`\_connections\` map retains and reuses the single SSH client/helper; reconnecting only the WebSocket relay does not spawn another helper. Stderr retention is capped at 4096 characters and keeps only the tail.
- Mechanism confidence: High: the changed guard, single \`cp.spawn\`, assignment to \`ConnectConfig.sock\`, same-address coalescing, and active-connection reuse directly establish cardinality and lifetime.
- Magnitude uncertainty: OpenSSH startup and extra-hop latency depend on host configuration and network topology. This is intentional, restricted to ProxyJump-configured hosts, and replaces a failed direct dial rather than slowing a previously successful supported path.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:resolveSSHConfig</code>: Run \`ssh -G &lt;target alias&gt;\` to obtain the resolved target, identity, and ProxyJump settings.; cardinality: One subprocess per fresh configured-host resolution.
    - Introduced by diff: false; previous behavior: The same resolution subprocess ran, but its ProxyJump value was discarded.; critical-path effect: Must finish before the ProxyJump transport can be constructed.
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:\_createProxyTransport</code>: Start native OpenSSH with \`BatchMode=yes -W target:port -- jump\` and use its stdin/stdout as ssh2's socket.; cardinality: Exactly one long-lived helper per fresh coalesced SSH session with a supported single-hop ProxyJump.
    - Introduced by diff: true; previous behavior: No helper was started; ssh2 attempted a direct target connection, so ProxyJump-only targets failed instead of establishing a session.; critical-path effect: The process must spawn and establish forwarding before ssh2 can complete its handshake; it remains the session transport afterward.
  - network at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:\_createProxyTransport/\_connectSSH</code>: Open the jump-host SSH connection and forward one byte stream to the resolved target; ssh2 then authenticates to the target over that stream.; cardinality: One jump connection and one forwarded target stream per fresh logical session.
    - Introduced by diff: true; previous behavior: The target was dialed directly and the supported ProxyJump-only scenario could not progress.; critical-path effect: Adds the required network hop to make progress for hosts that are not directly reachable.
  - network at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:connect</code>: Run the existing target-side platform probes, CLI check/install, endpoint discovery, liveness filtering, and relay setup over the established SSH client.; cardinality: The same bounded bootstrap sequence per fresh session; endpoint checks scale with discovered endpoint count as before.
    - Introduced by diff: false; previous behavior: The same operations followed successful direct SSH handshakes; ProxyJump-only hosts previously never reached them.; critical-path effect: Existing bootstrap remains on the connection critical path after the tunnel succeeds.
- Verdict: No reportable regression. The added subprocess and network hop are necessary to enable the requested scenario, remain one-per-session, and are not multiplied by auth attempts, endpoint count, or protocol messages.

### Scenario 3: Automatic or user-initiated reconnect and teardown of a ProxyJump-backed Agent Host.

- Critical path: Every reconnect first performs the pre-existing \`ssh -G\`. If the main service still owns the SSH client, \`connect(..., replaceRelay=true)\` replaces only the relay and reuses the existing proxy helper. If the SSH session has closed, a fresh coalesced dial creates one new helper. Teardown destroys streams immediately; process-tree termination is fire-and-forget and off the reconnect/UI critical path.
- Scaling input: One active helper per live SSH session and at most one in-flight reconnect per normalized address. Failed fresh handshakes are bounded by the existing 30-second handshake deadline (or interactive timeout while a prompt is open).
- Effective concurrency: The browser service joins duplicate reconnect requests through \`\_pendingConnects\`; retries for one address are sequential. Different addresses may reconnect concurrently and each can own one helper.
- Cache behavior: The active connection map is the warm-session cache: relay reconnection preserves the SSH client and proxy helper. A cold reconnect resolves config again and creates a fresh helper. Diagnostic stderr remains capped; no history accumulates across sessions.
- Mechanism confidence: High for normal connect, retry, and disposal paths: coalescing and connection reuse are explicit, and helper disposal is idempotent and registered on socket/client failure and close.
- Magnitude uncertainty: OS process-tree termination cost varies by platform, but it is once per still-running helper and off the critical path. Parent shutdown behavior outside normal connection disposal was not directly exercised in repository tests, though normal close/error ownership is explicit.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:reconnect/resolveSSHConfig</code>: Run \`ssh -G\` during reconnect configuration resolution.; cardinality: One per reconnect invocation that reaches the main service; duplicate same-address dials are coalesced at the browser layer.
    - Introduced by diff: false; previous behavior: Reconnect already resolved SSH config with one subprocess.; critical-path effect: Blocks deciding whether to reuse or establish the connection, as before.
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:\_createProxyTransport</code>: Create a new \`ssh -W\` helper only when no active SSH connection exists.; cardinality: Zero for warm relay-only reconnect; one for a cold/fresh reconnect attempt.
    - Introduced by diff: true; previous behavior: Cold reconnect attempted direct ssh2 networking and warm relay reconnect reused the existing direct SSH client.; critical-path effect: Cold reconnect waits for helper spawn and forwarding; warm relay reconnect does not.
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:\_createProxyTransport dispose</code>: Terminate the owned OpenSSH helper process tree when its ssh2 client closes or connection setup fails.; cardinality: At most one kill operation for each still-running owned helper due to the \`disposed\` guard; none when the helper has already exited.
    - Introduced by diff: true; previous behavior: There was no native proxy helper requiring process cleanup.; critical-path effect: Stream destruction is synchronous, while \`killTree\` is intentionally not awaited and therefore does not block connection close or retry progress.
- Verdict: No performance finding: warm reconnect avoids repeated helper creation, cold retries are coalesced and bounded, and helper lifetime plus diagnostic memory are explicitly capped.

**Summary:** Completed the performance pass over all six changed files and all diff pages. Traced initial direct connections, fresh ProxyJump sessions, reconnect reuse/retry behavior, subprocess/network cardinality, stderr retention, and helper cleanup. The only new expensive work is one required OpenSSH forwarding helper per supported ProxyJump session plus bounded asynchronous cleanup; no actionable diff-introduced performance regression was found.
