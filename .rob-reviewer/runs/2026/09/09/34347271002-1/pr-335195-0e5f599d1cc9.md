<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** eager-work, repeated-work, synchronous-ui-work

### Scenario 1: Open or restore an existing local or remote Agent Host chat session in editor chat or the Agents window, showing the newly visible disabled harness picker.

- Critical path: Menu context expressions are evaluated, then the toolbar creates one DelegationSessionPickerActionItem for the live chat input; construction scans registered session contributions and rendering replaces the picker's small label subtree. This is on the chat-input render path, but the work is bounded and required to display the harness.
- Scaling input: Scales with the number of simultaneously live chat input widgets and registered chat-session contribution types. Effective cardinality is one picker per live input and one linear scan of the small provider registry per picker construction.
- Effective concurrency: Synchronous toolbar construction on the UI thread; no queue, parallelism, IPC, or asynchronous fan-out.
- Cache behavior: No cache or cold/warm boundary is involved. Provider metadata is read from the in-memory ChatSessionsService registry; known providers use hard-coded metadata.
- Mechanism confidence: High confidence from the menu condition, action-view-item factory, constructor, contribution scan, and render call paths.
- Magnitude uncertainty: The maximum number of concurrently retained chat widgets and third-party session providers is not explicitly bounded, but normal cardinality is small and each widget needs its own visible action item.
- Expensive boundaries: none found
- Verdict: The diff intentionally adds a visible affordance and therefore a small amount of per-widget object/listener/DOM work, but it does not eagerly initialize a heavyweight model or cross an expensive boundary. The bounded cost is not a reportable regression.

### Scenario 2: Register, unregister, enable, disable, or update sign-in availability for a chat-session provider while an Agent Host picker is rendered.

- Critical path: ChatSessionsService fires onDidChangeAvailability after provider lifecycle changes. Each live SessionTypePickerActionItem already rebuilds its in-memory provider item list; the diff additionally rerenders its label so newly arrived display metadata is shown. The synchronous label reset is on the availability-event path, not an input, scroll, frame, or request path.
- Scaling input: Effective work is O(L × P), where L is the number of live picker instances and P is the registered provider count; each event is coalesced at the service level for extension-point availability evaluation, while individual programmatic registrations fire once.
- Effective concurrency: Event delivery and DOM refresh are synchronous and serialized on the UI thread. Provider registrations do not create per-provider asynchronous work in the changed listener.
- Cache behavior: The registry is in memory. No new cache is introduced or bypassed, and warm/cold behavior is equivalent apart from the required metadata refresh after registration.
- Mechanism confidence: High confidence from all availability fire sites, listener ownership via disposables, and the bounded renderLabel implementation.
- Magnitude uncertainty: Extensions could contribute more provider types or emit repeated sign-in changes, but availability changes are lifecycle/configuration events rather than high-frequency UI events and the rendered label contains only an icon and optional text node.
- Expensive boundaries: none found
- Verdict: The added rerender performs small bounded DOM allocation only when provider availability changes. It neither forces geometry reads/layout nor adds unbounded repeated work, so no finding is warranted.

### Scenario 3: Attempt to activate delegation from an existing Agent Host session by mouse, keyboard, command, or overflow action.

- Critical path: The changed action precondition disables execution for Agent Host sessions and unsupported sources; the picker also rejects show when disabled. Only context-key evaluation and in-memory state checks occur before activation is blocked.
- Scaling input: Constant work per activation attempt; no collection fan-out.
- Effective concurrency: Fully synchronous with no spawned or queued work.
- Cache behavior: No caches are read or changed.
- Mechanism confidence: High confidence from the action precondition and picker enablement call path.
- Magnitude uncertainty: None material for performance; the path is constant-time.
- Expensive boundaries: none found
- Verdict: The diff blocks rather than adds expensive work on this path, with no performance regression or independently evidenced shipped-regression fix.

**Summary:** Reviewed the complete six-file diff and traced toolbar construction, picker rendering, provider availability events, inherited tooltip updates, listener disposal, and activation guards. The PR adds only bounded in-memory scans and small DOM-label refreshes; no actionable performance issue or concrete regression fix was found.
