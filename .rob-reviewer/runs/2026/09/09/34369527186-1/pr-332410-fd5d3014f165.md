# Performance review: agentHost: centralize session and chat catalog metadata

[PR #332410](https://github.com/microsoft/vscode/pull/332410) at `fd5d3014f165531587976426e03479c6653599af`

## Findings (1)

### 1. [medium] Defer catalog reconciliation until startup has settled

**Finding ID:** `PERF-2B9EE03C2771`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:821</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** filesystem operations and SQLite reads/writes across per-session databases and the central catalog  
**Scaling:** On the first run with this catalog verification version, the scheduled pass marks every catalog row dirty and immediately processes up to 50 registered sessions, opening up to four session databases concurrently; remaining rows are processed by later bounded passes.  
**Outcome:** increased startup and first-interaction latency from competing disk I/O and database work  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change there was no catalog reconciliation pass scheduled from the constructor, and existing maintenance in this constructor used \_runWhenStartupSettled so it could not overlap host startup or the first session listing.  
**Changed behavior:** The constructor now schedules reconciliation on a fixed 1-second timer independently of the startup-settled barrier. On a fresh version marker, the pass dirties the whole catalog and reprojects the first 50 sessions.  
**Confidence:** 0.98 — The scheduling delay, initial all-dirty behavior, 50-row batch, four-way concurrency, per-dirty-row database open, and existence/purpose of the startup-settled barrier are all explicit in changed code and tests. Only the exact latency magnitude varies with session count and storage speed.

**Causal diff evidence:** The added call \`this.\_catalogReconciliationService.schedule()\` at line 821 starts a background pass after the service's default 1,000 ms delay, while the adjacent \`\_runWhenStartupSettled\` mechanism explicitly waits for both host startup completion and the first served listing.

After upgrading to this schema/version, users with a sizable session history can have up to 50 session databases statted/opened/read and catalog rows verified or rewritten beginning one second after Agent Host construction, while startup or the first session list/load is still in progress. On slower or busy disks this can delay the first useful interaction.

**Evidence:** \`AgentHostCatalogReconciliationService\` defaults to a 1-second background delay, batch size 50, and concurrency 4. Its first pass calls \`\_ensureInitialPayloadDirtyMark()\`, which marks all payloads dirty when \`agentHost.catalogReconciliation.verificationVersion\` is absent or changed, then \`\_runBatch\` invokes per-session reconciliation. The reconciliation test \`opens and re-projects dirty rows once...\` confirms one session-database open per selected dirty row. \`AgentService.\_startupSettled\` documents that deferred maintenance waits for host startup and the first listing specifically to avoid startup competition, but this new schedule bypasses it.

**Suggested direction:** Queue the initial reconciliation through \`\_runWhenStartupSettled\` (or otherwise gate \`start\`/\`schedule\` on the same barrier), then begin its periodic schedule after that deferred pass so repair remains automatic without competing with startup.

### Scenario 4: Active chat turns and list-visible metadata changes

- Critical path: Turn processing updates in-memory summaries immediately; list-visible changes enqueue catalog persistence in the background rather than blocking action dispatch.

- Effective concurrency: Summary emission is debounced by 100 ms. Catalog synchronization is serialized per session and collapses an in-flight burst to one trailing write; different sessions may proceed independently.
- Cache behavior: Activity-only and transient status-only changes are excluded. Payload hashes/receipts let unchanged synchronized projections avoid unnecessary central replacement, while dirty markers preserve failed work for repair.
- Mechanism confidence: High: changed-field filtering, debounce, per-key sequencing, and trailing-write coalescing are explicit and covered by tests.
- Magnitude uncertainty: A long turn can generate separated changes and therefore more than one sync, but payloads and nested collections are bounded and high-frequency activity is filtered.
