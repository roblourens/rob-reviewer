**Relevant issue families:** repeated-work, synchronous-ui-work, boundary-fanout, cleanup-lifecycle

### Scenario 1: Agents window restoration and opening a code, text-diff, or multi-diff editor

- Critical path: After restoration, the contribution synchronously reads the two word-wrap observables and applies options to currently visible panes; opening or changing a visible pane also runs the layout application before the editor is fully settled. Code-editor no-op updates stop in EditorConfiguration.applyUpdate before recomputation, while multi-diff layout options have an explicit equality guard.
- Scaling input: Distinct visible editor panes V and currently bound multi-diff templates R; normal restoration performs O(V) pane inspection and option application, with multi-diff propagation limited to R.
- Effective concurrency: Synchronous and sequential over the deduplicated visible editor panes. Multi-diff content remains virtualized; only bound/rendered diff templates observe the option override.
- Cache behavior: Configuration values are held by observables. Repeated unchanged code-editor options are deduplicated by EditorConfiguration, and unchanged multi-diff layout triples are deduplicated by \_updateDiffLayoutOptions. No external cache or cache miss is involved.
- Mechanism confidence: High: constructor autoruns and editor-service listeners, option deduplication, and multi-diff virtualization were traced directly.
- Magnitude uncertainty: The number of visible groups varies, but is normally small; the changed work scales with visible panes and rendered multi-diff templates rather than all open editors or all changed files.
- Expensive boundaries: none found
- Verdict: No reportable regression. The new propagation is required for the feature, remains bounded to visible/rendered editors, and suppresses unchanged expensive editor recomputation.

### Scenario 2: Switching active editors or changing the visible editor set in the Agents window

- Critical path: Editor-service active/visible events synchronously call applyLayout, which scans the deduplicated visible panes and invokes option updates. An active-editor switch may produce both events, but repeated code-editor updates are no-ops after raw-option comparison and multi-diff updates are explicitly guarded.
- Scaling input: Visible panes V and editor-switch frequency; effective expensive work is generally one newly visible pane, while the remaining O(V) checks are small in-memory operations.
- Effective concurrency: No parallel fan-out; one synchronous loop per event over visible panes. Duplicate notifications are handled serially.
- Cache behavior: Warm panes already carrying the requested override avoid code-editor recomputation and multi-diff observable invalidation. A newly visible pane receives one effective option change.
- Mechanism confidence: High: editor event firing, contribution listeners, and option equality behavior were inspected.
- Magnitude uncertainty: Exact event duplication and visible group count depend on layout, but neither introduces unbounded work or work proportional to all workspace files.
- Expensive boundaries: none found
- Verdict: No reportable regression. Although the diff adds a second visible-pane pass for code-editor wrapping, unchanged updates are suppressed before layout and realistic V is bounded by visible groups.

### Scenario 3: User invokes Word Wrap for a code editor or diff/multi-diff editor

- Critical path: The action awaits the configuration update; the Agents configuration service writes the selected setting and reloads configuration, then reactive listeners update visible editors. Transient per-model state cleanup follows the awaited update and can request one additional empty diff-editor option refresh.
- Scaling input: One command invocation, visible panes V, rendered multi-diff templates R, and cached workspace folders F during configuration reload.
- Effective concurrency: Exactly one setting update per invocation. Configuration targets are processed through Promises.settled, but this application-scoped setting resolves to one effective user target; editor propagation is synchronous and sequential after the configuration event.
- Cache behavior: The settings model is reloaded after writing; editor observables then deliver the new value. Multi-diff templates are virtualized, and no-op guards prevent redundant widget invalidation.
- Mechanism confidence: High: the action-to-service-to-ConfigurationEditing call path and awaited ordering were traced directly.
- Magnitude uncertainty: Configuration reload cost varies with filesystem latency and workspace-folder count, but the operation is explicitly user-triggered and occurs once per toggle rather than on typing, scrolling, rendering, or startup.
- Expensive boundaries:
  - filesystem at <code>src/vs/sessions/services/configuration/browser/configurationService.ts:207 writeConfigurationValue</code>: Write the user settings resource through ConfigurationEditing, then reload user/workspace/folder configuration models.; cardinality: One settings write per actual toggle, followed by one configuration reload; cached folder configurations may each be read once during reload.
    - Introduced by diff: true; previous behavior: These two Word Wrap commands did not exist, so this user-triggered configuration write/reload did not occur.; critical-path effect: The command awaits this work before clearing transient word-wrap state and completing.
- Verdict: No reportable regression. The single persisted configuration update is inherent to changing an experiment-controlled setting and is neither repeated per editor nor issued concurrently per diff item.

### Scenario 4: Active editor control changes inside a composite or multi-diff editor

- Critical path: The global word-wrap context-key tracker now listens to the active pane's onDidChangeControl event and synchronously resolves the focused/active code editor; it replaces listeners only when the active code-editor identity changes.
- Scaling input: Control changes over time; cost is O(1) per event with constant retained listener count.
- Effective concurrency: One event handler per active pane and one listener set per active code editor; DisposableStore.clear serially removes prior subscriptions.
- Cache behavior: The tracker compares the active editor by identity and returns immediately when unchanged. Pane and editor listeners are disposed on replacement and shutdown.
- Mechanism confidence: High: listener ownership, identity guard, and disposal paths were inspected.
- Magnitude uncertainty: Control-change frequency depends on navigation among multi-diff items, but each event performs bounded identity/context-key work and does not iterate the diff collection.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added listener is lifecycle-bounded and the hot path exits when the active editor did not change.
