# Performance review: chore: bump foundry-local-sdk to 2.x

[PR #335329](https://github.com/microsoft/vscode/pull/335329) at `7b1addd2da741949551bd89aa5fb898281f504aa`

## Findings (3)

### 1. [high] Keep first-use model downloads cancellable

**Finding ID:** `PERF-CBE1CB4F23D6`  
**Location:** <code>src/vs/platform/localTranscription/node/localTranscriptionService.ts:563</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** model-download network bytes, filesystem writes, and downloader CPU work  
**Scaling:** Waste grows with the bytes remaining in the uncached 0.6B model when the user cancels; an early cancellation can leave nearly the entire model transfer running.  
**Outcome:** continued bandwidth and disk/CPU consumption after dictation cancellation  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The service created an \`AbortController\`, wired \`\_modelPrepareCts\` cancellation to \`ac.abort()\`, and passed \`ac.signal\` to \`model.download\`, so \`cancel()\` or service disposal stopped the transfer.  
**Changed behavior:** The added SDK 2.x call invokes \`model.download\` with only the progress callback, while \`cancel()\` still merely cancels \`\_modelPrepareCts\`; that token is checked only after the download resolves and can no longer stop the active model transfer.  
**Confidence:** 0.99 — The before/after cancellation wiring and the normal user \`cancel()\` call path are explicit. The exact model byte size is not in-repo, but the mechanism applies to any nontrivial uncached model and the configured model is a 0.6B ASR model.

**Causal diff evidence:** RIGHT line 563 replaces the prior \`model.download(..., ac.signal)\` invocation and removes the cancellation subscription, directly severing the only abort path for this network operation.

If a user cancels first-use dictation while the model is downloading, cancellation returns but the utility process continues fetching and writing the large model until completion or network failure.

**Evidence:** \`cancel()\` at line 781 calls \`\_modelPrepareCts?.cancel()\`, and disposal does the same. The changed download await at line 563 has no signal or token; the next cancellation check is after it completes. The deleted hunk explicitly bridged this token to an AbortSignal passed into the same download call.

**Suggested direction:** Restore an abortable SDK 2.x download path and wire \`\_modelPrepareCts\` to it; if the new API offers no per-download signal, cancel by tearing down/recreating the downloader or utility worker and await that cleanup rather than leaving the transfer detached.

### 2. [medium] Package only the target platform's Foundry addons

**Finding ID:** `PERF-8EAC856EBC2F`  
**Location:** <code>build/gulpfile.vscode.ts:263</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** native-addon bytes in every product archive, installer, and installed tree  
**Scaling:** The excess grows with the SDK's prebuild target count: the package contains two addons for each of five supported targets, while one product can load only one target pair.  
**Outcome:** larger product/update downloads, more installation I/O, and additional disk usage for every desktop user  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous filter excluded the SDK's entire prebuild tree; after the SDK upgrade the product needs two addons for its own runtime target, but no foreign-platform copies.  
**Changed behavior:** The added \`prebuilds/\*\*/foundry\_local\_node.node\` include uses an unrestricted target wildcard, and the adjacent preload include does the same, so \`packageTask(platform, arch, ...)\` retains both addons from every SDK prebuild directory instead of just the product's loadable target.  
**Confidence:** 0.98 — The glob semantics, five-target SDK layout documented and consumed by this diff, package-task arguments, and exact-target runtime gate are all explicit. Only the binary sizes—and therefore the magnitude, not the mechanism—are unknown.

**Causal diff evidence:** RIGHT line 263 newly re-includes \`\*\*/foundry-local-sdk/prebuilds/\*\*/foundry\_local\_node.node\`; the next added line identically includes every target's preload addon, whereas the deleted filter excluded all prebuilds.

Each packaged desktop build carries up to ten native addon binaries although its support gate can use only two. Every installation and update transfers and stores the other targets' binaries.

**Evidence:** \`packageTask\` has the concrete \`platform\` and \`arch\`, but calls \`getFoundryLocalExcludeFilter()\` without them. The new include at line 263 matches every directory under \`foundry-local-sdk/prebuilds/\*\*\`; \`SUPPORTED\_TARGETS\` lists five target pairs, and the renderer support check permits only the current \`${platform}-${arch}\` pair (with the existing macOS arm64 mapping nuance).

**Suggested direction:** Parameterize the filter with the package platform/arch and re-include only the two addon files for the single runtime target that build can load (mapping the universal macOS build to darwin-arm64).

### 3. [low] Leave bundled addons out of the runtime tarball

**Finding ID:** `PERF-CBBC07BE99AE`  
**Location:** <code>build/dictation-runtime/package.ts:132</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** duplicate \`.node\` addon bytes downloaded, extracted, and retained in the per-user runtime cache  
**Scaling:** Every cold runtime cache downloads two duplicate addon binaries once per SDK runtime version; cost scales with their compressed/uncompressed sizes and version churn.  
**Outcome:** extra first-dictation latency, network transfer, extraction work, and cache disk usage  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous product excluded its sole addon and the runtime tarball supplied the addon actually loaded from the cache, so that transfer was required.  
**Changed behavior:** The product now deliberately bundles both SDK addons and configures \`libraryPath\` only for shared libraries, but \`requiredSdkNativeFileNames\` newly forces both \`.node\` files into the CDN tarball and runtime validation requires them in the cache as well.  
**Confidence:** 0.96 — The diff explicitly documents and implements package-loaded addons plus a shared-library override, and the tarball/cold-cache path is direct. Only the addon sizes, hence the severity, are uncertain.

**Causal diff evidence:** RIGHT line 132 newly lists both packaged addon names as required SDK files for the staging tree that is archived and uploaded by \`buildOne\`.

On the first dictation after each runtime-version change, users must download and extract cached copies of both addons even though the SDK loads the packaged copies.

**Evidence:** The new gulp filter keeps \`foundry\_local\_node.node\` and \`foundry\_local\_preload.node\` in the product. \`LocalTranscriptionService\` then calls \`configureNativeLoader({ libraryPath })\` for the shared-library cache, while line 132 requires those same addons in \`buildOne\`'s tarball and \`requiredRuntimeFileNames\` requires them after download.

**Suggested direction:** Build and validate the CDN payload from only the shared libraries used through \`libraryPath\`; omit the two \`.node\` files from staging and from runtime cache completeness checks.

### Scenario 3: Cancel dictation while the first model download is running

- Critical path: The cancel RPC awaits session disposal and resets UI/session state; resource cleanup should abort the in-flight model network operation even though that operation is no longer on the user's post-cancel critical path.

- Effective concurrency: Only one model preparation promise runs per service/model, but cancellation no longer terminates it; repeated same-model starts reuse the detached promise rather than adding more transfers.
- Cache behavior: Only cold model caches trigger the issue. A warm cache skips \`model.download\`; a partially/completely downloaded cache changes subsequent SDK behavior but does not bound the current detached transfer.
- Mechanism confidence: Very high: both the deleted abort wiring and current cancel/token call path are explicit, with the next token check only after download completion.
- Magnitude uncertainty: Exact artifact size and how often users cancel during first-use setup are unknown; remaining-transfer cost depends on cancel timing.
- Expensive boundaries:
