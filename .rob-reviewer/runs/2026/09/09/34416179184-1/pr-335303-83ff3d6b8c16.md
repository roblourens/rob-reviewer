# Performance review: sessions: add Dev Container workspace menu option

[PR #335303](https://github.com/microsoft/vscode/pull/335303) at `83ff3d6b8c1627eb1f6ddc8063c7d3dc399ad5e6`

## Findings (2)

### 1. [medium] Coalesce availability-driven picker refreshes

**Finding ID:** `PERF-1F725D25464F`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts:1896</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** ActionList objects, popup DOM nodes, event listeners, and synchronous layout work  
**Scaling:** Every local recent whose availability resolves true independently invokes showPicker(true); with N configured recent folders resolving while the picker remains open, the entire up-to-20-row popup is torn down and rebuilt N times in quick succession.  
**Outcome:** repeated synchronous popup reconstruction and layout, causing picker jank  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, opening the workspace picker constructed and laid out the popup once; no asynchronous per-row availability completion could force additional popup recreations.  
**Changed behavior:** Each successful availability promise now immediately force-reopens the visible picker instead of batching results or updating the affected list row.  
**Confidence:** 0.99 — The per-promise callback, visibility guard, force-reopen path, and synchronous ActionList/DOM/layout implementations are directly visible. The exact frame cost varies, but N successful results deterministically cause N full popup rebuilds.

**Causal diff evidence:** RIGHT lines 1895-1897 newly call showPicker(true, ...) independently from each availability promise's then callback.

Users with several Dev Container projects in recent workspaces can incur a burst of full list allocations, DOM teardown/recreation, focus work, and layout just after opening the menu, producing visible jank and unnecessary CPU/GC pressure.

**Evidence:** Line 1896 calls showPicker(true) from every successful promise completion. showPicker sees an already-visible picker and calls \_hidePicker before \_showFlatPicker/\_showTabbedPicker. The flat path creates a new ActionList and ActionWidgetService.\_renderWidget calls layout and focus; the tabbed path creates a new ActionList and reads offsetHeight during layout. The platform already exposes ActionWidgetService.updateItems and TabbedActionListWidget.refreshActiveList for in-place refresh, but this path reconstructs the popup once per completion.

**Suggested direction:** Aggregate or debounce availability completions and refresh the visible list once, preferably using updateItems/refreshActiveList (or patching the resolved row) rather than hiding and recreating the popup.

### 2. [medium] Cache or lazily validate Dev Container availability

**Finding ID:** `PERF-9D986219B162`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts:1470</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem existence checks and shared-process IPC calls  
**Scaling:** Each picker open starts one availability request for every visible local recent workspace (up to 20 after the service combines 10 session recents and 10 VS Code recents); each request performs two fileService.exists operations, and configured folders also issue an isDockerAvailable IPC call. The loop starts them without a limiter, and the cache is cleared on every fresh open.  
**Outcome:** excessive filesystem and IPC activity whenever the workspace picker is opened  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, opening the workspace picker only built the recent-workspace list; Dev Container availability was checked once for the workspace when a draft was created, not for every recent folder.  
**Changed behavior:** The added call inside the recent-workspace loop probes Dev Container availability for every local row, and showPicker clears the probe cache whenever the popup is freshly opened. Selecting a row then still creates a draft whose existing \_resolveDevContainerAvailability path probes the selected workspace again.  
**Confidence:** 0.98 — The changed loop, hard list caps, cache reset, provider delegation, and exact two-stat/IPC implementation are directly traced. Magnitude varies with the number and storage location of local recents, but the new boundary cardinality and repeated-open trigger are certain.

**Causal diff evidence:** RIGHT line 1470 newly invokes \_isDevContainerWorkspaceAvailable from inside the recent-workspace loop; RIGHT lines 624-626 clear the cache at each fresh picker opening, making the fan-out recur.

Opening the picker with a populated local history now launches up to 40 concurrent filesystem stats plus IPC roundtrips; slow disks or file-scheme network folders can generate an I/O burst on a routine UI interaction, and the selected folder is immediately re-statted during draft creation.

**Evidence:** \_buildItems iterates the merged recentWorkspaces and line 1470 calls \_isDevContainerWorkspaceAvailable for each local row. That helper calls provider.isDevContainerWorkspaceAvailable, which delegates to IDevContainerAgentHostService.isAvailable; isDevContainerWorkspaceAvailable in devContainerAgentHostConnector.contribution.ts awaits two fileService.exists calls and then mainService.isDockerAvailable. SessionsRecentWorkspacesService caps each of its own and VS Code lists at 10 but returns their deduplicated combination, while showPicker clears \_devContainerAvailability on every fresh open. LocalAgentHostSessionsProvider.createNewSession separately retains the pre-existing per-selected-workspace availability check.

**Suggested direction:** Keep availability results across picker opens and invalidate them from bounded provider/configuration/file-change signals, or defer the check to the row/submenu the user interacts with. Also share/coalesce the selected workspace's result with draft creation so the required final validation does not duplicate the same stats.
