### Scenario 1: Open the Plugins page in the customizations modal

- Critical path: The installed/available shell renders synchronously; the marketplace snapshot request is asynchronous and only gates population of Available results, not initial page display. The diff removes the Featured section from both the initial and post-fetch render paths.
- Scaling input: Installed and remote plugin counts plus the deduplicated marketplace plugin result across configured marketplaces. The Available list remains virtualized; the removed Featured work was capped at three rendered entries but also performed an extra full marketplace filter/sort pass.
- Effective concurrency: One widget snapshot request is admitted by the uninitialized/loading state guard. Configured marketplace references are fetched concurrently with Promise.all in the service; repeated home renders do not start another snapshot request.
- Cache behavior: The widget snapshot changes from uninitialized to loading to loaded/failed and is reused for the widget lifetime. GitHub marketplace sources use a TTL cache; cold sources may perform HTTP or clone-backed reads, while warm sources return cached entries. None of these cache rules changed.
- Mechanism confidence: High: the visibility guard, snapshot state machine, service fan-out, and removed render call are directly traced.
- Magnitude uncertainty: Marketplace count and cold-source latency vary by configuration, but request cardinality and scheduling are unchanged; rendering work is reduced.
- Expensive boundaries:
  - network/filesystem/subprocess at <code>src/vs/workbench/contrib/chat/common/plugins/pluginMarketplaceService.ts:459 fetchMarketplacePlugins</code>: Fetch each configured plugin marketplace through raw GitHub HTTP or ensure a cloned repository and read manifests.; cardinality: At most one snapshot fetch per visible widget initialization, fanning out once per deduplicated configured marketplace; warm GitHub entries can be served from the TTL cache.
    - Introduced by diff: false; previous behavior: The same snapshot request populated both Featured and Available; after the diff the same single request populates Available only.; critical-path effect: Off the initial-render critical path, but completion is required to populate Available marketplace cards.
- Verdict: No regression. The change removes duplicate card/filter/layout work and does not add, move, or multiply the marketplace boundary.

### Scenario 4: Render plugin catalog component screenshot fixtures

- Critical path: The new setVisible(true) synchronously starts refresh and an asynchronous snapshot fetch before fixture capture; the helper already waits fixed 100/600 ms plus 200 ms, so this in-memory fetch does not add an external wait. - Scaling input: Five helper variants, each rendered in light and dark themes, over a fixed marketplacePlugins fixture array.
- Effective concurrency: The home variants start one snapshot promise. Browse/search variants can also start their existing explicit query path, but both fake service calls resolve immediately from memory and are bounded per fixture.
- Cache behavior: Each fixture constructs a fresh widget and snapshot; there is no cross-fixture cache. The fake marketplace service returns the static array directly.
- Mechanism confidence: High: the injected IPluginMarketplaceService implementation is directly visible and its fetch method only returns marketplacePlugins.
- Magnitude uncertainty: Fixture runner scheduling can vary, but there is no subprocess, IPC, filesystem, database, or network operation behind the changed visibility call.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. The added work is test-only, bounded, in-memory, and fits inside pre-existing fixed screenshot waits.
