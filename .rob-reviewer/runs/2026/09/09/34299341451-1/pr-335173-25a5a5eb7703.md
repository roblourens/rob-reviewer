### Scenario 1: Typing-triggered NES prompt construction and inline-edit request

- Critical path: Context gathering and bounded prompt construction complete before the existing debounce and model request; path encoding runs synchronously while rendering the current file, up to five default recent documents, and up to 25 token-bounded history entries. The model network request remains the dominant critical-path boundary.
- Scaling input: One active path, at most the configured recent-document count (default 5), and token/count-bounded edit history (default maximum 25 entries); work scales with their path characters.
- Effective concurrency: Language and neighbor context may be gathered by existing provider logic, but prompt rendering is synchronous and one model fetch is issued after debounce for the surviving request; existing cancellation/debounce behavior is unchanged.
- Cache behavior: No path cache is added or invalidated. Existing request debounce/cancellation and any upstream edit caching remain unchanged; cold and warm prompt construction both perform bounded O(total rendered path characters) encoding.
- Mechanism confidence: High confidence that the added split/map/encode work is linear in bounded path text and does not add an expensive boundary or multiply model requests.
- Magnitude uncertainty: Exact path lengths and frequency of escapable characters vary, but prompt sections are count/token bounded and the whole request has a 120,000-character hard limit, so no realistic unbounded allocation or material latency mechanism is established.
- Expensive boundaries:
  - network at <code>extensions/copilot/src/extension/xtab/node/xtabProvider.ts:\_performFetch</code>: Send the constructed NES prompt and stream a model response.; cardinality: One request per non-cancelled inline-edit attempt; path metadata appears once for the active file and in bounded recent/history sections.

- Verdict: No reportable regression: percent encoding increases prompt bytes and local CPU only in proportion to bounded path metadata, while preserving request cardinality and budget enforcement.

### Scenario 2: Streaming custom diff-patch responses into inline edits

- Critical path: Each model-emitted patch is parsed sequentially from the existing response stream before its edit can be yielded. Active-document patches use identity comparison and skip decoding; cross-file patch targets perform one decode and URI construction before yield.
- Scaling input: The number of cross-file patches in one bounded model response and each target path's character length.
- Effective concurrency: A single async response stream is consumed serially with for-await; no new task fan-out, queue, subprocess, filesystem operation, or concurrent boundary is introduced.
- Cache behavior: No cache participates in patch target decoding, and the diff neither adds retained keys nor changes warm/cold behavior.
- Mechanism confidence: High confidence from the sequential handler loop that added work is O(cross-file patches × path length), with no added I/O or concurrency.
- Magnitude uncertainty: Model patch counts and path lengths vary, but they are bounded by one response and response token limits; decode cost is small relative to network streaming and existing patch/diff processing.
- Expensive boundaries:
  - network at <code>extensions/copilot/src/extension/xtab/node/xtabProvider.ts:\_performFetch and XtabPatchResponseHandler.handleResponse</code>: Consume the existing model SSE/line stream and convert emitted patches to edits.; cardinality: One network stream per request and one local path resolution per cross-file patch; active-file patches do not invoke the new decoder.

- Verdict: No reportable regression: decoding replaces the prior target-path resolution step with bounded local CPU/allocation and does not amplify boundary calls.

### Scenario 3: Next-cursor prediction and optional cross-file edit

- Critical path: After the initial edit stream, one existing cursor-prediction model request may run. For a different-file OnlyWithEdit result, the decoded target is resolved before one awaited document open; if valid, an existing retry obtains the edit. Jump-only results perform no document open.
- Scaling input: One model-returned target path per eligible cursor prediction; no collection multiplicity.
- Effective concurrency: Cursor prediction, target resolution, document open, and optional edit retry are sequential and cancellation/user-typing checks remain between stages; no burst or new parallelism is introduced.
- Cache behavior: Target-path decoding itself is uncached but constant-cardinality. A warm/open document can be served by the workspace service rather than cold filesystem loading, and the existing retry passes the original edit window so the edit cache can serve either location; cache keys and coalescing are not changed.
- Mechanism confidence: High confidence that resolveUniquePath executes once before the same pre-existing open/retry boundaries and cannot fan them out.
- Magnitude uncertainty: Cold document-open and model latency vary by provider and workspace, but their count and critical-path placement are unchanged; added decoding is one bounded path operation.
- Expensive boundaries:
  - network at <code>extensions/copilot/src/extension/xtab/node/xtabNextCursorPredictor.ts:predictNextCursorPosition</code>: Request one next-cursor prediction from the configured model endpoint.; cardinality: At most one cursor-prediction request for an eligible non-retry edit request.
    - Introduced by diff: false; previous behavior: The same cursor-prediction request occurred before path decoding was added.; critical-path effect: Awaited before a cursor jump or cursor-jump edit can be returned.
  - filesystem at <code>extensions/copilot/src/extension/xtab/node/xtabProvider.ts:handleCrossFilePrediction</code>: Open the predicted target text document for OnlyWithEdit mode.; cardinality: At most one open for one cross-file prediction; none for Jump mode.
    - Introduced by diff: false; previous behavior: The same URI target was opened once; the diff decodes the model token before constructing the equivalent URI.; critical-path effect: The open must finish before validating the line and constructing the synthetic retry request.
  - network at <code>extensions/copilot/src/extension/xtab/node/xtabProvider.ts:handleCrossFilePrediction -&gt; doGetNextEditWithSelection</code>: Obtain the optional edit at the predicted cross-file cursor location.; cardinality: At most one retry after one successful target-document open; existing edit caching may satisfy it.
    - Introduced by diff: false; previous behavior: The same optional retry existed and used the original edit window for cache reuse.; critical-path effect: Gates delivery of an OnlyWithEdit cross-file suggestion when not served from cache.
- Verdict: No reportable regression: the diff changes only target-token decoding and leaves the existing one-open/one-retry maximum, cancellation checks, and cache reuse intact.
