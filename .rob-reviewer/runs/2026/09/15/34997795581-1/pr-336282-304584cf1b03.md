- Cache behavior: Cold section observation starts a fetch. Warm active-source provider data is reused through cachedPromise; source changes invalidate it. The diff neither changes cache keys/lifetime nor bypasses coalescing.
- Mechanism confidence: High: setSection, sectionLoading, refetchSection, cachedPromise, and aria.status were directly traced.
- Magnitude uncertainty: Provider latency and item count vary by harness, but those costs are unchanged. The added fixed DOM update is bounded and occurs after the expensive boundary.

### Scenario 2: Delete, add, or update a workspace agent while the Agents section is open

- Critical path: The source change invalidates the provider cache, a RunOnceScheduler coalesces same-turn events, and the accepted refresh result updates the observable and rerenders the list. The added ARIA status call then updates a fixed live-region node synchronously.
- Scaling input: Number of same-turn source events after scheduler coalescing, number of previously observed sections for existing refresh work, and current-section item count for existing render work. The new status operation remains one per accepted current-section update and does not scale with item count.
- Effective concurrency: Same-turn source notifications are coalesced by a zero-delay RunOnceScheduler. Observed sections may refetch concurrently, while provider enumeration is promise-coalesced. Sequence checks discard stale results. The changed code starts no asynchronous work.
- Cache behavior: A source event invalidates cachedPromise once; the following observed-section refreshes share the replacement provider promise. Warm data remains cached until another source change. The announcement has no cache and uses two fixed global status containers, so it retains no growing state.
- Mechanism confidence: High: event coalescing, cache invalidation, stale-result checks, observable subscription ownership, and the fixed two-node aria.status implementation were directly inspected.
- Magnitude uncertainty: Change-event frequency depends on provider behavior, but even frequent accepted updates add only one short text replacement and visibility toggle each; there is no geometry read, collection copy, boundary fan-out, or unbounded retention.
- Expensive boundaries:
  - IPC/filesystem/provider boundary at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationItemsModel.ts:scheduleRefetchObserved/refetchObserved/refetchSection</code>: Refetch customization items from the active provider after its change event; existing hook/skill sections may perform their existing section-specific file work.; cardinality: At most one refetch batch per scheduler turn for source events. Each previously observed section is refreshed once; raw provider enumeration is shared by cachedPromise after invalidation. Only the currently bound section's accepted observable update invokes the changed announcement.
    - Introduced by diff: false; previous behavior: The same coalesced refreshes, filtering, count event, and list rerender occurred, but no ARIA status mutation was made for post-load model updates.; critical-path effect: The refresh boundary must complete before the updated count can be rendered or announced. The diff does not introduce or move the boundary; it adds a constant-size DOM status mutation after completion.
- Verdict: No reportable regression: the diff adds bounded O(1) synchronous DOM work after each coalesced accepted update, with no new expensive boundary, fan-out, or lifecycle growth.

**Summary:** Reviewed the complete two-file diff and traced initial loading, post-load source updates, section subscription replacement, provider/file boundaries, cache behavior, and concurrency. The only runtime change is one fixed-size ARIA live-region update per accepted current-section item update; it is suppressed during initial loading, uses two preallocated nodes, and introduces no actionable performance regression.
