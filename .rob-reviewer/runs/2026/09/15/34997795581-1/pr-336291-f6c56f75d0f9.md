## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/base/common/fuzzyScorer.ts:392` (`RIGHT`)  
**Blamed base line:** `src/vs/base/common/fuzzyScorer.ts:386`  
**Introducing path:** `src/vs/base/common/fuzzyScorer.ts`  
**Introducing commit:** `629d9f6dd7ab37d8dc41f1388a68d1f51bf92987`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.98

**Mechanism:** Every fuzzy-score cache lookup reconstructed and recursively hashed a nested object and mapped query-piece array. Sorting invokes the lookup twice per comparison, so this allocation and generic traversal repeated O(N log N) times on warm Quick Open sorts despite score-cache hits.

**Symptom:** Higher warm Quick Open input-to-render latency plus avoidable allocation/GC pressure for large workspaces; the controlled benchmark cited in the PR observed about a 19-21% latency reduction after removing the mechanism.

**Fixed behavior:** The added direct accumulator sequence at fuzzyScorer.ts:392 reproduces the same object/array hash recipe in sorted-key order while iterating existing query pieces, eliminating temporary nested objects, mapped arrays, property enumeration/sorting, and recursive dispatch from every cache-key computation.

**Evidence:** Base line 386 begins the old `hash({ ... })` cache-key construction, introduced by blame commit 629d9f6dd7ab37d8dc41f1388a68d1f51bf92987. `scoreItemFuzzy` computed this key before every cache lookup, and `compareItemsByFuzzyScore` calls it twice per comparator invocation; Quick Open applies the comparator across large candidate sets, so even cache hits repeatedly allocated a nested object, mapped query pieces into a new array/object set, sorted property keys in `objectHash`, and recursively dispatched `doHash`. The PR's controlled 11,082-path benchmark reports roughly 20% lower warm input-to-render-boundary latency, consistent with this directly traced CPU/allocation mechanism.
