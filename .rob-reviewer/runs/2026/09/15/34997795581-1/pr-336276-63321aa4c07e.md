### Scenario 1: Opening or switching to a local Windows/macOS session artifact with breadcrumbs enabled

- Critical path: BreadcrumbsModel construction synchronously calls LabelService.getUriHome, scans registered static/template home formatters, walks the resource's parent path, and renders the shortened breadcrumb before the editor breadcrumb model is ready.
- Scaling input: Number of registered static/template home formatters and resource path depth; effective cardinality is one scan per breadcrumb model initialization, not per breadcrumb element.
- Effective concurrency: Single synchronous UI-thread execution per breadcrumb model initialization or refresh; no queue, limiter, IPC, or parallel work is involved.
- Cache behavior: No result cache exists before or after the change; both versions scan the same registered formatter collections. Template regular expressions remain precompiled at formatter registration, and the diff only enables case-insensitive matching for local file templates.
- Mechanism confidence: High confidence in the synchronous call path and formatter cardinality from BreadcrumbsModel.\_initFilePathInfo through LabelService.findHomeFormatter; high confidence that no boundary operation was added.
- Magnitude uncertainty: The number of session-home formatter groups and editor switches varies, but realistic work remains an in-memory scan over registered homes plus path-depth traversal; the added case-insensitive comparisons do not establish a user-visible regression.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff preserves scan frequency and collection size, changing local-file comparisons to case-insensitive matching and preserving resource casing; any extra comparison cost is bounded string work required by the behavior.

### Scenario 2: Refreshing local agent-host resource-label homes after session or draft-session changes

- Critical path: The in-memory session-change handler synchronously enumerates known sessions and their already-loaded artifacts, derives home URIs, groups them, and updates formatter registrations before label-home refresh completes.
- Scaling input: Known sessions plus artifacts attached to copilotcli sessions, after grouping homes by parent; registration count remains one template/root formatter per effective parent group.
- Effective concurrency: One synchronous refresh per emitted session/draft-session event; artifacts are processed serially in the existing loops, and formatter registrations are deduplicated by parent-group keys.
- Cache behavior: Session and artifact data are already held in memory. Existing registration maps reuse formatters for unchanged group keys; the diff neither adds a cache nor invalidates one. Cold startup and warm updates retain the same session/artifact enumeration.
- Mechanism confidence: High confidence from the constructor event wiring and updateResourceLabelHomeFormatters implementation that the changed comparison and session-ID extraction remain in-memory and do not alter event frequency or fan-out.
- Magnitude uncertainty: Session and artifact counts vary, but the effective cardinality remains one URI containment check per artifact and one grouping pass per refresh. There is no evidence of large enough added case-folding cost to cause measurable latency.
- Expensive boundaries: none found
- Verdict: No reportable regression. The changed comparator performs case-insensitive local-path containment and the direct slice replaces relativePath without increasing refresh frequency, artifact cardinality, registration churn, or boundary calls.

### Scenario 3: Registering and using template-based resource label homes

- Critical path: Formatter registration compiles one anchored regular expression, while subsequent URI label/home requests execute that precompiled expression during synchronous label resolution.
- Scaling input: Compatible registered template formatter count and resource path length; effective work is one anchored regex match per compatible formatter per lookup.
- Effective concurrency: Registration and matching run synchronously on the caller thread; one regex execution occurs per compatible template formatter during each label lookup.
- Cache behavior: The compiled matcher remains cached in IHomeFormatterRegistration for its registration lifetime in both versions. The added ignore-case flag does not introduce recompilation per lookup or alter registration lifecycle.
- Mechanism confidence: High confidence from createTemplateFormatterRegistration and findHomeFormatter that compilation remains one-time and matching cardinality is unchanged.
- Magnitude uncertainty: Exact formatter counts and lookup frequency vary across workbench surfaces, but matching remains anchored and segment-bounded, with no catastrophic backtracking mechanism introduced.
- Expensive boundaries: none found
- Verdict: No reportable regression. Case-insensitive local-file matching changes regex semantics but does not add repeated compilation, unbounded retention, or new scaling work.
