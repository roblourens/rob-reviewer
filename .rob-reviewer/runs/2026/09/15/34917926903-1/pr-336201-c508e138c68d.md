### Scenario 1: Startup, focus, session-change, and manual rediscovery of cached dev tunnels

- Critical path: A silent status check must obtain authentication and complete one tunnel inventory request before reconciliation updates cached providers and statuses; automatic connection attempts are independent and may proceed concurrently from already-cached entries.
- Scaling input: Number of cached tunnel addresses; discovery remains one grouped inventory request, while background connection work scales by cached address with per-address coalescing and capped retries.
- Effective concurrency: Status-check invocations are not globally coalesced, but the diff does not change that behavior. Connection dials are coalesced per address; different cached addresses can connect concurrently under the existing service policy.
- Cache behavior: Successful discovery still authoritatively reconciles the persisted cache, including successful empty results. Failed discovery now preserves the warm cache and providers. There is no added cache key or unbounded retention; entries remain bounded by the user's persisted tunnel inventory and later successful reconciliation or explicit removal.
- Mechanism confidence: High confidence in the one-request discovery cardinality, cache-preservation behavior, per-address dial coalescing, and retry cap from the traced implementations.
- Magnitude uncertainty: Users may have multiple cached tunnels and prolonged network failures can retain bounded retry work, but typical cardinality and connection duration are unknown. The retained retries are coupled to the requested availability behavior and governed by existing caps.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/browserTunnelAgentHostService.ts:listTunnels and src/vs/sessions/contrib/providers/remoteAgentHost/browser/webTunnelAgentHostService.ts:listTunnels</code>: Enumerate the account's dev tunnels through the browser SDK or embedder discovery provider.; cardinality: One inventory request per status-check trigger, independent of tunnel count; successful results are reconciled in memory.
    - Introduced by diff: false; previous behavior: The same request occurred; failures were converted to an empty inventory in these browser implementations.; critical-path effect: Blocks completion of status reconciliation, but does not block already-staged cached-host connection attempts.
  - IPC at <code>src/vs/sessions/contrib/providers/remoteAgentHost/electron-browser/tunnelAgentHostServiceImpl.ts:listTunnels</code>: Delegate desktop tunnel enumeration to the shared process.; cardinality: One IPC request per authenticated status check; no request occurs when authentication is unavailable.

  - network at <code>src/vs/platform/agentHost/browser/remoteAgentHostServiceImpl.ts:\_reconcileConnections/\_createAndConnect via tunnel connection factories</code>: Create or restore a tunnel connection for cached entries when auto-connect is enabled.; cardinality: At most one in-flight dial per cached address; independent addresses can dial concurrently, and failed nonterminal dials use the existing capped 10-attempt exponential retry policy.

- Verdict: No reportable regression. Failure semantics change cache lifetime rather than adding successful-path boundary calls; retained connection attempts are bounded and are part of keeping cached hosts available.

### Scenario 2: Open the Connect via Dev Tunnel picker and delete a tunnel

- Critical path: Opening waits for authentication and one inventory request. Deletion waits for confirmation and one delete request; after success the picker is updated locally before the existing refresh inventory request completes.
- Scaling input: Tunnel inventory size controls local filtering, sorting, item allocation, and picker assignment. The diff adds one immediate O(N log N) picker rebuild per successful deletion before the existing refresh rebuild.
- Effective concurrency: Deletion is serialized by the isDeleting guard; delete and refresh are sequential, with no added concurrent boundary fan-out.
- Cache behavior: The tunnel service removes the deleted tunnel from persisted cache after successful deletion; the local picker array is also filtered immediately. A failed refresh preserves the remaining displayed entries.
- Mechanism confidence: High confidence in the extra local rebuild and unchanged network cardinality.
- Magnitude uncertainty: Tunnel lists are expected to be small; no evidence establishes a size where the extra user-triggered picker rebuild causes perceptible UI cost.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostActions.ts:promptToConnectViaTunnel</code>: Enumerate tunnels when opening the picker and refreshing after deletion.; cardinality: One list call on open and one list call after each confirmed successful deletion.
    - Introduced by diff: false; previous behavior: The same initial and post-delete list calls occurred.; critical-path effect: Initial listing blocks picker population; post-delete refresh keeps the picker busy, but the local removal is visible immediately.
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostActions.ts:promptToConnectViaTunnel</code>: Delete the selected tunnel through the service or embedder.; cardinality: Exactly one delete call per confirmed item deletion.
    - Introduced by diff: false; previous behavior: The same delete call occurred before refresh.; critical-path effect: Must succeed before the item is locally removed.
- Verdict: No reportable regression. The only added work is a bounded immediate in-memory picker update on a user-triggered deletion; expensive boundary count and ordering are unchanged.

### Scenario 3: Connect, exchange protocol messages, reconnect, and close an embedder-provided web tunnel

- Critical path: Initial connect waits on one embedder connection call; each received JSON frame is parsed and synchronously forwarded to the protocol client. Reconnect waits on one embedder connection call per existing reconnect attempt.
- Scaling input: Inbound protocol-frame rate and number of connection/reconnection lifecycle events.
- Effective concurrency: A transport processes each event callback synchronously. Reconnection scheduling and coalescing remain in the existing ReconnectingTransport and remote-host service; the diff does not alter them.
- Cache behavior: No cache is involved on the frame path. Timing fields retain three scalar values per live transport and are released with the transport.
- Mechanism confidence: High confidence in per-frame placement and constant retained state, with low confidence that its magnitude is material.
- Magnitude uncertainty: Protocol traffic rate varies, but a single clock read per frame is small relative to the existing JSON parse and event dispatch; no benchmark or call-path evidence indicates user-visible CPU or frame impact.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/webTunnelAgentHostService.ts:\_createConnection</code>: Establish the initial or replacement tunnel transport through the embedder discovery provider.; cardinality: One connect call for initial establishment and one per reconnect attempt; the diff only surrounds these calls with timing/context logs.
    - Introduced by diff: false; previous behavior: The same provider connect calls occurred with the same sequencing.; critical-path effect: Directly blocks initial connection or reconnection completion.
  - serialization at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/webTunnelAgentHostService.ts:TunnelConnectionTransport</code>: Parse each inbound JSON frame and stringify each outbound protocol message.; cardinality: Once per protocol frame/message.
    - Introduced by diff: false; previous behavior: The same JSON parse/stringify occurred; the diff adds one Date.now clock read per inbound frame and lifecycle-only logging.; critical-path effect: Synchronous on message delivery.
- Verdict: No reportable regression. Added diagnostics do not add network calls, unbounded retention, serialization, or materially expensive synchronous work.
