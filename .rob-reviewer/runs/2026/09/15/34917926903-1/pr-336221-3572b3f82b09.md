**Relevant issue families:** synchronous-ui-work, repeated-work, cleanup-lifecycle

### Scenario 1: Mouse click on the consolidated workspace picker's Remote row

- Critical path: The list selection callback clears selection and calls \_showSubmenuForItem, which synchronously converts the already-materialized remote actions into submenu items, constructs a virtualized ActionListWidget, measures/layouts it, and displays it before the interaction completes. If focus or hover already opened this same row, \_currentSubmenuElement short-circuits duplicate construction.
- Scaling input: Effective submenu cardinality is the already-grouped union of remote recent workspaces, remote browse actions, remote providers, and contributed remote menu actions; one widget is created per transition from closed/different row to this row.
- Effective concurrency: Single synchronous UI-event path; no queued or parallel expensive work. Repeated clicks on the currently open row are coalesced by the current-element guard.
- Cache behavior: Remote action descriptors are built once when the parent picker is shown. The submenu widget is retained while that row remains open, disposed when cleared, and rebuilt on a later reopen so current action state is reflected; the diff does not alter this lifecycle.
- Mechanism confidence: High: the changed branch and the synchronous submenu construction/layout call path are directly visible, as is the duplicate-open guard and disposal path.
- Magnitude uncertainty: The synchronous cost grows with the number of remote recents, browse actions, providers, and contributed menu actions, although width measurement is capped for lists of 50 or more. Real-world list sizes are uncertain, but opening this list is the requested interaction and the same construction path already ran from hover, chevron, and keyboard activation.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff intentionally makes row click invoke the existing submenu-opening path, does not multiply work for one activation, and adds no subprocess, IPC, filesystem, database, or network boundary to opening the submenu.

### Scenario 2: Touch tap on an opted-in submenu row

- Critical path: A gesture tap delivered through the existing List selection event now takes the same synchronous submenu construction/layout path as a mouse click instead of continuing to parent selection.
- Scaling input: One activation, with synchronous DOM/list work proportional to effective submenu action cardinality.
- Effective concurrency: One synchronous handler per tap. Gesture registration already belongs to the List implementation, and the changed EventType import does not instantiate another Gesture service.
- Cache behavior: Identical to mouse opening: already-built action descriptors feed one live submenu widget, duplicate opens are skipped, and submenu disposables are cleared on hide or replacement.
- Mechanism confidence: High: the tap type check, List's existing touch dependency, current-element guard, and cleanup store are directly traced.
- Magnitude uncertainty: Touch prevalence and remote action counts vary, but there is no evidence of repeated tap dispatch or duplicate widget construction for one activation.
- Expensive boundaries: none found
- Verdict: No reportable regression. The new work is the necessary first rendering of the requested submenu on touch, remains bounded to activation, and introduces no expensive external boundary.

### Scenario 3: Activation of non-opted-in rows, toolbar controls, submenu indicators, and selection of a Remote submenu child

- Critical path: All row selection events perform one event-type comparison and, for mouse/tap activation, bounded closest-ancestor checks. Non-opted-in rows retain their previous dispatch path. Choosing a child still runs that action and then dispatches the mutable parent item, exactly as when the submenu was opened by hover, chevron, or keyboard before this diff.
- Scaling input: Constant work per ordinary row activation; one downstream operation per selected child, independent of total submenu size.
- Effective concurrency: Synchronous selection routing; any selected child starts at most one existing command/provider operation. The diff adds no fan-out, queue, or concurrency burst.
- Cache behavior: No cache lookup or invalidation changes. Menu and provider action objects are prepared before activation, and existing submenu teardown releases widget/listeners on hide.
- Mechanism confidence: High: changed checks are constant per activation and the downstream child dispatch path is unchanged.
- Magnitude uncertainty: DOM ancestor depth for closest() is small and activation frequency is user-paced; provider operation duration varies but its scheduling and cardinality are unchanged.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts:\_dispatchPickerItem and submenu action run callbacks</code>: Execute the chosen contributed command, browse provider action, remote-host management action, or workspace-selection provider flow.; cardinality: At most one operation per explicit submenu child selection; action count in the menu does not cause action execution fan-out.
    - Introduced by diff: false; previous behavior: The same child action path was reachable through the pre-existing hover, chevron, and keyboard submenu-opening mechanisms with the same one-action cardinality.; critical-path effect: This operation begins only after a child is selected, not when the changed parent-row click opens the submenu.
- Verdict: No reportable regression. The added checks are bounded interaction-path work, while potentially expensive child operations are neither introduced nor moved onto parent-row opening.
