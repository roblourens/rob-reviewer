## Findings (1)

### 1. [low] Build a set before counting dismissed tunnels

**Finding ID:** `PERF-28270550049A`  
**Location:** <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/connectionDiagnosticsService.ts:111</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU string comparisons over the persisted dismissed-tunnel array.  
**Scaling:** The added cost grows as discovered tunnel count multiplied by persisted dismissed-ID count, rather than linearly with the discovery result.  
**Outcome:** Increased synchronous completion latency and UI-thread CPU after each successful tunnel enumeration.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The same enumeration returned its tunnel array to the caller without an additional diagnostics-wide dismissal count; the network request count and existing reconciliation remained unchanged.  
**Changed behavior:** Each successful startup, focus-triggered, rediscover, interactive, or post-delete enumeration now counts dismissed results synchronously before trackDiscovery resolves.  
**Confidence:** 0.96 — The call path and complexity are direct: every successful tracked discovery executes this filter before resolving, and TunnelAgentHostStorage.isTunnelDismissed performs Array.includes over a persisted list. The only uncertainty is how often users accumulate enough dismissed IDs and returned tunnels for the delay to become conspicuous, so severity is low rather than omitting the proven mechanism.

**Causal diff evidence:** The added line 111 filters every discovered tunnel and calls isTunnelDismissed; before this PR, listTunnels resolved directly to its existing callers without this diagnostics counting pass.

Accounts with many tunnels and a long-lived set of dismissed tunnel IDs can pause after enumeration completes before startup host status, the host picker, or rediscovery becomes ready.

**Evidence:** trackDiscovery line 111 invokes isTunnelDismissed once per returned tunnel. TunnelAgentHostStorage.isTunnelDismissed uses \`\_dismissedTunnels.get().includes(tunnelId)\`, while dismissTunnel appends unique IDs to the application-scoped persisted array and IDs are removed only by an explicit clear. Therefore a result of T tunnels with D historical dismissals adds O(T\*D) string comparisons on the discovery completion path.

**Suggested direction:** Read getTunnelVisibility once, construct a Set from \`dismissed\`, and count with Set.has (or expose set-backed membership) so the added diagnostics pass is O(T + D) while preserving the same count.
