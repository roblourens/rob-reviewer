**Relevant issue families:** serialization-allocation, synchronous-ui-work, cleanup-lifecycle

### Scenario 1: Browser tunnel reconnect receives and restores a large saved conversation in one WebSocket message

- Critical path: The tunnel stream must receive the full frame/message, WebSocketFrameParser must assemble a contiguous payload, TextDecoder must create the string, and BrowserTunnelConnectionTransport synchronously JSON.parse it before the protocol consumer can process the restored conversation.
- Scaling input: Incoming saved-conversation payload size, now bounded at 100 MiB. Parser buffering, contiguous assembly, UTF-8 decoding, and downstream JSON parsing grow linearly with message bytes; effective cardinality is one complete protocol message after fragmentation is coalesced.
- Effective concurrency: Frame processing is synchronous and serialized per stream data event. A normal connection handles one message at a time; separate active tunnel connections can process independently, with no new concurrency burst introduced by the diff.
- Cache behavior: No cache is involved in frame/message receipt or parsing; cold and warm behavior are equivalent, with no coalescing beyond assembling fragments into one message.
- Mechanism confidence: High confidence that larger accepted messages cause proportionally larger buffering, decoding, and synchronous JSON parsing. However, this is the bounded work required to restore the previously supported message range, not evidence of avoidable repeated work or an introduced boundary.
- Magnitude uncertainty: An approximately 11 MiB frame is evidenced by the change and covered at 12 MiB in tests, but prevalence of messages approaching the 100 MiB ceiling and browser-specific pause duration are not measured.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/browserTunnelAgentHostService.ts:191 BrowserTunnelSocketFactory.open</code>: Open a WebSocket over an existing Dev Tunnels relay stream and receive the agent-host protocol response.; cardinality: One upgraded relay stream per active connection and one inbound network message per logical protocol response; stream chunking or WebSocket fragmentation does not create additional network requests.
    - Introduced by diff: false; previous behavior: The same relay/WebSocket boundary existed, but the browser framing layer rejected frames above 1 MiB and assembled messages above 8 MiB; this diff accepts up to 100 MiB.; critical-path effect: The full response must arrive before decoding, JSON parsing, and restoration can proceed.
- Verdict: No finding. The diff deliberately restores compatibility for large responses with a finite cap matching the existing Node transport. It does not add network calls, fan-out, concurrency, or unbounded retention, and the review found no narrower existing transport API or surgical correction that preserves the required large-message behavior while proving a concrete regression.

### Scenario 2: Browser tunnel gateway selection and normal agent-host protocol traffic

- Critical path: Management lookup, relay connection, forwarded-port connection, WebSocket upgrade, and the gateway selection acknowledgement must complete before an active agent-host connection is returned.
- Scaling input: Gateway inventory and acknowledgement messages are small single logical messages; tunnel count does not multiply operations inside the changed hunks.
- Effective concurrency: Connection steps are awaited in sequence. The diff changes no limiter, queue, retry, or parallelism behavior.
- Cache behavior: Tunnel metadata loading follows existing SDK/service behavior; the changed payload constants do not alter cache keys, warm-cache behavior, coalescing, or negative caching.
- Mechanism confidence: High confidence from the unchanged caller and connector flow that boundary cardinality and critical-path ordering are unchanged.
- Magnitude uncertainty: Exact management and relay latency depends on the network, but the diff introduces no additional boundary operation or waiting point.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/browserTunnelAgentHostService.ts:139 BrowserTunnelRelayClientFactory.getTunnel</code>: Fetch tunnel metadata from the Dev Tunnels management service.; cardinality: One management request per connection or selection attempt.
    - Introduced by diff: false; previous behavior: Identical management request count and placement.; critical-path effect: Must complete before creating and connecting the relay client.
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/browserTunnelAgentHostService.ts:166 BrowserTunnelRelayClient.connect</code>: Connect the Dev Tunnels relay client.; cardinality: One relay connection per connection or selection attempt, with a bounded retry only on gateway-selection rejection in unchanged code.

  - network at <code>src/vs/platform/agentHost/common/webSocketOverDuplex.ts:33 connectWebSocketOverDuplex</code>: Write one HTTP upgrade request and await one WebSocket upgrade response over the relay stream.; cardinality: One upgrade exchange per opened message socket.

- Verdict: No finding. Raising receive limits does not affect ordinary small gateway/protocol messages and adds no repeated work, fan-out, or critical-path boundary.

### Scenario 3: Relay socket closes normally or fails due to a protocol/payload error

- Critical path: Closure happens after the connection can no longer make progress. The connector emits one log entry, disposes the TunnelConnection, socket, and relay client, then notifies consumers of closure.
- Scaling input: Number of socket closures; message size affects at most the temporary buffers held by that closing socket, not log count.
- Effective concurrency: One close callback per connection. Different connections may close independently; the diff introduces no burst scheduling.
- Cache behavior: No cache is involved.
- Mechanism confidence: High confidence that TunnelConnection.dispose removes listeners, closes/disposes the socket, disposes the relay client, and releases the connection from the map, so the raised limit does not create persistent post-close retention.
- Magnitude uncertainty: Log sink implementation cost varies, but call cardinality remains one and the added string is bounded by the Error message.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/platform/agentHost/common/tunnelAgentHostConnector.ts:447 TunnelAgentHostConnector.\_createConnection close callback</code>: Emit one info log for a normal close or one warning containing the underlying error for a failed close.; cardinality: Exactly one log call per socket-close event because TunnelMessageSocket finishClose fires once.
    - Introduced by diff: false; previous behavior: The same close path emitted one info log; the diff changes severity and adds the error message without increasing call count.; critical-path effect: The log occurs synchronously on the terminal close path but does not delay an otherwise-progressing connection.
- Verdict: No finding. Error logging replaces rather than adds a boundary call, and close ownership releases large fragmented buffers for garbage collection.

**Summary:** Reviewed all four changed files and traced the browser receive, gateway startup, synchronous decode/JSON parse, logging, and cleanup paths. The payload-cap increase permits larger linear buffering and parsing by design, but remains finite, restores an established transport allowance, and introduces no extra boundary calls, multiplicative work, concurrency burst, cache defect, or retained-resource lifecycle bug. No high-confidence actionable performance finding was identified.
