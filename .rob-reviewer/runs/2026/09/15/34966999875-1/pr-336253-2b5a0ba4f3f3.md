- Critical path: Service initialization completes, then claimInstance binds the main named-pipe IPC server and checkInnoSetupMutex dynamically loads the mutex module and performs one native mutex query before CodeApplication startup can proceed. - Scaling input: One operation per cold first-instance launch; no collection-sized input or loop is entered when the mutex is inactive.
- Effective concurrency: A single process owns the main IPC handle; no new parallel work is introduced.
- Cache behavior: The dynamic import uses the runtime module cache. Cold launch pays module loading once; subsequent calls in the process are warm. No application cache affects the native mutex query.
- Mechanism confidence: High: the old and new control flow both bind once and execute the same inactive-mutex check before application startup.
- Magnitude uncertainty: Native mutex-query duration is not measured, but its count and critical-path placement are unchanged.

- Verdict: No regression: the normal first-launch boundary count and critical path are unchanged.

### Scenario 2: Launching a secondary instance while an existing VS Code instance owns the IPC handle

- Critical path: nodeIPCServe fails with EADDRINUSE, claimInstance connects to the existing main process, forwards launch/status work, and terminates. The updater mutex check is not reached because claimInstance does not return a server on this path.
- Scaling input: One IPC forwarding sequence per secondary process; status mode additionally requests the same diagnostics as before.
- Effective concurrency: The existing primary process remains the sole server; secondary launches are independent clients, unchanged by the diff.
- Cache behavior: No changed cache or coalescing behavior; the mutex module is not loaded on this path before or after the PR.
- Mechanism confidence: High: EADDRINUSE transfers control directly into the unchanged catch branch, so the moved mutex check is bypassed.
- Magnitude uncertainty: Existing-instance RPC duration depends on requested work, but no changed operation reaches this path.
- Expensive boundaries:
  - IPC at <code>src/vs/code/electron-main/main.ts:352-486 claimInstance</code>: Attempt named-pipe bind, connect to the existing instance, and invoke launch or diagnostics RPC; cardinality: One failed bind, one client connection, and the existing scenario-specific RPC calls per secondary launch
    - Introduced by diff: false; previous behavior: The same claimInstance flow completed or terminated before the old caller-side mutex check could run.; critical-path effect: The IPC forwarding is the secondary launch critical path.
- Verdict: No regression: secondary-instance IPC cardinality and latency are unchanged.

### Scenario 3: Launch races a Windows background update holding the -updating mutex

- Critical path: The process first binds the main IPC handle, observes the updater mutex, immediately closes its server, polls the native mutex every 250 ms for at most 120 attempts, and either exits after 30 seconds or, after release, performs one recursive claim that rebinds the IPC server before application startup. Waiting on the updater remains intentional and was already on the critical path; releasing ownership permits the updater to progress.
- Scaling input: Cost is bounded by one updater overlap and 120 polls in the normal scenario, not by workspace size or user data. Concurrent manually repeated launches could each wait independently, but each process was already retained waiting on or connecting to the pre-startup owner and the diff does not establish a realistic aggregate performance regression.
- Effective concurrency: Each process serializes its own bind, mutex wait, and optional rebind. Named-pipe ownership serializes successful binds; there is no unbounded internal task fan-out or newly launched subprocess.
- Cache behavior: The first dynamic import may be cold; the recursive pass is module-cache warm. There is no stale or growing cache and mutex polling is intentionally uncached.
- Mechanism confidence: High: changed lines explicitly dispose on active mutex and recurse only after the bounded check returns false; inspection of Server.dispose confirms it closes the underlying net server.
- Magnitude uncertainty: Exact Windows named-pipe bind/close latency is unmeasured, but the added work is one bounded local IPC lifecycle operation only on the rare update-overlap path.
- Expensive boundaries:
  - IPC at <code>src/vs/code/electron-main/main.ts:352-364 claimInstance</code>: Bind, close, and after updater release rebind the main named-pipe server; cardinality: At most one additional close/rebind cycle for the ordinary single-update overlap; further cycles require distinct external mutex reacquisitions between attempts
    - Introduced by diff: true; previous behavior: The process bound once and retained the main server throughout the updater wait, which is the ownership conflict this change removes.; critical-path effect: The final rebind follows the required updater wait and must complete before startup.
  - other expensive boundary at <code>src/vs/code/electron-main/main.ts:558-580 checkInnoSetupMutex</code>: Poll the Windows updater mutex; cardinality: One initial query plus up to 120 queries at 250 ms intervals; after release, the recursive pass performs one additional inactive query
    - Introduced by diff: false; previous behavior: The same initial query and bounded 120-retry polling loop ran after the first server bind; only one extra inactive query occurs after a successful release.; critical-path effect: Polling intentionally blocks launch for up to 30 seconds while installation is active.
- Verdict: No reportable regression: the PR adds a bounded local close/rebind and one warm mutex query to resolve an updater ownership conflict, without introducing collection scaling, retained growth, or meaningful boundary fan-out.
