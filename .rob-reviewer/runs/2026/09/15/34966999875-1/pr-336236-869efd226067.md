# Performance review: fix(copilot-chat): dispose PromptRenderer's hydrated InstantiationService when super.render throws

[PR #336236](https://github.com/microsoft/vscode/pull/336236) at `869efd226067a9cea94dbe942418e0f847c1917d`

## Findings

No high-confidence performance findings.

## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `extensions/copilot/src/extension/prompts/node/base/promptRenderer.ts:137` (`RIGHT`)  
**Blamed base line:** `extensions/copilot/src/extension/prompts/node/base/promptRenderer.ts:133`  
**Introducing path:** `extensions/copilot/src/extension/prompts/node/base/promptRenderer.ts`  
**Introducing commit:** `333d9a4053e71ed5249450e112b6a9decd3997b4`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.99

**Mechanism:** A per-render child InstantiationService was retained by the parent after cancellation or any render exception because cleanup only ran after the awaited render succeeded. Retained children grew linearly with failed render attempts until the root service was disposed, increasing extension-host memory and GC pressure.

**Symptom:** Repeated cancelled or failed prompt renders caused monotonically retained child instantiation-service objects and their service collections for the extension-host lifetime.

**Fixed behavior:** The added `try/finally` executes child-service disposal after both successful and rejected renders, removing the child from its parent's `_children` Set and releasing its service collection and endpoint references instead of allowing failed renders to accumulate for the parent lifetime.

**Evidence:** `PromptRenderer.create` allocates one child `InstantiationService` per prompt render at lines 66-67. In the base revision, `render()` awaited `super.render()` before reaching the sole trailing dispose at line 133, so any rejection skipped cleanup. `InstantiationService.createChild` inserts the child into the parent's `_children` Set, and only the child's overridden `dispose()` removes it; therefore every failed/cancelled render remained strongly reachable from the long-lived parent. The added failure test exercises this exact rejection path and asserts disposal.

### Scenario 1: Successful chat or utility prompt rendering through \`PromptRenderer.render\` / \`renderPromptElement\`

- Critical path: \`super.render\` and existing trace/message/reference post-processing must complete before the caller receives the rendered prompt. Child disposal was already synchronous on this success path; moving it to \`finally\` preserves its position before promise settlement and adds no extra disposal.
- Scaling input: Prompt tree/message/reference size controls unchanged rendering and post-processing work; request concurrency controls the number of independent renderer instances.
- Effective concurrency: Concurrent requests still render independently with one child service per request and no new queue, limiter, serialization, or fan-out. Disposal remains one call per completed render and is idempotent.
- Cache behavior: Each render creates a fresh hydrated child \`InstantiationService\`; inherited application services remain parent-owned and warm. The diff does not change tokenizer, prompt-result, or reference deduplication cache behavior.
- Mechanism confidence: High: the changed control flow and success-path operation count are explicit; the same single local disposal still occurs after one render.
- Magnitude uncertainty: Prompt-tree size and the cost of individual unchanged prompt elements vary by caller, but the diff does not increase their work or frequency.
- Expensive boundaries: none found
- Verdict: No performance regression. The success path performs the same render, logging, normalization, deduplication, and one disposal as before.

### Scenario 2: Cancelled or otherwise failed prompt rendering while \`super.render\` walks the prompt tree

- Critical path: The unchanged prompt walk runs until cancellation or exception. The new \`finally\` performs local child-service cleanup before the rejection propagates; this bounded cleanup is on the failure path and prevents lifetime retention.
- Scaling input: The old retained object count scaled linearly with the number of cancelled or exceptional renders over the extension-host lifetime; the diff bounds it to currently active renders.
- Effective concurrency: Multiple failing renders may execute concurrently, but each performs exactly one idempotent disposal. There is no new subprocess/IPC/filesystem/network burst or shared serialization point.
- Cache behavior: A fresh child service is allocated per attempt and is not reused. Before the diff, failed attempts remained in the parent's \`\_children\` Set until parent shutdown; after the diff, each failed attempt removes its own child immediately. No negative cache or coalescing is involved.
- Mechanism confidence: Very high: \`createChild\` inserts into the parent's strong \`\_children\` Set, only child disposal removes it, and the base revision skipped the trailing disposal on any rejection. The added test confirms disposal on failure.
- Magnitude uncertainty: Cancellation/failure prevalence and retained bytes per child vary in production, but retained-child count previously grew exactly with failed attempts and persisted for the parent lifetime.
- Expensive boundaries: none found
- Verdict: This PR fixes an unbounded cleanup-lifecycle retention mechanism. The newly executed failure-path disposal is bounded per failed request and is not a reportable regression.

No diff-introduced performance finding was found. Recorded the concrete failed-render memory-retention regression fix with its blamed introducing commit.
