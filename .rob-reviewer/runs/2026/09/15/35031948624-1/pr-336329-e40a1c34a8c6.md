# Performance review: agentHost: Recover customization sync after reconnect

## Findings (1)

### 1. [medium] Cancel superseded reverse reads before retrying

**Finding ID:** `PERF-4DC0D717E266`  
**Location:** <code>src/vs/platform/agentHost/common/agentHostFileSystemProvider.ts:622</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** reverse-RPC request entries, promises, and duplicate client filesystem operations  
**Scaling:** The retained and duplicate work grows as the number of in-flight read/stat/list operations multiplied by overlapping active-connection changes; each change can leave one request on every still-open older transport while launching another on the newest transport.  
**Outcome:** retained memory and excessive IPC/filesystem I/O  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A logical filesystem read issued one reverse-RPC request and waited for that request to settle or for its transport to close; it could hang across reconnect, but it did not create replacement requests while the original remained live.  
**Changed behavior:** The added Promise.race abandons the operation promise when the connection-change event wins, loops, and invokes the operation again on the replacement connection without canceling or unregistering the old request.  
**Confidence:** 0.94 — The retry and lack of cancellation are directly visible in the changed loop, the updated integration test proves simultaneous original and replacement requests, and the server map's only cleanup paths are response/transport close/server disposal. Exact reconnect frequency and tree size vary, which limits severity rather than confidence in the mechanism.

**Causal diff evidence:** Added RIGHT line 622 starts operation(connection) inside a race with the connection-change promise; when the latter wins, the new while loop repeats the operation. The changed protocol test explicitly observes a replacement resourceList request before replying to the original request.

During an overlapping reconnect while the agent host is copying a customization/plugin tree or otherwise reading client files, every in-flight read can be duplicated on the new transport, while unanswered requests on the old transport remain retained. Repeated reconnects can accumulate pending reverse-RPC state and unnecessary client filesystem/IPC work even after the logical read has completed on a replacement connection.

**Evidence:** In the product server, \_sendReverseRequest stores every request in ProtocolServerHandler.\_pendingReverseRequests and removes it only when that same transport responds, closes, or the server disposes. Overlapping reconnects intentionally keep older connections registered, and \_attachConnection retains all live transports. Therefore a stalled-but-open old transport keeps the abandoned map entry/closures indefinitely, while a responsive old client can still perform the duplicate filesystem read. AgentPluginManager syncs customizations with fileService.copy, which can have many directory-list/read requests in flight, so reconnecting during a plugin copy amplifies the duplicate work.

**Suggested direction:** Make read operations cancelable/abandonable across the connection interface. When the connection-change branch wins, synchronously remove and reject the corresponding pending reverse request (and send protocol cancellation if supported) before retrying on the new connection, while preserving the non-retry behavior for mutations.

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/syncedCustomizationBundler.ts:366` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/syncedCustomizationBundler.ts:339`

**Introducing commit:** `300ad62e2cf7322acd14de7a00ca0924370d9c9a`  
**Mechanism family:** `repeated-work`  
**Performance category:** `io`  
**Confidence:** 0.95

**Mechanism:** The old bundle nonce was derived from mtime and size, so a touch-only update changed the nonce and forced the bundler to delete/rewrite the complete in-memory bundle; the changed nonce then defeated AgentPluginManager's cache and caused a full reverse-RPC fileService.copy to host storage.

**Symptom:** Touching an unchanged customization or skill resource triggered O(total bundle files and bytes) local reads/writes plus a complete remote customization copy, delaying customization publication/session readiness.

**Fixed behavior:** The PR reads and hashes content after a metadata miss, then reuses the prior bundle and nonce when line 366 finds identical content, preventing both the destructive local rewrite and the downstream remote copy for touch-only changes.

**Evidence:** resolveCustomizationRefs awaits bundler.bundle, AgentCustomizationScope gates its initial resolved state on that result, and AgentPluginManager skips fileService.copy only when the nonce matches. The added touch-only test verifies that the previous result is reused and the in-memory tree is not rewritten. Base line 339 carried the metadata-derived nonce mechanism, and blame identifies its introducing commit.

### Scenario 2: Read client-side files from the agent host while the client reconnects

- Critical path: stat, realpath, readFile, and readdir await \_readFromConnection. A replacement connection now lets the logical read continue, and plugin synchronization may depend on many such reads. Superseded operations on older transports are off the logical critical path after the replacement succeeds but continue consuming retained state and possibly client I/O.
- Scaling input: The number of in-flight read/list/resolve operations, multiplied by active-connection replacements before old transports respond or close; customization tree copying can supply many simultaneous logical reads.
- Effective concurrency: Each connection change races every active operation and can launch another request on the newest transport while prior requests remain concurrent on all still-open older transports. There is no cross-request cancellation or retry limiter at this layer.
- Cache behavior: No cache or coalescing exists for these provider reads. Each retry is a fresh reverse request, and old pending entries remain until their own response, transport close, or server disposal.
- Mechanism confidence: Very high: the changed Promise.race/loop, integration test, connection retention, and pending reverse-request map establish the mechanism.
- Magnitude uncertainty: The exact number of simultaneous plugin-copy reads and frequency/duration of overlapping transports vary, but the updated integration test proves both requests coexist and product cleanup only occurs on response, close, or disposal.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/common/agentHostFileSystemProvider.ts:\_readFromConnection and src/vs/platform/agentHost/node/protocolServerHandler.ts:\_sendReverseRequest</code>: Send resourceRead/resourceList/resourceResolve as reverse JSON-RPC over the client transport; cardinality: Previously one request per logical operation; now one additional request per active-connection change until an attempt settles, with old and replacement requests overlapping.
    - Introduced by diff: true; previous behavior: A logical read stayed attached to its original request and could hang, but did not fan out across replacement transports.; critical-path effect: The newest request is on the logical read's critical path; abandoned older requests are off-path but remain live.
  - filesystem at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:resourceList/resourceRead and reverse-request handling</code>: Client handles each reverse request by listing, resolving, or reading its local resource; cardinality: Up to one client filesystem operation per original and retry request; duplicates scale with in-flight reads and overlapping reconnects.
    - Introduced by diff: true; previous behavior: Only the original transport requested the operation.; critical-path effect: Only the winning replacement result advances the logical read; work performed for older requests is wasted.
- Verdict: Reported a medium cleanup-lifecycle/IPC finding because retries do not cancel or unregister superseded requests, allowing duplicate client I/O and retained pending state.
