- Effective concurrency: The new readdir/glob and declaration/registry reads execute synchronously and serially in one Node process. \`task.series\` then preserves the existing downstream ordering; after transpilation, the three esbuild bundle subprocesses still run in parallel. In the quality pipeline, other npm-run-all jobs remain separate concurrent processes.

Success and failure both stop after this single scan, with stale registries failing before downstream work.

### Scenario 2: Developer explicit compilation and watch regeneration of the API proposal registry

- Scaling input: All entries under \`src/vscode-dts\`, with effective proposal generation cardinality deduplicated by proposal name. The new path array temporarily includes non-proposal entries, but this directory is small and the array is released after each stream flush.
- Effective concurrency: Each gulp source stream and generator flush is serial. Watch events are coalesced by the existing \`util.debounce(task)\` and regeneration remains parallel with the other top-level watch tasks.
- Cache behavior: No persistent generation cache was added or removed. Gulp/watch and the OS may serve warm metadata/pages; unchanged output is still detected by comparing the generated string with the existing registry and skips the write.
- Mechanism confidence: High confidence from the before/after diff that source discovery, debounce, registry comparison, and conditional write behavior remain equivalent. The only retained-state increase is a small temporary array of all source paths rather than proposal map entries.

### Scenario 3: Focused build-script tests for registry validation and core-ci sequencing

- Critical path: The new tests create small temporary repositories, run synchronous validation, and snapshot fixtures before/after assertions. This work is on the test invocation path only and does not affect editor startup or runtime.
- Scaling input: A fixed test matrix with fixtures containing two proposal declarations, two ignored files, one registry, and a handful of directories. Recursive snapshots scale only with each tiny fixture.
- Effective concurrency: Node test cases in these suites use synchronous fixture I/O around awaited task tests; process-wide \`chdir\` use is serialized by the runner behavior exercised here. No unbounded task or subprocess fan-out is introduced by the tests.
- Cache behavior: Each test uses a fresh temporary directory, so fixture metadata is initially cold; snapshots reread the same tiny files and may benefit from OS cache. Fixtures are removed in test cleanup, so no retained cache or artifact growth remains.
- Mechanism confidence: High confidence that test-only filesystem work is bounded by fixed fixtures and cleanup; the test instrumentation explicitly suppresses full build consumers.
- Magnitude uncertainty: Runner-wide test frequency is not quantified, but per-test fixture size and operation count are fixed and small.

- Verdict: No reportable regression. Added test overhead is bounded, cleans up all temporary state, and avoids spawning the expensive build consumers.
