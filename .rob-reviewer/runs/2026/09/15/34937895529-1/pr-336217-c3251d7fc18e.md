## Findings (2)

### 1. [medium] Avoid full occluder recomputation on chat scroll and mutation

**Finding ID:** `PERF-D49CE3B1BC24`  
**Location:** <code>src/vs/sessions/services/chatBackground/browser/chatBackgroundRenderer.ts:185</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Main-thread DOM traversal, DOMRect/layout reads, and cell-by-occluder intersection CPU work  
**Scaling:** Each coalesced refresh traverses the sessions subtree, reads a DOMRect for every discovered control, then checks every visible Codicon cell against those controls: O(D + C×O), where C grows with viewport area and O/D grow with visible chat/session DOM. Captured scroll and streaming DOM updates can trigger one refresh per event-loop/frame.  
**Outcome:** Increased main-thread CPU and forced-layout risk during transcript rendering and scrolling, causing input/scroll latency and dropped frames on large or split chat views.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, the renderer observed only the sessions part's size. renderCodicons returned immediately when the 80px grid dimensions were unchanged, so transcript scrolling and ordinary chat DOM mutations performed no background geometry work.  
**Changed behavior:** The added subtree MutationObserver schedules a refresh for class/style/child-list changes anywhere outside the background, and the added captured scroll listener does the same for descendant scrollers. renderCodicons now calls getConfettiCandidateGeometry before its unchanged-grid early return, scanning the full subtree and synchronously reading every occluder's bounds on every such refresh.  
**Confidence:** 0.99 — The changed event registrations, SessionsPart ownership, synchronous call path, grid/control nested loops, and pre-diff absence are explicit. RunOnceScheduler coalesces same-turn events but does not remove recurring per-frame scroll or streaming updates; exact frame cost varies with viewport and visible control count.

**Causal diff evidence:** RIGHT lines 185-195 newly register subtree mutation and captured scroll invalidations; previously only the root ResizeObserver called renderCodicons. The diff also moves expensive candidate geometry ahead of the unchanged-grid return, so these new events cannot take the old constant-time early exit.

With the Codicons background selected, scrolling a transcript or streaming/virtualizing a response repeatedly runs the full geometry pass on the UI thread. A default 960×800 background has roughly 107 cells; a 4K part has roughly 1,150, and each is compared with every visible link/button/input/role-based control across all split sessions.

**Evidence:** SessionsPart constructs this renderer with interactive=true. Added lines 185-195 observe the entire part subtree and all captured descendant scrolls. The scheduled callback calls renderCodicons; line 224 invokes getConfettiCandidateGeometry before the grid-size equality check at line 252. Lines 295-310 recursively enumerate foreground descendants and call getBoundingClientRect for each, while lines 322-327 compare each candidate cell against every collected rectangle. ChatView embeds the scrolling ChatWidget tree in this same SessionsPart, and ChatWidget auto-scrolls while responses render.

**Suggested direction:** Do not rebuild all candidates on every descendant scroll/mutation. Keep structural candidate rebuilding on bounded geometry changes, validate only the current target on scrolling (for example with a point hit-test), and scope observation to the known foreground/composer surfaces; preserve target transfer only when that validation fails.

### 2. [medium] Keep inactive Codicon cells lightweight

**Finding ID:** `PERF-F6782ACFFE82`  
**Location:** <code>src/vs/sessions/services/chatBackground/browser/chatBackgroundRenderer.ts:276</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Button objects, emitters, focus trackers, event listeners, disposable graphs, and extra DOM nodes retained for decorative cells  
**Scaling:** Allocation grows with the full viewport grid, approximately 8/9 × ceil(width/80) × ceil(height/80): about 107 cells at the 960×800 fallback and about 1,150 at 3840×2160, although only one cell can be active.  
**Outcome:** Higher Codicons-background creation/resize latency plus persistent DOM/listener memory and later disposal/GC pressure while the background is selected.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each visible cell was one renderIcon HTMLElement with no per-cell controller, focus tracker, emitter, or listeners.  
**Changed behavior:** The loop now calls createCodiconButton for every interactive-renderer cell. Each call constructs a full base Button, an animation wrapper and icon, a DisposableStore, and a per-cell onDidClick subscription; Button itself creates click/tap/keydown/mouseover/mouseout and focus-tracking machinery, even though CSS disables pointer events and tabindex for every inactive cell.  
**Confidence:** 0.99 — The allocation site is explicitly inside the viewport-cell loop, SessionsPart always enables the interactive branch, and only one resulting element is activated. The exact latency varies by display size, but the object/listener cardinality and retention are deterministic.

**Causal diff evidence:** RIGHT line 276 replaces the old one-renderIcon-per-cell path with createCodiconButton for every cell in the interactive renderer; the added implementation at line 343 instantiates the heavyweight Button. Before this diff no Button or per-cell event machinery existed.

Selecting the Codicons background eagerly constructs hundreds—and on a full 4K sessions part over a thousand—full Button instances and their listener/disposable graphs for a feature with exactly one interactive target. This blocks the initial background render and retains the overhead until the background changes or the part is disposed.

**Evidence:** Line 276 is inside the visibleCells loop and chooses createCodiconButton for every cell because SessionsPart passes interactive=true. createCodiconButton at lines 341-361 constructs Button plus wrapper/icon and click subscription. Base Button's constructor registers gesture support, click, tap, keydown, mouseover, mouseout, and focus/blur tracking. updateConfettiButtons marks only cell===confettiCell active and makes every other cell tabindex=-1, aria-hidden, and pointer-events:none.

**Suggested direction:** Render inactive cells as the previous lightweight icon/cell elements and keep only the current target interactive, or use one delegated click/keydown handler on the Codicon layer while toggling role/tabindex/class on the selected lightweight cell. This preserves stable geometry and target transfer without per-cell Button controllers.
