# Performance review: Fix Copilot CLI plugin updates on Windows

## Findings (1)

### 1. [medium] Reuse unchanged CLI plugin entries across state refreshes

**Finding ID:** `PERF-9971034BA886`  
**Location:** <code>src/vs/workbench/contrib/chat/common/plugins/agentPluginServiceImpl.ts:332</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** filesystem resolve/read operations and rebuilt observable/plugin objects  
**Scaling:** For each committed install, update, or uninstall, the cost grows with every installed CLI plugin and each plugin's component directories/files, even when only one installedPlugins record changed.  
**Outcome:** excessive filesystem I/O and delayed plugin/MCP refresh after CLI transactions, especially on remote filesystems  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A discovery refresh reused an existing same-format plugin entry by URI, so unchanged plugins kept their parsed manifests and component observables; only relevant in-plugin watcher events refreshed changed contents.  
**Changed behavior:** Because every CLI source sets watchPluginContents to false, this condition disposes the existing entry for every source on every changed inventory refresh. The rebuild path then re-detects format, rereads the manifest, and eagerly starts reads for commands, skills, agents, rules, automations, hooks, and MCP definitions for all installed plugins.  
**Confidence:** 0.96 — The state-change call path, unconditional eviction, and eager filesystem readers are directly traced in the changed code. Exact wall-clock impact depends on plugin count, component size, and local versus remote filesystem latency, so severity is medium rather than high.

**Causal diff evidence:** The added \`\!watchPluginContents \|\|\` branch at line 332 changes same-format URI entries from reusable to unconditionally disposable whenever content watching is disabled; this PR disables content watching for every CLI plugin source.

Updating or installing one plugin now causes collection-wide cache-directory I/O and object churn. With multiple plugins, particularly under vscode-remote, refresh fans out across all plugin component trees rather than the single changed record, increasing refresh latency and remote filesystem traffic.

**Evidence:** CopilotCliInstalledPluginsStore computes and compares a per-record revision, but \_discoverPluginSources drops that revision and marks all sources watchPluginContents:false at line 1086. On any inventory difference, \_refreshPlugins iterates all sources; this changed line evicts each existing no-watch entry. \_toPlugin then calls readPluginManifest and creates seven recomputeInitiallyAndOnChange component readers whose parser helpers resolve directories and read files. The MCP identity check also re-registers collections for rebuilt objects, although stable server IDs avoid proving a subprocess restart.

**Suggested direction:** Keep content watchers disabled, but propagate the store's revision or another stable content token into the plugin-entry cache and dispose/rebuild only entries whose revision changed; continue removing absent URIs through the existing seen-set cleanup.
