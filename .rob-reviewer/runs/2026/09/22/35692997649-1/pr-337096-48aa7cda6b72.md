## Findings (1)

### 1. [medium] Avoid rescanning every session history for Fusion ownership

**Finding ID:** `PERF-E65C9FB1B530`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/mapSessionEvents.ts:433</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and per-turn Map/Set entries allocated while traversing persisted SDK events  
**Scaling:** Each cold reconstruction now adds two serial O(N) traversals over all persisted SDK events and retains O(U) request-correlation entries, where N is event count and U is root user-turn count; this applies even when the history contains zero Fusion events.  
**Outcome:** Increased latency and allocation/GC pressure before long chat histories can be displayed.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The mapper already performed its existing preprocessing and mapping passes, but did not build Fusion request/SDK-turn correlation indexes or make these two extra full-history traversals.  
**Changed behavior:** Constructing FusionReplayState with the complete event array synchronously runs both constructor loops to index user-message interaction/turn IDs and assistant-turn ownership before the mapper's normal event pass.  
**Confidence:** 0.98 — The two constructor loops, unconditional call site, and serial restore call path are explicit. The exact millisecond impact depends on history size and device speed, but the added O(N) work and its placement before history publication are certain.

**Causal diff evidence:** The added line 433 unconditionally constructs \`FusionReplayState(events)\`; the newly added constructor in \`copilotFusionReplay.ts\` contains two \`for (const event of events)\` loops, so this line introduces two full-log scans for all histories.

Opening or reconnecting to a long Copilot chat blocks history reconstruction on two additional scans of thousands of persisted events; ordinary non-HydraFusion sessions pay the same cost despite never using the replay state.

**Evidence:** The added \`new FusionReplayState(events)\` executes on every \`mapSessionEvents\` call. Its constructor iterates \`events\` once to index every root \`user.message\`, then iterates the full array again to correlate \`assistant.turn\_start\`; \`mapSessionEvents\` subsequently performs its existing main traversal. \`CopilotAgentSession.\_computeMappedEvents\` awaits this mapper after \`session.getEvents()\` and before returning turns, so the added CPU/allocation is on the cold session-open critical path. The surrounding \`\_mappedEventsMemo\` coalesces warm callers, but does not avoid this cost on each cold reconstruction/invalidation wave.

**Suggested direction:** Collect the user/interaction/SDK-turn ownership data inside an existing preprocessing pass in \`mapSessionEvents\` and pass that index to replay state, or otherwise use a no-Fusion fast path that does not add another full traversal; preserve the current memoization and ordering semantics.
