### Scenario 2: A failed test or teardown cleanup error is followed by another test

- Critical path: release serially disposes sessions, closes the client/proxy, and stops the existing server. The next acquire synchronously creates a fresh home and .codex directory, then performs the server launch that was already required after forceRestart or cleanup failure.

- Effective concurrency: Release, directory creation, and replacement launch are awaited serially. There is no aggregate launch or filesystem concurrency introduced.
- Cache behavior: The next server intentionally starts with cold home/user-data/provider disk state so stale sessions cannot contaminate it. In-memory provider reuse was already lost because the process was force-restarted; healthy shared-server caches remain unaffected.
- Mechanism confidence: High for the added operations and serial critical path; low evidence for any material latency impact beyond negligible directory creation.
- Magnitude uncertainty: Provider-specific disk caches may slightly affect replacement startup, but the repository provides no evidence of a significant disk-cache dependency; the directly added filesystem work is two constant operations after an already-failed test.

### Scenario 3: Suite teardown removes active and retired isolated homes

- Critical path: dispose first closes the replay proxy and stops any live server, then removeTempDirs synchronously recursively deletes every tracked root, retrying serially until all are gone or the existing shared 30-second deadline expires.
- Scaling input: Number of isolated roots and total files written across them. Root count grows linearly with failure events, while total persisted test state was already retained in the old shared root until teardown.
- Effective concurrency: All recursive removals are synchronous and serial; retries share one aggregate timeout rather than multiplying the timeout per directory.
- Cache behavior: No cleanup cache. removeTempDirs consumes the tracked array once; failed paths are retried in a local pending list under the same deadline.
- Mechanism confidence: High: the array retention and splice-based serial cleanup are explicit, and the prior single home also retained accumulated contents until teardown.
- Magnitude uncertainty: Exact bytes and deletion time depend on provider logs and failed-test artifacts, but partitioning does not duplicate the dominant per-test artifacts; only constant directory/startup files are added per failure.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/test/node/e2e/harness/agentHostE2ETestHarness.ts:AgentHostE2EServerLease.dispose</code>: Close the replay proxy and stop the final Agent Host process; cardinality: At most one live server per lease
    - Introduced by diff: false; previous behavior: The final server was stopped before deleting the single shared root.; critical-path effect: Must complete before filesystem deletion so provider watchers and descendants release handles
  - filesystem at <code>src/vs/platform/agentHost/test/node/e2e/harness/agentHostE2ETestHarness.ts:removeTempDirs</code>: Recursively remove all tracked temporary roots with rmSync, with read-only repair and retries; cardinality: One root for a failure-free lease, plus one root per failed/cleanup-error release followed by another acquire; each root is attempted serially within one 30-second aggregate deadline
    - Introduced by diff: true; previous behavior: Only the single shared root was passed to removeTempDirs, but it retained the same accumulated sessions and logs from failed tests; the new scheme adds small duplicated root/config overhead.; critical-path effect: Blocks suite teardown, as did deletion of the prior shared root
- Verdict: No reportable unbounded-retention or cleanup-lifecycle regression. Retention is suite-scoped, failure-driven, intentionally diagnostic, and cleanup remains bounded by the existing aggregate timeout.

### Scenario 4: Intentional within-test restart or crash-and-restart persistence checks

- Critical path: restart/crashAndRestart stops or kills the current process, then launches against the same \_startOptions and existing replay proxy before reconnecting the client. The fresh-directory flag is only set by release after failure/cleanup errors, not by these methods.

- Effective concurrency: Process stop/kill and relaunch are sequential and awaited; the replay proxy sequence is preserved rather than duplicated.
- Cache behavior: Persistent disk state and replay-proxy consumed sequence remain warm across intentional restarts exactly as before.
- Mechanism confidence: High from direct call-flow inspection of restart, crashAndRestart, \_restart, and release.
- Magnitude uncertainty: None material to the diff; the changed release flag is not reached during the intentional restart operation.
- Expensive boundaries:

    - Introduced by diff: false; previous behavior: The same home, user-data, and Codex directories were preserved.; critical-path effect: Persistence restore is on the test critical path, unchanged by the diff
- Verdict: No regression; intentional persistence tests retain the prior paths and process-boundary behavior.
