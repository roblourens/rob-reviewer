### Scenario 1: Open the AI Customization MCP Servers section and render installed/available rows with provenance

- Critical path: The widget synchronously filters cached server collections, resolves each row's source from cached observables/arrays, computes virtual-list heights, and renders visible rows. The pre-existing gallery snapshot request starts after the initial home render and is not required for installed rows to appear.
- Scaling input: N installed MCP rows, P discovered plugins, and E installed extensions. Provenance height/render resolution is in-memory; plugin/extension matching uses linear array scans, so worst-case CPU is proportional to N\*(P+E), while DOM/hover creation remains bounded by virtualized visible rows.
- Effective concurrency: Source resolution is synchronous. Gallery loading permits one effective request because a replacement disposes the previous cancellation token source.
- Cache behavior: MCP definitions are cached observables, plugin discovery is a derived observable, and the extension service caches its local projection. Gallery results are held in gallerySnapshotServers; failed/active loads are tracked and requests are cancellation-replaced.
- Mechanism confidence: High confidence that provenance adds bounded synchronous lookups and formatting but no filesystem, IPC, subprocess, or network boundary to list rendering.
- Magnitude uncertainty: Users can install many extensions, but realistically only a small number of MCP rows require extension/plugin matching; there is no evidence that the added in-memory scans create measurable latency.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts:1685 queryGallerySnapshot</code>: Fetch the first MCP gallery page through IMcpWorkbenchService.queryGallery.; cardinality: At most one active snapshot request per cold visible widget state; a new request cancels the prior CTS, and a populated snapshot suppresses further cold loads.
    - Introduced by diff: false; previous behavior: The same gallery snapshot request occurred before this PR.; critical-path effect: Asynchronous and off the installed-list render critical path; it only populates the Available section when complete.
- Verdict: No reportable regression: the added work is bounded in-memory presentation work on a virtualized list, while the only network operation on this scenario is pre-existing and off the installed-row critical path.

- Cache behavior: Cached definition/plugin/extension data is reused. Gallery snapshot/search state and cancellation behavior are unchanged. No new retained map or unbounded cache is introduced.
- Mechanism confidence: High confidence from the refresh listeners, list splice path, virtual delegate, and animation-frame layout path.

- Verdict: No reportable regression: no new expensive boundary or unbounded retention is introduced, and viewport DOM work remains virtualized and layout-coalesced.

### Scenario 3: Activate a plugin provenance link from an MCP row

- Critical path: A single click opens the existing embedded plugin detail and starts README loading; the detail shell renders before the asynchronous README completes.
- Scaling input: One selected plugin and one README whose parse/render cost scales with that README's byte length.
- Effective concurrency: One read is launched per activation; generation checks prevent stale results from rendering, though the underlying existing read is not canceled.
- Cache behavior: No README cache is used, but loading occurs only on explicit activation and stale render results are guarded by a generation token.
- Mechanism confidence: High confidence that the new link reaches the existing detail loader and performs exactly one boundary read for an installed plugin.
- Magnitude uncertainty: README size and remote filesystem latency vary, but activation is deliberate and singular.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/embeddedAgentPluginDetail.ts:66 loadPluginReadme</code>: Read README.md below the selected installed plugin URI (including remote-filesystem access for vscodeRemote).; cardinality: One read for the one explicitly selected plugin per detail render; no collection fan-out.
    - Introduced by diff: true; previous behavior: The same plugin detail and README read were already reachable through the existing Show Plugin management action; this PR adds a direct provenance-link trigger.; critical-path effect: The README subsection waits for the read, but navigation and the rest of the detail render proceed synchronously.
- Verdict: No reportable regression: this is intentional user-triggered detail loading, not eager work or fan-out, and the same operation was already available through the row's management action.

### Scenario 4: Activate an extension provenance link from an MCP row

- Critical path: A single click calls IExtensionsWorkbenchService.open for the source extension and opens its MCP feature editor.
- Scaling input: Exactly one extension ID per explicit activation; no per-server or per-extension fan-out occurs.
- Effective concurrency: One awaited open operation per click; the changed code does not launch a burst.
- Cache behavior: The normal path scans the ExtensionsWorkbenchService cached installed list. Only a cache miss reaches the gallery fallback.
- Mechanism confidence: High confidence in the one-click call path and warm-cache behavior; low evidence that the fallback is prevalent enough to constitute a regression.
- Magnitude uncertainty: A transient initialization race could use the fallback, but the MCP collection source normally corresponds to an already installed extension and the service is eagerly initialized.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts:1699 open</code>: If the extension ID cannot be found in the cached installed collection, fall back to a gallery getExtensions request before opening the editor.; cardinality: Zero requests in the normal warm path because extension provenance is derived from an installed MCP collection; at most one gallery lookup for the selected ID on a cold/missing-cache fallback.
    - Introduced by diff: true; previous behavior: There was no direct extension provenance link in the MCP row before the diff.; critical-path effect: Editor opening awaits the fallback only when the installed extension cannot be resolved locally.
- Verdict: No reportable regression: the operation is explicit, singular, and normally local; there is no realistic scaling or hot-path mechanism.
