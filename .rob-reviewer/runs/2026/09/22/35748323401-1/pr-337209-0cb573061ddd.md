### Scenario 1: Workbench startup and plugin discovery with managed enablement policy applied

- Critical path: The four registered discovery sources start independently; each source must finish its existing discovery work before the combined plugin list becomes available. The added policy overlay runs synchronously only after discovery/config observables publish and performs in-memory map construction; it adds no filesystem or network wait to discovery.
- Scaling input: Total unique discovered plugins across configured, marketplace, extension, and Copilot CLI sources. The new policy map is O(P) per discovery or policy invalidation, after source-level deduplication; collision grouping was already collection-wide.
- Effective concurrency: Discovery schedulers can run independently across the four sources, while each source's per-plugin filesystem operations are awaited serially. Observable recomputation and the policy transaction are synchronous and coalesced by derived-observable caching/transactions; there is no new concurrency burst.
- Cache behavior: Existing plugin entries are reused by URI across refreshes. The new derived policy map is cached while observed and invalidated only by discovery-list or policy changes; it is not rebuilt for every per-plugin reactive read. No negative-cache behavior changes.
- Mechanism confidence: High: the diff and observable implementation show one cached collection scan per invalidation, with no newly introduced boundary operations.
- Magnitude uncertainty: No benchmark quantifies the additional O(P) map allocation, but plugin collections are bounded by discovered installations and the work occurs on infrequent discovery/policy invalidations, not input/render loops.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/common/plugins/agentPluginServiceImpl.ts:ConfiguredAgentPluginDiscovery, MarketplaceAgentPluginDiscovery, CopilotCliAgentPluginDiscovery, and AbstractAgentPluginDiscovery.\_discoverAndBuildPlugins</code>: Resolve plugin directories, detect formats, read manifests/components, and establish file watchers during discovery.; cardinality: Existing per discovered source/plugin, deduplicated by URI within each discovery refresh; the PR adds no calls.
    - Introduced by diff: false; previous behavior: The same discovery sources performed the same filesystem operations before the diff.; critical-path effect: These existing operations gate each discovery source's publication. The added policy map executes only after those publications and does not add another boundary call.
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/common/plugins/agentPluginServiceImpl.ts:enabledPluginsPolicy</code>: Read the effective ChatEnabledPlugins policy from the configuration service when the relevant configuration event fires.; cardinality: One inspection per relevant configuration event, unchanged by the diff; the resulting value serves all plugins.
    - Introduced by diff: false; previous behavior: The same observable and configuration inspection already drove policy-blocked handling.; critical-path effect: The inspection feeds existing and new in-memory derived state but is not multiplied per plugin.
- Verdict: No reportable regression. The added O(P) in-memory policy-map pass is bounded, cached while observed, and small relative to the pre-existing discovery and collision-group passes.

### Scenario 2: Open or update the plugin list, embedded detail, or plugin editor while policy state changes

- Critical path: Visible row/detail/editor autoruns synchronously read per-plugin enablement and policy observables and update a switch, action bar, or detail DOM. The virtualized list limits row work to rendered entries; a policy change updates managed plugins transactionally.
- Scaling input: Rendered plugin rows plus any open detail/editor panes. Per rendered item, the diff adds constant-time observable reads and DOM property updates; full detail rerender occurs only when that selected plugin's policy value changes.
- Effective concurrency: UI updates run synchronously on the renderer thread through observable transactions. There is no subprocess, IPC, filesystem, database, or network work introduced by the policy checks, and no asynchronous fan-out.
- Cache behavior: Per-plugin policy observables hold the current tri-state value. Global policy lookup is served from the observed derived map; list virtualization and disposable stores bound active row subscriptions to rendered UI lifetime.
- Mechanism confidence: High: changed UI hunks only add observable reads, action replacement, and bounded DOM state updates; transitive detail/marketplace boundaries remain unchanged.
- Magnitude uncertainty: Exact visible-row counts and policy-update frequency vary, but the changed work is constant per rendered row and policy updates are administrative rather than frame-rate events.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/agentPluginEditor/agentPluginEditor.ts:fetchReadme</code>: Load an installed plugin README when opening details.; cardinality: At most one cached README request for the selected editor item; unchanged by the policy-action diff.
    - Introduced by diff: false; previous behavior: Opening plugin details already loaded the selected plugin README.; critical-path effect: README loading is on the existing detail-open path, but the new policy observable read neither triggers nor multiplies it.
  - network at <code>src/vs/workbench/contrib/chat/browser/agentPluginEditor/agentPluginEditor.ts:renderInput and PluginListWidget refresh flow</code>: Use existing marketplace data/fetch state when rendering plugin editor/list metadata and actions.; cardinality: Existing list/editor refresh behavior, grouped by the marketplace service rather than per policy check.
    - Introduced by diff: false; previous behavior: Marketplace fetching and cached snapshots already existed on these surfaces.; critical-path effect: Policy reads are local and do not initiate marketplace requests.
- Verdict: No reportable regression. The UI work is bounded by visible/rendered items and no changed line adds layout reads, network/filesystem calls, or long-lived unbounded state.

### Scenario 3: User toggles plugin enablement or invokes a managed plugin action

- Critical path: For unmanaged plugins, a click performs the existing enablement-model write and now immediately reads the effective in-memory state before updating the switch. For managed plugins, the handler exits before persistence; managed actions only show a notification.
- Scaling input: One selected plugin and, only when enabling a collision member, that plugin's collision group. The added policy check is O(1) map lookup; collision-group scanning remains bounded to duplicate identities.
- Effective concurrency: A single synchronous user action runs at a time. Collision updates use one transaction; there is no parallel I/O or burst scheduling.
- Cache behavior: The policy map is cached while plugin enablement is observed. The base enablement maps remain the authoritative persisted state, preserving the existing storage lifecycle; rejected managed writes do not mutate or invalidate storage.
- Mechanism confidence: High: the call path shows the only added operation after setEnabled is readEnabled, while managed paths avoid the existing persistence boundary.
- Magnitude uncertainty: Collision-group size depends on duplicate installations, but effective cardinality is the duplicate group rather than the full plugin collection and is normally small.
- Expensive boundaries:
  - database at <code>src/vs/workbench/contrib/chat/common/enablement.ts:EnablementModel.setEnabled</code>: Persist profile/workspace plugin enablement through ObservableMemento/storage when an unmanaged toggle is accepted.; cardinality: One logical toggle update, plus existing updates for duplicate collision members; unchanged for unmanaged plugins and eliminated for managed plugins.
    - Introduced by diff: false; previous behavior: Unmanaged toggles already called setEnabled and persisted the same enablement state.; critical-path effect: The added post-write read is in-memory and does not add another storage write. Managed policy checks return before the storage boundary.
- Verdict: No reportable regression. The diff neither increases storage-call cardinality nor introduces a hot synchronous workload.
