**Relevant issue families:** boundary-fanout, repeated-work, serialization-allocation

### Scenario 1: Linux CI diagnostics before smoke tests

- Critical path: The diagnostics task must finish before smoke tests begin, but remains capped by the pre-existing 60-second process-group timeout and is allowed to fail without failing the job.
- Scaling input: Directory-entry count and bytes on the agent's HOME, /tmp, /var, and root filesystem; effective cardinality is four sequential du traversals, with root intentionally overlapping the narrower scans exactly as before.
- Effective concurrency: Commands are sequential except lsof\|wc and each du\|sort\|sed pipeline, which run two or three processes concurrently; no new cross-scan concurrency or burst was introduced.
- Cache behavior: No cache exists or was added. Cold and warm behavior both scan current filesystem state; there is no request coalescing or negative-cache behavior.
- Mechanism confidence: High confidence that filesystem/subprocess work and concurrency are unchanged; high confidence that stderr is newly buffered, but low confidence that its realistic volume produces a material performance impact.
- Magnitude uncertainty: The exact number of transient missing-entry or permission messages from hosted agents is unknown. The mechanism is bounded by the task timeout, and the reviewed paths provide no evidence that such messages realistically reach memory-, log-, or latency-significant volume.
- Expensive boundaries:
  - subprocess at <code>build/azure-pipelines/linux/collect-test-diagnostics.sh:49-62</code>: Run df, ps, cat, lsof\|wc, and four du\|sort\|sed diagnostic pipelines.; cardinality: Per job: 5 basic external commands and 12 pipeline commands across four du scans; pipelines have at most three concurrent children.
    - Introduced by diff: false; previous behavior: The inline pre-smoke script executed the same commands, scans, ordering, pipeline widths, and timeout.; critical-path effect: All commands block smoke-test startup, subject to the unchanged aggregate 60-second timeout.
  - filesystem at <code>build/azure-pipelines/linux/collect-test-diagnostics.sh:55-62,75</code>: Traverse HOME, /tmp, /var, and the root filesystem with du -x.; cardinality: Four traversals per pre-smoke task; work scales with entries on the root filesystem and preserves the pre-existing overlapping root traversal.
    - Introduced by diff: false; previous behavior: The same four du traversals were present inline before the diff.; critical-path effect: Traversal latency delays smoke-test startup but cannot exceed the existing 60-second process-group deadline.
  - other at <code>build/azure-pipelines/linux/collect-test-diagnostics.sh:17-21</code>: Capture each diagnostic command's stderr in a shell variable and emit it to the Azure task log.; cardinality: One capture per command; retained bytes scale with that command's stderr, while normal successful runs retain an empty string.
    - Introduced by diff: true; previous behavior: Non-du stderr was already logged directly; du stderr was discarded. The diff buffers stderr to classify expected du failures, but no concrete realistic source of sufficiently large stderr was established for a reportable regression.; critical-path effect: Capture and log emission complete before the diagnostic task proceeds; the whole task remains deadline-bounded.
- Verdict: No reportable regression: expensive scans, command cardinality, concurrency, and timeout are preserved; added stderr buffering lacks evidence of material realistic scale.

### Scenario 2: Linux CI diagnostics after smoke tests

- Critical path: The diagnostics task runs after smoke tests and must finish before subsequent Copilot integration and result-publication steps, but remains capped by the same 60-second process-group timeout and is continue-on-error.
- Scaling input: Entries on HOME and root plus the number and contents of matching vscsmoke-\* directories. All matching smoke directories are passed to one du invocation, so effective boundary cardinality is one grouped smoke-directory operation rather than one call per directory.
- Effective concurrency: HOME and root scans run sequentially; each du\|sort\|sed pipeline has at most three concurrent children. The optional smoke-directory du is one process over all matched directories. No new aggregate concurrency was introduced.
- Cache behavior: No caching or coalescing state exists. The glob groups all current matching smoke directories into one invocation; cold and warm filesystem-cache effects are unchanged from the inline implementation.
- Mechanism confidence: High confidence that process fan-out, filesystem traversal count, grouping, and deadline are unchanged; the only added allocation/logging mechanism is real but not shown to be materially expensive.
- Magnitude uncertainty: Smoke-directory count and disk size vary by test run, but they were already handled by one grouped du call. Error-output volume is unknown and could grow with races, yet no realistic high-cardinality source or observed performance symptom is established.
- Expensive boundaries:
  - subprocess at <code>build/azure-pipelines/linux/collect-test-diagnostics.sh:49-57,63-75</code>: Run df, ps, cat, lsof\|wc, HOME and root du pipelines, and optionally one du over all smoke directories.; cardinality: Per job: 5 basic commands, 6 commands across two broad du pipelines, and at most 1 grouped smoke-directory du invocation.
    - Introduced by diff: false; previous behavior: The inline post-smoke script used the same commands, grouped smoke-directory du invocation, two broad scans, ordering, and timeout.; critical-path effect: Blocks later pipeline steps until completion, with the unchanged 60-second upper bound.
  - filesystem at <code>build/azure-pipelines/linux/collect-test-diagnostics.sh:55-57,66-75</code>: Traverse HOME and root and measure all matched smoke-test directories.; cardinality: Two broad traversals plus one grouped measurement when matches exist; cost scales with filesystem entries and smoke-test data size, not directory count in terms of process fan-out.
    - Introduced by diff: false; previous behavior: The same traversals and grouped smoke-directory measurement existed before the diff.; critical-path effect: Traversal latency delays subsequent CI steps but remains deadline-bounded.
  - other at <code>build/azure-pipelines/linux/collect-test-diagnostics.sh:17-36</code>: Buffer command stderr for classification and then write it to the task log.; cardinality: One temporary string per command; only one command's stderr is retained at a time and successful commands retain none.
    - Introduced by diff: true; previous behavior: du stderr was suppressed while other command stderr streamed directly. No evidence shows realistic stderr volume large enough to cause material allocation, I/O, or latency.; critical-path effect: Classification and emission are synchronous within the diagnostics task, under its aggregate timeout.
- Verdict: No reportable regression: the refactor preserves expensive work and batching, and the new error reporting does not have sufficient evidence of meaningful performance degradation.

**Summary:** Reviewed the complete two-file diff and traced both pre- and post-smoke diagnostic scenarios. The PR extracts existing work into a shared script without increasing filesystem traversal count, subprocess fan-out, concurrency, or timeout. New per-command stderr buffering is theoretically input-scaled but lacks a realistic material-volume trigger in the reviewed scenario, so no performance finding was submitted.
