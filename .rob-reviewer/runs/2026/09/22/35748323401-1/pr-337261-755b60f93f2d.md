# Performance review: mcp: enforce destination policy and contain redirected credentials

[PR #337261](https://github.com/microsoft/vscode/pull/337261) at `755b60f93f2ddf9718c8705fbfdd549fbe4d7947`

## Findings (1)

### 1. [medium] Cache approved destinations instead of awaiting policy RPC per request

**Finding ID:** `PERF-9227788740BE`  
**Location:** <code>src/vs/workbench/api/common/extHostMcp.ts:917</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** extension-host-to-main-thread RPC/IPC calls (and a remote-agent network round trip for remote extension hosts)  
**Scaling:** The added boundary call occurs once for every MCP data request and again for every redirect hop and authenticated retry; after initialization, concurrent tool calls bypass the request sequencer and each independently performs the check.  
**Outcome:** Every MCP tool request is delayed before its existing server fetch, with the added delay becoming a full editor/remote-agent round trip in Remote SSH, Codespaces, and similar remote workspaces.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** \`\_fetch\` proceeded directly to \`\_fetchInternal\` (apart from local cancellation/header work), so an MCP message paid only the existing server-network boundary for this portion of the path.  
**Changed behavior:** Each iteration now awaits \`$checkMcpServerAllowed\` before dispatch, even when the same URL was already approved and recorded in \`\_serverRequestUrls\` by earlier requests.  
**Confidence:** 0.98 — The added awaited RPC, its exact request call path, duplicate behavior for the same URL, absence of coalescing, and remote-extension-host transport are all directly evidenced. Actual RTT varies by deployment, which affects severity rather than the mechanism.

**Causal diff evidence:** Added line 917 inserts \`await raceCancellationError(this.\_proxy.$checkMcpServerAllowed(this.\_id, currentUrl), ...)\` directly before each \`\_fetchInternal\` dispatch; no equivalent boundary call existed before this diff.

A normal long-lived MCP HTTP session repeatedly targets the configured URL, so every tool invocation, notification, backchannel reconnect, or retry gains an avoidable control-plane round trip on its critical path; remote workspaces are affected most.

**Evidence:** \`McpServerRequestHandler.sendRequest\` sends each JSON-RPC request through \`ExtHostMcpServerLaunch\` to \`McpHTTPHandle.send\`; \`\_sendStreamableHttp\` reaches \`\_fetch\`, where added line 917 awaits the main-thread proxy before line 926 can call the network. \`MainThreadMcp.$checkMcpServerAllowed\` adds every approved URL to \`\_serverRequestUrls\`, but it does not use membership to avoid repeated checks. The new tests explicitly expect \`\[TEST\_MCP\_URL, TEST\_MCP\_URL\]\` for an auth retry, confirming duplicate checks of an unchanged destination. \`McpHTTPHandle.send\` only sequences while mode is Unknown, so established-session requests can create concurrent duplicate RPCs.

**Suggested direction:** Keep a per-handle set of destinations that have successfully passed \`$checkMcpServerAllowed\` and call the main thread only for a destination's first use. Preserve revocation by retaining the new main-thread destination tracking and policy-change handler, which already stops active handles when any recorded destination becomes denied.

### Scenario 1: Established streamable-HTTP MCP tool invocation or client notification

- Critical path: The workbench serializes a JSON-RPC message to the extension host; \`McpHTTPHandle.\_fetch\` now waits for \`$checkMcpServerAllowed\` to return before it can start the MCP server fetch. This control call is therefore on every request's critical path.
- Scaling input: Number of MCP JSON-RPC messages. Each message normally targets the same configured URL, so effective destination cardinality is one while check cardinality remains one per message.
- Effective concurrency: Only initial Unknown-mode sends are sequenced. Once HTTP mode is established, concurrent tool requests independently issue policy RPCs; there is no shared limiter, coalescing, or successful-destination cache.
- Cache behavior: \`\_serverRequestUrls\` remembers approved URLs for later revocation but does not serve as a warm approval cache. Cold and warm requests both perform the same main-thread policy RPC; retries also recheck the same URL.
- Mechanism confidence: High: the awaited boundary is directly in the dispatch loop, tests prove unchanged URLs are checked repeatedly, and established sends are not globally serialized.
- Magnitude uncertainty: Local IPC cost may be small, while Remote SSH/Codespaces RTT can be material; request rates and remote latency vary by user and server.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/common/extHostMcp.ts:917, McpHTTPHandle.\_fetch</code>: Await \`$checkMcpServerAllowed\` in the main thread before request dispatch; for a remote extension host this RPC traverses the remote-agent connection.; cardinality: One per MCP request for the common no-redirect case, plus retries; concurrent requests each issue their own call.
    - Introduced by diff: true; previous behavior: No ext-host-to-main-thread policy RPC occurred here; dispatch followed local preparation.; critical-path effect: Blocks the existing server fetch and adds process or remote-workspace round-trip latency.
  - network at <code>src/vs/workbench/api/common/extHostMcp.ts:926, McpHTTPHandle.\_fetchInternal</code>: Fetch the MCP HTTP endpoint.; cardinality: One server request per JSON-RPC message in the no-redirect case.

- Verdict: Reportable boundary fan-out and missing coalescing regression; cache successful destinations for the handle lifetime while retaining main-thread revocation shutdown.

### Scenario 2: Redirected MCP request or server-selected legacy SSE POST endpoint

- Critical path: Each first destination and each redirect hop must pass policy before its network dispatch. Validation is legitimately required for unseen destinations, but repeated requests through the same redirect chain also repeat all RPC checks.
- Scaling input: MCP request count multiplied by redirect-chain length, capped at five loop iterations per \`\_fetch\`; effective unique destinations are commonly stable across requests.
- Effective concurrency: Redirect hops are serial within a request. Separate established-session requests can traverse and validate their chains concurrently without coalescing.
- Cache behavior: Approved redirect URLs are retained in \`\_serverRequestUrls\` for revocation, but that retained set is not consulted to warm-cache validation. Unique redirect URLs accumulate for the connection lifetime; realistic cardinality is generally low, so retention alone was not reported.
- Mechanism confidence: High for repeated per-hop RPC; medium for large retained URL cardinality.
- Magnitude uncertainty: Stable one-hop redirects are plausible, but prevalence and RTT vary; highly dynamic signed redirect URLs could also grow retained URL state, though prevalence was insufficient for a separate finding.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/common/extHostMcp.ts:917</code>: Validate each current redirect destination in the main thread.; cardinality: One per dispatched redirect hop per request, even for destinations approved in previous requests.
    - Introduced by diff: true; previous behavior: Redirect hops were followed without a main-thread policy boundary.; critical-path effect: Serially precedes every network hop.
  - network at <code>src/vs/workbench/api/common/extHostMcp.ts:926-968</code>: Manually fetch each MCP redirect hop.; cardinality: One per hop, at most five loop iterations.
    - Introduced by diff: false; previous behavior: The same manual network redirect chain existed.; critical-path effect: Existing serial redirect-chain latency.
- Verdict: Covered by the reported per-request policy-RPC finding; no separate retention finding due uncertain realistic unique-URL scale.

### Scenario 3: Streamable HTTP backchannel connection and reconnection

- Critical path: Before every backchannel GET can connect or reconnect, \`\_fetchWithAuthRetry\` reaches the same awaited policy RPC. Retry timers remain off-path while sleeping, but the check blocks each actual reconnect attempt.
- Scaling input: Number of active MCP HTTP servers times backchannel reconnect attempts; successful long-lived streams normally have one initial connection.
- Effective concurrency: Each server owns an independent reconnect loop with capped retry delay; there is no cross-server limiter or approval coalescing.
- Cache behavior: No warm approval cache. The same configured endpoint is checked on every reconnect. Authentication metadata fetches intentionally skip MCP destination policy checks.
- Mechanism confidence: High for the boundary placement; frequency depends on server/network health.
- Magnitude uncertainty: Healthy servers reconnect rarely; unstable links can trigger repeated attempts, but exponential/capped delay bounds frequency.
- Expensive boundaries:

    - Introduced by diff: false; previous behavior: Same network connection/retry behavior without the added RPC.; critical-path effect: Existing network boundary for receiving asynchronous notifications.
- Verdict: Same reported missing-coalescing mechanism, with lower normal frequency than tool invocations.

### Scenario 4: Policy configuration change while HTTP MCP servers are active

- Critical path: The configuration event synchronously walks active HTTP servers and their contacted URL sets, evaluates policy, and requests stop for denied transports. This is control-plane work, not on normal tool invocation progress.
- Scaling input: Active HTTP server count multiplied by unique contacted destinations retained per server. Typical effective cardinality is one or a small redirect chain.
- Effective concurrency: Single synchronous event-handler traversal; stop RPCs are fired without awaiting and each denied server stops after the first denied URL.
- Cache behavior: The contacted URL sets live for the connection lifetime and are deleted on non-running state or main-thread disposal. There is no stale-server retention after normal cleanup.
- Mechanism confidence: High for traversal and cleanup; low for a user-visible performance consequence at realistic scale.
- Magnitude uncertainty: Organizations could have many servers or dynamic redirect URLs, but normal active-server and unique-destination counts are small and policy changes are rare.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadMcp.ts:86</code>: Send \`$stopMcp\` for each active server found newly denied.; cardinality: At most one stop call per denied active server per policy-change event.
    - Introduced by diff: true; previous behavior: Active redirected destinations were not revalidated or stopped by this event.; critical-path effect: Off normal request critical path; policy application triggers it.
- Verdict: No separate performance finding. Cleanup deletes all per-server URL state, and expected cardinality/frequency do not establish a concrete regression.

### Scenario 5: OAuth metadata discovery and authentication retry

- Critical path: OAuth resource and authorization metadata network reads remain serial discovery work. They pass \`isAuthMetadata: true\`, so they do not invoke MCP destination policy RPC; the subsequent retried MCP data request does invoke it again before dispatch.
- Scaling input: Authentication challenges and metadata fallback attempts; generally cold-session work, with MCP retry check cardinality one per retried data fetch.
- Effective concurrency: Discovery awaits network operations serially according to the existing OAuth helpers; no new concurrency burst.
- Cache behavior: \`\_authMetadata\` caches successful discovery for the handle. Policy approvals are not cached, so the original and authenticated retry check the same MCP URL twice, as asserted by the changed test.
- Mechanism confidence: High.
- Magnitude uncertainty: Authentication retries are colder and less frequent than ordinary tool calls, but the duplicate same-URL check is directly tested.
- Expensive boundaries:
  - network at <code>src/vs/workbench/api/common/extHostMcp.ts:844-852 and createAuthMetadata</code>: Fetch OAuth protected-resource and authorization-server metadata.; cardinality: Cold authentication discovery only; helper fallback may try multiple well-known URLs.
    - Introduced by diff: false; previous behavior: Metadata discovery already performed network reads.; critical-path effect: Existing cold-auth critical path; policy checking is intentionally skipped for these metadata URLs.
  - IPC at <code>src/vs/workbench/api/common/extHostMcp.ts:917</code>: Revalidate the MCP URL before the authenticated retry.; cardinality: The same URL is checked once for the initial data request and once again for its authenticated retry.
    - Introduced by diff: true; previous behavior: Authentication retries did not call the main thread before dispatch.; critical-path effect: Adds an awaited control round trip before each data fetch.
- Verdict: Corroborates the reported missing approval cache; metadata network work itself is unchanged.

### Scenario 6: Legacy SSE send failure and transport disposal

- Critical path: A failed background fallback send is now caught, disposes its HTTP handle, aborts streams, and reports error. This is failure-path cleanup rather than added steady-state work.
- Scaling input: One cleanup per failing transport; disposed guards prevent repeat handling.
- Effective concurrency: The fallback promise may run in the background, but disposal cancels transport resources and subsequent handling short-circuits.
- Cache behavior: No cache involved; disposable maps remove handles when stop/close completes.
- Mechanism confidence: High that cleanup is bounded and beneficial; insufficient evidence of a shipped regression and symptom to record a regression fix.
- Magnitude uncertainty: Legacy SSE and failure prevalence are unknown.
- Expensive boundaries:
  - network at <code>src/vs/workbench/api/common/extHostMcp.ts:531-540 and 709-730</code>: Legacy SSE POST and attached stream.; cardinality: One POST per legacy JSON-RPC message; failure ends the transport.
    - Introduced by diff: false; previous behavior: The POST existed, but a rejected background fallback was not routed through the new disposal handler.; critical-path effect: Existing legacy transport operation; new error cleanup bounds further work.
- Verdict: No introduced performance issue and no regression-fix record; the changed lifecycle reduces failure-path resource lifetime.
