## Findings (1)

### 1. [medium] Prune completed-attempt telemetry keys with their comparison

**Finding ID:** `PERF-9E62DEAC7D4B`  
**Location:** <code>src/vs/sessions/services/sessions/browser/sessionComparisonService.ts:585</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** UUID key strings retained in a Set and profile storage, along with repeated full-array/JSON allocations and storage writes.  
**Scaling:** Retained bytes and each save/load cost grow linearly with the lifetime number of completed attempts, including attempts whose comparison was deleted; because the full history is rewritten after each completion, cumulative serialization bytes grow quadratically over continued use.  
**Outcome:** Unbounded retained memory and profile storage, plus increasing synchronous CPU/GC and storage-write latency after each completed attempt and increasing startup parse cost.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no comparison-attempt telemetry Set or persisted deduplication history, so archived comparison runs left no permanent telemetry-key state and did not add whole-history serialization to session completion.  
**Changed behavior:** Each completed comparison attempt now permanently adds a UUID-based telemetry-deduplication key to an in-memory Set backed by profile storage, then synchronously serializes the entire accumulated history whenever another attempt completes.  
**Confidence:** 0.96 — The added Set insertion, full-set JSON serialization, startup reload, and absence of pruning in both comparison-removal paths are directly visible in the changed service. Exact profile sizes vary, but the lifetime-linear retention and repeated whole-history serialization do not depend on timing assumptions.

**Causal diff evidence:** The added completion path at line 585 inserts \`${comparison.id}/${participant.id}\` into a profile-lifetime Set, and \`\_removeComparison\`/missing-group cleanup only remove comparison records without deleting the corresponding keys; the added save routine rewrites the full Set after each newly completed attempt.

Users who repeatedly run and archive comparisons accumulate retained strings and an ever-growing profile value. Later attempt completions allocate and serialize the entire history on the session-change critical path, increasing CPU/GC and storage-write latency; window startup also reloads and parses all stale keys.

**Evidence:** \`\_loadAttemptTelemetryState\` restores every historical key into \`\_reportedAttemptTelemetry\`; \`\_captureTerminalAttemptMetrics\` adds one key per terminal attempt and calls \`\_saveAttemptTelemetryState\`; that method executes \`JSON.stringify(\[...this.\_reportedAttemptTelemetry\])\` and stores it at PROFILE scope. \`\_removeComparison\` and \`\_removeComparisonsWithMissingGroups\` update only \`\_comparisons\`, so archived/deleted comparisons leave these keys resident forever.

**Suggested direction:** Bound deduplication state to live comparisons: remove and persist all \`${comparisonId}/...\` keys when a comparison is removed (including missing-group cleanup), or keep/cap the marker within the already bounded comparison record so archived comparisons cannot grow profile state indefinitely.

- Cache behavior: There is no launch-result cache or coalescing across configured attempts; each distinct attempt is intentionally independent. Harness/model configuration is resolved before launch, and repeated harness choices still create separate sessions and worktrees.

- Magnitude uncertainty: Very large user-configured attempt counts could create a resource burst, but normal product use and wording center on a small bakeoff; no evidence establishes a regression at realistic 2-4 attempt cardinality, so this intentional parallelism was not reported.

### Scenario 2: Launch the Judge and optional synthesis after attempts finish

- Critical path: Judge launch is gated until all attempts are terminal and at least two completed. It then creates one Judge session; synthesis similarly creates at most one session after a verdict/user plan. These agent runs are necessarily on the comparison-result critical path.
- Scaling input: One comparison with its attempt count; Judge and synthesis creation remain O(1), while their prompts/manifests scale with the attempt count.
- Effective concurrency: At most one Judge and one synthesis participant per comparison; guards and persisted participant roles prevent concurrent duplicate launches. The Agent Host fallback handles a disconnected-client case, not an additional normal launch.
- Cache behavior: The comparison record and participant resources are retained in memory/profile storage. \`\_judgeStarting\` and the presence of a Judge participant suppress duplicate launches in the window; Agent Host launch state is reconstructed from in-memory session summaries rather than cached separately.
- Mechanism confidence: High: terminal-state gating, launch guards, and the single provider creation calls are explicit.
- Magnitude uncertainty: Provider duration and worktree cost vary, but launch cardinality is tightly bounded per comparison.
- Expensive boundaries:
  - IPC/network/filesystem at <code>src/vs/sessions/services/sessions/browser/sessionComparisonService.ts:\_startJudge/startSynthesis</code>: Create an isolated provider session/worktree and send the Judge or synthesis request.; cardinality: One provider-backed Judge session per eligible comparison, then zero or one synthesis session if requested/configured.
    - Introduced by diff: true; previous behavior: These comparison-only agent sessions did not exist before the PR.; critical-path effect: The Judge model request must finish before a verdict can be displayed; synthesis must finish before its implementation is available.
- Verdict: No reportable scheduling regression: the expensive boundaries are required, occur once per role, and duplicate launch is guarded.

### Scenario 6: Persist comparison state and deduplicate completed-attempt telemetry across restarts

- Critical path: On window/service initialization, the entire stored array is synchronously read and parsed into the Set. When a terminal attempt first gains elapsed time, telemetry capture adds its key and synchronously serializes/stores the full Set on the session-change path.
- Scaling input: Lifetime number of completed attempts across all comparisons, including comparisons later archived or deleted; effective save count is terminal event batches after cache misses.
- Effective concurrency: A session-change callback checks retained comparisons synchronously. Multiple newly observed completions within one comparison check coalesce to one save, but completions arriving in separate provider events each trigger another whole-Set save.
- Cache behavior: The persisted Set acts as a positive deduplication cache for telemetry, so warm checks avoid duplicate telemetry events. However it reloads every historical key at startup and has no eviction when a comparison/group is removed, making warm-state cost grow for the profile lifetime.
- Mechanism confidence: Very high: insertion, persisted reload/full save, and both removal paths were traced directly; neither cleanup path deletes keys.
- Magnitude uncertainty: The exact time to reach thousands of attempts depends on feature adoption and usage, but the absence of pruning makes lifetime-linear retention and repeated O(history) work certain for continuing users.
- Expensive boundaries:
  - filesystem at <code>src/vs/sessions/services/sessions/browser/sessionComparisonService.ts:\_loadAttemptTelemetryState/\_saveAttemptTelemetryState</code>: Load or rewrite the complete profile-lifetime array of telemetry deduplication keys.; cardinality: One profile read/JSON parse at service initialization; then up to one full-history profile write per terminal-completion event batch.
    - Introduced by diff: true; previous behavior: No comparison telemetry-key profile entry, startup parse, or completion write existed before the PR.; critical-path effect: Startup parse/load blocks service construction; completion serialization and storage execute synchronously inside session-change processing.
  - serialization at <code>src/vs/sessions/services/sessions/browser/sessionComparisonService.ts:\_captureTerminalAttemptMetrics/\_saveAttemptTelemetryState</code>: Copy the Set to an array and stringify the entire accumulated key history.; cardinality: One full-array allocation and JSON serialization per event batch that observes at least one previously unreported completed attempt.
    - Introduced by diff: true; previous behavior: No whole-history comparison telemetry serialization occurred.; critical-path effect: Runs before the session-change callback returns and grows with all historical attempts, not current comparisons.
- Verdict: Reportable unbounded-retention regression; submitted a medium-severity finding anchored to the Set insertion.

### Scenario 7: Stop, clean up, or archive all comparison participants

- Critical path: Stop All waits for every active cancellation in parallel. Startup cleanup waits for parallel cancellations and then parallel deletions. Archive Comparison awaits provider archive operations sequentially before deleting the group.
- Scaling input: Number of active/all participant sessions after filtering active statuses; normally attempts plus at most Judge and synthesis.
- Effective concurrency: Cancellation and deletion are \`Promise.allSettled\` fan-outs; archive calls are serialized, matching existing multi-session archive actions elsewhere in the repository.
- Cache behavior: Cancellation acquires/loads chat models as needed and disposes references afterward. There is no comparison-level result cache; session/provider state remains authoritative.
- Mechanism confidence: High for cardinality and concurrency structure.
- Magnitude uncertainty: Provider cancellation/archive latency varies, but comparisons normally contain a small participant set.
- Expensive boundaries:
  - IPC/filesystem at <code>src/vs/sessions/services/sessions/browser/sessionComparisonService.ts:\_cancelAndDeleteSessions</code>: Cancel active agent requests and delete their provider sessions/worktrees.; cardinality: One cancellation model load/IPC per active participant, then one provider deletion per participant during failed/orphaned startup cleanup.
    - Introduced by diff: true; previous behavior: There was no comparison-wide cleanup path; individual session actions performed the equivalent per session.; critical-path effect: The respective cleanup phase waits for all calls; cancellation and deletion phases are ordered, while calls within each phase are parallel.
  - IPC/filesystem at <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:comparisonArchive.onDidClick</code>: Archive each comparison participant through its sessions provider.; cardinality: One provider archive call per comparison group member.
    - Introduced by diff: true; previous behavior: Users could invoke existing multi-session/group archive actions, which also await archive operations sequentially.; critical-path effect: Calls are sequential and the group is deleted only after all archive operations finish.
- Verdict: No introduced performance regression: parallel cleanup bounds latency, and sequential archive follows existing group-action behavior at small cardinality.
