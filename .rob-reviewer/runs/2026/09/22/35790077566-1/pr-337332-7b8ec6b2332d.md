# Performance review: Implement tabbed model picker collapse animation

[PR #337332](https://github.com/microsoft/vscode/pull/337332) at `7b8ec6b2332d2ba0ed8bb8f5d68bb06322ef17a3`

## Findings (1)

### 1. [medium] Avoid full context-view layout on every animation frame

**Finding ID:** `PERF-01CF3AD9E134`  
**Location:** <code>src/vs/platform/actionWidget/browser/tabbedActionListWidget.ts:456</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Main-thread DOM style, layout, and geometry computation for the context view and popup subtree  
**Scaling:** Each Auto on/off transition schedules one callback per display frame for the full 200 ms animation (about 12 callbacks at 60 Hz, more on high-refresh displays); each callback forces geometry work, whose cost grows with the rendered popup/workbench DOM.  
**Outcome:** Repeated synchronous layout on the animation critical path can consume the frame budget and make the new collapse/expand transition visibly stutter.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, toggling Auto refreshed the list in place but did not start a body-height animation or repeatedly invoke context-view layout per frame.  
**Changed behavior:** The new collapse animation starts an unbounded requestAnimationFrame loop for its lifetime and calls IContextViewService.layout on every frame to keep the shrinking popup reanchored.  
**Confidence:** 0.96 — The diff establishes the 200 ms trigger, \`dom.animate\` is a recursive requestAnimationFrame loop, and the traced context-view implementation performs synchronous geometry reads after writes. Exact milliseconds vary by hardware and DOM size, so severity is medium, but the repeated forced-layout mechanism and critical-path reachability are direct.

**Causal diff evidence:** Added line 456 installs \`dom.animate(..., () =&gt; this.\_contextViewService.layout())\` only for the newly introduced body-collapse animation; no equivalent per-frame relayout existed before the PR.

When a user toggles Auto in the tabbed model picker, the 200 ms transition repeatedly forces context-view layout while height is changing, causing animation jank on slower machines or complex workbench DOMs.

**Evidence:** The added dom.animate callback invokes \_contextViewService.layout() every frame until the Web Animation finishes. ContextView.layout() reaches doLayout(), which writes top/left to 0, reads getDomNodePagePosition(view), getTotalWidth(view), and getTotalHeight(view), then writes top/left again. Those synchronous geometry reads follow style and animated-height writes, forcing layout during every animation frame. The added tests explicitly assert that layoutCount increases while the animation is in progress, confirming this is intentional repeated work rather than a one-time final relayout.

**Suggested direction:** Keep anchoring with a compositor-friendly transform or interpolate the known anchor offset during the animation, and run the full context-view layout only at the end (and on interruption), rather than calling ContextView.doLayout on every frame.
