### Scenario 1: Session customization discovery on initial load and filesystem/configuration-triggered refresh, including SDK discovery failure logging

- Critical path: In discover mode, progress waits for three SDK discovery RPCs, local hook discovery, watcher resolution, and any discovered skill/plugin parsing. The changed expression runs only in the terminal non-cancellation error handler after one of those operations fails, immediately before returning an empty result; it is not on successful discovery's critical path.
- Scaling input: The added CPU/allocation and log-byte cost scales linearly with the number and total character length of primary plus additional workspace roots. Typical sessions have a small root list, and refresh triggers are debounced for 100 ms and cancel/coalesce prior in-flight refreshes.
- Effective concurrency: The three SDK discovery calls and local hook/watcher tasks run concurrently inside one refresh. SessionDiscoveredEntry uses a Delayer and cancels the prior CancelablePromise, so rapid file/configuration events coalesce rather than creating an unbounded aggregate of active refreshes from this owner.
- Cache behavior: Discovery-path metadata is loaded once into \_discoveredDirectories and reused on warm refreshes. The changed error formatting has no cache and runs once whenever the main discovery phase fails; successful warm and cold paths do not execute it.
- Mechanism confidence: High confidence in the exact added mechanism and reachability: the diff eagerly joins projectPaths only in the non-cancellation catch, while all expensive discovery boundaries and the log call itself pre-existed.
- Magnitude uncertainty: Configured logger fan-out and unusually large multi-root workspaces can increase bytes written, but no evidence shows realistic root counts or failure frequency large enough for the added single join to create measurable latency, CPU/GC pressure, or I/O regression.
- Expensive boundaries:
