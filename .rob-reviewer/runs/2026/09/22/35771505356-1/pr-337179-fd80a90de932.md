# Performance review: mcp: Show non-migratable servers

[PR #337179](https://github.com/microsoft/vscode/pull/337179) at `fd80a90de93232a527e4d86796df9bc0f6d57f39`

## Findings (1)

### 1. [medium] Short-circuit partial servers before reading each workspace config

**Finding ID:** `PERF-2235B5AA995D`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpServerCustomizationMigration.ts:61</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem-provider reads of distinct workspace .vscode/mcp.json files, including remote/agent-host provider calls  
**Scaling:** Cost grows with the number of distinct workspace roots whose MCP inventory contains only partially supported servers. Reads are deduplicated per source URI, but createPlan awaits the first read for each source inside the server loop, so effective concurrency is one and latency sums across roots.  
**Outcome:** increased migration-dashboard latency and repeated remote filesystem I/O  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The prior compatibility.kind === 'supported' gate rejected every partially supported server before source-file validation, so roots containing only these servers caused no planner filesystem read.  
**Changed behavior:** Partially supported servers (including the newly classified cwd, version, and SSE cases) now enter the planner's source-validation path. For each distinct source URI, createPlan starts readMcpServers and immediately awaits it before advancing to the next root.  
**Confidence:** 0.96 — The changed predicate, the planner call path, the per-source deduplication, and the sequential await are explicit. Remote/agent-host roots are covered by this subsystem and its tests; only the exact number and latency of affected workspace roots varies by user.

**Causal diff evidence:** RIGHT line 61 newly lets compatibility.kind === 'partiallySupported' pass isMcpServerMigrationDeliverable. Those servers now proceed to sourceServers/readMcpServers in createPlan; previously the supported-only predicate excluded them before any file read.

With migration enabled, opening the AI Customizations editor or receiving an MCP refresh in a multi-root remote workspace can block the inventory on the sum of one remote read per affected root, even though these partial servers are ultimately listed as not migratable. Ten or more roots can turn provider round-trip latency into a noticeable wait on every refresh.

**Evidence:** createPlan calls isMcpServerMigrationDeliverable before source access, then caches one readMcpServers promise per sourceUri but immediately awaits it in the same loop. The added predicate therefore creates one serial read per newly admitted source file. CustomizationMigrationService.computeMcpServerMigration awaits createPlan before returning inventory, and the management editor invokes it on initial load and MCP/workbench changes. Tests in customizationMigrationServiceImpl.test.ts explicitly exercise vscode-remote and agent-host URI providers, proving these reads can cross a remote filesystem boundary.

**Suggested direction:** Preserve the exclusion listing but classify known partially supported/non-portable servers into exclusions before readMcpServers. If source validation is genuinely required for some partial reason, pre-group those source URIs and read them with a small shared concurrency limit rather than serially in the server loop.
