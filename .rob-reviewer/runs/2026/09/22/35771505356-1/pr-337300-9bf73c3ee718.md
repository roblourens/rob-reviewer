# Performance review: agentHost: Keep external Codex sessions and transcripts live

[PR #337300](https://github.com/microsoft/vscode/pull/337300) at `9bf73c3ee718e3117bb4bcc8d408eed42c7a5e32`

## Findings (2)

### 1. [medium] Back off idle transcript polling

**Finding ID:** `PERF-D4126B94D18C`  
**Location:** <code>src/vs/platform/agentHost/node/codex/codexChatHistory.ts:48</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Codex app-server JSON-RPC calls, full turn-page parsing, and periodic downstream history hydration  
**Scaling:** Each subscribed chat performs 12 refreshes per minute while idle; each refresh makes at least thread/read plus thread/turns/list (up to additional 100-turn pages), so total work is 24\*N subprocess calls per minute for N retained chat subscriptions despite the global limiter only capping concurrency.  
**Outcome:** persistent background CPU/IPC and app-server contention, with extra database/hydration work every 30 seconds even when the transcript is unchanged  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, opening a Codex chat read its history once; there was no recurring passive-history poll for an unchanged subscribed chat.  
**Changed behavior:** The new scheduler unconditionally schedules another refresh after every run, using a five-second delay whenever no invalidation is pending, so an unchanged chat is polled forever until its subscription is disposed.  
**Confidence:** 0.99 — The unconditional reschedule, exact subscription lifetime, two-call minimum app-server path, page size, and per-chat/global-concurrency behavior are explicit in the changed code. Only the exact CPU duration varies by history size and number of open editors.

**Causal diff evidence:** Added line 48 calls \`this.\_scheduler.schedule(this.\_dirty ? 1000 : 5000)\` from \`finally\`, including successful clean refreshes, creating the recurring idle poll that did not exist before the diff.

Leaving one or more Codex conversations open now wakes the Agent Host and Codex subprocess every five seconds. With several retained editors this can keep both processes continuously busy and increase battery/CPU use even when no external client is writing.

**Evidence:** CodexChatHistory.\_run always schedules at 5 seconds on the clean path. Each callback reaches CodexAgent.\_refreshChatHistory -&gt; \_readSession, whose paginated path issues thread/read(includeTurns:false) and thread/turns/list(itemsView:'full', limit 100), with more pages when the overlap anchor is absent. \_chatHistoryReads limits concurrency to 2 but does not coalesce different chats. In addition, CodexAgent only suppresses equal snapshots for 30 seconds, so unchanged polling periodically fires a full snapshot that AgentService hydrates after opening workspace-transition storage.

**Suggested direction:** Keep the one-second watcher-driven refresh, but after a clean/unchanged read exponentially back off to the existing safety interval (or stop until invalidated), resetting the fast window on filesystem invalidation; also suppress equal snapshots without the 30-second expiry.

### 2. [medium] Publish transcript deltas instead of full histories

**Finding ID:** `PERF-97016B05DAF2`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostStateManager.ts:558</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** serialized Turn payload bytes, replay-buffer arrays/objects, protocol messages, and workbench ChatModel update allocations  
**Scaling:** For U persisted external updates to a chat containing H turns of average payload size S, this path sends and processes O(U\*H\*S) data rather than O(changed suffix); the server replay buffer can retain many of those full-history action arrays up to its 1,000-envelope cap.  
**Outcome:** increased IPC volume, Agent Host/workbench CPU and GC pressure, retained memory, and potential chat UI stalls for long or tool-heavy conversations  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, an external Codex transcript was materialized once when opened or reselected; later external writes did not repeatedly traverse the Agent Host protocol and rebuild the open workbench model.  
**Changed behavior:** Every changed passive snapshot now clears the chat and dispatches ChatTurnsLoaded with a copy of the entire merged turn list, even when only the newest turn or response changed.  
**Confidence:** 0.98 — The full-array action, replay retention, subscribed-client broadcast, JSON transport, and full-history workbench conversion are directly traced. Magnitude depends on transcript size and persisted update frequency, so severity is medium rather than high.

**Causal diff evidence:** Added line 558 dispatches \`ChatTurnsLoaded\` with \`turns: \[...turns\]\` for each passive refresh; paired with the added preceding truncate, this converts a one-turn external change into a full-history protocol payload.

Keeping a long external Codex conversation open while another client sends messages or persists tool/assistant items repeatedly serializes and parses the whole transcript and reconverts it on the UI path. Cost grows with both conversation length and update count, and old full snapshots remain in the server replay buffer.

**Evidence:** CodexAgent preserves an overlap and maps only changed native turns, but AgentService then rebuilds the complete merged array. This added line places all turns in a ChatTurnsLoaded envelope after ChatTruncated. ProtocolServerHandler stores every envelope in its 1,000-entry replay buffer and broadcasts it to subscribed clients, whose transport JSON-serializes it. AgentHostSessionHandler then runs turnsToHistory over state.turns, and ChatService scans the full history and reconstructs the changed request/response parts on the workbench thread.

**Suggested direction:** Carry the common turn prefix/change suffix through a dedicated passive-history delta/replace action, and coalesce replay entries per chat, so subscribers update only changed turns while preserving local turns and drafts.

### Scenario 2: Watching an open external Codex transcript while it is idle or updated by ChatGPT

- Critical path: A filesystem invalidation waits one second, or the idle fallback waits five seconds, then a Codex history read must finish; changed snapshots additionally load workspace-transition metadata, hydrate/interleave turns, replace host chat state, cross the AHP transport, and update the open workbench ChatModel.
- Scaling input: Number N of concurrently subscribed Codex chats, each chat's turn count H and payload size S, and persisted external update count U. Warm paginated reads overlap near the prior penultimate turn, usually one 100-turn page.
- Effective concurrency: Each chat has its own scheduler; provider history reads share a global limiter of 2. AgentService coalesces refreshes by chat key, but different chats remain independent. Workbench history application is synchronous per received event.
- Cache behavior: Cold history reads all pages and rollout metadata. Warm reads request the recent tail and preserve mapped identity for unchanged turns. Equal native snapshots are suppressed only for 30 seconds; the scheduler still polls every five seconds, and every changed snapshot carries the complete merged history downstream.
- Mechanism confidence: Very high: scheduler timing, minimum app-server requests, limiter behavior, full-array action, replay retention, transport serialization, and UI application were all traced.
- Magnitude uncertainty: Exact persisted-item frequency and transcript payload size vary by Codex version and workload; mechanism, minimum polling rate, and full-snapshot scaling are explicit.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts::\_doReadSession</code>: thread/read followed by thread/turns/list with full items; cardinality: At least two app-server calls every five seconds per subscribed idle chat (24\*N calls/minute), plus extra turn pages when the overlap anchor is absent.
    - Introduced by diff: true; previous behavior: History was read on materialization/reselection only; no recurring passive poll existed.; critical-path effect: Blocks each passive refresh and competes with other Codex app-server work; idle polling remains off the visible critical path but consumes persistent background resources.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts::\_loadWorkspaceTransitions</code>: Open session storage and read workspace-transition metadata; cardinality: Once per provider history event, including unchanged snapshots republished after the 30-second suppression window.
    - Introduced by diff: true; previous behavior: This read occurred during initial history restoration, not periodically for an unchanged open transcript.; critical-path effect: Blocks hydration before a passive snapshot can be applied.
  - IPC at <code>src/vs/platform/agentHost/node/agentHostStateManager.ts::refreshChatHistory</code>: Broadcast ChatTruncated plus ChatTurnsLoaded containing the complete Turn array; cardinality: Two actions per changed snapshot; the full payload is O(H\*S) and is sent to each subscribed protocol client, for O(U\*H\*S) total bytes.
    - Introduced by diff: true; previous behavior: The full transcript crossed this path once when the session was opened; subsequent external writes were not live-broadcast.; critical-path effect: Blocks delivery to the workbench and triggers full-history conversion/diffing before the visible model is current.

    - Introduced by diff: true; previous behavior: No repeated full-history action was generated for passive external updates.; critical-path effect: Adds Agent Host CPU/allocations and transport bytes before client application.
- Verdict: Two findings reported: perpetual five-second idle subprocess polling, and full-history serialization/model work for every changed snapshot.
