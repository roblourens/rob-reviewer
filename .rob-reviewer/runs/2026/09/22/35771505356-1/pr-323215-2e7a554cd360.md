# Performance review: Show per-turn file changes summary for agent host chat responses

[PR #323215](https://github.com/microsoft/vscode/pull/323215) at `2e7a554cd36041d3a97ac5c3eb1fd72ca923c7de`

## Findings (2)

### 1. [low] Evict memoized turn observables after their summaries are released

**Finding ID:** `PERF-076D86BE5019`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostResponseFileChanges.ts:55</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** Map keys and per-turn observable/closure graphs  
**Scaling:** Retained entries grow once per distinct backend-session/request pair whose response summary is rendered, across all agent chats visited during the handler's lifetime.  
**Outcome:** Steadily increasing retained heap and associated GC scanning in long-lived windows that browse many agent turns.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no handler-wide per-request provider cache for agent-host response summaries.  
**Changed behavior:** Each first lookup inserts a per-turn observable into \`\_perRequest\`, but no code removes that entry when the row is unmounted or when \`AgentHostChatSession\` disposal releases the backend session.  
**Confidence:** 0.99 — Ownership and cleanup paths are explicit: the map has a single set site and no delete/clear, while its provider outlives individual rows and chat sessions. Only the exact heap size per turn is uncertain.

**Causal diff evidence:** RIGHT line 55 newly stores each request observable in a handler-lifetime map with no corresponding delete path.

With file-change summaries enabled, opening and scrolling through many agent chats permanently retains one observable graph and composite URI/request key per visited turn until the agent registration or workbench is disposed.

**Evidence:** The new \`\_perRequest\` map is owned by \`AgentHostResponseFileChangesProvider\`, which is registered once on the long-lived \`AgentHostSessionHandler\`. Line 55 inserts every distinct key. Renderer disposal removes observers, and \`Derived.onLastObserverRemoved\` clears subscription/value caches, but it does not remove the outer map entry. \`AgentHostSessionHandler\`'s per-chat dispose callback releases active session subscriptions without notifying this provider, so closed sessions' entries remain reachable.

**Suggested direction:** Remove this permanent memoization (the connection already refcounts/coalesces live subscriptions), or add observer/session-lifecycle eviction so an inactive or closed session's request entries are deleted.

### 2. [medium] Defer the nested file list until changes resolve non-empty

**Finding ID:** `PERF-EC7C0EF23D0F`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts:1502</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** WorkbenchList instances, scoped context keys, DOM nodes, listeners, and observable/list allocations  
**Scaling:** The synchronous construction repeats for every mounted completed agent-host response and again as responses are recreated while scrolling; no-edit turns pay the same setup cost as turns with files.  
**Outcome:** Extra main-thread rendering work and allocation/GC pressure can make opening or scrolling no-edit-heavy agent chats janky.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this gate changed, agent-host responses did not pass the text/notebook edit-group check, so they did not construct a changes-summary content part or its nested WorkbenchList.  
**Changed behavior:** The new agent-host exemption appends a changesSummary part to every completed agent-host response whenever the setting is enabled, even though the asynchronous provider commonly resolves to an empty array.  
**Confidence:** 0.97 — The added gate, constructor call, and unconditional WorkbenchList construction are directly traced. The exact frame-time cost varies with viewport and hardware, but the mechanism and repetition for no-edit mounted rows are explicit.

**Causal diff evidence:** RIGHT line 1502 bypasses the prior edit-group gate for agent-host sessions, newly routing responses with no file changes into the heavyweight summary constructor.

With \`chat.checkpoints.showFileChanges\` enabled, opening or scrolling a conversation containing many short/no-edit turns synchronously constructs a full hidden nested list for each mounted response before the provider establishes that there are no files.

**Evidence:** This added condition admits all completed agent-host responses. \`renderChangesSummary\` then constructs \`ChatCheckpointFileChangesSummaryContentPart\`; its constructor unconditionally calls both \`renderHeader\` and \`renderFilesList\`, and \`renderFilesList\` immediately creates a \`WorkbenchList\`. The newly added autorun merely applies \`display:none\` after reading empty diffs, so it does not avoid that list construction. \`WorkbenchList\` itself creates scoped context keys, registers with the list service, and installs listeners, establishing substantial synchronous UI work rather than a metadata-only pass.

**Suggested direction:** Keep observing the provider with a lightweight placeholder, but create the header and WorkbenchList only after the first non-empty diff array; empty turns should dispose without ever constructing nested list infrastructure.
