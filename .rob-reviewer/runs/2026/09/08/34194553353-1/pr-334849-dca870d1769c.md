**Relevant issue families:** boundary-fanout, cleanup-lifecycle, concurrency-burst

### Scenario 1: Initial connection from the Agents UI to a configured SSH host with ProxyJump

- Critical path: The UI awaits the existing resolveSSHConfig IPC and its \`ssh -G\` subprocess, then awaits connect IPC. The changed path starts one native \`ssh -W\` helper, waits for its spawn, and performs the ssh2 handshake through that stream before existing remote platform discovery, CLI checks, endpoint discovery, and relay setup can proceed.
- Scaling input: One selected configured host per user connection attempt; ProxyJump is a single destination, and comma-separated chains are rejected. Effective helper cardinality is one per proxied SSH connection attempt, not one per discovered endpoint or SSH config entry.
- Effective concurrency: One helper is started within each connection attempt. Established connections are keyed in \`\_connections\`; subsequent relay reconnects reuse the existing SSH client. Concurrent duplicate attempts are not newly introduced or expanded by this diff.
- Cache behavior: There is no cache for \`ssh -G\`, as before. The active \`\_connections\` map acts as the warm path: an established connection reuses its SSH client and proxy transport. A cold or failed attempt creates one helper; direct-host attempts create none.
- Mechanism confidence: High: changed code and tests establish one helper, one socket attachment, direct-host bypass, and teardown behavior.
- Magnitude uncertainty: Actual process startup and jump-host network latency vary by platform and topology, but cardinality and critical-path placement are explicit. The added boundary is inherent to making previously unreachable ProxyJump hosts connect.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:resolveSSHConfig</code>: Resolve effective OpenSSH configuration with \`ssh -G\`.; cardinality: One invocation for the selected host before an initial configured-host connection.
    - Introduced by diff: false; previous behavior: The same \`ssh -G\` subprocess already ran; the diff only preserves its ProxyJump field.; critical-path effect: Must complete before the connection config is built.
  - IPC at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostActions.ts:connectToConfiguredSSHHost</code>: Resolve SSH config and request the main-process SSH connection from the browser action.; cardinality: One resolve request and one connection request per selected host.
    - Introduced by diff: false; previous behavior: The same service calls existed; the diff adds a small optional string to existing config serialization.; critical-path effect: Both requests are awaited on the connection path.
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:\_createProxyTransport</code>: Spawn native OpenSSH with BatchMode and \`-W\` to create the jump-host transport.; cardinality: Exactly one helper for each cold ProxyJump-backed connection attempt; none for direct hosts.
    - Introduced by diff: true; previous behavior: ssh2 dialed the target directly and no jump helper existed, so ProxyJump-only hosts failed rather than establishing a connection.; critical-path effect: Process spawn and the resulting jump/target network path are required before ssh2 authentication can complete.
  - network at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:\_createProxyTransport/\_connectSSH/connect</code>: Connect to the jump host with native OpenSSH, forward to the target, then perform the existing ssh2 handshake and remote setup over the forwarded stream.; cardinality: One jump transport and one target SSH session per cold proxied connection attempt; existing remote exec cardinality after connection is unchanged.
    - Introduced by diff: true; previous behavior: Only a direct target network attempt occurred, which was unusable for ProxyJump-only hosts.; critical-path effect: The jump and target handshakes are on the critical path for hosts that require ProxyJump.
- Verdict: No reportable regression. The single new subprocess/network hop is required for the feature, is bounded to one per proxied attempt, and does not fan out over remote endpoints.

### Scenario 2: Reconnect an Agent Host session configured with ProxyJump

- Critical path: Reconnect first awaits the existing \`ssh -G\` resolution. If \`\_connections\` contains the connection key, it recreates only the WebSocket relay over the existing SSH client, so no helper is spawned. If the prior SSH connection is gone, the cold path creates one helper before the ssh2 handshake.
- Scaling input: One reconnect request for one saved SSH config host; warm effective helper cardinality is zero and cold cardinality is one.
- Effective concurrency: The warm reconnect path is serialized through one service call and reuses one SSH client. The cold path has the same one-helper-per-attempt behavior as initial connect.
- Cache behavior: The \`\_connections\` map distinguishes warm relay reconnects from cold SSH reconnects. ProxyJump is persisted in the sanitized config and refreshed from \`ssh -G\` for cold reconnects.
- Mechanism confidence: High: the existing-connection branch returns before \`\_connectSSH\`, while tests verify ProxyJump survives cold reconnect configuration.
- Magnitude uncertainty: Reconnect frequency depends on session stability, but the warm/cold branches and helper cardinality are clear.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:reconnect/resolveSSHConfig</code>: Refresh effective config using \`ssh -G\`.; cardinality: One per reconnect request.
    - Introduced by diff: false; previous behavior: Reconnect already resolved config this way; only preservation of ProxyJump is new.; critical-path effect: Awaited before lookup/connect because it supplies the reconnect config.
  - network at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:connect</code>: Recreate the WebSocket relay over the established SSH client on a warm reconnect.; cardinality: One relay creation per warm reconnect.
    - Introduced by diff: false; previous behavior: The same relay replacement reused the existing SSH client.; critical-path effect: Awaited, with an existing timeout bound.
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:\_createProxyTransport</code>: Create a native \`ssh -W\` helper only when no active SSH connection remains.; cardinality: Zero for warm relay reconnect; one for a cold ProxyJump reconnect.
    - Introduced by diff: true; previous behavior: Cold reconnect attempted a direct ssh2 connection and did not create a helper.; critical-path effect: On cold reconnect only, required before ssh2 can reach the target.
- Verdict: No reportable regression. Warm reconnects do not multiply helpers, and cold reconnects add only the required single proxy transport.

### Scenario 3: Close or fail a ProxyJump-backed SSH connection

- Critical path: Handshake errors, timeout, synchronous connect failure, socket close, or SSH client close dispose the proxy transport. Established connection disposal calls \`sshClient.end()\`, whose close listener disposes the helper. Cleanup is off the successful connection critical path; handshake timeout bounds failed attempts to 30 seconds except intentional interactive prompt extension.
- Scaling input: Cleanup scales with proxied connection attempts: one guarded disposal per helper and at most one process-tree termination operation when the helper is still alive.
- Effective concurrency: The \`disposed\` guard coalesces socket-close and client-close cleanup. Process-tree termination is asynchronous, so it does not serialize successful UI progress.
- Cache behavior: No cache applies. Ownership is per connection, and the active connection map disposes SSHConnection objects on service shutdown or connection close.
- Mechanism confidence: High: all explicit rejection and close paths converge on idempotent disposal, and established SSH clients are owned by disposable connection objects.
- Magnitude uncertainty: Platform-specific process termination duration is uncertain, but cleanup cardinality is bounded and asynchronous.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:\_createProxyTransport.dispose</code>: Terminate the owned OpenSSH process tree using \`killTree\`, which itself invokes taskkill or the repository termination shell script.; cardinality: At most one termination subprocess for each still-live proxy helper due to the \`disposed\` guard.
    - Introduced by diff: true; previous behavior: There was no owned ProxyJump helper to terminate.; critical-path effect: Fire-and-forget cleanup; it does not delay promise settlement or normal session progress.
- Verdict: No reportable regression. The introduced process has explicit, idempotent cleanup across failures and normal closure, with no evidenced unbounded retention.

### Scenario 4: Connect to a configured SSH host without ProxyJump

- Critical path: The existing \`ssh -G\`, ssh2 direct handshake, remote discovery, and relay setup remain the critical path. \`\_createProxyTransport\` returns before parsing or spawning because \`proxyJump\` is absent.
- Scaling input: One selected direct host per connection attempt; zero helper processes regardless of endpoint count.
- Effective concurrency: Unchanged from the pre-diff direct connection path.
- Cache behavior: Unchanged existing connection reuse; no new cache or negative-cache behavior.
- Mechanism confidence: High: the guard and focused test prove zero spawn calls without ProxyJump.
- Magnitude uncertainty: None material to the reviewed change.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:resolveSSHConfig</code>: Resolve config with \`ssh -G\`.; cardinality: One per configured-host resolution.
    - Introduced by diff: false; previous behavior: Identical boundary and cardinality.; critical-path effect: Awaited as before.
  - network at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:\_connectSSH</code>: Direct ssh2 connection to the target.; cardinality: One direct SSH session per cold connection.
    - Introduced by diff: false; previous behavior: Identical direct connection path.; critical-path effect: Awaited as before.
- Verdict: No reportable regression. Direct connections incur only a constant optional-field check.

**Summary:** Completed the performance pass over all six changed files and all diff pages. Traced initial connection, warm/cold reconnect, failure/teardown, and direct-host control paths. The feature introduces one required native SSH helper only for cold ProxyJump connections, reuses it across warm relay reconnects, drains its pipes, bounds handshake time, and disposes it idempotently. No high-confidence actionable performance regression was found.
