# Performance review: Add opt-in auto-archive/delete inactive sessions with merged pull requests

[PR #334341](https://github.com/microsoft/vscode/pull/334341) at `5859c8badc910de8359b9f5bc8037f5fc83e55dd`

## Findings (2)

### 1. [medium] Avoid refreshing every cleanup PR twice

**Finding ID:** `PERF-96FF2B3D5739`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionLifecycle.ts:164</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** authoritative GitHub core API requests and API quota  
**Scaling:** For C cleanup candidates whose P related PRs are all complete, each startup/hourly pass performs 2 × C × P authoritative requests instead of C × P; P is durably capped at 10, while C grows with retained worktree sessions.  
**Outcome:** doubled background network traffic, GitHub API-budget consumption, and lifecycle sweep latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no background lifecycle sweep or lifecycle-specific GitHub refresh for inactive worktree sessions.  
**Changed behavior:** The new cleanup-only path first refreshes all related PRs at the top of \_evaluateCandidate, performs only local settings/summary checks, and then refreshes the same URLs authoritatively again immediately before cleanup.  
**Confidence:** 0.99 — The two call sites, authoritative network implementation, serial candidate loop, default-enabled setting, and test-observed duplicate URL sequence are explicit. Exact request duration and typical candidate count vary, affecting severity but not the mechanism.

**Causal diff evidence:** Added line 164 calls \_arePullRequestsComplete a second time on the cleanupWorktree branch after line 145 already completed the same authoritative check; cold cleanup candidates with no live summary skip even the intervening summary revalidation.

With the default-on standalone worktree cleanup, Agent Host startup and every hourly pass issue two GitHub core reads per related PR for each merged/closed cleanup candidate. Users retaining many completed agent worktrees consume twice the required API quota and wait twice as long for the serialized cleanup sweep.

**Evidence:** \_arePullRequestsComplete loops over every related URL and resolveForLifecycle creates a background subscription then calls subscription.refresh('core', ..., { authoritative: true }), which reaches the GitHub query boundary rather than accepting the cached snapshot. The lifecycle test's cleanup harness records restored: \[\] together with each pullRequestUrl appearing twice, confirming that cleanup candidates pay both complete refresh rounds without a restore between them. Candidates run serially in run(), so this also lengthens the pass directly.

**Suggested direction:** Perform cleanup's local settings/summary revalidation first and make a single \_arePullRequestsComplete call immediately before cleanup; keep the pre-restore check only for archive/delete candidates where restoration creates a meaningful intervening boundary.

### 2. [medium] Do not reopen every session database on each cleanup pass

**Finding ID:** `PERF-76DAF2A9FA29`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:2129</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem stats plus per-session SQLite connection opens, metadata queries, and closes  
**Scaling:** The cost is one filesystem stat and, for existing data, one SQLite open/query/close for every unloaded internal registry entry (O(S) in retained session history), with only four operations in flight. It is paid even when a session has no PR or no worktree and is repeated hourly while cleanup remains enabled.  
**Outcome:** excessive background filesystem/database I/O and startup-time resource contention that grows with the user's session catalogue  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, Agent Host did not run a startup/hourly lifecycle pass over the durable session registry, so inactive unloaded sessions incurred no per-session database open for worktree cleanup.  
**Changed behavior:** The default-enabled cleanup pass enumerates all internal registered sessions. For an unloaded session \`archived\` is undefined, making this condition true unconditionally, so \`tryOpenDatabase\` runs before the code can reject sessions without related PR metadata or a worktree.  
**Confidence:** 0.98 — The default setting, scheduler, unconditional cold-session branch, concrete stat/SQLite implementation, immediate disposal, and collection cardinality are all explicit. The number of retained sessions and platform-specific I/O duration vary, so magnitude affects severity rather than mechanism confidence.

**Causal diff evidence:** Added line 2129 opens each entry's per-session database from inside the registered-session map. Because \`cleanupWorktrees\` defaults true, the earlier cutoff filters do not exclude recent unloaded sessions, and \`archived === undefined\` guarantees entry into this block.

Users with large retained agent-session histories now get a catalogue-wide burst of filesystem and SQLite work after provider startup and on every hourly pass, including the common majority of sessions that have no lifecycle-relevant PR/worktree. This can contend with normal Agent Host startup and creates ongoing disk/CPU overhead.

**Evidence:** SessionDataService.tryOpenDatabase first performs a file-service stat, then acquires a SessionDatabase; the reference is disposed at the end of this block, and the reference collection closes the underlying database when the last reference is released. Thus cold sessions are not kept warm across passes. The added scheduler starts when a provider registers and reschedules every hour while cleanup is enabled, which it is by default. The lifecycle-candidate test also instruments tryOpenDatabase and confirms candidate enumeration opens cold session databases to discover metadata.

**Suggested direction:** Keep the minimal lifecycle eligibility facts in the existing durable session registry (or an equivalent invalidated candidate index) so the pass can select sessions with related PR/worktree metadata before opening per-session databases; retain the current per-session read as final authoritative validation only for selected candidates.
