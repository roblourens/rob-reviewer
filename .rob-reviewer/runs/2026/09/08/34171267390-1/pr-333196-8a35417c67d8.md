# Performance review: chat: add customization migration assessment telemetry

[PR #333196](https://github.com/microsoft/vscode/pull/333196) at `8a35417c67d8dfce97b4a61ef90ed0d7df397b80`

## Findings (2)

### 1. [medium] Gate migration assessment to session changes, not chat-tab opens

**Finding ID:** `PERF-8A2F086781BA`  
**Location:** <code>src/vs/sessions/services/sessions/browser/sessionsService.ts:789</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** MCP compatibility resolution, provider source-folder calls, and associated IPC/allocations  
**Scaling:** The full assessment repeats once for every \`openChat\` invocation, so cost grows with chat-tab switches/reopens inside the same session and with the number of MCP servers and customization types.  
**Outcome:** Repeated background CPU/IPC work and contention while navigating chats  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Switching or reopening child chats only activated the target chat and updated visibility state; it did not recompute customization migrations or MCP support.  
**Changed behavior:** Every \`openChat\` now starts \`computeMigrations\` for the owning session, even when the session is already active and only its selected child chat changes.  
**Confidence:** 0.97 — The changed call site, widespread \`openChat\` tab-navigation callers, session-scoped computation, IPC provider implementation, and zero-ref scope disposal are directly traced. Exact milliseconds vary with installed MCP/customization count, but the repeated mechanism is deterministic.

**Causal diff evidence:** The added call at line 789 invokes \`\_reportCustomizationMigrationTelemetry\` from \`\_openChat\` after every chat load; before this diff \`\_openChat\` performed no migration assessment.

For sessions with multiple chats, normal tab switching or reopening a side chat repeatedly recomputes the same session-wide assessment. Users with many MCP servers/customizations can see avoidable background CPU and extension-host traffic competing with chat navigation.

**Evidence:** \`openChat\` is the tab-navigation API used throughout \`chatGroupsView.ts\` and the sessions list, including reopening a closed side chat. The added call reaches \`computeMigrations\`, which invokes three file-migration computations plus MCP migration. Each file migration calls \`provideSourceFolders\` for its candidate types (an extension-contributed provider crosses the main-thread/ext-host IPC boundary), and MCP migration acquires a support scope whose initial update waits 50 ms then resolves every known MCP server and local installed-server state. The migration method disposes the scope after each run; refcount zero removes it from \`AgentHostActiveClientService\`, so a later tab switch reconstructs and reruns that assessment rather than hitting a warm scope.

**Suggested direction:** Trigger the assessment only when navigation actually changes the active session (for example, compare the previously active session before \`\_activate\`), while keeping the session-open telemetry path for genuine session opens; do not run it for child-chat selection within the same session.

### 2. [medium] Bound migration assessment concurrency during session restore

**Finding ID:** `PERF-74E69F40C4F9`  
**Location:** <code>src/vs/sessions/services/sessions/browser/sessionsService.ts:1614</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Concurrent MCP configuration assessments, extension-host IPC calls, promises, and temporary result objects  
**Scaling:** Restore launches one four-category assessment per persisted visible session with no limiter; work grows as O(N) assessments and their provider/MCP fan-out, where N is the persisted grid size (which can grow through sticky sessions).  
**Outcome:** A burst of CPU, IPC, and allocation pressure immediately after window restore  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Persisted-session restore resolved sessions and rebuilt the visible grid, with no migration assessment fan-out after layout.  
**Changed behavior:** After \`restoreGrid\`, all resolved sessions simultaneously start \`computeMigrations\`; late sessions do the same from \`place\`, with no queue or concurrency bound.  
**Confidence:** 0.95 — The unbounded fire-and-forget loop, persisted-cardinality source, IPC boundary, and per-root MCP scope key are explicit. The number of pinned sessions and installed MCP servers determines magnitude, not whether the burst occurs.

**Causal diff evidence:** The newly added loop at lines 1611-1615 fire-and-forgets \`\_reportCustomizationMigrationTelemetry\` for every already-resolved restored session; before this diff restore rebuilt the grid without launching this assessment work.

Restoring a window with several pinned sessions, especially across different workspaces, can produce an avoidable startup CPU/IPC spike and GC pressure while the restored UI is becoming interactive.

**Evidence:** \`\_getVisibleSessionStates\` returns every persisted grid slot, and sticky sessions can be appended without a fixed cap. For each restored session, \`computeMigrations\` starts three file categories and MCP assessment in parallel. File categories call \`provideSourceFolders\` per effective prompt type (extension providers use main-thread/ext-host IPC), while distinct workspace roots create distinct \`AgentHostMcpServerSupportScope\`s that each debounce and resolve all MCP server configurations. Because the loop does not await or limit these promises, sessions with different roots execute these assessments concurrently during restore; prompt-list caching does not coalesce the provider-folder or per-root MCP work.

**Suggested direction:** Feed restore telemetry assessments through a small concurrency limiter or idle queue with restore-token cancellation; coalesce only assessments proven to share the same session/resource key, while still emitting the required per-session aggregate telemetry.
