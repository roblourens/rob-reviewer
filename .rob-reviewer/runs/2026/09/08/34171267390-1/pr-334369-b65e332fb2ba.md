## Findings (1)

### 1. [medium] Avoid rescanning every root for each migration group

**Finding ID:** `PERF-4D5A0235B4A0`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpServerCustomizationMigration.ts:224</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem read operations against \`.mcp.json\` and \`.vscode/mcp.json\`, including remote file-provider calls  
**Scaling:** With G selected source/target groups and R workspace roots, this call runs once per group and reads two files for every other root; \`migrateGroup\` repeats the same scan twice more, so the successful path performs about 6\*G\*(R-1) cross-root reads in addition to each group's own reads. When one group is selected per root, this is quadratic in the root count.  
**Outcome:** excessive filesystem I/O and migration latency, especially for remote multi-root workspaces where the reads are sequential IPC/network round trips  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no MCP customization migration execution path, so confirming a migration performed none of these cross-root filesystem scans.  
**Changed behavior:** The new execution loop invokes \`findCrossRootConflicts\` for every migration group; that helper serially reads both MCP configuration locations in every other workspace root, and the same full-root scan is invoked again after the target write and after verification.  
**Confidence:** 0.98 — The nested sequential loops and all three call sites are explicit, tests exercise multiple roots, and the caller passes the complete ordered session root list. Exact wall-clock cost varies by filesystem/provider, but the quadratic call count and critical-path placement are deterministic.

**Causal diff evidence:** The added line 224 places a complete all-roots filesystem scan inside the newly added per-group loop; added calls in \`migrateGroup\` repeat that scan at two later phases.

Confirming migration for servers spread across a 10-root workspace causes roughly 540 cross-root conflict reads before counting source/target verification and write guards, and the nested loops await them serially. On remote filesystems this can turn a one-click migration into a long-running operation.

**Evidence:** \`executeMigration\` processes \`groups.values()\` sequentially and line 224 awaits \`findCrossRootConflicts(group, workingDirectories, fileService)\`. \`findCrossRootConflicts\` loops every root and awaits \`readTargetDocument\` plus \`readSourceDocument\`; \`migrateGroup\` then calls \`ensureNoCrossRootConflicts\` after writing the target and once more after \`verifyMigration\`, each of which calls the same scanner. The service supplies all session roots through \`migrate(..., { roots })\`, so G can equal R in a normal multi-root migration.

**Suggested direction:** Build a conflict index by reading each root's source and target once per validation phase, then check all groups against that index. Preserve concurrency safety by refreshing only roots whose files may have changed after each write (or track etag/mtime and re-read changed documents), rather than rescanning every file for every group.

- Critical path: The confirmation remains in progress until re-planning, all guarded group writes, conflict scans, verification, and any rollback complete. Every conflict scan and file guard is awaited on the execution path.
- Scaling input: Number of distinct selected source/target root groups and total ordered session roots; server names are grouped per source pair, so effective group cardinality, not raw server count, controls the cross-root fan-out.

Existing-file write guards deliberately reread current content/metadata; missing target/source reads are repeated rather than negatively cached.
- Mechanism confidence: Very high: nested loops, three full conflict-scan call sites, grouping behavior, sequential awaits, and caller-provided complete root list are explicit and covered by multi-root tests.
- Magnitude uncertainty: Most workspaces have few roots, but multi-root workspaces with roughly 10 or more roots are realistic, and remote file-provider latency varies. This affects severity, not the deterministic quadratic mechanism.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts:migrateMcpServers</code>: Recompute the current plan by reading each eligible source file before execution.; cardinality: One source read per distinct eligible source root before selected candidates are matched.
    - Introduced by diff: true; previous behavior: No MCP migration execution or re-planning existed.; critical-path effect: Migration does not begin writing until the fresh plan completes.
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpServerCustomizationMigration.ts:executeMigration/findCrossRootConflicts/migrateGroup</code>: Read source and target documents, scan other roots for duplicate names, perform guarded target/source writes, verify both documents, and conditionally restore them.; cardinality: For G selected source groups and R roots, cross-root conflict checks perform about 6\*G\*(R-1) reads on a successful write path because each group scans every other root before migration, after the target write, and after verification; own-document reads/resolves/writes add O(G). With G=R this is quadratic.
    - Introduced by diff: true; previous behavior: Before the PR this workflow and all associated filesystem operations were absent.; critical-path effect: All groups and each root within a conflict scan are awaited sequentially, so remote provider round-trip latency accumulates before completion.
