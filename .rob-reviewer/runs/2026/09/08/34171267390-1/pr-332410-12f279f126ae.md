# Performance review: agentHost: centralize session and chat catalog metadata

[PR #332410](https://github.com/microsoft/vscode/pull/332410) at `12f279f126ae279b3a69347c4e1dec15300e012f`

## Findings (1)

### 1. [medium] Avoid rebuilding the entire chat catalog for one-chat mutations

**Finding ID:** `PERF-7BBA8541C085`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostDatabase.ts:1281</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SQLite statements, row writes, JSON allocations, and the globally serialized orchestrator-database transaction queue  
**Scaling:** Each peer-chat create, dispose, or provider-data change now executes one DELETE plus one INSERT per current peer chat, so a mutation is O(C) database operations for C chats and building C chats is O(C^2); tests establish catalogs near the 1,000-child limit and also permit authoritative catalogs beyond it.  
**Outcome:** increased interactive create/dispose latency, excessive filesystem I/O, and reduced throughput for unrelated orchestrator-database work queued behind the transaction  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The same per-session mutation previously read the PEER\_CHATS\_METADATA\_KEY blob and persisted the updated array with one setMetadata call. It already serialized and encoded O(C) bytes, but did not fan the update out into C individual central-database row writes.  
**Changed behavior:** AgentHostPeerChatStore now sends every single-chat upsert/remove through replaceSessionChatCatalog; that method deletes all rows and awaits one SQLite INSERT for every surviving/current chat, then the compatibility path still writes the legacy blob.  
**Confidence:** 0.97 — The full call path, transaction behavior, and C-sized statement count are explicit in changed code, while repository tests establish realistic C near 1,000. Exact wall-clock cost depends on storage, so severity is medium rather than high.

**Causal diff evidence:** The newly added loop at RIGHT line 1281 is reached from the newly substituted \_peerChatStore.upsert call in \_onChatDataChanged and from createChat/disposeChat. It follows an unconditional DELETE of the session's existing chat rows, converting one-chat mutations into full-catalog SQL replacement.

Creating or removing a peer chat, or changing one chat's model/provider data, can issue about 1,000 serialized INSERTs for a large session. Repeated chat creation accumulates quadratic writes and stalls the operation and other work sharing the orchestrator database.

**Evidence:** AgentHostPeerChatStore.\_applyWrite reads the full catalog and calls \_replaceCentral; \_replaceCentral calls replaceSessionChatCatalog with all entries. replaceSessionChatCatalog performs DELETE FROM session\_chats and then awaits run(INSERT...) once per chat inside BEGIN IMMEDIATE. createChat awaits this path before publishing state, disposeChat awaits it during teardown, and provider data changes enqueue it. The peer-chat tests explicitly exercise AGENT\_HOST\_CATALOG\_CHILD\_LIMIT - 1 entries and verify that authoritative current membership is not truncated beyond the limit.

**Suggested direction:** Keep the revision/CAS and legacy-mirror semantics, but add mutation-specific database operations: UPDATE one row for provider-data changes, INSERT one appended row for creation, and DELETE plus a set-based order adjustment for removal. Reserve full replacement for migration/reconciliation; alternatively execute a true bulk insert rather than one awaited statement per row.
