# Performance review: agentHost: surface Codex skill validation errors

[PR #335053](https://github.com/microsoft/vscode/pull/335053) at `3dc67c0c882fdd00f005130ec907fec2325bebe2`

## Findings (1)

### 1. [medium] Batch invalid-skill updates instead of emitting one container per error

**Finding ID:** `PERF-6B15FF63E079`  
**Location:** <code>src/vs/platform/agentHost/node/codex/codexCustomizations.ts:362</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** session action envelopes, customization-array copies, and downstream customization change notifications  
**Scaling:** For E invalid skill paths in a session with M other customizations, one catalog refresh emits E sequential updates and performs O(E\*M + E²) reducer work; the same fan-out repeats on each coalesced skills-change notification and for each live materialized session.  
**Outcome:** excessive IPC and CPU/allocation pressure during skill catalog refreshes, with repeated UI invalidation  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The same SDK response ignored \`entry.errors\`; invalid skills produced no containers or \`SessionCustomizationUpdated\` actions, while successfully loaded skills remained grouped into at most one container per scope.  
**Changed behavior:** Invalid skill paths are now projected as E separate top-level containers, which the existing refresh publisher emits as E independent state updates.  
**Confidence:** 0.96 — The one-container-per-error cardinality, synchronous per-container publish loop, and linear-copy reducer are directly traced in production code. The exact wall-clock cost varies with the number of invalid skills and active UI listeners, but a repository-wide validation failure is realistic because the motivating required-field diagnostic can affect an entire legacy skill collection.

**Causal diff evidence:** The added \`containers.push\` at line 362 creates a separate top-level container for every entry in the new errors map; before this diff, validation errors were discarded, so they contributed zero containers and zero refresh actions.

When a workspace contains many invalid or legacy skills (for example, a collection whose SKILL.md files all omit the newly required description), every coalesced \`skills/changed\` refresh now publishes one \`SessionCustomizationUpdated\` action per invalid file. Those actions are processed synchronously and individually, so repairing or editing skills can cause noticeable Customizations UI churn and agent-host IPC/CPU spikes.

**Evidence:** \`codexSkillsToContainers\` now appends one top-level \`DirectoryCustomization\` for every distinct error path. \`\_doRefreshSkillHookCustomizations\` iterates every returned container and calls \`\_fire(...SessionCustomizationUpdated...)\` separately (codexAgent.ts:7240-7242). Each action is immediately routed through \`AgentSideEffects.\_handleAgentSignal\` to \`dispatchServerAction\`, while the session reducer handles each update with \`findIndex\` plus a full array spread (reducer.ts:373-380), and the workbench customization service fires change events for every update (agentHostCustomizationService.ts:487-493). Thus E invalid skills add E action envelopes and O(E\*M + E²) array-reference copying for a customization list initially of size M, in addition to repeated downstream invalidation.

**Suggested direction:** Preserve the visible per-skill diagnostics but batch their state publication—for example, add a directory-customization batch replacement action—or group children that share the same diagnostic into one error container so a common schema failure does not create one top-level update per file.
