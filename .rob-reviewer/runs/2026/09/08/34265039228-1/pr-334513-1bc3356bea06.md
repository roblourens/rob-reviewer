# Performance review: feat: implementing word wrap indicators

## Findings (1)

### 1. [medium] Use undecorated line data for the viewport-wide indicator pass

**Finding ID:** `PERF-AEC8DB282DDE`  
**Location:** <code>src/vs/editor/browser/viewParts/wordWrapIndicator/wordWrapIndicator.ts:108</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and transient ViewLineRenderingData objects  
**Scaling:** Each enabled overlay render performs V calls for V visible view lines, and each call derives text direction by scanning the full cached list of D viewport decorations, making the added pass O(V×D) rather than O(V).  
**Outcome:** Increased render-thread CPU/GC pressure and scroll or decoration-update jank in decorated wrapped editors.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no word-wrap-indicator overlay, so scrolling or decoration changes did not add this extra viewport-wide decorated rendering-data pass.  
**Changed behavior:** The new overlay calls ctx.viewportData.getViewLineRenderingData for every visible line on each invalidation even though it reads only continuesWithWrappedLine.  
**Confidence:** 0.97 — The added per-visible-line call path and its nested full decoration loop are explicit in the repository, and scrolling/decoration events explicitly invalidate the enabled overlay. The exact frame cost varies with viewport height and decoration density, so severity is medium rather than high.

**Causal diff evidence:** Added line 108 calls ctx.viewportData.getViewLineRenderingData(lineNumber) inside the new prepareRender viewport loop; this is the line that introduces the repeated decorated-data derivation.

With wordWrapIndicator enabled, a tall wrapped editor containing many visible decorations (for example search matches, diagnostics, and inline decorations) repeats the viewport-decoration scan once per visible line whenever scrolling or decoration changes trigger rendering; hundreds of visible lines and decorations can therefore produce tens of thousands of checks on a frame and cause dropped frames.

**Evidence:** prepareRender loops from viewport start through end and calls \_renderLine for every line. Added line 108 invokes ViewportData.getViewLineRenderingData, which delegates to ViewModel.getViewportViewLineRenderingData. Although ViewModelDecorations caches the viewport collection, ViewModel.\_getViewLineRenderingData calls \_getTextDirection(lineNumber, decorations), and \_getTextDirection iterates the entire viewport decoration array for every line. The overlay only consumes lineData.continuesWithWrappedLine; IViewModel.getViewLineData exposes that same property without collecting or scanning decorations.

**Suggested direction:** Read continuesWithWrappedLine from this.\_context.viewModel.getViewLineData(lineNumber) (or add an equally narrow accessor) so the pass remains O(V) and avoids allocating full rendering data.

### Scenario 1: Open, scroll, or update decorations in a wrapped editor with wordWrapIndicator enabled

- Critical path: The editor's animation-frame render calls ContentViewOverlays.prepareRender, then WordWrapIndicatorOverlay.prepareRender synchronously before DOM rendering can complete.

- Effective concurrency: Events are coalesced to at most one scheduled render per editor animation frame, but each editor processes its visible lines serially; side-by-side editors incur separate passes.
- Cache behavior: The viewport decoration collection is cached for the current visible range, but every per-line rendering-data call still scans that cached collection for text direction. The overlay replaces its string array each dirty pass; unchanged per-line HTML can avoid a DOM replacement only after this CPU work has completed.
- Mechanism confidence: High: the added viewport loop, the cached collection lookup, the nested decoration scan, event invalidation, and animation-frame critical path are all explicit in code.
- Magnitude uncertainty: Exact frame impact depends on viewport height, zoom, decoration density, and the number of visible editor panes; search results, diagnostics, and inline decorations make hundreds of decorations realistic.
- Expensive boundaries: none found
- Verdict: Reportable medium-severity repeated CPU work: the overlay needs only continuesWithWrappedLine but requests full decorated rendering data once per visible line.

### Scenario 2: Construct and render editors while the option remains disabled or wrapping is off

- Critical path: View construction synchronously allocates and registers one lightweight overlay and snapshots a few computed options; prepareRender exits before per-line work whenever the feature is disabled.
- Scaling input: Number of live editor instances and view events; no viewport-line loop runs while disabled.
- Effective concurrency: Construction is synchronous per editor; scheduled editor renders remain animation-frame coalesced.
- Cache behavior: The disabled overlay retains only its options snapshot and a null render result. There is no external cache or repeated per-line work.
- Mechanism confidence: High: constructor and disabled guards are explicit.
- Magnitude uncertainty: Workbench layouts can contain several editors, but the marginal object/listener and constant-time event checks are small.
- Expensive boundaries: none found
- Verdict: No reportable regression for the default-disabled path; eager allocation is bounded and lightweight.

### Scenario 3: Enable the indicator or resize an editor using viewport word wrapping

- Critical path: Configuration/layout recomputation changes wrappingColumn, updates the view-line mapping, and schedules the resulting paint before the editor presents the new layout.
- Scaling input: Document line count and line lengths control rewrapping; visible wrapped lines control indicator DOM cardinality. Reserving one column can add view lines for content near a wrap boundary.
- Effective concurrency: Configuration and line-mapping updates are serialized on the editor thread; resulting paint is animation-frame coalesced.
- Cache behavior: Changing the effective wrapping column invalidates wrapping/layout state; unchanged subsequent renders reuse normal view-model state, while the indicator keeps only viewport HTML strings.
- Mechanism confidence: High for the rewrap path and one-column change; low concern that it is independently avoidable while preserving the proposed layout behavior.
- Magnitude uncertainty: The cost varies with file size and how many lines lie near exact viewport-width boundaries, but it occurs on explicit enable/resize and is inherent to reserving indicator space.
- Expensive boundaries: none found
- Verdict: No separate finding: this is bounded, intentional layout work rather than an accidental frequency or fan-out regression.
