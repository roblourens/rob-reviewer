# Performance review: Add word wrap control to Agents editors

[PR #335070](https://github.com/microsoft/vscode/pull/335070) at `841383d8071492f0ba7b7e04b123d0da02574eb1`

## Findings (1)

### 1. [medium] \[medium\] Coalesce the multi-diff option writes

**Finding ID:** `PERF-560B519E17D0`  
**Location:** <code>src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorWidget.ts:133</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Synchronous option validation, object allocation, and updateOptions calls for both embedded code editors in every currently bound multi-diff item  
**Scaling:** Each setter notification fans out across the effective set of bound/visible multi-diff entries; each entry updates two Monaco code editors. The new setter is called directly after setViewMode, so each activation/visibility callback or preference change causes two O(bound diff entries) passes.  
**Outcome:** Increased synchronous CPU/allocation work and editor-switch or preference-toggle latency, with the cost growing with the number of compact diff entries instantiated in the viewport.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The multi-diff editor received one \_diffLayoutOptions write from setViewMode per layout application, producing one options propagation pass across bound entries.  
**Changed behavior:** setDiffWordWrap always writes a second fresh \_diffLayoutOptions object. Both SessionsDiffEditorLayoutContribution and SessionChangesEditor call it immediately after setViewMode, so even when neither effective value changed, the same bound entries process another full options update.  
**Confidence:** 0.96 — The synchronous call chain and strict-reference notification are explicit in the repository, and both changed callers demonstrably issue back-to-back writes. Virtualization bounds cardinality to currently bound entries, so exact duration varies with viewport/content, but the doubled per-entry work is certain.

**Causal diff evidence:** The added \_diffLayoutOptions.set at lines 133-136 introduces a second observable write, while added calls at src/vs/sessions/contrib/editor/browser/diffEditor.sessions.contribution.ts:145 and src/vs/sessions/contrib/changes/browser/sessionChangesEditor.ts:285 place that write immediately after the existing setViewMode write on hot editor activation/visibility and settings autoruns.

With a multi-diff/Changes editor showing many compact entries, switching active editors, changing visible editors, or changing either layout preference synchronously traverses every bound diff twice and updates both inner editors twice, adding avoidable UI-thread work and potential interaction jank.

**Evidence:** MultiDiffEditorWidget.\_diffLayoutOptions is an observableValue using strict object equality, so the fresh object at this line always notifies. MultiDiffEditorWidgetImpl derives a fresh options override from it; DiffEditorItemTemplate has one autorun per bound item that calls DiffEditorWidget.updateOptions; DiffEditorEditors then updates both original and modified CodeEditorWidgets. The changed callers at diffEditor.sessions.contribution.ts:144-145 and sessionChangesEditor.ts:284-285 invoke setViewMode and setDiffWordWrap sequentially, yielding two notifications/passes.

**Suggested direction:** Expose one setter that applies view mode and word wrap in a single \_diffLayoutOptions.set (and skip the write when the resulting values are unchanged), then use it from both callers; alternatively add equality guards and batch the two fields in one observable transaction.

- Cache behavior: Virtualization limits live templates to rendered/kept-alive entries. There is no equality/coalescing at \_diffLayoutOptions because each setter creates a new object; inner editors can reject equal computed options only after cloning, validating, and traversing them.
