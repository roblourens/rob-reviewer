### Scenario 1: Opening or reopening a local repository for session initialization and GitHub metadata resolution

- Critical path: GitService.openRepository waits for delegate readiness, MainThreadGitExtensionService serializes the request, performs extension-host IPC, converts the returned repository snapshot, updates or creates the wrapper, and waits for HEAD. All of this is on the caller's critical path.
- Scaling input: Number of explicit repository-open requests and, for the returned snapshot, number of changed/untracked files. One stable wrapper is retained per extension-host handle rather than one new wrapper per reopen.
- Effective concurrency: Main-thread opens are serialized globally by Sequencer; the Git extension model also sequentializes openRepository. There is no diff-introduced concurrency burst.
- Cache behavior: The Git API is cached after first activation; extension-host URI/handle maps and the Git model cache already serve warm repositories. The PR adds reuse of the main-thread wrapper and structural equality suppresses observer notifications for unchanged snapshots.
- Mechanism confidence: High confidence in the call path, serialization, and global sequencing from the traced implementations.
- Magnitude uncertainty: Repository snapshots can be large, but reopen frequency and snapshot size vary. The added structural comparison is linear in snapshot size, while serialization and conversion of the same full snapshot were already linear and dominant; no concrete regression is established.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadGitExtensionService.ts:106 openRepository</code>: Calls ExtHostGitExtensionService.$openRepository and returns a serialized repository-state snapshot.; cardinality: One IPC call per explicit open request, both before and after the diff; repeated requests are not coalesced but are serialized.
    - Introduced by diff: false; previous behavior: The same IPC call and full state payload occurred; the main thread then allocated and stored a new wrapper.; critical-path effect: The caller cannot receive the repository until the round trip and state conversion complete.
  - filesystem/subprocess at <code>extensions/git/src/model.ts:600 Model.openRepository</code>: On a cold/non-exact repository path, resolves real paths and may run git rev-parse before opening the repository; an already-open exact root returns early.; cardinality: At most one open traversal per request; warm exact-root requests use the open-repository lookup and avoid these boundaries.
    - Introduced by diff: false; previous behavior: Identical Git API open path was invoked before the diff.; critical-path effect: Cold or non-exact paths block the extension-host response; warm exact-root opens do not perform this work.
- Verdict: No reportable regression: boundary count, critical-path placement, and serialization cardinality are unchanged; wrapper reuse removes allocation churn and only refreshes state in process.

### Scenario 2: Resolving local session changesets

- Critical path: Each observed changeset recomputation calls openRepository and then diffBetweenWithStats2; the resulting file list is required before the changes view resolves.
- Scaling input: Number of active changeset recomputations and files emitted by git diff; there is no per-file IPC fan-out.
- Effective concurrency: Repository opens are globally sequenced. Separate changeset observables may initiate independent diff requests, but this behavior and its concurrency are unchanged by the PR.
- Cache behavior: Repository handles and wrappers are reused, but diff results are not cached here. The PR neither adds nor defeats result caching.
- Mechanism confidence: High confidence from direct resolver, RPC, and Git command traces.
- Magnitude uncertainty: The UI's simultaneous observation count varies, but all boundary multiplicity is pre-existing.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/copilotChatSessions/browser/copilotChatSessionsChangesets.ts:41 GitRepositoryChangesetResolver.resolve</code>: One repository-open RPC followed by one diff RPC for each resolver invocation.; cardinality: One open and one diff per changeset recomputation; effective multiplicity depends on which of the uncommitted/all/last-turn observables are actively consumed.
    - Introduced by diff: false; previous behavior: The same two RPCs occurred; only the main-thread wrapper object returned by open changed identity.; critical-path effect: Both calls must complete before that changeset's files are available.
  - subprocess at <code>extensions/git/src/git.ts:1840 diffBetweenWithStats</code>: Runs one git diff --raw --numstat command and parses output.; cardinality: One git subprocess per diff resolver invocation, not per changed file.
    - Introduced by diff: false; previous behavior: Same subprocess count and arguments before the diff.; critical-path effect: The subprocess is the principal blocking work for changeset resolution.
- Verdict: No reportable regression: the PR does not change open/diff frequency, subprocess count, or output scaling.

### Scenario 3: Reloading branches in the automation dialog after folder selection

- Critical path: A folder change opens the repository, attaches one observable watcher, then requests refs before branch controls become ready.
- Scaling input: Folder-selection/retry frequency and number of local branches.
- Effective concurrency: Each reload cancels the prior token and disposes its watcher; open calls remain serialized, while getRefs accepts cancellation. Wrapper reuse does not accumulate dialog watchers.
- Cache behavior: Warm exact-root opens reuse the Git model repository; refs are freshly queried. The main-thread wrapper is now reused, and the previous autorun is explicitly disposed before each reload.
- Mechanism confidence: High confidence from reloadRepository cancellation/disposal and Git getRefs implementation.
- Magnitude uncertainty: Branch counts and rapid folder changes vary, but no changed scheduling or fan-out mechanism exists.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/automations/browser/automationDialog.ts:858 reloadRepository</code>: One repository-open RPC and then one getRefs RPC per accepted reload.; cardinality: One pair per selected-folder reload; stale requests are ignored and refs are requested once for the repository rather than per branch.
    - Introduced by diff: false; previous behavior: The same RPC pair was issued before the diff.; critical-path effect: The branch selector remains loading until these operations complete.
  - subprocess at <code>extensions/git/src/git.ts:2941 getRefs</code>: Runs git for-each-ref and parses all matching local branches.; cardinality: One subprocess per accepted branch reload, with output proportional to local branch count.
    - Introduced by diff: false; previous behavior: Same subprocess and branch cardinality before the diff.; critical-path effect: Blocks readiness of the branch picker.
- Verdict: No reportable regression: resource ownership remains bounded and all expensive boundary work is unchanged.

### Scenario 4: Propagating Git repository state changes to existing consumers and enumerating known repositories

- Critical path: A Git state event triggers one main-thread notification, which requests and serializes the latest state; updating the stable observable synchronously notifies its currently registered consumers. Repository enumeration itself is in process and off any external boundary.
- Scaling input: Git state-event frequency, number of files represented in state, number of live observable consumers, and number of distinct repository handles.
- Effective concurrency: One state-fetch RPC is initiated per extension event as before; no new batching, parallelism, or fan-out across repositories is introduced. Observable fan-out is proportional only to live consumers of that repository.
- Cache behavior: The map keeps one wrapper per handle and now updates it on reopen, so repeated opens do not grow wrapper cardinality. Structural equality avoids notifications for identical snapshots. No repository-removal lifecycle exists in either revision.
- Mechanism confidence: High confidence in one-wrapper-per-handle behavior and event flow; insufficient evidence for a post-disposal retention mechanism.
- Magnitude uncertainty: Consumer count and repository-state size vary. Removing DisposableMap no longer explicitly clears entries on service disposal, but no independently rooted post-disposal service or disposable resource inside GitRepository was found, so retained-memory impact is not established.
- Expensive boundaries:
  - IPC/serialization at <code>src/vs/workbench/api/browser/mainThreadGitExtensionService.ts:168 $onDidChangeRepository</code>: Fetches and converts one full repository-state snapshot after a Git state event.; cardinality: One RPC per state-change event, with payload proportional to changed/indexed/untracked entries.
    - Introduced by diff: false; previous behavior: The same event-driven state fetch and observable update occurred.; critical-path effect: Consumers update after the snapshot returns; this path existed unchanged before the PR.
- Verdict: No reportable regression: stable identity prevents replacement churn, notifications are bounded by live observers, and no concrete leak or new external work is introduced.

**Summary:** Completed the performance pass over all three changed files and traced repository open/reopen, state propagation, session changeset resolution, GitHub metadata resolution, and automation branch loading through IPC, filesystem, and Git subprocess boundaries. The change reuses one main-thread wrapper per handle and performs an in-process state refresh; it does not increase expensive-boundary cardinality, concurrency, or retained wrapper count. No high-confidence diff-introduced performance issue was found.
