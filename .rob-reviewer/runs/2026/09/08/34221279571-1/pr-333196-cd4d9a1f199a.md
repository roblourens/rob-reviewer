# Performance review: chat: add customization migration assessment telemetry

[PR #333196](https://github.com/microsoft/vscode/pull/333196) at `cd4d9a1f199af5462d0e97190012a87f28eca618`

## Findings (1)

### 1. [medium] Cancel queued migration assessments when restore is abandoned

**Finding ID:** `PERF-965773D04187`  
**Location:** <code>src/vs/sessions/services/sessions/browser/sessionsService.ts:939</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Queued filesystem/extension-provider discovery, customization scans, and per-root MCP support assessment work.  
**Scaling:** Wasted work grows with the number of persisted visible sessions still running or queued at cancellation, and within each assessment with customization-file candidates and configured MCP servers; the limiter caps concurrency at two but does not reduce total stale work.  
**Outcome:** Excessive stale I/O and CPU contention after navigation cancels startup restore.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, restoring or abandoning persisted sessions performed no migration telemetry assessments, so cancellation left no assessment queue to drain.  
**Changed behavior:** Startup restore now queues a full customization migration assessment for every restored session. Although each enqueue receives the restore cancellation token, queued and running factories discard it once admitted by the limiter.  
**Confidence:** 0.98 — The call flow is explicit: restore schedules one task per resolved session; explicit navigation calls \`\_cancelRestore\`; \`Limiter\` retains outstanding factories until consumed; and the changed callback omits the token even though the helper supports it. The assessment's file discovery, source-folder scans, and MCP support resolution are directly visible in \`CustomizationMigrationService\`. Exact milliseconds vary with customization and MCP counts, but cancellation failure and scaling are certain.

**Causal diff evidence:** The diff adds one \`\_reportCustomizationMigrationTelemetry(..., token)\` enqueue for every session restored at RIGHT lines 1590 and 1638, but the newly added limiter callback at RIGHT line 939 invokes \`reportCustomizationMigrationTelemetry\` without that token, so it uses \`CancellationToken.None\`.

If the user opens a session while startup is restoring several persisted sessions—especially while agent/customization state is cold—all stale restore assessments continue in the background. They consume filesystem/extension-provider I/O and MCP assessment CPU after the restore was abandoned, contending with the newly opened session and prolonging post-navigation activity.

**Evidence:** \`\_cancelRestore()\` cancels the restore token specifically so explicit opens bail out of cold restore work. \`\_reportCustomizationMigrationTelemetry\` checks that token only before \`Limiter.queue\`; once queued, line 939 calls the helper without it. \`Limiter\` does not inspect cancellation and drains all outstanding factories. Each factory calls \`computeMigrations\`, which lists prompt files for multiple types, queries source folders for candidate types, and creates a per-working-directory MCP support scope that resolves all MCP servers/configuration. Therefore cancellation while two tasks run leaves both running and every queued session assessment still starts afterward.

**Suggested direction:** Recheck the restore token inside the limiter factory and pass it to \`reportCustomizationMigrationTelemetry\`; make the MCP assessment wait cancellation-aware as well so already-running work releases its scope promptly. This preserves the concurrency limit and telemetry for restores that remain active while dropping only superseded work.
