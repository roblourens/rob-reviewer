### Scenario 1: Desktop startup and policy-definition registration with native managed settings

- Critical path: Policy configuration submits changed definitions through renderer/main-process IPC; native watcher creation and its initial callback must complete before the update resolves. The background initial native-settings read is otherwise not always on UI startup's critical path.
- Scaling input: Number of registered managed-setting definitions (tens in normal use) and number of definition-change events during contribution registration; equality checks suppress unchanged replacements.
- Effective concurrency: Definition updates cross IPC and are serialized by the native service Throttler; each replacement keeps only one active watcher and callbacks from superseded versions are ignored.
- Cache behavior: The client memoizes initializationPromise and the service skips replacement when definitions are deeply equal. A changed definition rebuilds the watcher; there is no separate cold data cache. The pending initial callback list exists only during synchronous watcher creation and remains bounded by watcher initialization callbacks.
- Mechanism confidence: High confidence from the IPC client, equality guards, Throttler, and watcher replacement implementation.
- Magnitude uncertainty: Exact native watcher creation cost and frequency of dynamic contribution registration vary by platform, but the changed work is bounded and serialized.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/policy/common/nativeManagedSettingsIpc.ts:94 NativeManagedSettingsChannelClient.updatePolicyDefinitions</code>: Send policy definitions from the workbench client to the main-process native managed-settings service and return current values.; cardinality: One IPC call per distinct submitted definition batch; unchanged policy definitions are filtered by PolicyConfiguration and equal aggregate definitions are skipped by the native service.
    - Introduced by diff: false; previous behavior: The same definition updates crossed IPC and were awaited before this PR.; critical-path effect: The call is awaited before policy configuration/account policy refresh completes.
  - other expensive boundary at <code>src/vs/platform/policy/node/nativeManagedSettingsService.ts:134 updateWatcher</code>: Create/replace the &#64;vscode/policy-watcher native watcher, which reads OS-managed policy storage and subscribes for changes.; cardinality: Normally one native watcher creation per distinct definition set. - Verdict: No reportable regression: normal 1.5 watcher creation cardinality is unchanged; the legacy fallback is a one-time bounded retry, and transactional replacement avoids leaked or concurrently active watchers.

### Scenario 2: Managed-settings refresh and selective prompt/agent/skill/hook discovery

- Critical path: Server responses or managed-settings file changes are normalized, projected, and applied to configuration. Prompt filesystem discovery/parsing occurs later on demand after cache invalidation; selected blocked surfaces return before discovery.
- Scaling input: Managed-settings object size (file capped at 1 MB), selector array size (canonical schema has four selectors), number of prompt source folders/files on an allowed surface, and number of policy refreshes.
- Effective concurrency: File refreshes are coalesced by a 500 ms ThrottledDelayer. Prompt file parsing uses the existing discovery queue/Promise.all behavior; the selector checks add only bounded in-process scans.
- Cache behavior: Prompt location and custom-agent caches are invalidated on a relevant configuration change. Cold access rediscovers allowed surfaces; warm access uses existing CachedPromise/location caches. Selected blocked surfaces short-circuit before filesystem work.
- Mechanism confidence: High confidence from normalization, file refresh coalescing, prompt cache invalidation, and early discovery gates.
- Magnitude uncertainty: Enterprise prompt collections and refresh cadence vary, but the added selector processing is bounded by a four-value domain and does not multiply filesystem operations.
- Expensive boundaries:

### Scenario 3: MCP collection visibility, connection resolution/start, and live policy tightening

- Critical path: A server start is sequenced per McpServer, may activate an extension, prompt for trust, read stored inputs/secrets, resolve variables, and prepare sandbox launch before creating the connection. The diff revalidates collection identity and policy after those awaits and before connection creation. Live policy changes synchronously recompute derived state and may dispose a running connection.
- Scaling input: Number of registered MCP collections for lookup, definitions in the selected collection, simultaneously starting servers, and frequency of enterprise policy/configuration changes.
- Effective concurrency: Starts for one server are serialized by \_connectionSequencer; separate servers may resolve concurrently. Existing trust interaction coalesces participants, while the added final check is local and does not fan out boundaries.
- Cache behavior: Lazy collections load only when needed and cached lazy collections are skipped by discovery. Existing stored variable/input maps and cached server metadata remain unchanged. Policy checks read current observable/config values without a new cache.
- Mechanism confidence: High confidence from McpServer.start sequencing, resolveConnection call flow, observable collection filtering, and the post-await checks.
- Magnitude uncertainty: Very large installations may have more collections and concurrent server starts, but the added post-resolution work is one linear in-memory lookup plus membership/policy checks per start, dwarfed by existing awaited boundaries.
