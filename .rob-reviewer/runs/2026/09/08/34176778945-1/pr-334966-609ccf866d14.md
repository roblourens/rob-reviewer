**Relevant issue families:** eager-work, repeated-work, synchronous-ui-work, cleanup-lifecycle

### Scenario 1: Open the Agents Window with ordinary code editors, query editors, and other embedded editors

- Critical path: The new module is loaded with the Sessions search contribution, and the contribution is instantiated for each code editor after first render during idle time (or within the framework's 50 ms fallback). It is not on the initial-render critical path.
- Scaling input: Number of simultaneously instantiated code editors in the Agents Window; contribution construction is once per editor.
- Effective concurrency: Each editor schedules its own idle callback; contribution construction and listener registration execute synchronously on the renderer thread, without a new queue or parallel boundary.
- Cache behavior: observableCodeEditor uses a process-local map keyed by editor, so an existing facade is reused; on a cold editor it creates one facade, while later requests are warm. The map entry and listeners are removed when the editor is disposed.
- Mechanism confidence: High: registration is global to code editors in the Sessions bundle and AfterFirstRender semantics are explicit; the actual work and lifecycle are directly visible.
- Magnitude uncertainty: The number of embedded editors varies, but the added per-editor work is bounded to one contribution/autorun and reuse of a cached observable facade; no heavyweight model, I/O, serialization, or DOM subtree is created for non-search models.
- Expensive boundaries: none found
- Verdict: No reportable regression. There is small eager per-editor bookkeeping, but it is deferred beyond first render, bounded, cached, disposed with editor lifetime, and lacks a concrete user-visible performance outcome.

### Scenario 2: Open or restore a Sessions Search editor with empty, populated, no-results, or restored content

- Critical path: After the search result model is attached, the autorun reads the model scheme and O(1) value length. Only an empty SearchEditor model synchronously creates a three-element empty-state DOM subtree and one overlay; populated/no-results models do not create it.
- Scaling input: Search-result model content changes. The observer runs once per version change, performs a constant-time length check, and creates/removes one fixed-size overlay only when transitioning through empty content.
- Effective concurrency: Search submissions remain coalesced by the existing RunOnceScheduler/delayer and existing search cancellation. Empty-state updates are synchronous reactive callbacks on model changes and introduce no additional concurrency.
- Cache behavior: The observable editor facade is shared per editor. The overlay is retained only while the current SearchEditor model is empty and is disposed on content/model change or contribution/editor disposal; there is no result cache or retained history.
- Mechanism confidence: High: the model/version dependencies, scheme guard, fixed DOM creation, and disposal through reader.store are explicit, and the existing search boundary call path was inspected.
- Magnitude uncertainty: Search result sizes and providers vary, but the diff does not alter search cardinality, result serialization, or boundary traffic; its incremental work remains constant per model event.
- Expensive boundaries:

  - filesystem at <code>src/vs/workbench/contrib/searchEditor/browser/searchEditorInput.ts:278</code>: Existing persisted Search editor model resolution/revert may read a saved search file or working-copy backup.; cardinality: At most one existing resolve/read for the SearchEditor input being opened or reverted.

- Verdict: No reportable regression. The change adds only bounded constant-time observation and a fixed DOM subtree, without increasing existing search I/O, serialization, or concurrency.

### Scenario 3: Resize or relayout an empty Sessions Search results editor

- Critical path: The existing SearchEditor layout synchronously computes query/results dimensions; after the editor emits its layout event, the new nested autorun writes the already-provided width and height to the overlay styles. This is on the resize/layout path but performs no geometry read.
- Scaling input: One pair of style writes per emitted editor layout event while the results model is empty; independent of workspace size and search-result count.
- Effective concurrency: Fully synchronous on the renderer thread and serialized with editor layout events; no timers, tasks, or fan-out are added.
- Cache behavior: The layout observer exists only while the empty overlay exists and is disposed when content becomes non-empty, the model changes, or the contribution is disposed.
- Mechanism confidence: High: layoutInfo is event-backed and the callback only assigns CSS width/height; the overlay CSS uses flex centering without queried geometry.
- Magnitude uncertainty: Resize event frequency depends on user interaction, but the changed callback has fixed work and does not force a read-after-write layout cycle in the traced code.
- Expensive boundaries: none found
- Verdict: No reportable regression. The resize work is bounded, scoped to the empty state, and does not establish forced synchronous layout or dropped-frame risk.

**Summary:** Reviewed all six changed files and traced global editor-contribution instantiation, SearchEditor model/search flow, overlay lifecycle, and resize behavior. No high-confidence actionable performance regression was introduced, and the PR does not fix a traced prior performance regression.
