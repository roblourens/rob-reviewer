### Scenario 3: An assignment transition changes chat.agentMerge.enabled while VS Code and Agent Host are running

- Critical path: After an existing TAS refetch, the defaults contribution applies one changed experimental default. Each connected Agent Host client mirrors one key in one RootConfigChanged action. - Scaling input: Number of connected Agent Host clients/windows, loaded session URIs, and persisted sessions explicitly indexed as Agent Merge enabled. The restore does not enumerate the full session registry and limits materialization concurrency to four.
- Effective concurrency: Configuration refetches are Throttler-serialized. Root-config writes are chained serially. Persisted-session restore is serialized through \_agentMergeRestore and bounded by Limiter(4). Per-host loaded-session notification/reconciliation loops are synchronous but occur only on an actual treatment transition.
- Cache behavior: Treatment values come from the refreshed in-memory TAS state. Identical treatments are suppressed; only a changed value reaches the bridge. The persisted enabled-session index narrows restore work, and already-materialized sessions are skipped.
- Mechanism confidence: High: the changed line makes runtime assignment transitions authoritative for this setting, and the traced bridge, persistence, loaded-session loops, indexed restore, limiter, and background GitHub refresh are explicit.
- Magnitude uncertainty: The number of open windows and explicitly monitored sessions varies, and treatment transitions are remotely controlled; exact I/O cost is therefore deployment-dependent. Effective cardinality is nevertheless bounded to connected clients and the indexed monitored-session set.
