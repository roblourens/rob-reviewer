### Scenario 1: Open an Agent Host session or chat from a product-protocol browser link in an already-running application

- Critical path: The main process parses the URL, awaits openAgentsWindow (including ensuring the Agents workspace and creating a renderer), sends one handoff IPC, the Agents renderer waits for LifecyclePhase.Eventually, resolves the target from loaded sessions, optionally awaits one provider connection, then opens the chat. All of this is on the requested navigation's critical path.
- Scaling input: One invocation per clicked protocol link; resolution scans the currently merged, deduplicated session list once initially and again only on session/resolution events during the bounded 15-second wait
- Effective concurrency: A single invocation sequences window creation, IPC readiness, session resolution, optional connection, and chat opening. Separate protocol invocations can create separate windows, consistent with the existing openAgentsWindow contract; no diff-added per-item concurrency occurs.
- Cache behavior: Warm Agents workspace avoids the file write but still performs one existence check. Already-loaded sessions avoid the wait, and already-connected providers avoid the network connection. Cloud provider connection attempts are coalesced by address in their existing pending-connect map.
- Mechanism confidence: High: the changed main-process branch, existing openAgentsWindow implementation, renderer IPC handler, and optional provider.connect call establish the complete path.
- Magnitude uncertainty: Renderer startup and remote connection duration vary by machine and provider, but their cardinality is one per explicit navigation rather than scaling with session count.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/windows/electron-main/windowsMainService.ts:ensureAgentsWindow</code>: Check whether the Agents workspace file exists and create it only if absent; cardinality: One existence check per opened external link; one write only on the first cold use when the workspace file is absent
    - Introduced by diff: true; previous behavior: This external Agent Host link shape was not routed to openAgentsWindow, so this link-specific path did not perform the check; critical-path effect: The check, and cold-only write, complete before the Agents window can open
  - subprocess at <code>src/vs/code/electron-main/app.ts:handleProtocolUrl -&gt; IWindowsMainService.openAgentsWindow</code>: Create a dedicated Agents renderer window; cardinality: One window-open request per external link invocation
    - Introduced by diff: true; previous behavior: External Agent Host links were not recognized and did not launch the dedicated Agents window; critical-path effect: The destination window must become ready before the session handoff can be consumed
  - IPC at <code>src/vs/platform/windows/electron-main/windowsMainService.ts:openAgentsWindow</code>: Send the parsed internal session URI and source to the Agents renderer; cardinality: One sendWhenReady message per successfully opened window
    - Introduced by diff: true; previous behavior: No Agent Host link handoff IPC existed for this URL shape; critical-path effect: Carries the target after renderer readiness; no per-session fan-out
  - network at <code>src/vs/sessions/contrib/chat/electron-browser/chat.contribution.ts:resolveAndOpenSessionLink</code>: Connect the owning remote Agent Host provider when the linked cached session is found but its host is disconnected; cardinality: Zero for local/already-connected sessions; at most one provider.connect call for the resolved session
    - Introduced by diff: true; previous behavior: The external-link path did not exist; ordinary session opening used its existing provider connection flow; critical-path effect: Awaited before opening the chat so remote session state is available; failures still proceed to the seeded session
- Verdict: No reportable regression. The expensive boundaries implement the requested navigation and are bounded to one logical window/target rather than fanning out across sessions or providers.

### Scenario 2: Cold application startup from an Agent Host product-protocol link

- Critical path: openFirstWindow identifies the first matching Agent Host URL, opens the Agents workspace as the initial window, sends one target IPC when ready, and follows the same lifecycle/session-resolution path as the running-app scenario.
- Scaling input: The initial protocol URL list is scanned linearly until the first match; realistic startup lists are small, and only one Agent Host URL is selected for initial-window creation.
- Effective concurrency: Initial window creation is serialized. Provider initialization can emit events, but each retry is synchronous in-memory lookup and only the resolved provider may connect.
- Cache behavior: Workspace-file creation is cold-only. Session lookup uses provider-loaded in-memory sessions; disconnected identities are resolved from provider policies, and the wait is bounded to 15 seconds.
- Mechanism confidence: High for the startup path and boundary cardinality.
- Magnitude uncertainty: Cold renderer and provider initialization time is platform-dependent; no changed multiplicative boundary was found.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/windows/electron-main/windowsMainService.ts:ensureAgentsWindow</code>: Check/create the Agents workspace before opening it; cardinality: One existence check and at most one cold write
    - Introduced by diff: true; previous behavior: Startup did not specially route this URL to the Agents workspace; critical-path effect: Blocks initial Agents-window creation
  - subprocess at <code>src/vs/code/electron-main/app.ts:openFirstWindow -&gt; IWindowsMainService.openAgentsWindow</code>: Start the initial Agents renderer window; cardinality: One initial renderer for the selected Agent Host URL
    - Introduced by diff: true; previous behavior: The application followed its normal initial-window/protocol handling instead of selecting the Agents window for this link; critical-path effect: This is the destination UI and therefore necessarily on startup's critical path
  - IPC at <code>src/vs/platform/windows/electron-main/windowsMainService.ts:openAgentsWindow</code>: Deliver the target session link to the initial renderer; cardinality: One handoff after the renderer is ready
    - Introduced by diff: true; previous behavior: No Agent Host session-target handoff occurred; critical-path effect: Required for selecting the requested session after startup
  - network at <code>src/vs/sessions/contrib/chat/electron-browser/chat.contribution.ts:resolveAndOpenSessionLink</code>: Optionally connect one disconnected remote provider for the resolved target; cardinality: At most one provider connection after the target session resolves
    - Introduced by diff: true; previous behavior: No startup Agent Host-link target existed; critical-path effect: Awaited before opening the requested remote chat
- Verdict: No reportable regression. The new startup work is the single requested destination window and target handoff, with no per-URL or per-session external fan-out.

### Scenario 3: Resolve and refresh internal Agent Host rich links as session providers or sessions change

- Critical path: Each actively observed, canonically shared link watcher recomputes its presentation on session-change events by building the merged/deduplicated session array and finding the matching backend identity. This is synchronous renderer CPU work but has no IPC, filesystem, database, subprocess, or network boundary.
- Scaling input: CPU scales with distinct observed link resources times effective deduplicated session count per session-change event. Remote identity resolution also scans known connection/policy authorities; provider counts are lifecycle-bounded and generally much smaller than sessions.
- Effective concurrency: Observable recomputation is synchronous and serialized on each event. Shared watchers coalesce duplicate rendered links with the same canonical resource.
- Cache behavior: Link-presentation watchers are shared by canonical provider/resource key in DataChannelService and disposed when the last consumer releases them. Identity policies are held in a map and removed with their owning provider. There is no negative result cache, but recomputation is event-driven rather than polled.
- Mechanism confidence: High for the scan and watcher sharing; low for any material regression magnitude because the dominant scan and event path predate the change.
- Magnitude uncertainty: Large histories can contain many distinct links, but the PR replaces an existing full-session scan and existing remote-authority resolution rather than adding a new per-frame or per-message boundary. The added Set/policy participation is insufficient by itself to establish user-visible latency.
- Expensive boundaries: none found
- Verdict: No finding. The change enables disconnected identity matching and modestly expands in-memory authority work, but does not high-confidence introduce or materially amplify an expensive boundary or hot-path cost.

### Scenario 4: Copy an Agent Host session or chat browser link from a context menu

- Critical path: The context menu action resolves the selected session identity in memory, formats one URL, and awaits one clipboard write.
- Scaling input: Constant work per explicit menu invocation; identity resolution scans known authorities only for a remote session resource.
- Effective concurrency: One awaited clipboard write per command; no loop or fan-out.
- Cache behavior: No cache is needed for a one-shot command. Provider resolution policies remain provider-scoped and are disposed with providers.
- Mechanism confidence: High.
- Magnitude uncertainty: Clipboard latency is platform-dependent but cardinality is fixed and user initiated.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/agentHostSessionBranchActions.ts:CopyAgentHostSessionLinkAction.run / CopyAgentHostChatLinkAction.run</code>: Write the generated URL to the system clipboard through IClipboardService; cardinality: Exactly one clipboard write per explicit Copy Link command
    - Introduced by diff: true; previous behavior: The Copy Link command did not exist, so there was no clipboard write; critical-path effect: The command completes after the clipboard write
- Verdict: No reportable regression. The single clipboard boundary is the direct requested effect and does not scale with chats or sessions.

### Scenario 5: Register and dispose remote Agent Host session-resolution policies

- Critical path: Remote provider construction inserts one in-memory policy and emits one resolution-change event; provider disposal removes it and emits once. This occurs during provider lifecycle, not on every render or input event.
- Scaling input: One map entry and registration/removal event per live remote provider. Providers are keyed by configured/discovered remote host or sandbox environment.
- Effective concurrency: Provider reconciliation is synchronous; registrations are individual but perform no external I/O and no asynchronous burst.
- Cache behavior: The policy map is authoritative identity metadata rather than a cache. Each registration disposable is owned by the provider, so entries are removed when providers are reconciled away.
- Mechanism confidence: High: constructor registration and Disposable ownership are explicit.
- Magnitude uncertainty: Users may have multiple cached tunnels or sandbox environments, but each contributes one small object with explicit lifecycle cleanup.
- Expensive boundaries: none found
- Verdict: No unbounded-retention or startup regression. The previously conditional registration is now one bounded map entry per provider and is required for disconnected identity resolution.
