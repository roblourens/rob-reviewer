# Performance review: Hide repository controls for new chats in a session

[PR #334965](https://github.com/microsoft/vscode/pull/334965) at `5053699fb8c54efa4eaf5ac4dd6ea0d377fc961c`

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** eager-work, synchronous-ui-work, cleanup-lifecycle

### Scenario 1: Open a new-chat composer inside an existing session

- Critical path: NewChatView synchronously creates NewChatInSessionWidget, which creates and renders NewChatInputWidget before the composer is usable. The new renderRepositoryControls=false option is checked during render and skips MenuWorkbenchToolBar construction for Menus.NewSessionRepositoryConfig; this is on the critical path but removes work rather than adding it.
- Scaling input: One repository toolbar and its bounded menu/action-view items per open in-session composer; multiplicity scales with concurrently retained chat views, not repository count or history size.
- Effective concurrency: Synchronous UI construction per NewChatView; there is no added queue, fan-out, or parallel boundary work. Normally one visible composer is rendered per view.
- Cache behavior: Menu/context-key lookup is local. The change does not add a cache, alter keys, create cold/warm divergence, or require request coalescing; it avoids the lookup and action-view construction entirely for this composer.
- Mechanism confidence: High: the added false option reaches the added conditional directly, and MenuWorkbenchToolBar construction, menu listeners, and provider action-view creation are skipped.
- Magnitude uncertainty: Exact allocation and listener savings depend on which provider-specific menu entries are active, but the direction is strictly reduced work and retained UI state.
- Expensive boundaries: none found
- Verdict: No performance regression. The change reduces eager DOM objects, menu evaluation, listeners, and picker instances on the composer startup path.

### Scenario 2: Resize the in-session composer or grow its attachment row

- Critical path: CSS now makes new-chat-widget-content positioned, so the existing attachment ResizeObserver's getBoundingClientRect read and parent.style.top write visibly offset the centered composer. ResizeObserver callbacks and flex layout run on the UI rendering path; no external operation must complete.
- Scaling input: One observed attachment row per composer, with callback frequency driven by attachment-row size changes and resize notifications; observer delivery batches size changes rather than scaling into per-repository or per-history work.
- Effective concurrency: One browser ResizeObserver callback stream per widget on the UI thread; no added parallelism, queue, IPC, or unbounded scheduling.
- Cache behavior: No cache is involved. Geometry is read from the live DOM for each delivered resize, as before the diff.
- Mechanism confidence: High for the CSS/observer interaction; low evidence of harmful magnitude because the read/write callback pre-existed and the change only makes its intended offset effective.
- Magnitude uncertainty: The exact layout/paint cost varies by attachment content and viewport, but each event touches a single small composer subtree and does not create a feedback resize loop because relative top positioning does not change the observed row's dimensions.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added positioning can add bounded local paint/compositing work when the row changes size, but it is not a scaling or repeated-work mechanism with realistic user-visible impact.

### Scenario 3: Open the existing new-session composer with repository controls

- Critical path: NewChatWidget still creates NewChatInputWidget without renderRepositoryControls, so the new condition evaluates true and constructs the repository MenuWorkbenchToolBar exactly as before. The scoped CSS does not apply outside new-chat-in-session.
- Scaling input: One toolbar per new-session composer with a bounded number of provider menu entries; effective cardinality is unchanged by the diff.
- Effective concurrency: Unchanged synchronous widget/menu construction per view; no new fan-out or concurrency.
- Cache behavior: Unchanged local menu/context-key behavior; no cache lifecycle, key, miss, or coalescing behavior changes.
- Mechanism confidence: High: the only caller passing false is NewChatInSessionWidget, while NewChatWidget leaves the option undefined and therefore retains the toolbar.
- Magnitude uncertainty: Provider-specific picker internals vary, but the default-true condition demonstrably preserves the pre-diff construction path.
- Expensive boundaries: none found
- Verdict: No performance regression. Existing new-session startup and repository-control behavior remain unchanged.

**Summary:** Reviewed all four changed files and traced composer construction, menu/action-view creation, responsive layout, attachment resize handling, disposal ownership, and unchanged callers. No high-confidence diff-introduced performance issue was found; the primary production effect is removal of eager repository-control UI work from in-session composers.
