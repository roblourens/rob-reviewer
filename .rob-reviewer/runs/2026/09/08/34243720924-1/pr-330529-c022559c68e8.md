# Performance review: agentHost: add session and chat rename tools

[PR #330529](https://github.com/microsoft/vscode/pull/330529) at `c022559c68e8846c60fc37c67732ad52e6d8de2a`

## Findings (5)

### 1. [medium] Check title eligibility before materializing the whole prompt

**Finding ID:** `PERF-455073BB7F77`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionTitleController.ts:174</code> (<code>RIGHT</code>)  
**Performance category:** <code>gc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Per-code-point JavaScript array entries, copied arrays/strings, and synchronous CPU work  
**Scaling:** The temporary allocation and traversal grow linearly with the full user-prompt length on every ChatTurnStarted, even though at most 40 or 200 code points can become a title and most turns are rejected as no longer eligible only afterward.  
**Outcome:** Large pasted prompts create avoidable CPU and GC pressure and can pause synchronous turn dispatch before provider work starts.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The previous normalization collapsed whitespace and used string slice(0, 200); it did not allocate an array element for every code point. There was also no active-mode helper that slices and rejoins the entire suffix.  
**Changed behavior:** Normalization now calls Array.from over the entire normalized prompt before taking the bounded prefix. Active mode additionally creates \`characters.slice(40).join('')\` and may convert the crossing word again. seedTitleFromFirstMessage is called for every user turn and performs this work before checking \`\_canSeedFirstMessageTitle\`.  
**Confidence:** 0.99 — The synchronous call path, ordering before eligibility, and unbounded Array.from/slice/join allocations are explicit. Prompt prevalence affects severity, not the mechanism.

**Causal diff evidence:** The changed return expression at line 174 replaces the bounded string slice with \`Array.from(...).slice(...)\`; the newly added active helper similarly materializes the whole prompt and suffix before the eligibility check later in seedTitleFromFirstMessage.

A multi-megabyte pasted log or generated prompt can produce a multi-megabyte array of per-code-point strings plus copied suffixes on the event-loop path, increasing turn-start latency and GC pauses.

**Evidence:** AgentSideEffects.handleAction calls seedTitleFromFirstMessage synchronously for every ChatTurnStarted. In that method fallbackTitle is normalized before state and turn-count eligibility are checked, so a long prompt on an already-titled conversation still incurs the full new allocation.

**Suggested direction:** Move the state/turn eligibility check ahead of normalization, then collect code points with a bounded iterator that stops after the title cap (and only scans enough to finish the crossing word) instead of materializing the full prompt.

### 2. [medium] Skip prompt serialization when no plugin hook consumes it

**Finding ID:** `PERF-7561AC60CCB9`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotPluginConverters.ts:438</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** A full JSON string copy of each Copilot UserPromptSubmittedHookInput plus serialization CPU  
**Scaling:** Cost grows linearly with prompt bytes and repeats for every Copilot turn, including sessions with no UserPromptSubmit plugin commands and turns with no rename instruction.  
**Outcome:** Every Copilot prompt pays additional CPU, allocation/GC, and awaited hook latency before model processing.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Without configured UserPromptSubmit commands, no onUserPromptSubmitted handler was installed and the prompt input was not JSON.stringify'd by this converter.  
**Changed behavior:** The broadened condition installs the handler whenever the internal callback exists. CopilotSessionLauncher now always supplies that callback, so the handler unconditionally JSON.stringify's input before iterating an empty command list, even when handleUserPromptSubmitted returns undefined.  
**Confidence:** 0.99 — The always-provided callback and unconditional serialization path are directly visible; only the exact prompt-size distribution is uncertain.

**Causal diff evidence:** The changed condition at line 438 adds \`\|\| editTrackingHooks?.onUserPromptSubmitted\`; the launcher always passes this callback, making the unchanged \`const stdin = JSON.stringify(input)\` newly reachable for ordinary prompts.

Long prompts are copied and serialized on every Copilot turn for no consumer, increasing prompt-submit latency and transient heap usage.

**Evidence:** CopilotSessionLauncher supplies onUserPromptSubmitted for every launched session. In the handler, serialization occurs before \`for (const cmd of promptCommands ?? \[\])\`, while the callback only joins optional host instructions and commonly returns undefined after rename or when active naming is disabled.

**Suggested direction:** Only create \`stdin\` inside a \`promptCommands?.length\` branch, then invoke the internal additional-context callback separately without serializing the SDK input.

### 3. [medium] Avoid listing every session to rename the current one

**Finding ID:** `PERF-2003155A41A9`  
**Location:** <code>src/vs/platform/agentHost/node/shared/sessionServerTools.ts:825</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Registry SQLite queries, per-session provider SDK/IPC lookups, filesystem existence checks, and per-session metadata queries  
**Scaling:** Each current-session rename scales with the total registered session history S, issuing one global registry read plus concurrent provider and metadata work for each of the S sessions instead of O(1) work for the current session.  
**Outcome:** The rename tool response and therefore the first active-agent response are delayed, while large histories cause a burst of SDK and filesystem/database work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, first-turn title handling did not invoke a full session listing; catalog enumeration occurred only in tools/workflows that actually needed a catalog.  
**Changed behavior:** Every rename\_session invocation now awaits accessor.listSessions() before resolving the target, including the normal reminder-driven call where session is omitted and currentSession already identifies the target. rename\_chat repeats the same pattern for the current peer chat.  
**Confidence:** 0.99 — The unconditional added call, the reminder's current-session usage, and the full listSessions call path are directly traced. Exact duration varies by provider/cache state, but the O(S) boundary fan-out and its placement on tool completion are certain.

**Causal diff evidence:** The added line \`const sessions = await accessor.listSessions();\` runs unconditionally in applyRenameSessionTool before getRenameSessionArgs can take its currentSession branch; the analogous added call is present in applyRenameChatTool.

With tens or hundreds of stored Copilot/Claude/Codex sessions, the automatic rename requested during a new session's first response waits for unrelated sessions' SDK and disk metadata. The Promise.all loops also issue those per-session operations as a concurrency burst.

**Evidence:** AgentService.listSessions first reads the global session registry, then Promise.all-maps every registered session through provider getChatMetadata and default-chat provider-data reads, and then Promise.all-maps the resulting catalog through tryOpenDatabase/getMetadataObject. SessionDataService.tryOpenDatabase itself performs a filesystem exists check. Thus the ordinary current-target rename introduced here fans out across the entire stored history.

**Suggested direction:** Resolve omitted/current targets from the current channel and live session state through a targeted accessor; only enumerate the catalog when an explicit cross-session target must be validated. If project-title normalization needs metadata, expose a targeted current-session metadata lookup rather than listing all sessions.

### 4. [low] Persist automatic title provenance only once

**Finding ID:** `PERF-3F00B654518C`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionTitleController.ts:213</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SQLite INSERT OR REPLACE operations and database references  
**Scaling:** The added writes scale with every automatic fallback/generated title phase and peer chat: a normal utility-generated title now causes four metadata writes across fallback and final application instead of the previous single final-title write; provisional flows add still more.  
**Outcome:** Excessive serialized SQLite I/O increases background load and lengthens session idle/deletion drains.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Applying an in-memory fallback did not write metadata; once utility generation completed, only the final title was persisted once.  
**Changed behavior:** Each \`\_applySeedTitle\` now persists the auto source immediately, while the subsequent active \`markTitleAuto\` or utility completion \`\_persistAutoTitle\` persists that same source again alongside the title. Each call opens/acquires a database reference and queues a separate setMetadata write.  
**Confidence:** 0.98 — The exact call sequence and duplicate key writes are explicit in the controller. They are off the immediate send await chain, so severity is low, but the I/O amplification is certain.

**Causal diff evidence:** The added \`\_persistAutoTitleSource\` call at line 213 (and its session branch counterpart) writes provenance during in-memory application, duplicating the source write already added in \`\_persistAutoTitle\`.

Creating/titling many sessions or peer chats generates multiple redundant disk writes per title and can delay cleanup that waits for SessionDatabase.whenIdle.

**Evidence:** For utility mode, seedTitleFromFirstMessage applies the fallback (one source write), then generated-title apply writes source again and its persist callback writes title plus source, totaling four INSERTs versus the old one. SessionDatabase now globally sequences metadata writes, and dispose/eviction waits for pending database work.

**Suggested direction:** Keep \`\_applySeedTitle\` in-memory-only and persist title plus source once at the durable persistence point, preferably through the new atomic setMetadataValues helper.

### 5. [low] Use cached title provenance before reading the session database

**Finding ID:** `PERF-EF39572439FF`  
**Location:** <code>src/vs/platform/agentHost/node/agentSideEffects.ts:2033</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Filesystem existence checks and SQLite metadata reads  
**Scaling:** At least one stat/query pair is added for every newly auto-titled session or peer chat, and it repeats once per sent turn until a rename succeeds because persisted \`auto\` provenance is not cached as a resolved state.  
**Outcome:** Cold or contended storage delays checkpointing, provider dispatch, and time to first model response.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Turn dispatch proceeded from attachment resolution to checkpoint capture and provider send without reading title provenance from disk.  
**Changed behavior:** Every active-naming send now awaits prepareInstructionForAgent. That method reads persisted provenance before consulting the already-populated \`\_autoTitles\` set; for restored auto titles it also does not cache the \`auto\` result, so subsequent turns repeat the lookup until renamed.  
**Confidence:** 0.98 — The awaited critical path and both boundary operations are directly traced, and the in-memory auto provenance is set before this call. Storage latency magnitude varies, hence low severity.

**Causal diff evidence:** The added awaited call at line 2033 places title-provenance resolution directly on \`\_sendTurnMessage\`'s critical path before captureTurnStartCheckpoint and agent.chats.sendMessage.

Every new active-agent conversation waits for local filesystem and database boundaries before its first request can reach Copilot, Claude, or Codex; failures to rename repeat the delay on later turns.

**Evidence:** prepareInstructionForAgent calls \`\_readPersistedTitleSource\` first, and SessionDataService.tryOpenDatabase performs \`\_fileService.exists\` before the controller issues getMetadata. New-session seeding has already called markTitleAuto, so the disk lookup is provably unnecessary for that common first send.

**Suggested direction:** Return the reminder directly when \`\_autoTitles\` contains the key. For restored sessions, cache the persisted user/agent/auto source after the first read (or hydrate provenance during restore) so later turns do not hit disk.

### Scenario 2: Agent calls rename\_session for the current session or rename\_chat inside the current peer chat

The full catalog listing and rename transaction both must finish before the agent can continue/finalize.
- Scaling input: Total registered top-level sessions S across all providers; explicit current-target calls normally need one session/chat. For rename\_chat, peer catalog size C matters only if the chat is not live and existence falls back to persisted catalog lookup.
- Effective concurrency: AgentService uses Promise.all over all registered sessions for provider metadata and again for per-session overlays, producing up to O(S) concurrent provider/filesystem/database operations. The final two title writes are serialized inside one SQLite transaction.
- Cache behavior: The global registry is queried each call. Live state is overlaid only after provider and persisted metadata have already been fetched. Per-session \`tryOpenDatabase\` always performs an existence check; there is no catalog result cache/coalescing for repeated rename calls.
- Mechanism confidence: High: the unconditional listSessions call and its two O(S) Promise.all stages are directly traced; currentSession/currentChannel already identify the normal target.
- Magnitude uncertainty: The number of stored sessions and provider SDK cost vary. Warm SDK/database state may reduce duration, but every call still scales with S and issues the per-session existence/metadata work.

### Scenario 3: Create, fork, import, restore, or provisionally title a session/chat while utility-model naming is disabled or enabled

- Critical path: Title fallback application is synchronous. Utility-model generation when active naming is disabled is delayed/coalesced and off the initial send path; active mode skips that network call. Metadata persistence is fire-and-forget, except authoritative agent rename transactions. Fork/create provider metadata stores may await their own writes before materialization completes.
- Scaling input: Number of newly titled sessions/chats T and automatic title phases per target; provider overlay field count is bounded (roughly 1-10 keys), while imported conversation context is separately capped by existing title-context limits.
- Effective concurrency: Automatic title metadata writes are now globally serialized per SessionDatabase. Utility title generation remains one coalesced/cancellable request per title key. Provider overlay callers use Promise.all, although the changed global metadata sequencer serializes their writes.
- Cache behavior: Generation cancellation and last-applied title maps coalesce utility calls; new auto/renamed sets are cleared on session eviction/disposal. No unbounded retained-state issue remains because clearSession and dispose clear all keys.
- Mechanism confidence: High for redundant title I/O and bounded lifecycle cleanup; insufficient evidence that global metadata sequencing alone materially changes native SQLite throughput, so no separate finding was filed for that sequencing change.
- Magnitude uncertainty: Automatic-title creation frequency is usually low, and provider metadata batches are bounded. The redundant write count is exact, but user-visible contention depends on storage speed and concurrent session activity.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/agentHostSessionTitleController.ts:\_generateTitleSoon</code>: Copilot utility-model title generation; cardinality: At most one active call per session/chat key after cancellation; skipped entirely in active-agent mode

### Scenario 4: Advertise/execute server tools across provider session materialization and later configuration changes

- Critical path: At materialization, AgentServerToolHost filters definitions according to the root setting and providers project the resulting tool definitions into their SDK sessions. During execution, the host validates against the session's advertised tools before dispatch.
- Scaling input: Small bounded number of tool groups/definitions; repeated tool executions per turn may recompute filtered toolNames arrays, but cardinality is currently bounded by the server-tool registry.
- Effective concurrency: Synchronous filtering/allocation; no new subprocess, filesystem, database, IPC, or network boundary is added by advertisement itself. Provider SDK launch/registration boundaries already existed.
- Cache behavior: Definitions are no longer cached globally because newly materialized sessions must observe current configuration; each materialized session stores its advertised snapshot in state. Existing sessions retain that snapshot.
- Mechanism confidence: High that advertisement is bounded and boundary-free; low evidence of material regression from the small synchronous array allocations.
- Magnitude uncertainty: Tool-call counts can be high, but the filtered collection is small and no evidence establishes user-visible cost from getter recomputation, so it was not reported.
- Expensive boundaries: none found
- Verdict: No additional reportable performance regression beyond the prompt-hook serialization that the provider projection enables.

### Scenario 5: Dispose a session or evict an idle materialized session

- Critical path: Disposal now clears title-controller state and awaits SessionDatabase.whenIdle before deleting session data; idle eviction likewise awaits database idle, rechecks subscribers/active turn, clears title state, removes state, and releases provider memory. Destructive disposal then performs existing filesystem/session/provider/worktree cleanup.
- Scaling input: Pending write count W for the one session, number of peer chats C cleared from controller sets, and any existing worktree/filesystem size. Redundant title writes increase W by a small bounded amount per automatic title phase.
- Effective concurrency: whenIdle waits for all tracked writes; metadata writes are globally sequenced, while other tracked writes may proceed according to their own sequencers. Idle eviction is asynchronous and revalidates state after the wait.
- Cache behavior: All title-generation cancellation sources and title-state sets are deleted for the session and its C chats. No unbounded retention was found. Durable data is retained for idle eviction and deleted for explicit disposal.
- Mechanism confidence: High that title state is released and no leak remains. The wait can delay cleanup, but the correctness-preserving ordering and bounded scope do not by themselves establish a reportable regression.
- Magnitude uncertainty: Pending write latency and worktree size vary. The new drain is intentional for persistence/cleanup ordering and bounded to one session; no independent cleanup performance bug was reported.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:2838-2847 and 3157</code>: Drain pending per-session database writes; cardinality: One drain per explicit disposal or idle eviction, waiting on W pending writes
    - Introduced by diff: true; previous behavior: Cleanup did not explicitly await this per-session drain at these points; critical-path effect: Blocks destructive deletion; for idle eviction it delays releasing provider/state memory but is off active user-turn progress
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts:2829 via SessionDataService.deleteSessionData</code>: Delete the per-session data directory; cardinality: One recursive deletion per explicit session disposal
    - Introduced by diff: false; previous behavior: Same filesystem deletion already occurred; critical-path effect: Part of explicit disposal completion
  - subprocess/filesystem at <code>src/vs/platform/agentHost/node/agentService.ts worktree removal after session data deletion</code>: Remove an isolated session worktree when present; cardinality: At most one worktree cleanup per disposed worktree session
    - Introduced by diff: false; previous behavior: Same worktree cleanup already occurred; critical-path effect: Part of explicit disposal completion
- Verdict: No standalone cleanup-lifecycle finding; the duplicate title writes are reported because they unnecessarily enlarge the newly awaited drain.
