## Findings (1)

### 1. [medium] Skip catalog rewrites for non-projected summary changes

**Finding ID:** `PERF-1EDD185AD219`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:776</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Per-session and host-wide SQLite operations plus full catalog payload validation, serialization, hashing, and allocations  
**Scaling:** Cost grows with each debounced session-summary notification (up to the notifier's 100 ms cadence), the number of concurrently active sessions, and each session's chat/metadata payload size. The per-session queue only merges notifications that arrive while a write is already in flight, so spaced activity/status updates each cause another complete synchronization; host-wide database transactions then serialize globally.  
**Outcome:** Repeated filesystem/SQLite I/O and CPU/GC pressure contend with session listing and other Agent Host persistence, increasing latency while agents are active.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this added listener call, summary notifications updated recency and existing reconciliation state but did not open the session database, rebuild the complete catalog payload, or perform the new central catalog transactions for each summary delta.  
**Changed behavior:** Every emitted summary delta now queues \`\_persistListVisibleSessionStateNow\`. That opens the session database, reads all catalog metadata and per-chat title keys, validates/stable-serializes/hashes the full payload, writes the local catalog snapshot, reads/upserts/acknowledges \`sessions\_v2\`, and marks the central payload dirty before and after. This also runs for \`activity\` changes and transient status-bit changes, although \`AgentHostCatalogData\` stores no activity and the resolver only projects the IsRead/IsArchived status bits.  
**Confidence:** 0.96 — The changed call is unconditional, the notifier's emitted field set and cadence are explicit, and the complete call path to per-session and central SQLite plus full serialization/hash work is directly traced. Exact event prevalence varies by provider and active workflow, which affects severity but not the mechanism.

**Causal diff evidence:** The added unconditional \`this.\_queueCatalogSync(URI.parse(session), {});\` at line 776 is inside \`onDidChangeSessionSummary\`, so the PR newly routes every summary delta—not only catalog-visible deltas—through catalog persistence.

During worktree setup, tool/status progress, or multiple active automation sessions, activity/status summary updates can repeatedly rewrite or replay unchanged catalog state. This adds avoidable disk traffic and globally serialized host-database work, delaying list and persistence operations even though the list-visible payload is unchanged.

**Evidence:** \`SessionSummaryNotifier\` emits deltas for title, status, activity, modifiedAt, project, changes, workingDirectories, and \_meta on a 100 ms scheduler (\`agentHostStateManager.ts:111-221\`). The changed listener queues sync without inspecting \`changes\`. \`\_persistListVisibleSessionStateNow\` calls \`synchronizeWithFactory\`, \`buildCatalogSyncRequest\` reads all session and per-chat metadata, and \`encodeAgentHostCatalogPayload\` validates, stable-stringifies, byte-counts, and SHA-256 hashes the complete payload. \`synchronize\` additionally calls \`markSessionV2PayloadDirty\` before and after local snapshot/central upsert/acknowledgement transactions. Activity is absent from the catalog schema, and transient InProgress/InputNeeded/Error bits are discarded when the resolver derives only read/archive state.

**Suggested direction:** Gate the queue on fields that can alter \`AgentHostCatalogData\`; specifically ignore activity-only deltas and transient status changes when the IsRead/IsArchived projection is unchanged. A cached projected signature or comparison of the projected status bits can preserve required title, recency, project, changes, working-directory, metadata, read, and archive synchronization while avoiding no-op full writes.

### Scenario 3: Periodic catalog reconciliation and compatibility verification

- Mechanism confidence: High: batch, interval, cursor, limiter, coalescing, and receipt behavior are explicit and tested.

### Scenario 5: Peer-chat membership, routing, title updates, and deletion

- Effective concurrency: Parent membership writes use a per-session promise chain; chat-local metadata fan-out is capped at 4. Catalog synchronization is serialized per session and burst-coalesced to one trailing write.
- Cache behavior: Central catalog is authoritative; legacy mirrored revision/payload acts as a merge base and avoids rewriting unchanged entries when available. Conflict loops reread authoritative revisions. Maps tracking writes and deletion fences clear when operations settle/end.
- Mechanism confidence: High for boundaries, limits, and ordering.
- Magnitude uncertainty: Large peer catalogs are uncommon, but limits and changed-entry filtering bound the worst case.

- Effective concurrency: Synchronous CPU work within one request; no new parallel boundary.

- Mechanism confidence: High: the changed loops and call sites are direct.

- Expensive boundaries: none found
- Verdict: No reportable performance regression; bounded synchronous request-size work adds no expensive boundary and has no realistic jank/latency mechanism.
