# Performance review: Agent Host: Forward Git identity to Dev Containers

[PR #336049](https://github.com/microsoft/vscode/pull/336049) at `a6b6349b38d7c5d4ad74e48094c386618b978e1a`

## Findings (1)

### 1. [medium] Batch Git identity setup into one container invocation

**Finding ID:** `PERF-DE6FDBF88125`  
**Location:** <code>src/vs/platform/agentHost/node/devContainerAgentHostService.ts:309</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Subprocess launches and container exec round trips  
**Scaling:** Cost is incurred on every initial connection and every transport reconnect, growing from two local subprocesses when host identity is absent to two local plus 3-5 serialized Dev Container CLI subprocesses when one or two identity fields are present/missing; there is no identity-result cache or coalescing.  
**Outcome:** Increased Dev Container Agent Host connection and reconnection latency on the critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The connection path proceeded from safe.directory setup directly to the parallel platform probes; it performed none of these host Git subprocesses or identity-related Dev Container CLI invocations.  
**Changed behavior:** Every Dev Container connection now synchronously reads two host Git keys and, when host identity exists, performs a separate container \`exec\` for Git availability, each configured key lookup, and each missing-key write before platform detection and relay establishment.  
**Confidence:** 0.98 — The production call path from connector create/reconnect through \`connect\` is explicit, every identity \`exec\` is proven to spawn a fresh Dev Container CLI process, and the new test establishes exact command cardinality. Actual milliseconds vary by host/container, but the serialized critical-path mechanism and common two-field trigger are direct.

**Causal diff evidence:** RIGHT line 309 adds a per-field awaited container probe inside the new identity loop; RIGHT line 313 adds another separately awaited container write, while RIGHT line 176 awaits the whole setup on every connection's critical path.

With the normal host configuration containing both user.name and user.email, connecting or reconnecting now blocks on two serialized local Git processes plus three Dev Container CLI child processes when the container identity is already set, or five CLI child processes when it is missing. Repeated Node/CLI/container-exec startup can add noticeable connection latency before the Agent Host relay is usable.

**Evidence:** The added loop awaits \`exec("git config --get ...")\` once per present host identity field and separately awaits a write for each missing field. \`\_configureGitIdentity\` also awaits a standalone \`command -v git\`; \`\_getHostGitIdentity\` serially awaits two \`\_runLocalCommand('git', ...)\` calls. The traced \`\_createExec\` implementation maps every \`exec\` call to \`\_runDevContainer(getDevContainerExecArgs(...))\`, and \`\_runDevContainer\` starts a fresh Dev Container CLI child process. The test's common two-field case confirms four identity commands after the availability check.

**Suggested direction:** Read both host keys in one local Git invocation and execute one container shell command that checks Git, inspects both effective keys, and conditionally writes missing values while preserving the current no-overwrite semantics. This bounds the added setup to one local and one container subprocess instead of serial per-key fan-out.

### Scenario 2: Dev Container Agent Host connection when the host has no global Git identity

- Critical path: After existing \`devcontainer up\` and safe.directory work, connection waits for both new local Git queries; identity setup then returns without container commands and platform detection proceeds.
- Scaling input: One connection or reconnect; absence of both host-global keys still causes two local process launches.
- Effective concurrency: The two local Git queries execute sequentially; no container identity process is launched.
- Cache behavior: Only shell environment resolution is cached. Negative host identity results are not cached, so every reconnect repeats both misses.
- Mechanism confidence: High: both reads are unconditional and serial before the early return, with no negative cache.
