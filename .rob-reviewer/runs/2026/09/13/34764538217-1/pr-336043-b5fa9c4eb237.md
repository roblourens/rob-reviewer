<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work, boundary-fanout, eager-work, cleanup-lifecycle

### Scenario 1: Open the create/edit Automation dialog with a workspace target

- Critical path: The dialog synchronously constructs the form, standalone target MenuWorkbenchToolBar, target controls, and ChatInputPart before focus is assigned. Git repository/ref loading and automation-draft synchronization are asynchronous and do not have to finish for the dialog or prompt to render; session-configuration controls wait for draft availability. The diff moves the same three target action view items from ChatInputPart's secondary toolbar into the new target toolbar, without adding another target-control instance.
- Scaling input: A fixed three target actions per dialog. For a selected workspace, one effective folder and one selected session type drive one branch lookup and one coalesced draft target.
- Effective concurrency: The branch lookup and draft synchronization can overlap asynchronously, as before. Draft synchronization is globally serialized by syncInProgress/syncScheduled and coalesces equal targets; branch requests cancel/supersede prior requests by request id.
- Cache behavior: Session type/workspace metadata is read from existing in-memory services. AutomationSessionDraftSynchronizer caches captured configuration by target and skips equal/applied targets. The toolbar relocation neither changes keys nor bypasses these checks. Git refs are loaded once for the selected folder on action render, as they were before.
- Mechanism confidence: High confidence from tracing renderForm through both the deleted ChatInput secondary-toolbar provider and the added standalone toolbar provider, plus the unchanged isolation action and draft synchronizer implementations.
- Magnitude uncertainty: Provider-specific draft creation and Git operation duration vary, but their call count and scheduling are unchanged by the diff.
- Expensive boundaries:
  - subprocess at <code>src/vs/sessions/contrib/automations/browser/automationDialog.ts, AutomationIsolationGroupActionViewItem.reloadRepository</code>: Open the selected Git repository and enumerate local refs via gitService.openRepository followed by repo.getRefs({ pattern: 'refs/heads' }).; cardinality: One openRepository and, when a repository exists, one getRefs call for the single selected folder on initial render; later one pair per effective folder change.
    - Introduced by diff: false; previous behavior: The same AutomationIsolationGroupActionViewItem was rendered once in ChatInputPart's secondary toolbar and started the same lookup.; critical-path effect: Runs asynchronously to populate branch/worktree controls; it does not block initial dialog rendering, though branch availability waits for it.
  - other expensive boundary at <code>src/vs/sessions/contrib/automations/browser/automationDialog.ts, AutomationSessionDraftSynchronizer.sync</code>: Resolve workspace trust and create a provider-backed automation draft session for the selected target.; cardinality: At most one synchronization for the effective initial target after equality/coalescing; repeated identical updates are skipped.
    - Introduced by diff: false; previous behavior: The synchronizer and its scheduling run before toolbar construction in both versions, so moving the target controls does not add or advance this boundary.; critical-path effect: Does not block dialog paint; it controls when session-configuration controls become available.
- Verdict: No reportable regression: the new toolbar replaces rather than duplicates target controls, preserves one-time ownership/disposal, and leaves expensive-boundary cardinality unchanged.

### Scenario 2: Resize or narrow the Automation dialog, including phone-width layouts

- Critical path: The added ChatInputPickerResponsiveLayout observes only the target toolbar. On resize it synchronously measures a fixed three-item DOM subtree, toggles compact classes, and asks the toolbar to relayout. allowOverflow:false prevents action removal/recreation, so responsive relayout does not rerender the isolation view item or repeat Git work.
- Scaling input: Fixed at three target controls; work scales with resize/mutation events, not repository size, prompt length, or branch count.
- Effective concurrency: Resize and mutation observer callbacks run synchronously on the UI thread and are guarded against reentrant layout by \_isLayouting. There is no asynchronous fan-out.
- Cache behavior: No cache is involved. Preferred-layout measurement clones only the small target subtree for each relevant callback; class mutations made during layout are disconnected from the mutation observer.
- Mechanism confidence: High confidence from ChatInputPickerResponsiveLayout.layout and ToolBar.relayout/updateActions: allowOverflow:false returns without pulling or pushing action view items.
- Magnitude uncertainty: Exact layout cost depends on platform and resize frequency, but the subtree is fixed and small. The prior ChatInput secondary responsive layout measured these controls in its own subtree; splitting them adds an observer but removes the same controls from that prior measurement.
- Expensive boundaries: none found
- Verdict: No actionable performance regression: the added synchronous work is bounded to three elements and cannot trigger repeated Git/session operations.

### Scenario 3: Select or rapidly switch workspace, No workspace, agent, isolation mode, or branch

- Critical path: A target change updates the isolation model, validates the form, coalesces automation-draft synchronization, updates labels, and for an effective folder change reloads repository/refs. The new target toolbar's mutation observer may perform a bounded responsive measurement after label/class changes, but prompt typing is outside its observed subtree.
- Scaling input: One selected target at a time; draft work scales with distinct effective target changes after equality/coalescing, and Git work with distinct effective folder changes. Branch rendering scales with the returned local branch list exactly as before.
- Effective concurrency: Draft updates serialize and coalesce to the latest generation. Branch changes cancel the prior token and suppress stale results; at most the already-started openRepository operation can overlap a replacement, unchanged by this PR.
- Cache behavior: Captured session configurations are cached per target key. Identical target updates are skipped. Branch lists are not cached across folder changes, but this behavior is pre-existing and unchanged.
- Mechanism confidence: High confidence from observable subscriptions, synchronizer equality/generation guards, and the unchanged isolation action call path.
- Magnitude uncertainty: Very rapid target changes may overlap an already-started Git open or provider operation, but that cancellation limitation predates the diff and is not amplified by the toolbar move.
- Expensive boundaries:
  - subprocess at <code>src/vs/sessions/contrib/automations/browser/automationDialog.ts, AutomationIsolationGroupActionViewItem.reloadRepository</code>: Open a Git repository and request local refs after an effective folder change.; cardinality: One open call per effective folder change and one refs call only for the latest successfully opened repository; stale results are suppressed.
    - Introduced by diff: false; previous behavior: The same isolation action subscribed to the same folder observable while hosted in the prompt's secondary toolbar.; critical-path effect: Only branch/worktree readiness waits; target selection and prompt editing continue.
  - other expensive boundary at <code>src/vs/sessions/contrib/automations/browser/automationDialog.ts, AutomationSessionDraftSynchronizer.sync</code>: Capture/discard/create provider-backed automation draft sessions while retargeting.; cardinality: Serialized to one active sync with latest-target coalescing; equal targets do not resynchronize.
    - Introduced by diff: false; previous behavior: Target changes fed the same synchronizer before this toolbar relocation.; critical-path effect: Session-configuration availability waits for synchronization, but the rest of the form remains usable.
- Verdict: No reportable regression: target-change boundary fan-out, coalescing, cancellation, and retained state are unchanged; the only new work is bounded toolbar measurement.

**Summary:** Reviewed all four changed files and traced dialog opening, responsive layout, target switching, Git ref loading, provider draft synchronization, cache/coalescing, concurrency, and disposal. The PR relocates existing controls into one owned toolbar and adds bounded three-item layout measurement; it does not duplicate expensive work, increase boundary cardinality, retain unbounded state, or introduce a high-confidence user-visible performance regression.
