# Performance review: Agents - refactor repository pickers so that all actions are in one toolbar

[PR #336058](https://github.com/microsoft/vscode/pull/336058) at `b344f351180f0e7127f7e517d1450d6a4c5f6f03`

## Findings (1)

### 1. [medium] Avoid structurally rebuilding every repository toolbar on value changes

**Finding ID:** `PERF-965EBE411942`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/agentHostSessionConfigPicker.ts:1545</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Repository-toolbar action objects, picker instances, event listeners, and DOM nodes  
**Scaling:** Each provider config pulse causes one coalesced structural menu update; every live NewSessionRepositoryConfig toolbar then disposes and recreates all P repository picker items, so work grows as O(V×P) for V visible session composers and P renderable config properties. A normal draft selection produces at least an optimistic pulse and a later resolution pulse.  
**Outcome:** Unnecessary main-thread DOM/allocation work and GC pressure during branch/worktree interactions, increasing interaction latency and risking visible jank as visible sessions and schema properties grow.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The repository menu contained one statically registered action. Provider config pulses re-rendered the existing composite picker in place, without mutating MenuRegistry or forcing MenuWorkbenchToolBar.setActions to dispose and recreate the entire toolbar.  
**Changed behavior:** The new provider-wide listener calls \_refreshRepositoryMenuItems for every onDidChangeSessionConfig event, regardless of which session changed or whether the renderable schema changed; that method clears and re-appends menu items, publishing a structural menu change consumed by every toolbar.  
**Confidence:** 0.97 — The event source, synchronous refresh, microtask-coalesced structural menu notification, and toolbar disposal/recreation path are all directly traced in repository code. The exact frame cost varies by the number of visible sessions and provider-defined properties, so severity is medium, but the repeated rendering mechanism is certain.

**Causal diff evidence:** The added RIGHT-side line 1545 registers \`provider.onDidChangeSessionConfig(() =&gt; this.\_refreshRepositoryMenuItems(actionViewItemService))\`; before this PR there was no provider-config listener that mutated the repository MenuRegistry.

Selecting a branch or isolation option fires onDidChangeSessionConfig synchronously before the existing asynchronous config resolution and again when resolution completes. Both value-only events now rebuild each visible repository toolbar, recreating all per-property controls even though the set/order/titles of actions usually did not change.

**Evidence:** The added listener at line 1545 ignores the event's sessionId and always calls \_refreshRepositoryMenuItems. That method clears \_repositoryMenuItems and appends entries for every visible session. MenuRegistry.appendMenuItem/disposal fires a structural menu event (actions.ts:509-520); MenuWorkbenchToolBar handles it with \_updateToolbar/setActions (toolbar.ts:374-405), whose ActionBar.clear path disposes all view items and removes their DOM. BaseAgentHostSessionsProvider.setSessionConfigValue emits once immediately before async resolution (baseAgentHostSessionsProvider.ts:4060) and \_refreshNewSessionConfig emits again on completion (3772/3799).

**Suggested direction:** Use the event's sessionId and retain a signature of each visible session's renderable property keys/order/titles. Skip MenuRegistry mutation for value-only config pulses, and replace registrations only when that schema signature or visible-session membership actually changes.

### Scenario 2: Open, close, pin, restore, or rearrange visible session composers

- Critical path: A visibleSessions publication synchronously triggers the new contribution autorun, which scans every visible session and rebuilds global repository-menu registrations. The session grid update is also reacting to the same publication, so this extra CPU/allocation runs during session-view presentation.
- Scaling input: The scan and menu-item allocation grow with V visible sessions times P renderable properties; the resulting structural event rebuilds each live repository toolbar once after coalescing.
- Effective concurrency: The autorun executes synchronously with observable publication. Menu updates are coalesced/debounced, but there is no cancellation or incremental update; every publication clears and reconstructs the complete set.
- Cache behavior: Session config reads are warm in-memory provider cache reads. Command/action-view factory registrations are retained by property key for contribution lifetime; menu-item registrations are fully discarded and recreated on every publication.
- Mechanism confidence: High for the O(V×P) refresh and structural toolbar update; user-visible duration depends on grid size and property count.
- Magnitude uncertainty: Visible session grids are ordinarily small, but pinned/multi-column workflows can keep several composers alive. No external boundary dominates this path; the concern is avoidable synchronous scan/allocation and subsequent DOM reconstruction.
- Expensive boundaries: none found
- Verdict: The same reported mechanism applies. A schema-signature/membership diff can preserve the required dynamic menu while avoiding complete recreation.

### Scenario 3: Cross the phone-layout breakpoint and render the consolidated repository/status toolbar

- Critical path: The phone context-key event synchronously refreshes repository menu ordering, then each picker also re-renders to switch isolation presentation; CSS layout updates follow. - Effective concurrency: Synchronous context-key listeners followed by coalesced menu update; no async fan-out.
- Cache behavior: All config reads are from existing in-memory state; mobile dynamic completion data remains lazy and is not fetched merely by crossing the breakpoint.
- Mechanism confidence: High that work occurs, but low concern due to infrequency and the need to reorder controls.
- Magnitude uncertainty: Breakpoint transitions are uncommon, and typical property counts are low.
- Expensive boundaries: none found
- Verdict: No separate finding: rebuilding on an actual layout/order change is intentional and bounded.
