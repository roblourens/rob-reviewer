# Performance review: Agents: support multiple pull requests per session

[PR #333189](https://github.com/microsoft/vscode/pull/333189) at `1d7a79d3ab691e9e567e330f4eb3786c3b4b7dca`

## Findings (2)

### 1. [medium] Bound background polling across associated pull requests

**Finding ID:** `PERF-7ECB7F19CB55`  
**Location:** <code>src/vs/sessions/contrib/github/browser/github.contribution.ts:239</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub REST and GraphQL API calls, response bytes, and request-processing work  
**Scaling:** The cost grows with the number of distinct pull-request references across every unarchived session (shared model keys coalesce only duplicate references to the same PR). Each additional open PR adds two PR metadata/review REST calls, one CI call, and one review-thread GraphQL call per 60-second cycle, plus the same four-call startup burst; closed/draft PRs still add the two metadata/review calls.  
**Outcome:** Excessive background network traffic and GitHub API rate-limit pressure, with startup bursts and delayed or failed status updates once the quota is exhausted.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Each tracked session acquired and refreshed only its primary pull-request model, then polled CI and review threads only for that one PR.  
**Changed behavior:** The added loop invokes \`\_pollPullRequest\` for every associated PR of every unarchived session. \`\_pollPullRequest\` immediately refreshes each model and starts independent 60-second PR/CI/review-thread polling as applicable.  
**Confidence:** 0.98 — The changed loop, all-session ownership, uncapped source collection, 60-second model intervals, and concrete REST/GraphQL calls are directly traced. The exact number of users with large PR histories is uncertain, which limits severity rather than mechanism confidence.

**Causal diff evidence:** The changed hunk replaced a single \`{ owner, repo, prNumber }\` poll setup with \`for (const pullRequest of identity.pullRequests)\`, so background requests changed from one PR per session to all associated PRs.

Opening a profile with many retained agent sessions that each produced multiple PRs now starts a burst proportional to the total PR history and keeps issuing up to four GitHub requests per open PR per minute, even when those sessions are not active. A realistic set of a few dozen unique PRs can consume thousands of API requests per hour and make session icons/banners stop updating under rate limiting.

**Evidence:** \`\_onDidChangeSessions\` installs a poller for every session, and \`toGitHubPromotion\` retains all deduplicated PR artifacts without a cardinality cap. This new loop calls \`\_pollPullRequest\` for each ref. That helper calls \`GitHubPullRequestModel.refresh()\` immediately and starts its 60-second poll; the model refresh performs \`getPullRequest\` and \`getReviews\` in parallel. For every open non-draft PR it also refreshes and starts 60-second CI and review-thread models, whose fetchers cross the REST/GraphQL boundary. Reference collections prevent duplicate calls only when two sessions reference the exact same PR; they do not bound aggregate unique-PR concurrency.

**Suggested direction:** Keep inactive sessions on the primary/cached PR presentation, and refresh all associated PRs only for the active session; alternatively route additional-PR refreshes through a shared bounded/staggered scheduler with a substantially lower inactive cadence so aggregate GitHub traffic is capped.

### 2. [medium] Do not continuously poll review threads for inactive PR states

**Finding ID:** `PERF-8BE970CA33B8`  
**Location:** <code>src/vs/sessions/contrib/codeReview/browser/codeReviewService.ts:148</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub GraphQL requests and review-thread/comment response payloads  
**Scaling:** For the active session, one 60-second GraphQL poll is retained for every associated PR. Shared polling suppresses duplicate timers for open PRs already owned by the GitHub polling contribution, but each additional closed, merged, or draft PR gains a new recurring request because that contribution deliberately does not poll review threads for those states.  
**Outcome:** Persistent unnecessary network traffic and GitHub API quota consumption while a multi-PR session remains active.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** CodeReviewService only consumed the primary review-thread model; polling was owned elsewhere. The existing GitHub session poller limits CI/review-thread polling to open, non-draft PRs (apart from the legacy primary active-session owner).  
**Changed behavior:** The new autorun refreshes and calls \`startPolling()\` on the review-thread model for every associated PR without checking the PR's live state.  
**Confidence:** 0.97 — The unconditional added call, active-session lifetime, state gate in the existing owner, one-minute interval, and GraphQL boundary are directly visible. Only the typical number of historical PRs per session is uncertain.

**Causal diff evidence:** Added line 148 registers a polling client for each entry in \`context.pullRequests\`; before this PR, CodeReviewService did not start review-thread polling at all.

Selecting a long-running session with historical merged/closed PRs keeps a GraphQL \`GetReviewThreads\` request running every minute for each historical PR. The query can return up to 100 threads with up to 100 comments each, so sessions with several prior PRs continuously consume bandwidth and API quota despite those PRs no longer changing.

**Evidence:** The added loop calls \`refresh()\` and \`startPolling()\` unconditionally. \`GitHubPullRequestReviewThreadsModel.startPolling\` schedules every 60 seconds, and \`\_refresh\` invokes \`GitHubPRFetcher.getReviewThreads\`, which performs a GraphQL query. By contrast, \`GitHubPullRequestPollingContribution\` starts review-thread polling only after \`\!isDraft && state === Open\`; therefore model client-count coalescing does not eliminate the newly introduced polling for historical non-open PRs.

**Suggested direction:** Refresh historical PR thread models once to populate combined state, but call \`startPolling()\` only for live open, non-draft PRs (or rely on the existing GitHub polling owner for those models).

- Mechanism confidence: High: unconditional added startPolling call, active-session lifetime, 60-second model cadence, and GraphQL implementation are direct.

- Expensive boundaries:
