# Performance review: Cache API Scan dependencies in official builds

[PR #335993](https://github.com/microsoft/vscode/pull/335993) at `179eca4cffc29dd54aa1e21a2939d2542dfdec03`

## Findings (1)

### 1. [medium] Run registry setup before extracting the dependency cache

**Finding ID:** `PERF-69C82B9EB4DC`  
**Location:** <code>build/azure-pipelines/win32/sdl-scan-win32.yml:77</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Sequential filesystem readdir/stat operations over the extracted node\_modules trees, plus rewrites of nested package-lock files  
**Scaling:** On every warm API Scan build, cost grows with the total number of files and directories in all cached node\_modules trees rather than only the checked-out source tree; setup-npm-registry.ts awaits a stat for each entry and recursively descends without excluding node\_modules.  
**Outcome:** Increased warm-build latency and excessive filesystem I/O on the API Scan critical path  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The registry setup ran immediately after checkout/key-vault setup, before npm ci, so its recursive package-lock search traversed the source checkout while no dependency trees existed.  
**Changed behavior:** The moved setup step now runs after Cache&#64;2 restoration and 7z extraction, so a cache hit places every cached node\_modules tree under the recursive search root before it starts.  
**Confidence:** 0.98 — The ordering is explicit in the changed YAML, the restored archive explicitly contains all node\_modules files, and the invoked script explicitly performs an unpruned sequential recursive filesystem walk. Only the exact elapsed-time magnitude varies with dependency-tree size and agent filesystem performance.

**Causal diff evidence:** The diff deletes the Setup NPM Registry task from before include.gypi/cache handling and re-adds it at RIGHT line 77, after RIGHT line 73 extracts .build/apiscan\_node\_modules\_cache/cache.7z into the checkout.

Each official Windows x64 API Scan cache hit can perform a sequential metadata walk over the entire restored dependency forest before compilation, eroding the intended dependency-cache latency savings; large dependency trees make this potentially minutes of Windows filesystem work.

**Evidence:** Added line 77 invokes build/setup-npm-registry.ts after the added cache extraction at line 73. That script's getPackageLockFiles recursively calls readdir for every directory and awaits fs.stat for every entry with no node\_modules pruning. The cache archive is built from listNodeModules.ts, which enumerates files from every node\_modules tree across the repository, so the warm path guarantees a much larger traversal than the pre-diff placement.

**Suggested direction:** Move the Setup NPM Registry task back before cache extraction (the cache key already includes NPM\_REGISTRY), or make setup-npm-registry.ts explicitly prune node\_modules for this invocation so only repository lockfiles are visited.
