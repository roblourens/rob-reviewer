# Performance review: Sort chat pill dropdown entries newest first

[PR #334889](https://github.com/microsoft/vscode/pull/334889) at `3e5d8f7d9fdfe9645aa53cc9fde4e78fccd1d149`

## Findings (1)

### 1. [medium] Build newest-first browser lists without quadratic front insertion

**Finding ID:** `PERF-2A880626482E`  
**Location:** <code>src/vs/workbench/contrib/browserView/common/browserView.ts:113</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** JavaScript array element moves and temporary allocation on the renderer/UI thread  
**Scaling:** Each recomputation still scans all n known browser views, but \`unshift\` additionally moves every previously matched element, making construction O(n + m²) for m matching agent-owned views instead of O(n). The helper is used by both pill surfaces and recomputes on browser-set and label events (title, favicon, loading-state, and navigation changes).  
**Outcome:** increased UI-thread CPU/GC pressure and pill update latency, potentially causing visible jank in long-running agent sessions with many browser views  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Both call sites built their matching browser list with \`filter\` or \`push\`, preserving an O(n) scan of the known-browser map on each reactive update.  
**Changed behavior:** The shared newest-first helper inserts every match at index zero, shifting the accumulated array for each matching browser on every recomputation.  
**Confidence:** 0.97 — The complexity change, both reactive call paths, event sources, and map lifecycle are directly visible in repository code. Exact user-visible magnitude depends on how many browser views a session accumulates, so severity is medium rather than high.

**Causal diff evidence:** The added RIGHT-side line 113 replaces the prior callers' append/filter construction with \`views.unshift(input)\`, introducing repeated shifting proportional to the number of already matched views.

When an agent session accumulates many browser pages, each page load/navigation emits several label events; both pill surfaces can repeatedly perform quadratic array copying before updating the UI, delaying rendering and increasing GC pressure.

**Evidence:** \`getAgentBrowserViewsNewestFirst\` iterates the complete \`getKnownBrowserViews()\` map and executes \`views.unshift(input)\` for every matching owner. \`SessionBrowsersControl\` and \`AgentHostSessionInputPills\` both call it from derived UI state, and both register every browser input's \`onDidChangeLabel\`; \`BrowserEditorInput\` fires that event for title, favicon, loading-state, navigation, model resolution, and explicit navigation changes. The known-view map has no cardinality cap and removes entries only when an input is disposed.

**Suggested direction:** Append matching inputs with \`push\` during the map walk and call \`views.reverse()\` once afterward; this preserves newest-first ordering and restores O(n) construction.
