## Performance regression fixes detected (1)

### 1. boundary-fanout

**Fix location:** `src/vs/platform/agentHost/node/agentService.ts:2839` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentService.ts:2200`  
**Introducing path:** `src/vs/platform/agentHost/node/agentService.ts`  
**Introducing commit:** `150119bd223150e10f6bf341435e680cd8f26d4b`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `latency`  
**Confidence:** 0.96

**Mechanism:** Each list computation scaled across all visible sessions with provider metadata retrieval followed by opening and querying every session.db, placing O(number of sessions) filesystem and SQLite boundaries on the list critical path.

**Symptom:** Large session catalogs produced slow cold and warm `listSessions` calls; the base code explicitly classified the all-session database pass as slow, and equivalent-profile measurements show roughly 1.3s cold mean and 432ms warm mean before the fix.

**Fixed behavior:** Normal warm and migrated listings read one verified payload per visible registration from the central `agent-host.db`; provider metadata prewarming and per-session database opens now occur only for ineligible central rows, so the expensive filesystem/SQLite fan-out is removed from the steady-state list critical path.

**Evidence:** In the base `_computeSessions`, every visible registered session went through provider metadata work and then a second `overlayLimiter` pass that called `tryOpenDatabase(s.session)` and read a broad metadata object; the base comments identify provider reads as the dominant cost on a large catalogue and state that a catalog pass opens every registered database. The changed `_computeSessions` at line 2839 instead calls `AgentHostCatalogListReader.read`, whose only normal-path boundary is `AgentHostDatabase.getSessionV2` in the already-open central SQLite database; only missing/stale rows take `_legacyRegisteredSessionMetadata`. PR measurements corroborate the traced mechanism with cold mean 1314.9ms to 123.4ms and warm mean 431.6ms to 80.0ms.

### Scenario 1: Warm and cold session listing

- Critical path: A non-empty migrated registry lists registrations, reads verified central payloads, overlays in-memory live summaries, and returns. An empty registry waits for initial provider migration; individual missing or invalid central rows synchronously use the legacy fallback before that row can be returned.
- Scaling input: Number of visible registered sessions after external-mode filtering; steady-state cardinality is one central row read per visible registration, with legacy work only for ineligible rows.
- Effective concurrency: Concurrent list calls are shared by mode and coalesced to at most one trailing refresh. Catalog and fallback loops use limiters of 4, while the central SQLite transaction sequencer effectively serializes central queries.
- Cache behavior: Verified current-version central payloads are the warm path. Missing, stale, corrupt, or version-mismatched rows fall back individually, are marked dirty, and are repaired in the background; provider metadata is prewarmed only for providers with fallback rows.
- Mechanism confidence: High: the before/after boundary paths, per-registration multiplicity, limiter, and fallback condition are explicit.
- Magnitude uncertainty: Exact latency depends on catalog size, storage, and fallback rate; the mechanism and supplied equivalent-profile measurements strongly establish the improvement.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:2839, AgentHostCatalogListReader.read</code>: Read and decode one \`sessions\_v2\` payload from the central SQLite database.; cardinality: One read per visible registration; all use the same already-open central database and are sequenced.
    - Introduced by diff: true; previous behavior: Each visible session used provider metadata work and then opened/read its individual session database.; critical-path effect: Required for each steady-state listed session, but replaces much heavier per-session boundaries.
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts, \_legacyRegisteredSessionMetadata</code>: Open an individual session database and read legacy metadata on a central-row miss.; cardinality: Only ineligible central rows, bounded to four queued fallbacks; zero in the migrated warm case.
    - Introduced by diff: false; previous behavior: Performed for every visible session.; critical-path effect: Blocks only the affected row's list result.
  - other expensive boundary at <code>src/vs/platform/agentHost/node/agentService.ts, \_computeSessions/\_legacyRegisteredSessionMetadata</code>: Provider metadata prewarm and per-session metadata fallback.; cardinality: One prewarm per provider with misses and one fallback per ineligible row.
    - Introduced by diff: false; previous behavior: Provider metadata was used for every visible registration.; critical-path effect: Blocks affected fallback rows only.
- Verdict: No regression. The diff removes the prior all-session provider and session-database fan-out from the steady-state critical path and was recorded as a regression fix.

### Scenario 2: Initial provider migration and profile upgrade

- Effective concurrency: Provider migrations are coordinated and retried in the background; session work is bounded rather than launched without a limiter. SQLite writes are transaction-sequenced.
- Cache behavior: Versioned per-provider backfill markers skip completed migration. Durable exclusions avoid repeatedly importing stale, backing, subagent, or absent candidates; partial work resumes from persisted state.
- Mechanism confidence: High: migration gates, durable markers, no-create probe behavior, and bounded processing are covered by changed code and tests.
- Magnitude uncertainty: Provider-specific enumeration latency and profile sizes vary, but completed markers and deferred execution bound repeated startup cost.

### Scenario 3: Periodic catalog reconciliation and repair

- Critical path: Dirty or sampled registrations are resolved, local pending snapshots may be replayed, and central payloads are updated or marked clean. Periodic work is off the user-facing list critical path except explicit external-session reconciliation, which intentionally verifies before broadcasting.
- Scaling input: Dirty rows in batches of 50; compatibility verification samples from the registered population no more than hourly.
- Effective concurrency: Maximum four reconciliation tasks run concurrently; five-minute scheduling, a single in-flight pass, and one coalesced trailing rerun prevent storms.
- Cache behavior: Clean acknowledged rows are skipped before opening session.db. Dirty epochs and exact acknowledgements prevent lost updates; successful repair clears the observed marker, while failures remain retryable.
- Mechanism confidence: High: batch size, concurrency, scheduling intervals, dirty filtering, and coalescing are explicit and tested.
- Magnitude uncertainty: The number of dirty rows after crashes or upgrades varies, so a full repair can be long, but batching and background scheduling cap burst pressure.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostCatalogReconciliationService.ts, runPass/runFullPass</code>: Read central receipts and, only for selected dirty/sample rows, probe a session database and synchronize payloads.; cardinality: At most 50 selected rows per ordinary pass, concurrency four; clean rows do not repeatedly open local databases.
    - Introduced by diff: true; previous behavior: No central repair service existed; list calls themselves paid per-session database reads.; critical-path effect: Usually background; explicit external-mode reconciliation awaits a bounded/full verification pass before publishing.
- Verdict: No regression. Work is bounded, skips clean rows, and is shifted off normal listing.

### Scenario 4: Live session title, status, workspace, and changes updates

- Critical path: A debounced session summary change queues a per-session catalog synchronization: build bounded payload, write legacy metadata plus a pending snapshot locally, upsert central SQLite, then acknowledge locally. UI state notifications are emitted before this durability work and do not await it.
- Scaling input: Distinct sessions with changed list-visible summaries and the frequency of debounced 100ms summary changes; concurrent updates to one session coalesce to one trailing write.
- Effective concurrency: Writes are serialized per session and changes arriving during an active write collapse into one trailing synchronization. Central and local databases also sequence transactions.
- Cache behavior: The live state manager remains authoritative in process. Pending snapshots provide crash recovery; unchanged streamed token content does not itself alter the compared summary fields.
- Mechanism confidence: High: notifier field comparison, 100ms debounce, asynchronous listener, and per-session trailing-write state are explicit.
- Magnitude uncertainty: Status/activity producers may differ by provider, but token streaming is not a direct write trigger and coalescing bounds bursts.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostCatalogSyncService.ts, synchronize</code>: Write local metadata/pending catalog snapshot, upsert central payload, and acknowledge the local snapshot.; cardinality: One active plus at most one trailing write per session burst after summary debounce.
    - Introduced by diff: true; previous behavior: List-visible metadata was persisted through existing local metadata paths and then reread from each session database during listing; no central copy was maintained.; critical-path effect: Off the UI notification critical path; durability proceeds asynchronously.
- Verdict: No reportable regression. The new durable writes are asynchronous and coalesced rather than per token or unbounded.

### Scenario 5: Peer-chat creation, mutation, restoration, and legacy compatibility

- Effective concurrency: Membership mutations are serialized per parent session. Compatibility peer-database writes use concurrency four; SQLite central transactions are sequenced.
- Cache behavior: Central membership is authoritative. Recorded legacy mirror payloads detect old-build changes; matching prior entries suppress unchanged peer metadata writes. Migration-only state remains unmirrored until a compatible local database is available.
- Mechanism confidence: High: full central replacement, changed-entry filtering, migration no-create behavior, serialization, and concurrency four are explicit and tested.
- Magnitude uncertainty: Very large current-authority peer sets could make replacement and first compatibility publication expensive, but the normal workflow changes a small set and imported data is capped.

### Scenario 6: Chat prompt parsing and variable range remapping

- Critical path: Prompt text replacements are applied in memory and each variable range endpoint is remapped through replacement edits before the request proceeds; no subprocess, IPC, filesystem, database, or network boundary is reached by the changed helper.
- Scaling input: Product of parsed variable ranges and prompt replacement edits. Typical prompts contain few variables and replacement edits.
- Effective concurrency: Synchronous CPU work within one prompt parse; no concurrency or queueing.
- Cache behavior: No cache is involved; work is performed once for the prompt transformation.
- Mechanism confidence: High for O(V×E) CPU behavior, low for material impact at realistic prompt sizes.
- Magnitude uncertainty: Pathological prompts with many variables and edits could increase CPU, but repository context provides no realistic cardinality or measured user-visible delay sufficient for a finding.
- Expensive boundaries: none found
- Verdict: No reportable regression; the nested remapping is a small in-memory computation without evidence of meaningful latency.
