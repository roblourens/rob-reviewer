# Performance review: agentHost: make the orchestrator own session enumeration and chat lifecycle

[PR #329633](https://github.com/microsoft/vscode/pull/329633) at `675bfbd56de910baf8efa75a42248a812a6f7ad7`

## Findings (2)

### 1. [high] Bound registry hydration instead of issuing one SDK request per session

**Finding ID:** `PERF-811C29CB0EDE`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:1243</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Provider SDK/IPC calls, subprocess work, and per-session database reads  
**Scaling:** Each list refresh now launches one metadata lookup for every registered session with unbounded Promise.all concurrency, so request count and concurrent pressure grow linearly with the full retained history rather than with the small number of providers.  
**Outcome:** Session-list startup and post-turn refresh latency increase, while large histories can flood provider subprocesses with concurrent metadata requests and filesystem/database work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The same scenario called each provider's bulk listSessions API once (one catalog boundary per provider); providers then joined local metadata onto that bulk response.  
**Changed behavior:** listSessions reads the registry and maps every registered row through \_registeredSessionMetadata. That method calls agent.getChatMetadata for the default chat, which is a per-session getSessionMetadata IPC for Copilot, a getSessionInfo SDK lookup for Claude, and potentially thread/read(includeTurns: true) for Codex, before another per-session database overlay pass.  
**Confidence:** 0.99 — The call path, refresh triggers, and exact provider boundaries are explicit in production code. Cardinality is the durable registry size and there is no limiter or cache around this Promise.all; only exact wall-clock magnitude varies by history size and provider latency.

**Causal diff evidence:** RIGHT line 1243 changes the outer cardinality from providers to every registered session and starts all per-session metadata requests concurrently; the deleted implementation at this hunk called agent.listSessions once per provider.

Opening the sessions view and every ChatTurnComplete-triggered refresh can issue tens or hundreds of concurrent SDK/IPC calls for a user with a long session history. The list cannot complete until all requests settle, so one slow provider subprocess delays the whole catalog and the unbounded burst can reduce host responsiveness.

**Evidence:** The changed Promise.all at line 1243 invokes \_registeredSessionMetadata once per registry row. Traced provider implementations show CopilotAgent.getChatMetadata calls client.getSessionMetadata(sessionId), ClaudeAgent.getChatMetadata calls \_sdkService.getSessionInfo(sessionId), and CodexAgent.getChatMetadata calls \_readSession, which sends thread/read with includeTurns:true when not live. baseAgentHostSessionsProvider.\_refreshSessions awaits connection.listSessions both for initial cache population and after every ChatTurnComplete. The old deleted implementation used Promise.all over providers and each provider's bulk listSessions catalog call.

**Suggested direction:** Keep the orchestrator-owned registry for identity, but hydrate entries through one bulk metadata snapshot per provider and join by backing/session id, or add a provider bulk-metadata API. If targeted reads remain necessary, cap concurrency and avoid full thread history reads; preserve registry rows when metadata is unavailable.

### 2. [medium] Fan out only to the chat that was added

**Finding ID:** `PERF-549293180FE2`  
**Location:** <code>src/vs/platform/agentHost/node/agentSideEffects.ts:338</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Repeated tool-set updates, plugin-cache filesystem checks/copies, plugin parsing, and provider customization reconciliation  
**Scaling:** With C active clients and M chats added incrementally, each SessionChatAdded replays all C clients across all chats, producing C × (1+2+...+M) = O(C×M²) assignments instead of O(C×M).  
**Outcome:** Creating side chats or spawning many subagent chats causes growing background filesystem/CPU work and provider reconfiguration bursts, which can delay customization availability and contend with active chat work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, active-client state was session-scoped and a chat-add event did not replay tool/customization assignment across the existing chat catalog.  
**Changed behavior:** Every SessionChatAdded loops all active clients and calls \_fanOutActiveClient, which loops the complete post-add chat catalog and reassigns tools and customizations to old handles as well as the new chat. The added action already carries summary.resource, so prior chats do not need to be revisited.  
**Confidence:** 0.98 — The event payload, catalog iteration, cumulative call count, and provider setter boundaries are explicit, and the new test proves old chats are deliberately revisited. Magnitude depends on chat/subagent count and enabled plugin count, so severity is medium rather than high.

**Causal diff evidence:** The new SessionChatAdded branch at lines 336-340 reuses the full-catalog fan-out helper rather than addressing only envelope.action.summary.resource; this event-side work did not exist before the diff.

A session accumulating chats repeatedly reprocesses every previous chat. For Claude and Codex, each customization assignment calls AgentPluginManager.syncCustomizations and then reconciles/parses provider state; even nonce cache hits perform filesystem existence checks. Copilot repeatedly writes the same session-level handle once per chat (its equality guard avoids deep resync but not all repeated dispatch work).

**Evidence:** RIGHT line 338 calls \_fanOutActiveClient from each SessionChatAdded. \_fanOutActiveClient iterates getSessionChatsForFanOut's full state.chats list and sets both fields on every handle. The added unit test explicitly expects the default chat to be called a second time when one peer is added. Provider setters trace to ClaudeAgent.\_syncClientCustomizations and CodexAgent.\_syncClientCustomizations, both invoking the shared AgentPluginManager's filesystem-backed sync before provider reconciliation.

**Suggested direction:** For SessionChatAdded, iterate active clients but apply each one only to URI.parse(envelope.action.summary.resource). Retain full-catalog fan-out for SessionActiveClientSet, where the client's complete snapshot genuinely changed.

### Scenario 1: Populate and refresh the session catalog at startup and after a completed turn

- Critical path: The workbench awaits connection.listSessions before marking its session cache authoritative; AgentService awaits every registry-row metadata lookup and every overlay read before returning. The same path runs for initial population and on every ChatTurnComplete.
- Scaling input: Number of non-idle sessions retained in the durable registry, without grouping by provider or effective deduplication; realistic long-lived histories can contain tens or hundreds of sessions.
- Effective concurrency: One renderer-to-host list request fans out through an unbounded Promise.all over all registry rows. Provider requests for all sessions are launched together; there is no limiter or cross-refresh coalescing.
- Cache behavior: The durable registry lookup is warm after database initialization, but metadata is rehydrated on every refresh. The renderer cache is not updated until the complete response returns. Codex can answer already-live sessions from memory after a cold pass, while cold Codex rows and all normal Copilot/Claude rows still cross provider boundaries; there is no negative or result cache at AgentService.
- Mechanism confidence: Very high: production code and provider implementations directly establish the per-row IPC/SDK boundaries and refresh triggers.
- Magnitude uncertainty: Exact history sizes and provider response times vary, but the N-request call graph and lack of a limiter are deterministic.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_refreshSessions</code>: Workbench connection.listSessions request to the agent host; cardinality: One outer request per initial refresh, explicit post-send refresh, retry, or ChatTurnComplete refresh.
    - Introduced by diff: false; previous behavior: The same outer request existed, but server-side hydration used one bulk catalog request per provider.; critical-path effect: The UI cache waits for the response before becoming authoritative.
  - database at <code>src/vs/platform/agentHost/node/agentHostDatabase.ts:listSessions</code>: Read all registered session identities from SQLite; cardinality: One query per catalog refresh.
    - Introduced by diff: true; previous behavior: No orchestrator-owned registry query was required.; critical-path effect: Completes before any provider metadata fan-out begins.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:getChatMetadata</code>: Copilot client getSessionMetadata for one backing session; cardinality: One per registered Copilot session per refresh, all launched concurrently.
    - Introduced by diff: true; previous behavior: One Copilot listSessions IPC returned the provider catalog, followed by local joins.; critical-path effect: Every request must settle before the catalog response returns.
  - subprocess at <code>src/vs/platform/agentHost/node/claude/claudeAgent.ts:getChatMetadata</code>: Claude SDK getSessionInfo for one session; cardinality: One per registered Claude session per refresh, all launched concurrently.
    - Introduced by diff: true; previous behavior: One SDK listSessions call returned all Claude session metadata.; critical-path effect: Every lookup must settle before the catalog response returns.
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_readSession</code>: Codex app-server thread/read with includeTurns:true for a cold session; cardinality: Up to one per registered non-live Codex session per refresh, all launched concurrently; live rows use memory.

    - Introduced by diff: false; previous behavior: Provider bulk enumeration already joined per-session overlays and AgentService applied host overlays; the principal regression is replacing bulk SDK access with per-row SDK access.; critical-path effect: All reads are awaited before list completion.
- Verdict: Reportable high-severity boundary fan-out and concurrency burst: the diff changes provider-boundary cardinality from provider count to registered-session count on a user-visible critical path.

### Scenario 2: Add a side chat or spawned subagent while clients already contribute tools/customizations

- Critical path: SessionChatAdded dispatch synchronously walks active clients and the complete post-add chat catalog. Tool setters run inline; customization setters launch asynchronous plugin synchronization and provider reconciliation, so much of the I/O is off the immediate dispatch stack but competes with subsequent chat work and may queue reconfiguration.
- Scaling input: Effective active-client count times the cumulative number of chats in a session. Incrementally adding M chats produces C×M²/2 handle assignments; subagent spawning and side-chat creation both grow M.
- Effective concurrency: All client/chat setter calls are initiated synchronously without batching. AgentPluginManager serializes identical plugin URIs through SequencerByKey, turning duplicate calls into a queue; provider-specific session sequencers further serialize some reconciliation while work across different chats can overlap.
- Cache behavior: Per-chat handles are cached and correctly cleaned up. Copilot skips a deep resync when inputs are structurally equal, but the full loop and repeated setter dispatch remain. Claude and Codex call the process-wide plugin manager; nonce hits avoid copies but still perform cache/filesystem checks, and Codex reparses/reconciles synced plugins.
- Mechanism confidence: Very high: the new branch, full-catalog helper, provider setters, and an added unit test explicitly prove that old chats are revisited.
- Magnitude uncertainty: Most sessions have one active client and few chats, but side-chat and subagent-heavy sessions can accumulate many chats; plugin count and cache-hit rates determine absolute I/O.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentPluginManager.ts:syncCustomizations</code>: Resolve/copy cached client plugins and check nonce directories; cardinality: For each chat-add event, up to active clients × all existing chats × customizations; identical plugin URIs serialize rather than coalesce.
    - Introduced by diff: true; previous behavior: Chat additions did not replay active-client customizations over the existing catalog; only the client's session-scoped assignment was applied.; critical-path effect: Launched by the event handler and continues in background, consuming I/O and delaying queued customization syncs.
  - other expensive boundary at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_syncClientCustomizations and src/vs/platform/agentHost/node/claude/claudeAgent.ts:\_syncClientCustomizations</code>: Parse and reconcile provider customization state, potentially mark/restart Codex thread state or dirty Claude sessions for rebind; cardinality: Repeated for old chat handles on every addition, yielding quadratic cumulative work.
    - Introduced by diff: true; previous behavior: No per-chat replay existed; under the new exact-chat model only the newly added chat requires initialization.; critical-path effect: Mostly asynchronous, but queues provider work and can contend with the next turn or delay customization readiness.
- Verdict: Reportable medium-severity repeated work: use the action's new chat resource for incremental propagation and reserve full fan-out for a changed client snapshot.

### Scenario 3: Create, fork, restore, and lazily materialize an individual chat

- Critical path: The operation reads provider metadata/backing state, opens the relevant session/chat database, and may start or resume the provider SDK subprocess before the chat is usable. Restores for the same session are coalesced and provider sends/materialization are serialized by per-chat/session lifetime or sequencer guards.
- Scaling input: One addressed chat, plus inherited turns when forking/restoring and the number of that chat's customizations; no newly introduced scan across unrelated sessions beyond the catalog issue already reported.
- Effective concurrency: Concurrent restores of the same session share an in-flight promise; Claude/Copilot/Codex use keyed sequencing/lifetime coordination around materialization and teardown. Independent chats may proceed concurrently.
- Cache behavior: Chat backings and live runtime maps provide warm resolution; durable providerData and per-chat databases support cold restore. Failed create paths remove optimistic backing/scope state, and released chats retain only durable routing needed for later resume.
- Mechanism confidence: High: lifecycle calls, keyed sequencers, and backing maps are explicit.
- Magnitude uncertainty: Fork transcript size and SDK startup latency vary by provider and conversation history.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:createSession/restoreSession/createChat</code>: Read/write chat metadata, turns, drafts, providerData, and configuration overlays; cardinality: Bound to the addressed session/chat, with turn-volume-dependent history reads.
    - Introduced by diff: false; previous behavior: Equivalent session-oriented persistence and history boundaries existed; this PR relocates ownership and addressing.; critical-path effect: Required before restored state is published or the first send can proceed.
  - subprocess at <code>ClaudeAgent, CopilotAgent, and CodexAgent chat lifecycle implementations</code>: Create/resume/fork provider conversation; cardinality: One backing operation for the addressed chat, with provider-specific retries/serialization.
    - Introduced by diff: false; previous behavior: Providers already created/resumed SDK sessions; the PR changes chat identity and orchestration.; critical-path effect: Required for materialization or first send; not multiplied by unrelated catalog entries.
- Verdict: No additional reportable regression: work is scoped to the requested chat and duplicate restores/materializations are coalesced.

### Scenario 4: Send a turn, checkpoint files, and publish completion

- Critical path: Before provider send, working directories and attachments resolve and the turn-start checkpoint is awaited. Provider send is then the dominant boundary. Completion schedules changeset work and triggers a session-catalog refresh in the workbench.
- Scaling input: Changed repositories/files for checkpointing, attachment count, and one provider send per turn; the completion-triggered catalog refresh additionally scales with total registered sessions as described in the first scenario.
- Effective concurrency: Selection updates are joined, checkpoint capture is awaited before send, and changeset refresh remains deferred. Provider sends use their existing per-chat sequencing. Catalog hydration fans out without a limiter.
- Cache behavior: Checkpoint and changeset services retain their existing repository-oriented behavior; prompt-cache metadata writes no-op when unchanged. Session metadata is not cached across completion refreshes.
- Mechanism confidence: High for ordering and boundaries; no independent checkpoint regression was found.
- Magnitude uncertainty: Checkpoint cost depends on repository/file state; the reported new cost depends on retained session history.
- Expensive boundaries:

### Scenario 5: Release an idle session or destructively delete a multi-chat session

- Critical path: AgentService visits each catalog chat, awaiting provider release/dispose operations; destructive teardown orders peer chats before the default chat and then removes durable host state/worktrees.
- Scaling input: Number of actual chats/backing SDK conversations in the session, not all registered sessions.
- Effective concurrency: Per-session teardown is intentionally sequential to preserve default-last ordering and keyed provider lifecycle semantics; failures are accumulated so all chats are still visited.
- Cache behavior: Release removes live runtime state while retaining durable backing metadata for cold resume. Destructive disposal removes per-chat active-client handles, provider routing/backing maps, trace contexts, and managed resources; no unbounded retained map was found.
- Mechanism confidence: High: disposal loops and provider cleanup paths explicitly remove chat-keyed handles/maps and preserve required ordering.
- Magnitude uncertainty: Sessions generally have few chats, while subagent-heavy sessions may have more; provider shutdown duration varies.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/agentService.ts:\_disposeSession/\_releaseSession</code>: Provider-specific conversation destroy/unsubscribe/stop operations; cardinality: One per actual chat backing during teardown.
    - Introduced by diff: true; previous behavior: Single-session providers previously exposed coarser session teardown; the added calls correspond to newly independent chat backings.; critical-path effect: Deletion/release waits for all chat operations; default-chat-last ordering protects shared scope cleanup.
  - filesystem at <code>AgentService and provider disposeChat implementations</code>: Delete provider data and managed worktree/session storage on destructive teardown; cardinality: Bound to the deleted session and its concrete chat resources.
    - Introduced by diff: false; previous behavior: Session deletion already removed provider and host durable resources.; critical-path effect: Required before destructive deletion completes.
- Verdict: No reportable cleanup regression: cost grows with independently owned resources and cleanup prevents lifetime leaks.
