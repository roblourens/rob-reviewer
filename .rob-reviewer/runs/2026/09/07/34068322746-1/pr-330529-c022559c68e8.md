# Performance review: agentHost: add session and chat rename tools

[PR #330529](https://github.com/microsoft/vscode/pull/330529) at `c022559c68e8846c60fc37c67732ad52e6d8de2a`

## Findings (4)

### 1. [high] Avoid scanning the full session catalog for an in-place rename

**Finding ID:** `PERF-76693211AAA0`  
**Location:** <code>src/vs/platform/agentHost/node/shared/sessionServerTools.ts:825</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SQLite/filesystem operations and provider IPC calls  
**Scaling:** Each automatic current-session rename performs O(S) metadata work for S registered sessions: one registry query, per-session database/provider-data reads, per-session provider metadata lookups, and another per-session metadata overlay read; concurrent lookups are launched with Promise.all.  
**Outcome:** The first response is delayed before it can finish, with latency and I/O/IPC load growing with the user's accumulated session count.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no automatic rename tool call at the end of a new session's first request, so that request did not enumerate the entire session catalog merely to rename itself.  
**Changed behavior:** The new rename\_session implementation always awaits accessor.listSessions(), even when the tool omitted session and currentSession already identifies the target; the new first-request reminder explicitly asks the agent to make exactly this call.  
**Confidence:** 0.99 — The automatic reminder, tool dispatch, unconditional list call, AgentService fan-out, per-session database reads, and Copilot provider IPC are all directly traced. Exact per-provider duration varies, but the O(S) critical-path mechanism is unambiguous.

**Causal diff evidence:** The added \`const sessions = await accessor.listSessions();\` at RIGHT line 825 is unconditional in the newly introduced automatic rename tool, despite \`currentSession\` already being passed by the changed dispatch path.

With tens or hundreds of saved sessions, every newly created session's first response can trigger a burst of provider metadata calls and per-session SQLite reads and must wait for the slowest one before the rename tool returns and the model can produce its final response. The sibling rename\_chat path has the same unconditional catalog scan for current peer chats.

**Evidence:** applyRenameSessionTool line 825 calls listSessions before resolving the already-supplied currentSession. AgentService.listSessions reads the global registry, maps every registered session through \_registeredSessionMetadata, and then opens every returned session database for getMetadataObject. For Copilot, \_registeredSessionMetadata reaches CopilotAgent.getChatMetadata, which calls client.getSessionMetadata over the provider boundary for each session; Codex can similarly reach \_readSession/thread reads for non-live entries. AgentHostSessionTitleController injects a reminder requiring rename\_session on the first active-agent request, making this scan part of the normal first-response path rather than an explicit catalog operation.

**Suggested direction:** Resolve and validate the current-session/current-peer case directly from the current state (or a targeted metadata accessor), and call listSessions only when an explicit cross-session URI must be resolved. Preserve the full validation path for explicit targets.

### 2. [medium] Do not serialize every Copilot prompt when no prompt hook needs stdin

**Finding ID:** `PERF-EBD2D5905AAB`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotPluginConverters.ts:438</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU time and temporary strings proportional to the user prompt payload  
**Scaling:** One JSON serialization occurs for every Copilot user prompt, with CPU and allocated bytes growing linearly with prompt size; this repeats across all turns and concurrent chats even after naming is complete or disabled.  
**Outcome:** Large pasted prompts incur avoidable synchronous CPU work and allocation/GC pressure before the SDK can continue processing the turn.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The UserPromptSubmitted handler was installed only when plugin prompt commands existed, so sessions without those commands did not stringify the hook input at all.  
**Changed behavior:** The broadened condition installs the handler whenever the internal title callback exists, and CopilotSessionLauncher now always supplies that callback. The handler immediately runs JSON.stringify(input) even when promptCommands is empty and the callback returns no additional context.  
**Confidence:** 0.99 — The launcher-to-converter call path and unconditional callback are explicit, and JSON.stringify necessarily scales with the prompt-bearing input. Only the exact size distribution of user prompts is uncertain.

**Causal diff evidence:** The changed condition at RIGHT line 438 expands execution of the existing JSON.stringify block from sessions with actual prompt hook commands to every Copilot session because the PR also unconditionally wires onUserPromptSubmitted.

All Copilot turns now copy/serialize the full prompt object solely for a command loop that is usually empty. Large code/log pastes amplify the added latency and GC work, while ordinary turns pay the fixed handler and serialization cost indefinitely.

**Evidence:** RIGHT line 438 makes editTrackingHooks.onUserPromptSubmitted sufficient to install the handler. CopilotSessionLauncher always passes that function. Inside the handler, \`const stdin = JSON.stringify(input)\` runs before iterating \`promptCommands ?? \[\]\`; CopilotAgentSession.handleUserPromptSubmitted often returns undefined once no rename instruction is present, but the serialization has already happened.

**Suggested direction:** Only compute \`stdin\` inside a \`promptCommands?.length\` branch (or lazily on the first command), then return the internal additional-context callback directly when there are no shell commands.

### 3. [medium] Persist title provenance once instead of issuing duplicate SQLite writes

**Finding ID:** `PERF-E4AFE7E7DCE6`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionTitleController.ts:219</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Per-session SQLite INSERT operations, database references, and queued write promises  
**Scaling:** The cost repeats for every newly seeded or refined session/chat title. A fresh active-agent session issues three separate metadata writes for one fallback title, while a successful utility-generated title now issues source plus title/source writes after an earlier source write, versus one final title write before the PR.  
**Outcome:** Title creation produces 3-4x metadata write traffic, increasing filesystem I/O and queue contention and extending deletion/idle-eviction waits that now drain pending session writes.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Applying a fallback title did not write metadata, and successful utility title generation persisted the final custom-title key once.  
**Changed behavior:** \_applySeedTitle now immediately writes the auto source. The active path then calls markTitleAuto, whose \_persistAutoTitle writes both title and the same source as two more independent setMetadata calls. Utility generation similarly writes source in apply and then writes title plus source again in persist.  
**Confidence:** 0.98 — The synchronous call sequence and exact INSERT multiplicity are directly visible in the changed methods. Storage latency varies, but the repeated I/O and new lifecycle wait are certain.

**Causal diff evidence:** The added source persistence at RIGHT line 219 duplicates the source write performed by the newly expanded \`\_persistAutoTitle\`; this turns one logical title update into multiple physical metadata writes.

Every first session/chat title creates multiple serialized SQLite writes for the same provenance value. These writes are fire-and-forget but retain database references and are explicitly awaited by the new whenIdle calls during eviction/deletion, so the amplification affects I/O throughput and lifecycle latency.

**Evidence:** RIGHT line 219 adds \`\_persistAutoTitleSource\` to the common session apply path. seedTitleFromFirstMessage immediately follows that apply with markTitleAuto in active mode; markTitleAuto calls \_persistAutoTitle, which invokes persistSessionMetadata separately for customTitle and customTitleSource. In utility mode, \_generateTitle invokes apply and then persist consecutively, causing the source write in both callbacks. SessionDatabase.setMetadata serializes each as a distinct INSERT.

**Suggested direction:** Commit title and provenance together once at the persistence point, using the new setMetadataValues transaction/helper where ordering matters. Keep in-memory provenance during apply and remove duplicate source-only writes unless a path truly has no subsequent title persistence.

### 4. [low] Bound Unicode title normalization before materializing prompt characters

**Finding ID:** `PERF-33819518C320`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionTitleController.ts:174</code> (<code>RIGHT</code>)  
**Performance category:** <code>gc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Per-code-point array elements and copied strings derived from the full first user prompt  
**Scaling:** Allocation grows O(N) with the complete first prompt even though only 40 or 200 code points can appear in the title; the active path additionally slices and joins the entire remainder while looking for a word boundary.  
**Outcome:** Large pasted first prompts create avoidable memory churn and synchronous CPU/GC work before the request is sent to the provider.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The normalizer collapsed whitespace and used string.slice(0, 200), which did not allocate an array entry for every code point in the full prompt.  
**Changed behavior:** The changed normalizer calls Array.from on the entire normalized prompt before slicing to maxLength. The new active-agent normalizer repeats this full materialization and can also copy/join all characters after position 40.  
**Confidence:** 0.95 — The full-input allocations and pre-send call path are explicit. User prompt sizes vary, so severity is low, but large pasted prompts are a realistic supported input.

**Causal diff evidence:** RIGHT line 174 replaces the prior bounded string slice with a full code-point array allocation on the first-message hot path.

A first request containing a large pasted log, source file, or generated text allocates a full code-point array solely to derive a short display title, delaying turn startup and increasing young-generation GC pressure.

**Evidence:** RIGHT line 174 materializes \`Array.from(text.trim().replace(...))\` before applying the 200-character cap. The adjacent active path creates \`characters = Array.from(normalized)\` and later \`characters.slice(40).join('')\`, although its output target is only 40 characters. seedTitleFromFirstMessage runs synchronously from ChatTurnStarted before provider send setup.

**Suggested direction:** Collapse/iterate code points incrementally and stop once the output cap plus the needed next-word boundary is known; do not build an array or joined suffix for the entire prompt.

### Scenario 1: First request in a newly created default session with active-agent naming enabled

- Critical path: The host seeds a provisional title, awaits title-source preparation, sends the prompt, and instructs the model to call rename\_session before its final response. The rename tool must finish its catalog scan and atomic title persistence before the model can continue to the final response.
- Scaling input: Number S of registered sessions accumulated across providers; the automatic flow invokes one rename per new session, and each scan processes all S sessions after registry filtering.
- Effective concurrency: AgentService uses Promise.all across all registered sessions and another Promise.all for per-session overlays, so per-session filesystem/database/provider work is burst concurrently without a limiter. Metadata writes for the renamed session are serialized by that SessionDatabase's metadata sequencer.
- Cache behavior: There is no result cache or request coalescing for listSessions. Warm per-session database references can avoid reopening SQLite connections, but tryOpenDatabase still checks file existence and each call executes metadata queries; provider metadata may be served from live state for some Codex sessions, while Copilot still performs getSessionMetadata IPC for each listed session.
- Mechanism confidence: High: the reminder, tool dispatch, unconditional listSessions call, per-session fan-out, and final-response dependency are directly traced.
- Magnitude uncertainty: The exact delay depends on catalog size, provider mix, disk speed, and whether sessions are live, but users with tens or hundreds of sessions are realistic and the O(S) fan-out is certain.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostDatabase.ts:listSessions</code>: Read the global session registry; cardinality: One query per rename tool invocation
    - Introduced by diff: false; previous behavior: Used for explicit catalog operations, not automatically on every new session's first response; critical-path effect: Blocks construction of the catalog needed by the rename tool
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts:listSessions/\_readDefaultChatProviderData</code>: Check/open each session database and read provider data plus metadata overlays; cardinality: Multiple checks/queries for each of S registered sessions, after provider filtering
    - Introduced by diff: true; previous behavior: The first response did not invoke listSessions solely to rename its current session; critical-path effect: The rename waits for all per-session reads
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:getChatMetadata</code>: Fetch provider session metadata, including Copilot client.getSessionMetadata for each registered Copilot session; cardinality: Up to one provider call per registered session; effective count follows the provider mix and live-session fast paths

  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_renameSessionFromTool</code>: Persist title and source atomically; cardinality: One transaction with two INSERTs per successful rename

- Verdict: Reportable high-severity boundary fan-out because an in-place rename now performs catalog-wide I/O/IPC on the first-response critical path.

### Scenario 2: First request in a newly created peer chat with active-agent naming enabled

- Mechanism confidence: High: the unconditional list call and automatic reminder are explicit.
- Magnitude uncertainty: Peer chats are less frequent than default sessions, but the same session-count scaling applies whenever the flow is used.
- Expensive boundaries:

### Scenario 4: Session/chat title seeding and utility-model refinement

- Critical path: Fallback title normalization runs synchronously during ChatTurnStarted before provider send. Utility-model generation and its metadata writes are scheduled asynchronously; active-agent fallback metadata writes are also fire-and-forget, although later eviction/deletion waits for them.
- Scaling input: First-prompt length N controls normalization allocations; number of newly titled sessions/chats and title refinements controls metadata write count.
- Effective concurrency: Title metadata writes are queued through one per-database metadata Sequencer. Utility generation network calls retain their existing cancellation and GitHub-context limiter behavior; active-agent mode skips them.
- Cache behavior: No normalization cache. In-memory title sets prevent repeated seeding for an already titled live target, so the large-input allocation is once per newly titled session/chat. Metadata writes are not coalesced, including repeated writes of the same source value.
- Mechanism confidence: High: both normalization and persistence call sequences are explicit.
- Magnitude uncertainty: The write latency depends on SQLite/filesystem characteristics and prompt sizes vary, but exact write multiplicity and full-input allocations are deterministic.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/agentHost/node/agentHostSessionTitleController.ts:\_normalizeTitle/\_normalizeActiveAgentFallbackTitle</code>: Collapse whitespace and materialize the full prompt as code-point arrays/strings to derive a 40/200-character title; cardinality: Once for the first message of each newly titled session/chat; O(N) allocated elements/bytes
    - Introduced by diff: true; previous behavior: Whitespace normalization still scanned the string, but bounded slicing did not create one array element per code point or join the entire suffix; critical-path effect: Runs synchronously before provider send
  - database at <code>src/vs/platform/agentHost/node/agentHostSessionTitleController.ts:\_applySeedTitle/\_persistAutoTitle</code>: Write automatic title and provenance metadata; cardinality: Three writes for one active-agent fallback; up to four around a utility-generated initial title where one final-title write previously sufficed

  - network at <code>src/vs/platform/agentHost/node/agentHostSessionTitleController.ts:\_generateTitleFromPrompt</code>: Utility-model title completion and optional GitHub issue/PR enrichment; cardinality: Existing bounded generation calls when active-agent mode is disabled; active-agent mode removes these calls
    - Introduced by diff: false; previous behavior: Utility model generation already ran when enabled by the old flow; critical-path effect: Off the initial send critical path and cancellable; not a regression introduced by the active path
- Verdict: Reportable repeated-write and large-input allocation regressions; the removed utility-model call in active mode is a performance improvement but does not offset these mechanisms on disabled mode or lifecycle paths.

### Scenario 5: Idle eviction and explicit session deletion

- Critical path: After provider teardown, deletion waits for pending per-session database writes before removing data. Idle eviction now also waits for pending writes before dropping in-memory session/provider state; this is off active interaction unless an unsubscribe immediately triggers eviction.
- Scaling input: Number and duration of pending writes for the one session, amplified by the duplicate title metadata writes. Chat count controls title-state cleanup iteration.
- Effective concurrency: whenIdle repeatedly waits for the current pending-write set; metadata writes are serialized, so drain time is the sum of queued metadata operations. Re-subscription/restoration checks prevent eviction after the wait.
- Cache behavior: openDatabase acquires a ref-counted, lazily initialized database; calling whenIdle alone does not open SQLite when there are no pending writes. Existing live references share the same database object.
- Mechanism confidence: High for the lifecycle sequence; uncertain only in observed queue depth.
- Magnitude uncertainty: Normally the queue is short; duplicate title writes increase it. The wait is intentional for durability, so only the write amplification is reported rather than the cleanup ordering itself.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_whenSessionDataIdle</code>: Wait for pending session writes to settle; cardinality: Once per deletion and once per eligible idle eviction; waits over writes already queued for that session
    - Introduced by diff: true; previous behavior: Deletion/eviction could proceed without draining pending metadata writes; critical-path effect: Blocks deletion completion or eviction, not active turn progress
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts:disposeSession</code>: Delete per-session data and optional worktree; cardinality: One recursive session-data deletion and at most one worktree cleanup per explicit disposal
    - Introduced by diff: false; previous behavior: The same deletion boundaries existed without the preceding drain; critical-path effect: Existing destructive cleanup path; the new wait precedes it for ordering
- Verdict: No separate cleanup-lifecycle finding: waiting is a justified ordering constraint, while the avoidable queue growth is captured by the repeated-write finding.
