**Relevant issue families:** synchronous-ui-work, cleanup-lifecycle, repeated-work

### Scenario 1: Open and interact with an ordinary action widget, including keyboard invocation beneath a stationary pointer and the first deliberate mouse movement or click.

- Critical path: Popup construction, list rendering/layout, focus, and the first pointer event are synchronous UI work. The diff removes one fixed full-window pointer-shield node and two listeners, then adds a temporary list mousemove subscription. Before pointer activation, a mousemove maps the event to one virtual-list row; the first non-zero movement clears the subscription and invokes the same hover/focus path previously reached by mouseover after the shield was removed. No asynchronous boundary must complete.
- Scaling input: One ActionListWidget per visible popup. Cost is constant per popup plus one mapped non-zero mousemove; zero-delta events can be mapped until activation, but these are bounded by the short open-to-interaction interval and perform only row lookup. Menu item count does not multiply the new listener work.
- Effective concurrency: All changed work runs serially on the renderer event loop. There is one temporary subscription per live widget, and the service presents one ordinary action widget at a time.
- Cache behavior: No cache behavior changes. List rendering and existing hover/submenu state are unchanged; the temporary subscription is newly created per widget and disposed on first real movement, mousedown, or widget disposal.
- Mechanism confidence: High confidence: the diff and ListView implementation show one event-to-row mapping before self-disposal, while removal of the full-window element reduces DOM/listener work.
- Magnitude uncertainty: Exact rates of synthetic zero-delta mousemove events vary by browser/input device, but the changed handler is short-lived and has no collection-wide or boundary work, so no realistic user-visible regression is established.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added work is bounded and lightweight, while the removed full-window shield eliminates a DOM element and event listeners.

### Scenario 2: Open, switch tabs in, hover, and directly click items in the tabbed model/workspace pickers.

- Critical path: Each show or tab switch synchronously constructs popup chrome and an ActionList, renders rows, and lays out the context view. The diff removes the tabbed full-window pointer shield; the shared ActionList adds only the bounded initial-movement handling described above. Model/workspace list building already occurred on this path and is not made more frequent by the diff.
- Scaling input: The changed pointer handling remains one temporary listener per active tab's ActionList, independent of model/workspace count after virtual-list event mapping. A tab swap replaces and disposes the prior popup/list.
- Effective concurrency: Popup rebuilds and pointer handling are serialized on the UI thread. The MutableDisposable permits only one active popup; tab swaps dispose the old list before installing the new one.
- Cache behavior: The tabbed widget retains its existing sizing measurements and previous-tab geometry/text state. The diff neither invalidates those caches nor changes cold/warm model-list construction.
- Mechanism confidence: High confidence from TabbedActionListWidget ownership and ActionList listener disposal paths.
- Magnitude uncertainty: Provider/model counts vary, but the diff does not add per-model processing, repeated list construction, or boundary calls.
- Expensive boundaries: none found
- Verdict: No reportable regression. Direct clickability is achieved by deleting an overlay; new pointer work is constant and bounded.

### Scenario 3: Show an action/context-view overlay above an editor backed by a native WebContentsView.

- Critical path: DOM mutations from opening or closing overlays are observed and microtask-coalesced; BrowserOverlayManager then computes overlapping DOM rectangles and hit-tests the overlap. Existing renderer logic may capture a screenshot and issue native model visibility changes when obscured state changes. Removing the pointer shield and its exclusion leaves the tracked context-view overlay as the authoritative overlap, so it does not add or multiply that downstream work.
- Scaling input: Overlay checks scale with the existing number of tracked overlays and browser editor containers. The diff removes one child element and one excluded-class test; it does not increase overlay cardinality.
- Effective concurrency: Mutation notifications are microtask-coalesced. Per browser renderer, visibility updates are state-guarded; hiding is scheduled by one animation-frame callback and screenshot work follows the existing asynchronous cadence.
- Cache behavior: Overlay rectangles remain cached while observers are connected; microtask emission still coalesces structural mutations. Removing the deleted class from the exclusion array slightly reduces each exclusion scan and does not change cache invalidation.
- Mechanism confidence: High confidence from the overlay definitions, hit-test exclusion path, and renderer subscription/visibility guards.
- Magnitude uncertainty: The number of simultaneous browser editors and overlays varies, but all changed mechanisms reduce or preserve work rather than increasing it.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/browserView/electron-browser/features/webContentsViewRendererFeature.ts:\_refresh</code>: Existing IBrowserViewModel.setVisible call hides or shows the native WebContentsView when overlay obscuration changes.; cardinality: At most one call when the computed visibility state transitions; repeated overlay notifications with unchanged state do not call setVisible.
    - Introduced by diff: false; previous behavior: Opening the same tracked context-view already obscured the browser view and could transition visibility.; critical-path effect: A hide is deferred one animation frame; a show is initiated asynchronously. The diff does not add this boundary or increase its transition count because the context-view remains tracked before and after.
  - IPC at <code>src/vs/workbench/contrib/browserView/electron-browser/features/webContentsViewRendererFeature.ts:\_doScreenshot</code>: Existing native browser-view screenshot capture via IBrowserViewModel.captureScreenshot.; cardinality: One capture on a relevant hide/refresh transition, followed by the existing one-second screenshot loop while visible.
    - Introduced by diff: false; previous behavior: The pointer-shield/context-view mutations already triggered overlay observation and screenshot/visibility handling.; critical-path effect: The screenshot is initiated before deferred hiding but is not awaited by overlay-state handling. The diff removes one DOM mutation and does not introduce or multiply captures.
- Verdict: No reportable regression. Native screenshot and visibility boundaries are pre-existing and retain their cardinality; the removed overlay node reduces mutation and hit-test work.

### Scenario 4: Run Playwright automation and component fixtures that select or hover model-picker rows.

- Critical path: Automation now performs a normal click instead of a forced click, with the same wait and existing retry structure. The component fixture emits one additional synthetic mousemove before its existing 50 ms settle delay. These paths affect tests only, not product startup or interaction.
- Scaling input: One added synthetic mousemove per rendered fixture that requests an open card; Playwright click count remains one per attempt and does not scale with row count.
- Effective concurrency: Automation operations remain sequential and awaited. Existing retries are serialized until confirmation or timeout.
- Cache behavior: No cache behavior is involved.
- Mechanism confidence: High confidence from the changed automation calls and fixture dispatch.
- Magnitude uncertainty: Browser actionability-check timing for normal clicks can vary, but the production overlay removal directly removes the prior blocker and no additional call count is introduced.
- Expensive boundaries:
  - IPC at <code>test/automation/src/chat.ts:Chat.selectModel and test/automation/src/agentsWindow.ts model selection helper</code>: Playwright sends a click command to the browser page.; cardinality: One click per selection attempt; the pre-existing retry loop remains, but removing the intercepting shield makes retries less rather than more likely.
    - Introduced by diff: false; previous behavior: The same click command was issued with force:true and could fail to commit due to the pointer shield, causing retries.; critical-path effect: The click is awaited in the automation flow. Changing force mode does not add a command or boundary crossing.
- Verdict: No reportable product performance regression; test-side boundary cardinality is unchanged and likely reduced in failed-attempt cases.
