- Effective concurrency: One dial per normalized address is enforced by \_pendingConnects; distinct configured hosts may connect concurrently. ProxyJump chains are handled by one native OpenSSH process.
- Cache behavior: There is no SSH-config cache; \`ssh -G\` is rerun for each full connection. Same-address concurrent requests are coalesced, and a live connection is reused where possible.
- Mechanism confidence: High: changed lines directly add the bridge filesystem work and one proxy subprocess to this path.

### Scenario 2: Startup auto-connect or full automatic reconnect for persisted proxied SSH hosts

- Critical path: Each configured auto-connect entry independently resolves SSH config and establishes a full proxy-backed SSH connection. A failed full dial retries with exponential backoff; successful relay-only restoration reuses the existing SSH client and proxy transport.
- Scaling input: Number of persisted auto-connect hosts H; added live proxy processes and bridge setup scale O(H), while failure work is bounded to 10 sequential attempts per address.
- Effective concurrency: Per-address attempts are coalesced and retries are serialized with exponential backoff up to 10 attempts. Startup reconciliation has no global host limiter, so distinct configured entries connect concurrently, as before.
- Cache behavior: No cache across full attempts. A warm live SSH connection avoids config resolution and proxy respawn during relay replacement; failed or dropped SSH connections require a cold full attempt.
- Mechanism confidence: High for per-host subprocess/filesystem cardinality and retry serialization; moderate for startup magnitude because configured-host counts are unknown.
- Magnitude uncertainty: Users may persist from one to several hosts; very large host collections are possible but not established as a realistic dominant case. Existing remote bootstrap work already fans out across the same collection.
- Expensive boundaries:

### Scenario 3: Native proxy helper requests host confirmation, password, or key passphrase

- Critical path: OpenSSH launches the configured askpass executable, which connects to the attempt-local IPC server; the shared process emits a renderer IPC request and waits for user input before replying to the helper and allowing SSH authentication to continue.
- Scaling input: Number of interactive prompts P in one connection attempt; CPU, process, and IPC work scale O(P), while prompt payloads are bounded.
- Effective concurrency: OpenSSH normally serializes authentication prompts. The implementation supports separate request IDs if multiple helpers prompt and cleans each listener/request when settled or cancelled.
- Cache behavior: No prompt response caching, appropriately avoiding reuse of secrets or trust answers. Background reconnects fail closed without emitting UI requests.
- Mechanism confidence: High: the subprocess, local IPC, renderer IPC, cancellation, and payload bounds are explicit in the changed code.
- Magnitude uncertainty: Authentication methods and jump chains determine P, but normal connections use a small bounded sequence.
- Expensive boundaries:

### Scenario 4: Disconnect, failed handshake, cancellation, or service disposal of a proxied connection

- Critical path: The proxy socket and streams are destroyed immediately; if the helper remains active, process-tree termination runs asynchronously. Askpass sockets, server, launcher files, helper file, and endpoint/junction are then closed or removed.
- Scaling input: Number of concurrently closing proxied connections C; cleanup process and filesystem work scale O(C) with fixed work per connection.
- Effective concurrency: Each transport owns one idempotent cleanup operation. Distinct host disconnects may clean up concurrently; repeated error/close/dispose signals collapse through the local disposed guard.
- Cache behavior: No cache is involved. Ownership transfers preserve the live proxy transport during relay replacement, avoiding premature cleanup and respawn.
- Mechanism confidence: High: ownership is carried in SSHConnection, WeakMap handoff is deleted after adoption, and all failure/close/dispose paths call idempotent cleanup.
- Magnitude uncertainty: Platform process-tree termination cost varies, but it occurs only for a still-live helper and does not block immediate stream teardown.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:1819-1849 \_createProxyTransport.dispose</code>: Invoke process-tree termination for a still-live proxy helper, falling back to direct SIGKILL if tree termination fails.; cardinality: At most once per proxy transport because disposal is idempotent.
    - Introduced by diff: true; previous behavior: There was no native proxy process tree to terminate.; critical-path effect: Socket destruction is synchronous; the killTree subprocess is not awaited and is off the connection's immediate teardown path.
  - filesystem at <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:1762-1770 \_createNativeSSHAskpassBridge.dispose</code>: Asynchronously unlink the POSIX launcher, helper, and socket path or recursively remove the Windows junction.; cardinality: A fixed number of removals once per bridge; disposal is idempotent.
    - Introduced by diff: true; previous behavior: No launch artifacts or askpass endpoint existed.; critical-path effect: Cleanup is off the immediate critical path after server/socket closure.
- Verdict: No leak or repeated-cleanup finding. The diff retains the transport only for the owning connection, disposes it on all traced terminal paths, and guards cleanup against duplicate signals.
