### 1. [medium] Batch cross-root conflict scans across migration groups

**Finding ID:** `PERF-A64925E945BE`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpServerCustomizationMigration.ts:243</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** remote/local filesystem reads of every workspace root's .mcp.json and .vscode/mcp.json  
**Scaling:** With R working-directory roots and selected candidates in G roots, each conflict pass performs 2\*G\*(R-1) file reads; the same scan runs before migration, after the target write, and after the source write, reaching about 6\*R\*(R-1) reads when G=R.  
**Outcome:** Migration latency grows quadratically and all reads are serialized on the user-confirmation critical path, which can make multi-root remote workspaces take seconds or minutes to finish.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no MCP server migration execution path and therefore no cross-root filesystem scan when migrating customizations.  
**Changed behavior:** The new execution loop calls findCrossRootConflicts once for each source/target group, while findCrossRootConflicts sequentially reads both MCP configuration files in every other root; migrateGroup repeats that full cross-root scan twice more for revalidation.  
**Confidence:** 0.99 — The nested group/root loops, three call sites, exact two-read boundary per other root, and serial awaits are explicit in the added code. Root counts and provider latency vary, so prevalence affects severity, but the quadratic mechanism and critical-path reachability are certain.

**Causal diff evidence:** Added RIGHT line 243 starts a sequential \`for (const root of roots)\` scan that reads both root MCP files; added line 218 places the first scan inside the per-group loop, and added ensureNoCrossRootConflicts calls repeat it after target and source writes.

Migrating eligible servers spread across a multi-root workspace, especially through a remote filesystem provider, blocks completion on hundreds or thousands of sequential file operations; e.g. 20 roots produce roughly 2,280 cross-root reads.

**Evidence:** executeMigration iterates groups serially (line 218) and awaits findCrossRootConflicts (line 216/line 217 context). The helper at lines 241-273 iterates all roots and awaits readTargetDocument plus readSourceDocument for each other root. migrateGroup then invokes ensureNoCrossRootConflicts after the target write and again after verification, and that helper delegates to the same full scan. For a realistic 10-root workspace with one selected group per root, this is 540 cross-root reads before counting each group's own source/target reads and writes.

**Suggested direction:** Snapshot each root's source and target once per required validation phase, build a name-to-root conflict index, and reuse it for all groups; preserve optimistic concurrency by revalidating each file once at the phase boundary (or only affected names/files), rather than rescanning every root for every group.

### 2. [medium] Coalesce duplicate MCP-triggered migration refreshes

**Finding ID:** `PERF-B3E096A933B4`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts:1175</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** MCP support assessments, per-root MCP configuration file reads, customization collection scans, and synchronous migration-page DOM renders  
**Scaling:** Each MCP server-list or enablement change is observed both directly by the added autorun and indirectly through IMcpWorkbenchService.onChange; every invocation recomputes all enabled migration categories, and when MCP migration is enabled each uncancelled computation reads one source file per distinct candidate root.  
**Outcome:** Duplicate I/O and CPU/DOM work increases editor latency and can cause visible loading/render churn, with cost growing with workspace roots, MCP servers, and customization candidates.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, MCP inventory and enablement changes did not trigger customization-migration recomputation in the management editor.  
**Changed behavior:** The PR adds an IMcpWorkbenchService onChange listener and a separate autorun over the same IMcpService server list and enablement observables. Both immediately call refreshCustomizationMigrationInfo, which only uses a sequence to discard stale results and does not cancel or coalesce the work already started.  
**Confidence:** 0.97 — The duplicate dependency is directly established by the editor's two added subscriptions and McpWorkbenchService's existing derived onChange implementation. Exact latency depends on root count and provider speed, but both refreshes and their uncancelled critical-path work are deterministic.

**Causal diff evidence:** Added RIGHT line 1175 begins the direct IMcpService autorun, while adjacent added line 1174 also subscribes to IMcpWorkbenchService.onChange; both route to the same uncoalesced refresh method.

While the Customizations editor is open, toggling/installing/updating an MCP server can launch duplicate full refreshes. In an enabled multi-root migration setup this doubles per-root configuration reads; even with MCP migration disabled by default, it unnecessarily reruns the default-enabled prompt migration and loading render for unrelated MCP changes.

**Evidence:** McpWorkbenchService already observes mcpService.servers and every server.enablement and fires onChange for those changes (mcpWorkbenchService.ts lines 372-384). The added editor subscriptions at lines 1174-1180 therefore launch at least two refreshes for one enablement/list change. refreshCustomizationMigrationInfo synchronously renders loading state, then starts every enabled category; computeMcpServerMigration awaits support and calls createPlan, whose ResourceMap only deduplicates reads within one call, not across the overlapping refreshes. The refreshSequence checks occur after this work and merely drop the older result.

**Suggested direction:** Route all MCP signals through one RunOnceScheduler/delayer (or subscribe to one authoritative source), gate it on the MCP migration setting, and cancel/suppress superseded refresh computations so one logical MCP change produces one assessment, one per-root planning pass, and one UI update.
