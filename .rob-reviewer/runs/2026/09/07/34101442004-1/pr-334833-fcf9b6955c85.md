### 1. [medium] Avoid rebuilding each platform just to extract Agent Host E2E

**Finding ID:** `PERF-A1E5C59319FC`  
**Location:** <code>.github/workflows/pr.yml:153</code> (<code>RIGHT</code>)  
**Performance category:** <code>throughput</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** three additional runners performing checkout, dependency-cache extraction, full transpilation, Electron download, and filesystem/network I/O  
**Scaling:** For every PR classified as Agent Host-affecting, the cost is repeated once on each of Linux, macOS, and Windows; the classifier includes broad prefixes such as \`build/\`, \`src/vs/base/\`, and \`src/vs/platform/\`, so this is not limited to changes in the E2E tests themselves.  
**Outcome:** increased runner-minutes and boundary I/O, with lower aggregate CI throughput and additional shared-pool queue pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Agent Host E2E ran from each existing Electron integration job after that job had already restored dependencies, transpiled the client and extensions, and downloaded Electron; unaffected changes skipped the suite in place.  
**Changed behavior:** The integration jobs now always skip Agent Host E2E, while each affected platform starts a separate full reusable workflow whose only enabled test is Agent Host E2E, repeating all unconditional preparation solely to move the suite beside the integration job.  
**Confidence:** 0.98 — The move from in-job execution to three new reusable-workflow invocations and the unconditional transitive setup steps are explicit. Exact queue delay depends on runner availability, but the added work and its three-platform cardinality are certain.

**Causal diff evidence:** The added reusable-workflow call at \`.github/workflows/pr.yml:153\` creates a dedicated Linux job, with equivalent added calls for macOS and Windows. The diff simultaneously changes each original integration workflow to \`VSCODE\_SKIP\_AGENT\_HOST\_E2E: '1'\`, proving the test execution was moved out of an already-prepared job into three newly prepared jobs.

A realistic platform or build change now causes three extra full repository preparations before the same three platform suites run. Parallel execution can shorten that PR's longest check, but the duplicated CPU, cache traffic, and Electron downloads consume additional shared CI capacity and reduce throughput for concurrent PRs.

**Evidence:** Following this call into the platform workflows shows that \`unit\_tests\`, \`integration\_tests\`, and \`smoke\_tests\` being false does not bypass checkout, node\_modules cache download/extraction (or install), built-in-extension cache access, \`transpile-client-esbuild transpile-extensions\`, or Electron download. Only after all of those boundaries does \`scripts/test-agent-host-e2e.ts\` run. Previously that script was reached from the already-prepared Electron integration job, so the diff adds three complete setup passes whenever detection returns true.

**Suggested direction:** Keep Agent Host E2E parallel, but fan the integration and E2E test jobs out from one prepared build artifact per platform, or otherwise make the dedicated E2E workflow consume existing compiled outputs instead of rerunning the full platform bootstrap.

### 2. [medium] Share smoke setup instead of rerunning the full platform workflow

**Finding ID:** `PERF-30DA1A8D5D1E`  
**Location:** <code>.github/workflows/pr.yml:174</code> (<code>RIGHT</code>)  
**Performance category:** <code>throughput</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** runner CPU plus checkout, cache-download/extraction, Electron-download, and filesystem I/O  
**Scaling:** The duplicated setup grows with smoke shard count and PR concurrency: this change adds one full chat workflow on each of Linux, macOS, and Windows, plus a third full macOS proxy workflow, so every PR performs four extra platform preparations before executing the partitioned tests.  
**Outcome:** substantially more runner-minutes and I/O per PR, reducing aggregate CI throughput and increasing queue pressure when PRs run concurrently  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each platform had one Electron smoke job that performed checkout, dependency/cache restore, client and extension transpilation, Electron download, smoke compilation, and then ran the complete smoke suite; the macOS proxy tests reused that already-prepared job.  
**Changed behavior:** The added chat job invokes the same reusable Linux workflow as an independent job; analogous added macOS and Windows chat jobs and the macOS proxy job each independently repeat all unconditional preparation before running only their shard.  
**Confidence:** 0.98 — The new workflow invocations, their always-on PR conditions, and every transitive setup step are explicit in the YAML; the before/after job cardinality is exact. Only the magnitude of queue delay depends on cache size and available runner capacity, so severity is medium rather than high.

**Causal diff evidence:** The added \`uses: ./.github/workflows/pr-linux-test.yml\` at \`.github/workflows/pr.yml:174\` creates a second Linux smoke job. The same diff adds equivalent chat invocations for macOS and Windows and a separate macOS proxy invocation, while the reusable workflows unconditionally restore/extract node\_modules, restore built-ins, run \`transpile-client-esbuild transpile-extensions\`, and download Electron for every invocation.

On every PR, smoke coverage now launches two complete prepared environments per platform and three on macOS instead of one, even though each added environment runs only a complementary subset. This trades test wall-clock latency for a fixed four-job burst of duplicated CPU and I/O, which consumes shared/self-hosted capacity and lowers repository-wide CI throughput under realistic concurrent PR traffic.

**Evidence:** Tracing the added call into \`.github/workflows/pr-linux-test.yml\` shows that before the group-specific smoke command can run, every invocation performs an LFS checkout, node\_modules cache download/extraction (or npm installs on a miss), built-in-extension cache access, full client/extension transpilation, and Electron download; because \`smoke\_tests\` remains true, it also recompiles the common smoke extensions, smoke runner, and Copilot extension. The Darwin and Windows workflows have the same unconditional preparation. The grep/invert groups partition only Mocha execution, not this setup, so cache hits still repeat archive download/extraction and all compilation.

**Suggested direction:** Preserve the shards but prepare the smoke build once per platform and have core/chat/proxy jobs consume that prepared artifact; if a shared artifact is not viable, keep the suites in one workflow until shard-specific jobs can skip the unrelated checkout/cache/build work.
