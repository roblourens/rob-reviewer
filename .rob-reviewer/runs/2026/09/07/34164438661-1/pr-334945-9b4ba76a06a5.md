### Scenario 1: Cold startup account probe and first persistent Codex activation

- Critical path: A cold account probe or first explicit Codex use waits for proxy startup, Codex subprocess spawn, and the initialize IPC handshake. The diff only appends four fixed permission-profile command-line overrides before that spawn.
- Scaling input: Fixed four-profile launch configuration per spawned app-server process; independent of workspace size, thread count, and history size.
- Effective concurrency: Startup probe is one transient process; on-demand work is sequenced, and persistent connection creation is coalesced by the existing starting promise. The diff does not change these limits.
- Cache behavior: Cold paths spawn and parse launch configuration once per process. Warm activated sessions reuse the existing ready process, so the new overrides are not rebuilt per turn.
- Mechanism confidence: High confidence that the subprocess/IPC path and cardinality are unchanged; repository code directly shows fixed argument construction and existing connection coalescing.
- Magnitude uncertainty: No measurements quantify native parsing of the four extra constant strings, but their fixed size and once-per-process placement rule out realistic scaling or repeated hot-path regression.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_startRawConnection</code>: Start the local Codex proxy service; cardinality: Once per raw app-server connection, unchanged by the diff.
    - Introduced by diff: false; previous behavior: The same proxy start completed before every raw connection.; critical-path effect: Blocks subprocess launch on cold startup or activation.
  - subprocess at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_startRawConnection and src/vs/platform/agentHost/node/codex/codexLaunchConfig.ts:buildCodexLaunchConfig</code>: Spawn the Codex app-server with command-line configuration; cardinality: One spawn per cold/transient/replacement connection; the diff adds four constant-size -c pairs to that spawn.

### Scenario 2: Create and materialize a fresh session or additional backing chat

- Critical path: Materialization performs existing MCP/customization filesystem work, ensures the shared process, then waits for one thread/start IPC. The diff replaces the sandbox field with a permission-profile id and may serialize explicit runtime roots for single-root workspace-write sessions.
- Scaling input: Workspace roots plus configured additional directories after path deduplication; normally one or a small number of roots.
- Effective concurrency: Each materialization issues one thread/start request on the shared app-server. The diff adds no loop, fan-out, queue, or new request.
- Cache behavior: The shared app-server is reused when warm. Session configuration is read from in-memory state; permission selection has no cache and is constant-time. Root normalization is linear in the small root list.
- Mechanism confidence: High confidence in unchanged host-side request count and O(root-count) serialization; low evidence for any additional native cost, so no regression mechanism is established.
- Magnitude uncertainty: The app-server implementation is external to this repository, so internal handling cost of an explicit single workspace root is not measured. No repository evidence shows that setting runtime roots triggers scanning or extra boundary calls.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_materializeSession</code>: Refresh session MCP discovery and build customization launch data; cardinality: Existing work over current workspace roots once during materialization; unaffected by permission-profile selection.
    - Introduced by diff: false; previous behavior: The same MCP discovery/customization work occurred before computing and sending sandbox settings.; critical-path effect: Completes before thread/start and remains on the existing materialization critical path.
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_materializeSession and \_startChatBacking</code>: Send thread/start to the Codex app-server; cardinality: Exactly one request per successful fresh/backing thread creation, unchanged.
    - Introduced by diff: false; previous behavior: One thread/start carried sandbox mode and, for multi-root sessions, runtime roots; it now carries a short profile id and explicit effective roots where required.; critical-path effect: Blocks creation until the app-server returns the thread id.
- Verdict: No reportable regression: one IPC remains one IPC, local work is bounded by the effective root list, and no expensive per-root host boundary was introduced.
