**Relevant issue families:** boundary-fanout, concurrency-burst, cache-lifecycle

### Scenario 1: A pull request targets main or a release/\* branch and triggers chat-lib tests.

- Critical path: GitHub evaluates the base-branch filter before scheduling the three matrix jobs; once admitted, checkout, dependency setup, extraction, build, and tests are the CI critical path exactly as before.
- Scaling input: One workflow run per qualifying pull\_request event, multiplied by a fixed three-OS matrix; concurrency grouping coalesces superseded runs for the same PR via cancel-in-progress.
- Effective concurrency: Up to three matrix jobs run concurrently per admitted event; the existing workflow-level concurrency group cancels an older run for the same pull request. The diff does not alter either behavior.
- Cache behavior: setup-node's npm cache is keyed by the two package lockfiles. Warm runs can avoid package downloads but still execute npm ci, extraction, build, and tests; branch filtering does not change keys or invalidation.
- Mechanism confidence: High: the changed YAML is solely the pull\_request branch predicate, while all jobs, matrix cardinality, cache configuration, and commands are unchanged.
- Magnitude uncertainty: Runner availability and cache-hit rates vary, but they affect only the unchanged cost of admitted runs.
- Expensive boundaries:
  - network at <code>.github/workflows/chat-lib-package.yml, jobs.test matrix and Checkout/Setup/Extract/Install steps</code>: Three OS-specific runners check out the repository and may restore/download npm packages before building and testing chat-lib.; cardinality: Three jobs per admitted pull\_request event; each job performs one checkout and up to two npm dependency installations, with setup-node caches reducing package downloads on warm runs.
    - Introduced by diff: false; previous behavior: The same three jobs and boundary operations ran for every pull request regardless of base branch; the diff only suppresses runs for other base branches.; critical-path effect: These operations must finish for the chat-lib workflow check to complete.
- Verdict: No performance regression. Main/release pull requests retain identical cost; other base branches now consume zero chat-lib runner work.

### Scenario 2: A pull request targets main or release/\* and runs the telemetry metadata check.

- Critical path: After GitHub admits the event, checkout, Node setup, and telemetry extraction must complete before this CI check finishes; nonmatching base branches no longer enter this path.
- Scaling input: One workflow run per qualifying pull\_request event, with extractor cost scaling with repository size rather than any new diff-controlled collection.
- Effective concurrency: No workflow concurrency group is defined, so distinct PR events may overlap as before; the new filter can only reduce the number admitted.
- Cache behavior: No explicit workflow cache is configured. Runner/npm incidental caching may vary, but the diff neither changes cache keys nor adds cold-cache work.
- Mechanism confidence: High: the only changed behavior is event filtering before runner allocation.
- Magnitude uncertainty: Exact package download and scan durations depend on runner state and repository size, but the admitted-run path is unchanged.
- Expensive boundaries:
  - network at <code>.github/workflows/telemetry.yml, jobs.check-metadata steps</code>: The runner checks out the repository, installs or resolves Node tooling, and npx fetches &#64;vscode/telemetry-extractor when unavailable locally.; cardinality: One job and one extractor invocation per admitted pull\_request event; any package-manager caching is platform-managed and unchanged.
    - Introduced by diff: false; previous behavior: The identical job ran on pull requests to every base branch; after the diff it runs only for main and release/\*.; critical-path effect: The checkout/package resolution and full-source extractor invocation are serial steps on the workflow's completion path.
  - filesystem at <code>.github/workflows/telemetry.yml, Run vscode-telemetry-extractor</code>: The extractor scans the checked-out source tree for telemetry metadata.; cardinality: One repository-wide scan per admitted workflow run.
    - Introduced by diff: false; previous behavior: The scan already occurred once on every pull\_request workflow run; the branch filter only reduces the number of runs.; critical-path effect: The scan is the terminal substantive step and directly determines check latency.
- Verdict: No performance regression. The change reduces possible network, filesystem, and CPU work and leaves eligible-run latency unchanged.

### Scenario 3: The Copilot setup workflow is invoked by a matching workflow-file change, a push, or manual dispatch.

- Critical path: For pull requests, GitHub now evaluates both the existing path filter and the new base-branch filter before allocating the runner. For admitted PRs, pushes, and manual dispatches, system package setup, cache restoration, dependency installation on misses, and artifact downloads remain serial prerequisites to workflow completion.
- Scaling input: One run per manual dispatch, matching push, or qualifying path-and-branch pull\_request event; dependency volume controls bytes, while retries bound failed network attempts.
- Effective concurrency: Electron and Playwright downloads run as two parallel subprocesses within one step. Separate workflow runs have no explicit coalescing and may overlap as before; filtering decreases potential overlap from pull requests.
- Cache behavior: node\_modules cache uses a Linux/x64 architecture key and skips both npm ci steps on hits. Built-in extensions use a content hash and download only on misses. The filter does not alter cold/warm behavior, keys, or invalidation.
- Mechanism confidence: High: push and workflow\_dispatch definitions are untouched, while the pull\_request predicate is strictly narrower and all jobs are unchanged.
- Magnitude uncertainty: Cold-cache frequency and network retry incidence are variable, but all costly paths are pre-existing and the diff only removes some invocations.
- Expensive boundaries:
  - network at <code>.github/workflows/copilot-setup-steps.yml, Setup system services</code>: apt-get updates package indexes and installs system packages.; cardinality: One apt update/install sequence per admitted workflow run, with script-level retry behavior unchanged.
    - Introduced by diff: false; previous behavior: This sequence ran for every path-matching pull request plus the unchanged push/manual triggers; it now skips pull requests to other base branches.; critical-path effect: System service setup blocks all later setup steps.
  - network at <code>.github/workflows/copilot-setup-steps.yml, Restore node\_modules cache and npm ci steps</code>: The workflow restores dependency caches and performs two npm ci installs on a cache miss.; cardinality: One cache restore per run and at most two npm installations per cold run, each with up to five attempts on failure.
    - Introduced by diff: false; previous behavior: Cache keys, retry counts, and installation placement are unchanged; only fewer pull\_request events are admitted.; critical-path effect: Cache restoration or cold installation must complete before extension and runtime downloads.
  - network at <code>.github/workflows/copilot-setup-steps.yml, built-in extension and Electron/Playwright download steps</code>: The workflow conditionally downloads built-in extensions and always invokes parallel Electron and Playwright download scripts, with up to three attempts.; cardinality: One built-in-extension download on a cache miss and one paired runtime-download invocation per run; retries occur only on failure.
    - Introduced by diff: false; previous behavior: The same downloads and retry behavior existed on all triggers; the diff removes them only for non-main/non-release pull requests.; critical-path effect: These downloads are the final prerequisites and block successful workflow completion.
- Verdict: No performance regression. Existing push/manual behavior and eligible PR cost are preserved; excluded PRs avoid substantial setup I/O.
