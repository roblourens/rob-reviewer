# Performance review: agentHost: Show Linux SDK sandbox diagnostics in chat

[PR #338261](https://github.com/microsoft/vscode/pull/338261) at `731625aa666f7dccea41273a6060fbc116a32749`

## Findings (1)

### 1. [high] Keep the sandbox diagnostic probe off every turn's critical path

**Finding ID:** `PERF-8D6EF137664B`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:4783</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** One additional SDK-runtime stdio IPC request per initialization and per turn, plus an uncancelled pending RPC on each timeout.  
**Scaling:** Cost grows linearly with the number of turns (one uncached probe for every normal send, resume, or fleet start); a session with N turns issues N+1 probes, and each slow probe serially blocks that turn for as long as five seconds.  
**Outcome:** Increased turn-start latency and blocked initialization, up to five seconds per probe when the runtime does not answer.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, turn preparation applied the sandbox configuration and proceeded to the model send without querying host-support diagnostics; session initialization likewise did not await this diagnostic RPC.  
**Changed behavior:** Every Linux turn with SDK sandboxing enabled now invokes \`client.rpc.sandbox.getHostSupport()\` and waits for the result (or a 5,000 ms timeout) after applying the sandbox config and before starting the provider request.  
**Confidence:** 0.99 — The changed await is directly on the traced \`\_prepareSdkTurn\` critical path, \`CopilotSandboxDiagnostics.update\` unconditionally starts the RPC whenever \`config.enabled\`, and the SDK client is explicitly connected to its runtime subprocess through \`RuntimeConnection.forStdio\`. The added test itself establishes two probes for initialization plus one first send and a 5,000 ms elapsed timeout. Exact normal RPC duration and user prevalence are uncertain, but the per-turn call and worst-case delay are explicit.

**Causal diff evidence:** The added RIGHT-side line \`await this.\_sandboxDiagnostics.update(...sandboxConfig)\` at \`copilotAgentSession.ts:4783\` inserts the diagnostics probe into \`\_updateEffectiveSandboxConfig\`; \`\_prepareSdkTurn\` awaits \`\_applyEffectiveSandboxConfig\` before \`session.send\` for normal sends, resumes, and fleet starts.

On Linux with sandboxing enabled, a slow or wedged SDK runtime delays session readiness and each prompt before model work begins; in the explicit timeout case users wait an extra five seconds on every turn. Repeated timeouts also leave each underlying RPC unresolved because the timeout wrapper does not cancel it.

**Evidence:** \`\_send\` and \`resume\` await \`\_prepareSdkTurn\` before calling \`session.send\`/\`rpc.sendMessages\`; \`\_prepareSdkTurn\` awaits \`\_applyEffectiveSandboxConfig\`; the changed line awaits \`CopilotSandboxDiagnostics.update\`; that method calls \`raceTimeout(this.\_getHostSupport(), 5\_000)\` without caching, and \`raceTimeout\` does not cancel the losing promise. \`CopilotAgent\` creates the SDK client with \`RuntimeConnection.forStdio\`, proving this is a subprocess IPC round trip rather than local metadata access. The new timeout test expects \`queries: 2\` for initialization followed by one send and separately measures a hung query at exactly 5,000 ms.

**Suggested direction:** Keep diagnostics off the turn critical path: probe asynchronously at initialization/config changes, cache/coalesce the latest host-support result, and refresh on an explicit bounded cadence or invalidation event. If polling before turns is required, reuse an in-flight/cached result and do not await it before \`session.send\`; also cancel or otherwise bound timed-out RPC requests.
