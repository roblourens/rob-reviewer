<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** boundary-fanout, concurrency-burst, cache-lifecycle, repeated-work, eager-work

### Scenario 1: A GitHub authentication session keeps the same token and session ID but changes account ID or authorization server.

- Critical path: The authentication provider event first completes three existing concurrent session lookups, then the diff makes the forced Copilot-token mint complete before publishing onDidAuthenticationChange. Consumers run after that event; most synchronously invalidate bounded caches, while the CLI model subscriber starts an asynchronous model fetch.
- Scaling input: Authentication identity changes, not token refresh frequency: string-value comparisons suppress equivalent reconstructed sessions, and the code-search subscriber also suppresses token-only events.
- Effective concurrency: The three session reads run in parallel; token mint follows them and is coalesced per identity. Event listeners fan out synchronously, with their asynchronous work independently scheduled.
- Cache behavior: Session requests and token minting coalesce concurrent identical keys. Identity-sensitive model, routing, organization, and cloud-session caches are invalidated once; most network reads remain lazy, while CLI models refresh eagerly.
- Mechanism confidence: High: the changed condition, forced token call, TaskSingler key, and event subscribers are directly traced.
- Magnitude uncertainty: Exact authentication-provider event duplication and remote latency vary, but identity changes are infrequent and equivalent-session notifications are explicitly deduplicated.
- Expensive boundaries:
  - IPC at <code>extensions/copilot/src/platform/authentication/common/authentication.ts:\_handleAuthChangeEvent</code>: Queries the any GitHub, permissive GitHub, and ADO authentication sessions concurrently through the authentication API.; cardinality: Three lookups per provider event, coalesced per session lookup key by AuthenticationService TaskSingler when overlapping.
    - Introduced by diff: false; previous behavior: The same three session lookups already ran for every relevant authentication-provider event.; critical-path effect: All three settle before identity comparison and token minting.
  - network at <code>extensions/copilot/src/platform/authentication/common/authentication.ts:340-358 via VSCodeCopilotTokenManager.getCopilotToken(true)</code>: Forces a Copilot token request for the newly detected account/issuer identity.; cardinality: One effective request per identity key; concurrent requests for the same provider/account/issuer/access-token key are coalesced by the token manager TaskSingler.
    - Introduced by diff: true; previous behavior: A same-token, same-session-ID account/issuer change did not force a token mint or publish the identity-change event.; critical-path effect: The authentication-change event is published only after this request settles, but provider-event dispatch itself does not await \_handleAuthChangeEvent.
  - network at <code>extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotCli.ts:101-169</code>: The existing authentication-change subscriber eagerly refreshes the available CLI model list through the SDK.; cardinality: One model-list fetch for the published identity event; a newer event supersedes the stored promise rather than multiplying normal equivalent-session notifications.
    - Introduced by diff: false; previous behavior: This subscriber already fetched on sign-in/sign-out and token-backed identity events, but was not reached for the newly recognized same-token account/issuer case.; critical-path effect: Started asynchronously by the event and not awaited by authentication refresh; it does not block publication of the event.
- Verdict: No reportable regression. The bounded one-time network work is tied to a real identity transition and is required to prevent credentials and identity-derived caches from remaining scoped to the previous account or host.

### Scenario 2: Repository authorization/index status refresh after a GitHub session account, issuer, session ID, or sign-out transition.

- Critical path: The authentication event handler snapshots the current two GitHub sessions, compares IDs and account/issuer identity, updates the snapshots before scheduling work, and launches repository refreshes without awaiting them. Code-search consumers may observe CheckingStatus while requests run, but authentication processing is not blocked.
- Scaling input: Number of tracked GitHub repositories in the workspace after repo tracking; ADO repositories are filtered out. Frequency scales with distinct session/account/issuer transitions, not ordinary token refreshes.
- Effective concurrency: All eligible GitHub repository status requests run concurrently via Promise.all with no shared limiter. This is inherited from the existing session-ID refresh path; the diff adds the same behavior only for rare account/issuer identity transitions.
- Cache behavior: refreshStatusFromEndpoint(true) intentionally bypasses Ready/NotAuthorized short-circuiting because authorization is identity-scoped. The listener stores the latest sessions before scheduling requests, so duplicate equivalent events are negative-cached by equality checks. There is no status-request coalescer across distinct repos.
- Mechanism confidence: High: force=true, per-repository mapping, GitHub-only filtering, and unbounded Promise.all are directly visible, as are the added identity predicates and token-only suppression test.
- Magnitude uncertainty: Very large multi-root workspaces can create a wider burst, but typical repository counts are small and the newly added trigger is rare rather than periodic or input-hot.
- Expensive boundaries:
  - network at <code>extensions/copilot/src/platform/workspaceChunkSearch/node/codeSearch/codeSearchChunkSearch.ts:179-190,1004-1009 -&gt; GithubCodeSearchService.getRemoteIndexState</code>: Forces a CAPI remote-index-status GET for every tracked GitHub repository; some not-yet-indexed states may additionally check whether the GitHub repository is empty.; cardinality: One status request per tracked GitHub repository/root for one effective identity transition; Promise.all issues them concurrently. Equivalent session objects and token-only changes issue zero requests. There is no cross-root grouping, but realistic cardinality is the number of GitHub repositories tracked in the open workspace.
    - Introduced by diff: true; previous behavior: Session-ID/sign-out transitions already forced the same per-repository request wave. Same-ID account/issuer transitions previously issued no repository refresh and could retain status authorized for the old identity.; critical-path effect: Requests are fire-and-forget from the authentication event and therefore off the auth critical path; they update later code-search availability.
- Verdict: No reportable regression. The diff adds a bounded refresh only when cached authorization has become identity-invalid; it neither makes token refreshes hit the network nor increases per-transition cardinality beyond the established session-change behavior.

**Summary:** Reviewed all five changed files and traced the authentication-event expansion through token minting, event subscribers, repository tracking, and remote index-status calls. The added work is bounded to rare account/issuer identity transitions, equivalent sessions and token-only refreshes are suppressed, same-key token work is coalesced, and repository requests are off the authentication critical path. No high-confidence actionable performance regression was found.
