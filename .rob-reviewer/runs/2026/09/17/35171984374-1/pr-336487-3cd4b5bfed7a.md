### Scenario 1: Web startup and first tunnel discovery automatically connect configured or newly discovered hosts while showing pending status

- Critical path: Factory registration/reconciliation starts existing cached-host dials before the tunnel contribution subscribes; first discovery later caches newly found tunnels and starts their dials. The new pending event synchronously updates provider status, but remote authentication, gateway setup, and protocol connection remain the dominant asynchronous critical path.
- Scaling input: Configured/cached tunnel count after suppression and dismissal filtering; one deduplicated in-flight attempt per normalized address. Discovery can add multiple hosts, but each address has at most one pending dial.
- Effective concurrency: RemoteAgentHostService coalesces by address in \_pendingConnects. Different addresses can still connect concurrently exactly as before the diff; the PR does not add a global limiter or increase per-address concurrency.
- Cache behavior: Warm startup reads the existing tunnel cache and auto-connects unsuppressed entries. Cold discovery performs one tunnel-list request, then persists newly discovered tunnels; pending metadata is uncached and exists only for each live attempt. Removed, disabled, and disposed entries are filtered from the exposed catalog.
- Mechanism confidence: High confidence in event and dial cardinality from \_connectTo deduplication, constructor ordering, the pending event listener, and cache iteration.
- Magnitude uncertainty: Tunnel cache size is unbounded, so pending start/configuration events can cause repeated host-list scans during a large discovery. However, these scans are in-memory, status writes are equality-checked observables, startup registration events precede the new contribution listener, and the diff does not introduce the pre-existing per-host network burst. There is insufficient evidence of a concrete user-visible regression at realistic cardinality.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/tunnelAgentHost.contribution.ts:\_silentStatusCheck</code>: List available tunnels during discovery; cardinality: One request per initial or user-triggered rediscovery, serving the full tunnel collection.
    - Introduced by diff: false; previous behavior: The same discovery request and collection-wide response occurred before the PR.; critical-path effect: Discovery must complete before newly found hosts can be cached and connected.
  - serialization at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/tunnelAgentHostStorage.ts:cacheTunnel</code>: Persist each newly discovered tunnel into application storage; cardinality: One storage update per previously uncached discovered tunnel.
    - Introduced by diff: false; previous behavior: Discovery already cached each new tunnel individually.; critical-path effect: Occurs synchronously while applying discovery results before status reconciliation completes.
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/browserTunnelAgentHostService.ts:\_createConnection and webTunnelAgentHostService.ts:\_createConnection</code>: Authenticate, establish the tunnel gateway/relay, and perform the agent-host protocol connection; cardinality: At most one active setup per normalized address; up to the number of unsuppressed configured hosts across distinct addresses.
    - Introduced by diff: false; previous behavior: The same per-address dials and aggregate cross-address concurrency existed; the PR adds pending metadata/events but no extra dial.; critical-path effect: Each host cannot become connected until its own setup and protocol handshake finish.
- Verdict: No reportable regression. The PR exposes existing in-flight work and adds synchronous status recomputation, but does not increase expensive-boundary cardinality or concurrency, and the remaining in-memory scans are not evidenced as materially costly.

### Scenario 2: A user manually connects or reconnects one tunnel from the host UI or diagnostics report

- Critical path: The action stages the tunnel, RemoteAgentHostService starts or joins the one address-specific attempt, then waitForConnection follows that attempt through gateway and protocol setup. Pending status events update the UI without awaiting additional work.
- Scaling input: One selected host action; repeated requests for the same address join the existing pending promise.
- Effective concurrency: Serialized/coalesced per normalized address by \_pendingConnects; unrelated addresses retain pre-existing independent concurrency.
- Cache behavior: stageTunnel refreshes the cached tunnel and clears suppression as part of staging. A staged initiation flag is consumed by the first createConnection and then removed, so later automatic attempts are not pinned as user-initiated.
- Mechanism confidence: High confidence from reconnect's \_pendingConnects check, stageTunnel consumption, and waitForConnection call flow.
- Magnitude uncertainty: Authentication and gateway latency vary by environment, but the changed code neither duplicates nor newly awaits them.
- Expensive boundaries:
  - serialization at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/tunnelAgentHostStorage.ts:cacheTunnel</code>: Update the cached tunnel and suppression state in application storage; cardinality: One staged cache update for the selected host.
    - Introduced by diff: false; previous behavior: The same staging cache write occurred; suppression was previously also cleared earlier by callers.; critical-path effect: Synchronous staging precedes the dial.
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/browserTunnelAgentHostService.ts:connect/\_createConnection or webTunnelAgentHostService.ts:connect/\_createConnection</code>: Acquire authentication if needed and establish gateway/relay plus protocol connection; cardinality: One dial for the selected address because concurrent requests join.
    - Introduced by diff: false; previous behavior: The same dial occurred. Moving suppression clearing into staging changes initiation ordering/metadata, not boundary count.; critical-path effect: The connect action waits for this boundary to produce a connection.
- Verdict: No reportable regression. Pending tracking retains three small metadata fields per already-retained promise and emits start/end UI notifications without adding remote calls.

### Scenario 3: Open and use Connection Information on desktop or from the mobile Hosts sheet

- Critical path: Opening the report captures one snapshot before rendering. Snapshot capture scans bounded diagnostic buffers and host state, then reads a bounded Window-log excerpt. Subsequent pending-state changes only schedule a live DOM rebuild at the next animation frame; they do not call getSnapshot or reread the log. Copy uses the captured text and download encodes it on explicit action.
- Scaling input: Number of visible/cached/configured hosts plus bounded diagnostic history (up to 200 connection and 200 discovery events) and the bounded log excerpt; one modal instance at a time.
- Effective concurrency: Pending UI invalidations are coalesced to one render per animation frame. Snapshot requests are explicit; request IDs discard stale refresh results, and host actions are serialized by pendingHostId.
- Cache behavior: The initial snapshot is retained by the report. Live status rereads current in-memory host state, while detailed sections and exports remain on the captured snapshot until explicit refresh. There is no automatic snapshot or negative-cache retry on pending events.
- Mechanism confidence: High confidence from ConnectionDiagnosticsReport.scheduleRender calling render rather than refresh/getSnapshot and from getSnapshot's single collectConnectionLogs call.
- Magnitude uncertainty: Exact log-read latency and report size depend on platform and host count, but the new pending invalidations provably do not repeat snapshot capture, and the newly exposed mobile path performs only the operation explicitly requested by the user.
- Expensive boundaries:
  - filesystem at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/connectionDiagnosticsService.ts:getSnapshot/collectConnectionLogs</code>: Read and filter the Window log excerpt for connection-related lines; cardinality: One file read per initial open or explicit refresh, independent of host count.
    - Introduced by diff: true; previous behavior: The diagnostic command already performed this read; the diff adds a direct mobile Hosts-sheet entry point, so one deliberate tap from that new control now reaches the same single snapshot read.; critical-path effect: Initial report display waits for snapshot capture. Live pending status updates are off this boundary and only rerender in-memory state.
  - serialization at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/connectionDiagnosticsService.ts:getSnapshot and connectionDiagnosticsReport.ts:download</code>: Build snapshot sections/text and optionally encode captured text for download; cardinality: One collection-wide serialization per open/refresh; one encoding per explicit download.
    - Introduced by diff: false; previous behavior: Snapshot text construction and download encoding already existed; pending attempts add six small entries only for currently pending hosts.; critical-path effect: Snapshot serialization precedes report display; download encoding occurs only on the user's download action.
- Verdict: No reportable regression. The new mobile entry deliberately invokes existing diagnostics once, while frequent live changes are coalesced and remain in memory.

### Scenario 4: Close mobile Connection Information after its originating host control was replaced

- Critical path: The contribution checks the originating focused part before snapshot capture and, on modal close, synchronously focuses either the still-connected element or the mobile titlebar/toolbar fallback.
- Scaling input: Constant work per modal open/close; independent of host count and connection history.
- Effective concurrency: One active diagnostics modal is guarded by contribution state; no queue or background work is introduced.
- Cache behavior: No cache is involved. The fallback closure is cleared with the mobile titlebar disposable lifecycle.
- Mechanism confidence: High confidence from the explicit focusPart/hasFocus branches and mobile titlebar lifecycle wiring.
- Magnitude uncertainty: None material; DOM containment and focus operations are constant-sized and user-triggered.
- Expensive boundaries: none found
- Verdict: No reportable performance regression; the change adds only constant synchronous focus work on modal open/close.
