### 1. [medium] Clean up the superseded dictation model cache

**Finding ID:** `PERF-509478547200`  
**Location:** <code>src/vs/platform/localTranscription/node/localTranscriptionService.ts:474</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** persistent model files and disk bytes  
**Scaling:** Each legacy model already cached under chatDictationModels remains in addition to the new Foundry model; the deleted transcriber documents the prior default payload as approximately 800 MB.  
**Outcome:** retained disk usage and disk-space pressure after upgrade  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Legacy Nemotron and Whisper files in chatDictationModels were the active reusable cache.  
**Changed behavior:** The PR deletes the legacy cache consumers and switches model IDs, then points the new Foundry manager at the same cache root without retiring legacy files.  
**Confidence:** 0.97 — The old path, payload magnitude, deleted reader, unchanged root, and incompatible new model ID are explicit. Only adoption of the experimental feature is uncertain.

**Causal diff evidence:** RIGHT line 474 makes the new Foundry manager populate the existing dictation cache while this diff deletes the only legacy-cache consumer and changes the model identity, turning previously reusable model bytes into permanent dead cache data.

Existing dictation users retain the old approximately 800 MB default model and must also store the new Foundry model; the unreachable old payload persists across sessions and upgrades.

**Evidence:** Deleted \`NemotronTranscriber.prepare\` placed the prior model under \`chatDictationModels/nemotron/&lt;model&#64;revision&gt;\` and documents an approximately 800 MB download. The diff deletes that reader, migrates legacy IDs to a new Foundry ID, and added line 474 configures the new manager with the unchanged cache root. No cleanup or remaining reader exists in the repository.

**Suggested direction:** After the Foundry model is successfully available, remove the known legacy Nemotron and transformers cache layouts with a one-time, version-aware cleanup that does not race older running windows.

### 2. [medium] Coalesce runtime provisioning across VS Code windows

**Finding ID:** `PERF-B39445E88D67`  
**Location:** <code>src/vs/platform/localTranscription/node/foundryLocalRuntime.ts:133</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** network bytes, temporary disk bytes, and four download operations per utility process (one npm tarball plus three NuGet artifacts)  
**Scaling:** On a cold cache, work scales linearly with the number of VS Code windows that start dictation before any one process publishes the completion marker; each window owns a separate utility process and therefore a separate process-local inFlight map.  
**Outcome:** duplicate large native-runtime downloads contend for bandwidth and disk I/O, increasing first-use latency and transient disk usage  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The native transcription runtime was bundled with VS Code, so starting dictation did not provision an npm addon tarball or three NuGet native packages at runtime.  
**Changed behavior:** Each window's utility process observes the same cold shared cache, creates its own process-unique staging directory, and downloads the complete runtime before attempting atomic promotion; the inFlight map only deduplicates callers inside one process.  
**Confidence:** 0.96 — The per-window worker ownership, process-local deduplication, shared cache path, and download-before-promotion ordering are all explicit in the changed code. Only the exact payload size and frequency of simultaneous first use are uncertain, which affects severity rather than the mechanism.

**Causal diff evidence:** RIGHT line 133 creates a process-specific staging directory for the newly added runtime provisioning path; combined with the added process-local \`inFlight\` map and the download calls immediately below it, this makes concurrent cold-cache utility processes independently fetch the same payload. Before this diff those runtime network boundaries did not exist.

With multiple VS Code windows open, starting first-use dictation in a second window while the first is still preparing launches a second full runtime provision. The loser only discovers the winner after both the npm tarball and all three NuGet artifacts have downloaded, causing avoidable bandwidth/disk contention and slower preparation.

**Evidence:** \`LocalTranscriptionService\` is instantiated inside a per-window utility worker. \`ensureFoundryLocalRuntime\` checks the shared marker, but its \`inFlight\` map is module/process-local. \`doEnsure\` then calls \`ensureAddon\` and \`ensureCoreLibraries\` before \`promoteDir\`; \`ensureCoreLibraries\` requests three native artifacts. The process-unique staging path at line 133 explicitly permits every process to perform all downloads, and atomic rename only prevents corrupt publication, not duplicated transfer.

**Suggested direction:** Use a cache-root filesystem claim/lock so one process provisions while others wait for and re-check the completion marker; include stale-lock recovery and preserve the existing atomic staging/promotion semantics.

### Scenario 1: First on-device dictation on a cold runtime and model cache

- Critical path: The renderer lazily creates a per-window utility process and sends start. Audio capture starts immediately, but the first transcript requires native-runtime provisioning, SDK/manager initialization, model download/load, and session.start; stop also awaits the open promise. Runtime and model downloads therefore gate useful transcription even though microphone capture proceeds.
- Scaling input: The effective runtime-download cardinality is the number of workbench windows entering first use before any process publishes the shared marker. Within one utility process calls coalesce by override directory; across windows they do not. Payload work is one npm tarball plus three NuGet artifacts per racing process.
- Effective concurrency: Addon and core provisioning are serialized within one process. The inFlight map coalesces same-process callers, but every window owns a separate utility process and can provision concurrently without a cross-process lock; each uses a unique staging directory and only converges at final rename.
- Cache behavior: Warm runtime cache verifies marker and payload then performs no network work. Cold successful provisioning writes a per-platform marker. Failures leave no positive marker and retry on the next attempt; same-process attempts coalesce only while in flight. Model caching is delegated to Foundry Local.
- Mechanism confidence: High: worker ownership, cache key, process-local map, download order, and publish point are directly traced.
- Magnitude uncertainty: Exact compressed/native payload size and frequency of users invoking dictation in multiple windows during the same cold interval are unknown; the duplicated request count and critical-path placement are explicit.

### Scenario 2: Warm-cache dictation and live audio streaming

- Critical path: After the cached model is loaded and session.start completes, each 4096-sample audio callback crosses IPC and is appended to native core through one FIFO chain; native streaming results cross IPC and update the editor. stop waits for queued appends, native stop, and stream drain.
- Scaling input: Recording duration controls audio IPC/native append count linearly; endpointed segment count controls transcript accumulation. The capture callback rate is fixed at about 3.9/second.
- Effective concurrency: Native appends are explicitly serialized by one promise chain; result consumption is one async iterator. Renderer audio callbacks can have outstanding IPC promises but no aggregate concurrency issue is proven at the fixed callback rate.
- Cache behavior: The loaded model promise/model/manager are retained and reused within the window utility process. A warm disk cache avoids runtime/model downloads but each new window loads its own native model into memory.
- Mechanism confidence: High for IPC cardinality and serialization; insufficient evidence that native result frequency or append latency exceeds real-time capacity.
- Magnitude uncertainty: Foundry result emission frequency and native append duration are not measurable from repository code, so no high-confidence live-render or append-backlog regression is reported.
- Expensive boundaries:

### Scenario 3: Upgrade after using a legacy Nemotron or Whisper dictation model

- Critical path: On first dictation after upgrade, configuration migration selects the new Foundry model. Runtime provisioning and the new model download/load proceed from the existing chatDictationModels root; old model files are not consulted.
- Scaling input: Retained bytes scale with the count and size of legacy model variants previously used; the common prior default contributes about 800 MB.
- Effective concurrency: One model promise coalesces within a utility process; cross-window SDK behavior is not visible. Retention itself has no concurrency.
- Cache behavior: The cache root is unchanged but the model ID/runtime and layout are replaced. No remaining reader or cleanup exists for the old nemotron subtree or transformers cache, so legacy positive cache entries become permanent dead data.
- Mechanism confidence: High: old path/layout, deleted reader, new model identity, and unchanged cache root are explicit.
- Magnitude uncertainty: The number of users who exercised the experimental feature and whether they cached multiple model choices are unknown; per-affected-user stale payload size for the prior default is documented in deleted code.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/localTranscription/node/localTranscriptionService.ts:\_ensureModel modelCacheDir</code>: Retain legacy Hugging Face/Nemotron model files while writing the new Foundry model cache; cardinality: One stale payload for each legacy model the user previously cached; the prior default alone is documented as approximately 800 MB

  - network at <code>src/vs/platform/localTranscription/node/localTranscriptionService.ts:\_ensureModel</code>: Download the incompatible new Foundry model; cardinality: One logical cold download after migration

### Scenario 4: Cancel dictation while first-use preparation is still running

- Critical path: Cancel stops capture and increments the session generation, but runtime provisioning uses CancellationToken.None and model preparation remains in flight. This work is no longer on the canceled UI path but can continue to populate reusable caches.
- Scaling input: Bounded by one preparation promise per model in the utility process rather than by repeated audio events.
- Effective concurrency: Same-process provisioning/model work is coalesced. Cancel invalidates the session generation but does not cancel the download.
- Cache behavior: Successful background completion leaves reusable runtime/model cache entries; failures clear the model promise and can retry.
- Mechanism confidence: High for non-cancellation, lower for harmful impact because the behavior is bounded and intentionally warms the cache.
- Magnitude uncertainty: How often users cancel during initial preparation is unknown, and the work has future cache value.
- Expensive boundaries:
  - network at <code>src/vs/platform/localTranscription/node/localTranscriptionService.ts:\_ensureModel</code>: Continue native runtime and model downloads after the initiating recording is canceled; cardinality: At most one in-flight runtime provision and one model preparation per utility process/model selection
    - Introduced by diff: true; previous behavior: The old model preparation also continued after cancel, though it had no separate runtime provisioning leg.; critical-path effect: Off the canceled interaction's critical path; consumes background network/disk and may warm later use.
- Verdict: Not separately reported: model preparation already continued after cancel before the diff, and the added bounded runtime leg does not independently establish a high-confidence material regression beyond the reported provisioning issue.
