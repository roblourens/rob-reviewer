## Performance regression fixes detected (1)

### 1. cache-lifecycle

**Fix location:** `src/vs/platform/localTranscription/node/localTranscriptionService.ts:564` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/localTranscription/node/localTranscriptionService.ts:556`  
**Introducing path:** `src/vs/platform/localTranscription/node/localTranscriptionService.ts`  
**Introducing commit:** `eb62e28c3ca69961e96d8cca2be65539c6e22959`  
**Mechanism family:** `cache-lifecycle`  
**Performance category:** `network`  
**Confidence:** 0.94

**Mechanism:** Across utility-process restarts, stale catalog selection metadata could identify an uncached variant despite a compatible variant already existing in the disk cache, causing the model preparation path to fetch the model again before transcription could start.

**Symptom:** An already-installed, hundreds-of-megabytes dictation model could be downloaded again after restart, consuming network bandwidth and delaying first local transcription.

**Fixed behavior:** After catalog lookup, the service checks the selected variant first, then scans the model's bounded variant metadata and selects an already-cached variant. The subsequent existing `model.isCached` branch therefore skips the unnecessary network download and proceeds to load the persisted model.

**Evidence:** Before this change, `_ensureModel` trusted only the catalog-selected model's `isCached` value at base line 556 and immediately entered `model.download()` when it was false. The added helper and regression test establish that the selected variant can be uncached while another variant in the same catalog model is already persisted. The local dictation caller states first-use model downloads can be hundreds of MB and transcription cannot begin until model preparation reaches load/session startup. The helper is invoked immediately after the single coalesced `catalog.getModel(modelId)` result and before the download branch.
