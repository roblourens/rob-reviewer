<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, serialization-allocation, boundary-fanout, concurrency-burst

### Scenario 1: Browse or inspect MCP gallery entries and evaluate install eligibility under enterprise allow/deny policy

- Critical path: A gallery page network request and deserialization must complete before entries render; policy evaluation then synchronously derives one identity per entry when install actions/status are queried. The new normalization is in-memory and does not add to the network critical path beyond small per-entry string processing.
- Scaling input: Number of gallery entries whose install state is evaluated, multiplied by the small number of declared variables in the first remote transport. Each helper invocation scans one URL and its declaration keys.
- Effective concurrency: Pagination is demand-driven and sequential by cursor. URL normalization itself is synchronous per evaluated server and does not spawn concurrent work.
- Cache behavior: No new cache is introduced or defeated. Gallery paging and existing service behavior are unchanged; normalization is recomputed when policy evaluation is requested but only over per-entry metadata.
- Mechanism confidence: High confidence that regex construction/allocation is real and diff-introduced, but high confidence that its realistic cardinality and frequency are too small to constitute a concrete regression.
- Magnitude uncertainty: Registry manifests do not expose explicit local cardinality bounds for variable maps, but realistic MCP URL templates contain only a few variables and URLs are short.
- Expensive boundaries:
  - network at <code>src/vs/platform/mcp/common/mcpGalleryService.ts:query</code>: Fetch one paginated MCP gallery result page (default 50 entries).; cardinality: One request for the first page and one request for each explicitly requested next page; each page contains at most the requested page size (default 50).
    - Introduced by diff: false; previous behavior: The same gallery page request and deserialization occurred before the diff; the diff only preserves remote variable metadata and normalizes an entry URL in memory when policy is evaluated.; critical-path effect: The requested page must arrive before its entries can be displayed.
- Verdict: No reportable regression. The new CPU/allocation cost is bounded per entry, adds no I/O, and is not on a frame/input loop.

### Scenario 2: Install a remote MCP server from the gallery or a local manifest with URL/header variables

- Critical path: Manifest conversion and policy validation run synchronously before the existing configuration-resource write. The new URL replacement and input conflict checks must finish before persistence, but operate only on one selected remote plus its headers.
- Scaling input: Declared URL variables plus header variables for the selected remote. Replacement is proportional to URL/header text and declaration count; deduplication compares URL-derived inputs with header-derived inputs, which are realistically small manifest-local collections.
- Effective concurrency: One manifest conversion runs per install. Existing gallery resolution and file persistence sequencing are unchanged; the diff adds no parallel tasks or limiter bypass.
- Cache behavior: No changed cache behavior. Conversion is intentionally performed for each explicit installation; no repeated miss or negative-cache loop is introduced.
- Mechanism confidence: High confidence in the call path and unchanged I/O cardinality. The possible quadratic in-memory deduplication is real only in variable count and is not a realistic performance bug for MCP manifests.
- Magnitude uncertainty: Malformed user-selected manifests can contain unusually large maps because this conversion path accepts parsed input, but that is a one-shot user action and there is no evidence of realistic sizes large enough for visible latency.
- Expensive boundaries:
  - network at <code>src/vs/platform/mcp/common/mcpGalleryService.ts:getMcpServer / getMcpServerByName</code>: Resolve or fetch the gallery server manifest before installation.; cardinality: One successful lookup in the common case; existing fallback endpoints may be tried sequentially if earlier lookups fail.
    - Introduced by diff: false; previous behavior: Gallery lookup already occurred; remote variable fields are now retained but no additional request is made.; critical-path effect: Manifest retrieval must complete before conversion and installation.
  - filesystem at <code>src/vs/platform/mcp/common/mcpManagementService.ts:installFromGallery -&gt; src/vs/platform/mcp/common/mcpResourceScannerService.ts:addMcpServers</code>: Persist the converted server and input configuration through addMcpServers.; cardinality: One grouped configuration update for the single installation request.
    - Introduced by diff: false; previous behavior: The same configuration update occurred before the diff; only the URL/header values and input metadata supplied to it change.; critical-path effect: The write must complete before installation returns.
- Verdict: No reportable regression. Added work is small install-time CPU/allocation before an unchanged single persistence operation.

### Scenario 3: Synchronize installed MCP servers with the registry and compute registry-only enablement

- Critical path: On startup or MCP/profile/gallery changes, installed server metadata is resolved from the gallery; after responses arrive, enablement scanning compares each installed remote URL against its gallery remotes. The changed normalization runs after the network response and before enabled definitions are published.
- Scaling input: Installed MCP server count after name deduplication; each remote server checks its gallery remote list and only constructs a replacement regex when raw equality fails. Realistic lists contain one or very few remotes and variables.
- Effective concurrency: Registry resolutions use the pre-existing Promise.all across deduplicated server names, while each server's fallback URLs are sequential. Change events are coalesced through the existing throttler/delayer. The normalization adds no concurrency.
- Cache behavior: Gallery identity is associated with the current registry generation and invalidated only on manifest/profile/install changes. No cache key, positive/negative cache state, or invalidation rule is changed.
- Mechanism confidence: High confidence that the changed branch is reached only for registry-only remote enablement and that all expensive boundary fan-out is pre-existing.
- Magnitude uncertainty: Users may install many MCP servers, but the additional work per remote is short-string matching and does not multiply existing network calls.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/mcp/browser/mcpWorkbenchService.ts:syncInstalledMcpServers -&gt; src/vs/platform/mcp/common/mcpGalleryService.ts:resolveMcpServersFromGallery</code>: Resolve gallery metadata for each distinct installed server name, with endpoint fallbacks.; cardinality: One logical resolution per unique installed server name; resolutions run concurrently, and each may try up to the existing configured lookup endpoints sequentially until success.
    - Introduced by diff: false; previous behavior: The same per-unique-name concurrent gallery resolution occurred before the diff. The diff adds only an in-memory converted-template equality alternative after metadata is available.; critical-path effect: Registry-only membership cannot be refreshed until the relevant resolutions settle; prior verified state is retained on failures.
  - filesystem at <code>src/vs/workbench/contrib/mcp/browser/mcpWorkbenchService.ts:queryLocal and src/vs/workbench/contrib/mcp/common/discovery/installedMcpServersDiscovery.ts:sync</code>: Read installed MCP configuration resources and, during discovery sync, resolve one text model per distinct MCP resource.; cardinality: Configuration reads follow existing profile/workspace resources; discovery coalesces text-model work by distinct resource, not by server.
    - Introduced by diff: false; previous behavior: The same configuration scanning and per-resource model lookup happened before the diff.; critical-path effect: Installed definitions require these reads; URL-template normalization does not alter their count or placement.
- Verdict: No reportable regression. The diff adds bounded local comparisons without moving or multiplying network/filesystem work.

### Scenario 4: Resolve and start a remote MCP connection whose URL contains interactive variables

- Critical path: Existing variable replacement resolves the URI before policy evaluation and creation of the remote HTTP/SSE connection. This PR enables the stored URL template to contain input references; it does not add another connection or an additional resolution pass on each protocol message.
- Scaling input: Number of remote servers explicitly started and number of placeholders in each URL; no per-message or per-tool-call replacement was introduced.
- Effective concurrency: Connection concurrency remains driven by existing server start requests. No Promise.all, queue, limiter, or backpressure behavior is changed.
- Cache behavior: Input persistence and runtime connection caching/lifecycle remain unchanged. Fixed values generate no prompt; interactive values use the existing variable resolver.
- Mechanism confidence: High confidence that the diff changes configuration generation only and does not alter runtime boundary cardinality.
- Magnitude uncertainty: Remote endpoint latency varies independently of this change; the new local preprocessing is negligible relative to the existing network startup boundary.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/mcp/common/mcpServer.ts connection start path for McpServerTransportType.HTTP</code>: Open and use the remote MCP HTTP/SSE connection.; cardinality: One connection per explicitly started remote server, with lifecycle and parallelism unchanged by this diff.
    - Introduced by diff: false; previous behavior: Remote MCP servers already opened the same connection after configuration resolution. The diff changes how a registry URL template is generated, not connection count or scheduling.; critical-path effect: The connection is the dominant startup boundary; URL input resolution and policy checking must complete first.
- Verdict: No reportable regression. Existing network startup cost and concurrency are unchanged.

The PR adds bounded string/regex work and small temporary collections but no hot-loop UI work, retained lifecycle state, cache regression, extra boundary call, or concurrency burst.
