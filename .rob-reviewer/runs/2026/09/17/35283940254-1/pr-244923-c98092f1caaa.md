# Performance review: add table count to chat response's aria label

[PR #244923](https://github.com/microsoft/vscode/pull/244923) at `c98092f1caaad64e18be5b3f8761a09c24c7669c`

## Findings (1)

### 1. [medium] Reuse the Markdown tokenization for both counts

**Finding ID:** `PERF-7E671C8B00F3`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatAccessibilityProvider.ts:57</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** synchronous Markdown lexing CPU work and token-array allocations  
**Scaling:** For a streamed response of final length N delivered across U updates, this adds one parse of the entire accumulated response on every visible-row rerender, adding O(U\*N) aggregate work (quadratic when similarly sized chunks grow the response). The effective cardinality is one added lexer call per changed visible response row per update, not per conversation item.  
**Outcome:** increased synchronous UI-thread CPU and allocation/GC pressure during streamed chat rendering, which can increase update latency and contribute to jank for long responses  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Each ARIA-label computation converted the response and lexed it once to count code blocks.  
**Changed behavior:** The added table count converts and lexes the same full response before the existing code-block lexer, so every ARIA-label computation now performs two complete Markdown tokenizations.  
**Confidence:** 0.98 — The changed duplicate parse, synchronous rendering call path, and per-update identity change are explicit in repository code. Exact milliseconds vary with response length and provider chunk frequency, but the extra full-input parse and allocation on each reached update are certain.

**Causal diff evidence:** RIGHT line 57 adds \`marked.lexer(element.response.toString())\` while the same method still executes the pre-existing full-response \`marked.lexer(...)\` at line 82, changing one tokenization per label computation into two.

While a response streams, \`ChatResponseViewModel\` increments its model-change identity on every model update; \`ChatWidget.onDidChangeItems\` then replaces/renders that visible row, and \`AccessibiltyRenderer.renderElement\` synchronously calls this provider. Long, frequently updated responses therefore pay an extra full Markdown parse on the UI thread for every update, even when they contain no tables.

**Evidence:** \`ChatResponseViewModel\` increments \`\_modelChangeCount\` in its model \`onDidChange\` listener and includes it in \`dataId\` (\`chatViewModel.ts:426-429, 614\`); \`ChatWidget\` handles each accumulated view-model change with \`onDidChangeItems\`, whose diff identity is \`element.dataId\` (\`chatWidget.ts:961-970, 588-607\`); replacement renders invoke \`AccessibiltyRenderer.renderElement\`, which calls \`getAriaLabel\` synchronously (\`listWidget.ts:1281-1283\`). In this method, added line 57 calls \`marked.lexer(element.response.toString())\`, and unchanged line 82 immediately repeats the same lexer call for code blocks.

**Suggested direction:** Call \`element.response.toString()\` and \`marked.lexer(...)\` once, retain the token array, and derive both table and code-block counts from that shared result so ordering and label behavior remain unchanged.

### Scenario 1: Streaming a visible chat response

- Critical path: Each response-model update reaches the view-model change listener, \`ChatWidget.onDidChangeItems\`, tree row replacement/rendering, and synchronous ARIA-label computation before that render completes.
- Scaling input: One changed visible response row per streamed update; the parsed input is the full accumulated response, so cost grows with both update count and response length.
- Effective concurrency: Updates are accumulated within a zero-delay event turn, then processed serially on the UI thread; there is no worker or limiter for label tokenization.
- Cache behavior: There is no token cache or coalescing across updates. Each rendered identity performs two fresh \`response.toString()\`/Markdown lexer passes after the diff, versus one lexer pass before it.
- Mechanism confidence: High: model updates increment the response identity, the widget renders the changed row, the accessibility renderer calls the provider synchronously, and the diff visibly duplicates the full lexer call.
- Magnitude uncertainty: Provider chunk rate and response lengths vary, so exact latency is workload-dependent; long generated answers and frequent chunks are realistic and magnify the cost.
- Expensive boundaries: none found
- Verdict: Reportable material amplification: the diff adds a second complete Markdown tokenization and token-array allocation per visible streamed update, increasing UI-thread CPU/GC pressure.

### Scenario 2: Opening or restoring a chat with completed responses

- Critical path: Visible rows receive ARIA labels synchronously as the object tree renders them; offscreen virtualized rows are outside the immediate critical path until scrolled into view.
- Scaling input: Number and Markdown length of visible/restored response rows; virtualization limits immediate cardinality to rendered rows.
- Effective concurrency: Visible-row label computations are serial UI-thread work during tree rendering.
- Cache behavior: Cold and subsequent rerenders both tokenize each rendered response afresh; no shared tokenization exists between table and code-block counting.
- Mechanism confidence: High for the duplicate synchronous parsing; moderate impact because virtualization bounds row cardinality.
- Magnitude uncertainty: The number of simultaneously rendered rows is bounded by the viewport, making this less severe than streaming despite potentially long historical responses.
- Expensive boundaries: none found
- Verdict: The same reported duplicate-parse mechanism applies, but viewport virtualization limits this scenario's fan-out.

### Scenario 3: Focusing or navigating chat list responses

- Critical path: Ordinary focus changes use existing row ARIA attributes; keyboard type navigation can call the provider for the focused element, but does not introduce subprocess, IPC, filesystem, database, or network work.
- Scaling input: At most the focused response per navigation event, with cost proportional to that response's Markdown length.
- Effective concurrency: Synchronous and serial on the UI thread.
- Cache behavior: No cache; any direct provider call repeats both lexer passes. Existing rendered labels otherwise avoid recomputation on focus alone.
- Mechanism confidence: High that no external expensive boundary is reached and that any provider call duplicates tokenization.
- Magnitude uncertainty: Direct navigation-triggered provider calls are less frequent than streaming rerenders, so this is a secondary trigger.
- Expensive boundaries: none found
- Verdict: No separate finding beyond the shared-tokenization issue; event cardinality is low.
