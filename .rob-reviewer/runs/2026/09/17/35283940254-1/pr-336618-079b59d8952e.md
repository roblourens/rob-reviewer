## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/accessibility/chatAccessibilityProvider.ts:148` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/accessibility/chatAccessibilityProvider.ts:145`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/chatAccessibilityProvider.ts`  
**Introducing commit:** `91666d9a366e670f5387ceca12a50a3efad4cbd2`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.98

**Mechanism:** Adding table counting placed a second synchronous full-response Markdown lex in accessibility label generation. Because the accumulated response is reparsed whenever a changed chat row is rendered during streaming, CPU work scaled as two O(response length) parses per render and could block UI updates for long responses.

**Symptom:** Elevated UI-thread CPU and render latency during streaming or rerendering long chat responses, with potential interface/animation stutter.

**Fixed behavior:** The changed code snapshots the response text once and traverses a single `marked.lexer(responseText)` result to count both table and code tokens, reducing each accessibility-label render from two full-response parses to one while preserving label semantics.

**Evidence:** Base line 145 introduced `marked.lexer(element.response.toString())` for table counting while the same method already lexed the full response again at base line 179 for code-block counting. `Response.updateContent` invalidates the cached string and fires `onDidChangeValue`; `ChatResponseViewModel` and `ChatViewModel` propagate that event, and `ChatWidget` accumulates it then calls `listWidget.refresh()`. The list accessibility renderer calls `getAriaLabel` during row rendering. Thus each visible streamed rerender of an accumulated response performed two synchronous full Markdown lexes on the UI thread. The added test directly asserts one lexer invocation per label after the fix.

### Scenario 1: Visible chat response streaming and accessibility-label rerendering

- Critical path: A non-quiet \`Response.updateContent\` invalidates the response string, fires through \`ChatResponseViewModel\`/\`ChatViewModel\`, is accumulated by \`ChatWidget\`, and refreshes the chat list. Rendering the changed visible row synchronously calls \`ChatAccessibilityProvider.getAriaLabel\`; response serialization and Markdown lexing must complete before the row's aria-label is set.
- Scaling input: The accumulated response length controls each parse cost; the number and frequency of streamed updates that cause visible row rerenders controls repetition. Tree diffing limits rerendering to changed/rendered rows rather than all history items.
- Effective concurrency: Event handling, tree refresh, label generation, and Markdown lexing are synchronous and serialized on the UI thread. Event accumulation coalesces same-turn model events, but there is no parallel parsing or boundary fan-out.
- Cache behavior: \`AbstractResponse.toString()\` lazily caches its representation until each content update invalidates it. The changed code reads that representation once per label. \`marked.lexer\` has no observed cache; the PR reduces two full lexes of the same current text to one. Cold and post-update labels rebuild the string once; warm labels reuse the string but still lex once.
- Mechanism confidence: High: the event chain, list accessibility renderer call, two pre-diff lexer calls, and one post-diff lexer call are explicit in code and covered by the added invocation-count test.
- Magnitude uncertainty: Exact response sizes, stream cadence, and milliseconds saved vary by model and session. The duplicate O(response length) synchronous parse and its render-path reachability are direct.
- Expensive boundaries: none found
- Verdict: No regression introduced. The production change removes repeated synchronous CPU/allocation work and was recorded as a regression fix; it adds no external boundary, concurrency burst, or retained cache state.

### Scenario 2: Initial display, scrolling, and rerendering of existing chat history rows

- Critical path: When list virtualization renders a response row, \`AccessibiltyRenderer.renderElement\` synchronously obtains its aria-label before assigning DOM accessibility attributes. Only currently rendered rows incur this work; sticky-row rendering may independently request a label for that rendered sticky node.
- Scaling input: Cost scales with the lengths of response rows entering the rendered viewport and the number of rows newly rendered or explicitly refreshed, not with every stored response at once under normal virtualization.
- Effective concurrency: Rows are rendered synchronously by the list/tree renderer on the UI thread; there is no worker or shared parallelism.
- Cache behavior: Existing response string representations may be warm and avoid reconstruction, but Markdown tokens are not cached. Post-change each rendered label performs one lex instead of two; no new cache key, negative-cache state, or invalidation path is introduced.
- Mechanism confidence: High: both list and sticky tree accessibility rendering directly invoke the provider, and the diff reduces work within that provider.
- Magnitude uncertainty: The number of rows rendered during a refresh depends on viewport and sticky-scroll behavior, but per-label parse reduction is certain.
- Expensive boundaries: none found
- Verdict: No regression introduced; CPU and temporary token allocation decrease for each rendered response label.

- Expensive boundaries: none found
- Verdict: No reportable regression. This is test-only paint suppression; screenshot references in the Markdown inventory are documentation data and do not add runtime network work.
