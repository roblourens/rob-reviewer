## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/base/common/objects.ts:27` (`RIGHT`)  
**Blamed base line:** `src/vs/base/common/objects.ts:27`  
**Introducing path:** `src/vs/base/common/objects.ts`  
**Introducing commit:** `10541d91a74351643b5a0982ebc11cc7288993aa`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.97

**Mechanism:** Array.shift() repeatedly compacts a wide FIFO worklist, causing cumulative quadratic CPU work while synchronously freezing broad object graphs.

**Symptom:** Large, broad configuration values or document-change payloads can spend disproportionate synchronous time draining deepFreeze's queue, delaying getter completion or extension event delivery.

**Fixed behavior:** The indexed for-loop advances through the dynamically growing worklist without removing its prefix, reducing queue bookkeeping from O(N^2) slot movement to O(N) indexed reads; RIGHT line 29 clears each consumed reference so processed graph objects are not retained solely by the worklist.

**Evidence:** In the base revision, deepFreeze uses a FIFO array worklist and drains it with stack.shift(). Object-property enumeration can enqueue a wide frontier, so each subsequent shift moves the remaining array elements; draining N queued objects performs a quadratic number of slot moves. The changed RIGHT line 27 replaces that drain with a monotonically increasing cursor while preserving FIFO traversal. This synchronous helper is reached by configuration value/inspection getters (configurationModels.ts:24,101-117,611) and twice before extension document-change listeners are fired (extHostDocuments.ts:196-219), so the queue bookkeeping directly delays those consumers for large wide object graphs.

### Scenario 1: Reading or inspecting a configuration value that returns a structured object

- Critical path: ConfigurationModel.inspect/value getters synchronously call freeze/deepFreeze before returning the value, so traversal is on the caller's critical path.
- Scaling input: The reachable unfrozen configuration object graph, including broad arrays/maps represented as objects; effective worklist cardinality is the number of enqueues after already-frozen and typed-array properties are skipped.
- Effective concurrency: One synchronous traversal per cold returned root; no internal parallelism, limiter, queue, or async overlap.
- Cache behavior: Cold unfrozen roots traverse and freeze the reachable graph. Warm reads of the same root are bypassed by Object.isFrozen(data), so they do not rebuild the worklist. There is no negative-cache state.
- Mechanism confidence: High: the old shift-based FIFO performs repeated prefix compaction, while the changed cursor performs one indexed read per enqueue. The added undefined assignment releases consumed object references, though the backing array remains transiently sized to total enqueues until return.
- Magnitude uncertainty: Repository call flow proves synchronous reachability and graph-size scaling, but typical production configuration graph widths and exact durations are not established from repository code.
- Expensive boundaries: none found
- Verdict: No introduced regression. The diff removes quadratic queue-compaction CPU work. Its transient worklist backing storage can grow with total enqueues rather than current frontier size, but it is call-bounded, clears processed references, and no realistic narrow configuration graph large enough for a reportable memory regression is established.

### Scenario 2: Delivering a text document model-change event to extension-host listeners

- Critical path: An incoming $acceptModelChanged RPC updates the document, constructs two public change-event graphs, deep-freezes each synchronously, and only then fires the corresponding extension events. Both freezes are on event-delivery's critical path.
- Scaling input: The number of serialized content changes in one model event and each change's reachable range/metadata objects. Two event graphs are built and frozen sequentially per accepted model change; the second uses a separately mapped changes array.
- Effective concurrency: One incoming model-change handler runs its two deepFreeze calls sequentially. The changed loop itself is synchronous and introduces no burst or additional concurrency.
- Cache behavior: Each emitted event root and mapped contentChanges array is newly allocated, so both roots are cold. Objects such as the document that were frozen by the first traversal are skipped when encountered by the second. There is no cross-event worklist cache or coalescing.
- Mechanism confidence: High: queue order and traversal cardinality are preserved, while repeated Array.shift compaction is replaced by linear cursor advancement. No extra IPC, serialization, or traversal was added.
