- Critical path: Chromium resolves a vscode-remote-resource URL, the Electron protocol handler awaits net.fetch to the forwarded HTTP endpoint, the remote server validates the token and origin, and serveFile stats and potentially opens/streams the file before the renderer can use it. - Scaling input: The number of distinct remote resource URLs requested by the rendered workbench content after browser caching and request coalescing.
- Effective concurrency: Chromium/Electron controls concurrent resource fetches; the PR adds no Promise.all fan-out, queue, limiter, or retry and preserves one net.fetch per protocol request.
- Cache behavior: Built-in and installed extension resources retain public max-age caching; other files retain ETag revalidation. The added Access-Control-Allow-Origin and existing Vary: Origin do not alter cache policy, keys, or coalescing in this code.
- Mechanism confidence: High: the old inline handler and new helper are operation-for-operation equivalent, while the server change performs only bounded header selection before the unchanged serveFile call.
- Magnitude uncertainty: Resource counts and remote filesystem/network latency vary by workbench content and remote environment, but the diff does not increase their cardinality or scheduling.
- Expensive boundaries:
  - network at <code>src/vs/platform/protocol/electron-main/remoteResourceProtocol.ts:createRemoteResourceRequestHandler</code>: Electron net.fetch relays the custom-scheme request to the remote authority over HTTP.; cardinality: One HTTP request per browser cache miss or revalidation for each effective resource URL; browser caching/coalescing remains authoritative.

- Verdict: No reportable performance regression. Native-origin requests now short-circuit before the existing web-origin regular expression, and the required network and filesystem work is unchanged.

- Effective concurrency: HTTP/browser request concurrency is unchanged; origin matching remains one synchronous regular-expression test per request with an origin, and there is no added fan-out.
- Cache behavior: Positive browser caching and ETag behavior are unchanged. Vary: Origin and allowed configured-origin handling already existed before this PR; there is no application cache or negative-cache change.

- Magnitude uncertainty: Actual resource counts vary by page and extensions, but no changed mechanism scales beyond constant header work per existing request.
- Expensive boundaries:

- Verdict: No reportable performance regression; boundary count, cache behavior, and concurrency are unchanged.

- Mechanism confidence: High: the awaited startup work and cleanup are explicit in the changed harness code.

- Verdict: The harness gains small constant startup work, but there is no realistic scaling mechanism or material performance regression warranting a finding.
