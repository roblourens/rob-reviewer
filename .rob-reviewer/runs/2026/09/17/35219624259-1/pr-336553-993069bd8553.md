## Findings (1)

### 1. [medium] Preserve focus without restarting the session open

**Finding ID:** `PERF-8A4AF96A46E1`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:4270</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** provider resolution work and agent-host IPC/subscriptions (and potentially on-demand connection work)  
**Scaling:** Every successful double-click rename while the initial open promise is pending turns one user gesture into two overlapping open pipelines; repeated rename gestures repeat this 2x boundary work.  
**Outcome:** increased session-open latency from cancelling and restarting progress, plus duplicate backend/IPC work  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A double-click still caused the list's normal open event once, then began inline rename; the renderer did not issue another onSessionOpen/onChatOpen call.  
**Changed behavior:** After inline rename starts, preservePendingOpenFocus mutates the request and calls invokeOpenRequest again whenever the first open has started, forwarding a second onSessionOpen/onChatOpen while the first promise is still pending.  
**Confidence:** 0.99 — The changed reinvocation, two-call test expectation, forwarding path, service cancellation/restart behavior, and uncancellable provider hook are all explicit. Exact duration depends on provider/cache state, so severity is medium rather than high.

**Causal diff evidence:** The added RIGHT line 4270 directly calls this.invokeOpenRequest(request) from the double-click focus-preservation callback; the new test explicitly expects preserveFocusValues \[false, true\], proving two opens for one double-click.

Double-clicking a renameable session/chat while it opens can discard up to the elapsed open progress and issue duplicate provider/backend work. This is especially visible for cold or legacy agent-host sessions, where resource resolution is explicitly documented as taking seconds and performs an IPC subscription.

**Evidence:** SessionsView forwards each invocation to sessionsService.openSession/openChat. Each service call runs \_startOpenSession(), so the second cancels the first and starts resolution again. openSession awaits sessionsManagementService.resolveSessionResource, which sequentially invokes provider hooks without a cancellation token; LocalAgentHostSessionsProvider's hook creates an agent-host subscription and may wait up to LEGACY\_MIGRATION\_TIMEOUT\_MS (30s). Thus cancellation cannot stop the first boundary operation, while the second starts another one and the visible open can complete only through the restarted pipeline.

**Suggested direction:** Do not invoke the open callback a second time. Preserve or restore the inline editor's focus when the original open settles, or defer the one open until the click/double-click intent is known, while retaining a single provider-resolution pipeline.
