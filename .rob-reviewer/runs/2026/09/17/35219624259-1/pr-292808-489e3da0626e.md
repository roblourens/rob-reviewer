### Scenario 1: Normal VS Code Snap launch on an already-seen revision

- Critical path: The shell launcher performs environment setup and filesystem existence checks, waits only for pre-existing asynchronous setup jobs, then replaces itself with the Electron process. The diff removes an environment copy/export and leaves the same local-share directory check and XDG\_DATA\_DIRS prepend, so it adds no work to this critical path.
- Scaling input: One launcher invocation; no collection or fan-out is introduced by the diff.
- Effective concurrency: Launcher setup is synchronous, existing revision cache jobs are skipped on a warm revision, and one Electron process is exec'd.
- Cache behavior: SNAP\_DESKTOP\_LAST\_REVISION makes this the warm path. Existing directories avoid mkdir; the diff does not alter the revision key or cache state.
- Mechanism confidence: High confidence that no filesystem, process, IPC, or network boundary was added to warm startup by the changed hunks.
- Magnitude uncertainty: Downstream libraries may consult the user's inherited/default XDG data home, but repository evidence does not establish extra call count, larger effective data, or a new hot-path operation.
- Expensive boundaries:
  - filesystem at <code>resources/linux/snap/electron-launch:118</code>: Check and, only when absent, create $SNAP\_USER\_DATA/.local/share.; cardinality: One directory stat per launch and at most one mkdir for the lifetime of the directory.
    - Introduced by diff: false; previous behavior: The launcher exported XDG\_DATA\_HOME to this same path, then called ensure\_dir\_exists on it.; critical-path effect: Synchronous before Electron starts, but identical physical path and call count before and after the diff.
  - subprocess at <code>resources/linux/snap/electron-launch:269</code>: Replace the launcher with the VS Code Electron executable.; cardinality: Exactly one exec per application or URL-handler launch.
    - Introduced by diff: false; previous behavior: The same exec occurred after the same launcher setup.; critical-path effect: This is the existing application-start boundary; the changed environment is inherited but the boundary count and scheduling are unchanged.
- Verdict: No reportable regression: the diff changes data-home semantics without adding startup work, frequency, fan-out, retention, or concurrency.

### Scenario 2: First Snap launch after a VS Code revision update

- Critical path: The launcher performs revision-scoped cache maintenance and waits for its existing asynchronous module/schema/cache compilation before exec. The diff removes synchronous recursive deletion of the Snap-local fonts directory and symlink creation; the MIME deletion still targets the same physical directory as before.
- Scaling input: Revision-local cache contents; the diff decreases operations by removing font cleanup and leaves MIME cleanup cardinality unchanged.
- Effective concurrency: Existing cache compilation jobs run asynchronously but are all joined before exec. Removed font operations were synchronous; no new burst is introduced.
- Cache behavior: Cold per SNAP\_VERSION through .last\_revision; warm launches skip all revision update work. Cache key and negative behavior are unchanged.
- Mechanism confidence: High confidence from the literal before/after paths and launcher ordering.
- Magnitude uncertainty: The amount of removed font-tree work depends on the local path contents, but this uncertainty can only affect the size of an improvement, not create a regression.
- Expensive boundaries:
  - filesystem at <code>resources/linux/snap/electron-launch:176</code>: Recursively remove $SNAP\_USER\_DATA/.local/share/mime on revision change.; cardinality: One recursive deletion per new SNAP\_VERSION, proportional to files in the revision-local MIME directory.
    - Introduced by diff: false; previous behavior: One rm -rf of $XDG\_DATA\_HOME/mime, where the launcher had just assigned XDG\_DATA\_HOME=$SNAP\_USER\_DATA/.local/share.; critical-path effect: Synchronous on update startup, but the path and multiplicity are unchanged because the old XDG\_DATA\_HOME value was the same literal directory.
  - filesystem at <code>resources/linux/snap/electron-launch deleted lines 173-179</code>: Delete the revision-local fonts path and recreate a symlink to the real-home fonts directory.; cardinality: Previously one recursive deletion and at most one symlink per revision update; now zero.
    - Introduced by diff: false; previous behavior: Each changed SNAP\_VERSION synchronously removed the fonts path and conditionally linked the user's fonts before continuing.; critical-path effect: The diff removes synchronous filesystem work from update startup.
  - subprocess at <code>resources/linux/snap/electron-launch:185-264</code>: Compile existing GIO, schema, pixbuf, and input-module caches and wait for completion.; cardinality: A fixed small set of existing jobs once per revision update.
    - Introduced by diff: false; previous behavior: The same jobs and wait occurred after font and MIME maintenance.; critical-path effect: The launcher already waits for these jobs before Electron starts; the changed hunks do not add, move, or increase them.
- Verdict: No reportable regression; update startup performs strictly less synchronous filesystem maintenance in the changed area.

### Scenario 3: Open the terminal Run Recent Command picker for a Fish shell in the Snap build

- Critical path: The picker awaits getShellFileHistory before it finishes materializing shell-history quick-pick items. On a cold per-window lookup, fetchFishHistory performs one file read and parses the file; subsequent lookups use the in-memory shellFileHistory map.
- Scaling input: Fish history file size and unique command count, with one effective file per shell type per window after caching.
- Effective concurrency: The cold read is a single awaited operation; the result is cached for later picker invocations, with no per-entry I/O or concurrency fan-out.
- Cache behavior: Cold lookup reads and parses once; successful and missing results are both cached in shellFileHistory until clearShellFileHistory or window lifetime ends.
- Mechanism confidence: High confidence in the one-read cached call path, low confidence in any diff-caused cost increase because both before and after paths are real Fish history stores.
- Magnitude uncertainty: The host and Snap-local history files can differ in size, but the diff provides no evidence that the newly selected file is systematically larger; both can accumulate over time.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/terminalContrib/history/common/history.ts:464-542</code>: Read the Fish history file selected from inherited XDG\_DATA\_HOME or HOME.; cardinality: One read per Fish shell type per window after caching, not one read per command; parsing and item allocation scale with file bytes and unique commands.
    - Introduced by diff: false; previous behavior: The same code read $SNAP\_USER\_DATA/.local/share/fish/fish\_history because the launcher overrode XDG\_DATA\_HOME; integrated Fish shells inherited that same location and could populate it, so the diff does not establish a systematic increase in effective history cardinality.; critical-path effect: The picker awaits the read on its cold invocation. The boundary and full-file parsing are pre-existing; the launcher diff changes which valid user data location is selected.
- Verdict: No finding: restoring the authoritative user data path does not itself prove greater frequency or effective cardinality, and the expensive operation remains a cached one-time read.

**Summary:** Reviewed the complete one-file diff and traced warm startup, revision-update startup, Electron execution, and the downstream Fish-history workflow. The change removes update-time filesystem work and does not introduce a high-confidence performance regression.
