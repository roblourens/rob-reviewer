## Findings (4)

### 1. [medium] Stop duplicating every server payload into the log channel

**Finding ID:** `PERF-C3099A1CB0D5`  
**Location:** <code>src/vs/workbench/api/node/extHostMpcNode.ts:85</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Message bytes, string allocations, extension-host-to-renderer IPC calls, and filesystem log writes  
**Scaling:** For every stdout JSON line, cost scales with payload bytes and message rate: the line is converted to a string and sent once as a log and again as the protocol message. MCP tool results can contain arbitrary text, embedded blobs, and base64 image data.  
**Outcome:** Higher tool-call latency, IPC/CPU pressure, and excessive log I/O for large or frequent results  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, MCP stdout payloads were not copied through an additional logging IPC and persisted to a per-server log file.  
**Changed behavior:** The new PassThrough data listener sends the complete stdout line through $onDidPublishLog, while the second data listener on the same stream sends that same line through $onDidReceiveMessage. McpServerConnection then writes the first copy with ILogger.info to a logger backed by the logs folder.  
**Confidence:** 0.99 — The duplicate listeners, duplicate string conversion, two IPC methods, and file-backed logger are directly traced. Payload magnitude varies, but the protocol explicitly permits base64 image/blob content.

**Causal diff evidence:** Added line 85 forwards every complete server stdout payload as an info log in addition to the protocol-forwarding call added on line 88.

A server returning a multi-megabyte image/blob or streaming frequent messages makes VS Code allocate and transfer the full content twice and persist an extra copy before/alongside normal JSON parsing, causing avoidable stalls and disk traffic.

**Evidence:** Lines 84-88 attach two data listeners to the same debug stream. One performs '\[Server Says\] ' + line.toString() and an RPC; the other performs line.toString() and a second RPC. MainThreadMcp parses the protocol copy, while McpServerConnection forwards the log copy to ILogger.info; createLogger(id) resolves to a file under logsHome.

**Suggested direction:** Do not info-log raw protocol payloads. Log bounded metadata or byte counts, and gate any capped payload tracing behind an explicit trace/debug mode so the normal path performs one IPC transfer.

### 2. [medium] Remove exited MCP children from the server map

**Finding ID:** `PERF-4B4EB6411BD5`  
**Location:** <code>src/vs/workbench/api/node/extHostMpcNode.ts:109</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Retained ChildProcess objects, AbortControllers, stdio streams, pipeline objects, and event-listener closures  
**Scaling:** Retention grows by one full subprocess object graph for every server that exits or errors without first receiving an explicit $stopMcp; each restart uses a new numeric id and adds another map entry for the extension-host lifetime.  
**Outcome:** Unbounded retained memory and increasing GC pressure across crash/restart cycles  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, the extension host had no MCP child-process map and retained no MCP subprocess object graphs.  
**Changed behavior:** The new code inserts every spawned child into nodeServers, but deletion only occurs in $stopMcp. The child exit handler reports Stopped/Error to the main thread without removing its id, and the main thread then drops its own id mapping, so no later stop call can clean the extension-host entry.  
**Confidence:** 0.99 — Map ownership, the only deletion site, terminal-state call flow, and monotonically increasing restart ids are explicit. Per-entry size varies but unbounded lifetime growth is certain under repeated spontaneous exits.

**Causal diff evidence:** Added line 109 roots every spawned child in nodeServers without a corresponding removal in the newly added terminal exit/error path.

A misconfigured or unstable MCP server that exits and is repeatedly restarted steadily grows extension-host memory even though all prior processes are dead.

**Evidence:** nodeServers.set retains abortCtrl and child at line 109. $stopMcp is the sole delete site. The exit callback at lines 100-107 only publishes state, and MainThreadMcp deletes its \_servers entry on Stopped/Error; a restart allocates a new id via \_serverIdCounter.

**Suggested direction:** Use a once-only close/exit cleanup that removes the entry (guarded so it only deletes the same child) and disposes its stream pipeline/listeners; keep explicit stop cleanup idempotent.

### 3. [medium] Coalesce tool-list refresh notifications

**Finding ID:** `PERF-0A303A5907A9`  
**Location:** <code>src/vs/workbench/contrib/mcp/common/mcpServer.ts:168</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Concurrent JSON-RPC requests, pending DeferredPromises/cancellation listeners, IPC messages, and MCP server work  
**Scaling:** Each tools/list\_changed notification starts one additional refresh per server, with potentially multiple paginated boundary calls per refresh; replacements do not cancel or dispose the previous ObservablePromise, so concurrency and retained pending requests grow linearly with notification count.  
**Outcome:** Excessive IPC/server work and memory growth, reducing responsiveness and throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no MCP tool-list notification path and no corresponding burst of tools/list requests.  
**Changed behavior:** The added listener invokes updateTools for every notification. updateTools immediately calls handler.listTools and merely replaces the observable wrapper; all older requests remain active under the same connection-lifetime cancellation token.  
**Confidence:** 0.98 — The event-to-request call path and absence of per-refresh cancellation, sequencing, or coalescing are explicit. Notification burst frequency varies by server, but even legitimate dynamic initialization can overlap slow or paginated list calls.

**Causal diff evidence:** Added line 168 installs a direct one-notification-to-one-refresh listener without checking for an in-flight refresh or coalescing queued changes.

A dynamic server that emits a burst while loading plugins—or a server that emits changes while previous list requests are slow—causes overlapping full tool enumerations. If it stops replying, every notification leaves another entry and listener in \_pendingRequests until the whole connection is torn down.

**Evidence:** populateLiveData creates one CancellationTokenSource for the connection, line 168 maps every onDidChangeToolList event directly to updateTools, and updateTools constructs a new ObservablePromise around handler.listTools. ObservablePromise has no disposal/cancellation behavior, while sendRequest retains each DeferredPromise in \_pendingRequests until response or token cancellation.

**Suggested direction:** Serialize refreshes per server and coalesce notifications while one is in flight into a single dirty rerun, or cancel the superseded list request with a refresh-scoped token.

### 4. [medium] Defer MCP cache loading until after workbench restore

**Finding ID:** `PERF-E3352DCA9B76`  
**Location:** <code>src/vs/workbench/contrib/mcp/browser/mcp.contribution.ts:34</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Synchronous JSON parsing and allocation of persisted tool metadata objects  
**Scaling:** Cost grows with both persisted PROFILE and WORKSPACE tool-cache payloads; each cache permits 128 server entries, while each entry can contain an unbounded number and size of tool descriptions and JSON schemas.  
**Outcome:** Increased startup latency by blocking editor/UI restoration on cache deserialization  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, workbench restore did not instantiate the MCP service or synchronously deserialize MCP tool metadata.  
**Changed behavior:** The new BlockRestore contribution immediately reads \`mcpService.servers\`; that forces the delayed McpService, whose constructor creates two McpServerMetadataCache instances and synchronously calls storageService.getObject for each scope.  
**Confidence:** 0.97 — The changed registration phase, eager observable read, service-construction chain, and synchronous JSON parse are all explicit. Exact cache size in bytes varies by installed servers, which affects severity rather than the mechanism.

**Causal diff evidence:** Added line 34 registers McpContextKeysController at WorkbenchPhase.BlockRestore; its immediate servers read forces the newly added service and its two synchronous cache loads before restore.

Every window start reaches this path. On warm starts for users with cached MCP tools, potentially large schemas are parsed and materialized before an editor can be shown, even though MCP discovery itself is intentionally scheduled AfterRestored.

**Evidence:** WorkbenchPhase.BlockRestore is documented as blocking an editor from showing. McpContextKeysController's constructor immediately starts an autorun that reads IMcpService.servers. McpService constructs PROFILE and WORKSPACE metadata caches, and McpServerMetadataCache synchronously calls getObject; the storage implementation parses the stored JSON synchronously. Discovery is registered one line earlier for AfterRestored, so no real server count can arrive during restore.

**Suggested direction:** Register the context-key/action-rendering contributions AfterRestored (matching discovery), or keep them lazy and avoid touching IMcpService until discovery or the MCP UI is first used.

### Scenario 1: Window startup and editor/UI restoration

- Critical path: McpContextKeysController is instantiated in BlockRestore and immediately reads IMcpService.servers, forcing McpService construction before editors can show. Its two metadata-cache constructors synchronously deserialize storage on this critical path.
- Scaling input: Persisted tool metadata in PROFILE and WORKSPACE scopes: up to 128 server keys in each LRU, with unbounded tools, descriptions, and input-schema bytes per key.
- Effective concurrency: Both cache constructions and getObject parses run synchronously and serially on the renderer startup path; no deferral or background boundary exists.
- Cache behavior: Cold/empty caches make the two lookups cheap. Warm caches synchronously parse and materialize all stored entries on every window start; the cache is entry-count bounded but not byte bounded.
- Mechanism confidence: High: registration phase, forced property read, service constructor, and synchronous storage parse were traced directly.
- Magnitude uncertainty: Typical cache byte size depends on configured servers and their schemas, but large tool schemas are permitted and the two synchronous parses are definitively on the blocking phase.
- Expensive boundaries:
  - serialization at <code>src/vs/workbench/contrib/mcp/common/mcpServer.ts:45 McpServerMetadataCache constructor</code>: Read and synchronously JSON-parse persisted mcpToolCache data; cardinality: Exactly two reads/parses per McpService construction, one PROFILE and one WORKSPACE; bytes scale with cached metadata.
    - Introduced by diff: true; previous behavior: No MCP cache was loaded during restore before this PR.; critical-path effect: Blocks BlockRestore and therefore delays editors/UI from showing.
- Verdict: Reportable eager startup work because MCP discovery itself occurs only AfterRestored, so forcing and deserializing the service during BlockRestore provides no earlier usable discovery result.

### Scenario 2: Post-restore discovery of local, remote, and configured MCP servers

- Critical path: McpDiscovery runs AfterRestored, so environment IPC, Claude configuration reads, and watcher creation are off the editor-restore critical path. Configuration inspection and mapping run after restore as well.
- Scaling input: Three configuration scopes plus one Claude config adapter locally and, when connected, one remotely; server-definition mapping scales with configured server count.
- Effective concurrency: Local and remote discovery instances start independently. Each filesystem adapter performs one initial read and uses a 500 ms RunOnceScheduler for watcher changes; there is no unbounded per-file fan-out with the current single adapter.
- Cache behavior: No discovery-result cache. Existing or missing Claude files are read once after restore; watcher events are coalesced over 500 ms. Configuration changes are equality-checked before registry updates.
- Mechanism confidence: High: scheduling phase, exact adapter count, watcher debounce, and boundaries are explicit.
- Magnitude uncertainty: Remote filesystem/IPC latency varies, but placement after restore and fixed current adapter cardinality bound user-visible startup impact.
- Expensive boundaries:

### Scenario 3: Starting, stopping, crashing, and restarting a stdio MCP server

- Mechanism confidence: High: monotonically increasing ids, sole explicit-stop deletion, terminal state flow, and retained map were traced.
- Magnitude uncertainty: Per-child retained object size is runtime-dependent, but retention is unbounded across crash/restart history and ownership proves old entries remain rooted.
- Expensive boundaries:

### Scenario 4: MCP protocol traffic, live tool refresh, and tool invocation

- Critical path: Each protocol request is JSON-stringified in the renderer, crosses to the extension host, travels over child stdin/stdout, crosses back, and is parsed in MainThreadMcp. Tool calls await this path. On connection and each tools/list\_changed notification, a paginated tools/list request refreshes registrations.
- Scaling input: Message count and payload bytes, including arbitrary text/blob/base64 image tool results; number of notifications; pages and tools per list response; number of simultaneously connected servers.
- Effective concurrency: Each paginated refresh is serial page-by-page, but refreshes created by separate notifications overlap without a limiter or coalescer. Different servers are independent. Every inbound stdout line also triggers two extension-host-to-renderer RPCs.
- Cache behavior: Warm metadata supplies pre-start tools only. Once connected, the initial and notification-triggered live list requests always run; replacing ObservablePromise does not cancel prior work. Responses update the cache later.
- Mechanism confidence: High: both stdout listeners, file-backed logger, notification listener, pending-request map, and non-cancelling ObservablePromise were traced.
- Magnitude uncertainty: Normal server payloads and notification rates vary, but large binary results are explicitly allowed and the duplicate transfer plus unbounded refresh concurrency are deterministic.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/node/extHostMpcNode.ts:85 stdout logging listener</code>: Forward the full stdout line as a log RPC in addition to forwarding it as the protocol-message RPC; cardinality: Two renderer-bound IPC calls per stdout JSON line instead of the one needed for protocol delivery; bytes in both calls equal the full payload plus a prefix.
    - Introduced by diff: true; previous behavior: No MCP payload duplication or MCP per-server log write existed.; critical-path effect: Runs synchronously on every incoming message and adds allocation/IPC/logging work alongside tool-result delivery.
  - filesystem at <code>src/vs/workbench/contrib/mcp/common/mcpServerConnection.ts:82 launch log listener</code>: Write the duplicated raw protocol payload through a file-backed per-server logger; cardinality: One info log entry for every inbound protocol line, in addition to stderr/log notifications and state logs.
    - Introduced by diff: true; previous behavior: Raw MCP protocol results were not persisted to logs.; critical-path effect: Adds filesystem/log-buffer pressure to protocol handling; magnitude scales with payload bytes.
  - IPC at <code>src/vs/workbench/contrib/mcp/common/mcpServer.ts:168 tool-list change listener</code>: Issue tools/list JSON-RPC requests through renderer/extension-host/child boundaries; cardinality: One complete, potentially paginated enumeration per notification per server, with no reduction for in-flight refreshes.
    - Introduced by diff: true; previous behavior: No MCP tool-list refresh traffic existed.; critical-path effect: Refresh completion controls updated tool registration; overlapping requests compete with normal tool traffic.
- Verdict: Two reportable regressions: duplicate full-payload IPC/logging and missing refresh coalescing. Pagination accumulation was considered but omitted because realistic page counts were not established strongly enough for a separate finding.
