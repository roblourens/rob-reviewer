## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/workbench/contrib/mcp/common/mcpServerConnection.ts:156` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/mcp/common/mcpServerConnection.ts:141`  
**Introducing path:** `src/vs/workbench/contrib/mcp/common/mcpServerConnection.ts`  
**Introducing commit:** `eb700003ebf3797af1de1f9e222478d6d7f7eea3`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `latency`  
**Confidence:** 0.98

**Mechanism:** Pending start promises waited exclusively for Running/Error while explicit disposal transitioned the connection to Stopped, so callers and the per-server sequencer could remain blocked indefinitely after policy-driven or user-driven cleanup.

**Symptom:** Stopping or disposing an MCP connection during Starting could leave startup and later sequenced operations waiting forever.

**Fixed behavior:** The connection now records an explicit stop request and line 156 makes pending state waiters accept Stopped when that request is active, so disposing or stopping a Starting transport releases all queued startup callers instead of retaining an indefinitely blocked critical path.

**Evidence:** In the base revision, start() callers that arrived while a connection was Starting waited only for Running or Error via \_waitForState. dispose() then forced the state to Stopped, which was outside those accepted kinds, leaving every pending start promise unresolved; the added tests exercise two concurrent starts and prove both previously vulnerable waiters now settle on stop/dispose. Blame attributes the old wait condition at base line 141 to eb700003ebf3797af1de1f9e222478d6d7f7eea3.

### Scenario 4: Stopping or disposing a connection while startup is pending

- Critical path: Pending start calls wait on connection state while the per-server Sequencer cannot progress until the active start settles. Explicit stop/disposal now marks stop requested and allows Stopped to resolve those waiters.
- Scaling input: The old retained-wait cost grew with concurrent callers waiting on the same Starting connection and with the lifetime of the process. The fix resolves all observers on the same state transition.
- Effective concurrency: Concurrent start callers coalesce on the same state wait; outer McpServer starts are serialized by Sequencer. Stop/dispose releases all waiters without spawning replacement work.
- Cache behavior: No cache participates. The stop-request flag is reset transactionally on a new valid start and retained only for the connection object's lifetime.
- Mechanism confidence: Very high: the base wait predicate, disposal transition, new stop flag, tests with two pending starts, and introducing commit were all established.
- Magnitude uncertainty: How often users revoke policy or stop during Starting is unknown, but the indefinite-wait mechanism is deterministic once triggered.
- Expensive boundaries:
  - subprocess at <code>src/vs/workbench/contrib/mcp/common/mcpServerConnection.ts stop/dispose</code>: Stop/dispose the underlying local transport when present.; cardinality: One cleanup for the connection; all concurrent start callers share the same connection state and are released without duplicate transport cleanup.
    - Introduced by diff: false; previous behavior: Transport cleanup already occurred, but waiters accepted only Running/Error and could remain unresolved after disposal forced Stopped.; critical-path effect: Cleanup unblocks pending startup and subsequent sequenced operations.
  - network at <code>src/vs/workbench/contrib/mcp/common/mcpServerConnection.ts stop/dispose</code>: Stop/dispose the underlying remote transport when present.; cardinality: One cleanup for the connection regardless of the number of pending start callers.
    - Introduced by diff: false; previous behavior: The transport was disposed but pending starts could remain blocked indefinitely.; critical-path effect: Releases the connection and now also releases pending startup promises.
- Verdict: This PR fixes, rather than introduces, a cleanup-lifecycle latency regression; it was recorded through report\_regression\_fix.
