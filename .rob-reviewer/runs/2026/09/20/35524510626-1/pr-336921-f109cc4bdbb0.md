**Relevant issue families:** cleanup-lifecycle

### Scenario 1: Send an MCP request whose HTTP response is an SSE stream and the response reader fails while the handle remains active

- Critical path: Main-thread message IPC invokes ExtHostMcpService.$sendMessage; the handle performs the existing POST fetch, reads/parses the SSE response, publishes messages by IPC, and resolves send after the read loop ends. On a read failure, the changed await observes reader.cancel() before the existing warning path completes.
- Scaling input: One response reader per in-flight POST request. The initial request is serialized while transport mode is unknown; after HTTP mode is established, sends can be concurrent, so failures scale with concurrently in-flight requests rather than SSE events or payload items.
- Effective concurrency: A Sequencer serializes only requests while mode is Unknown. Established HTTP requests can overlap without a shared limiter; each failed response independently reaches this catch once.
- Cache behavior: No cache participates. Authentication discovery/token behavior is unchanged, and neither warm nor cold state changes the stream cleanup branch.
- Mechanism confidence: High: ReadableStream cancellation on an already errored stream returns a rejected promise with the stored error and does not execute the underlying source cancellation algorithm. Awaiting it adds promise observation but no network cancellation or input-scaling work.
- Magnitude uncertainty: Real deployments may vary in the number of simultaneous HTTP requests and stream failures, but the changed cancellation branch is reached only after the reader is already errored.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadMcp.ts:97 and src/vs/workbench/api/common/extHostMcp.ts:145</code>: Dispatch the MCP request from the main thread to the extension host; cardinality: One IPC call per outgoing MCP message
    - Introduced by diff: false; previous behavior: The same IPC dispatch occurred before the diff.; critical-path effect: Starts request processing and is already on the send critical path
  - network at <code>src/vs/workbench/api/common/extHostMcp.ts:\_sendStreamableHttp/\_doSSE</code>: POST the MCP message and consume its response body; cardinality: One POST per message, plus response-body reads per delivered chunk
    - Introduced by diff: false; previous behavior: The same POST and stream reads occurred before the diff.; critical-path effect: The fetch and response stream determine send completion
  - IPC at <code>src/vs/workbench/api/common/extHostMcp.ts:\_handleSuccessfulStreamableHttp and \_log</code>: Publish parsed MCP response messages or the stream warning to the main thread; cardinality: One receive-message IPC per parsed MCP message; at most one warning for this failed response
    - Introduced by diff: false; previous behavior: The same publication paths existed before the diff.; critical-path effect: Message publication is required for response delivery; warning publication follows failure
- Verdict: No reportable regression. Before the diff cancellation was invoked without awaiting and the original read error was thrown; after the diff the same already-settled rejection is awaited. This handles the promise chain without adding a network boundary or multiplicative work.

### Scenario 2: Dispose or stop an HTTP MCP handle while an SSE response read is pending

- Critical path: Disposal marks the handle's DisposableStore disposed, aborts the shared fetch signal, and cancels the token. The pending read rejects; the changed disposed check returns before reader.cancel(), allowing teardown to complete without the redundant cancellation promise.
- Scaling input: At most one backchannel reader plus the currently in-flight response readers per handle; cost scales with active requests at teardown, not message history.
- Effective concurrency: All active fetches share the handle AbortController and are aborted together. Each read loop independently observes disposal; no new work is scheduled by the diff.
- Cache behavior: No cache participates in stop/disposal.
- Mechanism confidence: High: DisposableStore sets isDisposed before invoking registered abort/cancellation callbacks, so the changed catch branch returns before reader.cancel() for teardown-triggered failures.
- Magnitude uncertainty: The number of active response readers at disposal depends on concurrent requests, but the diff removes rather than adds a per-reader cleanup call on this path.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadMcp.ts:96 and src/vs/workbench/api/common/extHostMcp.ts:135</code>: Request MCP server stop from the main thread; cardinality: One IPC call per server stop
    - Introduced by diff: false; previous behavior: The same stop IPC and close sequence occurred before the diff.; critical-path effect: Initiates close; normal session close may complete before handle disposal
  - network at <code>src/vs/workbench/api/common/extHostMcp.ts:\_closeSession</code>: Optionally send the existing HTTP DELETE session-close request; cardinality: At most one DELETE per HTTP MCP handle with a session ID
    - Introduced by diff: false; previous behavior: The same DELETE was awaited before disposal.; critical-path effect: The stop path awaits this request before disposing the handle
  - network at <code>src/vs/workbench/api/common/extHostMcp.ts:McpHTTPHandle constructor disposal callback</code>: Abort active fetches/readers via the existing AbortController during disposal; cardinality: One shared abort signal per handle, affecting its active requests
    - Introduced by diff: false; previous behavior: The same abort occurred, followed by an unnecessary reader.cancel() call whose rejected promise was discarded.; critical-path effect: Unblocks pending stream reads during teardown
- Verdict: No regression. The diff reduces redundant cleanup work and prevents a discarded rejected promise during disposal; it adds no retained resource or blocking boundary.

### Scenario 3: Maintain the streamable-HTTP GET backchannel across an active stream read failure

- Critical path: The handle performs the existing GET, reads SSE notifications, reports the read failure, and re-enters the existing retry loop after its delay. The changed await occurs after the response stream is already errored and before the retry loop resumes.
- Scaling input: One backchannel per HTTP MCP handle. Failures scale with reconnect attempts across active handles, with the existing retry delay capped at 30 seconds.
- Effective concurrency: Each handle has one sequential backchannel loop; multiple MCP handles may reconnect independently. The diff neither adds parallelism nor removes backoff.
- Cache behavior: No response cache is used. Session ID and Last-Event-ID are per-handle state and unchanged.
- Mechanism confidence: High: the stream is already errored when this catch executes, and the existing per-handle loop preserves its retry delay and single-stream concurrency.
- Magnitude uncertainty: Backchannel failure frequency and number of simultaneously configured servers vary, but cancellation remains constant-time promise observation per failed stream.
- Expensive boundaries:
  - network at <code>src/vs/workbench/api/common/extHostMcp.ts:\_attachStreamableBackchannel</code>: GET and consume the MCP asynchronous-notification SSE backchannel; cardinality: One active GET per handle, repeated after failures according to the existing retry loop
    - Introduced by diff: false; previous behavior: The same GET, read loop, and reconnect schedule existed before the diff.; critical-path effect: Required for asynchronous notifications but off the outgoing message critical path
  - IPC at <code>src/vs/workbench/api/common/extHostMcp.ts:\_attachStreamableBackchannel</code>: Publish each backchannel MCP notification to the main thread; cardinality: One IPC call per parsed message event
    - Introduced by diff: false; previous behavior: The same event publication occurred before the diff.; critical-path effect: Required for delivering asynchronous notifications
- Verdict: No reportable regression. Awaiting the already-rejected cancellation promise does not add network cancellation, increase retry frequency, or fan out work.

**Summary:** Reviewed the complete two-file diff and traced active response failures, handle disposal, and backchannel reconnects. The production change only changes error-promise handling after a stream read failure and removes redundant cancellation during disposal; no actionable performance regression or qualifying performance-regression fix was found.
