# Performance review: chat: Add draft handoff and parallel-work invitation for Agents

[PR #336954](https://github.com/microsoft/vscode/pull/336954) at `4177136ed14c3a8adacfbf48c214bdfc5c6e53cd`

## Findings (2)

### 1. [medium] Bound draft serialization before opening the Agents Window

**Finding ID:** `PERF-02418BED597E`  
**Location:** <code>src/vs/workbench/contrib/chat/common/attachments/chatDraft.ts:68</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** UI-thread CPU plus transient strings and bytes created while snapshotting models, base64-encoding images, and JSON-serializing the complete attachment collection  
**Scaling:** Cost grows linearly with total attachment payload bytes; untitled models are copied in full with no size bound, and image entries are synchronously base64-encoded (4/3 expansion) before the entire collection is stringified.  
**Outcome:** The Open Agents action can block the source renderer and delay window creation while producing large transient allocations and GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Opening the Agents Window forwarded only workspace/session URI metadata, so it could call the native window service without reading full text models or encoding attachment payloads.  
**Changed behavior:** The new handoff maps every attachment, snapshots complete untitled models via getValue(), exports binary entries to base64, and synchronously stringifies the resulting collection before the caller can invoke nativeHostService.openAgentsWindow.  
**Confidence:** 0.98 — The synchronous call path, full-model reads, base64 conversion, JSON allocation, and placement before the native open call are explicit. Exact pause duration varies with attachment sizes and hardware, which limits severity rather than confidence.

**Causal diff evidence:** The added line 68 creates a single JSON string for the entire newly captured attachment set; this serialization did not exist on any Agents Window open path before the PR.

A realistic draft containing a large unsaved log or several accepted image attachments makes the Open Agents click synchronously copy and encode tens of megabytes before the window begins opening, causing a visible pause and potentially a large memory spike.

**Evidence:** serializeChatDraft synchronously calls model.getValue()/getValueInRange for untitled resources, IChatRequestVariableEntry.toExport for each remaining attachment, and stringify for the full array at line 68. toExport base64-encodes Uint8Array values synchronously. captureDraftHandoffOptions calls this directly on the command path before openAgentsWindow; image attachment loading accepts files up to 30 MB, and untitled snapshots have no bound.

**Suggested direction:** Keep large bytes in a buffer-aware IPC representation and transfer the draft after window opening has begun, rather than base64/stringifying it on the source UI thread. Also enforce a total handoff payload bound (surfacing the existing retained-source warning when exceeded) so untitled documents and multiple images cannot create an unbounded synchronous snapshot.

### 2. [medium] Cache running-session state instead of rescanning on every context change

**Finding ID:** `PERF-3919C7DDC7D7`  
**Location:** <code>src/vs/workbench/contrib/chat/electron-browser/agentSessions/agentSessionsActions.ts:718</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** UI-thread full-catalog array allocations, URI deduplication passes, session predicate checks, and resulting garbage  
**Scaling:** Each global context-key event costs O(N) in the complete active-and-archived session catalog; focus/add events can perform the same scan twice through \_onSessionChanged followed by \_update, and cost grows with retained session history.  
**Outcome:** Routine context/focus churn increasingly consumes CPU and creates GC pressure for users with large session histories, risking workbench interaction jank even when the banner owner has not changed.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** There was no parallel-work contribution listening to every context-key change, and Agents Window invitation state did not require materializing and deduplicating the full session catalog on those events.  
**Changed behavior:** The added unfiltered global context listener calls \_update; \_updateOwner calls hasRunningAgentHostSession, whose model.sessions access allocates Array.from(\_sessions.values()) and runs the migrated-session dedupe pass before .some can test status. \_onSessionChanged also calls the same helper and then \_update, duplicating the catalog pass for a new focus/session.  
**Confidence:** 0.97 — The event subscription, synchronous call graph, unconditional catalog getter, and getter allocation/deduplication are directly visible. Only the exact user-visible duration depends on catalog size and local event frequency.

**Causal diff evidence:** The PR adds the line-718 global listener and the new \_update path that performs the full session-catalog read for each event; this repeated work was absent before the new contribution.

With hundreds or thousands of accumulated active and archived sessions, unrelated context-key updates and ordinary chat focus transitions repeatedly traverse and allocate the entire catalog although the running-session boolean changes only on session-model events.

**Evidence:** Line 718 subscribes to all context-key changes. The added hasRunningAgentHostSession helper at line 83 reads service.model.sessions; AgentSessionsModel.sessions constructs a new array and dedupes all entries on every read. \_updateOwner invokes it unconditionally whenever the feature is enabled, and \_onSessionChanged invokes it once more before calling \_update.

**Suggested direction:** Compute and cache hasRunningAgentHostSession when onDidChangeSessions fires, then let context/widget updates read that O(1) value. Filter context-key notifications to the keys used by the precondition, and reuse the cached result inside \_onSessionChanged/\_update to avoid the duplicate scan.
