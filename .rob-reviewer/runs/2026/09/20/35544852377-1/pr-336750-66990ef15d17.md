- Scaling input: One active draft and one selected workspace, with an optional single detached worktree. Progress cardinality is phase-count, not CLI-output-line count; tests cover multiple phase updates retaining one temporary chat view.
- Effective concurrency: Preparation uses one token per submitted draft. Cold connections are coalesced per normalized workspace by \_pendingConnections; retries reuse availability state and active connections where valid. The optional worktree operations remain serial. Progress has only a constant number of phase transitions.

- Mechanism confidence: High: changed UI state and all transitive preparation boundaries were traced, and tests explicitly show one preparation view across multiple progress values plus disposal on cancellation.

### Scenario 2: Start a new session while an existing Dev Container Agent Host is automatically reconnecting

- Critical path: The new connect call now waits for the existing remote-host connection to leave connecting/reconnecting state before acquiring it; on success, normal replacement-session setup and send proceed. No new container process is started for this warm path.
- Scaling input: Number of simultaneous draft submissions targeting the same reconnecting workspace, realistically small because the visible composer owns one draft; each listener performs a linear lookup across registered remote connections.
- Effective concurrency: The transport owns a single reconnect. Joiners wait independently on the same connection-status event stream; they do not initiate parallel container starts.
- Cache behavior: The warm \_activeConnections entry prevents cold connection creation. If status becomes disconnected, the wait fails rather than populating a negative cache; later explicit retry follows the existing connection path.
- Mechanism confidence: High: the branch, event predicate, active-connection reuse, and tests for connected/canceled/disconnected outcomes are explicit.
- Magnitude uncertainty: Reconnect duration can be long, but it already gates useful remote work. The added local event/list scan cost is small and bounded by active connections and joiners.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/devContainerAgentHostService.ts:251 \_waitForReconnection</code>: Observe remote Agent Host connection status until the existing reconnect completes.; cardinality: One listener per joining request, while the underlying reconnect remains one per active workspace; each status event scans the typically small connection list for the matching address.
    - Introduced by diff: true; previous behavior: connect returned the cached active target immediately even while its underlying connection was reconnecting; downstream remote work still depended on that host becoming usable.; critical-path effect: The reconnect completion is intentionally placed on the new-session critical path so setup does not use a reconnecting host.
  - subprocess at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/devContainerAgentHostService.ts:228-233 \_ensureConnection</code>: Reuse the existing Dev Container transport rather than launch a second CLI connection.; cardinality: Zero new subprocesses on the active reconnecting path; one existing reconnect per workspace.
    - Introduced by diff: false; previous behavior: The same active transport was reused.; critical-path effect: No additional subprocess blocks the join; only connection readiness does.
- Verdict: No reportable regression. The diff serializes the join behind an already-required reconnect without increasing remote-operation cardinality or starting duplicate containers.

- Effective concurrency: UI updates are serialized by observables. The preparation view is created once when progress becomes present and disposed when the boolean clears; phase-message changes do not reconstruct it. Repeated log activations are independent user actions but reuse one channel.

### Scenario 4: Open connection logs for a restored Dev Container provider before its connector is registered

- Critical path: A user-triggered Show Log waits for connector registration (with the existing bounded registration timeout), then reveals a workspace-keyed output channel. Session reconnection itself proceeds independently.
- Scaling input: Explicit user activations and number of restored workspace providers; channel identity is deduplicated per workspace.
- Effective concurrency: No automatic fan-out. Multiple rapid clicks could create multiple timeout-bounded waits, but each requires user action and does not create connections or subprocesses.
- Cache behavior: The registered connector is reused after initialization, and output-channel registration checks the global channel registry before creating a channel.
- Mechanism confidence: High: showLog and \_waitForConnector call paths are direct and contain no connection creation.
- Magnitude uncertainty: Connector registration timing depends on startup, but retained waits are timeout-bounded and not scheduled automatically.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/devContainerAgentHostService.ts:222 showLog / :291 \_waitForConnector</code>: Wait for the renderer-side Dev Container connector registration and invoke its output service.; cardinality: One bounded wait per explicit click before registration; after registration, direct channel reveal. No automatic calls are introduced.
    - Introduced by diff: true; previous behavior: There was no pre-connection log-opening action on restored providers.; critical-path effect: Only the explicit log-opening action waits; reconnect and session startup are not blocked by it.
- Verdict: No reportable regression. The new boundary is user-initiated, bounded, and off session startup’s critical path.
