# Performance review: workbench: add frosted glass overlays with safe fallbacks

## Findings (1)

### 1. [medium] Avoid live blur on long-lived notification overlays

**Finding ID:** `PERF-B4569CA130BF`  
**Location:** <code>src/vs/workbench/contrib/modernUI/browser/media/frostedGlass.css:100</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** offscreen backdrop pixels and GPU blur/compositing passes  
**Scaling:** Cost grows with the filtered pixel area, the rate at which the editor/terminal behind it repaints, and the number of concurrently visible filtered overlays (up to three settled toasts, plus another popup surface).  
**Outcome:** repeated GPU rendering work and potential dropped frames during otherwise smooth editor or terminal updates  
**PR causality:** <code>introduced</code>  
**Previous behavior:** These surfaces used opaque theme backgrounds, so updates behind a notification or popup did not require capturing and blurring the backdrop.  
**Changed behavior:** Supported desktop Sessions windows, and Modern UI editor windows, now keep a live 12px backdrop filter on every selected visible overlay; settled notification surfaces retain that filter for their full visible lifetime.  
**Confidence:** 0.93 — The changed selectors and test coverage directly establish which surfaces receive the live filter, while the existing notification controller bounds but retains up to three settled toasts for 10-15 seconds (or indefinitely when sticky/hovered). Chromium must update a backdrop-filter result when pixels behind that surface change. Exact GPU time varies by driver, overlay area, and backdrop activity, so the severity is medium rather than high.

**Causal diff evidence:** RIGHT line 100 adds \`backdrop-filter: blur(12px)\` to the shared \`::before\` layer selected for quick input, action widgets, hovers, dialogs, the notification center, and settled toasts (selectors at lines 84-91). The new setting defaults to enabled, and the contribution enables it automatically in Sessions windows once GPU compositing is reported.

With the default glass setting in the Sessions window, a sticky notification or up to three ordinary toasts over an active terminal/editor can add repeated GPU filter work on every underlying frame, increasing GPU usage and causing dropped frames or battery drain for the entire toast lifetime.

**Evidence:** \`frostedGlass.css\` applies one live blur layer to the notification center and each settled toast, as well as other overlays. \`NotificationsToasts.MAX\_NOTIFICATIONS\` is 3, normal purge time is 10-15 seconds, and sticky/hovered toasts are retained. These overlays sit over the editor/terminal, so typing, cursor animation, terminal output, or editor animation changes the sampled backdrop and causes repeated offscreen backdrop capture/filter/compositing for each visible surface. The GPU capability check only establishes hardware compositing; it does not eliminate this per-frame blur pass.

**Suggested direction:** Keep long-lived notification center/toast surfaces solid, or gate their blur behind an explicit opt-in rather than the default glass class; retain glass only for short-lived modal popups whose backdrop is effectively static.
