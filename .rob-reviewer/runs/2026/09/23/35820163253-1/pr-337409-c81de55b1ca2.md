# Performance review: Reduce automatic post-edit review for OpenAI Agent Host models

[PR #337409](https://github.com/microsoft/vscode/pull/337409) at `c81de55b1ca2c6bbc1249ace39457388baa14220`

## Findings (1)

### 1. [medium] Move workspace scanning off the first-turn critical path

**Finding ID:** `PERF-13B1B047B494`  
**Location:** <code>src/vs/platform/agentHost/node/chatContributions/workspaceContext/workspaceContextContribution.ts:64</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** ripgrep subprocesses, filesystem traversal, and up to 50,000 retained URI objects per root  
**Scaling:** Cold cost grows with the number of independent workspace roots and files visited: one ripgrep scan per root, up to four concurrently, with each scan collecting up to 50,000 paths. The caller waits for all roots or the 2000 ms timeout; queued/running scans survive cancellation.  
**Outcome:** blocked first-turn critical path, with continued I/O after timeout  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, outgoing-turn contributions did not enumerate workspace files, so provider dispatch incurred zero ripgrep/file-tree work on this path.  
**Changed behavior:** Every first outgoing Copilot turn for a chat now synchronously enumerates all independent workspace roots and renders their file tree before provider dispatch.  
**Confidence:** 0.99 — The changed call, dispatcher await, and provider-dispatch ordering are explicit. \`AgentHostWorkspaceFiles\` proves each cold root spawns \`rg --files\`, uses a four-operation global limiter, and races caller cancellation without stopping the underlying work. The added test proves a slow scan delays the send by the full 2000 ms. Only real-world filesystem speed and prevalence of large/multi-root workspaces affect magnitude.

**Causal diff evidence:** Added line 64 awaits \`this.\_workspaceFiles.getFiles(root, cancellation.token)\` inside \`Promise.all\` for every independent workspace root before the contribution returns; the newly registered contribution is then awaited by \`AgentSideEffects\` before \`agent.chats.sendMessage\`.

On the first message of each new or empty Copilot chat, a large, slow, network-mounted, or multi-root workspace can add up to two seconds before the request even reaches the model; timed-out scans continue consuming filesystem and subprocess capacity afterward.

**Evidence:** \`WorkspaceContextContribution.onOutgoingTurn\` awaits \`getFiles\` for all \`enumerationRoots\`. \`AgentHostWorkspaceFiles.\_enumerate\` spawns ripgrep and collects up to 50,000 URIs per root; its cancellation path explicitly leaves shared enumeration running. \`AgentHostChatContributions.outgoingTurn\` awaits contributions serially, and \`AgentSideEffects\` awaits that result before \`agent.chats.sendMessage\`. The contribution owns a new \`AgentHostWorkspaceFiles\`, separate from the existing completion provider's cache, so prior file-completion activity does not make this path warm.

**Suggested direction:** Start the bounded snapshot asynchronously when the session/chat working directories become known and attach it only if ready by first send (or share the existing workspace-files service/cache); do not await a cold full-workspace scan on the send path, and ensure abandoned queued/running scans are canceled when no consumer remains.

### Scenario 1: Send the first message in a Copilot Agent Host chat with one or more local workspace roots.

- Critical path: After working-directory resolution, model selection, and attachments, \`AgentSideEffects\` awaits all outgoing-turn contributions; this contribution awaits every root enumeration before provider dispatch. A slow scan therefore blocks first-token progress for up to 2000 ms. After timeout, the user request proceeds but underlying scans remain active/off the request critical path.
- Scaling input: The effective cardinality is the number of deduplicated, non-nested file roots and up to 50,000 returned paths per root; first-turn frequency is once for every new or restored-empty Copilot chat.
- Effective concurrency: All roots are submitted with \`Promise.all\`; a process-wide limiter permits four ripgrep enumerations concurrently and queues the rest. Contributions themselves execute serially. Cancellation rejects only each caller promise, so running and queued root scans continue under the limiter.
- Cache behavior: \`WorkspaceContextContribution\` owns a separate \`AgentHostWorkspaceFiles\` cache, so existing file-completion enumeration cannot warm it. Within this contributor, in-flight requests coalesce per root and successful results stay warm for 30 seconds; failures are removed. The first-turn memento limits attachment to once per chat, but each new/empty peer chat can consume the cached result or trigger a cold scan after expiry. Caller timeout does not cancel or evict the shared enumeration.
- Mechanism confidence: High: the added await, subprocess implementation, limiter, non-canceling timeout semantics, separate cache ownership, and pre-provider call ordering are directly traced; the new test explicitly asserts a 2000 ms delay for a slow filesystem.
- Magnitude uncertainty: Local small repositories may enumerate quickly, while large, ignored-poor, network-mounted, or multi-root workspaces can reach the tested two-second bound. Workspace-size and filesystem-latency prevalence are unknown, affecting severity but not the mechanism.
- Expensive boundaries:
