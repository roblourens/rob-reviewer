<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** serialization-allocation, synchronous-ui-work, eager-work, repeated-work, boundary-fanout

### Scenario 1: A tracked Copilot SDK tool reaches a normal permission prompt and is projected into the workbench confirmation UI.

- Critical path: The permission callback builds one pending\_confirmation state, synchronously emits it, the host applies approval policy, and—when user input is required—the workbench renders the confirmation before the tool can continue. The new toToolCallMeta call is a shallow copy of the tracked metadata on this path.
- Scaling input: Cost scales with the number of permission prompts, not tool history. For terminal calls the tracked metadata created at tool start is normally two scalar fields (toolKind and language).
- Effective concurrency: Each tool call owns its own pending permission; concurrent tool calls can each prompt, but the diff adds neither a launcher nor aggregate concurrency and the UI carousel presents one active confirmation at a time when enabled.
- Cache behavior: No cache is consulted or invalidated by the change. Metadata is read from the existing active-tool-call record and copied once for the event.
- Mechanism confidence: High confidence in the event path and per-prompt cardinality from the changed emission and active-tool-call construction.
- Magnitude uncertainty: The prevalence of simultaneous permission prompts is unknown, but the added shallow object enumeration is bounded by the small typed metadata schema and occurs once per prompt.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:4212, handlePermissionRequest pending-confirmation emission</code>: Transport one pending\_confirmation protocol signal from the agent host to the workbench/approval side.; cardinality: One signal per permission request that is not auto-approved; no collection fan-out or retry was added.
    - Introduced by diff: false; previous behavior: The same pending\_confirmation signal crossed the boundary; tracked calls omitted \_meta, while untracked shell calls already sent a small terminal metadata object.; critical-path effect: The signal must arrive before the confirmation can render or approval can resume the tool.
- Verdict: No reportable regression: the diff preserves rendering metadata in an existing event without adding an expensive boundary, retry, or unbounded serialization.

### Scenario 2: A custom bash or PowerShell command requests unsandboxed execution and waits for confirmation before process execution.

- Critical path: The shell tool invokes requestUnsandboxedCommandConfirmation, which emits one pending\_confirmation event and waits for the user. Once approved, the existing shell-tool implementation may execute the command; the PR only attaches terminal metadata so the visible card is routed to the terminal renderer.
- Scaling input: Cost scales one-for-one with unsandboxed command requests. The new metadata fallback computes a small tool-kind/language object once per request.
- Effective concurrency: Concurrency remains whatever independent shell tool calls already permit; the PR does not add parallel requests or move subprocess launch before approval.
- Cache behavior: No cache is added or bypassed. Session sandbox policy is read before and after approval exactly as before.
- Mechanism confidence: High confidence: the callback wiring and await on pendingPermission establish ordering, and the changed line only enriches the existing signal.
- Magnitude uncertainty: Command duration and the number of concurrent prompts vary by workload, but neither is changed by this diff.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:4708, \_requestUnsandboxedCommandConfirmation</code>: Send the unsandboxed pending-confirmation state to the host/workbench and return one approval decision.; cardinality: One outbound prompt and one response per unsandboxed command request.
    - Introduced by diff: false; previous behavior: The same prompt/response round-trip blocked execution; the event lacked terminal \_meta.; critical-path effect: Approval round-trip intentionally blocks command execution.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:857, createShellTools confirmation callback</code>: Execute the approved shell command through the existing custom shell tool.; cardinality: At most one command execution for each approved request; denied requests launch none.
    - Introduced by diff: false; previous behavior: Approved commands followed the same execution path and count.; critical-path effect: Execution is after the confirmation and is the command's primary work.
- Verdict: No reportable regression: no new subprocess, IPC round-trip, or critical-path await is introduced.

### Scenario 3: The workbench renders a terminal confirmation with server-provided custom approval options, either inline or in the confirmation carousel, and the user selects one option.

- Critical path: State adaptation maps the protocol options into confirmation messages; constructing the visible terminal card creates the existing pooled code editor and groups the option list into up to two buttons plus dropdown actions. Clicking an option sends one confirmation result. For sandbox-bypass cards, terminal metadata changes routing from the generic input card to the terminal card, but the generic input card also created a pooled code editor for the command payload.
- Scaling input: Button construction is O(number of confirmation options), with the realistic changed scenario containing three options. Visible editor work is one card per active confirmation; carousel mode retains pending items but mounts the active content.
- Effective concurrency: Inline mode can display existing concurrent prompts; carousel mode serializes visibility to one active item. The PR does not increase the number of prompts or editors generated by a request.
- Cache behavior: The editor pool is reused as before. No new cache keys or negative-cache behavior are introduced; button arrays are rebuilt only at card creation or existing auto-approve-action updates.
- Mechanism confidence: High confidence in the O(n) grouping, pooled editor lifecycle, and single confirmation response from the changed constructor and click handler.
- Magnitude uncertainty: The protocol does not state a hard option-count cap, but repository producers/tests use small human-facing lists and there is no realistic evidence of a large collection.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatTerminalToolConfirmationSubPart.ts:505, IChatToolInvocation.confirmWith</code>: Return the selected confirmation option identifier and kind to the agent-host session.; cardinality: Exactly one response for the selected action; dropdown construction does not issue boundary calls.
    - Introduced by diff: false; previous behavior: Generic custom-option confirmations already returned one selected option. This diff enables the same single response from the terminal-specific renderer.; critical-path effect: The response resumes or rejects the pending tool call after user interaction.
- Verdict: No reportable regression: the extracted grouping logic matches the previous generic implementation, realistic lists are small, and the terminal renderer replaces comparable visible editor work rather than adding repeated hidden work.

**Summary:** Completed the performance pass over all six changed files and traced metadata serialization, confirmation rendering, option grouping, approval transport, and shell execution. The diff adds bounded per-prompt metadata/button work, no new expensive boundary calls, no fan-out or concurrency burst, and no cache or cleanup lifecycle regression. No findings were submitted.
