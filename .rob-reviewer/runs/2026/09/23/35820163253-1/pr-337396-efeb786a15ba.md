### Scenario 1: Windows Agent Host integration-test graceful shutdown, including suite teardown and harness restarts

- Critical path: Capture descendants, send EOF, wait for the Agent Host server to exit, then verify and terminate any still-matching descendants before teardown/restart can finish. All added identity probes are on this teardown critical path.
- Scaling input: The captured Agent Host descendant tree after deduplication by PID; each reachable process with a readable command line contributes one identity probe and at most one taskkill, with a second probe only when taskkill fails.
- Effective concurrency: The initial descendant snapshot and server shutdown are sequential. After server exit, Promises.settled over descendants launches identity probes concurrently across all captured descendants; successful matches then launch the pre-existing per-descendant taskkill operations, also concurrently. There is no explicit limiter, but cardinality is bounded by one test server's process tree rather than suite size.
- Cache behavior: The first call cold-loads &#64;vscode/windows-process-tree; subsequent calls use Node's module cache. Process identity observations are intentionally not cached because exit and PID reuse make them time-sensitive. There is no cross-server coalescing, and each server teardown has an independent descendant set.
- Mechanism confidence: High confidence in the added per-descendant native probes and their unbounded-within-tree concurrent scheduling; high confidence that this path is test-only and bounded to one server tree. That bounded scope prevents treating the extra probes as a concrete reportable regression.
- Magnitude uncertainty: Exact descendant counts and native enumeration duration vary by provider and Windows host. The tree is test-server-scoped and teardown-only, and repository harness cleanup disposes terminals while shared-server recycling bounds accumulated provider processes, so evidence does not support a severe or user-facing burst.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/platform/agentHost/test/node/serverIntegrationTestHelpers.ts:getServerDescendants (lines 704-711)</code>: Native Windows process-tree enumeration with command-line capture for the server subtree; cardinality: One enumeration per live server teardown on Windows; it returns the server-rooted process list, then local traversal deduplicates PIDs.

  - other expensive boundary at <code>src/vs/platform/agentHost/test/node/serverIntegrationTestHelpers.ts:isSameWindowsProcessRunning and stopServer (lines 713-721, 788-799)</code>: Native Windows process-tree enumeration with command-line capture to compare PID, name, and command line; cardinality: One concurrent probe per captured readable descendant, plus one additional probe only for descendants whose taskkill fails.

The PR adds boundary work, but it is on test cleanup rather than product interaction, is bounded by one server's descendants, and directly prevents taskkill from targeting reused PIDs. The diff also skips taskkill for already-exited/reused descendants, partially offsetting the added probes.

### Scenario 2: Stale-parent-PID branch pruning during Windows descendant capture

- Critical path: The native process list must be captured, indexed, and traversed before graceful shutdown can begin; local collection work is therefore on teardown's critical path.
- Scaling input: Number of IProcessInfo records returned for the requested server root, with each record indexed once and each reachable readable descendant visited once.
- Effective concurrency: Single synchronous O(P + D) local pass after the one asynchronous native snapshot; no additional tasks or boundary fan-out are created by collection.
- Cache behavior: No cache is appropriate because process parentage and identities are point-in-time data. The Map and Set are per-teardown temporary allocations and are released after collection/cleanup.
- Mechanism confidence: High confidence from the changed Map/Set traversal and single call site.
- Magnitude uncertainty: Returned process-list size depends on the native module and stale Toolhelp metadata, but local work remains linear and the new pruning can reduce downstream cleanup of unrelated branches.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/platform/agentHost/test/node/serverIntegrationTestHelpers.ts:getServerDescendants (lines 704-711)</code>: Obtain the native process list consumed by collectServerDescendants; cardinality: One native call per Windows server teardown, unchanged from the base behavior.
    - Introduced by diff: false; previous behavior: One getProcessList call followed by filter/map; the diff still performs one call and adds linear indexing/traversal.; critical-path effect: Blocks EOF so descendants can be captured while the server PID still exists.
- Verdict: No finding. The replacement remains linear, uses temporary bounded structures, prevents recursion cycles, and prunes unreadable branches rather than increasing downstream work.

### Scenario 3: Focused Agent Host cleanup unit tests on all platforms

- Critical path: Each of three new failure-path tests starts a short-lived Node child, waits for readiness, invokes stopServer with injected process operations, and awaits cleanup before that test finishes.
- Scaling input: Exactly three newly added test cases, each with one Node child and one synthetic descendant; work is constant and does not scale with repository or user input.
- Effective concurrency: The test runner executes these suite cases serially under the normal suite contract. Within each case there is one child process; injected identity and kill operations are sequential for the single synthetic descendant.
- Cache behavior: No reusable result or negative cache is relevant. Node executable/module startup benefits only from operating-system caches; every test intentionally owns an independent child lifecycle.
- Mechanism confidence: High confidence in the constant subprocess count from the three direct helper invocations.
- Magnitude uncertainty: Exact Node startup cost varies by runner, but the count is fixed at three and isolated to a focused test suite.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/test/node/serverIntegrationTestHelpers.test.ts:runDescendantKillFailureTest (lines 20-58)</code>: Spawn and gracefully stop a Node child used to exercise descendant-kill failure races; cardinality: One child launch in each of three new tests, for three launches per execution of this focused test suite.
    - Introduced by diff: true; previous behavior: These three tests and subprocess launches did not exist.; critical-path effect: Child readiness and shutdown are awaited, so launches add constant test-suite latency.
- Verdict: No finding. The added subprocess cost is small, fixed, test-only coverage of real ChildProcess shutdown behavior, and does not create scaling or retained-resource risk.
