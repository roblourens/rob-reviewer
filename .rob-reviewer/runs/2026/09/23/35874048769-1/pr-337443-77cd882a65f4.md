### Scenario 2: User confirms migration of selected MCP server configurations

- Critical path: The editor delegates once to the harness migration provider. The provider waits for an existing support snapshot, replans, groups candidates by source/target configuration files, and executes sequential guarded filesystem transactions. After the provider resolves, the diff maps failures to enum reasons and sends the existing one completion telemetry event before refresh and notifications.
- Scaling input: Selected MCP candidates, with effective filesystem cardinality determined by distinct source/target groups and roots. Added mapping scans result.failures once; telemetry uniqueness is bounded by the finite failure-reason enum.
- Effective concurrency: The editor-level customizationMigrationInProgress guard serializes this workflow with other migration actions. MCP source/target groups are executed sequentially; the diff adds only a synchronous map and deduplication, with no burst or new concurrency.
- Cache behavior: The provider uses a support snapshot and groups shared configuration files; plan reads are coalesced per source URI within a plan. No cache key, miss behavior, or invalidation policy changes. Telemetry client cold/warm behavior is unchanged.
- Mechanism confidence: High: the only caller, provider implementation, grouped migration engine, serialization, and Electron/browser telemetry paths were inspected.
- Magnitude uncertainty: A very large server inventory could enlarge the temporary mapped array, but realistic effective migration work is grouped by workspace configuration files, and existing provider/editor processing already retains and scans the same failures. The incremental enum-reference array and bounded Set are not a credible user-visible cost.
