### Scenario 1: Sessions sidebar temporarily lays out at zero height and later regains height

- Critical path: SessionsList.layout synchronously updates the virtualized tree; disposal of the normal or sticky header template reparents the single shared header into the stable header container and invokes updateHeaderLayout before layout returns. Relayout later renders that same node back into the tree.
- Scaling input: Number of zero-height/restore relayout transitions, not the number of sessions; effective header cardinality is one.
- Effective concurrency: All tree disposal, DOM reparenting, focus restoration, and layout callbacks run serially on the renderer/UI thread; no queue, limiter, or parallel work is involved.
- Cache behavior: No data cache participates. The virtualized row/template cache can retain header templates, but the shared header DOM node is now parked in its stable owner rather than retained in a detached template.
- Mechanism confidence: High confidence in the synchronous DOM handoff and callback path; repository code directly shows the callback's style writes and geometry reads.
- Magnitude uncertainty: Browser style/layout cost varies with sidebar complexity, but the changed work is bounded to one header node and a small fixed set of geometry/style operations per actual handoff.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:522-527 via src/vs/sessions/contrib/sessions/browser/views/sessionsView.ts:updateHeaderLayout</code>: DOM reparenting plus updateHeaderLayout; the desktop path writes display styles and may synchronously read clientWidth for the header row and label.; cardinality: One shared header handoff per header-template disposal; cardinality is constant with respect to session count and the zero-height transition disposes at most the normal/sticky header instances.
    - Introduced by diff: true; previous behavior: The header was detached (or returned from sticky to the connected source row) during disposal and no layout callback ran from disposal; rendering still invoked the existing layout callback.; critical-path effect: Runs synchronously inside list layout and must complete before the zero-height or restored layout returns.
- Verdict: No reportable regression. The diff adds bounded synchronous work to preserve the shared header across a rare relayout transition, with no collection-scaled allocation or boundary fan-out.

### Scenario 2: Scrolling the navigation treatment so the Sessions header becomes sticky or returns to its source row

- Critical path: A scroll event updates sticky-scroll state. When the state materially changes, the sticky widget disposes its prior template, the changed renderer reparents the shared header and runs the layout callback, and a new sticky template may render and run the existing callback again before the state update completes.
- Scaling input: Material sticky-state transitions while scrolling, after state-equality suppression; one header regardless of session collection size.
- Effective concurrency: Scroll handling, sticky-state comparison, renderer disposal/rendering, DOM focus operations, and geometry reads are serialized on the UI thread. Unchanged sticky states are coalesced by StickyScrollState.equal; only changed states rerender.
- Cache behavior: Sticky state equality suppresses rebuilding for unchanged states. The row/template cache does not duplicate the shared header, and no warm/cold data cache changes.
- Mechanism confidence: High confidence in the added disposal-side callback and sticky lifecycle. User-visible frame impact is not strongly evidenced because state equality bounds frequency and only one header is processed.
- Magnitude uncertainty: The number of sticky-state transitions depends on scrolling and section structure; the per-transition incremental cost is a fixed header layout and is not session-cardinality-scaled.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:510-527 and src/vs/base/browser/ui/tree/abstractTree.ts:StickyScrollWidget.renderState</code>: Reparent the header, optionally restore focus, and update responsive header visibility using DOM style writes/clientWidth reads.; cardinality: At most one extra layout callback for the single shared Sessions header per sticky-template disposal. Equal sticky states avoid rerendering; work does not run once per session row or once per unchanged scroll event.
    - Introduced by diff: true; previous behavior: Sticky disposal could return the header to its connected source and restore focus, while the subsequent render performed the sole header layout callback. The diff adds a disposal-side callback to cover parking in the stable container.; critical-path effect: Synchronous on sticky-state transitions and therefore on those scroll updates, but fixed-size and limited to one header.
- Verdict: No finding. Although the change can add one synchronous responsive-header layout on a sticky handoff, it is bounded, coalesced for unchanged scroll states, and insufficiently evidenced as a concrete user-visible regression.

### Scenario 3: Typing in Find while the header moves between normal, sticky, and parked containers

- Critical path: Find input events filter the tree; if filtering causes header template replacement, disposal captures the focused descendant, reparents the shared header, restores focus, and runs the layout callback before the filtered tree render completes.
- Scaling input: Find keystrokes that materially replace the header template, after tree filtering/template reuse; effective DOM cardinality is one header and one focused input.
- Effective concurrency: Input filtering and header lifecycle work are serialized on the UI thread. There is no external concurrency; the shared header ensures only one focused input node exists.
- Cache behavior: No network/data cache is involved. Tree filtering and template reuse are unchanged; only ownership of the one header DOM node changes.
- Mechanism confidence: High confidence in the input-to-filter and header lifecycle path; low evidence of meaningful performance degradation because work is constant and primarily replaces detach/reattach operations needed for focus preservation.
- Magnitude uncertainty: Filter frequency follows keystrokes, but a handoff is required for the changed work and the Find-open callback avoids geometry reads, limiting cost.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:510-527</code>: DOM focus restoration with preventScroll, header reparenting, and responsive-header style updates.; cardinality: One shared header/input per template handoff caused by a filter update; not per matching session. When Find is open, updateHeaderLayout takes the early style-only branch and does not read clientWidth.
    - Introduced by diff: true; previous behavior: Focus was captured only in disposeElement and the header could be detached by disposeTemplate. The diff also captures focus during template disposal and parks the node instead of detaching it.; critical-path effect: Runs before the filter render completes so focus remains usable; work is fixed-size for each actual handoff.
- Verdict: No reportable performance issue. The focus-preservation work is constant per actual handoff and does not fan out with session results.

### Scenario 4: Constructing the Sessions list with or without an externally owned header

- Critical path: SessionsList construction performs a constant-time option consistency check and creates either an empty renderer list or one SessionsHeaderRenderer before constructing the tree.

- Effective concurrency: Synchronous single-threaded constructor work; no scheduling or parallelism.
- Cache behavior: No cache behavior changes.
- Mechanism confidence: High confidence from the constructor diff.
- Magnitude uncertainty: None material; the added check and zero/one-element array are fixed-size.
- Expensive boundaries: none found
- Verdict: No performance regression. The additional startup work is constant and negligible, and the fixture-only option normalization does not affect product runtime.
