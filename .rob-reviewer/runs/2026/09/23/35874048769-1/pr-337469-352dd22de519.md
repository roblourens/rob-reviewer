### 1. [medium] Cache clipping geometry off the scroll path

**Finding ID:** `PERF-28566A44C844`  
**Location:** <code>src/vs/sessions/browser/parts/chatCompositeBar.ts:204</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** browser style resolution and layout work from class/style mutations, three getBoundingClientRect calls, clientWidth, and two getComputedStyle calls  
**Scaling:** The forced style/layout work repeats for every horizontal scroll event and can run twice per movement through the native-scroll and ScrollableElement callbacks; active-tab lookup also grows with the number of chat tabs.  
**Outcome:** increased scrolling latency and dropped frames while horizontally scrolling an overflowing chat tab strip  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The native scroll listener only synchronized scrollLeft into ScrollableElement, and the ScrollableElement listener only copied its position back to the DOM; neither path measured tab geometry or resolved styles.  
**Changed behavior:** Both scroll synchronization handlers now call \_updateConnectedTabClipping, which clears clipping classes/styles, finds the active tab, then immediately reads three DOM rectangles, clientWidth, and two computed styles before writing clipping state.  
**Confidence:** 0.99 — The changed event handlers, synchronous Scrollable event propagation, write-before-read ordering, exact geometry/style operations, and overflow trigger are all directly traced in repository code. Exact frame cost varies by machine and DOM size, but the repeated synchronous-layout mechanism is certain.

**Causal diff evidence:** RIGHT line 204 newly invokes \_updateConnectedTabClipping from the native scroll event; the same diff also invokes it from ScrollableElement.onScroll and adds the synchronous geometry/style reads in that routine.

With enough chats to overflow the strip, wheel, trackpad, or drag scrolling places synchronous layout/style work on every movement. setScrollPositionNow fires ScrollableElement.onScroll synchronously when the position changes, so a native scroll can execute the routine once from that callback and again when the native handler resumes, making visible tab scrolling prone to jank.

**Evidence:** The added call at line 204 is inside the native SCROLL listener. That listener first calls ScrollableElement.setScrollPosition; Scrollable.setScrollPositionNow synchronously calls \_setState, which fires onScroll when scrollLeft changes, reaching the second added call at line 211. \_updateConnectedTabClipping starts by mutating classes/styles via clearConnectedTabClipping, then reads \_tabsContainer, active fill, and scrollbar getBoundingClientRect(), clientWidth, and two getComputedStyle values. The existing editor-tab implementation avoids this by computing IConnectedTabBounds during layout and having its scroll callback perform only updateConnectedTabClipping arithmetic/class toggles.

**Suggested direction:** Compute and cache IConnectedTabBounds and the radii when tabs are rebuilt, the active tab changes, or the ResizeObserver fires, as MultiEditorTabsControl does. On scroll, update clipping from the cached bounds and current scrollLeft through one synchronization path (or coalesce to one animation-frame update).

### 2. [medium] Cache connected-label metrics across resize layouts

**Finding ID:** `PERF-5F5C17513923`  
**Location:** <code>src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:2069</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** main-thread computed-style queries, canvas text measurement/cache lookups, DOM queries, CSS custom-property writes, and offsetWidth layout reads for every tab  
**Scaling:** Cost is O(open side-panel editor tabs) on each animation-frame layout while the Agents window or its Details/editor split is resized; Browser tabs use unique IDs, so this collection can realistically grow beyond the built-in Changes/Search/Files tabs.  
**Outcome:** increased resize latency and dropped frames when resizing an Agents window or dragging its editor/detail sash with many open tabs  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Agents windows did not satisfy the old \`.modern-ui.modern-ui-connected-editor-tabs\` condition and had a read-only pill-style override, so layoutConnectedTabLabels(false) skipped per-tab computed styles, text metrics, decoration metrics, and offsetWidth reads.  
**Changed behavior:** The broadened \`.modern-ui-tabs.modern-ui-connected-editor-tabs\` condition makes connected true for the Agents side-panel tab bar by default. Every scheduled doLayout then runs layoutConnectedTabLabels(true), which recomputes each tab's intrinsic minimum metrics before reading every tab's offsetWidth.  
**Confidence:** 0.96 — The newly activated condition, default Agents configuration, resize-to-layout call path, per-tab operations, and unbounded Browser-tab cardinality are directly established in code. Exact frame impact depends on tab count and platform style/layout cost, so severity is medium rather than high.

**Causal diff evidence:** RIGHT line 2069 replaces the Modern-UI-only ancestor check with the Agents-compatible modern-ui-tabs check; together with the diff's removal of the Agents pill override and new connected-style contribution, this newly activates the expensive connected-label branch for every Agents side-panel layout.

During continuous resize, the control schedules one layout per animation frame and repeats up to several getComputedStyle calls per tab plus width reads on the UI thread. With many file/browser/search editors open in the Agents side panel, this consumes the frame budget and makes sash or window resizing visibly stutter.

**Evidence:** SinglePaneMainEditorPart sets useModernUITabs and supplies an Add Tab menu; NewBrowserTabAction creates a fresh UUID-backed editor each time. EditorGroupView.layout calls titleControl.layout for every group resize, and MultiEditorTabsControl schedules doLayout on the next frame. The changed condition at line 2069 now enters layoutConnectedTabLabels(true), whose per-tab body queries label nodes, reads getComputedStyle for the tab/name/ellipsis/suffix/badge, writes minimum-width properties, then reads offsetWidth for every measured tab. The text-width LRU does not avoid the computed-style reads or offsetWidth pass.

**Suggested direction:** Cache each tab's intrinsic minimum width and font/decorative metrics, invalidating only when that tab's label, decorations, theme/font, or relevant editor options change. Width-only resize layouts should reuse those minima and perform only the current-width/narrow-state work needed for the new viewport.

### Scenario 1: Horizontally scroll an overflowing connected chat-tab strip in the Agents window

- Critical path: Each native or ScrollableElement scroll update synchronously reaches clipping-state calculation before the next paint; the geometry/style reads are therefore on the interaction critical path.
- Scaling input: Scroll-event frequency and the number of chat tabs. A realistic overflow fixture uses 5-6 long-titled chats; active-tab lookup scans the effective tab collection once per clipping update.
- Effective concurrency: All work is serialized on the renderer main thread. A native scroll updates ScrollableElement synchronously, so its onScroll callback can run before the native listener resumes, producing two clipping updates for one movement rather than coalescing at animation-frame granularity.
- Cache behavior: No clipping geometry or computed radii are cached. The active tab, three rectangles, client width, and two computed-style values are recomputed on each call; cold and warm paths are equivalent.
- Mechanism confidence: Very high: synchronous event propagation, duplicate reachability, write-before-read ordering, and all DOM operations are directly visible in code.
- Magnitude uncertainty: Exact layout duration depends on platform, theme, tab DOM size, and browser state, but trackpad/wheel events are frequent and overflow with several chats is explicitly supported.
- Expensive boundaries:
  - other at <code>src/vs/sessions/browser/parts/chatCompositeBar.ts:\_updateConnectedTabClipping and scroll listeners</code>: Synchronous browser style resolution and layout through class/style writes followed by getBoundingClientRect, clientWidth, and getComputedStyle; cardinality: Up to two full clipping measurements per scroll movement, each with three rectangle reads, one clientWidth read, two computed-style reads, and an O(chat tabs) active-tab scan
