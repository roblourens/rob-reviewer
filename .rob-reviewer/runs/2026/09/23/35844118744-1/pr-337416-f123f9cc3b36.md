<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** eager-work, serialization-allocation, boundary-fanout

### Scenario 1: Launch or resume an Agent Host coding session using a GPT-6-family model with the default tool-search setting and the client toolSearch tool available

- Critical path: Launch configuration filters the tool snapshot, evaluates the changed GPT-6 model predicate, constructs SDK tools with defer metadata, then creates/resumes the SDK session and sends the first model request. The predicate and tool-array mapping are synchronous local work; the model request is the expensive critical-path boundary.
- Scaling input: The number and schema size of registered client/MCP tools. Tool search replaces eager inclusion of non-core tool definitions with defer metadata; the changed model check itself is O(model-id length).
- Effective concurrency: One launch/resume configuration is built per session operation. Tool construction is synchronous and no new parallel fan-out or limiter is introduced.
- Cache behavior: No new application cache or retained key set is introduced. Provider prompt caching may benefit from a smaller/stabler request, but that is outside the changed code and not required for the verdict.
- Mechanism confidence: High: the changed predicate reaches toolSearchActive, createClientSdkTools, and the SDK toolSearch option directly, and repository tests/documentation establish deferThreshold=1 behavior.
- Magnitude uncertainty: Exact token and latency savings depend on each user's installed MCP/client tool set and provider behavior; this affects benefit magnitude, not the traced mechanism.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:\_buildSessionConfig / returned SDK session options</code>: Create/resume the SDK session and send the model request containing the active and deferred tool projection; cardinality: One session create/resume request, followed by the normal per-turn model requests; tool schemas scale with the registered tool set but are deferred rather than eagerly exposed for GPT-6 after the change.
    - Introduced by diff: false; previous behavior: GPT-6 failed the support predicate, so the same existing model request eagerly exposed non-core client/MCP tool definitions instead of marking them for on-demand discovery.; critical-path effect: The initial model request must complete before the session can respond. The diff changes its tool projection for GPT-6 but does not add another launch-time boundary call.
- Verdict: No reportable regression. The diff extends an existing payload-bounding mechanism to GPT-6 and adds no launch-time boundary fan-out, unbounded retention, or repeated work.

### Scenario 2: A GPT-6 coding turn needs a deferred MCP or non-core VS Code tool

- Critical path: The model first invokes tool\_search\_tool; Agent Host forwards one ready action with the deferred candidate corpus to the workbench, the workbench invokes the existing toolSearch client tool, returns its result, and the model then selects/invokes the desired tool. These steps are serialized and lie on the turn critical path only when the model chooses tool search.
- Scaling input: Effective candidate cardinality is the set of tools marked deferLoading after SDK grouping/filtering. Candidate metadata is copied once per model-selected search invocation, not once per candidate boundary call.
- Effective concurrency: Search and selected-tool execution are sequential for the demonstrated workflow. There is no changed Promise.all, burst, queue, or per-candidate IPC fan-out.
- Cache behavior: There is no code-level result cache or coalescing on this path; repeated searches are model-selected invocations. Warm sessions reuse the established session but do not cache search results in the reviewed code.
- Mechanism confidence: High: the runtime implementation and end-to-end test establish exactly one search client-tool call followed by the selected tool, with candidate metadata grouped into that call.
- Magnitude uncertainty: How often GPT-6 selects deferred tools, the installed tool count, provider round-trip latency, and net latency versus reduced prompt processing are workload-dependent.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_createClientSdkTools and src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:\_executeClientTool</code>: Forward the tool-search call and candidate metadata from Agent Host to the workbench, then return the tool result; cardinality: One IPC-style client-tool interaction per tool\_search\_tool invocation, carrying one grouped candidate list; not one call per candidate.
    - Introduced by diff: true; previous behavior: For GPT-6 specifically, tool search was inactive, so the model received all tool schemas up front and could invoke the desired tool directly without this discovery interaction.; critical-path effect: Blocks discovery of the selected deferred tool for that turn.
  - network at <code>Copilot SDK/provider turn continuation reached from the Agent Host session</code>: Continue the model turn after the tool-search result so the model can invoke a discovered tool; cardinality: One additional serialized continuation per model-selected search invocation; no candidate-level fan-out.
    - Introduced by diff: true; previous behavior: GPT-6 turns had no tool-search continuation because schemas were eagerly available in the model request.; critical-path effect: Adds an on-demand round trip before a deferred tool can execute, while avoiding eager transfer/processing of every deferred schema on the initial request.
- Verdict: No actionable performance bug. The extra serialized discovery boundary is the intentional on-demand side of deferred loading, is bounded per model-selected search invocation rather than per candidate, and is offset by removing eager schema payload from every request. No evidence shows an accidental repeat, fan-out, concurrency burst, or cache/lifecycle defect.

### Scenario 3: Run or record the Claude Opus 5.5 prompt E2E matrix

- Critical path: The test harness substitutes Opus 5.5 for Opus 4.8 in a fixed model list, constructs one prompt snapshot for that model, and uses the existing capture/provider request path. This is test-only and off the product runtime path.
- Scaling input: Fixed snapshot-model matrix cardinality; the PR replaces one entry rather than increasing the number of models.
- Effective concurrency: Unchanged test-runner scheduling; no new parallel work is introduced.
- Cache behavior: Static capture and snapshot fixtures replace prior files; no runtime cache keys or retained state change.
- Mechanism confidence: High: all relevant changes are model-id substitutions and generated snapshot updates with unchanged matrix cardinality.
- Magnitude uncertainty: None material for product performance; fixture text size changes only repository/test I/O by a bounded amount.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/test/node/e2e/providers/copilotPromptsE2E.integrationTest.ts and captures/copilotcli-claude-opus-5-5.yaml</code>: Recorded/replayed provider exchange in the E2E harness; cardinality: One model case replaces one previous case in the fixed matrix.
    - Introduced by diff: false; previous behavior: The same matrix slot and capture path ran for Claude Opus 4.8.; critical-path effect: Affects only the selected E2E test case, not product startup or interaction latency.
- Verdict: No product performance regression and no meaningful test-suite scaling regression.
