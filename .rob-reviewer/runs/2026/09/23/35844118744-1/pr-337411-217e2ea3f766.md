# Performance review: Agents/remove automation prioritized notifications

[PR #337411](https://github.com/microsoft/vscode/pull/337411) at `217e2ea3f7667579bb000c5975c6c3377524cccd`

## Findings (5)

### 1. [high] Bound preview generation instead of firing one model request per item

**Finding ID:** `PERF-193F82D6DD10`  
**Location:** <code>src/vs/sessions/contrib/inboxOne/browser/inboxNotificationsService.ts:420</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Language-model provider IPC/network requests and concurrent streamed responses  
**Scaling:** On a cold service instance the loop schedules one request per distinct notification preview signature, including active and dismissed items; aggregate concurrency is therefore O(N) in the number of current notification items, with only per-signature deduplication and no global limit.  
**Outcome:** Excessive concurrent network/IPC traffic, provider throttling, and reduced throughput for other language-model work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, notifications used their existing descriptions and this path made zero language-model requests.  
**Changed behavior:** A constructor autorun now eagerly calls ensurePreview for every item; every cache miss immediately invokes generatePreview, which independently calls sendChatRequest.  
**Confidence:** 0.99 — The one-item-to-one-provider-request call path and absence of an aggregate limiter are explicit. Only the exact typical item count is uncertain; model calls are intrinsically expensive enough that an unbounded cold-start burst is material.

**Causal diff evidence:** Added line 420 creates the collection-wide eager loop; each iteration can reach the newly added sendChatRequest boundary, whereas the base revision had no preview generation.

Restoring or receiving a batch of many sessions can launch tens or hundreds of utility-model calls at once while the Inbox is closed, consuming bandwidth/quota and delaying both previews and unrelated Copilot requests.

**Evidence:** The added autorun at lines 417-423 iterates allItems, explicitly including active and dismissed items. ensurePreview calls generatePreview immediately on every miss (line 440); generatePreview has only a Set keyed by signature, and invokePreviewModel delegates directly to the provider with sendChatRequest (lines 476-487). ILanguageModelsService.sendChatRequest itself directly delegates to provider.sendChatRequest (languageModels.ts:1461-1473), so there is no downstream global limiter established here.

**Suggested direction:** Generate previews only for items needed by the visible Inbox (or a bounded prioritized subset), and route misses through a small shared limiter that drops/cancels stale signatures. Preserve the existing signature cache and per-key coalescing inside that bounded queue.

### 2. [medium] Evict stale entries from the published preview map

**Finding ID:** `PERF-603A53D48AA4`  
**Location:** <code>src/vs/sessions/contrib/inboxOne/browser/inboxNotificationsService.ts:448</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** Retained preview keys/strings and repeatedly copied Map entries  
**Scaling:** After H unique preview signatures over the workbench lifetime, retained state is O(H), and publishing the next result clones all H entries, making cumulative publication allocation O(H²); removed items and changed signatures are never deleted.  
**Outcome:** Unbounded retained memory plus increasing CPU/GC pressure as notification content churns.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The base service had no generated-preview map or retained preview history.  
**Changed behavior:** Every generated preview clones the entire observable map and appends the signature, but no lifecycle path removes signatures that are no longer present in allItems.  
**Confidence:** 0.99 — The map mutation sites and absence of eviction are exhaustive in repository search, and the allocation/retention scaling follows directly. Only the time needed for a user to accumulate a large H is uncertain.

**Causal diff evidence:** Added line 448 copies the ever-growing published map on each new signature; both the map and this repeated-copy mechanism are introduced by the diff.

Long-running workbenches with recurring session turns, PR state changes, or external notifications steadily retain obsolete previews; later preview completions become progressively more allocation-heavy despite the nominal 200-entry LRU.

**Evidence:** The service declares a bounded PREVIEW\_CACHE\_SIZE of 200 and an LRUCache at lines 288-292, but publishPreview creates \`new Map(current)\` at added line 448 and adds the new entry before publishing it. Repository search shows \_previews is only initialized, read, and appended to (lines 312, 432, 444-450); there is no delete/clear synchronized with allItems. Thus the observable map bypasses the LRU bound and each insertion copies its entire retained history.

**Suggested direction:** On allItems changes, retain only signatures still referenced by current items (optionally plus a truly bounded recent set), and publish a bounded snapshot; alternatively expose per-key observables backed directly by the existing LRU so obsolete signatures can be evicted without cloning retained history.

### 3. [medium] Apply the transcript cap before processing the whole history

**Finding ID:** `PERF-FB276A03DE1E`  
**Location:** <code>src/vs/sessions/contrib/inboxOne/browser/inboxNotificationsService.ts:731</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Main-thread Markdown-to-plaintext CPU work and intermediate strings/arrays  
**Scaling:** Selection cost grows with every markdown response part and total transcript bytes in the session, even though only 6,000 output characters are retained.  
**Outcome:** Increasing click latency and potential UI jank when opening details for a long completed session.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the detail-summary feature, selecting a notification did not synchronously convert its full chat history.  
**Changed behavior:** Detail generation synchronously walks the complete chat history, renders every markdown part to plaintext, joins all output, and only then truncates it to DETAIL\_MAX\_INPUT\_CHARS.  
**Confidence:** 0.98 — The synchronous pre-await call path and post-processing-only cap are directly visible. Session-history sizes vary, but long agent sessions are a realistic input and cost scales linearly with their full history.

**Causal diff evidence:** Added line 731 introduces per-part Markdown rendering on the selection call stack; the diff's nominal 6,000-character bound does not bound this work because it is checked only after all parts are processed.

Selecting a completed card from a long-running agent session can block the renderer while the entire transcript is converted and allocated before the loading state can remain responsive.

**Evidence:** renderCompletedEvidence calls requestDetailSummary synchronously from the selection render (view line 1415). The async generateDetailSummary performs getSessionTranscript before its first await (service lines 622-630). That helper traverses all requests and executes renderAsPlaintext at added line 731, then joins and normalizes the full accumulated transcript at line 734; the 6,000-character slice is applied only afterward at line 738.

**Suggested direction:** Build the transcript incrementally and stop once the 6,000-character budget is satisfied (also bound oversized individual source parts before conversion where possible), then defer any remaining preparation off the immediate selection/render stack.

### 4. [medium] Keep full inbox hydration off the after-restore path

**Finding ID:** `PERF-B8DFDA901FBD`  
**Location:** <code>src/vs/sessions/contrib/inboxOne/browser/inboxNotificationsToast.ts:98</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub network refreshes and pollers plus chat-session load operations  
**Scaling:** On every restored workbench, cost grows with non-archived sessions and their pull requests: the service launches up to three refresh/poll paths per open PR and one chat-model load per needs-input or unread-completed chat, without a shared limiter.  
**Outcome:** Increased post-restore network traffic, background CPU, and contention that can degrade startup responsiveness.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The singleton was registered with InstantiationType.Delayed and was reached only when the Inbox view or its accessible view was requested, so users who did not open Inbox paid none of its PR hydration, polling, or chat-load cost.  
**Changed behavior:** The new AfterRestored contribution injects IInboxNotificationsService, forcing its previously delayed singleton to construct in every workbench and run all constructor autoruns even when the Inbox is never opened.  
**Confidence:** 0.98 — The delayed registration, new eager dependency, constructor autoruns, and concrete refresh/load calls are directly traced. Exact latency varies with session/PR count and provider speed, but the moved boundary fan-out is certain.

**Causal diff evidence:** The added line 98 registers an always-on AfterRestored contribution whose added constructor requires IInboxNotificationsService; before this diff there was no after-restore consumer forcing the delayed service to initialize.

Starting VS Code with many agent sessions or PR-backed sessions now immediately fans out GitHub refreshes/startPolling calls and chat model loads in the background, even if the user never opens Inbox.

**Evidence:** inboxOne.contribution.ts:27 keeps the service delayed, but the added contribution registered here is instantiated AfterRestored and its constructor dependency at inboxNotificationsToast.ts:31 resolves that service. InboxNotificationsService's constructor then loops every session through ensureGitHubModels (lines 333-337); that method calls refresh and startPolling for PR, review-thread, and CI models (lines 864-907), while another constructor autorun calls acquireOrLoadSession for each relevant chat through line 1418. These are fire-and-forget loops with no aggregate limiter.

**Suggested direction:** Keep toast detection lightweight: defer PR refresh/polling and chat-model hydration until the Inbox is shown, or split/gate the service so the toast path hydrates only a changed resource through a bounded shared limiter rather than initializing every session.

### 5. [medium] Cancel or serialize detail summaries when selection changes

**Finding ID:** `PERF-F895CF5096B4`  
**Location:** <code>src/vs/sessions/contrib/inboxOne/browser/inboxNotificationsView.ts:1415</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Language-model provider IPC/network requests carrying up to 6,000 transcript characters each  
**Scaling:** For cold entries, concurrency grows with the number K of completed cards selected before earlier generations finish; deduplication is only by item id, so K different selections produce K simultaneous requests.  
**Outcome:** Excessive model traffic and contention that delays the summary for the item the user is currently viewing.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** There was no completed-item detail pane or detail-summary model request before this change.  
**Changed behavior:** Rendering every newly selected completed item starts a detail-summary generation immediately; leaving that item disposes the UI but does not cancel its service-side request.  
**Confidence:** 0.97 — Selection-to-request reachability and missing cancellation are explicit. The number of rapid selections varies, which affects severity but not the concurrency mechanism.

**Causal diff evidence:** Added line 1415 puts a model-generation boundary on each completed-card selection; the base view had no selection-triggered model work.

A user browsing several completed notifications in quick succession can leave all prior 6k-character generations running while only the last result is useful, consuming network/provider capacity and slowing the selected detail.

**Evidence:** The added call at line 1415 runs on completed-item detail render. requestDetailSummary starts generateDetailSummary immediately for every uncached item (service lines 595-608), and invokeDetailModel sends a provider request (lines 647-676). Each request's CancellationTokenSource is placed in \_previewCancellationSources (line 624), but that set is cancelled only when the whole service is disposed (lines 350-354), not when selection/detailDisposables change. There is no shared limiter across item ids.

**Suggested direction:** Own the active detail request from the selected-item lifecycle: cancel the prior item's token when selection changes and/or serialize requests through a latest-selection-first limiter. Keep completed cached results, but do not continue cold requests for details no longer displayed.
