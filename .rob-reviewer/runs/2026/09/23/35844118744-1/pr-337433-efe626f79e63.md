### Scenario 1: First user turn in a new Agent Host chat with artifact tools enabled

- Critical path: Contribution collection runs before agent.chats.sendMessage; the artifact instruction is added to hostInstructions and therefore reaches the provider request critical path. The existing memento limits this instruction to the first turn of each chat.
- Scaling input: Number of newly created chats controls how often the first-turn instruction is sent; within one chat it does not scale with turn count. Tool count and artifact collection size are unchanged.
- Effective concurrency: No new parallelism or burst is introduced. Contribution processing remains serial and each turn performs the existing single provider dispatch.
- Cache behavior: The per-chat firstTurnSeen memento is the effective cache and suppresses the instruction after the first turn, including hydrated non-empty chats. No cache key, invalidation, coalescing, or negative-cache behavior changed.
- Mechanism confidence: High confidence that the full wording reaches the first provider request and that the memento bounds it to once per chat; high confidence that request cardinality is unchanged.
- Magnitude uncertainty: Exact tokenization and provider latency impact of replacing compact wording with the full wording varies by provider/model, but the increase is a small constant rather than input-scaled or repeated per turn.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:1814 agent.chats.sendMessage</code>: Send the user turn, host instructions, and tool metadata to the selected model provider.; cardinality: One provider send per user turn; the changed artifact instruction is included only on the first turn of each chat. - Verdict: No reportable regression. The fixed prompt-size increase is intentional, bounded, and does not establish meaningful latency, throughput, CPU, memory, or network degradation under realistic scaling.
