## Findings (1)

### 1. [high] Bound polling to active or repository-associated pull requests

**Finding ID:** `PERF-8101EC6CE9D2`  
**Location:** <code>src/vs/sessions/contrib/github/browser/github.contribution.ts:214</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub REST and GraphQL requests plus one live metadata/CI/review model set per unique recorded pull request  
**Scaling:** For N unique newly included recorded PRs across unarchived sessions, restoration launches 2N metadata/review REST requests concurrently; each open non-draft PR then adds N CI REST and N review-thread GraphQL requests immediately and every minute. Reference collections coalesce duplicate coordinates across sessions, so the effective cardinality is unique PRs, but no limiter or collection bound caps N.  
**Outcome:** A large session history can create sustained background network traffic, GitHub API pressure, and request bursts after workbench restore even when none of those sessions or pills is open.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The poller read only getGitHubPullRequestRefs(gitHubInfo), which required a workspace repository; agent-host promotion also kept repository metadata scoped to matching owner/repo, so workspace-less and cross-repository recorded PRs stayed out of global polling.  
**Changed behavior:** getSessionGitHubReferences now adds every recorded PR from session artifacts to each per-session polling identity, including workspace-less and foreign-repository links, and the existing polling loop refreshes and polls every resulting model.  
**Confidence:** 0.98 — The changed source, all-session call path, request counts, one-minute schedulers, and lack of a shared limiter are directly traced. Exact catalog sizes vary, but the artifact API accepts unbounded batches and persists entries, so magnitude uncertainty affects severity rather than mechanism confidence.

**Causal diff evidence:** RIGHT line 214 replaces the workspace-scoped getGitHubPullRequestRefs(gitHubInfo) source with getSessionGitHubReferences(session, reader), whose new implementation scans session.artifacts and returns recorded PRs regardless of workspace or repository.

After restore, users with accumulated sessions containing recorded PR links can see a concurrent request burst and continuous background polling. Roughly 20 unique open non-draft recorded PRs already drive about 80 GitHub requests per minute (two PR requests, one CI request, and one GraphQL review-thread request per PR) while VS Code remains open.

**Evidence:** GitHubPullRequestPollingContribution initializes trackers from getSessions() at WorkbenchPhase.AfterRestored and this changed line broadens each tracker to all artifact-derived PRs. \_pollPullRequest immediately calls model.refresh(); GitHubPullRequestModel.refresh performs two REST calls in Promise.all. Once an open PR resolves, the same tracker refreshes CI and review-thread models and starts all three schedulers at 60-second intervals. GitHubApiClient issues requests directly through IRequestService with no limiter. parseSessionArtifactInputs accepts an arbitrary non-empty items array, and persisted artifact collections have no size bound.

**Suggested direction:** Keep all recorded refs available to the pills, but do not enroll every historical ref in catalog-wide one-minute polling. Restrict global polling to repository-associated or active/visible-session PRs, refresh other recorded refs on demand, and use a shared bounded scheduler if background refresh is still required.

### Scenario 2: Active session chat toolbar resolving dedicated pull-request and issue pills, including workspace-less and cross-repository records

- Critical path: Reference parsing and pill construction are synchronous on the active toolbar render path but linear/small per artifact in normal use. Network refreshes are fire-and-forget; fallback labels/icons render without awaiting them.
- Scaling input: Recorded artifacts plus repository associations in the active session. Shared model collections coalesce identical GitHub coordinates; artifact storage normally deduplicates identical values.
- Effective concurrency: PR data is supplied by the central poller. When issue pills are enabled, all distinct issue models refresh concurrently and each open issue schedules a 15-minute poll; there is no shared limiter across distinct issues.
- Cache behavior: Issue models debounce on-demand refreshes for 60 seconds and retain up to 100 disposed snapshots with ETags; warm unchanged responses can be 304. PR references use shared live models. getSessionGitHubReferences itself does not cache but recomputes only when observed session/workspace/artifact inputs invalidate.
- Mechanism confidence: High for reachability and request count; lower magnitude than catalog-wide PR polling because only one active session participates and issue polling is much slower.
- Magnitude uncertainty: Typical active sessions likely contain few issue links, so this active-only, 15-minute fan-out was not separately reported despite the same unbounded artifact input.
- Expensive boundaries:

- Verdict: No separate finding: dedicated issue resolution adds network work but is active-session-only, off the UI critical path, cached, and has a 15-minute cadence; the stronger catalog-wide PR fan-out is reported.
