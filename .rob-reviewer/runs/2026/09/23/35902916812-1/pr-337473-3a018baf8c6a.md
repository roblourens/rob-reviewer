# Performance review: Automations: Scope list tool results to providers

[PR #337473](https://github.com/microsoft/vscode/pull/337473) at `3a018baf8c6a7727a11d202e7e1f5877ee60f037`

## Findings (1)

### 1. [low] Avoid re-routing every row's capabilities through the aggregate service

**Finding ID:** `PERF-D6C41A08CC27`  
**Location:** <code>src/vs/sessions/contrib/automations/browser/automationTools.ts:1102</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and temporary strings/descriptors created by repeated provider sorting, ID scans, URI/config projection, and capability-array construction.  
**Scaling:** For N visible automations, the diff adds 3N aggregate capability queries; each scans registered provider stores and linearly searches catalogue entries, then the selected store linearly searches again. Effective work is quadratic in catalogue size, with extra repeated provider sorting as provider count grows.  
**Outcome:** Increased synchronous list-tool latency and CPU/GC pressure as catalogues grow.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The prior list implementation read the aggregate automation snapshot once, mapped each descriptor once, and serialized it, so work was linear in visible automations plus output bytes and made no per-row capability queries.  
**Changed behavior:** Each listAutomations invocation now performs canRunAutomation, canUpdateAutomation, and canDeleteAutomation through the aggregate service for every visible automation, adding repeated provider enumeration and catalogue scans to the synchronous tool path.  
**Confidence:** 0.94 — The changed per-row calls and synchronous list invocation are direct. ProviderAutomationService.can\* each calls findAutomationStore; findAutomationStore calls getStores/getProviders and probes stores with getAutomation, while AgentHostAutomationStore.getAutomation and can\* each use a linear \_findAutomationEntry scan. Exact latency depends on how many definitions and hosts users accumulate, so severity is low, but the quadratic mechanism is explicit and unbounded.

**Causal diff evidence:** Added line 1102 is the first of three new per-row calls to the aggregate IAutomationService capability methods; line 162 invokes this helper for every automation in every provider. The deleted implementation only mapped each aggregate automation through toAutomationToolOutput and performed no capability routing.

Invoking listAutomations with a catalogue accumulated to many definitions, especially across several local/remote Agent Hosts, synchronously burns CPU and allocations before the tool can return, increasing chat tool latency and GC pressure.

**Evidence:** toAutomationListToolOutput calls all three aggregate capability methods per row. ProviderAutomationService routes each call via findAutomationStore(), whose getStores() obtains and sorts providers and whose find() calls store.getAutomation(id). AgentHostAutomationStore.getAutomation() linearly scans catalog.entries and projects a descriptor; the subsequent store.can\* call linearly scans the same entries again. Thus listing N definitions creates O(N^2) ID comparisons/string construction plus 3N discarded descriptor projections rather than a single catalogue pass.

**Suggested direction:** Build operation metadata in one provider-local pass: expose or derive each entry's operation set from the owning store, or add an indexed/batched capability lookup, and pass that provider-local result into serialization instead of routing three aggregate can\* calls per row.
