## Findings (2)

### 1. [medium] Bound cross-host workspace probes during placement

**Finding ID:** `PERF-80E1B89E8156`  
**Location:** <code>src/vs/sessions/contrib/remoteSessions/browser/remoteSessionService.ts:202</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** remote filesystem \`resourceResolve\` RPCs and their pending protocol request objects  
**Scaling:** One stat RPC is issued for every eligible connected remote provider (H calls in parallel), and completion latency is the maximum of all H probes; a non-returning probe leaves the creation pending until external cancellation or connection closure.  
**Outcome:** increased latency and blocked critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no remote-session placement path that broadcast a workspace stat across all connected agent hosts; ordinary creation targets one provider/workspace.  
**Changed behavior:** Remote creation with a target-local file URI now probes every eligible connected host concurrently and waits for all probes before selecting the least-loaded host.  
**Confidence:** 0.97 — The added map/Promise.all call path is explicit; \`RemoteAgentHostSessionsProvider.mapWorkingDirectoryUri\` converts each file URI to that host's \`vscode-agent-host\` authority, and \`AgentHostFileSystemProvider.stat\` forwards it through \`resourceResolve\`. Protocol requests have no request timeout, while \`raceCancellationError\` only races the caller token and does not cancel the underlying RPC. The only uncertain factor is how many hosts a typical user connects, which affects severity rather than the mechanism.

**Causal diff evidence:** RIGHT line 202 introduces \`Promise.all(this.remoteProviders().map(...))\`, and RIGHT line 207 performs \`fileService.stat(candidate.workspace)\` inside that per-provider map. For an unqualified \`file:\` workspace, \`getCandidate\` maps the same path into every eligible remote host, so this diff creates one remote filesystem RPC per host and awaits the whole fan-out before placement.

Creating a remote session for \`file:///...\` can hang on one unrelated slow/reconnecting host even when another healthy host is eligible; larger host fleets also receive a burst of simultaneous filesystem RPCs.

**Evidence:** \`RemoteSessionService.candidates\` maps an unqualified workspace to each provider, launches all validations with \`Promise.all\`, and calls \`IFileService.stat\` for each. The mapped scheme is backed by \`AgentHostFileSystemProvider.stat\`, which awaits a remote \`resourceResolve\` JSON-RPC. \`AgentHostProtocolClient.\_dispatchRequest\` registers the pending request without a timeout and deliberately waits through reconnect cycles. Therefore one slow/reconnecting candidate blocks the entire creation request, and H eligible hosts produce H simultaneous remote filesystem calls.

**Suggested direction:** Bound candidate probing with a shared concurrency limiter and a per-host deadline. Treat a timed-out host as rejected and continue with healthy candidates; preserve exact-host behavior by probing only the pinned host when \`hostId\` or a host-qualified workspace is supplied.

### 2. [low] Cap workspace inventory before serializing host lists

**Finding ID:** `PERF-E8C5977FB9E0`  
**Location:** <code>src/vs/sessions/contrib/remoteSessions/browser/remoteSessionService.ts:116</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** workspace objects and JSON/tool-result bytes  
**Scaling:** Cost grows with the effective number of distinct workspace URIs across every connected host after deduplication; the scan additionally grows with total sessions, even when many map to the same workspace.  
**Outcome:** CPU/GC pressure and increased tool latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR no language-model tool scanned every remote provider's session catalog and serialized its workspace inventory into a prompt-visible result.  
**Changed behavior:** The new \`list\_agent\_hosts\` tool exports all distinct workspaces from each connected host's complete in-memory session catalog into one language-model tool result.  
**Confidence:** 0.94 — The full-catalog scan, URI/label retention, and whole-result JSON serialization are direct. \`BaseAgentHostSessionsProvider.getSessions\` returns every entry in \`\_sessionCache\`; only persisted startup snapshots are capped at 100, while a successful live \`listSessions()\` repopulates the cache from the full host result. Exact user catalog sizes are uncertain, so severity is low.

**Causal diff evidence:** RIGHT line 116 walks every session returned by every remote provider and accumulates every distinct workspace without a limit; \`ListAgentHostsTool.invoke\` then serializes the resulting structure in full with \`JSON.stringify({ hosts })\` at RIGHT line 45.

Users with long-lived hosts or many repositories can get a very large tool result, increasing list-tool latency, allocation/GC pressure, and model-context consumption before the agent can continue.

**Evidence:** \`describeHost\` deduplicates workspaces but never bounds their effective cardinality, and \`listHosts\` repeats this for all remote providers. The tool then pretty-prints the entire object, allocating and passing all bytes downstream. On connected hosts, \`\_refreshSessions\` inserts the complete \`connection.listSessions()\` response into \`\_sessionCache\`, so the live result is not constrained by the 100-entry persistence cap.

**Suggested direction:** Cap workspaces per host before constructing/serializing the result (prefer the most recently used entries) and include total/truncated metadata so callers can request or target a narrower inventory without materializing the full catalog.

- Cache behavior: Provider session catalogs and registered model metadata are reused when warm. A cold \`provider.getSessions()\` can start one coalesced asynchronous \`listSessions()\` refresh per provider, but the tool returns the currently available cache. Workspace inventory is deduplicated by URI but not capped or otherwise cached as a bounded projection.
- Mechanism confidence: High: full session scans, distinct-workspace accumulation, and uncapped JSON serialization are explicit.

### Scenario 2: Create a remote session with automatic host placement

- Critical path: Resolving the exact source session, validating all candidate hosts, selecting one, creating/configuring its session, acquiring the background chat, and accepting the first prompt all block completion. For an unqualified file workspace, every candidate stat is awaited before selection.
- Scaling input: Eligible connected host count H for file-workspace validation; workspace-less creation performs no stat fan-out.
- Effective concurrency: Candidate workspace validation uses unbounded \`Promise.all\` across eligible providers. After selection only one host creation proceeds. Pending-creation counters influence placement but do not limit aggregate candidate probes.
- Cache behavior: Creation requests are coalesced by source/request ID and retained up to 25 per window. Candidate workspace stats have no positive/negative cache and are repeated for distinct creation calls. Registered model/session state is read from warm in-memory catalogs when available.
- Mechanism confidence: High: URI mapping reaches the remote filesystem provider, which sends an un-timed \`resourceResolve\`; outer cancellation races but does not cancel the underlying RPC.
- Magnitude uncertainty: Fleet sizes and remote RPC durations vary, but the absence of a per-probe deadline and protocol request timeout makes the slowest-host dependency real at any fleet size above one.
- Expensive boundaries:

    - Introduced by diff: true; previous behavior: No remote delegation creation path resolved an originating host session.; critical-path effect: Must provide verified source identity/depth before placement.
  - network at <code>src/vs/sessions/contrib/remoteSessions/browser/remoteSessionService.ts:202-210</code>: Validate that the requested target-local workspace exists and is a directory on each candidate host.; cardinality: For an unqualified file URI, one remote \`resourceResolve\`/stat per eligible connected host; a host-qualified workspace or host ID effectively narrows this to one.

  - IPC/network at <code>src/vs/sessions/contrib/remoteSessions/browser/remoteSessionService.ts:292-304</code>: Create/configure a remote session, load its chat model, and submit the initial prompt.; cardinality: One session creation/send on the selected host and one background chat acquire/load; no per-candidate creation fan-out.

### Scenario 3: Send a remote follow-up or reply to the originating chat

- Critical path: Source resolution, target session/chat snapshots, workspace trust checks, client-tool preparation, dispatch, and host acknowledgement block the send result. The subsequent model turn runs asynchronously after acknowledged queueing.
- Scaling input: Up to 50 admitted sends per window, serialized per exact target chat; multi-root trust checks scale with target folder count.
- Effective concurrency: Sends are FIFO-serialized per exact target chat by \`SequencerByKey\`; different target chats can run concurrently, with the window-wide request cap bounding total admitted sends at 50.
- Cache behavior: Send requests are coalesced by source/request ID and capped at 50 per window. Protocol subscriptions are temporary/ref-counted. \`acquireOrLoadSession\` reuses an existing warm model; cold targets load once per active reference. Background model references remain until active and queued requests are both idle.
- Mechanism confidence: High: ordering, caps, temporary subscription disposal, and idle release are explicit and covered by changed tests.
- Magnitude uncertainty: Cold model/history load duration depends on target history and connection latency; the request cap and per-chat sequencer bound retained references and same-chat pressure.
- Expensive boundaries:

### Scenario 4: Inspect a remote session's current status and latest response

- Critical path: Exact host/provider resolution and verified session/chat snapshots must complete before returning. A 10-second cancellation timeout bounds the operation.

- Cache behavior: Inspection intentionally does not use cached chat-model content; it reads current verified protocol state. Temporary subscriptions are disposed after each call and unavailable results are not cached.
- Mechanism confidence: High: exact two-subscription flow, timeout, disposal, and output caps are explicit.
