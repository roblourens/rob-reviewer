### Scenario 1: An MCP server is enabled or disabled outside the Agent Host session (for example by another SDK/CLI runtime entry point).

- Critical path: The SDK status event synchronously updates the live customization, compares the prior and current enablement, resolves the desired state, and emits one customization-toggle action only for a real enablement transition. Client notification and local enablement synchronization are on this event path; cross-session reconciliation is scheduled asynchronously and does not block the originating runtime toggle.
- Scaling input: Number of active Agent Host sessions affected by a global decision, plus MCP/customization counts used by bounded linear lookups. Typical status chatter that does not change the enabled bit is filtered out.
- Effective concurrency: Unexpected transitions are handled once per server status stream. Reconciliation is serialized by the existing per-session MCP enablement sequencer; separate affected sessions may reconcile concurrently. Local enablement writes are transactionally coalesced by the existing observable/storage model.
- Cache behavior: Live prior enablement is retained per server and suppresses duplicate status emissions. Desired state is recomputed from current authoritative customization data; no new cache miss loop is introduced. Local enablement storage avoids rewriting unchanged map entries.
- Mechanism confidence: High: the event guards, action emission, persistence side effect, per-session reconciliation listener, sequencer, and RPC calls are directly traced.
- Magnitude uncertainty: The number of simultaneously active sessions and configured MCP servers varies, but the new work occurs only on actual enablement transitions rather than every lifecycle event.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_syncObservedMcpServerEnablement</code>: Emits a SessionCustomizationToggled action through the Agent Host action stream to connected clients.; cardinality: One action per actual enabled/disabled transition after the previous-enabled and desired-enabled guards; repeated status updates with unchanged enablement emit none.
    - Introduced by diff: true; previous behavior: External runtime enablement transitions updated lifecycle state but did not publish a scoped toggle action.; critical-path effect: Synchronous event publication occurs on the status-event path, while downstream client handling is event-driven.
  - filesystem at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:\_recordCustomizationEnablement -&gt; agentHostCustomizationEnablementService.ts:replaceEnablement</code>: Persists the changed global customization decision and session metadata through the existing enablement service.; cardinality: One replacement per emitted transition; global changes can notify all active sessions, but identical repeated statuses are suppressed before emission.
    - Introduced by diff: true; previous behavior: No enablement decision was persisted from an externally observed runtime transition.; critical-path effect: The in-memory replacement is synchronous; host storage/database persistence is queued and is not awaited by the SDK status callback.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_doReconcileMcpServerEnablement</code>: Calls rpc.mcp.list for each affected active session, then enable/disable only where that session differs from the new global decision.; cardinality: At most one queued reconciliation per enablement-change notification per active affected session; server mutations are sequential within each session.

    - Introduced by diff: true; previous behavior: Agent Host toggle actions did not synchronize the client-owned local MCP enablement model.; critical-path effect: Synchronous model update can notify UI observers; persistence uses the existing storage service and is not a network/process boundary.
- Verdict: No reportable regression. The new boundary work is the required synchronization behavior, is transition-deduplicated, and uses existing per-session serialization; there is no high-confidence avoidable fan-out or critical-path amplification.

### Scenario 2: Agent Host reconciles desired MCP enablement after a user customization change or session send/resume.

- Critical path: The existing reconciliation lists MCP servers and sequentially applies required mutations. The diff only records the expected result before each enable/disable RPC and clears it when the matching SDK status arrives, preventing that host-requested transition from being reclassified as external.
- Scaling input: Number of configured MCP servers with desired state and number actually mismatched after the list result.
- Effective concurrency: A single existing sequencer serializes reconciliation per session, and enable/disable calls remain sequential across servers. The two new maps are keyed by server name and do not create additional tasks or parallel RPCs.
- Cache behavior: Launch projection and desired-state resolution remain unchanged. Expected-transition entries are deleted on matching status or RPC failure; retained entries are bounded by server names in a session.
- Mechanism confidence: High: before/after RPC placement and sequencer behavior are explicit in the changed and surrounding code.
- Magnitude uncertainty: SDK status delivery timing varies, but bookkeeping cost is constant per mutation and does not change boundary cardinality.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_enableMcpServer/\_disableMcpServer</code>: Invokes SDK rpc.mcp.enable or rpc.mcp.disable for servers whose observed state differs from desired state.; cardinality: Unchanged from before the diff: one mutation per mismatched server after a single mcp.list for the reconciliation; calls remain sequential.
    - Introduced by diff: false; previous behavior: The same RPCs were called directly without expected-transition bookkeeping.; critical-path effect: When reconciliation is awaited by send/resume it remains on that existing critical path; the added map operations do not add an awaited boundary.
- Verdict: No performance regression. RPC count, serialization, and critical-path placement are unchanged; the added work is constant-time bookkeeping.

### Scenario 3: Workbench receives a customization-toggle action while MCP/customization UI is active.

- Critical path: The action handler synchronously locates the matching session customization and local MCP server, updates profile enablement, then emits the existing customization and custom-agent change notifications. Visible MCP rows may synchronously refresh from those notifications.
- Scaling input: Subscribed Agent Host chat sessions, customizations in the matching session, configured local MCP servers, and currently rendered listeners. These are not multiplied by normal server lifecycle statuses because unchanged enablement is filtered at the producer.
- Effective concurrency: Handling is synchronous per action. Session, customization, and local-server lookups are linear scans; there is no spawned concurrency or boundary burst. The local enablement model coalesces unchanged values.
- Cache behavior: Authoritative current or verified session snapshots are reused. No new cache is introduced; local storage updates are skipped when the stored value already matches.
- Mechanism confidence: High for the synchronous scans and notifications; low evidence of a realistic hot frequency or material latency impact.
- Magnitude uncertainty: Large customization management views can have many listeners, but enablement toggles are low-frequency discrete events and the diff does not place this work on scrolling/render loops.
- Expensive boundaries:
  - serialization at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts:\_syncClientMcpEnablement</code>: Scans subscribed sessions, flattens one session's customizations, scans local MCP servers, and updates the persisted enablement map.; cardinality: One pass over subscribed sessions, one pass over that session's customizations, and one pass over local servers per global toggle action; only one uniquely matched server is updated.
    - Introduced by diff: true; previous behavior: Toggle actions relied on eventual session-state notification and did not synchronize the local MCP profile model in this handler.; critical-path effect: Runs synchronously before listeners are notified, but actions are user/runtime enablement transitions rather than render-, input-, scroll-, or frame-frequency events.
- Verdict: No reportable regression. The work scales linearly on a low-frequency transition and is bounded by active subscriptions/configured servers; evidence does not establish jank or excessive I/O.

### Scenario 4: Workbench service construction and ordinary MCP lifecycle updates that do not change runtime enablement.

- Critical path: The customization service receives a delayed IMcpService dependency. Ordinary pending/connected/failed/stopped updates perform only map lookups and return before desired-state resolution when the enabled bit is unchanged.
- Scaling input: Frequency of normal MCP lifecycle status events and number of live server names stored in the session maps.
- Effective concurrency: No work is scheduled by unchanged enablement statuses. Both the customization service and MCP service are registered as delayed services, so constructor injection does not itself eagerly discover or start servers.
- Cache behavior: The controller's live map supplies the previous enabled bit, allowing unchanged lifecycle updates to avoid action emission and synchronization. Expected and observed maps are per session and keyed by server name.
- Mechanism confidence: High based on delayed singleton registrations and early-return guards.
- Magnitude uncertainty: Sessions can observe many lifecycle statuses, but the changed path adds constant-time map reads for unchanged enablement and no boundary call.
- Expensive boundaries: none found
- Verdict: No eager-startup or hot-status-path regression. The new dependency remains lazy, and unchanged lifecycle updates do not cross persistence, IPC mutation, or UI fan-out boundaries.
