**Relevant issue families:** synchronous-ui-work, cleanup-lifecycle, repeated-work, serialization-allocation, boundary-fanout

### Scenario 1: Dismiss an active spotlight from external participating UI with Escape

- Critical path: A capture-phase window keydown runs the added target guards; for an external HTMLElement it constructs one StandardKeyboardEvent, and Escape synchronously fires onDidSkip. The presentation's listener resolves the current step, then hide/disposal clears the per-step listener. No subprocess, IPC, filesystem, database, or network operation is on this changed key path.
- Scaling input: One added listener per currently shown external-participation spotlight; work is constant per window keydown, with two DOM containment checks and at most one keyboard wrapper allocation. It does not scale with DOM-tree traversal in application code, tour history, or step count.
- Effective concurrency: The listener belongs to the current overlay step and is replaced on show, cleared on hide, and disposed with the overlay. A normal tour has one active overlay; there is no asynchronous fan-out or queued work.
- Cache behavior: No cache is involved. Re-showing a step replaces the listener through DisposableStore.clear rather than accumulating listeners.
- Mechanism confidence: High: the listener registration, per-event operations, synchronous emitter path, and cleanup ownership are explicit in SpotlightOverlay.show/hide and SpotlightPresentation.\_runStep.
- Magnitude uncertainty: Exact typing frequency while an external target is active varies, but each event performs bounded, lightweight DOM/event work and only Escape ends the step.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff adds bounded input-path work but no layout read/write, rendering pass, I/O, accumulation, or concurrency burst; listener lifecycle is correctly scoped to the shown step.

### Scenario 2: Open a malformed or unknown direct feature-example link from release notes

- Critical path: The release-notes webview click is delivered to ReleaseNotesEditor, which calls ReleaseNotesTryouts.openLink. Malformed command arguments are decoded/JSON-parsed and now return from the local catch; unknown IDs perform the existing linear map search and return. Both changed cases stop before interact, command execution, tryout service run, focus restoration, notification rendering, or webview postMessage.
- Scaling input: For malformed links, bounded URI argument parsing only. For a syntactically valid unknown ID, the existing spread/find remains O(number of tryout links in that single release-notes document) and allocates one array; the diff neither introduced nor increased that work.
- Effective concurrency: One async handler per user click. The changed early returns launch no interaction, command, service request, IPC, queue, or parallel work.
- Cache behavior: The document-local \_links map is populated once during render and reused; no new cache state, invalidation, miss retry, or retained key is introduced.
- Mechanism confidence: High: the before/after diff preserves parse and map-search cardinality while replacing error notification with early return, and interact is unreachable for malformed or unknown IDs.
- Magnitude uncertainty: Release-note link counts and malformed-link click frequency vary, but changed paths strictly remove notification work and do not add a scaling boundary.
- Expensive boundaries: none found
- Verdict: No reportable regression. The change removes downstream UI work on rejected links; valid-link dispatch and its existing service/command boundaries are unchanged.

**Summary:** Completed the performance pass over all four changed files and traced both affected product scenarios. No diff-introduced hot-path, boundary fan-out, retention, cache-lifecycle, or allocation regression met the reporting threshold.
