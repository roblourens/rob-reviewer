## Findings (1)

### 1. [medium] Stop polling spotlight geometry on every animation frame

**Finding ID:** `PERF-280220A8D08B`  
**Location:** <code>src/vs/workbench/contrib/onboarding/browser/spotlight/spotlightOverlay.ts:197</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** requestAnimationFrame callbacks and synchronous DOM geometry/layout reads  
**Scaling:** One callback and getBoundingClientRect() run per display frame for the full user-controlled lifetime of every shown spotlight (about 60-144 reads/second); while the target moves, each frame also calls layout(), repeats geometry measurement, reads callout offsets, and rewrites overlay geometry.  
**Outcome:** continuous renderer CPU/layout pressure, with increased frame time and potential UI jank/battery usage while onboarding remains open  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The overlay measured on show and only re-laid out after resize, scroll, ResizeObserver, or workbench layout events, so a stationary user-paced step did no frame-by-frame geometry work.  
**Changed behavior:** The added animate() registration creates an unconditional recursive requestAnimationFrame loop for each shown step and synchronously samples the target rectangle every frame until the step is hidden.  
**Confidence:** 0.99 — The perpetual RAF semantics, synchronous geometry call, disposal lifetime, and user-paced production call path are all directly visible in repository code. Exact milliseconds vary by DOM complexity and refresh rate, which affects severity rather than the mechanism.

**Causal diff evidence:** RIGHT lines 197-203 newly register animate(targetWindow, ...) in show(); before this hunk, only event/observer-driven listeners scheduled layout.

Opening any spotlight tour or model-picker tryout now keeps the renderer sampling layout at the monitor refresh rate for as long as the user reads or interacts with the step; a one-minute pause produces roughly 3,600-8,640 geometry reads, and active picker/workbench animation additionally invokes the full overlay layout each frame.

**Evidence:** animate() is an unbounded recursive requestAnimationFrame helper (src/vs/base/browser/dom.ts:1766-1774). The changed callback calls target.getBoundingClientRect() every iteration; on movement it calls layout(), which reads getBoundingClientRect() again and then offsetWidth/offsetHeight after geometry writes (spotlightOverlay.ts:270-333). \_showStep awaits user action with no duration bound, and production tours contain interactive workspace/model-picker steps, so the loop remains live on a realistic user-paced path.

**Suggested direction:** Replace the perpetual poll with bounded tracking: start RAF sampling only while a relevant target/ancestor animation or a recent mutation/layout signal can move the target, stop after geometry is stable, and retain the existing resize/scroll/ResizeObserver/workbench-layout triggers for steady state.
