# Performance review: Suggest agent session storage cleanup when worktrees accumulate

[PR #338502](https://github.com/microsoft/vscode/pull/338502) at `0828825bad3f8d83310c01ebe67d85e4b4165e98`

## Findings (3)

### 1. [high] Bound per-entry worktree stat requests

**Finding ID:** `PERF-F278F2113E08`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/worktreeDiskUsage.ts:40</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** agent-host protocol requests and filesystem stat operations  
**Scaling:** Each worktree now performs one resourceList request per directory and one resourceResolve request per child entry. The Promise.all concurrency grows with every child in each of up to 8 directories, multiplied again by all worktrees in up to 2 concurrently measured sessions.  
**Outcome:** protocol/host I/O saturation, high CPU/allocation pressure, and long manager load times or interference with active agent traffic  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, opening the cleanup manager or Sessions view did not recursively stat worktree contents, so this protocol and filesystem load did not exist.  
**Changed behavior:** The new recursive measurement maps every directory entry to resourceResolve inside Promise.all; MAX\_CONCURRENT\_REQUESTS limits directory batches but does not limit the number of child stat requests, and the provider concurrently starts every worktree traversal for a session.  
**Confidence:** 0.99 — The changed call path from manager/notice to getSessionWorktreeDiskUsage to these protocol calls is explicit, and repository protocol implementations prove one request and filesystem stat per entry. Exact tree sizes vary, but large dependency trees are realistic and the concurrency is mathematically unbounded by entry count.

**Causal diff evidence:** Added lines 38-40 create Promise.all(children.entries.map(...resourceResolve...)); this is the new unbounded per-entry request burst.

Opening Clean Up Agent Worktrees on a cold cache—or enabling the Sessions cleanup suggestion—can launch thousands or tens of thousands of simultaneous protocol requests for a large source tree (for example a worktree containing node\_modules). The manager awaits the traversal, while the background suggestion scan can contend with normal agent traffic.

**Evidence:** resourceList is implemented as a protocol \_sendRequest and returns all immediate entries; resourceResolve is another \_sendRequest backed by IFileService.stat. At lines 38-41, every child from each batched directory is resolved through one Promise.all. BaseAgentHostSessionsProvider also uses Promise.all across a session's worktrees, while SessionWorktreeCleanupService permits two sessions concurrently, so the aggregate is not bounded by the apparent directory batch of 8.

**Suggested direction:** Use one shared limiter for resourceResolve work across directories/worktrees (and ideally sessions), or add/use a host-side aggregate disk-usage operation so only one bounded request crosses the protocol per worktree.

### 2. [high] Classify protected sessions before measuring them

**Finding ID:** `PERF-56240D1A5BB4`  
**Location:** <code>src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupService.ts:184</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** recursive filesystem walks, agent-host IPC requests, and filesystem stat operations  
**Scaling:** Cold-scan cost is the sum of every file and directory in every session that has a worktree, including active, running, needs-input, pinned, recent, archived, untitled, and errored sessions; it therefore grows with all retained worktrees rather than only cleanup candidates.  
**Outcome:** excessive I/O/IPC and delayed cleanup-manager loading, with hourly background contention when suggestions are enabled  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no disk-usage scan when opening the cleanup UI or Sessions view.  
**Changed behavior:** \_measureWorktrees filters only for the presence of a worktree, invokes the recursive getDiskUsage for every such session, and computes cleanupState only after the traversal. The editor subsequently renders only cleanupState === 'eligible' rows, so protected sessions' measurements are discarded.  
**Confidence:** 0.99 — The ordering and downstream eligibility filter are explicit in changed code, and the provider implementation proves each call recursively traverses the worktree. Magnitude depends on retained session/tree counts, but this feature targets users with accumulated worktrees, making multi-root scans the intended scenario.

**Causal diff evidence:** Added line 184 invokes the new recursive disk measurement for every item selected only by worktree presence at lines 168-171, before the eligibility classification at line 193.

A user opening the manager with many recent or protected agent sessions must wait for complete recursive scans that cannot produce a selectable row. With suggestions enabled, opening the Sessions view repeats this cold work at the hourly cache boundary even when few or no sessions are eligible.

**Evidence:** Lines 168-171 collect all worktree sessions without eligibility checks; line 184 awaits getSessionWorktreeDiskUsage; only line 193 calls \_getCleanupState. That state rejects archived/active/running/needs-input/pinned/recent/untitled/error sessions. SessionWorktreeCleanupEditor.setInput awaits getWorktrees and renderRows explicitly iterates only eligible rows, proving the extra boundary work is on the manager critical path and unused by the UI.

**Suggested direction:** Compute all metadata-only protection states first and call getSessionWorktreeDiskUsage only for sessions that can be cleanup candidates; preserve summary counts from workspace metadata without traversing protected trees.

### 3. [medium] Coalesce concurrent worktree measurements

**Finding ID:** `PERF-461C1B029766`  
**Location:** <code>src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupService.ts:223</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** duplicate recursive filesystem walks and duplicate agent-host protocol requests  
**Scaling:** When two cold callers overlap, each independently traverses every worktree and performs one list per directory plus one stat per entry, doubling work proportional to the total files across all retained worktrees.  
**Outcome:** avoidable I/O/IPC saturation and increased manager load latency during the initial suggestion scan  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR neither the automatic storage scan nor manager measurement existed, so there was no duplicate traversal race.  
**Changed behavior:** \_refreshIfNeeded coalesces only callers entering the automatic refresh path. The editor calls getWorktrees directly; while \_refresh is still measuring, \_lastMeasuredWorktrees is unset, so \_getMeasuredWorktrees starts a second \_measureWorktrees call instead of joining the in-flight one.  
**Confidence:** 0.97 — The two concurrently reachable changed entry points and absence of a shared measurement promise are explicit. The trigger requires suggestions enabled and quick manager opening, so prevalence is uncertain, but whenever it occurs the full duplicate traversal is deterministic.

**Causal diff evidence:** Added line 223 directly awaits a new \_measureWorktrees call whenever the completed-result cache is empty, even if the automatic refresh has the same measurement in flight.

With suggestions enabled, SessionsView immediately starts a background scan. If the user opens Clean Up Agent Worktrees from the always-available command or menu before that scan completes—a likely interval for large trees—the editor launches the same expensive scan again and waits behind competing duplicate I/O.

**Evidence:** SessionStorageCleanupNotice line 97 fire-and-forgets activate(), while SessionWorktreeCleanupEditor line 161 independently awaits getWorktrees(). The only in-flight field is \_refreshPromise in \_refreshIfNeeded; line 223 in \_getMeasuredWorktrees directly starts \_measureWorktrees and stores results only after it finishes, leaving the second entry point uncoalesced.

**Suggested direction:** Track a shared in-flight measurement promise inside \_getMeasuredWorktrees, keyed by the measured session signature as needed, and have both refresh and editor callers await it before starting another scan.
