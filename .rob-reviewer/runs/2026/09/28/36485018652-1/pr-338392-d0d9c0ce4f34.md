# Performance review: agentHost: Keep remote hosts alive while agents are running

[PR #338392](https://github.com/microsoft/vscode/pull/338392) at `d0d9c0ce4f34645a9341b2a21c46920e62bfcd56`

## Findings (2)

### 1. [low] Preserve the original idle deadline when the server exits

**Finding ID:** `PERF-A419CB4D7797`  
**Location:** <code>cli/src/tunnels/agent\_host.rs:440</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** the detached supervisor process, its Tokio runtime/tasks, listener, and registry state  
**Scaling:** The retained resources grow with the number of dedicated remote hosts launched; each idle host now remains for one additional configured idle-timeout interval.  
**Outcome:** retained remote memory and process slots for an extra five minutes with the default configuration  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After the last client disconnected, the supervisor's 300-second timer and the backend's 5-minute auto-shutdown timer ran concurrently, so both processes ended at roughly the same deadline.  
**Changed behavior:** The new server-lifetime guard keeps the activity count nonzero until the backend exits; dropping it emits a Disconnected event that starts a fresh full supervisor timeout only after the backend's own 5-minute shutdown period has elapsed.  
**Confidence:** 0.98 — The guard lifetime, event semantics, and both default five-minute durations are explicit in the traced code. The exact per-process RSS varies, but the additional process lifetime is deterministic.

**Causal diff evidence:** Added line 440 releases the newly added process-wide activity guard only after the backend process has exited, which queues the event that re-arms the supervisor's full idle timer.

Every default SSH/WSL dedicated host that has served a client remains as an otherwise-idle supervisor for about 10 minutes after disconnect instead of about 5 minutes. Repeated or parallel dedicated-host use leaves extra remote processes and memory resident.

**Evidence:** \`activity\_guard\` is held across \`child.wait()\` and dropped here. \`ClientGuard::drop\` sends \`ActivityEvent::Disconnected\`, and \`wait\_for\_idle\_timeout\` starts a new full timeout when the active count reaches zero. The backend independently uses \`SHUTDOWN\_TIMEOUT = 5 \* 60 \* 1000\`, while \`buildAgentHostSpawnCommand\` defaults \`--idle-timeout\` to 300 seconds, proving the two periods are now serialized rather than concurrent.

**Suggested direction:** Track the client-idle deadline separately from the backend veto: suppress shutdown while the backend is running, but when it exits, honor the already-elapsed client deadline instead of treating backend exit as a new client disconnect.

### 2. [low] Cancel output readers when the server exits

**Finding ID:** `PERF-FF58A71FD622`  
**Location:** <code>cli/src/tunnels/agent\_host.rs:379</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** pending Tokio tasks and inherited stdout/stderr pipe handles  
**Scaling:** Each backend restart can add one reader task and two pipe readers that survive as long as an old descendant keeps the pipes open.  
**Outcome:** retained memory and file descriptors that grow across restart generations  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Output reading and process-state cleanup shared one task, so descendant-held pipes could strand one reader but also kept \`running\` populated and blocked additional backend generations.  
**Changed behavior:** The changed reader now owns only an output prefix and the pipes, with no cancellation, while a separate waiter clears \`running\` on parent-process exit and permits another backend and reader to start.  
**Confidence:** 0.96 — The task and pipe ownership plus restart path are explicit, and the added test proves the trigger; only production frequency is uncertain.

**Causal diff evidence:** Added line 379 replaces the reader's prior manager/process-cleanup ownership with an output-only prefix; together with the added independent child waiter, this leaves the pipe reader alive after \`running\` is cleared.

A long-lived supervisor whose sessions leave descendants holding inherited output pipes accumulates a task and pipe handles on each idle-shutdown/reconnect cycle, eventually creating FD and memory pressure.

**Evidence:** The changed reader loops until both pipes close without a join handle or cancellation signal. The adjacent comment says descendants can keep the pipes open after server exit, and the added test creates such a lingering child. The separate waiter clears \`running\`, making repeated generations reachable.

**Suggested direction:** Signal or abort the reader when the owning child exits, optionally after a bounded drain period, so pipe readers from an old generation cannot survive into the next.
