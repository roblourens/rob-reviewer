**Relevant issue families:** boundary-fanout, concurrency-burst, cache-lifecycle

### Scenario 1: Scheduled or manually queued publish-enabled product build on main/release/\*, with the default Windows, Linux, Alpine, Web, Quality, Copilot, Publish, source-analysis, and APIScan work

- Critical path: Platform build jobs and artifact publication remain the pipeline's critical path; release, when enabled, waits for Publish and ApproveRelease. The diff only selects dedicated Windows/Linux agent pools before these unchanged jobs execute.
- Scaling input: The default matrix has two Windows CLI jobs, three Linux CLI jobs, four Alpine jobs, one Web job, the full platform builds, and independent quality/security/publish jobs. Template expansion and job count are unchanged by the diff.
- Effective concurrency: Stages with dependsOn: \[\] can queue concurrently, and jobs within those stages retain their prior Azure Pipelines scheduling. The diff changes the target pool for each eligible job but adds no jobs, Promise/task fan-out, limiter, serialization, or dependency edge.
- Cache behavior: The existing Cache&#64;2 keys, cache-hit branches, artifact reuse, and publish retry/idempotency files are unchanged. Changing the agent pool can affect transient machine warmth, but repository evidence does not establish a persistent cache miss or invalidation mechanism; service-backed cache keys remain the same.
- Mechanism confidence: High confidence that pool selection changes and that job/boundary cardinality do not; all changed templates and their call sites were inspected.
- Magnitude uncertainty: Actual publishing-pool capacity, machine image warmth, and queue duration are external to the repository. Without evidence that they are worse, these unknowns cannot establish an actionable regression.
- Expensive boundaries:
  - other expensive boundary at <code>build/azure-pipelines/product-build.yml:181-191 and pool assignments throughout the changed stages</code>: Allocate an Azure Pipelines agent for each eligible Windows/Linux job from the new publishing pool; cardinality: One allocation per existing job; effective job cardinality is unchanged, with multiple independent jobs queued in parallel for a default product build.
    - Introduced by diff: true; previous behavior: The same jobs and concurrency requested agents from 1es-windows-2022-x64 or 1es-ubuntu-22.04-x64.; critical-path effect: Agent queueing precedes every affected job, but there is no repository evidence that the dedicated pools have lower capacity or slower machines, so a queue-time regression is not established.
  - network at <code>build/azure-pipelines/{alpine,linux,win32,web} templates and build/azure-pipelines/product-publish.yml</code>: Restore dependencies/caches, fetch secrets and toolchains, upload build artifacts/CDN data, and publish processed artifacts; cardinality: Existing per-job operations across the unchanged build matrix; cache hits continue to suppress the same dependency-install work.
    - Introduced by diff: false; previous behavior: Identical network operations ran on the legacy pools with the same per-job cardinality and ordering.; critical-path effect: These calls remain on each job's build/publish path, but the diff neither adds calls nor increases retries, payloads, or item fan-out.
  - subprocess at <code>build/azure-pipelines/alpine/product-build-alpine.yml, alpine/product-build-alpine-cli.yml, linux/product-build-linux-cli.yml, win32/product-build-win32-cli.yml, and web/product-build-web.yml</code>: Run npm, gulp, Rust compilation, archive, signing, Docker, and platform build commands; cardinality: Existing fixed command sequences per matrix job; no command or loop was changed.
    - Introduced by diff: false; previous behavior: The same subprocesses ran in the same jobs on the prior default pools.; critical-path effect: Compilation and packaging dominate job runtime, but their placement and multiplicity are unchanged; only their agent pool is parameterized.
- Verdict: No reportable regression. The PR reroutes an unchanged workload to dedicated publishing pools without code evidence of extra work, lower concurrency, cache defeat, or a slower critical path.

### Scenario 2: CI or publish-disabled run, including callers of the parameterized templates from product-build-template.yml and product-build-ado-ci.yml

- Critical path: The same existing compilation/test jobs remain on the standard pools because VSCODE\_USE\_PUBLISHING\_POOLS is false, while external template callers omit the new optional parameter and receive its legacy default.
- Scaling input: The job matrix depends on existing build parameters; the new parameter does not alter matrix size or command count.
- Effective concurrency: Unchanged stage/job parallelism and dependencies; every added template parameter has a default matching the formerly hard-coded pool.
- Cache behavior: Unchanged cache services, keys, hit variables, and negative/failure behavior because these runs remain on the original pools.
- Mechanism confidence: High; all repository call sites of the changed templates were searched, and omitted parameters use legacy defaults.
- Magnitude uncertainty: None material for PR causality: pool names resolve to previous values in this scenario.
- Expensive boundaries:
  - other expensive boundary at <code>build/azure-pipelines/product-build.yml:181-191 and defaults in the six changed job templates</code>: Allocate standard-pool build agents; cardinality: One allocation for each pre-existing job.
    - Introduced by diff: false; previous behavior: The same jobs used the same standard Windows and Ubuntu pools.; critical-path effect: No change: these scenarios resolve to the exact previous pool names.
  - network at <code>build/azure-pipelines product job templates</code>: Existing dependency, secret, artifact, signing, and publication-service calls in transitive job templates; cardinality: Unchanged per job and per artifact.
    - Introduced by diff: false; previous behavior: Identical network calls and cache behavior.; critical-path effect: No changed placement or call count.
- Verdict: No performance change for CI/publish-disabled and legacy template callers.
