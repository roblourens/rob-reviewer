# Performance review: Skip content exclusion checks for apply\_patch Add File

[PR #337324](https://github.com/microsoft/vscode/pull/337324) at `aa4182aad5a51cf38261385237654b4457087628`

## Findings (1)

### 1. [medium] Batch Add File existence checks instead of serializing filesystem round trips

**Finding ID:** `PERF-BCA6EFA5D87E`  
**Location:** <code>extensions/copilot/src/extension/tools/node/applyPatchTool.tsx:291</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem-provider/extension-host IPC calls issued by vscode.workspace.fs.stat  
**Scaling:** The validation adds one awaited stat per distinct Add File section, and the nested for-loop serializes all N checks, so pre-edit latency grows as the sum of N filesystem-provider round trips.  
**Outcome:** increased apply\_patch latency and a longer blocked interval before any edits are emitted  
**PR causality:** <code>introduced</code>  
**Previous behavior:** For Add File entries, this loop previously called only assertFileNotContentExcluded. When content exclusions are disabled, BaseIgnoreService returns false immediately; it did not issue a workspace.fs.stat for each destination.  
**Changed behavior:** Each Add File destination is now synchronously existence-checked with await this.fileSystemService.stat(uri) before the loop can inspect the next file or construct and emit edits.  
**Confidence:** 0.96 — The changed line, multi-operation grammar, serial loop, production service registration, and workspace.fs delegation are all directly traced. Exact provider latency and typical scaffold size vary, which affects severity but not the serial N-round-trip mechanism.

**Causal diff evidence:** Added RIGHT line 291 introduces \`await this.fileSystemService.stat(uri)\` inside the loop over all commit file changes; the pre-diff code proceeded directly to the exclusion check and contained no existence-stat boundary on Add File destinations.

A realistic agent scaffold that adds many files in a remote workspace or through a non-local filesystem provider waits for every destination stat in series before showing any edit. For N added files, users pay N provider/IPC latencies on the tool's critical path even though the checks are independent.

**Evidence:** The patch grammar explicitly permits one or more file operations and commit.changes retains one entry per distinct path. invoke builds fileChanges from all entries, then line 291 awaits stat inside the per-file loop. Production registers VSCodeFileSystemService, whose stat implementation directly returns vscode.workspace.fs.stat(uri), establishing the expensive provider boundary. No cache, grouping, or concurrency limiter coalesces these destination checks, and workspace edits are only constructed after this entire validation loop.

**Suggested direction:** After preserving the current allowedEditUris checks, validate Add File destinations with bounded parallel workers (or a provider batch API if one exists), retain results in fileChanges order, and then throw for the first existing target before emitting edits. This preserves all-or-nothing validation while reducing critical-path latency from the sum of N round trips to bounded batches.
