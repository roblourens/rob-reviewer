# Performance review: bring back custom location migrations

## Findings (1)

### 1. [medium] Show the migrations view before awaiting its refresh

**Finding ID:** `PERF-CAFE7B65D70A`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts:298</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** filesystem discovery and agent-host session-state/IPC waits performed by the migration refresh  
**Scaling:** The delay grows with cold prompt-file discovery and agent-host readiness; the remote source-folder provider can wait up to its 2-second first-snapshot timeout, while additional enabled categories add parallel discovery/provider work whose slowest operation gates navigation.  
**Outcome:** blocked migration-page navigation and increased perceived latency after clicking any affected setting's deprecation link  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The link passed \`migrationCategory: ConfiguredLocations\`; \`startCustomizationMigration(categoryId)\` entered and rendered that category immediately, allowing the existing loading state to appear while the editor's background refresh completed.  
**Changed behavior:** The link now omits \`migrationCategory\`, so \`startCustomizationMigration()\` follows the overview branch, which awaits \`refreshCustomizationMigrationInfo()\` before calling \`showCustomizationMigrationDashboard()\`. That refresh computes every enabled category, lists prompt files, and queries source folders before the migration view is shown.  
**Confidence:** 0.98 — The changed argument deterministically selects the awaited branch, the prior argument deterministically selected the immediate-render branch, and the transitive refresh boundaries and 2-second cold readiness bound are explicit in repository code. Actual delay varies with cache/session warmth, which affects severity rather than mechanism confidence.

**Causal diff evidence:** The added \`arguments: \[{ migration: true }\]\` at line 298 replaces the category-specific argument. This selects the no-category branch in \`showCustomizationMigrationPage\`, whose first operation is \`await this.refreshCustomizationMigrationInfo()\`, unlike the prior category branch that renders immediately.

On a cold agent-host session or uncached prompt discovery, clicking “Migrations tab” in any of the five deprecation messages can leave the user on the previous UI for up to the remote snapshot wait (plus discovery time) before the migrations page appears.

**Evidence:** \`OpenEditor\` awaits \`pane.startCustomizationMigration(migrationCategory)\`. With the changed undefined category, \`showCustomizationMigrationPage\` awaits the complete refresh before preparing the migration view. \`computeCustomizationMigrationInfo\` awaits all enabled \`computeMigration\` calls; those call \`listPromptFiles\`, and then \`provideSourceFolders\`. For the agent-host provider, \`provideSourceFolders\` awaits \`whenCustomizationsReady\`, which explicitly permits a cold first-snapshot wait up to 2000 ms. The editor already starts this refresh in the background, so the diff primarily moves that existing expensive work onto the click-to-page critical path rather than adding useful prerequisite work.

**Suggested direction:** Enter the migration view and render its loading state before awaiting the refresh, then update the dashboard when the refresh settles; keep the desired generic dashboard destination without gating first paint on discovery.
