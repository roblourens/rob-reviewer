## Performance regression fixes detected (2)

### 1. boundary-fanout

**Fix location:** `build/lib/screenshotDiffReport.ts:522` (`RIGHT`)  
**Blamed base line:** `build/lib/screenshotDiffReport.ts:523`  
**Introducing path:** `build/lib/screenshotDiffReport.ts`  
**Introducing commit:** `d97705790f3ac6cc63a6e95530f6c0c9c7ace7e2`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `network`  
**Confidence:** 0.98

**Mechanism:** Unbounded Promise.all fan-out performed one remote image download plus one local image read and full-image comparison for each changed fixture before report-label filtering.

**Symptom:** Screenshot-diff CI incurred avoidable network/I/O latency, PNG allocation/CPU, and an aggregate request burst proportional to changed animated or flaky fixtures that were ultimately omitted.

**Fixed behavior:** Filters diff.changed to screenshot-labeled entries before computePixelDiffs, eliminating the HTTPS download, local PNG read, decode, allocation, and pixel scan for every excluded changed fixture.

**Evidence:** Before this PR, main passed every changed manifest entry to computePixelDiffs. That helper maps every entry through Promise.all, issuing one HTTPS GET for the baseline image and one filesystem read for the local PNG, then decodes and walks every pixel. generateMarkdown filtered animated/flaky entries only afterward, so excluded changes paid all boundary and CPU costs despite never appearing in the report. The added filter at head line 522 narrows the input before that call.

### 2. repeated-work

**Fix location:** `src/vs/workbench/test/browser/componentFixtures/editor/findWidget.fixture.ts:119` (`LEFT`)  
**Blamed base line:** `src/vs/workbench/test/browser/componentFixtures/editor/findWidget.fixture.ts:119`  
**Introducing path:** `src/vs/workbench/test/browser/componentFixtures/findWidget.fixture.ts`  
**Introducing commit:** `96baba2cc4d3cf49b48492b5be4c67cc588241a8`  
**Mechanism family:** `repeated-work`  
**Performance category:** `latency`  
**Confidence:** 0.96

**Mechanism:** A fixed 300 ms real-time wait was repeated for each Find widget fixture variant on render and screenshot-capture paths.

**Symptom:** Full fixture capture and individual Find fixture loads were delayed by 300 ms per render; the two fixtures across their default two theme variants contributed four unnecessary waits.

**Fixed behavior:** Returns immediately after constructing and revealing the Find widget instead of keeping each fixture render pending on an additional 300 ms timer.

**Evidence:** The removed base line awaited a 300 ms timer at the end of renderFindWidget after state.change. The function is the render callback for both Find and FindAndReplace, each normally expanded to Dark and Light variants, so full capture paid the fixed wait once per rendered variant even though the fixture adapter already states that component-explorer waits two animation frames after synchronous render. The PR makes the callback synchronous and deletes this delay.
