# Performance review: Honor useTsgo in web TypeScript extension

[PR #337765](https://github.com/microsoft/vscode/pull/337765) at `f706499fa25da3980f5e55c6ecd08925fb762f45`

## Findings (1)

### 1. [medium] Dispose conditions when replacing the web client

**Finding ID:** `PERF-2B109428F1D9`  
**Location:** <code>extensions/typescript-language-features/src/extension.browser.ts:71</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** workspace/editor event listeners, retired TypeScriptServiceClientHost graphs, and provider registrations  
**Scaling:** After a JS/TS document activates the client, every normal→Tsgo→normal cycle leaves another set of conditional-feature listeners rooted by global VS Code events; later configuration/editor events fan out linearly with the number of mode switches and can recreate registrations from every retired instance.  
**Outcome:** retained memory and increasing event-dispatch/provider work over a long-lived web extension host  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The browser extension created one normal TypeScript client registration for its lifetime, so switching experimental.useTsgo did not repeatedly construct and retire client feature registrations.  
**Changed behavior:** The added top-level conditionalRegistration now disposes and recreates the normal client branch whenever experimental.useTsgo or the native extension condition flips.  
**Confidence:** 0.98 — The new branch recreation path is explicit, the global listener ownership gap is visible in dependentRegistration.ts, and the activated host's nested global Conditions are directly traced through LanguageProvider and ATA. The exact bytes retained per cycle are unmeasured, which limits severity, but the retention and linear growth mechanism do not depend on timing or an external service.

**Causal diff evidence:** RIGHT line 71 wraps the browser client in a mode-switching conditionalRegistration; its false branch constructs the client and all nested language-feature conditional registrations anew on each re-entry.

In a web session where a developer tries Tsgo, switches back, and repeats while JS/TS is open, each cycle retains another disposed TypeScript client/provider graph and adds callbacks to common configuration/editor events. Memory and callback/provider work continue growing until the extension host is reloaded.

**Evidence:** An activated host creates two standard LanguageProviders, whose formatting, copy/paste, code-lens, and tag-closing registrations create Conditions backed by vscode.workspace/window events; registerAtaSupport adds another. Condition calls onUpdate(...) without retaining the returned Disposable, and ConditionalRegistration.dispose() disposes only state.registration, not its conditions or condition.onDidChange subscriptions. Therefore disposing the new branch cannot detach these globally rooted listeners; their callbacks retain each ConditionalRegistration's doRegister closure and disposed client, and a later condition change can call update() and install a registration again after disposal.

**Suggested direction:** Make Condition own the Disposable returned by onUpdate, make ConditionalRegistration own and dispose both its conditions and onDidChange subscriptions, and prevent update() after disposal before relying on this registration for a recreatable client branch.

### Scenario 3: Toggle experimental.useTsgo between normal and Tsgo modes after a JS/TS client has activated

- Critical path: A configuration event synchronously evaluates the outer conditions, disposes the normal store (including killing the worker), and registers the alternate branch. Returning to normal mode immediately sees the already-open supported document, awaits workspace preload, and starts a fresh worker.
- Scaling input: Number of completed mode-toggle cycles, multiplied by two standard LanguageProviders and their nested conditional features; remote preload cardinality is eligible GitHub workspace-folder count per normal re-entry.
- Effective concurrency: Each outer condition update is synchronous. On normal re-entry, folder preloads fan out concurrently and worker startup follows them; separate user-driven toggle cycles are sequential.
- Cache behavior: Each normal re-entry creates fresh local preloaders, so their \_preload promises are cold; downstream remote API caching is unknown. More importantly, global event subscriptions from nested Conditions are not released, so retired registrations accumulate rather than being invalidated.
- Mechanism confidence: High for branch recreation, worker teardown/startup, and leaked global listeners; high uncertainty only in downstream preload cost.
- Magnitude uncertainty: Users normally toggle an experimental setting infrequently, and the remote API may cache loaded contents; this keeps repeated boundary work from supporting a separate high-confidence finding.
- Expensive boundaries:
  - network at <code>extensions/typescript-language-features/src/extension.browser.ts:110 startPreloadWorkspaceContentsIfNeeded</code>: Reinvoke loadWorkspaceContents through a newly created preloader on normal-mode re-entry; cardinality: One call per eligible GitHub virtual workspace folder per normal-mode re-entry when a supported document remains open

- Verdict: Reported the unbounded listener/client retention: nested Conditions do not release global subscriptions when the new recreatable branch is disposed, so memory and event work grow per cycle. Repeated preload/worker work is intentional to restore normal mode and lacks enough downstream cost evidence for a separate finding.

### Scenario 4: Dispose the normal branch while remote workspace preload is still pending

- Critical path: Disposal marks lazilyActivateClient as disposed and disposes current preload watchers; the in-flight remote API promise may finish, but the added guard prevents forcing TypeScript client/worker construction afterward.
- Scaling input: Eligible remote workspace folders with unresolved preload calls at the moment of a mode switch or extension shutdown.
- Effective concurrency: In-flight folder preloads remain concurrent; no replacement worker is started by their completion after disposal.
- Cache behavior: The disposed loader's in-flight promise is not canceled, but its result cannot activate the retired client. No additional cache state is retained through that branch.
- Mechanism confidence: High: isDisposed is set synchronously and checked before lazyClientHost.value.
- Magnitude uncertainty: The remote API exposes no cancellation contract, so whether the underlying fetch itself can be stopped is unknown.
- Expensive boundaries:
  - network at <code>extensions/typescript-language-features/src/extension.browser.ts:174</code>: Already-started loadWorkspaceContents calls may complete after disposal; cardinality: At most one in-flight call per eligible folder for that disposed loader
    - Introduced by diff: false; previous behavior: Preload could also be in flight during extension disposal; the old callback would force lazy client creation when it completed.; critical-path effect: Off the retired branch's critical path after disposal; completion is ignored for activation.
- Verdict: The added guard improves cleanup behavior and introduces no regression.
