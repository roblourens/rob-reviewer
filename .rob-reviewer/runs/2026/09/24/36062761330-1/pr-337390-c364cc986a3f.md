# Performance review: Persist full Codex command output across chat reloads

[PR #337390](https://github.com/microsoft/vscode/pull/337390) at `c364cc986a3f1f8c029a287412f490fed45ec70c`

## Findings (2)

### 1. [high] Reject oversized output before encoding it

**Finding ID:** `PERF-54289029FC89`  
**Location:** <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:3633</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU work and a UTF-8 buffer proportional to the complete command output  
**Scaling:** The synchronous encoding and temporary allocation grow linearly with the command's full output size, with no bound before encoding; outputs above 10 MiB pay the entire cost and are then discarded.  
**Outcome:** blocked agent-host event loop, delayed command completion publication, and memory/GC pressure for very large command output  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Command completion reused the already-accumulated output string and published it directly; it did not synchronously create a second full UTF-8 representation before mapping the completion.  
**Changed behavior:** Every output above the 80,000-character retention threshold is synchronously converted with VSBuffer.fromString before the 10 MiB database limit is checked, including output that can never be retained.  
**Confidence:** 0.99 — The synchronous call order, unbounded accumulated string, allocation, and post-allocation rejection are directly visible in the changed call path. Exact stall duration depends on output size and machine memory, but the mechanism and linear scaling are certain.

**Causal diff evidence:** Added RIGHT line 3633 performs \`VSBuffer.fromString(output)\` before added RIGHT line 3634 rejects \`content.byteLength &gt; MAX\_TERMINAL\_OUTPUT\_BYTES\`; this full-output encoding did not exist before the PR.

A command that prints a large log or file (for example, tens or hundreds of MiB) now blocks all agent-host notification processing while allocating another full copy, only to reject it afterward; completion and other chats can visibly stall and the extra allocation can trigger heavy GC or OOM pressure.

**Evidence:** \_dispatchItemCompleted calls \_retainCommandOutput synchronously before firing ChatToolCallComplete. The changed line invokes VSBuffer.fromString(output), while the next line is the first MAX\_TERMINAL\_OUTPUT\_BYTES check. Codex output is accumulated without a size cap in mapCommandExecutionOutputDelta via \`entry.output += params.delta\`, so the input to this conversion is not bounded by the database limit.

**Suggested direction:** Check \`output.length &gt; MAX\_TERMINAL\_OUTPUT\_BYTES\` before any encoding (UTF-8 cannot be shorter than the JS code-unit count), then use a non-allocating byte-length check for remaining multibyte cases and only create the VSBuffer for output that will actually be stored.

### 2. [medium] Batch retained-output deletion for reverted turns

**Finding ID:** `PERF-2D02F6B5C334`  
**Location:** <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:6545</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** serialized SQLite DELETE mutations and their filesystem transaction work  
**Scaling:** The awaited rollback cost grows with every commandExecution in the removed turn suffix, not with the smaller set of commands that actually retained output; N commands produce N serialized database mutations.  
**Outcome:** increased rollback latency and excessive database/filesystem I/O on long chats  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After the single app-server thread/revert or thread/rollback request completed, truncateChat returned without issuing per-command SQLite mutations.  
**Changed behavior:** The new cleanup collects every removed command id and awaits Promise.all of deleteTerminalOutput calls. SessionDatabase routes each call through one turn-usage sequencer and a separate SQLite DELETE, so the apparent Promise.all is effectively N serial mutations.  
**Confidence:** 0.97 — The changed loop cardinality, awaited call path, SQL operation, and sequencer-enforced serialization are explicit. The exact delay varies by chat length and storage speed, which affects severity but not the mechanism.

**Causal diff evidence:** Added RIGHT line 6545 fans the removed command-id collection into one awaited \`deleteTerminalOutput\` call per command; before this diff no local deletion boundary existed on truncateChat.

Reverting a long Codex chat with hundreds of shell commands now waits for hundreds of separate SQLite DELETE operations—even when most commands had inline output and no row to delete—delaying completion of the user’s rollback action.

**Evidence:** \_deleteRetainedCommandOutputs builds toolCallIds from all commandExecution items, then the changed line invokes deleteTerminalOutput once per id. sessionDatabase.ts implements deleteTerminalOutput as one \`DELETE FROM terminal\_outputs WHERE tool\_call\_id = ?\` through \`\_mutateTurnUsage\`; that helper serializes all operations on \`\_turnUsageSequencer\`. truncateChat awaits this helper after the remote revert, placing all mutations on its critical path.

**Suggested direction:** Add a bounded bulk database operation that deletes all supplied tool-call ids in one transaction/statement (or deletes retained outputs by the reverted turn ids), and await that single cleanup operation after the app-server rollback.

- Effective concurrency: Item notifications execute serially on the agent-host event loop. Accepted database writes are serialized with other turn-data operations by the session database sequencer; separate commands may queue multiple writes but do not execute them concurrently within one database.
- Cache behavior: No output-size or encoding cache exists. Every qualifying completion performs the check and encoding once. Database/open-reference reuse may make warm storage access cheaper, but it does not avoid serialization.
- Mechanism confidence: Very high: the changed code performs full synchronous encoding before its only 10 MiB rejection, while command deltas accumulate without a cap.
- Magnitude uncertainty: Exact event-loop stall and GC cost depend on output size and host memory; commands printing tens or hundreds of MiB are realistic, and no protocol-side bound was found.
