### Scenario 1: Cold GitHub authentication with Copilot, Codex, and Claude providers active

- Critical path: The authenticate RPC fans out to matching providers with Promise.allSettled and completes only after Copilot/Codex account or MCP endpoint resolution and Claude proxy acquisition finish. Copilot's restricted-telemetry resolution is fire-and-forget, but Copilot SKU and Codex MCP endpoint discovery are on the authentication critical path.
- Scaling input: Number of distinct credentials, not turns, tools, models, or providers. A normal authentication has one Copilot-scoped credential.
- Effective concurrency: Provider authentication runs in parallel. Per-token CAPI discovery is promise-coalesced; Claude proxy binding is shared by its acquire lifecycle. There is no per-provider network fan-out for the same token.
- Cache behavior: Cold cache performs one discovery. Successful entries remain usable for 30 minutes and concurrent callers coalesce. 401/403 invalidates the exact client; endpoint changes invalidate all cells. Non-auth failures remain retryable, while successful metadata is read from the existing cell.
- Mechanism confidence: High: authentication fan-out, shared promise cache, and network call are directly traced.
- Magnitude uncertainty: Actual network duration varies by GitHub endpoint, but the effective request count and critical-path placement are established.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/shared/copilotApiService.ts:\_buildClientForToken</code>: GET /copilot\_internal/user to discover CAPI endpoints and raw entitlement metadata; cardinality: One request per effective GitHub token on a cold cache; concurrent Copilot and Codex consumers share the same IClientRequest promise.
    - Introduced by diff: false; previous behavior: Cold changed-token Copilot and Codex authentication already resolved data through the same per-token CAPI client cache and performed this discovery.; critical-path effect: Codex authentication awaits endpoint discovery; Copilot authentication awaits SKU resolution. The shared request therefore gates cold authentication once, not once per provider.
  - other expensive boundary at <code>src/vs/platform/agentHost/node/claude/claudeProxyService.ts:ClaudeProxyService.start</code>: Acquire or bind the loopback Claude HTTP proxy; cardinality: One shared runtime acquisition for the active Claude credential; concurrent acquires share the proxy server lifecycle.
    - Introduced by diff: false; previous behavior: Claude authentication already started the proxy for a new token; the diff adds stale-completion guards without adding starts.; critical-path effect: Claude authentication awaits the proxy handle before completing.
- Verdict: No reportable regression: the diff preserves one effective cold discovery and adds race/lifecycle guards rather than additional fan-out.

### Scenario 2: Warm unchanged-credential forwarding and proactive authentication refresh

- Critical path: Most repeated token forwarding is suppressed by the workbench's per-connection AgentHostAuthTokenCache. If an unchanged token reaches a provider, Copilot and Codex now consult the shared CAPI entry before authentication completes.
- Scaling input: Distinct host connections and credential refreshes; it does not scale with turns or tools. Successful network refresh is bounded to once per token per TTL.
- Effective concurrency: Same-token requests are deduplicated in the workbench and, if multiple connections still forward concurrently, coalesced by the service's per-token promise.
- Cache behavior: Warm success is memory-only. Refresh-window callers share one promise. Failed discovery can be retried on reauthentication, which is the intended recovery behavior; no successful request is repeated per provider.
- Mechanism confidence: High for cache behavior and boundaries.
- Magnitude uncertainty: The prevalence of unchanged-token RPCs from multiple connections is uncertain, but client deduplication and server coalescing bound effective network cardinality.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/shared/copilotApiService.ts:\_getEntryForToken</code>: Refresh /copilot\_internal/user when the per-token entry enters its refresh window or prior discovery failed; cardinality: Zero calls for a warm entry outside the five-minute refresh window; at most one coalesced call for concurrent consumers when refresh is needed.
    - Introduced by diff: true; previous behavior: Codex reused its cached MCP configuration and Copilot returned early for an unchanged credential, so those exact provider methods did not initiate a retry. Other CAPI consumers still refreshed the same entry when needed.; critical-path effect: A refresh-window miss or retry is awaited by authentication; ordinary warm forwarding resolves from memory.
- Verdict: No actionable regression: the newly reachable network retry is bounded, coalesced, and specifically enables recovery after failed discovery; ordinary warm authentication adds only map/promise work.

### Scenario 3: Turn, tool, usage, hang, and forwarded SDK telemetry attribution

- Critical path: Turn dispatch captures an account context, and terminal/tool telemetry reads its copilotSku getter while constructing existing telemetry payloads. This work is not on model-network dispatch beyond small synchronous map/time checks.
- Scaling input: Number of active turns and telemetry events. Each context retains a token reference, a cache-cell reader, and a small closure until existing turn/tool cleanup.
- Effective concurrency: One captured context per tracked turn plus existing per-tool timing references; tool trackers reuse the turn context rather than creating per-tool CAPI requests. Concurrent turns remain independent and perform no network work through the getter.
- Cache behavior: Getters read only the existing cache cell; they do not launch discovery. Captured cells are invalidated on rejected credentials, endpoint changes, and service disposal. Turn and tool maps already remove entries on completion/session cleanup.
- Mechanism confidence: High: all added context capture/read call paths are synchronous and their cleanup owners are visible.
- Magnitude uncertainty: Exact telemetry-event volume varies by turn, but payload growth is one bounded SKU string and context objects are tied to existing lifecycle owners.
- Expensive boundaries: none found
- Verdict: No reportable CPU, serialization, or retention regression; added work is bounded metadata propagation with existing lifecycle cleanup.

### Scenario 4: GitHub enterprise endpoint switch while providers and caches are live

- Critical path: The endpoint event synchronously invalidates CAPI cells and provider credential generations. Copilot asynchronously clears credentials and requests a client restart; Claude releases its proxy handle; Codex clears its proxy token and model state. Subsequent authentication performs discovery against the new endpoint.
- Scaling input: Endpoint-change events, normally rare configuration transitions, not sessions or turns. Session reconciliation scales with existing Codex sessions only when the credential generation changes.
- Effective concurrency: Provider listeners run independently. Copilot subprocess restarts are coalesced, CAPI in-flight results cannot repopulate invalidated cells, and stale Claude proxy startups dispose their late handle.
- Cache behavior: All per-token CAPI cells are invalidated on endpoint change; old captured readers become empty. New authentication creates a fresh endpoint-specific entry and concurrent consumers share it.
- Mechanism confidence: High: listener, invalidation, restart coalescing, and stale-completion guards are directly traced.
- Magnitude uncertainty: Provider-specific cleanup duration varies, but event cardinality is rare and cleanup prevents more costly stale-resource use.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_requestClientRestart/\_applyPendingClientRestart</code>: Stop the Copilot SDK client subprocess so startup-baked endpoint configuration is replaced; cardinality: One coalesced stop/restart request per endpoint change; pending restart reasons are merged and cleared synchronously before stop.
    - Introduced by diff: false; previous behavior: Endpoint changes already called \_restartClientIfStartupConfigChanged and restarted the client when the enterprise host changed. The new credential-clear request coalesces into the same pending restart.; critical-path effect: Restart is deferred past active turns and runs asynchronously from the endpoint event; a later Copilot use recreates the client.
  - other expensive boundary at <code>src/vs/platform/agentHost/node/claude/claudeAgent.ts endpoint-change listener</code>: Release the refcounted loopback Claude proxy handle; cardinality: At most one active handle is disposed for the provider on each endpoint change.
    - Introduced by diff: true; previous behavior: Claude retained the existing proxy handle across endpoint changes.; critical-path effect: Cleanup is asynchronous from configuration notification and prevents use of retired credentials; next authenticated use reacquires the shared proxy.
  - network at <code>src/vs/platform/agentHost/node/shared/copilotApiService.ts:\_buildClientForToken</code>: Discover endpoints after reauthentication on the new GitHub host; cardinality: One coalesced request for the new credential/endpoint cache generation.
    - Introduced by diff: false; previous behavior: Discovery occurred when a token first needed a client, but the old base cache could preserve endpoint-derived state; the diff ensures endpoint-specific invalidation.; critical-path effect: Subsequent authentication waits for new-endpoint discovery; the configuration change itself does not issue the request.
- Verdict: No performance finding: added cleanup is bounded to rare endpoint changes, and the existing expensive Copilot restart remains coalesced and off active-turn critical paths.

### Scenario 5: Late provider registration during an in-flight authentication request

- Critical path: Provider registration starts authentication replay in the background. Replay now waits for matching current authentication requests to settle before replaying stored credentials; normal provider lookup and dispatch do not await the replay promise.
- Scaling input: Number of simultaneously pending authentication resources during rare late provider initialization, normally one Copilot resource.
- Effective concurrency: Pending requests are awaited together with Promise.all. New replacements are observed by the loop; there is no duplicate concurrent replay of the superseded credential.
- Cache behavior: After the wait, replay reads the latest stored, unexpired token. CAPI work reached by replay uses the same per-token coalescing cache.
- Mechanism confidence: High for the wait and its non-critical placement.
- Magnitude uncertainty: An unusually slow external authentication can prolong background replay, but provider use is not gated by \_authenticationReplays.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/agentHostAuthenticationService.ts:replay</code>: Wait on the already-running provider authentication/discovery promise; replay itself does not launch an additional boundary call until the authoritative request completes; cardinality: One wait per currently pending matching resource snapshot; replacements wake waiters, which then observe the latest request. Subsequent replay invokes provider authentication once per stored resource.
    - Introduced by diff: true; previous behavior: Replay immediately iterated stored tokens and could race an in-flight replacement instead of waiting for the authoritative request.; critical-path effect: Registration and normal provider availability remain synchronous; only background replay and orderly shutdown await completion.
- Verdict: No reportable latency regression because the new wait is background lifecycle coordination and avoids duplicate/stale authentication work rather than blocking provider dispatch.
