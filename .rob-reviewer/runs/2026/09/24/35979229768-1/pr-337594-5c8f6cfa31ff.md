## Findings (1)

### 1. [low] Evict Agent Merge observables when chats are removed

**Finding ID:** `PERF-C0B6CBE46FD3`  
**Location:** <code>src/vs/sessions/browser/sessionAgentMerge.ts:20</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Per-chat observable graphs, configuration-event wrappers, provider observables, and chat URI keys  
**Scaling:** Retained objects grow linearly with the number of distinct chats that have been active during a session, including chats later removed; the outer WeakMap is collectible only when the entire session is released.  
**Outcome:** Long-lived multi-chat sessions accumulate retained objects and eventually incur higher memory and GC pressure as chats/subagent chats churn.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The cache held one Agent Merge state observable and one configuration observable per session, so chat creation/removal did not increase retained cache entries.  
**Changed behavior:** The new nested Maps cache a separate state/configuration observable for each chat URI, while neither this helper nor the provider's matching \`\_agentMergeSessionStateObservables\` Map removes a key when that chat disappears; cleanup is only performed when the whole session is removed.  
**Confidence:** 0.96 — The changed cache shape, insertion path, chat-removal lifecycle, and whole-session-only cleanup are directly visible. Exact memory per chat is small and workload-dependent, which is why severity is low, but retention and linear growth with chat churn are certain.

**Causal diff evidence:** The added \`WeakMap&lt;ISession, Map&lt;string, ...&gt;&gt;\` declarations at lines 19-20 replace the previous single observable per session with history-keyed per-chat Maps; added \`byChat.set(chatCacheKey(...))\` then retains each distinct chat entry.

Opening Agent Merge UI surfaces for a sequence of peer or tool-created chats and then removing those chats leaves one client state observable, one derived configuration observable (including its global configuration event wrapper), and one provider observable cached per historical chat until the session itself is discarded.

**Evidence:** \`setCached\` inserts every non-main chat under \`chat.resource.toString()\` into both nested Maps. There is no deletion path in this module. The provider similarly stores each chat in \`\_agentMergeSessionStateObservables\` at \`baseAgentHostSessionsProvider.ts:4769\`, and only deletes the entire per-session map in \`\_removeCachedSession\` at line 6997; chat metadata removal updates the live chat collection without pruning these caches.

**Suggested direction:** Tie both cache layers to chat lifecycle: use a weak cache keyed by the live \`IChat\` object where possible, and prune provider URI entries whenever the session's chat metadata removes a chat (retaining only the \`''\` session-folder entry and currently live chat URIs).
