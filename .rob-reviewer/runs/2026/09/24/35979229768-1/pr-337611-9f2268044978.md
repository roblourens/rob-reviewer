The diff only adds the originating requestId to the existing token and DTO; it adds no await or boundary call.
- Scaling input: One short request identifier per tool invocation. Cost scales linearly with the number of tool calls already made by the agent, with constant additional payload per call.
- Effective concurrency: Unchanged; tool calls retain the model/tool service's existing scheduling. The new field introduces no queue, mutex, limiter, or burst.
- Cache behavior: No cache lookup is added on this propagation path. Cold and warm behavior differ only in pre-existing agent/model/tool caches; the requestId is directly copied.
- Mechanism confidence: High: the conversion, opaque token propagation, DTO construction, and preparation context were traced end to end.
- Magnitude uncertainty: Request IDs are expected to be short call identifiers; exact serialized-byte overhead varies by identifier length but remains one field per existing call.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/common/extHostLanguageModelTools.ts: invokeTool</code>: Send the existing tool invocation DTO between the extension host and workbench; cardinality: One existing IPC round trip per tool invocation; the diff adds one string field to that payload and does not add a round trip.
    - Introduced by diff: false; previous behavior: The same tool invocation crossed IPC with sessionResource and optional workingDirectory but without requestId.; critical-path effect: The existing IPC is on the tool invocation critical path, but the incremental serialization/allocation is constant-sized.
- Verdict: No reportable regression. The diff adds only constant payload and property-copy work to an existing IPC call.

### Scenario 2: A running named subagent invokes another named subagent, including parallel sibling subagents

- Critical path: The nested runSubagent call performs constant-time caller lookup and allowlist validation, resolves the requested agent/model, collects existing instructions/hooks, then invokes the default agent. Successful nested agent execution is on the parent tool call's critical path; this PR intentionally restores that workflow where the old caller lookup rejected valid chains.
- Scaling input: Nested chain depth is bounded by RUN\_SUBAGENT\_MAX\_NESTING\_DEPTH=5 per session. Parallel cardinality is the number of model-issued sibling runSubagent calls; each active request contributes one map entry.
- Effective concurrency: Sibling subagents may run concurrently as before. The new map neither serializes nor increases sibling concurrency; entries are keyed per request so caller resolution remains constant-time.
- Cache behavior: Model preparation continues to use the pre-existing \_resolvedModels per-tool-call cache. The new \_runningSubagents state is active-lifetime state rather than a cache and is deleted in the invokeAgent finally block on success, failure, or cancellation settlement.
- Mechanism confidence: High: changed map lifetime, nested caller lookup, depth cap, and invokeAgent call path were directly inspected.
- Magnitude uncertainty: Exact sibling concurrency and model latency depend on generated tool calls and provider response times, but map cardinality and nesting bounds are explicit.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts: RunSubagentTool.invoke</code>: Invoke the extension-host chat agent for each accepted nested subagent request; cardinality: One existing agent invocation per accepted runSubagent call, with chain depth capped at 5; parallel siblings retain model-selected cardinality.
    - Introduced by diff: false; previous behavior: The same boundary existed for runSubagent. In valid B-to-C chains the buggy top-level allowlist could reject the call before this boundary; the diff intentionally allows the requested product workflow to execute.; critical-path effect: Each accepted nested agent must complete before its runSubagent tool result completes.
  - network at <code>extensions/copilot/src/extension/intents/node/toolCallingLoop.ts: ToolCallingLoop</code>: The invoked Copilot/default agent performs its normal language-model request(s); cardinality: Per accepted subagent and its bounded tool-calling loop; the PR does not change loop limits or request scheduling.
    - Introduced by diff: false; previous behavior: Agent model requests already occurred for accepted runSubagent calls; invalid caller resolution prevented some intended nested calls from reaching them.; critical-path effect: Model responses dominate nested-agent latency and are required for the restored nested workflow.
- Verdict: No reportable regression. Additional work only occurs when a formerly broken but allowed nested workflow now proceeds; bookkeeping is O(active subagents), constant-time per call, and cleaned deterministically.

### Scenario 3: A nested runSubagent call omits agentName and copies the calling subagent's model, tools, instructions, and hooks

- Critical path: The call looks up the running caller, shallow-copies its tool enablement map because the child mutates depth/tool restrictions, reuses the already-resolved model, merges global and agent hooks, and invokes the same agent. Model and agent invocation boundaries already existed for no-name copies.
- Scaling input: At most one shallow copy over registered tool enablement entries per copied subagent. Agent hooks scale with explicitly configured hook commands and nested depth, which is capped at 5.
- Effective concurrency: Nested copies execute through the existing parent tool call; parallel top-level branches remain possible and unchanged. Hook commands are executed serially by the existing ChatHookService per hook event.
- Cache behavior: The inherited resolved model bypasses repeated auto-model/custom-agent discovery on the warm nested path. The copied metadata is retained only while the child agent runs and is deleted in finally.
- Mechanism confidence: High: the shallow copy, inherited model fast path, hook merge without accumulation, max depth, and serial command executor were inspected.
- Magnitude uncertainty: Tool-map size and user hook duration vary. Hook commands may be slow, but their execution is explicit configured behavior required by making the child a true copy rather than accidental repeated work.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/common/tools/builtinTools/runSubagentTool.ts: RunSubagentTool.invoke</code>: Invoke the extension-host agent for the copied subagent; cardinality: One existing invocation per no-name runSubagent call; depth capped at 5.
    - Introduced by diff: false; previous behavior: A no-name call already invoked an agent, but incorrectly copied top-level rather than calling-subagent configuration.; critical-path effect: Required and unchanged for the child subagent to execute.
  - subprocess at <code>extensions/copilot/src/extension/chat/vscode-node/chatHookService.ts: ChatHookService.executeHook</code>: Execute inherited frontmatter hook commands such as SubagentStop/PreToolUse; cardinality: One serial subprocess per configured command for each applicable hook event in the copied subagent; nesting is capped at 5, while Pre/PostToolUse follows that subagent's existing tool-call count.
    - Introduced by diff: true; previous behavior: No-name nested copies omitted the calling subagent's frontmatter hooks, so those configured commands did not run for the copy.; critical-path effect: Configured hooks are awaited and can add their configured command duration to the child agent's path.
  - network at <code>extensions/copilot/src/extension/intents/node/toolCallingLoop.ts: ToolCallingLoop</code>: Perform the copied agent's normal model request(s); cardinality: Existing per copied subagent/tool loop; no additional model invocation is introduced by inheriting the correct model.
    - Introduced by diff: false; previous behavior: The no-name child already ran a model, but could resolve a different top-level/default model.; critical-path effect: Required for subagent progress and unchanged in count.
- Verdict: No reportable performance regression. The only newly reached subprocess work is the intentional execution of explicitly configured hooks for a child that now correctly copies its caller; hooks are not duplicated or accumulated across generations, and nesting is bounded.
