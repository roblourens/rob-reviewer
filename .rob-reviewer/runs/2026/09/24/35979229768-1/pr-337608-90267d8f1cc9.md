## Findings (1)

### 1. [medium] Avoid walking checkpoint history with one Git process per ref

**Finding ID:** `PERF-08588E034D55`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostCheckpointService.ts:290</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Sequential \`git rev-parse\` subprocesses plus a full checkpoint-ref database read  
**Scaling:** For a checkpoint in repository R, cost grows with the number of session checkpoint refs since R was last active; a first checkpoint in a newly used repository scans the entire session checkpoint history. Multi-folder capture repeats this per repository, serially.  
**Outcome:** Increased end-of-turn checkpoint latency and Git process churn, delaying the post-checkpoint Session Changes refresh and reducing host throughput.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Checkpoint capture fetched only the immediately previous checkpoint ref and then performed the existing single parent \`revParse\`; it did not probe every older session checkpoint ref.  
**Changed behavior:** When the immediately previous session checkpoint does not exist in the current repository, the new reverse loop awaits \`revParse\` for each older ref until one happens to exist there.  
**Confidence:** 0.99 — The changed loop, the session-wide checkpoint table ordering, and AgentHostGitService.revParse's \`\_runGit(... \['rev-parse', ...\])\` implementation directly prove sequential subprocess fan-out. The exact number of intervening turns varies by workflow, which affects severity but not the mechanism.

**Causal diff evidence:** Added line 290 places \`await this.\_gitService.revParse(repositoryRootUri, checkpointRef)\` inside a reverse loop over every value returned by \`getAllCheckpointRefs()\`.

In a realistic multi-folder session where users alternate chats or spend many turns in another checkout, switching back can make checkpoint completion and the Changes surface wait on dozens of serial Git invocations; a repository first used late in a long session scans every prior checkpoint.

**Evidence:** \`SessionDatabase.getAllCheckpointRefs()\` returns all checkpoint refs ordered over the whole session, without repository identity. \`\_getRepositoryParentRef\` walks that list in reverse and awaits each probe. \`AgentHostGitService.revParse\` invokes \`\_runGit\` with \`git rev-parse --verify --quiet\`, so a chat returning to repo A after N turns in other folders executes up to N+1 Git subprocesses before checkpoint capture can continue. Capture itself is serialized by the per-session sequencer, and the turn-end contribution refreshes Session Changes only after this checkpoint promise settles.

**Suggested direction:** Persist/index the latest checkpoint ref per repository (or resolve all candidate refs in one batched Git invocation) so parent lookup is O(1) boundary calls per repository while preserving repository-specific ancestry.


## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:4683` (`RIGHT`)  
**Blamed base line:** `src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:4664`

**Mechanism family:** `eager-work`  
**Performance category:** `ipc`  
**Confidence:** 0.98

**Mechanism:** The row-height autorun read every chat's `_withDetails`-wrapped workspace, including offscreen rows; observing that wrapper acquires the chat's detailed state subscription, so opening/reconciling a large sessions list eagerly loaded details for all chats.

**Symptom:** Sessions-list height reconciliation caused unnecessary detail subscriptions and host traffic for offscreen chats, increasing list-load work with chat count.

**Fixed behavior:** The changed autorun reads session/chat workspaces only when `getRelativeTop` confirms the row is fully visible, and sizes offscreen rows without observing workspace details.

**Evidence:** The deleted unconditional workspace reads were inside a loop over every collected chat row. `AdditionalChat.workspace` is wrapped by `_withDetails`, whose observation calls `_acquireDetails()`. The added visibility branch avoids those reads for offscreen rows; `getRelativeTop` returns null outside the fully visible viewport. Blame identifies the base line as introduced by the prior chat-folder presentation change.

- Effective concurrency: Checkpoint work is serialized per session by a sequencer; \`\_getRepositoryParentRef\` awaits every Git probe sequentially. Session repository diffs use a shared limiter of four and static recomputes coalesce same-key pending requests.
- Cache behavior: Baseline refs are reused. There is no repository-indexed cache for the latest applicable checkpoint; every non-immediate parent miss rereads all checkpoint refs and reprobes them. Static recompute requests coalesce, and prior changeset state supports incremental tracked-edit computation only in single-chat fallback paths.
- Mechanism confidence: High: database ordering, loop placement, subprocess implementation, serialization, and refresh sequencing are all explicit.
- Magnitude uncertainty: Typical sessions may have few intervening turns, but switching back after tens of turns in other folders or first using a repository late in a session produces the proven linear subprocess walk.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/sessionDatabase.ts:getAllCheckpointRefs</code>: Read all session checkpoint refs from SQLite in row order; cardinality: Once for turn numbering and, after an immediate repository miss, once again for parent lookup; result size grows with completed checkpointed turns
