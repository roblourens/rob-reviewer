**Relevant issue families:** repeated-work, synchronous-ui-work, cache-lifecycle, boundary-fanout, eager-work

### Scenario 1: Open, search, and switch groups in Agents/Skills/Instructions/Hooks customization lists

- Critical path: Initial section progress awaits IAICustomizationItemsModel.whenSectionLoaded; once loaded, search and tab/tree switching only regroup in-memory items and update the virtualized object tree.
- Scaling input: Number of customization files in the active section; tab layout renders one effective group while tree layout models all visible groups.
- Effective concurrency: One section load is awaited by setSection; observable updates are serialized on the UI thread, and no new per-item asynchronous work is started by the diff.
- Cache behavior: The items model owns section loading and its observable result; the redesign does not change its keys or invalidation. Switching groups reuses allItems and performs no reload.
- Mechanism confidence: High confidence that the new work is local collection/DOM-tree work and adds no boundary fan-out.
- Magnitude uncertainty: Repositories can contain many customization files, but the changed grouping work is linear and virtualized; no evidence shows a material increase over the prior full-list/card regrouping.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationListWidget.ts:setSection</code>: Load the selected customization section through IAICustomizationItemsModel.whenSectionLoaded.; cardinality: One model section load per section selection, with subsequent group switches and searches served from the observable item array.
    - Introduced by diff: false; previous behavior: The same setSection path awaited the same model load before this redesign.; critical-path effect: The initial section render waits for this load; tab selection and filtering do not.
- Verdict: No reportable regression: the diff changes presentation and replaces list contents, but does not increase load cardinality or move filesystem work onto group switching.

### Scenario 2: Open/search Plugins, switch User/Workspace/Available tabs, and browse the plugin marketplace

- Critical path: Opening the page filters installed/provider items and may load one marketplace snapshot; a typed search is delayed and then waits for one marketplace request plus one provider fetch before rendering results. Tab switches are local.
- Scaling input: Installed plugins, remote provider items, and returned marketplace entries; effective network cardinality is per refresh/search request, not per plugin.
- Effective concurrency: CancellationTokenSource replaces stale marketplace requests; search is delayed, and provider plus marketplace work is not multiplied by the new tabs. Rendering is serialized on the UI thread.
- Cache behavior: PluginMarketplaceSnapshotModel coalesces the home snapshot through uninitialized/loading/loaded/failed states. Browse/search requests replace stale requests; the redesign preserves these behaviors.
- Mechanism confidence: High confidence in request cardinality and cancellation; medium confidence in upper-bound installed-plugin cardinality.
- Magnitude uncertainty: Very large plugin inventories make the new scope partitioning more expensive, including an O(n²) includes-based partition, but realistic cardinality and the small operation do not establish a material user-visible regression.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/pluginListWidget.ts:queryMarketplaceSnapshot/queryMarketplace/queryPluginSearch</code>: Fetch marketplace plugins.; cardinality: At most one current snapshot or search request; results serve the entire Available group.
    - Introduced by diff: false; previous behavior: The pre-diff cards used the same marketplace fetch, cancellation, and snapshot model.; critical-path effect: Marketplace results wait on the request; installed-plugin tabs do not.
  - other at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/pluginListWidget.ts:getRemotePluginItems</code>: Fetch remote customization-provider plugin items.; cardinality: One provider fetch per refresh/search, not per displayed plugin.
    - Introduced by diff: false; previous behavior: The same provider fetch was already performed by filterPlugins/search before the presentation redesign.; critical-path effect: Plugin refresh/search waits for the provider result before committing the combined list.
- Verdict: No finding: no new network fan-out or eager request was introduced, and the local regrouping cost is insufficiently material for a performance issue.

### Scenario 3: Open/search MCP Servers and switch active agent sessions or MCP groups

- Critical path: The widget synchronously rebuilds current installed/group models on service or active-session changes; marketplace visibility/search may await one gallery request. Group switching itself is local.
- Scaling input: Current local/runtime/session MCP servers plus current gallery results; render cost grows linearly with current entries.
- Effective concurrency: Refresh notifications are handled serially; gallery requests use cancellation and loading guards. No loop introduces per-server network or IPC calls.
- Cache behavior: Gallery snapshot state and CancellationTokenSource prevent duplicate current requests. The new installedEntryOrder map retains historical row keys for the widget lifetime, but each entry is only a string/number and the evidenced session-switch scale does not support a material regression.
- Mechanism confidence: High confidence that the map retains historical keys and that active-session changes refresh it; low confidence that realistic lifetime cardinality is large enough for user-visible memory impact.
- Magnitude uncertainty: The number of distinct transient MCP row IDs encountered over a long-lived editor is unknown; retained map entries are tiny and cleared when the widget is disposed.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts:queryGallerySnapshot/queryMcpSearch</code>: Fetch MCP marketplace snapshot/search results.; cardinality: One guarded snapshot or one current search request for the whole Available group.
    - Introduced by diff: false; previous behavior: The prior card layout invoked the same gallery methods and guards.; critical-path effect: Only marketplace availability/search waits for this request; installed group rendering does not.
- Verdict: No finding: request cardinality is unchanged, tree rebuilds replace prior card/list rebuilds, and the only unbounded-looking retention is too small and lifetime-scoped to meet the reporting threshold.

### Scenario 4: Search, expand/collapse, enable, and browse Tools groups

- Critical path: Search and expand/collapse synchronously recompute group entries and replace the object-tree model; browsing waits for one extension-gallery query and manifest filtering.
- Scaling input: Tool sets plus visible tools in expanded sets; gallery filtering scales with the first result page after one gallery query.
- Effective concurrency: UI tree updates are serialized. Gallery searches cancel the prior request; manifest reads use Promise.all over one returned page, matching the pre-existing browse flow.
- Cache behavior: No new cache is introduced for tree rows. Gallery requests are cancellation-scoped; warm in-memory tool-set updates avoid marketplace work unless browse mode is explicitly entered.
- Mechanism confidence: High confidence in the local O(sets + expanded tools) rebuild and unchanged boundary behavior; medium confidence in comparative DOM cost versus prior list splices.
- Magnitude uncertainty: Large tool inventories increase full-tree replacement cost on expansion, but the previous implementation also recomputed and re-spliced every section; repository evidence does not prove a material increase in rendered DOM work.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/toolsListWidget.ts:\_queryGallery/\_filterGalleryResults</code>: Query the extension gallery and resolve manifests for returned candidates.; cardinality: One gallery query per browse/search action, followed by at most one manifest resolution per candidate on the first page.
    - Introduced by diff: false; previous behavior: This marketplace flow and its Promise.all manifest filtering predate the redesigned tree.; critical-path effect: Browse results wait for query and manifest filtering; ordinary tool search, toggles, and expansion do not.
- Verdict: No reportable regression: expensive network work remains explicitly browse-only and coalesced, while the changed synchronous rebuild lacks evidence of materially worse cost than the prior all-section refresh.

### Scenario 5: Change customization toggle or list-layout experimental settings while customization pages are open

- Critical path: The configuration event synchronously rerenders currently instantiated row controls or rebuilds the current tree, then relayouts the widget.
- Scaling input: Rendered virtual-list templates and current tree entries, not every possible marketplace item; configuration changes are explicit and infrequent.
- Effective concurrency: All configuration callbacks execute serially on the UI thread; there are no subprocess, IPC, filesystem, database, or network operations on this path.
- Cache behavior: Virtualization bounds instantiated row toggles to rendered templates; disposed controls and listeners are owned by template/widget disposable stores.
- Mechanism confidence: High confidence that control recreation is bounded to instantiated templates and that disposal ownership is present.
- Magnitude uncertainty: Viewport size and current collection size vary, but this user-triggered setting path is not a hot interaction loop.
- Expensive boundaries: none found
- Verdict: No finding: synchronous work exists but is bounded and only triggered by explicit experimental-setting changes.
