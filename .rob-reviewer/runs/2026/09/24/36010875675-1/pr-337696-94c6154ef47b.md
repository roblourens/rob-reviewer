# Performance review: list: report list changes requested while rendering an element

[PR #337696](https://github.com/microsoft/vscode/pull/337696) at `94c6154ef47b214c5711acaf0142ecae08ddb1d9`

## Findings (1)

### 1. [low] Build renderer labels only when a violation is reported

**Finding ID:** `PERF-E81EBD09743F`  
**Location:** <code>src/vs/base/browser/ui/list/listView.ts:1056</code> (<code>RIGHT</code>)  
**Performance category:** <code>gc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** short-lived diagnostic string objects and their interpolation CPU work  
**Scaling:** One label allocation per row render and, when present, one per row disposal; cost grows with rows crossing the viewport during scrolling and with visible rows replaced by splices, rerenders, or layout changes.  
**Outcome:** increased CPU/GC pressure on list rendering and scrolling  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Renderer callbacks were invoked directly, so ordinary rendering, disposal, and scrolling did not construct callback-name strings or retain callback tracking state.  
**Changed behavior:** Every rendered or disposed row now eagerly constructs a diagnostic label and assigns/restores callback state, even though almost all callbacks never trigger a report and \`supportDynamicHeights\` lists can never report one.  
**Confidence:** 0.97 — The scroll call path is explicit: \`onScroll\` calls \`render\`, which calls \`insertItemInDOM\`/\`removeItemFromDOM\` for rows crossing the viewport, and the added template literals execute directly before each renderer callback. The reporter explicitly returns for dynamic-height lists, proving these allocations are unused there. Exact frame-time magnitude depends on row churn and renderer cost, so severity is low rather than the mechanism being uncertain.

**Causal diff evidence:** RIGHT line 1056 newly evaluates \`renderElement(${item.templateId})\` before every \`renderer.renderElement\` call; the same added interpolation appears for each disposal at lines 671 and 1136.

Rapid scrolling or replacing visible rows in long lists now creates avoidable short-lived strings on the rendering critical path, increasing allocation/GC pressure and the chance of scroll jank; chat and notebook dynamic-height lists pay the cost even though this diagnostic is disabled for them.

**Evidence:** \`ListView\` is the virtual scrolling engine. \`onScroll\` invokes \`render\`; the render-range loops invoke \`insertItemInDOM\` and \`removeItemFromDOM\` once for each row entering/leaving the viewport. The added wrappers eagerly interpolate \`item.templateId\` into fresh \`renderElement(...)\` / \`disposeElement(...)\` strings. Over a traversal of R rows this adds about R render-label allocations plus up to R disposal-label allocations, and viewport replacement/splice work scales similarly with the affected visible rows. \`reportChangeDuringRendererCallback\` normally returns because there is no nested change, and always returns when \`supportDynamicHeights\` is true, yet the labels have already been allocated. Dynamic-height consumers include chat and notebook lists.

**Suggested direction:** Track the callback kind and template id without formatting (for example, separate primitive fields) and construct the human-readable label only inside the first reporting branch. Also bypass tracking entirely for dynamic-height lists and once \`didReportChangeDuringRendererCallback\` is set, while preserving nested callback restoration.

- Magnitude uncertainty: The exact allocation/GC cost depends on scroll distance, row height, renderer cost, and template-id length. The per-row allocation and synchronous critical-path reachability are certain, but DOM renderer work may dominate in many lists, supporting low severity.

- Verdict: Reportable low-severity regression: the diff adds eager short-lived string allocation per row on a global UI hot path, although labels are only consumed on the rare first nested change.

### Scenario 2: Scrolling dynamic-height chat and notebook lists

- Critical path: A scroll event synchronously performs the standard render and then \`\_rerender\` height reconciliation before the viewport update completes. Added labels in \`insertItemInDOM\` and \`removeItemFromDOM\` are on this UI critical path.
- Scaling input: Visible and newly exposed chat messages, notebook cells, settings rows, or profile rows; cost grows with row churn over the session.
- Effective concurrency: Height reconciliation and row churn are serialized on the UI thread; each affected row is processed sequentially.
- Cache behavior: Dynamic-height measurements cache widths/heights per item, but the new callback-label work in normal insert/remove paths is not cached. The reporter always exits when \`supportDynamicHeights\` is true, so labels created by those paths cannot produce a report.
- Mechanism confidence: High: chat and notebook enable \`supportDynamicHeights\`, while \`reportChangeDuringRendererCallback\` unconditionally returns for that option after the wrapper has already allocated its label.
- Magnitude uncertainty: Dynamic-height consumers and the disabled-report condition are established; the number of row crossings and resulting GC impact varies with notebook/chat length and scrolling behavior.
- Expensive boundaries: none found
- Verdict: Reportable as part of the same allocation finding because these important consumers pay per-row diagnostic allocation despite being categorically excluded from reporting.

### Scenario 3: Reporting a renderer-triggered list mutation

- Critical path: A renderer-triggered splice, height update, or nested render constructs \`BugIndicatingError\` and synchronously invokes unexpected-error handling while the original renderer callback remains on the UI stack. - Scaling input: Number of distinct ListView instances that encounter a renderer-induced list change, not number of rows or repeated violations within one instance.

- Cache behavior: The diagnostic is negatively coalesced only per list instance by \`didReportChangeDuringRendererCallback\`; separate lists can each report once. Error telemetry deduplicates equal events in a five-second buffer before flushing.
- Mechanism confidence: High for the synchronous handler and delayed telemetry paths; lower magnitude concern because they run only after an actual renderer-induced list mutation and once per instance.
- Magnitude uncertainty: The known triggering pattern is realistic, but repository-wide prevalence and logger backend latency are unknown. Once-per-instance coalescing bounds the cost.

- Verdict: No separate finding: the synchronous work is bounded to one report per affected list and is the intentional diagnostic behavior; the delayed telemetry boundary is coalesced and off the render critical path.
