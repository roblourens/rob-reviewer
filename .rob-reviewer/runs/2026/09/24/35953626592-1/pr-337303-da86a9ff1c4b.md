# Performance review: sessions: add image previews to reference hovers and align all artifact type behavior better

[PR #337303](https://github.com/microsoft/vscode/pull/337303) at `da86a9ff1c4be901882d172def0b935994b74efd`

## Findings (4)

### 1. [high] Check the image size before starting the preview read

**Finding ID:** `PERF-7BB65424D246`  
**Location:** <code>src/vs/workbench/browser/chatPills.ts:140</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Full file bytes, including Agent Host base64 IPC payloads and renderer buffers  
**Scaling:** The work and peak allocation scale with the actual resource size rather than the advertised 20 MB limit; an arbitrarily large image can be transferred and materialized before rejection.  
**Outcome:** Excessive I/O and peak memory can stall or terminate the renderer when an oversized reference is hovered.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Image-file references had a path-only hover, so hovering them did not read or transfer the referenced file.  
**Changed behavior:** The new hover immediately calls IFileService.readFile with a size limit, but FileService starts its stat validation and provider read concurrently.  
**Confidence:** 0.99 — The changed call, FileService ordering, and Agent Host provider implementation are directly traced. The only uncertainty is how often users hover unusually large image references, which affects severity prevalence rather than the mechanism.

**Causal diff evidence:** Added line 140 introduces the first filesystem read on the reference-hover path and relies on \`{ limits: { size: 20 MB } }\` as the safety boundary, even though that API starts the underlying read before the size validation finishes.

Hovering an oversized local, remote, or Agent Host image can still read the complete file before showing “Image preview unavailable.” Agent Host is especially costly because its provider performs resourceRead(Base64), so the full remote payload is transferred and decoded despite the cap.

**Evidence:** IFileService.doReadFileStream starts validateReadFile() and readFileUnbuffered() in parallel when no etag is supplied. The unbuffered path calls provider.readFile(resource) before validateReadFileLimits completes, and the Agent Host provider's readFile calls connection.resourceRead(..., Base64) without a cancellation token. On validation failure FileService consumes the already-started stream, so the 20 MB option does not bound this transfer.

**Suggested direction:** Resolve/stat the resource first, reject files above 20 MB, and only then start the cancellable read (or use a streaming provider path that enforces the byte limit before buffering).

### 2. [medium] Subscribe to GitHub details only while the rich hover is active

**Finding ID:** `PERF-555D8285C7F2`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionInputPills.ts:365</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub REST/GraphQL requests and API rate-limit budget  
**Scaling:** For N distinct references, opening the session creates O(N) initial requests. Every open issue then polls once per minute; each open PR keeps core polling once per minute plus checks every 15 seconds while pending or every five minutes otherwise.  
**Outcome:** Sustained excess network traffic, rate-limit pressure, and lower GitHub request throughput while the reference pills remain mounted.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Agent Host reference pills were built from recorded session metadata and GitHub session state and created no per-reference GitHub subscriptions.  
**Changed behavior:** Building the pill sections now calls the resolver for every issue and PR. Each resolver entry is retained for the whole session and subscribes at \`visible\` priority, including checks for every PR, even when the collection is collapsed and no hover is shown.  
**Confidence:** 0.99 — The per-reference construction path, subscription lifetime, queue behavior, and exact polling intervals are all directly established. Only the typical number of references per session is uncertain.

**Causal diff evidence:** Added line 365 creates a long-lived visible subscription for each issue reached from the newly added per-entry resolver calls; the adjacent added PR path creates equivalent core/checks subscriptions. Before the diff \`\_buildReferenceSections\` did not query GitHub.

A long-running session with several referenced issues/PRs continuously occupies the GitHub request queue just to keep hidden hover details current. The queue limits same-account concurrency to one, but it does not reduce request cardinality, so ten pending PR references can approach 3,600 checks/core polls per hour.

**Evidence:** The changed resolver subscribes issues at line 365 and PR core plus optional checks at lines 389-393, then explicitly refreshes both. GitHubQueryService polls open visible issues every 60 seconds; PullRequestResourceService polls visible open PR core every 60 seconds and pending checks every 15 seconds. The subscriptions are removed only when metadata drops the reference or the whole component is disposed.

**Suggested direction:** Create and dispose these subscriptions with the expanded row/hover lifetime, using recorded metadata while collapsed. If row enrichment is required, use one-shot batched/background hydration and avoid retaining visible polling interests for hidden details.

### 3. [medium] Bound or defer commit metadata requests

**Finding ID:** `PERF-D1BC9B8714B4`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionArtifacts.ts:419</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Concurrent GitHub HTTP requests, response objects, and API rate-limit budget  
**Scaling:** Opening a session launches one request concurrently for every distinct commit target in the artifact/reference collections, so request count and in-flight work grow linearly with commit history.  
**Outcome:** A network burst and rate-limit pressure can reduce throughput for other GitHub operations when large session histories are opened.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Commit pills used the recorded label/hash and did not issue GitHub requests when artifact/reference sections were observed.  
**Changed behavior:** SessionGitHubCommitResolver starts getCommit immediately on first \`get\`; section construction calls \`get\` for every commit while the toolbar evaluates its sources, before a dropdown or hover is opened.  
**Confidence:** 0.98 — The eager call path and absence of a limiter in GitHubApiClient are explicit. Exact user-visible delay depends on session commit count and network latency, but the unbounded burst mechanism is deterministic.

**Causal diff evidence:** Added line 419 introduces the per-commit HTTP request; the newly added section loop reaches it for each distinct commit during normal toolbar rendering. The base behavior had zero commit metadata requests.

Opening an Agents session with many recorded commits sends all corresponding REST requests at once. GitHubApiClient forwards directly to IRequestService with caching disabled and has no request queue or concurrency limit on this path.

**Evidence:** sectionsFor iterates all filtered artifacts and calls commitResolver.get(...).read(reader); added line 419 immediately invokes GitHubService.getCommit. That service performs one \`/repos/{owner}/{repo}/commits/{sha}\` request, and GitHubApiClient contains no limiter/coalescing across distinct targets. ChatInputPills evaluates every source's hasData to render the toolbar, so this runs while the pill collection is collapsed.

**Suggested direction:** Defer commit resolution until the relevant dropdown/hover is opened, or route collection hydration through a bounded shared request queue; retain the per-target cache for coalescing duplicate SHAs.

### 4. [medium] Reuse the loaded preview across hover reopenings

**Finding ID:** `PERF-2D7965DAA87C`  
**Location:** <code>src/vs/workbench/browser/chatResourcePill.ts:76</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Filesystem reads, remote/Agent Host transfers, and full image byte buffers  
**Scaling:** Cost grows with both image byte size and the number of times the user reopens the singleton reference hover; rapid reopenings can overlap provider reads that do not support cancellation.  
**Outcome:** Repeated preview latency, bandwidth consumption, and allocation/GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A singleton image reference displayed only its location, so reopening its hover performed no filesystem I/O.  
**Changed behavior:** The WeakMap caches only an element factory. ManagedHoverWidget invokes that factory on every show, and the factory creates a fresh preview whose initialization reads the full resource each time.  
**Confidence:** 0.98 — The managed-hover lifecycle and downstream read call are explicit. Provider-level caching may reduce disk cost for some schemes, but remote and Agent Host providers still cross their boundary on every invocation.

**Causal diff evidence:** Added line 76 changes the singleton image pill from a static location hover to a per-show factory that creates a new filesystem-backed preview.

Repeatedly hovering the same remote image rereads up to 20 MB on every opening. The thumbnail LRU does not avoid this boundary call because its cache key and lookup are reached only after readFile has returned the bytes.

**Evidence:** ManagedHoverWidget.update calls \`content.element(token)\` for each show and cancels it on hide. Added line 76 constructs a new createChatPillImagePreview each invocation; that helper immediately calls fileService.readFile. The only shared cache is getOrCreateImageThumbnail in chatImagePreview.ts, downstream of the full read.

**Suggested direction:** Cache/coalesce the completed preview data or thumbnail for the entry's visible lifetime, keyed by resource version and invalidated on file changes, so reopening does not reread unchanged bytes.
