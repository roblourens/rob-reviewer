**Relevant issue families:** repeated-work, cache-lifecycle, boundary-fanout, missing-coalescing, cleanup-lifecycle

### Scenario 1: First message sent from a new local or remote agent-host session

- Critical path: The send waits for draft configuration/eager creation, loads the chat model, dispatches the message through IChatService, then awaits \_refreshSessions/listSessions and resolves the committed session from the cache or a session-added event. The diff keeps the post-send listSessions boundary on the critical path but replaces the former cache snapshot and full-cache fallback scan with an exact Map lookup.
- Scaling input: The session catalogue size controls refresh reconciliation cost. The removed Set construction and fallback scan previously added O(number of cached sessions) CPU/allocation per first send; the new exact lookup is O(1).
- Effective concurrency: A single send performs one awaited post-send refresh. Independent concurrent sends can still issue independent listSessions calls because \_refreshSessions is not coalesced, but that behavior predates the diff; removing the pre-send \_ensureSessionCache call can eliminate an additional cold-cache refresh rather than increase concurrency.
- Cache behavior: With a warm cache, the requested raw ID is checked directly after refresh. With a cold/uninitialized cache, the old code could start a pre-send refresh through \_ensureSessionCache and then start the existing post-send refresh; the new code only performs the post-send refresh. Empty and failed refresh behavior remains owned by the existing authoritative-cache and retry logic.
- Mechanism confidence: High: the changed hunk directly deletes the Set copy, fallback cache scan, and pre-send cache initialization while retaining the same post-send refresh call.
- Magnitude uncertainty: Catalogue sizes and local/remote round-trip durations vary, but the direction of the changed CPU, allocation, and boundary counts is non-increasing.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_sendNewSessionRequest</code>: Dispatch the first chat request to the selected agent-host-backed chat participant through IChatService.; cardinality: One dispatch per user first-send action.
    - Introduced by diff: false; previous behavior: The same IChatService.sendRequest call occurred before the diff.; critical-path effect: The message dispatch must complete before commitment waiting starts.
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_refreshSessions</code>: List all local agent-host sessions through the MessagePort-proxied IAgentConnection.; cardinality: One awaited post-send listing per first send; on an uninitialized cache the diff may remove one additional pre-send listing previously launched by \_ensureSessionCache.
    - Introduced by diff: false; previous behavior: The post-send listing was already present, and the old pre-send cache initialization could add another listing.; critical-path effect: The post-send listing must complete before the immediate exact cache check; otherwise the waiter continues via notifications.
  - network at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_refreshSessions</code>: List all sessions through the remote agent-host connection for a remote provider.; cardinality: One awaited post-send listing per remote first send, with the same possible reduction of a cold pre-send listing.
    - Introduced by diff: false; previous behavior: The same remote listSessions round trip was already performed after sending.; critical-path effect: The remote round trip remains on the commitment critical path exactly as before.
- Verdict: No reportable regression. The changed path reduces cache-sized CPU/allocation and may reduce cold-cache IPC/network work while preserving the existing mandatory send and refresh boundaries.

### Scenario 2: Concurrent first sends while same-type and archived sessions are discovered

- Critical path: Each send dispatches independently, performs its existing post-send catalogue refresh, then waits for only its own scheme/raw-ID match. Unrelated cached sessions and notification batches are inspected locally but no longer qualify through novelty fallback.
- Scaling input: Cost scales with the number of concurrent first sends and the number of sessions in each refresh result. Notification matching scales with the size of each added batch. The diff changes cache matching from a full catalogue scan (and potentially two event-array scans) to one exact cache lookup and one event-array find.
- Effective concurrency: For k concurrent sends, up to k chat dispatches and k post-send listSessions operations may overlap; there is no shared refresh coalescing in this path. This concurrency existed before the diff, and the removed pre-send initialization cannot increase it. Each waiter owns a DisposableStore that is released on exact match, cancellation, connection loss, or provider disposal.
- Cache behavior: Every waiter checks the refreshed cache by its own raw ID, so warm discoveries resolve immediately and unrelated positive cache entries are ignored. Misses remain pending for a matching notification; failed refreshes follow existing retry behavior. Removed claim and in-flight ID sets decrease temporary retained state.
- Mechanism confidence: High: the tests and production call flow establish independent waiters, exact ID matching, existing per-send refreshes, and deterministic listener disposal.
- Magnitude uncertainty: Large bursts of simultaneous drafts are uncommon and catalogue sizes are product-dependent, but neither uncertainty affects the before/after conclusion that no work or concurrency was added.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_sendNewSessionRequest</code>: Dispatch each first message to the agent host.; cardinality: One per concurrent send, so k dispatches for k independently initiated drafts.
    - Introduced by diff: false; previous behavior: The same per-draft dispatch fan-out existed before the diff.; critical-path effect: Each corresponding send must finish before that draft starts commitment matching.
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_waitForNewSession</code>: Refresh the full session catalogue with listSessions for each waiter.; cardinality: Up to k overlapping post-send listings for k concurrent sends; catalogue reconciliation is per listing.
    - Introduced by diff: false; previous behavior: Each waiter already called \_refreshSessions; the diff removes auxiliary pre-send cache initialization rather than adding refreshes.; critical-path effect: Each waiter awaits its own refresh before checking the cache and subscribing for later additions.
- Verdict: No reportable regression. Exact matching removes fallback scans and temporary ownership sets; existing uncoalesced per-send boundary fan-out is not introduced or materially amplified by this PR.

**Summary:** Completed the performance pass over all three changed files and all diff pages. The production change is performance-neutral to beneficial: it removes O(catalogue-size) snapshot/scan work, temporary ID retention, and a possible cold-cache refresh without adding boundary calls, eager work, or longer-lived resources. Test-only changes add bounded fixtures and assertions and do not affect product runtime.
