# Performance review: Remove the phase plan line from the HydraFusion workflow milestone

[PR #337563](https://github.com/microsoft/vscode/pull/337563) at `746f00f649e97ce0adff3123058055c69b3d5ade`

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** serialization-allocation, repeated-work

### Scenario 1: Live HydraFusion workflow selection milestone during an active chat turn

- Critical path: The SDK delivers one \`session.fusion\_resolved\` event, \`\_acceptFusionEvent\` synchronously calls \`CopilotFusionProgress.accept\`, constructs the milestone Markdown, and \`\_emitFusionProgress\` emits one \`ChatResponsePart\` action before the selected-workflow milestone can appear. The diff removes phase-plan map/localize/join work and shortens that action payload; it adds no work to this path.
- Scaling input: One accepted resolution per workflow/fusion ID. \`\_record(route:&lt;fusionId&gt;)\` suppresses duplicates, and realistic phase plans contain the workflow's small fixed set of phases (the fixture has three).
- Effective concurrency: Fusion events are handled synchronously through the event listener; there is no changed parallelism, queue, limiter, or fan-out. Duplicate resolution events are coalesced by the progress object's milestone set.
- Cache behavior: There is no external data cache on this path. The in-memory \`\_milestones\` set is the deduplication state; cold first delivery emits the milestone, while repeated delivery for the same fusion ID performs no milestone construction or transport. The diff does not alter invalidation or negative-cache behavior.
- Mechanism confidence: High: the changed hunk, deduplication guard, synchronous caller, and unchanged action emission are directly visible in the traced code.
- Magnitude uncertainty: The exact Markdown serialization and rendering savings depend on locale and plan length, but the direction is strictly reduced work and the plan cardinality is small.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts \`\_subscribeToSdkEvents\` / \`\_acceptFusionEvent\`</code>: Receive the SDK \`session.fusion\_resolved\` event from the Copilot runtime.; cardinality: One effective event per unique workflow resolution after \`\_record\` deduplication.
    - Introduced by diff: false; previous behavior: The same resolution event was received and processed once.; critical-path effect: The inbound event initiates milestone creation, but the diff neither adds nor moves this network boundary.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts \`\_emitFusionProgress\` -&gt; \`\_emitAction\`</code>: Emit one \`ChatResponsePart\` action containing the selected-workflow Markdown to the chat consumer.; cardinality: One action per accepted unique fusion resolution.
    - Introduced by diff: false; previous behavior: The same single action was emitted with the description plus a formatted phase-plan line.; critical-path effect: This action is required for the milestone to become visible. The diff keeps the same call count and sends fewer Markdown bytes because the phase-plan line is omitted.
- Verdict: No reportable regression. The production change eliminates bounded formatting/allocation work and reduces the existing action payload and rendered content without increasing frequency, retention, or boundary calls.

### Scenario 2: Cold and warm reconstruction of persisted chat history containing HydraFusion workflows

- Critical path: On a cold reconstruction, \`\_computeMappedEvents\` pages the persisted event log, then \`mapSessionEvents\` walks the event array and \`FusionReplayState.observe\` calls \`CopilotFusionProgress.accept\` for each Fusion event before reconstructed turns are returned. On a warm request, \`\_mappedEventsMemo\` reuses the reconstruction promise/result. The diff removes phase-plan formatting for each accepted persisted resolution and therefore shortens, rather than lengthens, the cold critical path.
- Scaling input: Total persisted session events N, with F accepted \`session.fusion\_resolved\` events after turn ownership and per-turn milestone deduplication. The removed work previously scaled with the sum of phase-plan lengths across F workflows; the changed code performs none of that work.
- Effective concurrency: Event-log pages are fetched sequentially by cursor and replay is serial over the event array. File-edit metadata is fetched once as a batch. The diff changes neither concurrency nor backpressure.
- Cache behavior: \`\_mappedEventsMemo\` coalesces concurrent reconstruction and serves warm requests per agent scope; rejected reconstructions are evicted for retry. During replay, progress state deduplicates milestones and resets at turn boundaries. The diff does not alter these cache keys, lifetimes, or miss behavior.
- Mechanism confidence: High: the memoization, paginated RPC loop, batched database read, serial replay, and changed milestone construction are directly traced.
- Magnitude uncertainty: Session history size and number of Fusion workflows vary, but every affected resolution now allocates and serializes less content; no plausible input reverses that direction.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts \`\_computeMappedEvents\`</code>: Read persisted SDK event-log pages through \`rpc.eventLog.read\`.; cardinality: One sequential RPC per page of up to 1000 events, approximately ceil(N/1000) on a cold reconstruction; zero additional reads for a warm memoized reconstruction.
    - Introduced by diff: false; previous behavior: Identical pagination and call count before the diff.; critical-path effect: Cold reconstruction waits for all pages before mapping. The changed milestone formatting occurs only afterward and does not introduce or increase these RPCs.
  - database at <code>src/vs/platform/agentHost/node/copilot/mapSessionEvents.ts \`mapSessionEvents\`</code>: Batch-load stored file-edit records with \`db.getFileEdits(editToolCallIds)\` when edit calls exist.; cardinality: At most one batched database call per cold mapping, independent of the number of Fusion phase-plan entries.
    - Introduced by diff: false; previous behavior: The same optional single batch read occurred before the diff.; critical-path effect: The batch can delay cold history mapping, but it is unrelated to the changed Fusion milestone content and its placement/cardinality are unchanged.
- Verdict: No reportable regression. Cold replay does less per-workflow string work and retains smaller response parts; warm-cache behavior and all expensive-boundary cardinalities are unchanged.

**Summary:** Completed the performance pass over the full two-file diff. The only production change removes a bounded phase-plan map/localization/join and its Markdown payload from live and replayed workflow milestones. No expensive boundary, fan-out, synchronous UI work, cache lifecycle, concurrency, or retention regression is introduced, and there is no evidenced shipped performance symptom warranting a regression-fix record.
