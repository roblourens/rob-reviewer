### 1. cleanup-lifecycle

**Fix location:** `src/vs/platform/actionWidget/browser/actionList.ts:1699` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/browser/chatDropdownPill.ts:375`  
**Introducing path:** `src/vs/workbench/browser/chatDropdownPill.ts`  
**Introducing commit:** `05ffe98d55ba4d22054b6f18366985bd0180d2dc`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `io`  
**Confidence:** 0.98

**Mechanism:** Refreshing an open action-list hover invokes the replacement entry's image content factory as a preservation probe. That factory immediately starts a cancellable fileService.readFile of up to 20 MiB; when the new element is not the one already attached, the pre-fix path discarded it without retaining or disposing its preview handle, so the read and subsequent image allocations could continue for every refresh.

**Symptom:** Live session/reference updates while an image row hover is open can leave rejected preview candidates doing unnecessary filesystem/remote-filesystem I/O and retaining their preview resources until completion.

**Fixed behavior:** The hover descriptor now exposes disposeContent, and ActionListWidget calls it whenever the factory-created preservation candidate is rejected; the image implementation disposes the candidate and cancels its read immediately.

**Evidence:** The base factory at chatDropdownPill.ts:375 creates createChatPillImagePreview on first invocation, whose implementation starts fileService.readFile with a 20 MiB cap. ActionListWidget.updateItems invokes that factory during preserveHover refreshes, and the new RIGHT line 1699 disposes a candidate when preservePanel is false. The added test verifies the rejected replacement token becomes cancelled. The introducing-line blame resolves to the image-preview change 05ffe98d55ba4d22054b6f18366985bd0180d2dc.

### 2. cleanup-lifecycle

**Fix location:** `src/vs/platform/hover/browser/updatableHoverWidget.ts:100` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/hover/browser/updatableHoverWidget.ts:93`  
**Introducing path:** `src/vs/editor/browser/services/hoverService/updatableHoverWidget.ts`  
**Introducing commit:** `85fb8cb6fd694d9f55eac35ab158ba5dbb6d7707`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `io`  
**Confidence:** 0.96

**Mechanism:** ManagedHoverWidget previously passed its target directly to the rendered HoverWidget, so disposal of that rendered widget did not notify ManagedHoverWidget.onDidHide and therefore did not cancel the CancellationTokenSource owned by an in-flight asynchronous content factory. Such factories include session-summary hover resolution that can activate providers and query session items.

**Symptom:** Closing a rendered managed hover through the hover UI could leave its async content computation running after the result was no longer visible, wasting I/O/CPU and retaining associated state until it completed or the managed-hover owner was later disposed.

**Fixed behavior:** The rendered hover now receives a wrapper target whose dispose callback invokes ManagedHoverWidget.onDidHide for the current widget, cancelling the in-flight content token as soon as that widget is dismissed.

**Evidence:** HoverWidget.dispose calls its target's dispose method; the base line passed this.target directly, which for HTMLElement-backed managed hovers had no callback to ManagedHoverWidget.onDidHide. The new wrapper calls onDidHide at RIGHT line 100, and the added hoverService test demonstrates the content token transitions to cancelled when the rendered hover is dismissed. ChatRichLink supplies a real async token-aware factory through SessionSummaryHoverService.
