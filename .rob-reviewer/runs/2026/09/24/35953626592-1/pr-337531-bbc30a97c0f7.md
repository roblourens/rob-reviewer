# Performance review: Revamp tabbed model picker UI card

[PR #337531](https://github.com/microsoft/vscode/pull/337531) at `bbc30a97c0f7a7d9dc162e3f542239067ffff5b9`

## Findings (2)

### 1. [medium] Coalesce configuration-driven card refreshes

**Finding ID:** `PERF-9E4B045C991E`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerTabbedWidget.ts:575</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** DOM nodes, controls, managed hovers, rendered descriptions, and allocations  
**Scaling:** Three full rebuilds per successful option choice; each grows with option, warning, action, description, and pricing content.  
**Outcome:** Higher input latency plus CPU and GC pressure from repeated synchronous DOM reconstruction.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The card rebuilt once in \`\_setValues\`; \`onDidAccept\` refreshed only the backing list, and no scoped listener independently refreshed the card.  
**Changed behavior:** One option save now invokes picker refresh from the synchronous scoped-change event, the card's existing completion render, and another picker refresh from \`onDidAccept\`.  
**Confidence:** 0.99 — The new listener, synchronous emitter, card \`finally\` render, and changed completion callback establish three card rebuilds without timing assumptions.

**Causal diff evidence:** Added line 575 changes \`onDidAccept\` from refreshing only the backing list to \`this.refresh()\`, which refreshes the mounted details card even though \`ModelCard.\_setValues\` has just rebuilt it; added line 159 also refreshes it from the same save's scoped-change event.

Choosing effort or context can jank because the mounted details subtree is reconstructed three times for one click.

**Evidence:** \`ChatModelConfigurationStore.\_applyLocalModelConfiguration\` synchronously fires \`onDidChange\` before persistence finishes. The new listener calls \`TabbedModelPicker.refresh\`, which calls \`\_getModelCard(...).refresh()\`. \`ModelCard.\_setValues\` then calls \`\_renderPreservingFocus\` in \`finally\` and invokes \`onDidAccept\`; line 575 calls \`refresh()\` and rebuilds the card again. \`\_render\` clears and recreates radios, actions, hovers, description content, banners, and pricing rows.

**Suggested direction:** Coalesce internal save notifications into one card rebuild; keep external-change refreshes, but make \`onDidAccept\` update only list/footer summaries or deduplicate the listener and completion refresh.

### 2. [low] Skip the second render of a newly created details card

**Finding ID:** `PERF-6477B80927FD`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerTabbedWidget.ts:605</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** DOM nodes, Radio and ActionBar controls, hover objects, rendered description nodes, and pricing rows  
**Scaling:** Paid once per distinct model inspected during each popup lifetime; each duplicate render grows with the model's options, messages, actions, description, and pricing metrics.  
**Outcome:** Increased details-opening latency and avoidable CPU/GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A newly created hover details card rendered once in its constructor and was mounted directly.  
**Changed behavior:** The first details opening for each inspected model constructs the complete card subtree and then immediately clears and reconstructs it before mounting the page.  
**Confidence:** 0.99 — Constructor rendering, the unconditional refresh, and the render method's full clear/recreate behavior are directly visible; only the exact milliseconds vary with card content.

**Causal diff evidence:** Added line 605 unconditionally calls \`card.refresh()\` immediately after \`\_getModelCard\`; for an uncached model, \`\_getModelCard\` has just run \`new ModelCard(cardOptions)\`, whose constructor already calls \`\_render()\`.

The first click into a model's details performs twice the necessary synchronous DOM/control construction, delaying page display and creating avoidable allocation/GC pressure.

**Evidence:** \`ModelCard\`'s constructor invokes \`\_render()\`. \`\_showModelDetails\` obtains that new card and immediately invokes \`refresh()\`, which calls \`\_renderPreservingFocus()\` and \`\_render()\` again. \`\_render()\` clears both card and header and recreates radio controls, action bars, managed hover, rendered description, warnings/promotions, and pricing rows. The former hover-card creation path returned a newly constructed card without this second render.

**Suggested direction:** Refresh only reused cached cards. Have \`\_getModelCard\` report whether it created the card, or move the freshness check into that method so a just-constructed card is not rendered again.
