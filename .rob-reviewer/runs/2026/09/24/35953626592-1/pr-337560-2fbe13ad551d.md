# Performance review: sessions: Add an External section and session import action

[PR #337560](https://github.com/microsoft/vscode/pull/337560) at `2fbe13ad551d5afd98e6db14625fa23aa38af2e7`

## Findings (1)

### 1. [medium] Avoid restoring full sessions just to import them

**Finding ID:** `PERF-B08EA723C1E3`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:1423</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Provider SDK chat materialization, full transcript reads/hydration, session-database reads, and retained turn objects  
**Scaling:** For a cold session the cost grows with its transcript and persisted session state; the new multi-selection action invokes this path once per selected external session at effective concurrency 1, so completion latency grows roughly with the sum of all selected sessions' restore times.  
**Outcome:** Import is blocked on unrelated provider and history hydration, causing avoidable action latency, I/O/CPU work, and memory/GC pressure; importing more than the 10-session residency limit can additionally restore and then immediately release earlier sessions.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, an unopened external session stayed as list metadata until the user actually opened or messaged it; no provider chat was materialized and no transcript was loaded merely to change ownership.  
**Changed behavior:** The new import request always awaits restoreSession before changing the registry ownership bit, even though Import neither opens the session nor sends a message. On a cold session restoreSession proceeds through exact metadata lookup, materializeChat, session-database hydration, provider getMessages for the full default-chat transcript, and retention in AgentHostStateManager.  
**Confidence:** 0.98 — The changed call and cold restore call graph are explicit, including provider materialization, full-message retrieval, database reads, and state retention. The exact-session metadata API already exists, so avoiding full hydration is bounded and does not require a shadow catalog. Provider-specific duration and typical transcript size affect severity, not the mechanism.

**Causal diff evidence:** The added line \`await this.restoreSession(session);\` places full provider/session hydration on every Import request before the added registry adoption call; this work did not exist for unopened external sessions before the PR.

Selecting Import on an unopened session can take as long as opening and hydrating that session; multi-selecting N external sessions serializes N such cold restores before the action reports completion.

**Evidence:** AgentService.restoreSession only short-circuits when AgentHostStateManager already contains the session. Otherwise \_restoreSessionState calls agent.getChatMetadata, agent.materializeChat, opens persisted metadata, calls provider.chats.getMessages, hydrates/interleaves every turn, and stores the resulting summary/turns. The provider already exposes the exact-session getChatMetadata path used by \_registeredSessionMetadata, and AgentSessionRegistry.adoptExternalSession itself only needs the registered identity and a database write. The UI action at sessionsViewActions.ts:966-967 loops selected sessions with await, making the cold cost cumulative.

**Suggested direction:** Validate the registered external session with the existing exact-session metadata lookup, adopt it in AgentSessionRegistry, and publish/update the surfaced summary without materializing the chat or loading turns. Keep restoreSession only for sessions that are actually opened; preserve the not-found check by rejecting when the exact metadata lookup confirms the provider session is gone.

### Scenario 2: Import one or multiple unopened external sessions

- Critical path: The action awaits each selected session in sequence. Each call crosses renderer-to-Agent-Host RPC, and a cold host session then must complete metadata lookup, provider chat materialization, persisted-state reads, full default-chat transcript retrieval/hydration, registry adoption, and the response before the next selected item starts.
- Scaling input: N selected sessions after filtering to external, import-capable, unarchived targets, plus each session's transcript size H\_i. Effective cost is approximately the sum of N cold restore costs and all H\_i; warm resident sessions skip most restore work.
- Effective concurrency: Exactly one import at a time because sessionsViewActions.ts awaits inside a for-of loop. Provider work within one restore has limited internal parallelism, but different selected sessions do not overlap. Residency reconciliation is sequenced and retains at most 10 ordinary sessions by default.
- Cache behavior: Warm AgentHostStateManager entries make restoreSession short-circuit after residency handling. Cold sessions materialize and retain full state; after the 10-session residency limit, earlier imports may be released while later ones restore. In-flight coalescing is per session and does not coalesce distinct selected sessions.
- Mechanism confidence: Very high confidence from the direct changed call to restoreSession and the traced cold restore path through materializeChat, persisted-state reads, getMessages, turn hydration, and state retention.
- Magnitude uncertainty: Provider materialization time and transcript sizes vary, but cold restores demonstrably perform heavyweight work and multi-selection makes latency cumulative.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:1415</code>: Send vscode/importSession and await its response; cardinality: One request per selected eligible session; no batching, effective concurrency 1.
    - Introduced by diff: true; previous behavior: No explicit Import request existed; unopened external sessions incurred no RPC merely to change ownership.; critical-path effect: Each response is awaited before the next selected session and before completion status is announced.
  - other expensive boundary at <code>src/vs/platform/agentHost/node/agentService.ts:1423 via restoreSession/\_restoreSessionState</code>: Resolve exact provider metadata, materialize the default chat, and fetch the full provider transcript; cardinality: For each cold selected session: one metadata lookup, one materialization, and one full getMessages retrieval; warm resident sessions skip these calls.
    - Introduced by diff: true; previous behavior: Provider materialization and history retrieval occurred when the session was actually opened/restored, not for a standalone ownership change.; critical-path effect: All provider work blocks that session's import response and therefore the serial multi-import action.
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts:\_restoreSessionState</code>: Read session metadata, chat backing, annotations, workspace transitions, and related persisted state during restore; cardinality: Multiple bounded persisted-state reads per cold imported session, with transcript-associated allocation scaling by history.
    - Introduced by diff: true; previous behavior: Unopened external sessions remained list metadata and did not hydrate their session databases.; critical-path effect: Required by restoreSession before registry adoption returns, despite Import not opening the chat.
  - database at <code>src/vs/platform/agentHost/node/agentSessionRegistry.ts:83</code>: Read and rewrite the AgentSessionRegistry ownership entry; cardinality: At least one registry read and, while external, one registration write per imported session.
    - Introduced by diff: true; previous behavior: The same adoption write occurred only on the first accepted outgoing user message.; critical-path effect: This is the ownership operation Import actually needs and is expected on its critical path.
- Verdict: Reportable medium-severity eager-work regression. Import should validate through the existing exact metadata path and publish the ownership update without hydrating conversation state.

### Scenario 3: Propagate imported ownership to the sessions list

- Critical path: AgentSessionRegistry fires adoption synchronously; because Import first restored the session, AgentHostStateManager metadata is updated immediately. A catalog reconciliation is queued asynchronously and is not awaited by importSession.
- Scaling input: Number of adoption events and total catalog size. The reconciler coalesces events arriving while a pass is in flight into at most one trailing pass, though serial long-running imports can allow separate passes to complete between items.
- Effective concurrency: A single promise chain serializes reconciliations; storm-driven requests are coalesced to one active plus one dirty trailing run.
- Cache behavior: listSessions coalesces same-mode in-flight computations and provider metadata can use prewarming/bulk reads. Registry epoch invalidation prevents stale reuse.
- Mechanism confidence: High confidence in the coalescing and off-critical-path behavior; lower confidence in repeated-pass cardinality, so it was not reported separately.
- Magnitude uncertainty: Whether multi-import causes one or several completed reconciliation passes depends on provider restore duration versus catalog-pass duration.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_queueSessionListReconciliation</code>: Recompute current session metadata from registry/catalog and republish surfaced summaries; cardinality: Usually one coalesced pass per adoption burst, potentially more when serial imports are spaced by cold restores; each pass scales with the visible catalog.
    - Introduced by diff: true; previous behavior: The same reconciliation mechanism ran after message-triggered adoption; explicit Import adds another adoption trigger but preserves coalescing.; critical-path effect: Queued off the Import response critical path; immediate metadata comes from the restored state.
- Verdict: No separate finding. Coalescing bounds bursts, and the dominant actionable regression is the unnecessary cold restore already reported.
