## Findings (1)

### 1. [low] Coalesce transition loading with the existing restore DB pass

**Finding ID:** `PERF-ABC24421A76B`  
**Location:** <code>src/vs/platform/agentHost/node/chatContributions/sessionWorkspaceConversion/sessionWorkspaceConversionContribution.ts:76</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** filesystem stat calls, SQLite connection/migration checks on a cold reference, and SQLite transition queries  
**Scaling:** One additional storage lookup/query per hydrated converted chat; the cost scales with the number of peer/subagent transcripts a user materializes, while cold references also pay database open and migration-check costs.  
**Outcome:** increased session and transcript restore latency from serialized storage I/O  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Transcript hydration did not touch session storage after provider history retrieval; default-session restore performed only its existing metadata database pass.  
**Changed behavior:** Hydrating a converted transcript now performs a fresh storage existence check/database acquisition and a full workspace-transition query after provider history has returned.  
**Confidence:** 0.96 — The changed call path is direct: restoreSession reads and disposes the session DB, \_getChatMessages awaits provider history, and this contribution then awaits tryOpenDatabase plus getTurnWorkspaceTransitions. chatStorageUri maps the default chat back to that same session storage; for peer/subagent chats the session-level marker also enables one analogous lookup per materialized chat. Exact milliseconds vary with filesystem and database warmth, so severity is low, but the added serial I/O is certain.

**Causal diff evidence:** The added onHydrateTurns path at lines 76-79 calls tryOpenDatabase(storage) and getTurnWorkspaceTransitions(). AgentService now invokes this only after its earlier session metadata database reference has been disposed and after provider.chats.getMessages completes, so the new storage lookup/query is a separate serial boundary introduced by this diff.

Reopening a converted agent session is delayed by an additional filesystem/database round trip after provider history has already completed; sessions with many lazily opened peer or subagent transcripts repeat the delay per transcript.

**Evidence:** AgentService's changed restore path reads AH\_META\_HAS\_WORKSPACE\_TRANSITIONS\_DB\_KEY through an existing database reference, disposes that reference, then awaits \_getChatMessages. hydrateTurns runs contributions sequentially, and this added contribution awaits tryOpenDatabase(storage) followed by a SQLite SELECT before restored turns can be returned. tryOpenDatabase first performs fileService.stat; a cold reference then opens SQLite and runs migration checks. For the default chat, storage is the same session URI already opened for metadata. The session summary marker is also consulted for calls where no explicit flag is supplied, so each lazily materialized peer/subagent transcript in a converted session can incur its own storage lookup/query.

**Suggested direction:** Read the transition map while the existing restore database reference is open and start that read alongside provider history, then pass the resolved map into hydration. For peer/subagent chats, propagate a storage-specific marker/map so a parent session transition does not trigger empty child-database probes.
