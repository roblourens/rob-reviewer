## Findings (1)

### 1. [medium] Cancel personalization when an option is selected

**Finding ID:** `PERF-81DE79864892`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/newChatInput.ts:685</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** filesystem operations and GitHub GraphQL requests  
**Scaling:** Per early selection, work can continue for the remaining total budget: repository discovery scans up to 50 parents, then one issue summary, one PR summary, one linkage request, and up to five parallel per-PR review requests. Cost repeats for each onboarding impression or workspace refresh selected before completion.  
**Outcome:** unnecessary network/filesystem activity and possible contention with the newly started session  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Options were not selectable until the GitHub lookup had completed or timed out, so selection could not leave personalization I/O running after its UI result became unusable.  
**Changed behavior:** The PR makes prompt options selectable immediately while repository discovery and GitHub personalization are still in flight, then only suppresses later renders after selection instead of cancelling that work.  
**Confidence:** 0.96 — The changed first-paint path, selection guard, and cancellation ownership are explicit. \`selectOption\` sets the new flag but never cancels the refresh; cancellation only occurs on refresh/clear/dispose. The transitive lookup is bounded but concrete: repository resolution may perform up to 50 parent filesystem stats, followed by two summary GraphQL calls, one batched linkage call, and up to five parallel review-thread calls.

**Causal diff evidence:** RIGHT line 685 sets \`\_promptOptionsSelected = true\` when a streamed option click begins, but unlike \`\_cancelPromptOptionsRefresh\` it does not cancel \`\_promptOptionsRefresh\`; the resolve token therefore remains live. RIGHT line 362 now publishes selectable standard options before \`\_resolveGitHubPromptOptionsWithFallback\` starts, making selection-before-lookup-completion newly possible.

A user who immediately chooses one of the newly available standard or partial options can still trigger the rest of a 10-second personalization run in the background. That consumes filesystem and GitHub network capacity after its result can no longer be rendered, potentially contending with session startup and wasting up to eight GraphQL requests per impression.

**Evidence:** \`resolveOptions\` publishes three standard options before awaiting personalization. A click reaches the added \`\_promptOptionsSelected = true\`, while \`refreshPromptOptions\` continues awaiting \`controller.resolve(cts.token)\`. The flag only makes \`canRerender()\` false. The live token continues through \`\_resolveGitHubRepository\`, \`getRecentAssignedIssues\`, \`getRecentAuthoredPullRequests\`, batched \`getIssuesWithLinkedPullRequests\`, and \`Promise.all\` review-thread requests. Before this PR, the widget stayed loading until \`resolve\` returned, so a user could not select an option while any of these operations remained.

**Suggested direction:** When option selection begins, cancel the active prompt-options refresh/token in addition to setting the selection guard (without clearing the selected/generated input). Preserve the existing guard for focus-only render suppression, since focus alone should not abort personalization.


## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/sessions/contrib/onboardingTours/browser/newSessionViewV3Prompt.ts:362` (`RIGHT`)  
**Blamed base line:** `src/vs/sessions/contrib/onboardingTours/browser/newSessionViewV3Prompt.ts:215`  
**Introducing path:** `src/vs/sessions/contrib/onboardingTours/browser/newSessionViewV3Prompt.ts`  
**Introducing commit:** `99d3dc07f4c0eed84d7a62c8690cce30bb826063`  
**Mechanism family:** `eager-work`  
**Performance category:** `rendering`  
**Confidence:** 0.98

**Mechanism:** Initial prompt-option rendering was serialized behind repository discovery and multiple GitHub GraphQL stages, with up to the full 10-second total timeout on the onboarding critical path.

**Symptom:** The onboarding widget remained in loading skeletons for seconds or timed out before presenting usable options; experiment telemetry cited in the PR observed 61% timeout impressions with zero GitHub options.

**Fixed behavior:** The runner now sends a complete standard three-option state through the progress callback before awaiting GitHub personalization, then incrementally refines slots. GitHub work remains asynchronous and no longer blocks first usable prompt-option paint.

**Evidence:** In the base implementation, `_runPromptOptions` displayed loading skeletons and awaited `resolveOptions(token)` before calling `showPromptOptions(state)`. `resolveOptions` awaited repository resolution plus concurrent issue and PR chains; the PR chain could sequentially consume the 5s summary and 4s review budgets under the 10s total timeout. The changed line publishes the three standard options synchronously before entering that lookup, so first usable paint no longer waits for filesystem/GitHub boundaries. The PR reports the affected experiment had 61% zero-GitHub-option timeouts and a tour-reach deficit, matching this call-path mechanism.
