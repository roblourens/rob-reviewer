# Performance review: Add prompt options to V3 onboarding

[PR #329837](https://github.com/microsoft/vscode/pull/329837) at `7d0cfd40e5bf3abb43323a877380638e27b2affc`

## Findings (1)

### 1. [medium] Batch GitHub lookups before making options the default

**Finding ID:** `PERF-238C4419CE17`  
**Location:** <code>src/vs/sessions/contrib/onboardingTours/browser/newSessionViewV3Prompt.ts:193</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub GraphQL requests and repository-discovery filesystem operations  
**Scaling:** Each resolution performs two summary requests, up to one issue-linkage request, and one review-thread request per eligible authored PR up to five; the entire uncached cost repeats per workspace change.  
**Outcome:** Increased first-run and workspace-refresh latency plus excessive network traffic  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** An absent treatment selected the local prompt path, which performed no repository filesystem discovery or GitHub API calls. The GitHub fan-out was limited to the explicitly assigned githubPrompt variation.  
**Changed behavior:** An absent or empty treatment now selects personalized prompt options, which await repository discovery and uncached GitHub issue and pull-request resolution before replacing loading skeletons.  
**Confidence:** 0.98 — The default change, awaited call path, query limit, absence of caching, request count, concurrency, and timeout are directly established by the code. Only real-world request duration is uncertain.

**Causal diff evidence:** Added line 193 returns \`options\` for undefined or empty treatments, moving this boundary fan-out from an explicit GitHub variation onto the common no-treatment path.

Eligible first-time users can see prompt cards remain as loading skeletons until the slowest of up to eight GitHub requests completes, and each draft workspace change repeats the burst, increasing API traffic and rate-limit pressure.

**Evidence:** The options resolver awaits issue and PR branches. The issue branch makes a summary request and a linkage request. The PR branch makes a summary request, then \`\_resolveReviewCandidates\` starts one review-thread GraphQL request for every eligible PR with \`Promise.all\`. The fetcher returns up to five PRs and these service methods are uncached, yielding up to eight requests per resolution and six concurrent requests; final options wait for every request or the six-second outer timeout. Workspace changes call the resolver again.

**Suggested direction:** Preserve the options experience but include review-thread data in the existing authored-PR GraphQL query, or otherwise batch and coalesce the per-repository lookup, so candidate ordering is retained without per-PR fan-out.
