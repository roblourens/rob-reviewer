# Performance review: agentHost: make the orchestrator own session enumeration and chat lifecycle

[PR #329633](https://github.com/microsoft/vscode/pull/329633) at `675bfbd56de910baf8efa75a42248a812a6f7ad7`

## Findings (3)

### 1. [high] Batch registry metadata instead of fanning out per session

**Finding ID:** `PERF-3E9797CD1E3A`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:1243</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Provider RPC/IPC calls, full transcript bytes and objects, per-session DB reads, and retained Codex sessions  
**Scaling:** Cold request count grows from about one catalog request per provider to one metadata request per registered session, launched without a limit; Codex payload also grows with every session's complete history.  
**Outcome:** Higher list latency, IPC bursts, CPU/GC pressure, and retained memory  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A refresh called each provider's bulk listSessions implementation once: one Copilot list RPC or one Codex paginated thread/list sequence per provider, followed by the existing overlay work.  
**Changed behavior:** The registry path calls provider.getChatMetadata once for every registered session, concurrently, before per-session database overlays.  
**Confidence:** 0.99 — The replacement fan-out is explicit in one hunk, the workbench eagerly invokes this path, and each provider's concrete per-session boundary is traced. Exact duration varies, but the request-count increase and Codex retention are direct.

**Causal diff evidence:** RIGHT line 1243 adds Promise.all(registered.map(...)), replacing the deleted Promise.all over providers; each mapped registry entry awaits \_registeredSessionMetadata.

Startup/sidebar refresh with a large history now bursts provider IPC. Codex reads every full conversation and retains runtime entries although none were opened, increasing latency and memory/GC pressure.

**Evidence:** \_registeredSessionMetadata calls provider.getChatMetadata. Copilot performs a per-session DB read plus getSessionMetadata RPC; Claude calls SDK getSessionInfo; Codex calls \_readSession, sends thread/read with includeTurns:true, and installs a resumed entry in \_sessions.

**Suggested direction:** Group entries by provider and join them to one bulk provider snapshot. Use bounded targeted fallbacks only for IDs absent from that snapshot, and keep Codex includeTurns/full session materialization off the list path.

### 2. [medium] Fan out active clients only to the chat that was added

**Finding ID:** `PERF-A30B8DF38797`  
**Location:** <code>src/vs/platform/agentHost/node/agentSideEffects.ts:336</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Plugin filesystem operations, parsing, allocations, and provider runtime reconciliation  
**Scaling:** With A active clients and C chats, each addition does A\*C assignments; over C additions this is O(A\*C^2), while only O(A) work for the new chat is required.  
**Outcome:** Excessive I/O and CPU, delayed new-chat setup, and lower creation throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Adding a chat did not replay every active client's contributions over every existing chat, so unchanged sibling chats did not rerun customization synchronization.  
**Changed behavior:** Each chat addition now reassigns every active client's tools and customizations to all old chats plus the new one.  
**Confidence:** 0.98 — The nested fan-out is directly added, tests confirm prior chats are revisited, and provider setters trace to concrete filesystem/runtime work. Only magnitude varies with chat and plugin count.

**Causal diff evidence:** RIGHT lines 336-339 add a SessionChatAdded handler that loops all active clients and calls \_fanOutActiveClient; that helper loops the entire chat catalog.

Successive peer/subagent creation performs avoidable plugin I/O and CPU before the new chat is ready, especially with several customizations or parallel subagents.

**Evidence:** \_fanOutActiveClient loops getSessionChatsForFanOut and executes handle.customizations for each chat. Claude and Codex setters call customization synchronization without equality checks; this reaches AgentPluginManager filesystem checks/copies, and Codex additionally reparses plugins, refreshes roots, and reconciles runtime state. The added test expects the default chat to receive a duplicate call when a peer is added.

**Suggested direction:** For SessionChatAdded, apply active clients only to action.summary.resource. Reserve full-catalog fan-out for SessionActiveClientSet, or make identical provider assignments no-op before synchronization.

### 3. [medium] Reuse transcript reads across subagent matching strategies

**Finding ID:** `PERF-59539765ABC1`  
**Location:** <code>src/vs/platform/agentHost/node/claude/claudeSubagentResolver.ts:240</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Claude SDK transcript I/O, transcript bytes/objects, and repeated parsing  
**Scaling:** The fallback adds N sequential child transcript reads for N subagents on top of PromptMatch's existing up-to-N reads, plus another parent transcript fetch/map.  
**Outcome:** Increased child-chat open/restore latency and repeated I/O/CPU  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After TextSuffix and PromptMatch failed, resolution stopped; PromptMatch made one listSubagents call and at most one transcript read per candidate.  
**Changed behavior:** ResultMatch starts a second listSubagents pass and sequentially rereads every child transcript; it also independently refetches/maps the parent transcript.  
**Confidence:** 0.96 — Strategy order, duplicate reads, and critical-path awaits are explicit. Prevalence of legacy/uncorrelated children is uncertain, but repeated sequential boundary work whenever this fallback runs is certain.

**Causal diff evidence:** RIGHT line 240 adds a sequential getSubagentMessages call inside ResultMatchStrategy's loop, which runs after PromptMatch has already looped over the same SDK subagents and read their messages.

Opening/restoring an uncorrelated Claude subagent waits for two serial scans of all child transcripts plus the final selected read, causing visible load latency in sessions with many parallel subagents.

**Evidence:** The production chain orders PromptMatch immediately before ResultMatch and awaits strategies serially. Both list and read candidate subagents. On a ResultMatch hit, getSubagentTranscript then reads the selected transcript once more for rendering; \_readSubagentMessages awaits this chain on child restore/open.

**Suggested direction:** Cache the parent transcript, subagent list, and child messages for one resolution attempt, or combine prompt/result checks into one candidate scan and reuse the winning messages for rendering.

### Scenario 1: Cold startup and sessions-sidebar refresh

- Critical path: After authentication settles, LocalAgentHostSessionsProvider eagerly awaits connection.listSessions before reconciling the live sidebar cache. Registry enumeration, all provider metadata lookups, and overlay reads must finish before that refresh completes; persisted summaries can render earlier but remain unreconciled.
- Scaling input: Number of durable non-provisional registry entries after grouping by provider; effective metadata cardinality remains one lookup per entry rather than one catalog lookup per provider. Codex byte volume additionally scales with total historical turns.
- Effective concurrency: The changed path launches every registered session lookup in one unbounded Promise.all. Provider/app-server capacity is not used as a limiter; only underlying IPC scheduling provides incidental backpressure.
- Cache behavior: The registry query is always performed. A warm Codex \_sessions entry can avoid thread/read, but the list path itself creates and retains those entries on cold access. Copilot and Claude still perform per-session metadata boundaries; per-session overlays are read separately. There is no request coalescing across concurrent list refreshes beyond the workbench's local in-flight guard.
- Mechanism confidence: Very high: the changed per-entry Promise.all, eager caller, provider boundaries, full-history Codex request, and retained map insertion are explicit.
- Magnitude uncertainty: Actual session counts, provider mix, transcript lengths, and IPC latency vary. Users with only a few sessions see less impact; long-lived histories and Codex users see the largest burst and retention.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentSessionRegistry.ts:AgentSessionRegistry.list</code>: Read the durable SQLite session registry; cardinality: One registry query per list refresh
    - Introduced by diff: true; previous behavior: No registry database query; providers were enumerated directly.; critical-path effect: Must complete before provider metadata fan-out begins
  - IPC at <code>src/vs/platform/agentHost/node/agentService.ts:AgentService.listSessions</code>: Fetch provider metadata for each registry entry; cardinality: N concurrent calls for N registered sessions, grouped by no provider-level batching
    - Introduced by diff: true; previous behavior: One bulk provider catalog call per provider.; critical-path effect: Promise.all waits for the slowest lookup before sessions can be reconciled
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:CodexAgent.\_readSession</code>: Send thread/read with includeTurns:true and deserialize the full thread; cardinality: One cold call per registered Codex session; warm entries hit retained \_sessions state

### Scenario 2: Adding peer chats or provider-spawned subagent chats to an active session

- Critical path: The SessionChatAdded side effect applies active-client tool/customization contributions before the added chat has fully synchronized provider behavior. Replaying old chats consumes the same side-effect sequence and can delay completion for the new chat.
- Scaling input: Active-client count A, current chat count C, and plugin/customization count K. Effective work per addition is A\*C assignments and up to A\*C\*K customization operations; across successive additions it is quadratic in C.
- Effective concurrency: The handler awaits each active client serially, while each \_fanOutActiveClient awaits chats serially. This limits bursts but puts all redundant work in the event's critical sequence without coalescing.
- Cache behavior: Provider handles are cached per chat, but assigning identical customizations does not short-circuit before provider synchronization. Plugin fingerprint/state checks may avoid some physical copies on warm state, yet filesystem checks, collection/parsing, root refresh, and runtime reconciliation are still revisited.
- Mechanism confidence: Very high: the added event branch, nested loops, duplicate-call test expectation, and provider synchronization paths are explicit.
- Magnitude uncertainty: Most sessions have few chats and clients, while parallel subagent workflows can create several quickly. Plugin count and filesystem speed determine absolute cost.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentPluginManager.ts:AgentPluginManager.syncCustomizations</code>: Check and synchronize plugin/customization files for each reassigned chat; cardinality: Up to A\*C\*K operations for each added chat; old chats are revisited
    - Introduced by diff: true; previous behavior: A chat addition did not trigger customization synchronization for every unchanged existing chat.; critical-path effect: Awaited through provider customization setters before fan-out completes
  - other at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:CodexAgentSession.\_syncClientCustomizations</code>: Parse plugins, refresh process-wide skill roots, and reconcile materialized runtime configuration; cardinality: Once per customization assignment, including duplicate assignments to old chats
    - Introduced by diff: true; previous behavior: Existing chats were not reprocessed merely because a sibling chat was added.; critical-path effect: Consumes CPU and can queue runtime configuration work during chat creation
- Verdict: Reportable repeated-work regression: only the new chat needs inherited active-client contributions, but the diff resynchronizes every prior chat on every addition.

### Scenario 3: Opening or restoring a Claude provider-spawned subagent chat

- Critical path: On a SubagentRegistry cache miss, \_readSubagentMessages awaits the strategy chain before returning any child turns. TextSuffix, PromptMatch, and the added ResultMatch execute serially; rendering then awaits a final selected-child read.
- Scaling input: Number N of SDK subagents attached to the parent and transcript sizes. The reported fallback applies when suffix correlation is absent and prompt matching fails but result matching is attempted.
- Effective concurrency: Strategies are serial, candidates inside PromptMatch and ResultMatch are also awaited one by one, and no limiter or parallel batch is used. The effective concurrency is one, so every duplicate SDK read adds directly to latency.
- Cache behavior: A populated SubagentRegistry agentId bypasses the chain. On a miss, parentTranscript, the subagent list, and child message arrays are not shared across strategies; ResultMatch rereads them after PromptMatch. A successful mapping is cached for future opens, so the regression is concentrated on first resolution/restoration and unsuccessful resolutions.
- Mechanism confidence: High: strategy order, duplicate SDK operations, serial awaits, cache-miss condition, and render-path reachability are direct in code.
- Magnitude uncertainty: The share of restored chats lacking suffix/prompt correlation and the typical number/size of parallel subagents are unknown; cached modern sessions avoid the fallback.
- Expensive boundaries:
  - other at <code>src/vs/platform/agentHost/node/claude/claudeSubagentResolver.ts:fetchParentTurns</code>: Fetch and map the parent SDK transcript; cardinality: Up to one fetch per transcript-dependent strategy; the added fallback can cause another full parent fetch/map
    - Introduced by diff: true; previous behavior: The chain ended after PromptMatch and therefore performed no ResultMatch parent fetch.; critical-path effect: Each fetch is serial before candidate result matching
  - other at <code>src/vs/platform/agentHost/node/claude/claudeSubagentResolver.ts:ResultMatchStrategy.lookup</code>: List subagents and fetch each child transcript through the Claude SDK; cardinality: An added N sequential child reads after PromptMatch already performed up to N reads; a winner is read again for rendering
    - Introduced by diff: true; previous behavior: Only PromptMatch's single candidate pass occurred before resolution failed.; critical-path effect: All reads must complete, including ambiguity detection, before the child transcript can render
- Verdict: Reportable medium-severity repeated I/O: the new result fallback duplicates the immediately preceding full candidate scan rather than reusing its messages.

### Scenario 4: Creating, restoring, deleting, and persisting ordinary agent sessions

- Critical path: Registry writes are awaited when durable identity/lifecycle state must be committed; explicit restore performs a targeted provider metadata/read path for the selected session. Per-session state remains isolated in its own database.
- Scaling input: One registry row and one selected session per lifecycle operation; peer-chat rows scale with chats belonging to that selected session rather than the entire catalog.
- Effective concurrency: Registry mutations are serialized by the registry/database sequencing. Explicit restore is targeted rather than launched across the whole catalog.
- Cache behavior: Live provider session maps avoid reconstructing an already-open session; durable registry and per-session databases supply cold restoration. Deleted/tombstoned identities are bounded by lifecycle cleanup rather than continually accumulated in the inspected path.
- Mechanism confidence: High for the new boundaries and bounded cardinality based on registry ownership and targeted restore call flow.
- Magnitude uncertainty: Database latency varies, but operation cardinality is bounded and no catalog-sized fan-out occurs in this scenario itself.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentSessionRegistry.ts</code>: Insert/update/delete durable session and chat records in SQLite; cardinality: Bounded writes per lifecycle event
    - Introduced by diff: true; previous behavior: Durable cross-provider registry writes did not exist; state was derived from provider catalogs.; critical-path effect: Some writes are intentionally awaited to make restored membership authoritative
  - IPC at <code>src/vs/platform/agentHost/node/agentService.ts:restore/open paths</code>: Fetch or resume metadata for the explicitly selected provider session; cardinality: One targeted provider call per cold explicit restore
    - Introduced by diff: false; previous behavior: Opening a selected provider session already required provider-side reconstruction/resume work.; critical-path effect: Necessary to restore the selected session and comparable to prior provider resume behavior
- Verdict: No additional reportable regression: the durable writes are bounded lifecycle work, and the selected-session restore boundary is necessary and not amplified beyond one session. The catalog listing path is assessed separately.
