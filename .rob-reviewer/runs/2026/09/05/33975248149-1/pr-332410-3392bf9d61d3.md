## Findings (1)

### 1. [medium] Move catalog synchronization off the read/archive critical path

**Finding ID:** `PERF-0F4637FF2C0D`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:5313</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** per-session and central SQLite reads and transactions  
**Scaling:** Each read/archive toggle for a surfaced but unmaterialized session performs a full catalog synchronization; its latency is inherited by every later action already serialized on the same client dispatch queue and increases when central catalog work is queued behind migration or reconciliation.  
**Outcome:** increased interaction latency and blocked client action dispatch  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After the existing per-session metadata write completed, the service immediately updated the surfaced status and continued dispatching the action; no central catalog transaction or acknowledgement was awaited on this path.  
**Changed behavior:** The passive toggle now awaits \`\_synchronizePassiveSessionMetadata\` before updating surfaced state. That synchronization reads the local snapshot and central row, writes a local pending snapshot, upserts the central catalog, and writes a local acknowledgement, after which this method also marks the payload dirty.  
**Confidence:** 0.97 — The await is directly on the per-client dispatch queue, and the called synchronizer is traced through local snapshot writes, a central catalog upsert, and a local acknowledgement. The exact wall-clock cost depends on SQLite contention, but the added critical-path I/O and queue blocking are certain.

**Causal diff evidence:** The added RIGHT line \`await this.\_synchronizePassiveSessionMetadata(sessionUri, key, flag, set);\` places the complete cross-database projection sequence before \`setSurfacedSessionStatusFlag\` and before the queued dispatch can continue.

Marking an unopened session read or archived can now remain pending while several SQLite operations complete, and any subsequent action from that client waits behind the same dispatch promise. This is especially visible while startup migration or reconciliation is using the central database sequencer.

**Evidence:** \`dispatchAction\` awaits \`\_applyPassiveSessionMetadata\` inside \`\_clientDispatchQueues\`; the added await at line 5313 calls \`AgentHostCatalogSyncService.\_synchronizeWithDatabaseNow\`, which performs \`getCatalogSyncSnapshot\`, \`getSessionV2\`, \`setMetadataValuesAndCatalogSyncSnapshot\`, \`upsertSessionV2\`, and \`acknowledgeCatalogSyncSnapshot\` before returning. The pre-existing line 5311 already durably writes the requested flag, so these projection operations are newly added synchronous work rather than required durability for the toggle itself.

**Suggested direction:** After the original metadata write, update/dispatch the surfaced state immediately and enqueue the catalog projection on the existing per-session sequencer/background-write tracker. Preserve deletion ordering by draining that tracked work, and invalidate/reconcile the list when the projection finishes.


## Performance regression fixes detected (1)

### 1. boundary-fanout

**Fix location:** `src/vs/platform/agentHost/node/agentService.ts:2794` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentService.ts:2202`  
**Introducing path:** `src/vs/platform/agentHost/node/agentService.ts`  
**Introducing commit:** `150119bd223150e10f6bf341435e680cd8f26d4b`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `io`  
**Confidence:** 0.96

**Mechanism:** Every list computation opened each visible session's separate SQLite database and read a broad metadata object, creating filesystem/SQLite fan-out proportional to the catalog size even when entries were unchanged.

**Symptom:** The old code explicitly described catalog listing as slow because it opened every registered session database and emitted slow-list timing when this path exceeded the threshold.

**Fixed behavior:** The added catalog-reader call serves eligible rows from the central `sessions_v2` database and only sends missing, stale, or invalid rows through the legacy per-session fallback, removing steady-state per-session database opens.

**Evidence:** The deleted overlay mapped every listed session through `tryOpenDatabase(s.session)` and `getMetadataObject(...)`; the added path at line 2794 reads the central catalog projection under concurrency 4, returns eligible metadata directly, and reserves `_legacyRegisteredSessionMetadata` for ineligible rows. The base line carrying the unconditional per-session open blames to the supplied introducing commit.

### Scenario 5: Periodic and startup catalog reconciliation

- Critical path: Reconciliation is scheduled in the background. It scans central dirty/unverified state, opens only selected per-session databases, and repairs projections; ordinary warm listing does not await the scheduled pass.
- Scaling input: Dirty or verification-due sessions D, processed in default batches of 50. The hourly safety sweep may make D approach the registered catalog size; ordinary five-minute passes typically operate on a smaller dirty subset.
- Effective concurrency: Per-session repair concurrency is 4, with batch size 50. Scheduling prevents overlapping uncontrolled reconciliation passes, and central database mutation remains serialized.
- Cache behavior: Clean centrally verified rows are skipped without opening session.db. Successful repair clears dirty state; failures remain dirty for later retry. Startup and hourly sweeps deliberately invalidate verification to bound stale-cache lifetime.
- Mechanism confidence: High: tests and implementation establish dirty filtering, batch size, interval, and concurrency.
- Magnitude uncertainty: Hourly I/O depends on the user's total session count and storage speed, but work is bounded and replaces much hotter per-list fan-out.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostCatalogReconciliationService.ts:242-272</code>: List dirty/unverified central rows and update verification/dirty metadata; cardinality: Central scans per scheduled pass, followed by batches of at most 50 candidates.
    - Introduced by diff: true; previous behavior: There was no central projection requiring repair.; critical-path effect: Background; it can contend with the shared central database but does not need to finish for a warm list.
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostCatalogReconciliationService.ts:275 onward</code>: Open session.db and rebuild the catalog payload for a selected dirty row; cardinality: D selected sessions, not every clean row, with concurrency 4 and batch size 50.
    - Introduced by diff: true; previous behavior: Listing itself opened every visible session database, while no separate reconciliation pass existed.; critical-path effect: Background repair; startup scheduling does not synchronously block service availability.
- Verdict: No finding. Maintenance work is background, filtered, batched, and concurrency-limited; its hourly full verification is a deliberate bounded cache-lifecycle tradeoff.
