# Performance review: Add opt-in auto-archive inactive sessions with merged pull requests

[PR #334341](https://github.com/microsoft/vscode/pull/334341) at `7e6d14157062b843b8a4ca0efc58f6b2157f306b`

## Findings (1)

### 1. [medium] Preflight retained worktrees before restoring deletion candidates

**Finding ID:** `PERF-C0E90FA03E86`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionLifecycle.ts:144</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** GitHub API calls, provider/session database reads, transcript objects, and provider chat materialization/release work.  
**Scaling:** Once per hourly pass for each retained-worktree session past the deletion cutoff; restore cost also grows with transcript and chat metadata size.  
**Outcome:** Persistent background network/filesystem I/O and CPU/GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** There was no background deletion pass restoring archived sessions before this PR.  
**Changed behavior:** The new hourly lifecycle restores every due deletion candidate before checking whether its retained worktree makes automatic deletion impossible; rejected candidates remain eligible and repeat the sequence next hour.  
**Confidence:** 0.98 — The changed ordering, hourly retry, and expensive restore call path are explicit. Only the prevalence of retained worktrees is uncertain.

**Causal diff evidence:** Added line 144 unconditionally awaits \`\_accessor.restoreSession(session)\` before the delete branch reaches the added \`canDeleteSession\` worktree guard at lines 188-191.

Automatically archived sessions whose worktree cleanup was skipped or failed repeatedly consume GitHub API budget and provider/database I/O every hour despite being unable to make deletion progress.

**Evidence:** \`restoreSession\` materializes the provider chat, loads message history, and hydrates metadata/configuration. The later worktree guard only reads persisted worktree metadata and performs \`fs.access\`, so it can reject without restored session state. A rejected deletion keeps its archive timestamp and is returned by the next hourly candidate scan.

**Suggested direction:** For delete candidates, run a cheap \`canDeleteSession\` preflight before the GitHub refresh and restore, while retaining the current in-disposal recheck for race safety.
