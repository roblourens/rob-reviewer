# Performance review: chat: add customization migration assessment telemetry

[PR #333196](https://github.com/microsoft/vscode/pull/333196) at `37e5ee7b1a9747057e9f3d6b4797ce90f27ba6e9`

## Findings (2)

### 1. [medium] Report migration telemetry once per session open, not per chat tab

**Finding ID:** `PERF-5FAA842058E5`  
**Location:** <code>src/vs/sessions/services/sessions/browser/sessionsService.ts:789</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Prompt discovery work and MCP configuration-resolution work for every known MCP server  
**Scaling:** The cost repeats for every side-chat/subagent/tab open within the same session and grows with the number of prompt sources and configured MCP servers; sequential opens rebuild the MCP scope because the assessment disposes it when complete.  
**Outcome:** Repeated background CPU/I/O pressure and avoidable telemetry/network traffic while navigating chats, which can make tab switching and the surrounding UI less responsive.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this line, \`\_openChat\` only activated the selected chat and updated open telemetry; chat-tab navigation did not run customization migration discovery or MCP support assessment.  
**Changed behavior:** The added fire-and-forget call invokes \`reportCustomizationMigrationTelemetry\` after every \`\_openChat\`, including opens of side chats and subagent chats in a session that is already active.  
**Confidence:** 0.99 — The call chain from user chat navigation to the added line and from there to full migration/MCP computation is explicit. The only magnitude uncertainty is the user's number of configured prompts/MCP servers and tab-switch frequency.

**Causal diff evidence:** RIGHT line 789 newly calls \`\_reportCustomizationMigrationTelemetry(...)\` inside \`\_openChat\`, a method used for both entering a session and selecting another chat within the same session; no corresponding migration computation existed on this path before the PR.

Opening or switching among chats in an already-open Agents session calls \`\_openChat\` each time, so normal tab navigation repeatedly launches the complete customization assessment even though the session lifecycle has not changed.

**Evidence:** \`openChat\` always routes through \`\_openChatSession\` to \`\_openChat\`, and numerous chat-tab UI paths call it. The added line calls the helper unconditionally after load. That helper reaches \`computeMigrations\`, which runs all four migration computations; the MCP branch creates a ref-counted support scope, waits through its 50 ms delayed assessment, resolves every MCP server configuration, and disposes the scope afterward. Thus a later tab open recreates and reruns the assessment rather than reusing a completed result.

**Suggested direction:** Move this report to the actual session-entry transition (or guard/deduplicate it by session resource for the current open lifecycle) and leave chat-only navigation free of migration recomputation.

### 2. [medium] Bound migration assessments during session restore

**Finding ID:** `PERF-6B0FB446082D`  
**Location:** <code>src/vs/sessions/services/sessions/browser/sessionsService.ts:1614</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Concurrent prompt discovery, per-workspace MCP support scopes, and per-server configuration-resolution work  
**Scaling:** For N immediately restored sessions with distinct workspace roots and M configured MCP servers, this loop starts N detached assessments at once and the MCP work grows as O(N×M); prompt listing is coalesced only when its cache is warm, while MCP scopes are keyed by session type and roots.  
**Outcome:** A burst of background CPU, filesystem/provider work, and asynchronous configuration resolution during workbench restore, increasing startup contention and responsiveness risk.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this loop was added, restoring the visible-session grid performed session resolution/layout only and did not launch customization discovery or MCP support assessments for each restored slot.  
**Changed behavior:** The new loop fire-and-forgets one \`\_reportCustomizationMigrationTelemetry\` call for every already-resolved restored session without a limiter, idle deferral, or grouping by equivalent assessment scope.  
**Confidence:** 0.97 — Startup reachability, unbounded loop cardinality, detached concurrency, scope keying, and per-server work are all explicit in the code. Exact slowdown varies with restored-session and MCP-server counts, which affects severity rather than mechanism confidence.

**Causal diff evidence:** RIGHT line 1614 is inside a loop over all resolved restored sessions and newly starts one unawaited migration assessment per element; this startup fan-out did not exist before the PR.

Reloading an Agents window with several persisted visible sessions immediately launches a full customization assessment for every restored session just as the workbench is restoring. Different workspace roots prevent MCP-scope coalescing, so a realistic multi-session grid fans out concurrent work.

**Evidence:** \`Workbench.restore\` invokes \`restoreVisibleSessions\` during startup. At the added loop, every call synchronously enters \`computeMigrations\`; its MCP branch acquires a scope keyed by \`\[sessionType, roots\]\`. Each distinct scope schedules a 50 ms-delayed assessment, iterates all MCP servers, awaits local MCP loading, and resolves server configurations. The repository test itself demonstrates three calls for three restored sessions, and persisted visible-session state has no bound here.

**Suggested direction:** Queue these reports with bounded concurrency or defer them to idle, and coalesce assessments that share the same session type/workspace scope while preserving the required per-session telemetry semantics.
