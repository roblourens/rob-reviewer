### Scenario 1: Desktop startup and policy-definition updates recreate the native managed-settings watcher

- Critical path: PolicyConfiguration submits changed policy definitions through AccountPolicyService and the browser-to-main channel; initial desktop policy resolution waits for the main-process native watcher to deliver its initial snapshot. Later account/configuration events await the same path before policy values are recomputed.
- Scaling input: Number of declared managed-setting policies and bursts of policy-definition changes during startup; Throttler reduces concurrent updates to at most one active and one latest queued factory.
- Effective concurrency: Watcher creation is serialized by Throttler. MutableDisposable disposes the previous watcher when a successfully created replacement is installed; failed replacement leaves the old watcher active.
- Cache behavior: Equal definition maps return the existing initialization path and avoid native watcher recreation. Cold startup dynamically imports the addon and creates the watcher; warm unchanged updates reuse it.
- Mechanism confidence: High: the IPC call, equality guard, throttler behavior, replacement disposal, and conditional retry are explicit in the traced code.
- Magnitude uncertainty: Native addon initialization cost is platform-dependent, and legacy-addon fallback prevalence is unknown, but the added work is bounded to one immediate failed attempt in that compatibility case.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/policy/common/nativeManagedSettingsIpc.ts: NativeManagedSettingsChannelClient.updatePolicyDefinitions</code>: Send the policy-definition map from the workbench process to the main-process native managed-settings service.; cardinality: One call per AccountPolicyService reevaluation that has managed-setting definitions; unchanged definition sets are recognized in the main-process service and reuse initialization. This call frequency predates the diff.
    - Introduced by diff: false; previous behavior: The same IPC update and payload traversal occurred; the diff only permits scalar-union type metadata in the existing payload.; critical-path effect: Initial configuration/policy resolution awaits the response; later policy refreshes await it before publishing updated values.
  - other expensive boundary at <code>src/vs/platform/policy/node/nativeManagedSettingsService.ts: updateWatcher</code>: Create an OS registry/managed-preferences watcher and replace the previous native watcher.; cardinality: One active watcher; Throttler serializes and coalesces a burst to the active update plus the latest queued update.     - Introduced by diff: false; previous behavior: A watcher was already created/replaced for each distinct submitted definition set. The diff changes replacement ordering and adds a bounded legacy fallback, without increasing normal-path watcher cardinality.; critical-path effect: The initial callback resolves watcher initialization, so startup waits for it. Normal 1.5 operation still constructs one watcher; the legacy retry is constant and only follows immediate type rejection.
- Verdict: No reportable regression. The normal path does not add watcher or IPC fan-out, queued replacements are coalesced, and successful replacement keeps exactly one live native watcher.

### Scenario 4: MCP collection discovery, autostart, manual start, and live policy changes under selective MCP lockdown

- Effective concurrency: Per-server start is sequenced. Existing autostart uses Promise.all across eligible servers. Collection reconciliation is delayed 500 ms, and policy filtering can reduce the eligible set.
- Cache behavior: Lazy collections skip activation when cached; server metadata caches are unchanged. Selective filtering is reactive and does not defeat those caches.
- Mechanism confidence: High: collection filtering, lazy activation, 500 ms reconciliation, per-server sequencing, autostart fan-out, and subprocess/network placement were traced.
- Magnitude uncertainty: Installations vary in MCP collection/server count and remote startup latency, but the only newly added per-start work is bounded in-memory validation and one collection lookup.

    - Introduced by diff: false; previous behavior: Boolean lockdown already filtered all standalone MCP collections.
