**Relevant issue families:** repeated-work, boundary-fanout, missing-coalescing, eager-work

### Scenario 1: Send the first turn immediately after opening an existing Agent Host session

- Critical path: Session/chat hydration completes and starts the shared customization scope; the changed claim path now waits for any remaining initial customization resolution, performs a microtask reconciliation, and queues any required active-client publication before ChatTurnStarted. The initial resolution is therefore newly on this turn's critical path only when it has not already completed while the session UI was opening.
- Scaling input: Number of eligible plugins, prompt files, agents, MCP definitions, and recursively contained skill files for one root set; effective scope cardinality is one cold resolution per concurrently retained root/session-type key, not one scan per turn.
- Effective concurrency: Customization discovery runs its independent top-level resolvers in parallel; bundle filesystem operations use a limiter of 10, writes are sequential, and one ref-counted scope is shared by identical roots. Concurrent turn claims share one Delayer completion and reconcile once per microtask snapshot.
- Cache behavior: Cold scopes resolve and bundle once. Warm calls use the settled initial promise, cached derived active-client data, nonce reuse in the bundler, and equality suppression. Disposing the final session reference drops the scope, so a later cold reopen resolves again.
- Mechanism confidence: High confidence in the changed ordering and filesystem call graph; medium confidence that meaningful residual latency remains in normal use because resolution starts before the UI becomes invokable and is shared/cached.
- Magnitude uncertainty: Residual cold-resolution time depends on how quickly the user submits after hydration and on customization/file-system size. The code proves a temporary critical-path wait, but not a sustained or high-impact regression; the ordering is required to prevent stale tool/customization publication.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostActiveClientService.ts AgentCustomizationScope and agentHostLocalCustomizations.ts resolveCustomizationRefs/resolveLocalCustomAgents</code>: Enumerate prompt/customization sources; stat plugin roots and skill trees; read agent and bundle files; write the synthetic in-memory customization bundle when its nonce changes.; cardinality: Once per cold shared sessionType-plus-root scope; enumeration covers each configured storage source and eligible customization, while recursive skill traversal scales with files in each skill. File operations are limited to 10 concurrently and the scope is shared across simultaneously open sessions with the same roots.
    - Introduced by diff: false; previous behavior: The same scope resolution and filesystem work ran after opening the session but a turn could dispatch before it completed; the diff changes ordering by waiting for it.; critical-path effect: Only the unfinished portion of cold initial resolution blocks the changed claim; warm scopes return immediately. This work already started when the session content acquired the scope.
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts ActiveClientEntry.\_requestReconciliation and \_handleTurn</code>: Publish SessionActiveClientSet through the Agent Host connection when the authoritative state differs, followed by ChatTurnStarted.; cardinality: At most one active-client publication for the reconciled snapshot before one turn dispatch; Delayer coalesces concurrent claims and equality/\_lastPublished suppress duplicate publications.
    - Introduced by diff: false; previous behavior: Both message types already existed; active-client reconciliation used a 5 ms delayed asynchronous path and could be queued after ChatTurnStarted.; critical-path effect: The active-client message is now synchronously queued before the turn message, but dispatch does not await a host acknowledgement.
- Verdict: No finding. The diff intentionally places only unfinished initial resolution on the critical path to guarantee the first request observes the published client snapshot; the work is once-per-scope, already initiated before invocation, bounded/coalesced, and no evidence establishes a user-visible regression large enough for an actionable performance finding.

### Scenario 2: Create a new Agent Host session and send its first turn

- Critical path: The pre-existing create path already waits for ActiveClientEntry.whenSettled before createSession, sends the active client in createSession, hydrates subscriptions, then reaches the changed claim. The added claim normally sees a resolved scope and adds one microtask reconciliation before ChatTurnStarted.
- Scaling input: Customization count affects the pre-existing create barrier; one turn and one session are dispatched.
- Effective concurrency: Scope initialization is shared and in flight while session setup proceeds; claim does not launch another resolution. Reconciliation is serialized/coalesced by one Delayer.
- Cache behavior: The scope was acquired when the new chat content was provided and is warm by the time createSession returns; nonce and active-client equality avoid redundant bundle writes/publications.
- Mechanism confidence: High confidence from the explicit pre-existing whenSettled call before createSession and the shared scope instance.
- Magnitude uncertainty: Only microtask scheduling and equality cost are newly added here; exact metadata size varies, but there is no new scaling boundary.
- Expensive boundaries:

    - Introduced by diff: false; previous behavior: The first new-session turn already awaited active-client settlement before the createSession boundary.; critical-path effect: Already blocked createSession before the diff; the changed post-create claim does not add a second scan.
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts \_createAndSubscribe and \_handleTurn</code>: Create and subscribe to the backend session, then dispatch ChatTurnStarted; SessionActiveClientSet is only queued if hydrated state differs.; cardinality: One create request, session/chat subscriptions, and one turn dispatch per new session/turn; active-client publication remains equality-suppressed.

- Verdict: No finding. The expensive initialization was already on the new-session critical path, while the diff adds only a warm, coalesced reconciliation needed for ordering.

### Scenario 3: Send later turns after client tools or customization metadata changes

- Critical path: Each changed turn now forces pending active-client reconciliation to the next microtask and waits until its current snapshot is queued; unchanged warm turns perform a derived snapshot read and equality checks before dispatching ChatTurnStarted.
- Scaling input: Enabled client tool and customization count, with realistic effective cardinality one list comparison and at most one publication per turn-time snapshot rather than one per changed item.
- Effective concurrency: Microtask Delayer calls collapse simultaneous claims and metadata notifications to the latest task. \`\_lastPublished\` prevents repeated sends while server state has not converged.
- Cache behavior: Derived observables cache until dependencies change; warm scope promise is settled; unchanged and last-published snapshots are negative-cached by equality checks.
- Mechanism confidence: High confidence that in-memory reconciliation is newly ordered before the turn and remains coalesced/deduplicated.
- Magnitude uncertainty: Deep equality grows with metadata size, but typical tool/customization inventories are bounded and the diff does not establish measurable CPU or serialization pressure.
- Expensive boundaries:
  - serialization at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostActiveClientService.ts AgentCustomizationScope.activeClient and agentHostSessionHandler.ts ActiveClientEntry.\_requestReconciliation</code>: Compose/copy the tool and customization arrays and deep-compare the active-client snapshot with session state and the last publication.; cardinality: Once per turn claim after microtask coalescing; comparisons scale with the enabled tool/customization list. Concurrent claims in the same microtask share the reconciliation.
    - Introduced by diff: true; previous behavior: The same composition/comparison ran asynchronously after a 5 ms debounce rather than before the turn.; critical-path effect: Newly moved onto the turn critical path, but it operates on already-resolved in-memory metadata and avoids dispatch when equal.
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts lines 999 and 3009</code>: Queue SessionActiveClientSet before ChatTurnStarted when metadata changed.; cardinality: One publication for the latest coalesced changed snapshot and one turn dispatch; no publication for unchanged or already-unacknowledged equivalent snapshots.
    - Introduced by diff: false; previous behavior: The active-client publication was already produced on metadata changes but could be delayed and ordered after the turn.; critical-path effect: Ordering changes so publication is queued first; neither dispatch waits for host acknowledgement.
- Verdict: No finding. The added critical-path work is one microtask plus bounded in-memory comparison, and changed snapshots retain the existing one-message coalescing and duplicate suppression.

### Scenario 4: Retry/resume a turn while scope resolution is pending, including concurrent resume and cancellation

- Critical path: The resumed invocation now joins the same scope-resolution/reconciliation barrier before inspecting and observing the resumed turn. Cancellation races the barrier and exits without active-client or turn dispatch. Concurrent resumes share reconciliation, after which existing state determines whether a resume message is needed.
- Scaling input: Number of concurrent local retries for one turn; effective expensive-work cardinality remains one scope resolution and one reconciliation, not one per retry.
- Effective concurrency: Concurrent callers await one shared initial-resolution promise and one Delayer settlement. Cancellation is caller-specific via raceCancellation and does not cancel or duplicate the shared scope work.
- Cache behavior: Warm scopes bypass filesystem work; the settled promise and shared scope are reused. Active-client equality and last-published state suppress duplicate messages.
- Mechanism confidence: High confidence in joining/coalescing and cancellation behavior from the changed call order, Delayer implementation, and focused regression tests.
- Magnitude uncertainty: A cold retry can inherit residual discovery latency, but retries are less frequent and the work is shared; no evidence shows unbounded concurrency or repeat I/O.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts ActiveClientEntry.claim</code>: Complete the same cold customization scope resolution described for an existing session.; cardinality: One shared cold scope resolution regardless of the number of concurrent retries.
    - Introduced by diff: false; previous behavior: Resolution ran independently and retry observation/dispatch proceeded without waiting.; critical-path effect: Newly blocks retry attachment only while initial resolution is pending; cancellation releases the caller without waiting for completion.
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts \_handleResumedTurn</code>: Queue a changed SessionActiveClientSet and, only if still necessary, ChatTurnResume; cancellation may queue ChatTurnCancelled after observation is installed.; cardinality: One coalesced active-client update and zero or one resume dispatch for concurrent retry attempts; the tested concurrently accepted remote resume avoids a duplicate local resume.
    - Introduced by diff: false; previous behavior: The same messages existed, but active-client claiming did not delay state inspection and publication was not guaranteed to precede resume.; critical-path effect: Active-client publication is ordered first without acknowledgement; a remote resume received during the barrier can remove the need for local resume dispatch.
- Verdict: No finding. The barrier may add bounded cold latency but prevents stale duplicate resume behavior, coalesces concurrent callers, and introduces no additional expensive boundary or fan-out.

Traced cold/warm customization resolution, active-client publication, normal/new/resumed turn critical paths, cancellation, cache lifetime, dispatch ordering, filesystem cardinality, and effective concurrency. No high-confidence actionable performance regression was found; the only newly critical work is intentionally ordered, shared/coalesced, and either already pre-existing on new-session creation or bounded to residual cold resolution/in-memory reconciliation.
