<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, boundary-fanout, serialization-allocation

### Scenario 1: Refresh a multi-chat Session Changes changeset after a hidden host-notice turn completes

- Critical path: Turn completion schedules the session recompute fire-and-forget, so it is off the agent turn's completion critical path; an observing Session Changes client waits for the per-session sequencer, checkpoint lookup, Git diff, publication, and persistence before the refreshed file list is ready.
- Scaling input: The in-memory selector visits each chat and scans backward only over its trailing host-notice turns; effective work is O(chat count plus trailing notices), while downstream boundary cardinality remains one grouped session computation. Typical turns stop at the first attributable tail turn.
- Effective concurrency: Refreshes are serialized by the per-session, per-kind sequencer. The two checkpoint lookups run in parallel, followed by one Git diff; the change adds no concurrency or fan-out.
- Cache behavior: Checkpoint selection is recomputed from in-memory state on every queued refresh. Persisted changeset data can seed restored UI, but successful refreshes still perform checkpoint resolution and a Git diff; the diff does not alter cache keys or cold/warm behavior.
- Mechanism confidence: High: the changed selector, sequencer, checkpoint calls, and Git boundary are directly traced. It retains the prior reverse-turn scan complexity and adds only one timestamp conversion per chat.
- Magnitude uncertainty: Chat counts and notice-tail lengths vary, but the added Date conversion is bounded by chat count and is dominated by the unchanged checkpoint/Git work.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:\_doComputeStaticChangeset</code>: Open the session database for the static changeset computation.; cardinality: One session DB open per queued session recompute.
    - Introduced by diff: false; previous behavior: The same DB open occurred before the diff.; critical-path effect: Required before the session changeset compute can proceed.
  - other expensive boundary at <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:\_tryComputeGitDiffs</code>: Resolve baseline and selected-turn checkpoints.; cardinality: Two checkpoint lookups issued in parallel per Git-backed session recompute, independent of chat count.
    - Introduced by diff: false; previous behavior: The same two checkpoint lookups occurred; only the selected turn ID changes.; critical-path effect: Both must complete before the Git diff starts.
  - subprocess at <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:\_tryComputeGitDiffs</code>: Compute file diffs between the baseline and selected checkpoint refs through the Git service.; cardinality: One Git diff per session recompute; no per-chat fan-out.
    - Introduced by diff: false; previous behavior: One Git diff was already performed per recompute, previously against the last attributable turn of the most-recently-modified chat.; critical-path effect: Blocks publication of the refreshed Session Changes contents.
  - serialization at <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:\_doComputeStaticChangeset</code>: Serialize and persist the computed diff list.; cardinality: One full diff-list serialization/persist per successful recompute.
    - Introduced by diff: false; previous behavior: The same serialization and persistence occurred before the diff.; critical-path effect: Occurs after publication and does not determine the in-memory ready state.
- Verdict: No reportable regression. The diff changes which existing checkpoint lookup and single Git diff are used; it neither adds a boundary nor increases boundary cardinality. The per-chat timestamp conversion is minor bounded CPU work.

### Scenario 2: Refresh Session Changes after a genuine newer peer or Agent Merge repair turn

- Critical path: For turn-complete refreshes, recomputation is queued asynchronously and does not delay turn completion; the Session Changes view waits for the queued DB/checkpoint/Git pipeline. Initial subscription likewise waits for this pipeline to populate fresh state.
- Scaling input: Number of chats and trailing hidden notices controls selector CPU; repository change size controls the unchanged Git diff and result serialization. There is no per-chat Git or checkpoint fan-out.
- Effective concurrency: Per-session session-changeset recomputes are serialized. Checkpoint reads are parallelized as before, and only one Git operation runs for this scenario.
- Cache behavior: The previous file list remains visible while recomputation runs and successful results are persisted. Endpoint selection itself is not cached, but prior code also rescanned each chat's turns; restored turns without timing data use the existing chat modifiedAt value.
- Mechanism confidence: High: added code performs one Date parse/format per chat after the same reverse attributable-turn search and feeds the same single-checkpoint pipeline.
- Magnitude uncertainty: Large chat catalogs could increase timestamp-conversion CPU linearly, but realistic cardinality and the unchanged dominant Git operation make user-visible degradation unsupported.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:\_doComputeStaticChangeset</code>: Open the session database.; cardinality: One open per queued session recompute.
    - Introduced by diff: false; previous behavior: Unchanged.; critical-path effect: On the changeset-refresh critical path.
  - other expensive boundary at <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:\_tryComputeGitDiffs</code>: Read baseline and selected-turn checkpoint refs.; cardinality: Two parallel lookups per recompute, not per chat.
    - Introduced by diff: false; previous behavior: Unchanged cardinality; the selector can now choose a different turn.; critical-path effect: Precedes and gates Git diff computation.
  - subprocess at <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:\_tryComputeGitDiffs</code>: Diff the baseline against the selected latest completed turn checkpoint.; cardinality: One Git diff per recompute after all chats are grouped into one selected endpoint.
    - Introduced by diff: false; previous behavior: One Git diff was already issued against the chat chosen by modifiedAt.; critical-path effect: On the refreshed view's critical path.
- Verdict: No performance finding. Before and after perform one grouped session Git diff, and the changed work is bounded in-memory ordering logic rather than new I/O, retention, eager initialization, or concurrency.

**Summary:** Completed the performance pass over both changed files and traced session refresh triggers, sequencing, checkpoint resolution, Git computation, fallback/persistence, turn-history scaling, and tests. No diff-introduced actionable performance regression was found; the change preserves existing scan complexity and expensive-boundary cardinality while correcting checkpoint ordering.
