**Relevant issue families:** serialization-allocation, synchronous-ui-work, repeated-work

### Scenario 1: Live HydraFusion workflow selection reaches the active chat transcript

- Critical path: The Copilot SDK emits session.fusion\_resolved; CopilotFusionProgress.accept creates one SystemNotificationResponsePart; the existing agent-host state protocol delivers it; systemNotificationToChatPart escapes the selected description; ChatSystemNotificationContentPart synchronously renders it before the row is visible.
- Scaling input: Distinct HydraFusion selections, effectively one selected notification per fusionId; CPU and payload bytes scale linearly with the hint length and number of turns, not with phase count or activity-event frequency.
- Effective concurrency: Fusion events are accepted serially into state; duplicate selections are coalesced by the milestone key. No new parallel task, queue, or burst is introduced.
- Cache behavior: No cache is involved. Both cold and warm live selections perform one conversion and one render; deduplication is stateful per CopilotFusionProgress instance and reset between turns.
- Mechanism confidence: High confidence in the one-per-fusion cardinality, existing transport boundary, added metadata bytes, and synchronous render path from direct call-flow evidence.
- Magnitude uncertainty: The SDK type does not establish an explicit hint-length bound in repository code, but the field is a workflow description and test/product examples are short. One duplicate serialized string per selected turn is insufficient for a concrete user-visible regression.
- Expensive boundaries:
  - IPC/network serialization at <code>src/vs/platform/agentHost/node/copilot/copilotFusionProgress.ts:124-132; transports serialize protocol messages in src/vs/platform/agentHost/browser/agentHostIpcChannelTransport.ts:81 and src/vs/platform/agentHost/browser/webSocketClientTransport.ts:188</code>: Serialize and deliver the existing chat response-part update/snapshot containing the workflow notification; the new namespaced metadata carries the SDK hint in addition to content.; cardinality: One selected notification per distinct fusionId because CopilotFusionProgress.\_record rejects duplicate route events; no additional protocol call is introduced.
    - Introduced by diff: false; previous behavior: The same selection notification crossed the same transport with a locally generated description only in content; no extra transport operation occurred.; critical-path effect: The existing state update must arrive before the selection description appears. The diff increases that message by one short workflow-description field but does not add a boundary crossing.
- Verdict: No finding. The diff adds bounded serialization/allocation proportional to one short hint but no extra call or fan-out, and replaces the previous title/body renderer path with a single body Markdown render.

### Scenario 2: Opening or reconnecting to a session reconstructs Fusion workflow descriptions from durable/replayed state

- Critical path: Historical SDK events are replayed serially by mapSessionEvents and FusionReplayState into responseParts; an existing snapshot/update crosses the agent-host protocol; turnsToHistory or activeTurnToProgress scans response parts and systemNotificationToChatPart projects the description before visible history rows render.
- Scaling input: Number of restored turns/fusions and total hint bytes. FusionReplayState scans the event collection serially and CopilotFusionProgress deduplicates each route milestone; effective notification cardinality is one per fusion, not one per replay event.
- Effective concurrency: Replay, turn projection, and response-part iteration are synchronous serial loops. The diff introduces no Promise fan-out, worker, subprocess, or concurrent boundary calls.
- Cache behavior: No description cache exists or is needed. Reconnect/history reconstruction repeats the existing linear projection; visible row reuse is governed by hasSameContent, which includes the new presentation value and stable description content.
- Mechanism confidence: High confidence from the replay deduplication, response-part loops, and transport serializers; only the real-world upper bound of SDK hint length is unspecified.
- Magnitude uncertainty: Large histories increase existing snapshot and projection costs, but the incremental metadata is one short duplicate string per selected workflow and the rendering branch performs less work. There is no evidence of large hints or a measurable history-load symptom.
- Expensive boundaries:
  - network/IPC serialization at <code>src/vs/platform/agentHost/common/state/protocol/channels-chat/state.ts:558-605; src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts:1043-1128 and 1488-1551</code>: Fetch/deliver the existing session snapshot containing completed or active turns and their responseParts.; cardinality: One existing snapshot/subscription flow per open or reconnect, containing at most one selected notification for each replayed fusion; no new request is issued per notification.
    - Introduced by diff: false; previous behavior: The same turn history and response parts were fetched and scanned; selected notifications retained one localized description in content without a duplicate metadata field.; critical-path effect: Snapshot delivery and linear projection are on the history/reconnect path, but the diff changes only bytes in each existing selection record and does not add I/O calls.
- Verdict: No finding. Incremental retained/serialized data is linear but small and coalesced per fusion, with no added boundary cardinality or concurrency.

### Scenario 3: Scrolling or rerendering a chat row containing the selected workflow

- Critical path: The chat list synchronously creates ChatSystemNotificationContentPart for a visible systemNotification and invokes the Markdown renderer to build the row DOM.
- Scaling input: Number of visible/recreated workflow-selection rows and description length; one Markdown render per row after the diff.
- Effective concurrency: Synchronous UI rendering on the chat list render path; no asynchronous work or boundary concurrency.
- Cache behavior: hasSameContent permits reuse when content and presentation are unchanged. There is no separate Markdown cache, but the changed branch reduces selected-workflow rendering from separate title and optional body renders to one description render.
- Mechanism confidence: High confidence from the constructor branches and chatListRenderer call site.
- Magnitude uncertainty: Exact rerender frequency depends on list virtualization and scrolling, but the direction of changed work is non-regressive: fewer Markdown render calls and fewer DOM elements for normal selected records.
- Expensive boundaries: none found
- Verdict: No finding. The changed visual path removes the title/icon and performs one Markdown render instead of the previous title plus optional body renders.
