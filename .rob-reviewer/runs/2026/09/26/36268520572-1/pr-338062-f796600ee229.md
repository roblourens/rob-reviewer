<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, cleanup-lifecycle, boundary-fanout, concurrency-burst

### Scenario 1: Ordinary transient remote-connection loss while the process remains awake

- Critical path: The existing reconnect loop waits 0/5/10/30 seconds, resolves the remote address, and opens/authenticates a socket; those operations must complete before the window or remote extension host reconnects. The added one-second scheduler only decrements its counter and eventually flips a local boolean, so it is not itself on the per-attempt critical path.
- Scaling input: Elapsed disconnected process time, with one one-second timer callback per active reconnect loop and one network attempt per configured retry interval; default grace is three hours.
- Effective concurrency: \_beginReconnecting guards each PersistentConnection to one loop. Management and extension-host connections are separate and can retry concurrently, but there is no per-item fan-out and tunnel connections do not use this loop.
- Cache behavior: Remote-authority resolution and any cache it uses are unchanged. The new scheduler has no cache or retained per-attempt state, and successful reconnection disposes it.
- Mechanism confidence: High: the changed line creates exactly one interval-backed scheduler per guarded reconnect loop; implementation and call sites establish its one-second cadence and bounded lifetime.
- Magnitude uncertainty: Exact timer wake-up energy cost varies by runtime and platform, but at most two typical client timers run only while disconnected, and existing network retries dominate the work.
- Expensive boundaries:
  - network at <code>src/vs/platform/remote/common/remoteAgentConnection.ts: resolveConnectionOptions and PersistentConnection.\_reconnect</code>: Resolve the remote endpoint and perform the management or extension-host socket reconnection handshake.; cardinality: One address resolution and one socket connection per retry attempt; retries are serialized within each connection and spaced by 0, 5, 10, then 30 seconds. A typical remote window can have one management and one extension-host connection retrying independently.
    - Introduced by diff: false; previous behavior: The same serialized address resolution and network connect occurred at the same retry cadence until Date.now() exceeded the grace period.; critical-path effect: Each retry's resolution and socket handshake must finish or fail before the next retry and before reconnection succeeds.
- Verdict: No reportable regression. The new timer adds bounded low-cost callbacks only during an already active reconnect loop, without increasing ordinary retry cardinality, concurrency, startup work, or healthy-connection overhead.

### Scenario 2: Resume from hibernation after a large wall-clock jump while the remote remains unavailable

- Critical path: After wake, the next scheduled retry performs endpoint resolution and a socket attempt. With the changed process-time deadline, failures continue through the remaining active-process grace period instead of terminating because wall time advanced during sleep; successful socket reconnection remains the critical path.
- Scaling input: Remaining configured grace time after resume and duration of continued remote unavailability, not wall-clock sleep duration.
- Effective concurrency: One in-flight retry per PersistentConnection; at most the independent management and extension-host loops normally overlap. No burst is created on wake because existing waits and per-loop awaits serialize attempts.
- Cache behavior: The address provider's existing resolver/cache behavior is unchanged; every socket attempt necessarily creates a fresh connection. No new negative cache is introduced.
- Mechanism confidence: High: the deadline change directly preserves retries after hibernation, and the transitive network boundaries are explicit in the loop.
- Magnitude uncertainty: A long post-resume outage can produce many more retries than the old incorrect early termination, but frequency is capped by the existing 30-second cadence and configured grace.
- Expensive boundaries:
  - network at <code>src/vs/platform/remote/common/remoteAgentConnection.ts:694 and the retry body at resolveConnectionOptions/\_reconnect</code>: Continue remote address resolution and socket reconnection attempts after resume.; cardinality: One resolution plus one socket attempt per serialized retry, eventually spaced 30 seconds apart, for up to the remaining active-process portion of the default three-hour grace period; management and extension-host connections may each do this independently.
    - Introduced by diff: true; previous behavior: After the wall clock jumped beyond the grace deadline, the first failed post-resume attempt caused permanent failure, so no later attempts occurred.; critical-path effect: These calls are required to restore the remote session and directly determine reconnection latency.
- Verdict: No performance finding. The additional bounded, serialized network attempts are the intended reconnection behavior needed to restore the session, not avoidable duplicate work or an uncontrolled fan-out.

### Scenario 3: Reconnect succeeds, reaches permanent failure, or the connection is disposed during reconnection

- Critical path: A current sleep or socket attempt completes, the loop observes success/failure/disposal, and then disposes the new scheduler. Scheduler disposal is off the network critical path and constant time.
- Scaling input: Number of concurrently disconnected persistent connections, normally management plus extension host; scheduler state is constant-sized per loop.
- Effective concurrency: Per-connection serialization remains enforced; cleanup executes once after the loop exits.
- Cache behavior: No cache is involved. The scheduler retains only a callback, counter, and interval handle, all released on normal loop completion; if it reaches the deadline first, it self-clears its interval.
- Mechanism confidence: High for normal and deadline cleanup paths based on the scheduler implementation and loop structure; no credible exception path was found that makes the added resource unbounded.
- Magnitude uncertainty: A pre-existing unresolved address/connect operation could delay final cleanup, but the added interval self-clears at the grace deadline and does not retain an unbounded history.
- Expensive boundaries:
  - network at <code>src/vs/platform/remote/common/remoteAgentConnection.ts: PersistentConnection.\_runReconnectingLoop</code>: Finish the current socket reconnection attempt before the loop can exit.; cardinality: At most one in-flight attempt per connection; disposal does not create an additional attempt.
    - Introduced by diff: false; previous behavior: The same current wait or connect had to settle before the loop exited; there was no process-time scheduler to clear.; critical-path effect: The existing in-flight wait/connect may delay loop exit; the added scheduler does not extend that operation and is cleared immediately afterward.
- Verdict: No cleanup-lifecycle finding. The new resource is constant-sized, disposed after loop completion, and self-clearing at expiration.

**Summary:** Reviewed the complete three-file diff and traced the scheduler through persistent management and extension-host reconnection paths, including hibernation, ordinary retries, success/failure, disposal, timer lifetime, network boundaries, retry cardinality, caching, and concurrency. No high-confidence actionable performance regression was introduced, and the PR does not establish a performance-regression fix suitable for blame-based learning.
