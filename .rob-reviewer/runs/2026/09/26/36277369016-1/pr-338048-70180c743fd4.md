# Performance review: browser: reconcile popup state missed before the renderer subscribes

[PR #338048](https://github.com/microsoft/vscode/pull/338048) at `70180c743fd40f8cc203e55197986d4145216e33`

## Findings (1)

### 1. [low] Batch reconciliation for restored browser views

**Finding ID:** `PERF-772A4A1CAAE4`  
**Location:** <code>src/vs/workbench/contrib/browserView/common/browserView.ts:673</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** main-process IPC calls, synchronous Electron WebContents state reads, and serialized navigation-state bytes including favicon data URLs  
**Scaling:** On renderer startup \`\_initializeExistingViews\` creates one model for each of N existing views in a synchronous loop; every constructor reaches this line without awaiting the previous call, so the change produces N concurrent IPC requests and serializes the sum of all favicon payloads. There is no cache, grouping, or coalescing.  
**Outcome:** A burst of main-process IPC handling and renderer serialization/deserialization competes with window-reload startup, increasing CPU/GC pressure and reducing startup responsiveness as the number of restored browser tabs and favicon bytes grows.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The restoration path called \`getBrowserViews(windowId)\` once and used the returned state to construct every model. It did not issue a second per-view command after model construction.  
**Changed behavior:** Every \`BrowserViewModel\` now unconditionally calls \`getNavigationState(id)\`. During restoration, \`\_initializeExistingViews\` loops over all returned views and constructs their models synchronously, causing all per-view calls to be queued together after the existing aggregate \`getBrowserViews\` call.  
**Confidence:** 0.94 — The production call path, one-call-per-constructor multiplicity, synchronous restoration loop, IPC proxy boundary, and duplicate state fields are directly established in repository code. Exact user-visible delay depends on the number of restored views and favicon sizes, so severity is low rather than the mechanism being speculative.

**Causal diff evidence:** Added line 673 unconditionally invokes \`this.browserViewService.getNavigationState(this.id)\` from each model constructor; no equivalent per-model IPC existed before the PR because models used the state from the aggregate \`getBrowserViews\`/creation response.

Reloading a window with many integrated-browser tabs adds one IPC round trip per tab in a concurrent burst; large favicon data URLs are also copied over IPC for a second time. The reconciliation is not awaited by model creation, but its main/renderer work runs during startup and scales linearly with restored views.

**Evidence:** \`BrowserViewWorkbenchService.\_initializeExistingViews\` first performs one \`getBrowserViews\` IPC and then loops synchronously over all views calling \`\_createModel\`; \`\_createModel\` constructs \`BrowserViewModel\`, whose new line 673 immediately starts \`getNavigationState\`. The main implementation synchronously reads URL/title/history/loading state and returns \`lastFavicon\`; the initial \`getBrowserViews\` response already obtained the same fields through \`view.getState()\`. Favicon fetching accepts data URLs and buffers fetched images without a size cap, so the duplicate snapshot can carry nontrivial bytes.

**Suggested direction:** Coalesce reconciliation requests created in the same turn into one batched \`getNavigationStates(ids)\` IPC after all per-view listeners have been registered, then dispatch the returned states to their models. Keep a single-view path for isolated popup creation so the subscription-before-snapshot ordering remains intact.

### Scenario 1: Renderer/window reload restores browser views that remain alive in the main process

- Critical path: \`BrowserViewWorkbenchService\` asynchronously calls \`getBrowserViews(windowId)\` to discover all existing views. Model construction then completes without awaiting reconciliation, so the new snapshots are off the model-availability critical path but execute during startup and contend for main/renderer IPC and CPU.
- Scaling input: Number N of integrated-browser views owned by the reloading window after grouping by view ID; payload cost also scales with the summed lengths of their favicon data URLs.
- Effective concurrency: The restoration loop constructs models synchronously and each constructor starts a promise without awaiting it, producing an unbounded burst up to N in-flight reconciliation calls. There is no batcher, limiter, cache, or coalescer.
- Cache behavior: Every model reconciles unconditionally. Warm main-process state and an immediately preceding \`getBrowserViews\` response do not suppress or coalesce the call; unchanged favicon strings are still serialized before renderer equality checks.
- Mechanism confidence: High: the synchronous N-model loop, constructor call, ProxyChannel IPC boundary, and duplicate fields are directly visible.
- Magnitude uncertainty: Typical users may have only a few browser tabs and normal favicons are small; users with many retained tabs or unusually large favicon data see proportionally more work. This uncertainty supports low severity.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts:\_initializeExistingViews</code>: Fetch all existing browser-view info and full state in one response; cardinality: One call for the window, returning N view states
    - Introduced by diff: false; previous behavior: The same single aggregate call supplied model state before the diff.; critical-path effect: Must complete before existing models can be constructed
  - IPC at <code>src/vs/workbench/contrib/browserView/common/browserView.ts:BrowserViewModel.\_reconcileNavigationState</code>: Fetch current navigation state for one view, including favicon data URL; cardinality: N calls for N restored views; constructors launch them without awaiting, so effective concurrency is N
    - Introduced by diff: true; previous behavior: No second per-view command followed the aggregate state response.; critical-path effect: Not awaited for model construction, but all requests execute during renderer startup and consume main/renderer IPC, serialization, CPU, and GC capacity
- Verdict: Reportable low-severity boundary fan-out because the diff changes one aggregate startup fetch into one aggregate fetch plus N concurrent per-view fetches.

### Scenario 2: A page opens one popup or a caller creates one new integrated-browser view

- Critical path: The main process creates/loads the view and sends its initial state. The renderer constructs a model, registers dynamic listeners, and starts one reconciliation snapshot. The snapshot is not awaited by model construction or editor opening; it is required only to recover events missed before subscription.
- Scaling input: Number of concurrently created views/popups after deduplication by browser view ID, plus favicon byte size.
- Effective concurrency: One reconciliation per model; isolated creation is one call, while many simultaneous creations are not globally limited. Favicon requests use a per-view URL promise cache but no cross-view limiter.
- Cache behavior: Navigation reconciliation has no cache and always runs once per model. Favicon fetches are cached per view URL; successful current favicon strings are returned in both initial and reconciliation state.
- Mechanism confidence: High for the extra IPC and ordering; low concern for a standalone single view because it is off the critical path and bounded.
- Magnitude uncertainty: Normal popup creation is isolated, making one lightweight extra IPC inexpensive; burst creation is less common and overlaps the restoration issue.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts:\_getOrCreateLazy / main onDidCreateBrowserView</code>: Create or discover the browser view and return initial full state; cardinality: One response per newly created view
    - Introduced by diff: false; previous behavior: Initial state was already returned once per created view.; critical-path effect: The create/discover response is required before model construction
  - IPC at <code>src/vs/workbench/contrib/browserView/common/browserView.ts:BrowserViewModel.\_reconcileNavigationState</code>: Read lightweight navigation state after listeners subscribe; cardinality: One additional call per created view; multiple simultaneous popups can produce one call each
    - Introduced by diff: true; previous behavior: No post-subscription state read existed, so pre-subscription events could be missed.; critical-path effect: Fire-and-forget and off editor/model creation's awaited critical path, though state reconciliation awaits it
  - network at <code>src/vs/platform/browserView/electron-main/browserView.ts:page-favicon-updated handler</code>: Fetch and base64-encode a page favicon; cardinality: At most one attempt per favicon candidate URL until success, cached per view by URL

- Verdict: No separate finding: one post-subscription snapshot is a bounded intentional cost for the race fix; the actionable scaling problem is the uncoalesced restoration burst already reported.

### Scenario 3: Live page navigation, title/loading/favicon updates, and model consumers

- Critical path: Electron emits a per-view event in main, the renderer model updates authoritative local state, then synchronously notifies local consumers such as editor labels and navigation UI. Cross-origin navigation may issue the existing forced zoom IPC before local event notification, but it is fire-and-forget.
- Scaling input: Live browser event frequency and number of local model consumers.
- Effective concurrency: Cross-process delivery is consolidated to one subscription per model/event type; consumers fan out synchronously in-process. Zoom calls remain one per navigation and are not coalesced, unchanged from before.
- Cache behavior: Model fields suppress reconciliation events when snapshot state equals current state. Live events are not cached; zoom index lookup uses existing zoom-service state.
- Mechanism confidence: High based on the replaced proxy getters and added local emitters.
- Magnitude uncertainty: Consumer work varies by enabled browser features, but the PR reduces duplicate cross-process subscriptions rather than increasing them.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/browserView/common/browserView.ts:BrowserViewModel constructor relay registrations</code>: Forward dynamic navigation/title/loading/favicon events from main to renderer; cardinality: One cross-process subscription and one delivered event per event type per model, followed by local emitter fan-out

- Verdict: No regression: the changed relay architecture reduces IPC event fan-out and preserves the existing per-navigation zoom cost.
