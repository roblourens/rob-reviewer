### 1. [low] Remove the second Discover render when the page becomes visible

**Finding ID:** `PERF-C054AAC903C3`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationDiscoveryPage.ts:1783</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** DOM nodes, list rows, buttons, hover/listener objects, layout work, and image elements  
**Scaling:** The duplicate cost grows with the loaded result/card count and occurs every time the Discover page transitions from hidden to visible.  
**Outcome:** Extra synchronous UI work and allocation when switching to Discover, increasing avoidable latency and GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The existing branch rendered once when cached content was shown; when a catalog load was needed, loadCatalog rendered the loading state itself.  
**Changed behavior:** The new unconditional render() runs after the branch, so the cached branch calls render twice back-to-back, and the loading branch also renders once inside loadCatalog before this second call.  
**Confidence:** 1.00 — The duplicate synchronous calls and full rebuild behavior are directly visible in the changed method with no timing or control-flow assumptions.

**Causal diff evidence:** Added line 1783 unconditionally invokes this.render() while the unchanged else branch at line 1781 already does so, and loadCatalog also synchronously renders its loading state.

Opening or returning to Discover rebuilds the same result list or clears and recreates all browse sections/cards twice before scheduling layout, which can make section switching less responsive on populated pages.

**Evidence:** setVisible() lines 1777-1783 calls render() in the else branch and then immediately calls it again unconditionally. render() invokes renderSearchResults() or renderBrowse() and layout(); renderSearchResults replaces the whole list, while renderBrowse clears browseSections and recreates sections, cards, buttons, hovers, listeners, and images for loaded catalog entries.

**Suggested direction:** Keep exactly one render path: remove the unconditional call or remove the branch-local call and only render explicitly when loadCatalog does not already render.

### 2. [medium] Coalesce connector status polling across pending operations

**Finding ID:** `PERF-B8AB1C90D024`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts:367</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** HTTPS catalog requests, response bytes, JSON parsing, and connector object allocations  
**Scaling:** Each connect or disconnect operation performs a full catalog GET immediately and then every 2 seconds for up to 5 minutes, so one unresolved action can issue about 150 GETs and N simultaneous connector actions can issue about 150×N requests for the same account catalog.  
**Outcome:** Excessive network traffic and repeated parsing/allocation, with contention that can delay status updates and other workbench requests.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no connector connect/disconnect polling path and therefore no repeated full-catalog request per pending connector action.  
**Changed behavior:** The new connect loop calls refresh() on every iteration; refresh bypasses the 60-second getConnectors cache and sends a new authenticated query. The disconnect loop repeats the same pattern, while installation deduplication is keyed per connector rather than per shared catalog.  
**Confidence:** 0.99 — The call path, request interval, timeout, full-catalog network boundary, response bound, and per-connector concurrency are explicit in the changed code; only the typical number of simultaneously pending connectors is uncertain.

**Causal diff evidence:** Added line 367 invokes this.refresh(operation.token) inside the new 2-second/5-minute connect polling loop; the same added construction appears in disconnect().

If authorization remains open or several connectors are connected from Discover in parallel, VS Code repeatedly downloads and parses the same catalog (responses are allowed up to 5 MiB) every two seconds per operation for as long as five minutes.

**Evidence:** connect() lines 365-372 repeatedly await refresh(), and disconnect() has the same loop. refresh() line 323 calls request({ type: 'query' }); request() line 495 crosses ICopilotConnectorsRequestService, whose native implementation performs GET /plugins with cache disabled and buffers/parses the response. The 2-second interval and 5-minute timeout bound this at roughly 150 catalog reads per unresolved operation. CustomizationMarketplaceInstallService uses getConnectorOperationKey(resource), allowing different connector names to run concurrently, and CopilotConnectorsService has no in-flight catalog-refresh coalescer (its Throttler is only for Agent Host refresh).

**Suggested direction:** Use one account-scoped, cancellable polling/coalescing loop for all pending connector names (or at minimum coalesce in-flight refresh calls), apply backoff, and let cancellation unsubscribe one operation without cancelling a refresh still needed by others.

### 3. [medium] Do not force a remote catalog refresh for every session launch

**Finding ID:** `PERF-1BD01DF43038`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:774</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** runtime RPC/IPC calls and connector catalog network requests  
**Scaling:** The cost is paid once for every created or resumed Copilot SDK session, including sessions recreated after connector/configuration changes; concurrent session launches each perform their own four-call sequence.  
**Outcome:** Higher chat/session startup latency because the first turn cannot proceed until the runtime refreshes and reconciles the connector catalog.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, \_finalizeSession completed after script-safety and sandbox setup and performed no connector capability, authentication, account, or catalog-reconciliation RPCs.  
**Changed behavior:** Every connector-enabled create/resume now synchronously awaits getCapabilities(), getStatus(), getAllUsers(), and reconcile({ refreshCatalog: true }) before wrapping and exposing the session.  
**Confidence:** 0.94 — The synchronous critical path and per-launch multiplicity are explicit. refreshCatalog:true and the runtime-owned connector service establish the catalog refresh boundary; exact backend latency and runtime cache behavior are the remaining magnitude uncertainties.

**Causal diff evidence:** Added line 774 explicitly requests refreshCatalog:true from the runtime inside an awaited method newly inserted into \_finalizeSession for every create/resume.

With connectors enabled, every new or resumed chat is placed behind a forced connector catalog refresh, so normal first-message latency inherits remote catalog latency even when connector membership has not changed since the previous session.

**Evidence:** \_createSession and both resume paths now call \_finalizeSession with a launch plan; \_finalizeSession awaits \_reconcileCopilotConnectors before returning. Lines 749-774 issue three sequential runtime RPCs followed by reconcile with refreshCatalog:true. CopilotAgentSession.initializeSession awaits launcher.launch, and CopilotAgent.\_refreshSessionConfiguration destroys/resumes sessions before a send when configuration is dirty, placing this work directly on session availability and first-turn paths.

**Suggested direction:** Track catalog freshness per runtime account/change generation and request a remote refresh only for the first launch or after membership/auth invalidation; subsequent sessions should reconcile against the runtime's cached catalog (while still projecting servers per session). Coalesce concurrent launches for the same account.
