# Performance review: feature: edit previous requests

[PR #251732](https://github.com/microsoft/vscode/pull/251732) at `62299da6514a629f97cfe2cb06b208c7c743231b`

## Findings (3)

### 1. [medium] Dispose request hovers with their markdown parts

**Finding ID:** `PERF-42D04A6685E0`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatListRenderer.ts:1203</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** detached request markdown DOM nodes, managed-hover objects, map entries, timers, and DOM event listeners  
**Scaling:** Retained objects grow with every request markdown render, including repeated virtualized-row renders while scrolling and checkpoint-driven rerenders, for the lifetime of the chat renderer.  
**Outcome:** unbounded retained memory and increasing GC pressure during long chat sessions and repeated history scrolling  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the change, request markdown rendering did not create this managed hover, so disposing a virtualized markdown part did not leave a hover-service entry retaining its DOM node.  
**Changed behavior:** Each render creates a managed hover but registers it with \`this.\_register\`, tying cleanup to the whole ChatListItemRenderer instead of the short-lived markdownPart.  
**Confidence:** 0.99 — The new hover is registered on the renderer's lifetime store, while the surrounding click/focus listeners are correctly registered on markdownPart. setupManagedHover stores the target in HoverService.\_managedHovers and installs several DOM listeners until its returned disposable is disposed.

**Causal diff evidence:** The added RIGHT-side call \`this.\_register(this.hoverService.setupManagedHover(... markdownPart.domNode ...))\` explicitly extends each per-render hover to renderer lifetime.

Scrolling through or rerendering a long conversation leaves every old request DOM node and its hover listeners retained until the entire chat widget is destroyed, rather than reclaiming them when rows leave the viewport.

**Evidence:** renderMarkdown creates a new ChatMarkdownContentPart per rendered request. Its other listeners use markdownPart.addDisposable, but the added hover uses renderer-level \_register. HoverService.setupManagedHover inserts targetElement into a strong Map and removes it only in the returned disposable; the existing ChatMarkdownRenderer pattern keeps these hovers in a render-result DisposableStore.

**Suggested direction:** Register the managed hover with \`markdownPart.addDisposable(...)\` so virtualization and content-part replacement dispose the hover and release its target immediately.

### 2. [medium] Avoid reparsing every unchanged response on checkpoint changes

**Finding ID:** `PERF-AEC7642EA7E8`  
**Location:** <code>src/vs/workbench/contrib/chat/common/chatModel.ts:765</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work for markdown lexing and code-block model updates across prior responses  
**Scaling:** On both entering and leaving edit mode, work grows with the number and total text size of unchanged responses before the edited request; editing a late request reparses nearly the entire conversation twice.  
**Outcome:** increased input latency and UI-thread CPU/GC pressure when starting or ending request editing in long chats  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, checkpoint events and the per-response session listeners did not exist, so clicking or canceling request editing did not route historical response content through ChatViewModel.updateCodeBlockTextModels.  
**Changed behavior:** Each response subscribes to setCheckpoint and treats equality (\`old === new\`) as a change. Unchanged responses therefore fire \_onDidChange, and ChatViewModel synchronously re-lexes every complete response before accumulated UI updates can coalesce.  
**Confidence:** 0.99 — The added equality check is directly inverted, and the traced response-change listener synchronously calls updateCodeBlockTextModels, which lexes the complete response with marked before widget event coalescing occurs. The only magnitude uncertainty is typical conversation length and response size.

**Causal diff evidence:** The added RIGHT-side line \`const didChange = this.\_shouldBeBlocked === isDisabled;\` makes unchanged checkpoint state trigger response change events; this entire checkpoint listener is new in the PR.

Editing a request near the end of a long conversation synchronously reparses all preceding response markdown on both edit start and edit end, causing visible pauses as history size and response length grow.

**Evidence:** ChatResponseModel's added listener computes \`didChange\` with equality and fires for unchanged responses. ChatViewModel.onAddResponse handles every such event by calling updateCodeBlockTextModels for complete responses; that method runs marked.lexer over the full response and updates each code block. ChatWidget only coalesces downstream view events, so this parsing has already happened per response.

**Suggested direction:** Update blocked state through the single checkpoint model event without emitting content-change events per response, or at minimum use inequality and a distinct metadata-only change reason that skips updateCodeBlockTextModels.

### 3. [medium] Own inline inputs in an edit-scoped disposable store

**Finding ID:** `PERF-46181663CD1E`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatWidget.ts:1110</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** disposed ChatInputPart/editor object graphs, child instantiation services, context-key scopes, DOM references, and per-input subscription disposables  
**Scaling:** Retained state grows by one heavyweight ChatInputPart, one scoped service, and multiple widget-level subscriptions for every request-edit cycle until the ChatWidget itself is destroyed.  
**Outcome:** steadily increasing retained memory and GC pressure in a long-lived chat panel after repeated request edits  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Previously createInput constructed the primary ChatInputPart once for the widget, so widget-lifetime registration matched the resource lifetime.  
**Changed behavior:** The edit branch now constructs a fresh inline ChatInputPart on every clicked request and registers it and its scoped instantiation service in the widget's lifetime store. Edit completion calls \`this.input.dispose()\`, but that does not remove the object from the parent DisposableStore's Set; createInput and clickedRequest also add each edit's subscriptions to the same lifetime store.  
**Confidence:** 0.98 — createInput is called for every edit and the new input plus child instantiation service are added to ChatWidget's lifetime DisposableStore. DisposableStore retains registered values in a Set until delete/clear, even when callers invoke dispose directly; the PR never deletes these per-edit values.

**Causal diff evidence:** The added RIGHT-side assignment \`this.inlineInputPart = this.\_register(scopedInstantiationService.createInstance(ChatInputPart, ...))\` places a per-edit resource in a widget-lifetime owner.

Repeatedly editing requests in the same chat retains all prior inline editor/input graphs even after each editor is closed, so memory use grows with edit count rather than returning to a stable baseline.

**Evidence:** clickedRequest invokes createInput for every edit. The added line wraps each inlineInputPart in this.\_register, and the preceding added line does the same for its child service. DisposableStore.add stores disposables in \`\_toDispose\`; only delete/clear removes them. Submit/cancel paths directly dispose the input but never delete either object from the widget store.

**Suggested direction:** Use a MutableDisposable or dedicated edit-scoped DisposableStore containing the child service, inline input, and all per-edit listeners; clear that store from the common edit teardown path instead of registering each edit on ChatWidget.
