## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts:2514` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/widget/chatWidget.ts:2627`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/chatWidget.ts`  
**Introducing commit:** `c6e8ac17784881782a3e0bcdb0728d8a12301b3c`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.99

**Mechanism:** Every completed inline edit left event registrations, autoruns, the editor/model/DOM graph, and scoped services reachable from widget-lifetime owners, so retained memory and listener work grew linearly with edit count.

**Symptom:** Repeated inline request edits accumulated editor models, detached DOM, listeners, and approximately one megabyte of retained heap per measured edit cycle until the chat widget was disposed.

**Fixed behavior:** All resources specific to an inline edit are now owned by a per-edit store and released by finishedEditing, bounding retained edit resources to the active edit rather than the widget lifetime.

**Evidence:** In the base revision, createInput registered each inline input focus listener at line 2627 and the rest of the inline input listeners and autoruns in ChatWidget.\_store, so their registrations remained rooted for the widget lifetime after finishedEditing. The inline ChatInputPart holder and child instantiation service were likewise not cleared at edit completion. The changed code passes a per-edit store into createInput, adds those registrations and the child service to it, clears the inline input and paste-target holders, and clears that store at changed line 2514. The PR's heap measurements show per-edit retention of CodeEditorWidget, TextModel, detached DOM, and emitter/disposable graphs before the change and flat edit-only counts after it.
