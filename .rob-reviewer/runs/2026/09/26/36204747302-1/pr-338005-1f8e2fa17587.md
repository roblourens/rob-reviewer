# Performance review: Refactor Markdown rich editor messaging to HubRPC

## Findings (2)

### 1. [medium] Keep per-keystroke edits on a one-way channel

**Finding ID:** `PERF-CCA327C8B631`  
**Location:** <code>extensions/markdown-language-features/src/preview/markdownEditorProtocol.ts:66</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** webview/extension-host IPC messages, client-side pending-request entries, and Promise objects  
**Scaling:** Each source-text change creates one JSON-RPC request and one response, so typing N edits now causes 2N cross-boundary messages and retains N request completions until the serialized WorkspaceEdit queue catches up; the same pattern also affects the bidirectional embedded-editor message stream.  
**Outcome:** excessive IPC and allocation/GC pressure on continuous typing or chatty embedded-editor sessions, reducing extension-host/webview throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The renderer posted each edit as a one-way webview message. The extension host enqueued the WorkspaceEdit, but no acknowledgement crossed back to the webview and no client request remained pending.  
**Changed behavior:** \`edit\` is now declared as \`requestType(..., z.void())\`. \`Editor\` invokes it from the source-text autorun for every local edit and immediately discards the returned result through \`\#send\`; HubRPC must still correlate the request and send a void response after the host's serialized edit completes.  
**Confidence:** 0.97 — The per-edit call path, serialized host queue, discarded Promise result, and old one-way behavior are all explicit in the diff. Exact millisecond cost varies by platform and typing rate, but the 2x boundary-message count and backlog-proportional pending requests are deterministic.

**Causal diff evidence:** Added line 66 changes the edit event to \`requestType(..., z.void())\`; deleted editor/provider hunks show the prior one-way \`postMessage({ type: 'edit', ... })\` path, while added editor.ts lines 483-486 call the request from the text-change autorun without consuming a result.

Typing in the rich Markdown editor generates an otherwise-unused response for every keystroke. If WorkspaceEdit processing falls behind input, pending RPC promises grow with the backlog, while nested editor transport messages declared the same way can further amplify the webview/extension-host traffic.

**Evidence:** The changed source-text autorun calls \`this.\#host.edit(...)\` for every text change, while the handler awaits \`editQueue.enqueue\`, whose tasks serialize \`workspace.applyEdit\`. HubRPC tests added in this PR explicitly verify request correlation and rejection of pending calls on close, confirming that even void methods are tracked requests. The deleted implementation used one \`postMessage\` per edit with no response path.

**Suggested direction:** Use a typed one-way notification for \`edit\` (and the two \`codeBlockEditorHostTransportMessage\` event streams), preserving transport ordering and the existing host-side edit queue. Keep request/response only for operations whose result or completion is actually consumed, such as ready barriers, history, and code-block resolution.

### 2. [medium] Avoid recursively parsing RPC payloads in the transport

**Finding ID:** `PERF-A9E7F08F046F`  
**Location:** <code>extensions/markdown-language-features/src/preview/markdownEditorRpc.ts:17</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU work and temporary arrays/objects produced while validating full JSON payload trees  
**Scaling:** The added \`z.json()\` checks traverse payloads by total nested value count. Highlight responses contain one object per syntax token, so the added work is O(token count) for every completed request, including stale responses from rapid edits; opaque embedded-editor payloads scale with their full message size as well.  
**Outcome:** increased webview/extension-host CPU and GC pressure, delaying syntax-highlight updates and increasing typing jank for large or frequently edited fenced code blocks  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous authenticated message switch checked message type/IDs and passed highlight token arrays or opaque embedded-editor payloads directly to their consumers; stale highlighting results were rejected by the highlighter without first running a generic recursive JSON parse.  
**Changed behavior:** Every received JSON-RPC request/result/error now goes through \`rpcMessage.safeParse\`, whose \`params\`, \`result\`, and \`error.data\` use recursive \`z.json()\` schemas. HubRPC then applies the method-specific schemas such as \`highlightResult\`, so large payloads are traversed generically before the authoritative interface validation and before request-version stale-result checks.  
**Confidence:** 0.94 — The recursive schema, receive path, token-array shape, per-edit request frequency, and post-response stale check are directly visible in changed code. Payload sizes vary by document, affecting severity but not the extra O(payload-size) mechanism.

**Causal diff evidence:** Added line 17 defines all RPC results as \`z.json()\`; added lines 42-46 run \`rpcMessage.safeParse\` before dispatch, and the new protocol separately defines the token-array \`highlightResult\` validator used by the highlight request.

Opening, editing, or theme-refreshing Markdown with large fenced code blocks returns large token arrays. Rapid edits can leave multiple full-highlighting requests in flight; each stale result still pays the newly added full-tree parse before \`HighlighterDocument\` discards it, wasting CPU and allocations on the rendering path.

**Evidence:** \`MarkdownEditorRpcTransport\` calls \`rpcMessage.safeParse\` before forwarding any message. The new highlight result schema is an array of token objects, \`HighlighterDocument.update\` requests full highlighting on every code-block edit, and staleness is checked only after awaiting the RPC result. The protocol's method-specific \`highlightResult\` schema already provides runtime validation.

**Suggested direction:** Validate only the JSON-RPC envelope shape in \`MarkdownEditorRpcTransport\` (protocol version, id, method, and presence of params/result/error), leaving payloads as unknown for HubRPC's method-specific runtime schemas. This preserves authentication and typed validation while removing the redundant full-tree traversal.

- Effective concurrency: Reload is ordered by an edit-queue barrier; connection close aborts in-flight handlers and detaches the transport subscription. Disposal is idempotent.
- Cache behavior: Per-generation pending messages and listeners are cleared; embedded runtime maps are disposed; no unbounded retained generation state was found.

- Verdict: No cleanup-lifecycle regression found; the new connection and transport are closed on both reload and disposal.
