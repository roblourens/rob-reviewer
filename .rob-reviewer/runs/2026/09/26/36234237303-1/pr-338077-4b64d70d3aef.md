**Relevant issue families:** repeated-work, synchronous-ui-work, cleanup-lifecycle, serialization-allocation

### Scenario 1: Open and close the flat or tabbed model picker

- Critical path: Opening synchronously creates one telemetry session, builds picker items, and renders the list. The tabbed picker may also compute heights for the regular Copilot list and one alternate Auto/routing list before first layout; height computation only loops over item metadata. Closing the UI is synchronous and does not wait for pending configuration saves; only the close telemetry event is deferred.
- Scaling input: The regular sizing pass scales with the number of Copilot rows as before. The new alternate sizing pass contains the bounded first-party routing choices (Auto tiers and HydraFusion) when an explicit fallback model exists, so it does not duplicate the full provider catalogue.
- Effective concurrency: UI construction and measurement run serially on the UI thread. A warm picker retains its measured sizing; refreshes recompute serially. No subprocess, IPC, database, or network fan-out is introduced.
- Cache behavior: Tabbed picker creation is lazy. Its measured sizing is retained after the first sizing pass, while model-card caches are cleared on hide. Flat picker items and hover disposables remain scoped to one open.
- Mechanism confidence: High: the changed build callback, arithmetic-only computeHeightForItems implementation, telemetry constructor, and hide callbacks were traced directly.
- Magnitude uncertainty: Exact model catalogue size and telemetry appender cost vary, but the introduced alternate list and event cardinality are bounded.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerTelemetry.ts:154 and :230</code>: Dispatch model-picker opened and closed telemetry through the telemetry service appenders; cardinality: Two events per completed picker session, plus one event per explicit interaction such as model/configuration/pin change
    - Introduced by diff: true; previous behavior: There were no picker open/close events; model-change telemetry already dispatched once per selection.; critical-path effect: The open event is synchronously handed to configured appenders during open; close dispatch is immediate unless configuration writes are pending, in which case only telemetry waits.
- Verdict: No reportable regression. The extra first-layout CPU/allocation is bounded and the telemetry volume is one open/close pair per user session.

### Scenario 2: Search or filter models in the picker

- Critical path: Typing follows the existing list filtering path; opening tabbed search rebuilds the picker once, and subsequent input filters the list. The new callbacks only set an in-memory boolean on the telemetry session.
- Scaling input: Existing filtering and cross-provider search scale with the effective model count. The diff adds O(1) state mutation per typed input event and no per-model boundary operation.
- Effective concurrency: All work is synchronous on the UI thread with no added queue, parallelism, IPC, filesystem, database, subprocess, or network operation.
- Cache behavior: Search remains transient and resets when the popup hides. No new cache or retained query data is introduced; query text is not stored in telemetry.
- Mechanism confidence: High: both onType and onDidChangeFilter lead only to logSearch(), which assigns a boolean.
- Magnitude uncertainty: Large third-party model catalogues can make the pre-existing search rebuild expensive, but the changed telemetry callback does not amplify that collection work.
- Expensive boundaries: none found
- Verdict: No reportable regression; the diff adds constant work to an existing input path.

### Scenario 3: Select or pin/unpin a model

- Critical path: Selection applies the model and closes the picker as before, with enriched model-change telemetry and a new close event. Pinning still persists the pinned list and rebuilds/reopens the flat picker; the diff additionally logs one pin-change event and reuses the same telemetry session.
- Scaling input: Cost scales with explicit user interactions, not with all models. Model classification scans the locally held vendor descriptors once per logged event.
- Effective concurrency: Interactions are serialized by the UI. Flat-picker pinning closes and immediately rebuilds one picker; no concurrent fan-out is added.
- Cache behavior: The model cache and pinned ID storage behavior are unchanged. Reopened flat pickers reuse the same telemetry session only for the pinning interaction.
- Mechanism confidence: High: pin/unpin implementations and all callers were inspected, including the pre-existing persistence call.
- Magnitude uncertainty: Telemetry appender implementation differs by product build, but event cardinality is strictly tied to user actions.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/common/languageModels.ts:2459 and :2470</code>: Persist the pinned model ID list through the profile storage service; cardinality: One existing storage write per real pin or unpin change
    - Introduced by diff: false; previous behavior: The same \_savePinnedModels storage write occurred per real pin/unpin change.; critical-path effect: Occurs synchronously in the existing pin/unpin action path before listeners fire.
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerTelemetry.ts and src/vs/workbench/contrib/chat/common/languageModels.ts:2489</code>: Dispatch model-change, pin-change, and picker-close telemetry; cardinality: One model-change event per selection, one pin-change event per effective pin state transition, and one close event per picker session
    - Introduced by diff: true; previous behavior: Model selection already emitted one telemetry event; pin changes and picker close did not emit their new events.; critical-path effect: Telemetry is synchronously handed to appenders but does not add a waited network request. Pin telemetry follows the existing storage write.
- Verdict: No reportable regression; added telemetry is bounded to one event per effective action.

### Scenario 4: Change model configuration and dismiss or reopen the picker

- Critical path: A choice reads current local configuration, queues one save per model key, and writes the existing scoped/global configuration. The picker can dismiss immediately. The diff snapshots pending promises at close so only the close telemetry event waits until existing saves and their change events settle.
- Scaling input: Writes scale with deliberate configuration selections. SequencerByKey coalesces ordering per model identifier but does not coalesce distinct choices; pending keys are removed when their promise settles. A close snapshots only currently pending model keys.
- Effective concurrency: Configuration saves are serialized per model identifier; different model identifiers may proceed independently. Close telemetry joins the current pending promises without starting duplicate filesystem operations.
- Cache behavior: Configuration values are cached in the per-editor store and model service. The WeakMap is keyed by configuration scope, and SequencerByKey removes settled keys; there is no persistent accumulation from completed edits.
- Mechanism confidence: High: setModelConfigValues, SequencerByKey cleanup, the configuration store, language-model configuration file save, and close callbacks were traced.
- Magnitude uncertainty: Filesystem save duration varies, but it is pre-existing and off the picker-close critical path in the new coordination logic.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/widget/input/chatModelConfigurationStore.ts:122 and src/vs/workbench/contrib/chat/browser/languageModelsConfigurationService.ts:215</code>: Persist editor-scoped configuration through storage and save the profile languageModels configuration file; cardinality: One existing scoped storage update and at most one serialized profile configuration-file save per effective user configuration change
    - Introduced by diff: false; previous behavior: Configuration changes already awaited the same setModelConfiguration persistence path.; critical-path effect: The action awaits the save for post-save UI/configuration reporting, but picker dismissal itself does not await it. This boundary predates the diff.
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerTelemetry.ts:194 and :230</code>: Dispatch configuration-change telemetry after save and close telemetry after all pending per-scope saves settle; cardinality: One configuration event per effective changed property and one close event per picker session
    - Introduced by diff: true; previous behavior: Configuration-change telemetry was already emitted after each successful save, without correlated close telemetry or save-order waiting.; critical-path effect: Ordering is enforced only for telemetry; Promise.allSettled is not awaited by the UI close path.
- Verdict: No reportable regression. The diff neither adds configuration writes nor blocks dismissal, and pending telemetry retention is bounded by outstanding user edits and released when their existing saves settle.
