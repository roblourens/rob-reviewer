# Performance review: feat: bundle generated code cache into product

[PR #336410](https://github.com/microsoft/vscode/pull/336410) at `747914899a9ae2165732feed9e6f4b9df64ddcdc`

## Findings (2)

### 1. [medium] Merge both architecture caches into the universal macOS app

**Finding ID:** `PERF-F2633E46B023`  
**Location:** <code>build/darwin/create-universal-app.ts:51</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** Packaged arm64 bytecode cache files and associated download, extraction, filesystem, and disk bytes  
**Scaling:** The wasted footprint scales with every generated entry across the five cache kinds; all of those bytes are unusable for every x64 execution of the universal product.  
**Outcome:** Intel users pay larger download and installation I/O and disk usage while receiving no compile-cache startup benefit.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR the universal package contained no compile-cache payload and Intel launches did not pay to download/install architecture-incompatible cache files.  
**Changed behavior:** The universal package is made to contain the arm64-generated cache tree in both merge inputs, so the merged artifact ships that tree even when running as x64.  
**Confidence:** 0.99 — The generation gate, tag format, universal merge input, and runtime architecture-prefix check are all explicit in the changed code. The only magnitude uncertainty is the compressed size of the generated cache tree, not whether Intel processes reject it.

**Causal diff evidence:** The added line copies the whole \`node-compile-cache\` directory from whichever macOS input has it into the other. \`shouldGenerateNodeCompileCache\` generates only for \`darwin/arm64\`, while runtime matching requires a \`${process.version}-${process.arch}-\` tag.

Any Intel Mac using the universal archive downloads and installs all five arm64 cache sets, then each Node process finds no x64-prefixed directory and falls back to parsing/compiling as before.

**Evidence:** \`shouldGenerateNodeCompileCache\` returns true for Darwin only when the build target is arm64 (build/lib/nodeCompileCache.ts:32). The new cross-copy operates at the cache root, so the x64 input receives the arm64 tag directories. At runtime \`enableNodeCompileCache\` looks specifically for \`${process.version}-${process.arch}-\`; an x64 process therefore cannot consume the copied arm64 entries.

**Suggested direction:** Generate an x64 cache in the x64 artifact and merge the per-kind architecture tag directories so the universal app contains both arm64 and x64 entries; if x64 generation is unavailable, do not copy/package the unusable arm64 tree in the Intel-only artifact path.

### 2. [medium] Limit eager compilation to the measured startup modules

**Finding ID:** `PERF-953ECCFFD0E9`  
**Location:** <code>src/vs/base/node/nodeCompileCache.ts:84</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** CPU work and packaged bytecode bytes for inner functions in every startup-loaded module across five processes  
**Scaling:** Generation and shipped cache size grow with the total number and size of functions in every module loaded while main, extension host, shared process, pty host, and agent host initialize, rather than with the small measured module set needed for startup.  
**Outcome:** Increased product-build CPU plus larger archives, downloads, and installation I/O from bytecode that may never execute.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR the product build did not eagerly compile or package bytecode for these modules; a bounded implementation would eagerly compile only selected measured startup modules and leave other functions lazy.  
**Changed behavior:** Every inner function in every module loaded by each generated process is eagerly compiled and serialized into the packaged cache.  
**Confidence:** 0.94 — The added option is explicitly the boolean all-eager mode, its adjacent comment says it includes inner functions, and the same file declares the bounded moduleIdentifiers form. Generation starts all five cache kinds, so the broader compilation and retained bytecode are directly reachable; only the exact artifact-size increase is unmeasured.

**Causal diff evidence:** The added generation-only options at lines 78-84 set \`eager: true\`; the newly added declaration at lines 12-15 exposes \`{ moduleIdentifiers: string\[\] }\` as the selective alternative, while app.ts starts all critical Node processes during generation.

Every official cache-generating product build performs the extra compilation, and every user downloads and installs the resulting unused bytecode; the cost increases as startup-loaded modules gain functions.

**Evidence:** \`enableCompileCache\` receives generation-only \`eager: true\`, and the code comment confirms this includes inner functions. Generation explicitly starts the window/extension host, shared process, pty host, and agent host before flushing each cache, so the setting applies across all five startup module graphs. The local API declaration provides a module-identifier allowlist, proving a bounded alternative exists.

**Suggested direction:** Pass the measured entry points/dependencies through \`eager: { moduleIdentifiers: \[...\] }\` and leave all other loaded modules in the default lazy mode before flushing the packaged caches.
