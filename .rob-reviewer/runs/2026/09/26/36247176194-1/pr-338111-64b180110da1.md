## Findings (1)

### 1. [medium] Keep disabled and dismissed nudges out of PR polling

**Finding ID:** `PERF-33F2577B3670`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionArchiveNudge.ts:301</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub REST requests and retained polling/model references  
**Scaling:** For the currently viewed eligible session, work scales with its distinct associated PRs: each PR starts with at least two GETs (PR details and paginated reviews) and repeats them every 60 seconds; review lists over 100 entries add further page requests. The polling continues while that chat view remains active until a session's PRs are all merged and the one-time trigger is emitted.  
**Outcome:** Unnecessary recurring network traffic, API-rate-limit consumption, and background CPU/allocation for users who disabled or already dismissed the feature.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The old gate returned from \`eligibleSession\` whenever the nudge setting was disabled or the current session was dismissed, so \`models\` never acquired PR model references, called \`refresh()\`, or started polling for that nudge.  
**Changed behavior:** The new condition applies the disabled/dismissed gate only after \`experimentTriggerPending\` becomes false. On a disabled or dismissed nudge with an open PR, pending remains true, so the derived \`models\` path creates references, refreshes every PR immediately, and keeps their one-minute pollers alive despite no UI being shown.  
**Confidence:** 0.99 — The before/after gate and the full call path to concrete GitHub GET requests are explicit. The only magnitude uncertainty is how often users leave a disabled/dismissed eligible session with open PRs selected and how many PRs/reviews it contains; this affects severity, not the mechanism.

**Causal diff evidence:** The added \`\!this.\_nudgeService.experimentTriggerPending.read(reader) &&\` prefix on line 301 bypasses the pre-existing \`\!enabled \|\| isDismissed\` early return until a merged-PR trigger is observed. This directly activates the unchanged model refresh/polling block for states that previously never reached it.

Opening a completed session with one or more open PRs now generates GitHub requests indefinitely even when \`chat.agentSessions.archiveNudge.enabled\` is false or that session's nudge was dismissed. A session with N PRs causes at least 2N immediate requests and roughly 2N requests per minute while open, potentially more for paginated reviews.

**Evidence:** \`eligibleSession\` now permits disabled/dismissed sessions while the trigger is pending (changed line 301). Its consumer at lines 311-317 maps every associated PR to \`createPullRequestModelReference\`, calls \`model.refresh()\`, and calls \`model.startPolling()\`. \`GitHubPullRequestModel.refresh()\` issues \`getPullRequest\` and \`getReviews\` concurrently, while \`startPolling()\` schedules another refresh every 60,000 ms. The new test explicitly changes the disabled case from expecting no requests to expecting a PR request, corroborating that this boundary work is intentional and diff-introduced.

**Suggested direction:** Preserve the disabled/dismissed gate for the polling model. Derive the trigger from already-available session/PR summary state if possible, or perform a bounded one-shot status lookup only when needed; do not start recurring full PR-and-reviews polling solely to emit telemetry.
