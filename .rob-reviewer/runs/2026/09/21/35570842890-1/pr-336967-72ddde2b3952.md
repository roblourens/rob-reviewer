# Performance review: Add explicit Responses API prompt caching

[PR #336967](https://github.com/microsoft/vscode/pull/336967) at `72ddde2b3952245d915918309d6fa8c458e63d5d`

## Findings (1)

### 1. [medium] Keep implicit caching when no breakpoints were inserted

**Finding ID:** `PERF-9A14C233B363`  
**Location:** <code>extensions/copilot/package.json:4097</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** uncached server-side prompt-token processing on existing Responses API calls  
**Scaling:** The wasted processing scales with the stable prompt prefix size multiplied by the number of non-agent tool-loop requests; Inline Chat permits more than nine read-only rounds and rerenders the growing previous-round history each time.  
**Outcome:** increased latency and repeated server compute for multi-round non-agent requests  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With this setting defaulting to false, supported Responses models used \`prompt\_cache\_options: { mode: 'implicit' }\`, so requests that did not contain explicit markers could still use automatic prompt caching.  
**Changed behavior:** The new true default makes \`createResponsesRequestBody\` select explicit mode for every GPT-5.6/GPT-6 Responses request, even when its messages contain no cache-breakpoint parts.  
**Confidence:** 0.97 — The default flip, global serializer gate, sole production marker-insertion call, and repeated Inline Chat request path are directly traced. The exact provider-side latency varies with prompt size and cache residency, but explicit mode without any markers necessarily removes the prior implicit-cache opportunity.

**Causal diff evidence:** Changing the contributed setting default from \`false\` to \`true\` at line 4097 activates explicit mode by default for all supported Responses requests; no corresponding marker insertion was added to non-Agent request builders.

Inline Chat and other non-Agent callers using GPT-5.6/GPT-6 send no explicit breakpoints. Their repeated tool-loop requests now reprocess the unchanged system/file/history prefix instead of receiving implicit cache hits, increasing response latency as the prompt and round count grow.

**Evidence:** \`createResponsesRequestBody\` reads this setting globally and selects explicit mode solely from the setting plus model support (\`responsesApi.ts:131-153\`), not from request location or the presence of a marker. The only production call to \`addCacheBreakpoints\` is in \`AgentIntentInvocation\` (\`agentIntent.ts:1050-1052\`). In contrast, Inline Chat directly calls \`makeChatRequest2\` with rendered messages (\`inlineChatIntent.ts:450\`) inside a loop that appends \`previousRounds\` and allows more than nine read-only rounds (\`inlineChatIntent.ts:293-383\`), without inserting markers. The serializer attaches \`prompt\_cache\_breakpoint\` only when a \`CacheBreakpoint\` part is present (\`responsesApi.ts:634-645\`), so these explicit-mode requests contain no cache anchors.

**Suggested direction:** Select explicit mode only when the serialized request actually contains at least one explicit breakpoint (or gate it to the Agent path); otherwise retain implicit mode. Alternatively, wire marker insertion into every supported request builder before enabling the default globally.

### Scenario 2: Multi-round Inline Chat tool loop on a supported GPT-5.6/GPT-6 Responses model
