### Scenario 1: Workbench startup resolves the new automatic default-sort experiment and constructs the Sessions view

- Critical path: ConfigurationDefaultOverridesContribution runs in BlockRestore and adds one treatment lookup for the registered setting; SessionsView construction then performs an in-memory profile-storage read and, only without a valid stored preference, an in-memory configuration read. The shared assignment fetch can be on the cold startup path, but this diff does not add a separate fetch.
- Scaling input: One additional setting among the existing collection of experimental configuration properties; no scaling with session count during startup preference selection.
- Effective concurrency: Experimental properties are resolved by the existing sequential loop, while the underlying network fetch is shared; the diff adds one constant-time cached treatment lookup after that fetch rather than concurrent or per-session work.
- Cache behavior: Cold assignment state uses the shared TAS initialization/fetch; warm state prefers cached treatments while that fetch is pending. Profile storage and configuration are already initialized and read synchronously from memory.
- Mechanism confidence: High: configuration registration, BlockRestore processing, shared TAS initialization, and cached treatment-read paths were traced directly.
- Magnitude uncertainty: Exact treatment-read and telemetry overhead is unmeasured, but it is constant and does not create an additional network request.
- Expensive boundaries:
  - network at <code>src/vs/workbench/services/assignment/common/assignmentService.ts:497 setupTASClient / initialFetch</code>: Fetches all treatment assignments through the shared TAS client.; cardinality: One shared initial assignment fetch for the workbench; the new setting adds one treatment read from that fetched/cached assignment set, not another request.
    - Introduced by diff: false; previous behavior: The same shared assignment fetch already served the many existing automatic experiment settings; this setting was not read from its result.; critical-path effect: On a cold cache, experiment default resolution may await the already-existing shared initial fetch during BlockRestore; on a warm cache, getTreatmentVariableAsync is explicitly allowed to use cached treatments.
- Verdict: No reportable regression: startup gains one cached/shared treatment lookup and one in-memory preference read, without new boundary fan-out or session-scaled work.

### Scenario 2: A user or experiment changes sessions.list.defaultSortOrder while the Sessions view exists

- Critical path: The configuration event listener synchronously reads the stored preference/configuration and calls SessionsList.update only when the effective sort actually changes. update filters/groups/sorts the known sessions, rebuilds tree elements, and calls tree.setChildren on the renderer main thread.
- Scaling input: CPU/allocation scales with known sessions and their rendered chat children; workspace capping limits many rendered groups, but filtering/grouping still examines the session collection.
- Effective concurrency: One synchronous main-thread update per effective setting-value change. A valid stored user preference makes updateSorting hit its equality guard, so assignment/default changes do no list work for opted-in users.
- Cache behavior: The stored preference and configuration value are in-memory reads. Equal experimental defaults are retained without configuration delta notifications, and equal effective sort values are deduplicated by updateSorting.
- Mechanism confidence: High: the listener, equality guard, SessionsList update implementation, and experimental-default equality handling were traced directly.
- Magnitude uncertainty: Large session histories make a rebuild more costly, but actual default changes are rare and one rebuild is required to display the new sort; periodic refetches with unchanged assignments do not repeatedly rebuild.
- Expensive boundaries: none found
- Verdict: No reportable regression: the only collection-scaled UI work occurs once when the authoritative effective sort genuinely changes, with no I/O and no repeated-work mechanism.

### Scenario 3: A user selects a sort order from the desktop menu or mobile sort sheet and later recreates the view

- Critical path: setSorting synchronously records the explicit choice and updates the list only when the effective order changes. Recreated views read that preference from initialized storage and the normal initial SessionsList refresh renders once.
- Scaling input: Constant per user action for persistence; a genuine sort change separately scales with the current session collection, exactly as before.
- Effective concurrency: User-driven actions are serialized on the UI thread; storage flushes are coalesced by the storage service rather than launched concurrently per session.
- Cache behavior: The preference is cached in initialized profile storage and reused on recreation. Re-selecting an already persisted identical value is deduplicated by the underlying storage value layer; no list update occurs when currentSorting is unchanged.
- Mechanism confidence: High: all setSorting callers are explicit menu/sheet actions, and storage scheduling plus the update equality guard were traced.
- Magnitude uncertainty: Backend flush timing varies by platform, but action frequency and payload are bounded to one tiny value per explicit click.
- Expensive boundaries:
  - database/IPC at <code>src/vs/sessions/contrib/sessions/browser/views/sessionsView.ts:715 setSorting -&gt; IStorageService.store</code>: Persists one small profile-scoped sort string; native storage can flush through remote storage IPC/database and browser storage through IndexedDB.; cardinality: At most one store call per explicit user sort action; selecting a different order already stored once before the diff, while selecting the current default newly stores one value to preserve the explicit preference.
    - Introduced by diff: true; previous behavior: A changed sort was persisted once, but selecting the already-effective default returned before persistence and performed no boundary write.; critical-path effect: The immediate call updates in-memory storage; underlying persistence is scheduled/coalesced and flushing is off the interaction's critical path.
- Verdict: No reportable regression: the one new write for selecting the current default is bounded, user-triggered, deferred/coalesced at persistence, and required to distinguish an explicit preference.

**Summary:** Reviewed all four changed files and traced startup experiment resolution, live configuration changes, list rebuild/sort behavior, explicit sort actions, persistence, and view recreation. No actionable performance regression was introduced, and the PR is not itself a performance-regression fix.
