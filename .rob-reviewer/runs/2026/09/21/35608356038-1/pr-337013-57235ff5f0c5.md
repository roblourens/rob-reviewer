# Performance review: Enable Modern UI Update by default

[PR #337013](https://github.com/microsoft/vscode/pull/337013) at `57235ff5f0c5634f5b5525d50e811cc2bc8c70d9`

## Findings (1)

### 1. [medium] Keep connected-tab measurement off the routine layout path

**Finding ID:** `PERF-D140BAD91ADA`  
**Location:** <code>src/vs/workbench/browser/workbench.contribution.ts:836</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** main-thread style recalculation, layout, and per-tab DOM/CSSOM reads and writes  
**Scaling:** Every editor-group layout now processes every open tab in that group; the cost grows linearly with tab count and repeats on window/part resize, editor opens, decoration changes, toolbar changes, selection changes, and group activation.  
**Outcome:** increased layout latency and dropped frames during resizing and tab/editor interactions  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** With the setting defaulting to false, users without an explicit opt-in skipped the connected-tabs branch: \`layoutConnectedTabLabels(false)\` only removed stale properties and did not perform per-tab computed-style/text measurements or the connected-tab bounds reads.  
**Changed behavior:** Defaulting Modern UI on also enables the default \`Connected\` editor-tab style, so normal workbench layouts enter \`layoutConnectedTabLabels(true)\` and connected clipping measurement for every editor group.  
**Confidence:** 0.96 — The default-to-class-to-layout call path and the per-tab synchronous CSSOM/geometry operations are explicit. Exact milliseconds vary by tab/group count and platform, so severity is medium, but the mechanism and default exposure are high confidence.

**Causal diff evidence:** The added \`default: true\` at line 836 makes \`ModernUIContribution\` add \`.modern-ui-connected-editor-tabs\` by default; \`MultiEditorTabsControl.doLayoutTabs\` detects that class and calls \`layoutConnectedTabLabels(true)\` on each scheduled layout.

A realistic workspace with dozens of open tabs now incurs O(tab count) synchronous style/layout work on the main thread for each resize frame and common tab updates, causing visibly slower editor switching/opening and resize jank; multiple editor groups multiply the work serially.

**Evidence:** \`multiEditorTabsControl.ts:2068-2140\` iterates all tabs on every layout, removes a class, then for each tab calls \`getComputedStyle\` on the tab/name/suffix/badge and writes CSS custom properties before the next tab; it subsequently reads every \`offsetWidth\`. These interleaved DOM writes and CSSOM/geometry reads can repeatedly force style/layout. The same layout then reads \`offsetWidth\`/\`scrollWidth\`, three \`getBoundingClientRect()\` values, and pseudo-element styles at 2325-2386. Layout is requested by editor opens (628-686), decoration/toolbar changes (619-636), selection/group changes (838-858), label changes (885), and editor-group resizing (\`editorGroupView.ts:2239\`).

**Suggested direction:** Preserve the default-on UI while taking intrinsic connected-tab measurement out of routine layout: cache each tab's minimum width until its label/font/theme/options change, batch all required computed-style/geometry reads before class/style writes, and leave resize layouts to compare cached minima against current widths. Keep clipping measurement limited to the active tab.

### Scenario 2: Resize the window/parts or open, switch, rename, decorate, pin, or select editors with multiple tabs

- Critical path: Each trigger requests \`MultiEditorTabsControl.layout\`; work is coalesced to the next animation frame, but \`doLayoutTabs\` must synchronously measure and update connected labels and clipping before the frame's tab layout completes.
- Scaling input: Open tabs per group after no deduplication; dozens of tabs are realistic, and multiple visible groups multiply the work. Frequency follows resize frames and tab/editor events.
- Effective concurrency: One scheduled layout per editor group per animation frame; all style/layout work is serialized on the UI thread, with no worker or shared limiter across groups.
- Cache behavior: The text-width LRU can be warm, but font/style extraction and geometry are not cached. There is no negative state or coalescing across editor groups; layout requests within one group are RAF-coalesced.
- Mechanism confidence: Very high: callers for resize, editor open, decorations, toolbar changes, selections, activation, and labels are explicit, as are the CSSOM and geometry reads.
- Magnitude uncertainty: Exact dropped-frame threshold varies with machine, theme, labels, tab count, and group count.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:2068-2140</code>: Interleaved per-tab class/style mutation, computed-style reads, text measurement lookup, and width reads; cardinality: O(T) for every effective group layout, where T is the group's open-tab count.
    - Introduced by diff: true; previous behavior: Profiles using the old false default did not enter the connected measurement branch; routine layouts only performed the legacy tab layout.; critical-path effect: Consumes the animation-frame budget before tabs and editor geometry can be presented, so high T can produce resize or interaction jank.
- Verdict: Reportable; this is the concrete runtime trigger and impact for the submitted medium-severity finding.

### Scenario 3: Automation opens or reads chat model configuration when the auxiliary bar is initially too narrow

- Critical path: The test waits for button visibility, obtains the auxiliary-bar box, enumerates candidate top-level vertical sashes, queries each box sequentially, drags the nearest sash, then sleeps 300 ms before retrying. All Playwright operations are on the test's critical path.
- Scaling input: Number S of top-level workbench vertical sashes after \`.part\` descendants are excluded, multiplied by retries until the model button appears. In normal layouts S is small; the loop is bounded by 20 seconds and exits immediately when already expanded.
- Effective concurrency: Sash bounding-box requests are awaited sequentially. Retries are serialized with a 300 ms delay; there is no concurrent IPC burst.
- Cache behavior: No sash-box caching between retries because geometry changes after each drag. The already-expanded path performs only the visibility check and no sash enumeration.
- Mechanism confidence: High for the added IPC count; low concern for product performance because this code is test-only and bounded.
- Magnitude uncertainty: Exact S and retry count depend on test layout, but the selector excludes numerous internal part sashes and successful dragging should end the loop promptly.
- Expensive boundaries:
  - IPC at <code>test/automation/src/chat.ts:323-335</code>: Playwright locator enumeration and one \`boundingBox\` browser query for each top-level vertical sash; cardinality: Previously zero sash enumeration plus one auxiliary-bar box query per retry; now one locator enumeration and S sash-box queries per retry, normally a handful and usually one retry.
    - Introduced by diff: true; previous behavior: The test inferred the sash from the auxiliary bar's left edge and issued no per-sash browser queries.; critical-path effect: Adds bounded automation IPC latency only when the picker needs expansion; it does not affect product runtime.
- Verdict: No finding: the added fan-out is small, bounded, test-only, and needed to locate the offset sash under the new card layout.
