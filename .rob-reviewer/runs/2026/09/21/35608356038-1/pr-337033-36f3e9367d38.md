### Scenario 1: Workbench eventually initializes the current-chat handoff and parallel-work contributions

- Critical path: Both contributions are created in WorkbenchPhase.Eventually, after restore; their treatment reads are asynchronous and do not block workbench restore or chat interaction because localized fallback copy remains usable while reads resolve.
- Scaling input: A fixed four treatment names across the two singleton contributions: two pre-existing parallel-work names and two newly added current-chat handoff names; cardinality does not depend on chats, sessions, messages, or widgets.
- Effective concurrency: Each contribution reads its title and description in one Promise.all. Assignment refreshes can overlap, but a monotonically increasing request id drops stale completions. The assignment service owns one shared TAS client and assignment-bundle fetch rather than issuing one network request per treatment.
- Cache behavior: On a warm assignment cache, treatment values are read from the initialized TAS client. During cold initialization, all reads await the same client and prefer cached treatment variables until its single shared initial fetch completes; assignment refetches replace values and trigger bounded rereads.
- Mechanism confidence: High: contribution phase, Promise.all cardinality, stale-request suppression, and the shared assignment-client initialization path are directly visible in code.
- Magnitude uncertainty: Exact TAS initialization latency and refresh frequency vary by account/network, but they do not increase with message or session count and do not block the touched user workflows.
- Expensive boundaries:
  - network at <code>src/vs/workbench/services/assignment/common/assignmentService.ts:setupTASClient/getAssignedTreatment</code>: Fetch the shared experimentation assignment bundle through the main-process request service during TAS client initialization/refetch.; cardinality: One service-level initial fetch (and one per service refetch), shared across all treatment names; the diff adds two logical value reads but not two independent network calls.
    - Introduced by diff: false; previous behavior: The assignment service already initialized/fetched globally, and the adjacent parallel-work contribution already read two treatments. The diff adds two local consumers for handoff copy without changing shared network-fetch cardinality.; critical-path effect: Off the restore and chat critical paths: contribution initialization launches reads without awaiting them, and fallback copy is available immediately.
- Verdict: No reportable regression. The added eager work is fixed-cardinality, eventually scheduled, cache-backed, and off the critical path.

### Scenario 2: A user sends or queues messages in an eligible running Copilot CLI/agent-host chat and the handoff tip appears after the configured delay

- Critical path: On request start, queue changes, focus changes, or relevant configuration changes, the contribution computes the latest user-message timestamp and arms one timeout. No filesystem, IPC, database, subprocess, or network operation is required before the tip can appear; expiration performs an in-memory notification update/render.
- Scaling input: The latest completed request is found by a reverse search and pending requests are scanned once per relevant lifecycle event. Effective cardinality is the focused chat's history tail plus its usually small pending queue, not all sessions or all widgets.
- Effective concurrency: A MutableDisposable owns exactly one timeout. Every reevaluation clears the previous timeout before arming another; focus changes replace model listeners through autorun reader-owned disposal. Queued follow-ups therefore move, rather than multiply, the deadline.
- Cache behavior: No external cache is involved. The focused model and notification state are read in memory; \`\_lastPostedFor\` plus copy fields suppress duplicate notification posts after the deadline.
- Mechanism confidence: High: the model's outer onDidChange emits request-structure events, while response fragments update the response model separately; timer replacement and listener disposal are explicit.
- Magnitude uncertainty: Very long histories containing many trailing system-initiated requests could make the reverse search longer, but the event frequency is lifecycle-level rather than per streamed token and the pending queue is bounded by realistic user interaction; evidence does not establish material latency.
- Expensive boundaries: none found
- Verdict: No reportable regression. Work is bounded to one focused model, one timer, and sparse request/queue lifecycle events, with correct cancellation and deduplication.
