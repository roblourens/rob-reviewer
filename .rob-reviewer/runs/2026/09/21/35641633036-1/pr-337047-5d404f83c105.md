## Findings (1)

### 1. [medium] Prune per-chat Test App storage when chats disappear

**Finding ID:** `PERF-DAD66E09A127`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionTestAppButton.ts:120</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Persistent profile-storage rows, in-memory key-target entries, and serialized key-target bytes  
**Scaling:** Retained state grows O(N) with the number of distinct chats ever tested, including deleted chats; because adding a new target rewrites the full key-target JSON object, cumulative metadata serialization across N additions grows O(N²).  
**Outcome:** Unbounded retained memory/disk and progressively more profile-storage serialization/startup work  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, Test App history did not exist, so using and later deleting agent chats added no persistent profile-storage entries.  
**Changed behavior:** Every accepted Test App request now creates a distinct profile-storage key derived from the chat resource, and the new component never removes or bounds those keys.  
**Confidence:** 0.96 — The unique key construction, profile lifetime, lack of any removal reference, and available deletion lifecycle are directly established in the changed and surrounding code. The exact number of affected profiles is uncertain, but retention grows deterministically with distinct tested chats.

**Causal diff evidence:** Added line 120 calls \`storageService.store\` with a key containing the unique session resource; no changed code removes that key or imposes a cap.

Profiles that use Test App across many chats retain every chat URI after those chats are deleted. The retained rows and storage target metadata grow for the lifetime of the profile, increasing profile-storage memory/disk usage and the cost of loading and updating that metadata.

**Evidence:** The added callback stores \`sessions.testApp.requested.${getComparisonKey(resource)}\` for each accepted chat. Repository search finds no removal for this prefix. \`ISessionsManagementService\` exposes \`onDidDeleteSession\`/\`onDidDeleteChat\`, and nearby \`SessionArchiveNudgeService\` explicitly removes per-session persisted state on deletion, but this component does not subscribe to lifecycle cleanup. \`AbstractStorageService.updateKeyTarget\` also serializes the complete key-target object whenever a new key is added, so stale keys affect both retained bytes and subsequent storage updates.

**Suggested direction:** Persist this flag in chat-owned metadata that is deleted with the chat, or centralize it in a bounded record that removes entries on chat/session deletion and draft/session replacement (and prunes orphaned entries at startup).
