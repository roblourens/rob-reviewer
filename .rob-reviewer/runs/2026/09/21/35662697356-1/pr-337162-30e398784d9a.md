# Performance review: sessions: Show catalog chats in the session list

## Findings (2)

### 1. [high] Back off failed detail subscriptions

**Finding ID:** `PERF-A54849AC40F5`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:5892</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Repeated IPC subscribe requests and repeated provider/database/filesystem session-restore work  
**Scaling:** For every observed failing session, each failed subscribe queues the next attempt immediately; work grows without bound with failure duration and multiplies across simultaneously visible failing sessions.  
**Outcome:** Sustained CPU, IPC, and I/O load that can saturate the agent host while the Sessions view remains open  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A subscription failure removed the failed session-state subscription; this path did not immediately recreate it in a microtask solely because peer-chat details remained observed.  
**Changed behavior:** The new error handler deletes the failed subscription and immediately calls \`\_ensureSessionStateSubscription\` again whenever a chat-detail reference is still held.  
**Confidence:** 0.99 — The complete changed call path is explicit: observed peer detail -&gt; retained reference -&gt; async subscription error -&gt; deletion -&gt; microtask reacquire -&gt; fresh subscribe/restore. The only magnitude uncertainty is how often persistent restore failures occur, not whether they loop.

**Causal diff evidence:** The added \`queueMicrotask\` block at lines 5892-5896 recreates the failed subscription immediately; this retry loop did not exist before the diff.

An expanded catalog-backed peer row keeps title/status observed. If that session cannot be restored (for example a persistently unavailable provider or corrupt backing), every restore failure immediately starts another subscribe. Server-side \`AgentService.subscribe\` then retries \`restoreSession\`, including provider materialization, transcript/database reads, and possible catalog work, indefinitely.

**Evidence:** \`AdditionalChat.\_withDetails\` holds the new session detail reference for rendered title/status observables. On \`onDidError\`, line 5892 queues an unconditional retry while that reference exists. \`AgentSubscriptionManager.getSubscription\` creates a fresh wire subscription after an errored entry, and \`AgentService.subscribe\` invokes \`restoreSession\` whenever no snapshot exists; restore performs registry/database/provider/history work. There is no delay or retry cap in this loop.

**Suggested direction:** Keep the reference alive but retry with bounded exponential backoff (cancelled when the last reference is released), or wait for an explicit host/provider-ready event before resubscribing; do not recursively retry in the next microtask.

### 2. [medium] Bound peer-row session restoration

**Finding ID:** `PERF-05F42793AEB2`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:840</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Concurrent IPC subscriptions, provider materializations, transcript/database reads, and related restore allocations  
**Scaling:** The first observed peer row for each distinct nonresident session starts one restore; default-expanded, virtualized rows therefore fan out up to the number of distinct sessions represented in the viewport, with additional bursts as the user scrolls.  
**Outcome:** Burst I/O and CPU contention in the agent host, reducing responsiveness and throughput when opening or scrolling the Sessions view  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Catalog listings did not instantiate peer-chat rows for unloaded sessions, so rendering the session list could not subscribe to and fully restore each listed session merely to display child rows.  
**Changed behavior:** Every reactive listener attached to a peer chat's wrapped title/status details acquires a session-detail lease; the first lease immediately starts a session-state subscription, and nested sessions now start expanded.  
**Confidence:** 0.96 — The renderer-to-subscription-to-restore path and one-restore-per-distinct-session cardinality are directly established. Exact duration depends on provider and transcript size, which is reflected in medium severity.

**Causal diff evidence:** The added \`\_withDetails\` acquisition at line 840 places full session hydration on peer-row render; the same diff seeds peers from lightweight listings and expands newly nested sessions by default, making this path reachable on view open.

Opening the Sessions view with several catalog-backed multi-chat sessions can concurrently restore every distinct session whose peer row is rendered. A restore crosses IPC and can materialize the provider, read the session database and full transcript, and refresh related state even though the user has not opened any chat.

**Evidence:** \`SessionChatItemRenderer.renderElement\` reactively reads both \`chat.title\` and \`chat.status\`; line 840 now turns those reads into \`\_acquireDetails()\`. The reference collection calls \`\_ensureSessionStateSubscription\`, which issues \`connection.getSubscription\`. Server-side \`AgentService.subscribe\` calls \`restoreSession\` for a missing snapshot; \`\_restoreSessionState\` performs provider metadata/materialization, database metadata, and \`\_getChatMessages\`. Restore coalescing is only per session key, and this new client path has no shared limiter across distinct sessions.

**Suggested direction:** Queue row-triggered restores through a small provider-wide concurrency limiter, preserving per-session coalescing and cancellation when the row/reference disappears; alternatively keep catalog values until an explicitly prioritized interaction requests transient details.
