# Performance review: agentHost: prevent duplicate Codex skills across sessions

[PR #335475](https://github.com/microsoft/vscode/pull/335475) at `dcb7fae71ca24d4a1d7e0916350bb2648a95922f`

## Findings (1)

### 1. [medium] Avoid appending the skill catalog on every turn

**Finding ID:** `PERF-CDF5A6053BE0`  
**Location:** <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:5930</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Serialized prompt bytes and model input tokens retained in thread history and transmitted/processed by subsequent model requests.  
**Scaling:** For S bytes of catalog and T turns, the Tth request can contain O(S\*T) historical catalog bytes and the session cumulatively processes O(S\*T^2) catalog bytes; S grows with enabled skill count and description/path lengths.  
**Outcome:** Increasing network payload, token-processing latency, and context-window pressure over the lifetime of a chat.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Client skills were registered through \`skills/extraRoots/set\` when roots changed or a connection started; \`turn/start\` did not append a client-skill catalog to each turn's persisted conversation history.  
**Changed behavior:** Every normal turn now adds a \`vscode.clientSkills\` application-context entry containing the entire current client-skill catalog, even when the catalog is empty or unchanged.  
**Confidence:** 0.98 — The per-turn insertion, full-catalog serialization, normal send path, and persistence of older catalogs are all directly evidenced by changed source, changed subsystem documentation, and the integration-test request inspection. Exact latency depends on chat length and catalog size, which affects severity rather than mechanism confidence.

**Causal diff evidence:** RIGHT line 5930 unconditionally inserts the full \`clientSkillInstructions\` value into \`turn/start.additionalContext\`; previously no per-turn client-skill context entry existed.

Long Codex chats repeatedly resend and reprocess unchanged skill metadata, increasing request bytes, input-token usage, and model latency; sufficiently long chats or large plugin catalogs reach the context limit earlier. This also affects sessions with no client skills because the empty-catalog block is still appended every turn.

**Evidence:** The changed \`turn/start\` payload unconditionally includes \`currentCustomizationLaunch.clientSkillInstructions\`. \`codexClientSkillInstructions\` serializes every model-invokable skill name, description, and absolute file path. The updated agent-host documentation explicitly states that every turn receives this catalog and that older catalogs can remain in conversation history; the provider integration test searches all developer-role input in a later model request and selects the last \`&lt;client\_skills&gt;\` block, corroborating that these entries reach the model request history.

**Suggested direction:** Track the last catalog/signature advertised for each backing thread and add this context only on the first turn and when the enabled catalog changes, including one explicit empty update for removal; reset that state only when a new thread/history requires it.

### Scenario 2: Adding, removing, or changing client-synced skills after a thread already has history

- Critical path: Customization sync/copy and parsing complete first; reconciliation marks an existing materialized thread for reload when skill roots/profile change. The next turn resumes the thread before sending one new current-catalog application context.
- Scaling input: Number of client plugin revisions, enabled skills, and changed session permission profiles; effective roots are deduplicated absolute skill directories.
- Effective concurrency: Customization reconciliation is serialized per session by a \`Sequencer\`; thread resume is awaited before the next turn, avoiding concurrent reload bursts.
- Cache behavior: Synced plugin files and parsed plugin state are retained by the per-session store. Signature comparison avoids resume when launch-relevant state is unchanged, but catalog advertisement itself has no unchanged-state suppression.
- Mechanism confidence: High for call path and serialization; low evidence of harmful fan-out because signature checks and the per-session sequencer bound reload work.
- Magnitude uncertainty: Plugin revision frequency and catalog size vary, but reconciliation is bounded and serialized; no independent regression beyond the repeated catalog-history issue was established.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_syncClientCustomizations/\_parseClientPlugin</code>: Sync and parse client plugin bundles; cardinality: Once per changed client customization set, across the changed plugins rather than per chat turn.
    - Introduced by diff: false; previous behavior: Plugin bundles were already copied and parsed before computing process-global skill roots.; critical-path effect: Precedes customization publication/reconciliation; existing behavior, not newly introduced by this diff.
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_ensureCurrentLaunchBeforeTurn/\_resumeSession</code>: Unsubscribe and resume a materialized thread with updated permission-profile filesystem roots; cardinality: At most one serialized reload per converged customization/profile state before a turn.
    - Introduced by diff: false; previous behavior: Skill-root changes already altered selected capability roots/signatures and triggered thread reconciliation; the diff changes the config/profile payload and removes the global roots update.; critical-path effect: Blocks the first turn after a relevant customization or permission change.
- Verdict: No additional finding: dynamic changes are serialized and reload only when launch state differs; the significant regression is the catalog copies retained per turn.

### Scenario 4: Model invocation of a selected client skill outside the workspace

- Critical path: The model receives the catalog, then may issue a shell/file-reading tool call for the advertised SKILL.md. That subprocess/filesystem read is required only when a task matches a skill, not on every turn.
- Scaling input: Number of skills actually selected by the model, normally one matching skill per task; catalog construction includes all enabled skills but body reads are on demand.
- Effective concurrency: Tool calls follow Codex turn execution and approval/sandbox sequencing; tests exercise one shell invocation, with no diff-added parallel fan-out.
- Cache behavior: Synced skill files remain on disk. Metadata is advertised each turn, but skill bodies are read lazily only on invocation; removal revokes read permission while the cached file remains.
- Mechanism confidence: High that body reads are lazy and permission-scoped; no evidence of changed read fan-out.
- Magnitude uncertainty: Actual model skill-selection frequency is workload-dependent.
- Expensive boundaries:
  - subprocess at <code>Transitive Codex tool execution exercised by codexCustomizations.integrationTest.ts</code>: Run shell/file tool to read the selected SKILL.md; cardinality: On demand per selected skill/tool call, not per catalog entry.
    - Introduced by diff: false; previous behavior: Codex native skill handling also read selected skill files on demand; this diff changes discovery/permission delivery rather than proving additional body reads.; critical-path effect: Blocks the model step that needs the skill body.
  - filesystem at <code>Path emitted by src/vs/platform/agentHost/node/codex/codexClientCustomizations.ts:codexClientSkillInstructions</code>: Read the selected synced SKILL.md from its cache path; cardinality: One read per model-issued file command in the tested path.
    - Introduced by diff: false; previous behavior: Client skills were discovered from registered extra roots and their bodies remained file-backed.; critical-path effect: Required for the model to use that skill, but remains lazy.
- Verdict: No separate finding: the expensive file boundary remains demand-driven rather than eager or per-catalog-item.
