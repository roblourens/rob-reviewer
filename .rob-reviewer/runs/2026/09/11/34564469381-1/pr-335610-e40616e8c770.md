### Scenario 1: Interactive GitHub sign-in brokered through Microsoft Entra

- Critical path: Microsoft token acquisition, GitHub discovery token exchange, GitHub user lookup, user confirmation, final token exchange, final user verification, and account-link persistence must complete before the session is published. The changed seconds-to-milliseconds multiplication and property propagation are constant-time work on this existing path.
- Scaling input: Explicit login attempts and explicit account reselections; expiration conversion remains O(1) per successful exchange.
- Effective concurrency: The exchanges and user lookups are intentionally serialized around confirmation. Selecting a different Microsoft account repeats the flow only on explicit user choice. The diff does not change concurrency.
- Cache behavior: A remembered Microsoft account may avoid account selection but does not remove required identity verification. No cache key or invalidation behavior is changed.
- Mechanism confidence: High: the complete login call path and all changed expiration operations were traced.
- Magnitude uncertainty: Network timings vary by provider and geography, but the diff adds no network calls and only one numeric multiplication per exchanged token.
- Expensive boundaries:

- Verdict: No reportable regression; boundary count, ordering, and concurrency are unchanged.

### Scenario 2: GitHub cached transient-session lookup, restoration, and near-expiry renewal

- Critical path: A getSessions call filters persisted and transient candidates, checks expiration, renews only requested sessions inside the renewal window, and restores missing linked accounts. A valid warm transient session performs only in-memory collection work; stale or cold-restored sessions wait for Microsoft token acquisition, GitHub exchange, and GitHub user verification.
- Scaling input: Number of requested matching transient sessions and missing linked accounts after scope/account filtering and per-key coalescing.
- Effective concurrency: Missing linked accounts and stale sessions are processed with Promise.all. Concurrent work for the same account/scope restore key or session ID is coalesced by \_restores and \_renewals maps. The diff preserves these controls.
- Cache behavior: Warm sessions outside the renewal window cause no network work. Deadlines remain absolute milliseconds internally; returned remaining lifetime is recomputed once using a shared Date.now value. Restore attempts and in-flight renewals remain cached/coalesced exactly as before.
- Mechanism confidence: High: filtering, deadline checks, Promise.all fan-out, and both coalescing maps were inspected.
- Magnitude uncertainty: Account counts can vary, but effective boundary cardinality is unchanged and the new expiration arithmetic is constant-time per returned session.
- Expensive boundaries:
  - IPC at <code>extensions/github-authentication/src/github.ts restoreNow/renewNow and extensions/github-authentication/src/entraTokenExchange.ts renew</code>: Read Microsoft accounts and silently acquire a Microsoft token for restoration or renewal.; cardinality: At most once per effective missing account/scope restore or stale requested session; concurrent duplicates share one promise.
    - Introduced by diff: false; previous behavior: The same Microsoft account and token operations occurred under the seconds-based lifetime.; critical-path effect: Only cold restoration and near-expiry renewal await it; warm valid sessions do not.
  - network at <code>extensions/github-authentication/src/entraTokenExchange.ts renew/exchange/verifyAccount</code>: Exchange a Microsoft token for a GitHub token and verify it with GET /user.; cardinality: One exchange plus one verification per effective restore or renewal after coalescing.
    - Introduced by diff: false; previous behavior: The same pair of GitHub calls occurred; expiry arithmetic used seconds when storing the deadline.; critical-path effect: Blocks only restoration or renewal for the requested session.
- Verdict: No reportable regression; the unit change preserves renewal timing and slightly reduces repeated Date.now calls in transient-session projection.

### Scenario 4: Agent Host startup/session-change authentication and token refresh

- Critical path: For each declared protected resource, workbench resolves an authentication provider and session, converts remaining milliseconds back to protocol seconds, and forwards an authenticate RPC unless the same resource/scope/token is already completed or in flight. On the host, matching providers receive the token in parallel; known expiration can enable the existing threshold-based refresh path when an SDK later asks for a near-expiry token.
- Scaling input: Distinct protected resource/scope/token tuples after cache normalization, multiplied by authorization servers attempted and matching host providers; expiration conversion remains O(1) per forwarded token.
- Effective concurrency: Agents and resources are traversed serially. Same-token authenticate calls are coalesced by AgentHostAuthTokenCache. The host fans one accepted RPC to matching providers in parallel, and Copilot authentication updates are sequenced. The diff does not alter these controls.
- Cache behavior: Cold connections forward each distinct token once. Warm same-token calls skip the RPC regardless of the recomputed remaining lifetime, preserving prior behavior. Pending same-token calls are coalesced; cache clears on restart, revocation, and recovery. Known Microsoft-session expiry may activate the existing bounded refresh mode rather than leaving a token static until failure.
- Mechanism confidence: High: session resolution, token-cache keys, RPC forwarding, host fan-out, and refresh coalescing were traced.
- Magnitude uncertainty: The number of agents/resources varies, but the diff neither increases that cardinality nor changes the token cache key. The optional numeric protocol field has negligible serialization cost.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts resolveAuthenticationSessionForResource</code>: Activate/resolve an authentication provider and request exact-scope sessions, falling back to all sessions only when exact lookup is empty.; cardinality: Per authorization server, one exact lookup; a second all-session lookup only on an exact miss. Repeated provider operations are queued by provider.
    - Introduced by diff: false; previous behavior: The same lookup sequence occurred and returned seconds-based expiration when a provider supplied it.; critical-path effect: Session resolution must complete before a token can be forwarded.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts forwardAuthenticationToken</code>: Send authenticate request to the Agent Host, now converting expiresAfter milliseconds to protocol expiresIn seconds.; cardinality: At most one completed RPC per distinct resource/scope/token per connection until cache invalidation; same-token concurrent calls share one promise.
    - Introduced by diff: false; previous behavior: The same authenticate RPC was sent with the prior expiresIn value; the diff only converts the renamed millisecond value back to seconds.; critical-path effect: Required for initial credential installation, but skipped on warm same-token reconciliation.
  - other at <code>src/vs/platform/agentHost/node/agentHostAuthenticationService.ts authenticate and src/vs/platform/agentHost/node/copilot/copilotGitHubCredentials.ts update/tokenProvider</code>: Fan the authenticated token to matching Agent Host providers and optionally install a refreshable Copilot credential.; cardinality: One call per matching provider for each non-deduplicated authenticate RPC; providers run in parallel. Refresh requests are coalesced by a single pending refresh promise.
    - Introduced by diff: false; previous behavior: The protocol already supported expiration and the same provider fan-out/refresh machinery; sessions that already supplied expiration used it directly.; critical-path effect: Initial provider setup awaits matching providers. Future refresh is requested only near expiry or when explicitly requested by the SDK.
- Verdict: No reportable regression; protocol compatibility is preserved without increasing RPC or refresh fan-out.
