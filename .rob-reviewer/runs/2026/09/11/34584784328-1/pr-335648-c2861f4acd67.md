# Performance review: Allow leaving PR comments in agents

[PR #335648](https://github.com/microsoft/vscode/pull/335648) at `c2861f4acd679953ec8bb034768f5834342409ed`

## Findings (2)

### 1. [medium] Move PR line mapping off the UI thread

**Finding ID:** `PERF-C031E8B13616`  
**Location:** <code>src/vs/sessions/contrib/codeReview/browser/codeReviewService.ts:147</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Renderer-thread CPU plus full-file line-array and diff allocations  
**Scaling:** Work grows with the complete PR-head file and current editor buffer, not the selected line, and is repeated for every PR-comment target selection; the explicit budget permits 1000 ms of synchronous computation per selection.  
**Outcome:** The renderer can be blocked for up to one second, causing visible input/rendering freezes before the comment editor opens.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, selecting a feedback line did not perform a whole-file diff on this editor interaction path.  
**Changed behavior:** Selecting a PR comment target now splits both complete file contents and invokes the synchronous default lines diff computer with maxComputationTimeMs set to 1000 before returning the target.  
**Confidence:** 0.99 — The call path from the editor action to the synchronous diff is direct, the full-file inputs and one-second budget are explicit in changed code, and the only magnitude uncertainty is how often users select very large/diverged files.

**Causal diff evidence:** Added line 147 introduces the synchronous computeDiff call, and added caller line 340 invokes it while resolving the target that the editor awaits before showing its widget.

With the experimental PR-comments setting enabled, choosing “Pull Request Comment” on a large or substantially diverged file can freeze the UI for up to the configured one-second diff budget before the input widget appears; each additional comment selection repeats the freeze.

**Evidence:** AgentFeedbackEditorInputContribution awaits getPRReviewCommentTargets before calling \_show (line 536). That browser-side method reaches mapCurrentLineToPullRequestLine, where line 147 synchronously calls linesDiffComputers.getDefault().computeDiff over arrays produced from the entire remote head content and current model content, with maxComputationTimeMs: 1000. There is no worker handoff, yielding, cancellation, or cached mapping.

**Suggested direction:** Run line mapping through the asynchronous editor worker/diff service with cancellation, or derive/cache the mapping by head SHA, path, and model version; do not execute the full-file diff synchronously in the editor interaction.

### 2. [medium] Reuse PR target data across comments

**Finding ID:** `PERF-2D6A31D58647`  
**Location:** <code>src/vs/sessions/contrib/codeReview/browser/codeReviewService.ts:329</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** GitHub REST requests, response bytes for all changed-file patches and full file content, and API rate-limit capacity  
**Scaling:** The current UI selects one PR, but every attempted PR comment independently performs four GETs; cost therefore grows as 4 × the number of comment-target selections, with compare payload size also growing with the PR's changed files.  
**Outcome:** Repeated multi-round-trip latency before the comment input appears, excessive network I/O, and avoidable GitHub API usage.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, opening the line-feedback input performed no GitHub target-resolution requests. The new compare and file-content methods also have no result cache on this path.  
**Changed behavior:** Each target lookup unconditionally refreshes the selected PR model (two concurrent GETs), then serially fetches the full compare result and full head-file content before the editor can open the input.  
**Confidence:** 0.99 — Repository tracing proves exactly one selected PR in the production caller, two concurrent requests inside refresh, then two serialized uncached requests, all awaited before widget display. Only network duration and reviewer comment count vary.

**Causal diff evidence:** Added lines 329, 334, and 339 place four GitHub GETs on every newly introduced target-selection path; line 329 is the first unconditional boundary call and is awaited before any target can be returned.

With PR comments enabled, every time a reviewer starts a line comment they wait for three sequential network phases (PR/reviews refresh, compare, then contents). Writing several comments on the same unchanged PR/file repeats all four GitHub GETs and can make the editor feel persistently slow on high-latency or enterprise connections.

**Evidence:** The editor awaits getPRReviewCommentTargets before \_show. Added line 329 calls GitHubPullRequestModel.refresh(), whose implementation issues getPullRequest and getReviews in Promise.all; added lines 334 and 339 then await getChangedFiles and getFileContent serially. GitHubChangesFetcher is explicitly stateless, getFileContent directly calls GitHubApiClient, and the API client sets disableCache: true. No cache or in-flight coalescing is present for immutable base/head/path data.

**Suggested direction:** Reuse already-loaded PR model data when fresh, and cache/coalesce compare patches and head-file content by owner/repo/base SHA/head SHA/path (invalidating naturally when head SHA changes) so repeated comments on the same revision do not refetch immutable data.

- Effective concurrency: Posting and refresh are strictly sequential. The thread model coalesces ordinary refreshes, while force semantics deliberately run a fresh request after any in-flight request.
- Cache behavior: Review threads are held in a reference-counted observable model and polled every 60 seconds while active; forced refresh intentionally bypasses warm state after mutation.
- Mechanism confidence: High confidence in the boundary count and critical path. The refresh is an intentional consistency operation, and there is insufficient evidence that moving it off-path would preserve UX semantics.
- Magnitude uncertainty: Thread counts and network latency vary, but cardinality is bounded at two sequential operations per submission.
