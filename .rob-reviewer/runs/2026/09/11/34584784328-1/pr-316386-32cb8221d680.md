# Performance review: fix: race activateByEvent with provider registration to prevent auth deadlock

[PR #316386](https://github.com/microsoft/vscode/pull/316386) at `32cb8221d680b8478bdb46c51616c7ce4598c9cd`

## Findings

No high-confidence performance findings.

## Performance regression fixes detected (1)

### 1. boundary-fanout

**Fix location:** `src/vs/workbench/services/authentication/browser/authenticationService.ts:454` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/services/authentication/browser/authenticationService.ts:421`  
**Introducing path:** `src/vs/workbench/services/authentication/browser/authenticationService.ts`  
**Introducing commit:** `4e81df7ea90350b1c2205e39c4e5a1a4197432c0`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `latency`  
**Confidence:** 0.98

**Mechanism:** An all-extension-host activation barrier was placed before observing successful authentication-provider registration, so one blocked host could indefinitely hold the tunnel authentication and connection critical path even after another host had supplied the provider.

**Symptom:** Connecting to a remote tunnel can deadlock indefinitely while obtaining cached authentication sessions when the local webworker extension host is blocked on remote authority setup.

**Fixed behavior:** The changed code starts activation but races its aggregate promise against the provider-registration event, then reads the provider map immediately. Tunnel authentication can therefore continue as soon as any host registers the requested provider, without waiting for an unrelated blocked host; host activation itself remains cached and continues in the background.

**Evidence:** Before this PR, AuthenticationService.tryActivateProvider awaited activateByEvent before checking the provider map. AbstractExtensionService.\_activateByEvent returns Promise.all over the selected extension-host managers, each manager crosses its extension-host proxy via activateByEvent. The remote-tunnel connect critical path calls \_getTokenForProvider -&gt; AuthenticationService.getSessions(..., activateImmediate=true) before it can call the tunnel main service. A local process host can register MainThreadAuthenticationProvider and fire onDidRegisterAuthenticationProvider while a local webworker host's activation remains blocked; the added test reproduces that aggregate activation promise never settling despite successful provider registration.

### Scenario 1: Connect to a remote tunnel using GitHub or Microsoft authentication while a local webworker extension host is blocked during remote-authority setup.

- Critical path: TunnelAgentHostService.connect waits for \_getToken/\_getTokenForProvider, which waits for AuthenticationService.getSessions and cold-provider activation before \_mainService.connect and protocol setup can begin. After the diff, provider registration from the local process host releases this path even if the aggregate activation promise remains blocked.
- Scaling input: At most the configured GitHub and Microsoft providers are attempted sequentially; each provider can perform an exact-scope session query and, only when empty, one all-sessions fallback. Cold activation fans out to the selected extension-host managers, while the effective IPC cardinality is one cached activation per provider event per host manager.
- Effective concurrency: Providers and exact/all session queries are sequential. Extension-host activation is concurrent via Promise.all, but the changed Promise.race no longer makes every host's completion a barrier. ExtensionHostManager caches each activation-event promise, so concurrent callers do not multiply extension-host IPC for the same host/event.
- Cache behavior: A registered provider is a warm map hit and skips tryActivateProvider entirely. On a cold provider, each host manager caches the activation event; the registration event is the new early completion signal. There is no negative provider cache, and a completed activation without registration retains the existing five-second wait.
- Mechanism confidence: High: getSessions is directly on tunnel connection's critical path, activation is a Promise.all over extension hosts, and the test proves registration can occur while that promise never resolves.

### Scenario 2: An extension or workbench action gets/creates sessions for an authentication provider that is not yet registered.

- Critical path: getSessions/createSession waits for tryActivateProvider, then invokes the provider RPC. The diff races activation completion with registration; if activation completes first without registration, the existing five-second registration timeout still applies.
- Scaling input: One provider ID per request. getOrActivateProviderIdForServer can examine the filtered set of matching, unregistered declared providers sequentially; that loop and its candidate cardinality are unchanged.
- Effective concurrency: Activation fans out concurrently to selected extension hosts. Concurrent requests can each hold a registration listener, but the underlying host activation is cached per event/manager; listeners are disposed in tryActivateProvider's finally block as soon as each request completes.
- Cache behavior: Warm provider-map hits avoid activation. Cold activation is coalesced by ExtensionHostManager's event cache. No new persistent cache or negative cache is introduced.
- Mechanism confidence: High: listener ownership, activation caching, and all completion branches are visible in the implementation.
- Magnitude uncertainty: The number of concurrent cold requests is workload-dependent, but each added listener is bounded by an in-flight call and synchronously registered providers are caught by the map check; disposal is explicit.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/extensions/common/abstractExtensionService.ts:\_activateByEvent</code>: Activate the provider extension in selected extension hosts.; cardinality: One effective activation IPC per selected host manager for a cold provider event; duplicate requests reuse manager-cached promises.
    - Introduced by diff: false; previous behavior: AuthenticationService awaited all selected hosts before checking registration or beginning the timeout.; critical-path effect: The diff shortens the wait when registration arrives before all hosts settle and otherwise preserves the prior activation-plus-timeout path.
  - IPC at <code>src/vs/workbench/api/browser/mainThreadAuthentication.ts:MainThreadAuthenticationProvider</code>: Get or create authentication sessions through the extension-host provider proxy.; cardinality: One provider RPC for the requested operation after successful registration.
    - Introduced by diff: false; previous behavior: The same provider RPC followed activation.; critical-path effect: Unchanged and remains after provider readiness.
- Verdict: No reportable performance regression. Temporary listener lifetime is bounded, effective IPC count is unchanged, and the main behavioral change reduces cold-path latency.
