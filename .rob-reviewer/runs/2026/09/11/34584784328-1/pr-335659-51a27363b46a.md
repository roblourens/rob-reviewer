## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/workbench/services/authentication/browser/authenticationService.ts:459` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/services/authentication/browser/authenticationService.ts:468`  
**Introducing path:** `src/vs/workbench/services/authentication/browser/authenticationService.ts`  
**Introducing commit:** `184d76ec60143813b7cc2f20b6ca267f3f9cdb4a`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.99

**Mechanism:** Timed-out provider activation attempts leave raceCancellation promises pending and retain one cancellation listener on the AuthenticationService lifetime token per attempt until service shutdown.

**Symptom:** Repeated requests for unavailable authentication providers accumulate listeners and retained promise closures for the lifetime of the workbench, eventually triggering listener-leak warnings and increasing memory/dispatch work.

**Fixed behavior:** Each activation attempt now owns a linked CancellationTokenSource whose dispose(true) runs from tryActivateProvider's finally block. Successful registration, activation failure, and the 5-second timeout all cancel the operation token and remove the registrations from the long-lived service token, bounding retained listeners to currently active attempts.

**Evidence:** Before this change, tryActivateProvider passed the AuthenticationService lifetime token directly to raceCancellation. raceCancellation registers token.onCancellationRequested and disposes that registration only when its input promise settles or the token is cancelled. On the 5-second missing-provider timeout, Event.toPromise is disposed without settling, so providerRegistered remains pending and its cancellation listener remains attached until the whole service is disposed. getSessions/createSession and the declared-provider scan can invoke this path repeatedly; the added regression test exercises repeated missing-provider timeouts and verifies that listener-leak warnings no longer occur. The changed lines create a child source linked to the service token and register dispose(true) in the operation store, so finally cancellation settles raceCancellation and removes both its listener and the child source's parent listener.

### Scenario 2: Repeated requests for an unavailable or non-registering provider

- Critical path: Each request waits for activation and, when no provider registers, up to the existing 5-second registration timeout. The cleanup runs in finally after success, error, service cancellation, or timeout and is not an additional awaited step.
- Scaling input: Number of timed-out attempts over the AuthenticationService lifetime and number of simultaneously active attempts. The fixed retained-resource cost previously grew linearly with cumulative failures; it now grows only with active calls.
- Effective concurrency: Concurrent failed callers have independent 5-second waits and child cancellation sources. Same-provider activation IPC is coalesced per extension-host manager; listener count is now bounded by currently active callers instead of cumulative failures.
- Cache behavior: There is no negative provider cache, so each failed request retries tryActivateProvider. Extension-host managers still cache a repeated provider's activation event, while distinct provider IDs use distinct activation keys. Before the diff, each timeout left one listener on the service lifetime token; after the diff, finally disposes and cancels the child source, removing both child and parent registrations.
- Mechanism confidence: Very high: raceCancellation's token listener survives while Event.toPromise remains pending; timeout does not settle that promise; dispose(true) on the operation source cancels the race and unlinks its parent listener.
- Magnitude uncertainty: The frequency of unavailable-provider requests in production is workload-dependent, but the old retention mechanism and the new bounded lifecycle are directly established and covered by the added repeated-timeout test.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/extensions/common/abstractExtensionService.ts:989-1042</code>: Request authentication-provider activation from relevant extension hosts when the registry contains the activation event.; cardinality: For a declared unavailable provider, one cold underlying call per relevant extension-host manager and activation event; repeated same-ID failures reuse host-manager promises. Undeclared/no-interest events return without host IPC. Distinct declared IDs can each have one cold activation fan-out.
    - Introduced by diff: false; previous behavior: Identical activation requests, coalescing, and timeout behavior existed; only listener cleanup after the timeout differed.; critical-path effect: Activation is in the request race; if it completes without registration, the request remains blocked on the existing timeout.
- Verdict: This is a concrete cleanup-lifecycle performance fix, recorded through report\_regression\_fix. It introduces no new performance issue.

### Scenario 3: Authorization-server provider discovery across declared candidates

- Critical path: Candidate activation is sequential. For each candidate, activation/provider registration and any existing 5-second timeout must finish before the next candidate is tried. The new child token is disposed at the end of each candidate attempt and does not add an awaited boundary.
- Scaling input: Number of unregistered declared providers whose authorization-server globs match, after filtering already registered providers.
- Effective concurrency: Candidates are serialized by the for/await loop. Within one candidate, relevant extension hosts are activated concurrently and cache/coalesce that event per manager.
- Cache behavior: Already registered providers are checked first. Remaining declared provider candidates are filtered, then activated sequentially. Each candidate uses a distinct activation-event cache key in extension-host managers; later discovery calls benefit from those activation caches and from any successful provider registration, but failed providers have no negative cache.
- Mechanism confidence: High: the sequential loop and transitive concurrent/cached extension-host activation are explicit.
- Magnitude uncertainty: Typical matching-candidate counts are not established here; this pre-existing serialized behavior is unchanged by the PR.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/authentication/browser/authenticationService.ts:351-363; src/vs/workbench/services/extensions/common/abstractExtensionService.ts:1023-1042</code>: Activate each matching declared authentication provider across relevant extension hosts.; cardinality: Up to one cold activation IPC per relevant extension-host manager for each distinct matching candidate; candidates are serialized. Warm activation-event caches avoid repeating host work.
    - Introduced by diff: false; previous behavior: The same sequential candidate loop, host fan-out, cache behavior, and timeouts existed before the diff.; critical-path effect: Each candidate's activation/registration result gates checking the next candidate and therefore provider discovery completion.
- Verdict: No reportable regression. The changed cleanup prevents listeners from accumulating across candidate failures and leaves existing critical-path and boundary behavior unchanged.
