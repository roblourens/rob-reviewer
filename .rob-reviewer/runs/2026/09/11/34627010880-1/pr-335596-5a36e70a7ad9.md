### Scenario 1: Developer or CI runs the repository-wide \`npm run eslint\` command after the lint rule change.

- Critical path: The lint command must enumerate, parse, and lint applicable files before CI or the developer workflow can complete. The new branch executes synchronously inside the existing \`MemberExpression\` visitor; it adds only fixed AST-kind/name comparisons for computed string-literal members and returns before the existing TypeScript scanner for direct \`process.env\[...\]\` accesses.
- Scaling input: Cost scales with uncached source files and, within each parsed file, computed member expressions whose property is a string literal without escapes. The changed work is O(1) per such node; direct \`process.env\[...\]\` nodes avoid the pre-existing scanner call. Repository search shows many direct accesses, but they are grouped naturally within each file's single ESLint traversal rather than triggering separate work.
- Effective concurrency: \`build/eslint.ts\` configures ESLint with \`concurrency: 'auto'\`; files are processed with ESLint-managed parallelism. The rule itself creates no promises, queues, locks, subprocesses, or additional concurrency.
- Cache behavior: ESLint uses a content cache at \`.eslintcache\`. Cold or invalidated files run the visitor once during their AST traversal; warm unchanged files can be served from the cache. The rule adds no cache, cache key, retained state, or negative-cache behavior.
- Mechanism confidence: High: the complete diff and visitor control flow show no allocation proportional to repository size beyond existing traversal, no new boundary, and no retained state. The branch is constant-time and can reduce work for direct \`process.env\[...\]\` accesses.
- Magnitude uncertainty: Exact cold-run node counts and timing are not measured, but the changed mechanism is bounded to several primitive comparisons per qualifying AST node and removes scanner work for the newly exempted receiver; there is no realistic material regression mechanism.
- Expensive boundaries:
  - subprocess at <code>package.json:80 (\`eslint\` script)</code>: The package runner launches one Node process for \`build/eslint.ts\`.; cardinality: One Node process per lint command, independent of source-file or AST-node count.
    - Introduced by diff: false; previous behavior: The same package script launched the same Node lint process before the diff.; critical-path effect: The process must finish for the lint command and CI check to complete.
  - filesystem at <code>build/eslint.ts:25-35 (\`ESLint\` construction and \`lintFiles\`)</code>: ESLint enumerates and reads applicable repository source files, parsing uncached files before invoking AST visitors.; cardinality: Cold runs cover files selected by the repository lint filters; warm runs reuse \`.eslintcache\` for unchanged content. Each processed file is traversed once and the changed rule shares that traversal.
    - Introduced by diff: false; previous behavior: The same \`lintFiles\` operation, file patterns, content cache, and auto concurrency existed before the diff.; critical-path effect: File discovery/read and lint completion are on the command's critical path, but no filesystem call was added or moved by this diff.
- Verdict: No reportable performance regression. The full-repository lint path receives only bounded constant-time checks inside an existing visitor, while the targeted exempted accesses skip more expensive pre-existing scanner creation.
