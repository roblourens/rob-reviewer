# Performance review: agentHost: Exclude SDK-native skills from directory discovery

[PR #335500](https://github.com/microsoft/vscode/pull/335500) at `ce80772038d90f96f2ce4c8b6aa80702bb1afc13`

## Findings (1)

### 1. [medium] Cache plugin-root discovery across reported plugin files

**Finding ID:** `PERF-D663C0F5DF58`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:771</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Serialized filesystem resolve/stat operations  
**Scaling:** For F unique files reported across installed plugins and ancestor depth D, the new root phase performs up to 3\*F\*D filesystem operations serially; deduplicating pluginRoots only happens after this cost. A plugin with many agents/rules/skills therefore repeats the same ancestor probes for each child.  
**Outcome:** Increased session-creation and customization-refresh latency from serialized filesystem I/O  
**PR causality:** <code>introduced</code>  
**Previous behavior:** SDK-native plugin agents and rules were converted from the SDK discovery response without filesystem root probing; plugin skills incurred their existing skill-file parse, but no ancestor walk was performed for every reported plugin child.  
**Changed behavior:** Every unique SDK-reported plugin agent, rule, or skill is now sent through findPluginRoot before roots are deduplicated. That helper performs up to three awaited filesystem existence checks at each ancestor, and the outer loop awaits files one at a time.  
**Confidence:** 0.97 — The changed filesystem calls, their serialized placement, per-session critical-path caller, and F-by-D scaling are directly visible in the changed code. Exact latency depends on plugin count, contribution count, path depth, and filesystem speed, which is reflected in medium severity rather than lower mechanism confidence.

**Causal diff evidence:** The added call \`const root = await this.findPluginRoot(file, token);\` at line 771 introduces one serialized ancestor walk per SDK-reported plugin file; the added findPluginRoot implementation at lines 807-824 performs up to three awaited existence checks at every ancestor before roots are deduplicated.

Creating a Copilot agent session with SDK-installed plugins now waits for these probes through createSession -&gt; getChatCustomizations -&gt; getCustomizationsSettled -&gt; discover. Workspace customization changes and root-config changes rerun the same uncached work, so plugins with many contributions can also delay refreshes and slash-command customization reads.

**Evidence:** SessionDiscoveredEntry is per session and its initial refresh is awaited by getCustomizationsSettled; AgentService awaits getChatCustomizations while creating the initial session snapshot. In the added code, toPluginCustomizations loops over every pluginFiles entry and awaits findPluginRoot, whose loop awaits three IFileService.exists calls per ancestor. ResourceSet removes duplicate file URIs, not the many distinct files belonging to one plugin, and pluginRoots is populated only after each full walk.

**Suggested direction:** Memoize visited ancestor directories to their resolved plugin root (including negative results) for the duration of a discovery, so all files under one plugin share one walk; preserve cancellation and manifest-format checks. Grouping SDK results by a cached root before parsing also keeps root-level work proportional to installed plugins rather than contributed files.

**Fix location:** `src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:639` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:875`

**Mechanism family:** `boundary-fanout`  
**Performance category:** `io`  
**Confidence:** 0.94

**Mechanism:** SDK-native plugin customizations were treated as directory-backed items even though their paths were outside all SDK discovery directories, causing the fallback invariant error to be emitted once per such customization on every discovery refresh.

**Symptom:** The PR records a recent session emitting the invariant error tens of thousands of times, creating excessive logging work and log I/O during customization refreshes.

**Fixed behavior:** The added source check diverts plugin-owned agents into plugin projection instead of directory conversion (with corresponding checks for rules and skills), so these SDK-native items no longer hit the per-customization fallback error path; the remaining fallback diagnostic is also lowered from error to trace.

**Evidence:** Before the change, discoverAgents/rules/skills returned plugin-owned children to toDirectoryCustomizations; when no discovery directory contained them, base line 875 logged an error inside the per-customization loop. Added line 639 identifies plugin agents before insertion, corresponding added source checks handle rules and skills, and the new plugin projection keeps them out of that fallback path. blame identifies the SDK-discovery change that introduced the old mechanism.

### Scenario 2: Refresh open-session customizations after a watched workspace/user customization change or root configuration change

- Critical path: A file watcher or root-config event schedules a 100 ms debounced SessionDiscoveredEntry refresh. The refresh reruns discover, including the new plugin root probes and parses, before publishing the customization update. Calls such as skill slash-command candidate retrieval that arrive while this refresh is pending await getCustomizationsSettled; otherwise the work is on the customization-update critical path rather than the message-rendering path.
- Scaling input: The same F plugin files, D ancestor depth, and P plugin roots per affected session; a user-home change can affect N open sessions, producing N independent copies of the work after per-entry debouncing.
- Effective concurrency: Events within one entry are coalesced by Delayer and an in-flight refresh is canceled/replaced. There is no coalescing across open sessions; each session entry can issue its SDK RPCs and filesystem work concurrently, while each entry serializes root walks and root parses internally.
- Cache behavior: The \`\_discoveredDirectories\` cache avoids repeated getDiscoveryPaths calls within one entry, but SDK discover calls, plugin-root walks, plugin parsing, and their negative results are repeated on each settled refresh. The 100 ms debounce limits event frequency but does not reuse plugin results across refreshes or sessions.
- Mechanism confidence: High: watcher/config events are wired directly to the per-session refresh, no plugin cache exists, and the changed filesystem work is awaited.
- Magnitude uncertainty: The number of simultaneously open sessions and frequency of relevant watched changes vary. Debouncing bounds bursts within one session, but shared user customization changes can still fan out across sessions.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:discover</code>: Repeat Copilot SDK discover RPCs; cardinality: Three concurrent discover RPCs per affected session and settled refresh.
