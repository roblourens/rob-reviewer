# Performance review: agentHost: record PR action results as artifacts

[PR #335729](https://github.com/microsoft/vscode/pull/335729) at `ad7289124768f1b95713f6017112395796618553`

## Findings (1)

### 1. [medium] Keep artifact persistence off the Create PR response path

**Finding ID:** `PERF-5CE95BB03063`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostPullRequestOperationProvider.ts:268</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** two serial per-session SQLite metadata writes plus serialization of the complete artifact array  
**Scaling:** A new or promoted PR incurs one artifact transaction followed by one GitHub-state write; artifact serialization and duplicate lookup grow with the session artifact count, while wait time also includes all earlier mutations queued on the per-session database. An already-promoted duplicate skips the artifact transaction but still waits for the GitHub-state write.  
**Outcome:** blocked critical path and increased tail latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The callback only updated GitHub state and returned synchronously. Its database save was started fire-and-forget, so once GitHub create/find (and optional auto-merge) completed, the handler could immediately return the follow-up and clear Running status without waiting for local metadata I/O.  
**Changed behavior:** Every successful create/reuse-PR operation now synchronously serializes the full artifact collection and waits for a new SQLite transaction, then waits for the existing GitHub-state SQLite write, before the operation can leave Running or return its PR follow-up.  
**Confidence:** 0.97 — The changed handler-to-provider call path is explicitly awaited; \`SessionArtifacts.mutate\` explicitly awaits persistence; \`persistSessionMetadataValues\` calls the per-session SQLite database; and the operation service leaves the operation Running until the handler promise resolves. Exact delay depends on cold database initialization, disk speed, and queued mutations, but the newly blocked critical path and two serial metadata boundaries are certain.

**Causal diff evidence:** RIGHT src/vs/platform/agentHost/node/agentHostPullRequestOperationProvider.ts:268 adds \`await artifacts.mutate(...)\`; that mutation awaits \`persistSessionMetadataValues\`, which executes a SQLite \`setMetadataValues\` transaction. The handler also changed \`\_onPullRequestCreated\` to a Promise and awaits it before constructing the result, so this new transaction and the subsequently awaited GitHub-state metadata write now precede the JSON-RPC response.

After GitHub has already created or located the PR, the Create PR action can remain spinning and delay opening/reporting the PR while the session database initializes or drains queued writes; slow or busy disks directly add tail latency to every newly recorded PR.

**Evidence:** \`SessionArtifacts.mutate\` queues by session and awaits \`\_persist\` before publishing. \`\_persist\` opens the session database and calls \`setMetadataValues\`; \`SessionDatabase.setMetadataValues\` acquires both the metadata and shared mutation sequencers and runs \`BEGIN\`/\`INSERT OR REPLACE\`/\`COMMIT\`. After that completes, \`recordCreatedPullRequest\` awaits \`setSessionGitHubState\`, whose \`\_saveSessionState\` performs another sequenced SQLite metadata write. \`AgentHostChangesetOperationService.\_executeChangesetOperation\` keeps status Running and withholds the result until all of this resolves.

**Suggested direction:** Keep the in-memory artifact/GitHub-state updates synchronous for immediate publication, but move durable persistence off the operation response path using the database's tracked-write/shutdown-flush mechanism. If success must wait for durability, write the artifact and GitHub/source-control metadata together in one \`setMetadataValues\` transaction instead of awaiting separate transactions.
