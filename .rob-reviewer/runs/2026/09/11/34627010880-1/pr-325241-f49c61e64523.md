# Performance review: Use Copilot SDK APIs to discover customizations

## Findings (2)

### 1. [medium] Run the initial customization refresh without the debounce

**Finding ID:** `PERF-0AF7178B65AE`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3217</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** A 100 ms scheduled timer wait on the session creation and restoration critical path, followed by customization filesystem/RPC work  
**Scaling:** The fixed delay is paid once for every newly created or restored Copilot session, independent of workspace size; the subsequent discovery cost still scales with customization roots and files.  
**Outcome:** At least 100 ms of avoidable session creation/restoration latency before the first session snapshot can be published  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The constructor called \`\_queueRefresh(false, 0)\`, so the initial discovery task was scheduled immediately; only watcher-driven follow-up refreshes used \`REFRESH\_DEBOUNCE\_MS\`.  
**Changed behavior:** The constructor now omits the delay argument, so \`Delayer.trigger\` uses its 100 ms default before starting the initial refresh.  
**Confidence:** 0.99 — The exact timer value, Delayer semantics, and fully awaited create/restore call paths are explicit in the repository. Magnitude beyond the guaranteed 100 ms depends on discovery duration, but the mechanism and critical-path delay do not.

**Causal diff evidence:** The added RIGHT line \`this.\_settled = this.\_queueRefresh(false);\` replaces \`this.\_queueRefresh(false, 0)\`, directly moving initial discovery behind the 100 ms default debounce.

Creating a Copilot session blocks in \`AgentService.createSession\` while \`provider.getSessionCustomizations()\` reaches \`getCustomizationsSettled()\` and waits for \`whenSettled()\`. Restoring a session has the same awaited path. Every create/restore therefore waits at least 100 ms before customization discovery even begins, delaying the first usable snapshot.

**Evidence:** \`REFRESH\_DEBOUNCE\_MS\` is 100 and \`\_queueRefresh\` forwards its default delay to \`Delayer.trigger\`. \`CopilotAgent.getSessionCustomizations\` awaits \`pluginController.getCustomizationsSettled()\`, which awaits \`entry.whenSettled()\`, and \`AgentService.createSession\` awaits that provider call before registering initial state. The modified test also changed from observing work after 50 ms to waiting \`REFRESH\_DEBOUNCE\_MS + 200\`, corroborating the scheduling change.

**Suggested direction:** Keep debounce for change bursts, but pass \`0\` for the constructor's initial \`\_queueRefresh\` as before (or otherwise start the first refresh immediately).

### 2. [medium] Refresh sessions only when the discovery mode changes

**Finding ID:** `PERF-386C56B7F0A7`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3221</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Filesystem resolves/scans and, in discover mode, Copilot SDK IPC requests and subprocess-side discovery work  
**Scaling:** Each unrelated root-config event triggers one full refresh per live session entry. In the default scan mode this is roughly the configured discovery-root traversal per session (13 roots in the updated tests, plus recursive hook/instruction contents); in discover mode it is three content-discovery RPCs per warm entry, plus local hook scans and watcher-stat resolves. Root-config handling starts these session publishes concurrently, so cost grows as O(active sessions × discovery roots/files) or 3 × active sessions RPCs.  
**Outcome:** Bursty excessive filesystem I/O or SDK IPC/subprocess work, increasing config-update latency and contending with active agent-host work  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Session-discovered entries refreshed on filesystem watcher changes only. A root-config action republished all sessions, but already-settled live entries did not re-run their disk discovery merely because an unrelated root key changed.  
**Changed behavior:** Every \`SessionDiscoveredEntry\` now subscribes to the payload-less \`onDidRootConfigChange\` and unconditionally queues a discovery refresh, even when \`sessionCustomizationDiscoveryMode\` is unchanged.  
**Confidence:** 0.97 — The event's all-keys semantics, one-listener-per-session ownership, full refresh call paths, and concurrent all-session publisher are explicit. The exact number of simultaneously live sessions and filesystem duration vary by user, affecting severity but not the fan-out mechanism.

**Causal diff evidence:** The added RIGHT listener at line 3221 invokes \`\_queueRefresh(true)\` for every root-config event; no per-session config-triggered discovery existed before this hunk.

Changing any host setting—telemetry, permissions, proxy, auto-approve, model-related options, and others—causes all live Copilot session entries to rescan customization trees. With SDK discovery enabled, each warm session issues three concurrent SDK RPCs; multiple sessions create a 3N request burst. The root-config side effect simultaneously republishes every session and awaits these queued refreshes.

**Evidence:** \`IAgentConfigurationService.onDidRootConfigChange\` explicitly fires for every \`RootConfigChanged\` action and carries no changed key; the GitHub endpoint service documents this and guards by comparing its derived value. The added listener has no such guard. Its \`\_queueRefresh\` reaches \`\_discovery.scan\` (filesystem traversal) in the default mode or \`\_discovery.discover\` in SDK mode; the latter calls \`agents.discover\`, \`instructions.discover\`, and \`skills.discover\` in \`Promise.all\`. \`AgentSideEffects.\_publishAllSessionCustomizations\` iterates every session on each root-config action without a limiter.

**Suggested direction:** Store the last effective discovery mode in the entry, re-read it on root-config events, and queue a refresh only when that value actually changes, matching the existing derived-value guard pattern.

### Scenario 2: Create or refresh a session with SDK discovery mode enabled

- Critical path: On a cold entry, \`getSessionCustomizations\` waits for Copilot client availability, three discovery-path RPCs, then three content-discovery RPCs plus local hook scanning/watcher resolution. Warm watcher refreshes skip discovery-path RPCs but still await three content RPCs and local filesystem work.
- Scaling input: One project path per session; content and mapping work scale with discovered agents, instruction sources, skills, hook files, and directory depth. Across sessions, RPC count scales per session rather than per unique working directory.
- Effective concurrency: The three path RPCs run concurrently; after they finish, three content RPCs, hook scanning, and watcher updates run concurrently. One entry coalesces bursty watcher events using a 100 ms Delayer and cancels its prior refresh, but entries have no cross-session limiter.
- Cache behavior: \`\_discoveredDirectories\` caches discovery-path results for the entry lifetime, so cold success costs three path RPCs and warm refreshes do not. Content discovery is always fresh. There is no cross-session cache or request coalescing, and negative/failure results from the caught path-discovery block are cached as the returned hook-only list after successful assignment.
- Mechanism confidence: High: RPC counts, cache placement, ordering, and awaited critical path are explicit.
- Magnitude uncertainty: SDK RPC and cold subprocess startup duration depend on environment. The mode is opt-in/defaults to scan, so the base six-RPC cold path is an intentional feature tradeoff rather than an additional finding by itself.
- Expensive boundaries:

    - Introduced by diff: true; previous behavior: SDK discovery mode and these RPCs did not exist; local scan was used.; critical-path effect: All three must settle before content discovery starts
  - IPC at <code>src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:520</code>: Copilot SDK \`agents/instructions/skills.discover\` requests; cardinality: Three concurrent RPCs per discovery refresh per session entry

### Scenario 3: Apply any root-level agent-host configuration change while sessions are live

- Mechanism confidence: Very high: event all-key semantics, per-entry listener, refresh bodies, and unbounded all-session publisher are explicit.

### Scenario 4: Edit customization files while a session is open

- Critical path: Filesystem watcher changes signal the entry, which waits the intended 100 ms debounce and then refreshes before emitting updated customization state. This is off the immediate typing/render path but controls when customization UI/state reflects file edits.
- Scaling input: File-event burst frequency, number of affected session entries (especially shared user-home roots), and customization tree size; SDK mode adds three RPCs per effective debounced refresh.
- Effective concurrency: Within one entry, events coalesce into one delayed refresh and an in-flight refresh is canceled when superseded. Across sessions watching shared user-home paths, each entry refreshes independently with no global coalescing.
- Cache behavior: Scan mode performs a fresh local scan. Discover mode reuses cached discovery directories but refreshes content RPCs and local hooks/watchers. Equality checks suppress unchanged publication after work completes.
- Mechanism confidence: High for per-entry behavior; lower only for typical simultaneous session count.
- Magnitude uncertainty: Shared-home watcher fan-out depends on how many session entries remain live and which SDK paths are returned.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3218</code>: Watcher notification followed by local scan or hook/watcher resolution; cardinality: One effective refresh per entry per debounced event burst
    - Introduced by diff: false; previous behavior: Watcher-driven local rescans already existed and used the same debounce/coalescing mechanism.; critical-path effect: Determines customization update latency but is not on an active turn's core request path
  - IPC at <code>src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:520</code>: Three SDK content-discovery RPCs after a debounced watcher event in discover mode; cardinality: Three per affected entry per effective burst
    - Introduced by diff: true; previous behavior: File edits caused local rescans only.; critical-path effect: Must complete before changed customizations are published
- Verdict: No additional finding: per-entry debounce/cancellation is intentional and bounded; cross-session cost is concretely problematic when the new unrelated root-config listener forces it, which is reported separately.
