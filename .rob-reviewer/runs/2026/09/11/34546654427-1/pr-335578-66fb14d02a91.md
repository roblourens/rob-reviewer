# Performance review: actionWidget: fix: resume interrupted IME searches

[PR #335578](https://github.com/microsoft/vscode/pull/335578) at `66fb14d02a916676638641c6e0c21749253487a6`

## Findings (1)

### 1. [medium] Cancel the stale search before restarting it

**Finding ID:** `PERF-89CC2C0C30C1`  
**Location:** <code>src/vs/platform/actionWidget/browser/actionList.ts:1082</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** JSON-RPC requests and Git subprocesses  
**Scaling:** When a dynamic search takes longer than successive unchanged IME composition cycles, every cycle that reaches compositionend after the 200 ms delayer starts another request; concurrent stale work grows linearly with the number of cycles. For branch completion, each request launches at least three and up to five uncached Git subprocesses.  
**Outcome:** Concurrent stale RPC/Git work can contend with the replacement search, increasing picker result latency and subprocess/CPU load in slow or large repositories.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The prior unchanged-value guard returned for every compositionend whose committed text matched \`\_filterText\`, so after the first request was cancelled no replacement RPC or Git work was launched for repeated unchanged composition cycles.  
**Changed behavior:** The new condition deliberately falls through whenever the stored request token is cancelled, and \`\_applyOrUpdateFilter\` immediately creates a replacement request. The two production delegates ignore the supplied cancellation token, so cancelling the ActionList request only suppresses its result and does not stop the underlying completion RPC.  
**Confidence:** 0.96 — The changed fall-through, immediate request creation, ignored token, 200 ms coalescing window, JSON-RPC boundary, and uncached Git subprocess fan-out are all directly traced. Exact user frequency and Git duration vary, which affects severity, but not the concurrency mechanism.

**Causal diff evidence:** Added line 1082 changes an unchanged cancelled query from an unconditional return into a call to \`\_applyOrUpdateFilter\`; before this line, the same compositionend could not launch another provider request.

In a dynamic branch picker on a repository where completion is slow, repeatedly starting and cancelling IME composition without changing the query can leave multiple branch scans running at once. The useful replacement waits behind contention from stale scans, while the agent host executes 3–5 Git commands per scan.

**Evidence:** \`onFilterValueChanged\` now restarts the same text when \`\_filterCts\` is cancelled (line 1082), and \`\_applyOrUpdateFilter\` invokes the delegate immediately after the consumer's 200 ms Delayer. Both \`AgentHostChatInputPicker\` and \`AgentHostSessionConfigPicker\` define \`onFilter\` without the cancellation-token argument, then call \`sessionConfigCompletions\`/\`getSessionConfigCompletions\`; neither completion API accepts a token. \`AgentHostProtocolClient.sessionConfigCompletions\` sends JSON-RPC, and \`WorktreeIsolation.branchCompletions\` executes \`getBranches\`, \`getCurrentBranch\`, and \`getDefaultBranch\` in parallel. \`AgentHostGitService\` implements these as uncached Git invocations (\`for-each-ref\`, \`branch --show-current\` with fallback, and \`symbolic-ref\` plus up to two \`show-ref\`s). The added regression test also leaves the first DeferredPromise unresolved when the second request is created, directly demonstrating overlap.

**Suggested direction:** Preserve the IME restart, but ensure it cannot overlap stale backend work: forward the ActionList cancellation token through the dynamic picker delegates and completion protocol/Git implementation, or sequence/coalesce same-query retries so at most one underlying provider search is active.
