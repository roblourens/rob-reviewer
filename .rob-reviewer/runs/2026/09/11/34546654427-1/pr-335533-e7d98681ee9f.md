# Performance review: sessions: Show status indicators in collapsed sections

[PR #335533](https://github.com/microsoft/vscode/pull/335533) at `e7d98681ee9fad7b2eec4c8875a8d5f1d8ec9802`

## Findings (1)

### 1. [medium] Reuse the existing blocked-session aggregation

**Finding ID:** `PERF-9C2B79C6FFB9`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:2707</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and transient objects/references created while scanning sessions and aggregating blocked CI state  
**Scaling:** Each relevant update adds O(N + P + B log B) work for N managed sessions, P sessions with pull requests/CI references, and B blocked sessions, even though an equivalent workbench-owned blocked-session computation is already live.  
**Outcome:** increased UI-thread CPU/GC pressure and slower Sessions-list updates  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, constructing/rendering \`SessionsList\` did not create another \`BlockedSessions\`; blocked-state collection-wide work was performed by existing workbench owners only, and the list had no duplicate full-history aggregation.  
**Changed behavior:** Opening the Sessions view with the setting enabled now activates an additional independent blocked-session derivation. On every management-session event or observed status/archive/PR/CI change, that derivation walks the complete session collection, reacquires shared PR/CI references for applicable sessions, sorts blocked results, and then allocates filter/map arrays plus a new failing-CI \`Set\`.  
**Confidence:** 0.94 — The changed constructor path, lazy activation through the consumed \`sessionsWithFailingCI\` observable, and \`BlockedSessions\` implementation were traced directly. Its \`\_allSessions\` and per-session observables drive a full loop, PR/CI reference acquisition, and sort on recomputation. Existing reference collections coalesce network models, so the regression is CPU/allocation rather than duplicate requests; exact delay depends on session-history size.

**Causal diff evidence:** The added line constructs a fresh \`BlockedSessions\` inside every \`SessionsList\` when the experiment is enabled (\`reader.store.add(instantiationService.createInstance(BlockedSessions))\`), rather than reusing the already workbench-owned model created by \`SessionsTitleBarContribution\` (and, on desktop, \`SessionsApplicationBadge\`).

With the experiment enabled and the Sessions view open, users with long agent-session histories pay a second collection-wide pass and transient reference/array allocation for routine session updates and CI polling changes, increasing UI-thread CPU/GC pressure and delaying list reactions.

**Evidence:** \`BlockedSessions.blockedSessionsWithReasons\` iterates every \`ISessionsManagementService.getSessions()\` entry, calls \`\_getBlockedSession\` (including shared PR and CI reference acquisition), and sorts the blocked array. This work is already owned at workbench scope by \`SessionsTitleBarContribution\` from BlockRestore (and by the application badge on desktop), but the new list-local instance cannot reuse that computation. Agent-host providers emit session-change events for read, archive, title, summary, and notification updates, so the duplicate pass is not limited to initial render.

**Suggested direction:** Provide one shared workbench/service-owned \`BlockedSessions\` (or shared failing-CI observable) to the list and reference-count only the list subscription while the setting is enabled, instead of constructing an independent model per list.
