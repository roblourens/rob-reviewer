# Performance review: mcp: add gated workspace-root configuration entry points

[PR #335551](https://github.com/microsoft/vscode/pull/335551) at `a517096615a85d779c3f5c5d1388c3ef14525e2a`

## Findings (1)

### 1. [medium] Avoid duplicating \`.mcp.json\` I/O for every workspace folder

**Finding ID:** `PERF-F0C7404D6708`  
**Location:** <code>src/vs/workbench/services/mcp/common/mcpWorkbenchManagementService.ts:643</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem reads, provider watch subscriptions, and file-change listener CPU work  
**Scaling:** For F workspace folders, this adds F eager \`readFile\` attempts and F long-lived uncorrelated file watches/listeners; the additions are launched together through \`Promise.allSettled\`, so remote workspaces receive an F-wide startup burst, and subsequent filesystem events are checked by F extra listeners.  
**Outcome:** increased MCP readiness/startup latency in large or remote multi-root workspaces, plus persistent filesystem watcher and event-dispatch overhead  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Workspace management eagerly created services only for the workspace and each folder's \`.vscode/mcp.json\`. Workspace-root \`.mcp.json\` already had its own \`WorkspaceDotMcpDiscovery\` path, which performs an initial read and owns a correlated watcher for each folder after restore.  
**Changed behavior:** The added call creates a second management service for every folder's \`.mcp.json\`, even when the file does not exist. \`addWorkspaceService\` awaits \`service.getInstalled()\`, which reads the file, and \`AbstractMcpResourceManagementService.initialize()\` then always calls \`fileService.watch\` and registers a global \`onDidFilesChange\` listener for that same resource.  
**Confidence:** 0.97 — The added per-folder call, its awaited startup path, the unconditional scan/watch lifecycle, and the pre-existing independent root discovery read/watch are all directly traced in repository code. Exact remote latency and typical folder count vary, which affects severity but not the duplicated F-scaling mechanism.

**Causal diff evidence:** The added RIGHT-side call at line 643 invokes \`addWorkspaceService(...WORKSPACE\_ROOT\_MCP\_CONFIG\_FILE...)\` for every added/initial workspace folder. That transitive path calls \`service.getInstalled()\` and then \`startWatching()\`, while unchanged \`WorkspaceDotMcpDiscovery.\_watchFolder\` already reads and watches the identical root file.

Opening a large multi-root workspace, especially over SSH/Codespaces or another remote filesystem, now bursts one additional remote file read per folder and keeps a second watcher for every root config. MCP local readiness—and therefore agent-host support assessment, which awaits \`whenInitialLocalMcpServersLoaded\`—cannot complete until these added scans settle; ongoing file activity also fans out through the extra listeners.

**Evidence:** \`McpWorkbenchService\` is registered eager and its constructor starts \`queryLocal\`; \`queryLocalForGeneration\` awaits \`mcpManagementService.getInstalled()\`, which awaits \`workspaceUpdatePromise\`. Initialization reaches the added flat-mapped root service for every folder. Each service's \`populateLocalServers\` calls \`scanMcpServers\`/\`readFile\`, and its \`startWatching\` installs both \`fileService.watch(this.mcpResource)\` and a global file-change listener. Separately, \`WorkspaceDotMcpDiscovery\` still calls \`readFile(configFile)\` and \`createWatcher(configFile)\` for every \`.mcp.json\`, so the new work duplicates an existing boundary and watcher rather than replacing it.

**Suggested direction:** Use one owner for root-file inventory and watching: share the existing \`WorkspaceDotMcpDiscovery\` read/watch results with management, or make root management services lazy for write operations and subscribe them to the existing discovery updates. Preserve exact resource identity, but do not eagerly issue and retain a second read/watch pair per folder.

- Effective concurrency: Each owner coalesces its own events with a \`RunOnceScheduler\`, but there is no coalescing across discovery and management. Their reads can overlap; discovery rejects stale sequences, while management's scheduler does not share that sequence.

- Mechanism confidence: High for duplicated reads and independent scheduling; user-visible duration depends on provider and file size.
