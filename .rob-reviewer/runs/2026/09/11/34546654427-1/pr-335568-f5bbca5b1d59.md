# Performance review: Use TextMate highlighting in component fixtures

[PR #335568](https://github.com/microsoft/vscode/pull/335568) at `f5bbca5b1d59981220f4fc4799b767c7c10d571f`

## Findings (1)

### 1. [medium] Initialize TextMate only for fixtures that render text models

**Finding ID:** `PERF-B39FC3DFE002`  
**Location:** <code>src/vs/workbench/test/browser/componentFixtures/fixtureUtils.ts:1164</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** XHR/filesystem grammar reads, grammar parsing, and tokenizer construction CPU  
**Scaling:** In serial screenshot/CI rendering, fixture-scoped disposal drops the final shared reference after each fixture, so grammar setup repeats with fixture/theme count; non-editor fixtures also pay the cost.  
**Outcome:** Blocked fixture startup and reduced screenshot/CI throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Fixtures awaited their requested UI/file-icon theme before options.render; non-editor fixtures did not initialize Oniguruma or TextMate grammars.  
**Changed behavior:** Every fixture now awaits TextMate setup before its render callback. Acquisition creates the Oniguruma runtime, a TMGrammarFactory, and tokenizers for seven root languages; final-reference disposal clears the shared instance.  
**Confidence:** 0.97 — The unconditional critical-path call, resource loader, grammar construction, and teardown are directly traced. HTTP caching may reduce later physical I/O, but parsing/construction and the await remain; only exact duration is uncertain.

**Causal diff evidence:** Added line 1164 unconditionally awaits registerFixtureSyntaxHighlighting on every component fixture's render critical path.

Rendering even simple Buttons or Toggles fixtures now waits for grammar resource loading/parsing. Serial fixture capture can reconstruct grammars for each fixture/theme, extending component-explorer startup and CI duration.

**Evidence:** This call precedes options.render at fixtureUtils.ts:1207. registerFixtureSyntaxHighlighting awaits acquire; FixtureTextMateTokenizerInstance.create builds Oniguruma/TMGrammarFactory and seven language grammars, while TMGrammarFactory invokes the XHR-backed readFixtureTextResource for loaded scopes. FixtureTextMateTokenizers clears its instance when the fixture-owned final reference is disposed. baseUI.fixture.ts demonstrates many fixtures with no text models.

**Suggested direction:** Gate setup behind an editor/syntax-highlighting fixture capability enabled only for fixtures that create highlighted models, or retain one run-scoped installation across serial fixture renders rather than owning the final reference in each fixture store.

### Scenario 2: Render editor and multi-diff fixtures that create highlighted text models

- Critical path: The same TextMate setup completes before options.render. Each createTextModel then synchronously force-tokenizes through the model's final line before the fixture render promise can settle and capture can proceed.
- Scaling input: Total lines across models created by one fixture. Existing call sites create roughly one to six models; inspected multi-diff inputs are bounded samples, including 20-line unchanged blocks and short source snippets.
- Effective concurrency: Grammar initialization uses the coalesced shared promise and concurrent root grammar creation. forceTokenization itself runs synchronously per model in call order, with no limiter or worker boundary.
- Cache behavior: Tokenizer supports are shared while fixture references overlap. Each model stores its own tokens; forcing to the last line avoids later work for those lines but performs all line tokenization eagerly.
- Mechanism confidence: High for O(total model lines) synchronous CPU work; moderate for material impact because present fixture inputs are small and deterministic highlighting before capture is intentional.
- Magnitude uncertainty: Future fixtures could provide larger models, but current inspected model samples and model counts are modest. No measured evidence establishes a separate user-visible regression from force-tokenizing these bounded screenshot fixtures.
- Expensive boundaries:
  - network/filesystem at <code>src/vs/workbench/test/browser/componentFixtures/fixtureSyntaxHighlighting.ts:FixtureTextMateTokenizerInstance.create</code>: Load and parse the shared TextMate runtime and grammar resources; cardinality: One initialization per overlapping fixture group, potentially repeated after serial final-reference disposal; shared by all models in that group.
    - Introduced by diff: true; previous behavior: Editor fixtures created models without the TextMate runtime/grammar resource boundary.; critical-path effect: Models are not created until initialization completes because options.render runs afterward.
- Verdict: No separate finding: synchronous full-model tokenization is newly eager but currently bounded by small fixture models and directly serves deterministic highlighted screenshots. The unconditional setup affecting non-editor fixtures is covered by the reported finding.

### Scenario 3: Render multiple fixtures concurrently in explorer UI and dispose them independently

- Critical path: All overlapping renders await the same \_instancePromise; once initialized, each creates only host-scoped token CSS before its own options.render. Disposal decrements the shared reference count.
- Scaling input: Number of simultaneously mounted fixtures and token color-map entries used to generate one style element per fixture host.
- Effective concurrency: Initialization is correctly coalesced by \_instancePromise. The reference count retains tokenizers until the final active fixture disposes; no duplicate grammar burst occurs among overlapping acquisitions.
- Cache behavior: Warm overlapping acquisitions reuse the same tokenizer instance and Oniguruma promise. Each fixture generates its own scoped CSS; final disposal releases tokenizer supports and permits recreation for a later non-overlapping group.
- Mechanism confidence: High for coalescing and lifecycle behavior based on the implementation and explicit fixtureUtils comment that explorer UI renders fixtures in parallel.
- Magnitude uncertainty: The explorer's typical overlap count and color-map size affect CSS generation cost, but no evidence shows material rendering or allocation impact from one scoped style per mounted fixture.
- Expensive boundaries: none found
- Verdict: No additional finding: concurrent initialization is coalesced and cleanup is reference-counted; the remaining concern is unnecessary critical-path initialization for fixtures without models.
