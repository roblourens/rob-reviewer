### 1. [medium] Keep draft CI polling scoped to the active preview

**Finding ID:** `PERF-4381EBC812DE`  
**Location:** <code>src/vs/sessions/contrib/github/browser/github.contribution.ts:281</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Authenticated GitHub REST requests, response bytes, JSON parsing, and API rate-limit quota  
**Scaling:** O(U) immediate concurrent refreshes at workbench restore and O(60U) requests per hour, where U is the number of unique owner/repo/PR/head combinations among open drafts in non-archived sessions after model-reference coalescing  
**Outcome:** Excessive background network I/O, startup request bursts, and GitHub API quota pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Draft pull requests returned before creating or refreshing a CI model in this all-sessions contribution. The existing active-session CI observer already refreshes and polls the active draft, so inactive drafts caused no CI requests.  
**Changed behavior:** The per-session background poller no longer excludes draft pull requests, so every tracked open draft acquires a CI model, immediately refreshes it, and starts its 60-second poll loop even when that session is inactive and its hover cannot be viewed.  
**Confidence:** 0.99 — The all-session lifecycle, draft condition change, shared-model key, exact 60-second interval, and REST boundary are directly traced. Only the number of open draft PRs in a user's session history is uncertain, which limits severity rather than mechanism confidence.

**Causal diff evidence:** This changed condition removed the previous \`prDetails.isDraft\` exclusion; the added draft test now expects one CI refresh and \`startPolling\` call, while \`\_pollPullRequest\` is invoked for every PR of every non-archived tracked session.

Opening VS Code with many non-archived sessions backed by distinct draft PRs creates a startup burst and then sustained background GitHub traffic. For 20 drafts this is up to 20 immediate requests plus 1,200 requests/hour, consuming API quota and potentially slowing or rate-limiting GitHub-backed session actions that users actually invoke.

**Evidence:** \`GitHubPullRequestPollingContribution\` is registered \`AfterRestored\`, enumerates all sessions, and loops over all associated PRs. For each open draft now admitted at line 281, lines 287-289 call \`refresh()\` and \`startPolling()\`. \`GitHubPullRequestCIModel\` schedules every 60,000 ms, and each refresh performs \`GET /repos/{owner}/{repo}/commits/{sha}/check-runs\` with the request cache disabled. Models coalesce duplicate references by owner/repo/PR/head SHA, so the effective fan-out is one immediate request and one request per minute per unique open draft, not per duplicate session.

**Suggested direction:** Restore the draft exclusion in this all-sessions poller. Let the existing active-session CI observer cover the currently viewed draft, or tie any additional draft CI reference to the lifetime of the visible PR hover instead of polling every inactive session.

### 2. [medium] Bound Markdown work before building the 200-character preview

**Finding ID:** `PERF-68F181BBB423`  
**Location:** <code>src/vs/sessions/contrib/github/browser/githubHover.ts:16</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Main-thread CPU plus transient Markdown tokens, rendered/sanitized strings, regex output, and Unicode arrays  
**Scaling:** O(sum of raw body lengths for focus transitions); revisiting rows repeats the full O(body length) pipeline, while useful output remains capped at 200 code points  
**Outcome:** Blocked UI input latency and avoidable CPU/GC pressure during dropdown navigation  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Dropdown rows had no rich body preview, so changing focus performed no body parsing or sanitization. The standalone hover directly inserted \`body.trim()\` rather than running a full Markdown parse-and-sanitize pipeline.  
**Changed behavior:** Every rich GitHub hover synchronously sends the entire issue or PR body through \`marked.parse\`, Markdown sanitization, whitespace normalization, and only then truncates the result to 200 Unicode code points.  
**Confidence:** 0.94 — The synchronous focus call path, full-input parser/sanitizer, post-transformation cap, and lack of reuse are explicit. Exact pause duration depends on Markdown body length and structure, so severity is medium.

**Causal diff evidence:** The new helper at line 16 transforms all of \`body\`; its 200-code-point bound is applied only on the following line. The diff also attaches this factory as each issue/PR dropdown row's \`hover.content\`, introducing the work on row focus.

Opening a GitHub-reference collection and arrowing through issues or PRs with long template-heavy bodies can block each focus transition while tens of thousands of characters are tokenized, rendered, sanitized, normalized, and allocated even though only 200 code points are displayed, producing keyboard-navigation jank and CPU/GC spikes.

**Evidence:** \`ActionListWidget.\_showSubmenuForElement\` invokes \`element.hover.content()\` synchronously on every newly focused row. \`createIssueHover\` and \`createPullRequestHover\` call this helper, while \`renderAsPlaintext\` parses the complete input with \`marked\`, sanitizes the complete generated string, and itself warns in code that long values freeze the UI (only imposing a 100,000-character input cap). Returning to a row recreates the hover, so there is no normalized-description cache.

**Suggested direction:** Use a bounded plaintext-extraction path that stops tokenization/output once the preview budget is satisfied (with a small bounded lookahead for Markdown constructs), and cache the normalized 200-code-point description with the resolved issue/PR data so revisiting a row does not repeat parsing.
