## Findings (1)

### 1. [medium] Avoid expanding every narrow tab during each layout

**Finding ID:** `PERF-7423DD934673`  
**Location:** <code>src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:2099</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** browser style recalculation and DOM layout for tab icon, description, and width geometry  
**Scaling:** Cost grows linearly with the number of open tabs in each laid-out editor group and repeats once per animation frame during window or sash resizing; narrow tabs incur the geometry-changing remove/re-add cycle every frame.  
**Outcome:** blocked UI-frame work and dropped frames during continuous resize/layout  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, the tab layout path did not clear and restore a geometry-affecting class across every tab or perform these added per-tab computed-style/text measurements before the existing wrapping measurements.  
**Changed behavior:** Every connected-tab layout now expands all narrow tabs, performs per-tab computed-style/text work, forces geometry measurement, and collapses the tabs again before the existing wrapping/non-wrapping measurements run.  
**Confidence:** 0.98 — The call path and forced-layout mechanism are explicit: \`EditorGroupView.layout\` calls the tab control on each group resize, the control schedules at most once per animation frame, and the new class controls \`display\` of tab children. Removing that class, reading \`offsetWidth\`, restoring it, and then entering existing geometry-reading layout code guarantees repeated style/layout work for narrow tabs. Exact milliseconds vary by tab count and platform, which affects severity rather than mechanism confidence.

**Causal diff evidence:** RIGHT line 2099 newly removes \`connected-tab-narrow\` from every tab on every \`doLayoutTabs\` pass. The added CSS at connectedEditorTabs.css:335-338 makes that class hide icon and description elements with \`display: none\`, so removing it changes tab geometry. The same new method then reads every \`tab.offsetWidth\` at line 2134 and re-adds the class, before \`doLayoutTabsWrapping\` performs further offset/scroll measurements.

Dragging an editor-group sash or resizing a window with connected Modern UI and many compressed tabs can miss frames and feel visibly janky because the tab strip performs two geometry states and collection-wide DOM measurements each frame.

**Evidence:** \`EditorGroupView.layout\` calls \`titleControl.layout\` for every editor-group resize; \`MultiEditorTabsControl.layout\` runs the work on the next animation frame. In the new \`layoutConnectedTabLabels\`, line 2099 removes \`connected-tab-narrow\` from all tabs; connectedEditorTabs.css:335-338 uses that class to set the icon and description to \`display: none\`. Line 2134 then reads \`offsetWidth\` for all tabs, forcing layout with those elements restored, and the following loop restores the class. \`doLayoutTabsWrapping\` immediately reads \`offsetWidth\`, \`scrollWidth\`, and potentially \`offsetHeight\` again, requiring the browser to resolve the second geometry state. The canvas LRU only caches text widths and does not avoid these DOM passes.

**Suggested direction:** Keep each tab's intrinsic minimum-width measurement cached and invalidate it only when its label, decoration, font/theme, or relevant options change. On pure container resizes, preserve the current narrow class and only update tabs whose narrow state actually changes, avoiding the expand-measure-collapse cycle before the existing layout pass.

### Scenario 1: Resize a window or drag an editor-group sash with connected Modern UI tabs, especially when tabs are compressed.

- Critical path: \`EditorGroupView.layout\` synchronously enters title/tab layout; \`MultiEditorTabsControl\` coalesces it to the next animation frame, but the full per-tab measurement must finish within that frame before the resized editor UI settles.
- Scaling input: Open tabs per editor group, number of visible editor groups, and resize/sash-drag animation frames; realistic pressure cases in the added tests use ten tabs, while real sessions can have many more.
- Effective concurrency: One tab-layout task per control per animation frame; editor groups are laid out by the workbench layout flow, with no worker offload or additional backpressure beyond animation-frame coalescing.
- Cache behavior: Canvas text widths use a 256-entry LRU keyed by font, letter spacing, and text, so warm layouts avoid repeated \`measureText\` calls. The cache does not cover per-tab \`getComputedStyle\`, geometry-changing class resets, CSS custom-property writes, or \`offsetWidth\`/\`offsetTop\` reads, so the reported browser work repeats on warm layouts.
- Mechanism confidence: High: the changed class directly controls \`display\`, it is removed before an \`offsetWidth\` read and restored before existing geometry reads, and the resize call path is explicit.
- Magnitude uncertainty: Exact frame cost depends on platform, zoom, theme CSS complexity, number of groups, and open-tab count; the repeated two-state layout mechanism is definite, while whether a given machine drops frames is workload-dependent.
- Expensive boundaries: none found
- Verdict: Reportable regression: the diff adds collection-wide style/geometry work and a repeated expand-measure-collapse cycle on every frame-coalesced layout.

- Verdict: No finding: color changes and one theming rule do not establish a new scaling or boundary cost beyond normal theme restyling.
