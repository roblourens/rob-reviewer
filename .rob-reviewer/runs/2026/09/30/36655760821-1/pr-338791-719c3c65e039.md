### Scenario 1: First external-session discovery result for Copilot, Claude, or Codex during early migration-enabled startup or deferred post-startup discovery

- Critical path: The existing provider catalog enumeration and per-session classification must finish before the new first-result marker is recorded. Candidate batches are synchronously emitted first; telemetry is synchronously enqueued afterward but no telemetry flush is awaited. In the normal external-session path discovery starts only after startup settles, so this work is off the host startup critical path; legacy migration enablement can start it earlier.
- Scaling input: Provider catalog size. Copilot classifies in batches of 250 with limiters of 4; Claude classifies its listed catalog with concurrency 4; Codex reads up to 50 catalog pages and maps top-level threads. The added count is one linear pass over only the first result's emitted candidates (or constant-time lengths for Claude), after existing classification.
- Effective concurrency: Copilot discovery is serialized by a Sequencer and uses per-stage limiters of 4. Claude has one cached discovery promise and a limiter of 4. Codex coalesces scans through CodexChatDiscovery and \_codexChatList, with metadata caching and scheduled invalidation. Providers may run independently.
- Cache behavior: Copilot's discovered-signature map suppresses unchanged emissions; Codex coalesces an in-flight list and reuses keyed metadata while its watcher/safety refresh controls rescans; Claude's successful discovery promise prevents repeat startup scans. The first-result milestone is normalized and retained once per provider bucket, including when telemetry is disabled, so warm passes neither recount nor replay it.
- Mechanism confidence: High: provider call paths, batching, coalescing, and the one-shot isPending guard are explicit in the changed and surrounding code.
- Magnitude uncertainty: Exact catalog sizes and telemetry enqueue duration vary, but the added work is one bounded marker plus a single linear count over already-loaded first-result candidates, not another enumeration or metadata read.
- Expensive boundaries:

### Scenario 2: Host registration of provider discovery batches and subsequent external-session publication

- Critical path: After the existing per-provider promise queue and any forced migration, registration awaits three registry snapshots and existing per-candidate registration/catalog synchronization. The new timing wraps that same work. Session-list publication reconciliation is scheduled with awaitReconciliation=false and remains off the measured registration critical path.
- Scaling input: Received batch size after provider deduplication: Copilot batches are at most 250; Claude emits unknown chats in one batch (including an existing empty batch); Codex emits only changed chats. Added metrics perform one external-flag reduction and constant-time counter increments during existing candidate processing while an operation attempt or first successful milestone is pending.
- Effective concurrency: Batches are strictly serialized per provider by \_providerDiscoveryRegistrations; different providers can progress independently. Candidate registration remains limited to 4 within each batch. The diff adds no parallel database work or aggregate burst.
- Cache behavior: Registry snapshots and provider deduplication remain authoritative. Timing stops after the first success or three attempts; first-success accounting remains pending through partial/error attempts, then is consumed once. With telemetry disabled the operation and milestone are consumed without metric aggregation or later replay; after a warm successful observation, later batches skip all added aggregation.
- Mechanism confidence: High: the event listener's promise chain proves per-provider serialization, the existing Limiter proves candidate concurrency 4, and operation/milestone state proves bounded telemetry cardinality.
- Magnitude uncertainty: Database cost and batch size vary by catalog, but those boundaries are pre-existing. Added CPU is linear only in already-processed candidates and telemetry payload/event cardinality is fixed.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_registerDiscoveredChats</code>: Load runtime-compatible keys, modified times, and provider exclusions, then perform existing per-candidate registry/catalog reads and writes plus batch post-processing writes; cardinality: Three parallel snapshots per emitted batch; per-candidate work scales with effective batch size at concurrency 4, with existing batched post-processing writes
    - Introduced by diff: false; previous behavior: The identical snapshot, registration, synchronization, and post-processing boundaries already ran for every discovery batch.; critical-path effect: These existing operations determine registration latency; the diff only records counters around them
  - network at <code>src/vs/platform/agentHost/node/agentHostStartupPerformance.ts:AgentHostStartupPerformance.\_report</code>: Queue registration start/end markers and the first-success milestone through publicLog2; cardinality: Normally three small events on first successful registration; at most three start/end attempt pairs plus one eventual first-success event per normalized provider (seven total), and none without consent
    - Introduced by diff: true; previous behavior: Registration did not emit these telemetry markers.; critical-path effect: Events are synchronously enqueued but never flushed or awaited; publication reconciliation is still merely scheduled
- Verdict: No reportable regression. The PR neither fans out expensive boundaries nor moves publication onto the critical path; its added allocation, counters, and telemetry calls are bounded and disabled after observation.

**Summary:** Completed the performance pass over all 14 changed files and relevant provider/registration call paths. No high-confidence performance regression was introduced, and the PR does not itself fix a concrete prior performance regression requiring blame attribution.
