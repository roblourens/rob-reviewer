# Performance review: sessions: Show per-chat state in the sessions list

[PR #338786](https://github.com/microsoft/vscode/pull/338786) at `8711cbc262e905c162ae10f005d1b3c73d174cd7`

## Findings (1)

### 1. [medium] Keep single-chat rows on summary-backed metadata

**Finding ID:** `PERF-2986F9629524`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:296</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** one live Agent Host session-state IPC subscription plus restored per-session state/database objects for each distinct rendered row  
**Scaling:** Cold work grows with the number of distinct Agent Host session rows rendered while opening or scrolling the Sessions list; subscriptions are coalesced per session across fields, but unique rows remain retained for the 30-second idle window, so fast scrolling can exceed viewport cardinality.  
**Outcome:** excessive IPC, Agent Host restore/database I/O, process CPU and retained memory, with degraded Sessions-list responsiveness  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The row read \`session.updatedAt\` and \`session.description\`, which the provider projects from the verified listing payload without opening the per-session database or subscribing to each session URI.  
**Changed behavior:** The row now selects \`mainChat.updatedAt\` for every single-chat session (and main-chat description/read state on the same scope). This PR also wraps those main-chat observables in \`\_withChatDetails\`, whose first observer calls \`\_ensureSessionStateSubscription\` and \`connection.getSubscription(StateComponents.Session, ...)\`.  
**Confidence:** 0.97 — The changed observer, provider wrapper, reference collection, IPC subscription call, 30-second retention, and prior payload-only listing path are all directly traced in code. Exact user counts and restore duration are uncertain, which limits severity, but the per-unique-row fan-out mechanism is deterministic.

**Causal diff evidence:** The diff replaces the prior \`element.updatedAt.read(reader)\` row read with \`getSessionRowUpdatedAt(...)\`, whose added RIGHT line 296 reads \`session.mainChat.updatedAt\`; in the same diff, \`mainChat.updatedAt\` changes from the summary observable to \`\_withChatDetails(defaultChatUpdatedAt)\`. Thus the list newly crosses the session-subscription boundary for each single-chat row, whereas it did not before.

Opening or scrolling a history containing many Agent Host sessions now creates a burst of per-session subscriptions and can restore every encountered session even though the user only asked to view the summary list. Each row leaves its underlying subscription alive for 30 seconds after recycling, so scrolling through dozens of rows can keep dozens of restored sessions live.

**Evidence:** \`isSessionRowMainChatScoped\` returns true whenever \`session.chats.length &lt;= 1\`, independent of collapse state, and line 296 observes \`mainChat.updatedAt\` from the ordinary session-row renderer and accessibility label. In \`AgentHostSessionAdapter\`, this PR changes \`mainChat.updatedAt\`, \`isRead\`, and \`description\` to \`\_withChatDetails(...)\`; \`\_withChatDetails\` acquires \`\_sessionChatDetailsReferences\`, whose first reference calls \`\_ensureSessionStateSubscription\`. That method issues \`connection.getSubscription(StateComponents.Session, ...)\`, and its own comment notes that subscribing can trigger Agent Host restore; the provider documentation states listing payload projection otherwise avoids opening each per-session database.

**Suggested direction:** For single-chat and collapsed rows, continue rendering summary-backed session fields (\`session.updatedAt\`, \`session.description\`, and \`session.isRead\`), which are equivalent to the only chat without requiring hydration. Acquire chat-detail observables only for an explicitly expanded multi-chat session (or add the default-chat timestamp to summary metadata if it can genuinely differ).

### Scenario 2: Open an unread main or peer chat

- Scaling input: One selected chat per user navigation; aggregate-read evaluation scans the chats in the active session.
- Effective concurrency: No collection burst from one open. Agent Host mutates multi-chat local read state synchronously; providers with remote chat-scoped read APIs may have one request in flight, followed by one session-level request only when the final unread chat is cleared.
- Cache behavior: Read state is observable provider state rather than a cache. Agent Host local overrides persist until newer protocol activity or an explicit protocol read transition; no repeated cold lookup is introduced.
- Mechanism confidence: High for call count and non-blocking placement; transport cost varies by provider.
- Magnitude uncertainty: Provider implementations may use IPC or network transport, but the changed cardinality is bounded to explicit navigation.
- Expensive boundaries:
  - network at <code>src/vs/sessions/services/sessions/browser/sessionsManagementService.ts:markChatRead and markRead</code>: Optional provider \`setChatReadState\`, and \`setSessionReadState\` when aggregate unread clears; cardinality: At most one chat-scoped call per navigation plus one session-scoped call when that navigation clears the final unread chat; Agent Host multi-chat marking is local and only the aggregate session update crosses its protocol boundary.
    - Introduced by diff: true; previous behavior: Opening an unread active session made one session-level read-state call and had no chat-scoped operation.; critical-path effect: Calls are fire-and-report-error on navigation and do not block opening the chat.
- Verdict: No report: the extra operation is bounded to an explicit open, preserves chat-scoped semantics, and does not fan out with session history.

### Scenario 4: Render expanded peer-chat rows with activity, markdown, unread state, and relative time

- Cache behavior: No cross-row cache is added. Row disposal clears timers and rendered markdown; the associated session-detail subscription is coalesced per owning session.
- Mechanism confidence: High from renderer ownership and element-disposable cleanup.
- Magnitude uncertainty: Large viewports and unusually dense expanded sessions increase visible-row count, but the work remains viewport-bounded and minute-cadenced.
- Expensive boundaries: none found
