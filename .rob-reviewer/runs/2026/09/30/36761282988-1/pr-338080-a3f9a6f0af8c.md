# Performance review: \[4/4\] authentication: enable multiple configured enterprise hosts

[PR #338080](https://github.com/microsoft/vscode/pull/338080) at `a3f9a6f0af8ccbe91872208fee714c2c471dc081`

## Findings (1)

### 1. [medium] Register hosts before restoring every brokered session

**Finding ID:** `PERF-C4683F28A784`  
**Location:** <code>extensions/github-authentication/src/githubEnterprise.ts:87</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Microsoft authentication IPC calls and GitHub token-exchange/user-info network requests  
**Scaling:** On a cold window, work grows with the total remembered Microsoft-linked accounts across all newly configured hosts: each missing linked account performs Microsoft account/token lookups plus a GitHub token-exchange POST and user-info GET, while the outer Promise.all fans this out across hosts and waits for the slowest request.  
**Outcome:** Enterprise authentication provider registration and extension activation are blocked by the slowest configured host, with a concurrent network burst and potentially long startup/authentication latency when any secondary host is slow or unreachable.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Before this change, initialization could configure only one enterprise host, so at most that host's linked accounts were restored before registration; an unrelated secondary host could not add requests or hold the provider registration barrier open.  
**Changed behavior:** The new multi-host initialization calls the full restoring getSessions path for every newly created host in parallel and does not commit/register the provider until all calls complete.  
**Confidence:** 0.98 — The changed critical path and boundary calls are directly traced in production code, and brokered sessions are explicitly transient while account links persist, making cold-window restoration repeatable. The number of users with multiple linked enterprise accounts is uncertain, which limits severity rather than confidence in the mechanism.

**Causal diff evidence:** Added line 87 changes startup from one awaited host engine to \`Promise.all\` over every \`created\` host and places all of their restoring session reads before \`commitHosts\`/provider registration.

After a reload with multiple configured GHE.com hosts and remembered Microsoft-brokered accounts, opening or using enterprise authentication waits for restoration on every host. One unreachable secondary host can therefore delay all otherwise usable enterprise accounts, while N hosts/accounts issue token-acquisition and GitHub exchange requests concurrently.

**Evidence:** \`applyConfiguration\` awaits \`Promise.all(created.map(host =&gt; host.engine.getSessions(...)))\` before \`commitHosts\` registers the provider. \`GitHubSessionEngine.getSessions\` calls \`restore\`; with a fresh engine, brokered sessions are absent because they are process-only, so each persisted account link enters \`restoreOne\`. \`restoreNow\` calls Microsoft account discovery and \`renewWithMicrosoft\`; \`EntraTokenExchange.renew\` silently acquires a Microsoft token, POSTs the token exchange, then GETs \`/user\` to verify identity. The engine coalesces only the same account/scope key, and the provider adds an outer all-host Promise.all, so distinct host/account work is neither bounded nor removed from the registration critical path.

**Suggested direction:** Commit/register hosts from \`getCachedSessions()\` first, then restore brokered sessions after registration with bounded concurrency and forward the resulting session events; at minimum, avoid making one host's restoration a barrier for all hosts.

### Scenario 1: Cold extension activation or configuration refresh with multiple enterprise hosts

- Scaling input: H distinct configured hosts after URI-key deduplication, S machine secret keys scanned by migration, and L total remembered Microsoft-linked accounts lacking process-local sessions across those hosts.
- Effective concurrency: Host migrations run serially. Engine initialization then uses an outer \`Promise.all\` across hosts; each engine uses another \`Promise.all\` across missing linked accounts, with only same host/account/scope requests coalesced and no aggregate limiter.
- Cache behavior: Canonical persisted sessions are read once per engine and then cached. Microsoft-brokered sessions are intentionally process-only, so every cold window starts with misses; successful restores populate transient sessions, failed restore keys are negatively cached only for that engine lifetime, and concurrent identical restores coalesce.

### Scenario 2: Routine enterprise session enumeration for account menus and extension authentication requests

- Critical path: A request without account or issuer hints awaits every configured host; issuer/account-resolved requests use one host. Persisted and already-restored sessions are local after engine initialization, while an unresolved cold brokered link performs restoration before the request returns.
- Scaling input: H configured hosts, sessions per host, and any linked accounts not already represented by a matching session; URI keys deduplicate equivalent configured entries.
- Effective concurrency: Unresolved requests use \`Promise.all\` across hosts. Per-engine renewals/restores coalesce by session or account/scope key, but distinct hosts/accounts run concurrently without a shared limiter. Ext-host provider operations serialize calls for the provider.
- Cache behavior: Persisted-session promises and transient sessions make normal warm enumeration local. Restore failures are negatively cached for the engine lifetime and successes suppress later restoration for that account/scope. A window reload clears transient/negative caches.
- Mechanism confidence: High for routing and cache behavior.
- Magnitude uncertainty: Most warm reads perform no network work; frequency depends on callers and brokered-session use.
- Expensive boundaries:
  - network at <code>extensions/github-authentication/src/github.ts:getSessions, stillGood, restore</code>: Renew or restore Microsoft-brokered GitHub sessions when no matching warm session exists; cardinality: Zero on the normal warm persisted path; on misses, one renewal flow per distinct stale session or missing account/scope key after coalescing.
    - Introduced by diff: true; previous behavior: Broad enterprise enumeration reached only the one configured host.; critical-path effect: Requests requiring the missing session await renewal/restoration; broad unhinted enumeration can await all hosts.
- Verdict: The cold all-host cost is covered by the activation finding. Warm fan-out is predominantly local and returning all configured hosts is required, so no additional finding.

### Scenario 3: Interactive enterprise sign-in and session removal

- Critical path: Sign-in resolves an issuer/account hint or waits for the native host picker, then only the selected host's interactive login/token/user-info path runs. Removal scans already-loaded host caches, then logs out and updates credentials on the single owning host.
- Scaling input: H configured hosts for local ownership scans; one selected host and one session for interactive boundary work. Ambiguous native IDs stop before logout.
- Effective concurrency: Host ownership cache checks are sequential for removal/account resolution but are local after initialization. Interactive authentication and logout target one engine; no per-host network fan-out is introduced.
- Cache behavior: Host ownership uses each engine's persisted/transient cache. Sign-in writes one host's canonical secret, and secret-change listeners may trigger additional per-engine cache reads, but token changes are infrequent and the added cost is not independently significant enough to report.
- Mechanism confidence: High.
- Magnitude uncertainty: The number of configured hosts affects only cheap local scans here; sign-in/removal frequency is user-driven and low.
- Expensive boundaries:
  - network at <code>extensions/github-authentication/src/githubEnterprise.ts:createSession/removeSession -&gt; GitHubSessionEngine</code>: Selected-host OAuth/Microsoft sign-in, user lookup, or logout; cardinality: One selected/owning host per operation.

  - IPC at <code>extensions/github-authentication/src/common/keychain.ts</code>: Read/write the selected host's secret storage entry; cardinality: One canonical entry for the selected host, with extension-wide change notifications causing low-frequency cache reconciliation.
    - Introduced by diff: false; previous behavior: Credential persistence and reconciliation already occurred for the single enterprise engine.; critical-path effect: Credential persistence is awaited; unrelated-host reconciliation is off the direct interactive return path.
- Verdict: No separate performance regression: expensive work remains constrained to one selected/owning host.
