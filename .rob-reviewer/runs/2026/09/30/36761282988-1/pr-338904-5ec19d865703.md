## Findings (1)

### 1. [medium] Cache PR labels before the synchronous find loop

**Finding ID:** `PERF-515E7B38629C`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:359</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU regex/URI serialization work and short-lived arrays, strings, and parsed PR objects.  
**Scaling:** For every typed character or edited query, cost grows as O(searchable sessions × (workspace PR refs + session artifacts)); active find removes the normal per-group cap, and there is no cold/warm distinction because labels are rebuilt on every lookup.  
**Outcome:** Increased synchronous input latency and CPU/GC pressure during session filtering.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each candidate lookup returned \`element.title.get()\` directly, so a refilter performed only title fuzzy matching and did not walk folders/artifacts, serialize URIs, run PR regexes, or allocate a label array per session.  
**Changed behavior:** Each label lookup now reconstructs all searchable labels from mutable session metadata and parses every GitHub pull-request artifact instead of returning the already-stored title string.  
**Confidence:** 0.96 — \`FindController.applyPattern\` synchronously refilters on each input, \`FindFilter.filter\` invokes the label provider once per candidate node, and the sessions list explicitly removes per-group caps while a find pattern is active. The exact history size varies by user, which affects severity, but the synchronous repeated mechanism and scaling are directly traced.

**Causal diff evidence:** RIGHT lines 347-366 add a helper that rebuilds an array, walks every folder/PR and artifact, serializes artifact URIs, and regex-parses PR URLs; RIGHT line 3838 replaces the prior \`element.title.get()\` label with this helper on the tree label-provider path.

Typing in Sessions Find can become progressively laggy and create CPU/GC pressure for users with a large session history or artifact-heavy sessions; ordinary title searches pay the PR extraction cost even when the query contains no PR number.

**Evidence:** The new helper creates \`labels\` and \`\#number\` strings on every invocation, calls \`getGitHubPullRequestRefs\` for each folder (which additionally allocates a legacy ref object/array), and calls \`artifact.link.toString(true)\` plus \`parseGitHubPullRequestUrl\` for each eligible artifact. \`abstractTree.ts\` invokes this provider from \`FindFilter.filter\`, and \`FindController.applyPattern\` calls \`tree.refilter()\` for every input value. \`sessionsList.ts\` also sets \`hasFindPattern\` and rebuilds the tree without workspace/group limits once text is entered, so the work covers the full searchable history rather than the usual five-item capped groups.

**Suggested direction:** Memoize the derived label array per session (for example with a WeakMap-backed observable/derived value) and invalidate it when title, workspace GitHub metadata, or artifacts change, so each metadata version is parsed once rather than once per keystroke while preserving live updates.
