<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** eager-work, repeated-work, serialization-allocation, boundary-fanout

### Scenario 1: Enumerating and selecting BYOK/OpenAI-compatible language models, including OpenRouter and configured custom model groups

- Critical path: \`selectLanguageModels\`/provider refresh awaits \`\_resolveAllLanguageModels\`, the extension-host provider's \`provideLanguageModelChatInformation\`, existing model discovery, and the new capability projection before models become selectable.
- Scaling input: Number of discovered models per provider, multiplied by repeated selection/refresh calls and configured groups.
- Effective concurrency: Model resolutions are sequenced per vendor by \`\_resolveLMSequencer\`; multiple vendors may resolve in parallel. The new \`Promise.all\` creates all endpoint projections in one burst, although the observed endpoint factories perform synchronous object construction and no additional I/O.
- Cache behavior: Provider model metadata may be cached internally (for example Ollama model info), but \`selectLanguageModels\` still resolves providers. The new endpoint objects are transient and not cached; no new positive/negative cache or boundary miss behavior is introduced.
- Mechanism confidence: High confidence that the diff adds one transient endpoint construction and several metadata objects/promises per discovered model; low confidence that this lightweight in-process work crosses the reporting threshold.
- Magnitude uncertainty: OpenRouter can return a broad catalogue, but repository evidence does not establish that transient endpoint construction is costly enough relative to the pre-existing network discovery and catalogue parsing to create a user-visible regression.
- Expensive boundaries:
  - network at <code>extensions/copilot/src/extension/byok/vscode-node/abstractLanguageModelChatProvider.ts:getModelsFromEndpoint</code>: GET the provider model catalogue (for providers such as OpenRouter/OpenAI/Ollama); cardinality: One catalogue request per provider/group resolution; returned model cardinality can be large for OpenRouter.
    - Introduced by diff: false; previous behavior: The same catalogue request and model metadata mapping already occurred before this change.; critical-path effect: The catalogue response is awaited before model selection or refresh completes.
  - IPC at <code>src/vs/workbench/api/browser/mainThreadLanguageModels.ts:$registerLanguageModelProvider / src/vs/workbench/api/common/extHostLanguageModels.ts:$provideLanguageModelChatInfo</code>: Request and return language-model metadata between the main thread and extension host; cardinality: One RPC round trip per provider/group resolution, carrying one metadata record per discovered model.
    - Introduced by diff: false; previous behavior: The RPC already carried the model catalogue; the diff adds two scalar capability fields without adding calls.; critical-path effect: Model selection waits for this metadata RPC.
- Verdict: No finding. The added O(model-count) allocation is avoidable eager work, but it performs no new boundary operation and available evidence does not establish concrete latency, CPU, or GC impact beyond a speculative optimization.

### Scenario 2: Sending a genuine follow-up chat turn to an opted-in Chat Completions model such as Kimi K3

- Critical path: Prompt rendering walks historical tool-call rounds, now retains same-model thinking for opted-in Chat Completions endpoints, serializes it into the existing request body, and sends the single model request; all are on response latency's critical path.
- Scaling input: Same-model historical tool/final rounds and their thinking text/opaque metadata, bounded by the prompt renderer's context budget and any summarization/compaction policy.
- Effective concurrency: Historical rounds are rendered within one prompt and serialized into one request; there is no per-round network fan-out or new request concurrency.
- Cache behavior: Replay can preserve the model-visible history/prefix for supported models; the same-model and API-type guards prevent cross-model or unknown-protocol replay. Cold and warm requests have the same request count; any provider prompt-cache benefit depends on the remote service.
- Mechanism confidence: High confidence that payload bytes and serialization work increase in proportion to retained reasoning; high confidence this is the direct, required behavior of preserving reasoning rather than an accidental extra pass or duplicate boundary call.
- Magnitude uncertainty: Reasoning can materially enlarge long-history payloads, especially for custom endpoints whose existing serializer emits compatibility aliases, but exact history sizes, provider compression, token accounting, and cache effects are not established here.
- Expensive boundaries:
  - network at <code>extensions/copilot/src/extension/prompts/node/panel/toolCalling.tsx:ChatToolCalls.renderOneToolCallRound -&gt; endpoint request serialization</code>: Send the chat-completions request containing conversation history and replayable historical thinking; cardinality: One network request per user turn; no extra calls are introduced. Payload size grows with the effective number and byte size of same-model historical thinking rounds that survive prompt rendering/summarization.
    - Introduced by diff: false; previous behavior: The same one request was sent, but historical Chat Completions thinking was omitted while assistant/tool history remained.; critical-path effect: The request payload must be rendered, serialized, uploaded, and processed before the follow-up response streams.
- Verdict: No finding. The larger payload is the feature's required semantic data, is gated to compatible/same-model history, and the diff neither adds network calls nor establishes an avoidable unbounded copy independent of that requirement.

### Scenario 3: Registering provider protocol/adaptive-thinking metadata and selecting extension-contributed models across the proposed VS Code API

- Critical path: Provider metadata is converted in the extension host, transferred over the existing provider RPC, cached in the workbench, then converted back into the selected \`LanguageModelChat\` API object before Copilot constructs its endpoint.
- Scaling input: Number of model metadata records returned by a provider.
- Effective concurrency: Conversion is synchronous per model inside the existing catalogue map; provider resolutions retain existing per-vendor sequencing.
- Cache behavior: Selected models remain in \`\_localModels\`/workbench model caches under existing invalidation rules; the new scalar fields do not create a separate cache or alter cache lifetime.
- Mechanism confidence: High confidence in the call path and unchanged RPC cardinality.
- Magnitude uncertainty: Only a few bytes and constant-time enum/object mapping are added per model; no evidence indicates measurable transport or allocation impact.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/common/extHostLanguageModels.ts:$provideLanguageModelChatInfo</code>: Transfer language-model metadata through the existing extension-host/main-thread language-model provider bridge; cardinality: One existing RPC response per provider resolution with two additional scalar fields per model.
    - Introduced by diff: false; previous behavior: The metadata record crossed the same RPC without \`apiType\` and \`adaptiveThinking\`.; critical-path effect: Selection waits for metadata transport, but no additional round trip is introduced.
- Verdict: No finding. This is bounded metadata enrichment on an existing transport, not a new expensive boundary or materially amplified serialization path.
