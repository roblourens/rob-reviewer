# Performance review: agentHost: Retract orphaned provisional sessions

## Findings (1)

### 1. [medium] Collapse affected providers into one catalog refresh

**Finding ID:** `PERF-1FFBD56365E5`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:1045</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SQLite operations, provider metadata calls, session-database accesses, decoded catalog objects, and CPU for full-catalog processing  
**Scaling:** For A affected readable providers and N registered sessions, the callback performs A serialized full-catalog computations rather than one; catalog read/decoding grows as O(A\*N), and provider checks for Q provisional rows can grow as O(A\*Q), with additional per-session fallback opens on catalog misses.  
**Outcome:** Excessive I/O and increased latency for publishing removals and other work serialized behind session-list reconciliation  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Retroactive provisional marking only mirrored each marker and invalidated the next session-list computation; it did not force a session-list recomputation for each provider after the run.  
**Changed behavior:** After one reconciliation run batches all newly provisional session keys, the added loop queues a separate published-list refresh for every affected readable provider.  
**Confidence:** 0.96 — The changed loop, serial queue, unconditional invalidation, and full-list storage/provider call path are explicit in the code. The exact duration and prevalence of multi-provider orphan batches vary, but the multiplicative boundary work is deterministic whenever at least two readable providers are affected.

**Causal diff evidence:** The added \`for (const provider of readableProviders) { this.\_queuePublishedSessionListRefresh(provider); }\` at RIGHT line 1045 introduces one forced refresh per provider after the batch; no corresponding forced refresh existed in this callback before the diff.

When one pass discovers orphaned sessions for multiple providers, removal publication for later providers is delayed behind repeated whole-catalog scans, while the agent host repeats SQLite and provider/session-storage work and can contend with normal session listing.

**Evidence:** \`readableProviders\` already deduplicates sessions by provider, but line 1045 invokes \`\_queuePublishedSessionListRefresh\` once for each provider. Each queued task is serialized through \`\_sessionListReconciliation\`; \`\_refreshPublishedSessionList\` invalidates the list and calls \`listSessions()\`. That starts \`\_computeSessions\`, which calls \`\_listRegisteredSessions()\` (SQLite registration scan), \`\_catalogListReader.readMany(catalogCandidates)\` (bulk SQLite catalog read over all registered candidates), and \`\_withoutUnmaterializedProvisionalSessions\`, which invokes provider \`getChatMetadata\` for provisional rows and may use per-session fallback storage. Because each task invalidates before listing and settled list computations are not cached, work from the first provider cannot serve the next.

**Suggested direction:** Queue one batched refresh with the full affected-provider set: await marker loading once, collect the exposed affected sessions, invalidate and compute \`listSessions()\` once, then retract hidden sessions across all affected providers from that single visible-key set.

### Scenario 3: A single readable provider has retroactively marked orphan sessions and one or more of those rows were published by an earlier listing.

- Critical path: After background reconciliation, one serialized refresh waits for marker loading, computes one fresh session list, and emits removals. This delays removal notification but does not block initial startup.
- Scaling input: One affected provider, N registered sessions, Q provisional rows, and M exposed newly hidden rows.
- Effective concurrency: Exactly one new refresh is queued for the provider. Catalog fallback work is limited to 4; provisional metadata checks retain the existing listing concurrency behavior.
- Cache behavior: The refresh deliberately invalidates and recomputes once. A concurrent in-flight list can hand off to a trailing computation at the new epoch, so callers coalesce around that work. Cold storage/provider reads cost more; warm catalog data still requires the query and decode.
- Mechanism confidence: High: the test and call path establish the published-row race and one refresh.
- Magnitude uncertainty: Absolute latency depends on catalog size, catalog eligibility, and provider speed. With one provider, one proactive recomputation is necessary to preserve the intended notification semantics and is not independently reported.
