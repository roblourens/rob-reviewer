# Performance review: Add opt-in merging of document highlight providers

## Findings (1)

### 1. [medium] Keep the editor merge setting out of the API command

**Finding ID:** `PERF-89F69CEFA678`  
**Location:** <code>src/vs/editor/contrib/wordHighlighter/browser/wordHighlighter.ts:230</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** main-thread-to-extension-host IPC calls and downstream language-provider/language-server requests  
**Scaling:** For each vscode.executeDocumentHighlights invocation, work grows from providers queried only until the first non-null answer (normally one) to all P matching non-textual providers concurrently; repeated command calls multiply this by the call frequency.  
**Outcome:** Increased command latency to the slowest provider plus avoidable IPC, extension-host CPU, and language-server load.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The command called getOccurrencesAtPosition without merge mode, whose first(...) loop stopped as soon as the highest-priority provider returned a non-null result.  
**Changed behavior:** The command now reads editor.occurrencesHighlightFromAllProviders and passes it into getOccurrencesAtPosition; when enabled, that helper uses Promise.all over every matching provider.  
**Confidence:** 0.96 — The changed command call, Promise.all fan-out, per-provider RPC bridge, tsserver request, absence of cancellation, and before/after short-circuit behavior are all directly traced. Only prevalence is uncertain because the option is opt-in and requires an API-command caller plus multiple matching providers; that limits severity, not mechanism confidence.

**Causal diff evidence:** RIGHT line 230 newly passes mergeProviders into the API command's getOccurrencesAtPosition call; this is the exact switch from the pre-diff first-success path to the added all-provider Promise.all path.

When a user enables the editor-only merge option and an extension invokes vscode.executeDocumentHighlights, each invocation now starts all matching providers and waits for the slowest. With overlapping language extensions, command-driven navigation or analysis becomes slower and can burst multiple extension-host/language-server requests even though the API command previously needed only the first successful answer.

**Evidence:** The added command argument at line 230 reaches the new Promise.all provider loop at lines 48-55. Extension providers cross one $provideDocumentHighlights RPC per registration in mainThreadLanguageFeatures.ts:327-330, and the built-in TypeScript provider then issues a documentHighlights request to tsserver in extensions/typescript-language-features/src/languageFeatures/documentHighlight.ts:63. The command supplies CancellationToken.None, so this non-UI API path has no cancellation and cannot complete until every provider settles.

**Suggested direction:** Keep \_executeDocumentHighlights on the existing first-answer behavior (pass false) and apply the setting only in WordHighlighter; if API callers need merged results, expose that as an explicit cancellable API choice rather than inheriting a global editor option.
