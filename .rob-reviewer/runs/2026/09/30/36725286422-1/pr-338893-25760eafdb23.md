# Performance review: Don't cache prompt discovery results from a cancelled scan

[PR #338893](https://github.com/microsoft/vscode/pull/338893) at `25760eafdb2305e4ecf8c7815bb75254db14d94f`

## Findings

No high-confidence performance findings.

<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** cache-lifecycle, repeated-work, boundary-fanout, concurrency-burst

### Scenario 1: Cold prompt-file discovery for one prompt type, including cancellation during an extension provider

- Critical path: listPromptFiles awaits computeListPromptFiles, which awaits all five source branches; extension discovery waits for extension registration, activation, and sequential provider callbacks, while standalone discovery waits for local/user filesystem search. The new token check runs only after all branches settle and is therefore on the critical path, but it is a constant-time read.
- Scaling input: Configured prompt source locations, workspace roots, and registered providers for one prompt type. Cancellation does not add a boundary call; a later explicit request starts one fresh discovery after the canceled result is rejected.
- Effective concurrency: The five source branches run under one Promise.all. Local and user scans can overlap; providers remain sequential after one activation. The per-type promise cache coalesces concurrent callers when a file-locator event has initialized caching; rejection clears only that same promise.
- Cache behavior: Warm successful results remain unchanged. On a cold canceled scan, the added guard rejects instead of admitting a partial positive/empty result; the existing catch evicts that rejected promise. The next request performs a fresh scan and can then become the warm cached result. No negative cache or retry loop is introduced.
- Mechanism confidence: High: the changed guard, surrounding Promise.all, cache assignment, identity-checked eviction, provider loop, and filesystem cancellation behavior were directly traced.
- Magnitude uncertainty: Filesystem and activation duration vary with workspace layout and extensions, but the added work itself is one token-state read and one exception only when the initiating scan was canceled.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/common/promptSyntax/utils/promptFilesLocator.ts:listFilesWithSource</code>: Resolve or search configured local and user prompt locations and enumerate matching files.; cardinality: Two top-level branches per uncached prompt type (local and user), with configured locations processed sequentially inside each branch; effective calls scale with deduplicated configured source locations and workspace roots.
    - Introduced by diff: false; previous behavior: The same local and user scans ran with the same cardinality and parallel placement before the diff.; critical-path effect: Both branches must finish before the combined discovery result can be returned. Cancellation is already surfaced from these branches after each location.
  - IPC at <code>src/vs/workbench/contrib/chat/common/promptSyntax/service/extensionPromptFileService.ts:getExtensionPromptFiles/\_listFromProviders</code>: Wait for extension registration, activate extensions for the prompt-type activation event, and invoke each registered prompt-file provider.; cardinality: One activation event per uncached type discovery, then one callback per provider of that type, sequentially; in the strict-plugin-only test there is one provider and zero standalone filesystem branches.
    - Introduced by diff: false; previous behavior: The identical activation and provider calls ran before the diff, but a normally resolved partial provider result could pass through to cache admission.; critical-path effect: Provider activation/callbacks are awaited by the extension branch and the combined Promise.all. A provider may observe cancellation and return normally, which is the condition handled by the added guard.
- Verdict: No reportable regression. The diff adds no expensive boundary or fan-out and prevents a canceled partial result from entering the cache. Re-execution occurs only after cancellation and a subsequent request, preserving intentional cancellation semantics.

### Scenario 2: Warm or concurrent prompt discovery consumers, including all-type commands and customization migration

- Critical path: A warm per-type call returns the cached promise before computeListPromptFiles, so it never reaches the new check. Cold calls for different types can run concurrently in all-type consumers; same-type callers share the existing promise when caching is active.
- Scaling input: Number of distinct prompt types requested concurrently, configured locations, and providers. Same-type concurrency is coalesced by the existing cache; cross-type work remains independent.
- Effective concurrency: All-type consumers use Promise.all across up to five types. Within each type, source branches overlap and providers serialize. The diff does not create an aggregate concurrency burst.
- Cache behavior: Warm cache hits return before the new line. Successful cold cache population is unchanged. If the token owning a shared cold computation is canceled, all sharers already observe that shared computation's outcome; the new behavior rejects and evicts rather than preserving a partial result, after which a later call may retry once.
- Mechanism confidence: High: callers using Promise.all, the early cache return, per-type cache key, and changed post-computation guard were inspected directly.
- Magnitude uncertainty: The frequency of concurrent canceled and uncanceled consumers is unknown, but no automatic retry or newly introduced boundary exists.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts:computeListPromptFiles</code>: Discover local/user files for each cold prompt type requested by the consumer.; cardinality: At most two top-level standalone discovery branches per cold type; all-type consumers may request five distinct types concurrently, exactly as before. Warm per-type calls add no scans.
    - Introduced by diff: false; previous behavior: The same per-type branch count and cross-type concurrency existed before the diff.; critical-path effect: Cold consumers await discovery; warm consumers await or receive the cached promise. The token check does not affect uncanceled completion.
  - IPC at <code>src/vs/workbench/contrib/chat/common/promptSyntax/service/extensionPromptFileService.ts:\_listFromProviders</code>: Activate and query prompt-file providers for agent, instructions, prompt, and skill types; hooks have no provider activation event.; cardinality: One activation event per cold supported type and sequential calls to providers registered for that type; warm results avoid these calls.
    - Introduced by diff: false; previous behavior: Identical provider cardinality, ordering, and cache coalescing.; critical-path effect: Cold discovery waits for activation/providers. The diff neither adds nor reorders these operations.
- Verdict: No reportable regression. The change does not alter warm-path work, normal cold-path cardinality, or concurrency; only canceled incomplete computations are denied cache admission.

**Summary:** Completed the performance pass over both changed files and the surrounding cache, provider, filesystem, built-in, and caller paths. The added post-computation cancellation check is constant-time and routes canceled partial discovery through the existing identity-checked cache eviction. It introduces no boundary work, retention, fan-out, or hot-path repetition. No performance findings and no qualifying performance regression fix were identified.
