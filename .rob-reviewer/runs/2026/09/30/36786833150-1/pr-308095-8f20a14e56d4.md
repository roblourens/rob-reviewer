### 1. [high] Avoid uncached full-workspace searches for \`\#\` completions

**Finding ID:** `PERF-C0D5DBCCF25B`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/variableCompletions.ts:254</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Filesystem enumeration/search-process CPU plus arrays and completion objects for up to 20,000 file results and derived folders.  
**Scaling:** Cost is O(F) filesystem enumeration plus scoring/allocation for workspace file count F on bare \`\#\`, multiplied by the number of typed completion prefixes because no cache key is reused.  
**Outcome:** Blocked completion latency with repeated I/O, CPU, and GC pressure while typing.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, typing \`\#\` in the sessions new-chat editor did not start file search. The existing workbench chat completion implementation shows history for an empty pattern and, once a pattern exists, reuses a search cache key across prefixes.  
**Changed behavior:** The new completion provider always calls searchFilesAndFolders, including for a bare \`\#\`, and passes no cache key; because its list is marked incomplete, subsequent typed characters invoke the provider again.  
**Confidence:** 0.99 — The changed call, empty-pattern expansion, absence of a result bound/cache key, sorted-search implementation, and incomplete-provider re-trigger path are all directly traced. Exact wall time varies with repository size and filesystem speed, but the full-scan and per-prefix multiplicity are deterministic.

**Causal diff evidence:** Added line 254 invokes \`searchFilesAndFolders(workspaceUri, pattern \|\| '', ..., undefined, ...)\`, newly placing an empty, uncached workspace search on the \`\#\` completion path.

In a large local or vscode-remote repository, merely typing \`\#\` can scan and score the whole workspace before suggestions appear; continuing to type repeats the scan, causing delayed completions, high filesystem/search-process CPU, and allocation/GC pressure during normal input.

**Evidence:** At line 254, \`pattern \|\| ''\` turns bare \`\#\` into an empty fuzzy search and the \`undefined\` cache key disables search reuse. \`searchFilesAndFolders\` converts the empty pattern to \`\*\`, sets \`sortByScore: true\`, and specifies no \`maxResults\`; the raw search path walks all candidates before selecting up to the 20,000-result default. \`result.incomplete = true\` at line 158 causes SuggestModel to re-trigger incomplete providers as the cursor advances, so each prefix starts another uncached filesystem/search-provider traversal. The core chat analogue guards the search with \`if (pattern)\` and supplies \`updateCacheKey().key\`.

**Suggested direction:** Match the existing chat provider: return history-only suggestions for an empty pattern, keep a short-lived per-handler search cache key for non-empty prefixes and clear it on disposal/expiry, and set an explicit completion-sized result bound.

### 2. [high] Bound virtual-workspace traversal independently of matches

**Finding ID:** `PERF-F05837D35AC0`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/variableCompletions.ts:295</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** One cold recursive-tree network response, D serial file-service resolves, and repeated renderer-thread scans over F cached tree entries.  
**Scaling:** For a query with fewer than 100 matches, resolves scale with all reachable directories D (depth at most 10); in \`github-remote-file\`, warm CPU work scales as O(D×F) because each \`readdir\` scans the F-entry tree map.  
**Outcome:** Severe completion latency and renderer CPU blocking, potentially making input appear frozen.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, typing in the sessions new-chat input never traversed a virtual workspace. A similar pre-existing walk was reachable only after explicitly opening the attachment picker; the diff newly moves it onto completion retrieval while typing.  
**Changed behavior:** For virtual workspaces, the new typing-triggered completion recursively calls \`IFileService.resolve\` once per directory and stops only after collecting 100 matching suggestions, reaching every directory up to depth 10 when a selective pattern has few or no matches.  
**Confidence:** 0.98 — The recursive call count, match-dependent stopping condition, serial awaits, file-service cancellation limitation, and GitHub provider's full-map \`readdir\` implementation are directly traced. Repository shape controls duration, but large repositories with unmatched prefixes are a realistic trigger.

**Causal diff evidence:** Added line 295 places \`await this.fileService.resolve(uri)\` in a newly recursive completion walk invoked from the added provider; this boundary did not exist on the editor typing path before the diff.

After typing a selective \`\#\` query in a large GitHub remote repository, the suggestion request can perform thousands of serial resolves and repeated full-tree scans, freezing or severely delaying the new-chat UI; a cold cache also waits for the full recursive GitHub tree request.

**Evidence:** Line 295 is inside \`collect\`, which recursively awaits itself for every child directory at line 311. The 100-result guard counts matches rather than visited directories, so a miss visits D directories serially. For the sessions \`github-remote-file\` provider, the first resolve fetches the entire recursive GitHub tree over the network, and each directory \`readdir\` then iterates every entry in that cached tree; this makes a warm traversal O(D×F), with the synchronous map scans occurring in the renderer. \`resolve\` has no cancellation token, so cancellation is only observed between directory calls.

**Suggested direction:** Do not recursively enumerate the virtual tree on each completion request. Use a cancellable cached/indexed search where available, or constrain completion work with a visited-directory/time budget independent of match count and show recent/top-level entries until a more explicit search; coalesce/cache the index per workspace.
