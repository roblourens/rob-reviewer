- Scaling input: Number of active resource subscriptions, requested PR fragments, and bounded pagination pages; equivalent reads collapse to one wire request with at most 64 waiters.
- Effective concurrency: The changed queue caps four active requests globally, two per host, two per caller, and one per account; cooldown-waiting work consumes no active slot. Same-key reads coalesce, while account-level serialization limits the common single-account case to one active network request.
- Cache behavior: Credentials and host capabilities share in-flight work; REST uses a 500-entry ETag LRU; identical REST/GraphQL reads coalesce. Cold cache performs network work, warm ETag reads still revalidate, and failures do not remain in the coalescing maps.
- Mechanism confidence: High confidence in the call path and bounds from transport, queue, resource-service cancellation, and lifecycle tests.
- Magnitude uncertainty: Actual fragment counts and response sizes vary by PR and subscription visibility, but all changed retention, waiter, response, and concurrency dimensions are explicitly bounded.
- Expensive boundaries:
  - network at <code>src/vs/platform/github/common/githubCredentialService.ts:\_resolveIdentity</code>: GET the authenticated /user identity; cardinality: One shared request per credential generation; concurrent credential callers await the same identity promise.

### Scenario 3: Credential replacement, identity bootstrap failures, and rate-limit cooldown recovery

- Critical path: Token acquisition and a cold /user lookup are critical. Server cooldown waits are parked before active admission, and each credential caller has a five-minute end-to-end deadline.
- Scaling input: Credential generations and concurrent callers; callers share generation work while token rotation invalidates the old generation.
- Effective concurrency: One identity promise per generation; callers have independent deadlines. Cooldown-waiting requests occupy retained admission but no active network slot.
- Cache behavior: Successful identity is cached for the current generation. Failures back off; server cooldown is transferred out of the transient bootstrap account and inactive quota state is removed after expiry.
- Mechanism confidence: High confidence from credential, backoff, coordinator, and deterministic scheduler tests.
- Magnitude uncertainty: Token churn and rate-limit prevalence vary, but the changed behavior reduces rather than increases retry cardinality.
- Expensive boundaries:
  - network at <code>src/vs/platform/github/common/githubCredentialService.ts:\_resolveIdentity</code>: Resolve the GitHub account identity after token acquisition or replacement; cardinality: At most one shared /user request per credential generation; failed subsequent generations wait for preserved Retry-After/backoff rather than burst.
    - Introduced by diff: false; previous behavior: Identity resolution already performed /user; the diff prevents repeated attempts during server cooldowns and bounds stalled token/identity waits.; critical-path effect: Blocks authenticated GitHub work until identity is known; cooldown waits occur before the next network attempt.
- Verdict: No reportable regression: the diff coalesces and delays boundary work and adds bounded cleanup rather than increasing network attempts.

### Scenario 4: Request-health telemetry and client-attribution headers

- Critical path: Header construction and counter/sample updates run synchronously per admitted logical request or wire attempt. A five-minute flush or service disposal emits one summary and at most ten timing events; emission is not awaited by GitHub requests.
- Scaling input: Logical request and wire-attempt frequency within each five-minute window; retained timing samples stay capped at ten regardless of traffic volume.
- Effective concurrency: Telemetry does not create concurrent GitHub requests. Flush emits a bounded sequence through the telemetry service, while GitHub request concurrency remains queue-controlled.
- Cache behavior: Aggregation is window-local, reset after flush, discarded immediately when telemetry is disabled, and does not cache request/account/repository content.
- Mechanism confidence: High confidence from the collector implementation and flood/opt-out tests.
- Magnitude uncertainty: Telemetry service internals may buffer or transmit later, but this diff invokes it at a fixed maximum of eleven events per active window.
- Expensive boundaries:
  - other at <code>src/vs/platform/github/common/githubRequestTelemetry.ts:flush</code>: Submit aggregated product telemetry events through ITelemetryService.publicLog2; cardinality: Only for active windows: one summary plus at most ten reservoir samples every five minutes or on disposal; idle engines emit nothing.
    - Introduced by diff: true; previous behavior: No GitHub request-health summary or timing events were emitted.; critical-path effect: Flush is timer/disposal-driven and off the GitHub request critical path; per-request work is fixed-size counters and a reservoir update.
  - network at <code>src/vs/platform/github/common/githubTransport.ts:\_fetchWithRetry/\_download</code>: Send existing GitHub requests with bounded attribution headers; cardinality: No additional calls; fixed headers are added to each existing eligible wire attempt, with browser egress limited to one header.
    - Introduced by diff: false; previous behavior: The network calls already occurred without these attribution headers.; critical-path effect: Header construction precedes the existing fetch but adds no round trip or serialization proportional to request content.
- Verdict: No reportable regression: the introduced work is fixed per request, retained state is bounded, and emission cardinality is capped independently of request volume.

### Scenario 5: Cancellation, resource dormancy, timeout, and service shutdown

- Critical path: Resource disposal/dormancy, waiter cancellation, credential replacement, and deadlines abort the propagated signal; callers reject immediately and replacement work can be admitted. Underlying browser and Agent Host fetch adapters receive the abort signal.
- Scaling input: Frequency of resource interest changes, credential invalidations, and deadlines while requests are active.
- Effective concurrency: The queue admits replacements immediately after abort. Browser fetch and the Agent Host proxy-patched global fetch receive the queue controller signal, so no concrete sustained concurrency beyond abort settlement was established.
- Cache behavior: Cancelled waiters detach immediately; when the last waiter leaves, the shared map entry is removed and its controller is aborted. Rejected unique reads do not retain coalescing entries or waiter timers.
- Mechanism confidence: High confidence in immediate logical release and signal propagation; insufficient evidence that production adapters ignore abort long enough to create a material burst.
- Magnitude uncertainty: Physical socket teardown may lag JavaScript abort settlement, but repository adapters are abort-aware and there is no evidence of realistic accumulated live requests or retained tasks.
- Expensive boundaries:
  - network at <code>src/vs/platform/github/common/githubRequestQueue.ts:enqueue cancel/finish and src/vs/platform/github/common/githubTransport.ts:\_fetchWithRetry</code>: Abort active fetches and admit replacement GitHub requests; cardinality: Active queue occupancy is capped at four, with one per account. Cancelled logical work is removed immediately; production fetch implementations receive the abort signal.
    - Introduced by diff: true; previous behavior: The old queue retained active occupancy until the task promise settled; the changed queue rejects and releases capacity synchronously after signaling abort.; critical-path effect: Cancellation is off the abandoned request's success path and permits current user-visible work to proceed without waiting for an obsolete request.
- Verdict: No finding: although release moved earlier, the diff propagates abort through both production egress paths and no concrete user-visible concurrency or retention regression is established.
