**Relevant issue families:** eager-work, serialization-allocation

### Scenario 1: Starting or continuing an agent chat with an OpenAI-backed vscModelF endpoint

- Critical path: PromptRegistry resolves the F specialization once for the intent, AgentPrompt renders and token-counts the selected system prompt plus the current-turn reminder on every request, then the endpoint serializes those messages and waits for the existing model network request. All prompt rendering and serialization are on the response critical path.
- Scaling input: Cost scales with chat/tool turns and prompt bytes. The new F system prompt is a large static bundle, but the prior OpenAI fallback was also a large GPT-6 bundle on every request; conversation history cardinality, request count, and concurrency are unchanged.
- Effective concurrency: One in-flight model request per active agent turn, with the pre-existing endpoint scheduling/stateful-history behavior; the diff adds no Promise.all burst, queue, or fan-out.
- Cache behavior: The prompt is reconstructed/token-counted for each request as before. Explicit cache-breakpoint eligibility is determined by modelSupportCacheBreakPoints and remains false for the vscModelF family both before and after routing; no cache key, coalescing, positive/negative cache, or stateful marker behavior changes.
- Mechanism confidence: High confidence in the per-turn rendering, serialization, and one network request call path; low confidence that its cost increased materially because the baseline already carried the GPT-6 bundle.
- Magnitude uncertainty: The exact token delta between the new static F prompt and the prior GPT-6 fallback was not measured, but both are similarly large instruction bundles. No evidence shows a substantial increase rather than a model-specific replacement.
- Expensive boundaries:
  - network at <code>extensions/copilot/src/platform/endpoint/node/responsesApi.ts:140</code>: Serialize rendered chat messages into an OpenAI Responses API body and submit the existing streaming model request.; cardinality: One model request per user/tool turn; no loop or per-item network fan-out is added by this PR.
    - Introduced by diff: false; previous behavior: An unrecognized OpenAI-backed vscModelF family was handled by the latest OpenAI fallback and sent the full GPT-6 prompt bundle in the same single request. The PR selects a model-specific static prompt instead; it does not add another boundary call.; critical-path effect: The request must complete before the assistant can produce the next response or tool call.
- Verdict: No reportable regression. The PR replaces the existing large fallback prompt and reminder with an F-specific bundle on the same critical path and does not increase boundary cardinality, concurrency, or disable an existing cache optimization.

### Scenario 2: Agent tool capability construction for vscModelF

- Critical path: agentIntent synchronously evaluates model capability helpers to choose apply-patch versus replace-string tools before prompt rendering. Added F classification uses bounded startsWith checks after already-cached hash lookups.
- Scaling input: A constant number of capability checks per intent/tool setup over a bounded model identifier and family string; it does not scale with workspace files, conversation history, or tool results.
- Effective concurrency: Synchronous local checks only; no queue, parallel burst, or asynchronous work is introduced.
- Cache behavior: Existing SHA-256 lookups in isVSCModelReplaceStringSet remain backed by getCachedSha256Hash. The new startsWith classification adds no cache state or repeated miss behavior.
- Mechanism confidence: High confidence from the direct agentIntent callers and capability helper implementation.
- Magnitude uncertainty: None material: the added string-prefix checks are bounded and negligible relative to prompt rendering and the model request.
- Expensive boundaries: none found
- Verdict: No reportable regression. Tool selection changes behavior but adds only constant local string checks and no expensive boundary, retained collection, or scaling work.

### Scenario 3: Loading the agent prompt modules before model-specific prompt resolution

- Critical path: Importing AgentPrompt synchronously imports allAgentPrompts, which imports vscModelPrompts and initializes the new static F prompt string and resolver registration before any F chat is selected.
- Scaling input: One additional roughly tens-of-kilobytes source literal per module load, independent of workspace size, chat history, model count, or turn count.
- Effective concurrency: Single module initialization on the JavaScript loader path; no concurrent work is scheduled.
- Cache behavior: The loaded module and static string are retained by the module cache for the extension process lifetime, as are all existing model prompt modules. There is no separate eviction or lazy model cache.
- Mechanism confidence: High confidence that the literal is eagerly initialized and retained; low confidence that the bounded addition is large enough to be an actionable performance regression.
- Magnitude uncertainty: The eager source/retained-byte increase is concrete, but no evidence establishes a user-visible startup or memory consequence at this bounded size, and the subsystem already eagerly imports multiple comparably large prompts.
- Expensive boundaries: none found
- Verdict: No reportable regression. Although the new prompt adds bounded eager bundle/retained bytes for all agent users, the size is not sufficient by itself to prove meaningful startup latency or memory pressure, and no scaling or repeated mechanism is introduced.

**Summary:** Completed the performance pass over all four changed files and all diff pages. Traced model routing, prompt rendering/tokenization, current-turn reminders, tool capability selection, module initialization, response serialization, cache-breakpoint behavior, and network cardinality. No high-confidence actionable performance regression was introduced.
