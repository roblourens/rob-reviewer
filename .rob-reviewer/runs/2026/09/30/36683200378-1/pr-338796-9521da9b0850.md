## Findings (1)

### 1. [low] Gate row-class updates to connected tab bars

**Finding ID:** `PERF-61E9C9E99E06`  
**Location:** <code>src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:2316</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** main-thread CPU and per-tab DOMTokenList operations  
**Scaling:** Two live-DOM class operations are added for every open tab in each editor group on every non-wrapping layout; cost grows linearly with tab count and with resize/layout event frequency after animation-frame coalescing.  
**Outcome:** increased UI-thread layout/render latency and reduced resize frame throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** For the normal non-wrapping state, doLayoutTabsWrapping returned without scanning all tab children for row-boundary classes; it only removed last-in-row when transitioning out of wrapping.  
**Changed behavior:** Every non-wrapping tab-bar layout now scans all tab DOM children and performs two DOMTokenList operations per tab, including default legacy and pill tab bars.  
**Confidence:** 0.94 — The changed loop, its unconditional reachability from doLayoutTabsWrapping, and the animation-frame layout call path are explicit. Repository-wide search shows production uses of first-in-row are confined to connectedEditorTabs.css, so the added work is unnecessary for legacy and pill bars. Exact milliseconds vary with tab count and host/browser speed, which is reflected in low severity.

**Causal diff evidence:** RIGHT lines 2316-2324 add an unconditional loop over every tab whenever tabs are not wrapping, invoking classList.toggle/remove for each child. Before this diff, the non-wrapping path had no row-boundary per-tab pass unless wrapping had just been disabled.

With many open editors, resizing the window or editor groups, opening editors, or decoration/toolbar updates add O(number of tabs) synchronous DOM work on the UI thread per coalesced layout, increasing resize/render latency and risking dropped frames on large tab sets even in tab styles that do not use the class.

**Evidence:** MultiEditorTabsControl.layout schedules doLayout on the next animation frame; doLayoutTabs always calls doLayoutTabsWrapping. The new else branch at 2316 scans tabsContainer.children on every non-wrapping layout. Layout is triggered by group/window layout and explicitly by decoration and toolbar changes, and opening an editor redraws/layouts the control. Each iteration calls classList.toggle and classList.remove on live DOM. All production selectors consuming first-in-row are under .modern-ui-connected-editor-tabs in connectedEditorTabs.css; legacy and pill tabs cannot use this class.

**Suggested direction:** Pass the already-computed connected-tab state into this helper and run the non-wrapping first-in-row assignment only for connected tabs (clearing it only when leaving that mode), rather than scanning every legacy and pill tab bar on every layout.
