# Performance review: Support activity bar on top of primary side bar

[PR #195067](https://github.com/microsoft/vscode/pull/195067) at `3df84b15f948c06d04128f4c1f31c1162078cc19`

## Findings (2)

### 1. [medium] Dispose activity listeners when replacing the top bar

**Finding ID:** `PERF-A31AC7722ADF`  
**Location:** <code>src/vs/workbench/browser/parts/paneCompositeBar.ts:658</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Retained ViewContainerActivityAction objects and ActivityService emitter listeners, plus repeated callback CPU on each badge update.  
**Scaling:** For V registered sidebar view containers and T completed top-to-non-top transitions, the service retains O(V\*T) dead actions/listeners; each subsequent activity event dispatches across the same growing listener set.  
**Outcome:** Unbounded retained memory and steadily increasing synchronous badge-update CPU over the window lifetime.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** ActivityService delegated badge updates directly to the currently selected pane composite bar, and ViewContainerActivityAction did not subscribe to a singleton service, so discarding a bar did not leave each action rooted by a long-lived emitter.  
**Changed behavior:** Every ViewContainerActivityAction now registers itself on the singleton ActivityService emitter. The new top-position UI creates a fresh PaneCompositeBar for every side/hidden-to-top transition and clears that bar when leaving top, but PaneCompositeBar keeps these actions in a plain Map and has no whole-map disposal path.  
**Confidence:** 0.98 — The subscription, singleton service lifetime, eager per-container action creation, MutableDisposable teardown, and absence of a PaneCompositeBar-wide action disposal are all directly visible. The exact number of user toggles varies, but retention and linear growth occur for every completed cycle.

**Causal diff evidence:** The added line \`this.\_register(this.activityService.onDidChangeActivity(...))\` roots each per-container action in the long-lived ActivityService; the same PR adds transient top-bar construction and teardown via SidebarPart/updateTitleArea.

After toggling the activity bar from top back to side/hidden, one action and listener per registered sidebar view container remains retained. Repeating the toggle grows heap usage by O(view containers × toggles), and every later SCM/Problems/debug badge change synchronously walks the accumulated dead listeners, progressively increasing UI-thread work.

**Evidence:** SidebarPart's configuration listener calls updateTitleArea; the top branch creates an ActivityBarCompositeBar, whose PaneCompositeBar constructor calls onDidRegisterViewContainers and getCompositeActions for every sidebar container. Leaving top calls paneCompositeBar.clear(), but only individual hideComposite/removeComposite paths dispose actions. Therefore this added subscription survives disposal of the transient bar and ActivityService retains each action callback.

**Suggested direction:** Own all entries of compositeActions with a disposable collection and dispose/clear every activity, pinned, and badge action when PaneCompositeBar is disposed (or keep one stable bar instead of recreating it), so clearing the top bar unregisters every ActivityService listener.

### 2. [medium] Avoid initializing a second accounts controller for the top bar

**Finding ID:** `PERF-19826C5070E6`  
**Location:** <code>src/vs/workbench/browser/parts/titlebar/titlebarPart.ts:298</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Authentication-provider getSessions IPC calls and duplicate account-controller objects/listeners.  
**Scaling:** Cold top-mode initialization grows from P to 2P concurrent getSessions calls for P registered providers; each later reconstruction of the title-bar account item adds another P-call initialization pass.  
**Outcome:** Excessive IPC/provider work and avoidable post-startup CPU/network activity.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** There was one AccountsActivityActionViewItem owned by the activity bar, so startup account discovery issued one getSessions request per registered authentication provider.  
**Changed behavior:** When the activity bar location is top, the new title-bar toolbar instantiates SimpleAccountActivityActionViewItem in addition to the AccountsActivityActionViewItem already constructed by the ActivitybarPart's GlobalCompositeBar. Each instance independently registers authentication listeners and runs its own post-restore account initialization.  
**Confidence:** 0.96 — Both construction paths and the uncached per-provider getSessions call are explicit, and the provider implementation demonstrably crosses the extension-host boundary. Initialization is scheduled after restore/idle, so the exact visible latency varies, but the duplicate call cardinality is deterministic in top mode.

**Causal diff evidence:** The added actionViewItemProvider branch creates \`SimpleAccountActivityActionViewItem\`; that subclass invokes the same eager initializer as the pre-existing activity-bar account view item instead of sharing its loaded account state.

Starting or switching into top mode after restoration issues two extension-host session queries per authentication provider and duplicates account aggregation/listeners. Providers may perform storage or network-backed session work, adding avoidable background IPC and extension-host load; re-entering top repeats the extra fan-out.

**Evidence:** SimpleAccountActivityActionViewItem subclasses AccountsActivityActionViewItem, whose constructor calls initialize(); doInitialize maps every provider to addAccountsFromProvider(), which calls authenticationService.getSessions(providerId). MainThreadAuthenticationProvider.getSessions crosses to the extension host through \`$getSessions\`. SidebarPart always constructs ActivitybarPart and its GlobalCompositeBar even when the grid activity bar is hidden for the top setting, so top mode has two concurrent initializers rather than replacing the first.

**Suggested direction:** Keep account discovery in one shared controller/model and have both renderers subscribe to it, or suppress construction/initialization of the hidden side-bar global account item while the title-bar instance is active.

- Effective concurrency: The two account controllers independently issue their P-provider batches; each batch uses Promise.allSettled, so up to 2P provider calls can overlap. Top-bar construction and state serialization are synchronous.

PaneCompositeBar reads cached container metadata but rebuilds actions and serializes state for the new instance.
- Mechanism confidence: High: both account instances, their eager initialization, and the uncached provider RPC are directly traced.

### Scenario 3: Toggle activity bar top, then side or hidden, repeatedly; later receive badge updates

- Critical path: Each transition to top synchronously constructs one action per sidebar view container. Leaving top disposes the PaneCompositeBar through MutableDisposable, but its plain compositeActions map is not disposed wholesale. Later badge publications synchronously dispatch through ActivityService before callers return.
- Scaling input: V registered sidebar view containers, T top-to-non-top cycles, and E later activity events.
- Effective concurrency: Construction, teardown, and event delivery are synchronous on the UI thread. Each event serially invokes the emitter's listener set.
- Cache behavior: A fresh top-bar action map is created on every entry to top. The ActivityService emitter retains callbacks from disposed bars, preventing those action objects from becoming collectible; there is no eviction/coalescing for these stale listeners.
- Mechanism confidence: Very high: action creation for all containers, singleton-emitter registration, MutableDisposable teardown, and missing map disposal are explicit.
- Magnitude uncertainty: Most users toggle layout infrequently, but every completed cycle deterministically retains V listeners and the cost persists for the window lifetime.
- Expensive boundaries: none found
- Verdict: Reported unbounded listener/action retention and the resulting O(V\*T) memory plus future badge-dispatch work.

### Scenario 4: Resize and render the activity bar in side or top orientation

- Critical path: Grid layout invokes ActivityBarCompositeBar.layout, which reads menu/global element dimensions before laying out the composite bar; top mode uses the sidebar title area's existing part layout.
- Scaling input: Resize frequency and number of visible composite actions.
- Effective concurrency: Entirely synchronous UI-thread DOM/layout work; no asynchronous queue or coalescing is introduced here.
- Cache behavior: Composite sizes and action models remain in memory; no external cache boundary is involved.
- Mechanism confidence: High for reachability, insufficient evidence of a material regression.
- Magnitude uncertainty: DOM geometry reads can force style resolution, but the changed code does not establish a new repeated read-after-write loop on normal resize, and top mode does not construct global controls inside this layout method.
- Expensive boundaries: none found
- Verdict: No finding: the geometry reads are bounded per layout and largely preserve the previous vertical activity-bar behavior.
