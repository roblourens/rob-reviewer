- Effective concurrency: The two commands are serialized by \`&&\`; npm may internally parallelize bounded dependency downloads, but the diff adds no loop, fan-out, queue, or concurrency burst.
- Cache behavior: npm's normal package cache can make repeated installs warmer, but the script intentionally invokes installation each time and adds no custom cache, cache key, negative cache, or request coalescing.
- Mechanism confidence: High confidence that the command adds sequential network/filesystem setup work only when explicitly invoked; the changed package.json script has no implicit lifecycle hook.
- Magnitude uncertainty: Exact package dependency count, cache-hit rate, registry latency, and global installation duration are not established, but invocation is manual and bounded.
- Expensive boundaries:
  - subprocess at <code>package.json:101 \`setup-feed\`</code>: Launches npm to globally install one named credential-provider package, then launches npm config to set one registry value.; cardinality: Two top-level subprocesses per explicit invocation; installation transitively resolves the single package's dependency graph, not a repository-sized collection.

- Verdict: No reportable regression: the expensive work is the requested, opt-in setup operation, is bounded to one package installation, and does not move onto a hot product path.

### Scenario 2: Developer explicitly runs \`npm run reauth-feed\` to force credential refresh.

- Critical path: The npm wrapper and credential-provider command must finish authentication before this explicit command completes; it is not wired into installs, startup, build, or application interaction.
- Scaling input: One explicit refresh request per command invocation; no collection or persistent history increases work.
- Effective concurrency: One credential-provider invocation with no changed loop, batching, fan-out, limiter, or concurrent scheduling.
- Cache behavior: \`--force\` intentionally bypasses reuse of an existing credential for this manually requested refresh; no changed automatic caller repeatedly defeats the credential cache.
- Mechanism confidence: High confidence that only one manually triggered provider process is added; possible internal network work is bounded by a single refresh flow.
- Magnitude uncertainty: The provider's internal request count and authentication latency are not visible in the repository, but the changed invocation count and opt-in reachability are clear.
- Expensive boundaries:
  - subprocess at <code>package.json:102 \`reauth-feed\`</code>: Launches \`artifacts-npm-credprovider --force\` through the npm script runner.; cardinality: One subprocess per explicit invocation.
    - Introduced by diff: true; previous behavior: No repository reauthentication script existed; developers had to invoke the credential provider directly.; critical-path effect: Credential refresh is the entire explicit reauthentication command's critical path.
  - network at <code>package.json:102 \`artifacts-npm-credprovider --force\`</code>: The credential provider may contact the configured authentication/feed service to force credential refresh.; cardinality: One credential-refresh flow per explicit invocation, with no collection-driven multiplicity visible in the changed code.
    - Introduced by diff: true; previous behavior: The repository did not initiate this flow; equivalent direct reauthentication incurred the same boundary outside the script.; critical-path effect: Any authentication/network interaction blocks completion of the manually requested reauthentication.
- Verdict: No reportable regression: forced refresh is explicit command semantics rather than newly repeated or hot-path work.
