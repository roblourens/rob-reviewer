### Scenario 1: Open a Rust single-folder or multi-root workspace with usage telemetry enabled

- Critical path: LifecyclePhase.Eventually constructs WorkspaceTags and starts getTags; workspace-tag telemetry waits for tag collection, but editor/workbench progress does not wait for it, so the Cargo work is off the user startup critical path.
- Scaling input: Cost scales with R workspace roots for existence probes, C root Cargo manifests for reads, and total Cargo.toml lines/dependency declarations for linear parsing. Effective cardinality is normally R=1 and C=1; the fixed allowlist bounds emitted Cargo fields.
- Effective concurrency: All root Cargo existence probes and reads are joined into the existing Promise.all with other manifest probes, without a separate limiter. The overall tag result is cached after the first completed getTags call, so this does not recur during the session.
- Cache behavior: Cold session performs tag collection once. After resolveWorkspaceTags completes, WorkspaceTagsService.\_tags serves warm getTags calls without more Cargo I/O or parsing. No cross-session cache is used, consistent with workspace telemetry collection.
- Mechanism confidence: High: the changed call path, exact R-probe/C-read multiplicity, Promise.all concurrency, linear parser, one-session cache, and eventual lifecycle placement are directly established by the code.
- Magnitude uncertainty: Remote filesystem latency and unusually large multi-root counts can increase background I/O, but typical root Cargo manifests and root counts are small; no evidence shows this eventual telemetry work causes user-visible contention or latency.
