### Scenario 3: Resize, keyboard-scroll, or dynamically reflow an open plugin detail

- Critical path: ResizeObserver callbacks and content-change events synchronously call DomScrollableElement.scanDomNode, which reads client/scroll dimensions and updates scrollbar state. Keyboard navigation performs constant-time dimension reads and one scroll-position update per handled key event.
- Scaling input: Cost scales with actual editor resize notifications, narrow-layout threshold transitions, asynchronous markdown completion, image load events, or user key events, not with the number of plugins in the inventory.
- Effective concurrency: Browser ResizeObserver delivery is frame-coalesced; narrow-layout class changes are scheduled for the next animation frame. Markdown code blocks invoke one aggregate callback after Promise.all, while image loads notify individually. Work remains on the UI thread but is bounded to actual changes.
- Cache behavior: No cache is involved. Scroll dimensions are current DOM state and must be refreshed after viewport or content changes.
- Mechanism confidence: High confidence from DomScrollableElement.scanDomNode reading six geometry properties and the traced observer/event registrations.
- Magnitude uncertainty: A very large README increases browser layout cost, but the changed code does not rescan per row/frame continuously and follows established DomScrollableElement patterns.
- Expensive boundaries: none found
- Verdict: No reportable regression. The synchronous work is bounded and directly supports scrollbar correctness; there is no demonstrated loop, per-frame polling, or collection-wide repetition.
