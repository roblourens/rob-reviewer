### Scenario 3: Render chat Markdown containing the new preview link, including local and remote Agent Host sessions

- Critical path: Markdown rendering rewrites internal link targets, scans anchors once, and synchronously parses query-bearing anchors to identify preview metadata. - Scaling input: Synchronous query parsing scales with query-bearing anchors in a rendered response; filesystem stats scale only with anchors explicitly tagged \`vscodeLinkType=markdown-preview\`, whose normal effective cardinality is one per policy invocation.
- Effective concurrency: One DOM scan per rendered Markdown part. Preview widgets independently issue their file stats with no limiter, so effective stat concurrency equals the number of preview links in that rendered part; the intended policy response contributes one.
- Cache behavior: No stat cache is added, but unchanged Markdown parts are reused when content is identical. Streaming rerenders rebuild the part when content changes; the policy command emits its complete link in a single terminal response rather than token streaming. URI rewriting preserves preview metadata without network access.
- Mechanism confidence: High for the single-scan path, metadata filter, widget construction, and asynchronous stat call.
- Magnitude uncertainty: Arbitrary model-authored content could manufacture many tagged links, but no realistic product path in the diff does so; the supplied feature creates one link.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatInlineAnchorWidget.ts:227</code>: Resolve \`stat\` for the preview resource through the file service, potentially via the Agent Host filesystem provider; cardinality: One asynchronous stat per newly rendered preview widget; normally one for each policy-command response

- Verdict: No reportable regression. The implementation avoids a second anchor scan, unchanged responses are reusable, and the only new boundary is one off-critical-path stat for the intended one-link response.
