## Findings (1)

### 1. [medium] Coalesce picker measurement instead of cloning per item during layout

**Finding ID:** `PERF-AD82D9573023`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/input/chatInputPickerResponsiveLayout.ts:88</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** DOM subtree clones, temporary DOM nodes, style recalculation, and synchronous geometry reads  
**Scaling:** Each layout pass expands every picker and then calls \_fitsAvailableWidth once per picker until the row fits; every call re-enumerates items, deep-clones the entire lane, inserts the clone into the live document, and reads several bounding rectangles. The work is therefore roughly O(P \* (D + P)) for P pickers and D lane descendants, multiplied by resize/layout and observed-mutation frequency, and two lanes are processed per chat input.  
**Outcome:** Repeated forced style/layout and DOM allocation on the UI thread can cause CPU/GC pressure and dropped frames while resizing the chat/sidebar, and adds avoidable latency to repeated same-width chat layouts.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, the chat input layout path only updated a width observable (which is a no-op for an unchanged value), while the sessions composer used CSS container queries; neither path deep-cloned picker DOM or performed per-picker synchronous geometry measurement from every host layout.  
**Changed behavior:** The new loop invokes \_fitsAvailableWidth for each candidate compact state. That helper calls \_measurePreferredLayout, which cloneNode(true)s the lane, appends it to the live parent, measures each item and the clone, then removes it. ChatInputPart.layout and NewChatInput.layout now invoke two such controllers synchronously, while each controller also installs a synchronous ResizeObserver and MutationObserver callback.  
**Confidence:** 0.98 — The synchronous call paths, repeated clone insertion, geometry reads, two controllers per input, and dynamic-layout/resize reachability are explicit in the changed code. Exact frame cost depends on picker/subtree size and platform, so severity is medium rather than high.

**Causal diff evidence:** This added file introduces the per-item \_fitsAvailableWidth call at RIGHT line 88; that call performs a fresh deep clone and synchronous measurement for every candidate state. The PR also adds direct invocations from both chat input layout methods, whereas the deleted implementation only set a stable-width observable or relied on CSS.

Dragging a sidebar/window divider, or repeated ChatWidget layouts such as dynamic response item-height updates, can perform many full picker-lane clones and forced layouts per frame even when the width is unchanged, making the composer visibly janky.

**Evidence:** The changed loop at line 88 calls \_fitsAvailableWidth once for each item. \_fitsAvailableWidth calls \_measurePreferredLayout at line 119; lines 159-181 deep-clone, attach, and synchronously measure the lane and every item. The same pass also alternates all compact states and invokes toolbar relayout up to three times. Changed callers at chatInputPart.ts:4984-4985 and newChatInput.ts:1506-1507 run both controllers from host layout; chatWidget.ts:3678 calls inputPart.layout, and dynamic item-height handling reaches chatWidget.layout repeatedly at lines 3797-3815. The constructor additionally runs the same work directly in ResizeObserver and MutationObserver callbacks at lines 50 and 53.

**Suggested direction:** Schedule/coalesce invalidations to one animation-frame pass, skip unchanged width/content, and measure the expanded/compact intrinsic widths in one detached or contained measurement per invalidation so the compact cutoff can be computed without cloning and forcing layout once per picker. Avoid the direct host-layout calls when the ResizeObserver already covers the width change.
