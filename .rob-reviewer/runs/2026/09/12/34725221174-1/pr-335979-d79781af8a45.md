### Scenario 1: Background task status notification reconciles retained subagent completion

- Critical path: The SDK \`session.background\_tasks\_changed\` event queues reconciliation; the serialized \`rpc.tasks.list\` result must complete before terminal child states emit \`subagent\_completed\` progress. This is on the child-status update path, not editor startup/render/input.
- Scaling input: Frequency of background-task notifications and resumes while an RPC is in flight; task processing scales with the task list returned by the SDK. Effective RPC concurrency is one.
- Effective concurrency: \`Throttler\` enforces one active RPC. The new loop absorbs stale revisions serially, while any already queued throttler factory becomes a no-op once the reconciled revision catches up.
- Cache behavior: No result cache is used because status must be authoritative. Warm/cold behavior is the same; revisions coalesce invalidations, and only a stable final read is applied.
- Mechanism confidence: High: the changed loop, revision checks, throttler implementation, and deterministic call-count tests directly establish the call path and concurrency.
- Magnitude uncertainty: SDK RPC duration and real notification burst frequency are not measured, but tests establish single-flight behavior and coalesced call counts.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:1600 \`\_reconcileSubagentTaskStatuses\`</code>: Lists authoritative SDK background tasks through \`session.rpc.tasks.list()\`.; cardinality: One active call at a time. Notification bursts during an active call coalesce; at most one stable trailing list is needed after one or more invalidations, with further calls only if each read is invalidated again before completion.
    - Introduced by diff: false; previous behavior: The same RPC ran for each active/coalesced reconciliation. The prior throttler already produced an active call plus one coalesced queued call for notification bursts, but a resume-only revision change could invalidate the active result without guaranteeing the trailing authoritative call.; critical-path effect: A stable list response is required before terminal subagent completion can be reconciled and published.
- Verdict: No reportable regression. The additional serialized read occurs only when an otherwise-lost resume invalidates a read, and preserves the prior active-plus-trailing cardinality for notification bursts.

### Scenario 2: A status completion synchronously resumes another retained child while applying a task list

- Critical path: Applying terminal tasks emits progress synchronously; a listener may resume another child and advance the revision. The current collection scan stops and a fresh authoritative task-list RPC must complete before applying the new stable state.
- Scaling input: Number of distinct resume/status revisions that occur before each list response stabilizes, not raw task count or duplicate notifications after coalescing.
- Effective concurrency: Strictly serialized by the existing \`Throttler\`; the test asserts maximum active calls of one.
- Cache behavior: No cache is appropriate for this authoritative state transition. Duplicate invalidations share the newest revision and do not each force a call.
- Mechanism confidence: High: production revision checks and the new two-child deterministic test prove the mechanism.
- Magnitude uncertainty: The prevalence of synchronous cross-child resumes is uncertain, but the extra boundary operation is limited to actual invalidation races.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:1600 \`\_reconcileSubagentTaskStatuses\`</code>: Repeats \`rpc.tasks.list()\` after the current result is invalidated during completion application.; cardinality: One serialized retry for the resulting revision, coalescing multiple synchronous or queued invalidations; never concurrent.
    - Introduced by diff: true; previous behavior: The prior implementation continued applying the fetched collection without an intra-loop freshness check; if only the resume advanced freshness, it did not perform a required follow-up authoritative read.; critical-path effect: The retry delays final completion reconciliation but prevents applying the remainder of a stale collection.
- Verdict: No reportable regression. The bounded extra RPC is necessary to replace stale data, and duplicates are coalesced rather than fanned out.

### Scenario 3: Session abort or disposal while a task-status list call is pending

- Critical path: An already-started SDK list call may finish, but cancellation/disposal checks prevent applying it or starting retry work. Session teardown does not wait for a new reconciliation loop iteration.
- Scaling input: One active reconciliation per session because of throttling; teardown does not scale retries with queued notifications.
- Effective concurrency: One active RPC; cancellation/disposal terminates the loop and queued factories cannot issue another call for the captured canceled token.
- Cache behavior: No cache. Reconciled state is abandoned on teardown.
- Mechanism confidence: High: token capture, loop guards, post-await checks, throttler disposal, and lifecycle tests establish the behavior.
- Magnitude uncertainty: Underlying RPC cancellation support is not visible, but no changed line increases retained work after teardown.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:1600 \`\_reconcileSubagentTaskStatuses\`</code>: Potentially in-flight \`rpc.tasks.list()\` begun before abort/disposal.; cardinality: At most the single already-active call; no trailing call after cancellation or disposal.
    - Introduced by diff: false; previous behavior: An in-flight list could also remain until its promise settled; the old post-await disposal check prevented application but had no abort-token check.; critical-path effect: The existing in-flight operation is not newly cancellable, but the diff prevents additional list calls and completion processing after teardown.
- Verdict: No regression; cleanup behavior is improved by suppressing trailing work.

### Scenario 4: Retained-child E2E polling failure diagnostics

- Critical path: The existing test polls \`subscribe\` and, only while assertions fail, builds an expanded error message containing active-turn state and up to the expected one-to-three child turns. This affects test failure diagnostics, not product runtime.
- Scaling input: At most the test's expected one, two, or three turns per failure message and up to the existing bounded 100 polling attempts.
- Effective concurrency: Sequential polling through the existing assertion helper; no new concurrency.
- Cache behavior: No cache; each poll intentionally requests current test state. The diff does not alter polling or subscription behavior.
- Mechanism confidence: High: the changed hunk only maps turns and JSON-stringifies diagnostics after the existing subscribe result.
- Magnitude uncertainty: Markdown response size can vary, but this is bounded test-only failure work over at most three turns.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/test/node/e2e/suites/subagentSuite.ts:321 polling callback</code>: Calls the existing test client's \`subscribe\` method once per polling attempt.; cardinality: Unchanged: one subscribe call per existing polling attempt, at 50 ms intervals for up to 100 attempts.
    - Introduced by diff: false; previous behavior: The same subscribe polling occurred and failures constructed a constant error string.; critical-path effect: The boundary call already governed each E2E polling attempt; the diff only enriches a locally constructed failure message after the response.
- Verdict: No reportable product performance regression; added serialization is bounded and test-only.
