<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** cleanup-lifecycle, boundary-fanout, repeated-work

### Scenario 1: Reuse a terminal editor container for a different terminal instance, including detaching after drag-and-drop initialization

- Critical path: \`TerminalEditor.setInput\` synchronously detaches the old instance and attaches the new one; the new DnD controller is initialized by a zero-delay timer. The added \`clear()\` only synchronously disposes a fixed set of emitters/listeners and is on the tab-reuse path, but does not perform layout, I/O, or scaling work.
- Scaling input: One old and one new terminal per editor-input replacement. Disposal cardinality is constant: one controller store and the fixed drag listener set for the detached instance.
- Effective concurrency: Initialization callbacks are queued on the UI event loop. The container-identity guard prevents a stale callback from initializing after ownership changes; the active instance still creates one observer. There is no worker pool, queue burst, or parallel boundary operation.
- Cache behavior: No cache participates. Cold and repeated attachment both schedule initialization; same-container \`attachToElement\` calls return before scheduling. Detach clears the current observer immediately.
- Mechanism confidence: High: the changed line disposes the MutableDisposable's prior store, whose fixed DOM listeners and controller emitters are directly visible; the test demonstrates old/new container reuse.
- Magnitude uncertainty: Exact frequency of terminal editor tab reuse followed by file drops is unknown, but the changed mechanism is bounded and removes work rather than adding it.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminal/browser/terminalInstance.ts \`\_initDragAndDrop\`, \`sendPath\`, and \`sendText\`; src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts \`write\`</code>: On a subsequent file drop, \`sendPath\` prepares the path and calls \`TerminalProcessManager.write\`, which invokes terminal process input.; cardinality: After the diff, one terminal-process input per file drop on the reused container. Before the diff, the old and new observers could each handle the same drop, producing up to two process-input calls for the demonstrated two-instance reuse.
    - Introduced by diff: false; previous behavior: The boundary already existed for normal file drops; stale observer retention could duplicate it after container reuse. The diff reduces rather than increases this boundary cardinality.; critical-path effect: The process input occurs only when the user drops a file, not during detach/attach. The diff removes the stale call and does not add a boundary to the editor-reuse critical path.
- Verdict: No reportable regression. The change performs constant-time cleanup on a relatively infrequent lifecycle transition and prevents duplicate event handling and process input.

### Scenario 2: Detach a terminal when removing it from a panel group or moving it to the background before deferred DnD initialization runs

- Critical path: Group removal/backgrounding calls \`detachFromElement\`; the added observer clear is synchronous and fixed-size. A pending attach timer later checks the captured container against the current container and exits before allocating the controller or listeners.
- Scaling input: One observer store per detached terminal. Across multiple terminals, cost grows linearly with the number explicitly detached, with constant work per terminal and no collection-wide scan introduced by the diff.
- Effective concurrency: All detach and deferred initialization work runs on the UI event loop. Each prior attach may have one queued timer; the new guard suppresses stale initialization rather than increasing concurrency.
- Cache behavior: No cache or negative cache. When the terminal is later attached to a valid container, it creates a fresh observer; same-container attachments remain coalesced by the existing early return.
- Mechanism confidence: High: direct call sites show detach during group removal/backgrounding, and MutableDisposable.clear synchronously disposes the held store.
- Magnitude uncertainty: The number of simultaneously backgrounded terminals varies, but no subprocess, IPC, filesystem, database, or network work was added, and retained DOM/listener state is reduced.
- Expensive boundaries: none found
- Verdict: No reportable regression. Cleanup bounds retained listener/controller state, while the stale-callback guard avoids eager allocation after detach.

**Summary:** Completed the performance pass over all changed files and hunks. Traced terminal editor reuse, panel/group removal, backgrounding, deferred observer initialization, DOM listener disposal, and the file-drop process-input boundary. The PR removes stale observers and duplicate boundary work with only fixed synchronous cleanup; no actionable performance regression was introduced.
