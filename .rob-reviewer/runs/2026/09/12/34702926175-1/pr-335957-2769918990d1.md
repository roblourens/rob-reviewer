# Performance review: Add PR comment on selection in Agents

[PR #335957](https://github.com/microsoft/vscode/pull/335957) at `2769918990d1a010bea0244871b4be775e52c96d`

## Findings (1)

### 1. [medium] Cache PR context off the cursor-selection path

**Finding ID:** `PERF-B8E1126435D1`  
**Location:** <code>src/vs/sessions/contrib/agentFeedback/browser/agentFeedbackEditorInputContribution.ts:427</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous CPU work scanning session change entries and allocating replacement menu actions  
**Scaling:** The cost is O(selection events × session changes), plus O(selection events × associated pull requests); keyboard range extension generates one cursor-selection event per key repeat.  
**Outcome:** Increased editor input latency and selection jank for sessions with large change sets when the PR-comments experiment is enabled.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Ordinary non-empty cursor selections opened/repositioned the feedback widget without resolving PR comment context. The change-list scan occurred only when the user explicitly invoked the line/gutter comment flow.  
**Changed behavior:** Every qualifying cursor-selection event now calls getPRReviewCommentPullRequests synchronously before showing the widget. For normal file resources that call enters \_getPRReviewCommentContext and \_resolveWorkspaceResource, which walks session.changes and compares up to three URIs per change; the result is then used to rebuild disposable Action objects.  
**Confidence:** 0.94 — The event registration, synchronous call chain, linear loop, and before/after placement are explicit in the repository. The only material uncertainty is how often users have very large session change sets, so severity is medium rather than high; the experiment can be auto-enabled despite its false default.

**Causal diff evidence:** The added argument \`this.\_getPRCommentPullRequests(sessionResource, model.uri)\` at RIGHT line 427 is executed from \`\_onSelectionChanged\`, which is directly registered to \`onDidChangeCursorSelection\`. Before this hunk \`\_show\` was called with only geometry/focus arguments, so selections did not enter the PR-context/change-list scan.

With \`chat.experimental.agentsWindowPRComments\` enabled, extending a selection via the keyboard in a session containing hundreds or thousands of changed files repeatedly scans that entire list on the editor event path, delaying each selection update and causing visible input lag. A file absent from or late in the list exercises the full scan.

**Evidence:** \`\_onSelectionChanged\` is called by \`editor.onDidChangeCursorSelection\` (line 213). The new call reaches \`CodeReviewService.getPRReviewCommentPullRequests\` -&gt; \`\_getPRReviewCommentContext\` (codeReviewService.ts:308-329) -&gt; \`\_resolveWorkspaceResource\` (403-411), whose \`for (const change of changes ?? \[\])\` compares each change's URI candidates until a match is found. \`\_show\` then calls \`\_setInputPRCommentActions\`, and \`FeedbackInputWidget.setAdditionalActions\` clears and recreates actions. Mouse dragging is coalesced by \`\_mouseDown\`, but Shift+Arrow/keyboard selection changes are not, so repeated key events synchronously repeat the full scan before widget positioning.

**Suggested direction:** Resolve and cache the PR context/actions once per session and model resource, invalidating it when the session change list, workspace GitHub metadata, model, or setting changes; alternatively defer the lookup until the split-button menu is opened. Keep cursor-selection handling limited to range/position updates.

- Cache behavior: PR refresh uses ETags and coalesces overlapping refreshes, but still performs conditional requests. Changed-file and file-content reads are uncached. Failures are not negative-cached. Passing a selected PR prevents multi-PR fan-out.
