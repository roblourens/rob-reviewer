### Scenario 2: Copilot MCP start/stop for a currently published customization missing from the live SDK inventory

- Critical path: UI lifecycle action performs an in-memory session-state lookup, flattens current MCP customizations, and scans for the exact ID; on a match it queues one SDK start/stop RPC. The O(C) flatten-and-find runs synchronously before the RPC, where C is current top-level customizations plus children.
- Scaling input: All currently published customization containers and children in one session; effective frequency is one fallback scan per explicit lifecycle action that misses the live inventory.
- Effective concurrency: Lookup is synchronous and single-shot. Accepted Copilot lifecycle calls remain serialized per server by SequencerByKey, preventing same-server bursts.
- Cache behavior: A subsequently live server returns through the existing live fast path. The fallback deliberately reads current session state rather than retaining a stale cache; unknown IDs repeat the bounded scan.
- Mechanism confidence: High: the added line invokes findMcpServerName, which allocates and scans a flattened MCP list, and a match newly reaches the established RPC path.
- Magnitude uncertainty: Customization counts can vary, but realistic session inventories are bounded and lifecycle clicks are infrequent; no evidence shows the linear temporary array is material at those cardinalities.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:startMcpServer/stopMcpServer</code>: Copilot SDK starts or stops the resolved MCP server; start then seeds current server states from the SDK; cardinality: One queued lifecycle RPC per user action; no per-customization boundary fan-out.
    - Introduced by diff: true; previous behavior: Before the fallback, this valid published ID was rejected and no lifecycle RPC or server process start/stop occurred.; critical-path effect: The RPC/process lifecycle is required for the requested action and dominates the small in-memory lookup.
- Verdict: No reportable regression: the bounded O(C) lookup and single serialized boundary call are necessary to restore the explicitly requested lifecycle operation, without repeated fan-out or hot-path execution.

### Scenario 3: Codex MCP start for a published customization not resolved by the refreshed live inventory, including an unmaterialized session

- Cache behavior: Existing inventory/live entries remain the fast path after refresh. The fallback uses authoritative current session state; the subsequent status refresh replaces the in-memory inventory for future calls.
- Mechanism confidence: High for reachability and boundary count; lower prevalence because the fallback only matters when live inventory cannot already resolve the published ID.
- Magnitude uncertainty: Thread materialization and pagination latency vary, but each is bounded to an explicit start request and no evidence shows accidental repetition or fan-out.
- Expensive boundaries:

  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:startMcpServer</code>: Send config/mcpServer/reload to the Codex app server; cardinality: Exactly one reload request per accepted start action.

- Verdict: No finding: one bounded scan per invalid explicit action is insufficient to establish actionable CPU/GC impact.
