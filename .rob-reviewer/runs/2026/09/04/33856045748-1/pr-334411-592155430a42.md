<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** eager-work, boundary-fanout, concurrency-burst, repeated-work

### Scenario 1: Open Agent Customizations &gt; MCP Servers for the first time with MCP access enabled and one or more uncached extension-contributed collections

- Critical path: The section's existing refresh and gallery rendering can proceed immediately; the new activateCollections call is fire-and-forget. Extension-provided rows cannot appear until lazy collection activation and provider registration finish, but activation does not block the initial section render.
- Scaling input: The number U of allowed uncached lazy MCP collections after policy filtering; activation fan-out is U, while extension-host managers process the event requests concurrently and cache each event.
- Effective concurrency: McpRegistry uses Promise.all across U lazy collections. Each activation event fans out across applicable extension-host managers, whose per-event promises are cached. There is no new limiter, but U is the number of installed uncached MCP collection contributions, not the number of servers.
- Cache behavior: Uncached lazy collections are activated once and then replaced by normal collections or removed; cached lazy collections are excluded. Extension activation events are promise-cached by ExtensionHostManager. The gallery snapshot remains cached in the widget after a successful query.
- Mechanism confidence: High: the changed setVisible call reaches discoverCollections, its Promise.all fan-out, and extension service activation directly.
- Magnitude uncertainty: Provider activation duration and the number of installed uncached provider collections vary by profile; no repository evidence shows a harmful burst for realistic U.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts:\_activateExtensionServers</code>: Activate each uncached MCP collection's extension activation event and wait for initial provider promises; cardinality: One activation-event request per uncached allowed lazy collection; discoverCollections starts all such requests with Promise.all. ExtensionHostManager caches each activation event, and an extension itself is activated at most once even if it contributes multiple collection events.
    - Introduced by diff: true; previous behavior: Opening this section did not request lazy collection activation; another MCP discovery command had to introduce the same IPC later.; critical-path effect: Off the initial UI render path because setVisible does not await activation; it is on the path for extension-provided servers becoming visible.
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts:queryGallerySnapshot</code>: Query the MCP gallery snapshot; cardinality: At most one cold snapshot request per widget while no snapshot is loaded; loading/failure state suppresses duplicate requests.
    - Introduced by diff: false; previous behavior: The same setVisible refresh already initiated this gallery query before the diff.; critical-path effect: Asynchronous and independently populates marketplace entries.
- Verdict: No finding. The new boundary work is necessary to materialize the requested list, is gated on explicit visibility and access, runs off the initial render path, and is cached after discovery.

### Scenario 2: Leave and reopen the MCP Servers section after all lazy collections are known

- Critical path: setVisible schedules activateCollections and refresh without awaiting either. discoverCollections resolves without extension activation, then McpService reconciles collected server definitions on a microtask; the initial section display is not blocked by the returned promise.
- Scaling input: The number S of currently collected MCP server definitions. The existing reconciliation maps S definitions and matches current servers with linear searches, giving O(S^2) comparisons on each false-to-true visibility transition.
- Effective concurrency: One fire-and-forget activation per actual hidden-to-visible transition; duplicate setVisible(true) notifications are suppressed. Reconciliation runs serially on the renderer/main thread after the empty discovery promise resolves.
- Cache behavior: The extension activation cache and registry lazy state eliminate extension-host IPC on the warm path. The widget does not suppress the service-level warm reconciliation, although unchanged arrays avoid publishing a new server observable value.
- Mechanism confidence: High for the repeated warm reconciliation; low for material user-visible impact at realistic MCP server counts.
- Magnitude uncertainty: Repository evidence does not establish realistic server counts large enough for the identifier comparisons and short-lived arrays to cause measurable latency, especially beside the existing list refresh/render.
- Expensive boundaries: none found
- Verdict: No finding. Although the diff adds repeated warm reconciliation, the available evidence supports only a speculative micro-optimization rather than a concrete performance regression.

### Scenario 3: Restore MCP access while the MCP Servers section is already visible

- Critical path: The changed activation request is fire-and-forget. Existing code independently starts either the current gallery search or a refresh; provider rows appear after activation publishes server definitions.
- Scaling input: Uncached allowed collection count U for activation, plus one current gallery request determined by the existing search state.
- Effective concurrency: Lazy collection loads run with Promise.all; the existing gallery operation runs concurrently rather than serially behind activation.
- Cache behavior: Successful lazy discovery removes the uncached state; extension events are cached. Gallery requests use cancellation and retain successful snapshot data within the widget.
- Mechanism confidence: High: configuration change reaches the added activation line only when access changes to enabled and the section is visible.
- Magnitude uncertainty: Rapid disable/enable toggling could overlap registry discovery calls, but extension activation events are coalesced and this is not a realistic high-frequency workflow.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts:\_activateExtensionServers</code>: Activate uncached extension-contributed MCP collections and await provider registration; cardinality: One request per allowed uncached lazy collection, concurrently, with extension-host event promise caching.
    - Introduced by diff: true; previous behavior: Restoring access while visible only refreshed/searched; it did not activate lazy provider extensions.; critical-path effect: Not awaited by updateAccessState, but required before newly activated provider servers can be listed.
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts:updateAccessState/queryMcpSearch/queryGallerySnapshot</code>: Resume an MCP gallery text query or snapshot query; cardinality: One current query; cancellation tokens replace prior gallery work, and snapshot/loading state suppresses duplicates.
    - Introduced by diff: false; previous behavior: The access-restoration branch already performed this query or refresh before the diff.; critical-path effect: Asynchronously populates marketplace results and is independent of extension provider activation.
- Verdict: No finding. The introduced activation is required by restored access, does not serialize the existing network/UI work, and is effectively one cold activation per provider.

**Summary:** Reviewed the complete two-file diff and traced MCP section visibility and access restoration through registry discovery, extension-host activation, server reconciliation, widget refresh, and gallery queries. No high-confidence actionable performance regression was established.
