# Performance review: sessions: redesign unified workspace picker

[PR #334591](https://github.com/microsoft/vscode/pull/334591) at `654e64b0d74b497aa99a56aaaa11657fe92ffa14`

## Findings (1)

### 1. [low] Defer remote session counts until the Remote flyout opens

**Finding ID:** `PERF-5A60A2E0A679`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts:1416</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Synchronous CPU work and temporary session arrays/filtered arrays  
**Scaling:** Each unified-picker open now performs serial work proportional to the sum of cached sessions across every registered remote host, O(sum sessions per host), even when the user only wants a local or GitHub workspace.  
**Outcome:** Increased workspace-picker open latency plus CPU/GC pressure for users with large accumulated remote-session histories.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, \`includeRemoteProviders\` was true only on the Remote tab, so opening the picker on Local/GitHub did not enumerate remote-host sessions; the work occurred only after selecting Remote.  
**Changed behavior:** With tabs removed, \`activeGroup\` is normally undefined, and this added condition includes every remote provider while constructing the unified picker. The subsequent loop calls \`getRemoteHostStatusDescription\`, which calls \`provider.getSessions()\` and filters every session to compute active counts before the Remote submenu is opened.  
**Confidence:** 0.96 — The changed gate, synchronous picker call path, and full-cache scans are directly traced. Session enumeration is cache-backed and coalesces any initialization refresh, so magnitude depends on users' remote-host and session counts; that uncertainty is reflected in low severity rather than mechanism confidence.

**Causal diff evidence:** The RIGHT-side condition \`activeGroup === undefined \|\| activeGroup === SESSION\_WORKSPACE\_GROUP\_REMOTE\` newly activates remote-provider row construction for the default tabless unified picker; the deleted condition required \`\_activeTab === SESSION\_WORKSPACE\_GROUP\_REMOTE\`.

Opening the workspace selector for any new session can pause longer as remote session history grows, even if the user selects Open Folder or a GitHub action and never opens Remote.

**Evidence:** \`includeRemoteProviders\` now accepts \`activeGroup === undefined\` at line 1416. That drives the loop at lines 1500-1503 for every remote provider. \`getRemoteHostStatusDescription\` at lines 167-170 calls \`provider.getSessions().filter(...)\`; \`BaseAgentHostSessionsProvider.getSessions\` itself copies the full session cache, after which this helper allocates and scans another filtered array. The picker builds these items synchronously before \`actionWidgetService.show\` at lines 746-760.

**Suggested direction:** Gate remote-provider status/count construction behind opening the Remote flyout (or otherwise compute those rows lazily), while keeping only the cheap top-level Remote action in the initial unified list.
