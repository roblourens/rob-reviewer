# Performance review: Harden content exclusion failrue condition

[PR #332368](https://github.com/microsoft/vscode/pull/332368) at `16178935fe9a0b9d7633f3b2cf9e02c0aca89e21`

## Findings (4)

### 1. [high] Bound empty-remote repository revalidation per repository

**Finding ID:** `PERF-A41F4C04E717`  
**Location:** <code>extensions/copilot/src/platform/ignore/node/remoteContentExclusion.ts:326</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Git extension API calls and, on the unopened-repository path, filesystem stat/open/read operations for .git/config.  
**Scaling:** O(F×R) lookups for F distinct files plus repeated evaluations R while the repository has no remote, instead of O(1) repository resolution followed by cache hits. Search filtering runs up to 20 checks concurrently, so the repeated calls also burst at that concurrency.  
**Outcome:** Excessive Git/filesystem I/O, higher CPU, and substantially increased bulk-search/index latency.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Resolved RepoMetadata was cached by repository root regardless of remote count, so later files under a local-only repository skipped getRepositoryFetchUrls and each settled file verdict could be memoized.  
**Changed behavior:** A successfully resolved repository with no fetch remote is deliberately omitted from \_repoRootCache, and negative file verdicts for it are also left unsettled, so every file check resolves the same repository through Git again.  
**Confidence:** 1.00 — The new test pins the per-file call count, and the complete call path to Git/filesystem operations and high-cardinality production callers is explicit. Only whether a given local-only repo is already open determines how much filesystem I/O accompanies each call.

**Causal diff evidence:** RIGHT lines 326-327 newly refuse to cache metadata when fetchUrls.length===0; before the PR each resolved repoMetadata was inserted directly into \_repoRootCache.

A newly initialized or intentionally local-only repository subjected to a bulk file search/index now performs one Git repository lookup per returned file; repeated checks of the same file also miss the verdict cache. For an unopened repository each lookup can additionally stat the path, ask Git for its root, and read .git/config. Whole-workspace indexing can reach 100,000 files or all files, causing severe I/O/API fan-out and startup delay.

**Evidence:** Line 326 makes cacheRepoMetadata return for an empty fetchUrls list. isIgnored calls getRepositoryFetchUrls on every \_repoRootCache miss, while repoSettled=false also prevents negative verdict memoization. The production Git implementation may perform workspace.fs.stat, getRepositoryRoot, and workspace.fs.readFile(.git/config). Tests added by this PR explicitly assert two calls for two files in a no-remote repo, and workspace indexing enumerates up to 100,000/all files.

**Suggested direction:** Negative-cache/coalesce the empty-remote resolution by repository root with a short expiry or invalidate it from a repository/remote-state event. This preserves eventual remote discovery while bounding Git resolution to once per repository per refresh interval instead of once per file.

### 2. [medium] Preserve the no-regex fast path for file searches

**Finding ID:** `PERF-E50A24E1275A`  
**Location:** <code>extensions/copilot/src/platform/search/vscode-node/searchServiceImpl.ts:43</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Promise, closure, and array allocations plus repeated enablement/cache/glob-check CPU work.  
**Scaling:** O(N) extra work for N provider results; realistic N reaches 100,000 files, while external reconciliation can request every file.  
**Outcome:** Increased indexing latency, CPU usage, allocation, and GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The method returned provider results directly whenever isRegexExclusionsEnabled was false, avoiding per-resource promises and duplicate rule evaluation.  
**Changed behavior:** findFiles now post-filters every provider result through isCopilotIgnored even when exclusion is disabled or all loaded rules are globs already passed to the provider.  
**Confidence:** 0.99 — The removed guard and eager O(N) helper are explicit, as are production cardinalities. Only exact duration varies by workspace.

**Causal diff evidence:** RIGHT line 43 replaces the previous conditional no-regex return with unconditional filterIngoredResources; the same change exists in findFilesWithDefaultExcludes.

Large workspace enumeration now allocates and awaits one queued promise per file and builds additional arrays. With the 100,000-file local-index default, this adds startup CPU, GC pressure, and latency without changing results in disabled or glob-only configurations.

**Evidence:** Line 43 unconditionally calls filterIngoredResources after the exclusion glob was supplied to super.findFiles. That helper eagerly maps the entire array into Limiter jobs and Promise.all. The removed pre-diff guard returned results when \!isRegexExclusionsEnabled; workspace indexing uses the same search service at high cardinality.

**Suggested direction:** After rules are loaded and globs are passed to the provider, return directly when \!isRegexExclusionsEnabled; reserve per-resource post-filtering for content/regex rules.

### 3. [high] Avoid waiting 30 seconds when Git discovery is unavailable

**Finding ID:** `PERF-552DCEAF42E3`  
**Location:** <code>extensions/copilot/src/platform/git/vscode-node/gitServiceImpl.ts:202</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Wall-clock time waiting on Git extension initialization/discovery and pending search requests.  
**Scaling:** The delay is a fixed 30 seconds on the cold unavailable-Git path; it is shared rather than multiplied by callers, but it blocks every concurrent exclusion-dependent search during that interval.  
**Outcome:** Blocked search critical path and cold-search timeout.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The method immediately read the current Git API and returned undefined when the extension/API was unavailable, so content-exclusion checks were not blocked on Git initialization.  
**Changed behavior:** Every getRepositoryFetchUrls call now waits for global initial Git discovery before it can return, with a shared 30-second timeout when discovery never settles.  
**Confidence:** 0.98 — The changed ordering and both timeout constants are explicit, and the extension activation-failure/null-service paths that never settle the observable are directly implemented. Only the prevalence of those environments is uncertain.

**Causal diff evidence:** RIGHT line 202 newly executes await this.waitForInitialDiscovery() before the prior immediate API availability check; the same diff defines that wait with a 30,000 ms timeout.

With content exclusion enabled and vscode.git missing or activation failing, the first file or text search blocks in its first exclusion check for the full 30 seconds. The Copilot text-search tool has a 20-second timeout, so that cold search times out before this wait completes; concurrent callers all wait on the same promise.

**Evidence:** The added await at line 202 precedes even getExtensionApi(). waitForInitialDiscovery uses INITIAL\_DISCOVERY\_TIMEOUT\_MS=30,000 and only resolves earlier when \_isInitialized changes. GitExtensionServiceImpl returns from a failed activate() without firing onDidChange, and NullGitExtensionService exposes Event.None, so those supported unavailable/failure paths leave \_isInitialized false. findTextInFilesTool independently times searches out after 20,000 ms.

**Suggested direction:** Keep pending discovery off the search critical path: when the Git API is unavailable/pending, return an unsettled result that RemoteContentExclusion does not memoize (it already gates negative caching on initialization), or explicitly settle immediately for unavailable/failed activation. Do not use a 30-second wait that exceeds the caller's timeout.

### 4. [medium] Pipeline content checks for streamed text results

**Finding ID:** `PERF-5282998B23D9`  
**Location:** <code>extensions/copilot/src/platform/search/vscode-node/searchServiceImpl.ts:103</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Filesystem open/read/close operations and SHA-256 computation for each cold unique matching file.  
**Scaling:** Cold cost grows linearly with the number of unique result URIs (cached repeat matches in the same file are cheap), with effective filesystem concurrency fixed at 1 despite RemoteContentExclusion's file-read limiter allowing 10.  
**Outcome:** Reduced streaming throughput, delayed first/subsequent results, and search timeout risk.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** findTextInFiles2 directly returned the provider stream and did not insert per-result work into its critical path. The existing non-streaming exclusion paths either batch checks or use limiters with greater concurrency.  
**Changed behavior:** The new streamed text-search wrapper awaits isCopilotIgnored inline before requesting and yielding the next result, making all exclusion checks effectively single-threaded.  
**Confidence:** 0.97 — Sequential control flow and the transitive filesystem boundary are explicit, as are realistic result caps. The exact delay depends on cache warmth and filesystem latency, which affects severity rather than mechanism confidence.

**Causal diff evidence:** RIGHT line 103 introduces an awaited exclusion check inside the sequential async-generator loop; no such work existed in the previous findTextInFiles2 path.

When content regex rules are loaded, the first result for each matching file opens, reads up to 1 KiB, and closes that file before the stream advances. The find-text tool can request up to 1,001 grep-style results, so a broad search across distinct files serializes hundreds of filesystem operations and can consume its 20-second timeout, especially on remote filesystems.

**Evidence:** Line 103 awaits each isCopilotIgnored inside a for-await loop. RemoteContentExclusion routes content rules through readFileFromTextBufferOrFS, which opens, reads, and closes the file and then hashes it. The tool caps ordinary results at 200 but grep mode requests 5× that plus one; all work is on the collection critical path.

**Suggested direction:** Use a small bounded look-ahead pipeline for exclusion checks (reusing a limiter near the existing 10/20 limits), preserve provider order when yielding, and cancel queued work once maxResults or the caller token is reached.
