# Performance review: Add opt-in auto-archive inactive sessions with merged pull requests

[PR #334341](https://github.com/microsoft/vscode/pull/334341) at `597a753b6fa15d563544dcaacd743bc4b5520fd9`

## Findings (3)

### 1. [medium] Resolve pull request state before restoring candidate sessions

**Finding ID:** `PERF-830BEC7DDDC1`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionLifecycle.ts:151</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** provider chat runtimes, transcript bytes/objects, filesystem reads, and session-state allocations  
**Scaling:** Cost grows with both the number of inactive pull-request sessions and the total size of their chat histories; sessions beyond the default residency limit of 10 are repeatedly restored and evicted on later passes.  
**Outcome:** Recurring CPU/I/O and GC pressure, plus provider-session residency churn that can interfere with active agent work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, an inactive nonresident session was restored when a user or existing feature actually needed its full live chat state; there was no hourly background hydration of all stale pull-request sessions.  
**Changed behavior:** Every cleanup candidate is fully restored before the lifecycle service performs the authoritative core GitHub refresh that determines whether any archive/delete action is possible.  
**Confidence:** 0.99 — The ordering and heavy restore call path are directly traced, as are the residency limit and full transcript fetch. Provider-specific restore latency is uncertain, but the allocation/I/O work and candidate/history scaling are not.

**Causal diff evidence:** RIGHT line 151 introduces full AgentService restoration on the new startup/hourly candidate path before the changed code knows whether the designated pull request is merged.

With cleanup enabled, old sessions whose pull requests are still open are cold-restored every lifecycle pass merely to discover that no action is needed. AgentService restoration activates provider metadata, materializes the default provider chat, calls provider.chats.getMessages for the whole transcript, hydrates contributions, and reads session databases. Restores touch residency and reconcile against a default limit of 10, so a catalogue with many candidates churns restored sessions; archived sessions are immediately release-eligible and can repeat this work each pass. Users can see periodic CPU/disk spikes and memory/GC pressure proportional to accumulated histories.

**Evidence:** The added \_evaluateCandidate starts with restoreSession at line 151, while resolveForLifecycle is not called until after restoration. AgentService.\_restoreSessionState calls agent.materializeChat and \_getChatMessages; \_getChatMessages fetches all provider turns and hydrates them. AgentSessionResidency retains only 10 sessions by default and treats archived sessions as always release-required. The authoritative PR operation itself needs only the designated PR URL/core state, already present in IAgentSessionMetadata used by \_isCandidate.

**Suggested direction:** Let the new lifecycle resolver accept the designated PR identity/branch from IAgentSessionMetadata and perform the core refresh without live session hydration; restore (and hold) the session only after a merged result, immediately before revalidation and the archive/delete action.

### 2. [medium] Do not rerun cleanup for unrelated root configuration changes

**Finding ID:** `PERF-143EAF12DECA`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionLifecycle.ts:64</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub API requests, provider restores, and catalogue filesystem operations  
**Scaling:** Each unrelated root-config event fans out into one lifecycle evaluation per stale pull-request candidate, including one authoritative GitHub core refresh per effective candidate after catalogue work/restoration.  
**Outcome:** Unnecessary network/API consumption and repeated background CPU/I/O whenever unrelated Agent Host settings change.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this listener was added, changing an unrelated Agent Host root setting did not start a merged-session cleanup scan or issue lifecycle GitHub refreshes.  
**Changed behavior:** The new listener schedules an immediate cleanup pass for every onDidRootConfigChange event, although that event is unkeyed and explicitly fires for every root-config key, not only the two lifecycle thresholds.  
**Confidence:** 0.98 — The event's all-keys semantics and the lifecycle call path to authoritative network refresh are explicit. The number of unrelated edits varies by workflow, so prevalence affects severity rather than mechanism confidence.

**Causal diff evidence:** RIGHT line 64 newly maps every root configuration notification to \_schedule(0), materially increasing lifecycle-pass and GitHub-refresh frequency beyond startup/hourly and beyond changes to the feature's own settings.

Once either cleanup threshold is enabled, changing settings such as proxy, sandbox, MCP, model, migration, or provider setup values can trigger a full catalogue pass and authoritative refreshes for all stale PR sessions. For users with many inactive sessions this converts a single unrelated setting update into N GitHub requests and session restores, consuming rate limit and causing avoidable background latency.

**Evidence:** RIGHT line 64 subscribes directly to the unfiltered Event&lt;void&gt;. IAgentConfigurationService documents that the event fires whenever any RootConfigChanged action is processed, and another service in the same subsystem explicitly notes it fires for every root-config key and compares its own relevant value before reacting. AgentHostSessionLifecycle.run then lists sessions and serially calls resolveForLifecycle, whose subscription.refresh('core', ..., { authoritative: true }) reaches a GitHub core fetch.

**Suggested direction:** Cache the last validated archive/delete threshold pair and schedule an immediate pass only when one of those two values actually changes; ignore root-config events whose effective pair is unchanged.

### 3. [medium] Filter cleanup candidates before rebuilding the full catalogue

**Finding ID:** `PERF-5979444802F1`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionLifecycle.ts:117</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** provider metadata operations and per-session filesystem/database reads  
**Scaling:** Each enabled startup/hourly pass performs O(total registered sessions) provider metadata work and database stats/reads, even when zero sessions are old enough or have a pull request.  
**Outcome:** Repeated background filesystem/provider I/O and CPU work, with user session-list requests able to wait on the same in-flight catalogue computation.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, enabling no cleanup lifecycle meant Agent Host did not periodically call listSessions; full catalogue computation occurred only for existing consumers such as an actual session-list request.  
**Changed behavior:** The new scheduled lifecycle pass calls AgentService.listSessions before applying any cutoff or pull-request filtering, at startup, hourly, and after scheduled configuration/provider events.  
**Confidence:** 0.98 — The recurring schedule, unconditional call, and transitive provider/database operations are explicit. Exact elapsed time varies by provider cache warmth and catalogue size, which affects severity but not the O(total sessions) repeated-work mechanism.

**Causal diff evidence:** RIGHT line 117 adds the unconditional full-catalogue call to the new recurring lifecycle path; candidate filtering begins only on the following loop, so the diff directly puts all-session provider and database work on every pass.

Users who opt into cleanup and retain a large session history now pay a complete catalogue rebuild every hour even if there are no cleanup candidates. AgentService.\_computeSessions prewarms each involved provider, reads metadata for every registered session, then stats/opens every per-session database for overlays; its own comments identify those operations as the dominant cost on large catalogues. This can create recurring disk/provider activity and delay a concurrent user-triggered listing that joins the shared computation.

**Evidence:** The added run() calls \_accessor.listSessions() at line 117 and only then invokes \_isCandidate. The accessor is AgentService.listSessions(None); its \_computeSessions enumerates all registered sessions, prewarms provider bulk metadata, runs \_registeredSessionMetadata for every entry with a limiter, and performs tryOpenDatabase/getMetadataObject for every returned session. The scheduler starts immediately and reschedules every hour while either setting is enabled. Thus the expensive work is collection-wide rather than candidate-wide.

**Suggested direction:** Add a cutoff-aware lifecycle candidate enumeration that first filters registry entries by external/modified state and reads only the archived/provenance and GitHub metadata needed for survivors (folding provenance into the existing metadata batch where applicable), rather than invoking the presentation-oriented full listSessions computation on every tick.
