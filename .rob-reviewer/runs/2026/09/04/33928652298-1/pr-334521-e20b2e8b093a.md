## Findings (1)

### 1. [medium] Cancel fallback mode discovery with the draft lifecycle

**Finding ID:** `PERF-42C46C5674C8`  
**Location:** <code>src/vs/sessions/contrib/providers/copilotChatSessions/browser/copilotChatSessionsProvider.ts:1919</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** ChatModes instances, global event listeners, pending custom-agent discovery promises, and captured session/provider objects  
**Scaling:** For every fallback Automation draft or scheduled run whose saved mode is not immediately found, one independent ChatModes refresh is created. If discovery stalls, retained objects and listeners grow linearly with subsequent runs; simultaneous runs also issue concurrent discovery requests.  
**Outcome:** unbounded retained memory and listener/IPC growth while custom-agent discovery is stalled  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Fallback Automations supplied modeId through the management service's post-create setMode path. The provider performed a synchronous lookup with a temporary ChatModes instance and disposed it immediately, so no pending refresh survived the call.  
**Changed behavior:** Initial Automation configuration now launches \`\_resolveAutomationSessionMode\` with \`void\`; that method owns a ChatModes instance but disposes it only after \`waitForPendingUpdates()\` settles, with no timeout or cancellation tied to deletion, replacement, send completion, or provider disposal.  
**Confidence:** 0.97 — Ownership and cleanup are explicit in the added method, and ChatModes cancellation occurs only in dispose. The trigger depends on slow or hung discovery, but extension-host/customization discovery is a real asynchronous boundary and recurrence makes the retention scaling deterministic once it stalls.

**Causal diff evidence:** RIGHT line 1919 adds the unbounded \`await modes.waitForPendingUpdates()\` in a newly added fire-and-forget resolver; cleanup is reachable only after that await settles.

If custom-agent discovery is hung or delayed by an unavailable/restarting extension host, each older-host/browser Automation run using an unresolved provider/custom mode leaves another ChatModes object, subscriptions, refresh token, and session closure alive. Recurring Automations then cause renderer memory and listener counts to grow for the lifetime of the stalled discovery.

**Evidence:** The added caller at line 1753 fire-and-forgets \`\_resolveAutomationSessionMode\`. At lines 1917-1930 the method creates ChatModes, awaits its pending refresh, and only disposes in \`finally\`. ChatModes registers global customization, storage, configuration, and agent listeners; its \`dispose()\` is what cancels \`\_refreshCancellationSource\`. Because no owner can dispose this local instance while the await is pending, cancellation is circular. \`waitForPendingUpdates\` awaits customizationHarnessService.getCustomAgents, an asynchronous extension/customization boundary.

**Suggested direction:** Register the resolver/ChatModes instance with the draft or provider lifecycle and race pending discovery with that cancellation (and a bounded timeout). Dispose it immediately when the draft is replaced, deleted, committed, or the provider shuts down; also coalesce discovery where multiple runs resolve the same session scope.
