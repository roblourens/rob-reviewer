**Relevant issue families:** serialization-allocation, boundary-fanout

### Scenario 1: Workbench startup and configuration refresh resolving experiment-backed settings

- Critical path: On a cold start, the first treatment request awaits the shared TAS client initialization and initial fetch; subsequent setting reads use the populated in-memory client. Telemetry payload cleaning and appender dispatch happen synchronously after each treatment result but the diff only changes how one already-present property is represented.
- Scaling input: Cost scales with the number of experiment-backed configuration properties processed and with scoped-key fallback misses. The diff preserves the existing O(number of telemetry properties) copy and adds only one constant-time conditional/object allocation for the matching property; it may avoid regex cleaning of that string.
- Effective concurrency: Experimental settings are processed sequentially by processExperimentalSettings. All cold treatment reads share the same tasClient/initialFetch promise, so there is one effective initial assignment fetch rather than one network request per setting. Telemetry dispatch remains one postEvent path per tas-client query with the existing appender fan-out.
- Cache behavior: Cold treatment access awaits the shared initial fetch; warm accesses read the TAS client's in-memory assignments. Client replacement resets that cache generation, while normal feature-query telemetry is not cached or coalesced. The changed trusted wrapper neither changes TAS cache keys nor negative-cache behavior.
- Mechanism confidence: High: the changed helper, treatment callers, shared initial-fetch promise, cleaner, IPC client, and telemetry appender path were directly traced.
- Magnitude uncertainty: The exact number of registered experiment-backed settings and configured telemetry appenders varies by product build, but neither cardinality nor concurrency is changed by this PR.
- Expensive boundaries:
  - network at <code>src/vs/workbench/services/assignment/common/assignmentService.ts:348 assignmentsFetch and setupTASClient</code>: Fetch legacy/new TAS assignments used by all treatment reads.; cardinality: One coalesced initial fetch per TAS client generation, plus existing timer/filter-driven refetches; not one fetch per queried setting.
    - Introduced by diff: false; previous behavior: The same TAS initialization, assignments request, cache, and refetch behavior existed before the payload-wrapping change.; critical-path effect: The cold first treatment waits for initialFetch; warm reads do not cross this network boundary.
  - IPC at <code>src/vs/platform/telemetry/common/telemetryIpc.ts:35 TelemetryAppenderClient.log</code>: Forward each cleaned telemetry event to telemetry appenders.; cardinality: One existing appender call per emitted query event per configured IPC appender; scoped lookup can avoid the bare fallback, while a miss can cause a second tas-client query event.
    - Introduced by diff: false; previous behavior: Each query event already traversed publicLog, cleaning, and appender dispatch; the diff adds no event or appender call.; critical-path effect: Fire-and-forget channel dispatch occurs after treatment resolution and does not gate returning the treatment.
  - network at <code>src/vs/platform/telemetry/common/1dsAppender.ts:128 AbstractOneDataSystemAppender.log</code>: Queue the existing cleaned event in the telemetry SDK for backend transmission.; cardinality: Unchanged one tracked event per emitted query event and configured 1DS appender; SDK transport batching is unchanged.

- Verdict: No reportable regression. The runtime loop and telemetry boundaries already existed; marking one value trusted adds bounded constant work and skips cleaner regex work without increasing calls, retained state, or critical-path I/O.

### Scenario 2: GitHub Copilot extension reading TAS feature variables and emitting query telemetry

- Critical path: Treatment reads synchronously consult the initialized delegate's in-memory assignments, first using the /vscode/-scoped key and then the bare key on a miss. The tas-client query telemetry then traverses BaseTelemetryService.postEvent and existing Microsoft reporters; initial assignment fetching is managed separately by the delegate and is unchanged.
- Scaling input: Work scales with the number of feature-variable reads and scoped-key misses. Per emitted event, the diff adds one property lookup, type check, and short-lived wrapper allocation; payload size and sender count remain unchanged, while downstream cleaning can skip work for that value.
- Effective concurrency: Each caller performs synchronous in-memory reads. Delegate initialization/refetch owns the existing network concurrency. postEvent keeps its existing two sender invocations: the internal reporter is a no-op for non-internal users, while the external reporter queues the event; the PR adds no parallel request or queue.
- Cache behavior: Assignments are cached in the tas-client delegate and shared across feature reads. Scoped and bare names remain distinct lookup keys, with bare fallback only on a scoped miss. Query telemetry itself remains uncached. The trusted-value object is event-local and not retained.
- Mechanism confidence: High: the changed postEvent method, scoped fallback, delegate cache lifecycle, reporter construction, and sender fan-out were directly inspected.
- Magnitude uncertainty: Exact query frequency varies with enabled Copilot features and account type, but the added work is constant and event-local even at high lookup counts.
- Expensive boundaries:
  - network at <code>extensions/copilot/src/platform/telemetry/node/baseExperimentationService.ts:220 \_createDelegate</code>: Initialize/refetch TAS assignments used by feature reads.; cardinality: One initial fetch per delegate generation plus existing polling/filter-driven refreshes, shared by feature lookups.
    - Introduced by diff: false; previous behavior: Delegate creation, caching, and assignment network requests are unchanged.; critical-path effect: Initialization can gate callers that explicitly await hasTreatments, but ordinary getTreatmentVariable reads are in-memory; the changed postEvent logic does not move assignment fetching onto either path.
  - network at <code>extensions/copilot/src/platform/telemetry/common/baseTelemetryService.ts:205 postEvent via BaseMsftTelemetrySender</code>: Queue the existing query event to external Microsoft telemetry and, for internal users, the existing raw internal reporter.; cardinality: Unchanged one external sender call per query event and at most one additional internal sender call for internal users; scoped misses may already produce an additional query event through the bare lookup.
    - Introduced by diff: false; previous behavior: Both sender calls and their destination fan-out existed before the PR. The change only wraps the already-present queried-feature string before those calls.; critical-path effect: Reporter methods are invoked synchronously but no promise is awaited by the feature read; transport remains off the read's awaited critical path.
- Verdict: No reportable regression. There is no new network/IPC boundary, concurrency burst, retained collection, or scaling payload transformation; the constant wrapper allocation is not actionable and can reduce cleaner CPU.
