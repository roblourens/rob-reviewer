## Findings (1)

### 1. [medium] Keep the incremental rewrap path enabled

**Finding ID:** `PERF-D6DF762FB5F8`  
**Location:** <code>src/vs/editor/common/viewModel/monospaceLineBreaksComputer.ts:46</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and line-break arrays/ModelLineProjectionData objects  
**Scaling:** On each viewport-width change, the extra work grows with every character in every previously wrapped model line; repeated resize events rerun the full model-wide scan and allocations synchronously.  
**Outcome:** increased resize latency, main-thread blocking, and GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** When only the wrapping column changed, ViewModelLines passed each model line's prior projection data into the monospace line-break computer, which used createLineBreaksFromPreviousLineBreaks to search near existing breakpoints and reuse the projection object and pooled offset arrays.  
**Changed behavior:** With forceFullwidthCharacterWidth enabled, the added condition rejects prior projection data unconditionally and sends every wrapped line through createLineBreaks, which scans the complete line and allocates fresh break-offset arrays and a new ModelLineProjectionData.  
**Confidence:** 0.99 — The synchronous resize/configuration call path, model-wide cardinality, bypass condition, full-line scan, and fresh allocations are all explicit in the code. Only prevalence and exact stall duration vary with use of the opt-in setting and document size.

**Causal diff evidence:** The added \`&& \!forceFullwidthCharacterWidth\` on line 46 is the sole gate that bypasses the existing previous-line-break reuse path whenever the new option is enabled.

In a large CJK/Markdown document with viewport word wrap and this new option enabled, dragging a panel or resizing the editor synchronously reconstructs all model lines on every wrapping-column update, causing avoidable UI stalls and GC pressure.

**Evidence:** ViewModelLines.setWrappingSettings recognizes a wrapping-column-only change, collects projection data for all model lines, and synchronously calls \_constructLines; \_constructLines queues every model line before finalize. The changed condition at line 46 discards that cache solely because the option is true. The full path loops from startOffset through lineText.length and allocates two arrays plus ModelLineProjectionData, while the existing incremental path searches around prior offsets and explicitly reuses the object and pooled arrays (noted in code as materially reducing GC pauses). Forced width is exactly two columns, so that path can operate with an effective full-width column count of 2.

**Suggested direction:** Retain the previous-data branch and call createLineBreaksFromPreviousLineBreaks with \`forceFullwidthCharacterWidth ? 2 : columnsForFullWidthChar\`; add a resize/previousLineBreakData test with the option enabled to preserve the exact two-column semantics.
