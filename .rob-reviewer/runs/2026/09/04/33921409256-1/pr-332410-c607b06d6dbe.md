# Performance review: agentHost: centralize session and chat catalog metadata

[PR #332410](https://github.com/microsoft/vscode/pull/332410) at `c607b06d6dbec2888b4ff59bd366acfd883919e3`

## Findings (1)

### 1. [high] Coalesce catalog writes for summary bursts

**Finding ID:** `PERF-B72480E1577D`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:749</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Per-session and host-wide SQLite reads/transactions, catalog payload serialization, and queued promise objects  
**Scaling:** Cost grows linearly with the number of summary notifications across active sessions; each status, activity, modified-time, title, project, changes, or metadata update queues a complete projection even when later notifications supersede it before persistence finishes.  
**Outcome:** Excessive filesystem I/O and serialization, contention on the host-wide database sequencer, queued-write backlog, and increased latency for registry/list operations and session teardown  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Session summary changes updated the existing modified-time/list notification paths but did not enqueue a complete per-session catalog projection and central database synchronization for every emitted summary delta.  
**Changed behavior:** The new unconditional callback sends every \`onDidChangeSessionSummary\` event to \`\_queueCatalogSync\`. That method immediately creates and retains a distinct \`\_persistListVisibleSessionStateNow\` promise; it does not merge an update into an existing pending write.  
**Confidence:** 0.98 — The event source, added call, absence of coalescing, complete SQLite call path, global serialization, and teardown wait are directly traced in code. Exact wall-clock impact varies with tool-event rate and storage speed, but the multiplied boundary work and queue growth are deterministic.

**Causal diff evidence:** RIGHT line 749 is the newly added unconditional \`\_queueCatalogSync(URI.parse(session), {})\` call in the existing summary-change listener; this is the exact change that moves full catalog persistence onto every summary-notification event.

A tool-rich agent turn produces repeated summary status/activity/timestamp changes (the notifier can flush every 100 ms), and concurrent active sessions multiply them. Every change opens \`session.db\`, reads all catalog metadata, canonicalizes/hashes the full payload, writes the local pending snapshot and compatibility metadata, upserts \`agent-host.db\`, acknowledges the local snapshot, and marks the central row dirty. These writes are serialized per session and host-wide, so bursts can build a disk-I/O backlog and delay list/registry work or deletion, which explicitly waits for all background catalog writes.

**Evidence:** \`AgentHostStateManager\` uses a 100 ms \`SessionSummaryNotifier\` and emits deltas whenever summary fields change. The added line 749 invokes \`\_queueCatalogSync\` unconditionally for each delta. \`\_queueCatalogSync\` at lines 1705-1733 starts a new \`\_persistListVisibleSessionStateNow\` for every call and merely stores all promises in a Set. That method calls \`synchronizeWithFactory\`, whose path opens the session database, reads metadata, serializes the aggregate, performs local snapshot/metadata writes, central \`upsertSessionV2\`, acknowledgement, and dirty-marker writes. \`AgentHostDatabase\` routes all central writes through one \`\_transactionSequencer\`, and \`\_whenBackgroundCatalogStateWritesIdle\` waits for every queued promise before deletion.

**Suggested direction:** Keep at most one in-flight catalog write and one merged trailing update per session. Merge metadata overrides and rebuild the trailing projection from the latest state when the in-flight write settles; preserve the existing ordered/teardown flush paths by awaiting that coalesced drain.

- Effective concurrency: Central row reads and fallback resolution each use a limiter of 4. Concurrent list calls for the same mode share one in-flight computation, with at most one trailing recomputation after registry invalidation.
- Cache behavior: A verified current-version central payload is the warm-cache entry. ### Scenario 3: Live session summary updates during active agent turns

- Critical path: Summary notifications do not await persistence, so agent streaming can initially progress, but every emitted delta immediately queues a full catalog sync. Host-wide catalog writes serialize with registry/list database operations, and session deletion/residency waits for the queued per-session writes to drain.
- Scaling input: Number of list-visible summary changes per turn (status, activity, modified time, title, project, changes, working directories, and metadata) multiplied by concurrently active sessions; the notifier can emit at 100 ms intervals.
- Effective concurrency: No latest-state coalescing exists. Every event creates a promise; synchronization is serialized per session, while all central writes share the single AgentHostDatabase transaction sequencer. Multiple sessions can prepare work concurrently but contend at the central boundary.
- Cache behavior: Each sync rereads session metadata and rebuilds the full canonical payload. Acknowledged receipts can avoid some replacement work only after entering the sync path; the callback still queues every intermediate snapshot, and dirty markers force later verification.
- Mechanism confidence: Very high: the added event callback, promise Set, full sync path, global sequencer, and teardown wait are directly traced.
- Magnitude uncertainty: Tool/event rate and filesystem latency determine backlog duration, but the one-full-sync-per-delta multiplier and lack of coalescing are deterministic.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts:\_queueCatalogSync/\_persistListVisibleSessionStateNow and agentHostCatalogSyncService.ts</code>: Open session.db, read catalog metadata, write compatibility metadata and pending snapshot, then acknowledge it; cardinality: One complete sequence per emitted summary delta, with no coalescing; M deltas produce M sequences
    - Introduced by diff: true; previous behavior: Summary notifications did not perform full catalog projection persistence.; critical-path effect: Fire-and-forget for streaming, but queued work delays teardown and competes for local I/O
  - serialization at <code>src/vs/platform/agentHost/node/agentHostCatalogSourceResolver.ts and agentHostCatalogProjection.ts</code>: Construct, canonicalize, serialize, and hash the full session/chat catalog payload; cardinality: Once per queued summary delta, including superseded intermediate states
    - Introduced by diff: true; previous behavior: No central payload was rebuilt for every summary notification.; critical-path effect: Consumes Agent Host CPU and allocations alongside active turns
  - database at <code>src/vs/platform/agentHost/node/agentHostCatalogSyncService.ts and agentHostDatabase.ts</code>: Dirty-marker transactions and serialized sessions\_v2 upsert in agent-host.db; cardinality: Multiple host-database operations per summary delta; all active sessions share one transaction sequencer
    - Introduced by diff: true; previous behavior: The summary path performed only its existing modified-time/list notification work, not central catalog synchronization.; critical-path effect: Can delay unrelated registry/list writes and contributes to the teardown drain
- Verdict: Reportable high-severity missing-coalescing regression; submitted as a finding.

### Scenario 4: Peer-chat creation, compatibility mirroring, and title hydration

- Critical path: Creating or changing membership must commit the central chat catalog, mirror changed chat-local metadata, and write the legacy parent-session peerChats payload. Hydration uses an already-cached title without I/O; otherwise it reads chat-local title metadata before the parent compatibility mirror.
- Scaling input: Number of peer chats in one session and number changed in a membership revision; imported lists and catalog payload children are bounded by defined limits.
- Effective concurrency: Membership writes serialize per parent session. Changed chat-local metadata writes use a limiter, while the central host database globally serializes transactions. Title hydration reads are sequential for the addressed chat only.
- Cache behavior: Central membership is authoritative and revisioned. Matching mirrored revisions avoid compatibility repair. Cached catalog titles bypass chat/session metadata reads; missing chat-local titles fall back to the parent mirror.
- Mechanism confidence: High: central revisions, per-session sequencing, limited per-chat writes, and cached-title early return are explicit and tested.
- Magnitude uncertainty: Typical peer counts and frequency of legacy-title misses vary, but catalog limits and cached-title bypass bound the path.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostPeerChatStore.ts and agentHostDatabase.ts</code>: Replace revisioned central peer-chat membership and mark the legacy mirror revision; cardinality: One central replacement per membership mutation, plus mirror bookkeeping; retries only on revision conflict
    - Introduced by diff: true; previous behavior: Peer membership lived in one parent session metadata value.; critical-path effect: Creation/membership mutation waits for authoritative central replacement
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostPeerChatStore.ts:\_publishCompatibilityState/\_writeChatMetadata/\_writeLegacyMirror</code>: Write provider/origin/inherited-turn metadata to changed chat databases and peerChats to the parent session database; cardinality: One chat database write per changed peer plus one parent mirror write, with bounded concurrency
    - Introduced by diff: true; previous behavior: The parent peerChats metadata was written without central membership and chat-local mirroring.; critical-path effect: Compatibility publication may continue/retry after central authority is committed depending on caller path
  - filesystem at <code>src/vs/platform/agentHost/node/chatContributions/sessionTitle/sessionTitleContribution.ts:hydrateChat</code>: Read chat-local title, then parent compatibility title on a miss; cardinality: Zero reads for a cached title; otherwise one chat database read and at most one parent database read for the addressed chat
    - Introduced by diff: true; previous behavior: Hydration read only the parent-session compatibility title.; critical-path effect: Blocks hydration only when catalog/restored state did not already provide a title
- Verdict: No reportable regression: added I/O is bounded to membership mutations or cache misses and is required for the new authoritative/compatibility ownership model.
