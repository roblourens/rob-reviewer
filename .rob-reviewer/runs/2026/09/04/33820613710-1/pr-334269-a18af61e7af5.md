- Critical path: The BlockRestore constructor synchronously creates observables/listeners and schedules updateNewSessionButtonStyle, but does not await it; restore and initial button rendering can proceed with the default style. The async treatment result and class update are off the startup critical path.
- Scaling input: Constant per workbench contribution instance, independent of session count; rendered button count does not multiply treatment reads.
- Effective concurrency: The style read may overlap the existing title-bar treatment read, but both share one TAS client and initial fetch; no per-button requests are created.
- Cache behavior: Cold startup may await the assignment service's one shared initial fetch; warm reads resolve from the initialized TAS client's in-memory assignments. An explicit developer setting bypasses getTreatment entirely.
- Mechanism confidence: High: constructor call flow, non-awaited async scheduling, and shared assignment-service implementation were directly inspected.
- Magnitude uncertainty: Exact TAS initialization and telemetry enqueue cost varies by platform and cache state, but the added work is constant and off the critical path.
- Expensive boundaries:

- Verdict: No reportable regression: the diff adds one bounded cached treatment read and telemetry event without adding a network fetch or blocking startup.

### Scenario 3: Experiment assignments refetch while New Session controls are present

- Critical path: After the assignment service completes its own refetch and emits onDidRefetchAssignments, the contribution performs one style getTreatment and the pre-existing title-bar getTreatment. Style changes propagate to mounted controls, but product interaction does not wait for either read.
- Scaling input: Assignment-refetch event frequency, not session or button cardinality; effective style lookup cardinality is one per event.
- Effective concurrency: One style promise and one existing title-bar promise may run together; the request counter discards stale style results if events overlap, while underlying reads remain cached.
- Cache behavior: The refetch has completed before the signal fires, so getTreatment reads the updated in-memory assignment cache. Explicit style configuration still bypasses the treatment read.
- Mechanism confidence: High: event ordering and assignment-service cache/network implementation were directly inspected.
- Magnitude uncertainty: Refetch frequency is externally controlled, but normal polling/filter events are infrequent and each added read is constant.
- Expensive boundaries:
  - network at <code>src/vs/workbench/services/assignment/common/assignmentService.ts:refetchAssignments</code>: Refresh all TAS assignments before onDidRefetchAssignments is emitted.; cardinality: One service-level refetch per filter/poll trigger, shared by all consumers.
    - Introduced by diff: false; previous behavior: Assignment-service polling/filter changes already performed this shared refetch and the contribution already reread the title-bar treatment afterward.; critical-path effect: The network operation precedes the event consumed by this diff and is not introduced or multiplied by the style listener.
  - serialization at <code>src/vs/workbench/services/assignment/common/assignmentService.ts:getTreatment</code>: Serialize and enqueue one telemetry event for the newly reread style treatment.; cardinality: One additional style event per assignment-refetch event, not per button or session.
    - Introduced by diff: true; previous behavior: The refetch already caused the title-bar treatment reread/event, but not the style-treatment reread/event.; critical-path effect: No user workflow waits for it; class updates occur after the cached read.
- Verdict: No reportable regression: no new network fan-out, unbounded burst, or button-count multiplier.

### Scenario 4: Render and dispose the shared New Session action in sidebar and optional title bar

- Critical path: Rendering registers one autorun per action that reads the contribution-wide style and writes two class toggles. Disposing the action disposes the autorun through the view item's Disposable registration.
- Scaling input: One autorun per rendered action, bounded to the two registered menu surfaces.
- Effective concurrency: Synchronous constant-time class writes on render/style changes; no asynchronous fan-out.
- Cache behavior: All actions share the single already-resolved observable; no per-action cache or treatment read exists.
- Mechanism confidence: High: renderer ownership, registration, and disposal were directly inspected.
- Magnitude uncertainty: Whether both surfaces are simultaneously mounted depends on the title-bar experiment, but the upper bound remains two.
- Expensive boundaries: none found
- Verdict: No reportable regression: bounded listeners and correct cleanup prevent retained controls or lifecycle growth.
