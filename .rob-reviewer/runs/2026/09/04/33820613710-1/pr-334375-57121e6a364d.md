## Findings (1)

### 1. [medium] Restore the libc filters for optional native binaries

**Finding ID:** `PERF-928442F489FA`  
**Location:** <code>package-lock.json:255</code> (<code>LEFT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** native-package tarball bytes, extracted files, and filesystem operations  
**Scaling:** On a Linux x64 or arm64 install, each of three native package families now has two eligible same-OS/same-CPU artifacts instead of one; cold \`npm ci\` therefore grows from three matching binary artifacts to six, with one redundant GNU/musl variant per family.  
**Outcome:** increased dependency-install latency, network transfer, disk usage, and extraction I/O on cache misses  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The base lockfile carried \`libc: \[glibc\]\` or \`libc: \[musl\]\` on the Linux variants for \`&#64;anthropic-ai/claude-agent-sdk\`, \`&#64;github/copilot\`, and \`&#64;vscode/os-proxy-resolver\`, so npm could exclude the incompatible variant before fetching and unpacking it.  
**Changed behavior:** This lockfile refresh deletes every \`libc\` selector while retaining both GNU and musl packages as optional dependencies with identical Linux OS and CPU constraints, making both variants eligible in the lockfile's install tree.  
**Confidence:** 0.98 — The before/after lock metadata, parent optional-dependency fan-out, and CI critical path are directly visible. npm lockfile v3 uses these OS/CPU/libc fields to filter optional packages; with libc absent, both same-OS/same-CPU variants are eligible. Exact tarball sizes are unknown, which limits severity rather than mechanism confidence.

**Causal diff evidence:** At deleted lines 255-257 the PR removes the first \`libc: \[glibc\]\` constraint; the same diff removes the paired musl/glibc constraints at old lines 272-274, 289-291, 306-308, 1218-1220, 1237-1239, 1256-1258, 1275-1277, and 4847-4911, without removing either optional package from its parent.

A Linux x64 cache-miss \`npm ci\`—including the root install on component-fixtures and CSS-order-scan CI—downloads and unpacks both x64 variants for all three families before any build or fixture can start. Warm node\_modules-cache hits avoid the install, but fresh developer/CI installs pay the extra binary transfer and disk cost.

**Evidence:** The parent entries enumerate GNU and musl optional dependencies for all three families (\`package-lock.json\` current lines 202-213, 1155-1164, and 4779-4788). After the deletion, each corresponding Linux package retains only \`os: \[linux\]\` and the same \`cpu\` value (for example current lines 246-295, 1199-1268, and 4820-4881), so npm's lockfile platform check can no longer distinguish libc. The component fixture workflows put \`npm ci --ignore-scripts\` on the cache-miss critical path before build/test (\`.github/workflows/component-fixtures.yml:48-60\` and \`.github/workflows/css-order-scan.yml:39-51\`).

**Suggested direction:** Restore the deleted \`libc\` arrays (or regenerate the lockfile with the repository-supported npm version that preserves them) so only the host's GNU or musl artifact is fetched and unpacked.
