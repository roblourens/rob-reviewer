### Scenario 1: Open Agent Customizations &gt; MCP Servers for the first time with MCP access enabled and one or more uncached extension-contributed collections

- Critical path: McpListWidget.setVisible(true) synchronously starts activateCollections and refresh, but both promises are deliberately fire-and-forget, so neither extension activation nor gallery loading must complete before the section can render its current state. Provider results arrive through the MCP service observable and trigger a later refresh.
- Scaling input: U, the number of allowed uncached lazy MCP collections, controls extension activation fan-out; S, the number of discovered server definitions, controls the subsequent reconciliation (including an existing O(S^2) matching loop). Typical effective U is the user's installed MCP-provider collection count.
- Effective concurrency: All U uncached collection loads run concurrently through Promise.all. The gallery request may overlap with activation. There is no new UI-thread await or serialized queue.
- Cache behavior: Only collections with lazy.isCached === false are activated. Successful providers replace their lazy collection with a non-lazy collection; providers that publish nothing are removed, so later discovery has no provider boundary. Cached lazy collections are excluded by existing registry semantics.
- Mechanism confidence: High confidence in the added call path, fire-and-forget placement, Promise.all fan-out, and lazy-collection cache transition based on the changed hunk and registry/discovery implementations.
- Magnitude uncertainty: Extension activation cost and installed provider count vary, and arbitrary extension activation work is not measurable from this diff. The concrete fan-out is generally small and user-initiated.
- Expensive boundaries:

### Scenario 2: Leave and later re-enter the MCP Servers section after collection discovery completed

- Critical path: Each false-to-true visibility transition calls activateCollections and refresh. discoverCollections finds no uncached collections, resolves immediately, and updateCollectedServers reconciles the already materialized definitions; setVisible still does not await it.
- Scaling input: Section navigation frequency R and server count S; the added warm activation wrapper performs registry filtering plus existing server reconciliation per re-entry, with matching cost up to O(S^2).
- Effective concurrency: No provider work after successful discovery. The activation promise and refresh are independently scheduled, but warm activation completes after an empty Promise.all and performs one reconciliation.
- Cache behavior: Successful or empty uncached providers are transitioned out of the unknown set. Gallery snapshot state is retained by the widget. There is no new retained cache or key growth.
- Mechanism confidence: High confidence that warm transitions invoke reconciliation but do not cross the extension-host activation boundary.
- Magnitude uncertainty: Very large MCP server counts are not established as realistic, and the reconciliation avoids observable writes when server identities/order are unchanged.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/mcp/common/discovery/extensionMcpDiscovery.ts:164-167</code>: Extension-host provider activation; cardinality: Zero after successful discovery because no uncached lazy collections remain.
    - Introduced by diff: true; previous behavior: No activation attempt was made from section re-entry.; critical-path effect: No warm boundary call occurs.
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts:1444-1448 and queryGallerySnapshot</code>: Query the MCP gallery snapshot if it is still absent and eligible; cardinality: Normally zero with a warm snapshot; existing state guards bound it to one active request.
    - Introduced by diff: false; previous behavior: The same refresh and cache guards ran on every visible transition.; critical-path effect: Unchanged and asynchronous.
- Verdict: No finding. Although the diff adds repeated warm reconciliation, realistic server cardinality and unchanged observable output do not establish a concrete user-visible regression rather than a minor optimization opportunity.

### Scenario 3: Restore MCP access while the MCP section is already visible

- Critical path: updateAccessState starts provider activation and then immediately starts the pre-existing search query or refresh; neither is awaited by the configuration event handler. The disabled UI can be removed without waiting for providers.
- Scaling input: U uncached lazy collections and, independently, one current gallery query; access restoration is an infrequent user or policy/configuration event.
- Effective concurrency: Provider loads fan out with Promise.all and can overlap the existing single gallery operation. No new limiter exists, but the trigger is explicit/infrequent and collections are cache-bounded.
- Cache behavior: While access is disabled the public registry view is empty but underlying lazy registrations persist. On restoration only uncached unknown collections load; subsequent restorations after successful discovery have no provider IPC.
- Mechanism confidence: High confidence in the configuration listener, access-state branch, asynchronous scheduling, and cache behavior.
- Magnitude uncertainty: The extension activation burden varies by provider, but the event frequency and uncached-state transition bound repeated impact.
- Expensive boundaries:
  - IPC at <code>added src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts:1506 through McpRegistry.discoverCollections and ExtensionMcpDiscovery</code>: Activate allowed uncached extension MCP collections and await initial provider publications; cardinality: One concurrent load per allowed uncached collection U; zero once collections have previously been discovered.
    - Introduced by diff: true; previous behavior: Restoring access only restarted the current gallery search or local refresh; lazy provider extensions remained inactive.; critical-path effect: Introduced by the diff but asynchronous and off the configuration handler's blocking critical path.
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts:1507-1511 and query methods</code>: Run one MCP gallery search for a non-empty query, or load one eligible gallery snapshot for an empty query; cardinality: One current query, with existing cancellation/loading guards.
    - Introduced by diff: false; previous behavior: The same query-or-refresh branch existed before the diff.; critical-path effect: May overlap with provider activation but was already triggered by access restoration.
- Verdict: No finding. The new boundary is necessary to repopulate the visible section after access restoration, is not awaited, and does not recur after successful discovery.
