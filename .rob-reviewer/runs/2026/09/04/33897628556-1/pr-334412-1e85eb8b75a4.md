### Scenario 1: Copilot MCP start/stop for a customization ID that is published in current session state but not yet represented by the SDK live inventory

- Critical path: A client dispatches one session MCP lifecycle action; the reducer updates optimistic state, AgentSideEffects invokes the provider, serverNameForCustomizationId checks the live inventory and then synchronously scans current session customizations. On a match, the provider lifecycle RPC is on the critical path. Start also schedules an inventory-list RPC in its finally block; that refresh is not awaited by the lifecycle promise. Stop awaits its lifecycle RPC.
- Scaling input: The fallback cost grows with the number of current top-level customizations and their MCP children. It runs once per explicit lifecycle action; realistic effective cardinality is one target ID, not one provider call per customization. Existing live entries are checked first, and published-only entries become live after SDK reporting.
- Effective concurrency: Copilot serializes lifecycle RPCs per server name with SequencerByKey; different server names may progress concurrently. The synchronous fallback scan itself is not parallelized and runs once before queueing.
- Cache behavior: The live inventory is the warm fast path. A published-only ID falls back to authoritative session state until the SDK reports it; unknown IDs also scan once and then stop. There is no separate fallback cache or negative cache, but the trigger is a low-frequency user action.
- Mechanism confidence: High: the fallback, call path, per-action cardinality, and per-server sequencer are explicit in the code.
- Magnitude uncertainty: The exact customization count and provider RPC duration vary, but the new local work is one shallow state projection plus one linear flatten/find scan per explicit click. The heavier newly reachable provider operation is intentional functionality rather than redundant work.

  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:3387 and 3511</code>: Copilot SDK startServer or stopServer lifecycle RPC; cardinality: One lifecycle RPC per accepted action, serialized per server name. ### Scenario 2: Codex MCP start/stop for a customization ID published before the thread inventory contains it

- Critical path: A lifecycle action resolves the session, synchronously rebuilds controller state from the current per-thread inventory, refreshes the name-to-ID map, and then uses the new session-state fallback. For start, a successful fallback proceeds through lazy thread materialization, one configuration reload request, and a paginated status refresh. Stop currently performs no provider boundary after successful resolution.
- Scaling input: Resolution scales with current MCP inventory plus published top-level customizations and children. The fallback is one scan for one target ID. Status refresh scales by the provider's paginated server inventory, not by issuing one request per customization.
- Effective concurrency: No lifecycle sequencer is present on the Codex start path; separate accepted actions can overlap. Normal UI dispatch is one action for the selected row, and this diff does not alter concurrency for already-live IDs. Stop performs only local resolution.
- Cache behavior: Current thread inventory populates the live path when available; published-only IDs use current session state. After reload/status refresh, inventory is refreshed and subsequent resolution can use live data. Unknown IDs do not cross provider boundaries.
- Mechanism confidence: High: the synchronous resolver, reload request, pagination loop, and absence of a stop boundary are directly traced.
- Magnitude uncertainty: Provider inventory page count and cold materialization latency vary. The local added scan remains bounded by current published customizations, while the newly reachable expensive work is the intended start behavior.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:1560</code>: Client-to-Agent-Host MCP lifecycle action; cardinality: One inbound action per explicit user request.
    - Introduced by diff: false; previous behavior: Identical protocol dispatch occurred before the diff.; critical-path effect: The action dispatch precedes provider handling and is unchanged by the diff.
  - subprocess at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:7682</code>: Lazily materialize the Codex thread/connection when needed; cardinality: At most once for an unmaterialized session, then reused by later operations.
    - Introduced by diff: true; previous behavior: A published-only unresolved ID returned before materialization; accepted live IDs already followed this path.; critical-path effect: Materialization must finish before reload can proceed on a cold session.
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:7305</code>: Codex config/mcpServer/reload request; cardinality: Exactly one request per accepted start action.
    - Introduced by diff: true; previous behavior: Published-only unresolved IDs did not issue reload; live IDs already issued one reload.; critical-path effect: Awaited on the start critical path.
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:7478</code>: Paginated mcpServerStatus/list inventory refresh; cardinality: One or more requests according to nextCursor; grouping is by the full thread inventory, not per customization.

- Verdict: No reportable performance regression. The fallback only makes the requested lifecycle operation reachable for an exact current ID; it adds no per-item provider fan-out, and the local scan is not a hot path.

### Scenario 3: Lifecycle resolution for an already-live ID or an unknown ID

- Critical path: Already-live IDs return from the existing live-inventory loop before executing the added fallback. Unknown IDs execute the added session-state scan and then return without provider work.
- Scaling input: Live resolution retains its prior behavior. A miss adds one O(C) flatten/find over current MCP customizations, where C is the effective total of top-level MCP entries and MCP children, once per explicit action.
- Effective concurrency: No additional asynchronous work is created for unknown IDs. Provider-specific concurrency behavior is unchanged for live hits.
- Cache behavior: Live hits avoid the fallback on both cold and warm actions. Unknown misses are not negatively cached, but they require repeated explicit invalid actions to repeat the scan.
- Mechanism confidence: High: the early return and fallback placement are explicit in the changed method.
- Magnitude uncertainty: Only unusually large customization collections and repeated invalid lifecycle actions increase the added local CPU/allocation cost; neither is evidenced as a realistic hot path.
- Expensive boundaries: none found
- Verdict: No finding. Existing successful requests incur no new work, and misses add only a bounded in-memory scan with no I/O, IPC, or subprocess operation.

No valid performance finding and no qualifying performance-regression fix signal.
