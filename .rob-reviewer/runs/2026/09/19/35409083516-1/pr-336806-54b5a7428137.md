# Performance review: agentHost: retroactively recognise unmarked crash orphans

[PR #336806](https://github.com/microsoft/vscode/pull/336806) at `54b5a742813792fc6942a2aa2d846c9e48364b11`

## Findings (2)

### 1. [medium] Park unreadable provider catalogs instead of reopening every session

**Finding ID:** `PERF-66F9240D55E0`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:1987</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Per-session filesystem stat calls, SQLite connection opens/migrations on cache misses, and provider metadata resolutions  
**Scaling:** While a registered provider's catalog remains unreadable, reconciliation processes up to 50 dirty sessions per five-minute pass at concurrency 4; with N affected sessions the cursor rotates through them in ceil(N/50) passes and then repeats for the lifetime of the unavailable/deferred catalog.  
**Outcome:** Sustained background filesystem and SQLite I/O, with avoidable CPU and disk/virus-scanner contention every reconciliation interval.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** When provider metadata returned undefined, reconciliation classified the row as sourceUnresolvable, performed at most one tryOpenDatabase attempt, and then excluded the row from subsequent passes via \_parkedSessions until a provider/discovery wake signal or the hourly safety sweep.  
**Changed behavior:** The new readability guard changes the same metadata miss to providerUnavailable. That outcome leaves payloadDirty set and does not park the row, so every periodic pass selects it again; runMigrationExclusive has already called tryOpenDatabase before this classification.  
**Confidence:** 0.97 — The changed branch, database-open ordering, retry scheduling, batch/concurrency bounds, and before/after multiplicity are all explicit in production code and corroborated by focused tests. The only uncertainty is how long a provider catalog remains unreadable and how many affected sessions a profile has, which limits severity rather than mechanism confidence.

**Causal diff evidence:** Added RIGHT line 1987 diverts an undefined metadata result from the pre-existing sourceUnresolvable/park path to providerUnavailable, directly changing one-time storage work into periodic repeated work.

A provider whose SDK/catalog stays deferred or unavailable causes the host to repeatedly stat and reopen session.db files in the background. The repository explicitly identifies these per-session storage accesses as the dominant cost and notes that filesystem/virus-scanner costs vary by an order of magnitude; profiles with many registered sessions sustain a 50-row I/O batch every five minutes.

**Evidence:** \_resolveCatalogReconciliationSource first awaits \_getCatalogReconciliationMetadata and the added lines 1987-1989 return providerUnavailable when the catalog is unreadable. \_reconcileSession reaches that resolver only inside AgentHostCatalogSyncService.runMigrationExclusive, which first calls ISessionDataService.tryOpenDatabase. The real implementation performs IFileService.stat and acquires/opens the SQLite database. \_listDirtySessions excludes only \_parkedSessions; tests prove providerUnavailable opens twice across two passes while sourceUnresolvable opens once and is absent from the second pass. \_scheduleNextPass runs periodic passes at DEFAULT\_INTERVAL\_MS=5 minutes with batch size 50 and concurrency 4.

**Suggested direction:** Represent an unreadable catalog as a deferred/parked source state after the first attempt, and wake/schedule those rows when the provider catalog becomes readable (retaining the existing hourly safety sweep). Alternatively add a cheap preflight that skips tryOpenDatabase when there is neither a readable catalog nor live-session metadata, while preserving retries needed for correctness.

### 2. [medium] Keep retroactive orphan checks off the listing critical path

**Finding ID:** `PERF-E38A1B6D3084`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostCatalogReconciliationService.ts:368</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Per-orphan filesystem stats and SQLite metadata reads for default-chat/session databases plus provider SDK/RPC metadata lookups  
**Scaling:** For M retroactively marked orphans, every non-overlapping listSessions call performs M suppression probes. \_withoutUnmaterializedProvisionalSessions launches them together with unbounded Promise.all, so aggregate I/O/RPC work and burst concurrency both grow linearly with the accumulated orphan count.  
**Outcome:** Higher session-list latency and bursty filesystem/SQLite/provider work on every refresh, defeating the catalog-served fast path for all retroactively marked rows.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** An unmarked historical orphan with an eligible central catalog row was returned by the catalog-served path without provider or session-database reads; the code’s list diagnostics define catalog-served rows as costing neither boundary.  
**Changed behavior:** The new setSessionProvisional call durably adds every confirmed empty historical orphan to \_provisionalSessionKeys. Thereafter every listSessions computation enters \_withoutUnmaterializedProvisionalSessions and calls \_registeredSessionMetadata for each such row before it can suppress it.  
**Confidence:** 0.96 — The durable marker-to-listing call path, repeated list lifecycle, filesystem/SQLite boundaries, Copilot RPC fallback, and unbounded concurrency are explicit in production code. Only the number of historical crash orphans per profile is uncertain, so severity is medium rather than high.

**Causal diff evidence:** RIGHT line 368 newly turns previously unmarked, catalog-served historical rows into durable provisional-marker entries, moving per-row database/provider validation onto every future listSessions critical path for that population.

After reconciliation hides historical crash orphans, each session-list refresh is blocked on probing every hidden row. \_registeredSessionMetadata first calls \_readDefaultChatProviderData, which can stat/open both the default-chat and session SQLite databases, then calls provider.getChatMetadata. For Copilot, these catalog-served rows are not included in fallback prewarming, so getChatMetadata falls back to one getSessionMetadata SDK RPC per orphan. Settled list results are intentionally removed from the in-flight map, so later refreshes repeat the fan-out.

**Evidence:** The added marker write at line 368 is mirrored into \_provisionalSessionKeys by the new callback. \_computeSessions serves eligible central rows without provider/storage reads, but if any provisional key exists it then awaits \_withoutUnmaterializedProvisionalSessions. That method maps all listed rows with Promise.all and invokes \_registeredSessionMetadata for each marked row. \_registeredSessionMetadata awaits \_readDefaultChatProviderData and provider.getChatMetadata; the former performs up to two tryOpenDatabase calls, while CopilotAgent.getChatMetadata performs getSessionMetadata RPC when no prewarmed entry exists. Prewarming is only established for fallbackProviders earlier in the list, whereas these rows are catalog eligible. \_startSessionListComputation deletes settled entries, so this work recurs on subsequent calls.

**Suggested direction:** Persist a distinct “reconciliation-confirmed empty orphan” state that listing can suppress directly, and revalidate it in background reconciliation on provider discovery/materialization/readability wake signals (with the existing periodic safety sweep). Alternatively cache the negative provider result and invalidate it on those same signals, rather than re-running database and provider probes for every list.
