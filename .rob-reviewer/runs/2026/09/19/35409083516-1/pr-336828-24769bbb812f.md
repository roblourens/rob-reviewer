<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, serialization-allocation, boundary-fanout, unbounded-retention, synchronous-ui-work

### Scenario 1: Open the customization editor or refresh migration candidates after prompt, MCP, configuration, harness, or project-root changes

- Critical path: A zero-delay Delayer coalesces same-turn requests, then enabled migration categories compute in parallel; after candidate discovery and destination lookup complete, the new reconciliation synchronously builds candidate-key sets, parses both persisted activity scopes, scans their entries, conditionally stores cleaned state, and only then refreshes the UI. The reconciliation is therefore on the refresh-to-visible-results critical path.
- Scaling input: Work scales linearly with the effective distinct migration candidates plus persisted activity items across the user and active-project scopes. Candidate arrays are grouped by two storage scopes; activity is parsed/scanned once per scope, not once per candidate.
- Effective concurrency: Enabled categories run through Promise.all. Source-folder lookups inside each file category are sequential by distinct target type, while the final destination lookup is parallel by distinct target type. Refresh generations cancel/supersede stale results; there is no growing queue. The added reconciliation is synchronous and single-threaded after all async work settles.
- Cache behavior: Prompt-file lists cache one promise per prompt type and invalidate on locator changes, so duplicate requests across categories coalesce while warm and cold invalidations rediscover files/providers. MCP support uses the active support scope/snapshot. Migration activity itself is read from profile storage on every completed refresh with no object cache; writes occur only when a current candidate matches a prior non-copied activity item.
- Mechanism confidence: High confidence in the added O(candidates + activity-items) synchronous scan, allocation, and two JSON parses; low confidence that its practical magnitude reaches a reportable regression.
- Magnitude uncertainty: Persisted activity has no explicit cap, but it grows only through user-initiated migration batches and the dashboard already parses and rebuilds DOM for that history on refresh. Candidate collections are normally customization-file/server sized. No evidence establishes a realistic history large enough for the added linear scan and two parses to cause visible latency independently of the pre-existing rendering work.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts:computeMigration</code>: Discover prompt/customization files through listPromptFiles and file locators on cold or invalidated caches.; cardinality: At most one effective cold discovery per distinct prompt type because PromptsService coalesces cached promises; enabled categories may request agent/instructions more than once, but warm calls share the same result.
    - Introduced by diff: false; previous behavior: The same category computation and cold/warm file discovery occurred before this change.; critical-path effect: Discovery must finish before candidates can be reconciled and displayed.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts:computeMcpServerMigration and agentCustomizationItemProvider.ts:provideSourceFolders</code>: Wait for active agent-host customizations/MCP support and obtain source folders or an MCP migration plan.; cardinality: One category computation per enabled MCP category and a fixed number of source-folder calls by distinct prompt target type; candidate count does not create per-candidate IPC.
    - Introduced by diff: false; previous behavior: The same support-scope and provider work was already on each completed refresh.; critical-path effect: These async results precede reconciliation and UI refresh.
  - serialization at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts:reconcileMigrationActivity</code>: Parse both profile-storage activity objects; if stale non-copied entries are found, serialize and store the filtered state.; cardinality: Exactly two storage reads per completed refresh and zero to two writes; writes are per affected storage scope, not per activity item.
    - Introduced by diff: true; previous behavior: Candidate refresh did not reconcile or conditionally store activity, although dashboard rendering separately read activity state.; critical-path effect: The parse, scan, and any conditional serialization complete synchronously before migration UI refresh.
- Verdict: No finding. The diff adds repeated linear CPU/allocation work, but it does not add per-candidate boundary fan-out, refreshes are superseded/coalesced, and conditional writes happen only during actual stale-activity cleanup and reduce subsequent retained/rendered state.

### Scenario 2: Record file migration activity and refresh after moving or converting source customizations

- Critical path: The existing migration performs target resolution, user confirmation, file writes/copies/deletes, records activity, and—when originals are deleted—refreshes candidates. The diff adds one URI-based key computation per successfully migrated item before the existing profile-storage write; the later refresh may reconcile reverted activity.
- Scaling input: Key generation and added retained bytes scale once per successfully migrated file. Existing filesystem operations and activity payload size already scale with the selected file count.
- Effective concurrency: File migration behavior is unchanged: selected files are handled by the existing migrateCustomizations helper, and activity key creation is synchronous after results return. No new parallelism or burst is introduced.
- Cache behavior: Target/source-folder providers may use their existing prompt/customization caches. Activity storage appends history and has no explicit cap or deduplication; the new key is stored with the same lifecycle as its existing activity item and is removed when that activity is dismissed/reconciled.
- Mechanism confidence: High confidence that the only changed cost is one key string computation/allocation and retained string per migrated item.
- Magnitude uncertainty: URI/key lengths and selected batch sizes vary, and activity history is uncapped, but the added string is comparable to source/target labels already retained and does not alter write frequency.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts:runCustomizationMigration</code>: Copy/convert selected customization files and optionally delete originals.; cardinality: Scales with selected migrated files according to the existing helper; no extra filesystem operation is caused by migrationKey.
    - Introduced by diff: false; previous behavior: The same migration I/O occurred before the diff.; critical-path effect: File migration must complete before activity is recorded.
  - serialization at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts:recordMigrationActivity</code>: Serialize and store the activity state containing migrated-item metadata.; cardinality: One existing state write per applicable activity context/batch; the diff adds one key string per successful item but no additional write.
    - Introduced by diff: false; previous behavior: The whole activity state was already serialized and stored; its per-item payload lacked migrationKey.; critical-path effect: The synchronous storage update occurs before success UI, as before.
- Verdict: No finding. The added metadata modestly increases an existing activity payload but does not materially amplify boundary count, concurrency, or a demonstrated memory/storage problem.

### Scenario 3: Record MCP server migration activity and refresh the migration dashboard

- Critical path: The existing MCP support scope is resolved, a plan is created and migrated, activity is stored, then candidates refresh. The diff computes one stable key per successfully migrated server before the existing activity write and uses those keys during the post-migration reconciliation.
- Scaling input: Added CPU and stored bytes scale once per successfully migrated server; reconciliation scales with current server/file candidates and retained activity items grouped into two storage scopes.
- Effective concurrency: The MCP migration flow remains serialized around one support scope and one migration call. Candidate refresh categories may run in parallel as described above; no per-server concurrency burst is added.
- Cache behavior: MCP support is represented by the active resolved support scope/snapshot; post-migration refresh reuses current service state where valid. Activity has the same persisted lifecycle as file activity, and the key adds no separate cache.
- Mechanism confidence: High confidence that the diff changes only in-memory key work and activity payload shape on this path.
- Magnitude uncertainty: Server batch sizes and historical activity counts vary, but they are bounded by user-selected discovered servers per operation and no new remote call is multiplied by that size.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts:migrateMcpServers</code>: Resolve active-client MCP support and perform the existing MCP migration.; cardinality: One support-scope/migration operation for the selected server batch, not one newly added call per server.
    - Introduced by diff: false; previous behavior: The same MCP support and migration boundary was present before the diff.; critical-path effect: Must complete before recording activity and refreshing candidates.
  - serialization at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts:recordMigrationActivity</code>: Serialize and persist the existing migration activity state with one additional key string per successful server.; cardinality: One existing state write for the successful MCP batch; no new write is introduced by key generation.
    - Introduced by diff: false; previous behavior: Activity was already stored for the batch without migrationKey.; critical-path effect: Occurs before the post-migration refresh, unchanged except for payload bytes.
- Verdict: No finding. Stable-key generation is linear in successful servers and does not change expensive-boundary frequency or effective concurrency.

**Summary:** Completed the performance pass over all three changed files and traced candidate refresh, file migration, MCP migration, storage serialization, cache behavior, concurrency, and dashboard history rendering. The PR adds a synchronous linear reconciliation and small per-item metadata, but no high-confidence actionable performance regression: boundary fan-out is unchanged, writes are scope-coalesced and conditional, and the new cleanup can reduce retained/rendered stale activity.
