# Performance review: agentHost: Attribute and reduce agent Host turn pre-send latency

[PR #336836](https://github.com/microsoft/vscode/pull/336836) at `52ea82a3d347f6fd4827a65087e342509bf20386`

## Findings (1)

### 1. [medium] Do not block pre-send failures on the speculative checkpoint

**Finding ID:** `PERF-E6F2D68C8182`  
**Location:** <code>src/vs/platform/agentHost/node/agentSideEffects.ts:1805</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Git subprocesses, temporary-index filesystem I/O, and per-session checkpoint queue time  
**Scaling:** The wasted work runs once per failed/cancelled pre-dispatch turn for every working directory; within each directory it scans the repository and stages every changed path, and all captures/discards are serialized by session.  
**Outcome:** Delayed error reporting and delayed dispatch of a subsequent turn, with unnecessary CPU, disk I/O, and subprocess activity after the original turn can no longer reach the provider.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The turn-start checkpoint was created only after model selection, attachment resolution, contributions, and the first cancellation check. A rejection or cancellation during those stages therefore dispatched the error or returned without running checkpoint Git commands.  
**Changed behavior:** The diff starts capture immediately after working-directory resolution. On any later pre-provider failure, the added catch path awaits \`\_discardPendingTurnStartCheckpoint\`, which first awaits the full capture; cancellation cleanup is likewise sequenced behind the capture.  
**Confidence:** 0.98 — The changed ordering, full Git subprocess chain, catch ordering, and session serialization are directly visible in code and covered by the new cancellation test. Exact duration varies by repository size and cache warmth, which affects severity but not the mechanism.

**Causal diff evidence:** Added line 1753 starts the expensive checkpoint before model selection, attachments, and contributions, and added line 1805 awaits its cleanup on pre-provider failure. In the base code the capture call was below all of those stages and the cancellation check, so these abort paths never incurred or waited for it.

If model validation rejects, attachment or contribution resolution fails, or the user cancels during those stages, the host still runs git status, read-tree, optional git add, and write-tree for each workspace. The error is not dispatched until this completes, and a quick retry's checkpoint queues behind the abandoned capture.

**Evidence:** \`captureTurnStartCheckpoint\` calls \`captureWorkingTreeAsTree\` per working directory. That implementation launches repository-wide \`git status --untracked-files=all\`, \`git read-tree\`, optional \`git add\` over all changed paths, and \`git write-tree\`, with temp-directory I/O. \`AgentHostCheckpointService\` uses one \`SequencerByKey\` per session, and the new cancellation test explicitly establishes that capture finishes before discard. Added line 1805 awaits the helper before constructing and dispatching \`ChatError\`; the helper awaits the capture before queueing discard.

**Suggested direction:** Keep the overlap for successful sends, but make turn-start capture cancellable: check turn liveness before each queued repository snapshot and propagate an abort signal to active Git commands. On pre-provider failure, surface the error immediately and await only bounded cleanup rather than completion of the abandoned snapshot.


## Performance regression fixes detected (2)

### 1. eager-work

**Fix location:** `src/vs/platform/agentHost/node/agentSideEffects.ts:1753` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentSideEffects.ts:1762`  
**Introducing path:** `src/vs/platform/agentHost/node/agentSideEffects.ts`

**Mechanism family:** `eager-work`  
**Performance category:** `latency`  
**Confidence:** 0.99

**Mechanism:** Every non-ephemeral turn synchronously awaited its turn-start checkpoint immediately before provider dispatch. The checkpoint traverses each working directory and runs git status, read-tree, optional git add, and write-tree plus temporary filesystem work, so that entire repository-scaled subprocess chain sat on time-to-first-provider progress.

**Symptom:** Agent Host turns incur avoidable pre-provider latency from a full Git working-tree snapshot, scaling with working directories and changed paths.

**Fixed behavior:** The capture now starts as soon as working-directory resolution completes and runs concurrently with model selection, attachment resolution, and outgoing contributions; only its residual duration is awaited before provider dispatch.

**Evidence:** Base line 1762 awaited captureTurnStartCheckpoint directly after all other pre-send stages and immediately before setting the provider stage. AgentHostCheckpointService.\_captureTurnStartCheckpoint calls getRepositoryRoot and captureWorkingTreeAsTree for every working directory; captureWorkingTreeAsTree runs git status, read-tree, optional git add, write-tree, and temporary-directory I/O. The added call at line 1753 starts that same promise earlier while the subsequent selection/attachment/contribution work proceeds, reducing the serialized critical path without changing the before-dispatch invariant.

### 2. repeated-work

**Fix location:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5135` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5102`  
**Introducing path:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`  
**Introducing commit:** `4560ad6d87cabe534b4bb725e361e0d52fda3298`  
**Mechanism family:** `repeated-work`  
**Performance category:** `network`  
**Confidence:** 0.98

**Mechanism:** Model selection awaited any in-flight catalog refresh before validating even when the requested model was already present in the published catalog. The refresh reaches client.rpc.models.list, so an unrelated catalog RPC/network round trip serialized every affected turn's model-selection stage before provider dispatch.

**Symptom:** Turns selecting an already-known model can have their provider dispatch and first response delayed by an unrelated in-flight model-catalog request.

**Fixed behavior:** For ordinary refreshes, validation now returns immediately when the model is already present; only unknown models or credential/client-invalidating refreshes retain the wait.

**Evidence:** Base line 5102 unconditionally awaited \_scheduledModelRefresh or \_modelRefreshInFlight. \_refreshModels calls \_listModels, whose line 3000 awaits client.rpc.models.list. The added fast path at line 5135 checks the current catalog and returns for a known model unless an invalidating refresh is active; the included test gates models.list and proves changeModel reaches the SDK while that request remains in flight.

### Scenario 2: Turn cancelled or rejected during model selection, attachment resolution, or outgoing contributions

- Critical path: The speculative checkpoint starts after working-directory resolution. A pre-provider failure enters the catch block, which awaits capture completion through \`\_discardPendingTurnStartCheckpoint\` before dispatching \`ChatError\`. Cancellation marks the turn complete independently, but discard and any subsequent turn's checkpoint remain queued behind the abandoned capture.
- Scaling input: One newly wasted snapshot per aborted turn, multiplied by working-directory count and each repository's total scan/changed-path set.
- Effective concurrency: The snapshot runs concurrently with pre-send work, but checkpoint capture and discard are serialized per session. A subsequent turn's checkpoint cannot overtake the cancelled/failed capture.
- Cache behavior: There is no reusable result because the snapshot is discarded. Warm filesystem caches may reduce individual Git durations, but every aborted turn still launches a fresh command sequence; failures are not negatively cached.
- Mechanism confidence: Very high: the new test proves capture completes before discard, and production code shows both the Git chain and per-session serialization.
- Magnitude uncertainty: The frequency of pre-dispatch cancellation/failure and exact Git duration vary, but invalid model rejection and user cancellation are realistic and repositories can make each capture materially slow.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:1753 and src/vs/platform/agentHost/node/agentHostGitService.ts:captureWorkingTreeAsTree</code>: Run Git status, read-tree, optional add, and write-tree for a turn that never reaches the provider.; cardinality: One command sequence per working directory for each cancellation/failure after checkpoint start.
    - Introduced by diff: true; previous behavior: Checkpoint capture occurred after all these failure-prone stages and after a cancellation check, so the same aborted turns performed zero checkpoint Git snapshots.; critical-path effect: Directly delays pre-send error reporting because the catch awaits capture cleanup, and indirectly delays the next turn through the session sequencer.
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostGitService.ts:captureWorkingTreeAsTree and src/vs/platform/agentHost/node/agentHostCheckpointService.ts:\_captureTurnStartCheckpoint</code>: Create/write/delete a temporary Git index directory and pathspec file, plus database turn creation for the abandoned checkpoint.; cardinality: One temporary index per working directory and one database turn operation per abandoned capture.

- Verdict: Reportable medium-severity eager-work regression because abandoned turns now consume repository-scaled subprocess/I/O work and failure handling waits for it.
