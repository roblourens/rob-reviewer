# Performance review: inline chat: add experimental Agent Host backend

[PR #331874](https://github.com/microsoft/vscode/pull/331874) at `2e18f96c95f7c2ee4216da5598e09abb82344fea`

## Findings (1)

### 1. [medium] Reuse the file watcher while the selection range changes

**Finding ID:** `PERF-1C23B85FEF72`  
**Location:** <code>src/vs/workbench/contrib/inlineChat/browser/inlineChatController.ts:389</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem watcher registrations and provider watch operations  
**Scaling:** One delete/add cycle and one uniquely correlated provider watch request per non-empty selection change; drag-selection and Shift+Arrow repeat this at input-event frequency, and asynchronous watcher setup can overlap.  
**Outcome:** excessive filesystem/IPC work and input latency while changing the inline-chat selection  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Inline chat did not mirror the editor selection into ChatAttachmentModel on each cursor-selection event, so changing the selection did not create or dispose file watchers.  
**Changed behavior:** The new autorun rebuilds a file attachment whenever editorObs.cursorSelection changes and calls updateContext with the range-derived attachment ID.  
**Confidence:** 0.98 — The changed event dependency, range-derived changing ID, watcher disposal/recreation, unique correlation IDs, and asynchronous provider boundary are all directly traced. Only the platform-specific duration of each watch registration is uncertain.

**Causal diff evidence:** Added line 389 calls attachmentModel.updateContext for every cursorSelection invalidation; the immediately preceding asFileVariableEntry builds IDs as URI plus range, so each changed non-empty range deletes the old attachment and adds a new one.

With Agent Host inline chat open, adjusting a non-empty selection (dragging or Shift+Arrow) can issue a filesystem watch registration for every selection event, causing avoidable I/O/IPC churn and visible selection/input jank.

**Evidence:** ChatAttachmentModel.updateContext disposes the old attachment watcher and calls \_watchAttachment for the added ID. \_watchAttachment calls fileService.createWatcher; FileService assigns a fresh correlationId to every createWatcher call, includes it in the watch hash (preventing deduplication), and asynchronously invokes provider.watch. Thus rapid range changes fan out into overlapping provider watch registrations.

**Suggested direction:** Keep the attachment's file watcher stable while only its range changes, or coalesce/defer range updates until request submission; avoid deleting and re-adding the same URI attachment on every selection event.


## Performance regression fixes detected (1)

### 1. boundary-fanout

**Fix location:** `src/vs/platform/agentHost/node/agentSideEffects.ts:2235` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentSideEffects.ts:2229`  
**Introducing path:** `src/vs/platform/agentHost/node/agentSideEffects.ts`  
**Introducing commit:** `150119bd223150e10f6bf341435e680cd8f26d4b`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `subprocess`  
**Confidence:** 0.98

**Mechanism:** Before sending every turn, ephemeral Agent Host sessions synchronously captured a turn-start checkpoint. For each working directory this opens session state, resolves the Git repository, captures the working tree through git status/read-tree/staging/write-tree subprocesses and temporary filesystem operations, and can initialize baseline commits.

**Symptom:** Existing Agent Host terminal-chat ephemeral turns were blocked before provider send by repository-wide Git checkpoint work, with cost scaling by working-directory count and changed/untracked files.

**Fixed behavior:** The added isEphemeralSession guard skips checkpoint capture entirely for transient sessions, removing the per-turn Git/database/filesystem work from the send critical path while durable sessions retain checkpoints.

**Evidence:** TerminalChatSessionResolver already creates Agent Host sessions with isEphemeral:true. AgentSideEffects awaited captureTurnStartCheckpoint immediately before agent.chats.sendMessage. AgentHostCheckpointService iterates all working directories and invokes captureWorkingTreeAsTree; that implementation runs git status, creates a temp index, stages changed paths, runs read-tree/write-tree, and deletes the temp directory. Added line 2235 guards this await for non-ephemeral sessions. Base blame resolves the old unconditional await to the supplied commit.

### Scenario 4: Change a non-empty editor selection while Agent Host inline chat is visible

- Critical path: Every cursorSelection invalidation rebuilds the file attachment. Because the attachment ID includes the changing range, updateContext removes the old attachment and adds a new one, synchronously initiating a uniquely correlated asynchronous filesystem watch request.
- Scaling input: Selection-change events, including every drag-selection update or Shift+Arrow keypress; one watcher dispose/create cycle per distinct range.
- Effective concurrency: There is no debounce or shared limiter. FileService starts doWatch asynchronously, so rapid events can leave multiple provider.watch setups in flight even though old watcher handles were disposed.
- Cache behavior: FileService normally hashes watch requests, but createWatcher assigns a fresh correlationId and includes it in the hash, so these same-URI requests cannot reuse the active watcher cache.
- Mechanism confidence: Very high: the range-derived ID, update/delete-add behavior, watcher creation, unique correlation key, and async provider call are directly traced.
- Magnitude uncertainty: Provider watch registration cost varies by platform and remote filesystem, affecting severity but not the fan-out mechanism.

- Verdict: Reportable medium-severity boundary fan-out; submitted as a finding.
