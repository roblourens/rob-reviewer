## Findings (1)

### 1. [low] Keep local browser-tool tests off the public network

**Finding ID:** `PERF-BAED1EA66D2E`  
**Location:** <code>extensions/vscode-api-tests/src/singlefolder-tests/browser.tools.test.ts:265</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** DNS lookup, TCP/TLS setup, the HTTPS response, and any page subresource requests made by the integrated browser  
**Scaling:** One cold public navigation is added to each execution of this suite; that cost repeats across the Electron/remote OS test jobs, and a blocked endpoint can hold each invocation for the 30-second browser navigation timeout.  
**Outcome:** Increased integration-test latency and avoidable long stalls/timeouts on offline, DNS-restricted, or rate-limited runners.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The changed test navigated to an in-process loopback HTTP server. In non-remote Electron runs it performed no public DNS/TLS request; only remote runs additionally opened a tunnel.  
**Changed behavior:** The test now awaits \`open\_browser\_page\` for \`https://google.com/\` in every non-web suite run, moving a public network load onto the test's critical path.  
**Confidence:** 0.97 — The changed URL and fully awaited network call path are explicit, as is the 30-second navigation bound. The exact healthy-network delay and number of Google subresources vary, which limits severity, but the new external boundary and its critical-path placement are certain.

**Causal diff evidence:** RIGHT line 265 replaces the deleted \`http://127.0.0.1:${address.port}/\` invocation with an awaited \`https://google.com/\` invocation, introducing the public-network dependency on local test runs.

A normal local or CI run must now reach Google before this test can complete. \`OpenBrowserTool.\_openNewPage\` awaits \`createBrowserView\`, whose \`model.loadURL\` reaches Electron's awaited \`webContents.loadURL\` with a 30-second timeout, so unavailable external networking can add tens of seconds and fail the suite; healthy runs still pay external DNS/TLS/page-load cost instead of loopback latency.

**Evidence:** The added line invokes \`open\_browser\_page\` with a public URL. The traced call path is \`OpenBrowserTool.\_openNewPage\` -&gt; \`BrowserViewWorkbenchService.createBrowserView\` -&gt; \`BrowserViewModel.loadURL\` -&gt; \`BrowserView.loadURL\` -&gt; awaited \`webContents.loadURL\`; \`createBrowserView\` caps this wait at 30,000 ms and only afterward waits for Playwright DOM readiness. The deleted hunk served the page from \`127.0.0.1\`, and the GitHub workflows compile/run these API integration tests on Windows, macOS, and Linux.

**Suggested direction:** Keep the loopback fixture for non-remote runs, where no tunnel is needed, and use a separately bounded remote-only strategy (or skip this external-content case remotely) so fixing the tunnel hang does not make every integration run depend on Google.
