## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `build/azure-pipelines/product-publish.yml:123` (`RIGHT`)  
**Blamed base line:** `build/azure-pipelines/product-publish.yml:132`  
**Introducing path:** `build/azure-pipelines/product-publish.yml`  
**Introducing commit:** `4b8bd3cb6fb916c3abd4801003599ea653a6fe80`  
**Mechanism family:** `repeated-work`  
**Performance category:** `network`  
**Confidence:** 0.96

**Mechanism:** Terminal producer failures were checked inside a task configured for three retries, causing repeated process startup, checkpoint scanning, and timeline/artifact API reads that could not repair the terminal failure.

**Symptom:** Failed producer builds spend additional CI time and AZDO requests rerunning the publication task after all recoverable artifact work has already drained.

**Fixed behavior:** The retryable task now exits after artifact processing, while producer-stage validation runs in a separate task without `retryCountOnTaskFailure`; terminal producer failures therefore no longer trigger three redundant task reruns and repeated AZDO reads.

**Evidence:** Before this PR, the retryable `Process artifacts` task ran `publish.ts` in combined mode. After artifact draining, the unchanged old main validated producer results and threw on a terminal failed/canceled/skipped producer, so Azure Pipelines' `retryCountOnTaskFailure: 3` reran the task even though that terminal stage result could not change. Each retry created a Node process and re-read the timeline and artifact list through AZDO network APIs (checkpoint state avoided republishing completed artifacts). The changed command at line 123 selects processing-only mode, and the following non-retryable task performs terminal validation once.

One worker is started per prepared artifact and all publication workers may overlap without a new shared limiter; this is unchanged from the base implementation. ### Scenario 2: A producer reaches a terminal failure while another producer later emits artifacts

- Critical path: Processing continues polling and publishing late artifacts until all enabled stages complete and all discovered publications drain. The following standalone validation reads the final timeline once and fails the job, preventing release.
- Scaling input: The wait scales with remaining producer duration; polling remains two grouped AZDO reads every 10 seconds, and late artifact work scales with distinct uncheckpointed artifacts rather than producer jobs.
- Effective concurrency: Late artifacts are prepared serially and published in overlapping workers. Terminal validation is serialized after the drain and has no task-level retry.
- Cache behavior: Previously completed artifacts are skipped from the persisted checkpoint. Late successful outputs are checkpointed before validation fails, so a later stage/job attempt is warm. Terminal producer results are deliberately fetched fresh rather than cached.
- Mechanism confidence: High: command-mode branching, task retry placement, checkpoint behavior, and network call flow are directly visible. The performance regression fix was recorded against the blamed base line.
- Magnitude uncertainty: Azure Pipelines retry delay and exact API latency are environment-dependent, but the removed repeated execution is explicit and bounded by the configured three retries.
- Expensive boundaries:
  - network at <code>build/azure-pipelines/common/publish.ts:processArtifacts integration</code>: Poll timeline/artifact list and process any late artifact through download, Blob/CDN/ESRP, and Cosmos calls; cardinality: Two grouped reads per poll plus one existing publication sequence per late uncheckpointed artifact
    - Introduced by diff: false; previous behavior: The base loop used the same completion predicate and artifact processing boundaries.; critical-path effect: Processing waits for remaining producers and publications before surfacing terminal producer failure
  - network at <code>build/azure-pipelines/product-publish.yml:Validate producer stages</code>: Read the final producer timeline in the non-retryable validation task; cardinality: One successful GET before the task reports the terminal failure
    - Introduced by diff: true; previous behavior: Validation occurred inside the task configured with three retries, so a terminal producer failure reran Node and AZDO state reads despite being irreparable.; critical-path effect: Determines job failure after useful artifact work has drained
  - subprocess at <code>build/azure-pipelines/product-publish.yml:Process artifacts / Validate producer stages</code>: Run publication processing and then standalone validation; cardinality: One processing process plus one validation process; terminal validation itself is not retried
    - Introduced by diff: true; previous behavior: One combined command failed inside \`retryCountOnTaskFailure: 3\`, causing repeated process startup and state reads.; critical-path effect: Removes up to three task-level reruns after terminal failure
- Verdict: Performance improves on terminal producer failures by moving irreparable validation outside the retryable processing task; no new regression is introduced.

### Scenario 3: Transient artifact download or publication failure followed by a Process artifacts task retry

- Critical path: An internal retry first handles recognized transient boundary failures. If processing still fails, Azure Pipelines may rerun the processing task up to three times; standalone validation does not run until processing succeeds.
- Scaling input: Retry work scales with failed boundary attempts and uncheckpointed artifacts. Successfully checkpointed artifacts are excluded on subsequent task attempts; the failed artifact remains eligible for retry.
- Effective concurrency: Downloads stay serial. Publication workers overlap and are all drained before an aggregate publication error is thrown. A task-level retry starts only after the failed attempt exits, so task attempts do not overlap.
- Cache behavior: The persisted checkpoint is the warm cache across task/stage attempts. Successes are retained; failed artifacts are not added and are intentionally redownloaded/republished. No negative cache is used.
- Mechanism confidence: High: retry nesting, checkpoint lifecycle, and task sequencing are explicit in the changed and surrounding code.
- Magnitude uncertainty: Failure frequency and whether retries reach their maximum depend on external services, but diff causality is clear: recoverable processing retries are retained rather than increased.
- Expensive boundaries:
  - network at <code>build/azure-pipelines/common/publish.ts and build/azure-pipelines/common/retry.ts</code>: Retry AZDO reads/downloads and artifact publication service calls; cardinality: Up to ten internal attempts for recognized transient failures and up to three serial task retries; only uncheckpointed artifact work repeats
    - Introduced by diff: false; previous behavior: The same internal retries, task-level retry setting, and successful-artifact checkpoint reuse applied to the combined command.; critical-path effect: Failures block completion and validation, as before
  - filesystem at <code>build/azure-pipelines/common/publish.ts:State</code>: Load the latest checkpoint and recreate the current attempt's checkpoint file; cardinality: Once per processing task attempt, plus one append per successful artifact
    - Introduced by diff: false; previous behavior: Identical \`State\` construction and append behavior existed before extraction.; critical-path effect: Avoids repeating expensive publication work on warm retries
- Verdict: No regression. The split preserves retry behavior for recoverable processing failures and does not amplify artifact cardinality or concurrency.

    - Introduced by diff: false; previous behavior: This is the compatibility path and preserves the old combined behavior.; critical-path effect: All processing drains before in-process validation
- Verdict: No reportable performance change; the refactor preserves default CLI boundary cardinality and scheduling.
