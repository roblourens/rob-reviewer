**Relevant issue families:** serialization-allocation, repeated-work, boundary-fanout, concurrency-burst

### Scenario 1: Cold Copilot CLI startup and configuration-driven runtime restart

- Critical path: Environment sanitization runs synchronously before CLI path resolution and the existing CopilotClient.start subprocess boundary; all of it is on the startup/restart critical path.
- Scaling input: Number of inherited environment entries E plus comma-separated feature flags F. The diff adds one Object.keys scan and, only when the aggregate flag variable exists, one split/filter/join over F; realistic cardinality is tens to hundreds of environment entries and a short flag list.
- Effective concurrency: Concurrent callers are coalesced by \_clientStarting, and stopping is serialized by \_clientStopping, so one effective CLI startup occurs at a time.
- Cache behavior: A live \_client is the warm cache and bypasses environment construction. Cold starts and explicit restarts rebuild the environment once; no negative-cache behavior is involved.
- Mechanism confidence: High: the changed loop and aggregate-flag filtering are directly on the startup path, while \_clientStarting and client.start establish frequency and boundary cardinality.
- Magnitude uncertainty: Exact process-environment size varies by host, but the new CPU/allocation work is bounded by an already-copied small environment and does not add an expensive boundary.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:243 resolveCopilotCliPath</code>: Probe platform-specific Copilot CLI entry-point candidates with fileExists during resolveCopilotCliPath.; cardinality: One successful probe normally; up to the bounded platform candidate list plus one legacy path probe on misses.
    - Introduced by diff: false; previous behavior: The same bounded CLI path probes ran on every cold start/restart before the diff.; critical-path effect: Must resolve before the subprocess can start.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:2400 \_ensureClientOnce</code>: Start the Copilot CLI over a stdio RuntimeConnection via CopilotClient.start.; cardinality: One subprocess start per cold runtime start or coalesced restart.
    - Introduced by diff: false; previous behavior: The same subprocess start occurred with HydraFusion represented by two environment variables instead of per-session SDK flags.; critical-path effect: Startup waits for the client to start.
- Verdict: No finding. The extra O(E+F) string/object work is negligible relative to the unchanged filesystem probes and subprocess startup, runs once per effective start, and is not an actionable regression.

### Scenario 2: Create or resume an SDK session with HydraFusion enabled

- Critical path: \_buildSessionConfig resolves existing BYOK/customization state, then the returned config is passed to the existing createSession or resumeSession SDK call. The two feature booleans are serialized on that existing call and add no extra await or boundary.
- Scaling input: One two-entry featureFlags object per opted-in session launch. Existing plugin/custom-agent work scales with the projected plugin resources, but the diff does not change that collection or its effective cardinality.
- Effective concurrency: Independent session launches retain their prior concurrency. Concurrent BYOK-enabled launches share the memoized \_byokProxyHandle promise; the diff creates no new fan-out or burst.
- Cache behavior: HydraFusion configuration is read once for each launch with no cache needed. The BYOK proxy is lazily memoized across launches and cleared on runtime stop; feature-flag transport has no cold/warm behavioral difference beyond the existing SDK session call.
- Mechanism confidence: High: the changed object is constructed once in \_buildSessionConfig and reaches the already-existing create/resume call without loops, extra RPCs, or new awaits.
- Magnitude uncertainty: The SDK's internal handling of HydraFusion is external to this repository, but the prior environment flags requested the same feature; there is no evidence the transport change increases runtime work.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:893 \_buildSessionConfig -&gt; toSdkSessionCustomAgents</code>: Read explicitly projected custom-agent resources while constructing session config.; cardinality: Scales with non-file-directory custom agents plus the selected agent; ephemeral sessions skip it.
    - Introduced by diff: false; previous behavior: The same custom-agent projection and reads occurred before featureFlags were added.; critical-path effect: The reads must finish before create/resume, but their collection and count are unchanged.
  - other at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:827 \_resolveByokSessionConfig</code>: Lazily start the shared BYOK loopback proxy when BYOK models are enabled.; cardinality: At most one proxy start per launcher lifetime between runtime stops, shared by concurrent launches.
    - Introduced by diff: false; previous behavior: The same memoized proxy startup behavior existed before the diff.; critical-path effect: Only BYOK-enabled launches with surfaced models wait for it; unrelated HydraFusion flag construction does not alter this path.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:691 \_resumeSession and :713 \_createSession</code>: Invoke Copilot SDK createSession or resumeSession against the CLI runtime, including existing retry/fallback rules for resume.; cardinality: One RPC for a normal launch; existing resume failures can cause one custom-agent retry and, only for empty history, an existing create fallback.
    - Introduced by diff: false; previous behavior: The same SDK calls and retry cardinality occurred; HydraFusion was supplied process-wide through environment variables, while the diff adds two booleans to the existing per-session payload.; critical-path effect: The session cannot open until the SDK call completes.
- Verdict: No finding. Per-session serialization grows by two booleans, while boundary count, plugin scale, retries, and concurrency are unchanged.

### Scenario 3: Toggle the HydraFusion setting while the Copilot runtime is active

- Critical path: The root-config listener compares CopilotAgentStartupConfig and requests the existing deferred runtime restart; model refresh and subsequent sessions then use the new setting. The restart is deferred past active turns.
- Scaling input: One startup-config comparison per root configuration event; a HydraFusion value change results in one restart request, independent of session or model collection size.
- Effective concurrency: Restart requests use the existing deferred/serialized client lifecycle, wait for active chats to become idle, and client starts remain coalesced.
- Cache behavior: \_lastStartupConfig suppresses restarts when effective startup values are unchanged. A live client is replaced only when the comparison changes; the diff intentionally leaves HydraFusion in that comparison.
- Mechanism confidence: High: HydraFusion remains in CopilotAgentStartupConfig, and the root listener/restart path are unchanged.
- Magnitude uncertainty: Restart duration is host-dependent, but its trigger and cardinality are explicitly preserved rather than introduced or amplified by the changed hunks.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:1146 \_restartClientIfStartupConfigChanged</code>: Stop and restart the Copilot CLI after an effective HydraFusion configuration change.; cardinality: One deferred lifecycle restart for an effective setting transition, with concurrent starts coalesced.
    - Introduced by diff: false; previous behavior: HydraFusion was already part of CopilotAgentStartupConfig and already triggered the same process restart because its environment variables were startup-baked.; critical-path effect: Not on an in-flight turn because restart waits for a quiet point; subsequent runtime use waits for startup.
- Verdict: No finding. Although restarting is expensive, that behavior is pre-existing and unchanged, so it does not meet PR-causality requirements.

**Summary:** Completed the performance pass over all five changed files and every diff page. The PR replaces process-wide HydraFusion environment transport with two fields on existing SDK session payloads and strips inherited overrides during the already-existing startup environment copy. It introduces no new expensive boundary, fan-out, concurrency burst, cache retention, or realistically significant critical-path work, and it is not itself a proven regression fix.
