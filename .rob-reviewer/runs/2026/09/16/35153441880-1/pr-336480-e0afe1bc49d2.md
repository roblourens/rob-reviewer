# Performance review: agentHost: recognise a crash-orphaned provisional session

[PR #336480](https://github.com/microsoft/vscode/pull/336480) at `e0afe1bc49d2ec920a49d0ce0b0ab1c2cfa4dab1`

## Findings (1)

### 1. [medium] Bound and coalesce provisional-session validation

**Finding ID:** `PERF-E3EF0547E5F2`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:1662</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Per-session filesystem/database opens and provider SDK IPC calls  
**Scaling:** Each visible session whose durable provisional marker survives contributes one concurrent validation. The marker is retained after an orphan is hidden, so the same P validations recur on every backend list computation, and P can accumulate across crash-orphaned sessions or failed marker clears.  
**Outcome:** An initial or invalidated session-list request can issue an unbounded burst of provider requests and filesystem reads and remains blocked until the slowest request completes, increasing list/startup latency and provider load.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With an eligible central catalog row, \`\_computeSessions\` returned catalog metadata without provider metadata or session-database reads; existing tests explicitly assert zero \`getChatMetadata\` calls and zero session DB opens for that path. Provider fallback reads, when needed, were limited to four and could use \`prewarmSessionMetadata\`.  
**Changed behavior:** Whenever any provisional marker exists, the new post-catalog pass identifies each marked visible session and calls \`\_registeredSessionMetadata\` under an unbounded \`Promise.all\`. This occurs after \`prewarmDisposables\` have been disposed, so Copilot falls back to targeted \`getSessionMetadata\` IPC instead of its bulk-warmed cache.  
**Confidence:** 0.96 — The new call site, unbounded concurrency, repeated list reachability, and concrete Copilot/Claude boundary operations are directly traced. Exact latency depends on marker count and SDK/storage speed, but the boundary fan-out and bypass of the existing limiter/prewarm are certain.

**Causal diff evidence:** The added \`await Promise.all(sessions.map(...))\` at line 1662 schedules every marked session's \`\_registeredSessionMetadata\` validation concurrently; this validation pass did not exist before the change.

After one or more crash-orphaned provisional chats (or stale markers from failed clears), opening or refreshing the sessions list waits for a burst of one provider validation per marked row. On Copilot this can mean multiple session DB probes plus one SDK IPC per row on the list critical path.

**Evidence:** \`\_registeredSessionMetadata\` first calls \`\_readDefaultChatProviderData\`, which can try both the default-chat and session databases, then calls the provider. \`CopilotAgent.getChatMetadata\` additionally opens stored session metadata and, once its prewarm cache is gone, calls \`client.getSessionMetadata\`; Claude calls \`sdk.getSessionInfo\`. The surrounding fallback phase uses \`Limiter(4)\` and keeps provider prewarm alive specifically to avoid N metadata round trips, but the added pass runs afterward without either protection. Provisional markers are removed only on successful materialization or disposal, not after a successfully hidden orphan, so these calls repeat.

**Suggested direction:** Validate only the marked intersection, route those reads through a bounded limiter, and keep/group provider prewarming across this pass (or maintain an invalidated cache of definitive orphan classifications) so catalog-backed listing does not issue unbounded targeted provider reads while preserving stale-marker revalidation semantics.

### Scenario 2: Session listing after restart with crash-orphaned or stale provisional markers

- Critical path: After registry/catalog resolution, the list awaits \`\_withoutUnmaterializedProvisionalSessions\`; every marked visible row must complete provider validation before results return.
- Scaling input: P marked visible sessions after intersecting catalog results with registrations. P can persist and accumulate because successfully hidden orphans keep both registration and marker until explicit disposal.
- Effective concurrency: All P validations are launched by one unbounded \`Promise.all\`. This bypasses the existing fallback \`Limiter(4)\`; Copilot's bulk prewarm disposable has already been released before this phase.
- Cache behavior: The marker set is cached, but provider validation results are not. Hidden or provider-vouched markers are checked again on each backend recomputation. The front-end coalesces/cache-valid refreshes, while host restarts, invalidations, modes, and direct callers produce new computations.
- Mechanism confidence: Very high: changed Promise.all, provider implementations, prewarm disposal ordering, and existing zero-read tests directly establish the behavior.
- Magnitude uncertainty: Typical P after a single crash may be one, while repeated aborted sessions or failed marker clears increase it; exact provider RPC latency varies. This lowers severity but not confidence in the fan-out mechanism.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts:\_registeredSessionMetadata and \_readDefaultChatProviderData</code>: Read default-chat provider data via up to two session database probes, followed by provider-specific stored metadata reads.; cardinality: Up to multiple session-database probes for each of P marked visible sessions on every computation.

  - IPC at <code>src/vs/platform/agentHost/node/agentService.ts:\_withoutUnmaterializedProvisionalSessions</code>: Fetch targeted provider metadata; Copilot falls back to \`client.getSessionMetadata\` after prewarm disposal, Claude calls SDK \`getSessionInfo\`, and activated Codex may read through its app-server.; cardinality: One provider validation per marked visible session, P concurrent and repeated per computation.

- Verdict: Reportable medium-severity concurrency burst and repeated boundary work; finding submitted.
