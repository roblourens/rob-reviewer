### 1. [medium] Defer live polling for linked issues

**Finding ID:** `PERF-0CFD5D70FA71`  
**Location:** <code>src/vs/sessions/contrib/providers/copilotChatSessions/browser/copilotChatSessionsProvider.ts:1295</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Concurrent GitHub REST issue requests, response bytes/objects, and long-lived polling timers/models.  
**Scaling:** After URL deduplication the cost is linear in K distinct public closing issues, with K capped at 100 per PR. Cold activation performs K requests concurrently; warm activation within 60 seconds is coalesced, while a long-lived active session performs another request for each still-open issue every 15 minutes (conditional 304s still cross the network).  
**Outcome:** Excessive network I/O and API pressure from a large concurrent burst plus sustained polling.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Cloud sessions did not populate gitHubInfo.issues from PR-closing relationships, so opening an existing cloud session created no issue models and issued no per-issue REST refresh or polling traffic.  
**Changed behavior:** The changed adapter promotes every deduplicated public linked-issue artifact into gitHubInfo.issues. SessionChatInputToolbar consumes that array by creating one shared model per distinct issue, immediately calling refresh(), and starting polling for every issue not known to be closed whenever the Issues pill is enabled.  
**Confidence:** 0.99 — The changed promotion line, default-visible consumer, one-model-per-key cache, REST boundary, and 15-minute cadence are all explicit. Only how often PRs link unusually many issues is uncertain, affecting severity rather than the mechanism.

**Causal diff evidence:** Added line 1295 appends every parsed public linked-issue artifact to the issues array that is returned in gitHubInfo; the same PR requests closingIssuesReferences(first: 100), so this newly populated array can contain up to 100 distinct references.

Opening a cloud session whose PR closes many public issues now launches up to 100 GitHub REST requests off the UI critical path and keeps up to 100 open-issue pollers active, repeating that network fan-out every 15 minutes. This can contend with other GitHub features and consume API/network capacity even though the PR metadata already supplies the titles needed to render the pill.

**Evidence:** The Issues pill is visible by default (defaultHiddenKinds excludes Issues). Its autorun loops every issue ref, invokes model.refresh(), and starts polling in sessionChatInputToolbar.ts lines 388-404. GitHubIssueModel refresh calls GitHubIssueFetcher.getIssue, which performs GET /repos/{owner}/{repo}/issues/{number}; each open issue then revalidates every 900,000 ms. The reference collection coalesces duplicate keys and refreshes within 60 seconds, but there is no aggregate limiter across distinct issues, so K unique links still produce K concurrent REST requests.

**Suggested direction:** Render all references from the supplied URL/title metadata, but create and refresh live issue models only when the Issues dropdown or a specific hover is opened; if background state is required, cap or batch the subset that is polled rather than eagerly polling all 100.

### 2. [medium] Coalesce cutoff expiry instead of rebuilding every remaining session

**Finding ID:** `PERF-1EC92E67AEFC`  
**Location:** <code>extensions/copilot/src/extension/chatSessions/vscode-node/copilotCloudSessionsProvider.ts:464</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Task API calls plus per-session GitHub GraphQL PR lookups and REST PR-file/commit-comparison requests.  
**Scaling:** For N visible sessions with distinct cutoff times, the timer rebuilds N, then N-1, and so on remaining enrichments: O(N^2) session-boundary work (up to 5,050 enrichments for the 100-item catalog), with each rebuild launching its remaining per-session operations concurrently via Promise.all.  
**Outcome:** Repeated network bursts, excessive API I/O, and avoidable refresh latency as sessions age out.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change there was no exact per-session age cutoff timer. Enriched chat-session items remained cached until an existing provider refresh; the five-minute background check fetched the task catalog but only invalidated the enriched cache when its size changed.  
**Changed behavior:** The added expiry scheduler calls refresh() at the oldest visible session's exact activity cutoff. That clears the whole enriched cache and fires onDidChangeChatSessionItems; the extension-host bridge immediately invokes provideChatSessionItems again, which refetches the Task API catalog and re-resolves PR and changed-file metadata for every still-visible session before scheduling the next session's cutoff.  
**Confidence:** 0.97 — The timer-to-refresh-to-extension-host-provide path and all expensive transitive boundaries are explicit in the repository. The exact number and clustering of user sessions is uncertain, which limits severity, but the repeated-work mechanism and quadratic relationship are deterministic.

**Causal diff evidence:** The added callback at line 464 invokes this.refresh() whenever cachedSessionItemsExpiresAt passes; added lines 1497-1498 install the next per-session expiry after every rebuild, and filterCloudSessions computes that expiry as the minimum individual task expiry.

With the Agents window open and many cloud tasks from a clustered work period reaching the 30-day cutoff, each individual task expiry causes another full concurrent GitHub enrichment burst for all remaining tasks. The list can contain up to 100 Task API results, so distinct expirations can produce quadratic repeated enrichment, consuming network/API quota and creating repeated list refresh latency.

**Evidence:** refresh() clears cachedSessionItems/chatSessionItemsPromise and fires the change event (lines 918-927). ExtHostChatSessions handles that event by immediately calling controller.refreshHandler, whose implementation calls provider.provideChatSessionItems. That method performs one backend fetch and Promise.all over the remaining sessions (lines 1428-1484), resolving each PR via GraphQL and then fetching PR files or a commit comparison via GitHub REST. The new tests at provider spec lines 423-441 explicitly establish that the timer fires a change event and the ensuing provide performs another backend fetch.

**Suggested direction:** Keep the raw/enriched catalog through age-only expiry and remove or hide expired cached items locally, scheduling the next cutoff without refetching unchanged PR/file metadata. Alternatively coalesce expirations into a bounded time bucket and reuse per-session enrichment across cutoff refreshes.
