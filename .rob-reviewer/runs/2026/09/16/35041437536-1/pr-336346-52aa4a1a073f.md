**Relevant issue families:** serialization-allocation, missing-coalescing, boundary-fanout, synchronous-ui-work

### Scenario 1: A user opens a Copilot setup or provider sign-in dialog from commands, Accounts/title bar/URL, chat or inline rename, Agents onboarding/Agent Host, SCM, or code review.

- Critical path: The existing setup path checks trust and setup state, constructs and shows the dialog, then waits for user dismissal. The diff synchronously builds a five-field telemetry payload immediately after dialog.show() and calls publicLog2; delivery is not awaited, so only bounded object/enum/button inspection and telemetry sanitization/scheduling occur before returning to the dialog wait. Provider authentication or setup runs only after selection and is unchanged.
- Scaling input: One event per actually displayed dialog. The source allowlist has 13 fixed values and the dialog button list is small and fixed by setup strategy, so Object.values/includes and buttons.some do not scale with repositories, files, chat history, or SCM resources.
- Effective concurrency: ChatSetup.run retains a single pendingRun, so concurrent callers share one dialog and emit one event. A later redisplay emits one later event; there is no aggregate Promise.all or per-resource fan-out.
- Cache behavior: No result cache is added or bypassed. The existing pendingRun acts as in-flight coalescing. Telemetry may be buffered while experiment properties initialize and the telemetry SDK/appender performs its normal batching; warm and cold setup behavior otherwise remains unchanged.
- Mechanism confidence: High confidence: the changed callback, pendingRun coalescing, fixed enum/button scans, and desktop/web appender behavior are directly visible in the traced code.
- Magnitude uncertainty: Exact telemetry sanitization and IPC scheduling time varies with common-property size and platform, but the changed event is tiny, fixed-cardinality, emitted only at human-paced dialog displays, and its delivery is asynchronous.
- Expensive boundaries:

- Verdict: No reportable regression. The diff adds a bounded, asynchronous telemetry record at dialog presentation without adding collection-scaled work, awaited I/O, or unbounded retention.

### Scenario 2: Concurrent, skipped, or pre-canceled setup requests.

- Critical path: Concurrent requests return the existing pendingRun and do not construct another dialog. Pre-canceled, entitled, anonymous-without-dialog, explicit-strategy, and skip-once paths bypass showDialog, so the new callback and telemetry boundary are not reached.
- Scaling input: Multiplicity is the number of concurrent setup requests or skip attempts. Effective displayed-dialog cardinality remains one for any overlapping request group and zero for bypassed runs.
- Effective concurrency: A single in-flight promise serializes/coalesces all callers globally for the ChatSetup instance; the diff neither weakens this guard nor starts parallel telemetry work per caller.
- Cache behavior: The in-flight pendingRun is cleared after completion, allowing a later independent display and event. There is no retained event cache or source map and no negative-cache behavior.
- Mechanism confidence: High confidence from ChatSetup.run's pendingRun guard and the callback placement solely inside showDialog after the cancellation check.
- Magnitude uncertainty: Caller burst sizes are unknown, but they do not change event cardinality because the first pendingRun owns the only dialog and callback.
- Expensive boundaries: none found
- Verdict: No reportable regression. Existing coalescing prevents boundary fan-out, and bypassed flows perform no new telemetry work.

**Summary:** Reviewed all 11 changed files and every diff hunk. The only new runtime cost is fixed-size source validation, button classification, account/entitlement snapshot reads, and one non-awaited telemetry dispatch per displayed dialog. Concurrent calls remain coalesced and skipped/pre-canceled paths emit nothing; no hot-path, scaling, retention, startup, rendering, or blocking-boundary regression was found.
