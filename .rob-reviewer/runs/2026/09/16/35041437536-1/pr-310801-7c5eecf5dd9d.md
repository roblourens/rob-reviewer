# Performance review: Add incremental chat rendering experiment

[PR #310801](https://github.com/microsoft/vscode/pull/310801) at `7c5eecf5dd9dfbc4978b23ca50537b640c951f45`

## Findings (2)

### 1. [medium] Cap full markdown reconstruction below the display frame rate

**Finding ID:** `PERF-74973BA9A402`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatIncrementalRendering/chatIncrementalRendering.ts:259</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work, DOM nodes, code-block/editor objects, and temporary regex/markdown-render allocations  
**Scaling:** While the default word buffer has a backlog, cost repeats on animation frames and each pass processes the entire growing rendered prefix; total work therefore grows with both response length and the number of reveal frames, and code blocks/tables multiply reconstruction work.  
**Outcome:** Sustained main-thread CPU/GC pressure and dropped frames while long or code-rich chat responses stream or drain after completion.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Progressive rendering was driven by a 50 ms interval, bounding full markdown-part replacement to at most 20 passes per second and revealing multiple words per pass at higher stream rates.  
**Changed behavior:** The added needsNextFrame branch continuously schedules requestAnimationFrame; WordBuffer scans the complete accumulated string on every frame and, whenever at least one word becomes due, the callback runs doRenderMarkdown, which clears the node, disposes all prior render refs, reparses/sanitizes the full prefix, walks decorations, wraps tables/KaTeX, and recreates code blocks.  
**Confidence:** 0.99 — The scheduler, default word-buffer rates, full-string getNWords implementation, callback wiring, and destructive doRenderMarkdown path are all directly traced. Exact milliseconds depend on response complexity and hardware, which limits severity because the feature is experimental and disabled by default, but the 20 Hz to near-60 Hz multiplicity is deterministic when enabled.

**Causal diff evidence:** Added line 259 turns buffered content into a continuous rAF loop; together with the newly added callback at line 253, this newly permits whole-prefix markdown/DOM reconstruction once per display frame rather than the prior 50 ms cadence.

With the experiment enabled (default buffering is word), a model rate at or above roughly one word per frame drives the full markdown pipeline near 60 Hz instead of 20 Hz; even the 40 words/s floor commits roughly every other frame. Long responses and fenced code blocks can visibly jank during streaming, and completion forces at least an 80 words/s drain that keeps the loop at frame rate while backlog remains.

**Evidence:** The changed rAF loop reschedules itself at line 259 whenever WordBuffer reports backlog. WordBuffer.filterFlush calls getNWords(fullMarkdown, revealedWordCount), whose implementation materializes all regex matches for the full string, and successful frames invoke the callback at line 253. ChatMarkdownContentPart wires that callback to doRenderMarkdown; that function clears the DOM, disposes all refs, calls renderer.render over the full prefix, recreates code/diff blocks, walks the DOM for references and KaTeX, and wraps tables. The deleted/default path uses WindowIntervalTimer at 50 ms.

**Suggested direction:** Keep rAF for visual coalescing, but bound expensive markdown commits to a cadence no faster than the prior 50 ms path (or batch enough newly due words per commit), and schedule the next due commit rather than scanning and rerendering on every frame. Preserve the final flush by draining multiple words per bounded pass.

### 2. [medium] Avoid forcing layout after every incremental markdown flush

**Finding ID:** `PERF-C9D649B01F87`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatMarkdownContentPart.ts:176</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous browser style/layout computation for the chat row and list height update  
**Scaling:** The geometry read occurs after every successful buffered-word commit, up to the display refresh rate, and its cost grows with the rendered response DOM, code blocks, tables, math, and surrounding chat-list layout.  
**Outcome:** Blocked animation frames and dropped frames during streaming as DOM reconstruction is immediately followed by forced synchronous layout.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The 50 ms progressive path replaced markdown parts without an onDidChangeHeight emission from the synchronous constructor render; the row's existing ResizeObserver could report size changes asynchronously.  
**Changed behavior:** Every morpher callback now calls doRenderMarkdown to clear and rebuild the DOM and then immediately fires onDidChangeHeight. The registered listener calls fireItemHeightChange, whose fallback executes rowContainer.getBoundingClientRect().height before returning to the rAF callback.  
**Confidence:** 0.98 — The DOM-write → event → getBoundingClientRect call path is explicit, synchronous, and newly added. Browser layout may occasionally already be valid, but after clearNode plus full DOM recreation a geometry read generally requires style/layout; exact duration varies with content and hardware.

**Causal diff evidence:** Added line 176 introduces a synchronous height notification after each rAF-driven DOM rebuild; its unchanged listener immediately performs the geometry read, placing forced layout directly on the new per-frame render path.

For the default word mode, long streaming responses can perform a forced row/list layout roughly 30–60 times per second immediately after large DOM writes, consuming the same frame budget intended for smooth animation and causing visible chat scrolling/render jank.

**Evidence:** Added line 176 fires synchronously after doRenderMarkdown. ChatListRenderer.renderMarkdown registers this event to fireItemHeightChange, and fireItemHeightChange computes template.rowContainer.getBoundingClientRect().height when no measured height is supplied. The callback is reached from IncrementalDOMMorpher's rAF flush for each committed word batch; the same row already has ResizeObserver-based height handling.

**Suggested direction:** Do not synchronously emit this unmeasured height notification after each flush. Rely on the row ResizeObserver's measured block size, or coalesce a measured height update after browser layout and only propagate it when the size actually changed.

### Scenario 2: Complete or cancel a response while the word buffer still has unrevealed content.

- Critical path: The renderer marks the active morpher complete, raises its reveal floor to 80 words/s, and the morpher continues its rAF loop until the backlog drains. Each successful drain pass still runs the full markdown pipeline and forced height measurement before the remaining text appears.
- Scaling input: Unrevealed word backlog at completion and complexity of the full accumulated response. At the 80 words/s completion floor, at least one new word becomes due each 16 ms frame on a 60 Hz display, so effective commit cardinality is up to one full-prefix rebuild per frame until caught up.
- Effective concurrency: One serialized rAF chain per backlogged morpher; completion does not collapse the backlog into one render. Multiple independently completing chat widgets could drain concurrently without a shared limiter.
- Cache behavior: The final response prefix is not parsed or rendered once and reused; every drain step rebuilds a larger prefix. Warm KaTeX/editor pools reduce cold initialization but do not cache markdown parsing, DOM, decoration walks, or layout.
- Mechanism confidence: High: setRate floors completed streams at 80 words/s, needsNextFrame retains the rAF loop, and each committed prefix reaches the same full renderer and height read.
- Magnitude uncertainty: Backlog size depends on model burstiness and whether the UI fell behind before completion; the mechanism is most visible after a large/bursty response.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatIncrementalRendering/chatIncrementalRendering.ts:\_flushRender</code>: Repeated full-prefix markdown/DOM/code-block reconstruction while draining buffered words.; cardinality: Up to one per display frame for backlogWords divided by words revealed per frame; at 80 words/s and 60 Hz this is commonly one or more words per frame, hence near-60 rebuilds/s.
    - Introduced by diff: true; previous behavior: Completion still accelerated progressive rendering, but the WindowIntervalTimer limited reconstruction to one pass every 50 ms and could reveal several words in that pass.; critical-path effect: On the critical path to showing the completed response's buffered tail; CPU and layout can delay visual completion and drop frames.
- Verdict: Covered by the two submitted findings; completion amplifies their cadence rather than introducing a separate issue.

### Scenario 3: Use paragraph buffering, switch animation/buffering configuration, or render completed responses from chat history.

- Cache behavior: lastBlockBoundary does not cache scan state, but the prior progressive implementation also rescanned full markdown for word counting on its timer, and repository evidence does not establish a sufficiently higher realistic model-event cardinality for a separate high-confidence regression. CSS filter/mask animation cost depends heavily on compositor behavior and chosen opt-in style.

- Verdict: No additional finding: paragraph rendering is boundary-coalesced, completed history bypasses the morpher, cleanup cancels pending rAF work, and animation costs are bounded/intentional.
