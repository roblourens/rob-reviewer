## Findings (1)

### 1. [medium] Scope Dev Container availability invalidation to the changed host

**Finding ID:** `PERF-0821F7834E9B`  
**Location:** <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/devContainerAgentHostService.ts:185</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem existence checks and remote Agent Host RPC calls  
**Scaling:** Each connection-state event invalidates availability for every cached recent workspace; rebuilding the visible picker performs two fileService.exists calls per effective local or connected-remote recent, with up to four probes concurrently, and configured workspaces also issue an isDockerAvailable RPC. Cost grows with recent-workspace count and repeats across connecting, connected, reconnecting, and disconnected transitions.  
**Outcome:** excessive filesystem/remote I/O and delayed Dev Container mode decoration while connecting or reconnecting hosts  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this added listener, the Dev Container availability event fired only when the connector was registered or removed, so the workspace picker retained its per-provider/per-folder cache across unrelated remote connection changes.  
**Changed behavior:** Every IRemoteAgentHostService connection change now emits one global Dev Container availability event. Each initialized provider re-emits it, and WorkspacePicker responds by clearing its entire availability map and limiter before re-probing all visible recent workspaces.  
**Confidence:** 0.98 — The changed event source, repeated connection-state emissions, global cache clear, two-per-workspace filesystem boundary, limiter, and picker-visible refresh path are all directly traced in repository code. Exact recent counts and filesystem/network latency vary, which affects severity but not the mechanism.

**Causal diff evidence:** RIGHT line 185 newly registers \`this.\_remoteAgentHostService.onDidChangeConnections(() =&gt; this.\_onDidChangeAvailability.fire())\`, converting every generic remote connection transition into a global availability-cache invalidation; no equivalent connection-driven invalidation existed before the diff.

Opening the workspace picker while connecting or reconnecting an SSH/Tunnel host causes all local and other-host Dev Container availability entries to be discarded and probed again. RemoteAgentHostService emits at least once before connect and again after connect, so a normal host connection can repeat the full cold probe and generate 2N filesystem calls for N recents per transition, plus Docker RPCs for configured folders.

**Evidence:** The added line forwards every onDidChangeConnections event without identifying the affected address or checking whether Dev Container capability changed. RemoteAgentHostService fires this event before client.connect(), after successful connection, and on reconnect state changes. WorkspacePicker subscribes to each provider's onDidChangeDevContainerAvailability and calls \_clearDevContainerAvailability(true), which clears the global cache/limiter; rebuilding invokes \_isDevContainerWorkspaceAvailable for each recent. The connector's hasDevContainerConfiguration uses Promise.all over two fileService.exists calls, and then calls mainService.isDockerAvailable for matching folders.

**Suggested direction:** Track the availability signature per SSH/Tunnel address and emit only when that host's connected/capability state changes, carrying the affected provider/address so WorkspacePicker invalidates only matching cache keys. Preserve the existing global invalidation only for connector registration/removal.
