# Performance review: Fix built-in extensions manifest cache never being hit

[PR #336383](https://github.com/microsoft/vscode/pull/336383) at `884e006365dfc8ac4e3c496ddc945dc2622dab17`

## Findings (1)

### 1. [low] Coalesce cache invalidation for batched installs

**Finding ID:** `PERF-1BB33C635A05`  
**Location:** <code>src/vs/platform/extensionManagement/node/extensionsManifestCache.ts:47</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem directory resolutions and cache-file delete operations  
**Scaling:** For an install event containing N successful extensions for one profile, this loop invokes invalidation N times. The new invalidation performs at least N directory resolves and can race up to N×L deletes for the same L language cache files, although one resolve/delete set is sufficient.  
**Outcome:** redundant filesystem I/O bursts and reduced post-install throughput  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Each result attempted one direct delete of the single known user-cache path; it did not enumerate the cache directory or fan out across language files.  
**Changed behavior:** Each successful result independently calls deleteUserCacheFiles, which resolves the profile cache directory and deletes every matching per-language file with Promise.all.  
**Confidence:** 0.97 — The event batching, lack of coalescing, and filesystem operations are directly traced in code. The exact duration depends on extension count, locale-cache count, and filesystem speed, so severity is low, but the redundant operation count and concurrency are deterministic for batched results.

**Causal diff evidence:** RIGHT line 47 replaces the per-result single-file deletion with deleteUserCacheFiles; changed lines 58-63 make every invocation enumerate cacheHome and fan out deletes across matching language files.

Updating all extensions, importing a profile, installing workspace recommendations, or Settings Sync can produce one event with many successful results for the same profile. The listener launches all invalidations without awaiting or coalescing them, so these redundant directory reads and racing deletes run concurrently with follow-up extension work and can degrade post-install responsiveness.

**Evidence:** AbstractExtensionManagementService fires one onDidInstallExtensions event containing the full results array after a batched install (abstractExtensionManagementService.ts:562), and updateAll/profile import/Settings Sync pass collections to installGalleryExtensions. This handler loops every local result and calls invalidate; invalidate awaits the newly added fileService.resolve and Promise.all deletes. There is no profile deduplication or shared in-flight invalidation.

**Suggested direction:** Deduplicate successful results by profile and invalidate each profile once per event; additionally share an in-flight invalidation per profile if metadata/uninstall bursts can overlap, while preserving deletion of every language cache.

### 2. repeated-work

**Fix location:** `src/vs/platform/extensionManagement/common/extensionsScannerService.ts:972` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/extensionManagement/common/extensionsScannerService.ts:970`  
**Introducing path:** `src/vs/platform/extensionManagement/common/extensionsScannerService.ts`  
**Introducing commit:** `2df55d8428d1d6464a78d2778006791133987150`  
**Mechanism family:** `repeated-work`  
**Performance category:** `io`  
**Confidence:** 0.99

**Mechanism:** Every cache hit scheduled validateCache, which calls super.scanExtensions and therefore re-enumerates the built-in extension directory and rereads/parses manifests and localization files after a three-second delay.

**Symptom:** A warm startup that successfully used the built-in cache still performed a redundant full built-in extension scan shortly afterward, creating avoidable filesystem I/O and CPU contention during startup settling.

**Fixed behavior:** Installed-product system-extension cache hits no longer schedule validation; user-extension and development-mode caches retain validation.

**Evidence:** The deleted unconditional trigger reached validateCache, whose expected value is built from await super.scanExtensions(this.input); ExtensionsScanner.scanExtensionsFromLocation resolves the directory and scans every child concurrently. The new type/devMode guard and focused timer test verify that built-product system hits do not execute that scan.
