# Performance review: \[Experiment\] Show a pip and popup when a Copilot sale is ongoing and the chat is closed

[PR #331588](https://github.com/microsoft/vscode/pull/331588) at `473e0be5e8b42add978bb2b5c9c2a6bb667f2526`

## Findings (2)

### 1. [medium] Gate the global keydown handler behind an armed promo

**Finding ID:** `PERF-AFBB6A4A6C32`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatPromoWidget.ts:105</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Main-thread keyboard event normalization and one StandardKeyboardEvent allocation per keydown  
**Scaling:** The added capture listener runs once for every keydown anywhere in the workbench for the entire window lifetime, including all editor typing, even when no promo is eligible or displayed.  
**Outcome:** Persistent extra CPU and allocation/GC pressure on the latency-sensitive typing path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no ChatPromoIconPopup contribution and no promo keydown listener on the main workbench container, so ordinary editor keystrokes did no promo-related work.  
**Changed behavior:** Constructing ChatPromoIconPopup at AfterRestored installs a capture-phase listener on mainContainer unconditionally; onWorkbenchKeyDown constructs StandardKeyboardEvent and computes normalized key/chord state before it checks whether a promo payload exists.  
**Confidence:** 0.98 — The registration, global event target, eager contribution construction, and pre-guard allocation are all directly visible in the changed code; no assumptions about model count, experiment enrollment, or network state are required.

**Causal diff evidence:** Added line 105 installs \`keydown\` on the entire main container during unconditional popup construction; the new handler normalizes each event before any \`pendingPayload\` check.

Every user pays promo-specific main-thread work on every keystroke, not just users in the experiment or while the pip is armed. During sustained typing this adds one object allocation and key-normalization pass per input event, increasing input-path CPU and GC pressure.

**Evidence:** The constructor at line 105 registers the listener unconditionally. Its target is layoutService.mainContainer, so editor keydowns bubble through it. onWorkbenchKeyDown immediately executes \`new StandardKeyboardEvent(e)\`; that constructor copies modifiers, calls extractKeyCode, and computes both keybinding and chord values. The pending-promo guard exists only later in onPipActivate. ChatClosedPromoContribution is registered globally at WorkbenchPhase.AfterRestored, so this path is active even with no eligible sale.

**Suggested direction:** Register the keydown/click interception only while \`pendingPayload\` is armed and dispose it in \`disarmChatPromo\` (preferably on the current icon anchor). At minimum, return before constructing StandardKeyboardEvent when no payload is pending.

### 2. [low] Do not rescan promo state on every workbench layout

**Finding ID:** `PERF-E799E53C7E01`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatClosedPromo.ts:78</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Main-thread model iteration, temporary arrays/Sets, storage decoding, and an eligible-case DOM geometry read  
**Scaling:** Cost is O(L × (M + D + S)), where L is main-container layout events during resize/part transitions, M is registered language models, and D/S are persisted dismissed/seen promo histories; none of this work is coalesced.  
**Outcome:** Extra resize/layout latency plus avoidable allocation and GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR no closed-promo contribution listened to main-container layouts, so resizing or changing workbench part visibility did not parse promo storage or scan the language-model cache.  
**Changed behavior:** The added layout listener calls the full \`sync()\` on every main-container layout. \`sync()\` calls \`getOpportunity()\`, which allocates and populates two Sets from application storage, allocates the language-model ID array and scans it; when a sale is eligible it then calls \`getClientRects()\` immediately after the grid layout.  
**Confidence:** 0.95 — The resize-to-layout-to-sync call path and all repeated allocations/scans are directly established in repository code. Exact model counts and milliseconds vary, which is reflected in low severity, but the synchronous multiplicity is certain.

**Causal diff evidence:** Added line 78 moves the entire closed-promo recomputation onto every main-container layout event; this listener and work were absent before the PR.

Native window resize events call \`layoutService.layout()\`, which fires this event after laying out the workbench grid. Continuous resizing therefore repeats the full promo scan on the synchronous rendering path for all users, and eligible users also incur a geometry read after layout writes, increasing resize jank as model/history cardinality grows.

**Evidence:** Workbench window resize calls \`layoutService.layout()\`, and WorkbenchLayout.layout writes container/grid dimensions before firing onDidLayoutMainContainer. The new line 78 subscribes \`sync\` directly. In changed getOpportunity, every call reads both storage keys into new Sets and iterates getLanguageModelIds(); getLanguageModelIds itself returns a newly allocated Array from the model cache. Changed line 94 additionally evaluates anchor.getClientRects() for eligible promos.

**Suggested direction:** Cache the opportunity and recompute it only from the existing language-model/storage/chat-state events. On layout, update only anchor availability, coalesced to at most once per animation frame; avoid a synchronous geometry read in the post-grid-layout callback (for example, track visibility with an observer/state event).

### Scenario 1: Normal editor typing after the workbench restores, including users with no eligible promo or experiment enrollment

- Critical path: Each keydown bubbles through the newly registered capture listener before editor input completes; the added handler synchronously constructs and normalizes a StandardKeyboardEvent before it can discover that no promo is pending.
- Scaling input: One invocation and allocation per workbench keydown for the lifetime of the window; sustained typing directly controls cardinality.
- Effective concurrency: Fully serialized on the renderer main thread with the rest of keyboard dispatch; there is no debounce, gating, or coalescing.
- Cache behavior: No cache is relevant: even a stable absent \`pendingPayload\` does not prevent event normalization because the guard occurs after construction.
- Mechanism confidence: High: eager contribution construction, main-container capture registration, and pre-guard StandardKeyboardEvent construction are all explicit in the changed code.
- Magnitude uncertainty: The exact per-keystroke duration and resulting GC frequency depend on device and workload, but the global hot-path work and allocation are certain.
- Expensive boundaries: none found
- Verdict: Reportable: the diff adds avoidable promo work to every user's latency-sensitive typing path.

### Scenario 2: Window resize and workbench part visibility/layout transitions with Chat collapsed

- Critical path: A viewport resize synchronously lays out the workbench grid and then fires onDidLayoutMainContainer; the new listener immediately runs full promo synchronization before the event completes. Eligible promos additionally execute getClientRects after layout writes.
- Scaling input: Cost grows with main-layout event frequency, registered language-model count, and dismissed/seen promo history size; continuous resizing can generate many events without coalescing.
- Effective concurrency: Synchronous and serialized on the renderer main thread; no frame coalescing or debounce exists.
- Cache behavior: Treatment is cached after resolution, but opportunity state is not: both storage sets and the model ID array are recreated and rescanned on every layout event, on both cold and warm treatment states.
- Mechanism confidence: High: window resize calls layout(), layout writes grid dimensions then emits the event, and the changed callback directly invokes the full sync path.
- Magnitude uncertainty: Model/history cardinality and resize frequency vary, so severity is low, but repeated work on the rendering path is established.
- Expensive boundaries: none found
- Verdict: Reportable: cacheable promo state and a synchronous geometry check were newly placed on every main-container layout.

### Scenario 3: Eligible discounted model appears while Chat is collapsed and the status icon is visible

- Mechanism confidence: High for the lookup path and coalescing; whether a particular lookup reaches the network depends on assignment-service warm state.
- Magnitude uncertainty: Cold fetch latency varies, but it is off the application critical path and therefore not independently reportable.

- Verdict: No additional finding: the potentially remote lookup is eligibility-gated, coalesced, cached, and off the workbench critical path.

### Scenario 4: Promo banner renders in one or more chat inputs and records that the sale was seen

- Critical path: After rendering and shown telemetry, onDidShow synchronously reads the seen-ID set and stores it only if the promo ID is new. That storage notification then causes the closed-promo contribution to resync.
- Scaling input: At most one persisted write per unique promo ID across inputs/windows in the normal non-racing case; later renders still parse/check the small set but do not write.
- Effective concurrency: Inputs can render independently, but application storage and the membership check deduplicate ordinary repeats; only a genuine cross-window race can duplicate work.
- Cache behavior: The seen set is persisted but not bounded or expired. Its growth follows the number of distinct promo campaigns over the application lifetime, expected to be low; the same ID is negative-cached by membership.
- Mechanism confidence: High for storage cardinality and callback placement.
- Magnitude uncertainty: Future campaign count is unknown; realistic growth is too small to establish meaningful retained-memory or serialization impact.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/chatPromoNotification.ts:onDidShow</code>: Persist and broadcast the application-scoped \`chat.seenPromoIds\` value.; cardinality: One store per distinct promo ID after deduplication, not one per render or input.
    - Introduced by diff: true; previous behavior: Banner display did not persist a separate seen-promo history.; critical-path effect: Runs immediately after the notification render callback; the write is needed only to suppress the collapsed-chat pip and is not on message-send progress.
- Verdict: No finding: writes are effectively deduplicated by promo ID, and evidence does not support a realistic unbounded-history performance consequence.

### Scenario 5: User opens the collapsed-chat promo card and clicks Try on a warm or cold Chat

- Critical path: Opening the card builds one small DOM subtree. Try executes the existing Open Chat command, reveals the widget, waits for a session resource only on a cold widget (bounded by two seconds), switches harness if needed, then selects or requests the promoted model.
- Scaling input: One card and one command sequence per user activation; there is no per-model fan-out and only the selected model identifier is processed.
- Effective concurrency: The CTA steps are deliberately serialized to preserve harness/model ordering. A cold unresolved session has one listener and one two-second timeout, both disposed in finally.
- Cache behavior: Warm widgets skip the session wait and use the current model list. If the model is already present, switchModelByIdentifier succeeds synchronously; otherwise requestProgrammaticSelection waits for existing model discovery rather than starting an explicit network call here.
- Mechanism confidence: High: the changed command path and bounded timeout are explicit, and the transitive model request was checked.
- Magnitude uncertainty: Chat reveal duration depends on current UI state, but the PR does not add per-item boundary fan-out or unbounded concurrency.
- Expensive boundaries: none found
- Verdict: No finding: one user-triggered sequence is bounded, cleaned up, and ordered; no concrete performance regression beyond required feature work was established.

### Scenario 6: Promo remains armed while status-bar entries update or the Chat status entry is replaced

- Critical path: A MutationObserver on the Chat entry's parent receives right-status-bar subtree child-list changes and reapplies the icon/ARIA state; if the anchor is replaced it reconnects, and if absent it retries every 250 ms until disarmed or found.
- Scaling input: Observer callbacks follow status-bar child-list mutation batches; missing-anchor retries occur four times per second while a payload remains pending.
- Effective concurrency: Mutation records are browser-batched; retry ownership uses one MutableDisposable timer, so there is only one outstanding retry and no burst.
- Cache behavior: An unchanged promo payload prevents re-arming from sync, while the observer maintains the current DOM state. Retry state is cleared on disarm/dispose.
- Mechanism confidence: High for observer and timer behavior; real-world duration of an absent anchor after treatment activation is uncertain.
- Magnitude uncertainty: The observer's per-callback DOM work is small, and a permanently missing anchor after treatment activation was not shown to be prevalent enough for a separate performance finding.
- Expensive boundaries: none found
- Verdict: No finding: lifecycle is bounded to one observer/timer and the demonstrated costs are insufficient for a concrete user-visible regression.
