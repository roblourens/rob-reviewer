### Scenario 1: Default-chat session eviction and reconstruction before an Agent Host restart in parity E2E persistence tests

- Critical path: The helper unsubscribes the default chat and session, then \`fetchSessionWithChat\` sequentially awaits session and default-chat subscribe RPCs. The server-side subscribe waits for any in-flight residency release before restoring, so reconstruction—not a fixed delay—gates progress.
- Scaling input: One session and its default chat per helper invocation; two test cases call the helper, with retries bounded at 20. Turn comparison scales with the small transcript created by each test.
- Effective concurrency: Subscribe calls are awaited sequentially. Server releases are serialized by the residency sequencer and subscribe joins an in-flight release/restore; there is no new aggregate burst.
- Cache behavior: A warm snapshot is rejected by response-part identity, while successful eviction produces a cold restore with new IDs. Server-side release and restore are coalesced; failed attempts unsubscribe before retry so retained subscriptions do not suppress the next eviction.
- Mechanism confidence: High: helper, retry implementation, ordered WebSocket transport, subscription handler, residency wait, and restore call path were traced directly.
- Magnitude uncertainty: Provider release/restore duration varies by provider, but the changed observable wait removes rather than adds a fixed 50 ms critical-path delay and does not increase successful-path boundary cardinality.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/test/node/e2e/suites/sessionPersistenceSuite.ts:83-105, via TestProtocolClient.notify/call</code>: Local WebSocket JSON-RPC unsubscribe notifications and subscribe requests; cardinality: Three unsubscribe notifications initially and after each failed attempt (two when no additional chat), plus two sequential subscribe requests per attempt; retries are capped at 20 with 50 ms spacing.
    - Introduced by diff: false; previous behavior: The same unsubscribe and two subscribe operations occurred after an unconditional 50 ms sleep; failed identity checks explicitly unsubscribed the default chat and session.; critical-path effect: The two subscribe round trips and any server-side release/restore they await are on the test critical path.
  - filesystem at <code>src/vs/platform/agentHost/node/agentSessionResidency.ts:\_release and src/vs/platform/agentHost/node/agentService.ts:subscribe/restoreSession</code>: Wait for session database writes to become idle, release provider chat state, and restore persisted session/default-chat state; cardinality: At most one coalesced release and one restore for the one session per successful helper invocation; retries can repeat only after a failed attempt and are capped at 20.
    - Introduced by diff: false; previous behavior: The same release and restoration were triggered by unsubscribe/subscribe, but the test inserted a blind 50 ms delay before observing completion.; critical-path effect: Server subscribe explicitly awaits the in-flight release and then restores missing state, so the boundary is observable and on the critical path.
  - other at <code>src/vs/platform/agentHost/node/agentService.ts:\_getChatMessages</code>: Provider transcript reconstruction through provider.chats.getMessages; cardinality: One default-chat transcript read on a successful cold reconstruction; state-manager and in-flight caches avoid duplicate work within an attempt.
    - Introduced by diff: false; previous behavior: The pre-diff helper triggered the same provider reconstruction after its fixed delay.; critical-path effect: The session subscribe does not complete until the provider transcript and persisted overlays are hydrated.
- Verdict: No reportable regression. The changed retry cleanup prevents failed attempts from retaining subscriptions, and immediate observation safely waits on the authoritative release rather than creating parallel or unbounded work.

### Scenario 2: Peer-chat persistence reconstruction and materialization before server restart

- Critical path: After the owning session/default chat have been observably reconstructed, the changed loop sequentially subscribes to each supplied peer chat. That subscribe resolves the restored peer's lazy provider backing and transcript before the helper permits restart.
- Scaling input: The caller supplies exactly one peer chat. The helper accepts a collection, but processes it sequentially and this PR does not introduce a realistic large-cardinality caller.
- Effective concurrency: Additional chats are materialized serially. Per-chat resolution coalesces concurrent work, and session residency release is sequenced.
- Cache behavior: The owning session is cold-restored first. The peer starts as catalog-only and is materialized once; successful peer state is cached. On any failed attempt, all session/chat subscriptions are removed before retry, enabling a fresh eviction rather than pinning warm state.
- Mechanism confidence: High: the sole caller, sequential loop, subscribe RPC, lazy peer resolver, database reads, provider materialization, transcript fetch, and state cache were directly traced.
- Magnitude uncertainty: Provider-specific peer materialization latency can vary, but cardinality is exactly one in the changed test and the operation is required to establish the tested state before restart.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/test/node/e2e/suites/sessionPersistenceSuite.ts:97-99</code>: Local WebSocket JSON-RPC subscribe for each additional peer chat; cardinality: One additional request for the sole \`peerUri\` passed by the only caller; sequential for a general additionalChats array and repeated only if that attempt fails, with 20 total attempts maximum.
    - Introduced by diff: true; previous behavior: The helper did not re-subscribe/materialize the peer before restart and only verified the default chat reconstruction.; critical-path effect: Intentionally blocks restart until the peer snapshot is materialized, making the persistence assertion deterministic.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_materializeRestoredPeerChat</code>: Read peer metadata/draft/workspace-transition persistence during lazy chat resolution; cardinality: One peer-chat materialization for the one peer in this test; successful state is cached and concurrent same-chat resolutions are coalesced.
    - Introduced by diff: true; previous behavior: This pre-restart peer materialization boundary was absent.; critical-path effect: The peer subscribe awaits these reads before returning.
  - other at <code>src/vs/platform/agentHost/node/agentService.ts:\_materializeRestoredPeerChat and \_getChatMessages</code>: Materialize the provider chat backing and fetch the peer transcript; cardinality: One provider materialize call and one transcript read for the single peer chat on the successful path; no parallel peer fan-out because the loop awaits each call.
    - Introduced by diff: true; previous behavior: The peer was left lazy until after restart, which made the intended persistence scenario race reconstruction.; critical-path effect: These operations are deliberately on the test critical path so restart cannot happen before peer restoration.
- Verdict: No reportable performance regression. The one newly introduced materialization is bounded, sequential, test-only, and necessary for the scenario's authoritative completion condition; it does not create collection fan-out or production-path cost.

**Summary:** Completed the performance pass over the sole changed test file and traced retry, subscription, residency release, session restore, and lazy peer-chat materialization paths. No actionable diff-introduced performance regression was found.
