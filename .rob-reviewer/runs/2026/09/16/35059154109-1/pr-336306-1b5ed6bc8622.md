### Scenario 1: Fresh or prewarmed Codex chat sends its first user turn in a trusted workspace

- Critical path: Before turn/start can be issued, the send awaits materialization, then the added post-start hooks/list recheck. If grants changed, it also awaits thread/unsubscribe and replacement thread/start. Baseline checkpointing and later customization publication remain off the critical path.
- Scaling input: One recheck per chat before its first successful turn; the request is cwd-scoped to one primary working directory, not per hook or per workspace root. Hook result processing scales linearly with the returned catalog.
- Effective concurrency: Materialization is coalesced by session.materializePromise. The added hook recheck is sequential on the first-send path; normal host turn handling drains queued user messages after the active turn, so this does not create aggregate per-item fan-out. Different chats can progress independently as before.
- Cache behavior: An untrusted or missing cwd short-circuits without IPC. Trusted workspaces query the app-server catalog even when a prewarm populated it; warm catalogs avoid replacement when the signature matches. There is no host cache because Workspace Trust and hook hashes must be current; pending trust is consumed and cleared after replacement.
- Mechanism confidence: High confidence in the extra serialized IPC and conditional replacement: changed code and unit request-order assertions establish both cardinality and critical-path placement.
- Magnitude uncertainty: The external app-server implementation and measured warm/cold hooks/list latency are not in this repository, so exact milliseconds are unknown. The added round trip is one-time per chat and specifically required to observe a catalog that becomes available only after startup.
- Expensive boundaries:

### Scenario 2: A restored Codex session resumes on a cold or warm app-server

- Critical path: Resume preparation performs the existing initial hooks/list before thread/resume. When that result contains no eligible grants, the changed path awaits one post-resume hooks/list; only newly discovered grants cause thread/unsubscribe and a second thread/resume. MCP inventory refresh after successful resume remains fire-and-forget.
- Scaling input: One restored thread at a time per session; the added fallback is one cwd-scoped catalog request when initial eligible grant count is zero, plus one replacement resume only if late eligible project hooks appear.
- Effective concurrency: session.resumePromise coalesces concurrent resume demand for the same session, and all hooks/list/resume/unsubscribe calls are serialized. Different restored sessions remain independent; no new shared burst is created by a single collection loop.
- Cache behavior: Warm catalog with eligible project hooks skips the second query. Empty/ineligible catalogs take one negative recheck because the first cold resume may populate project hooks; a second empty result is not retried in a loop. Failures return undefined and do not trigger replacement.
- Mechanism confidence: High confidence: changed control flow and tests explicitly establish hooks/list, resume, hooks/list, unsubscribe, resume ordering, with no loop after the second resume.
- Magnitude uncertainty: Exact catalog scan and resume costs are external and unmeasured here. The tests prove the maximum changed sequence but not production prevalence of cold empty catalogs.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:6666 \_resumeSession/resumeWithHookTrust</code>: Initial thread/resume using the pre-resume hook trust snapshot; cardinality: One per restored session, unchanged except that it may be followed by a bounded retry
    - Introduced by diff: false; previous behavior: One thread/resume was issued after one pre-resume hooks/list.; critical-path effect: Required resume boundary on the send/restore critical path
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:6670 \_resumeSession</code>: Re-query hooks/list after an empty-grant initial resume; cardinality: At most one added request per resume attempt whose initial eligible grant set is empty
    - Introduced by diff: true; previous behavior: No post-resume catalog query occurred.; critical-path effect: Serialized after initial resume and before the session is considered resumed
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:6674 \_resumeSession</code>: Unsubscribe and resume the thread again with late-discovered grants; cardinality: At most one added unsubscribe and one added resume when the second query finds eligible grants
    - Introduced by diff: true; previous behavior: The initial resume completed without a late-grant replacement.; critical-path effect: Adds two serialized round trips only in the cold late-discovery case
  - filesystem at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:7639 \_tryBuildSessionHookTrustState</code>: App-server hook catalog discovery behind the post-resume hooks/list request; cardinality: One cwd catalog query in the empty-grant fallback
    - Introduced by diff: true; previous behavior: Only the pre-resume hook catalog was queried.; critical-path effect: Transitively contributes to resume latency
- Verdict: No reportable regression. The extra work is bounded to the cold/negative-catalog recovery path, same-session resumes are coalesced, warm positive catalogs skip it, and no unbounded retry or fan-out is introduced.

### Scenario 3: Direct backing creation or fork applies workspace hook trust

- Critical path: The operation builds one trust snapshot and awaits one hooks/list before thread/start or thread/fork. Trust context validation is synchronous and may rebuild only if Workspace Trust or cwd changes during the operation.
- Scaling input: One cwd-scoped catalog per direct creation or fork; grant signature work scales linearly with the returned eligible hooks.
- Effective concurrency: Each chat creation is serialized by \_chatLifecycleSequencer for that chat. There is no new per-hook IPC and no changed global limiter behavior.
- Cache behavior: No host cache is added; an untrusted cwd returns an empty snapshot without hooks/list. A context change invalidates the snapshot and can cause one fresh query before applying it, preserving authorization freshness.
- Mechanism confidence: High confidence that normal boundary cardinality is unchanged; changed call sites only pass cwd and validate the captured trust context.
- Magnitude uncertainty: A trust/cwd mutation during the small discovery-to-apply window can add a rebuild, but prevalence is low and bounded by user configuration changes.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:4884,5263 direct start/fork trust application</code>: Fetch hooks/list and then start or fork one Codex thread; cardinality: One hooks/list plus one thread/start or thread/fork per operation
    - Introduced by diff: false; previous behavior: These operations already queried hooks/list and then started/forked a thread; the diff wraps grants with a context signature without increasing normal boundary count.; critical-path effect: Awaited before creation/fork completes
- Verdict: No performance regression: normal IPC count, cardinality, and serialization are unchanged, while added signatures are small bounded CPU/allocation work.
