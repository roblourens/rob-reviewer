# Performance review: chat: surface out-of-band subagent approvals

[PR #336317](https://github.com/microsoft/vscode/pull/336317) at `fb8d71608489e1d27a4dfdabe64237d50c0a820e`

## Findings (3)

### 1. [medium] Avoid rescanning every request for each response delta

**Finding ID:** `PERF-D37902637A22`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentSessionApprovalModel.ts:119</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Main-thread CPU work and a reversed request-array allocation  
**Scaling:** With H requests in a live session and D streamed response updates, the autorun performs O(H × D) request iteration while no approval is pending; the response pending observable also scans the active response parts on those updates.  
**Outcome:** Increasing UI-thread CPU and GC pressure in Sessions/Automations views as chat history grows  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous model observed the session-level \`requestNeedsInput\` signal and inspected only the latest response after that signal became truthy, so ordinary token streaming did not trigger a historical request scan.  
**Changed behavior:** The new autorun reverses and walks all requests, creates/subscribes a broad \`response.onDidChange\` signal for each visited response, and reads that signal before checking \`isPendingConfirmation\`. Consequently, normal content updates in the active response rerun the full historical search even when every pending state remains false.  
**Confidence:** 0.99 — The changed subscription order and response event cadence are directly traced. The model is instantiated by Sessions lists, Automations, and blocked-session indicators; only the exact history length at which stutter is noticeable is uncertain.

**Causal diff evidence:** The PR replaces the previous last-response/requestNeedsInput path with a reverse full-history loop and adds \`changed.read(reader)\` before the pending-state guard, directly moving the historical scan onto every streamed response change.

When a live chat streams while a Sessions, Automations, or blocked-session surface owns this approval model, long histories cause progressively more synchronous work per token and can make those UI surfaces stutter.

**Evidence:** \`ChatResponseModel\` forwards every non-quiet response content change through \`onDidChange\`. The added \`changed.read(reader)\` subscribes the full-history autorun to that broad event. In the common no-approval case, the loop reaches and subscribes every historical response and allocates \`toReversed()\` each run. \`isPendingConfirmation\` is already derived from response/tool state and only needs to notify this consumer when its value changes.

**Suggested direction:** Track the request collection on structural model changes, but observe each response's \`isPendingConfirmation\` value rather than its broad \`onDidChange\`; only scan that response's parts when pending transitions to a non-empty state, preserving newest-request precedence.

### 2. [medium] Stop diffing the full transcript on every streamed update

**Finding ID:** `PERF-A160EC026C5A`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts:1020</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Main-thread CPU work and temporary arrays/Sets/observable transactions  
**Scaling:** For H transcript responses and D non-quiet response deltas, this adds O(H × D) collection filtering and keyed reconciliation; H includes offscreen history that virtualization previously kept off the render path.  
**Outcome:** Increased main-thread CPU/GC pressure and dropped-frame risk while long chats stream  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, confirmation routing was installed from rendered tool/subagent parts, so a response delta did not enumerate and keyed-diff every response in the transcript.  
**Changed behavior:** The new observable maps every broad view-model change to \`getItems().filter(isResponseVM)\`, and its keyed autorun traverses that newly allocated response array even when no approval exists.  
**Confidence:** 0.99 — The event chain, synchronous collection work, and O(history × deltas) scaling are explicit in the repository. Exact frame loss depends on history length and stream cadence, so that affects severity rather than mechanism confidence.

**Causal diff evidence:** The added \`observableFromEvent(this, viewModel.onDidChange, () =&gt; viewModel.getItems().filter(isResponseVM))\` puts whole-transcript enumeration behind the per-response streaming event; no equivalent model-wide observer existed before the PR.

In a long conversation, each streamed markdown/reasoning/tool delta synchronously walks all historical responses on the UI thread, so opening or continuing a heavily populated chat can become progressively less responsive while the answer streams.

**Evidence:** \`ChatViewModel.onAddResponse\` forwards every \`ChatResponseViewModel.onDidChange\` to \`viewModel.onDidChange\`; \`ChatResponseModel\` fires that event from \`Response.onDidChangeValue\` for each non-quiet progress update. The added line responds by calling \`getItems()\` (which filters all \`\_items\`) and filtering again for responses. \`autorunPerKeyedItem\` then traverses the entire returned array and builds a \`Set\` on each invalidation. This work happens regardless of whether \`isPendingConfirmation\` is true.

**Suggested direction:** Drive the keyed response collection only from structural add/remove/initialize events, or maintain an incrementally updated response index; subscribe directly to each indexed response for pending-state transitions without rebuilding the full collection on generic response changes.

### 3. [low] Do not reconstruct the full transcript during send-only resume

**Finding ID:** `PERF-31B25B4CD25C`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:2496</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** SDK RPC bytes, database reads, event-loop CPU, and reconstructed turn objects  
**Scaling:** Cold-resume cost grows with the persisted event count and edit-tool history; replay makes multiple full event passes and one batched historical edit read.  
**Outcome:** Extra I/O and CPU contend with the newly submitted turn, increasing cold resumed-session latency and allocation pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Persisted events were fetched and mapped only when getMessages or getSubagentMessages requested transcript data; a resume used solely to send a turn did not reconstruct full history.  
**Changed behavior:** Every resumed session now starts the full memoized mapped-events pipeline from initializeSession merely to seed subagent names.  
**Confidence:** 0.96 — The resume/send call path and replay boundaries are explicit; uncertainty is limited to how often history is requested immediately anyway and typical log size.

**Causal diff evidence:** The added \`\_getMappedEvents()\` call moves full transcript RPC/database reconstruction from explicit history reads onto every cold resumed-session initialization.

Sending to a long session evicted from memory starts a full event-log transfer, historical edit metadata read, and turn reconstruction alongside first-response processing.

**Evidence:** The send path reaches \_ensureResolvedChatSession and awaits initializeSession. The added call starts \_computeMappedEvents, which invokes session.getEvents and mapSessionEvents; replay then calls db.getFileEdits for all historical edit calls and constructs all parent/subagent turns. Memoization only prevents a later duplicate read.

**Suggested direction:** Cache raw events or a lightweight agent-name index during resume, but defer mapSessionEvents and its historical edit load until getMessages or getSubagentMessages actually requests history.

### Scenario 1: Stream a response in a long writable chat while discovering confirmations from offscreen historical responses

- Critical path: Each non-quiet response progress update synchronously fires ChatResponseModel -&gt; ChatResponseViewModel -&gt; ChatViewModel.onDidChange on the UI thread; the new response collection mapping and keyed reconciliation complete before observers settle. No boundary call is involved.
- Scaling input: Number of transcript responses H, including virtualized/offscreen history, multiplied by streamed deltas D; response-part count also affects the pending-state derivation for the changing response.
- Effective concurrency: Single UI-thread serialization; there is no debounce or frame coalescing around the new whole-transcript collection observer.
- Cache behavior: Per-response keyed cells are retained, but \`getItems()\` and both filtering/key-set passes are redone with newly allocated arrays/Sets for every broad view-model event. The cache does not avoid O(H) reconciliation.
- Mechanism confidence: High: the event forwarding, full collection creation, and keyed traversal are explicit.
- Magnitude uncertainty: Exact frame impact depends on transcript length, delta cadence, and concurrent renderer work; the synchronous O(H × D) mechanism is certain.
- Expensive boundaries: none found
- Verdict: Reportable repeated synchronous UI work introduced by the diff; finding submitted.

### Scenario 2: Show approval rows in Sessions, Automations, or blocked-session UI while a live chat streams

- Critical path: The approval model's autorun runs synchronously on response changes, reverses and scans request history, and reads pending state before the UI can settle. No subprocess, IPC, filesystem, database, or network operation is reached.
- Scaling input: Requests H per tracked live chat multiplied by streamed response changes D; when no approval is pending, every eligible historical response is visited/subscribed.
- Effective concurrency: Serialized on the renderer/UI thread. Multiple approval-model owners can independently observe the same live chat models; there is no shared scan/coalescer.
- Cache behavior: The request array is refreshed only on model structural events, but \`toReversed()\` allocates each autorun and broad response-change subscriptions invalidate the full search on ordinary content deltas. - Mechanism confidence: High: ChatResponseModel emits for non-quiet content changes and the added signal is read before the pending guard.
- Magnitude uncertainty: Visible stutter threshold depends on history size and how many approval-model surfaces are alive; the per-delta historical scan is directly established.
- Expensive boundaries: none found
- Verdict: Reportable repeated synchronous work introduced by the diff; finding submitted.

- Mechanism confidence: High for the added RPC trigger and global coalescing semantics.
- Magnitude uncertainty: SDK event ordering determines how often turn-end and background-task-change reads coalesce; no evidence establishes a costly enough uncoalesced rate for a separate finding.
- Expensive boundaries:
