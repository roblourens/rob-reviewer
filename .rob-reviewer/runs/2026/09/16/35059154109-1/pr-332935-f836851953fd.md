### 1. [medium] Avoid running the full preinstall twice on cache misses

**Finding ID:** `PERF-256119D80FC4`  
**Location:** <code>.github/workflows/pr.yml:48</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Nested npm/node-gyp subprocesses, package filesystem operations, and Electron/Node header cache or network I/O.  
**Scaling:** The duplicate full preinstall occurs once per node\_modules cache-miss job and multiplies across the six changed workflow jobs (and any architecture/template expansions); cold header/npm caches make each duplicate more expensive.  
**Outcome:** Increased cache-miss build latency and lower CI throughput from duplicated subprocess and I/O work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the diff, these jobs ran only root \`npm ci\`, which invoked the existing \`preinstall\` lifecycle once. They did not execute a separate full preinstall beforehand.  
**Changed behavior:** On every node\_modules cache miss, the job now executes the full preinstall once explicitly and once again as part of the immediately following root \`npm ci\`.  
**Confidence:** 0.98 — The changed workflow ordering, the root npm lifecycle declaration, and the preinstall implementation are all explicit. The cache-miss condition means the \`.postinstall-state\` guard stored under root \`node\_modules\` cannot suppress the first execution, and root \`npm ci\` recreates that directory before running its lifecycle, so it cannot suppress the second. Only the exact duration varies with runner caches and network speed.

**Causal diff evidence:** The added \`.github/workflows/pr.yml:48\` runs \`node build/npm/preinstall.ts\` immediately before the existing \`npm ci\`; identical added steps appear in five other changed workflows. The root \`package.json:23\` already declares that command as the \`preinstall\` lifecycle script, so \`npm ci\` invokes it again.

Cache-miss PR and product-build jobs wait for an extra nested npm installation plus two extra node-gyp header-install subprocesses, increasing pipeline latency, registry/cache I/O, and aggregate CI load across the six newly modified jobs.

**Evidence:** \`build/npm/preinstall.ts\` synchronously runs a nested \`npm ci\` for \`build/npm/gyp\`, then invokes \`node-gyp install\` for both Electron and Node headers and overlays files. The fast-path state lives at \`node\_modules/.postinstall-state\`; these workflow steps run specifically when node\_modules restoration missed. Therefore the added explicit call and the existing lifecycle call each launch the nested package installation and header checks/downloads on the build's critical path.

**Suggested direction:** Preserve the required early header overlay but avoid rerunning it from the lifecycle: add a focused header-preparation mode/marker and have the subsequent \`npm ci\` preinstall skip \`installHeaders\` when that exact preparation has already succeeded, while retaining the version/toolchain checks.
