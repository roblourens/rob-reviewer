### Scenario 2: TAS assignment refetch updates an open Settings editor using &#64;tag:expassigned

- Critical path: After the existing TAS refetch completes and the configuration contribution re-reads auto/pending settings, membership changes are coalesced to the next event-loop turn. If the assignment filter is active, the editor re-inspects changed keys and performs one search-model/TOC/tree rebuild; otherwise it performs only keyed updates.
- Scaling input: Number of assignment keys whose membership actually changed, deduplicated in a Set, and size of the current settings search result (up to the settings catalog for a filter-only query).
- Effective concurrency: The configuration throttler serializes refetch processing. RunOnceScheduler coalesces sequential/microtask membership changes into one notification and the editor performs one full rebuild for an active assignment filter, not one rebuild per key.
- Cache behavior: Warm TAS reads are in-memory. Membership lookups are O(1) Set reads; unchanged positive or negative membership does not emit. The search model rebuilds once because assignment membership changes filter inclusion.
- Mechanism confidence: High confidence from the scheduler implementation, 40-key batching test, editor rebuild tests, and changed event handler.
- Magnitude uncertainty: A full filter-only result can contain roughly the settings catalog, but assignment updates are infrequent and explicitly batched; no frame/input-frequency trigger was found.
- Expensive boundaries:
  - network at <code>src/vs/workbench/services/assignment/common/assignmentService.ts: refetchAssignments and onDidRefetchAssignments</code>: Existing periodic/account-triggered TAS refetch; cardinality: One existing refetch for the logical assignment update; changed configuration reads use the initialized client cache rather than adding per-setting network requests.
    - Introduced by diff: false; previous behavior: TAS already refetched and emitted onDidRefetchAssignments; the diff adds local membership propagation and editor refresh after that boundary.; critical-path effect: The network refetch precedes assignment-change publication; editor rendering does not issue network, filesystem, database, subprocess, or IPC work.
- Verdict: No reportable regression: collection-wide UI work is gated to the active new filter and coalesced once per assignment batch; inactive searches retain keyed refresh behavior.

### Scenario 3: Opening and searching Settings, including toggling the ExP Assigned filter

- Critical path: Search parsing builds the local result model, each candidate setting is inspected as needed, assignment membership is checked from an in-memory Set, matching rows are filtered, and the settings tree/TOC are rendered. - Cache behavior: Assignment status is a constant-time in-memory Set lookup. SearchResultModel retains its existing unique-result cache and clears/rebuilds only under existing result changes or the new membership-driven filter refresh.
- Mechanism confidence: High confidence from SettingsTreeSettingElement, SearchResultModel.updateChildren, renderTree, and focused/context-menu tests.
- Magnitude uncertainty: Exact catalog size and render duration vary, but the added per-element work is a constant-time Set lookup/tag update and the full rebuild is limited to use of the new assignment filter.
- Expensive boundaries: none found
- Verdict: No reportable regression: the work scales with the existing settings result model and is necessary for the requested filter; no per-frame repetition, expensive boundary, or uncoalesced fan-out is introduced.
