<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, serialization-allocation

### Scenario 1: Serializing file and resource URIs with URI.toString(true) for identifiers, labels, logs, and collection processing

- Critical path: Minimal serialization must finish synchronously before the caller can use the URI string. For skipEncoding calls, every non-empty authority/user-info, path, and query component is encoded; fragments bypass this helper.
- Scaling input: Cost scales with the total characters across URI components and the number of uncached toString(true) calls. The existing URI perf corpus uses about 105,025 fresh file URIs, while ordinary calls usually serialize one URI at a time.
- Effective concurrency: Synchronous and serialized within each JavaScript call; collection callers generally loop or map without an internal limiter, but this diff adds no asynchronous work or concurrency burst.
- Cache behavior: URI.toString(true) is intentionally not cached, so cold and repeated calls both execute minimal encoding. URI.toString(false) retains its existing per-instance formatted-string cache and uses a different encoder, so warm normal serialization is unaffected.
- Mechanism confidence: High: the changed helper and uncached toString(true) call path are explicit, and the before/after character scanning and allocation behavior is directly visible in the diff.
- Magnitude uncertainty: Exact end-to-end impact varies by URI length, delimiter placement, and caller frequency. Very short delimiter-heavy components may not benefit, but no realistic user-visible regression is established.
- Expensive boundaries:
  - serialization at <code>src/vs/base/common/uri.ts:605 encodeURIComponentMinimal / src/vs/base/common/uri.ts:475 Uri.toString</code>: Convert URI components into a minimally encoded string.; cardinality: Up to several component encodings per toString(true) call; one path encoding for common file URIs, multiplied by the number of serialized resources.
    - Introduced by diff: false; previous behavior: The same serialization occurred, scanning every character in JavaScript and appending unchanged suffix characters individually after the first '?' or '\#'.; critical-path effect: Synchronous CPU work directly gates availability of the URI string.
- Verdict: No reportable regression. Delimiter-free components now return after native searches, and components requiring escaping copy safe runs rather than appending unchanged characters one by one; this removes repeated JavaScript work without adding retained state or scaling fan-out.

### Scenario 2: Loading extension, worker, webview, and other browser resources whose URLs are produced with toString(true)

- Critical path: URI serialization completes synchronously before dynamic import, fetch, loadURL, or DOM resource assignment can start; the subsequent network/module load dominates and is unchanged by this patch.
- Scaling input: One serialization and one downstream load per requested resource in the inspected call sites; batching/grouping behavior belongs to those unchanged consumers, and the diff does not increase request cardinality.
- Effective concurrency: Downstream loads may run concurrently according to existing caller/browser scheduling. URI encoding itself is synchronous per request, and the diff neither creates nor expands concurrency.
- Cache behavior: Minimal URI strings are recomputed on repeated calls because skipEncoding output is not cached. Browser/network caches remain owned by unchanged consumers and are not affected; cold and warm boundary-call counts are identical before and after.
- Mechanism confidence: High: representative toString(true)-to-loader call sites and the formatter selection are explicit; all network and module boundaries are unchanged.
- Magnitude uncertainty: The fraction of startup or UI loading latency attributable to URI formatting is workload-dependent, but the changed mechanism does not add work or boundary calls for realistic URLs.
- Expensive boundaries:
  - serialization at <code>src/vs/base/common/uri.ts:605 encodeURIComponentMinimal</code>: Minimally encode the resource URI before handing it to a loader.; cardinality: One URI serialization per resource URL construction, with one encoding call for each populated authority/path/query component.
    - Introduced by diff: false; previous behavior: The resource URL was serialized on the same critical path using a full JavaScript character scan.; critical-path effect: Must finish before the load is initiated, but the patch reduces common-case serialization work.
  - network at <code>src/vs/platform/extensionResourceLoader/browser/extensionResourceLoaderService.ts:48 fetch and analogous unchanged resource loaders</code>: Fetch or load the serialized resource URL.; cardinality: One downstream load per requested resource; unchanged by URI encoding and subject to existing browser/network caching.
    - Introduced by diff: false; previous behavior: The identical fetch/load boundary occurred after the old minimal formatter, with the same URL and call count.; critical-path effect: The load gates resource availability; URI formatting precedes it but does not add a new boundary.
- Verdict: No reportable regression. The diff changes only CPU/string-allocation strategy before existing resource loads and neither introduces network I/O nor amplifies its cardinality.

### Scenario 3: Serializing custom URIs whose authority, path, or query contains '?' and '\#' delimiters

- Critical path: The helper locates the first delimiter, scans from it to the end, escapes each delimiter, and copies intervening safe runs before returning synchronously.
- Scaling input: Cost scales linearly with component length plus the number of delimiter-separated runs. Typical URIs have few embedded delimiters; adversarial alternating delimiter/safe-character strings increase substring count but remain linear.
- Effective concurrency: Single synchronous formatter invocation; repeated callers independently execute it because skipEncoding output is not cached.
- Cache behavior: No positive or negative cache is introduced. Repeated minimal serialization performs the same linear work each time, as before; normal serialization caching is unaffected.
- Mechanism confidence: High for the linear algorithm and allocation behavior; low that the small shape-specific slowdown reaches a meaningful product scenario.
- Magnitude uncertainty: The PR notes some very short delimiter-heavy inputs can benchmark slower, but repository call patterns and URI syntax do not establish realistic multiplicity or a user-visible latency/throughput impact. Pathologically huge components are not a realistic basis for a finding.
- Expensive boundaries:
  - serialization at <code>src/vs/base/common/uri.ts:606-630 encodeURIComponentMinimal</code>: Search for '?' and '\#', escape delimiter code units, and assemble safe substrings.; cardinality: Two native searches per non-empty component, followed only when a delimiter exists by one suffix scan and allocations proportional to delimiter-separated runs.
    - Introduced by diff: true; previous behavior: One JavaScript scan covered the whole component and, after the first delimiter, appended every unchanged character separately. The new searches can add a small constant-pass cost for some delimiter-heavy shapes but avoid per-character suffix concatenation.; critical-path effect: Entirely synchronous CPU/allocation work; no filesystem, IPC, database, subprocess, or network operation is reached by the helper itself.
- Verdict: No reportable regression. Worst-case asymptotic complexity remains linear, output allocation remains bounded by input/output size, and the plausible counter-cases are microbenchmark-only without a realistic performance trigger.

The patch removes common repeated per-character work and adds no actionable performance regression; no finding or regression-fix learning record was warranted.
