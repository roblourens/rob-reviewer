# Performance review: sessions: add Agents window layout telemetry

[PR #334255](https://github.com/microsoft/vscode/pull/334255) at `c09239548ceacd7694e0bcc766bbba65a2784711`

## Findings (1)

### 1. [low] Defer layout telemetry until after the first render

**Finding ID:** `PERF-0D437A7C38F8`  
**Location:** <code>src/vs/sessions/browser/workbench.ts:618</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Synchronous telemetry service graph construction, telemetry payload processing, and cold-web network/module-load initiation  
**Scaling:** The cost is paid once for every Agents window opened; on a cold web window it initiates an endpoint health fetch and lazy loading of the telemetry SDK before the workbench has rendered, while warm module caches avoid the SDK fetch but not service construction and the health ping.  
**Outcome:** Increased Agents window startup latency and competing network/CPU work before the first render  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The Sessions workbench did not resolve or log through ITelemetryService on this pre-render path. The existing SessionsTelemetryContribution resolves it in WorkbenchPhase.AfterRestored, whose registry instantiation is scheduled during browser idle time.  
**Changed behavior:** The added line synchronously resolves the delayed ITelemetryService and logs an event immediately after Ready-phase contributions, before renderWorkbench, createWorkbenchLayout, layout, and restore.  
**Confidence:** 0.94 — The call order, delayed service registration, web health fetch, lazy SDK load, desktop IPC, and idle scheduling of the existing Sessions telemetry contribution are all directly visible in the repository. The exact millisecond impact varies with module cache and telemetry configuration, so severity is low, but the newly earlier work and critical-path placement are concrete.

**Causal diff evidence:** The new call at line 618 is placed before the render/layout calls in Workbench.startup and is the first direct ITelemetryService resolution added to this startup path; ITelemetryService is registered as InstantiationType.Delayed on both browser and desktop.

Opening an Agents window, especially a cold web window with telemetry enabled, now begins telemetry initialization, a health-check request, and telemetry SDK loading before the UI is rendered. This adds synchronous startup work and lets telemetry traffic/module parsing contend with first-render work for a constant one-event benefit.

**Evidence:** On web, constructing the delayed telemetry service calls initializeService, whose OneDataSystemWebAppender constructor immediately starts a GET to the telemetry health endpoint; the first publicLog2 also enters AbstractOneDataSystemAppender.log, which starts loading the 1DS client modules. On desktop, the log synchronously queues a shared-process channel call. These completions are asynchronous, but resolving the service graph, constructing appenders/common properties, cleaning/mixing the payload, and initiating those boundaries all happen before Workbench.renderWorkbench. The existing SessionsTelemetryContribution is registered AfterRestored and therefore provides an idle-time owner for this event without moving telemetry initialization onto startup.

**Suggested direction:** Record the fixed layout from an AfterRestored/idle contribution (for example, the existing SessionsTelemetryContribution using IAgentWorkbenchLayoutService), or otherwise schedule this log after first render, so the event is preserved without forcing the delayed telemetry stack onto the startup critical path.
