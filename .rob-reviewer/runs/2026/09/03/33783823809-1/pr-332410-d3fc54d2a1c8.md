## Findings (1)

### 1. [high] Keep cached titles off the per-chat database path

**Finding ID:** `PERF-60F8B7D90E18`  
**Location:** <code>src/vs/platform/agentHost/node/chatContributions/sessionTitle/sessionTitleContribution.ts:77</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem stat operations, SQLite database opens/migrations, metadata queries, and database objects  
**Scaling:** Cost grows linearly with restored peer-chat count, and \`\_restorePeerChatsFromCatalog\` starts all hydrations concurrently rather than applying a limiter.  
**Outcome:** increased restore latency and excessive concurrent filesystem/SQLite I/O  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The existing \`if (restored.title \!== undefined) return restored\` ran before any database access, so verified central cached titles required zero chat-local database probes during peer catalog restore.  
**Changed behavior:** Every title hydration now stats and potentially opens/queries the chat-local SQLite database before accepting an already-restored title.  
**Confidence:** 0.99 — The changed ordering is explicit, \`tryOpenDatabase\` is proven to issue a filesystem stat and acquire a SQLite database, and \`\_restorePeerChatsFromCatalog\` invokes hydration for all peers via an unbounded \`Promise.all\` while passing cached catalog titles. The only magnitude uncertainty is the typical number of peer chats and disk speed.

**Causal diff evidence:** RIGHT line 77 inserts \`await this.\_sessionDataService.tryOpenDatabase(URI.parse(context.chat))\` and a metadata query before the existing \`restored.title \!== undefined\` early return, so callers that already supplied a catalog title now perform per-chat disk/SQLite work they previously skipped.

Opening a session with many restored peer chats now launches one filesystem probe and SQLite metadata read per chat concurrently, delaying restore and creating an I/O/open-handle burst; up to the catalog limit of 999 peers can be affected.

**Evidence:** \`SessionDataService.tryOpenDatabase\` performs \`\_fileService.stat\` and then acquires a \`SessionDatabase\`, whose first use opens/migrates SQLite; line 79 calls \`getMetadata\`. \`AgentService.\_restorePeerChatsFromCatalog\` maps every persisted peer through \`hydrateChat\` in \`Promise.all\` and passes \`{ title: cachedTitle }\` when the verified central payload already contains one. Session restore awaits \`\_restorePeerChats\`, so all probes are on the restore critical path.

**Suggested direction:** Restore the cached-title fast path before chat-local database access, and import chat-local title changes through the catalog reconciliation path. If local verification must remain on restore, batch/limit it and only probe chats whose central title is missing or known stale.
