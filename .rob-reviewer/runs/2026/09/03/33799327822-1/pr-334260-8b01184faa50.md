### Scenario 1: send\_message targets an idle chat with no pending messages

- Critical path: The tool must complete listSessions/getSendMessageArgs, then startPrompt dispatches ChatTurnStarted and begins provider delivery. The added getChatState/busy predicate is synchronous constant-time work and does not add a boundary.
- Scaling input: Visible registered-session count controls session-list metadata/database work; connected relevant clients control broadcast fan-out. The diff does not change either cardinality for idle targets.
- Effective concurrency: Session metadata and database overlays use limiters of 4. The single target turn follows the existing provider scheduling.
- Cache behavior: Concurrent listSessions calls for the same mode coalesce through \_inFlightListSessions; provider bulk metadata may be prewarmed for the computation. The changed busy check uses already-materialized chat state and has no cache miss path.
- Mechanism confidence: High: the changed branch falls through to the prior startPrompt behavior when no busy/pending state exists.
- Magnitude uncertainty: Provider and catalogue sizes vary, but all scaling boundary work is pre-existing and unchanged on this path.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:listSessions/\_computeSessions</code>: Enumerate registered sessions, fetch provider metadata, and open/read each visible session database metadata object.; cardinality: One listSessions computation per send\_message invocation; concurrent invocations for the same mode share an in-flight computation, while metadata/database work scales with registered visible sessions under limiters of 4.

  - filesystem at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:\_sendTurnMessage</code>: Resolve the target working directory/worktree and capture a turn-start checkpoint.; cardinality: Once for the newly started target turn, with checkpoint skipped for ephemeral sessions.

  - network at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:\_sendTurnMessage</code>: Send the message through the selected agent provider.; cardinality: One provider send for the target turn.
    - Introduced by diff: false; previous behavior: One provider send was started immediately.; critical-path effect: Asynchronous relative to the server-tool result, but it is the target turn's delivery critical path.
  - IPC at <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:\_broadcastAction</code>: Broadcast the ChatTurnStarted state action to each connected relevant client.; cardinality: One envelope per send, fanned out to relevant active clients.

### Scenario 2: send\_message targets a chat with an active turn; multiple messages are sent while it remains busy

- Critical path: Each tool call still waits for listSessions, then returns after an in-memory queue action and result formatting. Provider delivery is intentionally moved off the tool-call critical path and admitted one message at a time after successful turn completion.
- Scaling input: Queue length grows with accepted send\_message invocations while busy, but the shared group enforces a process-wide cap of 50. Reducer insertion scans/copies the current queue, making cumulative CPU/allocation O(k^2) only over k&lt;=50, with message storage O(total queued text).
- Effective concurrency: QueueDrainContribution admits at most one active turn per chat and only drains the next after success/local-command completion. This reduces provider/filesystem concurrency compared with the pre-diff immediate start for every call.
- Cache behavior: The queue uses authoritative in-memory chat state; no cache lookup or duplicate reconstruction is added. listSessions retains its existing in-flight coalescing and provider prewarm behavior.
- Mechanism confidence: High: reducer, process cap, turn-end drain, provider send path, and broadcasts are directly traced.
- Magnitude uncertainty: Message text lengths and connected-client count vary, but the count is capped at 50 and the extra queue envelope/array copies are small relative to provider-turn work.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:listSessions/\_computeSessions</code>: Resolve the session catalogue and metadata before target lookup.; cardinality: One logical listing per send invocation, with concurrent same-mode calls coalesced; work scales with visible registered sessions.
    - Introduced by diff: false; previous behavior: The same listing was required before immediately starting the target prompt.; critical-path effect: Remains on the server-tool critical path before queue insertion.
  - IPC at <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:\_broadcastAction</code>: Broadcast ChatPendingMessageSet to relevant connected clients.; cardinality: One queue envelope per accepted message, up to the process-wide maximum of 50 successful send\_message calls; fan-out scales with relevant connected clients.
    - Introduced by diff: true; previous behavior: The invocation instead emitted ChatTurnStarted immediately; the queued design later emits ChatTurnStarted when that message is admitted, so it adds one small state envelope per queued message but avoids immediate expensive turn launch.; critical-path effect: Occurs synchronously with queue insertion but carries only the action/message, not the full chat state.
  - filesystem at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:\_sendTurnMessage</code>: Resolve working directory/worktree and capture a checkpoint when each queued turn is eventually admitted.; cardinality: One per queued message eventually run, serially per chat; up to 50 process-wide send\_message calls.
    - Introduced by diff: false; previous behavior: The same work started immediately for every call, potentially overlapping while the target was already active.; critical-path effect: Off the send\_message tool-result critical path; on each later queued turn's delivery path.
  - network at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:\_sendTurnMessage</code>: Send each eventually admitted message to the provider.; cardinality: One per queued message that runs, serially after successful predecessor completion.
    - Introduced by diff: false; previous behavior: One provider send was launched immediately per call, permitting overlapping expensive work.; critical-path effect: Off the originating tool-call critical path and on the later target-turn path.
- Verdict: No reportable regression. The diff adds bounded in-memory queue bookkeeping and one extra action broadcast per queued item while removing an immediate concurrency burst of filesystem/checkpoint/provider work.

### Scenario 3: send\_message targets an idle chat that already has a queued or steering message

- Critical path: After listSessions and target resolution, the new condition appends a queued message and returns without starting a provider turn. The server-dispatched queue action is observable by general dispatch contributions and clients, while automatic queue policy currently reacts through the separate client-action hook; that behavior concern is correctness rather than an independently concrete performance regression.
- Scaling input: Existing pending state activates the changed branch; retained messages scale with accepted sends but are bounded to 50 across the process. Message size is schema-unbounded, although realistic model tool-call output is constrained by model/context limits.
- Effective concurrency: No provider turn is launched by this branch at insertion time; therefore it cannot create a provider concurrency burst.
- Cache behavior: No new cache. Chat state is read directly; session listing has existing in-flight coalescing only.
- Mechanism confidence: High for queue retention and absence of immediate provider work; lower relevance to user-visible performance because retention is bounded and the dominant issue is delivery behavior.
- Magnitude uncertainty: How long pending messages remain and their text sizes vary. The hard count cap and lack of evidence for large realistic retained payloads keep this from meeting the performance reporting threshold.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:listSessions/\_computeSessions</code>: Enumerate and enrich session metadata.; cardinality: One logical listing per invocation, coalesced when concurrent and scaling with visible sessions.
    - Introduced by diff: false; previous behavior: The same listing preceded immediate startPrompt.; critical-path effect: Must complete before queue insertion.
  - IPC at <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:\_broadcastAction</code>: Broadcast the pending-message action to relevant clients.; cardinality: One per added message, capped by 50 successful process-wide sends and fanned out by connected relevant clients.
    - Introduced by diff: true; previous behavior: The old path emitted ChatTurnStarted and initiated turn delivery instead.; critical-path effect: Synchronous notification during the queue operation.
- Verdict: No performance finding. Potential non-drain behavior is correctness-only, and bounded retained state does not establish meaningful memory growth.

- Critical path: The longer static tool description is serialized with tool definitions into provider prompts/requests; it adds a small fixed payload to requests where this tool is advertised.
- Scaling input: Cost grows linearly with the number of model requests, with a fixed small byte/token increment per request and no collection amplification.
- Effective concurrency: Unchanged provider request concurrency.
- Cache behavior: Materialized tool membership is reused per session, while current metadata wording is refreshed; no cache invalidation or miss amplification is introduced.

    - Introduced by diff: false; previous behavior: The same requests transmitted the shorter description.; critical-path effect: On model request submission, but the byte/token delta is constant and small.
- Verdict: No reportable regression; this is necessary fixed-size contract metadata rather than meaningful serialization or network amplification.
