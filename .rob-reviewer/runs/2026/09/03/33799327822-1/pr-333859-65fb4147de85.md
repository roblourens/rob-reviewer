# Performance review: Surface extensions blocked by the marketplace

## Findings (1)

### 1. [medium] Skip the redundant latest-only fallback for blocked versions

**Finding ID:** `PERF-4184AE7C59DE`  
**Location:** <code>src/vs/platform/extensionManagement/common/extensionGalleryService.ts:1394</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Marketplace HTTP requests and response bytes  
**Scaling:** For B installed extensions whose latest version is blocked, the resource GETs remain B-way concurrent as before, but all B failures are grouped into one latest-only query POST followed serially by one IncludeVersions POST; the extra POST pair repeats on each uncached update check.  
**Outcome:** Two additional network round trips delay update resolution and consume extra network I/O; one of those round trips is redundant because the resource response already established that the latest version is unusable.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A compatible latest-version resource response was accepted directly, so the update check completed after the existing per-extension resource GETs without entering the query API fallback.  
**Changed behavior:** The added blocked bit makes getValidRawGalleryExtensionVersion reject a version-blocked latest resource result. getLatestGalleryExtension then returns NOT\_COMPATIBLE, getExtensionsUsingResourceApi retries the affected IDs through a latest-only query, and queryGalleryExtensions rejects the same versions again before issuing its all-versions query.  
**Confidence:** 0.97 — The call path, request flags, awaited ordering, and HTTP boundaries are explicit in the code. The POSTs are grouped rather than per extension, and no repository cache is present; only the real-world frequency and network RTT are uncertain.

**Causal diff evidence:** The RIGHT-side addition \`blocked: isBlocked(rawGalleryExtensionVersion.flags, rawGalleryExtensionVersion.blocking)\` at line 1394 newly rejects the already-fetched latest resource result and then rejects the repeated latest-only query result, activating both fallback POSTs; pre-diff the same version passed this validation.

Periodic and manual extension update checks that encounter a version-blocked latest release wait for two serial Marketplace POSTs after the existing resource fetches. On high-latency links this can add multiple round-trip times before VS Code can determine the usable older version and schedule updates.

**Evidence:** checkForUpdates calls getExtensions with compatible=true for installed extensions. The resource path runs getLatestGalleryExtension for each ID; line 1394 feeds isBlocked into isValidVersion, causing a blocked latest version to produce NOT\_COMPATIBLE. getExtensionsUsingResourceApi batches those IDs into getExtensionsUsingQueryApi with the original options, whose default is IncludeLatestVersionOnly. That query reaches the same added check, populates needAllVersions, and only then performs a second query with IncludeVersions. queryRawGalleryExtensions shows each query is an awaited HTTP POST with no cache or coalescing layer.

**Suggested direction:** Propagate a distinct latest-version-is-blocked fallback result and batch those IDs directly into an IncludeVersions query, skipping the intervening latest-only query while preserving selection of an older permitted version.
