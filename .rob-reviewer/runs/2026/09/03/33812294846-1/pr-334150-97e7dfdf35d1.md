## Performance regression fixes detected (1)

### 1. synchronous-ui-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/widget/media/chat.css:60` (`LEFT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/widget/media/chat.css:60`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/widget/media/chat.css`  
**Introducing commit:** `5a60c4adaee7c072e1c20c29d25e8ea7dddca7bc`  
**Mechanism family:** `synchronous-ui-work`  
**Performance category:** `rendering`  
**Confidence:** 0.96

**Mechanism:** An infinite CSS animation changed a large blurred box-shadow on a pseudo-element covering the entire chat widget while each request was in progress, forcing continuous rendering/paint work until completion.

**Symptom:** Sustained CPU/GPU paint load and potential dropped frames while a chat request runs, especially for large chat editor surfaces or multiple simultaneously visible sessions.

**Fixed behavior:** In-progress sessions no longer create or animate the full-widget pseudo-element; only static idle-unvisited and needs-input frames remain, eliminating the continuous large-area box-shadow repaint during long-running requests.

**Evidence:** The base CSS applies `animation: chat-session-working-glow 1.4s ease-in-out infinite` to the full-widget `.interactive-session.chat-state-in-progress::before` overlay. The keyframes animate `box-shadow` from spacing-size20 to spacing-size60, so every active chat request continuously repaints a large blurred region for the request lifetime. This PR deletes both the in-progress pseudo-element selector and the infinite box-shadow animation, while `ChatWidget.updateSessionStateIndicator` still transitions request state normally.

- Effective concurrency: One accumulated event callback per widget batch; multiple visible chat widgets update independently. No queue or external concurrency is introduced.

- Mechanism confidence: High: the call path, O(1) model reads, DOM class mutations, and deleted infinite box-shadow animation are explicit in the changed hunks.

### Scenario 3: Collect main-editor Chat Editor topology telemetry after restoration and on editor/group changes

- Critical path: Initialization awaits main editor restoration asynchronously without blocking workbench progress. Each event burst schedules one snapshot after 100 ms; snapshot construction synchronously copies/scans all main-part groups and open editors, compares five counts, and calls telemetry only for a distinct topology entering, changing within, or leaving a Chat Editor state.
- Scaling input: Total open editors across main-part groups after coalescing, not raw editor event count; telemetry cardinality is distinct count snapshots while Chat Editors are present or on exit.
- Effective concurrency: A single RunOnceScheduler serializes and coalesces events; there is at most one pending scan and no concurrent telemetry burst from this contribution.
- Cache behavior: previousSnapshot is a one-entry warm cache that suppresses identical snapshots. Cold startup performs one full scan; without a Chat Editor it sends nothing. Warm event bursts still scan all open main-part editors, but coalescing limits scans to 10/s and telemetry remains suppressed unless counts change.
- Mechanism confidence: High for the O(open editors + groups) scan, one-snapshot retention, coalescing, and telemetry reachability; lower only for telemetry transport details because appenders are abstracted.
- Magnitude uncertainty: Open-tab counts and editor-event burst rates vary; scans allocate arrays proportional to open editors, but realistic cardinality plus 100 ms coalescing does not establish user-visible latency or GC pressure.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/telemetry/chatEditorTopologyTelemetry.ts:logCurrentSnapshot</code>: Submit the count-only \`chat.editorTopology\` usage event via ITelemetryService/publicLog2 (subject to telemetry buffering, level, and appender behavior).; cardinality: One initial eligible event after restoration and at most one event per distinct count snapshot after 100 ms coalescing; identical snapshots and all steady no-Chat snapshots are suppressed.
    - Introduced by diff: true; previous behavior: No Chat Editor topology snapshot or telemetry boundary existed before this contribution.; critical-path effect: The publicLog2 call is made after the scheduled snapshot and does not await network completion; it is off editor restoration and navigation progress except for the small synchronous handoff.
- Verdict: No reportable regression. The contribution introduces bounded linear snapshot work and a telemetry boundary, but coalescing, constant-size retention, identical-snapshot suppression, and realistic editor cardinality do not support a concrete user-visible performance impact.

### Scenario 4: Recompute chat visited state on widget focus, mouse interaction, and owning-window blur

- Critical path: Focus or mouse-down clears an existing unvisited flag and performs one state/class update; window blur performs one update per live widget. These handlers are synchronous but contain only constant-time model/focus reads and class toggles.
- Scaling input: Number of live chat widgets on a window blur, or direct interactions with one widget.
- Effective concurrency: Browser events dispatch serially; each widget owns and disposes its three listeners with the widget Disposable store.
- Cache behavior: The \`\_hasUnvisitedCompletion\` flag acts as a guard: focus/mouse handlers return immediately once visited. There is no external cache or I/O.
- Mechanism confidence: High: listener registration, guard, synchronous update path, and disposal ownership are explicit.
- Magnitude uncertainty: The number of live widgets in a window varies, but blur is infrequent and widget count is normally small; no unbounded listener retention is introduced because ownership is registered.
- Expensive boundaries: none found
- Verdict: No performance regression; work is bounded and listeners are disposed with widget lifecycle.
