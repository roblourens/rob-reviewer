### Scenario 1: Desktop new-session composer: add/remove or wrap attachment pills, and resize the Sessions view

- Critical path: Attachment-row size changes are delivered by one ResizeObserver callback that measures the single row and updates the composer's top offset before paint. Outer view resizing synchronously calls NewChatView.doLayout -&gt; NewChatWidget.layout -&gt; NewChatInputWidget.layout; the new offset read occurs before the already-existing editor and two responsive-picker layout passes.
- Scaling input: One observed attachment row per mounted composer. Attachment count can increase row height through wrapping, but measurement cardinality remains one per observer delivery or outer layout pass rather than one per attachment.
- Effective concurrency: ResizeObserver delivery is serialized by the browser; workbench grid layout and editor/picker layout execute synchronously on the UI thread. No concurrent fan-out is introduced.
- Cache behavior: No cache is involved. The row height is re-read on observer delivery and outer layout; warm and cold behavior are equivalent. The observer coalesces DOM size changes according to browser resize-observation delivery.
- Mechanism confidence: High confidence in the call path, one-row cardinality, disposal, and synchronous DOM measurement; low confidence that the added read creates an additional material layout cycle rather than joining the existing layout flush.
- Magnitude uncertainty: Exact resize frequency and browser layout cost vary with platform and composer complexity. The added geometry read is real, but surrounding pre-existing editor and responsive-picker layout already performs synchronous geometry reads on the same pass, so an independently material regression is not established.
- Expensive boundaries: none found
- Verdict: No reportable regression. The observer and observed target are disposed with the widget, work is bounded to one row, and the diff does not prove materially worse UI-thread scaling.

- Expensive boundaries: none found
- Verdict: No performance finding; the phone guard prevents desktop offset behavior and adds only constant work.

### Scenario 3: Render and update new-session status toolbar actions

- Critical path: Each rendered MenuItemAction uses NewChatInputStatusActionViewItem. Rendering or an action class update scans the label's small class list, toggles one container class, and for codicons traverses that action item's shallow DOM to substitute a registered compact icon class.
- Scaling input: Scales with the number of visible status menu actions and their class-update events. Each traversal is confined to one action-item subtree; realistic toolbars contain a small number of actions.
- Effective concurrency: Menu rendering and action updates are synchronous and serialized on the UI thread; no async burst or queue is added.
- Cache behavior: The selected compact codicon class is retained only on its owning view item so it can be removed before a class refresh. It is lifecycle-bounded by toolbar/view-item disposal; no global or unbounded cache is introduced.
- Mechanism confidence: High confidence in per-action cardinality and bounded ownership; no evidence of hot-frame invocation or substantial DOM traversal.
- Magnitude uncertainty: Extensions can contribute additional status actions, but each action adds a tiny bounded subtree/class scan and updates occur only when the action presentation changes.
- Expensive boundaries: none found
- Verdict: No reportable regression. The broader provider performs bounded presentation work and does not introduce retained growth or meaningful render-path scaling.

- Mechanism confidence: High confidence from the changed call sites and responsive-layout implementation that the algorithmic behavior is unchanged.

- Expensive boundaries: none found
