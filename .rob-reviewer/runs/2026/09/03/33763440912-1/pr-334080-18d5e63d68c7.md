# Performance review: editor: hide mouse cursor while typing

[PR #334080](https://github.com/microsoft/vscode/pull/334080) at `18d5e63d68c7f31cb03d5c2b649e1cf5e2af0db5`

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, cleanup-lifecycle, serialization-allocation

### Scenario 1: Keyboard text input with the option disabled or already hidden

- Critical path: After the existing synchronous view-model edit, \`\_type\` calls \`\_hideMouseCursor\` before \`onDidType\`; with the default-disabled option it performs one configuration lookup, and once hidden it exits on the boolean guard without DOM or listener work.
- Scaling input: Number of keyboard input batches; the only repeated default-path addition is one option lookup per batch, and enabled continuous typing does no work after the first batch.
- Effective concurrency: Keyboard input is serialized on the renderer event loop; there is no spawned or overlapping work.
- Cache behavior: The hidden-state boolean acts as transition coalescing: disabled input always takes the option-check path, while enabled input after the first character takes the warm early-return path until reveal.
- Mechanism confidence: High: the changed \`\_type\` call and \`\_hideMouseCursor\` guards directly establish the execution frequency and bounded work.
- Magnitude uncertainty: Exact per-keystroke configuration lookup cost is unmeasured, but it is constant-time and adds no allocation or boundary call on the default path.
- Expensive boundaries: none found
- Verdict: No reportable regression: the default path adds only a constant lookup, and hidden-state coalescing prevents listener or DOM work from scaling with continuous typing.

### Scenario 2: First keyboard input after enabling the option or after a mouse-driven reveal

- Critical path: The first qualifying input synchronously checks read-only/focus state, adds one CSS class, creates one disposable store, and registers six DOM listeners before the typing event returns; browser style recalculation can cover the rendered editor subtree because of the descendant cursor selector.
- Scaling input: Mouse-to-keyboard modality transitions and the number of currently rendered editor DOM descendants, not document line count or every typed character.
- Effective concurrency: One focused editor can enter the hidden state at a time in normal use; \`\_mouseCursorHidden\` prevents duplicate registration while it remains hidden, and all work is event-loop serialized.
- Cache behavior: Cold state is each visible-to-hidden transition; warm state is all subsequent typing while hidden. Pointer input clears the state, so effective cardinality is modality transitions rather than characters.
- Mechanism confidence: High for the class mutation and six listener registrations; medium for material style-cost magnitude because the editor virtualizes visible content and the transition is coalesced.
- Magnitude uncertainty: Rendered editor descendant count and browser selector-invalidation duration vary with viewport, decorations, and widgets; no evidence establishes a user-visible stall from the opt-in, transition-only invalidation.
- Expensive boundaries: none found
- Verdict: No finding: the work is opt-in, coalesced to one operation per modality transition, bounded to the focused editor, and lacks evidence of material latency or dropped frames.

### Scenario 3: Pointer, blur, configuration, model-detach, or disposal reveal and cleanup

- Critical path: A reveal event synchronously flips one flag, disposes the six-listener store, and removes one CSS class; configuration/model/disposal hooks call the same guarded cleanup.
- Scaling input: Number of hide/reveal intervals; retained listener/object count remains constant per hidden editor and does not grow with typing duration.
- Effective concurrency: Reveal sources are serialized; the first source clears state and later sources take the early return. \`MutableDisposable\` ownership bounds retained listeners to one store.
- Cache behavior: No cache is used. Cleanup is idempotently coalesced by \`\_mouseCursorHidden\`, and listeners exist only during the hidden interval.
- Mechanism confidence: High: ownership, clear-on-reveal, model detach, blur, and disposal are explicit in changed code and covered by the added lifecycle tests.
- Magnitude uncertainty: Browser style invalidation on class removal varies with rendered subtree size, but occurs only once per hidden interval.
- Expensive boundaries: none found
- Verdict: No cleanup-lifecycle or retention regression: listeners and the disposable store are deterministically released and cannot accumulate across repeated transitions.

### Scenario 4: Code editor construction when the setting is unused

- Critical path: Every \`CodeEditorWidget\` now allocates one \`MutableDisposable\` and registers blur/disposal callbacks during construction; this remains local synchronous initialization and is off any external boundary.
- Scaling input: Live \`CodeEditorWidget\` instance count, with constant added state per instance.
- Effective concurrency: Editors construct independently on the renderer event loop; no task burst, queue, or parallel operation is introduced.
- Cache behavior: Not applicable; state is per editor instance and released with editor disposal.
- Mechanism confidence: High for the per-instance allocation and registration, low that its magnitude could be material.
- Magnitude uncertainty: The number of simultaneously constructed embedded editors varies by workbench view, but the added state is a constant small number of objects/listeners per instance.
- Expensive boundaries: none found
- Verdict: No reportable startup or memory regression: the per-instance overhead is small, bounded, and lifecycle-owned.

Traced typing, IME, reveal, configuration, model, disposal, and editor-construction scenarios; checked listener ownership, state coalescing, CSS subtree invalidation, and external boundaries. The PR adds only bounded opt-in transition work and small constant default/per-instance overhead, with no high-confidence actionable performance regression and no regression-fix signal.
