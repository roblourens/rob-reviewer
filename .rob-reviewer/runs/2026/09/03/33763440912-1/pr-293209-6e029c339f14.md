# Performance review: mcp: initial data flow for MCP gateway

## Findings (1)

### 1. [medium] Unwrap the IPC arguments before disposing the gateway

**Finding ID:** `PERF-FAAB30121CDE`  
**Location:** <code>src/vs/platform/mcp/node/mcpGatewayChannel.ts:39</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** McpGatewayRoute objects and ownership entries retained in two Maps, plus the localhost HTTP server/socket and accumulated log/cleanup work  
**Scaling:** Retention grows linearly with each startMcpGateway()/dispose() cycle during the lifetime of one renderer or remote connection; disconnect cleanup later scans all historically retained entries.  
**Outcome:** Retained memory and an HTTP listener that never shuts down after normal disposal, with increasing disconnect-cleanup CPU/log I/O as gateway churn accumulates.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no gateway API, route registry, ownership map, or gateway HTTP listener to retain across extension operations.  
**Changed behavior:** ProxyChannel.toService packages disposeGateway(info.gatewayId) as the argument array \[gatewayId\], but the new custom channel casts that whole array to string and passes it as the Map key. The lookup always misses, so normal disposal removes nothing and cannot stop the server.  
**Confidence:** 0.99 — The proxy argument packaging, both reachable local/remote call paths, scalar-string Map keys, early return on lookup miss, and lifetime fallback are all directly established in repository code. Only the rate of repeated gateway creation varies by extension workload.

**Causal diff evidence:** Added line 39 passes \`args as string\` directly to \`disposeGateway\`; the newly added proxy call path supplies \`\[info.gatewayId\]\`, while the newly added service stores entries under the scalar UUID string.

An extension that creates a gateway for each agent/task and disposes it afterward leaks one route and ownership record per task until the window or remote connection disconnects; even after the final public gateway is disposed, the localhost server remains live.

**Evidence:** ProxyChannel.toService invokes channel.call(propKey, methodArgs), where methodArgs is an array. Both desktop-local and remote workbench implementations call the proxied disposeGateway(info.gatewayId), reaching this channel. This changed line passes args (the array) to McpGatewayService.disposeGateway, whose string-keyed \_gateways.get(gatewayId) misses and returns before deleting either Map or calling \_stopServer(). Disconnect cleanup is only a later connection-lifetime fallback.

**Suggested direction:** Type \`args\` as an argument tuple/array and pass its first element (for example, \`const \[gatewayId\] = args as \[string\]\`) to disposeGateway; retain the channel context injection only for createGateway.

- Scaling input: Distinct start/dispose cycles during one long-lived renderer or remote connection. The effective retained cardinality equals the number of successfully started gateways, not the number currently exposed to extensions.
- Effective concurrency: Disposals are not awaited and have no backpressure, but the leak is deterministic even for sequential calls; concurrency is not required.
- Cache behavior: The workbench DisposableMap evicts its ID, but the platform \_gateways and \_gatewayToClient Maps never evict on explicit disposal. Disconnect cleanup is the only eventual lifetime fallback and scans/removes all entries owned by that connection.
- Mechanism confidence: Very high: ProxyChannel's array encoding, the custom channel cast, string-keyed lookup, early return, and missed server shutdown are directly established.
- Magnitude uncertainty: Extensions may create one long-lived gateway or repeatedly create per task/agent session; that prevalence controls severity, not the proven linear retention mechanism.
- Expensive boundaries:

  - IPC at <code>src/vs/platform/mcp/node/mcpGatewayChannel.ts:call(disposeGateway)</code>: Sends the gateway ID to the local main process or remote server for route disposal.; cardinality: One downstream call per distinct gateway removed from MainThreadMcp; ProxyChannel encodes it as the one-element array \[gatewayId\].

### Scenario 4: A renderer or remote-agent connection disconnects after creating gateways

- Critical path: IPCServer.onDidRemoveConnection synchronously scans the ownership Map, gathers entries matching the connection context, removes them, and initiates server close if no global routes remain. This is cleanup triggered after the connection is already lost, not a user workflow critical path.
- Scaling input: Total gateway ownership entries G. Because explicit disposal is broken, G includes historical starts for all still-connected clients rather than only live gateways.
- Effective concurrency: One synchronous scan per connection-removal event; no batching across simultaneous disconnects, and each event independently scans the current Map.
- Cache behavior: Disconnect cleanup finally evicts matching entries. There is no separate index by client, so cleanup scans the full Map; normal disposal should have kept G bounded but does not.
- Mechanism confidence: High: event registration and full-Map iteration are explicit.
- Magnitude uncertainty: Disconnect frequency and historical gateway count vary, but the O(G) fallback cost is secondary to the reported retention root cause.
- Expensive boundaries:
  - network at <code>src/vs/platform/mcp/node/mcpGatewayService.ts:disposeGatewaysForClient/\_stopServer</code>: Closes the localhost HTTP listener after owned routes are removed and no routes remain.; cardinality: At most one close per disconnect cleanup; Map scan cardinality is all retained gateway ownership entries across connected clients.
    - Introduced by diff: true; previous behavior: No gateway ownership scan or listener close existed.; critical-path effect: Off normal interaction paths, though the synchronous O(G) scan runs on the main/remote server event loop.
- Verdict: Covered by the disposal finding rather than reported separately; fixing scalar-ID disposal bounds this cleanup to genuinely live gateways.
