**Relevant issue families:** hot-path CPU and string allocation, browser/native boundary call frequency, retained input-state memory, synchronous input critical-path work

### Scenario 1: Regular keyboard text insertion through Native EditContext

- Critical path: A browser \`textupdate\` synchronously applies the update to \`NativeEditContextInputState\`, dispatches \`viewController.type\`, mutates the model, and runs the model-content listener before input handling returns.
- Scaling input: The cached EditContext text is the complete line containing a collapsed selection, or all lines spanned by a selection. \`applyTextUpdate\` performs string work proportional to that window, while realistic source lines are usually short; exceptionally long/minified lines increase cost.
- Effective concurrency: Single-threaded and serialized in the browser event/model notification stack; no batching or parallel fan-out.
- Cache behavior: Each editor retains one current text/selection snapshot. It is refreshed on EditContext/model synchronization; there is no external cache, coalescing, or cold/warm I/O distinction.
- Mechanism confidence: High confidence in the synchronous call flow and string scaling from the changed handler and model listener; low confidence that added string work outweighs the removed native update for realistic inputs.
- Magnitude uncertainty: Very long single lines can make the added reconstruction noticeable, but normal typing previously forced a redundant full native \`updateText\`, so the inspected change does not establish a net regression on this scenario.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts:\_updateEditContext</code>: Read EditContext text/selection and conditionally call native \`EditContext.updateText\` / \`updateSelection\`.; cardinality: One synchronization attempt per relevant synchronous model-content event and cursor-state event; for a normal browser-originated insertion, the changed browser-state comparison generally yields zero \`updateText\` calls.
    - Introduced by diff: false; previous behavior: The same synchronization ran, but compared against stale JS caches and normally issued one redundant full-range \`updateText\` after the browser had already applied the textupdate. The diff removes that redundant call.; critical-path effect: Runs synchronously on the input path; an actual native update must complete before synchronization returns.
- Verdict: No reportable regression: the diff adds a JS state reconstruction but removes a redundant native full-text update on the same critical path.

### Scenario 2: macOS Pinyin composition candidate preview and commit

- Critical path: Composition events synchronously synchronize state; each \`textupdate\` applies the candidate update. A composition-only selection excursion with unchanged replacement text is detected and returned before model editing; the eventual changed candidate commit proceeds through \`compositionType\` and model synchronization.
- Scaling input: Candidate update frequency and EditContext window length (normally one source line). The unchanged-text test may compare a line-sized string, but effective cardinality is one operation per emitted IME update, with no fan-out.
- Effective concurrency: Strictly serialized composition events on the UI thread; no queue, limiter, or concurrent requests.
- Cache behavior: The per-editor input snapshot is warm from \`\_updateEditContext\` at composition start and updated before synchronous model listeners. No external cache or negative-cache behavior exists.
- Mechanism confidence: High confidence in the event ordering and suppression path, corroborated by the focused tests; insufficient evidence of adverse net performance versus the removed model work.
- Magnitude uncertainty: Equal-text candidate previews on unusually long lines perform line-sized JS comparison/reconstruction, but prevalence and cost are limited, and the same branch now avoids a model composition edit and native synchronization work.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts:composition handlers and \_updateEditContext</code>: Synchronize full EditContext text/selection with native \`EditContext.updateText\` / \`updateSelection\` at composition start/end and after model changes.; cardinality: At most one synchronization attempt at composition start, one per accepted candidate text change via the model listener, and one at composition end; ignored unchanged candidate previews do not trigger model synchronization.
    - Introduced by diff: false; previous behavior: The same native synchronization boundary existed. Unchanged candidate previews were forwarded as composition edits and could trigger model/content synchronization; the diff suppresses that downstream work and avoids redundant native text writes by consulting current browser state.; critical-path effect: Synchronous with IME event handling; ignored previews now stop before the editor model mutation and its downstream synchronization.
- Verdict: No reportable regression: candidate-preview suppression reduces synchronous downstream work, and the added state calculation does not prove a realistic net slowdown.

### Scenario 3: Cursor movement, selection changes, and external model edits near the active selection

- Critical path: Cursor-state changes or overlapping model-content changes synchronously compute the selected-line text, compare it with native EditContext state, update native text/selection only when different, and refresh the local snapshot.
- Scaling input: Length of the line or multi-line selection returned by \`model.getValueInRange\`, plus cursor/model event frequency. No collection fan-out or deduplicated groups are involved.
- Effective concurrency: Serialized on the UI thread with no asynchronous boundary, batching, or parallelism.
- Cache behavior: One retained snapshot per editor replaces the prior retained text and selection caches, so steady-state retained cardinality remains constant. No cold/warm external cache behavior applies.
- Mechanism confidence: High confidence that update cardinality and retained-state cardinality do not increase; uncertain low-level native getter cost is explicitly excluded from findings.
- Magnitude uncertainty: Native property-read implementation cost is not established by repository evidence; it cannot support a finding absent proof that reads copy large strings or materially increase latency.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/editor/browser/controller/editContext/native/nativeEditContext.ts:\_updateEditContext</code>: Read native EditContext properties and conditionally update native text or selection.; cardinality: One comparison per cursor-state event or overlapping model-content notification; zero or one text update and zero or one selection update per attempt.
    - Introduced by diff: false; previous behavior: The same native updates and full selected-range model read existed, using \`\_previousEditContextText\` and \`\_previousEditContextSelection\` for comparisons. The diff changes the comparison source to authoritative native properties without increasing update cardinality.; critical-path effect: Synchronous with cursor/model event delivery; unchanged text avoids \`updateText\`.
- Verdict: No reportable regression: retained memory remains one text snapshot per editor and conditional native update count does not increase.
