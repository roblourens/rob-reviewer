**Relevant issue families:** shutdown critical-path latency, subprocess and filesystem I/O, connection lifecycle memory, batching and concurrency

### Scenario 1: Standalone Agent Host graceful shutdown or restart with active protocol requests and provider sessions

- Critical path: Signal/stdin closure synchronously disposes protocol ingress and the WebSocket listener, then waits for tracked protocol requests, provider shutdown, and persistence flushing in that order. The entire asynchronous sequence is capped at 4500 ms; supervising process shutdown is separately capped at 6000 ms. This work is on the shutdown/restart critical path but not interactive steady-state paths.
- Scaling input: Currently in-flight protocol requests, registered providers, live provider chats, active client connections, live session databases, and pending writes at the moment shutdown begins; completed historical work is not retained by the new shutdown helper.
- Effective concurrency: Tracked protocol requests settle concurrently through Promise.all snapshots; registered providers shut down concurrently after authentication replay settles; Claude live sessions are drained concurrently across per-session sequencer keys while work for the same session remains serialized; session databases and the two persistence services flush concurrently. The phases themselves are intentionally serialized to prevent late writes.
- Cache behavior: No result cache is relevant. Shutdown promises are memoized at provider-service and Claude-provider levels, database close is memoized, and idle checks observe only outstanding work. Cold shutdown with no active work resolves quickly; warm/active shutdown drains outstanding work under the same deadline.
- Mechanism confidence: High: the changed call order, deadline, tracked-request set, provider shutdown fan-out, database close, and persistence idle loops are directly traced in repository code.
- Magnitude uncertainty: Exact provider/subprocess drain duration depends on active SDK work and filesystem speed, but the global 4500 ms child deadline and 6000 ms supervisor deadline bound user-visible restart delay.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/agentHostServerMain.ts:390 via AgentService.shutdown and provider shutdown</code>: Drain provider activity; Claude aborts live SDK conversations after previously queued per-session work, which can include SDK/process transcript completion.; cardinality: One coalesced provider shutdown per registered provider (normally Copilot and Claude, optionally Codex), with Claude work proportional to currently live chats and concurrent across distinct session IDs.
    - Introduced by diff: true; previous behavior: Standalone signal shutdown did not call or await provider shutdown and proceeded directly to persistence idle checks.; critical-path effect: Newly awaited on standalone shutdown so provider transcript/process cleanup can finish before process exit; bounded by the shared 4500 ms deadline.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:6776 reached from src/vs/platform/agentHost/node/agentHostServerMain.ts:390</code>: Close the orchestrator SQLite database after provider shutdown.; cardinality: At most one close operation; the database close implementation memoizes the close promise.
    - Introduced by diff: true; previous behavior: The standalone signal path relied on synchronous disposal/process exit and did not await this close.; critical-path effect: Now part of standalone shutdown before persistence flushing; included in the shared deadline.
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostServerMain.ts:391 via SessionDataService.whenIdle and AgentHostCustomizationEnablementService.whenIdle</code>: Wait for already queued session SQLite writes, customization session writes, and host-storage file writes to settle.; cardinality: Concurrent across currently live session databases and pending write promises; no new writes are created merely by the idle checks.
    - Introduced by diff: false; previous behavior: The same two persistence idle checks were awaited immediately after closing the WebSocket listener, with a 3000 ms persistence-only cap.; critical-path effect: Already on the shutdown critical path before the PR; now starts after provider shutdown so provider-generated writes are included, while the total sequence remains capped.
  - network at <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:361 and src/vs/platform/agentHost/node/agentHostServerMain.ts:383-384</code>: Close active WebSocket transports and stop the TCP/WebSocket listener before draining requests.; cardinality: One transport disposal per currently active connection plus one listener close; typical cardinality is the number of connected clients, not historical connections.
    - Introduced by diff: true; previous behavior: The listener was closed, but ProtocolServerHandler did not centrally dispose every active or pre-initialize transport before the idle wait.; critical-path effect: Synchronous ingress stop precedes asynchronous draining and prevents additional critical-path work from being admitted.
- Verdict: No reportable regression. The diff intentionally moves bounded provider and outstanding-request cleanup onto terminal shutdown to preserve transcripts. It does not affect steady-state throughput/startup, fan-out is coalesced and mostly concurrent, and the total wait remains below the supervisor's existing termination budget.

### Scenario 2: WebSocket connection churn and ProtocolServerHandler disposal

- Critical path: Each accepted connection creates a DisposableStore and inserts it into a DisposableMap. Normal close deletes and disposes that single entry; handler shutdown disposes all entries once before process exit. The added map operations are not on request message processing beyond one O(1) insertion per connection.
- Scaling input: Concurrent active WebSocket connections; entries are removed on close, so historical connection count does not accumulate.
- Effective concurrency: Connection callbacks run on the Node event loop. Each close performs one keyed deletion/disposal; final handler disposal iterates only currently active transports. DisposableStore's idempotent disposal makes the onClose re-entrancy bounded.
- Cache behavior: No cache. The DisposableMap is lifecycle ownership state keyed by transport and has immediate removal on close.
- Mechanism confidence: High: insertion, keyed removal, bulk disposal, and DisposableMap/DisposableStore semantics are directly visible.
- Magnitude uncertainty: Very high concurrent connection counts are not characterized, but each connection already owned listeners and a transport before this diff; the new incremental retained state is one map entry and store reference per active connection.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:425,566 and src/vs/platform/agentHost/node/webSocketTransport.ts:95</code>: Dispose/close the WebSocket transport when its connection store is disposed.; cardinality: One close per active transport; closed transports are removed immediately, so cost and retained objects scale with concurrent connections rather than lifetime connection churn.
    - Introduced by diff: true; previous behavior: Per-connection listeners and initialized-client cleanup used a local store, but the handler did not own stores for bulk shutdown and pre-initialize transports could remain open until server/process teardown.; critical-path effect: Normal close cleanup is event-driven and off interactive request critical paths; bulk disposal occurs only during terminal handler shutdown.
- Verdict: No reportable regression. The added O(1) ownership bookkeeping is bounded by active connections and enables prompt socket/listener cleanup; it does not create unbounded retention or repeated expensive work.

**Summary:** Completed the performance pass over all five changed files and traced standalone shutdown, provider/session draining, persistence/database boundaries, supervisor deadlines, and connection lifecycle ownership. No actionable diff-introduced performance regression met the reporting threshold.
