[PR #335980](https://github.com/microsoft/vscode/pull/335980) at `8802fa19ed1649af798c5475e0dfe9adf0b5e2aa`

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, serialization-allocation

### Scenario 1: Auto-approving a Bash or PowerShell shell tool call with literal or fully quoted redirect destinations

- Critical path: A provider pending-confirmation signal reaches AgentSideEffects.\_handleToolReady, which awaits SessionPermissionManager.getAutoApproval; CommandAutoApprover synchronously parses the command, walks tree-sitter captures, classifies each redirect, checks workspace containment, and then responds to the provider. The added regular-expression scans are on this critical path but are linear over each redirect destination and add no I/O.
- Scaling input: Command-line length and number of redirect captures. Effective cardinality is one classification per captured redirect per evaluation; ordinary commands contain one or a few redirects. Total added CPU scales O(total redirect destination characters).
- Effective concurrency: Classification and path checks run synchronously on the Node event loop, so concurrent pending-confirmation signals do not create a resource burst; their synchronous sections serialize. Provider session creation runs auto-approver initialization in parallel with provider creation, but session creation waits for both.
- Cache behavior: Tree-sitter resources are coalesced by the process-global treeSitterResourcesPromise, and compiled rule objects are cached by configuration identity. The new stateless destination checks have no cache, but each scan is linear and bounded by command input; cold initialization behavior and warm parsing behavior are unchanged.
- Mechanism confidence: High confidence from the changed hunk and traced capture loop that the only added resource cost is up to three linear scans of rawDest for each non-safe redirect; no allocation proportional beyond regex matching, retained state, or new expensive boundary is introduced.
- Magnitude uncertainty: Real command lengths and redirect counts vary, but shell command inputs are realistically small and the added regexes have disjoint alternatives without catastrophic backtracking. Exact nanosecond-level overhead is unmeasured and does not support a reportable regression.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/commandAutoApprover.ts:loadTreeSitterResources</code>: Read the Bash and PowerShell grammar WASM files during auto-approver initialization; cardinality: Two explicit filesystem reads once per process, coalesced by treeSitterResourcesPromise across sessions
    - Introduced by diff: false; previous behavior: The same two grammar reads and initialization wait existed before the diff.; critical-path effect: Session creation starts initialization in parallel with provider creation and waits for both before completing; these reads do not occur per redirect or per approval event.
  - IPC at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:\_handleToolReady</code>: Send the approval response to the agent/provider after the local policy decision; cardinality: At most one permission response for the tool-ready event on this path
    - Introduced by diff: false; previous behavior: The same permission response was sent after redirect classification before the diff.; critical-path effect: The provider cannot proceed until the approval response, but the diff adds only local linear string scans before the unchanged response.
- Verdict: No reportable performance regression. Before the diff, each redirect was parsed, safe-sink checked, quote-stripped, and workspace-checked; after it, unresolved globs are rejected after bounded linear scans. The added CPU is dominated by the existing tree-sitter parse/query and does not change boundary cardinality or concurrency.

### Scenario 2: Requiring confirmation and computing rule eligibility for an unresolved redirect glob

- Critical path: The first getAutoApproval evaluation parses and classifies the command, returning noMatch because the changed glob check yields an undefined destination. AgentSideEffects then calls isAutoApproveRuleResolvable, causing the existing second synchronous evaluation before dispatching the confirmation-ready action. The diff changes the classification result and adds linear scans, but did not introduce the second evaluation.
- Scaling input: Total command length and number of redirect captures, evaluated twice only on the existing unresolved-confirmation path. Effective added work is at most two executions of the quote/glob scans per redirect for this scenario, O(total redirect text).
- Effective concurrency: Both evaluations are synchronous and serialized on the Node event loop. There is no Promise.all fan-out, subprocess launch, filesystem access, or network request caused by the changed check.
- Cache behavior: Warm tree-sitter languages and cached rule configuration are reused. Parse trees and redirect classifications are intentionally per-event and not retained; the diff introduces no cache keys, misses, negative-cache behavior, or lifecycle changes.
- Mechanism confidence: High confidence that the noMatch path evaluates twice and that the added regex checks run per redirect in each evaluation; equally high confidence that the scans are linear and introduce no boundary fan-out or retention.
- Magnitude uncertainty: Commands with generated, unusually long redirect tokens could increase linear scan time, but the pre-existing parser already processes the full command twice on this path. There is no evidence that the new scans become independently user-visible at realistic sizes.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:\_handleToolReady via AgentHostStateManager.dispatchServerAction</code>: Emit the tool-ready confirmation action for presentation to the client; cardinality: One action envelope per pending tool call requiring confirmation
    - Introduced by diff: false; previous behavior: A non-auto-approved, non-resolvable shell command already performed the eligibility evaluation and emitted one confirmation action.; critical-path effect: The confirmation UI/action follows both local evaluations, as it did previously; the diff does not add or multiply envelopes.
- Verdict: No reportable performance regression. The PR preserves existing evaluation multiplicity and client/provider boundary counts; it adds only bounded linear CPU work needed to classify unresolved globs.

**Summary:** Reviewed all three changed files and the complete production call path through command parsing, session permission evaluation, provider response, client action dispatch, and one-time tree-sitter initialization. No actionable performance issue was introduced, and the PR is a correctness/security classification change rather than a performance-regression fix.
