## Findings (1)

### 1. [low] Avoid a new metadata syscall on every regular-file read

**Finding ID:** `PERF-57ED47C6BA77`  
**Location:** <code>src/vs/platform/files/node/diskFileSystemProvider.ts:360</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem metadata syscalls and libuv thread-pool work  
**Scaling:** The added descriptor \`fstat\` runs once for every \`readFile\` and read-only \`open\`; cold extension scanning invokes those paths concurrently for each installed extension manifest, so the extra boundary work grows linearly with extension count and other files loaded.  
**Outcome:** increased startup and file-open latency, with additional filesystem/thread-pool contention  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A regular \`readFile\` delegated directly to \`fs.promises.readFile(path)\`, and a read-only \`open\` performed only the open operation; FileService already started its own metadata resolution in parallel for each read.  
**Changed behavior:** Every regular read now awaits \`open\`, then an additional \`fstat\`, before any bytes can be read. This provider-level metadata call is serialized on the read critical path even when FileService is already resolving metadata for the same resource.  
**Confidence:** 0.94 — The added syscall, its serialized placement before reading, and the per-extension cold-start call path are explicit in repository code. Exact milliseconds vary with extension count, filesystem latency, and cache state, which is why severity is low rather than suppressing the concrete mechanism.

**Causal diff evidence:** Added RIGHT line 360 introduces \`await Promises.fstat(fd)\` inside the helper now used by both \`readFile\` and every read-only \`open\`; no such provider-level pre-read metadata syscall existed on those paths before this diff.

Cold extension scans issue one added metadata operation for every installed extension's \`package.json\` (the scanner maps all extension directories through \`Promise.all\`), while editor/file loads pay the same extra round trip. This is especially visible on high-latency or heavily monitored filesystems.

**Evidence:** \`FileService.doReadFileStream\` starts \`validateReadFile\`, which calls \`resolve(..., { resolveMetadata: true })\`, alongside the provider read. The changed \`openFileForRead\` then independently awaits \`Promises.fstat(fd)\` before returning. \`ExtensionsScanner.scanExtensionsFromLocation\` uses \`Promise.all\` over all extension directories and \`scanExtensionManifest\` reads one \`package.json\` per extension, placing the added filesystem boundary on startup's extension-scan path. The warm user-extension cache reduces this to one cache read, but system scans and cold/invalid caches still fan out across installed extensions.

**Suggested direction:** Keep the nonblocking special-file protection, but coalesce the descriptor type check with the read implementation instead of adding an independent metadata round trip to every normal read (for example, carry the opened descriptor's stat into a read routine that consumes it rather than restatting, and preserve equivalent validation for direct provider/open callers).


## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts:255` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts:263`  
**Introducing path:** `src/vs/workbench/contrib/bulkEdit/browser/bulkFileEdits.ts`  
**Introducing commit:** `37249cba4aaffc7ea0ec2a9e7c2ae2ccb595a485`  
**Mechanism family:** `eager-work`  
**Performance category:** `io`  
**Confidence:** 0.99

**Mechanism:** Bulk delete eagerly read every non-folder entry to capture undo contents. A FIFO is reported as an unknown, non-folder file type, so reading a FIFO without a writer can block indefinitely before the delete operation runs.

**Symptom:** Deleting a selection containing a named pipe can hang indefinitely before deletion because undo capture waits for pipe contents.

**Fixed behavior:** The added file-type guard skips undo-content reads for entries that are neither regular files nor directories, allowing the delete batch to proceed without opening the FIFO for a blocking read.

**Evidence:** Before the added guard, `DeleteOperation.perform` resolved each entry and then called `fileService.readFile` whenever the edit was not marked as a folder and did not exceed the size limit. The new test models `FileType.Unknown` and proves no read occurs, while the named-pipe tests create a FIFO without a writer and require all read APIs to reject rather than block. Added line 255 excludes that special-file path before undo capture.

- Effective concurrency: Bulk-delete metadata/undo preparation is sequential per edit, followed by a grouped delete call. Provider read attempts are independent; no new burst is introduced.
- Cache behavior: No content or negative cache participates; each operation resolves current filesystem state.
- Mechanism confidence: High: the control flow, FIFO fixture, and tests directly establish the blocking boundary and its removal.
