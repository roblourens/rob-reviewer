### Scenario 1: Opening the slash-command prompt picker or first resolving a prompt command in the VS Code repository workspace

- Critical path: On the first cold request, prompt discovery must resolve the configured .github/prompts location, enumerate files, read and parse each discovered prompt, and build slash-command metadata before commands are returned. Warm requests use CachedPromise and only rebuild after file/model/configuration invalidation.
- Scaling input: The number of discovered prompt and enabled skill files after URI deduplication. This diff lowers prompt cardinality by exactly two files; configured source-folder count is unchanged.
- Effective concurrency: Source locations are resolved by the existing locator flow; discovered prompt/skill reads are queued through the service-wide Limiter with concurrency 10, including overlapping invalidated discovery passes.
- Cache behavior: Cold discovery enumerates and parses files. The resulting discovery promise is cached; file, model, extension, plugin, or lockdown changes invalidate it. Removing these files neither changes cache keys nor miss/error coalescing and reduces cold parse work.
- Mechanism confidence: High: the deleted files match the default .github/prompts source and the service explicitly enumerates, reads, parses, limits, and caches discovered files.
- Magnitude uncertainty: Exact repository prompt/skill count and filesystem latency vary, but the direction is unambiguous: two fewer files and no added work.
- Expensive boundaries:

### Scenario 2: Invoking the removed doc-comments or micro-perf workspace prompt

- Critical path: Before the PR, command resolution awaited cached slash-command discovery and then read/parsed the selected prompt before handing its instructions to the agent. After the PR, these two commands are absent, so this invocation path no longer exists.
- Scaling input: A single explicitly selected prompt invocation; any subsequent agent tool/model activity is user- and model-driven rather than automatic per repository item.
- Effective concurrency: Prompt resolution handles the selected command only. Discovery reads remain globally limited to 10; no new parallel tool, subprocess, IPC, or network work is introduced by deletion.
- Cache behavior: Slash-command metadata discovery is cached, but resolvePromptSlashCommand parses the selected file when present. Deletion removes that selected-file read for these names; it introduces no cache state or retained object.
- Mechanism confidence: High that the filesystem read is removed; no evidence of any replacement work or newly retained state exists in the diff.
- Magnitude uncertainty: Downstream agent model/tool operations depended on explicit invocation and model choices, so their duration and cardinality cannot be established statically; no such boundary is newly introduced.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts:687</code>: Read and parse the selected prompt file during slash-command resolution.; cardinality: At most one selected prompt-file read per invocation after cached command lookup; zero for these deleted prompts after the PR.
    - Introduced by diff: false; previous behavior: Invoking either named prompt caused its file to be read and parsed; deletion removes that boundary call.; critical-path effect: Before the PR, the selected file read completed before prompt execution could proceed. The deleted commands now have no execution path.
- Verdict: No performance regression. This is removal of an optional workflow and its associated per-invocation work, not added or amplified performance cost.

**Summary:** Reviewed both deleted prompt files and traced workspace prompt discovery, caching, bounded reads, parsing, and command resolution. The diff only decreases discovered-file cardinality and removes optional invocation work; it adds no hot-path work, boundary fan-out, allocation, retention, or concurrency.
