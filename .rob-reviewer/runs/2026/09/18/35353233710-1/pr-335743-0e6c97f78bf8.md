<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work, cache-lifecycle, serialization-allocation

### Scenario 1: Editor-focused Add Next/Previous or Move Next/Previous Occurrence from a selection or caret (for example Cmd+D)

- Critical path: The keybinding synchronously determines whether Find owns the request, reuses or creates a MultiCursorSession, then performs one in-memory text-model findNextMatch/findPreviousMatch before updating and revealing selections. The diff adds only constant-time focus/state/option reads and can avoid the prior hidden Find-options UI highlighting; no subprocess, IPC, filesystem, database, or network work is reached.
- Scaling input: Search cost scales with text traversed to the next/previous match; selection-array copying scales with the number of existing cursors. Case-insensitive mode can increase matches reached, but the default Find state was already case-insensitive and each incremental command still performs one search.
- Effective concurrency: Fully serialized on the editor input path: one model search per command invocation; repeated commands reuse one session until selection, model, blur, or ownership changes end it.
- Cache behavior: The MultiCursorSession caches query text and matching flags for the sequence, not search results. Focus ownership changes intentionally invalidate the session. There is no negative-cache behavior or concurrent request to coalesce.
- Mechanism confidence: High confidence: the changed calls and model-search path are directly visible, and all work remains in-process and synchronous.
- Magnitude uncertainty: Exact model-search latency varies with document size and query, but the diff does not increase search cardinality or concurrency on the normal default path.
- Expensive boundaries: none found
- Verdict: No reportable regression. The new option substitutes a constant-time option read for Find-state settings and the ownership guard avoids irrelevant Find-options UI work for editor-driven selection.

### Scenario 2: Find-widget-focused occurrence navigation and select-all

- Critical path: The command synchronously checks text focus and revealed/non-empty Find state, then uses the existing Find query and performs one local model search (findNext/findPrevious or findMatches for select-all) before setting selections. No external boundary is reached.
- Scaling input: Navigation scales with text scanned to the next match. Select-all scales with document size and effective match count, with the existing MAX\_SAFE\_SMALL\_INTEGER result limit unchanged by the diff.
- Effective concurrency: Serialized in the UI command handler, with one model search per navigation command or one full search for select-all.
- Cache behavior: A session is reused while Find retains ownership; crossing focus ownership clears it. No remote/cache boundary exists, and no new retries are introduced.
- Mechanism confidence: High confidence from the complete selectAll and session call paths.
- Magnitude uncertainty: Very match-dense documents can already create many selections, but the diff neither removes the existing limit nor adds a second scan.
- Expensive boundaries: none found
- Verdict: No reportable regression. The new drivenByFind routing preserves one-search behavior and only recreates a session when ownership changes.

### Scenario 3: Selection occurrence highlighting after selection, model content, Find state, or selectionMatchCase configuration changes

- Critical path: Selection changes may update immediately; model content uses the existing 300 ms RunOnceScheduler; changing the new option schedules one coalesced zero-delay update. The update creates/reuses SelectionHighlighterState, performs at most one in-memory full-model findMatches on a cache miss, filters matches, allocates decoration descriptors, and updates the decoration collection. Large-tokenization models retain the existing early exit. No external boundary is reached.
- Scaling input: On a cache miss, CPU/allocation scales with document text and effective occurrence count; decoration work scales with matches. Case sensitivity may change effective cardinality by intended semantics, while the default false matches the pre-diff default Find state.
- Effective concurrency: UI-thread serialized. RunOnceScheduler coalesces repeated configuration schedules; there are no parallel searches.
- Cache behavior: SelectionHighlighterState reuses matches when model identity/version, search text, case mode, and word separators are unchanged. A selectionMatchCase toggle changes the cache key and correctly triggers one recomputation; warm unchanged updates reuse cached matches.
- Mechanism confidence: High confidence from the scheduler, cache-key, model-size guard, findMatches, and decoration paths.
- Magnitude uncertainty: Match density determines decoration count, but option toggles are infrequent and the changed scheduling is coalesced rather than per event burst.
- Expensive boundaries: none found
- Verdict: No reportable regression. The only new work is one necessary, coalesced refresh when the matching option itself changes; normal selection highlighting retains its existing scan and allocation structure.

### Scenario 4: Editor option registration and Monaco/standalone API exposure

- Critical path: Editor startup/configuration constructs one additional boolean option descriptor and exposes its enum/type declarations. This is constant startup work with no changed transitive I/O or network boundary.
- Scaling input: Constant per editor option registry, independent of document size, editor events, or number of matches.
- Effective concurrency: Single synchronous registration during module initialization; no fan-out.
- Cache behavior: The resolved option value follows the existing editor configuration cache/event mechanism; no new standalone cache is introduced.
- Mechanism confidence: High confidence from the option registration and declaration-only hunks.
- Magnitude uncertainty: Negligible constant metadata size; no scaling mechanism is present.
- Expensive boundaries: none found
- Verdict: No reportable regression.
