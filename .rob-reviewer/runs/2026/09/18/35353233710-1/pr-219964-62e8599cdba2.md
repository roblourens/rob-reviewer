# Performance review: Don't listen on menu changed, method 2

[PR #219964](https://github.com/microsoft/vscode/pull/219964) at `62e8599cdba29c6f9abbdf685f99ab341a39e4c8`

## Findings (3)

### 1. [medium] Initialize each MenuInfo only once

**Finding ID:** `PERF-18B8C9EA3068`  
**Location:** <code>src/vs/platform/actions/common/menuService.ts:265</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** menu-item array copies, O(M log M) sorting, group arrays, and context-expression traversal  
**Scaling:** Every MenuInfo construction now performs two complete passes over M entries; recursive submenus repeat the duplicate pass, and large menus such as CommandPalette include the full command registry.  
**Outcome:** increased startup and interaction latency with extra allocation and GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the refactor, the MenuInfo constructor called refresh exactly once, producing one copied, sorted, and grouped menu snapshot per construction.  
**Changed behavior:** MenuInfoSnapshot's constructor now calls this.refresh(), which dynamically dispatches \_sort to MenuInfo's override and fully builds the sorted groups. The added this.refresh() in the subclass constructor immediately repeats the same MenuRegistry copy, sort, grouping, and context-key collection.  
**Confidence:** 0.99 — Virtual dispatch makes the superclass refresh use the subclass sorting implementation, and the first pass does not depend on subclass fields. The second call is therefore demonstrably duplicate work; only absolute menu size varies.

**Causal diff evidence:** The added RIGHT-side this.refresh() at menuService.ts:265 is a second immediate invocation after the newly added superclass constructor already invoked refresh.

Opening the command palette, constructing startup toolbars and menus, and rendering custom-tree rows all synchronously pay twice for menu snapshot initialization. The command-palette path is especially large because it includes all registered commands.

**Evidence:** MenuInfoSnapshot's constructor calls refresh at menuService.ts:177. refresh calls the virtual \_sort, so the first call already uses MenuInfo.\_sort and fully initializes the snapshot. The subclass calls refresh again at line 265. MenuRegistry.getMenuItems allocates an array and appends all commands for CommandPalette; CommandsQuickAccessProvider creates that menu on its opening critical path. createActionGroups also recursively constructs MenuInfo for submenus.

**Suggested direction:** Invoke refresh only once: remove the subclass call if the base constructor remains eager, or make the base constructor non-eager and call refresh once after subclass initialization.

### 2. [medium] Hoist menu-context discovery out of the row loop

**Finding ID:** `PERF-47BD98E5F285`  
**Location:** <code>src/vs/workbench/browser/parts/views/treeView.ts:1441</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** MenuRegistry item-array copies, context-expression traversals, and transient Map/Set objects on the UI thread  
**Scaling:** For every global context-key event, cost grows as O(R \* M), where R is the number of rendered custom-tree rows after virtualization and M is the total number of built-in and extension-contributed ViewItemContext menu entries; this occurs even when the changed key is unrelated to the menu.  
**Outcome:** increased UI-thread CPU and GC pressure, causing interaction latency or dropped frames while custom trees are visible  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each rendered row retained a MenuImpl whose MenuInfo collected the menu's dependency sets once when that row was rendered. Subsequent context events checked the cached sets with affectsSome; they did not rescan MenuRegistry or allocate a new dependency snapshot per row and event.  
**Changed behavior:** The renderer now handles every context event itself and, inside the nested rendered-row loop, calls getEntireMenuContexts(). That method constructs MenuInfoSnapshot, copies and traverses all ViewItemContext entries, and allocates another Set on every invocation.  
**Confidence:** 0.99 — The synchronous call path and allocation sites are explicit, and the before/after cache behavior is visible in the deleted per-row MenuImpl listener versus the added snapshot call. Exact row/menu counts vary by viewport and installed extensions, which affects magnitude but not the O(R\*M) mechanism.

**Causal diff evidence:** The added RIGHT-side condition at treeView.ts:1441 places getEntireMenuContexts() inside both loops over \_renderedElements; getEntireMenuContexts and the uncached MenuService.getMenuContexts implementation are also added by this diff.

With a custom tree showing tens of rows and extensions contributing many view-item actions, ordinary global context updates such as focus/editor/context changes synchronously repeat the full menu scan once per row, including for keys that ultimately do not rerender anything.

**Evidence:** TreeRenderer is instantiated with the workbench context service and subscribes directly to onDidChangeContext at line 1208. At line 1441 each rendered element calls TreeMenus.getEntireMenuContexts; that delegates to MenuService.getMenuContexts, which creates a new MenuInfoSnapshot and Set. MenuInfoSnapshot.refresh calls MenuRegistry.getMenuItems (itself an array copy) and traverses every item's when/precondition/toggled expressions. The prior MenuImpl listener at menuService.ts:417-425 uses its already-populated MenuInfo sets instead.

**Suggested direction:** Keep one dependency snapshot per renderer/menu ID and refresh it on ViewItemContext registry changes, or at minimum compute it once before entering the rendered-row loops. Reuse fixed overlay-key sets rather than allocating a Map per row/event.

### 3. [medium] Restore coalescing before rerendering tree rows

**Finding ID:** `PERF-5D60877ADB47`  
**Location:** <code>src/vs/workbench/browser/parts/views/treeView.ts:1208</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** synchronous tree list splices, action-object construction/disposal, and DOM action-bar nodes  
**Scaling:** For U rapid updates to a context key used by ViewItemContext actions, work grows as O(U \* R \* A), where R is affected rendered rows and A is the per-row action/render work; the previous 50 ms menu debounce collapsed updates within the window.  
**Outcome:** blocked UI-thread time and dropped frames during bursts of relevant context-key updates  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each row listened to MenuImpl.onDidChange. MenuImpl uses a DebounceEmitter with the default 50 ms delay, so repeated relevant context changes were merged before the row was rerendered.  
**Changed behavior:** The added direct ContextKeyService listener invokes onDidChangeContext synchronously for every event. An affected event immediately fires all matching items, and the added listener at line 721 calls tree.rerender separately for each; rerender reaches list.splice and renderElement, which clears/recreates action-bar DOM and rebuilds menu actions.  
**Confidence:** 0.96 — The old 50 ms DebounceEmitter and the new immediate call path to per-row DOM rebuilding are explicit. Frequency of relevant extension-defined context updates varies, so severity is medium, but any burst deterministically multiplies work.

**Causal diff evidence:** The added RIGHT-side subscription at treeView.ts:1208 replaces the deleted MenuImpl.onDidChange subscriptions but adds no scheduler, debounce, or event/item coalescing before synchronous rerendering.

An extension or workbench feature that updates a view-item menu context several times during one operation now forces a complete visible-row action rebuild for every intermediate update instead of one coalesced rebuild, making tree interactions visibly janky.

**Evidence:** MenuService.createMenu defaults eventDebounceDelay to 50 ms, and MenuImpl.onDidChange is a DebounceEmitter using that delay at menuService.ts:426-435. The deleted TreeMenus code subscribed to that debounced event. The new subscription at treeView.ts:1208 is directly on ContextKeyService; treeView.ts:1447 fires synchronously, treeView.ts:721 rerenders every item, asyncDataTree.ts:578-585 reaches the tree rerender, and ActionBar.clear/push disposes and creates DOM nodes.

**Suggested direction:** Use one renderer-level debounce/run-once scheduler (preserving the prior delay or scheduling once per frame), merge changed keys and deduplicate affected item handles, then rerender each row once after the burst.
