**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.99

**Mechanism:** Initial MenuInfo construction performed two consecutive full registry reads, sorts, grouping allocations, and context-key/submenu dependency walks with no intervening state change.

**Symptom:** Menu creation paid roughly duplicate initialization CPU and allocation cost, amplified by large contribution sets and recursively constructed submenus.

**Fixed behavior:** Removing the subclass constructor's second refresh leaves the superclass initialization pass as the sole initial registry read, sort, grouping, and dependency-collection pass while later registry-change refreshes remain intact.

**Evidence:** MenuInfoSnapshot's constructor already invokes refresh(), which reads MenuRegistry, sorts menu items through the overridden MenuInfo.\_sort, groups them, and walks all items to collect context keys/submenu IDs. The deleted MenuInfo constructor line invoked refresh() a second time immediately after super(), duplicating that full pass for every persistent menu and each submenu MenuInfo created by the old action path.

### 2. repeated-work

**Fix location:** `src/vs/platform/actions/common/menuService.ts:40` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/actions/common/menuService.ts:41`  
**Introducing path:** `src/vs/platform/actions/common/menuService.ts`  
**Introducing commit:** `603b0ee03b82cc77f90f56a5e0ecfbeee3213de1`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.98

**Mechanism:** Every one-shot menu lookup built and tore down event-tracking persistent-menu infrastructure, repeating registry scans, sorting, context-key collection, listener allocation, and disposal on synchronous per-row/per-selection paths.

**Symptom:** Synchronous menu resolution latency and allocation/GC pressure scaled with the number of selected or rendered tree elements and registered menu contributions.

**Fixed behavior:** One-shot requests now call createMenuActionGroups directly, avoiding persistent-menu listeners, schedulers, dependency collection, and immediate disposal; filtering also occurs before sorting, bounding sort/action construction to contributions matching the current row context.

**Evidence:** The base getMenuActions implementation constructed MenuImpl, called getActions, and immediately disposed it. MenuImpl synchronously constructs MenuInfo, a RunOnceScheduler, a registry listener, disposable stores, and a debounce emitter; MenuInfo scans/sorts registry entries and collects context-key dependencies. Tree-view action resolution calls getMenuActions once for every selected element with a row-specific context, so all of that setup repeated serially per element even though no event could be observed before disposal. The added direct call at line 40 reads/filter/sorts the registry and constructs only the returned actions.

### Scenario 3: Persistent menu creation, registry-driven refresh, and submenu action construction

- Magnitude uncertainty: Persistent-menu sizes and registry-change rates vary, but constructor duplication is directly proven. The replacement of the outer group array on refresh and per-group filtered arrays are small in-memory allocations with no evidence of user-visible regression.
- Expensive boundaries: none found
