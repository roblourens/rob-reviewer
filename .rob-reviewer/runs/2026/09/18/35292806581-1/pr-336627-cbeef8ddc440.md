### Scenario 2: Assignment updates refresh the promoted-action treatment

- Critical path: After WorkbenchAssignmentService has completed a refetch and emits onDidRefetchAssignments, the contribution reads one treatment and updates one context key. This is not on user input, rendering, or startup restoration's synchronous critical path.
- Scaling input: One treatment lookup per assignment-change event, independent of the number of sessions. Events are assignment/filter/configuration changes rather than row-level events.
- Effective concurrency: Each event replaces the prior MutableDisposable and cancels the stale race consumer. The underlying shared assignment lookup may finish, but stale results cannot update the context key; there is no per-session fan-out.
- Cache behavior: The post-refetch read uses the already initialized shared TAS client and current assignments. There is no separate cache owned by the contribution and no miss loop or negative-cache retry per row.
- Mechanism confidence: High: event subscription, cancellation/replacement, and the shared cached getTreatment path are explicit.
- Magnitude uncertainty: The precise frequency of upstream assignment-context events is product-dependent, but the changed work remains constant per event and is not multiplied by sessions or menu instances.
- Expensive boundaries:

### Scenario 3: Rendering visible session rows and switching their primary toolbar action

- Critical path: Each rendered row owns a MenuWorkbenchToolBar scoped to that row. When the global experiment context key changes, affected visible toolbars reevaluate menu expressions and replace the Pin/Unpin or New Chat action.
- Scaling input: Scales with the number of currently rendered/virtualized row templates, not the total session history. It occurs when the resolved experiment value changes, not on scroll, pointer movement, or every row render beyond ordinary menu evaluation.
- Effective concurrency: Context-key notifications are synchronous menu invalidations, but only instantiated/rendered row toolbars are listeners; there is no asynchronous concurrency or boundary call.
- Cache behavior: Menu metadata is registered once. Context expressions read the global experiment key plus existing row-scoped keys; no cache is added or defeated.
- Mechanism confidence: High: SessionItemRenderer creates one scoped MenuWorkbenchToolBar per rendered template, and MenuImpl listens only to relevant context-key changes.
- Magnitude uncertainty: The exact number of simultaneously rendered rows depends on viewport size, but realistic cardinality is bounded by virtualization and updates are infrequent.
- Expensive boundaries: none found
- Verdict: No reportable regression: the intended one-time/infrequent action swap causes bounded toolbar reevaluation and adds no I/O, IPC, layout read, or unbounded retained state.
