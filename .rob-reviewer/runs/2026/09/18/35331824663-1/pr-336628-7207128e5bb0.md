## Findings (1)

### 1. [low] Do not await background catalog refreshes before switching models

**Finding ID:** `PERF-06729DC60296`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5104</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** A Copilot runtime \`models.list\` RPC and its backing network request  
**Scaling:** Every model-change request that overlaps the 30-minute activity-gated refresh, an authentication/token refresh, or a client-restart refresh inherits the full remaining latency of that shared network request; concurrent model changes all remain blocked behind the same request.  
**Outcome:** Increased model-switch latency and a blocked user action when catalog enumeration is slow or stalled  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, \`\_changeModelOnce\` resolved the chat and queued the SDK \`setModel\` operation immediately; background catalog refreshes did not gate the model-selection action.  
**Changed behavior:** \`\_validateModelSelection\` now awaits any scheduled or in-flight catalog refresh before even entering the per-chat queue, despite an already populated \`\_models\` snapshot being available for validation.  
**Confidence:** 0.96 — The changed call path and network boundary are explicit in repository code, and the scheduler establishes realistic periodic and activity-driven overlap. Exact service latency and how often users switch during that overlap are uncertain, so severity is low rather than suppressing the finding.

**Causal diff evidence:** Added RIGHT line 5104 directly inserts \`await (this.\_scheduledModelRefresh?.deferred.p ?? this.\_modelRefreshInFlight);\` on every \`changeModel\` call; no equivalent wait existed before the PR.

Selecting a model while a periodic, token-driven, or restart-driven refresh is in flight now waits for \`client.rpc.models.list\`; the scheduler explicitly documents this as a real network request. On a slow connection or service hiccup, the model picker action can pause for that request even though the current catalog already contains the selected model.

**Evidence:** The added await reads \`\_scheduledModelRefresh?.deferred.p ?? \_modelRefreshInFlight\`. Those promises run \`\_refreshModels\`, which calls \`\_listModels\`, which awaits \`client.rpc.models.list({ gitHubToken })\`. \`AgentModelRefreshScheduler\` starts this real network request after active turns and every 30 minutes. The existing Codex model-resolution path demonstrates the bounded pattern: it starts/waits for refresh only when its model collection is empty.

**Suggested direction:** Validate synchronously against the already populated \`\_models\` snapshot, and only await/start catalog loading when the snapshot is empty or has been explicitly invalidated. Keep refresh coalescing and stale-generation handling unchanged.

### Scenario 3: Executing directory-backed plugin hooks during prompts and tool calls

- Critical path: The session now explicitly registers hooks from all plugins. When the runtime invokes a hook callback, matching commands execute sequentially before the prompt/tool phase can continue.

- Effective concurrency: Commands within one hook type are intentionally serialized; callback invocation is exactly once rather than duplicated between directory discovery and explicit projection.
- Cache behavior: There is no command-result cache; each declared hook invocation intentionally reruns its commands. Session hook configuration is built once per launch.
- Mechanism confidence: High for subprocess execution and serialization; these are the intended semantics of enabling previously inactive directory-backed hooks.
- Magnitude uncertainty: User hook counts and durations vary widely, but the diff's exact-once callback cardinality is tested.
- Expensive boundaries:
