### Scenario 1: An active draft or provider session is replaced while focus remains inside that session's composer.

- Critical path: The provider's synchronous replacement event flows through SessionsManagementService to SessionsService.\_onDidReplaceSession, performs two slot lookups, replaces the visible wrapper transactionally, reruns the renderer reconciliation, and restores composer focus. The focus call performs two getBoundingClientRect reads and may scroll the view before focusing it.
- Scaling input: One replacement per draft graduation/provider replacement, multiplied by the number of visible session slots V. getSessionView, getFocusedSessionView, renderer active-slot lookup, and focusSession each scan at most V mounted slots; V is the user-visible grid cardinality rather than the full session catalog.
- Effective concurrency: Replacement listeners and observable reconciliation execute synchronously and serially on the renderer thread; there is no parallel work or queue burst.
- Cache behavior: Mounted SessionView slots are reused by SessionsPart. Lookups are uncached linear scans over the small mounted slot set; the wrapper is intentionally recreated once for the replacement. No cold/warm network, filesystem, or process cache is involved.
- Mechanism confidence: High: the event path, linear slot scans, identity guard, and geometry reads are directly traced. They do not form a realistic hot or scaling regression.
- Magnitude uncertainty: Exact visible-slot counts and browser layout cost vary, but replacement frequency is lifecycle-bounded and tests establish the focus call occurs at most once per replacement.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/sessions/browser/parts/sessionsPart.ts getFocusedSessionView/focusSession/\_revealView, reached from changed src/vs/sessions/services/sessions/browser/sessionsService.ts lines 535-537 and 519</code>: Read the active DOM element, perform two geometry reads, optionally scroll the active SessionView, and focus its composer.; cardinality: One focus-detection scan per replacement; geometry/focus occurs once only when the replaced mounted view owned focus. Each scan is over V mounted slots.
    - Introduced by diff: true; previous behavior: Different-ID active replacements already triggered focus and geometry work regardless of external focus; same-ID replacements did not refocus because the guard compared IDs. The diff adds refocus only for same-ID replacements whose old view actually owned focus, while suppressing focus for externally focused replacements.; critical-path effect: Synchronous on the replacement event path, but bounded to a single lifecycle event and a small visible-slot set.
- Verdict: No finding. The added same-ID focus restoration is one bounded UI operation when focus was already in the replaced composer, while the new focus test removes previously unnecessary focus work when another surface owns focus.

### Scenario 3: A WSL Dev Container smoke scenario fails and emits connection diagnostics before preserving the original failure.

- Critical path: After the scenario has already failed, automation evaluates a bounded DOM snapshot, then the fixture enumerates the suite log directory and serially reads the shared-process log plus one renderer log per window, capped at 256 KiB each, filters to the last 20 matching entries, redacts/output-caps entries, and then runs the pre-existing broader failure diagnostics before rethrowing.
- Scaling input: W+1 log files where W is the number of windowN directories in one isolated smoke suite; at most 256 KiB is read per file, 20 matching entries retained per file, and individual emitted entries are sliced to 2,000 characters. UI collections are capped at 5 quick inputs, 10 rows each, 10 notifications, and 5 dialogs.
- Effective concurrency: DOM evaluation is one automation IPC request. Files are opened/read/closed serially in a for loop, so there is no I/O burst; errors are handled per file and diagnostic work completes before the original error is rethrown.
- Cache behavior: No cache is used because this is a one-shot failure snapshot. Each selected file is read once from its tail; no negative-cache behavior or retries are introduced.
- Mechanism confidence: High: call placement, file cardinality, byte caps, serial scheduling, and output caps are explicit in the changed code.
- Magnitude uncertainty: A pathological suite with many window directories increases serial reads linearly, and slow filesystem duration is unmeasured, but suite isolation and the per-file cap keep realistic cost bounded.

- Scaling input: One process query per canceled job, stop calls proportional to lingering test processes under the test root, and one log artifact whose bytes scale with that job's generated logs.
- Effective concurrency: Pipeline steps and output publication are sequenced during cancellation; cleanup does not create a concurrent process burst. The phase is globally bounded by cancelTimeoutInMinutes: 10.
- Cache behavior: No caches. Publication transfers the current job log tree once; canceled jobs previously skipped these cancellation-only operations.
- Mechanism confidence: High: conditions and cancellation budget directly establish the added cancellation-only process and network work.
- Magnitude uncertainty: The number of canceled jobs, lingering processes, log bytes, and upload duration are not established. The worst scheduling extension is explicitly bounded at ten minutes.
