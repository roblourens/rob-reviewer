# Performance review: Fix Enterprise Managed OTel Race in Copilot Extension

[PR #336701](https://github.com/microsoft/vscode/pull/336701) at `9ff9a507646cb73861c2ed9b5adcdb9988c72852`

## Findings (1)

### 1. [medium] Preserve the configured OTel attribute-size cap under policy

**Finding ID:** `PERF-D998E088F2C3`  
**Location:** <code>extensions/copilot/src/platform/otel/common/otelConfigResolution.ts:91</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Serialized prompt, response, tool, and hook attribute bytes retained by spans/batches and encoded into OTLP requests.  
**Scaling:** Cost changes from at most the configured number of characters per content attribute to the full payload size, multiplied by the several content attributes and model/tool spans emitted during each agent turn; large contexts and tool results amplify retained and exported bytes.  
**Outcome:** Larger OTLP batches increase extension-host memory/GC pressure and network transfer, and can exceed collector attribute/request limits that the setting was intended to enforce.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Service construction previously passed \`otelSettings.get&lt;number&gt;('maxAttributeSizeChars')\` directly to \`resolveOTelConfig\`, so an enterprise policy for enablement/endpoint/capture settings did not discard the user's positive content-size bound.  
**Changed behavior:** The new resolver obtains \`maxAttributeSizeChars\` through \`read()\`. Whenever any recognizable enterprise OTel setting exists, \`read()\` returns \`inspect().defaultValue\` for every key; because \`maxAttributeSizeChars\` is not policy-backed, that value is the schema default \`0\` (unlimited), even when the user configured a positive cap.  
**Confidence:** 0.98 — The before/after resolver behavior is explicit in the diff, the manifest confirms this key has no policy reference and defaults to 0, and numerous traced production call sites use this value to bound content attributes that the SDK retains and batch-exports. Exact payload sizes vary, but the loss of the bound and its scaling are deterministic.

**Causal diff evidence:** Added lines 79-82 switch all settings to policy/default values when \`hasEnterpriseSettings\` is true, and added line 91 routes \`maxAttributeSizeChars\` through that switch. The replaced code in \`services.ts\` read this key directly from effective user settings.

In an enterprise-managed OTel deployment, a user who configured a finite \`maxAttributeSizeChars\` limit silently gets unlimited attributes after this change. Large agent contexts or tool results are then retained and exported in full on each turn, increasing memory and network cost and risking oversized batch failures.

**Evidence:** \`truncateForOTel\` explicitly treats values &lt;= 0 as unlimited. Chat/model/tool paths pass \`config.maxAttributeSizeChars\` when attaching serialized input messages, system instructions, tool definitions, request metadata, tool arguments, results, and outputs. \`RealSpanHandle\` keeps these strings in its attribute map, while \`NodeOTelService\` uses \`BatchSpanProcessor\` and OTLP exporters, so removing the cap increases retained and transmitted attribute bytes until each batch exports.

**Suggested direction:** Keep user-only controls outside the enterprise block replacement: read \`maxAttributeSizeChars\` directly from \`settings.get()\` (while retaining the existing environment-variable precedence), and add a policy-present regression test that preserves a positive user cap.
