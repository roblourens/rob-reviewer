# Performance review: VS code remote tunnel terminal in external terminal

[PR #336724](https://github.com/microsoft/vscode/pull/336724) at `79a8ea37b0d4429dc1cf914c5ee02a11ce4eca4a`

## Findings (3)

### 1. [medium] Abort in-flight setup RPCs on termination

**Finding ID:** `PERF-AE9FE538394C`  
**Location:** <code>experimental/tunnel-terminal-client/src/terminal.ts:181</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** A pending WebSocket JSON-RPC request and, during createTerminal, a potentially running remote shell process  
**Scaling:** Cancellation latency grows to the remaining timeout of whichever initialize, createTerminal, or subscribe request is active, up to the shared 30-second default.  
**Outcome:** Blocked CLI termination and delayed remote-shell cleanup  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no standalone runTerminal setup path or signal handler that could enter these timeout-bound RPC waits.  
**Changed behavior:** The new SIGINT/SIGTERM/SIGHUP handlers only resolve the separate completion promise via finish(), while setup remains synchronously awaited in initialize, createTerminal, or subscribe.  
**Confidence:** 0.99 — The signal handler, awaited setup requests, default 30-second timeout, and lack of cancellation propagation are all explicit in the changed code. Only how often a remote host stalls is uncertain.

**Causal diff evidence:** The added termination handler at line 181 records completion but does not abort the newly added timeout-bound setup requests at lines 195, 207, and 217.

If the agent host is slow or stops replying during setup, Ctrl+C or process termination appears ignored for as long as 30 seconds. If createTerminal was already sent, cleanup is also deferred while the remote shell may continue running.

**Evidence:** Line 181 calls finish() only. The same function is still awaiting client.request at lines 195, 207, or 217; ProtocolClient.request has no AbortSignal and uses the 30,000 ms default timeout, so finish() cannot settle the active await. The outer setup abort handlers are removed before runTerminal is invoked.

**Suggested direction:** Give the terminal session an AbortController and make ProtocolClient.request/deadline accept it, aborting the pending setup await on these signals; retain the disposeTerminal request when creation may already have reached the server.

### 2. [medium] Coalesce terminal resize actions

**Finding ID:** `PERF-7FC6AAEC733D`  
**Location:** <code>experimental/tunnel-terminal-client/src/terminal.ts:169</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** WebSocket messages, server state reductions, native PTY resize calls, and headless-terminal reflow CPU  
**Scaling:** Cost grows with every grid-size event while a window is dragged, and each horizontal resize becomes more expensive as the remote terminal's scrollback grows.  
**Outcome:** Excess network/CPU work and resize jank for long-running terminals  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR the standalone client emitted no resize traffic. The existing VS Code terminal path routes layout changes through TerminalResizeDebouncer, using a 100 ms debounce for costly horizontal reflow once scrollback is nontrivial.  
**Changed behavior:** Every stdout resize event immediately dispatches a terminal/resized protocol action, including repeated intermediate dimensions, with no deduplication or coalescing.  
**Confidence:** 0.97 — The event-to-WebSocket-to-PTY/headless-terminal call path and the repository's established debounce for reflow are explicit. Exact event rate varies by terminal host and drag behavior, affecting magnitude rather than mechanism.

**Causal diff evidence:** The added onResize callback at line 169 sends one protocol action synchronously for each local resize event rather than retaining and flushing the latest dimensions.

Dragging a terminal window after accumulating scrollback can generate a burst of round trips and remote reflows, making resize and terminal interaction stutter.

**Evidence:** Line 169 dispatches directly from the resize event. AgentHostTerminalManager handles each TerminalResized envelope by calling both terminal.pty.resize() and terminal.headlessTerminal.resize(); the platform's TerminalResizeDebouncer documents horizontal resize as expensive due to reflow and debounces it by 100 ms.

**Suggested direction:** Send the initial dimensions immediately, then deduplicate identical dimensions and debounce/coalesce subsequent resize events to the latest cols/rows (with a final flush on quiescence/teardown).

### 3. [medium] Start remote disposal before waiting for local output

**Finding ID:** `PERF-ADE090D87099`  
**Location:** <code>experimental/tunnel-terminal-client/src/terminal.ts:273</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Queued terminal output, an unnecessarily live remote shell process, and a subsequent network cleanup RPC  
**Scaling:** Shutdown delay grows with queued output and local terminal drain speed up to 5 seconds, then adds the disposeTerminal RPC's separate timeout of up to another 5 seconds.  
**Outcome:** Increased exit latency and delayed release of the remote process  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no standalone session cleanup sequence that serialized local terminal draining ahead of remote process disposal.  
**Changed behavior:** The new finally block first waits up to five seconds for local output and the keyboard-mode reset to flush, restores input mode, and only then sends disposeTerminal at line 290.  
**Confidence:** 0.96 — Both timeout values and their strict sequential ordering are explicit, and the server contract confirms disposal releases the remote process. The uncertain factor is how often users exit with a slow-output backlog.

**Causal diff evidence:** The added await at line 273 places the bounded local-output flush directly before, and therefore serializes it with, the added remote cleanup request at line 290.

When a user presses Ctrl+\] or terminates during heavy output on a slow terminal, the command can remain open for up to roughly 10 seconds and the remote shell keeps running throughout the first wait, even though remote disposal is independent of the required local write ordering.

**Evidence:** Line 273 awaits a 5,000 ms local drain. The disposeTerminal request is not started until line 290 and has its own 5,000 ms timeout. The protocol contract states disposeTerminal kills the process if it is still running, while the local reset only needs to precede restoring cooked input.

**Suggested direction:** Start the disposeTerminal request as soon as cleanup begins and await it alongside the local flush; keep the keyboard reset flush ordered before setRawMode(wasRaw), but do not make remote process cleanup wait on local rendering.
