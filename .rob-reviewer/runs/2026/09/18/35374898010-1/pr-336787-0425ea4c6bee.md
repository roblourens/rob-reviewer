## Findings (1)

### 1. [medium] Keep header measurement out of list refresh rendering

**Finding ID:** `PERF-15FA5F87128F`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:495</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** DOM style and layout work across the rendered sessions tree  
**Scaling:** The cost is paid once per SessionsList.update/refresh and the forced layout must resolve the DOM mutations made while re-rendering the currently visible rows; it therefore grows with provider/session change frequency and rendered sidebar complexity.  
**Outcome:** increased synchronous update latency and sidebar jank while sessions are changing  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The Sessions header remained outside the object tree. Its width-dependent layout was measured only from SessionsView layout/find-state paths, so ordinary session-list model updates did not detach, append, and synchronously measure the header.  
**Changed behavior:** The header is now a tree row, and every renderElement call appends it and immediately invokes updateHeaderLayout. That callback writes display styles and reads headerLabel.clientWidth, synchronously resolving layout during the tree's root splice.  
**Confidence:** 0.96 — The call path and synchronous geometry read are explicit, and the tree implementation confirms full rendered-row disposal/re-render on setChildren without diff options. Exact milliseconds and event prevalence vary by provider and list size, which affects severity but not the mechanism.

**Causal diff evidence:** Added line 495 calls this.layoutHeader() from SessionsHeaderRenderer.renderElement immediately after appending the live header. SessionsList.update still calls tree.setChildren(null, children), whose non-diff object-tree splice disposes and reinserts visible rows on each update, so this new callback runs for each visible-list refresh.

With the Sessions sidebar visible, each provider/session update—such as title, status, read, or archive changes during active work—now introduces a synchronous layout flush while the list is rebuilding. This lengthens UI-thread refreshes and can make the sidebar stutter, especially with many visible rows or concurrent session changes.

**Evidence:** SessionsList.update ends in tree.setChildren(null, children) (line 4073) and is reached from visible provider onDidChangeSessions refreshes, list-model changes, active-session changes, filters, and other events. ObjectTreeModel.setChildren performs a full splice without diffIdentityProvider; ListView.\_splice calls disposeElement for rendered rows and then renderElement on reused rows. The new renderer therefore removes/re-appends the header and invokes SessionsView.updateHeaderLayout, whose desktop path reads headerLabel.clientWidth after setting display styles (sessionsView.ts:623-646), forcing layout in the middle of the refresh.

**Suggested direction:** Do not call the width-measuring updateHeaderLayout from renderElement on every model refresh. Keep it on the existing view resize and find-open/close paths, and if initial reparenting needs a pass, coalesce a single measurement after rendering (for example on the next animation frame) rather than measuring inside the tree splice.
