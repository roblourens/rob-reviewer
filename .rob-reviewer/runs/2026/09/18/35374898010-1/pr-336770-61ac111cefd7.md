### Scenario 1: Render or refresh the new-session repository configuration toolbar for Agent Host or Copilot sessions

- Critical path: MenuWorkbenchToolBar synchronously reads visible menu groups, creates the visible picker action view items plus one separator between groups, and renders them before the toolbar is ready. The diff adds only O(A) short group-key formatting and A-1 lightweight separator actions/DOM items; no asynchronous operation is placed on this path.
- Scaling input: A is the effective count of repository controls visible for the current scoped session after context-key filtering, not all registrations across sessions. The schema-backed Agent Host path can register V×P global menu entries for V visible sessions and P renderable properties, but the toolbar renders only the current session's P entries; typical built-in configurations expose a small handful.
- Effective concurrency: All grouping, sorting, action creation, and DOM rendering is synchronous on the UI thread. Menu changes remain debounced by the existing menu service; the diff does not add parallel work or a new event source.
- Cache behavior: Menu/action visibility continues to use existing MenuWorkbenchToolBar and menu-service state. The new group helper has no cache and performs one bounded string conversion per registration/refresh; there is no cold-versus-warm boundary behavior to change.
- Mechanism confidence: High confidence in the added synchronous DOM/allocation work because getActionBarActions inserts a Separator for each additional primary group and ActionViewItem renders one anchor. High confidence that effective visible cardinality is session-filtered and that no boundary call is introduced.
- Magnitude uncertainty: Third-party or future provider schemas could expose more properties, but the incremental cost remains one tiny separator item and one short group string per visible property. There is no evidence of realistically large cardinality or frame-frequency rebuilds sufficient for a reportable regression.
- Expensive boundaries: none found
- Verdict: No reportable regression. The extra synchronous work is linear in the already-rendered, realistically small action count and is the intentional mechanism for visual separators.

- Mechanism confidence: High confidence from tracing \_showPicker through \_getItems to provider.getSessionConfigCompletions and IAgentConnection.sessionConfigCompletions, and from the changed lines being after the existing await.

### Scenario 3: Refresh repository menu registrations when visible sessions, provider configuration, or phone layout changes

- Critical path: The existing contribution synchronously clears registrations, iterates visible sessions and renderable schema properties, and re-registers menu items; menu listeners then rebuild affected toolbars. The diff replaces each constant group name with a stable padded group string, without adding a new refresh trigger or additional provider lookup.
- Scaling input: Work remains O(V×P) for V visible sessions and P renderable properties during a refresh. The changed portion adds one bounded string construction per existing menu item; visible toolbars still context-filter to one session.
- Effective concurrency: Refreshes remain synchronous event/autorun work. Provider listeners, context-key listeners, and visible-session autorun are unchanged; no new concurrency, queue, or burst is introduced.
- Cache behavior: Command/action-view registrations remain retained in the existing DisposableMap and menu items in the existing DisposableStore, which is cleared each refresh. Group strings live only with their corresponding existing menu registrations and are disposed on the same lifecycle.
- Mechanism confidence: High confidence from constructor listener tracing and \_refreshRepositoryMenuItems: all refresh sources and provider/config reads predate the diff, and the only changed operation inside the loop is group-key formatting.
- Magnitude uncertainty: The maximum number of visible sessions and provider-defined properties is not fixed here, but the PR neither changes that cardinality nor adds collection-wide work beyond a short string format for each already-created registration.
- Expensive boundaries: none found
- Verdict: No reportable regression. Existing O(V×P) refresh behavior is not materially amplified by the bounded string allocation.

### Scenario 4: Hover repository controls and keep the repository action bar highlighted while its branch picker is open

- Critical path: Pointer hover and picker open/close trigger normal selector matching and repaint for the small toolbar container. The changed CSS uses background/color state and does not add geometry reads, filters, animations, transitions, or nested synchronous relayout.
- Scaling input: Cost is bounded by the repository toolbar's small visible action count and user hover/open events; it does not scale with chat history, repository size, branch count, or frame-driven animation.
- Effective concurrency: Browser style and paint work is event-driven with no JavaScript loop or asynchronous fan-out. Attribute writes happen once on open and once on hide.
- Cache behavior: No application cache is involved. CSS matching and browser style caches are used normally; the data-picker-open attribute is removed on hide, so no state accumulates across picker lifetimes.
- Mechanism confidence: High confidence from the changed selectors/declarations and picker lifecycle: the diff adds only bounded style state and no layout read-after-write path.
- Magnitude uncertainty: Exact paint cost varies by theme/compositor, but the affected area is a small control bar and the declarations are simple colors/background images without known high-cost effects.
- Expensive boundaries: none found
- Verdict: No reportable regression. The rendering work is small, user-driven, and bounded.
