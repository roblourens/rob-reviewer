# Performance review: sessions: Track editor chat cohorts in Agents telemetry

## Findings (2)

### 1. [low] Do not hold shutdown open for the telemetry probe timeout

**Finding ID:** `PERF-F201D406EAB4`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/editorChatUsage.contribution.ts:114</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Shutdown join time waiting on 200 ms timer-backed probe promises  
**Scaling:** Any submission during the 200 ms before close/reload adds a pending operation; because probes run concurrently, delay is bounded by the latest probe's remaining timeout but can approach the full 200 ms after the most recent submission.  
**Outcome:** Blocked window close or reload for up to 200 ms  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this contribution, closing or reloading an editor window had no editor-usage probe promise to join and therefore no telemetry-imposed 200 ms wait.  
**Changed behavior:** Every accepted request creates a probe that resolves only after a peer response or the 200 ms timeout. The added shutdown listener joins \`Promise.all(pending)\`, and desktop lifecycle explicitly awaits default joiners before the window closes.  
**Confidence:** 0.99 — The 200 ms timeout, pending-set lifecycle, and blocking shutdown join are explicit and deterministic. Only how often users close within that interval is uncertain, which is reflected in low severity.

**Causal diff evidence:** Added line 114 newly joins all pending cross-window telemetry operations during shutdown; those operations are introduced at lines 92-105 and use a 200 ms timeout.

In the common single-window/no-responding-peer case, closing or reloading shortly after sending a chat message visibly waits for the remainder of the 200 ms telemetry timeout, even though this accounting is documented as best effort.

**Evidence:** The promise is added to \`pending\` after scheduling \`disposableTimeout(..., 200)\` and has no earlier completion when no peer replies. \`NativeLifecycleService.handleWillShutdown\` awaits \`Promises.settled(joiners)\`, and the lifecycle contract states joined promises block application closing. Line 114 places all such timer-backed operations into that blocking phase.

**Suggested direction:** On shutdown, synchronously dispose/finalize outstanding probes and record the local counters without waiting for remote replies, or split baseline recording from the optional cross-window increment so the best-effort remote check never joins the shutdown critical path.

### 2. [medium] Keep telemetry probes from activating every window's session providers

**Finding ID:** `PERF-33D8B5F28DE5`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/editorChatUsage.contribution.ts:52</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Extension-host IPC refreshes, synchronous cached-session parsing, and per-window session-array allocations  
**Scaling:** For one accepted message, work grows across all W open editor windows; a previously idle peer can refresh each of its P registered providers, and every probe scans/materializes its C chat models plus S persisted agent sessions, yielding O(W\*P) provider refreshes and O(W\*(C+S)) local work.  
**Outcome:** Excessive cross-window IPC/CPU and increased latency returning from an editor chat send  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, accepting an editor chat message did not broadcast a probe, access \`IAgentSessionsService.model\`, parse the agent-session cache, or refresh session providers in unrelated windows; the delayed service/model stayed lazy until a feature that displayed or used agent sessions requested it.  
**Changed behavior:** The new \`hasOtherSession\` closure reads \`agentSessionsService.model.sessions\`. It is called synchronously for the submitting request and by every window receiving the new broadcast probe. The first read creates \`AgentSessionsModel\`, parses all cached sessions, and calls \`resolve(undefined)\`; that path refreshes every registered controller, with extension controllers crossing \`$refreshChatSessionItems\` IPC. Subsequent probes still materialize and deduplicate the entire historical session array.  
**Confidence:** 0.98 — The changed synchronous listener, broadcast fan-out, lazy model getter side effect, full-list getter, and extension-host refresh RPC are all directly traced in repository code. The exact session/window counts vary, affecting magnitude but not the mechanism or reachability.

**Causal diff evidence:** Added line 52 newly dereferences \`agentSessionsService.model.sessions\` from the telemetry predicate; added line 80 invokes that predicate for every incoming cross-window probe, and added line 91 invokes it synchronously for every accepted local submission.

Sending one editor chat message with several VS Code windows open can activate and refresh all chat-session providers in every idle peer window, while the submitting window synchronously pays full-history setup/scanning before \`sendRequest\` returns. Users with multiple windows or large agent-session histories can see first-send latency and a burst of extension-host/provider work unrelated to the requested chat.

**Evidence:** \`Emitter.fire\` delivers the new acceptance listener synchronously. This closure dereferences the lazy \`agentSessionsService.model\`; its getter constructs \`AgentSessionsModel\`, whose constructor parses \`agentSessions.model.cache\` and whose service getter invokes \`model.resolve(undefined)\`. \`resolve\` schedules every registered provider, \`refreshChatSessionItems\` calls each controller's \`refresh\`, and extension-backed controllers implement that as \`\_proxy.$refreshChatSessionItems\`. The \`sessions\` getter also converts the complete map to an array and runs full-list deduplication before \`some\`. The broadcast receive path calls the same closure in every peer.

**Suggested direction:** Answer telemetry from a lightweight set/count of currently in-progress resource IDs that is maintained by existing status/model events, and let probe handling inspect only already-initialized state. In particular, do not dereference the lazy agent-sessions model or call its full \`sessions\` getter from this best-effort telemetry path; if no lightweight state exists yet, expose a non-activating peek rather than resolving providers.

### Scenario 2: Close, quit, or reload an editor window shortly after sending a chat request

- Scaling input: Submissions made in the final 200 ms before shutdown. Multiple probes settle concurrently, so delay is bounded by the most recent probe's remaining timeout and can approach 200 ms.
- Effective concurrency: All pending operations are awaited with \`Promise.all\`; concurrency prevents additive N\*200 ms waits but does not remove the latest timer deadline.
- Cache behavior: No cache or negative response shortens the common no-peer case; absence of a peer is learned only by the fixed timeout.
- Mechanism confidence: High: timeout creation and native lifecycle join semantics are explicit.
- Magnitude uncertainty: Closing/reloading within 200 ms of submission is intermittent, but when triggered the blocking interval is deterministic.
- Expensive boundaries:

- Verdict: Reportable low-severity shutdown latency regression; best-effort telemetry should not block close/reload.
