### Scenario 1: GitHub CodeQL analysis on pull requests, main/release pushes, and the weekly schedule

- Critical path: Each workflow run must complete checkout, CodeQL initialization, and analysis for its matrix language before the CodeQL job completes; this is CI-only and not on an editor product path.
- Scaling input: Repository source size after paths-ignore filtering, with two matrix entries: JavaScript/TypeScript and Rust.
- Effective concurrency: The two language matrix jobs may run in parallel; fail-fast is disabled. Each language performs one checkout, one initialization, and one analysis.
- Cache behavior: CodeQL dependency caching is enabled. Cold runs may populate/download dependencies; warm runs can reuse the action cache. The source filtering is static and has no application cache lifecycle.
- Mechanism confidence: High confidence in the new workflow's two-job boundary and trigger model; insufficient evidence that it regresses performance relative to the external default setup.
- Magnitude uncertainty: Exact default-setup triggers, runner cache hit rate, and prior analysis duration are external to the repository. The diff and PR context indicate replacement and scope reduction, not additive application work.
- Expensive boundaries:
  - network at <code>.github/workflows/codeql.yml:36-46</code>: Checkout the repository and obtain CodeQL action/dependency data.; cardinality: Once per language job, so two checkout/init sequences per workflow run.

- Verdict: No reportable regression. The workflow adds explicit CI boundaries but is designed to replace default setup and narrows analyzed paths; there is no high-confidence diff evidence of duplicated or increased work.

### Scenario 3: TypeScript task auto-detection when VS Code requests contributed TypeScript tasks

- Critical path: provideTasks waits concurrently for active-file projectInfo and one workspace-wide findFiles call, then checks discovered config URIs and builds task definitions. Workspace search remains bounded by the same five-second timeout.
- Scaling input: Number of workspace tsconfig files after the single workspace search; existence checks and task construction scale with distinct config paths.
- Effective concurrency: Active-file lookup and workspace search run in parallel. Config existence checks use Promise.all. The workspace search itself is one coalesced VS Code findFiles request, not one request per config.
- Cache behavior: No cache is introduced or bypassed. Each provider invocation performs the existing workspace search; cancellation terminates a timed-out search. The new raceTimeout also clears its timer when the search completes early.
- Mechanism confidence: High confidence from the direct call path and helper implementation that the new code does not add work; it removes the dependency on test utilities and clears the timer on early completion.
- Magnitude uncertainty: Actual workspace search duration and config count vary by workspace, but the changed helper preserves both boundary cardinality and the timeout.
- Expensive boundaries:
