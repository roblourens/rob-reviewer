## Findings (1)

### 1. [medium] Coalesce capture before applying the latest target

**Finding ID:** `PERF-E7F1A29971F1`  
**Location:** <code>src/vs/sessions/contrib/automations/browser/automationDialog.ts:365</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Provider configuration capture promises, including Agent Host configuration-resolution IPC, plus serialized wall-clock wait time.  
**Scaling:** Cost is one capture/timeout per synchronization iteration rather than one per old draft; rapid target changes during a stalled capture can repeatedly pay 1,000 ms against the same session, and timed-out underlying promises remain pending.  
**Outcome:** Retarget UI latency grows by the one-second capture timeout for each stale synchronization iteration, blocking creation and display of the final target draft.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, target synchronization validated the workspace and immediately created the latest draft; it did not await provider capture or repeat stalled capture work while coalescing target changes.  
**Changed behavior:** Retargeting now synchronously captures the previous provider draft before creating the requested draft; stale retarget iterations still pay that capture and leave the old draft installed, causing the next iteration to capture it again.  
**Confidence:** 0.97 — The synchronizer's serialized while-loop, generation update, one-second timeout, and post-await generation check are explicit in the changed code. The new test also establishes that provider capture may never settle. Exact provider stall prevalence is uncertain, which affects severity rather than the mechanism.

**Causal diff evidence:** The added \`await this.captureSessionConfiguration(this.session, this.appliedTarget, this.retargetConfigurationCaptureTimeoutMs);\` runs before the stale-generation check. \`update()\` marks another sync iteration while the await is pending, so after a timeout the stale iteration returns and the next iteration invokes the same capture again against the unchanged draft.

When an Agent Host/provider configuration request is slow or disconnected, quickly switching folder/provider/session type leaves the session controls unavailable for roughly two seconds for a common A→B→C correction, and further switches can add another timeout while also spawning additional never-settling capture promises.

**Evidence:** \`scheduleSync()\` serializes updates in a loop. During \`sync()\`, line 365 awaits capture with a 1,000 ms timeout and only then checks whether \`generation\` changed. For A→B followed quickly by C while A's capture stalls, B's iteration waits one second, observes it is stale, leaves A as \`this.session\`, and the queued C iteration waits another second capturing A again. \`captureSessionConfiguration\` uses \`raceTimeout\` without cancelling the underlying provider promise, and \`automationDialog.test.ts\` explicitly covers a never-resolving capture promise.

**Suggested direction:** Coalesce capture by applied session: start at most one capture attempt for the old draft, share its result/deadline across queued target updates, and after it settles or times out create only the latest requested target. Also cancel or otherwise release the underlying provider capture when abandoning the draft.
