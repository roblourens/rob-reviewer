## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/bootstrap-esm.ts:137` (`RIGHT`)  
**Blamed base line:** `src/bootstrap-esm.ts:175`  
**Introducing path:** `src/bootstrap-esm.ts`  
**Introducing commit:** `08a1ad01b35e41b7412e2290c010cda68bdf6333`  
**Mechanism family:** `repeated-work`  
**Performance category:** `startup`  
**Confidence:** 0.98

**Mechanism:** Repeated imports of the same packaged bare module synchronously repeated default resolution and ASAR package/direct resolution instead of reusing the prior successful result.

**Symptom:** Repeated synchronous module and ASAR resolution consumed main-process CPU during packaged startup and later repeated dynamic imports.

**Fixed behavior:** The hook keys successful archive resolutions by specifier, normalized parent path, conditions, and import attributes, then returns the cached resolver output before invoking the default resolver or ASAR lookup. It leaves failures, closer dependencies, external parents, CommonJS, and non-packaged processes uncached.

**Evidence:** Before this PR, every packaged ESM bare-specifier resolution that missed the default resolver reached synchronous ASAR resolution (`asarRequire.resolve`) even when the same specifier and parent had already resolved. The added integration test invokes four resolutions for two effective specifier-parent contexts and proves the changed hook performs only two archive package lookups plus two cache hits; without the added cache lookup/set, all four invocations follow the old archive-resolution path. `bootstrap-esm.ts` is imported by packaged Electron main/fork/CLI entry points, placing this repeated synchronous resolver work on startup and later dynamic-import paths.
