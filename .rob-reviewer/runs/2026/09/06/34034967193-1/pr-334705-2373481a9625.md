# Performance review: Make action widget menu items directly clickable by Playwright

[PR #334705](https://github.com/microsoft/vscode/pull/334705) at `2373481a96253a7623f1df8234169b1b000cb224`

## Findings (1)

### 1. [low] Dispose the one-shot mousemove listener after activation

**Finding ID:** `PERF-4343BCF772A7`  
**Location:** <code>src/vs/platform/actionWidget/browser/actionList.ts:961</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Main-thread DOM ancestor traversal and one IListMouseEvent allocation for each mousemove  
**Scaling:** The cost repeats at pointer-event frequency for the entire lifetime of every open action list (including code-action and chat model-picker menus), rather than only for the first non-zero movement; high-polling mice can generate hundreds to thousands of events per second.  
**Outcome:** Increased main-thread CPU and allocation/GC pressure while moving the pointer over an open action menu, with avoidable input/rendering contention on high-event-rate devices.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The pointer shield handled POINTER\_MOVE only until the first movement, then removed itself from the DOM, so later pointer motion did not execute this activation work.  
**Changed behavior:** The diff registers List.onMouseMove for the full widget lifetime. Although the callback body becomes a no-op once \_ignoreInitialHover is false, ListView still maps every DOM mousemove through toMouseEvent before invoking it.  
**Confidence:** 0.97 — The permanent subscription, one-way state transition, and ListView's per-event mapper/ancestor walk are directly established in repository code, and the affected widgets are product-facing code-action and chat picker menus. Exact CPU cost varies with pointer polling rate and popup dwell time, which limits severity but not mechanism confidence.

**Causal diff evidence:** Added line 961 registers \`this.\_list.onMouseMove(...)\` in the widget-wide disposable store; lines 962-965 show that only the first non-zero event has useful behavior, while all subsequent mapped events remain subscribed. The deleted pointer-block implementation removed its event-receiving DOM node on the first POINTER\_MOVE.

After the first movement over an open code-action, dropdown, or model-picker list, all later movements still perform DOM target-to-row resolution and allocate a mapped list event. This scales with mouse polling rate and can add avoidable CPU/GC pressure while the popup is being interacted with.

**Evidence:** ListView.onMouseMove is an Event.map over a DOM \`mousemove\` emitter (\`src/vs/base/browser/ui/list/listView.ts:1159\`), and the mapper calls \`toMouseEvent\`, which invokes \`getItemIndexFromEventTarget\`; that method walks ancestors, calls \`scrollableElement.contains\`, reads \`data-index\`, and allocates the returned IListMouseEvent (\`listView.ts:1165-1169,1541-1559\`). The new callback only needs the first non-zero movement, because it permanently sets \`\_ignoreInitialHover = false\`, but the subscription at the changed line remains registered until the entire ActionListWidget is disposed.

**Suggested direction:** Use a raw disposable \`mousemove\` listener on the list element and dispose/clear that listener immediately after the first non-zero movement (while retaining mousedown activation), so row hover continues via the existing \`onMouseOver\` handler without permanent per-move mapping.

- Verdict: Reportable low-severity repeated work: the diff replaces a first-movement-only shield path with a widget-lifetime mousemove subscription whose mapping cost continues after activation.
