### Scenario 1: Open an MCP server install link containing a direct gallery server URL

- Critical path: Resolve the active gallery manifest, validate the URL, fetch one server document, parse it, then open the server UI. The manifest and server request are on the critical path.
- Scaling input: One user-opened install URL; URL parsing and package filtering scale with one server document and its package count.
- Effective concurrency: The direct install path is serial. Manifest initialization is promise-coalesced; there is no new concurrent burst.
- Cache behavior: Workbench manifest initialization is cached by initPromise, and custom-version discovery is cached by URL. Server documents are not cached before or after this diff.
- Mechanism confidence: High: the direct caller, manifest cache, and request call were traced end to end.
- Magnitude uncertainty: Registry latency varies, but the diff does not add a request and prevents redirect/external requests on rejected inputs.
- Expensive boundaries:
  - network at <code>src/vs/platform/mcp/common/mcpGalleryService.ts:getMcpServer</code>: Fetch the individual MCP server document with redirects disabled; cardinality: One request for a valid direct install URL; zero for a URL rejected by origin/path validation. Redirect targets are no longer requested.
    - Introduced by diff: false; previous behavior: One initial server request was also made, with fetch redirects followed automatically; invalid external URLs could also trigger that request.; critical-path effect: The request must complete before the server editor opens.
  - network at <code>src/vs/platform/mcp/common/mcpGalleryManifestService.ts:getVersion</code>: Probe supported gallery versions when a custom gallery omits an explicit version; cardinality: At most two probes on the cold custom-gallery path, coalesced by the manifest service's initPromise/versionByUrl caches; normally zero for the product gallery's fixed v0.1 version.
    - Introduced by diff: false; previous behavior: A valid direct URL fetched the server first and then resolved the same manifest; total boundary cardinality was unchanged.; critical-path effect: The changed method now awaits manifest resolution before the server request, but the same manifest resolution already occurred later on the pre-diff valid-URL path.
- Verdict: No reportable regression. Valid links retain the same required manifest and server boundaries, while rejected links and redirects perform less network work.

### Scenario 2: Synchronize installed MCP servers with gallery metadata by name

- Critical path: After a delayed registry sync, deduplicate installed servers by name, resolve the shared manifest once, and resolve each unique name through configured endpoints before applying metadata. This is asynchronous maintenance rather than an input/render critical path.
- Scaling input: Distinct installed MCP server names after Map deduplication, typically a small user-managed set.
- Effective concurrency: One serial endpoint chain per unique name, with all unique names concurrently active through the existing Promise.all; no limiter or new concurrency was introduced.
- Cache behavior: One cached/coalesced manifest is shared across the batch; individual server responses are uncached both before and after the change.
- Mechanism confidence: High: caller deduplication, shared manifest ownership, endpoint loop, and concurrency were directly traced.
- Magnitude uncertainty: Very large installed-server sets could expose the pre-existing unbounded Promise.all fan-out, but the diff neither introduces nor amplifies it.
- Expensive boundaries:
  - network at <code>src/vs/platform/mcp/common/mcpGalleryService.ts:resolveMcpServersFromGallery/getMcpServerByName</code>: Resolve each unique installed server through latest, named, and optional ID gallery endpoints; cardinality: Up to three sequential endpoint requests per unique server name; names run concurrently via Promise.all.     - Introduced by diff: false; previous behavior: The same endpoints, ordering, and Promise.all fan-out existed. The diff passes the already-resolved manifest into getMcpServer and adds local URL validation before each unchanged request.; critical-path effect: Blocks completion of background registry synchronization, not immediate UI progress.
- Verdict: No reportable regression. Added URL parsing is small local CPU work relative to unchanged network resolution, and redirect suppression can only reduce redirect-chain I/O.

- Verdict: No reportable regression. Unsupported package types are discarded before command construction; supported mappings do not add boundary work or repeated passes.
