# Performance review: agentHost: make the orchestrator own session enumeration and chat lifecycle

[PR #329633](https://github.com/microsoft/vscode/pull/329633) at `675bfbd56de910baf8efa75a42248a812a6f7ad7`

## Findings (2)

### 1. [high] Batch provider metadata reads for the session catalog

**Finding ID:** `PERF-D13A207294DF`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:1243</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Provider SDK/IPC requests and, for Codex, full transcript bytes returned by thread/read  
**Scaling:** Each catalog refresh now starts one metadata lookup for every registered session (N calls at unrestricted Promise.all concurrency); cold Codex lookups additionally scale with the total turns in those sessions because includeTurns is true.  
**Outcome:** Increased session-picker/startup latency and burst load on provider subprocesses/SDK connections  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The host enumerated sessions with one bulk provider list call per provider and did not issue a separate provider metadata RPC for every catalog entry.  
**Changed behavior:** listSessions now maps the complete registry through \_registeredSessionMetadata, which calls getChatMetadata separately for each session, and waits for all calls before returning the catalog.  
**Confidence:** 0.99 — The changed loop, all three provider boundary implementations, Codex payload, and the awaited UI refresh call path are explicit. Only the exact number of stored sessions and provider latency vary by user.

**Causal diff evidence:** RIGHT line 1243 introduces Promise.all(registered.map(...)); the added body at line 1256 invokes \_registeredSessionMetadata for each registered session instead of using the prior per-provider bulk enumeration.

Opening or refreshing the session list with a large history can send tens or hundreds of concurrent SDK/IPC requests before any results are published. Copilot calls getSessionMetadata once per row, Claude calls getSessionInfo once per row, and cold Codex rows issue thread/read with includeTurns:true, so catalog latency and subprocess pressure grow with both session count and Codex history size.

**Evidence:** The added Promise.all at agentService.ts:1243 calls \_registeredSessionMetadata for every registry row; that helper delegates to agent.getChatMetadata. CopilotAgent.getChatMetadata crosses the SDK through client.getSessionMetadata, ClaudeAgent.getChatMetadata calls \_sdkService.getSessionInfo, and CodexAgent.getChatMetadata falls through to \_readSession, whose thread/read request explicitly sets includeTurns:true. BaseAgentHostSessionsProvider.\_refreshSessions awaits connection.listSessions before updating its cache, placing the entire fan-out on the visible refresh path.

**Suggested direction:** Group registry entries by provider and join them against one bulk provider metadata snapshot per refresh, with targeted cached/bounded-concurrency fallbacks only for missing rows. Also make the Codex fallback request metadata without turns when the catalog does not need history.

### 2. [medium] Seed only the chat that was just added

**Finding ID:** `PERF-22B6F2AC1009`  
**Location:** <code>src/vs/platform/agentHost/node/agentSideEffects.ts:339</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Repeated plugin filesystem checks/copies plus provider-side plugin parsing and customization reconciliation  
**Scaling:** Adding the kth chat reassigns every active client to all k chats, so adding N chats performs C\*(1+...+N) handle updates and up to O(C\*P\*N²) plugin-sync work for C clients and P customizations.  
**Outcome:** Filesystem/CPU pressure and growing customization queues that delay chat readiness in sessions that create many peers or subagents  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this handler was added, a SessionChatAdded event did not reapply every active-client contribution to every already-existing provider handle; active-client setup was applied when the client contribution itself was set.  
**Changed behavior:** Every SessionChatAdded envelope now invokes \_fanOutActiveClient once per active client, and that helper loops the session's entire chat catalog and reassigns tools and customizations to old chats as well as the new one.  
**Confidence:** 0.99 — The nested active-client/chat loops and duplicate default-chat call are directly encoded and tested, and each provider setter's expensive synchronization path is explicit. Magnitude depends on chat, client, and plugin counts, which is reflected in medium severity rather than uncertainty about the mechanism.

**Causal diff evidence:** RIGHT line 339 adds a session-wide \_fanOutActiveClient call for every active client whenever one SessionChatAdded action arrives; the same diff's helper fans that call over the full chat collection.

In a live session that creates multiple peer chats or subagents, each addition re-synchronizes unchanged customizations for all earlier chats. The new test explicitly records the default chat being invoked a second time when one peer is added. Each customization assignment triggers Copilot SessionPluginController.sync or Claude/Codex plugin synchronization; cache hits still perform filesystem existence checks, while misses copy trees, and Codex reparses plugins and refreshes skill roots.

**Evidence:** agentSideEffects.ts:336-340 handles each SessionChatAdded by looping all active clients; \_fanOutActiveClient at lines 378-389 then loops all chats and assigns handle.customizations. agentSideEffects.test.ts:3047-3074 expects calls \[default, default, peer\], directly proving duplicate work. CopilotActiveClientHandle.customizations calls pluginController.sync, Claude routes the setter to AgentPluginManager.syncCustomizations, and Codex additionally parses synced plugins and runs \_refreshSkillExtraRoots/\_reconcileMaterializedCustomizations. AgentPluginManager performs an exists call even on a nonce-cache hit and recursive copy/cache writes on a miss.

**Suggested direction:** For SessionChatAdded, create/update each active-client handle only for action.summary.resource. Keep the full fan-out for SessionActiveClientSet, where a newly contributing client genuinely must seed every existing chat.

### Scenario 1: Cold startup and session-picker catalog refresh

- Effective concurrency: All N provider metadata calls are launched through an unrestricted Promise.all; Codex shares one app-server connection, while provider-specific internal limiters only cover narrower sub-work. The browser coalesces overlapping refreshes into one in-flight refresh but does not reduce the N calls inside it.
- Cache behavior: The registry is durable. Copilot still performs an SDK metadata request per row; Claude can skip when its SDK cannot load locally but otherwise performs per-row SDK reads; Codex serves live sessions from its in-memory map but cold startup misses issue thread/read. No refresh-level metadata snapshot coalesces the rows.
- Mechanism confidence: High: the added per-row Promise.all, each provider boundary, Codex full-history flag, and awaited cache refresh are explicit.
- Magnitude uncertainty: Exact N and provider response times vary, but long-lived users can realistically accumulate many sessions and cold Codex histories can be large.

### Scenario 2: Creating peer chats or spawning subagents while clients contribute plugins/tools

- Critical path: SessionChatAdded dispatch itself does not await provider synchronization, but it synchronously schedules a full client-by-chat fan-out. The resulting plugin jobs are on the path to customizations being available in the new chat and contend with later provider work.
- Scaling input: C active clients, k chats currently in the catalog, and P plugin customizations per client; over N additions the repeated assignments grow as C\*(1+...+N), with plugin work up to O(C\*P\*N^2).
- Effective concurrency: The outer client/chat loops schedule work immediately. AgentPluginManager runs different customizations in parallel but serializes repeated work per plugin URI; provider session sequencers further serialize some application, so duplicate jobs become queue backlog rather than being coalesced.
- Cache behavior: Nonce caching skips recursive copies only after a filesystem exists check. It does not coalesce repeated sync calls, and Codex still reparses cached plugin directories and refreshes skill roots.
- Mechanism confidence: High: the nested loops, duplicate default-chat invocation asserted by the new test, and provider setter-to-plugin-sync paths are all direct.
- Magnitude uncertainty: Sessions with one chat or no client plugins see little impact; sessions that create many peer/subagent chats with active extension clients amplify it rapidly.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentPluginManager.ts:syncCustomizations/\_syncPlugin</code>: Check cached plugin directories, copy plugin trees on misses, clean stale nonces, and persist cache metadata.; cardinality: Up to C\*k\*P sync attempts on the kth chat addition; cache hits avoid copies but retain at least one existence check per plugin.
    - Introduced by diff: true; previous behavior: A chat-added event did not reassign every active client's unchanged customizations to every pre-existing chat.; critical-path effect: Usually fire-and-forget from the catalog action, but serialized plugin queues delay customization settlement and consume shared I/O/CPU.
  - other at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_syncClientCustomizations</code>: Parse each synced plugin, rebuild process-wide skill roots, and reconcile materialized customization state.; cardinality: Repeated for every Codex handle assignment generated by the nested fan-out, even when plugin nonces are unchanged.
    - Introduced by diff: true; previous behavior: Existing chat handles were not resynchronized merely because another chat joined the catalog.; critical-path effect: Runs asynchronously but adds CPU and queue pressure before provider customization state settles.
- Verdict: Reportable medium-severity repeated work: only the added chat needs seeding, while the diff reprocesses every existing chat on each addition.

### Scenario 3: First-run registry migration and provider change backfill

- Critical path: The first list after upgrade waits for each provider's backfill before reading the registry. A successful sweep performs provider enumeration, filters internal backings, registers identities, and writes a durable completion marker.
- Scaling input: Number of providers and legacy sessions M returned by each provider.
- Effective concurrency: Providers backfill in parallel via Promise.allSettled; per-provider backing checks use Promise.all; registry registrations are deliberately sequential. Concurrent callers share one in-flight provider sweep, and forced notifications queue at most one immediate follow-up at a time.
- Cache behavior: Durable per-provider completion markers make the normal migration one-time; in-flight attempts are shared. Failed or unavailable enumerations remain unmarked and retry later; forced provider-change signals intentionally re-enumerate.
- Mechanism confidence: High for the one-time O(M) work and scheduling; there is no evidence that realistic one-time cost is severe enough to outweigh the required migration.
- Magnitude uncertainty: Migration duration depends on legacy history size and database latency, but it occurs once for a successful provider migration rather than on every steady-state refresh.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/agentService.ts:\_enumerateProviderSessions</code>: Bulk-enumerate legacy chats from each provider.; cardinality: One bulk call per provider per initial or forced sweep.
    - Introduced by diff: true; previous behavior: Provider bulk enumeration was the normal listing operation rather than a durable one-time migration.; critical-path effect: Initial list waits for the non-forced sweep; provider-triggered forced sweeps are separate refresh work.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_backfillProviderFromLegacyChats</code>: Check each candidate for a backing marker, register non-tombstoned identities, and mark the provider backfilled.; cardinality: M backing checks are concurrent, followed by up to M sequential registry writes and one marker write.
    - Introduced by diff: true; previous behavior: No registry migration writes were performed.; critical-path effect: The initial migration must finish before the first registry-backed list proceeds.
- Verdict: No finding: the extra work is bounded to migration/provider-change reconciliation, is coalesced per provider, and preserves existing sessions when adopting the registry.

### Scenario 4: Restoring a session and lazily opening peer chats

- Critical path: Restoring the top-level session materializes the default chat and its history. Peer chat summaries are registered from persisted catalog data without provider history; selecting or otherwise resolving one peer then awaits that chat's provider materialization and transcript read.
- Scaling input: Number of persisted peer chats and size of the one chat history being opened; turn-ID validation can inspect already-established unresolved peers according to the existing validation semantics.
- Effective concurrency: Summary title/draft reads are parallel. Each peer entry coalesces concurrent materialization through one in-flight promise; distinct requested peers may materialize concurrently.
- Cache behavior: Resolved ChatState remains in memory until session eviction. Summary metadata is persisted; provider backing/history is intentionally lazy and retried after failures.
- Mechanism confidence: High for lazy/coalesced behavior from registerRestoredChatSummary and resolveChatState.
- Magnitude uncertainty: Peer counts and transcript sizes vary, but ordinary restore does not eagerly fetch every peer provider history solely to render the catalog.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_restorePeerChats</code>: Read persisted peer catalog data, titles, drafts, and providerData.; cardinality: One catalog read plus title/draft reads per persisted peer summary.
    - Introduced by diff: true; previous behavior: The pre-diff session-centric model did not restore a host-owned peer-chat catalog.; critical-path effect: Summary restoration runs while reconstructing the session, but provider histories remain deferred.
  - IPC at <code>src/vs/platform/agentHost/node/agentService.ts:\_materializeRestoredPeerChat</code>: Materialize the selected provider chat and fetch/interleave its turn history.; cardinality: Once per peer chat actually resolved; concurrent requests for the same chat share state-manager entry.inFlight.
    - Introduced by diff: true; previous behavior: Peer chats were not independently host-owned/lazily materialized.; critical-path effect: Blocks opening/using that peer, not initial summary enumeration for every peer.
- Verdict: No additional finding: the new per-chat boundary is deferred until the peer is needed and coalesced per chat; no separate diff-introduced redundant call was proven.

### Scenario 5: Idle eviction and explicit deletion of a multi-chat session

- Critical path: Idle unsubscribe removes host cache immediately and releases provider chats asynchronously. Explicit deletion awaits provider chat disposal and durable registry/database cleanup before completing.
- Scaling input: Number of concrete chats K owned by the session.
- Effective concurrency: Provider chat teardown is intentionally sequential to preserve teardown order; independent idle releases are tracked per session. Subscriber and in-flight restore checks prevent unnecessary/racing release.
- Cache behavior: Eviction drops in-memory state but preserves durable metadata for restoration; deletion uses tombstones to prevent later backfill from reviving the entry. Release completion is tracked so restore waits for the same session's prior release.
- Mechanism confidence: High for K sequential calls and lifecycle placement; user-visible regression magnitude is low because the work is required to avoid retained provider runtimes and idle cleanup is asynchronous.
- Magnitude uncertainty: K can grow with peer/subagent use, but cleanup is infrequent and idle eviction does not block the user-facing unsubscribe path.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/agentService.ts:\_releaseSession/\_disposeSession</code>: Release or dispose each provider chat in teardown order.; cardinality: One provider lifecycle call per owned chat, sequentially, while still attempting later chats after an error.
    - Introduced by diff: true; previous behavior: The session-centric provider API issued one lifecycle call for the top-level session.; critical-path effect: Idle release is fire-and-forget and off the unsubscribe critical path; explicit destructive disposal is awaited.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:disposeSession and AgentSessionRegistry</code>: Tombstone/unregister the top-level identity and clean durable session/chat metadata.; cardinality: Bounded by the session and its K owned chats.
    - Introduced by diff: true; previous behavior: There was no host-owned catalog requiring per-chat provider cleanup.; critical-path effect: Awaited for explicit deletion, not normal browsing or sending.
- Verdict: No finding: per-chat cleanup scales with newly owned resources and prevents retention; the only common idle path is off the critical path.
