# Performance review: agentHost: centralize session and chat catalog metadata

## Findings (2)

### 1. [medium] Batch discovery recency writes instead of queueing one transaction per session

**Finding ID:** `PERF-CBD6F2A77FD7`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:2320</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SQLite statements and transactions on agent-host.db  
**Scaling:** For N sessions whose provider timestamp advanced in one discovery result, updateSessionModifiedTimes performs 2N awaited UPDATE calls, then this Promise.all queues N more dirty-marker transactions; the database transaction sequencer makes those N transactions execute serially.  
**Outcome:** Provider discovery and its post-processing take linearly more serialized database round trips, delaying refreshed session-list state and increasing SQLite I/O/CPU.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The pre-PR registry implementation assembled all modified-time updates into one SQL script and executed it in a single transaction, with no per-session central-catalog dirty transaction.  
**Changed behavior:** After the nominally batched registry update, the added line invokes \_markCatalogPayloadDirty once for every advanced session. Each invocation runs BEGIN, SELECT, INSERT/UPDATE, SELECT, and COMMIT through the same transaction sequencer; the new updateSessionModifiedTimes implementation also issues two awaited UPDATE calls per item.  
**Confidence:** 0.98 — The caller's N-sized discovery batch, both database implementations, and the central transaction sequencer are directly traced. Exact disk latency varies by catalog and platform, but the change from one transaction to N+1 transactions and 2N UPDATE callbacks is deterministic.

**Causal diff evidence:** Added line 2320 maps every entry in modifiedTimeAdvances to a separate \_markCatalogPayloadDirty call and awaits all of them; this per-session catalog work did not exist before the PR.

When discovery returns many existing sessions with newer timestamps, completion is blocked on roughly N serialized transactions plus 2N sequential UPDATE bridge calls instead of one bulk transaction. Large provider catalogs therefore make discovery and list invalidation noticeably slower.

**Evidence:** \_registerDiscoveredChats accumulates every advanced registration in modifiedTimeAdvances and awaits this Promise.all before scheduling reconciliation. AgentHostDatabase.markSessionV2PayloadDirty (1104-1122) uses \_transactionSequencer and a separate transaction with multiple SQLite calls, so Promise.all does not provide database concurrency. AgentHostDatabase.updateSessionModifiedTimes (553-568) loops and awaits two UPDATEs per input. The deleted implementation performed the whole update array through one generated SQL script/transaction.

**Suggested direction:** Add a bulk database operation that updates both registry tables and advances all affected payload-dirty markers in one sequenced transaction (using a batched statement/script or reused prepared statements), then schedule reconciliation once.

### 2. [medium] Do not revalidate every clean session database immediately after startup

**Finding ID:** `PERF-B25DB608FB39`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostCatalogReconciliationService.ts:557</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Per-session SQLite database opens, provider metadata reads, payload serialization/hashing, and central SQLite reads  
**Scaling:** Every process startup marks all verified catalog rows dirty; periodic passes then process up to 50 rows at a time with concurrency 4 until the catalog is drained. The same O(N) validation is reintroduced hourly, regardless of whether rows changed.  
**Outcome:** A healthy warm catalog generates avoidable background disk/provider work one second after startup and recurring I/O/CPU bursts, competing with interactive startup and active sessions.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no unconditional background service that opened and re-projected every registered session after process startup; per-session database reads occurred when listing/restoring required them.  
**Changed behavior:** The new service initializes \_initialPayloadDirtyMarkPending to true and this line marks all payloads dirty on its first pass. AgentService schedules that pass during construction with the default 1-second delay; each dirty row enters reconciliation, opens its session database, resolves provider metadata, rebuilds/hashes the payload, and queries the central database even when already synchronized.  
**Confidence:** 0.96 — Startup scheduling, delay, batch/concurrency limits, per-row open path, and tests counting database opens are explicit. The exact contention depends on profile size and provider cost, which is reflected in medium rather than high severity.

**Causal diff evidence:** Added line 557 unconditionally invokes \_markAllPayloadsDirty for the first reconciliation pass of every new service/process, turning all otherwise clean cached rows into work.

Profiles with dozens or hundreds of sessions incur up to 50 local database/provider validations shortly after every startup, followed by another batch every five minutes until complete; the hourly full sweep repeats this work for unchanged catalogs. This can cause startup-time disk contention and sustained background CPU/I/O.

**Evidence:** AgentService line 815 schedules reconciliation unconditionally. Defaults are 1 second, batch size 50, concurrency 4, five-minute passes, and hourly full verification. \_runSinglePass calls \_ensureInitialPayloadDirtyMark before selecting dirty rows, and \_reconcileSession opens the session database before checking hashes. The test 'opens and re-projects dirty rows once, then skips clean rows before session.db' records one database open on the first pass even for an already synchronized row, while the periodic-verification test records another open for the clean row after each safety sweep.

**Suggested direction:** Gate the full compatibility scan on an upgrade/persisted verification epoch and defer it until genuine idle, or keep a persisted rotating verification cursor that samples a bounded number of clean rows without marking the entire catalog dirty. Preserve event-driven dirtying for known writes.

Base blame resolves the old per-session path to the introducing commit.

### Scenario 2: Provider discovery advancing modified times for existing sessions

- Critical path: Discovery compares each provider result with its registration, accumulates every timestamp advance, awaits persistence of the entire batch, then awaits dirtying every affected catalog payload before invalidating/scheduling reconciliation and completing post-processing.
- Scaling input: N existing sessions in one provider discovery result whose modifiedTime advanced; effective cardinality is N after session-key deduplication in the discovery map.
- Effective concurrency: New-session discovery work uses an outer limiter, but modified-time updates execute sequentially inside one central transaction. The subsequent Promise.all submits N dirty markers, yet AgentHostDatabase's transaction sequencer serializes all N transactions.
- Cache behavior: Registration lookups avoid updates for unchanged timestamps. Every actual advance invalidates the session-list cache and dirties the catalog payload; dirty markers are not coalesced into one bulk database operation.
- Mechanism confidence: Very high: N is explicitly accumulated, all calls are awaited, and the shared transaction sequencer proves effective serialization.
- Magnitude uncertainty: The number of timestamps advancing in any one real discovery run is provider-dependent, but catalogs with many changes directly produce proportionally more serialized transactions.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostDatabase.ts:updateSessionModifiedTimes</code>: Execute two SQLite UPDATE statements for each advanced session, mirroring sessions\_v2 and legacy sessions.; cardinality: 2N awaited SQLite calls in one transaction.
    - Introduced by diff: true; previous behavior: The old registry generated one SQL script for the full update array and crossed the SQLite execution boundary once in one transaction.; critical-path effect: Fully blocks completion of the discovery batch.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:2320 -&gt; AgentHostDatabase.markSessionV2PayloadDirty</code>: For each advanced session, begin a transaction, check row existence, increment its dirty epoch, read the epoch, and commit.; cardinality: N serialized transactions, each with multiple SQLite operations.
    - Introduced by diff: true; previous behavior: No central payload dirty marker existed; all recency updates completed in the single legacy bulk transaction.; critical-path effect: The awaited Promise.all blocks discovery post-processing, but the database sequencer means the calls cannot run concurrently.
  - other expensive boundary at <code>src/vs/platform/agentHost/node/agentService.ts:\_registerDiscoveredChats</code>: Provider discovery returns session metadata used to construct the advance batch.; cardinality: One provider discovery result containing up to the provider's catalog size.
    - Introduced by diff: false; previous behavior: Provider discovery already supplied the same set of candidate sessions.; critical-path effect: Provider enumeration precedes the changed persistence fan-out.
- Verdict: Reportable medium boundary-fan-out regression: nominal batching now expands to 2N statements plus N serialized dirty-marker transactions.

- Effective concurrency: Per-session reconciliation is limited to four concurrent tasks. Batches are serialized by periodic scheduling, while central database writes are additionally serialized by AgentHostDatabase.
- Cache behavior: Even fully verified clean rows are invalidated at every service/process startup. Clean rows are skipped only after opening the local database, resolving source metadata, rebuilding/hashing the payload, and comparing receipts. The same all-dirty transition recurs hourly.
- Mechanism confidence: High: unconditional construction-time scheduling, one-second delay, all-dirty initialization, batch/concurrency settings, and database-open counts are explicit.
