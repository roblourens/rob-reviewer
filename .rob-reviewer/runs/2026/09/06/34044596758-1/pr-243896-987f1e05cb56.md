# Performance review: check for valid account and provide option to sign in

[PR #243896](https://github.com/microsoft/vscode/pull/243896) at `987f1e05cb56c661e491e3ca4abec28294e9e854`

## Findings (2)

### 1. [high] Release the account barrier on every initialization exit

**Finding ID:** `PERF-7D8680CC42FA`  
**Location:** <code>src/vs/workbench/services/extensionManagement/electron-sandbox/extensionGalleryManifestService.ts:89</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Pending manifest promises and downstream Marketplace IPC/network operations  
**Scaling:** A single account-initialization exit or entitlement failure leaves the one cached manifest promise pending for the entire window lifetime; every Marketplace query, install, update, and shared/remote-process consumer coalesces behind that same unresolved promise.  
**Outcome:** Unbounded Marketplace latency and permanently blocked extension operations for the affected window  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the change, a configured service URL was fetched directly and the default manifest was otherwise built immediately; manifest resolution had no dependency on account initialization completing.  
**Changed behavior:** When a configured gallery URL is present, manifest resolution now awaits the default-account barrier before it can select either the configured or fallback gallery.  
**Confidence:** 0.98 — The call path is explicit: this added await reaches DefaultAccountService.getDefaultAccount(), which waits only on initBarrier, while the new contribution returns without setDefaultAccount() when product configuration or the declared provider is absent and also fails to set it when the entitlement request rejects. The manifest promise is cached, so no later caller can recover. The prevalence of custom Marketplace policy is deployment-specific, but the indefinite wait once triggered is deterministic.

**Causal diff evidence:** RIGHT line 89 adds \`await this.defaultAccountService.getDefaultAccount()\` to the configured-gallery manifest path; no account barrier existed on this path before the PR.

With a configured Marketplace URL, an offline/failing entitlement endpoint, missing defaultAccount product entry, or unavailable declared authentication provider prevents the barrier from opening. Opening Extensions or any install/update/query then waits forever instead of falling back to the default gallery.

**Evidence:** The added condition at line 89 awaits defaultAccountService.getDefaultAccount(). That method waits on initBarrier, and only setDefaultAccount() opens it. DefaultAccountManagementContribution has early returns for missing product configuration and an undeclared provider, and its awaited entitlement request can reject before setDefaultAccount() executes. ExtensionGalleryService.query() awaits this manifest before issuing its Marketplace request, while the shared/remote IPC manifest service also waits on a barrier populated only after this promise resolves.

**Suggested direction:** Make account initialization settle the service on every terminal path: set the unavailable/null state before each early return and in a narrowly handled entitlement failure path (while logging or surfacing the error), or otherwise expose an initialization promise that always resolves. Then let manifest selection fall back to the default gallery instead of retaining a permanently pending promise.

### 2. [medium] Coalesce excluded policies into the initial policy update

**Finding ID:** `PERF-44FA7AF24474`  
**Location:** <code>src/vs/platform/configuration/common/configurations.ts:112</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** An extra IPC request plus native policy-watcher initialization or policy-file read  
**Scaling:** The cost is one additional serialized boundary operation per cold desktop window when this newly registered excluded policy is not already present in policiesData; warm windows with the definition already cached can skip it.  
**Outcome:** Increased cold-window startup latency on the configuration initialization critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** PolicyConfiguration.initialize() made one awaited updatePolicyDefinitions call for all initial configuration keys before workspace startup could continue.  
**Changed behavior:** Initialization now awaits the included-policy batch and then separately awaits a second excluded-policy batch, despite both key sets being available before either update.  
**Confidence:** 0.97 — The new excluded setting has a policy definition, so this added call is non-empty on a cold first window. PolicyChannelClient turns each new-definition batch into an awaited IPC call; NativePolicyService serializes it through a throttler and creates/replaces a native watcher, while FilePolicyService performs another file read. Workspace initialization explicitly awaits policy initialization before returning. Only the exact duration is platform-dependent.

**Causal diff evidence:** RIGHT line 112 adds a separate awaited \`updatePolicyDefinitions\` invocation for excluded properties; the PR also adds an excluded property with a policy, guaranteeing this batch contains a new definition on the cold path.

On the first window after launch, the new hidden Marketplace policy causes configuration startup to perform a second renderer-to-main IPC round-trip and reconstruct the OS policy watcher (or reread the policy file) before the workspace service and workbench can start.

**Evidence:** Line 112 adds a second sequential await. PolicyChannelClient.\_updatePolicyDefinitions calls the policy IPC channel; NativePolicyService.\_updatePolicyDefinitions imports the native module and queues createWatcher(), replacing its watcher, and FilePolicyService refreshes by reading the policy file. WorkspaceService.initialize() awaits initializeConfiguration(), which awaits this policy promise, and desktop startup awaits WorkspaceService.initialize() before creating the workbench.

**Suggested direction:** Concatenate the default-model keys and excluded-property keys and call updatePolicyDefinitions once, then update the configuration model from that single result so registration ordering and policy values are preserved without a second boundary crossing.
