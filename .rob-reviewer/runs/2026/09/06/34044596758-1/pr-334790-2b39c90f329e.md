## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/platform/configuration/common/configurations.ts:125` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/configuration/common/configurations.ts:124`  
**Introducing path:** `src/vs/platform/configuration/common/configurations.ts`  
**Introducing commit:** `567f6dee8a8f4caa2c5bd0b25eb2e1f87880a261`  
**Mechanism family:** `repeated-work`  
**Performance category:** `startup`  
**Confidence:** 0.99

**Mechanism:** Two sequential definition batches each changed the accumulated policy definitions, causing the backend to perform collection-wide policy initialization twice; native desktop recreated the policy watcher after the first batch and blocked startup on the second watcher creation.

**Symptom:** Configuration/policy initialization occupied the startup critical path and delayed main-process I/O callbacks; measured policy initialization improved by 12 ms after batching, with related callbacks improving by 8-10 ms.

**Fixed behavior:** The added array union at configurations.ts:125 submits regular and excluded configuration keys to one `updatePolicyDefinitions` call, so the abstract service performs one backend update and native watcher construction (or one file-policy refresh) instead of two sequential updates during configuration startup.

**Evidence:** Base `PolicyConfiguration.initialize()` invoked `updatePolicyDefinitions` once for default keys and awaited it before invoking it again for excluded keys. `AbstractPolicyService.updatePolicyDefinitions` calls `_updatePolicyDefinitions(this.policyDefinitions)` whenever each batch adds definitions; on Windows/macOS `NativePolicyService._updatePolicyDefinitions` dynamically imports `@vscode/policy-watcher`, queues creation, and replaces its `MutableDisposable<Watcher>`, while Linux `FilePolicyService` rereads and parses the policy file. This initialization is awaited by `ConfigurationService.initialize()` and the workbench/session initialization path. The PR's instrumented startup data reports that eliminating the second batch removes one watcher build and reduces the blocking policy initialization segment by 8-12 ms.

### Scenario 1: Desktop workbench / Agents Window configuration startup on Windows or macOS

- Critical path: \`WorkbenchConfigurationService.initializeConfiguration()\` awaits \`PolicyConfiguration.initialize()\` in the same \`Promise.all\` gate as user/application configuration, so policy initialization must finish before workspace configuration loading proceeds. The diff combines the two definition groups before this awaited operation.
- Scaling input: All registered default configuration keys plus excluded/internal configuration keys; policy names are deduplicated by a \`Set\`, and each resolved policy definition is submitted once in the combined batch.
- Effective concurrency: Before the diff, regular and excluded groups were explicitly serialized by two awaits. Each native watcher rebuild is additionally serialized by \`NativePolicyService\`'s \`Throttler\`. In the renderer, \`MultiplexPolicyService\` fans a single batch to the policy IPC client and account-policy service in parallel; the diff changes two sequential multiplex batches into one.
- Cache behavior: \`PolicyConfiguration.\_submittedPolicyDefinitions\` structurally suppresses resubmission within an instance, and \`AbstractPolicyService\` suppresses identical object identities. The native module import is warm after first load, but watcher creation was not reused across changed batches. Combining works for cold startup and prevents the redundant warm watcher recreation.
- Mechanism confidence: High: the two old awaits, abstract changed-batch dispatch, IPC path, watcher replacement, throttler serialization, and startup await are directly traced.
- Magnitude uncertainty: Exact policy counts and native watcher latency vary by product build, platform, and profile; the supplied startup measurements establish an 8-12 ms blocking-segment improvement but end-to-end variance remains larger.

### Scenario 2: CLI/main-process configuration initialization and Linux/file-policy startup

- Critical path: \`ConfigurationService.initialize()\` awaits policy initialization alongside default and user configuration; \`cliProcessMain\` awaits that entire initialization before continuing. Main-process desktop startup uses the same configuration service. The changed call is therefore on startup's completion path.
- Scaling input: Number of registered configuration keys and policy definitions; processing remains O(regular + excluded), while whole-file reads/watcher builds decrease from two to one.
- Effective concurrency: The two old policy updates were sequential. File reads inside each \`FilePolicyService.refresh()\` were consequently serialized; after the diff there is one refresh for the union. Other state/user configuration work can run concurrently via the surrounding \`Promise.all\`.
- Cache behavior: A warm filesystem/page cache can make the second old file read cheaper, but \`FilePolicyService\` has no parsed-content initialization cache. Native import caching avoids repeated module loading after the first call but does not avoid watcher replacement. Definition maps suppress later unchanged updates.
- Mechanism confidence: High: the CLI await, configuration \`Promise.all\`, abstract update dispatch, and file/native backend implementations directly establish the boundary path.
- Magnitude uncertainty: Filesystem and watcher costs are platform- and cache-dependent; the cardinality reduction is deterministic.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/policy/common/filePolicyService.ts:48 \`FilePolicyService.read\`</code>: Reads and JSON-parses the configured system policy file.; cardinality: One read for the combined changed-definition batch instead of up to two sequential reads during initialization.
    - Introduced by diff: false; previous behavior: Each of the two changed definition groups triggered a full file read/parse; the diff coalesces them.; critical-path effect: \`FilePolicyService.\_updatePolicyDefinitions\` awaits \`refresh\`, and configuration startup awaits policy initialization.
  - other expensive boundary at <code>src/vs/platform/policy/node/nativePolicyService.ts:25 \`NativePolicyService.\_updatePolicyDefinitions\`</code>: Creates the OS-native policy watcher for CLI or main-process configuration on Windows/macOS.; cardinality: One creation for the union instead of two sequential creations when both groups add definitions.
    - Introduced by diff: false; previous behavior: The watcher was rebuilt after each group.; critical-path effect: Awaited before CLI configuration initialization completes.
- Verdict: No regression. Batching removes one whole-backend initialization and adds only a transient union array proportional to keys already scanned by the old two calls.

### Scenario 3: Sessions / Agents Window configuration initialization

- Critical path: \`sessions\` configuration initialization awaits \`PolicyConfiguration.initialize()\` in a \`Promise.all\` with user and workspace configuration before constructing the effective configuration model.
- Scaling input: Union of policy-bearing regular and excluded settings registered for the sessions product; policy names are deduplicated before submission.
- Effective concurrency: User/workspace operations remain parallel with policy initialization. Within policy initialization, two sequential definition submissions become one; desktop multiplex backends remain parallel within that one submission.
- Cache behavior: Initial definitions are cold for the local \`PolicyConfiguration\`; downstream services retain definition maps and suppress unchanged later submissions. The diff improves both cold initialization and any fresh sessions window instance without changing invalidation behavior.
- Mechanism confidence: High for the startup and IPC call path; medium for whether every backend receives both old batches because that depends on registered policy content.
- Magnitude uncertainty: The number of sessions-window launches and presence of excluded managed policies vary, so some launches may previously have produced only one effective backend update.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/policy/common/policyIpc.ts:74 and src/vs/platform/policy/common/nativeManagedSettingsIpc.ts:94</code>: Updates main-process policy and eligible managed-settings definitions from the sessions renderer.; cardinality: Up to one call per backend for the combined initialization batch instead of calls from two sequential batches; backend-specific guards may reduce the count further.
    - Introduced by diff: false; previous behavior: Included and excluded definitions traversed the renderer-to-main boundary separately.; critical-path effect: The policy branch must resolve before sessions configuration initialization completes, although user/workspace work proceeds concurrently.
- Verdict: No reportable regression. The combined batch cannot increase downstream update count and bounds initialization to one submission.

**Summary:** Reviewed the complete two-file diff and the production call graph across startup, IPC, native watcher, managed-settings, and file-policy backends. No performance regression was introduced. The change is a concrete repeated-work fix: it coalesces two sequential initialization batches into one, and the introducing commit was recorded via base blame.
