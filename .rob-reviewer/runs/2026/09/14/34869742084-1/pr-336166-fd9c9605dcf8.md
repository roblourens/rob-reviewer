- Scaling input: The fixed PR matrix currently has four Electron-consuming jobs per OS, so cache restores and setup execute 12 times per PR; retries scale only with failed attempts.
- Effective concurrency: The 12 reusable workflow jobs can run independently in parallel; within each job, cache restore and npm preparation are serialized. The diff does not add an aggregate limiter, but it replaces the prior parallel Releases ZIP downloads with cache restores on warm keys.
- Cache behavior: The exact key includes runner OS, target architecture, .npmrc, and the Electron checksum file. Main populates the cache; PRs restore without saving. Warm hits restore the original archive and still validate/prepare Electron. Cold misses perform the previous direct download after the added lookup. There are no fallback keys or negative-cache retention.
- Mechanism confidence: High: the workflow callers, conditions, cache action, retry loop, and downloader/preparation implementation are directly traced.
- Magnitude uncertainty: Exact archive size and cache-service versus Releases throughput are not recorded in the repository; cold-cache lookup latency is also unmeasured.

### Scenario 2: Main-branch Linux, macOS, and Windows dependency-cache warming jobs

- Critical path: Each platform job now checks the Electron cache before deciding whether node\_modules only needs a lookup. On an Electron miss, dependency restoration/installation, Electron setup, and cache save must finish before that warming job completes; on a hit, only lookup operations remain.
- Scaling input: A fixed three-platform matrix per main push. Heavy work occurs once per OS for each new exact key, normally when Electron configuration/checksums change; warm ordinary pushes perform three lookup-only queries.
- Effective concurrency: Linux, macOS, and Windows warming jobs run independently and may perform up to three cold downloads/uploads concurrently; each job serializes dependency availability, Electron setup, and save.
- Cache behavior: An exact OS/architecture/configuration key gates all heavy work. Warm hits retain the old node\_modules lookup-only fast path and skip Electron setup/save. Cold misses restore or install node\_modules, recheck the Electron key, download/validate/prepare Electron, and save the archive. No fallback or negative cache is used.
- Mechanism confidence: High: changed conditions and all transitive cache, subprocess, filesystem, and download boundaries are explicit.
- Magnitude uncertainty: Repository evidence does not quantify archive size, node\_modules extraction time, or main-push frequency between Electron key changes.
- Expensive boundaries:
