## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `build/next/index.ts:121` (`LEFT`)  
**Blamed base line:** `build/next/index.ts:121`  
**Introducing path:** `build/esbuild.ts`  
**Introducing commit:** `b08e9e5e4b63bb8c24d4f2e914884377104c0527`  
**Mechanism family:** `repeated-work`  
**Performance category:** `throughput`  
**Confidence:** 0.96

**Mechanism:** A duplicate top-level server-web entry caused the same large web workbench dependency graph and CSS graph to be bundled twice, retained in memory until post-processing, written to disk, and copied into every server-web artifact even though only the shell entry is loaded.

**Symptom:** Every server-web core build performed redundant CPU/allocation and filesystem work and produced a larger packaged artifact containing an unused workbench JS/CSS pair.

**Fixed behavior:** The server-web target now emits only the browser-shell entry, allowing that one bundle to include the statically imported web workbench and eliminating one complete workbench esbuild invocation plus its redundant packaged JS/CSS outputs; standalone web retains the direct internal entry.

**Evidence:** The base server-web target included both `vs/workbench/workbench.web.main.internal` and `vs/code/browser/workbench/workbench` as independent esbuild entries. The latter statically imports the former (`src/vs/code/browser/workbench/workbench.ts:24`), while `bundle()` starts one complete esbuild build per entry with `Promise.all` and retains each output before packaging. `core-ci` invokes the server-web bundle in production pipelines, and `packageTask` copies every generated file, but the server-web HTML loads only `vs/code/browser/workbench/workbench.js`. Thus each server-web core build rebuilt and packaged an otherwise unreferenced second full workbench JS/CSS pair.

### Scenario 2: Production/PR \`core-ci\` generation of the server-web core output

- Effective concurrency: One child process per target at the outer level; all entries within server-web are launched concurrently without a limiter. This PR reduces the server-web set from 17 to 16 by deleting the redundant direct workbench entry.

- Mechanism confidence: Very high: the shell statically imports the removed entry, bundle() invokes esbuild separately for each listed entry, and production pipelines invoke \`core-ci\`.
