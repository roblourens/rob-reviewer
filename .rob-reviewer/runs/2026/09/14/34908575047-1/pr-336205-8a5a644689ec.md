- Scaling input: One transport request per tool invocation; concurrent calls are determined by the existing chat/tool orchestration, and this diff adds no fan-out or concurrency.
- Effective concurrency: Existing calls may run concurrently across tool invocations; server startup remains sequenced/idempotent and the diff adds no queue, limiter, or parallel work.
- Cache behavior: On a cold server, callOn may start the MCP transport and initialize the handler; on a warm running server, start is idempotent. The diff does not alter tool caching, startup, or refresh behavior.
- Mechanism confidence: High: the production diff executes only inside the existing catch block after callTool fails.
- Magnitude uncertainty: Transport and server latency vary by MCP implementation, but no changed work is present on the successful path.
- Expensive boundaries:
  - subprocess/network at <code>src/vs/workbench/contrib/mcp/common/mcpServer.ts:McpServer.callOn</code>: Start or connect the MCP server transport when it is not already running.; cardinality: At most one cold start for the server lifecycle; warm invocations reuse the running connection.

- Verdict: No performance regression: successful invocation cost, cache behavior, boundary count, and concurrency are unchanged.

- Critical path: The pending tools/call request is cancelled by McpServerRequestHandler when the connection becomes terminal. - Scaling input: Cost scales once per failed tool invocation. Effective transport cardinality remains one request normally or two requests under the pre-existing single retry.
- Effective concurrency: No new automatic concurrency is introduced. Each failed invocation independently classifies its own error after the transport settles; aggregate concurrency remains controlled by existing callers.
- Cache behavior: No cache participates in failure classification. Cold and warm server states retain their existing start/reuse behavior, and no failure keys or objects are retained.
- Mechanism confidence: High for the bounded local classification and unchanged MCP request count; downstream model continuation is possible but caller-controlled.
- Magnitude uncertainty: Whether an agent makes another model request after receiving the error depends on the caller/model, but there is no code evidence of unbounded retries or changed concurrency.
- Expensive boundaries:
  - IPC/network at <code>src/vs/workbench/contrib/mcp/common/mcpServer.ts:McpTool.\_callWithProgress and src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts</code>: Send tools/call and receive connection termination/cancellation.; cardinality: One transport request per failed invocation, or two only when the existing Error.shouldRetry path is enabled.
    - Introduced by diff: false; previous behavior: Before the diff, the same request and optional one retry occurred, then CancellationError propagated.; critical-path effect: Connection failure settles the pending request; the added classification runs afterward and does not block on another boundary.
  - network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts client-tool error handling</code>: A higher-level agent may continue its normal model loop after receiving an ordinary tool error instead of treating it as user cancellation.; cardinality: Potential subsequent model work is determined by existing agent orchestration and model decisions; this diff adds no automatic retry or loop.

- Verdict: No reportable regression: the added work is one state read, checks, localization, and one error allocation per failed call. Normal agent continuation is the intentional functional correction, with no new automatic retries or fan-out.

- Scaling input: Constant work per cancelled invocation; no collection or history growth.
- Effective concurrency: Cancellation remains per invocation, and existing request/disposable cleanup runs in finally. No new asynchronous work is scheduled.
- Cache behavior: No cache reads, writes, keys, or negative entries are involved.
- Mechanism confidence: High: token/state guards and finally disposal are explicit in the traced code.
- Magnitude uncertainty: None material; all changed operations are bounded scalar checks.
- Expensive boundaries:
  - IPC/network at <code>src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts and src/vs/workbench/contrib/mcp/common/mcpServer.ts:McpTool.\_callWithProgress</code>: The already-issued MCP tools/call is cancelled or receives a server cancellation notification.; cardinality: One cancellation for the affected request.
    - Introduced by diff: false; previous behavior: The same request cancellation propagated as CancellationError.; critical-path effect: Cancellation settles the request immediately; the changed branch performs only local checks before rethrowing.
- Verdict: No performance regression: cancellation timing, boundary cardinality, and cleanup lifecycle remain unchanged.
