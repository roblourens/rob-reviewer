## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/editor/browser/viewParts/whitespace/whitespace.ts:234` (`RIGHT`)  
**Blamed base line:** `src/vs/editor/browser/viewParts/whitespace/whitespace.ts:219`  
**Introducing path:** `src/vs/editor/browser/viewParts/whitespace/whitespace.ts`  
**Introducing commit:** `2c8d5bdc55861f28e2fbbec599ff1eee54f0f2f7`  
**Mechanism family:** `repeated-work`  
**Performance category:** `rendering`  
**Confidence:** 0.99

**Mechanism:** The default SVG whitespace renderer created one SVG child element for every visible space or tab. Overlay line replacement on scrolling and selection-related rendering repeatedly constructed and destroyed a DOM subtree whose node count scaled with visible whitespace glyphs rather than visible lines.

**Symptom:** Editors with renderWhitespace enabled and whitespace-dense visible lines incurred excessive synchronous DOM/style recalculation during scrolling and drag selection, causing increased renderer task time and frame delays.

**Fixed behavior:** The added wrapper at whitespace.ts:234 emits the accumulated glyph geometry as a single SVG path per line, while \_renderCircle and \_renderArrow now return closed path-data subpaths. Rendering still scans and serializes each visible marker, but DOM element creation, attachment, style matching, and teardown shrink from one shape per whitespace glyph to at most one shape per rendered line.

**Evidence:** In the base revision, whitespace.ts:219 appends a separate &lt;circle&gt; for each visible space, while \_renderArrow returns a separate &lt;path&gt; for each visible tab. \_applyRenderWhitespace iterates every whitespace character of every visible line (bounded by stopRenderingLineAfter, whose default is 10,000), and SVG is the default experimentalWhitespaceRendering mode. ViewOverlays.prepareRender runs the overlay on invalidation, ViewOverlayLine concatenates its markup with the other overlays, and viewLayer applies changed line HTML through innerHTML, making all of those glyph nodes synchronous DOM/style work during visible-line rendering. The PR body provides controlled editor measurements showing 778 glyph elements before versus 49 per-line paths after and corresponding reductions in selection and scrolling style-recalculation time.
