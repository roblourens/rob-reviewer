### 1. [low] Keep component-explorer animations out of the production stylesheet

**Finding ID:** `PERF-79D4C155A040`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/media/chatWorkingLogo.css:102</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Production CSS bytes, parsed selectors/keyframes, and stylesheet memory  
**Scaling:** This fixed cost is paid whenever the Chat renderer stylesheet is loaded, for every window/session, regardless of whether persistent progress is enabled; roughly twenty unused motion families account for most of the new 612-line stylesheet.  
**Outcome:** Increased Chat/workbench load and stylesheet parsing cost plus retained style data for animations users cannot select.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The production bundle had no chat-working-logo stylesheet or prototype motion definitions.  
**Changed behavior:** The new production stylesheet includes Weave V and roughly twenty other explored animation families, while production configuration exposes only Weave, Orbit, Accordion, and Dial. Repository references show the extra \`ChatWorkingLogoMotion\` values are used only by the component fixture and tests, yet \`chatWorkingLogo.ts\` statically imports this entire CSS file.  
**Confidence:** 0.97 — The reachable production enum and repository-wide references establish that these animation definitions are fixture-only, and the static production CSS import establishes the eager load. The exact startup milliseconds are uncertain, hence low severity.

**Causal diff evidence:** RIGHT line 102 starts an added animation family that is unreachable from production configuration but is nevertheless included in the newly imported production stylesheet.

Users load and parse most of a ~24 KB stylesheet even when the opt-in feature is disabled, and those extra keyframes can never be reached through product settings.

**Evidence:** The first non-product family begins at line 102 (\`weave-v\`) and the file continues through 612 lines with fold, relay, stack, shutter, aperture, magnet, trace, pendulum, prism, ladder, carousel, piston, bridge, fan, comb, braid, sling, folio, and helix. \`ChatProgressAnimation\` exposes only off/weave/orbit/accordion/dial, while repository search finds the remaining motions only in \`chatWorkingLogo.fixture.ts\` and tests. \`chatWorkingLogo.ts:13\` imports the CSS from production code.

**Suggested direction:** Move exploratory motion classes/keyframes and their duration/type entries into component-fixture-only files; keep the production module and stylesheet limited to the four selectable animations.

### 2. [low] Stop repainting the progress text for the entire response

**Finding ID:** `PERF-D2F52F82753F`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatProgressContentPart.ts:383</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Continuous CSS background-position painting for the persistent progress label  
**Scaling:** The paint work runs continuously for the full lifetime of every enabled in-progress response, including long tool runs and indefinitely blocked question, confirmation, plan-review, and authentication states; it also multiplies across concurrently visible chat windows.  
**Outcome:** Sustained renderer CPU/GPU usage and battery drain, with avoidable frame contention during long responses.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this feature, a footer shimmer was conditional and absent while normal markdown streamed or specialized tool/interaction UI owned progress; there was no response-lifetime text animation.  
**Changed behavior:** This argument forces \`useShimmer\` on for every persistent working part. The existing \`.shimmer-progress\` rule animates \`background-position\` every two seconds forever, and all persistent states are emitted with \`isActive: true\`, even when waiting for user input. The separate progress-animation setting only makes the logo static and does not stop this text animation.  
**Confidence:** 0.93 — The call path from the added argument to the infinite background-position animation is explicit, and every persistent state is explicitly active. Exact device-level cost is hardware-dependent, so severity is low, but the continuous paint mechanism and response-lifetime trigger are deterministic.

**Causal diff evidence:** RIGHT line 383 newly passes \`isActive\` as the shimmer flag for every persistent working row; the PR also newly creates that row throughout the response rather than only at legacy progress pauses.

With \`chat.experimental.persistentProgress.enabled\` on (even with its default animation value \`off\`), every response continuously repaints the progress label until completion. Long-running agents or prompts left awaiting input therefore keep the renderer doing frame work while otherwise idle.

**Evidence:** The added constructor argument at line 383 makes persistent progress shimmer whenever \`isActive\` is true. \`getPersistentWorkingProgress\` sets \`isActive: true\` for active, question, confirmation, plan review, and authentication states (chatListRenderer.ts:1985-2009). \`chat.css:3465-3478\` applies \`animation: chat-thinking-shimmer 2s linear infinite\` and \`will-change: background-position\`; its keyframes at chat.css:192-199 mutate background-position, a paint-triggering property. Reduced motion is the only rule that disables it.

**Suggested direction:** Keep the persistent label but avoid a response-lifetime background-position animation: make the text static while output is streaming or the response is user-blocked, or implement the shimmer with a bounded/compositor-friendly transform and stop it after a short cycle.
