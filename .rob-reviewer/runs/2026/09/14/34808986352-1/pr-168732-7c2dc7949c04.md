## Findings (2)

### 1. [medium] Cache whitespace output across vertical scroll frames

**Finding ID:** `PERF-880BB7A1900E`  
**Location:** <code>src/vs/editor/browser/viewParts/whitespace/whitespace.ts:83</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and transient strings/Position/range objects  
**Scaling:** On each scrollTop event, cost grows with every character and rendered whitespace across the entire visible viewport, rather than only with lines entering the viewport.  
**Outcome:** Increased per-frame CPU/GC pressure and dropped frames during wheel or smooth scrolling.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Whitespace was serialized inside ViewLine. During overlapping vertical scrolls, ViewLayerRenderer laid out reused lines and rendered whitespace only for newly entering or otherwise invalid lines, so stable visible lines did not rebuild their whitespace markup.  
**Changed behavior:** The new overlay marks itself dirty for every vertical scroll; prepareRender then refetches all visible line data, scans each visible line, resolves each qualifying whitespace position, and rebuilds every line's SVG/font string before unchanged strings are compared.  
**Confidence:** 0.99 — The event-to-render path and full viewport loops are explicit, and the existing visible-line renderer proves prior reuse. Exact frame-time impact varies with viewport width, line length, and whitespace mode, so severity is medium rather than high.

**Causal diff evidence:** Added line 83 (\`return e.scrollTopChanged\`) newly invalidates WhitespaceOverlay on every vertical scroll, placing its full-viewport preparation loop on the scroll-frame path.

With renderWhitespace set to all/boundary/trailing (or a large selection), scrolling a viewport containing many long or whitespace-heavy lines repeats O(visible characters + visible whitespace) work every frame and can make scrolling visibly janky.

**Evidence:** The added onScrollChanged returns true for any scrollTop change. prepareRender consequently loops viewportData.startLineNumber..endLineNumber (lines 99-131), and \_applyRenderWhitespace scans each line and concatenates markup per whitespace (lines 176-233). ViewOverlayLine's later \_renderedContent equality check only avoids DOM replacement; it does not avoid this preparation. In contrast, ViewLayerRenderer.\_renderUntouchedLines only calls layoutLine on overlapping ViewLines and creates/renders lines entering the viewport.

**Suggested direction:** Retain whitespace results per view line/content/options and recompute only entering or invalidated lines; pure scrollTop changes should reuse cached output while the visible-line layer updates positions.

### 2. [medium] Batch whitespace position measurements per line

**Finding ID:** `PERF-85238F412650`  
**Location:** <code>src/vs/editor/browser/viewParts/whitespace/whitespace.ts:214</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous DOM geometry reads (\`getBoundingClientRect\`, \`offsetWidth\`, and Range.getClientRects\`) plus one position/range allocation chain per whitespace  
**Scaling:** Cold measurement cost grows linearly with qualifying whitespace in newly rendered or invalidated non-fast visible lines; long, proportional-font, Unicode/RTL, or decorated lines can require tens or hundreds of DOM range reads apiece.  
**Outcome:** Blocked editor render/input latency and potential typing or scrolling jank from synchronous layout/geometry work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The stable ViewLine renderer emitted whitespace glyphs while serializing the line and computed offsets from its character/visible-column state; it did not perform a DOM geometry query for each whitespace glyph.  
**Changed behavior:** For every whitespace selected for rendering, the overlay asks ViewLines for a visible range after text lines have been written to the DOM.  
**Confidence:** 0.98 — The changed loop and repository call chain directly prove per-whitespace geometry reads on non-fast cache misses. Magnitude depends on how often affected line shapes and whitespace modes occur, which is reflected in medium severity.

**Causal diff evidence:** Added line 214 introduces one \`visibleRangeForPosition\` call for each qualifying whitespace; before this PR whitespace rendering stayed inside renderViewLine and had no per-glyph DOM measurement boundary.

Opening, scrolling in, or editing a non-fast line with many spaces/tabs causes the render critical path to synchronously measure each whitespace. Because overlay preparation runs immediately after ViewLines.renderText, the first geometry read can also force pending layout before the frame can complete.

**Evidence:** The added call at line 214 runs inside the per-character loop. RenderingContext delegates it to ViewLines.visibleRangeForPosition, which creates a new DomReadingContext for each call. For RenderedViewLine cache misses, \_actualReadPixelOffset calls RangeUtil.readHorizontalRanges; that invokes Range.getClientRects, while each fresh context reads the view's getBoundingClientRect and offsetWidth. FastRenderedViewLine avoids DOM reads, but realistic non-fast cases include lines &gt;=300 characters, non-basic/RTL text, proportional fonts, and foreign inline elements.

**Suggested direction:** Resolve whitespace coordinates in one per-line batch using a shared DOM-reading context, or expose/reuse the rendered line's character mapping and font metrics; avoid invoking the single-position DOM API once per glyph.
