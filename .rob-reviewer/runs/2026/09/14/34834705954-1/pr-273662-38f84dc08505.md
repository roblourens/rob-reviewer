## Findings (3)

### 1. [medium] Prune baselines when truncating a branch

**Finding ID:** `PERF-A7EA39A3C502`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts:240</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Full text contents and serialized notebook snapshots retained in \`\_fileBaselines\`, plus the same bytes embedded in persisted timeline JSON  
**Scaling:** Each undo-then-new-request branch can retain another full baseline per edited file; retained memory and saved \`state.json\` bytes grow with the sum of file sizes across abandoned requests rather than the reachable timeline.  
**Outcome:** Retained memory, larger JSON serialization/allocation, and increasing save/shutdown filesystem I/O  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The deleted \`pushSnapshot\` branch logic rebuilt \`newLinearHistory\` only through the current pointer, so snapshots from the abandoned future branch became unreachable and were not persisted.  
**Changed behavior:** The new branch path truncates \`\_operations\` and filters \`\_checkpoints\`, but leaves every baseline in \`\_fileBaselines\`; \`getStateForPersistence\` later returns the entire map.  
**Confidence:** 0.99 — The branch truncation path, full-content baseline ownership, absence of any deletion path, and unconditional persistence of the map are all directly traced. Only the exact file sizes and number of user branches vary.

**Causal diff evidence:** Added RIGHT line 240 explicitly drops future operations on branching, and the adjacent added branch-truncation block drops future checkpoints without deleting their request/file baselines; this creates stale retained state that the previous history truncation released.

A user who repeatedly undoes an agent request and sends an alternative request against large files accumulates unreachable full-file baselines for the lifetime of the chat session, and every state save writes those stale contents into \`state.json\`.

**Evidence:** \`recordFileOperation\` truncates operations at line 240 and checkpoints immediately afterward, while repository-wide uses of \`\_fileBaselines\` show insertion, lookup, persistence, and restore only—no branch cleanup. Each \`IFileBaseline.content\` is a full text or serialized notebook snapshot, and \`ChatEditingSessionStorage.storeState\` assigns \`timeline\` directly before \`JSON.stringify(data)\`.

**Suggested direction:** When truncating a branch, remove baselines that are no longer reachable from the surviving operations/checkpoints, while preserving the newly recorded request baseline, and persist only that pruned set.

### 2. [medium] Replay text edits in one temporary model

**Finding ID:** `PERF-7C19648CB5E7`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts:650</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Temporary TextModel instances, full-file text buffers/strings, and CPU work to rebuild them  
**Scaling:** For N recorded edit batches to an S-byte file, replay constructs and disposes N text models and materializes a full string after every batch, making reconstruction roughly O(N × S) allocation/work instead of applying N batches to one model and reading once.  
**Outcome:** Increased undo/redo and historical-diff latency with heavy CPU and GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Undo restored the selected snapshot's already-materialized content once per file; it did not recreate a full text model for every streamed edit batch during the undo action.  
**Changed behavior:** The operation-log replay loop invokes \`\_applyTextEditsToContent\` for each \`TextEdit\` operation, and this added line constructs a fresh TextModel from the entire intermediate content each time.  
**Confidence:** 0.98 — The undo/redo call path and one-model-per-operation loop are explicit, and streamed response updates demonstrably create separate operations. Only the typical batch count and file size affect severity.

**Causal diff evidence:** Added RIGHT line 650 creates the per-operation temporary TextModel inside \`\_applyTextEditsToContent\`, which is called from the newly added replay loop once for every recorded text operation.

Undoing or opening a historical diff after an agent produced many incremental edits in a large file can synchronously allocate and rebuild that file dozens or hundreds of times before the action completes.

**Evidence:** Each response update is recorded as a separate \`TextEdit\` operation in \`ChatEditingSession.\_recordEditOperations\`. \`\_navigateToEpoch\` awaits reconstruction on undo/redo; \`\_replayOperations\` loops those operations, and every text operation reaches lines 647-669, creating a TextModel, applying one batch, calling \`getValue\`, and disposing it.

**Suggested direction:** Create one temporary model per text-file replay, apply all chronological text-operation batches to it (resetting only across create/delete boundaries), then materialize the final string once.

### 3. [medium] Avoid replaying every pill for each streamed operation

**Finding ID:** `PERF-06050A2CBEC9`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts:320</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Main-thread operation-log scans, temporary text models/full strings, model updates, and editor-worker diff IPC/CPU  
**Scaling:** Each visible collapsed code-block model subscribes to the global operation list. After each 500 ms quiet interval, every subscriber replays its file's growing operation prefix; for B spaced edit batches this can sum to O(B² × file size), multiplied by visible pills, even when an operation belongs to another URI.  
**Outcome:** Sustained CPU/GC and editor-worker load during agent streaming, causing slower edit application and UI responsiveness on large or multi-file responses  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The old timeline updated a stop snapshot when a streaming edit group resolved and diffed those stable snapshots; it did not rebuild a live end-state model from every recorded edit batch.  
**Changed behavior:** Every operation now invalidates a global listener per dynamic snapshot; each listener calls \`getContentAtStop\`, updates its model, and the model change launches another advanced worker diff.  
**Confidence:** 0.96 — The operation-per-stream-update call path, global listener fan-out, replay, model-change signal, and worker diff are explicit. Debouncing reduces frequency for tightly packed batches, so exact magnitude depends on stream cadence and visible pill count, not on the mechanism.

**Causal diff evidence:** Added RIGHT line 320 newly connects every operation-list mutation to every live snapshot model; this moves reconstruction and worker diffing onto the streaming path and increases both frequency and cross-file fan-out versus completion-only snapshots.

While an agent streams edits into large files—especially several files with visible collapsed pills—ordinary edit batches can repeatedly reconstruct full contents and run up-to-3-second diffs before the response is complete.

**Evidence:** \`\_acceptEdits\` records one operation for each newly streamed edit batch. Added line 320 listens to the unfiltered global \`\_operations\`; line 326 calls \`getContentAtStop\`, which scans/filter-sorts the log and replays all matching operations. \`getSnapshotModel\` then calls \`model.setValue\`, and \`\_getEntryDiffBetweenEpochs\` observes that change and invokes \`computeDiff(... maxComputationTimeMs: 3000)\`. \`ThrottledDelayer\` serializes per pill but does not coalesce across pills.

**Suggested direction:** Filter updates by affected URI and avoid recomputing the full diff until the edit group/checkpoint is final; if live counts are required, maintain an incrementally updated per-file reconstruction and coalesce/cancel worker diffs across pills.

### Scenario 1: Agent streams text or notebook edits while collapsed code-block pills are rendered

- Critical path: Per-resource edit application is sequenced and remains the direct streaming critical path. The new snapshot refresh runs after a 500 ms debounce, but reconstructs models on the UI side and then consumes the shared editor worker, so it competes with continued editing even when not directly awaited by \`pushText\`.
- Scaling input: Effective cardinality is the number of newly observed edit batches B, matching operations in the file/history, and visible pills V. Rapid updates coalesce per pill, but spaced updates replay a growing prefix; every pill listens to the global operation list, including operations for other files.
- Effective concurrency: Edits are serialized per resource by \`SequencerByKey\` and throttled to at least 15 ms. Each pill has its own \`ThrottledDelayer\`, which prevents overlap for that pill, but there is no URI filtering or shared limiter across pills; worker diff requests can queue across V pills.
- Cache behavior: Text model references are reused for a snapshot URI while alive, but reconstructed content has no per-file/per-epoch cache. Each invalidation scans and replays the log from the baseline, and diff observables/results are not shared across pills.
- Mechanism confidence: High: operation recording, global invalidation, full replay, model update, and worker diff are directly traced.
- Magnitude uncertainty: Exact cost depends on edit cadence, file size, and how many pills remain rendered; tightly packed updates are debounced. The full replay and cross-file fan-out are certain.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts:\_getEntryDiffBetweenEpochs/\_computeDiff</code>: Synchronize the changed snapshot models and compute an advanced text diff in the editor worker; cardinality: One initial request per pill, then another after each debounced model update; aggregate scales with visible pills, including pills unrelated to the changed URI.
    - Introduced by diff: true; previous behavior: Stable stop snapshots were updated when a streaming edit group resolved; operation-by-operation dynamic end models and their global invalidation did not exist.; critical-path effect: Asynchronous to the immediate edit callback but consumes the shared worker and follows main-thread reconstruction/model updates, degrading streaming responsiveness.
- Verdict: Reportable repeated-work regression: global operation changes repeatedly reconstruct and diff live pill models.

### Scenario 2: User invokes chat-edit undo, redo, or opens a historical diff after many incremental edits

- Critical path: Checkpoint navigation awaits structural operations, reconstruction of every affected file, and \`setContents\`; historical model creation also awaits reconstruction before the diff can render.
- Scaling input: Number of affected files F, total operations E, edit batches N per file, and file/notebook size S. Effective text replay cost is N full temporary-model builds for each file; log filtering also scans E for each reconstructed file.
- Effective concurrency: Structural filesystem operations are awaited serially in epoch order. File reconstructions then launch with \`Promise.all\` across affected URIs; operations within each replay are sequential, with no shared limiter across files.
- Cache behavior: No reconstructed checkpoint cache is used. Every navigation or model request starts from a baseline and replays matching operations; warm model references help only after that particular snapshot URI remains alive.
- Mechanism confidence: High: navigation awaits \`\_reconstructAllFileContents\`, \`\_replayOperations\` loops batches, and each text operation constructs/disposes a full TextModel.
- Magnitude uncertainty: The number and size of agent edit batches vary, but a text edit group is explicitly updated multiple times during streaming, so multi-operation replay is normal rather than hypothetical.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts:\_getTimelineDelegate and chatEditingCheckpointTimelineImpl.ts:\_applyFileSystemOperations</code>: Create, delete, or rename resources through \`IBulkEditService\` while crossing structural operations; cardinality: One boundary action per create/delete/rename operation in the traversed epoch range, serialized in order.
    - Introduced by diff: true; previous behavior: Snapshot restore set each recorded entry's state and did not replay a structural operation log; create/delete/rename representation was absent.; critical-path effect: Directly awaited before reconstruction and completion of undo/redo.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts:\_computeDiff</code>: Compute diffs for reconstructed historical text models in the editor worker; cardinality: One per observed historical diff pair after its two models are reconstructed.
    - Introduced by diff: false; previous behavior: The previous timeline also used the editor worker for stable snapshot diffs, but without operation replay to obtain model contents.; critical-path effect: The historical diff UI waits for the result; undo/redo itself does not await this worker call.
- Verdict: Reportable latency regression: one temporary full-file model is created per edit batch instead of once per reconstructed file.

### Scenario 3: User undoes requests and submits alternative requests, then the global editing session is saved or shut down

- Critical path: Branch creation itself mutates in-memory history synchronously. Saving captures the full timeline, JSON-stringifies it, and awaits a filesystem write; shutdown joins an outstanding storage task.
- Scaling input: Number of abandoned branches A multiplied by edited file/notebook baseline sizes. The effective retained cardinality is one full baseline per URI/request key, including requests whose operations and checkpoints were truncated.
- Effective concurrency: A session save is one filesystem write after serialization; saves for global sessions are launched together with \`Promise.all\`, while repeated save events are chained through \`storageTask\`.
- Cache behavior: Initial/recent snapshot content uses hash-based deduplication in the contents folder, but timeline baselines bypass that cache and are embedded directly in \`state.json\`. No pruning occurs when a future branch is discarded.
- Mechanism confidence: Very high: only operations/checkpoints are truncated, the baseline map has no deletion path, and all entries are persisted.
- Magnitude uncertainty: Impact depends on how often users branch and on file sizes; repeated regenerate/undo workflows and large generated files make growth realistic.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSessionStorage.ts:storeState</code>: Write JSON session state containing all timeline baselines; cardinality: One state-file write per session/save event; bytes include every retained baseline, including abandoned branches.
    - Introduced by diff: true; previous behavior: Future snapshot branches were removed from \`newLinearHistory\`, and snapshot contents were hash-deduplicated into content files rather than keeping abandoned baselines in persisted state.; critical-path effect: Normally asynchronous to editing, but session stop awaits it and shutdown joins an outstanding save.
- Verdict: Reportable unbounded-retention regression affecting memory and save/shutdown I/O.

### Scenario 4: A new request starts in an existing large chat editing working set

- Critical path: The add-request observer synchronously calls \`session.createSnapshot\` before observing response edits. After this change that call creates lightweight checkpoint metadata; a full baseline is deferred until a file is actually edited.
- Scaling input: Previously all F existing entries and their content sizes were copied per request; now baseline work scales only with files touched by the request and occurs once per URI/request.
- Effective concurrency: Synchronous checkpoint creation; per-file baseline creation is serialized with the resource's streaming-edit start.
- Cache behavior: \`hasFileBaseline\` provides one baseline per URI/request. There is no extra boundary call for untouched entries.
- Mechanism confidence: High: the add-request call path and deleted full-entry loop are explicit, and blame identified the introducing commit.
- Magnitude uncertainty: Exact prior delay depended on working-set and notebook sizes, but the removed collection-wide full snapshot mechanism is direct.
- Expensive boundaries: none found
