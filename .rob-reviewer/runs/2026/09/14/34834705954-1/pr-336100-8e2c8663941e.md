- Critical path: After esbuild completes, finalizeNLS must finish before output JavaScript is post-processed and written. The changed serialization is therefore on the build critical path, but it is a single linear pass over the collected message JSON per output directory.
- Scaling input: 24,742 collected messages, emitted to the primary output and the out-build compatibility mirror; effective multiplicity is two serializations because the existing flatMap builds one JavaScript payload per directory.
- Effective concurrency: Directory creation is serialized; the eight existing file writes for two directories run in one Promise.all. The diff does not change write concurrency or add a limiter need.
- Cache behavior: No cache is used before or after the diff. Both cold and warm builds regenerate these catalogs; output-directory mirroring already caused JSON serialization per destination.
- Mechanism confidence: High: the added replace scans the JSON string and can allocate a replacement string, while call placement and two-directory cardinality are directly visible.
- Magnitude uncertainty: Exact catalog byte size and build-machine throughput vary, but only sparse non-ASCII matches expand; the extra regex scan remains linear and bounded to generated catalog size.
- Expensive boundaries:
  - filesystem at <code>build/next/nls-plugin.ts: finalizeNLS</code>: Create two output directories and write four NLS files to each directory.; cardinality: Two mkdir calls followed by eight writes for the production call in build/next/index.ts; unchanged by the diff.
    - Introduced by diff: false; previous behavior: The same directories and files were created and written; nls.messages.js used JSON.stringify directly.; critical-path effect: finalizeNLS is awaited before bundle post-processing proceeds.
- Verdict: No reportable regression. The extra bounded build-time scan/allocation adds no boundary calls or concurrency and is small relative to collection, sorting, multiple existing JSON serializations, and eight filesystem writes.

### Scenario 2: Legacy compilation and localized Monaco catalog generation

- Critical path: The legacy compiler emits one base nls.messages.js after compilation, and the editor localization task synchronously reads translation data and builds one JavaScript catalog for each configured language before the gulp stream completes.
- Scaling input: One base catalog plus 13 configured localized catalogs, each proportional to the NLS key/message count after grouping by module.
- Effective concurrency: Languages are processed synchronously with forEach; existing translation reads and output queueing remain serialized. The diff does not increase language count or alter scheduling.
- Cache behavior: No in-process cache is used; each build regenerates catalogs. Missing translation files retain the existing fallback behavior and still produce one catalog per language.
- Mechanism confidence: High: serialization now adds a regex scan per catalog, but all filesystem cardinality and serialization grouping remain unchanged.
- Magnitude uncertainty: Build host speed and localization sparsity vary. The added scan is O(total emitted catalog bytes), but the PR evidence indicates only hundreds of bytes of expansion in release catalogs.
- Expensive boundaries:
  - filesystem at <code>build/lib/i18n.ts: processCoreBundleFormat</code>: Check for and synchronously read each language pack's main.i18n.json.; cardinality: Up to one exists check and one read for each of 13 configured languages; unchanged by the diff.

    - Introduced by diff: false; previous behavior: The same files were emitted with unescaped non-ASCII JSON source.; critical-path effect: The stream must complete before the build task finishes.
- Verdict: No reportable regression. The bounded extra scan does not create fan-out or meaningfully alter the existing build critical path.

- Effective concurrency: All these operations remain synchronous in their existing local loops; no new task, queue, fan-out, or parallel boundary is introduced.
- Cache behavior: Search results retain their version/URI parse cache; notebook slug counters reset per render; the other paths remain uncached as before. The source spelling changes do not alter keys or invalidation.
- Mechanism confidence: High: each diff only replaces a literal Unicode code point in a regex with its equivalent Unicode escape, preserving flags, captures, anchoring, and caller loops.
- Magnitude uncertainty: Input sizes vary, especially search-result documents and generated file trees, but regex engine work and iteration counts are semantically unchanged.
- Expensive boundaries: none found
- Verdict: No reportable regression. Runtime algorithms, match cardinality, synchronous work, allocations, and boundary behavior are unchanged.
