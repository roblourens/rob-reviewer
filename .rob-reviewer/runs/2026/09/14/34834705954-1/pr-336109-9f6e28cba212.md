<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** cache-lifecycle, repeated-work, serialization-allocation

### Scenario 1: Desktop packaging stamps the NLS cache identity into product configuration

- Critical path: The product.json packaging stream synchronously reads and hashes both generated NLS tables before that package can finish. This is on the packaging critical path, not an end-user startup path.
- Scaling input: Two generated metadata files per invoked package task; cost scales linearly with their combined byte size and with independently invoked platform/architecture packaging tasks.
- Effective concurrency: Each helper call performs two synchronous reads serially inside one package task. Platform/architecture jobs are otherwise independently scheduled by the existing build pipeline; the diff adds no concurrency burst.
- Cache behavior: No memoization is added, so each package invocation hashes its source output once. Minified and non-minified or distinct server/server-web outputs correctly receive identities derived from their own tables.
- Mechanism confidence: High: the synchronous reads and their once-per-package call sites are explicit in the changed hunks.
- Magnitude uncertainty: Exact generated table sizes and packaging timing are not measured, but cardinality is fixed at two reads per package and packaging already processes the full application payload.
- Expensive boundaries:
  - filesystem at <code>build/lib/nlsMetadata.ts:computeNLSMetadataHash</code>: Synchronously read nls.keys.json and nls.messages.json into buffers; cardinality: Exactly two reads per package invocation
    - Introduced by diff: true; previous behavior: Packaging copied the NLS files but did not synchronously reread them to derive a product identity.; critical-path effect: Blocks that package's product.json stream until both bounded generated files are read and hashed
- Verdict: No reportable regression. The new work is bounded build-time I/O performed once per package, not repeated per packaged file or runtime launch, and is small relative to the existing packaging workload.

### Scenario 2: Localized desktop startup resolves a cached or cold language pack

- Critical path: resolveNLSConfiguration runs before localized application code can load. A warm cache checks existing language-pack metadata and the hashed messages path; a cold cache reads and converts the same NLS and translation tables as before.
- Scaling input: One selected locale and language pack per desktop process; cold conversion scales with the number of NLS keys/messages, while warm startup remains constant-cardinality metadata checks.
- Effective concurrency: One promise is created for the user-selected locale during startup. The three cold-cache reads are joined with Promise.all as before; writes are likewise paired. No new fan-out is introduced.
- Cache behavior: The precomputed identity selects a cache directory without reading or hashing NLS tables at runtime. Warm hits reuse it and asynchronously touch its directory. Cold builds create one cache per unique commit/table identity. Existing cleanup removes inactive language packs and aged identity directories after startup.
- Mechanism confidence: High: changed code only substitutes the precomputed hash for commit in the cache path, and tests explicitly establish warm hits without table reads.
- Magnitude uncertainty: A first launch after adopting the new naming may not reuse a legacy directory, but normal product updates already change commits and force the same cold conversion; table sizes and storage bytes vary by build.
- Expensive boundaries:
  - filesystem at <code>src/vs/base/node/nls.ts:resolveNLSConfiguration</code>: Read languagepacks.json and test the selected translation/cache paths; cardinality: One language-pack configuration read and bounded existence checks per startup resolution
    - Introduced by diff: false; previous behavior: The same configuration read and checks used a commit-named messages directory.; critical-path effect: Existing startup-critical metadata access; unchanged by the diff except for the cache directory name
  - filesystem at <code>src/vs/base/node/nls.ts:resolveNLSConfiguration</code>: On a cache miss, read keys, default messages, and language-pack data, then write generated messages and translation configuration; cardinality: Three parallel reads and two parallel writes once per cold identity
    - Introduced by diff: false; previous behavior: The same cold conversion ran once per commit-based cache miss.; critical-path effect: Blocks localized startup only on a cold cache, as before
- Verdict: No reportable regression. Warm runtime I/O and cold conversion work are unchanged; cache directory cardinality remains approximately one per build/table, with existing age-based cleanup.

### Scenario 3: Default-English desktop, CLI, and server startup

- Critical path: The resolver returns the default NLS configuration before reading language-pack metadata because English, empty user-data paths, or development conditions satisfy the early guard.
- Scaling input: One resolver call per process startup; no collection-dependent work is added.
- Effective concurrency: No new asynchronous boundary or parallel work is reached for these default-locale entry points.
- Cache behavior: No translated-message cache is consulted. The added product field is passed through but unused after the early return.
- Mechanism confidence: High: the unchanged early guard precedes all filesystem accesses and hash-path construction.
- Magnitude uncertainty: None material for the changed behavior.
- Expensive boundaries: none found
- Verdict: No performance change beyond passing one optional string property.

### Scenario 4: Remote server resolves language packs for connected clients

- Critical path: The first request for each language/user-data pair resolves its language pack before returning configuration; subsequent requests reuse the process-local promise.
- Scaling input: Effective cardinality is one resolution per distinct language and userDataPath pair in a server process, after Map coalescing. Disk cache cardinality is one directory per distinct packaged table identity actually used with a language pack.
- Effective concurrency: Same-key calls coalesce through the existing promise cache. Different language/user-data keys can resolve concurrently as before; the diff adds no limiter change or new per-client fan-out.
- Cache behavior: The in-memory key remains language plus userDataPath. The disk cache now distinguishes server and server-web tables at the same commit, preserving warm reuse for identical identities and avoiding runtime hashing. Aged directories remain governed by the existing language-pack cache cleaner.
- Mechanism confidence: High: the changed call only supplies the product identity and the unchanged Map controls request multiplicity.
- Magnitude uncertainty: Operators sharing one user-data directory across different server target packages can retain an additional table-specific cache, but realistic target count is small and aged entries are cleaned.
- Expensive boundaries:
  - filesystem at <code>src/vs/server/node/remoteLanguagePacks.ts:getNLSConfiguration -&gt; src/vs/base/node/nls.ts:resolveNLSConfiguration</code>: Check default metadata, read language-pack configuration, and on a disk miss generate translated messages; cardinality: At most once per distinct in-process language/userDataPath key; cold filesystem conversion once per unique disk identity
    - Introduced by diff: false; previous behavior: The same boundary path used a commit-only disk cache and the same in-process coalescing.; critical-path effect: First matching request waits for resolution; warm in-process requests reuse the promise
- Verdict: No reportable regression. The change separates genuinely incompatible target tables while preserving process coalescing, warm-cache behavior, and cleanup.

**Summary:** Reviewed all 13 changed files and traced packaging, desktop/CLI/server startup, remote language-pack resolution, cold/warm cache behavior, and cache cleanup. No high-confidence actionable performance regression was introduced, and the PR does not establish a concrete performance-regression fix requiring blame attribution.
