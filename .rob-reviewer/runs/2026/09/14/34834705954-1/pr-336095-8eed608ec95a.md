## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts:575` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts:566`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts`  
**Introducing commit:** `c2091046fe3962bbddbfa8ae13d58e6821626cea`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.99

**Mechanism:** Checkpoint replay rebuilt and reserialized the entire text buffer for every recorded text-edit operation, producing O(K\*N)-style full-document CPU/allocation work for K small batches over a large file and blocking undo, redo, restore, and cold snapshot/diff model creation.

**Symptom:** Large chat-edited files with many recorded edit operations can freeze or substantially delay checkpoint undo/redo/restore and cold historical diff rendering because repeated full-document scans and copies execute before those actions complete.

**Fixed behavior:** The added contiguous TextEdit grouping applies all version-ordered edit batches to one PieceTreeTextBuffer and extracts content only once per ordinary-text run, reducing full-buffer construction/extraction from one per edit operation to one per run while retaining create/delete/rename and notebook boundaries and disposing the buffer in finally.

**Evidence:** Before this PR, \_replayOperations awaited \_applyOperationToState once for every TextEdit operation; that branch called \_applyTextEditsToContent for each operation. \_applyTextEditsToContent calls createTextBuffer on the complete current content, whose createTextBufferFactory passes the entire string to PieceTreeTextBufferBuilder.acceptChunk/createLineStarts, and then extracts the complete resulting string. The path is directly awaited by undoInteraction/redoInteraction/restoreSnapshot through navigateToCheckpoint, and by snapshot-model creation used for diff rendering. Thus K edit batches over a document of size N repeatedly scan and materialize the full document on the renderer-side critical path. The PR's tests also establish the old multiplicity versus the fixed invariant by asserting one buffer creation/disposal for multiple edit operations.

- Effective concurrency: Create/delete/rename operations are awaited serially in epoch order. The diff does not increase aggregate file concurrency.

### Scenario 2: Cold and warm historical snapshot/diff model creation for chat-edited files

- Critical path: On a cold model request, the snapshot content provider calls getSnapshotModel/getContentAtStop, which reconstructs the requested historical content before creating the text model. Diff observables request original and modified snapshot models in parallel, then await editor-worker diff computation. Warm existing models and finalized diff-cache entries bypass reconstruction or computation. The changed replay is on the cold critical path only.
- Scaling input: Observed file diffs D, usually two historical models per uncached diff; per snapshot, document length N and text-edit batches K between baseline and target. Grouping reduces reconstruction from K full-buffer rebuilds to one per contiguous ordinary-text run. Effective cardinality is per distinct uncached snapshot URI/diff key, not per UI row after model/cache reuse.
- Effective concurrency: The two snapshot model references for one diff use Promise.all. Multiple observed per-file diffs may progress concurrently. \_refCountedDiffs coalesces the same active key and \_finalizedDiffCache serves completed final keys. The diff does not change concurrency or coalescing.
- Cache behavior: The model service returns an existing live snapshot model on warm access. Active identical diff requests share \_refCountedDiffs, and finalized diffs use \_finalizedDiffCache. Cold misses reconstruct; failed provider/model requests are not newly cached by this diff. Grouping is local to each miss.
- Mechanism confidence: High: provider, model-cache, ref-count, finalized-cache, and editor-worker paths are explicit, and no changed line alters their scheduling or keying.
- Magnitude uncertainty: The number of simultaneously observed file diffs and model-cache hit rate vary by UI surface. The reduction in prerequisite replay work is certain; exact user-visible gain varies with N and K.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts:\_computeDiff</code>: Compute the original/modified text diff in the editor worker; cardinality: One worker request per uncached observed diff key after the two snapshot models are ready; active identical keys coalesce and finalized keys cache.
    - Introduced by diff: false; previous behavior: The same editor-worker call cardinality, cache keys, and scheduling existed before the diff.; critical-path effect: Diff UI remains busy until the worker result; the changed replay only reduces prerequisite local CPU before this unchanged request.
- Verdict: No performance regression. Cold reconstruction becomes cheaper, while warm cache behavior, active coalescing, worker IPC cardinality, and concurrency are unchanged.

### Scenario 3: Live snapshot model refreshes while agent edits continue

- Critical path: Operation changes schedule getContentAtStop through a 500 ms ThrottledDelayer; reconstruction completes before the callback replaces the snapshot model value. The changed replay runs on each executed refresh, but reduces rather than increases full-buffer work.
- Scaling input: Recorded edit history up to the target epoch K, current document length N, and operation-event frequency. Coalescing limits execution to approximately one refresh per 500 ms burst; finalization disposes the listener after the target epoch is reached.
- Effective concurrency: One ThrottledDelayer per live snapshot subscription coalesces operation events. Separate snapshot subscriptions can refresh independently; this behavior is unchanged. Each reconstruction owns a separate temporary buffer, as covered by concurrent reconstruction tests.
- Cache behavior: No reconstructed-content cache is used for live targets because content changes. Event bursts are time-coalesced, and the subscription disposes when finalized. The diff does not alter keys, negative caching, or subscription lifetime.
- Mechanism confidence: High: the 500 ms scheduler, reconstruction call, callback, and changed one-buffer-per-run replay are explicit.
- Magnitude uncertainty: The number of simultaneously open live snapshots varies, but event throttling and per-call isolation are established. Exact model setValue cost depends on document size and is unchanged downstream work.
- Expensive boundaries: none found
- Verdict: No performance regression. Refresh frequency and downstream model replacement are unchanged; each refresh performs fewer full-document allocations/scans and disposes its buffer.

### Scenario 4: Notebook checkpoint reconstruction, including cell text edits and final notebook snapshot serialization

- Critical path: Notebook baselines create an untitled notebook model, replay notebook/cell operations in order, resolve the notebook data provider, serialize the final snapshot, and dispose the notebook model. The new ordinary-text grouping is gated off whenever currentState.notebook exists; the only notebook change wraps the existing single edit batch in an outer array.
- Scaling input: Notebook cell count, notebook operation count, and edited-cell content sizes. Cell text edits still create one temporary text buffer per cell TextEdit operation, exactly as before; notebook serialization remains once per surviving reconstructed notebook.
- Effective concurrency: Operations within one notebook replay remain sequential. Separate affected notebooks may reconstruct under the existing Promise.all across resources. The diff does not add notebook parallelism.
- Cache behavior: No new notebook cache is added. Provider resolution and snapshot serialization follow the prior path. Temporary cell buffers and the notebook model retain their existing disposal ownership.
- Mechanism confidence: High: the \!currentState.notebook guard and unchanged provider/serialization path are explicit; the signature adaptation supplies one group for the existing cell behavior.
- Magnitude uncertainty: Provider activation cost and notebook sizes vary, but the changed grouping is provably excluded from notebook state and does not alter this boundary.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts:\_replayOperations</code>: Resolve/activate the notebook data provider before serializing the reconstructed notebook snapshot; cardinality: Once per surviving notebook reconstruction after all operations; separate notebooks follow the pre-existing per-resource Promise.all.
    - Introduced by diff: false; previous behavior: The same provider resolution, notebook serialization, model lifecycle, and per-notebook cardinality existed before the diff.; critical-path effect: Notebook reconstruction waits for provider resolution and serialization before returning content.
- Verdict: No performance regression. Notebook replay cost, boundary count, concurrency, and cleanup remain unchanged.
