## Findings (1)

### 1. [medium] Coalesce submenu relayouts during scrolling

**Finding ID:** `PERF-6D4A3CE1D5C3`  
**Location:** <code>src/vs/platform/actionWidget/browser/actionList.ts:1054</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous DOM geometry/style work on the UI thread  
**Scaling:** One complete panel-positioning pass is now executed for every emitted wheel, trackpad, touch, smooth-scroll, or programmatic scroll update while a child panel is open; cost therefore scales with scroll-event frequency.  
**Outcome:** Repeated style/layout work on the scroll critical path can increase scroll latency and drop frames.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The scroll listener was registered only for widgets with persistentHover. Nested Remote submenu widgets are non-persistent, so scrolling them did not invoke their open child hover's layout callback.  
**Changed behavior:** Every ActionListWidget now subscribes to onDidScroll and synchronously invokes \_layoutSubmenu whenever any child panel is open.  
**Confidence:** 0.96 — The listener registration change, non-persistent Remote submenu options, synchronous ListView render-before-notification ordering, and geometry-heavy callback are all directly traced. Exact frame loss varies by device, menu complexity, and scroll input rate, which affects severity rather than mechanism confidence.

**Causal diff evidence:** Added lines 1054-1058 replace the prior \`if (this.\_options?.persistentHover)\` registration guard with an unconditional onDidScroll subscription that calls \`\_layoutSubmenu\` for non-persistent nested lists.

With a status hover open in a long Remote submenu, wheel or trackpad scrolling now performs panel geometry reads and style writes on every scroll update, putting extra layout work directly on the interaction path and risking visible jank.

**Evidence:** ListView registers its internal scroll listener first and \`onScroll\` calls \`render(...)\`, which mutates/recycles rows; this new listener then calls \`\_layoutSubmenu\`. That callback reads the list, anchor, and panel via multiple \`getBoundingClientRect()\`/\`offsetHeight\` accesses and writes panel position (and, for constrained nested menus, relayouts the submenu list). The added regression test explicitly observes one \`\_layoutSubmenu\` call for one nested-list scroll, and the Remote test uses a non-persistent filtered submenu, proving the changed path is reachable.

**Suggested direction:** Keep immediate relayout for explicit layout/filter operations, but coalesce scroll-triggered submenu positioning to at most once per animation frame and cancel any pending callback when the submenu is cleared or the widget is disposed.
