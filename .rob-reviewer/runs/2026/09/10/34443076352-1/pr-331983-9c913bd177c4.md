## Findings (1)

### 1. [low] Prune completed turn correlations

**Finding ID:** `PERF-3994892C73E7`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:6587</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Map entries and retained SDK interaction/turn ID plus host-turn ID strings  
**Scaling:** O(U + T) retained entries for U unique root interaction IDs and T unique SDK root-turn IDs over the lifetime of one live chat session; completed turns do not reduce either cardinality.  
**Outcome:** retained memory and increasing GC pressure over long-running sessions  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, the session did not allocate or retain these root-turn correlation maps, so completed root interactions added no such session-lifetime state.  
**Changed behavior:** Every root \`assistant.turn\_start\` with an interaction ID now retains the interaction-to-host-turn pair, and distinct SDK turn IDs are retained as well, even after the protocol turn completes.  
**Confidence:** 0.98 — The writes are directly on the normal root-turn path, repository-wide searches show no deletion or clearing for either new map, and \`CopilotAgent\` retains live \`CopilotAgentSession\` instances until chat release/destruction. The exact heap cost per real-world session is uncertain, but the linear retention mechanism and lifecycle are explicit.

**Causal diff evidence:** The diff adds \`\_hostTurnIdsBySdkTurnId\`/\`\_hostTurnIdsByInteractionId\` and inserts a new interaction entry at line 6587 (also for steering at line 4913), but there is no corresponding delete or clear anywhere in \`CopilotAgentSession\`; \`resetTurnState\` only clears streaming state, and the maps survive until the whole session object is disposed.

A long-lived Copilot chat accumulates unreachable historical correlation keys and host-turn UUID values, increasing agent-host heap retention and eventual GC pressure until the chat/session is released.

**Evidence:** \`onTurnStart\` stores both SDK turn and interaction correlations; the steering user-message path stores another interaction correlation. \`\_completeActiveTurn\`, \`failActiveTurn\`, \`discardActiveTurn\`, \`onTurnEnd\`, and \`resetTurnState\` do not remove them. Tests exercise distinct \`interaction-1\` and \`interaction-2\`, demonstrating cardinality grows with interactions rather than remaining a single active entry.

**Suggested direction:** Expire correlations when their host protocol turn completes, aborts, or is discarded. Maintain reverse keys per host turn (or a bounded active/recent correlation set if late-event rejection requires it) so cleanup is O(entries for that turn) rather than scanning the full maps.
