# Performance review: mcp: Await workspace .mcp.json discovery before autostart

[PR #335390](https://github.com/microsoft/vscode/pull/335390) at `8996c34a2c020caab36bb6c1ea7a1d5f22ec6fbb`

## Findings

No high-confidence performance findings.

<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** boundary-fanout, eager-work, repeated-work, missing-coalescing

### Scenario 1: Workbench AfterRestored startup discovers workspace-root .mcp.json files across a multi-root workspace

- Critical path: McpDiscovery.start synchronously installs one watcher and starts one read per workspace folder, but does not await any read, so workbench restoration remains off this filesystem critical path.
- Scaling input: Workspace-folder count N. Initial filesystem concurrency is N in both versions; registry placeholder registration/replacement also scales with N, while McpService's existing 500 ms scheduler coalesces collection updates.
- Effective concurrency: Initial reads run in parallel across workspace folders, as before. Each folder's watcher uses its own RunOnceScheduler to coalesce changes.
- Cache behavior: loadInitial memoizes the initial update promise, so registry discovery and the eager kickoff share one read. After resolution, the lazy collection is replaced by a normal collection or removed; watcher updates remain independently throttled.
- Mechanism confidence: High confidence that no filesystem call or startup wait was added, based on the before/after updateFile call and the non-awaited void loadInitial invocation.
- Magnitude uncertainty: Very large multi-root workspaces cause extra in-memory placeholder registry churn, but the operations are small and downstream server recomputation is already coalesced; evidence does not establish a user-visible regression.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/mcp/common/discovery/workspaceDotMcpDiscovery.ts:104</code>: create a non-recursive watcher for &lt;folder&gt;/.mcp.json; cardinality: One watcher per workspace folder for the folder lifetime.
    - Introduced by diff: false; previous behavior: The same watcher was created once per workspace folder before the diff.; critical-path effect: Watcher setup is synchronous during AfterRestored discovery, while file-change processing is deferred by a 500 ms scheduler.
  - filesystem at <code>src/vs/workbench/contrib/mcp/common/discovery/workspaceDotMcpDiscovery.ts:79</code>: read and parse &lt;folder&gt;/.mcp.json; cardinality: One eager initial read per workspace folder, issued independently; later change events are coalesced for 500 ms per folder.
    - Introduced by diff: false; previous behavior: The same eager updateFile call issued one initial read per workspace folder; the diff memoizes that initial invocation rather than adding another read.; critical-path effect: The initial reads are started but not awaited by discovery startup, so they do not block workbench restoration.
- Verdict: No reportable startup regression. The diff preserves eager I/O cardinality and keeps it off the workbench restoration critical path.

### Scenario 2: A cold first native chat request autostarts MCP servers while workspace .mcp.json discovery is still pending

- Critical path: chatServiceImpl awaits ChatMcpServersStarting.wait before invoking the agent; McpService.\_autostart awaits registry.discoverCollections, whose Promise.all now includes each pending workspace lazy collection load. Progress therefore waits for the slowest pending workspace read before candidate selection.
- Scaling input: Number of workspace folders whose initial reads are still pending when the first tool-capable chat request is sent; effective latency is the maximum remaining read duration because loads run in parallel.
- Effective concurrency: All pending folder reads were already started eagerly and discoverCollections awaits them concurrently with other lazy collections using Promise.all. The diff does not add I/O concurrency.
- Cache behavior: The promise is memoized per folder and the lazy placeholder is replaced or removed after the initial read, so subsequent requests do not repeat or await this initial read. There is no negative cache beyond completion because watcher events remain authoritative.
- Mechanism confidence: High confidence in the changed critical-path wait from the added lazy.load through discoverCollections, McpService.\_autostart, and chatServiceImpl's await.
- Magnitude uncertainty: The delay is observable only when a request arrives before AfterRestored discovery finishes, especially on slow remote filesystems; typical local reads likely complete first.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/mcp/common/discovery/workspaceDotMcpDiscovery.ts:106-116</code>: complete the already-started read of each workspace-root .mcp.json; cardinality: At most one memoized initial read per workspace folder; effective cold fan-out is N folders and warm fan-out is zero.
    - Introduced by diff: true; previous behavior: Reads were still eagerly issued, but workspace-dot-MCP discovery was not represented in discoverCollections, so chat autostart did not await their completion and could omit those servers.; critical-path effect: The diff moves completion of pending reads onto cold MCP autostart and therefore the first tool-capable chat request's critical path; parallel Promise.all latency is governed by the slowest pending read, not the sum.
- Verdict: No finding. The cold wait is the intentional bounded ordering needed to make workspace MCP servers available before autostart selects tools; it is memoized, parallel, and does not add boundary calls. No behavior-preserving narrower operation is established.

### Scenario 3: Adding or removing a workspace folder while the workbench is running

- Critical path: The workspace-folder event synchronously disposes removed folder state or creates watcher/placeholder state for an added folder, then starts the new folder's initial read without awaiting it. A concurrent later collection activation can await that one memoized read.
- Scaling input: Number of folders in a single workspace-folder change event; each added folder receives one independent read and watcher.
- Effective concurrency: Added-folder reads run independently in parallel; each folder's subsequent watcher events are coalesced by its scheduler.
- Cache behavior: Each added folder gets a fresh memoized initial promise. Removal disposes its watcher and current registry registration; no long-lived initial promise is retained by the discovery map after removal.
- Mechanism confidence: High confidence from the workspace event loop, disposable map ownership, and memoized load path.
- Magnitude uncertainty: Bulk folder additions are uncommon, and no evidence shows the small added registry placeholder work causing measurable latency.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/mcp/common/discovery/workspaceDotMcpDiscovery.ts:39-46,104-116</code>: watch and initially read the added folder's .mcp.json; cardinality: One watcher and one initial read per added folder; one disposal per removed folder.
    - Introduced by diff: false; previous behavior: Added folders already created a watcher and started an initial read; removed folders already disposed their watcher and registration.; critical-path effect: The folder-change handler does not await the read. Only MCP collection activation occurring while it is pending waits for completion.
- Verdict: No reportable regression. Boundary cardinality and lifecycle are unchanged, and the new awaitability applies only if MCP activation races the initial read.

**Summary:** Completed the performance pass over both changed files and traced startup discovery, cold chat autostart, and workspace-folder lifecycle paths. The PR adds an intentional cold-path barrier but no new filesystem operation, repeated read, unbounded retention, serialization growth, or concurrency burst. No valid performance finding or shipped performance-regression fix was identified.
