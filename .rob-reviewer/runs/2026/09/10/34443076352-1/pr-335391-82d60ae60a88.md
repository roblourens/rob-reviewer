# Performance review: chat: expand customization migration assessment telemetry

[PR #335391](https://github.com/microsoft/vscode/pull/335391) at `82d60ae60a881e4eeec9277ef438089f7382600f`

## Findings (1)

### 1. [high] Keep disabled-category assessment off the request critical path

**Finding ID:** `PERF-C19E345CD38A`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts:224</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** filesystem operations and an agent-host session-state wait  
**Scaling:** On each eligible chat request, the five unconditional inventories fan out across the default locations for agents, instructions, prompts, skills, and hooks; under \`once\`, this repeats on every turn when no migration hint is produced, and source-folder discovery can wait up to 2 seconds for the first agent-host snapshot.  
**Outcome:** blocked chat request dispatch and increased time to first response  
**PR causality:** <code>introduced</code>  
**Previous behavior:** \`computeMigrationHint\` called \`computeMigration\` for each category, whose existing enablement guard returned before file discovery for disabled categories. With the default settings, only prompt-file discovery ran; if there were no prompt candidates, \`getSourceFolders\` received an empty collection and did not wait for agent-host customizations.  
**Changed behavior:** The added \`Promise.all\` invokes \`listPromptFiles\` for all five customization types regardless of which migration categories are enabled, then derives source-folder target types from the entire inventory. This performs discovery solely for telemetry assessment and can call \`provideSourceFolders\` for otherwise-disabled agents/instructions/skills/hooks.  
**Confidence:** 0.98 — The changed test proves the new unconditional calls even when categories are disabled; repository implementations prove the filesystem operations, the explicit 2-second readiness bound, and that \`sendRequest\` awaits the collector before agent invocation. Exact disk latency and how often the experiment enables hints vary, affecting severity but not the mechanism.

**Causal diff evidence:** RIGHT lines 224-228 add unconditional \`listPromptFiles\` calls for every prompt type, replacing the old enabled-gated \`computeMigration\` calls. The changed test at lines 951-957 explicitly updates the all-disabled case from zero requested types/folders to all five types plus agent/skill source folders.

With migration hints enabled by the experiment and the default migration-category settings (prompt migration enabled, the other file migrations disabled), a user who has native agent/instruction/skill/hook customizations but no prompt migration candidate now pays all-category filesystem discovery and may wait up to 2 seconds for remote session state before their message is sent. In \`always\` mode this occurs every turn; in \`once\` mode it also repeats while no hint is returned.

**Evidence:** \`PromptsService.listPromptFiles\` cold misses call \`PromptFilesLocator.listFilesWithSource\`, which resolves each configured/default location via filesystem/search operations; the defaults span multiple agent, instruction, skill, and hook locations. \`AgentCustomizationItemProvider.provideSourceFolders\` awaits \`whenCustomizationsReady\`, whose production implementation has a 2000 ms first-snapshot timeout. \`ChatService.sendRequest\` awaits this hint collector in the request-context \`Promise.all\` before invoking the agent, so these added operations delay request dispatch rather than running as background telemetry.

**Suggested direction:** Preserve the full assessment telemetry, but collect/cache it outside chat request dispatch (for example once per target/inventory generation after the request is sent), or at minimum keep hint computation enablement-gated and schedule the disabled-category assessment separately with invalidation on customization changes.

### Scenario 2: Subsequent chat turns in \`once\` or \`always\` hint mode when all customizations are native/supported and no hint is returned

- Critical path: Every eligible turn calls the assessment before agent invocation. \`once\` suppresses later calls only after an actual hint is shown, so a no-hint assessment repeats; \`always\` intentionally assesses every turn.
- Scaling input: Cost grows with chat-turn count and with distinct inventory type/source buckets after file-level aggregation.
- Effective concurrency: Inventory promises are concurrent; target source-folder projections are sequential; telemetry rows are synchronously dispatched one by one.
- Cache behavior: Warm prompt inventories reuse cached promises until invalidated, and session-state readiness is already settled. Assessment arrays/maps and telemetry payloads are rebuilt each turn; there is no assessment-result coalescing.
- Mechanism confidence: High for repeated invocation and bounded event cardinality; lower magnitude concern for telemetry because transport is asynchronous.
- Magnitude uncertainty: Turn count and number of non-empty source buckets vary. The telemetry fan-out alone is bounded and not severe enough for a separate finding.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/common/promptSyntax/service/promptsServiceImpl.ts:listPromptFiles</code>: Refresh prompt inventories after any relevant invalidation.; cardinality: Usually cache hits; after invalidation, five type inventories on the next turn.
    - Introduced by diff: true; previous behavior: Only enabled categories requested inventories, so disabled-category invalidations did not affect hint latency.; critical-path effect: Cache hits are cheap, but any cold/invalidated type blocks that turn.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts:computeMigrationHint</code>: Dispatch aggregate assessment telemetry rows.; cardinality: One event per distinct type/source bucket per turn; bounded and typically small.
    - Introduced by diff: true; previous behavior: No assessment telemetry was emitted when no migration hint existed.; critical-path effect: Only local preparation and enqueue are synchronous; transport completion is off the critical path.
- Verdict: Covered by the reported eager-work issue for disabled inventories. The bounded per-row telemetry does not independently meet the reporting threshold.

### Scenario 3: Customization management editor computes file or MCP migration plans directly

- Critical path: The editor awaits the selected migration computation to render candidates or perform migration; it does not call the new full \`collectMigrationAssessment\` path unless requesting a hint.
- Scaling input: File plans scale with candidate count and target folder count. MCP counting scales linearly with the support snapshot's server count.
- Effective concurrency: \`computeMigrations\` still starts four category computations concurrently. Individual source-folder target types remain sequential inside each file category.
- Cache behavior: File inventory behavior remains category-specific. MCP support uses the existing refcounted scope lifecycle; no new persistent cache is added.
- Mechanism confidence: High: the changed return wrapper adds only an in-memory assessment-count loop to direct MCP computation.
- Magnitude uncertainty: MCP server lists and customization collections are normally modest; no evidence of large production cardinality was found.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts:computeMigration/computeMigrations/migrateMcpServers</code>: Discover category-specific prompt files and read/write MCP configuration during explicit migration actions.; cardinality: Grouped by migration category and target type; explicit MCP writes remain per migration plan.
    - Introduced by diff: false; previous behavior: The same inventory and MCP migration boundaries existed.; critical-path effect: Required for rendering or executing the user-requested migration.
- Verdict: No reportable regression; added work is bounded linear CPU/allocation without a new boundary or hot-path amplification.
