## Findings (1)

### 1. [medium] Filter filesystem-provider events before restarting history expansion

**Finding ID:** `PERF-FFB19C6C28AC`  
**Location:** <code>src/vs/sessions/services/sessions/browser/sessionsRecentWorkspacesService.ts:136</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** main-process IPC calls plus filesystem/extension-host reads and JSON buffers  
**Scaling:** Each filesystem-provider registration or removal restarts one \`getRecentlyOpened()\` IPC and fans out to as many as 10 workspace-file reads (up to 1 MiB each), so cost grows as O(provider events × recent workspace files).  
**Outcome:** Repeated I/O/IPC and restarted five-second loads delay recent-workspace availability and add startup I/O/CPU pressure in the Agents window.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, filesystem-provider registrations did not refresh session workspace history, and VS Code history refreshes did not parse \`.code-workspace\` files.  
**Changed behavior:** The added unfiltered global registration listener invokes \`\_refreshVSCodeRecentWorkspaces()\` for every added or removed scheme; each refresh cancels the prior scan, performs \`getRecentlyOpened()\`, and may launch up to 10 \`readFile\`/parse operations.  
**Confidence:** 0.97 — The trigger, call path, fan-out bound, and non-propagating extension-provider cancellation are directly visible in repository code. The exact number and latency of provider registrations vary by installation, which affects severity but not the repeated-I/O mechanism.

**Causal diff evidence:** The added line \`this.\_register(this.fileService.onDidChangeFileSystemProviderRegistrations(() =&gt; this.\_refreshVSCodeRecentWorkspaces()));\` newly binds every provider add/remove event to the full history scan introduced below.

When built-in or extension filesystem providers register after the fresh composer is created, unrelated schemes repeatedly restart recent-workspace loading. A window with 10 recent \`.code-workspace\` entries can issue 10 reads per event and keep the picker history in \`loading\` until registrations settle; extension-backed \`readFile\` calls cannot be canceled at the provider RPC, so superseded scans can continue consuming I/O.

**Evidence:** \`FileService.registerProvider\` fires this global event for every scheme and for unregisters. \`\_refreshVSCodeRecentWorkspaces\` crosses the desktop workspaces proxy via \`getRecentlyOpened()\` and \`Promise.all\`s up to \`MAX\_RECENT\_WORKSPACE\_FILES\` calls to \`\_readWorkspaceFolders\`; \`\_readWorkspaceFolders\` calls \`fileService.readFile\`. The extension-host \`RemoteFileSystemProvider.readFile\` forwards \`$readFile\` without a cancellation token, so disposing a superseded refresh does not necessarily stop the underlying boundary operation. This repository also registers several unrelated Agents filesystem schemes at \`WorkbenchPhase.AfterRestored\`, making the trigger realistic during window startup.

**Suggested direction:** Track schemes for recent workspace files that could not be read and refresh only on an \`added\` event for one of those schemes (or otherwise filter by relevant config-path schemes); ignore unrelated registrations/removals and coalesce matching events so only one scan can proceed.
