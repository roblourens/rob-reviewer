### Scenario 1: Activating the built-in HTML or JSON language extension and starting its language server

- Critical path: Extension activation constructs one language client, launches one node IPC server or one browser worker, performs the LSP initialize exchange, and awaits client.start() before feature registration completes. The dependency versions change, but the diff does not add another launch, initialization request, or synchronous startup operation.
- Scaling input: One client/server pair per activated built-in language extension; participant changes can trigger a restart, but existing code coalesces those changes with a single 2-second timer.
- Effective concurrency: HTML and JSON each run one server independently. Within each extension, participant-triggered restarts are serialized by disposing the old client before starting the replacement, and repeated triggers are coalesced by replacing the pending timer.
- Cache behavior: No startup result cache is involved. JSON initializes its existing persistent schema cache once; HTML discovers custom-data URIs once. Neither cache lifecycle is changed by these dependency-only hunks.
- Mechanism confidence: High confidence that launch, handshake, restart coalescing, and visible boundary cardinality are unchanged; low confidence in any unobservable internal package implementation delta, so no regression mechanism is established.
- Magnitude uncertainty: The internal startup cost differences between the old prerelease packages and new published packages are not available in the repository diff, so exact bytecode, allocation, and timing deltas cannot be measured from repository evidence.
- Expensive boundaries:
  - subprocess at <code>extensions/html-language-features/client/src/node/htmlClientMain.ts:31 and extensions/json-language-features/client/src/node/jsonClientMain.ts:36</code>: Launch the node language-server module (or create one web worker in browser builds).; cardinality: One launch per extension activation, plus one replacement after a coalesced participant-change restart.

### Scenario 2: Editing HTML/JSON documents: synchronization, validation, completion, hover, symbols, formatting, and related language requests

- Critical path: Each editor operation is serialized over the existing LSP client/server transport and then invokes the corresponding language-service method. JSON reuses a bounded parsed-document cache; HTML caches per-document settings and mode models. The changed manifests do not alter handlers, request frequency, result limits, cancellation flow, or document synchronization mode.
- Scaling input: Cost scales with document size, open-document count, edit frequency, and requested result count. Effective request cardinality remains one protocol operation per editor feature invocation or document synchronization event, not one new boundary per syntax node or result item.
- Effective concurrency: The language server handles requests through the existing JSON-RPC connection with cancellation tokens passed to feature handlers. Validation scheduling and request concurrency are unchanged by the manifest-only diff.
- Cache behavior: JSON's parsed-document model cache remains bounded to 10 entries with a 60-second cleanup interval. HTML's scoped settings are cached by document URI and removed on close; both servers dispose model resources on shutdown. No key, bound, invalidation, or allocation policy changes in the diff.
- Mechanism confidence: High confidence that repository-visible hot-path cardinality, cache bounds, cancellation, and result limits are unchanged. There is insufficient evidence for a concrete regression inside the upgraded packages.
- Magnitude uncertainty: Published dependency internals are not included in the patch, so small implementation-level CPU or allocation changes cannot be ruled out; there is no code, benchmark, or transitive dependency evidence of increased work.
- Expensive boundaries:
  - IPC at <code>extensions/html-language-features/server/src/htmlServer.ts:80 and extensions/json-language-features/server/src/jsonServer.ts:124</code>: Send incremental text synchronization and feature requests/results between the extension host and language-server process/worker.; cardinality: One transport exchange per existing synchronization or feature request; result payload scales with the existing bounded/unbounded feature result semantics.

### Scenario 3: Loading HTML custom-data files and JSON schemas during initialization, configuration changes, and validation

- Critical path: HTML sends custom-data URIs to the server and reads each requested URI through an existing client filesystem/document request. JSON validation resolves referenced schemas through existing file/client requests; remote schemas may require network access before validation completes. These paths and their placement are unchanged.
- Scaling input: HTML work scales with the deduplicated Set of configured custom-data URIs. JSON work scales with distinct referenced schema URIs after language-service caching; schemastore HTTP content is additionally served from a persistent cache for up to 48 hours before revalidation.
- Effective concurrency: HTML custom-data loads are initiated by the existing language-service fetch flow. JSON schema requests are request-driven over the single LSP connection; no new Promise.all fan-out, limiter removal, or concurrency burst appears in the diff.
- Cache behavior: JSON schemastore entries use persistent ETag/file caching and a 48-hour warm-cache window; 304 responses read cached files and avoid downloading content. HTML deduplicates URI inventories with Sets but reads content when requested. The dependency updates do not change these repository-owned cache keys, invalidation, negative-cache behavior, or cleanup.
- Mechanism confidence: High confidence in the existing boundary locations, cache behavior, and repository-owned cardinality; insufficient confidence that the upgraded language-service packages increase request count or defeat caching.
- Magnitude uncertainty: A new language-service implementation could theoretically alter when it asks for custom data or schemas, but the patch contains no dependency source, tests, call-count change, or evidence showing increased requests. Existing lockfile changes only show version substitutions and some type-package deduplication.
- Expensive boundaries:
  - filesystem at <code>extensions/html-language-features/client/src/customData.ts:53</code>: Read HTML custom-data content from workspace/extension storage.; cardinality: At most one request per language-service load of each deduplicated configured URI; edits/configuration changes can invalidate and reload through the existing path.
    - Introduced by diff: false; previous behavior: The same custom-data inventory, IPC request, and filesystem/document read path existed before the version changes.; critical-path effect: Custom-data availability waits for the relevant content request, but server startup does not await the initial fetch promise.
  - IPC at <code>extensions/html-language-features/server/src/htmlServer.ts:98 and extensions/json-language-features/server/src/jsonServer.ts:100</code>: Request custom-data or non-file JSON schema content from the extension host.; cardinality: One request per distinct content resolution initiated by the existing language service; no diff-visible increase in distinct URIs or retries.
    - Introduced by diff: false; previous behavior: The same custom request types and handlers were used with the prior protocol packages.; critical-path effect: The requested content must arrive before that data/schema can be consumed; it is off the initial HTML initialize response path.
  - network at <code>extensions/json-language-features/client/src/node/jsonClientMain.ts:105 and extensions/json-language-features/client/src/jsonClient.ts:424</code>: Download remote JSON schema content with redirects and optional ETag revalidation.; cardinality: Cold or expired cache: one HTTP request per distinct requested schema URI; warm schemastore cache under 48 hours: zero network calls; ETag cache: one conditional request, with one fallback request only if cached content is unexpectedly unavailable after 304.
    - Introduced by diff: false; previous behavior: The identical request-light version, request service, ETag policy, and call sites existed before the PR.; critical-path effect: Cold schema validation waits for the network response; warm cached reads avoid the network.
  - filesystem at <code>extensions/json-language-features/client/src/node/schemaCache.ts:46-136</code>: Read/write/delete persistent JSON schema cache files and update cache metadata.; cardinality: One file write after a cacheable successful download; one file read per warm-cache hit or 304 reuse; clear-cache is explicitly user-triggered and scales with cached files.
    - Introduced by diff: false; previous behavior: The cache implementation and lifecycle are unchanged by the dependency updates.; critical-path effect: Warm reads and cache writes are awaited on schema resolution; clear-cache is command-driven.
- Verdict: No reportable regression. All filesystem, IPC, and network boundaries predate the diff, and there is no evidence that the upgrades increase their cardinality, concurrency, or critical-path placement.
