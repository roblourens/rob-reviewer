# Performance review: Add migration page for agent file compatibility in chat customization

[PR #335073](https://github.com/microsoft/vscode/pull/335073) at `9aed9e96e31727483b758c96d5ebdf372faac53f`

## Findings (1)

### 1. [medium] Route agent-file migration discovery through bounded cached parsing

**Finding ID:** `PERF-BEE906E50589`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts:89</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** filesystem reads, parser CPU, and file handles for every local/user agent file  
**Scaling:** Each migration assessment launches one \`parseNew\` per local/user agent file simultaneously, so read/parse work is O(N) and peak filesystem concurrency is N; closed files are reread on every assessment because \`parseNew\` only caches open text models.  
**Outcome:** increased first-request latency and bursty filesystem/CPU load, with file-handle exhaustion risk for large agent collections  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Migration hint computation and customization-editor refreshes did not parse agent-file contents to assess this category, so these paths incurred no per-agent content reads for handoff detection.  
**Changed behavior:** The added \`Promise.all(...map(...parseNew))\` reads and parses every eligible agent file during each AgentFiles migration computation, without using the service-wide discovery limiter or cached agent discovery result.  
**Confidence:** 0.99 — The direct filesystem fallback in \`parseNew\`, lack of closed-file parse caching, unbounded \`Promise.all\`, existing limiter rationale, and blocking chat call path are all explicit in repository code. Only the typical number and latency of user agent files are uncertain, which limits severity rather than mechanism confidence.

**Causal diff evidence:** Added line 89 invokes \`this.promptsService.parseNew(file.uri, token)\` for every local/user agent produced by the added \`Promise.all\` map; this per-file content read did not exist on migration assessment paths before the PR.

With the feature enabled, opening the Chat Customizations editor scans all local/user agents; when migration hints are set to \`once\` or \`always\`, the first or every agent-host chat request performs the same scan. \`sendRequest\` awaits \`collectCustomizationMigrationHint()\` in its context \`Promise.all\` before agent invocation, so slow or remote files directly delay the request. Large agent collections also open all reads concurrently.

**Evidence:** \`PromptsService.parseNew\` calls \`fileService.readFile\` for every URI without an open text model and does not cache that result. The surrounding prompt discovery code explicitly routes such reads through a service-wide \`Limiter\` capped at 10 because unbounded discovery can exhaust file handles, but this new call site invokes \`parseNew\` directly under \`Promise.all\`. The editor invokes \`computeMigration\` on initial load and customization changes, while \`ChatService.sendRequest\` awaits \`computeMigrationHint\` before invoking the agent.

**Suggested direction:** Reuse or extend the cached, limiter-backed agent discovery result to expose whether each file has handoffs, or add a bounded/coalesced migration scan with invalidation on agent-file changes. Ensure concurrent editor/hint assessments share one in-flight result rather than issuing another read per file.

### Scenario 2: Open or refresh the Chat Customizations management editor for an agent-host harness

- Critical path: The editor renders a loading migration state and awaits all enabled category computations before updating migration cards and shortcuts. AgentFiles is enabled by default, so its complete scan participates in every refresh.
- Scaling input: Number of local/user agent files; repeated refresh events from prompt changes, harness/session changes, configuration changes, and customization/MCP changes can start additional full scans.
- Effective concurrency: N file parses run concurrently inside each AgentFiles computation. Refresh sequencing discards stale results but does not cancel or coalesce their I/O, so overlapping refreshes can have aggregate concurrency above N.
- Cache behavior: Agent URI discovery can become cached because editor listeners initialize prompt-file events. File contents for closed models are still reread and reparsed on every refresh; there is no AgentFiles result or in-flight scan cache.
- Mechanism confidence: High: editor refresh call sites, stale-result-only sequencing, and direct unbounded reads are explicit.
- Magnitude uncertainty: Most users may have few agents, but repositories and user profiles can aggregate many files, and remote providers increase latency. Exact refresh overlap depends on emitted events.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts:84-102</code>: Read and parse every local/user agent file to detect the handoffs header; cardinality: N reads per refresh, potentially multiplied by overlapping event-triggered refreshes.
    - Introduced by diff: true; previous behavior: Editor migration refreshes did not inspect every agent file's contents for this category.; critical-path effect: Blocks completion of the editor's migration loading state and availability of migration cards/shortcuts, while consuming filesystem and parser resources alongside normal editor work.
- Verdict: Covered by the reported bounded/cached-discovery finding; no separate duplicate finding.

### Scenario 3: Confirm in-place migration of selected agent files

- Critical path: After confirmation, each selected file is read, transformed, and written before the completion notification; an explicit migration refresh then verifies remaining candidates.
- Scaling input: Number and size of user-selected candidate agent files and number of handoff entries in each file.
- Effective concurrency: The migration loop is sequential, giving bounded filesystem concurrency of one; the post-write discovery refresh uses the AgentFiles scan behavior described above.
- Cache behavior: Migration intentionally rereads current file contents to avoid transforming stale discovery content. There is no write cache; changed-file events are suppressed during writes and one explicit refresh follows successful in-place migration.
- Mechanism confidence: High.
- Magnitude uncertainty: Selection sizes are user-controlled, but this is an explicit, infrequent migration action and sequential I/O bounds resource pressure.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigration.ts:135-137</code>: Read and overwrite each selected agent file in place; cardinality: One read and one write per selected file, sequentially.
    - Introduced by diff: true; previous behavior: No in-place agent handoff migration existed.; critical-path effect: User-confirmed migration waits for all selected writes; this is expected for completion and error reporting.
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts:1665</code>: Refresh candidate discovery after migration; cardinality: One explicit full category refresh after a successful in-place migration, plus file-system events suppressed while writes are in progress.
    - Introduced by diff: true; previous behavior: Refresh was awaited only when original files were deleted; in-place migration did not exist.; critical-path effect: Awaited before the success notification and reveal action.
- Verdict: No separate finding: the per-selected-file read/write cost is necessary and bounded; the post-write scan is subsumed by the discovery finding.

### Scenario 4: Migrate agents through existing user-data or configured-location categories

- Critical path: For selected agent customizations, the already-read source content is additionally parsed and rewritten before the existing destination write/delete flow.
- Scaling input: Number and byte size of selected agent files, and handoff count per file.

- Mechanism confidence: High.
- Magnitude uncertainty: Selected migration sets are usually small; very large files increase transient string allocation but the sequential path bounds peak memory.
- Expensive boundaries:

- Verdict: No finding: added linear parsing/allocation is required for the requested transformation, does not add an I/O boundary, and occurs only during an explicit migration.
