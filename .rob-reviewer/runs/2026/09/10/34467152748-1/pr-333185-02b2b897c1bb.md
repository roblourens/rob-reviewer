# Performance review: editor: Balance auto-closing brackets

[PR #333185](https://github.com/microsoft/vscode/pull/333185) at `02b2b897c1bb337cb23d6fb8a6fc19a6324383a3`

## Findings (1)

### 1. [medium] Avoid building the whole bracket AST on an opener keystroke

**Finding ID:** `PERF-4A44BBEB98AF`  
**Location:** <code>src/vs/editor/common/cursor/cursorTypeEditOperations.ts:253</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** main-thread document token scanning, AST node allocations, and retained bracket-tree objects  
**Scaling:** Cold cost grows linearly with document text/tokens and bracket count, up to the 5,000,000-character AST cutoff. It occurs once per cold model; warm calls avoid rebuilding the whole tree, while multi-cursor typing adds one query per cursor after that initial build.  
**Outcome:** blocked input critical path with CPU/allocation pressure and retained model memory  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Auto-closing decisions did not request the bracket-pair AST. When colorization was disabled and guides were off, typing an opener left the lazy tree unbuilt and performed only the existing local line/token checks.  
**Changed behavior:** An opening-bracket keystroke now requests the bracket-pair tree. On a cold model this synchronously tokenizes/parses the entire document into an AST and retains it, before the query can decide whether token-aware data is usable.  
**Confidence:** 0.98 — The input call path is direct, the tree's lazy-construction guard and 5,000,000-character limit are explicit, and BracketPairsTree's constructor calls parseDocument over the text buffer when the tree is absent. The disabled colorization provider returns without requesting brackets and bracket guides default off, establishing a realistic cold-tree state. Exact pause duration varies by document and hardware.

**Causal diff evidence:** The added RIGHT-side call at cursorTypeEditOperations.ts:253 invokes hasUnmatchedClosingBracketAfter from the opener-typing loop. That new API sets bracketsRequested=true and calls updateBracketPairsTree before testing token accuracy; when no tree exists, updateBracketPairsTree constructs BracketPairsTree synchronously for every model up to 5,000,000 characters.

With bracket-pair colorization/guides disabled (or another editor/model where no bracket consumer has run), the first \`{\`, \`\[\`, or \`(\` in a multi-megabyte file can pause typing while up to 5 MB is parsed and a proportional AST is allocated and retained. This defeats the responsiveness benefit of disabling bracket visualization; the waste is especially clear while background tokenization is incomplete because the result is not used.

**Evidence:** AutoClosingOpenCharTypeOperation calls the query synchronously while producing edits. BracketPairsTextModelPart.hasUnmatchedClosingBracketAfter sets bracketsRequested and calls updateBracketPairsTree; updateBracketPairsTree creates BracketPairsTree when absent for documents &lt;= 50,000\*100 characters. Its constructor parses the text buffer with parseDocumentFromTextBuffer/FastTokenizer, whose parser walks tokens and constructs AST nodes. Only after this construction does BracketPairsTree.hasUnmatchedClosingBracketAfter check hasAccurateTokensForLine(lastLine) and potentially return false. ColorizedBracketPairsDecorationProvider does not request the tree when colorization is disabled, and bracket guides default to false.

**Suggested direction:** Keep whole-document tree creation off the keystroke path: query only an already-available token-aware tree and schedule/build it outside input handling, or at least check full-model token accuracy and tree availability before setting bracketsRequested/updateBracketPairsTree so an unusable AST is not constructed synchronously.
