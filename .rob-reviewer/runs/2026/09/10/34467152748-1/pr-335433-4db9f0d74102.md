- Critical path: The existing refresh awaits the Copilot model-catalog network request and Codex catalog refresh in parallel before publishing models; the diff adds only local billing normalization reuse and schema construction after the same response arrives.
- Scaling input: Number of returned picker-eligible models; each model receives one constant-size context schema at most.
- Effective concurrency: The two authoritative catalog refreshes remain under the existing sequencer and run through Promise.all; the diff adds no request concurrency.
- Cache behavior: The resulting schemas are retained in the existing in-memory \_models catalog. Warm reads use that catalog; retry/backoff and last-known-good behavior are unchanged.
- Mechanism confidence: High: the changed map body and unchanged request placement directly establish constant local work per returned model.
- Magnitude uncertainty: The model count varies by entitlement, but schema work is linear with a realistically small catalog and has no added boundary calls.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_refreshCopilotModels</code>: Fetch the authoritative Copilot model catalog.; cardinality: One request per existing refresh attempt, independent of model count; retries retain the existing bounded backoff.
    - Introduced by diff: false; previous behavior: The same catalog request and refresh sequencing occurred before the diff.; critical-path effect: Awaited before the refreshed model list is published.
  - subprocess/IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_refreshModels/\_refreshCodexModels</code>: Refresh native Codex models through the existing app-server path.; cardinality: One existing refresh operation per catalog refresh.
    - Introduced by diff: false; previous behavior: Unchanged by this diff.; critical-path effect: Runs in parallel with the Copilot catalog fetch and is awaited before publishing the combined list.
- Verdict: No reportable regression: no new network/subprocess fan-out, unbounded retention, or critical-path scheduling change.

### Scenario 3: Changing Codex context size on a materialized thread, then sending the next message

- Critical path: A real context-size change marks the thread for reload. On the next send, thread/unsubscribe and thread/resume are awaited before turn/start so app-server applies the launch-only compaction boundary; the asynchronous MCP inventory refresh is not awaited by the turn.
- Scaling input: Actual context-size changes for one live chat, not messages or history items. Multiple changes before the next send collapse into the same needsResume/unsubscribeBeforeResume booleans.
- Effective concurrency: The session resumePromise coalesces concurrent resume demand, and the send path waits for one resume before the turn. The MCP inventory list is started asynchronously after resume and may paginate according to server count.
- Cache behavior: Warm turns with unchanged context perform no reload. A changed value invalidates the loaded thread configuration once; after resume, subsequent turns reuse the loaded thread. The selected size is validated against the warm model schema.
- Mechanism confidence: High: the changed comparison, boolean coalescing, resume loop, and test-observed request sequence directly establish the path and cardinality.
- Magnitude uncertainty: IPC duration and MCP page count depend on app-server state and configured servers, but the first-turn delay after a change is bounded to one coalesced reload and is necessary to apply the requested launch-only setting.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_changeModel/\_resumeSession</code>: Unsubscribe the loaded thread so conflicting launch overrides can be replaced.; cardinality: At most one thread/unsubscribe before the next successful resume, even if the picker changes repeatedly before sending.
    - Introduced by diff: true; previous behavior: Same-provider model/config changes did not trigger this unsubscribe unless another existing launch-only setting independently required reload.; critical-path effect: Awaited on the first turn after an actual context-size change.
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_resumeSession</code>: Resume the same persisted history with the new model\_context\_window.; cardinality: One coalesced thread/resume after the change, with existing reconnect retries only on connection replacement/failure.
    - Introduced by diff: true; previous behavior: No context-size feature existed in Codex, so this reload was absent.; critical-path effect: Awaited before turn/start; required because app-server ignores conflicting overrides on an already-loaded subscribed thread.
  - IPC at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_refreshMcpInventory</code>: List MCP server status after the resumed thread loads.; cardinality: One asynchronous listing per resume, paginated by the existing server cursor.
    - Introduced by diff: true; previous behavior: This listing already followed every resume; the diff causes one additional resume/listing only when context size actually changes.; critical-path effect: Fire-and-forget after resume; not awaited before turn preparation, though it shares the IPC transport.
  - IPC/network at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_sendMessage turn/start path</code>: Start the provider turn after configuration is current.; cardinality: One existing turn/start per message.
    - Introduced by diff: false; previous behavior: The turn started directly when no other reload condition applied.; critical-path effect: Still follows required session preparation; request count is unchanged.
- Verdict: No finding: the added one-time latency is bounded, coalesced, deferred until use, and required to preserve history while applying a launch-only context setting.
