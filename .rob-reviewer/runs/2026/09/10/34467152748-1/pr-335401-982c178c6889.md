### Scenario 1: Open or restore the Agents Changes editor with sessions.changes.cardView enabled

- Critical path: The startup contribution reads the already-loaded configuration and registers the custom pane; opening then creates SessionChangesEditorInput, which lazily delegates to the same MultiDiffEditorInput and must resolve all file models before its view model is applied. Registration itself has no I/O and is not a new blocking boundary.
- Scaling input: Number N of changed files in the active session; model resolution performs up to 2N original/modified resource references, while visible diff-editor DOM remains virtualized.
- Effective concurrency: The unchanged MultiDiffEditorInput maps all resources to promises, resolves each original/modified pair with Promise.allSettled, and awaits all file promises with Promise.all. The wrapper introduced for card mode adds no additional model-resolution pass or limiter change.
- Cache behavior: SessionChangesEditorInput creates and retains one lazy inner MultiDiffEditorInput per input. Repeated getViewModel calls reuse its LazyStatefulPromise; warm text models are reused through model references. The card setting is read once at startup as documented.
- Mechanism confidence: High: the changed service routes card mode through the custom input, and that input directly delegates to a single unchanged MultiDiffEditorInput.
- Magnitude uncertainty: Actual provider latency and warm-model hit rate vary by resource scheme and workspace, but the PR does not change their count or scheduling.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:\_createModel (lines 203-279)</code>: Resolve original and modified text-model references for each changed file through ITextModelService; cardinality: Up to two model-reference resolutions per changed file, launched across N files; cache/provider behavior can make warm resolutions cheaper.
    - Introduced by diff: false; previous behavior: The plain multi-diff editor already constructed MultiDiffEditorInput and used this identical model-resolution path; the new SessionChangesEditorInput delegates to one inner MultiDiffEditorInput rather than duplicating it.; critical-path effect: All document promises complete before the multi-diff model is returned and the editor view model is applied.
- Verdict: No reportable regression: the extra wrapper/header UI is bounded per editor, while expensive per-file model resolution, concurrency, and caching are unchanged.

### Scenario 2: Scroll a card-style stacked multi-file diff

- Critical path: Scroll layout renders only virtualized multi-diff items near the viewport. A bound item creates one DiffEditorWidget and its card CSS/unchanged-region widgets; offscreen unfocused bindings are released and templates are pooled with a cap of five unused templates.
- Scaling input: Visible/buffered diff items rather than total changed-file count, plus the number of unchanged regions inside those bound files.
- Effective concurrency: Rendering and browser layout run synchronously on the UI thread; no subprocess, IPC, filesystem, database, or network operation is added by card styling or class-name construction.
- Cache behavior: Virtualized templates are reused; offscreen bindings are cleared unless focused, and at most five unused templates remain pooled per template type. CSS and variant configuration are static.
- Mechanism confidence: High: VirtualizedItemManager disposal/pooling and the changed DiffEditorItemTemplate wiring establish the lifecycle.
- Magnitude uncertainty: Viewport buffer size and unchanged-region density vary, but ownership is explicitly bounded by virtualization and pooling.
- Expensive boundaries: none found
- Verdict: No reportable regression: the diff adds static classes, borders, and bounded DOM to already-rendered items without defeating virtualization or adding a layout read-after-write loop.

### Scenario 3: Expand, collapse, or drag hidden unchanged-line regions in card mode

- Critical path: The interaction updates UnchangedRegion observables, hidden areas, view-zone positions, labels, and scroll anchoring synchronously. Card mode intentionally retains the 40px control so collapse remains available and layout does not jump.
- Scaling input: R unchanged regions in currently bound diff editors; each region has paired original/modified view zones, with only the visible side exposing the interactive card content.
- Effective concurrency: Observable reactions and editor layout are serialized on the UI thread. No external boundary is reached.
- Cache behavior: Card mode short-circuits shouldHideControls in the view-zone collection, so toggling does not tear down and reconstruct all overlay widgets. Existing widgets update their labels/icons; fully revealed regions skip breadcrumb lookup. Disposal follows the bound DiffEditorWidget lifecycle.
- Mechanism confidence: High: changed lines keep controls present, while surrounding derived ownership and virtualization bound them and eliminate rebuilds on each toggle.
- Magnitude uncertainty: Files with exceptionally many separated hunks increase retained per-region DOM and layout rows, but that row is required by the new collapse UX and avoids reconstruction; no evidence establishes harmful magnitude under realistic viewport-bound use.
- Expensive boundaries: none found
- Verdict: No reportable regression: retained per-region controls are an intentional bounded scheduling/layout tradeoff and avoid repeated widget reconstruction; there is no high-confidence performance bug.

### Scenario 4: Workbench startup with card mode disabled (default)

- Critical path: The BlockStartup contribution is instantiated as before, reads one boolean setting, and immediately returns without registering the custom editor when neither single-pane nor card mode is enabled.
- Scaling input: Constant per-window startup work, independent of sessions or changed files.
- Effective concurrency: Synchronous configuration lookup only; no new asynchronous work or external boundary.
- Cache behavior: Configuration is already available through IConfigurationService and read once; no cache or retained collection is introduced.
- Mechanism confidence: High: the changed constructor condition and default-false registration are explicit.
- Magnitude uncertainty: The exact lookup duration is unmeasured but constant and trivial compared with startup registration.
- Expensive boundaries: none found
- Verdict: No reportable regression: default startup adds only a constant in-memory configuration read and preserves the early return.
