# Performance review: agentHost: improve Agent Merge CI diagnostics

[PR #335501](https://github.com/microsoft/vscode/pull/335501) at `27a14a419cb9a60b96b2da3e68bc27a57814d8a4`

## Findings (3)

### 1. [medium] Collapse duplicate revalidation on every evidence page

**Finding ID:** `PERF-2B55639C0A64`  
**Location:** <code>src/vs/platform/agentHost/node/agentMergeTools.ts:144</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** GitHub GraphQL/REST requests and serialized network round-trip time  
**Scaling:** At least five remote requests per evidence page, multiplied by range pages or each 50,000-line search page; jobs pagination increases the count further.  
**Outcome:** Increased latency, excessive network/API I/O, and lower diagnostic throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there were no paginated cached-evidence reads; reading CI was a single pass. The new continuation path was intended to reuse cached logs, but it now pays repeated remote validation on every response page.  
**Changed behavior:** Every cached tail/range/search request first performs the outer authoritative core refresh, then lists workflow runs and jobs, then line 144 performs a second authoritative core refresh and line 145 lists workflow runs a second time before serving local cached text.  
**Confidence:** 0.99 — All five awaited boundaries are directly traced in the changed call path and authoritative refresh bypasses the warm resource result. The exact latency is network-dependent, but the request multiplicity is deterministic.

**Causal diff evidence:** RIGHT lines 144-145 add a second authoritative head refresh and second workflow-run listing after the same request already performed those operations on RIGHT lines 81 and 140.

Inspecting a cached long log is dominated by serial GitHub round trips rather than local range/search work, consuming API capacity and adding latency to every continuation; pagination multiplies this cost and can approach the three-minute call deadline.

**Evidence:** \_readFailedCI calls \_validateCIHead before dispatch at line 81. \_readCIEvidence then awaits \_ciRuns at line 140 and \_ciJobs at line 141, followed by the added \_validateCIHead at line 144 and another \_ciRuns at line 145. \_validateCIHead uses authoritative:true, which forces PullRequestResourceService.\_refreshFragment to call PullRequestQueryService.fetch; \_ciRuns and \_ciJobs each call paginated GitHub REST APIs. Thus a one-page local range/search read performs at least five serialized network requests (two core, two runs, one jobs). The added 500,000-line search test requires 10 pages, making this at least 50 requests for one cached-log search.

**Suggested direction:** Perform one coherent authorization snapshot per evidence request: keep one authoritative head refresh, fetch runs once and jobs once, and use those same results for both authorization and attempt checks. Reserve post-operation revalidation for paths that actually cross a slow mutable boundary such as downloading a new log.

### 2. [medium] Avoid downloading evidence that this page cannot retain

**Finding ID:** `PERF-C208F68B2A6A`  
**Location:** <code>src/vs/platform/agentHost/node/agentMergeTools.ts:225</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub network bytes, full-log strings/allocations, redaction CPU, and line-indexing CPU  
**Scaling:** The waste is one candidate log per cache-limited page transition; its cost grows up to the 16 MiB/job cap and repeats as the failed-job set spans additional 32 Mi-character cache pages.  
**Outcome:** Excessive network I/O, CPU/GC pressure, and increased summary latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous summary loop downloaded each failed job log once and emitted its bounded prefix directly; there was no cache-admission failure that caused the same job to be downloaded again on a continuation page.  
**Changed behavior:** Summary paging now downloads and fully redacts a job log before asking tryAdd whether that log fits alongside the evidence IDs already retained for the page. If retained logs plus this log exceed the 32 Mi-character cache budget, tryAdd returns undefined and the loop breaks without caching or advertising the downloaded log.  
**Confidence:** 0.99 — The admission checks and unchanged loop index make the duplicate download deterministic, and the PR's 12 MiB paging fixture supplies a realistic size/cardinality trigger; only actual network duration varies.

**Causal diff evidence:** RIGHT line 225 newly performs the job-log download inside a page loop whose following RIGHT-side tryAdd can reject the result without advancing the page index.

Large-log summary pages waste a full GitHub log transfer plus whole-log decoding, redaction, and line indexing at every cache boundary. Four 12 MiB jobs waste 12 MiB; eight near-16 MiB jobs can waste three downloads (about 48 MiB and up to 90 seconds of download deadlines), increasing latency and risking the three-minute tool timeout.

**Evidence:** canAdd(retainedEvidence) at line 221 checks only the already-retained entries, not the unknown candidate size. The changed line 225 then performs the up-to-16 MiB network download and redaction; tryAdd at line 227 rechecks with log.text.length and can return undefined at line 228. Because index is not advanced, the continuation retries that same job. The added test fixture explicitly uses four 12 MiB logs with a 32 Mi-character cache: after two retained logs, the third is downloaded, rejected because 24+12&gt;32 Mi, and downloaded again on the next page.

**Suggested direction:** Reserve capacity using the maximum possible candidate size before starting another download, or keep the just-downloaded redacted log in a bounded pending slot/continuation so the next page can admit it without redownloading it.

### 3. [medium] Do not serialize unrelated sessions behind one CI read

**Finding ID:** `PERF-291707085D75`  
**Location:** <code>src/vs/platform/agentHost/node/agentMergeTools.ts:40</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Agent-host CI-read execution slots and wall-clock time while network downloads occupy the sole slot  
**Scaling:** Effective concurrency is fixed at one process-wide; wait time grows with the sum of preceding sessions' validation, annotation, and up-to-16 MiB log downloads, with each queued caller timing out after 180 seconds including queue wait.  
**Outcome:** Head-of-line blocking, increased latency, and collapsed cross-session throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The prior readFailedCI implementation had no process-wide queue, so independent authorized sessions could perform their GitHub reads concurrently subject to the existing transport scheduler/rate limiter.  
**Changed behavior:** A single Queue instance owned by AgentMergeTools limits all readAgentMergeCI calls in the agent-host process to concurrency one, regardless of session, repository, or evidence scope. The three-minute deadline starts before admission to that queue.  
**Confidence:** 0.98 — The queue ownership and degree-one semantics are direct, and the new test demonstrates cross-session timeout behavior. The prevalence of simultaneous sessions is uncertain, which limits severity, but the mechanism and worst-case impact are explicit.

**Causal diff evidence:** RIGHT line 40 introduces one process-wide degree-one Queue, and all session reads are newly enqueued through it at RIGHT line 67.

One slow or stalled repository blocks diagnostics for every other active Agent Merge session in the host; unrelated reads can wait their entire deadline and fail without issuing any request.

**Evidence:** The changed field at line 40 constructs one Queue for the composition, and line 67 routes every session through it. A summary can sequentially download multiple 16 MiB logs with 30-second per-download deadlines. The added cross-session tests confirm maximumActive=1 and explicitly confirm that when one read occupies the queue for 180 seconds, both it and a peer session waiting behind it hit the three-minute timeout while only one download ever starts.

**Suggested direction:** Serialize per CI scope/session instead of process-wide, with a small global limiter or explicit cache-capacity reservations to bound memory and network concurrency without blocking unrelated scopes behind one FIFO.

### Scenario 4: Download and redact one workflow job log

- Effective concurrency: Transport uses the existing GitHub request queue/rate limiter. Agent Merge additionally serializes these downloads both within a summary and globally across read calls.
- Cache behavior: Transport requests use no-store for the body; successful redacted logs are cached only by AgentMergeCIEvidenceStore. Redaction failure or cache-admission rejection leaves no reusable result.
- Mechanism confidence: High for the changed 8x bound and linear processing; insufficient evidence that the bounded intentional cost alone is a bug.
- Magnitude uncertainty: Large logs incur materially more allocation than the former cap, but this is an intentional requirement and the work is bounded; no independent regression beyond the reported discarded-download case was established.
