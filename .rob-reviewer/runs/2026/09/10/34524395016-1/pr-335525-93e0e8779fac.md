## Findings (1)

### 1. [medium] Bound stdin before copying it into review UI state

**Finding ID:** `PERF-14B61121C0DB`  
**Location:** <code>src/vs/platform/agentHost/node/codex/codexGuardianReview.ts:157</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** String bytes and allocations in Markdown formatting, AHP protocol payload bytes, retained chat/replay objects, and rendered Markdown nodes.  
**Scaling:** Cost is O(n) in the unbounded stdin length for formatting and retention, and broadcast serialization scales further with the number of connected relevant clients; one denial emits the large content in a durable Markdown action and again through tool-call actions.  
**Outcome:** Synchronous CPU/GC pressure and UI rendering latency, with retained chat memory proportional to the stdin payload.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, the protocol union and summary switch had no \`writeStdin\` action, so terminal-input payloads were not copied into durable Markdown or approval-card messages by this path.  
**Changed behavior:** Denied, timed-out, or aborted write-to-stdin reviews now surface the complete stdin payload as UI detail. \`\_handleGuardianReviewCompleted\` synchronously formats that detail into Markdown and also sends it as both the tool-call intention and invocation message.  
**Confidence:** 0.96 — The added branch, unbounded string type, and call path are explicit: \`summarizeGuardianReviewAction\` feeds \`formatGuardianDenialNotification\`/\`formatGuardianReviewStatusNotification\`; the denial path emits a durable \`ChatResponsePart\` and two tool-card actions; the state reducer retains both response and invocation text; \`ProtocolServerHandler\` broadcasts each envelope. Only the prevalence and typical size of large interactive stdin payloads is uncertain.

**Causal diff evidence:** The added \`case 'writeStdin'\` at line 157 assigns the entire unbounded \`action.stdin\` string to the display \`detail\`; the preceding SDK type diff adds \`writeStdin\` to \`GuardianApprovalReviewAction\`, so this is a newly reachable path.

If an agent sends a large script, generated data, or other bulk content to an interactive process and guardian denies or times out the write, the agent-host performs synchronous full-input scans/copies and the workbench receives and renders the entire payload. This can stall the review UI, increase IPC cost, and retain substantial duplicate text in chat/replay state.

**Evidence:** \`GuardianApprovalReviewAction\` newly permits \`{ type: 'writeStdin', stdin: string }\` with no size limit. At line 157 the full string becomes \`summary.detail\`. \`formatGuardianDenialNotification\` then calls \`trim\`, scans all text with \`/\`+/g\`, interpolates another full Markdown string, and prefixes every line. \`\_handleGuardianReviewCompleted\` stores that Markdown as a durable response part and reuses the raw detail in \`ChatToolCallStart\` and \`ChatToolCallReady\`; each action is dispatched into chat state and broadcast over the AHP transport. Thus one denied large stdin write creates multiple O(n) strings, protocol payloads, retained state entries, and a large Markdown render.

**Suggested direction:** Create a bounded, escaped preview for the \`writeStdin\` summary (with a truncation indicator) before it reaches Markdown/tool-card state, while keeping the original \`params.action.stdin\` only for the exact \`approveGuardianDeniedAction\` round-trip.
