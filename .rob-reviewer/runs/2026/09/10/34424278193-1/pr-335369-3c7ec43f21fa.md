<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** eager-work, repeated-work, boundary-fanout

### Scenario 1: TypeScript extension activation and TS7 experiment prompt eligibility

- Critical path: The extension constructs the TAS service and invokes suggestNativePreview without awaiting it, so eligibility, treatment resolution, notification UI, and persistence are off the synchronous activation critical path. Eligible users wait asynchronously for the already-started TAS initial fetch before the notification can appear.
- Scaling input: One execution per extension-host activation. Installed-extension checks have a fixed cardinality of three IDs; there is no dependence on files, documents, or workspace folders.
- Effective concurrency: One ExperimentationService and one unawaited suggestion task are created per extension-host activation; there is no per-document or per-workspace-folder fan-out.
- Cache behavior: The treatment lookup requests checkCache=true after awaiting the TAS service's initial fetch. The global dismissal state is persisted, although the changed commented-out return currently does not suppress later eligible prompt attempts. Extension and configuration checks use VS Code's in-memory APIs; no new cache is needed for their fixed number of lookups.
- Mechanism confidence: High confidence from the direct activate call path, the unawaited async invocation, TAS initialFetch construction, and explicit globalState operations.
- Magnitude uncertainty: Actual TAS fetch duration and notification frequency vary, but the fetch was already present and remains off the activation critical path. The newly repeated cached lookup/state write is constant-sized and once per session, so it does not establish meaningful latency, throughput, CPU, or I/O degradation.
- Expensive boundaries:
  - network at <code>extensions/typescript-language-features/src/experimentationService.ts:createTasExperimentationService</code>: TAS experimentation service initialFetch; cardinality: One initial fetch per TypeScript extension activation, independent of plugin count and workspace size.
    - Introduced by diff: false; previous behavior: The same ExperimentationService was constructed before the diff and started the same initialFetch on every activation.; critical-path effect: suggestNativePreview waits for it before showing the prompt, but activate does not await suggestNativePreview, so it does not block extension activation.
  - IPC at <code>extensions/typescript-language-features/src/ui/suggestNativePreview.ts:context.globalState.update</code>: Persist the prompt dismissal/terminal eligibility state; cardinality: At most one small boolean update per activation when the installed/configured gate matches or after the prompt closes. Because the dismissal return is commented out, dismissed eligible users can repeat the post-prompt update on later activations.
    - Introduced by diff: true; previous behavior: The prior dismissal key returned before further work on later activations; equivalent writes already occurred once when the prior prompt completed or an installed native-preview extension was found.; critical-path effect: Awaited only inside the unawaited suggestion task, so it does not block extension activation; the state payload is constant size.
  - network at <code>extensions/typescript-language-features/src/ui/suggestNativePreview.ts:workbench.extensions.installExtension / vscode.env.openExternal</code>: Install the selected TypeScript extension or open the learn-more URL after explicit user selection; cardinality: Zero or one user-triggered operation per displayed prompt.
    - Introduced by diff: false; previous behavior: The previous prompt exposed the same install-extension and external-link boundaries; the link target/text changed but boundary cardinality did not.; critical-path effect: Occurs only after explicit interaction and is not on extension activation's critical path.
- Verdict: No reportable performance regression. Ignoring the dismissal flag is a functional/UX issue; its independent performance cost is only bounded off-critical-path work once per activation.

### Scenario 2: Checking registered TypeScript server plugins before offering TypeScript 7

- Critical path: For prompt-eligible normal-mode users, pluginManager.plugins is read synchronously during activation-time eligibility. On the same normal registration path, lazilyActivateClient already reads pluginManager.plugins synchronously, so the diff moves the existing cached initialization slightly earlier rather than adding a second full scan.
- Scaling input: The initial scan scales with installed extensions plus contributed TypeScript server plugin entries. Effective cardinality remains one scan on the normal activation path; TS7-enabled/configured users return before this new read.
- Effective concurrency: A single synchronous scan initializes the PluginManager cache. Later reads use the cached map; extension-change rescans are serialized by VS Code events and are pre-existing behavior.
- Cache behavior: PluginManager memoizes its extension-to-plugins map. The new eligibility read warms that cache before lazilyActivateClient consumes it. On extension changes the existing manager invalidation path rebuilds the map; the diff does not add a listener or duplicate rebuild.
- Mechanism confidence: High confidence from PluginManager.plugins memoization and the immediate pre-existing plugins read in lazilyActivateClient.
- Magnitude uncertainty: Users may have many extensions, but the diff does not increase effective scan count on the reachable normal path.
- Expensive boundaries: none found
- Verdict: No regression: the collection-wide scan is pre-existing on this activation path and remains coalesced by the PluginManager cache.

### Scenario 3: Native TypeScript extension detection during activation, extension changes, commands, and version selection

- Critical path: Detection consists of synchronous VS Code extension-registry lookups. The array now contains three IDs instead of two, affecting initial conditional registration, extension-change reevaluation, explicit enable commands, and version-picker construction.
- Scaling input: Fixed cardinality grows from at most two to at most three extension ID lookups per check, independent of workspace size and extension count.
- Effective concurrency: Checks run synchronously once per triggering activation/event/command; no tasks, queues, subprocesses, or fan-out are introduced.
- Cache behavior: VS Code owns the extension registry and configuration state. Lookups are in-memory API reads; the changed code adds one fixed ID rather than an unbounded cache or collection.
- Mechanism confidence: High confidence from the constant tsNativeExtensionIds array and all located getTsNativeExtension/requireHasVsCodeExtension call sites.
- Magnitude uncertainty: Registry implementation cost is not measured, but the fixed one-lookup increase cannot support a realistic user-visible performance impact.
- Expensive boundaries: none found
- Verdict: No reportable performance issue; the additional fixed registry lookup is negligible and does not cross an expensive boundary.

**Summary:** Completed the performance pass over all six changed files. Traced activation/prompt scheduling, TAS fetch and persistence boundaries, plugin scan caching, and native-extension detection. No high-confidence actionable performance regression was introduced, and the PR does not itself prove a shipped performance-regression fix.
