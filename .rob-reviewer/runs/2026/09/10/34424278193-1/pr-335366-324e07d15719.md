# Performance review: chat: Show MCP server error details in customizations

[PR #335366](https://github.com/microsoft/vscode/pull/335366) at `324e07d15719037092f9c28704c5ce3003fe143c`

## Findings (2)

### 1. [medium] Bound error text before laying it out inline

**Finding ID:** `PERF-57EE47DD561E`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts:383</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Error-message bytes, DOM text/ARIA/hover state, and browser text wrapping and row-height calculation  
**Scaling:** Cost grows linearly with the unbounded error string and its wrapped line count. The full value is assigned to the row, hover, and ARIA label; dynamic-height measurement then synchronously computes the potentially enormous wrapped height, and width changes repeat wrapping.  
**Outcome:** Long UI-thread stalls, excessive memory/layout work, and an extremely tall Customizations scroll surface for verbose server failures.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Errored servers remained fixed-height rows showing a compact status indication; arbitrary error payload text was not inserted into or measured by the Customizations list.  
**Changed behavior:** The renderer now assigns the complete raw error message to textContent and the accompanying CSS uses pre-wrap, overflow-wrap:anywhere, and visible overflow, so no display or measurement bound remains.  
**Confidence:** 0.98 — The unbounded upstream sources, direct full-text assignment, no-clipping CSS, and synchronous dynamic-height measurement are all directly traced. Payload prevalence and exact duration vary, which limits severity to medium.

**Causal diff evidence:** RIGHT line 383 newly assigns the unbounded error string to the visible description; before this PR error payloads were not rendered in the row.

Opening Customizations after an HTTP MCP endpoint returns a large error body, or after an SDK reports verbose startup diagnostics, can freeze or severely jank the editor while that full payload is wrapped and measured.

**Evidence:** The new assignment at line 383 uses the complete value returned by getMcpErrorMessage without slicing. The same value is retained in the managed hover and included in the ARIA-label observable. The new dynamic list measures rows with offsetHeight. Upstream payloads are explicitly unbounded strings: Codex/Copilot pass SDK error strings directly, while extHostMcp.ts:655 builds a native connection error from await res.text(), which reads the entire HTTP response body. A misconfigured MCP URL can therefore place a large HTML/error response directly on this layout path.

**Suggested direction:** Cap the inline/ARIA preview by bytes or lines before DOM assignment and constrain row height, while preserving access to the complete diagnostic through Show Output or an explicit on-demand expansion that performs the large layout only when requested.

### 2. [medium] Avoid recomputing every server label on each update

**Finding ID:** `PERF-E9FB17579A2F`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts:1747</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** UI-thread CPU, temporary server-presentation objects, and DOM height measurements  
**Scaling:** With N installed host-backed servers, one customization event reads N labels; each label rebuilds and searches the N-server presentation snapshot, yielding O(N²) allocation/search work. The resulting rerender also invalidates N heights and measures visible rows. Startup/status bursts repeat the eager work; only the later animation-frame layout is coalesced.  
**Outcome:** Increased UI-thread latency, CPU/GC pressure, and potential dropped frames while the Customizations page is visible.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** ARIA observables were created and subscribed only when AccessibiltyRenderer rendered viewport rows, and status updates did not force a section-wide rerender.  
**Changed behavior:** A new section autorun reads every cached row label on any shared customization/session change, marks the whole list for remeasurement, and schedules rerender.  
**Confidence:** 0.97 — The all-entry loop, per-label full snapshot construction, global event dependency, and synchronous measurement path are directly established. Only the exact duration for a user's installed-server count is uncertain.

**Causal diff evidence:** RIGHT line 1747 newly executes label?.read(reader) for every section entry, converting viewport-limited label evaluation into all-entry work on each observed update.

With many installed MCP servers, startup, failure, recovery, or enablement updates can repeatedly delay interaction and rendering on the Customizations page.

**Evidence:** Lines 1746-1748 loop over every row label. getMcpEntryAriaLabel at lines 1785-1811 reads the global change signal and calls getMcpServers(...).find(...) for host rows. getMcpServers at agentHostCustomizationService.ts:232-255 flattens, filters, and maps the full snapshot per call. ListView.rerender at listView.ts:814-823 clears dynamic-height state for every item before visible-row offsetHeight probes. AccessibiltyRenderer at listWidget.ts:1313-1318 already subscribes rendered-row labels.

**Suggested direction:** Leave label subscriptions with rendered accessibility rows. Use one shared status/session subscription to request layout, and invalidate only rows whose error text or visibility changed rather than eagerly evaluating all labels and rerendering the whole list.

### Scenario 1: Open the MCP Customizations home or installed-search results with many installed servers

- Critical path: List construction creates per-entry ARIA observables, then the new section autorun immediately evaluates all of them and schedules an animation-frame section layout before the list geometry settles.
- Scaling input: N installed rows; host-backed labels each reconstruct and search an N-server snapshot, so the new eager pass is O(N²). Only roughly the allocated viewport rows are synchronously height-probed, but rerender invalidates all N cached heights.
- Effective concurrency: All observable evaluation and list measurement is serialized on the UI thread. MutableDisposable coalesces scheduled layouts to one per animation frame, but the eager all-label evaluation happens before scheduling and is not coalesced.
- Cache behavior: The WorkbenchList caches measured row heights, but the new rerender clears dynamic-height width validity for every item. getMcpServers has no presentation cache and rebuilds the flattened/mapped snapshot on every label evaluation.
- Mechanism confidence: High: the all-entry autorun, full-snapshot materialization, and ListView rerender/offsetHeight path are directly traced.
- Magnitude uncertainty: Typical installed MCP counts vary; the quadratic mechanism is certain, while noticeable jank is most likely for larger inventories or startup bursts.
- Expensive boundaries: none found
- Verdict: Reportable repeated UI-thread work introduced by eagerly reading every row label and forcing section-wide remeasurement.

- Mechanism confidence: High: raw upstream strings, full DOM assignment, no-clipping wrapping CSS, and synchronous dynamic measurement are directly traced.
- Magnitude uncertainty: Most errors are short, but a misconfigured HTTP endpoint can return a large HTML/error body and SDK error strings have no declared bound. Exact payload prevalence is uncertain; the unbounded layout mechanism is certain.
- Expensive boundaries:
