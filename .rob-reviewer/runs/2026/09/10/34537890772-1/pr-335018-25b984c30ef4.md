## Findings (1)

### 1. [medium] Avoid enumerating every branch for capability-only validation

**Finding ID:** `PERF-6AA4E779A121`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:4275</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** A remote Agent Host IPC plus Git subprocesses, including uncapped refs output and parsing  
**Scaling:** One eager completion per explicit worktree create/update; subprocess output and parsing grow with the repository's number of local branches, regardless of the 25-item post-processing limit.  
**Outcome:** Increased configure-automation tool latency and unnecessary Git CPU/I/O before persistence  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, ConfigureAutomationTool validated the static session-type capability and proceeded without provider IPC or Git branch enumeration.  
**Changed behavior:** Every explicit worktree target now calls getWorktreeOptions; Agent Host providers resolve the schema and then eagerly request empty-query branch completions even for the capability-only tool caller.  
**Confidence:** 0.98 — The new tool call path is explicit: ConfigureAutomationTool awaits getWorktreeOptions for every newly supplied worktree target and reads only supportsWorktree, while the Agent Host implementation always invokes loadBranches with an empty query. That completion runs three Git operations and getBranches executes an uncapped for-each-ref before the 25-item result limit is applied. The exact duration varies by repository and remote-host latency, but the extra critical-path work and its scaling are established.

**Causal diff evidence:** The added line \`? await loadBranches('', token)\` eagerly invokes the dynamic branch loader. The new ConfigureAutomationTool path awaits \`provider.getWorktreeOptions(...)\` for a worktree target but subsequently inspects only \`options?.supportsWorktree\`.

Creating or updating a worktree automation through the tool is blocked on avoidable remote IPC and \`git for-each-ref\`/current/default-branch subprocess work. Repositories with large branch sets pay growing output/parsing cost although validation only needs workspace support.

**Evidence:** \`ConfigureAutomationTool.resolveAvailableTarget\` awaits \`provider.getWorktreeOptions\` and only checks \`options?.supportsWorktree\`. In this implementation, dynamic schemas always execute \`loadBranches('')\`; \`AgentService.sessionConfigCompletions\` routes this to \`WorktreeIsolation.branchCompletions\`, which runs getBranches, getCurrentBranch, and getDefaultBranch. \`AgentHostGitService.getBranches\` uses \`git for-each-ref\` without a count, and the 25-item completion limit is applied only afterward.

**Suggested direction:** Provide a capability-only path (or an option that skips branch loading) for tool validation, and perform \`loadBranches\` only in the branch-picker scenario that consumes the results.


## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/platform/agentHost/node/agentService.ts:3445` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentService.ts:3448`  
**Introducing path:** `src/vs/platform/agentHost/node/agentService.ts`  
**Introducing commit:** `7c3cb26c995ce179ee9fb21e7debe7667da9f057`  
**Mechanism family:** `eager-work`  
**Performance category:** `subprocess`  
**Confidence:** 0.99

**Mechanism:** For host-generated worktree session IDs, the old code could not mark isolation pending before Codex createChat scheduled an eager prewarm. Codex then materialized a thread in the source checkout; first send had to await that stale materialization, unsubscribe it, and materialize again in the new worktree.

**Symptom:** Worktree-backed Codex sessions with host-generated IDs performed a wasted prewarm and could delay the first turn while the stale thread was cleaned up and recreated.

**Fixed behavior:** The host now mints the session URI before provider creation and marks that exact ID pending, so Codex's prewarm guard sees it and skips eager materialization until the worktree working directory is finalized.

**Evidence:** The changed `_createProviderSession` now computes `session` and calls `notePending` before `provider.chats.createChat`. Codex `_createChat` calls `_schedulePrewarm`, whose pending check suppresses `_materializeIfNeeded`; without it, `_adoptWorkingDirectoryBeforeSend` awaits and unsubscribes the stale prewarm before changing cwd. The expanded test proves both client- and host-generated IDs are pending during provider creation. Blame attributes the old conditional pending-ID logic to the supplied introducing commit.
