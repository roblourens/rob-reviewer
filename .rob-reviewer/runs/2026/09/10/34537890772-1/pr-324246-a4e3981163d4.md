## Findings (2)

### 1. [medium] Resolve the working directory only during materialization

**Finding ID:** `PERF-7F8708D05C47`  
**Location:** <code>src/vs/platform/agentHost/node/agentSideEffects.ts:1430</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** one filesystem access operation for the session working directory on every user turn  
**Scaling:** The added I/O grows linearly with the number of messages across all file-backed folder and already-materialized worktree sessions; one stat/access is performed before each send, including warm sessions.  
**Outcome:** increased turn-start latency and reduced throughput, especially when the working directory is on a slow or network-mounted filesystem  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The send path changed model/agent selections and called agent.chats.sendMessage directly; working-directory existence repair was performed when resuming a session, not before each message.  
**Changed behavior:** Every call to \_sendTurnMessage now awaits resolveWorkingDirectoryBeforeSend. Once a session is no longer pending, AgentService calls resolveWorkingDirectoryForResume, which serializes per session and awaits fs.access even for an ordinary folder that is already active.  
**Confidence:** 0.99 — The changed send path unconditionally awaits the hook for every turn; the hook routes every non-pending file-backed session through resolveWorkingDirectoryForResume, whose first operation is fs.access. The call path and per-turn multiplicity are explicit; only the absolute latency varies with filesystem type.

**Causal diff evidence:** The added line 1430 unconditionally awaits resolveWorkingDirectoryBeforeSend before every agent send; AgentService's added non-pending branch calls resolveWorkingDirectoryForResume, and WorktreeIsolation.\_resolveWorkingDirectoryForResume immediately awaits fs.access(workingDirectory.fsPath).

Each message waits for an unnecessary filesystem round trip before selection updates or the agent subprocess can receive the prompt. On remote/network-mounted repositories this can visibly delay every turn; locally it still adds repeated I/O across long chats.

**Evidence:** \_sendTurnMessage is the common user-turn path. AgentService.\_resolveWorkingDirectoryBeforeSend only skips work for workspace-less sessions; for any file URI with pending=false it calls AgentConfigurationService.resolveWorkingDirectoryForResume -&gt; WorktreeIsolation.resolveWorkingDirectoryForResume -&gt; \_resolveWorkingDirectoryForResume -&gt; fs.access. Pending is cleared after first-send resolution, so all subsequent turns still take this boundary.

**Suggested direction:** Keep repair in the actual resume/materialization path, or cache/mark the resolved directory after the first send and return it directly for live sessions. The common warm-turn path should not call resolveWorkingDirectoryForResume or fs.access.

### 2. [medium] Keep session setup work overlapped

**Finding ID:** `PERF-672FDD92989F`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:928</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** git subprocesses plus provider/session initialization and customization filesystem scans  
**Scaling:** The added serial latency is paid once per createSession with a working directory; git probe cost depends on repository/filesystem latency and customization cost grows with configured/session customization files.  
**Outcome:** longer new-session creation latency before the client receives the created session  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Provider creation and side-effect initialization ran first in parallel, then \_resolveCreatedSessionConfig and getSessionCustomizations ran together in a Promise.all, allowing git-backed config resolution and customization discovery to overlap.  
**Changed behavior:** The code now awaits \_resolveCreatedSessionConfig before starting provider.createSession, waits for provider creation, and only then starts/awaits getSessionCustomizations, turning the three setup stages into a serial chain.  
**Confidence:** 0.96 — The before/after scheduling is explicit in the diff: config resolution moved from a Promise.all after provider creation to an await before provider creation, and customization retrieval is now awaited afterward. The shared resolver's sequential git commands and customization providers' disk-backed work establish expensive boundaries; exact duration varies by repository and customization count.

**Causal diff evidence:** Added line 928 awaits \_resolveCreatedSessionConfig before the Promise.all that starts \_createProviderSession; added lines 976-981 await getSessionCustomizations only after that Promise.all. The deleted hunk ran config resolution and customization retrieval in one Promise.all after provider creation.

Creating any repository-backed session can now wait for the full git config probe, provider setup, and customization discovery in sequence. Slow repositories or substantial customization trees make the delay visible before the new chat is ready.

**Evidence:** \_withIsolationSchema calls WorktreeIsolation.resolveIsolationConfig, whose \_getGitInfo performs getRepositoryRoot followed by revParse, getCurrentBranch, and getDefaultBranch; AgentHostGitService implements these as git subprocess calls (repository-root may be cached, the other probes are not). Copilot and Claude customization resolution can perform plugin/directory discovery, while Claude/Copilot provider creation itself also performs git/project and customization setup. All are on createSession's awaited critical path after the change.

**Suggested direction:** Preserve the pending-worktree safety without serializing unrelated setup: derive/mark pending from the already-resolved isolation input when possible, keep provider creation concurrent for explicit folder sessions, and start customization retrieval as soon as the provider session exists while overlapping any remaining config/initialization work.

### Scenario 5: Archive, unarchive, dispose, or shut down worktree sessions

- Critical path: Archive/unarchive launch cleanup/recreation asynchronously after persisting the flag, so git work is off the archive action's critical path. Explicit dispose awaits provider teardown then per-session worktree removal. Shutdown awaits all providers, then removes all process-created worktrees.
- Scaling input: Per archive/unarchive operation, one session is inspected. Shutdown/removal scales with the number of worktrees created in the current host process.
- Effective concurrency: A per-session sequencer prevents lifecycle races. Archive cleanup performs metadata, access, branch, dirty-state, and removal operations sequentially. Shutdown removal uses Promise.all across session keys, while each key remains individually sequenced.
- Cache behavior: In-memory created-worktree ownership avoids metadata lookup for dispose/shutdown removal. Archive/unarchive intentionally reads persisted metadata because sessions can outlive the current process. Removed entries are deleted from the map.
- Mechanism confidence: High for lifecycle ownership, operation count, and sequencing.
- Magnitude uncertainty: The number of simultaneously process-created worktrees at shutdown is user-dependent. No evidence establishes a user-visible regression from the concurrent shutdown drain.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/shared/worktreeIsolation.ts:cleanup/recreate/resolve resume helpers</code>: Read persisted worktree metadata and archived flags; cardinality: One DB open and a three-key metadata batch for each archive/unarchive lifecycle action that reaches the controller.
    - Introduced by diff: true; previous behavior: Copilot performed equivalent work in provider-owned handlers; Codex/Claude did not manage worktrees.; critical-path effect: Off the archive/unarchive protocol action critical path because AgentSideEffects does not await it; on resume it is awaited.
  - filesystem at <code>src/vs/platform/agentHost/node/shared/worktreeIsolation.ts lifecycle helpers</code>: Check worktree/repository paths and create parent directories; cardinality: One or two checks per lifecycle operation, plus mkdir when recreating.
    - Introduced by diff: true; previous behavior: Equivalent lifecycle checks existed for Copilot only.; critical-path effect: Background for archive/unarchive, awaited for explicit dispose/resume/shutdown as applicable.
  - subprocess at <code>src/vs/platform/agentHost/node/shared/worktreeIsolation.ts cleanup/recreate/remove helpers</code>: Check branch and dirty state, remove or recreate git worktrees; cardinality: Archive of an existing clean worktree runs branch check, status, and remove; unarchive runs branch check and add; shutdown launches one remove per process-created worktree.
    - Introduced by diff: true; previous behavior: Copilot owned equivalent per-session cleanup; shared ownership extends it to new providers and centralizes shutdown cleanup.; critical-path effect: Off archive/unarchive action progress; awaited during dispose/shutdown.
- Verdict: No finding: cleanup ownership is preserved, per-session races are serialized, and archive work is off the interaction critical path.
