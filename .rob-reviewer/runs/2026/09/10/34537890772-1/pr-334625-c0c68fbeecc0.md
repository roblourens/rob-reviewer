## Findings (2)

### 1. [medium] Avoid rescanning layout for every activity row during render

**Finding ID:** `PERF-6D8F7331F1D8`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationDashboard.ts:288</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous browser geometry reads and repeated scrollbar layout work  
**Scaling:** Initial dashboard rendering performs one \`scanDomNode()\` per persisted activity entry while the DOM is incrementally growing; each scan measures the increasingly large activity tree, so cost grows with history entries and their preceding item nodes.  
**Outcome:** Opening or rerendering the Migrations dashboard can block the UI thread with repeated style/layout calculations and produce visible modal jank for larger activity histories.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no migration activity dashboard and therefore no per-history-entry geometry rescan during page construction.  
**Changed behavior:** For every activity entry, initial rendering calls \`updateDisclosure()\`, which invokes \`onDidChangeContent\`; the editor wires that callback directly to \`migrationDashboardScrollable.scanDomNode()\`. \`scanDomNode()\` synchronously reads \`clientWidth\`, \`scrollWidth\`, \`clientHeight\`, and \`scrollHeight\` before rendering proceeds to append more activity content.  
**Confidence:** 0.99 — The call path from the added line to synchronous geometry reads is direct, and the loop/write ordering is explicit. Exact milliseconds depend on retained history size and browser layout cost, which affects severity but not mechanism confidence.

**Causal diff evidence:** The added unconditional \`updateDisclosure();\` executes once for every activity entry during initial rendering and reaches the newly added \`onDidChangeContent: () =&gt; this.migrationDashboardScrollable?.scanDomNode()\` callback.

After multiple migration batches, merely opening or refreshing the dashboard interleaves DOM writes with one forced geometry measurement per entry, instead of measuring once after the complete tree is built. The uncapped persisted history makes the trigger cumulative across sessions.

**Evidence:** \`renderActivity\` calls \`updateDisclosure()\` at line 288 inside the activity loop. That function always calls \`onDidChangeContent\`; the editor callback calls \`scanDomNode()\`, whose implementation reads the element's client and scroll dimensions. Item DOM is appended immediately afterward, ensuring later iterations measure after additional writes. \`showOverview\` already emits a final content-change callback after rendering, so the per-entry calls are redundant for initialization.

**Suggested direction:** Initialize \`expandedActivity\` without notifying during construction, attach the toggle listener, and reserve \`onDidChangeContent\` for actual user toggles; rely on the existing single callback at the end of \`showOverview\` to scan after the full DOM is built.

### 2. [medium] Bound the persisted migration activity log

**Finding ID:** `PERF-A2B7BD77CA8D`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts:2460</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Persisted JSON bytes, parsed JavaScript activity/item objects, and dashboard DOM nodes  
**Scaling:** The stored array grows with every successful migration invocation and every migrated item for the lifetime of each profile/harness or workspace/harness key; no count, item, age, or byte limit is applied.  
**Outcome:** Increasing persistent-storage size and progressively higher parse, serialization, allocation, and dashboard-render costs, eventually causing slower migration completion and dashboard opening plus retained memory.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, successful migrations produced notifications and optionally revealed migrated files; they did not retain a persistent per-file activity history or render that history on later visits.  
**Changed behavior:** Each successful migration now prepends a full entry, including source and destination path strings for every item, to all prior activity and stores the complete object in profile-scoped machine storage indefinitely.  
**Confidence:** 0.98 — The append-without-limit, profile-scoped persistence, synchronous storage stringify, full-history reads, and full item render loops are directly traced. Only the rate at which individual users accumulate migrations is uncertain, so severity is medium rather than high.

**Causal diff evidence:** The added line \`activity: \[entry, ...state.activity\]\` retains every previous entry whenever a successful migration is recorded; this persistence and activity UI did not exist before the diff.

A user who performs migrations repeatedly (especially copy migrations whose sources remain eligible, or migrations accumulated over months) grows this record without bound. Every subsequent store synchronously serializes the whole history, while opening the Migrations page parses it and creates item DOM for all entries, including collapsed ones.

**Evidence:** \`recordMigrationActivity\` reads the existing state and stores \`activity: \[entry, ...state.activity\]\` with no eviction. \`getCustomizationMigrationDashboardOverview\` reparses the profile/workspace states and passes all entries to \`renderActivity\`; that method loops over every entry and every item and allocates the hidden details DOM. The storage implementation stringifies object values on \`store\`, so both stored bytes and update cost grow with history.

**Suggested direction:** Apply an explicit retention budget before storing (for example, cap total entries/items or serialized bytes and evict oldest records), and avoid retaining abandoned workspace keys; preserve recent activity and dismissal semantics within that bound.
