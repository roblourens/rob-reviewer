# Performance review: Single chat migrations setting

[PR #338756](https://github.com/microsoft/vscode/pull/338756) at `b47b75eef2b7b71bcfac1af0ba94895448d80ff0`

## Findings (1)

### 1. [medium] Keep migration discovery off every empty chat request

**Finding ID:** `PERF-556C9D09F558`  
**Location:** <code>src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:1699</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Filesystem discovery/read operations, MCP support assessment CPU work, and the 50 ms support-scope debounce  
**Scaling:** Cold work scans up to four prompt types across user and workspace locations; MCP plan reads once per distinct eligible source configuration. When no candidates are found, this entire hint computation is re-entered once per chat message, and remote/configured locations increase I/O latency.  
**Outcome:** Blocks agent dispatch and increases time to first response on each affected chat message, with additional I/O and CPU pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The old chat.customizations.migrationHint setting defaulted to Never, so ordinary agent-host requests returned before computeMigrationHint. MCP, user-data, and configured-location migrations also defaulted disabled.  
**Changed behavior:** The changed condition uses chat.customizations.migration.enabled, registered with default true, so ordinary requests now await full migration discovery; an empty result does not mark discovery as completed.  
**Confidence:** 0.98 — The changed gate, production default=true, awaited sendRequest call path, 50 ms MCP debounce, filesystem reads, and empty-result repetition are all directly established in repository code. Actual added latency beyond the guaranteed debounce varies with MCP initialization, remote filesystem speed, configured roots, and source count.

**Causal diff evidence:** The added line 1699 replaces the prior hint-mode check (whose default was Never) with ChatCustomizationsMigrationEnabled; the unified setting is registered default true in this diff.

With the new setting's production default of true, every Copilot agent-host request enters computeMigrationHint before the agent is activated. If no migration candidate exists, customizationMigrationHintShown is never set, so the same discovery runs again on every subsequent message, delaying agent invocation and time to first response.

**Evidence:** sendRequest awaits collectCustomizationMigrationHint in its Step 2 Promise.all before extension activation/agent invocation. computeMigrationHint concurrently scans user/workspace prompt files for agent, instructions, prompt, and skill types and invokes the MCP migration provider. That provider creates an AgentHostMcpServerSupportScope whose first resolution is deliberately delayed 50 ms, waits for initial MCP loading, and createPlan reads each distinct MCP source configuration via IFileService. The provider disposes the scope after each computation; the scope disposes at refcount zero, so absent another holder there is no warm MCP assessment to reuse. Prompt listings are cached/coalesced per type, but the MCP assessment/config reads repeat. The request state is committed only when a nonempty hint is shown, leaving the common empty result uncached.

**Suggested direction:** Preserve a separately default-off hint/discovery gate, or cache/coalesce the empty assessment with invalidation from onDidChangeCustomizations and run it outside the request-dispatch critical path. Ensure a request can invoke the agent without awaiting migration UI discovery.
