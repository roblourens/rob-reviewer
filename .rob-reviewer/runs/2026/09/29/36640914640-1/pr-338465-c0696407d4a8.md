## Findings (1)

### 1. [medium] Avoid cloning the options tray for every resize trial

**Finding ID:** `PERF-4F643D4AD023`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/newChatWidget.ts:1312</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Deep-cloned DOM nodes plus synchronous style/layout geometry reads  
**Scaling:** Cost grows with every ResizeObserver delivery while the composer is resized, multiplied by the number of compactable picker items because each failed fit trial calls \_fitsAvailableWidth again; each trial clones and measures the full tray subtree.  
**Outcome:** Increased main-thread layout/GC pressure and dropped frames while dragging or resizing the Sessions pane  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The workspace/repository/harness row had no ChatInputPickerResponsiveLayout, so resizing it did not repeatedly clone and synchronously measure this subtree.  
**Changed behavior:** The new responsive layout observes the full workspace-picker container, and usePreferredWidth routes every fit check directly through \_measurePreferredLayout. That helper deep-clones the observed subtree, attaches it, and reads every item and lane rect; the compaction loop can repeat this once per picker during each synchronous resize callback.  
**Confidence:** 0.96 — The synchronous callback, clone/attach/geometry-read implementation, resize reachability, and per-item retry loop are directly traced. Only the exact frame-time impact varies with DOM size and hardware, which is reflected in medium severity rather than lower confidence.

**Causal diff evidence:** RIGHT line 1312 newly enables usePreferredWidth for a newly-created responsive layout over the session-options container; before this hunk there was no responsive observer or intrinsic clone-and-measure loop for that row.

With the experimental composer enabled, continuously resizing a split Sessions pane runs several attach/measure/remove cycles per delivered width (workspace plus repository/harness controls), blocking the browser's resize/layout phase and causing visible resize jank.

**Evidence:** ChatInputPickerResponsiveLayout constructs an unthrottled DisposableResizeObserver whose callback calls layout synchronously. layout tests each visible item until the lane fits; with usePreferredWidth, \_fitsAvailableWidth always calls \_measurePreferredLayout, which cloneNode(true)s the lane, appends it, and forces getBoundingClientRect reads. The changed fixture explicitly exercises widths 520/420/360/300/220, establishing that realistic pane widths require multiple right-to-left compaction trials.

**Suggested direction:** Coalesce resize handling to one animation-frame pass and avoid rebuilding the measurement subtree for each candidate. Cache/invalidate intrinsic item widths when picker content changes, or build one measurement host per layout pass and derive the successive compact states from those measurements while preserving right-to-left compaction.
