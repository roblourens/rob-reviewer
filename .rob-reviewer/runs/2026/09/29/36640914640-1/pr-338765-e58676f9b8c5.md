<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** eager-work, repeated-work, cache-lifecycle, synchronous-ui-work

### Scenario 1: Open or switch an Agents Window chat while the MCP-auth pill experiment is disabled (default).

- Critical path: SessionChatInputToolbar constructs SessionMcpServers, but the derived sections return immediately after reading the false configuration value; MCP state acquisition is off the rendering critical path.
- Scaling input: Number of live chat toolbars; each retains only a configuration/event observer while disabled.
- Effective concurrency: One lightweight configuration observer per live chat toolbar; configuration events are processed synchronously, and strict equality suppresses unchanged boolean values.
- Cache behavior: No MCP session-state subscription is created while disabled. Configuration changes are observed so enabling takes effect without reload.
- Mechanism confidence: High: the enabled guard precedes both the session read and getMcpServers call, and observableFromEvent suppresses unchanged boolean values.
- Magnitude uncertainty: The number of split chat views varies, but disabled-state work is constant and does not scan MCP/customization state.
- Expensive boundaries: none found
- Verdict: No reportable regression: default-off construction does not cross an expensive boundary or perform collection work.

### Scenario 2: Open, switch, or receive MCP/customization state updates in a chat with the experiment enabled.

- Critical path: The pill derives sections synchronously before the toolbar can present current auth-required servers. On a cold session read, getMcpServers resolves the target and establishes the session-state subscription; warm updates read the already-materialized snapshot, filter presentable servers, and update the pill presentation.
- Scaling input: Distinct opened sessions control cold subscription count; live split chat views and customization/MCP server count control warm synchronous work.
- Effective concurrency: Cold subscription creation is coalesced by WorkbenchAgentHostCustomizationService's per-session DisposableResourceMap, so split views share one subscription. State events are handled serially on the UI thread; each live toolbar recomputes its own O(customizations + MCP servers) presentation.
- Cache behavior: Cold reads create one service-level subscription per session; warm reads reuse it. The subscription is disposed when the chat service disposes that session, on provisional rebinding, or with the service. Derived sections are not structurally memoized, so broad customization events allocate fresh arrays, but downstream presentation checks avoid DOM updates when labels/icons/ARIA are unchanged.
- Mechanism confidence: High for the subscription, cache sharing, and O(view count × customization count) synchronous recomputation; lower magnitude concern because no per-event boundary fan-out or unconditional DOM rebuild occurs.
- Magnitude uncertainty: Customization counts and event frequency are typically small; broad events can make multiple live split views recompute, but the traced work is bounded, in-memory after the cold subscription, and lacks evidence of user-visible latency.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts::\_ensureSessionStateSubscription</code>: Acquire a live agent-host Session state subscription through connection.getSubscription.; cardinality: At most one cached subscription per distinct session resource, shared across all split chat views and repeated reads for that session.
    - Introduced by diff: true; previous behavior: Opening the session chat toolbar alone did not request MCP state. Other customization consumers could already create the same cached subscription.; critical-path effect: Cold acquisition is initiated by the first enabled pill read, but the synchronous read can render an empty result until the asynchronous snapshot event arrives; it does not block toolbar rendering.
- Verdict: No high-confidence actionable performance regression. The single cached, non-blocking subscription is necessary for live auth status, and repeated in-memory work is bounded with presentation-level update suppression.

### Scenario 3: Click a single-server sign-in pill or choose one server from the multi-server dropdown.

- Critical path: The user action awaits authenticateMcpServer, which starts the selected server and runs interactive MCP authentication; this is intentionally on the action's completion path, not chat startup/rendering.
- Scaling input: User clicks, not total number of listed servers; multiple servers are displayed in a dropdown rather than authenticated eagerly.
- Effective concurrency: One authentication attempt per explicit click. The new code does not loop over servers or launch concurrent attempts.
- Cache behavior: Server lookup uses the current materialized session snapshot. Authentication/token caching and cancellation behavior remain owned by the existing resolver; the diff adds no new cache or retry loop.
- Mechanism confidence: High: the closure captures one resource/server id and calls the existing authentication method once.
- Magnitude uncertainty: Remote authentication duration depends on provider and user interaction, but cardinality is exactly one selected server per explicit action.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts::authenticateMcpServer</code>: Dispatch SessionMcpServerStartRequested to the owning agent host.; cardinality: One dispatch for the selected server per click.
    - Introduced by diff: false; previous behavior: The existing authentication service and server-management UI already used this operation; the diff adds a new explicit UI entry point.; critical-path effect: Required before interactive authentication can complete; user initiated and limited to the selected server.
  - network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts::authenticateMcpServer / resolveMcpServerAuthentication</code>: Perform interactive OAuth/authentication for the selected MCP endpoint.; cardinality: One flow for the selected server per click, subject to the existing authentication service's token/cache behavior.
    - Introduced by diff: false; previous behavior: The same existing authentication path was reachable from MCP server management; this diff routes the pill action to it.; critical-path effect: The action awaits the authentication result, as required for sign-in; it does not block unrelated chat rendering.
- Verdict: No performance regression: the expensive work is explicit, single-target, and semantically required.

**Summary:** Completed the performance pass over all 11 changed files and relevant service/rendering call paths. The feature is default-off, enabled state uses one cached non-blocking session subscription, warm updates perform bounded in-memory scans with downstream presentation suppression, and authentication remains one user-initiated existing boundary call per selected server. No valid performance finding or regression-fix record was identified.
