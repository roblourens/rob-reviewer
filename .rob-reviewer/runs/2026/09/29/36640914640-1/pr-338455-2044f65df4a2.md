## Findings (2)

### 1. [high] Keep extension readiness off generic session initialization

**Finding ID:** `PERF-763C3CFC358E`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:2771</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Copilot runtime IPC calls and extension provider subprocess startup  
**Scaling:** The delay is paid once for every durable local Copilot session materialization; when any discovered extension is still starting, initialization waits for that provider event for up to 10 seconds before the first turn can proceed.  
**Outcome:** blocked critical path and increased first-turn latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Durable session configs forced \`requestExtensions: false\`, and \`initializeSession()\` did not list extensions, wait for provider startup, or list canvases before registering the session.  
**Changed behavior:** All non-ephemeral sessions now request extensions/canvas rendering, and \`initializeSession()\` synchronously awaits \`\_waitForCanvasExtensions\`; that helper crosses two runtime RPC boundaries and waits up to 10 seconds whenever an extension reports \`starting\`.  
**Confidence:** 0.99 — The awaited call path from first-send materialization to the explicit 10-second timeout is direct and covered by a test; only the prevalence of slowly starting extensions is uncertain, not the mechanism or maximum delay.

**Causal diff evidence:** Added line 2747 awaits \`\_waitForCanvasExtensions(wrapper)\` inside \`initializeSession\`; added lines 2768-2771 call \`rpc.extensions.list()\` and await \`raceTimeout(..., 10\_000)\`. The launcher diff also changes \`requestExtensions\` from false to true for every durable session.

In a workspace with a project/user extension that starts slowly or fails to emit readiness promptly, even a normal non-canvas first prompt is held for as long as 10 seconds before the session is registered and the turn starts.

**Evidence:** \`CopilotAgent.\_materializeProvisional\` awaits \`\_initializeAndRegisterSession\` immediately before the first send, and \`\_initializeAndRegisterSession\` awaits \`session.initializeSession()\`. The new test \`observes extension readiness events that race with the status snapshot\` confirms session creation remains pending while a project extension is \`starting\`. The runtime launch provider executes each admitted extension via \`process.execPath\`, so this wait includes real subprocess startup rather than local bookkeeping.

**Suggested direction:** Start extension discovery/readiness in the background (ideally earlier than first-send materialization) and join it only for canvas-dependent work, or otherwise move this bounded wait off generic \`initializeSession()\` while preserving readiness before a canvas provider is actually consumed.

### 2. [medium] Fetch the accessibility tree without per-parent CDP calls

**Finding ID:** `PERF-D29FFCE49034`  
**Location:** <code>src/vs/platform/browserView/electron-main/browserViewAccessibility.ts:36</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Chrome DevTools Protocol IPC requests and AX node response objects  
**Scaling:** One Accessible View refresh sends one \`Accessibility.getChildAXNodes\` command for every expandable AX node encountered, up to the 2,000-node cap, in bursts of 32 concurrent commands.  
**Outcome:** increased Accessible View latency, IPC load, and allocation/GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Session canvases had no Accessible View snapshot path, so opening or refreshing this view issued no CDP accessibility traversal.  
**Changed behavior:** The new traversal starts at the root and fetches each parent's children through a separate CDP command, waiting batch-by-batch before it can format and display the snapshot.  
**Confidence:** 0.98 — The manual refresh call path, per-parent command placement, 2,000-node bound, and 32-command batch concurrency are explicit. Exact page tree shape and command duration affect magnitude only.

**Causal diff evidence:** Added line 36 invokes \`sendCommand('Accessibility.getChildAXNodes', { id })\` inside \`parentIds.map\`; the surrounding loop repeats this for every queued parent until 2,000 nodes are retained.

On a realistic complex canvas with hundreds or thousands of semantic containers, opening Accessible View can require hundreds to nearly 2,000 CDP round trips before any content appears, making an accessibility workflow noticeably slow while bursting main/renderer IPC.

**Evidence:** \`SessionCanvasEditor.refreshSemanticContent()\` awaits \`model.getAccessibilitySnapshot()\` on the Accessible View critical path, which crosses workbench-to-main IPC and reaches this loop. The test explicitly asserts separate child commands for successive parents. The repository's existing web-content extractor uses the bulk \`Accessibility.getFullAXTree\` CDP command instead, proving a non-per-parent boundary exists.

**Suggested direction:** Use the existing bulk AX-tree command for the main frame (with depth/retained-node and 32 KiB output bounds), or another subtree-batching strategy, so the snapshot requires a bounded small number of CDP calls rather than one per parent.

- Cache behavior: Bundled runtime/SDK paths are resolved once per Copilot client residency and the extension SDK path is held in a WeakMap. Extension status is queried anew per session; settled extensions avoid the timeout but still incur extension-list and canvas-list RPCs. Failures are not negative-cached.
- Mechanism confidence: High: the first-send call path and awaited timeout are direct and covered by a readiness-race test.

### Scenario 2: Receive canvas snapshots and automatically open live canvas editors

- Critical path: A runtime canvas event is projected through the Agent Host process and local protocol notification, updates Sessions observables, auto-opens an editor, resolves the source over RPC, creates an unlisted BrowserView over workbench/main IPC, and navigates it to the HTTP(S) source.
- Scaling input: At most eight projected canvases per chat; reconnect snapshots can contain all eight, while live open events usually add one at a time.
- Effective concurrency: The service invokes \`openEditor\` without awaiting it for every newly ready canvas, so up to eight opens can be in flight; actual editor-group serialization is internal and not established. BrowserView creation/navigation is otherwise per opened canvas.
- Cache behavior: Snapshots are full replacements and deduplicated at protocol boundaries. Presented revisions suppress duplicate editor opens. BrowserViews use ephemeral sessions and are recreated for a new revision; source URLs are resolved exactly per revision and are not cached.
- Mechanism confidence: High for the call path and boundary count; lower for actual parallel BrowserView creation because editor-service scheduling is internal.
- Magnitude uncertainty: The frequency of extensions opening several canvases at once and the cost of each page are unknown; the hard eight-canvas limit bounds the burst.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/protocolServerHandler.ts and src/vs/platform/agentHost/browser/agentHostProtocolClient.ts</code>: Broadcast and receive bounded full-replacement canvas snapshots.; cardinality: One notification per changed chat snapshot per capable local client, carrying at most eight canvases; equal snapshots are suppressed.
    - Introduced by diff: true; previous behavior: No canvas snapshot transport existed.; critical-path effect: Drives editor presentation but does not itself wait on network or disk.
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts \`AgentHostSessionCanvas.resolveSource\`</code>: Resolve the exact canvas source through workbench client, Agent Host protocol, and provider service.; cardinality: One RPC per canvas revision that is loaded into an editor.
    - Introduced by diff: true; previous behavior: No canvas source RPC existed.; critical-path effect: The editor cannot create/navigate its BrowserView until this completes.
  - IPC at <code>src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts \`createExternalBrowserView\` and \`WebContentsViewHost\`</code>: Create, lay out, show, and capture an unlisted Electron WebContentsView.; cardinality: One BrowserView per opened canvas editor; only visible models continue the inherited one-second screenshot cadence.

### Scenario 3: Open or refresh Accessible View for an active canvas

- Critical path: Accessible View calls \`SessionCanvasEditor.refreshSemanticContent\`, awaits workbench-to-main IPC, attaches the Electron debugger, traverses the main-frame AX tree through CDP, formats up to 32 KiB, then emits the semantic-content change.
- Scaling input: Expandable accessibility nodes in the main frame, capped at 2,000 retained nodes; command count approaches one per expandable node rather than one per snapshot.
- Effective concurrency: Child requests are issued in batches of 32 with a barrier between batches; there is no coalescing of concurrent refresh requests, though sequence checks discard stale results.
- Cache behavior: No AX snapshot cache is retained. Each refresh performs a cold traversal; navigation invalidates semantic text and the next refresh repeats all commands.
- Mechanism confidence: High: the critical path, command placement, cap, and batching are direct and test-asserted.
- Magnitude uncertainty: Actual AX tree size and per-command latency vary by canvas, but complex application canvases commonly contain hundreds of semantic containers and the algorithmic fan-out is explicit.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/browserView/electron-main/browserViewMainService.ts \`getAccessibilitySnapshot\`</code>: Request an accessibility snapshot from renderer/workbench to Electron main.; cardinality: One main-process request per Accessible View refresh.
    - Introduced by diff: true; previous behavior: Canvas Accessible View did not exist.; critical-path effect: Accessible content remains in a reading state until it resolves.
  - IPC at <code>src/vs/platform/browserView/electron-main/browserViewAccessibility.ts \`readBrowserViewAccessibilityTree\`</code>: Enable Accessibility, fetch the root, fetch each parent's children via CDP, and disable Accessibility.; cardinality: Four fixed commands plus up to roughly 2,000 per-parent child commands, in batches of 32.
    - Introduced by diff: true; previous behavior: No CDP AX traversal occurred for session canvases; existing repository extraction uses bulk \`Accessibility.getFullAXTree\` per frame.; critical-path effect: All batches complete before semantic text is shown.
- Verdict: Reportable boundary fan-out because a single accessibility refresh can require hundreds to nearly 2,000 serialized-batch CDP round trips.

### Scenario 4: Invoke the canvas extension reload tool

- Critical path: A model tool call awaits one live SDK \`extensions.reload()\` RPC; the Copilot runtime stops and restarts every extension provider before returning the tool result.
- Scaling input: Number and startup/cleanup cost of extensions in the current session; invocation frequency is controlled by model/tool use rather than ordinary turns.
- Effective concurrency: Provider restart concurrency is owned by the SDK and not visible here; the host awaits one aggregate reload RPC and does not issue per-extension calls.
- Cache behavior: No reload-result cache is appropriate because the operation intentionally re-reads changed extension files; failures are surfaced and subsequent calls retry.
- Mechanism confidence: High for the aggregate RPC and intended restart semantics; internal provider scheduling is opaque.
- Magnitude uncertainty: Provider count and restart duration are runtime-dependent.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts \`reloadExtensions\`</code>: Reload all extensions in the current Copilot SDK session.; cardinality: One aggregate SDK RPC per explicit \`extensions\_reload\` tool invocation.
    - Introduced by diff: true; previous behavior: No extension reload tool or runtime reload RPC was exposed.; critical-path effect: Blocks only the explicit reload tool result and canvas availability during provider restart.
  - subprocess at <code>Runtime reached from src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts \`reloadExtensions\`</code>: Stop and restart extension provider processes as part of the SDK reload.; cardinality: Runtime-defined, scaling with installed session extensions but grouped behind one host RPC.
    - Introduced by diff: true; previous behavior: No host-triggered extension provider restart path existed.; critical-path effect: Intentional critical work for the reload operation, not ordinary turn startup.
- Verdict: No finding: the expensive boundary is explicit, user/model-triggered reload work and is already grouped into one RPC rather than host-side per-extension fan-out.
