# Performance review: Add ARM64 Linux Snap builds with selectable core22/core24 bases

[PR #338607](https://github.com/microsoft/vscode/pull/338607) at `f3985918b87f1f79e48a3373e7e9b922ff5e0108`

## Findings (3)

### 1. [medium] Keep the x64 Snap in the grouped Linux sanity job

**Finding ID:** `PERF-03EC9A60DF56`  
**Location:** <code>build/azure-pipelines/product-build.yml:1097</code> (<code>RIGHT</code>)  
**Performance category:** <code>throughput</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** An additional CI agent plus duplicate checkout, Node/cache setup, sanity-test compilation, Key Vault access, and test-runner processes  
**Scaling:** Every artifact-sanity run with both the default Linux and Snap targets enabled now starts a second x64 sanity job for one Snap test, duplicating fixed harness setup once per product build regardless of artifact size.  
**Outcome:** Lower CI throughput and additional agent/network load; under finite pool capacity the extra job also increases queueing and artifact-sanity completion latency.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The existing artifact\_ubuntu\_x64 job downloaded the x64 Snap alongside the other Linux artifacts and its linux(-deb\|-snap)?-x64 grep ran the Snap test in the same initialized sanity harness.  
**Changed behavior:** The diff removes the Snap from that grouped job and adds a standalone artifact\_ubuntu\_snap\_x64 sanity-tests.yml job, repeating all common job setup before running only linux-snap-x64.  
**Confidence:** 0.99 — The before/after grouping is explicit in one changed hunk, and the shared template proves every duplicated setup boundary. Only queue-time magnitude is uncertain; the repeated work is unconditional for the stated flags.

**Causal diff evidence:** The hunk changes the existing grep from linux(-deb\|-snap)?-x64 to linux(-deb)?-x64, removes vscode\_client\_linux\_x64\_snap from its artifacts, and adds the separate artifact\_ubuntu\_snap\_x64 job at line 1097 for that same Snap target.

Default artifact validation now allocates and initializes another Linux agent solely for a test that was already coalesced with the x64 Linux suite before this PR.

**Evidence:** common/sanity-tests.yml performs a sparse checkout, pipeline artifact download, Node installation, cache restore (and npm ci on a miss), sanity TypeScript compilation, Azure Key Vault retrieval, and a runner invocation per template instance. The new x64 instance duplicates those boundaries; warm caches avoid only npm ci, not checkout, compilation, Key Vault, or process startup. Jobs can run in parallel, so exact wall-clock impact is pool-dependent, but total work and agent demand always increase.

**Suggested direction:** When VSCODE\_BUILD\_LINUX is true, keep the x64 Snap artifact and grep in artifact\_ubuntu\_x64 as before; instantiate the standalone Snap job only when the normal Linux target is disabled, matching the conditional coalescing already used by the non-artifact sanity section.

### 2. [medium] Keep Snap-only builds from running every ARM64 target

**Finding ID:** `PERF-154B321F8373`  
**Location:** <code>build/azure-pipelines/product-build.yml:483</code> (<code>RIGHT</code>)  
**Performance category:** <code>throughput</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** ARM64 client/server build CPU, package filesystem operations, and pipeline-artifact upload bytes  
**Scaling:** For every product run with VSCODE\_BUILD\_LINUX\_SNAP=true and VSCODE\_BUILD\_LINUX\_ARM64=false, the condition adds one complete ARM64 Linux product job; that job unconditionally produces and publishes the client archive, server, web server, DEB, and RPM in addition to the requested Snap.  
**Outcome:** Lower CI throughput and a longer Linux-stage critical path from building and uploading five unrelated ARM64 deliverables.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With VSCODE\_BUILD\_LINUX\_ARM64=false, the ARM64 product job was not instantiated; enabling the x64 Snap did not cause ARM64 client/server/DEB/RPM work.  
**Changed behavior:** The new OR condition instantiates the general-purpose Linux\_arm64 job whenever Snap is enabled, even when the separate ARM64 product target is explicitly disabled.  
**Confidence:** 0.98 — The trigger is explicit in the added condition, and the transitive template's unconditional build steps and outputs prove the extra work. Exact duration varies with caches and agent speed, but the full unrelated artifact cardinality is not uncertain.

**Causal diff evidence:** The changed condition at line 483 adds eq(parameters.VSCODE\_BUILD\_LINUX\_SNAP, true) as an alternative to VSCODE\_BUILD\_LINUX\_ARM64. The selected linux/product-build-linux.yml template has unconditional outputs for the ARM64 archive, server, web server, DEB, and RPM, and its compile template unconditionally builds those packages before the conditional Snap step.

A realistic Snap-only validation run that disables VSCODE\_BUILD\_LINUX\_ARM64 still consumes a full additional ARM64 product agent and waits for unrelated server and package work before the Snap artifact is available.

**Evidence:** Tracing the added branch into build/azure-pipelines/linux/product-build-linux.yml shows unconditional client/server/web/DEB/RPM artifact declarations, while product-build-linux-compile.yml builds DEB and RPM before the Snap block. Thus a Snap-only ARM64 request does not merely prepare the client needed by Snap; it executes and uploads all standard ARM64 targets. The duplicated condition in product-build-template.yml has the same behavior.

**Suggested direction:** Pass a snap-only mode to the ARM64 job or create a dedicated ARM64 Snap job that builds the required client and Snap but skips server/web/DEB/RPM generation and outputs when VSCODE\_BUILD\_LINUX\_ARM64 is false.

### 3. [medium] Pack ARM64 snaps on a native ARM64 worker

**Finding ID:** `PERF-77C6BE4F64EF`  
**Location:** <code>build/azure-pipelines/linux/steps/product-build-linux-compile.yml:419</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** CPU instructions and package/compression subprocess work executed through QEMU user-mode translation  
**Scaling:** Every ARM64 Snap build runs the entire Snapcraft 8 container as linux/arm64 on the Linux stage's x64 host; the translated work includes Snapcraft, Apt/dpkg staging of all manifest packages, priming, and LZO package creation.  
**Outcome:** Higher ARM64 packaging latency and x64 agent CPU consumption, with the serial ARM64 Linux job delaying its artifact publication and downstream artifact sanity stage.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The pipeline built only the x64 Snap, natively in an x64 container; no ARM64 Snapcraft workload ran under CPU emulation.  
**Changed behavior:** The added step registers ARM64 QEMU emulation on the x64 Linux stage, after which build-snap.sh invokes the Snapcraft image with --platform linux/arm64 and performs the complete destructive pack inside it.  
**Confidence:** 0.94 — The x64 host, QEMU registration, arm64 container platform, and full Snapcraft call path are explicit. The exact slowdown is agent-dependent, which limits severity, but the translated CPU mechanism and critical-path placement are certain.

**Causal diff evidence:** Line 419 newly registers qemu-user-static specifically for the ARM64 branch. The enclosing Linux stage is pinned to 1es-ubuntu-22.04-x64, and build-snap.sh's added pack\_snap path runs docker --platform linux/$SNAP\_ARCH ... snapcraft pack --destructive-mode for arm64.

Each requested ARM64 Snap spends the complete pack phase under emulation; on product/release builds this can make the ARM64 job the slow tail and consumes materially more agent CPU than native execution.

**Evidence:** The call path is product-build.yml Linux stage (x64 pool) -&gt; product-build-linux-compile.yml ARM64 branch -&gt; QEMU registration -&gt; build-snap.sh -&gt; an arm64 Snapcraft container. resources/linux/snap/snapcraft.yaml stages the desktop dependency set and uses LZO compression, so emulation covers substantial package-processing work rather than a small architecture check. The repository already references the native 1es-azure-linux-3-arm64 pool for Linux ARM64 jobs, establishing a bounded native scheduling option.

**Suggested direction:** Split ARM64 Snap preparation/packing into a job on the existing native ARM64 pool (or otherwise run the arm64 Snapcraft container on an ARM64 host), transferring only the prepared client input, while retaining the x64 job for cross-built non-Snap artifacts.
