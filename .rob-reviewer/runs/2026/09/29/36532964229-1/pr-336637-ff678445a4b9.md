### Scenario 1: Starting or restoring an agent chat with artifact tools enabled across Copilot, Claude, and Codex

- Critical path: Tool definitions are selected once while constructing the provider session. Copilot and Claude mark List/Remove deferred when provider search is available; Codex keeps all three eager. Provider session startup remains the critical path, but the diff reduces eager definition payload for supported providers and does not add a new blocking operation.
- Scaling input: Three artifact tools per enabled session; effective cardinality is fixed, with two deferred and one eager for Copilot/Claude, and all three eager for Codex.
- Effective concurrency: Copilot and Codex map definitions synchronously once per launch/resume. Claude creates the fixed tool set with Promise.all, but SDK module loading is cached and there are only three artifact definitions.
- Cache behavior: Static original/compact definition arrays are allocated once at module load. Configuration is read from in-memory root state when definitions are selected; the Claude SDK module is cached after first load. No miss loop or negative-cache retry is introduced.
- Mechanism confidence: High: provider construction paths and deferral gates are directly traced.
- Magnitude uncertainty: Exact token and provider startup savings depend on provider framing and model support for tool search, but call counts and fixed definition cardinality are established.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts launch; src/vs/platform/agentHost/node/claude/claudeAgentSession.ts \_buildStartupToolWiring</code>: Provider session/model startup receives serialized tool definitions.; cardinality: One provider startup payload per launch/resume; artifact definition cardinality is reduced from three eager tools to one where search is active.
    - Introduced by diff: false; previous behavior: All server tools were eager in Copilot, and Claude had no artifact-specific alwaysLoad metadata.; critical-path effect: The existing provider startup boundary is on the critical path; the diff reduces its eager prompt payload rather than adding calls.
  - ipc at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts \_buildDynamicTools / thread/start</code>: Codex thread/start serializes dynamicTools to the Codex process.; cardinality: One IPC request per thread start, carrying the same three artifact tools when enabled.
    - Introduced by diff: false; previous behavior: The same artifact tools were already included eagerly in dynamicTools.; critical-path effect: Existing thread startup IPC remains on the critical path; no additional request or fan-out is introduced.
- Verdict: No reportable regression. Definition selection adds only bounded in-memory reads and supported providers reduce eager serialized prompt content.

### Scenario 2: Sending the first turn in a new chat with artifact guidance enabled

- Critical path: The contribution performs two in-memory configuration reads and appends exactly one selected instruction before the first model request. Restored non-empty chats and subsequent turns do not repeat the instruction.
- Scaling input: One instruction per new or empty restored chat, independent of turn count; no per-message growth after the first turn.
- Effective concurrency: Synchronous contribution assembly; no queue or parallel work is introduced.
- Cache behavior: A per-chat memento records first-turn completion. Compact/original strings are module-level constants; there is no external cache or repeated construction.
- Mechanism confidence: High: memento lifecycle and first-turn tests establish the frequency.
- Magnitude uncertainty: Provider tokenization varies, but the once-per-chat bound is explicit.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/chatContributions/artifactTools/artifactToolsContribution.ts onOutgoingTurn</code>: The existing first model request includes the selected artifact guidance in its prompt.; cardinality: Exactly once per new chat; zero on later turns and restored chats with history.
    - Introduced by diff: false; previous behavior: The first request already included artifact guidance once; the diff selects compact or original wording.; critical-path effect: The instruction is part of the existing model request, not a separate boundary. Compact treatment reduces bytes; control remains bounded to one request.
- Verdict: No reportable regression. The experiment changes bounded prompt bytes without introducing another request or repeated work.

### Scenario 3: Adding a batch of artifacts, including promoting an existing reference

- Critical path: Inputs are validated in memory, then one per-session sequenced mutation scans the current artifact list for each batch entry. If the final collection changes, one catalog persistence operation completes before state publication and tool completion.
- Scaling input: Cost is O(batch size × current artifact count), as before for batched additions. Promotion adds one list map for a matching reference. Effective collections are user-visible session artifacts and expected to remain small; persistence is once for the entire batch.
- Effective concurrency: SessionArtifacts uses SequencerByKey, serializing mutations per session while allowing different sessions to proceed independently. No concurrency burst is introduced.
- Cache behavior: Current artifacts are read from authoritative session metadata for each mutation; unchanged duplicates do not persist. There is no cache miss retry path.
- Mechanism confidence: High: mutation loop, reference equality check, sequencer, and persistence call are directly traced.
- Magnitude uncertainty: No repository-wide upper bound for artifact count is visible, but the feature guidance defaults to sparse registration and realistic session lists are small.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts \_persistOrderedListVisibleSessionState / \_persistListVisibleSessionStateNow</code>: Catalog synchronization persists the final artifact metadata list.; cardinality: At most one persistence operation per mutating Add tool call, regardless of batch size; unchanged duplicate batches perform none.
    - Introduced by diff: false; previous behavior: Batched additions already persisted once per changed call. The new promotion case changes a former duplicate no-op into one required persistence operation because authoritative state now changes.; critical-path effect: Persistence is awaited before the Add tool returns and state is published.
- Verdict: No reportable regression. Promotion adds bounded CPU/allocation and only the single durable write required by the new state change; batching and per-session serialization are preserved.

### Scenario 4: Listing or removing artifacts after List/Remove are deferred

- Critical path: With active tool search, the model discovers the deferred List/Remove definition before invoking it. List reads session metadata in process; Remove performs one sequenced catalog persistence operation. Without search support, tools remain eager.
- Scaling input: Discovery candidates are fixed at two artifact tools. Listing output scales with recorded artifact count; removal scans that list once, both unchanged from before.
- Effective concurrency: Discovery is provider-controlled and bounded to a fixed candidate set. Removal is serialized per session by SequencerByKey; no aggregate burst is introduced.
- Cache behavior: Provider tool-search state is resolved at launch. Deferred definitions remain available as fixed metadata; there is no repeated host-side discovery miss or unbounded cache.
- Mechanism confidence: High for the added discovery step and fixed cardinality; lower only for user-frequency magnitude.
- Magnitude uncertainty: The prevalence of explicit List/Remove requests and provider-specific discovery latency is unknown.
- Expensive boundaries:
  - ipc at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts \_toToolSearchCandidates / server SDK deferral</code>: Copilot tool search round-trips through the existing client tool-search mechanism before a deferred List/Remove invocation.; cardinality: At most one discovery interaction when the model needs either of the two deferred tools; zero when tool search is inactive because they remain eager.
    - Introduced by diff: true; previous behavior: List and Remove were always eager and could be invoked without discovery.; critical-path effect: Discovery can add latency to the uncommon explicit List/Remove workflow, trading it for smaller eager prompts on all chats.
  - database at <code>src/vs/platform/agentHost/node/shared/sessionArtifacts.ts mutate and src/vs/platform/agentHost/node/agentService.ts persistence accessor</code>: Removing an artifact synchronizes updated session metadata to the catalog.; cardinality: One persistence operation for a successful removal; zero for a missing id.
    - Introduced by diff: false; previous behavior: Successful removals already performed the same single persistence operation.; critical-path effect: The existing durable write remains awaited before tool completion.
- Verdict: No reportable regression. The added discovery step is a deliberate, bounded scheduling tradeoff for rare management tools, with eager fallback when search is unavailable; evidence does not establish material user impact warranting rollback.
