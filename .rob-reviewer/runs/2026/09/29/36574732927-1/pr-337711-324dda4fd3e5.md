# Performance review: Add Visual Studio-style column selection paste

[PR #337711](https://github.com/microsoft/vscode/pull/337711) at `324dda4fd3e5073d47136a88eba37ab6bb3b3cbd`

## Findings (2)

### 1. [high] Let large block pastes use the model's edit coalescing safeguard

**Finding ID:** `PERF-BB44510FFCB0`  
**Location:** <code>src/vs/editor/common/commands/columnSelectionPasteCommand.ts:48</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Per-row edit, inverse-edit, undo, piece-tree, decoration-update, and content-change objects plus synchronous CPU  
**Scaling:** With R copied rows and enough existing destination lines, this loop creates R tracked edit operations; notebook mirroring can repeat that cost per one-selection tracked cell. Rows after EOF are coalesced, so the effective count is the copied rows that land on existing lines plus one append operation.  
**Outcome:** Large temporary memory/GC pressure, blocked paste latency, and possible out-of-memory failure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A single-cursor multiline paste used one ReplaceCommand and therefore one tracked edit operation regardless of pasted row count.  
**Changed behavior:** Block mode invokes ReplaceCommand/ReplaceOvertypeCommand once per destination row, and both add a tracked edit. CommandExecutor marks the first operation \_isTracked; PieceTreeTextBuffer then sets canReduceOperations=false, bypassing its &gt;=1000-operation reduction that is explicitly documented as preventing OOM crashes.  
**Confidence:** 0.99 — The per-row cardinality and exact flag chain that disables the repository's OOM guard are directly traced. Runtime duration depends on document/decorations, but the allocation and coalescing regression is certain.

**Causal diff evidence:** RIGHT line 48 newly adds one tracked model edit per block row; before this feature the single-selection paste path submitted one replacement for the entire text.

Pasting a realistic 1,000-10,000-row column block into a large file keeps thousands of edits separate on the UI thread instead of collapsing them, producing a long freeze and potentially exhausting memory. The editor's default multiCursorLimit permits 10,000 source rows.

**Evidence:** The new loop calls ChosenReplaceCommand.getEditOperations at line 48 for every copied row that maps to an existing destination line. replaceCommand.ts uses builder.addTrackedEditOperation. CommandExecutor propagates hadTrackedEditOperation to filteredOperations\[0\].\_isTracked. PieceTreeTextBuffer.applyEdits disables canReduceOperations on that flag; its \_reduceOperations threshold is 1000 and its comment states that collapsing is required to avoid OOM from temporary allocations. The same buffer path also creates inverse operations, content changes, and per-change decoration updates.

**Suggested direction:** Do not mark every row operation tracked. Use ordinary edit operations and compute the final cursor from a tracked selection or from the coalesced inverse range, or proactively collapse large block pastes into one equivalent contiguous edit while preserving undo and final-cursor semantics.

### 2. [medium] Avoid computing visual columns for every ordinary copy

**Finding ID:** `PERF-773A5230FFDC`  
**Location:** <code>src/vs/editor/browser/controller/editContext/clipboardUtils.ts:48</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Main-thread CPU spent slicing line prefixes and iterating grapheme boundaries  
**Scaling:** For an ordinary selection, the added lookup scans both the selection-start and cursor-position prefixes, so cost grows with their column offsets even when only a few selected characters are copied.  
**Outcome:** Copy/cut latency and editor input jank on very long lines  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Ordinary copy/cut proceeded directly to getPlainTextToCopy, whose getValueInRange work was proportional to the selected range; it did not calculate visual columns.  
**Changed behavior:** Every copy/cut now calls getCursorColumnSelectData().isReal. When the selection is not an active column selection, that getter constructs fallback data by calling visibleColumnFromColumn for both endpoints; each call substrings the prefix and walks it with GraphemeIterator.  
**Confidence:** 0.99 — The synchronous call path, ordinary-selection fallback, and linear grapheme scans are explicit in the repository. Only prevalence of extremely long lines affects magnitude, not the mechanism.

**Causal diff evidence:** RIGHT line 48 newly executes viewModel.getCursorColumnSelectData().isReal before getPlainTextToCopy for all copies, including non-column selections.

Copying a small token near the end of a multi-megabyte generated/minified line now synchronously scans that long prefix twice before clipboard data can be produced, visibly delaying Ctrl+C/Ctrl+X.

**Evidence:** The added line invokes CursorsController.getCursorColumnSelectData on every generateDataToCopy call. Ordinary setStates clears \_columnSelectData, so the getter's fallback path runs; cursor.ts:285-296 calls cursorConfig.visibleColumnFromColumn twice. CursorColumns.visibleColumnFromColumn creates a prefix substring and iterates every grapheme. createClipboardCopyEvent calls generateDataToCopy synchronously from the DOM clipboard event, while getPlainTextToCopy reads only the selected model ranges.

**Suggested direction:** Expose/read a cheap column-selection identity flag (for example an accessor that tests whether real column-select data exists) and only compute fallback visual coordinates for callers that actually need them.

### Scenario 2: Paste a copied column selection as a block into one cursor in a normal editor

- Critical path: Paste handling synchronously splits clipboard text, computes target columns, constructs edits, applies them to the piece tree, updates decorations, emits content changes, and computes the cursor before the editor responds.
- Scaling input: Effective row count is copied rows that map to existing destination lines, plus at most one coalesced append edit after EOF. Source column selections can reach the default 10,000-cursor limit.
- Effective concurrency: One synchronous command on the main thread. Row scans and model edits are serial; there is no limiter or deferred chunking.
- Cache behavior: No cache is relevant. Destination line contents and visual columns are read once per affected existing row; clipboard text is split once.
- Mechanism confidence: High: each row calls a tracked ReplaceCommand, CommandExecutor marks the operation set tracked, and PieceTreeTextBuffer consequently bypasses its &gt;=1000 edit coalescing path.
- Magnitude uncertainty: Exact freeze duration depends on row widths, decorations, listeners, and machine memory. The model's explicit 1,000-edit OOM safeguard establishes that keeping thousands of these edits separate is unsafe regardless of exact timing.
- Expensive boundaries: none found
- Verdict: Reportable memory and latency regression: the new block path defeats an existing OOM-prevention mechanism for realistic large blocks.

- Expensive boundaries: none found
- Verdict: The notebook change amplifies the reported large-block mechanism but does not warrant a separate finding because it is the same core tracked-edit issue and requires the narrower one-selection-per-cell state.
