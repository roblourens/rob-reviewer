## Findings (1)

### 1. [low] Avoid rescanning all secrets after migration has completed

**Finding ID:** `PERF-597321858122`  
**Location:** <code>extensions/github-authentication/src/common/enterpriseStorage.ts:88</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Cross-process SecretStorage calls, full machine-secret key enumeration/JSON parsing, and encrypted-secret reads  
**Scaling:** Every activation with a configured Enterprise URI repeats an O(S) scan over all machine secret keys, where S is the number of secrets stored by all extensions; a warm post-migration activation also adds two serialized SecretStorage RPCs before provider initialization, and cold migration adds one read per matching legacy alias.  
**Outcome:** Increased authentication-provider activation latency, with the delay growing with the machine secret store and recurring on every window/extension activation during the migration releases.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The provider constructed the Enterprise engine directly, so initialization performed only the engine's single read of its configured credential key and did not enumerate all extension secrets first.  
**Changed behavior:** applyConfiguration now awaits migrateEnterpriseStorage before creating/registering the host; migrateEnterpriseStorage always calls secrets.keys(), scans global-state keys, and reads the canonical target even when no legacy source remains, after which GitHubSessionEngine reads that same target again.  
**Confidence:** 0.96 — The changed call path and boundary cardinality are explicit: warm/no-legacy initialization changes from one engine secret read to one all-keys RPC plus a migration target read plus the engine read, all serialized by the main-thread per-extension sequencer. Exact milliseconds vary with profile size and platform, so severity is low, but recurrence and critical-path placement are certain.

**Causal diff evidence:** Added line 88 introduces \`await context.secrets.keys()\` on every configured-provider initialization; this path did not exist before the diff and is awaited before host creation.

Once credentials have already been migrated—or for a new profile with no legacy entry—any GitHub authentication activation still waits for a full SecretStorage key enumeration and an extra canonical secret read. MainThreadSecretState serializes these operations per extension, so they sit directly ahead of enterprise registration and the normal engine read.

**Evidence:** extension.ts awaits provider.update during activate. githubEnterprise.ts:80 awaits migration before createHost/registerProvider. extHostSecretState routes keys/get over RPC; MainThreadSecretState.$getKeys enumerates every machine secret key and serializes operations by extension. enterpriseStorage.ts:88 performs that enumeration unconditionally and line 101 reads the canonical target before the no-sources return; GitHubSessionEngine construction then calls Keychain.getToken, which reads the same canonical secret again.

**Suggested direction:** Make the temporary migration one-shot across successful activations (while retaining retry on failure), or move legacy discovery off the activation path once completion is known; also reuse or defer the canonical read so the no-source path does not read the same secret twice.
