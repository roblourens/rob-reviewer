## Findings (1)

### 1. [medium] Stop retries when the host's state was removed

**Finding ID:** `PERF-79A9959918B4`  
**Location:** <code>src/vs/sessions/contrib/remoteAgentHost/browser/remoteAgentHost.contribution.ts:365</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** \`ssh -G\` subprocesses plus SSH network connections and remote setup commands  
**Scaling:** One removal race can cause up to nine additional sequential attempts with 1s-to-30s backoff; independent removed hosts retry concurrently, so aggregate work scales with the number of affected hosts.  
**Outcome:** Excessive background subprocess and network I/O after the owning configuration entry has been removed.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, a reconnect rejection logged/unpublished cached sessions and stopped; removing a host while that one attempt was in flight could not start an autonomous follow-up chain.  
**Changed behavior:** A failed in-flight reconnect now recreates retry ownership even when configuration removal already disposed it, allowing the new exponential retry chain to continue against a host that no longer exists in configuration.  
**Confidence:** 0.98 — The cleanup and retry paths are explicit: reconciliation disposes state for hosts absent from configuration, but this changed catch handler unconditionally recreates that state and schedules another attempt. The transitive reconnect path unconditionally runs \`ssh -G\` and then SSH/network setup. The only magnitude uncertainty is how often users remove a host while an attempt is pending.

**Causal diff evidence:** The added line \`const liveState = this.\_getOrCreateSSHReconnectState(sshConfigHost);\` recreates per-host retry state after reconciliation may have deleted it, and the added call at line 372 schedules the next reconnect from that recreated state.

If a user removes an unreachable SSH host while reconnect is pending, VS Code can continue launching \`ssh -G\` and SSH/network attempts for that removed host for minutes, consuming subprocess/network resources and potentially multiplying across several removed hosts.

**Evidence:** \`\_reconnectSSHEntries\` calls \`deleteAndDispose(host)\` for no-longer-configured hosts, but \`\_attemptSSHReconnect\`'s catch uses \`\_getOrCreateSSHReconnectState\` and then \`\_scheduleSSHReconnect\` without rechecking configuration. Each timer calls \`\_sshService.reconnect\`; that reaches \`SSHRemoteAgentHostMainService.reconnect\`, which calls \`resolveSSHConfig\`, spawning \`ssh -G\`, and then may perform a fresh SSH connection plus remote commands. With no further reconciliation event, failed attempts keep rescheduling until the 10-attempt cap.

**Suggested direction:** Treat absence of retry state as cancellation: use \`\_sshReconnectStates.get(sshConfigHost)\` in the catch and return when it is missing, and revalidate that the host is still configured (and auto-connect enabled) before scheduling another attempt.


## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:493` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:461`  
**Introducing path:** `src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts`  
**Introducing commit:** `2bfd243feb70068823a0db14790ae152545a9af7`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `latency`  
**Confidence:** 0.98

**Mechanism:** Relay replacement reused an unresponsive SSH client and awaited relay creation without a deadline, so one half-open connection could permanently block reconnect and retain the dead shared-process connection.

**Symptom:** After a silent network loss, remote agent host reconnect could hang indefinitely and require restarting the application.

**Fixed behavior:** Relay creation on the replace path now times out after 60 seconds; the existing catch ends the dead SSH client, emits closure, and lets subsequent retries establish a fresh connection.

**Evidence:** The base reconnect path awaited `_createWebSocketRelay`, whose SSH `forwardOut` callback can remain pending when a reused TCP connection is half-open. That leaves the renderer reconnect promise and per-host pending state unresolved indefinitely. The changed line wraps that same operation in `raceTimeout`; the added unit test forces relay creation never to settle and verifies timeout rejection and `sshClient.end()`.
