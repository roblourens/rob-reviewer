# Performance review: Expose all onboarding tours in developer settings

[PR #338557](https://github.com/microsoft/vscode/pull/338557) at `d0719afe58998ee778b8fcfe55144c9557820b90`

## Findings (1)

### 1. [low] Keep a session-local guard for developer replay

**Finding ID:** `PERF-B23430216102`  
**Location:** <code>src/vs/sessions/contrib/onboardingTours/browser/parallelWorkOnboarding.ts:120</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** workbench view opening/reveal plus spotlight DOM, target polling, and layout work  
**Scaling:** With developer mode enabled for the parallel-work tour, the cost repeats once for every qualifying parallel-work handoff in the same window instead of stopping after the first replay; the existing Sequencer serializes these runs but does not suppress later ones.  
**Outcome:** Repeated main-thread rendering/layout work and repeated sessions-view activation during subsequent parallel-work launches.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous condition always consulted the shared shown key, so after the first new-session or parallel-work tour was shown, later handoffs took the lightweight handoff-only branch and did not open/reveal the Sessions view or construct another spotlight overlay.  
**Changed behavior:** The new \`\_hasBeenShown\` returns false unconditionally whenever developer mode is enabled for this tour. Every later handoff therefore proceeds through session resolution, \`openView\`, \`revealSessionForOnboarding\`, and \`runScenario\`. \`runScenario\` is explicitly on-demand and does not apply \`\_hasBeenShownKey\`, so the service's \`\_shownSinceStart\` guard cannot stop these subsequent runs.  
**Confidence:** 0.97 — The changed predicate, sole production caller, serial execution path, unconditional on-demand enqueue behavior, and concrete view/overlay work are all directly traced. Only the wall-clock magnitude varies with view state and number of handoffs; the repeated mechanism is deterministic when the toggle remains enabled.

**Causal diff evidence:** RIGHT line 120 adds \`return \!isOnboardingDeveloperModeEnabled(...) && ...\`; when the new developer setting is true, short-circuiting prevents the prior \`hasBeenShown(NEW\_SESSION\_ONBOARDING\_SEEN\_KEY)\` check from ever suppressing later handoffs.

A developer who enables this newly exposed toggle to replay the variation once will pay the full three-step tour rendering path after every additional parallel-work handoff in that window, including reopening/expanding the Sessions view and rebuilding the dimming overlay.

**Evidence:** \`runWithHandoff\` calls \`\_hasBeenShown\` before all expensive tour setup. The added line makes that predicate false for the entire lifetime of developer mode. The reached callback opens \`SessionsView\` and reveals a row, while \`SpotlightPresentation\` constructs an overlay, dims the window, resolves/polls targets, and schedules layout for each step. The onboarding service's \`runScenario\` directly enqueues and presents the scenario without checking shown state, so marking the shared seen key does not restore the fast path.

**Suggested direction:** Track a separate in-memory "parallel-work developer replay shown" flag (set once this variation is presented/attempted), or otherwise consult a session-local guard before the expensive setup, while still allowing exactly one replay after the shared regular V2 tour was shown.
