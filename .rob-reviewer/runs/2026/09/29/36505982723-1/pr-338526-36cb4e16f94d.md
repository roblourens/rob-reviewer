<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** cleanup-lifecycle, missing-coalescing, boundary-fanout, concurrency-burst

### Scenario 1: Active terminal input/output updates child-process state

- Critical path: PTY input/output delivery itself does not await monitoring. After one second of input quiet or the five-second output leading/trailing throttle followed by the one-second debounce, listProcesses must complete before HasChildProcesses can update; this work remains off the terminal data rendering/input critical path.
- Scaling input: Input event frequency, output event frequency, number of simultaneously active terminals, and OS process-tree size. Effective calls are reduced by per-monitor debounce/throttle but independent terminals may still query concurrently, exactly as before.
- Effective concurrency: Each monitor has one active and one inactive scheduler. Input resets the active scheduler; output maintains one trailing inactive scheduler. Slow listProcesses calls can overlap with later refreshes and different terminals are not globally limited, but neither behavior is introduced or amplified by this change.
- Cache behavior: No result cache exists. Scheduler state is per monitor; warm module loading may reduce Windows import overhead, but process trees are always re-read. The diff preserves coalescing and does not alter success, empty-result, or failure retry behavior.
- Mechanism confidence: High: decorator source, RunOnceScheduler source, terminal callers, and listProcesses implementations were traced directly.
- Magnitude uncertainty: Exact process enumeration time depends on platform and process-tree size, but there is no uncertainty that the diff preserves boundary count and scheduling cadence.
- Expensive boundaries:
  - subprocess at <code>src/vs/base/node/ps.ts:listProcesses</code>: On Linux/macOS, resolve and execute ps to enumerate processes; Linux additionally executes cpuUsage.sh for the selected process tree.; cardinality: Per monitor, repeated input is coalesced to one query after a one-second quiet period. Output causes one leading refresh and at most one trailing refresh per five-second interval. On Linux a successful refresh reaches up to three subprocess executions (which ps, ps/ps.sh, and cpuUsage.sh); macOS reaches two. Effective cardinality is unchanged by the diff.
    - Introduced by diff: false; previous behavior: The decorator-based debounce and throttle invoked the same listProcesses operation with the same one-second debounce and five-second leading/trailing output cadence.; critical-path effect: The subprocess sequence delays only the asynchronous child-process-state update, not terminal input/output progress.
  - other expensive boundary at <code>src/vs/base/node/ps.ts:listProcesses</code>: On Windows, dynamically load &#64;vscode/windows-process-tree and query the process list and CPU usage through native callbacks.; cardinality: One native process-tree query sequence per coalesced refresh per terminal; no global limiter across terminals and no change in per-terminal coalescing or aggregate concurrency.
    - Introduced by diff: false; previous behavior: The same Windows process-tree and CPU queries ran at the same coalesced refresh cadence before the diff.; critical-path effect: Completion gates only the child-process-state update and remains asynchronous from terminal I/O.
- Verdict: No reportable regression. The patch replaces decorator timers with disposable schedulers without increasing process-query frequency, concurrency, or critical-path work.

### Scenario 2: Terminal disposal with pending monitor refreshes

- Critical path: Disposal synchronously disposes the registered schedulers. No process-tree boundary must complete unless a query had already started before disposal.
- Scaling input: Number of terminals or tasks disposed while input/output timers are pending. Before the diff each pending decorator timer retained its monitor until expiry, with a trailing output callback able to schedule another one-second debounce; after the diff pending timers are canceled immediately.
- Effective concurrency: Each disposed monitor can have at most one input and one output timer. Disposal now cancels both; an already-running asynchronous listProcesses call remains uncancelled, as before.
- Cache behavior: No cache is involved. Cancellation applies to pending scheduler state only and does not fabricate cached child-process results.
- Mechanism confidence: High: both schedulers are registered in ChildProcessMonitor's DisposableStore, RunOnceScheduler.dispose cancels its timeout and clears its runner, and post-disposal input/output scheduling is guarded.
- Magnitude uncertainty: The amount of reclaimed object-graph memory and frequency of rapid terminal churn vary by workload; retention duration and timer ownership are directly established.
- Expensive boundaries: none found
- Verdict: This is a performance improvement, not a regression: pending timer roots and delayed callbacks are removed on disposal while in-flight process queries remain unchanged.

**Summary:** Reviewed the full two-file diff under the performance focus. Traced input, output, disposal, scheduler/decorator semantics, terminal ownership, and platform-specific process-tree boundaries. No actionable performance regression was introduced; the change preserves coalescing and expensive-boundary cardinality while reducing bounded post-disposal retention.
