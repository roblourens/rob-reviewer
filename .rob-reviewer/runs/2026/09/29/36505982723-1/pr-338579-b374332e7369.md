## Findings (1)

### 1. [medium] Bound the Draw animation's per-frame SVG work

**Finding ID:** `PERF-0158ADFA330F`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatWorkingLogo.ts:185</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Per-frame CPU work, transient arrays/Maps/path strings, SVG path parsing, and mask rasterization.  
**Scaling:** Cost grows with display refresh rate × active Draw-logo count × response duration. RAF runs for 100% of the active lifetime; geometry and strings are rebuilt during 80% of each 4-second cycle, and independent logos have no shared scheduler or frame cache.  
**Outcome:** Continuous main-thread CPU/GC pressure and SVG repaint work on the frame critical path, with increased risk of dropped frames and input latency.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** An active logo used three browser-managed CSS clip-path animations over fixed SVG paths. Application JavaScript did not wake each frame, construct path geometry or strings, update SVG attributes, or force dynamic SVG-mask painting.  
**Changed behavior:** Each active Draw logo now runs JavaScript every display frame, rebuilds ribbon geometry and path strings during 80% of every 4-second loop, compares the resulting strings only after construction, and mutates SVG mask path data. The previous implementation used three fixed SVG faces animated by browser-managed CSS clip-path keyframes and performed no per-frame application JavaScript or path allocation.  
**Confidence:** 0.99 — The RAF loop, active-response ownership, default-on Insiders configuration, geometry call chain, and removed CSS implementation are all explicit in the changed code. Exact milliseconds vary by refresh rate and machine, but the new main-thread work and its scaling are deterministic.

**Causal diff evidence:** RIGHT line 185 adds a perpetual requestAnimationFrame path that calls renderDrawFrame for each active Draw logo; RIGHT line 193 then invokes the new geometry builder before the next paint. The same diff removes the prior CSS keyframes from chatWorkingLogo.css.

With Draw enabled (the Insiders default, and available through experiments/settings), every foreground agent response adds continuous main-thread CPU/GC work and SVG mask repainting for its full lifetime. Long-running requests, high-refresh-rate displays, or multiple active chat widgets multiply this work and can reduce editor responsiveness or drop frames while streaming chat.

**Evidence:** ChatWorkingProgressContentPart creates one ChatWorkingProgressLogo for the persistent progress row and keeps it active while a response or interaction is pending. renderNextDrawFrame at chatWorkingLogo.ts:185 executes on every RAF and immediately requeues itself. renderDrawFrame calls getChatWorkingLogoDrawFrame; its Ribbon.bands/sections path allocates Maps, arrays, points, and concatenated SVG path strings, including up to the 32-step flattened fold geometry, before the path-data cache can reject unchanged output. setAttribute('d', ...) also reparses and repaints an SVG mask. The removed implementation was fixed SVG geometry plus CSS clip-path keyframes.

**Suggested direction:** Keep the frame path bounded: precompute and share a finite frame table (30 fps is already treated as acceptable in the added tests), advance only when the frame index changes, and pause scheduling through the hold/rest intervals; alternatively restore a declarative CSS/WAAPI mask animation. Avoid rebuilding completed bands and reparsing \`d\` attributes on every display refresh.
