<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, boundary-fanout

### Scenario 1: Hydrate or refresh a multi-chat session from a legacy pre-0.10 Agent Host

- Critical path: Session metadata/catalog processing must synchronously update the cached adapter and observables before the refreshed session list/chat UI reflects read state. No subprocess, filesystem, database, or network operation is added on this path.
- Scaling input: Number of chats in the refreshed session. The new legacy propagation scans the surfaced aggregate chats once and only mutates chats whose read state differs, so effective cost is O(chats) in memory.
- Effective concurrency: Synchronous per-session reconciliation inside existing transactions/notification handlers; sessions are processed by the existing event stream, with no new parallel work or limiter interaction.
- Cache behavior: The existing session cache and chat adapter map are reused. Warm adapters preserve client-side read state; cold legacy adapters initialize conservatively unread. No new cache key, miss retry, or retained cache is introduced.
- Mechanism confidence: High confidence in the O(chats) synchronous reconciliation and absence of an added expensive boundary, based on the changed adapter methods and notification/catalog call paths.
- Magnitude uncertainty: Sessions can contain multiple peer/tool chats, but repository evidence does not establish unusually large catalogs; the changed work is a bounded in-memory pass over the already-materialized chat list.
- Expensive boundaries: none found
- Verdict: No reportable regression. The linear in-memory propagation is required to keep legacy session-level state consistent across already-materialized chats and does not add boundary fan-out.

### Scenario 2: Automatically or explicitly mark one chat read on a legacy Agent Host

- Critical path: The provider synchronously updates optimistic cached read state, then dispatches one legacy SessionIsReadChanged notification; callers do not await a host response because dispatch is fire-and-forget.
- Scaling input: Invocation count, not chat count, controls boundary cardinality. Each invocation also scans the already-materialized chats once to apply the legacy session-wide state.
- Effective concurrency: Automatic active-chat requests are serialized by synchronous optimistic state mutation and guarded by a per-active-chat/version lastReadRequest. Explicit actions are individual calls; no new Promise.all or burst is introduced for this scenario.
- Cache behavior: Uses the warm session cache; no boundary is attempted without a cached adapter and initialized connection. There is no separate result cache, but optimistic read state suppresses normal automatic repeats.
- Mechanism confidence: High confidence that each invocation sends one uncoalesced JSON-RPC notification; high confidence that normal production callers suppress repeated invocations after the synchronous optimistic update.
- Magnitude uncertainty: External callers could manually repeat an already-satisfied request, as the test does, but inspected production callers either require unread state or are gated by unread UI context, so realistic duplicate frequency is not established.
- Expensive boundaries:
  - IPC/network at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_setLegacySessionReadState and src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:dispatch</code>: Serialize and send one JSON-RPC dispatchAction carrying SessionIsReadChanged to the Agent Host transport.; cardinality: One boundary call per accepted mark-read invocation. Although the new test deliberately invokes the same operation twice and observes two calls, production active-chat logic deduplicates by chat/version and only invokes while the chat is unread; optimistic state changes synchronously before another automatic trigger.
    - Introduced by diff: true; previous behavior: For protocol versions without ChatIsReadChanged, setChatReadState returned false before any host dispatch or local state update, causing callers to retry only after relevant observable changes.; critical-path effect: The local state update completes before dispatch and dispatch does not await remote completion, so transport latency is off the immediate UI critical path; serialization/send work is synchronous.
- Verdict: No finding. A new boundary call is intentional compatibility behavior, and the reviewed callers do not provide a realistic hot/repeated trigger for duplicate dispatches.

### Scenario 3: Mark an entire legacy session, section, or all unread sessions read

- Critical path: For each selected legacy session, the provider updates all aggregate chat observables and sends one session-level read action. Bulk commands await Promise.all, but dispatch itself is fire-and-forget and local optimistic updates happen synchronously.
- Scaling input: Number of unread sessions selected plus total already-materialized aggregate chats across those sessions. UI callers filter to unread sessions, making effective boundary cardinality equal to the intended update set.
- Effective concurrency: Bulk management uses Promise.all across selected sessions, but each legacy provider method performs synchronous local work and one immediate dispatch. Aggregate transport burst equals the number of unread legacy sessions selected; there is no added per-chat boundary fan-out.
- Cache behavior: All operations target cached sessions. No cold fetch is introduced, no negative cache is involved, and no new retained state survives beyond existing adapter/cache lifetimes.
- Mechanism confidence: High confidence in one dispatch per selected legacy session and in caller-side unread filtering from the traced global, section, and automation actions.
- Magnitude uncertainty: A user may have many unread legacy sessions, but one persistence action per intentionally updated session is the minimum legacy protocol cardinality; no narrower supported legacy action can represent multiple sessions together.
- Expensive boundaries:
  - IPC/network at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:setSessionReadState/\_setLegacySessionReadState</code>: Send one SessionIsReadChanged JSON-RPC notification per legacy session selected for the bulk operation.; cardinality: One call per effective unread session after UI filtering; global, section, and automation bulk callers filter out sessions whose cached isRead is already true.
    - Introduced by diff: true; previous behavior: Legacy hosts received no read action from this provider path because unsupported chat-level operations were rejected; current-protocol hosts already fan out unread chats plus a session action using existing behavior.; critical-path effect: Synchronous serialization/send occurs during the bulk command, while host persistence/processing is asynchronous and not awaited.
- Verdict: No reportable regression. The boundary scales with the intended number of sessions changed rather than with chats, and no redundant calls remain after effective caller filtering.

### Scenario 4: Receive a legacy session read-state notification or status delta

- Critical path: The existing Agent Host notification handler synchronously propagates the session-level boolean to cached aggregate chats before firing one sessions-changed event. No outbound dispatch is made from this receive path.
- Scaling input: Number of aggregate chats in the cached session per actual inbound read-state event.
- Effective concurrency: Handled synchronously in the existing event/transaction flow; repeated identical notifications perform a chat scan but do not emit a sessions-changed event when no state differs.
- Cache behavior: Warm cached adapters are updated in place. Identical state is recognized through per-chat/session comparisons, avoiding observable writes and downstream change events, though the bounded scan remains.
- Mechanism confidence: High confidence in the linear local scan, single conditional UI event, and absence of an outbound boundary from the receive path.
- Magnitude uncertainty: Host event frequency is not quantified, but read-state changes are user/session events rather than frame, input, render, or streaming-token events.
- Expensive boundaries:
  - IPC/network at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_handleIsReadChanged/\_handleSessionSummaryChanged</code>: Receive the pre-existing Agent Host action/status notification that triggered the handler.; cardinality: One inbound notification per host event; the diff does not introduce or multiply inbound notifications.
    - Introduced by diff: false; previous behavior: The same inbound event reached these handlers, but only the session observable was updated; the diff adds bounded local propagation to materialized chats.; critical-path effect: The changed in-memory reconciliation runs after receipt and before observers see the updated cached session.
- Verdict: No finding. The diff adds linear local reconciliation on a low-frequency state event without boundary fan-out or unbounded retention.

**Summary:** Reviewed all three changed files and all diff pages under the performance focus. Traced legacy read-state hydration, automatic and explicit chat reads, bulk session reads, inbound notifications, observable scans, cache behavior, and JSON-RPC dispatch transport. The only new expensive boundary is one intended legacy session-level dispatch per accepted update; production callers deduplicate or filter unread state, and no realistic redundant hot-path fan-out, unbounded retention, or critical-path blocking regression was established.
