# Performance review: sessions: Use first-prompt titles for Cloud Sandboxes

[PR #339620](https://github.com/microsoft/vscode/pull/339620) at `07c6ede3e58fe3739c0ce9772e3cb3091860a167`

## Findings (1)

### 1. [medium] Do not block the first prompt on task-title persistence

**Finding ID:** `PERF-F7FC997029BA`  
**Location:** <code>src/vs/sessions/contrib/providers/copilotChatSessions/browser/copilotChatSessionsProvider.ts:1758</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** one Mission Control HTTP PATCH per newly created sandbox session  
**Scaling:** The cost is one additional serialized network request for every Cloud Sandbox creation; concurrent creations each issue their own PATCH, while each individual first turn cannot progress until its PATCH completes.  
**Outcome:** increased latency and a blocked first-turn critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After sandbox preparation and model carry-over, the code dispatched the first chat request immediately; no task-title HTTP request was on this segment of the first-turn critical path.  
**Changed behavior:** Every new sandbox first turn now serially waits for a Mission Control task-title PATCH to complete before the chat request is dispatched.  
**Confidence:** 0.99 — The changed await, handler binding, HTTP implementation, 10-second timeout, and following send call are all directly traced. The only magnitude uncertainty is typical Mission Control latency; the critical-path network round trip is unconditional for this creation flow.

**Causal diff evidence:** RIGHT line 1758 adds \`await raceCancellationError(provisioned.provider.renameSession(...), token)\` immediately before \`provider.sendRequest\`; the provisioned CloudSandboxSessionsProvider has a task rename handler bound by CloudSandboxAgentHostContribution to \`\_renameSandboxSession\`, which awaits \`ICloudSandboxApiService.renameTask\`, an HTTP PATCH with a 10,000 ms timeout.

Starting a Cloud Sandbox session incurs an extra control-plane network round trip before the user's prompt reaches the agent, increasing time to first response by the PATCH latency and potentially by up to the request timeout on a slow service.

**Evidence:** \`provisionSession\` calls \`\_ensureProvider\` with the newly created task/session IDs, which binds \`setTaskRenameHandler(... \_renameSandboxSession ...)\`. \`CloudSandboxSessionsProvider.renameSession\` awaits that handler before queuing/updating the title. \`\_renameSandboxSession\` awaits \`\_apiService.renameTask\`, and \`CloudSandboxApiService.renameTask\` performs a PATCH using \`REQUEST\_TIMEOUT\_MS = 10\_000\`. Only after the added await resolves does line 1759 call \`sendRequest\`.

**Suggested direction:** Queue/apply the initial host title before sending, but move Mission Control title persistence off the prompt-dispatch critical path (for example, use a dedicated initial-title operation that installs the pending host title immediately and persists the task title asynchronously with explicit error reporting).

### Scenario 2: Reconcile a provisional session after delayed host creation

- Critical path: A provisional rename waits for Mission Control persistence before it enters the pending-title map. Later host listing or session-added metadata flushes one title action; that flush does not wait for a host acknowledgement.
- Scaling input: Number of simultaneously provisional sandbox sessions, effectively one entry per session and one latest title per key.
- Effective concurrency: Latest-title replacement coalesces multiple provisional renames to one pending value. Each cloud provider normally owns one sandbox session, so authoritative discovery flushes at most one queued title for that provider.
- Cache behavior: Pending titles are keyed by raw session ID, overwrite older titles for the same session, and are removed on authoritative metadata, host/local removal, or provisional eviction. There is no unbounded duplicate accumulation per session.
- Mechanism confidence: High: map replacement and all normal cleanup/flush paths are explicit in the changed code.
- Magnitude uncertainty: Host materialization timing varies, but effective cardinality is bounded to one pending title and one dispatch per session.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_refreshSessions/\_handleSessionAdded</code>: Receive authoritative session metadata from the agent host.; cardinality: One existing host listing when refresh discovers the materialized session, or one session-added notification.
    - Introduced by diff: false; previous behavior: The host metadata path already listed or notified sessions but did not flush a pending initial title.; critical-path effect: Establishes authoritative host metadata; listing latency is pre-existing, while notifications arrive asynchronously.
  - IPC at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/cloudSandboxSessionsProvider.ts:79-91</code>: Dispatch SessionTitleChanged after the host materializes the session.; cardinality: At most one title action for the latest pending title per provisional session.
    - Introduced by diff: true; previous behavior: No deferred title action was emitted.; critical-path effect: Dispatch is invoked synchronously during metadata reconciliation but does not await a remote response, so it adds only one enqueue operation to that path.
- Verdict: No additional report: the pending map is lifecycle-bounded and coalesces by session; the single deferred IPC dispatch is required for the feature and is not awaited on a remote acknowledgement.

### Scenario 4: Remove or evict a provisional sandbox before host creation

- Critical path: Removal and eviction perform constant-time map deletion with no new external boundary.
- Scaling input: Number of live provisional sessions, with one short title string per session.
- Effective concurrency: Cleanup is synchronous and per removed session.
- Cache behavior: Queued titles are explicitly deleted on local deletion, host removal, and provisional eviction; provider disposal releases all maps with the provider.
- Mechanism confidence: High: every existing provisional retirement path touched by the change also removes the pending title.
- Magnitude uncertainty: None; cleanup sites are explicit, though provider lifetime determines how long a still-valid provisional entry remains.
- Expensive boundaries: none found
- Verdict: No retention regression: pending title lifetime follows the already-bounded provisional-session lifecycle.
