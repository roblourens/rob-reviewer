# Performance review: Report failed and cancelled subagent turn outcomes

[PR #339628](https://github.com/microsoft/vscode/pull/339628) at `18d0e4e6065b0b9489636b57865399000fa91e0c`

## Findings (1)

### 1. [medium] Skip workspace-wide turn-end work for failed subagents

**Finding ID:** `PERF-C6C3C1C0A14E`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:1963</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Git subprocesses, diff-worker/database operations, and Git-state refresh work  
**Scaling:** For K task-backed subagent failures, staggered failures trigger K full child error turn-end pipelines. Same-strategy requests coalesce only while a recompute is already pending; a single failure can still enqueue both the immediate fileEditTracker session recompute and the post-checkpoint auto recompute because they use different strategies. Branch recomputation can fan out across repositories with concurrency capped at five.  
**Outcome:** Repeated background Git/diff/database work consumes CPU and I/O, reduces agent-host throughput, and can delay legitimate checkpoint and Git-state work for the parent session.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, a task whose status became failed was finalized through \`\_completeSubagentTurn\`; \`completeSubagentSession\` dispatched a child \`ChatTurnComplete\` and directly called \`\_completeTurn\`, without invoking the generic chat-contribution \`turnEnd\` pipeline.  
**Changed behavior:** The new failed outcome emits \`ChatError\` before \`subagent\_completed\`. AgentSideEffects routes that action to the child chat and invokes every \`onTurnEnd\` contribution, including workspace-wide checkpoint/changeset and GitHub-reference processing.  
**Confidence:** 0.95 — The changed task-status path, child-action routing, and downstream contribution calls are explicit. Subagent starts bypass the normal send/checkpoint-start path, but the contribution still schedules session and branch changeset recomputes, and the Git-state contributor still runs. Exact wall-clock cost varies by repository size and whether failures overlap enough to coalesce, which affects severity rather than mechanism confidence.

**Causal diff evidence:** RIGHT line 1963 adds the child \`ChatError\` emitted by \`\_emitSubagentOutcome\`; the same diff replaces the old terminal-task \`\_completeSubagentTurn(...)\` call with \`\_settleSubagentTurn(..., this.\_taskOutcome(task))\`, moving task failures into the generic error turn-end fan-out.

When an agent workflow has one or more task-backed subagents fail, each failure now starts parent-workspace recomputation that is unrelated to reporting the child outcome. In a multi-repository session this can launch Git diff work across repositories; repeated or staggered failures repeat that work and contend with the active parent workflow.

**Evidence:** \`\_taskOutcome\` turns a terminal task status into \`kind: 'failed'\`, and this added \`ChatError\` reaches \`AgentSideEffects.\_dispatchActionForSession\`, whose error branch calls \`\_chatContributions.turnEnd\`. \`CheckpointAndChangesetContribution.onTurnEnd\` accepts non-resumable errors, calls \`changesets.onTurnComplete\`, then calls \`refreshSessionChangeset(..., 'auto')\`; \`AgentHostChangesetService.onTurnComplete\` already schedules branch and containing-session recomputes with \`fileEditTracker\`. \`\_scheduleStaticRecompute\` only replaces adjacent requests with the same strategy, so the fileEditTracker and auto requests are distinct. \`GitHubReferencesContribution.onTurnEnd\` also calls \`attachSessionGitHubPullRequest\`, which refreshes Git state. None of this pipeline ran for task-backed failed statuses before the changed \`\_settleSubagentTurn\` path.

**Suggested direction:** Keep emitting and persisting the child error for state and telemetry, but prevent Tool-origin/subagent chats from running workspace-wide turn-end contributors such as checkpoint/changeset and GitHub-reference refresh. Alternatively add a child-outcome flag that those contributors can gate on; preserve the lightweight child completion/error lifecycle.
