### Scenario 1: Open a virtual pull-request workspace and initialize Workspace Trust

- Critical path: Initial Workspace Trust resolution completes before extension hosts start. Because the extension-provided canonical URI provider is not registered yet in production startup ordering, the initial service lookup returns undefined without IPC and the workbench proceeds in Restricted Mode. After the provider registers, source re-resolution is off the original workspaceTrustInitialized critical path, though trust-dependent extension readiness waits for that late transition.
- Scaling input: Current virtual workspace folders, saved workspace configuration, and explicitly supplied startup files. Effective cardinality is one canonical lookup per distinct encoded vscode-vfs URI; ordinary single-folder PR startup is one workspace URI, with a small additional count for explicit diff/merge/open arguments.
- Effective concurrency: Files and workspace folders are resolved with Promise.all within one update. Workspace-wide updates are globally serialized by the new Sequencer, so provider registrations do not overlap trust transitions.
- Cache behavior: Cold encoded virtual URIs call the provider; exact repeated URIs use \_resolvedVirtualUris. A missing provider returns immediately and remains retryable. Failed or timed-out lookups are not negative-cached, but automatic retries are limited to explicit trust checks, retry actions, workspace changes, or provider registration.
- Mechanism confidence: High confidence in the changed IPC path, startup ordering, exact cache, and sequenced concurrency; low confidence that realistic cardinality or provider cost creates a performance regression.
- Magnitude uncertainty: The companion provider implementation is outside this repository, so whether a provider IPC performs network work and its duration cannot be established from the supplied change. Explicit startup-file cardinality can vary but is ordinarily small.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/workspaces/common/workspaceTrust.ts:getCanonicalUri and src/vs/workbench/api/browser/mainThreadWorkspace.ts:$registerCanonicalUriProvider</code>: Main thread invokes the extension-host canonical URI provider through $provideCanonicalUri.; cardinality: Normally one call for the encoded workspace URI after provider registration; plus one per distinct explicit startup file/folder. Promise.all permits those calls concurrently.
    - Introduced by diff: true; previous behavior: Encoded vscode-vfs authorities were stripped synchronously, with no extension-host IPC and immediate inheritance of the base repository identity.; critical-path effect: Not on the initial production workspaceTrustInitialized path because the provider is extension-host supplied and registers later. It is on the late trust-resolution path and gates enabling extensions that require trust.
- Verdict: No finding. The new boundary is required to establish the correct source identity, is off initial workbench startup in normal ordering, and has bounded effective cardinality for the touched workflow.

### Scenario 2: Check or mutate trust for virtual resources, including opening files and extension API trust checks

- Critical path: getUriTrustInfo awaits canonical provider resolution before returning trust. Trust mutations additionally await canonicalization before storage and workspace trust transition. Warm exact-URI lookups avoid the provider.

Failures remain marked unresolved and retry on later checks. The maps are not explicitly size-bounded, but inspected production callers primarily check workspace/repository/folder identities, and the diff does not establish realistic unbounded file-level growth large enough for a high-confidence regression finding.
- Mechanism confidence: High confidence in per-cold-URI IPC and lifetime cache mechanics; insufficient evidence of a realistic high-cardinality trigger or material impact.
- Magnitude uncertainty: Extensions can call isResourceTrusted on arbitrary URIs, but repository evidence does not show a hot built-in path generating a large number of unique encoded vscode-vfs file keys. The external provider's internal cache and network behavior are unknown.

### Scenario 3: Canonical URI provider registration, replacement, or extension-host restart

- Critical path: Registration synchronously invalidates resolved entries and schedules a workspace trust refresh. The refresh awaits current workspace canonicalization before publishing trust changes; provider-triggered refreshes queue behind any in-flight update.
- Scaling input: Number of cached resolved virtual URI keys plus current workspace/startup URIs. Provider registration is typically once per extension-host lifetime.
- Effective concurrency: Synchronous cache invalidation is single-threaded. All refreshes are serialized by \_workspaceTrustUpdateSequencer; canonical lookups inside each refresh run concurrently per URI.
- Cache behavior: On registration, resolved entries are moved to unresolved and the resolved map is cleared. Current workspace entries are refreshed and become resolved again. Provider disposal alone preserves the last verified mappings. Historical unresolved entries can remain, but provider replacement is infrequent and no realistic large retained key population was established.
- Mechanism confidence: High confidence in invalidation, serialization, and bounded retry behavior; low confidence of material cost at realistic registration frequency.
- Magnitude uncertainty: Extension-host restart frequency and the number of prior virtual trust lookups vary. No evidence shows repeated registration on a hot path or a large cache in ordinary PR workspaces.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/workspaces/common/workspaceTrust.ts:registerListeners</code>: Re-resolve current virtual workspace identities against the newly registered extension-host provider.; cardinality: One call per distinct current encoded workspace/startup URI per registration, with at most two bounded attempts if the provider changes during resolution.
    - Introduced by diff: true; previous behavior: Provider registration did not affect Workspace Trust and caused no trust refresh IPC.; critical-path effect: Blocks the provider-triggered trust refresh but not the already-completed initial workbench trust initialization.
- Verdict: No finding. Registration-triggered work is infrequent, serialized, and bounded to current resources after invalidation.

### Scenario 4: Use the Workspace Trust editor to retry source verification or edit trusted URIs

- Critical path: Retry and trust-list edits await canonical verification before UI completion. The clicked action is disabled while awaiting the request, and render is debounced.
- Scaling input: Current workspace URI count for retry, or number of trusted URI entries submitted by the editor. Typical lists are small; unchanged approvals bypass provider resolution.
- Effective concurrency: A single action button prevents duplicate clicks while pending. New URIs are canonicalized concurrently, while workspace updates are sequenced.
- Cache behavior: Retry reuses successful mappings and re-attempts unresolved mappings. Trust-list replacement recognizes unchanged stored identities and avoids provider calls for them.
- Mechanism confidence: High confidence in the action critical path and bounded call count.
- Magnitude uncertainty: Provider latency is unknown because implementation is external, but user actions are low-frequency and duplicate clicks are suppressed.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/workspaces/common/workspaceTrust.ts:resolveWorkspaceTrust/setTrustedUris</code>: Canonicalize unresolved workspace or newly added encoded virtual trust entries through the extension host.; cardinality: One call per unresolved current workspace URI on retry, or per newly introduced encoded trust entry; unchanged stored entries perform zero calls.
    - Introduced by diff: true; previous behavior: Retry did not exist and trust-list edits used local authority normalization without provider IPC.; critical-path effect: Directly gates action completion, with the button disabled during the await.
  - serialization at <code>src/vs/workbench/services/workspaces/common/workspaceTrust.ts:setTrustedUris/saveTrustInfo</code>: Persist the updated trusted URI list.; cardinality: One storage write for a successful changed list, as before.
    - Introduced by diff: false; previous behavior: Trust-list edits already serialized and stored the resulting approvals.; critical-path effect: Blocks completion of a successful edit after source verification.
- Verdict: No finding. Added latency is bounded, required for verification, and duplicate UI-triggered work is suppressed.
