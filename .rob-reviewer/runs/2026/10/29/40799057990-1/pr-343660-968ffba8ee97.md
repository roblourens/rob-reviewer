## Findings (2)

### 1. [low] Bound platform collision scans as the course grows

**Finding ID:** `PERF-2A97E68FD809`  
**Location:** <code>src/vs/workbench/contrib/chat/common/chatPetJumpGame.ts:342</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU iterations and square-root collision calculations over retained platform objects  
**Scaling:** After reaching N platforms, airborne gameplay performs roughly 120N platform-state visits plus 120N collision tests per second, and rendering adds about 60N visibility tests per second; N only increases for the lifetime of the run.  
**Outcome:** steadily increasing frame CPU time, lower rendering throughput, and eventual gameplay jank in long high-score runs  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The product had no jump-game course or per-frame physics scans before this PR, so chat idle/input paths did not retain and revisit an ever-growing platform history.  
**Changed behavior:** The new course generator appends platforms indefinitely, and line 342 tests every retained platform for every fixed physics substep even though only platforms crossing the player's short vertical trajectory can collide; separate new loops also update and render-scan the full history.  
**Confidence:** 0.97 — The model appends every generated platform and never removes one, while the fixed 120 Hz physics loop and 60 Hz renderer explicitly iterate the complete arrays. The linear mechanism and hot-path reachability are certain; only how long typical users pursue high scores before the growth becomes noticeable is uncertain.

**Causal diff evidence:** Added \`ensurePlatforms\` lines 153/181 only push onto \`\_platforms\`; added line 342 loops over all \`\_platforms\` inside \`step()\`, which \`advance()\` runs at 120 Hz, while browser line 252 independently scans all model platforms each animation frame.

A player pursuing an extended high-score run accumulates hundreds or thousands of old platforms; even when only a handful are visible or near the player, all old platforms continue consuming physics and render CPU every frame, so controls and animation progressively stutter.

**Evidence:** The array is height-ordered and monotonically extended by \`ensurePlatforms\`, with no pruning or index. \`step()\` first loops over all platforms at line 267 and, while airborne, line 342 loops over all of them again and calls \`crossingTime\` (including \`Math.sqrt\`) for each. The requestAnimationFrame renderer also traverses the complete array merely to reject offscreen entries. Tests exercise generation only to bounded heights/16 hops and do not establish a runtime cap.

**Suggested direction:** Preserve lower-platform landing semantics but index the height-ordered platforms and query only the current trajectory/viewport range; track moving and actively crumbling platforms separately (or compute their phase lazily) so offscreen history is not revisited at 120 Hz.

### 2. [medium] Move the overlay geometry read before frame writes

**Finding ID:** `PERF-00D15D3A2362`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatPetJumpGame.ts:306</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** synchronous DOM style recalculation and layout work  
**Scaling:** The forced flush occurs once per rendered gameplay frame (typically 60 times per second) after mutations to every visible platform and wall; its cost grows with the dirty DOM/layout subtree.  
**Outcome:** extra main-thread layout passes and dropped animation frames during jumps  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no jump-game animation loop, no per-frame platform style mutation, and no overlay geometry read on this path.  
**Changed behavior:** The added render loop mutates platform and wall geometry, then calls getBoundingClientRect on the overlay before applying pet and gauge writes, splitting one animation frame into a forced layout followed by another set of invalidating writes.  
**Confidence:** 0.96 — The new requestAnimationFrame loop is explicit, and render writes layout-affecting left/top/width styles for visible platforms before synchronously reading overlay geometry on every active frame. During jumps those values change continuously, so the read-after-write flush is not speculative; exact cost varies with browser and workbench size.

**Causal diff evidence:** Added line 306 reads \`this.overlay.getBoundingClientRect()\` after added lines 252-305 have assigned layout-affecting \`left\`, \`top\`, \`width\`, and \`height\` styles; added \`scheduleFrame\` calls \`render()\` and reschedules itself every animation frame.

While the jump game is active, especially during camera movement, the renderer can force an avoidable synchronous layout every frame and then invalidate layout again, consuming frame budget and making animation/input visibly stutter on slower or layout-heavy workbenches.

**Evidence:** \`scheduleFrame()\` executes \`render()\` on each requestAnimationFrame. In \`render\`, visible platform and wall positions/sizes are written first, then line 306 synchronously requests geometry, and pet/gauge positions are written afterward. On airborne frames camera height changes all visible platform tops, guaranteeing dirty layout before the read.

**Suggested direction:** Cache the overlay-to-bounds offset during \`layout()\`/game setup, or perform the overlay geometry read at the start of the frame before any DOM writes, then batch all style updates afterward.
