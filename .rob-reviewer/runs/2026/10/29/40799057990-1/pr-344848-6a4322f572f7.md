- Critical path: The keyboard/mouse tooltip action calls QuickInputList.showHover, settles the entrance animation, lazily creates the fixed hover host, and synchronously renders and lays out one HoverWidget before it is visible. This work is on the tooltip-display critical path.

- Effective concurrency: All DOM construction and layout run serially on the UI thread; HoverService replacement prevents a burst of concurrent top-level item hovers.
- Cache behavior: The viewport host is lazy on the first tooltip and reused thereafter. A hidden controller keeps only that single host under its hidden subtree; disposing the controller disposes/removes the parent subtree. Hover contents themselves are not newly cached by this diff.
- Mechanism confidence: High: the changed showHover path, one-host lazy initialization, and prior-hover disposal are explicit in QuickInputList and HoverService.
- Magnitude uncertainty: Exact hover layout duration varies with tooltip markup and DOM size, but the diff adds only constant class/host work and does not increase active-hover cardinality.
- Expensive boundaries: none found
- Verdict: No reportable regression. The new work is bounded to first use or one class update per hover, while existing HoverWidget rendering/layout remains the dominant synchronous work.

### Scenario 2: Resize, realign, relayout, or drag a Quick Pick while an item tooltip is shown

- Critical path: QuickInputController.updateLayout writes picker geometry, lays out the list/tree, then the new hideHoverIfMoved check reads the list rectangle and synchronously disposes the hover if its viewport position changed. The geometry read is on the relayout event's UI-thread critical path.
- Scaling input: Host resize/layout events, content-height updates, and drag updates while a tooltip is live. An actual position change disposes the tooltip on the first such event; unchanged-position relayouts can repeat one rectangle read per event.
- Effective concurrency: Events are serialized on the UI thread. There is no queue, subprocess, IPC, or asynchronous fan-out; drag and resize updates invoke layout synchronously.
- Cache behavior: The recorded top/left pair is captured once when the hover is shown. Once the hover is disposed, the isDisposed guard skips subsequent geometry reads until another tooltip is shown.
- Mechanism confidence: High for the changed read-after-write path and its one-movement bound; medium for any measurable browser cost because tree layout already performs substantial synchronous DOM work.
- Magnitude uncertainty: A rectangle read can force style/layout after preceding writes, but the movement case is self-bounding after one event and unchanged-position events already execute list/tree layout; there is insufficient evidence of meaningful added frame cost.
- Expensive boundaries: none found
- Verdict: No finding. The only plausible synchronous-layout cost is guarded by a live hover and ceases on the first movement, so the diff does not establish realistic repeated jank or scaling regression.
