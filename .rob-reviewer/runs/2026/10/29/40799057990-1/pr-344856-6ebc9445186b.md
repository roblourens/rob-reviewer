### Scenario 1: Live MCP App tool completion and card update

- Critical path: The runtime emits one tool.execution\_complete event; CopilotAgentSession emits one ChatToolCallComplete action, the reducer commits it, the subscribed workbench receives it, and an initialized MCP App card receives one ui/notifications/tool-result notification. These steps are on the result/card update path; no new await or synchronous collection-wide work was added.
- Scaling input: Number of completed MCP App calls, number of relevant connected clients, and total JSON size of each result \_meta. The reducer and adapter retain/reuse object references and do not traverse or deep-copy nested metadata.
- Effective concurrency: Completion remains event-driven with one action per tool invocation. Protocol broadcast fans out to currently subscribed clients and the webview notification is sent once when the card initializes or completes; the diff adds no loop over tools and no new limiter or burst behavior.
- Cache behavior: No new cache is introduced. Completed tool state retains one metadata reference for the loaded conversation, and the MCP App model reuses the reconstructed result; empty and missing metadata remain distinguishable.
- Mechanism confidence: High: the complete event-to-action-to-adapter-to-webview path is explicit, and each changed line adds a field without changing call count or scheduling.
- Magnitude uncertainty: MCP result metadata is open-ended, so exact payload sizes vary by server, but the changed cost is linear payload retention/serialization on boundaries already required by the result.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:9787</code>: Carry the already-received runtime mcpResultMeta in the existing ChatToolCallComplete action.; cardinality: One existing runtime completion/action per completed MCP App invocation; effective cardinality is one metadata object per result, with no per-property boundary calls.
    - Introduced by diff: false; previous behavior: The same completion event and action were emitted without resultMetadata.; critical-path effect: The completion action must reach state/UI before the completed card is available; the diff increases payload bytes but adds no boundary round trip.
  - IPC at <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:\_broadcastAction</code>: Send the existing action notification to each relevant subscribed client.; cardinality: One send per relevant connected client for the completion action; metadata does not change client fan-out.
    - Introduced by diff: false; previous behavior: The completion action was already broadcast to the same subscribers without this field.; critical-path effect: Existing state synchronization boundary; only the serialized action size grows by the metadata size.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatMcpAppModel.ts:\_sendToolResult</code>: Post the reconstructed CallToolResult to the MCP App webview.; cardinality: One existing tool-result notification per initialized completed card (or once when a live invocation completes).
    - Introduced by diff: false; previous behavior: The same notification carried content, structuredContent, and error state but omitted result \_meta.; critical-path effect: Required for the app to consume its result; the diff adds \_meta to the existing notification rather than adding another notification.
- Verdict: No reportable regression. The intentional payload preservation adds linear bytes but no repeated reconstruction, extra boundary operation, unbounded cache, or concurrency amplification.

### Scenario 2: Cold session restore, history replay, and reopening an MCP App card

- Critical path: On a cold restore, persisted SDK events are read, mapSessionEvents builds completed tool-call states including resultMetadata, turns are synchronized to the client, and the adapter constructs the card result. Warm reads use the existing mapped-event promise/state; rendering the card then sends its existing tool-result notification.
- Scaling input: Persisted event/turn count in the loaded history window and aggregate result-metadata bytes across completed MCP App calls.
- Effective concurrency: Persisted event pages are fetched by the existing reader and mapped once per memoized scope. Reads of events and session metadata may run in parallel as before; metadata adds no additional task or per-result I/O.
- Cache behavior: Cold restore reads and maps events. CopilotAgentSession memoizes mapped events by primary/all scope, and isolated history reads memoize by chat identity; rejected reads are evicted. Warm access reuses the promise/result and does not re-read metadata.
- Mechanism confidence: High: both history callers, their paging, memoization, mapping, and adapter conversion were inspected.
- Magnitude uncertainty: The number and size of app results varies, but loaded-history cardinality and page behavior are unchanged.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_computeMappedEvents and src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_doReadPersistedChatHistory</code>: Read persisted runtime events in pages of up to 1000 events.; cardinality: Existing paginated history reads based on event count; the diff does not increase request count, though returned event bytes include metadata supplied by the runtime.
    - Introduced by diff: false; previous behavior: The same persisted events were read and mapped, but the mapped tool-call state dropped mcpResultMeta.; critical-path effect: Cold restore waits for the existing history read and mapping; warm memoized reads do not repeat it.
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_computeMappedEvents</code>: Open the existing session database and restore stored shell/resource outputs.; cardinality: One existing database scope per history reconstruction plus existing resource restoration work; result metadata causes no database operation.
    - Introduced by diff: false; previous behavior: Identical database access occurred while metadata was omitted from mapped tool-call state.; critical-path effect: Existing restore boundary remains on the cold path and is unaffected in count or placement.
  - IPC at <code>src/vs/platform/agentHost/common/state/protocol/channels-chat/actions.ts:ChatTurnsLoadedAction</code>: Synchronize loaded turns, including completed tool-call metadata, to the client.; cardinality: One existing turns-loaded action per loaded history page/window, carrying all turns in that page.
    - Introduced by diff: false; previous behavior: The action already transported the same turns without resultMetadata.; critical-path effect: History display waits for this existing action; payload bytes increase linearly with metadata in loaded MCP App results.
- Verdict: No reportable regression. The diff preserves data in an already-loaded result and does not add reads, defeat memoization, or multiply mapping work.

### Scenario 3: Conversation import or move to a remote agent host

- Critical path: The client serializes the imported conversation once. Payloads at or below 1 MiB use the existing createSession request; larger payloads are split into 1 MiB chunks and sent sequentially before createSession. Result metadata now contributes to the serialized transcript size.
- Scaling input: Aggregate imported transcript size, especially total MCP App result-metadata bytes across historical tool calls.
- Effective concurrency: Large imports deliberately serialize extension requests one chunk at a time; the diff does not alter this sequencing or create parallel requests.
- Cache behavior: There is no import cache; each explicit import serializes once. Staged chunks are temporary transfer data, and bulky import metadata is removed after extraction by existing code.
- Mechanism confidence: High: the serializer, 1 MiB threshold, chunk splitter, and sequential request loop were inspected.
- Magnitude uncertainty: Open metadata can vary in size and may add chunks, but there is no evidence in the diff of duplicate encoding, pre-cap transformation, or realistic pathological amplification beyond the required bytes.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:1927</code>: JSON.stringify the full imported conversation, now including resultMetadata accepted by the import schema.; cardinality: One full serialization per imported conversation; work scales with total transcript bytes, including metadata.
    - Introduced by diff: false; previous behavior: The same transcript was serialized once, but completed tool results had no resultMetadata field to include.; critical-path effect: Serialization is on the session-create critical path as before; metadata adds only its own linear bytes.
  - IPC at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:createSession</code>: Send the direct createSession request or sequential staged import chunks.; cardinality: One request below the 1 MiB threshold; otherwise ceil(serialized UTF-16 code units / 1 MiB) staged requests plus createSession. Metadata can increase bytes and may cross an existing chunk boundary, but does not create per-tool requests.
    - Introduced by diff: false; previous behavior: The same threshold and sequential chunking applied to a transcript that omitted result metadata.; critical-path effect: Chunk transfer must finish before remote session creation, as before.
- Verdict: No reportable regression. Carrying required metadata increases transfer proportionally, while existing chunking bounds each request and no avoidable duplicate serialization or per-result boundary fan-out is introduced.

**Summary:** Completed the performance pass over all 15 changed files. The change preserves one open metadata object per completed MCP App result through existing live, replay, confirmation, import, and webview paths. Costs scale linearly with required payload bytes; object references are reused, history reads remain memoized/paged, import remains chunked, and no new expensive-boundary call count, eager work, repeated work, cache leak, or concurrency burst was found.
