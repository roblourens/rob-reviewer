## Findings (1)

### 1. [medium] Dispose the per-row menu after extracting inline actions

**Finding ID:** `PERF-0C14E04E4505`  
**Location:** <code>src/vs/workbench/contrib/debug/browser/variablesView.ts:433</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Menu instances, overlay maps, RunOnceSchedulers, emitters, and MenuRegistry event subscriptions  
**Scaling:** Retention grows by one menu for every rendered variable row on each variables-tree refresh, rerender, or newly visible row; repeated stepping and scrolling therefore accumulate O(rendered rows × refreshes) live subscriptions over the debug session.  
**Outcome:** Retained memory and increasing event fan-out/CPU and GC pressure during long debugging sessions  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The Variables view created one DebugVariablesContext menu in its constructor and registered it with the view's lifetime disposable store, so menu state and its registry listener stayed bounded to one instance.  
**Changed behavior:** Each VariablesRenderer.renderActionBar call now creates a fresh DebugVariablesContext menu for an individual row, but only the extracted actions are added to elementDisposable; the menu itself is never disposed.  
**Confidence:** 0.99 — The changed per-row call site, repeated render path, prior singleton behavior, and Menu's unconditional global registry subscription are directly visible in the repository; only the exact rate at which users step or scroll is workload-dependent.

**Causal diff evidence:** The added \`const menu = this.menuService.createMenu(MenuId.DebugVariablesContext, contextKeyService);\` at line 433 replaces the deleted view-owned singleton menu but does not register or dispose the new per-render instance.

While stepping or switching stack frames, the variables tree repeatedly renders all visible rows. Every render leaves another MenuRegistry listener alive, so a long session can retain thousands of menu objects and make later menu-contribution changes fan out across all of them, causing memory growth and UI/GC overhead.

**Evidence:** VariablesView refreshes the tree on debug view updates and resets input while stepping; renderActionBar is called for each rendered variable. MenuService.createMenu constructs Menu, whose constructor unconditionally adds a MenuRegistry.onDidChangeMenu subscription to its DisposableStore, and that subscription is removed only by menu.dispose(). Here createAndFillInContextMenuActions is the sole disposable retained, so row disposal cannot release the menu. Nearby testing action providers use try/finally and menu.dispose() immediately after extracting actions, establishing that the actions do not require the menu to remain alive.

**Suggested direction:** Wrap action extraction in try/finally and call menu.dispose() immediately afterward, as the testing action providers do (or otherwise add the menu to a disposable that is guaranteed to run for every row render).

### Scenario 2: Choose View Memory for a variable when the hex editor is installed, then read or edit target memory

- Critical path: The command waits for installed-extension registration/lookup, opens the hex editor, and the editor's file operations synchronously depend on the debug-memory provider. Each provider read/write awaits a DAP request and base64 decode/encode before that chunk can be consumed.
- Scaling input: Memory I/O scales with bytes/pages requested by the hex editor. Through FileService's buffered path the nominal chunk size is 256 KiB, giving approximately one DAP read per requested chunk; writes produce one DAP write per provider write call.
- Effective concurrency: The provider adds no parallel fan-out, limiter, or coalescer: each read/write maps to one awaited DAP request, with aggregate concurrency determined by the hex editor/FileService caller. File-descriptor regions are disposed on close and session end.
- Cache behavior: Installed-extension lookup uses the in-memory extension registry after readiness. Memory data has no cache or request coalescing, so cold and warm reads both reach the adapter; this is appropriate for mutable debuggee memory and invalidation semantics.
- Mechanism confidence: High for the call path and cardinality; the provider performs no hidden per-byte or per-range DAP fan-out.
- Magnitude uncertainty: Actual page size, read-ahead, and concurrent request count are controlled by the external hex editor version, but the one-boundary-call-per-provider-call mapping is certain.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/debug/common/debugModel.ts:MemoryRegion.read -&gt; debugSession.ts:readMemory -&gt; rawDebugSession.ts:send</code>: DAP readMemory request and base64 response transfer; cardinality: One adapter request per provider read/page requested by the consumer; no loop in the changed provider multiplies a single chunk into additional requests.
    - Introduced by diff: true; previous behavior: There was no debug-memory filesystem or View Memory workflow.; critical-path effect: The requested memory chunk cannot render until the adapter response arrives and is decoded.
  - IPC at <code>src/vs/workbench/contrib/debug/common/debugModel.ts:MemoryRegion.write -&gt; debugSession.ts:writeMemory -&gt; rawDebugSession.ts:send</code>: DAP writeMemory request with base64 payload; cardinality: One adapter request per provider write call.

    - Introduced by diff: true; previous behavior: The scheme and provider did not exist.; critical-path effect: These virtual filesystem calls are the bridge to the DAP requests and are on the editor's memory-I/O critical path.
- Verdict: No additional reportable regression: the new boundary work is explicitly requested feature work and is one-for-one with consumer chunks, with descriptor cleanup present.
