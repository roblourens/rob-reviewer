# Performance review: Fix extension-host access to agent-host language models

[PR #343139](https://github.com/microsoft/vscode/pull/343139) at `dd521108f7d99959f05331db8c07fbbcfe7ffae1`

## Findings (1)

### 1. [medium] Avoid a metadata RPC before every token count

**Finding ID:** `PERF-69658ADDFE67`  
**Location:** <code>src/vs/workbench/api/common/extHostLanguageModels.ts:540</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** extension-host/main-thread IPC calls and metadata serialization  
**Scaling:** For N messages/token-count operations, the path adds N metadata lookup RPCs; the Copilot tokenizer awaits them sequentially, so latency accumulates linearly with conversation length.  
**Outcome:** increased latency on the request critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Local model token counts dispatch directly to their provider without re-resolving metadata, and external models were not usable before this PR. In the new external bridge, the API object already holds cached metadata and the count RPC itself is authoritative, but the changed line adds a separate lookup before every count.  
**Changed behavior:** External-model token counting now performs a metadata-lookup IPC round trip on every invocation, then performs the actual token-count IPC round trip.  
**Confidence:** 0.98 — The changed call path is explicit and unconditional for external models. Repository callers establish realistic multiplicity: \`ExtensionContributedChatTokenizer.countMessagesTokens\` iterates conversation messages sequentially and \`countMessageTokens\` calls \`languageModel.countTokens\` once per message. The only uncertainty is absolute IPC duration, which affects severity rather than the mechanism.

**Causal diff evidence:** The added \`await that.\_ensureModel(modelId);\` on RIGHT line 540 runs before every \`countTokens\` call. \`\_ensureModel\` calls \`\_lookupExternalModels(\[modelId\])\` for every non-local model, and \`\_lookupExternalModels\` excludes only \`\_localModels\`, not cached \`\_externalModels\`, so this always invokes the new \`$lookupChatModels\` RPC before \`\_computeTokenLength\` invokes the separate \`$countTokens\` RPC.

Extensions using a selected agent-host model block prompt construction on one extra extension-host/main-thread IPC round trip per history message. Longer conversations therefore incur linearly increasing latency before the model request can start.

**Evidence:** \`countTokens\` awaits \`\_ensureModel\` at \`extHostLanguageModels.ts:540\`; \`\_ensureModel\` refreshes every non-local model, while \`\_lookupExternalModels\` filters only local models and calls \`$lookupChatModels\`. It then calls \`\_computeTokenLength\`, whose external branch calls \`$countTokens\`. In \`extensions/copilot/src/platform/endpoint/vscode-node/extChatTokenizer.ts\`, \`countMessagesTokens\` awaits \`countMessageTokens\` inside a loop, and each message calls this API, making the extra round trips serial on prompt construction. The main-thread \`$countTokens\` path already performs the authoritative model lookup through \`LanguageModelsService.computeTokenLength\`, so a separate freshness lookup is not required to discover a removed model.

**Suggested direction:** Do not call \`\_ensureModel\` from \`countTokens\`; dispatch \`\_computeTokenLength\` directly and translate the authoritative main-thread missing-model failure if needed. If metadata freshness is required elsewhere, retain it for request authorization or coalesce/cache it across operations rather than refreshing once per token count.

### Scenario 2: An extension counts tokens for an external agent-host model while building a prompt

- Critical path: For every \`countTokens\`, the extension host awaits metadata lookup and only then starts the count RPC. Copilot's extension tokenizer awaits one count per conversation message in sequence, so all lookup round trips are on the prompt/request critical path.
- Scaling input: Conversation/history message count N or other token-count invocations; the added lookup count is N after model deduplication because all calls use the same model but are not coalesced.
- Effective concurrency: No coalescing is present for metadata refreshes. The established history-tokenization caller serializes calls in a loop; concurrent callers would independently issue duplicate lookups.
- Cache behavior: The external metadata map is populated, but \`\_lookupExternalModels\` checks only \`\_localModels\`; therefore warm external entries still incur lookup. Missing results delete the old entry. There is no in-flight coalescing.
- Mechanism confidence: Very high: the unconditional call chain and sequential production caller are both directly traced.
- Magnitude uncertainty: Exact IPC latency depends on host placement, but the N serialized extra round trips are certain.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/common/extHostLanguageModels.ts:540</code>: Refresh external model metadata through \`$lookupChatModels\` before counting.; cardinality: One call per token-count invocation, including one per history message; cached external metadata does not suppress it.
    - Introduced by diff: true; previous behavior: Local counts dispatch directly to the provider; no separate freshness RPC preceded each count.; critical-path effect: Serially blocks each actual count operation.
  - IPC at <code>src/vs/workbench/api/common/extHostLanguageModels.ts:735</code>: Route the actual token count through main-thread \`$countTokens\`.; cardinality: One call per token-count invocation.
    - Introduced by diff: true; previous behavior: External models could not be counted from this extension host; local models called their provider directly.; critical-path effect: Provides the requested count and must complete before prompt sizing proceeds.
  - IPC at <code>src/vs/workbench/api/browser/mainThreadLanguageModels.ts:191</code>: If the exact target belongs to another extension host, main thread forwards token counting to that owner.; cardinality: One additional provider IPC per count in the cross-host target case.

- Verdict: Reportable medium-severity IPC latency regression; submitted as a boundary-fanout finding.

### Scenario 4: Language-model catalogues and consent accounts refresh after provider metadata changes

- Critical path: Background/provider change handling re-resolves the changed vendor, republishes agent-host aliases that reference it, rebuilds tracked consent metadata, and notifies model consumers. This work is off the model-request critical path but runs on the workbench event path.
- Scaling input: Agent-host model count A, total workbench catalogue count C, tracked provider/model count P, source metadata-change rate K; the added target lookup work grows approximately K\*A\*(A+C), while consent reconciliation scans tracked metadata.
- Effective concurrency: Vendor resolutions are serialized and queued duplicates with matching provider/silent mode are coalesced. Different vendors may resolve independently. Agent-host aliases ignore agent-host vendor events to avoid feedback loops.
- Cache behavior: LanguageModelsService replaces each vendor's cache after resolution and coalesces queued resolutions. MainThreadLanguageModels additionally tracks complete per-vendor metadata for auth accounts and rebuilds it after change events. Agent-host target matching is recomputed rather than cached to preserve current metadata.
- Mechanism confidence: High for the work and coalescing mechanism; lower only for real-world magnitude.

    - Introduced by diff: false; previous behavior: Extension-owned provider refreshes already crossed this boundary.; critical-path effect: Background catalogue availability waits for it, but active model requests do not.
- Verdict: No finding: the diff adds repeated catalogue scans, but with vendor coalescing and currently bounded model counts there is insufficient evidence of concrete user-visible impact.
