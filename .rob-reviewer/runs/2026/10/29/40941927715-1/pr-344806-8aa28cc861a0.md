**Relevant issue families:** synchronous-ui-work, repeated-work, cleanup-lifecycle, eager-work

### Scenario 1: Open and interact with the Command Palette or another quick input, including opening its text-input context menu

- Critical path: Showing the picker creates/reuses the quick-input UI and starts a 250 ms CSS transform/opacity animation. A pointer/context-menu gesture synchronously queries and finishes only animations on the single widget before the hosted menu is laid out; no subprocess, filesystem, database, network, or IPC work is on the open/menu-render critical path. Clipboard work starts only if Paste is explicitly selected.
- Scaling input: Cost is constant per gesture: one widget animation query and an eight-entry menu. Quick-pick item count does not multiply this work because the menu belongs to the input, not each row.
- Effective concurrency: One lazily-created QuickInputController per quick-input service (or per standalone editor scope), one active quick input, and the shared context-view service permits one active context view. There is no fan-out or task burst.
- Cache behavior: No cache participates in opening or rendering the hosted menu. The controller and UI are lazily created and reused; action arrays are small and bounded. Clipboard reads are intentionally uncached to preserve current clipboard contents.
- Mechanism confidence: High confidence in the call path and constant cardinality from the changed listeners, controller ownership, and context-menu implementation.
- Magnitude uncertainty: Browser style/animation-query cost and compositor promotion vary by engine, but the query targets one element and is gesture-bound. No evidence shows measurable jank from removing will-change; transform animations are otherwise unchanged.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/clipboard/browser/textInputActions.ts:createTextInputActions Paste action; src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts:NativeClipboardService.readText</code>: Read clipboard text through the native host when the user explicitly selects Paste on desktop.; cardinality: Exactly one IPC call per explicit Paste action; independent of quick-pick item count and not performed when opening the picker or menu.
    - Introduced by diff: false; previous behavior: The pre-diff workbench TextInputActionsProvider used the same createTextInputActions logic and issued one clipboard read for Paste; the helper was moved without increasing read count.; critical-path effect: Blocks only completion of the explicit Paste action, not picker opening or context-menu rendering.
  - network at <code>src/vs/platform/clipboard/browser/clipboardService.ts:BrowserClipboardService.readText</code>: Invoke the browser Clipboard API to read text on web/standalone.; cardinality: Exactly one browser API call per explicit Paste action; no per-item scaling or retries.
    - Introduced by diff: true; previous behavior: Standalone quick input previously relied on the browser's native menu; the application now invokes navigator.clipboard.readText for its custom Paste action. Workbench web quick input already reached the same clipboard service through the generic text-input menu. The changed call remains one user-triggered operation, so it does not establish a performance regression.; critical-path effect: Blocks only the selected Paste action. It is off the picker-open and menu-open critical paths.
- Verdict: No reportable regression. The new synchronous DOM work is bounded to one element per user gesture, hosted-menu lifecycle is explicitly closed on hide, and clipboard access remains one explicit action rather than fan-out.

### Scenario 2: Open a quick-input title/inline toolbar overflow menu

- Critical path: The toolbar passes its own element as domForShadowRoot, after the container capture listener finishes the opening animation. ContextMenuHandler renders one local Menu and one blocker in the shared context view; there are no external boundaries.
- Scaling input: Menu rendering scales with the bounded number of overflow actions in that toolbar, not with quick-pick row count. Current product paths do not produce these overflow menus, further limiting prevalence.
- Effective concurrency: A single context view is active globally, so toolbar menu opens are serialized by replacement rather than concurrent.
- Cache behavior: Toolbar actions already exist on the toolbar; rendering the dropdown does not add a cache or miss path.
- Mechanism confidence: High confidence from ToolBar -&gt; DropdownMenuActionViewItem -&gt; ContextMenuHandler tracing.
- Magnitude uncertainty: Exact menu DOM cost depends on action count, but no changed code increases that count or repeats rendering.
- Expensive boundaries: none found
- Verdict: No performance regression. The diff changes the DOM host, not menu cardinality, external calls, or concurrency.

### Scenario 3: Open Terminal Change Icon or session-group appearance icon picker and use the search-input context menu

- Critical path: The picker already constructs and lays out its icon grid on invocation. The change adds one delegated contextmenu listener; on right-click it creates eight lightweight actions and renders one hosted menu. Clipboard access occurs only after selecting Paste.
- Scaling input: Added work is constant per right-click and does not scale with the number of registered icons. Listener lifetime is bounded by the picker's DisposableStore.
- Effective concurrency: One picker-local listener and disposable store per invocation; the picker is disposed when the operation resolves. The shared context view limits active menus to one.
- Cache behavior: No new cache. Icon enumeration and grid creation are pre-existing eager work; the added action list is created only on context-menu opening and is fixed-size.
- Mechanism confidence: High confidence from both terminal/session callers and picker disposal flow.
- Magnitude uncertainty: The existing icon-grid construction can scale with registry size, but the diff neither introduces nor increases that work.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/userDataProfile/browser/iconPicker.ts context-menu Paste -&gt; NativeClipboardService.readText</code>: Read desktop clipboard text through native-host IPC.; cardinality: One call per explicit Paste action, not per icon. The icon registry/grid size does not multiply it.
    - Introduced by diff: false; previous behavior: Before the diff, the event bubbled to the workbench's generic TextInputActionsProvider, whose Paste action performed the same single clipboard read.; critical-path effect: Only the explicit Paste action waits for the read; picker construction, filtering, and menu opening do not.
  - network at <code>src/vs/workbench/services/userDataProfile/browser/iconPicker.ts context-menu Paste -&gt; BrowserClipboardService.readText</code>: Read text with navigator.clipboard.readText on web.; cardinality: One call per explicit Paste action, independent of icon count.
    - Introduced by diff: false; previous behavior: The generic workbench text-input context menu already exposed the same browser clipboard read before this listener hosted the menu locally.; critical-path effect: Only Paste is delayed.
- Verdict: No reportable regression. The diff changes menu ownership while preserving one clipboard boundary call and adds no icon-count-scaled work or retention.

### Scenario 4: Use text-input actions in ordinary workbench inputs or Terminal Find after helper relocation

- Critical path: Ordinary inputs retain a lazy, shared eight-action array; Terminal Find still creates the same fixed-size array on a user context-menu gesture. Paste performs one clipboard read.
- Scaling input: Constant eight-action allocation where actions are created; no dependence on input length except the existing string splice during Paste.
- Effective concurrency: One context menu and one selected action at a time; no batching or parallel reads.
- Cache behavior: Workbench generic input actions remain Lazy and shared. Terminal Find remains gesture-created and fixed-size. Clipboard contents are not cached.
- Mechanism confidence: High confidence from direct before/after helper comparison and all repository call sites.
- Magnitude uncertainty: Very large pasted strings still allocate proportional to input plus clipboard length, but that mechanism is pre-existing and not materially amplified.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/browser/actions/textInputActions.ts and src/vs/workbench/contrib/terminalContrib/find/browser/terminalFindWidget.ts -&gt; NativeClipboardService.readText</code>: Read clipboard text for Paste through native-host IPC.; cardinality: One call per explicit Paste, unchanged by moving the helper.
    - Introduced by diff: false; previous behavior: The same implementation and call count existed in the workbench helper before it moved to platform clipboard.; critical-path effect: Only Paste waits for the call.
  - network at <code>src/vs/platform/clipboard/browser/clipboardService.ts:BrowserClipboardService.readText</code>: Read clipboard text with the browser API.; cardinality: One call per explicit Paste, unchanged.
    - Introduced by diff: false; previous behavior: The moved helper already called IClipboardService.readText once.; critical-path effect: Only Paste waits for the call.
- Verdict: No performance regression. The relocation preserves allocation and boundary cardinality; the empty-read guard can only avoid an unnecessary string rewrite and input event.
