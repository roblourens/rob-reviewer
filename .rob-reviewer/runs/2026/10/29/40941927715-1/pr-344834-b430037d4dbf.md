# Performance review: agent Host: List legacy Copilot CLI sessions in  agent Host when migration is enabled

[PR #344834](https://github.com/microsoft/vscode/pull/344834) at `b430037d4dbfac3aa95f84494bfd77bae4704902`

## Findings (1)

### 1. [medium] Reuse the discovered chat instead of rereading every catalog

**Finding ID:** `PERF-8BA84819DBC1`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:5863</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SQLite transactions and catalog header/chat SELECTs on the agent-host database  
**Scaling:** The added work is O(N) database transactions for N newly discovered adoptable sessions (up to 250 per discovery batch, with further batches for larger histories); database serialization prevents the four-way discovery limiter from coalescing or parallelizing these reads.  
**Outcome:** Increased migration/discovery latency and serialized database I/O on the session-surfacing critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, announcements did not perform this default-chat catalog read; active adoptable sessions were rejected before announcement work, and archived announcements did not request a default chat.  
**Changed behavior:** Every first announcement of an adoptable legacy session now awaits \`\_readDefaultChat\`, which falls through to \`readCatalogSnapshot(\[session\])\` when no summary has yet recorded the chat.  
**Confidence:** 0.96 — The added await, provider-supplied chat value, metadata stripping, database implementation, batch size, limiter, and globally serialized transaction path are all explicit in code. Exact milliseconds vary with profile size and storage speed, so severity is medium rather than high.

**Causal diff evidence:** The added line \`const defaultChat = readSessionEhcliAdoptable(meta.\_meta) ? await this.\_readDefaultChat(meta.session) : undefined;\` introduces the awaited per-session catalog lookup directly on the surfacing path.

On a profile with a large legacy Copilot CLI history, enabling migration delays discovery registration and delays later sessions becoming addressable in the Agents window while the host executes one extra SQLite transaction per newly surfaced session.

**Evidence:** Copilot discovery already constructs \`IAgentDiscoveredChat.chat\` with \`deriveLegacyDefaultChat(session)\`, but \`\_toSessionMetadata\` explicitly removes \`chat\` before \`\_registerDiscoveredChats\` calls \`\_announceSurfacedSession\`. With no live/evicted/announced record yet, \`\_readDefaultChat\` invokes \`IAgentHostDatabase.readCatalogSnapshot\` for one session. That database method runs a transaction with header and chat SELECTs through the single \`\_transactionSequencer\`. Discovery publishes batches of up to 250 candidates; AgentService processes four concurrently, but these added catalog reads serialize at the database boundary.

**Suggested direction:** Carry the already-known \`IAgentDiscoveredChat.chat\` through registration/announcement (or prefetch default chats for the batch) and pass it to \`\_surfacedSessionSummary\`, avoiding a one-session catalog transaction per announcement.
