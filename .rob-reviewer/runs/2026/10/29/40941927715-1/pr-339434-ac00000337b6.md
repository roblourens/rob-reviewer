# Performance review: base: avoid Base64 encoding string-chain amplification

## Performance regression fixes detected (1)

### 1. serialization-allocation

**Fix location:** `src/vs/base/common/buffer.ts:434` (`RIGHT`)  
**Blamed base line:** `src/vs/base/common/buffer.ts:443`  
**Introducing path:** `src/vs/base/common/buffer.ts`  
**Introducing commit:** `29bde3176c7451e966797931aa8a1f7c3fce2983`  
**Mechanism family:** `serialization-allocation`  
**Performance category:** `memory`  
**Confidence:** 0.98

**Mechanism:** The old loop appended four individual character strings per three source bytes, producing millions of concatenations and a retained string chain for multi-megabyte resource payloads.

**Symptom:** Large Base64 resource reads incurred excessive retained memory and synchronous encoding latency before their RPC response could be sent.

**Fixed behavior:** The encoder now allocates one exact-size byte buffer, writes Base64 character codes directly, and converts to a string once, eliminating per-character string-chain construction.

**Evidence:** Deleted base line 443 is one of four single-character appends performed for every three input bytes; the neighboring deleted loop therefore creates O(input bytes) string nodes. Added line 434 allocates one exact-size byte result which is filled in place and converted once. The synchronous encoder is called on complete filesystem results before resourceRead replies in src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:3254-3257, placing that work directly on large-file RPC latency.

### Scenario 2: Frequent Base64 encoding of streamed audio and chunked Agent Host transport data

- Scaling input: Speech capture uses 4096 samples per callback, producing multi-kilobyte PCM chunks; TCP writes split up to 4 MiB of queued data into configured chunks, and Web PubSub envelopes are bounded near 900 KiB. Cost scales with bytes and callback/chunk count.
- Effective concurrency: Audio callbacks arrive sequentially on the renderer event loop. Agent Host TCP writes are serialized by \_enqueue and bounded to 64 pending writes/4 MiB; the diff adds no parallelism or burst. Web PubSub chunk creation is synchronous.
- Cache behavior: Chunks are unique and never cached; each is encoded once. Cold and warm behavior are equivalent except for runtime allocator/decoder initialization.
- Mechanism confidence: High: chunk sizes, queue bounds, and synchronous call sites are explicit; the diff does not alter boundary cardinality or concurrency.
