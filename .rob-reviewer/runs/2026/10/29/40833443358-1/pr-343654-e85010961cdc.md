### Scenario 1: Resume a Copilot session whose chat has a confirmed sandbox bypass and current policy still allows bypass

- Critical path: SDK resume/open, launch finalization, the sandbox session command, and diagnostics must complete before the resumed session wrapper is attached and usable.
- Scaling input: One resumed session and its target chat; attachment scopes affect construction of readonly path arrays as before, while bypass restoration itself remains one runtime command.
- Effective concurrency: The sandbox operation is serialized by CopilotSessionSandbox.\_configSequencer; there is one launch finalization per resumed SDK session and no aggregate per-chat fan-out.
- Cache behavior: Confirmed state and selection are read from existing session metadata/configuration. There is no new cache; pending selections take precedence, and the applied-config cache is reset once for the newly opened runtime as before.
- Mechanism confidence: High confidence from the changed launch call path, sequencer ownership, and tests asserting exactly one command and no sibling-chat mutation.
- Magnitude uncertainty: Runtime command latency varies by SDK/runtime, but it replaces the prior launch-time options update and does not increase effective boundary cardinality.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionSandbox.ts:352</code>: Invoke the runtime \`sandbox disable session\` command to restore the confirmed bypass.; cardinality: One command for the resumed session when effective confirmed state is off; no call per sibling chat or attachment scope.

  - IPC at <code>src/vs/platform/agentHost/node/agentConfigurationService.ts:1168</code>: Publish applied sandbox state through SessionMetaChanged when state changes.; cardinality: At most one metadata action for the target chat after successful application; unchanged state is suppressed, and sibling chats are not rewritten.

- Verdict: No reportable regression: the required restore adds no scaling fan-out and retains one serialized launch-time runtime operation.

### Scenario 2: Resume or create a session when the runtime rejects sandbox configuration because of managed policy

- Cache behavior: Identical outstanding host conflicts are negatively coalesced by comparing the previous host error message. A later successful application replaces the error with confirmed state. No retry loop is introduced.
- Mechanism confidence: High confidence from the explicit result branch, message deduplication, and existing finalizer cleanup path.

### Scenario 3: Background sandbox synchronization at turn start and after configuration changes

- Critical path: At turn start, sandbox synchronization is awaited before the agent loop starts; settings-triggered synchronization is serialized with path grants and other sandbox updates.

- Effective concurrency: Per-session Sequencer enforces one sandbox mutation at a time. Unchanged accepted configurations are skipped via the serialized \_appliedConfig value.
- Cache behavior: Warm path compares JSON serialization to \_appliedConfig and avoids the runtime update. Identical conflict messages are coalesced; successful synchronization clears the error by publishing accepted state.
- Mechanism confidence: High confidence from \`\_appliedConfig\`, Sequencer, and \`reportChatSandboxConflict\` equality guard.
- Magnitude uncertainty: Exact metadata transport latency is not measured, but added work occurs once per outstanding conflict rather than every turn for stable error text.

### Scenario 4: Workbench clients receive sandbox state metadata and show host or client-attributed failure notifications

- Critical path: SessionMetaChanged handling runs on the client event path; notification display occurs immediately after parsing sandbox states.
- Scaling input: Number of sandbox-state chat entries in one session metadata envelope and number of connected clients. The map scan is pre-existing; added notifications scale only with unique host conflicts and connections.
- Effective concurrency: Each live agent-host connection owns one listener and one 100-entry LRU. Connection changes dispose removed listeners; envelopes are handled serially by the event emitter.
- Cache behavior: A per-connection 100-entry LRU deduplicates both host and client errors. Disconnect removes the listener and its captured cache, preventing unbounded lifetime retention.
- Mechanism confidence: High confidence from listener ownership, fixed LRU capacity, and unchanged iteration structure.
- Magnitude uncertainty: Sessions with extremely many chats could make the pre-existing map scan larger, but the diff does not increase scan cardinality or metadata entry count per conflict beyond one target chat.
- Expensive boundaries:

    - Introduced by diff: false; previous behavior: The handler already parsed the session state and all chat sandbox states for every metadata envelope and deduplicated client errors.; critical-path effect: Synchronous client-side work on metadata delivery, but the PR adds only a discriminated key check to an already-existing scan.
  - other at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSandboxNotifications.ts:61</code>: Display a standard error notification for a host-attributed conflict.; cardinality: Once per unique error ID per connection; the LRU bounds retained keys to 100.
    - Introduced by diff: true; previous behavior: Only the requesting client received client-attributed rejection notifications.; critical-path effect: Notification dispatch occurs in the envelope handler but is bounded to newly observed errors.
- Verdict: No reportable regression: dedupe memory is bounded and disposed, and the PR does not amplify the existing per-envelope state scan.

### Scenario 5: Managed sandbox policy changes while a session contains multiple chats

- Critical path: Policy publication updates metadata and reconciles each chat's saved selection synchronously before firing configuration change events.
- Scaling input: Number of chats in the session. The existing loop remains O(chats); the changed condition only determines whether confirmed sandbox metadata is retained when bypass is allowed.
- Effective concurrency: One synchronous policy reconciliation pass per policy change; no subprocess, filesystem, database, or network calls are reached by the changed condition.
- Cache behavior: Policy and confirmed state are stored in in-memory maps/session metadata. No new cache key, retention, or invalidation behavior affecting collection size is added.
- Mechanism confidence: High confidence from the unchanged loop and changed boolean condition immediately before it.
- Magnitude uncertainty: Large chat counts increase the pre-existing reconciliation loop cost, but this PR neither adds another pass nor expands the set iterated.
- Expensive boundaries: none found
- Verdict: No reportable regression: policy reconciliation complexity and expensive-boundary count are unchanged.
