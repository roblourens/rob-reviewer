[PR #345051](https://github.com/microsoft/vscode/pull/345051) at `86fa3745e9e6e55e0bbfc8d26ac448f280b4e458`

## Findings (1)

### 1. [medium] Index published provenance before merging draft agents

**Finding ID:** `PERF-C1C1A097F5BE`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:7200</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Renderer CPU and temporary URI/metadata objects  
**Scaling:** For C client-discovered agents and P host-published agents, getCustomAgents now performs Θ(C×P) candidate comparisons (an exact find plus a full provenance filter per client agent); after materialization C and P commonly describe the same inventory, making this quadratic.  
**Outcome:** Synchronous picker/catalog refreshes take increasing CPU time and allocation/GC pressure, delaying agent-picker updates or opening/switching a draft in large customization inventories.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The draft merge built one map of published URIs and inserted each client agent once, so the merge was linear in C+P apart from the final sort.  
**Changed behavior:** Each client agent now calls \_resolvePublishedDraftAgent, which scans the complete published array for an exact URI and, when the host URI differs as intended here, scans it again while allocating validated metadata views and parsing provenance URIs.  
**Confidence:** 0.96 — The nested loop, synchronous UI call path, and shared inventory sources are directly established in code. Exact user inventory sizes vary, which affects severity, but not the quadratic mechanism or its reachability.

**Causal diff evidence:** RIGHT line 7200 adds \_resolvePublishedDraftAgent inside the loop over every client agent; that helper scans all published agents, replacing the prior direct ResourceMap insertion path.

When a workspace/profile/extensions/plugins contribute many agent files and the host advertises their materialized copies, every synchronous getCustomAgents refresh from active-session or customization changes can perform a quadratic number of URI parses/comparisons, causing visible picker latency and renderer CPU/GC spikes.

**Evidence:** AgentCustomizationScope populates clientAgents from every eligible local, user, extension, and plugin agent file (resolveLocalCustomAgents), while getEffectiveAgents returns the host-published counterparts. AgentHostAgentPicker.\_initAgent calls getCustomAgents synchronously on active-session/mode changes and onDidChangeCustomAgents. At the changed loop, every client entry calls \_resolvePublishedDraftAgent; lines 7208-7218 use published.find followed by published.filter, and readAgentCustomizationMeta allocates a result object and validates/parses sourceUri for each candidate.

**Suggested direction:** Build exact-URI and source-URI indexes from published once per getCustomAgents call (retaining an explicit ambiguous-source state), then resolve every client agent in O(1); reuse the same indexed snapshot for resolveCustomAgent where possible.
