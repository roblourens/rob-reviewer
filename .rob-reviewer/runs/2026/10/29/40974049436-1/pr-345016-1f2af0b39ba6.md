### 1. [medium] Batch ownership adoptions before refreshing every session

**Finding ID:** `PERF-2DC3F504FE41`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:10607</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** per-session customization filesystem scans and SDK IPC calls  
**Scaling:** For D late-discovered MCP servers with migrated global decisions and S loaded sessions, this loop emits D all-session change events, causing O(D×S) queued customization recomputations; active Copilot sessions additionally issue D serialized mcp.listConfigured RPCs each.  
**Outcome:** Repeated background filesystem/SDK work increases discovery latency and I/O/IPC load, especially with multiple open sessions and multiple servers in one plugin discovery result.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The same discovery merge only projected the discovered child and updated ownership metadata; it did not mutate enablement storage or trigger cross-session customization refresh/reconciliation work.  
**Changed behavior:** Late plugin discovery now migrates each matching server independently and immediately notifies all affected sessions after each migration, rather than treating the discovery result as one state transition.  
**Confidence:** 0.97 — The changed per-server call, synchronous all-session notification path, non-coalescing downstream queue, and filesystem/IPC boundaries are all explicit in the call graph. Exact user session/server counts vary, so magnitude is uncertain, but the multiplicative mechanism and realistic trigger are direct.

**Causal diff evidence:** The added call at line 10607 runs inside the loop over every live MCP server. Each successful global migration synchronously calls \_notifyDecisionChanged; \_getAffectedSessions treats a global key move as affecting every session. Before this diff, this loop performed no ownership migration and emitted no enablement refreshes.

When a plugin exposes several runtime-first MCP servers that have explicit global enablement decisions, one discovery refresh schedules multiple full customization republishes for every loaded session. AgentSideEffects appends each refresh to a per-session promise chain without coalescing; Claude republishes perform four filesystem discovery scans (and may query the SDK), while each active Copilot session independently performs an mcp.listConfigured RPC per event.

**Evidence:** The added call is inside \`for (const server of live?.customizations ?? \[\])\`. \`adoptMcpServerOwnership\` immediately invokes \`\_notifyDecisionChanged\`; moving the global key makes \`\_getAffectedSessions\` enumerate every \`getSessionUris()\` entry for both source and destination snapshots. \`AgentSideEffects.\_publishSessionCustomizationsSoon\` chains every event onto the prior promise, so D events are not collapsed, and \`\_publishSessionCustomizations\` calls \`agent.getChatCustomizations\` each time. \`ClaudeAgentSession.getSessionCustomizations\` performs parallel multi-root/rules/MCP/hooks filesystem scans, and \`CopilotAgentSession\` reacts to every matching event by running \`\_reconcileMcpServerEnablement\`, whose first boundary is \`session.rpc.mcp.listConfigured()\`.

**Suggested direction:** Apply all ownership moves from one discovery result in a single service transaction (or defer/coalesce enablement notifications for the current turn): migrate decisions synchronously so later resolution sees them, but persist once and emit one unioned session-change event after the loop. Preserve immediate single-server behavior where batching is unavailable.
