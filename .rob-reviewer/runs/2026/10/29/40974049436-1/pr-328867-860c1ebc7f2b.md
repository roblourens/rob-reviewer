- Critical path: The focused renderer walks the current menu tree, resolves one accelerator per bound action, serializes the complete menubar payload, and sends one updateMenubar IPC before the native menu reflects the refresh. - Scaling input: Total menu actions with keybindings; the added branch executes only for layout-dependent scan codes that failed the existing stable-key lookup, so effective cardinality is at most the number of bound menu items in one rebuild.
- Effective concurrency: Menu traversal and accelerator formatting are synchronous and serial. The full tree is grouped into one existing asynchronous menubar IPC update; the diff adds no queue, task, or parallel boundary work.
- Cache behavior: The keyboard mapper and its precomputed scan-code tables are reused for both cold and warm menu rebuilds. The new two-entry named-character map is module-scoped; there is no per-item retained cache, miss retry, or invalidation behavior.
- Mechanism confidence: High: the changed branch and complete consumer path are directly traced; only constant-time property checks, character checks, and a two-entry Map lookup are added after existing resolution.
- Magnitude uncertainty: Exact menu size and rebuild frequency vary by installed contributions, but the added CPU is constant per affected binding and introduces no boundary or collection-wide nested work.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/electron-browser/parts/titlebar/menubarControl.ts:doUpdateMenubar</code>: Send the complete menubar model to the Electron main process for native rendering.; cardinality: One grouped IPC call per accepted menubar rebuild, regardless of menu item count.

- Verdict: No reportable regression. Work remains O(menu items), with a small bounded increment only for previously unsupported Mac layout-dependent bindings and unchanged IPC cardinality.

### Scenario 2: macOS native context-menu opening

- Critical path: On each native context-menu invocation, the renderer recursively maps visible actions to serializable items, resolves an accelerator for each bound action, then sends the full menu in one synchronous ipcRenderer.send. - Scaling input: Visible context-menu actions and submenu actions; effective added work is one constant-time fallback for each bound action whose scan code is neither immutable nor stable.
- Effective concurrency: Menu item creation is synchronous and serial, followed by one existing renderer-to-main IPC send. No fan-out or new concurrency is introduced.
- Cache behavior: Resolved mapper tables are warm process state; no new per-menu cache exists or is needed because each fallback consists of bounded local reads. Cold and warm calls have the same asymptotic behavior.
- Mechanism confidence: High: createMenuItem calls the changed API once per bound action and popup groups all items into the unchanged single IPC boundary.
- Magnitude uncertainty: Context-menu sizes and invocation frequency vary, but the fallback has no I/O, layout read, cache growth, or nested scan.
- Expensive boundaries:

- Verdict: No reportable regression. The synchronous path receives bounded constant work and the expensive native-menu boundary remains one call per popup.
