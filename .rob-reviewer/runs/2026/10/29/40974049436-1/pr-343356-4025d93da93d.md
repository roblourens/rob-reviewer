### 1. [medium] Coalesce CRON parsing and description work per edit

**Finding ID:** `PERF-A89EE98460B7`  
**Location:** <code>src/vs/sessions/contrib/automations/browser/automationDialog.ts:1235</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** UI-thread CPU, Intl.DateTimeFormat objects, Date objects, parsed sets and temporary strings  
**Scaling:** The full chain runs once for every input event while editing a CRON field; work also grows with the number of values represented by list/range fields when descriptions format those values.  
**Outcome:** increased input latency and potential typing jank in the automation dialog  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR the dialog had no CRON editor or live CRON description, so typing in the automation form did not execute this parser/formatter chain.  
**Changed behavior:** Every CRON edit now synchronously validates inside AutomationCronInput, validates again in updateCronDescription, reparses and formats the description, then revalidates the whole form and the CRON expression again.  
**Confidence:** 0.98 — The synchronous call chain is explicit: AutomationCronInput.changed() validates before firing onDidChange; this added callback validates again before describeAutomationCron and then calls revalidate(), whose updateSaveButtonState validates a third time. describeAutomationCron reparses and creates uncached locale formatters. Exact device cost is unmeasured, but the repeated UI-thread mechanism and per-keystroke reachability are certain.

**Causal diff evidence:** The added onDidChange path calls updateCronDescription(), whose added line 1235 invokes describeAutomationCron(expression), and then revalidate(). The new AutomationCronInput.changed() already calls validate(), while updateSaveButtonState's added cronError assignment performs the third validation.

Typing or using arrow keys in a valid CRON expression can stall feedback and caret handling, especially on lower-end machines or for list-heavy expressions, because multiple ICU formatter constructions and duplicate parses occur on every key event.

**Evidence:** getAutomationCronValidationError calls validateAutomationCron, which parses and constructs an Intl.DateTimeFormat. describeAutomationCron reparses and creates fresh safeIntl DateTimeFormat instances; safeIntl.DateTimeFormat returns a new Lazy each call, so these are not shared. It also builds hourDescription and weekDays eagerly even when the final branch says every hour/every day. Thus a valid keystroke performs four parses and several formatter constructions synchronously before returning to the browser event loop.

**Suggested direction:** Parse/validate once per changed value and pass that result to both the input error state, form validity, and description generation. Cache locale formatters and compute only the description branches needed; if description formatting remains nontrivial, coalesce it to one deferred update while keeping validation immediate.

### 2. [low] Resolve the local time zone once per catalog projection

**Finding ID:** `PERF-D20A6FCDF308`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts:1210</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Intl.DateTimeFormat instances and associated ICU initialization CPU/objects  
**Scaling:** One uncached formatter is constructed for each single-trigger canonical schedule on every catalog projection, so cost grows linearly with the number of visible Agent Host automations and repeats on catalog updates.  
**Outcome:** higher synchronous catalog refresh latency and avoidable allocation/GC pressure  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Before the diff, hourly, daily, and weekly schedules returned before resolving the local time zone; only the weekdays branch constructed Intl.DateTimeFormat for this comparison.  
**Changed behavior:** The local-time-zone comparison is now placed before preset parsing, so every otherwise representable hourly, daily, weekly, and weekdays schedule constructs its own formatter during projection.  
**Confidence:** 0.96 — The catalog derived observable maps every entry through \_projectAutomation/projectSchedule on each catalog change, and the added condition constructs Intl.DateTimeFormat before distinguishing hourly, daily, weekly, or weekdays. The exact automation counts and formatter duration vary, but the O(N) repeated construction and synchronous refresh path are directly established.

**Causal diff evidence:** Added line 1210 calls Intl.DateTimeFormat().resolvedOptions().timeZone in the common pre-parse guard. \_projectAutomations maps every catalog entry through projectSchedule, whereas the deleted implementation performed this check only inside the weekdays branch.

Opening or refreshing the Automations view for a host with many schedules does avoidable serial ICU initialization on the UI thread, delaying card updates and adding short-lived allocation pressure whenever the catalog changes.

**Evidence:** AgentHostAutomationStore.automations is a derived value invalidated by \_catalog.onDidChange; \_projectAutomations maps catalog.entries and \_projectAutomation calls projectSchedule for each. No formatter or local-zone cache exists in this path. Intl.DateTimeFormat construction is synchronous and substantially heavier than comparing the resulting time-zone string.

**Suggested direction:** Resolve the local time zone once at the start of \_projectAutomations and pass it into projectSchedule (with a one-off default for direct getAutomation calls), so system time-zone changes remain observable while each catalog refresh performs one formatter construction rather than one per entry.
