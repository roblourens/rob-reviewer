### Scenario 1: Persist open chat editor tabs during workbench state save or window shutdown

- Critical path: Each editor group synchronously serializes its existing editor inputs before the workbench state can be stored. The changed serializer now resolves one known title and includes it in the same JSON payload.
- Scaling input: Number of open serializable chat tabs; one title lookup and one additional short string per chat tab. For unresolved local tabs, the first lookup can initialize the session metadata index, which is capped at 400 entries, and subsequent lookups reuse the in-memory index cache.
- Effective concurrency: Serialization is synchronous and sequential across editors. There is no newly introduced asynchronous fan-out or concurrency burst.
- Cache behavior: Resolved models and active sessions are checked first. Unresolved local sessions use a synchronously cached metadata index; a cold cache parses the bounded index once, while warm lookups are map reads. Non-local sessions do not consult that index. restoredTitle is replaced rather than accumulated on each serialization.
- Mechanism confidence: High confidence in the synchronous call path and one-field payload increase; high confidence that no per-tab I/O, IPC, network, filesystem, or subprocess fan-out is introduced.
- Magnitude uncertainty: Exact open-tab counts and custom-title lengths vary, but normal titles are small and the local metadata parse is bounded and cached.

### Scenario 2: Restore a window with unresolved background chat tabs and render their tab labels

- Critical path: The existing editor-state JSON is parsed, ChatEditorInput instances are created, and getName serves the tab label. restoredTitle is a direct option read after live model/session lookups fail; background contributed sessions are not loaded to obtain it.
- Scaling input: Number of restored chat tabs and total title bytes present in editor state.
- Effective concurrency: Input deserialization and label reads follow the existing editor restore flow; the change does not start parallel session loads or remote requests.
- Cache behavior: The serialized title is the warm cache for background tabs. Live model or active-session titles supersede it. Missing titles retain the existing generic fallback without negative-cache retries beyond existing label reads.
- Mechanism confidence: High confidence from the synchronous implementation and test covering repeated serialize/deserialize without resolving the session.
- Magnitude uncertainty: A user can retain varying numbers of tabs, but each restored title contributes only its string size and no heavy resource is created.
- Expensive boundaries:
  - serialization at <code>src/vs/workbench/contrib/chat/browser/widgetHosts/editor/chatEditorInput.ts:561</code>: Parse the existing editor-state JSON containing restoredTitle; cardinality: One parse per serialized chat editor entry in the existing restore flow
    - Introduced by diff: false; previous behavior: The same entry was parsed without the extra title property.; critical-path effect: Adds only the title string's bytes to the existing parse and object revival
  - network at <code>src/vs/workbench/contrib/chat/browser/widgetHosts/editor/chatEditorInput.ts:getKnownTitle</code>: Load a contributed or agent-host chat session; cardinality: Zero for the restored-title label path
    - Introduced by diff: false; previous behavior: Background sessions also remained unloaded and displayed the fallback title until revealed.; critical-path effect: Off the critical path; getKnownTitle only checks synchronous registries/options and does not load the session
- Verdict: No reportable regression. The feature avoids eager session loading and adds only bounded per-tab state and constant-time label selection.

### Scenario 3: Split or duplicate a chat editor

- Critical path: copy creates a new ChatEditorInput with only the existing session-type selection metadata; it does not carry restoredTitle and therefore performs no added persistence or session work.
- Scaling input: One new input per user split/duplicate action.
- Effective concurrency: Synchronous input construction; no queue, limiter, or parallel boundary work is involved.
- Cache behavior: The cached restored title is intentionally not copied, so no cache growth or invalidation path is added for duplicated editors.
- Mechanism confidence: High confidence from the unchanged copy implementation and the added test assertion.
- Magnitude uncertainty: None material for performance; the action creates the same class of input as before.
- Expensive boundaries: none found
- Verdict: No reportable regression; no new expensive boundary or retained title is introduced on this path.
