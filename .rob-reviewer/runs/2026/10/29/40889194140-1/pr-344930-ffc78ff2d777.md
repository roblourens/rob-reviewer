# Performance review: agentHost: record a nested session's own conversation so it can move back out

[PR #344930](https://github.com/microsoft/vscode/pull/344930) at `ffc78ff2d777e2efdd75fafd423c6d687262cb94`

## Findings (1)

### 1. [medium] Reuse the backing check instead of rescanning the full catalog

**Finding ID:** `PERF-0EB18142224A`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:7842</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** SQLite SELECTs, decoding CPU, and allocated chat-row objects  
**Scaling:** O(number of source catalog rows) per probe: two full scans per UI move and four per checked-and-applied self tool move, with up to 1,000 default/private-descendant rows per movable session  
**Outcome:** increased critical-path move latency and shared database queue contention  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, \`\_movedSessionChat\` restored with \`dataOnly: true\` and \`\_checkChatMoveRequest\` did not perform a backing probe. Loaded/backed session moves therefore did not add these source-wide validation snapshots; cold restore and the move's existing catalog preparation performed only their pre-existing reads.  
**Changed behavior:** Every session move now reads and reconstructs the source's complete catalog once before restore and again during request validation just to determine whether the default chat has provider data. For the server tool's self-move flow, pre-check and scheduled apply each run both probes.  
**Confidence:** 0.98 — The two changed call sites, their shared helper, and the database implementation establish exact multiplicity and synchronous critical-path reachability. The catalog contract and \`\_checkMovedSession\` establish that movable sessions may contain up to 1,000 private descendants. Exact wall-clock cost varies with catalog size and database contention, but the repeated full-row reads and decoding are certain.

**Causal diff evidence:** RIGHT line 7842 replaces the prior unconditional data-only restore with an awaited \`\_recordsDefaultChatBacking(session)\` probe, and RIGHT lines 8079-8081 add the same probe again in \`\_checkChatMoveRequest\`. \`\_recordsDefaultChatBacking\` reaches \`\_readDefaultChatBacking\`, whose \`readCatalogSnapshot(\[session\])\` executes two SQL SELECTs and materializes every chat row before a separate \`getChatV2ProviderDetail\` SELECT.

Moving a long-running single-chat session with many subagent descendants waits for two unnecessary full catalog scans and allocations; a self \`move\_session\` tool invocation waits for four across check/apply. This increases move latency and holds the shared SQLite transaction queue longer, delaying unrelated agent-host database work.

**Evidence:** \`moveSession\` calls \`\_movedSessionChat\`, which now awaits the first probe, then \`\_moveChat\` calls \`\_checkChatMoveRequest\`, which awaits the second. \`\_readDefaultChatBacking\` calls \`readCatalogSnapshot(\[session\])\`; \`AgentHostDatabase.readCatalogSnapshot\` performs two queued SELECTs, fetches all live \`chats\_v2\` rows, and converts/groups each row. The catalog contract caps but permits 1,000 chats including private descendants, and \`\_checkMovedSession\` explicitly allows the default chat plus all descendants. Each probe then queues another provider-detail SELECT. The \`move\_session\` self flow calls \`\_checkServerToolMove\` before scheduling and \`\_applyServerToolMove\` when applying, repeating both probes twice.

**Suggested direction:** Carry the first probe result/default-chat identity through the same sequenced move and reuse it in \`\_checkChatMoveRequest\`; for an already-loaded source, query provider detail directly for the known default chat instead of rebuilding the catalog. Re-read only after an initially missing backing triggers a full restore, because that restore may recover and persist the backing.

### Scenario 4: Agent invokes \`move\_session\` for its current session, which is pre-checked and scheduled for application after the turn

- Critical path: Tool execution awaits \`\_checkServerToolMove\`; later scheduled application awaits \`\_applyServerToolMove\`. Each phase calls \`\_movedSessionChat\` and \`\_checkChatMoveRequest\`, so the new pair of backing probes runs in both phases.
- Scaling input: Four source catalog reconstructions per checked-and-applied self move, each scaling with private descendants. The process-wide tool guard allows up to 50 successful moved sessions.
- Effective concurrency: Pre-check and apply are ordered rather than concurrent; actual moves use the global move sequencer. Aggregate database work is serialized through the shared transaction queue.
- Cache behavior: No positive backing result survives from pre-check to scheduled apply, and no result is reused even within either phase. Persisted positive provider data therefore still incurs all four probes.
- Mechanism confidence: High: tool code explicitly checks before scheduling, and both check/apply call the same changed move helpers.
- Magnitude uncertainty: Frequency of self-moves and typical descendant counts are unknown, but exact four-probe multiplicity is established.
