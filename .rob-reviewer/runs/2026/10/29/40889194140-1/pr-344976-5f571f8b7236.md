**Relevant issue families:** repeated-work, synchronous-ui-work, serialization-allocation, boundary-fanout, concurrency-burst

### Scenario 1: Open or refresh extension-provided artifact details containing per-item actions

- Critical path: The extension-host details model is converted, validated, sent over the existing details IPC, then synchronously derived and rendered in the Agents window. All of this is on the panel-open/details-refresh critical path.
- Scaling input: Up to 200 effective detail items per validated snapshot, multiplied by the actions referenced by each item; pending registered-action matching inspects at most the 50 runs retained in the artifact snapshot.
- Effective concurrency: One acquisition per distinct leased details ID; subsequent model changes publish one update per extension event. Conversion and UI derivation are synchronous. No new asynchronous fan-out is introduced.
- Cache behavior: ArtifactDetailsModel leases each distinct integration/details ID while the panel model needs it. Warm updates reuse the lease and listener; there is no new cache key or miss path. Registered-run matching uses the bounded in-memory snapshot.
- Mechanism confidence: High confidence in the synchronous conversion/derivation and bounds from validation and snapshot construction; low evidence of user-visible regression at those bounds.
- Magnitude uncertainty: Extensions control action counts, but the motivating and tested use cases use two row actions; list items and visible run history are explicitly capped at 200 and 50 respectively.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/common/extHostChatArtifactIntegrations.ts:179,206,513</code>: Acquire initial details and publish changed details from the extension host to the main thread, now including item action descriptors and per-item action IDs.; cardinality: One acquisition per distinct details ID and one existing update message per onDidChange event; item metadata scales within the same message with at most 200 items.
    - Introduced by diff: false; previous behavior: The same acquire/update IPC calls already transferred all facts, links, and items. The diff enlarges their payload with item-action metadata but does not add calls.; critical-path effect: Initial acquisition blocks details display; later update serialization precedes repaint.
- Verdict: No finding. The diff adds bounded metadata copying and run matching to an existing render path, but available cardinality and realistic action counts do not establish a concrete performance regression.

### Scenario 2: Run a direct extension item action from a details row

- Critical path: A row click marks that item/action pending, updates the UI, sends one main-thread-to-extension-host RPC, revalidates current details, and awaits the extension's runItemAction callback before clearing pending state.
- Scaling input: One IPC and one extension callback per user click. The extension-host revalidation scans descriptors and at most 200 current items; the same item/action is coalesced while pending.
- Effective concurrency: The same item/action is disabled while pending. Different rows can be invoked concurrently, but concurrency is manually user-driven and no loop or automatic fan-out was added.
- Cache behavior: The existing acquired details model and handle are reused; no cache miss, negative cache, or repeated acquisition occurs on click.
- Mechanism confidence: High confidence in one-RPC-per-click behavior and same-row coalescing.
- Magnitude uncertainty: The extension's callback may itself perform expensive work, but that implementation is outside this diff and invocation remains explicitly user-triggered.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadChatArtifactIntegrations.ts:392 and src/vs/workbench/api/common/extHostChatArtifactIntegrations.ts:234</code>: Invoke $runItemAction in the extension host and await the extension callback.; cardinality: Exactly one RPC per accepted direct row click; repeat clicks on the same pending row are suppressed.
    - Introduced by diff: true; previous behavior: Extension integrations could not expose direct row actions, so this user-requested boundary did not exist for them.; critical-path effect: The RPC and extension callback are on the action-completion critical path, not on panel open or passive rendering.
- Verdict: No finding. This is the requested operation rather than accidental fan-out, and it is coalesced per item/action.

### Scenario 3: Run a registered code or prompt action for one item

- Critical path: A row click invokes the existing artifact action pipeline with a small {detailsId,itemId} input, records the run, queues execution, then crosses the existing extension-host action RPC or chat submission boundary. Completion updates the run and row state.
- Scaling input: One run and one existing action execution per accepted row click; the new input contains two strings. Other rows remain clickable, but queued executions for the same artifact resource/integration share SequencerByKey lanes.
- Effective concurrency: Same-item duplicates are suppressed by pending state and unsettled-run matching. Across items, requests may queue, but ArtifactExecutionService serializes execution by resource and integration key and blocks conflicting dispatched work.
- Cache behavior: No action-result cache is used. Request IDs remain idempotent; input equality is checked on reuse. The bounded 50-run snapshot supports row pending state, while the durable ledger retains normal run history as before.
- Mechanism confidence: High confidence from the changed call path and SequencerByKey execution code.
- Magnitude uncertainty: Users can queue actions on multiple rows and action implementations vary in duration, but expensive execution is serialized and no collection-driven scheduler creates requests automatically.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/artifactIntegrations/common/artifactExecutionService.ts:125</code>: Persist the manual ArtifactRun, now with a cloned two-string item input, through the existing ledger transaction.; cardinality: One existing run transaction per accepted invocation; the diff adds only the small input field and validation/clone work.
    - Introduced by diff: false; previous behavior: Every manual registered action already created and persisted one run; item context was absent.; critical-path effect: Run creation must complete before execution is queued, as before.
  - IPC at <code>src/vs/workbench/api/common/extHostChatArtifactIntegrations.ts:275,291,318</code>: Prepare/run a code action or provide a prompt through the existing extension-host action bridge.; cardinality: One action execution path per queued run, serialized per resource/integration by ArtifactExecutionService.
    - Introduced by diff: false; previous behavior: Top-level registered actions already used the same bridge; the diff exposes that existing path from a row with item input.; critical-path effect: Preparation and execution are on the requested action's critical path but not on passive rendering.
  - network at <code>src/vs/platform/artifactIntegrations/common/artifactExecutionService.ts:337</code>: For prompt actions, submit the prepared prompt to the artifact chat runtime.; cardinality: At most one submission per dispatched prompt run; resource/integration sequencing and chat-busy checks prevent a burst.
    - Introduced by diff: false; previous behavior: Top-level prompt actions already performed the same submission; the row action only supplies item context.; critical-path effect: Submission is required for prompt action progress.
- Verdict: No finding. The diff adds a bounded input to one user-requested invocation and preserves serialized expensive execution.

### Scenario 4: Forward optional manual-action input across the artifact integration/agent-host protocol

- Critical path: When an invocation already crosses the artifact protocol, input is validated as JSON and included in the same request before server dispatch. This is on invocation setup, not startup or rendering.
- Scaling input: One validation and serialization of the optional input per invocation. Item-action inputs are fixed-shape two-string objects.
- Effective concurrency: Protocol request concurrency is unchanged; downstream execution retains resource/integration sequencing.
- Cache behavior: No cache behavior changes. Existing request-ID idempotency now compares input as part of the key semantics.
- Mechanism confidence: High confidence in unchanged boundary cardinality and fixed-shape item input.
- Magnitude uncertainty: The internal type permits larger JSON values, but the newly exposed extension row-action path constructs only two strings and no changed public caller supplies unbounded input.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/artifactIntegrations/common/artifactIntegrationProtocol.ts:372 and src/vs/sessions/contrib/providers/agentHost/browser/agentHostArtifactIntegrations.ts:79</code>: Send the existing invoke request with an optional JSON input through the artifact integration transport/agent-host bridge.; cardinality: Still one protocol request per invocation; no additional round trip.
    - Introduced by diff: false; previous behavior: The invoke request already crossed this boundary with integration, action, chat, request ID, and actor; the payload did not contain input.; critical-path effect: The existing invoke request remains on action startup's critical path.
- Verdict: No finding. Payload size increases slightly without extra calls, fan-out, or realistic unbounded serialization on the changed caller path.

The potentially repeated UI work is bounded by 200 items and 50 snapshot runs; registered expensive work is serialized by resource/integration; direct actions add one coalesced RPC per user click. No high-confidence actionable performance regression was found.
