<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, boundary-fanout, cache-lifecycle

### Scenario 1: Signed-out Agents model picker receives BYOK bridge, root-configuration, or local-model-row updates

- Critical path: The event synchronously reads the BYOK registry cache or local provider rows, rebuilds the in-memory model array, publishes it, and refreshes live session configuration. The new token check is on this local publication path and skips construction of at most the two fixed HydraFusion rows; it does not block on external work.
- Scaling input: O(B + C + L + S) existing publication work for B BYOK models, C cached CAPI models, L local rows, and S live sessions. The changed work is O(1): one credential-field read and a condition in a fixed two-entry HydraFusion loop.
- Effective concurrency: Publication is synchronous per event. Existing follow-up model synchronization is launched once per live session without a shared limiter; this fan-out and its cardinality are unchanged by the diff.
- Cache behavior: BYOK enumeration uses the bridge registry's cached serving-window snapshot. Signed-out model refresh already clears the CAPI cache and returns without starting the runtime or fetching models. The diff does not change cache keys, invalidation, retries, or negative-cache behavior.
- Mechanism confidence: High: the changed line is inside a fixed-size local loop, and all publication callers and follow-up session synchronization paths were traced.
- Magnitude uncertainty: The number of simultaneously live sessions and frequency of renderer model events vary, but those scaling mechanisms are pre-existing and unaffected. The changed constant work is bounded regardless of those values.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_refreshByokModels and \_watchLocalModelRows</code>: Synchronize available BYOK/local model rows into each live Copilot SDK session after bridge or local-row changes; cardinality: At most one call per live session for a model-change event; model enumeration itself is one cached registry read for the serving window.
    - Introduced by diff: false; previous behavior: The same per-session synchronization occurred after publication before the PR; the added signed-in predicate neither adds calls nor changes session count.; critical-path effect: Publication to the picker completes before these fire-and-forget session synchronization calls; they are off the picker publication critical path.
- Verdict: No reportable regression. While signed out, the PR reduces allocation and downstream catalog size by omitting up to two unavailable synthetic rows and introduces no boundary call or repeated work.

### Scenario 2: GitHub sign-in or sign-out refreshes the Copilot model catalog

- Critical path: Authentication is serialized, updates existing live sessions as needed, resolves account metadata, and schedules one coalesced catalog refresh. A signed-in refresh performs model-list and managed-settings runtime RPCs before calling \_publishModels; a signed-out refresh clears cached CAPI state and publishes locally without those RPCs. The new check runs only at the final publication step.
- Scaling input: Existing credential-update cost scales with S live static-token sessions; catalog transformation scales with C returned models. The diff adds constant work and can remove two rows from the signed-out output.
- Effective concurrency: The authentication sequencer serializes credential transitions. Static-token live-session credential updates run sequentially. Model refresh scheduling coalesces repeated lifecycle triggers into one deferred refresh, and refreshModels joins an in-flight refresh; model-list and managed-settings RPCs execute sequentially.
- Cache behavior: Catalog refreshes are generation-guarded and coalesced; failures retain the last known CAPI list and retries use existing backoff. Sign-out clears CAPI models and avoids runtime enumeration. The added token read uses current in-memory credentials and changes no cache lifecycle.
- Mechanism confidence: High: authentication, restart, scheduler, model-list, managed-settings, and publication call paths were traced directly.
- Magnitude uncertainty: Remote and runtime latency vary, but no changed line adds, advances, duplicates, or parallelizes those calls.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_applyGitHubToken -&gt; copilotAgentSession.ts:updateGitHubCredentials</code>: Update GitHub credentials in each live static-token Copilot SDK session; cardinality: Up to one RPC per live static-token session per changed credential, executed sequentially; provider-backed sessions are skipped.
    - Introduced by diff: false; previous behavior: Identical sequential per-session credential updates occurred before the PR.; critical-path effect: These calls must finish before authentication proceeds to account resolution and model refresh.
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_resolveCopilotSku and \_updateLocalModelAccount</code>: Resolve Copilot SKU and, when a local-model provider exists, GitHub login/account metadata; cardinality: One SKU resolution per supplied changed token and at most one login resolution when a local provider is active.
    - Introduced by diff: false; previous behavior: These account requests were already on the token-update path and are not influenced by model publication.; critical-path effect: Authentication awaits these operations before scheduling the catalog refresh.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_requestClientRestart and \_applyPendingClientRestart</code>: Stop/restart the Copilot client when credential mode, enterprise authentication, or a failed live credential update requires it; cardinality: At most one coalesced restart for accumulated reasons once chats are idle; ordinary compatible token updates need no restart.
    - Introduced by diff: false; previous behavior: Restart gating, coalescing, and chat-idle deferral are unchanged.; critical-path effect: A required restart precedes replacement catalog enumeration; busy-chat deferral keeps it off active-turn critical paths.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_listModels</code>: List models from the Copilot runtime; cardinality: One runtime RPC per effective signed-in catalog refresh after scheduler/in-flight coalescing; zero while signed out.
    - Introduced by diff: false; previous behavior: The same single coalesced models.list RPC ran before publication; the new predicate is evaluated afterward.; critical-path effect: The signed-in picker catalog waits for this result.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_refreshModels -&gt; copilotManagedSettings.ts:resolveCopilotManagedSettings</code>: Resolve managed model settings through the Copilot runtime; cardinality: One runtime RPC per successful signed-in model-list refresh, with a timeout; zero while signed out.
    - Introduced by diff: false; previous behavior: The same policy RPC and ordering existed before the PR.; critical-path effect: Publication waits for policy resolution after model listing.
- Verdict: No reportable regression. The PR changes only final in-memory filtering and does not alter the expensive authentication or catalog-refresh boundaries.

### Scenario 3: Signed-in catalog publication after periodic refresh or cached model-source updates

- Critical path: A periodic refresh joins or starts the existing coalesced runtime catalog request, then transforms cached models and publishes them to the observable and live sessions. Cached BYOK/local updates can also republish without catalog network work.
- Scaling input: Publication remains O(C + B + L + S) in catalog entries and live sessions. HydraFusion candidate count is fixed at two, and signed-in behavior performs the same model creation as before plus a single precomputed boolean check.
- Effective concurrency: Only one scheduled or in-flight CAPI refresh is effective at a time. Publication remains synchronous; existing per-live-session refreshModelConfiguration fan-out is unchanged.
- Cache behavior: Warm BYOK/local publications use cached source data. CAPI refresh calls are coalesced, stale generations are discarded, and last-known successful models survive failures. The predicate does not affect any of these states.
- Mechanism confidence: High: every \_publishModels caller and its boundary placement was inspected.
- Magnitude uncertainty: Catalog and session sizes vary, but the diff does not change their effective cardinality or any operation tied to them.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:refreshModels, \_refreshModels, and \_listModels</code>: Runtime model listing and managed-settings resolution for periodic signed-in CAPI refresh; cardinality: One models.list RPC plus one managed-settings RPC per effective refresh after coalescing.
    - Introduced by diff: false; previous behavior: The same calls and sequential ordering existed before the diff.; critical-path effect: Both complete before the updated signed-in catalog is published.
- Verdict: No reportable regression. The new signed-in condition is constant-time and neither increases publication frequency nor changes fan-out.

**Summary:** Completed the performance review of both changed files and all production publication/authentication callers. The only production change is an in-memory credential boolean used in a fixed two-model loop; it suppresses unavailable rows while signed out and introduces no additional I/O, IPC, subprocess work, unbounded retention, concurrency burst, cache change, or scaling cost.
