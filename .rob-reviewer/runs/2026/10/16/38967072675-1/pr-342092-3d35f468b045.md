# Performance review: agentHost: keep plugin subagents in Copilot catalog

[PR #342092](https://github.com/microsoft/vscode/pull/342092) at `3d35f468b045167ec0158db5e01aa43a801af1f7`

## Findings (1)

### 1. [low] Avoid serially rereading every installed plugin agent at session launch

**Finding ID:** `PERF-7DFB311BE3B5`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotPluginConverters.ts:182</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem read operations plus frontmatter parsing and prompt-string allocation  
**Scaling:** Configuration latency now grows serially with the total number of agents across all enabled file-backed plugins; N agents cause N awaited reads with effective concurrency 1 on every non-ephemeral create or resume.  
**Outcome:** increased first-message and session-resume latency, especially when the plugin directory is on a slow or remote filesystem  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** File-backed plugin agents were excluded from this host-side conversion and loaded through \`pluginDirectories\`; only a selected file-backed agent could be added to the serial loop. Thus the host-side pre-session critical path had zero or one reads for those plugins rather than one read per enabled agent.  
**Changed behavior:** The changed \`flatMap\` feeds agents from every plugin, including file-backed plugins, into \`toSdkCustomAgents\`; that helper awaits \`fileService.readFile\` inside a \`for\` loop, so all newly included plugin files are read sequentially on \`\_buildSessionConfig\`'s critical path.  
**Confidence:** 0.93 — The changed cardinality, sequential \`await\`, and create/resume critical path are directly traced. Exact delay varies with plugin count and filesystem latency, and discovery may leave the OS cache warm, which is why severity is low rather than suppressing the finding.

**Causal diff evidence:** RIGHT line 182 changed the input from only plugins without file directories (plus at most the selected agent) to \`plugins.flatMap(plugin =&gt; plugin.agents)\`, increasing this serial filesystem boundary from O(non-file agents + selected agent) to O(all enabled plugin agents).

Creating a normal chat or resuming one now waits for every enabled plugin agent file to be read one after another before \`createSession\`/\`resumeSession\` can begin. A plugin catalog with tens of agents on a high-latency filesystem can add the sum of all read latencies to the first prompt or resume.

**Evidence:** \`toSdkCustomAgents\` at lines 115-161 performs \`await fileService.readFile(agent.uri)\` inside a sequential loop. \`\_buildSessionConfig\` at \`copilotSessionLauncher.ts:1185-1188\` awaits this promise before constructing the SDK session, and \`launch\` at lines 900-906 invokes that path for both create and resume. The snapshot is produced after customization discovery, whose \`readAgentComponents\` already reads agent frontmatter concurrently with \`Promise.all\`, so there is no retained content cache that makes these launch-time reads free; only the OS cache may be warm.

**Suggested direction:** Keep projecting all agents, but read/convert them with bounded concurrency while preserving input order (or retain the already-read agent body in the parsed snapshot with proper invalidation) so session startup does not sum one filesystem round trip per agent.
