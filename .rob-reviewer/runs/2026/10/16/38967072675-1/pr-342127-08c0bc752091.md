### 1. repeated-work

**Fix location:** `src/vs/platform/agentHost/node/agentHostCatalogReconciliationService.ts:704` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentHostCatalogReconciliationService.ts:671`  
**Introducing path:** `src/vs/platform/agentHost/node/agentHostCatalogReconciliationService.ts`

**Mechanism family:** `repeated-work`  
**Performance category:** `io`  
**Confidence:** 0.99

**Mechanism:** Dirty provider-unavailable sessions remained eligible forever, repeating per-session database opens and source resolution every periodic pass.

**Symptom:** Production logs showed dozens of older sessions repeatedly reopened; the representative test models 6,000 database opens per hour for 110 sessions.

**Fixed behavior:** Unavailable-provider rows are attempted once and excluded from normal periodic passes until a provider-readable wake or hourly verification releases them.

**Evidence:** Base line 671 returned providerUnavailable while leaving the row dirty, so `_listDirtySessions` selected it again on each 30-second pass and reconciliation reopened its session database. RIGHT line 704 now parks that row. The added 110-session test demonstrates the call path and multiplicity: 6,000 opens/hour before versus 110 initial opens plus bounded event/hourly retries after, with batches of 50 and concurrency 4.

### Scenario 1: Periodic catalog reconciliation while a registered provider cannot read its catalog, or while a provider is unregistered

- Critical path: This is background maintenance after startup/listing; it is not on an interactive critical path. Each pass must list receipts/sessions, then reconcile at most one batch. Before the PR, dirty unavailable-provider rows stayed eligible indefinitely; after the PR, their first attempt and parking must complete, while warm passes skip them.
- Scaling input: Number of dirty sessions owned by unavailable providers. The test and production context establish realistic cardinalities of roughly 70-110; batching reduces instantaneous work to 50 and concurrency to 4.
- Effective concurrency: A regular pass selects at most 50 sessions and uses a shared Limiter with concurrency 4. Per-session catalog sync is additionally serialized by storage key. Passes are coalesced and observe a minimum interval; there is no unbounded Promise.all boundary burst.
- Cache behavior: \`\_parkedSessions\` is an in-memory negative cache keyed by session and carrying provider. Cold restart retries each row once. Warm ordinary passes filter parked rows. Session mutation, provider registration/readability, and hourly verification invalidate it; empty/failure states are not persisted indefinitely.

### Scenario 2: Provider catalog transitions from unreadable to readable and wakes its parked sessions

- Critical path: Provider enumeration/import must finish before readability is recorded. The new provider-specific map scan and parked-session events execute synchronously at that transition; the actual re-projection is only scheduled and is off the import call's critical path.
- Scaling input: Total parked entries controls the synchronous scan; matching entries control later I/O. Realistic evidence is 55-70 matching sessions among 110 total parked sessions.
- Effective concurrency: The wake scan is single-threaded O(total parked sessions). Subsequent reconciliation remains at 50 sessions per pass and concurrency 4, with per-session key serialization. \`readableTransition\` makes the provider wake one-shot until readability is explicitly lost.
- Cache behavior: Readability is positively cached in \`\_readableProviderCatalogs\`; only a false-to-true transition invokes the new provider wake. The parked cache is invalidated only for matching provider entries, and a no-match wake returns false and avoids scheduling.
- Mechanism confidence: High: transition guard, provider-specific invalidation, return-value scheduling gate, and batch limiter are explicit in the code and tests.
- Magnitude uncertainty: Providers with much larger historical catalogs could increase the linear scan/event count, but no evidence indicates a user-visible latency issue at established cardinalities.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/platform/agentHost/node/agentService.ts:2333 \_enumerateLegacyProviderSessions</code>: Call \`provider.listChatsToMigrate()\` to establish that the provider catalog is readable.; cardinality: One provider enumeration per migration attempt, independent of parked-session count.
    - Introduced by diff: false; previous behavior: The same migration/enumeration occurred, but successful readability did not release only that provider's parked reconciliation rows.; critical-path effect: This existing provider operation gates the readability transition; the diff does not add or move it.
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostCatalogSyncService.ts:337 runMigrationExclusive</code>: Open and re-project each woken session database during scheduled reconciliation.; cardinality: One eventual open per woken dirty session, grouped into batches of 50 with concurrency 4; a 70-session provider takes two passes. A provider wake with no matching rows schedules no pass.
    - Introduced by diff: true; previous behavior: Those rows were already being opened on every ordinary periodic pass, including while unreadable; there was no event-triggered convergence point.; critical-path effect: Off the provider import critical path because \`schedule()\` only enqueues background reconciliation.
- Verdict: No reportable regression. The synchronous O(N) map scan is bounded by registered parked sessions and replaces substantially larger repeated I/O; projection remains deferred and limited.

### Scenario 3: Chat movability reacts when sessions are parked or released

- Critical path: Parking/release fires an in-memory event synchronously. For a loaded matching session, chat movability recomputes each chat before the event returns; for the old unloaded sessions that drive this fix, \`\_updateSessionChats\` immediately sees no state and does no work.
- Scaling input: Loaded chats in each affected session. The performance-fix scenario concerns legacy unloaded sessions, making effective chat cardinality zero there.
- Effective concurrency: Synchronous per event. Parking and provider-specific wake emit at most one event per affected session; the existing global hourly wake emits one \`undefined\` event and performs one all-loaded-session recomputation.
- Cache behavior: Movability reads the parked map directly; no stale cache or repeated scheduled work is introduced. Per-provider release deletes entries before firing, so consumers observe authoritative state.
- Mechanism confidence: High for the synchronous call path and no-op behavior on unloaded sessions; low prevalence for large loaded parked sets is not used as a finding.
- Magnitude uncertainty: A provider could theoretically have many loaded sessions/chats, but loaded sessions resolve from live summaries and are not expected to enter the provider-unavailable parked state; no realistic hot-path regression is established.
- Expensive boundaries: none found
- Verdict: No reportable synchronous-UI regression. The event fan-out is necessary, session-scoped, and effectively empty for the realistic affected population.
