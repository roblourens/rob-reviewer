### Scenario 1: Managed read/write/command permission in Assisted mode receives an approving derived verdict and executes once

- Critical path: The assistant emits a tool call, the SDK performs the Assisted permission-judge model request, then invokes Agent Host with promptRequest; the changed handler consumes that verdict before the requested tool can execute. The judge is on the critical path, while capture normalization is test-only and off the product path.
- Scaling input: One judge operation per managed permission request. The changed E2E captures show one added judge exchange for each distinct toolCallId, and one-time managed semantics intentionally repeat this for a later permission rather than reusing a grant.
- Effective concurrency: The exercised workflow is serialized per tool permission and per turn. The two one-time operations in each E2E scenario run sequentially; the diff adds no shared fan-out loop or concurrency burst.
- Cache behavior: There is no reusable approval cache by design: managed approvals remain one-time. Warm repetitions therefore perform a fresh judge request. Existing per-tool correlation maps are cleared on tool completion or session abort; the diff does not add a new long-lived collection.
- Mechanism confidence: High: the changed captures establish the added network exchange and ordering, and the launcher/session code establishes that the resulting verdict is consumed once.
- Magnitude uncertainty: Actual model latency and prevalence of enterprise managed ask rules are not measured, but the added one-per-permission network boundary is directly visible in the captures.
- Expensive boundaries:
  - network at <code>&#64;github/copilot-sdk 1.0.23-preview.1 behavior evidenced by package.json:105 and the added exchanges in src/vs/platform/agentHost/test/node/e2e/captures/copilotcli-managed-read-approval-remains-one-time-under-assisted.yaml</code>: Assisted permission-judge model request containing transcript, runtime-derived request context, and tool metadata; cardinality: Exactly one added judge request for each eligible managed permission in the captured read/write scenarios; repeated one-time permissions each receive their own request.

### Scenario 2: Managed Assisted verdict is missing, unsupported, human-required, denied, or blocked by sandbox-bypass safeguards

- Critical path: Agent Host performs constant-time eligibility checks on the supplied promptRequest and then uses the existing pending-confirmation path. A non-approving judge result can precede the human confirmation, but that judgment is necessary to determine whether the request qualifies for automatic approval.
- Scaling input: One eligibility check and at most one pending confirmation per permission request. Requests are keyed by toolCallId; no collection-wide scan was added.
- Effective concurrency: Pending confirmations remain independently keyed by toolCallId. The reviewed tests exercise them serially, and no changed limiter, queue, or fan-out behavior was found.
- Cache behavior: No verdict or denial is cached across managed requests, preserving one-time policy. Pending state is removed by the existing permission response/abort lifecycle; no changed retention owner was identified.
- Mechanism confidence: High for the unchanged host fallback path; medium for which conservative cases incur an SDK network judge because only supported read/write captures show the boundary.
- Magnitude uncertainty: The repository does not expose the upgraded SDK implementation, so whether it avoids judge calls for every statically ineligible prompt cannot be proven from the supplied diff. Human response time also dominates and is unbounded.
- Expensive boundaries:
  - network at <code>SDK behavior represented by invocation.promptRequest and the managed Assisted E2E captures</code>: Potential Assisted judge request before a non-approving derived verdict; cardinality: At most one per eligible permission request; the diff contains direct capture evidence for managed read/write judges but not a capture proving every unsupported or sandbox-bypass case invokes the judge.
    - Introduced by diff: true; previous behavior: Managed requests previously went directly to the existing human confirmation path.; critical-path effect: When present it precedes the existing human confirmation; exact latency is SDK/model dependent.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_handlePermissionRequest and agentSideEffects.ts</code>: Renderer/AHP human confirmation round trip for requests that cannot consume an approving verdict; cardinality: One confirmation per request in the tested conservative cases.
    - Introduced by diff: false; previous behavior: Managed requests required the same one-time human response.; critical-path effect: Blocks permission completion until the user responds, as before.
- Verdict: No finding. The changed host checks are O(1), preserve the existing confirmation path, and the diff does not provide high-confidence evidence of avoidable repeated boundary work for statically ineligible cases.

### Scenario 3: Record and replay E2E model requests containing permission-judge text and cross-platform paths

- Critical path: The test proxy loads a fixture, normalizes each observed/recorded request, projects it, and compares it before returning the local replay response. Added normalization is synchronous CPU/allocation work on the test request path, not a product runtime path.
- Scaling input: Work grows with request text/history size and, for out-of-order concurrent replay requests, with remaining candidate turns. Normal in-order requests match the first remaining candidate, so effective candidate cardinality is one.
- Effective concurrency: The proxy supports concurrent requests by scanning and swapping a matching remaining response. No new concurrency is created; the changed normalization runs inside the existing local request handler.
- Cache behavior: Fixtures are loaded once per proxy. Normalized candidate projections are not cached, but in-order matching examines one candidate and the pre-existing implementation already projected and serialized candidates on each comparison.
- Mechanism confidence: High that extra CPU/allocation occurs; low that it reaches reportable magnitude because this is bounded test-only work and ordinary in-order cardinality is one.
- Magnitude uncertainty: Very large histories or heavily out-of-order subagent captures could amplify the extra recursive normalization, but no changed test or repository invariant establishes a realistically large effective candidate count or material slowdown.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/test/node/e2e/harness/capiReplayProxy.ts:\_loadFixture/\_writeFixture</code>: Read the YAML fixture on proxy startup and write it in recording mode; cardinality: One fixture read per proxy startup and one write per recording; unchanged by this diff.
    - Introduced by diff: false; previous behavior: The same fixture I/O occurred before the normalization changes.; critical-path effect: Fixture loading precedes replay; recording write occurs when persisting the test capture.
  - network at <code>src/vs/platform/agentHost/test/node/e2e/harness/capiReplayProxy.ts</code>: Local HTTP request through the replay proxy; recording mode may forward to the configured model upstream; cardinality: One proxy request per model exchange; the diff adds no request.
    - Introduced by diff: false; previous behavior: The same proxy/upstream requests occurred before the diff.; critical-path effect: Replay response waits for local comparison; upstream latency in recording mode dominates normalization.
- Verdict: No reportable performance regression. The extra symmetric normalization is bounded to the E2E harness and no concrete CI latency, memory growth, or new boundary fan-out is established.
