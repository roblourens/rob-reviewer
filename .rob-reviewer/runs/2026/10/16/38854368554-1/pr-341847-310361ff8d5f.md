### Scenario 1: Build the Windows user or system installer

- Critical path: The existing Gulp setup task launches one ISCC subprocess; ISCC must enumerate and read the staged policy tree and include its contents before the installer artifact is complete.
- Scaling input: The generated Windows policy tree has one ADMX plus one ADML for en-us and each of the 13 fixed entries in Languages, so the diff adds 14 bounded locale files rather than scaling with user data.
- Effective concurrency: One existing ISCC subprocess packages the setup; the diff adds no Promise fan-out, workers, queue, or explicit concurrency and leaves processing to that single packaging invocation.
- Cache behavior: No cache is used on this path. The policy files are already generated/staged before setup packaging, and every installer build reads them once.
- Mechanism confidence: High: the added recursesubdirs flag directly causes ISCC to traverse and package the generated locale files; generator and staging code establish the bounded cardinality.
- Magnitude uncertainty: Exact generated XML byte size and compression time vary with policy count, but cardinality is fixed by 14 supported locale outputs and is small relative to the application payload.
- Expensive boundaries:
  - subprocess at <code>build/gulpfile.vscode.win32.ts:packageInnoSetup</code>: Run ISCC to compile the installer archive.; cardinality: One subprocess per user/system setup build, unchanged by the diff.
    - Introduced by diff: false; previous behavior: The same ISCC subprocess compiled the installer but the non-recursive policies entry included only the top-level ADMX.; critical-path effect: The subprocess is the packaging critical path; the diff only changes which staged files it consumes.
  - filesystem at <code>build/win32/code.iss:106</code>: Recursively enumerate and read policy subdirectories, then compress their ADML files into the solid installer archive.; cardinality: 14 added ADML files in 14 fixed locale directories for current generated output.
    - Introduced by diff: true; previous behavior: Only policies/\* at the top level was included, so locale subdirectories and ADML files were not read into the installer.; critical-path effect: Adds bounded file reads and compression work before installer production completes.
- Verdict: No finding. The bounded packaging I/O is necessary to deliver the required localized templates and does not establish an actionable performance regression.

### Scenario 2: Download and install or update VS Code with the Windows user/system installer

- Critical path: Installer download transfers the setup archive; installation then extracts and writes packaged files before setup completes. The changed ADML files are on these critical paths but not on VS Code application startup.
- Scaling input: One ADML per 14 supported locale directories, regardless of workspace, user data, extension count, or machine lifetime.
- Effective concurrency: A single installer invocation performs extraction/writes; the diff introduces no aggregate concurrency or independent per-user/per-item scheduling.
- Cache behavior: No application cache is involved. A fresh installer contains the files once; each install/update writes the current version's bounded policy set.
- Mechanism confidence: High: Inno Setup recursive source inclusion necessarily packages and extracts these files, and the generator proves the fixed locale count.
- Magnitude uncertainty: Exact transfer and disk latency depend on policy XML size and machine/network speed, but only a fixed small file set is added.
- Expensive boundaries:
  - network at <code>build/win32/code.iss:106 (packaged payload consumed by distribution)</code>: Transfer the installer archive containing the newly included compressed ADML resources.; cardinality: One installer download with 14 additional compressible XML files; no extra network requests.
    - Introduced by diff: true; previous behavior: The downloaded installer omitted all localized ADML payloads and therefore transferred fewer compressed bytes.; critical-path effect: Slightly increases installer bytes on the download critical path.
  - filesystem at <code>build/win32/code.iss:106</code>: Extract and write localized ADML files under the versioned policies directory.; cardinality: 14 additional file writes and locale directories per install/update.
    - Introduced by diff: true; previous behavior: Setup wrote only the top-level ADMX from the policy tree.; critical-path effect: Adds bounded disk I/O before setup completion; it does not affect editor startup or rendering.
- Verdict: No finding. The extra bounded bytes and writes are the intended product payload needed for usable Group Policy templates, with no unbounded scaling or avoidable repeated boundary work shown.

### Scenario 3: Uninstall a Windows user/system installation containing localized policy templates

- Critical path: The existing uninstaller removes files tracked from the installer payload before uninstall completes.
- Scaling input: The same fixed set of 14 localized ADML files and directories installed by this change.
- Effective concurrency: One uninstaller invocation; no new fan-out, parallel cleanup, or retained background resource.
- Cache behavior: No cache exists. Cleanup occurs once for the installed version and leaves no long-lived in-memory state.
- Mechanism confidence: High for the added installed-file cleanup implied by Inno Setup payload tracking; no evidence of orphaning or repeated cleanup exists.
- Magnitude uncertainty: Filesystem deletion latency varies, but the operation count is fixed and low.
- Expensive boundaries:
  - filesystem at <code>build/win32/code.iss:106</code>: Delete the newly installed ADML files and their locale directories through Inno Setup's tracked-file cleanup.; cardinality: Up to 14 additional file deletions and their fixed directories per uninstall.
    - Introduced by diff: true; previous behavior: There were no installed ADML locale files to delete.; critical-path effect: Adds small bounded filesystem cleanup on uninstall only.
- Verdict: No finding. Cleanup cost is bounded, occurs once on uninstall, and prevents retention of the newly installed payload.
