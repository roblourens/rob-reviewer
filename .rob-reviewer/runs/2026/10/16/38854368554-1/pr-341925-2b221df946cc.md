### Scenario 1: Extension-host startup and environment-collection synchronization

- Critical path: MainThreadTerminalService builds the target-authority snapshot and serializes it before the extension host receives its initial cached collection. Later extension mutations cross the extension-host RPC immediately, while terminal notifications are debounced for one second and persistence is throttled.
- Scaling input: Number of installed extensions with terminal environment collections and total mutators/descriptions; effective authority cardinality is normally local plus the window's remote authority.
- Effective concurrency: Initial bridge construction is synchronous per extension host. Collection mutations may arrive in bursts, but terminal notifications are debounced and each authority rebuild is coalesced through the shared map.
- Cache behavior: Cold authority views perform O(extensions + mutators) filtering/merge work; warm consumers are O(1) cache lookups. Any real collection update invalidates the views, while the one-second notification debounce prevents rebuild fanout for mutation bursts.
- Mechanism confidence: High: changed lines, cache invalidation, debounce, and RPC call sites were traced directly.
- Magnitude uncertainty: Exact extension and mutator counts vary, but repository code explicitly expects collections to be small; no new per-item boundary or unbounded authority source was found.
- Expensive boundaries:

### Scenario 3: Persistent terminal attachment, failed attachment fallback, and normal relaunch

- Effective concurrency: Attachment is serialized before fallback creation for each terminal. The diff does not launch attachment and creation concurrently and therefore introduces no resource burst.
- Cache behavior: Successful attachment does not need a new target view unless status comparison requires it; fallback/relaunch shares the service cache.
- Mechanism confidence: High: the before/after ordering is explicit in the changed hunk.
