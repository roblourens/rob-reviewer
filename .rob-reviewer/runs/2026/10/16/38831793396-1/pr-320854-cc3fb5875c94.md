## Findings (2)

### 1. [medium] Move stale plugin deletion off the first-sync critical path

**Finding ID:** `PERF-08C0F81E841E`  
**Location:** <code>src/vs/platform/agentHost/node/agentPluginManager.ts:278</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** recursive filesystem deletion operations and the subsequent cache-file write  
**Scaling:** The delay grows with the number of retained stale nonce entries (normally up to the 20-entry cache cap, but explicitly allowed to exceed it when revisions are locked) and with the file count/size of each plugin directory; all stale revisions are deleted sequentially.  
**Outcome:** increased first-turn latency while stale plugin trees are removed  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The first sync loaded the small cache JSON and proceeded directly to checking/copying the requested customizations; it did not recursively delete old plugin directories before sync could start.  
**Changed behavior:** After loading cache metadata, the first sync now awaits \`\_cleanupStaleNonces()\`, which iterates every tracked plugin and awaits recursive deletion of every stale revision before any requested plugin is checked.  
**Confidence:** 0.97 — The changed await, serial recursive-delete implementation, and first-turn call path are explicit. Exact milliseconds depend on stale revision size and filesystem speed, so severity is medium rather than high.

**Causal diff evidence:** RIGHT line 278 newly places \`await this.\_cleanupStaleNonces()\` inside \`\_ensureCacheLoaded()\`, ahead of the existing per-request sync scheduling; the base path only loaded cache metadata here.

After an older plugin revision was retained because a long-running session locked it, the next agent-host process blocks the first active-client customization sync—and therefore the first Copilot turn/session resume—while it recursively removes all released stale revision trees. Large plugins or several retained revisions make the user wait before the turn reaches the SDK.

**Evidence:** \`syncCustomizations()\` awaits \`\_ensureCacheLoaded()\` before scheduling any plugin sync. The added line 278 awaits \`\_cleanupStaleNonces()\`; that helper serially awaits \`\_tryDeleteDir()\` for each stale entry, and \`\_tryDeleteDir()\` calls \`IFileService.del(..., { recursive: true })\`. On first turn, \`SessionActiveClientChanged\` starts \`pluginController.sync\`; \`sendMessage()\` then waits the same \`\_clientSync\` through \`retryFailedClientSyncIfNeeded()\`/snapshot resolution before resuming or sending the turn.

**Suggested direction:** Load the cache metadata and let the requested sync proceed first; run stale-revision cleanup afterward/off the turn critical path under a single serialized cleanup task, retaining failed entries and persisting the resulting LRU once cleanup settles.

### 2. [medium] Keep restored-session plugin sync off the first turn

**Finding ID:** `PERF-5E2B1764BBF6`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:1159</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** filesystem existence/copy operations and plugin parsing CPU performed by active-client customization synchronization  
**Scaling:** First-turn delay grows with the number and size of active-client plugins: warm revisions still perform one filesystem existence check and parse each plugin, while cold or changed revisions recursively copy and then parse each directory.  
**Outcome:** blocked first-turn critical path and increased time to the first agent response  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Opening a restored session immediately dispatched \`SessionActiveClientChanged\`, so plugin synchronization began while the user was browsing the session and generally completed before the first message was sent.  
**Changed behavior:** The claim and its plugin synchronization are now initiated only immediately before \`SessionTurnStarted\`; host-side \`sendMessage()\` waits the resulting \`\_clientSync\` before snapshot comparison, resume/materialization, and SDK send.  
**Confidence:** 0.96 — The before/after placement and awaited host call chain are explicit, and the updated tests confirm restored sessions no longer claim until first turn. Magnitude varies with plugin count/cache state, so severity is medium.

**Causal diff evidence:** The diff removes the prior claim from restored-session open and adds it at RIGHT line 1159 immediately before turn dispatch, moving the same scaling filesystem/parsing work onto the user-input critical path.

For a restored session whose current active client differs or whose customization snapshot is stale—the exact cases covered by the updated tests—the first submitted prompt now waits for all client plugins to be validated/copied and parsed. A session with several or large plugins shows avoidable first-response latency that was previously hidden during session open.

**Evidence:** RIGHT line 1159 calls \`\_ensureActiveClientForMessage()\` on the input path immediately before dispatching the turn. That action invokes \`setClientCustomizations()\` and \`pluginController.sync()\`. Although the action side effect does not await it, the immediately following turn reaches \`CopilotAgent.sendMessage()\`, whose \`retryFailedClientSyncIfNeeded()\` and active-client snapshot paths await \`\_clientSync\`; \`sync()\` awaits \`AgentPluginManager.syncCustomizations()\` and then parses every resolved plugin.

**Suggested direction:** Preserve the no-dispossession behavior only while another client actually has an active turn; when the restored session is idle, pre-claim/pre-sync on open as before, or otherwise prewarm customization materialization without changing active ownership so the eventual claim can reuse settled plugin results.


## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLocalCustomizations.ts:164` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLocalCustomizations.ts:164`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLocalCustomizations.ts`  
**Introducing commit:** `150d40b6323c916a0e1a558b0dea3e8fe8417a83`  
**Mechanism family:** `repeated-work`  
**Performance category:** `io`  
**Confidence:** 0.95

**Mechanism:** Client plugin references previously omitted a nonce, while `AgentPluginManager` only takes its cache-hit path when `ref.nonce` is present. Every active-client customization sync therefore recursively recopied unchanged plugin directories and reparsed their contents.

**Symptom:** Repeated customization claims/refreshes performed avoidable full plugin-directory I/O, delaying first-turn plugin setup and increasing filesystem work; overwriting an in-use revision could also encounter the EBUSY symptom described by the change.

**Fixed behavior:** The plugin directory mtime is now sent as `nonce`, allowing unchanged revisions to hit the existing cache check and skip the recursive copy while changed revisions materialize separately.

**Evidence:** RIGHT line 164 adds the mtime-derived nonce to every resolved plugin ref. The downstream cache guard is `if (ref.nonce && ... && await fileService.exists(destDir)) return destDir`; without this field the guard was always false and execution reached `fileService.copy(pluginUri, destDir, true)`. Active-client synchronization invokes this path and is awaited when the session snapshot/first turn is prepared.
