## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:9303` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:9252`  
**Introducing path:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`  
**Introducing commit:** `74c45d448154f27b023e82a3b5e1be4043401118`  
**Mechanism family:** `eager-work`  
**Performance category:** `latency`  
**Confidence:** 0.97

**Mechanism:** The host treated transport connection as full readiness even while MCP tool enumeration remained on the turn's blocking startup path. Because backgrounding is offered only for blocking Starting servers, a slow or hung `tools/list` became non-deferrable and could hold the first response indefinitely.

**Symptom:** First-turn response can remain blocked for the duration of a slow or hung MCP `tools/list` operation, with no Skip/background action after the server reports connected.

**Fixed behavior:** A connected server remains `Starting` until `session.mcp_server_tools_loaded` or inventory `live.toolsLoaded` confirms tool discovery. Slow or nonresponsive `tools/list` work is now represented as blocking startup, so the existing Skip/background action can call `moveLoadingToBackground` and let the chat turn progress; normal servers become Ready when their tools arrive.

**Evidence:** In the base revision, `_translateSdkMcpStatus` mapped SDK `connected` directly to `McpServerStatus.Ready` (base line 9252, introduced by 74c45d448154f27b023e82a3b5e1be4043401118). The new runtime event contract explicitly distinguishes connection from completion of `tools/list`. The workbench only exposes `backgroundMcpServer` when a server is `Starting` with `blocking: true` (`agentHostCustomizationService.ts:299`), and after a 5s no-content grace renders the slow-start control (`agentHostSessionHandler.ts:3952-3977`); invoking it reaches `rpc.mcp.moveLoadingToBackground()` (`copilotAgentSession.ts:5963-5968`). Therefore the old Ready translation removed the only UI path that could release a turn still blocked on MCP tool discovery. The added branch at line 9303 retains connected-but-tools-pending servers as blocking Starting, while `_markMcpToolsLoaded` later promotes them to Ready.

### Scenario 1: First chat turn with an MCP transport connected while its tools/list response is slow or never arrives

- Critical path: The runtime's MCP tool discovery must finish before the turn produces content unless the user backgrounds startup. Before the diff, \`connected\` was published as Ready, which removed the workbench's Starting/blocking Skip action even though tools were still loading. After the diff, the server remains blocking Starting until \`mcp\_server\_tools\_loaded\`, and the existing 5-second slow-start UI can invoke the session-wide background RPC, taking tool discovery off the turn's critical path.
- Scaling input: Number of enabled MCP servers and duration of each server's tool enumeration; the severe case is one connected server whose tools/list never completes.
- Effective concurrency: Server startup concurrency is runtime-owned. The host performs constant-time Set/Map updates per event; backgrounding is one session-wide RPC rather than per-server fan-out.
- Cache behavior: A cached tool snapshot may emit tools-loaded before connected; the Set preserves that fact until connection. Inventory \`live.toolsLoaded\` is authoritative on newer runtimes, while missing metadata preserves older-runtime connected-is-ready behavior.
- Mechanism confidence: High: the event contract, status translation, workbench Starting/blocking gate, 5-second slow-start control, and background RPC call path are all directly traced.
- Magnitude uncertainty: Exact prevalence and delay depend on MCP implementations, but an MCP server that accepts initialization and stalls tools/list is a realistic and explicitly represented lifecycle state. The old path could block indefinitely.
- Expensive boundaries:

### Scenario 2: Initial and invalidated MCP inventory refresh while servers transition through tools-loaded

- Critical path: Inventory refresh is background bookkeeping for customization publication. It awaits both runtime \`listConfigured\` and the host client's MCP config list; lifecycle events can invalidate a snapshot and serialize another loop iteration. Direct tools-loaded handling promotes the affected server without waiting for inventory.
- Scaling input: Configured server count and the number/timing of once-per-connection tools-loaded events overlapping an inventory RPC.
- Effective concurrency: The two inventory/config IPCs run in parallel within an attempt; retries are serial. Newer refresh requests supersede older loops rather than allowing all of them to publish.
- Cache behavior: No inventory cache suppresses these calls. Request versions supersede older concurrent refreshes; lifecycle versions coalesce all events that occur during one attempt into a single retry. Older runtimes omit toolsLoaded and retain prior behavior.
- Mechanism confidence: High for the extra invalidation possibility and its coalescing; low for any user-visible degradation because the path is background and direct readiness does not await it.
- Magnitude uncertainty: A staggered event could cause an additional background attempt, but repeated worst-case overlap requires each once-per-connection event to land in a successive IPC window. No evidence shows material startup or turn latency from this bounded bookkeeping.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_refreshMcpServersFromRpc</code>: Fetch configured/live MCP server inventory; cardinality: One call per seed or \`mcp\_servers\_loaded\` refresh attempt; a tools-loaded event overlapping an attempt can cause one serialized retry, with multiple events during the same attempt coalescing through the lifecycle version
    - Introduced by diff: false; previous behavior: The same inventory RPC and retry loop existed; status events already invalidated in-flight snapshots. The diff adds tools-loaded as another validity-changing lifecycle event.; critical-path effect: Background inventory publication; not required for the tools-loaded event's direct Ready promotion
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:7366</code>: Fetch root/user MCP configuration names through \`client.rpc.mcp.config.list()\`; cardinality: Runs once in parallel with each inventory attempt, including a retry invalidated by lifecycle change
    - Introduced by diff: false; previous behavior: The same call accompanied every inventory attempt before the diff.; critical-path effect: Background provenance refresh, not the chat response critical path
- Verdict: No finding. The new invalidation prevents stale \`toolsLoaded:false\` inventory from reverting Ready state; retries are serialized/coalesced and no concrete user-visible performance regression is established.

### Scenario 3: MCP server reaches tools-loaded with host-side tool routing cache enabled

- Critical path: On tools-loaded, the host promotes the server to Ready and asynchronously refreshes routing metadata. The Ready publication is synchronous and does not await listTools or storage persistence.
- Scaling input: Connected server count, up to one normal refresh per connection, with tool metadata capped by the cache implementation.
- Effective concurrency: Different servers' fire-and-forget refreshes can overlap; there is no shared limiter, but the diff does not increase the normal connected-server burst and instead delays it until actual tool availability.
- Cache behavior: Warm cache is used to construct routing proxies, but live metadata is intentionally refreshed once the server's tools are available. Stored entries and descriptions are bounded; misses do not add retries here.
- Mechanism confidence: High: both old and new trigger paths call the identical helper, and the new connected translation prevents the old status handler from issuing the call before tools-loaded.
- Magnitude uncertainty: Server count may vary, but the changed trigger has the same effective per-connection cardinality as the prior connected trigger.
- Expensive boundaries:
