# Performance review: Agent Host: pre-warm Copilot sessions before the first send (experimental)

[PR #341698](https://github.com/microsoft/vscode/pull/341698) at `8f22493559d7e7fff5a7766ada7d51dacbac5aee`

## Findings (2)

### 1. [medium] Move stale warm-session teardown off the first-send path

**Finding ID:** `PERF-39D6E85BD3D0`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5815</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** SDK IPC calls, MCP subprocess shutdown, session deletion, and duplicated session-launch work  
**Scaling:** Added first-send latency grows with teardown time of the stale session and its configured MCP servers; every invalidated warm draft pays one full disconnect/delete plus a second launch, and delete failure can add a metadata IPC round trip.  
**Outcome:** Increased first-send latency on the critical path, especially with slow or stuck MCP servers.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before prewarming, the first Send launched the requested configuration once and did not have an obsolete live SDK session or MCP process set to disconnect and delete first.  
**Changed behavior:** When the first Send finds that the prewarmed launch is stale, it now synchronously awaits \_discardEarlyLaunch before launching the requested session. That cleanup awaits SDK disconnect (including MCP shutdown) and client.deleteSession, after which \_materializeProvisional performs a fresh SDK launch.  
**Confidence:** 0.99 — The sequential awaits and boundary implementations are explicit, and the PR's own tests prove common invalidation triggers cause two creates plus deletion. Only the absolute disconnect duration varies by MCP implementation.

**Causal diff evidence:** The added await at line 5815 serializes disposal/deletion of the speculative launch ahead of the cold launch on Send. No equivalent speculative resource or cleanup existed in the prior first-send path.

A user who changes model, agent, tools, MCP/plugin configuration, roots, or worktree choice while composing gets a slower first Send than before the feature: Send waits for all stale-session/MCP teardown and SDK deletion before the correctly configured session can even begin launching.

**Evidence:** \_materializeProvisional awaits \_takeEarlyLaunch before calling \_launchProvisional. At this added line, \_takeEarlyLaunch awaits \_discardEarlyLaunch; \_discardEarlyLaunch awaits \_destroyLiveSession and \_deleteSdkSession. \_destroyLiveSession awaits CopilotAgentSession.destroySession(), which awaits wrapper.disconnect(), and \_deleteSdkSession awaits CopilotClient.deleteSession (and may additionally query metadata on failure). Added tests demonstrate realistic pre-send invalidations for model/model-option, client-tool, and worktree changes, each producing two creates and deletion of the first session.

**Suggested direction:** Invalidate and tear down warm launches when launch-affecting draft state changes, before Send, or use a generation-specific speculative session identity so stale cleanup can run asynchronously while the requested launch starts; Send should not synchronously wait for obsolete MCP/session teardown.

### 2. [medium] Bound concurrent prewarming across drafts

**Finding ID:** `PERF-3FF050D95455`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionPrewarmer.ts:140</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** SDK sessions plus MCP subprocesses and their startup filesystem/network I/O  
**Scaling:** For N simultaneously open eligible drafts and M configured MCP servers, the host can retain N SDK sessions and start up to N×M server processes concurrently for five minutes; per-chat sequencing does not reduce aggregate concurrency.  
**Outcome:** Burst CPU/I/O and retained process memory, with reduced responsiveness and throughput during multi-draft creation or restore.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, an unsent provisional draft created no SDK session and started no MCP servers; only a draft that reached first Send paid one launch.  
**Changed behavior:** Every eligible provisional draft independently invokes warmChat, which creates an SDK session and then calls session.mcp.list() to start all configured MCP servers before Send; there is no shared limiter or one-warm-per-client/window policy.  
**Confidence:** 0.96 — The changed call path, unbounded per-draft dispatch, MCP-start boundary, and UI cardinality are directly established in code. Exact impact depends on how many drafts and MCP servers users keep open, so severity is medium rather than high.

**Causal diff evidence:** The added line 140 dispatches warmChat for each independently tracked candidate; the new warmChat implementation then launches the runtime and starts MCP servers. Previously AgentService did not dispatch any provider work for idle drafts.

Opening or restoring several unsent Copilot chat tabs while the experiment is enabled can launch duplicate sets of MCP subprocesses concurrently, causing CPU, memory, filesystem/network startup bursts and contention that slows the workbench even though none of the drafts has been sent.

**Evidence:** AgentService calls onProvisionalSessionCreated for every idle non-ephemeral provisional session; this line awaits warmChat independently per session. CopilotAgent.\_warmChat creates/registers the SDK session and line 5784 calls startMcpServers(), whose implementation awaits rpc.mcp.list() and explicitly documents that listing starts MCP servers. The workbench provisional service keeps one backend per untitled UI resource, and each input picker eagerly calls getOrCreate, so multiple open untitled chats produce multiple candidates. Neither AgentHostSessionPrewarmer nor CopilotAgent has an aggregate prewarm limiter; per-chat queues only serialize one chat.

**Suggested direction:** Put warmChat launches behind a small shared limiter and cap live unclaimed warm sessions per client/window (evict or skip older drafts), while preserving each chat's queue and TTL cleanup.

### Scenario 3: First Send after model, agent, tools, roots, MCP/plugin state, ownership, or worktree changed

- Critical path: Send validates the early launch, then synchronously disconnects the stale session, stops its MCP processes, deletes SDK state, creates a replacement SDK session, persists it, and only then sends the message.
- Scaling input: One stale speculative session per invalidated draft; cleanup latency scales with the number and shutdown behavior of that session's MCP servers.
- Effective concurrency: All stale cleanup and replacement launch steps are serialized by the chat queue. MCP listing may have been concurrent before invalidation, but replacement cannot start until awaited discard/delete finishes.
- Cache behavior: Any mismatch is a negative warm-cache outcome. There is no background invalidation or rewarm, so stale state is discovered at Send and the warm work is discarded.
- Mechanism confidence: Very high: the await chain and two-create/delete behavior are explicit and covered by changed tests for model, client-tool, and worktree invalidation.
- Magnitude uncertainty: Absolute delay depends on MCP shutdown and SDK deletion duration, but the added serialized boundaries occur deterministically for every stale warm launch.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_earlyLaunchStaleReason</code>: Revalidate launch configuration/customization state; cardinality: Once per first Send before deciding the cache is stale.
    - Introduced by diff: true; previous behavior: Cold Send performed launch discovery once without first validating a speculative runtime.; critical-path effect: Blocks Send before cleanup starts.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_discardEarlyLaunch/\_deleteSdkSession</code>: Disconnect the stale SDK session and delete its session state, with metadata confirmation on delete failure; cardinality: One disconnect and delete per stale warm launch; failure adds one getSessionMetadata call.
    - Introduced by diff: true; previous behavior: There was no speculative SDK session to disconnect or delete before first Send.; critical-path effect: Fully awaited before replacement creation can begin.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:destroySession</code>: Stop stale MCP servers during SDK disconnect; cardinality: One stale configured MCP process set per invalidated draft.
    - Introduced by diff: true; previous behavior: No stale MCP processes existed on first Send.; critical-path effect: Shutdown is part of the awaited disconnect and can dominate first-send latency for slow servers.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_materializeProvisional/\_launchProvisional</code>: Create and initialize the correctly configured replacement SDK session; cardinality: One replacement launch after cleanup, making two total creates for this draft.
    - Introduced by diff: true; previous behavior: First Send performed only this single launch.; critical-path effect: Begins only after stale cleanup and remains on Send's critical path.
- Verdict: Reportable first-send latency regression caused by cleanup placement.

### Scenario 4: Abandoning or expiring an unsent warmed draft

- Critical path: Closing a draft queues provider disposal; otherwise a five-minute timer queues discard. No message-send path is waiting unless disposal races with Send on the same chat queue.
- Scaling input: One live early session and timer per warmed draft until claimed, disposed, or expired.
- Effective concurrency: Cleanup is serialized per chat; different draft expirations/disposals can run concurrently with no aggregate limiter.
- Cache behavior: The one-shot warm entry has a five-minute TTL. Draft disposal and agent shutdown clear timers and destroy sessions; torn-down runtime state is deleted on later send/disposal.
- Mechanism confidence: High: TTL, disposal hooks, queueing, and disconnect/delete ownership are explicit.
- Magnitude uncertainty: Cleanup duration and overlap depend on server shutdown behavior and how many drafts are abandoned together.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_discardEarlyLaunch</code>: Disconnect and delete the unclaimed SDK session; cardinality: Once per abandoned/expired warmed draft.
    - Introduced by diff: true; previous behavior: Abandoned unsent drafts had no SDK state to clean up.; critical-path effect: Off user message progress for timer expiry; closing/disposal may await it.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:destroySession</code>: Terminate MCP servers owned by the discarded SDK session; cardinality: One configured process set per discarded draft.
    - Introduced by diff: true; previous behavior: No MCP subprocesses existed for abandoned unsent drafts.; critical-path effect: Off Send unless racing on the same queue.
- Verdict: No separate cleanup-leak finding: the PR provides bounded TTL, close, and shutdown cleanup; aggregate creation concurrency is covered by the reported burst finding.

### Scenario 5: Creating a draft with prewarming disabled (default/control arm)

- Critical path: The prewarmer waits for active-client arrival, awaits the session's coalesced customization-enablement initialization, checks pending/trust state, reports the experiment trigger, then exits before warmChat. This work is asynchronous relative to createSession completion.

- Effective concurrency: Evaluations are independent across drafts; no SDK/MCP work occurs because the setting check rejects treatment.
- Cache behavior: Session-enablement initialization is cached/coalesced by session key in \_sessionLoads; trust and root configuration are in-memory reads.
- Mechanism confidence: High for absence of SDK/MCP treatment work and per-session read coalescing.
- Magnitude uncertainty: Whether the prewarmer observes an already-started load depends on event ordering, but duplicate reads are prevented by \_sessionLoads.
- Expensive boundaries:

    - Introduced by diff: false; previous behavior: The enablement service already initialized sessions from emitted state envelopes; the new prewarmer awaits the same coalesced promise.; critical-path effect: Awaited only by the asynchronous gate evaluation, not by draft creation or Send.
- Verdict: No reportable regression in the default-off arm after accounting for existing/coalesced enablement initialization.
