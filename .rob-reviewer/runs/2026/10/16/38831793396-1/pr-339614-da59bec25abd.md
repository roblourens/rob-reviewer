## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/files/browser/explorerService.ts:457` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/files/browser/explorerService.ts:453`  
**Introducing path:** `src/vs/workbench/parts/files/electron-browser/explorerService.ts`  
**Introducing commit:** `688595bb5c6a07ef94d587d02cf153606a1873da`  
**Mechanism family:** `repeated-work`  
**Performance category:** `rendering`  
**Confidence:** 0.98

**Mechanism:** Each item in a bulk move independently refreshed both expanded Explorer parents, repeatedly filtering, sorting, diffing, and rendering the same child collections; for N sibling files this caused 2N tree update passes instead of two parent reconciliations.

**Symptom:** Bulk moves between expanded Explorer folders incurred latency growing linearly with the number of selected files because the same source and destination trees were reconciled once per file.

**Fixed behavior:** The changed refreshMove path records refresh requirements in a Map keyed by ExplorerItem (line 457), merges recursive requirements, and finishMoveBatch flushes each unique source parent once before each unique target parent once at working-copy operation completion. Cost now scales with unique affected parents rather than moved files.

**Evidence:** In the base revision, every synchronous FileService MOVE event enters ExplorerService.onDidRunOperation and the line at base 453 invokes view.refresh(false, oldParent) inside the per-moved-item handler; the adjacent target refresh does the same for the destination. ExplorerView.refresh delegates to tree.updateChildren, so moving N items between two expanded parents launches 2N collection-wide tree reconciliation passes. The added 32-item test directly establishes the changed cardinality: model mutations still happen for all 32 events while refreshes are deferred and reduced to exactly one source plus one target refresh.

### Scenario 2: Undo/redo and overlapping or multi-source bulk moves

- Critical path: Undo and redo reuse IWorkingCopyFileService.move and therefore enter the same correlation-scoped batching path. Completion waits for matching model continuations, then reconciles all unique source parents before all unique destination parents.
- Scaling input: N moved entries, P unique source/target ExplorerItem parents, and B concurrently active operations. Event matching is O(N\*B), but B is normally one and overlapping operations are short-lived; rendering is O(P) per batch rather than O(N).
- Effective concurrency: Each working-copy move operation has an independent correlation ID. Matching FileService events can join overlapping batches, while each batch flushes independently. Within a flush, distinct parents are parallelized by phase; source and target phases remain ordered. The pre-diff implementation launched more concurrent refresh promises, one set per item event.
- Cache behavior: Correlation IDs isolate batches; source-to-target URI maps only match actual events, and refresh maps retain state only for operation lifetime. Cleanup runs in finally and disposal clears all pending maps. Overlapping batches do not share cached refresh state and therefore do not create stale cross-operation entries.
- Mechanism confidence: High: event correlations, matching loop, phased Promise settlement, overlapping-batch tests, and disposal tests all establish ownership and bounded lifetime.
- Magnitude uncertainty: The prevalence of truly overlapping user operations and number of workspace-root aliases is low and not measured, but lifecycle and multiplicity are directly visible.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/services/workingCopy/common/workingCopyFileService.ts:402-444</code>: Perform reverse or repeated move operations for undo/redo.; cardinality: N sequential filesystem moves per undo or redo operation, unchanged by the diff.
    - Introduced by diff: false; previous behavior: Undo/redo used the same per-file filesystem operations and generated per-file Explorer events.; critical-path effect: Filesystem work remains the dominant mandatory operation and precedes completion refreshes.
  - other at <code>src/vs/workbench/contrib/files/browser/explorerService.ts:439-441</code>: Update unique source model parents first, then unique target model parents.; cardinality: At most one refresh per ExplorerItem per role/phase for each correlation-scoped batch; a parent serving both roles may correctly participate in both phases.
    - Introduced by diff: false; previous behavior: Every item event immediately launched source and target refreshes without per-operation coalescing or phase ordering.; critical-path effect: Flushes are joined to each operation's completion so subsequent undo/redo state observes a reconciled tree.
- Verdict: No reportable regression. No new unbounded concurrency or retention was found; phase-parallel work is bounded by unique parents and replaces a larger pre-existing refresh burst.

### Scenario 3: Partial failure, cancellation, single-file rename/move, and non-move file changes

- Critical path: Multi-file MOVE failures invoke the same completion flush for model mutations that already occurred. Single-file moves do not create a batch and continue to refresh immediately. Copy, delete, create, and external watcher paths bypass move batching.
- Scaling input: K successful moves before failure and P unique affected parents. Final rendering scales with P rather than K; single-item behavior remains constant.
- Effective concurrency: Partial successes are processed sequentially by WorkingCopyFileService and their collected refreshes are settled before the failure event completes. Single-file and non-move events preserve the prior immediate async-handler behavior.
- Cache behavior: Empty and partially filled batches are deleted before flushing and all transient maps/arrays/sets are cleared in finally. Late unmatched events take the immediate path. There is no negative cache or persistent retained-key growth.
- Mechanism confidence: High: didRun/didFail share finishMoveBatch, deletion precedes awaits, finally clears retained state, and tests cover empty failure, partial failure, late events, and disposal.
- Magnitude uncertainty: Provider-specific failure timing varies, but bounded cleanup and late-event behavior are covered by direct tests.
