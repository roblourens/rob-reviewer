### Scenario 1: Workbench/editor startup with font ligatures enabled

- Critical path: With no persisted reading, workbench startup synchronously calls FontMeasurements.readFontInfo before rendering can use font metrics, so the DOM measurement is on the cold-start critical path. With a restored reading, startup uses the cached value and the authoritative remeasurement occurs after the existing five-second eviction, off the startup critical path.
- Scaling input: Effective multiplicity is one measurement per distinct BareFontInfo key per registered window, not per editor. The diff increases a ligature-enabled measurement from 41 to 45 requests; each added probe renders 256 copies, adding eight DOM children and 2,304 text code units to the one measurement container.
- Effective concurrency: Measurement is synchronous. The first caller completes and writes the shared cache before another editor can read it, so same-window/same-font requests are naturally coalesced rather than concurrent.
- Cache behavior: FontMeasurementsCache shares positive readings by the full font key within each window. Restored readings are warm but untrusted and are evicted once after five seconds; the first subsequent caller repopulates the cache synchronously. Ligature-disabled fonts take no added probes.
- Mechanism confidence: High confidence in the synchronous DOM mechanism, exact probe cardinality, and cache deduplication from the traced implementations; uncertain only in the sub-operation's platform-specific duration.
- Magnitude uncertainty: Exact glyph-shaping and layout duration varies by browser, platform, and font. The added payload is fixed and small, does not increase layout-boundary count, and is absent for the default ligature-off configuration.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/editor/browser/config/charWidthReader.ts:43-56 via src/vs/editor/browser/config/fontMeasurements.ts:220</code>: Append a hidden font-probe container, synchronously read span offsetWidth values, and remove the container.; cardinality: One DOM insertion/removal and one browser layout pass per cold distinct window/font key; 45 offsetWidth reads after the diff versus 41 before. Because all DOM writes precede all reads, the four added reads do not interleave writes or create four additional layout flushes.
    - Introduced by diff: false; previous behavior: The same hidden-container measurement and synchronous layout already occurred with 41 requests. The diff only adds four regular ligature spans to that existing batch.; critical-path effect: Blocks cold font-info creation and therefore cold editor/workbench initialization; restored-cache startup avoids it.
- Verdict: No reportable regression. The diff adds bounded work to an existing single layout batch only for ligature-enabled cold keys, with no per-editor multiplication or extra forced-layout boundary.

### Scenario 2: Font remeasurement after editor font/zoom changes, display changes, or standalone remeasureFonts

- Critical path: The first editor recomputation for each affected window/font key synchronously remeasures before options can be committed. Display changes are already throttled for two seconds; explicit standalone remeasurement is intentionally immediate.
- Scaling input: Cost scales with distinct window/font-key combinations after cache deduplication, not with the number of open editors or notebooks. Each ligature-enabled key gets four added probes; unchanged keys remain cache hits.
- Effective concurrency: All listeners run synchronously on the event dispatch path. Cache insertion occurs before readFontInfo returns, serializing and coalescing same-key work. Different windows or genuinely different font settings remain separate measurements as before.
- Cache behavior: A new font or zoom value creates a different cache key. Display-change and explicit remeasurement clear the cache, but the first listener per key repopulates it and later listeners reuse that result. There is no negative-cache retry loop introduced by the diff.
- Mechanism confidence: High confidence from the clearAllFontInfos event flow, synchronous listener behavior, and per-window key cache.
- Magnitude uncertainty: The number of distinct simultaneous font configurations and auxiliary windows varies, but ordinary multi-editor fan-out collapses to one measurement per shared key.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/editor/browser/config/fontMeasurements.ts:220 and src/vs/editor/browser/config/charWidthReader.ts:43-56</code>: Synchronous hidden-DOM font measurement during the first cache miss after invalidation.; cardinality: Once per effective distinct window/font key after invalidation, with four more spans and width reads only when fontFeatureSettings is not OFF.
    - Introduced by diff: false; previous behavior: Invalidation already caused one 41-probe DOM measurement per effective key. The diff preserves invalidation, sharing, and scheduling and expands the batch to 45 probes.; critical-path effect: Blocks the first affected options recomputation, while subsequent same-key editors are cache hits.
- Verdict: No reportable regression. The changed work remains fixed per effective key and preserves existing throttling and coalescing.

### Scenario 3: Rendering editor lines with ligature-capable monospace fonts

- Critical path: The changed classification is computed only during font measurement. Renderers consume the cached isMonospace boolean; the diff adds no DOM measurement, IPC, filesystem, network, serialization, or allocation boundary per rendered line or frame.
- Scaling input: Classification scans at most the fixed 45-request array once per cold font key. It does not scale with document lines, viewport rows, typing frequency, or frames.
- Effective concurrency: No asynchronous or burst concurrency is introduced. Rendering reads immutable cached font information.
- Cache behavior: The resulting FontInfo, including isMonospace, is cached and reused by line, diff, accessibility, notebook, and ghost-text rendering paths.
- Mechanism confidence: High confidence from all isMonospace consumers and the cache ownership path.
- Magnitude uncertainty: Whether a specific font passes the ligature probes depends on browser shaping and the font, but this affects classification behavior rather than adding hot-path work.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. The change may enable existing monospace rendering optimizations; it does not add work on the render/scroll/input path.
