## Findings (1)

### 1. [medium] Move the all-session certificate refresh off the mutation critical path

**Finding ID:** `PERF-EF6AFE18B869`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3898</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SDK/runtime IPC calls for certificate relevance, installation support, and status, plus per-session metadata publications  
**Scaling:** The Promise.all visits every live session. Reads coalesce only for sessions sharing the same proxyCa RPC object and auth configuration, so effective IPC cardinality grows with distinct live runtimes/configuration groups while metadata publication still grows with live-session count.  
**Outcome:** Certificate commands and their success/error dialogs remain blocked after the OS trust mutation has already completed, adding up to a five-second timeout for a hung read stage (and potentially longer when multiple stages are each slow).  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no certificate mutation command and therefore no post-mutation global SDK status sweep on this management IPC/remote-request path; within the new operation, the SDK mutation result itself is already validated before reaching this finally block.  
**Changed behavior:** Every install, rotate, or remove attempt now awaits refreshSandboxCertificate for all live sessions in a finally block, including failed attempts, before returning the operation result to the UI.  
**Confidence:** 0.98 — The changed await, full live-session enumeration, SDK RPC chain, per-read timeout, and UI awaiting of the connection operation are all directly traced. Exact live-session/config counts and normal RPC duration vary, which affects severity but not the mechanism.

**Causal diff evidence:** The added RIGHT line \`await Promise.all(this.\_allLiveSessions().map(live =&gt; live.refreshSandboxCertificate()));\` explicitly joins every live-session status refresh to the newly added mutation request before it can return.

On a slow or partially unresponsive Copilot runtime, Install/Rotate/Remove keeps the progress notice active and delays both completion and failure feedback even though the trust-store mutation has already resolved. Multiple distinct live runtime/config groups also issue their refresh IPC chains concurrently.

**Evidence:** \_withSandboxCertificateRefresh awaits operation(session), whose install/rotate/remove implementations validate the SDK mutation outcome, then line 3898 awaits Promise.all over \_allLiveSessions(). Each refresh reaches CopilotSandboxCertificateDiagnostics.update -&gt; CopilotSandboxCertificate.getStatus -&gt; \_check, which performs checkRelevance, checkInstallationSupport, and getStatus across SDK IPC with a separate 5,000 ms raceTimeout per read. The cache groups reads by proxyCa RPC and auth configuration, so this is bounded per group but remains on the user-visible command critical path and fans out across distinct groups.

**Suggested direction:** After the validated mutation settles, schedule refreshes without awaiting the global sweep (for example, await only the target refresh if immediate metadata is required and run the remaining deduplicated runtime/config refreshes in the background with explicit error logging). Preserve the existing per-runtime mutation sequencer and cache invalidation.
