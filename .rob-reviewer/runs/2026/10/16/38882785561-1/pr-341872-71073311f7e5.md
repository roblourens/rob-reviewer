# Performance review: Add multi-file diff editor with optional file list widget

[PR #341872](https://github.com/microsoft/vscode/pull/341872) at `71073311f7e594811e1b4200f9b3cf1d3021aa7d`

## Findings (2)

### 1. [medium] Defer the file-list tree until it can be shown

**Finding ID:** `PERF-41537CC1A8DE`  
**Location:** <code>src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorWithFileListWidget.ts:133</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** The file-list widget, Workbench tree model nodes, per-item/tree-element objects, listeners, and hidden DOM infrastructure.  
**Scaling:** Retained objects and initial tree work grow O(number of changed files plus folder path nodes) and persist for the editor lifetime; hidden viewport synchronization additionally scales with scrolling frequency.  
**Outcome:** Increased open latency and retained-memory/GC pressure in narrow editor groups, with unnecessary ongoing CPU while the hidden list remains subscribed.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no file-list tree or its listeners. Even within the new composite, a disabled list is cleared; only the new responsive-hidden path retains the full widget despite rendering none of it.  
**Changed behavior:** Enabling the experiment now constructs and retains the complete file-list widget even when the editor is narrower than 400 + 160 pixels and the split view immediately hides that widget.  
**Confidence:** 0.99 — The creation condition ignores hasRoom, and the added test explicitly expects fileListVisible=false while hasList=true at 500px. The file-list constructor and autorun explicitly create a tree model for every current item and subscribe to viewport changes; only prevalence and collection size vary.

**Causal diff evidence:** RIGHT lines 127-137 compute hasRoom but instantiate MultiDiffEditorFileList whenever enabled, before applying visible = enabled && hasRoom; line 133 is the eager construction point.

Opening an enabled multi-diff editor in a narrow/split editor group performs O(N) tree construction and retains the list/tree nodes for the editor lifetime even though no file list can be displayed; subsequent diff scrolling also continues list synchronization work. Large commits or SCM groups therefore pay extra open-time CPU, memory, and GC cost for invisible UI.

**Evidence:** The autorun clears the list only when the user disables it. If enabled but too narrow, it still creates MultiDiffEditorFileList, whose constructor creates a WorkbenchCompressibleObjectTree and calls getFileListElements(...)/setChildren(...) for the full view-model item collection. It also keeps currentItem subscribed to visibleDiffItems. The PR's own responsive test records \`{ fileListVisible: false, hasList: true }\` at 500px, proving this hidden lifetime. SCM group and commit sources pass their full, uncapped changed-file collections.

**Suggested direction:** Gate initial creation on \`enabled && hasRoom\`, and suspend or dispose the list's item/viewport observers while responsive-hidden. If tree expansion/focus must survive resize, save that small view state and restore it when recreating the visible tree.

### 2. [medium] Avoid rescanning every diff item on each scroll

**Finding ID:** `PERF-A666801A9900`  
**Location:** <code>src/vs/editor/browser/widget/multiDiffEditor/multiDiffEditorWidgetImpl.ts:211</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Main-thread CPU plus the arrays allocated by filter and map.  
**Scaling:** Cost grows as O(number of diff items × scroll updates); equality comparison only suppresses notifications after both full scans and allocations have already occurred.  
**Outcome:** Increased scroll latency, CPU/GC pressure, and dropped frames on large multi-file diffs.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, scrolling ran the existing compressed-layout and render passes, but there was no visibleDiffItems observer and no extra filter/map traversal solely to synchronize a file list.  
**Changed behavior:** When the file list is enabled, every scroll-layout update now performs two additional synchronous passes over all diff items and allocates intermediate/result arrays before equality suppression can prevent downstream updates.  
**Confidence:** 0.97 — The scroll view derives layout directly from onScroll and replaces the layout object on each update; the new file-list currentItem observable keeps visibleDiffItems observed. The changed filter/map and its O(N) cardinality are explicit. Only the exact millisecond impact varies with commit size and hardware.

**Causal diff evidence:** RIGHT lines 208-213 add a derived observable that reads the per-scroll layout and then runs filter(...).map(...) across every view item; MultiDiffEditorFileList now observes that value to follow the viewport.

With the file list enabled, scrolling a large SCM group or commit adds O(N) synchronous CPU and short-lived array allocation to every wheel/trackpad update, increasing main-thread and GC pressure and risking dropped frames for large change sets.

**Evidence:** CompressedVirtualizedScrollView observes onScroll, recomputes and sets layout on each scroll update, and its existing render already loops over all items. This new derived value reads that layout and independently filters and maps the entire \_viewItems array. MultiDiffEditorFileList.currentItem reads visibleDiffItems, so the derived is live whenever the optional list exists. SCM groups and history commits feed the editor's complete resource/change arrays with no cap, making hundreds or thousands of items realistic.

**Suggested direction:** Publish visible view models from the scroll view's existing layout/render traversal (or expose a maintained visible index range) so each scroll does O(visible items) incremental work rather than another full-collection filter/map.
