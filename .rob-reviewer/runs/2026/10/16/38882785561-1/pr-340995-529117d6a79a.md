## Findings (1)

### 1. [medium] Keep the bounded atlas cache across transient invisibility

**Finding ID:** `PERF-26D0800ED392`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatWorkingLogoAtlas.ts:154</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** 320 SVG serializations and image decodes, canvas pixel buffers, and atlas encoding work  
**Scaling:** The full atlas-generation cost repeats once for every transition from zero visible Draw logos back to any visible Draw logo; simultaneous same-key logos coalesce, but sequential session switches, panel hide/show, or scrolling the only active logo out and back do not.  
**Outcome:** repeated background CPU and allocation/GC pressure while navigating active chats  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Draw used the existing SVG artwork directly and visibility changes only stopped and restarted frame updates; there was no 320-frame resource to regenerate after each reveal.  
**Changed behavior:** Each visible logo now owns an atlas reference, and releasing the last reference immediately disposes the per-window store and all cached atlases. The next visible logo must create a new cache entry and rerun atlas generation.  
**Confidence:** 0.98 — The hide-to-clear-to-last-reference-disposal-to-320-frame-generation call path is explicit and the single-logo hide/reveal scenario is covered by the added test. Exact duration varies by hardware and icon size, but the repeated work and trigger do not.

**Causal diff evidence:** The added \`if (--owner.references === 0) { owner.store.dispose(); }\` at lines 153-154 ties cache lifetime to currently acquired/visible playback references rather than to the window or live widget lifetime; before this PR no atlas regeneration existed.

With a single active request, scrolling its footer out of view, switching chat sessions, or hiding and reopening Chat destroys the warm atlas and makes the next reveal serialize/rasterize up to 320 poses and encode/load the sheet again. This adds avoidable CPU/GC activity to common navigation and keeps the SVG fallback running during every rebuild.

**Evidence:** \`observeVisibility\` calls \`restartDrawAnimation\` on every intersection/document visibility transition; \`restartDrawAnimation\` calls \`clearAtlas\`, which disposes the acquired reference. This added line then disposes the shared store when that was the last visible owner. Disposing the store destroys \`ChatWorkingLogoAtlasCache\`; the next acquire reaches \`createChatWorkingLogoAtlas\`, whose loop processes 320 frames with SVG serialization, object-URL image loads, canvas draw/getImageData/putImageData, and a final \`toBlob\`. The live-atlas test explicitly exercises hide then reveal for a single logo, which follows this cold path.

**Suggested direction:** Keep the existing 16 MiB LRU cache alive across transient zero-reference periods—e.g. own it for the window/widget lifetime or use a delayed idle teardown—and retain the current pagehide/window-unregister disposal. Playback references can still be released immediately while decoded atlases remain bounded and reusable.
