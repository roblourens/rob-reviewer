### 1. [medium] Clean up imports when image preparation is cancelled

**Finding ID:** `PERF-99E8CB6C11AC`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/chatBackgroundTool.ts:256</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Imported image files and their bytes in per-profile local storage.  
**Scaling:** Retained storage grows linearly with the number of distinct invocations canceled after import, at up to 25 MB per invocation; a future prune also performs metadata/filter/delete work proportional to the accumulated file count.  
**Outcome:** Unbounded retained filesystem storage and eventual extra metadata/delete I/O when a later prune scans the accumulated files.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no agent-driven import folder or tool path that copied images into profile storage, so canceling a background operation could not strand these content-addressed copies.  
**Changed behavior:** Background-tool invocations now copy non-known source images into per-profile storage before decoding/applying them, but a cancellation after the copy aborts before any cleanup or pruning runs.  
**Confidence:** 0.98 — The call path is explicit and fully awaited: importImage writes the content-addressed file and returns created=true; cancellation at lines 256 or 269 throws through invoke; neither cancellation branch deletes the file, and the sole pruning caller is after successful apply. Repository search finds no other owner or cleanup call for agentsChatBackgrounds. Exact prevalence is uncertain, but retention and scaling are deterministic.

**Causal diff evidence:** The added prepareImage path assigns a newly copied import, then added RIGHT line 256 throws on cancellation without deleting it; the only targeted delete is inside the later decode-error catch, while pruneImportedImages is awaited only after apply succeeds at line 221.

Canceling an image-background tool call after its copy finishes (or while image decode is in progress) leaves an unreferenced file of up to 25 MB in profile storage. Repeated canceled generation/apply attempts with distinct images permanently grow disk usage until a later successful background operation happens after the grace period; if the user stops using the tool, those files are never reclaimed.

**Evidence:** importImage reads up to MAX\_IMAGE\_SIZE (25 MB) and writes the content to agentsChatBackgrounds. prepareImage then checks cancellation before decode and again after decode. Only the decode-error catch deletes imported.created; cancellation is rethrown by invoke. pruneImportedImages is called only after the switch in apply, which canceled preparation never reaches, and no other pruneImportedImages/agentsChatBackgrounds cleanup exists.

**Suggested direction:** Track whether importImage created the file and delete that new copy in a cancellation/failure cleanup path before rethrowing (while preserving reused files and files that were successfully applied); alternatively give the import folder an independent startup/disposal cleanup owner so reclamation does not depend on a later successful invocation.
