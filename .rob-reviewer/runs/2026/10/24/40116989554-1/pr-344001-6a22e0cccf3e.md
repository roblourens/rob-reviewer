# Performance review: Automations: graduate settings

[PR #344001](https://github.com/microsoft/vscode/pull/344001) at `6a22e0cccf3e0e048900f1fb46475ddc7fa10727`

## Findings (1)

### 1. [medium] Defer the default-on cloud refresh until Automations is used

**Finding ID:** `PERF-A9CDCC803DC7`  
**Location:** <code>src/vs/sessions/contrib/automations/browser/automations.contribution.ts:41</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Filesystem stats/reads, shared-process IPC calls, GitHub API requests, and hydrated definition/history objects.  
**Scaling:** Per window launch, filesystem discovery grows with up to 10 recent workspaces times up to 50 parent lookups. Network work grows with effective repository count R and definition count D: at least capability/list calls per eligible repository, one detail hydration per definition, and one history request per definition, with active-run detail requests on top. Repository refresh is serialized; definition hydration is five-wide and history is four-wide.  
**Outcome:** Excessive background filesystem and network I/O after workbench restoration, with avoidable resource contention and bandwidth use.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With the prior default \`false\`, users who had not opted in failed the \`enabled\` gate, no \`GitHubCloudAutomationStore\` was created, and startup/restoration caused zero cloud-automation filesystem or API work.  
**Changed behavior:** Users without an explicit override now automatically create the cloud store and run a full catalogue-and-history refresh after every workbench restoration, even if they never open or invoke Automations.  
**Confidence:** 0.98 — The setting-to-refresh call path is direct and unconditional for a non-enterprise default GitHub account: the changed default feeds \`enabled\`, the autorun creates the store, and then awaits \`refresh()\`. The repository code explicitly enumerates the filesystem and network operations and their limits. Only prevalence and real-world repository/automation counts are uncertain; the mechanism is not.

**Causal diff evidence:** The added \`default: true\` at \`automations.contribution.ts:41\` changes the no-override value consumed by \`CloudAutomationStore.enabled\`; that value makes its autorun create \`GitHubCloudAutomationStore\` and immediately call \`this.refresh()\` after the default sessions provider is registered post-restore. With the prior \`default: false\`, the same autorun left \`store\` undefined and made no requests, as also codified by the existing \`default-off ... create no API requests\` test.

A signed-in GitHub.com user can incur dozens to hundreds of filesystem, shared-process IPC, and GitHub API operations after opening a window without using Automations, consuming bandwidth/battery and contending with normal post-startup work. The cost is especially visible for users with several recent repositories or many cloud definitions.

**Evidence:** \`CopilotChatSessionsProvider\` is constructed at \`WorkbenchPhase.AfterRestored\` and always constructs \`CloudAutomationStore\` for the default provider. When enabled, \`CloudAutomationStore\` immediately calls \`refresh()\`, which invokes \`refreshRepositories\` and then \`refreshHistory\`. \`refreshRepositories\` serially resolves up to 10 Agents recent workspaces; each local resolution can perform up to 50 parent \`.git\` stats plus config reads. It then performs \`getConfiguration\` and a paginated definition list for every discovered/persisted repository, hydrates every definition in batches of five, and \`refreshHistory\` performs one \`listRuns\` per definition (plus detail calls for active runs) with concurrency four. Definitions are only memory-cached, so this repeats on each new workbench process/window.

**Suggested direction:** Keep the graduated setting on, but defer store refresh and recent-workspace discovery until the Automations UI/tool first requests cloud data (coalescing that first load), or otherwise restrict the automatic post-restore path to a cheap persisted signal and schedule any necessary refresh as background work.

### Scenario 2: Open the Automations UI or invoke an automation tool after restoration.

- Critical path: Rendering or invoking an Automations surface requires provider catalogue state; an in-flight cold refresh can delay cloud results, while a completed eager refresh makes first use faster. Explicit mutations and tool/trigger loads remain user-initiated critical-path network work.
- Scaling input: Repository and definition counts on cold load; one tool catalogue and one trigger catalogue request on their respective first uses.
- Effective concurrency: Cold catalogue refresh uses the same serialized repository processing, five-wide detail hydration, and four-wide history limiter. Subsequent refresh requests coalesce while in flight; mutation operations serialize through the store sequencer.
- Cache behavior: If the automatic post-restore refresh completed, first use is warm from in-memory catalogue/history caches. If it is still running, refresh promises coalesce duplicate reads. Tools/triggers remain separately lazy and cache successful results for the account lifetime; failed loads can retry. A new process loses catalogue/history warmth.
- Mechanism confidence: High for cache/coalescing behavior from \`refreshPromise\`, \`historyRefresh\`, and account-lifetime tool/trigger caches.
- Magnitude uncertainty: The first-use latency benefit from prefetching depends on whether the user opens Automations and how quickly after restoration. No measurement establishes that this benefit outweighs eager cost for the broader default-on population.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/copilotChatSessions/browser/cloudAutomationStore.ts and githubCloudAutomationStore.ts</code>: Reads cloud automation catalogue/history and lazily loads tool/trigger catalogues.; cardinality: Cold first use reaches the same R-repository and D-definition GitHub request set; warm first use performs no catalogue/history boundary calls unless it explicitly refreshes. Loading tools or triggers adds one separately cached API call each when requested.
    - Introduced by diff: false; previous behavior: Explicitly opted-in users already had this first-use behavior. For users with no override, cloud automation was unavailable and issued no calls; the reported regression is the work being moved before any first use, not the existing on-demand boundaries.; critical-path effect: Cold network work blocks cloud catalogue availability; warm cached data is immediate. Tool/trigger calls block only the corresponding requested configuration.
- Verdict: No separate finding: first-use request fan-out is pre-existing for enabled users and is coalesced/bounded. This scenario supports deferring the newly eager refresh until actual use while preserving behavior.
