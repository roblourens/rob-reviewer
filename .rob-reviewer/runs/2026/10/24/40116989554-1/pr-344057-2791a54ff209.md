# Performance review: agentHost: don't allow moving a chat that hasn't sent a message

[PR #344057](https://github.com/microsoft/vscode/pull/344057) at `2791a54ff2095c0e699d8460a8f36d7c9cf73a8b`

## Findings (1)

### 1. [medium] Skip movability rebuilds after the first turn

**Finding ID:** `PERF-8D9D59EE85A6`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostChatMovability.ts:215</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and temporary Maps/Sets/arrays allocated while rebuilding a session's movability context  
**Scaling:** Each ChatTurnStarted now performs O(C) work in the number of chats in the session: update() linearly finds the summary, \_sourceContext() walks all chats and builds children/summary indexes, and sessions with per-chat worktrees scan the summaries again. This repeats for every turn, including all turns after the first; the repository's own perf tests model 100- and 400-chat sessions.  
**Outcome:** Increased prompt-start latency and CPU/GC pressure for sessions that have accumulated many nested chats  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, ChatTurnStarted did not trigger AgentHostChatMovability.update(), so sending a message performed no session-wide movability rebuild on this path.  
**Changed behavior:** The added action branch synchronously calls update(envelope.channel) for every ChatTurnStarted, although notStarted can only transition to false when a chat starts with no completed turns.  
**Confidence:** 0.98 — The changed synchronous call path, per-event frequency, and linear session scan are directly established by the listener, dispatch implementation, update/\_sourceContext code, and existing 100/400-chat perf tests. Exact milliseconds vary by catalog/worktree shape, but the repeated mechanism and scaling are not speculative.

**Causal diff evidence:** Added RIGHT line 215 includes ActionType.ChatTurnStarted in the new event branch, and RIGHT line 217 invokes this.update(envelope.channel), placing the full recomputation on every turn start; neither operation existed on this event before the PR.

Every subsequent message in a large multi-chat session synchronously rescans and reindexes the full chat catalog before dispatchServerAction returns and turn processing continues, delaying prompt submission; with hundreds of chats this repeated O(C) allocation/work occurs on every message even though movable is unchanged.

**Evidence:** AgentHostStateManager.\_applyAndEmit synchronously fires onDidEmitEnvelope; this new branch handles every ChatTurnStarted and calls update(). With no MovabilityPass, update() reaches \_listedSummary(...).find over the session catalog, then \_sourceContext(), which loops over state.chats and allocates children plus a Map of all summaries; \_worktreeUsers() can loop all summaries again. setChatMovable() suppresses the notification when unchanged but only after this work. The added tests establish that the subsystem explicitly supports/scales against 100 and 400 chats.

**Suggested direction:** Gate ChatTurnStarted recomputation to the actual notStarted transition (for example, after reduction only when the chat has zero completed turns and this is its first active turn), and similarly recompute truncation/load cases only when the notStarted boolean can change. This preserves immediate first-turn eligibility without rebuilding on every later message.
