### Scenario 1: Successful browser unit-test run across selected browsers

- Critical path: For each selected browser, the runner creates a local HTTP server, launches a browser, discovers CSS, opens the renderer, imports test modules sequentially, runs Mocha, disposes the stall watchdog, waits for already-running console handlers, and closes the browser. The added listener wait is only during teardown, after tests finish.
- Scaling input: Number of selected browsers (three by default), test modules, tests, CSS files, and console events. Module imports are sequential within a browser; browser runs are parallel by default or explicitly sequential with --sequential.
- Effective concurrency: Up to one run per selected browser executes concurrently via Promise.all. Each browser imports modules serially. Console handlers may overlap; removeAllListeners with behavior 'wait' joins only handlers already in flight and does not add handler invocations.
- Cache behavior: Each fresh page has its own browser module cache; there is no cross-browser page cache. The diff does not change module/cache keys, CSS discovery, negative caching, or coalescing.
- Mechanism confidence: High confidence that successful-path boundary cardinality is unchanged and that the only new synchronization is bounded teardown joining.
- Magnitude uncertainty: Pending console-handler duration depends on test logging and Playwright serialization latency, but the diff waits only for already-started handlers during teardown and adds no calls; no realistic unbounded or multiplicative regression is established.
- Expensive boundaries:
  - subprocess at <code>test/unit/browser/index.js:runTestsInBrowser</code>: Launch and close one Playwright browser process tree per selected browser.; cardinality: One launch and one close per selected browser; three concurrent runs by default.
    - Introduced by diff: false; previous behavior: The same browser process was launched and closed once on a successful run; cleanup occurred after the catch block.; critical-path effect: Browser launch precedes all testing and browser close remains on teardown. The diff moves close into finally but does not increase cardinality.
  - network at <code>test/unit/browser/index.js:createServer and test/unit/browser/renderer.html:loadModules</code>: Serve renderer assets, CSS, and imported test modules from the per-run localhost server.; cardinality: One renderer navigation plus asset/module requests per browser; one module import per discovered test module, sequentially initiated.
    - Introduced by diff: false; previous behavior: The same local server and sequential dynamic imports were used.; critical-path effect: All imports must finish before Mocha runs. The diff leaves successful import cardinality and ordering unchanged.

### Scenario 2: Browser test-module import failure, including runs with --grep

- Critical path: Modules are imported sequentially until the first failing import. The page logs that module, rejects loadAndRun, and the CLI tears down the watchdog, pending console handler, local server, and browser before exiting nonzero. No later module or Mocha test is on the changed failure path.
- Scaling input: Position of the first failing module among the discovered module list and number of selected browsers. Each browser can encounter at most its first failure because loading aborts immediately.
- Effective concurrency: Selected browsers still run concurrently by default, so up to one failure/cleanup path per browser can execute simultaneously. Within a browser, imports remain serial and failure propagation is single-shot.
- Cache behavior: A failed dynamic import terminates the page run; the diff neither retries nor negatively caches it. Fresh browsers/pages do not share module caches. There is no repeated failure loop.
- Mechanism confidence: High confidence from the sequential loop, rethrow, page-promise rejection, outer finally, and browser-level Promise.all call flow.
- Magnitude uncertainty: The amount of work avoided depends on where the failed module appears, but the direction is unambiguous: later imports and tests are removed from the failure path.
- Expensive boundaries:
  - network at <code>test/unit/browser/renderer.html:loadModules</code>: Fetch dynamic test modules from localhost until an import fails.; cardinality: Imports through the first failing module per browser; remaining modules are not requested by this run.
    - Introduced by diff: false; previous behavior: The failing request was logged and converted to an empty module, after which all remaining modules were imported and the surviving tests ran.; critical-path effect: The failing import rejects the critical path immediately.
  - ipc at <code>test/unit/browser/renderer.html:loadModules and test/unit/browser/index.js:runTestsInBrowser</code>: Send one failed-module console event and reject the outstanding page.evaluate call.; cardinality: One error log and one evaluation rejection per failing browser run.
    - Introduced by diff: true; previous behavior: The page emitted one BAD console message but resolved the failed import, so page.evaluate continued through remaining modules and tests instead of rejecting.; critical-path effect: Failure reaches the CLI immediately; waiting for the pending console callback ensures its already-issued serialization completes before browser shutdown.
  - subprocess at <code>test/unit/browser/index.js:runTestsInBrowser</code>: Close the Playwright browser process tree during failure cleanup.; cardinality: One close per failing browser run, unchanged from the eventual cleanup count.
    - Introduced by diff: false; previous behavior: The caught failure path eventually reached browser.close after the catch; import failures themselves were swallowed and therefore did not enter that path.; critical-path effect: Cleanup is on the failure exit path and prevents browser-resource retention.
- Verdict: No reportable regression. The change reduces failure-path CPU, I/O, and elapsed time by aborting remaining module/test work, while preserving bounded cleanup.
