# Performance review: ci: run only the unit tests a change can affect on macOS and Windows

[PR #342907](https://github.com/microsoft/vscode/pull/342907) at `ecf3b9afd9636b5c6725a093cfa9937a0c107ea5`

## Findings (1)

### 1. [medium] Keep the Detect Changes working tree sparse

**Finding ID:** `PERF-484764BB8A2B`  
**Location:** <code>.github/workflows/pr.yml:57</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** filesystem writes, worktree bytes, and checkout CPU  
**Scaling:** The extra work is proportional to the number and size of files in the repository and occurs once on every PR workflow run, before all \`needs: changes\` jobs can start.  
**Outcome:** increased latency and excessive filesystem I/O on the CI critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The Detect Changes checkout materialized only \`.github/actions/detect-changes\` and \`.github/actions/detect-agent-host-e2e-changes\`; repository blobs for the fetched commit were still available through Git object commands.  
**Changed behavior:** \`actions/checkout\` now populates the full VS Code working tree before change detection instead of materializing only the two local action directories. The additional depth is required, but removing sparse checkout is not required for \`git ls-tree\`/\`git cat-file\` access.  
**Confidence:** 0.99 — The diff directly removes sparse checkout, Git sparse checkout affects worktree population rather than availability of already-fetched commit objects, ripple reads repository content by object ID through \`git ls-tree\` and \`git cat-file\`, and the only worktree paths used here are the two local actions plus \`build/ripple\`. All downstream jobs explicitly depend on \`changes\`, so this I/O is on their critical path.

**Causal diff evidence:** The hunk deletes the existing \`sparse-checkout\` list and replaces it with the added claim at RIGHT line 57 that the checkout cannot remain sparse, leaving only \`fetch-depth: 2\`; this changes the worktree from two action directories to the entire repository on every PR run.

Every pull-request push performs unnecessary full-repository worktree materialization and delays all jobs gated on Detect Changes; the added filesystem I/O grows with repository size even when the PR ultimately needs no unit tests.

**Evidence:** \`Engine::snapshot\` calls \`git ls-tree\` and \`BlobReader\` runs \`git cat-file --batch\`, so ripple reads blobs from the Git object database, not from checked-out files. \`fetch-depth: 2\` can therefore be combined with sparse checkout. The workflow itself only executes \`./.github/actions/detect-changes\`, \`./.github/actions/detect-agent-host-e2e-changes\`, and files under \`build/ripple\`; meanwhile 29 jobs declare \`needs: changes\`, making the unnecessary worktree expansion gate broad CI progress.

**Suggested direction:** Keep \`fetch-depth: 2\`, restore sparse checkout, and add \`build/ripple\` to the existing two action paths. This leaves both commits' objects available to \`ls-tree\`/\`cat-file\` while avoiding a full worktree checkout.

### Scenario 2: macOS and Windows Electron, Node, and browser unit-test jobs consume the plan and run only selected files.

- Critical path: Each of four unit-test jobs downloads the artifact before its test steps. Within a job the Electron, Node, and browser steps remain serial workflow steps; each runner first discovers its default test files, intersects them with the plan, and then starts only its supported selected tests. When \`plan.json\` exists without \`unit.txt\`, the test steps are skipped; when no trusted plan exists, the prior full-suite path runs.
- Scaling input: Number of selected unique test files after declaration-graph deduplication, capped by the 50% weighted-work fallback. Each runner filters that set against its existing candidate glob.
- Effective concurrency: The four macOS/Windows unit jobs can run in parallel. Artifact download occurs once per job. Selection is a Set membership filter; no per-selected-file network or IPC fan-out is added. Individual runner process/browser behavior remains controlled by the pre-existing runners.
- Cache behavior: The artifact is per workflow run, with no cross-run cache. Presence of \`plan.json\` selects plan mode; absence or failed download is a negative state that safely runs all tests. An empty valid selection has \`plan.json\` but no \`unit.txt\`, causing the unit steps to skip. Runner file discovery is not newly cached.
- Mechanism confidence: High: artifact conditions, fallback states, Set construction, candidate filtering, and browser zero-match exit are explicit in changed code.
- Magnitude uncertainty: Runner startup overhead for a shared list containing no tests of one family varies, especially Electron, but it replaces a full-suite run rather than adding work relative to the pre-diff scenario.
- Expensive boundaries:

### Scenario 3: The main-branch Ripple workflow maintains the executable cache after source changes and on a daily schedule.

- Critical path: This workflow is off the pull-request job critical path, but its successful cache population determines whether later PR Detect Changes runs use a warm binary or compile from source.
- Scaling input: Ripple source/dependency compilation size and frequency of source changes or cache eviction, not repository test count.
- Effective concurrency: A workflow-level concurrency group serializes runs for the same workflow/ref and does not cancel an in-progress build. Steps are serial; Cargo provides its own compile parallelism.
- Cache behavior: Exact positive cache entries are keyed by OS plus Cargo manifests, toolchain, and all Rust sources. Lookup-only avoids binary transfer on a hit. A miss performs and saves one build; the daily run repairs eviction. There is no negative cache, so persistent build failures retry daily, which is bounded by schedule and timeout.
- Mechanism confidence: High: triggers, exact key, lookup-only behavior, build condition, save condition, and concurrency group are explicit.
- Magnitude uncertainty: Cold Cargo duration and cache eviction frequency vary, but execution is daily/change-triggered and timeout-bounded.
- Expensive boundaries:
  - network/filesystem at <code>.github/workflows/pr-ripple.yml:30-35</code>: Sparse-check out \`build/ripple\`.; cardinality: Once per push changing ripple, daily schedule, or manual dispatch; only the ripple directory is materialized.
    - Introduced by diff: true; previous behavior: No cache-maintenance workflow existed.; critical-path effect: Precedes cache lookup in this maintenance workflow and is off the active PR critical path.
  - network at <code>.github/workflows/pr-ripple.yml:38-45</code>: Lookup the exact ripple binary cache without downloading it on hit.; cardinality: One lookup per maintenance run.
    - Introduced by diff: true; previous behavior: No ripple cache existed.; critical-path effect: A hit ends the expensive path; a miss triggers the build.

- Verdict: No reportable regression. The bounded maintenance cost is intentionally off the PR critical path and prevents repeated cold builds across unrelated pull requests.
