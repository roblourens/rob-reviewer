## Findings (1)

### 1. [medium] Coalesce plugin reloads across profile changes

**Finding ID:** `PERF-9EB0C7A9CA90`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3065</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Per-session plugins.reload IPC calls and the MCP server subprocess restarts they can trigger  
**Scaling:** For T profile enablement changes while S chats are live, the new path performs T×S session reloads, in addition to three root plugin RPCs per change. Reloads run in parallel across chats but serialize in each chat's queue, so a burst leaves S queues with T expensive reloads each.  
**Outcome:** Increased plugin-management latency, blocked chat queues, and repeated CPU/subprocess churn from restarting plugin MCP servers  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Profile enablement actions only wrote the local enablement model; they did not cross into the Agent Host or reload any live SDK sessions.  
**Changed behavior:** Each profile enable/disable now performs list, enable/disable, and verification RPCs, then awaits a queued plugins.reload for every live session. The management bridge starts mutations immediately, and the list UI disables only the clicked row, so changing several plugins can enqueue overlapping mutations without any shared reload coalescing.  
**Confidence:** 0.97 — The changed UI-to-Agent-Host call path, T×S call count, per-chat serialization, cross-chat parallelism, and MCP restart capability are all explicit in repository code. Exact reload duration and typical live-chat count are unmeasured, which limits severity but not mechanism confidence.

**Causal diff evidence:** The added RIGHT line 3065 introduces the all-live-session loop on every setPluginEnabled call; before this PR profile actions called enablementModel.setEnabled locally and had no reload loop.

Managing several plugins in the installed list, or overlapping automatic activation with another toggle, queues one full plugin reload per change in every open chat. Since reloadPlugins explicitly notes that it can restart MCP servers and uses the same per-chat queue as chat control work, settings actions and subsequent chat work wait behind repeated restarts.

**Evidence:** setPluginEnabled ends with Promise.all over \_allLiveSessions(), queuing reloadPluginEnablement for every session. \_allLiveSessions returns every live chat entry; \_queueChat serializes work only within one session, not across mutations; AgentHostManagementService.\_runMutation invokes each operation immediately. PluginListWidget disables only the selected toggle, allowing other rows to start additional changes. CopilotAgentSession.reloadPlugins calls the session plugins.reload RPC and documents that it can restart MCP servers.

**Suggested direction:** Coalesce pending profile mutations into a shared flush: apply the requested enable/disable updates, then schedule at most one queued reload per live session for the burst and have all callers await that shared reload/error result. Preserve workspace-only changes as local operations.
