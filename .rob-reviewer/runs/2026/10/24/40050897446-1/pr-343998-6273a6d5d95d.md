## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:3701` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:3695`  
**Introducing path:** `src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts`  
**Introducing commit:** `7d57b0daeff127033ba2e0ed31b9c54008f0bb1c`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `latency`  
**Confidence:** 0.96

**Mechanism:** A newly offered client-tool handler could park a DeferredPromise in PendingRequestRegistry during the asynchronous setTools boundary while routing still reflected only the old snapshot. Because the emitted start lacked a client contributor, no client response resolved it, blocking the tool invocation and turn indefinitely and retaining the pending entry until session cleanup.

**Symptom:** A client tool invoked in the narrow setTools acceptance window could hang the active agent turn indefinitely, with one pending deferred retained per affected invocation until the session ended.

**Fixed behavior:** The fix stages the union of applied/offered client names and the offered definitions before awaiting replaceTools, so an invocation started by the runtime during that boundary is attributed to the providing client and its pending handler receives a completion; rejection restores the prior routing.

**Evidence:** In the base revision, updateClientTools awaited configuration.replaceTools/session.setTools at line 3695 before updating \_clientToolNames and \_appliedSnapshot. The runtime can invoke a newly supplied Tool handler while setTools is still pending: the handler calls \_pendingClientToolCalls.register(toolCallId), while tool.execution\_start attribution uses \_clientToolNames and \_appliedSnapshot through \_getToolCallContributor/\_resolveClientToolOwner. With the old post-await state, the start had no client contributor, so no client completion was produced and the PendingRequestRegistry entry remained parked until session teardown. The changed test exercises exactly this ordering and awaits the handler before releasing the setTools gate.

### Scenario 2: A newly offered client tool starts executing before the SDK setTools response reaches the host

- Critical path: The runtime emits tool.execution\_start and invokes the supplied handler during the in-flight replacement. Correct attribution must synchronously route the start to the owning client; the handler then waits for the client's completion. Before this fix, missing staged routing left the PendingRequestRegistry promise unresolved until session teardown, blocking the tool call and active turn.
- Scaling input: Cost scales with actual tool invocations during the short replacement window, not with every definition. Ownership lookup scans the offered definition list and active clients once per such start; this replaces the prior applied-list scan and is bounded by configured tools/clients.
- Effective concurrency: The replacement itself is one per-chat serialized operation, but the runtime can overlap one or more model-issued tool invocations with it. Each invocation captures its contributor and has its own toolCallId/deferred; the diff does not add parallel SDK requests or remove backpressure.
- Cache behavior: There is no result cache for tool execution. The offered routing state exists only until setTools settles; success commits it, rejection restores the applied name set, and each invocation retains its captured contributor. Pending results are keyed by toolCallId and removed on response or session cleanup.
- Mechanism confidence: Very high: the handler registers a DeferredPromise, the client response is the only normal resolver, the old routing commit occurred after await, and the changed test completes the handler before releasing the setTools gate.
- Magnitude uncertainty: The race frequency and number of parallel model tool calls are workload-dependent, but the old indefinite wait and the fixed call path are directly demonstrated. The diff's additional lookup/temporary state is short-lived and bounded.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:replaceTools</code>: The in-flight session.setTools request causes the runtime to accept and potentially invoke the newly offered handler.; cardinality: One replacement IPC for the changed snapshot, regardless of how many tools are in the snapshot.
    - Introduced by diff: false; previous behavior: The runtime could already invoke an offered handler before setTools settled, but host routing still used only the applied snapshot.; critical-path effect: Its response is not required before the newly offered handler can start, which creates the race addressed by staged routing.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_getToolCallContributor / handleClientToolCallComplete</code>: Publish the attributed client-tool start to the owning client and receive its completion back into the pending registry.; cardinality: One start/completion round trip per actual client-tool invocation; ownership lookup is in-memory and no extra boundary call is made per candidate client.
    - Introduced by diff: false; previous behavior: Normal applied client tools used this round trip, but a newly offered tool in the setTools window was emitted without a client contributor, so no completion arrived and its deferred remained parked.; critical-path effect: The completion resolves the SDK handler and lets the active turn continue. The diff restores this existing round trip for invocations occurring during replacement.
- Verdict: No introduced performance regression. This PR fixes a concrete latency/cleanup regression by making the existing client completion path reachable during the SDK acceptance window; the fix was recorded with its blamed introducer.
