### Scenario 1: Render and refresh the Automations catalogue, then open a card's More Actions menu

- Critical path: The catalogue autorun synchronously groups all automations, updates persistent card DOM, computes the new cloud/event context keys, and returns; the menu later reads those scoped keys. No subprocess, IPC, filesystem, database, or network operation is on this changed path.
- Scaling input: The number of visible automation descriptors; each refresh visits each descriptor once, and the added event check scans that descriptor's small trigger-name record. Persistent cards avoid reconstruction on warm refreshes.
- Effective concurrency: Single synchronous renderer on the UI thread; no queued or parallel boundary work is introduced.
- Cache behavior: Cards and scoped context-key services are retained by automation ID and reused across refreshes. Context-key writes suppress change events when values are unchanged. There is no new positive or negative remote cache.
- Mechanism confidence: High confidence in the O(number of automations plus trigger names) path and in the absence of an expensive boundary; surrounding render and context-key implementations were inspected.
- Magnitude uncertainty: Very large catalogues could increase linear UI work, but the diff adds only two bounded boolean context updates and one small trigger-name scan per card; no evidence establishes meaningful latency or jank.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added action gating is bounded per card, reuses persistent cards, and does not introduce layout reads, allocation growth, or boundary fan-out.

- Effective concurrency: The dialog guards against concurrent saves, and GitHub mutations run through a provider-wide Sequencer. Cold target eligibility checks elsewhere are limited to five, but this save path remains serialized.
- Cache behavior: The GitHub API client is coalesced by clientPromise and reused warm.
