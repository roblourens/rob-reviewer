### Scenario 1: Send or synchronize a remote-agent chat message with selected-agent and resource attachments, including draft, queued, steering, and initial messages

- Critical path: The handler converts input variables and rebases attachment URIs, then EditorRemoteAgentHostTransport synchronously projects selected-agent/resource identities before the existing protocol send. Turn submission waits for this projection; draft publication is coalesced by a 500 ms per-session Delayer before reaching the same send path.
- Scaling input: A resource attachments in the message and D requested/workspace directories used for ownership/rebase checks; effective work is in-memory O(A\*D) in the existing attachment conversion/rebase path plus O(A) transport projection. Typical D is the workspace-root count, and one transport message is emitted per dispatched action, not per attachment.
- Effective concurrency: Turn/queue actions issue one dispatch each. Draft edits are last-value coalesced per session over 500 ms, so typing does not dispatch per keystroke. The diff adds no Promise.all, worker, subprocess, or per-attachment concurrency.
- Cache behavior: URI projection is deterministic and uncached; cold and warm behavior are the same. There is no negative-cache state or repeated remote lookup to coalesce.
- Mechanism confidence: High: the call path, 500 ms draft debounce, attachment loops, mapper implementation, and single transport send are explicit in the inspected code.
- Magnitude uncertainty: Attachment and multi-root counts vary, but the added mapper work is shallow URI parsing/transformation and object copying; no evidence shows counts or costs large enough to create input latency beyond the already more substantial attachment conversion and serialization.
- Expensive boundaries:
  - IPC/network at <code>src/vs/workbench/services/agentHost/common/editorRemoteAgentHostTransport.ts:send</code>: Send the JSON-RPC createChat or dispatchAction protocol message over the existing agent-host transport; cardinality: Exactly one existing transport send per create-chat/action after draft coalescing; attachments are grouped inside that message, so A attachments do not cause A boundary calls.
    - Introduced by diff: false; previous behavior: The same createChat/dispatchAction message crossed the transport once, but selected-agent and resource-attachment URI fields were not projected by this adapter.; critical-path effect: The single existing send is required for the host to receive the message; the new URI work executes synchronously immediately before it.
- Verdict: No reportable performance regression. The diff adds bounded in-memory identity projection without per-attachment boundary fan-out, and draft coalescing prevents per-keystroke repetition.

### Scenario 2: Initialize, subscribe, reconnect, or load older history for remote chat sessions

The diff now projects selected-agent URIs across loaded turns, active/draft/pending messages, and reconnect replay actions; history refresh then performs its existing full state-to-history conversion.
- Scaling input: N turns in the loaded snapshot/page or replay and P pending messages; added CPU/allocation is O(N+P), with one shallow turn/message copy per loaded turn. Work is bounded by the history already present in the protocol payload.
- Effective concurrency: Incoming protocol messages are delivered through the transport event path and mapped synchronously per message. The diff introduces no concurrent requests or burst; replay/snapshot arrays are traversed once.
- Cache behavior: Snapshots and replay actions are mapped when received and are not cached by this adapter. Cold initialize and reconnect perform the same per-payload mapping; steady-state streaming deltas do not remap the entire turn history.
- Mechanism confidence: High: all response/action branches and array traversals are explicit, and there are no transitive filesystem, subprocess, database, or additional network operations in the mapper.
- Magnitude uncertainty: Very long loaded histories increase shallow allocations, but the same payload is already deserialized and subsequently converted into full chat history. No repository evidence establishes that these added shallow copies materially affect hydration or reconnect latency.
- Expensive boundaries:
  - IPC/network at <code>src/vs/workbench/services/agentHost/common/editorRemoteAgentHostTransport.ts:\_fromHost</code>: Receive initialize, subscribe, reconnect, or fetch-history protocol data from the agent host; cardinality: One existing response per request, or one existing server action per loaded history page/replay batch; the diff does not add requests.

- Verdict: No high-confidence actionable regression. The new cost is a single linear pass required to project identities in already-loaded data, with no retained duplicate state or repeated full-history pass on streaming updates.

### Scenario 3: Request remote resource and skill completions while typing in chat input

- Critical path: Monaco invokes completion only while the cursor is inside a host-announced trigger token. One existing agent-host completions request must finish, then each returned item is synchronously converted; the diff wraps resource/skill URIs through the owning connection before suggestions are returned.
- Scaling input: R completion items returned by the host; added URI wrapping is O(R) only for resource and skill items, after effective result cardinality is established by the host.
- Effective concurrency: The completion provider uses Monaco cancellation and drops stale results after the await. The token is not forwarded across IPC, so underlying overlap is pre-existing; the diff neither adds requests nor changes concurrency.
- Cache behavior: No completion cache is used on this path; cold and warm requests both delegate to the host. The URI mapping is local and has no cache miss behavior.
- Mechanism confidence: High: the completion provider trigger guard, cancellation check, single connection call, and local result loop are explicit.
- Magnitude uncertainty: Host result sizes and request durations vary, but only small per-item serialization/allocation is added and there is no evidence of a realistically large result set making it material.
- Expensive boundaries:
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:provideChatInputCompletions</code>: Request completion items from the agent-host connection; cardinality: One existing host request per eligible Monaco completion invocation; returned R items are mapped locally with zero per-item boundary calls.
    - Introduced by diff: false; previous behavior: The same single completions request returned the same items, which were already iterated and converted; resource and skill URIs were parsed but not additionally wrapped through the owning connection.; critical-path effect: The existing request dominates the asynchronous critical path; URI wrapping runs after it and before suggestions render.
- Verdict: No reportable performance regression. The diff preserves one boundary call and adds only linear local projection to the existing result conversion loop.

### Scenario 4: Create a registered native-remote handler and rebase same-authority WSL/SSH attachments into a resolved worktree

- Critical path: Handler registration stores the editor remote authority. On turn construction, each attachment and requested/resolved directory is checked with in-memory resource mappers and authority comparison before the existing message dispatch.
- Scaling input: A attachments and D candidate working directories; effective cardinality remains one final chat action, with local ownership/rebase checks scaling with A and D rather than boundary calls.
- Effective concurrency: Attachment conversion is synchronous and sequential during one turn build. The final dispatch retains existing connection sequencing; no new parallelism or resource burst is introduced.
- Cache behavior: Ownership checks are uncached and deterministic. Cold/warm behavior is identical, and no filesystem existence lookup or remote-resolution cache is consulted.
- Mechanism confidence: High: mapper implementations are pure URI encode/decode operations, and all inspected rebase callers run during attachment conversion without I/O.
- Magnitude uncertainty: Large multi-root workspaces or unusually attachment-heavy prompts increase local comparisons, but typical root/attachment cardinalities are modest and no concrete latency mechanism beyond bounded CPU/allocation is established.
- Expensive boundaries:
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:\_rebaseAttachmentUri</code>: Dispatch the completed turn action to the agent host after all attachments have been rebased; cardinality: One existing message dispatch after all attachments are grouped; zero filesystem, database, subprocess, or per-attachment remote calls.
    - Introduced by diff: false; previous behavior: Attachment rebasing already ran during turn construction and the grouped action was dispatched once; the diff broadens local ownership normalization to connection-wrapped and same-authority native-remote URIs.; critical-path effect: Local URI checks precede the existing dispatch but do not add a boundary or await.
- Verdict: No reportable performance regression. The added native-remote ownership checks are pure local work and preserve grouped transport behavior.
