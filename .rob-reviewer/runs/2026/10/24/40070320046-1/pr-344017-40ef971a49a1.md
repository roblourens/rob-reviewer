<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, serialization-allocation, boundary-fanout, cleanup-lifecycle

### Scenario 1: A steering message is promoted while a HydraFusion phase and one or more provisional root tool calls are still running.

- Critical path: The SDK user.message event synchronously enters \_beginSteeringTurn, completes the old host turn, creates the successor, scans ownership/tool-call state, republishes the running phase and eligible root tool rows, then records the SDK turn. These steps must finish before the successor turn is fully projected to chat.
- Scaling input: Cost scales with the session-lifetime sizes of \_fusionEventTurnIds and \_hostTurnIdsBySdkTurnId, plus the effective number and total argument bytes of surfaced provisional root tool calls that are active or still publishing. Phase-chat tools, client tools, pending-permission tools, and task\_complete rows are filtered out.
- Effective concurrency: Transfer is a synchronous serialized loop. Each eligible root tool emits Start then Ready and optionally ContentChanged in order; there is no parallel boundary burst or limiter because emission is synchronous.
- Cache behavior: No cache lookup or remote cache is involved. Ownership maps are warm session state; Fusion progress and active tool records are reused. Tool presentation is recomputed rather than cached, including JSON serialization of parameters.
- Mechanism confidence: High confidence in the synchronous scans, replay cardinality, and duplicate parameter serialization from the traced call path; only their practical magnitude is uncertain.
- Magnitude uncertainty: Real sessions can have large edit/patch arguments and multiple tool calls, but the effective count of simultaneously eligible root provisional calls and measured steering delay are not established. Map scans and duplicate serialization are therefore bounded-looking in ordinary use and do not clear the actionable regression threshold without latency evidence.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_beginSteeringTurn and \_transferProvisionalFusionToolCalls</code>: Publish the resumed Fusion phase and replayed ChatToolCallStart/Ready/ContentChanged actions through the agent progress channel to chat clients.; cardinality: At most one resumed phase update, then two actions per eligible root tool plus one content action when the tracked tool has content; filtering occurs before emission.
    - Introduced by diff: true; previous behavior: The old turn was completed and Fusion state reset; no running phase or provisional tool rows were replayed to the successor.; critical-path effect: Synchronous action construction/emission is on steering promotion's immediate UI path.
  - serialization at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_transferProvisionalFusionToolCalls</code>: Reconstruct invocation text and serialize each replayed tool's parameters for toolInput.; cardinality: Once per eligible replayed root tool; getToolInputString serializes structured parameters and the changed call also eagerly computes a raw JSON string.
    - Introduced by diff: true; previous behavior: No presentation reconstruction occurred during steering handoff; serialization happened only when the original tool start was surfaced.; critical-path effect: CPU and temporary strings are allocated synchronously before each Ready action is emitted.
- Verdict: No finding. The new replay work is causally introduced, but it is required to project the handed-off workflow and is filtered to active surfaced root tools. The only clearly avoidable portion is an extra stringify, whose standalone user-visible impact is not sufficiently evidenced.

### Scenario 2: A steering handoff occurs after a provisional Fusion tool completed but while its edit/resource/terminal result is still being persisted.

- Critical path: The completion's filesystem/database/edit-tracker work was already started by tool.execution\_complete. The handoff moves the tracked completion to the successor turn and trackToolCompletion causes the successor's session.idle handler to drain it before ChatTurnComplete.
- Scaling input: Latency is the remaining duration of each effective unpublished completion handed over; drainToolCompletions waits for all tracked promises, while each completion may include file-edit capture, resource persistence, or bounded terminal-output persistence.
- Effective concurrency: The underlying completion promises may already execute concurrently. The idle path coalesces them with Promise.allSettled and waits as a group; it does not start duplicate persistence operations.
- Cache behavior: No result cache is introduced or bypassed. The session data database is opened per pre-existing completion path, and the new map only indexes promises until finally removes them.
- Mechanism confidence: High confidence that the successor now waits for the existing promise and that no duplicate filesystem/database operation is scheduled.
- Magnitude uncertainty: Slow storage could expose added tail latency when steering work finishes before persistence, but the diff starts no new I/O, the work normally overlaps the continuing workflow, and no duration/prevalence evidence shows a material regression.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:handleToolComplete completion pipeline</code>: Read bounded terminal output and capture completed file edits.; cardinality: Existing work per completed tool: zero or one bounded terminal-output read plus edit captures for that tool's affected file paths.
    - Introduced by diff: false; previous behavior: The old turn tracked the operation, but after steering reset the successor did not wait for it and its eventual UI completion was dropped.; critical-path effect: The diff can make already-running work part of the successor turn's completion critical path by tracking its promise; it does not add the read/edit operation.
  - database at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:handleToolComplete completion pipeline</code>: Persist SDK result resources or terminal output and clean up unpublished terminal output if necessary.; cardinality: Existing per qualifying completion; one database handle with resource/terminal stores and conditional cleanup.
    - Introduced by diff: false; previous behavior: Persistence already ran, but was not transferred to or awaited by the successor turn.; critical-path effect: Outstanding persistence must now settle before the successor turn can complete if the SDK reaches idle first.
- Verdict: No finding. Waiting preserves the required completion-before-turn-end ordering and reuses already-running promises; there is no duplicate boundary work or unbounded concurrency introduced.

### Scenario 3: A steering message is promoted in a non-Fusion turn or after no provisional Fusion tools are eligible for transfer.

- Critical path: The new continuesFusionWorkflow branch still starts a successor and scans both ownership maps plus active/unpublished tool maps before finishing promotion, but emits no transfer actions when no eligible Fusion state exists.
- Scaling input: Synchronous CPU scales with accumulated ownership-map history and current active/unpublished tool counts, even when the filter rejects every tool.
- Effective concurrency: All scans are synchronous and serial; no external calls are launched.
- Cache behavior: The maps are session-lifetime routing state rather than caches and are cleared on session disposal; there is no cold/warm cache distinction.
- Mechanism confidence: High confidence that the condition is not gated on an active Fusion phase and that the scans occur; low confidence that their cost is materially user-visible.
- Magnitude uncertainty: Map history is session-bounded but can grow with turns/events. No evidence establishes realistic cardinalities large enough for these simple scans to create visible steering latency.
- Expensive boundaries: none found
- Verdict: No finding because this is small in-memory iteration with no demonstrated costly payload or boundary fan-out on the non-Fusion path.

**Summary:** Completed the performance pass over all three changed files and all diff pages. Traced steering promotion, Fusion ownership transfer, provisional tool replay, delayed completion persistence, UI progress emission, and map cleanup. The PR introduces bounded synchronous replay and moves existing persistence waits onto the successor turn for ordering, but no high-confidence actionable performance regression meets the reporting threshold.
