- Scaling input: One explicitly selected connector; polling scales with authorization duration up to the fixed five-minute deadline, not catalog size beyond parsing the bounded catalog.
- Effective concurrency: Operations within one connect are serialized. Existing callers can initiate independent connector actions, but the diff adds no collection fan-out or new parallel scheduling.
- Cache behavior: Catalog GETs can revalidate through the GitHub client cache/ETag. The ordinary path reuses the current client; no new cache invalidation occurs.
- Mechanism confidence: High: the unchanged boundary calls, two-second cadence, five-minute deadline, and serial awaits are explicit in the service and tests.
- Magnitude uncertainty: Actual catalog and Agent Host round-trip durations vary, but the diff leaves their normal-path cardinality and placement unchanged.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts authorize/getAuthentication</code>: Resolve authentication sessions and, only if needed, create an authorized connector session; cardinality: At least one session lookup per connect attempt; session creation is only performed when no suitable connector-scoped session exists.

### Scenario 2: A same-account authentication-session change resets the catalog before the connection request has completed

- Critical path: The reset cancels the current catalog-bound operation. The changed loop reauthorizes, creates a fresh operation, and resumes; completion therefore waits for the replacement session lookup/client acquisition and catalog request before proceeding.
- Scaling input: The number of relevant same-account session changes during one explicit connect; retries are capped at three and remain tied to one connector.
- Effective concurrency: Replacement attempts are strictly serial because each loop iteration disposes its operation before the next begins. No burst is introduced within one connect.
- Cache behavior: resetCatalogContext clears the API client and catalog state, so each resumed attempt is cold and cannot reuse the prior ETag/client cache. The reset count bounds these cold misses; there is no negative cache involved.
- Mechanism confidence: High for one added cold lookup/GET per reset and serial bounded resumption; medium for duplicate completed PUT/consent work because dispatch completion relative to cancellation is inherently uncertain.
- Magnitude uncertainty: A reset during the initial catalog GET is demonstrated by tests. A reset precisely during the PUT is possible from the same cancellation wiring but its prevalence and server-side completion are uncertain.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts connect -&gt; authorize/getAuthentication</code>: Re-resolve authentication sessions on each resumed attempt; cardinality: One additional lookup per observed reset, capped at three resumed resets.
    - Introduced by diff: true; previous behavior: The first catalog reset canceled connect, so no replacement lookup occurred.; critical-path effect: Each lookup must complete before a replacement catalog operation starts.
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts requestConnection -&gt; refresh/query</code>: Refetch the full connector catalog using a newly acquired account client; cardinality: One replacement GET per reset before poll state exists, capped at three; the added test establishes two GETs for one pre-consent reset.
    - Introduced by diff: true; previous behavior: The reset canceled connect after the interrupted GET and did not continue.; critical-path effect: The replacement GET is required to determine whether the connector became connected and whether PUT is still needed.
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts requestConnection</code>: Request connector connection with PUT; cardinality: Normally one PUT after the replacement GET. If reset lands after dispatch but before the PUT result is committed to pollState, an uncertain mutation can be repeated, bounded to four total attempts.
    - Introduced by diff: true; previous behavior: An in-flight PUT interrupted by catalog reset was not retried by the service.; critical-path effect: A replacement or repeated PUT must complete before polling begins.
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts requestConnection</code>: Open the consent page returned by a completed PUT; cardinality: Normally once. In the narrow uncertain-PUT reset race it could repeat with the repeated request, bounded by the reset cap.
    - Introduced by diff: true; previous behavior: The reset canceled the action rather than reopening consent.; critical-path effect: Awaited before polling.
- Verdict: No reportable performance regression: the added work is bounded to three resets, is necessary to preserve progress after a real session change, and has no collection or lifetime scaling. The narrow uncertain-mutation race does not provide enough evidence of a significant performance outcome to justify a performance finding.

### Scenario 3: A same-account authentication-session change resets the catalog while consent polling is active

- Critical path: The canceled polling GET unwinds to the changed retry loop. Reauthorization and a fresh operation/client must complete, after which polling resumes with the existing state and original deadline; no new connection request or consent open is performed once pollState exists.
- Scaling input: Session-reset count during one connector's remaining authorization window; the deadline is preserved and resets are capped at three.
- Effective concurrency: Polling and reset recovery are serial. A reset cancels the old operation before the next iteration creates a replacement; no overlapping GET burst is scheduled by the changed loop.
- Cache behavior: Each reset clears the client/catalog cache, so resumed polling starts cold; subsequent GETs on that client can revalidate. pollState retains initial status, pending observation, and deadline, preventing a second PUT and preventing timeout extension.
- Mechanism confidence: High: the changed pollState lifetime and reset cap prove the bounded serial behavior, and the added test proves the one-reset request sequence.
- Magnitude uncertainty: The cost of reacquiring a client and authentication sessions varies, but cardinality and the absence of deadline extension are explicit.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts connect -&gt; authorize/getAuthentication</code>: Re-resolve the active account's authentication sessions; cardinality: One added lookup per reset, capped at three.
    - Introduced by diff: true; previous behavior: Polling ended with cancellation, so no resumed lookup occurred.; critical-path effect: Required before resumed polling can issue its next request.
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts pollConnection -&gt; refresh/query</code>: Resume catalog polling with GET requests; cardinality: One immediate replacement polling GET per reset, then the existing serial two-second cadence until the preserved deadline; at most three reset resumptions.
    - Introduced by diff: true; previous behavior: The reset canceled the polling action and no further GET was made by that connect call.; critical-path effect: The first authoritative connected/error state determines when the action completes.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts refreshAgentHostConnectorSessions</code>: Refresh Agent Host sessions if resumed polling observes changed connected membership; cardinality: Membership-based, normally once when connected state is first authoritatively observed; a reset overlapping reconciliation may cause another bounded reconciliation on the next authoritative refresh.
    - Introduced by diff: false; previous behavior: The boundary already existed, but the diff allows the action to reach it after a reset instead of terminating.; critical-path effect: Awaited inside refresh when membership changes.
- Verdict: No reportable regression: additional boundary work is bounded and directly implements successful continuation, while preserving the original overall polling window and avoiding repeated mutation after pollState is established.

### Scenario 4: The caller cancels, connectors are disabled/disposed, or the default account changes during connection

- Critical path: Cancellation or identity/lifecycle checks terminate the action rather than entering another retry iteration.
- Scaling input: One user action and one active request; no dependence on connector collection size.
- Effective concurrency: No replacement operation is created after these terminal conditions. Existing independent connector actions remain independently cancellable.
- Cache behavior: Account or enablement changes reset and clear catalog state as before; the changed catch explicitly refuses reuse/retry across account identity or disabled/disposed lifecycle.
- Mechanism confidence: High: every terminal condition is checked in the added catch, and account-switch behavior is covered by the added test.
- Magnitude uncertainty: None material to the performance verdict.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts connect/createOperation/withClient</code>: Abort any active catalog GET or connection PUT through the operation token/AbortSignal; cardinality: At most the currently active request per connect action.
    - Introduced by diff: false; previous behavior: These conditions canceled the active operation before the diff as well.; critical-path effect: Abortion causes immediate rejection; no resumed request is issued when caller cancellation, lifecycle shutdown, or account mismatch is detected.
- Verdict: No regression: terminal cancellation does not retain polling, issue replacement boundary calls, or extend resource lifetime.

**Summary:** Reviewed the complete two-file diff and traced connect callers, catalog-reset ownership, authentication/session lookup, GitHub client caching, network mutation and polling, Agent Host reconciliation, cancellation, tests, and concurrency. The PR adds bounded serial recovery work after same-account catalog resets, preserves the original five-minute deadline and polling state, and does not introduce a high-confidence actionable performance regression. No finding or regression-fix learning record was warranted.
