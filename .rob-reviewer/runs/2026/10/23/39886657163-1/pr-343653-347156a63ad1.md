<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, boundary-fanout, serialization-allocation, cleanup-lifecycle

### Scenario 1: An MCP tool call starts after its server has already raised an authentication request

- Critical path: The runtime emits tool.execution\_start; handleToolStart records the active call, emits ChatToolCallReady, scans local active-call and pending-auth collections, and synchronously emits ChatToolCallAuthRequired. The runtime's MCP execution remains blocked on the already-pending authentication independently of this added local state publication; no new remote operation must complete because of the diff.
- Scaling input: Effective cardinality is the number of concurrently active MCP tool calls for the same server and the number of pending authentication requests. Only the latest requirement is eligible, and each tool-call ID is attached/emitted once through the existing deduplication check. Tests and telemetry logic establish parallel rounds as a supported pattern, but no evidence indicates realistically large in-flight sets.
- Effective concurrency: JavaScript event callbacks execute serially. Logical parallel tool calls produce separate starts; the pending toolCalls list coalesces duplicate attachment by toolCallId, and authentication resolution remains shared by the pending request.
- Cache behavior: No remote cache lookup is added. Warm and cold behavior differ only in whether a matching pending requirement exists; without one, the added path performs local bounded scans and emits nothing. Matching attachments are retained only for the pending request and removed when the registry responds or is cancelled.
- Mechanism confidence: High: the changed call path, local scans, deduplication, cleanup, and single action emission are directly visible in the source; no added network, filesystem, subprocess, or database call is reached.
- Magnitude uncertainty: Exact production parallel-call distributions are unavailable, but the added action payload is small and local collection sizes are lifecycle-bounded by in-flight calls and pending requests.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_attachActiveMcpToolCallsToPendingAuthentication</code>: Publish ChatToolCallAuthRequired through the agent progress event toward the client; cardinality: One small action per newly attached MCP tool call; duplicate starts/reattachment are suppressed by toolCallId.
    - Introduced by diff: true; previous behavior: No auth-required action was published for a tool that started after the auth request, so this boundary event was absent for that call.; critical-path effect: Synchronous process-local emission occurs in the start handler; downstream publication updates UI/auth state but does not add an awaited boundary to MCP execution.
  - network at <code>Copilot runtime MCP tool execution associated with tool.execution\_start</code>: Execute the MCP tool against its configured server after authentication succeeds; cardinality: One remote execution per logical MCP tool call, subject to runtime behavior and shared authentication.
    - Introduced by diff: false; previous behavior: The same MCP tool execution and authentication wait existed; the diff only publishes the missing local auth-required state.; critical-path effect: The tool remains blocked on the pre-existing authentication requirement; this remote operation is the scenario's expensive execution boundary.
- Verdict: No reportable regression. The diff adds the required single state-transition publication and bounded local bookkeeping, without increasing remote boundary count or placing an await on the tool-start path.

### Scenario 2: A cached MCP routing proxy activates a server while authentication is pending

- Critical path: Activation is coalesced by server, refreshes MCP inventory, adopts matching pending authentication and waits for its completion, refreshes inventory again, then waits for Ready. The helper extraction preserves the previous adoption and wait behavior.
- Scaling input: Effective cardinality is one activation promise per server plus pending auth requests for that server. Callers for the same server share \_mcpRoutingActivations; the changed helper returns the same matching completion promises as before.
- Effective concurrency: Concurrent activation requests for one server coalesce to one promise. Server lifecycle work remains serialized by existing mechanisms; the diff does not widen concurrency.
- Cache behavior: Warm activation callers reuse the in-flight per-server activation promise. Routing cache refresh and MCP inventory behavior are unchanged; authentication completion is shared rather than repeated per caller.
- Mechanism confidence: High: the before/after helper logic returns the same filtered pending completion set, and the existing per-server activation map explicitly coalesces callers.
- Magnitude uncertainty: RPC duration and server count vary by environment, but their count and placement are unchanged by this PR.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_refreshMcpServersFromRpc</code>: Call SDK MCP listConfigured during inventory refresh; cardinality: Two inventory refresh phases per activation in this path, with lifecycle-version retries possible; unchanged by the diff.
    - Introduced by diff: false; previous behavior: The same pre- and post-authentication inventory RPCs were performed before the helper extraction.; critical-path effect: Both refreshes are awaited before routing activation completes.
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_refreshMcpServersFromRpc / \_doActivateMcpRoutingServer</code>: Refresh user MCP server state as part of the inventory refresh and eventually execute routed MCP work; cardinality: Grouped with each inventory refresh and one routed tool activation; no changed call count.
    - Introduced by diff: false; previous behavior: The same refresh and routed execution boundaries were already on this path.; critical-path effect: Existing remote work remains on the activation critical path.
- Verdict: No reportable regression. The refactor preserves pending-auth adoption semantics, cache/coalescing behavior, effective concurrency, and expensive-boundary cardinality.

The PR adds bounded local bookkeeping and one deduplicated progress action per affected call, with no new remote operation or material critical-path cost; no findings submitted.
