<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work

### Scenario 1: Pet throw lands naturally after pointer or keyboard interaction

- Critical path: The requestAnimationFrame throw loop writes left/top/transform, detects a landing, then \_finishThrow clears transform and synchronously reads the pet bounds before removing the throwing class; \_completeFall then performs the pre-existing landing geometry read and position/state updates. The added flush is on the landing frame's critical path.
- Scaling input: One added geometry read per completed throw, independent of platform count; throws are user-driven and one throw animation is active per widget.
- Effective concurrency: A MutableDisposable owns the active throw animation and replacement/cancellation clears it, so effective concurrency is one throw completion per widget rather than per frame or per platform.
- Cache behavior: No cache participates. Cold and warm behavior are identical; geometry is read directly from the live DOM once at completion.
- Mechanism confidence: High confidence that the diff adds a synchronous DOM geometry read after style mutation; high confidence that it is bounded to throw completion rather than the per-frame loop.
- Magnitude uncertainty: The geometry read can force pending style/layout work after animation-frame writes, and the overlay has no explicit CSS containment, but it occurs only once per user-driven landing and the browser was already about to perform pre-existing landing geometry reads/rendering. No realistic high-frequency or collection-scaling trigger is established.
- Expensive boundaries: none found
- Verdict: No reportable regression. The synchronous flush is intentional to commit the transform reset before transitions resume, is bounded to one per landing, and does not establish realistic sustained jank or scaling work.

### Scenario 2: An active throw is interrupted by reduced-motion enablement or pet disablement

- Critical path: The reduced-motion autorun and disable paths call \_finishThrow synchronously; the added bounds read runs before either completing the fall or returning from the disabled path.
- Scaling input: At most one added geometry read for the single active throw when the setting/visibility state changes.
- Effective concurrency: State changes run synchronously and \_finishThrow guards on the throwing class; repeated calls after the first return without work.
- Cache behavior: No cache or coalescing layer is involved; the throwing-class guard effectively deduplicates completion.
- Mechanism confidence: High confidence in the call paths and single-execution guard; the actual flush duration depends on browser/layout state.
- Magnitude uncertainty: A disable during an active throw newly incurs a geometry flush even when \_finishThrow returns immediately afterward, but this requires the narrow overlap of a user/configuration state change with one active animation and has no realistic multiplicity.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added synchronous UI work is one bounded operation under an infrequent interruption and does not meet the impact threshold.

**Summary:** Reviewed the complete two-file diff and traced all production callers of \_finishThrow, CSS transition behavior, layout reads, cancellation ownership, and landing paths. The only changed production mechanism is a deliberate one-time synchronous geometry read at throw completion; it is not in the per-frame loop, has no boundary fan-out, cache/lifecycle growth, or concurrency burst, and lacks a realistic performance-impact trigger. The test-only additions do not affect product runtime.
