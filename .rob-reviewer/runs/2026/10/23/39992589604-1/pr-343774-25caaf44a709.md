**Relevant issue families:** synchronous-ui-work, repeated-work, cleanup-lifecycle, serialization-allocation

### Scenario 1: A custom session group is being renamed while a sessions-list refresh or model update rerenders the row.

- Critical path: The existing synchronous list update rebuilds tree children, rerenders the visible group template, clears its element disposables, captures the old input selection/focus, creates one replacement InputBox, and restores its draft and selection. Only the visible editing group participates in the changed work; sticky scrolling can add one second rendered copy.
- Scaling input: List reconstruction still scales with the existing sessions/groups collection, but the diff-specific work scales with rerender count and the effective cardinality of the active editor: one group, or at most its normal row plus sticky-header copy. Each input event also copies the current short group-name string into the single state object.
- Effective concurrency: All changed DOM work is synchronous on the UI thread. Scheduled list updates are already coalesced to the next animation frame; explicit refresh remains immediate. There is no new parallelism, queue, subprocess, or burst.
- Cache behavior: The first render initializes a single in-memory draft from the saved group name; warm rerenders reuse it. Selection and focus are captured during deterministic template cleanup. The state is cleared on commit, cancel, or a non-editing render of that group, so retention is bounded to one draft for the renderer.
- Mechanism confidence: High: the renderer call path and one-object lifecycle are explicit in the changed helper and SessionGroupRenderer; no changed boundary call is reachable from rerendering.
- Magnitude uncertainty: Refresh prevalence varies with session activity, but the changed per-refresh work is a bounded set of DOM property reads/writes and one InputBox lifecycle that already existed before the diff.
- Expensive boundaries: none found
- Verdict: No reportable regression. Before the diff every rerender already disposed and recreated/focused/selected the group InputBox. The diff adds only bounded draft/selection/focus bookkeeping and one lightweight input listener, without increasing editor cardinality or introducing layout, IPC, storage, filesystem, database, network, or subprocess work.

### Scenario 2: The user commits, cancels, or restarts a custom-group rename after one or more rerenders.

- Critical path: Commit clears the draft state, invokes the existing commitGroupEdit path, optionally renames the group, and updates the list; cancel clears state and updates the list. Restart initializes from the authoritative saved group name after the prior state was cleared.
- Scaling input: The commit-side serialization scales with the existing number of groups and memberships, once per changed non-empty committed name. Rerender count and keystroke count do not multiply commits or storage writes. Cancel and restart add no boundary call.
- Effective concurrency: The commit and profile-storage path is synchronous and singular. The diff adds no concurrency, retry, fan-out, or missing coalescing.
- Cache behavior: Draft state is deliberately invalidated on commit/cancel and a subsequent rename starts cold from the saved name. There is no collection cache, negative-cache state, or unbounded key retention.
- Mechanism confidence: High: commit/cancel callbacks, state clearing, renameGroup, and save are directly traced; before/after boundary cardinality is unchanged.
- Magnitude uncertainty: The serialized state can grow with a large sessions/groups profile, but this PR neither changes its size materially nor changes persistence frequency.
- Expensive boundaries:
  - serialization at <code>src/vs/sessions/services/sessions/browser/sessionGroupsService.ts:955-971, SessionGroupsService.save</code>: Serialize the complete existing session-group state with JSON.stringify during rename persistence.; cardinality: At most once for a commit that changes a non-empty group name; zero for rerenders, cancellation, and unchanged names.
    - Introduced by diff: false; previous behavior: The same commit callback called renameGroup and serialized the same state once before this diff.; critical-path effect: Runs synchronously on the rename-commit path, not while preserving a draft across rerenders.
  - other at <code>src/vs/sessions/services/sessions/browser/sessionGroupsService.ts:971, SessionGroupsService.save</code>: Store serialized session-group state through the profile-scoped storage service.; cardinality: One storage-service call per effective rename commit; no call per keystroke or rerender.
    - Introduced by diff: false; previous behavior: The same profile-storage store occurred once on an effective group rename before the diff.; critical-path effect: Part of the existing synchronous commit path only.
- Verdict: No reportable regression. The new draft state does not defer, duplicate, or fan out commits, and both serialization and storage boundaries retain their prior one-per-effective-rename behavior.

### Scenario 3: An existing session or chat inline rename editor is rendered or rerendered through the extracted helper.

- Critical path: The session/chat renderers call the extracted helper, which performs the same container clear, InputBox construction, state restore, input listener, focus/selection behavior, and disposal work that was previously inline before installing the unchanged finish listeners.
- Scaling input: Effective changed cardinality is one active session or chat rename editor per renderer state, per rerender. The helper extraction does not add work per non-editing row or increase collection-wide processing.
- Effective concurrency: Synchronous UI-thread DOM work only; no new scheduling or concurrency behavior.
- Cache behavior: Existing per-item draft state remains the cache, with the same value, selection, focus, and lifecycle semantics. No cache key or invalidation behavior changed.
- Mechanism confidence: High: the deleted inline operations and added helper call have a direct one-for-one correspondence, including the existing input listener.
- Magnitude uncertainty: Exact rerender frequency depends on list activity, but the helper preserves the previous operation count and placement.
- Expensive boundaries: none found
- Verdict: No reportable regression. This is a mechanical extraction for session/chat rename rendering and does not add expensive work, boundary calls, retained state, or hotter-path execution.
