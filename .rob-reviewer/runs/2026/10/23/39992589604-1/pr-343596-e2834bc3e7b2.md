## Findings (1)

### 1. [medium] Coalesce plugin inventory reads across customization updates

**Finding ID:** `PERF-9A8B8698DC0A`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationMarketplaceInstallProvider.ts:290</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** SDK subprocess RPC calls and serialized plugin inventory objects  
**Scaling:** For E session customization updates (including MCP server state transitions and subscription snapshots), this adds E global plugins.list RPCs; because refreshProviderInstallations only increments a version and does not cancel or coalesce prior work, a burst can leave up to E reads in flight concurrently.  
**Outcome:** Excess IPC/subprocess work and delayed marketplace installed-state refreshes, with CPU/serialization pressure during MCP state-update bursts.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** getPluginInstallations synchronously read the already-published IAgentPluginService observable, so customization-driven provider refreshes did not cross the SDK plugins.list boundary before loading receipt inventory.  
**Changed behavior:** Every getInstallations refresh now awaits getPluginInstallations, which crosses the renderer/agent-host bridge and calls client.rpc.plugins.list(), before it starts the existing listCustomizationInstallations request.  
**Confidence:** 0.96 — The added await, complete call path to client.rpc.plugins.list(), broad event sources, and absence of request cancellation/coalescing are explicit in code. Exact event burst size and SDK list duration vary by session, which affects severity but not the mechanism.

**Causal diff evidence:** RIGHT line 290 changes the plugin portion of every provider refresh from a synchronous local observable read to an awaited host/SDK inventory request, placing one new plugins.list boundary call on each broad customization-update path.

After the customization install service has been activated for a Copilot session, each SessionMcpServerStateChanged/session subscription update triggers another provider refresh. Rapid MCP startup/authentication transitions therefore issue overlapping global plugin inventory RPCs, and the latest installed-state update also waits for this new RPC before the existing receipt inventory request can begin.

**Evidence:** AgentHostCustomizationMarketplaceInstallProvider.onDidChange includes agentHostCustomizationService.onDidChangeCustomizations; WorkbenchAgentHostCustomizationService fires that event for SessionMcpServerStateChanged and every subscribed session-state change. CustomizationMarketplaceInstallService responds by calling refreshProviderInstallations, whose refreshVersion rejects stale responses but neither cancels nor reuses their requests. The changed await at line 290 reaches CopilotAgent.listPluginInstallations -&gt; \_retryAfterClosedConnection -&gt; client.rpc.plugins.list(), then only afterward invokes listCustomizationInstallations.

**Suggested direction:** Cache/coalesce the global plugin inventory independently of broad customization state events (invalidate it on host start and plugin mutations, with a bounded refresh path for external changes), and share any in-flight read. Also start the independent plugin and receipt inventory requests together so the plugin RPC does not add a serial round trip to the installed-state critical path.

- Critical path: CustomizationMarketplaceInstallService binds the provider or receives provider.onDidChange, calls getInstallations, and cannot publish the authoritative provider snapshot until the new plugin inventory read completes and the existing receipt inventory read subsequently completes.

- Effective concurrency: Each event starts a refresh immediately. refreshVersion discards stale responses but does not cancel/coalesce their work, so up to E plugin inventory reads can overlap during an event burst; SDK client startup is coalesced, but plugins.list calls are not.
- Cache behavior: Plugin installation inventory has no positive, negative, or in-flight cache: cold and warm refreshes both call plugins.list. Session receipt inventory is cached only as an error fallback and still performs its authoritative read on each refresh.
- Mechanism confidence: High: event sources, lack of cancellation/coalescing, sequential await placement, and the SDK RPC call path are explicit.
- Magnitude uncertainty: Exact MCP event burst size, SDK RPC duration, and installed plugin count vary by session; this lowers severity but does not affect the proven uncoalesced one-call-per-event mechanism.
