# Performance review: Add proposed GitHub API for profile gist sharing

[PR #343432](https://github.com/microsoft/vscode/pull/343432) at `3e45356fcccc8818d1b6c60aae84a481fd43f749`

## Findings (1)

### 1. [low] Reuse the authenticated client across profile exports

**Finding ID:** `PERF-42A18419DFB8`  
**Location:** <code>extensions/configuration-editing/src/importExportProfiles.ts:25</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** authentication-provider session enumerations and extension-host/shared-process IPC calls  
**Scaling:** The added session selection and client acquisition run once for every profile export; total control-plane work and remote round trips grow linearly with repeated exports instead of being paid once per handler lifetime.  
**Outcome:** increased latency on the profile-export critical path, particularly in remote windows  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The deleted \`\_octokit\` promise cached both \`authentication.getSession(...)\` and the authenticated Octokit instance, so after the first export each later export went directly to the single Gist POST.  
**Changed behavior:** Each \`saveProfile\` invocation now calls \`authentication.getSession\`, acquires a fresh proposed-API client, performs the POST, and immediately disposes the client. The acquisition path then resolves the same session again in \`MainThreadGitHub.\_resolveSession\` and again in \`WorkbenchGitHubCredentialProvider.resolveClient\` before acquiring the shared-process lease.  
**Confidence:** 0.96 — The before/after cache removal and all three session-resolution call paths are explicit in the diff and repository code, and the export awaits them serially. Exact milliseconds vary with extension-host placement and authentication-provider latency, which is why severity is low rather than suppressing the finding.

**Causal diff evidence:** RIGHT line 25 places \`authentication.getSession(...)\` inside every \`saveProfile\` call, followed by the newly added per-call \`github.getClient(...)\` and \`client.dispose()\`; the same diff deletes the prior handler-level \`\_octokit\` promise cache.

After the first export, every additional profile export now waits for three session-resolution passes plus client lease acquisition/release before its one Gist POST; on a remote workspace these add multiple networked RPC round trips to an otherwise user-initiated serial critical path.

**Evidence:** \`saveProfile\` is awaited directly by \`UserDataProfileImportExportService.doExportProfile\`, so all acquisition work blocks export completion. \`MainThreadGitHub.$getClient\` calls \`\_resolveSession\`, which invokes \`IAuthenticationService.getSessions\`; \`WorkbenchGitHubService.acquireAccountApiClient\` then calls \`WorkbenchGitHubCredentialProvider.resolveClient\`, whose \`getSession\` invokes \`IAuthenticationService.getSessions\` again. That service delegates to the authentication provider rather than caching. Configuration Editing has \`main\` and \`browser\` entries but no \`extensionKind\`, which is classified as a workspace extension on desktop, so these newly repeated API calls traverse the remote extension-host bridge in remote workspaces.

**Suggested direction:** Keep a handler-lifetime promise for the authenticated \`GitHubClient\`, as the old implementation did, and dispose it with the handler registration. Clear/reacquire it when the client reports authentication or disposal invalidation; continue passing each operation's cancellation token only to the Gist request.

### Scenario 2: Import a profile from a GitHub Gist link or Gist identifier

- Critical path: The workbench activates the profile handler, invokes it in the extension host, acquires an anonymous GitHub client, performs one Gist GET, transfers the projected Gist DTO, selects the first usable file, and returns that content for JSON parsing and profile application.
- Scaling input: One Gist per import. The response can contain multiple files and is bounded by the GitHub transport's 16 MiB response cap; DTO mapping and IPC serialization scale with total returned inline file content, while only the first file is consumed by this handler.
- Effective concurrency: Client acquisition, GET, DTO conversion, and handler return are serial. The shared transport may coalesce/cache compatible GETs, but one import does not create concurrent fan-out.
- Cache behavior: Before the PR, the anonymous Octokit object was cached but each import still performed a Gist GET. After the PR, anonymous client acquisition/release repeats per import; the shared transport can retain a warm REST response independently of the short-lived lease. Failures are not negatively cached by the handler.
- Mechanism confidence: High for the added DTO/IPC route and per-read acquisition; lower for material user impact at normal profile sizes.
- Magnitude uncertainty: Large multi-file Gists amplify the new IPC copies, especially with a remote extension host, but ordinary profile Gists contain one comparatively small text file and the transport rejects responses over 16 MiB.
- Expensive boundaries:

  - IPC at <code>extensions/configuration-editing/src/importExportProfiles.ts:48; src/vs/workbench/api/browser/mainThreadGitHub.ts::$getAnonymousClient</code>: Acquire/release an anonymous client through the main thread and desktop shared process.; cardinality: One acquisition and release per attempted handler read after the PR.
