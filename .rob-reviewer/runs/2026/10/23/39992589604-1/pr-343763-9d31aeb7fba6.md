## Findings (1)

### 1. [medium] Limit rerun revalidation to core and checks

**Finding ID:** `PERF-DE6F194D6C9B`  
**Location:** <code>src/vs/platform/agentHost/node/artifactIntegrations/githubPullRequestArtifactIntegration.ts:634</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub GraphQL/REST requests and response bytes for pull-request core, review threads, checks, mergeability, job, run, and rerun operations.  
**Scaling:** Every rerun click adds four pull-request fragment fetches before three Actions API requests; review-thread work grows by pages of 100 threads and additional comment pages, and repeated/concurrent clicks repeat or restart authoritative reads.  
**Outcome:** Increased action latency and excessive network I/O on the critical path.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no per-check row action placing a whole authoritative PR refresh on this interaction path; existing details observation relied on the polling subscription rather than a user click forcing all fragments.  
**Changed behavior:** Each new Rerun Check row action now performs an authoritative whole-pull-request refresh, then performs getJob, getRun, and rerunJob. The whole refresh includes review-thread and mergeability reads that are not used by rerun validation.  
**Confidence:** 0.99 — The added call, resource interests, and refresh implementation establish the exact synchronous call path and fragment set. The only magnitude uncertainty is GitHub/network latency and how many pages a particular PR's review threads require; the unrelated calls and critical-path wait occur on every rerun click.

**Causal diff evidence:** The added RIGHT line \`const snapshot = await this.resource.refresh(token);\` in \`rerunCheck\` invokes the resource-wide refresh before any job validation. \`GitHubPullRequestArtifactResource.refresh\` calls \`subscription.refresh(undefined, ..., { authoritative: true })\`; the subscription's effective interests are core, reviewThreads (with bodies), checks (including optional), and mergeability, and \`refreshSubscription\` fetches core then awaits all other effective fragments.

Clicking Rerun Check is delayed by unrelated GitHub reads and consumes extra API/rate-limit capacity; on PRs with large review histories, pagination can make a simple job rerun noticeably slow. Rapid reruns on different rows can further cancel/restart authoritative fragment reads.

**Evidence:** \`rerunCheck\` awaits \`resource.refresh\` before deriving \`headSha\` and the check. The unchanged refresh implementation passes no fragment, so \`PullRequestResourceService.refreshSubscription\` fetches core and then \`Promise.all\`s every effective fragment. This binding subscribes to reviewThreads with bodies, all checks, and mergeability. Review threads are fetched 100 per GraphQL page (and comments can paginate), so a large review history adds multiple unrelated network requests and the action waits for their completion before its three Actions API calls.

**Suggested direction:** Refresh only the authoritative data required for this mutation—core followed by checks—then keep the existing getJob/getRun/rerunJob validation. Expose a fragment-scoped resource refresh (or equivalent sequential core/check refresh) so reviewThreads and mergeability remain off this critical path; coalesce concurrent core/check refreshes if multiple rows are invoked.
