# Performance review: automations: refine cloud repository ownership UX

## Findings (1)

### 1. [high] Reuse search privacy instead of refetching every repository

**Finding ID:** `PERF-EAB503AFF612`  
**Location:** <code>src/vs/sessions/contrib/providers/copilotChatSessions/browser/cloudAutomationStore.ts:193</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub repository metadata network calls and their response bytes.  
**Scaling:** The added request count grows linearly with cold search results (up to 100 per search); execution is capped at five candidates, but batches are awaited sequentially and each private candidate chains metadata then capability requests.  
**Outcome:** Increased repository-picker latency and excessive network I/O/API usage on cold searches.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each cold search candidate incurred only the automation capability request, in bounded groups of five. Privacy was already present in the search response but was not separately re-fetched.  
**Changed behavior:** Repository search now performs a repository-metadata network read for every candidate and, for private repositories, then performs the prior automation-capability read serially.  
**Confidence:** 0.99 — The call path and cardinality are explicit: \`GitHubRepositoryFetcher.getRepositories\` requests up to 100 results and maps \`repository.private\` to \`IGitHubRepository.isPrivate\`; this loop discards that field and calls \`isRepositorySelectable\`; that method awaits \`repositories.get\` before \`automations.getConfiguration\`. The updated test itself observes five metadata requests before the first batch is released. Cache hits can remove repeat work, but a cold search is definitively affected.

**Causal diff evidence:** At RIGHT line 193, the search loop changed from \`store.isRepositoryManageable(...)\` to \`store.isRepositorySelectable(...)\`. The latter newly calls \`client.repositories.get(repository, signal)\` before the existing \`client.automations.getConfiguration(...)\`, even though each \`repository\` returned by \`getRepositories\` already has \`isPrivate\`.

Opening or typing in Add Repository can make up to 100 unnecessary GitHub metadata requests and force each private-repository batch through two serial network round trips, delaying repository results and consuming API quota.

**Evidence:** \`IGitHubRepository\` includes \`isPrivate\`, populated directly by \`GitHubRepositoryFetcher.toGitHubRepository\`. \`getRepositories\` asks GitHub for up to 100 results. The changed loop processes groups of five and awaits each whole group before starting the next. \`isRepositorySelectable\` issues \`client.repositories.get\` for every cold key, then issues \`getConfiguration\` for private keys. \`cloudAutomationStore.test.ts\` now expects \`metadataRequestsBeforeRelease: 5\`, directly proving the added per-candidate boundary calls.

**Suggested direction:** Filter public results using \`repository.isPrivate\` before batching, then retain the existing manageability check for private candidates (or pass/seed the known privacy into the store). This preserves privacy filtering and cache semantics without a second metadata request per result.
