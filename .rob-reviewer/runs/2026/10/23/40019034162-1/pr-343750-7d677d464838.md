# Performance review: Honor custom agent model and reasoning-effort pins across harnesses

[PR #343750](https://github.com/microsoft/vscode/pull/343750) at `7d677d464838f070138cf31d2182a9f2cb19f773`

## Findings (2)

### 1. [medium] Reuse the fetched custom-agent list before delegation

**Finding ID:** `PERF-14BBEDFFFDEE`  
**Location:** <code>extensions/copilot/src/extension/chatSessions/vscode-node/copilotCloudSessionsProvider.ts:2749</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** One authenticated HTTP GET and response parse for the repository's full custom-agent list per qualifying delegation.  
**Scaling:** The extra request repeats once for every cloud task submitted with a non-default custom agent and non-default model, regardless of the warm provider-options cache.  
**Outcome:** Cloud task creation is delayed by an additional network round trip and service latency.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The same submission proceeded from existing validation directly to createSession; provider option discovery had already fetched the repository's custom-agent list and cached the resulting options for 15 minutes, but submission did not perform another list request.  
**Changed behavior:** When both a custom agent and picker model are selected, invokeRemoteAgent now awaits getCustomAgents before it can call createSession.  
**Confidence:** 0.99 — The changed line, endpoint implementation, existing options fetch/cache, and serial call order are all directly traced. Only the exact RTT varies by network and service conditions.

**Causal diff evidence:** The added \`await this.\_octoKitService.getCustomAgents(...)\` at line 2749 introduces the HTTP request on the delegation critical path; the base code called \`\_backend.createSession\` without this lookup.

After choosing a custom agent and explicit model, pressing Delegate now waits for a second custom-agent-list request before the create-session request starts; on a slow or high-latency connection this directly increases task-submission latency.

**Evidence:** getCustomAgents is implemented as an authenticated CAPI GET with no service-level cache. provideChatSessionProviderOptions already calls the same endpoint and caches its result for 15 minutes, but only the projected option objects are retained. The added await at line 2749 is serially between checkCCAEnabled and \_backend.createSession, so even a warm options picker cannot avoid this duplicate network boundary.

**Suggested direction:** Retain/coalesce the fetched CustomAgentListItem data per repository alongside the existing options cache and consult that here, falling back to one shared in-flight fetch only when no cached list exists.

### 2. [low] Cache or bound the per-agent frontmatter reads

**Finding ID:** `PERF-F7627FEFB2F7`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:597</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Filesystem reads, file buffers, string conversion, and YAML/frontmatter parsing for all discovered agent files.  
**Scaling:** A refresh performs N added reads for N workspace/user agents, strictly one after another because the await is inside the loop. The per-directory entry runs initially and after any watched customization change, and no pin cache skips unchanged agents.  
**Outcome:** Initial custom-agent availability and watcher-triggered picker refreshes incur additive I/O latency that grows linearly with the number of agents.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After the single SDK agents.discover call, the loop projected each agent from returned metadata without any per-agent filesystem operation.  
**Changed behavior:** discoverAgents now awaits a full IFileService read and frontmatter parse for every non-plugin, non-builtin discovered agent before publishing customization results.  
**Confidence:** 0.98 — The initial/refresh call path, per-agent cardinality, absent cache, and serial await are explicit in the code. Magnitude depends on agent count and filesystem latency, so severity is low.

**Causal diff evidence:** The added \`const pins = await this.\_readAgentFileModelPins(uri)\` at line 597 places one new filesystem boundary per discovered agent in the serial projection loop.

In multi-root or centrally provisioned setups with many custom agents, opening the agent-host experience or editing any watched customization delays the refreshed agent list by the sum of all agent-file reads, even when only one file changed.

**Evidence:** SessionDiscoveredEntry awaits discovery on construction and on 100 ms-debounced watcher refreshes. SessionCustomizationDiscovery invalidates and rediscovers on watched file changes. In the changed loop, each \`\_readAgentFileModelPins\` awaits \`IFileService.readFile\`, and the next agent is not processed until it completes; there is no URI/etag pin cache.

**Suggested direction:** Cache parsed pins by agent URI/etag and invalidate them from the existing file-change watcher; for cold misses, use a small shared concurrency limit so result ordering is preserved without serializing all reads.
