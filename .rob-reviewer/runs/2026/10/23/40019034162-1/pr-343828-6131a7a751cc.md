# Performance review: agentHost: separate PR polling from unchanged repair cooldowns

[PR #343828](https://github.com/microsoft/vscode/pull/343828) at `6131a7a751cc27a5ff7c2ba53c3a5ab84743a046`

## Findings (2)

### 1. [medium] Avoid re-evaluating the snapshot just refreshed

**Finding ID:** `PERF-2B3F806EA522`  
**Location:** <code>src/vs/platform/agentHost/node/agentMergeController.ts:1024</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Git subprocess launches and branch-read filesystem work  
**Scaling:** The redundant work grows linearly with enabled folder count and monitoring lifetime: approximately one extra Git process per folder per minute.  
**Outcome:** avoidable background subprocess, CPU, and filesystem overhead  
**PR causality:** <code>introduced</code>  
**Previous behavior:** There was no per-minute authoritative refresh in the backstop evaluation, so the controller did not manufacture this extra snapshot-triggered evaluation every minute; evaluations were driven by independent resource updates and the much slower prior backstop.  
**Changed behavior:** Every new 60-second backstop refresh self-schedules a second full controller evaluation after the 30-second snapshot debounce.  
**Confidence:** 0.99 — The timer path, observable write path, and repeated call path are direct: backstop -&gt; \`\_evaluate(refresh=true)\` -&gt; authoritative refresh -&gt; snapshot autorun -&gt; evaluation scheduler -&gt; \`\_evaluate(refresh=false)\`. Every evaluation reaches \`\_readCurrentBranch\` for a bound target, and the concrete Git service implements that as \`git branch --show-current\`. Magnitude varies with the number and lifetime of enabled folders.

**Causal diff evidence:** The added authoritative refresh at line 1024 publishes loading/ready snapshot changes. The existing subscription autorun schedules \`runtime.evaluationScheduler\` on every such change, so the poll evaluation queues another evaluation 30 seconds later even though the current evaluation already awaits the refresh and evaluates that same final snapshot.

A long-lived Agent Merge folder now incurs an avoidable Git subprocess about once per poll in addition to the poll evaluation itself (roughly 60 redundant process launches per hour per enabled folder), causing background CPU/disk wakeups and process churn; multi-folder sessions multiply the cost.

**Evidence:** \`AgentMergeRuntime.backstopScheduler\` now runs every 60 seconds with \`refresh=true\`. \`subscription.refresh\` updates the observed snapshot, whose autorun unconditionally calls \`runtime.evaluationScheduler.schedule()\`. The current evaluation then proceeds using the refreshed snapshot, but the scheduled evaluation repeats branch validation; \`\_readCurrentBranch\` calls \`AgentHostGitService.getCurrentBranchName\`, which spawns \`git branch --show-current\` via \`execFile\`.

**Suggested direction:** Suppress or consume snapshot notifications produced by the refresh currently being awaited (for example, track the refresh generation and cancel only its queued debounce once that snapshot has been processed), while preserving evaluations for genuinely external snapshot changes.

### 2. [medium] Coalesce polling across bindings of the same pull request

**Finding ID:** `PERF-48AC0B13CFB3`  
**Location:** <code>src/vs/platform/agentHost/node/artifactIntegrations/githubPullRequestArtifactIntegration.ts:897</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub REST/GraphQL requests for core, review threads, checks, mergeability, and paginated thread data  
**Scaling:** For B enabled bindings of one pooled PR, the new path requests roughly B full refreshes per minute, each spanning at least four fragment fetches; cost can grow further with review-thread pagination.  
**Outcome:** excessive network I/O, request-queue latency, and avoidable rate-limit consumption  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The pooled pull-request resource owned one fragment-aware, jittered polling schedule per unique PR; artifact bindings did not each force an authoritative full refresh.  
**Changed behavior:** Each automation binding now independently forces a full authoritative refresh of its shared pull-request resource every 60 seconds.  
**Confidence:** 0.98 — The binding-local timer and pooled-resource lifetime are explicit in the traced code. \`GitHubPullRequestArtifactResource.refresh\` refreshes core and all effective fragments, while authoritative refreshes cancel an existing fragment operation rather than joining it. Only the prevalence of users recording the same PR in many retained sessions is uncertain.

**Causal diff evidence:** The added \`schedulePoll()\` at line 897 installs a 60-second timer in every \`GitHubPullRequestArtifactBinding\`; its callback reaches the added authoritative \`resource.refresh\`. Artifact resources are pooled by authority/runtime/resource/credential scope, but automation activation is per recorded artifact/session binding, so multiple bindings for one pooled PR each create this timer.

When the same PR is recorded with automation enabled in multiple sessions/artifacts, background GitHub traffic and request-queue pressure grow with binding count rather than unique PR count. Synchronized polls can cancel/restart each other's fragment reads, delaying automation and increasing rate-limit consumption.

**Evidence:** \`ArtifactResourcePool\` shares one \`GitHubPullRequestArtifactResource\` for the same resource and credential scope, while \`ArtifactBinding.observeView\` invokes \`activateAutomation\` separately per recorded artifact/session. Each added poll calls \`subscription.refresh(..., { authoritative: true })\`; the resource interests include core, review threads, checks, and mergeability, so one poll fans out to at least four GitHub fragment fetches (and potentially pagination). \`PullRequestResourceService.\_refreshFragment\` cancels an existing operation for authoritative requests, so sibling binding polls do not coalesce at this layer.

**Suggested direction:** Own the 60-second authoritative deadline on the pooled \`GitHubPullRequestArtifactResource\`, or coalesce binding refresh requests through one shared in-flight/deadline state, then let every binding evaluate the resulting shared snapshot.


## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/platform/agentHost/node/agentMergeController.ts:1092` (`LEFT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentMergeController.ts:1092`  
**Introducing path:** `src/vs/platform/agentHost/node/agentMergeController.ts`  
**Introducing commit:** `95f9401ceb4916bb0a2f5ee9807f8fea240f0b2c`  
**Mechanism family:** `eager-work`  
**Performance category:** `latency`  
**Confidence:** 0.99

**Mechanism:** The old gate synchronously withheld an otherwise applicable repair prompt for a 10-minute quiet period whenever any sibling check remained pending, putting timer delay directly on the autonomous CI-repair critical path.

**Symptom:** Applicable Agent Merge CI repairs could not start for at least 10 minutes, including when a human-approval check remained pending indefinitely.

**Fixed behavior:** CI-only Agent Merge prompts are evaluated and dispatched immediately; only an identical already-dispatched repair fingerprint observes the separate 10-minute retry cooldown.

**Evidence:** In the base revision, line 1092 computed `_getCIRepairHold(runtime)` for CI-only prompts; the helper delayed work until checks had been unchanged for 10 minutes (and up to a 60-minute maximum hold). This PR deletes that hold path, and the added pacing tests show a failed CI check now starts immediately even while an approval/other workflow remains pending.
