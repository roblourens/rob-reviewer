## Findings (1)

### 1. [medium] Keep optional checks from forcing the pending poll cadence

**Finding ID:** `PERF-6DD35168AEFA`  
**Location:** <code>src/vs/platform/agentHost/node/agentMergeController.ts:1337</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** GitHub GraphQL requests and local git subprocesses  
**Scaling:** For each Agent Merge pull request, cost repeats every minute for as long as any optional check remains queued or running; multiple enabled pull requests each have a separately coalesced resource stream.  
**Outcome:** Excess GitHub API traffic plus increased agent-host CPU, filesystem I/O, and subprocess churn.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The subscription retained only required checks. Once the failed required check was completed, the shared checks fragment used its 5-minute backstop cadence; optional pending jobs could not accelerate it.  
**Changed behavior:** Setting includeOptional makes optional queued/running checks visible to PullRequestResourceService.checksPending, selecting checksPendingBackground (60 seconds) instead of checksBackstop (300 seconds), even after the required checks have settled.  
**Confidence:** 0.97 — The changed option, filter behavior, poll constants, pending predicate, snapshot observer, and Git subprocess call path are all explicit. Exact wall-clock cost varies by repository and pagination, but the 5x checks-request frequency and realistic optional-job trigger are deterministic.

**Causal diff evidence:** The added \`includeOptional: true\` at line 1337 broadens the value consumed by the unchanged shared polling policy; \`checksPending\` treats every visible incomplete check as pending, so this changed option alone switches the cadence.

A realistic long-running or stuck optional workflow causes five times as many checks refreshes (at least two GraphQL requests per refresh) while Agent Merge is enabled, and raises full controller/Git refresh frequency from the existing 2-minute mergeability cadence to about once per minute. This persists beyond the 10-minute CI hold and can last indefinitely until the optional job completes or Agent Merge is disabled.

**Evidence:** PullRequestResourceService uses a 60-second background interval when \`checksPending(snapshot.checks.value)\` is true and a 300-second backstop otherwise. The query fetches all checks and filters optional checks only before publishing, so this option changes the scheduler-visible state. Each checks fetch performs the rollup GraphQL query and, because \`required: true\`, the expected-suite GraphQL query (with pagination possible). Each published snapshot schedules AgentMergeController evaluation, whose critical path calls \`attachSessionGitHubPullRequest\`; that refresh computes session Git state through \`git status\`, \`git remote\`, \`symbolic-ref\`, divergence probes, and then calls \`git branch --show-current\`.

**Suggested direction:** Do not expose optional pending state to the permanent shared polling predicate. Scope optional-check polling to an active CI-only hold, or make the resource cadence depend on required-check pending state while scheduling a bounded pacing-specific refresh for optional activity; return to the backstop cadence after the hold.


## Performance regression fixes detected (1)

### 1. missing-coalescing

**Fix location:** `src/vs/platform/agentHost/node/agentMergeController.ts:1020` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentMergeController.ts:1001`  
**Introducing path:** `src/vs/platform/agentHost/node/agentMergeController.ts`  
**Introducing commit:** `30ad9a507bd8d7e610d598065aac600efcc7881d`  
**Mechanism family:** `missing-coalescing`  
**Performance category:** `throughput`  
**Confidence:** 0.96

**Mechanism:** Before this change, a CI-only gate started a repair as soon as the prior turn completed whenever the fingerprint changed. The fingerprint includes failed check names/IDs, so normal CI fan-in can present successive distinct failure sets and bypass the unchanged-fingerprint backstop, producing one expensive agent repair turn per intermediate state.

**Symptom:** Redundant agent repair turns and authoritative GitHub refreshes while workflows are still settling, consuming repair throughput and remote/local resources without waiting to collect the final failure set.

**Fixed behavior:** The added CI hold computes a shared quiet/deadline window and returns before claiming a turn, coalescing changing pending-check states until ten minutes of quiet with a one-hour upper bound; non-CI repairs retain their immediate behavior.

**Evidence:** `evaluateAgentMerge` fingerprints actionable failed check IDs and context; `shouldRunFingerprint` permits every changed fingerprint immediately; `_completeTurn` authoritatively refreshes all subscribed fragments and immediately reevaluates. Thus successive check completions/failures could each start another full repair turn. Added line 1020 gates CI-only repair through `_getCIRepairHold`, and the pacing tests prove no prompt while checks change and one prompt after quiet. Blame identifies the original immediate budget/start path in the Agent Merge controller introduction.
