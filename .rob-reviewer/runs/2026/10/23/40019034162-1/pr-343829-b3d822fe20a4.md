- Critical path: Opening the visible section synchronously groups and sorts installed extensions, builds tree entries, renders the virtualized viewport, and lays out the tree. Search is delayed by 200 ms; extension changes rerender only while visible. The added warning and AI-feature labels are on this UI critical path.
- Scaling input: Installed non-built-in extensions (typically tens to hundreds) control grouping; only viewport-visible rows create warning hover listeners and at most seven fixed-list feature badges. Manifest feature checks inspect fixed lists of 8 AI points and 8 unsupported points, although warning detection enumerates each visible extension's contribution object.
- Effective concurrency: Single UI-thread render; searches are coalesced by the existing Delayer, hidden-section changes are deferred with renderPending, and WorkbenchObjectTree virtualizes extension rows.
- Cache behavior: The suggestions observable memoizes derived results until extension/configuration changes. Warning/label strings are recomputed when virtualized rows render rather than cached, but their fixed contribution vocabulary and viewport cardinality bound the added work; there is no cold boundary fetch.
- Mechanism confidence: High: the render, accessibility-label, hover-disposal, virtualization, and manifest-helper call paths are directly visible.
- Magnitude uncertainty: Exact installed-extension and viewport counts vary, but the added work remains local DOM/allocation and fixed-list manifest inspection; no changed filesystem, IPC, database, network, or subprocess call is reached.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff adds bounded per-visible-row DOM nodes, hover registrations with element-scoped disposal, and fixed-list manifest scans; it does not add collection-wide boundary fan-out, forced layout reads after writes, or unbounded retention.

### Scenario 4: Suggestion badge recomputation when installed extensions or configuration changes

- Critical path: When management is enabled and the badge/group observable is consumed, an extension-change signal filters the local installed extension collection and checks fixed AI contribution keys. Badge dismissal serializes the dismissed identifier set to profile storage only on explicit section navigation or visible changes.
- Scaling input: Installed extension count controls the local filter; effective suggestions are a subset selected by eight fixed AI keys, narrower than the previous contribution set.
- Effective concurrency: Observable recomputation is synchronous and coalesced by dependency invalidation; storage writes remain one per changed dismissal set, without parallel fan-out.
- Cache behavior: Derived observables retain results until extension/configuration invalidation; dismissal state is persisted and unchanged writes are skipped by size comparison.
- Mechanism confidence: High: observable dependencies, filtering, persistence guard, and before/after contribution sets are explicit.
- Magnitude uncertainty: Installed extension counts vary, but the PR removes candidate contribution categories and introduces no new boundary or hotter invalidation source.
- Expensive boundaries:
  - filesystem at <code>src/vs/sessions/contrib/extensions/browser/agentsWindowExtensionSuggestions.ts:dismissBadge</code>: Store the dismissed suggestion identifiers in profile storage.; cardinality: One existing store operation when dismissal adds identifiers; no write when the set size is unchanged.

- Verdict: No reportable performance regression; candidate scanning remains linear local work and storage-call cardinality is unchanged or reduced.
