## Findings (1)

### 1. [medium] Index configured remotes once before mapping picker rows

**Finding ID:** `PERF-22F9D6E8CA79`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionEnvironmentPicker.ts:231</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU comparisons plus arrays and normalized entry/connection object allocations  
**Scaling:** O(N^2) work and allocations for N displayed configured remote environments (N getter snapshots of N configured entries), rather than one O(N) index build.  
**Outcome:** increased picker-open latency and CPU/GC pressure on the UI thread  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With global Manage enabled, the previous ternary assigned \`undefined\` directly for every row and did not read or scan the configured remote catalog while constructing picker items.  
**Changed behavior:** Opening the Environment picker with global Manage enabled now snapshots, normalizes, and linearly scans all configured remote entries separately for each displayed remote environment.  
**Confidence:** 0.98 — The synchronous click path, per-row invocation, allocating service getter, and one-provider-per-configured-entry reconciliation are directly established in the repository. Exact delay depends on users' remote-catalog size, but the quadratic CPU/allocation mechanism is deterministic.

**Causal diff evidence:** RIGHT line 231 adds \`this.isManagedInRemotes(environment)\` inside \`this.environments.get().map(...)\`, so it executes once per displayed environment. The added helper's line 289 reads \`remoteAgentHostService.configuredEntries\` on every call; that getter maps the entire configured-entry collection and \`\_normalizeEntry\` copies normalized entries/connections before \`.find\` scans it.

For users with a large configured remote fleet, clicking the Environment control can synchronously allocate and scan quadratically before the popup appears, causing input latency and avoidable GC pauses.

**Evidence:** \`showPicker()\` synchronously maps all environments before calling \`actionWidgetService.show\`. \`isManagedInRemotes\` reads \`configuredEntries\` per remote; \`RemoteAgentHostService.configuredEntries\` is implemented as \`\_configuredEntries.get().map(entry =&gt; this.\_normalizeEntry(entry))\`, and normalized-address entries are copied with new entry and connection objects. Entry-driven contributions register one session provider for each configured SSH/WSL/etc. entry, so with N configured remotes the picker generally has N remote environments and performs N full N-entry snapshots plus N linear finds.

**Suggested direction:** When \`showManage\` is true, read \`configuredEntries\` once before mapping, build a map from address to connection, and have the per-environment check use that map; this preserves the entry-type rules while reducing picker-open work to O(N).
