# Performance review: Improve worktree cleanup progress, preservation, and leftover-folder handling

[PR #343676](https://github.com/microsoft/vscode/pull/343676) at `3edb01cc9c7410596388874f90d96d77a1a1e2bf`

## Findings (2)

### 1. [medium] Avoid reattaching every row on each measurement update

**Finding ID:** `PERF-07195D218F17`  
**Location:** <code>src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupEditor.ts:505</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Existing DOM row nodes plus synchronous browser style/layout work from scrollWidth and scrollHeight reads  
**Scaling:** For N visible sessions and R progressive renders, this loop performs N appendChild mutations per render even when order is unchanged, for O(N×R) DOM work (up to O(N²) as sessions finish); updates are only capped at one render per 100 ms.  
**Outcome:** Repeated main-thread DOM mutation and forced layout can increase interaction latency and cause dropped frames while the cleanup table is progressively populated.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The editor waited for all measurements and built the table once, so it incurred one O(N) row insertion/layout pass.  
**Changed behavior:** Progressive snapshots now call renderRows repeatedly; although rows are cached by session ID, this added line appends every cached element on every pass. appendChild moves an already attached node, and renderRows then calls updateScrollDimensions, which synchronously reads container.scrollWidth/scrollHeight after those writes.  
**Confidence:** 0.98 — DOM appendChild semantics, the progressive callback frequency, the full-row loop, and the subsequent geometry reads are explicit. Device-specific frame cost is uncertain, but the repeated O(N×R) mutation/layout mechanism is not.

**Causal diff evidence:** Added line 505 unconditionally re-appends each reused row inside the new progressive render loop; before the PR there were no intermediate table renders.

Opening Worktree Cleanup with dozens or hundreds of sessions while measurements finish over time repeatedly moves the entire table and forces layout, making the visible editor jank even when only one row's size changed.

**Evidence:** The service publishes an initial N-row snapshot and another snapshot after each measured session. The editor coalesces those to 100 ms, but renderRows sorts all visible rows, executes line 505 for every row unconditionally, then reads scroll dimensions. The signature guard avoids cell updates but does not avoid these DOM moves.

**Suggested direction:** Reconcile order conditionally: walk the desired sequence and use insertBefore only when a row is not already at the expected sibling, skipping structural DOM writes when order is unchanged; update scroll dimensions once after an actual structural change.

### 2. [medium] Prevent slow scans from monopolizing the shared scan queue

**Finding ID:** `PERF-A6093C379AFC`  
**Location:** <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:3608</code> (<code>LEFT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Two globally limited recursive filesystem scans, each issuing directory opens and batches of file lstat calls  
**Scaling:** One measurement is issued per distinct session worktree (and sequentially per additional worktree in a session); if the first two roots are very large or an opendir/lstat stalls, all remaining N-2 measurements wait for their full duration with no upper bound.  
**Outcome:** The cleanup editor and background cleanup-suggestion scan can remain pending indefinitely, with later small worktrees starved and filesystem I/O continuing for the lifetime of the caller.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Both this protocol handler and the cleanup service canceled a per-worktree measurement after 10 seconds, which released the AgentHostWorktreeDiskUsageService's shared two-slot limiter and allowed queued worktrees to progress.  
**Changed behavior:** The diff removes the protocol watchdog and the service's raceTimeout; requests now stop only on explicit caller cancellation, editor close when it is the last consumer, disconnect, or service disposal.  
**Confidence:** 0.97 — The complete call path, fixed concurrency of two, per-worktree boundary cardinality, recursive I/O, and removed cancellation deadline are explicit in code. Exact prevalence and stall duration vary by checkout and filesystem, which affects severity rather than mechanism confidence.

**Causal diff evidence:** Deleted line 3608 previously scheduled cancellation after 10,000 ms; the changed handler now awaits the recursive measurement without any deadline, while the same diff removes the matching service timeout.

With two huge checkouts or stalled filesystem operations at the front of the scan, every later row stays in “Calculating…” and the hourly background measurement never reaches the remaining sessions; this is especially realistic for large generated trees or slow/mounted storage.

**Evidence:** SessionWorktreeCleanupService queues sessions with concurrency 2 and calls getSessionWorktreeDiskUsage; the provider sends one protocol request per distinct worktree. AgentHostWorktreeDiskUsageService applies another process-wide Limiter(2), and measureWorktreeDiskUsage recursively awaits opendir/lstat. Removing line 3608 eliminates the final time bound on those occupied slots; the same PR also deletes WORKTREE\_MEASUREMENT\_TIMEOUT\_MS/raceTimeout in the caller.

**Suggested direction:** Preserve eventual results without queue starvation by time-slicing traversal across requests (release/reacquire the shared budget between bounded directory batches); if that is not feasible, retain a bounded watchdog with an explicit failed/pending state so one root cannot hold a global slot indefinitely.
