## Findings (1)

### 1. [medium] Discover PRM only after the index rejects the current token

**Finding ID:** `PERF-D5AEE750958E`  
**Location:** <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:211</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** HTTP network requests to OAuth protected-resource metadata endpoints  
**Scaling:** Each eligible Microsoft account resolution performs discovery with no positive or negative cache. \`fetchResourceMetadata\` issues one request for a root service URL, or sequentially tries path-appended and root well-known URLs for a service index with a path; every Microsoft session-change revalidation repeats those calls.  
**Outcome:** increased latency and excessive network I/O before the extension marketplace becomes available  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After resolving the existing Microsoft session and eligibility locally, the manifest service fetched the configured service index directly. Open marketplaces therefore required only the index request and account-change revalidation did not probe well-known metadata endpoints.  
**Changed behavior:** The added awaited call discovers protected-resource metadata before \`doGetAccount\` returns, so the manifest service cannot start its service-index request until discovery finishes, even when the index would accept the existing sign-in token.  
**Confidence:** 0.99 — The changed call order, network implementation, lack of caching, helper retry cardinality, eager service initialization, and test-observed request are all explicit. Exact endpoint latency varies by deployment, which affects severity but not the mechanism.

**Causal diff evidence:** The added line \`const protectedResource = await this.discoverProtectedResource(serviceIndexUrl);\` places uncached PRM HTTP discovery in every eligible Microsoft account resolution before the existing service-index fetch.

Opening or initializing an authenticated Microsoft private marketplace that does not require a resource-scoped token is delayed by an unnecessary well-known request (two sequential requests when the service-index URL has a path). Slow or absent well-known endpoints extend the marketplace critical path, and Microsoft session events repeat the delay and traffic.

**Evidence:** \`doGetAccount\` now awaits \`discoverProtectedResource(serviceIndexUrl)\` before returning the account; only afterward can \`handleMarketplaceAccountAccess\` call \`getExtensionGalleryManifestFromServiceUrl\`. \`discoverProtectedResource\` delegates to \`fetchResourceMetadata\` without a cache, and that helper sequentially probes the path-appended and root well-known URLs when the target has a path. The added test \`an index without protected resource metadata uses the sign-in token\` explicitly observes one well-known request even though the index returns 200, proving this extra boundary call is made on the open-marketplace path.

**Suggested direction:** Fetch the service index first with the current session token; only on 401/403 perform PRM discovery and resource-token acquisition, then retry once. Cache/coalesce positive and negative discovery per service-index URL and invalidate it when the configured marketplace changes.
