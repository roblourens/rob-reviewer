# Performance review: Parent the ConPTY console window to the VS Code window

[PR #342784](https://github.com/microsoft/vscode/pull/342784) at `fb04e9e3d8e4bc56375e4795d7fdc8ff4293f2b3`

## Findings (1)

### 1. [low] Gate window-handle IPC on conpty.dll

**Finding ID:** `PERF-7BD2F3304CCF`  
**Location:** <code>src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts:782</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Electron main-process handle requests, renderer-to-pty-host IPC calls, and serialized handle bytes  
**Scaling:** The native-handle request is coalesced to one per unique VS Code window by NativeHostService, while the no-op pty-host RPC scales once per terminal startup/restore and once per actual window move.  
**Outcome:** Excessive IPC and marginally increased terminal startup/restoration latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, terminals with windowsUseConptyDll disabled performed neither the native-window-handle lookup nor the setParentWindow pty-host RPC.  
**Changed behavior:** Windows local terminals now resolve a native window handle and attempt a setParentWindow call whenever windowsReparentConsoleWindow is enabled, including configurations where windowsUseConptyDll is false and the pty layer cannot use the result.  
**Confidence:** 0.96 — The call chain is explicit: TerminalInstance invokes this method before createProcess; createProcess awaits \_resolveParentWindowHandle; NativeHostService crosses to Electron main on the first lookup per window and memoizes it; LocalPty forwards setParentWindow to the pty host; TerminalProcess drops it when useConptyDll is false. The exact latency varies with IPC load, so severity is low, but the no-op boundary work and trigger are certain.

**Causal diff evidence:** RIGHT line 782 adds the eligibility guard for the new setParentWindow path but checks only platform, remote authority, and windowsReparentConsoleWindow; it does not check windowsUseConptyDll, even though the newly added TerminalProcess.setParentWindow returns immediately when useConptyDll is false.

On Windows installations that disable terminal.integrated.windowsUseConptyDll, the first terminal in each window is unnecessarily held behind a main-process IPC, and terminal creation/restoration still sends one useless pty-host RPC per terminal. Restoring many terminals adds avoidable IPC traffic and launch work without enabling reparenting.

**Evidence:** TerminalInstance calls TerminalProcessManager.setParentWindow before every local terminal creation. The manager's added guard at line 782 allows the call when windowsReparentConsoleWindow=true even if windowsUseConptyDll=false, then createProcess awaits the handle resolution. NativeHostService.getNativeWindowHandle performs one Electron-main request per window, and LocalPty.setParentWindow performs a renderer-to-pty-host RPC per process. The added TerminalProcess.setParentWindow checks \!useConptyDll and returns without using the handle, proving all of this work is wasted for that supported configuration.

**Suggested direction:** Include windowsUseConptyDll in the early eligibility guard (and avoid retaining/resolving a parent handle when it is false), so configurations that cannot call node-pty's reparenting API stay on the previous startup path.

### Scenario 1: Create, revive, or reattach local Windows terminals with conpty.dll reparenting enabled

- Critical path: For a new, revived, or reattached local Windows terminal, backend process-object creation completes first, then createProcess explicitly awaits the latest native-handle lookup before issuing setParentWindow and start. Thus the cold Electron-main lookup is on shell startup's critical path; the setParentWindow RPC is issued immediately before start to preserve ordering.
- Scaling input: Number of unique VS Code windows for cold native-handle lookups and number of restored/created terminals for pty-host calls.
- Effective concurrency: Concurrent terminal restores share the per-window native-handle Promise, but each terminal independently emits setParentWindow and start messages to the pty host. There is no added shared limiter; effective pty-host concurrency/cardinality follows the number of terminals restored.
- Cache behavior: IHostService caches the Promise and result by VS Code window ID, so concurrent terminal creations in one window coalesce to one cold Electron-main lookup; warm creations reuse the resolved handle. Each TerminalProcessManager retains its own 8-byte handle, but the pty-host setParentWindow call is per terminal and is not cached.
- Mechanism confidence: High: the added awaits, cache implementation, direct proxy call chain, and node-pty invocation are explicit.
- Magnitude uncertainty: The handle is only eight bytes and the main-process lookup is coalesced, so exact added latency under normal IPC load is uncertain and likely small; the changed critical-path ordering and per-terminal pty RPC are certain.

  - IPC at <code>src/vs/workbench/contrib/terminal/electron-browser/localPty.ts:setParentWindow</code>: Serialize the VSBuffer handle and send it from the renderer to the pty host.; cardinality: One new setParentWindow RPC per terminal creation/revival/reattachment when a handle exists.

### Scenario 2: Start or restore Windows terminals when windowsUseConptyDll is disabled

- Critical path: The first terminal in a window still awaits the cold native-handle IPC before start. Every terminal then issues setParentWindow immediately before start; TerminalProcess discards it because useConptyDll is false.
- Scaling input: Unique windows for main-process calls and terminal count/window moves for pty-host calls.
- Effective concurrency: A multi-terminal restore coalesces the main-process lookup but fans out one useless pty-host RPC per terminal. Those calls are not grouped or suppressed by backend capability.
- Cache behavior: The same per-window native-handle cache coalesces the Electron-main request, but the resolved handle is still retained by each manager. There is no negative capability cache at the manager layer; every terminal forwards the handle to the pty host despite the backend configuration making it unusable.
- Mechanism confidence: High: the manager omits the prerequisite setting from its guard while the terminal process explicitly no-ops on that setting.
- Magnitude uncertainty: Users must explicitly or experimentally disable windowsUseConptyDll, and each individual payload is tiny, so prevalence and milliseconds are uncertain; the wasted boundaries and terminal-count scaling are proven.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts:782-800</code>: Resolve the HWND for a backend that cannot reparent.; cardinality: One cold Electron-main IPC per unique window; subsequent lookups are warm.
    - Introduced by diff: true; previous behavior: No HWND request was made.; critical-path effect: The cold request blocks first-terminal startup even though its result cannot be used.
  - IPC at <code>src/vs/workbench/contrib/terminal/electron-browser/localPty.ts:setParentWindow</code>: Send an eight-byte handle to TerminalProcess.setParentWindow, which rejects the capability via its useConptyDll guard.; cardinality: One renderer-to-pty-host RPC per terminal startup/restore, plus one per actual window move.
    - Introduced by diff: true; previous behavior: No parent-window RPC was sent.; critical-path effect: The startup call is issued directly before start and consumes serialization/dispatch work; the pty implementation returns without using it.
- Verdict: Reportable low-severity boundary fan-out: the diff adds IPC and startup waiting that cannot produce the requested behavior.

### Scenario 3: Reattach or move a live terminal between VS Code windows

- Critical path: TerminalInstance does not await setParentWindow during attachToElement, so reparenting work is off the synchronous DOM-attachment/render critical path. The pty-host RPC runs asynchronously after the window lookup.
- Scaling input: Number of terminal instances moved to a different VS Code window, after deduplication by unchanged handle.
- Effective concurrency: Moving a group of terminals can schedule one independent RPC per terminal. Native-handle lookup is coalesced by destination window, but pty calls are not globally limited.
- Cache behavior: Moves to an already-seen VS Code window use NativeHostService's cached handle. Reattaching to the same window still performs an async cached lookup, but handle equality suppresses the pty-host RPC; moving to a different window updates the per-manager handle and sends once.
- Mechanism confidence: High for cardinality and scheduling; low uncertainty only in real-world group sizes.
- Magnitude uncertainty: The number of simultaneously moved terminals varies, but normal window counts are small and same-window reattachments suppress downstream RPC. No evidence shows a realistic jank or throughput threshold on the supported path.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminal/browser/terminalInstance.ts:attachToElement</code>: Resolve the destination window's native handle.; cardinality: At most one cold Electron-main request per newly encountered VS Code window globally; cached calls per attached terminal otherwise resolve from the memoized Promise.
    - Introduced by diff: true; previous behavior: Moving or reattaching terminal DOM did not request an HWND.; critical-path effect: Off the synchronous attachment path because the caller does not await it.
  - IPC at <code>src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts:setParentWindow</code>: Apply the destination HWND to the live pty.; cardinality: One pty-host call per terminal whose effective window handle changed; zero when equality detects the same handle.
    - Introduced by diff: true; previous behavior: No live reparenting IPC was sent.; critical-path effect: Asynchronous and not awaited by DOM attachment, though it consumes pty-host work.
- Verdict: No additional finding: required live reparenting scales per affected terminal, destination handle reads are coalesced, and the work is not awaited by the UI attachment path.

### Scenario 4: Create remote, non-Windows, reparenting-disabled, or custom pseudoterminals

- Critical path: The guarded non-Windows, remote, and setting-disabled cases add no boundary to startup. A first local custom PTY in a Windows window may wait for the shared cold handle lookup, but this is bounded once per window.
- Scaling input: Unique VS Code windows rather than custom-PTY count after cache coalescing.
- Effective concurrency: Early-return cases perform no added concurrent work. Custom PTYs share the per-window handle Promise.
- Cache behavior: Non-Windows and remote terminals return before lookup. Disabling windowsReparentConsoleWindow also returns before lookup. Local custom PTYs on Windows can populate the same one-per-window handle cache, but their optional setParentWindow method is absent, so no pty RPC follows.
- Mechanism confidence: High for guards and cache behavior.
- Magnitude uncertainty: Custom PTY prevalence and cold-lookup duration are uncertain; coalescing bounds this to one native request per window, so evidence does not establish a separate material regression.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts:setParentWindow</code>: Conditionally request the native HWND.; cardinality: Zero for non-Windows, remote, or explicit reparenting-off cases; at most one cold main-process lookup per window for local Windows custom PTYs.
    - Introduced by diff: true; previous behavior: None of these scenarios requested it.; critical-path effect: No effect for early-return cases; the custom-PTY cold lookup is awaited before start/open.
- Verdict: No separate finding: primary guards eliminate work for remote/non-Windows/disabled cases, while custom-PTY overhead is bounded and shares the same cold cache miss.
