### 1. repeated-work

**Fix location:** `src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:283` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:208`  
**Introducing path:** `src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts`  
**Introducing commit:** `d71149f1290a26993dda238eb699f2d3aa4c254c`  
**Mechanism family:** `repeated-work`  
**Performance category:** `network`  
**Confidence:** 0.97

**Mechanism:** Each private-marketplace account revalidation repeated RFC 9728 protected-resource metadata discovery, including sequential authentication-session events and concurrent resolutions, producing redundant network requests on the manifest/account critical path.

**Symptom:** Repeated or concurrent marketplace account revalidation incurred avoidable network latency and request load before the private marketplace manifest could be refreshed.

**Fixed behavior:** Successful protected-resource metadata is reused for the same full service URL for five minutes, and concurrent cold lookups share one discovery promise. Failures remain retryable, URL/provider changes invalidate the cache, and resource-scoped token acquisition still executes on every account lookup.

**Evidence:** Base line 208 invoked discoverProtectedResource(serviceIndexUrl) for every eligible Microsoft account resolution. WorkbenchExtensionGalleryManifestService.handleMarketplaceAccountAccess calls getAccount on initial private-marketplace bootstrap and again for each Microsoft onDidChangeSessions event; fetchResourceMetadata crosses IRequestService and can issue one well-known GET for root URLs or a path-appended GET plus root fallback for path URLs. The added successful-value check and in-flight request reuse remove repeated discovery while preserving per-resolution token acquisition. Added tests prove sequential resolutions perform one metadata request and three concurrent resolutions coalesce to one.

On a warm metadata cache, discovery is removed from this critical path; token and manifest operations remain required.
- Scaling input: The prior cost scaled with eligible account-resolution count and concurrent authentication events. After the diff, metadata network cost scales with distinct sequential service URLs and five-minute cache windows; production normally has one configured service URL.
- Effective concurrency: The steps within one resolution are awaited serially. Concurrent account resolutions share one metadata discovery promise for the current exact service URL; the manifest service separately cancels superseded resolutions but does not add concurrency in this diff.
- Cache behavior: One positive entry is keyed by the exact service URL, including path. Its five-minute TTL starts after successful discovery and does not slide on reads. In-flight cold requests are coalesced. Missing, invalid, failed, or unusable metadata is not negatively cached and is retried. URL changes and provider replacement create empty cache state.
- Mechanism confidence: High: direct call flow and deterministic tests establish both the old per-resolution boundary and the new one-request cache/coalescing behavior.

### Scenario 2: Microsoft authentication-session change and marketplace revalidation

- Critical path: Each Microsoft onDidChangeSessions event fires the account-change event, which starts handleMarketplaceAccountAccess. Sign-in session lookup, resource token lookup, and manifest fetch remain on the revalidation path; protected-resource discovery is now off-path on a valid warm cache.
- Scaling input: Event count and event burst width determine auth-provider and manifest work; metadata discovery is reduced from event count to URL/TTL-window count after coalescing.
- Effective concurrency: Rapid events can overlap at the manifest-service level; beginResolution cancels older manifest resolutions. The added cache coalesces only metadata discovery globally for the current URL, while sign-in/resource-session lookups still execute per resolution as before.
- Cache behavior: Concurrent events for the same URL share an in-flight metadata promise, and subsequent events reuse a successful value until fixed expiration. Failed discovery is immediately retryable, so a sustained endpoint failure can still produce one attempt per sequential event, matching prior retry semantics rather than adding work.
- Mechanism confidence: High: provider event wiring, manifest handler, and cache request identity checks are explicit.
- Magnitude uncertainty: Real session-event burst rates are deployment-dependent; tests and event wiring prove this path exists.
- Expensive boundaries:

### Scenario 3: Interactive Microsoft marketplace sign-in and protected-resource consent

- Critical path: The user-triggered flow creates the sign-in session, obtains metadata from the captured current cache, checks silently for an existing resource-scoped session, and only then may create an interactive resource-scoped session. Metadata discovery is off-path when the cache is warm, but a missing or expired cache is refreshed before consent.
- Scaling input: Cost scales with user sign-in attempts and cache expiration windows, not marketplace catalog size. Concurrent attempts share discovery but retain their own authentication-provider operations.
- Effective concurrency: Operations in one consent flow are serial. Any concurrent account lookup for the same URL shares metadata discovery. Cache identity, expiration, provider disposal, or URL replacement aborts stale consent rather than launching additional resource-session creation.
- Cache behavior: Consent captures the current one-entry URL cache. It uses a successful warm value, joins an in-flight request, or refreshes an expired value. Before prompting for resource consent it rechecks provider ownership, cache identity/value, and expiration. Failures are not cached and simply skip resource consent for that attempt.
- Mechanism confidence: High: the serial awaits and stale-result guards are explicit and covered by race/expiration tests.
- Magnitude uncertainty: Endpoint latency after expiration varies, but this is a bounded single discovery required to avoid using stale authorization metadata; there is no evidenced harmful burst or unbounded delay introduced by the cache design itself.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:357 signIn</code>: Enumerate accounts and create the selected Microsoft sign-in session.; cardinality: One account enumeration and one sign-in session creation per completed user choice.
    - Introduced by diff: false; previous behavior: Unchanged.; critical-path effect: User interaction and provider session creation are the main sign-in critical path.
  - network at <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:304 discoverProtectedResource</code>: Fetch current protected-resource metadata when absent or expired.; cardinality: Zero warm; one coalesced logical discovery cold/expired, with optional root fallback for path URLs.
    - Introduced by diff: true; previous behavior: After any prior successful discovery, sign-in reused metadata indefinitely; if none existed but a service URL was known, it performed discovery.; critical-path effect: Cold/expired discovery is awaited before resource consent. The diff can refresh after five minutes where the old indefinite value avoided this request, an intentional freshness bound; cardinality is one and coalesced.
  - IPC at <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:260 and :415</code>: Check for and, if needed, create a resource-scoped Microsoft session.; cardinality: One silent check and at most one interactive creation per consent flow.
    - Introduced by diff: false; previous behavior: Same operations, using the last indefinitely retained metadata.; critical-path effect: The silent check and optional consent must finish before signIn resolves.
- Verdict: No reportable regression. The bounded refresh can add one network round trip to an expired interactive flow, but it is required by the stated freshness semantics, coalesced, and does not create scaling fan-out.

### Scenario 4: Service URL change and provider replacement

- Critical path: A resolution for a different full service URL replaces the one-entry cache; provider replacement starts with a new empty provider cache. The next eligible lookup performs fresh metadata discovery before token acquisition.
- Scaling input: Network cost scales with URL transitions rather than historical distinct URLs; realistic production configuration has one active URL and configuration changes require restart.
- Effective concurrency: Old in-flight discovery is not canceled at the transport layer, but its result is rejected by cache identity checks. A new URL may therefore overlap with one obsolete request; repeated same-URL callers still coalesce on the current cache.
- Cache behavior: The cache key is the complete service URL string. There is no multi-URL retention, preventing unbounded key growth. Provider disposal/replacement invalidates ownership, and replacement providers never inherit metadata.
- Mechanism confidence: High: one-entry replacement and stale-object identity checks are direct.
- Magnitude uncertainty: Tests synthesize rapid URL alternation; normal product flow rarely changes URL without restart.
- Expensive boundaries:
  - network at <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:292-304</code>: Discover metadata separately for the new service URL while an obsolete URL request may still be in flight.; cardinality: One logical discovery for each effective URL transition; at most the obsolete request plus the current request overlap in the traced transition. Returning to a previous URL creates another cold request because this is deliberately a one-entry cache.
    - Introduced by diff: false; previous behavior: Every resolution discovered afresh, so URL transitions also issued new requests and old requests could remain in flight.; critical-path effect: Only the current URL discovery can advance the new resolution; obsolete completion is ignored.
- Verdict: No regression. The design bounds memory to one entry and prevents obsolete requests from repopulating current state; lack of transport cancellation is pre-existing and does not increase request cardinality.
