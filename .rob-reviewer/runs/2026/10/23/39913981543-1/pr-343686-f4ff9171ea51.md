### Scenario 1: Workbench startup with a configured private marketplace returning HTTP 403

- Critical path: The eager manifest service resolves the configured account and awaits the service-index request before publishing a null manifest/status and initializing shared-process and optional remote-server channels. The diff does not add an await or boundary; it changes the terminal local status from RequiresSignIn to AccessDenied. \`asJson\` checks the non-success status and throws before reading or parsing the response body.
- Scaling input: One coalesced manifest initialization per service instance (\`extensionGalleryManifestPromise\`), with one configured marketplace service-index URL. Account/provider work is one logical account resolution; no collection fan-out is introduced.
- Effective concurrency: Concurrent \`getExtensionGalleryManifest\` callers share one promise. Account resolution and the service-index request are awaited serially. Account-change resolutions can overlap but cancel the prior resolution token; that behavior and request cardinality are unchanged by the diff.
- Cache behavior: The manifest initialization promise coalesces cold callers and remains warm for later callers. Provider session/preferred-account and protected-resource behavior is unchanged. A 403 is not negatively cached separately before or after; it remains the current in-memory status until an account event.
- Mechanism confidence: High: the production hunk only removes 403 from the auth-required branch; traced \`asJson\` rejects before buffering non-2xx responses, and all network/IPC scheduling is unchanged.
- Magnitude uncertainty: Provider implementations and network latency vary by deployment, but no boundary count, response buffering, or scheduling changed. The new generic path adds at most the existing error-log calls for a 403, once per resolution, which is not a realistic reportable regression.
- Expensive boundaries:
  - network at <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:discoverProtectedResource</code>: Resolve OAuth protected-resource metadata for an eligible Microsoft account when applicable.; cardinality: At most one metadata discovery sequence per Microsoft account resolution; zero for the GitHub/default provider path. Effective cardinality is unchanged by this diff.
    - Introduced by diff: false; previous behavior: The same provider/account resolution and metadata discovery occurred before the changed 403 classification.; critical-path effect: For the Microsoft path this completes before the account/token can be returned and before the service-index request proceeds.
  - network at <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryManifestService.ts:getExtensionGalleryManifestFromServiceUrl</code>: GET the configured marketplace service index.; cardinality: One request for the initial coalesced resolution, and one per later account-change resolution; unchanged by the diff.
    - Introduced by diff: false; previous behavior: Before the diff, the same request was issued and the same 403 response completed; it was classified as MarketplaceAuthRequiredError rather than the generic AccessDenied path.; critical-path effect: The request determines whether a manifest can be published. On 403, response body buffering is skipped by \`asJson\` because the status is non-success.
  - IPC at <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryManifestService.ts:updateChannels</code>: Publish the null manifest and cleared authorization to shared-process and optional remote-server channels.; cardinality: One call per available channel after initial resolution, with later calls only when the manifest value changes. Since both old and new 403 handling publish null, cardinality is unchanged.
    - Introduced by diff: false; previous behavior: A 403 already resulted in a null manifest and the same channel publication.; critical-path effect: Channel calls are started after manifest resolution and are not awaited by the startup promise.
- Verdict: No finding. The change alters status classification and UI messaging without adding or amplifying expensive work.

### Scenario 2: User views marketplace access state and optionally invokes sign-in after a denied response

- Critical path: The manifest status event updates context keys and an eventual activity badge. RequiresSignIn previously displayed a sign-in badge/link; AccessDenied displays a warning/contact-administrator message. Authentication begins only if the user explicitly runs the sign-in command, so there is no automatic retry loop on either status.
- Scaling input: One local status transition per completed resolution and a constant number of context-key/badge updates. The number of extension rows or installed extensions does not multiply this work.
- Effective concurrency: Status consumers run synchronously/event-driven with constant work. Sign-in is user initiated and provider-owned; the diff does not schedule concurrent authentication operations.
- Cache behavior: The displayed status is held in memory. No new cache key, invalidation path, positive/negative cache, or retry policy is introduced.
- Mechanism confidence: High: all status consumers and the sign-in action were traced, and sign-in is not automatically invoked from the changed status event.
- Magnitude uncertainty: Activity-service rendering cost is not measured, but both statuses create one constant-size badge and one marketplace-access view; no scaling or hot-loop mechanism exists.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts:ExtensionsGallerySignInAction; src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:signIn</code>: Provider sign-in/session creation and possible protected-resource consent when the user invokes the command.; cardinality: Zero automatically; one provider flow per explicit user command. The changed 403 status removes the normal sign-in affordance for denied users rather than increasing calls.
    - Introduced by diff: false; previous behavior: A 403 was shown as RequiresSignIn, allowing users to invoke the same sign-in command repeatedly. The PR prevents that UX loop, but the loop was user-driven rather than an automatic performance mechanism.; critical-path effect: Off the denied-status rendering path; it runs only after explicit user interaction.
- Verdict: No finding. The UI work remains constant, and the change reduces the opportunity for repeated user-triggered auth work.

### Scenario 3: Extension gallery manifest service regression tests covering 401/403 providers, bearer states, sign-out races, and consent recovery

- Critical path: The added cases run only in the test suite. They instantiate mocked services, execute in-memory streams/events, and await deterministic mocked manifest/account flows.
- Scaling input: Twelve matrix cases are added for 3 providers x 2 token states x 2 statuses, one extra 403 sign-out-race case, and additional assertions in one consent test. This is fixed test cardinality, not product input scaling.
- Effective concurrency: Tests execute under the existing test runner; each case awaits its mocked operations. The consent test uses one event promise and disposes its listener through the suite disposable store.
- Cache behavior: Mocks are recreated/reset according to the suite setup; no production cache behavior is changed by test code.
- Mechanism confidence: High: these hunks are confined to the test file and use mocked request/authentication services.
- Magnitude uncertainty: Runner scheduling is outside the diff context, but the fixed number of lightweight mocked cases does not establish a product performance regression.
- Expensive boundaries: none found
- Verdict: No product performance finding. The fixed test-runtime increase is expected regression coverage.
