# Performance review: Renew marketplace resource tokens before expiry

[PR #343688](https://github.com/microsoft/vscode/pull/343688) at `6169719bb89f432258772297bd9f31797ec24ccd`

## Findings (1)

### 1. [medium] Renew the bearer without refreshing the whole marketplace

**Finding ID:** `PERF-455E8DA8D0EC`  
**Location:** <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:505</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** HTTP authentication/metadata/manifest/update-query requests, IPC calls, installed-extension scans, and Extensions view rendering work  
**Scaling:** The cycle repeats for the lifetime of every signed-in private-marketplace window at each refresh interval (every five minutes for the explicitly supported opaque-token case). Its update-check payload grows with installed extensions, and active-view refresh work grows with the number of visible Extensions panes.  
**Outcome:** recurring excessive network I/O and avoidable Extensions view CPU/rendering work while the window is otherwise idle  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, account resolution and manifest publication ran at initialization or on a real provider/account event; an unchanged signed-in window did not periodically refetch and republish its marketplace manifest.  
**Changed behavior:** The new scheduler invokes handleAccountChange at each token deadline. The manifest service treats that as a full marketplace-account change, resolves the account, rediscovers protected-resource metadata, downloads/parses the service-index manifest, republishes it over process channels, and fires the general manifest-change event.  
**Confidence:** 0.99 — The recurring callback, full call path, two request-service boundaries, IPC fan-out, Extensions view listener, and default-enabled update query are all explicit in repository code. Only deployment prevalence and actual token lifetime are uncertain, which affects severity rather than the mechanism.

**Causal diff evidence:** RIGHT line 505 newly schedules the account-change callback from account.refreshAfter; together with the added five-minute fallback at line 229, this converts the previously event-driven account/manifest path into recurring work even when the account and manifest are unchanged.

In a long-lived Entra private-marketplace window, each renewal causes at least the protected-resource discovery and manifest HTTP work plus shared/remote IPC. If the Extensions view has been created, its manifest listener calls refresh(), which rescans local extensions, reruns visible pane searches, and—with the default extensions.autoCheckUpdates=true—issues a gallery update query for the installed-extension set. Opaque tokens repeat this burst every five minutes and can visibly refresh an open Extensions view.

**Evidence:** The added schedule calls the RunOnceScheduler callback handleAccountChange(). WorkbenchExtensionGalleryManifestService subscribes to onDidChangeAccount and calls handleMarketplaceAccountAccess(), whose Eligible branch calls getExtensionGalleryManifestFromServiceUrl(). MicrosoftGalleryAccountProvider.doGetAccount() also calls discoverProtectedResource(), which uses IRequestService. update() then fires onDidChangeExtensionGalleryManifest; ExtensionsViewlet's listener calls refresh(), and refresh() calls queryLocal(), doSearch(true), and checkForUpdates(). checkForUpdates() calls galleryService.getExtensions(infos, ...) and extensions.autoCheckUpdates defaults to true. The same manifest event also calls setExtensionGalleryManifest over the shared-process and optional remote channels.

**Suggested direction:** Keep renewal on the scheduler, but give it an authorization-only path: reuse the protected-resource metadata and current manifest for the same account/service URL, update the bearer and process snapshots directly, and do not fire the general manifest-change event unless manifest capabilities actually changed. Preserve generation checks and the existing retry/cancellation semantics.

### Scenario 3: Transient resource-token renewal failure and 30-second retry

### Scenario 4: Account/provider/service replacement, sign-out, stale completion, and disposal

- Critical path: Real account/session changes intentionally trigger one fresh account/manifest resolution. Sign-out resolves the base session then retracts authorization without protected-resource or manifest requests. Stale in-flight results are rejected before publication.
- Scaling input: Number of actual account/provider changes, not collection size or window lifetime.
- Effective concurrency: handleAccountChange cancels the scheduled deadline, increments the generation, and clears the coalesced request. Service-URL changes do the same. RunOnceScheduler is registered for disposal. A previously started boundary call may finish, but generation/cancellation checks prevent it from scheduling or publishing stale state.
- Cache behavior: In-flight work is coalesced only within a generation. Provider/account/service replacement invalidates it; disposal cancels the scheduler. No retained timer or unbounded map remains after disposal.
- Mechanism confidence: High; generation checks, cancellation source, scheduler cancellation, and disposal ownership are explicit and tested.
- Magnitude uncertainty: An underlying request may not abort immediately depending on transport, but stale results are bounded to already-started work and cannot recursively reschedule.
- Expensive boundaries:
  - IPC/authentication-provider at <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:245</code>: Resolve session state after a real account/provider event.; cardinality: One coalesced resolution for the new generation; sign-out ends after this lookup.
    - Introduced by diff: false; previous behavior: Actual account changes already required account resolution.; critical-path effect: Determines when sign-out/account-switch state is published.
  - network at <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:303</code>: Discover metadata for an eligible replacement account/service.; cardinality: At most one discovery sequence for the surviving generation.
    - Introduced by diff: false; previous behavior: Eligible account changes already rediscovered access metadata.; critical-path effect: Required only for eligible protected-resource access.
  - network at <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryManifestService.ts:265</code>: Fetch the authenticated manifest for the surviving eligible generation.; cardinality: At most one request; canceled/stale resolution tokens suppress publication.

- Verdict: No cleanup/concurrency finding: cancellation and generation ownership bound stale work and prevent timer leaks or bursts.
