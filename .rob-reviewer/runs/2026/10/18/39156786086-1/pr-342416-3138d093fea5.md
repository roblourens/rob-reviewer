# Performance review: agentHost: exclude external sessions from Mission Control

[PR #342416](https://github.com/microsoft/vscode/pull/342416) at `3138d093fea54d69c9e605a4905b16ca03a80cfe`

## Findings (1)

### 1. [low] Evict summaries that leave the client catalogue

**Finding ID:** `PERF-65A9B1A32925`  
**Location:** <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:2186</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Per-client Set entries and retained session resource strings  
**Scaling:** Retained entries grow with every distinct session ever returned or announced during a connection, multiplied by the number of connected Mission Control clients, rather than with the current effective catalogue (all non-archived sessions plus 100 archived sessions).  
**Outcome:** Long-lived agent hosts retain steadily growing per-client hash tables, increasing heap use and GC pressure as sessions are created and archived.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, protocol clients had no knownSessionSummaries Set, so repeated Mission Control listings did not retain a per-client history of session identifiers.  
**Changed behavior:** Each filtered-listener connection now records every session resource sent by listSessions or sessionAdded and keeps it until the underlying session is explicitly removed or the connection closes.  
**Confidence:** 0.95 — The allocation, insertion sites, sole deletion site, connection lifetime, and 100-item archived rotation are all directly visible in the traced code. Exact heap impact depends on host lifetime, catalogue churn, and client count, so severity is low, but the monotonic retention mechanism is certain.

**Causal diff evidence:** The added loop at lines 2184-2187 inserts every listed resource into client.knownSessionSummaries; the diff only deletes entries on root/sessionRemoved at line 3808. Sessions that merely age out of toMissionControlSessionList's 100-archived-session window are never removed from the Set.

With a persistent Mission Control connection and ongoing session creation/archival, agent-host memory grows linearly with catalogue history; multiple connected clients duplicate the retained hash entries and add GC pressure even though only 100 archived sessions remain listable at a time.

**Evidence:** toMissionControlSessionList returns all non-archived summaries and only the 100 most recently modified archived summaries, so normal archive churn causes different IDs to enter the response over time. The new Set is populated from each response and from sessionAdded, but it is not reconciled against later authoritative list results; root/sessionRemoved is the only per-entry deletion. Thus a persistent connection retains the union of all historical result sets, not the current capped set.

**Suggested direction:** Track only summaries that were suppressed and need an adoption add, or reconcile known entries by list generation while preserving sessionAdded notifications that arrive during the async list computation, so retained state is bounded by the client's current catalogue.
