<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** boundary-fanout, concurrency-burst, cleanup-lifecycle, serialization-allocation, repeated-work

### Scenario 1: A user removes a Copilot steering message after it was sent to the SDK but before the model consumes it.

- Critical path: The host accepts and reduces the removal synchronously; queue-drain calls the provider without awaiting it, so the queue-row removal does not wait for SDK withdrawal. The asynchronous withdrawal awaits the existing send result and then one queue RPC.
- Scaling input: Effective cardinality is the number of distinct handed-off steering messages the user removes. Each removed ID causes at most one withdrawal attempt; normal interactive use is a small manually generated set.
- Effective concurrency: Withdrawals for different IDs or sessions can overlap because the provider hook is fire-and-forget. There is no shared limiter, but each operation is ID-specific and user-action bounded; no loop newly fans one removal into multiple RPCs.
- Cache behavior: No cache participates. Submitted IDs and pending SDK IDs are in-memory lifecycle state; successful withdrawal deletes the pending entry, while abort/disposal drains remaining entries.
- Mechanism confidence: High confidence in the one-RPC-per-removed-ID mechanism and off-critical-path placement from the traced queue-drain, provider, and session call chain.
- Magnitude uncertainty: SDK RPC duration and unusually large prompt sizes are not measured, but operation count is directly bounded by accepted removals and is normally low.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:5675, CopilotAgentSession.withdrawSteering</code>: Calls the Copilot SDK runtime queue withdrawal RPC with the SDK message ID and expected prompt.; cardinality: Exactly one RPC for one removed steering message that has reached session.send; zero if it is still being prepared or no longer pending.
    - Introduced by diff: true; previous behavior: No withdrawal RPC existed; removal was rejected while the turn was active and the already-sent steering remained queued for delivery.; critical-path effect: Off the UI/state-removal critical path because the provider hook discards the returned promise.
- Verdict: No reportable regression. The new boundary is necessary, off the interaction critical path, and has no realistic high-cardinality fan-out or retained-resource growth.

### Scenario 2: A user removes steering while MCP reconciliation or attachment preparation is still running.

- Critical path: Removal immediately deletes the pending steering entry. Preparation already in progress can finish, after which the new identity check prevents session.send; the user-facing removal does not await preparation.
- Scaling input: One MCP reconciliation per steering send attempt, plus one conversion per attachment. Only resource selections perform file reads, scaling with the number and size of selected resources.
- Effective concurrency: MCP reconciliation is serialized by \_mcpEnablementSequencer and server enable/disable changes run sequentially. Attachment conversions use Promise.all, so selected-resource reads can run concurrently per message; this behavior predates the diff.
- Cache behavior: MCP reconciliation reads current SDK state rather than using a new cache. The new pending-map deletion acts as a cancellation marker before SDK send; no negative-cache or coalescing behavior changes.
- Mechanism confidence: High confidence: the changed cancellation check is after unchanged preparation, and the new removal path only deletes map state.
- Magnitude uncertainty: The number and size of selected attachments vary, but the diff neither introduces nor increases this preparation work.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:6153, \_reconcileMcpServerEnablement</code>: Lists configured MCP servers and, when desired state differs, enables or disables affected servers.; cardinality: One list RPC per steering preparation; zero or one sequential control RPC per MCP server requiring a state change.
    - Introduced by diff: false; previous behavior: The same reconciliation ran before every steering send and then the message was sent.; critical-path effect: Already in flight before removal and not awaited by removal; it remains on the steering-send preparation path only.
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:5461 and 5550, \_toSdkAttachments/\_readSelectedText</code>: Reads selected resource contents while converting steering attachments.; cardinality: At most one file read per resource attachment carrying a selection; conversions are launched together with Promise.all.
    - Introduced by diff: false; previous behavior: The same parallel attachment conversion and reads occurred before the SDK send.; critical-path effect: Already-started reads may finish after removal, but removal does not wait for them and the later SDK send is skipped.
- Verdict: No reportable regression. Some pre-existing preparation can continue after removal, but the PR does not add, amplify, or move that work onto the removal critical path and prevents the subsequent SDK send.

### Scenario 3: The SDK reports that removed steering was already delivered, or emits an identical steering message while another withdrawal is pending.

- Critical path: One withdrawal RPC completes with removed:false or overlaps an SDK user.message echo. Echo matching scans pending steering by SDK ID first and falls back to content; turn projection then follows the existing event path.
- Scaling input: CPU matching is linear in currently pending steering entries and can make two passes only when an ID is present but has no exact match. The effective set is the small number of handed-off, not-yet-echoed steering messages.
- Effective concurrency: A withdrawal may overlap an echo by design. Map identity checks prevent the completed withdrawal from deleting a different or already-promoted entry; no repeated RPC is scheduled by the echo.
- Cache behavior: The pending map is cleared on successful withdrawal, matching echo, abort, or disposal. A removed:false result intentionally retains the entry until its authoritative echo or lifecycle cleanup.
- Mechanism confidence: High confidence in map lifecycle, event ordering, and unchanged database boundary from implementation and deterministic overlap tests.
- Magnitude uncertainty: Pending-map size is not hard-capped, but interactive steering production and SDK echo consumption keep realistic cardinality small; no evidence supports material CPU or memory impact from the additional ID pass.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:5675, CopilotAgentSession.withdrawSteering</code>: Attempts the same ID-specific SDK queue withdrawal and receives removed:false when delivery already occurred.; cardinality: One attempt per accepted removal.
    - Introduced by diff: true; previous behavior: No withdrawal attempt occurred; the delivered message was matched by content and promoted.; critical-path effect: Off the removal and echo critical paths except for local map matching; the RPC is asynchronous and the SDK event arrives independently.
  - database at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:7927, user.message handler</code>: Persists the SDK event ID for the projected turn through the existing \_withDatabase call.; cardinality: One existing asynchronous database update per relevant root user.message event.
    - Introduced by diff: false; previous behavior: The same event handler persisted the turn event ID after content-based steering matching.; critical-path effect: Fire-and-forget and unchanged by the diff.
- Verdict: No reportable regression. The extra bounded map pass disambiguates identical messages, while cleanup and boundary cardinality remain controlled.

### Scenario 4: A session provider without steering-withdraw support receives a mid-turn removal request.

- Critical path: AgentService rejects the action before state mutation or queue-drain handling.
- Scaling input: One constant-time provider capability lookup and queued-message lookup per client action; queued-message lookup behavior predates this capability branch.
- Effective concurrency: No asynchronous provider work is launched.
- Cache behavior: No cache or retained state changes.
- Mechanism confidence: High confidence from the AgentService branch and optional provider contract.
- Magnitude uncertainty: None material for performance; this is a local capability check.
- Expensive boundaries: none found
- Verdict: No performance regression; unsupported providers preserve the previous rejection behavior and introduce no new boundary.

**Summary:** Completed the performance pass over all 10 changed files. The PR adds one asynchronous, ID-specific SDK withdrawal RPC only for steering already handed off, prevents SDK send when removal occurs during preparation, and bounds pending state through echo, abort, and disposal cleanup. No high-confidence actionable performance regression was found.
