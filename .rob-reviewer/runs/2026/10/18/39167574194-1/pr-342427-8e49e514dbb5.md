**Relevant issue families:** eager-work, boundary-fanout, serialization-allocation

### Scenario 1: Create or resume a non-ephemeral Copilot session with plugin agents

- Critical path: Session launch calls toSdkSessionCustomAgents while building SDK config, waits for it alongside BYOK and shell-tool setup in Promise.all, then crosses the existing SDK createSession/resumeSession boundary. The diff adds a constant-time boolean resolver and an optional field before that boundary.
- Scaling input: Effective cardinality is the number of agent resources in the already-resolved plugin snapshot; toSdkCustomAgents reads each projected agent once and restricted agents add one boolean each to the existing customAgents array.
- Effective concurrency: Agent files are read sequentially by the existing for loop. The whole projection runs concurrently with BYOK resolution and shell-tool creation; the diff does not change either level of concurrency.
- Cache behavior: The converter has no own cache and rereads each agent file on every non-ephemeral launch; warm behavior may benefit from the file service or OS cache. This behavior, cache keying, and absence of coalescing are unchanged. Ephemeral sessions continue to skip these reads.
- Mechanism confidence: High: the complete changed hunk and launcher call path establish unchanged I/O/concurrency and only O(1) local work per agent plus O(R) small payload growth.
- Magnitude uncertainty: Plugin-agent counts and SDK serialization implementation vary, but the added payload is exactly one boolean property for each restricted agent and no extra call or read.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotPluginConverters.ts:122</code>: Read and parse each plugin agent Markdown file; cardinality: One sequential read per agent resource in the resolved plugin snapshot
    - Introduced by diff: false; previous behavior: The same loop read the same files and parsed the same frontmatter before this diff.; critical-path effect: Must finish before SDK session creation/resumption, although it overlaps independent BYOK and shell-tool work
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:989 and 1006</code>: Send the completed session configuration to the Copilot SDK runtime via createSession or resumeSession; cardinality: One SDK session call per launch attempt; fallback paths are unchanged
    - Introduced by diff: false; previous behavior: The same custom-agent catalog crossed the same SDK boundary; restricted entries simply lacked one boolean field.; critical-path effect: The session cannot become usable until this existing SDK call completes
- Verdict: No reportable regression. The new local computation is constant-time per existing item, introduces no boundary call, and the bounded payload increase is not a meaningful performance mechanism.

### Scenario 2: Run a chat turn where a selected plugin agent may delegate through the task tool

- Critical path: After session setup, the runtime uses the projected custom-agent catalog to decide which siblings are model-invocable. A normal sibling still follows the existing task-tool and model path; a restricted sibling is now rejected before delegated model work.
- Scaling input: The catalog scales with plugin-agent count, while an individual tested delegation targets one sibling. Restricted entries are filtered by the runtime flag rather than triggering extra per-entry work on each turn.
- Effective concurrency: The reviewed integration path issues two turns sequentially. Production task/model concurrency is runtime-owned and unchanged; the new flag only removes restricted agents from delegation eligibility.
- Cache behavior: The custom-agent catalog is established in session configuration and reused by the runtime for turns. No new lookup cache, miss retry, invalidation, or retained collection is introduced.
- Mechanism confidence: High: the added disableModelInvocation field is consumed as a catalog restriction, and the integration change demonstrates allowed delegation succeeds while restricted delegation does not.
- Magnitude uncertainty: Actual model latency and how often agents attempt restricted delegation vary, but that uncertainty only affects the benefit of preventing the call, not the absence of a regression.
- Expensive boundaries:
  - network at <code>Transitive from the task-tool delegation configured by src/vs/platform/agentHost/node/copilot/copilotPluginConverters.ts:160</code>: Invoke the model for the parent turn and, when allowed, delegated subagent execution; cardinality: Existing model work per chat turn plus delegated work only for an allowed sibling; restricted siblings no longer proceed to delegated execution
    - Introduced by diff: false; previous behavior: The missing runtime restriction could allow a restricted sibling onto the existing delegated model path; this diff adds no new model or network call.; critical-path effect: Allowed delegation remains on the turn critical path; for restricted siblings the diff prevents rather than adds downstream model work
- Verdict: No performance regression. The change can avoid unintended delegated model work and does not increase turn-time boundary cardinality.

### Scenario 3: Synchronize and publish plugin customizations before launching a session

- Critical path: Active-client plugin synchronization parses plugin directories and publishes child customizations before snapshots feed session launch. The changed converter module is already reached from the Copilot agent, which already imports pluginParsers at runtime.
- Scaling input: Work scales with plugin directories and their resources, as before; resolving the new flag during later SDK projection is constant-time per agent.
- Effective concurrency: Plugin parsing concurrency and synchronization sequencing are unchanged by the diff.
- Cache behavior: Resolved plugin snapshots are reused for catalog metadata, while the later agent prompt projection still rereads files as before. No cache state or lifecycle changes.
- Mechanism confidence: High: imports and call sites show pluginParsers was already a runtime dependency of the owning Copilot agent and the diff adds no top-level I/O or eager initialization.
- Magnitude uncertainty: Exact plugin resource counts vary; no changed operation scales beyond the existing one boolean computation per projected agent.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:9384</code>: Parse plugin manifests, directories, and agent files into the active snapshot; cardinality: Existing parsing per synchronized plugin and discovered resource
    - Introduced by diff: false; previous behavior: Copilot agent and discovery code already imported and invoked pluginParsers; the new converter value import does not introduce plugin scanning or file reads.; critical-path effect: Synchronization must resolve before the updated plugin snapshot is published and used for launch
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts plugin synchronization flow</code>: Publish active-client customization state and receive session actions; cardinality: Existing state publication per customization update
    - Introduced by diff: false; previous behavior: The same customization state crossed the same protocol boundary.; critical-path effect: Required for the client-visible synchronized catalog, but the new boolean resolver does not add messages
- Verdict: No eager-load or boundary-fanout regression. The runtime import reuses an already-loaded dependency on the owning product path and the helper has no side effects.

**Summary:** Completed the performance pass over all three changed files and traced session launch, plugin synchronization, SDK configuration transport, and delegated-agent execution. No high-confidence, diff-introduced performance issue was found.
