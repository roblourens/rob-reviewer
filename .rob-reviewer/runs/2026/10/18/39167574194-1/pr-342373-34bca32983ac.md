### Scenario 2: A steering message finishes preparation after its target turn has ended and is recovered as the next turn

- Critical path: The original attempt completes its existing MCP reconciliation and attachment conversion, detects the turn change before SDK dispatch, resolves false, and queue drain admits the pending message as a normal next turn. Normal turn admission then resolves the workspace, captures any enabled checkpoint, resolves attachments/contributions, and sends the message to the provider.
- Scaling input: The number of steering messages arriving in the narrow end-of-turn race. One message starts the recovered turn; remaining messages are coalesced into steering for that turn rather than causing per-message full-turn fan-out.
- Effective concurrency: Only one recovered turn is admitted because \_tryConsumeNextQueuedMessage returns while any turn is active. Additional late steering messages are handed to the newly active turn rather than each starting a full turn. Checkpoint capture may overlap normal provider preparation, as on every ordinary turn.
- Cache behavior: The existing live session and provider state are reused when warm. There is no negative cache for a missed turn; instead, the false result is an explicit ownership handback. Submitted-steering mementos are cleared for the returned ID and centrally evicted with the chat.
- Mechanism confidence: High: tests and call flow establish the false handback, active-turn guard, one admission, and steering of remaining messages into the new turn.
- Magnitude uncertainty: The race is timing-dependent, and workspace/checkpoint/provider latency varies with repository size and environment. These costs are real but occur only to execute a user message that previously never ran.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:sendSteering</code>: Perform the initial Copilot MCP reconciliation before discovering that the targeted turn ended.; cardinality: One initial reconciliation per handed-off steering message; this work already occurred before the PR even when the message was dropped.
    - Introduced by diff: false; previous behavior: The same preparation ran, then the message was consumed/dropped when the turn-change check skipped SDK dispatch.; critical-path effect: It delays the false handback and therefore the recovered turn, but was already on the original steering path.

  - filesystem at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:\_sendTurnMessage</code>: Resolve the working directory and capture the standard turn-start checkpoint for a recovered non-ephemeral turn.; cardinality: One workspace resolution and at most one checkpoint capture for the single recovered turn.

### Scenario 3: A message is handed back after another turn has already started

- Critical path: The promise callback removes the message ID from the submitted set and synchronizes pending messages. Because a turn is active, the same pending message is offered to that turn and follows the normal steering preparation path.
- Scaling input: Number of end-of-turn races a single pending message encounters before reaching a stable active turn; normally zero or one because only one turn can be active per chat.
- Effective concurrency: The submitted-ID memento prevents duplicate handoff while an attempt is held. A returned message is retried once against the currently active turn; any concurrent pending messages retain their own existing handoff state, and MCP reconciliation remains sequenced.
- Cache behavior: No preparation cache is added; attachment and MCP preparation are repeated because the authoritative target turn changed. Submitted and in-flight sets provide deduplication and are pruned when queue state changes or the chat is disposed.
- Mechanism confidence: High for the retry mechanism and boundaries; lower prevalence does not affect the traced path.
- Magnitude uncertainty: Repeated races are possible but require successive turns to end during preparation; practical frequency and attachment sizes are uncertain.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:sendSteering</code>: Repeat Copilot MCP reconciliation for the retry against the newer active turn.; cardinality: One additional attempt for the handed-back message per intervening active turn that wins the race; duplicate dispatch within the same held attempt is suppressed by submitted and in-flight sets.
    - Introduced by diff: true; previous behavior: The original attempt's skipped result was ignored and the message was consumed, so it was not retried.; critical-path effect: The retry must prepare before it can steer the newer turn.
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_toSdkAttachments</code>: Reconvert selected-resource attachments for the retry.; cardinality: At most one read per selected-resource attachment on each actual retry.
    - Introduced by diff: true; previous behavior: No retry conversion occurred because the message was dropped.; critical-path effect: Attachment conversion precedes the retried SDK send.
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:sendSteering</code>: Send the handed-back message as immediate steering to the newer active Copilot turn.; cardinality: One SDK send when the retry's turn remains current.
    - Introduced by diff: true; previous behavior: No second delivery attempt occurred.; critical-path effect: This delivers the pending user request without creating another full turn.
- Verdict: No actionable performance issue: the retry is bounded by turn transitions, deduplicated while held, and is required to deliver the message rather than silently discard it.

### Scenario 4: Held steering settles while the chat is idle, including cancellation and another handed-back message waiting

- Critical path: A successful settlement checks current chat state and only invokes queue draining if steering is still pending. Queue drain waits while any pending steering ID is still held; after the last held item settles, it admits the first unheld steering message. Cancellation removes pending steering and the submitted memento first, so later promise callbacks do no expensive work.
- Scaling input: Number of simultaneously pending steering handoffs in one chat; state checks scan that collection, which is driven by explicit user messages and normally small.
- Effective concurrency: Settlement callbacks may arrive independently, but the submitted-set check and active-turn guard serialize actual turn admission. Cancellation prevents post-cancel admission.
- Cache behavior: Submitted IDs are pruned against current pending IDs, deleted on cancellation, and all chat mementos are centrally evicted on chat/session disposal. No stale negative state is cached.
- Mechanism confidence: High: cleanup, cancellation, and admission guards are explicit in the changed code and surrounding memento lifecycle.
- Magnitude uncertainty: Very large pending sets are not evidenced by the product workflow. Exact callback ordering varies, but admission remains guarded.
- Expensive boundaries:
  - other at <code>src/vs/platform/agentHost/node/chatContributions/queueDrain/queueDrainContribution.ts:\_onSteeringHandoffSettled/\_tryConsumeNextQueuedMessage</code>: Scan pending steering and submitted IDs, then optionally admit one recovered turn.; cardinality: One bounded state check per settling handoff; at most one admission when no held steering remains.
    - Introduced by diff: true; previous behavior: Asynchronous handoff settlement was not observed, so no follow-up drain occurred.; critical-path effect: The state scan is synchronous and small; any admitted turn follows the normal expensive boundaries described above.
- Verdict: No performance regression: callbacks add small per-handoff state scans, preserve cleanup, and do not create concurrent turn bursts or unbounded retained state.

**Summary:** Completed the performance review over all nine changed files. The PR adds ownership handback and queue-drain scheduling for late steering. It newly reaches normal turn setup and provider-send boundaries only to execute messages that were previously dropped or stuck; one-active-turn gating, submitted-ID deduplication, MCP sequencing, cancellation cleanup, and chat-scoped memento eviction bound the work. No high-confidence actionable performance regression was found.
