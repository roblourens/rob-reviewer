- Scaling input: Scales with admitted API operations and pagination pages. Each operation carries one allowlisted scalar domain; pagination continues to issue the same number of pages as before. In-flight sharing reduces identical concurrent reads to one admitted network operation, as before.
- Effective concurrency: The existing RequestQueue still bounds aggregate active requests at 12, host requests at 12, account requests at 10, and caller requests at 8. Domain metadata neither creates tasks nor changes queue lanes or limits.
- Cache behavior: REST ETag cache keys and REST/GraphQL in-flight coalescing keys explicitly omit domain, so cold misses, warm revalidation, and identical-read coalescing are unchanged. Domain is attribution only; it creates no positive or negative cache.
- Mechanism confidence: High: transport key builders, queue limits, provider forwarding, and completion accounting were traced directly.
- Magnitude uncertainty: Exact API request volume varies by workflow, but the changed per-operation work is bounded by 18 allowlisted domains and is negligible relative to the unchanged IPC/network operation.

### Scenario 2: Ten-minute GitHub request telemetry aggregation and service-disposal flush

- Critical path: Normal flushes run on the collector timer and are off individual API request critical paths. Disposal synchronously invokes the same bounded flush during service shutdown.
- Scaling input: Per-request aggregation scales linearly with completed admitted operations but updates only one of at most 18 domain entries. Flush cardinality is capped at one engine summary, at most 18 domain summaries, and at most 10 timing samples.
- Effective concurrency: Flush emits summaries sequentially in one loop; there is no concurrency burst. One timer exists per GitHubService collector and is reset after each active interval.
- Cache behavior: No cache is involved. Aggregates are reset after each flush or telemetry opt-out; the domain Map is bounded by the fixed allowlist and does not retain values across windows.
- Mechanism confidence: High: the fixed 18-domain allowlist, reset lifecycle, timer interval, and sequential publicLog2 calls are explicit in the changed collector.
- Magnitude uncertainty: Appender implementation and downstream batching vary by host, but event count is hard-capped and occurs no more than once per active ten-minute window or disposal.
- Expensive boundaries:
  - other at <code>src/vs/platform/github/common/githubRequestTelemetry.ts GitHubRequestTelemetry.flush</code>: Pass telemetry events synchronously to the configured telemetry service and its appenders; downstream transport may later upload them.; cardinality: Previously at most 11 events per active ten-minute interval; now at most 29, with only domains that completed work or had rejection counters emitted.
    - Introduced by diff: true; previous behavior: One summary and up to ten timing samples were emitted; no per-domain summaries existed.; critical-path effect: Timer-driven emission is off API request critical paths; disposal emission is bounded shutdown work.
- Verdict: No reportable regression: the intentional boundary fan-out is strictly bounded, infrequent, and off the user-facing request critical path; retained state is bounded and cleared.

**Summary:** Reviewed all 31 changed files and all diff pages. The change adds fixed domain attribution through existing request paths and bounded per-domain telemetry aggregation. It does not alter network/IPC cardinality, queue concurrency, ETag caching, or in-flight coalescing. The only new boundary fan-out is capped telemetry emission once per active ten-minute window, which does not establish a concrete user-visible performance regression.
