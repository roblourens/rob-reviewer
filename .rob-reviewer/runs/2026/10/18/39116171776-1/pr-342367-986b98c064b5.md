# Performance review: github: migrate browser plugin downloads to shared clients

[PR #342367](https://github.com/microsoft/vscode/pull/342367) at `986b98c064b59effd5638af86111dc78cba1f74a`

## Findings (1)

### 1. [high] Reuse the authenticated credential across blob downloads

**Finding ID:** `PERF-60429D847DC9`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/githubRepoFetcher.ts:97</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** authentication-provider calls and workbench-to-extension-host RPC messages  
**Scaling:** For a repository with F supported blob entries, the extraction now performs F credential lookups (up to 10 concurrently) in addition to the initial session/client lookups; the cost grows linearly with repository file count even when the GitHub credential generation is already resolved.  
**Outcome:** increased install latency and extension-host IPC/CPU pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The browser plugin service called getExistingGitHubAuthenticationToken once, then passed that captured token through resolveGitHubRefToSha, fetchGitHubTree, and every fetchGitHubBlob request, so repository size did not increase authentication-provider calls.  
**Changed behavior:** Each added content.getBlob call now goes through ContentClient -&gt; LocalApiRequestProvider.execute -&gt; credentials.getCredential. GitHubCredentialService.getCredential invokes credentialProvider.getToken before reusing its current generation; WorkbenchGitHubCredentialProvider.getToken calls authenticationService.getSessions, which delegates to the registered provider and, for the GitHub extension provider, crosses MainThreadAuthenticationProvider.$getSessions RPC.  
**Confidence:** 0.98 — The changed loop, full credential call path, uncached AuthenticationService.getSessions implementation, and extension-host RPC are all directly visible. Repository file count and the old single-token behavior are explicit; only the exact per-call provider duration varies by environment.

**Causal diff evidence:** The added per-entry call at githubRepoFetcher.ts:97 replaces fetchGitHubBlob(..., authToken, ...), while pluginGitCommandService.ts changed from capturing one access token to acquiring an account API client. This places credential-provider resolution inside the existing blobsToFetch.map loop.

Installing or updating an authenticated browser plugin repository with tens or hundreds of files repeatedly invokes the GitHub authentication provider on the install critical path, increasing latency and potentially saturating the web extension host; larger repositories amplify the overhead one call per file.

**Evidence:** fetchAndExtractGitHubRepo queues one content.getBlob at this line for every blob entry. LocalApiRequestProvider.execute always awaits credentials.getCredential; GitHubCredentialService.getCredential always calls its token provider even when \_current already holds the same token; WorkbenchGitHubCredentialProvider.getToken resolves the session via AuthenticationService.getSessions, and MainThreadAuthenticationProvider.getSessions calls the extension-host $getSessions RPC. The limiter permits 10 such lookups concurrently. The deleted implementation passed one authToken directly to all blob requests.

**Suggested direction:** Keep credentials broker-owned but resolve/cache one validated credential for the account-client lease (invalidating it on onDidChangeToken/onDidInvalidate), so ref/tree/blob requests reuse it. Alternatively add an operation-scoped credential lease; do not invoke the authentication provider separately for each blob.

### Scenario 2: Existing batched GitHub reads such as Agent Host issue enrichment and Mission Control batches

- Critical path: Each scenario submits typed reads to the shared queue; network responses are required before enrichment or task results progress. Queue admission and any shared rate-limit cooldown are on the path.
- Scaling input: Up to ten issue references per title generation, potentially across two concurrent generations; Mission Control and other clients can submit retained batches up to existing 64-account/caller caps.
- Effective concurrency: Defaults change from 4 global/2 host/1 account/2 caller to 12 global/12 host/10 account/8 caller. Tests establish eight active same-caller issue reads and eight simultaneous same-account rate-limit responses.
- Cache behavior: Equivalent reads still coalesce and ETag-cache under existing limits; cooldown state is shared after a response establishes it. Cold independent URLs do not coalesce; warm ETag reads still perform conditional network requests.
- Mechanism confidence: High for changed concurrency and wire cardinality, but insufficient evidence of net user-visible degradation under normal workloads.
- Magnitude uncertainty: The frequency and server impact of simultaneous throttle responses are deployment-dependent; healthy-path latency improves and all limits remain bounded.
- Expensive boundaries:
  - network at <code>src/vs/platform/github/common/requestQueue.ts:31-34</code>: Execute batched GitHub REST requests.; cardinality: Logical request count is unchanged, but up to 8 requests from one caller and 10 from one account can now be in flight instead of 2 and 1 respectively.

- Verdict: No separate finding: this is an explicit bounded scheduling tradeoff with direct healthy-path latency benefit; the diff does not establish a distinct user-visible regression beyond the reported credential fan-out.

### Scenario 3: Browser read of a renamed GitHub repository through an opaque redirect

- Critical path: On a cold old repository URL, the manual browser fetch returns opaqueredirect and a sanitized native-follow fetch must complete and validate its final URL before body processing. A remembered canonical URL lets later reads make one normal manual fetch.
- Scaling input: One fallback per distinct redirected initial URL per transport lifetime; browser-internal hop count is bounded by the browser and response size remains capped at 16 MiB.
- Effective concurrency: Both attempts occupy the same admitted request task sequentially; retries remain at most one transient retry per attempt, and queue limits apply to the logical request.
- Cache behavior: The final URL is memoized in the transport redirect map and normal ETag caching resumes at that URL. Transport disposal clears redirects; authenticated per-operation plugin clients are disposed after use.
- Mechanism confidence: High.
- Magnitude uncertainty: Renamed-repository prevalence is unknown, but cold/warm request counts and lifetime are explicit.
- Expensive boundaries:
  - network at <code>src/vs/platform/github/common/githubTransport.ts:881-899</code>: Manual fetch followed by one browser-native redirect-follow fetch for an opaque repository redirect.; cardinality: Two fetch attempts on the first opaque redirect; subsequent reads use the canonical URL and normally issue one fetch.
    - Introduced by diff: true; previous behavior: Browser opaque redirects failed after the manual attempt, so the newly added second fetch enables a previously unsuccessful scenario rather than slowing a successful one.; critical-path effect: Both cold attempts are required before a renamed repository read succeeds.
- Verdict: No finding: the extra cold request is necessary to make the previously failing browser scenario work and is memoized for warm reads.

### Scenario 4: Typed noCache tree/blob and Mission Control reads through local or IPC providers

- Critical path: Request parsing, provider forwarding, queue admission, network response, bounded body parsing, and IPC return must finish before the typed read completes.
- Scaling input: One operation per typed call after in-flight coalescing; plugin tree/blob count follows repository size.
- Effective concurrency: Same shared queue limits apply. noCache calls coalesce only with compatible noCache calls, preventing cache-policy mixing.
- Cache behavior: noCache=true omits validators and prevents response-cache writes without clearing an existing representation; false/undefined preserves ETag reads and writes. Blob/tree noCache avoids retaining large encoded bodies.
- Mechanism confidence: High.
- Magnitude uncertainty: Exact encoded blob sizes vary, but response size is bounded and avoiding retention is favorable.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/github/common/client/request.ts:175 and local providers</code>: Validate and forward ApiRequestOptions.noCache through local/IPC request providers.; cardinality: Once per typed request.
    - Introduced by diff: true; previous behavior: Typed requests always used normal ETag policy.; critical-path effect: Small bounded option parsing is on the request path; body serialization/parsing was already required.
  - network at <code>src/vs/platform/github/common/client/localApiRequestProvider.ts:73</code>: Fetch without conditional validators when noCache is true.; cardinality: One network call per cache-bypassing logical read after compatible in-flight coalescing.
    - Introduced by diff: true; previous behavior: Shared typed clients normally revalidated cached responses, while the migrated plugin's old direct request path did not use this shared ETag body cache.; critical-path effect: Avoids cache body retention while preserving the network work the prior plugin IRequestService implementation already performed.
- Verdict: No finding: the policy deliberately prevents large tree/blob response retention and preserves compatible coalescing; it does not add network cardinality relative to the old plugin path.
