- Effective concurrency: Workflow steps are serial on one runner. Agent Host runner concurrency remains bounded by its existing jobs value (at most six workers); each worker owns one suite subprocess at a time. Remaining node and extension-host integration suites retain their existing script sequencing.
- Cache behavior: Both steps share the same allocated runner workspace, installed node\_modules, compiled output, and Electron installation. prepareTestRuntime performs the same existence/version checks as before; a cold missing dependency/Electron can still trigger npm/electron setup, while warm CI state avoids it. The step boundary neither invalidates nor duplicates these caches.
- Mechanism confidence: High: the old script order and new workflow order both invoke the Agent Host runner once before the same remaining suites, and the new skip flag explicitly prevents duplication.

### Scenario 2: Electron integration CI when change detection marks Agent Host E2E unaffected

- Critical path: Change detection completes, the new Agent Host step is skipped, and the remaining integration script runs once with VSCODE\_SKIP\_AGENT\_HOST\_E2E=1. Before the PR, that same script ran once and skipped its embedded Agent Host invocation using the same detection result.
- Scaling input: The ordinary Node and extension integration suite collection; Agent Host effective cardinality is zero.
- Effective concurrency: No Agent Host workers are created. The remaining script retains its existing suite sequencing on each platform job.
- Cache behavior: The runner workspace and Electron setup are unchanged. No Agent Host preparation or optional downloads are reached in either version when detection is definitively false.
- Mechanism confidence: High: the workflow conditions and constant skip environment establish the same effective work.
- Magnitude uncertainty: Suite duration varies, but there is no uncertain changed multiplicity: Agent Host remains zero and the remainder remains one invocation.
- Expensive boundaries:
  - subprocess at <code>.github/workflows/pr-linux-test.yml:Run integration tests (Electron) (equivalent Darwin/Win32 steps)</code>: The remaining integration script launches Node and Electron extension integration suites.; cardinality: One script invocation per platform job and one execution of the pre-existing selected suites.
    - Introduced by diff: false; previous behavior: The workflow invoked the same integration script once; its environment caused the Agent Host block to be skipped before running these suites.; critical-path effect: This is the Electron integration critical path after the Agent Host step is skipped.
- Verdict: No reportable regression; unaffected changes retain the prior skip behavior and expensive-work cardinality.

### Scenario 3: Electron integration CI when Agent Host E2E fails

- Critical path: The Agent Host runner completes its existing bounded fan-out and reports failure. The new status-aware condition then deliberately runs the full remaining integration script, so final job completion waits for those suites; previously test-integration.sh/.bat exited after the failed runner and did not reach them.
- Scaling input: One failed Agent Host run plus the complete remaining Node and extension-host integration collection. The extra work scales with the number and duration of those remaining suites, not with Agent Host item count.
- Effective concurrency: Agent Host workers remain capped at six and finish first. The newly reached remaining integration script is serial with that phase rather than concurrent, so there is no aggregate process burst across the two phases.
- Cache behavior: The remainder reuses the same workspace and Electron installation. It does not rerun Agent Host because the skip flag is fixed to 1; no new cache or unbounded retained state is introduced.
- Mechanism confidence: High: the changed condition explicitly admits the integration step when agent-host-e2e.outcome is failure, and the old scripts exited before subsequent suites on a nonzero runner result.
- Magnitude uncertainty: Failure frequency and exact added minutes are workload-dependent; the upper bound is the explicit 20-minute timeout. The extra boundary work itself is certain.
- Expensive boundaries:
  - subprocess at <code>.github/workflows/pr-linux-test.yml:359 (equivalent Darwin/Win32 integration-step condition)</code>: After an Agent Host failure, launch the remaining Node integration and extension-host/Electron test processes.; cardinality: One additional integration-script invocation on this failure path, reaching each remaining selected suite once.
    - Introduced by diff: true; previous behavior: The enclosing integration script stopped immediately after the Agent Host runner returned nonzero, so these later suites were not executed in that job.; critical-path effect: Newly extends failing-job completion until the independent suites finish, bounded by the existing 20-minute step timeout.
- Verdict: No finding. This bounded failing-path latency and runner consumption is the explicit product behavior of collecting independent suite results after an Agent Host failure, not accidental duplicate work; removing it would defeat the stated reporting semantics, and successful-run throughput is unchanged.

**Summary:** Completed the performance pass over all seven changed files and traced the changed CI paths through test selection, runner preparation, subprocess fan-out, cache behavior, and failure scheduling. No high-confidence actionable performance regression was found; the only added expensive work occurs intentionally after Agent Host failures to collect the remaining suite results and is bounded by the existing timeout.
