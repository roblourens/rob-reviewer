### Scenario 1: Complete an idle saved-chat continuation while a live source has a debounced turn-summary change

- Critical path: The renderer has already created/loaded and opened the Copilot destination before awaiting completeSavedChatContinuation. The RPC completion path waits for source residency release, now synchronously emits the pending summary, waits for its catalog synchronization, waits for source/destination peer-chat stores, then performs existing saved-history/database validation and archive persistence. The moved catalog write is on the RPC's completion-state path but not on the destination-opening path.
- Scaling input: One source session per request. The newly awaited synchronization serializes the source summary/catalog, whose work scales with that session's chat collection; it is not multiplied across all sessions. Saved-history and public-chat scans are pre-existing.
- Effective concurrency: Continuation attempts are serialized by source key in \_savedChatContinuations. Catalog writes are serialized and trailing-coalesced per source in \_backgroundCatalogStateWrites; peer-chat operations are awaited for only source and destination. Different sessions can proceed independently, unchanged by the diff.
- Cache behavior: SessionSummaryNotifier's dirty set and 100 ms scheduler are the relevant coalescing state. The diff consumes only an existing dirty entry; clean sessions do no new work. There is no new cache, key retention, negative-cache state, or changed cold/warm lookup behavior.
- Mechanism confidence: High confidence in call path, cardinality, ordering, and boundary placement from the changed line, synchronous notifier listener, per-session writer, renderer caller, and persistence implementation.
- Magnitude uncertainty: Local database synchronization duration varies by storage and catalog size, but this is one already-scheduled write moved earlier rather than a new recurring operation, and destination presentation has already completed.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:1719 and src/vs/platform/agentHost/node/protocolServerHandler.ts:3126</code>: JSON-RPC vscode/completeSavedChatContinuation request from renderer to agent host; cardinality: One request per continuation attempt

### Scenario 2: Attempt continuation while the live source is busy, then retry after its turn completes

- Critical path: Each per-source attempt is serialized. The busy attempt now flushes and awaits the turn-start summary write before existing continuation validation returns archived:false; after turn completion, the retry flushes and awaits the turn-complete summary before existing archive work. Destination UI presentation precedes the initial completion RPC.
- Scaling input: Number of user continuation attempts for one source and that source's public chats. The changed work does not fan out per turn or across sessions; effective cardinality is one pending summary synchronization per dirty attempt.
- Effective concurrency: Same-source attempts queue behind \_savedChatContinuations, and source catalog writes serialize/coalesce. No new burst is introduced; cross-session independence is unchanged.
- Cache behavior: Turn-start and turn-complete updates share the notifier dirty set but are separated by an awaited attempt in this scenario. A clean retry makes flushPendingSessionSummary a no-op. No retained keys or miss retries are introduced.
- Mechanism confidence: High confidence that the busy path awaits the moved write and remains per-session serialized; lower certainty only concerns local write duration and how often users continue a still-running saved source.
- Magnitude uncertainty: A busy attempt can now await a local catalog write that previously completed in the background, but the write was already guaranteed by the turn-summary debounce, this workflow is one-shot and post-presentation, and evidence does not establish user-visible latency or increased total I/O.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:1930 via onDidChangeSessionSummary and \_queueCatalogSync</code>: Catalog synchronization triggered by flushing the dirty turn-start or turn-complete summary; cardinality: At most one forced source-session write per attempt when dirty; repeated same-source attempts serialize, and writes coalesce per session
    - Introduced by diff: true; previous behavior: The turn summary still caused the same asynchronous catalog write after the debounce, but a completion attempt could return before it was queued.; critical-path effect: Awaited by the completion attempt instead of occurring after the debounce
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostSavedChatService.ts:160-205 and src/vs/platform/agentHost/node/agentService.ts:1950-2020</code>: Existing saved-history reads, destination catalog checks, continuation receipt update, and archive metadata synchronization on the successful retry; cardinality: One bounded operation sequence per attempt; successful aggregate decisions scale with public chats
    - Introduced by diff: false; previous behavior: The same attempt and retry operations existed before the diff.; critical-path effect: Existing awaited completion work; the busy attempt avoids archive persistence but still records/validates the continuation
- Verdict: No finding. The diff changes timing but not total boundary-call cardinality, and the bounded post-presentation delay is insufficient to establish an actionable performance regression.

### Scenario 3: Complete a cold surfaced or clean live saved-chat continuation with no pending summary

- Critical path: flushPendingSessionSummary checks the notifier dirty set and returns synchronously. Existing peer-store waits, saved-chat reads, receipt persistence, and archive synchronization remain the only expensive work.
- Scaling input: One source continuation; existing work scales with saved history and public chats. The added dirty-set lookup is constant time.
- Effective concurrency: Per-source completion serialization and existing database coordination are unchanged.
- Cache behavior: Cold surfaced sessions have no live summary dirty entry, and clean live sessions have no pending entry, so the new method performs no persistence or serialization. No cache lifecycle changes.
- Mechanism confidence: High.
- Magnitude uncertainty: None material for the changed mechanism; it is a constant-time Set lookup.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostSavedChatService.ts and src/vs/platform/agentHost/node/agentService.ts:\_archiveSavedChatContinuation</code>: Existing saved-chat history/metadata reads and archive writes; cardinality: One source/destination completion sequence, with pre-existing public-chat-dependent validation
    - Introduced by diff: false; previous behavior: Unchanged.; critical-path effect: Awaited by the continuation RPC
- Verdict: No performance regression.
