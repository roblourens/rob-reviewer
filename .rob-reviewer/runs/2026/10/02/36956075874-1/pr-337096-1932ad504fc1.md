## Findings (1)

### 1. [medium] Fold Fusion correlation into the existing restore pass

**Finding ID:** `PERF-47D303E015D7`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/mapSessionEvents.ts:425</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and temporary Map/Set entries for persisted user messages and SDK turns  
**Scaling:** Each restore now walks the full event array two additional times (2N checks) and retains O(T) correlation entries, where N is the complete persisted event count and T is the number of root requests/SDK turns; this cost is paid even when the log contains no Fusion events.  
**Outcome:** Increased historical-session open/resume latency plus additional CPU and GC pressure on long event logs  
**PR causality:** <code>introduced</code>  
**Previous behavior:** \`mapSessionEvents\` already preprocessed the event array for names/tool metadata and then reconstructed it in its main pass; there was no additional pair of Fusion-correlation scans or request/turn correlation maps.  
**Changed behavior:** Every call now builds Fusion replay correlation by scanning the complete history twice before the existing main pass, regardless of whether the session ever used HydraFusion.  
**Confidence:** 0.98 — The two added loops, their placement after \`getEvents()\` and before mapping completes, and their all-session reachability are explicit in code. Exact milliseconds depend on event-log size and hardware, which affects severity but not the mechanism.

**Causal diff evidence:** The added \`new FusionReplayState(events)\` at line 425 synchronously invokes a constructor that loops over \`events\` twice (copilotFusionReplay.ts lines 28-56) before the existing reconstruction pass.

Opening or resuming a Copilot session with a realistically long persisted event log does two avoidable extra full-history passes before any restored conversation can be shown; ordinary non-Fusion sessions pay the same regression.

**Evidence:** \`CopilotAgentSession.\_computeMappedEvents\` awaits \`session.getEvents()\` and then awaits \`mapSessionEvents\` before restored messages are available, so this synchronous work is on the session-open critical path. \`mapSessionEvents\` already has preprocessing loops at lines 338 and 348 and its reconstruction loop at line 503; \`FusionReplayState(events)\` adds constructor loops at lines 28 and 40. The repository also has \`mapSessionEvents.perf.test.ts\` specifically benchmarking this history-restoration path, corroborating that full-log mapping is performance-sensitive.

**Suggested direction:** Collect the request/interaction/SDK-turn correlation while one of \`mapSessionEvents\`' existing preprocessing passes is already visiting events and pass the resulting index into \`FusionReplayState\`. Keep Fusion replay state lazy/empty for histories with no Fusion events rather than rescanning all events in its constructor.
