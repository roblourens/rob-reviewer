### Scenario 1: Create a new Agent Host session with settings-derived worktree configuration

- Critical path: Schema discovery must complete before the draft config is ready; eager createSession then uses the resolved values. The diff changes which values survive filtering but does not add a new API stage.
- Scaling input: Number and size of advertised config values, principally a branch prefix and user-configured include/symlink pattern arrays; no collection-to-request fan-out is introduced.
- Effective concurrency: Configuration discovery and any follow-up resolution are awaited serially per draft. Eager create is one task per NewSession; the diff adds no parallel fan-out.
- Cache behavior: The resolved schema and values are retained on NewSession. Discovery is cold per new draft; subsequent reads use the cached result. No changed cache key or negative-cache behavior.
- Mechanism confidence: High confidence that payloads are richer while request cardinality and serialization points are unchanged.
- Magnitude uncertainty: Provider-specific readOnly values can vary, but repository-defined values are small and bounded in normal use; exact IPC serialization cost is not measured.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:3164 NewSession.resolveConfig</code>: Resolve the provider schema/config, with an optional second resolve when seeded values differ from discovered values.; cardinality: One discovery request and at most one follow-up request per draft resolution.

- Verdict: No reportable regression: the extra serialization is proportional to the existing config payload and restores settings explicitly configured for session creation without adding boundary calls or unbounded retained state.

### Scenario 2: Send the first prompt for a worktree-isolated session after folder settings load

- Critical path: The provider re-reads three settings-derived values before sending. On the host, first-send worktree materialization performs git checkout and then configured symlink/copy work before the turn can start.
- Scaling input: Effective matched ignored files and folders after user-configured patterns; one worktree per session and no repeated execution after materialization.
- Effective concurrency: Worktree creation is sequenced per repository. Symlink and include-file operations use limiters of 15, and materialization is cached by session ID so re-entry reuses the worktree.
- Cache behavior: The materialized worktree map is the warm cache and avoids repeated creation/copy work for the session. Empty settings clear prior carriers; there is no negative-cache loop introduced.
- Mechanism confidence: High confidence in the filesystem/subprocess path, its first-send placement, limiter, and one-time lifecycle.
- Magnitude uncertainty: Copy duration depends on user-selected files and repository size, but this is explicitly requested worktree behavior rather than accidental fan-out.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:6463 \_sendNewSessionRequest</code>: Send updated session config and the first chat request through the existing session path.; cardinality: At most one settings refresh over three fixed keys immediately before the first send; only changed values are written.
    - Introduced by diff: false; previous behavior: The refresh existed, but skipped readOnly worktree carrier properties.; critical-path effect: The refresh is synchronous in-memory work; subsequent existing config/send dispatches carry the corrected values.
  - subprocess at <code>src/vs/platform/agentHost/node/shared/worktreeIsolation.ts:922 resolveWorkingDirectory</code>: Run git repository discovery, optional fetch, and git worktree add.; cardinality: One materialization per worktree session; branch/worktree creation is sequenced per repository.

  - filesystem at <code>src/vs/platform/agentHost/node/shared/worktreeIsolation.ts:1022 resolveWorkingDirectory</code>: Resolve configured patterns, create symlinks, and copy matched ignored files into the new worktree.; cardinality: One pass per new worktree; work scales with configured patterns and effective matched files/folders, with 15 concurrent operations.

- Verdict: No reportable regression: the newly reachable file operations are the intended semantics of git.worktreeIncludeFiles and git.worktreeSymlinkFolders, are user-configured, bounded to one materialization, and concurrency-limited.

### Scenario 3: Open and filter a dynamic session-config picker, including a remote Agent Host

- Critical path: Opening a dynamic picker awaits one completions request; non-branch filtering waits for a 200 ms Delayer and then awaits another request. Branch items are loaded once for the picker and filtered locally.
- Scaling input: Number of coalesced filter queries and byte size of retained readOnly config. The built-in shell initializer produces one script described as a few hundred bytes, has a 64 KiB validation cap, and is not published in remote-development windows.
- Effective concurrency: The 200 ms Delayer coalesces rapid filter input. No new requests are launched by retaining readOnly values, and the branch path avoids per-keystroke remote calls.
- Cache behavior: Branch results are cached for a NewSession and picker-local branch results are reused. Generic dynamic provider queries are not cached but are coalesced by the 200 ms Delayer; the diff changes neither behavior.
- Mechanism confidence: High confidence that payload size increases and request count does not; low confidence that the bounded extra bytes have user-visible cost.
- Magnitude uncertainty: Third-party providers could advertise larger readOnly values, but no realistic repository path establishes enough repeated bytes to create material latency or throughput loss.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostChatInputPicker.ts:1119 \_getItems</code>: Serialize current config and request dynamic values from the Agent Host/provider; remote connections may carry this over a network-backed protocol.; cardinality: One request on picker open plus one per coalesced non-branch query; branch filtering uses the already loaded list.
    - Introduced by diff: false; previous behavior: The same completion requests occurred, but readOnly values such as locked reports or shellInitScripts were omitted from each config payload.; critical-path effect: Each request gates updated picker options.
- Verdict: No reportable regression: this is a small payload increase on existing coalesced requests, with no boundary fan-out or realistic evidence of user-visible serialization/network impact.

### Scenario 4: Edit or replace running session configuration

- Critical path: A user edit dispatches the changed property and, except for sandbox-only changes, starts one resolveSessionConfig request whose latest sequence wins. Replace dispatches one full replacement and starts one resolve.
- Scaling input: User config-edit frequency and config payload size; no per-property request loop is added.
- Effective concurrency: Calls are not globally serialized, but stale responses are discarded by a per-session sequence. The diff does not increase the number of edits, dispatches, or resolves.
- Cache behavior: Current running config is retained per session and replaced by the latest successful sequence. No cache invalidation, miss retry, or retention lifecycle changes are introduced.
- Mechanism confidence: High confidence in unchanged request cardinality and asynchronous optimistic behavior.
- Magnitude uncertainty: Provider-defined readOnly payload sizes vary, but edits are user-driven and repository-defined values are small.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:5331 \_resolveRunningSessionConfig</code>: Re-resolve running config after an edit, now carrying advertised readOnly values in addition to mutable values.; cardinality: One resolve per qualifying user config edit; replacement likewise triggers one existing resolve.
    - Introduced by diff: false; previous behavior: The same resolve request was issued with readOnly values filtered out.; critical-path effect: The optimistic local update proceeds before resolution; this request is off the immediate UI critical path, though it updates authoritative config when complete.
- Verdict: No reportable regression: richer payloads preserve host-owned state but do not add synchronous UI work, requests, or unbounded memory.
