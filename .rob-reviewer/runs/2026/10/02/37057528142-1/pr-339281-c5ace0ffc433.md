Renderer entry points only register a delayed remote-service descriptor. The shared-process constructor allocates bounded maps/queue/telemetry/rate-limit state and a configuration listener; it performs no fetch, filesystem, IPC, or timer operation, so the added work is small fixed CPU/allocation on startup.
- Scaling input: One engine and one channel per shared-process lifetime, plus one delayed renderer-side service descriptor per desktop window; cost does not scale with repositories, requests, or history while unused.
- Effective concurrency: Startup construction is synchronous and single-instance. Existing configuration/storage initialization completes before this added construction; the diff adds no concurrent boundary work.
- Cache behavior: No request cache is populated at startup. The engine's transport/cache is not created until an anonymous client is acquired, and telemetry schedules no timer until a request is recorded.
- Mechanism confidence: High confidence in the startup reachability and bounded setup from SharedProcessMain.initServices, GitHubService's constructor, and the explicit no-fetch test.
- Magnitude uncertainty: Exact module-evaluation and allocation time is unmeasured, but the traced constructor performs only bounded in-memory setup and no heavyweight boundary operation.
- Expensive boundaries: none found
- Verdict: No finding: although the setup is unconditional, the concrete work is fixed and lightweight rather than a realistic user-visible startup regression.

### Scenario 2: Opt-in anonymous GitHub JSON read from a desktop window

- Critical path: A caller awaits renderer-to-shared-process IPC, queue admission/cooldown, one shared-process fetch, bounded body read/JSON parsing, and response serialization back over IPC. This entire path is opt-in and search confirms no production ISharedProcessGitHubService caller in this PR or repository; existing workbench and Sessions callers remain on their prior engines.
- Scaling input: Explicit call count and number of distinct URL/options coalescing keys. Identical overlapping reads share one operation; distinct retained requests are capped at 256, with 4 globally active, 2 per host/caller, and anonymous account serialization further limiting a single origin.
- Effective concurrency: RequestQueue caps global activity at 4 and host/caller activity at 2, while account-key exclusion serializes requests for the same anonymous origin. Identical reads coalesce with at most 64 waiters; there is backpressure rather than an unbounded burst.
- Cache behavior: Overlapping identical reads coalesce. The transport has an LRU/ETag cache while its anonymous client lease lives, but the IPC channel acquires and releases the lease per call, so sequential non-overlapping IPC calls reacquire a cold client; rate-limit cooldown state remains engine-owned. There is no negative cache. Because there are currently no production callers, this does not regress an existing workflow.
- Mechanism confidence: High confidence from the only service references, request tests, queue limits, response-size cap, and transport coalescing implementation.
- Magnitude uncertainty: Future caller frequency and response sizes are unknown. The mechanism and limits are established, but there is no current product scenario exercising this boundary.

### Scenario 3: Two windows issue the same anonymous read and one disconnects

- Critical path: Each window sends an IPC request; both acquire leases for the same normalized API base and attach to one coalesced transport operation. A disconnected/cancelled waiter detaches and releases its lease, while the network operation remains live for the peer; the last waiter cancellation aborts the fetch.
- Scaling input: Number of overlapping windows/waiters for one equivalent request, capped at 64 shared waiters.
- Effective concurrency: One underlying operation for the coalescing key; cancellation is per waiter, and the final detached waiter aborts the operation. Global queue limits still apply across distinct keys.
- Cache behavior: This is warm only at the in-flight coalescing level; completed sequential calls do not retain the per-client transport cache after the final lease is released. Cooldowns survive client release.
- Mechanism confidence: High confidence from the IPC disconnect test, anonymous-client coalescing test, reference-counted lease implementation, and transport waiter cleanup.
- Magnitude uncertainty: No current production callers exercise cross-window sharing, so prevalence is zero in the reviewed revision and future multiplicity is unknown.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/github/common/githubIpc.ts:64 GitHubChannel.getAnonymous</code>: Carries each window's request/cancellation and response independently.; cardinality: Two IPC calls for two callers; cancellation affects only one waiter.
    - Introduced by diff: true; previous behavior: There was no cross-window shared-process read path; existing per-window engines could not share this operation across windows.; critical-path effect: The surviving caller remains blocked only on the shared network operation, not on the disconnected peer.
  - network at <code>src/vs/platform/github/common/githubTransport.ts:175 GitHubTransport.\_rest</code>: Coalesces equivalent in-flight GETs into one fetch and aborts only after all waiters detach.; cardinality: One fetch for the effective single coalescing key, not one per window.
    - Introduced by diff: true; previous behavior: Existing independent window engines would perform separate network operations; no existing caller is migrated in this PR.; critical-path effect: One network response serves the surviving window; disconnect cleanup does not trigger a duplicate request.
- Verdict: No finding: the introduced behavior reduces rather than amplifies overlapping network work and has bounded cleanup/lifetime.
