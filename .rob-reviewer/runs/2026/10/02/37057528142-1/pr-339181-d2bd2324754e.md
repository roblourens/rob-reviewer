## Findings (1)

### 1. [medium] Load catalogue details lazily instead of issuing one GET per summary

**Finding ID:** `PERF-5CFBC858FAB3`  
**Location:** <code>src/vs/sessions/contrib/providers/copilotChatSessions/browser/cloudAutomationApiClient.ts:116</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Copilot HTTP requests, repeated authentication-session lookups, response parsing, and network connection capacity  
**Scaling:** For N summaries lacking prompt, one list invocation performs N additional detail GETs. With concurrency five, critical-path latency grows in approximately ceil(N/5) request-latency waves per page; refreshing repeats the full work because requests are no-store and results are not cached.  
**Outcome:** Increased catalogue-load latency, excessive network I/O, lower request throughput, and avoidable API rate-limit consumption  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no cloud-automation catalogue client and therefore no eager per-entry detail traffic; the list endpoint itself supplies the catalogue summaries in one paginated request.  
**Changed behavior:** The new list implementation maps every automation summary whose optional prompt is absent to get(), eagerly hydrating it through an additional Copilot HTTP request before the page can be appended or the next page fetched.  
**Confidence:** 0.99 — The added call path, missing-prompt response shape, per-page size, concurrency limit, blocking Promise.all, and disabled transport cache are all directly established by changed production code and tests. Only the real-world catalogue size and endpoint latency are uncertain, which affects severity rather than the mechanism.

**Causal diff evidence:** Added line 116 calls this.get(...) from inside response.data.automations.map(...). The same added method requests up to 100 summaries per page for 10 pages, and the added test explicitly models list responses without prompts and verifies separate detail requests.

Opening or refreshing a catalogue with prompt-less summaries waits for one list request plus N detail requests. A 100-entry page requires 20 sequential network waves at concurrency five before list() can proceed, causing visibly slow catalogue loads and avoidable service/rate-limit pressure; the configured 10-page cap permits up to 1,010 requests per refresh.

**Evidence:** list() requests per\_page=100, then awaits Promise.all over the page. For every entry without prompt, line 116 invokes get(), which performs GET /agents/automations/{id}. The Limiter only caps concurrency at five; it does not reduce call count. GitHubApiClient marks all of these requests disableCache: true, and this client adds no data cache, so each catalogue refresh repeats the fan-out. The tests establish that missing prompts are an intended response shape and that seven summaries produce seven detail requests.

**Suggested direction:** Keep list() summary-only and call the existing get() endpoint when an automation is opened or edited. If every prompt is truly required for initial rendering, use a server/list response that includes prompts or an explicit bulk endpoint rather than eagerly issuing one detail request per entry.
