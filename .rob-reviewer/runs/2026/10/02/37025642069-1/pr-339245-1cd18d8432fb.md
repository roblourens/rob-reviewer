## Findings (1)

### 1. [medium] Reuse the ownership snapshot across the session-list map

**Finding ID:** `PERF-2C252A161CFC`  
**Location:** <code>extensions/copilot/src/extension/chatSessions/vscode-node/copilotCloudSessionsProvider.ts:1484</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and temporary Map/object allocations while decoding persisted ownership records  
**Scaling:** For M visible tasks whose API response omits event\_type and H persisted ownership records, this performs O(M×H) record validation and Map insertion; H is explicitly allowed to grow to 1,000.  
**Outcome:** Increased cloud-session list refresh latency plus extension-host CPU and GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** fetchSessionList read ownership once through getOwnedTaskIds(), built one Set, and reused its isExternal closure for every returned task, so ownership decoding was O(H) per refresh.  
**Changed behavior:** Each no-event\_type task now calls CloudTaskOwnership.getApplication(), which invokes \_read(), enumerates the entire stored ownership object, validates every record, and rebuilds a Map before looking up one task ID.  
**Confidence:** 0.99 — The call path, per-task placement, full-map reconstruction, 1,000-record bound, and optional event\_type fallback are all explicit in changed code and tests. Exact task counts vary, affecting severity but not the repeated-work mechanism.

**Causal diff evidence:** The added RIGHT line 1484 inserts this.\_ownership.getApplication(entry.taskId) into the per-session map; before the PR the metadata expression only used the already-snapshotted isExternal lookup.

Opening or periodically refreshing a cloud-session list containing legacy/tasks-without-event\_type repeatedly rebuilds the up-to-1,000-entry ownership map once per such task, delaying publication of the refreshed list and creating avoidable garbage on the extension host.

**Evidence:** provideChatSessionItems maps all sessionList entries at lines 1457+, and line 1484 performs getApplication(entry.taskId) inside that map. CloudTaskOwnership.getApplication calls \_read().get; \_read iterates Object.entries(stored) into a new Map, while MAX\_OWNED\_CLOUD\_TASKS is 1000. The same refresh already reads ownership once at fetchSessionList line 1413, proving a reusable per-refresh snapshot exists conceptually. eventType is optional and the added TaskApiBackend test explicitly covers undefined, so the fallback path is real.

**Suggested direction:** Read ownership once per provideChatSessionItems refresh and reuse that snapshot for both external status and application lookup (for example return a taskId→record snapshot/lookup closure from fetchSessionList), rather than calling \_read() from each mapped task.
