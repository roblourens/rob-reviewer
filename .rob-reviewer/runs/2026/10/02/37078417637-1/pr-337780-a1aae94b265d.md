## Findings (1)

### 1. [medium] Avoid replacing the full chat catalog on turn status changes

**Finding ID:** `PERF-9E8F25A08DB7`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostStateManager.ts:514</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** serialized chat-summary objects and IPC bytes  
**Scaling:** O(C \* K) payload processing per start/completion, where C is the non-tool chat count and K is connected clients; the 100 ms scheduler only coalesces transitions within one window.  
**Outcome:** increased IPC traffic and CPU/GC pressure on turn transitions  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Per-chat status was omitted from the compact root catalog, so turn activity changed only scalar session fields and did not attach \`changes.chats\`.  
**Changed behavior:** A single chat's InProgress/Idle transition now changes the projected compact-chat array, so the notifier sends the entire array and the protocol server broadcasts it to every active client.  
**Confidence:** 0.98 — The changed test proves the before/after payload, and the turn-action-to-summary-to-broadcast call path is explicit. Only the typical chat/client counts and exact duration are uncertain.

**Causal diff evidence:** Added line 514 copies each chat's volatile status into the compact root catalog. The changed protocol-server test now expects a complete \`changes.chats\` array after \`ChatTurnStarted\`; before the diff it expected only scalar \`modifiedAt\` and \`status\`.

Each normal turn generally sends a full chat catalog at start and completion. Sessions with many peer/side chats incur extra IPC serialization, parsing, allocation, and GC even though only one chat changed.

**Evidence:** \`\_onChatStateChanged\` updates chat status and marks the summary dirty. \`SessionSummaryNotifier.flush\` assigns all of \`current.chats\` whenever one projected entry differs. \`\_broadcastNotification\` sends root notifications to every active client without subscription filtering.

**Suggested direction:** Keep volatile activity bits off the full-replacement root catalog until a single-chat delta is available, or introduce a compact per-chat status delta and reserve full replacement for membership/reordering.
