## Findings (2)

### 1. [medium] Coalesce update checks after extension enablement

**Finding ID:** `PERF-161857F0699F`  
**Location:** <code>src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts:1142</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** marketplace network requests plus request/response bytes and per-extension metadata processing  
**Scaling:** For N installed extensions and E separate enablement events, the new path performs E network requests each carrying/processing O(N) extension metadata; because calls are fire-and-forget, closely spaced events can overlap rather than coalesce.  
**Outcome:** excessive network I/O and avoidable CPU/serialization work, with concurrent requests able to reduce responsiveness and throughput  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Before the PR, the default legacy value \`true\` did not satisfy the \`=== 'onlyEnabledExtensions'\` gate, so enabling an extension did not trigger this full-gallery refresh. Only users explicitly configured for \`onlyEnabledExtensions\` paid this cost.  
**Changed behavior:** Extension enablement events in both \`'on'\` and \`'delayed'\` modes now call \`checkForUpdates\`, instead of doing so only for the former \`'onlyEnabledExtensions'\` mode. \`checkForUpdates\` enumerates every installed extension and sends the complete list to \`galleryService.getExtensions\`; calls are neither debounced nor protected by an in-flight promise.  
**Confidence:** 0.97 — The changed gate, legacy-value migration, event batching, absence of coalescing, and full-inventory gallery call are all directly visible in the traced code. Exact request latency and how often users toggle extensions vary, but the added network mechanism and O(installed extensions) payload per event are unambiguous.

**Causal diff evidence:** RIGHT line 1142 changes the gate from \`getAutoUpdateValue() === 'onlyEnabledExtensions'\` to \`getAutoUpdateValue() \!== 'off'\`; the same PR maps legacy/default \`true\` to \`'on'\` at extensions.contribution.ts:2139, so the default population newly reaches \`checkForUpdates\` on enablement events.

With the default auto-update setting, enabling one extension now causes a background marketplace request for metadata for every installed extension; enabling several extensions separately can launch overlapping requests. On profiles with many extensions or a slow/enterprise marketplace this creates avoidable network traffic, serialization/response processing, and contention immediately after each enable action.

**Evidence:** \`initializeAutoUpdate\` subscribes directly to \`extensionEnablementService.onEnablementChanged\` and invokes \`checkForUpdates\` without awaiting, debouncing, or reusing an in-flight call. \`ExtensionEnablementService.setEnablement\` emits one event per command (including recursively enabled dependencies/packs), while separate commands emit separate events. \`checkForUpdates\` at lines 1976-2020 rebuilds \`infos\` from all \`this.local\` entries and calls the network-backed \`galleryService.getExtensions(infos, ...)\`. Thus rapid separate enable actions can overlap full-inventory marketplace requests.

**Suggested direction:** Preserve the newly enabled-extension semantics without querying the whole inventory per event: coalesce enablement events behind a single in-flight/debounced check and, preferably, pass only the newly enabled extension infos to the existing batched \`galleryService.getExtensions\` path before syncing those results.

### 2. [medium] Limit delayed-deadline checks to eligible extensions

**Finding ID:** `PERF-CED7A606935B`  
**Location:** <code>src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts:2251</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** marketplace requests, request/response bytes, and CPU work for all installed extension metadata  
**Scaling:** For N installed extensions and D distinct delayed-update publication deadlines, the timer path performs up to D full O(N) marketplace checks during the six-hour window rather than refreshing only the candidates whose deadline expired.  
**Outcome:** excessive network I/O and repeated serialization/metadata processing  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no per-publication deadline timer; stable builds used one grouped update check on the existing 12-hour schedule (and eligible Insider builds used the existing 1-hour schedule), so staggered extension publication times did not add full-inventory checks.  
**Changed behavior:** Delayed mode records the earliest remaining publication delay and, at every expiry, starts a complete update check for all installed extensions. After the eligible extension is handled, any other delayed extension with a later publication timestamp schedules another complete check.  
**Confidence:** 0.96 — The timer-to-network call path and rescheduling loop are explicit, and \`checkForUpdates\` demonstrably enumerates the full installed collection. The number of staggered updates varies by profile, affecting severity but not the mechanism.

**Causal diff evidence:** RIGHT line 2251 newly schedules \`eventuallyCheckForUpdates(true)\` for \`soonestDelayRemaining\`; that helper immediately calls full \`checkForUpdates()\` and then \`autoUpdateExtensions\` schedules the next remaining deadline.

When several installed extensions have updates published at different times within the six-hour window, VS Code issues a full marketplace metadata request at each distinct deadline, even though only the extension(s) reaching that deadline need refreshing. Profiles with many installed extensions therefore incur repeated large background requests and metadata processing throughout the delay window.

**Evidence:** \`autoUpdateExtensions\` computes the minimum positive delay over \`this.outdated\`, sets this timer, and returns when nothing is eligible. The callback reaches \`eventuallyCheckForUpdates(true)\`, which cancels the periodic delayer and immediately awaits \`checkForUpdates\`; that method serializes all installed extension infos and calls \`galleryService.getExtensions\`. Gallery synchronization invokes \`eventuallyAutoUpdateExtensions\` again, which installs mature entries and schedules the next distinct deadline. No grouping window or candidate subset prevents repeated all-installed queries.

**Suggested direction:** At a deadline, refresh only the delayed extension IDs whose eligibility time has arrived using the existing batched \`galleryService.getExtensions\` API, then sync/install those results and schedule the next deadline. Coalesce nearby deadlines so one targeted request serves the group while preserving the check for a newer published version.
