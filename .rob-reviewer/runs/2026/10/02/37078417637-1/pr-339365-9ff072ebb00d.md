## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts:2306` (`LEFT`)  
**Blamed base line:** `src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts:2306`  
**Introducing path:** `src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts`  
**Introducing commit:** `da03e4ef04b9338a69f2fbb638bb173ff06471f3`  
**Mechanism family:** `repeated-work`  
**Performance category:** `network`  
**Confidence:** 0.98

**Mechanism:** Each earliest quarantine expiry initiated another full installed-extension update check outside the normal cadence. For N installed extensions this repeated O(N) metadata and synchronization work and could launch N concurrent latest-version HTTP GETs, or a grouped marketplace query POST.

**Symptom:** Quarantine expiry caused an additional marketplace update-check burst, increasing network traffic and CPU/serialization beyond the regular polling cadence.

**Fixed behavior:** Removing the expiry timer keeps full marketplace checks on the existing 12-hour scheduler, avoiding the extra full synchronization and network burst when an extension becomes eligible.

**Evidence:** Deleted base line 2306 scheduled eventuallyCheckForUpdates(true) at the earliest delay expiry. That cancels the cadence delayer, immediately runs checkForUpdates(), builds infos for all installed extensions, and calls galleryService.getExtensions(infos). The resource API uses Promise.all over those infos and sends a GET per UUID-backed extension; its fallback sends a grouped query POST. The added fake-timer test counts getExtensions and proves that crossing expiry no longer adds a check, while the unchanged scheduler still checks every 12 hours.
