# Performance review: Refine sandbox settings and native policy command

[PR #339401](https://github.com/microsoft/vscode/pull/339401) at `47810dbce6b4ef1c81fd97e063a723dd5504f288`

## Findings (1)

### 1. [medium] Bound command discovery before running the local sandbox command

**Finding ID:** `PERF-C362B98063F8`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotSlashCommandProvider.ts:51</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** A full \`session.rpc.commands.list\` IPC request and its built-in/skill/client-command catalog payload  
**Scaling:** The extra serialized work occurs once for every cold or invalidated slash-command catalog; catalog construction and transfer grow with the session's installed skills, plugins, and client commands, and invalidation occurs on tools/commands updates.  
**Outcome:** Increased command latency and potentially an indefinitely blocked \`/sandbox policy\` turn when command discovery is slow or does not settle  
**PR causality:** <code>introduced</code>  
**Previous behavior:** \`resolveSlashCommand\` recognized the VS Code-owned \`sandbox-policy\` command before consulting the runtime catalog, so a cold policy request proceeded directly to the command invocation without listing runtime commands.  
**Changed behavior:** A cold \`sandbox\` resolution now awaits \`\_getRuntimeSlashCommandCatalog(maxWaitMs)\` before falling back to the local command, and the send path calls it without a \`maxWaitMs\`.  
**Confidence:** 0.99 — The changed await, its unbounded call site, the concrete session RPC callback, cache invalidation sites, and the updated test's new IPC expectation establish the mechanism and critical path directly. Only the typical RPC duration and catalog size vary by installation.

**Causal diff evidence:** The added \`const catalog = await this.\_getRuntimeSlashCommandCatalog(maxWaitMs)\` at line 51 moves full runtime catalog discovery ahead of the local sandbox fallback; the updated session test explicitly changes the expected \`commandListCalls\` from \`\[\]\` to one \`commands.list\` call for \`/sandbox policy\`.

Submitting \`/sandbox policy\` in a fresh session—or after commands/tools change—cannot make progress until a full SDK command-list IPC completes. A slow runtime adds that latency before the actual policy invocation; a stuck list RPC strands the turn even though the local fallback is already sufficient.

**Evidence:** \`CopilotAgentSession.send\` awaits \`resolveSlashCommand(slashCommand.command)\` before \`commands.invoke\`; the provider's \`listCommands\` callback is \`session.rpc.commands.list({ includeBuiltins: true, includeSkills: true, includeClientCommands: true })\`. \`resolveSlashCommand\` defaults \`maxWaitMs\` to \`undefined\`, and \`\_getRuntimeSlashCommandCatalog\` then returns the raw in-flight promise with no timeout. Although the result is cached and concurrent lookups coalesce, \`onToolsUpdated\`, \`onCommandsChanged\`, and runtime-setting changes clear that cache, making the delay recur.

**Suggested direction:** Keep SDK-first resolution within a bounded budget for \`sandbox\` (for example, pass the existing completion wait to catalog lookup), then use \`copilotSandboxPolicyCommand\` while allowing the coalesced catalog refresh to finish in the background. This preserves native resolution when promptly available without making the local fallback depend indefinitely on catalog discovery.
