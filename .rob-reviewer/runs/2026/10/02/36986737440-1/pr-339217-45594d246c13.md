# Performance review: sessions: Fix cloud session rename via Mission Control

[PR #339217](https://github.com/microsoft/vscode/pull/339217) at `45594d246c13e35aa2ebf08076ab831d6857f66a`

## Findings (1)

### 1. [medium] Stop invalidated discovery before issuing the remaining requests

**Finding ID:** `PERF-82D2FBA71947`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts:546</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Mission Control listTasks/getTask network requests and their response parsing  
**Scaling:** The wasted work grows with the cold full-discovery inventory: two repository scopes, up to 10 pages of 100 summaries each, followed by one getTask request per uncached sandbox task at concurrency 5.  
**Outcome:** Excessive network I/O and lower discovery throughput, with avoidable API/rate-limit pressure while the invalidated scan remains in flight.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Renaming a restored disconnected sandbox was a no-op, and a connected rename only dispatched to AHP; neither operation invalidated Mission Control discovery or caused its remaining requests to be discarded.  
**Changed behavior:** After the new PATCH succeeds, this line increments the discovery generation. listSessions checks that generation only after all list pages and all limiter-queued getTask calls have completed, so an overlapping scan continues doing work even though it must return a failed invalidation result.  
**Confidence:** 0.97 — The changed trigger, restored-row overlap, request limits/concurrency, and late generation check are all explicit in the code and the new in-flight test. Exact user inventory size and request duration vary, which limits severity but not the mechanism.

**Causal diff evidence:** The added \`this.\_discoveryGeneration++;\` at line 546 creates a new invalidation trigger for session rename. Unlike the pre-PR rename path, this trigger can fire from a restored offline row while cold discovery is still fetching tasks.

A realistic cold-start overlap exists because persisted rows are restored before network discovery finishes: renaming one of those rows can leave the startup scan issuing getTask calls for every remaining sandbox task (and any remaining pages), all of which are thrown away. This increases Mission Control traffic and can delay later refreshes behind the still-running scan.

**Evidence:** CloudSandboxSessionContribution restores and seeds persisted sessions before awaiting listSessions. listSessions captures \_discoveryGeneration at line 287, can scan up to 2×10 pages, then queues getTask for sandboxTasks with a limiter of 5; it does not compare the generation again until line 438 after Promise.all. The added rename path increments the generation at line 546, and the added test "invalidates discovery in flight when a task is renamed" proves this can occur while getTask is pending and that the completed scan is discarded.

**Suggested direction:** Preserve stale-response protection while stopping fan-out: cancel the active discovery with a per-pass CancellationTokenSource when rename commits, or check the captured generation before each page and before each limiter-queued getTask so no further boundary calls are issued after invalidation. Keep the next pass's \`needsRefresh\` behavior for the renamed task.
