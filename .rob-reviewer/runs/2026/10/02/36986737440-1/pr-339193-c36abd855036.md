### Scenario 1: Open or reopen the Chat Customizations editor while the marketplace setting remains at its experiment-provided default

- Critical path: setInput performs one configuration inspection, then calls the experiment-trigger helper before the existing editor-open telemetry and EditorPane.setInput. The helper's bounded registry lookup and local telemetry enqueue are synchronous; telemetry transport is not awaited and remains off the editor-open critical path.
- Scaling input: Editor-open frequency within one window. Configuration inspection remains constant-size across eight known layers, and the experiment event is deduplicated to one event per telemetry service/window and treatment name.
- Effective concurrency: Synchronous editor setup; no queue, parallel work, or new concurrent boundary. WeakMap/Set state coalesces repeated opens to one experiment event.
- Cache behavior: The first eligible open creates the per-telemetry-service Set and records the treatment; subsequent warm opens still perform the constant-size configuration inspection and registry lookup but return before telemetry dispatch. Explicitly configured values skip the helper.
- Mechanism confidence: High: the changed call site, WeakMap/Set deduplication, and synchronous telemetry dispatch path were directly traced.
- Magnitude uncertainty: Appender implementations and enabled telemetry modes vary by product environment, but the new event's cardinality and bounded payload are established.
- Expensive boundaries:
  - IPC/network/filesystem telemetry transport at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts:3399 and src/vs/platform/telemetry/common/experimentTrigger.ts:53</code>: Dispatch the new experimentTrigger event through configured telemetry appenders; desktop/remote appenders can enqueue IPC and web appenders enqueue network telemetry, while the log appender can write the telemetry log.; cardinality: At most one new event per window for this setting, regardless of editor reopen count.
    - Introduced by diff: true; previous behavior: The editor already emitted chatCustomizationEditor.opened on each setInput, but did not emit this once-per-window experimentTrigger event.; critical-path effect: Only bounded sanitization/appender enqueue occurs synchronously before editor setup continues; IPC/network completion is not awaited.
- Verdict: No reportable regression. Added work is constant-size and the only new boundary is deduplicated to one asynchronous telemetry event per window.

### Scenario 2: Install a skill, MCP server, plugin, configured plugin, or Copilot connector from the unified customization marketplace

- Critical path: The existing install operation still performs the same type-specific install and record reconciliation. The new wrapper starts one stopwatch and emits one bounded telemetry event after success or failure before the install promise settles; transport completion is not awaited.
- Scaling input: Effective cardinality is one operation per unique marketplace resource/connector key. Concurrent callers for the same key share the existing pending promise and therefore produce one event, not one per caller.
- Effective concurrency: Existing pending-key coalescing remains intact. Different resource keys may install concurrently as before; the diff adds no fan-out, limiter bypass, or extra install task.
- Cache behavior: Existing source/manifest/plugin caches and warm behavior are unchanged. Configured-plugin fetches, manifest retrieval, and installation records follow their prior cache semantics; telemetry is one event per effective attempt with no retained per-resource cache.
- Mechanism confidence: High: install ownership, pending-key coalescing, wrapper placement, and all type branches were directly inspected.
- Magnitude uncertainty: Exact installation duration and transport implementation vary by customization kind and environment, but those expensive installation boundaries are pre-existing; the introduced payload is fixed-size.
- Expensive boundaries:
  - network/filesystem/subprocess/IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceInstallService.ts:746 via installTarget/runConnectorOperation</code>: Perform the existing type-specific install: marketplace/plugin fetches, MCP management installation, Git/package/plugin installation, skill installation, or connector connection.; cardinality: One existing install workflow per unique pending key; internal calls vary by installation kind but are unchanged by the diff.

  - filesystem/storage at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceInstallService.ts:748 via addRecord</code>: Persist and reconcile the installation record after the install succeeds.; cardinality: One record update per effective successful install.

- Verdict: No reportable regression. The wrapper neither duplicates installation work nor increases boundary cardinality; one fixed-size telemetry event is negligible relative to the user-initiated install.
