**Relevant issue families:** eager-work, boundary-fanout, repeated-work, unbounded-retention, cache-lifecycle, serialization-allocation

### Scenario 1: An eligible closed-chat promo first arms its status-bar pip after workbench restoration or a promo/treatment change.

- Critical path: The status-bar update synchronously selects one eligible promo and resolves cached/configured treatment; on the first eligible result, the added Set insertion and telemetry logging run before entry props return. A cold experiment assignment is asynchronous and already existed; the status entry makes progress only after that treatment resolves. Telemetry transport is fire-and-forget and does not await IPC or network completion.
- Scaling input: Language-model metadata may contain multiple models, but getOpportunity returns the first eligible promo, so one update arms at most one promo. Across a session, added telemetry cardinality is one event per distinct promo ID encountered, normally one active campaign at a time.
- Effective concurrency: UI updates execute serially on the renderer event loop. Existing pending treatment state coalesces assignment lookup to one in-flight request. The telemetry call is not awaited; desktop enqueues one IPC call and web hands one event to the appender without creating a concurrent per-model burst.
- Cache behavior: Configured treatment bypasses assignment lookup. Cold uncached experiment treatment starts one request; warm/repeated updates reuse treatment, and pending prevents duplicate requests. armedPromos is a positive session cache: repeated updates for the same ID perform only Set lookups and no telemetry boundary call. A new session intentionally emits once again; ineligible/previously seen persisted promos do not reach the added event.
- Mechanism confidence: High confidence in the call path, deduplication, one-active-promo cardinality, and asynchronous telemetry transport based on the changed code, caller, telemetry service, and appenders.
- Magnitude uncertainty: Exact telemetry sanitizer/appender duration and number of campaign IDs encountered in unusually long sessions are unmeasured, but realistic cardinality is tiny and transport is asynchronous.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/chatStatus/chatStatusPromo.ts:210 resolveExperiment</code>: Fetch experiment treatment through IWorkbenchAssignmentService when no explicit configuration or cached treatment exists.; cardinality: At most one in-flight treatment request, coalesced by pending; refetch invalidation can intentionally cause another request.
    - Introduced by diff: false; previous behavior: The same treatment fetch and wait occurred before this change.; critical-path effect: An uncached treatment must resolve before the promo can arm; configured or cached treatment has no request. This behavior predates the diff.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/chatStatus/chatStatusPromo.ts:160 getEntryProps -&gt; TelemetryAppenderClient.log</code>: On desktop, enqueue the new chatPromoWidgetArmed telemetry event to the shared-process telemetry appender.; cardinality: Exactly once per distinct promo ID per ChatStatusPromo session instance due armedPromos; not per status update or per model.

- Verdict: No reportable performance regression. The diff adds bounded constant-size work and one asynchronous telemetry boundary per promo ID, not per refresh or model; the session Set retains only encountered campaign IDs and does not plausibly create meaningful memory growth.

### Scenario 2: The status bar refreshes repeatedly while the same promo remains eligible, including model metadata refreshes and hover transitions.

- Critical path: Each refresh still scans the pre-existing model list and reads pre-existing promo state. The diff adds O(1) Set checks; after the initial arm, it skips telemetry entirely. Hover display continues its existing storage write and shown-event path.
- Scaling input: Frequency is status/entitlement/editor/configuration/model/view events, while effective armed-event cardinality remains one for the stable promo ID regardless of refresh count.
- Effective concurrency: Refresh callbacks are synchronous and serialized. No timers, promises, subprocesses, IPC calls, or network calls are added after the first arm for the same ID.
- Cache behavior: armedPromos remains warm for the lifetime of ChatStatusPromo. shownPromos suppresses the pip after display, and persisted seen state prevents a previously seen promo from being re-offered after restart. Promo metadata text changes with the same ID rebuild the tooltip but do not emit another armed event.
- Mechanism confidence: High confidence from getEntryProps and tests that invoke update/metadata refresh while expecting only one armed event.
- Magnitude uncertainty: The raw refresh rate varies with user activity, but the added steady-state work is two bounded Set lookups on a very small session set.
- Expensive boundaries: none found
- Verdict: No repeated boundary work or rendering regression is introduced; deduplication occurs before telemetry logging.

**Summary:** Reviewed both changed files and traced the added event through status-bar callers, treatment caching, telemetry sanitization, desktop IPC, web/remote transport, and session lifecycle. No high-confidence actionable performance issue was found; the only added boundary is asynchronous and session-deduplicated per promo ID.
