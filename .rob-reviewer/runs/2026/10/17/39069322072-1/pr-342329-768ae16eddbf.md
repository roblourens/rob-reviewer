**Relevant issue families:** boundary-fanout, serialization-allocation, repeated-work, cache-lifecycle

### Scenario 1: Browse the MCP marketplace with a 100-item workbench page over the 99-item native registry cap

- Critical path: The workbench aggregator calls the platform aggregator, which calls McpGalleryMarketplaceProvider and then McpGalleryService.queryPage. The first page requires two sequential registry responses because the native provider is capped at 99; response parsing and server mapping complete before the page can be returned. The added total propagation and Number.isSafeInteger check occur after the existing request and parsing and add only constant-time scalar work.
- Scaling input: Requested page size and registry native page size. At the maximum 100-item combined page, effective cardinality is two registry pages (99 plus at least one item); the remaining 98 items from the second response are buffered for the continuation.
- Effective concurrency: For the MCP-only source, each aggregator's Promise.all contains one active source. Registry pages are fetched sequentially because the second request is issued only after consuming the first 99 items; the diff does not add parallelism or a burst.
- Cache behavior: Cold browse fills the platform continuation with the unused 98 entries from the second response and stores bounded LRU continuation state (maximum 32, 30-minute expiry). The next 100-item request is warm and drains those buffered entries without another registry request in the covered 198-item case. Explicit versus unknown total does not alter continuation keys, exhaustion, or caching; nextCursor remains authoritative.
- Mechanism confidence: High: the complete production diff, provider loop, both aggregation layers, request implementation, and regression test all show that totals are informational and do not control fetches.
- Magnitude uncertainty: Registry response latency and real catalog size vary, but request cardinality and sequencing are established by the provider cap and aggregation loop.
- Expensive boundaries:
  - network at <code>src/vs/platform/mcp/common/mcpGalleryService.ts:1130 queryRawGalleryMcpServers</code>: HTTP GET of a native MCP registry page followed by JSON response parsing; cardinality: Two sequential GETs for a cold 100-item outer page when the first native page has 99 items and a continuation; zero additional GETs for the immediate continuation that drains the 98 buffered items in the tested 198-item catalog.
    - Introduced by diff: false; previous behavior: The same query loop issued the same two GETs based on item count and nextCursor. The diff only replaces the reported count-derived total with validated metadata.total.; critical-path effect: Both cold GETs and parsing must complete before the first 100-item page returns; buffered continuation work avoids another request on the next page.
- Verdict: No reportable performance regression. The diff preserves network cardinality, serialization scale, buffering, and concurrency while adding constant-time validation of one metadata scalar.

### Scenario 2: Search or continue MCP marketplace results with a page size up to 99

- Critical path: Manifest selection precedes one McpGalleryService.queryPage call per native result page. The initial request includes search text; continuation requests use only the opaque cursor. Each response is parsed and mapped before returning. Total validation is constant-time and does not gate or schedule continuation.
- Scaling input: One native page of at most 99 returned servers per provider call; additional work scales with user-requested continuation pages and is driven by nextCursor, not total.
- Effective concurrency: A single MCP provider performs one registry request at a time. When other marketplace sources are selected, the existing aggregator may query independent sources concurrently, but this diff does not change that fan-out.
- Cache behavior: Marketplace continuation state buffers source items and cursors in the bounded LRU. Product manifests are constructed without discovery I/O; version discovery for manifests without a supplied version is coalesced by a per-URL Promise map. The changed total is not part of a cache key and neither creates misses nor pins new collections.
- Mechanism confidence: High: the request URL construction, provider retry condition, continuation state, and manifest cache were traced directly.
- Magnitude uncertainty: The prevalence of custom registries requiring version discovery and the number of user continuations vary; the diff does not change either multiplicity.
- Expensive boundaries:
  - network at <code>src/vs/platform/mcp/common/mcpGalleryService.ts:1130 queryRawGalleryMcpServers</code>: HTTP GET and JSON parsing for the searched or continued registry page; cardinality: One GET per requested native page, capped at 99 servers; empty-page skipping can make up to five existing sequential attempts but is based on items and nextCursor, not total.
    - Introduced by diff: false; previous behavior: One GET and the same full response parsing/mapping occurred per queryPage call before the diff; only the scalar returned as page.total changed.; critical-path effect: The GET and parsing are on the page's critical path.
  - network at <code>src/vs/platform/mcp/common/mcpGalleryManifestService.ts:134 checkVersion</code>: Probe supported registry schema version for manifests created without an explicit version; cardinality: At most one coalesced discovery sequence per URL, trying up to two versions sequentially; normal product-default manifests supply v0.1 and skip these probes.
    - Introduced by diff: false; previous behavior: Manifest discovery and its per-URL Promise cache are unchanged and are not affected by total metadata.; critical-path effect: When needed, discovery completes before the first registry page can be requested.
- Verdict: No reportable performance regression. Neither valid nor absent totals change page fetching, retries, source concurrency, or cache behavior.

### Scenario 3: Query an MCP gallery whose query resource is a local file

- Critical path: McpGalleryService reads the file, converts the buffer to a string, parses JSON, maps returned servers, and then validates the optional total before returning the page. File read and parsing are on the critical path; the added scalar access/check is negligible and non-scaling.
- Scaling input: The local registry file byte size and number of server entries. Existing parsing and mapping are linear in those inputs; the new metadata operation remains O(1).
- Effective concurrency: One file read per queryPage invocation; no added queue, parallelism, subprocess, database, network, or IPC operation is introduced.
- Cache behavior: This path has no response cache in McpGalleryService, so each invocation rereads the file as before. Aggregator continuation caching remains based on items and nextCursor; total does not change invalidation or retention.
- Mechanism confidence: High: the file branch and post-query total handling are directly visible in the changed service.
- Magnitude uncertainty: Local-file registry size and usage frequency are unknown, but the unchanged I/O cardinality and O(1) added work are clear.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/mcp/common/mcpGalleryService.ts:1115 queryRawGalleryMcpServers</code>: Read the local registry file, decode it, and JSON.parse its contents; cardinality: One file read per queryPage invocation, independent of whether metadata.total is present.
    - Introduced by diff: false; previous behavior: The same full-file read and parse occurred on every queryPage invocation; preserving and checking total adds no read or extra traversal.; critical-path effect: The read and parse must finish before results can be returned.
- Verdict: No reportable performance regression. Existing file I/O and parsing costs are unchanged.
