## Performance regression fixes detected (3)

### 1. boundary-fanout

**Fix location:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts:2248` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts:2236`  
**Introducing path:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`  
**Introducing commit:** `6f96a7816c2a7b68d26b65a353c411912fee7b30`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `io`  
**Confidence:** 0.99

**Mechanism:** Startup discovery opened and queried one SQLite session database for every SDK catalog entry, including hundreds already represented in the host registry; work scaled with SDK session count despite the registry already containing the answer.

**Symptom:** Large Copilot SDK catalogs caused tens of seconds of startup discovery latency from hundreds of unnecessary per-session SQLite opens and metadata reads.

**Fixed behavior:** Discovery now bulk-queries the authoritative registry once and drops registered candidates with in-memory Set membership before any per-session database I/O.

**Evidence:** Before this PR, \_discoverCopilotChats mapped every SDK session through \_readStoredSessionMetadata; that helper calls tryOpenDatabase and issues metadata SQL for each session, under a limiter of four. The changed host filter performs one AgentSessionRegistry.list query for the full candidate set, and the changed Set lookup at line 2248 bypasses all per-session database opens for registered candidates. The added test instruments tryOpenDatabase and proves zero opens for registry-known candidates. The PR's reproduced 941-session startup attributes 66.9s to this classification path.

### 2. eager-work

**Fix location:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts:2257` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts:2265`  
**Introducing path:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`  
**Introducing commit:** `6f96a7816c2a7b68d26b65a353c411912fee7b30`  
**Mechanism family:** `eager-work`  
**Performance category:** `subprocess`  
**Confidence:** 0.97

**Mechanism:** Discovery eagerly resolved projects through Git for adoptable sessions that the next stage always discarded; cost scaled with the number of distinct candidate working-directory/context keys, bounded only to four concurrent resolutions.

**Symptom:** Startup discovery spent avoidable Git/project-resolution time on hundreds of legacy extension-host sessions while migration was disabled.

**Fixed behavior:** When legacy migration is disabled, adoptable extension-host candidates are discarded immediately after marker classification, before project/Git resolution that cannot affect emitted output.

**Evidence:** Before the change, every unknown candidate reached \_resolveSessionProject before \_emitCopilotChats later filtered adoptable extension-host sessions when migration was disabled. \_resolveSessionProject calls projectFromCopilotContext through a limiter and Git service; effective calls are deduplicated only by context key. The new guard at line 2257 runs after marker classification but before project resolution. The added test supplies an adoptable session with migration off and asserts getRepositoryRoot is never called.

### 3. missing-coalescing

**Fix location:** `src/vs/platform/agentHost/node/agentService.ts:1554` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentService.ts:1549`  
**Introducing path:** `src/vs/platform/agentHost/node/agentService.ts`  
**Introducing commit:** `513b43f0b7b4fb09d5cebf9d55ce99be45a4b0ef`  
**Mechanism family:** `missing-coalescing`  
**Performance category:** `io`  
**Confidence:** 0.99

**Mechanism:** A multi-window restore burst launched a complete registry traversal and per-session database-overlay pass for every concurrent IPC request, multiplying filesystem/SQLite work by the number of windows.

**Symptom:** Concurrent startup list requests each took roughly 73-110 seconds and duplicated full-catalog SQLite work, increasing startup latency and I/O pressure.

**Fixed behavior:** Concurrent listSessions requests for the same external-session mode now share one registry traversal and one set of per-session metadata reads, while registry mutations invalidate sharing and each caller receives an independent array.

**Evidence:** Before the PR, each listSessions invocation independently awaited migration, traversed the registry, fetched provider metadata, and opened every listed session database for metadata overlay (with per-call limiters of four). The new per-mode in-flight map at line 1554 shares one \_computeSessions promise; mutation epochs prevent post-mutation callers from joining stale work, and results are copied per caller. The added test proves two concurrent calls execute one computation. The reproduced multi-window startup recorded individual list calls of 109.8s, 91.0s, and 73.2s on a 1,437-database corpus.

### Scenario 1: Copilot provider startup discovers SDK sessions and additively registers unknown sessions for surfacing.

- Critical path: For discovered sessions to appear, the provider must complete the SDK catalog RPC, the new registry filter, per-candidate classification, and AgentService registration. This work starts from the first discovery listener and is not awaited by provider registration, so it is off the host's basic startup critical path but is the critical path for session-list completeness.
- Scaling input: SDK catalog size S, registry size R, unknown candidates U, distinct project context keys P, and newly emitted sessions E. The reproduced large case has 941 SDK sessions; the new expensive classification work scales with U rather than all S for database access, Git work scales with eligible distinct P after per-pass coalescing, and registration scales with E.
- Effective concurrency: One SDK catalog request and one registry query run serially before classification. Candidate classification is limited to 4; project resolution is separately limited to 4 and coalesced per context key within the pass. Registration is limited to 4. There is no unbounded subprocess, filesystem, or database burst.
- Cache behavior: Extension-host marker reads are promise-cached by session ID for the agent lifetime, including missing/malformed results. Project resolution is coalesced by context only within one discovery pass. The registry filter is recomputed per discovery pass so mutations are observed. With the host filter installed, known sessions do not open per-session databases; the optional fallback now uses one bulk metadata query per candidate.
- Mechanism confidence: High: call flow, limiter bounds, cache keys, database implementation, and added operation-count tests directly establish the boundary cardinalities.
- Magnitude uncertainty: Exact SDK RPC, Git, and SQLite duration varies by machine and catalog composition; an empty SDK catalog now performs a registry SELECT, but discovery is background and this bounded one-query edge case does not establish a user-visible regression against the removed per-candidate path.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_discoverCopilotChats/\_listSdkSessions</code>: Copilot SDK sessions.list catalog RPC; cardinality: Exactly one RPC per discovery attempt, independent of S.
    - Introduced by diff: false; previous behavior: The same single SDK catalog RPC ran before the PR.; critical-path effect: Must finish before classification and surfacing can proceed.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_filterKnownSessions</code>: Read all host registry session rows and intersect them with candidate URIs; cardinality: One SQLite SELECT over R rows per discovery pass, then O(S+R) in-memory Set work.
    - Introduced by diff: true; previous behavior: Provider classification did not query the registry and instead attempted to open/query each candidate's session database; AgentService separately listed the registry only when candidates were emitted for registration.; critical-path effect: Runs before candidate classification, but replaces S per-session database probes for host-managed Copilot discovery.
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_readExtensionHostCliMarker</code>: Read vscode.metadata.json to classify extension-host sessions; cardinality: At most one cold read per unknown session ID over the agent lifetime; later passes reuse cached promises.
    - Introduced by diff: false; previous behavior: The same marker read occurred for every candidate that survived the old stored-metadata check.; critical-path effect: Required to distinguish adoptable candidates before filtering or project resolution.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotGitProject.ts:resolveGitProject</code>: Resolve repository/worktree project through IAgentHostGitService; cardinality: At most one resolution per distinct eligible context key P in a pass, with concurrency 4.
    - Introduced by diff: false; previous behavior: Unknown adoptable sessions also performed this Git work even though \_emitCopilotChats immediately filtered them when migration was disabled.; critical-path effect: Blocks metadata emission for eligible unknown sessions. The diff removes this boundary entirely for adoptable candidates when migration is disabled.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_registerDiscoveredChats</code>: Register emitted sessions atomically and seed each new external session's read metadata; cardinality: Up to E registry mutations and one per-session database write for each newly registered external session; concurrency is limited to 4.
    - Introduced by diff: false; previous behavior: The same writes occurred for newly registered sessions, while repeated already-registered candidates additionally opened their databases for chat-backing checks before this PR.; critical-path effect: Required before new sessions become registry-backed and are reconciled into the visible list.
- Verdict: No reportable regression. The diff replaces per-candidate SQLite fan-out with one registry query, prevents eager Git work for candidates guaranteed to be discarded, and short-circuits repeated registration I/O.

### Scenario 2: One or more restored windows request the Agent Host session catalog concurrently.

- Critical path: Each client request waits for initial provider migration, registry enumeration, provider metadata lookup, per-session metadata overlay, filtering, and IPC response serialization. Concurrent requests for the same mode and registry epoch now wait on one shared computation; response array copying and serialization remain per caller.
- Scaling input: Registered session count N, concurrent callers W, and external-session modes M. Before the PR the dominant boundary work scaled as O(W\*N); after the PR it scales as O(K\*N), where K is the number of distinct active mode/epoch computations and K is no greater than W.
- Effective concurrency: At most one computation per external-session mode and registry epoch is shared. Registry mutations clear sharing so a post-mutation caller starts a new computation. Within a computation, provider metadata and session overlay work are each limited to 4; no global unbounded concurrency is introduced.
- Cache behavior: This is in-flight coalescing only, not a settled-result cache. Entries are removed on fulfillment or rejection and invalidated on registry mutation. Rejections are shared only by current waiters. Each caller receives a distinct shallow-copied array, so mutable result ownership is not shared.
- Mechanism confidence: High: map keying, epoch invalidation, cleanup, limiters, and the added test proving one computation for two concurrent calls are explicit.
- Magnitude uncertainty: The savings depend on overlap, mode equality, N, and provider/database latency. The shallow-copy cost is not benchmarked, but its N reference assignments are dominated by the eliminated full metadata computations and cannot increase the number of computations over pre-change behavior.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_refreshSessions</code>: Renderer/window listSessions request and response; cardinality: One request and one serialized response per window refresh; W requests remain, but host-side computation is coalesced.
    - Introduced by diff: false; previous behavior: Each request independently triggered the complete host computation.; critical-path effect: Each window waits for the shared host computation and its own response.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_computeSessions -&gt; \_listRegisteredSessions</code>: Enumerate the authoritative session registry; cardinality: One registry SELECT per active mode/epoch computation rather than one per concurrent caller.
    - Introduced by diff: false; previous behavior: Every listSessions call issued its own registry traversal.; critical-path effect: Blocks all metadata processing for the shared computation.
  - IPC at <code>src/vs/platform/agentHost/node/agentService.ts:\_registeredSessionMetadata and src/vs/platform/agentHost/node/copilot/copilotAgent.ts:getChatMetadata</code>: Fetch provider metadata for each registered session, including Copilot getSessionMetadata RPC; cardinality: Up to one provider metadata lookup per registered session N in a computation, limited to 4; coalescing removes duplicate sets across same-mode concurrent callers.
    - Introduced by diff: false; previous behavior: Each concurrent list call repeated these per-session provider lookups.; critical-path effect: Blocks inclusion of each registry row in the shared result.
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_computeSessions</code>: Open each returned session database and bulk-read list overlay metadata; cardinality: At most one open and one bulk metadata query per listed session N in a computation, limited to 4.
    - Introduced by diff: false; previous behavior: Every concurrent call repeated this full per-session database overlay pass.; critical-path effect: Blocks completion of the catalog result.
  - serialization at <code>src/vs/platform/agentHost/node/agentService.ts:listSessions</code>: Copy the result array and serialize it for each IPC caller; cardinality: One O(N) shallow array copy per caller plus the pre-existing response serialization.
    - Introduced by diff: true; previous behavior: Each caller already owned a separately computed array and serialized its own response, so there was no extra shallow copy but all O(N) metadata and database work was duplicated.; critical-path effect: Adds bounded per-caller CPU/allocation after shared computation, while avoiding substantially larger duplicated metadata objects and boundary work.
- Verdict: No reportable regression. Coalescing bounds duplicated registry/provider/database work while preserving mutation freshness and caller-owned arrays.

### Scenario 3: Copilot session metadata is read during resume, listing fallback, discovery fallback, and session operations.

- Critical path: For call sites that need persisted metadata, opening the session database and reading all requested keys must finish before metadata parsing and the operation can proceed. Fire-and-forget project persistence is off the caller's critical path, but the changed read helpers themselves remain synchronous dependencies of their callers.
- Scaling input: Number of metadata helper invocations Q and keys K (6 for \_readSessionMetadata, 9 for \_readStoredSessionMetadata). Database opens remain Q, while SQL statements fall from Q\*K to Q.
- Effective concurrency: The helper issues one SQLite query per invocation. Outer callers retain their existing bounds, including discovery's limiter of 4; the diff does not introduce a new concurrency burst.
- Cache behavior: No new long-lived cache is added. Each call reads current database values through the existing session database reference. Missing keys are returned explicitly as undefined by the bulk query.
- Mechanism confidence: High: SessionDatabase.getMetadataObject builds one parameterized IN query, and the added test records exactly one bulk call.
- Magnitude uncertainty: Per-query latency varies and the registry-first discovery path now bypasses this helper for known sessions, but statement-count reduction is directly established and no larger payload is selected than the same fixed key set.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_readSessionMetadata</code>: Read six persisted Copilot session metadata keys; cardinality: One database open and one IN query per invocation instead of six single-key SQL queries.
    - Introduced by diff: false; previous behavior: The same keys were fetched through six concurrent getMetadata calls, resulting in six SQLite statements on one database.; critical-path effect: Blocks consumers such as customization-anchor and resume/config resolution.
  - database at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_readStoredSessionMetadata</code>: Read nine persisted Copilot discovery/project metadata keys; cardinality: One database open and one IN query per invocation instead of nine single-key SQL queries.
    - Introduced by diff: false; previous behavior: The same keys were fetched through nine getMetadata calls, resulting in nine SQLite statements on one database.; critical-path effect: Blocks provider metadata and fallback discovery classification when this helper is used.
- Verdict: No reportable regression. The fixed-size bulk query strictly reduces SQLite statement fan-out without changing lifetime or concurrency.
