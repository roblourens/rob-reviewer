# Performance review: agentHost: expose root config before AHP authentication

[PR #342324](https://github.com/microsoft/vscode/pull/342324) at `8bc56e8780c786259f1bdc7612d7c72978abafbf`

## Findings (1)

### 1. [medium] Coalesce configuration updates before reconnect replay

**Finding ID:** `PERF-167405626D3A`  
**Location:** <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:3854</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** serialized full-root-configuration bytes and Web PubSub frames  
**Scaling:** Reconnect payload size now grows as O(U × C), where U is the number of root configuration/catalogue updates since the client's last sequence (up to the 1,000-entry replay buffer) and C is the full overlaid root-config size; each retained update is projected as a complete replace action rather than a delta.  
**Outcome:** increased reconnect latency and network/serialization pressure, with sufficiently large histories reaching the 32 MiB single-payload ceiling and closing the lane instead of reconnecting  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this added allowlist case, an unauthenticated reconnect filtered every RootConfigChanged envelope, so its replay response contained no accumulated full-configuration history.  
**Changed behavior:** Unauthenticated reconnects now retain every RootConfigChanged envelope in the replay range; the reconnect path collects all matching replay-buffer entries, and \_projectRelayRootAction replaces each with the full overlaid configuration captured by \_relayRootConfigEnvelopes.  
**Confidence:** 0.94 — The changed predicate, replay loop, 1,000-action bound, full-config projection, clone-progress publisher, and 32 MiB transport ceiling are all directly traced. Exact config sizes and the number of updates missed by a typical mobile disconnect are uncertain, which limits severity, but the multiplicative payload mechanism and reconnect critical-path placement are deterministic.

**Causal diff evidence:** The added \`envelope.action.type \!== ActionType.RootConfigChanged\` allowlist term at line 3854 is what changes pre-auth reconnect filtering from zero config envelopes to all matching config envelopes; tests in this diff explicitly change replay expectations from \`actions: \[\]\` to a config action.

A relay client reconnecting before reauthentication after a long project clone or a series of host-setting/catalogue changes must download and parse every intermediate full configuration before it can make progress. MissionControlProjects publishes catalogue progress repeatedly, and the global replay buffer can retain 1,000 actions, so a sizeable MCP/customization config is duplicated many times in one Web PubSub response.

**Evidence:** \_restoreReconnectSubscriptions iterates the entire replay buffer and pushes every relevant envelope; this changed predicate makes RootConfigChanged relevant pre-auth. \_recordAndBroadcastAction stores every successful config update in \_relayRootConfigEnvelopes as \`{ config: values, replace: true }\`, where \`values\` is a deep clone of the complete native config plus the extension overlay, and \_projectRelayRootAction returns that full envelope. MissionControlProjects.\_publish emits these actions for clone start/progress/completion. The Mission Control transport serializes the whole reconnect result and chunking rejects payloads above 32 MiB.

**Suggested direction:** When projecting a pre-auth replay, collapse successful RootConfigChanged envelopes to the latest full \`replace: true\` envelope (preserving the latest server sequence), or switch to a fresh root snapshot once more than a small bounded amount of config history would be replayed. Intermediate full replacements are not needed to reconstruct the final catalogue/config state.

### Scenario 3: A Mission Control client reconnects before reauthentication and requests replay of missed root updates

- Critical path: Reconnect restores the root subscription, scans the bounded replay buffer, retains every now-allowed RootConfigChanged event after the client's sequence, projects each to its captured full replacement config, then serializes the entire actions array into one reconnect response before the client can resume.
- Scaling input: Missed root-config/catalogue update count U (up to the 1,000-entry replay buffer) times complete overlaid config size C. Subscription URIs are deduplicated, but replayed config actions are not coalesced.
- Effective concurrency: Replay construction is synchronous after subscription restoration. One reconnect response is serialized/chunked; lane framing permits a maximum 32-MiB application payload and queues chunks under per-lane/global backpressure.
- Cache behavior: The replay buffer is a warm bounded history, not a latest-value cache. Each config envelope has a precomputed full replacement overlay, but all historical replacements are included. If the cursor is older than the buffer or baseline is missing, the code falls back to one current snapshot instead.
- Mechanism confidence: Very high: the changed allowlist, replay scan, 1,000-entry bound, full replacement projection, and 32-MiB framing ceiling are directly evidenced.
- Magnitude uncertainty: Exact missed-update counts and host-config sizes vary, so severity is medium rather than high. Long clones, settings changes, authentication-triggered catalogue publications, and temporary mobile disconnects provide realistic multiplicity.
- Expensive boundaries:
