## Performance regression fixes detected (1)

### 1. cache-lifecycle

**Fix location:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts:8683` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts:8676`  
**Introducing path:** `src/vs/platform/agentHost/node/copilot/copilotAgent.ts`  
**Introducing commit:** `be2aeccba1a5853e07d22d23f0419a6e2a4b4cee`  
**Mechanism family:** `cache-lifecycle`  
**Performance category:** `latency`  
**Confidence:** 0.94

**Mechanism:** A workspaceless chat was created with scratch guidance in its system prompt, but resume read the flag from the SDK-session database instead of the host-owned session state. When that provider metadata lacked the marker, resume dropped the guidance, changed the provider-bound system prompt, and invalidated exact-prefix prompt-cache reuse for the conversation's next model request.

**Symptom:** The first model turn after restoring a workspaceless conversation had to process an uncached changed system prompt, increasing prompt-prefill work and time to first output instead of reusing the conversation's warm prompt cache.

**Fixed behavior:** The changed lookup prefers the owning session's retained host setting and falls back to provider metadata only when the host has no value. The resume launch plan now receives the same workspaceless value as creation, keeping the system prompt stable so a resumed first turn can reuse the existing prompt cache rather than processing an altered prompt prefix.

**Evidence:** Before this change, `_resumeSessionOnce` reads metadata for the SDK session URI and `_readSessionMetadata` derived `workspaceless` only from that storage's `AH_META_WORKSPACELESS_DB_KEY`. The added tests construct the realistic host-owned workspaceless state separately and prove that create/resume system messages must be byte-identical. `CopilotSessionLauncher` maps the flag into `IAgentHostPromptContext`, and `AgentHostPromptRegistry` conditionally appends `AGENT_HOST_WORKSPACELESS_INSTRUCTIONS`; therefore losing the flag changed the provider-bound system prompt on resume. Repository configuration explicitly documents that stable system prompts enable cross-session prompt-cache reuse, and SDK usage metadata exposes prompt-cache writes. The blamed base line is the old provider-storage-only lookup introduced by be2aeccba1a5853e07d22d23f0419a6e2a4b4cee.

The added setting lookup and launch-plan property do not create or move any boundary.
- Scaling input: Cost scales with the number of explicitly created peers/forks, one launch per chat. There is no changed collection fan-out. Fork database-copy cost continues to scale with source history size, but that mechanism is pre-existing and unaffected.
- Effective concurrency: Minting uses the existing session/source queue, serializing operations that share the source unless \`independentQueue\` is explicitly requested. The diff does not change queue selection or launch concurrency.
- Cache behavior: A new peer/fork now receives the same workspaceless prompt layer as its parent. On a cold provider cache this adds only the required bounded instruction block; when compatible prompt prefixes are cached, stability permits reuse rather than defeating it. No host metadata cache is invalidated.
