# Performance review: chat: Hide unavailable MCP Gallery source

[PR #342193](https://github.com/microsoft/vscode/pull/342193) at `4dee1b673f83d42a32730fbc384ee0f798ae5732`

## Findings (1)

### 1. [medium] Avoid the two-phase catalog load while manifest availability initializes

**Finding ID:** `PERF-B963A8542175`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceWorkbenchService.ts:36</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** network requests to every enabled non-MCP customization marketplace provider, plus the MCP manifest version probe  
**Scaling:** On VS Code Web, one opening of Browse Customizations while a custom MCP gallery without an explicit version initializes causes the first catalog request to fan out across all enabled non-MCP providers; when the manifest probe completes, the source event cancels that request and fans out across those providers again. The duplicate count grows with configured plugin/provider marketplaces and other enabled feeds.  
**Outcome:** extra network I/O and a restarted loading critical path, increasing time to stable Browse results  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, MCP was present in \`sources\` immediately. The first combined query started all providers once; the MCP provider awaited the same coalesced manifest initialization while the other providers ran in parallel, so manifest discovery did not require a second whole-catalog query.  
**Changed behavior:** The platform source list now temporarily omits MCP during asynchronous manifest initialization, publishes non-MCP results from an initial all-sources query, then announces a source change that invalidates and reloads the whole catalog after initialization.  
**Confidence:** 0.94 — The delayed web registration, initial status, network-awaiting initialization, immediate first catalog load, forced source-event reload, and per-provider query fan-out are all directly traced. Exact latency depends on registry and provider response times, but duplicate or partially duplicated boundary work is deterministic when the first catalog load starts before version negotiation completes.

**Causal diff evidence:** The added getter at line 36 now excludes MCP whenever the delayed web manifest service is still in its initial \`Unavailable\` state, while the added constructor call at line 45 starts asynchronous initialization. Completion then flows through the newly exposed source-change event and forces the consumer to reload.

In web sessions using a custom version-negotiated MCP registry, opening Browse Customizations can issue duplicate plugin/feed/connector catalog requests and reset the loading UI after the potentially slow registry probe. More configured marketplaces produce more duplicated requests.

**Evidence:** \`IMcpGalleryManifestService\` is delayed in \`workbench.web.main.ts\`; \`WorkbenchMcpGalleryManifestService\` initializes \`currentStatus\` to \`Unavailable\`, and a custom URL with no version awaits serial \`checkVersion\` network requests before \`update()\` emits the status event. The changed constructor starts that work, while this changed getter omits MCP until it completes. \`AiCustomizationDiscoveryPage.setVisible()\` immediately calls \`loadCatalog(false)\`; its source-change listener calls \`scheduleMarketplaceRefresh(true)\`, whose \`handleAvailabilityChanged(true)\` cancels the request, clears the browse cache, and calls \`loadCatalog(false)\` again. \`CustomizationMarketplaceService.query()\` invokes every selected provider concurrently, so all non-MCP feeds already started by the first query are invoked again.

**Suggested direction:** Do not expose the initialization placeholder as a real unavailable source state. Preserve MCP in the source set while availability is unknown (for example with an explicit initializing/unknown state), letting its provider await the coalesced manifest promise in the first combined query; only publish a source change once initialization establishes that MCP is actually unavailable or later changes availability.
