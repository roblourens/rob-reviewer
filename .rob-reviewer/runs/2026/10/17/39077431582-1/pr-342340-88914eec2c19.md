## Findings (1)

### 1. [medium] Filter guidance changes before invalidating all migration discovery

**Finding ID:** `PERF-07D76FEEE3F4`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMigrationServiceImpl.ts:64</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** filesystem searches and reads, extension-provider discovery calls, secret-storage checks, and repeated migration-plan allocations  
**Scaling:** Cost grows with the number of agent/tool-set registration events times the number of live migration consumers and, on each discovery, with configured prompt locations, workspace folders, and distinct MCP source files. Agent registration commonly fires again for implementation/metadata updates, and MCP/internal tool sets also change even though both classes are excluded from guidance.  
**Outcome:** excessive I/O and repeated/cancelled discovery work during extension activation and MCP/tool initialization, increasing startup and migration-surface latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Agent implementation/metadata changes and language-model tool-set changes were not part of onDidChangeCustomizations, so chat notices, Sessions navigation, and other subscribers did not rerun full migration discovery for those events.  
**Changed behavior:** The added Event.map(onDidChangeAgents) and toolSets observable are broadcast directly through onDidChangeCustomizations. Consumers respond by calling computeMigrationHint or refreshing the editor; computeMigrationHint runs all migration categories in parallel, including four unique prompt-file inventories and MCP migration planning.  
**Confidence:** 0.96 — The changed subscriptions, excluded item classes, event firing sites, downstream consumers, and filesystem/MCP call paths are all directly traced. Exact timing and cache warmth vary, which limits severity, but the unfiltered fan-out and cold-path boundary work are deterministic.

**Causal diff evidence:** RIGHT lines 64-65 add chatAgentService.onDidChangeAgents and the entire toolsService.toolSets observable to the shared invalidation event, without filtering to the participant/tool-set inventory accepted by RIGHT lines 83-104 or coalescing bursts.

When extensions or MCP servers register participants/tool sets, every live migration notice/navigation/editor consumer can restart full discovery. Cold or invalidated prompt caches search user/workspace locations and extension providers, while MCP planning reads each distinct source configuration and may query secret storage; bursts cancel prior work without globally coalescing the replacement calls.

**Evidence:** ChatAgentService.onDidChangeAgents fires for registerAgent, registerAgentImplementation, updateAgent, dynamic agents, and disposal, although computeMigration filters core/default/dynamic participants. ILanguageModelToolsService.toolSets contains internal and MCP sets, although computeMigration accepts only user and eligible extension sets; MCP tool sets are created per enabled server. ChatCustomizationMigrationNotice and CustomizationsNavigationState subscribe to onDidChangeCustomizations and immediately call computeMigrationHint. That method invokes UserData, PromptFiles, ConfiguredLocations, and MCP discovery; listPromptFiles cold paths scan user/local locations and extension providers, and AgentHostMcpServerMigrationProvider.createPlan reads grouped MCP source files. These newly irrelevant events therefore fan out into concrete boundary work.

**Suggested direction:** Expose a guidance-inventory change signal that fingerprints only eligible static third-party participants and user/eligible extension tool sets, and fire once when that filtered inventory actually changes. Ignore implementation/metadata-only agent events and internal/MCP/external/hidden tool-set churn; coalesce registration batches before forwarding to full migration consumers.
