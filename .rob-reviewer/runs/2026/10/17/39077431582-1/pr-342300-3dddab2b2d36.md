### Scenario 1: Normal catalog synchronization for an imported/loaded session after list-visible metadata, discovery, passive metadata, or reconciliation changes

- Critical path: The request is built, the per-session catalog queue and session-state exclusive section are acquired, central session state is adopted, session.db receives the metadata plus receipt transaction, and the central catalog is upserted before synchronization completes. The new \`legacyMetadata\` snapshot runs synchronously immediately before adoption and is therefore on this path, but it is an in-memory render with no boundary crossing.
- Scaling input: The new snapshot scales with \`Object.keys(request.legacyMetadata)\`; most requests carry a bounded set of session keys, while map-shaped Git/GitHub metadata can scale with the session's working-directory set and chat-specific overrides can scale with changed chat metadata. It does not scan all sessions. Reconciliation selects at most 50 sessions per batch and limits cross-session work to 4.
- Effective concurrency: Catalog synchronization and session-state operations are serialized per session/storage key. Reconciliation permits up to 4 independent sessions concurrently; the diff does not change either limiter or create new aggregate parallelism.
- Cache behavior: The session state must already be loaded in \`\_records\` when the new \`legacyMetadata\` call executes; cold loading remains owned by the enclosing exclusive section. The snapshot reads the loaded model and introduces no cache key, miss, retry, negative cache, or coalescing change. Existing mirror writes remain scheduled/coalesced on a 250 ms window.
- Mechanism confidence: High: the new call is synchronous against an already-loaded record, and the implementation shows only rendering/allocation rather than filesystem, IPC, or database access.
- Magnitude uncertainty: Exact metadata-map sizes and render duration vary by session, but the changed steady-state mechanism is a single in-memory pass and does not add an expensive boundary. There is no evidence that realistic key cardinality turns it into user-visible latency.

### Scenario 2: A catalog synchronization is superseded while its session.db receipt write is in flight, such as owner reload during restored-subagent admission or a stale passive metadata continuation

- Critical path: After the local receipt write returns \`cancelled\`, the new rollback writes the previously rendered values back to central state before returning the pending/cancelled result. The coalesced mirror may later settle to session.db; it is not needed before the cancelled result unless an explicit idle drain runs.
- Scaling input: Rollback work scales with the metadata keys in the single cancelled request and occurs once for that cancelled receipt attempt. It does not loop over sessions or history. Cancellation is caused by the per-operation validator becoming stale.
- Effective concurrency: The rollback executes inside the existing per-session session-state exclusive section and catalog queue, so it is serialized with other work for that session. Different reconciliation sessions remain bounded at concurrency 4; no new burst is introduced.
- Cache behavior: The previous values are captured from the loaded session-state model before adoption. No cache is introduced. The adoption and undo both use the existing coalesced mirror scheduler, so multiple dirty entries still produce one delayed mirror flush rather than one flush per key.
- Mechanism confidence: High: the call path and database write are explicit, the per-session sequencer is established, and the test exercises both set and transition cancellation paths.
- Magnitude uncertainty: Database latency varies by platform and load, but the additional transaction is exactly one per superseded write, is serialized rather than bursty, and cancellation is exceptional. The transaction is intentional cleanup necessary to preserve cancellation semantics.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentHostCatalogSyncService.ts:695</code>: Restore the pre-adoption metadata in agent-host.db via \`writeLegacyMetadata\`; cardinality: One central-state transaction for one cancelled local receipt attempt; empty patches short-circuit in \`\_writeCentral\`.
    - Introduced by diff: true; previous behavior: Before the diff there was no rollback transaction; stale adopted values remained and were later mirrored.; critical-path effect: Introduced on the cancellation result's critical path so stale adopted state cannot escape the exclusive section.
  - database at <code>src/vs/platform/agentHost/node/agentHostSessionStateStore.ts:runExclusive mirror scheduler</code>: Flush dirty legacy metadata to session.db through the coalesced mirror; cardinality: At most one coalesced flush for the dirty session after the 250 ms window (or an explicit idle drain), not one per metadata key or per adoption/undo write.
    - Introduced by diff: false; previous behavior: The cancelled adoption already scheduled a coalesced mirror before the PR; the diff changes the value ultimately mirrored back to the prior value, not the flush fan-out.; critical-path effect: Normally off the cancellation critical path; explicit \`whenIdle\` drains it before proceeding.
  - database at <code>src/vs/platform/agentHost/node/agentHostCatalogSyncService.ts:\_writeThroughCentral callback</code>: Attempt the guarded metadata-and-receipt transaction in session.db; cardinality: One guarded attempt that returns \`cancelled\`.

- Verdict: No reportable performance regression. The one added database write is bounded to cancellation cleanup and prevents a stale mirror write; there is no unbounded repetition, fan-out, or concurrency amplification.

### Scenario 3: Unit test settles session-state mirrors before asserting the final session.db title

- Critical path: After reconciliation, the added \`whenIdle(undefined)\` waits for queued session-state work and actively flushes loaded records before the test reads session.db. This affects test execution only, not a product workflow.
- Scaling input: The drain scales with loaded test-store records and sequencer keys in this isolated service instance; the test invokes it once per receipt-path case.
- Effective concurrency: The drain waits queued work and flushes records with \`Promise.all\`; it does not change product concurrency.
- Cache behavior: It drains existing loaded records and scheduled mirrors; it creates no cache or retained state.
- Mechanism confidence: High: \`whenIdle(undefined)\` explicitly waits sequencers and flushes every loaded record.
- Magnitude uncertainty: The isolated store may hold several records, but the test fixture bounds them and the drain cancels scheduler delays before flushing. No product latency is affected.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/test/node/agentService.test.ts:27299</code>: Flush pending legacy mirrors for loaded test session-state records; cardinality: One global idle drain in each of the two test cases, over records loaded by that isolated test service.
    - Introduced by diff: true; previous behavior: The test read session.db without waiting for pending mirror work.; critical-path effect: On the test's assertion path only; it replaces a race against the 250 ms scheduler with an immediate drain.
- Verdict: No reportable product performance issue; the added test-only drain is bounded and necessary to assert settled persistence deterministically.
