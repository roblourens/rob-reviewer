### 1. cache-lifecycle

**Fix location:** `src/vs/platform/github/common/githubRateLimitCoordinator.ts:103` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/github/common/githubRateLimitCoordinator.ts:107`  
**Introducing path:** `src/vs/platform/github/common/githubRateLimitCoordinator.ts`  
**Introducing commit:** `6a60e32fab82e03830238273f20cef26128602d8`  
**Mechanism family:** `cache-lifecycle`  
**Performance category:** `latency`  
**Confidence:** 0.98

**Mechanism:** A generic authorization denial was stored as a negative cooldown entry, delaying all later requests for the same account/resource for at least 60 seconds despite healthy quota.

**Symptom:** After a generic 403 containing "Rate Limit Exceeded", otherwise valid REST, GraphQL, download, or bootstrap work for the same quota bucket could remain queued or time out behind an invented 60-second cooldown.

**Fixed behavior:** The shared classifier now accepts a generic 403 body only when exhausted-quota or Retry-After evidence exists, or when the explicit "API rate limit exceeded" message has no usable remaining-quota feedback. Healthy-quota generic denials remain authorization failures and no longer create the 60-second queued-request delay.

**Evidence:** In the base revision, line 107 classified any HTTP 403 body containing "rate limit" as throttling. updateFromResponse then assigned the unhinted 60,000 ms blockedUntil, CooldownState.getDelay exposed that delay, and RequestQueue skipped matching account/resource requests until its wake timer. The added bootstrap test exercises the concrete trigger—a 403 body "Rate Limit Exceeded" with x-ratelimit-remaining: 4999—and verifies that subsequent requests should dispatch without a cooldown.
