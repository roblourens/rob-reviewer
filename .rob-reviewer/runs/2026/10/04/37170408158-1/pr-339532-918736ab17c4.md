# Performance review: Copilot: migrate embedding-backed features to Metis

[PR #339532](https://github.com/microsoft/vscode/pull/339532) at `918736ab17c4dfc1b5490cbf6f20e687cdc4ee87`

## Findings (1)

### 1. [medium] Keep binary Metis index vectors compact

**Finding ID:** `PERF-505ECB865E87`  
**Location:** <code>extensions/copilot/src/platform/embeddings/common/vscodeIndex.ts:294</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Long-lived JavaScript number-array elements for every cached setting and command embedding, plus CPU work for their dot products  
**Scaling:** Resident elements and dot-product iterations scale with the total settings and commands loaded from core and installed extensions; changing each vector from 512 to 1024 dimensions doubles both per-entry quantities.  
**Outcome:** Increased retained heap and CPU/GC pressure, with longer synchronous ranking work after each settings search or VS Code assistant query  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The settings and command caches and query embeddings used text3small\_512, so each retained item had 512 numeric components and each distance calculation iterated 512 components.  
**Changed behavior:** The changed cache constructors load Metis 1024-dimensional vectors for both complete indexes, while BaseEmbeddingsIndex keeps every vector in its session-long maps and rankEmbeddings/distance scans every component of every indexed entry.  
**Confidence:** 0.94 — The model dimensions, number-array representation, full-index retention, and component-wise ranking loop are explicit in the repository, so the 2x scaling mechanism is certain. Exact heap and latency magnitude depends on each installation's contributed setting/command count and engine representation, which is why severity is medium rather than high.

**Causal diff evidence:** RIGHT line 294 replaces EmbeddingType.text3small\_512 with EmbeddingType.metis\_1024\_I16\_Binary for the complete settings cache; the adjacent changed command-cache line makes the same replacement, increasing retained vector width for all entries from 512 to 1024.

On installations with thousands of core and extension-contributed settings/commands, loading these indexes now retains twice as many JS numeric elements, and every settings-editor search or VS Code assistant lookup performs twice as many multiply-add iterations before returning ranked results.

**Evidence:** EmbeddingType metadata defines Metis at 1024 dimensions versus text3small at 512, and EmbeddingVector remains readonly number\[\]. RemoteEmbeddingsCache JSON-parses these arrays, BaseEmbeddingsIndex.\_calculateEmbeddings attaches them to every item in \_items, and distance() loops to the vector length. The changed lines 294-298 migrate both all-settings and all-commands caches to Metis, while provideSettingsSearchResults and VscodePrompt synchronously rank the full loaded indexes on their response path.

**Suggested direction:** Convert cached binary document embeddings to a compact representation (for example a bit-packed or Int8-backed vector) as they are loaded and make distance consume that representation, rather than retaining 1,024 boxed/JS-number components per entry; keep query/document semantics and ranking results unchanged.
