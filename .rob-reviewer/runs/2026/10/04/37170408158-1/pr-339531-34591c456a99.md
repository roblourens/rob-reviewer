# Performance review: github: add reusable repository queries

[PR #339531](https://github.com/microsoft/vscode/pull/339531) at `34591c456a990d7a6ad930a663ee1e4eabac7367`

## Findings (1)

### 1. [medium] Do not retain every distinct repository search response

**Finding ID:** `PERF-285196D9A00E`  
**Location:** <code>src/vs/platform/github/common/githubQueryServiceImpl.ts:563</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** decoded JSON response strings and LRU cache entry objects  
**Scaling:** Retention grows with the number of distinct successful query/page URLs, up to 500 entries per authorized client; bytes per entry grow with repository-result count (up to 100) and metadata size.  
**Outcome:** retained memory and increased GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, the shared GitHub query service had no arbitrary repository-search route, so changing repository-picker text could not populate its long-lived transport cache with distinct search result bodies.  
**Changed behavior:** Repository search now stores each successful, ETagged search response body under its full URL (including arbitrary \`q\`, page, sort, and order) in the client transport's shared LRU.  
**Confidence:** 0.94 — The changed request sets \`etag: true\`; \`GitHubTransport\` keys cache entries by the complete URL and retains the decoded response body in a 500-entry LRU, while search results can contain 100 full repository objects. The documented target consumers are type-ahead repository pickers, and the existing remote-source picker dispatches successive distinct queries after a 300 ms debounce. Exact concurrent requests remain coalesced even with ETags disabled. The exact retained byte total depends on result density and session usage, affecting severity rather than the mechanism.

**Causal diff evidence:** The added \`searchRepositories\` request at RIGHT line 563 opts every \`/search/repositories?q=...&page=...\` response into transport ETag caching; this search endpoint and its arbitrary query/page key space did not exist in the shared query service before this PR.

Repeated repository-picker searches retain obsolete full search pages for the lifetime of the authorized client, growing memory and GC pressure as users type different queries or reopen the picker; at the 500-entry cache limit this can retain hundreds of dense 100-repository JSON pages.

**Evidence:** \`searchRepositories\` builds a URL containing the trimmed user query and pagination options, then sets \`etag: true\`. \`GitHubTransport.\_restCacheKey\` includes the full URL, and \`\_executeRest\` stores the complete decoded \`body\` in \`\_restCache\`, an \`LRUCache&lt;string, IRestCacheEntry&gt;(500)\` whose limit is entry-count rather than bytes. Thus no two distinct search strings share an entry, and each dense page can retain JSON for up to 100 repository records. The existing intended remote-source consumer invokes search as the quick-pick value changes, so repeated picker use realistically accumulates many large entries for queries unlikely to be repeated.

**Suggested direction:** Keep exact-request in-flight sharing but disable representation caching for search (\`etag: false\`), or place search results in a separate short-lived, byte-bounded cache; reserve the existing ETag cache for stable repository/list URLs that are realistically revalidated.
