## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/platform/github/common/githubCredentialService.ts:127` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/github/common/githubCredentialService.ts:132`  
**Introducing path:** `src/vs/platform/github/common/githubCredentialService.ts`  
**Introducing commit:** `ff1603fb33ea729b0d8cab7f05ccc80575011a55`  
**Mechanism family:** `repeated-work`  
**Performance category:** `network`  
**Confidence:** 0.98

**Mechanism:** Each authentication or identity failure discarded the only credential generation, while invalidation listeners immediately rescheduled all subscribed resources; with no retained failure state, every outage round reissued identity and resource network requests at zero delay.

**Symptom:** During a persistent GitHub authentication/network outage, active Agent Merge pull-request subscriptions could sustain a zero-delay request loop whose work scaled with subscribed sessions and fragments.

**Fixed behavior:** The credential service now retains consecutive failures per host/token, waits with jittered exponential backoff before rebuilding identity, and coalesces all callers behind the one generation created after the delay. Token or endpoint replacement releases the wait, preserving recovery.

**Evidence:** In the base revision, a failed identity generation clears `_current` without retaining any failure/backoff state (base line 132, introduced by ff1603fb33ea729b0d8cab7f05ccc80575011a55). Authentication errors also invalidate the generation and synchronously notify `PullRequestResourceService` and `GitHubQueryService`; both handlers reschedule every active fragment/entity at `now`, and each refresh calls `getCredential`, so the next coalesced generation immediately performs another network `GET /user`. The changed line gates that generation before identity resolution, while added failure recording occurs both on identity-resolution failure and before authentication invalidation events.

### Scenario 1: Agent Merge background pull-request refresh during a persistent authentication or identity outage

- Critical path: Each active session refresh reaches \`PullRequestResourceService.\_runFragmentFetch\`, then \`GitHubCredentialService.getCredential\`; after a recorded failure the new gate must expire before one shared \`/user\` identity request and subsequent fragment request can proceed. This is background work except authoritative refresh and merge preparation, where the same chain is on the caller's critical path.
- Scaling input: Number of active Agent Merge sessions, distinct pull requests, and effective fragments per subscription; identity work remains one request per generation while fragment work scales by distinct pull request/fragment after coalescing.
- Effective concurrency: Credential generation and identical transport reads are coalesced. GitHubRequestQueue permits at most four global, two per host, and one active request per account, so the post-delay burst is serialized per account; many waiting callers still share one credential generation.
- Cache behavior: A successful current credential is reused. Failures are now negatively remembered per host/token with one immediate retry, exponential 5s-to-120s delay, jitter, and five-minute decay. Token/host replacement releases the gate; transport ETags and in-flight maps continue to coalesce exact reads.
- Mechanism confidence: High: changed failure recording, gate wait, invalidation handlers, and network call path were all traced.
- Magnitude uncertainty: The exact number of simultaneously active sessions per host and outage duration varies, but the zero-delay pre-diff loop and the bounded post-diff schedule are directly established.
- Expensive boundaries:
  - network at <code>src/vs/platform/github/common/githubCredentialService.ts \`\_resolveIdentity\`</code>: Resolve the current token's stable account identity with REST \`GET /user\`.; cardinality: One in-flight identity request is coalesced per credential generation; waiting callers scale with active sessions/fragments but share the generation after the delay. A network GET may retry once inside the transport.
    - Introduced by diff: false; previous behavior: The same boundary existed, but every failed/invalidated generation could be rebuilt immediately; invalidation listeners rescheduled all active work at \`now\`, producing repeated outage rounds with no retained delay.; critical-path effect: Required before any pull-request fragment or entity request can proceed with an account-scoped credential.
  - network at <code>src/vs/platform/github/common/pullRequestResourceService.ts \`\_runFragmentFetch\` -&gt; \`PullRequestQueryService.fetch\`</code>: Fetch subscribed pull-request fragments over REST or GraphQL.; cardinality: Up to the effective subscribed fragment set per pull request (Agent Merge requests core, three conversation fragments, review threads, checks, and mergeability); transport coalescing applies only to identical reads, and the request queue serializes one request per account with two per host and four globally.
    - Introduced by diff: false; previous behavior: The boundaries were identical, but authentication invalidation immediately rescheduled every fragment and could repeat them each outage round.; critical-path effect: Authoritative subscription refresh waits for core and then all interested fragments; steady polling is background.
- Verdict: No performance regression. The change removes repeated network work during outages and keeps aggregate request concurrency bounded.

### Scenario 2: Capability-dependent checks, review-thread, and mergeability refresh after an unusable GraphQL introspection result

- Critical path: Each capability-dependent fragment first calls \`GitHubHostCapabilitiesService.getCapabilities\`. A cold host performs one coalesced GraphQL introspection; an unusable result now returns cached degraded capabilities until retryAt, after which the next lookup re-probes. Fragment fallback work remains on authoritative-refresh and merge-preparation critical paths.
- Scaling input: Distinct subscribed pull requests and capability-dependent fragment polls during a degraded window; the negative-cache key cardinality is effectively one for the configured host/version in the production service.
- Effective concurrency: The capability probe is promise-coalesced per host/version. Distinct fallback requests are constrained by the shared GitHub request queue to one active request per account.
- Cache behavior: Positive and schema-negative results remain cached indefinitely until endpoint clear. Unexpected degraded results are now negatively cached with escalating retry windows and discarded immediately on credential generation or endpoint change.
- Mechanism confidence: High for cache and boundary behavior; moderate for how often transient introspection errors recover inside the first window.
- Magnitude uncertainty: A transient probe may recover before the first 60s retry, but Agent Merge's relevant background cadences are 60s or longer, limiting extra fallback work; interactive mutation timing varies.
- Expensive boundaries:
  - network at <code>src/vs/platform/github/common/githubHostCapabilitiesService.ts \`\_probe\`</code>: GraphQL schema introspection for pull-request/repository capabilities.; cardinality: One coalesced cold probe per host and enterprise version. After an unusable result, at most one re-probe per escalating 60s-to-15m window for the same credential generation.
    - Introduced by diff: false; previous behavior: Successful/schema-negative probes were cached, but other unusable results deleted the entry immediately, so the next capability lookup reissued introspection.; critical-path effect: Cold capability-dependent fragment requests wait for it; warm positive or degraded-cache lookups do not cross the network.
  - network at <code>src/vs/platform/github/common/pullRequestQueryService.ts \`\_fetchChecksFallback\` and \`\_fetchMergeabilityFallback\`</code>: REST fallback reads for checks and mergeability when degraded capabilities disable GraphQL.; cardinality: Per pull request, checks use at least two REST calls plus check-run pagination, mergeability uses one REST call, and review threads perform no fallback call. Calls remain grouped by fragment and account-serialized.
    - Introduced by diff: false; previous behavior: The same fallbacks ran for every caller receiving the unusable probe result; a later lookup could re-probe immediately and switch back to GraphQL sooner.; critical-path effect: These calls complete the degraded fragment refresh and can be on authoritative refresh or merge-preparation paths.
- Verdict: No reportable regression. The bounded negative cache removes an otherwise per-lookup introspection request; fallback boundaries are pre-existing and production polling cadence limits the short recovery tradeoff.

### Scenario 4: REST or GraphQL request following primary or secondary rate limiting without a usable retry hint

- Critical path: The refusal response updates the shared account/resource coordinator. Subsequent requests call \`\_enqueueWithRateLimit\` and wait before entering the request queue or crossing the network; recovery is delayed by 60 seconds when no future hint is usable.
- Scaling input: Number of callers sharing the affected account/resource and duration/frequency of GitHub refusals; waiting callers coalesce on state, while timers are per request.
- Effective concurrency: Waiters remain outside GitHubRequestQueue during cooldown, so they do not consume its four global/two host slots. Once released, the queue still permits only one active request per account.
- Cache behavior: Rate-limit state is account/resource scoped and cleared when that account is invalidated. Retry-After wins; reset is honored only for spent quota; otherwise a 60s floor applies.
- Mechanism confidence: High: response classification, shared state, pre-queue wait, and tests for all hint shapes are explicit.
- Magnitude uncertainty: Actual GitHub refusal duration is external, but the changed boundary suppression and maximum unhinted floor are exact.
- Expensive boundaries:
  - network at <code>src/vs/platform/github/common/githubTransport.ts \`\_enqueueWithRateLimit\` and githubRateLimitCoordinator.ts \`updateFromResponse\`/\`markGraphQLRateLimited\`</code>: Subsequent REST or GraphQL request after a rate-limited refusal.; cardinality: All requests for the affected resource share one resource block; secondary limits share one account-wide block. - Verdict: No performance regression. The intentional latency prevents immediate repeated network calls, avoids holding queue slots, and corrects overlong secondary-limit waits.
