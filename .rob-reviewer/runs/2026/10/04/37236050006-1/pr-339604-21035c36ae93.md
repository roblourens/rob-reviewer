### Scenario 1: First prompt in a new Cloud Sandbox session (default Cloud provider with sandbox enabled or explicit sandbox provider)

- Critical path: The draft now waits for Mission Control task creation, sandbox connection/handshake, repository preparation to reach ready, optional model propagation, and first-turn dispatch. The repository-ready wait is newly on the critical path and can last until the helper's five-minute deadline, but it is the explicit behavior required to prevent dispatch before the checkout exists; progress rendering is local and does not add another remote boundary.
- Scaling input: One logical first request per draft. Overlapping sends for the same draft are rejected, connect attempts are coalesced per environment, and repository preparation performs at most one clone request for this call when no matching ready/cloning project is advertised. Progress processing is O(root-state updates × advertised projects), normally one repository and bounded to setup.
- Effective concurrency: Per-draft first sends are serialized by \_sandboxSends; CloudSandboxSessionContribution coalesces concurrent connects by environment address. Separate drafts/environments can still provision concurrently as before. The newly invoked preparation has a per-call coalescing map, but this path invokes it once after same-draft overlap is rejected.
- Cache behavior: A live connection is reused and an in-flight connection is coalesced by address. Root project state is the authoritative warm state: a matching ready project resolves immediately and a matching cloning project is joined without another clone call. A cold/missing project may issue one extensions/cloneProject request. There is no negative cache, but the operation is scoped to one setup attempt and has cancellation plus a five-minute deadline.
- Mechanism confidence: High confidence in the newly ordered critical path and zero-or-one clone IPC because the contribution directly awaits the established preparation helper. High confidence that task creation, connection, and first-turn dispatch were pre-existing boundaries.
- Magnitude uncertainty: Repository clone duration and the frequency of a cold root state are environment-dependent. The changed wait is intentional and bounded; repository progress can generate many updates, but project cardinality is expected to be small and no evidence shows a material CPU or boundary fan-out regression.

### Scenario 2: Cancel sandbox setup while the environment is provisioning or connecting

- Critical path: Cancellation now clears the draft preparation surface and rejects the caller immediately through raceCancellationError. An already-started connection continues off the UI critical path until its existing bounded timeout/success/failure, after which the provisioning guard is released.
- Scaling input: At most one continuing connection attempt per canceled environment because pending connects are coalesced by address. Retained provisioning state scales with simultaneously canceled, still-connecting environments and is bounded by each connection's existing timeout.
- Effective concurrency: The base contribution shares one pending connection promise per address. Cancellation does not create retries or additional attempts; it detaches the request while the original connection settles.
- Cache behavior: The pending-connect map and provisioning set retain the environment only during the bounded attempt. Success leaves the normal reusable live connection; failure removes the pending entry and releases the provisioning guard. No indefinite negative cache is added.
- Mechanism confidence: High confidence: the new race lets the caller settle before connectionAttempt, and the finally handler retains \_provisioning until that promise settles; the service has an existing timeout and per-address coalescing.
- Magnitude uncertainty: Users may rarely cancel during VM wake, and the remaining connection duration varies up to the existing deadline. The lifecycle and bound are explicit in the service.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/cloudSandboxAgentHostContribution.ts:provisionSession</code>: Continue the already-started sandbox wake/connection after the request UI is canceled; cardinality: One existing connection attempt per canceled environment, coalesced for that address
    - Introduced by diff: true; previous behavior: Before the diff the caller remained awaiting the same connection attempt, so the work was not detached and the provisioning guard was released only after the await settled.; critical-path effect: Off the canceled caller's critical path; bounded by the pre-existing connection deadline
- Verdict: No reportable regression. The diff improves cancellation latency and intentionally retains a bounded guard so discovery cannot tear down a still-waking environment; it does not add another network attempt or unbounded retention.

### Scenario 3: Display clone percentages and setup messages in the Agents/chat preparation transcript

- Critical path: Root-state notifications synchronously scan advertised projects, parse matching GitHub remotes, and update one observable progress message; the chat view then replaces the progress item by stable id. This is UI-visible but involves no subprocess, filesystem, database, or network call.
- Scaling input: Work scales with root-state change count times project count. During preparation there are two short-lived consumers of project state (readiness and progress tracking); tracking self-disposes at ready/failed and the outer request store disposes it on completion/cancellation.
- Effective concurrency: Updates run serially on root-state events. Message equality suppresses duplicate preparation updates, and the tracker is scoped to one active first request.
- Cache behavior: The current root state is the warm authoritative snapshot. Repository identity is recomputed on each relevant event rather than cached, but the lifecycle is bounded to setup and project cardinality is small; ready/failed terminal states dispose the observer.
- Mechanism confidence: High confidence in the O(events × projects) local CPU/allocation path and bounded observer lifecycle from the added code and disposal branches.
- Magnitude uncertainty: Exact progress event frequency is host-dependent, but percentages are finite/clamped and typical project collections are small. There is no evidence of frame-rate frequency, large collections, or retained history growth.
- Expensive boundaries: none found
- Verdict: No reportable regression. The repeated local scan is bounded to setup, has realistic small cardinality, and does not cross an expensive boundary or establish material UI jank.

- Mechanism confidence: High confidence from the explicit \_usesSandbox checks in startNewSessionRequest and createNewChat.
- Magnitude uncertainty: None material for the changed gating path.
- Expensive boundaries: none found
- Verdict: No performance regression on the non-sandbox path.
