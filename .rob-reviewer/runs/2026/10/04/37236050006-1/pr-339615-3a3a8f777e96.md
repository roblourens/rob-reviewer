<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** serialization-allocation, repeated-work, cache-lifecycle

### Scenario 1: First open of an offline Cloud Sandbox conversation using prefetched persisted AHP history

- Critical path: Environment status resolution completes first; for an offline environment, the prefetched Mission Control history request, JSON body read, event decoding/reassembly, reducer folding, and turns-to-history conversion must complete before the transcript renders. The changed duplicate index and equality check run synchronously on this critical path.
- Scaling input: The complete persisted event count E, duplicate count D after mirror-batch overlap, action count A, and chunk payload bytes. The changed work is O(E) small Map entries plus O(total bytes of D exact duplicate records), while existing reassembly/folding remains O(E + payload bytes + A).
- Effective concurrency: One environment-status request precedes one history request for this activation. The history promise is passed into the read-only handler and consumed once, preventing a duplicate first-open request; replay itself is single-threaded and sequential.
- Cache behavior: The in-flight prefetch is reused for the first open and then deliberately cleared. There is no persistent replay cache or negative cache; this diff does not alter those policies. Sequence tracking is per replay and cleared at mirror epoch restarts, then released after folding.
- Mechanism confidence: High confidence in the synchronous call path and linear scaling; high confidence that no boundary fan-out, concurrency burst, or lifetime retention was introduced.
- Magnitude uncertainty: Very long token-delta histories can contain many records, but the added Map retains only references plus per-entry metadata while the parsed response already owns the full objects. No evidence establishes enough incremental allocation or duplicate comparison to produce user-visible latency or GC pressure.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxSessionContribution.ts:\_isEnvironmentOnline</code>: GET the sandbox environment record to decide between live connection and persisted history.; cardinality: One request per activation attempt for an environment with a task.
    - Introduced by diff: false; previous behavior: The same environment-status request and ordering existed before this diff.; critical-path effect: Must complete before the offline/history branch is selected.
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts:getSessionHistory</code>: GET /agents/tasks/&lt;id&gt;/events and read/parse the complete AHP JSON response.; cardinality: One request for the opening activation; all events for the task are returned and replayed together.
    - Introduced by diff: false; previous behavior: The same single full-history request and replay path existed before the diff; the diff adds duplicate recognition inside replay but no additional boundary calls.; critical-path effect: The response, JSON parsing, replay, and history conversion must finish before transcript content is available.
  - serialization at <code>src/vs/platform/agentHost/common/taskEventReplay.ts:decodeEvents</code>: Reassemble chunk envelopes, parse completed chunk groups, index sequence records, and fold action envelopes.; cardinality: One sequential pass over E persisted records; Map lookup/set is O(E), and deep equality traverses only D records whose sequence number has already appeared, proportional to the duplicated record bytes. Unique records hit equals(undefined, value) and return immediately.
    - Introduced by diff: true; previous behavior: Replay already validated, reassembled, parsed, and folded every record; it did not allocate one Map entry per unique sequence and stopped with an error at the first overlapping record. The added Map is response-scoped and stores references to records already retained by the response array.; critical-path effect: Synchronous CPU and allocations occur after JSON parsing and before transcript rendering.
- Verdict: No reportable performance regression. The new response-scoped linear index is necessary to recognize non-adjacent overlaps, avoids replaying duplicate chunks/deltas, and does not retain history beyond the existing replay lifetime.

### Scenario 2: Later reopen or additional content resolution through the read-only Cloud Sandbox provider

- Critical path: After the one-shot prefetch is consumed, provideChatSessionContent performs a fresh history request, parses and replays the complete response, selects the requested session/default chat, and converts turns before rendering.
- Scaling input: Persisted records and duplicate bytes in the task history per reopen; no multiplication by number of chats because one fetched task response is replayed once and sessions/chats are grouped in memory.
- Effective concurrency: Each provider resolution awaits its own request; no shared replay cache or coalescer exists after first use. The diff neither adds resolutions nor changes request concurrency.
- Cache behavior: Cold on each later resolution by design; first-open prefetch is no longer available. No positive or negative replay result persists, and the diff does not modify this lifecycle.
- Mechanism confidence: High confidence that later resolutions refetch and replay and that this behavior predates the diff; high confidence that the diff adds no request or concurrency amplification.
- Magnitude uncertainty: Frequency of repeated later content resolutions and maximum production history size are not established. The incremental index is transient and linear, so available code evidence does not support a meaningful regression even though repeated opens repeat it.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxReadOnlySessionHandler.ts:\_readHistory -&gt; CloudSandboxApiService.getSessionHistory</code>: Fetch the task's complete persisted AHP event history.; cardinality: One request per later content resolution after the prefetched promise has been consumed.
    - Introduced by diff: false; previous behavior: Later opens already fetched and replayed the complete history afresh so stale prefetch data would not pin the transcript.; critical-path effect: Blocks that transcript resolution until response parsing and replay finish.
  - serialization at <code>src/vs/platform/agentHost/common/taskEventReplay.ts:decodeEvents</code>: Build a per-epoch sequence index and compare repeated sequence records while decoding the fetched response.; cardinality: One linear index construction per fetched history; deep traversal only for repeated sequence numbers, with the index reset on a mirror restart.
    - Introduced by diff: true; previous behavior: The prior decoder had no duplicate index and rejected the first overlap instead of producing a transcript.; critical-path effect: Adds transient CPU/allocation before rendering on each later resolution.
- Verdict: No finding. Existing repeated full-history reads are outside PR causality, and the changed duplicate handling adds only bounded per-response linear work while enabling successful replay.

**Summary:** Reviewed the complete two-file diff and traced offline first-open and later read-only reopen paths through network fetch, JSON parsing, chunk reassembly, reducer folding, and rendering conversion. Considered repeated work, serialization/allocation, cache lifecycle, boundary fan-out, concurrency, and retention. The change introduces a transient per-epoch sequence Map and duplicate-only deep comparisons, but no extra boundary calls, fan-out, persistent retention, or superlinear work; no actionable performance issue was found.
