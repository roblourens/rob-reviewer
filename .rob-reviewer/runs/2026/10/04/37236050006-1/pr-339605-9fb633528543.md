Concurrent activation coalescing is unchanged by the diff, and no loop fans out boundary calls by event or chat.

The changed default-chat inference does not add retained cache state.

### Scenario 2: Open a sandbox conversation while an explicit wake/connect is already succeeding

- Critical path: Activation now joins the existing per-address pending connect, then waits for the registered relay connection's root state to advertise the requested provider. This intentionally moves the already-running wake and relay handshake onto the open's critical path so a temporary offline-history provider cannot win the session resolution.
- Scaling input: One sandbox address/session open. Cost is governed by wake duration and relay handshake latency, not collection size.
- Effective concurrency: \_pendingConnects coalesces all callers for an address onto one promise; calling connect from activation reuses that promise and does not mint another credential or establish another relay. Different addresses remain independent, unchanged by the diff.
- Cache behavior: No response cache is used. The pending-connect map is a short-lived positive in-flight entry removed in finally on success or failure; successful connection state is then reused by the agent-host service.
- Mechanism confidence: High confidence that the critical-path join is real and coalesced because both changed pending-map checks lead synchronously to connect, which returns the stored per-address promise.
- Magnitude uncertainty: A cold wake can take minutes according to the connection-path comments, but prevalence and observed timings are unknown.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxAgentHostService.ts:connect</code>: Mission Control credential/wake request followed by Web PubSub relay establishment and AHP handshake; cardinality: Exactly one already-running connect per sandbox address, shared by activation and the explicit wake caller.
    - Introduced by diff: true; previous behavior: The explicit wake still incurred this boundary, but activation did not join it; activation could instead status-check and resolve against offline history while wake continued.; critical-path effect: The diff makes activation await the existing wake and live host advertisement; it does not create a second wake request.
- Verdict: No reportable regression: moving the existing explicit wake onto activation is the required scheduling change, while coalescing prevents added network work and the initial pending case now avoids the separate environment-status request.

### Scenario 3: Open a sandbox conversation while an explicit wake is pending and then fails

- Critical path: Activation joins the one existing wake attempt. After that promise rejects, it registers the read-only provider and the first session resolution waits for persisted task history. This delays fallback until failure is known, preserving successful-wake handoff semantics.
- Scaling input: One wake attempt and one history response containing E persisted events; no per-event or per-chat boundary fan-out.
- Effective concurrency: The connect remains one shared per-address attempt. On failure, the activation starts one history request for the provider's first open; there is no new burst introduced by the changed lines.
- Cache behavior: The failed pending entry is removed in connect's finally. The fallback history promise is passed to the handler and consumed once; later opens fetch fresh state.
- Mechanism confidence: High confidence in ordering and boundary count from \_waitForActivation, the per-address pending map, and connect's catch/finally lifecycle.
- Magnitude uncertainty: Failure frequency and typical time-to-failure are unknown; the connection attempt is bounded by existing timeout/cancellation behavior.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxSessionContribution.ts:\_waitForActivation</code>: Await the already-running Mission Control wake/credential request and relay connection attempt; cardinality: One shared attempt per address, regardless of concurrent callers reaching connect while its pending entry exists.
    - Introduced by diff: true; previous behavior: Activation could status-check the environment and serve history while the separate explicit wake was still pending.; critical-path effect: The diff places the pending wake before history fallback; a failure must settle before activation can proceed.
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxSessionContribution.ts:\_fetchTaskHistory</code>: Fetch and replay persisted task events after wake failure; cardinality: One prefetched request for the fallback provider's first open.
    - Introduced by diff: false; previous behavior: The same history request existed, but for an offline status it could begin before the separate wake settled.; critical-path effect: Runs after the failed wake and must complete before rendering the transcript.
- Verdict: No finding: the latency shift is an intentional, bounded correctness tradeoff needed to avoid resolving a stand-in while an explicit wake may succeed; the diff neither duplicates the wake nor increases boundary cardinality, and a failed wake still falls back through the existing history path.
