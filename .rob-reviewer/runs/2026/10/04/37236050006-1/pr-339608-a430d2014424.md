# Performance review: sessions: Sync Cloud Sandbox archives through Mission Control

## Findings (2)

### 1. [medium] Run archived discovery scopes concurrently with active scopes

**Finding ID:** `PERF-7B671B042FEC`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts:298</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Mission Control task-list network requests  
**Scaling:** Every discovery now performs at least four sequential list requests instead of two; archived pagination adds up to 20 more sequential requests, and stale focused-window refreshes can repeat this once per minute.  
**Outcome:** increased refresh and startup latency plus doubled steady-state discovery traffic  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Discovery iterated only the two repository scopes, so an empty or warm incremental refresh required two sequential list-task requests.  
**Changed behavior:** The changed scope list adds archived=true variants for both repository scopes, while the existing nested loop awaits every page and scope serially before discovery can reconcile sessions.  
**Confidence:** 0.99 — The sequential awaits, refresh call path, 60-second stale trigger, and before/after request counts are all explicit in code and tests. Only the per-request duration varies by network conditions.

**Causal diff evidence:** The added archived scope entries at lines 298-299 expand the serial loop from \`{withRepository:true/false}\` to four \`{withRepository, archived}\` combinations; no parallelism or deferred archive path was added.

Opening a window, manually refreshing sessions, or returning focus after the 60-second stale interval must wait for two additional network round trips even when the account has no archived tasks. Accounts with paginated archives can block reconciliation behind up to 20 additional list calls.

**Evidence:** \`listSessions\` awaits \`\_sendTask\` inside nested scope/page loops, and \`\_doDiscoverAndSeed\` awaits \`listSessions\` before publishing discovery. The updated tests explicitly raise warm incremental request count from 2 to 4 and a two-page scan from 3 to 5, proving the extra calls are on the critical path rather than background work.

**Suggested direction:** Fetch the independent scope streams concurrently under a small shared limiter, preserving serial pagination and existing failure/checkpoint semantics within each stream, then merge their task maps before reconciliation.

### 2. [medium] Lazy-load archived task details instead of expanding the entire archive

**Finding ID:** `PERF-03D9EE24D9C5`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts:364</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** per-task Mission Control detail GETs, provider objects, registrations, and persisted inventory entries  
**Scaling:** On a cold process, each archived task is absent from \`\_discoveredTasks\`, so all A archived summaries trigger A detail GETs in batches of five; the two archived scopes permit up to 2,000 distinct archived tasks before truncation.  
**Outcome:** cold-start and full-refresh latency grows with the account's archived history  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Archived summaries were excluded by \`\!task.archived\_at\`, so normal startup discovery issued no detail GETs and created no environment providers for archived history.  
**Changed behavior:** All cloud-sandbox summaries, including archived ones, now enter \`sandboxTasks\`; the existing \`\!cached?.session\` branch fetches \`/tasks/{id}\` for each, and the caller eagerly seeds every returned session into a full per-environment provider.  
**Confidence:** 0.98 — The cold-cache condition, one-request-per-task mapping, concurrency limit, eager provider call path, and page bounds are explicit. The only uncertainty is how many archived tasks typical accounts have, which is reflected in medium severity.

**Causal diff evidence:** Line 364 removes the prior \`\!task.archived\_at\` guard, newly feeding every archived task returned by the added archive scans into the existing per-task detail-expansion and provider-seeding path.

A long-lived account with dozens or hundreds of archived sandboxes makes every fresh window process wait through many waves of detail requests before discovery completes, then retains a provider/controller and registrations per archived environment. At the supported 1,000-task-per-scope range this can dominate startup and memory.

**Evidence:** \`sandboxTasks\` feeds \`Promise.all(sandboxTasks.map(... limiter.queue(...)))\`; a cold cache always satisfies \`\!cached?.session\`, causing one \`\_sendTask('/tasks/{id}')\` per summary with concurrency 5. \`\_doDiscoverAndSeed\` waits for that promise and calls \`\_seedDiscoveredSession\` for every result, which invokes \`\_ensureProvider\`. The test suite demonstrates discovery cardinality of 1,000 sessions for one scope.

**Suggested direction:** Keep archived results as lightweight summaries and resolve their environment/session detail lazily or page-wise when archived rows are requested/opened; alternatively supply the binding in a batched list response. Do not eagerly send every archived task through the per-task detail/provider path during normal startup discovery.

### Scenario 2: User archives or unarchives an owning Cloud Sandbox session

- Critical path: The UI/provider sequencer awaits one Mission Control POST; only after success does it update local archive state and persist inventory. Sandbox connection/wake-up is explicitly not on this path.
- Scaling input: One operation per user archive/unarchive action. Rapid toggles queue in order for that provider/controller.
- Effective concurrency: A \`Sequencer\` serializes mutations per environment provider/controller. Independent environment controllers can operate concurrently, but a normal single-session toggle creates one request and no loop/burst.
- Cache behavior: Successful mutation deletes that task from \`\_discoveredTasks\` and increments the discovery generation, preventing stale in-flight discovery from committing. There is no optimistic state cache; rejection retains the previous flag.
- Mechanism confidence: High: the single POST, sequencer, cancellation, cache invalidation, and post-success persistence are explicit and tested.
- Magnitude uncertainty: Actual POST latency varies, but cardinality and serialization are fixed and bounded.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts:setTaskArchived</code>: POST \`/tasks/{id}/archive\` or \`/unarchive\`; cardinality: Exactly one request per dequeued user mutation, with a 10-second timeout.
    - Introduced by diff: true; previous behavior: Archive state changed locally with no network request, so it was not synchronized across clients.; critical-path effect: Local state and completion wait for the POST, preserving server-authoritative ordering.
  - other at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxSessionContribution.ts:\_setSandboxSessionArchived/\_persistInventory</code>: Persist the changed environment inventory entry; cardinality: One batched profile-storage update after each successful mutation, with unchanged entries skipped.
    - Introduced by diff: true; previous behavior: Local provider state changed without updating the shared contribution inventory archive flag.; critical-path effect: Occurs after the POST and before mutation completion; it does not wake or connect the sandbox.
- Verdict: No additional finding. The added network boundary is the required cross-client mutation, is one-per-action, and is intentionally serialized without environment startup.

### Scenario 3: Cross-client archive reconciliation for disconnected or connected environments

- Critical path: A normal discovery scan detects the archive timestamp change, fetches that task's detail if the cache summary differs, then updates the existing provider/controller archive observable and persists inventory. No AHP host action or sandbox connection is required.
- Scaling input: One changed task detail GET per remote archive transition on a warm cache; a cold scan scales with total archived history as covered in the startup scenario.
- Effective concurrency: List calls remain serial; changed detail reads share the concurrency-5 limiter. Local observable updates are synchronous and discovery itself is coalesced.
- Cache behavior: Warm summaries avoid unchanged task details; an \`archived\_at\` difference forces the changed task detail read. Successful local mutations explicitly invalidate that task and stale discovery generation. Cold processes have no \`\_discoveredTasks\` cache.
- Mechanism confidence: High: timestamp comparison, detail-fetch condition, local update path, and absence of host connection are explicit.
- Magnitude uncertainty: Cross-client update frequency is likely low; network latency is unmeasured.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts:listSessions</code>: Incremental active/archived task-list scan and changed-task detail read; cardinality: Four minimum list GETs plus one detail GET for each changed archive timestamp; before the diff there were two list GETs and archived tasks were removed rather than retained.
    - Introduced by diff: true; previous behavior: Discovery did not query archived scopes; an archived task was excluded/removed and no retained-session reconciliation occurred.; critical-path effect: All reads finish before another client's archive state becomes visible locally.
  - other at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxSessionContribution.ts:\_persistInventory</code>: Persist reconciled archive flags; cardinality: One batched storage call per completed discovery, writing only changed entries.
    - Introduced by diff: false; previous behavior: Inventory persistence existed, but had no Mission Control archive flag to reconcile.; critical-path effect: Completes as part of reconciliation; connected and disconnected environments use the same path.
- Verdict: No separate finding beyond the discovery regressions already reported; a single changed-task detail read is bounded and necessary, while cold historical fan-out is covered by the second finding.
