**Relevant issue families:** boundary-fanout, missing-coalescing, concurrency-burst, repeated-work, cleanup-lifecycle

### Scenario 1: A connected Cloud Sandbox receives an expired GitHub protected-resource notification and renews its sealed credential.

- Critical path: The notification synchronously selects the connection customization, then progress waits for AgentHostAuthenticationRecovery, a Mission Control credential reconnect, and the agent-host authenticate RPC. The PR removes user-session resolution and prompting from this path; renewal remains necessarily on the recovery critical path.
- Scaling input: The number of cloud-sandbox connections and completed expiry challenge groups. Within one connection, identical concurrent notifications collapse to one recovery; distinct concurrent keys collapse to one credential HTTP refresh but may each forward authentication.
- Effective concurrency: AgentHostAuthenticationRecovery serializes identical resource/scopes/authorization-server keys in \_pendingRecoveries. CloudSandboxCredentialRefresher additionally shares one \_refreshInFlight request across challenge keys and rate-limits forced reconnects to one per 30 seconds.
- Cache behavior: The cached sealed token is intentionally bypassed for an expired challenge. Positive renewal is stored in the staged credential bundle. In-flight work is coalesced per challenge key and again globally per connection; failed refresh state enforces retry delay rather than negative-caching forever.
- Mechanism confidence: High: the notification-to-refresh-to-authenticate call path, both coalescing layers, rate limit, and pre-diff transform path are explicit in code and tests.
- Magnitude uncertainty: The exact frequency of host expiry notifications and Mission Control latency varies, but tokens are described by the subsystem as roughly hourly and forced requests are bounded to one per 30 seconds per connection.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxCredentialRefresh.ts:CloudSandboxCredentialRefresher.\_doRefresh</code>: POSTs a reconnect request to Mission Control to mint fresh connection and sealed GitHub credentials.; cardinality: One request for a completed expiry recovery; exact duplicate notifications share AgentHostAuthenticationRecovery, distinct concurrent resource keys share the refresher's single in-flight request, and sequential forced refreshes are bounded by the 30-second rate limit.
    - Introduced by diff: false; previous behavior: The generic recovery first resolved the unchanged GitHub session, then \_authenticateCallback transformed the outgoing token with the same expired-reason refresh, reaching the same Mission Control reconnect boundary.; critical-path effect: The credential must be minted before it can be forwarded, so its network latency is on the expiry-recovery critical path.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts:\_authenticateNotificationResource</code>: Calls connection.authenticate with the renewed sealed credential over the existing agent-host protocol connection.; cardinality: One call after each successful coalesced recovery; duplicates arriving before authentication completes share the same recovery promise.
    - Introduced by diff: false; previous behavior: The generic recovery also called connection.authenticate after the customization transformed the user token into a fresh sealed credential.; critical-path effect: Recovery completes only after the host accepts the renewed credential.
- Verdict: No reportable regression. The diff changes ownership of renewal and removes session-resolution/prompt work, while preserving the pre-existing one-refresh and one-authenticate boundary costs for a successful expiry recovery.

### Scenario 2: Several expiry notifications arrive while renewal or host authentication is still in flight.

- Critical path: All identical notifications await the first pending recovery; the pending entry is retained through both credential refresh and connection.authenticate, so later duplicates add no boundary work and do not delay the authoritative recovery beyond that shared operation.
- Scaling input: Concurrent notifications, after deduplication by resource URL, normalized scopes, and authorization-server list; effective HTTP cardinality is one per connection while refresh overlaps.
- Effective concurrency: One recovery per normalized challenge key. Across different keys, credential refresh is globally coalesced by \_refreshInFlight for the connection. Authentication forwards can fan out by distinct key after the shared mint, but realistic cardinality is the advertised protected-resource set rather than arbitrary messages.
- Cache behavior: The pending-recovery map is cleared on settlement, allowing a genuinely later expiry to retry. Credential refresh failures enter bounded unhealthy/backoff state, so immediate notifications do not create retry traffic.
- Mechanism confidence: High: tests explicitly hold both renewal and authentication promises open and prove one renewal/forward for duplicate notifications, while the refresher implementation proves cross-key HTTP sharing.
- Magnitude uncertainty: A host could advertise multiple GitHub resource metadata variants, but the shared refresher still caps concurrent HTTP traffic; only the small protocol-authenticate forwarding count varies with distinct keys.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxCredentialRefresh.ts:CloudSandboxCredentialRefresher.\_refresh</code>: Shares the Mission Control reconnect HTTP request through \_refreshInFlight.; cardinality: One HTTP request for all notifications overlapping the refresh, including different resource keys on the same connection.
    - Introduced by diff: false; previous behavior: The same refresher and \_refreshInFlight coalescing were reached by the expired-reason authenticate transform before the diff.; critical-path effect: All overlapping recoveries wait for the same request.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts:\_authenticateNotificationResource</code>: Forwards the renewed token to the agent host.; cardinality: Exactly one for duplicate identical notifications through authentication completion; at most one per distinct challenge key when metadata differs.
    - Introduced by diff: false; previous behavior: Generic AgentHostAuthenticationRecovery already coalesced identical notification keys through its authenticate callback.; critical-path effect: The shared recovery remains pending until this call settles, preventing identical notification replay.
- Verdict: No missing-coalescing or concurrency-burst finding. The pending promise spans the full expensive path, and the lower-level network request has connection-wide sharing and pacing.

### Scenario 3: Renewal fails, or the cloud-sandbox connection is replaced while renewal is in progress.

- Critical path: A failed renewal terminates that notification recovery; a later notification may retry after refresher policy permits. Replacement is checked before forwarding, and disposal of the old connection's refresher cancels its network request.
- Scaling input: Failure count over connection lifetime and connection replacement frequency; both are bounded by disposer ownership and persistent refresh backoff state.
- Effective concurrency: At most one in-flight credential request per connection. Retryable failures arm a 30-second-or-server-directed delay; permanent failures stop refresh. Replacement cancellation prevents continued protocol forwarding.
- Cache behavior: Failures are not cached permanently, but persistent CloudSandboxCredentialRefreshState distinguishes stopped, backoff, rate-limited, and in-flight states across client replacement. Successful credentials update the staged bundle only while the refresher remains current.
- Mechanism confidence: High: cancellation ownership, replacement checks, persistent retry state, and limits are explicit in the changed call path and transitive refresher.
- Magnitude uncertainty: External failure duration is unknown, but request rate and lifecycle are concretely bounded.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxCredentialRefresh.ts:CloudSandboxCredentialRefresher.\_doRefresh</code>: An in-flight Mission Control reconnect is cancelled when the owning refresher is disposed; failures are paced or stopped by refresh state.; cardinality: One attempted request, with retries driven by later eligible events no faster than backoff/rate-limit policy and a maximum of ten unhealthy scheduled cycles.
    - Introduced by diff: false; previous behavior: Expired-token transformation used the same connection-owned refresher, cancellation token, backoff, and stop policy.; critical-path effect: Failure leaves authentication unrecovered, but does not start parallel retries or replay stale credentials.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts:\_authenticateNotificationResource</code>: Checks current connection identity before calling connection.authenticate.; cardinality: Zero after replacement; one only if the original connection remains current and renewal succeeds.
    - Introduced by diff: true; previous behavior: The existing transformed authenticate callback already performed equivalent current-connection checks before and after renewal.; critical-path effect: The identity check keeps late results off the replacement connection and avoids wasted host RPC work.
- Verdict: No cleanup-lifecycle or repeated-I/O regression. The new hook preserves existing refresher cancellation/backoff and adds a direct current-connection guard before forwarding.

### Scenario 4: An ordinary remote host, a non-expiry challenge, or a non-GitHub sandbox resource is processed.

- Critical path: Ordinary hosts and non-expiry reasons continue through generic authentication recovery. A non-GitHub sandbox expiry is rejected locally before any credential refresh boundary.
- Scaling input: Number of ordinary auth notifications or invalid resource challenges; changed work is a customization lookup and, only for an expired sandbox challenge, local URL validation.
- Effective concurrency: Existing per-challenge recovery coalescing is unchanged. No new network concurrency is introduced for these cases.
- Cache behavior: Generic token-cache and rejected-session behavior remains unchanged because renewAuthentication is undefined outside expired customized connections.
- Mechanism confidence: High: the reason guard and optional customization hook isolate the new branch, and resource validation precedes refresh.
- Magnitude uncertainty: The customization registry size is not documented, but it contains host-kind registrations and its linear lookup/factory allocation is tiny relative to auth boundaries and only occurs on notification handling, not a UI hot path.
- Expensive boundaries: none found
- Verdict: No performance regression. Unaffected cases retain prior behavior, and invalid sandbox resources fail before network or IPC work.

**Summary:** Completed the performance pass over all six changed files and traced expiry renewal through authentication recovery, customization lookup, Mission Control reconnect, protocol authentication, retry state, and connection disposal. No high-confidence diff-introduced performance issue was found; boundary counts are preserved or reduced, with two layers of coalescing plus per-connection rate limiting.
