<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** cleanup-lifecycle, repeated-work, cache-lifecycle, concurrency-burst

### Scenario 1: Automatically reveal canvases when the active chat publishes canvas membership

- Critical path: For each newly sourced, non-dismissed, non-presented canvas, the autorun creates/reuses a SessionCanvasInput and starts editorService.openEditor. The diff adds an in-memory findEditors fallback only when openEditor resolves without a pane; normal pane-returning opens do no added work. Calls are fire-and-forget from the autorun, so editor opening is the scenario's UI critical work but does not block the observable update loop.
- Scaling input: Number of newly presented canvas keys whose openEditor call resolves undefined after \_presented deduplication.
- Effective concurrency: Distinct newly presented canvases can open concurrently because each \_openInput promise is launched without awaiting the others. \_presented deduplicates subsequent metadata/status updates by canvas key. The diff does not increase concurrency for successful pane-returning opens; undefined results each perform one synchronous lookup.
- Cache behavior: Cold canvas keys allocate one input and enter \_presented before opening. Warm metadata updates reuse \_inputs and are suppressed by \_presented. Failed opens remove current presentation state and enter the dismissed/reopenable state, preventing automatic retry storms. There is no negative external cache or network lookup on this path.
- Mechanism confidence: High: the changed \_openInput branch and editorService.findEditors implementation show a fast observer miss check followed by an in-memory group scan only when the resource exists; no changed external boundary is reached.
- Magnitude uncertainty: The maximum canvases published simultaneously is not documented, but effective added cardinality is limited to one indexed editor lookup per openEditor result that is undefined, not per metadata update or editor row.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added fallback is bounded, only executes on undefined open results, and does not add an expensive boundary or realistic hot-path amplification.

### Scenario 2: Manually reopen a dismissed canvas from the Add Tab action

- Critical path: The command resolves one dismissed target, reuses or creates its input, removes dismissal, awaits one editorService.openEditor call, and on an undefined result performs one in-memory findEditors lookup before returning or restoring dismissal. The editor open remains the dominant critical-path operation and was already present before the diff.
- Scaling input: One selected reopen target per user command; fallback cost scales with open editor groups only when openEditor returns undefined and the observer reports the resource present.
- Effective concurrency: One invocation performs one open. Separate user command invocations are not coalesced explicitly, but \_presented and the synchronous dismissed-state removal prevent the normal menu flow from repeatedly targeting the same entry; the diff adds no burst scheduler.
- Cache behavior: Dismissed references are the positive menu-state cache. A successful reopen deletes the dismissed entry; a failed current-input open restores it. Existing \_inputs reuse avoids duplicate input construction. Warm successful opens returning a pane skip the new lookup.
- Mechanism confidence: High: the command registration, reopenCanvas path, and findEditors implementation were traced directly.
- Magnitude uncertainty: Editor group counts and frequency of undefined open results vary, but the fallback uses the editor observer for fast misses and has one-call cardinality per manual reopen.
- Expensive boundaries: none found
- Verdict: No reportable regression. The one fallback lookup is required to distinguish a successful non-active open from failure and is not a significant scaling or boundary mechanism.

### Scenario 3: Close canvas editors when canvases, sessions, or enablement are removed

- Critical path: For each affected live input, the autorun/session-removal handler starts \_closeInput, which finds matching in-memory editor identifiers and awaits editorService.closeEditors. The diff moves input disposal, lifetime disposal, and programmatic-close marker deletion into finally, so cleanup also completes if closeEditors rejects.
- Scaling input: Number of concurrently removed live canvas inputs after exact-input deduplication; replacement generations are independent.
- Effective concurrency: Different canvas inputs can close concurrently because callers launch \_closeInput without awaiting; this behavior predates the diff. The marker now deduplicates by exact input rather than logical key, allowing a replacement generation to own its independent close while the older generation settles. Each specific input still has at most one active close.
- Cache behavior: \_inputs and \_inputLifetimes are removed before awaiting close; \_programmaticCloses is temporary bookkeeping and is now always deleted in finally. There is no external cache. Replacement inputs with the same key are kept distinct, avoiding stale generation cleanup mutating the current generation.
- Mechanism confidence: High: service ownership and editorService.closeEditors were traced; closeEditors groups identifiers in memory and invokes UI editor-group closes, with no transitive subprocess, IPC, filesystem, database, or network operation in the inspected path.
- Magnitude uncertainty: A provider could churn membership while editor closes are pending, but ordinary effective cardinality is one close per removed live input, and no evidence shows a slow external boundary or unbounded aggregate close workload introduced by the change.
- Expensive boundaries: none found
- Verdict: No reportable regression. The change improves cleanup lifecycle on rejection and narrows bookkeeping ownership; possible overlap between distinct generations is necessary to close each live input and lacks evidence of a realistic performance burst.

### Scenario 4: Handle failed or superseded canvas opens

- Critical path: After openEditor rejects or an undefined result has no matching open editor, the catch checks whether the attempted input is still current before removing presentation and restoring dismissal. Superseded failures do not modify the newer presentation. Failure handling is off the successful-open critical path except for the undefined-result verification.
- Scaling input: Number of overlapping open generations for a canvas key during provider membership churn.
- Effective concurrency: Older and newer opens for the same logical key may overlap during membership churn. State mutation is guarded by exact input identity, so completion of an older attempt does not trigger retries or clear suppression for the newer one.
- Cache behavior: \_presented is the suppression state and \_dismissed is the failure/reopen state. The identity guard preserves the newer warm state, while a current failed open is negatively represented as dismissed rather than automatically retried on every canvas update.
- Mechanism confidence: High: changed catch guards, autorun suppression conditions, and tests establish exact-generation behavior.
- Magnitude uncertainty: Provider churn and undefined open outcomes are expected to be uncommon, but the mechanism is directly bounded even if they occur frequently.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff prevents stale failure completion from defeating presentation suppression, reducing rather than increasing repeated work.

**Summary:** Reviewed the complete two-file diff and traced automatic reveal, manual reopen, close/cleanup, and overlapping failure scenarios. Added work is a bounded in-memory lookup on undefined editor-open results; no changed external boundary, hot-loop amplification, unbounded retention, or actionable performance regression was found. Cleanup and exact-input ownership changes reduce failure-path retention and stale-generation work.
