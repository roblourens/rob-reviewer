**Relevant issue families:** boundary-fanout, serialization-allocation, repeated-work, concurrency-burst, cache-lifecycle

### Scenario 1: User accepts a Dev Container sample from the submenu, filtered results, or a recent-workspace entry

- Critical path: A user selection enters \_dispatchPickerItem, emits the pre-existing newChatPickerClosed event, optionally connects the provider, awaits selection validation, commits the folder selection, performs a fixed-catalog sample lookup, and synchronously prepares one new telemetry event before the dispatch promise resolves. Desktop/remote telemetry transport and web SDK delivery are fire-and-forget and are not awaited; the picker is hidden immediately by the selection delegate.
- Scaling input: One selected workspace URI per user action. findDevContainerSample scans at most the six built-in catalog entries, and the diff emits exactly one small event for an accepted sample; there is no workspace-, repository-, or result-list-sized loop.
- Effective concurrency: Selection generations suppress accepted superseded async selections. Each accepted user action can enqueue one telemetry append; the diff does not launch a collection burst or add parallel provider operations.
- Cache behavior: The six-entry catalog lookup needs no cache. If experiment properties are not ready, telemetry uses the existing globally capped pending-event buffer; once warm it immediately forwards to configured appenders. Provider connection status is reused on warm selections. The diff adds no cache keys, misses, negative-cache state, or invalidation lifecycle.
- Mechanism confidence: High: the changed line, fixed six-element lookup, accepted-selection call path, telemetry service cleaning, configured appenders, and fire-and-forget IPC/network behavior were all traced directly.
- Magnitude uncertainty: No timing measurement is available for telemetry cleaning/channel enqueue, and configured appenders vary by desktop/web/remote environment. The payload and event cardinality are fixed and tiny, so this uncertainty does not establish a realistic regression.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts:\_connectProviderOnDemand</code>: Optional on-demand provider connection before workspace acceptance; cardinality: At most one connection attempt for the selected provider, only when disconnected and connectable; zero for the local sample provider or an already-connected provider.
    - Introduced by diff: false; previous behavior: The same provider connection attempt was awaited before accepting the selected workspace.; critical-path effect: Awaited and potentially dominant when needed, but unchanged by this PR and completed before the added lookup/event.
  - filesystem at <code>src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts:\_canSelectWorkspace</code>: Existence check for file-scheme workspace selections; cardinality: At most one exists call per selected local file URI; Dev Container sample URIs use a distinct scheme, so this is zero for the sample-selection scenario.
    - Introduced by diff: false; previous behavior: The same existence check occurred before accepting local file workspaces.; critical-path effect: Awaited for ordinary local folders, but not reached as filesystem I/O for sample URIs and unchanged by the diff.
  - IPC at <code>src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts:1061 via src/vs/platform/telemetry/common/telemetryIpc.ts:TelemetryAppenderClient.log</code>: Desktop telemetry appender channel enqueue for devContainerSampleSelected; cardinality: Exactly one new IPC call per accepted sample when desktop telemetry is enabled; no call when telemetry is disabled. The scenario already emits one separate newChatPickerClosed telemetry event.
    - Introduced by diff: true; previous behavior: An accepted selection emitted newChatPickerClosed, but did not emit this second sample-specific telemetry call.; critical-path effect: Payload cleaning and channel enqueue are synchronous and bounded; delivery is fire-and-forget and not awaited.
  - network at <code>src/vs/workbench/services/telemetry/browser/telemetryService.ts and src/vs/platform/telemetry/common/1dsAppender.ts</code>: Web or remote telemetry appender enqueue/delivery for devContainerSampleSelected; cardinality: Exactly one small event per accepted sample when usage telemetry is enabled, forwarded through one configured transport plus the existing log appender.
    - Introduced by diff: true; previous behavior: The same accepted selection had no sample-specific event, although it already emitted newChatPickerClosed.; critical-path effect: The appender queues/tracks the event without awaiting network completion; only bounded preparation is on the selection path.
- Verdict: No reportable performance regression. The PR intentionally adds one bounded telemetry event to a low-frequency accepted user action; it neither fans out with a collection nor awaits transport, and the fixed lookup cannot grow with user data.

### Scenario 2: User selects an ordinary folder or a malformed sample URI

- Critical path: After the unchanged provider-connect and selection-validation steps, the diff calls findDevContainerSample. Ordinary schemes fail the initial scheme test; malformed sample-scheme URIs either fail authority/query/fragment checks or scan the six-entry catalog. No new telemetry append occurs.
- Scaling input: One URI per accepted user selection; lookup cost is constant and capped at six comparisons regardless of workspace history or picker result count.
- Effective concurrency: One lookup per accepted dispatch. Superseded asynchronous selections are rejected by the existing generation checks before reaching the added lookup.
- Cache behavior: No cache is needed or introduced because the lookup's maximum cardinality is six. Existing provider connection state remains the only warm-path distinction.
- Mechanism confidence: High: helper guards and the fixed catalog were inspected, and the changed telemetry branch is not entered for these inputs.
- Magnitude uncertainty: Custom provider validation duration is provider-specific, but it is unchanged and unrelated to the constant-time added lookup.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts:\_connectProviderOnDemand and \_canSelectWorkspace</code>: Optional provider connection or custom canSelectWorkspace validation; cardinality: At most one provider connection/validation sequence for the single selected URI.
    - Introduced by diff: false; previous behavior: The same connection and validation sequence occurred before the PR.; critical-path effect: Awaited but entirely pre-existing; the added lookup runs only after it completes.
  - filesystem at <code>src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts:\_canSelectWorkspace</code>: Local folder existence check; cardinality: At most one exists call for one file-scheme folder.
    - Introduced by diff: false; previous behavior: The same existence check occurred before the PR.; critical-path effect: Awaited and unchanged; no telemetry boundary is added for the ordinary or malformed URI.
- Verdict: No reportable performance regression. The only new work is a bounded URI check/fixed six-entry scan with no new IPC, filesystem, or network operation.

### Scenario 3: Workspace selection is restored programmatically, unavailable, declined, failed, or superseded

- Critical path: Programmatic restoration uses setSelectedWorkspace rather than \_dispatchPickerItem. Unavailable providers return before validation; declined/failed/superseded asynchronous selections return or throw before the changed lines. Therefore neither the new catalog lookup nor the new telemetry event runs.
- Scaling input: One attempted selection; effective new-work cardinality is zero for all listed outcomes.
- Effective concurrency: The existing selection generation invalidates superseded attempts. The diff adds no queued, concurrent, or retained work on these paths.
- Cache behavior: No new cache access or telemetry buffering occurs because the changed branch is not reached.
- Mechanism confidence: High: generation and early-return guards precede the changed lines, and tests exercise each non-emitting outcome.
- Magnitude uncertainty: Provider-specific connection/validation cost is not measured, but the PR introduces no work on these rejected or restoration paths.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/chat/browser/sessionWorkspacePicker.ts:\_connectProviderOnDemand and \_canSelectWorkspace</code>: Possible pre-existing provider connection or selection validation before a declined/failed/superseded outcome; cardinality: At most one sequence for the attempted selection; zero for programmatic restoration and immediately unavailable providers.
    - Introduced by diff: false; previous behavior: Identical connection/validation behavior, with no sample-specific telemetry.; critical-path effect: May be awaited for an attempted selection, but unchanged by the diff; rejection occurs before the new telemetry boundary.
- Verdict: No reportable performance regression because all newly added runtime work is bypassed.

**Summary:** Completed the performance pass over both changed files and all diff pages. The sole production change adds a fixed six-entry lookup and one small, non-awaited telemetry append after a rare accepted sample selection. Existing provider, filesystem, IPC, and network boundaries were compared before/after; no scaling, burst, retention, eager-work, or critical-path regression met the reporting threshold.
