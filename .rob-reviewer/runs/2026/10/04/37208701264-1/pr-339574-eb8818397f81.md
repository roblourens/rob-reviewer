### Scenario 2: Dismiss a live canvas and keep its Add Tab entry synchronized with provider metadata

- Critical path: Input disposal synchronously records one dismissed reference, invalidates the derived list, computes labels for at most eight active-chat canvases, and registers or updates menu items. Provider metadata updates rerun this in-memory projection; unchanged title/order values avoid menu re-registration.
- Scaling input: At most eight active-chat canvas entries. Inactive dismissed references may remain in the pre-existing map, but realistic update work is bounded by the service's existing lifecycle and the provider cap.
- Effective concurrency: Observable invalidations are transactional. Menu changes are emitted through a MicrotaskEmitter, coalescing multiple registration changes in one turn.
- Cache behavior: Registrations are keyed by stable canvas reference and reused across metadata changes; unchanged labels/orders are skipped. Removed entries dispose both command and menu registration.
- Mechanism confidence: High: stable-key reuse, disposal, update guards, the provider cap, and microtask coalescing are explicit in the traced code.
- Magnitude uncertainty: A long-lived service can hold dismissed references across chats, but each chat has at most eight canvases and the diff does not create unbounded command/menu retention.
- Expensive boundaries: none found
- Verdict: No reportable regression: CPU/allocation work is small and bounded, menu updates are coalesced, and lifecycle cleanup is present.

### Scenario 3: Reopen one dismissed canvas from the Add Tab menu

- Critical path: The selected command removes its dismissed/menu state, opens one editor, creates one external BrowserView over IPC, and loads its HTTP(S) URL before the canvas is usable.
- Scaling input: Exactly one selected canvas per command invocation; the dismissed item is synchronously removed, preventing the same menu action from remaining active during the open.
- Effective concurrency: One open promise for the selected command. Different canvases could be selected independently, but the UI exposes at most eight and the diff introduces no bulk fan-out.
- Cache behavior: Reopening creates a fresh ephemeral BrowserView because closing disposed the prior input/model; there is no warm browser-view cache to reuse. Canvas state itself comes from the existing live provider subscription.
- Mechanism confidence: High: the command-to-editor-to-BrowserView call path and both awaited boundaries are explicit.
- Magnitude uncertainty: Page load duration depends on the selected source, but cardinality is one and directly user-requested.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts:createExternalBrowserView</code>: Create an external BrowserView in the main process.; cardinality: One getOrCreateBrowserView IPC call per explicit reopen.
    - Introduced by diff: true; previous behavior: A dismissed canvas could not be reopened manually, so this explicit user-triggered boundary did not exist; initial automatic presentation already used the same editor/browser-view path.; critical-path effect: Awaited on the user-triggered reopen path before the editor can present the view.
  - network at <code>src/vs/workbench/contrib/browserView/electron-browser/browserViewWorkbenchService.ts:createExternalBrowserView</code>: Load the selected canvas HTTP(S) source in the BrowserView.; cardinality: One navigation per explicit reopen.
    - Introduced by diff: true; previous behavior: No manual reopen was available after dismissal; the same single navigation occurred for initial automatic canvas presentation.; critical-path effect: Awaited before the reopened canvas is displayed.
- Verdict: No reportable regression: the new IPC/network work is the requested operation, has cardinality one, and is not eagerly or repeatedly triggered.

### Scenario 4: Automatic reveal failure, session/chat switch, and dismissed-entry cleanup

- Critical path: Automatic reveal still performs one editor open as before. On failure, the diff records a reopenable entry in memory; switching/removing ownership deletes entries and disposes their dynamic commands/menu registrations. Existing editor closure remains asynchronous and unchanged in cardinality.
- Scaling input: At most eight current-chat canvases plus retained dismissed references from prior chats/sessions; removals are synchronous per reference and menu events are coalesced.
- Effective concurrency: Automatic opens remain independently initiated per newly published canvas, capped at eight by the provider. This PR does not increase that fan-out; it centralizes the same open call in \_openInput.
- Cache behavior: Failed opens become a negative/reopenable state rather than being retried automatically. Successful reopen removes the state; failed reopen restores it only while the input is still live and enabled.
- Mechanism confidence: High: \_presented/\_dismissed transitions and the unchanged automatic autorun call site establish the scheduling and cardinality.
- Magnitude uncertainty: Failure frequency and provider behavior vary, but the changed state prevents retry loops rather than creating them.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/canvases/electron-browser/sessionCanvasService.ts:\_openInput/\_closeInput</code>: Open/close editor and create/destroy its BrowserView as applicable.; cardinality: One open per newly published canvas or explicit reopen; existing close cardinality is unchanged.
    - Introduced by diff: false; previous behavior: Automatic reveal and ownership cleanup already opened/closed the same editor resources; the refactor adds failure bookkeeping but no extra automatic open.; critical-path effect: Automatic reveal is off the caller's critical path; explicit reopen awaits completion. Cleanup closes are asynchronous.
- Verdict: No reportable regression: failure handling does not retry expensive work, cleanup disposes registrations, and automatic boundary count is unchanged.
