## Findings (1)

### 1. [medium] Cap queued-message text before returning it to the model

**Finding ID:** `PERF-AF369FBED137`  
**Location:** <code>src/vs/platform/agentHost/node/shared/sessionServerTools.ts:1493</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Tool-result bytes and model prompt tokens allocated, JSON-encoded, and sent to the provider.  
**Scaling:** O(L × C) extra bytes/tokens for message length L and context/replacement call count C; unlike transcript data, L is not capped by detail or transcriptLimit.  
**Outcome:** Increased model-request payload and latency, plus serialization/allocation pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Previously, get\_session\_context contained only a bounded transcript and send\_message returned only a short status/link; queued text was not duplicated into either model-facing result.  
**Changed behavior:** A context read, and every successful replacement, now copies the entire previous queued message into a tool result that becomes model input, bypassing the serializer's existing per-detail caps.  
**Confidence:** 0.96 — The raw-text insertion, lack of an input maximum, established transcript caps, and model-facing return path are directly visible. The prevalence of very long messages is uncertain, but byte/token scaling is not.

**Causal diff evidence:** RIGHT line 1493 adds \`undelivered.message.text\` directly to the model-facing JSON after transcript fields have been truncated by \`contextCaps\`; RIGHT line 1327 also interpolates the complete replaced text into the send\_message result. Neither path applies a length bound, and the send\_message schema has no \`maxLength\`.

A detailed status, log, or code message can dominate the compact summary and add thousands or more prompt bytes before the next model response. Repeated checks or replacements increase provider upload, token processing, latency, and allocation linearly.

**Evidence:** \`serializeSessionContext\` truncates transcript messages using \`contextCaps\` and caps the window at 50, but \`yourUndeliveredMessage\` uses raw queued text. The new test verifies that a 5,008-character message remains intact even in \`summary\`, where user text is otherwise capped at 160 characters. \`applyGetSessionContextTool\` returns this JSON as the server-tool result, so the bytes are serialized and included on the next model-provider request; repeated checks repeat the payload. The replacement formatter creates the same uncapped copy on send.

**Suggested direction:** Return a bounded preview with original length and truncation metadata. If full recovery is required, expose it only through an explicit opt-in/full-detail path with a documented maximum rather than bypassing summary and digest caps.


## Performance regression fixes detected (1)

### 1. missing-coalescing

**Fix location:** `src/vs/platform/agentHost/node/shared/sessionServerTools.ts:1294` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/shared/sessionServerTools.ts:1287`  
**Introducing path:** `src/vs/platform/agentHost/node/shared/sessionServerTools.ts`  
**Introducing commit:** `be6bce25cb71024a380e88a1439201591b0188aa`  
**Mechanism family:** `missing-coalescing`  
**Performance category:** `network`  
**Confidence:** 0.98

**Mechanism:** Repeated send\_message calls to a busy target previously appended a fresh pending message each time. After the active turn completed, the queue drain serialized all of those stale entries into separate full agent/provider turns, multiplying model/network work and delaying the latest update linearly with the number of follow-ups.

**Symptom:** Busy target chats could accumulate many stale same-sender turns, causing avoidable LLM requests and making the final/current update wait behind all earlier follow-ups.

**Fixed behavior:** Same-sender follow-ups now reuse and replace the sender's existing undelivered queue entry, bounding that sender to one pending provider turn while preserving FIFO position and separate messages from other senders.

**Evidence:** In the base revision, every busy-target send\_message dispatches ChatPendingMessageSet with a fresh generateUuid() id, so the reducer appends each follow-up. QueueDrainContribution consumes queuedMessages\[0\] after each successful turn and calls host.sendTurnMessage for every entry, making each stale follow-up a separate provider/model turn. The changed path finds the same source chat's still-undelivered entry and dispatches ChatPendingMessageSet with that existing id, which the reducer upserts in place; tests establish that multiple same-sender sends leave one queued message while different senders remain distinct.
