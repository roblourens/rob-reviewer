### Scenario 2: send\_message targets a chat with an active turn or pending messages

- Critical path: The tool still awaits the existing listSessions computation, then synchronously appends a pending message and returns. Provider work is deferred until queue admission after a successful/local-command turn end and is therefore off the send\_message tool critical path.
- Scaling input: Queue length and message size control retained bytes, reducer copying, and IPC bytes. Queue cardinality from this server-tool group is bounded by the singleton process-wide 50-send cap; completed entries are removed and session/chat disposal releases state.
- Effective concurrency: Per-chat effective provider concurrency is one queued turn at a time. Different chats can progress independently, while the global server-tool send count remains capped at 50.
- Cache behavior: The queue is authoritative state rather than a cache. There are no cache misses or retries; state is removed on consumption and all chat state is removed on chat/session disposal. Existing listSessions cold/warm behavior is unchanged.
- Mechanism confidence: High: reducer append behavior, IPC emission, queue-drain serialization, process cap, and cleanup ownership are all directly traced.
- Magnitude uncertainty: Exact message bytes and connected-client count vary, but the extra action count and queue cap are explicit. At this bound, O(q) append copies and one additional broadcast per item do not establish a significant user-visible regression.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:2080-2190 listSessions/\_computeSessions</code>: Resolve the known target through the existing session catalogue and metadata pipeline.; cardinality: One logical listing per invocation with existing provider grouping, concurrency-4 metadata limiting, and in-flight coalescing.

- Verdict: No reportable performance regression. The added retention and action broadcast are bounded, and serial provider admission is the intended busy-chat scheduling behavior rather than an accidental fan-out or burst.

- Critical path: After the unchanged listSessions call, the new branch appends another pending message and returns. Because QueueDrainContribution reacts to client-action hooks and turn-end events, this server-originated enqueue does not itself force an idle stale queue to drain.
- Scaling input: Number and size of later send\_message calls while stale pending state remains; at most 50 successful calls from the singleton tool group before process restart, with state also bounded by chat/session lifetime.
- Effective concurrency: No provider work is launched by these server-originated pending actions; local enqueues are synchronous.
- Cache behavior: No cache is involved. Pending messages remain authoritative state until manual removal/admission or chat/session cleanup.
- Mechanism confidence: High for the hook mismatch and bounded retention; low that the bounded retained bytes create a material performance symptom independent of the correctness issue.

- Verdict: No performance finding. The dominant defect risk is correctness (messages may remain queued), which this focus must not report; the associated memory and IPC work are bounded and cleaned up with the owning state.
