### Scenario 1: Open the Settings editor and reflect managed sandbox-policy changes

- Critical path: Opening Settings constructs the delayed presentation service and synchronously scans registered configuration properties before the editor is usable. A later managed-policy or configuration-registry event rescans in process, then only changed setting keys are rerendered. No filesystem, network, subprocess, or IPC operation is invoked by the changed service itself; upstream policy refresh has already completed before its event fires.
- Scaling input: Number of registered configuration properties, typically thousands, plus the small number of properties declaring managedSettingsPresentation (seven in this change). Policy-change frequency is low and registry updates are batched by configuration contribution events.
- Effective concurrency: All projection and rerender scheduling is synchronous on the UI thread; policy events are naturally serialized by the event loop. There is no parallel fan-out.
- Cache behavior: The service builds a cold Map of effective managed values, then retains only defined presentation values. Warm updates still scan the registry but compare against the Map and suppress notifications/rerenders when values are unchanged; no negative-cache ambiguity or unbounded key retention was found.
- Mechanism confidence: High confidence in the full-registry scan and UI-thread reachability; surrounding registry code confirms one event per batched registration/update. The bounded scan and low event frequency do not establish a user-visible regression.
- Magnitude uncertainty: Exact configuration-property count and scan duration vary by installed extensions, but work is a shallow object enumeration with only seven callbacks in this diff.
- Expensive boundaries: none found
- Verdict: No reportable regression. The generic scan is broader than the previous three-key comparison, but it is lifecycle-bounded, event-driven, suppresses unchanged rerenders, and lacks evidence of meaningful latency or repeated hot-path cost.

### Scenario 2: Render and operate Copilot Agent Host permission/sandbox pickers

- Critical path: The changed picker derives the unified setting ID locally, so toggle availability and rendering no longer wait for host OS diagnostics.

- Cache behavior: Before the diff, host OS diagnostics were positively cached per connection; failures removed the cache entry. After the diff, that cache and lookup are not reached from these pickers.
- Mechanism confidence: High confidence: deleted call paths and tests explicitly change expected diagnostics request counts from one/retries to zero.
- Magnitude uncertainty: Remote-host latency varied, but this is an improvement rather than a regression.
- Expensive boundaries:

- Verdict: No finding. The diff removes an IPC dependency and related asynchronous refresh work.

- Scaling input: Number of live Agent Host connections for workbench forwarding, and number of session launches/turns/config changes for SDK updates. Configuration payload growth is constant (four optional booleans).
- Effective concurrency: Workbench dispatch iterates live connections synchronously with no limiter, as before. Per-session SDK sandbox updates are serialized by \_sandboxConfigSequencer; separate sessions may proceed concurrently, unchanged by the diff.
- Cache behavior: Workbench caches the desired settings object until a relevant configuration change and deep-compares against each host root state. SDK configuration is recomputed per required update; filesystem path sets are deduplicated during construction. No new unbounded cache or missed coalescing was introduced.
- Mechanism confidence: High confidence from the forwarder, launcher, per-turn preparation, and sequencer call paths.
- Magnitude uncertainty: SDK processing cost of individual new flags is not visible in-repository, but no changed call cardinality or scaling input supports a regression.
- Expensive boundaries:

- Verdict: No reportable regression. Boundary counts, sequencing, and effective cardinality are unchanged; richer constant-size metadata alone is insufficient.

### Scenario 4: Run terminal commands under unified sandbox enablement, including Windows

- Critical path: When the unified setting is on, sandbox prerequisite checks and first-use configuration generation precede wrapped command execution. The first configuration is cached per engine; commands then use the existing sandbox runtime/MXC path. The diff intentionally makes Windows consume the same enablement setting.
- Scaling input: One first-use setup per sandbox engine plus sandbox wrapper execution per command; filesystem policy work scales with configured paths/workspace roots as before.
- Effective concurrency: Existing engine promises/caches serialize first-use runtime/config state; command execution concurrency is owned by existing terminal/session machinery and is not changed here.
- Cache behavior: OS/runtime info, dependency status, temporary directory, and sandbox config path are cached. Force refresh occurs only for explicit refresh or marked configuration changes. Cold Windows users newly covered by unified enablement pay normal sandbox setup; warm commands reuse cached policy/config state.
- Mechanism confidence: High confidence in first-use caching and existing per-command sandbox boundary; there is no diff-introduced duplicate setup or boundary fan-out.
- Magnitude uncertainty: Sandbox startup overhead varies by OS and runtime, but it is the intended cost of enabling the existing security feature and no bounded behavior-preserving optimization is exposed by the changed hunks.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/sandbox/common/terminalSandboxEngine.ts:\_createSandboxConfig/getSandboxConfigPath</code>: Create the sandbox JSON configuration file on first use or forced refresh; cardinality: One cached file creation per engine in the normal case; no per-command rewrite unless existing force-refresh conditions apply.
    - Introduced by diff: false; previous behavior: The same work occurred when the platform-specific Windows setting or shared non-Windows setting enabled sandboxing; the diff changes which setting selects the existing path.; critical-path effect: First sandboxed command waits for policy/path resolution and file creation.
  - subprocess at <code>src/vs/platform/sandbox/common/terminalSandboxEngine.ts command wrapping path</code>: Launch commands through the existing sandbox runtime or Windows MXC containment; cardinality: One sandboxed execution per terminal command while enabled.
    - Introduced by diff: false; previous behavior: Windows used this path when enabledWindows was on; other platforms used it when the shared setting was on. The diff deliberately unifies selection rather than adding another wrapper layer.; critical-path effect: Sandbox wrapper startup is on command execution, inherent to enabled sandbox semantics.
- Verdict: No finding. Unified Windows enablement changes feature applicability intentionally, while the underlying cached setup and per-command boundary are unchanged and not duplicated.
