### Scenario 1: Forward memory and local-memory settings or preview-policy changes into the local Agent Host

- Critical path: A setting or account-policy event computes an effective boolean, dispatches a RootConfigChanged action over the existing local Agent Host protocol, updates root state, and persists root configuration. This is on the setting-change path, not chat input/rendering.
- Scaling input: Number of effective memory-related settings changed in one infrequent user or policy event (maximum two), not number of sessions or chats.
- Effective concurrency: The two key pushes may begin independently, but each is equality-guarded and root writes are serialized by the existing configuration service.
- Cache behavior: Root state is the warm cache for forwarded values; structural equality suppresses unchanged dispatches. Persisted root config seeds later host lifetimes.
- Mechanism confidence: High: the dispatch, equality guard, state update, and persistence path are directly traced.
- Magnitude uncertainty: Exact persistence duration is platform-dependent, but cardinality is fixed and events are infrequent.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostRootConfigForwarder.ts:\_push</code>: Dispatch one RootConfigChanged patch for each effective key whose structurally compared value changed; cardinality: At most one dispatch per changed Memory or LocalMemory key; unchanged values are suppressed. A policy transition can change both keys, while initial reconciliation only sends missing/different values.
    - Introduced by diff: true; previous behavior: These two keys and their dispatches did not exist; existing forwarded keys already used the same per-key path.; critical-path effect: The setting/policy propagation waits only for local dispatch scheduling; it does not block an active turn.
  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts:\_dispatchActionNow</code>: Persist the merged Agent Host root configuration after RootConfigChanged; cardinality: One persistence request per effective changed key, normally one or two on an explicit setting/policy transition; structural equality prevents steady-state repeats.
    - Introduced by diff: true; previous behavior: No persistence was triggered for these absent memory keys; other settings already used the same persistence path.; critical-path effect: Persistence is sequenced by the configuration service and is not on chat turn progress.
- Verdict: No finding: the diff adds at most two bounded, infrequent config updates and does not create collection-scaled or hot-path work.

### Scenario 2: Enable or disable the in-repository memory store while a Copilot SDK client exists

- Critical path: The forwarded root-config event recomputes effective local memory. If it changed, a restart is requested; active turns/subagents finish first, then the single shared client and resident sessions stop. A replacement subprocess starts lazily on the next operation.
- Scaling input: One explicit LocalMemory/effective Memory transition; resident chat count affects teardown breadth but not subprocess restart count.
- Effective concurrency: Restart waits for zero busy chats, pending reasons are coalesced in a Set, and client startup is shared through one promise.
- Cache behavior: Warm client is retained when only cloud memory changes or LocalMemory changes while Memory is off. A required effective local-store change invalidates the shared client once; later sessions reuse the replacement.
- Mechanism confidence: High: startup snapshot comparison, active-work gating, reason coalescing, teardown, and shared startup are explicit.
- Magnitude uncertainty: Cold runtime startup cost and number of resident sessions vary, but the trigger is an explicit, infrequent setting/policy transition.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_restartClientIfStartupConfigChanged / \_requestClientRestart / \_ensureClientOnce</code>: Stop the shared Copilot runtime and lazily start a replacement with the new startup snapshot; cardinality: One coalesced restart per effective local-store transition, shared across all sessions; concurrent restart reasons are accumulated and concurrent starts share \_clientStarting.
    - Introduced by diff: true; previous behavior: Memory settings did not trigger a client restart. Existing startup-baked settings already used this same deferred, coalesced lifecycle.; critical-path effect: Never interrupts or delays active turns; a cold replacement start is on the next Copilot operation's critical path.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_applyPendingClientRestart</code>: Refresh the model catalog after stopping the old client; cardinality: One scheduled refresh per applied shared-client restart.
    - Introduced by diff: false; previous behavior: Every existing startup-config restart already cleared and refreshed the catalog.; critical-path effect: Catalog refresh is scheduled after teardown and is not awaited by the setting change; the next session may independently ensure the client.
- Verdict: No finding: restart cost is bounded, deferred outside active work, coalesced globally, and required because resident sessions do not reapply this runtime feature flag.

### Scenario 3: Create or resume a durable Copilot SDK session with cloud or local memory enabled

- Critical path: Session launch builds configuration, then performs the existing SDK createSession or resumeSession IPC. The diff adds a boolean memory option and local-store feature flag to that same request.
- Scaling input: One session launch/resume and subsequent explicitly opted-in memory usage; no repository collection is looped over by changed host code.
- Effective concurrency: Existing launcher behavior applies; independent config preparation is already grouped with Promise.all, and the diff adds no new concurrent operation.
- Cache behavior: The runtime owns cloud/local memory caching and persistence; host configuration is read once per launch. Warm resident sessions reuse the existing runtime until an effective local-store transition requires restart.
- Mechanism confidence: High for unchanged host boundary cardinality; limited for runtime-internal costs because implementation is external.
- Magnitude uncertainty: The external runtime's memory lookup/write frequency and cache implementation are not present in this repository.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:launch / \_createSession / \_resumeSession</code>: Create or resume one Copilot SDK session with memory configuration; cardinality: Exactly one existing SDK create/resume call per session launch attempt; the diff does not add another call or increase concurrency.
    - Introduced by diff: false; previous behavior: The same create/resume call occurred without explicit memory and local-store fields.; critical-path effect: The existing SDK call remains on session-launch critical path; adding two booleans has negligible serialization cost.
  - network at <code>External Copilot runtime configured by src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:\_buildSessionConfig</code>: Runtime-owned cloud memory storage/recall when the opted-in feature is used; cardinality: Not visible in this repository; controlled by runtime behavior and only enabled by explicit opt-in.
    - Introduced by diff: true; previous behavior: Memory was not enabled through Agent Host session configuration.; critical-path effect: Potential runtime memory service work may occur during turns, but this diff exposes the requested feature rather than adding host-side fan-out.
  - filesystem at <code>External Copilot runtime selected by COPILOT\_LOCAL\_MEMORY\_FEATURE\_FLAG</code>: Runtime-owned reads/appends to .github/copilot-memories.jsonl for local memory; cardinality: Not visible in repository code; applies only when both memory settings are enabled.
    - Introduced by diff: true; previous behavior: The Agent Host did not select the runtime's in-repository memory store.; critical-path effect: Runtime-owned file work may affect memory-enabled turns, but no host-side per-item loop or eager scan is introduced here.
- Verdict: No finding: enabling a requested opt-in feature may incur its inherent runtime work, but the diff does not demonstrate avoidable fan-out, repeated host work, or an unbounded host allocation.

### Scenario 4: Create a peer chat under an ephemeral session

- Critical path: AgentService performs one O(1) ephemeral-state lookup, passes the flag through chat creation, and the launcher explicitly disables memory before the existing SDK create/resume call.
- Scaling input: Number of user-created ephemeral peer chats; each independently follows the existing one-launch path.
- Effective concurrency: Creation remains serialized by the existing per-session/per-chat queues in CopilotAgent; the diff adds no burst.
- Cache behavior: Ephemeral state is read from the in-memory state manager. No memory cache/store is initialized because the launch config explicitly disables it.
- Mechanism confidence: High: state lookup, option propagation, and launch-time memory gate are direct.
- Magnitude uncertainty: None material for the changed mechanism; lookup and payload growth are constant.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/agentService.ts:\_createChat and src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:\_buildSessionConfig</code>: Existing provider chat creation and SDK create/resume with memory disabled; cardinality: One provider call and one existing SDK launch per peer chat; no additional boundary call.
    - Introduced by diff: false; previous behavior: Peer creation already crossed these boundaries, but ephemeral ownership was not propagated to the Copilot launch plan.; critical-path effect: The added state lookup and boolean serialization are negligible; disabling memory avoids runtime network/filesystem work for ephemeral peers.
- Verdict: No finding: the change prevents heavyweight memory behavior on ephemeral peers without adding an expensive boundary.
