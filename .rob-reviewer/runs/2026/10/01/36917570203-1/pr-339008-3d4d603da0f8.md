# Performance review: Avoid unnecessary --numstat diff for incoming changes decorations

[PR #339008](https://github.com/microsoft/vscode/pull/339008) at `3d4d603da0f851903e39e213c33652739deb43a4`

## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `extensions/git/src/decorationProvider.ts:261` (`RIGHT`)  
**Blamed base line:** `extensions/git/src/decorationProvider.ts:261`  
**Introducing path:** `extensions/git/src/decorationProvider.ts`  
**Introducing commit:** `c95739960ff4c35dd0bf89ef8a8812eb377d7dfc`  
**Mechanism family:** `eager-work`  
**Performance category:** `io`  
**Confidence:** 0.97

**Mechanism:** The automatic incoming-decoration refresh eagerly requested insertion/deletion statistics for every changed path even though the only consumer discarded those fields. --numstat requires content comparison and can hydrate missing blobs in partial or virtualized repositories, so the cost scales with the incoming changed-file/content set and can overlap across refreshes.

**Symptom:** Incoming-decoration refreshes on large partial-clone or virtualized repositories could spend 60-200+ seconds and fetch thousands of objects solely for unused numstat data, delaying decoration updates and consuming network/disk I/O.

**Fixed behavior:** Changed line 261 calls diffBetween, whose no-path implementation executes git diff --name-status -z --diff-filter=ADMR for the same triple-dot range. This preserves the Change\[\] metadata needed by decorations while removing --numstat output, its parser allocations, and eager per-file content/stat work.

**Evidence:** Base line 261 called Repository.diffBetweenWithStats from GitIncomingChangesFileDecorationProvider.getIncomingChanges. That wrapper invokes git diff with --raw --numstat and parses insertion/deletion maps, while collectIncomingChangesFileDecorations consumes only status, uri, and originalUri. The provider runs initially when enabled and on current-history-ref changes after write operations; reported measurements for large partial-clone/VFS ranges are 60-200+ seconds and thousands of hydrated objects. Blame attributes the base line to c95739960ff4c35dd0bf89ef8a8812eb377d7dfc.

### Scenario 2: Incoming-decoration refresh after commits, fetches, pulls, and enabled periodic autofetch

- Critical path: Write-operation completion fires the history-ref event without awaiting decoration listeners, so decoration work is off the originating commit/fetch/pull critical path. The merge-base and diff remain on the critical path for updated badges and can compete for Git, disk, CPU, and network resources with later work.
- Scaling input: E effective changed-ref events across R repositories, each covering N incoming paths after equality suppression; subprocess count is up to 2\*E\*R and overlapping work is unbounded by the repository operation tracker, while per-diff data scales with N.
- Effective concurrency: GitHistoryProvider throttles its own write-operation handler to a current call plus one queued call, but the decoration event callback is async and not awaited. Its cached refs are committed only after computation, and Repository.run has no read-only limiter, so slow refreshes can overlap across events and repositories. This missing coalescing is pre-existing; replacing numstat makes each overlapping operation materially cheaper.
- Cache behavior: After a refresh completes, equal local/remote ref identities skip subsequent unchanged events. There is no cache by range and no negative cache; a changed range is recomputed. Cold versus warm object behavior matches the initialization scenario, and the new command removes numstat-driven content hydration.
- Mechanism confidence: High: all write operations feed the throttled history update, changed refs fire the subscribed provider, the callback awaits merge-base then diff, and only status/URI fields are consumed. No added boundary or hotter placement is introduced.
- Magnitude uncertainty: Autofetch is opt-in, write frequency varies, and exact overlap depends on diff duration and event timing. Large incoming ranges and remote-backed object stores maximize the difference; the changed mechanism is still definitively cheaper for the data this consumer uses.
