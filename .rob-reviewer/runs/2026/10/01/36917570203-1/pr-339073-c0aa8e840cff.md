<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work, cache-lifecycle

### Scenario 1: Scroll and reveal the Agents Window Sessions list with New, Sessions, and structural group headers sticky

- Critical path: A scroll event synchronously recomputes sticky state and updates sticky-row DOM only when state changes; reveal additionally computes the constrained sticky height before adjusting scroll position.
- Scaling input: The visible tree may contain many sessions, but the new consumer selects exactly two custom candidates and sticky traversal/rendering is capped by stickyScrollMaxItemCount (configured as 7 by default).
- Effective concurrency: Single synchronous UI-thread computation per scroll/layout event; no queue, parallel work, or asynchronous fan-out is introduced.
- Cache behavior: Candidate classification and source-range eligibility are populated on tree splices and reused on warm scrolls. Candidate lookup is binary within each parent, and the provider is not rerun while scrolling. Explicit refresh invalidates and rebuilds the cache.
- Mechanism confidence: High confidence in the synchronous scroll path, cache reuse, two-candidate cardinality, and seven-row rendering bound from the changed implementation and consumer configuration.
- Magnitude uncertainty: Very deep trees can increase ancestry traversal, but this sessions tree has shallow grouping and only two custom candidates; no evidence establishes a user-visible regression on this path.
- Expensive boundaries: none found
- Verdict: No reportable regression: the changed hot path avoids collection scans during scrolling, bounds sticky work, and introduces no subprocess, IPC, filesystem, database, or network boundary.

### Scenario 2: Refresh the visible Sessions list after session/model/group/active-session changes

- Critical path: The existing update routine rebuilds local section elements and synchronously calls tree.setChildren; the new sticky resolver classifies inserted rendered rows, updates two cached candidates, and recomputes the current sticky state before the list update completes.
- Scaling input: Work scales with the number of rendered sessions/rows on a cold or replacement splice; effective custom-candidate cardinality remains two regardless of session count.
- Effective concurrency: Updates are synchronous on the UI thread; active-session updates are scheduled to the next animation frame, while other model events invoke one list update. No new concurrency burst or limiter interaction is present.
- Cache behavior: A replacement splice invalidates candidate indices and rebuilds classification for inserted rows. Subsequent scrolling is warm-cache. Empty/no-sticky state still evaluates the candidate predicate for inserted rows, but the pre-existing setChildren path already creates and splices the same full rendered collection.
- Mechanism confidence: High confidence in the full-splice call path and linear classification cost; low evidence that its incremental constant-factor work independently creates perceptible latency.
- Magnitude uncertainty: The exact maximum session count and update frequency are not measured, but the added predicate pass is linear alongside the pre-existing full-tree rebuild and retains only two candidates.
- Expensive boundaries: none found
- Verdict: No reportable regression: the diff adds bounded cache maintenance to an already collection-wide synchronous rebuild without adding a higher-order cost, expensive boundary, or retained state proportional to all sessions.

### Scenario 3: Use the new sticky sibling provider in a generic ObjectTree or AsyncDataTree across splices, filtering, collapse/expand, and explicit refresh

- Critical path: Tree rendered-splice and collapse notifications synchronously maintain candidate indices/sections, then recompute sticky state. Explicit refresh scans the current rendered list by contract; warm scrolls use the cache.
- Scaling input: Cache maintenance scales with rendered inserted rows plus selected candidate count; tests exercise 1,000 candidates. Recursive collapse can emit multiple collapse notifications, but the only production consumer added here selects two candidates and does not place a large recursive candidate hierarchy on this path.
- Effective concurrency: All model notifications and cache updates are serialized synchronously on the UI thread; there is no background work, coalescing, or external concurrency.
- Cache behavior: Positive candidates and source-range suppression are cached, removed or reindexed on rendered splices, rebuilt on explicit refresh, and scoped to the tree controller lifetime. Deleted/hidden rendered nodes are removed through splice events; no unbounded cache retention was established.
- Mechanism confidence: High confidence in cache lifecycle and synchronous event multiplicity from the model implementation; confidence is insufficient that a realistic changed product scenario reaches high candidate cardinality.
- Magnitude uncertainty: Future consumers could select many candidates or combine them with large recursive collapse operations, but no such changed production call site exists in this PR, so that risk is not a concrete diff-triggered product regression.
- Expensive boundaries: none found
- Verdict: No finding: current changed usage keeps candidate cardinality constant, and reporting hypothetical high-cardinality future API use would not meet PR-causality and realistic-trigger requirements.
