# Performance review: Git - get the diff and num stats for a commit

## Findings (1)

### 1. [medium] Avoid computing numstats for file-list-only callers

**Finding ID:** `PERF-F0B3C1239F9C`  
**Location:** <code>extensions/git/src/git.ts:1771</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Git subprocess CPU, blob/object reads, diff allocations, and additional numstat output bytes.  
**Scaling:** Cost grows with the total bytes and diff complexity of all modified files in the compared range (and is incurred once per UI request or actual incoming-ref change), rather than primarily with the number/path metadata of changed entries as before.  
**Outcome:** Increased user-visible latency on commit/comparison/history actions and additional background CPU/I/O contention after ref changes.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Built-in file-list paths ran one metadata-only \`git diff --name-status\` (or \`diff-tree --name-status\` for the empty-tree case), so ordinary modified files did not require line-count computation before the UI could proceed.  
**Changed behavior:** Git now computes line-count statistics for every changed blob during all ref/commit file-list requests, including built-in UI paths that only need change status and file names.  
**Confidence:** 0.98 — The command-line change and call paths are explicit: \`--numstat\` requires content diffs, all five built-in call sites discard the statistics, and each awaits this single Git subprocess (or runs it after ref changes). Exact wall-clock cost varies with repository/object-cache state and file contents, but the added work and scaling input are certain.

**Causal diff evidence:** RIGHT extensions/git/src/git.ts:1771 replaces the prior metadata-only \`git diff --name-status\` implementation reached by \`diffBetween2\` with \`git diff --raw --numstat\`; the diff also migrates commands.ts, historyProvider.ts, and decorationProvider.ts to this method, although those callers only map status/URIs and never read the new counters.

Opening a comparison/commit or expanding a history item's changes now waits for content diffs of the entire changed set; commits or incoming ranges containing large generated files, lockfiles, or many modified files can visibly delay the editor. Ref updates also repeat this work in the background for incoming decorations, creating avoidable Git CPU and disk/object-read pressure.

**Evidence:** Previously \`diffBetween2\` delegated to \`diffFiles\`, whose command is \`git diff --name-status -z\`; first-commit comparisons similarly used \`diff-tree --name-status\`. The new central command includes \`--numstat\`, which requires loading changed blobs and computing line diffs. \`\_openChangesBetweenRefs\`, timeline/view-commit, \`provideHistoryItemChanges\`, and incoming decorations consume only \`Change\` fields through \`toMultiFileDiffEditorUris\` or status switches. Thus the line statistics are eagerly computed but unused on these paths.

**Suggested direction:** Keep a metadata-only diff method for callers that only need statuses/URIs and migrate these built-in call sites back to it; reserve \`--numstat\` for the new opt-in API or a caller that actually surfaces the counters. Preserve the existing single-process ordering and path filtering.

### Scenario 3: Refresh incoming-change file decorations after repository/ref updates

- Critical path: On provider construction and actual current/upstream ref changes, an async event handler resolves a merge base and runs the changed diff. - Scaling input: One changed ref pair per affected repository after equality suppression; numstat cost scales with total modified content in the incoming range.
- Effective concurrency: Within a repository, unchanged ref pairs are skipped and history write handling is throttled; actual ref changes launch one merge-base process followed by one diff process. - Cache behavior: The provider retains the last ref identities and skips unchanged pairs, but it does not cache a prior diff result for a new pair. Warm object caches may reduce reads; line stats are recomputed on each real ref update.
- Mechanism confidence: High for the added content-diff work and background reachability; user-visible contention magnitude varies by repository and update pattern.
- Magnitude uncertainty: Impact depends on number of repositories and size of incoming ranges; small repositories remain cheap, while monorepos or broad fetched ranges can create noticeable contention.
- Expensive boundaries:

- Verdict: Covered by the reported finding as an automatic background amplification of the same unused numstat work; no separate concurrency-burst finding because realistic per-repository cardinality is bounded to actual ref changes.
