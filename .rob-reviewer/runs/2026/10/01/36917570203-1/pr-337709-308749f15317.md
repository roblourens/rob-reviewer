# Performance review: Add beforeText condition to auto-closing pairs

[PR #337709](https://github.com/microsoft/vscode/pull/337709) at `308749f153176079adb42de9bb30328b421c1960`

## Findings (1)

### 1. [medium] Skip prefix extraction for unconditional auto-closing pairs

**Finding ID:** `PERF-4A37276813B1`  
**Location:** <code>src/vs/editor/common/cursor/cursorTypeEditOperations.ts:348</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous piece-tree range lookups plus newly allocated prefix strings on the editor input path  
**Scaling:** For each typed opening delimiter, cost grows with the sum of the cursor columns for every matching candidate; multi-cursor edits on long/minified lines allocate and scan a full prefix per cursor before the edit can proceed.  
**Outcome:** Increased keystroke latency and avoidable allocation/GC pressure, with visible input jank on long lines or many cursors.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The candidate check read only the short span needed to compare the configured opening string. Existing language configurations without beforeText did not copy the text from column 1 to every cursor during candidate selection.  
**Changed behavior:** After an opening candidate matches, the changed line synchronously copies the entire line prefix for every cursor and passes it to shouldAutoCloseBefore; this happens even though that method immediately returns true for the overwhelmingly common beforeText === undefined case.  
**Confidence:** 0.98 — The call path from every non-composition typing event through typeWithInterceptors/getAutoClosingPairClose/\_findAutoClosingPairOpen is direct, and the new range read is visibly evaluated before shouldAutoCloseBefore can discover that beforeText is undefined. The exact delay depends on line length and cursor count, but the added synchronous work and allocation are certain.

**Causal diff evidence:** RIGHT line 348 adds model.getValueInRange(new Range(position.lineNumber, 1, ..., position.column)) inside the candidate/cursor loop without checking candidate.beforeText, introducing a whole-prefix read for all matching auto-closing pairs.

Typing common delimiters such as quotes, braces, and parentheses now performs an extra O(cursor-column) model read/allocation per cursor even for existing pairs that do not use the new option. Long generated/minified lines and multi-cursor typing can therefore stall the synchronous input handler and add GC pressure.

**Evidence:** \_findAutoClosingPairOpen is called directly by the normal typing interceptor. The added getValueInRange spans column 1 through position.column and runs inside both the candidate and positions loops. StandardAutoClosingPairConditional.shouldAutoCloseBefore immediately returns true when beforeText is absent, proving the extracted prefix is unused for legacy pairs. TextModel.getValueInRange delegates to the piece-tree and returns a newly constructed string; later processing already reads the line again with getLineContent.

**Suggested direction:** Guard the extraction and predicate with candidate.beforeText (or make shouldAutoCloseBefore accept a lazily supplied prefix), so the full prefix is read only for pairs that actually configure this condition; preserve lastIndex reset and matching semantics for configured regexes.
