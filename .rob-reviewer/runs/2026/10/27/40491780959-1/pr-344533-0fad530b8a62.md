### Scenario 1: An installed extension's Markdown code-block editor contribution changes only its maxAutomaticHeight while Markdown editors and previews are open.

- Critical path: The extension-registry change recomputes contributions across installed extensions; the new scalar comparison can now notify contribution listeners. Each open Markdown editor reloads provider definitions and posts changed definitions to its webview, while each open Markdown preview schedules a refresh. This event handling is on the update critical path, but the newly distinguished case is an infrequent extension-contribution lifecycle event rather than typing, rendering, scrolling, or startup.
- Scaling input: Installed extension count controls contribution comparison; open Markdown editor/preview count controls fan-out; static provider count controls filesystem reads. A cap-only same-version contribution mutation is uncommon in normal extension update flows, where version changes already triggered the same work.
- Effective concurrency: Each open editor starts its own asynchronous provider reload without a shared global limiter. A per-editor contributionUpdate counter suppresses stale completion results, though it does not cancel already-started reads. Webview notifications are one per open editor after definitions load.
- Cache behavior: Contribution snapshots remain cached until an extension-registry event. A detected change clears resolved code-block-editor caches before definitions are rebuilt; subsequent block resolutions warm those caches and coalesce identical request keys. There is no repeated work without another contribution/provider event.
- Mechanism confidence: High confidence in the listener, cache-clear, filesystem, and webview-notification paths; low prevalence does not affect the traced mechanism.
- Magnitude uncertainty: Large numbers of simultaneously open Markdown editors or static providers increase fan-out, but cap-only same-version contribution changes are primarily development/lifecycle events and the refresh is required for the advertised behavior.
- Expensive boundaries:
  - filesystem at <code>extensions/markdown-language-features/src/preview/markdownEditorProvider.ts:\#loadCodeBlockEditorProviders</code>: Read each static code-block editor provider's source resource while rebuilding provider definitions.; cardinality: At most one read per static provider per open Markdown editor for the contribution-change event; exportApi providers such as Mermaid perform no filesystem read here.

  - IPC at <code>extensions/markdown-language-features/src/preview/markdownEditorProvider.ts:postCodeBlockEditorProviders and extensions/markdown-language-features/src/preview/preview.ts contribution listener</code>: Post refreshed code-block editor definitions to each open Markdown editor webview and refresh open Markdown previews.; cardinality: One provider-definition notification per open editor and one scheduled refresh per open preview for the rare cap-only contribution event.

- Verdict: No reportable regression. The diff intentionally makes a previously ignored contribution field participate in a rare lifecycle refresh; it does not add recurring hot-path work, and normal versioned extension updates already paid this cost.

### Scenario 2: A Mermaid block is re-rendered after an edit, including transitions into and out of a syntax error.

- Critical path: Each content notification aborts the prior render, renders Mermaid into a detached staging node, then the changed line performs one querySelector for .mermaid-error and sets role before the existing DOM swap and size report. The added work is synchronous but bounded to the single detached diagram and is negligible beside the existing Mermaid parse/render.
- Scaling input: Work scales with edit frequency and Mermaid diagram complexity in pre-existing rendering. The added query is once per completed render over one detached diagram subtree, not per SVG node or per error line.
- Effective concurrency: At most one current render is authoritative; newer edits abort older renders. Aborted renders return before the changed query and DOM swap. Size IPC is deduplicated by reportedHeight.
- Cache behavior: There is no render-result cache. AbortController coalesces authority to the latest edit, and reportedHeight acts as a one-value negative duplicate cache for size notifications. The diff changes neither behavior.
- Mechanism confidence: High confidence from the direct render call path and abort/dedup guards.
- Magnitude uncertainty: Exact Mermaid render duration varies with diagram size, but the added DOM operation remains bounded and does not alter renderer complexity.
- Expensive boundaries:
  - IPC at <code>extensions/mermaid-markdown-features/preview-src/markdownEditor/index.ts:main/render/reportSize</code>: Receive editor content through WebEditorClient and report a changed natural height to the parent.; cardinality: One content event per editor update; at most one reportSize IPC per distinct resulting height because equal heights are suppressed.
    - Introduced by diff: false; previous behavior: The same content and size IPC occurred before the diff; only the error element lacked role=alert.; critical-path effect: Existing content delivery starts rendering and a size report follows a completed authoritative render; the role attribute does not add, duplicate, or delay either IPC boundary materially.
- Verdict: No reportable performance regression. The accessibility attribute adds constant bounded DOM work and no new boundary call, retained state, or concurrency.

### Scenario 3: A Mermaid editor webview loads, lays out its diagram, resizes, or encounters a startup failure.

- Critical path: The CSS reset removes default body margin/padding before first layout. Existing ResizeObserver callbacks calculate natural height and report only changed values. On startup failure, the changed code creates one error element, sets one role attribute, and replaces the root children.
- Scaling input: Resize work scales with actual viewport size changes, not document node count introduced by this diff. Startup error work is constant per failed webview.
- Effective concurrency: Browser layout and ResizeObserver delivery are serialized on the webview UI thread. Height reports are deduplicated; startup failure handling runs once from the rejected main promise.
- Cache behavior: No cold/warm resource cache is changed. reportedHeight suppresses repeated equal size reports across resize callbacks.
- Mechanism confidence: High confidence from the stylesheet, ResizeObserver, and startup catch paths.
- Magnitude uncertainty: Browser layout costs vary by diagram complexity, but removing default spacing does not add layout passes or a feedback mechanism.
- Expensive boundaries:
  - IPC at <code>extensions/mermaid-markdown-features/preview-src/markdownEditor/index.ts:WebEditorClient.connect/reportSize</code>: Connect the Mermaid guest to its parent and report natural size after layout changes.; cardinality: One connection per webview and one size IPC per distinct measured height; the CSS reset may alter the initial measurement but does not add an observer or remove height deduplication.
    - Introduced by diff: false; previous behavior: The same connection, observer, geometry measurement, and deduplicated size reporting existed with browser-default body spacing.; critical-path effect: Connection is required before normal rendering; size IPC follows layout. The changed CSS and startup error role do not introduce additional messages.
- Verdict: No reportable performance regression. The CSS reset simplifies geometry, and the error role is constant one-time work.
