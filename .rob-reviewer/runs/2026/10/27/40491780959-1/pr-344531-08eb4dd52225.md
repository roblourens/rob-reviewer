<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** boundary-fanout, cache-lifecycle, concurrency-burst

### Scenario 1: Pull requests whose change detector enables the three chat-lib checks

- Critical path: The Linux, macOS, and Windows jobs run independently after \`changes\`; \`pr-gate\` waits for all three results, so runner queue/provisioning, checkout, dependency setup, build, and tests are on the required-check critical path.
- Scaling input: A qualifying PR creates exactly three OS jobs, not work proportional to changed files or package count. Each job extracts and tests one chat-lib package.
- Effective concurrency: Up to three OS jobs run in parallel; steps within each job are serial. The diff changes runner labels but neither adds jobs nor raises aggregate concurrency.
- Cache behavior: Each job restores one node\_modules cache keyed by OS/architecture and lockfile state. On a hit, Copilot dependency installation is skipped; chat-lib still performs one npm install. On a miss, one additional Copilot npm install runs. The macOS cache warmer is explicitly arm64 and the cache key includes \`process.arch\`; the changed workflow does not alter cache-key logic, and repository evidence does not establish a new miss state from the versioned labels.
- Mechanism confidence: High confidence that job count, ordering, transitive commands, cache logic, and boundary cardinality are unchanged; low evidence for any performance degradation caused by selecting the stated images.
- Magnitude uncertainty: Versioned images can have different queue or hardware characteristics over time, but the diff and repository provide no concrete evidence of slower capacity, added work, or cache misses; exact hosted-runner timing is external and variable.
- Expensive boundaries:
  - other expensive boundary at <code>.github/workflows/pr.yml:767-809</code>: GitHub-hosted runner scheduling and provisioning for Linux, macOS, and Windows; cardinality: Exactly three conditional jobs per qualifying PR, up to three concurrently
    - Introduced by diff: false; previous behavior: The same three jobs provisioned GitHub-hosted runners through floating \`-latest\` labels; the diff only selects versioned labels.; critical-path effect: Provisioning and queue time block each job and therefore the required PR gate.
  - network at <code>.github/workflows/pr.yml:774-809 and .github/actions/test-chat-lib/action.yml:6-51</code>: Repository checkout, Node setup, cache restore, and npm registry access; cardinality: One checkout, one Node setup, and one cache lookup per OS job; one unconditional chat-lib npm install per job plus one Copilot npm install only on cache miss
    - Introduced by diff: false; previous behavior: Identical actions and cache/install conditions ran on each of the same three floating-label jobs.; critical-path effect: All operations execute serially within each job before build/test completion and are on the PR-gate critical path.
  - subprocess at <code>.github/actions/test-chat-lib/action.yml:27-51</code>: Extract chat-lib, remove ancestor node\_modules, build, and run tests; cardinality: One extract, build, and test sequence per OS job
    - Introduced by diff: false; previous behavior: The same composite action executed once on each OS job.; critical-path effect: These serial commands determine each job's completion time.
- Verdict: No reportable regression: the runner-label substitutions do not add critical-path work, increase fan-out, defeat a demonstrated cache, or increase concurrency.

### Scenario 2: Manual chat-lib workflow dispatch

- Critical path: A dispatch starts the three matrix jobs; each job must provision a runner and serially complete checkout, cache/dependency setup, extraction, build, and tests for the workflow to finish.
- Scaling input: The fixed matrix has exactly three OS entries and one chat-lib package per entry, unchanged by the diff.
- Effective concurrency: The three matrix jobs may run concurrently; the workflow-level concurrency group cancels an older run for the same ref. The diff does not change matrix size, fail-fast behavior, or cancellation.
- Cache behavior: The same OS/architecture-and-lockfile caches are consulted as in PR checks. Warm hits skip Copilot installation; misses add one Copilot npm install, while chat-lib npm install always runs. No changed cache key or demonstrated negative-cache behavior is introduced.
- Mechanism confidence: High confidence that the matrix cardinality, concurrency controls, boundaries, and commands are unchanged by the label pinning.
- Magnitude uncertainty: Hosted image performance and queue depth can vary externally, but no changed code establishes a slower image or greater work.
- Expensive boundaries:
  - other expensive boundary at <code>.github/workflows/chat-lib-package.yml:16-23</code>: GitHub-hosted runner scheduling and provisioning for the three matrix entries; cardinality: Exactly three jobs per dispatch, with same-ref older runs cancelled by the existing concurrency policy
    - Introduced by diff: false; previous behavior: The matrix already provisioned exactly three hosted runners through floating labels.; critical-path effect: Queue and provisioning time precede every matrix job and affect total workflow completion.
  - network at <code>.github/workflows/chat-lib-package.yml:25-30 and .github/actions/test-chat-lib/action.yml:6-33</code>: Checkout, Node setup, cache restore, and npm dependency downloads; cardinality: One checkout/setup/cache lookup per matrix job; one chat-lib install per job and one extra Copilot install on a cache miss
    - Introduced by diff: false; previous behavior: The same composite action and boundary calls ran once for each of the same three matrix entries.; critical-path effect: These serial operations must complete before build and tests.
  - subprocess at <code>.github/actions/test-chat-lib/action.yml:27-51</code>: Package extraction, filesystem cleanup, build, and tests; cardinality: One serial sequence per matrix job
    - Introduced by diff: false; previous behavior: Unchanged composite action and multiplicity.; critical-path effect: Directly determines each job's completion latency.
- Verdict: No reportable regression: the manual workflow retains the same three-way fan-out and work per job.

**Summary:** Reviewed all changed files and diff pages for the performance focus. Traced both affected CI workflows through runner provisioning, checkout, cache restore, dependency installation, extraction, build, and test execution. The version pins preserve job count, concurrency, command multiplicity, and cache-key behavior; no high-confidence actionable performance regression or provable shipped-regression fix was found.
