# Performance review: build: cache Playwright browsers in product build test jobs

[PR #343395](https://github.com/microsoft/vscode/pull/343395) at `b3a9723a21056a74d955dce3b93672ceb03e91ce`

## Findings (1)

### 1. [medium] Populate each cold Playwright cache only once

**Finding ID:** `PERF-F5C37685827B`  
**Location:** <code>build/azure-pipelines/common/restore-playwright-browsers.yml:9</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Filesystem reads, archive/hash CPU, and cache-service upload calls for the Playwright browser directory.  
**Scaling:** Cost grows with the browser cache size and the number of sibling test jobs sharing a cold key: six duplicate save attempts per OS/architecture in the current product-build fan-out, across multiple platform stages.  
**Outcome:** Increased cold-run post-job latency and aggregate CPU/disk/network load, reducing CI throughput.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, each job could download Playwright browsers, but it did not additionally archive/hash and publish that browser tree in a post-job cache save; there was no same-key save burst.  
**Changed behavior:** Each test job now restores the Playwright cache and, after a miss, independently schedules a post-job save of the downloaded browser directory under the same key.  
**Confidence:** 0.94 — The changed template explicitly documents that a miss saves the folder after the job, and the product-build template defines six sibling test jobs per platform with identical Agent.OS, VSCODE\_ARCH, and Playwright package contents. All six begin only after the same compile dependency, so a new/evicted key is realistically missed by all before any one job can publish it. Exact upload deduplication is service-dependent, but each miss-side save must at least traverse/hash/archive the multi-browser directory independently.

**Causal diff evidence:** RIGHT line 9 adds a Cache&#64;2 task to a template that RIGHT lines 21 of each OS test-step file now invoke from every product test job; RIGHT line 10 gives all jobs for one OS/architecture/version the same cache key.

A cold cache after a Playwright upgrade or eviction makes up to six sibling jobs per platform archive/hash and attempt to publish the same large multi-browser payload, consuming agent CPU, disk I/O, and cache-service bandwidth and delaying job/pipeline completion after tests finish.

**Evidence:** \`product-build-template.yml\` creates six parallel UnitElectron, Unit, BrowserRemote, Integration, AgentHostE2E, and Smoke jobs for each tested platform. Each reaches the newly included restore template. The cache key contains only OS, architecture, and \`node\_modules/playwright/package.json\`, so those six jobs share one key. On the first run after a Playwright update or cache eviction they all miss, then the existing \`playwright-install\` populates \`.build/ms-playwright\`; Cache&#64;2 consequently runs six post-job saves for the same browser tree. Even if the cache backend deduplicates the final object, each agent performs the directory walk/archive/hash work and issues a save boundary call.

**Suggested direction:** Populate/save each OS/architecture Playwright cache in a single producer job before releasing the test-job fan-out (or otherwise designate one miss-side writer), while keeping the test jobs restore-only so warm behavior remains unchanged.
