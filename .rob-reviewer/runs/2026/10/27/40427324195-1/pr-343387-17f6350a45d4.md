# Performance review: ci: cache Playwright browsers for pull request browser tests

[PR #343387](https://github.com/microsoft/vscode/pull/343387) at `17f6350a45d4f3d28700b6356c85c3b10ca599a5`

## Findings (1)

### 1. [medium] Use lookup-only mode in the cache-warming jobs

**Finding ID:** `PERF-89FC1D14D1BC`  
**Location:** <code>.github/workflows/pr-node-modules.yml:207</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Playwright browser cache archive bytes, filesystem writes, and decompression CPU  
**Scaling:** The wasted restore occurs once for each Linux, macOS, or Windows warming job that runs because any other cache for that platform is missing; its cost scales with the cached browser set, especially the macOS Chromium plus WebKit archive.  
**Outcome:** increased cache-warming job latency, network I/O, disk I/O, and runner CPU  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, these platform warming jobs did not fetch or extract Playwright browser archives. Existing warm-only resources such as the WSL installer explicitly use actions/cache lookup-only mode.  
**Changed behavior:** Each new Cache Playwright browsers step invokes restore-playwright with save-cache true, but the composite action always performs a normal actions/cache/restore. Therefore an exact browser-cache hit downloads and extracts the archive even though pr-node-modules never runs browser tests or otherwise consumes the restored files.  
**Confidence:** 0.98 — The job gates, normal restore behavior, lack of downstream browser use, and existing lookup-only repository pattern are all explicit in the changed workflows. Archive size and exact duration vary by browser version, but the unnecessary network/extraction mechanism and critical-path placement do not.

**Causal diff evidence:** Added pr-node-modules.yml lines 207-213 (and analogous macOS/Windows additions) place restore-playwright in warm-only jobs; added restore-playwright/action.yml lines 37-43 perform a full cache restore on every hit rather than a metadata lookup.

After an unrelated node\_modules, Electron, WSL, or detector miss starts a platform job while the Playwright cache is already warm, that job unnecessarily downloads and extracts a large browser archive before it can finish. This adds substantial CI latency and bandwidth on up to three platform jobs per dependency/cache change.

**Evidence:** The platform gates run when any cache in getCaches is missing, not specifically Playwright (.github/actions/detect-missing-caches/detect.ts:160-170 and pr-node-modules.yml:121/217/302). The added steps at lines 207, 292, and 384 all set save-cache true. restore-playwright/action.yml:37-43 uses actions/cache/restore without lookup-only, while the analogous warm-only restore-wsl-installer/action.yml:23 passes lookup-only when save-cache is true. No later step in any of these three jobs uses .build/ms-playwright.

**Suggested direction:** Add an explicit lookup-only input to restore-playwright and set it to true in the three pr-node-modules warming calls, while leaving it false for browser-test/component-fixture consumers that need the files. On a miss, continue downloading and saving exactly as today.

### Scenario 3: Component fixture tests and screenshot rendering on pull requests and branch pushes

- Critical path: Each of the two parallel jobs restores the browser cache before its existing playwright install and test/render step. On pushes, a miss also downloads and saves the browser before the consumer runs.
- Scaling input: Two Ubuntu jobs, each requesting Chromium 1.61.1 under the current lockfiles. Because OS, architecture, version, and browser arguments match, both currently address the same cache key.
- Effective concurrency: The Playwright fixture and screenshot jobs run concurrently and may race on a cold push. Each performs one restore/install sequence. Existing workflow-level cancellation coalesces superseded runs by PR number or SHA.
- Cache behavior: Pull requests restore only; main/release pushes restore and save on misses. Warm runs transfer the shared Chromium archive into each isolated runner. On a simultaneous cold push both jobs may miss and download, but both already downloaded Chromium independently before the PR, so browser-download cardinality is not increased; one cache save may win the identical key.
- Mechanism confidence: High: both job inputs, lockfile versions, concurrency, and downstream consumers are explicit.
- Magnitude uncertainty: The exact benefit depends on cache hit rate and relative GitHub-cache versus Playwright-CDN throughput; cold concurrent save conflict behavior is service-dependent.
