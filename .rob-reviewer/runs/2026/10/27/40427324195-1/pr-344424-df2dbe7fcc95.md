### Scenario 1: First on-device dictation after upgrading from Foundry Local SDK 2.0.1 to 2.2.1

- Critical path: The renderer lazily creates one utility process and sends start over IPC. start schedules model/session preparation and returns so microphone capture can proceed, but the first transcript depends on runtime provisioning, SDK import/manager initialization, model catalog lookup, optional model download/load, and native session start. The runtime and model downloads are therefore off the capture-start path but on the first-transcript path.
- Scaling input: One host target, one runtime version, and one selected model per utility-process service; audio IPC scales with capture chunks but that unchanged stream is not caused by this dependency pin.
- Effective concurrency: One active transcription session is enforced. Runtime provisioning is coalesced per library path within a process, and model preparation is coalesced by one model promise. Separate VS Code windows can still fetch into separate staging directories before a filesystem publish lock selects a winner, but that cross-process behavior predates the diff.
- Cache behavior: The runtime cache is keyed by SDK version and target. Existing 2.0.1 caches do not satisfy 2.2.1, so the first post-upgrade use performs one 2.2.1 CDN fetch/extraction; a per-target completion marker plus required-file checks make later uses warm. The model cache is separate and remains keyed by the configured model; model.download runs only when model.isCached is false. In-flight runtime and model work is positively coalesced in-process; failures clear the in-flight state for retry.
- Mechanism confidence: High confidence in the version-keyed cold miss, one-target CDN request, extraction, and downstream first-transcript dependency because these are directly traced through product stamping, renderer IPC, runtime provisioning, and model initialization.
- Magnitude uncertainty: The repository diff does not expose the 2.2.1 tarball size, native initialization duration, or SDK-internal catalog behavior, so it does not establish that the upgraded payload is larger or slower than 2.0.1.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/localTranscription/electron-browser/localTranscriptionService.ts:75-131</code>: Create the local-transcription utility process and invoke start; subsequent PCM chunks are sent to that process.; cardinality: One worker per renderer window on first local-dictation use, one start call per session, then one IPC call per captured PCM chunk.
    - Introduced by diff: false; previous behavior: The 2.0.1 SDK used the same lazy utility-process and audio IPC path.; critical-path effect: Worker creation/start must complete before capture setup continues; chunk IPC is the existing streaming path.
  - filesystem at <code>src/vs/platform/localTranscription/node/foundryLocalRuntime.ts:98-184, 274-374</code>: Check the versioned completion marker and required native files, then extract and atomically publish a downloaded runtime on a miss.; cardinality: Warm use checks one marker and a fixed set of six or seven target files; first use for 2.2.1 extracts one tarball and publishes one target directory.
    - Introduced by diff: true; previous behavior: A warm 2.0.1 cache avoided extraction, while a cold 2.0.1 cache performed the same fixed-cardinality work under the old version directory.; critical-path effect: Warm checks precede SDK initialization; extraction is on the first-transcript path for the first 2.2.1 use.
  - network at <code>src/vs/platform/localTranscription/node/foundryLocalRuntime.ts:155-184, 344-374</code>: Download one target-specific 2.2.1 native-runtime tarball from the VS Code CDN.; cardinality: One download per version/target cache miss per process, coalesced for concurrent callers in that process; zero on warm cache.
    - Introduced by diff: true; previous behavior: Users with a complete 2.0.1 cache made no runtime request; cold 2.0.1 users made the same single target-specific request.; critical-path effect: The fetch blocks SDK manager creation and therefore the first transcript, while audio is buffered.
  - network at <code>src/vs/platform/localTranscription/node/localTranscriptionService.ts:548-581</code>: Query the SDK model catalog and optionally download the selected speech model.; cardinality: One catalog lookup per model preparation and at most one model download when the existing model cache reports a miss.
    - Introduced by diff: false; previous behavior: The 2.0.1 SDK followed the same catalog, cache-check, and conditional model-download path.; critical-path effect: Model availability/load blocks the first transcript but not initial audio capture.
- Verdict: No reportable regression. The version bump necessarily causes one bounded, cached post-upgrade runtime fetch, but it does not increase request cardinality, move provisioning to startup, defeat warm-cache checks, or add concurrency. There is no code evidence that 2.2.1 materially increases payload size or native work.

### Scenario 2: Warm-cache repeated on-device dictation sessions

- Critical path: Each session crosses IPC to the existing utility process, verifies the fixed runtime file set, reuses the imported SDK, manager, and already loaded selected model, opens one native transcription session, and streams PCM chunks serially. Session start and transcript production remain user-visible critical paths.
- Scaling input: Session count and PCM chunk frequency; the changed version pin does not alter the number of runtime checks, IPC calls, or native append operations per session in repository code.
- Effective concurrency: One active recording and one FIFO append chain. The loaded model and resolved model promise are reused for the same model ID, so repeated sessions do not create concurrent model loads.
- Cache behavior: After the first 2.2.1 provisioning, the marker and required files produce a warm hit with no CDN request. The SDK module, manager, and model are retained for the utility-process lifetime; the model's on-disk cache survives process restarts.
- Mechanism confidence: High confidence that repository-level scheduling, caching, and boundary cardinality are unchanged; only the loaded SDK implementation changes.
- Magnitude uncertainty: The native SDK implementation is opaque in the supplied repository, so internal CPU or memory differences between 2.0.1 and 2.2.1 cannot be established from this diff.

### Scenario 3: Dependency installation and publish-time dictation-runtime packaging

- Critical path: A dependency restore fetches the pinned npm package and permits its single install script, after which the repository postinstall patches the SDK loader. On publish builds, each supported target job copies fixed native files, sequentially downloads two NuGet artifacts, compresses/hashes one tarball, performs one Azure blob property request, and uploads the blob when absent. These operations block dependency setup or the publish job, not product startup.
- Scaling input: A fixed set of two NuGet artifacts per target and at most five supported platform/architecture targets across build jobs; no repository-sized or user-input-sized loop is introduced.
- Effective concurrency: Within one target build, the two NuGet packages are installed sequentially and blob upload follows packaging. Platform target jobs may run concurrently in CI, as before. The versioned blob path prevents overwrite and HEAD-before-upload makes reruns idempotent.
- Cache behavior: The package-lock pins the npm tarball by integrity. NuGet downloads are per publish build with only the feed service index cached within that two-package operation. Azure blobs are positively cached by version/target and SHA metadata; 2.2.1 uses a new path, so its first publish uploads once and matching reruns skip.
- Mechanism confidence: High confidence in fixed artifact cardinality, sequential per-target downloads, and idempotent versioned upload from the build scripts and lockfile.
- Magnitude uncertainty: The supplied diff does not provide npm or native artifact byte sizes, so exact clean-install, compression, and upload duration changes are unknown.
- Expensive boundaries:

### Scenario 4: Dictation-runtime build test execution

- Effective concurrency: The test is synchronous within its test case. The existing download-failure test iterates two targets sequentially with an empty feed list, so it performs no network request.
- Cache behavior: Operating-system file cache may make repeated test runs warm, but no application cache is relevant; work is fixed per invocation.
- Mechanism confidence: High confidence because the entire added test hunk is visible and all I/O calls are explicit.
- Magnitude uncertainty: Exact filesystem latency varies, but the files and cardinality are fixed and tiny.
- Expensive boundaries:

- Verdict: No reportable regression. The added test performs bounded validation-only I/O with no realistic product or CI throughput impact.
