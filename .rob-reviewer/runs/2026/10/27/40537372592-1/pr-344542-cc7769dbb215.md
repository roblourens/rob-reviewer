# Performance review: sessions: show automation sessions in the Sessions list on reply or on request

[PR #344542](https://github.com/microsoft/vscode/pull/344542) at `cc7769dbb215919443de6cc10b24f5767ce2346f`

## Findings (2)

### 1. [medium] Avoid scanning the full session catalog on every chat send

**Finding ID:** `PERF-A3ACA5A43FF5`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/automationSessionsListing.ts:35</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU, a newly allocated merged session array, chat-array traversals, and URI equality comparisons  
**Scaling:** The added work is O(S+C) per accepted request, where S is every loaded session across providers and C is the chats inspected before the owner is found; \`\_getMergedSessions()\` allocates all S entries even when the active session matches early, so total cost grows with catalog size times message frequency.  
**Outcome:** increased synchronous message-submit latency and UI-thread CPU/GC pressure; queued requests are also delayed before \`processPendingRequests\` starts  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this contribution, accepting a request did not perform this session-catalog ownership lookup for automation-listing purposes.  
**Changed behavior:** Every accepted request now calls \`getSessionForChatResource\` before checking whether the owner is an automation session or whether the setting is \`afterReply\`, so regular sessions and disabled/non-applicable modes pay the full catalog scan too.  
**Confidence:** 0.99 — The new AfterRestored contribution subscribes to the global accepted-request event, which fires synchronously for every non-system, visible user request. The called implementation constructs a merged array of every provider's sessions and scans each session's chats until a match, before the new code can reject ordinary non-automation sessions.

**Causal diff evidence:** The newly added listener at lines 34-35 invokes \`sessionsManagementService.getSessionForChatResource(chatSessionResource)\` for the global request event; there was no automation-listing listener or per-send catalog scan before this PR.

Sending any ordinary chat message now synchronously rebuilds and scans the complete provider session catalog. Users with long session histories or many nested chats pay this cost on every message even though almost all such requests cannot change automation listing state.

**Evidence:** \`ChatService.notifyAccepted\` synchronously fires \`onDidAcceptRequest\` for every accepted non-system, visible submission; in the queued path it does so before \`processPendingRequests\`. \`SessionsManagementService.getSessionForChatResource\` first calls \`\_getMergedSessions()\` (which concatenates every provider catalog), then loops each session and linearly searches \`session.chats\` plus \`mainChat\`. The new listener performs that call before \`session?.isAutomation\` and before reading \`SESSIONS\_LIST\_SHOW\_AUTOMATION\_SESSIONS\_SETTING\`.

**Suggested direction:** Do not resolve ownership through a full catalog scan for every global request. At minimum gate on \`AfterReply\` before lookup; then route automation replies through an automation/session-specific signal or add/reuse an authoritative resource-to-session index in the management service so ordinary sends and repeated replies are O(1) rather than rebuilding and scanning the catalog.

### 2. [medium] Preserve status short-circuiting before resolving historical runs

**Finding ID:** `PERF-8169E7709E97`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:2428</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** URI equality checks, temporary run/status objects, and filtered arrays on the renderer's synchronous observable derivation  
**Scaling:** Each history publication now performs O(R\*S) session matching before checking run priority, where R is the aggregate retained run count (up to 50 per cloud automation) and S is the full loaded session catalog; this repeats every 15 seconds while any cloud run is active.  
**Outcome:** periodic CPU and allocation spikes on the UI thread, causing slower rendering and possible interaction jank for users with substantial automation history and session catalogs  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous derivation checked statuses in priority order with short-circuiting: it resolved sessions only for running runs while checking NeedsInput, returned immediately when any pending/running run existed, and inspected completed history only when no active run existed.  
**Changed behavior:** The added map eagerly resolves a session with a full \`automationSessions.find(...)\` for every historical run and allocates an intermediate object for every run before the later NeedsInput/InProgress checks can return.  
**Confidence:** 0.98 — The changed renderer now maps the complete aggregate run history and linearly searches the complete loaded-session catalog for every run before any priority check. The cloud store fetches up to 50 runs per automation and republishes history every 15 seconds while a run is active, so the multiplicity and repeated UI-path execution are directly established; only the exact frame-time cost depends on user history size.

**Causal diff evidence:** The PR adds \`runs.read(reader).map(...)\` and the per-run \`automationSessions.find(...)\` at lines 2426-2428 ahead of all status checks, replacing the deleted status-specific \`some(...)\` passes that returned on NeedsInput or any pending/running run before examining completed history.

While an automation is pending or running, the cloud provider refreshes history every 15 seconds. Each refresh can now scan the entire loaded session catalog once per retained run before rendering the Automations indicator, even though an early active run already determines the indicator; large histories can produce recurring UI-thread CPU/GC spikes.

**Evidence:** \`automationService.runs\` is documented as all runs across all automations. \`GitHubCloudAutomationStore.refreshHistory\` requests \`per\_page: 50\` for every automation and publishes the flattened history, while \`CloudAutomationStore\` schedules another refresh every 15 seconds when any run is pending/running. \`automationSessions\` is assigned \`this.sessions\`, the full session catalog. The added line therefore performs one linear URI search per aggregate run before the active-status checks; the deleted implementation deferred completed-run matching until after active checks.

**Suggested direction:** Keep the priority checks lazy, or build one resource-keyed session map in O(S) and scan runs without intermediate arrays. In particular, determine NeedsInput/InProgress before resolving completed historical runs, while applying \`isSessionListed\` only to candidates whose status can affect the current result.
