### Scenario 3: First-task parallel, review, and upgrade follow-ups

- Critical path: Session observables detect InProgress/Completed state, a disposable 1.5-second settle timer fires, and the onboarding engine may open the Sessions view or show a Spotlight. Plan navigation runs only after the user presses See Plans.
- Scaling input: Active-session checks are O(1). The free-user parallel-upgrade condition scans the current merged session collection, O(number of sessions across providers), on session-list or observed status changes. The per-window developer-mode set grows with distinct active sessions run in that window.
- Effective concurrency: Each condition has one autorun; its settle timer is owned by the reader store and is cancelled on invalidation, preventing timer accumulation. No parallel subprocess/network burst is introduced.
- Cache behavior: Session lists and status are existing in-memory provider models. First-task progress persists across windows; the developer-mode session-id set is window-local and discarded with the contribution.
- Mechanism confidence: High confidence in the O(n) pass and timer ownership; lower confidence in any meaningful user-visible cost because the path is gated and performs no external I/O.
- Magnitude uncertainty: Provider session counts and metadata-change frequency vary. Live agent-host persistence is capped at 100 summaries per host, while active provider collections can differ; no evidence shows this extra in-memory pass causes measurable latency.
- Expensive boundaries:

### Scenario 4: Generic Spotlight and sequence-step interactions

- Critical path: A Spotlight step checks target selection once before showing, renders button labels once per displayed step, and an advancing primary action completes after its action promise. A visible run step invokes onDidShow, which is guarded to emit one scenario impression.
- Scaling input: Linear in the small number of onboarding steps; this PR's tours contain one or two visible steps.
- Effective concurrency: Only one presentation occupies the onboarding slot. Primary actions are single-flight per step and cancellation is disposed when the step ends or target is replaced.
- Cache behavior: No cache is involved. Target providers and DOM elements are resolved per displayed step; missing targets use fixed 3- or 5-second waits.
- Mechanism confidence: High confidence from the service's didReportShown guard and per-step render flow.
- Magnitude uncertainty: Telemetry transport batching details are service-dependent, but the call is non-awaited and cardinality is explicitly one.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/onboarding/browser/sequence/runOnboardingStep.ts:44-47 and src/vs/workbench/contrib/onboarding/browser/onboardingService.ts:492-535</code>: Queue the onboarding.scenarioShown telemetry event when a run step rendered UI.; cardinality: At most one event per scenario run because OnboardingScenarioService guards repeated onDidShow calls.
    - Introduced by diff: true; previous behavior: Run-only visible steps could complete without reporting the shown impression.; critical-path effect: Telemetry logging is not awaited by the presentation and is off the interaction critical path.
- Verdict: No reportable regression: new DOM/selection work is constant per step, and the added telemetry event is single, asynchronous, and off the UI critical path.
