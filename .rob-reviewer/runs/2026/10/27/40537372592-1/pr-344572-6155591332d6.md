<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, boundary-fanout, cache-lifecycle

### Scenario 1: An active top-level agent-host chat turn receives session-state updates while one or more MCP servers require authentication.

- Critical path: Each relevant state change derives the pending-auth list, reads routing metadata and the in-memory routing setting, builds a bounded deferred-server set, and then runs the existing auto-auth filter before publishing an inline prompt or screen-reader notification. Connector-owned servers are newly excluded from this presentation-side filter when routing is enabled; other servers retain the prior path. The setting lookup and Connector metadata read are synchronous in-memory work.
- Scaling input: The number of auth-required MCP servers S and registered routing server names R. The changed CPU work is O(S\*R + S), because routing membership remains an array includes check and deferred IDs are collected once; MCP server collections are realistically bounded by the session's configured customizations.
- Effective concurrency: The existing auto-auth filter awaits servers serially within one run. State updates can start overlapping filter runs, but non-Connector operations are coalesced by the existing \_pendingMcpAutoAuthentication map per session/server/scope key. The diff does not increase concurrency and skips Connector-owned entries in this turn-presentation invocation when routing is enabled.
- Cache behavior: Routing and Connector ownership come from current session metadata. In-flight non-Connector auto-authentication is coalesced by key; completed attempts are not persistently cached, unchanged by the diff. Connector-owned servers take the new local deferred branch in the presentation path, while the persistent session watcher independently recognizes them from customization metadata and returns locally.
- Mechanism confidence: High: the changed lines, observable dependencies, serial filter, and in-flight coalescing were traced directly. No new expensive boundary or retained lifecycle was introduced.
- Magnitude uncertainty: Exact server counts and OAuth metadata cache hit rates vary, but the changed mechanism is bounded linear collection processing and reduces rather than increases expensive-boundary eligibility for Connector-owned servers.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:\_filterAutoGrantedMcpAuthentication and src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts:autoAuthenticateMcpServer</code>: Existing noninteractive MCP OAuth metadata discovery and credential resolution through autoAuthenticateMcpServer/resolveMcpServerAuthentication; depending on metadata availability this can fetch protected-resource or authorization-server metadata and call the host authentication boundary.; cardinality: At most one serial attempt per effective nondeferred auth-required server in a filter run, with overlapping attempts coalesced by authentication key. Connector-owned servers selected by the new condition are removed before this call in the turn-presentation path.
    - Introduced by diff: false; previous behavior: Before the diff, routing-tool servers were excluded, while Connector-owned servers without a routing tool entered the filter; the existing Connector check could return locally when ownership was already visible. Other server boundary cardinality was the same.; critical-path effect: For nondeferred servers, completion gates whether proactive authentication UI is emitted, as before. For newly deferred Connector-owned servers, this boundary is avoided on this path, so the diff does not add latency.
- Verdict: No reportable performance regression. The added Set and metadata/property checks are bounded to pending servers and replace repeated membership checks in downstream filtering; the only changed boundary eligibility removes work for Connector-owned servers.

### Scenario 2: Connector ownership metadata arrives after a proactive inline hint or screen-reader notification has already been shown.

- Critical path: The customization state update recomputes pending-auth records including connectorName, reruns the auth-prompt autorun, deletes the server from surfaced/owned sets, disposes its notification if present, and filters it out of the presentation-side auto-auth pass. Notification disposal is synchronous UI cleanup; no remote operation must complete before withdrawal.
- Scaling input: The current pending-auth server count S and routing-name count R for one session update. Work remains O(S\*R + S), with one map lookup/disposal per newly deferred pending server.
- Effective concurrency: One autorun execution reacts to each observable value change; stale async filter completions are discarded by runId. Existing in-flight authentication is coalesced by key. The new cleanup does not launch concurrent external work.
- Cache behavior: The surfaced-server Set and notification DisposableMap are session-scoped existing state. The diff removes matching IDs when ownership arrives rather than retaining them. Derived equality now observes connectorName changes, causing exactly the needed reconciliation; no negative cache is added.
- Mechanism confidence: High: the late-update test and production observable path directly establish recomputation and disposal behavior.
- Magnitude uncertainty: The frequency of late ownership discovery is product-dependent, but each occurrence performs bounded local collection work and cleanup only.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. Late metadata triggers bounded local reconciliation and releases notification resources; it does not introduce I/O, IPC, network work, unbounded retention, or a concurrency burst.

### Scenario 3: Settings UI renders the experimental MCP routing setting description, and the modified regression tests exercise routing and screen-reader combinations.

- Critical path: The production change is a static localized description string read by existing configuration UI. Test-only timeout loops run only under the test harness and do not affect product startup or chat execution.
- Scaling input: One configuration schema entry in product; six bounded test cases in the test suite.
- Effective concurrency: No changed production concurrency. Test cases use the existing fake-timer harness sequentially.
- Cache behavior: No changed runtime cache behavior.
- Mechanism confidence: High: the configuration diff changes only static text and the remaining changes are test-only.
- Magnitude uncertainty: None material for product performance.
- Expensive boundaries: none found
- Verdict: No reportable performance regression.

**Summary:** Reviewed all three changed files and every diff hunk. Traced proactive MCP authentication from session-state observables through metadata parsing, routing/deferred filtering, notification lifecycle, auto-authentication, in-flight coalescing, and OAuth/network boundaries. The diff adds bounded in-memory checks, releases late-discovered Connector notification state, and narrows an existing expensive path; no actionable performance regression or qualifying shipped-regression fix was established.
