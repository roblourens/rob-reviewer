# Performance review: Add prioritized Sessions Inbox notifications view

## Findings (2)

### 1. [high] Stop polling every historical pull request each minute

**Finding ID:** `PERF-BD6D6F427804`  
**Location:** <code>src/vs/sessions/contrib/inboxOne/browser/inboxNotificationsService.ts:1741</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub REST/GraphQL requests and API quota  
**Scaling:** After model sharing coalesces duplicate session references, cost still grows with the number of distinct PRs linked from all non-archived sessions: each open PR keeps three 60-second pollers, whose refresh paths issue at least five API requests per cycle (PR metadata, reviews, PR metadata again for review threads, review threads, and CI checks), plus pagination.  
**Outcome:** Continuous excessive network traffic and GitHub API throttling that can degrade all GitHub-backed UI in the window.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, merely enabling the experimental Inbox did not create any all-session GitHub pollers; existing GitHub models were polled only by their existing active consumers.  
**Changed behavior:** The new enabled-service autorun walks every session and \`ensureGitHubModels\` starts PR, review-thread, and CI polling for each linked open PR, regardless of whether the Inbox view is open or the session is recent/actionable.  
**Confidence:** 0.99 — The changed call path, 60-second schedules, model-key coalescing, and underlying network request count are all explicit in repository code and corroborated by the new polling-count test. Exact user PR counts vary, affecting severity magnitude but not the mechanism.

**Causal diff evidence:** Added RIGHT line 1741 calls \`pullRequestModelRef.object.startPolling()\` from the new all-session derivation; added RIGHT lines 1761 and 1781 do the same for review-thread and CI models.

With tens of historical session-linked PRs, an enabled but unopened Inbox can generate hundreds of GitHub requests per minute (for example, 50 distinct open PRs imply at least 250 requests/minute), consuming bandwidth/battery and exhausting rate limits.

**Evidence:** \`ensureGitHubModels\` is called for every session at lines 754-756. This line starts the PR poller, with additional review-thread and CI pollers at lines 1761 and 1781. All three model implementations use a 60,000 ms default interval. Their fetchers show the PR refresh performs two requests, review-thread refresh performs two, and CI refresh performs one. Reference collections share models by PR key, so this count is per distinct PR rather than per duplicate session; the added test at \`inboxNotificationsService.test.ts:891\` explicitly expects three live pollers for one open draft PR.

**Suggested direction:** Do not attach 60-second pollers to every historical PR. Bound the tracked set (for example to active/recent actionable sessions), use a slower/coalesced background refresh for the badge, and only enable the fast PR/review/CI polling while the Inbox is visible; dispose those subscriptions when hidden.

### 2. [medium] Load completed chat histories only when their cards are viewed

**Finding ID:** `PERF-0B6D9EC4FA2A`  
**Location:** <code>src/vs/sessions/contrib/inboxOne/browser/inboxNotificationsService.ts:801</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Persisted-session reads or remote session requests, parsed transcript objects, and retained chat models  
**Scaling:** Cold cost grows with every unique unread completed session (and every chat of each needs-input session); distinct resources are launched concurrently, while only already-loaded duplicate resources are coalesced.  
**Outcome:** A burst of background I/O/network and history replay plus retained-memory/CPU pressure immediately after enablement or restore, competing with interactive startup work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, enabling the Sessions surface did not load every unread completed session's chat model merely to populate a hidden Inbox; histories were loaded by existing consumers when needed.  
**Changed behavior:** As soon as the feature is enabled, the new autorun traverses all non-archived sessions and this line eagerly calls \`ensureChatModelLoaded\` for every unread completed session, even if the Inbox is never opened. The resulting model reference is retained until the session leaves that state.  
**Confidence:** 0.98 — The eager all-session loop, cold/warm guard, local and remote load boundaries, unbounded launch pattern, and retained references are explicit. The number and size of unread histories vary by profile, so magnitude is reflected in medium severity.

**Causal diff evidence:** Added RIGHT line 801 invokes \`ensureChatModelLoaded\` for every unread completed session from the feature-enable autorun; added RIGHT line 2384 launches the underlying asynchronous load.

Profiles with many unread completed cloud or local sessions pay to fetch/read and replay all full histories during restore, although only a viewport-sized subset of cards can be inspected; this can increase startup contention and memory use.

**Evidence:** Lines 789-803 iterate the complete session collection and select all unread completed sessions. \`ensureChatModelLoaded\` at lines 2368-2398 starts \`acquireOrLoadSession\` without a shared limiter and retains each reference. The transitive implementation reads local persisted session data (\`chatServiceImpl.ts:760-780\`) or calls the remote provider's \`getOrCreateChatSession\` and replays its full history (\`chatServiceImpl.ts:951-1005\`). The PR's own enablement test records a chat load immediately when the setting is turned on, without opening the view.

**Suggested direction:** Keep completed notifications derived from session metadata initially, and acquire the completed chat only from \`requestPreview\`/selection when that card becomes visible. If some proactive loading is required, cap it to a small recent set behind a shared limiter and release offscreen/inactive models.

### Scenario 2: Opening and scrolling the Inbox, then selecting a notification

- Critical path: Initial cards render synchronously. One-line preview generation begins only after a card intersects the viewport and is off the first DOM render critical path; selected completed/needs-input detail generation is on the detail-pane content path but has a fallback.
- Scaling input: Active notifications in enabled categories determine DOM cardinality; intersecting cards determine preview requests. A selected item determines one detail summary and one subsequent classification.
- Effective concurrency: Preview, detail, and classification model work shares a Limiter capped at 3. IntersectionObserver gates previews, and signature/in-flight sets coalesce repeats. DOM cards are rebuilt serially for the active collection.
- Cache behavior: Preview signatures have in-flight deduplication and a 200-entry LRU; detail summaries use in-flight deduplication and a 50-entry LRU. Fallbacks are invalidated when language models appear. Offscreen cards do not request previews.
- Mechanism confidence: High for the lazy boundaries and limiter; medium for potential DOM scale because realistic notification counts are not established.
- Magnitude uncertainty: Very large active-notification collections would make the non-virtualized DOM rebuild more expensive, but the diff provides no evidence of a realistic cardinality or measured jank sufficient for another finding.
- Expensive boundaries:

- Verdict: No additional finding: expensive model work is lazy, deduplicated, cached, and concurrency-bounded; full-list DOM rebuilding alone lacks enough impact evidence.

### Scenario 3: Running an Inbox PR action or answering inline input

- Critical path: The clicked action waits for one session acquisition and one send/notification operation; this is the user-requested action's critical path. Inline answers mutate the already-loaded chat model and may update session read state.
- Scaling input: One selected notification per user action; combined CI/review work is intentionally coalesced into one slash-command turn for the session.
- Effective concurrency: User-paced. Each click starts one action; the corresponding button is disabled while agent-merge submission runs. ChatService coalesces an in-progress load for the same resource.
- Cache behavior: Already-loaded chat sessions avoid restore; cold session acquisition uses ChatService's per-resource load coalescing. There is no collection-wide loop on this action path.
- Mechanism confidence: High.
- Magnitude uncertainty: Provider latency varies, but operation count is fixed per user action.
