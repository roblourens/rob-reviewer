## Findings

<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** boundary-fanout, concurrency-burst, eager-work, repeated-work

### Scenario 1: Healthy macOS server and web-server signing in package or product-test jobs

- Critical path: The pipeline's Sign server binaries step invokes sign-server.ts twice in sequence, once per server directory. Each process must finish its recursive scan and every Mach-O codesign call before the next invocation or later packaging/tests can proceed.
- Scaling input: For each of the two server trees, directory-entry count E controls the existing filesystem scan and Mach-O count M controls the existing codesign subprocess count. The diff adds only fixed import-time work on the healthy path.
- Effective concurrency: Within a job, both directory invocations and all per-binary codesign calls are serialized. Separate package/test jobs can run on independent agents, but the diff does not increase healthy-path calls or local parallelism.
- Cache behavior: There is no application-level cache for scans or signatures. Importing sign.ts newly reads and parses product.json once in each sign-server process; Node's module cache cannot span the two processes, while the OS filesystem cache may make the second read warm. Successful signing still performs one codesign call per Mach-O binary.
- Mechanism confidence: High confidence in the critical path and boundary counts from the script and pipeline template; high confidence that healthy codesign cardinality is unchanged.
- Magnitude uncertainty: Exact module-load time is not measured, but the directly evidenced new filesystem work is a fixed two small reads per step and does not scale with server size. There is no evidence that this fixed startup cost is materially user-visible beside the existing multi-second signing work.
- Expensive boundaries:
  - filesystem at <code>build/darwin/sign-server.ts:isMachOBinary and main</code>: Recursively enumerate each server tree, then open/read four bytes from each file to identify Mach-O binaries.; cardinality: Two recursive scans per pipeline step and one small file read per regular file across both trees.
    - Introduced by diff: false; previous behavior: The same recursive scans and per-file reads occurred before the diff.; critical-path effect: The scan must complete as part of each serialized signing invocation.
  - subprocess at <code>build/darwin/sign-server.ts:65</code>: Run codesign --timestamp for each detected Mach-O binary; codesign contacts Apple's timestamp service.; cardinality: On a healthy run, exactly one subprocess per Mach-O binary, M across each tree; retries do not execute.
    - Introduced by diff: false; previous behavior: Before the diff, each detected Mach-O binary already incurred exactly one awaited codesign subprocess.; critical-path effect: Each subprocess is awaited serially and blocks progress through the signing step.
  - filesystem at <code>build/darwin/sign.ts:13, reached by build/darwin/sign-server.ts:9</code>: Synchronously read and parse product.json while evaluating the newly imported sign.ts module.; cardinality: One small synchronous read per sign-server process, therefore two reads per Sign server binaries step.
    - Introduced by diff: true; previous behavior: sign-server.ts did not import sign.ts and therefore did not perform this product.json read or load &#64;electron/osx-sign.; critical-path effect: Adds fixed process-startup work before argument validation and scanning.
- Verdict: No reportable regression. The normal path preserves the existing per-binary subprocess count and serialization. The eager import adds fixed startup/module-loading work, but repository evidence establishes only two small synchronous reads and does not establish a concrete material performance impact.

### Scenario 2: Server signing when codesign returns a recognized transient timestamp or keychain error

- Critical path: For the current Mach-O binary, the changed wrapper waits 10/20/40/80 seconds and retries before the scan can continue. A recovered call lets signing proceed; an exhausted or unrecognized error rejects, and set -e prevents the second directory invocation and later pipeline work.
- Scaling input: Additional work is controlled by the number F of recognized transient failures: one extra codesign subprocess per failure, capped at four retries for a given current binary. Persistent failure stops the serialized loop at that binary rather than multiplying retries over all remaining binaries; intermittent failures can recur on later binaries.
- Effective concurrency: Retries for one binary and binaries within one job are fully serialized. Multiple package/test jobs have independent retry loops and no shared limiter or jitter, but they reach this server step only after the pre-existing app-sign step, which uses the same timestamp service and retry policy; repository evidence does not establish synchronized server-stage retry bursts.
- Cache behavior: There is no cache or cross-binary coalescing; retry state is local to a single codesign call. Successful prior signatures are retained because --force allows replacement, and a service recovery affects later calls naturally rather than through a cache.
- Mechanism confidence: High confidence in the retry count, serialization, backoff, and pipeline failure behavior. Confidence is lower that independent jobs synchronize enough to create harmful aggregate load because their phases and failure times are not established.
- Magnitude uncertainty: The duration and prevalence of Apple/keychain failures and the degree of overlap among independent jobs are external and variable. Exact codesign internal timeout is unknown, while the added call cap and 150-second explicit delay are certain.
- Expensive boundaries:
  - subprocess at <code>build/darwin/sign-server.ts:65-74 via build/darwin/sign.ts:64-79</code>: Re-run codesign --timestamp after a recognized transient failure, crossing both the process boundary and Apple's timestamp network boundary.; cardinality: One initial call plus at most four additional calls for the affected current binary. With intermittent recoveries on multiple binaries, total calls are M + F; with a persistent recognized error, the script stops after five calls on the first affected binary.
    - Introduced by diff: true; previous behavior: The first codesign failure immediately rejected the script, so there were no retry subprocesses or explicit backoff and the build could not make further progress.; critical-path effect: Each retry and its preceding backoff is on the signing step's critical path; total explicit backoff before exhaustion is 150 seconds, in addition to subprocess duration.
- Verdict: No reportable performance regression. The added work is bounded, executes only after a failure that previously terminated the scenario, and directly enables successful progress. A persistent error delays final failure by 150 seconds, but the code intentionally caps that tradeoff and no repository evidence shows an unacceptable latency or concurrency burst warranting a performance finding.

**Summary:** Reviewed the complete one-file diff and traced healthy, transient-recovery, and exhausted-retry paths through filesystem, subprocess, and timestamp-service boundaries. Normal-path subprocess cardinality is unchanged; the only eager cost is fixed import-time module loading and two small product.json reads per pipeline step. Failure-path retries are sequential, capped, and intentional, with no proven harmful fan-out or burst. No high-confidence actionable performance regression was found.
