# Performance review: agentHost: count jobs behind required checks and surface SSO blocks

## Findings (2)

### 1. [medium] Use one polling loop for each pull request's checks

**Finding ID:** `PERF-621E40487D84`  
**Location:** <code>src/vs/sessions/contrib/github/browser/models/githubPullRequestCIModel.ts:187</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** GitHub REST and GraphQL requests  
**Scaling:** For every distinct open pull request retained by the sessions UI, the existing 60-second REST check-runs poll continues while the new shared resource independently polls required checks every 60 seconds while pending (and every 5 minutes otherwise); cost therefore grows linearly with open PR sessions.  
**Outcome:** Increased network traffic, GitHub quota consumption, queued-request latency, and slower CI-status updates under many sessions.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** GitHubPullRequestCIModel refreshed check runs through one coalesced model request and one 60-second RunOnceScheduler loop.  
**Changed behavior:** Each refresh now creates a PullRequestChecksSource subscription. PullRequestResourceService automatically polls that subscription in addition to the unchanged GitHubPullRequestCIModel poller, while the model still calls GitHubPRCIFetcher.getCheckRuns on every legacy cycle.  
**Confidence:** 0.98 — The two independent schedulers, their 60-second pending intervals, the unchanged REST fetch, the new GraphQL call path, and the all-open-PR consumer are directly traced. Exact latency depends on session count and GitHub response time, but request multiplication is deterministic.

**Causal diff evidence:** The added call at line 187 starts \_subscribeRequiredChecks from refresh without removing the existing \_poll/\_refresh path; the new source subscribes with required checks, and line 266 also explicitly refreshes it.

Opening or retaining many sessions with open PRs causes every pending PR to issue roughly the legacy REST poll plus two new GraphQL reads per minute, before cold metadata reads. This can consume GitHub quotas and delay visible CI state as requests queue.

**Evidence:** GitHubPullRequestCIModel.\_refresh still calls GitHubPRCIFetcher.getCheckRuns (one REST check-runs traversal). The added PullRequestChecksSource uses PullRequestResourceService, whose background pending-check policy is 60 seconds and whose required-check fetch performs a GraphQL rollup plus a separate expected-suite GraphQL request, with cold branch/ruleset and workflow reads. github.contribution starts the legacy CI poller for every open non-draft session PR, so the two loops are simultaneously reachable and the request queue only bounds concurrency, not total requests.

**Suggested direction:** Make the CI model use a single authoritative polling source: either populate its check list/status from PullRequestChecks and remove the legacy getCheckRuns poller, or make the shared subscription passive and refresh it from the existing loop. Keep annotation/output reads on demand.

### 2. [medium] Back off failed required-context reads

**Finding ID:** `PERF-23D869EABFD5`  
**Location:** <code>src/vs/platform/github/common/pullRequestQueryService.ts:483</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** GitHub REST requests for branch protection and rulesets  
**Scaling:** After an initial metadata failure, every checks poll for every distinct active PR retries the same base-branch request; pending or missing required checks poll every 15 seconds when visible or 60 seconds in background, and timers for separate PR resources are not request-count coalesced once their calls no longer overlap.  
**Outcome:** Repeated network I/O, GitHub rate-limit consumption, and request-queue pressure while authorization, SSO, enterprise compatibility, or network failures persist.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Checks polling did not read branch protection or branch rulesets, so these failure retries did not exist.  
**Changed behavior:** Required-check refreshes now call \_fetchRequiredContexts. Only successful reads populate the five-minute cache; a GitHubRequestError is swallowed by returning cached?.contexts, leaving an initial failure uncached and making the outer resource treat the refresh as successful rather than applying failure backoff.  
**Confidence:** 0.97 — The cache-write, swallowed-error, and polling paths are explicit. Transport concurrency limits cap simultaneous requests, but neither they nor ETags suppress later retries; prevalence of partial authorization failures affects severity, not the mechanism.

**Causal diff evidence:** The added return at line 483 exits the failure path without recording a cache state or propagating the error; the added call at line 425 invokes this path on every required-check fetch.

A credential that can read PR checks but is blocked from branch/rules metadata—such as an organization SSO or authorization restriction—causes the same failed metadata call to repeat for the lifetime of each active PR, increasing quota pressure and delaying other GitHub work.

**Evidence:** \_fetchRequiredContexts checks \_requiredContexts, performs GET branches/&lt;base&gt; and then GET rules/branches/&lt;base&gt;, and writes the cache only after both succeed. Its catch returns undefined when there was no prior success. PullRequestResourceService therefore commits the checks result and schedules its normal pending cadence rather than \_scheduleAfterFailure; missing required checks specifically remain on the fast cadence.

**Suggested direction:** Store a bounded negative/backoff state per host/repository/base branch (and coalesce an in-flight read), or propagate transient failures so PullRequestResourceService applies its existing exponential backoff. Invalidate terminal authorization negatives when credentials change and retain the last successful contexts while retrying at a bounded interval.
