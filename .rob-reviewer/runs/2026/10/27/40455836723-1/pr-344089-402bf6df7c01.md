# Performance review: sessions: keep cloud creation context for New Session

[PR #344089](https://github.com/microsoft/vscode/pull/344089) at `402bf6df7c0195e141cdb5d152326bf164d94f63`

## Findings (1)

### 1. [medium] Avoid hydrating the source chat when deriving the creation target

**Finding ID:** `PERF-B037F5763893`  
**Location:** <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/cloudSandboxSessionsProvider.ts:44</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** agent-host session/chat subscriptions, including a full default-chat snapshot and its deserialized objects  
**Scaling:** The added work is one remote Session subscription plus a ref-counted Chat subscription per previously inactive source session selected by a New Session gesture; the transferred and retained chat snapshot grows with that source conversation's transcript size and remains subscribed for the 30-second idle window.  
**Outcome:** unnecessary remote traffic, transcript deserialization/GC pressure, and contention that can delay the newly opened composer or the chat the user is actually viewing  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Section/environment New Session actions used the already-present ISession workspace and provider fields and did not resolve the source through BaseAgentHostSessionsProvider.getSessionByResource, so choosing an inactive cloud row did not restore or hydrate that source session.  
**Changed behavior:** CloudSandboxSessionsProvider.getNewSessionTarget now calls getSessionByResource merely to read cached workspace metadata. That base lookup is an opening/query path: it calls \_keepSessionStateAlive with hydrateDraft=true, acquiring a Session subscription and then draft agent/model hydration subscriptions for the default Chat.  
**Confidence:** 0.97 — The changed call path and subscription behavior are explicit in repository code, and grouped-list actions demonstrably choose inactive sessions. Exact transcript sizes and remote latency vary, which affects severity but not the mechanism.

**Causal diff evidence:** RIGHT line 44 newly routes creation-target lookup through getSessionByResource; before this PR no creation-target lookup existed and openNewSessionLike directly reused session.workspace/providerId.

Clicking New Session on a repository/workspace/environment group whose chosen cloud sandbox session is not currently visible can restore and download that old session's default chat. Large historical chats therefore consume remote bandwidth and frontend allocation while the user is moving to a fresh session.

**Evidence:** The added line calls getSessionByResource. BaseAgentHostSessionsProvider.getSessionByResource invokes \_keepSessionStateAlive(cached.sessionId); \_ensureSessionStateSubscription then opens StateComponents.Session and, because hydrateDraft defaults true, \_ensureDraftHydration opens StateComponents.Chat for draft agent/model. The base provider explicitly documents that a chat snapshot carries the whole transcript and that passive observers must pass false because fetching unopened chats delays the chat being viewed. sessionsViewActions now reaches this path after selecting a source from grouped list sessions, which need not be a visible/pinned session.

**Suggested direction:** Resolve the target from a side-effect-free cached-session lookup, or add/use a non-hydrating getSessionByResource mode (equivalent to the existing passive-observer hydrateDraft=false behavior) so reading repository metadata never opens Session/Chat subscriptions.

### Scenario 2: New Session from a workspace/repository/environment section using an inactive cloud sandbox as the source

- Critical path: After opening the fresh draft, openNewSessionLike derives the source target and applies it to the new view. The derivation synchronously calls the cloud backend; remote subscriptions it starts are asynchronous but contend with the newly opened session and remain alive for 30 seconds.
- Scaling input: Exactly one selected source per command after section grouping/deduplication. Payload cost scales with the selected source's default-chat transcript size, not with every row in the section.
- Effective concurrency: One source lookup per command. Session and Chat subscriptions are reference-counted, but an inactive list-only source has no visible-session pin and can therefore create a new remote subscription alongside new-session work.
- Cache behavior: The session summary/workspace is already present to render the section, but getSessionByResource upgrades that cached adapter into live Session state and hydrateDraft=true Chat state. The subscription and hydrated objects remain until the 30-second idle timer expires; repeated gestures reset the timer.
- Mechanism confidence: Very high: base-provider comments explicitly state passive reads must avoid hydrateDraft because Chat snapshots carry the whole transcript, and grouped-list sources need not be visible.
- Magnitude uncertainty: The cost is small for short/warm chats but can be substantial for long remote histories or a sleeping/slow host.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/cloudSandboxSessionsProvider.ts:44 via BaseAgentHostSessionsProvider.getSessionByResource</code>: Subscribe to agent-host Session state and the default Chat snapshot for draft agent/model hydration; cardinality: One Session channel plus one effective ref-counted Chat channel for the chosen inactive source; transcript bytes scale with that single conversation
    - Introduced by diff: true; previous behavior: The section action directly reused the ISession workspace/provider data and did not open source-session state.; critical-path effect: Not awaited by target derivation, but downloads/deserializes an unrelated historical chat while the new composer/session is progressing, causing transport, CPU, GC, and retained-memory contention.
  - network at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_ensureSessionCache</code>: Cold listSessions refresh if the backend adapter cache has not initialized; cardinality: At most one coalesced refresh per provider because in-flight/retry guards suppress duplicates
    - Introduced by diff: true; previous behavior: The section action did not call getSessionByResource, though normal session-list loading commonly initialized this cache earlier.; critical-path effect: Fire-and-forget and generally already completed when a section can display the source; not the primary regression.
- Verdict: Reportable eager remote work: deriving repository metadata from an inactive source unnecessarily restores/hydrates its chat.

- Cache behavior: Provider/session metadata is cached, but the cloud lookup can still create/reset the 30-second live state subscription. There is no negative cache for an unavailable creation target; invocation frequency is bounded by explicit gestures.
- Mechanism confidence: High for the extra source subscription and two synchronous availability scans.
- Magnitude uncertainty: Provider count is small and resolveWorkspace/getSessionTypes are synchronous for the relevant GitHub/agent-host URI schemes, so the second scan is unlikely to be user-visible.
- Expensive boundaries:

    - Introduced by diff: true; previous behavior: Only the fallback workspace/provider availability scan ran; no source hydration occurred.; critical-path effect: Background contention rather than an awaited target check; covered by the submitted finding.
- Verdict: The hydration is covered by the finding; the additional bounded provider scan is not independently reportable.
