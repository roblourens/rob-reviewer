# Performance review: quickinput: Distinguish appearance selection from focus

[PR #344673](https://github.com/microsoft/vscode/pull/344673) at `4b26f2a236b40574fa07ecbed1210acb57656495`

## Findings (1)

### 1. [medium] Avoid indexing the entire Quick Pick on first render

**Finding ID:** `PERF-556FA6AE8270`  
**Location:** <code>src/vs/platform/quickinput/browser/quickInputList.ts:316</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** CPU work plus one Map entry and position object for every sibling item  
**Scaling:** After each items assignment, the cache is cleared; rendering the first row then performs two full sibling filters and populates the map for all n siblings, so cold open/update cost and allocation grow O(n) even though the list virtualizes DOM rows.  
**Outcome:** increased picker-open/update latency and CPU/GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, AbstractTree computed aria-setsize from parentNode.visibleChildrenCount and aria-posinset from node.visibleChildIndex, both O(1) for each rendered row, and Quick Input retained no parallel position map.  
**Changed behavior:** The new QuickInputAccessibilityProvider handles those attributes itself; on the first rendered element in each sibling group it copies/filters the full sibling collection twice and inserts every sibling into positions. The companion AbstractTree change now delegates to these methods.  
**Confidence:** 0.97 — The synchronous call chain, cache reset, full-sibling iteration, and prior O(1) behavior are explicit in the repository. Exact milliseconds vary with provider size, but the added O(n) CPU/allocation on a virtualized picker’s render-critical path is deterministic.

**Causal diff evidence:** Added lines 316-324 introduce the full sibling scans and per-sibling Map population, while the added AbstractTree delegation at lines 184-196 makes this provider execute instead of the previous constant-time tree metadata path.

Opening or refreshing a large flat Quick Pick—such as an extension-provided picker or the command palette’s full command set—now synchronously walks and allocates for every item before the first virtualized rows finish rendering. Reassigning items repeats the cost, which can visibly delay large picker updates and add GC pressure.

**Evidence:** QuickPick.items synchronously calls QuickInputList.setElements during update; \_setElementsToTree clears positions, and ListView.updateItemInDOM immediately requests getSetSize/getPosInSet for rendered rows. This added cold path calls getSiblings(element).filter(...), filters that result again, then creates a Map value for every sibling. Built-in command quick access groups all registered editor/global commands, while the shared Quick Pick API permits uncapped extension item arrays; the work is therefore collection-sized rather than viewport-sized.

**Suggested direction:** Keep the existing O(1) tree size/index path when a parent has no decorative divider. For parents that do, compute divider-adjusted counts/offsets during the existing tree-build pass (or cache compact per-parent divider metadata) rather than materializing a position object for every item during row rendering.
