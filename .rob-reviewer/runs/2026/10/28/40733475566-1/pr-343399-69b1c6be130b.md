# Performance review: automations: preserve run history and filter editor sessions

## Findings (2)

### 1. [high] Index legacy origins instead of scanning every run per session

**Finding ID:** `PERF-E8F2EC05741F`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:5251</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** synchronous CPU work comparing every persisted Automation run and its session arrays for every listed session  
**Scaling:** Each listSessions call now does O(S × R × K) matching work for S registered sessions, R retained Automation runs, and average K sessions per run; ordinary sessions never receive an origin and therefore repeat the full miss scan on every refresh.  
**Outcome:** increased startup and Sessions-list refresh latency, with event-loop CPU pressure on profiles containing substantial session and Automation histories  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Catalog-served rows and provider fallbacks were returned after their bulk/session metadata reads; listing did not traverse the Automation run history for each row.  
**Changed behavior:** Both catalog-served and fallback rows now call \_withAutomationSessionOrigin, which calls getLegacySessionOrigin whenever origin is absent; that helper linearly traverses the unbounded \_runs map and checks run.sessions.includes.  
**Confidence:** 0.99 — The changed critical path, nested cardinality, unbounded retained run map, and eager callers are directly visible. Exact milliseconds depend on profile history size, which affects severity rather than mechanism confidence.

**Causal diff evidence:** The added return wrapper at agentService.ts:5251 moves legacy-origin lookup onto every catalog-served session in listSessions; before this diff the same row returned directly without any Automation-run traversal.

Opening VS Code or refreshing Agent Host sessions eagerly calls listSessions. A profile with hundreds or thousands of ordinary sessions and retained Automation runs performs the complete run-history scan once per session before the list response can complete; the four-way async limiter does not parallelize this synchronous scan.

**Evidence:** AgentService.listSessions maps every catalog result through the added call at line 5251 (and the analogous fallback call), while \_withAutomationSessionOrigin invokes AgentHostAutomationService.getLegacySessionOrigin for every origin-less row. getLegacySessionOrigin loops all \_runs and performs run.sessions.includes; \_runs retains all terminal history rather than the 50-item presentation window (withRunWindow only slices summaries). BaseAgentHostSessionsProvider eagerly awaits listSessions to initialize its cache, and AgentHostSessionListStore uses the same call for refreshes.

**Suggested direction:** Build and maintain a session/provider-to-origin index once from \_runs and \_sessionCreations (updating it on run mutations), or bulk-resolve all missing origins once per listing. Preserve the existing positive backfill write, but make ordinary-session misses O(1) so later refreshes do not rescan history.

### 2. [medium] Checkpoint history deletion in bounded batches

**Finding ID:** `PERF-E40853D1979A`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostAutomationService.ts:552</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** backend session-deletion calls plus whole Agent Host storage JSON serialization, temporary-file writes, renames, and removals  
**Scaling:** For N retained session identities, deletion is strictly serial and performs N backend deletes and at least N full storage-file flushes; legacy entries without a recorded provider add another full flush each. Because every checkpoint serializes all remaining Automation runs and a growing deletedSessions array, bytes serialized/written grow approximately quadratically with N.  
**Outcome:** excessive filesystem I/O and long blocking latency for Delete Run History, with lower deletion throughput as history grows  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Removing an Automation performed one catalog/storage mutation and did not place per-history-session backend deletion plus durable full-file rewrites on this request path.  
**Changed behavior:** The new \_deleteHistory loop awaits deleteSession for one entry and then awaits \_recordDeletedHistorySession before proceeding; that method calls \_persist, whose setAndFlush rewrites the complete Agent Host storage JSON to a temporary file and renames it.  
**Confidence:** 0.97 — The serial call path, full-file flush implementation, and 102-session exercised scenario are explicit. Storage size and provider deletion duration vary by profile, so magnitude is uncertain but the I/O amplification is not.

**Causal diff evidence:** The added await at agentHostAutomationService.ts:552 forces a full durable checkpoint after every newly introduced per-session deletion before the loop can advance.

Deleting retained history with many runs waits for every backend operation and durable rewrite in sequence. The added test explicitly exercises 51 runs with two sessions each (102 identities), which entails over one hundred whole-file writes before the command returns, and histories are retained beyond the 50-row published page.

**Evidence:** agentHostAutomationService.ts:541-552 serializes the per-entry boundary calls. \_recordDeletedHistorySession calls \_persist after every success; \_persist materializes all runs/maps and AgentHostStorageService writes JSON.stringify(this.\_data) to a temp file, renames it, and removes the temp file. The new 'deletes all retained members beyond the history page' test establishes a realistic effective cardinality of 102 session deletions.

**Suggested direction:** Keep crash recovery, ordering, and exact receipts, but process a bounded batch of session deletions and persist one compact checkpoint per batch (or move deletion progress to an incremental journal) rather than rewriting the entire Automation store after every member. Use bounded concurrency only if provider disposal semantics permit it.
