<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** cleanup-lifecycle, serialization-allocation, boundary-fanout

### Scenario 1: Browser and Remote PR jobs prepare the server runtime before integration or smoke tests

- Critical path: The added workflow step must finish before the test command. It synchronously resolves the expected server Node path and, on a cold matching-version job, copies the runner binary; this replaces the later server-start path's Node.js download and extraction. On version mismatch or helper failure, the later download remains on the test-start critical path as before.
- Scaling input: One server Node runtime per selected CI job. The three shared workflow step lists select a fixed set of Browser/Remote jobs; there is no per-test or per-file multiplication within a job.
- Effective concurrency: Within each job, path resolution, filesystem checks, and copying are synchronous and serial. Jobs run independently according to GitHub Actions scheduling; the change adds no in-job burst or shared unbounded concurrency.
- Cache behavior: If the exact \`.build/node/v&lt;version&gt;/&lt;platform&gt;-&lt;arch&gt;/node\[.exe\]\` path already exists, the helper performs no copy and the later gulp node task also skips download. On the normal clean-job miss with a matching setup-node version, one local copy populates that path. Version mismatch and copy failure deliberately leave a miss, so the unchanged later download occurs; there is no negative cache.
- Mechanism confidence: High: workflow conditions, setup-node placement, helper synchronization, and gulp's directory-existence gate directly establish the before/after path.
- Magnitude uncertainty: Exact local binary-copy duration and runner cache warmth vary by platform, but the fixed one-copy cost is clearly bounded and replaces a network download/extraction on the common cold path.
- Expensive boundaries:
  - subprocess at <code>build/azure-pipelines/common/useRunnerNodeForServer.ts:main</code>: Run the current Node executable once to evaluate \`build/lib/node.ts\` and print the expected server Node path.; cardinality: Exactly one short subprocess per selected Browser/Remote CI job.
    - Introduced by diff: true; previous behavior: No preparatory subprocess ran; the server startup later resolved/downloaded Node through the gulp task.; critical-path effect: The subprocess is newly on the pre-test critical path but performs only local module startup and one small file read; it is fixed-cardinality.
  - filesystem at <code>build/azure-pipelines/common/useRunnerNodeForServer.ts:useRunnerNodeForServer/main</code>: Read \`remote/.npmrc\`, test the destination, create its directory, and copy the runner's Node executable when versions match.; cardinality: One metadata/read sequence per selected job and at most one binary copy on a cold matching-version job.
    - Introduced by diff: true; previous behavior: A cold \`.build/node\` path remained absent until the server-start gulp task downloaded and wrote/extracted Node.; critical-path effect: The synchronous copy delays the test command by local copy time, but substitutes for a larger network download plus archive extraction or binary write on the same scenario.
  - network at <code>build/gulpfile.reh.ts:nodejs</code>: Download the pinned Node runtime from nodejs.org through \`fetchUrls\` when \`.build/node\` is absent.; cardinality: Previously one logical download per cold job, with sequential retries on failure. After the diff it is zero when setup-node has the pinned version, and unchanged on version mismatch or helper failure.
    - Introduced by diff: false; previous behavior: Every cold Browser/Remote job reached this network download when starting the server.; critical-path effect: This boundary blocks server startup. The diff removes it from the common matching-version path rather than introducing or moving it earlier.
- Verdict: No reportable regression. The fixed local preparation work removes a slower and failure-prone network boundary for matching versions, while warm and mismatch paths remain bounded.

### Scenario 2: Build tooling downloads Node runtimes, marketplace extensions, and GitHub release assets through \`fetchUrl\`

- Critical path: Each caller awaits the complete response buffer before checksum verification and downstream extraction/processing, so network body progress and full-body buffering remain on build or dependency-setup critical paths. The new idle timer is also on that path only as a cancellation guard.
- Scaling input: Cost scales linearly with downloaded bytes and with the number of caller-requested assets. Each logical asset uses one request when successful; an idle/erroring asset can make up to 11 attempts through the existing sequential retry recursion.
- Effective concurrency: A single \`fetchUrl\` reads one response at a time and retries serially after a one-second delay. \`fetchUrls\` may map caller-provided URL arrays, but reviewed production calls here pass one URL per logical asset; no new aggregate concurrency or fan-out is introduced.
- Cache behavior: \`fetchUrl\` has no internal cache. Node's \`.build/node\` directory and workflow caches can avoid calls before reaching it; extension/build callers control their own cache or invocation. Successful and failed fetches are not memoized or coalesced by this change.
- Mechanism confidence: High for the network critical path, retry limit, serial scheduling, and linear full-body buffering; insufficient evidence that explicit chunk accumulation materially regresses memory versus the prior native full-body conversion.
- Magnitude uncertainty: Asset sizes and network stall prevalence vary, and repository evidence does not establish a materially higher peak allocation than native \`arrayBuffer()\` for normal downloads. The stalled-read latency mechanism itself is deterministic.
- Expensive boundaries:
  - network at <code>build/lib/fetch.ts:fetchUrl/readBody</code>: Fetch one HTTP response and retry it after errors or body inactivity.; cardinality: One request for a successful logical download; up to 11 sequential requests under the pre-existing retry limit. The diff changes the inactivity detection point from the five-minute whole-download limit to 30 seconds without data, not successful-request cardinality.
    - Introduced by diff: false; previous behavior: The same HTTP request and retry path existed, but a response that returned headers and then stopped sending bytes occupied the critical path until the five-minute whole-download timeout.; critical-path effect: The complete body is required before checksum and downstream processing. On a stalled body, the change shortens the time before retry; on a progressing body, the idle timer refreshes and does not add another boundary.
  - serialization at <code>build/lib/fetch.ts:readBody/fetchUrl</code>: Accumulate response bytes into memory, concatenate them into a Buffer, and optionally hash the complete Buffer.; cardinality: Once per successful asset; retained bytes are O(asset size), followed by one checksum pass when configured.
    - Introduced by diff: true; previous behavior: Native \`response.arrayBuffer()\` materialized the full body and \`Buffer.from\` wrapped it before the same optional checksum and downstream processing.; critical-path effect: Full buffering and checksum remain prerequisites for returning the Vinyl file. The explicit chunk reader enables idle detection; the prior \`response.arrayBuffer()\` also required a complete in-memory body, so the diff does not establish a new asymptotic buffering cost.
- Verdict: No diff-introduced performance issue. Progressing downloads retain the prior one-request, O(bytes) behavior, while stalled bodies release the network critical path earlier. This also constitutes a concrete performance fix, though the internal regression-fix recorder rejected both submission attempts.

**Summary:** Reviewed all seven changed files and complete diff pages. Traced the CI runtime-reuse path and every production \`fetchUrl\` caller, including subprocess, filesystem, network, buffering, retry, cache, and concurrency behavior. No actionable performance regression was introduced; the PR removes a cold-job Node download and adds progress-sensitive cancellation for stalled bodies. No findings were submitted.
