### Scenario 1: Selecting a different action from a toggle-primary split-button, including an extension-provided editor-title Run action

- Critical path: The dropdown ActionRunner fires onWillRun synchronously; the changed listener performs one eligibility check, one cached storage read and at most one store scheduling, disposes/renders one primary action view, then ActionRunner invokes MenuItemAction.run and CommandService.executeCommand. The command/activation remains the dominant awaited work; database persistence is delayed and not awaited.
- Scaling input: One selected MenuItemAction per user invocation. Cost does not scale with submenu size except the unchanged single primary-action instance/keybinding setup; rapid selections produce one update per selection, with unchanged total update cardinality versus the previous onDidRun listener.
- Effective concurrency: Each view item owns one ActionRunner. A user can initiate overlapping commands, but every invocation performs one bounded update; storage writes are coalesced by the existing 100 ms ThrottledDelayer rather than issued concurrently.
- Cache behavior: The current primary ID is read from the in-memory storage cache and identical IDs skip the store. Distinct selections update the cache immediately; persistence is coalesced. Cold command activation may await extension activation, while warm registered commands execute directly, unchanged by the diff.
- Mechanism confidence: High: ActionRunner ordering, update implementation, cached storage behavior, delayed flush, and command dispatch were traced directly. The diff only moves the existing one-per-selection update before the awaited command.
- Magnitude uncertainty: The exact synchronous cost of storage-change listeners and creating one action view varies by host and extensions, but there is no collection-scaled work, synchronous database I/O, or increased operation count.
- Expensive boundaries:
  - database/filesystem at <code>src/vs/platform/actions/browser/menuEntryActionViewItem.ts:514 update; src/vs/base/parts/storage/common/storage.ts:264 Storage.set</code>: Persist the workspace-scoped last-action ID through Storage.set/doFlush.; cardinality: At most one scheduled write for a changed action ID per selection; repeated selection of the stored ID performs none, and writes within the delay are coalesced.
    - Introduced by diff: true; previous behavior: The same conditional write and persistence scheduling occurred once from onDidRun after the command promise settled.; critical-path effect: The synchronous cache/event update now occurs before command dispatch, but the actual database update is delayed by 100 ms and is not awaited, so it remains off the command critical path.
  - IPC/other at <code>src/vs/platform/actions/common/actions.ts:672 MenuItemAction.run; src/vs/workbench/services/commands/common/commandService.ts:49 CommandService.executeCommand</code>: Dispatch the selected command, potentially activating an extension and invoking extension-host or command-specific subprocess/network work.; cardinality: Exactly one command dispatch per selected action, with activation dependent on cold/warm registration state.

- Verdict: No reportable regression. The change adds a small constant amount of local UI/cache work before command dispatch, but does not introduce synchronous expensive boundaries, fan-out, retention, or additional repeated work.

### Scenario 2: A long-running selected command changes context and rebuilds the editor-title toolbar before it completes

- Critical path: After the pre-run update, the existing command runs. A context/menu change can call updateEditorActionsToolbar, which recreates menu actions and calls toolbar.setActions. The new listener ensures the old view's selection has already reached the storage cache before disposal; rebuild work and command boundaries are otherwise unchanged.
- Scaling input: One editor action toolbar and one selected split-button for the triggering context change; rebuild cost scales with the existing editor-title action list, not with any collection introduced by this diff.
- Effective concurrency: The toolbar rebuild executes on the UI event path while the command promise is pending. The PR neither starts another rebuild nor adds command concurrency; it changes only when the selected item updates.
- Cache behavior: The recreated item reads the already-updated action ID from the storage cache. Warm reads require no boundary; persistent storage initialization and the menu/action caches are unchanged.
- Mechanism confidence: High: the editor toolbar rebuild path, view disposal behavior, cached storage read, and deferred persistence were inspected directly.
- Magnitude uncertainty: The action count and command duration vary, but the added pre-run work remains one view replacement and one cache update regardless of duration or rebuild count.
- Expensive boundaries:
  - database/filesystem at <code>src/vs/platform/actions/browser/menuEntryActionViewItem.ts:514 update; src/vs/base/parts/storage/common/storage.ts:397 Storage.doFlush</code>: Eventually persist the selected action ID while the toolbar may be recreated.; cardinality: One conditional, coalesced write for the selection, independent of the number of toolbar rebuilds.
    - Introduced by diff: true; previous behavior: The write was scheduled only after command completion and could be skipped entirely if disposal removed the onDidRun listener.; critical-path effect: The cache is updated before rebuild; the delayed database flush is off both the command and toolbar-rebuild critical paths.
  - IPC/other at <code>src/vs/workbench/services/commands/common/commandService.ts:49 CommandService.executeCommand</code>: Execute the long-running command whose context changes can trigger the toolbar rebuild.; cardinality: One command invocation; downstream boundary count is command-specific and unchanged.
    - Introduced by diff: false; previous behavior: The same command and downstream work ran once, before the old post-run update.; critical-path effect: Its promise remains pending across the rebuild and determines command completion latency; no new downstream operation is introduced.
- Verdict: No reportable performance regression. The toolbar rebuild and long-running command already existed, while the moved update is bounded and avoids neither batching nor cleanup.

### Scenario 3: Recreating a split-button after a prior selection, including window reload or toolbar replacement

- Critical path: The constructor performs the unchanged workspace-storage cache read, finds at most one matching action, creates one default action view, and renders it. The diff changes which selections are available in cache before disposal but adds no constructor or reload work.
- Scaling input: One cache read and a linear find over that split-button's existing action list per recreated item; the find and item creation are unchanged by the PR.
- Effective concurrency: Toolbar creation is synchronous UI construction with no new parallelism. Persistence may flush independently through the existing storage delayer.
- Cache behavior: Warm recreation reads the in-memory cached ID. On process reload, storage initialization populates the cache as before. Unknown or absent IDs fall back to the first eligible action; negative behavior is unchanged.
- Mechanism confidence: High: constructor and storage cache paths are unchanged; only event timing changed.
- Magnitude uncertainty: Actual submenu sizes vary, but no changed loop or additional item creation exists in this path.

- Verdict: No reportable regression. The PR does not alter startup/recreation cardinality, cache lifecycle, or boundary behavior.
