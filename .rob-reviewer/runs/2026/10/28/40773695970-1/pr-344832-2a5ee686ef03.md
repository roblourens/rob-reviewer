- Critical path: The telemetry pipeline creates a fresh extraction directory, performs its prerequisite repository setup, then synchronously runs the extractor processes; CI cannot progress until those subprocesses finish. - Scaling input: Repository/source-program size and number of classified telemetry events. This hunk changes resolution of one property in two fixed-size type aliases, so its work does not scale with automation runs or user data.
- Effective concurrency: The prerequisite clone loop and both extractor invocations use synchronous child-process calls and therefore run serially. The diff does not change this scheduling or add parallel work.
- Cache behavior: Extraction uses a fresh staging directory and performs cold source analysis each pipeline run; no new cache key, miss path, negative cache, or cache invalidation behavior is introduced by the type alias change.
- Mechanism confidence: High: the changed syntax is a TypeScript-only alias, and the extraction script's subprocess and filesystem topology is unchanged.
- Magnitude uncertainty: Exact extractor type-resolution cost is not measured, but Omit applies to a fixed classification with a handful of properties and supplies no realistic scaling mechanism.

### Scenario 2: Create an automation run and emit automation.runCreated / automation.runStarted telemetry

- Critical path: A run claim or first session linkage persists durable state before logging telemetry. Runtime logging synchronously hashes the automation ID, sanitizes/mixes the small event object, and submits it to appenders; the collector's HTTP send is fire-and-forget and is off the run's awaited critical path. The modified classification aliases are erased and do not affect any of this runtime work.
- Scaling input: Number of newly persisted run claims and first non-terminal session linkages. Scheduled claims are coalesced to at most one run per automation per tick; effective telemetry cardinality remains one runCreated per claimed run and one runStarted per first eligible session linkage.
- Effective concurrency: Scheduled claims share one persistence operation and then emit telemetry synchronously once per claimed run; manual claims persist independently. Collector HTTP submission is asynchronous. The diff changes neither batching nor concurrency.
- Cache behavior: Telemetry can use the existing bounded pending-event buffer until experiment properties are available; warm versus cold telemetry state and all buffering behavior are unchanged. No cache is added or bypassed by this type-only edit.
- Mechanism confidence: High: publicLog2 delegates using the same runtime event data, and both modified classification aliases exist only in generic type positions that TypeScript erases.
- Magnitude uncertainty: Appender-internal batching size is not established here, but it cannot affect PR causality because event frequency and payload are byte-for-byte unchanged at runtime.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostAutomationService.ts:745-769,1028-1039,1389-1394</code>: Persist and flush the catalog, run maps, and related automation state before run-created or run-started telemetry is emitted.; cardinality: One flush per manual run claim or run commit; scheduled claims are grouped into one flush for the tick.
    - Introduced by diff: false; previous behavior: The identical persistence calls and cardinality existed before the PR.; critical-path effect: Persistence is awaited and is on the run creation/linkage critical path, but it completes before the changed telemetry classification is referenced.
  - filesystem at <code>src/vs/platform/agentHost/node/agentHostTelemetryService.ts:283-290; src/vs/platform/telemetry/common/telemetryService.ts:251-265</code>: Write each telemetry event through the existing TelemetryLogAppender/logger.; cardinality: One logger appender call per emitted runCreated/runStarted event when telemetry is enabled.
    - Introduced by diff: false; previous behavior: The same runtime event and logger submission occurred before the PR.; critical-path effect: Appender submission occurs synchronously after durable state is committed; classification generic types do not alter the event object or appender call.
  - network at <code>src/vs/platform/agentHost/node/agentHostTelemetryService.ts:287-292; src/vs/platform/telemetry/node/1dsAppender.ts:98-115</code>: Submit enabled telemetry through OneDataSystemAppender, whose Node transport starts an asynchronous HTTP POST.; cardinality: One logical telemetry event submission per emitted transition, with transport batching controlled by the existing appender.
    - Introduced by diff: false; previous behavior: The same events, provider payload, and collector submission existed before the PR; only compile-time classification ownership changes.; critical-path effect: HTTP sending is explicitly fire-and-forget, so network completion is not awaited by automation execution.
- Verdict: No reportable regression. Runtime serialization, hashing, logging, persistence, network cardinality, and concurrency are unchanged.

**Summary:** Completed the performance pass over the sole changed hunk and traced both build-time extraction and runtime automation telemetry paths. The PR changes only erased classification types, with no added runtime work or changed expensive-boundary cardinality, so no performance finding was submitted.
