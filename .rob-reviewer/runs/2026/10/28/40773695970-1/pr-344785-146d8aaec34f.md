<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** boundary-fanout, repeated-work, serialization-allocation

### Scenario 1: Authenticated startup or scheduled Copilot model-catalog refresh, followed by model-picker publication

- Critical path: The refresh waits for the Copilot client, models.list, managed-settings resolution, synchronous projection of M models and T Auto tiers, and publication. The changed offersFusionAutoTier predicate executes only after the remote catalog is available; for unavailable Fusion it changes the single Auto row's name/schema/meta decoration but adds no wait or boundary. Publication then schedules the same existing model-configuration refresh for each live chat session.
- Scaling input: M returned models, T provider Auto tiers, and S live chat sessions. The changed predicate remains O(T), and the new presentation allocation is bounded to the single Auto model; existing publication work remains O(M + T + S).
- Effective concurrency: Public refreshModels calls coalesce onto one in-flight refresh, invalidating lifecycle triggers coalesce onto one next-task refresh, and failures retry sequentially with backoff. Per-session configuration refreshes are queued by each session; aggregate concurrency can scale with S, but the diff does not add publications or session refreshes.
- Cache behavior: The last-known catalog is retained on refresh failure, model refreshes are coalesced, and the same provider metadata is reused during publication. The diff changes neither cache keys nor cold/warm refresh behavior and adds no positive or negative cache state.
- Mechanism confidence: High: both offersFusionAutoTier call sites and the full publication/session-refresh path were traced; the before/after difference is only predicate eligibility and resulting in-memory presentation metadata.
- Magnitude uncertainty: Actual catalog sizes and live-session counts vary, but the changed work is a tiny bounded transformation of one Auto row and does not change the dominant remote or per-session operation counts.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_refreshModels/\_ensureClient</code>: Ensure/start the Copilot SDK client used for model discovery; cardinality: At most one client start when the shared client is absent; subsequent warm refreshes reuse it.
    - Introduced by diff: false; previous behavior: The same client startup/reuse path ran before the predicate change.; critical-path effect: Required before the model catalog can be listed on a cold client.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5247</code>: List Copilot models and Auto-tier metadata via client.rpc.models.list; cardinality: One call per refresh attempt; failure retries are sequential and bounded by the existing retry policy.
    - Introduced by diff: false; previous behavior: Exactly one models.list call per attempt before the diff as well.; critical-path effect: The catalog cannot be published until this call completes.
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3768</code>: Resolve managed model settings after a successful model listing; cardinality: One resolution per successful refresh attempt.
    - Introduced by diff: false; previous behavior: The same policy resolution was already on the refresh critical path.; critical-path effect: Publication waits for policy resolution.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_refreshManagedModelConfiguration</code>: Refresh each live session's model configuration with session.model.list and session.model.getCurrent; cardinality: Two control-plane RPCs per live session after each existing catalog publication; each session sequences its own refreshes.
    - Introduced by diff: false; previous behavior: \_publishModels already iterated every live session and queued the same refresh regardless of whether unavailable Fusion tiers presented Auto as Fusion.; critical-path effect: Off the catalog publication's synchronous critical path because refreshModelConfiguration queues asynchronous work, though it consumes IPC proportional to live sessions.
- Verdict: No reportable regression. The PR does not add or fan out any expensive boundary and does not increase refresh frequency; it only chooses the existing Fusion presentation branch for metadata that was already fetched and published.

### Scenario 2: Model discovery for an alternate scoped credential source

- Critical path: On a cold scoped-catalog entry, the host starts a temporary scoped Copilot runtime, lists models, resolves managed settings, projects the model list (including the changed Fusion predicate), and then stops the runtime. The caller waits for this entire sequence.
- Scaling input: M models and T Auto tiers for one credential source. The presentation check remains O(T) and decorates at most the one Auto model; no extra remote request is caused.
- Effective concurrency: Calls for the same source/current credential/startup configuration share the cached promise. Different credential sources may discover in parallel as before; the diff adds no concurrency or limiter bypass.
- Cache behavior: The scoped catalog/promise is cached by source and reused while credentials and startup configuration remain current. Cancellation without a completed catalog can recreate it. The changed predicate neither changes the cache key nor invalidates the entry.
- Mechanism confidence: High: the scoped cache ownership, temporary runtime lifecycle, and \_presentModels call were directly inspected.
- Magnitude uncertainty: The number of simultaneous credential sources is product-dependent, but same-source coalescing and all expensive operation counts are unchanged.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:getModelsForCredentials</code>: Start and stop a temporary ScopedCopilotClient runtime; cardinality: One start and one stop per cold scoped-catalog creation; shared calls for the same source use one promise.
    - Introduced by diff: false; previous behavior: The temporary runtime lifecycle was identical before the presentation predicate changed.; critical-path effect: Both startup and shutdown are awaited by scoped discovery.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3648/\_listModels</code>: List models through the scoped runtime; cardinality: One models.list call per cold scoped-catalog creation.
    - Introduced by diff: false; previous behavior: The same single catalog request occurred before the diff.; critical-path effect: Required before scoped models can be returned.
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3649</code>: Resolve managed settings for the scoped credential; cardinality: One resolution per cold scoped-catalog creation.
    - Introduced by diff: false; previous behavior: The same resolution was already awaited.; critical-path effect: Returned models wait for policy resolution.
- Verdict: No reportable regression. The diff changes only how already-returned metadata labels the Auto row and does not alter scoped runtime, request, cache, or concurrency behavior.

### Scenario 3: In-memory model republishing after BYOK registry changes or local-model row changes

- Critical path: The trigger reads cached/local model rows, rebuilds and publishes the merged model array, then queues existing per-session model-configuration refreshes. BYOK publication may separately synchronize BYOK registrations to active sessions. The changed predicate can choose Fusion decoration during the synchronous rebuild but introduces no new trigger or publication.
- Scaling input: M catalog/BYOK/local rows and S active sessions. Existing work scales O(M + S); the changed branch adds a constant-size copy for the single Auto row and no additional S-scaled operation.
- Effective concurrency: Each trigger calls \_publishModels synchronously. Session model-configuration work is queued per session, while BYOK registration may run across active sessions; these scheduling rules and trigger counts are unchanged by the diff.
- Cache behavior: BYOK models come from the bridge registry's cached serving window, and unchanged root config values suppress redundant BYOK refreshes. Local rows are read from the current provider. Fusion eligibility uses already-held Auto-tier metadata; no new cache miss or external fetch occurs.
- Mechanism confidence: High: all \_publishModels calls touched by local/BYOK changes and the transitive session refresh implementation were traced.
- Magnitude uncertainty: Large active-session counts make the pre-existing publication fan-out more expensive, but this PR neither increases publication frequency nor adds a session-level call.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:6760-6780</code>: Per-session model.list and model.getCurrent during queued model-configuration refresh; cardinality: Two RPCs per active session for each publication, sequenced within each session.
    - Introduced by diff: false; previous behavior: Every \_publishModels call already queued these same per-session refreshes; the predicate result does not control that loop.; critical-path effect: Queued after synchronous publication and therefore off the immediate picker-update path.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_refreshByokModels</code>: Synchronize BYOK model registrations to active sessions when BYOK rows are present; cardinality: One sync attempt per active session on qualifying BYOK refreshes.
    - Introduced by diff: false; previous behavior: The BYOK session-sync loop and its cardinality are unchanged.; critical-path effect: Asynchronous after model publication.
- Verdict: No reportable regression. The only new cost on this path is bounded object spreading/localization for one Auto presentation; all session-scaled IPC is pre-existing and occurs at the same frequency.
