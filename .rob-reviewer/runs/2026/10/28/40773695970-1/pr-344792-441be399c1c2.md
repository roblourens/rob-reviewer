# Performance review: chat: add a file chooser to the attachment menu

[PR #344792](https://github.com/microsoft/vscode/pull/344792) at `441be399c1c26001fd2bb0f02d9e1430b73137f5`

## Findings (2)

### 1. [medium] Resolve selected attachments with bounded concurrency

**Finding ID:** `PERF-F90530A4291B`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/actions/chatContext.ts:176</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Filesystem stat/read operations, full image byte buffers, image hashing, decoding, canvas resizing, and encoding CPU work  
**Scaling:** Critical-path time grows as the sum of work for all N selected files; for images it also grows with total selected bytes and pixel counts because each file completes its stat/read/hash/resize chain before the next starts.  
**Outcome:** Increased attachment latency and delayed return of focus after choosing multiple files, especially multiple screenshots or remote files  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no multi-select Files action on this menu; the existing equivalent multi-file attachment path for drag-and-drop resolves entries concurrently with Promise.all in chatDragAndDrop.ts.  
**Changed behavior:** The new chooser accepts an arbitrary multi-selection but awaits resolveEditorAttachContext inside a for loop, serializing every selected resource before any attachments are committed and before the finally block restores input focus.  
**Confidence:** 0.99 — The new loop, awaited caller, and transitive stat/read/hash/resize operations are directly traced, and the same resolver's existing multi-file drag/drop caller demonstrates that independent resources need not be serialized. Exact delay varies with file size and provider latency, which affects severity but not the mechanism.

**Causal diff evidence:** RIGHT line 176 is the per-resource \`await this.attachmentResolveService.resolveEditorAttachContext({ resource })\` newly placed inside the chooser's multi-select loop; RIGHT line 160 explicitly enables \`canSelectMany: true\`.

Selecting several files makes the Add Context action wait for every file in series. Each image resolution performs filesystem stats, a full read, hashing, decode, and possible canvas resize/encode, so a realistic batch of screenshots incurs roughly the sum of all per-image delays rather than bounded parallel latency.

**Evidence:** The added line awaits resolveEditorAttachContext within \`for (const resource of resources)\`. That resolver calls fileService.stat; image resources then perform another stat, readFile, imageToHash, and resizeImage. \`\_handleContextPick\` awaits this whole method before adding the returned entries, while the established multi-file drag/drop path calls the same resolver through Promise.all.

**Suggested direction:** Resolve selections through Promise.allSettled with a small shared concurrency limit, preserve input order, and emit the existing per-file notifications from settled results; this keeps memory/decoder pressure bounded while removing fully serial I/O and image processing.

### 2. [medium] Avoid serial re-stat of every checked item

**Finding ID:** `PERF-E7C0960F2009`  
**Location:** <code>src/vs/workbench/services/dialogs/browser/simpleFileDialog.ts:602</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Filesystem provider stat calls, including remote filesystem IPC/network requests  
**Scaling:** For N checked items, acceptance now issues 2N stat calls in N sequential rounds; all items from one displayed folder redundantly stat that same parent N times.  
**Outcome:** Increased file-dialog acceptance latency and reduced responsiveness on remote or high-latency filesystem providers  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the diff the simplified dialog was single-select and acceptance validated at most one URI, causing one pair of parent/target stats.  
**Changed behavior:** Enabling canSelectMany adds a loop that awaits validate for each checked item sequentially. \`validate\` always performs parallel stats for the item's parent and target, but the next pair is not started until the prior pair completes.  
**Confidence:** 0.99 — The exact 2N call count, serial ordering, shared-parent duplication, and remote/simplified routing are all explicit in the code. Filesystem provider latency is environment-dependent, so magnitude varies, but the scaling mechanism and blocked accept path are certain.

**Causal diff evidence:** RIGHT line 602 introduces the awaited per-selected-item validation loop after RIGHT line 359 enables multi-selection; this raises the pre-diff maximum from one validation pair to N serialized pairs.

In a remote/simplified dialog, checking a realistic batch of files and pressing Attach leaves the picker busy for N round trips, even though the directory listing already resolved those rows and every selected file commonly shares one parent. The delay scales linearly with selection count and remote latency before the dialog can close.

**Evidence:** RIGHT lines 601-607 iterate selectedItems and await validate. \`validate\` calls \`fileService.stat(dirname(uri))\` and \`fileService.stat(uri)\` via Promise.allSettled. Browser non-file schemes and Electron remote schemes/settings route showOpenDialog through SimpleFileDialog, putting those provider calls on the accept critical path.

**Suggested direction:** Use an open-dialog multi-selection validator that groups items by parent, stats each parent once, and validates target URIs with a small concurrency limit; retain the current failure message and reject the selection if any target is invalid.
