**Relevant issue families:** repeated-work, boundary-fanout, eager-work

### Scenario 1: Open a sessions window and initialize installed extensions with extension management enabled or disabled

- Critical path: Installed manifests are scanned and enablement is computed before the extension registry and hosts receive enabled extensions. With management enabled, the diff admits codeless extensions with non-declarative contributions; registering those contributions is required for the feature. No new filesystem or network operation is placed on this path.
- Scaling input: Total installed extensions N, with added registry/serialization work proportional to the subset C of codeless extensions that have non-declarative contribution points and no explicit override. Typical contribution-key checks are linear in each manifest's small contributes object.
- Effective concurrency: Initial extension descriptions are grouped into existing registry/extension-host initialization batches; extension-host updates run concurrently across the bounded set of host managers rather than issuing one IPC call per extension.
- Cache behavior: Manifests have already been scanned and configuration reads are in-memory. There is no new cache, miss retry, negative-cache state, or invalidation path. Warm execution repeats only the inexpensive eligibility checks when callers recompute state.
- Mechanism confidence: High: the eligibility path, in-memory checks, extension registry update, and batched IPC call path are directly traced. There is no evidence of per-extension I/O or unbounded retention.
- Magnitude uncertainty: The repository does not establish how many installed codeless non-declarative extensions users commonly have or their manifest sizes, but the effective set is bounded by installed extensions and enabling their contributions is the requested behavior.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/extensions/common/abstractExtensionService.ts::\_updateExtensionsOnExtHosts</code>: Send the enabled extension-description set to each extension host during existing host initialization/update batching; cardinality: One batched delta per active extension-host manager; payload size can grow by C newly eligible codeless extension descriptions, not C independent IPC calls.
    - Introduced by diff: false; previous behavior: The same batched extension-host boundary existed, but codeless manifests with contribution points outside the declarative allowlist were excluded unless support was otherwise declared or configured.; critical-path effect: Extension registration must complete before newly eligible manifest contributions are available; host-manager updates are awaited as part of existing extension initialization/update handling.
- Verdict: No reportable regression. The additional registry/serialization work is the necessary, bounded cost of enabling the newly supported codeless extensions, and no avoidable fan-out or eager heavyweight boundary was introduced.

### Scenario 2: Toggle extensions.experimental.agentsWindowManagement or extensions.experimental.agentsWindowAutoEnable in an open sessions window

- Critical path: The synchronous configuration listener filters installed extensions and expands dependents, then emits an enablement event. Extension deltas are queued and processed asynchronously; only actual registry changes reach extension hosts. The changed helper adds an in-memory contribution-key scan to preserve notification of codeless extensions whose support depends on management.
- Scaling input: Installed extension count N and dependency relationships. The existing dependent expansion can scan the installed list repeatedly; the diff does not materially increase its seed set for the management transition because those codeless unsupported extensions were already selected before the PR. Manifest key checks scale with contribution-point count.
- Effective concurrency: Configuration filtering and dependent expansion are synchronous and serialized for one setting event. Delta items are serialized by the extension-service queue; updates to the bounded extension-host-manager set use Promise.all and each host receives one batched delta.
- Cache behavior: Configuration values and manifests are read from memory. No cache is added or invalidated. Repeated work occurs only per rare setting-change event, not per frame/input/message.
- Mechanism confidence: High: the synchronous scan, queue serialization, duplicate filtering, and host batching are explicit in the traced code.
- Magnitude uncertainty: Exact N and dependency density vary, but setting changes are infrequent and the potentially quadratic dependent expansion predates the diff with substantially the same affected population.
- Expensive boundaries:
  - filesystem at <code>configuration service update preceding ExtensionEnablementService.onDidChangeConfiguration</code>: Persist the user configuration change; cardinality: One configuration update initiated by the user or experiment assignment.
    - Introduced by diff: false; previous behavior: The same setting update and configuration event occurred before the diff.; critical-path effect: Persistence is part of the pre-existing setting update and occurs before the listener path reviewed here.
  - IPC at <code>src/vs/workbench/services/extensions/common/abstractExtensionService.ts:\_updateExtensionsOnExtHost</code>: Apply the resulting batched extension-description delta to each active extension host; cardinality: At most one batched call per active host manager for the queued setting event; already-present or already-absent descriptions are filtered before IPC.
    - Introduced by diff: false; previous behavior: The event already drove the same batched delta path for unsupported/auto-enabled extensions. The diff changes which codeless descriptions legitimately change state under management.; critical-path effect: Processed asynchronously after the synchronous enablement event; required state-changing extensions are added or removed before their contributions are authoritative.
- Verdict: No reportable regression. The changed classification does not introduce per-extension I/O, a concurrency burst, or a material new hot-path multiplier; state-changing registration work is required by the setting semantics.

### Scenario 3: Render or recompute the Agents-window extension customization list and extension suggestions

- Critical path: The widget/suggestions iterate installed extensions and call canExecuteOnSessionsWindow. For codeless non-declarative manifests the diff adds one in-memory configuration lookup after the existing contribution-key scan. Rendering and suggestion filtering perform no newly introduced boundary call.
- Scaling input: Installed extensions displayed or considered, effectively N after local filtering; work is linear in N and each manifest's contribution-key count.
- Effective concurrency: Computation is synchronous in the renderer/observable derivation. No queue, network concurrency, subprocess, or IPC is involved in the changed eligibility check.
- Cache behavior: There is no result cache, but inputs are in-memory manifests and configuration. Recomputations are driven by extension/configuration changes or widget updates, not continuous frames. Cold and warm behavior differ only in surrounding observable/widget state, not in boundary work.
- Mechanism confidence: High: all callers and the implementation are directly visible, with no transitive expensive boundary from the changed branch.
- Magnitude uncertainty: UI recomputation frequency depends on surrounding extension change events, but the added operation is an in-memory boolean configuration read and there is no evidence it dominates rendering.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added in-memory lookup is bounded linear work and does not establish measurable synchronous UI jank or a new expensive boundary.

**Summary:** Reviewed all four changed files and traced startup eligibility, live setting changes, extension registry/host deltas, customization rendering, and suggestion recomputation. The diff enables a bounded subset of installed codeless extensions and preserves batched extension-host updates. No actionable performance regression or evidenced regression fix was found.
