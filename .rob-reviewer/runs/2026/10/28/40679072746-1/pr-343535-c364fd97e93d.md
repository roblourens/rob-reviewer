# Performance review: transitioning to clipboard api

[PR #343535](https://github.com/microsoft/vscode/pull/343535) at `c364fd97e93d4cc3ffd487fb9638e92bf8438a92`

## Findings (1)

### 1. [medium] Keep clipboard files lazy until a paste provider requests them

**Finding ID:** `PERF-3D2FE629DABE`  
**Location:** <code>src/vs/editor/browser/dataTransfer.ts:17</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Binary clipboard bytes allocated as an ArrayBuffer/Uint8Array and copied again into a new Uint8Array and File for every file representation  
**Scaling:** The transient allocation and decoding cost grows with the summed size of all binary clipboard representations; a single high-resolution screenshot can be many megabytes, and multiple representations are processed sequentially before paste can proceed.  
**Outcome:** Increased paste latency plus transient memory and GC pressure on image/media paste  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The legacy paste route received browser-owned File objects from the ClipboardEvent and converted them to VSDataTransfer items whose data() callback read bytes only when a provider requested them; the extension-host DataTransferFileCache likewise resolves file bytes lazily.  
**Changed behavior:** The experimental Clipboard API route first creates lazy file items in readClipboardData, then calls toDataTransfer before firing onWillPaste; this added line eagerly awaits every file.data(), allocates another Uint8Array, and constructs a new File before providers are selected or invoked.  
**Confidence:** 0.98 — The allocation, call path, and before/after behavior are directly visible: all API pastes await this loop before firing providers, file.data() performs blob.arrayBuffer(), and the existing provider bridge demonstrably preserves file.data() as a lazy resolver. Only the exact browser-level copy count and payload sizes vary.

**Causal diff evidence:** The added file branch at RIGHT line 17 (\`new File(\[new Uint8Array(await file.data())\], ...)\`) is the new eager byte-materialization step, and the same PR adds its unconditional invocation on the experimental paste critical path at src/vs/editor/contrib/clipboard/browser/clipboard.ts:461.

With editor.experimentalClipboardApi enabled, pasting a screenshot or other large media blocks provider dispatch on full payload materialization and creates multiple payload-sized transient allocations, causing slower paste and avoidable GC/memory spikes even when no provider ultimately consumes that file.

**Evidence:** readClipboardData stores non-text blobs behind a lazy data() callback (src/vs/base/browser/clipboard.ts:46), but executeClipboardApiPaste unconditionally awaits toDataTransfer before triggerOnWillPaste (src/vs/editor/contrib/clipboard/browser/clipboard.ts:461-463). This line calls file.data(), wraps the returned Uint8Array in a new Uint8Array, and then a File. Existing paste providers consume VSDataTransfer; DataTransferFileCache.resolveFileData invokes file.data() only on demand, and the Markdown image provider carries DataTransferFile contents into its workspace edit without eagerly calling data().

**Suggested direction:** Avoid round-tripping the Clipboard API result through a DOM DataTransfer. Build the paste event directly over the IReadonlyVSDataTransfer: parse only text/metadata eagerly, expose file names/types without reading bytes, and return the original lazy transfer to paste providers so file.data() runs only for the selected provider.

- Effective concurrency: One Clipboard API write is awaited per command. Existing prepare-paste providers may start concurrently by provider, but this behavior already ran from the legacy onWillCopy/onWillCut event and is not introduced or amplified.
- Cache behavior: No clipboard write cache or coalescing is used. In-memory editor metadata is a single last-copy entry and does not retain payload bytes; cold and repeated writes each serialize the current selection.
- Mechanism confidence: High confidence: the command and service call graph shows one grouped write and unchanged provider preparation ownership.

### Scenario 2: Plain-text and rich-text editor paste with the experimental API enabled

- Critical path: A single navigator.clipboard.read completes, each available string representation is decoded, the result is converted for the editor event, synchronous onWillPaste listeners run, and either an existing paste provider operation or the default text paste completes.
- Scaling input: Number and total size of clipboard text/custom formats plus applicable paste-provider count; common clipboard contents have a few representations.
- Effective concurrency: Clipboard items and formats are read sequentially by the new loops. Existing applicable providers may be queried concurrently downstream; no added unbounded task launch was found.
- Cache behavior: No clipboard read cache or in-flight coalescing is used, so each paste sees current clipboard contents. Provider copy metadata can reference existing prepared data; this does not cache clipboard payload decoding.
- Mechanism confidence: High confidence in the one-read/per-format critical path; low evidence of harmful magnitude for ordinary text formats.
- Magnitude uncertainty: Custom-format count and Blob decoding cost vary, but typical text clipboard cardinality is low and no evidence establishes a material regression independent of the intended rich read.
- Expensive boundaries:
  - other at <code>src/vs/base/browser/clipboard.ts:34-50 readClipboardData</code>: Browser/OS rich clipboard read and per-format Blob retrieval; cardinality: One clipboard.read per paste and one getType per advertised representation.
    - Introduced by diff: true; previous behavior: The browser supplied DataTransfer through a ClipboardEvent triggered by the legacy paste route.; critical-path effect: All reads and text decoding complete before editor paste listeners or default insertion can progress.
  - IPC at <code>src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts:1115-1154 provideDocumentPasteEdits</code>: Existing paste-edit provider invocation in extension hosts; cardinality: One request per matching provider, using one data-transfer DTO per request; provider count is bounded by registered applicable providers.
    - Introduced by diff: false; previous behavior: The same CopyPasteController provider dispatch ran for legacy ClipboardEvent paste data.; critical-path effect: Only applies when paste providers are enabled and match the clipboard types; default text paste otherwise proceeds without this IPC.
- Verdict: No additional finding. The read is a required part of the opted-in rich API path, typical effective cardinality is small, and no avoidable boundary fan-out was proven.

### Scenario 3: Pasting a screenshot or other binary media into an editor with the experimental API enabled

- Critical path: The browser clipboard read yields lazy VSDataTransfer file items, but toDataTransfer then awaits every file.data(), allocates another Uint8Array and File sequentially, and only afterward fires onWillPaste. Matching paste providers then run and may save the selected media through an existing workspace edit.
- Scaling input: Summed bytes across all binary clipboard representations, number of binary representations, and matching providers/files. A realistic high-resolution screenshot is a single multi-megabyte image; multiple advertised media representations increase the total proportionally.
- Effective concurrency: Binary materialization is serialized across transfer entries before provider dispatch. Existing matching providers can run downstream; the eager allocations cannot overlap with or be skipped based on provider selection.
- Cache behavior: The Clipboard API service initially exposes each Blob through a lazy data() callback, with no byte cache. The new conversion consumes every callback once before dispatch; the existing extension-host bridge otherwise resolves only a requested file and does not require warm-cache materialization.
- Mechanism confidence: Very high confidence: the new command unconditionally awaits toDataTransfer, the added file branch explicitly calls lazy file.data(), and the existing provider bridge proves bytes can remain lazy.
- Magnitude uncertainty: Exact screenshot compression, browser Blob/File internal copy behavior, and GC timing vary, but blob.arrayBuffer plus the explicit new Uint8Array guarantee payload-sized work before provider dispatch.
- Expensive boundaries:
  - other at <code>src/vs/base/browser/clipboard.ts:34-50 readClipboardData</code>: Browser/OS rich clipboard read and binary Blob retrieval; cardinality: One clipboard.read per paste and one getType per advertised image/media representation.
    - Introduced by diff: true; previous behavior: Legacy ClipboardEvent paste supplied browser-owned File objects directly.; critical-path effect: Required before conversion and provider dispatch.
  - serialization at <code>src/vs/editor/browser/dataTransfer.ts:12-22 toDataTransfer</code>: Full Blob-to-ArrayBuffer conversion followed by Uint8Array and File construction for every binary item; cardinality: Once per binary transfer entry, with bytes proportional to that entry's full payload.
    - Introduced by diff: true; previous behavior: Legacy conversion wrapped File.arrayBuffer behind IDataTransferFile.data(); providers and the extension-host file cache requested bytes lazily.; critical-path effect: All payload materialization and copies complete before onWillPaste and before provider filtering/consumption.
  - IPC at <code>src/vs/workbench/api/browser/mainThreadLanguageFeatures.ts:1115-1171</code>: Matching paste-provider request and optional lazy file-data resolution to an extension host; cardinality: One provider request per matching provider; at most one file-data resolution per file actually requested by that provider.
    - Introduced by diff: false; previous behavior: Existing legacy paste providers received lazy file items and resolved bytes on demand.; critical-path effect: Provider selection/edit computation occurs after the newly eager conversion; file-data IPC is only incurred when provider logic or an applied edit needs bytes.
  - filesystem at <code>extensions/markdown-language-features/src/languageFeatures/copyFiles/dropOrPasteResource.ts:198-259</code>: Create/write pasted media file through the provider's workspace edit; cardinality: Typically one create/write for one pasted screenshot; scales with accepted media files.
    - Introduced by diff: false; previous behavior: The Markdown provider already created workspace media files for legacy image paste.; critical-path effect: Occurs only after a matching provider creates and the editor applies the paste edit.
- Verdict: Reportable medium performance regression. The diff defeats lazy binary ownership and adds full-payload critical-path allocations before knowing whether a provider will consume the media.

### Scenario 4: Legacy clipboard routes and Safari text-write workaround

- Critical path: With the option disabled, existing editor execCommand/triggerPaste routes remain selected. On Safari text writes, a user-gesture-started clipboard.write now has its result awaited after pending text is supplied; fallback execCommand creates and removes one textarea.
- Scaling input: One text payload and one clipboard operation per command; cost scales with text length but not collection cardinality.
- Effective concurrency: The Safari workaround retains only the latest pending user-gesture write and cancels an unresolved predecessor's data promise. One write result is awaited by the matching writeText call.
- Cache behavior: No payload cache. Pending state is cleared when consumed or replaced, so no unbounded retention was found.
- Mechanism confidence: High confidence: changed state tracks the already-existing clipboard.write promise and introduces no additional browser call.
- Magnitude uncertainty: Browser acknowledgement latency varies, but boundary count and payload work are unchanged.
- Expensive boundaries:
  - other at <code>src/vs/platform/clipboard/browser/clipboardService.ts:122-179</code>: Safari browser/OS clipboard write acknowledgement; cardinality: One pending browser write per gesture and one acknowledgement awaited by the corresponding writeText.
    - Introduced by diff: false; previous behavior: The browser write itself already started on every relevant gesture; the diff records and awaits its existing result rather than adding another write.; critical-path effect: writeText now resolves with the actual browser write result instead of only completing the supplied-data promise.
- Verdict: No performance finding. Waiting for the existing acknowledgement is bounded to one operation and does not add work, fan-out, or retention; the default editor route remains legacy unless explicitly enabled.

**Summary:** Reviewed all 18 changed files and traced experimental editor copy, cut, text/rich paste, image paste, legacy fallback, and Safari write acknowledgement paths. One medium eager-allocation regression was reported: the new image paste route defeats lazy file data and creates payload-sized copies before providers run. Clipboard boundary cardinality is otherwise bounded and existing provider/IPC/filesystem work is not amplified by the diff.
