### Scenario 1: Local debugger discovery probes GET /json/version and GET /json/list against a running replay proxy

- Critical path: The HTTP server parses the request URL and immediately drains the request and returns 404. No fixture lookup, replay matching, body concatenation, or record-mode forwarding must complete before the probe receives its response.
- Scaling input: Two known endpoint probes per discovery scan for each listening proxy port; repeated scans scale linearly with debugger discovery frequency. There is no cache or grouping, but each request is handled independently with constant work.
- Effective concurrency: Node's HTTP server may accept overlapping probes without an explicit limiter; each changed-path probe performs only synchronous URL parsing plus nonblocking request drain and response completion. No asynchronous upstream operations are spawned after the change.
- Cache behavior: The changed probe path bypasses replay buckets and recording state entirely. Warm versus cold fixture state does not affect it; no positive or negative cache entry is created. Replay construction still loads its fixture once, and record shutdown still writes its fixture once.
- Mechanism confidence: High: the changed guard returns before body listeners and before both \_replay and \_record, so the removed processing and upstream boundary are explicit in the call flow.
- Magnitude uncertainty: Debugger scan frequency varies by local tooling, but the changed mechanism unambiguously removes rather than adds downstream work for each matching probe.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/test/node/e2e/harness/capiReplayProxy.ts:\_handle (lines 521-529)</code>: Receive a loopback HTTP discovery request and return HTTP 404.; cardinality: One loopback request/response per probed endpoint, normally two requests per scan of this proxy port.

  - network at <code>src/vs/platform/agentHost/test/node/e2e/harness/capiReplayProxy.ts:\_record</code>: Forward unknown requests to the configured CAPI or mock upstream.; cardinality: Before the diff, one outbound request per debugger probe in record mode; after the diff, zero.

- Verdict: No performance finding. The change shortens the probe critical path and eliminates record-mode boundary fan-out.

### Scenario 2: Normal ancillary and model traffic through the CAPI replay proxy during agent-host integration tests

- Critical path: Every request now performs one initial URL parse before the existing body collection. Replay then uses in-memory fixture buckets and response generation; recording forwards one request upstream and buffers the response for fixture generation.
- Scaling input: Work scales with the number of SDK HTTP requests in an integration scenario. The diff adds one URL object/path extraction per request; managed-settings requests parse the URL again in the existing special case, and replay/record requests parse it again in their existing handlers.
- Effective concurrency: Requests are accepted by the Node HTTP server without a shared limiter. The diff does not add promises, queues, subprocesses, or outbound requests, so aggregate network concurrency is unchanged.
- Cache behavior: Replay fixtures are loaded into in-memory buckets at construction/reset and consumed by key; ordinary replay remains warm after loading and never contacts upstream. Recording remains uncached and forwards each request. The new probe comparison neither invalidates nor bypasses caches for non-probe traffic.
- Mechanism confidence: High that one URL parse/allocation is added per request; high that no expensive boundary count, scheduling, or retained lifecycle changes for ordinary traffic.
- Magnitude uncertainty: Integration scenarios vary in request count, but this is test-only traffic and the added operation is a bounded parse of the short request URL, dwarfed by existing HTTP, body, fixture, and model-processing work.
- Expensive boundaries:

- Verdict: No performance finding. The only added ordinary-request cost is a constant, short URL parse in a test harness, with no realistic material latency, throughput, or memory impact.

### Scenario 3: New CapiReplayProxy regression tests for probe exclusion and strict replay preservation

- Critical path: The tests sequentially start local proxies, issue fixed loopback fetches, consume each response, stop each proxy, and perform bounded fixture assertions and temporary-directory cleanup.
- Scaling input: Fixed cardinality: two proxy modes times two probe endpoints, plus four strictness cases. No data-dependent collection or unbounded history controls the work.
- Effective concurrency: All proxy starts and fetches are awaited sequentially. No Promise.all burst or subprocess is introduced; each proxy is stopped before the next relevant iteration proceeds.
- Cache behavior: The record pass writes one temporary empty fixture, the replay pass loads it, and each strictness case loads the committed empty fixture into a fresh proxy. There is no cross-test cache, but the total is fixed and intentional for lifecycle isolation.
- Mechanism confidence: High: test loops and awaits establish exact cardinality and serialization.
- Magnitude uncertainty: Filesystem and loopback latency vary by CI host, but the fixed eight requests and small fixture operations cannot scale with product input.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/test/node/capiReplayProxy.test.ts:29-34 and 57-62</code>: Start loopback HTTP servers and issue fetch requests to them.; cardinality: Eight fixed loopback requests across six fixed proxy lifecycles.
    - Introduced by diff: true; previous behavior: These regression cases and their loopback requests did not run.; critical-path effect: Each fetch response is awaited before the test advances.
  - filesystem at <code>src/vs/platform/agentHost/test/node/capiReplayProxy.test.ts:23-43</code>: Create/remove one temporary directory and read/write a small empty capture fixture.; cardinality: One temporary directory lifecycle, one recording write, and bounded small fixture reads.
    - Introduced by diff: true; previous behavior: The test suite did not perform this specific temporary fixture lifecycle.; critical-path effect: These synchronous filesystem operations occur on the test critical path but have fixed tiny cardinality.
- Verdict: No performance finding. The added regression coverage has small, fixed test-only cost and no burst, leak, or scaling mechanism.

**Summary:** Reviewed all three changed files and traced matching probes, ordinary proxy traffic, and the added tests through URL parsing, fixture I/O, loopback HTTP, and record-mode upstream forwarding. The PR removes expensive downstream work for debugger probes and adds only bounded test coverage plus a negligible per-request parse for ordinary test-harness traffic; no reportable performance regression was found.
