## Findings (4)

### 1. [high] Send incremental edits instead of full documents

**Finding ID:** `PERF-FB851A350428`  
**Location:** <code>extensions/markdown-language-features/markdown-editor-src/editor.ts:102</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Full-document strings, JSON serialization bytes, extension-host/main-thread IPC calls, and whole-document text-edit CPU/allocation  
**Scaling:** For a document of N characters and E editor mutations, the bridge transfers and compares O(N×E) text and applies E full-range WorkspaceEdits; rapid typing can also leave multiple async applyEdit calls in flight because the message callback is not sequenced or coalesced.  
**Outcome:** Increased typing latency, extension-host/main-thread CPU and GC pressure, and excessive IPC for large Markdown files  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no editable Markdown webview bridge, so typing did not serialize the entire document through a webview message and submit a full-range WorkspaceEdit for every source mutation.  
**Changed behavior:** The new autorun reads the complete sourceText and the callback on this line posts that complete string for every model change. The provider then calls document.getText() for comparison and replaces Range(0,0..lineCount,0) with the full payload through workspace.applyEdit.  
**Confidence:** 0.99 — The changed callback, full-string observable read, JSON webview transport, full-range WorkspaceEdit, and uncoalesced async call path are all directly traced in repository code. Exact latency varies with file size and typing rate, but the O(document size) cost per mutation is not speculative.

**Causal diff evidence:** Added line 102 explicitly sends \`{ type: 'edit', content: text }\`, where \`text\` is the complete model source read by the new autorun, creating the per-mutation full-document bridge that did not exist before this diff.

Typing in the experimental editor for a realistically large Markdown file performs document-sized serialization and a whole-document bulk edit per keystroke, directly on the input critical path. A burst of keystrokes can queue overlapping document-sized edits and make the editor lag or churn CPU/GC.

**Evidence:** editor.ts:83-86 invokes onEdit with model.sourceText.value whenever the observable changes, and line 102 sends that full value. markdownEditorProvider.ts:50-62 compares against another full document string, constructs a replacement spanning the entire document, and calls workspace.applyEdit. Core webview transport JSON.stringify's messages in mainThreadWebviews.ts:79-82/extHostWebviewMessaging.ts:22-64, and applyEdit crosses to MainThreadBulkEdits through extHostBulkEdits.ts:31-34.

**Suggested direction:** Transport and apply the actual changed range (or a minimal diff against the last acknowledged text) as an incremental WorkspaceEdit. Sequence/coalesce pending edits so rapid input cannot accumulate concurrent full-document work.

### 2. [medium] Release hidden Markdown editor webviews

**Finding ID:** `PERF-ECE0EFE4F2AE`  
**Location:** <code>extensions/markdown-language-features/src/extension.shared.ts:53</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Hidden webview iframes, Markdown source/model and parse objects, rendered DOM and Mermaid SVG nodes, and loaded editor/Mermaid JavaScript heaps  
**Scaling:** Retained memory grows with the number of opened-but-hidden custom-editor tabs and with each document's text, rendered node count, and diagrams; there is no eviction before a panel is closed.  
**Outcome:** Sustained renderer memory growth and greater GC pressure across normal tab switching sessions  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this provider was registered, opening Markdown files did not create these editor webviews, and the default custom-webview lifecycle would destroy hidden HTML contexts rather than retain them.  
**Changed behavior:** The registration now opts every Markdown editor panel into \`retainContextWhenHidden\`, preserving the full iframe and editor state after the user switches tabs even though the implementation can reconstruct itself from the authoritative TextDocument on its existing ready/init handshake.  
**Confidence:** 0.98 — The retention flag and API lifecycle contract directly prove the memory lifetime, and the new init protocol proves the document state is reconstructible. Exact bytes depend on tab/document size, so severity is medium rather than high.

**Causal diff evidence:** Added line 53 changes the custom editor from the default destroy-when-hidden lifecycle to retaining each complete webview context in the background.

A user who opens several large Markdown files in the experimental editor and then moves among tabs keeps every hidden editor's model, full rendered DOM, and heavyweight webview modules resident until the tabs are closed, increasing VS Code renderer memory and GC overhead.

**Evidence:** The added option on line 53 retains hidden contexts. vscode.d.ts:10055-10077 explicitly documents that this has high memory overhead and should only be used when context cannot be quickly saved/restored. Here markdownEditorProvider.ts:44-46 already sends the complete authoritative TextDocument whenever a context posts \`ready\`, and editor.ts:104-123 rebuilds the editor from that init; getState/setState are unused. The adjacent \`supportsMultipleEditorsPerDocument\` option also permits more retained contexts.

**Suggested direction:** Remove \`retainContextWhenHidden\`; persist only compact view state such as selection/scroll if needed and rebuild from TextDocument on the existing ready/init path.

### 3. [medium] Forward text-document patches instead of full snapshots

**Finding ID:** `PERF-ED2BB794985A`  
**Location:** <code>extensions/markdown-language-features/src/preview/markdownEditorProvider.ts:75</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Full-document string allocations and JSON IPC bytes, followed by full editor-model resets and Markdown render work in the webview  
**Scaling:** For a document of N characters and E external/source-editor changes, each matching custom editor sends O(N×E) text instead of the usually small \`contentChanges\`; the cost also multiplies by the number of live custom-editor views for that document.  
**Outcome:** Excessive IPC, CPU/GC pressure, and slower synchronized editing for large Markdown files  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no custom Markdown editor listener forwarding TextDocument changes into a webview, so normal source edits did not trigger this document-sized message and model reset.  
**Changed behavior:** The new onDidChangeTextDocument handler ignores the event's incremental \`contentChanges\`, calls document.getText(), and posts the entire current document. The webview handles every message by constructing a new full StringValue and setting model.sourceText.  
**Confidence:** 0.98 — The event frequency, available incremental ranges, full getText payload, JSON transport, and full StringValue reset are directly traced. The exact render cost inside the package is not required to prove the O(document size) serialization/allocation regression and only affects magnitude.

**Causal diff evidence:** Added line 75 converts every incremental TextDocumentChangeEvent into a full-document \`update\` message, introducing document-sized synchronization work per external change.

When a large Markdown document is changed outside this webview—for example while the source editor and experimental editor are open side by side—every keystroke or formatter edit serializes the full file across the extension-host/webview boundary and resets the webview model, causing lag and allocation churn.

**Evidence:** The added handler at lines 71-75 sends \`document.getText()\` for every matching event. vscode.d.ts:13411-13462 shows the event already provides range/offset/length/text patches. editor.ts:109-117 receives the snapshot and creates a new StringValue for the complete content. ExtHostWebview.postMessage serializes every payload with JSON.stringify before IPC (extHostWebview.ts:129-134 and extHostWebviewMessaging.ts:22-64).

**Suggested direction:** Serialize \`e.contentChanges\` as ordered range/offset patches and apply corresponding StringEdits in the webview; coalesce batches while preserving the event's edit ordering.

### 4. [medium] Load Mermaid only when a diagram is rendered

**Finding ID:** `PERF-96B715715CFD`  
**Location:** <code>extensions/markdown-language-features/markdown-editor-src/editor.ts:8</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Bundled JavaScript bytes plus browser parse, compile, initialization, and module-heap work for Mermaid and its D3/Cytoscape/layout dependency graph  
**Scaling:** The fixed Mermaid bundle and initialization cost is paid once for every newly created Markdown editor webview, regardless of whether the document contains zero Mermaid blocks; it grows further with simultaneously retained editor contexts.  
**Outcome:** Slower custom-editor first paint and increased CPU/memory for ordinary Markdown documents  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, opening a Markdown document in this new editor did not load Mermaid or its dependency graph; Mermaid-specific work in the existing dedicated extension is scoped to Mermaid rendering surfaces.  
**Changed behavior:** The new webview entrypoint statically imports Mermaid and initializes it at module evaluation, before the document is received and even when renderCustomCodeBlock never encounters a Mermaid block.  
**Confidence:** 0.97 — The static import, unconditional initialization, single-bundle build settings, and Mermaid-only call site are directly visible. Bundle byte size is not measured, so magnitude is reflected as medium severity, but the eager critical-path mechanism is certain.

**Causal diff evidence:** Added line 8 places the Mermaid package in the unconditional editor entry module, and added line 13 initializes it before any content or code-block language is examined.

Every user who opens the experimental editor—including for plain Markdown—must load and evaluate Mermaid's large renderer graph before the editor is ready, delaying first paint and consuming heap for functionality most documents do not use.

**Evidence:** Line 8 is a top-level static import and editor.ts:13 immediately initializes it; the only consumer is the \`language === 'mermaid'\` branch at lines 63-80. esbuild-webview-common.mts:11-19 bundles and minifies a single ESM entry without splitting, while the lockfile shows Mermaid bringing D3, Cytoscape, dagre, layout, parser, and related packages into this bundle.

**Suggested direction:** Split Mermaid into a separate webview chunk/entry and initialize it lazily on the first \`mermaid\` code block, caching the resulting module promise for subsequent diagrams.
