**Relevant issue families:** repeated-work, boundary-fanout, missing-coalescing, concurrency-burst, cleanup-lifecycle

### Scenario 1: Apply a customization installation or uninstall, then refresh discovered customizations for every active Copilot session and live anchor.

- Critical path: The installation SDK operation completes first; then applyCustomizationInstallation awaits Promise.all across active session controllers and anchors. The changed refresh return now remains on the critical path through any discovery scan that supersedes the scan it originally queued, until the latest scan publishes.
- Scaling input: Effective multiplicity is active sessions × distinct live ordered anchor sets per session. Workspace roots within one anchor are grouped into each SDK discovery request rather than called per root or per discovered file.
- Effective concurrency: Sessions and anchors refresh concurrently via nested Promise.all. One anchor cancels its prior scan, uses a 100 ms delayer for watcher-triggered work, and runs discovery categories concurrently. The diff neither increases aggregate scan concurrency nor introduces a limiter; it only makes waiters follow an already-queued replacement.
- Cache behavior: A live anchor reuses its SessionDiscoveredEntry. Discovery-path metadata is cached after the cold scan and invalidated by relevant file events; undiscovered anchors are skipped during explicit refresh and scan current state on first use. Superseding refreshes cancel/coalesce at the anchor, and the changed promise follows the newest scan rather than retrying or adding scans.
- Mechanism confidence: High: the call chain, cancellation, debounce, grouped RPC count, anchor deduplication, and Promise.all fan-out are directly visible. The changed lines alter only which existing promise completion is awaited.
- Magnitude uncertainty: Replacement scans add their actual remaining duration to operation latency, and sustained edits can keep a settled read pending; prevalence and scan duration depend on customization-file churn and workspace contents. This is the explicit consistency contract of the change, not extra work or fan-out introduced by it.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/customizations/copilotCustomizationInstallations.ts:apply</code>: Apply the prepared installation through the Copilot SDK/runtime.; cardinality: One apply operation per user-approved installation action.
    - Introduced by diff: false; previous behavior: The same SDK apply operation was awaited before the PR.; critical-path effect: Must complete before discovery refresh begins.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:discover</code>: Discover agent, instruction, and skill customizations through grouped Copilot SDK RPCs; a cold entry also fetches discovery paths for those three categories.; cardinality: Warm scan: three grouped discovery RPCs per refreshed live anchor. Cold scan: three additional grouped discovery-path RPCs. Superseding scans already existed and cancel the prior wrapper.
    - Introduced by diff: false; previous behavior: The same scans and replacement scans ran, but a waiter could finish when its originally observed scan was canceled.; critical-path effect: All active-anchor scans must settle before the installation call returns; after the diff, a replacement scan also remains on that wait path.
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:discover</code>: Resolve watched customization locations, parse discovered skills/plugins/manifests, and reconcile filesystem watchers.; cardinality: Filesystem work scales with customization files and distinct plugin roots within each anchor; plugin roots are deduplicated before parsing.
    - Introduced by diff: false; previous behavior: Identical filesystem work was already performed by each queued scan.; critical-path effect: Runs inside each discovery scan and therefore must finish before the refreshed state publishes.
- Verdict: No reportable performance regression. The longer critical path is the intended synchronization needed to avoid returning before the authoritative replacement scan publishes, while scan count, boundary cardinality, cache invalidation, and concurrency remain unchanged.

### Scenario 2: Create/resume a chat or obtain a settled customization/snapshot view while customization discovery is in flight.

- Critical path: getChatCustomizations/getCustomizationsSettled and ActiveClient.snapshot/getAppliedCustomizations await the selected anchor's discovery before returning customization state or launching with the snapshot. The changed whenSettled follows a replacement scan if a watcher or explicit refresh supersedes the current one. Session MCP discovery also completes on this path independently of the changed promise.
- Scaling input: One deduplicated anchor set per requested chat snapshot, with project paths grouped in SDK requests. Selected-agent fallback can additionally read the published anchor when it differs from the chat anchor.
- Effective concurrency: Host sync, client syncs, discovered customization scan, and MCP refresh run in Promise.all. Inside customization discovery, category RPCs run in parallel; MCP root scans run in parallel and their merges are sequenced. The diff adds no task, loop over files, or boundary concurrency.
- Cache behavior: Warm chat reads reuse the anchor's current customization state and cached discovery-path metadata; relevant watcher events invalidate path metadata and queue a debounced replacement. Concurrent settled readers observe the same latest \_settled promise sequence, with no new cache key or retained result introduced.
- Mechanism confidence: High: production callers, watcher invalidation, cancellation, debounce, and snapshot critical paths were traced. Only waiter attachment changes.
- Magnitude uncertainty: The added wait under a supersession is bounded by how long replacement scans continue; ordinary file events are debounced, while continuous writes could defer settlement. There is no evidence the PR adds such events or increases their frequency.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:discover</code>: Fetch grouped agent/instruction/skill discovery results from the Copilot SDK.; cardinality: Three grouped RPCs per actual anchor scan, plus three discovery-path RPCs only when path metadata is cold or invalidated.
    - Introduced by diff: false; previous behavior: The same scans were on the path, but cancellation of the observed scan could let the read finish before its replacement.; critical-path effect: A requested snapshot cannot proceed until the active/latest scan settles.
  - filesystem at <code>src/vs/platform/agentHost/node/shared/sessionMcpDiscovery.ts:refresh</code>: Read and parse customization files and plugin manifests, and refresh workspace MCP configuration roots.; cardinality: Customization file work scales with discovered files/plugin roots; MCP refresh is one shared root discovery per workspace root and is deduplicated across sessions using the same file service/root.
    - Introduced by diff: false; previous behavior: These filesystem scans and shared-root deduplication were already present.; critical-path effect: Both discovery and MCP refresh are awaited for settled snapshots. MCP work is unaffected by the changed lines.
- Verdict: No finding. Awaiting the latest already-scheduled scan is a correctness-motivated scheduling tradeoff, and no independent repeated work, allocation growth, boundary fan-out, or concurrency burst is introduced.

### Scenario 3: Relevant customization file changes while discovery is running, followed by publication or session teardown.

- Critical path: A watched relevant file event invalidates cached discovery locations and queues a debounced scan. Publication occurs only when a notifying scan changes state; publishWhenSettled is asynchronous unless another consumer explicitly awaits settled state. On teardown, the active cancelable scan and delayer are disposed.
- Scaling input: Work scales with relevant watcher events after 100 ms debounce and with live anchors watching distinct root sets; one event per entry schedules at most the replacement represented by its delayer state.
- Effective concurrency: Each entry has one active cancelable refresh handle; a new event cancels/replaces it. Across anchors entries are independent. Disposal cancels the current operation and prevents further discovery events from that disposed entry.
- Cache behavior: Watcher events invalidate discovered-directory metadata. The refresh delayer coalesces pending events, \_pendingRefreshNotify preserves notification intent across replacement, and cancellation resolves stored settlement without surfacing rejection. The diff does not alter these policies.
- Mechanism confidence: High for lifecycle and scheduling behavior; low uncertainty only concerns real-world churn frequency.
- Magnitude uncertainty: A continuously modified customization tree could keep settled consumers pending, but that requires sustained relevant writes and is inherent in requiring an authoritative settled snapshot. No evidence shows changed event generation, lost debounce, or leaked teardown ownership.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/sessionCustomizationDiscovery.ts:SessionCustomizationDiscovery</code>: Receive relevant file-change notifications, recompute discovery locations when invalidated, read customization content, and maintain watchers.; cardinality: One queued/coalesced replacement per live entry for events inside its watched resources; scan work is grouped by anchor rather than event or file after debounce.
    - Introduced by diff: false; previous behavior: Watcher scheduling, invalidation, debounce, cancellation, and scan work are unchanged.; critical-path effect: Usually off the user request critical path; it becomes critical only for an explicit settled reader or installation refresh waiting at that time.
- Verdict: No finding. Cleanup still cancels the live resource, replacement work remains coalesced, and the async loop performs one constant-time comparison per actual superseding scan rather than adding polling or busy work.

**Summary:** Reviewed the complete two-file diff and traced installation refresh, chat startup/snapshot, watcher replacement, IPC/filesystem boundaries, cache invalidation, fan-out, cancellation, and teardown. The PR changes promise settlement semantics only: callers now await already-existing replacement scans. It introduces no additional scan, boundary call, serialization, allocation, concurrency, or retained cache state, so no actionable performance issue was submitted.
