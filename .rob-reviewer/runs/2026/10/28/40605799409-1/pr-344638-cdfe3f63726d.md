## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `extensions/markdown-language-features/src/preview/markdownEditorProvider.ts:651` (`RIGHT`)  
**Blamed base line:** `extensions/markdown-language-features/src/preview/markdownEditorProvider.ts:645`  
**Introducing path:** `extensions/markdown-language-features/src/preview/markdownEditorProvider.ts`  
**Introducing commit:** `58c0981e26a02df7f5de5630dab4208906e3a648`  
**Mechanism family:** `repeated-work`  
**Performance category:** `rendering`  
**Confidence:** 0.96

**Mechanism:** Each save-related dirty-state event with no text changes redundantly triggered an O(document size) getText/full-content RPC transfer and renderer replaceSourceText; with after-delay autosave this repeated during active typing and could occur up to twice per save without coalescing.

**Symptom:** Large Markdown documents incurred repeated full-model replacement during autosave, adding IPC, allocation, and renderer work on the typing path and causing visible typing lag/caret disruption.

**Fixed behavior:** The added contentChanges.length === 0 guard returns before diagnostics refresh, epoch invalidation, full-document RPC serialization, and renderer model replacement, while content-bearing external changes continue through the existing synchronization path.

**Evidence:** The base event listener at line 645 handled every same-document onDidChangeTextDocument event. For empty dirty-state/save events it fell through to postAuthoritativeUpdate, which reads the entire document (postAuthoritativeUpdate at current lines 435-442), sends the full content over the extension/webview RPC boundary, and the renderer handles update by constructing a StringValue and calling model.replaceSourceText (markdown-editor-src/editor.ts:190-198). The new bridge test demonstrates two saves can occur between same-epoch edits and expects zero renderer updates. Blame identifies the listener's introducing commit.

### Scenario 1: Typing in the Markdown custom editor while after-delay autosave saves the active file

- Critical path: A webview edit is applied to the TextDocument and the filesystem save completes; the resulting empty onDidChangeTextDocument dirty-state event now returns immediately. - Scaling input: Cost before the fix scaled linearly with Markdown document length and with autosave frequency; an empty save event caused a full-content synchronization rather than O(1) handling. There is one active provider listener per open Markdown editor panel, filtered to its document.
- Effective concurrency: The filesystem save is managed by VS Code. Before the guard, each matching empty change event independently launched postAuthoritativeUpdate without local coalescing or awaiting it in the event callback, so multiple save/dirty-state events could leave RPC replacements in flight. After the diff, effective synchronization concurrency for empty events is zero.

### Scenario 2: External edits or save participants that actually modify Markdown text

- Critical path: A same-document event with one or more contentChanges still refreshes diagnostics, compares against expected local content, and sends an authoritative full-document update only when the change is external. The new guard does not run for this case.
- Scaling input: One listener invocation per TextDocument change event; an authoritative update transfers content proportional to document length. Effective cardinality is unchanged by the diff.
- Effective concurrency: External events retain the existing fire-and-report behavior and have no newly introduced limiter or burst. The diff neither increases request frequency nor changes concurrency for content-bearing events.
- Cache behavior: No content cache serves this path. expectedWebviewContent suppresses the echo for accepted local webview edits; the diff leaves that deduplication unchanged.
- Mechanism confidence: High: contentChanges.length greater than zero bypasses the new return and executes the original code unchanged.
- Magnitude uncertainty: External edit frequency and document sizes vary, but the PR leaves both boundary cardinality and payload size unchanged.
- Expensive boundaries:
  - IPC at <code>extensions/markdown-language-features/src/preview/markdownEditorProvider.ts:654-665</code>: Refresh diagnostics and, for non-local external changes, send the full authoritative document to the webview; cardinality: At most one diagnostics request and one document update per qualifying content-bearing event, unchanged from the base behavior after local-edit echo suppression.
    - Introduced by diff: false; previous behavior: The same diagnostics and authoritative update calls ran for content-bearing external changes.; critical-path effect: Required to synchronize real external content into the visible renderer; it remains on the external-edit propagation path.
- Verdict: No performance regression; required external synchronization retains its previous cost and behavior.
