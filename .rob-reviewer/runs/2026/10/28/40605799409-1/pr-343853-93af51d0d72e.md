<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, boundary-fanout, concurrency-burst

### Scenario 1: Copilot build/unit-test job setup via build/azure-pipelines/copilot/test-steps.yml

- Critical path: The AzureCLI&#64;2 setup task must complete before dotnet setup, typecheck, lint, compilation, and tests. On a successful first attempt the critical path is unchanged; only a failed attempt adds retry time before the job can progress.
- Scaling input: One setup task per Copilot test job. Each attempt performs a fixed-size setup independent of repository/test size; the diff raises failed-path attempts from 1 to at most 3.
- Effective concurrency: Retries for a task are sequential and bounded by Azure Pipelines. Separate pipeline jobs may execute concurrently, but this template is instantiated once in the main Copilot job (and once in a separately invoked recovery test job), so the diff does not create intra-job parallelism.
- Cache behavior: There is no secret cache: every attempt reacquires Azure credentials and fetches current Key Vault values. An existing .env is read and key entries are replaced, not used to skip remote reads. Warm and cold .env behavior therefore have the same remote-call cardinality; successful first attempts never retry.
- Mechanism confidence: High: the changed YAML directly enables two sequential retries, and the setup call path establishes the fixed network/subprocess/filesystem work repeated per failed attempt.
- Magnitude uncertainty: Exact Azure task retry backoff and failure timing are not present in the repository. The added cost occurs only after a failure, is capped at two retries, and the PR evidence describes two transient failures across 1,484 builds.
- Expensive boundaries:
  - network at <code>build/azure-pipelines/copilot/test-steps.yml:7 AzureCLI&#64;2</code>: Authenticate the AzureCLI task through the VS Code Development WIF service connection.; cardinality: Previously one login attempt per job; now up to three only when preceding task attempts fail.
    - Introduced by diff: false; previous behavior: A transient login failure ended the setup task and job after the first attempt.; critical-path effect: Authentication is on the setup critical path; retry delays a failed run but permits it to continue instead of terminating immediately.
  - subprocess at <code>build/azure-pipelines/copilot/test-steps.yml:12 inlineScript and extensions/copilot/package.json:6889 setup</code>: Launch npm, then tsx getEnv and non-interactive getToken setup scripts.; cardinality: One command chain per attempt, increasing from at most one to at most three on failures; getToken exits before network access on CI because stdin is non-TTY.
    - Introduced by diff: false; previous behavior: The command chain ran once and any nonzero result ended setup.; critical-path effect: The scripts must finish before downstream test steps.
  - network at <code>extensions/copilot/script/setup/getEnv.mts:45 fetchSecrets</code>: Acquire an Azure credential and make sequential Key Vault getSecret requests for fixed secret names.; cardinality: Up to six fixed secret reads per attempt (four required-path reads and up to two optional reads), hence up to 18 only if two complete attempts fail late and a third is attempted. No input-sized fan-out.
    - Introduced by diff: false; previous behavior: At most one fixed sequence of secret reads; a failure terminated the task.; critical-path effect: All required reads and attempted optional reads are awaited sequentially before tests can proceed.
  - filesystem at <code>extensions/copilot/script/setup/getEnv.mts:69 main</code>: Read, filter, and rewrite extensions/copilot/.env after successful secret retrieval.; cardinality: At most one small .env read/write per completed attempt; failed attempts before secret completion perform no write.
    - Introduced by diff: false; previous behavior: At most one .env rewrite.; critical-path effect: Synchronous but over a small fixed configuration file and on the setup critical path.
- Verdict: No reportable performance regression. Normal successful-job latency and boundary count are unchanged; the bounded extra work occurs only on an already-failing path and intentionally trades additional setup latency for avoiding a full failed build/rerun.

### Scenario 2: Cross-platform Copilot integration-test setup via build/azure-pipelines/copilot/test-integration-steps.yml

- Critical path: After Git LFS cache setup, AzureCLI authentication and npm setup must complete before executable-path discovery, Copilot compilation, and checkpointed integration tests. Retries affect this critical path only after setup failure.
- Scaling input: One setup task in each test job whose VSCODE\_TEST\_IDS contains copilot. Product pipelines schedule one such Unit job per enabled Windows, Linux, and macOS test stage, so effective aggregate cardinality can be three jobs, each with one normal attempt or at most three failed-path attempts.
- Effective concurrency: Within each job, retries and the six secret reads are sequential. Enabled OS jobs can run concurrently, so a shared transient outage could produce a bounded cross-job burst of up to three retrying tasks; the PR does not add jobs or unbounded concurrency.
- Cache behavior: No cross-job or per-attempt cache/coalescing exists for Azure login or Key Vault reads. Existing .env files do not avoid reads. The warm successful path remains one attempt; only failures trigger repeats.
- Mechanism confidence: High: template call sites establish up to one Copilot setup job per Windows/Linux/macOS stage, and changed line 30 directly bounds each failed task to two retries.
- Magnitude uncertainty: The exact set of OS stages enabled in each pipeline invocation and retry backoff are configuration-dependent. A simultaneous service outage could align retries, but the job count and per-job attempts are statically bounded.
- Expensive boundaries:
  - network at <code>build/azure-pipelines/copilot/test-integration-steps.yml:17 AzureCLI&#64;2</code>: Authenticate each selected OS test job using the WIF service connection.; cardinality: One login per OS job before the diff; now up to three per OS job only after failures. Across three enabled OS jobs, the maximum failed-path count rises from 3 to 9.
    - Introduced by diff: false; previous behavior: Each OS job attempted login once and stopped on transient failure.; critical-path effect: Each job is blocked until its own setup succeeds or exhausts retries.
  - subprocess at <code>build/azure-pipelines/copilot/test-integration-steps.yml:25 inlineScript and extensions/copilot/package.json:6889 setup</code>: Run npm setup, spawning getEnv and the non-TTY no-op getToken command.; cardinality: Fixed one command chain per attempt, bounded at three per affected OS job after the change.
    - Introduced by diff: false; previous behavior: One command chain per OS job.; critical-path effect: Compilation and integration tests cannot start until the command succeeds.
  - network at <code>extensions/copilot/script/setup/getEnv.mts:45 fetchSecrets</code>: Perform sequential Azure credential and Key Vault secret retrieval for a fixed set of names.; cardinality: Up to six secret reads per attempt; across three concurrently enabled OS jobs, six normal-path reads per job remain unchanged, while repeated late failures can produce at most 18 reads per job over three attempts.
    - Introduced by diff: false; previous behavior: One fixed sequence per OS job with no retry.; critical-path effect: Secret retrieval is awaited before .env generation and all tests.
  - filesystem at <code>extensions/copilot/script/setup/getEnv.mts:69 main</code>: Read and atomically replace key lines by rewriting the local .env file in each isolated agent workspace.; cardinality: One small local rewrite per completed attempt per job; no shared file contention across agents.
    - Introduced by diff: false; previous behavior: At most one local rewrite per OS job.; critical-path effect: Small synchronous work before compilation; retry can repeat it only when a later command in the task fails, while getToken normally exits successfully in CI.
- Verdict: No finding. The diff can repeat fixed remote setup work during transient failures and modestly amplify an outage across existing parallel OS jobs, but it neither changes successful-path cost nor introduces unbounded fan-out; bounded retry is the intended resilience behavior and is cheaper than rerunning whole failed jobs.

**Summary:** Reviewed both changed YAML hunks and traced their template call sites through AzureCLI authentication, npm/tsx subprocesses, sequential Key Vault reads, and .env filesystem updates. Considered repeated work, boundary fan-out, and concurrency burst behavior. The only added work is a maximum of two sequential retries after an already-failed setup attempt; successful paths are unchanged, cardinality is fixed, and no actionable performance regression was found.
