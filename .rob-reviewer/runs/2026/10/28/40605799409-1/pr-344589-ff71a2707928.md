# Performance review: sessions: improve bulk worktree cleanup feedback

[PR #344589](https://github.com/microsoft/vscode/pull/344589) at `ff71a27079289bca3f5c1d9dd965174f3665acbe`

## Findings (1)

### 1. [high] Keep cached filter changes off the all-session RPC path

**Finding ID:** `PERF-BAC67556C37E`  
**Location:** <code>src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupService.ts:372</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** agent-host RPCs: one cleanup-status request plus one or more resourceResolve filesystem-stat requests per archived session  
**Scaling:** For N archived sessions with R distinct worktree roots, every cached getWorktrees call now issues N status RPCs plus up to R existence RPCs. refreshPendingCleanup limits this to two sessions concurrently, and the two request types are sequential within each session, so latency grows roughly with N/2 host round-trip pairs even when the new age filter matches only a small subset.  
**Outcome:** increased latency and a blocked cleanup-editor critical path while rows are cleared and filter controls remain disabled  
**PR causality:** <code>introduced</code>  
**Previous behavior:** On a valid one-hour frontend cache hit with an unchanged session signature, \_getMeasuredWorktrees returned \_withCleanupState(this.\_lastMeasuredWorktrees, minimumAgeDays) synchronously, so changing the Untouched For filter only recomputed local state and made no host calls.  
**Changed behavior:** The cache-hit branch now calls refreshPendingCleanup for every archived entry. That method waits for all queued \_measureSessionWorktree calls, which invoke sessionWorktreeCleanup(false) and then sessionWorktreeExists; BaseAgentHostSessionsProvider implements the latter with resourceResolve RPCs for worktree roots. The editor awaits this before repopulating the table.  
**Confidence:** 0.98 — The before/after cache behavior, age-filter call path, exact RPC implementations, full archived-session cardinality, and concurrency-two serialization are all directly established in changed production code and tests. Only the exact host RTT and typical archived-session count vary by environment.

**Causal diff evidence:** The changed cache-hit return at RIGHT line 372 replaces the deleted local-only \`return this.\_withCleanupState(this.\_lastMeasuredWorktrees, minimumAgeDays);\` with \`return this.refreshPendingCleanup(...)\` over every archived cached worktree.

After an initial scan, changing the Untouched For selector in a history with many done sessions can leave the cleanup table empty/loading for seconds or longer. For example, 100 remote archived sessions require about 200 serialized host requests at concurrency two, regardless of how many sessions the chosen age filter displays; the editor explicitly targets histories up to thousands of worktrees.

**Evidence:** sessionWorktreeCleanupEditor.ts:181-182 calls load() for every age change, and load awaits getWorktrees before its final update. On the valid-cache path at this line, all archived IDs are passed to refreshPendingCleanup. refreshPendingCleanup uses Limiter(2), while \_measureSessionWorktree awaits sessionWorktreeCleanup(false) followed by sessionWorktreeExists. BaseAgentHostSessionsProvider.sessionWorktreeCleanup forwards to connection.sessionWorktreeCleanup, and sessionWorktreeExists awaits connection.resourceResolve for each distinct root. The added test 'rechecks archived existence on cached loads' explicitly establishes that this reconciliation repeats on each cached getWorktrees call.

**Suggested direction:** Preserve the local cache-hit path for age/filter-only loads and reconcile archived existence only on explicit open/force refresh, session lifecycle invalidation, and the existing pending-cleanup poll. If periodic reconciliation is required, cache/coalesce it separately and publish the cached rows immediately rather than awaiting all host requests on the filter-change critical path.

### Scenario 3: Submit and reconcile a bulk cleanup batch

- Critical path: After confirmation, cleanupWorktrees schedules each selected session sequentially. The editor immediately marks rows queued, coalesces progress renders at 100 ms, then reloads and polls pending sessions with exponential delay until completion or the fallback timeout.
- Scaling input: Selected session/worktree count for scheduling; pending archived-session count for each reconciliation poll.
- Effective concurrency: Scheduling remains deliberately serial. Reconciliation uses Limiter(2). Progress rendering is coalesced to at most one render per 100 ms and flushed before reload.
- Cache behavior: Archiving changes the session signature, invalidating the frontend measurement snapshot. Pending outcomes are refreshed rather than negatively cached; removed completion records remain only for the editor lifetime and are cleared on close.
- Mechanism confidence: High: the serial loop, render scheduler, polling limiter, and timeout/backoff are explicit.
- Magnitude uncertainty: Actual cleanup duration and host archive latency vary; the diff does not increase scheduling cardinality or concurrency.
- Expensive boundaries:
  - IPC/network at <code>src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupService.ts:cleanupWorktrees</code>: Archive an active session or request retry cleanup for an archived session; cardinality: One sequential scheduling request per selected session
    - Introduced by diff: false; previous behavior: The same loop already awaited one archive/retry request per selected candidate and stopped on the first failure.; critical-path effect: The scheduling progress notification and reconciliation wait for all selected requests; individual failures no longer abort later requests.
  - IPC/filesystem at <code>src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupService.ts:refreshPendingCleanup</code>: Poll cleanup status and worktree existence for pending sessions; cardinality: One status request plus up to one request per root for each pending session per backoff poll
    - Introduced by diff: true; previous behavior: Polling remeasured disk usage and cleanup status for pending archived sessions, which was generally more expensive than existence resolution.; critical-path effect: Each poll updates rows progressively but does not block unrelated application workflows.
- Verdict: No additional reportable regression: scheduling multiplicity is pre-existing, progress work is newly coalesced, and pending existence checks replace recursive size scans.

### Scenario 4: Render, scroll, resize, select, and update a large cleanup table

- Critical path: Once a snapshot is available, renderRows filters and sorts the full matching collection, updates two WorkbenchTable models, and lays out only viewport-near row templates. Scroll and keyboard navigation recycle those templates.
- Scaling input: All matching worktrees for in-memory filter/sort and selection calculations; only approximately the visible viewport for DOM nodes and cell updates.
- Effective concurrency: Synchronous UI work runs on the renderer thread, but measurement/progress callbacks are coalesced at 100 ms. No subprocess, IPC, filesystem, database, or network boundary occurs in this rendering path after the snapshot is loaded.
- Cache behavior: Stable row signatures skip unchanged cell rendering; storage-only changes rerender the storage cell. Table templates are recycled and disposed with the editor. Full worktree arrays remain editor-scoped and are cleared/replaced with the current snapshot.
- Mechanism confidence: High: model operations and viewport virtualization are explicit and covered by changed tests.
- Magnitude uncertainty: CPU cost of repeated full-array filter/sort depends on collection size, but the tests establish bounded DOM rows at 2,000 items and the previous implementation created a DOM row for every item.
- Expensive boundaries: none found
- Verdict: No reportable regression: full-collection CPU work remains, but the diff materially reduces DOM/rendering cost and retained nodes through virtualization and targeted cell updates.
