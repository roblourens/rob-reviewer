# Performance review: chat: add configurable GPT Live session awareness

[PR #343555](https://github.com/microsoft/vscode/pull/343555) at `5f723718a90725d0123b61b3f0559ff35c8af2fc`

## Findings (1)

### 1. [medium] Avoid rebuilding the full briefing for every streamed response delta

**Finding ID:** `PERF-453B5E31BB95`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/voiceClient/voiceClientService.ts:1515</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** renderer CPU work and temporary arrays/strings created by history extraction, sorting, mapping, and JSON serialization  
**Scaling:** Cost is approximately O(D × (S log S + B + H)), where D is the number of response change events in a streamed turn, S is tracked sessions, B is the serialized briefing size (bounded at 48,000 characters), and H is the full markdown size joined before the 600-character per-turn cap.  
**Outcome:** increased CPU/GC pressure and renderer latency during streamed responses  
**PR causality:** <code>introduced</code>  
**Previous behavior:** GPT-Live context updates compared only the small active-session grounding and did not rebuild a full session briefing or recent conversation on each response change; explicit session-thread extraction happened only when that tool was requested.  
**Changed behavior:** With awareness enabled by default, every context publication now rebuilds the complete bounded briefing before discovering that it is unchanged. The controller's reactive model path publishes context again for response \`onDidChange\` events, including ordinary streaming deltas where completed-only recent turns cannot change.  
**Confidence:** 0.97 — The added unconditional serializer call, the post-serialization deduplication, and the controller's subscription from response \`onDidChange\` to \`\_sendContext()\` are explicit. \`ChatResponseModel\` forwards response value changes through \`onDidChange\`, so multiplicity tracks streaming updates. Exact response sizes and event rates vary, affecting severity but not the repeated-work mechanism.

**Causal diff evidence:** RIGHT line 1515 adds \`serializeGptLiveSessionBriefing(sessionContext)\` to every GPT-Live \`sendSessionContext\` call, and the equality check is only performed after the complete snapshot has been sorted, mapped, JSON-stringified, and size-checked.

While an agent streams a response during BYOK Voice Mode, each response chunk can synchronously rebuild an unchanged multi-session briefing on the renderer thread. Sessions with long prior markdown responses or a large tracked roster cause repeated CPU and temporary-string allocation, increasing GC pressure and risking delayed voice/UI responsiveness throughout generation.

**Evidence:** \`voiceSessionController.ts\` subscribes an autorun to \`lastReq.response.onDidChange\`; when a delta does not create a state transition, its \`else\` branch calls \`\_sendContext()\`. That reaches this added line. \`serializeGptLiveSessionBriefing\` copies and sorts all tracked sessions, maps up to 20, and calls \`JSON.stringify\`; \`getVoiceRecentTurns\`, also newly attached to the active context, filters/maps/joins all markdown for up to three completed responses before slicing each assistant string to 600 characters. During an in-progress response, those completed turns and the briefing normally remain unchanged, but all of this allocation occurs before \`briefing \!== this.\_gptLiveBriefing\` suppresses the send.

**Suggested direction:** Keep immediate active-input grounding, but coalesce or gate briefing reconstruction on meaningful roster/state/pending/focus/completed-turn revisions rather than raw response deltas. Cache the bounded recent-turn representation per completed request, and stop collecting markdown once the 600-character limit is reached so discarded text is never joined.

### Scenario 2: Keep Voice Mode connected while the coding agent streams a response

- Critical path: Chat response \`onDidChange\` invalidates the controller autorun. Non-transition streaming deltas call \`\_sendContext\`, which synchronously builds recent turns and serializes the full briefing on the renderer thread. Only after that can equality suppress the network send.
- Scaling input: Response delta count multiplied by tracked-session snapshot size and full markdown size of up to three recent completed turns.
- Effective concurrency: Updates execute serially on the UI event loop. There is state-transition settling, but the autorun's no-transition branch publishes immediately for ordinary response deltas; there is no awareness-specific debounce before serialization.
- Cache behavior: Exact serialized briefing equality prevents WebRTC sends for unchanged contexts, but the cache is consulted only after rebuilding the snapshot. Completed recent turns are recomputed from model responses on every publication.
- Mechanism confidence: Very high: response changes explicitly feed \`\_sendContext\`, completed-only history remains stable while streaming, and equality occurs after serialization.
- Magnitude uncertainty: Streaming event rate and historical markdown sizes vary by provider and task, so exact frame/latency impact is workload-dependent; the per-delta repeated mechanism is certain.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/voiceClient/voiceClientService.ts:sendSessionContext</code>: Send changed session-briefing revisions over the WebRTC data channel.; cardinality: For unchanged streaming deltas, zero data-channel calls after deduplication, but one full briefing serialization per delta. For meaningful roster/state/completed-turn changes, one full briefing is split into 500-byte sequential sends.
    - Introduced by diff: true; previous behavior: Streaming context publications performed only small active-grounding comparisons; they did not construct a full briefing, and outbound grounding changed only with the active input.; critical-path effect: Repeated local work competes with UI and voice event handling during generation; changed snapshots also synchronously enqueue the outbound chunks.
  - ipc at <code>src/vs/workbench/contrib/chat/browser/voiceClient/voiceSessionController.ts:\_ensureModelLoaded</code>: Acquire or load an unloaded chat model.; cardinality: A needs-input unloaded session can trigger at most one guarded \`acquireOrLoadSession\` per session while a load is in flight.
    - Introduced by diff: false; previous behavior: The same load was already triggered for unloaded needs-input sessions before state scoping.; critical-path effect: Loading is asynchronous and supports pending-state narration; it is not caused or made more frequent by the awareness changes reviewed here.
- Verdict: Reportable medium regression: default-enabled awareness repeatedly rebuilds an unchanged snapshot on a hot response-delta path.

### Scenario 3: Tracked sessions start, complete, request input, or change focus during a long voice connection

- Critical path: Settled agent state, pending-detail, focus, roster, and completed-summary changes rebuild context before narration. Some paths explicitly flush because narration validation depends on current context.
- Scaling input: Effective changed state/roster/focus/completed-turn revisions and serialized snapshot byte size after session and field caps.
- Effective concurrency: State-transition storms are settled in the controller, then a full snapshot is serialized and RTC chunks are sent sequentially. Periodic polling itself sends only when it detects a state change.
- Cache behavior: A changed serialized snapshot advances \`\_gptLiveBriefingRevision\`; identical snapshots are suppressed. There is no delta encoding, so every meaningful change sends the complete bounded roster.
- Mechanism confidence: High for the full-snapshot sends and ordering; remote model retention semantics for appended revisions are not established by repository evidence and were not treated as a finding.
- Magnitude uncertainty: Realistic rosters are often below the 20-session/48,000-character caps, and state settling reduces bursts. Without measured model/session duration, full-snapshot boundary fan-out was not reported separately.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/voiceClient/voiceClientService.ts:sendSessionContext</code>: Append a revisioned complete session snapshot to GPT Live.; cardinality: One complete briefing per effective changed snapshot, split into 500-byte RTC messages; changes are coalesced at the controller's state-settle boundary but not encoded as deltas.

- Verdict: Bounded but potentially sizable network fan-out is introduced. Evidence is insufficient for a separate high-confidence user-visible regression beyond the reported repeated local reconstruction.
