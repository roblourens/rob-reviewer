# Performance review: Add custom agent skill suggestions

[PR #343534](https://github.com/microsoft/vscode/pull/343534) at `243cedb2405a15c0f5ac0d094ea00cec1d0db0ce`

## Findings (1)

### 1. [medium] Cache the customization inventory instead of re-querying providers

**Finding ID:** `PERF-B4454CDDE4A2`  
**Location:** <code>src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptSkillResolver.ts:39</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** extension-host IPC calls, provider-side inventory discovery, full customization-array serialization, and per-call filtering/allocation  
**Scaling:** For each validation, completion, or skill hover, the cost is one full inventory request per matching harness; validation is triggered after every 200 ms editing pause for each open agent model, and provider-change validation fans out across all open models. When no matching harness is active, all matching harnesses are queried concurrently.  
**Outcome:** repeated IPC and inventory work, increased extension-host CPU/I/O, and delayed diagnostics/completion/hover responses while the full inventories are rebuilt and serialized  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, skill language features did not invoke provideChatSessionCustomizations. Existing customization UI consumers cache each provider result and invalidate it only from itemProvider.onDidChange, matching the proposed API lifecycle contract.  
**Changed behavior:** The new resolver directly invokes provideChatSessionCustomizations for every matching descriptor each time resolveAgentFileSkills is called. The new validator calls it on every debounced edit of an agent file with a skills attribute, while completion and hover call it again independently.  
**Confidence:** 0.99 — The diff-introduced direct call, editor validation frequency, IPC forwarding, full-array serialization, provider cache contract, and existing cached consumer pattern are all explicit in repository code. Exact provider latency and users' inventory sizes vary, which affects magnitude but not the repeated boundary mechanism.

**Causal diff evidence:** Added line 39 directly calls itemProvider.provideChatSessionCustomizations inside resolveAgentFileSkills; all three newly added language-feature paths call this resolver, and no cache or in-flight coalescing exists in the new file.

Editing a GitHub Copilot agent that has \`skills\` now causes every 200 ms validation pause to fetch and serialize the complete customization inventory (agents, skills, instructions, hooks, prompts—not just skills) from each matching harness. Extension-backed harnesses cross the main-thread/ext-host boundary, and built-in providers perform collection-wide discovery; diagnostics wait for these calls, with additional calls on completion and hover.

**Evidence:** promptFileContributions.ts ModelTracker validates 200 ms after each content change and validateAll revalidates every open prompt model on provider events. The added validateCopilotSkills path reaches this line with CancellationToken.None. MainThreadChatAgents2 forwards provideChatSessionCustomizations to ExtHostChatAgents2 over IPC, where the entire returned item array is mapped and serialized. The API documentation states the UI calls this provider once, caches the result, and re-queries only after onDidChange; ItemProviderItemSource/PureItemProviderItemSource implement exactly that cache. PromptsServiceCustomizationItemProvider also shows that a call resolves all five customization types and performs collection-wide discovery before this resolver filters for skills.

**Suggested direction:** Cache/coalesce the inventory per descriptor and session resource, return filtered skills from that cache, and invalidate it from itemProvider.onDidChange (and descriptor/session changes). Share that cache across validation, completion, and hover rather than calling the provider directly on each request.

- Scaling input: One full provider request per matching harness for each validation of each open agent model containing skills. Normal typing is coalesced only within the 200 ms delay; provider-change events call validateAll for every open prompt model, and running validations use CancellationToken.None.
- Effective concurrency: Within one skill resolution, Promise.all starts all matching harness requests concurrently with no shared limiter. Separate open-model validations and a new validation started after an earlier one has begun are not coalesced by the new resolver.
- Cache behavior: The new resolver has no positive, negative, or in-flight cache. It ignores the provider's onDidChange-based cache lifecycle and requests the full inventory again on every validation. Existing customization item sources cache by session/provider and invalidate on onDidChange, demonstrating the intended warm-cache behavior.

- Magnitude uncertainty: Exact latency depends on installed matching harnesses, provider implementation, inventory size, and internal filesystem caches; the per-edit uncached boundary and complete-array serialization are certain.

### Scenario 2: Requesting completion inside a GitHub Copilot agent's skills sequence

- Critical path: The completion provider awaits resolveAgentFileSkills and Promise.all over all matching inventories before it can build and return suggestions.
- Scaling input: One complete inventory fetch per matching harness per completion invocation, with allocation proportional to the total customization inventory and then the number of skills/names.
- Effective concurrency: All matching harnesses are queried concurrently for one request. Editor cancellation is forwarded, but there is no sharing with validation, hover, or another completion request and providers may already have performed work before cancellation.
- Cache behavior: Cold and warm requests behave the same in the new resolver: every completion re-queries providers. There is no in-flight coalescing or event-invalidated cache.
- Mechanism confidence: High: the new completion hunk directly calls the resolver and awaits its result.
- Magnitude uncertainty: Completion invocation frequency and provider latency vary, but one uncached full-inventory call per matching harness is established.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptSkillResolver.ts:39</code>: Fetch and serialize complete customization inventories from extension-host providers; cardinality: H IPC calls per completion request, where H is the effective number of matching harnesses after active-harness selection.
    - Introduced by diff: true; previous behavior: No provider boundary existed for skills completion.; critical-path effect: The suggestion list is blocked on the slowest matching provider because Promise.all must settle.
- Verdict: Covered by the reported shared-cache finding; the same introduced repeated boundary delays completion.

### Scenario 3: Hovering a referenced skill in a GitHub Copilot agent header

- Critical path: Hover resolution checks the skill under the pointer and then awaits resolveAgentFileSkills before constructing hover content.
- Scaling input: One complete inventory request per matching harness for each skill hover request; post-fetch matching scans the returned skill array.
- Effective concurrency: Matching harness requests run concurrently within Promise.all. The editor token can cancel cooperative providers, but no result is shared with validation/completion or later hovers.
- Cache behavior: No warm-cache path exists in the new resolver; repeated hovers re-query unchanged inventories despite onDidChange being available for invalidation.
- Mechanism confidence: High: the changed getSkillHover path directly awaits the resolver only when the pointer is over a scalar skill.
- Magnitude uncertainty: Hover frequency is lower than validation frequency, so this is supporting impact rather than a separate finding.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptSkillResolver.ts:39</code>: Fetch and serialize complete provider customization arrays to resolve one hovered skill; cardinality: H IPC calls per hover request.
    - Introduced by diff: true; previous behavior: Skills hovers returned static attribute information and did not cross a provider boundary.; critical-path effect: Hover display waits for all matching harness inventory requests.
- Verdict: No separate finding because it shares the same root cause and bounded cache fix as validation/completion.
