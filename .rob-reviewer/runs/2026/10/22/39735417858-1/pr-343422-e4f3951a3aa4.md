**Relevant issue families:** boundary-fanout, cache-lifecycle, cleanup-lifecycle, repeated-work

### Scenario 1: Submit a turn after disabling a Connector MCP server and then restoring its inherited enablement default.

- Critical path: Turn preparation already awaits MCP reconciliation before the SDK send. Existing listConfigured must complete; after the decision returns to inherited enabled, the changed state can add one required mcp.enable call and server restart before that turn proceeds.
- Scaling input: Number of distinct servers successfully disabled by this host and still awaiting restoration; realistic effective cardinality is the user's disabled Connector servers, bounded by the session's configured MCP inventory.
- Effective concurrency: All reconciliation requests are serialized by \_mcpEnablementSequencer; enable/disable operations within one reconciliation are awaited sequentially. The effective changed cardinality is one enable per previously host-disabled server whose decision has returned to enabled, not one per customization candidate.
- Cache behavior: \_hostDisabledMcpServerNames is populated only after successful disable, checked during desired-state resolution, and deleted only after successful enable. Failed mutations do not corrupt the state, and later warm reconciliations observe the server enabled and issue no further enable call.
- Mechanism confidence: High: changed lines directly gate the existing enable IPC, and the new test proves one disable, one enable, then no repeated enable on a third turn.
- Magnitude uncertainty: MCP startup duration varies by server, but the work is necessary to restore requested functionality and is one-shot per restored server.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_doReconcileMcpServerEnablement</code>: List configured MCP servers.; cardinality: One listConfigured call per already-existing reconciliation; server candidates are processed from that single inventory.
    - Introduced by diff: false; previous behavior: The same reconciliation and listConfigured IPC ran before every prepared turn.; critical-path effect: Awaited during turn preparation before the SDK send.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_enableMcpServer</code>: Enable an MCP server, which restarts its runtime process/connection.; cardinality: At most once for each successfully host-disabled server after its desired state changes back to enabled; the set entry is deleted after success, and observed enabled state suppresses subsequent calls.
    - Introduced by diff: true; previous behavior: The broken path omitted this enable call and left the requested server unavailable; explicitly declared servers already used this same enable path.; critical-path effect: Awaited before the first turn sent after restoration, because the server's tools must be available to that turn.
- Verdict: No reportable regression. The added boundary work is the required restoration behavior, is coalesced by sequencing, and is suppressed after success.

### Scenario 2: Customization enablement changes while an Agent Host session is idle.

- Critical path: The customization event schedules reconciliation asynchronously, so it is off the immediate settings-change critical path. A later turn can queue behind the same sequencer if reconciliation remains active.
- Scaling input: Customization change events and the number of configured MCP servers resolved in each existing reconciliation.
- Effective concurrency: Customization events and turn preflights share one Sequencer, preventing overlapping inventory reads and duplicate runtime mutations.
- Cache behavior: Session-local tracking preserves the origin of a disable across the settings decision being removed. Successful enable invalidates that entry; disposal releases the set with the session.
- Mechanism confidence: High: the changed set membership is only consulted inside the pre-existing reconciliation and does not schedule work itself.
- Magnitude uncertainty: Event bursts could queue existing reconciliations, but this diff neither adds event subscriptions nor increases reconciliation frequency.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:initializeSession onDidChange callback -&gt; \_reconcileMcpServerEnablement</code>: List configured servers and optionally enable the restored server.; cardinality: One inventory read per queued event; the diff adds at most one successful enable per restored host-disabled server, after which the set entry is removed.
    - Introduced by diff: false; previous behavior: The callback already queued the inventory IPC and reconciliation; only the previously missing enable decision is added.; critical-path effect: Off the settings UI's synchronous critical path; may complete before or serialize with the next turn.
- Verdict: No reportable regression. Frequency and concurrency are unchanged, and added work occurs only when needed to restore a server.

### Scenario 3: Refresh Copilot Connectors after MCP customization changes.

- Critical path: Connector refresh already reconciles MCP enablement before connector reconciliation and again after newly discovered names. The first pass may restore a host-disabled server; the second pass observes it enabled and performs no duplicate enable.
- Scaling input: Number of Connector servers that this host disabled and whose enablement decisions were subsequently cleared.
- Effective concurrency: Connector refreshes are coalesced by \_connectorRefresh, guarded against active turns/control operations, and MCP reconciliations are serialized by \_mcpEnablementSequencer.
- Cache behavior: The set acts as one-shot session state. Warm post-refresh reconciliation incurs only O(1) membership checks and no repeated enable IPC.
- Mechanism confidence: High: call ordering, set deletion, refresh coalescing, and sequencer ownership are explicit in the traced code.
- Magnitude uncertainty: Connector/server startup latency is environment-dependent; the diff's call count and one-shot behavior are established.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_doRefreshConnectors</code>: Two existing MCP inventory reconciliations around Connector reconciliation.; cardinality: Existing pre/post refresh inventory calls; no new calls are scheduled by the diff.
    - Introduced by diff: false; previous behavior: Both reconciliation calls already occurred around Connector refresh.; critical-path effect: Awaited on the Connector refresh path.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_enableMcpServer</code>: Enable a previously host-disabled Connector server.; cardinality: One call per restored server; successful completion deletes tracking before the post-refresh reconciliation.
    - Introduced by diff: true; previous behavior: The server remained disabled, so the required enable IPC and restart did not occur.; critical-path effect: Awaited before Connector reconciliation so it sees the requested enabled state.
- Verdict: No reportable regression. The required enable work is bounded and does not duplicate across the two reconciliation passes.

### Scenario 4: Long-lived session with MCP servers disabled and removed or later restored.

- Critical path: Set retention is not on a user-visible critical path; membership checks occur during existing per-server enablement resolution.
- Scaling input: Distinct MCP server names successfully disabled during one session.
- Effective concurrency: All mutations occur through sequenced reconciliation on the session event loop; no concurrent worker or process resource is retained by the set itself.
- Cache behavior: Names remain only until successful re-enable or session disposal. A removed server name can remain for the session lifetime, but the set is bounded by distinct configured server names that the host successfully disabled, rather than turns, events, or history items.
- Mechanism confidence: High for lifecycle and scaling: the set is an instance field and no global/static owner retains the session.
- Magnitude uncertainty: Users could reconfigure servers over a long session, but realistic MCP inventories are small and each retained value is a string; there is no plausible material memory-growth impact.
- Expensive boundaries: none found
- Verdict: No reportable unbounded-retention issue; lifetime and cardinality are session-bounded and small.

**Summary:** Reviewed both changed files and all diff hunks. The production change adds one-shot session state that distinguishes host-disabled servers from SDK-config-disabled servers. It can intentionally cause one existing enable IPC/server restart when a decision returns to inherited enabled, but does not add reconciliation triggers, duplicate work, uncontrolled concurrency, or material retained growth. No performance findings and no qualifying performance-regression fix to record.
