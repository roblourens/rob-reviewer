### Scenario 1: Open the Agents Window or another non-default profile for the first time and instantiate MCP/plugin/tool-set enablement owners

- Critical path: Before each owner can expose enablement state, the migration checks the application-scoped profile marker. On the first owner for an unmigrated non-default profile it synchronously reads/parses the four profile values and corresponding application values, merges them, and updates cached application storage; backend persistence is not awaited. Default-storage profiles return immediately, and subsequent owners only parse the marker and return.
- Scaling input: At most four customization storage blobs, scaling linearly with the number of explicitly stored MCP servers, plugins/identity aliases, session types, tool sets, and tool overrides. The marker check scales with the number of profiles previously migrated; realistic profile counts are small.
- Effective concurrency: One synchronous migration call per delayed service construction. Within a window, the first instantiated owner writes the marker before later owners run, so they take the warm path. Separate windows can race, but each performs at most the same fixed four-key merge and five writes; there is no spawned task or unbounded concurrency.
- Cache behavior: Cold non-default profile: one marker read, up to four profile/application merges, and up to five application writes including the marker. Warm migrated profile: marker parse plus membership check only. Default or use-default-global-state profile: immediate return. There is no negative-cache retry because unreadable values are still marked migrated.
- Mechanism confidence: High: constructor calls, fixed key list, marker guard, parse/merge loops, and storage-service behavior are directly visible.
- Magnitude uncertainty: Exact stored blob sizes and user profile counts vary, but the key count is fixed and enablement data is sparse; there is no evidence of realistically large blobs or enough profiles to make the bounded one-time work user-visible.
- Expensive boundaries:
  - database at <code>src/vs/workbench/contrib/chat/common/customizationEnablementStorage.ts:migrateCustomizationEnablementToApplicationStorage</code>: Read cached profile/application storage and schedule persistence of up to four merged enablement values plus the migrated-profile marker; cardinality: Worst case nine cached reads and five writes once per non-default profile; later owner construction performs one marker read and no write
    - Introduced by diff: true; previous behavior: Owners directly loaded one profile-scoped enablement blob and performed no cross-scope migration or marker write; critical-path effect: JSON parsing and in-memory storage updates are on owner construction; durable database flushing is scheduled by the storage service and not awaited
- Verdict: No finding. The diff adds bounded, one-time cached storage and serialization work needed before authoritative state is read; it does not add network/subprocess work or an unbounded startup operation.

### Scenario 2: Toggle an MCP server or agent plugin while multiple windows/profiles and active agent sessions are open

- Critical path: The originating toggle serializes one sparse enablement map to application storage. External storage events make other windows parse that map and update observables. Active customization scopes debounce recomputation for 50 ms; affected agent sessions then publish changed active-client/customization state through their existing connection path.
- Scaling input: Effective cardinality is the number of open windows that instantiated the relevant service, then the number of live customization scopes/active session clients in those windows. Per-window model work scales with discovered plugins/MCP servers; publication occurs only for active scopes/sessions whose derived state changes.
- Effective concurrency: Storage notifications fan out across windows. Within each active customization scope changes are coalesced by a 50 ms Delayer; session active-client publication is also delayed and suppresses state equal to either backend state or the last publication. Work across separate windows remains independent.
- Cache behavior: Application storage is cached per window and external changes refresh observable mementos. Same-window writes do not feed back into observable memento persistence; external reads do not rewrite storage. No network result cache is added or defeated.
- Mechanism confidence: High: application-scoped memento propagation, active-scope observers, 50 ms debounce, and publication equality checks are explicit in the traced call path.
- Magnitude uncertainty: Users may have varying numbers of windows, sessions, and plugin files, but toggles are explicit and infrequent, only live scopes react, and both customization resolution and publication coalesce bursts.
- Expensive boundaries:
  - database at <code>src/vs/workbench/contrib/chat/common/enablement.ts:EnablementModel global memento</code>: Persist one application-scoped JSON enablement map and distribute external storage changes to other windows; cardinality: One storage write per toggle; one refresh per open window that has instantiated the matching memento
    - Introduced by diff: false; previous behavior: The same toggle wrote one profile-scoped map and notified windows sharing that profile; the diff broadens delivery to all profiles; critical-path effect: The originating UI updates from the local observable immediately; cross-window refresh follows storage propagation
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostActiveClientService.ts:AgentCustomizationScope</code>: Re-resolve and bundle enabled plugin/MCP customizations for a live agent customization scope; cardinality: At most once per 50 ms burst per live scope after observable enablement changes; scopes without active consumers do not exist
    - Introduced by diff: true; previous behavior: Only scopes in windows receiving the profile-scoped change recomputed; application scope lets active scopes in other profiles recompute too; critical-path effect: Runs before that scope publishes its updated customization snapshot, but is off the originating toggle's immediate UI update path
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:ActiveClientEntry</code>: Dispatch updated active-client/customization state to the agent host connection; cardinality: At most one deduplicated/debounced publication per affected active session/client; equal backend or last-published states are skipped
    - Introduced by diff: true; previous behavior: Only sessions in windows receiving the old profile-scoped update published; cross-profile windows retained and published their independent values; critical-path effect: Required before the remote/session host observes the shared switch; it does not block storage or immediate local UI state
- Verdict: No finding. The diff intentionally extends necessary synchronization to active cross-profile consumers, while existing debounce and equality suppression prevent feedback loops and burst publication.

### Scenario 3: Toggle an agent-host tool set or individual tool with multiple windows and sessions open

- Critical path: The service clones and serializes the sparse tool-set state to application storage. Other windows reload the JSON map; each instantiated session-type tool observable recomputes enabled client tools, and active session handlers publish a changed active-client snapshot after their existing debounce/deduplication.
- Scaling input: Per update, serialization scales with stored session types and overrides; recomputation scales with registered tool sets/tools for each observed session type. Cross-window work scales with open windows and live active sessions, not historical sessions.
- Effective concurrency: One write in the originating window, external notifications to other windows, independent recomputation per observed session type, and delayed/equality-checked publication per active session. Rapid changes for a session are coalesced by the existing publication Delayer.
- Cache behavior: Each service holds parsed observable state. External application changes reload once; local state is updated before storage. Empty state removes the key. There is no cache miss retry or retained per-event history.
- Mechanism confidence: High: state cloning/serialization, application listener, full tool derivation, and active-client publication path are directly traced.
- Magnitude uncertainty: Tool counts and simultaneously active windows/sessions vary, but stored overrides are sparse, user toggles are infrequent, and inactive session types do not create active publication work.
- Expensive boundaries:
  - database at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostToolSetEnablementService.ts:\_save</code>: Persist or remove the application-scoped serialized tool-set enablement map; cardinality: One write/removal per explicit toggle; one reload per open window with the delayed service instantiated
    - Introduced by diff: false; previous behavior: The same state was persisted in profile scope and propagated only within that profile; critical-path effect: Local UI state updates before persistence; other-window visibility follows storage propagation
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:ActiveClientEntry</code>: Publish the recomputed tool definitions in SessionActiveClientSet; cardinality: At most one debounced and equality-checked dispatch per affected active session/client
    - Introduced by diff: true; previous behavior: Only sessions in windows receiving the profile-scoped change republished tool definitions; critical-path effect: Required for the agent host to use the new shared tool availability; does not block the toggle handler
- Verdict: No finding. Cross-profile fan-out is bounded by live consumers and the transitive IPC path already coalesces and deduplicates updates.

**Summary:** Reviewed all 16 changed files and the complete performance pass. The only new costs are a fixed four-key, once-per-profile migration and intentional cross-window observable fan-out. Traced storage persistence, filesystem rebundling, and agent-host publication show bounded cardinality, lazy/live-scope reachability, debounce, and equality suppression; no actionable diff-introduced performance regression or qualifying regression fix was found.
