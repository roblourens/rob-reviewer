# Performance review: Agents - Add multi-file diff action to pull request rows

[PR #343468](https://github.com/microsoft/vscode/pull/343468) at `35f52343fb05d087edaddf8e202cea09f4cd9d6b`

## Findings (2)

### 1. [high] Bound remote file loading before opening the multi-diff

**Finding ID:** `PERF-22B6B7E7EDE3`  
**Location:** <code>src/vs/sessions/contrib/github/browser/pullRequestChangesMultiDiffSourceResolver.ts:68</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** GitHub file-content HTTP requests, decoded file bytes, and text models  
**Scaling:** For F changed files, a cold open creates F remote reads for added/removed files and 2F for modified/renamed files; the accepted GitHub limit of 3,000 files therefore reaches roughly 3,000-6,000 unique content requests and models in one aggregate burst.  
**Outcome:** The diff editor's initial display is delayed until all remote models settle, while the burst can saturate the network, exhaust GitHub quota, and create severe memory/GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, the pull-request row had no action that constructed a multi-diff over every remote PR file, so opening the row did not launch this collection-wide set of GitHub content reads.  
**Changed behavior:** The new resolver maps the complete changed-file list to one or two \`copilot-pr\` URIs per file. \`MultiDiffEditorInput.\_createModel\` eagerly calls \`createModelReference\` for both sides of every item and awaits one collection-wide \`Promise.all\`; the \`PRContentProvider\` resolves each unique URI with a direct GitHub contents request.  
**Confidence:** 0.99 — The changed all-files mapping, generic editor's collection-wide \`Promise.all\`, provider's direct per-URI GitHub request, and 3,000-file supported cardinality are all explicit in repository code. Exact latency varies by PR size and network, but the unbounded request count and critical-path wait are not assumptions.

**Causal diff evidence:** RIGHT lines 66-76 newly turn every returned PR file into eager remote model inputs; line 68 constructs each item that the existing multi-diff implementation resolves collection-wide.

Opening or restoring a moderately large PR changes tab can remain blank for a long time and can trigger hundreds or thousands of simultaneous GitHub requests; a new head SHA repeats the cold load because every URI changes.

**Evidence:** Added lines 66-76 map every \`changes.files\` entry to remote \`copilot-pr\` model URIs. \`multiDiffEditorInput.ts:204-254\` maps the entire resource array, starts both model references per item, and waits for all promises before publishing documents. \`extensions/copilot/.../prContentProvider.ts:93-123\` calls \`getFileContent\` for each URI, which reaches \`GET /repos/{owner}/{repo}/contents/{path}\`. The provider has no limiter, and its adaptive fetcher learns throttling per exact pathname only after a response, so unique file paths are not bounded. The added test explicitly models GitHub's 3,000-file response ceiling.

**Suggested direction:** Keep the full resource list but resolve remote models lazily for visible rows, or introduce a shared bounded limiter for \`copilot-pr\` model/content resolution and publish incrementally instead of awaiting every side at once.

### 2. [medium] Reuse the existing case-insensitive PR poller

**Finding ID:** `PERF-5B7D60E19AC8`  
**Location:** <code>src/vs/sessions/contrib/github/browser/pullRequestChangesMultiDiffSourceResolver.ts:118</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Repeated GitHub pull-request and review-list HTTP requests  
**Scaling:** For a mixed-case owner or repository, the extra model polls once per minute for the lifetime of the open editor; each cycle performs a PR GET plus review-list pagination at 100 reviews per page (up to 100 pages), in addition to the session's existing poll.  
**Outcome:** An open changes tab unnecessarily consumes network bandwidth and GitHub quota continuously, with cost growing with tab lifetime and review history size.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The session polling contribution held one shared, case-sensitive model key using the PR identity recorded on the session and coalesced all exact-key polling owners onto one scheduler.  
**Changed behavior:** The new editor URI lowercases owner/repository names, reparses those lowercased values, acquires a model with that different case-sensitive reference key, and starts its own poll loop. When the session identity uses GitHub's permitted mixed casing, this creates a second model instead of sharing the already-polled one.  
**Confidence:** 0.98 — The lowercasing, case-sensitive key construction, existing session poll owner, one-minute cadence, and review pagination are all directly traced. The only magnitude uncertainty is how often recorded GitHub identities contain uppercase characters, which affects severity rather than the mechanism.

**Causal diff evidence:** RIGHT line 118 newly acquires the live model from the lowercased source identity, and line 123 polls it; together with added line 37 this defeats the existing exact-key model/poll coalescing for mixed-case identities.

Opening changes for a session PR such as \`UpStream/Project\#7\` leaves both \`UpStream/Project/7\` and \`upstream/project/7\` models polling every minute until the editor closes, duplicating metadata and potentially multi-page review traffic.

**Evidence:** \`createPullRequestChangesEditorInput\` lowercases owner/repo at added line 37, while added line 118 acquires a model from the parsed lowercase URI and line 123 starts polling it. \`GitHubService.createPullRequestModelReference\` keys \`ReferenceCollection\` with the case-sensitive \`getPullRequestKey\`; the existing \`GitHubPullRequestPollingContribution\` acquires the original session casing and already calls \`startPolling\`. \`GitHubPullRequestModel.\_refresh\` fetches PR metadata and reviews in parallel, and \`getReviews\` paginates 100 reviews per request. The new casing test explicitly exercises \`UpStream/Project\` becoming the same lowercase editor URI.

**Suggested direction:** Normalize owner/repository casing in the shared PR reference-collection key (and related PR model keys), or preserve and resolve the canonical session identity before acquiring the model, so the editor adds a polling reference to the existing model rather than creating another one.

### Scenario 1: Open or restore a pull request changes multi-diff

- Critical path: The editor first waits for PR metadata, merge-base comparison, and the complete changed-file list. It then creates text-model references for every original/modified URI and waits for all of them before publishing the initial document set, so every remote content read is on the initial editor-display critical path.
- Scaling input: F changed files after complete pagination; effective remote-side cardinality K is F for all-added/all-removed PRs and approaches 2F for modified/renamed files. The code accepts complete lists up to GitHub's 3,000-file limit, so K reaches 3,000-6,000.
- Effective concurrency: The comparison and file-list reads run in parallel after the first PR GET; file-list pages are sequential. After resolution, all K model references are launched through nested Promise.all/Promise.allSettled without a shared limiter. The GitHub fetcher's learned throttle is keyed by exact endpoint pathname and is absent for cold unique file paths, so it does not bound this initial aggregate burst.
- Cache behavior: The two PR GETs and file list explicitly use noCache; comparison may use the platform provider's normal ETag behavior. Text models coalesce only identical URIs, but every file side is unique. A still-open editor is warm; closing/reopening may reuse model-service lifetime caching, but a new head SHA changes every URI and is fully cold. Provider failures return empty content that can become a cached model rather than a shared negative cache.
- Mechanism confidence: Very high: the added all-files URI mapping, multi-diff's eager aggregate model resolution, extension provider's direct per-URI GitHub call, and supported 3,000-file cardinality are all directly traced.
- Magnitude uncertainty: Exact latency, response sizes, and how often users open very large PRs vary, but hundreds-file PRs are realistic and the unbounded K-request mechanism is explicit. This uncertainty affects severity, not mechanism confidence.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/github/browser/fetchers/githubPRFetcher.ts:getChanges</code>: Fetch PR details before and after loading, compare base/head to obtain merge base, and paginate changed files.; cardinality: Two PR GETs, one comparison GET, and ceil(F/100) sequential file-list GETs; for 3,000 files this is 33 requests before content loading.
    - Introduced by diff: true; previous behavior: The row had no changes-editor action and did not perform this request sequence.; critical-path effect: All must finish before the resolver returns any multi-diff resources.
  - IPC at <code>src/vs/workbench/services/textmodelResolver/common/textModelResolverService.ts and extensions/copilot/src/extension/chatSessions/vscode-node/prContentProvider.ts</code>: Resolve each \`copilot-pr\` text document through the extension-host content provider.; cardinality: K unique provider resolutions, one per existing file side.
    - Introduced by diff: true; previous behavior: No all-files PR multi-diff was created from this row.; critical-path effect: The generic multi-diff waits for all model-reference promises before publishing documents.
  - network at <code>extensions/copilot/src/platform/github/common/githubService.ts:getFileContentWithToken</code>: Fetch each file side from GitHub's contents endpoint; large-file responses can add a blob request.; cardinality: K content GETs, potentially up to 2K when a contents response requires blob fallback.

- Verdict: Reportable high-severity concurrency burst and boundary fan-out; submitted a finding requiring lazy or bounded remote model resolution.

### Scenario 2: Keep a pull request changes tab open while the PR changes

- Critical path: Minute polling is background work and is off the steady-state display critical path. If head/base changes, the resolver performs a fresh metadata/comparison/file-list sequence; prior resources remain cached while refresh runs, but publishing the new resource set triggers another K-side model load before the updated document set is ready.
- Scaling input: Open-tab lifetime, review count R (100 reviews per page), changed-file count F, and number of head/base updates. Mixed-case owner/repo identities determine whether polling is duplicated.
- Effective concurrency: Exact-case model references share one scheduler and one in-flight refresh. The lowercased editor source defeats that coalescing when the session identity has mixed casing, producing two independent minute schedulers. Each refresh runs PR and paginated-review reads in parallel; changed head/base additionally triggers the changes fetch and later unbounded content load.
- Cache behavior: Unchanged poll results are structurally suppressed and do not refetch the changed-file list. Exact-key model references and refreshes coalesce. Case variants are distinct cache keys. A new commit invalidates all content URIs by SHA, so their model/content cache is cold; refresh failures keep the last successful changes.
- Mechanism confidence: Very high: lowercasing, case-sensitive reference keys, existing session polling ownership, polling cadence, and paginated review reads are explicit and covered by the added mixed-case test.
- Magnitude uncertainty: Mixed-case prevalence and review-history size vary. The duplicate model keys and duplicated minute request sequence are deterministic whenever mixed casing is present.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/github/browser/models/githubPullRequestModel.ts:\_refresh</code>: Poll PR metadata and the complete review list.; cardinality: Per model every 60 seconds: one PR GET plus ceil(R/100) review-list GETs, up to 100 review pages.
    - Introduced by diff: true; previous behavior: The session polling contribution already owned one model/poller under the session's original casing; no lowercased editor model existed.; critical-path effect: Background for an unchanged PR; it drives subsequent refresh when head/base changes.
  - network at <code>src/vs/sessions/contrib/github/browser/pullRequestChangesMultiDiffSourceResolver.ts:refresh and GitHubPRFetcher.getChanges</code>: Reload PR metadata, merge base, and changed files after head/base changes.; cardinality: Once per distinct observed head/base change: two PR GETs, one comparison, and ceil(F/100) file-list pages.
    - Introduced by diff: true; previous behavior: No open changes editor followed head/base updates.; critical-path effect: Off the current view's critical path because cached resources remain, but blocks the updated diff state.
  - network at <code>extensions/copilot/src/extension/chatSessions/vscode-node/prContentProvider.ts:provideTextDocumentContent</code>: Load all file sides for the updated SHA.; cardinality: K newly keyed content requests per distinct head/base update.
    - Introduced by diff: true; previous behavior: No PR changes multi-diff existed.; critical-path effect: Blocks publication of the updated multi-diff document set.
- Verdict: Reportable missing coalescing for mixed-case PR identities; submitted a medium-severity finding. Exact-case identities reuse the existing poller and do not have this duplicate cost.
