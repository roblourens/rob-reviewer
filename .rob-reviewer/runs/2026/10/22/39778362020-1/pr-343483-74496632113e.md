<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** serialization-allocation, boundary-fanout, synchronous-ui-work

### Scenario 1: Render or refresh the Artifacts/References pills for a local, Remote-SSH ambient, or named remote agent-host session

- Critical path: Session metadata/resolution or browser-view changes invalidate derived artifact sections; \`\_buildArtifactSections\` synchronously builds each visible entry before the pill UI can update. The changed \`resourceAuthority\` call is therefore on this render path, but it performs only local URI construction/encoding.
- Scaling input: The effective cardinality is the number of recorded file artifacts/references remaining after metadata partitioning and artifact-section merging. Existing work was already O(all visible artifacts); the diff adds one constant-size root-URI mapping per file entry, so added work is O(file artifacts).
- Effective concurrency: A single synchronous loop processes artifact entries serially; no tasks, IPC, filesystem operations, or network requests are launched by the changed mapping.
- Cache behavior: The derived sections are memoized by the observable graph until metadata, resolution, browser URLs, or related presentation state changes. \`resourceAuthority\` itself is not cached, but its input is a constant root URI and the production mapper only creates a URI and base64-encodes small constant metadata.
- Mechanism confidence: High: the changed line and mapper implementation establish synchronous allocation/serialization per file entry and establish that no boundary is crossed.
- Magnitude uncertainty: The repository does not establish a hard maximum artifact count or measured render duration. Even for larger sessions, the added constant-size encoding is small relative to the existing per-entry parsing, label formatting, action creation, and UI entry construction.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff preserves linear render scaling and adds only small constant local work per file artifact; there is no concrete mechanism for meaningful latency, jank, or memory growth.

### Scenario 2: Click a session file artifact to open or preview it, especially from a Remote-SSH window

- Critical path: The click invokes \`\_openResource\`, then the opener/editor loads the selected URI. For the fixed Remote-SSH case, the URI now reaches the agent-host filesystem provider and its remote read/resolve operations must complete before the editor or media preview can display the file.
- Scaling input: Cost scales with clicks and the selected file's size, not with the number of artifacts. The changed authority selection does not increase per-item fan-out or background concurrency.
- Effective concurrency: One user-selected resource is opened per click. Any provider calls are driven by the selected editor and are not concurrently scheduled across the artifact collection by this diff.
- Cache behavior: The authority is derived synchronously during pill construction. File/editor caching is owned downstream and is unchanged; cold remote opens fetch content, while warm behavior follows the existing file/editor services.
- Mechanism confidence: High: the click handler, opener path, registered agent-host filesystem provider, and \`resourceRead\` implementation establish the boundary and its one-resource trigger.
- Magnitude uncertainty: Exact provider call count and media buffering depend on the selected editor and file type, but the diff changes only routing for one clicked resource and does not duplicate requests.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/common/agentHostFileSystemProvider.ts \`stat\`/\`readFile\`</code>: Resolve/read the selected remote file through the agent-host filesystem provider (\`resourceResolve\`/\`resourceRead\`, with file contents base64-decoded client-side).; cardinality: One selected artifact per user click; the chosen editor may issue a bounded resolve/stat plus content read for that resource. There is no loop over all artifacts and no aggregate burst.
    - Introduced by diff: true; previous behavior: Named remote sessions already used the agent-host provider, and local sessions remained local. In the affected Remote-SSH ambient-session case, the old URI incorrectly targeted the client-local filesystem and failed rather than fetching the remote artifact.; critical-path effect: The selected remote file cannot display until the provider request returns; this is the intended critical-path fetch for opening remote content.
- Verdict: No reportable regression. The newly reached remote boundary in the affected case is necessary to make the requested remote file open, remains user-triggered and single-resource, and does not add avoidable fan-out, serialization, or concurrency.

**Summary:** Reviewed the complete two-file diff and traced both synchronous pill rendering and click-to-open paths. The production change performs a small local URI mapping during entry construction and corrects a single user-triggered remote filesystem route; no high-confidence actionable performance issue or regression fix was found.
