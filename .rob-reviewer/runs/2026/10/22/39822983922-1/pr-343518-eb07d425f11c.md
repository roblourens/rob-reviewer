### Scenario 2: Open the Extensions customization section, render/search its groups, and dismiss the badge

- Critical path: Navigation calls dismissBadge before the pending section render. Rendering reads the cached suggestion set, groups and sorts installed extensions, and updates the virtualized tree. Search continues to use the existing 200 ms delay; the PR adds a third group and suggestion-membership checks.
- Scaling input: O(E × C) suggestion classification plus O(E log E) grouping/sorting for E installed extensions; a non-empty search can perform the pre-existing second grouping pass. Dismissal serializes D identifiers, where D is the cumulative set dismissed by this profile.
- Effective concurrency: All classification, grouping, and tree-model updates are serialized on the UI thread. One extension-change event schedules one immediate render while visible; no subprocess or network concurrency is added.
- Cache behavior: Suggestion classification is cached by the shared derived observable while other badge consumers observe it. The render copies current suggestions into a Set for O(1) group membership. Dismissal skips storage when no new identifier is added, but retained dismissed identifiers are not pruned; expected extension-install history keeps this small enough that no concrete user-visible performance impact is established.
- Mechanism confidence: High: the render and dismissal call order, scan/sort multiplicity, delayed search, and guarded storage write are explicit.
- Magnitude uncertainty: Profiles with extreme long-term extension churn could grow the dismissal array, but no realistic size or demonstrated latency/memory consequence supports a high-confidence finding.

### Scenario 3: Open Agent Customizations management and update contributed-section badges

- Critical path: Editor sidebar creation registers one autorun. It resolves badge observables once per active harness, reads each management section's badge, and re-splices the short section list only when a badge value actually changes.
- Scaling input: O(S) over configured management sections on editor creation or harness change; one O(S) list splice/render for an actual badge transition. S is a small product-defined list, not user history.
- Effective concurrency: Synchronous observable/list work on the UI thread with no asynchronous fan-out. Harness changes serialize through the observable transaction.
- Cache behavior: The outer derived caches the section-to-observable mapping per active harness; each badge observable remains observed only while current. updateSectionBadge compares the prior value and avoids redundant list reconstruction.
- Mechanism confidence: High: the changed autorun, equality guard, list splice, and fixed management-section source are directly visible.
- Magnitude uncertainty: Exact list-render cost is unmeasured, but cardinality is product-bounded and updates occur only on badge/harness changes, not per frame or input event.
- Expensive boundaries: none found
- Verdict: No reportable regression. The work is bounded, change-gated, disposed with editorDisposables, and does not cross filesystem, IPC, database, subprocess, or network boundaries.

### Scenario 4: Show suggestion descriptions in hovers and accessibility help

- Critical path: Hover registrations are created only while a badge is visible and are disposed when the autorun reruns or the widget render store is cleared. Accessibility help performs a one-off suggestion read when explicitly opened.
- Scaling input: Constant work per badge hover target; accessibility help may perform one O(E × C) in-memory scan if no observer currently caches suggestions.
- Effective concurrency: Synchronous UI work only; no queues or parallel operations.
- Cache behavior: Hover disposables are scoped to MutableDisposable/reader.store. The accessibility read uses the derived value, which is cached when observed elsewhere and otherwise intentionally computes once without retaining dependencies.
- Mechanism confidence: High: lifecycle ownership and one-off read sites are explicit in the changed code and observable implementation.
- Magnitude uncertainty: The accessibility command is infrequent and installed-extension counts vary, but there is no evidence of a hot repeated invocation.
- Expensive boundaries: none found
- Verdict: No reportable regression. No leak, repeated hot-path work, or boundary operation is introduced.
