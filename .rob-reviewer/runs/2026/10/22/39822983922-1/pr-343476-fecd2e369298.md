# Performance review: agentHost: support Git branch naming settings

[PR #343476](https://github.com/microsoft/vscode/pull/343476) at `fecd2e36929828cfd12bfaa21d921ef8112fdc1a`

## Findings (1)

### 1. [medium] Defer random branch preparation for folder sessions

**Finding ID:** `PERF-BD8ACD5CAA5F`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:8055</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Extension-host command IPC, Git subprocesses, repository filesystem discovery, and cold repository initialization/status work.  
**Scaling:** The cost is paid once per new session first send, including folder sessions that never create a branch. The normal warm path performs one \`git for-each-ref\`; collision retries can perform up to five, while cold/closed repositories add repository-opening work and costs grow with repository/ref size.  
**Outcome:** Increased first-prompt latency and avoidable Git CPU/I/O on sessions that do not need a branch.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A folder-isolated session sent its first prompt without invoking the Git extension for branch naming; branch naming work was only relevant if the user later requested PR creation.  
**Changed behavior:** The first-send path now awaits \`\_prepareRandomBranchName\` whenever the Git settings are enabled and the host advertises the naming property, without checking whether the resolved isolation is \`worktree\`. The production host advertises that property for both folder and worktree isolation.  
**Confidence:** 0.96 — The added await, local-provider command call, Git \`for-each-ref\` implementation, and folder-isolation early return are directly traced. The only magnitude uncertainty is repository state and Git duration; the eager boundary and first-send reachability are explicit and covered by the added first-send tests.

**Causal diff evidence:** The added \`const candidate = await this.\_prepareRandomBranchName(namingResource);\` at line 8055 places Git-extension and Git-subprocess work directly before construction and dispatch of the first chat request; the surrounding added condition does not gate on \`SessionConfigKey.Isolation\`.

With \`chat.agentHost.branchName.useGitSettings\` and \`git.branchRandomName.enable\` enabled, every new folder-isolated local session delays its first prompt on an extension-host round trip and normally one Git subprocess, even when the user never creates a PR. Cold or manually closed repositories can add discovery/opening I/O and compete with an initial status scan, making first-response startup noticeably slower.

**Evidence:** \`\_sendNewSessionRequest\` cannot proceed to \`sendRequest\` until this await completes. For the local provider, \`\_prepareRandomBranchName\` crosses the extension-host command boundary. The new Git command calls \`Model.openRepository(..., true, true)\` and then \`Repository.generateRandomBranchName\`, whose collision check invokes \`git for-each-ref\`; a cold/closed repository can additionally perform repository discovery/opening and schedule a full status. \`WorktreeIsolation.resolveWorkingDirectory\` returns the original folder without creating a branch when \`config\[Isolation\] \!== 'worktree'\`, while its schema creates \`worktreeBranchNamingProperty\` for any Git folder, including folder isolation.

**Suggested direction:** Gate the awaited preparation to sessions whose effective isolation is \`worktree\`. For folder sessions, prepare the candidate only when PR creation is requested, or run/persist it off the first-send critical path with ordering that ensures PR creation waits for that preparation.
