# Performance review: Keep SDK marketplace add progress and errors in quick input

[PR #343509](https://github.com/microsoft/vscode/pull/343509) at `7215dd1d2b3c5608c2d0116876dc50eb21582076`

## Findings (1)

### 1. [medium] Keep dismissed marketplace adds behind the in-flight operation

**Finding ID:** `PERF-79F4A96FFF23`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/actions/chatPluginActions.ts:558</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Agent Host/SDK marketplace add and inventory-list RPCs, plus their retained async handlers  
**Scaling:** Each time a user dismisses a slow add and re-enters Add Marketplace, another provider.add can start while every earlier add is still pending; outstanding remote operations therefore grow linearly with repeated dismiss-and-resubmit cycles.  
**Outcome:** An avoidable burst of concurrent SDK RPC and remote marketplace work, increasing Agent Host load and request latency.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The built-in input resolved before provider.add started, and manageProviderMarketplaces awaited provider.add before returning to its loop, so one action invocation could not expose another Add Marketplace flow while an add was pending.  
**Changed behavior:** onDidHide now resolves promptMarketplaceSource immediately even when its async onDidAccept listener is still awaiting addMarketplace. The caller continues the management loop, calls provider.list, and can expose another add dialog while the prior provider.add remains live.  
**Confidence:** 0.97 — The changed promise lifetime, loop re-entry, provider call chain, SDK RPCs, and absence of a mutation limiter are all directly traced in repository code; only the duration and how often users repeat dismissal are uncertain.

**Causal diff evidence:** Added RIGHT line 558 resolves the outer prompt on hide while the added async accept path at lines 575-576 can still be awaiting provider.add; this new split lifetime is what permits loop re-entry and subsequent adds before completion.

When an SDK marketplace registration is slow, pressing Escape and trying Add Marketplace again can overlap multiple registrations. The concrete provider forwards each add across the Agent Host boundary to the SDK and performs a follow-up marketplace-list RPC; AgentHostManagementService tracks these mutations but applies no limiter, so repeated retries can create a real concurrent RPC burst.

**Evidence:** The changed hide handler disposes the input and resolves at line 558 independently of the onDidAccept handler's \`await addMarketplace(source)\`. \`manageProviderMarketplaces\` immediately \`continue\`s and starts \`provider.list\`; \`AgentHostCustomizationMarketplaceInstallProvider.add\` forwards to \`agentHostService.addPluginMarketplace\`, and \`CopilotAgent.addPluginMarketplace\` performs the SDK add RPC followed by \`listPluginMarketplaces\`. \`\_runMutation\` invokes operations immediately and only records them for shutdown, so it does not serialize overlapping adds.

**Suggested direction:** Preserve dismissal of the UI, but keep the action/provider mutation serialized: do not let the management loop expose another add until the in-flight add settles, or maintain an action-scoped in-flight promise/guard that the next add awaits.
