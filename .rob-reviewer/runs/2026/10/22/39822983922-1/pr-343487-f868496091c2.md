## Findings (1)

### 1. [medium] Avoid full-catalogue rescans from per-session observables

**Finding ID:** `PERF-5E5BDF3F94DB`  
**Location:** <code>src/vs/sessions/contrib/getStarted/browser/getStartedChecklistService.ts:169</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and observable subscriptions across every retained session  
**Scaling:** Each subscribed status, archive, workspace, quick-chat, or automation mutation reruns an O(N) scan of all sessions; a provider refresh/reconnect that updates N cached adapters separately can therefore perform O(N²) property reads. The agent-host cache persists up to 100 sessions per host and the merged catalogue spans providers, so N is realistically large for long-lived users.  
**Outcome:** Increased renderer CPU/GC pressure and delayed Agents-window updates during session catalogue refreshes or bursts of session state transitions.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, checklist tracking did not exist, so session mutations and provider refreshes did not trigger this additional collection-wide scan or attach these per-session observable dependencies.  
**Changed behavior:** The new derived signal loops over the merged session catalogue and reads several mutable observables from every session. Once eligibility is true, the model's lifetime autorun continuously reads this signal, including after the checklist is dismissed or all items are complete and the card can never render again.  
**Confidence:** 0.94 — The changed scan, its lifetime subscription, and the provider's per-adapter refresh behavior are directly traced. Exact milliseconds depend on catalogue size and provider mix, which is reflected in medium severity rather than uncertainty about the mechanism.

**Causal diff evidence:** RIGHT lines 169-181 add the full-session loop and per-session observable reads; RIGHT line 163 introduces the merged-session source consumed by that loop. This entire tracking path is new in the PR.

An initially eligible user who later accumulates many sessions can pay repeated full-catalogue scans for the rest of the window lifetime; host reconnects/full refreshes are the strongest trigger because cached adapters are updated one by one. This can produce avoidable CPU spikes and UI latency even after the checklist has disappeared permanently.

**Evidence:** The added loop reads \`isAutomation\`, \`status\`, \`isArchived\`, \`workspace\`, and \`isQuickChat\` with the same observable reader for every element. \`GetStartedChecklistModel\`'s autorun reads \`\_signals\` whenever \`state.eligible === true\` and has no completed/dismissed stop condition, while \`visible\` merely hides the card when \`allDone\`. In \`BaseAgentHostSessionsProvider.\_refreshSessions\`, cached adapters are updated inside a loop and the aggregate \`onDidChangeSessions\` event is emitted only afterward, so those child-observable writes can invalidate this scan once per adapter rather than once per refresh.

**Suggested direction:** Drive the calculation from the coalesced \`onDidChangeSessions\` event using untracked per-session snapshots, or maintain incremental counts from the event's added/removed/changed sets. Also stop observing each signal once its corresponding item is latched complete (and stop all session observation once the session-backed items are complete), while retaining only the automation/changes observers still needed.
