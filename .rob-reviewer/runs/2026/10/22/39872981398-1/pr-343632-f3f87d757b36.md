## Findings (1)

### 1. [low] Skip isolation updates when the draft already has that mode

**Finding ID:** `PERF-A8B35A17BDDD`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/newChatWidget.ts:1462</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** agent-host resolveSessionConfig RPCs and the associated config serialization/work  
**Scaling:** Adds one serialized agent-host config-resolution round trip for every local draft creation or replacement, including repeated replacements after workspace or harness changes; the work is redundant whenever the fresh draft's seeded isolation already equals the selected environment.  
**Outcome:** Increased local draft creation/replacement latency because the composer awaits the extra RPC before the scenario can complete.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Creating or replacing a local draft performed the provider's normal initial configuration resolution only; NewChatWidget did not issue a second isolation mutation after openNewSession returned.  
**Changed behavior:** After every successful local draft creation, the added await unconditionally calls setIsolationMode for both Local Folder and Local Worktree, even if the provider's freshly resolved config already contains that effective isolation.  
**Confidence:** 0.96 — The added awaited call, its one-per-draft call path, and the downstream resolveSessionConfig RPC are directly traced. Repository provider code proves new drafts are seeded to remembered isolation or worktree, making same-value calls realistic. Exact RPC duration varies by agent host, so severity is low rather than suppressing the mechanism.

**Causal diff evidence:** The added RIGHT line 1462 always awaits provider.setIsolationMode after openNewSession whenever a local isolation environment is selected; there is no equality check against provider.getSessionConfig before this call.

With the opt-in enabled, selecting Local Worktree (the provider's default) or recreating a draft whose seeded isolation matches the current picker choice incurs an avoidable agent-host round trip on the critical path of opening/replacing the draft. This repeats once per workspace or harness-driven replacement.

**Evidence:** BaseAgentHostSessionsProvider.setIsolationMode first waits for the draft config, then \_setTransientNewSessionConfigValues always calls \_refreshNewSessionConfig, which invokes connection.resolveSessionConfig. The provider seeds new local drafts from remembered workspace isolation or defaults to worktree in \_initialNewSessionConfig, so Local Worktree commonly already matches; similarly a remembered folder can match Local Folder. Even in those matching cases this line forces a second serialized resolve after the existing initial resolve.

**Suggested direction:** After the initial config is available, compare the effective isolation with the requested mode and skip the mutation when they match; the safest bounded location is setIsolationMode itself, since it already obtains the resolved config before issuing the refresh.
