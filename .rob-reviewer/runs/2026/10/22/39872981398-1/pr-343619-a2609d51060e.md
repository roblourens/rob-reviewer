## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `.agents/skills/launch/scripts/cleanup/cleanup.ps1:44` (`RIGHT`)  
**Blamed base line:** `.agents/skills/launch/scripts/cleanup/cleanup.ps1:45`  
**Introducing path:** `.agents/skills/launch/scripts/cleanup/cleanup.ps1`  
**Introducing commit:** `7804323acf13ca438f7ab508def63c0a8e85a714`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.94

**Mechanism:** The cleanup owner used a spelling-sensitive argument comparison and could lose the only targeted handle to still-running Electron processes when Windows represented the same temp directory in short versus long form, retaining the process tree and its 1-4 GB working set after the demo session.

**Symptom:** Windows launch sessions could survive cleanup indefinitely, retaining a full Code OSS Electron process tree and gigabytes of memory until manually terminated.

**Fixed behavior:** Cleanup now compares the canonical long form of the expected run directory and each `--user-data-dir` value, so short and long spellings select the launched Code OSS process and allow it to be terminated before deleting the profile.

**Evidence:** The base cleanup required an ordinal-insensitive exact `--user-data-dir=<path>` string match before every Stop-Process. The launcher derives that argument from `$env:TEMP` and returns `runDir`, while cleanup reparses the supplied runDir with GetFullPath; Windows short (8.3) and long spellings can therefore name the same directory without matching. The changed call at cleanup.ps1:44 delegates to a path-aware matcher that expands both spellings with GetLongPathName. If the old predicate misses, no Code OSS child is stopped; the documented cleanup path then attempts recursive deletion while the Electron instance remains live. Repository guidance identifies each instance as consuming 1-4 GB and explicitly requires cleanup.
