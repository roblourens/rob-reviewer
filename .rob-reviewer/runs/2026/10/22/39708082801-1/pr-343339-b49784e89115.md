# Performance review: agentHost: don't block session open on Copilot Connector reconciliation

[PR #343339](https://github.com/microsoft/vscode/pull/343339) at `b49784e891152aceecfbea6153eded35574e365d`

## Findings (1)

### 1. [medium] Serialize prewarm MCP startup after connector reconciliation

**Finding ID:** `PERF-BEEC57057D2B`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:1080</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Concurrent remote MCP server start/restart operations and their network initialization handshakes  
**Scaling:** For every prewarmed chat with Connectors enabled, one connectors.reconcile and one all-server rpc.mcp.list now overlap; both fan across that chat's configured Connector servers, so contention and duplicate lifecycle work grow with connector count and concurrent prewarmed chats.  
**Outcome:** Increased first-turn latency and extra network/process startup load when prewarming sessions with Connectors enabled  
**PR causality:** <code>introduced</code>  
**Previous behavior:** \_finalizeSession awaited reconcileCopilotConnectors before returning, so the unchanged prewarm rpc.mcp.list() ran only after Connector restart and remote initialization had completed.  
**Changed behavior:** Launch now returns while Connector reconciliation is restarting Connector MCP servers. CopilotAgent.\_warmChat immediately invokes launch.session.startMcpServers(), whose implementation calls rpc.mcp.list() specifically to start all lazy MCP servers, without waiting for \_launchConnectorReconcile.  
**Confidence:** 0.94 — The call path and overlap are explicit: launch returns with the reconcile promise pending, \_warmChat immediately starts MCP servers, and startMcpServers has no ordering wait. The exact amount of duplicate runtime work depends on SDK coalescing, so severity is medium, but concurrent expensive lifecycle requests and first-send dependency are established.

**Causal diff evidence:** The added line starts reconcileCopilotConnectors and hands off its still-pending promise, allowing \_finalizeSession to return immediately. The deleted implementation awaited that same reconciliation before returning the wrapper, so downstream prewarm startup could not overlap it.

When a chat is prewarmed with one or more Connectors, the all-server startup RPC races the launch-time Connector restart/remote handshake. The runtime must serialize or repeat overlapping lifecycle work for the same servers; because the first send waits for reconciliation, any resulting contention directly erodes prewarm latency and can delay that first turn.

**Evidence:** reconcileCopilotConnectors calls connectors.reconcile, which restarts Connector servers and waits for its result. CopilotAgent.\_warmChat calls startMcpServers immediately after \_launchProvisional returns, and startMcpServers documents that rpc.mcp.list starts the session's MCP servers. Unlike send, MCP controls, authentication, and refresh, startMcpServers has no \_launchConnectorReconcile wait. Thus prewarming deterministically places these two expensive lifecycle RPCs concurrently for the same session.

**Suggested direction:** Gate startMcpServers on the adopted launch reconciliation before calling rpc.mcp.list (the warm caller already fire-and-forgets this method, so this preserves non-blocking warmChat), then start any remaining lazy non-Connector servers.
