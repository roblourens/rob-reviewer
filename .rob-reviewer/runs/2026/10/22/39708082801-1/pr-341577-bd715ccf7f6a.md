# Performance review: agentHost: reconcile Copilot Connectors in place

## Findings (1)

### 1. [medium] Avoid retrying deferred Connector reconciliation on every turn

**Finding ID:** `PERF-D0CDDC2D1277`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:5595</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Sequential SDK/subprocess RPC calls and repeated MCP inventory/configuration work  
**Scaling:** While a request remains deferred, cost grows with chat turns: each turn can trigger one post-turn attempt and the next send performs another awaited attempt; the same pattern occurs independently for every affected live session.  
**Outcome:** Repeated pre-send latency and ongoing IPC/CPU load, with a slow attempt able to delay a prompt until the 60-second reconciliation timeout.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A Connector change set the existing MCP launch-configuration refresh flag; the next operation replaced/resumed the session once, and the replacement did not retain an unreconcilable request to retry on every later turn.  
**Changed behavior:** The new send path synchronously awaits a retained Connector request, while turn completion also schedules pending requests. Requests are deleted only after result.reconciled is true, so intentional stopped/not-configured/disabled state and permanently unsupported capabilities keep the request pending indefinitely.  
**Confidence:** 0.99 — The call path and persistence are explicit: tests assert stopped/unsupported requests remain pending, the send path awaits refreshConnectors whenever that bit is set, and every turn completion schedules it again. Exact IPC duration varies, but the repeated critical-path work is not speculative.

**Causal diff evidence:** The added await at line 5595 puts refreshConnectors on every send/resume/start preparation path whenever hasPendingConnectorRefresh remains true. The same diff adds scheduling from \_onChatTurnEnded, and \_doRefreshConnectors only deletes the pending map entry when result.reconciled is true.

After an ordinary catalog refresh, a user who intentionally stopped/disabled a Connector—or whose runtime lacks the capability—pays repeated Agent Host/SDK RPCs before each subsequent prompt and again when turns end, even though no relevant state changed.

**Evidence:** For a stopped Connector, one attempt calls mcp.listConfigured before reconciliation, connectors.getCapabilities/getAccount/getStatus, mcp.listConfigured again, then the inventory refresh calls mcp.listConfigured once more; reconcileCopilotConnectors returns reconciled:false and the map entry is retained. Unsupported capability/account cases likewise retain the entry after several RPCs. The added tests explicitly expect pending:true for disabled/unavailable/unsupported/missing-account and stopped-server scenarios, and also verify that the send path retries a pending request before sending.

**Suggested direction:** Retain the request without making it a per-turn retry condition: record the deferral reason and retry stopped-state requests on MCP status/configuration changes or an explicit refresh, retry capability/account negatives when the runtime/session/account changes, and back off transient failures. The send path should await only a newly actionable reconciliation.

### Scenario 2: Sending or resuming a chat with a retained Connector request, including an intentionally stopped Connector or unsupported runtime

- Critical path: Before returning the existing SDK session to send/resume/start preparation, \_refreshSessionConfiguration synchronously awaits refreshConnectors. A deferred request therefore runs before the model request can start.
- Scaling input: Cost repeats with every affected chat turn and every affected live session for as long as the stopped/disabled/unsupported/account-negative condition persists; a turn end can schedule one attempt and the next send can await another.
- Effective concurrency: Work is serialized by the chat queue and one in-session refresh promise. Different chats can retry concurrently. Same-name requests coalesce, but a non-reconciled key is never cleared.
- Cache behavior: Positive reconciliation deletes the matching generation. Stopped/not-configured/disabled, unavailable capability, unsupported account/target, and missing account all retain the same undifferentiated pending key, with no negative-cache invalidation signal or retry backoff.
- Mechanism confidence: Very high: production code and added tests explicitly retain these negative states, retry before send, and schedule pending work after turns.
- Magnitude uncertainty: Individual local RPC latency and the prevalence of intentionally stopped Connector servers are not measured. The repeat count and critical-path placement are certain, and a slow RPC can consume the full timeout.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_doRefreshConnectors</code>: Call mcp.listConfigured, connectors.getCapabilities/getAccount/getStatus, and refresh MCP inventory; cardinality: A stopped-server attempt performs three MCP inventory RPCs plus three Connector RPCs; unsupported variants perform a subset. This recurs per turn while pending.
    - Introduced by diff: true; previous behavior: The next use consumed one MCP launch-configuration refresh by replacing/resuming the session; it did not repeatedly probe the same negative state.; critical-path effect: All calls are sequentially awaited before a prompt can proceed; the attempt is bounded by the new 60-second timeout.
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotConnectors.ts:reconcileCopilotConnectors</code>: Refresh the Connector catalog inside SDK reconcile when the request is actionable; cardinality: At most one reconcile call per pending key/pass; deferred stopped/unsupported cases return before this network-backed operation.
    - Introduced by diff: true; previous behavior: The old next-use path recreated/resumed the session rather than invoking live reconcile on every pending retry.; critical-path effect: When reached, it is also awaited before send and can run until the reconciliation timeout.
- Verdict: Reportable repeated-work regression; one medium-severity finding was submitted.

### Scenario 4: MCP Start or Stop overlapping Connector reconciliation

- Critical path: Start/Stop increments the per-session control count and, when reconciliation started first, awaits the active Connector refresh before issuing the MCP lifecycle RPC. A control already in flight prevents a new reconciliation from starting.
- Scaling input: One wait and one lifecycle RPC per user control operation; operations are additionally sequenced per server name.
- Effective concurrency: Connector reconciliation and MCP controls are mutually ordered within one SDK session, while per-server lifecycle sequencing remains in place. Other chats/sessions are independent.
- Cache behavior: No cache is involved. A Connector attempt is bounded by 60 seconds and pending work remains available after cancellation/deferral.
- Mechanism confidence: High: ordering and timeout are explicit.
- Magnitude uncertainty: Overlap frequency and reconcile duration are unknown; worst-case wait is bounded by the configured timeout.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_runMcpServerControl</code>: Await Connector SDK reconciliation, then invoke mcp.startServer or mcp.stopServer; cardinality: One lifecycle RPC per Start/Stop; no extra lifecycle fan-out.
    - Introduced by diff: true; previous behavior: Start/Stop only used the per-server lifecycle sequencer and did not wait for Connector reconciliation.; critical-path effect: A later control can wait for the current reconciliation, preserving final-state ordering.
- Verdict: No finding: the serialization is an intentional same-session ordering constraint needed to prevent reconciliation from undoing a later control, and realistic overlap evidence is insufficient for a separate performance regression.

    - Introduced by diff: false; previous behavior: The launcher already performed the same reconciliation sequence inline; this PR extracts and shares it.; critical-path effect: Remains on session startup before registration.
- Verdict: No regression on launch; the helper refactor preserves the existing boundary count and map construction.
