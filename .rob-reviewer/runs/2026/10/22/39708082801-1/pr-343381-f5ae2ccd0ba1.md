## Findings (1)

### 1. [medium] Reuse the cached policy expansion for each request

**Finding ID:** `PERF-A73B9C932CB2`  
**Location:** <code>src/vs/workbench/api/browser/mainThreadMcp.ts:242</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** One additional extension-host RPC and policy-value object allocation per HTTP request or redirect hop, plus repeated scans of the full allow/deny policy list.  
**Scaling:** Cost grows as O(R × P), where R is the number of MCP HTTP request/redirect hops and P is the number of configured policy matcher strings; the expensive RPC occurs once per hop whenever at least one policy string references the environment, regardless of URL repetition.  
**Outcome:** Increased per-request latency and lower HTTP MCP throughput, especially when the executing extension host is remote.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The extension host already made one RPC to \`$checkMcpServerAllowed\` per HTTP destination, and the main thread checked the URL locally without another host round trip. This PR also passes the resolved policy values at server start and stores them in \`\_serverPolicyValues\`, so request checks previously had no nested host-resolution boundary.  
**Changed behavior:** Each \`$checkMcpServerAllowed\` invocation now retrieves all policy strings and, whenever any contains an environment reference, synchronously calls back into the extension host via \`$resolveMcpPolicyVariables\` before allowing the fetch to proceed.  
**Confidence:** 0.99 — The changed await, the per-fetch caller, and the start-time cache are directly traced in repository code. The exact milliseconds depend on extension-host placement, but the added serialized boundary and request multiplicity are certain.

**Causal diff evidence:** The added \`await this.\_proxy.$resolveMcpPolicyVariables(values)\` at line 242 is on \`$checkMcpServerAllowed\`, which \`ExtHostMcp.\_fetch\` awaits before every non-auth HTTP request and every redirect hop; the same diff stores start-time \`options.policyValues\` in \`\_serverPolicyValues\` at lines 127-130.

For remote MCP servers under environment-based enterprise policies, every MCP HTTP operation is delayed by an extra serialized extension-host round trip before its network request; remote extension hosts can turn this into an additional remote IPC/network latency per protocol message, reducing tool-call throughput. Redirects multiply the delay.

**Evidence:** \`ExtHostMcp.\_fetch\` calls and awaits \`$checkMcpServerAllowed(this.\_id, currentUrl)\` inside its redirect loop before \`\_fetchInternal\`. The changed handler then awaits a main-thread-to-extension-host RPC whenever the enterprise policy has an environment reference. \`McpServer.start\` already resolves those same values through the selected connection and forwards them in \`start(..., policyValues)\`, and \`MainThreadMcp.start\` retains that object, proving the per-request RPC duplicates available state.

**Suggested direction:** Use the policy values already stored for the server at start for request checks. If policy configuration changes, invalidate or refresh that cache once per server/policy epoch (or resolve only missing newly introduced strings), rather than calling the extension host on every fetch.
