# Performance review: sessions: badge the activity bar Changes entry on unseen changes and show its stats on hover

[PR #343335](https://github.com/microsoft/vscode/pull/343335) at `e7a91f5c9a174b38d6ebec4a62e621e65fd0ebff`

## Findings (3)

### 1. [medium] Reuse one aggregate for activity and hover stats

**Finding ID:** `PERF-F2A47832800D`  
**Location:** <code>src/vs/sessions/contrib/changes/browser/changesActivity.ts:185</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** main-thread iterations over the active chat's complete changed-file array  
**Scaling:** The diff adds two complete O(F) aggregations for each distinct file-edit snapshot (one through \`pillStats\`, one through \`activeChanges\`); over a turn that grows the list incrementally, the added work is O(U×F), approaching O(F²) when U tracks files added.  
**Outcome:** increased main-thread latency and reduced responsiveness during large multi-file agent turns  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR the existing Changes pill/context consumers aggregated their own stats, but there was no activity contribution performing these two additional full-list reductions per active-chat update.  
**Changed behavior:** The new contribution derives display stats and loaded activity stats independently from the same changed-file observable, causing duplicate complete aggregation whenever live file edits change.  
**Confidence:** 0.99 — Both call paths and the collection-wide loop are explicit, and the provider's live file-edit observable proves repeated execution. Only the magnitude varies with turn size.

**Causal diff evidence:** Added line 185 calls \`readLoadedSessionInputPillStats\` in \`activeChanges\`, while added lines 179-182 separately call \`computeSessionInputPillStats\` for the hover. Both reach \`readChatChangesStats\` and \`readFileChangesStats\`, whose loop sums every file.

An agent editing tens or hundreds of files causes two extra complete scans on each changed edit snapshot, adding synchronous CPU on the UI thread exactly while the transcript and Changes UI are updating.

**Evidence:** \`readLoadedSessionInputPillStats\` calls \`readLoadedChatChangesStats\`, which calls \`readChatChangesStats\`; \`computeSessionInputPillStats\` also calls \`readChatChangesStats\`. Both end in \`readFileChangesStats\`'s loop over all changes. Agent-host \`getLastTurnChanges\` is driven by live chat-state file-edit snapshots and feeds the selected changeset, so this runs repeatedly during an active turn, not just once on open.

**Suggested direction:** Create one shared derived result that contains loaded state plus aggregate stats, and derive both badge comparison and hover/cache fallback from it; do not invoke the full-file aggregation independently for \`pillStats\` and \`activeChanges\`.

### 2. [medium] Gate the activity observers on the activity-bar setting

**Finding ID:** `PERF-14CF365F2925`  
**Location:** <code>src/vs/sessions/contrib/changes/browser/changesActivity.ts:167</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** main-thread CPU, temporary objects/serialized bytes, and application-storage updates  
**Scaling:** Cost grows with active-chat change snapshots and changed-file count even when \`sessions.showSessionActivityBar\` is false; when Changes is visible it additionally grows with the persisted history (up to 200 chats) per snapshot.  
**Outcome:** background CPU/GC pressure and storage churn for a disabled feature  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no changes-activity contribution, no seen-state storage, and no additional stats observers when the Session Activity Bar was disabled.  
**Changed behavior:** Every desktop Agents window now observes active-session file-change snapshots and maintains seen state regardless of whether the Session Activity Bar is enabled or visible.  
**Confidence:** 0.98 — The setting default and CSS-only visibility gate are explicit, and the new unconditional autoruns and storage path are directly traced. Exact milliseconds depend on turn size and update rate, which affects severity but not the mechanism.

**Causal diff evidence:** The new contribution's only early gate is the desktop-layout check at line 167; after it, the diff unconditionally installs \`activeChanges\`/badge autoruns, the persisted seen store, and the custom hover stats observer. The activity bar itself merely hides via \`sessions.showSessionActivityBar\`, whose stable-build default is false.

On stable builds, where the activity bar defaults off, active agent turns that stream file-edit snapshots still perform full file-list aggregation and may persist seen state while the user watches Changes, adding main-thread work and GC/storage traffic with no visible feature.

**Evidence:** \`ChangesActivityContribution\` is registered AfterRestored and only checks \`AgentWorkbenchLayout.Desktop\`. Its autorun calls \`readLoadedSessionInputPillStats\`, and the registered view item observes \`pillStats\`; both aggregate the active file list. If the Changes editor is visible, the same autorun calls \`SeenChangesStore.set\`, which clones/serializes the history and writes application storage. The setting is checked only by \`SessionActivityBar\` when toggling CSS visibility, so these observers remain live while it is off.

**Suggested direction:** Tie these observers and the seen-store/view-item registration to an observable \`sessions.showSessionActivityBar\` lifetime (dispose them when disabled and recreate/seed the current baseline when enabled), rather than gating only on desktop layout.

### 3. [low] Coalesce seen-state serialization before writing storage

**Finding ID:** `PERF-716CA5968748`  
**Location:** <code>src/vs/sessions/contrib/changes/browser/changesActivity.ts:103</code> (<code>RIGHT</code>)  
**Performance category:** <code>gc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Map/array/object allocations and JSON bytes for up to 200 chat entries, plus queued application-storage database updates  
**Scaling:** While the Changes editor is visible, every distinct stats snapshot rebuilds and serializes H history entries, for O(U×H) allocations/bytes with H capped at 200; the storage layer coalesces physical updates on a 100 ms delay but cannot avoid the caller's per-update clone and JSON serialization.  
**Outcome:** avoidable main-thread CPU/GC pressure and bursty persisted-state I/O during live edits  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no per-chat seen-state history and no serialization/storage write tied to live change-stat updates.  
**Changed behavior:** Watching the Changes tab during an agent turn now clones the history map, maps all entries to new objects, JSON-serializes it, and schedules application-storage persistence for every changed stats value.  
**Confidence:** 0.98 — The caller condition, full-history serialization, and storage coalescing semantics are directly traced. Snapshot frequency and URI lengths vary, so severity is low rather than suppressing the proven mechanism.

**Causal diff evidence:** Added line 103 serializes and stores the entire bounded map on every \`SeenChangesStore.set\`; the new autorun calls \`set\` whenever \`activeChanges\` updates while \`isViewing\` is true.

With a populated history, live edit snapshots while Changes is open repeatedly allocate and stringify the same mostly unchanged history, increasing GC and potentially causing small UI stalls; sustained updates also keep scheduling database flushes.

**Evidence:** \`activeChanges\` depends on the live changed-file list. Its autorun unconditionally calls \`seenChanges.set\` while the matching Changes editor is visible. A changed insertion/deletion count bypasses the equality fast path, after which \`set\` clones the map and serializes all entries. \`Storage.set\` updates its cache synchronously and only coalesces the eventual database flush, so the allocation/serialization remains per snapshot.

**Suggested direction:** Update the in-memory observable immediately, but debounce/coalesce serialization at the store boundary and flush the latest snapshot on the existing save-state/shutdown lifecycle (or on leaving the viewed chat), preserving durability without serializing every intermediate count.
