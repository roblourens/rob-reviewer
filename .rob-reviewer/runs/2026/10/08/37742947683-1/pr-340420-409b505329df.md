## Findings (1)

### 1. [medium] Defer per-repository eligibility reads until the picker opens

**Finding ID:** `PERF-C9DE59E79315`  
**Location:** <code>src/vs/sessions/contrib/automations/browser/automationDialog.ts:2184</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub REST repository metadata requests  
**Scaling:** One REST request per uncached GitHub recent-workspace row: up to 10 with the default unified picker, and potentially more when the legacy uncapped picker setting is used; five execute concurrently and refresh/account invalidation causes the burst to recur.  
**Outcome:** excessive network I/O and avoidable contention for user-requested cloud data  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, constructing the automation dialog did not install an eligibility observer or perform per-row repository visibility requests; workspace-picker rows were built locally and no GitHub metadata calls occurred merely because the dialog opened.  
**Changed behavior:** Constructing any automation dialog with cloud configuration now enumerates all recent GitHub workspace rows and starts an eligibility lookup for each one, even while the workspace picker remains closed.  
**Confidence:** 0.98 — The call path is direct: renderForm calls setCloudConfiguration, its autorun executes synchronously, and each uncached getWorkspaceTarget queues client.query.getRepository. The shared picker caps the default unified list at 10 rows and the new store caps concurrency at five, so the exact common-case burst is bounded but real; only the number of users with a full GitHub recent list and network duration are uncertain.

**Causal diff evidence:** RIGHT lines 2182-2188 add an autorun in setCloudConfiguration that immediately calls super.\_buildItems() and invokes getWorkspaceTarget(...).read(reader) for every GitHub row; renderForm calls setCloudConfiguration during dialog construction at RIGHT line 1264, before the workspace picker is opened.

Opening the create/edit composer can launch up to ten unnecessary GitHub REST requests (five concurrently) before the user opens the workspace picker or chooses Cloud. On constrained connections these interactive-priority calls consume bandwidth/rate limit and compete with automation refresh and the tool-catalog request, slowing the cloud options the user actually uses.

**Evidence:** AutomationsWorkspacePicker.setCloudConfiguration loops over super.\_buildItems() and reads every GitHub target. CloudAutomationStore.configuration delegates each read to GitHubCloudAutomationStore.getWorkspaceTarget; on a cache miss that method queues a client.query.getRepository REST request. Repository reads use interactive priority. The default unified picker exposes up to 10 recent rows, while targetEligibilityLimiter permits five simultaneous requests. None of these row checks is needed to render the closed picker.

**Suggested direction:** Keep the selected workspace eligibility read needed for session-type validation, but defer enumeration/checking of other rows until showPicker (and the existing mobile readiness path) actually opens the workspace picker; cancel or stop observing row checks when it closes while retaining completed per-account cache entries.
