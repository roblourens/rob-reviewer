# Performance review: sessions: add cloud automation cards and run history

[PR #340434](https://github.com/microsoft/vscode/pull/340434) at `346df6a794e890e6840519b36526e1bd03cdbaf8`

## Findings (2)

### 1. [high] Poll only definitions that can change

**Finding ID:** `PERF-CAC368A8917B`  
**Location:** <code>src/vs/sessions/contrib/providers/copilotChatSessions/browser/cloudAutomationStore.ts:203</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub REST requests and the shared cloud-store operation sequencer  
**Scaling:** Each scheduled tick calls refreshHistory(), which issues one listRuns request for every cached definition and then task-detail requests for every active task returned. Cost is O(D + A) per tick for D definitions and A active tasks, every 15 seconds while any one run is active; definition reads allow up to 1,000 definitions per repository and remembered repositories are not capped.  
**Outcome:** excessive network traffic and increased latency for run, stop, update, and delete operations queued behind the poll  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, the catalogue-wide history fan-out ran only during explicit/initial refresh; one active run did not repeatedly reread every unrelated definition.  
**Changed behavior:** The added scheduler repeatedly invokes the existing catalogue-wide history refresh whenever any run is pending/running or discovery attempts remain.  
**Confidence:** 0.99 — The timer trigger, all-entry mapping, concrete REST methods, concurrency limit, catalogue bounds, and shared sequencer are directly traced. Only the prevalence of very large catalogues is uncertain; the regression already scales poorly for realistic catalogues of dozens.

**Causal diff evidence:** The added condition at line 203 schedules another 15-second refresh based on a single active run; the scheduler callback added at lines 44-48 invokes refreshHistoryInBackground(), moving the pre-existing all-definition fan-out onto a recurring path.

With dozens of cloud automations and one active run, every tick sends dozens of REST calls at concurrency 4. GitHubCloudAutomationStore serializes refreshHistory and mutations through the same Sequencer, so a long poll also delays user-triggered run/stop/update actions; the new post-dispatch discovery performs the same full fan-out immediately plus four more ticks.

**Evidence:** CloudAutomationStore schedules this path whenever runs contains any pending/running item. refreshHistory() in GitHubCloudAutomationStore maps every cachedEntries entry to client.automations.listRuns(...), limits only concurrency to 4, and performs client.tasks.get for active tasks. Both refreshHistory() and mutate() use this.operations.queue(), proving contention with mutations. listDefinitions permits ten pages of 100 definitions per repository, while persisted repositories have no cap.

**Suggested direction:** Keep the active/discovery set by automation ID and refresh only definitions with active cached runs plus the definition just dispatched/stopped. Remove IDs when their runs become terminal; retain a separately bounded/manual full-catalogue refresh for reconciliation.

### 2. [medium] Avoid one tree widget per interleaved run block

**Finding ID:** `PERF-D376B129475E`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/automationsView.ts:1394</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** WorkbenchObjectTree instances, SessionItemRenderer objects, DOM nodes, event listeners, and synchronous layout work  
**Scaling:** For an alternating sequence of cloud and native runs in one date group, the new segmentation creates O(B) SessionsFlatList/WorkbenchObjectTree instances where B can approach the number of native runs; before the PR there was one list instance per date group.  
**Outcome:** higher synchronous render/layout latency and retained UI memory when opening or updating mixed run history  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous group representation owned one listContainer and lazily created at most one SessionsFlatList for all native session rows in that date group, with temporary rows rendered separately.  
**Changed behavior:** updateGroupRuns now splits native sessions at every external row and calls createSessionList for each contiguous native block.  
**Confidence:** 0.97 — The one-tree-per-block behavior and constructor cost are explicit, and tests intentionally cover multiple segmented lists. Exact render time depends on history composition and hardware, so severity is medium rather than high.

**Causal diff evidence:** The added block at line 1394 calls createSessionList(entry.runsContainer) inside the per-block traversal; deleted code in createGroup/ensureGroupList maintained a single entry.list for the entire date group.

A realistic mixed history with many interleaved local and cloud runs constructs dozens of independent tree controls. Each SessionsFlatList creates a SessionItemRenderer and a WorkbenchObjectTree with service wiring and listeners, so history opening and polling updates become substantially heavier than rendering the same rows in a single control.

**Evidence:** The new loop changes listKey after every non-session row and creates a SessionsFlatList whenever that keyed block is absent. SessionsFlatList's constructor synchronously creates SessionItemRenderer, SessionsTreeDelegate, WorkbenchObjectTree, DOM, and multiple listeners. Cloud history can contribute up to 50 rows per definition, making alternating blocks realistic and not a fixed small count.

**Suggested direction:** Represent the date group with one mixed list/tree (custom elements for external rows and session elements for native rows), or use a lightweight shared session-row renderer so ordering does not require a separate WorkbenchObjectTree for every contiguous native block.
