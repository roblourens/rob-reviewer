# Performance review: Restore canvases closed by session and chat switches

[PR #340465](https://github.com/microsoft/vscode/pull/340465) at `85b5641b58db76006c4fb63b7a819ab145b3ea3c`

## Findings (1)

### 1. [high] Bound suspended canvas BrowserViews

**Finding ID:** `PERF-6C9210BD55B8`  
**Location:** <code>src/vs/sessions/contrib/canvases/electron-browser/sessionCanvasService.ts:287</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Live Chromium WebContentsView instances together with their renderer page heaps, DOM, JavaScript state, and BrowserView model/listener objects.  
**Scaling:** Retention grows by one heavyweight WebContents/page for every distinct admitted canvas the user opens across sessions or chats. There is no count, byte, or age bound; cleanup requires explicit dismissal, membership/source removal, archive/deletion, service disposal, or reload.  
**Outcome:** A long-lived Agents window can accumulate substantial retained memory and GC pressure as the user visits canvas-bearing sessions, eventually degrading responsiveness or exhausting memory.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The editor pane owned the model in a registered MutableDisposable; closing/disposal during a working-set switch cleared that disposable, and BrowserViewModel.dispose() destroyed the native BrowserView/WebContents.  
**Changed behavior:** The canvas service now stores each created IBrowserViewModel on a long-lived presentation. A working-set suspension only marks that presentation closed, so switching sessions/chats leaves the model retained for later reattachment.  
**Confidence:** 0.97 — The ownership transfer, switch-time retention, native WebContents allocation, and destroy-on-model-dispose behavior are directly traced in code and covered by new retention tests. Exact per-page memory and how many canvases typical users visit are uncertain, but the linear unbounded mechanism is not.

**Causal diff evidence:** This diff removes the pane-owned registered \`MutableDisposable&lt;IBrowserViewModel&gt;\` and its \`browserModel.clear()\` disposal, then adds \`presentation.model = model\` at RIGHT line 287 and intentionally preserves that presentation when a working-set switch disposes its input.

Opening canvases in many sessions/chats and switching away from each leaves all of their Chromium pages alive even though only the current owner is visible. Unlike before the PR, ordinary session/chat switching no longer releases those page heaps.

**Evidence:** The added assignment at line 287 roots the model in \`\_presentations\`. Suspension paths at lines 394-400 and 553-558 retain the presentation and only set \`opened = false\`; tests explicitly expect the interrupted/service-owned model not to be disposed and reattached later. \`WebContentsViewHost\` detachment only calls \`model.setVisible(false)\`, while \`BrowserView.setVisible\` merely calls Electron \`WebContentsView.setVisible\`; actual renderer destruction occurs only from \`BrowserViewModel.dispose()\` via \`destroyBrowserView\`. The service has disposal on dismissal/removal/source replacement/shutdown but no retention budget for suspended presentations.

**Suggested direction:** Keep models for the active owner, but add an explicit bounded suspended-model policy (for example, an LRU/count or memory budget) and dispose evicted BrowserViewModels so older canvases reload on return. Apply eviction when presentations become suspended, while preserving the current cleanup and restore ordering.
