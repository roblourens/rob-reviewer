# Performance review: sessions: configure external session application badges

[PR #340487](https://github.com/microsoft/vscode/pull/340487) at `8a403ac6bbf55612b214d9ab991ec7eab1efbad2`

## Findings (1)

### 1. [low] Create application badges only when they can be shown

**Finding ID:** `PERF-CCE25A7F6081`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:1359</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** DOM nodes, DOM event listeners, and per-row reactive computations  
**Scaling:** The added template work grows linearly with every simultaneously rendered session row; Automations history sizes each date-group SessionsFlatList to its full content height, so all N historical runs render rather than only viewport rows.  
**Outcome:** Increased synchronous view-render latency and retained DOM/listener memory for long session or automation histories.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, session-row templates did not allocate application-badge DOM, badge mouse listeners, or a badge autorun.  
**Changed behavior:** Every SessionItemRenderer template now eagerly appends two badge spans and installs mouseenter/mouseleave handlers, and every rendered row later gets the badge autorun, even when the new setting is at its default Off value or the session is ineligible/internal.  
**Confidence:** 0.94 — The eager allocations and listeners are directly visible in the changed template code, and the full-history rendering path is explicit in Automations history. Actual user history lengths vary, which limits severity, but not confidence in the linear mechanism or critical-path reachability.

**Causal diff evidence:** Added line 1359 unconditionally appends \`.session-external-application-badge\` for every row template; adjacent added lines 1361-1366 add another span and two listeners regardless of badge mode or eligibility.

Opening Automations with a long run history now synchronously creates and retains 2N hidden badge DOM nodes, 2N listeners, and N reactive computations although badges are default-off. Automations history explicitly lays each group out to its full content height and the run projection has no client-side limit, so months of runs can make this extra work scale into slower view opening and higher memory use.

**Evidence:** The changed renderTemplate lines unconditionally append the title badge and its label and register two listeners. renderSession also unconditionally adds the badge autorun. In automationsView.ts, layoutSessionList uses getContentHeight() and calls list.layout(height, width), while SessionsFlatList.getContentHeight() sums every row, making the tree render all history rows; AgentHostAutomationStore.\_projectRuns() projects all catalog runs without a client cap.

**Suggested direction:** Keep the stable row template lightweight and lazily create/dispose the title badge and its hover handling from the badge autorun only when an eligible row is in Title mode (or delegate hover handling at the list container), so Off/ineligible rows retain no badge-specific DOM or listeners.
