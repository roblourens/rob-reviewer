# Performance review: Show a language-status warning for diagnostic highlight limits

[PR #337719](https://github.com/microsoft/vscode/pull/337719) at `4cd345d3d7726ea5283700f92da5541fa9bf3f76`

## Findings (1)

### 1. [medium] Keep the default diagnostic decoration cap at 500

**Finding ID:** `PERF-0101E078E610`  
**Location:** <code>src/vs/editor/common/services/markerDecorationsService.ts:147</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** model decoration objects, interval-tree nodes, Set allocations, and UI-thread CPU work  
**Scaling:** Per affected model and marker update, comparison and creation scale with the capped diagnostic count, increased from O(min(n, 500)) to O(min(n, 5000)); retained decoration state likewise increases by up to 4,500 objects/nodes per loaded model.  
**Outcome:** increased synchronous latency and dropped frames, plus higher retained memory and GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The service read and decorated only the first 500 diagnostics per loaded model, bounding synchronous diff/insertion work and retained decoration state at 500.  
**Changed behavior:** Marker changes and model creation now eagerly materialize, interval-tree insert, retain, and compare as many as 5,000 marker decorations per loaded model rather than 500.  
**Confidence:** 0.99 — The changed limit and call path are explicit: \`MarkerService.onMarkerChanged\` reaches \`\_updateDecorations\`, \`update\` allocates Sets over the full capped collection and \`deltaDecorations\` synchronously creates interval nodes. The PR body also measures \`\_updateDecorations\` rising from 11.34 ms to 29.01 ms normally and from 21.20 ms to 70.01 ms under 4x throttling. Only trigger prevalence is uncertain; the supplied multi-provider example establishes a realistic way to exceed 500.

**Causal diff evidence:** RIGHT line 147 introduces \`MAX\_MARKER\_DECORATIONS\_LIMIT = 5000\`, and RIGHT line 122 uses that value to read and pass up to 5,000 markers into \`MarkerDecorations.update\`; the deleted implementation read only 500.

A large/generated file receiving diagnostics from several providers can block the editor UI for multiple frames whenever diagnostics are initially published or republished, with additional CPU/GC pressure and up to ten times as many retained decoration nodes even for non-visible loaded models.

**Evidence:** \`MarkerDecorationsService\` subscribes globally to marker changes for every loaded text model. \`\_updateDecorations\` reads up to the new cap and \`MarkerDecorations.update\` constructs two Sets over the collection, creates a decoration option/range per addition, and calls synchronous \`ITextModel.deltaDecorations\`, whose implementation inserts interval-tree nodes. The cap is not visibility-aware, so hidden loaded models also retain the extra nodes. The PR's benchmark documents 5,000-marker update medians of 29.01 ms on an M2 and 70.01 ms at 4x slowdown versus 11.34/21.20 ms at the old 500 cap.

**Suggested direction:** Keep the decoration cap at 500 and detect overflow with \`take: 501\`; the new status warning can still report that existing cap. If raising the cap is required, make it explicitly configurable/opt-in rather than multiplying the default synchronous rendering budget.

<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, eager-work, repeated-work

### Scenario 1: Publish or republish aggregate diagnostics above the old 500-decoration limit for a large loaded file.

- Critical path: After diagnostics reach \`MarkerService\`, its microtask event synchronously invokes \`MarkerDecorationsService.\_updateDecorations\`; reading, Set diffing, range/option creation, interval-tree insertion, and decoration-change notification must complete on the renderer/UI thread before the editor can finish reflecting the diagnostics. The work is therefore on the visible editor's critical path, and also runs for loaded background models.
- Scaling input: Aggregate diagnostics for one loaded resource after provider-level caps and before decoration truncation. The supplied scenario reaches 6,000 from six collections of 1,000; effective processed cardinality is 5,000 plus one overflow probe, not 6,000.
- Effective concurrency: Extension-host diagnostic collection updates arrive through IPC and are handled serially on the main/UI thread. \`MicrotaskEmitter\` can merge marker resources fired within one main-thread turn, but separate collection IPC messages can each trigger an update; there is no limiter or deferred chunking for decoration creation.
- Cache behavior: There is no decoration cache beyond retained marker identity and the per-model decoration map. On a cold publication, up to 5,000 decorations are created. On warm updates where the first 5,000 marker objects are unchanged, \`update\` still reads the collection and allocates/scans two Sets of up to 5,000 entries before avoiding \`deltaDecorations\`; overflow state is coalesced and emits only on threshold transitions.
- Mechanism confidence: Very high: the changed cap, marker event call path, synchronous interval-tree implementation, and benchmark deltas are directly evidenced.
- Magnitude uncertainty: The exact prevalence of files with more than 500 aggregate diagnostics from several providers is uncertain. The mechanism and cost are not: the supplied reproduction uses six providers, and the PR reports median update time increasing to 29.01 ms normally and 70.01 ms under 4x slowdown.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/common/extHostDiagnostics.ts DiagnosticCollection sync and src/vs/workbench/api/browser/mainThreadDiagnostics.ts\#$changeMany</code>: Serialize and transfer diagnostic batches from the extension host, revive marker fields, and call \`MarkerService.changeOne\`.; cardinality: One existing \`$changeMany\` IPC call per diagnostic collection synchronization; in the PR's realistic six-collection example, six collection \`set\` operations can produce six IPC calls, each carrying up to the existing 1,000-per-file provider cap. Downstream effective decoration cardinality grows until capped at 5,000.
    - Introduced by diff: false; previous behavior: The same IPC calls and payload caps existed, but each resulting loaded-model decoration update read, compared, created, and retained at most 500 marker decorations rather than 5,000.; critical-path effect: IPC delivery precedes the changed synchronous marker decoration update. The PR does not add IPC calls, but it multiplies the UI-thread work performed after each delivered update.
- Verdict: Reportable medium-severity regression: the default cap increase multiplies synchronous UI-thread work and retained decoration state by up to 10x and measured updates exceed a frame budget. Keeping the prior cap while reading one extra marker preserves the new overflow warning.

### Scenario 2: Switch editors/models or toggle validation visibility while the diagnostic-limit warning is active.

- Critical path: Active-editor/model/configuration changes synchronously query the current overflow boolean and may add or remove one language-status item. This constant work is on the editor-switch/configuration path but does not traverse or recreate marker collections.
- Scaling input: Number of active editor switches/model switches and validation-visibility configuration changes; marker count does not affect this reporter path after overflow state has been computed.
- Effective concurrency: Synchronous and serialized with active-editor events; there is one lazy reporter per instantiated editor and one active language-status listener. No queue, parallelism, or burst was found.
- Cache behavior: The reporter reads overflow state from the existing per-model decoration object in O(1). Its \`\_limited\` field suppresses unchanged notifications, and \`LanguageStatusEntry\` retains one listener/status disposable for the active editor only.
- Mechanism confidence: High: registration is lazy, access is a map lookup, and events are threshold-filtered by both the marker service state and reporter state.
- Magnitude uncertainty: None material; operations are constant-time aside from normal status-service notification fan-out.
- Expensive boundaries: none found
- Verdict: No reportable regression: the new status reporter is lazy, bounded, disposed, and performs constant work without new IPC, filesystem, database, network, or subprocess boundaries.

### Scenario 3: Open or retain multiple text models that already have high aggregate diagnostic counts.

- Critical path: Model addition synchronously constructs \`MarkerDecorations\` and calls \`\_updateDecorations\`; opening a model with existing diagnostics must create the decoration nodes before model-add handling completes. For already loaded background models, marker changes perform the same work off the visible editor's immediate paint path but still occupy the shared UI thread.
- Scaling input: Number of loaded models multiplied by effective diagnostics per model, now capped at 5,000 rather than 500.
- Effective concurrency: All model-add and marker-change decoration updates are serialized on the UI thread. A multi-resource marker event loops resources sequentially; there is no concurrency burst or backpressure.
- Cache behavior: Marker and decoration state is retained per loaded text model; reopening reconstructs decorations from the in-memory marker service. There is no visibility-aware cache or lazy creation, so hidden loaded models retain their full capped decoration maps until model removal.
- Mechanism confidence: High: the service eagerly creates one \`MarkerDecorations\` for every \`IModelService\` model and updates it independently of editor visibility.
- Magnitude uncertainty: The number of simultaneously loaded models with several thousand aggregate diagnostics varies by workspace and extension mix, so retained-memory magnitude across a session is uncertain.
- Expensive boundaries: none found
- Verdict: Covered by the reported cap regression: opening latency and retained interval-tree/map state scale up to tenfold per affected model; this is the same causal mechanism, not a separate finding.

**Summary:** Completed the performance pass over all five changed files and traced marker publication, model-decoration updates, editor lifecycle, and language-status reporting. One concrete cap-induced synchronous rendering/memory regression was submitted; the warning/reporting path itself is bounded and introduces no expensive boundary.
