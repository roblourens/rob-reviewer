**Relevant issue families:** eager-work, boundary-fanout, missing-coalescing, concurrency-burst, serialization-allocation, cleanup-lifecycle

### Scenario 1: Workbench startup with chat.mcp.discovery.enabled unset, locally and in a remote window

- Critical path: MCP discovery starts at WorkbenchPhase.AfterRestored, so it does not block workbench restoration. The async native-helper load must complete before discovery installs watchers; the Copilot config file read, JSON adaptation, and per-server nonce hashes must complete before its servers appear.
- Scaling input: The file read scales with config bytes and adaptation/hash work scales linearly with the number and size of configured servers; machine-side watcher cardinality remains bounded at one per local/remote side.
- Effective concurrency: One Copilot watcher/read runs for the local side; a remote window can also run one for the remote side. Each file is read once initially. Definitions are hashed concurrently with Promise.all, with cardinality equal to servers in that one config file.
- Cache behavior: There is no parsed-content cache. A missing file produces an empty result after one failed initial read while the watcher remains for future creation; successful definitions remain in the registered observable collection until a change, disable, or disposal.
- Mechanism confidence: High: the changed default directly enables the existing watcher/read path, and its phase, cardinality, and async call path are explicit.
- Magnitude uncertainty: Real Copilot config sizes vary, but typical files contain few servers; no evidence shows the bounded after-restored read/hash work causing noticeable latency.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/mcp/electron-browser/nativeMpcDiscovery.ts:31 and src/vs/workbench/contrib/mcp/common/discovery/nativeMcpRemoteDiscovery.ts:39</code>: Load native MCP discovery environment data from the main process or remote agent.; cardinality: Once for the local discovery instance and, when connected remotely, once for the remote discovery instance.
    - Introduced by diff: false; previous behavior: The helper was loaded regardless of whether Copilot discovery was enabled.; critical-path effect: Asynchronous and after restoration; discovery setup waits for it, but the workbench does not.
  - filesystem at <code>src/vs/workbench/contrib/mcp/common/discovery/nativeMcpDiscoveryAbstract.ts:78</code>: Create a non-recursive watcher and read mcp-config.json.; cardinality: One watcher and one initial read per active machine side, so one locally and at most one additional remote-side pair in a remote window.
    - Introduced by diff: true; previous behavior: With the setting unset, the Copilot source was disabled, so no Copilot-home watcher or initial read was created; explicit opt-in performed the same work.; critical-path effect: Off the restore critical path; server availability waits for the read and adaptation.
- Verdict: No reportable regression. The new work is the intended discovery feature, is bounded to one file per machine side, occurs after restoration, and has no evidenced user-visible performance impact.

### Scenario 2: Copilot MCP configuration changes while the workbench is running or discovery is toggled

- Critical path: A file event schedules updateFile; the read, parse, and hashes must finish before the observable server definitions and registry reflect the edit. Disabling the source synchronously clears the collection and disposes the autorun-owned scheduler/watcher.
- Scaling input: Cost scales with edit bursts, config bytes, and server count after coalescing; it does not fan out into per-server filesystem calls.
- Effective concurrency: RunOnceScheduler coalesces watcher events within 500 ms independently per machine side. Per-server SHA-256 hashes within one refresh run concurrently. Slow refreshes could overlap with later scheduled refreshes, but that behavior pre-existed for explicitly enabled discovery and the diff does not alter scheduling.
- Cache behavior: No warm parse cache is used, but watcher events are coalesced. Disabling or disposing discovery releases the watcher and registration; re-enabling performs a fresh read.
- Mechanism confidence: High for the refresh and cleanup mechanics; low that realistic inputs make them a performance regression.
- Magnitude uncertainty: External tools' save patterns and unusually large server lists are unknown. The bounded one-file refresh gives no concrete evidence of jank or excessive I/O.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/mcp/common/discovery/nativeMcpDiscoveryAbstract.ts:57</code>: Re-read the complete mcp-config.json after watcher notifications.; cardinality: At most one scheduled read per 500 ms event burst per local/remote config watcher.
    - Introduced by diff: true; previous behavior: The same coalesced refresh occurred only after explicit Copilot-source opt-in; default-unset users had no watcher.; critical-path effect: Only discovery freshness waits; general UI progress does not.
- Verdict: No finding. Coalescing and lifecycle cleanup are present, and the diff changes the default reachability rather than introducing repeated per-item I/O or an unbounded resource.

### Scenario 3: Agent-host support assessment and customization publication for Copilot-home servers

- Critical path: During active-client customization resolution, all discovered MCP servers are classified. Matching same-machine Copilot CLI sessions return RuntimeDiscovered immediately. Every other agent or host now returns NotDelivered immediately, before projection, variable resolution, serialization, or standalone bundle creation.
- Scaling input: Classification remains linear in all discovered MCP servers. Removed serialization scales with the count and configuration size of Copilot-home servers after grouping into one bundle.
- Effective concurrency: Server classifications are launched with Promise.all across the discovered server set. The new Copilot-home branch itself performs no asynchronous boundary work, and non-owner servers no longer contribute to bundling.
- Cache behavior: The bundler has a content nonce and reuses an unchanged prior bundle; the changed path bypasses it for Copilot-home servers. Runtime discovery continues to use the watched config on the owning machine.
- Mechanism confidence: High: the changed branch returns before projection and tests establish zero Copilot-home bundling for non-owner sessions.
- Magnitude uncertainty: The amount of avoided bundle work depends on server count and whether other standalone customizations still require a bundle.
- Expensive boundaries:
  - serialization at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/syncedCustomizationBundler.ts:321</code>: Serialize forwarded MCP servers into a synthetic .mcp.json and compute bundle content/nonces.; cardinality: Before the diff, one grouped standalone bundle contained all forwarded Copilot-home servers for the session; after the diff, these servers contribute zero entries and may avoid the bundle entirely when no standalone files remain.
    - Introduced by diff: false; previous behavior: Copilot-home servers not runtime-discovered by the target were projected and forwarded as one synthetic bundle.; critical-path effect: Bundling is awaited before publishing customization refs; this change removes rather than adds that work for non-owner sessions.
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/syncedCustomizationBundler.ts:379</code>: Write the synthetic bundle manifest and .mcp.json to the in-memory customization filesystem.; cardinality: Previously one manifest and one .mcp.json write per changed grouped bundle; now zero writes attributable to Copilot-home servers, and zero bundle calls when they were the only standalone content.
    - Introduced by diff: false; previous behavior: Non-owner Copilot-home servers could trigger or enlarge the standalone bundle.; critical-path effect: Previously awaited on active-client publication; removed by the changed delivery decision.
- Verdict: No regression. This path reduces serialization, virtual-filesystem writes, and forwarded bytes while preserving the same-machine runtime-discovery path.

**Summary:** Completed the performance pass over all 10 changed files and relevant transitive discovery, registry, hashing, agent-host resolution, and bundling paths. The PR intentionally adds one bounded post-restore Copilot config watcher/read per machine side and removes non-owner forwarding/bundling. No high-confidence actionable performance regression was found.
