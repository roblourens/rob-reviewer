- Effective concurrency: Migration discovery remains Promise.all across enabled categories (maximum four), and source-folder discovery remains Promise.all across deduplicated target types. The existing Delayer coalesces refresh requests and sequence/cancellation checks discard superseded work. The diff changes none of this concurrency.

### Scenario 2: Ignore or restore a migration group while retaining access to ignored pending migrations

- Critical path: The user confirmation/quick pick and existing storage update complete, then refreshCustomizationMigrationUi synchronously rebuilds migration summaries, updates the sidebar shortcut, and renders dashboard state. The new predicate checks whether any enabled category still has candidates so the shortcut remains reachable even when all are ignored.
- Scaling input: Four fixed categories. The added check does not enumerate candidates or inspect ignored-group storage; it checks only each existing candidate array's length.
- Effective concurrency: This UI-only refresh is synchronous after the user interaction; no new task, queue, IPC, or parallel work is introduced.
- Cache behavior: It reads the already-populated customizationsByMigrationCategory map. Ignore state storage behavior is unchanged, and the added predicate deliberately does not consult or alter it.
- Mechanism confidence: High: refreshCustomizationMigrationUi and updateSidebarMigrationShortcut are direct callers, and the changed line has no transitive boundary operation.
- Magnitude uncertainty: The number of ignore/restore interactions is user-driven, but each added check is fixed and negligible.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. Sidebar visibility now changes based on pending candidates using bounded in-memory work; existing synchronous layout remains one call per refresh.

### Scenario 3: Complete, delete, or otherwise remove the final migration candidate and hide the Migrations sidebar entry

- Critical path: Existing migration/delete operations perform their service or filesystem work, refresh candidate inventory, then updateSidebarMigrationShortcut reads the committed candidate map. The new predicate hides the entry when all four category arrays are empty.
- Scaling input: The new work is independent of migrated/deleted item count: at most four category map lookups and length checks.
- Effective concurrency: Migration and deletion sequencing is unchanged. Inventory refresh retains its existing coalescing, cancellation, and parallel category discovery; the local visibility predicate is synchronous after results are committed.
- Cache behavior: The predicate consumes the newly committed candidate map and requires no cache invalidation or negative-cache state.
- Mechanism confidence: High: the call paths update the same candidate map and reach the changed predicate only after existing operations complete.
- Magnitude uncertainty: Boundary durations depend on provider and filesystem, but none are introduced or amplified by this diff.
- Expensive boundaries:

The added visibility check executes afterward and adds no boundary latency.
- Verdict: No reportable performance regression. The change adds a fixed local predicate and does not alter expensive operation count, concurrency, or critical-path placement.
