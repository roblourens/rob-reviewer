# Performance review: agentHost: native Mission Control environments

[PR #339513](https://github.com/microsoft/vscode/pull/339513) at `680d699afd12266e3e42d5fb2db6b4723f77178b`

## Findings (3)

### 1. [high] Allow more than one relay publish per acknowledgement RTT

**Finding ID:** `PERF-9B19EDEE3B88`  
**Location:** <code>src/vs/platform/agentHost/node/missionControl/missionControlProtocolServer.ts:290</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Web PubSub publish operations and the shared outbound frame queue  
**Scaling:** For F outgoing AHP or mirror frames, completion now takes approximately F sequential Web PubSub acknowledgement round trips; all client lanes and mirror traffic share the same queue, so queued latency also grows with traffic from other sessions.  
**Outcome:** Remote session throughput is capped by relay acknowledgement latency, with head-of-line blocking and rising interactive response latency; bursts can fill the 512-frame queue and close the connection.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no native Mission Control server queue. The existing \`WebPubSubRelayTransport.send\` path sends every generated frame immediately and independently tracks all pending acknowledgement IDs, so relay throughput is not limited to one frame per acknowledgement RTT.  
**Changed behavior:** Every AHP response, notification, chunk, and mirrored event is appended to one process-wide queue, but the new drain sends only one frame and then waits for its Web PubSub acknowledgement before sending the next frame.  
**Confidence:** 0.99 — The single-outstanding-frame invariant, shared queue ownership, and ack-driven call path are explicit and test-covered. Exact RTT and action rate vary, affecting severity magnitude but not the throughput mechanism.

**Causal diff evidence:** The added \`\_drain\` loop at line 290 is conditioned on \`this.\_pending.size === 0\`, adds exactly one ack ID to \`\_pending\`, and is re-entered only when an acknowledgement deletes that ID. This new server is the PR's outbound Mission Control path.

On a realistic remote turn, streamed chat/actions and mirrored state generate many frames. With normal cloud RTT, each frame waits another RTT, and an interactive reply can sit behind mirror traffic from any session or lane.

**Evidence:** \`MissionControlLane.send\` routes all lanes through \`\_publish\`/\`\_enqueue\`; mirror events use the same \`\_enqueue\`. \`\_receive\` deletes one pending ack and invokes \`\_drain\` again. The added test \`serializes AHP publishes behind acknowledgements without reordering\` explicitly proves that only the first of two responses is sent before the first ack. By contrast, \`browser/webPubSubRelayTransport.ts:472-484\` sends all chunks without waiting for prior acks.

**Suggested direction:** Preserve send order while allowing a bounded window of outstanding publishes, as the existing client transport does, and/or batch adjacent frames before crossing WPS. Keep the current queue byte limits and per-frame acknowledgement/error handling.

### 2. [medium] Move mirror serialization off the synchronous action path

**Finding ID:** `PERF-80513886C593`  
**Location:** <code>src/vs/platform/agentHost/node/missionControl/missionControlSessionMirror.ts:236</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU time and temporary/retained strings, parsed objects, UTF-8 buffers, base64 buffers, and framed JSON  
**Scaling:** Cost grows with every emitted state action and its payload size. Each envelope is stringified here, parsed back at line 250, stringified at least twice again by \`chunk\`, UTF-8 encoded, and then stringified once per retained frame.  
**Outcome:** The Agent Host event loop is blocked by repeated serialization and allocation, increasing action/stream latency and CPU/GC pressure for both local IPC sessions and remote sessions while Mission Control is enabled.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, authoritative state emission did not synchronously clone, encode, chunk, and retain every envelope for Mission Control; normal local Agent Host dispatch only applied and emitted the action.  
**Changed behavior:** With Mission Control enabled, the synchronous \`Emitter.fire\` call now runs \`mirror.enqueue\`, which performs a JSON round trip plus chunk/framing serialization before the state dispatch can return. \`chunk\` itself stringifies the payload and the single-frame envelope and encodes the string to UTF-8.  
**Confidence:** 0.98 — The synchronous call chain and repeated full-payload transformations are directly visible. Payload distributions determine the exact pause length, so severity is medium, but the per-action CPU/allocation mechanism is certain.

**Causal diff evidence:** This added line synchronously serializes each envelope admitted by the newly added \`onDidEmitEnvelope\` listener in \`missionControlHost.ts:120-140\`; that listener directly calls \`mirror.enqueue\` before returning.

Streaming responses, terminal data, large response parts, and history-loading actions can make local turns consume extra CPU and pause subsequent Agent Host work even though mirror network publication itself is scheduled later.

**Evidence:** \`AgentHostStateManager.\_applyAndEmit\` calls \`\_onDidEmitEnvelope.fire(envelope)\` synchronously. The new listener calls \`mirror.enqueue\`; this method performs \`JSON.stringify(envelope)\`, \`JSON.parse(serialised)\`, \`chunk(payload)\`, and \`\_frameJson\` for each fragment. \`chunking.ts:97-119\` confirms two further stringifications and a \`TextEncoder.encode\`, with base64 work for large payloads.

**Suggested direction:** Make the event listener perform only bounded queue admission, then serialize/chunk in the scheduled mirror drain (or a worker). Serialize once and let chunking consume the serialized bytes instead of parsing and re-stringifying, while retaining the existing spool limits and failure signaling.

### 3. [medium] Avoid synchronous filesystem walks on every relay resource request

**Finding ID:** `PERF-D3E9A5B16550`  
**Location:** <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:2266</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Synchronous filesystem \`realpath\`, \`stat\`, and \`lstat\` operations on the Agent Host event loop  
**Scaling:** For R remote resource operations, P missing path ancestors, and G current grant/workspace/content roots, authorization performs O(R × (P + G)) synchronous filesystem operations; \`\_resourceRoots\` also rebuilds its roots by scanning all session summaries on each request.  
**Outcome:** Remote file reads/lists/writes incur added latency and can block unrelated local and remote Agent Host work, especially for tool bursts, many sessions/roots, missing paths, or slow/network-mounted filesystems.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, request dispatch did not run this synchronous canonicalization/grant scan. Resource handlers proceeded to their normal filesystem implementation without repeatedly canonicalizing every configured and session-derived root on the shared event loop.  
**Changed behavior:** Every Mission Control resource request now synchronously resolves the target (or each missing ancestor), may synchronously stat it, reconstructs all granted roots from session summaries, and synchronously resolves each root until a match is found.  
**Confidence:** 0.97 — The per-request synchronous boundary and multiplicative root/ancestor scans are explicit. Filesystem speed and realistic root count vary, affecting magnitude but not the blocking mechanism.

**Causal diff evidence:** The added relay authorization path invokes \`\_isGrantedRelayResource\` before every request at \`protocolServerHandler.ts:2007-2014\`; line 2266 begins a synchronous ancestor walk, and line 2293 synchronously resolves every dynamically recomputed root.

A remote agent commonly issues many file operations during a turn. These checks serialize filesystem waits on the single Agent Host thread and can make chat/tool progress stutter while also delaying local IPC sessions hosted by the same process.

**Evidence:** \`\_handleRequest\` unconditionally calls \`\_requireRelayResourceAccess\` for relay clients. File requests enter \`\_isGrantedRelayResource\`, whose loop calls \`realpathSync\`, \`statSync\`, and potentially \`lstatSync\` per ancestor; its final \`.some\` invokes \`relayResourceRoots\`, which scans session summaries, then calls \`realpathSync(root)\` per root.

**Suggested direction:** Cache canonical grant roots and session-derived content roots with invalidation on grants/session/workspace changes, and perform target canonicalization asynchronously while preserving the current missing-path and symlink checks.
