## Findings

No high-confidence performance findings.

<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, boundary-fanout, synchronous-ui-work

### Scenario 1: Start a migrated workspace HTTP MCP server whose raw URL contains a supported environment reference

- Critical path: McpServer.start serializes one connection attempt, resolveConnection checks the raw URL, then the extension host expands it before the HTTP transport starts. The added URL.canParse checks are on this startup critical path.
- Scaling input: One raw URL per server-start attempt; supported expansion is already limited to URLs of at most 1,000 UTF-16 code units by hasEnvVarReferences. Retries repeat the check, while starts for different servers remain independent.
- Effective concurrency: Starts are serialized per McpServer by \_connectionSequencer; there is no new aggregate limiter or new concurrency introduced by the diff. Different servers may start concurrently as before.
- Cache behavior: No cache participates in URL validation or expansion. Warm and cold starts both perform the checks once per attempted connection; the diff neither defeats nor adds a cache.
- Mechanism confidence: High: the call path shows URL.canParse once in the main-thread precheck and once in extension-host expansion, with the existing IPC and network boundaries unchanged.
- Magnitude uncertainty: Exact URL parsing cost varies by JavaScript runtime, but expandable inputs are capped at 1,000 code units and server starts are not a per-frame or per-message path.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadMcp.ts:111-116, NodeExtHostMpcService.$expandEnvironmentVariables</code>: Serialize the launch to the extension host, expand environment references using the host process environment, and deserialize the result.; cardinality: One IPC round trip per server-start attempt that has a recognized URL or header reference.
    - Introduced by diff: false; previous behavior: The same one IPC round trip occurred for a parseable raw URL containing a recognized reference.; critical-path effect: The IPC must finish before the remote HTTP connection can be created.
  - network at <code>src/vs/workbench/api/node/extHostMcpNode.ts:29-30</code>: Create the existing HTTP/SSE MCP transport to the resolved remote server URL.; cardinality: One transport start per resolved server connection, unchanged by the diff.
    - Introduced by diff: false; previous behavior: The same remote transport was started after environment expansion.; critical-path effect: The server cannot become connected until the remote transport starts.
- Verdict: No reportable regression. The diff adds two bounded URL parses on starts that still expand, but does not increase IPC/network cardinality or create realistic latency, throughput, or memory impact.

### Scenario 2: Start a migrated workspace HTTP MCP server whose raw URL is rejected by URL.canParse

- Critical path: resolveConnection calls URL.canParse before deciding whether environment expansion is needed. With no expandable header, a rejected raw URL now avoids the extension-host expansion IPC; with an expandable header, the existing IPC still occurs so the header can be resolved.
- Scaling input: One URL check per server-start attempt. Cost grows linearly with the configured URL length; ordinary MCP URLs are small, and the changed work is not inside a collection or message loop.
- Effective concurrency: Per-server attempts remain serialized; rejected URLs do not create new concurrent work and can remove one IPC from an attempt without expandable headers.
- Cache behavior: There is no positive or negative validation cache. Each retry rechecks the raw URL, but retries already repeated connection resolution and the check is one local parse per attempt.
- Mechanism confidence: High: the short-circuit behavior and optional IPC are explicit in getExpandableUrl and launchHasEnvironmentVariableReferences.
- Magnitude uncertainty: Extremely large configuration strings could make URL.canParse more expensive, but such inputs are not a realistic MCP URL workload and configuration parsing already processes the same string. There is no evidenced user-visible performance symptom.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/mcp/common/mcpRegistry.ts:545-546 and src/vs/workbench/api/browser/mainThreadMcp.ts:111-116</code>: Expand host environment references when any supported header reference remains.; cardinality: Zero IPC calls for an invalid raw URL with no expandable headers, versus one before the diff; one IPC if headers require expansion, unchanged from before.
    - Introduced by diff: false; previous behavior: Before the diff, a recognized reference in the invalid raw URL caused one expansion IPC even without header references.; critical-path effect: When present, IPC remains on the startup critical path; when absent, the diff shortens that path.
  - network at <code>src/vs/workbench/api/node/extHostMcpNode.ts:29-30</code>: Attempt to create the remote MCP HTTP transport from the launch URI retained by connection resolution.; cardinality: At most one transport start per connection attempt, as before.
    - Introduced by diff: false; previous behavior: Connection resolution also proceeded to one transport start after expansion.; critical-path effect: Transport startup remains necessary for the server to connect; the diff changes URL expansion semantics but does not fan out network operations.
- Verdict: No performance finding. The main changed boundary effect is eliminating an IPC for rejected URL-only references; remaining synchronous parsing is once per attempt and not a realistic regression.

### Scenario 3: Start a migrated workspace HTTP MCP server with a plain URL and no environment references

- Critical path: resolveConnection now runs URL.canParse and then the existing reference scan; it does not call the extension host and proceeds to the existing remote transport.
- Scaling input: One URL per server-start attempt; for normal configurations this is a short string. The added parser is not invoked per tool call, protocol message, render, or frame.
- Effective concurrency: Per-server start sequencing is unchanged. Different server starts may overlap as before, but each contributes only one local parse and no added IPC.
- Cache behavior: No cache is used; both first starts and retries perform one parse. The diff does not alter server metadata or connection caching.
- Mechanism confidence: High: the helper is called exactly once by launchHasEnvironmentVariableReferences on this main-thread path and short-circuits the extension-host call.
- Magnitude uncertainty: No benchmark quantifies URL.canParse, but the operation is one local parse of a normal configuration URL per connection attempt, so plausible impact is negligible.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/mcp/common/mcpRegistry.ts:545-546</code>: Environment expansion IPC is skipped because no supported references are present.; cardinality: Zero before and after the diff.
    - Introduced by diff: false; previous behavior: The reference scan returned false and skipped expansion IPC.; critical-path effect: No IPC is added to startup.
  - network at <code>src/vs/workbench/api/node/extHostMcpNode.ts:29-30</code>: Start the remote MCP HTTP transport.; cardinality: One per connection attempt before and after the diff.
    - Introduced by diff: false; previous behavior: The same transport was started directly after reference detection.; critical-path effect: This existing network operation dominates connection establishment and is unchanged.
- Verdict: No reportable regression. The diff adds minor synchronous CPU work but no meaningful hot-path multiplicity, retained state, boundary fan-out, or user-visible performance consequence.
