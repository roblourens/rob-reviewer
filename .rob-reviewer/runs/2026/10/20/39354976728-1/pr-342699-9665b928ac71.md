# Performance review: chat: load generated images in a square that only grows into the image

[PR #342699](https://github.com/microsoft/vscode/pull/342699) at `9665b928ac71468b890951cdf5a92f37832ebbed`

## Findings (1)

### 1. [medium] Throttle the enlarged loader's canvas repaint loop

**Finding ID:** `PERF-9A9878486E47`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/attachments/chatImageReveal.css:22</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Main-thread canvas cell computation and drawImage/clearRect work on every animation frame  
**Scaling:** Cost grows with the loader's pixel area and display refresh rate for the full generation duration. In a typical wide viewport the grid grows from 32x5 (160) cells to 26x26 (676) cells, so per-frame cell evaluation/drawing rises about 4.2x; canvas pixels cleared rise from 16,000 to about 70,756 CSS pixels (and scale further with devicePixelRatio).  
**Outcome:** Sustained CPU/rendering pressure while an image is generating, increasing battery use and risking dropped frames on lower-end, web, or remote clients  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The loader was a 320x50 band. GlyphSurface's requestAnimationFrame loop therefore cleared a 16,000-CSS-pixel canvas and evaluated/drew at most 160 10px cells per frame.  
**Changed behavior:** The new 1:1 aspect ratio makes the same continuously animated GlyphSurface up to roughly 266x266 under the default 400px cap, without changing its every-frame full-surface repaint algorithm.  
**Confidence:** 0.98 — The changed geometry, GlyphSurface's unconditional visible rAF loop, and exact cell-loop scaling are directly established in repository code. The main uncertainty is device-dependent frame-time impact, not whether the PR adds the sustained work, so severity is medium rather than high.

**Causal diff evidence:** RIGHT line 22 adds \`aspect-ratio: 1\` while lines 20-21 size the loader up to two thirds of the 400px cap; this replaces the deleted fixed \`height: 50px\` and raises the animated canvas area and cell count by up to about 4.4x/4.2x.

Whenever generated-image progress is visible with motion enabled, GlyphSurface repaints the full square every requestAnimationFrame for as long as generation runs. On a wide chat this turns roughly 9,600 cell draws/second at 60Hz into roughly 40,560, which can cause visible chat/input jank and sustained CPU/battery use during slow generations.

**Evidence:** GlyphSurface.update schedules another animation frame whenever motion is enabled, and paintLoading clears the entire backing canvas then runs nested row/column loops that call drawLoadingCell/drawImage for every 10px cell. This diff changes only the CSS geometry from 320x50 to a square capped at 2/3 of 400px; tests confirm 200x200 under a 300px test cap, while the production default reaches 266x266. Batch ownership suppresses duplicate loaders within one batch, but the selected loader still performs this amplified work continuously on the UI thread.

**Suggested direction:** Preserve the square visual but bound its animation work—for example, cap the loading-state repaint cadence (such as 30fps) and/or cache the static glyph field so each tick redraws only the moving wave—before increasing the surface area.
