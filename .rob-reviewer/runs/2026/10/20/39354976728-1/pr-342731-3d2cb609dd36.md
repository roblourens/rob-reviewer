**Relevant issue families:** serialization-allocation, boundary-fanout, repeated-work, cache-lifecycle

### Scenario 1: Workbench startup, agent-host connection, and sandbox setting changes

- Critical path: The forwarder synchronously reads the desired settings and enqueues RootConfigChanged when a host advertises the schema; connection establishment itself does not await this propagation. Configuration-change handling similarly dispatches synchronously but has no added asynchronous prerequisite.
- Scaling input: Number of simultaneously connected local/remote agent hosts; the settings read is over a fixed mapping that is one entry smaller after the diff
- Effective concurrency: Connections are visited serially in a synchronous loop; there is no added parallel burst or queue. Initial pushes remain deduplicated by the \_scheduled map.
- Cache behavior: The desired configuration is computed once and cached until a relevant configuration event. Cold computation performs one configuration inspection per fixed mapped key; warm pushes reuse the object. The diff removes one key and its invalidation trigger.
- Mechanism confidence: High: the removed SANDBOX\_SETTING\_KEYS and mapping entries directly eliminate one read, payload member, and event trigger; no replacement path is introduced.
- Magnitude uncertainty: Actual users usually have few connected hosts, but cardinality and scheduling are explicit in the implementation.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/agentHostSandboxForwarder.ts:\_tryPush</code>: Dispatch RootConfigChanged with the sandbox configuration to each connected local or remote agent host; cardinality: At most one dispatch per live connection on initial schema availability when state differs, and one per live connection for a relevant settings change when desired state differs
    - Introduced by diff: false; previous behavior: The same per-connection dispatch existed and additionally carried the masked-environment-variable object; changes to that setting could trigger another fan-out. The diff removes that trigger and payload field.; critical-path effect: The dispatch enqueue runs synchronously in the connection/configuration event, but is not awaited as part of host connection establishment
- Verdict: No reportable regression: startup/configuration work and IPC payload can only stay equal or decrease.

### Scenario 2: Create or resume a Copilot agent session with sandboxing enabled

- Critical path: After SDK create/resume, finalization awaits script-safety configuration and then one sandbox options.update RPC before the session wrapper becomes available. The diff only removes the credentials member from the object sent by this existing RPC.
- Scaling input: Number of launched sessions and, before the diff, configured environment-variable entries/host strings; after the diff that variable-sized field is absent
- Effective concurrency: Launch finalization awaits the RPC sequentially per session; the diff does not add cross-session concurrency.
- Cache behavior: No cache controls the launch RPC. Sandbox policy construction remains local and bounded by existing filesystem/network policy collections; the removed credential map is no longer copied into the SDK object.
- Mechanism confidence: High: the changed object spread was the only forwarding point and is deleted.
- Magnitude uncertainty: Credential maps could vary in size, but omission cannot increase launch cost.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:launch/\_createSession/\_resumeSession</code>: Create or resume the SDK session; cardinality: One successful create or resume attempt per launch, with existing fallback attempts only on the documented resume failures
    - Introduced by diff: false; previous behavior: Identical create/resume behavior.; critical-path effect: Required for session launch, but its call count and inputs are not changed by this diff
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:applySandboxConfig</code>: Apply sandboxConfig through session.rpc.options.update; cardinality: One RPC during successful launch finalization
    - Introduced by diff: false; previous behavior: The same RPC was made and could serialize the configured environment-variable map; after the diff the payload omits that map.; critical-path effect: Awaited on launch finalization
- Verdict: No reportable regression: launch boundary count is unchanged and serialization/allocation is reduced.

### Scenario 3: Start a normal agent turn or /fleet turn and synchronize live sandbox configuration

- Critical path: Every turn awaits the existing sequenced sandbox options.update RPC and then awaited host-support diagnostics before the agent loop starts. Certificate diagnostics begin in the background and are not joined by updateDiagnostics. The removed credential field does not add any operation or move one onto this path.
- Scaling input: Turn count per live session and, before the diff, unique credential configurations and map size
- Effective concurrency: Sandbox updates use a per-session sequencer. Certificate checks coalesce through a per-runtime promise map, and mutations use a per-RPC SequencerByKey. The diff adds no burst.
- Cache behavior: Certificate status caches successes and failures by runtime/config key. Removing credentials reduces possible key cardinality; no cold or negative-cache path is defeated.
- Mechanism confidence: High: call flow from \_prepareSdkTurn through applyConfig is explicit, and the diff only deletes data from the pre-existing config.
- Magnitude uncertainty: SDK RPC duration is runtime-dependent, but boundary count and payload direction are established.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionSandbox.ts:\_updateConfig via applySandboxConfig</code>: Apply current sandboxConfig with session.rpc.options.update; cardinality: One existing RPC per prepared turn, plus existing explicit configuration/grant updates; calls are serialized per session
    - Introduced by diff: false; previous behavior: The same RPC occurred and included the variable-sized credentials object when configured; after the diff it sends a smaller object.; critical-path effect: Awaited before session.send or fleet.start
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSandboxDiagnostics.ts:update</code>: Query sandbox host support for diagnostics; cardinality: One existing getHostSupport query after each successful enabled sandbox update
    - Introduced by diff: false; previous behavior: Identical query count and placement.; critical-path effect: Awaited by sandbox update and therefore on turn preflight; unaffected by the removed field
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSandboxCertificate.ts:\_check</code>: Check certificate relevance, installation support, and status; cardinality: At most one in-flight/completed check per runtime and effective auth/credential cache key; installation-support lookup is separately reused
    - Introduced by diff: false; previous behavior: Credential-map changes could create distinct cached checks. With credentials omitted, keys coalesce by the remaining auth values, so check cardinality cannot increase.; critical-path effect: Started by certificate diagnostics but not awaited by turn updateDiagnostics
- Verdict: No reportable regression: critical-path RPC count is unchanged, payload allocation is reduced, and certificate-cache cardinality may decrease.

### Scenario 4: Open or search the Settings UI for sandbox configuration

- Critical path: Settings registration and display-name formatting are local synchronous schema/model work. The diff removes one schema entry and one formatting branch; it does not add rendering, layout, filesystem, IPC, subprocess, database, or network work.
- Scaling input: Number of registered settings and settings rows; both decrease by one for this feature
- Effective concurrency: Local synchronous model/render preparation only; no queue or fan-out introduced.
- Cache behavior: No changed cache behavior was found on this path.
- Mechanism confidence: High: the only UI changes are deletions of the setting registration, display label, and tests.
- Magnitude uncertainty: The saved UI work is small, but its direction is unambiguously non-regressive.
- Expensive boundaries: none found
- Verdict: No reportable regression: the Settings UI has less schema and row work.
