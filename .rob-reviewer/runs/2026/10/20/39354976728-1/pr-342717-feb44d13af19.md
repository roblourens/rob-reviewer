### Scenario 1: Open the AI Customizations editor and set, replace, or delete an MCP OAuth client secret while migration details are visible

- Critical path: The secret-storage set/delete itself completes independently because the new event handler starts refreshCustomizationMigrationInfo without awaiting it. The refreshed migration reason waits for the asynchronous migration recomputation, but this work is not on the command's completion path.
- Scaling input: Distinct MCP source files, eligible OAuth-configured servers, enabled migration categories, and recovery manifests. The new trigger occurs once per explicit matching secret-storage change rather than per frame, input event, or server row.
- Effective concurrency: A zero-delay Delayer coalesces same-turn requests, newer refreshes cancel the prior request, enabled migration categories compute concurrently with Promise.all, MCP source files are deduplicated by source URI, and OAuth secret lookups inside MCP planning are sequential per eligible OAuth server.
- Cache behavior: MCP source reads are coalesced per source URI within a plan. There is no cross-refresh cache, which is appropriate because the changed secret invalidates the plan. Same-turn refresh requests are delayed/coalesced and stale requests are cancelled; secret misses are not cached across plans.
- Mechanism confidence: High confidence in the newly reachable boundary work and its bounded scheduling, based on the event handler, Delayer/cancellation logic, provider call path, source-file promise map, and secret lookup loop.
- Magnitude uncertainty: Secret changes may synchronize across windows, and exact provider/file-service latency varies, but the realistic trigger is rare and explicit. No evidence shows bursty writes or a hot path.

### Scenario 2: Keep an MCP server detail page open while migration candidates, exclusions, or compatibility state change

- Critical path: A completed migration refresh linearly finds the current server in candidate and exclusion arrays, then synchronously updates the three small diagnostic sections before the page reflects the new state.
- Scaling input: Number of migration candidates/exclusions for the active context and number of compatibility detail strings for one server. Only one open detail is updated, not every list row.
- Effective concurrency: Single UI-thread update for the one open detail. Migration computation is asynchronous; the final state application is serialized on the UI thread.
- Cache behavior: Candidate and exclusion arrays are current refresh results. Presentation setters short-circuit unchanged values; no external cache or negative-cache behavior is involved.
- Mechanism confidence: High confidence from refreshMcpDetailMigrationState and EmbeddedMcpServerDetail rendering paths.
- Magnitude uncertainty: Large MCP server inventories increase the two linear searches, but realistic inventories are modest and there are no per-row boundary calls or full-tree renders.
- Expensive boundaries: none found
- Verdict: No finding. Added work is bounded to two in-memory searches and small DOM reconstruction for one detail on migration/compatibility changes; it does not establish a realistic rendering regression.
