<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, eager-work, boundary-fanout, synchronous-ui-work, serialization-allocation

### Scenario 1: Open or edit a GitHub Copilot \*.agent.md file and receive diagnostics

- Critical path: The visible model is parsed, then validation runs after the existing 200 ms ModelTracker debounce; the new schema, hook, GitHub, and MCP checks are synchronous in-memory scans before markers are published. Existing body file-reference checks remain awaited on the diagnostics critical path.
- Scaling input: Header attributes, hook events/actions and MCP servers/properties; each new validator walk is linear in those parsed collections. Typical schemas contain tens of entries, and edits are coalesced by the existing per-model delayer.
- Effective concurrency: One delayed validation task per visible text model. Existing file-reference existence checks within one document fan out through Promise.all; the diff neither adds calls nor changes this concurrency.
- Cache behavior: The parsed AST is cached by model URI and version, so validation reuses it within a version and reparses once after a content change. Static schema metadata is module-scoped; validation constructs only bounded temporary arrays, maps, and sets.
- Mechanism confidence: High: registration, debounce, AST caching, new loops, and all transitive filesystem calls were traced directly.
- Magnitude uncertainty: Very large hand-authored hook or MCP maps increase linear CPU and short-lived allocation, but realistic files are small and validation is debounced; no evidence supports user-visible latency.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptValidator.ts:validateBody</code>: Check existence of each same-scheme body file reference; cardinality: One existing fileService.exists call per body file reference, coalesced only by the 200 ms document validation debounce and run concurrently with Promise.all.
    - Introduced by diff: false; previous behavior: The same per-reference filesystem checks ran before this PR; the added header-schema validation does not add references or change their scheduling.; critical-path effect: All checks are awaited before updated diagnostics are published.
  - filesystem at <code>src/vs/workbench/contrib/chat/common/promptSyntax/languageProviders/promptValidator.ts:validateFileName</code>: Check whether a migrated agent file can be created for a legacy .chatmode.md file; cardinality: At most one call per validation of a legacy agent file.
    - Introduced by diff: false; previous behavior: Unchanged by this PR.; critical-path effect: Awaited before diagnostics complete for that legacy-file scenario.
- Verdict: No reportable regression. The diff adds bounded linear in-memory validation and does not introduce or amplify an expensive boundary.

### Scenario 2: Request header, nested GitHub/MCP, or hook completions while editing an agent file

- Critical path: The completion provider retrieves the version-cached AST, locates the containing attribute/server/action, builds a small completion list, and returns it synchronously except for pre-existing model/agent inventory paths.
- Scaling input: Top-level attributes are bounded by the static schema; nested MCP completion location scales linearly with configured servers and properties, while hook completion location scales linearly with hook events/actions.
- Effective concurrency: A single provider invocation performs one local scan; there is no added queue, fan-out, IPC, filesystem, subprocess, database, or network operation.
- Cache behavior: Warm requests on an unchanged model reuse the cached AST. A changed model incurs one parse that is then cached by version. Static schema tables are reused, while small completion arrays and sets are rebuilt per request.
- Mechanism confidence: High: the completion entry point and all new nested helper paths were traced.
- Magnitude uncertainty: Completion can be invoked frequently during typing, but the added work is bounded or linear over realistically small frontmatter collections and has no expensive boundary.
- Expensive boundaries: none found
- Verdict: No reportable regression. Added scans and allocations are small, request-local, and proportional to the frontmatter being completed.

### Scenario 3: Hover over Copilot agent attributes, hook events, or hook action properties

- Critical path: The hover provider reads the version-cached AST, scans header attributes and hook properties until the hovered range is found, then creates one MarkdownString.
- Scaling input: Number of header attributes and hook-event properties in the current file; metadata lookup is constant-time after the range scan.
- Effective concurrency: One synchronous local lookup per hover request with no asynchronous boundary or fan-out.
- Cache behavior: The AST is reused for the current model version; module-scoped schema and hook metadata are reused across hovers.
- Mechanism confidence: High: the provider and changed metadata lookup path were directly inspected.
- Magnitude uncertainty: Hover frequency varies, but the diff adds only constant-time metadata lookup after existing linear containment scans.
- Expensive boundaries: none found
- Verdict: No reportable regression. The richer metadata does not trigger heavier rendering, I/O, or retained state.

**Summary:** Reviewed all 10 changed files and every diff page. The PR adds static schema metadata plus bounded linear validation/completion/hover work. Parsing remains version-cached, diagnostics remain debounced, and no subprocess, IPC, network, database, or new filesystem work is introduced. No valid performance finding or evidenced shipped-regression fix was identified.
