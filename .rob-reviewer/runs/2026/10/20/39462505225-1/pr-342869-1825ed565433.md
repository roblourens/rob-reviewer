**Relevant issue families:** synchronous-ui-work, repeated-work, boundary-fanout, cache-lifecycle, cleanup-lifecycle

### Scenario 1: Switch the active customization harness/provider while the marketplace detail or customization lists are open

- Critical path: The harness observable synchronously calls bindInstallProvider, clears the prior request, clears provider installations, assigns the replacement binding, and emits one change. Existing UI observers may synchronously read getInstallState or the cached installation snapshot and update/filter visible items. The asynchronous provider inventory fetch is started only after the notification and is off the synchronous UI critical path.
- Scaling input: Synchronous observer work scales with the number of existing listeners and visible/observed customization items; snapshot reconstruction scales with recorded/provider installations but is lazily cached. The diff preserves exactly one binding-change event and therefore does not increase that cardinality.
- Effective concurrency: One refresh is initiated for each provider bind. providerRequest.clear cancels the prior token and refreshVersion/binding identity rejects stale completions; underlying host IPC may overlap during rapid switches because that API does not accept the token, but this behavior is unchanged by the diff.
- Cache behavior: emitChange invalidates installationSnapshot as before; the next observer read rebuilds it once and later reads reuse it. The replacement provider starts from an intentionally empty snapshot, and the provider receipt cache remains bounded and unchanged.
- Mechanism confidence: High: the changed hunk only moves the existing emitChange after providerBinding assignment within the same bind invocation; all event guards and the subsequent refresh call are unchanged.
- Magnitude uncertainty: Visible collection sizes and exact filtering/layout cost vary, but the diff does not add an event, rebuild, layout, or boundary call, so magnitude does not create a regression mechanism.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationMarketplaceInstallProvider.ts:258</code>: Load session-bound customization installation receipts through agentHostService.listCustomizationInstallations; cardinality: At most one new inventory request per provider bind; rapid provider switches can leave prior non-cancellable host calls briefly overlapping, while stale results are rejected by binding/version checks.
    - Introduced by diff: false; previous behavior: The same refreshProviderInstallations call occurred once after every provider binding, with the same placement, cancellation token, and stale-response guards.; critical-path effect: The call is asynchronous and does not block the synchronous binding-change notification or immediate install-state read; its eventual changed inventory can cause a later notification.
- Verdict: No reportable performance regression. Consumers perform the same amount of synchronous work once per provider switch; they now observe the replacement binding rather than the old one.

### Scenario 2: Complete the replacement provider's initial inventory refresh, including an empty inventory

- Critical path: After the binding-change event, refreshProviderInstallations awaits the provider inventory boundary, compares the returned array with the cleared providerInstallations array, and emits only if inventory differs. An empty result exits through the unchanged equality guard without a second notification.
- Scaling input: Comparison cost scales with the provider inventory length and snapshot rebuilding scales with installation count. The diff neither changes inventory size nor adds comparisons or refreshes.
- Effective concurrency: Refreshes for one binding are versioned so only the newest completion commits. Replacement cancels the prior request token and identity-checks responses; no new concurrency or burst was added.
- Cache behavior: Cold replacement state clears prior provider installations; equal empty results are a negative/empty success and do not re-emit. Non-empty results populate providerInstallations and invalidate the lazily rebuilt snapshot. All cache keys, bounds, and invalidation frequency are unchanged.
- Mechanism confidence: High: direct diff and call-path inspection show assignment/event reordering only, with refresh, deduplication, cancellation, and cache behavior untouched.
- Magnitude uncertainty: Provider inventory sizes and host latency vary, but boundary count and serialization work are unchanged, so there is no diff-caused performance impact.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceInstallService.ts:171</code>: Fetch the replacement provider's installation inventory; cardinality: One fetch per binding; provider onDidChange events can trigger further fetches, each versioned, exactly as before the diff.
    - Introduced by diff: false; previous behavior: The fetch, JSON serialization comparison, and conditional later notification had identical cardinality and ordering relative to request setup; only the earlier notification observed the old binding.; critical-path effect: This asynchronous fetch determines authoritative installed state but does not delay the initial binding notification; non-empty changes notify observers later, while empty inventories are handled by the initial notification.
- Verdict: No reportable performance regression and no qualifying performance-regression fix; the PR fixes synchronous state visibility rather than reducing a performance mechanism.

**Summary:** Reviewed the complete two-file diff and traced provider rebinding through synchronous UI observers, lazy snapshot construction, list filtering, async provider inventory retrieval, cancellation, stale-response rejection, and bounded provider receipt caching. The change preserves event and boundary-call cardinality and introduces no performance issue.
