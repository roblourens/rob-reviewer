# Performance review: Remove image preview in favor of core image previewer

[PR #341900](https://github.com/microsoft/vscode/pull/341900) at `ea5590365abffd0e992ae9c14126925b59c4e706`

## Findings (2)

### 1. [medium] Transfer the bitmap to the encoder worker

**Finding ID:** `PERF-FD24EFE1F0DF`  
**Location:** <code>src/vs/workbench/contrib/mediaPreview/browser/imageViewer.ts:620</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Decoded RGBA bitmap pixels serialized from the renderer main thread to the image encoder worker  
**Scaling:** The transfer cost scales with pixel area (roughly width × height × 4 bytes), not compressed file size; repeated copies repeat the allocation, and high-resolution photos can require tens or hundreds of megabytes.  
**Outcome:** Higher copy latency and a large transient memory/CPU spike while copying non-PNG images, with increased GC/OOM risk for high-resolution images.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The deleted image-preview implementation posted the ImageBitmap with worker.postMessage(bitmap, \[bitmap\]), transferring ownership without cloning its pixel payload.  
**Changed behavior:** The new implementation passes ImageBitmap as a regular argument to worker.proxy.$encodePng. WebWorkerProtocol.\_send only adds top-level ArrayBuffer arguments to its transfer list, so the ImageBitmap is structured-cloned instead of transferred before the worker encodes it.  
**Confidence:** 0.99 — The worker call and transport's transfer-list construction are explicit, and the removed code explicitly transferred the same bitmap. The trigger is every non-PNG Copy action; only the exact browser serialization duration varies.

**Causal diff evidence:** RIGHT line 620 replaces the deleted direct \`worker.postMessage(bitmap, \[bitmap\])\` call with an RPC call whose transport cannot transfer ImageBitmap objects.

Copying a typical JPEG/WebP photo now clones the full decoded bitmap between main thread and worker before PNG encoding. For an 8K image this is about 132 MiB of pixel data, on top of the canvas/worker encode allocations, delaying the Copy operation and sharply increasing peak memory.

**Evidence:** Added line 620 sends bitmap through the generic web-worker proxy. The unchanged WebWorkerProtocol transfer collection checks only \`arg instanceof ArrayBuffer\`; it never adds ImageBitmap. The removed implementation explicitly included the bitmap in postMessage's transfer list, proving the prior path avoided this serialization copy.

**Suggested direction:** Use a worker call path that accepts an explicit transferable list (or a dedicated Worker/MessagePort) and include the ImageBitmap, preserving the existing ArrayBuffer transfer for the encoded response. Add a transport-level test that observes the transferred bitmap rather than the current in-process mock.

### 2. [medium] Keep image preview loading streamed

**Finding ID:** `PERF-13B217999F6A`  
**Location:** <code>src/vs/workbench/contrib/mediaPreview/browser/imagePreviewEditor.ts:209</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Encoded image bytes in renderer memory, Blob backing storage, remote/local filesystem stream chunks, and decoded image pixels  
**Scaling:** Peak memory and time-to-first-decode grow linearly with the encoded file size; image diffs and multiple visible previews can incur this concurrently, and every file-change reload repeats it.  
**Outcome:** Increased preview latency plus renderer memory/GC pressure, with large or remote images needing the entire payload materialized before decoding can begin.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The removed image-preview webview assigned the webview resource URI directly to the img element. That resource path is served by loadLocalResource via IFileService.readFileStream and forwarded chunk-by-chunk (including over the remote filesystem IPC stream), so the workbench did not aggregate the complete encoded image into a VSBuffer before browser loading.  
**Changed behavior:** The new editor awaits IFileService.readFile for the complete image, then \_showImage constructs a Blob from that full buffer and only then starts img.decode(). IFileService.readFile explicitly consumes its source stream through streamToBuffer, so this moves full-file aggregation onto the preview-open and reload critical path.  
**Confidence:** 0.98 — The before/after paths and buffer aggregation are directly visible in the diff and file-service/webview implementations. Exact milliseconds depend on image size and provider speed, but the new O(file-size) renderer allocation and full-transfer-before-decode critical path are certain.

**Causal diff evidence:** RIGHT line 209 is the newly introduced full-file read on the image editor's setInput critical path; the deleted implementation supplied the resource URL to img.src and relied on the existing streaming webview loader.

Opening or reloading a large screenshot/photo, especially from vscode-remote or an extension filesystem, now waits for all bytes to cross the filesystem boundary and be concatenated before the browser can load it. During Blob creation the renderer can hold both the aggregated encoded buffer and Blob backing bytes in addition to the decoded bitmap; an image diff doubles the same pattern.

**Evidence:** Added line 209 invokes readFile on every ImagePreviewEditor load; fileService.doReadFile converts readFileStream to a complete buffer with streamToBuffer. Added line 254 then wraps that buffer in a Blob before ImageViewer.setSource begins decode. By contrast, the deleted extension created an asWebviewUri src, and unchanged webview resource loading uses readFileStream and forwards a transferable ReadableStream/chunks to the webview.

**Suggested direction:** Preserve resource-backed/streamed loading for display (for example, a narrowly scoped resource URL or streaming response path), and acquire encoded bytes separately only when Copy actually needs them. Keep cancellation and reload generation checks so superseded streams are stopped.

### Scenario 1: Open or reload an image preview, including both sides of an image diff and remote/extension-backed resources

- Critical path: setInput waits for Git-LFS detection where applicable, then the newly added full IFileService.readFile, Blob creation, and Image.decode before the preview is shown. Reloads are delayed/coalesced by 100 ms but still repeat this path.
- Scaling input: Encoded image byte size; one load per visible preview side, repeated per coalesced file-change burst. Side-by-side diffs can run two image loads concurrently.
- Effective concurrency: Each pane loads independently. A RunOnceScheduler coalesces file events within 100 ms, but already-started reload reads are not canceled; generation IDs only suppress stale presentation.
- Cache behavior: No byte cache exists for ImagePreviewEditor. The current Blob/object URL is retained only for the displayed image and revoked on replacement/clear. Every reload re-reads all bytes; Git-LFS checks are not cached.
- Mechanism confidence: High: the changed call path reaches readFile -&gt; streamToBuffer, followed by Blob construction and decode; the old path reaches the streaming webview resource loader.
- Magnitude uncertainty: Exact memory peak and latency depend on compressed size, decoded dimensions, provider speed, and whether Blob construction copies backing storage, but full-buffer aggregation and full-transfer-before-decode are certain.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/mediaPreview/browser/imagePreviewEditor.ts:209</code>: Read the entire encoded image through IFileService.readFile, which consumes and concatenates its source stream; cardinality: One complete read per initial open and per scheduled reload, or two concurrent reads for an image diff
    - Introduced by diff: true; previous behavior: The removed custom editor set img.src to a webview resource URI; webview resource loading used IFileService.readFileStream and forwarded chunks/transferable stream data instead of aggregating a full workbench buffer.; critical-path effect: The complete read and concatenation must finish before Blob creation and image decoding can begin.

### Scenario 2: Copy the displayed image from the image preview or carousel

- Critical path: PNG sources are read and validated, then written to the clipboard. Other formats are drawn into a full-resolution OffscreenCanvas, converted to ImageBitmap, sent to the encoder worker, encoded as PNG, returned as an ArrayBuffer, and finally written through browser clipboard or desktop native-host IPC.
- Scaling input: Decoded pixel area for non-PNG images (approximately width x height x 4), and compressed PNG byte size for PNG pass-through and clipboard IPC.
- Effective concurrency: Each Copy invocation creates a new worker client and encode. There is no coalescing or shared limiter, so repeated Copy invocations can overlap, though normal usage is one user-triggered operation at a time.
- Cache behavior: The displayed Blob is retained by the viewer/editor, avoiding a filesystem reread. Encoded PNG results are not cached. Worker clients are disposed after each encode.
- Mechanism confidence: High: WebWorkerProtocol only transfers top-level ArrayBuffer arguments, and the changed call supplies ImageBitmap.
- Magnitude uncertainty: Browser-specific structured-clone implementation affects exact copy duration, but the RPC transfer list definitively excludes ImageBitmap while the prior code explicitly transferred it. High-resolution photos make the pixel cardinality large.
- Expensive boundaries:
  - serialization at <code>src/vs/workbench/contrib/mediaPreview/browser/imageViewer.ts:620</code>: Send ImageBitmap through generic web-worker RPC without including it in the transfer list; cardinality: One full-resolution bitmap serialization per non-PNG Copy
    - Introduced by diff: true; previous behavior: The deleted implementation called worker.postMessage(bitmap, \[bitmap\]) and transferred ownership zero-copy.; critical-path effect: The bitmap must be serialized/cloned before worker encoding can proceed.
  - IPC at <code>src/vs/workbench/services/clipboard/electron-browser/clipboardService.ts:34</code>: Send encoded PNG bytes from renderer to Electron main and write via Electron clipboard; cardinality: One IPC payload per Copy on desktop, proportional to encoded PNG size
    - Introduced by diff: true; previous behavior: The extension wrote through navigator.clipboard inside the webview, so this native-host IPC boundary was absent; it replaces browser clipboard access for core workbench compatibility.; critical-path effect: Clipboard completion awaits the IPC write after encoding.
  - other expensive boundary at <code>src/vs/platform/clipboard/browser/clipboardService.ts:76</code>: Browser ClipboardItem write for web builds; cardinality: One clipboard write per Copy
    - Introduced by diff: true; previous behavior: The removed extension also used navigator.clipboard.write once per Copy.; critical-path effect: Clipboard completion awaits promised PNG bytes and browser clipboard write.
- Verdict: Reportable regression: non-PNG Copy loses the prior transferable ImageBitmap path and adds full-pixel serialization/allocation.

### Scenario 3: Navigate quickly through image carousel entries, including adjacent preloading and videos

- Critical path: Current image bytes are loaded or reused from the Blob cache, decoded asynchronously, then shown; metadata/thumbnail state updates immediately and adjacent entries are preloaded off the direct navigation completion path. - Scaling input: Number and byte size of distinct images visited or adjacent-preloaded; effective cache cardinality is unique image IDs in the current carousel generation.
- Effective concurrency: Current load plus up to two adjacent preloads may run concurrently. Rapid navigation can start independent per-image reads, but generation/index checks suppress stale presentation; concurrent same-ID results are deduplicated only after one completes, not coalesced in flight.

No negative cache exists for failed/missing images.
- Mechanism confidence: High for boundary counts/cache lifecycle; moderate for the magnitude of the added layout probe.
