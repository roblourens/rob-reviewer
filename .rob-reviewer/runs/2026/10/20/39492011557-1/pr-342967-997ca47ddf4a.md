# Performance review: Engineering - let a timed-out sign job be retried without 'artifact already exists'

[PR #342967](https://github.com/microsoft/vscode/pull/342967) at `997ca47ddf4a99adc6b8b460bf4e1c413f6c5039`

## Findings (1)

### 1. [medium] Avoid nesting retries in every Sign job

**Finding ID:** `PERF-42E70D09AD09`  
**Location:** <code>build/azure-pipelines/linux/product-build-linux.yml:170</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Azure DevOps artifacts API calls and occupied build-agent time  
**Scaling:** The nested retry cost is up to 10 outer attempts × 10 inner fetch attempts per Sign job, multiplied by up to seven concurrently enabled platform/architecture Sign jobs; hanging calls also multiply the fresh 2-minute outer timeout to about 20 minutes of wall time.  
**Outcome:** blocked release critical path and excessive network retries during service failures  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Before this PR, Windows, Linux, and macOS Sign jobs proceeded directly from packaging/signing to their outputs without querying the artifacts API. Only the two pre-existing macOS compile paths used this helper; the PR adds the nested-retry boundary to up to seven Sign jobs on the artifact-publication critical path.  
**Changed behavior:** Each Sign job now blocks output publication on an artifact-list network request. On retryable transport failures that request is retried by both checkForArtifact and requestAZDOAPI, and the new YAML instantiates this nested retry in up to seven parallel architecture jobs.  
**Confidence:** 0.97 — The call path and bounds are explicit: the changed YAML invokes checkForArtifact; checkForArtifact uses retry(getPipelineArtifacts); requestAZDOAPI uses retry(fetch); retry.ts runs 10 attempts; and requestAZDOAPI creates a fresh 2-minute abort timer per outer call. The production template instantiates two Windows, three Linux, and two macOS Sign jobs. Actual outage frequency is uncertain, which limits severity rather than confidence in the mechanism.

**Causal diff evidence:** The added final script step at build/azure-pipelines/linux/product-build-linux.yml:170 invokes checkForArtifact.ts in every Linux Sign job; equivalent added steps are present in the Windows and macOS Sign templates. checkForArtifact.ts wraps getPipelineArtifacts() in retry(), while getPipelineArtifacts() calls requestAZDOAPI(), whose fetch is already wrapped in the same 10-attempt retry helper and whose AbortController timeout is recreated at 2 minutes for every outer invocation.

During an Azure DevOps artifacts-API transport outage, each affected Sign job can remain blocked for roughly 20 minutes before falling back to the intended \`false\` variables, delaying artifact publication and consuming agents; across a full product build the seven new call sites can generate up to 700 fetch attempts. Even immediate transport failures create a large synchronized request burst against the unhealthy service.

**Evidence:** checkForArtifact.ts:31 calls retry(() =&gt; getPipelineArtifacts()), and getPipelineArtifacts delegates to publish.ts:572 requestAZDOAPI. requestAZDOAPI itself calls retry(fetch) at publish.ts:577 with a 2-minute AbortController at lines 573-574; retry.ts:9 permits 10 attempts. Thus a hanging/transport-failing API can cause 10 outer requests, each with up to 10 fetch attempts, and each outer hanging request can consume a fresh 2-minute timeout. Because this added step is the last user step before templateContext outputs, continueOnError does not let publication proceed until all retrying finishes.

**Suggested direction:** Remove the outer retry in checkForArtifact.ts and call getPipelineArtifacts() directly, relying on requestAZDOAPI's existing retry policy before setting all variables to false on failure. If the best-effort check needs a tighter release-path bound, also use a short explicit timeout, but do not stack another retry loop.

### Scenario 2: Retry after partial artifact publication

- Critical path: The retry still performs the pre-existing signing/package steps first, then the new check gates output processing. Existing artifacts skip their output work; missing artifacts continue to publication.

- Effective concurrency: Each retried job handles one grouped list request rather than one request per artifact. Different architecture jobs remain independent and may retry concurrently.
- Cache behavior: The build artifact service is the authoritative warm state. Already published names are detected from one list response; there is no stale local cache. A failed lookup deliberately behaves as all misses.
- Mechanism confidence: High: one grouped request supplies all variables, and each added condition directly suppresses the matching output.
- Magnitude uncertainty: The number and size of artifacts already present varies with where the earlier attempt stopped, so upload savings vary.
- Expensive boundaries:
  - network at <code>build/azure-pipelines/common/checkForArtifact.ts:main</code>: Read existing artifact names after an earlier attempt partially published outputs.; cardinality: One artifacts-list GET serves all four to six names in a job.
    - Introduced by diff: true; previous behavior: No preflight read occurred; output processing attempted every artifact and an immutable-name conflict could fail the retried job.; critical-path effect: The GET must finish before any remaining artifact can publish.
  - network at <code>added conditions on templateContext.outputs in each platform product-build YAML</code>: Publish missing artifacts; conditions suppress already existing ones.; cardinality: Only outputs absent from the returned list publish; effective count ranges from zero to all outputs.
    - Introduced by diff: false; previous behavior: Every configured output attempted publication, including immutable artifacts from an earlier attempt.; critical-path effect: Skipping existing outputs avoids their upload/SBOM work and allows missing outputs to proceed.
- Verdict: The changed successful-retry path is performance-positive overall: one grouped metadata read can avoid multiple large artifact/SBOM publications and repeated failing job attempts.

### Scenario 3: Artifacts API transport failure during product build

- Critical path: The final check cannot reach its catch/fallback until nested retries finish. continueOnError changes the task result but does not bypass the wait, so all artifact publication remains blocked.
- Scaling input: Retry layers (10×10), enabled architecture jobs (up to seven), and whether each network failure returns immediately or waits for the two-minute abort.
- Effective concurrency: Up to seven jobs can enter the failure path together. Within each job retries are nominally sequential, but checkForArtifact's 10-attempt retry wraps requestAZDOAPI's own 10-attempt fetch retry.
- Cache behavior: There is no negative cache or cross-job failure coalescing. Each outer attempt creates a new request and timeout, and every job retries independently against the unhealthy service.
- Mechanism confidence: Very high: both 10-attempt loops, the fresh two-minute timeout per outer request, the final-step placement, and seven added production call sites are directly traced.
- Magnitude uncertainty: The prevalence and duration of Azure DevOps transport outages are not measured in the repository; immediate HTTP 5xx responses exercise only the outer ten attempts, while transport failures/timeouts exercise both loops.
- Expensive boundaries:
  - network at <code>added script at build/azure-pipelines/linux/product-build-linux.yml:170 and equivalent Windows/macOS additions -&gt; checkForArtifact.ts:31 -&gt; publish.ts:requestAZDOAPI</code>: Retry listing build artifacts during a transport failure or timeout.; cardinality: Up to 10 outer requestAZDOAPI calls × 10 fetch attempts per job, multiplied by up to seven jobs (700 fetch attempts). - Verdict: Reportable medium-severity network/latency regression: the PR materially amplifies a nested retry mechanism onto seven release-critical Sign jobs.
