**Relevant issue families:** repeated-work, synchronous-ui-work, serialization-allocation, boundary-fanout

### Scenario 1: Live and replayed HydraFusion workflow milestones in chat

- Critical path: Each incoming or restored system notification is decoded before publishing chat progress; activity updates also scan the leading response parts. The changed selected milestone returns no UI part, while terminal milestones continue normally.
- Scaling input: Number of leading Fusion system notifications in one turn; realistically a small workflow phase count. The scan short-circuits at the first answer, tool, or non-Fusion notification.
- Effective concurrency: Synchronous per notification and observable update; no parallel work, queue, or backpressure was added.
- Cache behavior: Metadata is read directly from each response part with no cache. Cold and warm behavior are equivalent; the diff removes description metadata and selected-row rendering rather than introducing cache misses.
- Mechanism confidence: High: changed host and adapter lines remove Markdown construction, metadata serialization, and DOM rendering for selected milestones; the replacement activity loop has the same linear, early-exit shape as the prior every() scan.
- Magnitude uncertainty: Exact UI savings vary with hint length and history size, but there is no added expensive work.
- Expensive boundaries: none found
- Verdict: No regression. The changed path reduces serialized content and rendering work; the remaining scan is bounded by the turn's leading milestone count.

### Scenario 2: Opening, refreshing, labeling, and hovering the model picker with provider-backed Fusion tiers

- Critical path: Picker refresh synchronously builds routing rows/cards and the input label; hover text is computed on hover. The new work consists of in-memory model lookups and scans of the selected model's configuration-schema properties.
- Scaling input: Model catalog size, at most two known HydraFusion IDs, and the small property list of one Fusion schema. Effective HydraFusion cardinality remains two after filtering.
- Effective concurrency: Entirely synchronous UI construction; no asynchronous fan-out or concurrent resource creation is introduced.
- Cache behavior: The model catalog and configuration schema are already in memory. Scoped model configuration reads use the existing store cache; no new cache key, miss path, or negative-cache behavior is added.
- Mechanism confidence: High: all new presentation operations are array/object scans and string formatting over in-memory metadata; no DOM geometry reads, layout forcing, IPC, filesystem, or network calls are reached.
- Magnitude uncertainty: Provider schema property counts can vary, but realistic schemas are small and the new scans are only for the two recognized HydraFusion IDs.
- Expensive boundaries: none found
- Verdict: No reportable regression. Added work is bounded metadata lookup and string formatting on picker render/hover paths.

### Scenario 3: Choosing a provider-backed HydraFusion tier from Fusion details

- Critical path: The click now saves the Fusion tier, awaits that save, then applies the Fusion model selection and refreshes the card. This is on the explicit user-selection critical path.
- Scaling input: One configuration edit per explicit tier activation. Rapid edits are serialized per model by SequencerByKey rather than executed concurrently.
- Effective concurrency: Per-model serialization through SequencerByKey; distinct models may proceed independently, but this interaction edits one Fusion model. No concurrency burst is introduced.
- Cache behavior: The scoped configuration store keeps effective values in memory and suppresses redundant persistence when the selected value is unchanged. A real change updates the scoped storage bucket and mirrors the profile-global configuration.
- Mechanism confidence: High that one save is newly reached for this interaction; high that it is bounded and coalesced against no-op persistence.
- Magnitude uncertainty: Storage latency varies by platform, but the operation is fixed-cardinality, user-initiated, serialized, and required to persist the newly selected tier semantics.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerModelConfig.ts:setModelConfigValues -&gt; chatModelConfigurationStore.ts:setModelConfiguration -&gt; languageModels.ts:setModelConfiguration</code>: Persist the editor-scoped model configuration through storageService and mirror the profile-global language-model provider-group configuration.; cardinality: At most one serialized save for each explicit changed tier click; reselecting the current value is suppressed by the scoped store.
    - Introduced by diff: true; previous behavior: For the replaced provider tier, the card treated the HydraFusion entry as a standalone routing alternative and selected that model directly instead of saving Fusion's tier.; critical-path effect: The changed interaction awaits the save before applying the model selection, so one persistence operation is on the click path.
- Verdict: No reportable regression. The newly reached boundary is a single bounded persistence operation necessary for the changed selection behavior, not fan-out or repeated background work.

### Scenario 4: Naming HydraFusion responses in response footers

- Critical path: When response details are finalized, the handler resolves the in-memory Fusion model and derives the provider tier label before formatting footer text.
- Scaling input: One lookup per completed response whose runtime reports a HydraFusion response model; schema scan cost scales with one model's configuration property count.
- Effective concurrency: Synchronous formatting within response-detail creation; no queue or parallel work is added.
- Cache behavior: Language-model metadata is obtained from the existing turn model lookup/cache. No network fetch or cache invalidation is introduced.
- Mechanism confidence: High: the transitive path reaches only metadata lookup, localization, and string formatting.
- Magnitude uncertainty: Schema size and response frequency vary, but each response performs only a small in-memory scan.
- Expensive boundaries: none found
- Verdict: No reportable regression. Provider-tier naming adds bounded in-memory work per completed response.
