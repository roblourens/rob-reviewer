### Scenario 2: A marker source or editor decoration count crosses a limit and updates the active editor's Problems language-status warning.

- Critical path: Marker-limit change synchronously calls DiagnosticDecorationLimitReporter.\_update, formats one detail string only when a limit exists, fires only when the resulting limited state changes, then disposes/registers one language status. The changed wording stays on the same path and adds no await or expensive boundary.
- Scaling input: One active editor and one status entry per state transition. Diagnostic count can exceed 5,000, but only the numeric limit is interpolated; message construction does not iterate over diagnostics and the effective status cardinality remains one.
- Effective concurrency: Synchronous event handling for the active editor. Background-editor marker changes are ignored by the active LanguageStatusEntry listener, and identical over-limit states are coalesced by the limited-string equality check.
- Cache behavior: No new cache is introduced. The localized format uses the existing in-memory NLS lookup, and an unchanged limited string suppresses repeat status recreation; cold and warm behavior are identical before and after the diff.
- Mechanism confidence: High confidence from tracing marker-limit events through \_update, \_getLimitedMessage, LanguageStatusEntry.updateStatusItem, and LanguageStatusServiceImpl.addStatus.
- Magnitude uncertainty: Exact status-bar rendering cost is not measured, but the diff neither changes rendering frequency nor adds layout/DOM work; only bounded text content changes.
- Expensive boundaries: none found
- Verdict: No reportable regression. Constant wording changes neither fan out per diagnostic nor increase event, localization, registration, or rendering frequency.

### Scenario 3: The user switches active editors while a diagnostic limit warning is present.

- Critical path: The active-editor event disposes the previous listener/status, reads the selected editor's limit reporter, and registers at most one warning. The changed accessor strings are reused and the detail string follows the existing formatting path.
- Scaling input: One selected editor and at most one diagnostic status per switch; background diagnostics do not multiply work on this path.
- Effective concurrency: Editor switches are processed synchronously and serially by the event source; prior listener ownership is disposed before the new listener is installed.
- Cache behavior: No new cache or miss behavior. Accessor metadata remains retained for the contribution lifetime exactly as before, and status lifetime remains bounded by editor selection and contribution disposal.
- Mechanism confidence: High confidence from the active-editor handler, disposal path, and tests demonstrating background changes do not recreate the active warning.
- Magnitude uncertainty: No material uncertainty: changed strings do not alter listener count, lifecycle, or status cardinality.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff does not affect cleanup, concurrency, retained state, or per-switch work.
