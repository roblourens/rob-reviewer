# Performance review: test: run Agent Host E2E as its own test unit in GitHub Actions and ADO

[PR #342346](https://github.com/microsoft/vscode/pull/342346) at `9daad9eaf1b9450f46dd21b8149f2b4ef4e25e0b`

## Findings (1)

### 1. [medium] Do not serialize the full integration suite after E2E has failed

**Finding ID:** `PERF-2CD69C1A2C42`  
**Location:** <code>.github/workflows/pr-linux-test.yml:362</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** an additional full Electron integration subprocess tree and its CPU, memory, and filesystem work  
**Scaling:** The added cost is one complete non-E2E integration suite per platform for every E2E failure; the steps are serialized, so all of that suite's duration is added directly to failed-job latency.  
**Outcome:** blocked critical path and increased CI runner time after a definitive test failure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Agent Host E2E ran at the start of \`test-integration.sh\`/\`.bat\`; a nonzero runner exit stopped the script before the node and extension-host integration suites, so failed jobs did not pay for that remaining work.  
**Changed behavior:** A failed Agent Host E2E step is now followed serially by the unrelated Electron integration suite on each affected GitHub Actions platform, rather than ending the test command immediately.  
**Confidence:** 0.98 — The changed status-function condition, sequential workflow order, full integration command, 20-minute timeout, and prior shell/batch fail-fast control flow are all explicit in the repository. Exact duration varies by platform, but the added critical-path subprocess and its serialization are certain.

**Causal diff evidence:** The added RIGHT-side condition at .github/workflows/pr-linux-test.yml:362 explicitly admits \`steps.agent-host-e2e.outcome == 'failure'\`, so the following full \`./scripts/test-integration.sh\` subprocess runs after the new E2E step has failed. The same condition is added on macOS and Windows. Before this diff, \`test-integration.sh\` invoked \`node ./test/integration/agentHost/runner.ts\` under \`set -e\` (and the batch script used \`if errorlevel 1 goto :failed\`), so an E2E failure terminated the combined step before the remaining integration suite started.

Whenever Agent Host E2E fails or flakes, the PR job retains the runner and delays the already-known failure result by one complete Electron integration run (up to the new 20-minute timeout on each platform), increasing CI latency and runner consumption precisely on failed runs.

**Evidence:** \`test/integration/agentHost/runner.ts\` runs six E2E entrypoints via child processes and returns a nonzero exit when any fails. The added workflow step runs that runner first; line 362 then overrides GitHub Actions' normal success gating and launches \`scripts/test-integration.sh\`, whose unfiltered path runs all non-E2E node integration tests followed by extension-host suites. These are sequential workflow steps on the same runner, with the second step capped at 20 minutes. Previously the E2E runner lived inside \`test-integration.sh\`; \`set -e\` on Unix and \`goto :failed\` on Windows prevented the remaining suites from running after its failure.

**Suggested direction:** Preserve collection of both results without serializing them: move Agent Host E2E and the regular integration suite to independent jobs/runner executions so they can run concurrently. Until that split exists, retain normal fail-fast gating instead of forcing the regular suite to start after E2E failure.

### Scenario 5: Azure DevOps flaky-detection iterations

- Critical path: Within every iteration, E2E remains before regular integration. Because both steps use continueOnError, the regular suite now also runs after an E2E failure; this intentionally collects both flaky-test results but lengthens that failing iteration.
- Scaling input: Effective configured iterations after Windows odd/even sharding; one extra regular suite for each iteration whose E2E unit fails.
- Effective concurrency: Iterations and the two units within each iteration are serialized, except for the E2E runner's internal suite workers. Windows shards divide configured iterations before execution.
- Cache behavior: Packaged builds are extracted once and reused across configured iterations. VSCODE\_SKIP\_PRELAUNCH=1 avoids downloads; there is no per-iteration checkpoint.
- Mechanism confidence: High: task order, continueOnError, and prior script fail-fast behavior are explicit.
- Magnitude uncertainty: Configured iteration count and failure rate vary. The added failure-path work is certain, but this pipeline's explicit purpose is to collect independent flaky results.
- Expensive boundaries:
  - subprocess at <code>build/azure-pipelines/{linux,darwin,win32}/product-smoke-flaky-\*.yml</code>: Run E2E and regular integration as separate continue-on-error tasks.; cardinality: Per effective iteration: six E2E suite subprocesses followed by the complete regular integration subprocess tree.
    - Introduced by diff: true; previous behavior: One integration script ran E2E first and exited before regular integration on E2E failure, though the pipeline continued to later iterations.; critical-path effect: Successful iteration cost is unchanged; after E2E failure, the regular integration tree is newly executed before the iteration sequence advances.
- Verdict: The same failure-path eager work exists, but it is an explicit diagnostic tradeoff in a flaky-detection pipeline; no duplicate finding beyond the actionable PR-job critical-path issue.

- Verdict: No reportable regression: command scope intentionally changes, worker concurrency remains bounded, and cold runtime preparation is guarded by existing positive checks.
