# Performance review: ci: run Agent Host E2E tests in their own job

[PR #342735](https://github.com/microsoft/vscode/pull/342735) at `8b165a6dafd751cde7554f483aabb98fa1b66c0b`

## Findings (1)

### 1. [medium] Keep single-producer checks off the reporter matrix

**Finding ID:** `PERF-734BEF0D1B1C`  
**Location:** <code>.github/workflows/pr.yml:482</code> (<code>RIGHT</code>)  
**Performance category:** <code>throughput</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Six GitHub-hosted Ubuntu runner VMs plus their startup and jq process work per pull-request run.  
**Scaling:** The cost is a fixed six runner allocations per workflow run and therefore grows linearly with PR update frequency and concurrent PR volume; within one run they join the 15-child reporter burst after the shared dependency barrier.  
**Outcome:** Excessive runner allocation and a burst of avoidable CI work on the required-check completion path, which can lower concurrent workflow throughput and delay status completion.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, each platform's Electron-Unit and Remote reusable workflow job directly emitted its required \`&lt;OS&gt; / &lt;job&gt;\` status, so these six statuses required no separate reporter runners. Only the three Browser and three sharded Smoke statuses used aggregation jobs.  
**Changed behavior:** Every PR now expands six additional \`required-checks\` matrix children for the three Electron-Unit and three Remote statuses. Each child allocates an \`ubuntu-24.04\` runner, waits for the shared dependency barrier, runs jq over \`needs\`, and exits, even though its status is a direct pass-through from one test job.  
**Confidence:** 0.98 — The matrix cardinality, \`runs-on\`, \`if: always()\`, and one-element \`parts\` arrays are explicit in the changed workflow. The base diff shows Electron-Unit and Remote reusable jobs previously reported the required names directly, while only Browser and Smoke needed aggregators. The only uncertainty is exact runner queue/setup duration, not whether six runner allocations occur on every PR.

**Causal diff evidence:** The added \`required-checks\` matrix entry at \`.github/workflows/pr.yml:482\` creates a reporter job for \`Linux / Electron-Unit\`; the same added matrix block does this for Electron-Unit and Remote on all three platforms. These six checks each have exactly one \`parts\` producer, unlike Electron, Browser, and sharded Smoke checks that actually require aggregation.

Every PR consumes six unnecessary GitHub-hosted runner starts and slots after the test phase, adding final check-reporting latency when runners queue and reducing CI throughput across concurrent PRs. The waste is especially visible for documentation/Rust-only changes, where expensive tests are correctly skipped but these six VMs still start solely to relay \`skipped\` as success.

**Evidence:** \`required-checks\` runs on \`ubuntu-24.04\` with one matrix child per \`check\`. Six newly added entries—Electron-Unit and Remote for Linux, macOS, and Windows—contain one producer each, so they perform no aggregation. Because the job uses \`if: ${{ always() }}\`, these six runner VMs are requested even when change detection skipped their test jobs. The repository's changed workflow comment also establishes that a reusable workflow can preserve a required status while skipping its inner job, so these pass-through runners are not necessary to retain path-based skipping.

**Suggested direction:** Keep aggregation only for multi-producer Electron, Browser, and Smoke checks. For Electron-Unit and Remote, pass the detection result into the reusable workflow, apply the skip condition to its inner job (the pattern documented at the top of this workflow), restore the required check name on that job, and remove these six single-part matrix entries and dependencies.


## Performance regression fixes detected (1)

### 1. concurrency-burst

**Fix location:** `.github/workflows/pr.yml:385` (`RIGHT`)  
**Blamed base line:** `.github/workflows/pr-win32-test.yml:233`  
**Introducing path:** `.github/workflows/pr-win32-test.yml`  
**Introducing commit:** `e886b81b9b9d4a39d8e397c33e76ce04d5cbbe85`  
**Mechanism family:** `concurrency-burst`  
**Performance category:** `latency`  
**Confidence:** 0.99

**Mechanism:** Agent Host E2E launched up to five test processes but the entire suite was sequenced before the Electron integration subprocess in one runner job, so integration could not start until the E2E suite completed.

**Symptom:** PR Windows / Electron checks that selected Agent Host E2E spent roughly 15 additional minutes on the serial critical path (about 37.5 minutes total per the traced workflow scenario), with analogous smaller delays on Linux and macOS.

**Fixed behavior:** The Agent Host E2E subprocess suite now runs on a separate Windows runner in parallel with Electron integration tests, removing its approximately 15-minute suite duration from the serial Windows Electron critical path; the required check still joins both results.

**Evidence:** In the base workflow, blame line 233 identifies the Agent Host E2E step introduced by e886b81b9b9d4a39d8e397c33e76ce04d5cbbe85. The base diff shows that this 30-minute subprocess suite ran in the same Windows reusable-workflow job immediately before `test-integration.bat`, whose condition explicitly allowed it to proceed after the E2E step. The PR adds `windows-agent-host-e2e-tests` as a distinct reusable-workflow invocation and passes `integration_tests: false`, while the existing Electron job no longer enables Agent Host E2E, so the two runner jobs can execute concurrently.
