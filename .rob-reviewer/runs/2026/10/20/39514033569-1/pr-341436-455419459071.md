# Performance review: NES: add applied-then-undone rejected-edit memory mode

[PR #341436](https://github.com/microsoft/vscode/pull/341436) at `45541945907178eb163f72f9a60e4abb59d843cc`

## Findings (1)

### 1. [medium] Cap repetitions before materializing rejected history

**Finding ID:** `PERF-4561C7824AED`  
**Location:** <code>extensions/copilot/src/extension/xtab/common/diffHistoryForPrompt.ts:211</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** temporary arrays and repeated prompt-string bytes  
**Scaling:** O(R \* S) temporary objects and bytes per next-edit request, where R is the unbounded configured repetition count and S is the applied/undone rejected-diff size (up to roughly twice the retained 3000-character rejection payload, plus headers); up to three retained rejections can trigger this work.  
**Outcome:** increased inline-edit latency and CPU/GC pressure, potentially process memory exhaustion  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no repetition option and each rejected edit rendered once, so prompt construction remained bounded by the three-entry/3000-character rejection-history limits.  
**Changed behavior:** Applied-then-undone rejection rendering now eagerly creates one full applied/undone string pair per configured repetition before token-budget checks run.  
**Confidence:** 0.99 — The call path is direct: each next-edit request calls \`getUserPrompt\`, which calls \`getEditDiffHistory\`, which invokes this renderer for a retained rejection. \`vNumber()\` checks only \`typeof\`, JSON model configuration can contain arbitrarily large finite numbers, and both \`computeTokens(docDiff)\` and the 120K final prompt guard execute only after this allocation. Rejection history itself is bounded to three entries and 3000 characters each, but configured repetition count is unbounded.

**Causal diff evidence:** RIGHT line 211 newly calls \`Array.from({ length: repetitions }, ...)\`, where \`repetitions\` comes from the new \`memory.rejectedEditsRepetitions\` option. The same diff validates that option only with \`vNumber()\`, and line 70 clamps only the lower bound, not the upper bound.

With applied-then-undone enabled and at least one retained rejection, a large or accidentally mistyped repetition value makes every subsequent inline-edit request synchronously allocate and scan megabytes or more of throwaway prompt text before rejecting it as over budget. This causes request latency, CPU/GC spikes, and at sufficiently large values can exhaust memory, even though no oversized prompt can be sent.

**Evidence:** \`repetitions\` is derived as \`Math.max(1, Math.floor(memory?.rejectedEditsRepetitions ?? 1))\` without a maximum. This line allocates an array of that length, creates a full interpolated pair for every element, and joins all pairs. Only after it returns does \`getEditDiffHistory\` call \`computeTokens(docDiff)\` and compare against \`maxTokens\`; the provider's 120K-character hard limit is later still. The model configuration parser accepts any JSON number because \`vNumber()\` performs only a \`typeof\` check.

**Suggested direction:** Validate \`rejectedEditsRepetitions\` as a small bounded integer and enforce that bound again at rendering; preferably compute one pair's token/character cost and stop before materializing repetitions that cannot fit the remaining history budget.
