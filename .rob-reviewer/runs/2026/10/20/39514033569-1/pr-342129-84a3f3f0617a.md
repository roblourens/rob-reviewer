# Performance review: Recommend connectors from prompt URLs

[PR #342129](https://github.com/microsoft/vscode/pull/342129) at `84a3f3f0617a5f1759aba7a6bf4db74c618d5128`

## Findings (1)

### 1. [medium] Avoid reparsing the entire prompt on every keystroke

**Finding ID:** `PERF-CCE859FBAD62`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/newChatConnectorRecommendations.ts:67</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** UI-thread CPU plus temporary full-input/token strings, sets, and URL objects.  
**Scaling:** Each edit costs O(L) in prompt length plus token allocations (and a small current connector-domain factor); appending N characters one by one is O(N^2) cumulative parsing, while K edits after pasting an L-character prompt cost O(K\*L).  
**Outcome:** Increased input latency and potential dropped frames while editing long prompts, with additional GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, connector recommendations were static cards initialized once; the component did not subscribe to prompt changes or read/tokenize the editor model on each edit.  
**Changed behavior:** Every new-session editor content change now synchronously reads the full Monaco model and reparses the entire prompt for connector URLs before the input event returns.  
**Confidence:** 0.96 — The call path is explicit: SharedChatInputComposer forwards each inputEditor.onDidChangeModelContent event through onDidChangeInput; the new listener calls update immediately; getInputValue reaches inputEditor.getValue; and the new matcher loops through input.length while allocating token slices/lowercase strings. The composer and restored/prefilled draft paths impose no text-length bound. Exact milliseconds depend on prompt size, so severity is medium rather than high.

**Causal diff evidence:** The added subscription at line 67 invokes update() synchronously for every composer input event; update() then calls findMatchingConnectorRecommendationIds(this.options.getInputValue(), ...) at line 117. That new helper walks the entire string, slices every whitespace-delimited token, lowercases it, and constructs URL objects for URL-like tokens.

After a user pastes or restores a long prompt and continues typing, each keystroke performs a full synchronous reparse on the renderer/UI thread, increasing key-to-paint latency and temporary-allocation/GC pressure; sufficiently large prompts can visibly hitch typing.

**Evidence:** SharedChatInputComposer fires onDidChangeInput directly from Monaco's onDidChangeModelContent and getInputValue() returns ChatWidget.getInput(), which calls inputEditor.getValue(). The newly added matcher iterates from 0 through input.length on every call, slices each token, lowercases it, and may instantiate URL for each URL-like token; no debounce, scheduler, length cap, or incremental cache exists. Even when the connector match set is unchanged, update() completes this scan and constructs a candidate tip before its tipStateKey early return.

**Suggested direction:** Keep URL recommendation work off the immediate content-change path: coalesce/debounce to the latest prompt and update an incremental token/hostname cache from Monaco change ranges (or otherwise bound the scanned text). Also create the Markdown tip only after the matched ID set actually changes.

### Scenario 1: Typing or editing a new-session prompt after pasting/restoring substantial text

- Critical path: Monaco onDidChangeModelContent synchronously fires SharedChatInputComposer.onDidChangeInput, whose new listener calls update(), inputEditor.getValue(), and the full URL matcher before the edit handler returns.
- Scaling input: Full prompt length and whitespace-delimited token count on every edit; current connector/domain metadata is small (the described rollout has six connectors), so prompt length is the dominant factor.
- Effective concurrency: Single-threaded and serialized on the renderer/UI event path; rapid edits are not debounced or coalesced, so every delivered model-change event performs a scan.
- Cache behavior: There is no scan-result cache or coalescing; each editor change rereads and reparses the latest full prompt. Connector metadata is held in maps, but token/hostname results are discarded after every event.
- Mechanism confidence: High: the synchronous event-to-full-scan call path and per-token allocations are explicit in the code.
- Magnitude uncertainty: Normal short prompts make the scan cheap; the exact prompt length and device speed needed for visible jank are unmeasured. Restored drafts, command-prefilled prompts, and direct editor input are not length-bounded, so long prompts are realistically reachable.
- Expensive boundaries: none found
- Verdict: Reportable medium-severity repeated-work regression: the diff adds an unbounded O(prompt length) synchronous parse and allocations to every input event, whereas the prior recommendation UI did no per-edit work.
