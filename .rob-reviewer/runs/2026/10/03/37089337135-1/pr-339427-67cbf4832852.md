### Scenario 1: Agent-host MCP inventory discovery and publication for Copilot and Codex sessions

- Critical path: Copilot performs the existing mcp.list RPC, maps the returned servers, and applies the inventory before publishing changed customizations; Codex applies its already-materialized inventory when sessions or configuration change. The diff adds display-name/source-plugin metadata and an in-memory provenance lookup but no new required boundary.
- Scaling input: Number of MCP servers in one inventory and, for Codex, number of live sessions sharing the inventory. Typical inventories are small; application remains serial and transaction-coalesced per controller.
- Effective concurrency: Copilot inventory refreshes are versioned so stale concurrent requests are discarded; controller application is synchronous and serial inside one transaction. Codex iterates sessions serially. No new burst or parallel boundary was introduced.
- Cache behavior: The controller retains the latest per-server customization and preserves metadata across lifecycle-only updates. Unchanged inventories compare equal and emit nothing. No new cache, miss retry, or negative-cache behavior was added.
- Mechanism confidence: High: the RPC, transaction, equality deduplication, and new metadata helper call paths were traced directly.
- Magnitude uncertainty: Very large inventories would add another linear published-customization scan/allocation during first/restored top-level reconciliation, but it is in-memory, short-lived, and not repeated on normal lifecycle updates because the live customization is retained.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_refreshMcpServersFromRpc</code>: Copilot SDK mcp.list inventory RPC; cardinality: One RPC for initial seeding and each existing inventory invalidation, with an existing retry only if a lifecycle event overtakes the snapshot; one result covers all servers.
    - Introduced by diff: false; previous behavior: The same mcp.list RPC and optional user-server-name lookup already occurred; the diff only forwards two additional optional fields from each returned server.; critical-path effect: The RPC must finish before the refreshed inventory is applied, exactly as before the diff.
  - IPC at <code>src/vs/platform/agentHost/node/shared/mcpCustomizationController.ts:\_applyOne</code>: Session customization update dispatch carrying MCP server state and metadata; cardinality: At most one existing update per server whose published customization changes; unchanged inventories remain deduplicated by structural equality.
    - Introduced by diff: false; previous behavior: Per-server customization updates already crossed this boundary for state/source changes; display/source-plugin changes can now legitimately trigger the same update so the UI can reflect them.; critical-path effect: Updates notify clients after in-memory inventory reconciliation; payloads gain at most two short optional metadata strings per changed server.
- Verdict: No reportable regression. Added CPU/allocation and serialized bytes are bounded by server count and required to publish the new metadata; no new external call, concurrency burst, or hot repeated work was introduced.

### Scenario 2: Opening, refreshing, and searching the Chat Customizations MCP server list

- Critical path: The widget reads an already-materialized server snapshot, matches local/runtime/host entries, computes grouping and membership, then renders or updates visible rows. Search remains delayed/coalesced before filtering.
- Scaling input: Installed, built-in, connector, and active-session MCP server counts; effective cardinality is one deduplicated row per presented server after matching.
- Effective concurrency: Filtering and rendering are synchronous on the UI thread; search uses the pre-existing delayed filter, and customization events run one serial refresh/update pass. No new asynchronous fan-out was introduced.
- Cache behavior: The widget consumes existing observable/service snapshots. Membership signatures now include the display label so a real label change rebuilds rows; state-only updates continue using row updates. No cold/warm external cache behavior changed.
- Mechanism confidence: High: list event handlers, matching, membership comparison, row listeners, and search debounce were inspected.
- Magnitude uncertainty: A display-name-only inventory change can cause a full list rebuild, but such changes are inventory events rather than keystroke/frame events and realistic lists are bounded; the work is necessary to update the visible label.
- Expensive boundaries: none found
- Verdict: No reportable regression. New work is short string validation/comparison and one additional label search predicate; there are no new filesystem, network, IPC, layout-read, or process boundaries on list refresh.

### Scenario 3: Selecting an MCP server detail and invoking provenance, settings, or configuration actions

- Critical path: Selection constructs one detail input and renders provenance plus either the existing source-backed definition, one host-held configuration, or an unavailable-definition message. Extension/settings/configuration actions execute only after explicit user clicks.
- Scaling input: One selected server and the size of its single configuration object or source file; there is no per-list-item eager detail work.
- Effective concurrency: One selected detail generation is active; generation checks discard stale file-read results. Click actions execute individually with no burst scheduling.
- Cache behavior: The code editor/model remains lazily created on the first actual definition. Host-held configuration is already in session state; no new cache or repeated fetch is used.
- Mechanism confidence: High: selection construction, render branches, lazy editor creation, filesystem reads, and click handlers were traced.
- Magnitude uncertainty: A user-provided host configuration can be large and is JSON-serialized when selected, but only one selected definition is processed and this is the requested visible content.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/embeddedMcpServerDetail.ts:loadSourceDefinition/editConfiguration</code>: Read a source configuration file to display or edit its MCP definition; cardinality: At most one read for the selected source-backed server render, plus an edit-time read only when no range is known.
    - Introduced by diff: false; previous behavior: Source-backed details already read the selected configuration file. The new host-configuration path serializes already-held state instead of adding a read.; critical-path effect: The display read remains on the selected detail's loading path; host-only provenance/configuration states added by the diff do not perform this read.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/embeddedMcpServerDetail.ts:renderDefinitionEmpty and src/vs/workbench/contrib/chat/browser/aiCustomization/mcpListWidget.ts:getBuiltinMcpServerSourceAction</code>: Open Settings, extension details, or show configuration through existing command/service APIs; cardinality: One command/service call per explicit user click.
    - Introduced by diff: true; previous behavior: These provenance-specific actions were unavailable, so there was no corresponding call; the diff does not invoke them eagerly.; critical-path effect: Off the initial render critical path; only the selected user action waits for it.
- Verdict: No reportable regression. New provenance DOM is small and on demand; newly reachable IPC actions are user-triggered and off render, while existing source-file I/O is unchanged.
