## Findings (3)

### 1. [medium] Move native input telemetry off the response-start path

**Finding ID:** `PERF-C6784E5202C0`  
**Location:** <code>extensions/copilot/src/extension/prompt/node/chatMLFetcher.ts:1626</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU work, large strings, telemetry event objects, and gzip input buffers  
**Scaling:** The synchronous work grows with the complete Responses API history: every message is classified and hashed, every new message is JSON-serialized, and one internal event is created per 8,000 characters; deduplication still hashes the full content on every request.  
**Outcome:** Increased time to start consuming the response stream, plus CPU and allocation/GC pressure on long agent conversations.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** This same finally block converted Responses history through responseApiInputToRawMessagesForLogging/rawMessageToCAPI, which reduced reasoning to a short summary placeholder and omitted compaction and image-generation items before telemetry processing.  
**Changed behavior:** The changed line now preserves complete provider-native reasoning, encrypted compaction state, and generated-image data, then passes that expanded history to sendEngineMessagesTelemetry synchronously from the postRequest Promise's finally handler.  
**Confidence:** 0.98 — The Promise.finally ordering, expanded data shape, synchronous hash/serialization implementation, and downstream stream-start call path are all directly visible. Exact milliseconds vary with history size and telemetry configuration, but the added critical-path work and linear/per-8K scaling are deterministic.

**Causal diff evidence:** RIGHT line 1626 replaces the compact logging conversion with responseApiInputToTelemetryMessages; that converter returns full reasoning/compaction items and image results, and unchanged line 1633 synchronously invokes sendEngineMessagesTelemetry before the postRequest Promise can settle.

A long Responses conversation—especially one carrying reasoning/compaction state or an image-generation result—adds telemetry CPU and allocation latency between receiving headers and reading the first response chunks, delaying first-token display and every subsequent agent model call.

**Evidence:** The HTTP request Promise executes this finally block before returning Response to the caller, while stream processing starts only afterward in chatMLFetcher.ts:1442. sendEngineMessagesTelemetry synchronously maps metadata and JSON.stringify's the full array; sendIndividualMessagesTelemetry then recursively hashes every character (hash.ts:stringHash), JSON.stringify's each new message, splits it into 8K chunks, and invokes an internal telemetry event for each chunk. multiplexProperties also creates the full JSON string and Buffer.from input before asynchronous gzip completes. Thus accumulated native reasoning or an image payload is repeatedly processed after headers arrive but before the stream can be consumed.

**Suggested direction:** Keep the richer telemetry, but hand the Response back and establish stream consumption first; schedule conversion and sendEngineMessagesTelemetry off that critical path (with explicit error handling), or otherwise bound/prepare telemetry before this response-start boundary.

### 2. [medium] Release Anthropic completions before processing native thinking

**Finding ID:** `PERF-1794D21AE363`  
**Location:** <code>extensions/copilot/src/platform/endpoint/node/messagesApi.ts:1422</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU work, retained and serialized strings, telemetry event objects, and temporary buffers  
**Scaling:** For responses containing thinking, synchronous completion-time work grows with answer plus thinking/signature/redacted bytes and creates one internal telemetry event per 8,000 serialized characters.  
**Outcome:** Increased completion/tool-loop latency and CPU/GC pressure for reasoning-heavy Anthropic responses.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The streaming Messages path sent only rawMessageToCAPI(completion.message), which contains the surfaced answer/tool result, before emitting the completion.  
**Changed behavior:** The added telemetryMessages assignment attaches the reconstructed provider content—including full thinking, signature, and redacted blocks—to the completion; the endpoint then synchronously processes that expanded payload before feed.emitOne.  
**Confidence:** 0.98 — The thinking-only trigger, expanded payload, synchronous helper work, and send-before-emit ordering are directly traced. Magnitude depends on reasoning length, but the latency mechanism is certain.

**Causal diff evidence:** RIGHT line 1422 installs the full native content array whenever a thinking block exists. At unchanged lines 737-739, sendEngineMessagesTelemetry runs before feed.emitOne; the non-streaming branch introduced the same expanded payload and ordering at lines 1059-1079.

When Claude emits substantial thinking, users and agent loops wait after message\_stop while hidden telemetry content is hashed and split into events; repeated reasoning model calls compound the delay.

**Evidence:** sendEngineMessagesTelemetry synchronously adds metadata and serializes the complete array, then sendIndividualMessagesTelemetry recursively hashes every string, serializes each message again, splits it into 8K chunks, and invokes an internal event for each chunk. The new content array includes provider thinking that was previously excluded, so long reasoning now extends the completion-critical path. The default chat processor in this PR demonstrates that completion delivery can remain immediate while telemetry waits until stream completion.

**Suggested direction:** Emit the completion before scheduling native-content telemetry, and apply the same deferred ordering to the non-streaming branch. Keep the captured content alive only until the deferred telemetry task has taken ownership.

### 3. [medium] Release Responses completions before serializing retained reasoning

**Finding ID:** `PERF-50D034CD919E`  
**Location:** <code>extensions/copilot/src/platform/endpoint/node/responsesApi.ts:1510</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU work, large serialized strings, telemetry event objects, and temporary buffers  
**Scaling:** Cost grows with provider reasoning/content bytes: the payload is traversed for classification, full-array JSON serialization, recursive hashing, per-message JSON serialization, and 8K event chunking before the completion is emitted.  
**Outcome:** Higher terminal-response latency, CPU/GC pressure, and delayed progress to the next tool or model call.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Responses completions exposed only completion.message to output telemetry, so this pre-emission telemetry path processed the visible answer rather than provider-native reasoning, summaries, encrypted state, and other output items.  
**Changed behavior:** The added telemetryMessages field retains the entire normalized provider output, including hidden reasoning and opaque fields, and sendCompletionOutputTelemetry synchronously processes it before feed.emitOne(completion).  
**Confidence:** 0.98 — The changed payload, synchronous serialization/hash path, and send-before-emit ordering are explicit in production code. Only the precise duration for a given model output is uncertain.

**Causal diff evidence:** RIGHT line 1510 adds responseApiInputToTelemetryMessages(normalizedOutput) to every completed Responses result; processResponseFromChatEndpoint calls sendCompletionOutputTelemetry at line 1033 and only emits that completion at line 1034.

Reasoning-heavy Responses calls stall completion delivery after the model has already finished. In agent workflows this delays tool execution or the next model iteration on every affected call, with larger stalls as reasoning/output size grows.

**Evidence:** sendCompletionOutputTelemetry forwards telemetryMessages to sendEngineMessagesTelemetry. That helper synchronously classifies and JSON.stringify's the array, hashes all message fields character-by-character for deduplication, JSON.stringify's each new message, splits it into 8K chunks, and invokes model.message.added per chunk. Both HTTP and the websocket callback call this telemetry helper before emitting the completion. Hidden reasoning can be much larger than the final answer, so the diff materially increases work at the terminal completion boundary rather than merely passing metadata through.

**Suggested direction:** Preserve telemetryMessages, but emit the ChatCompletion first and defer output telemetry until after delivery, following the defaultChatResponseProcessor pattern added in this PR; ensure deferred failures remain best-effort and do not affect completion semantics.
