# Performance review: agentHost: Restore peer chats lost after session refresh

[PR #339476](https://github.com/microsoft/vscode/pull/339476) at `6255f7845f274ef3dbbcca150b9bc50f98613947`

## Findings (1)

### 1. [medium] Batch the recovery projection check before listing sessions

**Finding ID:** `PERF-3E2F548BB6A6`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:3768</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** serialized SQLite queries and decoded chat-row objects  
**Scaling:** On the first list in each agent-host process, cost grows as one \`getSessionChatCatalog\` query per eligible local Copilot CLI session, plus all peer rows returned; the database's single \`Sequencer\` makes the effective query concurrency 1 despite the limiter of 4.  
**Outcome:** increased first-session-list and startup latency for users with large local Copilot CLI catalogs  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The list path fetched all eligible \`sessions\_v2\` rows with the single bulk \`readMany\`/\`listSessionsV2\` query and did not read each session's chat catalog separately.  
**Changed behavior:** After the bulk read, the added loop awaits \`\_refreshRecoveredSessionProjection\` for every eligible local Copilot CLI session not yet checked; that helper immediately calls \`getSessionChatCatalog(sessionKey)\`, even for healthy sessions that never underwent recovery.  
**Confidence:** 0.99 — The changed call path, default-enabled catalog path, one-call-per-candidate cardinality, cold-process cache behavior, and database-wide serialization are explicit in code. Exact milliseconds vary by catalog size and disk cache, which affects severity rather than mechanism confidence.

**Causal diff evidence:** The added \`centralResults\[index\] = await this.\_refreshRecoveredSessionProjection(...)\` line places a per-session catalog lookup, through \`\_refreshRecoveredSessionProjection\`, directly after and on the critical path of the existing bulk catalog read.

Opening the Sessions UI or requesting the initial session list after each restart now blocks on N additional serialized SQLite queries for N local Copilot CLI sessions. Large catalogs therefore lose the bulk-read startup behavior this path otherwise preserves; the in-memory checked set only helps later lists in the same process.

**Evidence:** \`AgentHostCatalogListReader.readMany\` issues one \`listSessionsV2(sessions)\` query. The added call at 3768 reaches \`\_refreshRecoveredSessionProjection\`, whose first operation is \`this.\_orchestratorDatabase.getSessionChatCatalog(sessionKey)\`. \`AgentHostDatabase.getSessionChatCatalog\` queues one SELECT through the database-wide \`\_transactionSequencer\`, so all candidate calls serialize and each materializes that session's chat rows. Candidate selection includes every eligible, non-external local \`copilotcli\` parent, not only sessions with a recovery marker.

**Suggested direction:** Perform one batched chat-catalog lookup for all candidates and compare in memory, or persist/query recovery candidates in bulk so healthy sessions are excluded before any per-session read; keep the existing per-session synchronization only for mismatches that are known to have completed recovery.
