## Findings (1)

### 1. [medium] Avoid defaulting Stable to the per-frame Draw renderer

**Finding ID:** `PERF-BCED62CD33F6`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatProgressConfiguration.ts:15</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Main-thread geometry calculations, short-lived path strings/arrays, and SVG \`d\` attribute writes on every animation frame  
**Scaling:** The work grows with display refresh rate × the duration of each visible active response × the number of simultaneously visible active chat panes; a 30-second response schedules roughly 1,800 frame callbacks at 60 Hz.  
**Outcome:** Sustained CPU and allocation/GC pressure during agent responses, consuming frame budget and battery and potentially causing dropped frames on slower clients.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** With no explicit override, Stable resolved \`chat.experimental.persistentProgress\` to \`Off\`; \`isPersistentProgressEnabled()\` was false, so \`ChatWorkingProgressContentPart\` did not construct \`ChatWorkingProgressLogo\` and there was no JavaScript animation-frame loop or SVG path regeneration. Only Insiders defaulted to Draw.  
**Changed behavior:** Stable now resolves the setting to \`Draw\`. Every visible active persistent-progress footer constructs the Draw logo and continuously runs \`getChatWorkingLogoDrawFrame()\` from \`requestAnimationFrame\`, then writes the generated paths into up to three SVG masks.  
**Confidence:** 0.97 — The default-resolution and render call path are directly traced, and the rAF loop plus path generation are explicit. Visibility and completion guards bound the work to visible active responses, and fixed-band caching lowers each frame's cost; only the exact milliseconds and device-level impact are uncertain, which is reflected in severity.

**Causal diff evidence:** RIGHT line 15 replaces the Stable-specific \`Off\` default with unconditional \`ChatProgressAnimation.Draw\`, newly routing default Stable sessions into the persistent logo's JavaScript rAF/SVG-generation path.

A normal long-running agent request in Stable now performs main-thread SVG geometry generation for its entire visible lifetime. The implementation's own moving-band path remains uncached, so long requests repeatedly allocate and serialize path geometry even after the new fixed-band cache is warm.

**Evidence:** The changed default is consumed by \`ChatListItemRenderer.isPersistentProgressEnabled()\` and passed as \`suppressProgressShimmer\`; \`ChatWorkingProgressContentPart\` then creates \`ChatWorkingProgressLogo\`. Its visible/active path recursively schedules \`requestAnimationFrame\`; \`renderDrawFrame\` calls \`getChatWorkingLogoDrawFrame\` and updates SVG \`d\` attributes. During tie/untie phases, \`Ribbon.bands\` builds Maps/arrays and long path strings, and the changed implementation explicitly notes that moving endpoints are never cached. There are no subprocess, IPC, filesystem, database, or network boundaries on this path; the regression is synchronous rendering CPU compared with Stable's prior Off path.

**Suggested direction:** Keep Stable's default at \`Off\` (or the no-icon persistent mode) until Draw has an absolute frame-cost budget, or throttle/coalesce path regeneration to a bounded cadence while preserving the same animation and existing visibility/completion guards.


## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/widget/chatWorkingLogoDraw.ts:240` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/widget/chatWorkingLogoDraw.ts:356`

**Introducing commit:** `2ed347f01becd0e6aa2f3589721f7b7932ad1d26`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.95

**Mechanism:** Every visible animation frame rebuilt identical full-band geometry and long SVG path strings for marks wholly inside the revealed ribbon interval.

**Symptom:** The Draw animation incurred avoidable geometry CPU and string allocations at display-frame frequency; the new finite cache removes the unchanged portion of that work.

**Fixed behavior:** Fully covered marks now reuse one of four cap-specific path strings from a bounded cache, while only genuinely moving endpoints call strip.

**Evidence:** ChatWorkingLogo calls getChatWorkingLogoDrawFrame from a recursive requestAnimationFrame loop. In the base revision, Ribbon.bands generated each visible mark by calling strip on every moving frame, including fully covered marks whose geometry and cap flags were unchanged. Blame ties that repeated frame-path work to the animation-introducing commit. The PR adds a finite per-mark path cache and uses it whenever the full mark is covered.
