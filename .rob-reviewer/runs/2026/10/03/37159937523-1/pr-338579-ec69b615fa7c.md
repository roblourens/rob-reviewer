# Performance review: chat: improve Draw persistent progress animation

[PR #338579](https://github.com/microsoft/vscode/pull/338579) at `ec69b615fa7c6a1cd3f640940055e983e82d3b59`

## Findings (1)

### 1. [medium] Avoid rebuilding SVG mask geometry on every animation frame

**Finding ID:** `PERF-20D41C1F713B`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatWorkingLogo.ts:245</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Renderer-main-thread geometry calculations, temporary arrays/path strings, SVG DOM attribute writes, and mask rerasterization  
**Scaling:** For each visible active Draw logo, this runs once per display refresh for the full response lifetime; 80% of every 2.667-second cycle rebuilds uncached ribbon geometry, so cost scales with refresh rate, response duration, and concurrently visible chat widgets.  
**Outcome:** Sustained renderer CPU/GC pressure and reduced frame budget during streaming, scrolling, and input, with increased risk of dropped frames on slower machines.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Draw used three fixed SVG faces animated by CSS keyframes over inset clip paths with \`will-change: clip-path\`; JavaScript did no per-frame geometry generation or DOM writes.  
**Changed behavior:** Each requestAnimationFrame now calls \`getChatWorkingLogoDrawFrame\`, which traverses the flattened ribbon, allocates section/point arrays, formats new SVG path strings, and writes up to three \`d\` attributes before scheduling the next frame.  
**Confidence:** 0.98 — The RAF loop, uncached moving-frame call path, allocations, SVG writes, and replacement of the CSS-only implementation are explicit in the diff. Visibility, reduced-motion, and completion guards bound which logos run; only the exact device-dependent magnitude is uncertain.

**Causal diff evidence:** The added call at line 245 moves the new ribbon generator onto every browser animation frame, line 246 repeats it indefinitely, and added line 258 applies each generated string to live SVG geometry. The diff simultaneously removes the prior CSS keyframes and \`will-change: clip-path\` implementation.

With Draw enabled (the Insiders default), every visible in-progress or user-blocked chat response continuously consumes main-thread time that directly competes with chat progressive rendering and UI interaction.

**Evidence:** \`renderNextDrawFrame\` invokes \`renderDrawFrame\` and immediately queues another RAF. \`renderDrawFrame\` calls the new geometry generator and mutates SVG \`d\` attributes. In \`chatWorkingLogoDraw.ts\`, moving phases call \`drawRibbon.bands\`; each band calls \`sections\`/\`breaks\`, recreating vertex-fraction arrays and sorting them, builds point arrays, and concatenates coordinate strings in \`toPath\`. IntersectionObserver suppresses hidden logos and completion deactivates them, but neither reduces work for the normal visible active-response path.

**Suggested direction:** Precompute a bounded set of ribbon path frames and reuse those strings at a capped cadence, or express the motion with CSS/Web Animations over fixed/compositable geometry, so the active chat path does not rebuild and rerasterize SVG geometry at display refresh rate.

### Scenario 1: A visible persistent Draw logo while a chat response is streaming, running tools, or waiting for user confirmation

- Scaling input: Display refresh rate multiplied by the active-response duration and the number of simultaneously visible active chat widgets/logos. Each 2.667-second loop spends 80% of its phases generating moving geometry.
- Effective concurrency: Each visible logo owns an independent RAF loop. Browser RAF callbacks are frame-batched but there is no shared scheduler, limiter, or frame cache; IntersectionObserver stops non-intersecting logos and completion stops the response logo.
- Cache behavior: The Ribbon model plus empty and fully tied paths are module-level cached, and artwork is created lazily only for Draw. Every intermediate moving frame is recomputed; moving path strings are neither memoized nor shared or coalesced across logos.
- Mechanism confidence: High: the diff replaces CSS keyframes with an unconditional per-visible-logo RAF loop whose traced moving-frame path allocates arrays/strings, sorts breakpoints, mutates SVG geometry, and triggers mask rendering.
- Magnitude uncertainty: Normal production cardinality is usually one visible active response per chat widget, but users can expose multiple chat surfaces and hardware/display refresh rates vary. Exact milliseconds and dropped-frame prevalence are unmeasured; the renderer-main-thread mechanism is explicit.
- Expensive boundaries: none found
- Verdict: Reportable medium-severity regression: the new animation continuously consumes main-thread CPU/GC and rendering budget on an interaction-sensitive path where the old implementation used fixed geometry and CSS animation.

### Scenario 2: Reduced-motion, hidden, inactive, completed, Off, and No Icon persistent-progress states

- Critical path: State changes synchronously cancel the pending RAF and render the assembled frame once where applicable; afterward no animation work blocks UI progress.
- Scaling input: Number of mounted response parts and configuration/accessibility changes, rather than display refresh rate or response duration.
- Effective concurrency: No recurring frame callbacks after completion, inactivity, hidden intersection, reduced motion, Off, or No Icon. Each logo has an IntersectionObserver and document visibility listener for its mounted lifetime, but mounted rows are controlled by chat-list virtualization and disposal.
- Cache behavior: Assembled/empty paths are reused, and Draw artwork is not created for logos that never select Draw. Artwork remains attached after a live switch away from Draw, bounded to that mounted logo.
- Mechanism confidence: High for cancellation and static rendering because the active, visibility, motion, and response-completion guards are explicit and covered by changed tests.
- Magnitude uncertainty: Observer/listener overhead depends on mounted-row count, but the list lifecycle bounds it and there is insufficient evidence of material user-visible cost.
- Expensive boundaries: none found
- Verdict: No additional finding: recurring animation work is correctly suppressed in these states, and retained observer overhead is not proven material at realistic mounted cardinality.

### Scenario 3: Module initialization and live switching of the persistent progress animation setting

- Cache behavior: Ribbon measurements and static endpoint paths are module-level singletons. Per-logo mask artwork is lazy and retained for reuse after subsequent setting changes.
- Mechanism confidence: High for the one-time bounded work based on the static initializer and \`ensureDrawArtwork\` guard.
- Magnitude uncertainty: No timing measurement is present, but the initialization has fixed small cardinality and does not scale with chat history or response size.
- Expensive boundaries: none found
- Verdict: No finding: the eager work is bounded and shared, while the reportable cost is the uncached per-frame moving geometry covered separately.
