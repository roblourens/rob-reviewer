# Performance review: chat: preserve transcript order when refreshing history

[PR #339458](https://github.com/microsoft/vscode/pull/339458) at `99835eb159d6198ffcd656ae01dca18047b4e730`

## Findings (1)

### 1. [low] Reuse the initial per-turn equality results

**Finding ID:** `PERF-820CA721DCFC`  
**Location:** <code>src/vs/workbench/contrib/chat/common/chatService/chatServiceImpl.ts:1023</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work traversing and sorting keys across nested history objects  
**Scaling:** The duplicated work grows with the total serialized size of all unchanged turns before the late change, not merely with the changed turn; each such payload is recursively compared twice.  
**Outcome:** increased synchronous refresh latency and CPU pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The old common-prefix loop deep-compared each history item once until the first difference, then rebuilt the changed suffix; a last-response metadata update therefore traversed the unchanged prefix once.  
**Changed behavior:** A history update whose change is near the end first traverses all preceding turn payloads in turns.every, then traverses those same payloads again in the per-turn reconciliation loop.  
**Confidence:** 0.96 — Both comparisons and their synchronous call path from AgentHostChatSession.updateHistory are explicit. Agent-host refreshes rebuild history objects, so object identity cannot short-circuit objects.equals; the only uncertainty is the transcript size at which the extra traversal becomes noticeable.

**Causal diff evidence:** Added line 993 deep-compares turns against lastTurns to detect a no-op, then added line 1023 deep-compares each unchanged turn against the same prior turn again during reconciliation; the pre-PR common-prefix loop compared each history item only once before rebuilding the changed suffix.

Completing or passively refreshing a long agent chat can spend roughly twice the prior deep-comparison CPU on the UI thread, increasing refresh latency and risking a visible pause for transcripts with many large response/tool parts.

**Evidence:** refreshHistory runs synchronously from onDidChangeHistory. objects.equals recursively visits arrays/objects and sorts every object's keys. For the common case where context-usage/elapsed metadata or the newest response changes, line 993 reaches the late change after walking the unchanged transcript; line 1023 then repeats deep equality for every unchanged turn before reaching that same changed turn. AgentHostSessionHandler triggers this after persisted-history/context-usage updates and turnsToHistory supplies full response parts, including nested tool data.

**Suggested direction:** Cache/reuse the first pass's equality result when the same turn ID remains at the same position, or perform a single reconciliation pass that both detects no-ops and records changed turns, so each payload is deep-compared at most once while preserving reorder handling.
