## Performance regression fixes detected (3)

### 1. repeated-work

**Fix location:** `src/vs/platform/agentHost/node/agentHostCheckpointService.ts:75` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentHostCheckpointService.ts:85`  
**Introducing path:** `src/vs/platform/agentHost/node/agentHostCheckpointService.ts`  
**Introducing commit:** `07175f3b36915b07829245fe9a30cb3cfb31b2b9`  
**Mechanism family:** `repeated-work`  
**Performance category:** `subprocess`  
**Confidence:** 0.99

**Mechanism:** Multi-root checkpoint loops repeated full Git working-tree capture and commit/ref work for every configured folder even when several folders shared one checkout root.

**Symptom:** Turn-start and turn-end checkpoint latency scaled with folder count rather than unique repositories, adding repeated Git subprocess and filesystem work for common multi-folder sessions.

**Fixed behavior:** Successful baseline, turn-start, and turn-end captures now mark the resolved repository root complete and skip additional folders resolving to that same root, reducing expensive working-tree snapshots and commit/ref subprocesses from O(folders) to O(unique checkout roots) per capture phase.

**Evidence:** The base implementation iterated every configured working directory and invoked \_writeCheckpointCommit for each. That helper calls captureWorkingTreeAsTree, which runs git status/rev-parse/index discovery and may create a temp index and run additional Git commands. Multiple workspace folders can resolve to the same checkout root; the added ResourceSet guard at RIGHT:75 makes each successful repository capture occur once per phase while the new tests prove retries remain possible after failure and later turns still take fresh snapshots.

### 2. missing-coalescing

**Fix location:** `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts:1557` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts:1555`  
**Introducing path:** `src/vs/platform/agentHost/node/shared/worktreeIsolation.ts`  
**Introducing commit:** `7c3cb26c995ce179ee9fb21e7debe7667da9f057`  
**Mechanism family:** `missing-coalescing`  
**Performance category:** `latency`  
**Confidence:** 0.98

**Mechanism:** Two independent Git branch-discovery subprocess chains were serialized on the session configuration critical path.

**Symptom:** Opening or resolving Agent Host session configuration incurred additive current/default branch discovery latency, especially on Windows where Git process startup is material.

**Fixed behavior:** Current-branch and default-branch discovery now overlap, so session configuration waits for the slower independent Git read rather than their sum, without increasing request cardinality.

**Evidence:** The base lines awaited getCurrentBranch before starting getDefaultBranch. Both methods execute independent read-only Git subprocesses, and resolveIsolationConfig awaits \_getGitInfo on the session-configuration critical path. RIGHT:1557 starts both reads together after repository and HEAD validation, while \_pendingGitInfo continues coalescing overlapping callers for one working directory.

### 3. boundary-fanout

**Fix location:** `src/vs/platform/agentHost/node/agentHostReviewService.ts:310` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentHostReviewService.ts:305`  
**Introducing path:** `src/vs/platform/agentHost/node/agentHostReviewService.ts`  
**Introducing commit:** `a8c1541df5a2123e56282a0f286861c872b569c8`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `subprocess`  
**Confidence:** 0.98

**Mechanism:** Session cleanup unconditionally spawned a Git update-ref subprocess for known ref names, including repositories with no matching reviewed refs and repeated folders sharing a checkout.

**Symptom:** Awaited session-data disposal accumulated avoidable Git process startup latency per configured working directory, including the common no-reviewed-ref case.

**Fixed behavior:** Successful ref enumeration now filters cleanup to refs that actually exist and avoids spawning git update-ref for empty results; after one folder removes shared-checkout refs, later folders also observe an empty result and skip redundant deletion.

**Evidence:** The base implementation always passed the non-empty known-ref set to deleteRefs after enumeration. deleteRefs launches `git update-ref --stdin -z` even when those refs do not exist, so session disposal paid one process per working directory and repeated it for multiple folders in the same checkout. The changed strict enumeration computes only existing refs and RIGHT:310 skips deleteRefs when none remain; failure/unavailable enumeration retains the previous known-ref fallback.
