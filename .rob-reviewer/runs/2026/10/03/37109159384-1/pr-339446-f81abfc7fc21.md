# Performance review: Agent host: show skill argument-hint as inline placeholder

[PR #339446](https://github.com/microsoft/vscode/pull/339446) at `f81abfc7fc2186585472df88b5af98f63440aa04`

## Findings (2)

### 1. [medium] Reject non-empty skill arguments before copying the prompt

**Finding ID:** `PERF-880C9965C04C`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCommandArgumentHint.ts:92</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** CPU spent traversing the text model and bytes allocated for the full suffix string  
**Scaling:** For one accepted hinted skill followed by P characters, E subsequent model edits copy up to P characters each, for O(E\*P) work and allocation; when the prompt is built incrementally this can become quadratic in its final length.  
**Outcome:** Increased synchronous input latency, allocation/GC pressure, and possible dropped frames  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The command-only guard skipped every skill reference, so editing a prompt accepted from a skill completion did not perform this suffix extraction.  
**Changed behavior:** The broadened guard now lets Skill references with argumentHint metadata reach isCommandOnlyContent during every input-model update; that method materializes the entire text after the skill reference with model.getValueInRange before comparing it with a one-character string.  
**Confidence:** 0.97 — The added guard, per-model-change subscription, exact call path, and allocating text-buffer API are all explicit in repository code. Only the user-visible magnitude varies with prompt size and edit count.

**Causal diff evidence:** RIGHT line 92 changes the filter from \`\!== AgentHostCompletionReferenceKind.Command\` to \`=== undefined\`, newly allowing Skill references into the hint-rendering path.

Editing a long prompt after a hinted \`/skill\` completion adds synchronous O(prompt length) traversal/allocation to each keystroke, causing input latency and GC pressure and potentially dropped frames for large pasted logs or code.

**Evidence:** The constructor subscribes update() directly to inputEditor.onDidChangeModelContent; the changed line admits skills, getArgumentHintDecoration calls isCommandOnlyContent, and line 130 reads the range from the skill through the full model end. The piece-tree implementation returns a string for getValueInRange, so a prompt such as \`/design-prep &lt;large pasted log or code&gt;\` is copied again on every subsequent edit even though any suffix longer than one character already proves the hint must be hidden.

**Suggested direction:** Use range/model positions or a length check to reject suffixes whose length is not exactly one before reading text, and read only that single character when it can still be the required space.

### 2. [medium] Reuse the resolved skill range when updating the hint

**Finding ID:** `PERF-6075B8ECC273`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/agentHostInputCompletions.ts:144</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU for duplicate full-string searches and bytes allocated by the suffix slice  
**Scaling:** With one accepted hinted skill, each of E edits over a P-character prompt adds another O(P) reference search and up to O(P) suffix allocation; additional attachments are also rescanned until the skill entry is reached.  
**Outcome:** Higher synchronous rendering/input latency with additional allocation and GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Skill entries were rejected by the command-only guard. The decoration updater located each inserted skill reference once for its normal inline decoration, but did not perform the second hint-specific full-text lookup or suffix slice.  
**Changed behavior:** The broadened attachment guard now runs hinted Skill entries through getAgentHostCompletionAttachmentRange and suffix slicing whenever the Sessions input decorations update.  
**Confidence:** 0.96 — The per-edit subscription, existing first range lookup, newly reachable second lookup, and suffix allocation are explicit. The exact frame impact depends on prompt length, but the duplicated scaling work is certain.

**Causal diff evidence:** RIGHT line 144 replaces the command-only check with an undefined-kind check, newly sending Skill attachments through the full hint lookup on every decoration update.

Editing a long Agents/Sessions prompt that starts with a hinted \`/skill\` repeats full-text scanning and suffix allocation on the synchronous input path, increasing typing latency and GC pressure and risking dropped frames for prompts containing large pasted logs or code.

**Evidence:** \_registerDecorations invokes \_updateDecorations on every editor model change. \_updateDecorations first calls getAgentHostCompletionAttachmentRange for every inserted reference, then calls \_getArgumentHintDecorations; after the changed guard admits a hinted skill, getCommandArgumentHintPlaceholder calls the same range finder again and evaluates value.slice(range.endExclusive). getAgentHostCompletionAttachmentRange searches the complete value for all occurrences to choose the closest match, so the hint path duplicates a full-prompt search and allocates the remaining suffix per edit.

**Suggested direction:** Carry the range already resolved in \_updateDecorations into the hint calculation (or use the tracked range directly), then compare offsets/length and charAt without searching the full value again or slicing its suffix.
