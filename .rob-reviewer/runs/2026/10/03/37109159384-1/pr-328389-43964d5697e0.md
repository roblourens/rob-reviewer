## Findings (2)

### 1. [medium] Restore the no-op checkpoint fast path

**Finding ID:** `PERF-30C8B50EC96E`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostCheckpointService.ts:144</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Git subprocesses, checkpoint refs/commit objects, and the subsequent git-diff subprocess  
**Scaling:** The extra commit/ref and later diff are incurred once per repository for every completed turn whose captured tree is unchanged; retained refs/commits grow with no-op turn count until session cleanup.  
**Outcome:** Increased end-of-turn changeset latency and subprocess/I/O load, plus avoidable Git object/ref growth during long sessions.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The deleted implementation resolved the parent tree, reused the parent ref when the tree was identical, and returned without commit-tree/update-ref; AgentHostChangesetService also recognizes parent === current and skips git diff entirely.  
**Changed behavior:** Every successfully captured tree now unconditionally runs commit-tree and update-ref and records a fresh turn ref, even when that tree equals the parent tree.  
**Confidence:** 0.99 — The before/after behavior, subprocess implementations, and downstream pair-equality fast path are all explicit in the diff and call chain; only exact wall-clock magnitude varies by repository and platform.

**Causal diff evidence:** RIGHT line 144 adds unconditional commitTree after the PR deletes the parent-tree equality branch that previously returned the parent ref for an unchanged tree.

Read-only or conversational turns with no repository edits now create a redundant commit/ref per repository and force changeset computation through git diff before publishing the final changeset. Long sessions with many such turns accumulate refs and repeatedly spawn avoidable git processes.

**Evidence:** captureWorkingTreeAsTree already returns a tree OID, but the added line commits it without comparing it to \`${parentCommitOid}^{tree}\`. The removed hunk explicitly performed that comparison and persisted parentRef on equality. The unchanged \_computeTurnDiffsPreferCheckpoint fast path returns \[\] only when pair.parent === pair.current; fresh refs defeat it. commitTree/updateRef/computeFileDiffsBetweenRefs each invoke git subprocesses in AgentHostGitService.

**Suggested direction:** Compare each captured tree with its parent before creating commits. If all repositories are unchanged, persist the previous ref so parent === current remains true; if another repository requires a new shared ref name, point unchanged repositories at the parent commit without creating redundant commits.

### 2. [medium] Deduplicate working directories by repository root

**Finding ID:** `PERF-13D5AA39DC69`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostCheckpointService.ts:117</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Git subprocesses and temporary index filesystem operations used to capture and commit a full repository tree  
**Scaling:** Cost scales with configured working-directory count rather than unique repository count; N workspace folders within one repository repeat the same sequential full-tree capture N times per turn.  
**Outcome:** Higher end-of-turn latency and avoidable CPU, subprocess, and filesystem I/O, delaying final changeset publication.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Checkpoint capture accepted only the primary working directory, so one turn could execute this full repository capture at most once.  
**Changed behavior:** The new multi-root loop resolves each working directory and immediately performs baseline lookup, parent lookup, full working-tree capture, commit-tree, and update-ref, without grouping equal repository roots.  
**Confidence:** 0.96 — The folder-to-root normalization, repeated repository-wide subprocess chain, sequential await ordering, and changeset dependency are directly traced. The only magnitude uncertainty is how often users include multiple workspace folders from one repository.

**Causal diff evidence:** RIGHT line 117 introduces iteration over every supplied working directory; the subsequent added body performs repository-wide Git work for each entry with no root-level deduplication.

A realistic multi-root workspace containing sibling folders or a repository plus one of its subfolders resolves multiple entries to the same Git root. Each completed turn then serially captures and commits that same repository once per folder before AgentSideEffects can invoke changesets.onTurnComplete.

**Evidence:** getRepositoryRoot canonicalizes each folder to its Git top level. captureWorkingTreeAsTree then runs git status, creates a temporary index directory, runs read-tree/staging/write-tree, and the caller follows with commit-tree/update-ref. The loop is sequential and has no Set keyed by repositoryRootUri, while AgentSideEffects waits for captureTurnCheckpoint to settle before scheduling the final changeset.

**Suggested direction:** Resolve all working directories to repository roots first, deduplicate by canonical URI, then run baseline/turn capture once per unique repository while preserving the current per-repository best-effort error handling.


## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/platform/agentHost/node/agentHostReviewService.ts:58` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentHostReviewService.ts:234`  
**Introducing path:** `src/vs/platform/agentHost/node/agentHostReviewService.ts`  
**Introducing commit:** `d44e5ba3d760fb1cd78754d8439edcb43a0bddf3`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.96

**Mechanism:** The review-ref cleanup listener looked up its working directory from live session state after AgentService had already deleted that state, so disposed reviewed sessions retained their refs indefinitely in the repository.

**Symptom:** One reviewed Git ref leaked per disposed reviewed session, causing repository ref/object retention and progressively more ref namespace work over time.

**Fixed behavior:** The deletion event now carries working directories captured before teardown, and the review cleanup consumes them directly to delete the reviewed ref before session data/worktree removal.

**Evidence:** In the base revision AgentService called stateManager.deleteSession before deleteSessionData fired the review listener; base line 234 then queried the now-removed session state and returned without deleteRefs. The PR captures effective working directories before teardown, forwards them through deleteSessionData, and line 58 passes them into disposal, making ref cleanup reachable.
