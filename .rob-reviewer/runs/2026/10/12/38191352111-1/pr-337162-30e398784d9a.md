## Findings (2)

### 1. [medium] Back off peer-detail resubscriptions after repeated failures

**Finding ID:** `PERF-BDBEC0BC0961`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:5893</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Repeated session subscribe/unsubscribe IPC or network requests plus retry CPU work  
**Scaling:** The cost grows without bound with failure duration: while any peer-detail observable remains observed, every failed subscribe schedules the next attempt immediately, with no delay, cap, or cancellation beyond removing the observer.  
**Outcome:** Persistent failures cause excessive IPC/network traffic and CPU churn, reducing throughput and potentially keeping the Agents window busy.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, a session subscription error disposed the failed subscription and waited for an existing external trigger such as a visibility change, query, or reconnect before attempting another subscription; there was no observer-held immediate retry loop.  
**Changed behavior:** The added onDidError branch now queues \_ensureSessionStateSubscription in a microtask whenever the new peer-detail reference collection still has references.  
**Confidence:** 0.99 — The observer-to-lease call path, error callback, microtask retry, errored-entry eviction, and fresh wire subscribe/unsubscribe are all explicit in the code. Only the exact request rate varies with how quickly the host rejects requests.

**Causal diff evidence:** RIGHT lines 5892-5895 add queueMicrotask(() =&gt; { if (...hasReferences(sessionId)) { this.\_ensureSessionStateSubscription(sessionId); } }), converting an error into an immediate retry for as long as the newly introduced detail lease is held.

When a rendered peer chat keeps title/status details observed and the host persistently rejects or cannot serve the session subscription (for example during auth failure, a missing session, or a failing remote host), the client continuously creates subscriptions. AgentSubscriptionManager.getSubscription sends a fresh wire subscribe and disposal sends unsubscribe on every iteration, so a fast local failure can become a tight IPC loop and a remote failure becomes an indefinite request stream.

**Evidence:** AdditionalChat.\_withDetails acquires a lease for each observed detail, and the reference collection keeps hasReferences(sessionId) true until the row observer is disposed. AgentSubscriptionManager.getSubscription explicitly evicts errored entries and starts a fresh \_subscribe request; disposing the provider store invokes unsubscribe. The added queueMicrotask path immediately calls \_ensureSessionStateSubscription again after every onDidError, and the added test only proves one failure followed by success, not persistent failure behavior.

**Suggested direction:** Replace the microtask retry with a cancellable bounded exponential backoff keyed by session, reset it after a successful snapshot or host reconnect, and cancel it when the last detail reference is released.

### 2. [low] Bound persisted collapse entries for removed sessions

**Finding ID:** `PERF-846384A3E82E`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:5088</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Persisted session-resource strings, in-memory Set entries, and bytes serialized on each collapse-state write  
**Scaling:** Retained state grows with the lifetime count of distinct nested sessions the user has collapsed, rather than with currently existing sessions; each later toggle copies and JSON-serializes the entire historical set.  
**Outcome:** Unbounded profile-state and memory growth, with increasing synchronous serialization/storage work on collapse toggles and list startup.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff there was no per-session collapse resource set, so deleted session identities were not retained or repeatedly serialized by the Sessions list.  
**Changed behavior:** The new collapse persistence adds every collapsed session resource to a profile-scoped Set and only removes it if that same session is explicitly expanded; session removal does not evict the resource.  
**Confidence:** 0.98 — Repository-wide references show the Set is loaded, queried, added to, and deleted only on explicit expansion; the session-removal handler does not prune it. Magnitude depends on profile lifetime and user collapse habits, which is reflected in low severity.

**Causal diff evidence:** RIGHT line 5088 introduces insertion into collapsedSessionResources, while the added persistence implementation has no deletion/lifetime path for sessions that leave the catalog.

Users who repeatedly collapse nested sessions and later delete them accumulate dead URI strings indefinitely. Over a long-lived profile, startup must parse all stale entries and every subsequent collapse/expand serializes and writes all retained identities, even though most can no longer affect the tree.

**Evidence:** saveSessionCollapseState adds resources at line 5088 and serializes the full Set at line 5093. The existing onDidChangeSessions removal branch at lines 3495-3508 refreshes the list and prunes section-order state, but never touches collapsedSessionResources. No other references to the new Set remove entries except expanding the same resource.

**Suggested direction:** Bound the persisted state, for example with an LRU cap, and prune entries on confirmed permanent session deletion (not transient provider disappearance), then persist the compacted set once.
