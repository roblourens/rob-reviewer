# Performance review: agentHost: preserve multiple pending steering messages

[PR #340669](https://github.com/microsoft/vscode/pull/340669) at `8789a68583c90882faaadfb1459fd76d8bc21843`

## Findings (1)

### 1. [medium] Coalesce provider preflight when flushing deferred steering

**Finding ID:** `PERF-9FAA14FA206B`  
**Location:** <code>src/vs/platform/agentHost/node/chatContributions/queueDrain/queueDrainContribution.ts:208</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Copilot SDK RPC calls and concurrent steering tasks, including attachment conversion work  
**Scaling:** A deferred batch of N independent steering messages performs N serialized rpc.mcp.listConfigured IPC calls before the N required sends; attachment conversion and SDK sends can then overlap N-way.  
**Outcome:** Avoidable IPC and head-of-line latency delay later steering messages after provider readiness, with additional CPU/I/O pressure when messages include attachments.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** During preparation the legacy steering slot retained only one replaceable message, so readiness flushed at most one Copilot steering operation and therefore one MCP reconciliation/listConfigured RPC from this path.  
**Changed behavior:** When provider readiness follows turn preparation, the host now releases every retained steering entry by starting a separate provider operation. For Copilot, each operation independently runs MCP enablement reconciliation before sending.  
**Confidence:** 0.96 — The changed loop and its Copilot call path are explicit: every retained entry calls sendSteeringMessage, which launches sendSteering; sendSteering always awaits \_reconcileMcpServerEnablement, whose sequenced body unconditionally invokes rpc.mcp.listConfigured. The only magnitude uncertainty is how many messages users or agent-to-agent callers accumulate during a long preparation window and the runtime latency of that local RPC.

**Causal diff evidence:** RIGHT line 208 is inside the newly added loop over every pending independent steering message and invokes provider.sendSteeringMessage once for each entry. Before this diff, \_syncPendingMessages handed the provider only the single replaceable state.steeringMessage slot.

After a user or agent queues several steering messages while Copilot is preparing or refreshing configuration, the kth message cannot reach the SDK until repeated MCP-list RPCs ahead of it complete; larger bursts also launch multiple attachment conversions and sends concurrently once their preflights clear.

**Evidence:** QueueDrainContribution lines 195-208 iterate state.steeringMessages and call sendSteeringMessage for each unsubmitted entry. CopilotAgent.sendSteeringMessage starts target.sendSteering without awaiting it; CopilotAgentSession.sendSteering always awaits \_reconcileMcpServerEnablement, and lines 5248/5253 serialize that reconciliation through \_mcpEnablementSequencer while unconditionally calling session.rpc.mcp.listConfigured. Thus an N-message deferred list causes N avoidable, serialized IPC preflights even though all entries share the same session configuration.

**Suggested direction:** Add a batch/provider queue boundary that performs MCP reconciliation once when a deferred list is released, then submits the independent messages in order (or coalesce concurrent reconciliation onto one in-flight promise) while retaining per-message IDs and completion handling.
