# Performance review: Private Marketplace extension blocking: add workbench UX and update gating

## Findings (1)

### 1. [medium] Keep gallery reconciliation off the search critical path

**Finding ID:** `PERF-CB43CF1FB981`  
**Location:** <code>src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts:1480</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Marketplace network requests, extension-management IPC calls, and extension-profile filesystem writes  
**Scaling:** Every first-page gallery search, subsequent page fetch, and direct extension lookup now waits for reconciliation on each configured local/remote/web extension server. If a page contains installed extensions whose returned versions are incompatible, each server performs one additional grouped getExtensions Marketplace request; UUID-less matches can also perform metadata lookups and sequential metadata writes.  
**Outcome:** Increased extension-search and paging latency, potentially up to an additional Marketplace request or remote-service timeout before results render.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** queryGallery/getPage/getExtensions invoked syncInstalledExtensionsWithGallery without awaiting it, so the pager or mapped gallery results were returned after the primary gallery query while compatibility reconciliation and metadata persistence continued off the result critical path.  
**Changed behavior:** The added await makes query completion depend on Promise.allSettled across all extension servers. Each server unconditionally awaits getTargetPlatform, checks installed matches, can issue galleryService.getExtensions for incompatible matches, and can persist missing gallery metadata before resolving.  
**Confidence:** 0.98 — The before/after critical-path change is explicit in the diff, and the awaited method's target-platform, fallback Marketplace query, and metadata-write paths are directly traced. The exact delay varies with installed/page overlap and service latency, but the added wait and realistic incompatible-installed-extension trigger are certain.

**Causal diff evidence:** RIGHT line 1480 changes \`this.syncInstalledExtensionsWithGallery(pager.firstPage);\` to \`await this.syncInstalledExtensionsWithGallery(pager.firstPage);\`; the same change is also made for page fetches and getExtensions, moving the existing asynchronous boundary work onto each caller's critical path.

Opening or typing in the Extensions view, paging results, and extension-tool ID lookups can now pause for a second Marketplace round trip whenever a page includes an installed extension whose latest gallery version is not compatible with the current local or remote target; slow or unavailable remote services can delay the whole result as well.

**Evidence:** The changed line awaits syncInstalledExtensionsWithGallery. That method awaits all configured Extensions.syncInstalledExtensionsWithGallery calls (line 2222). Each call awaits getTargetPlatform (line 752), and incompatible installed matches are grouped into galleryService.getExtensions(... queryAllVersions: true) (lines 763-765), an additional network query. UUID-less installed matches then await updateMetadata inside the result loop (line 683), which can query the Marketplace for the local version (line 802) and persists through extension-management IPC/profile storage (line 805).

**Suggested direction:** Refresh the blocking metadata needed by this PR synchronously/in memory before mapping the returned page, but leave compatibility resolution and metadata persistence off the query critical path as before (or split the method into a fast blocking-state refresh and a background reconciliation). Preserve ordering for the blocking-state update without awaiting unrelated target-platform, Marketplace fallback, or profile-write work.
