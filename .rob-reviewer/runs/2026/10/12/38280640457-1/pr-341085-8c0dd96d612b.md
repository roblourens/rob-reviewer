## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:7998` (`RIGHT`)  
**Blamed base line:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:7902`  
**Introducing path:** `src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts`  
**Introducing commit:** `4918ed64f11c8fb78f89b7c40805c1ddab82790b`  
**Mechanism family:** `repeated-work`  
**Performance category:** `network`  
**Confidence:** 0.99

**Mechanism:** A deterministic exception while applying an already-returned session catalog entered the network-failure retry path after the backoff had been reset, repeatedly fetching and deserializing the complete remote catalog once per second.

**Symptom:** Opening/reconnecting an affected Agent Host could continuously transfer and deserialize the full session list at 1 Hz, consuming remote connection bandwidth and making an SSH-backed sessions window unresponsive.

**Fixed behavior:** The added didList flag distinguishes a rejected listSessions boundary from failure after a listing was returned. At RIGHT line 7998, post-list failures are logged and returned without arming the retry timer, while genuine connection/auth listing failures retain the exponential-backoff retry. Per-row registration conflicts are also isolated so remaining rows can reconcile.

**Evidence:** Before this diff, one catch covered both the listSessions RPC and all synchronous reconciliation. A successful RPC reset \_sessionRefreshRetryDelay to the 1s minimum at base line 7902; if createAdapter/registerBackendSession or a later reconciliation hook then threw, that same catch called \_scheduleSessionRefreshRetry. The next successful full-list RPC reset the delay again before the deterministic apply failure, producing a full list request every second. The added test advances 10 seconds and requires exactly one list call for a deterministic apply failure, directly exercising the old repeated-request path.

### Scenario 1: Open or reconnect the Sessions window to an older remote Agent Host whose full catalog contains legacy fragment subagent rows that collide with parent identities.

- Critical path: setConnection immediately starts \_refreshSessions; on a cold cache the listSessions round trip and catalog reconciliation must complete before the authoritative remote session list appears. - Scaling input: N returned host sessions, including legacy subagent rows. The diff clones and sorts N entries in O(N log N), then performs the existing O(N) reconciliation; one operation serves the whole host and there is no per-session IPC fan-out.
- Effective concurrency: \_ensureSessionCache suppresses a second refresh while one request is in flight or a retry timer is armed. Direct refresh triggers use generations so only the newest response applies; the diff adds no concurrency burst.
- Cache behavior: Cold cache creates adapters for valid rows. A warm persisted cache contains at most 100 summaries and updates existing adapters, while the live host listing itself is not capped. Failed registrations are not negatively cached, so a later explicit refresh retries them, but the diff no longer creates a timer-driven poll after the successful list response.

### Scenario 2: Local Agent Host startup when authentication is unsettled or listSessions transiently rejects.

- Critical path: After authenticationPending settles, the provider eagerly requests the catalog so the sidebar can populate. A rejected request leaves the cache non-authoritative and the exponential-backoff retry is required for startup recovery.
- Scaling input: N local sessions in one catalog. Ordering adds one N-element array and O(N log N) cheap fragment comparisons before the existing adapter/update pass.
- Effective concurrency: The in-flight and pending-retry guards coalesce synchronous getSessions calls. One disposable timer owns backoff; no changed parallel IPC fan-out occurs.
- Cache behavior: Up to 100 persisted summaries may render immediately on warm startup. Empty success is authoritative and resets backoff; rejection remains distinct and retried. The change preserves those positive, empty, and failure states.
- Mechanism confidence: High: constructor/auth autorun trigger, local protocol boundary, retry state, and tests for first-failure recovery are explicit.
- Magnitude uncertainty: The local catalog is uncapped at the protocol boundary, but no evidence shows the added in-memory sort dominates the pre-existing full protocol mapping and reconciliation.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/electron-browser/localAgentHostService.ts:listSessions -&gt; src/vs/platform/agentHost/browser/agentHostProtocolClient.ts:listSessions</code>: Agent Host protocol listSessions request to the local Agent Host process, including full-catalog serialization and client-side URI/metadata mapping.; cardinality: One initial request; genuine rejection retries at 1s, 2s, 4s up to 30s until success. This behavior is unchanged. A successful response that later fails to apply now makes no automatic retry.
    - Introduced by diff: false; previous behavior: The same IPC request and exponential backoff existed, but apply failures were incorrectly classified as request failures and repeatedly reset to the minimum delay.; critical-path effect: The first successful request is required for an authoritative cold startup catalog; backoff retries are delayed recovery work after failure.
- Verdict: No regression. Genuine startup failures still recover with bounded backoff, while deterministic post-response failures stop generating repeated IPC.

### Scenario 3: A chat turn completes or a newly committed session waits for reconciliation.

- Critical path: ChatTurnComplete starts a background refresh and is off the immediate action-dispatch critical path. \_waitForNewSession explicitly awaits refresh, so its one catalog request and reconciliation are on the path to resolving the committed session.
- Scaling input: N sessions per host catalog and event frequency. Added CPU is O(N log N) per pre-existing explicit refresh, with no new request multiplicity.
- Effective concurrency: Refresh generations make the latest invocation authoritative; this change neither adds Promise.all fan-out nor increases aggregate request scheduling.
- Cache behavior: Warm adapters are updated instead of recreated. Failed colliding rows are attempted on each explicit refresh because they are not cached; that is bounded by existing refresh events rather than a new timer.
- Mechanism confidence: High for trigger and boundary cardinality; low evidence of any measurable regression from the added ordering alone.
- Magnitude uncertainty: Frequent turns and unusually large catalogs increase sorting/logging work, but the diff simultaneously eliminates the much larger 1 Hz failure loop and does not add a trigger or expensive boundary.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_attachConnectionListeners and \_waitForNewSession</code>: One full listSessions protocol request for the connected host.; cardinality: One host-wide request per completion/wait trigger, not one per session. This pre-existing cardinality is unchanged by the diff; generation checks prevent stale responses from applying.
    - Introduced by diff: false; previous behavior: The same triggers issued the same full-list request. The diff only orders the returned array and changes retry classification after a response.; critical-path effect: Background for ordinary turn completion; blocking for \_waitForNewSession until the returned catalog is reconciled.
- Verdict: No reportable regression because request frequency is unchanged on healthy explicit-refresh paths and deterministic apply failures now avoid automatic polling.
