# Performance review: sessions: recover empty Agent Host session list after a failed initial refresh

[PR #319216](https://github.com/microsoft/vscode/pull/319216) at `c78d12135d67fa679616383b49daf5585950230c`

## Findings (1)

### 1. [medium] Bound catalogue retries after persistent failures

**Finding ID:** `PERF-775009F4644F`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:2220</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** renderer-to-agent-host IPC/protocol requests plus repeated backend catalogue, SDK, and metadata work  
**Scaling:** After 1, 2, 4, 8, 16, and 30 seconds, cost remains one full attempt every 30 seconds indefinitely per live failed provider; aggregate work scales with provider/window count, connected remote hosts, catalogue size, and process lifetime.  
**Outcome:** persistent excessive IPC/network and backend I/O after a non-recovering failure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, the eager/connection refresh attempted \`listSessions()\` once and a failure did not create periodic work; another explicit connection/session event was required to refresh again.  
**Changed behavior:** A failed catalogue refresh now recursively re-arms a background timer forever, eventually issuing one full \`listSessions()\` request every 30 seconds for each affected provider.  
**Confidence:** 0.98 — The recursive retry and lack of a lifetime bound are explicit in the changed code. The call path is concrete: the always-created enabled local provider eagerly refreshes after restoration, its \`listSessions\` crosses the renderer/main-process proxy into \`AgentService.listSessions\`, and that method fans out to every registered backend; remote providers similarly send a protocol request per connected host. Exact cost depends on enabled backends and session count, but the recurring boundary work does not.

**Causal diff evidence:** RIGHT line 2220 saturates only the delay at 30 seconds; the new catch at line 2206 schedules after every rejection, and the timer callback invokes \`\_refreshSessions\` again, whose next rejection schedules another timer. No attempt or elapsed-time limit terminates the cycle.

If auth remains unavailable, an endpoint remains incompatible, or another persistent backend error occurs while the provider stays alive, each VS Code window (and each connected remote host) performs a full catalogue attempt every 30 seconds for the rest of its lifetime. This creates continuing IPC/network traffic and backend CPU/filesystem work; sibling providers may still execute because the local service fans them out in parallel, and the cost grows with open windows, remote hosts, session count, and uptime.

**Evidence:** \`\_scheduleSessionRefreshRetry\` doubles the delay only up to \`SESSION\_REFRESH\_RETRY\_MAX\_MS\` and always schedules \`\_refreshSessions\`; every catch calls it again. \`LocalAgentHostSessionsProvider\` eagerly calls \`\_refreshSessions\` after auth settles, \`LocalAgentHostService.listSessions\` forwards over its proxy, and \`AgentService.listSessions\` invokes every provider with \`Promise.all\`. Copilot's implementation calls its CLI client's \`listSessions\`; Claude lists SDK sessions and reads per-session overlays. \`RemoteAgentHostProtocolClient.listSessions\` sends a \`listSessions\` protocol request. Thus a persistent auth/configuration/offline failure keeps initiating catalogue boundary work rather than quiescing.

**Suggested direction:** Bound the automatic recovery window/attempt count and stop retrying terminal failures (especially auth-required without an auth-state transition). After the bound, re-arm only from existing authentication, connection, or explicit refresh events so transient startup failures still self-heal without permanent polling.

### Scenario 3: Remote host connection, failed catalogue reconciliation, reconnect, and disconnect

- Critical path: The initial remote protocol request is required to reconcile and republish that host's sessions. Retries are background recovery work; disconnect cancellation is off the catalogue critical path.

- Effective concurrency: One timer is coalesced per remote provider, but providers are instantiated per configured/tunnel host and retry independently, so aggregate concurrency/cardinality scales with connected hosts. Connection/action-triggered direct refreshes are not governed by a shared cross-host limiter.
- Cache behavior: Each remote provider retains persisted summaries, refreshes on \`setConnection\`, and marks the live cache authoritative only after success. \`clearConnection\` resets the initialized flag and cancels a pending retry; disposal also owns the timer through the base disposable store. While a connection remains assigned and requests reject, there is no terminal failed state.
- Mechanism confidence: High for per-host recursive retries and cancellation on clear/disposal; medium-high for duration of specific remote failure modes because connection-state handling can terminate some failures.
- Magnitude uncertainty: Connection management may promptly call \`clearConnection\` for transport failures, bounding those cases. Server-side auth, protocol, or catalogue failures can leave the connection object live; exact prevalence and server cost are uncertain.
