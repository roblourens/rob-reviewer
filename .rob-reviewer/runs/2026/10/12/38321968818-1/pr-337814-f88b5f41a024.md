### Scenario 2: New-user Copilot harness Chat eligibility and target readiness

- Critical path: When a visible eligible harness Chat exists, readiness waits one second and then resolves three DOM targets every 500 ms until all render or 40 attempts expire. This is off message-send and render critical paths, though each target visibility check synchronously reads computed style and bounds.
- Scaling input: At most 40 timer attempts over about 20 seconds for one currently eligible Chat widget. Target checks short-circuit on the first missing target; successful readiness stops polling.
- Effective concurrency: A single disposable timeout chain runs for the current eligible widget. Observable reruns dispose the prior chain when eligibility/widget identity changes.
- Cache behavior: No cache is used for target readiness; the ready widget is retained in an observable after success, avoiding repeat polling while the same widget remains ready.
- Mechanism confidence: High: timer bounds, disposal ownership, and visibility helper geometry/style reads were traced.
- Magnitude uncertainty: DOM dirtiness at each 500 ms check varies, but the bounded 2 Hz frequency and maximum duration are established.
- Expensive boundaries: none found
- Verdict: No reportable regression: polling is bounded, serialized, canceled with eligibility changes, and too infrequent to establish concrete UI jank.

### Scenario 3: Running the three-step Chat input spotlight tour

- Critical path: The spotlight overlay and picker opening are on the tour interaction path. The overlay samples target geometry each animation frame while a step is visible; mode/permissions steps add one menu element to the sampled bounds. Section switching may pause 400 ms by design before expanding the next section.
- Scaling input: One target plus at most one additional menu element per animation frame for a single active presentation; three total tour steps and one globally serialized onboarding presentation.
- Effective concurrency: The onboarding presentation queue permits one active presentation. Picker handoff polling is serialized and bounded to 20 attempts at 50 ms; step cancellation stops the section-delay continuation and the overlay/listeners are disposed between steps.
- Cache behavior: No geometry cache is appropriate because target/menu positions can move. The overlay compares current and previous rectangles and only performs full layout when bounds change.
- Mechanism confidence: High: overlay animation loop, additional-element provider, picker section path, and presentation serialization were inspected.
- Magnitude uncertainty: Tour dwell time is user-controlled, but per-frame cardinality remains constant and the pre-existing overlay already performed one target geometry read each frame.
- Expensive boundaries: none found
- Verdict: No reportable regression: the diff adds constant work for one extra element only during the rare active tour, without collection scaling or concurrent overlays.

### Scenario 4: Assignment refetch while onboarding treatment reads are unresolved

- Critical path: An existing assignment refetch event invokes onboarding experiment resolution. It reads cached post-refetch treatment variables asynchronously and reevaluates scenarios only when both values become valid; normal editor interaction does not wait for it.
- Scaling input: Number of unresolved experimental onboarding scenarios; currently a small registry count, with two reads each.
- Effective concurrency: Reads for different unresolved scenarios can overlap; within one scenario, refetches during an in-flight read coalesce into exactly one follow-up read rather than an unbounded burst.
- Cache behavior: Valid assignment pairs become a positive window-lifetime cache entry. Missing/partial pairs remain negative-unresolved and are retried only on assignment refetch, with no timers.
- Mechanism confidence: High: event source, local treatment read path, positive-cache lifetime, and in-flight coalescing were traced.
- Magnitude uncertainty: Future registry growth could increase local treatment reads, but current cardinality is small and each read uses the already-refetched client state.
- Expensive boundaries:

Onboarding treatment reads happen after the assignment update and consume client state.
- Verdict: No reportable regression: no per-scenario network fan-out is introduced, retries are event-driven and coalesced, and resolved states stop work.

- Verdict: Performance-neutral to beneficial; this is not recorded as a regression fix because the diff and repository context do not establish a shipped performance symptom or introducing commit.
