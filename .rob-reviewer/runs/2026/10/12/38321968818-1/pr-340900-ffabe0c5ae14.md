## Findings (1)

### 1. [medium] Batch enablement aliases while loading the manifest

**Finding ID:** `PERF-E0F93701284D`  
**Location:** <code>src/vs/workbench/contrib/chat/common/plugins/fileBackedInstalledPluginsStore.ts:198</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Map copies, serialized identity-map bytes, temporary objects, storage/observable updates  
**Scaling:** For E manifest entries with stable enablement identities and an identity map of size A, loading performs E full Map copies and E full JSON serializations, O(E\*A) work and allocation (typically O(E²) after moving an E-plugin inventory). The same work repeats on every startup and external manifest reload because enablementUri remains persisted.  
**Outcome:** Increased startup/reload latency and CPU/GC pressure before marketplace plugins become available, with repeated observable invalidations on live external reloads.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Manifest reads only parsed entries and then published the installed list; enablement identity persistence was not invoked once per stored entry during startup or file-watcher reloads.  
**Changed behavior:** Every parsed entry with enablementUri now calls copyEnablement synchronously. copyEnablement constructs new Map(this.\_identities.get()) and unconditionally sets the observable memento, whose storage adapter JSON-stringifies the whole map, even when that alias is already present.  
**Confidence:** 0.96 — The changed manifest parser demonstrably invokes copyEnablement once for every entry carrying enablementUri. That method clones the complete persisted identity Map and sets an observable memento on every call; the memento serializes the complete Map and publishes a change. The exact installed-plugin count in large real profiles is uncertain, but the repeated full-map work and its placement before installed entries are published are explicit in the traced code.

**Causal diff evidence:** RIGHT line 198 adds copyEnablement inside json.installed.map(...), changing one manifest parse from no identity updates to one full identity update per aliased installed entry.

After a portable move or URI-changing updates, all managed entries retain enablementUri. Opening a profile or receiving an external installed.json edit therefore repeats full identity-map copying/serialization once per plugin before the installed observable is updated, delaying plugin discovery for larger inventories and causing avoidable CPU/GC churn.

**Evidence:** At the added line, \_readFromFile's per-entry map calls \_pluginEnablementService.copyEnablement(enablementUri, pluginUri). AgentPluginEnablementService.copyEnablement clones the entire \_identities map at line 58 and always calls \_identities.set at line 68. ObservableMemento.\_setValue serializes the whole map and calls storageService.store; \_initialize awaits this parser before setting \_installed, so this work is on marketplace-plugin hydration's critical path. The same parser is reached by the file watcher through \_onFileChanged.

**Suggested direction:** Collect source/target aliases while parsing and apply them through one bulk enablement operation that clones and persists the identity map once; also skip the set entirely when every effective mapping is already present. Preserve \_copiedIdentities updates in that same batch so profile-switch behavior remains unchanged.
