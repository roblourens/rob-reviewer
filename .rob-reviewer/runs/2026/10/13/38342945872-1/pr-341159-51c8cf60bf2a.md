# Performance review: extensions: restore installed MCP and plugin sections

## Findings (2)

### 1. [medium] Render installed MCP servers from the populated cache

**Finding ID:** `PERF-C34A3E894F51`  
**Location:** <code>src/vs/workbench/contrib/mcp/browser/mcpServersView.ts:488</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** shared-process and remote-agent IPC calls plus serialization of installed MCP server records  
**Scaling:** Each activation of the default Extensions views or return to an empty search performs one grouped installed-server refresh; the two IPC reads run in parallel, and bytes/object mapping scale with the total installed MCP servers across local and remote scopes.  
**Outcome:** increased Extensions-view latency and unnecessary IPC/serialization work  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Opening the default Extensions view did not create an MCP list and therefore issued no MCP management getInstalled request; McpWorkbenchService had already populated and maintained its local server cache eagerly through its constructor and install/update/uninstall/profile events.  
**Changed behavior:** The added default installed-MCP descriptor creates McpServersListView with an empty query. ExtensionsViewlet calls show('') for each visible default view, which reaches queryLocal(); that unconditionally calls IWorkbenchMcpManagementService.getInstalled again before the new section can finish loading.  
**Confidence:** 0.96 — The added descriptor, empty-query path, awaited view loading, and IPC fan-out are directly traced. The exact delay depends on local versus remote topology and server count, but the redundant boundary calls and full-list serialization are deterministic.

**Causal diff evidence:** RIGHT line 488 newly instantiates McpServersListView as a default installed section; with the default empty query this descriptor adds the redundant queryLocal/IPC path to every Extensions default-view activation.

For users with installed MCP servers, opening Extensions or clearing a search now adds shared-process IPC and, in remote workspaces, a remote-agent IPC round trip to the view-loading Promise.all. This serializes/maps the full installed-server list even though \`mcpWorkbenchService.local\` already contains the authoritative event-maintained snapshot, delaying section readiness and adding work on every reactivation.

**Evidence:** ExtensionsViewlet.showExtensionsViews awaits every visible AbstractExtensionsListView.show call. The new descriptor is visible under DefaultViewsContext; McpServersListView.show('') calls query(''), whose local branch awaits mcpWorkbenchService.queryLocal(). McpWorkbenchService.queryLocal calls mcpManagementService.getInstalled; WorkbenchMcpManagementService fans that into shared/local, remote, and workspace reads, and McpManagementChannelClient.getInstalled is an IPC channel.call that serializes the returned array. McpWorkbenchService already starts queryLocal in its eager constructor and maintains \`\_local\` from management events.

**Suggested direction:** Give the installed descriptor a cached-local mode: await \`whenInitialLocalMcpServersLoaded\`, build the model from \`mcpWorkbenchService.local\`, and retain the existing onChange/onReset listeners. Reserve queryLocal/getInstalled for explicit cache refresh or profile changes already handled by the service.

### 2. [medium] Defer plugin discovery until the installed view is needed

**Finding ID:** `PERF-BE298C3FD1CE`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentPluginsView.ts:687</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** filesystem resolves, file reads, directory watchers, and per-plugin component objects  
**Scaling:** On every workbench restore, cost grows with configured, marketplace-installed, Copilot CLI, and extension-contributed plugins; each discovered plugin resolves its root and manifest and initializes observers/watchers for commands, skills, agents, rules, automations, hooks, and MCP definitions.  
**Outcome:** unnecessary post-restore I/O, CPU/GC pressure, and contention with initial user interaction  
**PR causality:** <code>introduced</code>  
**Previous behavior:** AgentPluginsViewsContribution only registered actions and view descriptors, so IAgentPluginService remained delayed unless MCP discovery or an actual chat/plugin consumer requested it. In sessions with MCP access disabled and no plugin use, startup performed none of this plugin discovery.  
**Changed behavior:** The added constructor dependency resolves the delayed IAgentPluginService as soon as the AfterRestored contribution is created, and AgentPluginService immediately constructs and starts all four discovery providers before the Extensions container or installed-plugin section is requested.  
**Confidence:** 0.92 — The DI activation, AfterRestored timing, and discovery filesystem/watcher call path are explicit. Normal MCP-enabled sessions may already instantiate the service, but the reported MCP-disabled/no-plugin-use trigger deterministically changes from no discovery to eager discovery; only exact wall-clock magnitude varies by plugin count and filesystem.

**Causal diff evidence:** The newly added \`&#64;IAgentPluginService agentPluginService\` constructor parameter at RIGHT line 687 forces resolution of a previously delayed heavyweight service during the always-created AfterRestored view-registration contribution.

With MCP access set to none (a realistic managed configuration) and no chat/plugin interaction, every startup now probes the Copilot CLI config, resolves all configured/installed plugin roots and manifests, and retains their filesystem watchers solely to compute a context key for a view the user may never open. Large plugin sets amplify the post-startup I/O and allocation and can make the restored workbench less responsive.

**Evidence:** chat.view.contribution.ts registers this contribution at WorkbenchPhase.AfterRestored; chat.shared.contribution.ts registers IAgentPluginService as InstantiationType.Delayed. AgentPluginService's constructor creates every registered discovery and calls start(); those starts schedule \_refreshPlugins, and \_discoverAndBuildPlugins performs fileService.resolve/detectPluginFormat/readPluginManifest and creates per-component/root watchers. McpDiscovery does not instantiate PluginMcpDiscovery when mcpAccess is None, establishing a pre-diff configuration where this service could remain dormant.

**Suggested direction:** Keep view registration lightweight and resolve/observe IAgentPluginService only when the Extensions container/default installed-plugin view is first activated (retaining the observer afterward), or expose a genuinely lightweight installed-presence signal that does not start full plugin discovery.
