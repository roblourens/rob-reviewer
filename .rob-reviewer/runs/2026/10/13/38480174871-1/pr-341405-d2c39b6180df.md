## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts:158` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts:458`  
**Introducing path:** `src/vs/workbench/services/search/node/ripgrepTextSearchEH.ts`  
**Introducing commit:** `ee40fa3e0d742709ab6de5e00c9807e28d113775`  
**Mechanism family:** `repeated-work`  
**Performance category:** `subprocess`  
**Confidence:** 0.98

**Mechanism:** Following symlinks in a cross-linked directory graph makes ripgrep revisit the same underlying folders through exponentially many distinct paths, consuming subprocess CPU and filesystem I/O while search appears not to finish.

**Symptom:** Text search can effectively never finish on cross-linked symlink trees such as fake sysfs layouts.

**Fixed behavior:** After more than 1,000 loop diagnostics, the changed stderr handler cancels the pathological ripgrep subprocess and line 158 retries the same folder once with `followSymlinks: false`, converting an exponentially expanding traversal into one bounded failed attempt plus one ordinary traversal.

**Evidence:** In the base text-search argument builder, the blamed line is the `--follow` ripgrep path enabled by the default `search.followSymlinks: true`. The changed `RipgrepSymlinkLoopDetector` documents and counts ripgrep's `File system loop found` diagnostics; the added fixture creates N folders linking to every folder and states that ripgrep enumerates exponentially many paths because it detects only ancestor loops. The integration test drives this through `TextSearchEngineAdapter`, establishing the user search call path and subprocess boundary.

### Scenario 4: File search in a cross-linked symlink tree

- Critical path: After more than 1,000 loop diagnostics, the affected root's process is killed and one non-following \`rg --files\` retry enumerates the physical tree; prior emitted paths are filtered before reporting.
- Scaling input: Cross-link branching and depth controlled the prior exponential work. The new first phase is bounded by loop diagnostics; retry cost and skip-set size scale linearly with the physical tree and already emitted matching paths.
- Effective concurrency: One process initially runs per root. The retry is launched immediately after sending kill, so an affected root can have a brief old/new process overlap during termination; there is only one retry because loop detection is disabled on it. Aggregate concurrency remains proportional to root count.
- Cache behavior: Sorted-search cache hits bypass this path. On a cold affected search, duplicate state is per root and per invocation, then released after callback completion.
- Mechanism confidence: Very high: the changed threshold handler, retry options, fixture, and integration test directly establish the path.
- Magnitude uncertainty: Kill-to-close delay and filesystem size vary, but the bounded retry is decisively cheaper than the demonstrated exponential traversal.
- Expensive boundaries:
