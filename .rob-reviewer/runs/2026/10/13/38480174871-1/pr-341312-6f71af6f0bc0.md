**Relevant issue families:** repeated-work, boundary-fanout, concurrency-burst, cache-lifecycle, serialization-allocation

### Scenario 1: Open or refresh the customization marketplace source picker and all-source metadata

- Critical path: The page's updateSources reads marketplaceService.sources once, constructs source metadata, sorts only repository-backed plugin/provider entries in memory, then renders the source button/menu. allSources is read for warnings and configuration/source-change handling. No subprocess, IPC, filesystem, database, or network operation is reached by the added sort.
- Scaling input: The effective number of policy-allowed, deduplicated configured plugin marketplaces plus harness-reported provider marketplaces; built-in/platform sources are not included in the sort.
- Effective concurrency: Synchronous single-threaded array copy and O(S log S) comparison; source-change refreshes are event-driven rather than frame- or row-driven.
- Cache behavior: Source metadata getters are recomputed on access both before and after the PR; the PR adds one bounded sorted copy. No cache key, negative cache, or remote cache behavior changes.
- Mechanism confidence: High: getter consumers and render paths were traced, including the detail renderer's constant-number source lookups and the discovery page's cached marketplaceSources snapshot.
- Magnitude uncertainty: Users can configure varying marketplace counts, but realistic counts are small and accesses occur on page/source refresh rather than per frame. The added CPU/allocation is not plausibly user-visible.
- Expensive boundaries: none found
- Verdict: No reportable regression. The new in-memory sort has bounded, small cardinality and is not on a high-frequency rendering path.

### Scenario 2: Browse/search customization catalogs across all enabled sources and continue pagination

- Critical path: Search input is coalesced by a 300 ms scheduler. Each request reads the sorted sources getter, filters enabled sources, then awaits CustomizationMarketplaceService.query; the query service retains its pre-existing provider-array order and starts providers with Promise.all. Thus the metadata reorder does not add boundary calls, serialize them, or move them onto a new critical path.
- Scaling input: One logical provider query per enabled provider, after source grouping: MCP Gallery has up to custom/default providers under one source, each configured plugin marketplace has one provider, and enabled harness/connectors/platform providers participate as before. Pagination reuses continuation state and only refills exhausted provider buffers.
- Effective concurrency: All provider states needing data start concurrently via the existing Promise.all. Plugin repository fetches are also concurrent over selected references; because each plugin provider selects one canonical marketplace, effective plugin fetch cardinality remains one repository per enabled plugin source. The PR neither increases nor caps concurrency.
- Cache behavior: Combined pages use an LRU continuation cache of 32 entries with 30-minute expiry. Plugin GitHub repositories use persisted positive TTL cache, cloned repositories use their existing TTL behavior, and connector pages/snapshots use existing continuation and 60-second refresh caching. Sorting changes neither cold/warm keys nor invalidation/coalescing.
- Mechanism confidence: High: source-ID creation, provider filtering, Promise.all fan-out, continuation state, and repository/connector cache paths were traced.
- Magnitude uncertainty: Provider count and cold-network duration vary by user configuration, but the before/after call count and scheduling are established as identical.

### Scenario 3: Render and expose accessibility content for a selected marketplace detail

- Critical path: EmbeddedMarketplaceDetail asks getSourceLabel once during visual render and once when accessibility content is requested. Each call reads sources and performs a linear find; the PR adds sorting of the small repository-source subset before that lookup. README/media loading remains the existing independent detail path.
- Scaling input: Number of configured/provider marketplaces, with a constant number of source-label lookups per selected detail rather than one per result row or animation frame.
- Effective concurrency: Synchronous metadata lookup only; no new concurrent work or queue is introduced.
- Cache behavior: No source-label cache existed before or after. Detail resource and remote preview behavior are unchanged.
- Mechanism confidence: High: both getSourceLabel call sites in EmbeddedMarketplaceDetail and the callback supplied by AICustomizationManagementEditor were inspected.
- Magnitude uncertainty: The exact source count varies, but execution multiplicity is constant per detail render and the work remains small.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added sort is not repeated per result row and is too bounded to establish rendering jank or meaningful latency.

Traced UI consumers, catalog query fan-out, continuation/cache behavior, and remote/filesystem-capable providers; no expensive boundary count, concurrency, lifecycle, or cache behavior changes, and no actionable performance regression was found.
