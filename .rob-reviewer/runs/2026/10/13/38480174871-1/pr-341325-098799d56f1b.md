# Performance review: agentHost: run on-device models with llama.cpp

[PR #341325](https://github.com/microsoft/vscode/pull/341325) at `098799d56f1b1ce289633adfe3418038f0dc0b56`

## Findings (2)

### 1. [medium] Avoid buffering every request before routing

**Finding ID:** `PERF-F27B00B3E4D0`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/localModelBridge/shim/copilotRequestHandler.ts:374</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Full request-body bytes and duplicate Uint8Array-backed objects  
**Scaling:** The added read and copy are O(request-body size) on every model-layer HTTP request while the opt-in handler is installed; long-context agent prompts can contain tens or hundreds of thousands of tokens, and the cost repeats for every model call.  
**Outcome:** Increased request-dispatch latency plus avoidable allocation and GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, the Copilot client had no custom request handler and ordinary cloud/BYOK requests followed the SDK's normal forwarding path without this bridge first materializing and copying their complete bodies.  
**Changed behavior:** With on-device models enabled, the client installs this handler globally; every relayed request now awaits bufferRequest before classification, including requests ultimately classified as passThrough. bufferRequest calls request.arrayBuffer(), and passThrough rebuilds the Request through toRequest(), whose body uses buffered.body.slice().  
**Confidence:** 0.99 — The client-wide installation, unconditional call path, full-body allocation, second copy, and pass-through reachability are explicit in the changed code. Exact milliseconds depend on prompt size and runtime internals, but the scaling mechanism and large-context trigger are not speculative.

**Causal diff evidence:** The added RIGHT line 374 unconditionally executes \`await bufferRequest(request)\` before route classification for every request handled by the newly installed client-wide bridge.

An opted-in user sending a large ordinary cloud agent request must now fully read and copy the prompt body before fetch can begin. At large context sizes this adds critical-path latency and transient memory/GC pressure even when no local model or Auto routing is used.

**Evidence:** CopilotAgent installs the handler as the client's requestHandler at src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3274. This class states that every model-layer request is relayed through it, line 374 unconditionally buffers before routing, bufferRequest at lines 70-76 materializes the whole body, and toRequest at lines 80-87 clones it again. The passThrough branch still uses that rebuilt request, so the mechanism reaches ordinary cloud and unrelated BYOK traffic.

**Suggested direction:** Keep the original Request on the fast path and classify obvious pass-through traffic before materializing its body. Buffer only candidate Auto/local routes that need inspection or replay, and avoid \`slice()\` for one-shot forwarding; create additional copies only when a fallback/reissue actually requires them.

### 2. [medium] Skip the full Auto benchmark on direct-only starts

**Finding ID:** `PERF-B24EE31DE654`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/localModelBridge/shim/serverSupervisor.ts:753</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** GPU model inference for an unrelated prompt and 32 generated tokens  
**Scaling:** The benchmark is paid on every server cold start, including the first direct request after the 15-minute idle unload and subsequent crash/restart loads; its latency is TTFT plus generation of 32 tokens, bounded only by the 120-second warm-up timeout.  
**Outcome:** Blocked first-response critical path for directly selected on-device models  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this feature, a direct chat did not start a local server or run this synthetic inference. Within the new start path, the server is already healthy and authenticated before this step and could otherwise admit the waiting direct request immediately.  
**Changed behavior:** Every successful server start now awaits \`\_warmUp\` before publishing \`server: 'ready'\`, regardless of whether Auto is enabled or the start was triggered by a direct request. \`\_warmUp\` sends an unrelated greeting with \`max\_tokens: 32\` and \`cache\_prompt: false\`.  
**Confidence:** 0.97 — The direct-request call path, awaited benchmark, readiness ordering, token count, and timeout are explicit. Hardware determines the exact delay, but all direct cold starts necessarily pay nontrivial model-inference work that is unrelated to the user's prompt.

**Causal diff evidence:** The added RIGHT line 753 synchronously awaits the synthetic model completion on the universal start path before the newly added server can transition to ready.

When a user directly selects an unloaded model, \`ensureStarted\` keeps their real prompt waiting while the model first processes and generates a separate 32-token completion. Even a model that just meets the configured 8 token/s Auto gate adds roughly four seconds of decode time plus TTFT; slower direct-capable configurations can wait up to the 120-second timeout.

**Evidence:** Direct requests call \`serving.ensureStarted\` in copilotRequestHandler.ts:799-808. A start reaches a healthy authenticated server before this hunk, but line 753 awaits \`\_warmUp\`; readiness is not published until serverSupervisor.ts:813. The warm-up body sets \`max\_tokens: WARMUP\_GENERATED\_TOKENS\` at line 1115, constants.ts defines that as 32 and the timeout as 120 seconds, and the result is primarily consumed by \`passesAutoGate\` for Auto eligibility.

**Suggested direction:** Run the full 32-token performance benchmark only when \`useInAuto\` is enabled (or off the direct-request critical path). For direct-only starts, use at most a minimal health/speculative-decoding probe, then publish ready so the waiting user prompt can run.

### Scenario 1: Ordinary cloud or unrelated BYOK model call after the user enables on-device models

- Scaling input: Request-body bytes per model call, realistically large for 64K-256K-token agent contexts; concurrent model calls multiply transient retained bytes.
- Effective concurrency: No coalescing or limiter applies to request buffering. Each concurrent SDK request independently materializes and copies its full body before its own fetch.
- Cache behavior: No cache applies; the read and copy repeat for every request, regardless of route or warm state.
- Mechanism confidence: High: global handler installation, unconditional buffering, pass-through reachability, and the second copy are explicit.
- Magnitude uncertainty: Exact body sizes and allocation behavior inside the SDK vary, but long-context agent prompts make multi-megabyte bodies realistic.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/localModelBridge/shim/copilotRequestHandler.ts:408</code>: Forward the model-layer HTTP request through proxyFetch or loopbackFetch; cardinality: One existing outbound fetch per pass-through model call; fallback/reissue paths can intentionally issue a second CAPI request.
    - Introduced by diff: false; previous behavior: The SDK used its normal forwarding path without the PR's client-wide custom bridge or mandatory pre-forward body materialization.; critical-path effect: The fetch cannot begin until the newly added full-body buffering and copy complete.
  - serialization at <code>src/vs/platform/agentHost/node/copilot/localModelBridge/shim/copilotRequestHandler.ts:70-86</code>: Read the complete Request body into an ArrayBuffer and copy it with Uint8Array.slice when rebuilding the request; cardinality: Once plus one full copy for every non-GET/HEAD request handled, including pass-through traffic.

### Scenario 2: First direct on-device prompt with the model unloaded, including after idle unload

- Critical path: The request waits in ensureStarted; runtime capability resolution and launch-plan preparation complete, llama-server is spawned and polled healthy, API-key enforcement is checked, props are read, then a 32-token synthetic completion is awaited before ready is published and the user's actual prompt can acquire a slot.

  - subprocess at <code>src/vs/platform/agentHost/node/copilot/localModelBridge/shim/serverSupervisor.ts:\_doStart/\_spawnUntilHealthy</code>: Fresh llama-server device admission probe and one long-lived llama-server spawn; cardinality: One device probe and normally one server spawn per cold start; bounded downgrade or port/auth retries can add spawns.

- Effective concurrency: Catalog resolutions share a limiter of two. One model download is sequential across files and guarded by a per-family process lock; transfers implement backpressure and retry from partial files rather than burst concurrency.
- Cache behavior: Catalog results and content facts persist for 24 hours; GPU/runtime capability is cached by topology and binary/library fingerprint; verified partials resume, but complete files are intentionally rehashed before reuse. Adopted-file hashes are cached by path, mtime, and size.
- Mechanism confidence: High: boundary counts, sequential transfer policy, caches, lock, and retry limits are explicit.
- Magnitude uncertainty: Catalog size is bounded and currently small; download duration depends mainly on network/disk throughput for the 56.7 GB model.
- Expensive boundaries:

### Scenario 4: Auto routing with a loaded on-device model and cloud fallback

- Critical path: A CAPI /auto request may be patched with the local offer; if selected, the handler leases the pinned generation and a nonblocking slot, sends to loopback, buffers only until first local output, and either commits local output or issues one cloud fallback before commitment.
- Scaling input: One route record per Auto session token (soft cap 1024); one local request per selected model call; a pre-output local failure adds one fallback request.
- Effective concurrency: Auto never queues for a model slot; it falls back when slots are full. llama-server slot count bounds local inference, while route records are leased and swept.
- Cache behavior: Route records are in memory, expire with a grace period, are capped, and are invalidated by account generation. Endpoint failures are temporarily down-marked. Loaded model state avoids cold starts until idle unload.
- Mechanism confidence: High.
- Magnitude uncertainty: CAPI currently may rarely choose the local offer, so prevalence is uncertain; the route and concurrency mechanics are explicit.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/localModelBridge/shim/copilotRequestHandler.ts:\_handleCapiAuto/\_fallback</code>: CAPI /auto declaration and optional cloud fallback request; cardinality: One /auto call; at most one fallback inference call for the traced local attempt.
    - Introduced by diff: true; previous behavior: CAPI selected and served cloud models without this local declaration/fallback bridge.; critical-path effect: CAPI selection precedes model inference; fallback begins only before any local output is committed.
  - network at <code>src/vs/platform/agentHost/node/copilot/localModelBridge/shim/copilotRequestHandler.ts:\_dispatchLocal</code>: Loopback llama-server completion; cardinality: One per locally selected Auto model call, bounded by available server slots.
    - Introduced by diff: true; previous behavior: No local inference boundary existed.; critical-path effect: This is the inference critical path when Auto selects local; first-output timeout permits fail-open fallback.
- Verdict: No separate finding beyond global request buffering; slot admission, route retention, and fallback cardinality are bounded.
