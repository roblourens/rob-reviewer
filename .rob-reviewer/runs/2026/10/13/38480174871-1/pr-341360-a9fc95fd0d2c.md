<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** serialization-allocation, boundary-fanout

### Scenario 1: Create a regular or ephemeral Copilot SDK session

- Critical path: The launcher builds session configuration, reads the already-published root assignment string synchronously, then the existing SDK createSession call must complete before the session is usable. The diff adds only a small object/string reference to that existing configuration path.
- Scaling input: One metadata object per session launch; assignment length scales with the finite workbench experiment assignment list. Concurrent session launches retain their own config objects until their existing create calls settle.
- Effective concurrency: Unchanged: each launch issues its existing createSession call, while aggregate launch concurrency remains controlled by callers. The diff adds no task, queue, timer, or parallel boundary operation.
- Cache behavior: The assignment context is read from the in-memory root config value bag; no cache miss or fetch is introduced. TAS retrieval and publication occur earlier in AgentHostPrewarmer and are not invoked by the changed launcher. Empty or unset values avoid constructing expAssignments.
- Mechanism confidence: High: the changed line reads an in-memory object and spreads one optional object into configuration passed to the existing SDK call; the PR description and code establish transitive header forwarding without a new request.
- Magnitude uncertainty: Exact assignment-string length and number of model requests vary by active experiments and conversation length, but the diff neither duplicates the string per item in host code nor creates an additional boundary call. The incremental header cost is not a reportable regression.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:\_createSession and added configuration at line 1228</code>: Send SDK session configuration to the Copilot runtime through client.createSession.; cardinality: One existing create call per successful create launch; the assignment metadata is included once in that existing call.
    - Introduced by diff: false; previous behavior: The same createSession IPC occurred with the full session configuration but without expAssignments.; critical-path effect: The create call was already on the session startup critical path. The diff slightly enlarges its serialized configuration but adds no round trip.
  - network at <code>Transitive SDK/runtime behavior configured by src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:1228</code>: Send subsequent model requests from the runtime to CAPI with X-Copilot-Client-Exp-Assignment-Context.; cardinality: One added bounded header value on each existing CAPI model request made by the session; no additional request is created.
    - Introduced by diff: false; previous behavior: The same CAPI requests occurred without the VS Code client assignment header.; critical-path effect: The existing model request remains critical; only header bytes and normal header serialization are added, with no evidenced material latency mechanism.
- Verdict: No reportable performance regression. The added bounded metadata is necessary for attribution and piggybacks on existing create and model-request boundaries.

### Scenario 2: Resume an existing Copilot SDK session, including retry and empty-history fallback

- Critical path: The launcher builds configuration once, reads assignment context from memory, and waits for the existing resumeSession call. Existing custom-agent retry and empty-history create fallback reuse that same config object; the diff does not rebuild or refetch assignment data for each attempt.
- Scaling input: One assignment object per logical resume launch, reused across at most the pre-existing resume retry/fallback attempts. Cost does not scale with session history because the launcher does not inspect or copy history.
- Effective concurrency: Unchanged per-launch sequencing: resume attempts and fallback creation are serialized by existing control flow; separate session resumes may run concurrently as before. No new burst or limiter bypass is introduced.
- Cache behavior: Warm in-memory root config read for both cold and previously active sessions. Refreshed assignments are consumed on the next launch; there is no new negative-cache behavior, polling, or network fetch on resume.
- Mechanism confidence: High for host-side allocation, call cardinality, and sequencing; medium-high for per-request runtime forwarding based on the SDK contract and PR's tested behavior.
- Magnitude uncertainty: Runtime-internal serialization details are outside the repository, but the changed host call flow proves no additional IPC or network operation. Potential byte overhead varies with assignment length and request count and is too small/bounded to establish actionable degradation.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:\_resumeSession/\_createSession and added configuration at line 1228</code>: Send resume configuration to the Copilot runtime through client.resumeSession, with an optional existing createSession fallback.; cardinality: Normally one existing resume call; up to a second resume and one create only on pre-existing error/fallback paths. The same assignment metadata is reused for all attempts.
    - Introduced by diff: false; previous behavior: Identical resume/retry/fallback call counts without expAssignments in their configuration.; critical-path effect: These calls were already serialized on resume's critical path. The diff increases payload by one small assignment structure but does not increase attempt count.
  - network at <code>Transitive SDK/runtime behavior configured by src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:1228</code>: Send subsequent resumed-session CAPI requests with the assignment-context header.; cardinality: One header value per existing model request after resume; effective network request cardinality is unchanged.
    - Introduced by diff: false; previous behavior: Existing CAPI requests omitted the VS Code client assignment context.; critical-path effect: Only existing request metadata changes; no separate attribution request or handshake is added.
- Verdict: No reportable performance regression. Resume call cardinality, ordering, and concurrency are unchanged, and metadata construction occurs once per logical launch.

**Summary:** Reviewed the complete three-file diff and traced session create/resume through configuration storage, SDK IPC, retry/fallback sequencing, and transitive CAPI requests. The change adds bounded metadata to existing boundaries without new calls, fan-out, eager heavyweight work, retention, cache churn, or concurrency, so no performance finding was submitted.
