# Performance review: chat: enable Insiders image generation and polish previews

## Findings (3)

### 1. [low] Avoid downloading image bodies just to display their byte size

**Finding ID:** `PERF-5360BFB4373E`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatInputOutputMarkdownProgressPart.ts:217</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Remote resourceRead calls, base64 bytes, decoded image buffers, and IPC/network bandwidth  
**Scaling:** One concurrent full-body read per referenced generated image; cost grows with both output count and total image byte size.  
**Outcome:** Excessive IPC/network I/O, expansion metadata latency, and transient memory pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, the dropdown had no image-size metadata and expanding it issued no file reads for referenced generated images.  
**Changed behavior:** Expanding a completed image-generation dropdown now launches Promise.all over referenced outputs and calls fileService.readFile for each image whose byte length is not embedded.  
**Confidence:** 0.99 — The changed read, per-image concurrency, provider boundary, full-body base64 decode, and expansion trigger are directly established. Exact byte volume depends on generated image sizes.

**Causal diff evidence:** RIGHT line 217 adds the full-body read inside Promise.all for every referenced image lacking byteLength; no corresponding read existed before the metadata feature.

Expanding details for remote generated images can re-transfer megabytes that were already loaded for preview, delay the size field, and transiently allocate all referenced image bodies at once; multiple outputs fan out concurrently.

**Evidence:** The added line reads each complete image into a VSBuffer only to use value.byteLength. For vscode-agent-host resources, AgentHostFileSystemProvider.readFile performs a remote resourceRead with Base64 encoding and decodes the returned body, so this is a full cross-boundary transfer and allocation rather than a metadata query. The added test explicitly verifies the read starts on expansion.

**Suggested direction:** Propagate optional byte length from tool/resource metadata into the reference part (or use resource stat when it reports a real size), and coalesce/cache any unavoidable fallback with the preview's existing load instead of issuing a separate concurrent body read per image.

### 2. [medium] Update generated-image pills incrementally instead of rescanning the transcript

**Finding ID:** `PERF-2E82098E5669`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionArtifacts.ts:571</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** UI-thread CPU work and transient observable, array, map, action, and pill-entry objects  
**Scaling:** O(total requests plus total response parts and surfaced artifacts) per response update; multiplied by the number of streamed updates in the active turn.  
**Outcome:** Increasing CPU/GC pressure and response-rendering latency for long conversations  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, SessionArtifacts derived its sections only from persisted session artifacts/references and did not observe streamed chat response updates or scan the chat transcript.  
**Changed behavior:** The new generated-images derivation subscribes to every response's onDidChange event and, when any response changes, walks every request and every response part again, then rebuilds all artifact sections and entries.  
**Confidence:** 0.98 — The event source, synchronous derived dependency, always-observed toolbar path, and full-history loop are explicit. Only the exact history length and stream update count vary by user.

**Causal diff evidence:** The added RIGHT line 571 subscribes generatedImages to each response.onDidChange; the surrounding added loop then recomputes generated images for all requests and causes sectionsFor to rebuild the artifact presentation.

In a long Agents conversation, each streamed chunk synchronously rescans the entire history and reallocates response signals, image arrays, maps, actions, and pill entries, adding UI-thread CPU/GC pressure and making response streaming increasingly janky as the conversation grows.

**Evidence:** ChatResponseModel forwards Response.onDidChangeValue to onDidChange, and Response.\_contentChanged fires that event for each non-quiet streamed content update. This added listener is inside a derivation that iterates model.getRequests().slice().reverse(), calls getGeneratedImageResources over each response.value, and feeds the newly allocated image list into buildSessionArtifactSections. SessionChatInputToolbar wires these sections into always-instantiated ChatInputPills, so the work is reachable while the Agents chat is open.

**Suggested direction:** Keep a per-response cached/derived image list keyed by response and update only the response that changed, then aggregate cached lists when requests are added/removed. Avoid recreating event observables inside the whole-history derivation.

### 3. [medium] Do not invalidate all artifact caches for every streamed chunk

**Finding ID:** `PERF-40E0B70EC064`  
**Location:** <code>src/vs/workbench/contrib/chat/common/tools/chatArtifactsService.ts:194</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** UI-thread CPU work plus transient event-observable, set, and aggregate-array allocations  
**Scaling:** O(total response parts plus cached artifacts) for every streamed response update, rather than O(changed response) or only artifact-relevant transitions.  
**Outcome:** Higher CPU/GC pressure and lower response-streaming throughput as transcript size grows  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, the derivation was invalidated by request-list/model changes and rule changes; ordinary streamed response content did not trigger a full-history artifact pass.  
**Changed behavior:** The rules-artifacts derivation now observes every response change. Any streamed content event reruns the outer loop over all requests, scans every part to recount tool states, reconstructs the aggregate artifact list, and recreates response event observables even when every per-response extraction cache entry remains valid.  
**Confidence:** 0.98 — The source event fires directly from streamed content updates, the full-history loops precede cache lookup, and ChatArtifactsWidget keeps the derived value observed. Magnitude depends only on chat length and provider chunk cadence.

**Causal diff evidence:** The added RIGHT line 194 introduces response.onDidChange as a dependency of the one derivation that loops all requests; the new counts at lines 200-210 ensure every response part is revisited before cache hits can be recognized.

Long chats with the artifacts widget pay history-wide synchronous CPU and allocation cost at token/progress cadence, reducing streaming throughput and causing UI jank even when a markdown chunk cannot change artifacts.

**Evidence:** Response.\_contentChanged emits onDidChangeValue for each non-quiet update, ChatResponseModel forwards that to response.onDidChange, and the added line subscribes the single history-wide derivation to it. The cache check occurs only after the code has iterated every response.value to compute partsLength, completedToolCount, and toolResultCount; afterward all cached artifacts are still deduplicated into a new allArtifacts array. ChatArtifactsWidget continuously observes artifactGroups after a session resource is set.

**Suggested direction:** Factor extraction/signature tracking into a per-response derived/cache so only the changed response is rescanned, and aggregate cached results separately on request add/remove. If possible, invalidate on tool-result/completion transitions rather than generic response content events.
