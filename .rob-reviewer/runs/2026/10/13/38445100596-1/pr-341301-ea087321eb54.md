# Performance review: Manage Copilot plugin marketplaces through Agent Host

[PR #341301](https://github.com/microsoft/vscode/pull/341301) at `ea087321eb54aaf77deb2fb10228226cc58e1230`

## Findings (2)

### 1. [medium] Cache each marketplace browse across pages

**Finding ID:** `PERF-B1FEFE173FA0`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationMarketplaceInstallProvider.ts:109</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** SDK/Agent Host IPC calls plus serialization, allocation, and filtering of complete plugin arrays  
**Scaling:** For P plugins and K requested pages, this performs K full browses and O(K\*P) transfer/filter work instead of one O(P) browse followed by cached slicing; aggregate work also multiplies by the number of enabled provider marketplaces.  
**Outcome:** Repeated continuation latency with excessive IPC, CPU, allocation, and GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, provider-owned marketplaces were not exposed as Discover sources, so continuing a Discover result set did not repeatedly invoke this new whole-marketplace SDK browse path.  
**Changed behavior:** Every source-page request now invokes Agent Host \`browsePluginMarketplace\`, receives the complete plugin array, filters the complete array, and only then slices out the requested page.  
**Confidence:** 0.99 — The full-array SDK return type, post-fetch slicing, continuation loop, 24-item page size, eight-page backfill limit, and two-call pagination test directly establish the mechanism. Exact marketplace sizes and SDK browse duration are the only magnitude uncertainties.

**Causal diff evidence:** Added RIGHT line 109 places \`browsePluginMarketplace\` inside \`queryMarketplace\`, which is the per-page provider callback; added lines 115-120 apply cursor and page size only after the complete response arrives.

Browsing or scrolling a provider marketplace with more than one page repeatedly blocks each continuation on a full SDK/IPC browse and retransfers every plugin. Search backfill can do this up to eight times in one load, increasing result latency, IPC traffic, CPU, allocations, and GC; multiple enabled marketplaces perform these calls concurrently.

**Evidence:** The added call at line 109 crosses LocalAgentHostServiceClient -&gt; AgentHostManagementService -&gt; AgentService -&gt; CopilotAgent, where \`client.rpc.plugins.marketplaces.browse({ name })\` returns the full \`plugins\` array. This method applies \`options.cursor\` only after that response. \`CustomizationMarketplaceService\` requests another source page whenever its buffered page is consumed, and Discover uses 24-item search pages and can backfill up to 8 pages. The added provider test explicitly requests two one-item pages and expects two \`browse\` calls, proving that continuation does not reuse the first complete result.

**Suggested direction:** Cache/coalesce the complete browse result per marketplace and marketplace-inventory generation, then filter and page that snapshot locally. Invalidate it only on marketplace add/remove/refresh or provider reconnect so continuations and repeated identical searches do not cross the SDK boundary again.

### 2. [medium] Listen only for marketplace inventory changes

**Finding ID:** `PERF-092C1F73B4CF`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceWorkbenchService.ts:164</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Agent Host/SDK list IPC calls and downstream catalog browse calls, serialized arrays, CPU, and allocations  
**Scaling:** Cost grows with unrelated customization/plugin/MCP event frequency; while Discover is visible, each event fans out across every enabled source and each provider marketplace's catalog size. Overlapping events are version-discarded but their boundary calls are not coalesced or cancelled.  
**Outcome:** Excessive background IPC and repeated visible catalog reload latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, the workbench marketplace service did not subscribe to this provider event, so unrelated customization, plugin inventory, and Agent Host lifecycle changes did not list marketplace inventory or invalidate/requery Discover sources. Those events only drove the pre-existing installation synchronization path.  
**Changed behavior:** The new binding treats every \`managementProvider.onDidChange\` event as a marketplace inventory change, calls \`provider.list()\`, and passes \`forceChangeEvent=true\`, which emits a source change even when the marketplace list is identical.  
**Confidence:** 0.98 — The broad event composition, event producers, added listener, unconditional forced source event, and Discover reload path are all explicit in repository code. Frequency depends on active MCP/customization activity and whether Discover is visible, which affects severity but not the mechanism.

**Causal diff evidence:** Added RIGHT line 164 subscribes the broad provider \`onDidChange\` and routes it to a fresh inventory list with forced notification; this subscription and boundary work did not exist before the PR.

After the customization marketplace service has been instantiated, ordinary Copilot plugin discovery, MCP start/stop/auth transitions, customization updates, or Agent Host reconnects trigger an extra SDK marketplace-list IPC. If Discover is visible, each event also discards the catalog cache and re-browses all enabled sources, delaying and repeatedly reloading results during unrelated agent activity.

**Evidence:** The concrete management provider is \`AgentHostCustomizationMarketplaceInstallProvider\`, whose existing \`onDidChange\` is \`Event.any\` over customization changes, the global plugin observable, Agent Host start/exit, and its own mutation emitter. \`WorkbenchAgentHostCustomizationService\` fires customization changes for session customization and MCP server state actions. The added listener at line 164 sends all of those events to \`refreshProviderMarketplaces\`; with \`forceChangeEvent\`, line 179 fires \`\_onDidChangeSources\` regardless of equality. The visible Discover page handles that as a forced availability change, clears its cache, and immediately reloads the catalog, issuing per-source queries/browses. The new workbench test also proves one generic provider event increases \`listCalls\` from one to two.

**Suggested direction:** Expose and subscribe to a marketplace-specific inventory-change event, fired only for add/remove/refresh or a relevant reconnect. Coalesce in-flight list refreshes and emit \`onDidChangeSources\` only when the inventory actually differs; keep installation/customization/plugin events on their existing installation listener.

### Scenario 1: Open Discover and browse/search provider-owned Copilot plugin marketplaces, including scrolling to continuation pages

- Critical path: The delayed marketplace service first lists provider marketplaces before those sources can appear. A Discover load then waits for \`CustomizationMarketplaceService.query\`, which waits for each selected source's provider query; provider marketplace queries synchronously await Agent Host and SDK browse before returning any page. This work is on the visible result critical path.
- Scaling input: M enabled provider marketplaces, P plugins per marketplace, K continuation/backfill pages, and debounced search revisions. Exhausting one marketplace costs K full-array transfers and O(K\*P) filtering rather than one transfer.
- Effective concurrency: All source states without buffered items are queried with \`Promise.all\`, so M provider marketplaces can issue M SDK browse calls concurrently. Continuations are serialized by the visible page loader, but each source continuation performs another full browse. Cancellation is checked only before and after the Agent Host call, so an obsolete in-flight SDK browse still runs.
- Cache behavior: The Discover page caches only completed empty-query browse pages. Search revisions are not cached. \`CustomizationMarketplaceService\` retains continuation state and one sliced source page, but the provider does not retain the full SDK browse response, so every source cursor is a cold full browse. There is no in-flight coalescing.
- Mechanism confidence: Very high: the provider test explicitly expects two SDK browse calls for two one-item pages, and the production call path and page sizes are directly traced.
- Magnitude uncertainty: Actual marketplace sizes and SDK browse latency vary, but the full-array transfer and per-page repetition are explicit. This supports medium severity without requiring a timing estimate.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceWorkbenchService.ts:166 -&gt; AgentHostCustomizationMarketplaceInstallProvider.list -&gt; CopilotAgent.listPluginMarketplaces</code>: List the provider's plugin marketplace inventory through the browser-to-Agent-Host management channel and Copilot SDK RPC; cardinality: One cold call when the delayed workbench service binds the active provider, then one per accepted provider change; no call for unsupported/local harnesses
    - Introduced by diff: true; previous behavior: Provider-owned marketplaces were not projected as sources, so this inventory boundary was absent from Discover.; critical-path effect: Provider sources are unavailable until the inventory result is committed and a source-change event is emitted
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationMarketplaceInstallProvider.ts:109</code>: Browse a complete marketplace plugin array through Agent Host and \`client.rpc.plugins.marketplaces.browse\`; cardinality: One call per enabled provider marketplace on the first source page, repeated for every later source page and every debounced search; up to eight sequential pages may be requested by one filtered backfill load
    - Introduced by diff: true; previous behavior: No provider-owned Discover source invoked this SDK browse path.; critical-path effect: Each requested page waits for the complete marketplace array to cross the SDK and Agent Host boundaries before local filtering and slicing
- Verdict: Reportable repeated-work regression: pagination/search repeatedly transfers and filters entire marketplace inventories instead of reusing one snapshot.

### Scenario 2: Run an agent, change plugins/customizations, or transition MCP server state after the provider marketplace service has been instantiated

- Critical path: The broad provider event immediately starts a marketplace-list IPC. When Discover is visible, completion forcibly emits a source change; the page clears its catalog cache and immediately reloads all current sources, putting list and browse work on the visible result path. When Discover is hidden, the list IPC remains background work.
- Scaling input: E unrelated provider events times M enabled marketplaces and their catalog sizes. MCP start/stop/auth and session customization state actions provide realistic repeated events during agent use.
- Effective concurrency: Each event launches a list promise immediately. \`marketplaceManagementRefreshVersion\` prevents stale results from committing but does not cancel or coalesce their boundary calls. A resulting catalog query fans out concurrently across enabled sources.
- Cache behavior: The stored inventory is replaced after each successful list. \`forceChangeEvent=true\` bypasses equality and forces Discover to clear \`browseCatalogCache\`; there is no negative cache or in-flight list coalescing.
- Mechanism confidence: Very high: the provider event is explicitly composed from customization, plugin, and host lifecycle events; the new test confirms a generic event causes another list; the forced cache-clear/reload path is direct.
- Magnitude uncertainty: Frequency depends on active plugins/MCP servers and whether the user has opened the customization service or currently shows Discover, but the extra list occurs for every broad event once bound.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceWorkbenchService.ts:164</code>: Relist provider marketplace inventory for a generic provider \`onDidChange\` event; cardinality: One list call for every customization change, global plugin observable update, Agent Host start/exit, or provider mutation event; overlapping events are not coalesced

  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceWorkbenchService.ts:179 -&gt; aiCustomizationDiscoveryPage.ts:1083</code>: Requery enabled catalog sources, including complete provider marketplace browses, after the forced source-change event; cardinality: Up to M provider browse calls per completed broad event while Discover is visible, plus unchanged platform/source queries
    - Introduced by diff: true; previous behavior: Unrelated plugin/customization/MCP events did not invalidate Discover marketplace sources or trigger this reload.; critical-path effect: Clears visible cached results and waits for a fresh catalog page
- Verdict: Reportable boundary-fanout regression: unrelated runtime state changes now cross the marketplace SDK boundary and can fan out into full visible catalog reloads.

### Scenario 3: Add, refresh, or remove a provider-owned marketplace from the management quick pick

- Critical path: The picker waits for the initial list, the selected mutation, and then the next loop's list before presenting refreshed choices. Forced removal waits for an initial remove, confirmation, and a second remove. These calls are intentionally on the user action path.
- Scaling input: Number of user-selected mutations and marketplace inventory size; this is an explicit, low-frequency management workflow rather than a hot path.
- Effective concurrency: One picker workflow awaits operations serially. \`\_runMutation\` tracks but does not globally serialize mutations; separate listener refreshes may overlap the loop's list.
- Cache behavior: The picker intentionally relists on each loop. Provider mutations emit the broad change event; there is no shared list promise with the workbench source service. SDK add also performs a follow-up list.
- Mechanism confidence: High: all calls and ordering are explicit.
- Magnitude uncertainty: SDK mutation and list duration are unknown, but user invocation frequency is low and inventory cardinality is normally modest.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/actions/chatPluginActions.ts:364-458 and src/vs/platform/agentHost/node/copilot/copilotAgent.ts:2097-2142</code>: List, add, refresh, and remove marketplaces through Agent Host and Copilot SDK RPCs; cardinality: One list per picker iteration. Add performs add plus an internal list to resolve the added item, then the loop lists again; when the workbench source listener is bound, the emitted change also starts a background list. Refresh/remove similarly emit a change and return to a fresh list; forced remove can perform two remove calls.
    - Introduced by diff: true; previous behavior: Local management read or wrote configured/Copilot settings rather than invoking provider marketplace SDK operations.; critical-path effect: The action awaits its mutation and loop list; listener-driven list work can overlap but is not required to finish the picker loop
- Verdict: No separate finding for the picker itself because the repeated calls are bounded by explicit user mutations; the generic event amplification is covered by the reported listener finding.

- Effective concurrency: Install waits are sequential, while listener-driven list refreshes can overlap subsequent plugin observable events. Version checks discard stale results but do not bound calls.
- Cache behavior: Installation inventory has its own refresh version. Marketplace inventory refresh is separate and uncoalesced; forced source notification clears the Discover cache even if inventory is unchanged.
- Mechanism confidence: High.
- Magnitude uncertainty: The exact number of plugin observable updates per install varies, but both explicit provider emissions and plugin inventory updates are established event sources.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationMarketplaceInstallProvider.ts:283-388</code>: Install/uninstall through Agent Host followed by provider installation/plugin inventory synchronization; cardinality: One mutation per explicit install/uninstall, with existing inventory waits/events
    - Introduced by diff: false; previous behavior: Provider installation operations already emitted \`onDidChange\` to refresh installation state.; critical-path effect: Required for the requested install state and pre-existing
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceWorkbenchService.ts:164</code>: Additional marketplace list and possible catalog browse fanout caused by reusing the same event for marketplace inventory; cardinality: At least one extra list per emitted provider change; plugin observable and explicit provider emissions can produce multiple events around one operation
    - Introduced by diff: true; previous behavior: Installation changes did not trigger marketplace-list or Discover source invalidation.; critical-path effect: Usually background to install completion, but visible Discover reload is user-facing and competes for the same Agent Host/SDK resources
- Verdict: The extra work is part of the reported broad-event boundary-fanout finding.
