# Performance review: sessions: make opening large Agent Host chats non-blocking

[PR #341322](https://github.com/microsoft/vscode/pull/341322) at `af7a5b4cd6c56c914d453d532f403c969ea49699`

## Findings (1)

### 1. [medium] Avoid rescanning listeners on every live response update

**Finding ID:** `PERF-E1E710E18059`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionArtifacts.ts:592</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU iterations and temporary Set/array allocations over every request and response listener  
**Scaling:** For a transcript with N requests, each non-coalesced live response-update burst now performs an added O(N) listener-tracking pass before the existing O(N) generated-image extraction pass, so added work grows as O(N × live update bursts).  
**Outcome:** Increased renderer CPU and GC pressure while a response streams in a large chat, causing avoidable interaction lag.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** A response onDidChange invalidated generatedImages directly, whose recomputation scanned model.getRequests once to extract generated images.  
**Changed behavior:** The coalesced event callback now always calls track(), which scans all requests, builds a Set, and iterates all tracked listeners; consuming that signal immediately recomputes generatedImages and scans the transcript again.  
**Confidence:** 0.96 — The added callback, response event call path, debounce semantics, and both transcript scans are directly visible in code. Exact user-visible duration varies with transcript size and streaming cadence, so severity is medium rather than high.

**Causal diff evidence:** Added RIGHT line 592 invokes track() from the shared coalesced callback for both model-structure events and response-content events; before the diff, response-content events only invalidated the generatedImages derived and did not run a listener-maintenance scan.

With the artifacts presentation active on a large chat, every streamed progress update that lands in a separate event-loop burst pays two transcript-wide passes instead of one. The debounce only combines synchronous events, so ordinary network-paced streaming repeatedly incurs the extra scan.

**Evidence:** Response progress calls ChatResponseModel.onDidChange without a structural ChatModel change (ChatModel.acceptResponseProgress delegates to response.updateContent). Line 592 runs track() for that response-only signal; track() calls model.getRequests(), allocates a Set, and walks responseListeners. The generatedImages derived then calls model.getRequests().slice().reverse() and scans responses. Event.accumulate with numeric delay 0 debounces only events arriving before its setTimeout fires, so separate streaming updates still trigger this pair of scans.

**Suggested direction:** Keep the coalesced image invalidation, but mark listener tracking dirty only from model structural changes (or use a separate coalesced model event); response onDidChange should fire the image signal without calling track().


## Performance regression fixes detected (2)

### 1. repeated-work

**Fix location:** `src/vs/sessions/contrib/chat/browser/sessionArtifacts.ts:591` (`RIGHT`)

**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.98

**Mechanism:** The generated-images derived subscribed directly to every model and response mutation and rescanned the entire transcript after each replayed mutation, making restore work grow with both mutation count and transcript size.

**Symptom:** Opening a large restored Agent Host chat could spend substantial renderer CPU repeatedly rescanning generated images and freeze the UI.

**Fixed behavior:** Event.accumulate coalesces synchronous restore mutation bursts before invalidating generatedImages, reducing many per-item transcript scans to one delayed scan per burst.

**Evidence:** The old base line subscribed generated-image computation directly to response.onDidChange. The changed code routes model/response events through Event.accumulate, and the added test fires 50 model plus 50 response events, proves zero synchronous scans, and bounds the delayed scans to at most two.

### Scenario 2: Apply live remote-history refreshes, server-initiated requests, and sends/resends

- Critical path: A pending history refresh is serialized through \_activeRefresh; sends, resends, queued requests, and server requests wait for the current refresh before mutating the model. Diff computation is synchronous, while changed model mutations yield in slices.

- Verdict: No reportable diff-caused regression. The changed path adds cooperative mutation scheduling and explicit coalescing/ordering; inherited synchronous diff scans were not materially amplified for ordinary published refreshes.

### Scenario 3: Stream a live response while the session artifacts presentation tracks generated images

- Critical path: Each response-content event is debounced to a zero-delay task; the callback updates response listeners and invalidates generatedImages, whose transcript scan must finish before artifact sections update. This is renderer-local CPU work with no external boundary.
- Scaling input: N requests/responses in the open transcript times U response-update bursts that remain after zero-delay coalescing.
- Effective concurrency: Events in one synchronous burst coalesce, but network-paced updates in separate tasks each trigger one callback. Work is serialized on the renderer event loop.
- Cache behavior: Response listeners are retained only for current responses and disposed on structural changes. There is no cache for the transcript scan; every coalesced signal rebuilds generated-image results.
- Mechanism confidence: High: response progress fires response.onDidChange without a model structural event, Event.accumulate uses setTimeout(0), and the added track() plus existing generatedImages loops are explicit.
- Magnitude uncertainty: Exact streaming cadence and transcript sizes vary, but the extra O(N) Set/listener pass per non-coalesced update is certain; this uncertainty is reflected in medium severity.
- Expensive boundaries: none found
- Verdict: Reportable medium repeated-work regression: response-only updates now perform an unnecessary full listener-maintenance scan before the existing full image scan.

### Scenario 4: Refresh/render a large chat list and compute row identities

- Effective concurrency: Synchronous renderer work in one list refresh; no parallelism or external queue.
- Cache behavior: Identity uses response id and model change count; no external cache. Tail state is computed once by the widget from its item array.
- Mechanism confidence: High from ChatResponseViewModel.dataId/isLast and ChatListWidget identity code.
- Magnitude uncertainty: Exact tree refresh frequency varies, but elimination of nested transcript traversal is directly proven by the test.
- Expensive boundaries: none found
- Verdict: This PR fixes a concrete repeated-work regression; it does not introduce a new one in this scenario.
