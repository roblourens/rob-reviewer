## Findings (1)

### 1. [low] Defer the pinned Unicode regexes until Snippy is used

**Finding ID:** `PERF-DFDE763BEC11`  
**Location:** <code>extensions/copilot/src/platform/snippy/common/snippyCompute.ts:6</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** bundle bytes, CPU work to parse/compile five Unicode regexes, and four intermediate RegExp objects  
**Scaling:** The cost is fixed but unconditional once per node or web extension-host bundle load, so it affects all activations rather than scaling only with Snippy usage.  
**Outcome:** increased startup latency from synchronous regex parsing and compilation on the extension activation path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The module created one compact property-escape tokenizer RegExp; no external Unicode category regex modules or intermediate category RegExp objects were loaded and compiled.  
**Changed behavior:** Extension bundle initialization now evaluates four Unicode-category regex modules and synchronously parses a fifth combined Unicode regex before any Snippy request is made.  
**Confidence:** 0.94 — The static import chain from both extension entry points through common service registration to \`snippyServiceImpl\` and \`snippyCompute\` is explicit, and the added imports plus \`new RegExp\` prove eager regex construction. The exact millisecond cost depends on runtime and bundled pattern size, so severity is low rather than uncertain causality.

**Causal diff evidence:** RIGHT lines 6-9 add four static \`.../regex.mjs\` imports and RIGHT line 12 reads each imported RegExp's source to compile another combined RegExp. \`snippyServiceImpl\` is statically imported by the common services module, which is imported by both node and web extension entry points, so these module initializers run when the extension bundle loads.

Every Copilot extension activation, including sessions that never accept an inline completion or next edit, pays additional extension-host startup CPU and retains the intermediate RegExp objects; on slower desktop and web extension hosts this lengthens activation/module initialization.

**Evidence:** \`extensions/copilot/.esbuild.mts\` bundles dependencies and does not externalize \`&#64;unicode/unicode-15.0.0\`; both node and web service modules statically import the common \`vscode/services.ts\`, which statically imports \`SnippyService\`, which statically imports this module. Each \`regex.mjs\` supplies a category RegExp (its \`.source\` is consumed), then line 12 constructs the actual tokenizer RegExp. This performs four unnecessary intermediate regex compilations plus the final compilation during bundle evaluation.

**Suggested direction:** Generate/store the pinned Unicode-15 category sources as one combined pattern and lazily compile a single tokenizer on first Snippy use (or otherwise keep the generated tokenizer module off the activation import path).
