## Findings (1)

### 1. [medium] Reuse the prepared placeholder instead of re-encoding the frame

**Finding ID:** `PERF-638B967465FD`  
**Location:** <code>src/vs/workbench/contrib/canvases/electron-browser/canvasView.ts:234</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** CPU work and image-sized JavaScript string allocations  
**Scaling:** Each visible canvas input switch performs work linear in the compressed screenshot byte length; repeatedly selecting pinned canvases repeats the full encoding and allocates a new base64/data-URL string each time.  
**Outcome:** Increased click-to-display latency, UI-thread stalls, and GC pressure when switching high-resolution canvases  
**PR causality:** <code>introduced</code>  
**Previous behavior:** CanvasEditor switched inputs by detaching the existing model directly; it did not synchronously serialize the model screenshot during setInput. WebContentsViewHost already encoded captured screenshots for its placeholder on the asynchronous capture path.  
**Changed behavior:** CanvasView.setInput now calls holdFrame synchronously, and holdFrame passes the full viewport screenshot through encodeBase64 before the selected canvas can change.  
**Confidence:** 0.99 — The changed synchronous call path, O(screenshot bytes) implementation, full-viewport source, and pre-existing encoded placeholder are directly established in repository code. Exact milliseconds depend on viewport/image complexity, which is reflected in medium severity rather than uncertainty about the mechanism.

**Causal diff evidence:** RIGHT line 234 newly invokes encodeBase64(screenshot) inside holdFrame; holdFrame is newly called synchronously from CanvasView.setInput on every visible input change.

Clicking another pinned canvas, or switching a visible canvas editor input, blocks the renderer while encodeBase64 loops over the quality-80 full-viewport JPEG and builds a roughly 4/3-sized string. Large/high-DPI canvas frames or rapid sidebar switching can therefore produce noticeable input jank and allocation/GC spikes.

**Evidence:** PinnedCanvasPage's selected-entry autorun calls view.setInput directly (pinnedCanvasPage.ts:89), which calls holdFrame before updating the input (canvasView.ts:207-214). The added line serializes model.screenshot synchronously. BrowserViewModel.captureScreenshot stores a full-page capture in model.screenshot (browserView.ts:913-919), and encodeBase64 is a synchronous byte-by-byte loop with repeated string appends (buffer.ts:431-459). WebContentsViewHost already turns that same screenshot into its placeholder background (webContentsViewHost.ts:241-244), so this is duplicate serialization on the interaction path rather than unavoidable capture work.

**Suggested direction:** Before detaching the host, reuse or transfer the already-prepared background image from host.screenshotElement (or retain an object URL/pre-encoded representation) for the held frame. Keep encoding/capture off the synchronous setInput path.
