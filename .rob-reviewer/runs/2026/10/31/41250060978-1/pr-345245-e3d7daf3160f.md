# Performance review: Fix Remove Keybinding for the chat steer and queue Enter bindings

## Findings (1)

### 1. [high] Bound OR distribution before materializing extension conditions

**Finding ID:** `PERF-18EBD56F54C1`  
**Location:** <code>src/vs/platform/contextkey/common/contextkey.ts:1718</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU work and allocated ContextKeyOrExpr/ContextKeyAndExpr branch objects  
**Scaling:** For N independent two-way OR groups followed by an \`in\` or comparison term, normalization now materializes 2^N conjunction branches; each installed extension contribution or user keybinding supplies another independently parsed expression.  
**Outcome:** Main-thread startup can stall and the renderer can exhaust memory while registering extension menus or keybindings.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Because comparison and \`in\` nodes sort after OR nodes, the old loop inspected the final comparison, stopped distribution, and retained this expression in O(N) AST nodes.  
**Changed behavior:** \`findLastIndex\` now selects an OR even when a comparison or \`in\` term follows it. After distributing that OR over the trailing term, subsequent iterations recursively combine the remaining ORs and form their Cartesian product.  
**Confidence:** 0.97 — The exponential branch construction follows directly from the recursive distribution code and parser grammar, and the synchronous extension-menu/keybinding call paths plus absent complexity limit are explicit. Only the prevalence of large real-world conditions is uncertain, which affects severity rather than the mechanism.

**Causal diff evidence:** The added \`expr.findLastIndex(e =&gt; e.type === ContextKeyExprType.Or)\` at RIGHT line 1718 bypasses the previous guard on the final element, newly entering distribution for expressions whose final sorted term is an \`in\` or numeric comparison.

An installed extension with a condition such as \`(a0 \|\| b0) && ... && (a19 \|\| b19) && count &gt; 0\` now causes over one million conjunction branches to be created synchronously during contribution registration, blocking workbench startup and risking OOM; the same shape is accepted in user keybindings.

**Evidence:** The parser accepts parenthesized expressions and normalizes every AND through this loop. \`menusExtensionPoint.setHandler\` synchronously calls \`ContextKeyExpr.deserialize(menuItem.when)\` for every installed extension menu, while validation checks only that \`when\` is a string and imposes no size or complexity bound; keybinding contribution registration does the same before updating the resolver. The recursive \`ContextKeyAndExpr.create\` at lines 1732-1734 distributes each selected OR against the next term, and \`ContextKeyOrExpr.create\` flattens the resulting branches, so N binary ORs produce 2^N retained branches.

**Suggested direction:** Avoid converting unrestricted conditions to full DNF: preserve grouping with a parenthesis-aware AST and serializer, or compute and enforce a small branch budget before distribution and reject/report over-budget extension or user expressions without first materializing them.
