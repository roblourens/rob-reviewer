# Performance review: workbench: auto-hide sash grippers when the mouse is idle

[PR #343441](https://github.com/microsoft/vscode/pull/343441) at `eab2e76f2cf41d084ecbe63216f270fda26a143c`

## Findings (2)

### 1. [medium] Gate the webview mouse bridge before sending frame-rate messages

**Finding ID:** `PERF-3BBD8C8C71A5`  
**Location:** <code>src/vs/workbench/contrib/webview/browser/pre/index.html:767</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** cross-frame MessagePort posts, structured-cloned payload objects, host message dispatch, and CustomEvent objects  
**Scaling:** Continuous movement over one webview produces one boundary message per animation frame (typically 60-120 per second) for the duration of movement, regardless of whether auto-hide is disabled or the owning workbench renders these grippers.  
**Outcome:** avoidable cross-context message traffic and main-thread CPU/GC pressure during webview interaction  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, webview mouse movement did not send a did-mouse-move message through the webview MessageChannel and did not allocate and dispatch a host-window CustomEvent.  
**Changed behavior:** The preload now always captures mousemove and posts did-mouse-move once per animation frame. WebviewElement always consumes each post and dispatches a CustomEvent, while SashGrippersController has no activity listener when workbench.sash.autoHideGrippers is false; the CSS consumers are additionally limited to modern-ui and agent-sessions-workbench roots.  
**Confidence:** 0.99 — The complete message path from capture listener through rAF, MessagePort, WebviewElement handler, and CustomEvent is explicit. The absence of a consumer when auto-hide is disabled and the limited CSS consumers are also directly established; only the exact platform-dependent cost per message is uncertain.

**Causal diff evidence:** Added line 767 introduces the frame-coalesced MessagePort post for mouse movement; added listeners at lines 957 and 1233 make this path unconditional for shell and content movement.

Moving the pointer over common webviews such as Markdown preview generates frame-rate MessagePort and host event work even after the user disables auto-hide, and also in workbench states with no applicable gripper styling. This wastes renderer/main-thread capacity and battery on an interaction path where the messages cannot affect UI.

**Evidence:** The added rAF callback posts did-mouse-move at lines 760-770 through HostMessaging's MessageChannel/MessagePort implementation (lines 307 and 329). WebviewElement handles every message and constructs/dispatches a CustomEvent at lines 248-250. By contrast, SashGrippersController returns before installing its webview activity listener when the setting is false (sash.ts lines 96-98). Repository search shows --sash-grip-opacity is consumed only by modernUI sashHandles.css and sessions workbench.css, so other roots also cannot use the traffic.

**Suggested direction:** Make activity forwarding subscription-based: have the host enable it only while the owning container has applicable gripper UI and auto-hide enabled, and disable it immediately with the setting/UI state. When enabled, send an immediate reveal plus bounded heartbeat/trailing activity sufficient to maintain the idle deadline instead of one boundary post every animation frame.

### 2. [medium] Keep one idle deadline instead of rebuilding the timer per mouse sample

**Finding ID:** `PERF-2018DC82DB36`  
**Location:** <code>src/vs/workbench/contrib/sash/browser/sash.ts:104</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** browser timeout registrations/cancellations and per-event position objects on the window mousemove path  
**Scaling:** The work runs once for every distinct mousemove sample in each active window; high-polling mice can produce hundreds to roughly a thousand samples per second during ordinary pointer movement.  
**Outcome:** continuous CPU and GC pressure on a latency-sensitive input path, with avoidable timer-queue churn while the pointer is moving  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no global sash-gripper mousemove tracker, no idle timeout to recreate, and no per-sample position object allocation.  
**Changed behavior:** The new capture listener sends every changed pointer position to showGrippers; showGrippers clears the current timeout, removes the class, and creates a fresh timeout for every sample, even though after the first sample the grippers are already visible and only the eventual idle deadline changes.  
**Confidence:** 0.98 — The listener-to-timer call path and default-enabled registration are explicit in the diff, and browser pointer events commonly arrive many times per frame. Exact CPU cost varies by platform, which affects severity, but the repeated timer/allocation mechanism and its hot-path reachability are certain.

**Causal diff evidence:** Added lines 103-110 introduce unconditional clearTimeout and setTimeout calls inside showGrippers, and added lines 116-123 invoke that function from every distinct global mousemove sample.

With the default-enabled setting, normal pointer movement anywhere in the workbench repeatedly cancels and allocates timers at hardware event frequency. This can consume main-thread time and generate garbage during input even though visible state changes only on the first movement and after the user becomes idle.

**Evidence:** registerContainer installs a window-level capture mousemove listener at line 123. Each changed coordinate allocates lastMousePosition and calls showGrippers (lines 116-121), which unconditionally clearTimeout/classList.remove/setTimeout (lines 103-110). ILayoutService documents one container per window, so this is one hot listener per workbench window rather than per sash; the realistic multiplicity is pointer sample rate. The CSS state itself changes only when entering/leaving idle, making the intervening timeout rebuilds redundant.

**Suggested direction:** Record the latest activity timestamp, reveal only on the visible-state transition, and keep a single timeout whose callback either hides or reschedules for the remaining deadline. This preserves hiding autoHideDelay after the final movement without canceling/recreating a timer or allocating a position object for every sample.

### Scenario 1: Ordinary pointer movement in a workbench or auxiliary window while sash gripper auto-hide is enabled

- Critical path: The capture-phase window mousemove handler runs synchronously during each pointer event; it deduplicates identical coordinates, then clears and recreates the idle timer before event dispatch completes. The eventual hide callback is asynchronous.
- Scaling input: Distinct pointer samples while moving. Effective cardinality is one handler invocation and one timeout cancellation/registration per changed coordinate per active workbench window, commonly hundreds of samples per second and potentially around 1000 Hz with high-polling devices.
- Effective concurrency: Events are processed serially on each window's main thread. Each window owns an independent tracker; repeated events replace one pending timeout rather than accumulating concurrent callbacks, but replacement work is unbounded by a throttle.
- Cache behavior: There is no cache. Exact duplicate screen coordinates are suppressed, but every real coordinate change repeats the full timer operation; cold and sustained movement behave the same after the first reveal.
- Mechanism confidence: High: the new global listener directly invokes unconditional clearTimeout/setTimeout and allocates a new position object for every distinct sample.
- Magnitude uncertainty: Timer and allocation cost varies by browser, pointer hardware, and movement duration; the global hot-path multiplicity is established, so uncertainty affects severity rather than mechanism confidence.
- Expensive boundaries: none found
- Verdict: Reportable repeated-work regression because the PR adds timer-queue and allocation churn at raw input frequency although visible state changes only at idle/activity transitions.

- Effective concurrency: Windows track independently with one timeout each. Configuration updates are serialized by the configuration event; no task burst or shared limiter is needed at realistic window counts.

- Mechanism confidence: High: layout service defines one container per window, and disposal ownership is explicit through container disposables plus onDidUnregisterWindow.

- Mechanism confidence: High: CSS consumers are limited to Modern UI and Agents-window selectors, and opacity is the only transitioned property.
- Magnitude uncertainty: The number of top-level sashes varies by layout but is small; browser style/compositor behavior varies by platform.
- Expensive boundaries: none found
- Verdict: No separate finding: one root class transition per idle/activity state change is bounded and aligned with the requested visual behavior; the reportable overhead is the repeated event/timer and webview messaging work between transitions.
