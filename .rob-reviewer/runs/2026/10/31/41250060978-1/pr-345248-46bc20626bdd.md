**Relevant issue families:** eager-work, boundary-fanout, repeated-work, missing-coalescing, cleanup-lifecycle

### Scenario 1: Workbench startup registers the readonly file-on-disk filesystem provider

- Critical path: The new BlockStartup contribution constructs one provider and registers it with IFileService before startup can proceed; construction performs only emitter/object allocation and provider-map registration.
- Scaling input: Constant: one provider registration per workbench window, independent of files, editors, or workspace size.
- Effective concurrency: Synchronous single registration; no queue, subprocess, IPC, filesystem, database, or network operation is started.
- Cache behavior: No content cache is created or warmed. Registration only makes the scheme available; file content and watchers remain lazy until a comparison opens.
- Mechanism confidence: High confidence from the changed constructor and registration call.
- Magnitude uncertainty: Exact contribution-framework overhead is not measured, but the changed constructor has no scaling work or expensive boundary.
- Expensive boundaries: none found
- Verdict: No reportable regression: the diff adds constant, lightweight startup work and defers all file reads and watches until use.

### Scenario 2: A stored notebook save detects FILE\_MODIFIED\_SINCE and offers Compare

- Critical path: The failed save's existing filesystem write completes with a conflict first. The diff then synchronously checks provider availability, finds the current working-copy editor, and scans registered diff-capable editor descriptors before constructing the notification action.
- Scaling input: One check per save-conflict notification; the scan scales with registered editor descriptors, a bounded application registry rather than notebook cells or workspace files.
- Effective concurrency: Synchronous registry lookup and array scan. The existing save attempt remains serialized by the working-copy save sequencer; the diff adds no filesystem/IPC call until the user invokes Compare.
- Cache behavior: Provider/editor registrations are already in memory. There is no cold-vs-warm boundary difference for merely offering the action.
- Mechanism confidence: High confidence from getCompareEditorId and EditorResolverService.getEditors implementation.
- Magnitude uncertainty: The number of third-party editor registrations varies, but the conflict path is infrequent and the scan does not cross a process or I/O boundary.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts save error path</code>: The pre-existing save/write that returns FILE\_MODIFIED\_SINCE; cardinality: One serialized write attempt per explicit or automatic save
    - Introduced by diff: false; previous behavior: The same save write occurred and the error notification offered only Overwrite and Revert.; critical-path effect: It must fail before the Compare action is offered, but this boundary existed before the PR.
- Verdict: No reportable regression: added work on the save-error path is bounded in-memory registry work.

### Scenario 3: The user invokes Compare for a notebook save conflict

- Critical path: Compare reloads any already-open readonly working copy, then waits for editorService.openEditor. A warm virtual working copy reload performs virtual stat/read operations that delegate to the original filesystem; a cold comparison resolves the original while opening the editor. Notebook deserialization and initial diff computation must complete to render useful content.
- Scaling input: Effective cardinality is one virtual resource per compared notebook and normally one working copy for its notebook type; getAll can include one entry per distinct working-copy type for that exact URI. File bytes and notebook cells control read, deserialize, and diff cost.
- Effective concurrency: Existing virtual working copies are reloaded sequentially by the changed loop. StoredFileWorkingCopyManager serializes resolves per resource. Different concurrently opened conflict comparisons can proceed independently, but user action normally creates one/few.
- Cache behavior: Cold: no virtual working copy exists, so openEditor creates and reads it once. Warm: the loop forces one ETag-aware reload so an existing comparison is current, and editor opening reuses that model. There is no retained byte cache in the provider; unchanged reloads can terminate through ETag validation.
- Mechanism confidence: High confidence from the compare loop, provider delegation, working-copy map keyed by exact URI/type, and per-resource resolve serialization.
- Magnitude uncertainty: Notebook files can be large and provider implementations can be remote, but this cost is explicitly user-requested, has exact-resource cardinality, and is not multiplied by workspace size.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/services/workingCopy/common/fileOnDiskFileSystemProvider.ts:38-47</code>: Stat and read the underlying on-disk resource through FileOnDiskFileSystemProvider; cardinality: One delegated read sequence per cold resolve or warm forced reload for each exact-resource working-copy type
    - Introduced by diff: true; previous behavior: There was no Compare action and therefore no readonly-resource stat/read path.; critical-path effect: The selected Compare action awaits warm reloads and then editor opening, so these operations are on its display critical path.
  - IPC at <code>src/vs/workbench/services/workingCopy/common/storedFileWorkingCopy.ts:1274-1279</code>: Open the requested diff editor and, for notebook editors, resolve serializer/model services that may cross extension-host or worker boundaries; cardinality: One openEditor request per Compare click; notebook serialization/diff work is one logical operation for the notebook, not per cell boundary calls
    - Introduced by diff: true; previous behavior: The save-conflict notification did not open a comparison.; critical-path effect: The editor must open and compute its initial model/diff before the comparison is usable.
- Verdict: No reportable regression: the I/O and diff work are necessary for the requested comparison and remain bounded to the selected resource; no realistic large fan-out is introduced.

### Scenario 4: An open conflict comparison tracks subsequent on-disk notebook changes

- Critical path: A provider watch forwards a real-resource change to the virtual URI. The clean virtual working copy is reloaded and deserialized; its merged notebook content event now invokes updateLayout even while the diff editor is active, causing one notebook worker diff and, when changed, view-model/list reconstruction.
- Scaling input: Cost scales with changed-file event frequency, notebook byte size, and cell count. Notebook reset batches raw edits into one onDidChangeContent event. The working-copy reload queue is capped at one running plus one queued resolve per resource.
- Effective concurrency: One correlated underlying watcher per actively watched virtual resource after FileService deduplication of identical outer watches. Reloads are serialized and coalesced to queue size two per resource. updateLayout cancels stale consumers; the worker request itself may finish, but one batched content event is emitted per completed reload.
- Cache behavior: The watcher is created only while the virtual resource is watched and disposed with that watch. Reloads send the prior ETag, so unchanged events avoid deserialization and diff events. There is no negative cache; missing/deleted state follows existing working-copy handling.
- Mechanism confidence: High confidence from provider watch delegation, FileService watcher deduplication, working-copy queue bounds, NotebookTextModel pauseable event batching, and the changed original-side listener.
- Magnitude uncertainty: Large notebooks or slow remote files make each update expensive, and exact external-write frequency is workload-dependent. However, reset events are batched, unchanged reads are ETag-checked, and per-resource reload accumulation is explicitly bounded.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/services/workingCopy/common/fileOnDiskFileSystemProvider.ts:50-68</code>: Create and maintain a correlated watcher for the underlying file (remote providers can route this through the filesystem channel); cardinality: One underlying watch per distinct active virtual file; identical outer watches are reference-counted by FileService
    - Introduced by diff: true; previous behavior: No file-on-disk virtual resource or watcher existed.; critical-path effect: Watcher setup is part of model lifetime, while individual notifications initiate the update path.
  - filesystem at <code>src/vs/workbench/services/workingCopy/common/storedFileWorkingCopyManager.ts:266-307 and fileOnDiskFileSystemProvider.ts:38-47</code>: Reload and deserialize the changed readonly notebook resource; cardinality: At most one running and one queued reload per exact resource; ETag suppresses unchanged content
    - Introduced by diff: true; previous behavior: The conflict comparison did not exist; for other notebook diffs, existing working-copy reload behavior supplied model changes.; critical-path effect: The new file contents must load before the diff can reflect the external change.
  - IPC at <code>src/vs/workbench/contrib/notebook/browser/diff/notebookDiffViewModel.ts:135-151</code>: Compute the notebook diff in the notebook editor worker; cardinality: One worker request per merged original-notebook content event; not per cell
    - Introduced by diff: true; previous behavior: While the diff editor was active, original-side changes were suppressed by the combined listener's active-editor guard.; critical-path effect: The active diff cannot update until the worker result returns; UI reconstruction follows only when the diff changed.
- Verdict: No reportable regression: the newly performed diff is required to keep an active comparison current, and realistic event multiplicity is batched/coalesced rather than per-cell or unbounded.

Traced startup registration, conflict-action eligibility, comparison open/reload, watcher lifecycle, delegated filesystem/IPC boundaries, notebook event batching, per-resource resolve coalescing, worker diff computation, and disposal.
