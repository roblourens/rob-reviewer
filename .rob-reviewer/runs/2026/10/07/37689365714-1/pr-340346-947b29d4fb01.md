# Performance review: chat: Move MCP and plugin discovery to Customizations

[PR #340346](https://github.com/microsoft/vscode/pull/340346) at `947b29d4fb01aa50067dc3e9060486214d82c5f6`

## Findings (1)

### 1. [medium] Scope “Show Plugins” to the selected marketplace

**Finding ID:** `PERF-0BAE4AD0BFA0`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/actions/chatPluginActions.ts:311</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Parallel network requests and filesystem reads for configured plugin marketplace repositories  
**Scaling:** Each click fans out to every enabled configured plugin marketplace, so cold work and aggregate concurrency grow linearly with the number of configured marketplaces rather than remaining one request/read for the marketplace the user selected.  
**Outcome:** Increased marketplace-open latency and an avoidable burst of network/filesystem work; one slow unrelated marketplace can hold up the combined first page.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff the per-marketplace management quick pick had no “Show Plugins” operation and initiated no catalog fetch. The new operation is entered after selecting one concrete \`ref\`, so the necessary new work can be bounded to that one source.  
**Changed behavior:** The new branch invokes \`OpenMarketplace\` with only the generic Plugins section and drops \`ref.canonicalId\`. Discovery therefore leaves \`selectedSourceId\` undefined and queries all enabled sources.  
**Confidence:** 0.98 — The changed line, selected-ref control flow, undefined-source discovery request, all-source expansion, Promise.all fan-out, and per-source marketplace fetch are all directly traced. Only the exact number of configured sources and cold-cache latency vary by user.

**Causal diff evidence:** The added \`executeCommand\` call at line 311 introduces the browse operation but omits the marketplace identifier that is available as \`ref.canonicalId\`, causing all-source discovery instead of a singleton-source query.

With several configured GitHub or cloned-repository marketplaces, choosing “Show Plugins” for one marketplace loads every marketplace concurrently and the discovery service awaits all providers before returning the page. Cold GitHub sources perform network reads and cloned sources perform repository filesystem reads, including unrelated or slow sources.

**Evidence:** The containing flow has already selected a concrete \`ref\`, but line 311 passes only \`AICustomizationManagementSection.Plugins\`. \`AICustomizationDiscoveryPage.loadCatalog\` consequently sends \`sourceIds: undefined\`; \`queryEnabledCustomizationMarketplaceSources\` expands that to every enabled source; \`CustomizationMarketplaceService.query\` invokes every selected provider with \`Promise.all\`. Each \`PluginCustomizationMarketplaceProvider\` then calls \`queryMarketplacePlugins\` for its own canonical marketplace, and the underlying fetch performs GitHub network or cloned-repository filesystem work. The discovery tests also establish that selecting a source changes requests from \`sourceIds: undefined\` to a singleton source ID.

**Suggested direction:** Pass the selected marketplace source through the command target (using its existing customization marketplace source ID) and initialize Discover with that source selected, so the first query has a singleton \`sourceIds\` value; retain the source picker so users can broaden the search explicitly.
