# Performance review: Copilot NES: add ExP toggle to omit max\_tokens

[PR #340327](https://github.com/microsoft/vscode/pull/340327) at `a2c0567c32dbd2cd63fa713e369f6ae9484820c8`

## Findings (1)

### 1. [medium] Keep a bounded output budget for non-prediction NES requests

**Finding ID:** `PERF-501B8F4A48FE`  
**Location:** <code>extensions/copilot/src/extension/xtab/node/xtabProvider.ts:902</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** model generation, streamed network bytes, response strings, and per-chunk objects  
**Scaling:** For every active or speculative NES request in the false treatment, server generation and client streaming now scale to the deployment's server-side default output budget rather than the endpoint's 4,096-token cap; reasoning deployments can have substantially larger defaults.  
**Outcome:** increased time to first/complete edit, network usage, CPU/GC pressure, and background work from superseded or speculative requests  
**PR causality:** <code>introduced</code>  
**Previous behavior:** When prediction was disabled, ChatMLFetcher always prepended max\_tokens: endpoint.maxOutputTokens; both XtabEndpoint and proxyXtabEndpoint declare that limit as 4096, so each NES model call was bounded to 4,096 generated tokens.  
**Changed behavior:** When both experiment toggles are false, the added assignment overrides ChatMLFetcher's default with undefined, and JSON serialization removes the output limit entirely from the network request.  
**Confidence:** 0.94 — The changed request serialization, prior 4,096-token bound, one-network-call-per-NES-request path, stream retention, and active/speculative consumption are directly traced in the repository. Exact server defaults and how often models stop naturally are deployment-dependent, which limits severity rather than confidence in the mechanism.

**Causal diff evidence:** RIGHT line 902 assigns undefined specifically to override and remove the existing endpoint.maxOutputTokens value; without this added assignment ChatMLFetcher serializes the 4096 cap.

A user assigned to this treatment on a reasoning-model deployment can pay the deployment's full default reasoning/output budget on each next-edit request. Active requests wait on streamed model output to form edits, while the caller also continues consuming remaining edits in the background; speculative requests do the same off the critical path, so a large default can make suggestions slower and retain/process much more response data during normal typing.

**Evidence:** The changed line sets requestOptions.max\_tokens to undefined. ChatMLFetcher.fetchMany merges { max\_tokens: chatEndpoint.maxOutputTokens, ...requestOptions }, so this explicitly defeats its cap. Both Xtab endpoint implementations set max\_output\_tokens to 4096. createCapiRequestBody copies the undefined property and JSON serialization omits it. The fetcher stores every streamed delta in FetchStreamRecorder and XtabProvider accumulates responseSoFar/feeds each chunk through its parsers; NextEditProvider continues draining the stream in an unawaited background loop after the first edit and also issues speculative provider calls. Thus larger server defaults translate directly into more generation, bytes, allocations, and potentially first-edit latency.

**Suggested direction:** Preserve endpoint.maxOutputTokens and make the endpoint select a deployment-compatible bounded field (for example max\_completion\_tokens for reasoning Chat Completions models) instead of omitting the budget. If parameter selection cannot be known here, add an endpoint capability/config for the accepted token-limit field and keep the 4,096 value.
