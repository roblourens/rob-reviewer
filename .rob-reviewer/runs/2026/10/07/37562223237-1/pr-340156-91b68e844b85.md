### Scenario 1: Resize the Sessions window or grid with multiple inactive chat panes whose picker controls are hidden

- Critical path: ResizeObserver delivery and picker/toolbar fitting run before the resized UI settles. The diff gates inactive controls before geometry reads, so hidden panes no longer add fitting work to this path.
- Scaling input: Visible ChatView count and resize-event frequency; each view owns up to two responsive toolbars and two picker layouts. Measurement-clone work occurs on cold/invalidated picker measurements, while geometry fitting otherwise uses cached thresholds.
- Effective concurrency: Browser observers deliver on the single UI thread. Each picker already coalesces scheduled work to one animation-frame callback, and disabling clears pending callbacks; no parallel subprocess, IPC, filesystem, database, or network work is reached.
- Cache behavior: Warm picker thresholds remain retained while suspended. Content/style invalidation clears the measurement cache but does not schedule hidden work; the next resume performs one cold measurement. Toolbar minimum-width dirtiness is similarly retained until resume.
- Mechanism confidence: High: the CSS hides inactive controls while the changed active-state bridge disables both toolbar and picker layout, and both layout implementations now check the gate before geometry work.
- Magnitude uncertainty: Exact pane counts and per-layout duration vary with picker content and cache state, but the removed hidden-work mechanism and UI-thread reachability are direct.
- Expensive boundaries:
  - other at <code>src/vs/workbench/contrib/chat/browser/widget/input/chatInputPickerResponsiveLayout.ts:125-239 and src/vs/base/browser/ui/toolbar/toolbar.ts:298-383</code>: DOM geometry reads, responsive action fitting, and on cold measurements cloned DOM insertion/removal plus bounds reads; cardinality: Before the diff, up to two picker layouts and two responsive toolbar relayouts per ChatView could react to resize/content changes; after the diff, inactive non-comparison views perform zero such hidden measurements until one resume.
    - Introduced by diff: false; previous behavior: Hidden controls remained observed and responsive layout continued to read geometry and fit actions on resize or invalidation.; critical-path effect: These synchronous DOM operations consume resize-frame time; the new gates remove them for hidden controls rather than adding a boundary.
- Verdict: Performance improvement; no diff-introduced regression.

### Scenario 2: Activate an inactive session or reveal all inputs when entering/completing a comparison grid

- Critical path: The newly visible controls must refit before interaction/paint. Toolbars resume first, then picker layouts synchronously fit; non-active comparison resumes are deferred to cancellable microtasks so grid CSS is applied first.
- Scaling input: One session for normal activation, or all visible comparison panes when comparison policy reveals inactive inputs; each resumed view has at most two toolbars and two picker layouts.
- Effective concurrency: Resume work is serialized on the UI thread. Comparison-driven enables use one cancellable microtask per affected ChatView; repeated state changes cancel stale microtasks through the autorun reader store.
- Cache behavior: A width-only resume reuses warm picker thresholds. Hidden content/theme/config changes invalidate thresholds and cause one cold clone-based measurement on resume; toolbar action changes leave one dirty minimum-width recomputation.
- Mechanism confidence: High: the call order, synchronous enable behavior, cache checks, and cancellable microtask are explicit in the changed code.
- Magnitude uncertainty: The exact one-time resume latency depends on DOM size and whether caches were invalidated, but it replaces repeated hidden work and is bounded by visible panes.
- Expensive boundaries:
  - other at <code>src/vs/workbench/contrib/chat/browser/widget/input/chatInputPart.ts:2373-2382 and src/vs/workbench/contrib/chat/browser/widget/input/chatInputPickerResponsiveLayout.ts:137-239</code>: Synchronous toolbar width fitting, picker geometry reads, and potentially cold intrinsic-size clone measurement; cardinality: Up to four component resumes per newly shown ChatView, with clone measurement only for invalidated picker lanes; comparison reveal scales with the effective visible-pane count.
    - Introduced by diff: true; previous behavior: Picker and toolbar layouts stayed enabled continuously, including while controls were hidden, so no explicit resume pass existed.; critical-path effect: The one-time resume is on the reveal critical path so controls are fit before paint. Before the diff, this work was not a resume cost because layouts remained active and repeatedly paid while hidden; the change bounds it to visibility transitions.
- Verdict: Intentional bounded scheduling tradeoff with coalescing/cancellation; no actionable regression.

### Scenario 3: Change picker actions, labels, themes, or configuration while controls are hidden, then reveal them

- Critical path: Action DOM updates still occur when their authoritative menus change, but responsive geometry and fitting are deferred off the hidden critical path and consolidated into the first resume.
- Scaling input: Number of hidden picker lanes and action/content changes during the hidden lifetime; effective fitting cardinality is one per lane at resume rather than one per change.
- Effective concurrency: Mutation and resize notifications remain browser-driven on the UI thread. The disabled state prevents frame scheduling, and a single synchronous resume consumes the accumulated dirty state.
- Cache behavior: Content/style changes invalidate picker measurements; repeated invalidations collapse into the same empty-cache state. Toolbar action replacement sets one dirty flag. Width-only changes preserve picker thresholds.
- Mechanism confidence: High: disabled scheduling, retained dirty flags, invalidation semantics, and synchronous resume are explicit.
- Magnitude uncertainty: Menu churn frequency varies, but dirty-state coalescing and the lack of hidden geometry work are directly established.
- Expensive boundaries:
  - other at <code>src/vs/base/browser/ui/toolbar/toolbar.ts:325-383 and src/vs/workbench/contrib/chat/browser/widget/input/chatInputPickerResponsiveLayout.ts:146-239</code>: DOM action rendering followed by deferred intrinsic-size and geometry measurement on resume; cardinality: Potentially many hidden mutations, but at most one responsive recomputation per toolbar/picker lane when re-enabled.
    - Introduced by diff: false; previous behavior: Each hidden invalidation could schedule layout on the next animation frame and perform geometry work despite invisibility.; critical-path effect: Measurement is off the hidden-update path and paid once on reveal; no subprocess, IPC, filesystem, database, or network boundary is introduced.
- Verdict: Improves repeated-work behavior; no regression.

### Scenario 4: Update active session/comparison/configuration state across several ChatView instances

- Critical path: Each ChatView autorun scans visible sessions and comparisons to decide whether its picker layout is enabled. The scan is synchronous but runs only on active/comparison/visibility-policy changes, not resize, typing, rendering, or scrolling.
- Scaling input: Visible ChatView count multiplied by comparison and participant counts; effective product usage has a small visible-pane set, and the trigger is infrequent state change rather than a frame-level event.
- Effective concurrency: All scans are synchronous on one UI thread; resulting comparison resumes are cancellable microtasks and do not cross process boundaries.
- Cache behavior: Observable dependencies suppress runs when unrelated state is unchanged. There is no result cache, but scans are tied to low-frequency policy changes; picker measurement caches remain independent.
- Mechanism confidence: High for the added repeated scan, low for material performance impact because triggers are infrequent and visible-pane cardinality is limited.
- Magnitude uncertainty: Repository code does not impose a tiny comparison-history bound, but no realistic hot trigger or expensive boundary was found that would make these URI comparisons a reportable regression.
- Expensive boundaries: none found
- Verdict: Diff adds modest repeated CPU bookkeeping but no concrete user-visible performance regression under a realistic trigger.
