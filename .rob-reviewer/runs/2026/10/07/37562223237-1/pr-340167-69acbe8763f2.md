## Findings (1)

### 1. [medium] Bound the error body before producing diagnostics

**Finding ID:** `PERF-99A2B46B3C05`  
**Location:** <code>src/vs/platform/agentHost/node/missionControl/missionControlEnvironment.ts:406</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Network response bytes, full-body strings, parsed JSON objects, and repeated redaction-string allocations  
**Scaling:** Cost is O(error response bytes) per failed register, heartbeat, token, or signing-key request and repeats with check-in recovery retries (500 ms exponential backoff capped at 30 seconds; normal heartbeats run every 60 seconds).  
**Outcome:** Increased connection/recovery latency and agent-host CPU, memory, and GC pressure on large non-success responses  
**PR causality:** <code>introduced</code>  
**Previous behavior:** On a non-2xx response, this branch handled credential rejection and threw from the status immediately; it did not drain or parse the response body for diagnostics.  
**Changed behavior:** The new \`await response.text()\` drains the entire uncapped body before the failure can propagate, then \`JSON.parse\` materializes the entire JSON payload and \`sanitizeConnectionDiagnosticText\` performs multiple whole-string replacements even though only 1024 characters are retained.  
**Confidence:** 0.98 — The changed line, standard Fetch implementation, shared call sites, retry schedule, and late 1024-character truncation are directly traced. Exact server error sizes vary, but the uncapped O(bytes) mechanism and its placement before failure/recovery are certain.

**Causal diff evidence:** The diff replaces the prior immediate \`throw new Error(...)\` in the non-OK branch with \`const text = await response.text()\` and full parsing/redaction before throwing, newly moving uncapped response consumption onto every HTTP-failure path.

A verbose JSON error or reverse-proxy HTML response during registration, heartbeat, token refresh, or signing-key recovery now blocks that critical path until the body is downloaded and transformed (up to the request's 15-second abort budget), while creating full-size intermediate allocations. Repeated failed check-ins can repeat the cost and delay Mission Control recovery.

**Evidence:** \`MissionControlHost\` supplies the standard proxy-patched \`fetch\` with no response-size cap. \`\_doRequest\` is the shared network boundary for register/heartbeat/token/signingKeys, and \`\_checkIn\` awaits it before scheduling recovery; failures back off from 500 ms to 30 seconds. The added line reads the whole \`Response\`, subsequent lines parse all JSON fields and only then call a sanitizer whose final operation is \`.slice(0, limit)\`.

**Suggested direction:** Read only a small bounded prefix from \`response.body\`, cancel the remainder once the diagnostic cap is reached, and parse/redact only that bounded text while preserving status and validated request ID.
