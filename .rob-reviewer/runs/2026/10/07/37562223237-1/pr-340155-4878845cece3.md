### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPickerResponsiveLayout.ts:190` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/widget/input/chatInputPickerResponsiveLayout.ts:60`

**Introducing commit:** `d77fa1711fcb0501c1049795fd8fbaddfb3a57ea`  
**Mechanism family:** `repeated-work`  
**Performance category:** `layout`  
**Confidence:** 0.98

**Mechanism:** Each ResizeObserver delivery synchronously reran collection-wide picker expansion, geometry reads, deep DOM cloning, clone attachment, and layout measurement, with additional measurement passes for compact/minimal states. The work repeated throughout continuous resizing and multiplied across visible chat panes.

**Symptom:** Continuous native-window or grid-sash resizing incurred repeated synchronous DOM cloning and layout resolution per picker lane, scaling with resize notifications, picker presentations, and visible chat panes and producing resize-frame latency/jank.

**Fixed behavior:** The new layout path stores intrinsic presentation thresholds in \_measurement, computes additional steps only until each bounded presentation is measured once, and then serves subsequent resize widths with fit() plus presentation updates; parent notifications are also coalesced onto animation frames.

**Evidence:** In the base revision, the ResizeObserver callback at line 60 called layout() for every observed size change. The deleted layout path reset every picker to expanded and repeatedly called \_fitsAvailableWidth; that helper synchronously read live geometry and called \_measurePreferredLayout, which deep-cloned and attached the lane for each presentation tried. The changed tests establish the intended multiplicity by asserting that subsequent width changes add zero cloneNode calls after threshold construction.

- Scaling input: Resize notification frequency multiplied by visible chat panes and their primary/secondary picker lanes; cold threshold count scales with effective responsive picker presentations, typically a small toolbar-sized collection.
- Effective concurrency: Each primary and secondary lane serializes itself with \_isLayouting and allows at most one queued parent layout through MutableDisposable. Different lanes and panes can still run in the same frame; there is no global limiter, but warm work is bounded to one fit per delivered width and one queued callback per lane.

- Critical path: The notification clears cached thresholds and schedules one animation-frame layout. The next connected, positive-width layout must rebuild thresholds before selecting and applying a presentation; repeated notifications before that callback do not create additional scheduled work.
