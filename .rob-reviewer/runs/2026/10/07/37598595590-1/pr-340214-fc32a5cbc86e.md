### Scenario 1: Selecting HydraFusion off, v1, or v2 and forwarding the setting into a running local agent host

- Critical path: The setting or preview-policy event recomputes the HydraFusion and HydraFusionV2 root keys, dispatches only changed values to the local agent host, applies each root action, persists root config, and requests a Copilot runtime restart when the startup snapshot changes. If a turn is active, restart is explicitly deferred until chats are idle.
- Scaling input: A single setting/policy transition affects two fixed root keys. false-to-v2 or v2-to-false can change both keys; true-to-v2 changes only the v2 key after structural equality filtering.
- Effective concurrency: The two per-key forwarder pushes can begin independently, but each has a structural equality guard. On the host, busy-chat restart requests accumulate in a Set and are applied once when idle; an immediate stop clears pending reasons synchronously and makes the client unavailable before awaiting subprocess shutdown.
- Cache behavior: The live root-state values act as a warm equality cache, suppressing unchanged dispatches. On cold hydration or a newly introduced key, the missing value is forwarded once and then persisted; there is no repeated negative-cache miss.
- Mechanism confidence: High confidence in the two-key forwarding, equality filtering, persistence, and restart coalescing paths from the forwarder, host action handler, and Copilot client lifecycle code.
- Magnitude uncertainty: Filesystem and IPC duration vary by platform, but multiplicity is fixed at two keys and setting/policy changes are infrequent.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCopilotCliSettingsContribution.ts:76-91 via AgentHostRootConfigForwarder.\_push</code>: Dispatch RootConfigChanged actions from the workbench to the local agent host.; cardinality: Zero to two actions per HydraFusion setting/policy transition after equality filtering; true-to-v2 is one action, while off-to-v2 can be two.

  - filesystem at <code>src/vs/platform/agentHost/node/agentService.ts:8236 and AgentConfigurationService.persistRootConfig</code>: Serialize and persist the complete agent-host root configuration after each accepted RootConfigChanged action.; cardinality: At most two serialized writes for an off-to-v2 transition; otherwise generally one, with writes sequenced by \_rootConfigWrite.
    - Introduced by diff: true; previous behavior: A HydraFusion boolean transition caused at most one persistence request.; critical-path effect: Persistence is scheduled from config handling but is not awaited by the workbench setting path; the added maximum is one write on the rare two-key transition.
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_restartClientIfStartupConfigChanged/\_applyPendingClientRestart</code>: Stop the existing Copilot SDK client/runtime so the next session starts with the selected feature flags.; cardinality: At most one effective stop for one logical version transition; pending requests coalesce while busy, and immediate stop clears pending reasons before awaiting client.stop().

- Verdict: No reportable regression: the extra config action/write is bounded and rare, and the expensive subprocess lifecycle is deliberately deferred/coalesced rather than duplicated.

### Scenario 2: Creating or resuming a Copilot session with HydraFusion v2 selected

- Critical path: Session launch reads the two root booleans, builds the existing featureFlags object, then follows the unchanged SDK create/resume path. A cold client may require the existing runtime subprocess startup; a resident client is reused when its startup configuration matches.
- Scaling input: One constant-time pair of config reads and one optional feature-flag property per session launch/resume, independent of plugin, model, workspace, or history cardinality.
- Effective concurrency: Existing session launch sequencing and concurrent BYOK/shell/custom-agent preparation are unchanged. The added flag does not start new parallel work.
- Cache behavior: The resident client is reused while the startup snapshot is unchanged. Changing the v2 value invalidates that lifecycle once via CopilotAgentStartupConfig; feature flags are rebuilt per launch as before.
- Mechanism confidence: High confidence that host-side work added by the diff is constant-size metadata construction with unchanged boundary cardinality.
- Magnitude uncertainty: The external v2 runtime's own model-planning cost is outside the supplied diff; this code only selects it and does not establish an added host-side call or allocation mechanism.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_ensureClient and CopilotAgentStartupConfig</code>: Start or reuse the Copilot runtime process.; cardinality: At most one runtime client per existing lifecycle; no additional spawn is added for each v2 session.
    - Introduced by diff: false; previous behavior: HydraFusion v1 used the same runtime lifecycle and startup invalidation path.; critical-path effect: Cold runtime startup remains on the existing session-launch path; the new boolean only selects startup/session metadata.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:\_buildSessionConfig</code>: Create or resume the SDK session with the assembled featureFlags.; cardinality: One existing SDK create/resume operation per session launch; adding HYDRAFUSION\_PLAN\_V2 does not add another call.

- Verdict: No performance finding: the diff adds a constant-size flag to an existing launch payload and correctly scopes restart invalidation to version changes.

### Scenario 3: Accepting live HydraFusion routing events and logging the experiment trigger

- Critical path: An accepted current-turn session.fusion\_route\_started event checks assignment-context availability and, once available, calls the experiment-trigger helper before continuing through the existing fusion progress reducer. If context is absent, one boolean is retained and a later root-config event retries in a microtask.
- Scaling input: The lightweight check executes once per accepted routing event, but telemetry emission is deduplicated to one event per telemetry service/treatment for the process lifetime. Deferred state is one boolean, not a per-event collection.
- Effective concurrency: Event handling remains synchronous except for a single queued microtask on a root-config change while the trigger is pending. Multiple routes do not launch concurrent network requests because logExperimentTrigger uses a per-service Set.
- Cache behavior: Cold behavior emits one trigger after assignment context exists. Warm behavior performs a Set membership check and emits nothing. Pending assignment context is represented by a bounded boolean and is cleared after successful reporting.
- Mechanism confidence: High confidence in fixed retained state and one-time emission from the helper implementation and accepted-event call path.
- Magnitude uncertainty: Exact telemetry backend batching is not visible in the reviewed path, but the helper's process-wide one-event cap and non-awaited call are explicit.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:5529-5537 via src/vs/platform/telemetry/common/experimentTrigger.ts</code>: Enqueue one experimentTrigger telemetry event through ITelemetryService.publicLog2.; cardinality: At most one emitted event per telemetry service for config.chat.copilot.hydraFusion.enabled, regardless of route count or session count in that process.
    - Introduced by diff: true; previous behavior: No HydraFusion-version experiment trigger was emitted from this event.; critical-path effect: The local telemetry enqueue occurs on the first accepted route; subsequent routes are deduplicated and no direct awaited network operation is added to turn progress.
- Verdict: No reportable regression: the only scaling work is a small map/schema lookup per route, while expensive telemetry emission is bounded to one and no unbounded event retention is introduced.
