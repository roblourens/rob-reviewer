### Scenario 1: Linux CI Agent Host E2E split-storage run

- Critical path: One outer runner performs runtime preparation, then synchronously waits for the full tmpfs replay pass, unmounts it, and synchronously waits for the required disk-backed lifecycle pass; both passes must finish before the integration job advances.
- Scaling input: The broad suite's test count controls tmpfs filesystem work; the required disk grep has a fixed curated selection spanning six entrypoints, while runner concurrency is capped at six workers.
- Effective concurrency: Within a pass, up to min(configured jobs, 6) suites run concurrently. The tmpfs and disk passes are strictly serialized; one tmpfs mount serves all broad-pass workers.
- Cache behavior: Each pass uses fresh test processes and isolated temporary state. Runtime preparation is initiated by the outer runner; child runners inherit VSCODE\_SKIP\_PRELAUNCH, while provider-server reuse remains bounded within each suite. OS caches may be warm for the second pass, but no new application cache determines fan-out.
- Mechanism confidence: High: runner orchestration, environment propagation, mount lifecycle, suite cap, and transitive host forks are directly visible in code.
- Magnitude uncertainty: Exact duration and tmpfs resident-memory use depend on worker load and suite data volume, but mount count, suite-process cardinality, pass ordering, and storage placement are explicit.
