# Performance review: Keep all Agent Host shell output scrollable in the inline chat terminal

[PR #340234](https://github.com/microsoft/vscode/pull/340234) at `51920cc0df3fe4339b8e8bbeadf03ac20689820b`

## Findings (3)

### 1. [high] Bound the transcript retained for chunked shells

**Finding ID:** `PERF-A464D28EFA98`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotNonPtyShellTerminals.ts:334</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Agent Host heap bytes held by the cumulative JavaScript string, plus allocation/GC work as it grows.  
**Scaling:** Retained memory grows linearly with total output over the full lifetime of each chunk-streamed shell and adds across concurrently or historically retained background shells, rather than staying near the 100,000-character terminal cap.  
**Outcome:** Unbounded retained memory and increasing GC pressure, potentially exhausting the Agent Host on long-lived log-producing commands.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The partial-result path replaced lastSnapshot with the runtime's throttled cumulative snapshot, which the surrounding contract documents as becoming a rolling tail after the large-output threshold; the terminal manager separately trims retained terminal content at 100,000 characters.  
**Changed behavior:** Chunk mode concatenates every ANSI-stripped output chunk into stream.lastSnapshot without applying the terminal manager's rolling content limit.  
**Confidence:** 0.99 — The uncapped append, independent bounded terminal store, background continuation path, and non-clearing finalize lifecycle are explicit. Output volume prevalence affects severity exposure, not the mechanism.

**Causal diff evidence:** RIGHT line 334 introduces cumulative concatenation of every streamed chunk into lastSnapshot, creating a second retained transcript that bypasses AGENT\_HOST\_TERMINAL\_MAX\_CONTENT\_LENGTH.

A noisy or long-running background shell can make the Agent Host retain its entire output indefinitely, causing steadily increasing heap use and GC pressure even though the visible terminal state is bounded.

**Evidence:** appendChunk executes stream.lastSnapshot += text for every tool.shell\_output event. AgentHostTerminalManager trims its own content to 80,000 after crossing 100,000, but that does not affect lastSnapshot. Background calls continue through isStreamingInBackground; completeBackgroundShell only finalizes the stream, and \_finalize does not clear lastSnapshot or remove the map entry, so the full transcript remains until the chat/session is disposed.

**Suggested direction:** Keep only a rolling suffix matching the terminal manager's cap and clear comparison state when the stream finalizes; if completion reconciliation needs whole-output equality, maintain bounded metadata such as length plus an incremental digest instead of the full transcript.

### 2. [high] Size scrollback from actual output instead of preallocating 100,000 rows

**Finding ID:** `PERF-36C288F621FE`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatTerminalToolProgressPart.ts:439</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Preallocated xterm scrollback rows and terminal cell-buffer memory.  
**Scaling:** The reserved row capacity increases 100× at the default configuration for each created mirror and scales with the number of tool outputs the user has ever expanded in the rendered chat.  
**Outcome:** Substantially increased retained renderer memory and GC pressure, with possible renderer slowdown or out-of-memory failures in chats containing several expanded shell outputs.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** These mirrors inherited terminal.integrated.scrollback, whose default is 1,000 rows, so opening a small output did not reserve a 100,000-row buffer.  
**Changed behavior:** Every Agent Host output-only terminal snapshot now creates its detached xterm with a 100,000-row scrollback override, even when the command produced only a few lines.  
**Confidence:** 0.99 — The changed value, 100× default ratio, xterm option propagation, schema's explicit preallocation behavior, and mirror lifetime are all directly established in repository code; only the exact bytes per row vary by xterm implementation.

**Causal diff evidence:** RIGHT line 439 changes Agent Host output-only mirrors from the configured scrollback (normally 1,000 rows) to AGENT\_HOST\_TERMINAL\_MAX\_CONTENT\_LENGTH (100,000), despite that constant being defined in characters rather than rows.

Expanding ordinary shell output can cause a large renderer-memory spike and GC pressure; the cost multiplies across tool blocks because collapsing a ChatTerminalToolOutputSection does not dispose its snapshot mirror.

**Evidence:** The added callback returns AGENT\_HOST\_TERMINAL\_MAX\_CONTENT\_LENGTH (100,000 characters) as xterm's row-count option. The repository's terminal.integrated.scrollback schema explicitly says xterm pre-allocates memory based on this value and defaults to 1,000. DetachedTerminalSnapshotMirror forwards the value to createDetachedTerminal, while toggle(false) only hides the output and leaves \_snapshotMirror registered for the part's lifetime. The same character-to-row override is also used by BackgroundShellOutputView.

**Suggested direction:** Do not pass the character cap directly as a row capacity. Size scrollback from the snapshot's actual wrapped row count (and grow it as retained output grows), and release/recreate the detached mirror on collapse so small and hidden outputs do not retain worst-case capacity.

### 3. [medium] Coalesce raw shell chunks before broadcasting terminal updates

**Finding ID:** `PERF-1E192BA700B9`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotNonPtyShellTerminals.ts:333</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** ANSI-processing CPU, action/envelope allocations, protocol transport sends, serialized message bytes, and downstream xterm writes.  
**Scaling:** Work scales with raw SDK chunk count times the number of subscribed clients and active chunk-streamed shells; processing is synchronous and serialized per event, with no coalescing to bound bursts.  
**Outcome:** Excessive IPC and CPU overhead, lower output throughput, and possible dropped frames in clients rendering noisy shell output.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The existing path consumed explicitly throttled cumulative tool.execution\_partial\_result snapshots and emitted only each snapshot's unseen suffix, so update frequency was bounded by snapshot throttling rather than raw process chunk frequency.  
**Changed behavior:** Each tool.shell\_output chunk is processed and immediately appended to the terminal manager, producing a separate TerminalData action and protocol notification.  
**Confidence:** 0.97 — The old throttled contract and new one-call-per-chunk path through synchronous envelope broadcast to transport.send are directly traceable. Runtime chunk size affects magnitude but not the fan-out mechanism.

**Causal diff evidence:** RIGHT line 333 places appendOutputTerminalData directly in the per-chunk handler, converting every newly handled raw shell chunk into its own state/protocol update.

High-volume commands can flood the Agent Host event loop and subscribed clients with small terminal messages, reducing shell/chat throughput and causing renderer work or jank while output streams.

**Evidence:** The new onToolShellOutput listener calls appendChunk for every SDK event. This line calls appendOutputTerminalData once per accepted chunk; that method synchronously dispatches a TerminalData action. AgentHostStateManager emits an envelope, ProtocolServerHandler adds it to the replay buffer and calls transport.send for every relevant client, with no batching, timer, queue limit, or backpressure in this path.

**Suggested direction:** Buffer processed text per tool call and flush ordered batches on a short scheduler or size threshold, with explicit flushes before completion/finalization and disposal so ordering and final output are preserved.
