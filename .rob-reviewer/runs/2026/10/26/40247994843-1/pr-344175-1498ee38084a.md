## Findings (1)

### 1. [medium] Update only the dropdown row whose artifact changed

**Finding ID:** `PERF-4EB6F4CD4506`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/artifactIntegrationGroup.ts:333</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** DOM nodes, hover registrations, event listeners, and synchronous JavaScript work  
**Scaling:** Each snapshot event for one member calls row.update for all N members. During cold load or polling, each of N pull requests publishes separate loading/ready updates for multiple fragments, so row rendering grows toward O(N² × fragments) rather than O(N × fragments).  
**Outcome:** increased input latency and dropped frames while the grouped-artifact dropdown is open  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each artifact was rendered as its own ArtifactIntegrationPill; its autorun depended only on that artifact's snapshot, so a check/comment/mergeability update refreshed only that pill and its keyed ArtifactButtons.  
**Changed behavior:** The new dropdown has one autorun that reads every member snapshot and, whenever any dependency changes, invokes row.update for every member.  
**Confidence:** 0.97 — The dependency fan-out, per-fragment snapshot publication, and full row reconstruction are directly established by the changed code and transitive resource service. Exact milliseconds depend on group size and update timing, so severity is medium rather than high.

**Causal diff evidence:** The added aggregate autorun maps all members and unconditionally calls \`row.update(member, member.presentation.snapshot.read(reader), ...)\` at line 333. \`ArtifactIntegrationGroupRow.update\` then clears its disposable store and recreates icon/status/action DOM, hovers, and listeners for that row.

Opening a group while several PRs are loading or polling can synchronously reconstruct every row repeatedly as independent check/comment/mergeability results arrive, making dropdown navigation visibly janky for larger groups.

**Evidence:** \`GitHubPullRequestArtifactResource\` subscribes to a \`PullRequestSnapshot\` containing core, reviewThreads, checks, and mergeability. \`PullRequestResourceService.\_setLoading\` and \`\_commitResult\` publish a new snapshot separately for each fragment state transition. Therefore one PR commonly emits multiple snapshot events. Because the dropdown autorun reads every member snapshot, any such event reruns the complete members loop; each \`row.update\` calls \`content.clear()\`, rebuilds status/action elements, resets DOM, and re-registers hovers/listeners. The old per-pill autorun in ArtifactIntegrationPresentation reads only \`this.presentation.snapshot\` and ArtifactButtons retains controls by ID.

**Suggested direction:** Keep the membership/order reconciliation in the aggregate autorun, but give each row an owned autorun keyed to only its member snapshot and selected state (or compare cached snapshot/selection before calling update). Preserve row identity and update only the row whose data changed.
