### Scenario 1: Open an agent session from the sessions list or picker with the setting disabled or enabled

- Critical path: The click marks the session read, waits for the session item provider activation and resolvability check, then opens either the existing Chat view path (setting disabled) or an editor in the active/side group (setting enabled). The destination UI must be ready before the open completes.
- Scaling input: One selected session per user action. The added widget lookup is linear in currently instantiated chat widgets; editor reuse may scan open editor groups and tabs once. It does not scale with session-list size or message count.
- Effective concurrency: One awaited open flow per click. The diff adds no Promise fan-out, queue, subprocess burst, or parallel remote work; downstream provider activation retains existing service coordination.
- Cache behavior: Warm providers return from registered controller/content-provider state. Existing widgets and editor inputs are reused. On a cold provider, activation occurs exactly as before the diff; the configuration branch does not alter cache keys, negative caching, or coalescing.
- Mechanism confidence: High confidence that the changed branch adds only a configuration read and bounded in-memory widget lookup before the existing openSession path; repository tracing shows no new boundary or multiplicative work.
- Magnitude uncertainty: The exact number of open tabs/widgets and provider activation duration varies, but the added lookups are bounded by open UI surfaces and occur once per explicit open action.
- Expensive boundaries:

### Scenario 2: Open an agent-host-session link, including a cold uncached authority and a warm known session

- Critical path: The opener resolves the client session resource, strips a default-chat fragment if needed, activates the session item provider, then opens the Chat view or editor according to the setting/openToSide option.
- Scaling input: One link per explicit open. A cold unresolved authority lists all sessions for that authority once; effective boundary cardinality remains one listSessions call regardless of returned session count.
- Effective concurrency: Concurrent cold resolutions for the same authority share \_sessionListRefreshes. The diff does not change that coalescing or add concurrent editor opens.
- Cache behavior: A known resource is resolved from IAgentHostConnectionsService without listing. Concurrent cold misses for one authority are coalesced; registered session identities make subsequent resolutions warm. The new setting is read only after resolution and provider activation, so it cannot defeat this cache.
- Mechanism confidence: High confidence from the unchanged resolution/activation call path and the new branch occurring afterward.
- Magnitude uncertainty: Agent-host session counts and remote latency vary, but neither boundary's call count or placement changes in this PR.
- Expensive boundaries:

- Verdict: No reportable performance regression. Cold remote work, warm caching, and same-authority coalescing are unchanged; destination selection adds only bounded in-memory lookup.

### Scenario 3: Open a session already shown in the Chat view, in an editor, or in an inactive editor tab

- Critical path: For an existing editor, the service reveals it. For a Chat-view session with editor targeting, it retains the model reference, clears/moves the source widget, and opens the editor. For an inactive tab without a widget, editor discovery reveals that input.
- Scaling input: One selected resource. Widget discovery scans instantiated chat widgets once; editor discovery scans open groups/tabs at most once or along the existing reveal/move path. There is no history- or session-list-wide reconstruction.
- Effective concurrency: Move and reveal operations are sequential and awaited. The model reference is retained until the destination acquires it, preventing duplicate asynchronous loads; no new burst is introduced.
- Cache behavior: Existing widgets/editor inputs are positive reuse states. Absence of a widget permits the editor service to find an inactive input. Session models are acquired from existing state during movement and released in finally; the diff introduces no persistent cache or retained key.
- Mechanism confidence: High confidence from shouldRevealSessionEditor and ChatWidgetService.openSession/prepareSessionForMove call tracing.
- Magnitude uncertainty: A workspace can have many open tabs, but the scan is once per explicit open and is the existing editor-reuse mechanism; no evidence supports user-visible scaling regression.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. The changed logic avoids revealing the Chat view when the opt-in editor destination is requested and relies on existing model-transfer and editor-reuse lifecycle.
