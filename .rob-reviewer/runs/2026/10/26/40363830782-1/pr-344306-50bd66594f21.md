# Performance review: Agents: add Move to Session... commands for chats and sessions

## Findings (1)

### 1. [medium] Avoid enumerating every destination while opening the context menu

**Finding ID:** `PERF-AC7E5E893254`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:7365</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** main-thread CPU work and temporary arrays/destination objects  
**Scaling:** Each session or nested-chat context-menu open now rebuilds the merged session list across all providers and then traverses every session; every eligible target also calls getChatMoveAppendAnchor, whose scan grows with trailing hidden/tool chats. This is O(all known sessions plus inspected target chats), not the five rows per group normally rendered by the capped list.  
**Outcome:** increased context-menu opening latency and possible UI jank for users with large agent-session histories  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, opening these context menus did not call ISessionsManagementService.getSessions or enumerate possible move targets; destination work only existed for an actual drag target.  
**Changed behavior:** The added context keys synchronously call getSessionMoveDestinations/getChatMoveDestinations and materialize the complete destination array before the menu can be shown, merely to test length &gt; 0. This runs even when chat moves are disabled and the command's when-clause will hide it.  
**Confidence:** 0.94 — The synchronous call path and all-session cardinality are explicit in the changed lines and helper implementations, and the setting gate is demonstrably only in the menu when-clause after overlay construction. Exact delay varies with history size and providers, but that affects severity rather than the mechanism.

**Causal diff evidence:** RIGHT line 7365 newly invokes getSessionMoveDestinations(element, this.\_sessionsManagementService.getSessions(), ...).length during context-menu construction; RIGHT line 7456 adds the same full enumeration for chat menus. Neither call existed before this diff.

Right-clicking any session row (and, via the analogous added line 7456, any nested chat row) can stall menu display while all provider sessions are merged, deduplicated, and scanned. The trigger is especially broad on Stable, where the move setting defaults off but this work still runs.

**Evidence:** onContextMenu and showChatContextMenu build their overlays synchronously before contextMenuService.showContextMenu. The added line calls getSessions(), whose implementation merges every provider's getSessions result and deduplicates it; getSessionMoveDestinations uses flatMap over that entire result, and getChatMoveAppendDestination computes getChatMoveAppendAnchor for each valid target. SessionsList already keeps the current uncapped collection in this.sessions, while rendering caps groups to DEFAULT\_SESSION\_GROUP\_LIMIT=5, so a large hidden history still participates. No subprocess/IPC/network call is awaited on the normal warm path; the regression is synchronous CPU/allocation on menu display.

**Suggested direction:** Gate this computation with the existing move-enabled/ChatContextKeys condition, reuse the SessionsList's cached this.sessions collection, and add an existence-only helper using some(canMoveIntoSession) so menu construction stops at the first valid target without computing append anchors or allocating destination objects. Keep full destination/anchor construction in the command after the user selects it.
