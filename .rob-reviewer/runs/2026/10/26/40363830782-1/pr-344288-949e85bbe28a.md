**Relevant issue families:** repeated-work, serialization-allocation

### Scenario 1: Menu-backed or manually populated toolbar creation and updates

- Critical path: A menu-change event (debounced where configured) or direct caller synchronously enters WorkbenchToolBar.setActions, classifies primary actions, then calls the base toolbar to rebuild action view items/DOM before the toolbar update completes.
- Scaling input: Primary toolbar action count N and configured alwaysShownItems count K. The new membership check is O(N\*K) only when the new option is configured; no production caller in the changed repository configures it, and realistic toolbars have a small bounded number of actions and fixed items.
- Effective concurrency: Toolbar updates execute serially on the UI JavaScript thread; MenuWorkbenchToolBar uses the menu service's existing debounce and introduces no new queue, fan-out, or parallel work.
- Cache behavior: No cache or remote lookup is added. The readonly option is reused for each update, and existing menu/action state supplies hidden flags. Cold and warm behavior differ only through pre-existing menu state; there are no misses, negative-cache retries, or coalescing changes.
- Mechanism confidence: High: the changed loop and includes scan are direct, and repository search establishes that only tests opt into the option. The added no-option function/type check is constant work per already-processed action.
- Magnitude uncertainty: Future consumers could provide larger arrays, but this is an internal toolbar API and the expected action/fixed-item cardinalities are small; there are currently no non-test consumers of alwaysShownItems.
- Expensive boundaries: none found
- Verdict: No reportable regression. The changed action classification is synchronous but bounded, adds no expensive boundary, and existing production toolbars do not opt into the only scaling scan.

### Scenario 2: Opening a customizable toolbar context menu, including repeated right-clicks on an always-shown item

- Critical path: A user contextmenu event synchronously resolves the clicked action, builds configure/hide/toggle entries, shallow-copies the joined action list, appends Reset Menu when applicable, and hands the list to the context-menu service for rendering.
- Scaling input: Number of toggle actions in that toolbar. The spread copies one small action-reference array once per user-triggered context-menu open; it does not clone actions or traverse unrelated menus.
- Effective concurrency: One synchronous UI event at a time on the renderer thread; context menus are user-triggered and no asynchronous tasks or concurrent boundary operations are launched.
- Cache behavior: Toggle actions are captured from the most recent setActions call. The new copy prevents the cached toggleActions array from being mutated by Reset Menu entries, so repeated opens remain constant-size rather than retaining one separator/action pair per open. No cold/warm cache or negative-cache behavior applies.
- Mechanism confidence: High: Separator.join aliasing and the shallow spread are explicit in the changed hunk and covered by the added repeated-open test.
- Magnitude uncertainty: Exact toolbar action counts vary, but context menus are typically small and manually triggered. The prior mutation condition was not reachable by existing production configurations according to the code search; it becomes reachable with the new always-shown option and is prevented in the same diff.
- Expensive boundaries: none found
- Verdict: No reportable regression. The one bounded allocation per open is negligible and prevents unbounded repeated-menu growth in the newly enabled scenario; no subprocess, IPC, filesystem, database, or network call is added or moved onto the path.
