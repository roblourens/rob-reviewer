# Performance review: chat: add a tool that screenshots the window

[PR #344282](https://github.com/microsoft/vscode/pull/344282) at `96bc4bb415e7945f3c59ffc7ada262d3898081ef`

## Findings (1)

### 1. [medium] Downscale screenshots before transferring them to the renderer

**Finding ID:** `PERF-9CB8FC9354EB`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/tools/screenshotWindowTool.ts:97</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Full-resolution JPEG bytes, decoded image pixels, renderer-thread canvas CPU, and temporary image/canvas objects  
**Scaling:** Cost grows with the window's pixel area and is paid once per screenshot; the updated background skill mandates at least one capture and can repeat it for a couple of revision rounds.  
**Outcome:** Increased tool latency plus renderer CPU/GC pressure and potential dropped frames while the full-window image is decoded, drawn, and JPEG-encoded.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The background-generation workflow did not capture or process the VS Code window, and no screenshotWindow tool invocation existed.  
**Changed behavior:** Each screenshotWindow call first receives a full-resolution quality-95 JPEG from the main process, then calls the DOM-based resizeImage helper in the workbench renderer, which decodes the full image, synchronously draws it to a canvas, and encodes a second JPEG.  
**Confidence:** 0.94 — The main-process capture/encode, renderer transfer, DOM decode/draw/re-encode call path and one-to-several invocation cardinality are explicit in code. Exact stall duration varies by window resolution and hardware, which affects severity rather than the mechanism.

**Causal diff evidence:** Added line 97 performs the only size reduction after the full-resolution capture has already been JPEG-encoded and transferred into the renderer; before this PR the new tool and its mandatory background-validation calls did not exist.

On large or 4K windows, every post-background check transfers and decodes a multi-megapixel capture on the workbench UI side before the model can continue; repeated checks multiply that latency and can visibly stall chat rendering.

**Evidence:** The added invoke path awaits IHostService.getScreenshot and then reaches this changed resizeImage call. The desktop implementation in nativeHostMainService.ts uses webContents.capturePage followed by captured.toJPEG(95), so full-resolution bytes cross main-process IPC. chatImageUtils.ts implements resizeImage with Image decoding, a synchronous canvas drawImage on the renderer thread, and canvas.toBlob/FileReader re-encoding. The changed SKILL.md requires a screenshot after setChatBackground and allows a couple of sequential revision checks.

**Suggested direction:** Add a bounded-size/quality screenshot option to the native host path and resize the Electron NativeImage before its first toJPEG/IPC transfer, returning the final JPEG so this tool can skip renderer-side resizeImage. Preserve the existing full-resolution default for other screenshot callers.
