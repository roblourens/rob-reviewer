# Performance review: Connect editor windows to workspace-configured remote agent hosts

[PR #344139](https://github.com/microsoft/vscode/pull/344139) at `2c6e8aa41eb37afdf66091bd78e1716818deb7f3`

## Findings (1)

### 1. [medium] Defer the full remote session-history fetch

**Finding ID:** `PERF-24422D50C7BD`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts:440</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** One full-history WebSocket RPC per workspace host, remote catalog/provider/session-database reads, serialized session-summary bytes, and retained client objects.  
**Scaling:** For H workspace-configured hosts with N\_h historical sessions, cold-open work and retained data grow with sum(N\_h); host requests can overlap up to H-way concurrency. Per-agent refresh calls are coalesced by the shared store, but each full delta is additionally projected by each advertised provider.  
**Outcome:** Increased post-restore latency and background CPU/GC, remote I/O, network transfer, and retained memory proportional to remote session history.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Editor windows did not create WebSocket remote-host connections or remote-host session-list controllers, so opening a normal workspace performed no remote listSessions RPC and retained no remote history. Session listing for these hosts was confined to the Agents-window flow.  
**Changed behavior:** Editor windows now register a session-list controller as soon as each workspace-configured remote host advertises an agent, which eagerly starts a full remote session catalog refresh even when Chat or session history has not been opened.  
**Confidence:** 0.98 — The call path is explicit: the added registration synchronously starts initialRefresh; controller.refresh delegates to the shared store; the store coalesces agents to one call per host but calls AgentHostProtocolClient.listSessions over JSON-RPC. The protocol documents the catalog as arbitrarily large, while this client omits limit/cursor and the server handler computes and returns every session. The only magnitude uncertainty is each configured host's history size and remote storage speed.

**Causal diff evidence:** RIGHT line 440 newly calls registerChatSessionItemController for every advertised agent of each workspace remote host; ChatSessionsService.registerChatSessionItemController immediately invokes controller.refresh(), which reaches AgentHostSessionListStore.refresh() and connection.listSessions().

Opening any workspace that lists a remote agent host immediately makes the remote machine enumerate its entire session history and transfers/materializes it in the editor, even if the user never opens Chat. Large histories or several configured hosts cause avoidable remote database/provider I/O, network bytes, CPU/GC, and retained memory; the requests can run concurrently across hosts and delay session-list readiness while contending with post-restore work.

**Evidence:** registerChatSessionItemController immediately executes controller.refresh at chatSessions.contribution.ts:1177. AgentHostSessionListController.refresh delegates to AgentHostSessionListStore.refresh, whose cold path calls connection.listSessions. AgentHostProtocolClient.listSessions sends a WebSocket JSON-RPC listSessions request without the supported limit/cursor and maps every returned summary. The protocol explicitly says this list can be arbitrarily large and provides pagination; protocolServerHandler currently ignores pagination, calls AgentService.listSessions for the complete catalog, performs catalog/provider/session-database work, and serializes all summaries. The store then retains every entry and projects the full result through each provider controller. The store coalesces simultaneous per-agent refreshes, so effective boundary cardinality is one unbounded RPC per connected workspace host, not one per agent.

**Suggested direction:** Do not trigger the full catalog from controller registration. Defer the first list refresh until the session-history UI actually requests that provider, or implement the existing listSessions limit/cursor contract end-to-end so initial registration fetches only a bounded recent page and backfills on demand while preserving notification-driven updates.

### Scenario 2: Add, rename, or remove workspace remote-host entries

- Cache behavior: Changing the setting reparses the complete array. - Mechanism confidence: High: desired-address reconciliation, pending-connect deduplication, disposal, and controller-triggered refresh are explicit.
- Magnitude uncertainty: Interactive edits normally add one host at a time; bulk workspace-setting replacement can add more. History size and remote latency remain host-dependent.
- Expensive boundaries:

- Verdict: The eager catalog load is covered by the submitted finding. Connection-per-added-host and cleanup-per-removed-host are expected feature costs; no separate regression is warranted.
