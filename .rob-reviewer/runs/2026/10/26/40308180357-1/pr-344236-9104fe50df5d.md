# Performance review: Engineering - run ESLint and hygiene only on changed files in batched CI builds

[PR #344236](https://github.com/microsoft/vscode/pull/344236) at `9104fe50df5d27135beec5b82f813b794daed1c7`

## Findings (1)

### 1. [medium] Keep the full-check fallback concurrent with compilation

**Finding ID:** `PERF-AABD4B779615`  
**Location:** <code>build/azure-pipelines/product-quality-checks.yml:165</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** full-repository hygiene and ESLint CPU/filesystem work plus the compilation subprocesses that are delayed behind it  
**Scaling:** When the new Azure changes request, shallow-history fetch, or base computation fails, VSCODE\_CHANGED\_SINCE remains unset and both checks scan the full repository; their entire runtime is then added before the six compilation checks can start, growing with repository size rather than the changed-file set.  
**Outcome:** increased Quality-job wall-clock latency and a higher risk of hitting the existing 30-minute job timeout on transient scope-resolution failures  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The pre-PR command launched core-ci, full hygiene, full ESLint, and all five other compilation checks together under one npm-run-all2 invocation, so a successful job's critical path was approximately the slowest branch.  
**Changed behavior:** This added command expands an unset VSCODE\_CHANGED\_SINCE to no arguments and performs full hygiene and ESLint in a separate task; the following Compile task cannot start until both full scans complete.  
**Confidence:** 0.94 — The fallback control flow, full-scan behavior, task ordering, and before/after concurrency are explicit in the changed YAML and called scripts. Exact duration and failure frequency are uncertain, but the new API/fetch boundaries make the trigger realistic and the repository-wide work is known to be substantially larger than the intended changed-file path.

**Causal diff evidence:** Added RIGHT line 165 invokes hygiene and eslint as a standalone pipeline step; added lines 167-170 place the compilation invocation in a subsequent step, while computeChangedSince.ts lines 96-99 deliberately convert every new network/git failure into a successful warning that leaves VSCODE\_CHANGED\_SINCE unset.

Any transient Azure DevOps API timeout/error, git fetch failure, or build with more than 1000 associated commits takes the fallback. In that case developers wait for full hygiene and ESLint to finish before compilation even begins, instead of those costs overlapping as they did before this PR.

**Evidence:** computeChangedSince performs a new Azure HTTP request with a 30-second timeout and a new git fetch, and its catch handler does not fail the task or set VSCODE\_CHANGED\_SINCE. The shell expansion on lines 164-165 therefore runs the unscoped package scripts. build/eslint.ts maps no arguments to the full eslintFilter, and build/gulpfile.hygiene.ts maps no changed-since value to hygiene(undefined, false). product-quality-checks.yml then starts Compile only after this step. The unchanged fallback before the PR was one parallel npm-run-all2 command.

**Suggested direction:** Preserve the old combined npm-run-all2 invocation when VSCODE\_CHANGED\_SINCE is unset (for example, have scope resolution set a success variable and condition two task variants), while retaining the staged changed-file path only when a base was computed.

### Scenario 2: Batched CI Quality job when changed-scope resolution fails or exceeds 1000 commits
