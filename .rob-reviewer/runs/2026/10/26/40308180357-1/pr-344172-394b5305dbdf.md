**Relevant issue families:** eager-work, synchronous-ui-work, boundary-fanout, serialization-allocation

### Scenario 1: Agents window startup and chat-view creation with the response-selection menu now enabled by default

- Critical path: Configuration registration resolves a boolean default during contribution loading. Opening a chat constructs ResponseSelectionSideChatController, but that constructor already eagerly creates both FeedbackInputWidget and Menu regardless of the setting; the changed default is not read until a response selection is shown.
- Scaling input: Number of open Agents chat views. Per view, controller, input, menu, actions, and listeners are unchanged before and after the diff.
- Effective concurrency: Synchronous per-view UI construction is unchanged; no queue, limiter, or parallel expensive work is added by the default flip.
- Cache behavior: Configuration lookup uses the existing configuration service. Cold and warm behavior are unchanged, and no new cache, cache key, miss, or retry behavior is introduced.
- Mechanism confidence: High confidence that the diff adds no startup CPU, allocation, I/O, IPC, subprocess, database, or network mechanism beyond resolving a different boolean constant.
- Magnitude uncertainty: Exact UI construction cost is not measured, but construction cardinality and objects are provably unchanged because both surfaces were already created unconditionally.
- Expensive boundaries: none found
- Verdict: No reportable regression: the changed default does not cause eager creation of the menu or add startup work.

### Scenario 2: Selecting assistant response text in an Agents chat

- Critical path: A document selectionchange is scheduled to an animation frame, resolves the response selection, then shows and positions either the prebuilt menu or prebuilt input. The new default chooses the menu; both variants perform the same selection resolution, highlighting, geometry reads, and overlay positioning, while the old input path additionally autosized and updated its action state.
- Scaling input: One scheduled update per completed selection gesture, with scroll-driven repositioning only while the affordance is visible. Transcript size does not change the diff's cardinality because selection resolution and positioning are shared by both variants.
- Effective concurrency: Selection changes are coalesced by the existing AnimationFrameScheduler. The diff neither removes coalescing nor adds parallel work.
- Cache behavior: No cache is involved. The selected Range and last placement rectangles are retained only for the lifetime of the visible affordance under both variants.
- Mechanism confidence: High confidence from tracing \_applySelectionChange, \_showFor, and \_reposition that the changed default swaps prebuilt surfaces without increasing event frequency or collection-wide work.
- Magnitude uncertainty: Browser layout costs vary by platform, but the shared positioning reads are unchanged and the newly selected menu path does not add a new repeated layout loop.
- Expensive boundaries:
  - serialization at <code>src/vs/sessions/contrib/chat/browser/chatView.ts:512 via logResponseSelectionWidgetAction</code>: Telemetry logs one response-selection 'shown' action with the selected variant.; cardinality: One event when the affordance transitions from hidden to visible, unchanged from the old default; only the variant value changes.
    - Introduced by diff: false; previous behavior: The same action was logged as askQuestionInput; after the diff it is logged as actionMenu.; critical-path effect: The existing telemetry call occurs after the overlay surface is selected and does not add a new boundary to selection handling.
- Verdict: No reportable regression: there is no added synchronous UI-work mechanism, and the action-menu path avoids the old input autosizing calls on initial display.

### Scenario 3: Using Ask in a Side Chat, Quote, or Copy from the newly default response-selection menu

- Critical path: After selection, explicit user activation invokes the chosen action. Ask first opens the already-created input and only creates/opens/sends a side chat after a later explicit submission; Quote updates the local chat input; Copy performs a clipboard write.
- Scaling input: One operation per explicit action activation. Quote formatting scales linearly with selected text length, and clipboard bytes scale with selected text length; neither runs merely because the default changed.
- Effective concurrency: Side-chat submission remains one promise chain per explicit submit and blocks duplicate submission with the existing busy state. Clipboard writes are awaited per explicit click. The diff adds no burst or fan-out.
- Cache behavior: No cache participates. The selected response text is retained only while the affordance is open, unchanged from the enabled-menu behavior that already existed.
- Mechanism confidence: High confidence from direct action-handler tracing that no network or clipboard boundary is executed by the changed default itself.
- Magnitude uncertainty: Selected text and side-chat latency can vary, but all expensive operations remain gated by explicit user actions and retain one-operation-per-action cardinality.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/responseSelectionSideChatController.ts:609</code>: Create/open/send a side chat through IChatSideChatService after the user chooses Ask and submits a question.; cardinality: At most one in-flight request chain per controller because isBusy prevents duplicate submissions.
    - Introduced by diff: false; previous behavior: With the old default, submitting the directly shown Ask Question input reached the same side-chat boundary; the menu adds an explicit Ask choice before that input.; critical-path effect: This boundary is on the explicit question-submit path, not response selection or menu display.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/responseSelectionSideChatController.ts:445</code>: Write selected response text through IClipboardService after the user explicitly chooses Copy.; cardinality: One clipboard write per explicit Copy activation, independent of transcript item count.
    - Introduced by diff: false; previous behavior: The operation already existed in the action-menu variant; the diff changes the default exposure but does not execute it automatically or increase calls per activation.; critical-path effect: Only the Copy action waits for the clipboard write; selection and menu display do not.
- Verdict: No reportable regression: the newly default menu exposes intentional actions, but expensive boundaries remain explicit, bounded, and no more frequent per activation.

### Scenario 4: Opening Sessions Chat accessibility help and running its updated tests

- Critical path: Accessibility help synchronously reads the configuration boolean and appends one of two localized strings. The changed test explicitly supplies false to continue testing the legacy description.
- Scaling input: Constant work per accessibility-help invocation and constant work per test case.
- Effective concurrency: Fully synchronous string assembly; no added asynchronous work or concurrency.
- Cache behavior: Existing localized strings and configuration service behavior are unchanged; no new cache state is introduced.
- Mechanism confidence: High confidence from the changed test and provider branch.
- Magnitude uncertainty: None material; the branch selects one constant string.
- Expensive boundaries: none found
- Verdict: No reportable regression: only branch selection and test configuration changed, with constant CPU and allocation cost.
