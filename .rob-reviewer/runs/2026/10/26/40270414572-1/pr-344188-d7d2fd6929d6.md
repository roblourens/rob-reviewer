**Relevant issue families:** repeated-work, eager-work, serialization-allocation

### Scenario 1: Open or search Chat Customizations → Tools and update tool enablement badges

- Critical path: Initial render synchronously materializes the registered tool-set iterable, lazily creates the cached 17-tool Copilot set once, enumerates tool memberships for the view model and badge, and renders the tree. Search recomputes the view model after the existing 200 ms delayer; the badge autorun is not dependent on the search query.
- Scaling input: Number of registered tool sets and their in-memory member tools; the diff adds one fixed set with 17 members and one shallow array materialization per reactive recomputation. Connected-source tools are excluded from this count.
- Effective concurrency: Tool-set enumeration and counting are synchronous and serial. Existing connected-source list operations may run once per expanded ready server, potentially concurrently across expanded servers, but this scheduling is unchanged by the diff.
- Cache behavior: The Copilot set and its 17 tool objects are lazily initialized and cached module-wide. Registered tool sets remain observable. Connected tools retain the existing per-server cache and are loaded only after expansion; session changes invalidate that cache.
- Mechanism confidence: High: the helper implementation, reactive dependencies, tool-set getTools implementation, search debounce, singleton cache, and connected-tool path were directly inspected.
- Magnitude uncertainty: Exact extension-contributed set/tool cardinality varies, but the incremental work is fixed at 17 tool checks plus a shallow set-array copy and does not cross an expensive boundary.
- Expensive boundaries:
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/toolsListWidget.ts:\_loadConnectedTools</code>: List tools exposed by a connected MCP server via server.listTools(); cardinality: At most one in-flight/load result per ready expanded server until the per-server cache is invalidated; effective count is the number of expanded connected servers, not registered customization tool sets.
    - Introduced by diff: false; previous behavior: The same expansion-gated listTools call and per-server cache existed before the diff; the new helper neither invokes it nor changes expansion or invalidation.; critical-path effect: Only blocks population of an expanded connected-server row; it is not on the registered-set badge or Copilot-set construction path.
- Verdict: No reportable regression. The diff replaces equivalent prior static-set rendering and adds a small fixed in-memory count to badges; it does not increase boundary calls or create unbounded work.

### Scenario 2: Render and reactively update the Agents window Customizations Tools toolbar badge and total count

- Critical path: Toolbar rendering and subsequent tool-set or enablement observable changes synchronously call readCustomizationCount, shallow-copy registered sets, append the cached Copilot set, enumerate enabled tool IDs, and update the badge DOM.
- Scaling input: Registered in-memory tool sets and member tools, plus the fixed 17 Copilot members. Effective deduplication is by tool ID in countEnabledCustomizationTools.
- Effective concurrency: Single-threaded synchronous autorun; no queue, subprocess, IPC, filesystem, database, or network work is reached.
- Cache behavior: The static Copilot tool objects are shared through a module singleton. Observable tool-set and enablement state drive recomputation; no miss/retry behavior is introduced.
- Mechanism confidence: High: both the toolbar autorun and count helper were traced to in-memory observable sets and context-key checks only.
- Magnitude uncertainty: The registered collection may vary with installed extensions, but the PR's incremental cardinality is fixed and small.
- Expensive boundaries: none found
- Verdict: No reportable regression. The added badge accuracy costs one fixed 17-item scan and shallow iterable copy per relevant observable update, with no hot input/frame trigger or expensive boundary.

### Scenario 3: Display the AI Customizations overview counts in the sidebar

- Critical path: loadCounts performs the existing prompt/customization discovery first; after it resolves, the tools autorun synchronously computes the badge from registered sets plus the cached 17-tool Copilot set and updates six count elements. Tool-set or enablement changes rerun only that in-memory autorun.
- Scaling input: Workspace prompt files for the pre-existing discovery phase; registered tool sets and members for the tools badge, with a fixed 17-member increment from this diff.
- Effective concurrency: The existing agent, skill, and instruction discovery branches run through Promise.all; instruction discovery contains a sequential second read. The added tool count is synchronous and serial after discovery and adds no concurrency.
- Cache behavior: Prompt-service caching is outside the changed path. The new Copilot set is lazily cached module-wide; each count uses the existing observable tool-set state.
- Mechanism confidence: High: loadCounts ordering and all changed/transitive calls were inspected; no new boundary is reachable from getCustomizationToolSets.
- Magnitude uncertainty: Workspace file-discovery duration varies, but that cost and its triggers are unchanged. The changed work is a fixed in-memory 17-tool count after the existing await.
- Expensive boundaries:
  - filesystem at <code>src/vs/sessions/contrib/aiCustomizationTreeView/browser/aiCustomizationOverviewView.ts:loadCounts</code>: Discover agent skills and list prompt files and agent instruction files; cardinality: Three parallel section branches per loadCounts call, with the instructions branch performing its existing additional instruction-file listing; cardinality scales with workspace prompt/instruction files.
    - Introduced by diff: false; previous behavior: The same discovery calls, Promise.all grouping, event triggers, and placement before the tools autorun existed before the diff; adding the Copilot set does not add or repeat any filesystem call.; critical-path effect: These reads must complete before loadCounts installs/updates the reactive counts, including the tools autorun.
- Verdict: No reportable regression. The PR does not move or multiply filesystem discovery and adds only bounded in-memory work to the existing tools count.
