# Performance review: chat: fix Keep and Undo review synchronization

[PR #344133](https://github.com/microsoft/vscode/pull/344133) at `5959768d29be203c75f3fb16e52b71e657086f0b`

## Findings (3)

### 1. [medium] Coalesce checkpoint snapshot comparisons

**Finding ID:** `PERF-D5475532B184`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCheckpointReview.ts:116</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Remote \`resourceRead\` calls plus full snapshot bytes, Base64 decoding, and buffer allocations  
**Scaling:** For N affected files and S registered views, this performs 2×N×S content reads. In the normal chat view S can be 2 because both \`AgentHostEditReview\` and \`AgentHostSessionInputPills\` register the same Working Set, producing up to four reads per file; the loops serialize files and sources.  
**Outcome:** Start Over and checkpoint Undo incur excessive remote I/O and serial network latency before any file restoration begins.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Checkpoint navigation resolved checkpoint edits and wrote crossed files; it had no pre-restore scan that fetched every visible Working Set snapshot or repeated that scan per UI source.  
**Changed behavior:** \`prepareRestore\` now loops every registered source and file, issuing the added pair of full \`readFile\` calls before restoration. It neither deduplicates equivalent source revisions nor caches content URIs, even though \`file.diff.originalURI\` and \`target.beforeContentUri\` commonly wrap the same normalized before-content reference.  
**Confidence:** 0.99 — The exact remote boundary, nested serial loops, duplicate registrations, and URI construction are all directly traced. The number and size of files affect severity, not the mechanism.

**Causal diff evidence:** New RIGHT lines 116-117 add two content reads inside nested source/file loops. The same diff also registers \`\_rawChanges\` at \`AgentHostEditReview.ts:352\` and \`checkpointSource\` at \`AgentHostSessionInputPills.ts:822\` with the shared checkpoint review.

Undoing a checkpoint with a multi-file Working Set now fetches each baseline and before snapshot repeatedly. Agent-host content URIs resolve through \`connection.resourceRead\`, so remote sessions pay multiple round trips and transfer/decode the full file contents; duplicate UI sources repeat the same work.

**Evidence:** Both changeset diffs and checkpoint tool edits derive their before URI with \`toAgentHostContentUri(normalized.beforeContentUri, ...)\`; \`AgentHostFileSystemProvider.readFile\` services these URIs with \`connection.resourceRead(..., Base64)\` and decodes the returned bytes. \`prepareRestore\` awaits each file in sequence and does not coalesce duplicate sources or URIs.

**Suggested direction:** Deduplicate files by channel/resource/revision across registered sources, short-circuit when the two content URIs are equal, and use an operation-scoped promise/content cache for remaining URI comparisons so each remote snapshot is fetched at most once.

### 2. [medium] Wait only for the selected file's review update

**Finding ID:** `PERF-141C0E3A5B95`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostEditReview.ts:361</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Filesystem/content-reference reads, text-model loads, and editor-worker diff CPU for every pending working-set file  
**Scaling:** The delay grows with the number and size of files in pending Working Set publications because \`\_update\` awaits \`\_updateFile\` serially for the full file list; each changed file reads snapshots and can run multiple diffs capped at 1 second each.  
**Outcome:** Opening a changed file can be delayed by seconds behind unrelated review reconciliation instead of opening immediately.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The working-set row used \`openFile: true\`, which called \`editorService.openEditor\` directly for the selected resource and did not wait for AgentHost review reconciliation.  
**Changed behavior:** The new live-diff path calls \`resolveEntry\`, and this added line queues an empty task on the single session-wide \`\_updates\` Sequencer, placing all previously queued \`\_update(files)\` work on the row-open critical path.  
**Confidence:** 0.99 — The changed default call path, global sequencing, serial per-file work, and pre-diff direct-open behavior are explicit. Only the exact duration and typical working-set size vary by provider and file size.

**Causal diff evidence:** Added RIGHT line 361 explicitly awaits the global \`\_updates\` Sequencer from \`resolveEntry\`; the newly added \`\_openFileDiff\` awaits \`session.resolveEntry\` before opening the editor, whereas the deleted \`openFile: true\` path opened directly.

With the default \`chat.editing.openChangedFileInDiffEditor=true\`, clicking a working-set row while a multi-file host publication is being reconciled waits for every queued file before the editor opens. A turn touching many or large files therefore makes the row feel unresponsive even when the selected file is already available.

**Evidence:** \`ChatSessionWorkingSet.\_openFileDiff\` now awaits \`AgentHostSnapshotController.resolveEntry\`, which delegates here. \`\_updates\` receives whole-publication \`\_update(files)\` jobs at line 342; \`\_update\` iterates files serially and \`\_updateFile\` performs content reads, model resolution/reload, and editor-worker diff computation. The setting that takes this path defaults to true.

**Suggested direction:** Track readiness per resource: return an already-current selected entry immediately, or await only the selected URI's reconciliation and fall back to the recorded diff on failure. Do not use the whole-session Sequencer as the row-open barrier.

### 3. [medium] Avoid pre-reading every normal checkpoint write

**Finding ID:** `PERF-7C9DEA03F197`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSnapshotController.ts:539</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** One extra full-file read, transfer, buffer allocation, and byte comparison for every write-eligible checkpoint edit  
**Scaling:** The extra I/O grows with total bytes and the number of edits across crossed checkpoints. Edits within one checkpoint launch concurrently, creating a read burst, while multiple checkpoints are processed serially.  
**Outcome:** Checkpoint Undo/Redo has higher latency and network/IPC traffic, especially for remote workspaces and large multi-file restores.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** For edit/create restoration, the controller read the checkpoint snapshot and immediately called \`writeFile\`; it did not read the current target file first.  
**Changed behavior:** \`\_writeCheckpointFile\` now reads the snapshot, then this added line reads and byte-compares the entire target, and only then performs the same write when content differs.  
**Confidence:** 0.97 — The additional full-file read and remote provider call are explicit and occur on every write helper invocation. Savings are possible only when target bytes already equal the snapshot, which is atypical on normal checkpoint traversal; exact remote latency is environment-dependent.

**Causal diff evidence:** Added RIGHT line 539 invokes \`\_readCheckpointFile(resource)\` before every \`\_writeCheckpointFile\` write; the deleted implementation in each edit branch directly read the snapshot and wrote it.

On an ordinary Undo/Redo the target content differs, so the new equality precheck does not save the write: it adds a full \`resourceRead\` before the existing \`resourceWrite\` for every edited file. Remote agent-host files therefore transfer the current file before writing the snapshot, increasing restore time and bandwidth.

**Evidence:** The helper is used for every Edit and content-bearing Create/Delete/Rename restoration. For \`vscode-agent-host\` targets, \`IFileService.readFile\` reaches \`AgentHostFileSystemProvider.readFile\`, which performs a remote \`resourceRead\` and Base64 decode. The PR's recovery tests show the equality check is needed only to make partially applied recovery idempotent, but it runs on all normal traversals.

**Suggested direction:** Track which per-edit operations succeeded during a partial restore and apply equality/idempotency checks only when recovering those checkpoints; retain the previous direct snapshot-read/write path for normal checkpoint traversal.
