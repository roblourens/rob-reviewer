# Performance review: Markdown editor: render Mermaid blocks like the Markdown preview

[PR #344399](https://github.com/microsoft/vscode/pull/344399) at `f6d4809eda8172f8c30f13189df4eecec710130d`

## Findings (1)

### 1. [medium] Lazy-load optional Mermaid add-ons

**Finding ID:** `PERF-DAC7DF9A4AC8`  
**Location:** <code>extensions/mermaid-markdown-features/preview-src/markdownEditor/index.ts:28</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** JavaScript module loading, parsing/evaluation CPU, and per-iframe addon/module objects  
**Scaling:** The cost is paid once for every instantiated Mermaid code-block iframe; documents with multiple Mermaid blocks create multiple isolated iframe realms, so parse/evaluation and retained module state grow with the number of active or parked frames even though extension-resource bytes may be browser-cached.  
**Outcome:** Increased time to first diagram render and higher CPU/memory usage when opening or scrolling Markdown documents containing Mermaid blocks.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The removed built-in guest imported only \`mermaid\`, connected to the host, initialized Mermaid, and rendered the block. It did not import or register the optional ELK, tidy-tree, or ZenUML packages.  
**Changed behavior:** The new guest statically imports the shared module, whose top-level imports include \`&#64;mermaid-js/layout-elk\`, \`&#64;mermaid-js/layout-tidy-tree\`, and \`&#64;mermaid-js/mermaid-zenuml\`, then awaits \`registerMermaidAddons()\` before \`WebEditorClient.connect\`. Thus even a basic flowchart cannot render until every iframe has loaded and initialized optional diagram support.  
**Confidence:** 0.97 — The eager call, its position before host connection, the static addon imports, the old guest comparison, and per-block iframe lifecycle are all directly visible in repository code/tests. Exact milliseconds and tree-shaken bundle size are uncertain, which limits severity, but not the mechanism or scaling.

**Causal diff evidence:** Added RIGHT line 28 places unconditional optional-addon registration on the startup critical path of each new Mermaid iframe; the deleted guest's startup path had no corresponding registration or addon imports.

Opening an experimental Markdown editor with ordinary Mermaid flowcharts now performs optional-addon startup in each diagram iframe. The iframe factory uses one isolated frame per rendered block and parks frames for reuse, so several blocks multiply and retain this work; users see slower initial rendering and more renderer-process memory.

**Evidence:** \`index.ts\` calls \`await registerMermaidAddons()\` before line 29 connects to the host. \`preview-src/shared/index.ts\` statically imports ELK, tidy-tree, and ZenUML and the helper registers all three; the lockfile shows ELK depends on \`elkjs\`/d3 and ZenUML pulls \`&#64;zenuml/core\` and its renderer/parser dependency graph. The existing browser fixture for the same \`VirtualizedIframeEmbeddedEditorFactory\` demonstrates two matching blocks create two iframes and that removed blocks leave those frames parked until disposal. The deleted \`mermaidGuest.ts\` used only \`mermaid\` and had no addon registration.

**Suggested direction:** Keep basic Mermaid startup limited to the core renderer. Split the editor entry/shared module so optional layout and external-diagram packages are dynamically imported and registered only when the block's syntax/config actually selects them (while preserving one registration per iframe), then connect and render ordinary diagrams without awaiting those packages.

- Scaling input: Edit-event frequency and Mermaid source/diagram complexity for the affected block; separate visible blocks have separate clients.

- Mechanism confidence: High for the call path and overlap behavior; insufficiently high for a distinct diff-caused performance impact beyond the reported addon initialization.

- Verdict: No additional finding: rapid-update work largely existed in the deleted guest, and the incremental parse cost is not sufficiently quantified/proven here.
