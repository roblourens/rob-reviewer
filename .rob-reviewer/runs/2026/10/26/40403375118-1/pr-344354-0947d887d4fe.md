# Performance review: Engineering - fetch Chromium build scripts through the GitHub API with fallbacks

[PR #344354](https://github.com/microsoft/vscode/pull/344354) at `0947d887d4feea4f5afcfe7d2ec35dbf0fb10cf3`

## Findings (1)

### 1. [medium] Fail over before a source can block for two minutes

**Finding ID:** `PERF-53764203F67C`  
**Location:** <code>build/lib/chromiumSource.ts:95</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** serial network requests and blocked build-agent time  
**Scaling:** Latency grows by up to 120 seconds for every earlier source that stalls before a healthy fallback; the cost is paid once per helper invocation, including independently in each Debian architecture job.  
**Outcome:** blocked critical path and increased build latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Both callers contacted raw.githubusercontent.com directly. If raw GitHub was healthy, API-host degradation could not delay dependency setup or package preparation.  
**Changed behavior:** Each download now waits for the newly preferred GitHub API request to finish or time out before trying the previously used raw GitHub URL. A slow API endpoint therefore delays a healthy raw fallback by up to 120 seconds.  
**Confidence:** 0.93 — The source order, synchronous spawnSync call, 120-second deadline, and critical-path callers are explicit in the changed code. The exact frequency of a slow-but-not-fast-failing API endpoint is uncertain, but the latency mechanism and affected build paths are deterministic when it occurs.

**Causal diff evidence:** The added loop at build/lib/chromiumSource.ts:94-95 synchronously calls each source in order; getSources adds api.github.com before raw.githubusercontent.com, and curlGet gives each call a 120-second --max-time. Both changed callers now use this helper on their critical path.

When api.github.com is degraded or filtered but raw.githubusercontent.com is healthy, cold Linux dependency installation and each architecture's Prepare deb package step gain up to two minutes of avoidable critical-path latency. Multiple sequential degraded sources can compound this delay and consume a meaningful fraction of the 50-90 minute Linux job timeout.

**Evidence:** getSources places api.github.com first when the pipeline's GITHUB\_TOKEN is present, then raw GitHub and Gitiles. downloadChromiumFile iterates these sources serially and curlGet uses spawnSync with --max-time 120. setup-env.sh invokes it before the clang update script during uncached x64 dependency setup, while calculate-deps.ts invokes it before the first dpkg-shlibdeps run during Debian package preparation. The pipelines provide GITHUB\_TOKEN in both cases. Thus an API connection that stalls while raw.githubusercontent.com remains healthy blocks progress rather than failing over promptly.

**Suggested direction:** Use a short per-source failover deadline (or hedge the next source after a short delay) while retaining the longer overall retry budget, so a healthy fallback is reached quickly without removing resilience.
