### Scenario 1: Open a session row, nested-chat row, chat-tab, section-header, group-header, automation, customization, or session-header context menu

- Critical path: A user right-click synchronously reads local observable/context-key state, constructs a small action list, sorts/joins menu groups, and paints the context menu. No subprocess, IPC, filesystem, database, or network operation is on this menu-opening critical path.
- Scaling input: Session-row menus scale with selected sessions and configured custom groups; section headers additionally scan the section's sessions/workspace folders and configured groups; tab menus scale with visible chat tabs during a tab rebuild. These are local in-memory collections and context menus are user-triggered rather than render/frame loops.
- Effective concurrency: Single synchronous UI event; menu construction is serialized on the UI thread. Header and item menu instances are disposed on hide or replacement, and tab action instances are disposed whenever tabs rebuild.
- Cache behavior: Menus are intentionally rebuilt from current context state on each opening; there is no remote cache or cache miss. Static registrations are reused, while per-opening menu/listener resources have explicit disposal.
- Mechanism confidence: High confidence in the synchronous call path and cleanup because the tree context-menu dispatcher, menu creation, action joining, and onHide disposal were traced directly.
- Magnitude uncertainty: Very large session/group collections could increase local menu-opening CPU and allocation, but realistic menus contain a bounded number of actions and the only newly added scan occurs once per right-click; there is no evidence of measurable latency or a hot-loop regression.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff mostly reorders existing actions; new header menu construction is bounded to explicit user interaction, performs only local work, and cleans up its menu resources.

### Scenario 2: Use Mark All as Read from a Date section or custom-group header

- Critical path: After the user selects the action, the list filters the target sessions and awaits ISessionsManagementService.markAllRead. That method waits for all selected provider updates before the command completes; this work is not performed merely by opening the context menu.
- Scaling input: Effective cardinality is unread eligible sessions in the selected section/group after filtering, plus unread aggregate chats for Agent Host sessions. This is less than or equal to the old Date-mode global action for the same list state.
- Effective concurrency: markAllRead uses Promise.all across target sessions. Within an Agent Host session, unread chats are updated sequentially; independent sessions can update concurrently. No new limiter or additional concurrency is introduced by this PR.
- Cache behavior: Read state is current observable/provider state and is not cached or negatively cached. There is no coalescing, but the diff narrows the target set and does not add retries.
- Mechanism confidence: High confidence from the action's filtering closure, markAllRead Promise.all implementation, and both provider implementations.
- Magnitude uncertainty: Provider latency and the number of unread nested chats vary, but the before/after cardinality comparison is clear: the changed Date workflow cannot fan out to more sessions than the removed global action.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/services/sessions/browser/sessionsManagementService.ts:1440 and src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:7289</code>: Update read state through each session provider; Agent Host dispatches read-state changes to its connection, including per-unread-chat updates when independent chat read state is supported, while the Copilot provider update is local observable state.; cardinality: One top-level update per unread, non-archived, non-automation session in the chosen section/group; Agent Host may additionally dispatch once per unread aggregate chat. Date-section cardinality is now the chosen Recent/Older section rather than all sessions.
    - Introduced by diff: true; previous behavior: In Date grouping, a session-row action marked every unread session globally. Non-Date section/group headers already exposed the same provider path. The diff moves Date-mode access to narrower section/group headers, reducing or preserving effective cardinality rather than increasing it.; critical-path effect: The action awaits all provider updates, so the slowest update controls completion; menu opening itself does not wait on this boundary.
- Verdict: No reportable regression. Although the command reaches provider/IPC boundaries with collection-scaled concurrency, the PR replaces a broader global Date action with section/group-scoped updates and therefore does not introduce or amplify the fan-out.

### Scenario 3: Run New Session, Archive/Mark All as Done, or Configure External Sessions from the newly added section/group context menus

- Critical path: Opening the menu performs no boundary work. Selecting New Session opens the existing composer/session flow; selecting Archive/Done runs the existing confirmation then serial archiveSessionsWithUndo path; configuring external sessions writes the existing user configuration value.
- Scaling input: Archive cost scales with eligible sessions in the selected section/group and active chats per session. The context-menu route supplies the same section/group object as the pre-existing toolbar route.
- Effective concurrency: Archive operations remain deliberately serial; configuration updates are single operations; session creation follows the existing single-command flow.
- Cache behavior: No new cache is added or bypassed. Existing session/provider state and configuration services remain authoritative.
- Mechanism confidence: High confidence because the new registrations point to unchanged Action2 run methods and the transitive archive/configuration implementations were traced.
- Magnitude uncertainty: Archive duration depends on provider and active-chat state, but no changed code alters that duration or multiplicity.
- Expensive boundaries:
  - other at <code>src/vs/sessions/contrib/sessions/browser/views/sessionsViewActions.ts:68 and src/vs/sessions/services/sessions/browser/sessionsManagementService.ts:1299</code>: Archive each selected session through its provider; active requests may first acquire/load chat state and cancel the request.; cardinality: One serial archive operation per non-archived session in the section/group, plus cancellation/load work only for active chats.
    - Introduced by diff: false; previous behavior: The identical Action2 command and archive implementation were already exposed from the section/group inline toolbar; the diff adds another menu entry point without changing the operation, cardinality, ordering, or concurrency.; critical-path effect: Runs only after explicit action selection and is awaited serially to preserve partial-batch undo semantics.
  - filesystem at <code>src/vs/sessions/contrib/sessions/browser/views/sessionsViewActions.ts:429</code>: Persist the external-session visibility/grouping preference through IConfigurationService.; cardinality: One configuration update when the user toggles a submenu item.
    - Introduced by diff: false; previous behavior: The same submenu and configuration action already existed in the section toolbar/filter menu; this PR only exposes that submenu in the section context menu.; critical-path effect: Awaited only after choosing the setting; it is off the context-menu opening path.
- Verdict: No reportable regression. These are alternate entry points to existing commands; expensive work remains deferred until selection and has unchanged cardinality/concurrency.

### Scenario 4: Use Close or Mark as Read/Unread from a chat-tab context menu

- Critical path: A right-click locally chooses actions from current chat/session capabilities. Selecting Close or read state invokes the shared command service and awaits the existing single-chat/session management path.
- Scaling input: Provider work is constant per click. Local tab rebuild allocation grows linearly with visible tabs; the diff adds three lightweight actions per tab to an already full DOM/action rebuild.
- Effective concurrency: One command per user activation; no burst across visible tabs. Tab rebuilds remain synchronous and only allocate/dispose local Action objects.
- Cache behavior: Capability and read-state observables are read directly; provider state is not prefetched. Per-tab actions are recreated with each rebuild and deterministically disposed by \_tabDisposables.clear().
- Mechanism confidence: High confidence from the tab listener, command invocation, tab disposable lifecycle, and management/provider paths.
- Magnitude uncertainty: Exact provider latency varies, but cardinality is provably one and the menu path is explicit user interaction.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/browser/parts/chatCompositeBar.ts:614 and src/vs/sessions/services/sessions/browser/sessionsManagementService.ts:1344</code>: Persist one chat/session read-state change through the owning provider; Agent Host can dispatch the change over its connection.; cardinality: One selected chat/session per click; no per-tab loop invokes provider work.
    - Introduced by diff: true; previous behavior: The same shared read/close commands were available from list/header surfaces, but not from this tab menu. The new tab route invokes one target and does not batch or multiply work.; critical-path effect: Awaited after the user selects the action; no provider call occurs while rebuilding tabs or opening the menu.
- Verdict: No reportable regression. The new commands add constant, user-triggered work and the added action objects have bounded lifetime with explicit cleanup.
