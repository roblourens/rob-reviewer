### Scenario 1: Open or edit an inline rich Markdown document diff containing pure additions

- Critical path: After the webview is ready, the document-diff listener awaits the version-cached text diff, converts every changed hunk to source offsets, and sends one gutter-marker notification before the new markers appear.
- Scaling input: Cost scales with document line count in the existing diff and with effective diff-hunk count H for the newly included marker objects, not with every added line (contiguous additions form one hunk).
- Effective concurrency: Each document-change event can start an asynchronous publish; identical document versions share the provider's cached promise, while newer versions may overlap and stale results are discarded. The PR does not change this scheduling or add calls.
- Cache behavior: Cold document-version pairs invoke getTextDiff once. Repeated requests for unchanged versions reuse \#cachedLineChanges, including concurrent callers; changing either document version replaces the cache. There is no persistent cross-version retention or negative-cache state.
- Mechanism confidence: High confidence in the added O(H) allocation/serialization and unchanged one-call boundary cardinality from the traced provider, cache, RPC, and webview consumer.
- Magnitude uncertainty: Very fragmented generated Markdown could produce many addition hunks, but each newly transmitted marker is a small fixed-shape object and this is the required feature output; no evidence shows material latency, rendering, or memory regression.
- Expensive boundaries:
  - IPC at <code>extensions/markdown-language-features/src/preview/lineDiff.ts:91 computeLineChanges</code>: vscode.workspace.getTextDiff computes/streams the original-to-modified text diff.; cardinality: One cold computation per original/modified document-version pair; all getters for the same pair reuse the cached promise.

- Verdict: No reportable performance regression. The bounded per-hunk work directly implements the requested gutter markers, while diff frequency, IPC count, stale-result handling, and cache lifecycle are unchanged.

### Scenario 2: Render inline or side-by-side classic Markdown previews after document changes

- Critical path: Preview refresh requests line changes and mappings; on a cold version pair it awaits the text diff, then computes preview indicators and line mappings used to render/synchronize the preview.
- Scaling input: The PR temporarily retains all H diff hunks and performs one O(H) filter before indicator splitting; downstream classic-preview indicators still include only deletion/modification hunks, and existing line/mapping work scales with changed lines/document size.
- Effective concurrency: The line-diff provider coalesces getters for the same version pair through one cached promise. Preview refresh behavior and concurrency are unchanged by the PR.
- Cache behavior: The first getter for a document-version pair computes all line changes; subsequent preview and mapping getters reuse the promise until either document version changes.
- Mechanism confidence: High confidence from direct inspection that preview outputs and expensive boundary cardinality are unchanged; only a bounded linear filter/allocation is added.
- Magnitude uncertainty: H can be large for highly fragmented diffs, but the added temporary references and one linear filter are minor beside the already-required diff iteration and arrays, with no boundary or rendered-output amplification.
- Expensive boundaries:
  - IPC at <code>extensions/markdown-language-features/src/preview/lineDiff.ts:91 computeLineChanges</code>: vscode.workspace.getTextDiff computes/streams the line and inner changes.; cardinality: One cold operation per document-version pair per diff provider; modified changes and mapping getters share it.
    - Introduced by diff: false; previous behavior: The same operation already ran and produced the same added/deleted/mapping data.; critical-path effect: Preview line-change metadata and side-by-side mappings wait for this result.
  - serialization at <code>extensions/markdown-language-features/src/preview/previewManager.ts:265 resolveCustomTextEditorInlineDiff</code>: Existing preview refresh sends rendered preview state and line-change metadata to its webview.; cardinality: One existing refresh per preview update; pure-addition line metadata was already represented by the added-line list.

- Verdict: No reportable performance regression. The additional O(H) temporary array/filter is bounded to each cold diff computation and preserves existing preview output without creating repeated boundary work or retained growth.
