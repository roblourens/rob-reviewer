### Scenario 1: Manual Run Now where the Agent Host publishes a primary session before that backend identity is advertised to the client

- Critical path: The existing runAutomation host request must return and the authoritative automation catalogue must contain the run; after the diff, client progress additionally waits for the in-memory session-resolution mapping or a terminal state. Session projection is required before AutomationRunner can complete whenDispatched with a usable session resource.
- Scaling input: Each resolution event checks the catalogue until it finds the requested run. The host initially exposes at most 50 terminal runs per automation plus active runs, though explicitly fetched history can enlarge the catalogue; effective pending-listener cardinality is the number of concurrently unresolved manual runs across distinct automations.
- Effective concurrency: One active run is permitted per automation by getActiveRunFor; different automations can run concurrently. Each unresolved manual dispatch owns one catalogue listener and one session-resolution listener, with no added subprocess or boundary concurrency.
- Cache behavior: A warm \_backendSessions identity mapping makes hasResolvedSession succeed immediately. A cold miss waits for onDidChangeSessionResolution; registration fires that event, and there is no boundary retry or negative-cache loop.
- Mechanism confidence: High confidence that the new wait and local scans are on the manual-dispatch critical path; high confidence that sessionResource resolution is an in-memory lookup and that the existing host request count remains one.
- Magnitude uncertainty: A very large explicitly expanded catalogue or many simultaneously unresolved runs could increase synchronous predicate scans, but manual dispatch concurrency and session-advertisement event frequency are normally low, and the diff adds no expensive boundary call.
- Expensive boundaries:
  - IPC/network at <code>src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts:266 runAutomation</code>: Send one manual automation run request to the local or remote Agent Host and receive catalogue updates through the existing subscription; cardinality: Exactly one runAutomation request per accepted manual dispatch; catalogue updates are subscription events rather than per-run polling calls.
    - Introduced by diff: false; previous behavior: The same single host request and catalogue subscription were used; the client returned as soon as primarySession was present or the run was terminal, without waiting for the local identity mapping.; critical-path effect: The host request and first qualifying catalogue/session-resolution update must complete before the dispatch result is exposed.
- Verdict: No reportable regression. The added latency is the intentional identity-resolution gate needed to avoid returning an unusable session, and the incremental work is bounded local event handling rather than new I/O or fan-out.

### Scenario 2: The run reaches a terminal state before its advertised session identity becomes resolvable

- Critical path: The first wait ends at terminal state, then the second local wait allows late session discovery for up to the existing 30-second mutation timeout. If identity arrives, dispatch completes; otherwise the timeout surfaces the existing failure path.
- Scaling input: Cost is one retained local wait per terminal unresolved dispatch for at most 30 seconds; predicate work scales with catalogue entries/runs on catalogue or session-resolution events.
- Effective concurrency: One timeout and one catalogue/session-resolution listener set per unresolved terminal manual dispatch. Different automations may overlap, but there is no spawned work, polling, or added remote concurrency.
- Cache behavior: A mapping already present at terminal transition resolves synchronously. A late positive registration wakes the wait. An unresolved miss is not cached and is bounded by the 30-second timeout after terminal state.
- Mechanism confidence: High confidence in the timeout, listener lifecycle, and absence of added boundary calls based on \_waitForCatalog and the new tests.
- Magnitude uncertainty: The exact incidence and delay of lost or late discovery are unknown; the test explicitly establishes the 30-second upper bound and listener cleanup.
- Expensive boundaries:
  - IPC/network at <code>src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts:292 runAutomation</code>: Observe terminal automation state over the already-open Agent Host catalogue subscription; cardinality: No additional request is sent; one existing subscription update marks the run terminal, followed only by local event observation.
    - Introduced by diff: false; previous behavior: The client consumed the same terminal catalogue update and returned immediately, potentially producing a false sessionless error before identity discovery.; critical-path effect: Terminal catalogue delivery starts the bounded identity-resolution grace period; no new boundary operation blocks it.
- Verdict: No reportable performance issue. The bounded post-terminal wait is an explicit correctness tradeoff, cleans up on every settlement path, and does not retain resources beyond the timeout.

### Scenario 3: Manual Run Now is cancelled, the provider disconnects, or the catalogue errors while identity resolution is pending

- Critical path: Cancellation fires the combined local event and forwards the existing host cancellation action when supported; disconnect disposes the connection-scoped store; catalogue errors reject the wait. These paths terminate the identity wait without requiring session discovery.
- Scaling input: Resource usage scales linearly with concurrently pending manual dispatches, with one DisposableStore and a small fixed listener set per dispatch until settlement.
- Effective concurrency: Cancellation dispatch remains at most once due cancellationForwarded. Store disposal clears all pending waits together; no retry queue or burst is added.
- Cache behavior: Session cache state is irrelevant once cancellation, disconnect, or catalogue error wins; no stale or negative cache entry is retained by the changed code.
- Mechanism confidence: High confidence because \_pendingWaits owns and disposes every listener store, and added tests assert listener cleanup for all these outcomes.
- Magnitude uncertainty: Concurrent manual runs across many distinct automations are possible but no realistic high-cardinality trigger was established in the reviewed call path.
- Expensive boundaries:
  - IPC/network at <code>src/vs/sessions/contrib/providers/agentHost/browser/agentHostAutomationStore.ts:274-286 runAutomation</code>: Optionally send one AutomationRunCancelRequested action to the Agent Host; cardinality: At most one cancellation action per manual run, deduplicated by cancellationForwarded.
    - Introduced by diff: false; previous behavior: Cancellation forwarding and connection/catalogue disposal already existed; the diff adds cancellation as a wake-up event for the identity predicates but does not add another boundary call.; critical-path effect: Cancellation can unblock the new local wait and proceeds over the same connection; disconnect/error paths complete locally through disposal or subscription error.
- Verdict: No reportable regression. Cleanup remains deterministic and the diff does not amplify cancellation I/O or retain unresolved listeners after settlement.

**Summary:** Reviewed the complete two-file diff and traced manual automation dispatch through AutomationRunner, provider stores, local/remote Agent Host boundaries, catalogue history limits, session identity registration, cancellation, timeout, and disposal. The PR adds event-driven local waiting and catalogue scans but no new IPC/network/filesystem operation, polling, concurrency burst, or unbounded retained cache. No valid performance finding was identified.
