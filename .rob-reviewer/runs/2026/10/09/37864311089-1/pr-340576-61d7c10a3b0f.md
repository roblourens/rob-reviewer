## Findings (1)

### 1. [medium] Bound deadline-driven wake polling

**Finding ID:** `PERF-BC2CF04E74CC`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxAgentHostService.ts:495</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** authenticated HTTPS \`/connect\` calls plus per-call authentication lookup, telemetry, and logging  
**Scaling:** Sequential requests grow with wake duration divided by Retry-After. At the tested one-second cadence, a 590-second wake produces roughly 500-plus calls. Normal callers coalesce to one loop per environment, so concurrency is one but cardinality is hundreds.  
**Outcome:** excessive I/O and reduced throughput under control-plane rate limiting  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The connection imposed a 5,000 ms minimum and stopped after 20 waking responses, so this scenario made at most 20 \`/connect\` calls.  
**Changed behavior:** A coalesced connection attempt now issues \`/connect\` requests for the full ten-minute deadline and honors a one-second Retry-After, rather than stopping after 20 attempts with a five-second floor.  
**Confidence:** 0.99 — The loop, delay, global deadline, network boundary, and caller coalescing are directly traced. The added test proves the long-wake cadence; only exact production response latency and rate-limit thresholds are uncertain.

**Causal diff evidence:** RIGHT line 495 replaces the 20-attempt loop with an unbounded loop; the same diff lowers the pending-response client floor from 5,000 ms to 1,000 ms. The added 590-second test explicitly asserts more than 20 sequential requests at roughly one-second intervals.

A sandbox returning \`202 waking\` with \`Retry-After: 1\` can cause roughly 500 authenticated HTTPS requests during one connect, increasing network/power use and consuming control-plane quota enough to risk rate-limiting this connection or neighboring Mission Control operations.

**Evidence:** Each \`\_mintWithWaking\` iteration calls \`CloudSandboxApiService.connect\`, which resolves the auth session and invokes \`\_requestService.request\` against the GitHub Copilot API. The loop is now attempt-unbounded, the floor is 1,000 ms, and cancellation occurs after 600,000 ms. The new 590-second test proves more than 20 calls at this cadence. This API service separately documents that a few dozen Mission Control requests can trip GitHub rate limits and starve later calls.

**Suggested direction:** Keep the overall deadline, but bound polling frequency by retaining the five-second client floor or backing off after the first few one-second polls.
