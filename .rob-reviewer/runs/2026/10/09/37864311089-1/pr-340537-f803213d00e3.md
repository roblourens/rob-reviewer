<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** boundary-fanout, concurrency-burst, cache-lifecycle, eager-work, serialization-allocation

### Scenario 1: Desktop automatic MCP authentication when an agent-host server reports AuthRequired

- Critical path: Provider lookup and, only when no matching active/persisted provider exists, OAuth metadata discovery must complete before session lookup and token forwarding can progress.
- Scaling input: Authorization-server count in one protected-resource challenge; servers are processed sequentially, and each uncached server can probe up to three well-known URLs.
- Effective concurrency: Authorization servers within one challenge are sequential. SequencerByKey serializes creation for the same dynamic provider; distinct providers may proceed concurrently. Session-handler pending operations coalesce identical in-flight attempts.
- Cache behavior: An active or persisted matching authentication provider bypasses metadata discovery. The new service adds no metadata cache, but this matches the pre-diff discovery lifecycle; failures can be retried by later auth events. Transport HTTP caching remains available.
- Mechanism confidence: High: the provider checks, keyed sequencer, call path, IPC proxy, discovery loop, and request retry policy are directly visible in the code.
- Magnitude uncertainty: Shared-process IPC and transient retry overhead vary by machine and network, but normal successful discovery adds only one small IPC exchange and retains the same network cardinality.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/electron-browser/agentHostMcpOAuthMetadataService.ts and src/vs/platform/agentHost/common/agentHostMcpOAuthMetadataService.ts:fetch</code>: ProxyChannel call from the desktop renderer to AgentHostMcpOAuthMetadataService in the shared process.; cardinality: One IPC round trip per authorization server that actually requires metadata; zero for an already active provider.
    - Introduced by diff: true; previous behavior: The renderer invoked the same discovery helper directly, with no IPC.; critical-path effect: The IPC round trip is on the provider-creation critical path, but its payload is only the parsed metadata and discovery URL.
  - network at <code>src/vs/platform/agentHost/common/agentHostMcpOAuthMetadataService.ts:fetch</code>: GET OAuth/OpenID well-known metadata through the shared-process request service.; cardinality: One successful request when the first discovery endpoint works, otherwise up to three sequential discovery endpoints; the request service can retry transient GET transport failures up to three attempts.
    - Introduced by diff: false; previous behavior: The same helper issued one to three sequential renderer fetches. The diff changes transport and adds bounded request-service transient retries, but does not increase normal successful endpoint cardinality.; critical-path effect: Discovery must finish before a dynamic provider can be created; subsequent active-provider authentication skips it.
- Verdict: No reportable regression. The added IPC is bounded and necessary to remove CORS from desktop discovery; normal network fan-out is unchanged, while extra retries occur only on bounded transient-failure paths.

### Scenario 2: Interactive desktop MCP sign-in from server customization UI

- Critical path: Starting the server, resolving or creating the provider, fetching metadata when needed, and session creation are all on the user-triggered sign-in path.
- Scaling input: The number of authorization servers advertised by the selected MCP server; iteration stops at the first successful authentication.
- Effective concurrency: Authorization servers are tried serially, and same-provider creation is serialized by SequencerByKey. Different user-triggered providers can overlap.
- Cache behavior: Existing/activated providers and matching stored client registrations avoid metadata fetches. There is no new long-lived retained metadata state.
- Mechanism confidence: High: the customization call site and provider-creation path are explicit.
- Magnitude uncertainty: Exact metadata endpoint latency and frequency of transient transport errors are provider-dependent.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts:authorizationServerMetadataFetcher</code>: Desktop metadata service invocation in the shared process.; cardinality: At most one IPC call per authorization server reached and needing provider creation.
    - Introduced by diff: true; previous behavior: Metadata discovery ran directly in the renderer.; critical-path effect: Adds a small IPC hop before the network request on first provider creation.
  - network at <code>src/vs/platform/agentHost/common/agentHostMcpOAuthMetadataService.ts:fetch</code>: OAuth/OpenID discovery GETs.; cardinality: One to three sequential discovery URLs per reached uncached authorization server, with bounded retries only for transient transport errors.
    - Introduced by diff: false; previous behavior: The renderer used the same one-to-three-URL discovery helper; only the transport location changed.; critical-path effect: Dominates first-time provider-creation latency.
- Verdict: No finding. The behavior remains demand-driven, serial per challenge, and bounded; no new collection-wide fan-out, retained cache, or unbounded allocation is introduced.

### Scenario 3: Web or Sessions MCP authentication

- Critical path: When provider metadata is absent, the delayed common service delegates discovery to IRequestService before provider creation. In browser deployments, a failed/405 browser request may fall back to the remote request channel.
- Scaling input: Authorization-server count and the same maximum of three discovery endpoint variants per server.
- Effective concurrency: Same keyed provider serialization and sequential authorization-server traversal as desktop; distinct provider keys may overlap.
- Cache behavior: Provider activation/registration remains the effective warm cache. The service itself is delayed and does not retain responses.
- Mechanism confidence: High for the service and fallback call paths; provider-specific endpoint behavior is variable.
- Magnitude uncertainty: Remote fallback prevalence depends on deployment, CORS policy, and remote connection presence.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/common/agentHostMcpOAuthMetadataService.ts:fetch via BrowserRequestService</code>: Browser request for each OAuth/OpenID discovery endpoint.; cardinality: Normally one request for first-endpoint success, up to three sequential endpoints on misses.
    - Introduced by diff: false; previous behavior: Direct fetch used the same discovery endpoint sequence.; critical-path effect: Required only for first provider creation.
  - IPC at <code>src/vs/workbench/services/request/browser/requestService.ts:\_makeRemoteRequest</code>: BrowserRequestService fallback through the remote-agent request channel after browser failure or status 405 when a remote connection exists.; cardinality: At most one remote fallback per attempted discovery endpoint.
    - Introduced by diff: true; previous behavior: Direct global fetch had no remote fallback and the authentication attempt failed after its browser-side discovery probes.; critical-path effect: Allows discovery to continue after a browser-side failure instead of terminating unsuccessfully.
- Verdict: No performance finding. The additional remote boundary occurs only to turn a previously failed discovery into a progressing authentication flow and remains bounded by the existing discovery sequence.

### Scenario 4: Workbench and shared-process startup without MCP authentication

- Critical path: Module registration occurs during startup, but renderer-side services are delayed; shared-process channel setup constructs only the thin metadata service around an already-created request service and performs no request.
- Scaling input: Constant per process/window, independent of MCP server or workspace size.
- Effective concurrency: No authentication work or network operation is scheduled at startup.
- Cache behavior: No metadata, response body, or per-server state is allocated until fetch is invoked.
- Mechanism confidence: High: constructors and registration descriptors are directly visible.
- Magnitude uncertainty: Object construction cost is negligible and contains no transitive I/O.
- Expensive boundaries: none found
- Verdict: No eager-work regression: no network, filesystem, subprocess, or IPC call is initiated merely by registration.

**Summary:** Reviewed all nine changed files and traced desktop, web/Sessions, automatic, interactive, and startup paths. The PR moves first-use metadata discovery behind a bounded IPC service on desktop and through the existing request service elsewhere, without increasing normal successful network fan-out, introducing unbounded retention, or adding eager expensive startup work. No high-confidence actionable performance regression found.
