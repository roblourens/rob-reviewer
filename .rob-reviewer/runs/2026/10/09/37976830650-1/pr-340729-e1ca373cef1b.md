# Performance review: Add built-in Markdown task progress and live widget themes

## Findings (3)

### 1. [medium] Keep ordinary code blocks from loading the iframe editor subsystem

**Finding ID:** `PERF-5F8088BFB7B2`  
**Location:** <code>extensions/markdown-language-features/markdown-editor-src/editor.ts:611</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Dynamic module bytes plus JavaScript parsing/evaluation and iframe-factory initialization  
**Scaling:** Once per live Markdown editor webview that contains at least one fenced code block, even when none use widget:task-progress; opening multiple editor webviews repeats initialization in each isolated webview context.  
**Outcome:** Increased live-editor open/render latency and CPU work for ordinary Markdown documents with fenced code  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The external provider list defaults to empty, and LazyCodeBlockEditorFactory.create only starts its dynamic import when providers.length is nonzero, so documents with ordinary fences and no contributed providers did not load &#64;vscode/markdown-editor/web-editors.  
**Changed behavior:** Appending the built-in task-progress provider makes the list permanently non-empty. The first ordinary fenced block now causes LazyCodeBlockEditorFactory to import and construct VirtualizedIframeEmbeddedEditorFactory before provider selection can reject the block's language.  
**Confidence:** 0.97 — The default empty provider state, exact providers.length lazy-load condition, unconditional added provider, and dynamic import call path are all directly traced. Only the absolute duration varies by machine and cache warmth.

**Causal diff evidence:** The added \`this.\#taskProgressProvider\` at editor.ts:611 changes \`\#createIframeProviders(\[\])\` from an empty array to a non-empty array. The unchanged lazy factory gates \`\#loadFactory()\` solely on \`this.\#providers.length\`, while the existing provider field defaults to \`\[\]\`.

Opening a live Markdown editor on a normal document containing an ordinary fenced snippet now loads and evaluates the iframe-editor implementation and constructs its factory. This delays rendering once per editor webview; warm resource caches may avoid transfer but not per-webview module evaluation/initialization.

**Evidence:** editor.ts initializes \`\#codeBlockEditorProviders\` to \`\[\]\`, passes the result of \`\#createIframeProviders\` to LazyCodeBlockEditorFactory, and the changed line always appends the built-in provider. lazyCodeBlockEditorFactory.ts:create states that creation is invoked for a block and starts \`\#loadFactory()\` whenever providers.length is nonzero; its loader dynamically imports \`&#64;vscode/markdown-editor/web-editors\`. Therefore any first fenced block, not only \`widget:task-progress\`, crosses the module-load boundary after this change.

**Suggested direction:** Preserve the lazy guard by triggering the iframe-editor import only when the current block matches an available provider (in particular, gate the built-in provider on the exact \`widget:task-progress\` language), while retaining existing external-provider selection semantics.

### 2. [medium] Load the self-contained task-progress guest only when resolved

**Finding ID:** `PERF-FD76A976CD15`  
**Location:** <code>extensions/markdown-language-features/markdown-editor-src/taskProgress/taskProgressProvider.ts:11</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Bundled HTML/JavaScript bytes and the resulting startup string allocation  
**Scaling:** A fixed duplicate guest payload is loaded and allocated once for every live Markdown editor webview, including documents with no code blocks; concurrent editor tabs multiply the retained strings, while cold opens also pay resource transfer.  
**Outcome:** Larger editor startup payload, additional parse/allocation work, and increased retained memory  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The sole editor entry did not contain a task-progress guest application, so opening a live Markdown editor loaded no task-progress HTML or guest-side WebEditorClient code.  
**Changed behavior:** The provider statically imports taskProgress.html. The build plugin first bundles taskProgressGuest.ts and its &#64;vscode/web-editors dependency into a self-contained HTML string, then emits that string as a JavaScript module; because editor.ts statically imports the provider, this opaque guest payload is included on every editor startup even though resolve may never be called.  
**Confidence:** 0.96 — The static import chain and nested bundling are explicit in the changed build and provider code. Bundle size is not measured, so magnitude is uncertain, but inclusion and per-webview allocation are deterministic.

**Causal diff evidence:** The new static import \`import taskProgressHtml from './taskProgress.html'\` at line 11 is reachable through editor.ts's static provider import. esbuild.markdownEditor.mts has one \`editor.ts\` entry and converts this HTML import to \`export default &lt;JSON string&gt;\` after separately bundling the guest.

Even a plain Markdown document with no \`widget:task-progress\` fence downloads/reads, parses as a literal, allocates, and retains the entire self-contained iframe app in its webview. The cost repeats across editor webviews and is absent before this PR.

**Evidence:** buildTaskProgressHtml.mts bundles taskProgressGuest.ts with esbuild and injects it inline into the template. taskProgressGuest.ts imports WebEditorClient from &#64;vscode/web-editors. The outer build has a single editor.ts entry; taskProgressProvider is statically imported and its static HTML import is returned by the plugin as an ordinary JS module, so splitting cannot defer this opaque string. markdownEditorProvider.ts loads editor.js for every live editor.

**Suggested direction:** Make the HTML module a dynamic import inside \`resolve\` (or emit it as a separate asset) so esbuild creates a guest chunk fetched only after an exact task-progress fence is selected.

### 3. [medium] Move full-document task recounts off the per-edit path

**Finding ID:** `PERF-67FCB2066D0D`  
**Location:** <code>extensions/markdown-language-features/markdown-editor-src/taskProgress/taskProgressProvider.ts:19</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Synchronous CPU traversal of every Markdown AST node  
**Scaling:** O(number of AST nodes) for every document observable invalidation while at least one task-progress transport is active. The shared derived value correctly keeps this to one traversal per edit rather than one per widget, but repeated keystrokes still produce repeated whole-document walks.  
**Outcome:** Additional input latency and main-thread CPU usage in large Markdown documents  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Edits updated the editor model without a task-progress-specific whole-AST traversal.  
**Changed behavior:** The new derived observable calls countTasks whenever model.document changes. Each active transport autoruns that derived value, and countTasks performs an explicit stack walk over every node before checking whether the task totals actually changed.  
**Confidence:** 0.94 — The observable dependency, synchronous autorun, exhaustive traversal, and edit reachability are directly visible and tested. The exact milliseconds depend on document size, so severity reflects magnitude uncertainty rather than mechanism uncertainty.

**Causal diff evidence:** The added expression \`derived(reader =&gt; countTasks(model.document.read(reader)))\` at line 19 directly places countTasks behind every document invalidation; added lines 47-57 show countTasks pushes every child and exhausts the full tree.

With a task-progress widget open in a large Markdown file, every keystroke or source update adds a collection-wide AST pass on the UI thread, increasing typing/paste latency even when no task changed.

**Evidence:** TaskProgressHostTransport constructs an autorun synchronously over the shared derived observable. The browser/unit tests demonstrate source replacement and checkbox edits immediately publish updated values. \`countTasks\` always walks all descendants, and only after it completes does the transport compare checked/total and suppress an unchanged message. Thus typing unrelated text in a document containing the widget still pays the full traversal.

**Suggested direction:** Coalesce document invalidations and compute from only the latest AST off the immediate edit turn, or maintain task totals incrementally from changed subtrees; continue sharing one result across all widget transports and publish the latest count.

### Scenario 1: Open a live Markdown editor for a plain document with no task-progress fence

- Critical path: The webview must load and evaluate editor.js before the live editor is usable. The new self-contained task-progress HTML is statically reachable from that entry and therefore sits on this critical path even though its provider resolve function is never called.
- Scaling input: One fixed guest payload per editor webview; memory and parse/allocation work multiply with concurrently open live Markdown editors.
- Effective concurrency: Each editor has an isolated webview context and performs its own evaluation/allocation. Browser resource caching may coalesce or cache byte reads across editors, but it does not share the resulting JavaScript heap string between webviews.
- Cache behavior: On a cold load, the enlarged editor.js must be read/transferred in full. On a warm resource cache, transfer can be avoided, but each webview still parses the module and allocates/retains the embedded HTML string. No negative-cache behavior applies.
- Mechanism confidence: High: the single entry, static import chain, nested guest bundle, and unconditional editor.js load are explicit.
- Magnitude uncertainty: The generated guest's exact compressed and in-memory sizes were not available from repository sources, so absolute startup milliseconds and bytes are uncertain.
- Expensive boundaries:
  - filesystem at <code>extensions/markdown-language-features/src/preview/markdownEditorProvider.ts:\#getHtml and markdown-editor-src/taskProgress/taskProgressProvider.ts:11</code>: Load the packaged editor.js webview resource, now containing the opaque self-contained task-progress guest string; cardinality: One editor.js resource load per editor webview, with cache reuse possible for bytes; the added payload is present for every load regardless of document content.

- Verdict: Reportable eager-startup regression because task-progress-only bytes are deterministically loaded and retained for documents that never request the feature.

### Scenario 2: Open a live Markdown document containing an ordinary fenced code block but no task-progress fence or external embedded-editor provider

- Critical path: Rendering encounters the fenced block and calls LazyCodeBlockEditorFactory.create. Because the changed provider list is now non-empty, create starts the dynamic web-editors import and later refreshes the view; this work is unnecessary for the ordinary block.
- Scaling input: Triggered once by the first fenced block per editor webview, not once per block, because \#loadStarted coalesces subsequent create calls.
- Effective concurrency: The lazy factory permits one in-flight module load per editor via \#loadStarted. Multiple editor webviews can independently load/initialize the subsystem concurrently.
- Cache behavior: Cold cache pays resource I/O/transfer plus parse/evaluation. A warm resource cache may avoid byte transfer, but each isolated webview still evaluates the module and constructs a factory. Failed loads are not retried in that factory instance because \#loadStarted remains true.
- Mechanism confidence: Very high: the list changes from empty to permanently non-empty, and the lazy guard checks only list length before importing.
- Magnitude uncertainty: Exact chunk size and device-specific load/evaluation duration are uncertain; ordinary fenced code is a common enough input that the trigger is realistic.
- Expensive boundaries:
  - filesystem at <code>extensions/markdown-language-features/markdown-editor-src/editor.ts:611 through src/preview/lazyCodeBlockEditorFactory.ts:\#loadFactory</code>: Dynamically load the &#64;vscode/markdown-editor/web-editors chunk from the packaged webview resources; cardinality: One newly reachable dynamic resource load per editor webview with at least one ordinary fence; coalesced across all fences in that editor.
    - Introduced by diff: true; previous behavior: With the default empty external-provider list, providers.length was zero and ordinary fences did not start this dynamic import.; critical-path effect: Starts during fenced-block rendering and factory completion triggers a view refresh, adding startup/render CPU and latency.
- Verdict: Reportable eager-work regression; the feature-specific subsystem now loads for unrelated code fences.

### Scenario 3: Render one or more widget:task-progress fences and edit the Markdown source

- Critical path: Initial widget rendering resolves the provider, creates an iframe/transport per live widget, and computes the document-wide task totals before publishing. On each document invalidation, the shared derived count synchronously traverses the current AST; changed totals are then sent to each ready widget.
- Scaling input: The recount is O(total AST nodes) once per document update after sharing/caching, while publication and iframe messaging scale with the number of ready task-progress widgets. Visible widgets create separate frames; the runtimeKey permits parked-frame reuse.
- Effective concurrency: The observable recount is synchronous and serialized on the webview main thread. The shared derived observable prevents one AST walk per widget. Widget initialization may have multiple visible frames, while the virtualized factory reuses parked frames; no explicit aggregate creation limiter was visible in repository-owned code.
- Cache behavior: The derived value is shared across transports for a given model update, so multiple widgets reuse one count. Any subsequent document invalidation recomputes the complete count even when totals are unchanged. Removed frames are parked and reused by runtimeKey; disposing the editor removes frames/transports. The guest HTML is self-contained and performs no guest requests.
- Mechanism confidence: High: tests and code establish synchronous immediate updates, one shared derived count, exhaustive traversal, and per-widget publication.
- Magnitude uncertainty: AST sizes and task-widget counts vary; the browser tests establish multiple simultaneous frames but not production-scale timing.
- Expensive boundaries:
  - IPC at <code>extensions/markdown-language-features/markdown-editor-src/taskProgress/taskProgressProvider.ts:TaskProgressHostTransport and taskProgressGuest.ts:main</code>: Cross-frame host-transport readiness and task-progress update messages; cardinality: One ready exchange per created widget transport and one update per ready widget when checked/total changes; unchanged totals suppress update fan-out.
    - Introduced by diff: true; previous behavior: No task-progress frames or associated cross-frame messages existed.; critical-path effect: Initial ready/update messaging is required before each widget displays current progress; subsequent messages are on the live-update path.
- Verdict: The iframe/message fan-out is intrinsic and bounded by explicit widget count, but the collection-wide recount on every edit is a reportable repeated-work regression for large documents.

### Scenario 4: Change the VS Code theme while live embedded editors are active or parked

- Effective concurrency: A single MutationObserver watches two attribute targets per editor. Delivery is browser-batched by mutation microtasks; iframe updates are managed by the factory.
- Cache behavior: Current theme CSS is regenerated from document styles on notification. Parked frames are deliberately retained and updated for reuse, then disposed with the factory/editor. There is no network, filesystem, subprocess, or database boundary.
- Mechanism confidence: High for observer reachability and lifecycle; moderate for internal per-frame implementation details.
- Magnitude uncertainty: The dependency's exact per-frame update implementation is outside repository sources, but theme changes are infrequent and allocated frame counts are user-controlled.
- Expensive boundaries:

- Verdict: No additional finding: the work is event-bounded, tied to an explicit theme change, and the observer/factory are disposed.
