<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work

### Scenario 1: Interactive Windows installer advances from task selection to the GitHub Copilot CLI choice page (basic or full variant).

- Critical path: NextButtonClick waits for the existing Copilot probe, then CopilotPreparePage constructs exactly one selected page before navigation can continue. The added SendToBack calls run synchronously during that one-time construction, but only for a fixed 6 controls on the basic page or 8 controls on the full page.
- Scaling input: Control count is compile-time bounded: 6 controls for the basic page and 8 for the full page. Only one page variant is built after the probe determines CopilotPageKind, so the added work does not scale with files, repositories, history, user data, or repeated navigation.
- Effective concurrency: All page construction and z-order updates are serialized on the installer UI thread. The probe subprocess is launched asynchronously but is explicitly awaited before page construction; the diff does not change its concurrency.
- Cache behavior: Probe launch/read and page construction are positively cached with CopilotProbeStarted, CopilotProbeRead, CopilotBasicPageBuilt, and CopilotFullPageBuilt. Returning through the wizard does not repeat SendToBack or the boundary work. There is no collection-dependent cache key or negative-cache change in the diff.
- Mechanism confidence: High confidence in the call path and cardinality: every added call is inside one-time builder helpers, all call sites and builder guards were inspected, and only one page variant is selected.
- Magnitude uncertainty: The exact native cost of each SendToBack call is not measured, but its invocation count and lifecycle are fully bounded and tiny; no realistic scaling trigger is present.
- Expensive boundaries:
  - filesystem at <code>build/win32/copilot.iss:CopilotExtractShim, CopilotWaitForProbe, CopilotReadProbeResult</code>: Extract the bundled Copilot shim to the temporary directory and poll/read the probe result INI file.; cardinality: One extraction at most, one result read, and polling every 50 ms for up to 6 seconds; guarded by CopilotShimExtracted and CopilotProbeRead.
    - Introduced by diff: false; previous behavior: The same shim extraction, result-file polling, and INI reads occurred before the diff.; critical-path effect: The result wait precedes page construction and may block advancing from task selection; the added z-order calls execute only after this existing wait.
  - subprocess at <code>build/win32/copilot.iss:CopilotStartProbe</code>: Launch copilot.exe --vscode-shim probe once without waiting directly on Exec.; cardinality: At most one probe process per installer run, guarded by CopilotProbeStarted.
    - Introduced by diff: false; previous behavior: The same single probe subprocess was launched before the diff.; critical-path effect: The process runs ahead where possible, but NextButtonClick can wait for its result for up to 6 seconds before preparing the page.
  - network at <code>build/win32/copilot.iss:CopilotStartProbe</code>: The user-installer probe may check Copilot CLI download availability; the system installer explicitly passes --no-network.; cardinality: At most one network-capable user-scope probe per installer run; no per-control or per-page fan-out.
    - Introduced by diff: false; previous behavior: The same user-scope probe could access the network before the diff.; critical-path effect: Its probe result can be on the page-navigation critical path, but the diff neither introduces nor reschedules it.
- Verdict: No reportable performance regression. The diff adds a fixed 6–8 native z-order operations during one-time page setup, with no new expensive boundary, loop amplification, cache defeat, retained growth, or repeated render path.

**Summary:** Completed the performance pass over the sole changed file and all diff hunks. Traced installer page construction, repeat-navigation guards, and the transitive probe subprocess/filesystem/network boundaries. The added z-order updates are fixed-cardinality, one-time synchronous UI setup and do not establish a concrete performance regression.
