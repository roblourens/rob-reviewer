### Scenario 1: A retained/background Copilot subagent continues markdown or reasoning streaming after its parent root turn becomes idle or is replaced.

- Critical path: An already-running provider stream delivers assistant.message\_delta or assistant.reasoning\_delta; the callback resolves the child tool-call scope, performs O(1) map lookup/update, and synchronously emits the corresponding chat action through AgentSideEffects/state management to subscribed clients. This is on the child response critical path. The diff does not add model/network requests; it permits the post-parent tail to use the same existing dispatch path instead of dropping it.
- Scaling input: Cost scales linearly with provider chunk count and concurrently live child scopes. Retained state is at most two short IDs per scope that has open markdown/reasoning content, rather than response text or history.
- Effective concurrency: SDK event callbacks are handled synchronously per delivered event. Independent children can interleave, but each child scope has one markdown ID and one reasoning ID; there is no new Promise.all burst, queue, subprocess, or boundary fan-out.
- Cache behavior: Cold child content creates one UUID and map entry; warm deltas hit the session-wide map in O(1). Entries are deleted on the child's next user message, tool-round boundary, confirmed completion, and abort completion; session disposal releases the maps. There is no negative-cache or retry behavior.
- Mechanism confidence: High: changed handlers, map insertion/deletion sites, completion/abort paths, and synchronous downstream routing were all traced.
- Magnitude uncertainty: Exact chunk rates and number of simultaneously retained children vary by model/session, but the state and dispatch cardinality are directly bounded by live stream activity.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts: wrapper.onMessageDelta/onReasoningDelta event handlers around lines 6832 and 7780</code>: Receive chunks from the already-established Copilot SDK/model event stream.; cardinality: One inbound event per provider stream chunk across active children; effective cardinality is response chunk count, not tool or repository item count.
    - Introduced by diff: false; previous behavior: The same upstream events already arrived. Events after parent-turn teardown were dropped because their part IDs were stored on the root CopilotTurn.; critical-path effect: Each event is the source of the next visible child-stream update; no new outbound model call is awaited.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_emitAction and src/vs/platform/agentHost/node/agentSideEffects.ts:\_handleAgentSignal</code>: Dispatch ChatResponsePart/ChatDelta/ChatReasoning through host state to subscribed clients.; cardinality: One initial response-part action per child content round, then one delta action per provider chunk. - Verdict: No reportable regression. The additional work is the required delivery of previously omitted child output, remains one-for-one with real stream chunks, and introduces neither redundant serialization nor unbounded retention.

### Scenario 2: A streamed child response is followed by the SDK's assembled assistant.message after the parent turn has already completed or been replaced.

- Critical path: The assembled-message callback checks the session-wide child part map before dispatch. An existing part causes the full response to be skipped; otherwise one ChatResponsePart is emitted. This check is on message-finalization but is O(1).
- Scaling input: The avoided duplicate cost scales with assembled child response bytes; lookup and retained metadata remain O(1) per message/scope.
- Effective concurrency: Per-message synchronous map access; interleaved children use distinct parent tool-call keys and do not contend on an asynchronous limiter or shared remote boundary.
- Cache behavior: The child part ID is a positive memo of an already-open response part. It survives parent turnover and is invalidated at child-owned user-message, tool-round, completion, or abort boundaries, so legitimate identical later answers miss and create a new part.
- Mechanism confidence: High for the deduplication mechanism and call path; lower only for any user-visible performance magnitude.
- Magnitude uncertainty: Response sizes vary, and no measured latency or memory symptom establishes this as a shipped performance regression rather than primarily a duplicate-output correctness defect.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:renderMessage around added lines 6842-6860</code>: Potentially dispatch a full ChatResponsePart to host state/subscribed clients.; cardinality: At most one full-part dispatch when no deltas preceded the message; zero when the same response already streamed.
    - Introduced by diff: false; previous behavior: The dispatch boundary already existed, but losing root-turn IDs made the assembled message appear unstreamed and could emit the full child answer again after parent teardown.; critical-path effect: The map check prevents a duplicate full-response allocation/state dispatch before child turn completion.
- Verdict: No finding. The diff reduces serialization/state/render work for the duplicate case and does not add a scaling mechanism. It was not recorded as a performance regression fix because the supplied evidence establishes duplicate output, not a concrete performance symptom.

### Scenario 3: Cancellation is followed by late child text/reasoning/message events, then the retained child is reused in a later turn.

- Critical path: abort marks late root events for quarantine and completes active child turns, which clears child part IDs. Late callbacks now return at the guard before UUID allocation or host dispatch; the resumed turn creates fresh IDs.
- Scaling input: Local guard cost scales linearly with the number of provider events already in flight at cancellation; retained response-part state does not grow.
- Effective concurrency: Abort iterates the pre-existing active-subagent set once; late callbacks are independently rejected synchronously. No new remote call, retry loop, or concurrent burst is added.
- Cache behavior: Abort completion deletes both child response-part entries; cancelled tails cannot repopulate them, and reuse starts cold with fresh IDs.
- Mechanism confidence: High from abort, completion, guard, and regression-test paths.
- Magnitude uncertainty: The count of late in-flight events is provider-dependent, but the changed path strictly removes downstream work.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:abort and late SDK event handlers</code>: Receive late events from the existing provider stream after cancellation.; cardinality: One callback per late provider event; all are locally dropped while quarantine is active.
    - Introduced by diff: false; previous behavior: Late provider events could still reach deeper response-part handling before existing action/drop guards rejected them.; critical-path effect: Late events are off the cancelled turn's progress path and do not cross into client state.
- Verdict: No reportable regression; cancellation now performs less work and preserves bounded lifecycle cleanup.

### Scenario 4: The retained-subagent E2E behavior snapshot compares independent parent and child action streams.

- Critical path: Only test execution is affected. Snapshot serialization projects captured AHP messages and, for this scenario, canonicalizes participating channels with a sort before reading/comparing the fixture. This is off every product/startup/rendering path.
- Scaling input: Test-only CPU scales O(n log n) with captured actions in each of three bounded rounds.
- Effective concurrency: The E2E driver performs three sequential rounds; canonicalization is one in-process O(n log n) sort over bounded captured actions, with no parallel remote burst introduced.
- Cache behavior: No product cache is touched. The recorder accumulates messages for the test and releases them with the test object; fixture I/O remains one-shot.
- Mechanism confidence: High from the changed option and canonicalizer implementation.
- Magnitude uncertainty: Exact captured action count varies slightly by provider timing, but remains test-scoped and bounded by the scenario.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/test/node/e2e/harness/ahpSnapshot.ts:assertRecordedAhpSnapshot</code>: Read/compare, or in update mode write, the YAML traffic snapshot.; cardinality: One fixture operation for this test after all three rounds; enabling orderIndependentActionTypes does not add another filesystem operation.
    - Introduced by diff: false; previous behavior: The same snapshot fixture was serialized and compared; only cross-channel ordering was strict.; critical-path effect: Affects E2E test completion only, not the shipped application.
  - serialization at <code>src/vs/platform/agentHost/test/node/e2e/harness/ahpSnapshot.ts:canonicalizeActionInterleaving</code>: Sort captured entries by channel while preserving per-channel order.; cardinality: One sort per recorded round over the scenario's captured server actions; realistic inventory is tens of actions per round.
    - Introduced by diff: true; previous behavior: With no order-independent action types, serialization returned entries without this canonicalizing sort.; critical-path effect: Adds bounded CPU/allocation to this one E2E assertion only.
- Verdict: No reportable product performance regression; the small sort is isolated to one E2E snapshot assertion.
