- Scaling input: One selected server, with form CPU/DOM work scaling with that server's argument count and environment/header rows rather than the total server inventory
- Effective concurrency: Each render may start one asynchronous resolution; renderGeneration suppresses stale completion but does not cancel or coalesce reads. This behavior is pre-existing, and only one detail is selected at a time.
- Cache behavior: Workspace-root configuration is warm from the workbench server model. Copilot-global configuration is read on each resolution with no form-level cache. The diff does not alter keys, miss handling, or coalescing.
- Mechanism confidence: High confidence from the direct renderItem -&gt; resolveSourceFormInput -&gt; resolveEditableMcpServerConfiguration call path and implementation.

### Scenario 3: Validate and save edits to a shared .mcp.json or Copilot mcp-config.json entry

- Critical path: Per-keystroke validation stays in memory. Save computes changed properties, queues access per resource, reads/parses the file, applies JSON edits, verifies an existing file with a second read, then writes once. Server-kind changes can add explicit type/transport JSON edits but not additional boundary calls.
- Scaling input: Validation/change detection scales with the selected server's properties. Filtering changed args uses a nested comparison over that server's argument list, while env/header filtering is linear in entries; saves are explicit and typical MCP argument lists are small.
- Effective concurrency: A per-resource Queue serializes saves and scans for the same canonical file; different resources may proceed concurrently. The diff does not change the queue or create a burst.
- Cache behavior: No save cache is used; every save revalidates current file contents to prevent lost updates. Equal properties produce no JSON edit/write. The diff preserves this behavior.
- Mechanism confidence: High confidence from updateMcpServer, getEditedMcpServerConfiguration, withServerTypeEdits, and withSharedMcpServersFile.
- Magnitude uncertainty: Pathological configurations with very large argument arrays could make in-memory validation quadratic, but the user-triggered path and realistic argument cardinality do not establish a concrete user-visible regression.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/mcp/common/mcpResourceScannerService.ts:241 withSharedMcpServersFile</code>: Read the shared MCP configuration, re-read it for modification detection, and write/create the updated content; cardinality: For an existing changed file, two reads and one write per explicit Save; for a new file, one failed read and one create. All property edits are grouped into that single transaction.
    - Introduced by diff: false; previous behavior: The same queued read/verify/write transaction and call count existed before the PR; explicit type/transport handling only adds up to two in-memory property edits; critical-path effect: Save remains pending until these operations complete
- Verdict: No finding: filesystem I/O count, serialization scope, grouping, and per-resource sequencing are unchanged; added CPU is bounded to one server and realistic inputs.

### Scenario 4: Open accessibility help from the MCP configuration form or update its verbosity/keybinding label

- Critical path: Form construction registers focus, configuration, and keybinding listeners and computes one ARIA label. Opening help lazily creates a short localized string provider and restores the previously focused connected element on close. This work is UI-local and has no expensive boundary.
- Scaling input: One listener set and one form DOM subtree per live embedded detail; help content is seven fixed strings and does not scale with configuration data
- Effective concurrency: All work is synchronous on UI events; no queue, subprocess, IPC, filesystem, database, or network operation is reached
- Cache behavior: No cache is relevant. The accessible provider is created on invocation and disposed by the accessible-view lifecycle; form listeners are registered to the form Disposable.
- Mechanism confidence: High confidence from the form constructor, accessibility provider, and contribution registration.
- Magnitude uncertainty: Keybinding/configuration changes may notify the live form, but there is normally one selected detail and each update performs one lookup and attribute write.
- Expensive boundaries: none found
- Verdict: No reportable regression: lifecycle is bounded to the form and all added work is constant-size.
