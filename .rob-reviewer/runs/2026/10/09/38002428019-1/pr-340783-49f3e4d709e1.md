# Performance review: Enable execution subagent by default with GPT-5.6 Luna

[PR #340783](https://github.com/microsoft/vscode/pull/340783) at `49f3e4d709e111140bbf0b19c6ca868aabf7d6f9`

## Findings (1)

### 1. [medium] Keep single commands on the direct terminal path

**Finding ID:** `PERF-365D00840537`  
**Location:** <code>extensions/copilot/package.json:4830</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** serialized model API requests and their prompt/completion token processing  
**Scaling:** For every terminal-oriented agent task that follows the now-default executionSubagent guidance, the cost grows with the nested loop's model iterations (up to the configured 10 calls); even one known command requires a subagent request to emit run\_in\_terminal and another to consume its result and emit the final answer.  
**Outcome:** increased end-to-end latency and model/network work before command results reach the user  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With the default false, execution\_subagent was absent from the parent agent's available tools. A request such as running one test command could use run\_in\_terminal directly, then make the normal parent follow-up model request after the command completed.  
**Changed behavior:** With the default true, the tool is exposed and its modelDescription explicitly says to use it instead of individual run\_in\_terminal calls and lists running tests as an example. Invocation awaits ExecutionSubagentToolCallingLoop.run(); that loop makes a model request to select run\_in\_terminal and, because ToolCallingLoop continues after a tool call, another model request to read the terminal result and produce &lt;final\_answer&gt;, all before the parent loop can continue.  
**Confidence:** 0.94 — The default-to-tool-availability path, imperative routing text, awaited nested loop, single exposed terminal tool, and one-request-per-loop-iteration behavior are all explicit in code. Exact added milliseconds and how consistently each parent model obeys the routing instruction vary by model, which limits severity rather than confidence in the mechanism.

**Causal diff evidence:** Changing the contributed setting default to true makes execution\_subagent available for users without overrides; the matching runtime default at configurationService.ts:795 causes getAgentTools() to include it on CAPI agent requests, whereas the previous false defaults excluded this path.

Common prompts such as “run the tests” or “run this command” can wait for two additional model round trips before showing a final result, even when the command is already known and needs no orchestration; multi-step executions can add further nested requests up to the 10-call limit.

**Evidence:** package.json:182-207 defines execution\_subagent with the imperative \`USE THIS INSTEAD OF RUNNING INDIVIDUAL COMMANDS WITH run\_in\_terminal\` and a run-tests example. agentIntent.ts:249-266 includes it when ExecutionSubagentToolEnabled is true. executionSubagentTool.ts:115 awaits loop.run(). executionSubagentToolCallingLoop.ts:347-363 exposes only run\_in\_terminal, and :366-390 sends each nested iteration through endpoint.makeChatRequest2. ToolCallingLoop.\_runLoop at toolCallingLoop.ts:1465-1495 repeats after any response containing a tool call, so a successful one-command execution needs one nested request to issue the command and a second to summarize its result. These requests are serialized around the terminal operation and then the parent still resumes its own loop.

**Suggested direction:** Keep the tool enabled, but remove the blanket routing instruction and direct the parent to use run\_in\_terminal for a single known command; reserve execution\_subagent for genuinely iterative command discovery or output-reduction tasks where the extra model round trips replace comparable parent-agent iterations.

### Scenario 2: Single known terminal command such as running one test command

- Critical path: The parent model selects execution\_subagent, then ExecutionSubagentTool.invoke awaits endpoint resolution and the nested loop. The nested model must first emit run\_in\_terminal; after that subprocess completes, a second nested model request consumes the result and emits final\_answer. Only then does the parent loop resume and make its normal follow-up request.
- Scaling input: One occurrence per terminal-oriented parent task routed to the tool. Added model calls scale with nested iterations; the configured loop permits up to 10 tool calls.
- Effective concurrency: The parent awaits the entire subagent; nested model request, terminal command, and summary request are serialized. The prompt explicitly prohibits parallel terminal calls.
- Cache behavior: Endpoint discovery coalesces and caches model metadata for ten minutes. The nested model requests themselves are not coalesced because each depends on the preceding tool result; provider prompt caching may reduce input processing but cannot remove their network round trips.
- Mechanism confidence: High: the default gating, routing instruction, awaited nested loop, one model fetch per loop iteration, and continuation after tool calls are explicit.
- Magnitude uncertainty: Exact latency depends on parent-model tool choice, endpoint response time, and command duration. The imperative tool description and run-tests example make the trigger realistic, while duration variability supports medium severity.
- Expensive boundaries:

    - Introduced by diff: true; previous behavior: With the tool disabled by default, the parent could issue run\_in\_terminal directly, execute the command, and proceed to its normal follow-up model request without the two nested model calls.; critical-path effect: Both requests block return from execution\_subagent and therefore delay the parent response.
  - subprocess at <code>extensions/copilot/src/extension/prompt/node/executionSubagentToolCallingLoop.ts:355-361</code>: Execute the requested command via run\_in\_terminal; cardinality: One subprocess/tool invocation for the realistic single-command case.

### Scenario 3: Iterative multi-command execution through the execution subagent

- Critical path: The parent blocks while the nested loop alternates model requests with run\_in\_terminal calls until final\_answer or the tool-call limit, then resumes its own loop.
- Scaling input: Number of commands and nested iterations, bounded by the 10-tool-call setting.
- Effective concurrency: Strictly serial: the prompt says one run\_in\_terminal per turn and the loop awaits each model and tool result. Background/time-out handling removes tools and forces finalization rather than creating a burst.
- Cache behavior: The selected endpoint is memoized within one subagent loop. Model metadata is shared/cached for ten minutes; dependent nested responses cannot be coalesced.
- Mechanism confidence: High for serialization and bounds; relative latency versus parent-only orchestration varies by task.
- Magnitude uncertainty: For genuinely iterative tasks, the compact execution model may replace similarly many parent rounds and could be beneficial; no additional finding is made beyond the clearly worse single-command case.
- Expensive boundaries:
  - network at <code>extensions/copilot/src/extension/intents/node/toolCallingLoop.ts:1465-1495 and extensions/copilot/src/extension/prompt/node/executionSubagentToolCallingLoop.ts:366-390</code>: Execution-subagent model request per nested iteration; cardinality: One serialized model request per nested iteration, supporting up to 10 terminal tool calls plus a final-answer iteration.
