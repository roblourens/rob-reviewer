## Findings (1)

### 1. [low] Overlap the tool-catalog RPC with session finalization

**Finding ID:** `PERF-B9827394620C`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:852</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** One runtime-subprocess RPC per affected session launch, plus a second full client-tool update when the runtime implementation is present  
**Scaling:** The cost repeats once for every created or resumed Agent Host session whose snapshot contains the extension-native execution tool; concurrent launches each issue their own uncached request, and the optional setTools payload grows with the session's client-tool catalog.  
**Outcome:** Increased first-turn and resume latency from an additional serialized IPC round trip (and, when available, a second tool-catalog transmission) before the session can be handed to the turn.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** After createSession/resumeSession, finalization completed script safety, sandbox, and connector reconciliation without querying the runtime tool catalog or retransmitting client tools for this feature.  
**Changed behavior:** Every launch containing \`executionSubagent\` now awaits \`session.rpc.tools.getBuiltinDescriptors\` after all other finalization work, and may then await \`setTools\`, before returning the wrapper.  
**Confidence:** 0.96 — The changed call path, one-request-per-launch behavior, subprocess RPC boundary, and first-turn blocking are directly established by production code and the new create/resume tests. Only the exact duration and affected-cohort size are uncertain, which is reflected in low severity.

**Causal diff evidence:** Added RIGHT line 852 inserts \`await this.\_configureExecutionSubagentTool(raw, config)\` into \`\_finalizeSession\`; the newly added helper at lines 866-875 performs the runtime RPC and optional \`setTools\`.

For users with the extension-native execution-subagent treatment enabled, the first prompt in each new chat and the first prompt after a persisted chat is resumed wait for this extra subprocess round trip. The same work is repeated for every session, including when the runtime execution subagent is unavailable.

**Evidence:** \`CopilotAgentSession.initializeSession\` awaits \`\_sessionLauncher.launch\` before registering the session, and both create and resume flow through \`\_finalizeSession\`. The added line 852 awaits \`\_configureExecutionSubagentTool\`; that helper unconditionally calls \`session.rpc.tools.getBuiltinDescriptors({})\` whenever \`config.tools\` contains \`executionSubagent\`, with no cache or coalescing. The added tests explicitly expect one descriptor request for every create/resume and for both runtime-default arms, confirming the multiplicity. The request is placed after the already-serialized script-safety, sandbox, and connector awaits, so none of its latency is overlapped.

**Suggested direction:** Start the descriptor request as soon as the raw session is available and await it only before returning, so it overlaps independent script-safety/sandbox/connector work. If catalog availability is stable for a client, additionally coalesce/cache it per runtime (and model where inheritance makes availability model-dependent), invalidating on client restart.

### Scenario 3: User or startup experiment changes runtime execution-subagent enablement/model

- Critical path: Workbench forwards changed settings through root-config protocol actions. Agent Host compares startup-baked configuration, waits for all active turns/subagents, disposes sessions and stops the runtime, then starts a new subprocess lazily on the next operation with updated environment defaults.
- Scaling input: Number of explicit setting or startup-treatment changes, not number of turns or sessions.
- Effective concurrency: Restart waits for zero in-flight chats/subagents; startup acquisition is coalesced, and additional config events during stopping do not create parallel runtime processes.
- Cache behavior: The replacement runtime is cold; resident session state must be resumed. Structural equality suppresses unchanged forwarded values.
- Mechanism confidence: High for the restart mechanism; low concern because it is bounded, deferred, and necessary for subprocess environment changes.
- Magnitude uncertainty: Runtime startup duration varies, but these changes are infrequent and explicitly documented as requiring restart.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCopilotCliSettingsContribution.ts:67-79</code>: Forward each setting as a RootConfigChanged action to Agent Host; cardinality: One action per changed setting; initial forwarding is suppressed when root state already has the same structural value.

  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_restartClientIfStartupConfigChanged/\_requestClientRestart/\_stopClient</code>: Stop the Copilot runtime and lazily start a replacement with new ExP environment defaults; cardinality: Startup changes are folded into the current config; pending reasons are held while work is active, and no restart runs without an existing/starting client.
    - Introduced by diff: true; previous behavior: Changes to these nonexistent settings could not restart the runtime.; critical-path effect: Never interrupts active work; the next session use can pay cold-start/resume cost after the intentional setting change.
- Verdict: No additional finding: the expensive restart is intentional, safely deferred/coalesced, and triggered only by setting changes rather than a hot path.

- Verdict: No finding: constant-size local telemetry bookkeeping does not establish a concrete performance regression.
