# Performance review: agentHost: support MCP sampling requests

[PR #340803](https://github.com/microsoft/vscode/pull/340803) at `7926288fd77e8fe9f86fb54228583c4454c66801`

## Findings (1)

### 1. [medium] Bound concurrent sampling executions

**Finding ID:** `PERF-3DE80F114A9D`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:5515</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Concurrent SDK model-inference RPCs and their retained pending request objects  
**Scaling:** With N simultaneous \`sampling.requested\` events from approved servers, the host starts N inference RPCs and retains N pending executions; there is no session-wide or per-server upper bound.  
**Outcome:** Unbounded concurrent model traffic can saturate provider capacity, reduce throughput through throttling, and delay the foreground chat turn.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, server-initiated \`sampling.requested\` events were immediately rejected through \`handlePendingSampling\`; they never crossed the \`executeSampling\` inference boundary, regardless of request concurrency.  
**Changed behavior:** Each approved request, and every request from a host-approved server, immediately starts its own SDK sampling execution. \`\_pendingMcpSamplings\` only tracks IDs for cancellation and does not bound active work.  
**Confidence:** 0.97 — The changed event callback is fire-and-forget, the execution call is directly awaited only inside each independent handler, no limiter/sequencer wraps it, and the added tests explicitly establish concurrent requests with independent confirmations. The SDK boundary is documented in the changed code as owning model selection and inference; only the number of servers that issue bursts is uncertain.

**Causal diff evidence:** Added RIGHT line 5515 invokes \`\_executeMcpSampling\` independently from every \`sampling.requested\` handler; the same diff registers the event with \`void this.\_handleSamplingRequest(e.data)\`, so handlers are not awaited or queued. Previously this event called \`\_rejectSamplingRequest\`, which performed no sampling execution.

After a user selects “Always Allow,” an MCP server that submits a batch of sampling requests can start all model inferences at once. Those calls contend with the active chat for provider/network capacity, causing throttling and increased turn latency; a larger burst also accumulates pending request state until every inference finishes.

**Evidence:** \`onSamplingRequested\` launches \`\_handleSamplingRequest\` without awaiting it; after approval, line 5515 calls \`\_executeMcpSampling\`, whose implementation immediately calls \`this.\_wrapper.session.rpc.mcp.executeSampling\`. The only shared structure is an unbounded \`Set\`. The added \`concurrent requests have independent tool confirmations\` test demonstrates that multiple sampling handlers coexist, while host-wide approval removes the only user-paced gate. Existing subsystem code uses \`Limiter\` for other fan-out boundaries, but this path has none.

**Suggested direction:** Route server-initiated sampling through a disposable session-level (or per-server plus global) limiter with a small explicit concurrency cap, preserving cancellation while queued; reject or bound excess queued requests so a server cannot grow pending state indefinitely.

### Scenario 1: Interactive or preapproved server-initiated MCP sampling

- Critical path: SDK \`sampling.requested\` event → validate/count request → identify server/read approval → emit start/ready UI state → wait for user approval when needed → \`rpc.mcp.executeSampling\` model inference → \`rpc.ui.handlePendingSampling\` response. Model inference and the final SDK response are on the server request's critical path; UI confirmation is additionally on the cold/unapproved path.
- Scaling input: Number N of concurrent \`sampling.requested\` events, especially from a server whose identity has host-wide approval.
- Effective concurrency: Each event starts an independent async handler. Unapproved calls are user-paced but multiple confirmations can remain pending; after approval, executions have no limiter and can overlap without bound.
- Cache behavior: The host reads the approval list from in-memory root state on every request and recomputes the server fingerprint; there is no sampling-result cache or request coalescing. A cold unapproved identity waits for confirmation; a warm approved identity skips that wait.
- Mechanism confidence: High: fire-and-forget event dispatch, independent handlers, direct inference RPCs, and absence of a limiter are all explicit in the changed code.
- Magnitude uncertainty: How often real MCP servers issue concurrent sampling requests is uncertain, but the approved path has no host-side cap and protocol requests can coexist, as the added concurrent-request test demonstrates.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_handleSamplingRequest line 5515</code>: Invoke SDK sampling, which owns model selection and inference.; cardinality: One model-inference RPC per approved sampling request; N simultaneous approved requests produce N calls.
    - Introduced by diff: true; previous behavior: Server-originated sampling events were rejected and made zero inference calls.; critical-path effect: The request cannot resolve until inference completes.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_handleSamplingRequest</code>: Publish synthetic tool-call state through the agent-host protocol.; cardinality: Two initial actions and one completion action per surfaced request, delivered to subscribed chat clients.

    - Introduced by diff: false; previous behavior: The same boundary was called once per event, always without a response to reject it.; critical-path effect: Completes the original server request after inference or denial.
- Verdict: Reportable medium-severity concurrency burst: after approval, N events immediately produce N expensive model calls and N retained pending executions.

### Scenario 2: Persisting and revoking sampling approval

- Critical path: User chooses “Always Allow” → synchronous root-state update → sampling proceeds. The queued filesystem persistence is launched without awaiting it, so disk completion is off the sampling critical path.
- Scaling input: Number of distinct server identities the user permanently approves.
- Effective concurrency: Root-config file writes are serialized by \`\_rootConfigWrite\`; concurrent approvals for the same identity observe the synchronously updated state and avoid duplicate writes.
- Cache behavior: Approval identity is persisted once and subsequently read from in-memory root config; duplicate identities avoid another write. There is no negative cache beyond absence from the list.
- Mechanism confidence: High for the write path and its off-critical-path placement.
- Magnitude uncertainty: The root configuration's total size varies, but approvals are explicit user actions and writes are serialized and deduplicated by identity.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/agentConfigurationService.ts:updateRootConfig/persistRootConfig, called from copilotAgentSession.ts:6408-6412</code>: Serialize root configuration and write the host config file.; cardinality: At most one filesystem write for each newly approved server identity, rewriting the root config file.
    - Introduced by diff: true; previous behavior: No sampling approval setting was persisted.; critical-path effect: Off the sampling critical path because \`updateRootConfig\` does not await persistence.
- Verdict: No additional finding: writes are user-paced, deduplicated, serialized, and off the inference critical path.

### Scenario 3: Publishing successful sampling results in chat

- Critical path: Inference result → resolve original SDK request → stringify result for the tool completion → dispatch/store completion. Serialization occurs synchronously before completion publication.
- Scaling input: Successful response byte size and number of sampling calls retained in a turn/history.
- Effective concurrency: Serialization occurs independently in every sampling handler and therefore can overlap across a burst, though each individual stringify is synchronous on the event loop.
- Cache behavior: No result cache is used; every approved request returns a fresh model response. The completion action retains a formatted copy in chat state.
- Mechanism confidence: High that the copy is made and retained; lower confidence that realistic individual response sizes alone create material degradation.
- Magnitude uncertainty: Normal response sizes are bounded in practice by the server's requested token limit, and repository evidence does not establish commonly large outputs; this kept the concern below the reporting threshold as a separate issue.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts line 5556</code>: Pretty-print the full sampling response into text content.; cardinality: One full JSON serialization and one chat action per successful sampling response.
    - Introduced by diff: true; previous behavior: Server sampling was rejected, so no response was serialized into chat state.; critical-path effect: Synchronous serialization precedes UI completion; the action is then published to clients and retained in the turn state.
- Verdict: No separate finding: the allocation mechanism is real but material impact beyond the reported burst is not sufficiently established.

### Scenario 4: Sampling cancellation and session teardown

- Critical path: Chat abort, session disposal, or SDK \`sampling.completed\` → cancel token and issue \`cancelSamplingExecution\` for active executions. Cleanup is not required to await remote cancellation before the chat stops.
- Scaling input: Number of active executions at abort/disposal.
- Effective concurrency: Cancellation RPCs are launched in parallel, one per active execution; their cardinality is inherited from the unbounded execution burst.
- Cache behavior: No cache is involved. Pending IDs are tracked in sets/maps only for ownership and cancellation.
- Mechanism confidence: High: disposal map, linked cancellation tokens, and cancellation RPC paths are explicit and tested.
- Magnitude uncertainty: Remote cancellation duration is irrelevant to teardown latency because calls are not awaited; burst cardinality remains covered by the concurrency finding.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_completeSamplingRequest and \_cancelPendingMcpSamplings</code>: Cancel model sampling executions in the SDK.; cardinality: One SDK cancellation RPC per active sampling execution.
    - Introduced by diff: true; previous behavior: Server sampling created no executions to cancel; direct MCP App executions were already tracked and cancelled on teardown.; critical-path effect: Best-effort and not awaited during teardown; it does not block chat cancellation.
- Verdict: No separate cleanup finding: ownership and late-result suppression are present; cancellation fan-out is a consequence of the reported unbounded execution fan-out.

- Critical path: MCP App \`sampling/createMessage\` → \`rpc.mcp.executeSampling\` → return SDK result. The PR adds cancellation racing/tracking around the existing boundary.

- Magnitude uncertainty: App request frequency is unknown, but PR causality for additional work is absent.

    - Introduced by diff: false; previous behavior: The old implementation already called \`rpc.mcp.executeSampling\` once per request.; critical-path effect: Inference remains on the request's critical path.
- Verdict: No finding: expensive-boundary cardinality is unchanged and cancellation is better bounded.
