### Scenario 1: Open a cloud sandbox with cached or recorded history while live Agent Host hydration succeeds or fails

- Critical path: Recorded history loading and live provider hydration start concurrently; the first authoritative source completes the open. On a successful live hydration, history is cancelled off the critical path. On a failed live hydration, the changed code keeps recorded history as the authoritative source rather than accepting the failure transcript.
- Scaling input: Number of simultaneously opened sandbox resources and transcript event/turn count; effective network cardinality is one history fetch per task, not one per reader or turn.
- Effective concurrency: One live attempt per sandbox entry and one recorded-history attempt run concurrently. Duplicate readers share the entry; history fetches are additionally coalesced per task. Retries are serialized by liveRequested/historyRequested guards.
- Cache behavior: A positive cached transcript can render immediately while one fresh request runs. Empty/missing cache results do not masquerade as positive history. The change preserves cache and pending refresh on rejected live hydration; successful live promotion retains existing invalidation behavior.
- Mechanism confidence: High: call flow, request guards, cache coalescing, and disposal are explicit in the inspected implementation and tests.
- Magnitude uncertainty: Agent Host subscription and history endpoint durations vary by connectivity and transcript size, but the diff does not add calls or increase their effective cardinality.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts:getSessionHistory/\_fetchSessionHistory</code>: Fetch and replay the task's persisted AHP event history; cardinality: At most one in-flight fetch per task after CloudSandboxHistoryCache coalescing; cached history may provide an immediate preview while the single fresh fetch continues.
    - Introduced by diff: false; previous behavior: The fetch already ran in parallel, but a failed live snapshot could be accepted as live, cancel the fetch, and invalidate its cache.; critical-path effect: Cold opens can wait for this fetch; warm opens can render the cached snapshot first. After a live failure, the request remains relevant and can complete the open.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:provideChatSessionContent</code>: Subscribe to Agent Host session state and then the selected default or peer chat state; cardinality: One shared session subscription plus one selected chat subscription per backend session/chat; existing subscription maps reuse successful subscriptions.
    - Introduced by diff: false; previous behavior: The same subscriptions were attempted, but their failure was rendered into a session that the sandbox facade treated as a successful live snapshot.; critical-path effect: Live promotion waits for subscription hydration; failure now causes that candidate session to be rejected and disposed.
- Verdict: No reportable regression. The diff removes erroneous cache invalidation/cancellation on failed live hydration and adds only constant-size metadata and disposal tracking.

### Scenario 2: Open a missing root sandbox session and decide whether it can be initialized lazily

- Critical path: When the live session subscription returns NotFound, the changed code waits for the already-running recorded-history result before allowing lazy initialization. A cached accepted history resolves this immediately; a cold result can place the history request on the open critical path. The live attempt remains bounded by its existing 30-second cancellation timer.
- Scaling input: One decision per opened root sandbox; history parsing scales with the task event stream, while network cardinality remains one per task.
- Effective concurrency: The live NotFound attempt and recorded read start concurrently. The new await joins the existing recorded read rather than starting another request; retries remain guarded and the pending live session is disposed on failure/cancellation.
- Cache behavior: Warm valid cached history settles the entry before the NotFound decision. Cold, empty, failed, and truncated outcomes remain distinct; failed/truncated reads do not authorize initialization.
- Mechanism confidence: High: the new await, cache states, coalescing, cancellation, and timeout are directly visible.
- Magnitude uncertainty: A cold history request can noticeably delay this rare recovery path, but duration depends on network conditions. There is no compatible cheaper authoritative source shown in the repository, and the wait is required by the change's preservation semantics.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:provideChatSessionContent</code>: Attempt Agent Host session subscription, which reports NotFound; cardinality: One live attempt for the sandbox entry, with duplicate opens sharing the entry.
    - Introduced by diff: false; previous behavior: The same subscription ran, but its NotFound result could be accepted immediately as an empty live session.; critical-path effect: The NotFound result no longer completes the open by itself; it gates on recorded history to avoid overwriting a preserved conversation.
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts:\_fetchSessionHistory</code>: Fetch persisted task history to prove that no conversation exists; cardinality: One coalesced request per task, with a warm positive cache delivered before the fresh response.
    - Introduced by diff: false; previous behavior: The request ran concurrently but could be cancelled when the failed live result was accepted.; critical-path effect: The diff moves this already-running request onto the critical path only for a root NotFound result that might otherwise erase recorded history.
- Verdict: No finding. This is an intentional correctness validation on a narrow failure path, reuses an in-flight coalesced request, and has no bounded alternative that preserves the required authority check.

### Scenario 3: Close or cancel a sandbox while failed live hydration is waiting for recorded history

- Critical path: Cancellation disposes the sandbox entry, cancels both the recorded read waiter and live token, and clears the pending live session/subscriptions; this cleanup is off the success critical path.
- Scaling input: Number of concurrently active sibling chats for the same backend session; cleanup checks existing holds and releases a constant number of owned subscriptions.
- Effective concurrency: Cleanup is token-driven and idempotent through disposable stores. A per-session hydration count prevents one failed candidate from tearing down a sibling's shared subscription.
- Cache behavior: Cancellation releases only this reader. Shared cache work survives while another waiter remains; no negative failure result is pinned.
- Mechanism confidence: High: ownership and disposal paths are explicit and covered by the added cancellation assertions.
- Magnitude uncertainty: The number of simultaneously open sibling chats is product-dependent, but the changed cleanup reduces rather than increases retained resources.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxHistoryCache.ts:load release path</code>: Cancel the outstanding task-history waiter and, when it is the final waiter, its shared request; cardinality: One waiter release; underlying request cancellation occurs only when no task waiters remain.
    - Introduced by diff: false; previous behavior: Entry disposal already cancelled history; the diff avoids prematurely cancelling it merely because live hydration failed.; critical-path effect: Does not block closure; cancellation propagates through tokens.
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:\_releaseChatSessionSubscriptions</code>: Dispose failed Agent Host session/chat subscription references; cardinality: At most the shared session/default-chat references and one peer-chat reference for the failed candidate; shared subscriptions remain while sibling holds exist.
    - Introduced by diff: true; previous behavior: When failure occurred before chat URI resolution, the disposal callback skipped subscription release and could retain the failed subscription ownership.; critical-path effect: Synchronous map/ref cleanup during disposal, with no new remote request.
- Verdict: No regression. The added pending-session owner and unconditional release call close prior cleanup gaps without introducing repeated remote work or unbounded retention.

### Scenario 4: Load a truncated recorded replay whose requested root session is absent or present

- Critical path: The existing history network request and replay complete before the read-only handler validates whether the requested session is represented. The changed predicate rejects an absent requested root but continues to render an included partial transcript.
- Scaling input: Predicate cost is constant after the existing session lookup; replay/folding remains proportional to event and transcript size as before.
- Effective concurrency: Unchanged; cache coalescing and the session entry guards control parallel work.
- Cache behavior: Truncated histories are not committed to the persistent in-memory history cache. The changed validation does not alter that policy.
- Mechanism confidence: High: the changed line and transitive fetch/cache code are direct.
- Magnitude uncertainty: None material for the changed predicate; it adds only boolean checks.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxReadOnlySessionHandler.ts:provideChatSessionContent</code>: Fetch the task event replay used by the validation; cardinality: One coalesced fetch per task, unchanged by the predicate.
    - Introduced by diff: false; previous behavior: The same replay was fetched, but a truncated response lacking the requested root could be treated as an empty conversation.; critical-path effect: The validation runs after the existing fetch; it adds no boundary call.
- Verdict: No performance regression; the changed predicate adds no I/O, fan-out, retention, or meaningful CPU work.
