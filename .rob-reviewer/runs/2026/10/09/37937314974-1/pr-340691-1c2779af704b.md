## Findings (1)

### 1. [low] Apply the plugin query before starting the default marketplace load

**Finding ID:** `PERF-358AB21432EA`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagement.contribution.ts:795</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Marketplace HTTP requests (and clone-backed marketplace discovery for private repositories)  
**Scaling:** On a cold deep link, the work grows from one fetch per configured plugin marketplace to two concurrent fetches per marketplace when the initial snapshot takes longer than the 400 ms search delay.  
**Outcome:** Duplicated network/subprocess work and additional contention before plugin search results appear  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Opening/selecting Plugins started its normal unfiltered marketplace snapshot; the command did not then deterministically enqueue a second marketplace fetch with a programmatic query.  
**Changed behavior:** After selecting Plugins, the new branch immediately sets the search input. Selection first makes PluginListWidget visible, whose refresh renders the home page and starts queryMarketplaceSnapshot(); the input change then schedules queryPluginSearch() 400 ms later.  
**Confidence:** 0.94 — The selection-to-snapshot and query-to-search call paths, distinct cancellation tokens, 400 ms overlap window, default legacy-marketplace setting, and lack of in-flight coalescing are all explicit in the repository. Exact cost varies with cache warmth, configured marketplace count, and request duration, which is why severity is low.

**Causal diff evidence:** The added RIGHT line 795 invokes \`pane.setSearchQuery(searchQuery)\` only after RIGHT line 793 has selected and made the target section visible, deterministically creating the second plugin-marketplace request path for searched deep links.

Opening \`vscode://chat-customizations/open?page=plugins&search=...\` from a cold cache can fetch every configured marketplace twice. Slow GitHub requests or clone-backed private marketplaces make the two requests overlap, wasting bandwidth/process work and competing with the request that supplies the visible search results.

**Evidence:** \`selectSectionById\` calls \`updateContentVisibility\`, which calls \`PluginListWidget.setVisible(true)\`; that calls \`refresh()\`, then \`filterPlugins()\`/\`renderPluginHome()\`, and \`queryMarketplaceSnapshot()\` calls \`fetchMarketplacePlugins\`. The added \`pane.setSearchQuery(searchQuery)\` changes the input, whose listener schedules \`queryPluginSearch()\` after 400 ms; that method independently calls \`fetchMarketplacePlugins\`. The search listener cancels only \`marketplaceCts\`, while the first request is owned by \`marketplaceSnapshotCts\`, and PluginMarketplaceService has a completed-result cache but no in-flight coalescing, so cold overlapping calls fan out independently across configured marketplaces.

**Suggested direction:** Populate the PluginListWidget query before making the section visible (for example, pass the query through \`selectSectionById\` and set it before \`updateContentVisibility\`), or explicitly cancel/reuse the in-flight snapshot so the searched deep link performs only one marketplace fetch.
