## Performance regression fixes detected (1)

### 1. serialization-allocation

**Fix location:** `src/vs/platform/github/common/client/schema.ts:145` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/github/common/client/schema.ts:123`  
**Introducing path:** `src/vs/platform/github/common/schema.ts`  
**Introducing commit:** `e63c52742b08f197ca9127f931531f1b11f4b4c2`  
**Mechanism family:** `serialization-allocation`  
**Performance category:** `gc`  
**Confidence:** 0.92

**Mechanism:** Schema validation allocated a duplicate object for every nested API record even when no value changed, scaling allocations with records across collected pages.

**Symptom:** Avoidable allocation and GC pressure while validating large nested or paginated GitHub API responses.

**Fixed behavior:** Unchanged plain API objects are returned by reference, with a shallow copy created only when parsing transforms a field.

**Evidence:** Base line 123 eagerly allocated a fresh result object for every parse.object call. This parser is recursively composed for nested API records and paginated lists that can collect up to 100 pages of 100 entries, so unchanged responses created one duplicate object per parsed record. Added line 145 reuses a plain input record and copies only if a declared field is transformed. Blame identifies the eager allocation as introduced by e63c52742b08f197ca9127f931531f1b11f4b4c2.

- Mechanism confidence: High: direct call flow shows the metadata object reaches the same provider and boundary exactly once.
- Magnitude uncertainty: The added shallow destructure allocates one metadata object, but it replaces the top-level object that parseRequest previously allocated, so no net per-request allocation regression was established.
- Expensive boundaries:
