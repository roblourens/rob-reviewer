# Performance review: sessions: Render artifact details, Autopilot, and activities

[PR #343003](https://github.com/microsoft/vscode/pull/343003) at `f81b1adb97d3b51075c6983d07f030a89b9053e2`

## Findings (3)

### 1. [medium] Bound integration discovery instead of acquiring every artifact at once

**Finding ID:** `PERF-476131518AEB`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sessionArtifacts.ts:614</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** IPC requests plus integration-provider match and model-initialization work  
**Scaling:** On each cold session ownership change, cost grows with every recorded artifact having a link or URI; each artifact acquisition then iterates every registered integration, so provider matching scales as artifacts × integrations, while all artifact acquisitions are launched concurrently without a shared limiter.  
**Outcome:** Excessive IPC/provider work and contention during session activation, increasing session-open latency and reducing extension-host or remote-agent throughput.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The toolbar previously built grouped artifact/reference pill data without acquiring an artifact integration model for each record, so opening a session generated no per-artifact integration subscriptions or provider-match sweep.  
**Changed behavior:** The new autorun loops over all session artifacts and immediately calls acquireArtifactIntegration for every linked/URI record, retaining successes for the session but starting all cold acquisitions in one burst.  
**Confidence:** 0.99 — The changed call, cold-session loop, provider delegation, IPC protocol request, per-registration match loop, and absence of a shared concurrency limiter are all directly traced. Exact session artifact counts and provider match duration vary, so severity is medium rather than high.

**Causal diff evidence:** Added line 614 invokes \`\_sessionsManagementService.acquireArtifactIntegration(current, artifact.id)\` from the newly added loop over the complete session artifact collection; before this hunk the toolbar performed no such per-artifact acquisition.

Opening an artifact-heavy agent session (for example one recording many files, links, images, and commits) now sends one acquisition per record; remote acquisition is an IPC subscription, and local model initialization invokes every registered integration's asynchronous match for each record. This background burst competes with opening and using the chat even when the user never opens an artifact pill.

**Evidence:** The changed loop accepts every artifact with link or URI and invokes acquireArtifactIntegration. That service delegates to the provider; AgentHostArtifactIntegrations.acquireArtifact calls access.acquireArtifact (and can additionally acquire the local fallback), ArtifactIntegrationClient sends a distinct \`acquire\` transport request per call, and ArtifactModel.initialize/refresh iterates all registry integrations whose ArtifactBinding.initialize calls each integration's async \`match\`. The toolbar test uses four records and the implementation acquires all four before any integration contribution is known. Successful models are cached only by the new lifetime map; failures are removed and can be retried after subsequent session-change events.

**Suggested direction:** Preserve integrated-pill behavior but put discovery behind a shared bounded queue (prioritizing visible records) and avoid re-running no-match work until the artifact or integration-registry revision changes; if possible, batch candidate discovery per session rather than opening one subscription per artifact.

### 2. [medium] Build artifact action detail lists only after expansion

**Finding ID:** `PERF-9ED21DA4B3EC`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatArtifactActionContentPart.ts:128</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** WorkbenchList instances, DOM nodes, event listeners, item arrays, and synchronous layout work  
**Scaling:** For every currently rendered artifact-action request row, construction scales with every captured detail section and up to 200 items per section; the details-array count is not capped, and virtualizing then re-rendering a row recreates this work.  
**Outcome:** Higher chat-history render/scroll latency plus avoidable CPU, allocation, and GC pressure, with potential dropped frames when several automation requests are visible.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Artifact-integration requests previously fell through the system-initiated request renderer to the lightweight notification/text presentation; they did not construct structured detail sections or WorkbenchList widgets.  
**Changed behavior:** The new specialized request part starts collapsed but its constructor still loops through the complete snapshot, creates a WorkbenchList for every nonempty detail section, splices all items, and lays each list out before the user expands the card.  
**Confidence:** 0.99 — The collapsed state, synchronous constructor path, item cap, unbounded detail-section multiplicity, and virtualized-row disposal/recreation are directly traced. The exact frame cost depends on snapshot size and viewport history density, reflected in medium severity.

**Causal diff evidence:** Added line 128 synchronously instantiates a \`WorkbenchList\` inside the constructor's loop over snapshot details, despite the shared card having already initialized itself as collapsed.

Recurring automatic artifact actions can place several compact collapsed cards in one viewport (the fixture exercises three). Merely opening or scrolling the chat now constructs all hidden detail list infrastructure; each section may carry 200 validated items even though CSS hides the entire body until disclosure.

**Evidence:** ChatActionRequestContentPart calls \`setExpanded(false)\` during construction. ChatArtifactActionContentPart then iterates every \`presentation.details\`; line 128 instantiates WorkbenchList, line 139 inserts the full item array, and line 141 performs layout immediately. Validation caps each detail at 200 items but does not cap the number of details. ChatListRenderer owns the part in \`elementDisposables\`, which are cleared when a row is virtualized, so revisiting the row rebuilds it.

**Suggested direction:** Render only the header initially and create the details DOM/list widgets on first expansion; retain them while that row remains rendered, and dispose them with the row as today. Keep accessible text generated from the snapshot so accessibility does not require eager visual widgets.

### 3. [medium] Acquire only the detail section needed for the initial panel

**Finding ID:** `PERF-FB0841D7FF2E`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/artifactDetailsModel.ts:106</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Artifact-details IPC subscriptions and provider detail models  
**Scaling:** One panel open starts one acquisition for every distinct \`(integrationId, detailsId)\` referenced by all contributions' main, sections, and lists; cardinality is deduplicated by that key but is otherwise unbounded by validation, and all requests begin concurrently.  
**Outcome:** Excessive IPC/provider work and contention when opening artifact details, delaying the main visible details and increasing remote/local provider load.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no artifact details context panel on this path and therefore no set of detail subscriptions opened from a pill click.  
**Changed behavior:** Constructing ArtifactDetailsModel gathers every main/section/list details ID and creates an ArtifactDetailsLease for all of them immediately, even though the panel initially displays only the main details and one selected list.  
**Confidence:** 0.98 — The fan-out, key-level deduplication, test-observed count, protocol boundary, and panel-click reachability are directly established. Provider-side duration is variable, so the finding remains medium severity.

**Causal diff evidence:** Added line 106 creates a new \`ArtifactDetailsLease\` for each entry in the full \`wanted\` map; each new lease immediately starts \`acquireDetails\`, placing all tabs/sections onto the click path.

A single click on an integrated pill opens all tab and section subscriptions at once. The added tests demonstrate three acquisitions for the normal main/checks/comments panel and six when another provider contributes details; remote models map each lease to a separate \`details\` transport request, so providers with more lists amplify click latency and service load.

**Evidence:** Lines 95-98 add every main, section, and list details ID to \`wanted\`; line 106 constructs a lease for every key, and the lease constructor immediately calls \`presentation.model.acquireDetails\`. ArtifactIntegrationClient.acquireDetails sends an individual protocol request/subscription, while provider detail models are retained until panel disposal. The test \`main click opens full details\` asserts \`acquired: \['main', 'checks', 'comments'\]\`, proving inactive details are fetched on the initial click rather than selection.

**Suggested direction:** Initially lease the main details plus the explicitly requested/selected section, then acquire an inactive tab's details when it is selected (retaining loaded leases for the open panel). Queue any remaining prefetch with a small shared limit rather than starting every subscription together.

Failed acquisitions are removed and can be retried after later session-change events. Retained models refresh against registry changes.

### Scenario 3: Open or scroll a chat transcript containing automatic/manual artifact action requests

- Critical path: Rendering each visible request row is synchronous on the UI path. The card header is all that is visible initially, but complete hidden detail sections and lists are constructed before the row can finish rendering.

- Effective concurrency: Work is synchronous and serialized on the renderer/UI thread. Chat row virtualization bounds simultaneously retained rows, but disposal clears the parts and revisiting a row recreates them.
- Cache behavior: No lazy visual cache exists before expansion. A rendered row retains its widgets until virtualized; once disposed, re-rendering rebuilds all hidden lists. The persisted snapshot itself is already available and needs no boundary call.
- Mechanism confidence: High: the card is explicitly collapsed first, followed by synchronous per-section WorkbenchList creation, full splice, and layout; virtualization disposal is directly traced.
- Magnitude uncertainty: Most snapshots are small, but recurring automation can produce multiple cards and providers may include several 200-item sections; exact WorkbenchList construction/layout duration is environment-dependent.

- Verdict: Reportable regression: hidden visual details are eagerly built on the transcript render/scroll path.
