### Scenario 1: Copilot Agent Host startup and periodic model-catalog refresh, including publication to the picker and refresh of active-session model configuration

- Critical path: The existing refresh awaits SDK model listing and then managed-settings resolution before projecting the catalog and publishing it. Publication then schedules the pre-existing per-live-session configuration refreshes. The diff adds only in-process Fusion-tier selection and one optional metadata string; it adds no awaited step.
- Scaling input: Catalog size M, managed source-layer count L, Auto routing-tier count T, and active session count S. Existing publication is O(M) and existing session refresh fan-out is O(S). New policy work is effectively O(L + T) for the single Auto model, not O(M\*L), and metadata adds at most one scalar per Auto tier.
- Effective concurrency: Model listing and policy resolution remain sequential. Concurrent managed-settings requests for the same runtime/token/workspace are coalesced while in flight. Active-session configuration refreshes remain independently queued per session; the diff neither increases their count nor creates a new aggregate burst.
- Cache behavior: CopilotManagedSettingsResolver still coalesces only in-flight requests keyed by runtime, token, and working directory; freshness and any persistent cache remain runtime-owned. Cold and warm behavior are unchanged by retaining \`layers\` and reading Fusion metadata.
- Mechanism confidence: High confidence: changed hunks and callers show bounded array scans/object fields only, while every remote call and session fan-out is in unchanged control flow.
- Magnitude uncertainty: Exact catalog, layer, tier, and live-session counts vary, but the changed work is bounded to one Auto model and does not multiply the existing remote operations.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_refreshModels/\_listModels</code>: List the Copilot model catalog through the SDK/runtime; cardinality: One existing model-list operation per refresh attempt, with the existing retry policy; independent of model or tier count.
    - Introduced by diff: false; previous behavior: The same model-list call already occurred before managed model defaults were projected.; critical-path effect: Must finish before the refreshed picker catalog can publish.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotManagedSettings.ts:resolveCopilotManagedSettings</code>: Resolve managed settings through the Copilot runtime; cardinality: One existing call per refresh unless an identical request is already in flight and coalesced.

  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_publishModels</code>: Publish the model catalog from Agent Host to workbench consumers; cardinality: One existing catalog publication per triggering refresh/change; payload gains only an optional short \`fusionTier\` string on Auto tier records.

- Verdict: No reportable regression. The added CPU/allocation and serialized bytes are small and bounded, and no expensive-boundary cardinality or critical-path ordering changes.

### Scenario 2: Creating a new Copilot Agent Host chat or changing an existing chat to/from Auto under managed Fusion policy

- Critical path: Policy resolution remains awaited before the existing session creation or model-change RPC. The changed helpers scan managed layers and Auto tiers synchronously, then alter whether an \`autoTier\` value is supplied; they do not add another runtime query or model operation.
- Scaling input: One model selection per create/change, with small source-layer and Auto-tier arrays. Cost does not scale with conversation history, prompt size, or number of models.
- Effective concurrency: Model changes remain serialized by the per-chat turn queue. Identical concurrent managed-settings requests are coalesced in flight by token/workspace; different workspace keys remain independent exactly as before.
- Cache behavior: No new cache exists or is needed for the bounded local scans. The runtime continues to own policy freshness, and the existing resolver's positive in-flight coalescing and lack of persistent caching are unchanged.
- Mechanism confidence: High confidence: direct call-path inspection establishes the same RPC count, queueing, and resolver coalescing before and after the diff.
- Magnitude uncertainty: Runtime latency varies by workspace and client state, but none of that latency is newly invoked or repeated by this change.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:resolveCopilotSessionManagedSettings and src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_changeModelOnce</code>: Resolve workspace-scoped managed settings; cardinality: One existing resolve per create/change path, coalesced only when an identical request overlaps.

  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:\_createSession/\_finalizeSession</code>: Create a Copilot session, including its existing fixed initialization sequence; cardinality: One create call per new chat plus the pre-existing fixed setup RPCs; independent of Fusion tier resolution.

  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:setModel</code>: Optionally synchronize changed BYOK provider state, then set the model on the live session; cardinality: At most one pre-existing provider sync when BYOK state changed, followed by one existing \`session.setModel\` RPC per model change.

- Verdict: No reportable regression. The functional policy mapping changes RPC parameters, not boundary count, concurrency, or retained state.

### Scenario 3: Workbench startup and managed-settings changes updating Auto defaults in chat model configuration stores

- Critical path: Native/file/server policy services populate an in-memory effective settings bag. Each store's existing managed-settings listener now performs one additional property read, and later schema/configuration reads perform one additional boolean check. No layout read/write or remote operation was moved onto picker rendering.
- Scaling input: Number of watched policy definitions D and open configuration stores/overrides C. Registering Fusion adds one static definition and one scalar to existing payloads; a rare policy event still triggers the existing O(C) listener/override processing.
- Effective concurrency: Native watcher creation remains serialized through its existing Throttler; file refresh remains coalesced by a 500 ms ThrottledDelayer; IPC emits one existing update event. The diff adds no listener, task, or parallel request.
- Cache behavior: After initialization, \`getManagedSettings()\` returns the existing in-memory object and \`getManagedSettingValue()\` is a direct lookup. Cold initialization and warm event handling use the same caches and event coalescing as before.
- Mechanism confidence: High confidence: getters are direct in-memory accesses, and source services show unchanged watcher, file-read, throttling, and IPC-event counts.
- Magnitude uncertainty: The number of open chat editors varies, but Fusion policy updates are infrequent and the diff adds constant work per existing listener invocation.
- Expensive boundaries:
  - other at <code>src/vs/platform/policy/node/nativeManagedSettingsService.ts:updateWatcher</code>: Create the native managed-settings watcher with policy definitions; cardinality: One existing watcher creation at initialization or definition replacement; its definition map grows by one scalar key.

  - filesystem at <code>src/vs/platform/policy/common/fileManagedSettingsService.ts:constructor/refresh</code>: Watch and read managed-settings.json; cardinality: One existing watch and one throttled read per relevant file-change burst; recognizing \`fusionTier\` does not add a read.

  - IPC at <code>src/vs/platform/policy/common/nativeManagedSettingsIpc.ts:initializeFromChannel/updateManagedSettings</code>: Send native managed-settings snapshots/changes to the workbench; cardinality: One existing initialization call and one existing event per changed snapshot; payload may gain one short scalar.

- Verdict: No reportable regression. The new key adds bounded scalar serialization and lookup work without synchronous UI, layout, I/O, or IPC amplification.
