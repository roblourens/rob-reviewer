## Findings (2)

### 1. [medium] Parse complete AHP histories without recursively cloning every frame

**Finding ID:** `PERF-BEFB00468A12`  
**Location:** <code>src/vs/platform/github/common/missionControl/tasksClient.ts:332</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Main-thread CPU plus temporary and returned JavaScript objects/arrays allocated while recursively copying parsed JSON.  
**Scaling:** CPU and allocation grow with total history bytes and nesting; message payload/action subtrees are copied in the outer event pass and then copied again at each nested amendment, so large extension payloads incur multiple full traversals.  
**Outcome:** Increased history-load latency, CPU/GC pressure, and potential dropped frames while parsing large task histories.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no Mission Control AHP history path or synchronous schema-copy pass over complete task histories in the GitHub client.  
**Changed behavior:** The new complete-history parser first recursively copies every JSON field in each AHP frame and then repeats recursive preservation at the payload, message-data, and action layers while validating known fields.  
**Confidence:** 0.97 — The recursive implementation of \`jsonObject\`, the nested amendment call graph, the complete unpaginated input, and browser-side execution path are explicit. Only the prevalence of near-limit histories is uncertain.

**Causal diff evidence:** Added line 332 introduces the outer recursive clone for each frame; nested added \`parse.amend(parse.jsonObject, ...)\` parsers cause the already-copied subtrees to be traversed and allocated again.

Opening a long-running task history can synchronously traverse and allocate several object graphs for a multi-megabyte response on the workbench thread, increasing response latency and causing UI pauses and GC churn. Cost is largest for message actions with deeply nested extension data and for histories near the 16 MiB transport cap.

**Evidence:** Added line 332 wraps every event in \`parse.amend(parse.jsonObject, ...)\`. \`parse.jsonObject\` recursively rebuilds every nested object/array via \`Object.fromEntries\` and \`jsonValue\` (\`schema.ts:145-149\`); the same frame then reaches nested \`parse.amend(parse.jsonObject, ...)\` calls for \`payload\` (lines 341-344), message \`data\` (line 310), and \`action\` (line 312). \`getAhpEvents\` requests the complete history across all sessions in one response, and the transport permits a 16 MiB body. This runs after JSON parsing in the browser-side workbench service.

**Suggested direction:** Validate the JSON-compatible frame once, then validate known envelope fields against that object without recursively rebuilding the same payload at each layer; preserve extension fields with a single pass or shallow object reuse.

### 2. [medium] Do not retain complete task histories in the entry-counted ETag cache

**Finding ID:** `PERF-590BFC1F91B9`  
**Location:** <code>src/vs/platform/github/common/missionControl/missionControlClient.ts:165</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** Raw response-body bytes retained as JavaScript strings in the shared LRU cache.  
**Scaling:** Retained memory grows with the number of distinct task/page/representation keys (up to 500 entries) times each history body size (up to 16 MiB); warm revalidation extends entry recency rather than releasing the body.  
**Outcome:** Substantial retained memory and resulting GC pressure during long-lived Mission Control usage.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Before this PR, Mission Control task-event and complete-history payloads could not enter this GitHub client's shared REST cache; the cache primarily served the pre-existing GitHub REST operations.  
**Changed behavior:** All non-sensitive Mission Control GETs, including paginated task events and the complete unpaginated AHP history, now opt into the shared transport's ETag body cache.  
**Confidence:** 0.92 — The new cache opt-in, complete unpaginated history contract, 500-entry count limit, 16 MiB body limit, and shared-client lifetime are directly established in code. Exact impact depends on server ETag/no-store headers and real history sizes, which lowers severity rather than mechanism confidence.

**Causal diff evidence:** Added line 165 passes \`etag: true\` for non-sensitive Mission Control requests, newly admitting the complete-history response bodies added by this PR into the long-lived shared cache.

When a consumer inspects event histories for many long-running tasks and the service supplies ETags without \`no-store\`, raw multi-megabyte response strings remain reachable until 500 newer entries evict them. Even dozens of histories can retain hundreds of megabytes for the lifetime of the account client, causing memory and GC pressure in the workbench.

**Evidence:** The changed line sets \`etag: \!sensitive\` for every ordinary Mission Control read. \`TasksClient.getAhpEvents\` is an ordinary GET whose contract is the complete raw stream across every session without pagination (\`tasks.ts:535\`), while \`GitHubTransport\` stores the raw body in an LRU limited to 500 entries (\`githubTransport.ts:130,705\`) and permits each response to reach 16 MiB (\`githubTransport.ts:148\`). The cache has no byte budget, and keys differ by task URL, page/query, and Accept representation, so histories for different tasks do not deduplicate; in-flight coalescing helps only concurrent identical reads.

**Suggested direction:** Separate in-flight coalescing from retained ETag caching and disable retained-body caching for \`getEvents\`/\`getAhpEvents\`, or enforce a byte-weighted cache budget so large histories evict proportionally while preserving small-response revalidation.
