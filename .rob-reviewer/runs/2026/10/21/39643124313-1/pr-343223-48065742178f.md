### Scenario 1: Open or reuse the release-notes editor for a product version

- Critical path: The release-notes text must be loaded, transformed/rendered, and assigned to the webview before the editor is usable. The diff adds one highlights-marker replacement over the loaded markdown and initializes ToC tracking inside the webview after HTML creation; it adds no new remote boundary.
- Scaling input: Release-notes markdown byte length and the number of fenced code blocks; the added marker transform runs once over the document, while existing markdown rendering/token collection scales with document content.
- Effective concurrency: One show request renders at a time logically; overlapping requests may execute, but request IDs discard superseded results. The existing per-version Promise cache coalesces concurrent network loads.
- Cache behavior: Successful remote text is cached by exact version, including in-flight coalescing; failures are removed. Current-file previews intentionally bypass the cache. The diff does not alter these states.
- Mechanism confidence: High confidence in the added local transformation and initialization path, and high confidence that no new network/filesystem/subprocess/database boundary was introduced.
- Magnitude uncertainty: Production release-note sizes vary, but the added transformation is a single document pass with normally one marker pair; no evidence shows a large multiplicative cost.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/update/browser/releaseNotesEditor.ts:loadReleaseNotes</code>: HTTP request for https://code.visualstudio.com/raw/v&lt;version&gt;.md; cardinality: One request per version on a cold successful load; zero on warm opens because the Promise is cached. Failed loads are evicted and may be retried by a later open.
    - Introduced by diff: false; previous behavior: The same cold fetch and per-version Promise cache existed before the PR.; critical-path effect: The cold fetch blocks rendering; warm opens reuse the cached text.
- Verdict: No reportable regression. The added render work is bounded to one pass per render and does not increase expensive-boundary cardinality.

### Scenario 2: Scroll or jump through release notes while the ToC marks the current major section

- Critical path: Scroll events schedule a current-section calculation on the next animation frame. At most one pending frame exists, and the calculation reads document metrics plus heading geometry before updating one ToC attribute; this work is directly on the scrolling/rendering path.
- Scaling input: The number of distinct ToC targets preceding the viewport and the number of rendered animation frames during scrolling. Initialization deduplicates duplicate targets, so effective cardinality is distinct linked sections rather than raw links.
- Effective concurrency: requestAnimationFrame coalesces any number of scroll, resize, hashchange, pageshow, and ResizeObserver notifications into one pending update. Updates execute serially on the webview UI thread.
- Cache behavior: The linked target list is built and document-sorted once per webview document. There is no cross-document cache and no per-scroll allocation of the list.
- Mechanism confidence: High confidence in the per-frame geometry scan, coalescing, and cleanup behavior; insufficient evidence that effective section cardinality or geometry cost reaches a user-visible regression threshold.
- Magnitude uncertainty: The repository does not establish a realistically large production ToC cardinality or measured frame cost. The O(section-count) geometry scan is concrete, but rAF coalescing and the small major-section examples prevent concluding that it causes dropped frames.
- Expensive boundaries: none found
- Verdict: No finding. Although the new scan is synchronous UI work, the diff coalesces it to one scan per frame, deduplicates targets, avoids DOM writes when the section is unchanged, and supplies no evidence of a realistically costly section count.

### Scenario 3: Retokenize fenced code blocks or resize release-notes content after the webview is shown

- Critical path: Existing host-side tokenization sends one grouped webview message containing all code-block updates. Applying those updates can resize content; the new ResizeObserver then schedules one ToC recalculation on the next frame. Tokenization itself remains off the initial HTML assignment path after the webview-ready message.
- Scaling input: Number and total bytes of fenced code blocks for existing tokenization, plus distinct ToC targets for the single follow-up navigation scan.
- Effective concurrency: Code blocks are tokenized with the existing Promise.all, then sent in one message. Resize notifications from all DOM changes are coalesced through the same single pending animation frame.
- Cache behavior: No tokenization cache is added or removed. Request IDs discard stale tokenization results, while the navigation target list persists only for the current document.
- Mechanism confidence: High confidence that the diff adds only a coalesced local observer reaction and does not fan out IPC or tokenization work.
- Magnitude uncertainty: Large code samples can make the existing tokenization message expensive, but the PR does not increase its count or payload; the added follow-up is one coalesced local scan.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/update/browser/releaseNotesEditor.ts:updateTokenization/applyReleaseNotesTokenization</code>: One webview postMessage carrying grouped tokenized HTML and CSS; cardinality: One IPC message per accepted tokenization request, containing all code blocks; not one message per block.
    - Introduced by diff: false; previous behavior: The grouped postMessage and in-webview DOM replacement existed before the PR; the PR only observes resulting size changes for navigation state.; critical-path effect: It updates syntax highlighting after the webview is ready and can indirectly schedule one ToC update; it does not block initial release-notes HTML assignment.
- Verdict: No reportable regression. Observer lifecycle is disconnected on pagehide, pending frames are canceled, and content changes schedule at most one additional local update frame.

**Summary:** Reviewed all six changed files and all diff pages. The performance-sensitive addition is scroll/resize-driven ToC tracking; it is frame-coalesced, target-deduplicated, mutation-guarded, and disposed on pagehide. Rendering adds one bounded marker transform. No high-confidence actionable performance regression or concrete regression fix was established.
