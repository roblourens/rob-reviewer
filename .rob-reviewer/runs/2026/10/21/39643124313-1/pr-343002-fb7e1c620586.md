# Performance review: artifacts: Add the shared integration runtime

[PR #343002](https://github.com/microsoft/vscode/pull/343002) at `fb7e1c62058632113d4e2203a9ac7a2873179ce9`

## Findings (3)

### 1. [high] Cap current-generation automation history

**Finding ID:** `PERF-66B5FD42CF70`  
**Location:** <code>src/vs/platform/artifactIntegrations/common/artifactIntegrationStore.ts:102</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Persisted ArtifactRun objects (including prompt/presentation/result payloads), heap copies, JSON bytes, and filesystem operations  
**Scaling:** Retained state grows at least linearly with distinct occurrence keys for the entire enabled consent generation, and additionally with every dispatched retry; every transaction then performs work proportional to the enlarged global ledger.  
**Outcome:** Progressively increasing CPU/GC pressure and durable-write latency, with growing disk usage, for every subsequent run transition or configuration change.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no artifact-integration ledger or durable automation-run history on this path.  
**Changed behavior:** The new pruning pass exempts every dispatched automation run in the current generation and also the latest run for every occurrence from the nominal 200-run-per-binding history cap.  
**Confidence:** 0.99 — The retention rule and full-ledger transaction path are explicit: each dispatched run in the enabled generation is retained, unique occurrence keys retain at least one run, and every later mutation clones, scans, serializes, and durably rewrites the resulting ledger. Only the real-world occurrence rate is uncertain.

**Causal diff evidence:** Added RIGHT line 102 calls retained.add(run.id) for every dispatched run in the current enabled generation; added line 104 also retains the latest run for each unique occurrence key.

A recurring or event-driven automation left enabled across many occurrences makes action dispatch/completion and configuration changes steadily slower and increasingly I/O-heavy; rich persisted presentations amplify the retained bytes.

**Evidence:** pruneSettledRuns first keeps only the last 200 settled runs per binding, but lines 95-107 override that bound for current-generation automation. transact at lines 154-163 deep-clones the entire state, reruns pruning/structural comparison, JSON.stringify's the whole ledger, and writes it. FileArtifactIntegrationStorage performs a temp-file write, file fsync, rename, and directory fsync for each such write. A long-lived enabled automation producing fresh occurrence keys therefore grows both retained bytes and the critical-path cost of every state transition without a bound.

**Suggested direction:** Keep full ArtifactRun history under the documented per-binding cap. Preserve deduplication and attempt budgets in a compact occurrence index/counter with an explicit lifecycle or quota, retaining full retry chains only while active/indeterminate instead of pinning every run payload for the generation.

### 2. [medium] Send the initial subscription snapshot only once

**Finding ID:** `PERF-80120D3FC5D4`  
**Location:** <code>src/vs/platform/artifactIntegrations/common/artifactIntegrationProtocol.ts:129</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Serialized snapshot/detail bytes, BroadcastChannel/transport messages, validation work, and temporary objects  
**Scaling:** Exactly two full payload transfers occur per artifact or details subscription instead of one; total duplicated bytes scale with opened subscriptions, snapshot richness, detail item count, and receiving windows.  
**Outcome:** Excess IPC/network traffic and serialization/validation CPU, increasing artifact/details opening cost.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR these artifact subscription payloads and transport messages did not exist.  
**Changed behavior:** Installing the new immediate autorun emits revision 1 through onDidUpdate, then request returns the same revision and snapshot; the details branch repeats the same pattern.  
**Confidence:** 0.99 — VS Code autorun executes immediately, and the added test explicitly covers an update arriving before the acquire response. The server therefore emits the initial value as an update and returns the same revision/value as the response; the local host forwards these as two separate BroadcastChannel messages.

**Causal diff evidence:** Added RIGHT line 129 fires the initial artifact snapshot from the immediate autorun, while line 131 returns that same snapshot/revision as the acquire response (and lines 140-142 do likewise for details).

Opening artifact models and expandable details sends and processes every initial full payload twice, multiplied across windows for the local coordinator and across subscriptions in richer views.

**Evidence:** ArtifactIntegrationClient subscribes to onDidUpdate before issuing acquire and discards a response whose revision is not newer, so one copy is knowingly redundant. ArtifactIntegrationProtocol.test.ts:95 confirms an update arrives before the acquire response. In LocalArtifactIntegrationHost, endpoint.onDidUpdate sends an update message at line 162 and endpoint.request().then sends a separate response at line 183, proving both payloads cross the BroadcastChannel boundary; artifact snapshots can carry 50 runs and details can carry 200 items.

**Suggested direction:** Capture the initial observable value for the acquire response without emitting it through onDidUpdate, then begin emitting only subsequent revisions (or suppress the autorun's first callback) for both artifact and details subscriptions.

### 3. [medium] Bound execution across independent resources

**Finding ID:** `PERF-4FB5A8410E44`  
**Location:** <code>src/vs/platform/artifactIntegrations/common/artifactExecutionService.ts:244</code> (<code>RIGHT</code>)  
**Performance category:** <code>throughput</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Concurrent provider CPU work, network/IPC authorization and chat calls, promises, and cancellation/observation objects  
**Scaling:** Aggregate concurrency grows with the number of queued runs whose resource/integration resource keys differ; deduplication and per-key sequencing do not reduce a burst spanning distinct artifacts.  
**Outcome:** CPU/network bursts, remote throttling, GC pressure, and reduced interactive throughput when many automations become runnable together.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no shared artifact execution scheduler launching provider actions from a persisted queue.  
**Changed behavior:** The new pump creates an active token and queues execute for every eligible run in one pass; SequencerByKey only orders runs sharing the same resource-scoped keys.  
**Confidence:** 0.97 — The pump loops over all runnable ledger entries and schedules each immediately. Both sequencer keys contain the resource identity, so they serialize conflicts but provide no aggregate bound; execute directly reaches authorization, provider preparation/execution, or chat submission. Only the typical burst size is uncertain.

**Causal diff evidence:** Added RIGHT line 244 queues execute for each run under resourceKey and integrationKey, both of which include per-resource identity, without any shared semaphore or limiter.

When automation queues work for many artifacts at once, the host can flood provider/network/chat boundaries and contend with interactive work instead of applying backpressure.

**Evidence:** pump iterates the entire run ledger at lines 227-244 and marks every eligible run active. Distinct artifacts have distinct resourceKey and integrationKey values, so their callbacks start concurrently. execute then awaits runtime.authorize, action.prepare and prepared code execution, or runtime.chat.submit, all before the active entry is released. Thus a reconnect/session update or provider event that queues N distinct resources can produce N simultaneous expensive operations.

**Suggested direction:** Retain the two per-key sequencers for ordering, but place a shared, cancellation-aware concurrency limiter immediately around execute; choose a small bounded parallelism and ensure queued work is removed on revocation/disposal.

### Scenario 5: Browsing and merging run history across host and client authorities

- Critical path: CompositeArtifactModel requests an initial page of up to 200 from each active source in parallel, merges by timestamp in memory, and fetches the next page from any exhausted source until it can satisfy the cursor/limit. Remote models turn each page into one protocol history request.
- Scaling input: Requested cursor depth and retained runs in the two source models; page size is capped at 200 and output limit at 200.
- Effective concurrency: The two sources fetch in parallel at each iteration; pagination within a source is serial. No unbounded source fan-out exists because the model list is primary plus optional secondary.
- Cache behavior: runOwners caches run-to-source routing from invocation/history, but source pages are not cached between getRuns calls. Stored history is nominally capped per binding, apart from the separately reported current-generation retention bypass.
- Mechanism confidence: High for paging behavior and IPC cardinality.
- Magnitude uncertainty: Deep cursors can reread earlier pages, but practical source count is fixed at two and the diff supplies no evidence of frequent deep-history cancellation/reconciliation requests.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/artifactIntegrations/common/artifactIntegrationProtocol.ts:348-355,186-187</code>: Fetch paged history through ArtifactIntegrationClient/Server; cardinality: At most one concurrent request per active source per merge iteration; there are currently at most primary and secondary sources, with 200-run source pages.
    - Introduced by diff: true; previous behavior: No composite artifact history protocol existed.; critical-path effect: Requested history cannot return until enough source pages are fetched to locate the cursor and fill the page.
- Verdict: No separate finding: source fan-out is bounded and parallelized; the material history-scaling problem is the unbounded durable automation retention already reported.
