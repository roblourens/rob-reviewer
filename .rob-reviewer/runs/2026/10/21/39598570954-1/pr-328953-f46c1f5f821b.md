# Performance review: agentHost: sync workspace folders for existing sessions

[PR #328953](https://github.com/microsoft/vscode/pull/328953) at `f46c1f5f821b75255773a5b64f1c2d462d03cd19`

## Findings (1)

### 1. [medium] Do not recreate every tracked provider session on folder changes

**Finding ID:** `PERF-E17DD3E688C1`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostUntitledProvisionalSessionService.ts:309</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Agent Host IPC calls, provider session objects, git/customization work, and possible Codex SDK thread/prewarm subprocess operations.  
**Scaling:** Cost grows linearly with the number of tracked open chat resources whose working-directory snapshot differs; all keys run concurrently because sequencing is only per resource.  
**Outcome:** A workspace event can cause concurrent provider lifecycle churn, increasing CPU/I/O pressure and interaction latency.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, workspace-folder events did not traverse \`\_entries\` or recreate provisional/provider generations; existing live sessions also had no replacement-session work on this event.  
**Changed behavior:** A workspace-folder add/remove now starts replacement generation work for every tracked chat resource whose roots differ. Each replacement crosses the Agent Host boundary to \`createSession\`, publishes the replacement, and disposes the previous provider session; per-key sequencing does not bound aggregate concurrency across resources.  
**Confidence:** 0.97 — The changed listener, retained rebound entries, per-key-only sequencer, and \`\_reconcileGeneration\` create/dispose calls are directly traced. Provider creation cost is concrete: AgentService resolves config/customizations; Copilot initializes its client and probes project state; Claude probes git project state; Codex schedules SDK thread prewarming when available. Typical open-session count is uncertain, which affects severity rather than mechanism confidence.

**Causal diff evidence:** The added workspace-folder listener iterates every \`\_entries\` item and, at RIGHT line 309, queues \`\_reconcileGeneration\` whenever the root set differs. Rebound real sessions remain in \`\_entries\` as \`newEntry\` until the chat UI is disposed, so this is not limited to untouched drafts.

Adding or removing one workspace folder with several open agent chats can burst provider session creation/disposal, git/customization work, IPC, and Codex prewarm thread operations, consuming CPU/I/O and making the workbench or next agent interaction sluggish. Materialized chats pay this churn even though the live-session synchronizer already updates their roots with lightweight deltas.

**Evidence:** \`\_entries\` contains both untitled drafts and rebound real resources (\`tryRebind\` installs \`newEntry\` and does not remove it until chat disposal). The new listener queues all differing entries independently. \`\_reconcileGeneration\` awaits \`\_agentHostService.createSession(...)\`, then \`\_disposeBackend(previous.backendSession)\`. AgentService \`createSession\` invokes provider creation and initial customization resolution; Codex \`createSession\` calls \`\_schedulePrewarm\`, which can \`\_materializeIfNeeded\` and issue thread operations. \`SequencerByKey\` serializes only a single resource, so N tracked resources can perform these expensive boundaries concurrently.

**Suggested direction:** Restrict this listener to genuinely unmaterialized untitled drafts (or remove entries when they are handed off to a live session) and let \`AgentHostSessionWorkingDirectorySynchronizer\` handle materialized sessions. If multiple drafts still need rebuilding, coalesce the event and run replacements through a shared concurrency limiter.

### Scenario 1: Add or remove a folder while existing agent chats are open

- Critical path: Live-session reconciliation is scheduled asynchronously from the workspace event, so it is not a direct UI event barrier; its IPC/provider work can still contend with the workbench. The newly added provisional-generation replacement also runs asynchronously and can overlap across chats.
- Scaling input: Number of active session registrations, number of tracked open chat resources, and number of changed workspace roots after set deduplication.
- Effective concurrency: Live reconciliation is serialized and burst-coalesced per session, but not globally. Provisional generation replacement uses \`SequencerByKey\`, which serializes one chat resource while allowing all tracked resources to create/dispose provider sessions concurrently.
- Cache behavior: The live synchronizer reads optimistic subscription state, preventing redispatch while confirmations are pending, and coalesces automatic triggers. Root comparisons avoid work when membership is unchanged. The replacement path has no global event-level coalescing or shared lifecycle-work limiter.
- Mechanism confidence: High: changed event handlers, cardinality, per-key concurrency, and provider create/dispose/prewarm boundaries are directly traced.
- Magnitude uncertainty: Most users have few simultaneous open chats and workspace-folder changes are infrequent, but the tracked set is not statically bounded and provider lifecycle cost varies by provider and warm SDK state.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionWorkingDirectorySynchronizer.ts \`\_reconcile\`</code>: Dispatch one optimistic session working-directory action for each effective root addition/removal.; cardinality: One dispatch per changed secondary root per active eligible session; optimistic state suppresses duplicate deltas and automatic triggers collapse to one follow-up pass.

### Scenario 2: Send the next prompt after workspace roots changed

- Critical path: Before turn dispatch, the workbench awaits a local reconciliation pass and trust lookup for new roots, then dispatches optimistic deltas before the turn. On the host, the complete resolved snapshot reaches the provider before the prompt enters its runtime. Provider reconfiguration is therefore on the prompt critical path only when roots actually changed.
- Scaling input: Effective number of changed roots and frequency of workspace changes, not message count when roots are stable.
- Effective concurrency: Reconciliation and sends are serialized per session/client ordering. Claude rebinds one query per changed snapshot; Copilot destroys and resumes one SDK session; Codex reuses the existing thread and places the latest roots in the existing per-turn request.
- Cache behavior: Warm unchanged sends use set equality to avoid Claude/Copilot lifecycle work. Cold resumes seed from persisted metadata, while a send-time authoritative snapshot supersedes stale metadata and is persisted after successful application. There is no negative cache needed because failures intentionally remain retryable.
- Mechanism confidence: High: provider equality gates and exact restart/rebind call paths are visible and tested.
- Magnitude uncertainty: SDK destroy/resume or Claude startup duration depends on provider state and machine, but its conditional placement on the changed-root prompt path is certain.
- Expensive boundaries:

### Scenario 3: Create or rebind an untitled provisional session in a multi-root workspace

- Critical path: Picker-driven provisional creation and first-send rebind await Agent Host session creation. Workspace-folder-triggered replacement is background until a consumer waits for the current mapping.
- Scaling input: Number of tracked open draft or rebound chat resources and effective workspace membership changes.
- Effective concurrency: Operations are serialized per chat resource. Independent untitled resources can create sessions concurrently; the new workspace event schedules all differing resources at once.
- Cache behavior: Per-resource pending work is deduplicated and desired root sets are compared unordered, so workspace reorders are no-ops. There is no aggregate limiter across resources. Provider warm state may make creation cheaper, while Codex warm SDK state enables rather than eliminates prewarming.
- Mechanism confidence: High: \`\_entries\` lifecycle, set comparison, queueing, and transitive provider work are traced.
- Magnitude uncertainty: The common number of simultaneous drafts/open rebound chats is product-usage dependent; each boundary and unbounded cross-key overlap is established.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostUntitledProvisionalSessionService.ts \`\_reconcileGeneration\` and \`tryRebind\`</code>: Call Agent Host createSession and disposeSession for provisional generations.; cardinality: Normally one create for the selected draft and one create/dispose during rebind; after this diff, a workspace event may add one create/dispose pair for every tracked differing resource.
    - Introduced by diff: true; previous behavior: Initial creation/rebind boundaries already existed, but workspace-folder events did not multiply them across entries.; critical-path effect: Picker/rebind calls are critical to observing preserved config; workspace-event replacement is background but can become a wait target and contend globally.
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts \`createSession\` and provider project discovery</code>: Resolve working directory and probe project/git/customization metadata during provider session creation.; cardinality: One provider initialization path per replacement session.
    - Introduced by diff: true; previous behavior: No folder-event-driven replacement creation invoked these probes.; critical-path effect: Part of each Agent Host createSession request; concurrent replacements amplify filesystem/git work.
- Verdict: This is the reported concurrency-burst regression; restrict replacement ownership to true unmaterialized drafts and bound any remaining multi-draft work.

### Scenario 4: Receive and validate working-directory actions in Agent Host state

- Critical path: The protocol notification is ordered per client, synchronously validated/canonicalized, and reduced before a later turn from that client can proceed.
- Scaling input: Effective changed-root action count multiplied by current workspace-root count.
- Effective concurrency: Existing client sequencing preserves action order. Validation scans the current directory list; no new asynchronous filesystem or network operation is performed.
- Cache behavior: No cache is needed for the small current root list; client-side optimistic state suppresses duplicate pending deltas. Canonicalization reuses existing URI spelling where possible.
- Mechanism confidence: High: the validation path and synchronous operations are direct.
- Magnitude uncertainty: Very large multi-root workspaces increase URI comparison work, but realistic root counts and absence of boundary I/O keep this below reporting threshold.
- Expensive boundaries:

- Verdict: No finding: bounded CPU/serialization work is proportional to effective deltas and is necessary for authoritative ordered state.
