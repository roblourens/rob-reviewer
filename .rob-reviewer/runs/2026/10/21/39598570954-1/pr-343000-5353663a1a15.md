## Findings (1)

### 1. [medium] Stop rescanning every chat checkout on each pull-request update

**Finding ID:** `PERF-EBEF4732BB9A`  
**Location:** <code>src/vs/platform/agentHost/node/artifactIntegrations/githubPullRequestArtifactIntegration.ts:349</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Git subprocesses and working-tree filesystem I/O  
**Scaling:** For every integrated pull request, each snapshot transition or broad session/chat/config event schedules a scan of every chat; each matching checkout executes five uncached Git commands (branch, remote, rev-parse, status, branch) per working directory, with all chats run through Promise.all. Multiple PR artifacts multiply this fan-out, and a new event can start another async scan before the prior one finishes.  
**Outcome:** Repeated subprocess bursts and repository scans increase CPU/filesystem load, contend with the agent's own Git operations, and can delay artifact automation/action availability in sessions with several chats or recorded pull requests.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no GitHub pull-request artifact binding and therefore no event-driven all-chat checkout scan on live pull-request polling or chat lifecycle changes.  
**Changed behavior:** The new autorun reads both the live pull-request snapshot and a broad hostChanges signal, then schedules refreshWorkspaces; that method maps every session chat concurrently and calls checkout, which crosses multiple Git subprocess boundaries.  
**Confidence:** 0.98 — The changed trigger, complete call path, subprocess implementation, polling cadence, and all-chat concurrency are directly visible in repository code. Exact latency varies with repository size and chat count, which affects severity but not the mechanism.

**Causal diff evidence:** The added \`resource.snapshot.read(reader); this.hostChanges.read(reader); refreshWorkspace.schedule();\` at lines 347-349 newly places a full all-chat checkout scan behind every PR snapshot and broad host event; the same added class performs the unbounded \`Promise.all(...chats.map(...checkout))\` fan-out.

With integrations enabled, an active multi-chat session causes background Git bursts whenever any PR fragment enters loading/ready (background checks can poll every 60 seconds, interactive checks every 15 seconds) and on turn/pending-message/session events. Ten eligible chats can launch roughly 50 Git processes for one scan of one PR, before overlapping scans or additional PRs, causing noticeable CPU/I/O spikes and slower agent Git work.

**Evidence:** Lines 347-349 subscribe checkout refresh to every resource.snapshot and hostChanges update. hostChanges includes ChatTurnStarted/Complete/Cancelled, pending-message, session metadata/chat events, and all root/session config changes. refreshWorkspaces at lines 644-651 uses Promise.all over every chat. checkout at lines 609-629 invokes getCurrentBranchName twice, getFetchRemoteUrls, revParse, and hasUncommittedChanges; AgentHostGitService implements each via child\_process.execFile('git', ...), except the repository-root lookup after its cache is warm. PullRequestResourceService commits separate loading/ready snapshot updates for core, checks, review threads, and mergeability and polls pending background checks every 60s. RunOnceScheduler only coalesces the 50ms timer; its callback does not await refreshWorkspaces, so later events can overlap an in-flight scan while workspaceRevision merely discards stale results.

**Suggested direction:** Refresh only checkout state that is actually needed: lazily validate the invoking chat for manual actions and the origin chat when a checkout-dependent automation is enabled. If per-chat action availability must stay live, cache/dedupe by working-directory plus relevant head/ref, invalidate only on chat workspace or Git-state changes, serialize/cancel stale scans, and put Git probes behind a shared concurrency limit.
