### Scenario 1: Send a Claude agent turn through the local Anthropic-compatible proxy after upgrading to SDK 0.3.304

- Critical path: The SDK subprocess posts to the local /v1/messages proxy; the proxy parses the request, filters the beta header, and awaits one CAPI messages network stream before deltas can reach the UI. Each returned display-update thinking delta is serialized through local SSE and synchronously mapped/dispatched as an existing ChatReasoning action, but no separate remote request is required for it.
- Scaling input: One remote CAPI request per active turn. Additional local serialization and action dispatch scale with the number and byte length of short thinking display-update chunks, which in turn scale with progress notes/tool-call phases rather than transcript history or collection size.
- Effective concurrency: Each session owns a long-lived SDK query/subprocess and active sessions can stream concurrently; this PR adds no new concurrency burst or limiter change. Proxy response writes honor backpressure, and turn processing remains sequential within each stream.
- Cache behavior: There is no response cache on the turn path. The beta filter is evaluated once per inbound request over the bounded SDK beta-header list. SDK module loading is memoized after first load.
- Mechanism confidence: High confidence in the request and event paths: the added allowlist line is reached once per /v1/messages request, proxy code performs one CAPI call, and thinking\_delta maps directly to ChatReasoning. The external SDK's exact emission policy is opaque in-repository, so no stronger performance claim is justified.
- Magnitude uncertainty: The exact number and size of model-generated display updates is not established by repository code, but they are described and handled as short incremental progress notes. No evidence shows enough additional events to cause latency, throughput loss, or dropped frames, and the change avoids an entire failed remote attempt.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/claude/claudeProxyService.ts::\_streamMessages/\_sendNonStreamingMessage</code>: CAPI Anthropic messages request and streamed response; cardinality: One successful CAPI request per turn with the SDK 0.3.304 beta forwarded; concurrent sessions can each have an active request.
    - Introduced by diff: false; previous behavior: SDK 0.3.281 made one successful CAPI request per turn without display-update thinking content. The coordinated version bump plus allowlist entry still makes one successful request; omitting the new allowlist entry would instead cause the new SDK's rejected attempt and retry, which this diff avoids.; critical-path effect: The first response event gates visible turn progress and the stream carries all subsequent response content.
  - serialization at <code>src/vs/platform/agentHost/node/claude/claudeProxyService.ts::\_streamMessages and src/vs/platform/agentHost/node/claude/claudeMapSessionEvents.ts</code>: JSON encode/decode and local SSE forwarding of thinking display-update chunks; cardinality: One local frame/action per SDK-emitted stream event; newly visible progress notes contribute a bounded number of thinking chunks per turn.
    - Introduced by diff: true; previous behavior: The prior SDK/default omitted these progress-note thinking chunks, so they did not incur local SSE serialization or ChatReasoning dispatch.; critical-path effect: Processing occurs inline with stream consumption, but uses the established incremental delta path and backpressure.
- Verdict: No reportable regression. The added stream work is incremental and bounded on an existing path, while forwarding the matching beta prevents a full failed request/retry cycle that would be materially more expensive.

### Scenario 2: First Claude use after a shipped SDK version upgrade, and subsequent warm uses

- Critical path: Before the first Claude SDK API call can proceed, the service resolves the versioned SDK root. On a cold 0.3.304 cache it downloads one platform tarball, writes and extracts it, then imports sdk.mjs; on a warm cache it checks the .complete sentinel and imports/memoizes the module.
- Scaling input: One artifact for the current platform/version. Cost scales with the single tarball size (repository comments place these artifacts around 70-95 MB), not with sessions or turns after the module is loaded.
- Effective concurrency: Same-process callers coalesce on one promise keyed by cacheDir; cross-window races may each fetch but converge through an atomic rename, behavior unchanged by this diff. Once loaded, \_sdkModule avoids repeated resolution/download within the process.
- Cache behavior: The cache key includes package id, SDK version, and target. Existing 0.3.281 caches do not satisfy 0.3.304, so the first use after upgrade is cold; later uses hit the .complete sentinel. Failures are negatively cached for 30 seconds.
- Mechanism confidence: High confidence in version-keyed cold/warm behavior and coalescing from the downloader implementation; low evidence for any changed artifact-size cost.
- Magnitude uncertainty: The exact 0.3.304 tarball size versus 0.3.281 is not present in the diff, so there is no evidence of a size or extraction-cost regression beyond the expected one-time cache miss for a new version.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/agentSdkDownloader.ts::\_fetch</code>: Fetch the platform-specific Claude SDK tarball from the configured CDN; cardinality: At most one coalesced download per process for claude/0.3.304/platform on a cold cache; zero on warm cache.
    - Introduced by diff: true; previous behavior: An installation already warm for 0.3.281 used that version's cache. Shipping 0.3.304 necessarily selects a new version-keyed artifact and causes one cold fetch before becoming warm.; critical-path effect: Cold download and extraction block the first SDK load; warm cache resolution is a sentinel check.
  - filesystem at <code>src/vs/platform/agentHost/node/agentSdkDownloader.ts::\_download and src/vs/platform/agentHost/node/claude/claudeAgentSdkService.ts::\_loadSdk</code>: Write tarball, extract SDK tree, write sentinel, atomically publish cache, and import sdk.mjs; cardinality: One write/extract/publish sequence per cold version/target; one sentinel existence check per pre-memoization resolution.
    - Introduced by diff: true; previous behavior: Equivalent work occurred when 0.3.281 was first installed; already-warm 0.3.281 installations did not need another artifact until this version bump.; critical-path effect: Cold extraction/import gates first use; subsequent module calls return the memoized binding.
- Verdict: No reportable regression. A one-time version-keyed download is inherent to deploying the requested SDK update, remains coalesced and persistently cached, and the diff provides no evidence that the artifact or extraction work materially increased.
