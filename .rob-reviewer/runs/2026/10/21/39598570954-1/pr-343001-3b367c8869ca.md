### 1. [medium] Acquire extension artifact details lazily

**Finding ID:** `PERF-3CF82CC13343`  
**Location:** <code>src/vs/workbench/api/common/extHostChatArtifactIntegrations.ts:167</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** extension provider detail models, serialized IPC bytes, and allocated fact/item DTO objects  
**Scaling:** Cost is O(number of advertised details IDs × facts/items per details snapshot) for each integration creation, and can be multiplied by up to 20 artifacts in the new list-status path.  
**Outcome:** increased latency and CPU/GC pressure from unnecessary extension-host serialization  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no extension artifact-integration bridge and therefore no eager detail construction or duplicate details IPC on artifact acquisition.  
**Changed behavior:** Creating an extension-backed artifact integration now eagerly constructs and serializes every advertised details model before the artifact model can finish initializing; actual details access then acquires the same details a second time to establish the live handle.  
**Confidence:** 0.99 — The changed call path is explicit: \`$createIntegration\` cannot return until the loop completes, \`convertDetails\` maps every fact and item, and \`ExtensionArtifactDetails\` unconditionally issues a second \`$acquireDetails\` RPC. The API places no item-count bound on a details snapshot, so only the real-world payload size is uncertain.

**Causal diff evidence:** Added lines 166-182 make \`$createIntegration\` synchronously iterate every main/section/list details ID, call \`integration.acquireDetails\`, convert the complete details payload, and include it in the creation response. The newly added main-thread \`ExtensionArtifactDetails\` constructor later always calls \`$acquireDetails\` again when the details are actually acquired.

An artifact with several or large details lists delays model creation and the agent status critical path while the extension host allocates and serializes data that may never be requested. With status listing, this can occur for up to 20 artifacts at once, causing IPC payload growth, CPU/GC pressure, and visible tool latency.

**Evidence:** \`ExtHostChatArtifactIntegrations.$createIntegration\` loops over all details IDs at lines 167-181 and calls provider \`acquireDetails\` plus \`convertDetails\`; \`convertDetails\` maps the full \`facts\` and \`items\` arrays. On first consumer access, \`ExtensionArtifactResource.acquireDetails\` creates \`ExtensionArtifactDetails\`, whose constructor unconditionally invokes \`proxy.$acquireDetails\`, so the eager snapshot does not replace the normal acquisition/subscription. This path is reached by agent artifact acquisition and is multiplied when status listing acquires several artifacts.

**Suggested direction:** Keep \`$createIntegration\` limited to state and action descriptors, then acquire details only when a consumer requests a details ID. If an initial snapshot is required, retain the created details model/handle and reuse it for updates instead of disposing it and issuing \`$acquireDetails\` again.

### 2. [medium] Bound status-list artifact acquisition concurrency

**Finding ID:** `PERF-8890214D6E91`  
**Location:** <code>src/vs/platform/agentHost/node/shared/artifactIntegrationServerTools.ts:348</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** AHP reverse requests, main-thread/extension-host RPC calls, provider model creation, and possible provider network requests  
**Scaling:** Aggregate concurrency grows linearly with recorded artifacts up to 20; each artifact checks registered integrations, while only identical post-match resources can share creation.  
**Outcome:** burst IPC/network load, contention, and reduced throughput during artifact status listing  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no \`get\_artifact\_status\` list operation and therefore no multi-artifact acquisition burst on an agent tool call.  
**Changed behavior:** The new status-list operation launches every selected artifact acquisition concurrently rather than applying any shared concurrency limit or backpressure.  
**Confidence:** 0.96 — The 20-way scheduling is explicit in the changed \`Promise.all\`. Tracing \`acquireArtifact\` shows cold model creation iterates registered integrations, client composition can issue one reverse AHP request per artifact, and extension integrations cross main-thread/extension-host RPC for matching and creation. Resource pools coalesce creation only after matching and only for identical canonical resources; they do not bound aggregate calls. Exact provider/network duration is the remaining magnitude uncertainty.

**Causal diff evidence:** Added line 348 wraps all \`recorded.slice(0, MAX\_LISTED\_ARTIFACTS)\` acquisitions in one \`Promise.all\`, immediately starting up to 20 \`accessor.acquireArtifact\` calls for a single omitted-argument \`get\_artifact\_status\` invocation.

A session with 20 recorded links can create a 20-request AHP/extension-host burst and up to 20 simultaneous provider match/create operations, increasing tool latency through contention and risking remote API throttling for integrations that load live status.

**Evidence:** \`listStatus\` starts up to \`MAX\_LISTED\_ARTIFACTS\` (20) acquisitions in one \`Promise.all\`. \`acquireComposedArtifact\` may add a client acquisition after the host model, \`ClientArtifactIntegrationEndpoint\` relays that over reverse RPC, and \`ArtifactModel.refresh\` invokes every registered integration's match/create path. The registry pools identical matched resources but performs matching per artifact and has no global limiter; references are released after each summary, so ordinary cold listings repeat this work.

**Suggested direction:** Process the selected artifacts through a small shared concurrency limiter while preserving result order and the existing 20-artifact output cap; keep model/resource coalescing intact.
