<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, serialization-allocation, repeated-work

### Scenario 1: A focused, visible Agent Host chat receives a not-installed sandbox CA status and displays the informational notification, with or without the Install link.

- Critical path: The session/focus/visibility update calls AgentHostSandboxNotification.\_updateCertificate, constructs one short MarkdownString, calls setNotification, and synchronously triggers the mounted chat input widget to select and render the notification. The changed appendMarkdown calls only concatenate the localized string and one space; Markdown rendering was already required before the PR because the description already contained a Markdown link.
- Scaling input: One notification controller per live Agent Host session, but only the focused visible matching session can show this CA notice. The cached scope, input URI, and capability fields suppress unchanged updates, so effective work is one short render per relevant state/focus transition rather than per chat message or per certificate item.
- Effective concurrency: Updates are synchronous UI events and are deduplicated by \_certificateScope, \_certificateInputUri, and \_certificateCanInstall. There is no asynchronous fan-out or aggregate concurrency introduced by the changed lines.
- Cache behavior: On a cold qualifying state, one notification is built and rendered. Warm unchanged state/focus/visibility events return before construction. Changing operation state can force a bounded rebuild; the diff does not alter cache keys, invalidation, coalescing, or negative state behavior.
- Mechanism confidence: High: MarkdownString.appendMarkdown is direct string concatenation, while the prior appendText escaped tokens and expanded spaces before the same notification Markdown renderer consumed the result.
- Magnitude uncertainty: Exact notification frequency depends on focus and host state changes, but the description is a fixed, short localized string and the PR replaces several escaping/space-expansion regex transformations with direct concatenation. No realistic scaling regression is present.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. The PR reduces local string transformation work and preserves the existing single Markdown render and notification lifecycle.

### Scenario 2: The user clicks Install in the sandbox CA notification and confirms installation on the agent host.

- Critical path: The existing command handler validates current state, shows a confirmation dialog, then awaits exactly one connection.installSandboxCertificate call. The changed text construction occurs before display and does not add to, move, or multiply the host operation on this path.
- Scaling input: One selected chat and one certificate scope per user command. Repeated clicks while an operation is active are rejected by \_certificateBusy, so effective boundary cardinality is one host call per confirmed operation.
- Effective concurrency: \_certificateBusy serializes certificate operations within the controller; command re-entry returns immediately. The PR does not modify this limiter or introduce parallel host calls.
- Cache behavior: There is no result cache for an explicit install operation; current subscription state is revalidated before the call. The displayed notification itself retains the same state-based deduplication behavior before and after the PR.
- Mechanism confidence: High: the changed lines only select appendMarkdown instead of appendText when constructing fixed notification text; command URI creation and the install callback are unchanged.
- Magnitude uncertainty: The duration and transport of the host operation vary by connection implementation, but its placement, cardinality, and concurrency are unchanged by this PR.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSandboxNotification.ts:\_certificateTarget/\_runCertificateOperation</code>: Invoke the resolved agent-host connection's installSandboxCertificate operation, which may perform remote/OS trust-store work.; cardinality: Exactly one call after each confirmed operation; zero when canceled, invalidated, disposed, or already busy.
    - Introduced by diff: false; previous behavior: The same command link, validation, confirmation, busy guard, and single host operation existed before the diff; only plain description text and separator construction changed.; critical-path effect: The user-visible installation waits for this host operation after confirmation.
- Verdict: No reportable performance regression. The sole expensive boundary is pre-existing, user initiated, single-call, and serialized.

**Summary:** Reviewed the complete two-file diff and traced notification construction, MarkdownString helper costs, widget rendering, update deduplication, controller ownership, and the certificate-install host boundary. No performance finding met the causality and impact threshold; the production change removes escaping and nonbreaking-space expansion rather than adding work.
