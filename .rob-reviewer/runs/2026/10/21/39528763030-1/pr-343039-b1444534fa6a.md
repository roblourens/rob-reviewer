# Performance review: chat: keep working progress above the composer

[PR #343039](https://github.com/microsoft/vscode/pull/343039) at `b1444534fa6a61abb95a13ef0328e04b8a5e755d`

## Findings (1)

### 1. [medium] Coalesce sticky-progress updates during streaming

**Finding ID:** `PERF-79F6DDB3931C`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/chatListRenderer.ts:1238</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** main-thread CPU plus temporary arrays, annotated content objects, and MarkdownString allocations  
**Scaling:** For E streamed response mutations, T visible transcript items, and P accumulated response parts, the added path performs O(E\*(T+P)) work: getItems rebuilds its invalidated visible-items cache, the autorun scans P tool states, annotateSpecialMarkdownContent recreates the P-part annotated array, and getPersistentWorkingProgress performs several more P-sized scans. Provider token/progress updates make E large, while agent sessions with many tool calls make P realistically large.  
**Outcome:** increased main-thread CPU and GC pressure during response streaming, causing delayed token rendering and potential dropped frames in long agent conversations  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Persistent progress lived in the rendered response and was updated as part of the list's existing render pass; when that response was virtualized away there was no independent renderer-level listener reprocessing the entire response on every model mutation.  
**Changed behavior:** The added Event.any(viewModel.onDidChange, configuration changes) signal drives an unthrottled autorun for every chat model change. Each run locates the latest response, subscribes by scanning all of its tool/elicitation parts, then updateStickyProgress locates it again, annotates the complete response, derives progress through multiple full-array scans, and only afterward lets updateWorkingContent discover that the displayed label may be unchanged.  
**Confidence:** 0.97 — The event path is direct: each non-quiet response content update fires ChatResponseModel.onDidChange, ChatResponseViewModel forwards it to ChatViewModel.onDidChange, and the added signal synchronously reruns this autorun. ChatViewModel invalidates its getItems cache before listeners run, while updateStickyProgress annotates and repeatedly scans the full response. The exact millisecond cost varies with provider chunking and response size, but the multiplicative work and main-thread reachability are established.

**Causal diff evidence:** RIGHT line 1238 adds a signal over the broad viewModel.onDidChange event; the added autorun at lines 1239-1249 calls updateStickyProgress for every signal, and added lines 1259-1260 rebuild annotated content and derive progress from the full response before any unchanged-content short circuit.

During a long tool-heavy agent response, each streamed token/progress chunk repeats collection-wide work even if the sticky text remains “Working.” Users can see slower streaming updates and UI jank as accumulated response parts and transcript length grow.

**Evidence:** ChatModel.acceptResponseProgress calls Response.updateContent; Response.\_contentChanged fires onDidChangeValue for each non-quiet chunk; ChatResponseModel forwards that event, ChatResponseViewModel fires onDidChange, and ChatViewModel forwards it after invalidating \_visibleItemsCache. Thus viewModel.getItems() in the autorun recomputes/filter-scans the transcript on each chunk. annotateSpecialMarkdownContent iterates and allocates a new representation of every response part. getPersistentWorkingProgress then filters pending confirmations and calls getPersistentProgressState/getPersistentActivityLabel, which perform several additional full-part scans. updateWorkingContent's equality check occurs only after all this work. This is synchronous renderer work on the streaming UI path and remains active when virtualization has removed the response row.

**Suggested direction:** Track the latest response separately and derive a compact progress signature from only state that can change the sticky label (tail progress item, pending-confirmation candidates, active background counts, completion state). Coalesce content-change notifications to at most one update per animation frame, and skip annotation/progress recomputation when that signature is unchanged; preserve immediate updates for completion and blocking approval/question transitions.

### Scenario 1: An active bottom-composer Chat or Agents-window response streams while the user reads the latest turn or scrolls earlier transcript rows out of virtualization.

- Critical path: A provider response chunk is applied to ChatResponseModel, synchronously forwarded through ChatResponseViewModel and ChatViewModel, then the new sticky-progress autorun runs on the renderer's main-thread event stack before UI processing can continue. Existing transcript rendering also consumes the same model event; the sticky recomputation is additional work and is still performed when the response row is virtualized.
- Scaling input: Effective cardinality is one latest response per widget, but each of E stream mutations scans T visible transcript items after cache invalidation and the P accumulated parts of that response multiple times. Long agent runs can accumulate many tool/progress parts, and token/progress chunking makes E large.
- Effective concurrency: Updates are synchronous and serialized on the UI thread. There is no frame coalescing or limiter for the new autorun, so a burst of provider chunks produces a corresponding burst of recomputations.
- Cache behavior: ChatViewModel's visible-items cache is invalidated before every forwarded response change, so the first getItems call in each autorun is cold and rebuilds the list; the second lookup in updateStickyProgress is warm only within that same run. Annotated response content and progress derivation are not cached, and unchanged labels are detected only after recomputation.
- Mechanism confidence: High: the synchronous event chain, cache invalidation, full annotation allocation, repeated part scans, and absence of coalescing are directly visible in the changed code and transitive implementations.
- Magnitude uncertainty: Provider chunk frequency, transcript length, and tool-part count vary, so exact frame-time impact is workload-dependent; long tool-heavy agent responses are a realistic high-cardinality trigger.
- Expensive boundaries: none found
- Verdict: Reportable medium-severity CPU/GC regression: the PR adds unthrottled collection-wide work to every streaming mutation, including when virtualization previously avoided response rendering.

### Scenario 2: The active response completes, is canceled, or the widget switches to another chat session.

- Critical path: The response completion observable or view-model replacement synchronously clears/disposes the sticky part and its observation store. Session replacement also clears renderer pools through the existing updateViewModel path.
- Scaling input: One sticky part and one observation store per widget/session; cost is constant per completion, cancellation, or session switch.
- Effective concurrency: Lifecycle transitions are serialized on the UI thread; disposal cancels the autorun before the next session observation is installed.
- Cache behavior: No cross-session cache is retained by the sticky component. Event-backed observables unsubscribe when the disposed autorun loses its last observer.
- Mechanism confidence: High: MutableDisposable and DisposableStore ownership, DOM removal, and lazy event-observable unsubscription were traced.
- Magnitude uncertainty: Session-switch frequency varies but does not change the bounded ownership model.
- Expensive boundaries: none found
- Verdict: No additional finding: cleanup is bounded and the old session/listeners are released.

- Mechanism confidence: High after tracing ChatInputPart creation, ChatWidget wiring, CSS selectors, and ChatWorkingProgressContentPart/ChatWorkingLogo behavior.
- Magnitude uncertainty: Theme and narrow-layout reflows depend on host dimensions, but the diff adds no per-row or per-frame layout read/write loop.
- Expensive boundaries: none found
- Verdict: No reportable layout/rendering regression beyond the separately reported streaming recomputation; DOM cardinality is bounded and no forced-layout loop is introduced.

### Scenario 4: Persistent progress is toggled, or the chat uses read-only, minimal, or input-on-top rendering.

- Critical path: Configuration or renderer-option changes synchronously recompute eligibility; disabled/read-only/minimal paths clear the sticky part and retain the existing transcript-owned progress behavior. Input-on-top/minimal hosts are not wired to a sticky container.

- Magnitude uncertainty: The number of simultaneously open chat widgets varies, but configuration changes are not a hot enough trigger to justify a separate finding.
- Expensive boundaries: none found
- Verdict: No separate finding: fallback lifecycle and cardinality are bounded; broad configuration observation is subsumed by the streaming repeated-work finding.
