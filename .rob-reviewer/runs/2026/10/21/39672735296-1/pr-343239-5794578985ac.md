# Performance review: sessions: nest automatic sections inside custom groups

[PR #343239](https://github.com/microsoft/vscode/pull/343239) at `5794578985ac2d1d1f663a6531239695c836c311`

## Findings (2)

### 1. [medium] Avoid rescanning every group for each rendered group

**Finding ID:** `PERF-482EE75C75F2`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:5346</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Synchronous CPU work and temporary arrays while rebuilding the sessions tree  
**Scaling:** For G rendered custom groups and K nested-section memberships, this invokes getChildIds G times; each invocation filters all G groups, scans all K section memberships, and sorts the matching children, making the new work O(G² + G\*K) per list update.  
**Outcome:** Increased synchronous list-update latency and UI jank  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A single SessionGroupTree was built for the update, and each group's children were read from its parent index in O(1), yielding an O(G) traversal (apart from unrelated session work).  
**Changed behavior:** Rendering now calls ISessionGroupsService.getChildIds for every group. That helper rebuilds each result by filtering \[...\_groups.values()\], calling getSectionIdsInGroup (which scans \_sectionMembership), and sorting.  
**Confidence:** 0.99 — The recursive call count, full-map scans, prior indexed lookup, and synchronous update call paths are explicit in code. Only the exact user group count and resulting milliseconds are workload-dependent.

**Causal diff evidence:** The added call at line 5346 is inside recursive renderGroup, so it runs once for every rendered custom group. The deleted code used groupTree.getSubgroups(groupId), whose SessionGroupTree pre-indexes children by parent.

With many custom groups, any visible Agents Sessions list refresh performs quadratic group scans on the UI path, causing increasingly slow updates and interaction jank even when no sections are nested.

**Evidence:** SessionsList.update synchronously builds children before tree.setChildren and is reached by session changes, active-session changes, filters, group changes, and order changes. renderGroup recursively visits every custom group. SessionGroupsService.getChildIds at lines 520-525 filters the complete group map and calls the linear getSectionIdsInGroup at lines 516-518 on each visit, while SessionGroupTree.getSubgroups is backed by subgroupsByParentId.

**Suggested direction:** Build the mixed child-id lists once per SessionsList.update from the existing groupTree plus one section-by-parent index, or maintain equivalent indexes in SessionGroupsService, then have renderGroup consume those precomputed lists.

### 2. [medium] Bound bulk read-state updates for nested sections

**Finding ID:** `PERF-98AAA3264376`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:7182</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Concurrent per-session provider calls and agent-host IPC dispatches  
**Scaling:** One group action now selects every unread, unpinned session in every automatic section nested anywhere in the group subtree. For N such sessions, markAllRead starts N setSessionReadState calls concurrently, and agent-host sessions can additionally dispatch per unread chat.  
**Outcome:** A catalog-sized IPC burst, provider contention, refresh-event pressure, and degraded action/UI latency  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The group action passed only sessions with explicit membership in the custom-group subtree. Automatic sections had separate per-section actions, so one group action did not aggregate several sections' catalogs.  
**Changed behavior:** A single Mark All as Read on a parent group can now aggregate all unread sessions from all nested automatic sections and pass that expanded set to the existing unbounded bulk implementation.  
**Confidence:** 0.94 — The expanded selection, Promise.all fan-out, and provider/IPC path are directly traced. The number of unread sessions and backend sensitivity vary, which limits severity rather than confidence in the mechanism.

**Causal diff evidence:** The added condition at line 7182 expands the existing group bulk action beyond explicit group memberships to all sessions whose section parent is in groupIds; one group may contain multiple workspace, repository, or environment sections.

When a user nests several active repository/workspace/environment sections under one group and chooses Mark All as Read, the action can immediately fan out across the full unread catalog, overwhelming remote/provider channels and triggering a burst of list updates.

**Evidence:** getMarkAllSessionsReadAction passes the selected array to ISessionsManagementService.markAllRead. SessionsManagementService.markAllRead at line 1432 uses Promise.all(sessions.map(setSessionReadState)); setSessionReadState calls the provider once per session, and BaseAgentHostSessionsProvider.setSessionReadState emits change events and connection.dispatch IPC for changed sessions, with additional per-chat calls for aggregate unread chats. No limiter or provider grouping bounds aggregate concurrency.

**Suggested direction:** Run the expanded set through a bounded-concurrency executor (preferably in the shared markAllRead implementation) while preserving the returned promise's completion semantics; use a provider batch API only if one actually exists.

### Scenario 1: Visible Agents Sessions list rebuild after session, active-session, filter, grouping, or order changes

- Critical path: SessionsList.update synchronously filters and sections the catalog, builds group presentation, recursively renders every group, then calls tree.setChildren; all changed group-child discovery is on the UI critical path.
- Scaling input: G custom groups, K persisted automatic-section placements, S sessions, and the visible tree rows. The reported added child lookup costs O(G² + G\*K) after effective grouping.
- Effective concurrency: Single-threaded synchronous tree-model construction. Chat-observable updates are animation-frame scheduled, but many management, model, group, order, and filter events call update directly; there is no parallelism or backpressure within one rebuild.
- Cache behavior: A fresh SessionGroupTree indexes group children once per update, but the changed render path bypasses that index and reconstructs each group's mixed children by rescanning service maps. Warm storage/cache state does not avoid those scans.
- Mechanism confidence: High: recursive call count, service scan implementation, prior indexed behavior, and synchronous reachability are explicit.
- Magnitude uncertainty: The exact number of custom groups and frame time varies by user; the quadratic mechanism applies even with no nested sections and becomes visible as group count grows.
- Expensive boundaries: none found
- Verdict: Reportable repeated-work regression: the diff replaces indexed child lookup with one full group/section scan per rendered group.

### Scenario 3: Mark All as Read on a custom group containing automatic sections

- Critical path: The group action scans current sessions, includes sessions from nested automatic sections, then awaits SessionsManagementService.markAllRead; that method immediately starts one provider setSessionReadState promise per selected session.
- Scaling input: N unread, unarchived, unpinned sessions across every automatic section nested anywhere in the selected group subtree, after section/group placement precedence. Agent-host sessions may contain multiple unread aggregate chats per session.
- Effective concurrency: Promise.all creates effective concurrency N across sessions with no shared limiter; individual agent-host sessions may sequentially dispatch additional chat updates, while different sessions remain concurrent.
- Cache behavior: Sessions and provider objects are warm in memory, but read-state calls are neither deduplicated across the selected set nor coalesced/batched by provider. Empty/already-read sessions are filtered before the boundary.
- Mechanism confidence: High: the changed inclusion condition, Promise.all implementation, and concrete agent-host IPC path are directly traced.
- Magnitude uncertainty: Unread catalog size, provider implementation, and remote latency vary; those affect severity, not the unbounded fan-out mechanism.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/services/sessions/browser/sessionsManagementService.ts:1431-1433 and src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:7231-7260</code>: Per-session provider setSessionReadState, including agent-host connection.dispatch updates and possible per-chat dispatches; cardinality: Exactly one provider call for each of N selected unread sessions, plus up to each agent-host session's unread aggregate-chat count; all N session calls start concurrently.

- Verdict: Reportable concurrency-burst regression because one newly broadened group action can issue catalog-sized concurrent provider/IPC work.
