# Performance review: Make the Integrated Browser an external URI opener

[PR #342935](https://github.com/microsoft/vscode/pull/342935) at `1d033d6785b2df9cb1df7a5e8d46803407c913ec`

## Findings (1)

### 1. [medium] Keep localhost opens off extension discovery

**Finding ID:** `PERF-7CC230F969F3`  
**Location:** <code>src/vs/workbench/contrib/browserView/electron-browser/features/browserTabManagementFeatures.ts:617</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Extension scanning/activation work and extension-host IPC calls  
**Scaling:** Cold latency scales with extension discovery/activation; every warm click issues one concurrent canOpen IPC per registered extension opener for the scheme.  
**Outcome:** Increased latency on localhost link opens  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The BlockStartup contribution registered directly with IOpenerService. Its localhost check handled enabled local links, and OpenerService short-circuited without entering extension-backed opener discovery.  
**Changed behavior:** Enabled localhost links now await aggregate opener discovery, extension activation, and canOpen checks before the built-in Preferred opener is selected.  
**Confidence:** 0.97 — The changed registration and full call path are directly traced. Only the exact duration varies by extension state and installed openers.

**Causal diff evidence:** At RIGHT line 617 the contribution stops registering as a direct IExternalOpener and instead joins ExternalUriOpenerService's provider list, whose selection always awaits every provider.

With workbench.browser.openLocalhostLinks enabled, opening a localhost URL can be delayed by cold extension scanning/activation and, thereafter, by extension-host round trips before the Integrated Browser editor appears.

**Evidence:** ExternalUriOpenerService.getAllOpenersForUri awaits all providers. MainThreadUriOpeners.getOpeners awaits activateByEvent(onOpenExternalUri:http\[s\]), then getValidOpeners calls canOpen for every extension opener through proxy.$canOpenUri. Native and web extension initialization starts only at LifecyclePhase.Ready, while this contribution is registered at BlockStartup, so an early open can wait for scanning; warm opens still repeat one canOpen IPC per matching extension opener.

**Suggested direction:** Keep a fast path for the static Preferred localhost opener: inspect requested/configured overrides first, then avoid activating extension-backed providers when no override applies. Retain full enumeration for explicit extension overrides, prompts, and link-handler listing.
