# Performance review: Authenticate GitHub marketplace API requests via RFC 8693 token exchange

[PR #325815](https://github.com/microsoft/vscode/pull/325815) at `524003e6751f48796de3c6fd373e99a19952a745`

## Findings (1)

### 1. [medium] Defer protected-resource discovery until the index challenges

**Finding ID:** `PERF-D14FF88DB9EC`  
**Location:** <code>src/vs/workbench/services/extensionManagement/electron-browser/extensionGalleryAccountService.ts:254</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** HTTP network requests to protected-resource metadata endpoints  
**Scaling:** Each marketplace bootstrap or GitHub account/session revalidation performs one failed metadata GET for an origin-only service URL, or two sequential failed GETs for a path-bearing service URL, before the service-index GET; the negative result is not cached.  
**Outcome:** increased marketplace startup/revalidation latency from extra network round trips on the critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** For an eligible GitHub account, account resolution was local and the configured marketplace service index was fetched immediately, so an open marketplace required only the index request.  
**Changed behavior:** Every eligible GitHub account resolution now awaits protected-resource discovery before the manifest is requested, even when the marketplace is auth-disabled and publishes no protected-resource metadata.  
**Confidence:** 0.99 — The changed line, helper implementation, and manifest call ordering directly prove the additional sequential HTTP boundary before startup can progress. The exact server delay varies, but the extra one-or-two request cardinality for metadata-absent marketplaces is deterministic.

**Causal diff evidence:** The added line \`const protectedResource = await discoverMarketplaceProtectedResource(this.requestService, serviceIndexUrl);\` unconditionally inserts metadata discovery into the GitHub account path; before this PR the GitHub provider returned immediately after the local eligibility check.

Opening VS Code against an open GitHub-configured private marketplace now delays extension marketplace availability by at least one additional request round trip (two when the configured service URL contains a path). A slow or poorly routed \`/.well-known\` endpoint can hold the bootstrap much longer because this probe is awaited before the actual index request; session-change revalidations repeat the same delay.

**Evidence:** \`doGetAccount\` awaits \`getMarketplaceAccessToken\`, whose first operation at line 254 is \`discoverMarketplaceProtectedResource\`. \`fetchResourceMetadata\` tries the path-appended well-known URL and then the root URL sequentially when the configured URL has a path. \`WorkbenchExtensionGalleryManifestService.handleMarketplaceAccountAccess\` awaits \`galleryAccountService.getAccount\` before calling \`getExtensionGalleryManifestFromServiceUrl\`, so these optional probes are on the manifest critical path. The added open-index test still enters this code path but only asserts that no token exchange occurs, not that metadata discovery is skipped.

**Suggested direction:** Fetch the service index anonymously first and only perform protected-resource discovery/token exchange after a 401/403 challenge, then retry the index with the exchanged token. If the flow cannot be challenge-driven, cache and coalesce both positive and negative discovery results per configured service URL so open marketplaces do not pay repeated probes.

### Scenario 2: Bootstrap and periodically refresh an RFC 8693-gated GitHub marketplace

- Critical path: Cold bootstrap serially resolves protected-resource metadata, resolves authorization-server metadata, reads the matching GitHub session, exchanges the token, and fetches the service index. - Scaling input: One configured marketplace per window. A successful cold/refresh cycle normally performs one PRM GET, one AS metadata GET when the first discovery URL succeeds, one token POST, and one index GET; malformed/mismatched AS metadata can expand discovery to three sequential GETs.
- Effective concurrency: Operations within one resolution are serial. The refresh timer owns one disposable timeout and replaces the previous timer. Separate session/default-account events can start overlapping uncancelled network requests, but realistic aggregate burst size was not proven.
- Cache behavior: The exchanged access token remains published until an account event or refresh timer. Its expiry schedules refresh at 75% with bounds. PRM and AS metadata are not cached, so cold and refresh behavior have the same metadata call count; this periodic overhead is modest and tied to token lifetime, so it was not reported separately.
- Mechanism confidence: High for call counts and serial ordering; medium for any user-visible impact beyond the reported open-marketplace case.
- Magnitude uncertainty: Token lifetimes and server RTTs vary. The serial call path is certain; the periodic metadata overhead is bounded to one marketplace and ordinarily once per 75% of token lifetime.
