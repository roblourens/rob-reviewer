# Performance review: ci: reuse the shared node\_modules cache in Monaco Editor checks

[PR #343088](https://github.com/microsoft/vscode/pull/343088) at `de475ad7aed020f5d62d04dca825a099b5fd5575`

## Findings (1)

### 1. [medium] Keep a warm cache for non-main dependency keys

**Finding ID:** `PERF-76F972EFF5AC`  
**Location:** <code>.github/workflows/monaco-editor.yml:31</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** npm package downloads plus filesystem and install CPU work for the repository's full dependency tree  
**Scaling:** The full \`npm ci\` is repeated once per Monaco workflow run for as many commits and reruns as a PR remains on a key that the main-only warmer never publishes; release-branch PRs can remain in this state indefinitely after their dependency graph diverges from main.  
**Outcome:** Repeated multi-minute critical-path installs, increased network/filesystem load, and slower Monaco checks.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** On an exact miss, the workflow restored the latest node\_modules/npm-cache prefix, ran \`npm ci\`, and \`actions/cache\` saved the resulting exact PR-scoped entries; later runs with the same dependency key skipped installation.  
**Changed behavior:** The new composite action restores only the exact \`node\_modules-compile\` key and never saves. Because \`pr-node-modules.yml\` publishes that key only on pushes to \`main\`, a dependency-changing PR or a \`release/\*\` PR with a different lockfile misses on every run and executes both apt installation and a cold \`npm ci\`.  
**Confidence:** 0.97 — The miss and repetition behavior follows directly from the exact hashed key, main-only cache producer, release/dependency-changing triggers, and absence of any save step. The precise install duration varies by runner/network, but the PR description itself corroborates that a cold miss costs minutes; that uncertainty affects magnitude, not the mechanism.

**Causal diff evidence:** RIGHT line 31 replaces the prior saving \`actions/cache\` path with the restore-only composite action; adjacent added lines 27-29 explicitly state that PR runs never save, and the deleted cache steps included both \`restore-keys\` fallbacks and automatic post-job saves.

A PR that changes dependencies—and especially an active release-branch PR whose lockfile no longer matches main—pays the full dependency installation on every update or rerun instead of only the first miss, delaying required Monaco checks by minutes and repeatedly downloading packages.

**Evidence:** \`computeNodeModulesCacheKey\` hashes every dependency section and lockfile, while the replacement action uses an exact key with no restore keys and has no save step. The only saver for \`node\_modules-compile\` is \`pr-node-modules.yml\`, whose trigger is \`push\` to \`main\`; this workflow also explicitly runs for \`release/\*\`. The deleted \`actions/cache\` steps supplied prefix fallbacks and automatically saved exact node\_modules and npm-cache entries after a successful miss.

**Suggested direction:** Preserve the shared exact-hit path, but ensure supported non-main keys can become warm without restoring the old per-PR cache flood—for example, run the shared warmer for active \`release/\*\` base branches and provide a bounded PR-local or shared npm-download fallback for dependency-changing keys.
