<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, boundary-fanout, cleanup-lifecycle

### Scenario 1: A running MCP child server's plugin is republished under a new URI and the session customization replacement is emitted.

- Critical path: The state manager first reduces the customization action, then synchronously fires onDidEmitEnvelope; the new controller listener scans the resulting in-memory customization inventory and relocates matching live child state before envelope dispatch returns.
- Scaling input: Top-level customizations plus their MCP children, and the controller's live MCP-server map. A relocation adds one lookup over the inventory for each orphaned live child whose server name is unique; ordinary entries are filtered without that lookup.
- Effective concurrency: Single-threaded synchronous event dispatch inside one state-manager action; relocation updates are coalesced in one observable transaction. No async fan-out or concurrent boundary work is added.
- Cache behavior: The controller reads authoritative session state directly and allocates transient Set/Map indexes per qualifying customization envelope; there is no cold/warm external cache and no negative-cache retry behavior.
- Mechanism confidence: High confidence in the synchronous O(customizations + children + relocated-live-children × inventory) CPU/allocation mechanism; low evidence that realistic cardinality or frequency makes it user-visible.
- Magnitude uncertainty: Plugin catalogs and MCP-child counts vary, but realistic plugins expose few MCP servers and republish is an administrative event rather than a per-token, per-frame, or per-message hot path.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. The diff performs bounded in-memory reconciliation on the customization-change path and introduces no expensive boundary operation.

### Scenario 2: Ordinary SessionCustomizationUpdated and SessionCustomizationsChanged actions, including Copilot plugin sync and Codex workspace skill/hook refreshes.

- Critical path: Each qualifying action is synchronously reduced and then invokes every MCP controller subscribed to that session; each listener scans the current customization tree even when no child container replacement occurred.
- Scaling input: Number of emitted top-level update actions times customization containers and children, multiplied by MCP controllers sharing the owner session. Codex groups skills by workspace root/scope and hooks into one container, limiting effective update cardinality rather than emitting one action per skill/hook child.
- Effective concurrency: Providers sequence or coalesce refreshes (Codex directory operations use a sequencer and native catalog notifications are debounced); state actions and listeners run serially. Multiple controllers create synchronous listener fan-out but no concurrency burst.
- Cache behavior: No memoized index is used; each envelope rebuilds transient published-id and child-name indexes. This is repeated CPU/allocation work, but there is no I/O cache, remote cache, or cache-miss amplification.
- Mechanism confidence: High confidence that scans fan out synchronously; moderate-to-low confidence that practical inventories/controller counts make the added CPU and transient allocations materially expensive.
- Magnitude uncertainty: Large multi-root catalogs and many retained Codex runtimes can multiply scans, but grouping keeps action cardinality small and repository evidence does not establish a realistic latency or throughput symptom.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_doRefreshSkillHookCustomizations</code>: Discover workspace agents, instructions, and skills before publishing the Codex refresh.; cardinality: One grouped discovery pass per coalesced/serialized refresh across configured workspace roots; this boundary occurs before the changed listener executes.
    - Introduced by diff: false; previous behavior: The same filesystem discovery and grouped publishing occurred before the PR; only the subsequent in-memory envelope listener is new.; critical-path effect: Discovery must finish before customization update actions are emitted; the added listener does not add, repeat, or move these filesystem calls.
  - network at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_fetchSkillHookContainers via \_doRefreshSkillHookCustomizations</code>: Fetch Codex native skill and hook catalogs through the app-server before constructing grouped containers.; cardinality: Grouped catalog requests per serialized refresh, independent of the number of customization children published.
    - Introduced by diff: false; previous behavior: Identical native catalog fetches occurred before the diff.; critical-path effect: Requests complete before the update loop; the changed code neither invokes them nor moves them onto a new path.
- Verdict: No finding. The broad listener adds repeated in-memory work, but traced grouping, event frequency, and lack of expensive boundaries do not support a high-confidence actionable performance regression.

### Scenario 3: MCP lifecycle transitions for top-level and child servers after the controller is installed.

- Critical path: Child transitions emit SessionMcpServerStateChanged and do not trigger the new listener. Top-level transitions emit SessionCustomizationUpdated, which synchronously triggers one inventory scan after the state update.
- Scaling input: Top-level lifecycle transition count times customization-tree size and same-owner controller count. Lifecycle changes are server-state events, not token/stream events.
- Effective concurrency: Provider updates are applied synchronously in observable transactions; state envelopes are serialized by JavaScript execution. No new limiter, queue, IPC, or subprocess is involved.
- Cache behavior: Runtime state is held in the existing observable live map. The new reconciliation has no persistent cache and cannot accumulate keys; transient indexes are released after each call.
- Mechanism confidence: High confidence in which action types trigger the listener and in the absence of an external boundary; low confidence in material impact.
- Magnitude uncertainty: Users may configure varying MCP server counts, but no evidence shows lifecycle transitions at a frequency or inventory size that produces user-visible CPU, GC, startup, or throughput degradation.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. The added scan is limited to top-level customization updates and does not affect the narrower high-frequency child-state action.
