<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** boundary-fanout, repeated-work, cleanup-lifecycle

### Scenario 1: Normal run\_in\_terminal command in a fresh or reused terminal using no/basic shell integration

- Critical path: Terminal initialization/reuse, xterm readiness, the existing idle wait, one PTY write for the command, then command completion/idle detection. The listener change is passive and does not add work before progress.
- Scaling input: One listener callback per input write rather than per PTY output chunk; command count controls executions, with one cached foreground terminal per chat session.
- Effective concurrency: Foreground commands are serialized through one reused terminal; background commands use separate terminals. The changed strategy operations remain sequential and add no aggregate concurrency.
- Cache behavior: Foreground terminal association is reused warm per chat session; cold creation still performs the unchanged terminal/profile/shell-integration setup. No cache key, miss, or invalidation behavior changed.
- Mechanism confidence: High: terminalInstance shows onData is PTY output while onDidInputData fires after process writes from keyboard/tool input; strategy call flow and waits are explicit.
- Magnitude uncertainty: Exact output-event volume varies by command, but the changed listener strictly moves away from the potentially high-volume PTY output stream and does not increase normal command latency.
- Expensive boundaries:
  - subprocess at <code>src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/basicExecuteStrategy.ts:218 and noneExecuteStrategy.ts:88</code>: Write the requested command to the terminal PTY via ITerminalInstance.sendText; cardinality: One command write per invocation, plus the pre-existing optional Ctrl+U write only when actual input is pending and the shell supports it.
    - Introduced by diff: false; previous behavior: The same command write occurred, while any shell output could mark the prompt as having pending input and cause an unnecessary Ctrl+U PTY write plus a 100 ms idle wait.; critical-path effect: The requested command write remains on the critical path; the diff does not increase normal-path boundary calls and avoids classifying high-volume shell output as pending input.
- Verdict: No regression. The listener reduces callback frequency for output-heavy commands and can remove unnecessary pre-command PTY writes/waits.

### Scenario 2: run\_in\_terminal on Windows PowerShell with pending terminal input

- Critical path: After the existing pre-execution idle wait, shell/OS detection now skips Ctrl+U and its following 100 ms idle wait, then sends the command.
- Scaling input: One shell classification per command invocation; constant-size path/enum checks. Effective boundary cardinality drops from two PTY writes to one when pending input is recorded.
- Effective concurrency: Operations are serialized within the terminal strategy; no new task, queue, or parallel PTY activity is introduced.
- Cache behavior: No cache participates. Detection uses current terminal shell type, launch executable, and OS on each invocation with constant work.
- Mechanism confidence: High: the helper result directly gates the existing sendText and waitForIdle calls.
- Magnitude uncertainty: Frequency depends on Windows PowerShell use and pending-input state, but direction is definitively reduced work.
- Expensive boundaries:
  - subprocess at <code>src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/strategyHelpers.ts:26 and noneExecuteStrategy.ts:75/basicExecuteStrategy.ts:207</code>: PTY input writes for Ctrl+U and the requested command; cardinality: Changed from optional Ctrl+U plus command to command only for Windows PowerShell; one removed PTY write and one removed 100 ms idle wait per affected invocation.
    - Introduced by diff: false; previous behavior: When the pending-input flag was true, the strategy wrote Ctrl+U, waited for 100 ms of PTY idleness, then wrote the command.; critical-path effect: The diff shortens this path by removing the unsupported clearing write and wait.
- Verdict: No regression. This is a bounded latency and boundary-call reduction.

### Scenario 3: Basic shell integration reuses a terminal whose previous command remains active after idle fallback

- Critical path: The strategy first waits for PTY idleness, observes executingCommandObject, writes Ctrl+C, waits for 100 ms of post-interrupt idleness, then writes the next command.
- Scaling input: At most one added interrupt PTY write and one idle wait per new invocation while a prior command object is still executing; it does not scale with output history or collection size.
- Effective concurrency: The interrupt, idle wait, and next command are deliberately serialized. No burst or per-item parallelism exists.
- Cache behavior: The warm foreground terminal is reused; there is no result cache. Shell integration state is read directly from the existing command-detection capability.
- Mechanism confidence: High for the added boundary and critical-path wait; high that it is limited to an already-running prior process and one operation per invocation.
- Magnitude uncertainty: This recovery state is uncommon and exact process response time varies; the explicit idle duration is 100 ms after the last output.
- Expensive boundaries:
  - subprocess at <code>src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/executeStrategy/basicExecuteStrategy.ts:203</code>: Send Ctrl+C through the terminal PTY before the next command; cardinality: One newly guaranteed interrupt write when command detection reports an active prior command; previously this happened only if the pending-input flag was also true.
    - Introduced by diff: true; previous behavior: If receivedUserInput was false, the strategy skipped the interrupt and immediately wrote the next command despite the active command object.; critical-path effect: Adds one PTY write and a 100 ms idle interval on this recovery path before sending the next command, while preventing the next command from being written into the still-running process.
- Verdict: No reportable regression. The added work is bounded, occurs only on a degraded recovery path, and is required to preserve command execution semantics rather than redundant scalable work.

### Scenario 4: Lifetime of the terminal input listener on cached and disposed tool terminals

- Critical path: The listener only updates a boolean on input events and is off the command critical path except for the strategy's later boolean read.
- Scaling input: One listener per newly created tool terminal; cached foreground reuse does not register another listener, and disposal removes it.
- Effective concurrency: Callbacks execute synchronously per input event with constant work; no queued async work or concurrency is introduced.
- Cache behavior: Listener ownership follows the cached terminal lifetime and is disposed once with terminal disposal; cache reuse does not duplicate registration.
- Mechanism confidence: High: \_registerInputListener is called only after terminal creation, cached terminals return before it, and Event.once(onDisposed) disposes the subscription.
- Magnitude uncertainty: Input event frequency varies with user/tool writes, but callback work is constant and output-heavy PTY traffic no longer invokes it.
- Expensive boundaries: none found
- Verdict: No cleanup or retention regression; listener cardinality and lifecycle remain bounded, with a cooler event source.

**Summary:** Reviewed all seven changed files and complete diff pages. Traced PTY writes, idle waits, listener ownership, normal/recovery execution, shell detection, cache reuse, and concurrency. No high-confidence actionable performance regression was introduced, and the PR does not establish a shipped performance-regression fix requiring blame attribution.
