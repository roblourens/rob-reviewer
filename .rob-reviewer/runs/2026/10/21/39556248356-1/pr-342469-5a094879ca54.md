### 1. [medium] Coalesce Working Set refreshes during edit bursts

**Finding ID:** `PERF-0807A12F9E1D`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:1486</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Database reads, decoded file strings, identity-map allocations, and diff-worker CPU  
**Scaling:** For a subscribed Working Set, cost grows with tool-edit event count multiplied by accumulated edit rows and changed files.  
**Outcome:** Repeated CPU, GC, and database work delays Working Set updates and reduces agent-host throughput.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Mid-turn refresh requests reset a 5-second debounce, combining a burst of edits into one full recomputation; turn completion still forced a final refresh.  
**Changed behavior:** Every onToolCallEditsApplied event now immediately calls refreshWorkingSetChangeset, and edits arriving during an active compute can queue another complete computation.  
**Confidence:** 0.98 — The diff replaces a 5-second resettable debounce with a direct refresh on every stored tool edit. The refresh reads every source database, scans all historical edit rows, reconstructs each file identity, reads content, and computes per-file diffs. Calls arriving after a queued compute starts can enqueue another full pass, so only exact pre-start bursts coalesce.

**Causal diff evidence:** RIGHT line 1486 replaces the deleted debounced Working Set scheduler with an immediate refresh call on each tool-edit event.

An edit-heavy turn in a large or long-running subscribed session repeatedly rescans all recorded edits and rediffs all changed files.

**Evidence:** The changed call reaches \_computeWorkingSetChangeset, computeWorkingSetFiles, and computeUnionedFileDiffs. That path calls getAllFileEdits for every source, scans and deduplicates all rows, reads before/after content, and invokes computeDiffCounts per effective file identity. The deleted scheduler used disposableTimeout with \_DIFF\_DEBOUNCE\_MS, which is 5000 ms.

**Suggested direction:** Coalesce requests that arrive while a compute is running, or incrementally recompute only the edited file/rows, while preserving a final ordered flush at turn completion.

### 2. [medium] Hydrate review entries lazily instead of opening every changed file

**Finding ID:** `PERF-2A39FBA6368A`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostEditReview.ts:402</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** File/content-provider reads, resolved text models, full-file strings, and diff-worker CPU  
**Scaling:** Cold review cost is per effective Working Set file: up to two snapshot reads plus a disk/model resolve and multiple full-text diff computations, processed serially; retained model/content memory grows with total changed file bytes.  
**Outcome:** Excessive I/O and CPU, slow review readiness, and retained-memory growth when opening sessions with large multi-file changes.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** AgentHostSnapshotController exposed an empty entries list and did not read Working Set snapshot contents, resolve each changed file into a text model, or compute editor diffs for all files.  
**Changed behavior:** The new review loops through the complete Working Set and awaits \_updateFile for each entry. Cold \_updateFile calls \_readContents, \_createEntry, \_reloadFromDisk, and \_prepareFile before publishing and retaining an entry.  
**Confidence:** 0.96 — The new review is fed a deduplicated Working Set file list and serially awaits \_updateFile for every non-deleted file. On a cold entry, the traced path reads baseline/current snapshots, creates a model reference, force-resolves the disk model, materializes strings, computes full-text worker diffs, and retains the model. Warm updates with an unchanged version skip this work, so the cold fan-out and its cardinality are well established; only the exact cost per repository is uncertain.

**Causal diff evidence:** agentHostEditReview.ts is entirely added by this PR; RIGHT line 402 introduces the per-file awaited hydration loop reached as soon as the Working Set subscription becomes ready.

Opening an opted-in Agent Host chat whose session changed tens or hundreds of files eagerly loads and diffs every file even if the user never opens the file or the multi-diff view; entries arrive serially and the work can continue behind the chat UI.

**Evidence:** RIGHT line 402 is inside \`for (const file of files)\` and serially awaits \`\_updateFile\`. The cold path performs \`\_fileService.readFile\` for baseline/current content, \`createModelReference\`, \`model.resolve({ forceReadFromFile: true })\`, and \`computeStringEditFromDiffWithMetadata\`; each created entry keeps the model reference until decision/disposal. \`isSameWorkingSetFile\` only avoids this after the cold version is hydrated.

**Suggested direction:** Represent Working Set files with lightweight entries first, then resolve/read/diff only files that are open, visible, or explicitly requested. If some eager hydration is required for overlays, use a small shared limiter and prioritize open editors rather than serially processing the entire set.

### 3. [medium] Drop published Working Sets when their subscriptions end

**Finding ID:** `PERF-243A6EE3C4C8`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:574</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** Retained Working Set keys and synchronous scans/URI parsing over every file in their persisted changeset states  
**Scaling:** Per edit-start/end CPU grows with the sum of files across every Working Set ever published for owners still retained by the host, not with currently subscribed Working Sets or the edited resource.  
**Outcome:** Increasing synchronous CPU overhead and edit-event latency over a long-lived process as users visit more chat sessions.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** There was no published-Working-Set registry and edit-tool lifecycle events did not scan historical Working Set states.  
**Changed behavior:** Successful computes permanently add changesetUri to \_publishedWorkingSets. onDidChangeEditing then loops that whole set and each state.files array on both edit start and edit end; removing a subscription leaves the key present.  
**Confidence:** 0.95 — The new set is populated after every successful subscribed Working Set compute, but subscription removal does not delete from it; deletion occurs only when the changeset state disappears or the owner itself is removed. Every edit start/end synchronously traverses every retained changeset and every file. The lifetime/scaling mechanism is direct; uncertainty is only how many historical sessions a typical long-lived host retains.

**Causal diff evidence:** RIGHT line 574 introduces retention independent of subscription lifetime; the same diff adds the onDidChangeEditing listener and full-set scan that consume those retained keys.

After opening/reviewing many sessions, every later agent edit scans all files from those earlier sessions even when no client observes them, making edit coordination progressively more expensive.

**Evidence:** RIGHT line 574 adds every published URI to \`\_publishedWorkingSets\`. \`\_publishWorkingSetEditing\` iterates that set and every \`state.files\`, parsing and comparing each URI. \`AgentHostChangesetSubscriptionService.removeSubscription\` only updates its own map/event, while this service deletes the new set entry only in \`onChangesetOwnerRemoved\` or when \`getChangesetState\` returns no state.

**Suggested direction:** Track only actively subscribed Working Sets: remove the URI on subscription removal (and failed/unpublished teardown), or derive/index active states by canonical file resource so each editing event touches only matching subscribed sets.

- Effective concurrency: A SequencerByKey serializes computes per owner, but requests arriving after a compute starts enqueue another pass. Within each compute, all effective file identities schedule content reads and diff work concurrently without a shared limiter.
