## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `cli/src/tunnels/agent\_host.rs:2281` (`RIGHT`)  
**Blamed base line:** `cli/src/tunnels/agent\_host.rs:1919`  
**Introducing path:** `cli/src/tunnels/agent\_host.rs`  
**Introducing commit:** `f5b3eba94e565baf60f563b8e13b3b6647dde4a1`  
**Mechanism family:** `repeated-work`  
**Performance category:** `network`  
**Confidence:** 0.96

**Mechanism:** A gateway-specific 16 MiB frame cap rejected otherwise-supported chat snapshot messages; the silent proxy return left the tunnel client idle until its liveness watchdog reconnected and restored subscriptions, repeatedly serializing and retrying the same large snapshot.

**Symptom:** Large tunnel-backed chats stall for roughly one 25-second liveness window and then repeatedly reconnect, recreating and retrying a 16+ MiB snapshot instead of completing the subscription.

**Fixed behavior:** The shared gateway WebSocket config raises both frame and assembled-message limits to 100 MiB and is applied to the client-facing socket and both target dial variants, so realistic large chat snapshots pass once instead of entering the liveness/reconnect/snapshot retry cycle. The added peer Close propagation also makes remaining over-limit failures visible without waiting for the 25-second watchdog.

**Evidence:** The introducing commit created the protocol-v6 gateway with `WebSocketStream::from_raw_socket(..., None)`, leaving tungstenite's 16 MiB frame cap in place, while the only browser tunnel socket factory uses `connectWebSocketOverDuplex`, whose established cap is 100 MiB. Agent-host `subscribe`/reconnect responses contain state snapshots (including chat `turns`) and `WebSocketProtocolTransport.send` JSON-stringifies each response into one WebSocket message. On a frame between 16 and 100 MiB, the gateway therefore rejected a message that both endpoint transports permit. The client liveness path waits 5 s before ping plus 20 s before forcing a close, and its transport-close path schedules another reconnect that restores current subscriptions, causing the host to rebuild and attempt the same snapshot again. Blame identifies f5b3eba94e565baf60f563b8e13b3b6647dde4a1 as introducing the default-config gateway line.

### Scenario 1: Open or reconnect a tunnel-backed chat whose subscription snapshot is between 16 MiB and 100 MiB.

- Critical path: The browser must open the dev-tunnel relay, upgrade \`/agent-host/select\`, select an endpoint, dial the endpoint, complete protocol initialization/subscription, and receive the snapshot before the chat is usable. The large snapshot serialization and both WebSocket hops are on this critical path.
- Scaling input: Serialized chat snapshot size and the number of liveness/reconnect attempts. The changed successful path remains one target dial and one forwarded frame per snapshot; memory scales linearly with a single payload up to 100 MiB.
- Effective concurrency: Each gateway session forwards one surfaced WebSocket message at a time through a single \`tokio::select\!\`; client-to-target and target-to-client compete in that loop, while different gateway sessions run in independent Tokio tasks. No additional fan-out or concurrency burst is introduced by the new limits.
- Cache behavior: No payload cache exists on the gateway. The selected endpoint inventory is read once and the registry is reread for an existing selection; chat subscription snapshots are rebuilt by the agent host. Warm reconnects may use protocol replay when available, but a fresh/baseline restore sends snapshots again, so the old frame rejection could repeatedly recreate the same large response.

### Scenario 2: A client or selected target errors, including a frame above the new 100 MiB cap.

- Critical path: After either proxy side errors, notifying the peer is now on the session cleanup path. It is not on successful message forwarding; the timeout bounds cleanup to five seconds if the peer cannot accept the close.
- Scaling input: Number of simultaneously failing gateway sessions; cost is one small close frame and one bounded task lifetime per failed session.
- Effective concurrency: At most one close handshake is attempted for the surviving peer of a failed session. Failed sessions can close concurrently, but each is independently bounded by one timeout and no retry loop is added.
- Cache behavior: No cache applies. Error handling is per connection, and the close frame is generated from the immediate tungstenite error.
- Mechanism confidence: High: all four changed error branches call the bounded close helper, and the helper wraps the close future in a five-second timeout.
- Magnitude uncertainty: How often peers stall during close is unknown, but retained work is strictly one failed session for at most five seconds and replaces a longer observed liveness wait.
- Expensive boundaries:
  - network at <code>cli/src/tunnels/agent\_host.rs::close\_gateway\_peer and proxy\_gateway\_frames</code>: Send close code 1009 for capacity failures or 1011 for other proxy errors to the surviving peer.; cardinality: At most one WebSocket Close write per proxy failure.
    - Introduced by diff: true; previous behavior: The proxy returned without explicitly notifying the opposite peer; on the tunnel client path this could leave the client silent until liveness timeout.; critical-path effect: It delays destruction of that failed session by only the close write duration, bounded at five seconds; it removes the client's prior wait for its 25-second liveness watchdog.
- Verdict: No reportable regression. The added bounded close is cleanup work only on failure and reduces stale-session/reconnect latency; it neither retries nor retains resources without a limit.

### Scenario 3: Forward ordinary gateway traffic at or below 16 MiB.

- Critical path: The successful forwarding critical path remains read one frame from one side and send it to the other. Configuration changes only validation bounds; the close helper is not reached.
- Scaling input: Number and size of ordinary frames and active sessions, unchanged from the base revision.
- Effective concurrency: Unchanged single-session forwarding loop and independent per-session tasks; no new parallel operations or queues.
- Cache behavior: No cache or coalescing behavior changes for ordinary frames. Gateway configuration is a small value constructed once per accepted or dialed WebSocket, with no payload-sized eager allocation evidenced.
- Mechanism confidence: High: the normal forwarding branches are unchanged except for failure-only close calls.
- Magnitude uncertainty: No material uncertainty: the changed config does not add boundary calls on this path.
- Expensive boundaries:
  - network at <code>cli/src/tunnels/agent\_host.rs::proxy\_gateway\_frames</code>: Forward ordinary WebSocket frames bidirectionally between tunnel client and target.; cardinality: One existing target dial per selected session and one send per received frame.
    - Introduced by diff: false; previous behavior: Identical forwarding cardinality and ordering; only the accepted maximum payload differed.; critical-path effect: Unchanged for frames at or below the old 16 MiB cap.
- Verdict: No performance change on the successful hot path.
