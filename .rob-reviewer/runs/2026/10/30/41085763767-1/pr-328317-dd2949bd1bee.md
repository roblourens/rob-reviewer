# Performance review: Fix multi-diff and native host event leaks

[PR #328317](https://github.com/microsoft/vscode/pull/328317) at `dd2949bd1bee6fc1b15d6e3da8b904c6c862894a`

## Findings (1)

### 1. [medium] Do not await the sibling model after this item has already failed

**Finding ID:** `PERF-29E5EC241222`  
**Location:** <code>src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:195</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** A pending text-model acquisition backed by filesystem, remote-file-provider, or virtual-content-provider work.  
**Scaling:** The added delay for a failed item is the remaining duration of its sibling acquisition; because the aggregate document load waits for every item, one slow or non-settling sibling among the multi-diff resources gates the entire editor.  
**Outcome:** Increased editor-open latency and potentially an indefinitely blocked critical path.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Promise.all rejected as soon as either model-reference acquisition rejected; the catch returned undefined for that item immediately, allowing the aggregate document load to progress without waiting for the sibling request.  
**Changed behavior:** Each item's two model-reference acquisitions are now awaited with Promise.allSettled, so a rejection no longer releases that item until the other acquisition has also settled.  
**Confidence:** 0.98 — The before/after Promise semantics, the setInput-to-Promise.all critical path, and the transitive file/content-provider boundary are directly established in repository code. Only prevalence and provider duration are uncertain, which limits severity rather than mechanism confidence.

**Causal diff evidence:** The deleted Promise.all failed fast on the first rejection, while added line 195 explicitly waits for both acquisitions to settle before the rejection branch can return undefined.

Opening an SCM/Chat/Agents multi-diff can remain blank or loading after one side is already known to be unusable whenever the other side is slow; a stalled remote or virtual-document provider can prevent the editor from opening indefinitely.

**Evidence:** MultiDiffEditor.setInput awaits input.getViewModel(); \_createModel awaits updateDocuments.get(); updateDocuments awaits Promise.all of every item promise. createModelReference resolves file-backed resources through textFileService.files.resolve/fileService and virtual resources through async content providers. Therefore line 195 puts the slower sibling request on the editor-open critical path even after the other request has rejected.

**Suggested direction:** Keep fail-fast completion for the item, but attach disposal handlers to both acquisition promises so any reference that fulfills after its sibling rejects (or after the item store is disposed) is disposed asynchronously rather than awaited on the editor-open path.


## Performance regression fixes detected (1)

### 1. cleanup-lifecycle

**Fix location:** `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:218` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:194`  
**Introducing path:** `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts`  
**Introducing commit:** `48e7527ada52bdc8855d727096e492218f640390`  
**Mechanism family:** `cleanup-lifecycle`  
**Performance category:** `memory`  
**Confidence:** 0.99

**Mechanism:** When one Promise.all branch rejected, the callback returned without retaining or disposing an IReference later produced by the sibling createModelReference call; AsyncReferenceCollection keeps the underlying ResourceModelCollection reference count until that handle is disposed.

**Symptom:** Failed multi-diff item resolution could retain text model references and their resolved models for the process lifetime.

**Fixed behavior:** The change waits for both acquisitions, adds every fulfilled reference to a DisposableStore, and disposes that store when either acquisition failed or the cached item was removed while resolution was pending.

**Evidence:** Base line 194 starts the fail-fast Promise.all whose catch had no handle to a late sibling result. AsyncReferenceCollection.acquire returns the sole disposable decrement for ResourceModelCollection's counter. Added fulfilled-result registration followed by disposal at line 218 closes that failure path. Blame identifies commit 48e7527ada52bdc8855d727096e492218f640390 as introducing the base line.
