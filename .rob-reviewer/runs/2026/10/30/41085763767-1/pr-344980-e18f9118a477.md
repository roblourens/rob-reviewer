# Performance review: files: support \`\!\` exclude exceptions in files.exclude and search.exclude

[PR #344980](https://github.com/microsoft/vscode/pull/344980) at `e18f9118a4771a360b30ab40f516ca9371988c67`

## Findings (1)

### 1. [high] Keep exception text-search runs bounded before parsing

**Finding ID:** `PERF-A2E459D641FD`  
**Location:** <code>src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts:82</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** ripgrep subprocess output, JSON parsing/allocation, queued result-filter promises, and conditional sibling-check filesystem reads  
**Scaling:** Cost grows with every raw text match under the exception globs, including duplicate and include-rejected matches, rather than with the configured 20,000 accepted-result limit.  
**Outcome:** Unbounded CPU/GC and I/O pressure can greatly delay or hang text search.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Text search passed include/exclude globs to a single ripgrep run and constructed RipgrepParser with options.maxResults (default 20,000), so the subprocess was killed once that bounded number of matches was parsed.  
**Changed behavior:** When any exclude exception is present, the added second run omits normal include globs and sets maxResults to Number.MAX\_SAFE\_INTEGER; only after each ripgrep JSON match is parsed does the callback deduplicate and the outer TextSearchManager apply query includes/excludes.  
**Confidence:** 0.96 — The changed subprocess call, parser limit, omitted include globs, outer acceptance counter, and optional per-result readdir path are all directly traced. Exact duration depends on workspace contents and query selectivity, but the unbounded scaling and critical-path reachability are deterministic.

**Causal diff evidence:** The added call at line 82 explicitly replaces the configured parser bound with Number.MAX\_SAFE\_INTEGER for the new exception run; the same diff's getRgArgs exception branch supplies only exception globs and defers includes to result filtering.

With a broad exception (for example \!\*\*/\*.js), a narrow files-to-include filter, and a common term in a workspace containing generated or ignored dependencies, search can consume a full core, produce heavy GC/subprocess traffic, and remain busy long after the configured result limit would previously have stopped it.

**Evidence:** searchWithRipgrep constructs RipgrepParser from options.maxResults and kills ripgrep only on its hitLimit event. For the new exception call, that limit is Number.MAX\_SAFE\_INTEGER. getRgArgs also skips pushIncludeAndExcludeGlobs for exception runs, while TextSearchManager increments its limit only after QueryGlobTester accepts a result. Thus a narrow files-to-include filter plus a broad exception such as \!\*\*/\*.js and a common query can make ripgrep emit and VS Code JSON-parse every matching line in regular and ignored JS trees even though almost all are discarded. If a sibling-clause exclude is configured, each forwarded candidate can additionally create a pfs.readdir-backed promise retained in testingPs until provider completion.

**Suggested direction:** Preserve a finite candidate bound by applying the intersection of exception and include/query filters before text matches reach RipgrepParser/TextSearchManager—for example, partition exception runs by anchored include roots or synthesize intersected globs—and bound any unavoidable post-filter pipeline/concurrency rather than using Number.MAX\_SAFE\_INTEGER.
