# Performance review: Avoid reading large agent host files when opening Changes

[PR #345124](https://github.com/microsoft/vscode/pull/345124) at `ea93357d180386eccecd1bebe1500abdf4998a66`

## Findings (1)

### 1. [medium] Reuse the preflight stat when loading small files

**Finding ID:** `PERF-107256C05684`  
**Location:** <code>src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:265</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Agent Host resourceResolve RPCs and remote filesystem stat operations  
**Scaling:** On a cold multi-diff with N changed resources, this adds up to one preflight stat for each original and modified URI (up to 2N calls); all are launched without a limiter, and each small file then incurs the existing validation stat again.  
**Outcome:** increased Changes-editor open latency, extra remote I/O, and a burst of metadata RPCs  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each side immediately created its model reference. The ensuing FileService.readFileStream path started its existing validateReadFile resolve/stat and the resourceRead concurrently, so a small Agent Host file paid one metadata RPC and one content RPC without a serialized preflight round trip.  
**Changed behavior:** The added per-item Promise.all calls \_isTooLargeToLoad for both sides before createModelReference. For whole-file providers that helper awaits IFileService.stat; when the file is below the limit, createModelReference then reaches FileService.validateReadFile, which resolves/stats the same resource a second time before the item can finish.  
**Confidence:** 0.98 — The changed loop, both concrete Agent Host RPC implementations, the existing FileService validation stat, and the all-documents await are directly traced. Exact network latency and typical change-set size vary, which affects severity but not the duplicated boundary mechanism.

**Causal diff evidence:** RIGHT line 265 newly invokes \_isTooLargeToLoad for every original URI (with line 266 doing the same for modified URIs) before the unchanged model-reference load; this is the added first stat stage that did not exist before the PR.

Opening Changes for a realistic remote change set of tens or hundreds of ordinary files now waits for an extra Agent Host round trip before any of those files starts loading, while doubling metadata RPCs per cold URI. The outer Promise.all also makes the entire view-model initialization wait for the slowest duplicated chain.

**Evidence:** The added calls at lines 265-266 run inside mapObservableArrayCached for every diff item, and line 248 awaits \_fileService.stat. The provider implements stat as an Agent Host resourceResolve request, while model resolution reads through TextFileService/FileService; FileService.doReadFileStream always starts validateReadFile, whose resolve performs another provider stat, alongside provider.readFile/resourceRead. updateDocuments awaits Promise.all of all item promises, so this work is on the editor-open critical path.

**Suggested direction:** Preserve the large-file guard but pass/reuse the preflight metadata in the subsequent model/file read, or coalesce the immediate validation stat with it, so small files perform one resolve/stat and do not serialize their read behind a redundant round trip.


## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:271` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts:225`  
**Introducing path:** `src/vs/workbench/contrib/multiDiffEditor/browser/multiDiffEditorInput.ts`  
**Introducing commit:** `92abb765af777baa2a424025882a32f52408a21d`  
**Mechanism family:** `eager-work`  
**Performance category:** `network`  
**Confidence:** 0.98

**Mechanism:** The old multi-diff mapper eagerly created a text-model reference for every side. AgentHostFileSystemProvider only exposes whole-file FileReadWrite, so its readFile issues resourceRead for the complete file, whose server implementation reads the full file and returns it base64-encoded; binary detection and size validation therefore occurred only after transferring and allocating the whole payload.

**Symptom:** Opening Changes with an oversized Agent Host file could transfer, base64 encode/decode, and allocate the entire remote file before showing it as binary, causing long open latency and high memory/GC pressure (the added regression test models a 150 MB file).

**Fixed behavior:** The new preflight size check classifies oversized resources and the condition on line 271 skips createModelReference for both sides, avoiding the whole-file resourceRead and showing a placeholder instead.

**Evidence:** Base line 225 created a model reference unconditionally for every defined URI. The traced provider path is createModelReference -&gt; TextFileService.readStream -&gt; FileService.readFileStream -&gt; AgentHostFileSystemProvider.readFile -&gt; resourceRead; FileSystemResources.read uses IFileService.readFile and returns the complete encoded payload. Added tests assert that a 150 MB Agent Host resource is not loaded, while an 80-byte resource still is.
