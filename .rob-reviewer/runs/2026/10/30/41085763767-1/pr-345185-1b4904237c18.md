# Performance review: agentHost: route Auto to the on-device model when the cloud fallback serves only /responses

[PR #345185](https://github.com/microsoft/vscode/pull/345185) at `1b4904237c18ebf7ad9fdc3b0fb5f5ee23dc22a3`

## Findings (1)

### 1. [medium] Preserve streaming for Responses fallbacks

**Finding ID:** `PERF-C3F2F2C1A727`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/localModelBridge/shim/requestRouter.ts:668</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** cloud response bytes, parsed response objects, and serialized SSE bytes retained until completion  
**Scaling:** Latency is the full generation duration rather than first-token latency, and peak allocations scale with the generated output (configured up to 64,000 tokens) before one large SSE chunk is emitted.  
**Outcome:** blocked time-to-first-token plus output-size-proportional memory and GC pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, a Responses-only fallback was rejected as a local route and \`/auto\` was reissued cloud-only; the runtime then used its ordinary HTTP Responses path, so the bridge did not force a streaming cloud request into a buffered non-streaming one.  
**Changed behavior:** Responses-only fallbacks now suppress upstream streaming and hold the entire generated response before returning a synthetic one-chunk stream.  
**Confidence:** 0.95 — The branch is reached only for the newly accepted \`/responses\` fallback endpoint; the streaming request path is explicit in \`\_sendResponsesFallback\`, the unit test sends the default \`stream: true\` request and asserts a single completed chunk, and fallback limits permit up to 64,000 output tokens. The current bundled integration happens to request JSON, so prevalence is lower, but the route advertises streaming support and handles streaming callers as a supported scenario.

**Causal diff evidence:** Added line 668 hard-codes \`stream: false\` for every Responses fallback, even when the incoming chat request has \`body.stream === true\`; added lines 748-759 then await \`response.arrayBuffer()\`, parse the completed body, and serialize the entire answer into one SSE frame.

When a streaming Auto turn selects the on-device model and it fails before first output (or falls back for image, ancillary, full-slot, or endpoint-down reasons), the user receives no cloud token until the fallback finishes. Long responses can delay visible output by the entire generation and require the agent host to retain and reserialize the complete response.

**Evidence:** \`buildFallbackResponsesRequest\` always sends \`stream: false\`. \`\_sendResponsesFallback\` awaits \`response.arrayBuffer()\` before constructing any downstream \`Response\`, then JSON-parses and JSON-stringifies the whole result. The added handler test at lines 1040-1091 exercises an incoming streaming request and expects no output until one full \`chat.completion.chunk\`; model fixtures expose \`max\_output\_tokens: 64000\`. Thus latency grows with full cloud generation time and retained/allocated bytes grow with the complete output.

**Suggested direction:** For \`body.stream === true\`, send \`stream: true\` to \`/responses\` and incrementally translate Responses SSE text/tool-call events to chat-completions chunks, forwarding completion and usage in order; keep the current completed-body conversion only for non-streaming callers.

### Scenario 4: Streaming Auto request falls back through a Responses-only cloud model

- Effective concurrency: One cloud request per failed invocation; concurrent sessions remain independent. Each in-flight request retains its full completed response and translated copies, so aggregate memory scales with concurrent fallbacks.
- Cache behavior: Route caching avoids repeated \`/auto\` selection but cannot reduce per-generation output buffering; no response cache is applicable.
- Mechanism confidence: Very high: \`stream: false\`, \`arrayBuffer()\`, and the single-chunk assertion directly prove the mechanism.
- Magnitude uncertainty: The bundled runtime currently sends the local chat request non-streaming, so streaming prevalence depends on caller/runtime evolution. However, streaming is explicitly advertised in the patched selected-model capabilities and covered by the added handler test.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/localModelBridge/shim/requestRouter.ts:668 and copilotRequestHandler.ts:748-759</code>: POST a forced non-streaming \`/responses\` request, buffer the full response, then emit one chat-completions SSE frame; cardinality: One per fallback invocation; a tool loop may encounter this once per sequential model call, and multiple sessions may do so concurrently.
