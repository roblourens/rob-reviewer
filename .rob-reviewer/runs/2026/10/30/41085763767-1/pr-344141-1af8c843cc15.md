# Performance review: update: opt-in restart to apply updates while the screen is locked

[PR #344141](https://github.com/microsoft/vscode/pull/344141) at `1af8c843cc150d55dd6f12a1efd721751062efed`

## Findings (1)

### 1. [medium] Stop retrying full readiness checks for opted-out users

**Finding ID:** `PERF-26BD3E0A73D1`  
**Location:** <code>src/vs/platform/update/electron-main/unattendedRestartScheduler.ts:533</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Per-window IPC calls plus renderer CPU and temporary strings/arrays produced by every registered readiness participant, including serialization of every open editor  
**Scaling:** After the screen has been locked for one minute, cost grows as locked minutes × ready windows × open editors; each retry fans out concurrently to all ready windows, with no result cache or coalescing across minutes  
**Outcome:** Recurring CPU wakeups and serialization/GC pressure while the machine is idle, increasing background energy use for users who did not enable the feature  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With \`update.restartWhenIdle\` absent, locking the screen after an update was downloaded did not periodically contact every workbench window or serialize open editors.  
**Changed behavior:** The PR adds a telemetry measurement path for disabled users and reschedules the entire readiness pipeline every minute whenever any blocker is present.  
**Confidence:** 0.98 — The scheduler condition, one-minute retry, IPC fan-out, and per-editor serialization are directly traced in changed code. The only magnitude variable is how long users remain locked and how large their editor state is; the repeated mechanism and opt-out reachability are explicit.

**Causal diff evidence:** The new line \`this.evaluation.schedule(isDue ? RETRY\_INTERVAL : ...)\` runs in the blocker branch regardless of the computed \`enabled\` value; before this PR there was no unattended-restart readiness loop, per-window IPC fan-out, or repeated editor serialization for opted-out users.

On macOS with a downloaded update and usage telemetry enabled, the default \`update.restartWhenIdle: false\` still enters this branch whenever any blocker remains and repeats the complete check every 60 seconds until unlock. A terminal or other common blocker left overnight therefore causes hundreds of cross-process scans even though no restart can occur.

**Evidence:** \`evaluate()\` only skips disabled users when telemetry is below USAGE (line 504), then this added line schedules another evaluation every \`RETRY\_INTERVAL\` whenever blockers exist without checking \`enabled\`. Every evaluation calls \`getBlockers\`, which uses \`Promise.all\` to send one IPC request per ready window (line 592). In each renderer, \`WorkbenchUnattendedRestartParticipants.getEditorsBlocker\` filters all open editors (line 90), and \`isRestorableEditor\` calls \`serializer.serialize(editor)\` (line 115). Concrete serializers JSON-stringify arbitrary webview state, while the search-editor serializer traverses and copies all match decorations, so this is not just a cheap flag read.

**Suggested direction:** In measurement-only mode, take at most the initial/due eligibility sample and do not schedule \`RETRY\_INTERVAL\` polling when \`enabled\` is false. Keep retries for enabled users, or separately make those retries event-driven/backed off without repeatedly serializing unchanged editor state.

### Scenario 1: Screen locks while a downloaded update is ready

- Critical path: The lock event schedules \`evaluate()\` immediately. When blocked after the threshold, the new one-minute retry loop repeats this full critical path.
- Scaling input: Effective cardinality is one IPC request per ready top-level window per evaluation, then one participant check per registered subsystem and serialization of every open editor in each window. With blockers, evaluations scale with locked minutes; rounds do not overlap because \`isEvaluating\` guards them.
- Effective concurrency: Ready windows are queried concurrently with \`Promise.all\`; each renderer also runs all participants concurrently with \`Promise.all\`. There is no global limiter, but one scheduler evaluation is serialized and window/participant checks have 10s/5s timeouts.
- Cache behavior: Readiness and editor-serialization results are not cached across minute retries. Only log text is deduplicated. The update overwrite/latest-version check is guarded to run once per quit attempt and skips metered connections for unattended restarts.
- Mechanism confidence: High: retry cadence, IPC fan-out, per-editor serialization, lack of cache, and default-disabled telemetry reachability are all directly established in changed code.

### Scenario 2: Unattended update shutdown, installation, and background relaunch on macOS

- Scaling input: One shutdown attempt, one \`caffeinate\`, and one detached relaunch shell per successful unattended restart. The shell polls once per second until the commit appears or ShipIt has been absent for five checks.
- Effective concurrency: Latest-version checking is single-flight per quit attempt. The two detached subprocesses run concurrently with application exit/installation; no burst scales with window or editor count.
- Cache behavior: \`\_hasCheckedForOverwriteOnQuit\` prevents duplicate latest-version checks. Pending/failed update versions are persisted across one restart, and a failed update version is negatively cached to prevent repeated unattended restarts for the same update.
- Mechanism confidence: High: subprocess launch points, polling interval, storage writes, and lifecycle ordering are explicit and tested.
- Magnitude uncertainty: Installer duration and ShipIt failure behavior vary, but normal cardinality is fixed at one helper pair and polling ends when installation completes.
- Expensive boundaries:

### Scenario 3: Startup after an unattended restart restores windows exactly and in the background

- Critical path: The main process reads and consumes the one-shot exact-restore state, creates the same saved windows, applies bounds/mode/minimized state, and uses inactive showing/order changes so restoration does not take focus. Renderer startup remains the normal per-window path.
- Scaling input: Work scales with the number of windows that already had to be restored; each saved window receives a constant number of native window-state operations.
- Effective concurrency: Window creation follows the existing startup/open flow. Native maximize/fullscreen operations may be deferred until focus; there is no new unbounded concurrent work.
- Cache behavior: Exact-restore metadata is one-shot and removed when read. Background-restore state is released on the first browser-window focus or application activation. Saved window state uses existing state-service persistence.
- Mechanism confidence: High for the changed native/state operations; no evidence shows multiplicative work beyond existing window cardinality.
- Magnitude uncertainty: Users with many windows incur proportionally more native operations, but that same window count already controlled restoration cost and the diff adds only constant work per window.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/windows/electron-main/windowsStateHandler.ts:102-119</code>: Read/remove exact-restore metadata and read normal persisted window state; cardinality: One state-service read at startup and one removal only when metadata exists
    - Introduced by diff: true; previous behavior: Only normal window state was read; no one-shot exact-restore metadata existed; critical-path effect: Required before choosing how initial windows are shown
  - other at <code>src/vs/platform/windows/electron-main/windowImpl.ts:345-430 and src/vs/platform/windows/electron-main/windowsMainService.ts:490-507</code>: Create/show/minimize/order Electron BrowserWindows through native window APIs; cardinality: Constant native operations per restored window
    - Introduced by diff: true; previous behavior: Windows were restored normally and were not shown with the new background/exact semantics; critical-path effect: Part of startup restoration; fullscreen/maximize can be deferred until focus to avoid activation
- Verdict: No reportable regression: added work is bounded per already-restored window and required to preserve exact/background state.

### Scenario 4: Ordinary workbench startup and subsystem participant registration

- Mechanism confidence: High that registration is bounded and lifecycle-owned; lower on exact micro-cost, which is why no startup finding is reported.
- Magnitude uncertainty: Contribution construction timings vary, but inspected registrations show idle scheduling and no new startup boundary sufficient for a high-confidence regression.
- Expensive boundaries: none found
- Verdict: No reportable startup regression: the new registrations are bounded and mostly reuse services already eagerly reached by existing contributions.
