## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCodeEditorIntegration.ts:825` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCodeEditorIntegration.ts:763`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/chatEditorController.ts`  
**Introducing commit:** `095a18f6a6006212a252c1d4403f041128273be1`  
**Mechanism family:** `eager-work`  
**Performance category:** `memory`  
**Confidence:** 0.99

**Mechanism:** Eager per-hunk toolbar construction retained one menu, global menu/action-view subscriptions, action items, and toolbar DOM per pooled DiffHunkWidget until the entire editor integration was disposed, although only the active hunk toolbar was visible.

**Symptom:** Renderer memory and shared-listener count grow linearly with the number of chat diff hunks and remain elevated across rerenders/removals for the session lifetime, increasing memory/GC pressure on large generated edits.

**Fixed behavior:** Toolbars are now created only when a hunk is revealed, preserved through its 200 ms fade and in-flight actions, and disposed when hidden or removed. Pooled widget shells remain, but their menu-backed toolbar resources no longer scale with all historical/current hunks.

**Evidence:** In the base revision, DiffHunkWidget constructed a MenuWorkbenchToolBar in every widget constructor. The render loop creates/reuses one DiffHunkWidget for every diff change and returns unused widgets to an ObjectPool whose free list survives render-store clears until integration disposal. MenuWorkbenchToolBar synchronously creates an IMenu, subscribes to menu/action-view changes, renders actions, and owns DOM. Thus a file with H hunks retained H menus, listeners, action items, and toolbar DOM for the editing session even though toggle() revealed only the cursor/hover hunk. The changed code moves construction into \_showToolbar() and \_hideToolbar() clears the toolbar store after fade/remove, so ownership tracks the one/few revealed or fading widgets.

### Scenario 1: Render or rerender a chat-edited file containing many diff hunks

- Critical path: The editor's diff autorun creates or reuses one lightweight DiffHunkWidget per hunk and lays each out before rendering can settle. After the change, menu-backed toolbar construction is off this collection-wide critical path except for at most the currently selected hunk revealed by the cursor autorun.
- Scaling input: Number H of effective diff changes after the document diff has grouped edits into hunks. The widget pool grows to the largest simultaneous H for the integration, while live toolbar/menu ownership now tracks revealed/fading hunks rather than H.
- Effective concurrency: Single renderer/UI thread; hunk creation and layout are serial. No async fan-out or shared limiter is involved.
- Cache behavior: DiffHunkWidget shells are pooled and reused across rerenders. Before the diff, each cold widget eagerly created and retained a toolbar; warm rerenders reused those toolbar-bearing widgets. After the diff, pooled hidden widgets have no toolbar, a visible widget reuses its toolbar across stable-pool rerenders, and removed/hidden widgets dispose it.
- Mechanism confidence: High: the render loop is explicitly per diff change, ObjectPool retains free widgets, and MenuWorkbenchToolBar creates an IMenu, listeners, action view items, and DOM. The changed lazy show/clear path removes that eager retained resource.
- Magnitude uncertainty: Exact bytes and listener cost per MenuWorkbenchToolBar depend on registered menu actions and context, but the old and new cardinalities are established directly by construction, pooling, and disposal ownership.
- Expensive boundaries: none found
- Verdict: This is a concrete performance fix, not a regression: retained menu/listener/DOM resources fall from O(H) for the session to O(revealed or fading widgets), normally one or two.

### Scenario 2: Move the cursor or pointer between diff hunks to reveal toolbar actions

- Critical path: Cursor-position and mouse-move handlers synchronously scan hunk ranges, toggle widgets, create a toolbar on a cold reveal, update the hover class, and measure/layout the active overlay before the interaction completes.
- Scaling input: Each pointer/cursor event still scans H widgets/ranges as before. New toolbar construction occurs once per reveal after that widget has remained hidden beyond the 200 ms fade; rapid re-reveal within the fade reuses the same toolbar.
- Effective concurrency: Single renderer/UI thread. Fade cleanup uses one RunOnceScheduler per widget, but only widgets that transitioned from visible to hidden have scheduled callbacks; repeated hidden mouse events do not reschedule them.
- Cache behavior: The visible toolbar is reused while shown, through the 200 ms fade, and across stable pool rerenders. A reveal after cleanup is a cold toolbar creation; there is no global toolbar cache or cross-widget sharing because the menu argument is widget-specific.
- Mechanism confidence: High for placement and cardinality; low for any user-visible latency regression because the bounded toolbar is small and no trace, benchmark, or established expensive boundary shows harmful duration.
- Magnitude uncertainty: Lazy creation adds menu/action DOM construction and an immediate width/layout read to a cold reveal, but only for one toolbar and there is no repository evidence that this bounded work causes measurable input jank. Repeated warm navigation can recreate toolbars, but avoids retaining all hunk menus.
- Expensive boundaries: none found
- Verdict: No reportable regression. The bounded cold-reveal work is an intentional scheduling tradeoff for eliminating O(H) retained menus, with fade reuse preventing churn during rapid hover transitions.

### Scenario 3: Hide, remove, disable, or pool a hunk toolbar during rerender/model changes

- Critical path: A hide waits for the existing 200 ms opacity transition, while remove/pool/disable cancels that delay and synchronously clears the toolbar disposable store. These operations occur during renderer diff updates and model/review-mode lifecycle changes.
- Scaling input: Removal can touch up to H widgets serially, but each toolbar is cleared at most once and only revealed/fading widgets own one; hidden updates do not postpone cleanup.
- Effective concurrency: Single renderer thread. Scheduler cancellation and store clearing are serial; no cleanup fan-out crosses a process or service boundary.
- Cache behavior: Widget shells remain in the pool for reuse. Toolbar state is invalidated on removal/disable and recreated only on the next reveal; integration disposal releases the pool and any remaining toolbar stores.
- Mechanism confidence: High: remove cancels scheduling, \_hideToolbar guards visible/running states, and DisposableStore.clear releases the MenuWorkbenchToolBar and subscriptions.
- Magnitude uncertainty: Disposal cost depends on menu action count, but effective toolbar cardinality at removal is bounded to revealed/fading widgets rather than all H.
- Expensive boundaries: none found
- Verdict: No cleanup-lifecycle regression. Cleanup is prompt on removal and bounded on fade, with no lost live resource handle.

### Scenario 4: Run Keep/Undo toolbar actions while the hunk hides, is removed, or its pooled widget is reused

- Critical path: The action executes through the existing ActionRunner. The changed code increments a local running count on will-run and defers toolbar disposal until on-did-run has notified listeners; a microtask then decrements the count and clears only if still hidden.
- Scaling input: Retention scales with the number of concurrently running actions on revealed toolbars, not total H. Multiple actions on one toolbar share that toolbar and are counted; resolved actions release it once the count reaches zero.
- Effective concurrency: Action promises may overlap without a new limiter, matching prior action concurrency. Disposal is coalesced by one counter per widget and occurs after all completions; the changed code introduces no subprocess/IPC/network concurrency.
- Cache behavior: A running toolbar is temporarily pinned even if hidden or pooled so its ActionRunner can finish notification. If the widget is revealed/reused before completion, that same toolbar is retained; otherwise it is released after the final completion. Full integration disposal remains immediate.
- Mechanism confidence: High: onWillRun/onDidRun accounting and tests cover success, failure, concurrent actions, removal, reuse, and integration disposal.
- Magnitude uncertainty: Downstream command implementations can perform unrelated work, but this diff neither adds nor moves those operations. Retention duration is action duration, and resource cardinality is bounded by concurrently active toolbar actions.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. Temporary retention preserves completion semantics and is bounded by in-flight action lifetime and concurrency.
