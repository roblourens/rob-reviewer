### Scenario 1: Open or search Customizations &gt; Browse while organization-required plugins are installed, including policy changes while results are visible

- Critical path: Initial search still waits on the existing marketplace catalog request; once data is present, the diff adds synchronous required-plugin URI checks while constructing result entries and visible rows. A policyEnablement change triggers render(true), which only rebuilds the local result model and virtualized rows and does not call loadCatalog.
- Scaling input: Current search entries: installed customizations plus catalog pages (24 items per normal page, with up to 8 sequential pages only for existing filtered backfill); policy checks scale as entries times the usually small required-plugin URI set. DOM work remains limited by list virtualization.
- Effective concurrency: Catalog pagination and source loading retain their existing sequencing/concurrency. The added derived observable runs synchronously and coalesces equal URI arrays; it starts no asynchronous work and no aggregate burst.
- Cache behavior: Existing marketplace page, browse-section, and installation caches are unchanged. requiredPluginUris is derived/memoized with URI-array equality, so unchanged policy state does not re-render; there is no new positive/negative remote cache.
- Mechanism confidence: High confidence from tracing requiredPluginUris, render, renderSearchResults, and loadCatalog: the added observable does not cross a boundary or restart catalog loading.
- Magnitude uncertainty: Organizations may require more than a few plugins and users may have many installed customizations, but the added work is cheap URI comparison/local allocation and visible-row rendering is virtualized.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationDiscoveryPage.ts:loadCatalog/loadSourceSections</code>: Query customization marketplace catalog and browse sources; cardinality: Normally one catalog page per query; existing filtered backfill can request up to 8 pages, while browse source sections use existing per-source queries.
    - Introduced by diff: false; previous behavior: The same catalog and browse-source requests occurred before the PR.; critical-path effect: Cold search/browse waits for these existing requests; the changed policy render does not invoke them.
- Verdict: No reportable regression. The local O(entries × required plugins) checks and occasional preserving render are bounded and necessary to update policy state; no expensive boundary is added or moved onto the critical path.

### Scenario 2: Render customization section lists and open inline/context menus for plugin-contributed prompts, skills, agents, or hooks

- Critical path: Visible row rendering creates the existing context-key overlay and menu; the diff adds one scan of the installed plugin array for rows with pluginUri. Opening a context menu performs the same check once for the selected item.
- Scaling input: Row work scales with visible virtualized rows, each scanning installed plugins until the owning URI is found; context-menu work has cardinality one.
- Effective concurrency: All added work is synchronous UI-thread CPU work with no queue or asynchronous fan-out.
- Cache behavior: The installed plugin observable is read directly; no remote cache is involved. No cache lifecycle or retention is introduced.
- Mechanism confidence: High confidence from both added isPluginUriRequiredByPolicy call sites and the helper implementation.
- Magnitude uncertainty: Plugin counts can vary, but practical visible-row and plugin counts keep the URI comparisons bounded; no evidence shows frame-scale pressure.
- Expensive boundaries: none found
- Verdict: No reportable regression. This is bounded local lookup work and does not establish user-visible jank or scaling boundary cost.

### Scenario 3: Open plugin detail or standalone plugin editor for an organization-required plugin

- Critical path: The action/button is created synchronously; the diff adds a disabled-action view item and delayed-hover registration. Hover content is created only when the button is rendered and no heavy model or boundary work is started.
- Scaling input: One uninstall action and at most one hover registration per open detail/editor surface.
- Effective concurrency: No asynchronous work is started by rendering; hover handling follows the existing hover service lifecycle.
- Cache behavior: No caches are added or invalidated.
- Mechanism confidence: High confidence from the changed action view item and button render call paths.
- Magnitude uncertainty: None material; cardinality is constant per surface.
- Expensive boundaries: none found
- Verdict: No reportable regression. Constant local UI setup is negligible and correctly disposed with the surface.

### Scenario 4: Open Plugins-page or MCP-server menus and attempt uninstall of an organization-required plugin or one of its contributions

- Critical path: Menu creation adds a policy read and disabled tooltip. For required plugins, command guards now stop before confirmation and plugin removal; unmanaged plugins retain the existing confirmation and removal path.
- Scaling input: One policy check per opened menu/action and one guarded command invocation per user interaction.
- Effective concurrency: No new concurrent operations are launched. The changed path reduces failed uninstall work for required plugins.
- Cache behavior: Policy state comes from existing observables; marketplace ownership/removal caches are unchanged.
- Mechanism confidence: High confidence from the new enabled checks and command guards before remove calls.
- Magnitude uncertainty: The exact removal implementation and duration vary by plugin source, but the diff removes rather than adds this work on the affected path.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/agentPluginActions.ts:removePluginWithMarketplaceOwnership and IAgentPlugin.remove callers</code>: Remove the plugin and its contributed resources; cardinality: At most one removal attempt per user click for unmanaged plugins; zero for organization-required plugins after the diff.
    - Introduced by diff: false; previous behavior: Before the PR, required-plugin actions could reach the existing removal attempt and fail; unmanaged plugin behavior is unchanged.; critical-path effect: Existing unmanaged uninstall waits for removal. The changed required-plugin path returns before removal, reducing boundary work.
- Verdict: No reportable regression. Boundary cardinality is unchanged for unmanaged plugins and reduced to zero for required plugins.
