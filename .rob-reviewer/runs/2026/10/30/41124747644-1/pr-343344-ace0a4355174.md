### Scenario 1: A compaction starts or completes while an Agent Host turn is active, and the runtime emits session\_compaction\_start/session\_compaction\_complete telemetry.

- Critical path: The SDK session-event handler synchronously performs O(1) owner lookup and one bounded LRU record before returning; the separate GitHub telemetry callback resolves the mapping and publishes telemetry. Compaction/model execution and the user turn do not await the GitHub telemetry callback, which is launched with void, so correlation and publication are off the user critical path.
- Scaling input: Number of compaction attempts and their two telemetry rows; there is no dependence on conversation message/token count because only bounded scalar metrics and identifiers are copied.
- Effective concurrency: SDK session events are ordered. Telemetry callbacks are detached and may overlap, but waiters coalesce on one DeferredPromise per attempt; each row has its own bounded timer and there is no expensive remote operation under that concurrency.
- Cache behavior: The start session event warms the attempt-to-turn LRU. A warm telemetry row resolves immediately; a cold row shares a per-attempt pending entry and waits at most 100 ms. The owner cache is capped at 200 attempts per session, and completion refreshes the same key.
- Mechanism confidence: High: the changed handlers, bounded LRU, 100 ms timeout, detached callback, and unchanged single publication are explicit in code.
- Magnitude uncertainty: Exact compaction frequency varies with session length and context limits, but realistic cardinality is a few rows per compaction rather than per message/token.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:4376 onGitHubTelemetry</code>: Receive an existing telemetry notification from the Copilot runtime connection.; cardinality: Two session-compaction rows per attempt under normal operation, plus any separately emitted response row; no collection fan-out.
    - Introduced by diff: false; previous behavior: The same runtime telemetry callback received each row and routed it directly to the generic forwarder.; critical-path effect: Already received before the changed correlation path runs; callback processing is detached from turn progress.
  - serialization at <code>src/vs/platform/agentHost/node/copilot/copilotGitHubTelemetryForwarder.ts:630 forwardCompaction</code>: Build, sanitize, and publish one scalar telemetry object through ITelemetryService.; cardinality: Exactly one publication for each runtime session-compaction telemetry row; the diff does not duplicate or add publications.
    - Introduced by diff: false; previous behavior: The generic forward path already built and published one telemetry object for each row.; critical-path effect: Off the user critical path; synchronous work is bounded by the telemetry row's scalar property count.
- Verdict: No reportable regression. The diff adds bounded O(1) map/timer work and does not increase expensive-boundary call count or place it on turn progress.

### Scenario 2: A compaction telemetry row arrives before the ordered session event records its owning turn.

- Critical path: The detached telemetry task allocates/reuses one pending entry and awaits up to 100 ms; record() completes all same-attempt waiters when the session event arrives. Nothing in chat rendering, input, compaction execution, or turn completion awaits this task.
- Scaling input: Distinct out-of-order compaction attempt IDs and at most the start, completion, and response rows sharing each attempt ID.
- Effective concurrency: Independent attempt IDs can wait concurrently without a global limiter, but each contributes only a DeferredPromise, counters, and short timer(s); natural cardinality is bounded by concurrently emitted compaction rows across live sessions.
- Cache behavior: A miss creates one pending DeferredPromise per attempt. Multiple rows share it; after every waiter expires the map entry is removed, and successful recording moves the result into a 200-entry LRU. Missing IDs do not allocate pending entries.
- Mechanism confidence: High: resolve(), waiter accounting, raceTimeout timer cancellation, and map deletion are directly visible.
- Magnitude uncertainty: The relative ordering rate between SDK session events and telemetry notifications is not quantified, but each miss is time-bounded and resource-light.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/agentHost/node/copilot/copilotGitHubTelemetryForwarder.ts:680 \_publish</code>: Publish the telemetry row after correlation resolves or expires.; cardinality: One publication per inbound row, unchanged from before the diff; waiting changes timing only.
    - Introduced by diff: false; previous behavior: The row was published immediately by the generic path; response rows could already wait up to 100 ms on model-call correlation.; critical-path effect: Delayed only on the telemetry path by at most 100 ms and detached from product progress.
- Verdict: No reportable regression. Waiting is bounded, coalesced per attempt, cleaned after expiry, and off the critical path.

### Scenario 3: A conversation-compaction response.success/response.error row is forwarded after its summarization model call.

- Critical path: The response path now resolves by compaction attempt. Warm mappings forward immediately; a cold mapping waits at most 100 ms. The runtime callback is detached, so the wait does not block the turn or compaction.
- Scaling input: One response row per compaction summarizer request emitted by the runtime; no per-history-item processing.
- Effective concurrency: Rows for independent attempts resolve independently; there is no serialization or expensive-operation burst added by the diff.
- Cache behavior: Uses the same capped attempt LRU and per-attempt pending coalescing. A recorded attempt avoids the former model-call correlation miss; an unrecorded attempt retains the same 100 ms upper-bound behavior.
- Mechanism confidence: High: the before/after branches both have a maximum 100 ms correlation wait and the callback ownership is explicit.
- Magnitude uncertainty: Future runtime versions may emit successful compaction response rows more often, but count remains tied to compaction model calls and publication count is unchanged.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/agentHost/node/copilot/copilotGitHubTelemetryForwarder.ts:581 forward</code>: Sanitize and publish one response telemetry event.; cardinality: One publication per runtime response row, both before and after the diff.
    - Introduced by diff: false; previous behavior: The existing response path attempted model-call correlation and could wait the same 100 ms before publishing.; critical-path effect: Off product progress; only telemetry delivery timing changes.
- Verdict: No reportable regression. This changes the correlation key and usually removes an unproductive wait; it does not add boundary calls or block user work.

### Scenario 4: A long-lived session accumulates many completed compaction attempts and is later disposed.

- Critical path: Each start/complete event records one key in a per-session LRU; session disposal removes the owning session object from the live-session map. Outstanding detached resolutions retain it for at most their 100 ms timeout.
- Scaling input: Lifetime number of compaction attempts in one session; effective retained cardinality is capped at 200 owner entries plus currently waiting attempt IDs.
- Effective concurrency: Pending attempts can overlap, but each waiter has a bounded timeout and each per-attempt entry is removed after its final waiter; no cleanup boundary is serialized with user work.
- Cache behavior: LRU eviction bounds completed mappings to 200. Pending entries are removed when recorded or when the last waiter expires. No negative result is pinned indefinitely.
- Mechanism confidence: High for cache and pending-entry lifecycle from the implementation; moderate for runtime-level compaction concurrency, which does not affect the bounded per-entry mechanism.
- Magnitude uncertainty: The maximum number of simultaneous compactions permitted by the runtime was not established, but retained completed state is hard-capped and pending state lifetime is 100 ms.
- Expensive boundaries: none found
- Verdict: No reportable memory regression. Completed state is capped, pending state has explicit removal, and disposal makes the session collectible after short detached waits settle.
