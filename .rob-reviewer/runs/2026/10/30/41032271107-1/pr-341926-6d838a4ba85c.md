## Performance regression fixes detected (3)

### 1. boundary-fanout

**Fix location:** `src/vs/platform/agentHost/node/copilot/copilotSessionHistory.ts:80` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/copilot/copilotSessionHistory.ts:68`  
**Introducing path:** `src/vs/platform/agentHost/node/copilot/copilotSessionHistory.ts`  
**Introducing commit:** `9dcad803e562f8fdfaad889ef0dfa765d955e5ea`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `io`  
**Confidence:** 0.98

**Mechanism:** The base implementation awaited getTerminalOutputSize inside the nested turn/response-part scan. Each lookup entered SessionDatabase.\_queueTurnData and issued a separate SQLite SELECT, so restoring N eligible shell calls required N serialized database round trips; callers also repeated the helper for parent and subagent chats.

**Symptom:** Opening or restoring a long Copilot chat is blocked on serialized SQLite work proportional to the number of completed non-PTY shell calls, including the common case where no retained output row exists.

**Fixed behavior:** The changed helper collects candidates across the parent and subagent chats and performs one getTerminalOutputSizes query before attaching terminal resources, reducing the critical-path size lookup count from N to one (or zero with no candidates).

**Evidence:** The deleted base line 68 awaited getTerminalOutputSize in the per-tool loop; SessionDatabase.getTerminalOutputSize executes one SELECT through \_queueTurnData. RIGHT line 80 performs a single batched lookup over all collected candidates, and the changed Copilot session callers pass parent and subagent turns together. The added test exercises 501 parent candidates plus a child and asserts one batched call per reconstruction and zero single calls.

**Evidence:** Codex \_getChatMessages and \_refreshChatHistory both await \_restoreRetainedCommandOutputs. Deleted base line 7325 performed one awaited size lookup per command; RIGHT line 7325 performs one batched query outside the loop. ### 3. boundary-fanout

**Symptom:** Reading a saved or materialized Claude chat with many Bash calls incurs restore latency that grows with every shell call, even when almost none have retained output.

**Evidence:** ClaudeTerminalOutputs.restore gathers all completed Bash calls, and both ClaudeSavedChatReader.read and ClaudeAgent history reconstruction await it before returning turns. Deleted base line 130 performed the size lookup in the loop; RIGHT line 129 performs one lookup before the loop. The new 502-call test asserts one batched lookup and zero single lookups.

**Relevant issue families:** boundary-fanout, repeated-work, serialization-allocation, concurrency-burst

### Scenario 1: Restore or open a persisted Copilot Agent Host chat, including parent and subagent transcripts with many completed non-PTY shell calls

- Critical path: Persisted event pages are read and mapped, then retained shell output metadata must be restored before getMessages or session reconstruction returns. The changed SQLite lookup is therefore on the cold reconstruction critical path; memoized primary/all mapped events and isolated persisted-history promises avoid repeating it on warm reads.
- Scaling input: The effective batch cardinality is the number of eligible completed shell calls across the parent and included subagent chats after filtering out PTY terminal content. A realistic long session can contain thousands; IDs are normally unique, while SQL IN semantics prevent duplicate result rows.
- Effective concurrency: Event pages are fetched sequentially by readCopilotSessionEvents as before. Database turn-data operations are serialized by \_turnUsageSequencer and the shared mutation sequencer; the diff replaces N serialized size queries (and formerly separate per-chat passes) with one queued query, with no concurrency burst.
- Cache behavior: Cold primary and all-scope reconstructions each perform at most one batch lookup when they contain candidates. CopilotAgentSession memoizes reconstruction by scope, and isolated history reads cache their promise by chat identity. Missing output rows are represented by absence from the returned map for the current batch rather than a persistent negative cache.
- Mechanism confidence: High: changed loops, database sequencers, indexed schema, callers, and tests establish the before/after boundary cardinality.
- Magnitude uncertainty: Exact latency depends on session size, SQLite/runtime overhead, and how often a scope is reconstructed, but the reduction from N serialized queries to one is directly established.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_computeMappedEvents and src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_doReadPersistedChatHistory</code>: Read persisted Copilot event-log pages through the SDK/control-plane RPC; cardinality: One RPC per up-to-1000-event page, unchanged by this diff
    - Introduced by diff: false; previous behavior: The same paginated event reads occurred before the diff; critical-path effect: All pages must be available before mapping and output restoration can complete
  - database at <code>src/vs/platform/agentHost/node/sessionDatabase.ts:getTerminalOutputSizes</code>: Look up length(output) for all eligible tool call IDs using json\_each over one bound JSON array and the terminal\_outputs primary-key index; cardinality: One SQLite query per cold reconstruction with candidates, zero with none; previously one queued query per eligible shell call and separate helper invocations per chat
    - Introduced by diff: true; previous behavior: Each candidate awaited getTerminalOutputSize, issuing N serialized indexed SELECTs; critical-path effect: Awaited before reconstructed turns are returned, but replaces N serialized boundary calls with one
- Verdict: This is a concrete boundary-fanout regression fix, not a new performance regression. The temporary candidate array and JSON parameter are O(N), but they replace O(N) objects plus N serialized database operations and are bounded by the already-loaded history.

### Scenario 2: Read or materialize a saved Claude chat containing many completed Bash tool calls

- Critical path: The SDK transcript is read and mapped first; ClaudeTerminalOutputs.restore is then awaited before turns are returned. Its database lookup is on the cold history-read critical path.
- Scaling input: Effective cardinality is completed Bash calls only; non-shell tools are filtered before the batch. Stored and missing IDs share the same single query.
- Effective concurrency: The changed lookup is one operation serialized by the session database sequencers. There is no Promise.all fan-out or aggregate burst; before the diff the loop awaited one serialized query at a time.
- Cache behavior: No provider-level retained-output lookup cache is added. Each actual transcript reconstruction performs one current-state query, preserving invalidation naturally; calls with no Bash candidates perform no query. The surrounding chat/history ownership determines whether reconstruction itself is reused.
- Mechanism confidence: High: both saved-chat and materialized-chat callers await restore, and the new multi-call test verifies one batch for 502 shell candidates with zero single lookups.
- Magnitude uncertainty: The exact user-visible saving varies with Bash-call count and storage speed; the scaling and critical-path placement are certain.
- Expensive boundaries:

### Scenario 3: Open a persisted Codex thread or refresh changed Codex history containing replayed commands

- Critical path: The Codex thread/rollout is read and replayed, then \_restoreRetainedCommandOutputs is awaited before the full history returns or a changed-history event is published. - Scaling input: For a full open, effective batch size is all replayed commands. For refresh, it is commands in changed non-host turns only. Subsequent full-output reads scale with the subset that both has a stored row and needs replacement, unchanged from before.
- Effective concurrency: History refreshes are sequenced by \_chatHistoryReads and terminal database operations are serialized. The diff performs one size query, followed by the same sequential conditional content reads as before; it does not introduce concurrent SQLite work.
- Cache behavior: A 30-second equality check and history snapshots can skip unchanged refresh processing. On a real cold/open or changed refresh, current stored sizes are queried once; absence is local to that batch. Existing snapshots cache mapped turns, not stale database size results.
- Mechanism confidence: High: both callers and filtering are explicit, and the 503-command test verifies one size batch and only the expected unchanged content read.
- Magnitude uncertainty: Refresh batches may be much smaller than full histories because unchanged turns are filtered, but the full-open path can contain hundreds or thousands of commands; duration depends on local database overhead.

### Scenario 4: Execute the new session-database batched terminal-output-size lookup with a very large ID set

- Critical path: Provider history restoration awaits the query. JSON.stringify occurs synchronously before the native SQLite dbAll call within the queued operation, so both serialization and SQL execution are on the critical path.
- Scaling input: CPU and transient bytes grow linearly with candidate ID count; the test covers 40,003 array entries including a duplicate, above ordinary SQLite bound-parameter limits. Returned map size is bounded by matching terminal\_outputs rows.
- Effective concurrency: One operation holds the turn-data/mutation sequence while serializing parameters and running the query. This is intentionally serialized for ordering and replaces many acquisitions/queries rather than adding contention.
- Cache behavior: There is no cross-call cache; each batch observes current database state. Empty input returns before serialization or SQLite. Missing IDs create no retained map entries, so negative results are not pinned.
- Mechanism confidence: High: query text, schema primary key, empty guard, queueing, and large-input test are directly visible.
- Magnitude uncertainty: Extremely large histories allocate a correspondingly large JSON string and candidate array, but those histories are already fully resident and the test establishes practical 40,000-ID support; no realistic threshold indicates a regression versus N database calls.
- Expensive boundaries:
  - serialization at <code>src/vs/platform/agentHost/node/sessionDatabase.ts:getTerminalOutputSizes</code>: Serialize all tool call IDs into one JSON array parameter; cardinality: One JSON serialization containing N IDs per non-empty batch; previously N individual one-element SQL parameter bindings across N calls
    - Introduced by diff: true; previous behavior: No aggregate JSON allocation; each ID was separately bound in its own query; critical-path effect: Linear synchronous allocation precedes the query, but is outweighed by eliminating N queued SQLite crossings for realistic long histories
  - database at <code>src/vs/platform/agentHost/node/sessionDatabase.ts:getTerminalOutputSizes</code>: Use json\_each(?) to probe terminal\_outputs by tool\_call\_id and compute BLOB lengths without loading output; cardinality: One query with N virtual-table values and up to matching-row count results; terminal\_outputs.tool\_call\_id is the primary key
    - Introduced by diff: true; previous behavior: N getTerminalOutputSize calls each executed a separate SELECT; critical-path effect: One indexed batch remains on the critical path instead of N serialized indexed queries
