# Performance review: Skip laying out the outgoing transcript when switching sessions

[PR #341963](https://github.com/microsoft/vscode/pull/341963) at `171e6c88686d33932da0eb0a0172c7609329f0f3`

## Findings

No high-confidence performance findings.

## Performance regression fixes detected (2)

### 1. synchronous-ui-work

**Fix location:** `src/vs/sessions/browser/parts/chatCompositeBar.ts:844` (`RIGHT`)  
**Blamed base line:** `src/vs/sessions/browser/parts/chatCompositeBar.ts:846`  
**Introducing path:** `src/vs/sessions/browser/parts/chatCompositeBar.ts`  
**Introducing commit:** `32ca9719c90b527b0ffa96b288bd2964256e5ac3`  
**Mechanism family:** `synchronous-ui-work`  
**Performance category:** `layout`  
**Confidence:** 0.99

**Mechanism:** A hidden chat tab bar synchronously read clientWidth/scrollWidth on every active-chat update, forcing Chromium to lay out the full window, including a large outgoing transcript that was immediately discarded.

**Symptom:** Switching between existing sessions with roughly 100 KB transcripts blocked the Agents window; measured time in the two outgoing-transcript layout-read sites was about 380 ms per switch before the fix and under 1 ms after both sites were fixed.

**Fixed behavior:** \_updateActiveTab now updates DOM state while hidden but defers width measurement and active-tab reveal until the bar becomes visible, eliminating the hidden synchronous layout read from the session-switch critical path.

**Evidence:** In the base revision, \_updateActiveTab unconditionally called \_updateScrollDimensions, which reads clientWidth and scrollWidth. setGroup wires \_updateActiveTab to activeChatResource while the bar may be display:none, and the session-switch path updates that observable before replacing the reused ChatView transcript. The added visibility guard at RIGHT:844 skips those synchronous geometry reads while hidden; the new test instruments both properties and proves zero reads for hidden active-chat/tab-list updates. The PR's measured large-transcript switch scenario attributes the prior reads to a forced-layout block and reports the combined layout-read time falling from about 380 ms to under 1 ms after both fixes.

### 2. synchronous-ui-work

**Fix location:** `src/vs/sessions/contrib/chat/browser/chatView.ts:768` (`RIGHT`)  
**Blamed base line:** `src/vs/sessions/contrib/chat/browser/chatView.ts:949`  
**Introducing path:** `src/vs/sessions/contrib/chat/browser/chatView.ts`  
**Introducing commit:** `6dfc9e40fbf801efd2e471c25021075ba44d161a`  
**Mechanism family:** `synchronous-ui-work`  
**Performance category:** `layout`  
**Confidence:** 0.97

**Mechanism:** Transcript clearing occurred only inside \_loadChat, after incoming-chat selection-controller rebinding synchronously inspected the DOM selection; with a large outgoing transcript attached, that selection read forced layout of content about to be removed.

**Symptom:** Switching reused ChatView instances with large completed responses blocked the UI; instrumentation of the hidden-bar and selection reads measured about 380 ms of wasted outgoing-transcript layout per switch before the ordering fix and under 1 ms after both fixes.

**Fixed behavior:** A genuine chat switch now cancels the outgoing load and clears/releases the reused widget before rebinding selection behavior or other incoming-chat consumers that synchronously inspect layout.

**Evidence:** In the base revision, setChat called \_selectionSideChatController.setChat for the incoming resource before \_loadChat reached the old \_clearCurrentChat at base line 949. ResponseSelectionSideChatController.setChat force-dismisses on a resource change; \_dismiss calls \_updateAutoScrollHold, whose \_hasTranscriptSelection reads Selection.isCollapsed and Selection.toString while the old widget transcript is still attached. The added \_clearCurrentChat at RIGHT:768 now removes the outgoing model and unbinds the controller before the incoming setChat call. The new ordering test proves the controller observes an empty rendered transcript during release and rebinding; the measured large-transcript scenario reports the two prior forced-layout sites dropping from about 380 ms to under 1 ms.

### Scenario 2: Switch chats within a session or reveal the multi-chat tab strip

- Critical path: When the strip is already visible, active-tab changes still update scroll dimensions and reveal the active tab synchronously. While hidden, active/tab-list updates now skip geometry reads; on the hidden-to-visible transition, \_setVisible reads height, updates scroll dimensions, and reveals the active tab before firing visibility change.
- Scaling input: DOM work scales linearly with the number of chat tabs for active-state updates; geometry/reveal work is one bounded operation per visible active-tab update or hidden-to-visible transition. It does not scale with transcript history once hidden reads are skipped.
- Effective concurrency: All tab DOM and geometry work is synchronous on the UI thread; ResizeObserver callbacks are browser-scheduled. The diff adds no queue, parallel operation, IPC, filesystem, database, subprocess, or network work.
- Cache behavior: No cache or remote data access is involved. Scroll dimensions are refreshed on reveal and remain maintained by the existing ResizeObserver while visible.
- Mechanism confidence: High: all geometry reads and visibility guards are directly visible in ChatCompositeBar, and the new test verifies no clientWidth/scrollWidth reads while hidden plus a refresh when shown.
- Magnitude uncertainty: A reveal may also receive a later ResizeObserver callback, but visibility transitions are bounded and the synchronous reveal follows an offsetHeight layout read; there is no realistic scaling regression established from the added refresh.
- Expensive boundaries: none found
- Verdict: No reportable regression. Deferring hidden measurements avoids transcript-wide forced layout, while the one reveal-time refresh preserves visible scroll state with bounded tab-strip work.

### Scenario 3: Select a session that is still being created and shows preparation input

- Critical path: setChat checks the observable preparation state and performs an O(1) lookup in the in-flight request map. For a changed chat with preparation input, it keeps the existing special path: cancel the prior load, construct/show the preparation ChatModel, set loading false, and lay out the widget; it does not call acquireOrLoadSession.
- Scaling input: The lookup is one map access per genuine chat change; preparation-model construction scales with the single request query and attachment list. The new chatChanged short-circuit avoids the lookup on same-chat reactive reruns.
- Effective concurrency: The prior transcript load is cancelled and no replacement provider load is started on this path. Preparation UI work is synchronous and singular; no boundary fan-out or concurrency burst is introduced.
- Cache behavior: The in-flight request registry is an in-memory map keyed by session resource. No cold/warm provider cache transition occurs until the normal transcript-loading path is entered later.
- Mechanism confidence: High: the guard, map lookup implementation, and branch are explicit in the changed and transitive code.
- Magnitude uncertainty: Query and attachment sizes vary, but the branch's construction and layout behavior is unchanged; only the lookup was moved and additionally short-circuited for unchanged chats.
- Expensive boundaries: none found
- Verdict: No reportable regression. The special preparation path remains behaviorally and computationally equivalent for real chat changes, while repeated same-chat updates do less work.
