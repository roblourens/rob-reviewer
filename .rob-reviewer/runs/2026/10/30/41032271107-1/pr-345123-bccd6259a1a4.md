## Findings

No high-confidence performance findings.

**Relevant issue families:** boundary-fanout, repeated-work, serialization-allocation, concurrency-burst

### Scenario 1: Copilot Chat edits one notebook cell with a matching request id and response stream

- Critical path: Resolve the notebook URI, open or reuse the notebook document, compute one insert/delete/text edit, emit it to the existing chat response stream, wait for document-change events, then render the bounded tool result. The diff's request-id comparison and stream selection are constant-time; \`workspace.applyEdit\` is not reached.
- Scaling input: Notebook cell count controls pre-existing in-memory scans; replacement text size controls the one edit payload. Effective boundary cardinality remains one logical edit per invocation.
- Effective concurrency: The tool issues one edit for this invocation and awaits existing event completion. No changed loop, \`Promise.all\`, limiter, or concurrency burst is present.
- Cache behavior: An already-open notebook is the warm state and avoids loading; a cold document is opened once. No new cache, cache key, miss retry, or negative-cache behavior is introduced.
- Mechanism confidence: High: request-id matching selects the unchanged stream path, and the new \`instanceof WorkspaceEditStream\` branch is therefore skipped.
- Magnitude uncertainty: Notebook sizes and stream implementation latency vary, but those costs and their scaling are unchanged on this path.
- Expensive boundaries:
  - filesystem at <code>extensions/copilot/src/platform/workspace/vscode/workspaceServiceImpl.ts:51 and extensions/copilot/src/extension/tools/node/editNotebookTool.tsx:123</code>: Open and deserialize the notebook if it is not already open; otherwise reuse the in-memory document.; cardinality: At most one open per tool invocation; warm open notebooks use \`findNotebook\` and perform no filesystem load.
    - Introduced by diff: false; previous behavior: The same open/reuse call ran after the old stream validation.; critical-path effect: Cold notebook loading blocks edit preparation; warm reuse does not cross the filesystem boundary.
  - IPC at <code>extensions/copilot/src/extension/tools/node/editNotebookTool.tsx:167-249</code>: Send one logical notebook cell operation or one cell text replacement through the chat response stream, bracketed by existing start/end notebook-edit notifications.; cardinality: One logical edit per invocation; no loop creates per-cell boundary calls.
    - Introduced by diff: false; previous behavior: Matching chat invocations used the same response-stream calls before the diff.; critical-path effect: The authoritative edit and resulting change events must complete before the result is rendered.
- Verdict: No reportable regression: the normal chat path retains its prior expensive boundaries and multiplicity.

### Scenario 2: Agent-host or tools-service invocation edits one cell without a chat response stream

- Critical path: Resolve and open/reuse the notebook, construct a single \`WorkspaceEdit\`, call \`workspace.applyEdit\` once, wait for the corresponding document events, and render the result. The newly enabled apply is on the critical path because the tool must update the open notebook before returning.
- Scaling input: One operation is accepted by the tool schema. Existing notebook scans scale linearly with cell count, and a text replacement payload scales with the target cell's new text; there is no per-cell I/O or IPC fan-out.
- Effective concurrency: One apply is awaited per invocation. The change does not spawn parallel applies or add a collection-wide \`Promise.all\`; separate external invocations are not coalesced, but the diff provides no realistic burst mechanism.
- Cache behavior: The open-document collection is the warm state; no additional cache is created. Cold opening happens once, and failures are not retried by the changed code.
- Mechanism confidence: High: the changed branch, tool schema, and workspace service implementation directly establish a single awaited apply boundary.
- Magnitude uncertainty: Very large notebooks can make the pre-existing scans and rendering more expensive, but the newly added boundary remains one operation and is necessary to provide the newly supported streamless edit behavior.
- Expensive boundaries:
  - filesystem at <code>extensions/copilot/src/platform/workspace/vscode/workspaceServiceImpl.ts:51 and extensions/copilot/src/extension/tools/node/editNotebookTool.tsx:123</code>: Open and deserialize the notebook when it is not already in \`workspace.notebookDocuments\`.; cardinality: At most one cold open per invocation; normally zero loads for the target open notebook.
    - Introduced by diff: true; previous behavior: The old no-stream validation failed before attempting to open the notebook.; critical-path effect: A cold open blocks edit construction; warm open notebooks avoid the load.
  - IPC at <code>extensions/copilot/src/extension/tools/node/editNotebookTool.tsx:259 and extensions/copilot/src/platform/workspace/vscode/workspaceServiceImpl.ts:82</code>: Apply the collected notebook edit or cell text edit through VS Code's \`workspace.applyEdit\`.; cardinality: Exactly one \`applyEdit\` call containing one logical cell operation per successful tool invocation.
    - Introduced by diff: true; previous behavior: Streamless invocations failed immediately and applied no edit.; critical-path effect: The call is awaited and its document-change events are required before the tool result can complete.
  - serialization at <code>extensions/copilot/src/extension/tools/node/editNotebookTool.tsx:300-317 and EditFileResult at 630-658</code>: Render the existing notebook edit result after the edit completes.; cardinality: Once per successful invocation; insertion summaries inspect the notebook once, while edit/delete return a fixed message.
    - Introduced by diff: true; previous behavior: Streamless invocations failed before result rendering; successful chat invocations already used this renderer.; critical-path effect: Result rendering occurs after the authoritative apply and is part of response completion.
- Verdict: No reportable regression: the PR intentionally turns a previously rejected invocation into one bounded notebook edit, without fan-out, repeated boundary work, or unbounded retention.

### Scenario 3: Invocation ignores a stale response stream from an earlier chat request

- Critical path: The request-id check rejects the stale context, then follows the same single-\`WorkspaceEdit\` path as a streamless agent invocation; the stale stream receives no calls.
- Scaling input: One tool operation and one edit payload; notebook size affects only existing in-memory preparation/result work.
- Effective concurrency: No internal parallelism or fan-out is added. Request-id selection is constant-time and each invocation owns its local workspace edit.
- Cache behavior: Same warm/cold notebook behavior as the streamless scenario; no new cache lifecycle exists.
- Mechanism confidence: High: the changed identity check and tests explicitly establish this branch and its one-call behavior.
- Magnitude uncertainty: How often stale contexts occur is unknown, but the resulting work is bounded and replaces an unusable stream path rather than multiplying work.
- Expensive boundaries:
  - IPC at <code>extensions/copilot/src/extension/tools/node/editNotebookTool.tsx:113-120 and 259</code>: Apply one collected cell operation via \`workspace.applyEdit\` rather than attempting the stale chat stream.; cardinality: One apply per invocation, independent of notebook cell count.
    - Introduced by diff: true; previous behavior: The old code reused whatever stream was stored in \`promptContext\`; it did not call \`workspace.applyEdit\`.; critical-path effect: The one apply and resulting events gate completion.
- Verdict: No reportable performance regression: stale-stream isolation adds a bounded authoritative apply and prevents calls to the stale stream.

**Summary:** Completed the performance pass over both changed files and every diff hunk. The only new expensive operation is one awaited \`workspace.applyEdit\` for previously unsupported streamless or stale-context invocations. The tool contract carries one cell operation, no changed loop amplifies IPC/filesystem work, listeners are installed before the apply, and all temporary edit/listener state is invocation-scoped and disposed. No actionable diff-introduced performance issue was found.
