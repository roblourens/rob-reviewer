# Performance review: Re-diff only the changed response while a chat reply streams

[PR #342254](https://github.com/microsoft/vscode/pull/342254) at `8ff4c2e94e1a43c10e1c9af792bf7bbfc76af730`

## Findings

No high-confidence performance findings.

<details>
<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, synchronous-ui-work, cache-lifecycle

### Scenario 1: Streaming a response while a long chat transcript is visible

- Critical path: A response-model change synchronously invalidates ChatViewModel's visible-items cache, Event.accumulate coalesces changes for the current timer turn, ChatWidget calls ChatListWidget.refresh, and the list synchronously computes visible items and updates the ObjectTree before the streamed content is rendered. The PR keeps the existing full-array visibility/equality scan but replaces the root tree diff with a diff under the changed response's request when cached rendered state is valid.
- Scaling input: Visible transcript length N controls the pre-existing getItems/equality scan; response children under the affected request control the changed tree diff, typically one. Accumulated distinct changed requests K are deduplicated, with the common streaming case K=1.
- Effective concurrency: Event.accumulate coalesces synchronous response events into one zero-delay batch. Normally one active response/request is targeted; duplicate events for that request are deduplicated by a Set. There is no asynchronous boundary or parallel worker on this UI path.
- Cache behavior: Each response event invalidates \_visibleItemsCache, so getItems recomputes the visible transcript before the comparison. A prior full refresh warms \_renderedState; matching view model, item identities, editing state, visibility generation, and settings enable the targeted child diff. Cold state or any mismatch falls back to a full refresh. No negative cache or external cache is involved.
- Mechanism confidence: High: the changed event payload identifies the response, the accumulated event reaches refresh(changes), and the new setChildren(request, children) limits tree diff input to that request's response children. The tests explicitly compare 5-turn and 100-turn transcripts and observe five targeted elements in both.
- Magnitude uncertainty: The remaining array scan still scales with transcript length, and exact DOM/tree-diff savings depend on transcript size and stream cadence, but this scan and cache invalidation predate the PR. The added retained maps/sets are bounded by the current transcript and replace on the next full refresh.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff reduces repeated synchronous tree-diff work from the whole transcript to the affected request for the primary streaming scenario; its new cached state is bounded and lifecycle-reset on view-model or full-refresh changes.

### Scenario 2: Structural transcript, editing, visibility, settings, and checkpoint changes

- Critical path: The same synchronous ChatWidget refresh path runs, but add/remove/null events, item-identity changes, editing changes, visibility-generation changes, setting changes, or request diff-identity changes reject the fast path and execute the existing full root refresh. Checkpoint operations can change many response blocked states in one accumulated batch, but the changed request identity causes an early full-refresh fallback rather than per-request targeted updates.
- Scaling input: Visible chat items N, with one coalesced full tree refresh per event batch. Hover widgets cap visible items at two and do not pass targeted changes.
- Effective concurrency: Events are accumulated into one timer-turn callback and one full refresh. The refresh is serialized on the UI thread; no limiter is relevant because no subprocess, IPC, filesystem, database, or network operation is started.
- Cache behavior: The cached rendered state is deliberately invalidated on setViewModel and replaced after every full refresh. Visibility and setting counters, item equality, editing identity, and cached request diff IDs prevent reusing it across state changes that require a full tree diff.
- Mechanism confidence: High: every fallback predicate and the request-identity guard is explicit in refreshChangedResponses, and unchanged callers that do not provide response changes continue to call refresh without entering the fast path.
- Magnitude uncertainty: Full refresh cost remains proportional to the visible transcript as before. The frequency of bulk checkpoint changes varies, but the changed code does not increase their boundary calls, concurrency, or tree-refresh cardinality.
- Expensive boundaries: none found
- Verdict: No reportable regression. Non-streaming and bulk state changes preserve the previous full-refresh behavior, while the added cache is bounded to the current view model and transcript.

### Scenario 3: Response updates while the chat widget is hidden, followed by showing it

- Critical path: While hidden, ChatWidget.onDidChangeItems does not call the list refresh, so response updates remain off the rendering critical path. Showing the widget increments visibleChangeCount and schedules an explicit refresh; because no response-change batch is supplied and progressive rendering must restart, that refresh uses the full path.
- Scaling input: Current transcript size at show time; hidden stream event count does not multiply list refreshes.
- Effective concurrency: Hidden updates may continue arriving and be accumulated, but no list/tree work is performed until the serialized show-time refresh on the UI thread.
- Cache behavior: The prior rendered state may remain retained while hidden, bounded by the current transcript. The changed visibility generation prevents a stale targeted refresh when the widget is shown, and the next full refresh replaces the cache.
- Mechanism confidence: High: ChatWidget gates refresh on visibility, increments visibleChangeCount on visibility changes, and the new state comparison rejects fast reuse across that change.
- Magnitude uncertainty: The number of hidden updates and transcript size vary, but the PR does not add eager hidden rendering or any external I/O.
- Expensive boundaries: none found
- Verdict: No reportable regression. The change does not move rendering onto the hidden path and preserves the required one-time full refresh on show.

**Summary:** Completed the performance pass over all four changed files and every diff hunk. Traced streaming, fallback/bulk-state, and hidden-widget paths through event coalescing, view-model caching, ObjectTree diffing, and lifecycle resets. No actionable performance regression was introduced; the main change bounds synchronous tree diffing during streaming, and no changed or transitive expensive boundary calls were found.
