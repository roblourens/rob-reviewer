# Performance review: Retain full Codex shell output across chat reloads

[PR #337390](https://github.com/microsoft/vscode/pull/337390) at `e6f61b1760aae47dc08dc36082386b32042bf290`

## Findings (1)

### 1. [medium] Read only the retained preview during history restore

**Finding ID:** `PERF-69AF27ED5C64`  
**Location:** <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:6756</code> (<code>RIGHT</code>)  
**Performance category:** <code>gc</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** SQLite BLOB bytes, Uint8Array buffers, and decoded UTF-16 strings up to 10 MiB per retained command  
**Scaling:** O(K \* B) bytes read and decoded, where K is the number of retained commands with replay output &lt;=80,000 characters and B is each retained blob size up to 10 MiB; the awaited loop also serializes their latency.  
**Outcome:** increased chat-history latency and CPU/GC pressure from full-blob reads and decoding  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, Codex replay mapped the app-server's output directly and did not read or decode any terminal-output blobs from the session database during history loading.  
**Changed behavior:** History restoration now loads the entire retained terminal-output blob from SQLite and UTF-8-decodes it when Codex replay supplies short, empty, or null output, then discards everything after the 400-character preview.  
**Confidence:** 0.99 — The call path is direct from \`\_getChatMessages\` and incremental \`\_refreshChatHistory\`, both await \`\_restoreRetainedCommandOutputs\` before publishing turns. \`SessionDatabase.readTerminalOutput\` performs SQLite reads of the full blob, retained output is explicitly bounded only at 10 MiB, and the new tests exercise retained commands whose native replay output is short, empty, and null. Only prevalence of that replay discrepancy is uncertain.

**Causal diff evidence:** The added restoration branch at RIGHT line 6756 calls \`readTerminalOutput\` whenever a retained command's replayed output is at most 80,000 characters; the next added line decodes the returned blob, while \`codexRetainedCommandOutputContent\` keeps only a 400-character slice.

Opening or refreshing a chat containing retained commands whose native replay output became short or missing can allocate and decode up to 10 MiB per command before any history is shown, increasing reload latency and causing avoidable memory/GC pressure. Multiple affected commands scale the total bytes read and decoded linearly.

**Evidence:** \`\_restoreRetainedCommandOutputs\` runs on the chat-history critical path. For every retained command with replay output &lt;=80,000 characters it awaits \`database.object.readTerminalOutput\`, whose implementation selects the full \`output\` BLOB after a size query, then \`VSBuffer.wrap(storedOutput).toString()\` allocates a full decoded string. The only consumer, \`codexRetainedCommandOutputContent\`, immediately slices that string to 400 UTF-16 code units. Retained blobs may be as large as \`MAX\_TERMINAL\_OUTPUT\_BYTES\` (10 MiB per the PR contract), and the loop repeats serially for every affected command.

**Suggested direction:** Add a bounded database read for just the preview prefix (or persist the 400-character preview alongside the retained blob) and use that here, while retaining the existence check needed to distinguish retained commands. Do not materialize the complete blob merely to construct the preview.

### Scenario 1: Live completion of a parent Codex shell command with large output

- Critical path: For output over 80,000 UTF-16 units and at most 10 MiB UTF-8, UTF-8 encoding and the SQLite write must complete before the command completion and every subsequently ordered chat signal are published. Non-qualifying and subagent output stays on the prior synchronous publication path.
- Scaling input: Number of qualifying large command completions and each output's UTF-8 size, bounded at 10 MiB per command.
- Effective concurrency: Each SQLite database serializes terminal-output mutations through its turn-data sequencer. Notifications can start multiple retention promises, but writes execute serially; chat publication is also serialized per session by \`\_pendingChatProgress\`.
- Cache behavior: No output cache is consulted before retention. The session database reference may already be warm, but each qualifying tool call gets its own write; tool-call IDs provide replacement semantics rather than coalescing. Failed writes fall back to the already-held full inline output.
- Mechanism confidence: High: the diff directly encodes the full string, starts a sequenced database mutation, and gates signal publication on its promise.
- Magnitude uncertainty: Local SQLite write duration and the frequency of multiple large outputs in one turn vary; the synchronous encoding and ordering dependency are certain. The intentional persistence-before-publication tradeoff and bounded 10 MiB size make this insufficient for a separate finding.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_retainCommandOutput</code>: Encode up to 10 MiB of output and insert/update the terminal\_outputs SQLite row.; cardinality: One database write per qualifying completed parent command; zero for output &lt;=80,000 characters, over 10 MiB, storage failures before write, or subagent output.
    - Introduced by diff: true; previous behavior: The complete command output was published inline immediately and no session-database terminal-output write occurred.; critical-path effect: The write is newly awaited before publishing the matching completion, and subsequent signals queue behind it to preserve order.
- Verdict: The new persistence and ordering cost is intentional and bounded per command. Potential queued allocations were considered, but no separate high-confidence regression beyond the reported restore allocation was established.

### Scenario 2: Initial chat reload and incremental watched-history refresh

- Critical path: Codex thread history IPC completes first, then \`\_getChatMessages\` and \`\_refreshChatHistory\` await all retained-output restoration before returning or publishing turns. Full retained blobs are therefore read and decoded on the visible history-load critical path when replay output is short or missing.
- Scaling input: Effective number of rendered shell calls after sandbox pre-flight coalescing; full-read cost further scales with the count and byte size of retained outputs whose native replay output is short, empty, or null.
- Effective concurrency: Cold-session reads are globally limited by \`\_coldSessionReadLimiter\`; Codex history pages and retained-output checks run serially. Within restoration, commands are iterated sequentially, and SessionDatabase also sequences terminal-output reads.
- Cache behavior: The database may benefit from an already-open handle and OS/SQLite page cache, but there is no retained-ID cache or bulk lookup. Every replayed rendered command is checked again; incremental refresh limits this to commands in changed turns.
- Mechanism confidence: Very high: both history entry points await the loop, the database implementation selects the full BLOB, and only a 400-character preview survives.

- Expensive boundaries:

    - Introduced by diff: false; previous behavior: The same app-server history requests were required before this PR.; critical-path effect: Supplies all turns before mapping and remains on the history-load critical path.
  - database at <code>src/vs/platform/agentHost/node/codex/codexAgent.ts:\_restoreRetainedCommandOutputs</code>: Discover retained outputs and reconstruct terminal preview content from the per-chat SQLite database.; cardinality: One filesystem stat/open attempt when at least one rendered command exists, one SQLite size query per rendered/coalesced shell command, and for each retained command with replay output &lt;=80,000 characters an additional full-output read that internally performs a size query plus a BLOB query.
    - Introduced by diff: true; previous behavior: Replay mapped app-server output directly and performed no session-database access for command output.; critical-path effect: All checks and reads are awaited before initial history returns or changed history publishes.

- Mechanism confidence: High: every removed command ID creates a distinct mutation, and the database sequencer makes them execute serially despite Promise.all.
- Magnitude uncertainty: Large multi-turn reverts can contain many commands, but truncation is infrequent and each indexed delete is small. This was considered as boundary fan-out but not reported without stronger evidence of user-visible magnitude.
