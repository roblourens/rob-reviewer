## Findings (2)

### 1. [medium] Keep preview measurement off the editor scroll path

**Finding ID:** `PERF-A0A7CAC2F426`  
**Location:** <code>src/vs/sessions/contrib/agentFeedback/browser/agentFeedbackEditorWidget.ts:1010</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous DOM style/layout calculations for every comment preview  
**Scaling:** Cost grows with editor scroll event frequency multiplied by the number of comment widgets and comments in each grouped widget; expanded previews additionally perform a class write, geometry reads, and a restoring write on every event.  
**Outcome:** Increased main-thread layout work and dropped frames while scrolling comment-heavy files  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The contribution already repositioned each widget on editor scroll, but the old layout path performed only a constant number of widget-level geometry reads and did not remeasure every comment preview.  
**Changed behavior:** The changed layout method now calls \_updateTextPreviews on every relayout; that helper iterates all previews, toggles the collapsed class, and reads clientHeight/scrollHeight before layout continues with more body/widget measurements.  
**Confidence:** 0.98 — The hot call path and multiplicity are explicit in repository code, and the diff directly adds the per-comment DOM measurements to it. Exact milliseconds depend on card count and markdown size, which affects severity but not mechanism confidence.

**Causal diff evidence:** RIGHT line 1010 adds \`this.\_updateTextPreviews();\` to \`layout()\`, which is transitively called for every editor scroll by the contribution; the helper and its per-comment geometry reads are also introduced by this diff.

With realistic grouped stacks such as the ten-card case covered by the added tests, every trackpad/wheel scroll synchronously remeasures all preview DOM even though scrolling does not change truncation. Long or expanded markdown cards can therefore make editor scrolling visibly janky.

**Evidence:** AgentFeedbackEditorWidgetContribution.ts:67-70 invokes widget.relayout() for every onDidScrollChange. The added call at AgentFeedbackEditorWidget.ts:1010 enters \_updateTextPreviews; lines 454-462 show its per-preview clientHeight/scrollHeight reads and collapsed-class mutations, and layout then reads body.scrollHeight/offsetHeight/clientHeight. This changes the existing scroll path from O(widgets) widget positioning to O(comments) preview measurement plus widget geometry.

**Suggested direction:** Separate position-only scroll relayout from size/content relayout. Recompute preview truncation only when card content or available width changes (for example from the resize observer), cache the result, and batch DOM writes before geometry reads.

### 2. [medium] Avoid a backdrop-filter surface for every comment card

**Finding ID:** `PERF-B1FCE9680364`  
**Location:** <code>src/vs/workbench/contrib/modernUI/browser/media/frostedGlass.css:90</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Independent compositor/backdrop-filter surfaces and blurred pixels for each visible comment card  
**Scaling:** Rendering cost grows with the number and painted area of visible cards on every frame whose editor backdrop or card position changes; the PR's own oversized-stack scenario renders ten cards.  
**Outcome:** Higher GPU/compositor load and dropped frames while scrolling or resizing editors with comment stacks  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Agent feedback cards were not selected by the frosted-glass surface rule, so they used an opaque background and created no 12px backdrop-filter layers.  
**Changed behavior:** The added selector makes every \`.agent-feedback-widget-item\` instantiate the shared \`::before\` surface, whose rule applies \`backdrop-filter: blur(12px)\`. A grouped stack therefore creates one persistent blur surface per card.  
**Confidence:** 0.94 — The one-filter-per-card DOM/CSS relationship and scrolling scenario are explicit. Hardware-specific GPU cost is uncertain, so severity is medium, but independent backdrop filtering over changing editor content is a concrete rendering mechanism.

**Causal diff evidence:** RIGHT line 90 newly includes \`.agent-feedback-widget-item\` in the selector whose \`::before\` applies the 12px backdrop filter; before this PR comment cards were absent from that selector.

When frosted glass is enabled, scrolling code underneath an always-visible multi-card stack requires recompositing multiple full-card blur regions each frame, making editor scrolling and resize less smooth as the stack grows.

**Evidence:** The added \`.agent-feedback-widget-item\` selector at line 90 joins the common surface rule; lines 95-106 define an absolute full-card pseudo-element with \`backdrop-filter: blur(12px)\`. The changed widget renders one \`.agent-feedback-widget-item\` per comment, and the added OversizedCommentStack fixture explicitly models ten visible cards.

**Suggested direction:** Consolidate frosted rendering to at most one backdrop-filter surface per widget/stack (using masking/clipping if gaps must remain clear), or keep repeated cards translucent without applying backdrop-filter individually.
