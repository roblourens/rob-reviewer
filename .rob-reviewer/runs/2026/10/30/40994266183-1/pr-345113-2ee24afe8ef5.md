# Performance review: agentHost: add scoped permission rules and smart approvals

## Findings (2)

### 1. [medium] Cache or bound the Git-root lookup before showing file confirmations

**Finding ID:** `PERF-1C48902F70F7`  
**Location:** <code>src/vs/platform/agentHost/node/sessionPermissions.ts:950</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** serial filesystem access calls for .git entries  
**Scaling:** Each read/write confirmation performs one awaited filesystem access per ancestor between the target's parent and the first Git root, or all the way to the filesystem root when none exists; the work repeats for every prompted file because there is no cache or coalescing.  
**Outcome:** increased confirmation latency and excessive filesystem I/O  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A pending read/write confirmation could be converted to ChatToolCallReady without probing ancestor directories for repository metadata.  
**Changed behavior:** The new path-option builder walks upward and awaits an existence check for .git at every directory before constructing and dispatching the confirmation action.  
**Confidence:** 0.99 — The added loop, concrete fs.promises.access implementation, awaited caller, and tests enumerating one probe per ancestor establish the mechanism and critical-path placement directly. Only the duration of each filesystem access and typical path depth are environment-dependent.

**Causal diff evidence:** Added RIGHT line 950 is the new awaited filesystem boundary inside the ancestor loop, and agentSideEffects.ts adds an await of this method before the UI-ready action is created.

For a file outside a repository, or in a deep checkout/network-mounted workspace, the confirmation card cannot appear until all ancestor filesystem requests complete. Repeated file prompts repeat the same walk, making agent interactions visibly stall and increasing I/O.

**Evidence:** \_handleToolReady now awaits getPathConfirmationOptions at agentSideEffects.ts:1769 before createToolReadyAction and before dispatching the ready action. The added loop at lines 949-956 serially calls this.\_exists for each ancestor; the default is Promises.exists, implemented with fs.promises.access. Added tests explicitly expect /repo/src/.git, /repo/.git, and /.git probes when no repository is found, confirming depth-proportional cardinality.

**Suggested direction:** Resolve the repository root from existing workspace/SCM metadata where possible, or memoize/coalesce ancestor results per directory and stop at a known workspace boundary; fall back to the direct parent without walking to the filesystem root.

### 2. [medium] Avoid resolving file paths twice for unrelated permission rules

**Finding ID:** `PERF-D09D2858FE62`  
**Location:** <code>src/vs/platform/agentHost/node/sessionPermissions.ts:286</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** filesystem realpath operations and ancestor probes for nonexistent paths  
**Scaling:** For each read/write tool request, any nonempty allow or ask list adds one full realpath-resolution chain; unmatched requests then perform the existing chain again, and nonexistent targets can issue one realpath call per ancestor. A nonempty deny list adds another chain before this pass.  
**Outcome:** increased tool approval latency and excessive filesystem I/O  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Per-tool permission checks were in-memory name lookups; read/write requests performed symlink resolution only in the existing read or edit auto-approval check.  
**Changed behavior:** The added generic allow/ask block resolves every read/write path before checking whether any rule can target that permission kind, then the normal read/write auto-approval logic resolves the same path again when no rule matches.  
**Confidence:** 0.98 — The changed call path is explicit: \_handleToolReady awaits getAutoApproval for every request; the added permission block calls \_resolvePermissionRequests, and unmatched read/write requests then continue into the pre-existing \_isReadAutoApproved or \_isEditAutoApproved path, which calls \_resolveResourcesForApproval again. Root permissions are populated with Shell/WebFetch approvals by this PR, so unrelated rules realistically activate the duplicate resolution. Exact filesystem latency varies by mount and path existence, which affects severity but not mechanism confidence.

**Causal diff evidence:** Added RIGHT line 286 introduces the first await of \_resolvePermissionRequests in getAutoApproval; before this hunk, permission lookup did not touch the filesystem and only the later read/write validation resolved the path.

After a user has any persistent shell or URL approval, each agent file read/write can incur duplicate realpath I/O before it proceeds. On deep, missing, network-mounted, or otherwise slow paths this delays auto-approval or the confirmation UI for every file operation in a turn.

**Evidence:** At the added line, getAutoApproval awaits \_resolvePermissionRequests whenever any allow/ask rule exists. \_resolvePermissionRequests calls \_resolveResourcesForApproval for read/write paths (line 924). If an unrelated Shell/WebFetch rule or a nonmatching path rule does not approve, execution reaches \_isReadAutoApproved (line 326) or \_isEditAutoApproved (line 343), which call \_resolveResourcesForApproval again at lines 648/782. resolveRealPathForNonexistent walks ancestors serially for missing targets. The same PR syncs terminal and URL approvals into root permissions, making unrelated nonempty rule lists a normal state.

**Suggested direction:** Filter allow/ask rules by the request's tool/kind before resolving paths, and carry the resolved literal/real-path candidates through the remaining read/write auto-approval checks so each request resolves at most once.

- Effective concurrency: Checks within one request are serial. Concurrent tool requests can launch independent realpath and Git-root walks without a shared limiter or coalescing.
- Cache behavior: No application cache exists for resolved request paths or nearest Git roots; only OS filesystem caches may make warm calls cheaper. Negative Git-root results are repeated.
- Mechanism confidence: High: changed awaits, filesystem implementations, pre-existing second resolution, and test-asserted ancestor cardinality directly establish both mechanisms.
- Magnitude uncertainty: Local shallow paths may make each access cheap, while deep paths, missing targets, network mounts, and repeated agent edits make the delay substantially larger.

### Scenario 2: Agent-host shell command approval and scoped-grant option generation

- Critical path: Tree-sitter parsing and rule classification run synchronously in the host before auto-approval or confirmation dispatch. A deny list adds a separate deny parse, and an unresolved command is evaluated again to construct scoped options.
- Scaling input: Number and length of shell commands, parsed subcommands, and permission rules.
- Effective concurrency: Each permission event evaluates independently on the event loop; there is no shared limiter, but parsing is synchronous and commands are normally short.
- Cache behavior: Tree-sitter grammars and compiled default rules are cached. Parse trees/evaluations are not cached per command.
- Mechanism confidence: High for execution flow, lower for material user-visible magnitude.

- Verdict: No additional finding; the PR also removes asynchronous renderer-side parsing, and the remaining added parse cost was not proven material independently.

### Scenario 3: Approve-once, session grant, or host grant for shell and URL tools

- Critical path: The confirmation response is dispatched to the host immediately. Mirroring a host-scoped grant into VS Code settings is fire-and-forget and therefore off the current tool's critical path.
- Scaling input: Number of host-scoped user approvals, not number of ordinary tool calls.
- Effective concurrency: A module-level Sequencer serializes all mirror writes, preventing lost-update bursts; no unbounded parallel settings writes.
- Cache behavior: Each queued write re-inspects the latest user value, which preserves earlier writes; there is no negative cache, but grants are user-driven and low frequency.
- Mechanism confidence: High.
- Magnitude uncertainty: Configuration persistence cost depends on the settings backend but is off path and low cardinality.
- Expensive boundaries:

    - Introduced by diff: true; previous behavior: Agent-host confirmation did not mirror persistent grants into these user settings.; critical-path effect: Off the current approval critical path; writes are queued after confirmation dispatch.
- Verdict: No reportable regression because the expensive boundary is deliberately serialized and off the approval critical path.

### Scenario 4: Local agent-host startup and permission-setting synchronization

- Critical path: On host/root-state hydration or relevant user-setting changes, the contribution converts configured URL/terminal entries and dispatches structurally changed root config to the host. - Scaling input: Number of configured approval rules and frequency of user settings changes, normally small and infrequent.
- Effective concurrency: The forwarder coalesces structurally equal values; host persistence is chained/serialized, and no subprocess or network boundary is introduced.

- Mechanism confidence: High.
- Magnitude uncertainty: Very large user rule tables increase conversion/allocation linearly, but realistic tables are small.

- Verdict: No reportable regression; work is bounded by infrequent configuration changes and existing equality/serialization guards.
