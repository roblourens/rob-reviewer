# Performance review: editor: keep wrapped Agents tab controls separate

[PR #340834](https://github.com/microsoft/vscode/pull/340834) at `79c015b84ef9196ab30b682fda61c9be552f499c`

## Findings (1)

### 1. [medium] Avoid remeasuring every tab on each wrapped layout

**Finding ID:** `PERF-3FF239118BC2`  
**Location:** <code>src/vs/workbench/browser/parts/editor/multiEditorTabsControl.ts:2245</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Per-tab DOM geometry and computed-style reads (\`offsetWidth\` plus two \`getComputedStyle\` margin reads in \`getTotalWidth\`)  
**Scaling:** Each wrapped/overflowing layout adds O(number of open tabs) style measurements; resize can schedule this once per animation frame, and the default editor limit is disabled, so the cardinality is not bounded.  
**Outcome:** Increased main-thread layout/style cost and dropped resize frames for groups with many open tabs  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The fit predicate measured only the last tab's \`offsetWidth\` and the toolbar width, so this portion of each layout was O(1) in the number of open tabs.  
**Changed behavior:** The predicate now calls \`getTotalWidth\` for the last item and then for every tab to find the widest item before deciding whether wrapping is allowed.  
**Confidence:** 0.96 — The call path, per-frame coalescing, helper implementation, and O(N) multiplicity are explicit in repository code; only the exact millisecond impact varies by tab count and browser. Existing layout loops do not negate the newly added two computed-style reads per tab.

**Causal diff evidence:** The added lines 2245-2247 introduce the full-tab \`forEachTab\` measurement loop inside \`tabsFitWrapped\`; the deleted predicate computed overlap from one \`lastTab.offsetWidth\` read.

With \`workbench.editor.wrapTabs\` enabled and enough tabs to overflow, every resize frame and other tab relayout scans all open tabs. Large editor groups therefore spend progressively more main-thread time measuring tab styles, making resizing and tab updates janky.

**Evidence:** \`doLayoutTabsWrapping\` runs from the animation-frame-coalesced \`layout\` path. When wrapping is active, or when an overflowing strip is being considered for wrapping, \`tabsFitWrapped()\` executes on each layout. The added \`forEachTab\` calls \`getTotalWidth\` for every tab; \`getTotalWidth\` reads \`offsetWidth\` and obtains left and right margins through two \`getComputedStyle\` calls. Open-editor limiting defaults to disabled, so realistic large tab sets are unbounded. The pre-diff predicate used only \`lastTab.offsetWidth\`.

**Suggested direction:** Maintain the maximum required tab width when tab geometry can change (open/close, label/decorations, sizing/options), or otherwise cache per-tab total widths with those invalidations, so resize-only layouts compare a cached maximum instead of querying every tab's computed style.
