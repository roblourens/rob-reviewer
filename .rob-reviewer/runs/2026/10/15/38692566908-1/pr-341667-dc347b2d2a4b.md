# Performance review: Make copilot work in any terminal with a native Copilot CLI shim

[PR #341667](https://github.com/microsoft/vscode/pull/341667) at `dc347b2d2a4bfbf7cb5c5818eb472547940ae8cf`

## Findings (2)

### 1. [medium] Stop PATH discovery after the first launchable CLI

**Finding ID:** `PERF-910A059741E5`  
**Location:** <code>copilot\_shim/src/candidate.rs:134</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem metadata operations and reads of candidate executables/scripts  
**Scaling:** Every invocation performs one candidate lookup per PATH directory on Unix and four per directory on Windows, plus canonicalization/metadata/identity calls for hits and up to 16 MiB of reads for each later small candidate; cost grows with PATH length and with shim copies after the selected CLI.  
**Outcome:** increased command startup latency and lower interactive throughput, with especially large stalls when trailing PATH entries are disconnected drives, UNC paths, or slow mounts  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The deleted script shims delegated command resolution to the shell/Get-Command, which stopped at the first matching real \`copilot\`; PATH entries after that command were not touched on the launch critical path.  
**Changed behavior:** \`select\_candidate\` calls \`discover\`, and this added loop always inspects every unique PATH directory and every platform candidate name before returning the result, even though normal launch later selects only the first usable candidate.  
**Confidence:** 0.98 — The exhaustive loop, per-entry filesystem boundaries, and per-launch call path are explicit. Exact latency varies with PATH contents, but trailing network or disconnected entries are a realistic trigger and were not reached by the prior first-match command lookup.

**Causal diff evidence:** The added \`for directory in directories\` loop at line 134 has no early-exit path and fills \`DiscoveryResult\`; \`app.rs:297\` invokes this on every launch, while \`app.rs:252-267\` consumes candidates in order and returns the first usable one.

Running \`copilot\` with an already-installed CLI early in PATH still probes every trailing entry. On enterprise Windows configurations with long PATHs and stale network/drive entries, each invocation can block on dozens of filesystem probes before the CLI starts.

**Evidence:** \`candidate.rs:134-147\` exhaustively walks all directories; on Windows \`CANDIDATE\_NAMES\` has four names. \`runtime.rs:158-192\` shows each hit incurs symlink metadata, canonicalization, metadata, file identity, and executable checks. \`candidate.rs:260-289\` additionally opens each non-current candidate up to 16 MiB and scans it for shim markers. The normal launch caller only needs the first usable candidate, so all work after it is unnecessary; exhaustive diagnostics are only needed for installer PATH filtering.

**Suggested direction:** Provide an ordered, short-circuiting discovery mode/iterator for \`select\_candidate\`, stopping once a candidate is resolved as launchable while continuing past shims or unusable scripts. Keep the existing exhaustive collection only for \`installer\_path\`, which genuinely needs every shim directory.

### 2. [medium] Do not block installer navigation on the download probe

**Finding ID:** `PERF-F1E4CDEE98EB`  
**Location:** <code>build/win32/copilot.iss:1101</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** two sequential HTTPS HEAD requests and synchronous wizard-thread waiting  
**Scaling:** The delay is bounded at six seconds per interactive setup run, but approaches the full bound on offline, proxy-autodiscovery, filtered, or high-latency networks; requests are sequential rather than parallel.  
**Outcome:** increased installer latency and a visibly blocked setup critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, leaving the Select Tasks page did not launch or wait for Copilot release-network probes.  
**Changed behavior:** The added NextButtonClick handler calls \`CopilotWaitForProbe\` before navigation can continue; that method loops on the UI thread until the result appears or \`CopilotProbeWaitMs\` (6000 ms) elapses.  
**Confidence:** 0.97 — The synchronous wait and the two network boundaries are directly traced and bounded. The exact prevalence depends on network conditions and how long the user spends on earlier pages, which affects severity but not the mechanism.

**Causal diff evidence:** Added line 1101 synchronously invokes \`CopilotWaitForProbe\`; added lines 532-539 wait in a Sleep loop for up to 6000 ms.

An interactive Windows install with no existing Copilot CLI can pause for roughly 5-6 seconds when the network or corporate proxy is unavailable, even if the user intends to choose “install on first use” or “don’t add.”

**Evidence:** \`CopilotStartProbe\` launches the shim with network enabled for the user installer. \`setup/mod.rs:257-353\` performs a HEAD to \`/latest\`, follows its release tag, then performs a second HEAD for the MSI asset, under a five-second probe deadline. \`copilot.iss:523-541\` converts that background work into a blocking marquee wait when the user leaves Select Tasks.

**Suggested direction:** Keep the probe off the navigation critical path: show the basic choices immediately and update download details asynchronously if the probe finishes, or defer release probing until the user explicitly selects “Install now.” Preserve a timeout for the eventual install operation.

### Scenario 1: Launch \`copilot\` when a real CLI is already installed, from an external or integrated terminal

- Effective concurrency: Discovery is fully serial; the final CLI starts only after it completes. There is no limiter need because there is one invocation, but there is also no short-circuiting.
- Cache behavior: No positive or negative discovery cache is used; every invocation repeats all metadata and marker reads. OS filesystem cache may make local warm launches cheaper but does not avoid remote/disconnected entry latency.
- Mechanism confidence: High: exhaustive iteration, boundary cardinality, and launch reachability are explicit in the added code.
- Magnitude uncertainty: Local short PATHs may hide the cost; enterprise PATHs containing UNC shares, mapped drives, automounts, or multiple VS Code shim copies can make it substantial.
- Expensive boundaries:
  - filesystem at <code>copilot\_shim/src/candidate.rs:discover\_directories/inspect\_candidate/other\_shim</code>: Inspect the running shim and candidate names in every unique PATH directory; canonicalize/stat/identify hits and scan small candidates for shim markers.; cardinality: For D unique PATH directories: D lookups on Unix or 4D on Windows, plus several metadata calls and up to 16 MiB read per existing small non-current candidate. ### Scenario 2: Run \`copilot\` when no CLI is installed and accept first-use installation

- Critical path: Initial exhaustive discovery and expected-install-directory fallback occur before prompting. After consent, tool discovery, downloader/install subprocesses, and post-install rediscovery are required before the CLI can launch.
- Scaling input: PATH size, number of available installer tools/routes, route failures, download size, and network latency.
- Effective concurrency: Discovery and installer routes are serial. The installer does not burst concurrent network/process work; fallback routes execute only after failure.
- Cache behavior: No persistent discovery or negative cache; expected install directories are checked on every missing-CLI invocation. Successful installation ends the missing state; failures are retried on a later invocation only after a fresh prompt.
- Mechanism confidence: High for call flow and boundary counts.
- Magnitude uncertainty: Install duration is dominated by external network/package-manager behavior, while repeated PATH passes vary by environment.
- Expensive boundaries:
  - filesystem at <code>copilot\_shim/src/app.rs:prepare\_workflow/request\_install; copilot\_shim/src/candidate.rs; copilot\_shim/src/install.rs:discover\_tools</code>: Initial PATH discovery, fallback directory discovery, installer-tool discovery, installer PATH filtering, and post-install rediscovery.; cardinality: Multiple serial passes over D PATH entries; tool discovery independently searches for bash/curl/wget and brew, and installer filtering performs another exhaustive Copilot search.

  - network at <code>copilot\_shim/src/install.rs:run\_installer\_with/downloader\_command</code>: Download the official install script with curl/wget, or invoke Homebrew/MSI installation.; cardinality: One route at a time; failed routes can fall through serially to the next available route.

  - subprocess at <code>copilot\_shim/src/install.rs:run\_command and copilot\_shim/src/app.rs:launch\_candidate</code>: Run downloader, installer script/Homebrew/MSI, then launch the installed CLI.; cardinality: Typically downloader plus installer plus final CLI; more if earlier installer routes fail.

### Scenario 3: Interactive Windows VS Code setup when Copilot CLI is absent

- Critical path: A shim probe starts in the wizard, and leaving Select Tasks synchronously waits for its result before the Copilot page can be shown. Publishing/installing later occurs after the user's selection.
- Scaling input: Network/proxy latency and failure behavior rather than collection size; wait is bounded to six seconds.
- Effective concurrency: Network work runs on one probe worker thread, but the two HEAD requests are sequential. Setup polls serially and blocks navigation; there is no coalescing need because only one probe is started.
- Cache behavior: No release metadata cache. The probe is guarded to one run per setup process, so it is not repeated within the same wizard.
- Mechanism confidence: High: the synchronous wait and exact network sequence are explicit.
- Magnitude uncertainty: Users who spend enough time on earlier pages may hide the wait; immediate navigation or slow/offline corporate networks exposes nearly the full bound.
- Expensive boundaries:
  - subprocess at <code>build/win32/copilot.iss:CopilotStartProbe/CopilotWaitForProbe</code>: Launch the temporary shim probe and poll its result INI file.; cardinality: One probe process and repeated result-file existence checks every 50 ms for up to six seconds.
    - Introduced by diff: true; previous behavior: No Copilot probe process or result polling existed.; critical-path effect: The wizard thread blocks at page navigation until the probe completes or the wait bound expires.
  - network at <code>copilot\_shim/src/setup/mod.rs:resolve\_latest\_tag/probe\_download</code>: Resolve the latest GitHub release and query MSI asset size using two sequential HTTPS HEAD requests.; cardinality: Two requests when policy allows, no CLI is found, and the user installer enables network probing; no cache.
    - Introduced by diff: true; previous behavior: Setup did not contact Copilot release endpoints before this change.; critical-path effect: Although executed in the probe process, setup waits synchronously for the result, moving network latency onto navigation.
  - filesystem at <code>copilot\_shim/src/setup/mod.rs; build/win32/copilot.iss</code>: Probe PATH/registry-derived directories, write/read result INI files, publish the shim, and manage retired copies.; cardinality: One PATH scan plus small result/progress files; publication cleanup scans the shim directory once.

### Scenario 4: Copilot extension activation and opening an integrated Copilot terminal

- Critical path: Activation checks for the shipped shim and removes stored legacy shims. \`openTerminal\` awaits this initialization, then resolves shell configuration and creates the terminal.

- Cache behavior: The initialization promise coalesces work within the extension instance. Packaged activation deletes stale stored state rather than retaining a growing cache; local retired copies are cleaned on later activation.
- Mechanism confidence: High for the activation flow; low magnitude for packaged builds.
- Magnitude uncertainty: Legacy storage is normally tiny; abnormal unrelated contents could enlarge recursive cleanup, but that is not a normal product trigger.
- Expensive boundaries:

- Cache behavior: Cargo compilation uses shared sccache; artifacts are immutable per build. No runtime cache concern.
- Mechanism confidence: High for the pipeline dependencies, uncertain for measured duration.
