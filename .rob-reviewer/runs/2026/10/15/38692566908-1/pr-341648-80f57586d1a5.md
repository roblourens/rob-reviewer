### Scenario 1: Search the customization marketplace from an unmaterialized/no-chat session while signed in

- Critical path: The request gets/starts the Copilot client, creates or reuses a hidden policy session, and then performs catalog.search. On a cold hidden session, mcp.discover and createSession were already serial prerequisites; the diff adds an awaited session.rpc.gitHubAuth.setCredentials call before catalog.search can begin. On a warm hidden session this setup is skipped.
- Scaling input: The added work scales with hidden-policy-session creation, not catalog result count or search count. Concurrent cold requests share policySessionCreation, and subsequent requests reuse one session until its 10-minute idle release or an auth/client lifecycle change.
- Effective concurrency: Hidden session creation is promise-coalesced globally in CopilotCustomizationInstallations. The added credential RPC executes once for that shared creation; it does not fan out by query, result, MCP server, or candidate.
- Cache behavior: Cold: one hidden session is created and credential-bound. Warm: the cached session is touched and reused, so no additional setCredentials call. The session is invalidated on auth/client changes and expires after ten minutes idle; failed creation is not cached.
- Mechanism confidence: High confidence in the added awaited IPC and its once-per-cold-session reachability; low confidence that it adds a separate network request.
- Magnitude uncertainty: The latency of setCredentials and whether its implementation performs a remote metadata lookup are not visible in this repository. The confirmed incremental cost is one coalesced IPC round trip on cold signed-in policy-session creation.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/customizations/copilotCustomizationInstallations.ts search/getClient</code>: Ensure/start the Copilot SDK runtime client when it is not already running; cardinality: At most once per cold client lifecycle, independent of result count
    - Introduced by diff: false; previous behavior: The same client startup was already required.; critical-path effect: Must complete before hidden-session creation and catalog search
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts createCustomizationPolicySession</code>: Discover MCP servers and create the hidden SDK session; cardinality: One discover RPC and one session creation per cold hidden policy session
    - Introduced by diff: false; previous behavior: Both boundaries already ran before each hidden-session creation.; critical-path effect: Serial prerequisites to marketplace search
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:841</code>: Install the current GitHub credential into the hidden session via gitHubAuth.setCredentials; cardinality: One call per signed-in hidden-session creation after coalescing; zero while signed out

The constant, coalesced credential-binding RPC is the behavior required to make the subsequent authenticated catalog operation work, is skipped on warm reuse, and has no collection fan-out or unbounded lifecycle. No bounded alternative preserving the required ordering is evidenced.

### Scenario 2: List, recover, install, or uninstall customizations without a visible Copilot chat session

- Critical path: These operations obtain the same hidden policy session before issuing their existing SDK installation RPCs. The diff adds the same credential-binding RPC only when that shared hidden session is cold; list/recover then issue their existing skill and MCP RPCs in parallel, while prepare/apply operations retain their existing sequencing.
- Scaling input: The added cost is one per hidden-session lifecycle regardless of installation count, candidate count, or the two skill/MCP service branches.
- Effective concurrency: Cold creation is coalesced across concurrent operations. Existing list/recover skill and MCP calls use Promise.all after the one shared session is ready; credential setup itself is serialized once before them.
- Cache behavior: All operation types share the same positive cached policy session and ten-minute idle timer. Failed creation clears policySessionCreation and does not pin a negative result.
- Mechanism confidence: High confidence in coalescing, lifecycle, and ordering from the service implementation and tests.
- Magnitude uncertainty: SDK-internal duration is not available, but the new cardinality is definitively one credential RPC per shared session rather than per installation or per file.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts createCustomizationPolicySession</code>: Discover MCP configuration, create the hidden session, and bind credentials; cardinality: One sequence per cold hidden session; only the final credential-binding RPC is new
    - Introduced by diff: true; previous behavior: Discovery and creation occurred, but explicit credential binding did not.; critical-path effect: Must finish before installation APIs receive the policySessionId
  - IPC at <code>src/vs/platform/agentHost/node/copilot/customizations/copilotCustomizationInstallations.ts</code>: Invoke SDK skill/MCP list, recovery, planning, or apply APIs; cardinality: List/recover use two grouped calls; other operations use their existing bounded operation sequence
    - Introduced by diff: false; previous behavior: The same operation calls and concurrency were present.; critical-path effect: Performs the requested management operation after session setup
  - filesystem at <code>Transitive SDK skill/MCP installation APIs called by CopilotCustomizationInstallations</code>: SDK customization installation planning/apply may inspect or modify installation files; cardinality: Depends on the selected single operation and its reviewed file set, not changed by this diff
    - Introduced by diff: false; previous behavior: Installation filesystem work was already performed by the same SDK APIs.; critical-path effect: Existing operation-specific work after policy setup
- Verdict: No reportable regression. The change adds no fan-out by installation/file count and does not reduce existing parallelism.

### Scenario 3: Create a hidden policy session while signed out or while credential binding fails

- Critical path: Signed out, the token guard skips the new RPC and returns the session as before. With a token and a binding failure, the new path awaits disconnect and then deleteSession before surfacing the error.
- Scaling input: Zero added boundary calls for signed-out creation. Failure cleanup is bounded to one disconnect and one delete for the single partially created session per failed, coalesced creation attempt.
- Effective concurrency: Creation remains coalesced. Failure cleanup is intentionally sequential for one session; concurrent callers observe the same creation rejection rather than each running cleanup.
- Cache behavior: A failed creation is removed from policySessionCreation and the session ID set; no failed session is cached. A later user operation may retry with a new session, but there is no automatic retry loop in the changed path.
- Mechanism confidence: High confidence in the token guard, bounded cleanup, and failed-creation cache clearing.
- Magnitude uncertainty: Individual cleanup latency is unknown; there is no evidence of automatic retry frequency or unbounded failure churn.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:841</code>: Bind GitHub credentials; cardinality: Zero if tokenless; one for a signed-in creation attempt
    - Introduced by diff: true; previous behavior: No binding attempt or binding-failure path existed.; critical-path effect: Determines whether the hidden session can be returned
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts:853-860</code>: Disconnect and delete the partially created hidden session after binding failure; cardinality: At most one disconnect plus one delete per failed coalesced creation
    - Introduced by diff: true; previous behavior: This failure mode did not exist because credential binding was not attempted.; critical-path effect: Delays error propagation by bounded cleanup but releases the runtime/session resources
- Verdict: No reportable regression. Signed-out behavior adds no work, and the failure-only cleanup trades bounded error-path latency for avoiding retained session resources.

**Summary:** Reviewed all three changed files and traced the hidden customization policy session through marketplace search, installation management, authentication lifecycle, SDK IPC, subprocess startup, catalog/network work, filesystem effects, coalescing, cache expiry, and failure cleanup. The only new steady-state performance mechanism is one awaited credential-binding IPC per cold signed-in hidden session; it is coalesced, reused for ten minutes, required before authenticated catalog use, and does not scale with queries, results, installations, or files. No high-confidence actionable performance regression or qualifying regression fix was found.
