- Scaling input: The effective cardinality is one customization anchor per ordered set of real-path-normalized working directories, not per turn or per chat when chats share that set. Multi-root discovery scales with the roots in that set.
- Effective concurrency: Discovery's SDK calls and filesystem work use Promise.all within one cold anchor. Session operations are generally session-queued; live references coalesce chats on the same anchor. No new unbounded limiter bypass was established.
- Cache behavior: Cold anchors resolve each file path once and initialize discovery once. Warm snapshots await settled promises and reuse cached real paths, parsed customization state, MCP root discovery, and watchers. Failed realpath resolutions are retried, but the single lookup per operation on a missing folder did not establish a meaningful regression on a viable chat workflow.
- Mechanism confidence: High confidence in the call path, cache keys, and boundary counts from the changed acquisition path and transitive discovery implementations.

### Scenario 2: Create peer chats in different folders or folder combinations

- Critical path: Each peer's first create/materialize/resume must acquire its own folder-set anchor and settle its SDK/filesystem customization discovery before constructing the peer SDK snapshot. Later sends reuse the live chat entry's anchor.
- Scaling input: Cost grows with the number of distinct simultaneously used ordered anchor sets after real-path normalization, not raw chat count. Multiple chats in the same folder set share one discovery. Different sets can overlap roots, but MCP root I/O/watchers are shared independently.
- Effective concurrency: Normal peer creation is session-queued. Independent fork queues can overlap cold anchors, but no evidence established a realistic unbounded burst; each anchor itself runs a fixed group of discovery operations.
- Cache behavior: Positive anchor entries are refcounted and shared by normalized key. Chats in the same folder set hit the warm anchor. Anchor state is dropped with the last user, so later reuse correctly performs a fresh scan rather than retaining stale watchers indefinitely. Symlink spellings are normalized before acquisition and live entries are rekeyed.
- Mechanism confidence: High confidence that boundary work scales with distinct anchors and that same-set chats coalesce, based on acquireAnchor refcounts, real-path keys, and tests asserting one discovery.
- Magnitude uncertainty: Sessions with many distinct folder combinations can perform more cold discovery than before, and exact SDK/filesystem duration is environment-dependent. However, this is the required work to produce distinct authoritative folder-scoped snapshots, is keyed by effective sets, and is released when unused; no redundant per-chat repetition was proven.

### Scenario 3: Move the default chat to another folder and publish the new customization view

- Critical path: The move transaction updates provider state and persisted metadata. Publishing the new view starts asynchronously via publishWhenSettled and is off the move's awaited critical path; the next send awaits the new anchor snapshot if discovery is still cold.
- Scaling input: One new cold anchor for the moved-to ordered folder set unless a peer already holds it. Repeated moves reuse any still-live matching anchor; otherwise released sets are rediscovered when legitimately revisited.
- Effective concurrency: The move is serialized by the existing working-directory transaction. Discovery internals parallelize fixed categories, while publication waits on the single effective anchor.
- Cache behavior: Reanchor clears only the published reference. If another chat holds the destination anchor, publication and relaunch share its settled discovery. The old anchor remains only while another live chat needs it and otherwise disposes.
- Mechanism confidence: High confidence from the reanchor, refcount, and publishWhenSettled paths.
- Magnitude uncertainty: Destination discovery latency varies by filesystem and customization volume, but it occurs once per effective destination and can be reused from a peer.
- Expensive boundaries:

- Verdict: No reportable regression. The destination scan is necessary for the requested published view, is off the immediate move critical path, and coalesces with an existing peer anchor.

### Scenario 4: Use a published default-chat custom agent from a peer whose own folder does not contain it

- Critical path: Snapshot construction first settles the peer anchor. If the selected agent is absent, it also reads the published anchor's applied plugins before SDK launch/restart can proceed.
- Scaling input: The fallback adds at most one published-anchor lookup per snapshot requiring cross-anchor agent fallback, independent of total chats. Plugin projection scales with the customization lists in the peer and published anchors.
- Effective concurrency: The published lookup awaits the same shared anchor promise; concurrent users coalesce discovery rather than launch separate scans.
- Cache behavior: The published anchor is refcounted and normally already warm because it supplies the session's picker. If cold, one discovery initializes it for all users. Only the selected agent is appended; no additional retained anchor is created beyond the published reference.
- Mechanism confidence: High confidence in the fallback call flow, but low evidence of meaningful repeated cost because the published anchor and its settled promise are shared.
- Magnitude uncertainty: A cold published anchor during fallback is uncommon because the picker view generally initializes it first; customization-list sizes vary.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:8727-8730</code>: Settle Copilot customization discovery for the published anchor if it has never been read.; cardinality: Zero boundary calls when the published picker anchor is warm; otherwise one cold anchor discovery shared session-wide.
    - Introduced by diff: true; previous behavior: The peer used the session-wide snapshot directly, so no second anchor lookup was needed.; critical-path effect: A peer launch/restart selecting the fallback agent waits for the published snapshot.
- Verdict: No finding. The fallback lookup is bounded to one shared anchor and is required to resolve an agent exposed by the picker.

### Scenario 5: Dispose peers, replace runtimes, or finalize a session

- Critical path: Disposal releases the chat's anchor reference; replacement acquires the next entry before releasing the previous one so a shared discovery is not torn down mid-restart. Session finalization disposes every remaining anchor and watcher.
- Scaling input: Cleanup is linear in live effective anchor sets and their owned discovery objects. The real-path map is session-scoped and dies with the controller.
- Effective concurrency: Reference release is synchronous. Restart paths hold a temporary reference across destruction/creation, preventing rediscovery races; final disposal iterates anchors once.
- Cache behavior: Anchors are removed at refcount zero, positive caches do not outlive their last chat except the published reference, and controller disposal clears all remaining anchors. MCP root discoveries have their own refcounts and release watchers at zero.
- Mechanism confidence: High confidence from explicit reference ownership, replacement ordering, and finalizer code.
- Magnitude uncertainty: Watcher-disposal implementation cost depends on the file provider, but live anchor count is bounded by active folder sets and cleanup has no evidenced expensive asynchronous boundary.
- Expensive boundaries:
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:8427-8459 and src/vs/platform/agentHost/node/shared/sessionMcpDiscovery.ts:84-108</code>: Dispose customization and MCP filesystem watchers owned by released anchors/roots.; cardinality: Once per anchor/root when its last reference is released; once for each remaining live anchor at session finalization.
    - Introduced by diff: true; previous behavior: One session discovery was disposed; the PR adds multiple refcounted anchors but also explicit last-user and final-session cleanup.; critical-path effect: Synchronous cleanup is proportional to live anchors but contains no scans or remote calls.
- Verdict: No cleanup-lifecycle finding. The diff retains handles through replacement and deterministically releases every discovery/watch set.
