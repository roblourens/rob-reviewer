# Performance review: agentHost: per-chat configuration (Block 3b)

## Findings (2)

### 1. [medium] Evict failed chat-config entries with their session

**Finding ID:** `PERF-D2A5E847C5E6`  
**Location:** <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:5686</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Retained backend chat keys and SessionState.chats catalog arrays  
**Scaling:** Each failed chat-state subscription inserts another entry keyed by backend chat and retains that session's full chats array; entries accumulate with distinct failed chats/sessions over the provider's lifetime until the entire connection is replaced.  
**Outcome:** Unbounded retained memory in long-lived windows that encounter subscription failures across many chats or sessions.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** There was no failed per-chat configuration cache, so failed chat subscriptions could not retain catalog arrays after sessions were removed.  
**Changed behavior:** The new error handler stores the backend chat and current catalog in \_failedChatConfigs, but successful session removal/list eviction only clears session state/config structures; this map is cleared only on a later retry caused by a changed catalog or when a new connection is attached.  
**Confidence:** 0.98 — The insertion and all map deletion/clear sites are directly enumerated, and session removal is traced to omit this map. Failure prevalence affects severity, but retained reachability and lifetime are deterministic once the error path occurs.

**Causal diff evidence:** Added line 5686 inserts every failed backend chat into the new \_failedChatConfigs map, while the PR's session-removal paths do not delete corresponding entries.

Transient failures for chats that are subsequently closed or whose sessions are deleted leave their catalog arrays reachable indefinitely. Repeating this across sessions steadily grows provider memory until reconnect/reload.

**Evidence:** The added onDidError path sets \_failedChatConfigs at line 5686 and immediately disposes the subscription. Search shows deletion only when \_keepChatConfigAlive observes a different catalog, plus a whole-map clear in \_attachConnectionListeners. \_removeSessionState deletes \_lastSessionStates and all existing session subscription/config maps but never removes failed chat-config entries, so there is no session-lifecycle cleanup for this cache.

**Suggested direction:** Track failed entries by session (or store the session ID with each entry) and remove all of that session's failures from both authoritative-list eviction and \_removeSessionState; also clear an entry when its chat disappears from a catalog.

### 2. [medium] Batch chat config into the existing hydration read

**Finding ID:** `PERF-0C19ABE939C4`  
**Location:** <code>src/vs/platform/agentHost/node/chatContributions/chatConfig/chatConfigContribution.ts:50</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SQLite database metadata queries and database reference opens  
**Scaling:** Adds one awaited chat-database metadata read for every restored catalog chat; AgentService hydrates all peer chats before registering the catalog, and AgentHostChatRowStore routes each read through the session-wide runExclusive sequencer, so effective concurrency is one and latency grows linearly with chat count.  
**Outcome:** Increased session restore and catalog-opening latency, especially for long-lived sessions with many peer chats or slower storage.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Catalog hydration already restored title/draft data, but did not query agentHost.chatConfigValues. A session with N peer chats therefore avoided these N additional metadata queries.  
**Changed behavior:** The new contribution awaits getChatConfig during every chat's eager onHydrateChat pass, before the restored chat catalog can be registered.  
**Confidence:** 0.96 — The changed call, per-chat catalog loop, awaited critical path, SQLite metadata operation, and session-wide sequencer are all directly traced in repository code. Storage speed and typical catalog size affect magnitude, but not the linear added boundary cost.

**Causal diff evidence:** Added line 50 awaits this.\_sessionStateStore.chatRows.getChatConfig(...) in the eager per-chat hydration hook; no corresponding config metadata read existed before the PR.

Opening a session with a large chat catalog now waits for an additional serialized SQLite metadata lookup per chat. The repository's hydration tests exercise 100 peer chats, so this is a realistic linear critical-path cost rather than a single-chat micro-optimization.

**Evidence:** AgentService.\_restorePeerChatsFromCatalog awaits Promise.all of hydrateChat for every catalog entry before registerRestoredChatSummary. This added line calls AgentHostChatRowStore.getChatConfig; \_read opens/leases the chat database, runs getMetadata, and is wrapped by \_runExclusive(session), which serializes all peer reads despite the outer Promise.all. The immediately preceding ChatDraftContribution already performs a row-store database read for the same chat, so config can be fetched in that existing lease rather than adding another boundary crossing.

**Suggested direction:** Extend the existing chat-row hydration/read used for drafts to return draft and config from one database lease/query batch (or prefetch config with the existing session-state load), while preserving per-chat ownership validation.
