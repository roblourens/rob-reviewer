# Performance review: Shard Windows tests as they're too slow to run 20x in one job

[PR #341719](https://github.com/microsoft/vscode/pull/341719) at `b21b32ae253971fb5a191e7f97e3096c9f816536`

## Findings (1)

### 1. [low] Skip empty shards for shortened debug runs

**Finding ID:** `PERF-0A41D8AA5BC3`  
**Location:** <code>build/azure-pipelines/win32/product-smoke-flaky-win32.yml:108</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** one extra Windows agent job, three pipeline-artifact downloads, three archive extractions, one Key Vault call, and one Electron/Playwright setup invocation per short run whose iterations occupy only one parity  
**Scaling:** The redundant cost is one full integration-job setup whenever the supplied iteration set contains only odd or only even values; it dominates the intended work as the manual iteration count shrinks, reaching a 2:1 job/setup fan-out for a single test iteration.  
**Outcome:** excessive I/O and reduced shared CI throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous integration path always instantiated one job, so a shortened one-iteration debugging run downloaded and extracted each of the three artifacts and initialized the toolchain exactly once before running that test.  
**Changed behavior:** Every enabled Windows integration invocation now creates two jobs before considering which iteration values belong to either shard. The common template therefore runs both jobs' setup even when one shard receives no test step.  
**Confidence:** 0.99 — The top-level parameter comment explicitly supports shortening \`iterations\` for manual debugging, and the default shard list, parity predicate placement, and common-template boundaries are all statically visible. For \`\[1\]\`, the odd job has one test and the even job has none, but both instantiate all setup tasks. Exact artifact sizes and wall-clock duration are unknown, affecting severity rather than the mechanism.

**Causal diff evidence:** Added line 108 wraps the integration test-job template in a fixed \`each shard in parameters.integrationShards\` loop whose default is \`\[odd, even\]\`; the parity condition is applied only inside \`testSteps\`, after both jobs have already executed common setup.

A one-iteration Windows integration debugging run allocates a second Windows agent and repeats all artifact, filesystem, secret-service, and tool-download setup for a job that runs no tests. This creates avoidable network/filesystem I/O and consumes shared CI capacity; the stage must also wait for that empty shard job to finish.

**Evidence:** \`product-smoke-flaky.yml\` documents that \`iterations\` may be shortened for manual debugging. With a realistic value such as \`\[1\]\`, line 108 still expands both \`odd\` and \`even\` jobs; only line 143 filters test steps. Before reaching that filter, each common test job downloads the repo, app, and server pipeline artifacts, extracts all three archives, selects Node, calls Azure Key Vault, and runs the Electron/Playwright download command. Thus the one-test scenario now performs six artifact downloads and two complete setup sequences instead of three downloads and one setup sequence, while the even shard executes no test.

**Suggested direction:** Keep the two shards for the default long run, but use the original single-job path for short iteration lists (for example, up to the per-job capacity) or derive/condition the shard jobs so a parity with no assigned iterations is not instantiated.


## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `build/azure-pipelines/win32/product-smoke-flaky-win32.yml:108` (`RIGHT`)  
**Blamed base line:** `build/azure-pipelines/win32/product-smoke-flaky-win32.yml:128`  
**Introducing path:** `build/azure-pipelines/win32/product-smoke-flaky-win32.yml`  
**Introducing commit:** `9f57500448ddef1b880e62c93b2832936a3142f6`  
**Mechanism family:** `repeated-work`  
**Performance category:** `latency`  
**Confidence:** 0.98

**Mechanism:** Twenty intentionally repeated, subprocess-heavy Windows integration runs were serialized in one Azure job, so aggregate duration scaled linearly past the fixed 300-minute job deadline.

**Symptom:** The default Windows integration job could not finish its 20 iterations before Azure's 300-minute timeout, truncating scheduled flaky-test runs.

**Fixed behavior:** The change partitions the 20 Windows integration invocations into odd and even jobs that run concurrently after the shared build, reducing the integration critical path from roughly 400–480 minutes to roughly 200–240 minutes plus setup and keeping each shard within its explicit 360-minute job timeout.

**Evidence:** The base template placed every value from the top-level default 20-entry `iterations` list into one Windows integration job (`each i in parameters.iterations` at base line 128). Each iteration invokes `scripts/test-integration.bat`, and the changed comments document ~20–24 minutes per Windows iteration while the common job timeout was 300 minutes. Thus the scheduled twice-daily default path required roughly 400–480 serial minutes in a job capped at 300 minutes. The added shard loop at line 108 creates exactly two jobs and the parity predicate assigns each default iteration to one of them, preserving 20 test invocations while reducing each job to 10 serial invocations.

- Scaling input: Manual \`iterations\` values containing only one parity, especially the documented shortened one-iteration debugging case. Redundant setup is fixed at one full job and becomes proportionally larger as requested test count approaches one.
- Effective concurrency: Two jobs are instantiated even though effective test cardinality is one and only one parity has work. There is no conditional suppression of the empty shard; actual simultaneous execution depends on Azure pool availability.
- Cache behavior: The two shard jobs have isolated workspaces. An empty shard still cannot reuse the active shard's artifact files or local tool setup, and no condition prevents its common-template steps.
