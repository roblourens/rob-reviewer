## Findings (1)

### 1. [low] Keep the repository scope cache across picker invocations

**Finding ID:** `PERF-0C9D0BE28B3C`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxRepositoryPicker.ts:53</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** Two GitHub REST requests (\`GET /user\` and \`GET /user/orgs\`) and their response parsing per reopened picker  
**Scaling:** The extra work grows as two wire requests for every picker invocation in which the user types a non-empty query, even when invocations occur seconds apart; queries within one invocation share the promise.  
**Outcome:** Increased interactive search latency and repeated GitHub API/network traffic  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The extension-backed \`BaseOctoKitService\` cached the computed \`user:&lt;login&gt; org:&lt;org&gt;...\` scope by token for five minutes, so reopening the picker and searching during that window issued only the repository search request.  
**Changed behavior:** The replacement declares \`scope\` inside \`pick()\`, so dismissing or completing the picker discards it. The first typed query after every reopen calls \`\_resolveSearchScope\`, which waits for \`/user\` and \`/user/orgs\` before it can issue the repository search.  
**Confidence:** 0.97 — The cache ownership and REST call path are explicit, and the previous five-minute token-keyed cache is present in the replaced extension implementation. The only magnitude uncertainty is how often users reopen and search the picker; the two added critical-path requests per reopen are deterministic.

**Causal diff evidence:** The added \`let scope: Promise&lt;string&gt; \| undefined;\` is local to \`pick()\`, replacing the prior service-level \`\_cachedUserReposScope\` with five-minute lifetime; therefore every new call to \`pick()\` starts with an empty scope cache.

If a user cancels or completes the repository picker and reopens it to try another search, the first result is now delayed by two additional GitHub REST round trips. ETags can reduce response bytes but still require both requests and responses on the critical path.

**Evidence:** Line 53 creates the scope promise with per-\`pick()\` lifetime, line 54 populates it through \`\_resolveSearchScope\`, and lines 91-94 perform the two parallel REST calls. The replaced implementation in \`BaseOctoKitService.\_getUserReposSearchScope\` retained the same qualifiers by token for a five-minute TTL. The new test covers only one picker invocation and confirms the sequence list -&gt; \`/user\` + \`/user/orgs\` -&gt; search, so it does not preserve the previous warm-reopen behavior.

**Suggested direction:** Retain the resolved scope across picker invocations, keyed to the acquired client/account with a bounded TTL, and invalidate it when the default client/credential changes. Keep the per-pick promise coalescing and cancellation semantics for in-flight resolution.


## Performance regression fixes detected (1)

### 1. concurrency-burst

**Fix location:** `src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxRepositoryPicker.ts:61` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/remoteAgentHost/editorCloudSandboxContribution.ts:300`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/remoteAgentHost/editorCloudSandboxContribution.ts`  
**Introducing commit:** `65b5fd7256a49fba9a5b95c436c2556b1d60580a`  
**Mechanism family:** `concurrency-burst`  
**Performance category:** `network`  
**Confidence:** 0.96

**Mechanism:** The old contribution entered an extension-backed picker whose repository callback ignored `RepositoryPicker`'s request cancellation token; after each 300 ms pause, a new extension-host command and GitHub request could start while superseded searches continued.

**Symptom:** Typing successive repository terms could leave stale GitHub searches running concurrently, consuming API/network capacity and delaying the latest interactive result.

**Fixed behavior:** The new callback creates a request AbortController, aborts it when the shared picker cancels a superseded request, and passes the combined signal through `_searchRepositories` to the GitHub transport, which removes/cancels requests with no remaining waiter.

**Evidence:** Base line 300 called `github.copilot.chat.cloudSessions.openRepository`; that extension invoked `_chat.pickRepository`, whose command callback accepted only `query` and executed the extension search command without forwarding the request token. Added lines 58-61 now connect `requestToken.onCancellationRequested` to an AbortController and pass its signal into all repository REST/query calls. The shared picker clears the prior request token on every value change and before each update.

### Scenario 2: Type a non-empty repository search during one picker invocation

- Critical path: After the shared 300 ms debounce, the first non-empty search waits for viewer and organization scope, then issues the repository search; later searches in the same invocation reuse the scope promise and wait only for their search request.
- Scaling input: One effective query per 300 ms pause, one result page capped at 100 repositories, and up to 100 organization qualifiers. Superseded requests are canceled.
- Effective concurrency: The two first-use scope requests run in parallel and are bounded by the transport host concurrency of 2; the search runs after both. Only the latest debounced repository query remains attached because value changes cancel the prior request token.
- Cache behavior: Scope is promise-coalesced only within the current picker. \`/user\`, \`/user/orgs\`, and search responses use ETags in the transport; repeated identical URLs revalidate over the network. Distinct query URLs occupy bounded LRU entries.
- Mechanism confidence: High: debounce, cancellation signal propagation, promise reuse, REST cardinality, and transport concurrency were inspected.
- Magnitude uncertainty: Exact search RTT and typing pause patterns vary, but the first-use 2+1 request chain and later one-request chain are explicit.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxRepositoryPicker.ts:91 \_resolveSearchScope</code>: Fetch viewer login and first 100 organizations in parallel; cardinality: Two requests on the first non-empty query in a picker invocation; zero for subsequent queries in that same invocation after successful resolution.
    - Introduced by diff: false; previous behavior: The old extension implementation performed the same two calls on a cold scope cache, but retained the resulting scope by token for five minutes across picker invocations.; critical-path effect: Both responses must complete before the first repository search can be sent.
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxRepositoryPicker.ts:85 \_searchRepositories</code>: Search \`/search/repositories\` with term, viewer/org qualifiers, sort, and 100-item page; cardinality: One request for each query that survives the 300 ms debounce; superseded in-flight requests are aborted.
    - Introduced by diff: false; previous behavior: The old extension issued an equivalent GitHub search for each debounced query, but the renderer-to-extension callback could not propagate cancellation.; critical-path effect: The matching item list remains busy until the latest search completes.
- Verdict: Within one invocation, request coalescing and cancellation are bounded and improve on the old path; no additional finding beyond the cross-invocation cache issue.

### Scenario 3: Dismiss or complete the picker, reopen it, and type another search within five minutes

- Critical path: Every reopened pick creates a fresh local scope promise. The first typed query therefore blocks on \`/user\` and \`/user/orgs\` before the repository search, even if the same account's scope was resolved moments earlier.
- Scaling input: Each reopen followed by a non-empty query adds exactly two scope REST calls; cost grows linearly with picker reopen count, not repository result count.
- Effective concurrency: The two scope requests run concurrently with each other but the search is serialized behind both. Separate picker invocations are serialized by \`\_currentPick\`, so the issue is repeated work rather than an unbounded concurrent burst.
- Cache behavior: The new cache lifetime ends with each \`pick()\` call. Transport ETags reduce warm response bytes but still require two wire round trips. Previously, the token-keyed scope remained warm for five minutes across picker invocations.
- Mechanism confidence: High: the cache variable is lexically scoped to \`pick()\`, cleanup disposes each pick, the two REST calls are explicit, and the prior five-minute cache is explicit.
- Magnitude uncertainty: Users commonly may select only once, so prevalence and aggregate traffic are uncertain; the deterministic two-request latency penalty on every warm reopen supports low severity.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxRepositoryPicker.ts:53 pick</code>: Re-fetch viewer and organizations for a scope already resolved by a prior picker; cardinality: Two additional requests per reopen with a typed query; for N reopened searches, 2N scope requests rather than two total during the prior five-minute TTL.
    - Introduced by diff: true; previous behavior: \`BaseOctoKitService.\_cachedUserReposScope\` cached by token for five minutes, making warm reopened searches issue only the search request.; critical-path effect: Both requests delay each reopened picker’s first typed result before the actual search can start.
- Verdict: Reportable low-severity cache-lifecycle regression; submitted as a finding.

### Scenario 4: Continue typing or dismiss while a repository search is in flight

- Critical path: A new value immediately clears the current request token; dismissal disposes the pick. The request-specific AbortController propagates this cancellation through the query/transport path so stale work is not required for the latest result.
- Scaling input: Potentially one request per query surviving the debounce, but superseded requests detach/cancel instead of accumulating with the number of pauses.
- Effective concurrency: The shared picker has one current request token, and the transport has bounded global/host/caller queues. Scope performs at most two parallel requests; stale operations with no waiter are aborted.
- Cache behavior: Successful scope resolution is reused for the rest of the current pick. A canceled scope resolution clears its promise so a later query retries; this avoids retaining a rejected promise.
- Mechanism confidence: High: the request-token clearing, listener, AbortController, transport cancellation, and old command callback were all traced.
- Magnitude uncertainty: Overlap depended on users pausing at least 300 ms between edits and on request latency, but the old inability and new ability to cancel are directly established.
- Expensive boundaries:
  - IPC at <code>base src/vs/workbench/contrib/chat/browser/remoteAgentHost/editorCloudSandboxContribution.ts:300</code>: Renderer/extension command round trips for opening and each repository query; cardinality: Previously one opening round trip plus one search command round trip per debounced query; removed from the changed cloud sandbox path.
    - Introduced by diff: false; previous behavior: This was the base behavior removed by the diff.; critical-path effect: Previously added serialization latency and prevented the renderer request token from reaching the extension’s network request; now absent.
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxRepositoryPicker.ts:61 pick</code>: Abort superseded GitHub list/search/scope requests through a combined AbortSignal; cardinality: At most the latest debounced query remains active for this picker, aside from bounded scope subrequests.
    - Introduced by diff: true; previous behavior: The old \`\_chat.pickRepository\` command callback ignored its request token when invoking the extension search command, so superseded GitHub requests could continue.; critical-path effect: Stale searches no longer consume network/queue capacity needed by the latest result.
- Verdict: This is a concrete performance regression fix, recorded with the introducing commit; it is not a review finding against this PR.
