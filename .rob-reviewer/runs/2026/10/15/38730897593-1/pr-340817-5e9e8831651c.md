# Performance review: chat: allow cloud sandbox creation from the editor window

[PR #340817](https://github.com/microsoft/vscode/pull/340817) at `5e9e8831651ca660fb7f61af35362d15a677a202`

## Findings (1)

### 1. [medium] Resolve the draft configuration only once

**Finding ID:** `PERF-5CF6FC6A4F4E`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/editorCloudSandboxContribution.ts:411</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Remote Agent Host resolveSessionConfig request/response round trips  
**Scaling:** The cost adds one serialized remote round trip for every cloud sandbox first send; N sandbox creations issue 2N configuration resolutions instead of N.  
**Outcome:** increased first-send latency on the provisioning critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The normal AgentHostSessionHandler creation path resolves a non-empty initial configuration once, immediately before createSession. The editor had no separate preflight resolution on that path.  
**Changed behavior:** Every Cloud draft is initialized with default mode and approval options, so draftConfig is normally non-empty. This added line awaits connection.resolveSessionConfig and stores the values; the added resolveInitialSessionConfig hook then supplies the same values to AgentHostSessionHandler, whose \_createAndSubscribe path awaits connection.resolveSessionConfig again before createSession.  
**Confidence:** 0.99 — The default-option initialization, both resolveSessionConfig call sites, and their sequential first-send call flow are directly visible in the repository. Exact network duration is environment-dependent, which affects severity but not the duplicated boundary mechanism.

**Causal diff evidence:** RIGHT line 411 adds the first awaited remote resolution; the PR also adds resolveInitialSessionConfig forwarding, which feeds those same values into the existing AgentHostSessionHandler resolution path.

Sending the first prompt to a new Cloud sandbox waits for two sequential remote configuration RPCs after the sandbox connects, adding a full host round trip to an already long setup path for every creation.

**Evidence:** ChatSessionsService initializes each option group to its selected/default item, and createCloudSandboxDraftOptionGroups always supplies mode and approval defaults. readCloudSandboxDraftConfig therefore returns a non-empty object for ordinary drafts. Line 411 awaits resolveCloudSandboxSessionConfig, which calls connection.resolveSessionConfig. The result is saved in CloudSandboxSessionListController; CloudSandboxSessionContribution exposes it through resolveInitialSessionConfig; AgentHostSessionHandler merges it into initialConfig and \_createAndSubscribe independently awaits this.\_config.connection.resolveSessionConfig before createSession. These awaits are serialized on the first-send critical path and use the same draft mode/approval values.

**Suggested direction:** Perform the strict “host did not change the draft picks” comparison at AgentHostSessionHandler's existing resolveSessionConfig step (for example via a validation hook), and remove this preflight call so the authoritative resolution with the prepared working directory serves both validation and creation.
