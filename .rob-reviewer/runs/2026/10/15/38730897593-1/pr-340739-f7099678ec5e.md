# Performance review: Adding shrink empty lines feature

[PR #340739](https://github.com/microsoft/vscode/pull/340739) at `f7099678ec5eed55b14e4521484074f6cc71bcf4`

## Findings (1)

### 1. [medium] Avoid rebuilding every empty-line decoration on each fold change

**Finding ID:** `PERF-6B42E7603871`  
**Location:** <code>src/vs/editor/contrib/shrinkEmptyLines/browser/shrinkEmptyLines.ts:44</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Main-thread CPU work, model-decoration mutations, and temporary decoration objects  
**Scaling:** For N model lines and H merged hidden ranges, each fold/unfold synchronously scans all N lines and the per-line hiddenAreas.some check performs up to H tests, making the added work O(N\*H), plus O(B) decoration replacement for B whitespace-only lines. Ordinary edits similarly pay O(C\*H) for C changed lines.  
**Outcome:** Increased input/folding latency and dropped frames while folding or editing large structured files with many collapsed regions  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, hidden-area changes did not trigger a second full-document content scan or wholesale replacement of empty-line line-height decorations; folding only performed the editor's existing hidden-range update.  
**Changed behavior:** The added onDidChangeHiddenAreas listener synchronously calls \_updateAllDecorations. That method passes the entire model to \_getDecorations, which trims every line, runs hiddenAreas.some for every line, and replaces all tracked decorations even when one fold changed.  
**Confidence:** 0.98 — The synchronous call path, full-model range, nested N-by-H membership test, and wholesale deltaDecorations call are explicit in the changed code and existing folding/view-model implementation. The exact pause duration depends on file size and enabled setting, which is reflected in medium severity, but the scaling mechanism and UI critical-path reachability are direct.

**Causal diff evidence:** Added line 44 registers \`this.editor.onDidChangeHiddenAreas(() =&gt; this.\_updateAllDecorations())\`, newly placing the controller's whole-model scan and decoration replacement on every fold/unfold event.

With shrinkEmptyLines enabled, toggling a fold in a large file (for example, tens of thousands of lines with hundreds or thousands of collapsed regions) can block the UI while the controller rechecks the entire file and churns every blank-line decoration. Typing also scans the complete hidden-range list for each changed line.

**Evidence:** The new listener at line 44 directly invokes \_updateAllDecorations on every HiddenAreasChanged event. \_updateAllDecorations constructs range 1..model.getLineCount(), and \_getDecorations nests its line loop with hiddenAreas.some before calling trim/getLineContent. Hidden ranges are normalized into sorted, non-overlapping ranges by viewModelLines.normalizeLineRanges, so H can remain large and the current search does not exploit that ordering. FoldingController.onHiddenRangesChanges synchronously calls editor.setHiddenAreas, which emits HiddenAreasChanged, placing this work on the fold interaction path. Decoration replacement also emits per-line line-height changes into the view layout.

**Suggested direction:** Track the previous normalized hidden ranges and update only lines whose visibility changed. For full rebuilds, traverse the sorted hidden ranges with a monotonic index (and use binary search for isolated edited lines) rather than calling some for every line; preserve existing decorations outside affected ranges.

### Scenario 2: Type, paste, multi-cursor edit, undo, or redo while shrinking is enabled

- Critical path: onDidChangeModelContent synchronously maps changed ranges, queries old decorations, checks each affected line against hidden ranges, and mutates decorations before the content event path completes.
- Scaling input: Changed lines C after event mapping, merged hidden ranges H, and model decorations intersecting those changed ranges; hidden membership scales as C\*H without deduplication/coalescing of overlapping changed ranges.
- Effective concurrency: Synchronous serial work on each model-content event; no debounce or coalescing across rapid input events.
- Cache behavior: Decoration IDs are retained, but line emptiness and hidden membership are recomputed for every event. There is no negative/positive classification cache.
- Mechanism confidence: High: the event listener and loops are direct. Common single-line edits usually keep the cost modest, while files with many hidden ranges amplify it.
- Magnitude uncertainty: Typical typing changes one line, so impact depends primarily on how many regions are concurrently hidden; bulk edits increase C.
- Expensive boundaries: none found
- Verdict: The per-edit H scan is part of the same reported hidden-range lookup issue; no separate finding was submitted to avoid duplicate comments.

### Scenario 3: Fold or unfold regions while shrinking is enabled

- Critical path: Folding synchronously calls editor.setHiddenAreas, emits onDidChangeHiddenAreas, and the new listener immediately runs \_updateAllDecorations before the interaction can render.
- Scaling input: N total lines, H normalized disjoint hidden ranges, and B whitespace-only lines. A single fold toggle adds an O(N\*H) membership scan and O(B) decoration replacement.
- Effective concurrency: Synchronous main-thread execution with no deferment, incremental visibility diff, cancellation, batching, or coalescing.
- Cache behavior: Previous empty-line classification and decorations are discarded/reprocessed wholesale. Warm cache state does not reduce work, and each fold event repeats it.
- Mechanism confidence: Very high: the folding-to-hidden-event path, whole-model range, nested hidden-area search, and decoration mutation are all established in repository code.
- Magnitude uncertainty: The largest pauses require both the feature and large/fold-heavy files; precise duration is environment-dependent, supporting medium severity rather than uncertainty in the mechanism.
- Expensive boundaries: none found
- Verdict: Reportable introduced regression; submitted a finding anchored to the added hidden-area listener.

- Critical path: LineNumbersOverlay.prepareRender now calls getLineHeightForLineNumber and conditionally appends a font-size style for each visible line before overlay HTML is emitted.
- Scaling input: Visible viewport line count V and number of custom-height lines B; each lookup is a binary search over custom lines, so added work is O(V log B), bounded by the viewport.

- Cache behavior: The line-height manager maintains ordered custom-line data and commits pending changes once; line-number HTML is regenerated under the existing overlay render lifecycle.
- Mechanism confidence: High for the added lookup, low that it creates material user-visible regression because cardinality is viewport-bounded and the operation is in-memory.
