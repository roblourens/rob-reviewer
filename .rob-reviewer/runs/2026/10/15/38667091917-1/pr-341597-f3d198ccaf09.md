# Performance review: Canvases: UI for opening Canvases from Editor Window

[PR #341597](https://github.com/microsoft/vscode/pull/341597) at `f3d198ccaf09f0b9d576a29989f622538b629ec4`

## Findings (1)

### 1. [medium] Defer canvas discovery until the restored chat runtime is needed

**Finding ID:** `PERF-DCEB5F9F68B6`  
**Location:** <code>src/vs/workbench/contrib/canvases/browser/editorCanvasActions.ts:194</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Agent SDK runtime/session initialization, control-plane RPCs, filesystem/network I/O, CPU, and retained process/session memory  
**Scaling:** Cost grows with the number of distinct historical chats selected or restored while canvases are enabled; the delayer coalesces bursts but cannot cancel an already-started runtime materialization, so each settled selection can resume another chat.  
**Outcome:** Unnecessary startup/background latency, CPU and I/O contention, and additional retained runtime memory  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this contribution, opening or restoring an editor-window chat hydrated its persisted session/chat state but did not request the registered canvas inventory or materialize a live Copilot chat runtime for menu data.  
**Changed behavior:** The new BlockRestore contribution automatically invokes definitionProvider.listCanvases as soon as an initialized Chat view model becomes active, without waiting for the New Chat/Canvas menu to be opened.  
**Confidence:** 0.98 — The added call, renderer/agent-host boundary, live-session materialization branch, and two downstream SDK RPCs are explicit in the traced code. The exact wall-clock cost varies by runtime and extension setup, which is reflected in medium severity rather than lower mechanism confidence.

**Causal diff evidence:** Added line 194 executes definitionProvider.listCanvases from the autorun scheduled at lines 87-113 whenever the active Chat view exposes a definition provider; the call is not conditioned on menu visibility or explicit canvas interaction.

Restoring or selecting an idle historical Copilot chat can start/resume its agent SDK runtime and issue two control-plane RPCs merely to populate a submenu the user may never open, adding background startup CPU, filesystem/network I/O, and resident runtime memory; switching among historical chats can repeat that work for each selected chat.

**Evidence:** AgentHostCanvasCollection wires listCanvases to connection.listSessionCanvases. That crosses the renderer-to-agent-host boundary (localAgentHostService -&gt; agentHostManagementService), where AgentService.listSessionCanvases calls \_restoreSessionChat and the Copilot provider's \_resolveSessionCanvasChat. When no live target exists, \_resolveSessionCanvasChat calls \_ensureResolvedChatSession, whose documented purpose is resolving a live session and whose restore path calls \_resumeSession. CopilotAgentSession initialization launches the SDK session and performs customization/MCP initialization, sandbox diagnostics, canvas-extension readiness, shell setup, and usage refresh; listCanvases then performs both rpc.canvas.list and rpc.extensions.list. Persisted Chat view hydration itself uses state-manager resolveChatState, so a historical initialized chat can have canvasContext while its SDK runtime is still lazy.

**Suggested direction:** Keep persisted/restored chats lazy: do not call listCanvases solely when canvasContext appears. Defer inventory discovery to explicit Canvas-menu interaction, or gate it on an already-live chat/runtime signal so first-message live chats still populate without resuming idle historical sessions.


## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:837` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:834`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts`  
**Introducing commit:** `bfa6dc95023e589f8bd93ab2b64b169d95e9ec98`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.96

**Mechanism:** The old fallback created a fresh empty canvas-reference array whenever the immutable chat state changed. Streaming ChatDelta actions therefore invalidated the mapped canvas observables even when the chat had no canvases.

**Symptom:** Agent response streaming caused avoidable per-delta canvas-array allocation, observable propagation, and CanvasService reconciliation, adding CPU and GC pressure.

**Fixed behavior:** The module-level emptyCanvasReferences fallback preserves reference equality while canvases are absent, preventing the canvas observable chain from rerunning for each streamed chat delta.

**Evidence:** ChatDelta immutably returns a new ChatState; every reconciliation fires subscription onDidChange; observableFromSubscription feeds presentationChat; mapObservableArrayCached allocates a new output array when the references input changes; and CanvasService observes context.canvases in its reconciliation autorun. The changed fallback at line 837 removes that per-delta invalidation. blame\_base\_line attributes the old line to bfa6dc95023e589f8bd93ab2b64b169d95e9ec98.
