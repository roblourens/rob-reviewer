### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/canvases/browser/editorCanvasActions.ts:77` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/canvases/browser/editorCanvasActions.ts:77`  
**Introducing path:** `src/vs/workbench/contrib/canvases/browser/editorCanvasActions.ts`  
**Introducing commit:** `b02a600a10a79b536aabb6696d6fac458eeff3b4`  
**Mechanism family:** `repeated-work`  
**Performance category:** `rendering`  
**Confidence:** 0.97

**Mechanism:** Every canvas membership publication or subscription snapshot that returned content-identical definitions produced a fresh array, invalidated the observable, rescanned the full definitions/targets collections, and replaced the Canvas submenu registration, causing redundant MenuRegistry notifications and observer rebuilds.

**Symptom:** Unchanged canvas refreshes caused avoidable menu refresh notifications and synchronous collection-wide menu reconciliation in the renderer.

**Fixed behavior:** The changed observable uses structuralEquals, so an unchanged flat definition catalog is rejected at set time. The catalog RPC still occurs, but collection-wide menu reconciliation, submenu disposal/recreation, MenuRegistry notifications, and dependent menu rebuilds are skipped unless catalog content changes.

**Evidence:** The base observable used strict reference equality, while loadAvailableDefinitions always creates a fresh filtered/sorted array after listCanvases. Canvas definition notifications are emitted for ChatCanvasesChanged actions and snapshots, so an unchanged catalog still reran the definitions/targets autorun. That autorun scans all definitions and targets and always replaces submenuRegistration; MutableDisposable disposes the old MenuRegistry item and appends a new one, and both operations fire MenuRegistry change events that schedule menu refreshes. The added test explicitly fires an unchanged definition refresh and proves the submenu object is now retained.
