# Performance review: chat: enforce strict marketplaces only from managed settings

[PR #341663](https://github.com/microsoft/vscode/pull/341663) at `5505434c397812fb17164b1ab466bc35ab07c1e9`

## Findings (1)

### 1. [low] Cache the decoded strict-marketplace allowlist

**Finding ID:** `PERF-A1FA6031897F`  
**Location:** <code>src/vs/workbench/contrib/chat/common/plugins/pluginMarketplaceService.ts:854</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** CPU work and temporary arrays/objects from JSON.parse and allowlist filtering  
**Scaling:** For N configured marketplaces and an M-entry managed allowlist, source construction invokes this decoder roughly twice per marketplace (plus additional policy checks), so decoding/allocation grows O(N\*M) per catalog query; malformed JSON also throws and logs on every invocation.  
**Outcome:** Increased synchronous search/picker latency and avoidable GC pressure; malformed managed values additionally cause repeated exception and log I/O.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The deleted configuration-backed path called getStrictKnownMarketplaces on configurationService.getValue(ChatConfiguration.StrictMarketplaces), which supplied the already-decoded array from the typed array policy setting, so trust checks did not JSON.parse the whole managed payload.  
**Changed behavior:** The new \_getStrictMarketplaces reads the raw JSON string and parses and validates it on every isStrictMarketplacePolicyActive/isMarketplaceTrusted call.  
**Confidence:** 0.96 — The changed JSON.parse, all callers, per-reference filtering, and catalog query source reconstruction are directly traced. Exact milliseconds depend on enterprise allowlist and marketplace counts, so severity is low, but the repeated serialization/allocation mechanism and UI-path multiplicity are certain.

**Causal diff evidence:** RIGHT line 854 adds JSON.parse(value) inside \_getStrictMarketplaces, and the same diff changes both trust methods to call this helper instead of consuming the configuration service's decoded array.

Opening or searching the customization marketplace rebuilds sources: CustomizationMarketplaceWorkbenchService.sources and getService call getMarketplaceReferences, whose per-reference filter calls isStrictMarketplacePolicyActive and then isMarketplaceTrusted. With several configured marketplaces and a nontrivial enterprise allowlist, one debounced search repeatedly decodes the same payload many times on the UI path; an invalid native/server/file value also emits the warning repeatedly.

**Evidence:** CustomizationMarketplaceWorkbenchService.query reads this.sources, then getService rebuilds provider descriptors; both paths call getMarketplaceReferences. getMarketplaceReferences filters every configured reference through \_isMarketplaceAllowedByStrictPolicy, which calls isStrictMarketplacePolicyActive and, when active, isMarketplaceTrusted, and both call \_getStrictMarketplaces. The added JSON.parse therefore runs repeatedly for the same immutable managed value within one query. The managed-settings observable already identifies value changes, providing a natural invalidation point.

**Suggested direction:** Decode and validate the raw value once when strictMarketplaces changes (or memoize by raw string), cache the resulting allowlist, and log malformed JSON once per distinct value; have both policy/trust methods read that cached result.
