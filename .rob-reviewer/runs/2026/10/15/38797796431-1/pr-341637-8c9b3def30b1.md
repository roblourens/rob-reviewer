<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, missing-coalescing, synchronous-ui-work, boundary-fanout

### Scenario 1: Typing, editing, or receiving echoed input at a shell prompt with command detection active

- Critical path: Each xterm onData/onCursorMove/onWriteParsed event synchronously enters PromptInputModel.\_sync, scans the relevant local xterm buffer lines and cells, and emits onDidChangeInput only when value/cursor/ghost text changed. This scan must complete before prompt-model consumers observe the new state; asynchronous completion-provider results are downstream and not required for the model update itself.
- Scaling input: CPU work scales with the number and width of command lines between the command-start marker and cursor, visible rows below the cursor, and cells inspected for ghost text. Event frequency follows xterm write/cursor/data events, but duplicate triggers that produce identical state do not fan out onDidChangeInput.
- Effective concurrency: Buffer reconstruction and local listeners run synchronously and serially on the renderer/UI thread. Optional completion providers fan out asynchronously across enabled providers; a newer request cancels the prior token, although provider implementations determine how promptly cancellation stops boundary work.
- Cache behavior: There is no cache for buffer reconstruction. State comparison suppresses downstream events for unchanged results. Completion requests keep current prompt state and cancel the prior token; no new cache behavior is introduced.
- Mechanism confidence: High. The decorator implementation compares lastRun + 0 with Date.now using &lt;=, so every call runs immediately for equal or increasing timestamps. The removed wrapper only changes behavior after a backward wall-clock step.
- Magnitude uncertainty: Exact command length, row count, xterm event multiplicity, and enabled completion-provider count vary, but the before/after call cardinality is established for normal clocks: it is unchanged.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/terminal/common/capabilities/commandDetection/promptInputModel.ts:120-124 PromptInputModel constructor subscriptions</code>: Terminal process output/input is delivered through the existing pty/xterm pipeline and surfaces as parsed write, cursor, and data events.; cardinality: One or more local xterm events per pty write/input chunk; Event.any does not itself coalesce them, while unchanged reconstructed state suppresses downstream model-change events.
    - Introduced by diff: false; previous behavior: The same xterm events and pty boundary drove \_sync before the diff. With a nondecreasing clock, throttle(0) invoked \_sync immediately on every event, including multiple events in the same millisecond.; critical-path effect: The upstream pty delivery precedes the synchronous local model scan; no new IPC call is made by \_sync.
  - IPC at <code>src/vs/workbench/contrib/terminalContrib/suggest/browser/terminalSuggestAddon.ts:522 \_sync -&gt; terminalCompletionService.ts:136 provideCompletions</code>: When terminal suggestions are enabled and a prompt change meets quick-suggestion or trigger-character rules, enabled completion providers may be invoked, including extension-host providers.; cardinality: At most one request initiated by each effective prompt-state change, fan-out across enabled providers; duplicate xterm events with unchanged model state do not request completions, and newer requests cancel the prior token.
    - Introduced by diff: false; previous behavior: The same prompt changes initiated the same provider requests before the diff whenever the wall clock was nondecreasing; the removed zero-delay throttle provided no normal-path batching.; critical-path effect: Provider work is asynchronous and off the prompt-model update critical path, though request initiation occurs from the synchronous change listener.
- Verdict: No reportable regression. The synchronous scan is a pre-existing hot-path cost, and removing throttle(0) does not increase its normal-path frequency or downstream fan-out.

### Scenario 2: Continuing to type or receive prompt updates after the system wall clock moves backward

- Critical path: The changed code immediately performs the same synchronous xterm-buffer reconstruction and state notification used during ordinary input. Before the diff, throttle(0) scheduled a timer for the wall-clock gap and suppressed subsequent calls behind its pending flag, so prompt-model progress waited for the clock to catch up.
- Scaling input: During the rollback interval, work now scales normally with effective xterm input changes and command/viewport size rather than collapsing all changes into one delayed scan. Downstream model-change events occur only for distinct reconstructed states.
- Effective concurrency: Model scans remain synchronous and serialized. Optional completion requests can overlap only according to existing provider cancellation behavior; the diff restores the same scheduling used before and after the rollback interval under ordinary clock progression.
- Cache behavior: No buffer cache is added or removed. State equality still suppresses duplicate notifications. Optional suggestion requests retain their existing cancellation behavior; there is no new persistent or negative cache.
- Mechanism confidence: High. The decorator's pending branch and wall-clock arithmetic directly explain the rollback-only difference, and the new test exercises that path.
- Magnitude uncertainty: Backward clock adjustments are uncommon and their duration varies. High-throughput writes while the model remains in PromptInputState.Input could perform more immediate CPU work than the stalled pre-diff state, but this is restoration of established normal behavior rather than a new multiplicity or unbounded mechanism.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/terminal/common/capabilities/commandDetection/promptInputModel.ts:120-124</code>: Existing pty/xterm events deliver shell echo and parsed terminal writes that trigger local prompt reconstruction.; cardinality: One or more trigger events per write/input chunk; during clock rollback the diff restores immediate handling for each event, while unchanged-state checks bound downstream notifications to effective state changes.
    - Introduced by diff: true; previous behavior: After a backward clock step, the first call created a timer for the rollback gap and the pending flag suppressed subsequent sync calls. This was the stale-model failure the change removes; outside rollback, behavior was already immediate per event.; critical-path effect: The local synchronous scan now runs before each affected event returns instead of being deferred until the wall clock catches up.
  - IPC at <code>src/vs/workbench/contrib/terminalContrib/suggest/browser/terminalSuggestAddon.ts:522 -&gt; terminalCompletionService.ts:194 provider.provideCompletions</code>: A restored prompt-state change can conditionally initiate existing terminal completion providers, including extension-host providers.; cardinality: Conditional on suggest settings and input shape; one request per effective model change can fan out across enabled providers, with prior request tokens canceled on replacement.
    - Introduced by diff: true; previous behavior: During the erroneous rollback stall these requests were likewise delayed because no current prompt-state event was emitted; under ordinary clocks the same requests already occurred at the same effective input cadence.; critical-path effect: Request initiation follows model notification, while provider completion is asynchronous and not required for prompt-model progress.
- Verdict: No reportable performance regression. The extra rollback-interval work is required to eliminate a correctness-only stale-model stall and matches the existing non-rollback scheduling; retaining the accidental suppression would reintroduce the bug.

**Summary:** Completed the performance pass over both changed files and traced prompt synchronization through xterm events, buffer reconstruction, UI listeners, and optional completion-provider boundaries. No high-confidence diff-introduced performance issue was found. The removed zero-delay wall-clock throttle was not a coalescer on normal clocks; it only suppressed work after backward clock movement. The PR fixes stale state rather than a qualifying shipped performance regression, so no regression-fix record was submitted.
