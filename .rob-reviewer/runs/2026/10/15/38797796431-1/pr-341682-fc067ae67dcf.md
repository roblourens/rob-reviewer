# Performance review: agentHost: apply managed model defaults without locking choices

[PR #341682](https://github.com/microsoft/vscode/pull/341682) at `fc067ae67dcf67ff6fb6cece4467185792515c7f`

## Findings (3)

### 1. [medium] Remove policy resolution from every prompt's critical path

**Finding ID:** `PERF-DBDB668BE1CB`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:7073</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** SDK IPC plus possible native MDM/GitHub policy I/O  
**Scaling:** One new awaited resolution per turn carrying a model selection (and per explicit model change), with retries able to repeat it; cost grows with prompt frequency rather than only policy changes.  
**Outcome:** increased prompt-send and model-switch latency on the critical path  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The same path resolved the chat entry and immediately called entry.setModel using the supplied configuration; it performed no managed-settings query before the turn could proceed.  
**Changed behavior:** Each live-chat model application now performs and awaits a managed-settings RPC before invoking session.setModel.  
**Confidence:** 0.99 — The changed await is directly on \_changeModelOnce's sequenced path, and AgentSideEffects awaits changeModel in Promise.all before progressing the turn. The only uncertainty is the typical duration of native/server policy resolution, not reachability or blocking behavior.

**Causal diff evidence:** The added await at RIGHT line 7073 resolves managed settings before the existing entry.setModel call; the pre-diff code proceeded directly from resolving the chat entry to setModel.

A normal prompt carrying the selected model, or an explicit picker change, can be delayed by an additional policy resolution before session.setModel and before the turn is sent; a slow policy source can add up to 3.5 seconds per request.

**Evidence:** resolveCopilotManagedSettings crosses the SDK RPC boundary and may wait for native MDM or GitHub policy resolution, with COPILOT\_MANAGED\_SETTINGS\_QUERY\_TIMEOUT\_MS set to 3500 ms. AgentHostSessionHandler attaches the selected model to outgoing turns, and AgentSideEffects calls and awaits agent.chats.changeModel whenever message.model is present before the provider send. The session launch already resolves the same token/working-directory policy, but that result is not retained for subsequent sends.

**Suggested direction:** Retain the launch/latest session-scoped policy keyed by token and working directory, update it on managed-settings notifications, and use that snapshot for model-option omission; coalesce any required refresh off the send critical path.

### 2. [medium] Resolve catalog policy in parallel with model discovery

**Finding ID:** `PERF-4CAD9AEB2AC4`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3070</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** sequential SDK IPC/network operations for models.list and managed-settings resolution  
**Scaling:** Adds one full policy-resolution latency to every catalog refresh; on slow native or GitHub policy sources the added delay is bounded only by the 3.5-second timeout.  
**Outcome:** delayed model-catalog publication and readiness  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A successful \_listModels result was published immediately; catalog readiness paid only the models.list latency.  
**Changed behavior:** A catalog refresh now serially waits for managed-settings resolution after the model-list RPC before publishing any models.  
**Confidence:** 0.98 — The source order proves serialization, \_listModels is documented and implemented as a real models.list request, and \_publishModels cannot run until the new await completes. Policy latency magnitude varies, but the added critical-path dependency is certain.

**Causal diff evidence:** RIGHT line 3070 adds a second awaited boundary only after \_listModels has completed, while model publication remains below both awaits.

On cold startup, sign-in, SDK reload, or catalog refresh, the model picker and dependent session setup remain unavailable for an extra policy-query duration after model discovery already finished.

**Evidence:** \_refreshModels first awaits client.rpc.models.list via \_listModels, then awaits resolveCopilotManagedSettings with a 3.5-second timeout, and only afterward updates \_models. refreshModels is used during SDK setup/reload and authentication-driven catalog loading, so picker availability waits for the sum of two independent boundary latencies. Neither result depends on the other.

**Suggested direction:** Start models.list and managed-settings resolution together and await them with Promise.all before the single atomic publication, preserving the requirement that projected defaults accompany the first published catalog.

### 3. [medium] Avoid per-chat RPC bursts on every model publication

**Finding ID:** `PERF-356FAF3BE90D`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3134</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** three SDK RPCs plus a session-config dispatch per live chat  
**Scaling:** For L live chats, one publication adds 3L sequential-per-chat RPCs launched concurrently across chats, plus L report updates; no aggregate limiter bounds the burst.  
**Outcome:** burst IPC/network load and reduced control-plane throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** \_publishModels only recomputed and published the shared model array; its cost did not scale through SDK control-plane calls with the number of live chats.  
**Changed behavior:** Every catalog/BYOK/local-row publication now starts a report refresh for all live chats. Each refresh performs managedSettings.resolve, session.model.list, and session.model.getCurrent sequentially, then dispatches a session-config report.  
**Confidence:** 0.97 — The loop, live-chat cardinality, and three-RPC callee are explicit. Each chat has only a per-chat Throttler, so simultaneous calls across distinct chats are not globally limited. The exact number of concurrently live chats varies by workload, affecting severity but not mechanism.

**Causal diff evidence:** The new loop at RIGHT line 3134 invokes refreshModelConfiguration for every live chat each time \_publishModels runs; no such per-chat work existed before.

Users with multiple live chats can see bursts of SDK subprocess/policy traffic and report serialization during catalog or local/BYOK model updates, contending with active turns and reducing responsiveness.

**Evidence:** \_publishModels is called by periodic catalog refreshes (30-minute scheduler for active providers), BYOK bridge changes, local model-row changes, and client restart paths. The added loop covers all \_chatEntriesBySdkId. CopilotAgentSession.\_refreshManagedModelConfiguration then crosses three SDK control-plane boundaries in sequence. Per-session Throttler coalesces only repeated work for the same chat and provides no shared limiter or policy-query grouping across chats.

**Suggested direction:** Keep the latest policy/current-model snapshot per chat and recompute reports locally on catalog changes; only perform boundary reads on actual session model or managed-policy changes. If reads remain necessary, coalesce policy resolution by token/working directory and apply a shared concurrency limit.

### Scenario 1: Cold startup, sign-in/reload, and periodic model-catalog refresh

- Critical path: Initial authentication/SDK setup cannot publish the model catalog until models.list and then the newly added managed-settings query both complete. Per-chat report refreshes happen after publication and are off the initial catalog critical path, but contend with warm live sessions.
- Scaling input: One cold or periodic refresh; warm cost additionally scales with L live chat sessions.
- Effective concurrency: models.list and managedSettings.resolve are serialized. After publication, all live chats start refreshes concurrently; each chat serializes its own three RPCs with a Throttler, but there is no cross-chat limiter.
- Cache behavior: The existing catalog refresh promise coalesces concurrent refresh callers and preserves the last good catalog, but the new managed-policy lookup has no host-side cache and runs on every refresh. Cold startup has no report cache; warm publication re-reads every live chat's policy/current model even when only the shared catalog changed.
- Mechanism confidence: High: source ordering, scheduler cadence, call graph, per-chat throttling scope, and RPC cardinality are directly established.
- Magnitude uncertainty: Native/server policy latency and the number of simultaneously live chats vary; the sequential dependency and 3L warm fan-out are explicit.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_listModels</code>: SDK models.list model-catalog discovery.; cardinality: One models.list RPC per coalesced catalog refresh.
    - Introduced by diff: false; previous behavior: This was the sole remote catalog boundary before publication.; critical-path effect: Blocks catalog publication and picker readiness.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:3070</code>: Resolve native/GitHub managed settings through the SDK subprocess.; cardinality: One resolution per catalog refresh.
    - Introduced by diff: true; previous behavior: No policy-resolution boundary existed between successful model discovery and publication.; critical-path effect: Newly blocks publication after models.list has already completed, for up to the 3.5-second timeout.

### Scenario 2: Sending a prompt or changing model in a live Agent Host chat

- Critical path: AgentSideEffects waits for changeModel before provider send. The new managed-settings await occurs before the existing session.setModel RPC, so prompt progress is blocked by both in sequence. Report readback after setModel is asynchronous and off this critical path.
- Scaling input: Number of prompts carrying model selections and explicit picker changes.
- Effective concurrency: Operations for one chat are serialized by the chat queue. One policy query and one setModel run sequentially per request; distinct chats may resolve policy concurrently without a shared limiter.
- Cache behavior: The session launch already resolves policy for the same token and working directory, and report refreshes obtain later snapshots, but neither is retained for changeModel. Consequently every request carrying a model selection performs a fresh resolution; there is no positive-result cache or in-flight coalescing by token/directory.
- Mechanism confidence: Very high: outgoing selected models are attached in AgentHostSessionHandler, AgentSideEffects awaits changeModel before send, and the added query precedes setModel.
- Magnitude uncertainty: The workbench normally supplies a selected model, but some host-default requests may omit it; policy sources may resolve quickly in common deployments. The blocking await and timeout are not uncertain.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:7073</code>: Resolve managed settings for the chat working directory.; cardinality: One new resolution for every turn whose message carries the selected model, plus explicit model changes; retries can repeat it.
    - Introduced by diff: true; previous behavior: The chat entry proceeded directly to session.setModel.; critical-path effect: Blocks session.setModel and the subsequent provider send, up to the 3.5-second policy timeout.
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:setModel</code>: Apply model/effort/context/tier to the runtime session.; cardinality: One setModel per request carrying model selection.

  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_refreshManagedModelConfiguration</code>: Read policy, model schema, and current model for report publication.; cardinality: At least one coalesced pipeline after a model-change burst: policy resolve, model.list, and getCurrent.

### Scenario 3: Live managed-policy/model changes and chat-scoped picker report updates

- Critical path: Managed-settings and session-model events schedule asynchronous readback. Picker state updates after the report dispatch; the report does not block session.setModel, but SDK control-plane work and AHP updates share resources with active turns.
- Scaling input: Live chats L, models M, and report refresh frequency; payload generation is O(M) per chat and owner-session report patches include peer reports.
- Effective concurrency: A per-chat Throttler coalesces queued triggers for that chat, while in-flight work is not cancelled. Different chats run independently and can burst concurrently.
- Cache behavior: Each live chat stores a full report snapshot containing model defaults/choices. Equality prevents dispatching an unchanged individual report, but generating it still performs all three RPCs. Reports are removed on chat disposal; no unbounded post-disposal retention was found.
- Mechanism confidence: High: ownership, disposal, report shape, equality check, and dispatch behavior are explicit.
- Magnitude uncertainty: Typical report/catalog size and peer-chat count vary. Disposal cleanup and equality checks bound retention and suppress unchanged dispatches, so no separate memory finding was submitted.
- Expensive boundaries:

- Verdict: The cross-chat burst is covered by the publication fan-out finding. Serialization growth is real but not separately reported because expected peer-chat cardinality is uncertain and cleanup is present.

### Scenario 4: Rendering the model picker, restoring automation configuration, and switching chats

- Critical path: Schema projection and picker updates are synchronous in-memory work on report/model changes; no new filesystem, database, network, subprocess, or direct IPC boundary is reached from rendering or ordinary picker reads.
- Scaling input: Number of models and configuration properties when a report/catalog changes, not frame or input frequency.

- Cache behavior: The workbench keeps per-conversation overrides/preferences in maps, clears them on store reset/disposal, and does not persist host-owned report defaults as personal preferences. Observable equality suppresses unchanged session-report application.
- Mechanism confidence: High for the inspected workbench call graph; all changed projection helpers are in-memory.
- Magnitude uncertainty: Catalog sizes are ordinarily limited; no evidence showed the added map/schema cloning on a per-frame, scroll, or keystroke path.
- Expensive boundaries: none found
- Verdict: No additional reportable performance regression: work is bounded in-memory projection, read-only state is cleaned up, and no hot UI boundary was introduced.
