### Scenario 1: Restore local terminal editors when serialized terminal state was revived in the current pty host

- Critical path: Editor deserialization creates a terminal instance; process creation waits for the local direct proxy, then getRevivedPtyNewId and attachToProcess must complete before LocalPty.start can replay/start the terminal.
- Scaling input: One restore path per serialized terminal editor; effective cardinality is two pty-host RPCs per editor. The PID argument does not add an operation when a revived ID exists.
- Effective concurrency: Multiple editor inputs may restore concurrently, but \_connectToDirectProxy coalesces them on one DeferredPromise. The two RPCs for each terminal remain sequential; the diff adds no aggregate concurrency or limiter bypass.
- Cache behavior: The direct proxy connection is coalesced and reused. Revived-ID lookup is a pty-host Map read keyed by workspace and old ID; successful and missing lookups are not separately cached in the renderer, but each restore invokes the path once and there is no retry loop.
- Mechanism confidence: High: the changed branch and direct-proxy call sequence are explicit, and successful revived restores retain the same RPC count and ordering.
- Magnitude uncertainty: The number of restored editor terminals varies by workspace, but it does not alter the before/after cost per terminal.
- Expensive boundaries:

- Verdict: No regression: successful revived restores retain two sequential RPCs per editor, shared connection establishment, and the same process start/replay behavior.

### Scenario 2: Restore a local terminal editor after a pty-host restart when no revived-ID mapping exists

- Critical path: The renderer performs the revived-ID lookup and then an attach RPC. If the original ID still maps to the saved PID, restore continues normally. If it maps to another PID, the attach is refused and the existing fallback resolves the launch configuration/environment and creates a replacement terminal process before the editor becomes usable.
- Scaling input: One lookup and attach attempt per restored editor. Replacement shell creation scales with the number of actual stale-ID/PID collisions, bounded by the number of restored editor terminals, with no retry or repeated attach.
- Effective concurrency: Editor restoration can initiate independent terminal restores concurrently; connection establishment is coalesced, while any required replacement processes may be created concurrently as they were for any pre-existing attach failure. The diff changes which stale-collision attaches enter that fallback, not its scheduling.
- Cache behavior: Cold restore coalesces direct-proxy startup; warm restore reuses it. The pty-host process Map provides the authoritative ID/PID state. There is no negative-cache need because each restored input attempts attachment once and then clears attachPersistentProcess before replacement creation.
- Mechanism confidence: High: PID mismatch is checked in the pty host before attach, and TerminalProcessManager explicitly falls back to one process creation when attach returns undefined.
- Magnitude uncertainty: Stale-ID collisions require a pty-host restart plus ID reuse and are uncommon; a workspace may restore several affected editors at once. Exact shell startup cost is platform/profile dependent.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminal/electron-browser/localTerminalBackend.ts:238</code>: Query the pty host for a revived ID.; cardinality: One RPC per restored local terminal editor.
    - Introduced by diff: false; previous behavior: The same lookup occurred before the diff.; critical-path effect: Must complete before deciding whether to attach by revived or original ID.
  - IPC at <code>src/vs/workbench/contrib/terminal/electron-browser/localTerminalBackend.ts:244</code>: Attach to the original persistent-process ID while sending the saved PID for validation.; cardinality: One RPC per editor without a revived mapping; the extra PID is a scalar in the existing request.
    - Introduced by diff: false; previous behavior: The same attach RPC was issued without PID validation and could attach a different window's process after ID reuse.; critical-path effect: A matching attach completes restore; a mismatch fails immediately before PersistentTerminalProcess.attach.
  - subprocess at <code>src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts:351</code>: Create and start a replacement shell through \_launchLocalProcess after attachment is refused.; cardinality: At most one replacement process per restored editor whose saved ID now belongs to a different PID.
    - Introduced by diff: true; previous behavior: A colliding ID incorrectly attached the already-running process, so no replacement shell was created; missing IDs and other attach failures already used this same fallback.; critical-path effect: The replacement must be created and started before that terminal is usable.
- Verdict: No reportable regression: the added replacement process is the required bounded behavior for a stale collision, occurs once per affected editor without retry, and matching-ID restores add only a constant-time PID comparison to the existing IPC.

### Scenario 3: Relaunch a terminal and serialize its editor while the replacement shell is starting

- Critical path: Relaunch creates the replacement process, installs it, resets shellProcessId locally, registers process listeners, and invokes start. The terminal becomes ready when onProcessReady supplies the new PID. Editor serialization is off the process-start critical path and reads current IDs synchronously.
- Scaling input: One scalar assignment per process creation/relaunch; serialization remains one small JSON object per persisted terminal editor.
- Effective concurrency: No new asynchronous work or boundary concurrency is introduced. Existing process creation/start remains one operation for the relaunched terminal.
- Cache behavior: No cache is involved. The PID is intentionally unknown until the authoritative ready event and then stored for subsequent serialization.
- Mechanism confidence: High: the assignment is synchronous and the existing ready handler restores the PID before queued input is flushed.
- Magnitude uncertainty: The duration of the shell-ready gap varies, but the diff adds no work proportional to that duration.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/terminal/browser/terminalProcessManager.ts:423</code>: Start the newly created or attached terminal process via LocalPty/remote pty.; cardinality: One start RPC per terminal creation or relaunch.
    - Introduced by diff: false; previous behavior: The same start RPC occurred; the manager could temporarily expose the prior shell PID alongside the new persistent ID.; critical-path effect: Required for terminal readiness.
  - serialization at <code>src/vs/workbench/contrib/terminal/browser/terminalEditorSerializer.ts:25</code>: Serialize the editor's persistent ID and current shell PID into workspace editor state.; cardinality: One small object per persisted terminal editor when workbench storage serializes editor state.
    - Introduced by diff: false; previous behavior: Serialization already occurred and could pair the new persistent ID with the previous shell PID during relaunch.; critical-path effect: Not on shell startup; storage serialization reads the reset value and emits PID 0 until ready.
- Verdict: No regression: clearing one scalar prevents stale serialization and neither adds boundary calls nor increases serialized size.

### Scenario 4: Dispose PtyService after pty-host shutdown or leak-checked construction

- Critical path: PtyService disposal shuts down persistent terminals and disposes registered emitters/listeners. Registering the seven trace-listener subscriptions only changes cleanup ownership.
- Scaling input: A fixed number of trace event subscriptions per PtyService instance, independent of terminal count and event volume.
- Effective concurrency: No scheduling or concurrency change.
- Cache behavior: No cache is involved; listener lifetime is now explicitly tied to service lifetime.
- Mechanism confidence: High: \_traceEvent is called for a fixed set of service events and the added \_register only records their disposables.
- Magnitude uncertainty: None material; the change is fixed-size lifecycle bookkeeping.
- Expensive boundaries: none found
- Verdict: No regression; this is a cleanup-lifecycle improvement with constant retained state and no added per-event work.
