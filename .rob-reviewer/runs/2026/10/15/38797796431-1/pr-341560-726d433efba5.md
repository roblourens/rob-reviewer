## Findings (2)

### 1. [medium] Bound workspace timeline Git-log concurrency

**Finding ID:** `PERF-B7BACEEA298C`  
**Location:** <code>extensions/git/src/timelineProvider.ts:311</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Concurrent Git subprocesses, parsed commit output, CPU, and filesystem I/O across all open repositories  
**Scaling:** With R open repositories and requested limit L, one workspace request immediately starts R \`git log -n(L+1) --shortstat\` subprocesses and parses up to R\*(L+1) commits. On refresh, TimelinePane sets L to at least the number of already loaded items, so the burst grows with both repository count and timeline depth.  
**Outcome:** Opening or refreshing the workspace timeline can saturate CPU/disk with simultaneous Git processes, increase extension-host latency, and contend with normal source-control operations; repeated repository metadata changes can retrigger the burst after the 500 ms debounce.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no Git workspace timeline path, so showing Timeline without a resource did not launch Git-log subprocesses across every open repository. File timelines issued a single repository log.  
**Changed behavior:** The new workspace provider maps every eligible repository through \`logRepository\` inside an unbounded \`Promise.all\`; \`Repository.log\` reaches \`git log\`, so all repository subprocesses begin concurrently before the global page is merged.  
**Confidence:** 0.98 — The call chain from the added \`Promise.all\` to one \`git log\` subprocess per repository and the R\*(L+1) output bound are explicit. The number and speed of repositories vary, which affects severity but not the concurrency mechanism.

**Causal diff evidence:** RIGHT line 311 newly starts all per-repository workspace log requests through one unbounded \`Promise.all\`; this cross-repository subprocess fan-out did not exist before the diff.

A multi-root workspace or folder containing many detected repositories, submodules, or worktrees can launch dozens of Git processes at once merely by showing the workspace timeline. After loading multiple pages, a change in any repository reloads that larger count from every repository, amplifying the I/O and CPU burst.

**Evidence:** Added line 311 uses \`Promise.all(repositories.map(...))\`; line 315 awaits \`logRepository(repo, limit + 1, ...)\` for each repository. \`logRepository\` calls \`repo.log\`, and \`Repository.log\` executes \`git log\`. Repository count is not globally bounded; defaults can additionally discover 10 submodules and optionally up to 50 worktrees. Added model change subscription at line 138 emits workspace changes, and TimelinePane reloads with \`Math.max(timeline.items.length, pageSize)\`. Existing Git startup status work uses a \`Limiter(5)\`, establishing a local bounded-concurrency pattern.

**Suggested direction:** Queue repository log requests through a shared bounded limiter (using the extension's existing \`Limiter\` pattern) while preserving result order and cancellation. Apply the same bound to per-repository detail resolution if it can invoke remote avatar providers.

### 2. [medium] Rerender only rows whose selection context changed

**Finding ID:** `PERF-5A718D466DFA`  
**Location:** <code>src/vs/workbench/contrib/timeline/browser/timelinePane.ts:552</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous tree-row rerenders, action-bar/menu reconstruction, DOM updates, and repeated scans of the selected-item array  
**Scaling:** For S selected timeline items, each selection event places all old and new selected items in \`changed\`; every rendered row then calls \`getMultiSelection\`, which filters/scans the S-item selection. This makes one event O(S^2) in the visible-row case and repeated Ctrl/Cmd additions repeatedly redo prior rows, while even virtualized offscreen items still incur the O(S) union/loop.  
**Outcome:** Increasing selection size causes progressively slower selection handling and can block the UI thread or drop frames while selecting many history entries.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR the Timeline tree disabled multiple selection, so selection changes did not synchronously rerender every selected row or rebuild per-row action menus.  
**Changed behavior:** The new multi-selection handler unions the complete previous and current multi-selection and rerenders every item on every selection change; rendering each item reconstructs its action bar and recomputes multi-selection by scanning the full tree selection.  
**Confidence:** 0.96 — The changed event handler, synchronous rerender loop, and downstream full-selection scan/action-bar rebuild are explicit. Virtualization may cap DOM work to visible rows, but it does not remove the repeated full-selection loop/scans, so only the exact jank magnitude is workload-dependent.

**Causal diff evidence:** RIGHT line 552 newly constructs the rerender set from the full old and new selections; the pre-diff tree had \`multipleSelectionSupport: false\` and no selection rerender path.

Selecting a large range, or Ctrl/Cmd-selecting many local-history or Git entries before a bulk action, repeatedly rebuilds action menus for rows whose \`listMultiSelection\`/\`listDoubleSelection\` state did not change, making each click increasingly expensive and causing visible interaction jank.

**Evidence:** Added line 552 creates \`new Set(\[...this.multiSelection, ...multiSelection\])\`, and lines 555-558 synchronously call \`tree.rerender\` for every member. The changed renderer at line 1425 rebuilds the action bar via \`getItemActions\` and calls \`getMultiSelection(item, this.getSelection())\`; \`getMultiSelection\` filters and searches the entire selection. Most rows retained between two selections have unchanged context yet are rerendered again.

**Suggested direction:** Track the prior selection by handle and rerender only rows whose selected membership or derived context (\`multi\` and \`double\`) actually changed. Compute the selection metadata once per event/render pass and pass it to row rendering instead of rescanning the full selection for every rerender.

### Scenario 2: Show, page, or automatically refresh the new Git workspace timeline across repositories

- Critical path: The visible Timeline view invokes the workspace provider over RPC. - Effective concurrency: All R repository logs are launched together by \`Promise.all\`; represented-repository detail batches also run in parallel. There is no shared limiter or backpressure, although the extension already limits initial status work to five concurrent operations.
- Cache behavior: GitHub user/commit and unpublished-commit caches make some warm detail calls cheaper, but Git logs are rerun. The extension-host item cache is reset on reload. Workspace change events are debounced for 500 ms, which coalesces close events but does not bound per-refresh fan-out.
