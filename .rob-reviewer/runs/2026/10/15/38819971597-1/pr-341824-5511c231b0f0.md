### Scenario 1: Close one live canvas from the Editor window canvas pill

- Critical path: Pointer/tap action runs CanvasesPillControl.closeCanvas, crosses the local Agent Host management bridge, resolves the resident live chat, and awaits rpc.canvas.close before announcing completion. No chat queue, session restore, or cold-chat materialization is on this path.
- Scaling input: Distinct canvas lifetimes closed by the user; live projection cardinality is capped at eight per chat.
- Effective concurrency: Same-channel requests are coalesced both in the UI control and runtime session. Distinct channels may close concurrently; \_runMutation tracks rather than serializes them, with a maximum live set of eight and user-driven dispatch.
- Cache behavior: No result cache is involved. The projection map is the authoritative live lookup; stale channels are negative lookups and return without a runtime RPC.
- Mechanism confidence: High: the complete call path and both boundary crossings are explicit in changed code.
- Magnitude uncertainty: Runtime close duration depends on the provider's onClose work, but the call count and timeout are established.
- Expensive boundaries:

  - other expensive boundary at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:3858 CopilotAgentSession.\_closeProjectedCanvas</code>: Calls the live runtime's rpc.canvas.close for the canvas instance.; cardinality: One runtime RPC per canvas lifetime; concurrent requests for the same channel share \_canvasCloses. - Verdict: No reportable regression. The new boundary is the feature's required user-triggered close, same-channel work is coalesced, and cardinality is tightly bounded.

- Cache behavior: Provider routing uses existing session/chat caches with O(1) lookup. No cold session is restored and no new cache miss triggers materialization.
- Mechanism confidence: High: management, provider, IPC, and runtime call paths are all explicit and covered by changed tests.

### Scenario 3: Handle a runtime closed event that arrives after its close acknowledgement

- Critical path: The close response removes membership immediately. If its expected closed event arrives after an instance with the same ID is projected again, the event handler asynchronously queries rpc.canvas.listOpen before deciding whether to remove that newer projection; this reconciliation is off the original close-response critical path.
- Scaling input: Rare close responses that precede their closed events and are followed by same-instance projection before the event arrives.
- Effective concurrency: Each qualifying event starts its own asynchronous listOpen request; realistic concurrency is bounded by user closes over the eight live projections. The runtime's observed normal ordering avoids this branch.
- Cache behavior: No cache is used because open runtime state must be authoritative. Expected-event counters are consumed by matching events and cleared on handoff, projection clear, and session disposal lifecycle.
- Mechanism confidence: High for the conditional RPC mechanism and bounds; lower prevalence does not affect the established call path.
- Magnitude uncertainty: The exact prevalence of response-before-event ordering is runtime-dependent; repository evidence states the current runtime emits the event first.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:3895 CopilotAgentSession.\_removeCanvasUnlessOpen</code>: Calls rpc.canvas.listOpen to disambiguate a late closed event from a reopened canvas with the same instance ID.; cardinality: At most one listOpen RPC per expected late event. The common event-before-response ordering performs zero listOpen calls; concurrent same-channel closes are coalesced, and only eight canvases can be projected at once.
    - Introduced by diff: true; previous behavior: There was no user-close response/event race and therefore no reconciliation RPC.; critical-path effect: Not on the original close acknowledgement path; it gates only reconciliation of the potentially reopened projection.
- Verdict: No reportable regression. The extra RPC is conditional, correctness-preserving, outside the initial close critical path, and bounded by the small live canvas set.

- Verdict: No reportable regression. The added UI work is bounded, reuses its DOM/hover resources, and does not introduce layout reads, I/O, or per-frame work.

- Effective concurrency: Per-control repeated actions are suppressed; host handling is non-serial and immediately returns when no resident target exists.
- Cache behavior: Resident session state and live-session maps are checked only; cold state is deliberately not restored or materialized.
- Mechanism confidence: High: changed guards and tests explicitly prove zero restore/resolver/runtime calls.
- Magnitude uncertainty: Stale actions are timing-dependent but perform only one bounded bridge call.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/electron-browser/localAgentHostService.ts:546 LocalAgentHostServiceClient.closeSessionCanvas</code>: Carries the stale user request to the local Agent Host.; cardinality: One request per user action; repeated in-flight activation is coalesced by the control.
    - Introduced by diff: true; previous behavior: No close request was available.; critical-path effect: The bridge completes after the host determines there is no live target; no runtime or storage boundary follows.
- Verdict: No reportable regression. The diff specifically keeps cold-session filesystem/runtime startup work off this path.
