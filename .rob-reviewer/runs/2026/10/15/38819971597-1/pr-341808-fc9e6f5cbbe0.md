**Relevant issue families:** boundary-fanout, repeated-work, concurrency-burst, cache-lifecycle

### Scenario 1: Pull-request Electron smoke tests on Linux, macOS, and Windows

- Critical path: For each platform, both shard jobs must provision a runner, check out the repository, restore/install dependencies, transpile and compile test assets, set up Electron, compile smoke tests, run their assigned top-level suites, and upload results. The new required-check gates start only after all Linux, macOS, and Windows shard groups finish, so merge readiness remains gated by the slowest platform plus a small gate-job startup. The duplicated setup is on each shard's critical path; the two shards execute in parallel.
- Scaling input: The matrix fixes effective concurrency at two shards per platform. Test execution scales with the number and measured duration of top-level suites, each assigned once. Repeated setup, cache, checkout, and root-hook work scales linearly with shard count, currently doubling from one to two.
- Effective concurrency: Two shard jobs run independently per platform, for up to six Electron smoke jobs across the workflow. GitHub Actions runner availability supplies backpressure; there is no in-workflow shared limiter. Suites are serial within each Mocha process. The three gate matrix jobs start after all shard groups complete.
- Cache behavior: Warm runs restore the same platform node\_modules and built-in-extension caches independently in both shards; cold misses make both shards install dependencies/download extensions concurrently. Suite balancing uses a small in-memory static duration map and no persisted runtime cache. WSL setup remains single-shard, and macOS proxy work remains single-shard.
- Mechanism confidence: High confidence in the duplicated boundaries and two-way concurrency because the matrix and reusable workflow steps are explicit. High confidence that actual top-level test suites are partitioned exactly once by the assignment/filter logic.
- Magnitude uncertainty: Aggregate runner minutes, network bytes, and setup CPU increase materially, but repository evidence does not establish runner-pool saturation or a user-visible throughput/queue regression. The critical-path suite duration is intentionally reduced, and the shard count is bounded at two.

### Scenario 2: Local smoke-test execution with and without --shard

- Critical path: The process parses the shard, registers all Mocha suites, computes one assignment over the suite tree, creates temporary test data, runs the root setup hook including the test-repository clone, then executes only selected suites. Without --shard or with 1/1, no suite filtering occurs.
- Scaling input: Assignment work traverses the registered suite/test tree once and then selects among the requested shard count. For the documented realistic input of two shards and the repository's bounded smoke suite list, CPU and allocation are negligible relative to app launches.
- Effective concurrency: One Mocha process executes suites serially. Running multiple local shard commands concurrently is user-managed; the code adds no internal worker pool or burst.
- Cache behavior: Each process recreates its temporary directory, so the test repository is cold per process. The static duration estimate map is initialized once per process. There is no cross-process coalescing or cache introduced.
- Mechanism confidence: High confidence from parseShard/selectShardSuites and the root setup hook call path.
- Magnitude uncertainty: Users could request unusually large shard totals, but the supported/documented path uses small totals and no realistic performance trigger was found for the assignment algorithm.
- Expensive boundaries:
  - filesystem at <code>test/smoke/src/main.ts:154-168</code>: Remove/create a temporary smoke-test directory and extension directory.; cardinality: Once per runner process, unchanged for an unsharded invocation; one per explicitly launched shard process.
    - Introduced by diff: false; previous behavior: Every smoke runner process already recreated its temporary directory.; critical-path effect: Synchronous setup occurs before suite execution.
  - network at <code>test/smoke/src/main.ts:281-301</code>: Clone or fetch/reset the smoke-test repository.; cardinality: Once per process. A user launching two shards creates two processes and therefore two clones; a normal unsharded run remains one.
    - Introduced by diff: true; previous behavior: An unsharded local invocation cloned once; there was no supported multi-process shard workflow.; critical-path effect: The root hook blocks all selected suites.
- Verdict: No finding. Existing unsharded behavior is preserved, and realistic sharded use adds bounded linear assignment work while intentionally distributing expensive suites.

### Scenario 3: End-of-run top-level suite duration reporting

- Critical path: Runner listeners record a timestamp at each runnable top-level suite start and append one duration at suite end. After Mocha completes, the bounded duration array is sorted and printed before process exit; formatting is off the test-execution critical path except for the final completion callback.
- Scaling input: State and final sort scale with the number of executed top-level suites in one shard, not tests, frames, or process lifetime. The process exits immediately after reporting.
- Effective concurrency: Mocha emits events synchronously in one process; no added parallel work or queue exists.
- Cache behavior: No cache. The map and array live only for one smoke runner process and are reclaimed at exit.
- Mechanism confidence: High confidence from the two runner event handlers and completion callback.
- Magnitude uncertainty: Exact suite count can evolve, but it is a small, repository-defined collection and each suite contributes one map entry and one result object.
- Expensive boundaries: none found
- Verdict: No finding. Retention and sorting are bounded by top-level suites and cannot accumulate across runs.

**Summary:** Completed the performance pass over all nine changed files and relevant workflow/runner call paths. The change partitions smoke suites while duplicating bounded per-job setup across two concurrent shards; this is an explicit latency/capacity tradeoff, not a demonstrated performance regression. Cache, subprocess, network, filesystem, concurrency, and lifecycle behavior were checked, and no high-confidence actionable performance issue was found.
