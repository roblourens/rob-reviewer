## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/notebook/common/notebookCommon.ts:1124` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/notebook/common/notebookCommon.ts:1110`  
**Introducing path:** `src/vs/workbench/contrib/notebook/common/notebookCommon.ts`  
**Introducing commit:** `43957ccfe1d7f387def153528812e5b513c7f11c`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.98

**Mechanism:** The old normalization loop repeatedly scanned, matched, replaced, and reallocated the entire accumulated stdout string once per carriage-return overwrite, making a multi-line progress batch scale approximately O(N\*R), quadratic when record size is bounded.

**Symptom:** Large notebook stdout progress batches can synchronously stall output updates and delay renderer/event publication; the PR's production-path regression test uses 4,000 carriage-return records, where the old algorithm performs thousands of full-stream passes.

**Fixed behavior:** The added line-wise replace processes each logical line once, splits only carriage-return-bearing lines, and walks their segments once from right to left. For ordinary streams this changes normalization from repeated whole-stream work per overwrite to work linear in the decoded bytes and carriage-return segments, while retaining the legacy fallback only for dollar-bearing overwritten lines.

**Evidence:** Before this PR, fixCarriageReturn's while loop handled one carriage-return overwrite at a time; each iteration re-matched and replaced against the whole accumulated decoded stream. NotebookCellOutputTextModel.appendData synchronously calls optimizeOutputItems -&gt; compressOutputItemStreams before incrementing the version or firing onDidChangeData, and the notebook text model emits the output-item event only afterward. The new 4,000-record model test demonstrates a realistic batch cardinality on this path. Thus R overwrite records in N bytes caused repeated whole-string scans and allocations on the notebook output update critical path.

### Scenario 1: A running notebook appends stdout/stderr progress output to an existing cell output and updates the visible renderer.

- Critical path: CellEditType.OutputItems reaches NotebookCellTextModel.changeOutputItems, then NotebookCellOutputTextModel.appendData synchronously merges and normalizes stream buffers before version advancement, onDidChangeData, notebook content events, and any back-layer webview update can proceed. The changed normalization is therefore on the update/render critical path.
- Scaling input: The effective input is the concatenated byte count for each MIME group plus the number of carriage-return segments in that group. A realistic tested batch contains 4,000 progress records in one output edit; grouping means this is one normalization per MIME, not one boundary call per record.
- Effective concurrency: Normalization is synchronous and serialized on the workbench event loop for each output edit. Carriage-return records inside one batch are processed by one call; no Promise concurrency, limiter, queue, or parallel fan-out is involved.
- Cache behavior: There is no normalization cache. Each merged stream group is decoded and normalized when compression is needed. The renderer's version cache suppresses sending an already-published output version, but normalization occurs before that consumer check. Cold and warm normalization have the same complexity; ordinary streams are now linear, while the legacy dollar-bearing overwrite fallback remains pre-existing.
- Mechanism confidence: High: the old loop performed whole-string regex scans/replacements once per overwrite, whereas the changed ordinary path makes one line-wise pass and one reverse pass over carriage-return segments.
- Magnitude uncertainty: Exact latency varies with batch shape, runtime, and notebook output size. The repeated whole-string mechanism and 4,000-record tested cardinality are established even without relying on a specific timing.

### Scenario 2: The extension host applies a main-thread notebook OutputItem delta and updates extension-visible cell outputs.

- Critical path: MainThreadNotebookDocuments sends the existing model-change RPC; ExtHostNotebookDocument processes each raw OutputItem event, converts items, groups all text-stream items by MIME, and calls compressOutputItemStreams synchronously before extension-visible cell-change events are delivered.
- Scaling input: For each OutputItem delta, cost scales with total retained stream bytes and carriage-return segments after grouping by MIME. Effective cardinality is one compression per MIME group in the affected output, regardless of how many progress records are in the batch.
- Effective concurrency: RPC deltas and their synchronous extension-host processing are serialized on the extension-host event loop. MIME groups are processed sequentially with forEach; there is no concurrency burst or additional scheduling introduced by the diff.
- Cache behavior: No compression cache or negative cache is used. Existing output items are merged with the delta and normalized each time there is more than one all-stream item. Cold and warm behavior are equivalent; the new ordinary path reduces repeated work without changing invalidation or grouping.
- Mechanism confidence: High: setOutputItems directly invokes the changed helper after MIME grouping, and the before/after algorithmic difference is visible in the diff.
- Magnitude uncertainty: Extension-host impact depends on output history, MIME grouping, and append frequency. No new boundary or concurrency was added, and the algorithmic reduction for ordinary streams is direct.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/api/browser/mainThreadNotebookDocuments.ts:onDidChangeContent -&gt; src/vs/workbench/api/common/extHostNotebookDocument.ts</code>: Transfer the notebook content-change delta from the workbench to the extension host via $acceptModelChanged.; cardinality: One existing RPC per content-change event, with output items serialized in that event; compression in the extension host does not add calls.
    - Introduced by diff: false; previous behavior: The same event and payload crossed the boundary, followed by the old repeated whole-stream normalization.; critical-path effect: The boundary delivers the delta; extension-host normalization must then finish before API consumers observe the cell change.
- Verdict: No reportable regression. The changed helper lowers CPU and temporary-string allocation on this pre-existing synchronous IPC-consumer path.
