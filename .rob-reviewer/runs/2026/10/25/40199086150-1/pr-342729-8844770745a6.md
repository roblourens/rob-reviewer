**Relevant issue families:** boundary-fanout, concurrency-burst, eager-work, repeated-work

### Scenario 1: Core source pull request where all core test suites are affected

- Critical path: The new \`changes\` job must check out the repository and finish the pull-request file lookup before any of the 18 calling test-job groups (21 effective jobs after the three 2-shard smoke matrices expand) can start. After all groups complete, the 15 required-check matrix entries provision runners and execute their status scripts before merge readiness. Previously core test jobs could start immediately; required Electron-Unit/Electron/Remote checks came directly from those jobs, while only six browser/smoke reporter entries ran. The PR explicitly trades this short detection/reporter tail for the ability to skip unaffected suites.
- Scaling input: Changed-file count, paginated in pages of 100 up to GitHub's pull-request file-list limit; selector CPU is three linear scans over the returned paths. Test concurrency is fixed by 3 platforms and suite/shard topology, not file count.
- Effective concurrency: One serialized Detect Changes job gates all core tests, then up to 21 effective reusable-workflow jobs can become runnable together. The 15 reporter matrix jobs are separately runnable only after every one of their 18 declared dependencies resolves; they do not overlap the tests. Before the diff, the test jobs had no Detect Changes barrier and six reporter matrix entries waited only on their browser or smoke dependency sets.
- Cache behavior: The changed-file lookup is uncached and performed once per workflow run. Existing node\_modules and built-in-extension caches inside each reusable test workflow are unchanged; warm caches reduce test setup but do not bypass the new detection dependency. Reporter jobs have no meaningful cache state.
- Mechanism confidence: High: the new \`needs: changes\`, fixed matrices, and reusable-workflow shard expansion directly establish the ordering and cardinality.
- Magnitude uncertainty: Exact queue/startup delay for GitHub-hosted reporter runners and the Detect Changes job varies by service load. The mechanism and fixed job counts are certain, but the PR's large avoided test workload and required-name constraint make the added bounded delay/resource use an intentional tradeoff rather than a reportable regression.
- Expensive boundaries:
  - network at <code>.github/workflows/pr.yml:28-38, jobs.changes</code>: Checkout used by Detect Changes; cardinality: One checkout per workflow run, unchanged from the pre-diff Detect Changes job.
    - Introduced by diff: true; previous behavior: The checkout already occurred for path-filtered CLI/Copilot jobs, but core test jobs did not wait for it.; critical-path effect: Its completion is newly on the critical path to every core test job.
  - network at <code>.github/actions/detect-changes/detect.ts:150-159, listChangedPaths</code>: Paginated GitHub pull-request files API lookup; cardinality: One paginated logical lookup per run, with one request per 100 changed files; the diff reuses the existing result and adds no requests.
    - Introduced by diff: true; previous behavior: The lookup ran concurrently with core tests and affected only existing path-filtered jobs.; critical-path effect: The existing lookup is newly a prerequisite for all core test jobs.
  - other at <code>.github/workflows/pr.yml:167-374 and reusable pr-\*-test.yml workflows</code>: Provision and execute core Linux/macOS/Windows test runners; cardinality: 21 effective test jobs when all outputs are true: 7 per platform including two smoke shards.
    - Introduced by diff: false; previous behavior: The same suite/shard jobs ran without waiting for Detect Changes.; critical-path effect: These remain the dominant CI work; they now start after change detection.
  - subprocess at <code>.github/workflows/pr.yml:382-472, jobs.required-checks</code>: Provision 15 Ubuntu reporter runners and run shell/jq status evaluation; cardinality: 15 matrix runners per run. The script executes about 66 jq subprocesses total: four for each of 12 single-part checks and six for each of three two-part Browser checks.
    - Introduced by diff: true; previous behavior: Six reporter matrix runners handled only Browser and Electron-Smoke; the other nine required checks were emitted directly by their test jobs.; critical-path effect: All required checks now receive a short runner-provisioning/script tail after the last core test completes.
- Verdict: No finding. The diff adds a bounded detection barrier and reporter fan-out, but these are explicit scheduling costs needed to safely eliminate much larger test work on unaffected PRs; all affected core-source PRs retain the same expensive suite cardinality.

### Scenario 2: Docs-, CLI-, or copilot\_shim-only pull request

- Critical path: Detect Changes performs checkout and the changed-files lookup, all 21 effective core test jobs are then skipped, and 15 lightweight required-check reporter jobs publish the required names. Before the diff, all 21 core test jobs performed checkout, setup, compilation, and tests regardless of these paths.
- Scaling input: The changed path list, after rename expansion; every path must match a skippable category. Realistic cardinality ranges from one documentation file to hundreds of Rust/docs files, but only three linear in-memory rule scans are added.
- Effective concurrency: Detection is serialized first. No core test runners start; 15 reporter matrix jobs can run concurrently after skipped dependencies resolve. Previously 21 core test jobs could run concurrently across platforms, followed by six reporter entries for Browser/Smoke.
- Cache behavior: Selection itself is uncached and fail-open. Warm dependency caches formerly reduced setup but did not eliminate runner provisioning, checkout, transpilation, or test execution; skipping now avoids both warm- and cold-cache work. A failed/incomplete/empty changed-file lookup deliberately falls back to running all tests.
- Mechanism confidence: High: rule predicates, fail-open handling, job-level conditions, and reporter handling of intended skips are directly visible and covered by changed tests.
- Magnitude uncertainty: Runner-minute savings vary with cache warmth and suite duration, but eliminating 21 complete cross-platform jobs dominates the fixed 15 lightweight reporters. File-list API duration varies with changed-file count.
- Expensive boundaries:
  - network at <code>.github/actions/detect-changes/detect.ts:150-159, listChangedPaths</code>: Paginated GitHub pull-request files API lookup; cardinality: One logical paginated lookup per run, one request per 100 files; no additional call was introduced because the new rules consume the existing path list.
    - Introduced by diff: true; previous behavior: The API call already existed for CLI/Copilot selection but did not control core tests.; critical-path effect: Must finish before skip decisions and reporters can proceed.
  - other at <code>.github/workflows/pr.yml:167-374 and .github/workflows/pr-\*-test.yml</code>: Core test runner provisioning, checkout, dependency restoration, transpilation, and test execution; cardinality: Reduced from 21 effective jobs to zero for this scenario.
    - Introduced by diff: false; previous behavior: All 21 effective jobs ran even though these changes could not affect their inputs.; critical-path effect: Removed from both the workflow critical path and runner-capacity demand.
  - subprocess at <code>.github/workflows/pr.yml:382-472</code>: Required-check shell/jq reporters; cardinality: 15 fixed reporter jobs and about 66 jq subprocesses, replacing six reporter jobs.
    - Introduced by diff: true; previous behavior: Six reporters ran only after the much larger core test workload.; critical-path effect: Forms the short post-detection critical path after core tests are skipped.
- Verdict: No regression; this is the main performance improvement. The fixed reporter overhead is bounded and substantially smaller than the removed runner work.

### Scenario 3: Built-in extension or Copilot-extension-only pull request

- Critical path: Detect Changes gates all core jobs, then selectively skips unit and/or browser-integration groups while product tests that load built-in extensions continue. For a Copilot-only change, six effective unit jobs and three browser integration jobs skip while 12 effective product jobs run; reporters wait for all groups and then publish all 15 required names.
- Scaling input: Changed paths after rename expansion. Selection requires every path to remain in a safe category; one non-skippable path restores the relevant group. Effective test cardinality is grouped by suite/platform, not per changed file.
- Effective concurrency: For Copilot-only changes, 12 effective product test jobs can run after detection; nine effective core jobs are skipped. Fifteen reporters run after all groups resolve. Other built-in extensions skip the six unit jobs unless they are one of the explicitly read grammar/theme extensions, while browser/product groups remain runnable.
- Cache behavior: No selection cache; existing test dependency/artifact caches remain unchanged for groups that run. Skip decisions avoid both cold misses and warm-cache setup for omitted groups. Failed detection runs every group.
- Mechanism confidence: High: output rules map directly to fixed workflow conditions and suite groups.
- Magnitude uncertainty: Exact savings depend on which extension is changed and cache state, but group counts and skip predicates are explicit.
- Expensive boundaries:
  - network at <code>.github/actions/detect-changes/detect.ts:150-159</code>: Changed-files API pagination; cardinality: One logical lookup per workflow, shared by all output rules.
    - Introduced by diff: true; previous behavior: Core suites launched independently of this existing lookup.; critical-path effect: New prerequisite to selective suite launch.
  - other at <code>.github/workflows/pr.yml:167-374</code>: Cross-platform reusable test workflows; cardinality: Copilot-only example: 12 effective product jobs run and nine effective unit/browser jobs skip, versus 21 effective jobs before.
    - Introduced by diff: false; previous behavior: All 21 effective core jobs ran for every extension-only change.; critical-path effect: Remaining product suites stay on the workflow critical path; omitted groups free runner capacity.
- Verdict: No finding. The diff reduces expensive runner work with conservative fail-open and all-path matching behavior.

### Scenario 4: Build-script test suite execution

- Critical path: When \`npm run test-build-scripts\` runs, the new detector test synchronously invokes one \`git grep\`, reads only matching candidate test files, performs existence checks for referenced extension paths, and validates each discovered extension through the in-memory detector. This work is part of the build-script test step but not product startup/runtime.
- Scaling input: Number of test files mentioning \`extensions/&lt;name&gt;/\` and the number of matching references within those candidates; \`git grep -l\` avoids reading every test file in JavaScript.
- Effective concurrency: One synchronous git subprocess inside one test case. Node's test runner may execute test files independently, but this test's scan itself is serial and runs once per build-script suite invocation.
- Cache behavior: No application cache. Git and operating-system filesystem page caches can make repeat runs warmer; candidate contents are read once per matching file per invocation.
- Mechanism confidence: High for the added subprocess/filesystem work; lower magnitude concern because it is scoped to one build test and narrows candidates before reading.
- Magnitude uncertainty: The exact candidate count can grow as tests add extension-path references, and cold filesystem timing is not measured here. The narrowing grep and one-time test-only invocation keep the current mechanism bounded.
- Expensive boundaries:
  - subprocess at <code>build/lib/test/detectChanges.test.ts:69-71, extensionsReadByCoreTests</code>: Synchronous \`git grep -l\` over core test directories; cardinality: One git subprocess per build-script test-suite run.
    - Introduced by diff: true; previous behavior: No repository scan or git subprocess existed for detector tests because this test file was absent.; critical-path effect: Blocks only this test case until candidate paths are returned.
  - filesystem at <code>build/lib/test/detectChanges.test.ts:75-93</code>: Read candidate test files and check referenced extension paths; cardinality: One file read per grep candidate plus existence checks per matched extension reference, rather than all repository tests.
    - Introduced by diff: true; previous behavior: No corresponding scan occurred.; critical-path effect: Adds bounded local I/O to the build-script test step.
- Verdict: No finding. This is test-only validation, one invocation per suite, and uses an optimized candidate scan rather than collection-wide repeated reads.

**Summary:** Completed the performance review of all five changed files and all diff pages. Traced core-source, fully skippable, partially skippable extension, and build-test scenarios through changed-file API, runner, cache, subprocess, and filesystem boundaries. The PR intentionally adds a short serialized detector stage plus 15 lightweight reporters, while removing substantially larger cross-platform test work for unaffected changes. No high-confidence actionable performance regression was introduced, and the prior unconditional execution is an optimization target rather than a single traceable shipped regression suitable for report\_regression\_fix.
