# Performance review: ripple: drop the 50% limit and always run only the affected unit tests

[PR #344134](https://github.com/microsoft/vscode/pull/344134) at `33646c6958547b5f6d8a5431e9a823be3b659051`

## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `build/ripple/src/main.rs:365` (`RIGHT`)  
**Blamed base line:** `build/ripple/src/main.rs:373`  
**Introducing path:** `build/ripple/src/main.rs`  
**Introducing commit:** `a383e08626828ceb9c32f45f4a2940070a2f27f1`  
**Mechanism family:** `eager-work`  
**Performance category:** `throughput`  
**Confidence:** 0.98

**Mechanism:** The default 50% cutoff discarded an already-computed affected-test selection and eagerly executed every unit test on macOS and Windows, adding unaffected test files in proportion to the gap between the selected share and 100%.

**Symptom:** PRs whose affected-test weight exceeded 50% consumed unnecessary macOS/Windows CI VM time and had longer unit-test critical paths; the replay indicates an average selected share of 69.6% for triggering commits and about 0.4 VM-minute average savings per push after removing the cutoff.

**Fixed behavior:** For graph-contained changes, the plan now always emits and uploads the selected unit-test list regardless of weighted share. Each unchanged test runner filters its discovered modules through that list, avoiding execution of the unaffected 0-50% rather than expanding every selection above 50% to a full run.

**Evidence:** The base-revision condition at line 373 turns selection off whenever the already-computed weighted share exceeds max\_share (default 0.5). In PR CI, `select: false` prevents upload of `unit.txt`; the four macOS/Windows unit jobs then invoke their Electron, Node, or browser runners without `--runList`, and each runner loads its full default module set. The changed RIGHT line 365 now bases selection only on `sel.run_all`, preserving the computed file list for changes above 50%. The PR's replay supplies concrete observed scale: 18/708 commits crossed the cutoff, averaging 69.6% selected work but previously executing 100%, while the full macOS/Windows unit steps consumed 49.4 VM-minutes.
