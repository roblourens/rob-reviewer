## Findings (1)

### 1. [medium] Keep environment invalidation out of sandbox task discovery

**Finding ID:** `PERF-649EA09101E8`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts:577</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Paginated task-list requests plus per-task detail, repository, and history network requests from an in-flight sandbox session discovery scan  
**Scaling:** On a cold/full scan, discarded work grows with the number of task pages across the four repository/archive lanes and with the number of sandbox tasks requiring detail reads (bounded to five concurrent detail requests); warm scans still repeat the fixed list fan-out plus changed-task reads.  
**Outcome:** Wasted network I/O and delayed sandbox-session discovery; the failed result backs off the next poll from 60 seconds to 2 minutes, or effectively up to the 5-minute safety interval when the session feed is connected.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, environment registrations could not be deleted here, so an environment-only operation did not advance the generation used by sandbox task discovery. Existing generation bumps were tied to authentication or task/history mutations that actually affect that discovery cache.  
**Changed behavior:** A successful environment DELETE now increments \`\_discoveryGeneration\`, the same counter captured by \`listSessions\`; an unrelated task scan that finishes afterward returns \`kind: 'failed'\` instead of publishing or caching its completed result.  
**Confidence:** 0.99 — The shared counter, the exact post-scan mismatch branch, the scan's network cardinality/concurrency, and the caller's retry backoff are all directly traced in production code. Magnitude varies with task count and whether deletion overlaps a scan, but the mechanism and critical-path delay are deterministic when it does.

**Causal diff evidence:** The added line \`this.\_discoveryGeneration++;\` immediately after successful environment deletion is the only new operation that changes the generation observed by the independent \`listSessions\` pipeline.

Deleting a user-shared environment while startup or periodic sandbox discovery is in flight can throw away a potentially large completed scan, force the same task inventory/details to be fetched again, and leave cloud sessions stale or absent until the backed-off retry.

**Evidence:** \`listSessions\` captures \`\_discoveryGeneration\` at cloudSandboxApiService.ts:592, performs four paginated task-list lanes and up to one detail read per uncached/changed sandbox task with concurrency 5, then at lines 833-835 converts any generation mismatch into a failed result before committing the cache. \`CloudSandboxSessionContribution\` treats that result as a discovery failure and doubles its 60-second retry interval (lines 428-431); with a connected feed, \`\_refreshIfStale\` uses at least the 5-minute safety interval (lines 301-304). Environment deletion does not alter task/session data, so the added increment is unrelated to all of that work.

**Suggested direction:** Use a separate environment-inventory generation for \`getCachedEnvironments\`/\`listEnvironments\`, and advance only that generation here (while still clearing \`\_environments\`) so stale environment reads are rejected without invalidating sandbox task discovery.

### Scenario 3: Delete an environment while cold or periodic cloud-sandbox session discovery is in flight

- Critical path: The DELETE is independent of task discovery, but its new generation increment causes \`listSessions\` to return a failed result after all scan work completes and before publishing/caching it. The session contribution then retains stale session state and waits for a later poll; failure doubles the retry interval from 60 to 120 seconds, and a connected feed imposes a five-minute minimum safety interval.
- Scaling input: Cold/full discovery scans four repository/archive categories with pagination at 100 tasks per page, then performs detail reads for uncached or changed sandbox tasks and optional repository/history reads. Effective detail concurrency is capped at five, but total call count scales with task pages and qualifying tasks.
- Effective concurrency: Inventory scans are serialized by the contribution. Per-task details run through a shared limiter of five. The diff does not increase simultaneous detail concurrency; it discards the completed pass and causes a later serialized replay.
- Cache behavior: Warm \`\_discoveredTasks\` state survives, but the invalidated pass cannot commit newly fetched cache entries or its discovery checkpoint. The next pass therefore repeats list fan-out and may repeat the same detail/repository/history misses. Environment and task discovery should have separate generations.
- Mechanism confidence: Very high: shared counter writes/reads, request cardinality, limiter, pre-commit generation check, and caller retry policy are explicit in production code.
- Magnitude uncertainty: Overlap timing and account task count vary, affecting wasted bytes and duration, but startup/periodic scans and user-triggered deletion can realistically overlap. The deterministic failed-result/backoff path establishes impact even without exact latency measurements.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts \`\_listSessions\`</code>: List task inventory across active/archived and with/without-repository lanes, with pagination.; cardinality: At least four list requests on a full pass, plus one request for every additional 100-task page in each lane; an incremental pass still has the four logical lanes.
    - Introduced by diff: false; previous behavior: One completed scan could publish/cache its result unless authentication or task/history state actually changed; environment-only actions did not invalidate it.; critical-path effect: All responses must be processed before discovery reaches the generation check; the new environment-only increment then discards them, delaying session publication until retry.
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts \`\_listSessions\`</code>: Fetch task details and, when needed, repository names or persisted histories.; cardinality: Up to one detail request per uncached/changed sandbox task, with optional repository/history requests; detail concurrency is five.
    - Introduced by diff: false; previous behavior: The calls belonged to one discovery pass and their results were committed when that pass completed; environment deletion could not force a replay.; critical-path effect: These calls are part of the discarded scan and may be repeated because the pass cannot commit its local cache/checkpoint.
- Verdict: Reportable medium-severity repeated network work and delayed session discovery. A finding was submitted on the added shared-generation increment.

### Scenario 4: Environment deletion fails, is cancelled, or receives 404

- Critical path: A non-404 HTTP failure ends after the request/status handling and leaves inventory, cache, storage, and connection unchanged; the widget re-renders to re-enable the action. Cancellation likewise avoids commit. A 404 follows the successful path because absence is authoritative.
- Scaling input: One request per explicit attempt; retries require another user activation. Error rendering scales with the existing table rows but occurs once per attempt.
- Effective concurrency: Same-row duplicate actions remain suppressed for the full promise lifetime. There is no automatic retry burst or queued replay.
- Cache behavior: Non-404 failures preserve the warm environment cache and inventory. 404 clears the cache like 2xx because the record is already absent. No failure is negatively cached, but retries are manual rather than event-driven.
- Mechanism confidence: High: status branches and widget pending-action lifetime are directly covered by changed production code.
- Magnitude uncertainty: Users can manually retry persistent failures, but there is no automatic frequency amplifier.
- Expensive boundaries:
  - network at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/cloudSandboxApiService.ts \`deleteEnvironment\`</code>: Attempt the environment DELETE and read status/error response.; cardinality: One request per user-confirmed attempt.
    - Introduced by diff: true; previous behavior: No deletion attempt existed.; critical-path effect: The failure response gates UI error reporting and action re-enablement.
- Verdict: No additional finding. Failure preserves caches/state and requires explicit retry; 404 success intentionally converges local state.
