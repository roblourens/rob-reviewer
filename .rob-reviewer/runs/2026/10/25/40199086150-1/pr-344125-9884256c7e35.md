## Performance regression fixes detected (1)

### 1. boundary-fanout

**Fix location:** `.github/workflows/pr.yml:562` (`LEFT`)  
**Blamed base line:** `.github/workflows/pr.yml:563`  
**Introducing path:** `.github/workflows/pr.yml`  
**Introducing commit:** `0db0bcecf5158725d69c48494b8cda2d1c50b81d`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `startup`  
**Confidence:** 0.98

**Mechanism:** One PR workflow fanned out result aggregation into a 15-entry matrix of hosted runner jobs, duplicating runner startup and status-processing work already performed by PR Gate.

**Symptom:** Every pull request incurred 15 redundant GitHub Actions runner startups and associated compute/status-processing overhead after its core tests.

**Fixed behavior:** Deleting the entire `required-checks` matrix removes 15 duplicate hosted-runner allocations and their shell/jq work from every PR workflow while retaining one aggregate PR Gate job.

**Evidence:** The deleted `required-checks` job used a 15-entry matrix, so every PR workflow allocated up to 15 additional ubuntu-24.04 runners after the core test jobs completed. Each matrix child started a shell and repeatedly invoked jq only to re-report job results under legacy names. The unchanged `pr-gate` job already depends on every workflow job and performs the same result aggregation once, and branch protection now requires that single gate.
