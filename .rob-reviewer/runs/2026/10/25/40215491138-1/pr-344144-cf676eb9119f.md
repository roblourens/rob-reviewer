# Performance review: editor: fix &#64;vscode/diff bridge, compare diff algorithms on a sample of diffs

[PR #344144](https://github.com/microsoft/vscode/pull/344144) at `cf676eb9119f308cb6337e778689af22a38152a2`

## Findings (1)

### 1. [medium] Skip sampled algorithms that cannot honor the timeout

**Finding ID:** `PERF-1027B96945A0`  
**Location:** <code>src/vs/editor/browser/widget/diffEditor/diffProviderFactoryService.ts:180</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU time on the singleton editor web worker  
**Scaling:** One extra comparison is launched per sampled, uncached diff; it runs full-document primary and secondary algorithms sequentially, and an external candidate's runtime is unbounded by maxComputationTimeMs as document size and diff complexity grow.  
**Outcome:** The shared editor worker can remain blocked beyond the configured diff timeout, delaying subsequent interactive diff recomputations and other editor-worker requests.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With the normal \`advanced\` algorithm, an uncached diff ran only the configured primary computation, whose DefaultLinesDiffComputer enforces maxComputationTimeMs (5000 ms by default). External algorithms ran only when explicitly selected as the primary algorithm.  
**Changed behavior:** When the experiment samples an \`advanced-external\` or \`advanced-wasm\` secondary, this added call schedules another worker request that runs the external computer even for users whose primary is \`advanced\`; ExternalLinesDiffComputer explicitly does not forward maxComputationTimeMs, so the nonzero-timeout guard does not bound this work.  
**Confidence:** 0.98 — The added dispatch, selectable external candidates, sequential full-document execution, omitted external timeout, default 5-second primary budget, and singleton worker are all directly traced in repository code. Only the frequency and worst-case duration in a particular experiment cohort are uncertain, which limits severity rather than mechanism confidence.

**Causal diff evidence:** RIGHT line 180 newly dispatches the sampled comparison from the normal diff path. Before this diff, an \`advanced\` primary never invoked the uncapped external backend; after it, selecting \`advanced-wasm\` or \`advanced-external\` as the experiment candidate moves that backend onto sampled \`advanced\` diff requests.

With the comparison experiment enabled, opening or editing a large/pathological diff can make a single sampled external comparison monopolize the singleton editor worker past the normal 5-second budget. The already-rendered result returns first, but later edits, dirty diffs, formatting/minimal-edit work, and worker-backed completions wait behind the sample.

**Evidence:** The added call at line 180 dispatches compareDiffAlgorithms after each sampled cache miss. \`$compareDiffAlgorithms\` resolves both algorithms and synchronously invokes \`compareDiffAlgorithms\`, which runs primary then secondary on the full line arrays. \`ExternalLinesDiffComputer.computeDiff\` omits maxComputationTimeMs with an explicit TODO because the pinned wasm build panics when timing. WorkerManager owns one EditorWorkerClient, and these synchronous computations execute on that shared worker event loop.

**Suggested direction:** Do not dispatch external candidates from this experiment until they can enforce maxComputationTimeMs, or isolate the comparison in a disposable/dedicated worker that can be terminated at the budget. Keep the existing sample/cache behavior, but ensure a sampled run cannot block the shared editor worker past the configured limit.
