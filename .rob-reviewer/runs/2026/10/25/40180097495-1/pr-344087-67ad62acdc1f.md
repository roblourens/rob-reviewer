<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** repeated-work, synchronous-ui-work, serialization-allocation

### Scenario 1: Render live Agent Host response Markdown containing relative and absolute links

- Critical path: Markdown rendering synchronously calls the session URI resolver once per link; the resolver reads in-memory session/chat state, derives the first working directory, parses URIs, and rewrites the target before the anchor can render.
- Scaling input: Number of links in the rendered Markdown multiplied by the number of full/incremental Markdown renders while a response streams; links are not deduplicated because each anchor requires its own target.
- Effective concurrency: All resolution is synchronous and serialized on the UI rendering path; no queue, limiter, IPC, or asynchronous work is involved.
- Cache behavior: Session and chat snapshots are already held in maps/subscriptions. The working-directory string is parsed per resolver call rather than cached, but there is no cold remote lookup, cache miss, negative-cache behavior, or coalescing opportunity involving an expensive boundary.
- Mechanism confidence: High confidence that the new base-directory lookup and URI parsing run per link, based on the Markdown transformUri call path into AgentHostSessionHandler; high confidence that the path remains entirely in memory.
- Magnitude uncertainty: Very link-heavy responses and repeated streaming renders increase small object/string/URI allocations, but realistic cardinality and duration are uncertain and existing Markdown parsing/DOM work dominates; the added work does not establish a concrete user-visible regression.
- Expensive boundaries: none found
- Verdict: No reportable regression. The diff extends existing image resolution to links with bounded synchronous CPU/allocation work and introduces no external boundary, collection scan, retained state, or asymptotic change beyond per-link processing.

### Scenario 2: Render recorded Cloud Sandbox history links before, during, or after live-provider attachment

- Critical path: Each Markdown link first consults the synchronous live resolver when present; if it returns the unchanged href, the composite synchronously consults the recorded in-memory context and rewrites the link before rendering.
- Scaling input: Number of rendered links and response re-renders. For unchanged links, at most two in-memory resolver calls occur; effective cardinality remains one live attempt plus one recorded fallback per anchor.
- Effective concurrency: Resolvers execute serially on the UI thread. No promise, worker, limiter, network request, filesystem read, or IPC call is started by URI resolution.
- Cache behavior: Recorded chat context and parsed working-directory URI are cached in a ResourceMap for the session lifetime and removed on session disposal. Live session state is already subscription-backed. There are no cold/warm boundary differences or repeated failed remote lookups.
- Mechanism confidence: High confidence from the composite handler and read-only handler call path that fallback can add one in-memory rewrite and that no expensive boundary is transitively reached.
- Magnitude uncertainty: External and already-normalized links can take the extra recorded fallback when the live provider returns the original href, but both operations are bounded URI/string work; no evidence shows enough realistic links for measurable rendering degradation.
- Expensive boundaries: none found
- Verdict: No reportable regression. The fallback adds bounded per-link CPU work to preserve recorded context, with no fan-out, blocking I/O, unbounded allocation, or retained-resource growth.

### Scenario 3: Present a pending URL permission card

- Critical path: Tool-call presentation checks protocol metadata, validates the URL request, optionally checks whether the invocation text already contains the URL, and formats one display string before the confirmation UI renders.
- Scaling input: Number of pending confirmation tool cards and presentation refreshes; the new URL-specific metadata work is status-gated and does not run past the initial status checks for streaming, running, or completed calls.
- Effective concurrency: Entirely synchronous per tool card with no parallelism, queue, or asynchronous operation.
- Cache behavior: No cache is used or needed; metadata resides on the tool-call object, and each presentation derives a short-lived string/object. There are no boundary-backed cold or warm states.
- Mechanism confidence: High confidence from readToolCallPresentation and readCopilotUrlPermissionPresentation that the work is status-gated, local, and bounded to one request/message.
- Magnitude uncertainty: URL and invocation-message lengths control linear string scanning/formatting, but permission metadata is expected to be small and pending cards are low-cardinality; no unbounded protocol transformation or downstream large-data copy was introduced.
- Expensive boundaries: none found
- Verdict: No reportable regression. The change performs only bounded metadata checks and string formatting for low-cardinality pending confirmations, without I/O, fan-out, or retention.
