- Effective concurrency: Selected jobs and smoke shards remain parallel GitHub jobs with the same matrix width. The diff does not add a limiter or increase runner concurrency for affected groups.
- Cache behavior: Existing node\_modules, built-in-extension, WSL, and test-plan cache behavior is unchanged; cold misses still install/download inside selected jobs, while warm hits bypass those steps.
- Mechanism confidence: High: every expensive step remains inside the reusable job, and the added \`if: ${{ inputs.affected }}\` preserves the previous selection condition passed by each caller.
- Magnitude uncertainty: Individual cache-miss and suite durations vary, but the diff does not change their reachability or cardinality when affected.
- Expensive boundaries:

- Verdict: No reportable regression: affected PRs execute the same runner-backed work with the same concurrency and cache behavior.

### Scenario 2: Docs-only or otherwise unaffected PR where change detection skips platform test groups

- Critical path: Detect Changes completes, the now-unconditional caller jobs instantiate reusable workflows, each reusable workflow job immediately skips on \`inputs.affected == false\`, and PR Gate waits for those skipped results. No runner, checkout, cache, install, or test step is reached.
- Scaling input: A fixed workflow inventory: 22 effective platform reusable-workflow entries after matrix expansion (7 Linux, 7 macOS, 8 Windows), rather than 19 skipped caller rows whose three smoke matrices were not expanded.
- Effective concurrency: GitHub evaluates the reusable workflow entries in parallel. All inner jobs skip before \`runs-on\`, so effective runner concurrency is zero, as before.
- Cache behavior: No caches are read or written because the inner job-level guard prevents runner allocation and all steps; cold versus warm cache state is irrelevant.
- Mechanism confidence: High that 22 control-plane entries are materialized and zero runners execute, based on caller matrices and the job-level guards in all three reusable workflows.
- Magnitude uncertainty: GitHub's exact control-plane scheduling latency is external and variable, but the fan-out is small and statically bounded.
- Expensive boundaries:
  - other at <code>.github/workflows/pr.yml:linux-electron-unit-tests through windows-remote-tests</code>: Instantiate and evaluate a local reusable GitHub Actions workflow, including expansion of two smoke shards per platform.; cardinality: 22 bounded control-plane entries for an unaffected PR; three more visible rows than before due to smoke matrix expansion.
    - Introduced by diff: true; previous behavior: The 19 caller jobs were skipped before reusable-workflow invocation, and the three smoke matrices were not expanded.; critical-path effect: PR Gate waits for the skipped results, but no runner-backed boundary is crossed; only GitHub control-plane evaluation is added.
  - network at <code>.github/workflows/pr-linux-test.yml:linux-test; .github/workflows/pr-darwin-test.yml:macOS-test; .github/workflows/pr-win32-test.yml:windows-test</code>: Checkout, cache restore, dependency/browser download, and test execution declared in the reusable workflows.; cardinality: Zero when \`affected\` is false.
    - Introduced by diff: false; previous behavior: Also zero because the caller itself skipped.; critical-path effect: None; the reusable job-level \`if\` is evaluated before runner allocation.
- Verdict: No reportable performance regression: the diff adds only a small bounded control-plane fan-out to stabilize check names, without allocating runners or reaching filesystem, network, or subprocess-heavy steps.

### Scenario 3: Running the build tests that validate change detection and workflow naming

- Critical path: The Node test process synchronously reads and parses workflow YAML while executing the affected test cases; this is test-only and not on VS Code startup, rendering, or product paths.
- Scaling input: A fixed list of five workflow files plus three reusable workflow reads added to one existing assertion; it does not scale with changed-file count or repository history.
- Effective concurrency: Reads and YAML parses are synchronous and serial within the test process, as the pre-existing helper already was.
- Cache behavior: No application cache is used; operating-system filesystem caching may make repeated reads warm, but the added count remains fixed.
- Mechanism confidence: High: the added calls are explicit and synchronous, but their test-only scope and fixed cardinality are also explicit.
- Magnitude uncertainty: Exact milliseconds depend on filesystem state, but the files and invocation count are small and bounded.
- Expensive boundaries:
  - filesystem at <code>build/lib/test/detectChanges.test.ts:loadWorkflow and changed assertions</code>: Read workflow YAML with \`readFileSync\` and parse it with the YAML loader.; cardinality: Eight added fixed workflow reads/parses across the changed tests per suite invocation.
    - Introduced by diff: true; previous behavior: The tests loaded only the main PR workflow where needed and did not perform these eight validation reads.; critical-path effect: Adds a small fixed amount to this build-test suite only; it is off all product critical paths.
- Verdict: No reportable regression: fixed reads of a handful of small YAML files in a CI unit test do not establish meaningful latency, throughput, CPU, or I/O impact.
