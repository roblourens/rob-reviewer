# Performance review: Rerun failed browser unit tests in fresh browsers

[PR #344074](https://github.com/microsoft/vscode/pull/344074) at `c97c095c19d6d2fe1e69b81788ebe297fdf6f7ac`

## Findings (1)

### 1. [medium] Index rerun results before reconciling failed targets

**Finding ID:** `PERF-EA919BACB73A`  
**Location:** <code>test/unit/browser/index.js:757</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and short-lived arrays/JSON strings while filtering and serializing test title paths  
**Scaling:** For T outstanding targets, P passes, and F failures in a rerun, findPassedTargets performs O(T\*(P+F)) scans; above MAX\_RERUN\_TARGETS the whole-file fallback leaves T unbounded, so a broad failure can make this quadratic in the number of tests.  
**Outcome:** increased rerun latency and CPU/GC pressure on the CI critical path, potentially consuming much of the browser-test timeout after a large rerun has already completed  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR the browser runner executed one attempt and did not reconcile failed targets against a later attempt, so this repeated result-scanning work did not exist.  
**Changed behavior:** The new retry loop calls findPassedTargets after each rerun; for every outstanding target, the added lines refilter all failures and all passes and repeatedly JSON-stringify title paths.  
**Confidence:** 0.96 — The changed control flow, unbounded target cardinality after the explicit &gt;50 fallback, and nested full-result scans are directly visible. Exact wall-clock cost varies with failure prevalence and suite size, but the repeated-work mechanism and its placement after every rerun on the critical path are certain.

**Causal diff evidence:** Added RIGHT line 757 places \`result.failures.filter(...)\` inside \`\[...targets\].filter(...)\`; adjacent added line 760 likewise filters all \`result.passed\` for every target. The new whole-file fallback at added lines 731-734 allows the enclosing target map to exceed 50.

When an infrastructure or shared-state failure produces more than 50 failed browser tests and a fresh-browser attempt recovers, the whole-file rerun can return thousands of passes while hundreds or thousands of targets remain. Reconciliation then repeatedly scans that complete result set once per target, delaying CI completion even though the browser work has finished.

**Evidence:** planRerun switches to whole-file mode when targets.size exceeds 50 but preserves every target in the map. runTestsWithReruns then passes that unbounded map to findPassedTargets. At lines 757-760, each target runs result.failures.filter, constructs a failed-path Set, runs result.passed.filter with JSON.stringify per pass, and then searches those arrays again. Thus 1,000 targets and 5,000 rerun passes cause roughly five million pass inspections plus allocations and stringification, rather than one indexing pass.

**Suggested direction:** Build per-file indexes of failures and non-ambiguous passes once per attempt, including precomputed serialized title-path keys, then resolve all targets from those indexes in O(P+F+T). Preserve the existing file/test/suite matching and teardown-failure semantics.

### Scenario 3: Broad attributable failure causing whole-file fallback, followed by a recovering rerun

- Critical path: The first attempt records more than 50 outstanding targets. \`planRerun\` loads their unique whole files in a fresh browser. After that attempt reports passes/failures, Node must reconcile every outstanding target before it can declare recovery, schedule the last retry, or finish the job. The new reconciliation repeatedly scans all result arrays once per target.
- Scaling input: T deduplicated outstanding targets (unbounded above 50), P passing tests, and F failures returned by the whole-file rerun. Boundary cardinality is grouped to unique failed files, but CPU reconciliation cardinality remains every target against every result.
- Effective concurrency: One rerun at a time per browser; reconciliation is synchronous host CPU work after each attempt and cannot overlap the next attempt or job completion.
- Cache behavior: There is no per-file or per-title-path index. \`findPassedTargets\` rebuilds filtered arrays, Sets, and JSON title-path strings independently for each target, so warm data does not reduce repeated scans.
- Mechanism confidence: Very high confidence: the nested per-target filters and unbounded whole-file target map directly establish repeated CPU/allocation work on the critical path.
- Magnitude uncertainty: The prevalence of failure storms and exact suite cardinality are uncertain, but broad transient failures are realistic in a retry feature and the explicit &gt;50 fallback proves target counts can exceed the bounded title-selection case.
- Expensive boundaries:
  - subprocess at <code>test/unit/browser/index.js:runTestsWithReruns</code>: Launch a fresh browser for whole-file retry.; cardinality: One launch per retry, capped at two in PR CI.
    - Introduced by diff: true; previous behavior: No rerun browser launched after the initial failure.; critical-path effect: Required before reconciliation; grouped across all unique failed files.
  - network at <code>test/unit/browser/renderer.html:loadModules</code>: Reload renderer and every unique file represented by the broad failure set.; cardinality: One dynamic import per unique failed file, not per failed target.
    - Introduced by diff: true; previous behavior: No whole-file recovery attempt existed.; critical-path effect: All whole-file tests complete before result reconciliation.
  - serialization at <code>test/unit/browser/index.js:findPassedTargets</code>: Filter pass/failure arrays and repeatedly JSON-stringify title paths for each outstanding target.; cardinality: O(T\*(P+F)) result inspections and associated temporary allocations per recovering attempt.
    - Introduced by diff: true; previous behavior: No cross-attempt target reconciliation existed.; critical-path effect: Runs synchronously after browser completion and blocks retry scheduling or successful job completion.
- Verdict: Reportable medium-severity repeated-work regression. Index passes and failures once by file and title path before resolving targets.
