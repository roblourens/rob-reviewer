# Performance review: chat: allow cloud sandbox creation from the editor window

[PR #340817](https://github.com/microsoft/vscode/pull/340817) at `5e9e8831651ca660fb7f61af35362d15a677a202`

## Findings (1)

### 1. [medium] Defer workspace-wide Git opening until Cloud is used

**Finding ID:** `PERF-194CE51E555B`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/editorCloudSandboxContribution.ts:229</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Extension-host IPC calls plus Git repository discovery/initialization filesystem and subprocess work  
**Scaling:** On a cold window the work grows once per unresolved workspace root; although the observable mapper starts promises together, \`\_openRepositorySequencer\` makes effective concurrency one, so elapsed Git work grows approximately with the sum of per-root open/initialization times.  
**Outcome:** Eager background I/O and serialized Git/extension-host contention that reduces startup and Git responsiveness  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, repository resolution was consumed through \`\_workspaceRepositories\` by \`CloudSandboxSessionListController\`; with no discovered sandbox environment/provider, enabling the feature did not itself observe that graph or open every workspace root just to build creation options.  
**Changed behavior:** After restoration, merely enabling cloud sandboxes creates an always-observed draft-option graph, immediately resolving all workspace roots so repository picker choices are ready before the picker or a Cloud draft is requested.  
**Confidence:** 0.97 — The changed observer, full observable dependency chain, after-restored registration, IPC implementation, and global serialization are all directly traced. Exact duration varies with the number and type of workspace roots and Git extension readiness, so severity is medium rather than high.

**Causal diff evidence:** The added constructor autorun reads \`\_draftOptionGroups\` at line 229 whenever the contribution is enabled, even without a Cloud draft. That transitively reads \`\_workspaceRepositoryChoices\` and the cached \`repositories\` array, whose mapper calls \`\_resolveRepository(root)\` for every workspace root.

Opening any editor window with cloud sandboxes enabled can start serialized extension-host/Git repository initialization for every unresolved workspace root, consuming filesystem/subprocess/IPC capacity and delaying other Git and startup work in large multi-root workspaces even when the user never opens Chat or selects Cloud.

**Evidence:** \`\_draftOptionGroups\` reads \`\_repositoryOptionGroups\`, which reads \`\_workspaceRepositoryChoices\`; its \`repositories\` mapper invokes \`\_resolveRepository\`, and unresolved roots call \`IGitService.openRepository\`. \`GitService.openRepository\` waits up to 10 seconds for the Git delegate, while \`MainThreadGitExtensionService.openRepository\` performs extension-host \`$openRepository\` IPC, queues all opens through one \`Sequencer\`, and waits for each repository's \`HEAD\` before advancing. Thus a workspace with N roots not already known to \`IGitService.repositories\` causes N cold repository-open operations serially, independent of Cloud UI use.

**Suggested direction:** Do not keep \`\_draftOptionGroups\` observed solely to precompute picker state. Start observing/resolving repositories when \`getNewChatSessionInputState\` or the Cloud draft content provider is first used (and retain the observation while a draft is active), while continuing to use already-open repositories for discovery filtering.
