## Findings (1)

### 1. [medium] Avoid rendering the loaded Discover page twice

**Finding ID:** `PERF-5E063C30601B`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationDiscoveryPage.ts:1783</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work, allocations, DOM nodes, list updates, and layout work  
**Scaling:** The duplicated synchronous work grows with the number of loaded search results and recorded resources; in browse mode it recreates every displayed section/card and associated listeners and image elements.  
**Outcome:** increased navigation latency, CPU/GC pressure, and potential UI jank when reopening Discover  
**PR causality:** <code>introduced</code>  
**Previous behavior:** When setVisible(true) found an already-loaded catalog, the existing else branch called render() once before scheduling layout.  
**Changed behavior:** The added unconditional render() runs immediately after that existing else-branch render, so the cached/loaded path now performs the complete render twice for one visibility transition.  
**Confidence:** 0.99 — The duplicate call is explicit on the loaded critical path, and both render branches perform full synchronous collection/DOM work. Exact milliseconds depend on accumulated results and host performance, but the doubled mechanism and navigation trigger are deterministic.

**Causal diff evidence:** RIGHT line 1783 adds an unconditional this.render() after the unchanged else branch already calls this.render() for loaded pages.

Returning to an already-loaded Discover page (including after scrolling through multiple result pages) synchronously rebuilds the list or card DOM twice before the next frame, delaying the section switch and doubling transient allocations/layout work.

**Evidence:** setVisible(true) enters the else branch whenever no initial/recovery catalog load is needed, calls render() there, then reaches the newly added render() at line 1783. renderSearchResults iterates catalog and recorded resources and replaces the full WorkbenchList via splice; renderBrowse clears browseSections and browseDisposables and recreates all sections, cards, listeners, and image elements, and render() invokes layout.

**Suggested direction:** Render once per visibility transition: keep the existing else-branch render for loaded state, and only perform the new immediate render in the catalog-loading branch (or remove the unconditional call if loadCatalog already establishes the loading UI).

### Scenario 1: Open or return to Discover, browse the composed marketplace, and search connector metadata

Warm search ranking and pagination use cached snapshots and avoid the network.
- Scaling input: Up to 1,000 connectors, up to 16 search words, bounded metadata arrays and strings, and the number of search pages accumulated in the UI. The reported duplicate render scales with loaded catalog plus recorded resources.
- Effective concurrency: Marketplace sources are queried concurrently by the aggregator. Within the connector source one query performs one catalog refresh, but cold refresh promises are not globally coalesced. Connector continuations are sequential cursor reads over a pinned snapshot; the source LRU is capped at 32.
- Cache behavior: The catalog is fresh for 60 seconds. Search snapshots pin up to 1,000 parsed connectors for 30 minutes in a 32-entry LRU, and account/session/enablement changes cancel their cache token. Continuation pages reuse the snapshot without network work; negative/no-account results do not set a fresh timestamp.
- Mechanism confidence: High: the network/cache path and the duplicate synchronous render are explicit; the added line deterministically executes after the existing loaded-state render.
- Magnitude uncertainty: Exact UI delay depends on loaded-result count, DOM/list implementation, and machine speed; this affects severity, not the proven duplicate work.

  - network at <code>src/vs/platform/copilotConnectors/common/copilotConnectorsRequestService.ts CopilotConnectorsRequestService.doRequest</code>: GET /plugins and read/parse a response capped at 5 MiB; cardinality: One request for a cold/expired refresh; the 60-second service cache and pinned continuations make warm searches and pagination local

### Scenario 2: Connect, reconnect, check, or disconnect a Copilot connector from Discover or connector details

- Critical path: An explicit action resolves/creates the scoped authentication session, sends PUT or DELETE, optionally opens browser consent, then polls the authoritative catalog until the status changes. Completion waits for the catalog result; a membership change also awaits the throttled Agent Host refresh bridge.
- Scaling input: Time spent completing browser consent controls poll count; concurrent distinct connector actions control aggregate request rate.
- Effective concurrency: Authorization creation is coalesced by authorizationPromise and Agent Host refreshes by a Throttler. The install service deduplicates an operation for the same connector key, while distinct connector actions can proceed concurrently. Each operation polls serially every two seconds for at most five minutes.
- Cache behavior: Action polling intentionally bypasses the 60-second getConnectors freshness check by calling refresh directly. Unchanged parsed catalogs are deep-equality suppressed, while membership changes invalidate live sessions. Cancellation, experiment disablement, account changes, and disposal stop the operation.
- Mechanism confidence: High: intervals, timeout, serial polling, per-action deduplication, and throttled Agent Host refresh are explicit and tested.
- Magnitude uncertainty: Typical consent duration and frequency of users starting multiple connector actions are unknown.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts doAuthorize/getAuthentication</code>: Silent authentication session lookup and, after explicit consent, authentication-session creation; cardinality: At least one lookup per operation; session creation occurs only when scoped permission is absent and is coalesced across simultaneous authorization attempts
    - Introduced by diff: true; previous behavior: No connector-specific authorization path existed; critical-path effect: Blocks connection mutation until the correct account credential is available
  - network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts connect/disconnect via CopilotConnectorsRequestService</code>: PUT or DELETE connector membership, followed by GET /plugins status polling; cardinality: One mutation plus one immediate refresh and then one GET every two seconds until success, bounded by five minutes (up to about 150 polling refreshes)
    - Introduced by diff: true; previous behavior: No connector membership mutation or status polling existed; critical-path effect: The user action remains pending until an authoritative status is observed or timeout/cancellation occurs
  - IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts refreshAgentHostConnectorSessions</code>: Notify the local Agent Host to mark live Copilot sessions stale after connected membership changes; cardinality: One throttled management call for a detected membership change; unchanged polls do not trigger it
    - Introduced by diff: true; previous behavior: No connector-session refresh bridge existed; critical-path effect: Awaited by the refresh that observes the change so the next live-session turn uses new membership
- Verdict: No additional finding. Polling can issue many bounded requests but is cancellation-aware, serial per operation, and necessary to await an authoritative asynchronous status; evidence is insufficient that its two-second cadence is a concrete user performance regression.

### Scenario 3: Create, resume, or refresh a Copilot agent session while connectors are enabled

- Critical path: The existing Copilot client/session launch remains on the chat startup or next-turn path. After session creation/resume and safety/sandbox setup, launch now awaits connector capabilities, session GitHub auth status, client account enumeration, and runtime reconciliation before exposing the session. A live membership change queues stale marks behind active turns; the next turn destroys/resumes each affected session and performs reconciliation.
- Scaling input: Number of newly created/resumed sessions and number of live sessions when membership changes.
- Effective concurrency: The four runtime RPC stages are sequential for each launched session. Live-session stale marking fans out with Promise.all across sessions but each mark is queued behind that chat's sequencer. Client restarts are coalesced/deferred around active turns.
- Cache behavior: The client authentication tuple is retained and compared before session launch. Runtime reconciliation intentionally requests a fresh catalog for every created/resumed session; no result cache is maintained in VS Code. Unchanged connector catalogs do not trigger live-session invalidation.
- Mechanism confidence: High: startup placement, sequential RPC order, fan-out, and queueing behind active turns are direct in the diff and tests.
- Magnitude uncertainty: Runtime RPC and remote catalog durations, plus typical live-session counts, are not measured in the repository.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts \_ensureClientForSession/\_startClient</code>: Start or restart the Copilot runtime client with account token authentication when connector credentials change; cardinality: Existing client startup is reused; at most one deferred restart is requested for the observed connector-authentication mismatch
    - Introduced by diff: true; previous behavior: GitHub.com sessions without enterprise authentication did not require a client restart for connector-scoped credential changes; critical-path effect: A session launch waits until the correctly authenticated client is available
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSessionLauncher.ts \_reconcileCopilotConnectors</code>: Call runtime RPCs for connector capabilities, GitHub auth status, account enumeration, and connector reconciliation with catalog refresh; cardinality: Four sequential RPC calls for each created or resumed session when enabled and capabilities are available; zero when the feature is disabled and reconciliation stops early after capabilities when unavailable
    - Introduced by diff: true; previous behavior: Session launch performed none of these connector RPCs; critical-path effect: Explicitly blocks session availability so a newly connected tool is present on the first turn
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts refreshConnectorSessions</code>: Queue a stale marker for every live Copilot backing after membership changes; cardinality: One in-memory queued operation per live session/chat, deduplicated at the upstream membership-change notification level
    - Introduced by diff: true; previous behavior: Membership changes did not fan out to live sessions; critical-path effect: Off the current active-turn critical path; the next turn pays one session refresh/reconciliation
- Verdict: No finding. The new RPC latency is an explicit connector feature contract—reconciliation must complete before session availability—and failure is non-fatal; no safe narrower call or redundant invocation was established.

- Cache behavior: Uses the shared 60-second connector catalog cache. Connector change listeners are installed only while the experiment is enabled, hidden/access-disabled states cancel requests, and unchanged service state suppresses events.
- Mechanism confidence: High: visibility gates, cancellation, cache use, and merge loops are explicit.

- Expensive boundaries:

### Scenario 5: Persist and reconcile account-scoped connector installation records

- Critical path: On an authoritative connector change, the install service scans connected connectors, derives account-scoped records, hashes IDs only for new records, upserts changed metadata into profile storage, then reconciles applicable connector records against the in-memory catalog.
- Scaling input: Number of connected connectors and number of changed/missing records for the active account.
- Effective concurrency: The change listener invokes one asynchronous synchronization per emitted service change; identical catalog refreshes are equality-suppressed. Record reconciliation uses the service's existing bounded reconciliation flow.
- Cache behavior: The parsed connector catalog is authoritative in memory; deep-equal refreshes emit no change. Existing record IDs are reused, and only changed metadata is upserted. Account and experiment gates limit applicable records.
- Mechanism confidence: High for loop and write conditions; exact storage implementation cost is less certain.
- Magnitude uncertainty: Typical connected connector count and profile-storage latency are unknown.
- Expensive boundaries:
  - serialization at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceInstallService.ts createConnectorRecord</code>: Serialize identity and compute SHA-256 for a new account-scoped record ID; cardinality: Once per connected connector lacking an existing record; existing records reuse their ID
    - Introduced by diff: true; previous behavior: No connector records or connector identity hashes existed; critical-path effect: Off catalog rendering's direct critical path, invoked asynchronously from the change listener
  - database at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceInstallService.ts synchronizeConnectedConnectorRecords -&gt; recordStore.upsert</code>: Persist new or metadata-changed connector installation records in profile storage; cardinality: At most one upsert per connected connector whose record is absent or changed for the active account
    - Introduced by diff: true; previous behavior: No connector record storage writes occurred; critical-path effect: Asynchronous bookkeeping after connector state changes
- Verdict: No finding. Work is change-driven, skips unchanged record writes, and scales with connected rather than all available connectors.

### Scenario 6: Authenticate the Agent Host against GitHub while connector preference is enabled

- Critical path: The existing protected-resource resolver first obtains a usable GitHub session. - Scaling input: Number of applicable GitHub protected-resource authentication passes, normally one resource per Agent Host reconciliation.
- Effective concurrency: Protected resources are processed sequentially by the existing loop. The added lookup is one awaited provider query per applicable resolution; it does not prompt or create sessions.
- Cache behavior: The existing auth token cache avoids forwarding unchanged tokens, but the additional session enumeration itself is not cached here. Authentication-session change events drive later reconciliation elsewhere.
- Mechanism confidence: High: condition, lookup, and cardinality are explicit and covered by tests.
- Magnitude uncertainty: Provider lookup latency and authentication reconciliation frequency are not established as hot.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts resolveSessionForProtectedResource</code>: Silently enumerate authentication sessions for the resolved provider/account; cardinality: One extra provider-session lookup for each applicable GitHub protected-resource resolution when enabled and the initially resolved session lacks connector scope; zero otherwise
    - Introduced by diff: true; previous behavior: The initially resolved usable GitHub session was forwarded without this second lookup; critical-path effect: Blocks forwarding the selected token to the Agent Host for that authentication pass
- Verdict: No finding. This is one gated silent lookup on an infrequent authentication path, with no realistic scaling trigger shown.
