### Scenario 1: Starting or resuming a Copilot agent session, and preparing each turn, when sandbox dependencies or capabilities are unavailable

- Critical path: The existing sandbox host-support RPC is awaited during session initialization and after the existing sandbox configuration RPC during turn preparation. The diff adds synchronous warning-log calls before publishing diagnostics metadata, but does not add or move the RPC onto this path.
- Scaling input: Number of initialized sessions, turns, relevant sandbox configuration updates, and missing capabilities. Capability cardinality is a small fixed SDK set; updates are serialized on turn/config paths and stale diagnostics responses are generation-checked.
- Effective concurrency: Turn and configuration sandbox applications use the existing sandbox-config sequencer; diagnostics also rejects stale generations. Sessions can operate independently, as before.
- Cache behavior: Host-support results are not cached before or after the diff. Session diagnostic metadata is still equality-deduplicated; the new technical warning logs are not deduplicated, but their bounded per-turn volume is insufficient to establish a user-visible performance regression.
- Mechanism confidence: High confidence in the call frequency and added logging because all update call sites and turn/config sequencing were traced.
- Magnitude uncertainty: Actual log sink cost varies by host, but only one to a few short records are added per explicit diagnostics update; no evidence shows meaningful latency, throughput, or I/O degradation.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotSandboxDiagnostics.ts:36</code>: Copilot SDK sandbox.getHostSupport RPC; cardinality: One query per diagnostics update: session initialization, each sandbox application before a turn, and relevant configuration changes; effective cardinality and scheduling are unchanged by the diff.

  - other at <code>src/vs/platform/agentHost/node/copilot/copilotSandboxDiagnostics.ts:43 and :56</code>: Warning logging for an unavailable backend or each relevant missing capability; cardinality: One warning for an unsupported backend, or at most the small SDK capability set per failed support result, repeated on each diagnostics query while the condition persists.

The added work is bounded to short messages and a small capability set.
- Verdict: No reportable regression: RPC cardinality and critical-path placement are unchanged, and the only new repeated work is a bounded number of short diagnostic log records.

### Scenario 2: Displaying and updating the session-scoped sandbox warning as session state, configuration, or managed policy changes

- Critical path: Session and policy events synchronously compute distinct reasons, inspect in-memory configuration policy, and update the chat input notification only when reasons or disable eligibility change. This is UI update work, but no layout read, network, filesystem, IPC, or subprocess boundary is introduced.
- Scaling input: Number of simultaneously active/open Agent Host chat sessions and session/policy events. Each active session owns one notification object; disposal removes its command and listeners.
- Effective concurrency: Updates run synchronously per event. Equality checks suppress notification republishing when diagnostics and eligibility are unchanged; managed-policy observables trigger one autorun per active session.
- Cache behavior: Reasons and disable eligibility are cached on each instance for update suppression. Dismissals retain one resource key per dismissed session for the notification-service lifetime, but that lifecycle predates the diff. Command registrations and new listeners are disposed with the active chat session.
- Mechanism confidence: High confidence from the creation path, active-session ownership, MutableDisposable replacement, and explicit disposal registration.
- Magnitude uncertainty: A window may have multiple active chat models, but no evidence indicates unbounded active-session retention or a high-frequency managed-policy event stream.
- Expensive boundaries: none found
- Verdict: No reportable regression: added policy checks and command registrations are lightweight, update-deduplicated, and lifecycle-bound; the diff also reduces diagnostic Markdown/link parsing to the first concise reason.

### Scenario 3: Clicking Disable Sandboxing from the warning

- Critical path: The command revalidates policy, optionally dispatches one session configuration action, then awaits one global configuration update before command completion.
- Scaling input: Explicit user command invocations, not session history or diagnostic collection size. One invocation affects one active session plus one global setting.
- Effective concurrency: No shared burst is created; each click invokes one command. Session dispatch is not awaited, while the configuration update is awaited.
- Cache behavior: The handler rechecks current session state and policy at invocation time. It skips redundant session dispatch when state/config already indicate off; standard configuration handling owns persistence and propagation.
- Mechanism confidence: High confidence from the command handler and resolved connection dispatch path.
- Magnitude uncertainty: Configuration persistence latency depends on environment, but cardinality is one and directly required by the user action.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSandboxNotification.ts:93</code>: Dispatch SessionConfigChanged to the resolved agent-host connection; cardinality: Zero when the session is already off; otherwise one dispatch per explicit command invocation.
    - Introduced by diff: true; previous behavior: There was no disable action and therefore no session dispatch from this notification.; critical-path effect: Issued synchronously before the settings update so the active session is disabled as part of the requested action.
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSandboxNotification.ts:59</code>: Persist/update the global sandbox-enabled configuration value; cardinality: One configuration update per explicit command invocation.
    - Introduced by diff: true; previous behavior: There was no disable action and therefore no configuration write from this notification.; critical-path effect: Awaited before the disable command resolves; this is the requested settings mutation, not incidental fan-out.
- Verdict: No reportable regression: both introduced boundaries are bounded to one explicit user action and are necessary to implement that action; redundant session IPC is suppressed.
