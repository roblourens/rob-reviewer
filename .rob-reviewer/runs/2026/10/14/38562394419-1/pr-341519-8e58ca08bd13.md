**Relevant issue families:** boundary-fanout, repeated-work, concurrency-burst

### Scenario 1: An extension calls the new Repository.rebaseContinue API after resolving and staging a conflicted rebase.

- Critical path: ApiRepository.rebaseContinue delegates to Repository.rebaseContinue, which waits for one \`git rebase --continue\` subprocess and then the standard non-read-only repository model refresh before the promise resolves. This work is on the API call's critical path by design.
- Scaling input: Number of explicit API invocations. Each invocation represents one logical rebase continuation and performs one continuation subprocess plus one existing repository-wide refresh; conflict-file count does not multiply boundary calls.
- Effective concurrency: Within a refresh, independent state probes are intentionally parallel, followed by parallel status and refs reads. Repository operations are tracked but this method adds no loop, Promise.all fan-out, or new aggregate scheduler burst.
- Cache behavior: Mutable Git state is refreshed rather than cached. The virtual-filesystem config probe is cached after first initialization; no new cache keys, negative-cache behavior, or cache retention is introduced.
- Mechanism confidence: High: the delegate, operation wrapper, subprocess call, and post-operation refresh are directly traced in the repository code.
- Magnitude uncertainty: Git command duration depends on hooks, repository size, and the remaining rebase sequence, but those costs are inherent to the explicitly requested operation and existing refresh path.
- Expensive boundaries:
  - subprocess at <code>extensions/git/src/git.ts:2152 Repository.rebaseContinue</code>: Executes \`git rebase --continue\` with GIT\_EDITOR=true.; cardinality: Exactly one subprocess per API invocation; there is no loop or collection fan-out.
    - Introduced by diff: true; previous behavior: The low-level operation and internal commit-driven continue path already existed, but extensions had no direct public rebaseContinue entry point.; critical-path effect: Must complete before the rebaseContinue promise can resolve.
  - subprocess at <code>extensions/git/src/repository.ts:2863 Repository.run / :3039 Repository.\_updateModelState</code>: Refreshes HEAD/branch information, status, and refs after the mutation; first use may also read the virtual-filesystem config.; cardinality: One standard refresh per invocation, with a bounded set of repository-wide Git commands; status and refs run in parallel after the initial state probes.     - Introduced by diff: true; previous behavior: All existing non-read-only Repository.run operations, including the internal rebase-continue path, already performed the same refresh; only the public caller route is new.; critical-path effect: The API promise waits for the standard post-mutation refresh so exposed repository state is current.

- Verdict: No reportable regression. The new boundary is the single operation explicitly requested by the API caller, and the remaining work is the established bounded refresh with no changed fan-out or scheduling mechanism.

### Scenario 2: Automatic or manual status refresh in a normal repository after file changes or Git operations.

- Critical path: Repository.status enters the existing throttled Repository.run path and refreshes model state. The changed marker probes remain part of the parallel initial-state phase before status and refs complete.
- Scaling input: Number of opened repositories and debounced/throttled refreshes, not number of files for the changed marker-path logic.
- Effective concurrency: File-change refresh requests are debounced by 1 second and throttled with an additional 5-second wait; initial status across repositories uses the existing initial-status limiter. State probes within one repository are parallel.
- Cache behavior: Marker state is intentionally read fresh because rebase/merge/cherry-pick state is mutable. No cache behavior changes for ordinary repositories.
- Mechanism confidence: High: both old and new path expressions resolve to the repository's \`.git\` directory in this scenario.
- Magnitude uncertainty: Filesystem latency can vary, especially on remote filesystems, but the diff changes neither operation count nor paths for ordinary repositories.
- Expensive boundaries:
  - filesystem at <code>extensions/git/src/repository.ts:3287 Repository.getRebaseCommit and :3308 state-marker helpers</code>: Per refresh, performs two existence checks and one REBASE\_HEAD read plus MERGE\_HEAD and CHERRY\_PICK\_HEAD existence checks.; cardinality: Five bounded marker probes per repository refresh, independent of file count; the rebase trio runs concurrently.
    - Introduced by diff: false; previous behavior: For an ordinary non-bare repository, \`&lt;root&gt;/.git\` and \`dotGit.path\` identify the same directory, so both call count and target are unchanged.; critical-path effect: The probes are in the model-refresh critical path but overlap the HEAD, remotes, submodules, worktrees, template, and VFS probes.
  - subprocess at <code>extensions/git/src/repository.ts:3039 Repository.\_updateModelState</code>: Runs the existing repository-wide Git status/refs and HEAD-related reads.; cardinality: A bounded set per throttled refresh; status processes the repository once rather than once per file.
    - Introduced by diff: false; previous behavior: Unchanged by this pull request.; critical-path effect: Determines when updated SCM state is published.
- Verdict: No performance change for normal repositories.

### Scenario 3: Status refresh for a linked worktree or submodule, including while a rebase is stopped on conflicts.

- Critical path: The standard refresh now probes the worktree/submodule-specific git directory. When REBASE\_HEAD and a rebase state directory exist, getRebaseCommit additionally waits for one \`git show -s\` of the stopped commit so SCM state can expose rebaseCommit.
- Scaling input: Number of linked repositories being refreshed and refresh frequency. During an active rebase, each affected repository adds at most one commit-metadata subprocess per refresh, independent of conflict count and rebase history length.
- Effective concurrency: Per-repository marker checks overlap through Promise.all; automatic refresh is debounced/throttled, and startup status uses the existing cross-repository limiter. No new per-item concurrency is introduced.
- Cache behavior: No cache is used for active operation markers because they must reflect external Git changes. Cold and warm refreshes have the same bounded probes; commit metadata is read only after positive rebase-state detection.
- Mechanism confidence: High: the corrected dotGit path, positive-state branch, and single getCommit subprocess are explicit in the changed and surrounding code.
- Magnitude uncertainty: A \`git show -s\` can vary with object storage and remote filesystem latency, but it is one bounded local Git read only during an active rebase. No evidence indicates a material latency regression relative to the required linked-worktree state reporting.
- Expensive boundaries:
  - filesystem at <code>extensions/git/src/repository.ts:3287 Repository.getRebaseCommit</code>: Probes rebase state in \`repository.dotGit.path\`, the per-worktree or submodule Git directory.; cardinality: Two existence checks and one small file read per refresh, in parallel; count is constant per repository.
    - Introduced by diff: false; previous behavior: The same three probes existed but targeted \`&lt;root&gt;/.git/...\`, which is not the repository-specific Git directory for linked worktrees and can be a file. The diff changes their target, not their count.; critical-path effect: Correctly detects active rebase state during the initial parallel refresh phase.
  - subprocess at <code>extensions/git/src/repository.ts:3299 Repository.getRebaseCommit -&gt; extensions/git/src/git.ts:3361 Repository.getCommit</code>: Runs one \`git show -s\` to obtain metadata for REBASE\_HEAD when a linked-worktree or submodule rebase is active.; cardinality: At most one per refresh and only while valid rebase state is present; no per-conflict or per-commit fan-out.
    - Introduced by diff: true; previous behavior: The invalid old path caused linked-worktree/submodule rebase detection to return undefined, so this commit lookup was not reached in that case. Main repositories already performed it.; critical-path effect: Adds bounded latency to active-rebase refreshes in exchange for publishing the previously unavailable rebase commit state.
  - filesystem at <code>extensions/git/src/repository.ts:3308 Repository.isMergeInProgress / :3313 Repository.isCherryPickInProgress</code>: Checks merge and cherry-pick marker files in the correct per-worktree/submodule Git directory.; cardinality: Two existence checks per refresh, constant per repository.
    - Introduced by diff: false; previous behavior: The same checks existed at invalid \`&lt;root&gt;/.git/...\` paths for these repository kinds; only the target path changes.; critical-path effect: Runs in parallel with the other initial state probes.
- Verdict: No reportable performance issue. The only newly reachable subprocess is bounded to one per active-rebase refresh and is necessary to provide the corrected rebase state; there is no multiplicative or unbounded mechanism.
