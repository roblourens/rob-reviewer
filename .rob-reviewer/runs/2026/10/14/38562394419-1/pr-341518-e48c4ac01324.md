**Relevant issue families:** boundary-fanout, repeated-work, serialization-allocation, cleanup-lifecycle, concurrency-burst

### Scenario 1: Sending or resuming a turn after configuration changes while one or more canvases are open

- Critical path: The chat queue checks configuration, destroys the old SDK session, resumes a replacement, waits for extension readiness, then the diff awaits one canvas.listOpen RPC before initialization completes and the turn can proceed. Per-canvas state publications are synchronous local dispatches but downstream subscriber delivery is not awaited.
- Scaling input: The handed-over projection set is capped at 8 canvases per chat. Reconciliation examines at most those 8 projections; the listOpen response contains the runtime's open-canvas snapshot and is fetched once per replacement attempt.
- Effective concurrency: Refresh is serialized by the owning chat queue. Session destruction, resume, extension readiness, and the added listOpen call occur sequentially. There is no per-canvas RPC fan-out.
- Cache behavior: No cache is used for listOpen because reconciliation needs the replacement runtime's post-extension snapshot. With no projected canvases, the handoff is absent and reconciliation returns without the new RPC. Warm sessions that do not require configuration refresh perform no added boundary work.
- Mechanism confidence: High confidence in the one added awaited IPC and bounded projection work; low confidence that its magnitude is large enough to be reportable.
- Magnitude uncertainty: The latency and serialized size of listOpen depend on runtime responsiveness and the total runtime open-canvas snapshot, which is not explicitly capped by the host's 8-projection limit. The diff nevertheless adds only one grouped RPC on an already exceptional configuration-refresh path, so there is insufficient evidence of a user-visible regression.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_refreshSessionConfiguration and \_resumeSession</code>: Destroy/disconnect the old SDK session and resume a replacement runtime session; cardinality: One destroy and one resume for a configuration refresh, excluding bounded restore retries
    - Introduced by diff: false; previous behavior: Configuration refresh already destroyed and resumed the SDK session.; critical-path effect: Both must complete before the turn proceeds
  - filesystem at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_resumeSessionOnce</code>: Read persisted session metadata and working-directory state during resume; cardinality: One grouped metadata/working-directory restore sequence per replacement attempt
    - Introduced by diff: false; previous behavior: The same metadata and workspace restoration occurred before the change.; critical-path effect: Required before replacement session creation
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_waitForCanvasExtensions</code>: List extension/canvas registry state while waiting for canvas extensions; cardinality: One extensions.list and one canvas.list per canvas-enabled replacement attempt
    - Introduced by diff: false; previous behavior: Replacement initialization already waited for these runtime RPCs.; critical-path effect: Already awaited during initialization before the change
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_reconcileCanvasHandoff</code>: Fetch the replacement runtime's complete open-canvas snapshot with rpc.canvas.listOpen; cardinality: Exactly one call per replacement attempt only when at least one handed-over canvas exists
    - Introduced by diff: true; previous behavior: No listOpen RPC occurred during refresh initialization; the old projection was cleared instead.; critical-path effect: Awaited after extensions settle and before replacement initialization completes; bounded by the existing 30-second control-plane timeout
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:takeCanvasProjection, constructor handoff seeding, and \_projectOpenedCanvas</code>: Publish unavailable/restored CanvasStateChanged updates to subscribed clients; cardinality: At most a small constant number of updates for each of at most 8 projected canvases; publications are local synchronous dispatches and subscriber transport is not awaited
    - Introduced by diff: true; previous behavior: Destroying the old session removed canvas membership rather than handing channels through replacement state updates.; critical-path effect: Only local event dispatch is synchronous; client transport is off the awaited refresh critical path
- Verdict: No finding. The added critical-path RPC is intentional reconciliation work, grouped rather than per-canvas, skipped without a handoff, and bounded in frequency by configuration refreshes.

### Scenario 2: Configuration refresh whose replacement is discarded because the SDK client changes during restore

- Critical path: Each restore attempt fully initializes a candidate replacement, including the added handoff reconciliation, before client-generation validation can discard it and retry.
- Scaling input: At most 8 handed-over canvases and at most 5 serial restore attempts, as capped by MAX\_SESSION\_RESTORE\_ATTEMPTS.
- Effective concurrency: Attempts are sequential, not concurrent. Aggregate added work is at most five listOpen RPCs and bounded canvas state updates under repeated client replacement.
- Cache behavior: The handoff is retained across attempts so each candidate must reconcile against its own runtime; no candidate result is reusable after client replacement. No negative cache is relevant.
- Mechanism confidence: High confidence in serial retry multiplicity and the five-attempt cap.
- Magnitude uncertainty: Five attempts are possible only when the SDK client is repeatedly replaced during restore, an exceptional condition. Individual RPC latency is runtime-dependent.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_retryRestoreAfterClientReplacement and \_resumeSessionOnce</code>: Launch/resume and dispose candidate SDK sessions across client-replacement retries; cardinality: Up to 5 serial attempts
    - Introduced by diff: false; previous behavior: The bounded retry loop and full candidate initialization already existed.; critical-path effect: All failed attempts delay refresh completion
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_reconcileCanvasHandoff</code>: Reconcile each candidate with rpc.canvas.listOpen; cardinality: One additional grouped RPC for each candidate, up to 5
    - Introduced by diff: true; previous behavior: Restore retries did not query open canvases.; critical-path effect: Awaited within each candidate initialization
- Verdict: No finding. The diff adds repeated work under retries, but retries are exceptional, strictly capped, and serialized; no concurrency burst or unbounded amplification is introduced.

### Scenario 3: Configuration refresh with no currently projected canvases, and ordinary cold create/resume outside a refresh

- Critical path: Session initialization still calls the reconciliation helper after extension readiness, but it returns immediately because no handed-over projection exists.
- Scaling input: Zero handed-over canvases.
- Effective concurrency: No added asynchronous operation occurs.
- Cache behavior: The absence of a handoff acts as the negative state and avoids listOpen entirely; no stale cache or repeated miss is introduced.
- Mechanism confidence: High confidence from the handoff guard and call path.
- Magnitude uncertainty: None material; the added local empty-map check is constant and negligible.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:\_waitForCanvasExtensions</code>: Existing extension readiness RPCs; cardinality: One extensions.list and one canvas.list for canvas-enabled session initialization
    - Introduced by diff: false; previous behavior: Identical boundary work occurred before the change.; critical-path effect: Awaited as before
- Verdict: No finding. The common no-handoff path adds no boundary call, retention, or meaningful allocation.

### Scenario 4: Refresh failure after the old canvas projection has been released

- Critical path: The old session hands off at most 8 projection records, replacement creation fails, and the finally block removes the handoff and publishes canvas membership removal.
- Scaling input: At most 8 projections retained only for the duration of the refresh.
- Effective concurrency: Cleanup runs synchronously in the refresh finally block; no background retry or parallel owner remains.
- Cache behavior: The ResourceMap entry is deleted only if it still owns the same handoff, preventing an older settlement from deleting a newer handoff. Failed handoffs are not cached.
- Mechanism confidence: High confidence that both the agent-level handoff map and failed candidate session are released through finally/disposal paths.
- Magnitude uncertainty: None material because retained state and cleanup cardinality are hard-capped.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:\_settleCanvasHandoff</code>: Publish removal of canvas membership after failed replacement; cardinality: One membership action for the chat
    - Introduced by diff: true; previous behavior: Destroying the prior session cleared membership during disposal instead of at handoff settlement.; critical-path effect: Synchronous local publication during finally; subscriber transport is not awaited
- Verdict: No finding. The change preserves bounded cleanup ownership and does not introduce unbounded retention.

**Summary:** Reviewed all six changed files and every diff hunk for performance. Traced configuration-refresh sends/resumes, canvas-enabled initialization, bounded restore retries, subscriber state publication, and failure cleanup. The only new expensive boundary is one grouped canvas.listOpen IPC per replacement attempt when a handoff exists; it is serial, skipped without canvases, and paired with at most eight projections. No high-confidence actionable performance regression was found.
