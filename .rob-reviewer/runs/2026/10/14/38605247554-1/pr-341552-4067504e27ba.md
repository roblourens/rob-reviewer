# Performance review: Support video and native context-menu media paste in Markdown

[PR #341552](https://github.com/microsoft/vscode/pull/341552) at `4067504e27bad71e7df14f30ea06e372a03ed184`

## Findings (2)

### 1. [high] Bound media size before materializing the whole file

**Finding ID:** `PERF-71F3BA994991`  
**Location:** <code>extensions/markdown-language-features/src/preview/markdownEditorMediaTransfer.ts:57</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** A full-size Uint8Array for every pasted media file, retained in the WorkspaceEdit until it is applied, plus transient decoded chunk strings  
**Scaling:** Peak retained memory grows with the sum of all pasted file sizes because createEditForMediaFiles materializes files sequentially but keeps each completed Uint8Array in additionalEdits; a single realistic large video can consume hundreds of MiB.  
**Outcome:** Large video/audio pastes can cause severe extension-host GC pressure or allocation failure/OOM before the workspace edit can write the files.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, clipboard filtering accepted images only, so video/audio files were not transferred or materialized in the extension host at all.  
**Changed behavior:** The PR newly accepts video/audio clipboard files and allocates \`new Uint8Array(file.size)\` for each without any per-file or aggregate bound.  
**Confidence:** 0.99 — The changed allocation, newly accepted MIME types, materializeContents=true call path, and WorkspaceEdit retention are directly visible. Exact failure size varies by extension-host memory limits, but the linear unbounded mechanism and realistic large-video trigger are certain.

**Causal diff evidence:** RIGHT line 57 adds the unbounded full-file allocation used by the newly supported video/audio path; the PR also explicitly removes any additional file-size limit.

Pasting a large native video or audio file into the Markdown editor now allocates the entire file in extension-host memory; multiple files accumulate until applyEdit, potentially freezing or crashing the extension host.

**Evidence:** \`getNativeClipboardMedia\` now admits \`video/\` and \`audio/\`; \`MarkdownEditorImagePaste\` routes each accepted file to \`readClipboardMediaContents\`; this changed line eagerly allocates exactly \`file.size\` bytes. \`createEditForMediaFiles(..., materializeContents=true)\` awaits each \`data()\` and stores every result in one WorkspaceEdit, so completed arrays remain live. The added 25 MiB test explicitly documents no file-size cap, while native video files commonly exceed that by an order of magnitude.

**Suggested direction:** Validate both per-file and aggregate media size before allocating or requesting chunks, and reject oversized pastes with an actionable message; only remove that bound if the workspace-edit path can consume a file-backed/streaming source without retaining all bytes.

### 2. [medium] Batch clipboard chunks to avoid sequential webview RPC fan-out

**Finding ID:** `PERF-1BE7247E7E1C`  
**Location:** <code>extensions/markdown-language-features/src/preview/markdownEditorMediaTransfer.ts:60</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Authenticated webview postMessage request/response pairs carrying JSON/base64 chunks  
**Scaling:** The critical path performs sum(ceil(file.size / 256 KiB)) strictly sequential RPC requests across all pasted files; there is no cache, grouping, or overlap.  
**Outcome:** Paste latency and IPC/serialization overhead increase linearly with media size, delaying both workspace file creation and markup insertion.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Image paste previously encoded each image once and sent all base64 data in the single \`pasteImages\` request, with no per-chunk reverse RPC round trips.  
**Changed behavior:** Each 256 KiB chunk is now awaited through \`readClipboardMedia\` before the next chunk is requested.  
**Confidence:** 0.99 — The postMessage transport, sequential await, fixed chunk size, exact test cardinality, and critical-path applyEdit ordering are all explicit; only the per-hop duration varies by platform.

**Causal diff evidence:** RIGHT line 60 introduces the awaited reverse-boundary call inside the 256 KiB loop, replacing the prior single-payload paste request.

A 25 MiB paste now waits for 101 sequential webview RPC round trips before applyEdit; even multi-megabyte images incur many extra process-boundary turns on the user-visible paste path.

**Evidence:** The loop awaits \`read\` once per 256 KiB. The renderer callback resolves through MarkdownEditorRpcTransport, whose send envelope is \`webview.postMessage\`; the materialization loop in createEditForMediaFiles is also sequential. The added test asserts exactly 101 calls for 25 MiB and another test confirms peak request concurrency is 1.

**Suggested direction:** Keep cancellation and bounded transient memory, but transfer multiple chunks per RPC (or use a substantially larger bounded/adaptive chunk) so a normal large image/video requires a small bounded number of webview round trips rather than one per 256 KiB.

### Scenario 2: Execute native copy, cut, or paste from a webview host context menu

- Critical path: The shell obtains the active frame; when focus has fallen to body/documentElement, it synchronously restores the last connected focused element with preventScroll, then immediately invokes \`execCommand\`. No asynchronous boundary is added.
- Scaling input: One WeakMap lookup and at most one focus call per native clipboard command; focusin updates are one constant-time WeakMap write per focus transition.
- Effective concurrency: Synchronous, one command at a time on the UI thread; no queue, fan-out, or background work.
- Cache behavior: WeakMap stores at most one element per live content Document and entries are collectible with their Documents; there is no miss retry or persistent cache growth.
- Mechanism confidence: High for the constant-time mechanism and WeakMap lifecycle.
- Magnitude uncertainty: Browser focus implementation cost varies, but the changed work is constant per command and uses preventScroll; no realistic scaling input or retained strong reference was found.
- Expensive boundaries: none found
- Verdict: No reportable performance regression: the added synchronous work is bounded to native clipboard commands and does not create collection scaling, layout loops, or retention.
