## Findings (1)

### 1. [medium] Avoid copying the full fork prompt on every edit

**Finding ID:** `PERF-A44A97A7EE89`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/widget/input/editor/chatInputCommandArgumentHint.ts:216</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** UI-thread string copying and scanning allocations  
**Scaling:** O(L) work and allocation per edit for prompt length L; O(L^2) cumulative copying across incremental typing, or O(E×L) for E edits to a long pasted prompt  
**Outcome:** increased input latency and CPU/GC pressure while editing long fork prompts  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, \`/fork\` was an immediate command and this local \`/fork prompt\` hint state and its per-edit full-suffix read did not exist on that workflow.  
**Changed behavior:** After accepting the new \`/fork prompt &lt;prompt&gt;\` completion, every subsequent prompt edit synchronously copies and scans the entire text after the command prefix to decide whether the argument hint should be visible.  
**Confidence:** 0.98 — The added completion installs this local hint, the added content-change listener invokes the check on every edit, and the added tests establish that the hint remains alive while argument text is present. The exact cost depends on prompt length, but the full-range allocation and edit-path reachability are explicit.

**Causal diff evidence:** The diff adds a persistent local command hint and, at RIGHT line 216, materializes \`model.getValueInRange(afterRange)\` from the \`/fork prompt\` prefix through the end of the input. The newly added model-content listener calls \`update()\` for every edit, and the new test \`restores a local hint after deleting an argument...\` confirms the hint remains installed while an argument is present.

Editing a long pasted \`/fork prompt\` can incur input lag and GC churn: every keystroke or deletion allocates a new string proportional to the full prompt length. Typing a prompt incrementally performs cumulative quadratic character copying.

**Evidence:** \`rebindEditor()\` calls \`update()\` on every \`onDidChangeModelContent\`; \`getLocalHintDecoration()\` constructs an \`afterRange\` ending at \`getFullModelRange()\` and line 216 calls \`getValueInRange\` before merely checking \`startsWith(' ')\` and equality with one space. Because \`localHint\` is not cleared when additional argument text follows that space, this repeats for every character/edit. The \`/fork prompt\` completion at \`chatSlashCommands.ts:233\` is the new trigger.

**Suggested direction:** Avoid reading the full suffix. Check the character immediately after the prefix and compare model positions/length to determine whether exactly one trailing space remains (for example with line/position metadata or a length query), so each edit stays constant or logarithmic without allocating the prompt.

- Effective concurrency: Completion requests are cancellation-aware; cold session resolution is coalesced per resource. Editor hint updates are serialized synchronously on the UI thread.

Cold resolutions are coalesced in \`\_pendingSessionResolutions\`, and cancellation removes the waiter; failures are not negatively cached.

- Verdict: Reportable: the changed local-hint path performs O(prompt length) UI-thread allocation per edit, yielding cumulative quadratic copying during incremental typing.

### Scenario 3: Creating a fork and sending its initial prompt with attachments

The provider response itself is off the create RPC critical path after turn dispatch.
- Scaling input: Inherited turns, attached resource count/bytes, and number of distinct concurrent prompt forks.
- Effective concurrency: One create request per non-coalesced prompt identity. Host catalog mutation is sequenced per session. Attached resource rewrites use \`Promise.all\`, so cardinality equals distinct attached resources with no shared limiter, but this matches the ordinary send path and is bounded by the composer attachment set.
- Cache behavior: Working-directory and active-client reconcilers retain session state and avoid redundant claims when already current. Target session models are retained briefly after hydration to avoid immediate reload. No automatic retry/resend occurs on unknown outcomes.
- Mechanism confidence: High: the combined path, one-request semantics, attachment fan-out, and per-session sequencing are explicit in code and tests.
- Magnitude uncertainty: Attachment count/size and remote-host latency vary; no evidence shows increased effective cardinality versus the equivalent fork-then-send workflow.
- Expensive boundaries:

### Scenario 4: Automatic naming and lifecycle of prompt-bearing forks

- Critical path: Utility title generation may issue one existing utility-model request; active-agent/deferred strategies keep naming work off chat creation except for bounded context construction and persistence.
- Scaling input: Number of resident prompt-fork chats and bounded title-context size (up to the configured context budget).
- Effective concurrency: Title generation uses existing per-key cancellation/replacement; no new aggregate burst was found.
- Cache behavior: Fork title context is truncated to bounded strings and removed on refinement, rename, instruction consumption, session eviction, or disposal. Deferred seeds are persisted/restored per chat.
- Mechanism confidence: High for lifecycle and bounds; lower for material memory impact under realistic chat counts.
- Magnitude uncertainty: Admission-rejected active-agent forks can retain bounded context until retry or session teardown, but realistic retained volume was not sufficient for a high-confidence user-visible regression.
- Expensive boundaries:

- Verdict: No report: context is individually bounded and has session/chat cleanup; observed worst-case accumulation did not establish material impact.

### Scenario 5: Idle release or deletion while title/catalog writes are pending

- Critical path: The new waits run during idle release/deletion, after interactive subscribers are gone. They are not on chat input, rendering, or active turn response paths.
- Scaling input: Outstanding writes for the releasing session, not total writes across all sessions.
- Effective concurrency: Writes remain serialized per session; the drain waits for that session's current and newly queued writes and uses settled waits where failures are reported elsewhere.
- Cache behavior: Pending peer metadata/catalog writes are tracked by owning session, preventing unrelated sessions from extending a release drain.
- Mechanism confidence: High: the call site is teardown/release and the tracked writes are session-filtered.
- Magnitude uncertainty: A slow or stuck write can extend resident lifetime, but session scoping removes cross-session fan-out and no interactive critical path is blocked.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_whenSessionDataIdle</code>: Drain peer metadata and background catalog writes before releasing session data.; cardinality: All outstanding metadata, catalog, and session-database writes for the one releasing session.
    - Introduced by diff: true; previous behavior: Release waited only on the session database and could race peer/catalog writes; global synchronization elsewhere could wait on unrelated sessions.; critical-path effect: Delays background eviction/deletion only; it preserves write ordering before state is discarded.
- Verdict: No performance finding: the added wait is background cleanup synchronization and is narrowed to the owning session.
