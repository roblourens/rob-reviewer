## Findings (1)

### 1. [medium] Keep incremental root updates out of full-config replay snapshots

**Finding ID:** `PERF-91DE6266A08B`  
**Location:** <code>src/vs/platform/agentHost/node/protocolServerHandler.ts:3284</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Deep-cloned host-configuration objects retained for replay, plus JSON-serialized Web PubSub bytes for each authenticated relay lane  
**Scaling:** Cost is O(root-config size) per RootConfigChanged event for cloning/retention and O(root-config size × authenticated root subscribers) for serialization and network. Listener-owned project clone progress emits such an event once per second, and up to 1,000 projected snapshots remain reachable through replay-buffer keys.  
**Outcome:** Increased CPU/GC pressure, retained memory, and relay bandwidth/queue occupancy; large host settings can delay other Mission Control traffic during long project clones or repeated settings updates.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Listener-owned project updates were replayed and broadcast as their small catalogue action, while native host-config updates were not projected to relay clients, so neither path copied and transmitted the complete host value bag for every update.  
**Changed behavior:** Every successful root-config envelope now deep-clones the complete current host values, marks that copy as a replacement action, stores it in the projection WeakMap, and substitutes it during live broadcast and reconnect replay.  
**Confidence:** 0.97 — The changed allocation, one-second project-progress caller, 1,000-entry replay lifetime, per-client broadcast, and JSON serialization boundary are all directly traced. Exact config sizes and simultaneous lane counts vary, which limits severity but not the mechanism.

**Causal diff evidence:** RIGHT line 3284 introduces \`deepClone(this.\_stateManager.rootState.config?.values ?? {})\` inside the per-envelope broadcast/replay path; the same added block replaces the original patch with that complete value bag.

A long repository clone publishes catalogue progress once per second. On hosts with sizable MCP server env/header maps, terminal rule maps, or customization lists, each tick now allocates and retains another full settings copy and sends the whole bag to every authenticated Mission Control window instead of sending only the changed catalogue data.

**Evidence:** The added deepClone at line 3284 copies \`\_stateManager.rootState.config.values\` for every successful RootConfigChanged envelope, including listener-owned events. Lines 3287-3289 store that full copy as \`replace: true\`; \`\_replayBuffer\` holds up to \`REPLAY\_BUFFER\_CAPACITY = 1000\` key envelopes, keeping the corresponding WeakMap values alive. \`\_broadcastAction\` projects this envelope separately to each relevant client, and \`MissionControlProtocolServer.\_publish\` JSON-stringifies publish frames. \`MissionControlProjects.\_driveClone\` invokes \`\_publish()\` through a 1,000 ms ThrottledDelayer, making long clone progress a realistic repeated trigger.

**Suggested direction:** Preserve patch semantics for non-replacement actions. Merge the listener overlay only into affected overlapping top-level namespaces (for example \`copilot\`) and retain a full snapshot only for true replacement actions or snapshot fallback, so replay ordering remains correct without copying every unrelated host setting.
