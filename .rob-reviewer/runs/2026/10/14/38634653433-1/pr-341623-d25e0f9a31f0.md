## Findings (4)

### 1. [medium] Bound empty-run output before materializing it

**Finding ID:** `PERF-5F8C49BA96E6`  
**Location:** <code>src/vs/workbench/contrib/testing/common/testingChatAgentTool.ts:242</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** output bytes, VSBuffer slices, JavaScript strings, and serialized tool-result content  
**Scaling:** Allocation and copy cost is O(total output bytes across all tasks), with additional joined-string allocation; there is no upper bound before materialization.  
**Outcome:** memory/GC pressure and increased tool-response serialization latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** A zero-execution result flowed through the normal summary path, which did not read task output when there were no failed/errored tests.  
**Changed behavior:** The new zero-execution branch calls \`getRange(0, task.output.length).toString()\` for every task and joins all complete outputs into the returned tool content.  
**Confidence:** 0.98 — The changed line unconditionally reads each task's full output and converts all buffers to strings whenever no test reaches passed, failed, or errored. Output length is explicitly unbounded here; only the frequency and real-world log sizes are uncertain.

**Causal diff evidence:** RIGHT line 242 newly reads and stringifies complete task outputs; the deleted implementation did not include task output in an empty result.

A runner that emits a large compile, discovery, or import log but executes no tests causes the extension host/workbench to copy the entire log into strings and then into one more joined result, creating CPU/GC pressure, retained response bytes, and potentially a very large chat-tool payload.

**Evidence:** RIGHT line 242 has no byte, line, or token cap and scales directly with every task's full \`output.length\`. The branch is specifically reached for zero-execution failures, where verbose build/import diagnostics are a realistic trigger; the added tests exercise this path with runner output.

**Suggested direction:** Apply a shared total byte/character budget before reading buffers (for example, bounded head/tail excerpts per task with a global cap) and append a truncation marker, so useful diagnostics remain without materializing unbounded output.

### 2. [medium] Keep file-stat diagnostics off the test-run critical path

**Finding ID:** `PERF-B69A7527FF99`  
**Location:** <code>src/vs/workbench/contrib/testing/common/testingChatAgentTool.ts:478</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** filesystem/provider I/O calls, potentially remote IPC/network operations  
**Scaling:** Boundary cardinality is one concurrent stat per requested file; critical-path latency is governed by the slowest check and reaches the fixed 5,000 ms deadline for any stalled path.  
**Outcome:** blocked test-start latency and unnecessary remote I/O  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Explicit-file invocations mapped paths to URIs and queried the in-memory test collection via testsInFile; they did not issue filesystem/provider stats before starting matching tests.  
**Changed behavior:** The diff starts one IFileService.stat per requested file and awaits all checks together with discovery before invoking runTests.  
**Confidence:** 0.98 — The changed call path is explicit: every requested URI starts IFileService.stat, and the enclosing Promise.all must settle before test selection and runTests. The added tests themselves establish that one stalled stat makes an otherwise runnable request take the full 5,000 ms deadline; only the prevalence of slow providers is uncertain.

**Causal diff evidence:** RIGHT line 478 newly invokes \`this.\_fileService.stat(file.uri)\` for every explicit file; no corresponding boundary existed in the deleted \`\_getFileTestsToRun\` implementation.

In remote or virtual workspaces, one slow or stalled provider stat delays every already-discovered matching test by up to the shared five-second deadline; a request for F files also creates F concurrent filesystem/provider calls.

**Evidence:** The added \`await raceCancellationError(this.\_fileService.stat(file.uri), discoveryToken.token)\` is included in \`checks\`, and line 491 awaits \`Promise.all(\[...checks, ...selection\])\`. The new \`runs a known healthy file despite a stalled stat\` test asserts exactly 5,000 ms elapsed even though \`/workspace/a.ts\` is already discovered and then runs successfully.

**Suggested direction:** Use in-memory discovery to start known matches immediately. Run existence checks only for unmatched paths or in parallel for later diagnostics without awaiting them before \`runTests\`, while retaining cancellation and bounded diagnostic completion.

### 3. [medium] Preserve lazy selection for unfiltered workspace runs

**Finding ID:** `PERF-779B740C3202`  
**Location:** <code>src/vs/workbench/contrib/testing/common/testingChatAgentTool.ts:535</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** extension-host/controller discovery IPC, provider CPU/I/O, and published test-item allocations  
**Scaling:** Work grows with the number of registered roots and each provider's discovery tree; concurrency is unbounded across roots, while critical-path latency is the slowest root up to the shared five-second timeout.  
**Outcome:** increased test-start latency, provider work, and allocation pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With no \`files\` argument, \`\_getFileTestsToRun\` immediately returned the published root items; with no name filter those roots were passed directly to \`runTests\`, allowing providers to execute without pre-enumerating their trees.  
**Changed behavior:** The no-files path now concurrently expands every expandable controller root, waits for discovery to become idle, and only selects roots that published children before it starts the run.  
**Confidence:** 0.97 — The before/after is direct in the diff: the old no-files branch returned collection roots immediately, while the new branch awaits expansion and idle state for every root. Tests confirm a stalled controller holds a healthy controller for the full five-second deadline. Provider-specific discovery cost varies, which affects magnitude but not the mechanism.

**Causal diff evidence:** RIGHT line 535 adds an awaited root expansion on the no-files path; the deleted code returned \`collection.rootItems\` without expansion.

A normal all-workspace test request now eagerly invokes every controller's discovery work and can wait five seconds for one stalled controller before any healthy tests start; large providers may also enumerate and publish substantial test trees solely to begin an all-tests run.

**Evidence:** RIGHT line 535 awaits \`\_expandRoot\` inside \`Promise.all\` over all root items, followed by \`\_waitForDiscovery\`. The new \`preserves ready workspace controller selection\` test asserts 5,000 ms elapsed when one of two controllers stalls, despite the healthy controller being runnable.

**Suggested direction:** For unfiltered all-workspace requests, keep passing roots directly to \`runTests\` and use the new zero-executed-result handling to classify empty runs. Restrict eager discovery to requests that require enumeration, such as name filtering or unresolved explicit files.

### 4. [medium] Avoid cross-product scans when collecting file diagnostics

**Finding ID:** `PERF-2A18F01D3780`  
**Location:** <code>src/vs/workbench/contrib/testing/common/testingChatAgentTool.ts:580</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU string-prefix comparisons and temporary traversal/allocation work  
**Scaling:** For F requested files the added work is O(sum over files of N×T\_file), plus repeated O(N) collection traversals; it runs once during discovery and again after execution.  
**Outcome:** CPU pressure and increased pre-run/post-run response latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The old explicit-file path used the URI index through \`testsInFile\` and did not rescan the entire workspace collection to construct discovery diagnostics.  
**Changed behavior:** For every requested file, \`\_updateDiscoveryEvidence\` walks every collection item and, for items not matched by URI or the ancestor set, linearly searches all tests already matched to that file. The method is then repeated after the test run.  
**Confidence:** 0.96 — The loops and call count are explicit: for each explicit file, this method traverses the full collection and runs \`file.tests.some\` for unrelated items, and invoke calls it both before and after the run. The repository already documents large per-file test collections as a performance-sensitive case; exact collection sizes per user remain the only magnitude uncertainty.

**Causal diff evidence:** RIGHT line 580 introduces the nested \`file.tests.some\` within the newly added full-collection loop; both invocations of \`\_updateDiscoveryEvidence\` are also added by this diff.

In a monorepo with N discovered tests and T top-level tests in a requested file, diagnostics can perform roughly N×T prefix checks per file, twice per invocation, delaying the tool response and consuming CPU even when the tests themselves are ready.

**Evidence:** RIGHT line 580 uses \`file.tests.some(test =&gt; TestId.isChild(...))\` inside \`for (const item of collection.all)\`. Call sites are lines 523 and 231. The surrounding \`testsInFile\` code explicitly notes that large numbers of tests in one file previously caused long delays (\#235819), establishing this as a realistic collection shape.

**Suggested direction:** Build the relevant set by traversing descendants from the file-matched nodes (and adding ancestors once), or use a prefix tree/index, then do O(1) membership checks during at most one collection pass. Recompute only evidence that can actually change after the run.
