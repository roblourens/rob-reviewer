## Findings (1)

### 1. [medium] Do not cold-subscribe every blocked session row

**Finding ID:** `PERF-257B706E20A6`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:979</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** One wire subscription and potentially full session restoration (database/filesystem and git-state work) per distinct rendered blocked Agent Host session  
**Scaling:** Cost grows linearly with the number of visible session rows carrying git-pull-request-error or git-pull-request-comment icons; same-session consumers are refcount-coalesced, but separate rows target separate session resources and are launched concurrently.  
**Outcome:** A burst of Agent Host IPC and restoration I/O, increasing host contention and resource usage when opening or scrolling the sessions list  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Session row rendering selected the cached PR icon without reading Agent Merge state, so rendering inactive rows issued no Agent Host session subscriptions or cold restores.  
**Changed behavior:** Rendering each blocker-icon row now observes Agent Merge configuration, which retains a full session-state subscription for that row's session.  
**Confidence:** 0.93 — The changed row-to-subscription call path and cold restore behavior are explicit in the repository. The exact number of simultaneously rendered blocked rows varies by viewport and user history, which affects magnitude but not the per-row fan-out mechanism.

**Causal diff evidence:** The added line 979 creates and observes an Agent Merge configuration observable inside each blocker-row render autorun; that observable's new provider implementation acquires a StateComponents.Session subscription on first observation.

Opening the sessions list with many inactive sessions whose cached PR icon is a blocker now starts one Agent Host session subscription per rendered blocked row. For evicted sessions, each subscription can restore the full session and trigger git-state refresh, creating a burst of IPC plus server filesystem/database work that can contend with list interaction and other Agent Host work.

**Evidence:** The added row autorun calls getSessionAgentMergeConfigurationObservable for every rendered row with a PR error/comment icon. That reaches BaseAgentHostSessionsProvider.getAgentMergeClientStateObservable, whose first observer calls \_keepAgentMergeSessionStateAlive and then connection.getSubscription(StateComponents.Session, ...). AgentSubscriptionManager sends a wire-level subscribe for each distinct resource, and AgentService.subscribe restores an uncached session and starts a git-state refresh. References coalesce only for the same session; distinct rows remain distinct cold subscriptions, with no aggregate limiter.

**Suggested direction:** Keep list rendering off the full-session subscription path. Project the small enabled/overrides state into already-loaded session catalog data, or fetch it through a batched/limited list-level mechanism; at minimum avoid launching unbounded cold subscriptions directly from per-row autoruns.
