## Findings (1)

### 1. [high] Avoid replaying the full per-automation fan-out every minute

**Finding ID:** `PERF-BE36439E225E`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/automationsView.ts:283</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub network requests, response bytes, JSON parsing/allocation, and credential/transport work  
**Scaling:** Each poll costs O(R + A + H), where R is all remembered/recent repositories, A is all automation definitions fetched in detail, and H is one history-list request per automation plus active-run detail requests. The cost repeats for the entire time the view is visible; the remembered repository set has no storage bound.  
**Outcome:** Excessive network I/O and background CPU/energy use, with growing refresh duration and rate-limit pressure  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Opening the view performed one explicit full refresh; the same expensive reconciliation was not automatically repeated every minute while the view remained visible. Independent history polling was limited to active/discovery cases.  
**Changed behavior:** The visible view now invokes the aggregate full refresh immediately and again 60 seconds after every completion. That refresh traverses every provider and, for the cloud provider, refreshes both the complete catalogue and complete history.  
**Confidence:** 0.99 — The changed timer and call are explicit and tested at a one-minute cadence; the complete transitive call path and every network boundary are visible in repository code. ETag revalidation may reduce response bytes on warm requests, but it does not remove the per-resource network-call fan-out, so only exact latency and prevalence remain uncertain.

**Causal diff evidence:** RIGHT line 283 adds a background aggregate refresh inside the newly scheduled one-minute loop; before the diff, the constructor issued only the one entry refresh and had no recurring scheduler.

Leaving the Automations view open continuously generates repeated GitHub traffic and credential/serialization work, can consume rate-limit/network/battery budget, and makes each poll increasingly long for accounts that have accumulated repositories and automations. For example, 10 repositories with 5 automations each cause at least 120 remote calls per tick before active-run detail requests (10 visibility + 10 list + 50 detail + 50 history), repeated roughly every minute.

**Evidence:** The added call reaches ProviderAutomationService.refresh -&gt; CloudAutomationStore.refreshCatalogueAndHistory -&gt; GitHubCloudAutomationStore.refreshRepositories and then refreshHistory. For every remembered repository (the storage map is not bounded, plus up to 10 recent workspaces), refreshRepositories performs getRepository, paginated list calls, and api.get for every automation detail in batches of five. refreshHistory then performs listRuns for every cached automation and tasks.get for each active run, with concurrency limited to four. AutomationSummary already exposes updated\_at, but the current path refetches every detail even when summaries are unchanged.

**Suggested direction:** Make the periodic background path incremental rather than calling the full manual-refresh path: use the existing list summaries and their id/updated\_at values to reuse cached details and fetch only new or changed definitions, and schedule history refresh independently so an unchanged catalogue tick does not automatically replay both fan-outs. Preserve the existing full reconciliation for entry/manual recovery and uncertain mutations.
