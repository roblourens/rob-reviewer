# Performance review: agentHost: make agent-host.db authoritative for session state (Block 3a)

[PR #341626](https://github.com/microsoft/vscode/pull/341626) at `ba019dcf7d5e844f6a53c062ab11773e6c138f51`

## Findings (3)

### 1. [high] Coalesce compatibility writes across the peer catalog

**Finding ID:** `PERF-87D0C5213DD5`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostPeerChatStore.ts:1201</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** SQLite transactions and peer-database metadata writes  
**Scaling:** For P changed peers, publication adds P central-state transactions and P extra peer-database mirror writes. The old P metadata writes retain concurrency 4, but the new store writes serialize per session; a legacy catalog can contain 999 peers.  
**Outcome:** increased first-restore and large catalog-update latency from serialized database I/O  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** Compatibility publication wrote each changed peer's full metadata, including working directories, once with setMetadataValues under a concurrency-4 limiter.  
**Changed behavior:** Each peer still gets its metadata transaction, then the added immediate store write commits agent-host.db and flushes that peer's working-directories value back to the same database. The session-state sequencer serializes these cycles.  
**Confidence:** 0.98 — The per-entry call, central transaction, immediate mirror, serialization, 999-entry bound, and import call path are explicit; only storage-dependent elapsed time is uncertain.

**Causal diff evidence:** Added line 1201 places every changed peer in its own immediate central-write-and-mirror cycle after the existing peer metadata write.

Importing or republishing a large legacy peer catalog can add hundreds of serialized commits and duplicate writes before restore continues; at the supported limit this is 999 central transactions plus 999 extra peer writes.

**Evidence:** \_publishCompatibilityState invokes \_writeChatMetadata for every changed entry. That method first awaits peer setMetadataValues, then line 1201 awaits SessionStateStore.write with Immediate. The store queues by session, \_writeCentral calls writeSessionState for every nonempty patch, and Immediate awaits \_flushLocked. reconcileLegacy reaches this publication while importing legacy membership. Tests exercise AGENT\_HOST\_CATALOG\_CHILD\_LIMIT - 1 compatibility entries, and the limit is 1000.

**Suggested direction:** Aggregate changed chat patches into one exclusive central write, include working directories in each peer's existing metadata transaction, then mark those entries mirrored or perform one aggregate flush.

### 2. [medium] Batch checkpoint ownership probes during first-open migration

**Finding ID:** `PERF-3B1101D01279`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostChatRowStore.ts:267</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** serialized SQLite point queries against each peer chat database  
**Scaling:** For P peer databases and C legacy checkpoint rows without event IDs, first open now performs up to P×C awaited getTurnEventId queries; misses and default-chat rows that no peer owns pay the full cross product, while matches pay until their owner is reached.  
**Outcome:** increased session first-open latency and lower restore throughput  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no checkpoint-ownership migration: legacy checkpoint rows stayed in session.db and opening a session did not probe every peer database for every checkpoint row.  
**Changed behavior:** The new first-load row migration reads all checkpoint records, then iterates peers and records and awaits getTurnEventId for each still-unclaimed row; each call executes its own SELECT through the peer database's sequencer before the next comparison can start.  
**Confidence:** 0.97 — The nested loops, one-query implementation, serialization, and restore critical path are directly traced. Exact delay varies with session history and storage speed, but the P×C query count is deterministic for unclaimed event-id-less rows.

**Causal diff evidence:** The added condition at line 267 introduces an awaited per-record SQLite lookup inside both the added peer loop and checkpoint-record loop, on the awaited first-open migration path.

Opening an older session with many peer chats/checkpointed turns can block restore on hundreds or thousands of serialized SQLite round trips before the session is usable.

**Evidence:** AgentService.\_restoreSessionState awaits loadWithCatalog; AgentHostSessionStateStore.\_loadLocked awaits chatRows.moveRows; moveRows awaits \_moveCheckpoints. \_moveCheckpoints loads records once but then nests the peer loop around the record loop, and SessionDatabase.getTurnEventId issues \`SELECT event\_id FROM turns WHERE id = ?1 OR event\_id = ?1 LIMIT 1\` per call. The migration tests establish multiple peers and legacy checkpoint rows, and rows without event IDs are explicitly the ownership-classification case.

**Suggested direction:** Fetch each peer database's turn/event IDs in one query and classify all checkpoint rows in memory (or add a bulk membership API), preserving peer-order ownership and existing copy/foreign-row semantics.

### 3. [medium] Release cached central state during residency eviction

**Finding ID:** `PERF-E04D359D4AEF`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostSessionStateStore.ts:644</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** retained per-session SessionStateModel maps, mirror base/dirty sets, snapshots, URIs, and schedulers  
**Scaling:** Retained memory grows with every distinct session restored during the agent-host process lifetime, rather than with the configured resident-session limit; reopening is warm, but normal idle eviction never removes historical entries.  
**Outcome:** unbounded retained memory and increasing GC pressure in long-lived agent hosts  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no authoritative session-state \`\_records\` cache; normal AgentSessionResidency eviction removed a session's in-memory state, keeping residency bounded.  
**Changed behavior:** Every successful load now inserts a permanent record into \`\_records\`. The new store has an \`evict()\` method that flushes and forgets a record, but normal AgentSessionResidency eviction still only calls AgentService.\_evictSessionState, which removes state-manager/chat contribution state and never calls the new store. Records are forgotten only by explicit store eviction or deletion.  
**Confidence:** 0.96 — The insertion, sole deletion helper, restore path, and residency callback were all traced. Per-session retained byte size varies with metadata/chat count, but lifetime growth by distinct opened sessions is certain.

**Causal diff evidence:** Line 644 adds each loaded session to the new unbounded \`\_records\` map; the PR does not connect this new cache to the existing normal residency-eviction path.

A long-lived host where a user opens more sessions than the residency limit continues retaining central state for all sessions ever opened, defeating the memory bound and causing process memory/GC cost to grow over time.

**Evidence:** \_restoreSessionState calls loadWithCatalog for each restored session, and \_loadLocked stores the resulting record at line 644. AgentSessionResidency invokes its delegate's evictSessionState when releasing idle sessions; AgentService wires that to \_evictSessionState, whose body clears chat/state-manager data but not \`\_sessionStateStore\`. \`\_forget\` is the only \`\_records.delete\` site, reached by explicit \`evict\` and deletion, not normal residency release.

**Suggested direction:** Wire residency release to await \`\_sessionStateStore.evict(session)\` after session data is idle (extending the residency delegate to support async cleanup if needed), so pending mirrors flush and the cache is bounded with the rest of resident session state.
