# Performance review: Update Foundry Local SDK to 2.1.0

[PR #341640](https://github.com/microsoft/vscode/pull/341640) at `4024b18cb0452a9b7e0199786148adedde58fc66`

## Findings (1)

### 1. [medium] Evict superseded dictation runtime versions

**Finding ID:** `PERF-65395CEAD29E`  
**Location:** <code>package.json:148</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** versioned native-runtime bytes on disk and one replacement CDN transfer  
**Scaling:** Each foundry-local-sdk version used for on-device dictation creates another \`&lt;cacheHome&gt;/chatDictationRuntime/&lt;version&gt;\` tree; because only staging and partial-download paths are removed, retained bytes grow linearly with SDK upgrades used on that profile.  
**Outcome:** Persistent duplicate native-runtime storage and repeated full runtime download/write cost after upgrades, eventually increasing disk pressure and risking cache writes failing on constrained profiles.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With the 2.0.1 pin, an already provisioned \`&lt;cacheHome&gt;/chatDictationRuntime/2.0.1\` was a verified cache hit and no new runtime directory or CDN transfer was needed.  
**Changed behavior:** The new 2.1.0 pin is read by \`getRuntimeVersion()\`, stamped into \`product.dictationRuntime\`, and passed to \`ensureFoundryLocalRuntime\`, which now provisions \`&lt;cacheHome&gt;/chatDictationRuntime/2.1.0\`; the existing 2.0.1 directory is left untouched.  
**Confidence:** 0.96 — The cache-key flow and absence of version eviction are explicit in repository code, and first-use reachability is confirmed through the local dictation start path. Exact compressed/uncompressed artifact sizes are not recorded in source, which affects magnitude but not the mechanism.

**Causal diff evidence:** Changing \`foundry-local-sdk\` from 2.0.1 to 2.1.0 at package.json:148 directly changes the versioned cache directory and makes the prior 2.0.1 payload unreachable from the updated product while leaving it retained.

A user who has used on-device dictation before upgrading pays a full native-runtime download/extraction on first use and permanently retains both the old and new ONNX/Foundry payloads. The same accumulation repeats on later SDK updates.

**Evidence:** \`build/dictation-runtime/common.ts:getRuntimeVersion\` reads this exact dependency pin; \`produce.ts\` stamps it into the product; \`LocalTranscriptionService\` passes that version to \`ensureFoundryLocalRuntime\`; and \`foundryLocalRuntime.ts\` derives \`overrideDir = join(cacheRoot, download.version)\`. Repository-wide searches show removals only for staging/temp/partial target paths, with no cleanup of sibling version directories. The payload contains two N-API addons plus Foundry Local, ONNX Runtime, and ONNX Runtime GenAI shared libraries, so this is substantial retained data rather than metadata.

**Suggested direction:** When provisioning 2.1.0 succeeds, prune superseded sibling version directories under \`chatDictationRuntime\` with cross-process-safe, age-based retention (for example, keep the current and recently used version for rollback), rather than deleting only staging data.

### Scenario 1: First on-device dictation after updating from a build that provisioned Foundry Local 2.0.1

The changed runtime version makes provisioning a cache miss, so the CDN download, filesystem write, extraction, verification, and publish are on the critical path to transcription even though audio is buffered meanwhile.
- Scaling input: One native runtime payload for the current platform per SDK version and user profile; model work is one selected model. Concurrent windows can each initiate the same first-use payload download because coalescing is process-local.
- Effective concurrency: Audio appends are serialized. Runtime provisioning coalesces to one promise per library path inside one utility process, but separate VS Code windows have separate utility processes and may download concurrently; a filesystem publish lock prevents conflicting final replacement, not duplicate transfers. NuGet/build concurrency is not involved at runtime.
- Cache behavior: Before the diff, a previously provisioned 2.0.1 directory was a warm verified hit. The 2.1.0 pin changes both CDN and cache keys, producing a cold miss while retaining the 2.0.1 sibling indefinitely. Later 2.1.0 sessions verify the marker/files and are warm hits. In-process requests coalesce; cross-process requests download separately and only serialize final publication.
- Mechanism confidence: High: the changed manifest pin is explicitly the source of the stamped runtime version, the runtime joins that version into the cache path, and no sibling-version eviction exists.

### Scenario 2: Subsequent on-device dictation sessions on Foundry Local 2.1.0

### Scenario 3: Publish-build production of the per-platform dictation runtime

- Critical path: For each supported build target, the publish job copies SDK native files, sequentially downloads two pinned NuGet packages, extracts matching libraries, gzip-compresses the payload, hashes it, performs upload existence checking, and uploads when absent. Packaging then stamps the resulting 2.1.0 URL template.
- Scaling input: Exactly one target per platform build job, two NuGet artifacts per target, and one tarball/CDN object per supported target and SDK version; five target jobs may operate independently in the pipeline.
- Effective concurrency: The two NuGet artifacts are fetched sequentially inside each target build. Different platform jobs may run concurrently; there is no newly introduced per-item Promise fan-out.
- Cache behavior: The NuGet service index is cached only within one \`fetchDependencyLibraries\` invocation. CDN upload uses HEAD-based idempotence for reruns. The version change intentionally selects a new CDN object and does not reuse 2.0.1 bytes.
- Mechanism confidence: High: source establishes exact boundary counts and sequential scheduling.
- Magnitude uncertainty: The newer NuGet/package byte sizes are not present in the diff, so no claim about increased build duration or artifact size is supportable.
- Expensive boundaries:
  - network at <code>build/dictation-runtime/nuget.ts:fetchDependencyLibraries</code>: Resolve the authenticated NuGet service index and download ONNX Runtime plus ONNX Runtime GenAI packages; cardinality: One service-index request and two sequential package downloads per target build, subject to existing bounded retries
    - Introduced by diff: false; previous behavior: The same two calls occurred for versions 1.28.0 and 0.15.2; only artifact versions change to 1.30.0 and 0.17.1; critical-path effect: All downloads and extraction must complete before tarball creation
  - filesystem at <code>build/dictation-runtime/package.ts:buildOne</code>: Copy native SDK files, extract NuGet libraries, gzip the tree, hash and stat the tarball; cardinality: One staging tree and one tarball per target job
    - Introduced by diff: false; previous behavior: Same operations and cardinality for the 2.0.1 payload; critical-path effect: Sequentially required before upload
  - network at <code>build/dictation-runtime/upload.ts:uploadOne</code>: Check and upload the versioned runtime tarball to CDN storage; cardinality: One HEAD decision and at most one upload per target/version
    - Introduced by diff: true; previous behavior: 2.0.1 already addressed existing CDN objects; 2.1.0 requires a new object, as expected for changed native binaries; critical-path effect: Publish completion waits for the versioned artifact to exist
- Verdict: No separate reportable build regression: boundary cardinality and concurrency are unchanged, and producing one new versioned payload is required by the dependency update.

### Scenario 4: Repository dependency installation and postinstall patching

- Critical path: Package installation fetches the new SDK tarball and runs its allowed install script; VS Code postinstall then reads and patches the SDK native loader in root and remote node\_modules when present.
- Scaling input: One pinned package tarball and at most two loader files per repository install.
- Effective concurrency: Controlled by the existing package manager; VS Code's two patch targets are processed sequentially.
- Cache behavior: npm's package cache may serve the 2.1.0 tarball after first fetch; the VS Code patch is marker-idempotent. The lockfile retains the same dependency set and install-script shape as 2.0.1.
- Mechanism confidence: High for repository-owned patching and lockfile dependency shape; low for opaque SDK-internal install work, which is therefore not reported.
- Magnitude uncertainty: The external package's install-script internals and tarball byte delta are not exposed in the supplied repository diff, so an install-time regression cannot be established.
- Expensive boundaries:

    - Introduced by diff: true; previous behavior: The same single package fetch targeted 2.0.1; critical-path effect: Required for dependency installation
  - filesystem at <code>build/npm/postinstall.ts:native loader patch loop</code>: Read, transform, and write up to two SDK native loader files; cardinality: At most root and remote copies; zero writes when already marked
    - Introduced by diff: false; previous behavior: Same bounded, marker-idempotent patching for 2.0.1; critical-path effect: Part of postinstall completion
- Verdict: No reportable install-time performance regression is proven beyond the expected one-time fetch of a newly pinned package.
