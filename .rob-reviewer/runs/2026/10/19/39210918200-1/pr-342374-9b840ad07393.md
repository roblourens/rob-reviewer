# Performance review: Keep tool results when a steering message starts a new turn

[PR #342374](https://github.com/microsoft/vscode/pull/342374) at `9b840ad07393c666e026e3c4c44770136e5e5968`

## Findings (1)

### 1. [medium] Drain held streaming deltas without a synchronous IPC burst

**Finding ID:** `PERF-C322DF5EE98C`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts:2397</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** Per-delta state reductions, string/object allocations, emitter fan-out, and protocol notifications  
**Scaling:** The synchronous drain grows with every root or subagent signal produced while an edit/resource/shell-output completion is pending, up to the five-second hold; assistant.message\_delta maps one-for-one to ChatDelta signals, so a streaming response can contribute dozens or hundreds of entries.  
**Outcome:** A concentrated CPU and IPC burst that blocks the agent-host event loop and makes the chat update in a visible stall/jump instead of streaming smoothly.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, each signal was forwarded immediately to \`onDidSessionProgress\`; model deltas and subagent progress were reduced and broadcast incrementally as they arrived, with no backlog replay in one event-loop turn.  
**Changed behavior:** While a pre-steering tool completion is being persisted, the session now buffers all unrelated signals for up to five seconds and then fires the full backlog synchronously without coalescing or yielding.  
**Confidence:** 0.96 — The buffering, five-second bound, one-signal-per-delta mapping, synchronous emitter/reducer chain, and one-message-per-envelope transport are directly traced in repository code and the gated-write test proves the changed critical path. Exact chunk counts and hitch duration vary by model and filesystem speed, which affects severity but not the mechanism.

**Causal diff evidence:** The PR adds \`hold.signals.push(signal)\` for every non-preempted-turn-result and then replays the entire array in the added \`for (const signal of hold.signals)\` loop at line 2395, calling \`\_onDidSessionProgress.fire(signal)\` synchronously at line 2397.

If a user steers just as a file edit, resource persistence, or spilled shell-output capture is slow (common on remote or busy filesystems), the steering response and concurrent subagent streaming can accumulate for as long as five seconds. Release then performs all reductions and sends all client messages back-to-back, causing an agent-host/UI hitch and a burst of IPC exactly when the delayed response finally becomes visible.

**Evidence:** \`\_beginSteeringTurn\` starts a hold whenever \`preempted.hasPendingToolCompletions\` and caps it at 5 seconds. \`\_emitMarkdownDelta\` converts each SDK \`assistant.message\_delta\` into a distinct ChatDelta signal. The added release loop synchronously fires every buffered signal. The traced consumer in \`AgentSideEffects\` synchronously calls \`dispatchServerAction\` per signal; the chat reducer appends each delta with \`part.content + action.content\`, and \`ProtocolServerHandler.\_broadcastAction\` sends each resulting envelope as a separate top-level transport message to every relevant client. The new test \`completes a file edit whose result is still being recorded when steering preempts the turn\` explicitly confirms that even the steering response remains absent until the gated write releases.

**Suggested direction:** Preserve ordering with a draining queue that yields between bounded batches, and coalesce adjacent ChatDelta/ChatReasoning entries for the same chat/turn/part before dispatch. Keep new arrivals queued until the drain completes so they cannot overtake held lifecycle boundaries.

### Scenario 3: Abort, stop, or dispose while steering signals are held

- Critical path: Abort computes which newly started turns remain unfinished, drops those signals, and synchronously releases the rest before beginning the provider abort. Dispose synchronously releases the entire hold before teardown. Thus the queued scan/replay is on stop/disposal latency.
- Scaling input: Number of signals accumulated during the active hold and number of turn boundaries represented in them.
- Effective concurrency: Abort performs two linear passes to classify and release signals; release invokes synchronous listeners serially. There is no yield or coalescing before provider abort or disposal continues.
- Cache behavior: No cache is involved. The queue is bounded by the five-second timeout and is cleared once, while the timeout's later callback becomes a no-op after release.
- Mechanism confidence: High: both new lifecycle calls synchronously invoke the added release loop; downstream action processing is synchronous.
- Magnitude uncertainty: Abort during the short hold is less frequent than normal release, and filtering can reduce the backlog. Dispose may still flush all queued deltas, so the same burst mechanism remains possible.
- Expensive boundaries:
