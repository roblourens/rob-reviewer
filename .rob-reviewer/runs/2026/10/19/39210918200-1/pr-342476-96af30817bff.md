# Performance review: chat: stop Copilot connector connect polling on declined or failed consent

[PR #342476](https://github.com/microsoft/vscode/pull/342476) at `96af30817bffb575a88cb5fffa4d33525cf0a629`

## Findings

No high-confidence performance findings.

## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts:437` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts:419`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/aiCustomization/copilotConnectorsService.ts`  
**Introducing commit:** `4ffbb26a9fe3a00f5cf7107f3f108f7469b56ffd`  
**Mechanism family:** `repeated-work`  
**Performance category:** `network`  
**Confidence:** 0.99

**Mechanism:** A terminal connector authorization failure remained inside a five-minute polling loop, issuing one full cache-disabled catalog HTTP GET every two seconds even though no future poll could make that attempt succeed.

**Symptom:** Declined or failed consent kept the UI action pending for five minutes and generated roughly 150 unnecessary catalog requests per attempt.

**Fixed behavior:** The new status switch throws as soon as an authoritative `error` is observed (and after `pending` transitions to `not_connected`), ending the connection action and preventing all subsequent two-second catalog refreshes for the remainder of the five-minute window.

**Evidence:** Before the PR, connect() entered a five-minute loop after the connection PUT and only returned when a refreshed catalog showed `connected`; every iteration awaited refresh(), whose request({ type: 'query' }) crosses the connectors IPC channel and performs a cache-disabled HTTP GET /plugins. connectionPollInterval is 2 seconds and connectionTimeout is 5 minutes, so an already-terminal error/decline still performed about 150 serialized GETs. The added tests establish the cardinality directly: a still-pending attempt reaches 152 total requests, while terminal errors now stop at 3 total requests and a pending-to-declined transition stops at 5.

- Critical path: The initial catalog GET, connection PUT, consent-page open, and catalog polls run until the terminal status is observed. The added branch now rejects immediately instead of holding the action open for the remaining five-minute timeout.
- Scaling input: Savings scale with remaining timeout after the terminal state: up to about 150 catalog GETs per failed attempt at the two-second interval. Catalog parsing per removed GET is bounded to 1,000 connectors and responses to 5 MiB.
- Effective concurrency: Requests remain serialized within each action. Multiple independently initiated connector operations may overlap, but each terminal attempt now releases its polling activity early; no new burst or limiter change is introduced.
- Cache behavior: Polling deliberately bypasses the service freshness cache and network cache, so every avoided iteration is a real IPC/network request. There is no negative-cache state; terminal status itself now ends this operation.
- Mechanism confidence: Very high: terminal branches, timers, cache settings, request path, and request-count tests all agree.
- Magnitude uncertainty: Prevalence of consent failures and response payload sizes is unknown, but the removed request count and five-minute latency are directly established by constants and tests.
- Expensive boundaries:

  - network at <code>src/vs/platform/copilotConnectors/common/copilotConnectorsRequestService.ts:71 CopilotConnectorsRequestService.doRequest</code>: Performs cache-disabled catalog GETs and the connection PUT.; cardinality: After the diff, one authoritative error poll ends the attempt; a decline ends after the pending-to-not\_connected poll.
