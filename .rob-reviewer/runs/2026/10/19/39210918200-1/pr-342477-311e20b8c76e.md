# Performance review: connectors: make unknown connector status actionable instead of "Checking…" forever

[PR #342477](https://github.com/microsoft/vscode/pull/342477) at `311e20b8c76e939be4f3b2e1b435a540b5ec4ca0`

## Findings (1)

### 1. [medium] Batch connector reconciliation before notifying the UI

**Finding ID:** `PERF-0B7EC4F4B47D`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/customizationMarketplaceInstallService.ts:1009</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** CPU work and DOM/tree nodes rebuilt by MCP and marketplace views  
**Scaling:** For N recorded connectors and M visible MCP/tree entries, the account-wide check produces up to N independent install-service events, each triggering O(M) filtering and tree reconstruction, for O(N×M) synchronous UI work.  
**Outcome:** Repeated full-list reconstruction increases completion latency and can cause dropped frames when checking an account with several recorded connectors and a sizable MCP list.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no account-wide explicit check that transitioned all unknown connector records together, so this bulk unverified-to-resolved path and its per-record UI notification burst did not exist.  
**Changed behavior:** The new check reconciles all applicable connector records after one catalog refresh; reconcileRecords runs reconcileRecord for every record, and each changed record immediately calls emitChange rather than publishing the completed batch once.  
**Confidence:** 0.97 — The added bulk call, per-record synchronous emissions, immediate observable delivery, and full-tree render path are directly traced in repository code. Only the exact frame-time cost and typical connector/MCP counts are uncertain; the multiplicative mechanism and trigger are not.

**Causal diff evidence:** RIGHT line 1009 newly invokes \`await this.reconcileRecords(this.getApplicableConnectorRecords())\` for the account-wide check, creating the collection-wide state transition whose existing per-record \`emitChange()\` behavior fans out into repeated full UI renders.

Clicking Check Connection with multiple recorded connectors can rebuild the entire MCP list once per connector before the action completes. This is especially visible in profiles with several connectors and dozens or more local, runtime, gallery, plugin, and provider MCP entries.

**Evidence:** The added await at line 1009 passes every applicable connector record to reconcileRecords. reconcileRecords maps them to reconcileRecord, whose connector branch is synchronous and whose changed-state branch calls emitChange once per record (lines 507-556). emitChange invalidates the snapshot and fires an Emitter; McpListWidget observes that event in an autorun and calls filterServers (lines 2139-2142), which reconstructs all server matchers/entries and calls renderMcpTree, including two list.setChildren calls (lines 2967-3068). Observable event delivery uses a separate synchronous transaction for each fire, so these renders are not coalesced.

**Suggested direction:** Reconcile the connector records while suppressing per-record notifications, then invalidate the snapshot and emit one change after the batch is complete (including a single final notification on failure/cancellation as needed). Preserve the existing start/end checking notifications and avoid exposing partial per-connector completion states.
