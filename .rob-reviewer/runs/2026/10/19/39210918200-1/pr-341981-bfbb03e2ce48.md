<summary>Reviewer scenario analysis</summary>

**Relevant issue families:** synchronous-ui-work, repeated-work

### Scenario 1: Two chats shown side by side while one chat completes and the peer remains in progress

- Critical path: A provider-fed chat status observable invalidates that chat header's existing synchronous autorun; the autorun updates the cached status icon before the next paint. No subprocess, IPC, filesystem, database, or network operation is reached by the changed header code.
- Scaling input: The number of mounted visible chat headers and status transitions. Each changed chat status affects its own header; before the diff, aggregate session status could also invalidate peer headers, while activeChat.status was already observed in each header for title/editability.
- Effective concurrency: One synchronous autorun per mounted header. StatusIcon coalesces identical glyphs through \_currentCacheKey; a real status/glyph transition schedules at most two animation-frame callbacks and one 220 ms cleanup timer for that header. There is no async fan-out or shared queue.
- Cache behavior: Cold header creation builds one icon. Warm updates with the same glyph recolor the active element without rebuilding it; status changes swap one icon and dispose the outgoing one. The diff does not alter cache keys or lifecycle.
- Mechanism confidence: High: the changed line replaces session.status.read with activeChat.status.read, and the same autorun already reads activeChat.status later in \_updateHeader. SessionStatusIcon source confirms cached DOM behavior and no external boundary.
- Magnitude uncertainty: Exact numbers of simultaneous visible chat groups and status transitions vary, but work is bounded per mounted header and the dependency change reduces rather than increases peer invalidations.
- Expensive boundaries: none found
- Verdict: No reportable performance regression. The intended extra icon transition occurs only when that header's displayed chat status changes, and peer-chat aggregate invalidations are removed.

### Scenario 2: Single-group session header follows the active chat while another chat in the session continues running

- Critical path: Changing the active chat or its status synchronously reruns SessionHeaderBar.\_updateHeader and updates title, classes, ARIA text, and the cached icon on the UI thread. The changed line introduces no external boundary and does not add a new autorun dependency because activeChat.status was already read for title selection.
- Scaling input: Active-chat switches and status transitions within one open session, independent of total session history except existing title ancestor lookup. The diff does not change ancestor traversal or collection cardinality.
- Effective concurrency: A single synchronous autorun for the mounted session header; active-chat changes are serialized by the observable transaction mechanism, with no concurrent I/O or worker activity introduced here.
- Cache behavior: SessionHeaderBar resets the icon cache only when context identity changes. Within one context, same-glyph updates reuse the active DOM node and status transitions retain outgoing DOM only for the existing bounded cross-fade timeout.
- Mechanism confidence: High: SessionHeader passes session.activeChat into the bar, and the inspected call path reaches only synchronous observable reads and cached DOM rendering.
- Magnitude uncertainty: Sessions may contain varying numbers of chats, but the changed status selection is O(1) and does not traverse that collection.
- Expensive boundaries: none found
- Verdict: No reportable performance regression; the change alters which already-observed scalar status is rendered without adding repeated work, retention, or boundary calls.

### Scenario 3: Header context temporarily has no chat

- Critical path: The header falls back to reading session.status and renders through the same synchronous cached icon path. This fallback behavior is unchanged by the diff.
- Scaling input: One header update per session status transition; no collection scaling is introduced.
- Effective concurrency: One synchronous autorun, no asynchronous work or external boundary.
- Cache behavior: Existing icon cache and bounded cross-fade behavior are unchanged.
- Mechanism confidence: High: the conditional's false branch is the exact pre-diff session.status.read call.
- Magnitude uncertainty: This state may be uncommon for active sessions, but the performance behavior is directly unchanged.
- Expensive boundaries: none found
- Verdict: No regression because the no-chat execution path preserves prior work and frequency.

**Summary:** Reviewed the complete two-file diff and traced the changed production autorun through SessionHeader, ChatHeader, and SessionStatusIcon. The active-chat status read adds no new invalidation source, icon updates are cached and lifecycle-bounded, peer aggregate invalidations are reduced, and no expensive process/IPC/filesystem/database/network boundary is introduced. Test-only observable changes and DOM assertions do not affect product runtime.
