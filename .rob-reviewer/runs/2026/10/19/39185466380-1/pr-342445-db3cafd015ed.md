## Performance regression fixes detected (1)

### 1. eager-work

**Fix location:** `src/vs/platform/agentHost/node/agentSideEffects.ts:1615` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentSideEffects.ts:485`  
**Introducing path:** `src/vs/platform/agentHost/node/agentSideEffects.ts`  
**Introducing commit:** `44065855e430e776bafc28fe7bd69f696a8baf58`  
**Mechanism family:** `eager-work`  
**Performance category:** `network`  
**Confidence:** 0.97

**Mechanism:** A client tool result that required user confirmation was immediately delivered to the provider, resolving its pending tool handler and starting a continuation model request before approval; denied results could therefore consume provider/network work that should never have started.

**Symptom:** An extra continuation model request and associated model inference/network latency could run while the UI was still waiting for result approval, and become entirely wasted when the user denied the result.

**Fixed behavior:** The changed helper reads the reduced tool-call state, suppresses provider notification while status is PendingResultConfirmation, and forwards exactly once after approval or denial. This removes the eager provider continuation/model-network request from the user-confirmation wait path and also suppresses duplicate completion notifications during that wait.

**Evidence:** In the base revision, every server-origin ChatToolCallComplete reached \_notifyClientToolCallComplete at line 485, which immediately called agent.onClientToolCallComplete and resolved the provider's parked client-tool handler. The Copilot implementation routes that result into the pending SDK tool call, allowing the provider to issue its continuation model request. The existing E2E scenario records model request bodies and establishes that the old call occurred while the tool state was still PendingResultConfirmation; the changed guard at line 1615 now returns while that state is pending and the new ChatToolCallResultConfirmed route resumes only after a decision.

### Scenario 1: A client- or server-origin client-tool result requiring confirmation arrives on a default or peer chat and is later approved.

Progress intentionally waits on the user's confirmation. The confirmation action is then reduced, the helper looks up the completed tool call, and the provider callback resolves the parked tool handler; the provider's continuation/model request is downstream of approval rather than completion.
- Scaling input: One helper invocation per completion and per confirmation. Each invocation searches the active turn's responseParts linearly; effective cardinality is the number of response parts in that single active turn, not all chats or sessions. The reducer already performs a full responseParts traversal for the same action, so the PR adds one inexpensive in-memory traversal, not extra boundary calls.
- Effective concurrency: Action reduction and side effects are synchronous for each dispatched action. Each confirmation resolves one pending tool handler; there is no collection-wide Promise.all or aggregate network burst.

### Scenario 2: A result requiring confirmation is denied, for client- or server-origin actions on default or peer chats.

- Critical path: Completion is reduced and withheld. On denial, the reducer changes the tool call to ResultDenied cancellation, the helper creates a small failure result without denied content, and the provider callback resolves the parked tool handler so the turn can handle the failure.
- Scaling input: One state lookup and one small failure object per denied tool call; denied result content is referenced in protocol state but is not copied into the provider failure.
- Effective concurrency: One synchronous decision action resolves one parked call. Independent chats can progress independently, but this diff adds no shared fan-out or unbounded scheduling.
- Cache behavior: No external cache. The active-turn state is the coalescing authority; absent or nonmatching state suppresses forwarding.
- Mechanism confidence: High: reducer cancellation state and all three provider callback implementations were traced.
- Magnitude uncertainty: Provider behavior after receiving a failure varies, but the changed timing and one-call cardinality are established.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:1631-1649 through provider continuation</code>: Resume the provider with a synthetic denial failure, which may lead to one continuation model request.; cardinality: At most one continuation per denied tool call; pending and duplicate completion actions do not cross the provider boundary.
    - Introduced by diff: false; previous behavior: The provider had already been resumed with the successful/denied content at completion time, before the denial; the denial action itself did not add a second provider call.; critical-path effect: Runs only after the user decision and is required to unblock the parked provider tool call.
- Verdict: No regression. Boundary cardinality remains one but moves after the user decision, avoiding speculative provider work and avoiding serialization of denied content into the provider continuation.

### Scenario 3: A normal client-tool completion does not require result confirmation, including duplicate or stale completion actions.

- Critical path: After the existing reducer traversal, the changed helper performs a second active-turn responseParts lookup, then immediately invokes the same provider callback as before. A stale completion whose authoritative state is already Completed may still be forwarded as before, while duplicates arriving during PendingResultConfirmation are newly suppressed.
- Scaling input: The added CPU work is O(responseParts in the active turn) per tool completion. It neither clones result content nor scans historical turns, sessions, or chats.
- Effective concurrency: Per-action synchronous execution; downstream provider work is controlled by each provider's pending-call map/deferred, not launched in a collection burst.
- Cache behavior: Resident in-memory state only. Provider/session map misses stop immediately; no retries or negative-cache changes occur.
- Mechanism confidence: High for the extra scan and unchanged boundary count; low evidence of meaningful magnitude, so it is not reportable.
- Magnitude uncertainty: Very large synthetic turns increase scan cost, but no realistic cardinality or measured duration makes this additional single array scan user-visible.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/agentSideEffects.ts:1620-1649 through Copilot/Claude/Codex pending-tool handlers</code>: Resume the provider tool handler and permit its continuation request.; cardinality: One callback per accepted normal completion action, unchanged from before; no loop or chat-wide fan-out is introduced.
    - Introduced by diff: false; previous behavior: The completion directly used action.result and invoked the same provider callback without the additional responseParts lookup.; critical-path effect: Required for the provider turn to continue; the new state scan is synchronous but only over one active turn.
- Verdict: No actionable performance regression. The only added cost is a bounded in-memory lookup alongside an existing reducer-wide traversal, with unchanged I/O/network cardinality.
