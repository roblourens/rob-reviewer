**Relevant issue families:** repeated-work, boundary-fanout, serialization-allocation, cache-lifecycle

### Scenario 1: Open or explicitly mark a recorded cloud conversation read/unread while its environment is connected but no longer advertises that chat

- Critical path: The UI read-state request performs an in-memory session/map lookup and backend-chat lookup, updates the cached chat observable, and fires one session-change event. The later cache serialization/storage write occurs on the storage service's onWillSaveState event and is off the interaction's critical path.
- Scaling input: One main-chat lookup and one changed-session event per actual state transition. The main chat uses the default-chat branch, so backend resolution does not scan the chat collection; persistence is coalesced across changes and scales with the existing cached-session snapshot only at save time.
- Effective concurrency: Each request runs synchronously through local mutation; there is no network concurrency. Multiple cache changes are coalesced by the dirty flag into the next storage save.
- Cache behavior: Warm connected state consults \_lastSessionStates and sees no advertised default chat; if no authoritative state exists, lookup falls back to the session cache. Persisted local state is restored when the provider is recreated. Repeating the same read value is a no-op and does not dirty the cache.
- Mechanism confidence: High: the changed guard, constant-time main-chat lookup, local event path, and deferred persistence listener are directly visible in the traced code.
- Magnitude uncertainty: The number of cached sessions serialized at save time varies by user, but this work is deferred, coalesced, and already the provider's normal offline persistence mechanism.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_onDidChangeSessionsImmediately/onWillSaveState listeners (lines 4432-4463)</code>: Serialize and persist the dirty session-cache snapshot on the next storage save/flush; cardinality: At most one coalesced cache persistence pass per storage save interval after one or more actual read-state changes; repeated requests for the already-current state return before firing the change event
    - Introduced by diff: true; previous behavior: With a connection present, the old branch entered the host path and failed backend-chat resolution before changing state, so this connected-missing-chat case did not dirty or persist the local cache; disconnected recorded chats already used this deferred persistence path; critical-path effect: Deferred until storage save/flush, so it does not block the read-state interaction
- Verdict: No reportable regression. The diff intentionally replaces a failing remote route with bounded local work and coalesced persistence; it adds no boundary fan-out or critical-path I/O.

### Scenario 2: Mark a live cloud chat read/unread while the connected host advertises its opaque backend URI

- Critical path: The request first resolves the advertised backend resource, then the existing superclass path validates state, resolves it again, updates the local observable optimistically, and dispatches one action to the connected host. Dispatch remains the interaction's only expensive boundary and is not awaited for confirmation.
- Scaling input: One user/open-triggered state request. For the default main chat, backend resolution returns the advertised default directly; peer-chat lookup can scan that session's chat summaries, but the diff adds only one such lookup per request and does not multiply requests.
- Effective concurrency: One fire-and-forget protocol dispatch per request; the diff adds no Promise.all, queue, retry, or concurrent burst.
- Cache behavior: The authoritative connected session snapshot supplies the backend URI. The local adapter is updated optimistically and marked dirty for the existing deferred cache persistence. No new cache key or negative cache is introduced.
- Mechanism confidence: High: both the new guard and unchanged superclass dispatch path are explicit, and the regression tests confirm two requests produce exactly two actions.
- Magnitude uncertainty: Peer-chat catalog size may vary, but normal main-chat read marking takes the constant-time default path and the extra URI parse is bounded per interaction.
- Expensive boundaries:
  - network at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:setChatReadState (lines 7014-7048)</code>: Dispatch one ChatIsReadChanged protocol action to the connected cloud agent host; cardinality: One dispatch per accepted chat read-state request; no collection-wide fan-out is added by this diff
    - Introduced by diff: false; previous behavior: Before the diff, every connected read-state request entered the same superclass path and issued the same single dispatch when the backend chat existed; critical-path effect: The dispatch call is synchronous/optimistic and does not await a remote response
- Verdict: No reportable regression. Existing network cardinality and concurrency are unchanged; the extra in-memory lookup/URI parse is bounded and not a realistic performance issue.

### Scenario 3: Mark a recorded cloud conversation read/unread while disconnected, including provider recreation from persisted state

- Critical path: The existing local path looks up the session/chat, updates state, and emits one change event. Cache persistence remains deferred to storage save; provider recreation synchronously hydrates the existing persisted cache without a network call.
- Scaling input: One map/session lookup per read-state request; provider hydration scales with the pre-existing number of persisted session summaries, unchanged by the diff.
- Effective concurrency: Local requests are synchronous; storage saving is coalesced by the existing dirty flag, with no new parallel boundary operations.
- Cache behavior: Cold construction reads the persisted summary cache; warm repeated same-state requests return early. No remote negative-cache retry behavior is added.
- Mechanism confidence: High: connection short-circuiting means the new backend lookup is not evaluated in the disconnected case, leaving behavior unchanged.
- Magnitude uncertainty: Persisted session count varies, but neither load cardinality nor serialization placement changes for this scenario.
- Expensive boundaries:
  - other expensive boundary at <code>src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts:\_enableSessionCachePersistence/\_loadCachedSessions and onWillSaveState</code>: Persist or reload the existing session-cache snapshot through the storage service; cardinality: One coalesced save per storage save interval and one cache load per provider construction
    - Introduced by diff: false; previous behavior: The old condition already selected this exact local persistence path whenever no connection existed; critical-path effect: Saving is deferred; loading is part of provider construction as before the diff
- Verdict: No performance change: short-circuit evaluation preserves the previous disconnected path exactly.

**Summary:** Completed the performance pass over both changed files and traced read-state routing, backend-resource resolution, session-change persistence, and remote dispatch. No high-confidence actionable performance regression was introduced, and the PR is a correctness fix rather than a demonstrated performance-regression fix.
