## Findings (1)

### 1. [medium] Select the sender before prelaunching the SDK session

**Finding ID:** `PERF-AEE61C6F1CD7`  
**Location:** <code>src/vs/platform/agentHost/node/copilot/copilotAgent.ts:6739</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** SDK session destruction, session resume calls, and replacement runtime/configuration objects  
**Scaling:** One redundant destroy/resume is added to a prepared first send whenever sender preference selects a structurally different same-name tool; thereafter the same lifecycle cost can recur once per sender/schema switch because chat turns are serialized.  
**Outcome:** Blocked prompt critical path and increased turn-start latency  
**PR causality:** <code>introduced</code>  
**Previous behavior:** \`prepareTurn\` created the deferred SDK session once and \`sendMessage\` retained the insertion-order client-tool snapshot, so this scenario proceeded directly to the SDK send without immediately destroying and resuming the new runtime.  
**Changed behavior:** A prepared first turn is launched using insertion-order tool definitions, then the new sender preference changes the selected definition during \`sendMessage\`; \`\_refreshSessionConfiguration\` detects \`clientToolsChanged\`, destroys that newly launched runtime, and resumes the same SDK session with the sender's schema before sending.  
**Confidence:** 0.99 — The changed call order, refresh comparison, destroy/resume implementation, and new test's exact create-then-resume sequence are all directly evidenced. Only prevalence of multiple clients contributing incompatible same-name definitions is uncertain, so severity is bounded rather than mechanism confidence.

**Causal diff evidence:** The added call at \`copilotAgent.ts:6739\` changes the preferred tool contributor only inside \`sendMessage\`, after \`prepareTurn\` may already have launched the SDK session. The added regression test explicitly records \`\[create(toolA), resume(toolB)\]\` for one prepared first send from client B, proving that this line invalidates the just-created snapshot and invokes the existing refresh/restart path.

When two connected clients expose the same tool name with different schemas and the first sender is not the insertion-order winner, the first prompt waits for two SDK session startups instead of one. The overlap from \`prepareTurn\` is discarded, increasing time-to-model-response; alternating senders can repeat the destroy/resume cost at later turn boundaries.

**Evidence:** \`prepareTurn\` calls \`\_ensureResolvedChatSession\` without knowing or setting \`senderClientId\`. On the subsequent serialized send, line 6739 updates the preferred client; \`toolsForChat\` now picks that client's definition, \`getRestartReason\` returns \`clientToolsChanged\`, and \`\_refreshSessionConfigurationWithAnchor\` awaits \`\_destroyLiveSession\` followed by \`\_resumeSession\` on the prompt critical path. The added \`send and resume refresh conflicting client schemas...\` test demonstrates one logical first send producing \`create(toolA)\` immediately followed by \`resume(toolB)\`.

**Suggested direction:** Make preparation sender-aware: pass \`senderClientId\` through the existing \`prepareTurn\` boundary and set the preferred client before \`\_ensureResolvedChatSession\`. If that boundary cannot carry sender identity, skip speculative prelaunch when incompatible duplicate tool definitions make the launch winner ambiguous. Either approach launches the required sender schema once and preserves the new routing semantics.

- Cache behavior: The applied snapshot acts as the warm-session state. Structural equality avoids refreshes for identical reconnects and repeated sends from a sender whose selected schema matches the applied one; a sender selecting a different same-name schema is a deliberate cache miss and restarts the runtime.
