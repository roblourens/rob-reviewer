## Findings (1)

### 1. [medium] Cache dispatch observers instead of sorting them per streamed action

**Finding ID:** `PERF-88C3E887459F`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostChatContributionsService.ts:164</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Array allocations and comparison/sort CPU over the complete contribution registry.  
**Scaling:** Cost is O(A × C log C), where A is the number of emitted action envelopes (including token/reasoning/tool deltas) and C is the registered contribution count; concurrent chats multiply A. The current built-in graph has roughly 17 contributions but only three observers for this hook.  
**Outcome:** Increased synchronous CPU work and GC pressure on response streaming, with cost multiplied by action frequency and concurrent active chats.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The envelope listener directly ran tightly filtered input-needed, usage, and session-flag logic; it did not allocate and sort the contribution registry for every streamed action. Contribution sorting was limited to less frequent lifecycle/client-dispatch hooks.  
**Changed behavior:** Every server or client action envelope now synchronously allocates and sorts the complete contribution registry before filtering down to the three contributions that implement \`onDidDispatchAction\`.  
**Confidence:** 0.98 — The synchronous call path is explicit: \`\_dispatchActionForSession\` dispatches every streamed action, \`AgentHostStateManager\` fires \`onDidEmitEnvelope\` before returning, and the new listener calls \`didDispatchAction\`, whose added loop invokes the allocation-and-sort helper. Built-in registration and documentation establish roughly 17 contributions while only three implement this hook; exact stream chunk counts vary by provider but the per-envelope mechanism is certain.

**Causal diff evidence:** The added \`didDispatchAction\` loop at RIGHT line 164 calls the existing \`\_getOrderedContributions()\` helper for every envelope; that helper spreads the entire registration map into a new array and sorts it. The new call site in \`AgentSideEffects\` invokes this hook unconditionally from \`onDidEmitEnvelope\`, including \`ChatDelta\`, \`ChatReasoning\`, and tool-delta actions.

Long or highly incremental agent responses do needless synchronous CPU work and short-lived allocation for every streamed chunk, increasing agent-host CPU/GC pressure and potentially reducing streaming throughput or responsiveness when several chats stream concurrently.

**Evidence:** \`AgentHostChatContributions.didDispatchAction\` iterates \`\_getOrderedContributions()\` at line 164. \`\_getOrderedContributions()\` creates \`\[...this.\_registeredContributions.values()\]\` and sorts it on every call. \`AgentSideEffects\` now calls \`didDispatchAction\` for every emitted envelope, and streamed \`ChatDelta\` actions are dispatched once per provider chunk. Therefore ordinary response streaming repeats an O(C log C) sort plus array allocation per chunk even though most contributions are immediately skipped.

**Suggested direction:** Cache the ordered registrations and invalidate that cache only when contributions are registered or removed; preferably cache a hook-specific ordered observer list so \`didDispatchAction\` iterates only its three implementers. This preserves ordering and failure isolation without per-envelope sorting/allocation.
