# Performance review: Unify new session and active session composer

[PR #342683](https://github.com/microsoft/vscode/pull/342683) at `492b538f3ecf13cb1e79a37b5712fc23241b956b`

## Findings (4)

### 1. [medium] Restrict the composer resize observer to width changes

**Finding ID:** `PERF-C977DA57704C`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sharedChatInputComposer.ts:320</code> (<code>RIGHT</code>)  
**Performance category:** <code>layout</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** Synchronous DOM/editor, toolbar, and hidden-list layout work  
**Scaling:** A full ChatWidget layout is repeated whenever the auto-sized composer changes height, including wrapped/new input lines, attachment rows, notices, prompt animation wraps, and host width changes.  
**Outcome:** Extra main-thread layout work on interactive input paths, causing typing/attachment jank and lower rendering throughput.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous composer handled editor content-height changes by resizing and laying out its CodeEditorWidget, while viewport layout called the composer layout separately; it did not relayout a full chat widget/list when its intrinsic input height changed.  
**Changed behavior:** The new observer watches the auto-height outer composer and calls \_layoutWidget for every resize. \_layoutWidget invokes ChatWidget.layout, which reruns ChatInputPart.layout and ChatListWidget.layout even when only the input's height changed.  
**Confidence:** 0.99 — The observed element is explicitly auto-height and the synchronous call chain to input/list layout is direct. The exact frame cost varies by platform and toolbar contents.

**Causal diff evidence:** Added line 320 introduces an unfiltered ResizeObserver callback that performs whole-widget layout for both width and intrinsic height changes; no equivalent whole-widget callback existed in NewChatInputWidget.

Typing until the prompt wraps, adding context pills, or showing a notice causes the already-laid-out ChatInputPart to be laid out again together with the hidden transcript surfaces.

**Evidence:** sharedChatInputComposer.css:14 gives .interactive-session height:auto, so input-height changes resize the observed container. The callback at line 320 calls \_layoutWidget, which calls widget.layout. ChatWidget.layout (chatWidget.ts:4277-4295) runs inputPart.layout and list layout. ChatWidget's own input-height autorun explicitly calls only \_layoutListForInputHeight and warns that re-entering inputPart.layout creates a layout loop (chatWidget.ts:2739-2752), but this outer observer bypasses that safeguard.

**Suggested direction:** Track the last measured width and call widget.layout only when width changes (or rely on the host layout callback); let ChatWidget's existing input-height path update list-side sizing without re-entering ChatInputPart.layout.

### 2. [medium] Add an input-only render path instead of constructing a hidden transcript

**Finding ID:** `PERF-C6EEE4902F25`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/sharedChatInputComposer.ts:213</code> (<code>RIGHT</code>)  
**Performance category:** <code>startup</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** ChatListWidget DOM, list renderers, widget contributions, listeners, and retained objects  
**Scaling:** The cost is paid once for every new-session or new-chat view and remains retained for each hidden view kept in the sessions grid.  
**Outcome:** Higher Agents window/new-chat creation latency and increased retained memory/GC pressure.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The removed NewChatInputWidget created only the composer editor, attachments, notices, pickers, and related input services; it did not construct a chat transcript list.  
**Changed behavior:** Each composer now instantiates and renders a full ChatWidget. ChatWidget.render unconditionally calls createList to construct ChatListWidget and then instantiates every ChatWidget.CONTRIBS entry, while the new CSS merely hides .interactive-list and the welcome DOM. The composer also marks the widget visible even when inputVisible later hides its container.  
**Confidence:** 0.98 — The changed constructor and unconditional transitive render path are explicit. Exact milliseconds and retained bytes vary by registered renderers/contributions, which affects severity but not the mechanism.

**Causal diff evidence:** Added line 213 replaces the former input-only NewChatInputWidget with a full ChatWidget instance; the old composer path had no ChatListWidget construction.

Opening the Agents window or adding a new-session/new-chat view synchronously builds a transcript/list subsystem that this surface can never display; retaining multiple hidden views retains one such object graph per view.

**Evidence:** The added createInstance(ChatWidget) at line 213 reaches ChatWidget.render, which unconditionally invokes createList (chatWidget.ts:1214); createList constructs ChatListWidget and its renderer/event graph (chatWidget.ts:2316-2350), and render then maps all ChatWidget.CONTRIBS (chatWidget.ts:1295). sharedChatInputComposer.css:8-15 only applies display:none/auto sizing, so it does not avoid this construction. NewChatView constructs and renders this composer for each new-session/new-chat view (chatView.ts:157-161).

**Suggested direction:** Add a ChatWidget input-only option that still creates/registers ChatInputPart but skips welcome/transcript DOM, ChatListWidget/renderers, transcript listeners, and contributions that are not input-related; also propagate host visibility instead of permanently calling setVisible(true).

### 3. [medium] Throttle GitHub ignore-file reads

**Finding ID:** `PERF-F6DBFB14944B`  
**Location:** <code>src/vs/sessions/contrib/fileTreeView/browser/fileTreeView.contribution.ts:34</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub Blob API calls  
**Scaling:** Cold search makes one blob request per .gitignore or .ignore across the remote tree; recursive visits let reads overlap. Warm cache-key searches reuse enumeration.  
**Outcome:** Excessive network calls and increased cold search latency.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** No GitHub file-search provider was registered, so file search made no ignore-file blob calls.  
**Changed behavior:** The registration routes GitHub searches through a recursive walker that reads every encountered ignore file through GitHubFileSystemProvider.  
**Confidence:** 0.98 — The registration-to-network call path and per-ignore-file cardinality are explicit; only repository ignore-file count varies.

**Causal diff evidence:** Added line 34 registers the recursive provider for github-remote-file, introducing this network fan-out on GitHub search paths.

Quick Open, Add Context, or \#file on a remote monorepo can wait on dozens of GitHub blob downloads and consume API rate limits.

**Evidence:** FileSystemFileSearchProvider limits only readdir (lines 106-118); ignore readFile calls are outside that limiter (121-128) while recursive visits overlap. GitHubFileSystemProvider.readFile (245-256) calls content.getBlob.

**Suggested direction:** Bound ignore-file reads with a shared network limiter and coalesce/cache immutable blobs by SHA while preserving ignore semantics and cancellation.

### 4. [medium] Bound or lazily build the cached child index

**Finding ID:** `PERF-1F3AD9E8E3F5`  
**Location:** <code>src/vs/sessions/contrib/fileTreeView/browser/githubFileSystemProvider.ts:208</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Retained tuple arrays, basename strings, directory arrays, and map entries  
**Scaling:** Each fetched tree now retains one additional tuple and basename string per repository entry plus one children array/map entry per directory; total retained memory grows with the summed entry counts of every distinct owner/repo/ref accessed during the workbench lifetime.  
**Outcome:** Increased retained heap and GC pressure after opening large cloud repositories or multiple branches.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The cache retained one entries Map for each recursive GitHub tree and readdir scanned that map; stat/readFile did not create a second per-entry index.  
**Changed behavior:** Every cold tree fetch now eagerly allocates a children Map and pushes a newly allocated \[basename, FileType\] tuple for every entry, even when the caller only requested stat or readFile. treeCache has no size bound or timed eviction: fetchedAt controls freshness on a later lookup, but old keys are removed only on account change or provider disposal.  
**Confidence:** 0.97 — Allocation cardinality and cache lifetime are explicit. Exact heap size depends on repository path lengths and number of refs visited.

**Causal diff evidence:** Added line 208 creates and retains one new tuple and substring per cached tree entry; this materially increases the size of the pre-existing unbounded per-ref cache.

A large repository pays the duplicate index cost on first file access, and switching among repositories/refs accumulates all duplicate indices until the workbench/provider is disposed.

**Evidence:** The added loop at lines 196-209 visits the complete entries map and line 208 allocates the per-entry basename/tuple retained by cacheEntry at line 211. treeCache is keyed by owner/repo/ref (line 48), fetchTree only tests TTL without deleting unrelated/stale keys (lines 130-143), and clearCaches is only called for client changes/disposal (lines 293-302).

**Suggested direction:** Keep the O(1) readdir optimization but build the child index lazily on first readdir/search (so stat/readFile do not pay it), use a more compact representation where possible, and evict tree entries with a bounded LRU or actual TTL cleanup.


## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/sessions/contrib/fileTreeView/browser/githubFileSystemProvider.ts:241` (`RIGHT`)  
**Blamed base line:** `src/vs/sessions/contrib/fileTreeView/browser/githubFileSystemProvider.ts:229`  
**Introducing path:** `src/vs/sessions/contrib/fileTreeView/browser/githubFileSystemProvider.ts`  
**Introducing commit:** `e1d1376d3424a7ad2562665c8436ae663de5bd52`  
**Mechanism family:** `repeated-work`  
**Performance category:** `cpu`  
**Confidence:** 0.95

**Mechanism:** The old readdir implementation scanned the complete recursive entries Map and tested/sliced every path for each directory listing, making browsing D directories in an N-entry repository O(D\*N).

**Symptom:** Expanding directories in large github-remote-file repositories repeatedly rescanned the full tree, increasing directory-open latency and CPU with both repository size and the number of directories visited.

**Fixed behavior:** The PR builds a parent-to-direct-children index once per fetched tree and changes readdir to a direct lookup/copy, reducing repeated listings to O(number of returned children) after the O(N) index build.

**Evidence:** Base line 229 is the loop over all tree.entries inside readdir, introduced by the blamed commit. Added line 241 returns only tree.children.get(path); the new index is constructed once when the already-recursive tree is fetched and shared by subsequent readdir calls.
