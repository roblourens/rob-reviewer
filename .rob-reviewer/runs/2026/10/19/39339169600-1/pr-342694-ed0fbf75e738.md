# Performance review: agentHost: move\_session server tool to move sessions and nested sessions

## Findings (1)

### 1. [medium] Avoid rescanning the entire session catalog for each move

**Finding ID:** `PERF-B425E08C9B4D`  
**Location:** <code>src/vs/platform/agentHost/node/shared/sessionMoveTools.ts:413</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** central catalog/database reads, provider metadata round trips, session-database opens, and CPU over all registered sessions  
**Scaling:** Each move\_session invocation performs work proportional to the complete registered session history, although argument resolution needs only the source, destination, and optional anchor; in the documented link-based flow this repeats the same full scan just performed by list\_sessions.  
**Outcome:** The move tool's critical path gains avoidable I/O and latency, with fallback sessions adding one provider round trip plus session-database reads each and fallback concurrency limited to four.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR, requesting list\_sessions performed one full catalog computation and no subsequent move tool immediately forced another one; existing targeted session operations can use the accessor's getSession(session) lookup.  
**Changed behavior:** Every move\_session execution constructs a lookup backed by accessor.listSessions(). createMoveSessionLookup coalesces lookups only within that one call, while AgentService.listSessions retains results only while a computation is in flight and deletes settled entries, so a preceding list\_sessions call is not reused.  
**Confidence:** 0.98 — The call path, cache lifetime, I/O boundaries, and all-sessions-to-three-targets cardinality mismatch are explicit in repository code. Magnitude depends on session count and fallback eligibility, so severity is medium rather than high.

**Causal diff evidence:** The new execute path at RIGHT line 413 unconditionally invokes the full listSessions accessor for move argument resolution; no equivalent post-list scan existed before the new tool.

The normal workflow tells the model to obtain links from list\_sessions and then call move\_session. On a large history, the second call blocks confirmation/move progress on another full catalog read; legacy/fallback rows can reopen per-session storage and contact providers before the requested move starts.

**Evidence:** RIGHT line 413 wires argument resolution to \`createMoveSessionLookup(() =&gt; accessor.listSessions())\`. AgentService.listSessions removes settled computations from \`\_inFlightListSessions\`; \`\_computeSessions\` bulk-reads all catalog candidates and documents that each provider fallback costs a provider round trip plus session-database reads, under a Limiter(4). getMoveSessionArgs performs only source/destination/anchor resolution (at most three distinct sessions).

**Suggested direction:** Resolve the at-most-three referenced sessions through targeted getSession/state-catalog lookups (including their recorded chats), or carry a generation-keyed short-lived listing from the immediately preceding list\_sessions call; preserve freshness by revalidating the selected sessions in the existing move sequencer rather than recomputing the entire catalog.

- Effective concurrency: Pre-check and apply serialize with all moves. The scheduled map holds at most one entry per chat/turn, and queued turns are explicitly held during apply.
- Cache behavior: The move lookup has only per-invocation coalescing. Pre-check state cannot safely serve as an authoritative cache because state may change before turn end; apply revalidates.
- Mechanism confidence: High for the two validation rounds and admission hold; lower for material user impact beyond the list scan.
- Magnitude uncertainty: Moved subtrees are usually small and the duplicate validation is an intentional freshness tradeoff; no measurements show it dominates the already reported full-list scan.
- Expensive boundaries:
