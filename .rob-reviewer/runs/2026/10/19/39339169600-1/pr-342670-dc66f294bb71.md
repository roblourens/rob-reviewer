# Performance review: chat: Restore enterprise harness enforcement and explain disabled Local

[PR #342670](https://github.com/microsoft/vscode/pull/342670) at `dc66f294bb714d0254bb682ce67dc7a41ccd1e62`

## Findings (1)

### 1. [medium] Limit concurrent policy-triggered history migrations

**Finding ID:** `PERF-494958A206DD`  
**Location:** <code>src/vs/platform/policy/common/copilotManagedSettings.ts:338</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Agent Host IPC calls, Copilot session creations, and full conversation-history payloads/objects  
**Scaling:** On policy settlement or refresh, work grows with the number of visible restored Claude/Codex chat widgets and with the turn count of each history; all affected resources run concurrently because deduplication is only per resource.  
**Outcome:** A burst of IPC, session-creation, serialization/allocation, and history-loading work can contend with workbench restore and delay usable chat UI.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** For the same managed sandbox.enabled or permissions.deny policy, requiresCopilotAgentHost returned false, so existing visible Claude/Codex histories were left in place and no automatic Agent Host continuation work was started; only the explicit temporary Local prohibition activated this path.  
**Changed behavior:** The added sandbox/deny condition makes the shared policy observable true for these common managed settings. Every visible affected widget's autoMigratePolicySession autorun independently schedules continueInCopilot, which lists sessions, reads the full saved chat, creates a Copilot session importing all turns, loads it, and completes the continuation.  
**Confidence:** 0.93 — The changed predicate, per-widget autorun, full migration call path, per-resource-only coalescing, and unsequenced new-session creation are all directly traced. The exact delay depends on how many chat editor groups are visible and history sizes, which affects severity rather than the mechanism.

**Causal diff evidence:** The added right-side return at line 338 extends the gate from only temporaryAllowLocalHarness=false to sandbox.enabled=true or any non-empty/malformed deny list; ChatWidget's existing per-widget migration autorun consumes this gate, so these policies newly fan out full-history continuations.

When an enterprise policy settles during window restore (or refreshes) while several Claude/Codex chats are visible across editor groups, VS Code starts all full-history migrations together, producing an avoidable Agent Host IPC/CPU burst and sluggish restore or migration UI.

**Evidence:** ChatWidget.autoMigratePolicySession creates a zero-delay task per visible model and calls AgentHostPolicyContinuationService.continueInCopilot. That service only coalesces by resource in \_pending; across resources it calls listSessions/readSavedChat, then \_connection.createSession({ importConversation: { turns } }), acquireOrLoadSession, and completeSavedChatContinuation. AgentService.createSession bypasses its per-session sequencer when config.session is absent, as it is here, so these creations are not globally bounded.

**Suggested direction:** Route automatic continuations through a shared small limiter or sequencer in AgentHostPolicyContinuationService, rechecking visibility/policy when each queued item starts; keep manual continuations immediate if needed.

### Scenario 1: Managed policy settles while restored Local/Claude/Codex chats are visible

- Critical path: Policy evaluation itself is synchronous. Automatic migration is deferred by a zero-delay task until widget binding completes, so it is off the initial bind critical path, but each affected chat remains read-only/moving until its continuation finishes.
- Scaling input: Effective cardinality is one migration per visible, non-archived, request-bearing affected chat resource; across split editor groups this can be several resources, and payload cost scales with each conversation's turn count.
- Effective concurrency: Each ChatWidget schedules independently. AgentHostPolicyContinuationService coalesces only duplicate work for the same resource; distinct resources run concurrently. New createSession calls omit an existing session ID and therefore bypass AgentService's per-session creation sequencer.
- Cache behavior: \_pending deduplicates in-flight work per source resource and \_destinations reuses a known destination. A warm/continued source can avoid creating another destination, but listSessions/readSavedChat still run; there is no cross-resource limiter or coalescing.
- Mechanism confidence: High: the changed predicate, per-widget autorun, per-resource-only deduplication, full-history import, and absence of a shared creation limiter were directly traced.
- Magnitude uncertainty: The exact burst depends on restored editor-group count, provider histories, and turn sizes; this uncertainty lowers severity, while the unbounded-across-resources scheduling and full-history operations are established.
- Expensive boundaries:

    - Introduced by diff: true; previous behavior: Under sandbox.enabled or permissions.deny alone, the shared policy gate stayed false, so this boundary was not reached automatically.; critical-path effect: Required before that chat can be imported and opened in Copilot; concurrent resources compete during restore.

### Scenario 2: Create or restore the default chat under managed sandbox or non-empty deny policy

- Critical path: Account policy must settle before session choice. Once Copilot is selected, Agent Host session acquisition must complete before the new chat can proceed; this boundary is intentionally moved onto the path by the policy requirement.
- Scaling input: One selected session acquisition per user-created/restored empty chat; no collection fan-out is introduced by a single action.
- Effective concurrency: Normal user/window-driven chat creation concurrency applies. The changed routing does not itself batch-launch a collection of new chats.
- Cache behavior: A warm Agent Host can reuse its running connection and existing session-loading infrastructure; a cold host pays startup/setup. The policy decision is observable/cached and recomputed on managed-setting or escape-hatch changes.
- Mechanism confidence: High for the routing and boundary placement; no diff-introduced fan-out was found.
- Magnitude uncertainty: Cold Agent Host startup duration varies by platform, but cardinality remains one per requested chat and the added cost implements the required harness policy.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/widgetHosts/viewPane/chatViewPane.ts:1339 acquireDefaultNewSession and src/vs/workbench/contrib/chat/browser/widgetHosts/editor/chatEditorInput.ts:350-390</code>: Acquire or load the selected Copilot Agent Host chat session; cardinality: One acquisition per new/empty chat resolution.
    - Introduced by diff: true; previous behavior: With sandbox/deny policies alone, routing selected the Local in-process session and did not require Agent Host acquisition.; critical-path effect: On the critical path to presenting the usable new chat.
- Verdict: No additional finding: this is a bounded one-for-one intentional routing cost, not repeated or unbounded work.

### Scenario 3: Open or refresh the chat harness picker as managed settings change

- Critical path: Session item rebuilding and deny-list JSON parsing run synchronously on the UI path before picker actions/labels are presented.
- Scaling input: Work scales with the number of registered visible chat session providers and the deny-list string length. Typical provider cardinality is small; one Local row is added when policy-disabled.
- Effective concurrency: Synchronous in each picker instance. Managed sandbox changes can invoke both the sandbox observable autorun and the managed-settings listener, causing duplicate bounded rebuilds, but policy updates are infrequent.
- Cache behavior: The deny list is reparsed by requiresCopilotAgentHost calls and session item arrays are rebuilt; there is no derived-result cache. Existing observables restrict recomputation to policy/configuration events, and no remote cache is involved.
- Mechanism confidence: High that duplicate bounded rebuilds and repeated parsing occur; low that they produce material latency.
- Magnitude uncertainty: Enterprises could have larger deny lists or many restored chat widgets, but realistic parsing/rebuild sizes remain too small and infrequent to establish user-visible regression severity.
- Expensive boundaries: none found
- Verdict: No finding: bounded synchronous UI work without a realistic material impact.

### Scenario 4: Send, retry, or queue a request in an existing Local chat after policy changes

- Scaling input: One cached boolean read per attempted request; policy parsing occurs on policy/configuration events rather than per streamed token or history item.
- Effective concurrency: No new outbound concurrency; blocked requests prevent downstream provider work.
- Cache behavior: observableFromEvent retains the current policy result and invalidates only on managed-settings or temporary-default configuration changes.
- Mechanism confidence: High from the observable construction and request-blocking tests/call path.
- Magnitude uncertainty: None material for performance; the changed gate removes downstream work on blocked requests.
- Expensive boundaries: none found
- Verdict: No finding: this path reduces expensive work rather than introducing it.
