# Performance review: github: migrate GitHub repository filesystem to shared API

[PR #341941](https://github.com/microsoft/vscode/pull/341941) at `8b3375938d93798e6c954bd5bab854e6dc267e8d`

## Findings (2)

### 1. [medium] Cache truncated-tree failures before rejecting them

**Finding ID:** `PERF-16047E0CF978`  
**Location:** <code>src/vs/sessions/contrib/fileTreeView/browser/githubFileSystemProvider.ts:172</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** the full recursive Git tree response, including network bytes, desktop IPC string transfer, JSON/schema parsing, and server API quota  
**Scaling:** Cost is O(tree response size) for every sequential stat/readdir/readFile attempt after the prior rejection; concurrent attempts coalesce only while one request remains in pendingFetches, and no result survives the failure.  
**Outcome:** repeated multi-megabyte downloads and parsing block repository file completions/context browsing and consume GitHub API/network capacity  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The provider accepted the recursive response, built a partial entry map, and cached it for five minutes, so later filesystem probes did not refetch the same tree during that window.  
**Changed behavior:** The added branch rejects a truncated response after getTree has fully downloaded, transferred, parsed, and schema-validated it, but stores neither a positive entry nor a negative/terminal cache entry; finally then removes the in-flight promise.  
**Confidence:** 0.99 — The changed line, cache control flow, added regression test's exact call count, completion caller, and network/IPC implementation are all directly traced. Only the prevalence and exact response size of truncated repositories are uncertain, which is reflected in medium severity rather than mechanism confidence.

**Causal diff evidence:** The added throw at line 172 exits before treeCache.set at lines 194-195, while the promise's finally removes pendingFetches; this newly converts a once-per-five-minute cached response into repeated full getTree calls for the same key.

For a large repository that GitHub returns with truncated=true, each later virtual-filesystem probe retries the entire recursive-tree request. This is particularly visible in github-remote-file completion/context workflows: completion results are marked incomplete and invoke IFileService.resolve again, so retries repeatedly stall UI results and redownload the large response.

**Evidence:** fetchTree caches successes and 404s and coalesces only a currently pending promise (lines 129-153). doFetchTree performs client.getTree before this added throw (lines 160-172), and the new test 'rejects truncated trees without caching a partial filesystem' proves three sequential provider operations produce three treeCalls. Production variableCompletions.ts registers an incomplete completion provider and calls IFileService.resolve for github-remote-file workspaces on each completion request, establishing a realistic retry path. On desktop, RemoteApiRequestProvider forwards the full response text over IPC before ContentClient parses every tree entry.

**Suggested direction:** Record a per-key truncated-tree failure sentinel before throwing and replay the same Unavailable error for a bounded TTL (for example the existing five-minute tree TTL, with account/grant invalidation clearing it), while retaining in-flight coalescing and never exposing the partial entries.

### 2. [high] Do not retain full blob payloads in the count-only ETag cache

**Finding ID:** `PERF-37DFADDB218B`  
**Location:** <code>src/vs/sessions/contrib/fileTreeView/browser/githubFileSystemProvider.ts:255</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** base64 Git blob JSON response strings retained by GitHubTransport.\_restCache  
**Scaling:** Retained bytes grow with the sum of unique blob response bodies read for the selected account until the transport's 500-entry LRU turns over. A permitted 10 MiB file produces roughly 13.3 MiB of base64 plus JSON, so dozens of large unique files retain hundreds of MiB and the count-only worst case is multiple GiB.  
**Outcome:** large long-lived shared-process/renderer heap growth, GC pressure, and potential process instability while browsing repository files  
**PR causality:** <code>introduced</code>  
**Previous behavior:** readFile issued a direct IRequestService request, parsed and decoded the blob, and retained no blob cache; after the returned bytes were consumed, the response JSON/base64 string was reclaimable.  
**Changed behavior:** The added content.getBlob call routes each blob GET through Local/RemoteApiRequestProvider and GitHubTransport. Ordinary GETs default to ETag caching, and an ETagged success stores the complete response body string in the transport's 500-entry LRU; the provider's retained GitHubApiClient keeps that account transport alive until account/grant invalidation or disposal.  
**Confidence:** 0.98 — The new call path, cache admission logic, 500-entry lifecycle, provider client lifetime, and 10 MiB payload bound are directly traced. Admission depends on the server returning an ETag, which is the transport's documented ordinary-read path; exact user file-size distributions affect severity frequency but not the retention mechanism.

**Causal diff evidence:** The added call at line 255 replaces the prior direct, uncached blob request with the shared typed client path whose default transport policy retains successful ETagged response bodies.

Opening or attaching many distinct large repository files now leaves every encoded blob body retained after readFile returns. On desktop this memory is held in the shared-process account transport; on web it is held locally. Since the new limit still allows 10 MiB decoded files, a realistic sequence of tens of media/data files can add hundreds of MiB even though callers retain only decoded file bytes.

**Evidence:** content.getBlob builds a normal GET without a cache opt-out. LocalApiRequestProvider forwards it as GitHubRestTextRequest with no etag:false, and GitHubTransport lines 813-827 stores every ETagged GET body in \_restCache. That cache is LRUCache(..., 500), bounded by entry count rather than bytes, and its entry type retains body:string. GitHubApiClient retains one client lease, while the architecture documents that ordinary reads preserve conditional-response state. The provider explicitly permits decoded payloads up to 10 MiB, whose base64 JSON representation is substantially larger.

**Suggested direction:** Add and use a no-body-cache/etag:false request policy for immutable getBlob reads (and consider recursive trees), or make the transport cache byte-weighted with a small total payload budget and reject oversized entries. Preserve in-flight coalescing; if repeat blob reads need caching, cache decoded bytes under an explicit byte budget rather than retaining base64 JSON bodies.
