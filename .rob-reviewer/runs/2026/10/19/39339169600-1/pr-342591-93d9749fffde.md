## Findings (1)

### 1. [medium] Avoid rebuilding date placement on every dragover

**Finding ID:** `PERF-AB359D6E453D`  
**Location:** <code>src/vs/sessions/contrib/sessions/browser/views/sessionsList.ts:5815</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** main-thread CPU work and temporary arrays/maps from full-tree traversal, filtering, and sorting  
**Scaling:** For every native dragover event over a date-section destination, cost grows as O(T + N log N): sortInDisplayOrder traverses the rendered tree T, computeSessionReorder filters and sorts the full session catalog N, and this line copies/sorts/groups all date sessions again. The work repeats at pointer-event frequency while hovering.  
**Outcome:** increased drag latency and dropped frames in large session histories  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Dragover validated the target with placement and selection predicates; the collection-wide scope filtering/sort used to compute synthetic sort keys ran only when the user dropped the sessions.  
**Changed behavior:** Date-section dragover now predicts final placement by traversing the tree, sorting the full reorder scope, then copying, sorting, and regrouping all date sessions before accepting each hover event.  
**Confidence:** 0.99 — The synchronous call path and unthrottled event forwarding are explicit, and both collection-wide sorts are directly visible. Exact catalog sizes vary by user, so magnitude is uncertain, but session history is persistent and Older is not capped.

**Causal diff evidence:** The added dragover resolver calls getSessionDropEffect for every hover event; its new rendersInDateSection path reaches added line 5815, while the deleted implementation only performed target/selection predicates during dragover and deferred reorder scope construction to reorderSessions on drop.

With date grouping and a long-lived catalog, dragging over a Recent/Older row or header repeatedly performs two collection sorts plus a full tree walk on the UI thread, making the insertion feedback and pointer movement stutter.

**Evidence:** SessionsListDragAndDrop.onDragOver synchronously calls resolveDrop -&gt; resolveSessionDrop -&gt; getSessionDropEffect -&gt; rendersInDateSection. At lines 5810-5815 that path invokes sortInDisplayOrder, computeSessionReorder (lines 5901+ filters and sorts this.sessions), and sortSessions/groupByDate. The base list forwards native dragover events directly without throttling. SessionsList.refresh assigns this.sessions from getSessions(), so the reorder sort uses the uncapped provider catalog; date grouping also retains all non-Recent sessions in Older.

**Suggested direction:** Keep dragover validation lightweight: cache the predicted date placement/reorder context by list-model revision, dragged IDs, and destination (or compute it once per target), invalidate it when sessions/order/grouping change, and perform the authoritative full recomputation once on drop.
