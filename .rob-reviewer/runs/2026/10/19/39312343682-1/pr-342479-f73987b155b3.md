# Performance review: agentHost: route Copilot Connector Sign In through Connector authorization

[PR #342479](https://github.com/microsoft/vscode/pull/342479) at `f73987b155b37c3b6af139d157141e2976b6b266`

## Findings (1)

### 1. [medium] Coalesce the authorization refresh with the forced reconcile

**Finding ID:** `PERF-C417EEB3E141`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts:531</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SDK connector RPCs, connector gateway/catalog requests, MCP inventory refreshes, and server restart work across live agent-host sessions  
**Scaling:** For N live Copilot sessions, first-time authorization now schedules two distinct refresh keys per session (the authorization-change refresh and this named forced refresh), so capabilities/account/status/reconcile and inventory work grows as 2N rather than N; sessions run in parallel and each session processes the two keys sequentially.  
**Outcome:** Duplicate IPC/network work and connector restarts increase Sign In latency, gateway load, and agent-host CPU/I/O, with the cost amplified by the number of live sessions.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this added Sign In refresh, adding the connector-scoped authentication session already caused CopilotConnectorsService.handleAuthenticationSessionsChanged to issue one host-wide refresh when authorization changed from absent to present.  
**Changed behavior:** After authorize creates the first full-scope session, its session-change listener starts an unforced refresh, and this line independently starts a named forced refresh. CopilotAgentSession.markConnectorConfigurationChanged keeps undefined and the connector name as separate Map entries, and \_doRefreshConnectors reconciles each entry rather than coalescing them.  
**Confidence:** 0.94 — The call path and multiplicity are explicit: a first scoped session synchronously transitions connector authorization from absent to present and schedules refreshAgentHostConnectorSessions(undefined); this added line then schedules refreshAgentHostSessions(connectorName). The agent stores undefined and the named connector as distinct pending Map keys and loops over both, while each refresh fans out to every live session. Exact wall-clock cost depends on live-session count and gateway latency, but the duplicate reconcile mechanism is deterministic for first-time authorization.

**Causal diff evidence:** RIGHT line 531 adds \`\_copilotConnectorAuthorization.refresh(connectorName)\` after \`authorize\`; when authorize creates the first connector-scoped session, the pre-existing authentication-session listener has already requested \`refreshAgentHostConnectorSessions()\` with an undefined key, so the added named request creates the second non-coalesced reconcile.

On a user's first Connector Sign In, every live Copilot session can reconcile twice and restart/reload connector state twice before the UI settles; work doubles across the realistic multi-session case and incurs extra remote catalog/gateway traffic.

**Evidence:** CopilotConnectorsService.handleAuthenticationSessionsChanged calls refreshAgentHostConnectorSessions() when updateConnectorAuthorizationSessions changes from zero authorized sessions to one. This added call then invokes refreshAgentHostSessions(connectorName). AgentService.refreshCopilotConnectorSessions fans out to providers and CopilotAgent.refreshConnectorSessions marks every live session. In CopilotAgentSession, \_pendingConnectorRefreshes is keyed by forceConnectorName and \_doRefreshConnectors iterates every entry; reconcileCopilotConnectors performs getCapabilities, getAccount, optional getStatus, reconcile({ refreshCatalog: true }), followed by MCP enablement/inventory refresh. Thus the undefined and named requests both cross the expensive boundary.

**Suggested direction:** Coordinate this path with the authorization-session listener so one refresh runs after the widened credential has been forwarded and is awaited for verification. For example, let the explicit Sign In join/supersede the pending authorization-change refresh (with an unforced refresh subsuming the named one), rather than enqueuing both distinct keys.

### Scenario 1: First-time Copilot Connector Sign In from an auth-required MCP row or tool prompt

- Critical path: The user action waits for Connector authorization, forwarding the widened GitHub credential to the agent host, a connector refresh, and then Ready/Rejected or the 60-second verification deadline. The authorization-session event also starts a separate host refresh before the explicit named refresh.
- Scaling input: Number N of live Copilot sessions; each session may own multiple connector runtime servers, though the explicit second reconcile targets one connector. Effective changed cardinality is two reconcile requests per live session when authorization transitions from no connector-scoped session to the first one.
- Effective concurrency: Authorization itself is coalesced by authorizationPromise. AgentService fans provider refreshes out with Promise.all, CopilotAgent fans live sessions out with Promise.all, and each session's per-chat queue processes its distinct undefined and named pending refresh keys sequentially. The two keys are not coalesced.
- Cache behavior: A warm account with an already suitable full-scope session skips consent and does not trigger the authorization-state transition, so it performs only the explicit named refresh. A cold/first authorization creates the session, triggers the unforced refresh, and then performs the named refresh. Authentication-session lookup is not a result cache; authorizationPromise only coalesces concurrent authorization calls, not refreshes.
- Mechanism confidence: High: the session event, added refresh call, fan-out, distinct Map keys, and sequential reconcile loop are all directly traced.
- Magnitude uncertainty: Exact latency and gateway cost depend on how many live sessions exist and runtime/network speed, but first-time authorization and the two distinct refresh keys are deterministic.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts AgentHostCopilotConnectorAuthorization.authorize</code>: Create/resolve the widened GitHub authentication session and forward its Copilot credential to the agent host; cardinality: One coalesced authorization operation and one credential-forwarding operation per Sign In attempt; credential application updates each live static-token SDK session.
    - Introduced by diff: true; previous behavior: Connector MCP Sign In resolved an MCP token and did not route through Connector authorization/credential forwarding.; critical-path effect: Authorization and credential forwarding must finish before the clicked connector can be restarted with the new credential.

- Cache behavior: Warm authorized-session state avoids consent and avoids the authorization-change refresh. Connector status itself is re-read/reconciled rather than cached because the server must restart with the bound credential.
- Mechanism confidence: High.
- Magnitude uncertainty: The number of concurrently live sessions varies, but no duplicate authorization-event refresh occurs in this warm case.
- Expensive boundaries:
  - IPC/network at <code>agentHostCustomizationService.ts AgentHostCopilotConnectorAuthorization.authorize/refresh</code>: Forward the selected GitHub credential and force targeted connector reconciliation in each live session; cardinality: One credential forward from the workbench and at most one named reconcile per live session after same-key coalescing.
    - Introduced by diff: true; previous behavior: The MCP path forwarded a per-server token and returned without connector reconciliation.; critical-path effect: Required to restart the clicked connector and verify that it becomes Ready.
- Verdict: No additional finding: the new boundary is necessary for the changed Connector authentication semantics and is targeted/coalesced in this warm path.

### Scenario 5: Connector authentication timeout, cancellation, and disposal

- Critical path: A verification listener/timer races refresh; Ready/Rejected, the 60-second timeout, or service disposal releases the Sign In action. Per-session connector refresh also has its own cancellation timeout and retry ownership.

- Cache behavior: No retained positive/negative result cache. Listener/timer state is deleted on completion, and service disposal releases all outstanding stores.
- Mechanism confidence: High for lifecycle behavior, lower for realistic repeated retry magnitude.

- Verdict: No separate finding: listener cleanup and per-session refresh ownership are bounded; the concrete duplicate-key case is covered by the submitted finding.
