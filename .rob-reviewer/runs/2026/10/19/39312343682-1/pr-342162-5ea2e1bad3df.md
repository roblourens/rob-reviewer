# Performance review: agentHost: track Codex edits from turn diffs

[PR #342162](https://github.com/microsoft/vscode/pull/342162) at `5ea2e1bad3df8c3131ecc63d060ea016304627ba`

## Findings (3)

### 1. [high] Bound checkpoint refreshes before restoring long chats

**Finding ID:** `PERF-033D7D0F395E`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSnapshotController.ts:249</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** one changeset subscription/refresh IPC and server-side database diff computation per crossed chat turn  
**Scaling:** The burst grows linearly with the number of checkpoints crossed; restoring or retrying an early request in a long Codex chat launches all N distinct turn refreshes concurrently.  
**Outcome:** blocked checkpoint-restore latency plus an unbounded IPC/database/CPU burst in the agent host  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Checkpoint navigation used the already-hydrated tool-call edits and immediately began applying crossed checkpoints; it did not fetch every crossed turn from the agent host.  
**Changed behavior:** The added Promise.all resolves every crossed checkpoint at once. For Codex, each resolve opens a distinct Changeset subscription and explicitly refreshes it; server computations are sequenced only by (session, turnId), so different turns execute independently rather than through a shared limit.  
**Confidence:** 0.98 — The restore callers, crossed-checkpoint cardinality, client refresh IPC, and per-turn server sequencing are all directly traced. Only the exact chat length and per-refresh duration vary by user, affecting magnitude rather than mechanism.

**Causal diff evidence:** RIGHT line 249 adds \`await Promise.all(crossed.map(checkpoint =&gt; this.\_resolveCheckpointEdits(checkpoint)))\`, placing all per-turn changeset refreshes on the restore critical path concurrently.

Using Restore Checkpoint, Retry, or Start Over on an older request in a chat with tens or hundreds of later turns blocks until every turn changeset has been refreshed and can saturate the agent-host IPC and SQLite work concurrently.

**Evidence:** \`\_navigateToCheckpointIndex\` builds \`crossed\` from every checkpoint between the current and target indices and the added line passes all of them to \`Promise.all\`. \`\_resolveTurnFileEdits\` calls \`getSubscription\` and \`refreshSubscription(resource)\` for each request. \`AgentSubscriptionManager\` coalesces only refreshes of the same resource, while \`AgentHostChangesetService.\_queueTurnChangeset\` uses a separate sequencer key containing each turnId, so this N-way fan-out is not globally bounded.

**Suggested direction:** Preserve the prefetch-before-write failure guarantee, but resolve crossed checkpoints through a small shared concurrency limiter or a single batched changeset request instead of issuing all turn refreshes at once.

### 2. [medium] Resolve local turn anchors in one database query

**Finding ID:** `PERF-E83E8387817A`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostChatRowStore.ts:111</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SQLite queries on the session database  
**Scaling:** Cold restore now performs one additional \`SELECT event\_id FROM turns\` for every persisted local turn whose host anchor is not directly present in the provider-restored ID set.  
**Outcome:** increased cold chat restore latency and database callback/queue pressure proportional to local-turn history  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Restoring local turns required one \`getPersistedTurnsForChat\` query; records were then interleaved in memory without per-record database reads.  
**Changed behavior:** When visible IDs are supplied, the added \`Promise.all(records.map(...))\` invokes \`db.getTurnEventId\` separately for each unresolved local anchor. For restored Codex history, host anchors commonly need translation to native turn IDs, so this path applies to each \`/rename\` acknowledgement or \`\!command\` turn in the chat.  
**Confidence:** 0.97 — The cold-restore caller, qualifying record type, and exact SQLite call cardinality are directly established. The number of local commands varies, which limits severity but not confidence in the N+1 mechanism.

**Causal diff evidence:** RIGHT line 111 adds a per-record \`await db.getTurnEventId(record.anchorTurnId)\` after the existing bulk persisted-turn query.

Reloading a long chat with many host-local commands incurs an N+1 database pattern on the session restore critical path instead of a single row read.

**Evidence:** \`AgentService.\_interleaveLocalTurns\` now always supplies the restored turn-ID set. \`getPersistedTurnsForChat\` first reads all local rows, then RIGHT line 111 calls \`getTurnEventId\` inside the per-record map; that method is a queued SQLite \`SELECT\` for one ID. The local-turn documentation identifies \`/rename\` and \`\!command\` as persisted examples.

**Suggested direction:** Join \`local\_turns.anchor\_turn\_id\` to \`turns\` in the initial chat query, or add one bulk event-ID lookup for all unresolved anchors and translate them in memory.

### 3. [medium] Stop reparsing the full cumulative diff on every update

**Finding ID:** `PERF-D441BDA6648A`  
**Location:** <code>src/vs/platform/agentHost/node/codex/codexTurnDiffTracker.ts:79</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** synchronous string scans and allocations for the complete aggregated unified diff  
**Scaling:** For a turn with K incremental file-change notifications, the kth update scans the entire diff accumulated so far; similarly sized additions therefore produce quadratic total bytes scanned and temporary strings as the turn grows.  
**Outcome:** increased agent-host CPU and GC pressure, delaying notification processing and turn progress for repository-wide edits  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The agent host did not consume \`turn/diff/updated\`, so it performed no synchronous full-diff parsing for each native edit update.  
**Changed behavior:** Every native diff notification now stores the latest aggregate and immediately splits the complete aggregate into file sections, then splits each section again to recover its header, even though previously seen sections dominate later cumulative notifications.  
**Confidence:** 0.95 — The cumulative payload semantics and synchronous per-notification call path are explicit. Notification count and diff size vary, so severity is medium, but repeated full-prefix work and its growth are certain whenever a turn emits multiple updates.

**Causal diff evidence:** RIGHT line 79 introduces \`notification.diff.split(...).filter(...)\` in the handler for every cumulative \`turn/diff/updated\` notification.

A Codex refactor that edits many files or repeatedly updates a large file makes each subsequent diff notification progressively more expensive, causing visible lag near the end of the turn.

**Evidence:** The protocol type documents \`diff\` as the latest aggregated diff across all file changes in the turn. \`\_handleTurnDiffUpdated\` dispatches every notification synchronously to \`update\`, where RIGHT line 79 splits that full aggregate and allocates sections before checking \`initialDiffs\`; only the map insertion is deduplicated, not the scan/allocation work.

**Suggested direction:** Capture first-seen file sections only when the corresponding file-change completion identifies new paths, or otherwise maintain incremental/path-indexed state so updates do not split and allocate the entire cumulative diff repeatedly.

- Effective concurrency: The added prefetch uses unbounded \`Promise.all\` across N checkpoints. File application remains serial by checkpoint and parallel by file within each checkpoint.

- Mechanism confidence: Very high: restore callers, crossed range, Promise.all, explicit protocol refresh, and per-turn server sequencer keys are all traced.
- Magnitude uncertainty: Chat history length and per-turn file count vary; early restore in a long-running agent chat produces the largest burst.
