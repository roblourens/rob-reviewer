## Findings (1)

### 1. [medium] Skip the catalog fallback when curated feeds succeed

**Finding ID:** `PERF-6F61AF5878DA`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationDiscoveryPage.ts:1313</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** network/IPC calls and catalog result objects for up to 100 items per enabled source  
**Scaling:** Each cold or invalidated queryless Browse load now issues the three saved-feed requests plus one catalog request per enabled marketplace source; the catalog service fans those source requests out with Promise.all, so cost grows with enabled sources and returned page sizes.  
**Outcome:** increased Browse latency and unnecessary network/IPC traffic  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Queryless Browse performed the ordinary marketplace query once and rendered its results; there were no saved-feed calls whose successful output made that query redundant.  
**Changed behavior:** The changed load starts curated-feed retrieval, immediately awaits the existing full marketplace query, and only afterward consumes the feed result. When any curated section succeeds, renderBrowse uses only curatedSections, so the catalog page fetched here is hidden, yet its slowest enabled source still delays the curated cards.  
**Confidence:** 0.99 — The changed call order, fixed three-feed Promise.all, per-enabled-source catalog Promise.all, 100-item page bound, and exclusive curated rendering are all explicit in the traced code. Only real-world endpoint duration and enabled-source count vary, which affects severity rather than the mechanism.

**Causal diff evidence:** The added branch at lines 1303-1305 starts curated retrieval, while the added/restructured line 1313 still executes the full catalog query in the same load before curated results are consumed; this creates the new duplicate boundary fan-out and makes the old query part of the curated critical path.

Opening Browse with the GitHub Feed enabled launches three Agent Host saved-feed RPCs plus the normal fan-out to GitHub Feed, MCP Gallery, connectors, and configured marketplaces. Even if the three curated feeds return quickly, a slow unrelated catalog source blocks the curated UI and all catalog responses are discarded from presentation; source/authentication invalidation repeats the burst.

**Evidence:** At lines 1303-1305 loadCatalog starts loadBrowseSections, whose workbench implementation maps the three product feeds through Promise.all and provider.getFeed; line 1313 then awaits marketplaceService.query before awaiting that feed promise at line 1364. CustomizationMarketplaceService.query concurrently invokes every selected source and requests up to the 100-item Browse page size. renderBrowse at lines 1616-1628 renders curated sections exclusively whenever any are nonempty, confirming the catalog results have no consumer in the successful-feed case.

**Suggested direction:** Resolve curated sections first for queryless Browse and run marketplaceService.query only when no nonempty curated section is available (including unsupported/error/empty fallback cases). Preserve the existing cache and cancellation behavior, and keep ordinary queries unchanged.
