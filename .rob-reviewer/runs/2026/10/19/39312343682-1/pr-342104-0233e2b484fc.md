# Performance review: agentHost: refresh discovery after account entitlement changes

[PR #342104](https://github.com/microsoft/vscode/pull/342104) at `0233e2b484fc8843749cb79e9552c33ea147fa4a`

## Findings (1)

### 1. [medium] Preserve the valid client after a failed background refresh

**Finding ID:** `PERF-94E8FD505B68`  
**Location:** <code>src/vs/platform/agentHost/node/shared/copilotApiService.ts:968</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** one additional \`/copilot\_internal/user\` network request per affected token/host, plus client reconstruction  
**Scaling:** The cost is one coalesced discovery round trip for each agent-host/token whose entitlement refresh fails, so it scales with active local/remote hosts and failed entitlement-change revalidations rather than with individual concurrent model calls.  
**Outcome:** blocked critical path and increased request latency from an avoidable network cache miss  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the PR, an entitlement change did not launch this background refresh or clear a valid host discovery entry, so subsequent model operations continued using the cached CAPI client until its normal refresh window. Existing ordinary refresh failures also retain an unexpired entry.  
**Changed behavior:** A failed background entitlement revalidation now removes the still-valid per-token CAPI client/cache entry. The next models, responses, messages, utility completion, or telemetry-context lookup rebuilds the client through \`/copilot\_internal/user\` before proceeding.  
**Confidence:** 0.98 — The changed failure branch, cache read/write logic, and request call path are explicit: refresh starts only with a readable cached entry; the branch clears it on network/5xx/parse errors; \`\_getClientForToken\` is awaited by all CAPI model operations and \`\_getEntryForToken\` performs discovery when the value is absent. The exact network duration is environment-dependent, but the added critical-path request is deterministic after this trigger and coalesced to one request per token/host.

**Causal diff evidence:** The added non-authentication failure branch at src/vs/platform/agentHost/node/shared/copilotApiService.ts:968 assigns \`request.skuCell.value = undefined\` after an entitlement-triggered background refresh fails, even though \`entry\` was read from an unexpired cache value at line 938. \`\_getEntryForToken\` then treats the next request as an initial miss and calls \`\_buildClientForToken\`, while before this PR no entitlement refresh could evict that valid entry.

If entitlement revalidation encounters a transient network error, 5xx, or malformed response, the next chat/model or utility operation is delayed by an extra account-discovery round trip before its real request. If discovery is still unavailable, the user-facing operation fails after waiting on that extra boundary. This occurs once per affected token and host after each failed entitlement refresh; concurrent callers coalesce behind the same lookup.

**Evidence:** \`refreshCopilotUser\` obtains an unexpired \`entry\` via \`\_readCachedClient\`, then on any non-401/403 failure clears \`request.skuCell.value\`. \`\_getEntryForToken\` only returns immediately when that value exists; otherwise it awaits \`\_buildClientForToken\`, whose changed code fetches \`${getApiBaseUri()}/copilot\_internal/user\`. Public \`models\`, \`responses\`, \`utilityChatCompletion\`, and \`\_sendRequest\` all await \`\_getClientForToken\` before issuing their actual CAPI request. The existing ordinary-refresh failure path already preserves an unexpired \`existing\` entry, demonstrating the cache can remain usable across transient discovery failures.

**Suggested direction:** On non-authentication refresh failures, retain the previous client until its normal expiry, as the ordinary refresh path does. If stale SKU telemetry must be suppressed, track that validity separately from the routing/client cache rather than converting the next model request into a discovery miss.

### Scenario 2: The same entitlement change is propagated to multiple remote Agent Host connections

- Critical path: The default-account listener starts authentication for every connected remote host without awaiting the collection. Within each connection, session resolution and protected resources are sequential; each host's entitlement HTTP lookup remains off its authenticate response path.
- Scaling input: Number of simultaneously connected remote Agent Hosts for the account.
- Effective concurrency: \`\_authenticateAllConnections\` launches one asynchronous reconciliation per connected host, so remote hosts refresh in parallel with no global limiter. Within a host/token, the WeakMap coalesces entitlement refreshes; host provider fan-out is parallel.
- Cache behavior: Each connection owns its own \`AgentHostAuthTokenCache\`; unchanged entitlement metadata is suppressed independently per connection. Each remote host has an independent per-token discovery cache and refresh coalescer.
- Mechanism confidence: High for parallel per-connection scheduling and independent host requests; lower only for real-world host-count magnitude.
- Magnitude uncertainty: Most users have few active remote hosts; there is no repository evidence of a realistically large connection count that would make the unbounded cross-host parallelism severe.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts:514 and agentHostAuth.ts:589</code>: Authenticate each connected remote host with the changed entitlement metadata.; cardinality: One RPC per affected protected resource per connected remote host after each connection's token-cache deduplication.
    - Introduced by diff: true; previous behavior: The listener already reconciled every connection, but same-token authenticate RPCs were suppressed.; critical-path effect: Runs asynchronously from the account-change event and does not serialize all remote connections.
  - network at <code>src/vs/platform/agentHost/node/shared/copilotApiService.ts:1155</code>: Each remote Agent Host independently fetches \`/copilot\_internal/user\` with its own credential.; cardinality: At most one concurrent lookup per affected token per host; aggregate burst scales with the number of connected remote hosts.
    - Introduced by diff: true; previous behavior: No entitlement-triggered lookup occurred on those hosts until normal cache refresh.; critical-path effect: Off each same-token authenticate call's critical path; can consume parallel network capacity across many hosts.
- Verdict: No finding: fan-out is required to refresh independent host caches, per-host work is coalesced, and realistic connection cardinality is not shown to create a high-confidence regression.

### Scenario 3: An entitlement-triggered background discovery refresh fails, followed by a model or utility request

- Critical path: The failed refresh itself is background work, but clearing the cache moves the next \`/copilot\_internal/user\` lookup onto the critical path of \`models\`, \`responses\`, \`messages\`, utility completion, restricted telemetry resolution, or another client lookup.
- Scaling input: Failed entitlement refreshes across active token/host pairs; concurrent calls coalesce rather than multiplying requests.
- Effective concurrency: One discovery retry is coalesced per token/host; all concurrent model callers wait behind that same promise. Different hosts/tokens retry independently.
- Cache behavior: The refresh begins only from an unexpired cached client. The new non-401/403 failure branch clears \`skuCell.value\`; the next \`\_getEntryForToken\` sees a miss. Concurrent next callers share \`request.promise\`, but the first must perform a new discovery. Ordinary cache-refresh failures already preserve an unexpired previous entry.
- Mechanism confidence: Very high: the added cache clear, subsequent miss logic, HTTP fetch, and model-method awaits are explicit.
- Magnitude uncertainty: The added latency equals account-discovery network duration and depends on transient failure prevalence, but the extra blocking boundary is deterministic after the failure and can be especially visible while the endpoint remains degraded.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/shared/copilotApiService.ts:968 then \`\_getEntryForToken\`/\`\_buildClientForToken\`</code>: Retry \`/copilot\_internal/user\` after the background refresh discarded the valid cached CAPI client.; cardinality: One coalesced retry per affected token/host after each failed entitlement refresh; if service remains unavailable, the user-facing operation waits and fails.
    - Introduced by diff: true; previous behavior: No entitlement-triggered failure could evict the valid entry; existing ordinary refresh failures retain an unexpired client.; critical-path effect: Directly blocks the next model/utility operation before its actual CAPI request can be issued.
  - network at <code>src/vs/platform/agentHost/node/shared/copilotApiService.ts:635, 671, 719, and 840</code>: The actual models/chat/utility CAPI request that can only start after client discovery resolves.; cardinality: One intended operation per caller, unchanged by the diff.
    - Introduced by diff: false; previous behavior: With a valid cached client, these requests proceeded directly to their intended endpoint.; critical-path effect: Its start is delayed by the newly forced discovery miss.
- Verdict: Reportable cache-lifecycle regression: a best-effort background failure converts an unexpired warm cache into a user-visible critical-path network miss.
