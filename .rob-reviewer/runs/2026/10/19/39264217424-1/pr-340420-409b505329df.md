## Findings (1)

### 1. [medium] Defer repository eligibility checks until a repository is selected

**Finding ID:** `PERF-E56F68F1DFA0`  
**Location:** <code>src/vs/sessions/contrib/automations/browser/automationDialog.ts:2183</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** GitHub repository-visibility network requests  
**Scaling:** One \`client.query.getRepository\` request is queued for every distinct GitHub remote workspace returned by \`\_buildItems\`; the current picker commonly exposes up to 10 recents, and the limiter runs five at a time, so a cold mobile open requires multiple network waves.  
**Outcome:** Excess network traffic on every cold dialog lifetime and delayed mobile workspace-picker opening.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, constructing or opening the automation workspace picker did not preflight repository visibility; the existing cloud-store refresh already checked known repositories separately.  
**Changed behavior:** \`setCloudConfiguration\` now installs an autorun during dialog construction that walks every picker item and calls \`getWorkspaceTarget\`, whose cache miss immediately queues a remote visibility read. The mobile path additionally waits for all of those targets before rendering the sheet.  
**Confidence:** 0.98 — The changed call path, one-request-per-cache-miss implementation, five-request limiter, and mobile \`Promise.all\` wait are directly traced in repository code. Exact network duration varies, but the fan-out and critical-path reachability are deterministic for cold cached GitHub recents.

**Causal diff evidence:** The added call \`value?.getWorkspaceTarget(item.item.folderUri).read(reader)\` at line 2183 is inside a loop over all picker rows and is installed eagerly by the newly added \`setCloudConfiguration\` call during form rendering.

With several remembered GitHub workspaces, merely opening the automation dialog launches a burst of visibility requests even if the user never opens the workspace picker. If a mobile user opens it before those requests finish, the sheet remains busy until all requests complete; 10 recents execute in two batches because concurrency is capped at five.

**Evidence:** \`renderForm\` immediately calls \`workspacePicker.setCloudConfiguration(...)\`; this added autorun loops over \`super.\_buildItems()\` and invokes \`getWorkspaceTarget\` for every GitHub row. \`GitHubCloudAutomationStore.getWorkspaceTarget\` creates a cache entry and queues \`client.query.getRepository(...).private\` on a \`Limiter(5)\` for each miss. \`waitForWorkspaceTargets\` then uses \`Promise.all\` over the same collection before mobile rendering. The recent picker is capped at 10 in the current layout, while the cloud store's existing refresh already performs visibility reads for known repositories, so these are additional per-dialog-lifetime requests rather than reuse of refresh results.

**Suggested direction:** Do not call \`getWorkspaceTarget\` for every recent row during dialog construction or wait for the full collection before showing mobile UI. Validate only the selected row through the existing \`\_dispatchPickerItem\` path, or defer/background row checks after the picker is visible and reuse eligibility established by the store refresh.
