# Performance review: tool calls in dropdown and thinking headers

[PR #279094](https://github.com/microsoft/vscode/pull/279094) at `2921de4c6c3b567d9c3ba57d018164baf3cd1e99`

## Findings (2)

### 1. [medium] Avoid a model request just to finalize each thinking header

**Finding ID:** `PERF-A5E45CF558A2`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatContentParts/chatThinkingContentPart.ts:335</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Language-model provider activations/resolution, remote model requests, streamed response bytes, and provider concurrency/quota  
**Scaling:** The cost is one full title-generation request per finalized thinking section unless it has exactly one captured title and no tools. Tool-containing sections always take this path; parallel chats create the same number of concurrent uncapped requests, and disposed parts do not cancel them.  
**Outcome:** Excess network/model load and lower chat throughput through contention or rate limits; title work can continue consuming resources after the user switches sessions or the rendered part is disposed.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Finalization chose an extracted or generic title locally and made no language-model/provider request.  
**Changed behavior:** Finalization now calls generateTitleViaLLM for common cases (no captured header, multiple headers, or any tool invocation), resolves Copilot models, sends a chat request, consumes the full stream, and passes CancellationToken.None.  
**Confidence:** 0.99 — The new remote boundary, trigger conditions, per-section cardinality, and lack of cancellation are explicit in the changed code and its callers. Exact provider latency/quota impact varies, so severity is medium rather than high.

**Causal diff evidence:** Added line 335 introduces the provider chat request on thinking-section finalization; the deleted implementation completed the header synchronously from local state.

A standard agent turn with thinking plus a tool now launches an additional remote model request after the main response. Rapid or parallel agent workflows fan this out per response, potentially competing with the user's next real chat request; navigation cannot stop already-started decorative title requests.

**Evidence:** \`finalizeTitleIfDefault\` reaches generateTitleViaLLM unless generatedTitle exists or there is exactly one extracted title with zero tools. \`appendItem\` increments toolInvocationCount, making every tool-containing section ineligible for the local path. \`ILanguageModelsService.sendChatRequest\` directly delegates to the provider, while the changed call uses CancellationToken.None and only checks disposal after consuming the entire response stream.

**Suggested direction:** Keep finalization local using the extracted/fallback title. If generated titles are required, move them behind an explicit/deferred path and tie a CancellationTokenSource to the part/response lifecycle, ensuring at most one in-flight title request per response.

### 2. [medium] Keep the raw title stable across streaming updates

**Finding ID:** `PERF-33D6834638CE`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/chatContentParts/chatThinkingContentPart.ts:446</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Markdown parsing/rendering, DOM replacement, file-widget queries and retained widget/listener objects  
**Scaling:** In collapsed thinking mode, the extra work occurs once per progressive thinking update after a header is present, so it grows with the number of streamed chunks; headers containing inline file anchors also retain another widget registration per update until the content part is disposed.  
**Outcome:** Increased main-thread CPU/GC and rendering work during streaming, with potential chat scrolling/animation jank on long reasoning streams.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The previous setter displayed the extracted label and then stored that same raw label in currentTitle. Subsequent updates with the same extracted header matched the guard and skipped title rendering.  
**Changed behavior:** The changed setter displays and stores \`Thinking: ${title}\` while updateThinking continues comparing the next raw extracted title against currentTitle. For a stable title such as \`Plan\`, \`Plan \!== Thinking: Plan\` forever, so every update calls setTitleWithWidgets again.  
**Confidence:** 0.99 — The raw-vs-prefixed mismatch and progressive update call path are explicit. The issue is limited to collapsed mode (fixedScrolling does not update the title while streaming), which affects prevalence but not the mechanism.

**Causal diff evidence:** Added line 446 assigns the prefixed \`thinkingLabel\` to currentTitle; before the diff, updateThinking assigned the unprefixed \`label\`, allowing its unchanged-title guard to succeed.

With \`chat.agent.thinkingStyle\` set to \`collapsed\`, a normal multi-chunk reasoning stream repeatedly reparses and replaces an unchanged title on the UI thread. \`setTitleWithWidgets\` also scans anchors and registers widgets in the part-wide store, amplifying allocation/retention when a title contains a file link.

**Evidence:** \`ChatListItemRenderer.renderChatContentDiff\` calls \`updateThinking\` whenever progressively rendered thinking content changes. \`updateThinking\` extracts the raw header and skips only when it equals currentTitle, but this added assignment stores the prefixed display string. Each miss reaches \`setTitleWithWidgets\`, which invokes the Markdown renderer, replaces label DOM, queries anchors via \`renderFileWidgets\`, and registers any widgets against the long-lived part store.

**Suggested direction:** Track the raw extracted title separately (or store the raw title in currentTitle) and add the \`Thinking:\` prefix only to the rendered value. Also dispose title-specific widgets when replacing the title rather than registering them for the full part lifetime.
