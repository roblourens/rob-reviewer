### Scenario 1: Workbench restoration with Mission Control disabled (the default)

- Critical path: After the workbench is restored, a zero-delay scheduler reads the opt-in setting and returns. No agent-host startup, authentication lookup, IPC configuration, filesystem, database, or network work is reached, so this is off the editor startup critical path beyond the small scheduled callback.
- Scaling input: One contribution instance per window; constant work independent of workspace folders, sessions, and accounts.
- Effective concurrency: RunOnceScheduler coalesces same-tick requests and Throttler serializes configuration callbacks within the window.
- Cache behavior: No cache is needed on the disabled path. The default remains false. The prior code additionally read the fake-endpoint setting before returning; the changed code does less work.
- Mechanism confidence: High: the changed enabled check and complete downstream call path were inspected.
- Magnitude uncertainty: None material; the path terminates before expensive boundaries.
- Expensive boundaries: none found
- Verdict: No regression. Disabled startup remains boundary-free and is slightly narrower than before.

### Scenario 3: Main opt-in changes, AI-hidden withdrawal, workspace/authentication changes, and removed-setting edits

- Critical path: Enabling follows the registration path above. Disabling or hiding AI withdraws immediately and sends one management IPC; if already registered, the Agent Host may serialize one offline heartbeat. Workspace/authentication events schedule a serialized reconfiguration as before. Changes to removed settings no longer schedule or withdraw anything.
- Scaling input: One coalesced update per event burst per window; authentication session events inspect only their added/removed session arrays. Multiple windows share a process-wide Sequencer in the Agent Host.
- Effective concurrency: RunOnceScheduler coalesces events, Throttler serializes per-window work, and the process-side Sequencer serializes configure/withdraw operations. This is unchanged for retained triggers; legacy setting triggers are eliminated.
- Cache behavior: The contribution retains account/session IDs to decide withdrawal and the backend retains the active environment. Withdrawal clears relay/sealing/mirror state and queues an optional offline heartbeat. Removed-setting values are now ignored rather than acting as cache/configuration keys.
- Mechanism confidence: High: all event handlers, coalescing primitives, withdrawal behavior, and downstream sequencing were inspected.
- Magnitude uncertainty: Actual event frequency and number of open windows vary, but the changed trigger set only decreases work for removed settings.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHost.contribution.ts:configuration/session/sentiment/workspace handlers</code>: Configure or withdraw Mission Control through the management channel.; cardinality: One call per serialized retained trigger when configuration proceeds; zero calls for edits to any removed setting after the diff.
    - Introduced by diff: false; previous behavior: Main setting, workspace, authentication, sentiment, and agent-host events already used this path; each legacy setting edit also triggered withdrawal/reconfiguration.; critical-path effect: Affects Mission Control availability, not the editor interaction critical path.
  - network at <code>src/vs/platform/agentHost/node/missionControl/missionControlEnvironment.ts:configure</code>: Optionally send an offline heartbeat on withdrawal, or repeat the bounded registration sequence on reconfiguration.; cardinality: At most one offline request for an established environment per sequenced withdrawal and one coalesced registration attempt on a retained update. Legacy-setting changes now cause zero requests.
    - Introduced by diff: false; previous behavior: Legacy setting changes could previously cause this network work; the diff removes that repeated-work trigger.; critical-path effect: Required only for remote registration state convergence.
- Verdict: No regression. Retained triggers preserve prior costs, while edits to removed settings eliminate authentication, IPC, filesystem/database, and network reconfiguration work.

### Scenario 4: Legacy configurations containing removed fake-endpoint or endpoint values

- Critical path: With the main opt-in false and a stale fake endpoint, the old code could start local test registration; the changed code returns before all boundaries. With the main opt-in true and a stale fake endpoint, the old conflict check failed before authentication while the changed code performs the normal production registration path because the stale key is intentionally no longer a control.
- Scaling input: A bounded migration subset: users with persisted removed keys. Work remains one registration lifecycle per explicitly enabled window, not per key/value or collection item.
- Effective concurrency: The same scheduler, Throttler, process Sequencer, and check-in coalescing apply. No parallel fan-out is added.
- Cache behavior: Removed keys are excluded from configuration registry and event invalidation. Production registration uses the existing backend caches and heartbeat lifecycle described above.
- Mechanism confidence: High: the deleted conflict branch and the new sole opt-in check establish the before/after reachability.
- Magnitude uncertainty: The prevalence of users who both opted in and retained a conflicting fake endpoint is unknown; the added lifecycle is nevertheless bounded to the explicitly enabled feature.
- Expensive boundaries:
  - subprocess at <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHost.contribution.ts:\_configure</code>: For main-enabled configurations formerly vetoed only by a stale fake-endpoint value, start the Agent Host and execute normal production registration.; cardinality: One lazy process startup and one serialized registration lifecycle for an explicitly enabled configuration.
    - Introduced by diff: true; previous behavior: The stale fake-endpoint conflict threw before authentication, process startup, IPC, filesystem/database, or network registration.; critical-path effect: Required for the now-intended Mission Control opt-in; asynchronous to general workbench restoration.
  - network at <code>src/vs/platform/agentHost/node/missionControl/missionControlEnvironment.ts</code>: Run the normal constant-count production identity/registration/JWKS/relay sequence for an explicitly enabled configuration whose stale fake-endpoint value is now ignored.; cardinality: The same cold and steady-state counts as the supported opt-in path; no scaling with the number of stale settings.
    - Introduced by diff: true; previous behavior: The old stale-value veto prevented these calls; conversely, with the main setting false a stale fake endpoint could cause local test registration, which the diff removes.; critical-path effect: Determines availability of the explicitly enabled feature.
- Verdict: No actionable performance finding. The only legacy edge that newly reaches expensive work has the main registration opt-in explicitly enabled, and executing that registration is the intended behavior of removing the obsolete veto; disabled users see a reduction in work.

**Summary:** Completed the performance pass over all three changed files and traced startup, configuration events, authentication, subprocess/IPC, filesystem/database, SDK policy, HTTP, relay, heartbeat, cache, cleanup, and concurrency behavior. No high-confidence actionable performance regression was introduced, and there is insufficient evidence that the cleanup of legacy reconfiguration triggers is a shipped regression fix requiring blame-based learning.
