## Performance regression fixes detected (1)

### 1. boundary-fanout

**Fix location:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatThinkingContentPart.ts:1615` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatThinkingContentPart.ts:1686`  
**Introducing path:** `src/vs/workbench/contrib/chat/browser/chatContentParts/chatThinkingContentPart.ts`  
**Introducing commit:** `49b5f6e36f68ec6be4ed6e81ad18dafbe9fcb94c`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `network`  
**Confidence:** 0.97

**Mechanism:** Each newly finalized persistent tool group launched asynchronous utility-model title generation, including a network-backed sendChatRequest with a five-second cancellation timeout. Responses containing several alternating tool/reasoning groups could launch one request per finalized tool group without a shared concurrency limiter, consuming network/model capacity for titles that this change replaces with deterministic step counts.

**Symptom:** Redundant utility-model network traffic and background model work scaled with the number of persistent tool groups in an agent response, with requests able to overlap while later groups continued streaming.

**Fixed behavior:** Persistent tool chains now set their stable step-count fallback and return before title reuse/cache/model generation, eliminating utility-model selection and chat requests for those groups while leaving title generation enabled for persistent reasoning sections.

**Evidence:** Before the PR, finalizeTitleIfDefault set a fallback for isToolChain but then continued into generateTitleViaLLM. With the setting defaulting to true, a live persistent tool group without reusable metadata/cache selected copilot-utility-small and called sendChatRequest; finalizeThinkingPart is reached each time streaming transitions from one persistent group to the next and at response completion. The added early return at line 1615 now prevents that boundary, and the new test proves modelSelections remains 0 for a two-tool chain.

- Effective concurrency: Before the fix, generateTitleViaLLM had a per-call cancellation source but no shared limiter or coalescing, so requests from separately finalized groups could overlap. After the diff, tool groups launch none.

### Scenario 3: A completed or restored persistent tool group is collapsed, expanded, or has tool-row visibility change.

- Critical path: Completion and visibility changes update the title and expansion state synchronously. Lazy tool DOM is materialized only on first expansion; the diff preserves that behavior and now always uses the inexpensive visible-step count for the title.

- Effective concurrency: No subprocess, IPC, filesystem, database, or network boundary is reached after the new tool-chain early return; visibility observers run synchronously per changed tool visibility.
- Cache behavior: Restored generated titles and persisted title-cache values are deliberately ignored for tool groups; this does not cause misses to trigger generation because the early return also bypasses generation entirely.
- Mechanism confidence: High: tests establish zero materialization before expansion and deterministic count updates after visibility changes.
- Magnitude uncertainty: DOM update cost depends on UI state, but the changed title calculation is constant-time and lazy materialization remains bounded to first expansion.
- Expensive boundaries: none found
- Verdict: No performance regression; the change avoids title model work without adding eager DOM construction or collection scans.
