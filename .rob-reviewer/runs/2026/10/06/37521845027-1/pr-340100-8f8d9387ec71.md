# Performance review: chat: Share and rate-limit core utility model requests

[PR #340100](https://github.com/microsoft/vscode/pull/340100) at `8f8d9387ec715d4e3a0023233f87185a548564ad`

## Findings (1)

### 1. [low] Index pending requests by key

**Finding ID:** `PERF-031A7E222234`  
**Location:** <code>src/vs/workbench/contrib/chat/common/chatUtilityModelService.ts:71</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** UI-thread CPU spent scanning pending request objects and comparing keys  
**Scaling:** For B uncached finalized thinking blocks, the three-wide limiter keeps nearly all B requests in \`\_pending\`, so the per-request linear lookup performs about B(B-1)/2 key comparisons during cold restoration.  
**Outcome:** Quadratic CPU work can delay chat restoration and briefly block UI responsiveness in long sessions before the limited network work progresses.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Each thinking block sent directly through \`ILanguageModelsService\`; there was no shared pending collection and therefore no collection-wide scan for every title request.  
**Changed behavior:** Every keyed utility request now linearly scans the full pending set before enqueueing. Restoring a long response finalizes one title per uncached thinking block, and line 1884 marks each as background so only three drain concurrently.  
**Confidence:** 0.96 — The renderer-to-title-to-service call path, one key per block, and three-request drain limit are explicit in code, making the quadratic mechanism certain. Only the wall-clock magnitude varies with how many uncached blocks a user's long session contains.

**Causal diff evidence:** Added line 71 introduces \`Iterable.find(this.\_pending, ...)\` on every keyed request; the same PR routes each thinking title through this keyed, three-wide background queue, so the growing scan did not exist before the diff.

Opening or rerendering a long chat with many uncached thinking blocks schedules one keyed title request per block; while model-selection continuations run on the workbench thread, lookup cost grows quadratically rather than linearly, causing avoidable restore latency/jank. Exact duration depends on session size, so severity is low, but the call path and scaling are deterministic.

**Evidence:** \`chatListRenderer.finalizeThinkingPart\` calls \`finalizeTitleIfDefault\` for completed thinking sections; \`ChatThinkingContentPart\` then calls \`sendRequest\` with a session/block cache key and \`background: true\`. The new limiter admits only three requests (line 82), leaving the rest in \`\_pending\`, while line 71 scans that entire set for each subsequent block. The cache permits 1,000 stored entries and cold/missing entries all reach this path.

**Suggested direction:** Maintain a \`Map&lt;string, IPendingRequest&gt;\` alongside the lifecycle set (insert in \`\_start\`, delete in \`\_settle\`) so keyed coalescing is O(1), while retaining the set only for unkeyed requests and disposal.

### 1. concurrency-burst

**Fix location:** `src/vs/workbench/contrib/chat/common/chatUtilityModelService.ts:82` (`RIGHT`)  
**Blamed base line:** `src/vs/workbench/contrib/chat/browser/widget/chatContentParts/chatThinkingContentPart.ts:1876`

**Mechanism family:** `concurrency-burst`  
**Performance category:** `network`  
**Confidence:** 0.96

**Mechanism:** Each finalized uncached thinking block immediately started its own language-model request, so restoring a session with B blocks created B concurrent extension-host/network requests with no aggregate limiter or cross-render coalescing.

**Symptom:** Long-session restoration could burst utility-model traffic and receive HTTP rate limits; the PR metadata reports 429 telemetry, while the changed call path and new concurrency test directly establish the prior unbounded fan-out.

**Fixed behavior:** Thinking-title requests now enter one shared limiter capped at three active background requests, share an in-flight request by cache key, and drop queued requests after all callers cancel.

**Evidence:** The deleted base call at the blamed line directly invoked `sendChatRequest` from every block's title finalization. The added caller marks title requests `background: true` with a stable key, line 82 queues them in the service's three-wide limiter, and the added test asserts only three background requests run concurrently while duplicate `b1` callers produce one send.

### Scenario 1: Cold or rerendered long chat session generates titles for finalized thinking blocks

- Critical path: Rendering/finalizing each completed thinking section starts title generation asynchronously after model selection. Title text is not required for the chat row to render because a fallback appears after two seconds, but the keyed enqueue/lookup runs on the workbench event loop and can affect restoration responsiveness.
- Scaling input: B finalized thinking blocks without reusable generated/profile-cached titles. Each stable session/block key is distinct after in-flight deduplication, so effective cardinality is B; duplicate renders of the same key share one remote request.
- Effective concurrency: Background model sends are globally limited to three. Requests beyond three remain pending; same-key callers share one promise. The added linear scan over this growing pending set makes cold enqueue CPU quadratic in B.
- Cache behavior: Warm profile-cache hits return before model selection and produce zero model calls. Cold misses enqueue one request per distinct key. Pending requests coalesce by key; canceled requests are dropped only before start. Failures are not negatively cached, while a model-level rate-limit entry suppresses sends until expiry.
- Mechanism confidence: High: renderer finalization, unique cache keys, the three-wide limiter, and the full-set scan are explicit in code.
- Magnitude uncertainty: The quadratic key-lookup mechanism is deterministic, but exact pause duration depends on the number of uncached blocks and hardware; this uncertainty is reflected in low severity.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/common/chatUtilityModelService.ts:120, ChatUtilityModelService.\_run</code>: Language-model request crosses from workbench core to the extension-host model provider.; cardinality: One IPC request per distinct cold title key that starts; warm cache hits produce zero, duplicate pending keys share one, and rate-limited queued work is skipped before IPC.
    - Introduced by diff: false; previous behavior: The same IPC request occurred once per rendered block, but all blocks started immediately and rerenders could duplicate it.; critical-path effect: Off the title fallback/render critical path after enqueue, but completion supplies and persists the generated title.
