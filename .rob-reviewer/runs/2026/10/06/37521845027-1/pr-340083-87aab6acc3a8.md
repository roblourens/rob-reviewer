# Performance review: sessions: enable archive nudge by default

[PR #340083](https://github.com/microsoft/vscode/pull/340083) at `87aab6acc3a84514b1ca74fd36cf4775acbda46a`

## Findings (1)

### 1. [medium] Stop polling terminal PRs when enabling the nudge

**Finding ID:** `PERF-877547DACCD4`  
**Location:** <code>src/vs/sessions/contrib/chat/browser/chat.contribution.ts:562</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** Authenticated GitHub HTTP requests, response processing, and retained PR model/polling objects.  
**Scaling:** Cost grows as 2 \* distinct associated PRs \* visible minutes, with additional review-page requests possible when the reviews endpoint returns changed paginated data. Polling is coalesced per shared PR model but is not bounded by nudge age.  
**Outcome:** Persistent excessive network I/O and GitHub API quota consumption while an already-actionable archive nudge remains on screen.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** On Stable the default was false. The nudge temporarily resolved/polled candidate PRs only until reportWouldShow cleared experimentTriggerPending; eligibleSession then became undefined and its derived-store references and polling handles were disposed. The disabled-path test confirms references=0 and polling=0 after that transition.  
**Changed behavior:** Defaulting the setting to true keeps eligibleSession alive after reportWouldShow and after every PR reaches Merged, so the models derived at sessionArchiveNudge.ts:375-383 retain one startPolling handle per distinct PR for as long as the completed session remains visible and the nudge is not dismissed, archived, or superseded.  
**Confidence:** 0.99 — The changed Stable default, enabled/disabled lifecycle branches, retained-poller test assertions, 60-second scheduler, and two concrete REST calls per refresh are all directly traced. Only how long users leave such a view visible and typical PR count are uncertain, which affects magnitude rather than the mechanism.

**Causal diff evidence:** The added \`default: true\` at chat.contribution.ts:562 changes Stable users without an override from the disposing disabled branch to the enabled branch. sessionArchiveNudge.test.ts:438-449 explicitly verifies that an enabled, already-merged two-PR nudge retains \`references: 2, polling: 2\`, whereas the disabled test at lines 318-331 ends with \`polling: 0\`.

A Stable user who leaves a completed merged session visible now generates about 120 authenticated GitHub requests per distinct PR per hour despite merged being terminal. Multi-PR sessions multiply this traffic, consuming rate-limit budget and network/CPU resources and potentially throttling user-initiated GitHub operations.

**Evidence:** Each retained GitHubPullRequestModel polls every 60 seconds (githubPullRequestModel.ts:14,103-129). Every refresh performs getPullRequest and getReviews concurrently (lines 134-137), which issue authenticated REST requests to \`/pulls/{n}\` and \`/reviews\` (githubPRFetcher.ts:194-220) with the renderer cache disabled (githubApiClient.ts:150-164). Model references are shared per PR, so effective fan-out is one poller and at least two HTTP requests per distinct associated PR per minute; the nudge does not add duplicate polling for a PR already polled by another consumer.

**Suggested direction:** Retain the resolved model state needed to render the nudge, but dispose or avoid each polling handle once its PR is Merged (or at least stop all polling once every candidate is merged); restart only when the candidate PR set changes.

- Mechanism confidence: Very high: enabled/disabled test assertions, observable ownership, 60-second scheduling, and two concrete REST calls per refresh directly prove the lifetime and cardinality.

- Cache behavior: Dismissal/impression/profile keys are persisted and invalidated on archive/delete/unarchive as before. Once an impression records continuation, the exposed PR set is suppressed; there is no repeated model creation for that set.
- Mechanism confidence: High for cardinality and sequencing; provider-specific boundary cost varies by session backend.
