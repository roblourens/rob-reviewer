### Scenario 1: Workbench startup registers the Open Worktree Cleanup action and its menu placements.

- Critical path: Module evaluation constructs the Action2 descriptor and registers it; the diff removes one SessionItemContextMenu descriptor while retaining Command Palette and Sessions header registration. No asynchronous work or expensive boundary is on this path.
- Scaling input: One static action registration per workbench window; cost scales with the number of declared menu placements, which decreases from two explicit menu placements to one.
- Effective concurrency: Synchronous, single registration during contribution loading; no queue or parallel work.
- Cache behavior: Menu metadata is held by the global registry for the window lifetime. The diff retains one fewer menu item; there are no cache misses or negative-cache states.
- Mechanism confidence: High: the changed hunk deletes only the SessionItemContextMenu object from the action descriptor.
- Magnitude uncertainty: The exact micro-cost of one menu descriptor is unmeasured, but the direction is strictly reduced allocation and registry work.
- Expensive boundaries: none found
- Verdict: No regression. Startup allocation and retained menu metadata decrease slightly, and no command handler work is executed during registration.

### Scenario 2: A user opens a context menu for a session row.

- Critical path: The UI event builds a per-session context-key overlay, creates SessionItemContextMenu, evaluates visible actions, and renders the menu. The removed contribution is no longer evaluated or rendered; selecting other actions follows unchanged handlers.
- Scaling input: One menu construction per context-menu opening; effective cardinality is the registered actions for that single menu, not the total session count. The action count decreases by one.
- Effective concurrency: Synchronous UI-event handling for one opened context menu; repeated user openings are serialized by interaction and the previous menu disposable is replaced.
- Cache behavior: Static contributions come from MenuRegistry, while a fresh context overlay/menu instance is created for each opening. Removing the item avoids its condition evaluation on both cold and repeated openings; no cache is defeated.
- Mechanism confidence: High: sessionsList.ts creates the same menu on demand, and the diff only removes one declarative contribution from that menu.
- Magnitude uncertainty: The saved per-opening CPU/allocation is small and unmeasured, but there is no plausible increase in work.
- Expensive boundaries: none found
- Verdict: No regression. The changed path performs less menu evaluation and rendering work.

### Scenario 3: A screen-reader user opens Sessions chat help or worktree-cleanup editor help.

- Critical path: Accessible help creation synchronously localizes fixed strings, stores them in a short array, and joins them when content is requested. The diff shortens two fixed strings and adds no service call or deferred work.
- Scaling input: One fixed-size string construction per help-provider invocation; content size does not scale with sessions or worktrees.
- Effective concurrency: Synchronous on-demand provider construction; no parallelism, limiter, queue, or backpressure is involved.
- Cache behavior: No data cache is involved. Localization lookup behavior is unchanged, using the same keys, and the resulting strings are slightly shorter.
- Mechanism confidence: High: both accessibility hunks alter only literal text passed to existing localize calls.
- Magnitude uncertainty: String allocation savings are negligible and unmeasured, but the change cannot create scaling work.
- Expensive boundaries: none found
- Verdict: No regression. CPU and allocation are unchanged in cardinality and marginally reduced in bytes.

### Scenario 4: A user invokes Open Worktree Cleanup from the remaining Command Palette, Sessions More Actions menu, or storage suggestion.

- Critical path: The unchanged action suppresses the suggestion and opens SessionWorktreeCleanupEditor. The editor then awaits getWorktrees before rendering rows; a cold measurement is therefore on the editor-content critical path, while warm measurements reuse cached results.
- Scaling input: Cold disk-usage measurement scales with sessions that own worktrees, grouped per session; each session measurement accounts for its distinct worktrees. Menu removal does not increase this effective cardinality and removes one former invocation surface.
- Effective concurrency: Disk usage calls are bounded by Limiter(2), concurrent measurements for the same session signature are coalesced, and each call has a 10-second timeout.
- Cache behavior: Measured worktrees are cached for one hour when the session signature is unchanged; concurrent requests share one measurement. Session changes invalidate timestamps/signatures as before. The diff does not change cache keys, success/failure behavior, or coalescing.
- Mechanism confidence: High: the action handler and cleanup service are unchanged, and the deleted descriptor was only an additional menu entry pointing to the same command.
- Magnitude uncertainty: Actual scan duration depends on the number and location of worktrees, but neither call count, concurrency, cache behavior, nor critical-path placement is increased by this diff.
- Expensive boundaries:
  - filesystem at <code>src/vs/sessions/contrib/sessionInputBanners/browser/sessionWorktreeCleanupService.ts:\_measureWorktrees</code>: Measure session worktree disk usage via ISessionsManagementService.getSessionWorktreeDiskUsage.; cardinality: At most one disk-usage call per worktree-owning session on a cold measurement, with two calls active concurrently; warm and coalesced requests reuse one-hour cached/shared results.
    - Introduced by diff: false; previous behavior: The same editor command and bounded/cached measurement ran after selecting Open Worktree Cleanup from any prior surface; the diff removes the session-row context-menu surface and leaves all execution code unchanged.; critical-path effect: A cold scan must complete before the cleanup editor renders its worktree rows; it is not performed merely by opening a session context menu or accessibility help.
- Verdict: No regression. Existing filesystem work remains bounded and cached behind explicit command invocation, while the diff only removes one way to invoke it.

**Summary:** Reviewed all three changed files and traced startup registration, per-session menu construction, accessibility help generation, and the remaining cleanup-editor filesystem path. The PR removes one static/per-open menu item and shortens fixed help text; it adds no work, retention, fan-out, boundary call, concurrency, or critical-path latency. No performance findings were submitted.
