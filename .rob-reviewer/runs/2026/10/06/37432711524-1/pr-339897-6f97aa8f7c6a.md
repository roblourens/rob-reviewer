# Performance review: extensions: wait for installed inventory before installing

[PR #339897](https://github.com/microsoft/vscode/pull/339897) at `6f97aa8f7c6ab3b8fc907d988179d53444128040`

## Findings (1)

### 1. [medium] Reuse the initial inventory instead of rescanning every server

**Finding ID:** `PERF-CC780CA01388`  
**Location:** <code>src/vs/workbench/contrib/extensions/browser/extensions.contribution.ts:500</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** Sequential extension-management IPC calls, extension inventory serialization, filesystem/cache scans, and per-extension object remapping.  
**Scaling:** Cost grows with the number of configured extension servers (up to local, remote, and web, queried serially) and the installed extension inventory returned by each server; it is paid once per command invocation even after initialization.  
**Outcome:** Increased command latency and delayed route/feature startup before installation or enablement can proceed.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** The command synchronously searched the already-populated in-memory \`local\` array and immediately proceeded to install/enable; it issued no inventory IPC or filesystem scan on this path.  
**Changed behavior:** Every string-based invocation of \`workbench.extensions.installExtension\` now refreshes all configured extension servers before deciding whether to install or enable one extension.  
**Confidence:** 0.98 — The changed command path, \`queryLocal\` implementation, initialization path, and \`getInstalled\` IPC/filesystem implementation are directly traced. The exact duration varies with server latency, cache state, and extension count, but the added sequential boundary calls and collection-wide work are certain.

**Causal diff evidence:** RIGHT line 500 replaces an in-memory \`extensionsWorkbenchService.local.find(...)\` with \`await extensionsWorkbenchService.queryLocal()\` before the same lookup.

Invoking the install command— including URI-driven, chat recommendation, and terminal speech installs—blocks before installation/progress on full installed-extension inventory work. In remote or multi-server windows this adds sequential IPC/remote latency; for already-installed extensions, the scan is the entire cost where the old path was an immediate memory lookup.

**Evidence:** \`ExtensionsWorkbenchService.queryLocal\` calls \`queryInstalled\` sequentially for local, remote, and web servers; \`queryInstalled\` unconditionally calls \`fetchInstalledExtensions\`, which invokes \`getExtensionsControlManifest\` and \`getInstalled\`. The IPC client sends \`getInstalled\` across its channel, and the native implementation runs \`scanAllExtensions\`, resolving extension collections and mapping every installed extension. The service constructor already starts \`initialize() -&gt; queryLocal()\`, while the added tests intentionally invoke this command before that inventory completes, so the new call can also duplicate the startup request instead of awaiting the existing \`whenInitialized\` promise.

**Suggested direction:** Wait for the service's existing initialization/inventory promise and then search \`local\` (or expose/coalesce a dedicated initial-inventory promise), rather than calling the refresh-oriented \`queryLocal()\` on every command invocation. This preserves the startup correctness requirement without rescanning warm inventories or duplicating the constructor's in-flight query.
