# Performance review: agentHost: fix SSH and WSL relay reuse on reconnect

## Findings (4)

### 1. [medium] Bound SSH relay replacement history

**Finding ID:** `PERF-14D012A228EF`  
**Location:** <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:1173</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Retained map entries and string UUIDs, plus synchronous map traversal CPU during relay release  
**Scaling:** After R successful reconnects on a long-lived host, \`\_replacements\` retains O(R) aliases. \`\_releaseRelay\` calls \`\_pruneReplacements\`, which iterates all aliases and \`\_getCurrentLease\` walks each remaining chain, making a renewal perform O(R²) map lookups in the worst case.  
**Outcome:** Retained memory and progressively increasing shared-process CPU/reconnect latency during network churn.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** SSH reconnect reused the stable connection key and retained no historical relay-ID chain.  
**Changed behavior:** Every successful renewal retains a predecessor-to-successor UUID in \`\_replacements\` for the lifetime of the current relay chain.  
**Confidence:** 0.99 — The retention and nested traversal follow directly from the added map write and prune implementation. User reconnect counts vary, but the growth mechanism and complexity are deterministic.

**Causal diff evidence:** The added \`\_replacements.set(expectedConnectionId, result.connectionId)\` creates one durable historical alias per successful reconnect; no equivalent state existed before this diff.

A long-lived SSH agent connection that repeatedly recovers from network changes accumulates every old relay ID; later reconnects synchronously rescan increasingly long chains before recovery completes.

**Evidence:** Line 1173 appends \`oldId -&gt; newId\`. \`\_pruneReplacements\` keeps every alias while its chain reaches the live lease, and \`\_getCurrentLease\` follows successor links one by one. Entries are removed only when the final chain no longer resolves or the entire session closes, so successful renewals do not bound the history.

**Suggested direction:** Use \`\_pendingReconnects\` for in-flight coalescing, then remove the superseded ID once callers have adopted the result; if stale lookup must remain, path-compress it to a bounded direct alias and explicitly expire old aliases.

### 2. [medium] Bound WSL relay replacement history

**Finding ID:** `PERF-E6AC6549B5D6`  
**Location:** <code>src/vs/platform/agentHost/node/wslRemoteAgentHostService.ts:521</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Retained UUID strings/map entries and synchronous map traversal CPU  
**Scaling:** With R successful recoveries in one long-lived distro session, the map holds O(R) IDs. Every \`\_closeRelay\` invokes \`\_pruneReplacements\`; it scans all aliases and calls \`\_getCurrentRelay\`, which can traverse O(R) links for each key, producing O(R²) lookup work.  
**Outcome:** Unbounded per-session memory growth and progressively slower relay replacement/cleanup.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** WSL reconnect replaced the single connection directly and retained no predecessor alias map.  
**Changed behavior:** Each successful WSL relay renewal adds another old-to-new connection ID that remains reachable while the current lease lives.  
**Confidence:** 0.99 — The changed map write, chain walker, and prune condition prove linear retention and quadratic worst-case pruning. Only the number of reconnects in typical sessions is uncertain.

**Causal diff evidence:** The added \`\_replacements.set(expectedConnectionId, result.connectionId)\` introduces one retained alias per successful reconnect; the base implementation had no replacement-history structure.

On a flaky network or repeatedly suspended machine, a WSL agent that successfully reconnects many times keeps all prior relay IDs and spends increasing shared-process time pruning them on subsequent recoveries.

**Evidence:** The changed line records \`expectedConnectionId -&gt; result.connectionId\`. \`\_pruneReplacements\` deliberately retains aliases whenever \`\_getCurrentRelay\` can reach the current lease, so every predecessor in a successful chain survives until final session teardown.

**Suggested direction:** Drop the old alias after the coalesced reconnect promise has handed out the new ID, or retain only a bounded/path-compressed direct alias with explicit expiry for late callers.

### 3. [medium] Do not drop every SSH window on one failed relay acquisition

**Finding ID:** `PERF-A62B704669F6`  
**Location:** <code>src/vs/platform/agentHost/node/sshRemoteAgentHostService.ts:1282</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** SSH connections and exec channels, remote endpoint-discovery commands, relay sockets, and renderer IPC reconnect work  
**Scaling:** The failure closes one lease per active renderer on the host. The next session setup is coalesced, but it still performs one full SSH handshake/discovery sequence and then creates a replacement relay for each affected renderer.  
**Outcome:** A per-channel failure causes cross-window reconnect latency, extra SSH/network traffic, and a burst of relay recreation.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** An existing-host connect returned the existing connection and created no additional relay; reconnect replaced the sole relay, so failure of a newly requested lease could not fan out to multiple active clients.  
**Changed behavior:** Any failed relay lease acquisition now disposes the shared SSH session, which disposes all sibling leases and forces all renderers to recover.  
**Confidence:** 0.96 — The changed catch, session close listener, expensive reconnect path, and multi-lease test establish the mechanism. The only uncertainty is how often a relay channel fails independently of an otherwise usable SSH session.

**Causal diff evidence:** The added \`session.dispose();\` at line 1282 converts one \`\_createRelayLease\` failure into disposal of the shared session introduced by this diff.

If a new window or one reconnecting client hits a transient \`forwardOut\`/relay error while sibling leases are healthy, all windows lose their relays. Recovery redoes \`\_connectSSH\`, remote \`uname\` calls, CLI installation checks, and endpoint discovery before those windows can proceed.

**Evidence:** The new catch unconditionally calls \`session.dispose()\`. \`SSHConnection.onDidClose\` then removes and disposes every lease for that session and fires close events. \`\_connect\` proves the replacement critical path includes \`\_connectSSH\`, two remote \`uname\` execs, \`\_ensureCLIInstalled\`, and \`runAgentEndpoints\`. The added regression test for a failed lease renewal expects both existing lease IDs to close and a second SSH client/discovery pass.

**Suggested direction:** Keep the shared SSH session and sibling leases alive when only one relay creation fails; dispose the session only when there are no live leases or a bounded session-level health check confirms the SSH connection itself is unusable.

### 4. [medium] Do not restart every WSL client when one relay dial fails

**Finding ID:** `PERF-FCEA69034AE9`  
**Location:** <code>src/vs/platform/agentHost/node/wslRemoteAgentHostService.ts:480</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** WSL subprocess launches, WebSocket connections, IPC close/reconnect notifications, and remote CLI bootstrap work  
**Scaling:** The failure fans out across the number of active renderer leases for the distro. Session creation is coalesced to one bootstrap, but every affected renderer then performs recovery and acquires its own replacement relay.  
**Outcome:** A transient per-relay open failure can interrupt all windows and put a full WSL platform probe and agent-host bootstrap on their recovery critical path.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** An already-live distro connect returned the existing connection and did not open another WebSocket; reconnect owned the single connection, so one new client could not evict multiple healthy clients.  
**Changed behavior:** A failed WebSocket acquisition for one lease now closes the shared distro session, which closes every other lease and kills the shared bootstrap process.  
**Confidence:** 0.96 — The fanout and subprocess restart are direct in the changed call path and asserted by the new test. Only the frequency of transient per-relay failures while sibling sockets remain healthy is uncertain.

**Causal diff evidence:** The added line \`this.\_closeSession(session.distro, session);\` runs for any \`\_createRelay\` exception, even when other entries in \`\_connections\` still reference a working shared session.

When another window connects or one client renews while existing leases are healthy, a single \`\_openWebSocket\` rejection closes all active sockets and kills the child; the next recovery runs \`wsl.exe\` platform detection and respawns the agent host, delaying every attached window.

**Evidence:** \`connect\` now shares one \`IWSLSession\` but creates an independent relay per caller. The added catch at line 480 calls \`\_closeSession\`; that method iterates all leases, closes them, and kills \`session.child\`. \`\_connectUnguarded\` shows recovery invokes \`\_resolvePlatform\` (\`wsl.exe\`) and \`\_spawnAgentHost\`. The added test explicitly expects a WebSocket-open failure on an existing session to close both leases, kill the old child, and spawn a second child.

**Suggested direction:** Reject and clean up only the failed lease while other live leases remain; close/rebootstrap the shared session only on child/session failure or after a bounded health check establishes that the shared endpoint is dead.

- Effective concurrency: \`\_pendingSessions\` coalesces SSH session creation per connection key, while callers awaiting that session invoke \`\_acquireRelay\` independently and may create relays concurrently. \`\_pendingConnections\` coalesces same-renderer connects and \`\_pendingReconnects\` coalesces renewals for one expected lease.
- Cache behavior: A live \`\_connections\` session is the positive cache. SSH config resolution also has time-bounded reuse. Failed session creation is removed from \`\_pendingSessions\`, so retries are not negatively cached. Warm connects avoid SSH/platform/discovery work but not per-client relay creation.

### Scenario 4: WSL relay renewal or additional-client WebSocket open fails while sibling leases are active

- Cache behavior: The failure unconditionally evicts the live session cache. Recovery is cold with no negative cache. \`\_replacements\` retains every successful predecessor alias while the current relay remains reachable.
- Mechanism confidence: High: the changed catch, session close loop, child kill, and test expecting two lease closes and a second child prove the mechanism.

    - Introduced by diff: true; previous behavior: A connect to an already-live distro returned the existing connection and did not perform another WebSocket open.; critical-path effect: Rejects the caller and, through session closure, blocks every sibling client.

- Verdict: Reportable boundary fanout. Separately, replacement aliases are retained for the full live chain, causing O(R) memory and O(R²) worst-case pruning after R successful recoveries.
