# Performance review: agentHost: avoid peer hydration and repeated MCP installs

[PR #339922](https://github.com/microsoft/vscode/pull/339922) at `33a7cee11519ba13c67fec2142128325e2980061`

## Findings (1)

### 1. [medium] Avoid probing every hydrated peer database on every turn

**Finding ID:** `PERF-5D60C5FC587F`  
**Location:** <code>src/vs/platform/agentHost/node/agentService.ts:7931</code> (<code>RIGHT</code>)  
**Performance category:** <code>io</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** One filesystem stat plus a SQLite database acquisition/query (and potentially connection open/migrations/close) for every non-tool peer chat  
**Scaling:** For a session with P peer chats and T newly started turns, the added work is P filesystem probes and P SQLite lookups per turn, or O(P\*T); Promise.all makes each turn issue the P operations as an aggregate I/O burst.  
**Outcome:** Increased message-send latency and filesystem/SQLite I/O, with later actions for the same client also blocked behind the lookup queue.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** The old \`\_getUnresolvedPeerChats\` selected only peers without hydrated state. Once peers were hydrated, \`requiresTurnOwnerResolution\` was false, so subsequent \`ChatTurnStarted\` actions stayed on the synchronous fast path with no peer filesystem or database work.  
**Changed behavior:** \`\_getPeerChatsForTurnValidation\` now returns hydrated as well as unresolved peers, and this \`Promise.all\` invokes \`tryOpenDatabase(...).hasTurn(...)\` for every peer whenever a turn starts and the in-memory collision check misses.  
**Confidence:** 0.99 — The changed call path, per-peer filesystem stat, per-peer SQL query, await on the send critical path, and prior hydrated-peer fast path are all explicit in production code; only the exact wall-clock cost and typical peer count vary by machine and session.

**Causal diff evidence:** RIGHT line 7931 adds \`Promise.all(peerChats.map(...))\` over all eligible peers; together with changed \`\_getPeerChatsForTurnValidation\`, hydrated peers that the deleted \`\_getUnresolvedPeerChats\` filtered out are now included on every turn.

After a session has multiple ordinary peer chats, starting any new turn waits for all peer database probes before dispatching the message. This repeats on every turn and becomes visible as send latency on slower or scanned filesystems as peer count grows.

**Evidence:** \`dispatchAction\` awaits \`\_isPersistedTurnIdUsedByAnotherChat\` before \`\_dispatchActionNow\`. The changed helper maps every non-default, non-tool, non-subagent peer through \`tryOpenDatabase\` and \`hasTurn\`. \`SessionDataService.tryOpenDatabase\` always performs \`fileService.stat\` and then acquires a ref-counted SQLite connection; \`hasTurn\` executes a SQL query, and disposing the last reference closes the connection. The added tests explicitly exercise this lookup with an already \`hydrated\` peer, proving that the repeated I/O is intentional and reachable after hydration rather than limited to one-time restore.

**Suggested direction:** Keep hydrated peers on an in-memory fast path by retaining the host/event/local turn-ID information needed for validation when they are loaded and updating it with turn writes/deletes; restrict SQLite probes to unresolved peers (or provide a session-level persisted ID index) so validation does not fan out to every peer for every send.


## Performance regression fixes detected (2)

### 1. boundary-fanout

**Fix location:** `src/vs/platform/agentHost/node/agentService.ts:7271` (`LEFT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentService.ts:7271`  
**Introducing path:** `src/vs/platform/agentHost/node/agentService.ts`  
**Introducing commit:** `b10759526092db723a7217e7627ae309d74719f4`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `latency`  
**Confidence:** 0.97

**Mechanism:** Every `ChatTurnStarted` with unresolved peers awaited `_resolvePeerChatsForTurnValidation`, which called `resolveChatState` for all unresolved chats in parallel. A restored chat's resolver materializes its provider backing and full history, so turn validation eagerly started provider/runtime and history work once per unresolved peer.

**Symptom:** Starting a turn in a restored multi-chat session was blocked by peer runtime/history hydration, with latency scaling across unresolved peers before the message could be dispatched.

**Fixed behavior:** The PR deletes the awaited peer-state resolution and replaces it with direct best-effort checks of existing peer SQLite databases, excluding tool/subagent chats, so provider runtimes and full histories are no longer materialized solely to validate a turn ID.

**Evidence:** The deleted base line 7271 awaited `_resolvePeerChatsForTurnValidation` on the `ChatTurnStarted` dispatch critical path. That helper mapped unresolved peers to `stateManager.resolveChatState`; `resolveChatState` invokes each registered resolver, and production registration points to `_materializeRestoredPeerChat`, which loads backing state/history. The changed dispatch instead awaits `_isPersistedTurnIdUsedByAnotherChat` and the old hydration helper is removed.

### 2. repeated-work

**Fix location:** `test/mcp/package.json:12` (`RIGHT`)  
**Blamed base line:** `test/mcp/package.json:12`  
**Introducing path:** `test/mcp/package.json`  
**Introducing commit:** `c8d90ab45fd1612379bbdf2208f042a4d4e58ed3`  
**Mechanism family:** `repeated-work`  
**Performance category:** `startup`  
**Confidence:** 0.99

**Mechanism:** The MCP `start-stdio` script synchronously ran `npm ci` before every compile and server launch, reinstalling the dependency tree on every startup even when Node and dependency inputs were unchanged.

**Symptom:** Every automation MCP launch was blocked on a full npm clean install, causing repeated subprocess, filesystem, package extraction, and lifecycle-script work before the server could accept protocol requests.

**Fixed behavior:** The startup script now invokes the repository's hash-based `fast-install.ts`; when Node and all tracked dependency inputs match the saved state it skips installation, while stale inputs still trigger the normal repository install before compilation.

**Evidence:** Base package line 12 placed `npm ci` directly in the serial `start-stdio` command. The replacement calls `fast-install.ts`; its `isUpToDate()` compares saved Node/input hashes and exits before spawning npm when unchanged, otherwise spawning `npm install`. Thus warm repeated starts remove the unconditional install boundary.
