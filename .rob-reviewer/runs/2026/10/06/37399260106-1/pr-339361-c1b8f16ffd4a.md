# Performance review: chat: Run marketplace prompts in new sessions

[PR #339361](https://github.com/microsoft/vscode/pull/339361) at `c1b8f16ffd4a4af3781ba40b302e9ed9c23738fb`

## Findings (1)

### 1. [medium] Disable all query actions while a prompt launch is in flight

**Finding ID:** `PERF-50CD4EBA9E8A`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/aiCustomization/embeddedMarketplaceDetail.ts:308</code> (<code>RIGHT</code>)  
**Performance category:** <code>ipc</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Agent Host backend sessions, createSession IPC calls, and subsequent chat requests  
**Scaling:** The burst grows with the number of distinct representative-query buttons clicked while one slow install or repair is pending; marketplace input validation permits up to 32 representative queries for an item.  
**Outcome:** Concurrent backend session startup and request dispatch can spike IPC/CPU/network work, contend with the foreground launch, and increase latency or reduce throughput.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Representative queries were inert list text, so opening an item or installing it could not queue multiple Agent Host session launches from this section.  
**Changed behavior:** Every query is now an independent action. During an installation, additional query actions observe \`installing\`/\`repairing\` and join the same coalesced operation; when it settles, all handlers continue concurrently into \`runPrompt\`.  
**Confidence:** 0.97 — Each representative query owns a separate enabled Button and callback; the install service explicitly coalesces only the install/repair promise, after which every waiter calls runPrompt. The sidebar command creates a UUID-backed resource per invocation and the Agent Host path directly calls connection.createSession without a cross-resource limiter. The exact number of users who multi-click is uncertain, but the fan-out mechanism and critical path are explicit.

**Causal diff evidence:** The added handler disables only its own \`button\` at line 308. Other newly added query buttons remain enabled and independently await \`ensureInstalled(resource)\` before each invokes \`this.options.runPrompt(query)\`.

On a slow first install or repair, a user can click several still-enabled “Try this” prompts. Completion releases all waiters at once, opening and starting several Copilot sessions concurrently instead of one, causing a visible resource/latency spike.

**Evidence:** \`renderQueries\` creates one Button and async listener per query but disables only the clicked Button. \`CustomizationMarketplaceInstallService.install\`/\`repair\` returns the existing pending promise for the same resource, so all listeners resume together. \`runMarketplacePrompt\` invokes \`openNewSessionSidebar.agent-host-copilotcli\`; \`openChatSession\` generates a fresh UUID resource for every invocation and sends the prompt, while \`AgentHostSessionHandler.\_createAndSubscribe\` calls \`connection.createSession\`. The only observed sequencer is keyed by session resource, so distinct UUIDs are not globally limited.

**Suggested direction:** Use a shared per-detail/per-resource launch-in-flight state: disable every query action when any query starts and re-enable them after that launch finishes (or serialize launches through one shared queue if multiple queued prompts are intentional). Keep the install service’s existing per-resource coalescing.

- Magnitude uncertainty: Button construction is heavier than the former text nodes, but the validated cardinality is bounded and no layout read/write loop or expensive boundary is added.
- Expensive boundaries: none found
- Verdict: No finding: the extra synchronous UI work is bounded and small.

### Scenario 2: Click one or more representative prompts for an available, installing, missing, or installed item

- Critical path: For a cold item, install/repair must finish before prompt launch; then opening a unique Copilot session and sending the prompt are on the critical path. For an installed item, session opening and send are immediately critical.
- Scaling input: The number of distinct query buttons clicked while a slow install/repair is pending; source validation permits up to 32 representative queries.
- Effective concurrency: Install and repair are coalesced per resource, but each Button has an independent continuation. No cross-resource/global launch limiter was found; unique session resources bypass the per-key provisional sequencer.
- Cache behavior: Installed state is the warm path and skips installation. Pending installs and repairs are positively coalesced; after completion, each waiting click still starts its own uncached session.
- Mechanism confidence: High: independent enabled buttons, coalesced install waiters, unique session UUIDs, direct createSession calls, and lack of a global limiter are all traced.
- Magnitude uncertainty: Typical items may expose only a few prompts and most users click once, but slow installs make exploratory multi-clicking realistic; exact Agent Host startup cost varies by provider and SDK warmth.
- Expensive boundaries:
  - filesystem/network/IPC at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/embeddedMarketplaceDetail.ts:311 and customizationMarketplaceInstallService.ts install/repair</code>: Install or repair the selected marketplace customization and reconcile/verify its installation.; cardinality: One operation per resource after the install service's pending-operation coalescing, even when several query handlers wait on it.
    - Introduced by diff: true; previous behavior: The representative-query list was inert; installation occurred only through the existing explicit install/repair action.; critical-path effect: Cold prompt launch blocks until installation/repair completes; warm installed launches skip this boundary.
  - IPC/network at <code>src/vs/workbench/contrib/chat/browser/aiCustomization/aiCustomizationManagementEditor.ts:1008, chatSessions.contribution.ts openChatSession, and agentHostSessionHandler.ts \_createAndSubscribe</code>: Create a fresh Agent Host session and send the selected chat prompt.; cardinality: One unique UUID-backed session and request per clicked query; multiple distinct buttons can release concurrently after the shared installation completes, up to the number clicked.

- Verdict: Reported a medium concurrency-burst regression because all waiting query actions fan out into simultaneous heavyweight session launches.

### Scenario 3: Run a marketplace prompt in the Agents Window and preserve the explicit no-workspace choice through materialization

- Mechanism confidence: High confidence in the command and send path; no separate folder-service performance regression is established.

### Scenario 4: Open a no-workspace Copilot sidebar session and transfer the marker from untitled to materialized resource

- Critical path: The no-folder marker is set before opening/loading the view, then copied to the real resource during first-send materialization; constant-time ResourceSet operations do not block an external boundary materially.
- Scaling input: Number of simultaneously live or not-yet-disposed session resources.

- Mechanism confidence: High for normal lifecycle cleanup and O(1) lookup; lower on rare partial-open failure ownership, so that edge was not reported.
