# Performance review: agentHost: Restrict automatic PR association

## Findings (2)

### 1. [medium] Bound pull-request reconciliation when the setting changes

**Finding ID:** `PERF-DEF4408B9E95`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostGitStateService.ts:75</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>concurrency-burst</code>  
**Resource:** Concurrent GitHub API requests and git rev-parse subprocesses  
**Scaling:** The burst grows linearly with every resident session lacking a verified pull request. The default residency limit is 10 (and held/subscribed sessions can exceed it); each cold miss performs one branch GET, then a git rev-parse and a second commit-to-PR GET.  
**Outcome:** A single setting or experiment flip can produce a burst of subprocess and network activity, consuming GitHub rate limit and contending with interactive repository work.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff there was no auto-attach setting listener, so a root configuration change did not trigger repository-wide pull-request discovery across resident sessions.  
**Changed behavior:** Changing this root setting now starts reconciliation independently for every materialized session with no aggregate concurrency limit.  
**Confidence:** 0.97 — The changed fan-out, per-key-only sequencing, default resident-session cardinality, and exact network/subprocess call chain are all directly established. The proportion of sessions that are cold/unassociated is workload-dependent, affecting magnitude rather than the mechanism.

**Causal diff evidence:** The added loop queues \`\_queuePullRequestLookup(sessionKey)\` for every session as soon as \`autoAttachPullRequests\` changes; \`\_pullRequestSequencer\` serializes only by session key, so all different sessions run concurrently.

With ten cold feature-branch sessions, enabling automatic association can immediately issue roughly ten concurrent branch lookups and, on misses, ten concurrent \`git rev-parse\` processes followed by ten more GitHub requests. This background burst can throttle GitHub requests and slow other git work.

**Evidence:** \`getSessionUris()\` enumerates all materialized session states; normal residency allows 10. \`\_queuePullRequestLookup\` uses \`SequencerByKey\`, which provides no global limit. \`resolveForCheckout\` calls \`findPullRequestByHeadBranch\`; a miss calls \`revParse('HEAD')\` and \`findPullRequestByHeadSha\`. The OctoKit cache only revalidates an already-seen exact route and does not coalesce cold requests across distinct session branches.

**Suggested direction:** Run setting-triggered reconciliation through a small shared limiter (and prioritize the active session), or lazily reconcile inactive sessions; preserve per-session sequencing while bounding aggregate GitHub and subprocess concurrency.

### 2. [medium] Avoid a full git refresh after every failed or cancelled turn

**Finding ID:** `PERF-6AC411A59B7B`  
**Location:** <code>src/vs/platform/agentHost/node/chatContributions/githubReferences/githubReferencesContribution.ts:27</code> (<code>RIGHT</code>)  
**Performance category:** <code>subprocess</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Git subprocess launches and repository filesystem I/O  
**Scaling:** The added cost occurs once per non-coalesced cancelled or errored turn. A refresh launches at least \`git status\` and \`git remote -v\`, usually \`symbolic-ref\`, and may add push-remote and base-divergence probes; rapid events coalesce per session, but ordinary turns separated by more than the five-second throttle each pay again.  
**Outcome:** Cancelled and failed requests now leave several background git processes running, increasing CPU/I/O load and contention with user or agent git commands.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before the diff, cancelled and errored turns performed no GitHub-reference attachment and therefore did not call \`refreshSessionGitState\` or its git probes.  
**Changed behavior:** Every started turn that ends in cancellation or error now invokes the same full attach path previously reserved for successful turns.  
**Confidence:** 0.96 — The before/after event filter and subprocess call path are direct, and the added tests explicitly require success, cancelled, and error outcomes. Exact wall-clock impact varies by repository size and cancellation/error frequency.

**Causal diff evidence:** The condition changed from \`turn.reason.kind === 'success'\` to accepting every outcome except \`rejected\` and \`localCommand\`, newly invoking \`attachSessionGitHubPullRequest\` for \`cancelled\` and \`error\`.

Users who cancel slow turns or retry repeated provider errors now incur a full repository-state probe after each outcome. Even when restricted-resolution caching or an existing branch association avoids all GitHub traffic, the git refresh still runs and can slow concurrent source-control operations in large repositories.

**Evidence:** \`GitHubReferencesContribution.onTurnEnd\` fire-and-forgets \`attachSessionGitHubPullRequest\`; that method unconditionally awaits \`refreshSessionGitState\` first. \`refreshSessionGitState\` calls \`getSessionGitState\`, whose implementation launches 3 initial git probes in parallel and additional branch probes as needed, then holds its per-session throttler for five seconds. Turn errors do not set \`SessionLifecycle.Failed\` (that lifecycle is for session creation failure), so the refresh is reachable.

**Suggested direction:** Preserve reconciliation semantics without always refreshing the repository: track whether the turn changed PR artifacts or checkout-relevant state and skip unchanged failed/cancelled turns, or add a restricted reconciliation entry point that uses the already-recorded git state when only artifact metadata changed.
