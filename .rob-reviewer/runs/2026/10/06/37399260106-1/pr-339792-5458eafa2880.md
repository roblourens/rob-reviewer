# Performance review: agentHost: Enable artifact tools by default

[PR #339792](https://github.com/microsoft/vscode/pull/339792) at `5458eafa288007c4a25673d03abe92a063da507e`

## Findings (2)

### 1. [medium] Bound artifact history before enabling it by default

**Finding ID:** `PERF-3A1F3FE3E8C8`  
**Location:** <code>src/vs/platform/agentHost/common/artifactToolsConfiguration.ts:15</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>unbounded-retention</code>  
**Resource:** Retained artifact objects plus repeatedly copied, JSON-serialized, database-written, and IPC-broadcast metadata bytes  
**Scaling:** With N distinct artifacts/references in a session, retained state and each persistence/publication are O(N); repeated additions are at least O(N²) overall because each item scans and copies the growing collection, and neither the batch schema nor the session collection has a maximum.  
**Outcome:** Unbounded retained memory, growing GC/serialization work, and progressively slower artifact calls, catalog synchronization, and session restoration  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** On Stable, the previous \`product.quality \!== 'stable'\` default kept the artifact group disabled unless explicitly enabled, so ordinary sessions could not invoke the agent tool and accumulate this unbounded metadata.  
**Changed behavior:** The unconditional \`true\` default advertises \`add\_artifact\_or\_reference\` in every Stable agent session. Its \`items\` schema has no \`maxItems\`, \`SessionArtifactCollection\` has no total cap, and every mutation rebuilds and persists the full aggregate before \`setSessionMeta\` broadcasts the full metadata object.  
**Confidence:** 0.97 — The default transition, absence of both per-call and total bounds, full-list copy/serialization path, database write, and metadata broadcast are directly visible in the repository. Only how often users accumulate very large unique histories is uncertain, which is reflected in severity rather than mechanism confidence.

**Causal diff evidence:** The added \`default: true\` at line 15 replaces the Stable-off default, making the existing unbounded recording path available by default to the full Stable population.

A long-running session that records many unique outputs/references—or one prompt that causes a large batch—retains every entry indefinitely and makes later recordings and restores increasingly allocation-, storage-, and IPC-heavy. This now affects default Stable sessions rather than opt-in/preview users.

**Evidence:** \`createArtifactServerToolGroup\` gates advertisement on this setting. The add schema only requires \`minItems: 1\`; \`SessionArtifactCollection.add\` performs a linear duplicate search and spreads the array; \`SessionArtifacts.mutate\` rereads, maps, merges, and persists the entire list; \`\_createArtifactServerToolAccessor.persist\` stringifies the whole list and synchronizes catalog storage; then \`setSessionMeta\` emits the full \`\_meta\` object to live subscribers. Deduplication only removes identical values and does not bound distinct resources.

**Suggested direction:** Before enabling this globally, add explicit \`maxItems\` validation and a bounded per-session collection with defined reject/eviction semantics; persist and publish only that bounded representation.

### 2. [low] Avoid loading the artifact schema into every agent turn

**Finding ID:** `PERF-F09609AD5018`  
**Location:** <code>src/vs/platform/agentHost/common/artifactToolsConfiguration.ts:15</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>eager-work</code>  
**Resource:** Serialized tool-definition bytes and model-context tokens  
**Scaling:** The overhead is paid once per active model turn/session for all default-enabled Stable chats: one large add-tool definition is always eager, and providers without active tool search eagerly load all three artifact definitions, independent of whether any artifact is recorded.  
**Outcome:** Larger model requests and avoidable token processing increase response latency and network/model throughput cost for ordinary chats that never use artifacts.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** With the prior Stable default disabled, \`AgentServerToolHost.getDefinitionsForSession\` filtered out the artifact group, so Stable agent sessions sent no artifact tool names, descriptions, or schemas to providers.  
**Changed behavior:** The unconditional default enables three artifact definitions for every Stable session. \`add\_artifact\_or\_reference\` is explicitly \`deferLoading: false\` and carries the full classification guidance and nested item schema, so Copilot maps it to \`defer: 'never'\`; Claude maps it to \`alwaysLoad: true\`; Codex keeps every dynamic tool eager because it cannot detect tool-search support.  
**Confidence:** 0.94 — The setting gate and provider-specific eager-loading mappings are explicit. Exact token count and latency vary by provider/model, so severity is low, but the added payload and its reachability on every default-enabled session are not speculative.

**Causal diff evidence:** Line 15 changes the Stable default from false to true, so these previously absent eager definitions are now loaded by default in every Stable agent session.

Every Stable agent chat now pays prompt/request overhead even when the task produces no artifact. The guaranteed cost is one sizeable eager definition on tool-search-capable sessions and all three definitions on Codex or Copilot sessions where tool search is unavailable.

**Evidence:** The enabled group is selected from this setting by \`\_isArtifactToolsEnabled\`. \`artifactServerToolDefinitions\` marks the large add definition non-deferred. Copilot \`\_createServerSdkTools\` only uses \`auto\` when \`deferLoading\` is true, Claude converts false to \`alwaysLoad: true\`, and Codex \`\_buildDynamicTools\` deliberately registers all definitions eagerly. The tool-search configuration itself describes deferred tools as avoiding loading every definition up front.

**Suggested direction:** Keep the rollout gated until the add tool can be deferred behind tool search with a compact always-present instruction, and use a compact/provider-gated fallback for Codex and models without tool search.


## Performance regression fixes detected (1)

### 1. repeated-work

**Fix location:** `src/vs/platform/agentHost/common/agentHostStarter.config.contribution.ts:207` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/common/agentHostStarter.config.contribution.ts:207`  
**Introducing path:** `src/vs/platform/agentHost/common/agentHostStarter.config.contribution.ts`  
**Introducing commit:** `b1ad71876550f0bfc4cf1ff8006d1d9397197446`  
**Mechanism family:** `repeated-work`  
**Performance category:** `network`  
**Confidence:** 0.98

**Mechanism:** With automatic association enabled, every accepted turn ends by calling `attachSessionGitHubPullRequest`; on a non-base branch with no PR, the resolver performs a GitHub head-branch query (and potentially a local `rev-parse` plus SHA query), but a miss does not record a negative result, so the next turn repeats the same lookup.

**Symptom:** Repeated background GitHub requests and local Git work after each completed turn on feature branches that do not yet have a pull request.

**Fixed behavior:** Defaulting automatic attachment off routes sessions through restricted reconciliation. With no recorded or explicitly associated PR candidates, `_canReuseResolution` completes without calling `resolveForCheckout`, eliminating the per-turn GitHub lookup for the default Stable scenario.

**Evidence:** `GitHubReferencesContribution.onTurnEnd` invokes attachment after every non-rejected turn. `_attachSessionGitHubPullRequest` in automatic mode calls `resolveForCheckout` whenever `pullRequestBranchName` does not equal the current branch; on a miss it returns without setting that branch marker. The test `keeps the known pull request but resumes looking after the branch changed` explicitly expects two calls for two attempts while the first has no PR. The changed default at line 207 selects restricted mode, whose zero-candidate path returns before network resolution.

- Effective concurrency: Each chat's model turns are sequenced by its provider runtime; separate sessions can incur the added payload concurrently. There is no cross-session coalescing because each provider session receives its own definitions.
- Cache behavior: Definitions are static in process, but provider registration is per session. Copilot/Claude can defer only definitions marked \`deferLoading\`; the add tool is deliberately non-deferred. Codex has no capability check and eagerly registers every dynamic tool. ### Scenario 2: Record many distinct artifacts or references in a long-running agent session

- Critical path: The tool validates every item, performs duplicate detection and immutable array growth, merges the complete session-wide history, awaits full-list catalog/database persistence, then publishes the complete \`\_meta\` object before returning the tool result. Pull-request artifacts additionally await association reconciliation.
- Scaling input: Effective number N of distinct artifact/reference values across all chats in a session, plus batch size K. Duplicate values do not grow N, but unique resources are unbounded; repeated insertions scan/copy growing arrays and full persistence/publication is O(N).
- Effective concurrency: Mutations are serialized per session by \`SequencerByKey\`, preventing lost writes but making full-list persistence additive on the tool's critical path. PR association is separately sequenced per session/folder; distinct sessions can write and query concurrently.
- Cache behavior: The in-memory session metadata is authoritative and pending PR rows are cached per session, but there is no artifact count/byte cap or eviction. Every successful mutation rebuilds and serializes the full list rather than incrementally persisting it.
- Mechanism confidence: Very high: unbounded inputs/retention, linear scans, full-array copies, full serialization, awaited persistence, and full metadata publication are all directly implemented.
- Magnitude uncertainty: Normal sessions may record only a handful of artifacts because the tool guidance discourages inventories. However, neither the input batch nor retained session history has a bound, so long-lived sessions and explicit requests for many deliverables can reach large N.
- Expensive boundaries:
  - database at <code>src/vs/platform/agentHost/node/agentService.ts:\_createArtifactServerToolAccessor.persist and \_persistOrderedListVisibleSessionState</code>: Stringify the complete artifact array and synchronize list-visible session/catalog metadata.; cardinality: One awaited catalog/database synchronization per successful tool mutation, carrying all N artifacts; related entries can be batched into one call but the persisted payload remains full-history.
    - Introduced by diff: true; previous behavior: Default Stable sessions could not invoke the disabled artifact tools, so agent-driven artifact persistence did not occur without explicit opt-in.; critical-path effect: The add/remove tool does not complete until the full-list write/synchronization finishes.
  - IPC at <code>src/vs/platform/agentHost/node/shared/sessionArtifacts.ts:SessionArtifacts.mutate -&gt; AgentHostStateManager.setSessionMeta</code>: Broadcast \`SessionMetaChanged\` containing the full \`\_meta\`, including the complete artifact array, to live subscribers.; cardinality: One full metadata envelope per successful mutation, with bytes proportional to N and fan-out to connected clients.

### Scenario 3: Complete turns or restore a GitHub-backed session on a feature branch without a pull request

- Critical path: Turn completion invokes Git state refresh and PR association asynchronously; restore also starts the same operation off the restore return path. Local Git inspection still occurs. With the new default, restricted reconciliation has no candidates and returns before GitHub resolution; previously automatic mode queried GitHub after each turn until a PR appeared.
- Scaling input: Number of accepted turns/restores and active folders. For a branch with no PR, the pre-diff network count grew with turns because misses were not negatively cached; after the diff it is zero absent recorded/explicit candidates.
- Effective concurrency: Git refresh is throttled per session and PR lookup is sequenced per session/folder, so overlapping triggers coalesce/serialize by key but independent sessions or folders can run concurrently.
- Cache behavior: Positive automatic results are cached by \`pullRequestBranchName\`, but automatic misses do not set a branch negative-cache marker and are retried. Restricted mode caches candidate resolution and immediately completes for an empty candidate set. Pending recorded PRs are cached per session and grouped by folder.
- Mechanism confidence: Very high: the turn-end trigger, missing negative cache, positive-only stop condition, restricted empty-candidate fast path, and changed default are explicit.
- Magnitude uncertainty: The number of affected turns depends on users working on feature branches before opening a PR and having GitHub authentication. The repeated request mechanism and its elimination are directly covered by call flow and query-count tests.
- Expensive boundaries:
  - subprocess at <code>src/vs/platform/agentHost/node/agentHostGitStateService.ts:refreshSessionGitState and AgentHostPullRequestAssociationResolver.resolveForCheckout</code>: Inspect session Git state and potentially resolve HEAD.; cardinality: Git state refresh is at most once per session per five-second throttle window; HEAD fallback occurred per uncached automatic miss when branch lookup found no PR.
    - Introduced by diff: false; previous behavior: The same Git refresh ran before; the diff primarily removes the default automatic lookup/fallback path.; critical-path effect: Turn-end work is asynchronous/off the response critical path; branch changes can await lookup inside refresh before emitting refreshed state. Restore launches it without awaiting the restore result.
  - network at <code>src/vs/platform/agentHost/node/agentHostPullRequestAssociationResolver.ts:resolveForCheckout</code>: Query GitHub for a PR by head branch and optionally HEAD SHA.; cardinality: Before: one or two requests after each eligible turn/restore on a feature branch with no PR, serialized per key but repeated after misses.     - Introduced by diff: false; previous behavior: Stable defaulted automatic attachment on and retried uncached misses; the changed false default removes this boundary from the ordinary no-PR path.; critical-path effect: Mostly background turn-end traffic, but consumes network/API throughput and can delay branch-refresh completion.
- Verdict: Performance improvement, recorded as a regression fix against the blamed introducing commit; no review finding is appropriate for this fixing change.
