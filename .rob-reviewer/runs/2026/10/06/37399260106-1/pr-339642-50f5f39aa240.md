### Scenario 1: Open compare mode, check models, and configure a same-model effort variant in Details

- Critical path: Opening/checking models synchronously rebuilds the visible picker list; changing effort awaits the model-configuration save before acceptance completes. While Details is visible, list refresh requests coalesce into one pending refresh, and preserveSize skips rebuilding/measuring the sizing tab.
- Scaling input: The provider model catalog controls list rebuild cost; committed launches remain limited to 2-10 attempts, while transient over-limit checkbox state is bounded by the catalog. Variant choices are bounded by the model's configuration enum.
- Effective concurrency: Pointer/keyboard interactions are sequential. Configuration edits are serialized per model by SequencerByKey; refreshActiveList calls while Details is open collapse behind a single refreshPending flag.
- Cache behavior: Model metadata and labels are read from in-memory caches. Configuration reads use the existing automation/model configuration caches; a changed value updates persistence and then the in-memory cache. No new negative-cache behavior is introduced.
- Mechanism confidence: High: the callback sequence, per-model sequencer, pending-refresh coalescing, and sizing-measure suppression are explicit in the traced code.
- Magnitude uncertainty: Catalog sizes vary by provider, but list and variant work is bounded and user-triggered; no evidence shows a frame-critical repeated boundary or unbounded retained state.
- Expensive boundaries:
  - filesystem at <code>src/vs/workbench/contrib/chat/browser/widget/input/modelPicker/modelPickerCard.ts:\_setValues -&gt; src/vs/sessions/contrib/automations/browser/automationModelConfiguration.ts:setModelConfiguration</code>: Persist the selected model configuration through AutomationModelConfiguration and LanguageModelsService's provider-group configuration service; cardinality: One persisted configuration update per explicit effort/context choice; edits for the same model are serialized.
    - Introduced by diff: true; previous behavior: The persistence operation already existed for ordinary model Details; compare-mode rows could not previously enter Details, so this PR makes the same one-save-per-choice path available there without increasing saves per choice.; critical-path effect: The Details interaction awaits the save before final acceptance and refresh, but repeated list refresh requests are coalesced while the details panel remains open.
- Verdict: No reportable regression. The new configuration boundary is one-for-one with an explicit user choice, and the potentially repeated list refreshes are coalesced while the details panel is open.

### Scenario 2: Launch a comparison containing distinct models or same-model effort variants

- Critical path: The send action resolves each selected harness locally, then awaits startComparison, which creates and sends every attempt before the scenario returns and optionally opens the comparison grid.
- Scaling input: Effective cardinality is the validated attempt count, 2-10 after variant deduplication and base-configuration reconciliation.
- Effective concurrency: All attempt launches are scheduled together with Promise.all, so aggregate concurrency is at most 10. This concurrency cap and scheduling are unchanged from the base behavior.
- Cache behavior: Harness/model resolution reads provider and language-model snapshots/configuration already held for the draft; attempt creation itself is not cached or coalesced because each attempt intentionally owns a distinct session/worktree.
- Mechanism confidence: High: the selection gate and service validation both enforce 2-10 attempts, and startComparison explicitly maps them into Promise.all.
- Magnitude uncertainty: Provider launch duration and resource cost vary, but neither maximum fan-out nor scheduling changed.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/services/sessions/browser/sessionComparisonService.ts:startComparison</code>: Create a session/worktree and send the initial chat request for each comparison attempt; cardinality: One call per effective attempt, concurrently, with a hard maximum of 10.
    - Introduced by diff: false; previous behavior: Before the PR, comparisons already launched 2-10 attempts concurrently, including up to 10 repeated runs of one model. The diff carries per-attempt configuration variants into the same existing launch loop without increasing maximum cardinality.; critical-path effect: startComparison waits for all launch promises before completing; individual launches proceed concurrently.
- Verdict: No reportable regression. Same-model variants reuse the existing bounded launch fan-out rather than adding calls beyond the prior maximum.

### Scenario 3: Render, expand, and act on the Judge scorecard

- Critical path: When a verdict becomes available, the UI synchronously renders the header and up to 10 rows, including markdown-backed detail DOM and validation hover registrations. Expanding a row only toggles hidden state and requests layout; opening an attempt or starting synthesis occurs only after an explicit action.
- Scaling input: At most 10 attempts, four validation checks per attempt, and verdict text already bounded by the comparison schema.
- Effective concurrency: Rendering and expansion are synchronous on the UI thread; only one row is expanded at a time. User-triggered open/synthesis actions are singular and not burst-scheduled by rendering.
- Cache behavior: No result cache is added. Renders are skipped when comparison id, verdict identity, and participant-array identity are unchanged; render-owned hover/listener resources are cleared before rebuilding.
- Mechanism confidence: High: row construction, eager details, disposal, identity guards, and explicit-action boundaries are visible in the changed implementation.
- Magnitude uncertainty: Markdown rendering cost depends on verdict text, but attempt count and schema text are bounded, and the old panel also eagerly rendered winner rationale plus other-attempt strengths.
- Expensive boundaries:
  - IPC at <code>src/vs/sessions/contrib/chat/browser/sessionComparisonResult.ts:focusAttempt</code>: Open one selected attempt session; cardinality: One call per explicit Open action.
    - Introduced by diff: false; previous behavior: The prior result UI exposed links and winner/alternate actions that invoked the same session-open operation; the PR changes presentation, not boundary cardinality.; critical-path effect: Off the initial scorecard render path; only blocks completion of the user's Open action.
  - IPC at <code>src/vs/sessions/contrib/chat/browser/sessionComparisonResult.ts:synthesize</code>: Start synthesis through the comparison service; cardinality: One call per explicit Synthesize action, guarded by the existing disabled/busy state.
    - Introduced by diff: false; previous behavior: The prior result panel already offered synthesis and additional instructions through the same service path.; critical-path effect: Off the render/expand path and only on explicit synthesis.
- Verdict: No reportable regression. Although collapsed detail DOM is eagerly built, it is bounded to 10 attempts and replaces similarly eager prior verdict content rather than materially amplifying work.
