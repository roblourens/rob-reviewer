# Performance review: sessions: integrate Mission Control host discovery and management

## Findings (2)

### 1. [medium] Avoid full discovery every time the management picker opens

**Finding ID:** `PERF-AFE70F58A1C9`  
**Location:** <code>src/vs/sessions/contrib/providers/remoteAgentHost/browser/manageRemoteAgentHosts.ts:213</code> (<code>RIGHT</code>)  
**Performance category:** <code>network</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** HTTP discovery requests and remote-tunnel service calls  
**Scaling:** Every initial picker open and every return through showManagePicker starts all registered discovery handlers; cloud-sandbox full discovery alone scans four task scopes with up to 10 sequential pages each, while tunnel and Mission Control discovery add parallel network calls. Reopening/back navigation repeats this boundary fan-out.  
**Outcome:** Excessive network I/O, server load, battery use, and prolonged busy-state activity in a management workflow that previously rendered entirely from cached providers.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this added call, opening or returning to Manage Remote Agent Hosts only built the picker from locally registered providers and performed no discovery boundary work.  
**Changed behavior:** Showing the picker now calls AgentHostFilterService.rediscover(), which fans out to every registered discovery handler rather than refreshing only stale host inventory or waiting for the explicit Refresh Hosts button.  
**Confidence:** 0.99 — The picker call path, handler fan-out, cache bypass, pagination bounds, and repeated back-navigation invocation are explicit. Actual request count varies with pagination, but the minimum cross-provider boundary fan-out and before/after regression are certain.

**Causal diff evidence:** The added \`void refreshHosts()\` after picker.show() runs on every showManagePicker invocation; the same function is called initially and again when returning from host options or menu actions.

Simply opening the management UI—or pressing Back after inspecting one host—can issue at least several and up to dozens of unrelated discovery requests, even when cached rows are already available and the user never asks to refresh.

**Evidence:** rediscover() executes all handlers with Promise.allSettled. The cloud-sandbox handler calls \_discoverAndSeed() with its default incremental=false; CloudSandboxApiService.listSessions then requests four repository/archive scopes and can paginate each to DISCOVERY\_TASK\_PAGE\_LIMIT=10. The tunnel handler calls listTunnels(), and the new Mission Control handler calls listEnvironments({ refresh: true }), explicitly bypassing its 60-second cache. Cloud sandbox coalesces overlap, but completed picker reopenings repeat the scan and the tunnel/Mission Control handlers have no shared in-flight coalescing.

**Suggested direction:** Render cached providers on show and reserve full rediscovery for the explicit Refresh Hosts button, or invoke stale-aware/coalesced discovery APIs and guard against an existing rediscovery before starting another pass.

### 2. [medium] Ignore local inventory write notifications

**Finding ID:** `PERF-56A77F20CDA6`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/remoteAgentHost/missionControlEnvironmentService.ts:85</code> (<code>RIGHT</code>)  
**Performance category:** <code>cpu</code>  
**Mechanism family:** <code>repeated-work</code>  
**Resource:** Main-thread storage-key scans, JSON parsing, host-array/object allocation, and downstream provider observer/reconciliation work  
**Scaling:** If H host metadata values change in one refresh and the profile has P machine-scoped storage keys, storeAll emits H unmerged value-change events and this listener performs H full restores, costing O(H\*P) key scans plus O(H^2) host parsing/republication and observer work.  
**Outcome:** Increased renderer CPU/GC pressure and delayed completion of host refreshes, with potential UI stalls as the retained host inventory grows.  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this PR there was no Mission Control profile-inventory listener or per-host metadata persistence, so a discovery refresh did not feed its own writes back into repeated full inventory restores.  
**Changed behavior:** Each local metadata write performed by a refresh now synchronously triggers a complete inventory restore; the batched storage API pauses notifications but replays every key event after the batch rather than merging them.  
**Confidence:** 0.99 — The storage event source flag, one-event-per-entry replay semantics, full-scan restore body, and downstream observable publication are all directly established in repository code; only the exact wall-clock magnitude depends on profile key and host counts.

**Causal diff evidence:** The added listener at lines 84-87 calls \_restore() for every prefixed profile-storage event, while the same new service persists one metadata entry per host via storeAll(..., false) at lines 269-276.

On initial discovery or a refresh that changes many host records, the picker remains busy while the renderer repeats the complete restore once per host; retained hosts make this progressively more expensive even though one restore would produce the same state.

**Evidence:** AbstractStorageService.storeAll loops over every entry and PauseableEmitter without a merge function replays each queued event. These writes pass external=false, yet this listener does not check e.external. Every callback calls \_restore(), which enumerates all PROFILE/MACHINE keys, parses every matching host JSON record, allocates a new host array, and calls hosts.set; that publication also reaches the newly added Mission Control provider reconciliation/description observers.

**Suggested direction:** Handle only external storage notifications here (as other storage-backed observables do), or suppress/coalesce notifications around \_persist. Keep the explicit single \_restore() after local preference writes so local rename/hide behavior remains immediate.
