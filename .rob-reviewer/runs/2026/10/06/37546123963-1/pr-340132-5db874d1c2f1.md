**Relevant issue families:** synchronous-ui-work, repeated-work, boundary-fanout, concurrency-burst

### Scenario 1: macOS system-wide Open Agents Window while the application is hidden

- Critical path: Electron global-shortcut callback selects one owning window, sends one run-action IPC to its renderer, the command makes one native-host IPC back to the main process, existing Agents-window resolution completes, then the changed path shows the single target window, activates the app, and focuses the window. The focus work is on the interaction's critical path and is the intended reveal operation.
- Scaling input: Shortcut trigger frequency; target-window cardinality remains one after owner selection and workspace-window reuse.
- Effective concurrency: One owner is selected per shortcut event. Events are not coalesced, but workspace matching reuses a single existing Agents window; the diff adds only one constant-size focus sequence per trigger and does not add aggregate fan-out.
- Cache behavior: Window matching reuses a warm Agents window. The workspace file is written only when absent, though existence is checked per request. The changed focus path has no cache, retained keys, or negative-cache state.
- Mechanism confidence: High confidence in the IPC, filesystem, and native-window sequence from the traced call path; no scaling or retention mechanism was introduced.
- Magnitude uncertainty: Exact native show/activation duration depends on macOS and window state, but the work is constant-size, explicitly requested, and only the show is conditional on hidden state.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/globalKeybindings/electron-main/globalKeybindingsMainService.ts:onTrigger</code>: Dispatches vscode:runAction from the main process to one renderer.; cardinality: One dispatch per shortcut trigger after selecting one owner, independent of the number of registered owner windows.
    - Introduced by diff: false; previous behavior: The same run-action IPC routed every system-wide trigger before this change.; critical-path effect: The renderer must receive and run the command before the Agents window can be opened and focused.
  - IPC at <code>src/vs/platform/native/electron-main/nativeHostMainService.ts:openAgentsWindow</code>: ProxyChannel invokes the main-process native host from the renderer.; cardinality: One invocation per command trigger.
    - Introduced by diff: false; previous behavior: The same native-host IPC and await were present; only its final focus mode changed.; critical-path effect: The open call must return before the target focus sequence executes.
  - filesystem at <code>src/vs/platform/windows/electron-main/windowsMainService.ts:ensureAgentsWindow</code>: Checks whether the Agents workspace file exists and writes it if absent.; cardinality: One existence check per open request; one write only on the cold first-use path where the file is missing.
    - Introduced by diff: false; previous behavior: Identical filesystem work occurred before the focus-mode change.; critical-path effect: The check, and cold-path write, complete before window resolution.
  - other at <code>src/vs/platform/windows/electron-main/windowImpl.ts:BaseWindow.focus</code>: Queries hidden application state, shows the target BrowserWindow, activates the macOS application, then focuses the BrowserWindow and its web contents.; cardinality: One hidden-state query, one show, one application focus, and one target focus sequence for the single returned target window.
    - Introduced by diff: true; previous behavior: Transfer mode only attempted BrowserWindow/webContents focus, which macOS ignored while the application was hidden.; critical-path effect: This is the final critical-path reveal work and corrects the hidden-app behavior.
- Verdict: No reportable regression. The new native operations are bounded to one target and are required to make the requested interaction progress; existing filesystem/window work and lack of trigger coalescing are unchanged.

### Scenario 2: Open Agents Window from foreground command palette, keyboard shortcut, chat action, or invitation

- Critical path: The renderer makes one native-host IPC, folder intent and the Agents workspace are resolved, an existing Agents window is reused or one window is created, one selection message is sent, and the returned target is focused. On macOS the diff adds an application hidden-state query and application-focus call; while already active these are constant-size native operations. On Windows and Linux Force reaches the same BrowserWindow focus path as Transfer.
- Scaling input: Frequency of explicit open actions; folder/session payload size does not multiply the changed focus work, and effective window cardinality is one.
- Effective concurrency: Each explicit user action starts one request. There is no new limiter or sequencer, but deduplication by the Agents workspace gives an effective target cardinality of one; concurrent invocation behavior of opening/resolution predates the diff.
- Cache behavior: Warm calls reuse the existing workspace window; cold calls may create/load one. No focus state is cached, and the PR does not change window matching or file caching.
- Mechanism confidence: High confidence that the call is new on macOS and constant per action; low evidence for any meaningful performance outcome.
- Magnitude uncertainty: The cost of a redundant macOS activation request while already active is platform-dependent, but there is no evidence of blocking, repeated layout, or user-visible latency beyond a constant user-triggered native call.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/native/electron-main/nativeHostMainService.ts:openAgentsWindow</code>: Crosses from the invoking renderer to the main process and later sends vscode:selectAgentsFolder to the Agents renderer.; cardinality: One request IPC and one target message for the single selected window per action.
    - Introduced by diff: false; previous behavior: Both IPC boundaries and their cardinality were unchanged.; critical-path effect: Main-process resolution and the returned target are required before final focus; the selection message uses existing sendWhenReady behavior.
  - filesystem at <code>src/vs/platform/windows/electron-main/windowsMainService.ts:ensureAgentsWindow</code>: Performs one existence check and a cold-only workspace-file write.; cardinality: One check per action and at most one cold write.
    - Introduced by diff: false; previous behavior: The same check/write path existed before the PR.; critical-path effect: Runs before reuse or creation of the Agents window.
  - other at <code>src/vs/platform/windows/electron-main/windowImpl.ts:BaseWindow.focus</code>: On macOS, checks app hidden state and requests application activation before the existing target-window/webContents focus.; cardinality: One application query and focus request for one returned window; no show call when the app is not hidden.
    - Introduced by diff: true; previous behavior: The target BrowserWindow and web contents were focused directly without an application-focus request.; critical-path effect: Adds a constant native activation request immediately before final window focus.
- Verdict: No finding. The new foreground macOS activation call is bounded and user-triggered, with no demonstrated latency, throughput, memory, or rendering regression; all heavyweight open work is pre-existing.

### Scenario 3: Other Force-focus consumers reveal a target window while VS Code is hidden on macOS

- Critical path: A consumer such as Focus Window, URL handling, task/debug completion, context menu handling, or notification focus reaches BaseWindow.focus(Force). The changed hidden-state branch shows the one target before the already-existing app activation and BrowserWindow/webContents focus calls.
- Scaling input: Number of explicit Force-focus requests; no collection size or application window count multiplies the new operation.
- Effective concurrency: Each consumer request targets one window. No loop, collection fan-out, queue, or new concurrent scheduling is added by the branch.
- Cache behavior: Hidden state is queried live because it is volatile; after the first reveal the application is no longer hidden, so subsequent requests skip show. There is no retained cache or lifecycle change.
- Mechanism confidence: High confidence in reachability and one-call cardinality; no evidence supports a concrete negative performance symptom.
- Magnitude uncertainty: Native show cost varies with target state, but the operation occurs once per hidden-app reveal and does not reconstruct hidden UI or retain resources.
- Expensive boundaries:
  - IPC at <code>src/vs/platform/native/electron-main/nativeHostMainService.ts:focusWindow</code>: Renderer callers may invoke main-process target focus through the native-host channel.; cardinality: At most one IPC per caller request and one target window.
    - Introduced by diff: false; previous behavior: Force-focus callers already crossed this channel and activated/focused the application.; critical-path effect: Focus cannot complete until the main process performs the native calls.
  - other at <code>src/vs/platform/windows/electron-main/windowImpl.ts:BaseWindow.focus</code>: Adds one hidden-state query and one BrowserWindow.show before existing application activation and target focus.; cardinality: One query per Force request and one show only while the app is hidden, for one target window.
    - Introduced by diff: true; previous behavior: Force mode activated the app and focused the target without first showing it.; critical-path effect: The show is synchronous native UI work on the reveal path, but it is required to avoid focusing the previously active window.
- Verdict: No reportable regression. The branch introduces bounded synchronous UI work only when needed to satisfy Force focus and naturally stops issuing show after the app is visible.

**Summary:** Reviewed all four changed files and traced the two executable hunks through global shortcut routing, native-host IPC, Agents-window resolution/reuse, filesystem initialization, BrowserWindow creation/reuse, and all Force-focus callers. The PR adds bounded native show/activation work for a single target and does not introduce scaling fan-out, repeated collection work, retained state, cache-lifecycle problems, or a concurrency burst. No valid performance findings were identified.
