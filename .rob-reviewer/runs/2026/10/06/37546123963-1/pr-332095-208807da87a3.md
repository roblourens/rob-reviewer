## Performance regression fixes detected (1)

### 1. synchronous-ui-work

**Fix location:** `src/vs/base/browser/ui/tree/abstractTree.ts:1874` (`RIGHT`)  
**Blamed base line:** `src/vs/base/browser/ui/tree/abstractTree.ts:1831`  
**Introducing path:** `src/vs/base/browser/ui/tree/abstractTree.ts`  
**Introducing commit:** `fdf686d3ea1ff5c371174e886962aa0a2ac4cdad`  
**Mechanism family:** `synchronous-ui-work`  
**Performance category:** `layout`  
**Confidence:** 0.94

**Mechanism:** A sticky-row position write was immediately followed by offsetHeight on each push-out scroll update, forcing browser style/layout work in the input-to-frame path.

**Symptom:** Sticky-scroll push-out could become visibly less fluid because each scroll update synchronously resolved layout before painting.

**Fixed behavior:** Sticky row heights are measured when the sticky state is rendered and cached; per-scroll root-height updates consume that cache, removing the synchronous DOM geometry read from the scroll/push-out critical path.

**Evidence:** StickyScrollController registers update() on view.onDidScroll; when the last sticky row is pushed out, StickyScrollWidget.setState first writes the row's style.top and then calls updateRootHeight(). In the base revision getRootHeight() synchronously read lastStickyElement.offsetHeight at line 1831, creating a write-then-layout-read cycle on successive scroll events. The changed line 1874 now obtains the already measured/capped height from \_previousElementHeights via getRenderedNodeHeight instead of querying DOM geometry.

- Effective concurrency: Single UI-thread scroll handler; no queue or parallel work. Sticky nodes are bounded by stickyScrollMaxItemCount (default 7).
- Cache behavior: Rendered sticky heights are now cached in \_previousElementHeights and reused on warm scroll updates; the cache is rebuilt on sticky rerender and cleared when hidden. No negative-cache behavior is involved.
- Mechanism confidence: High: the scroll listener, bounded ancestor traversal, DOM writes, and replacement of the per-scroll offsetHeight read are directly traced.

- Verdict: No reportable regression. The changed general tree path adds bounded bookkeeping and removes a synchronous geometry read from the push-out scroll path; the latter was recorded as a regression fix.

### Scenario 2: Scrolling a chat transcript with experimental tree sticky-scroll enabled

- Critical path: Each scroll synchronously resolves one sticky request, consults cached request-content/source-range state, and updates one sticky row because chat sets stickyScrollMaxItemCount to 1. Initial or invalidated geometry is refreshed on a requestAnimationFrame rather than measured on every scroll.
- Scaling input: Scroll frequency, one active sticky request, and the number of currently rendered request templates during a coalesced range refresh rather than the full transcript.
- Effective concurrency: One UI-thread sticky update per scroll; source-range refreshes are coalesced by MutableDisposable to one pending animation-frame callback.
- Cache behavior: Request content eligibility is cached by request id/content key; measured source ranges are cached by request id, cleared on view-model change or width change, and rejected ranges use an explicit null negative cache. Initial unseen requests use an estimated range until rendered/measured.
- Mechanism confidence: High: source provider calls, map lifecycle, rAF coalescing, and the one-row chat bound are explicit in the changed code and tests.
- Magnitude uncertainty: Very long transcripts retain small per-request cache entries while the view model lives, but those entries scale with an already-retained transcript and do not establish substantial incremental memory growth.
- Expensive boundaries: none found
- Verdict: No high-confidence performance regression. Geometry reads occur only during coalesced range refreshes, not per scroll, and effective sticky cardinality is one.

### Scenario 3: Chat resize, input-height change, configuration toggle, theme update, or explicit rerender

- Expensive boundaries: none found
- Verdict: No reportable regression. Added refresh work is bounded, coalesced where geometry is needed, and tied to resize/configuration/rerender events rather than unbounded transcript history.
