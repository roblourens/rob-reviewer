**Relevant issue families:** synchronous-ui-work, repeated-work, serialization-allocation

### Scenario 1: Session list, session header, comparison rows, chat rows, and collapsed-section indicators render or update a NeedsInput/needs-attention status

- Critical path: An observable status/read/archive change synchronously rerenders the currently bound tree/header template and calls SessionStatusIcon.setStatus; icon selection and DOM replacement are on the UI critical path.
- Scaling input: Cost scales with rendered templates whose status changes, effectively the visible/virtualized session and chat rows plus visible section headers, not the full stored session collection.
- Effective concurrency: Rendering is serialized on the UI thread; each template owns one icon widget and its cache key coalesces same-glyph rerenders into a color update.
- Cache behavior: Cold status transition creates the icon once. Warm rerenders with the report-icon cache key only recolor the existing element. Template reset/rebinding clears owned DOM and disposables as before; no positive/negative data cache is involved.
- Mechanism confidence: High: the changed branch replaces the seven-element ring spinner, six independent dot animations, and hidden-animation tracking with one codicon span and one existing opacity pulse; cache and virtualization behavior are preserved.
- Magnitude uncertainty: Exact visible row counts and animation compositor behavior vary by window size and platform, but the changed resource direction is unambiguous.
- Expensive boundaries: none found
- Verdict: No reportable regression. The runtime change reduces DOM nodes, animation count, and tracking work for each visible needs-attention icon; unchanged row-background pulses remain, and the text-only changes do not add render passes.

### Scenario 2: Agents window session and nested-chat rows render or update a needs-attention status

- Critical path: Tree template rendering calls AgentSessionStatusIcon.setStatus synchronously before the visible row is painted.
- Scaling input: Cost scales with visible parent-session and expanded child-chat rows in NeedsInput state after tree virtualization/filtering.
- Effective concurrency: UI-thread serialized. Each reusable row template owns one AgentSessionStatusIcon; identical cache keys avoid rebuilding the child icon.
- Cache behavior: A cold NeedsInput render now creates one codicon span. A warm render only updates its color. Before the diff, the same branch created a six-dot ring spinner and visibility-animation tracker; reset/disposal ownership is unchanged.
- Mechanism confidence: High: the renderer and CSS show the pre-existing container opacity pulse/background pulse remain while the nested six-dot ring animation is removed.
- Magnitude uncertainty: The number of simultaneously visible blocked sessions differs by user workload, but no assumption about large lists is needed to establish that per-row work decreases.
- Expensive boundaries: none found
- Verdict: No reportable regression. The change removes nested animation/DOM work and preserves template reuse, reduced-motion handling, and row cardinality.

### Scenario 3: Status labels are produced for filters, hovers, accessibility text, comparison summaries, pickers, voice descriptions, and open-session link presentation

- Critical path: These synchronous string/switch operations run while their existing UI or presentation object is built; no new prerequisite is added before display.
- Scaling input: At most one label operation per existing rendered item, summary refresh, help invocation, or link presentation; collection scans and render frequency are unchanged by the diff.
- Effective concurrency: In-process synchronous work follows each owning renderer/event; the diff does not add queues, fan-out, parallelism, or serialization.
- Cache behavior: Localization and presentation caching behavior are unchanged; only default message literals and one codicon identifier differ.
- Mechanism confidence: High: every traced hunk changes a literal/status icon value without adding a call, loop, allocation over user data, or lifecycle owner.
- Magnitude uncertainty: None material: string lengths differ slightly, with no changed multiplicity or unbounded payload.
- Expensive boundaries: none found
- Verdict: No reportable regression. The same operations occur at the same cardinality, and the few additional characters are not a realistic CPU, memory, GC, layout, or serialization mechanism.

### Scenario 4: A session transition emits an OS notification, or a background terminal input detector emits a system steering request

- Critical path: For session notifications, the existing delayed eligibility/dedupe checks precede host focus/showToast IPC; opening a session remains conditional on a user click. - Scaling input: One existing toast per eligible deduplicated status transition and one existing steering request per non-duplicate detected terminal prompt within the established throttle behavior; the diff does not change event counts or payload cardinality.
- Effective concurrency: Notification scheduling/cancellation and terminal duplicate throttling are unchanged. Existing requests can occur for independent sessions/terminals, but the diff neither increases nor unbounds that concurrency.
- Cache behavior: Existing notification dedupe keys, cancellation state, focus checks, and terminal last-output/time suppression are unchanged; cold and warm behavior differ only in displayed label text.
- Mechanism confidence: High: traced call sites show the changed literals flow into pre-existing calls after unchanged scheduling, dedupe, and throttling.
- Magnitude uncertainty: Underlying IPC/network latency is platform/provider dependent, but it is irrelevant to regression magnitude because no boundary placement, count, concurrency, payload scale, or critical-path dependency changed.
- Expensive boundaries:

    - Introduced by diff: false; previous behavior: The identical native calls ran with the previous 'Input needed' body text.; critical-path effect: The toast IPC is on notification delivery, not session execution; opening is user-initiated.
  - subprocess at <code>src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/tools/runInTerminalTool.ts input-needed listener</code>: Observe output from an already-running terminal execution.; cardinality: Existing monitor events per active terminal execution, with disposed/cancelled executions suppressed.
    - Introduced by diff: false; previous behavior: The same terminal was monitored and the same detection event was handled before the label wording changed.; critical-path effect: Detection triggers an asynchronous steering notification; terminal execution and monitoring already existed.
  - network at <code>src/vs/workbench/contrib/terminalContrib/chatAgentTools/browser/tools/runInTerminalTool.ts::\_chatService.sendRequest</code>: Send the existing system-initiated steering request for a detected terminal prompt.; cardinality: One request per distinct detected output, bounded against rapid duplicates by INPUT\_NEEDED\_NOTIFICATION\_THROTTLE\_MS; unchanged by the diff.

- Verdict: No reportable regression. Expensive boundaries are pre-existing and retain identical frequency, concurrency, and payload shape apart from a constant-size wording change.
