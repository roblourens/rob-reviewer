# Performance review: Agent Host: stop delivering standalone customizations as plugin content

[PR #340079](https://github.com/microsoft/vscode/pull/340079) at `e07bfc81465a0b3a0aa2d134bf9ca5145b2558af`

## Findings (1)

### 1. [medium] Clear a partition when its last customization is removed

**Finding ID:** `PERF-22CFC1151FF7`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostLocalCustomizations.ts:339</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** In-memory filesystem nodes and VSBuffer contents for removed skill/agent resources  
**Scaling:** Retained memory grows with the recursive size of the last standalone bundle (skill directories include all files except .git and node\_modules) and with the number/lifetime of affected workspace scopes; the process-wide filesystem provider keeps those trees reachable until window shutdown.  
**Outcome:** retained memory and avoidable memory pressure after customizations are removed  
**PR causality:** <code>introduced</code>  
**Previous behavior:** With one combined bundler, if a user removed the last standalone skill/agent while any instruction, prompt, extension skill, or other loose file remained, resolveCustomizationRefs still called bundle(looseFiles, mcpServers); \_bundle deleted and rewrote the authority root, releasing the removed files.  
**Changed behavior:** The split only invokes the standalone bundler while standaloneFiles or mcpServers is non-empty. When that partition transitions to empty but the synced partition remains, no operation reaches the standalone bundler, so its previous root and reverse-origin map remain populated.  
**Confidence:** 0.97 — The changed conditional, the sole recursive-delete site, the no-op disposal behavior, and the process-wide provider ownership are all directly traced. The exact prevalence and bundle sizes vary, which limits severity, but retention on the stated transition is deterministic.

**Causal diff evidence:** The added standalone conditional at RIGHT line 339 partitions the former single \`if (looseFiles.length &gt; 0 \|\| mcpServers.length &gt; 0) bundler.bundle(...)\` call. For a state change from {standalone skill + synced instruction} to {synced instruction}, the old call rebuilt the shared root without the skill, while the new code calls only \`bundlers.synced.bundle\` and never clears the standalone authority.

Removing a configured user/workspace skill can leave the skill's recursively copied assets resident for the rest of the VS Code window. Large skills or many long-lived workspace scopes retain correspondingly more memory even though the customization is no longer advertised.

**Evidence:** Line 339 skips bundlers.standalone.bundle entirely for an empty partition. SyncedCustomizationBundler.\_bundle is the only path that calls fileService.del(this.\_rootUri, { recursive: true }) and clears \_originByDest; its early empty check also has no reset behavior. SyncedCustomizationBundler.dispose only disposes its limiter, and AgentHostFileSystemService owns one process-wide InMemoryFileSystemProvider, so an omitted empty transition leaves the prior tree strongly reachable.

**Suggested direction:** Give each bundler an explicit empty/reset operation that deletes its authority root and clears \`\_lastNonce\`, \`\_lastRef\`, and \`\_originByDest\`, and invoke it whenever that partition becomes empty (or make \`bundle(\[\], \[\])\` perform this cleanup).
