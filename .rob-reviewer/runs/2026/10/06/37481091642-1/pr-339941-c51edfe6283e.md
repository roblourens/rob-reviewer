# Performance review: chat: Warn about BYOK models in remote Copilot sessions

[PR #339941](https://github.com/microsoft/vscode/pull/339941) at `c51edfe6283e543fc0c4f0255db3fa644dcf7a45`

## Findings (1)

### 1. [medium] Coalesce reconnect states before refreshing every chat input

**Finding ID:** `PERF-D72246F509F5`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostRemoteByokNotification.ts:60</code> (<code>RIGHT</code>)  
**Performance category:** <code>rendering</code>  
**Mechanism family:** <code>synchronous-ui-work</code>  
**Resource:** main-thread DOM teardown/recreation, notification predicate work, and associated object allocations in every mounted ChatInputNotificationWidget  
**Scaling:** Cost is O(reconnect state events × mounted chat inputs × registered notifications). The reconnect loop emits ConnectionLost plus ReconnectionWait and ReconnectionRunning on every attempt; after its initial schedule it can retry every 30 seconds for the three-hour grace period, while each event reaches every mounted chat input.  
**Outcome:** repeated main-thread rendering and allocation/GC pressure, causing intermittent UI stalls during prolonged remote outages  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Remote connection state changes did not refresh the global chat-input notification service, so reconnect attempts did not rebuild notification DOM in every chat input.  
**Changed behavior:** The added unfiltered onDidStateChange listener calls \_refresh for ConnectionLost, every ReconnectionWait, every ReconnectionRunning, ConnectionGain, and permanent failure. \_refresh synchronously fires the notification service's global onDidChange event, whose listeners clear and rebuild each ChatInputNotificationWidget.  
**Confidence:** 0.98 — The changed listener, reconnect event sequence, three-hour retry lifetime, synchronous global event fan-out, and widget DOM rebuild are all directly traced in repository code. The exact duration of each rebuild depends on the number and complexity of open chat inputs, affecting severity but not the mechanism.

**Causal diff evidence:** The added line \`this.\_register(remoteConnection.onDidStateChange(() =&gt; this.\_refresh()));\` newly maps every remote transport state event to a global synchronous notification refresh.

In any remote workspace, including users with no BYOK models and no eligible Copilot session, a prolonged network outage repeatedly tears down and recreates active notification UI across all open chat inputs on every reconnect phase. This can produce recurring main-thread jank while the editor is already handling a degraded connection.

**Evidence:** PersistentConnection.\_runReconnectingLoop emits ConnectionLost once and then ReconnectionWait/ReconnectionRunning for each retry, eventually using a 30-second interval under ProtocolConstants.ReconnectionGraceTime (3 hours). ChatInputNotificationService.refresh synchronously fires onDidChange, and each ChatInputNotificationWidget listener calls \_render(), which clears its DOM/disposables and reconstructs the selected notification. BYOK eligibility only observes connection.isConnected, so intermediate wait/running events after the first loss cannot change the predicate.

**Suggested direction:** Track the previous \`isConnected\` value and refresh only when that boolean changes (for example, map state events to \`remoteConnection.isConnected\` and latch duplicates). Once the one-time notice has been dismissed because its claimed connection became ineligible, stop refreshing for later reconnect phases; also avoid the extra unconditional refresh when dismissNotification already emitted a change.

### Scenario 2: Remote workspace network outage while chat inputs are mounted

- Critical path: PersistentConnection synchronously emits each reconnect state on the renderer thread. The new listener immediately calls the global notification service refresh, whose synchronous listeners clear and rebuild each mounted chat notification widget before reconnect processing continues to its next async boundary.
- Scaling input: Reconnect state count multiplied by mounted ChatInputPart instances and registered/active notifications. The three-hour grace period can produce repeated wait/running pairs every 30 seconds after the initial retry schedule.
- Effective concurrency: Reconnect attempts are serialized, but every state event synchronously fans out to all mounted widgets; there is no state deduplication, coalescing, or render batching.
- Cache behavior: Connection liveness is cached as one enum, but the listener ignores whether isConnected actually changed. Notification predicates re-read local model/storage/connection state on every refresh; no render-result cache prevents DOM reconstruction.
- Mechanism confidence: Very high: the unfiltered added listener, reconnect sequence, synchronous service emitter, and full widget DOM rebuild are directly traced.
- Magnitude uncertainty: The exact stall depends on how many chat editors and how complex their currently selected notifications are, but all remote workspaces can hit the mechanism even with no BYOK model.
- Expensive boundaries:
  - network at <code>src/vs/platform/remote/common/remoteAgentConnection.ts PersistentConnection.\_runReconnectingLoop</code>: Reconnect the existing remote management transport; cardinality: One serialized network attempt per retry; wait/running state pairs continue at up to one attempt per 30 seconds for the three-hour grace window.
    - Introduced by diff: false; previous behavior: The same serialized reconnect attempts occurred without globally refreshing chat input notifications for every intermediate state.; critical-path effect: The network reconnect is pre-existing. The new synchronous render fan-out runs immediately before each attempt/wait progression and consumes renderer main-thread time.
- Verdict: Reportable performance regression: intermediate reconnect states that cannot change boolean eligibility repeatedly rebuild notification DOM across all chat inputs.
