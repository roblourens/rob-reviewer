## Performance regression fixes detected (1)

### 1. boundary-fanout

**Fix location:** `src/vs/platform/agentHost/node/agentHostChangesetOperationService.ts:325` (`RIGHT`)  
**Blamed base line:** `src/vs/platform/agentHost/node/agentHostChangesetOperationService.ts:274`  
**Introducing path:** `src/vs/platform/agentHost/node/agentHostChangesetOperationService.ts`  
**Introducing commit:** `fe9f87ca05dca0086aabaf24c7ffaf33888e2a1d`  
**Mechanism family:** `boundary-fanout`  
**Performance category:** `ipc`  
**Confidence:** 0.97

**Mechanism:** A session-level refresh synchronously recomputed and published an operations action for every subscribed changeset even when all computed operation arrays were unchanged, multiplying state-envelope and downstream serialization/consumer work by subscription count.

**Symptom:** Workspace/configuration and operation-provider events in a 32-chat session with 804 subscriptions could publish hundreds of redundant unchanged operation envelopes, causing avoidable CPU/IPC fan-out and latency.

**Fixed behavior:** The new helper compares the computed operation list with the changeset's current operations and returns before dispatching an unchanged action; event-triggered refresh requests are also coalesced per microtask and owner, bounding duplicate computations within one burst.

**Evidence:** Base line 274 unconditionally dispatches ChangesetOperationsChanged after every operation recomputation. updateOperations(session) expands through \_getOperationOwners to each chat/folder owner and then every subscribed changeset. The added large-session test establishes a realistic 32-chat/804-subscription workspace-change scenario and asserts that unchanged operation state previously reached this publication path; the new \_dispatchOperationsChanged equality guard suppresses those unchanged actions. Blame identifies the unconditional publication as introduced by fe9f87ca05dca0086aabaf24c7ffaf33888e2a1d.

- Effective concurrency: Source reconciliation is synchronous. Watch attachment and static recomputation use existing per-key sequencing/coalescing; no new aggregate concurrency burst is introduced.
- Cache behavior: Watcher interest is keyed by resource and shared across source entries. Branch recomputation uses existing scheduled-static-recompute coalescing. The new source map retains O(chat count) small ownership records for session lifetime, then clears them on removal/disposal.
- Mechanism confidence: High for source/resource accounting and watcher deduplication; repository code directly shows keyed DisposableMap and scheduled recompute behavior.
