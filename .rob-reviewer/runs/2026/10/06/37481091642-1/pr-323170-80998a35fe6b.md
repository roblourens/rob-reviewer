# Performance review: AgentHost - adopt the ChangesetContentChanged action

[PR #323170](https://github.com/microsoft/vscode/pull/323170) at `80998a35fe6b36821ff45e38634e20eecd91a820`

## Findings (1)

### 1. [medium] Coalesce superseded full snapshots in the replay buffer

**Finding ID:** `PERF-564C889E60BC`  
**Location:** <code>src/vs/platform/agentHost/node/agentHostChangesetService.ts:881</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cache-lifecycle</code>  
**Resource:** ChangesetFile arrays and objects retained by action envelopes in the 1,000-entry protocol replay buffer  
**Scaling:** Retention grows with the product of changed-file count and buffered recompute count: each successful branch/session/turn recompute now contributes a complete N-file snapshot, and up to 1,000 envelopes remain live until displaced or server shutdown.  
**Outcome:** Increased retained heap and GC pressure, plus oversized reconnect replay payloads after repeated changeset recomputes.  
**PR causality:** <code>materially-amplified</code>  
**Previous behavior:** A publish emitted one ChangesetFileSet envelope per file (plus removals), so the envelope-count cap retained at most roughly 1,000 individual file payloads regardless of files per snapshot.  
**Changed behavior:** Each publish emits one ChangesetContentChanged envelope containing the entire file list. ProtocolServerHandler retains envelopes by count rather than bytes or semantic supersession, so many obsolete full snapshots for the same changeset coexist in the replay buffer.  
**Confidence:** 0.97 — The changed full-list envelope, repeated publish call paths, 1,000-envelope retention, and reconnect traversal are directly visible. Exact heap size depends on repository file count and action mix, but the multiplicative retention mechanism and realistic repeated-turn trigger do not.

**Causal diff evidence:** The added \`files\` field on the single ChangesetContentChanged dispatch carries all diffs in one envelope; the deleted implementation instead dispatched one ChangesetFileSet envelope for each file. Because the unchanged replay cache is capped by envelopes, this changes retained file cardinality from O(1,000) to O(1,000 × files-per-snapshot).

Long-running agent sessions that repeatedly recompute a large branch/session changeset (after tool edits and each turn completion) retain many historical copies of every ChangesetFile until 1,000 later actions evict them; reconnecting clients can also receive all relevant obsolete snapshots. This can materially increase Agent Host heap/GC and reconnect latency for repositories with tens or hundreds of changed files.

**Evidence:** \_publishChangesetDiffs is reached by branch, session, uncommitted, turn, compare, and persisted-restore paths. Tool edits schedule branch/session (and subscribed turn) recomputes after a 5s debounce, while every turn completion schedules fresh static recomputes. ProtocolServerHandler pushes every emitted envelope into \_replayBuffer, caps only envelope count at 1,000, and retains it until FIFO eviction or shutdown; reconnect iterates and returns every relevant retained envelope. The new action's files array is therefore retained as a complete snapshot on every successful recompute.

**Suggested direction:** Before storing replay actions, coalesce a new ChangesetContentChanged with older buffered content snapshots for the same channel (while preserving required ordering with later incremental/status actions), or enforce a byte/file-entry budget and fall back to a fresh state snapshot when replay no longer fits. This preserves the batched live update without retaining hundreds of superseded full lists.

### Scenario 2: Protocol reconnect and replay of changeset updates

- Critical path: Reconnect restores subscriptions, then either scans buffered envelopes newer than lastSeenServerSeq and returns them in one replay response, or returns fresh snapshots when the requested sequence predates the buffer. Constructing and sending this response is on reconnect's critical path.
- Scaling input: Number of buffered recomputes R, files per full snapshot N, relevant subscriptions, and gap since the client's last seen sequence.
- Effective concurrency: Subscription restoration uses Promise.all across requested subscriptions; replay-buffer scanning and action collection are synchronous. No limiter or coalescer removes superseded changeset snapshots.
- Cache behavior: The replay cache is warm across connections for the Agent Host lifetime, capped at 1,000 envelopes and cleared only at disposal. A cold/too-old reconnect falls back to current snapshots; an in-range reconnect replays every relevant retained full snapshot.
- Mechanism confidence: High: replay retention, cap, scan, and changed payload cardinality are directly established.
- Magnitude uncertainty: Reconnect gaps and changed-file counts vary, so latency severity is workload-dependent; retained-memory amplification occurs even without reconnect.
- Expensive boundaries:
  - network at <code>src/vs/platform/agentHost/node/protocolServerHandler.ts \_restoreReconnectSubscriptions</code>: Return a JSON-RPC reconnect response containing all relevant buffered actions; cardinality: Up to the relevant subset of 1,000 envelopes; changed content envelopes each carry N files, so serialized entries can scale as O(R×N).
    - Introduced by diff: false; previous behavior: Reconnect used the same boundary and envelope cap, but each buffered file-set envelope carried one file, limiting retained/replayed file entries to roughly the envelope count.; critical-path effect: The complete replay response must be assembled and transmitted before reconnect restoration completes.
- Verdict: Reportable together with the replay-cache retention finding; coalescing superseded full snapshots or using a byte/file budget bounds both heap and reconnect serialization.
