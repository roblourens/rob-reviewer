### 1. [medium] Coalesce superseded chat working-set restores

**Finding ID:** `PERF-328D6B0DA93D`  
**Location:** <code>src/vs/sessions/contrib/layout/browser/baseSessionLayoutController.ts:512</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>missing-coalescing</code>  
**Resource:** CPU work, editor-group/DOM reconstruction, and editor reopen operations  
**Scaling:** A burst of N chat selections queues N complete working-set applications; each application scales with the groups and editors in that owner's snapshot, and the final selected chat waits behind all N-1 obsolete restores.  
**Outcome:** Blocked final chat-switch completion, excess CPU/GC work, and visible editor churn or dropped frames during rapid navigation  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, the working-set derive was keyed only by session resource, so switching sibling chats in the same session did not enqueue editor working-set applications.  
**Changed behavior:** The derive now emits a chat owner key and the added line invokes \_applyWorkingSet for every owner transition; \_workingSetSequencer serializes all requests without replacing stale queued owners.  
**Confidence:** 0.99 — The changed key now follows activeChat, so each sibling-chat transition reaches \_applyWorkingSet. That method queues through Sequencer, which runs every task in order, and its stale-owner checks occur only after applyWorkingSet has completed. EditorParts.applyWorkingSet disposes groups, restores grid state, and reopens editors. The added test explicitly asserts that both superseded and superseding applies run to completion, eliminating uncertainty about the mechanism; only real-world editor counts and switch burst length affect magnitude.

**Causal diff evidence:** RIGHT line 512 changes restoration from session resource to the newly chat-scoped \`current.key\`, placing every sibling-chat focus change onto the full applyWorkingSet path.

Clicking or keyboard-navigating quickly across sibling chats with saved editors makes the final chat wait while intermediate, no-longer-visible chats fully tear down and reconstruct the editor area.

**Evidence:** The changed line schedules every current.key through \_applyWorkingSet. \_applyWorkingSet uses Sequencer, whose queue chains every task rather than coalescing. Its isStaleChatOwner checks are after IEditorGroupsService.applyWorkingSet. EditorParts.applyWorkingSet disposes groups, applies serialized grid state, and reopens editors. The added R4 test asserts \`\['empty', 'empty'\]\` with the message that both superseded and superseding applies must run to completion.

**Suggested direction:** Use latest-owner scheduling for pending restores (or check the captured owner snapshot before starting a queued apply) so only the active apply plus the newest requested owner can run; preserve the existing post-await stale guard for an already in-flight restore.

### 2. [medium] Avoid rebuilding every working-set snapshot on each chat switch

**Finding ID:** `PERF-271CEAC5986C`  
**Location:** <code>src/vs/sessions/contrib/layout/browser/baseSessionLayoutController.ts:302</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>serialization-allocation</code>  
**Resource:** Editor-grid snapshot objects and JSON bytes for the complete editorWorkingSets collection  
**Scaling:** Each sibling-chat focus transition performs O(E) current-grid snapshot work plus two O(W) serializations of all saved working-set state, where E is the outgoing editor tree and W is the accumulated state across retained chat owners; repeated A/B switching repeats this unchanged work every time.  
**Outcome:** Increased renderer CPU/GC pressure and synchronous chat-switch latency as the number of chats and saved editors grows  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this diff, same-session activeChat changes did not change activeSession and therefore did not call \_saveWorkingSet; working sets were rebuilt only when switching sessions or saving at shutdown.  
**Changed behavior:** The new ChatLayoutContext runOnChange handler calls \_saveWorkingSet for the previous owner on every sibling-chat owner change, even when that owner's editor set and active tab have not changed since its previous capture.  
**Confidence:** 0.98 — The added owner-change listener is specific to same-session chat transitions and directly invokes \_saveWorkingSet. That helper synchronously deletes the prior handle and saves a replacement; EditorParts.deleteWorkingSet and saveWorkingSet each call saveWorkingSets(), which JSON.stringify's the entire editorWorkingSets collection, while saveWorkingSet also serializes the current editor grid. Storage's database flush is deferred, but the snapshot construction and two full serializations happen synchronously. The only magnitude uncertainty is the typical number and size of retained chat working sets.

**Causal diff evidence:** RIGHT line 302 is inside the newly added ChatLayoutContext owner-change listener and adds \`this.\_saveWorkingSet(key)\` for sibling-chat changes; this path did not exist when ownership was session-scoped.

Rapidly switching among sibling chats with several retained editor sets repeatedly serializes the whole working-set catalog twice per switch on the UI thread, making chat navigation increasingly sluggish and allocation-heavy.

**Evidence:** At the changed line, every same-session previous.owner/current.owner transition calls \_saveWorkingSet(key). \_saveWorkingSet first calls \_deleteWorkingSet and then IEditorGroupsService.saveWorkingSet. EditorParts.deleteWorkingSet splices and calls saveWorkingSets(); saveWorkingSet builds mainPart.createState()/auxiliary state, appends it, and also calls saveWorkingSets(); saveWorkingSets synchronously JSON.stringify's the full editorWorkingSets array. IStorageService only defers the eventual backing-store flush, not these serializations.

**Suggested direction:** Track whether the focused owner's editor resources/active editor changed and reuse its existing handle when clean; when dirty, replace/update it once rather than delete-and-save two full catalog snapshots on every focus transition.

### 3. [medium] Batch working-set cleanup when removing a chat-heavy session

**Finding ID:** `PERF-062871C4F902`  
**Location:** <code>src/vs/sessions/contrib/layout/browser/baseSessionLayoutController.ts:769</code> (<code>RIGHT</code>)  
**Performance category:** <code>latency</code>  
**Mechanism family:** <code>boundary-fanout</code>  
**Resource:** CPU and temporary JSON strings for the global editor working-set catalog  
**Scaling:** Removing or archiving a session with K peer chat owners performs up to K deleteWorkingSet calls; each serializes the remaining O(K) working-set collection, producing O(K²) aggregate serialization/allocation for that lifecycle event, plus any unrelated owners in the global catalog.  
**Outcome:** Increased archive/removal latency and renderer CPU/GC pressure for sessions with many retained sibling-chat editor sets  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before chat-scoped ownership, a session had one working-set handle, so archive/removal performed at most one delete and one catalog serialization for that session.  
**Changed behavior:** The new \_forgetPeerChatState loop deletes every peer owner's working-set handle individually, and onDidChangeSessions invokes it with the complete peer-key set for an archived or removed session.  
**Confidence:** 0.97 — The new peer-cleanup method loops every owner key and calls \_deleteWorkingSet. Each unique handle reaches EditorParts.deleteWorkingSet, which immediately calls saveWorkingSets and synchronously JSON.stringify's the entire remaining global working-set array. Session removal/archive supplies all peer keys at once, so the repeated shrinking-catalog rewrites and quadratic scaling are directly established; uncertainty is limited to how many sibling chats users retain in one session.

**Causal diff evidence:** RIGHT line 769 is in the newly added peer-owner cleanup loop and invokes \`\_deleteWorkingSet(key)\` once per chat key; the pre-diff session cleanup deleted only \`session.resource\` once.

Archiving or removing a session after using many sibling chats can synchronously rewrite the full editor-working-set payload once per chat, causing a noticeable UI pause and allocation spike.

**Evidence:** The added loop calls \_deleteWorkingSet once for each key. \_deleteWorkingSet releases each unique handle through IEditorGroupsService.deleteWorkingSet. EditorParts.deleteWorkingSet splices one item and immediately calls saveWorkingSets(), whose implementation JSON.stringify's the entire editorWorkingSets array into workspace storage. onDidChangeSessions calls \_forgetPeerChatState(\_chatLayoutOwnerKeys.forgetSession(...)), so one session lifecycle event fans out across all retained peers.

**Suggested direction:** Collect all unreferenced handles for the session and remove them through a batched editor-working-set operation that persists the catalog once; if batching requires an explicit editor-groups dependency, defer or coalesce these lifecycle deletions rather than issuing one persisted delete per owner.
