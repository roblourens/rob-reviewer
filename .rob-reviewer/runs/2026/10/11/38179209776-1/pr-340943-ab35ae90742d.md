# Performance review: improve migrate with agent skill, use session tool to report results

[PR #340943](https://github.com/microsoft/vscode/pull/340943) at `ab35ae90742da5d3e4ad832ee3dbab998c14c509`

## Findings (1)

### 1. [low] Release per-session tool observables when sessions close

**Finding ID:** `PERF-A4FE06654754`  
**Location:** <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts:2540</code> (<code>RIGHT</code>)  
**Performance category:** <code>memory</code>  
**Mechanism family:** <code>cleanup-lifecycle</code>  
**Resource:** ResourceMap keys, URI objects, and settable observable objects retained by the workbench-scoped AgentHostActiveClientService  
**Scaling:** Retention grows by one \_sessionTools entry for every distinct ordinary agent-host session created during the lifetime of the workbench, including sessions that are later closed or fail to initialize.  
**Outcome:** gradually increasing retained heap and associated GC pressure in long-lived windows with many agent sessions  
**PR causality:** <code>introduced</code>  
**Previous behavior:** Before this change, ordinary ActiveClientEntry instances did not request or create per-session tool state, and the service had no \_sessionTools map retaining session resources.  
**Changed behavior:** Every ActiveClientEntry now calls observeSessionTools(sessionResource); that method calls \_getSessionTools, which allocates an observable and inserts it into \_sessionTools even when the session has no additional tools.  
**Confidence:** 0.98 — The allocation path, workbench-scoped owner, ordinary-session call frequency, and missing teardown call are directly visible in the changed code and all repository callers; only the exact bytes retained per session are uncertain.

**Causal diff evidence:** Added line 2540 calls this.\_activeClientService.observeSessionTools(sessionResource) for every newly created ActiveClientEntry, which is the allocation path that inserts an empty per-session observable into the service map.

Creating and then closing ordinary agent-host chats leaves one map entry and observable behind per session. Users who keep a window open while cycling through many chats accumulate retained session state that is no longer reachable from the handler.

**Evidence:** \_ensureActiveClientEntry invokes observeSessionTools for every agent-host session. observeSessionTools delegates to \_getSessionTools, which unconditionally stores a new observable in the singleton service's ResourceMap. Session teardown calls \_disposeActiveClientEntry and disposes only ActiveClientEntry; it never removes the service entry. Repository-wide clearSessionTools callers are limited to the migration launch/result/error paths, so ordinary sessions have no cleanup path.

**Suggested direction:** Give observation explicit lifecycle ownership (for example, return a ref-counted disposable handle and release it from \_disposeActiveClientEntry), deleting empty/unconfigured session entries when the last observer goes away while preserving configured migration tools across reconnects.

### Scenario 1: Create, use, and close ordinary agent-host chat sessions

- Critical path: Active-client state is created before the backend session can be claimed/reconciled. The added observeSessionTools call allocates session state synchronously on this path; publishing the active-client definition to the agent host remains on the claim/reconciliation path.
- Scaling input: Distinct agent-host session resources created over a long-lived workbench window; one retained \_sessionTools entry is added per resource, including sessions later disposed.
- Effective concurrency: Each session owns one ActiveClientEntry; different sessions may initialize independently. Reconciliation is debounced per entry, with no lifecycle mechanism that releases the service-level session-tools entry.
- Cache behavior: \_sessionTools acts as a URI-keyed cache. Reopening the same URI is a warm hit, but every new URI is a miss and empty entries are never evicted for ordinary sessions; migration-only clearSessionTools calls do not cover them.
- Mechanism confidence: High: every ActiveClientEntry calls the allocating observer, teardown disposes only the entry, the service is workbench-scoped, and all clear callers are migration-specific.
- Magnitude uncertainty: The retained bytes per session are small and exact real-world session counts are unknown, so severity is low; the monotonic lifetime scaling is certain.
- Expensive boundaries:
  - IPC at <code>src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts ActiveClientEntry</code>: Publish/reconcile SessionActiveClient tool and customization definitions to the agent host; cardinality: At least once per initialized session and again when observed active-client state changes; debounced per session.

- Verdict: Reportable cleanup-lifecycle regression: ordinary sessions leave URI and observable state retained indefinitely.
