### Scenario 1: Local Copilot Agent Host startup, settings synchronization, and model catalog publication

- Critical path: Agent-host enablement starts the root-config forwarder; values that differ from hydrated root state cross the local agent-host protocol before the host observes them. Existing model enumeration must complete before the catalog is published. Ensemble metadata transformation is synchronous after enumeration. A user setting transition that enables HydraFusion v2 can require the existing Copilot client to restart once all active turns are idle.
- Scaling input: Two new root-config keys; model publication scales linearly with the effective CAPI catalog, normally tens of models. Host root-config handling also inspects existing sessions, but the added actions are constant-cardinality and settings changes are rare.
- Effective concurrency: The forwarder evaluates each key independently and equality-gates dispatches. Model refreshes use the existing in-flight scheduling/retry mechanism. Client restart requests are deferred around active work and coalesced through pending restart state rather than launched concurrently.
- Cache behavior: Warm root state suppresses structurally equal key dispatches. The fetched CAPI catalog remains in \_capiModels and is transformed in memory on publication; no new model-list cache miss is introduced. Empty/error model refresh behavior is unchanged.
- Mechanism confidence: High confidence that two bounded IPC keys and a possible intentional setting-transition restart are added; high confidence no per-model boundary fan-out is added.
- Magnitude uncertainty: Exact local IPC and restart duration varies by machine and catalog size, but cardinality and restart coalescing are directly established.
- Expensive boundaries:

### Scenario 2: Opening, rendering, and changing the model picker with Ensemble/HydraFusion tiers

- Critical path: Opening the picker synchronously scans the already-loaded model list, builds destinations/cards, and renders DOM. Selection normalization runs when the selected-model observable or entitlement changes. Telemetry logging is synchronous but globally deduplicated; a compatibility config update is launched asynchronously and does not block normalization.
- Scaling input: Effective model-list cardinality, typically tens; tier choices and routing alternatives are bounded to a few entries. Added list scans are O(models), while card merge work is over two tiers and up to two routing alternatives.
- Effective concurrency: Model configuration edits are serialized per model with SequencerByKey. The editor-scoped configuration store suppresses no-op persistence; telemetry triggers are deduplicated per telemetry service/window.
- Cache behavior: Models and configuration schemas are in memory. Per-editor model configuration is cached after first read; no-op writes are suppressed. Experiment-trigger state is retained in a WeakMap for the window, making later picker opens warm/no-op.
- Mechanism confidence: High confidence in the UI call paths, telemetry deduplication, per-model sequencer, and persistence no-op guard from direct implementation inspection.
- Magnitude uncertainty: Model counts and DOM render time vary, but routing alternatives are fixed and the new scans do not alter asymptotic picker behavior.
- Expensive boundaries:
